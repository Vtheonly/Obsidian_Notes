# 4.9. Alternative Algorithms: ILP, GA, SA, Tabu

> [!abstract] What this note teaches you
> V2 picked CP-SAT, but it's not the only option. This note compares CP-SAT to Integer Linear Programming (ILP), Genetic Algorithms (GA), Simulated Annealing (SA), and Tabu Search — and explains why each was rejected as the primary solver (and where each is used as a fallback).

## The algorithm comparison table

| Algorithm | Guarantees | Cost | Convergence proof | Used in V2 |
|---|---|---|---|---|
| **Greedy first-fit** | Feasibility only, no optimality | O(poly) | No | V1 only; V2 rejects |
| **CP-SAT (OR-Tools)** | Proven optimal OR proven infeasible OR best-effort | Exponential worst case | Yes (given enough time) | **V2 primary** |
| **ILP (Gurobi/CPLEX)** | Same as CP-SAT | $$$ license | Yes | Rejected (cost, big-M) |
| **Genetic Algorithm** | No convergence guarantee | O(pop × gen) | No | Rejected |
| **Simulated Annealing** | Probabilistic convergence | O(iterations) | Theoretically yes (with slow cooling) | V2 fallback level 5 (polish) |
| **Tabu Search** | No optimality proof | O(iterations × neighborhood) | No | V2 fallback level 5 |

## ILP (Integer Linear Programming)

ILP models the problem as linear constraints over integer variables, solved via branch-and-bound with LP relaxation. Commercial solvers (Gurobi, CPLEX) are extremely fast.

**Why V2 rejects ILP as primary:**
- **License cost.** Gurobi is $10k+/year per production instance. CP-SAT is free.
- **Big-M reformulations.** Conditional constraints like "if `x[m,c]=1` then `y[m,r,c]=1`" require:
  $$y_{m,r,c} \leq x_{m,c} + M(1 - x_{m,c})$$
  where $M$ is a large constant. The LP relaxation of this is weak, leading to many branch-and-bound iterations.
- **Not materially better on timetabling benchmarks.** CP-SAT won ITC 2019; Gurobi won some MIP categories but not timetabling specifically.

**Where ILP could be useful:** if your organization already has a Gurobi license and you have a strong operations research team, ILP is a reasonable choice. For most organizations, CP-SAT is the better default.

## Genetic Algorithms (GA)

GAs maintain a population of candidate solutions, evolve them via crossover (combine two parents) and mutation (random changes), and select the fittest. They are inspired by natural selection.

**Why V2 rejects GA:**
- **No convergence guarantee.** You don't know when to stop. CP-SAT stops when it proves optimality or hits the time budget.
- **Hard to tune.** Mutation rate, population size, crossover operator, selection pressure — each must be tuned to the problem instance. Tuning one instance doesn't generalize.
- **Cannot prove infeasibility.** GA finding no feasible individual after 10,000 generations tells you nothing — maybe the problem is infeasible, maybe GA just didn't find it.
- **Worse than CP-SAT on standard timetabling benchmarks.** ITC winners are CP-SAT-based.

**Where GA could be useful:** if your problem has a smooth fitness landscape (small changes produce small fitness changes) and no hard constraints. Exam scheduling has the opposite — most mutations produce infeasible solutions.

## Simulated Annealing (SA)

SA is a local search metaheuristic inspired by metallurgy. It starts with a feasible solution, makes small random changes, and accepts worse solutions with probability $e^{-\Delta/T}$ where $T$ decreases over time.

**Why V2 rejects SA as primary:**
- **Polish algorithm, not a feasibility finder.** SA needs a feasible starting point. If you can't find one (which is the hard part), SA can't help.
- **No optimality proof.** SA cannot prove it found the optimum.
- **Cannot prove infeasibility.** Same as GA.

**Where V2 uses SA:** as a *polish* step after CP-SAT finds a feasible solution. CP-SAT might return `FEASIBLE` after 30s; running SA for another 10s can sometimes improve the objective by 5–10%. V2's fallback level 5 mentions this combination.

## Tabu Search

Tabu is a local search with memory. It maintains a "tabu list" of recently-visited solutions (or moves) and refuses to revisit them, forcing exploration of new areas.

**Why V2 rejects tabu as primary:** same reasons as SA — polish algorithm, no optimality proof, no infeasibility proof.

**Where V2 uses tabu:** fallback level 5 (see [[4.8. The Fallback Strategy]]). When CP-SAT cannot find a feasible solution after all relaxations, V2 falls back to "greedy + tabu search" — greedy first-fit produces a (possibly infeasible) starting point, tabu search tries to repair it.

## Hybrid CP-SAT + SA

The best practical approach for large scheduling problems:

1. Run CP-SAT with a moderate time budget (30s).
2. If CP-SAT returns `FEASIBLE` (not `OPTIMAL`), run SA for 10s on the CP-SAT solution to polish it.
3. If CP-SAT returns `INFEASIBLE` or `UNKNOWN`, fall through to the relaxation strategy.

V2 doesn't implement this hybrid (CP-SAT alone is sufficient for the current scale), but it's the natural next step if max-scale performance is insufficient.

## Graph coloring (Kempe chains, DSATUR)

For pure slot-assignment (no room/professor optimization), graph coloring algorithms are competitive. DSATUR (degree-of-saturation) is a greedy coloring heuristic that outperforms naive greedy.

**Why V2 doesn't use them:** exam scheduling is not pure coloring. It includes room assignment, professor assignment, capacity, equipment, and fairness — none of which are coloring problems. CP-SAT handles all of them in one model.

## Why CP-SAT won

CP-SAT was chosen because it is the **only** algorithm that simultaneously:

1. **Finds feasible solutions** when they exist.
2. **Proves infeasibility** when they don't (so you know to relax constraints).
3. **Optimizes soft constraints** with a weighted objective.
4. **Proves optimality** when given enough time.
5. **Is free** (Apache 2.0 license).
6. **Has won international timetabling competitions** (ITC, PATAT).

No other algorithm checks all 6 boxes.

## Common junior developer mistakes

- **Picking the algorithm you know.** If you know GA, you'll reach for GA even when CP-SAT is better. Learn the alternatives.
- **Using ILP for conditional constraints without big-M.** CP-SAT's `OnlyEnforceIf` is native; ILP's big-M is a workaround.
- **Treating SA as a primary solver.** SA polishes; it doesn't find feasible solutions from scratch.
- **Forgetting the fallback.** No algorithm works on every instance. Have a degradation path.
- **Not benchmarking on production-sized instances.** Algorithm comparisons on toy instances are misleading.
