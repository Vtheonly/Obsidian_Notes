# 7.2. The GenerateScheduleJob Lifecycle

> [!abstract] What this note teaches you
> The complete end-to-end trace of a V2 scheduling run, from HTTP request to persisted schedule. This note ties together every component from chapters 4, 5, 6, and 7 into one narrative.

## The full pipeline

```mermaid
sequenceDiagram
    participant UI as Streamlit UI
    participant API as Laravel API
    participant Handler as GenerateScheduleHandler
    participant Redis as Redis
    participant Queue as scheduling queue
    participant Job as GenerateScheduleJob
    participant DB as Postgres
    participant Solver as Python CP-SAT
    
    UI->>API: POST /sessions/{id}/generate
    API->>API: FormRequest authorize + validate
    API->>Handler: handle(GenerateScheduleCommand)
    Handler->>Redis: SET NX EX lock:scheduling:tid:pid
    Redis-->>Handler: acquired
    Handler->>Queue: dispatch(GenerateScheduleJob)
    Handler-->>API: return
    API-->>UI: 202 Accepted + ScheduleRun ID
    
    Queue->>Job: handle()
    Job->>DB: pg_advisory_lock(session_id)
    Job->>DB: REFRESH MATERIALIZED VIEW mv_module_conflicts
    Job->>Solver: HTTP POST /api/v1/schedule/optimize
    Solver->>Solver: build model, solve (30-120s)
    Solver-->>Job: {status, allocations}
    Job->>DB: DB::transaction { soft-delete old; insert new }
    Job->>DB: UPDATE schedule_runs SET statut='succes'
    Job->>DB: event(ScheduleGenerated)
    Job->>DB: pg_advisory_unlock(session_id)
    Job->>Redis: DEL lock:scheduling:tid:pid
    
    loop poll every 2s
        UI->>API: GET /schedule-runs/{id}
        API-->>UI: {statut: 'succes', ...}
    end
```

## Step-by-step

### Step 1: HTTP request

The Streamlit admin clicks "Generate schedule":

```python
run = api.post(f"/sessions/{session['id']}/generate", json={
    'algorithm': 'cp_sat',
    'max_exams_per_day': max_exams,
    'timeout_seconds': timeout,
})
st.session_state.current_run_id = run['id']
```

### Step 2: Form Request validation

`GenerateScheduleRequest::authorize()` checks `tokenCan('schedule:write')`. `rules()` validates the JSON body. See [[5.6. Form Requests and Validation]].

### Step 3: Handler acquires Redis lock

```php
$acquired = $this->repository->acquireLock($command->tenantId, $command->periodId, 300);
if (!$acquired) {
    throw new ConcurrencyLockException("An optimization run is already in progress.");
}
```

This is the first layer of mutual exclusion — see [[7.3. Distributed Locks Redis vs Advisory]].

### Step 4: Handler dispatches job

```php
OptimizeScheduleJob::dispatch(
    $tenantId, $periodId, $command->maxExamsPerDay, $command->allowSplitRooms
)->onQueue('scheduling');
```

The job is enqueued to the `scheduling` queue. Horizon picks it up.

### Step 5: HTTP returns 202

```json
{
  "message": "Schedule generation dispatched.",
  "status": "pending",
  "run_id": 42
}
```

The Streamlit UI stores `run_id` and starts polling.

### Step 6: Job acquires advisory lock

```php
DB::statement("SELECT pg_advisory_lock(?)", [$this->sessionId]);
```

This is the second layer — DB-level mutual exclusion. Even a manual `psql` session trying to schedule the same session will block.

### Step 7: Refresh conflict matrix

```php
DB::statement("REFRESH MATERIALIZED VIEW CONCURRENTLY mv_module_conflicts");
```

Ensures the solver sees the latest inscriptions. See [[3.6. Materialized Views and Refresh Strategies]].

### Step 8: Load solver input

```php
$exams = Exam::where('academic_period_id', $periodId)
    ->where('is_locked', false)
    ->with('module.inscriptions')
    ->get();
$rooms = Room::where('is_active', true)->orderBy('exam_capacity', 'desc')->get();
$timeslots = Timeslot::where('academic_period_id', $periodId)->get();
```

### Step 9: Call Python solver via HTTP

```php
$response = Http::withHeaders([
    'X-Tenant-Signature' => hash_hmac('sha256', $this->tenantId, config('app.key')),
])->timeout(300)
  ->post(config('services.solver.url') . '/api/v1/schedule/optimize', $payload);

if ($response->failed()) {
    throw new \RuntimeException("Solver error: " . $response->status());
}
$results = $response->json();
```

The solver runs the CP-SAT model from [[4.6. OR-Tools Implementation in Python]].

### Step 10: Persist in transaction

```php
DB::transaction(function () use ($results, $run) {
    // Soft-delete previous schedule
    Examen::where('session_id', $this->sessionId)
        ->whereNull('deleted_at')
        ->update(['deleted_at' => now(), 'statut' => 'annule']);
    
    // Insert new
    foreach ($results['allocations'] as $allocation) {
        Examen::create([
            'session_id' => $this->sessionId,
            'module_id' => $allocation['module_id'],
            'creneau_id' => $allocation['timeslot_id'],
            'lieu_id' => $allocation['room_id'],
            'surveillant_principal_id' => $allocation['professor_id'],
            'nb_etudiants_prevus' => $allocation['student_count'],
            'statut' => 'planifie',
            'university_id' => $this->tenantId,
            'annee_universitaire' => $this->anneeUniversitaire,
            'created_by' => $this->userId,
        ]);
    }
    
    $run->update([
        'statut' => 'succes',
        'finished_at' => now(),
        'duration_ms' => $results['duration_ms'],
        'scheduled_count' => $results['scheduled_count'],
        'unscheduled_count' => $results['unscheduled_count'],
        'objective_value' => $results['objective_value'],
    ]);
});
```

If anything fails, the transaction rolls back — the old schedule is untouched.

### Step 11: Fire event

```php
event(new ScheduleGenerated($run));
```

Listeners update KPIs, create validation rows, invalidate caches, notify admins — see [[5.7. Laravel Events Listeners and Notifications]].

### Step 12: Release locks in `finally`

```php
} finally {
    DB::statement("SELECT pg_advisory_unlock(?)", [$this->sessionId]);
    $this->repository->releaseLock($this->tenantId, $this->periodId);
}
```

Guaranteed to run even if the job throws.

### Step 13: Frontend polls for status

```python
# Streamlit
run = api.get(f"/schedule-runs/{st.session_state.current_run_id}")
if run['statut'] == 'en_cours':
    st.spinner("Génération en cours...")
    time.sleep(2)
    st.rerun()
elif run['statut'] == 'succes':
    st.success(f"✅ {run['scheduled_count']}/{run['total_modules']} planifiés en {run['duration_ms']/1000:.1f}s")
elif run['statut'] == 'echec':
    st.error(f"Échec: {run['error_message']}")
```

## Failure modes

| Failure | What happens |
|---|---|
| Redis lock not acquired | 409 Conflict, "run already in progress" |
| Solver timeout (120s) | Job catches exception, sets `statut='echec'` with `error_message`, releases locks |
| Solver returns INFEASIBLE | Job tries fallback strategy (see [[4.8. The Fallback Strategy]]) |
| DB transaction fails | Transaction rolls back, old schedule preserved, job retries (tries=3) |
| Worker crash | Advisory lock auto-releases on session close; Redis lock expires after 300s |
| Network error to solver | Job retries (tries=3), then dead-letters |

## Common junior developer mistakes

- **No `finally` for lock release.** A thrown exception leaks the lock. Always `try/finally`.
- **Synchronous solver call inside HTTP request.** 30s+ solve blocks the request. Always async.
- **Hard-delete instead of soft-delete in the swap.** If the new schedule fails to persist, the old one is gone.
- **No `ScheduleRun` row.** Without it, the frontend has nothing to poll. Create it before dispatching.
- **Forgetting to refresh `mv_module_conflicts`.** Stale conflict matrix produces wrong schedules.
