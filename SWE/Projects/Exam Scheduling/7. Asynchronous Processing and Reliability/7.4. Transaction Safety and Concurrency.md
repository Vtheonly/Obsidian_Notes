# 7.4. Transaction Safety and Concurrency

> [!abstract] What this note teaches you
> V1's `scheduling_service.clear()` + `scheduling_service.generate()` was two separate RPCs — if `clear()` succeeded and `generate()` failed, the schedule was gone. V2 wraps the swap in a single `DB::transaction`, soft-deletes the old schedule, and inserts the new one atomically. This note is the V2 transaction strategy.

## What a transaction is

A **transaction** is a unit of work that either fully completes (COMMIT) or fully rolls back (ROLLBACK). Postgres provides ACID guarantees:
- **A**tomicity — all or nothing.
- **C**onsistency — the database remains in a valid state.
- **I**solation — concurrent transactions don't interfere.
- **D**urability — committed data survives crashes.

## The V2 schedule-swap transaction

```php
DB::transaction(function () use ($result, $run) {
    // 1. Soft-delete previous schedule
    Examen::where('session_id', $this->sessionId)
        ->whereNull('deleted_at')
        ->update(['deleted_at' => now(), 'statut' => 'annule']);
    
    // 2. Insert new schedule
    foreach ($result->exams as $exam) {
        Examen::create([
            'session_id' => $this->sessionId,
            'module_id' => $exam['module_id'],
            'creneau_id' => $exam['creneau_id'],
            'lieu_id' => $exam['lieu_id'],
            'surveillant_principal_id' => $exam['surveillant_principal_id'],
            'nb_etudiants_prevus' => $exam['nb_etudiants_prevus'],
            'statut' => 'planifie',
            'university_id' => $this->tenantId,
            'annee_universitaire' => $this->anneeUniversitaire,
            'created_by' => $this->userId,
            'version' => 1,
        ]);
    }
    
    // 3. Update the ScheduleRun row
    $run->update([
        'statut' => 'succes',
        'finished_at' => now(),
        'duration_ms' => $result->duration_ms,
        'scheduled_count' => $result->scheduled,
        'unscheduled_count' => $result->unscheduled,
        'objective_value' => $result->objective,
    ]);
});
```

If step 2 fails (e.g. constraint violation on one exam), the entire transaction rolls back:
- The soft-delete is undone (old schedule rows have `deleted_at = NULL` again).
- The new exam rows are not inserted.
- The `ScheduleRun` update is not applied.

The old schedule is **untouched**. This is the critical property V1 lacked.

## V1's transaction failure

V1's flow:

```python
# 1. Clear (separate RPC)
scheduling_service.clear(session_id)  
# → DELETE FROM examens WHERE creneau_id IN (SELECT id FROM creneaux WHERE session_id = ?)

# 2. Generate (separate RPC)
result = scheduling_service.generate(session_id, max_exams_per_day)
# → CALL generate_schedule(...)
```

If `clear()` succeeds and `generate()` fails:
- The old schedule is **gone** (DELETEd).
- The new schedule is **partial or empty**.
- There is no rollback. The session is in a broken state.

V1's `generate_schedule()` PL/pgSQL function *was* atomic (it ran in one transaction), but the `clear()` + `generate()` sequence was not.

## Why soft-delete + insert beats hard-delete + insert

Even within a single transaction, soft-delete is safer than hard-delete:

```sql
-- Hard delete (V1):
DELETE FROM examens WHERE session_id = ?;
-- If the transaction fails, ROLLBACK restores the rows.
-- But if the transaction succeeds, the old rows are gone forever.

-- Soft delete (V2):
UPDATE examens SET deleted_at = NOW(), statut = 'annule' 
WHERE session_id = ? AND deleted_at IS NULL;
-- If the transaction fails, ROLLBACK restores deleted_at = NULL.
-- If the transaction succeeds, the old rows are still there (soft-deleted) for audit/rollback.
```

The soft-delete pattern means you can **roll back to yesterday's schedule** by un-soft-deleting the rows:

```sql
-- "Undo last generation"
UPDATE examens SET deleted_at = NULL, statut = 'planifie'
WHERE session_id = ? AND deleted_at IS NOT NULL
  AND deleted_at > NOW() - INTERVAL '1 hour';
```

V1 had no such capability — the old schedule was hard-deleted.

## `DB::transaction` vs `DB::beginTransaction`

Laravel offers two APIs:

### `DB::transaction(callback)` (preferred)

```php
DB::transaction(function () {
    // ... work ...
});
```

Automatically commits on success, rolls back on exception. The callback can return a value, which `DB::transaction` returns.

### `DB::beginTransaction` + manual commit/rollback

```php
DB::beginTransaction();
try {
    // ... work ...
    DB::commit();
} catch (\Throwable $e) {
    DB::rollBack();
    throw $e;
}
```

More verbose, but necessary when you need to do non-DB work between DB operations (e.g. calling an external API).

V2 uses `DB::transaction(callback)` for the schedule swap (pure DB work) and `beginTransaction` for the handler (which dispatches a job mid-transaction — see [[7.2. The GenerateScheduleJob Lifecycle]]).

## Isolation levels

Postgres defaults to **Read Committed** isolation, which means:
- A SELECT sees only data committed before the SELECT started.
- Two concurrent UPDATEs to the same row serialize (one waits for the other).

For the schedule swap, Read Committed is sufficient because:
- The advisory lock (see [[7.3. Distributed Locks Redis vs Advisory]]) prevents concurrent swaps.
- `lockForUpdate` on the rows being modified prevents lost updates.

V2 does not need Serializable isolation (the strictest level), which would add overhead and risk serialization failures.

## Nested transactions (savepoints)

`DB::transaction` calls can be nested. The inner transaction creates a savepoint; if it fails, only the savepoint rolls back, not the outer transaction.

```php
DB::transaction(function () {
    // Outer transaction
    
    DB::transaction(function () {
        // Inner transaction (savepoint)
        // If this throws, only this rolls back; outer continues
    });
    
    // Outer continues
});
```

V2 uses this pattern when inserting exams: each exam insert is wrapped in a savepoint so one bad row doesn't abort the entire batch.

## Common junior developer mistakes

- **Multiple RPCs where one transaction would do.** V1's `clear()` + `generate()` was two RPCs. Combine into one transaction.
- **Hard-delete before insert.** Soft-delete instead — preserves the old state for audit/rollback.
- **Forgetting `lockForUpdate` before UPDATE.** Without it, another transaction can modify the row between your SELECT and UPDATE.
- **Long-running transactions.** The longer the transaction, the more it blocks others. Keep transactions short.
- **Transactions spanning external calls.** Calling an HTTP API inside a transaction holds the transaction open during the network call. Bad. Do external calls outside the transaction.
- **Not handling serialization failures.** At higher isolation levels, transactions can fail with "could not serialize access". Retry them.
