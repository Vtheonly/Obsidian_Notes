# 10.6. The pg-cron Scheduler for Background DB Jobs

> [!abstract] What this note teaches you
> Some jobs are best run inside Postgres, not in Laravel. V2 uses `pg_cron` for: nightly materialized view refresh, yearly partition creation, and retention purges. This note is the `pg_cron` setup and the 4 V2 jobs.

## What `pg_cron` is

`pg_cron` is a PostgreSQL extension that runs scheduled SQL jobs inside the database. It's like `cron` for Postgres.

```sql
CREATE EXTENSION IF NOT EXISTS pg_cron;

-- Schedule a job
SELECT cron.schedule(
    'job_name',           -- human-readable name
    '* * * * *',          -- cron schedule
    'SELECT 1;'           -- SQL to run
);

-- Unschedule
SELECT cron.unschedule('job_name');

-- View jobs
SELECT * FROM cron.job;

-- View job history
SELECT * FROM cron.job_run_details ORDER BY start_time DESC LIMIT 10;
```

## Why use `pg_cron` instead of Laravel's scheduler

| Criterion | `pg_cron` | Laravel Scheduler |
|---|---|---|
| Where it runs | Inside Postgres | Inside a Laravel worker |
| SQL-only jobs (MV refresh, partition create) | ✅ Native | Awkward (wrap in `DB::statement`) |
| Cross-database jobs | ❌ One DB per pg_cron | ✅ Can connect to multiple DBs |
| Application-logic jobs | ❌ Bad fit | ✅ Native |
| Monitoring | `cron.job_run_details` table | Horizon dashboard |
| HA | Single-point per DB | Laravel workers scale horizontally |

V2 uses `pg_cron` for jobs that are fundamentally SQL (MV refresh, partition creation) and Laravel Scheduler for jobs with application logic (notifications, exports).

## The 4 V2 `pg_cron` jobs

### 1. Nightly MV refresh

```sql
SELECT cron.schedule(
    'refresh_enrollments',
    '0 2 * * *',  -- daily at 02:00
    'REFRESH MATERIALIZED VIEW CONCURRENTLY mv_module_enrollments'
);
```

See [[10.4. The Materialized View Refresh Strategy]].

### 2. Yearly partition creation

```sql
-- Function to create next year's partitions
CREATE OR REPLACE FUNCTION create_next_year_partitions() RETURNS VOID AS $$
DECLARE
    next_year TEXT;
    next_year_start DATE;
    next_year_end DATE;
BEGIN
    next_year := EXTRACT(YEAR FROM NOW() + INTERVAL '1 year')::TEXT;
    next_year_start := (next_year || '-01-01')::DATE;
    next_year_end := next_year_start + INTERVAL '1 year';
    
    -- inscriptions (LIST by annee_universitaire)
    EXECUTE format(
        'CREATE TABLE IF NOT EXISTS inscriptions_%s PARTITION OF inscriptions FOR VALUES IN (%L)',
        REPLACE(next_year, '-', '_'),
        next_year || '-' || (next_year::INT + 1)::TEXT
    );
    
    -- examens (LIST by annee_universitaire)
    EXECUTE format(
        'CREATE TABLE IF NOT EXISTS examens_%s PARTITION OF examens FOR VALUES IN (%L)',
        REPLACE(next_year, '-', '_'),
        next_year || '-' || (next_year::INT + 1)::TEXT
    );
    
    -- audit_log (RANGE by created_at)
    EXECUTE format(
        'CREATE TABLE IF NOT EXISTS audit_log_y%s PARTITION OF audit_log FOR VALUES FROM (%L) TO (%L)',
        next_year,
        next_year_start,
        next_year_end
    );
END;
$$ LANGUAGE plpgsql;

-- Schedule it for January 1st at 00:00
SELECT cron.schedule(
    'create_next_year_partitions',
    '0 0 1 1 *',  -- January 1st at midnight
    'SELECT create_next_year_partitions()'
);
```

This ensures next year's partitions exist before January 1st. Without it, all INSERTs on Jan 1 go to the `DEFAULT` partition, which becomes a bottleneck.

### 3. Audit log purge (7-year retention)

```sql
SELECT cron.schedule(
    'purge_old_audit',
    '0 3 1 1 *',  -- January 1st at 03:00
    $$
    DELETE FROM audit_log 
    WHERE created_at < NOW() - INTERVAL '7 years';
    $$
);
```

GDPR requires data minimization — don't keep PII longer than necessary. 7 years is the typical retention for educational records.

### 4. Soft-deleted records purge

```sql
SELECT cron.schedule(
    'purge_deleted_etudiants',
    '0 3 1 * *',  -- 1st of every month at 03:00
    $$
    DELETE FROM etudiants 
    WHERE deleted_at IS NOT NULL 
      AND deleted_at < NOW() - INTERVAL '5 years';
    $$
);
```

Soft-deleted records are kept for 5 years (for audit/historical reference), then hard-purged.

## Monitoring `pg_cron` jobs

```sql
-- All jobs
SELECT jobid, jobname, schedule, active FROM cron.job;

-- Recent runs
SELECT 
    jobname,
    start_time,
    end_time,
    status,
    return_message
FROM cron.job_run_details
ORDER BY start_time DESC
LIMIT 20;

-- Failed runs in the last 24h
SELECT jobname, start_time, return_message
FROM cron.job_run_details
WHERE status = 'failed'
  AND start_time > NOW() - INTERVAL '24 hours';
```

V2 sets up a Prometheus alert on failed `pg_cron` jobs:

```yaml
# prometheus alerts
- alert: PgCronJobFailed
  expr: pg_cron_failed_jobs_total > 0
  for: 5m
  labels:
    severity: warning
  annotations:
    summary: "pg_cron job failed"
```

## Common junior developer mistakes

- **Forgetting to install `pg_cron` in `shared_preload_libraries`.** The extension requires a server-level config change and restart:
  ```ini
  # postgresql.conf
  shared_preload_libraries = 'pg_cron'
  cron.database_name = 'univexam'
  ```
- **Not creating next year's partitions.** January 1 comes every year. Automate it.
- **No retention policy.** Audit logs and soft-deleted records accumulate forever. Define retention and automate purges.
- **Using `pg_cron` for application-logic jobs.** If the job needs Laravel models, events, or HTTP calls, use Laravel Scheduler, not `pg_cron`.
- **Not monitoring failed jobs.** A failed `pg_cron` job is silent — no alert unless you set one up.
- **`pg_cron` on a read replica.** `pg_cron` runs on the primary. Don't try to schedule jobs on replicas (they're read-only).
