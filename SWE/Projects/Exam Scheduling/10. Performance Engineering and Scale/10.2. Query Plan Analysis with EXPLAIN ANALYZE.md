# 10.2. Query Plan Analysis with EXPLAIN ANALYZE

> [!abstract] What this note teaches you
> V1's `detect_student_time_conflicts` was an O(N²) self-join that wouldn't finish at 100k students. V2 replaces it with a `GROUP BY ... HAVING COUNT(*) > 1` O(N log N) query. This note teaches you how to read `EXPLAIN ANALYZE` output and spot the same kind of inefficiencies.

## The V1 slow query

```sql
-- V1: detect_student_time_conflicts (O(N²) self-join)
WITH student_exams AS (
    SELECT et.id AS etudiant_id, et.matricule,
           m.id AS module_id, m.nom AS module_nom,
           c.date_examen, c.heure_debut
    FROM etudiants et
    JOIN inscriptions i ON et.id = i.etudiant_id
    JOIN modules m ON i.module_id = m.id
    JOIN examens e ON m.id = e.module_id
    JOIN creneaux c ON e.creneau_id = c.id
    WHERE c.session_id = p_session_id
      AND i.statut IN ('inscrit', 'rattrapage')
      AND e.statut != 'annule'
)
SELECT se1.etudiant_id, se1.date_examen, se1.heure_debut, 
       se1.module_nom, se2.module_nom
FROM student_exams se1
JOIN student_exams se2 ON 
    se1.etudiant_id = se2.etudiant_id
    AND se1.date_examen = se2.date_examen
    AND se1.heure_debut = se2.heure_debut
    AND se1.module_id < se2.module_id;
```

At 13k students × 6 exams each = 78k rows in the CTE. The self-join produces ~6 billion row comparisons before filtering.

At 100k students × 6 exams = 600k rows. The self-join produces **360 billion comparisons**. **Will not finish.**

## The V2 fix: GROUP BY + HAVING

```sql
-- V2: O(N log N) — group by (student, date, time) and find groups with > 1 row
SELECT etudiant_id, date_examen, heure_debut, 
       COUNT(*) AS exam_count,
       ARRAY_AGG(module_nom) AS modules
FROM (
    SELECT et.id AS etudiant_id, m.nom AS module_nom,
           c.date_examen, c.heure_debut
    FROM etudiants et
    JOIN inscriptions i ON et.id = i.etudiant_id
    JOIN modules m ON i.module_id = m.id
    JOIN examens e ON m.id = e.module_id
    JOIN creneaux c ON e.creneau_id = c.id
    WHERE c.session_id = p_session_id
      AND i.statut IN ('inscrit', 'rattrapage')
      AND e.statut != 'annule'
) student_exams
GROUP BY etudiant_id, date_examen, heure_debut
HAVING COUNT(*) > 1;
```

The GROUP BY is O(N log N) (sort + group). At 600k rows, this finishes in milliseconds.

## Reading `EXPLAIN ANALYZE`

```sql
EXPLAIN ANALYZE
SELECT * FROM etudiants 
WHERE university_id = 42 AND deleted_at IS NULL;
```

Output:

```
Index Scan using idx_etudiants_university on etudiants  (cost=0.42..85.34 rows=1245 width=256) (actual time=0.023..1.234 rows=1245 loops=1)
  Index Cond: (university_id = 42)
  Filter: (deleted_at IS NULL)
  Rows Removed by Filter: 3
Planning Time: 0.245 ms
Execution Time: 1.412 ms
```

### What each line means

- **`Index Scan using idx_etudiants_university`** — used the named index. Good.
- **`Seq Scan`** — sequential scan of the whole table. Bad on large tables.
- **`Bitmap Index Scan + Bitmap Heap Scan`** — index used to build a bitmap, then heap fetched. Good for medium selectivity.
- **`Index Only Scan`** — index used, heap not fetched (covering index). Best.
- **`cost=0.42..85.34`** — planner's cost estimate. Lower is better, but absolute numbers aren't meaningful; compare relative.
- **`rows=1245` (estimated) vs `rows=1245` (actual)** — estimate matches actual. Good.
- **`Rows Removed by Filter: 3`** — 3 rows were fetched from the index but filtered out by `deleted_at IS NULL`. Low is good.
- **`Planning Time: 0.245 ms`** — time to generate the plan.
- **`Execution Time: 1.412 ms`** — time to run the query. The number you care about.

### Red flags

- **`Seq Scan`** on a large table — missing index.
- **`Rows Removed by Filter: 1000000`** — index is not selective enough.
- **`Hash Join`** with a huge hash table — memory pressure.
- **`Nested Loop`** with high row counts on both sides — O(N²) join.
- **`Sort Method: external merge Disk`** — sort spilled to disk. Increase `work_mem` or add an index for the sort.
- **`Execution Time: 30000 ms`** — 30 seconds. Unacceptable for a web request.

## The V1 self-join plan

```
Nested Loop  (cost=10000.00..50000000.00 rows=600000000 width=128) (actual time=...)
  Join Filter: (se1.etudiant_id = se2.etudiant_id AND se1.date_examen = se2.date_examen AND ...)
  Rows Removed by Join Filter: 599999400
  ->  CTE Scan on student_exams se1  (cost=0.00..12000.00 rows=600000 width=64)
  ->  CTE Scan on student_exams se2  (cost=0.00..12000.00 rows=600000 width=64)
```

The nested loop produces 600k × 600k = 360 billion comparisons. Even at 1μs each, that's 100 hours.

## The V2 GROUP BY plan

```
GroupAggregate  (cost=25000.00..28000.00 rows=600000 width=128) (actual time=45.234..123.456 rows=23 loops=1)
  Group Key: etudiant_id, date_examen, heure_debut
  Filter: (count(*) > 1)
  Rows Removed by Filter: 599977
  ->  Sort  (cost=25000.00..26000.00 rows=600000 width=64) (actual time=40.123..95.234 rows=600000 loops=1)
        Sort Key: etudiant_id, date_examen, heure_debut
        Sort Method: quicksort  Memory: 50MB
        ->  Hash Join  (cost=1000.00..20000.00 rows=600000 width=64) (actual time=...)
              ->  ... (the CTE query)
```

Sort + group is O(N log N). At 600k rows, ~120ms. Acceptable.

## How to find slow queries

### 1. Laravel Pulse

Pulse shows the slowest queries in the last hour. Check daily.

### 2. `pg_stat_statements`

```sql
SELECT query, calls, mean_exec_time, total_exec_time, rows
FROM pg_stat_statements
ORDER BY mean_exec_time DESC
LIMIT 10;
```

Shows the 10 slowest queries by mean execution time. Install via `CREATE EXTENSION pg_stat_statements;`.

### 3. Slow query log

```ini
# postgresql.conf
log_min_duration_statement = 1000  # log queries > 1 second
```

Every query slower than 1 second is logged with its duration.

## Common junior developer mistakes

- **Not running `EXPLAIN ANALYZE`.** "It's slow" isn't a diagnosis. The plan tells you why.
- **Running `EXPLAIN` without `ANALYZE`.** `EXPLAIN` shows the plan; `ANALYZE` actually runs it and shows real numbers. Always use both.
- **Trusting the planner's row estimates.** The estimate can be wrong if statistics are stale. Run `ANALYZE etudiants;` after big loads.
- **Adding indexes without measuring.** An index that doesn't help slows down writes. Measure before and after.
- **Ignoring `Rows Removed by Filter`.** If your index returns 1M rows and the filter removes 999k, your index isn't selective enough.
