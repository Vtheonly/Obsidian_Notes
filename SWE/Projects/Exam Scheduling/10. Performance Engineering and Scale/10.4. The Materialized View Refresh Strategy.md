# 10.4. The Materialized View Refresh Strategy

> [!abstract] What this note teaches you
> V2 has two materialized views with different refresh cadences: `mv_module_enrollments` nightly via `pg_cron`, and `mv_module_conflicts` before each scheduling run. This note is the operational guide — when to refresh, how to refresh, and how to handle failures.

## The two materialized views

| View | Refresh trigger | Refresh duration (13k) | Refresh duration (100k) |
|---|---|---|---|
| `mv_module_enrollments` | Nightly at 02:00 via `pg_cron` | ~5s | ~30s |
| `mv_module_conflicts` | Before each scheduling run | ~3s | ~25s |

## `mv_module_enrollments` — nightly refresh

Precomputes per-module enrollment counts for dashboards and solver input.

```sql
CREATE MATERIALIZED VIEW mv_module_enrollments AS
SELECT
    m.id AS module_id, m.code, m.nom, m.formation_id, f.departement_id,
    m.university_id, m.periode_pedagogique_id, i.annee_universitaire_id,
    COUNT(DISTINCT i.etudiant_id) FILTER (WHERE i.statut IN ('inscrit','rattrapage')) AS nb_inscrits_actifs,
    COUNT(DISTINCT i.etudiant_id) FILTER (WHERE i.statut = 'valide') AS nb_valides,
    COUNT(DISTINCT i.etudiant_id) FILTER (WHERE i.statut = 'abandonne') AS nb_abandons,
    m.duree_examen_minutes
FROM modules m
JOIN formations f ON m.formation_id = f.id
JOIN departements d ON f.departement_id = d.id
LEFT JOIN inscriptions i ON i.module_id = m.id AND i.deleted_at IS NULL
WHERE m.deleted_at IS NULL
GROUP BY m.id, m.code, m.nom, m.formation_id, f.nom, f.departement_id, d.nom,
         m.university_id, m.periode_pedagogique_id, i.annee_universitaire_id, m.duree_examen_minutes;

CREATE UNIQUE INDEX ON mv_module_enrollments (module_id, annee_universitaire_id);
CREATE INDEX ON mv_module_enrollments (university_id, departement_id);
```

Refresh schedule:

```sql
SELECT cron.schedule(
    'refresh_enrollments',
    '0 2 * * *',  -- daily at 02:00
    'REFRESH MATERIALIZED VIEW CONCURRENTLY mv_module_enrollments'
);
```

Why 02:00? Lowest traffic. The refresh takes 5–30s; even if it briefly locks reads (it shouldn't with `CONCURRENTLY`), users won't notice.

## `mv_module_conflicts` — before each run

Precomputes the pairwise module conflict graph for the solver.

```sql
CREATE MATERIALIZED VIEW mv_module_conflicts AS
SELECT
    i1.module_id AS m1, i2.module_id AS m2,
    i1.university_id, i1.annee_universitaire_id,
    COUNT(DISTINCT i1.etudiant_id) AS shared_students
FROM inscriptions i1
JOIN inscriptions i2
    ON i1.etudiant_id = i2.etudiant_id
   AND i1.module_id < i2.module_id
   AND i1.university_id = i2.university_id
   AND i1.annee_universitaire_id = i2.annee_universitaire_id
WHERE i1.statut IN ('inscrit','rattrapage')
  AND i2.statut IN ('inscrit','rattrapage')
  AND i1.deleted_at IS NULL AND i2.deleted_at IS NULL
GROUP BY i1.module_id, i2.module_id, i1.university_id, i1.annee_universitaire_id;

CREATE UNIQUE INDEX ON mv_module_conflicts (annee_universitaire_id, m1, m2);
CREATE INDEX ON mv_module_conflicts (m1);
CREATE INDEX ON mv_module_conflicts (m2);
```

Refresh trigger: inside `GenerateScheduleJob::handle`, before calling the solver:

```php
DB::statement("REFRESH MATERIALIZED VIEW CONCURRENTLY mv_module_conflicts");
```

Why before each run? Because inscriptions can change between runs (students add/drop modules). The solver must see the latest conflict graph.

## `CONCURRENTLY` requirements

`REFRESH MATERIALIZED VIEW CONCURRENTLY` requires:
1. **A unique index** on the view (so Postgres can identify rows to update).
2. **No `GROUP BY` without all columns in the unique index.** (V2's views satisfy this.)
3. **The view must be populated** (can't `CONCURRENTLY` refresh an empty view; use plain `REFRESH` first).

Without `CONCURRENTLY`:

```sql
REFRESH MATERIALIZED VIEW mv_module_enrollments;
```

This locks the view for reads during the refresh. Unacceptable in production.

## Handling refresh failures

If the refresh fails (e.g. lock timeout, OOM), the view retains its old data. The job logs the failure but continues with stale data — better than no data.

```php
try {
    DB::statement("REFRESH MATERIALIZED VIEW CONCURRENTLY mv_module_conflicts");
} catch (\Throwable $e) {
    Log::warning('Failed to refresh mv_module_conflicts, using stale data', [
        'error' => $e->getMessage(),
    ]);
    // Continue with stale data
}
```

For `mv_module_enrollments` nightly refresh, set up an alert:

```sql
-- If the nightly refresh hasn't run in 25 hours, alert
SELECT cron.schedule(
    'check_enrollments_refresh',
    '0 4 * * *',  -- daily at 04:00 (2h after the refresh)
    $$
    INSERT INTO alert_log (severity, message)
    SELECT 'warning', 'mv_module_enrollments not refreshed in 25 hours'
    WHERE NOT EXISTS (
        SELECT 1 FROM cron.job_run_details
        WHERE jobid = (SELECT jobid FROM cron.job WHERE jobname = 'refresh_enrollments')
          AND end_time > NOW() - INTERVAL '25 hours'
          AND status = 'succeeded'
    );
    $$
);
```

## The unique index requirement (deep dive)

`REFRESH MATERIALIZED VIEW CONCURRENTLY` works by:
1. Building a new version of the view in the background.
2. Comparing it to the old version row-by-row.
3. Updating changed rows in place.

For step 3 to work, Postgres needs to identify "the same row" between old and new versions. This requires a **unique index** that exists on both versions.

```sql
-- This works:
CREATE UNIQUE INDEX ON mv_module_enrollments (module_id, annee_universitaire_id);
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_module_enrollments;

-- This fails:
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_with_no_unique_index;
-- ERROR: CONCURRENTLY cannot be used when the materialized view is not populated using a unique index
```

## Common junior developer mistakes

- **Forgetting the unique index.** `CONCURRENTLY` will fail. Always create a unique index immediately after creating the view.
- **Using `REFRESH` (non-concurrent) in production.** Locks reads. Always `CONCURRENTLY`.
- **Refreshing too often.** A materialized view that refreshes every minute is basically a regular view with extra overhead. Find the right cadence.
- **Not refreshing at all.** A stale materialized view gives wrong answers confidently. Always have a refresh schedule.
- **Not handling refresh failures.** If the refresh fails silently, you're using stale data without knowing it. Log and alert.
- **Using materialized views for real-time data.** If you need real-time, use a regular view or a direct query. Materialized views are for precomputation.
