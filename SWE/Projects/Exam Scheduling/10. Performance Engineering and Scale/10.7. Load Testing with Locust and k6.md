# 10.7. Load Testing with Locust and k6

> [!abstract] What this note teaches you
> V1 had no load tests — the 45-second target was claimed in the README but never verified. V2 has two load test suites: Locust for admin workflows (100 concurrent admins) and k6 for student/professor portals (1000 concurrent students). This note is the V2 load testing strategy.

## The two load test tools

| Tool | Language | Use case | V2 target |
|---|---|---|---|
| Locust | Python | Admin workflows, complex scenarios | 100 concurrent admins |
| k6 | JavaScript (ES6) | High-volume student/professor portal | 1000 concurrent students |

Both tools:
- Run from the command line or CI.
- Generate load by simulating HTTP requests.
- Report latency percentiles, error rates, throughput.
- Support distributed execution for very high load.

## The Locust admin scenario

```python
# load-tests/locustfile.py
from locust import HttpUser, task, between, tag

class AdminUser(HttpUser):
    wait_time = between(2, 10)  # 2-10s between actions
    host = "https://staging-api.univexam.cloud"
    
    def on_start(self):
        # Login
        response = self.client.post("/auth/login", json={
            "email": "admin@test.univ.dz",
            "password": "test-password",
        })
        self.token = response.json()["token"]
        self.headers = {"Authorization": f"Bearer {self.token}"}
    
    @tag('dashboard')
    @task(3)
    def view_dashboard(self):
        """Most common action — view the KPI dashboard."""
        with self.client.get("/sessions/1/dashboard", 
                             headers=self.headers,
                             name="Dashboard") as resp:
            if resp.status_code != 200:
                resp.failure(f"Dashboard failed: {resp.status_code}")
    
    @tag('schedule')
    @task(1)
    def view_schedule(self):
        """View today's schedule."""
        with self.client.get("/sessions/1/schedule?date=2026-01-15",
                             headers=self.headers,
                             name="Schedule") as resp:
            if resp.status_code != 200:
                resp.failure(f"Schedule failed: {resp.status_code}")
    
    @tag('generate')
    @task(1)
    def generate_schedule(self):
        """Trigger a schedule generation (less frequent)."""
        with self.client.post("/sessions/1/generate",
                              headers=self.headers,
                              json={"algorithm": "cp_sat", "max_exams_per_day": 1},
                              name="Generate") as resp:
            if resp.status_code == 202:
                run_id = resp.json()["run_id"]
                # Poll for completion (don't wait long — just verify it started)
                self.client.get(f"/schedule-runs/{run_id}",
                                headers=self.headers,
                                name="Poll run status")
            else:
                resp.failure(f"Generate failed: {resp.status_code}")
    
    @tag('conflicts')
    @task(2)
    def view_conflicts(self):
        """View conflict list."""
        with self.client.get("/sessions/1/conflicts",
                             headers=self.headers,
                             name="Conflicts") as resp:
            pass  # any 2xx is fine
```

Run:

```bash
locust -f locustfile.py --headless -u 100 -r 10 --run-time 5m \
    --host https://staging-api.univexam.cloud \
    --html report.html
```

- `-u 100` — 100 concurrent users.
- `-r 10` — spawn 10 users per second (ramp-up).
- `--run-time 5m` — run for 5 minutes.

## The k6 student scenario

```javascript
// load-tests/student-portal.js
import http from 'k6/http';
import { check, sleep } from 'k6';
import { Rate } from 'k6/metrics';

const failureRate = new Rate('check_failures');

export const options = {
    stages: [
        { duration: '2m', target: 100 },   // ramp to 100
        { duration: '5m', target: 100 },   // hold 100
        { duration: '2m', target: 500 },   // ramp to 500
        { duration: '5m', target: 500 },   // hold 500
        { duration: '2m', target: 1000 },  // ramp to 1000
        { duration: '10m', target: 1000 }, // hold 1000
        { duration: '2m', target: 0 },     // ramp down
    ],
    thresholds: {
        http_req_duration: ['p(95)<500', 'p(99)<1500'],  // 95% under 500ms, 99% under 1.5s
        http_req_failed: ['rate<0.01'],                   // < 1% errors
        check_failures: ['rate<0.01'],
    },
};

export function setup() {
    // Login once, share the token
    const loginResp = http.post('https://staging-api.univexam.cloud/auth/login', JSON.stringify({
        email: 'student@test.univ.dz',
        password: 'test-password',
    }), { headers: { 'Content-Type': 'application/json' } });
    return { token: loginResp.json('token') };
}

export default function (data) {
    const headers = { Authorization: `Bearer ${data.token}` };
    
    // View own schedule
    const resp = http.get('https://staging-api.univexam.cloud/me/schedule', { headers });
    
    const ok = check(resp, {
        'status is 200': (r) => r.status === 200,
        'has exams': (r) => r.json('exams').length > 0,
    });
    
    failureRate.add(!ok);
    sleep(1 + Math.random() * 4);  // 1-5s between requests
}

export function teardown(data) {
    // Logout
    http.post('https://staging-api.univexam.cloud/auth/logout', {}, {
        headers: { Authorization: `Bearer ${data.token}` },
    });
}
```

Run:

```bash
k6 run --vus 1000 --duration 30m student-portal.js
```

## The V2 performance targets

| Scenario | Tool | Concurrency | p95 latency | Error rate |
|---|---|---|---|---|
| Admin dashboard | Locust | 100 | < 2s | < 1% |
| Schedule generation | Locust | 10 (concurrent gens) | < 45s (13k), < 5min (100k) | < 5% |
| Student schedule view | k6 | 1000 | < 500ms | < 1% |
| Conflict detection | Locust | 50 | < 5s | < 1% |

These targets are encoded as k6 `thresholds` and Locust `--exit-code-on-error` flags. If a target is missed, the load test fails the CI pipeline.

## Running load tests in CI

```yaml
# .github/workflows/load-test.yml
name: Load Test
on:
  schedule:
    - cron: '0 2 * * 0'  # weekly on Sunday at 02:00
  workflow_dispatch:  # manual trigger

jobs:
  load-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      
      - name: Setup Python
        uses: actions/setup-python@v5
        with:
          python-version: '3.12'
      
      - name: Install Locust
        run: pip install locust
      
      - name: Run Locust admin test
        run: |
          locust -f load-tests/locustfile.py --headless \
            -u 100 -r 10 --run-time 10m \
            --host https://staging-api.univexam.cloud \
            --html report-admin.html \
            --exit-code-on-error 1
      
      - name: Install k6
        run: |
          sudo gpg -k
          sudo gpg --no-default-keyring --keyring /usr/share/keyrings/k6-archive-keyring.gpg --keyserver hkp://keyserver.ubuntu.com:80 --recv-keys C5AD17C747E3415A3642D57D77C6C491D6AC1D69
          echo "deb [signed-by=/usr/share/keyrings/k6-archive-keyring.gpg] https://dl.k6.io/deb stable main" | sudo tee /etc/apt/sources.list.d/k6.list
          sudo apt-get update
          sudo apt-get install k6
      
      - name: Run k6 student test
        run: |
          k6 run --vus 1000 --duration 10m load-tests/student-portal.js
      
      - name: Upload reports
        uses: actions/upload-artifact@v4
        if: always()
        with:
          name: load-test-reports
          path: |
            report-admin.html
            report-student.html
```

Weekly automated run. Manual trigger for pre-release validation.

## Common junior developer mistakes

- **No load tests.** "It works on my laptop" is not load testing. Run them.
- **Load testing in production.** Use staging. Load tests generate artificial traffic that distorts production metrics.
- **No ramp-up.** Going from 0 to 1000 users instantly is unrealistic. Ramp up gradually.
- **Testing only happy path.** Add scenarios for login failures, 404s, 500s. The system must handle errors gracefully under load.
- **No thresholds.** "It worked" isn't a result. Define p95 latency and error rate thresholds; fail the build if missed.
- **Not testing the scheduling pipeline.** Generating schedules under load is different from reading dashboards. Test it.
- **Ignoring database load during load tests.** Use `pg_stat_statements` to see which queries the load test hits. You may find unexpected hot spots.
