# 9.1. Structured JSON Logging with PII Redaction

> [!abstract] What this note teaches you
> V1's logging was `st.error(str(e))` leaking SQL to users and unstructured `print()` statements. V2 uses Monolog with a JSON formatter, PII redaction, centralized log shipping, and log levels per environment. This note is the V2 logging strategy.

## Why structured logging

V1's logs were unstructured strings:

```
2026-01-15 10:23:45 ERROR: Student overlap detected for date 2025-01-15
2026-01-15 10:23:46 INFO: User logged in
2026-01-15 10:24:01 WARNING: schedule generation took 65 seconds
```

These are hard to search, parse, or aggregate. You can't easily find "all errors in the last hour" or "all logins by user X".

V2's logs are JSON:

```json
{
  "timestamp": "2026-01-15T10:23:45.123Z",
  "level": "error",
  "message": "Schedule generation failed",
  "context": {
    "session_id": 42,
    "user_id": 17,
    "duration_ms": 65234,
    "error_class": "SolverTimeoutException",
    "tenant_id": 3
  },
  "extra": {
    "ip": "192.168.1.100",
    "user_agent": "Mozilla/5.0...",
    "request_id": "abc-123"
  }
}
```

Structured logs can be:
- Searched by field (`level:error AND tenant_id:3`).
- Aggregated (`count by error_class`).
- Alerted on (`alert when level:critical count > 0 in 5m`).
- Parsed by log shippers (Logstash, Fluentd, Vector).

## The Monolog JSON formatter

```php
// config/logging.php
'channels' => [
    'stack' => [
        'driver' => 'stack',
        'channels' => ['stderr', 'papertrail'],
    ],
    'stderr' => [
        'driver' => 'monolog',
        'handler' => StreamHandler::class,
        'formatter' => JsonFormatter::class,
        'with' => ['stream' => 'php://stderr'],
    ],
    'papertrail' => [
        'driver' => 'monolog',
        'handler' => SyslogUdpHandler::class,
        'handler_with' => [
            'host' => env('PAPERTRAIL_HOST'),
            'port' => env('PAPERTRAIL_PORT'),
        ],
        'formatter' => JsonFormatter::class,
    ],
],
```

Every log line is a JSON object. The `stderr` channel goes to the container's stdout (captured by Docker/K8s). The `papertrail` channel ships to a centralized log service.

## PII redaction

V2 redacts PII before logging via a custom processor:

```php
// app/Logging/PiiRedactionProcessor.php
class PiiRedactionProcessor
{
    private array $redactFields = [
        'password', 'password_confirmation', 'token', 'api_key',
        'email', 'matricule', 'ine', 'date_naissance', 'telephone',
    ];
    
    public function __invoke(array $record): array
    {
        $record['message'] = $this->redactPatterns($record['message']);
        $record['context'] = $this->redactArray($record['context']);
        return $record;
    }
    
    private function redactPatterns(string $message): string
    {
        // Redact email addresses
        $message = preg_replace('/[\w.+-]+@[\w.-]+\.[a-z]+/i', '[REDACTED_EMAIL]', $message);
        // Redact matricules (ETU followed by digits)
        $message = preg_replace('/ETU\d+/i', '[REDACTED_MATRICULE]', $message);
        // Redact phone numbers (Algerian format)
        $message = preg_replace('/\+213\d{9}|\d{10}/', '[REDACTED_PHONE]', $message);
        return $message;
    }
    
    private function redactArray(array $data): array
    {
        foreach ($data as $key => $value) {
            if (in_array($key, $this->redactFields, true)) {
                $data[$key] = '[REDACTED]';
            } elseif (is_array($value)) {
                $data[$key] = $this->redactArray($value);
            }
        }
        return $data;
    }
}
```

Registered in `AppServiceProvider`:

```php
public function register(): void
{
    $this->app->extend('log', function ($logger) {
        $logger->pushProcessor(new PiiRedactionProcessor());
        return $logger;
    });
}
```

Now even if a developer writes `Log::info('User logged in', ['email' => $user->email])`, the log shows `"email": "[REDACTED]"`.

## Log levels

V2 uses the standard Monolog levels:

| Level | When to use | Example |
|---|---|---|
| `DEBUG` | Detailed diagnostic info (dev only) | "Loaded 1245 modules into solver" |
| `INFO` | Normal operations | "Schedule generated for session 42" |
| `NOTICE` | Significant but normal | "Schedule run used fallback level 2" |
| `WARNING` | Something unexpected, but recoverable | "Solver timed out, returning best-effort" |
| `ERROR` | Operation failed but app continues | "Failed to send notification email" |
| `CRITICAL` | Operation failed, app degraded | "Database connection lost" |
| `ALERT` | Action required immediately | "Disk space < 5%" |
| `EMERGENCY` | System unusable | "All workers down" |

V2's per-environment log level:
- **local:** `DEBUG` (everything).
- **staging:** `INFO` (skip DEBUG).
- **production:** `WARNING` (skip INFO and below, except for audit events which are always `INFO`).

## Custom structured log calls

```php
Log::info('schedule.generated', [
    'session_id' => $sessionId,
    'duration_ms' => $durationMs,
    'scheduled' => $scheduled,
    'unscheduled' => $unscheduled,
    'user_id' => Auth::id(),
    'tenant_id' => $request->user()->tenant_id,
    'ip' => $request->ip(),
    'request_id' => app('request.id'),
]);

Log::warning('solver.timeout', [
    'session_id' => $sessionId,
    'timeout_seconds' => 30,
    'status' => 'FEASIBLE',
]);

Log::error('db.connection_failed', [
    'host' => config('database.connections.pgsql.host'),
    'error' => $e->getMessage(),
]);
```

The first argument is a **dot-namespaced event name** (`schedule.generated`, `solver.timeout`, `db.connection_failed`). This makes log search by event type easy.

## Request ID correlation

Every HTTP request gets a unique ID, propagated to all log entries in that request:

```php
// app/Http/Middleware/AssignRequestId.php
class AssignRequestId
{
    public function handle(Request $request, Closure $next): Response
    {
        $requestId = $request->header('X-Request-ID') ?? Str::uuid()->toString();
        $request->headers->set('X-Request-ID', $requestId);
        
        app()->instance('request.id', $requestId);
        
        $response = $next($request);
        $response->headers->set('X-Request-ID', $requestId);
        return $response;
    }
}
```

The `request.id` is included in every log entry via a Monolog processor. To trace a request: search for its `request_id` and see every log line from auth → controller → service → DB → response.

## Centralized log shipping

V2 ships logs to:
- **Local file** (`storage/logs/laravel.log`) for dev.
- **stdout** for Docker/K8s (captured by the orchestrator).
- **Papertrail** (or Logflare, or ELK) for centralized search.

```bash
# Search all logs for a specific request ID in Papertrail:
"request_id:abc-123"

# Find all schedule generation failures in the last hour:
"schedule.generated AND level:error AND timestamp:>1h"

# Count errors by error_class:
"level:error GROUP BY error_class"
```

## Common junior developer mistakes

- **`Log::info("User $id logged in")`.** Use structured context: `Log::info('user.login', ['user_id' => $id])`. String interpolation is hard to search.
- **Logging PII.** Always redact. Use the processor.
- **Using `Log::error` for business-rule violations.** A user trying to validate another department's schedule is `Log::info('authorization.denied')`, not `Log::error`.
- **No request ID.** Without correlation, you can't trace a single request through the system.
- **Log level too verbose in production.** `DEBUG` in prod generates gigabytes of noise. Use `WARNING`.
- **No log rotation.** Logs grow forever. Configure `logrotate` or use centralized shipping.
