# 2.7. Trigger Abuse for Control Flow

> [!abstract] What this note teaches you
> V1 used four `BEFORE INSERT OR UPDATE` triggers on `examens` to enforce room capacity, professor availability, professor daily limit, and room availability. Branch B then used `EXCEPTION WHEN OTHERS` blocks to catch trigger failures as a control-flow mechanism. This note explains why this pattern is slow, fragile, and deadlock-prone — and how V2 replaces it with declarative constraints + a Boolean validation function.

## The V1 trigger inventory

Branch A (`bda_test_univ_exam`) had four triggers on `examens`, all `BEFORE INSERT OR UPDATE FOR EACH ROW`:

| Trigger | Function | Errcode | What it checks |
|---|---|---|---|
| `trg_check_room_capacity` | `check_room_capacity()` | 45000 | `NEW.nb_etudiants_prevus > lieu_examen.capacite` |
| `trg_check_professor_availability` | `check_professor_availability()` | 45001 | Counts exams where prof is principal on same (date, heure_debut) — **exact-time match only** |
| `trg_check_professor_daily_limit` | `check_professor_daily_limit()` | 45002 | Counts exams where prof is principal on same date; if `>= max_surveillances_jour` ⇒ raise |
| `trg_check_room_availability` | `check_room_availability()` | 45003 | Counts exams at (lieu_id, creneau_id); if >0 ⇒ raise |
| `trg_examens_updated_at` | `update_timestamp()` | — | `NEW.updated_at = NOW()` on UPDATE |

Branch B (`univ_exam_optimizer`) had two triggers, with even worse implementation (recomputing `COUNT(*) FROM inscriptions` on every fire).

## Why triggers for control flow are bad

### 1. Triggers fire per-row, turning bulk inserts into sequential scans

A bulk `INSERT INTO examens SELECT ... FROM ...` that inserts 1,000 rows fires each trigger 1,000 times. Each trigger execution runs a separate query. There is no batching.

### 2. Triggers acquire shared locks in unpredictable order

`check_professor_availability` queries `examens` joined with `creneaux`. `check_room_availability` queries `examens` joined with itself. Under concurrent inserts, these locks can deadlock — and Postgres will resolve the deadlock by aborting one of the transactions, with a confusing error message.

### 3. Triggers can be silently disabled

```sql
ALTER TABLE examens DISABLE TRIGGER trg_check_room_capacity;
```

This is a single SQL statement that any superuser (or any user with the right grant) can run. After this, the constraint is gone. The application sees no error. **Constraints cannot be disabled this way** — they require `ALTER TABLE ... DROP CONSTRAINT`, which is a schema change that shows up in migrations.

### 4. Triggers don't appear in `\d+` constraint output

When you `psql -c '\d+ examens'`, you see CHECK constraints, UNIQUE constraints, FKs, and EXCLUDE constraints in the constraints section. Triggers appear in a separate "Triggers" section that is easy to miss. A junior reviewing the schema may not realize the trigger exists.

### 5. Trigger error messages are less actionable

A CHECK constraint violation produces:

```
ERROR: new row for relation "examens" violates check constraint "examens_check"
DETAIL: Failing row contains (1, 42, 13, ...).
```

A trigger violation produces:

```
ERROR: Professor conflict: ...
CONTEXT: PL/pgSQL function check_professor_availability() line 14 at RAISE
```

The trigger error includes a function name and line number, which is fine for debugging but exposes implementation details to the caller.

## The V1 exact-time-match bug

The `check_professor_availability` trigger checks for conflicts using **exact (date, heure_debut) match**, not time-range overlap:

```sql
SELECT COUNT(*) INTO v_conflict_count
FROM examens e
JOIN creneaux c ON e.creneau_id = c.id
WHERE e.surveillant_principal_id = NEW.surveillant_principal_id
  AND c.date_examen = v_creneau_info.date_examen
  AND c.heure_debut = v_creneau_info.heure_debut   -- EXACT match, no overlap test
  AND c.session_id = v_creneau_info.session_id
  AND e.id != COALESCE(NEW.id, 0);
```

This means: if creneau 1 is 10:00–12:00 and creneau 2 is 11:00–13:00 (overlapping by an hour), the trigger does NOT detect a conflict. A professor assigned to both would be in two places at once from 11:00 to 12:00.

The correct way to detect time-range overlap in Postgres is the `EXCLUDE USING GIST` constraint with the `&&` (overlap) operator on a `TSTZRANGE` column. See [[3.4. EXCLUDE Constraints and btree gist]].

## Branch B's exception-as-control-flow pattern

Branch B's `generate_exam_schedule` PROCEDURE used the trigger as control flow:

```sql
BEGIN
    UPDATE exams
    SET room_id = r.id, date_exam = curr_date, start_time = curr_time, is_scheduled = TRUE
    WHERE id = ex.id;
    scheduled := TRUE;
    EXIT;
EXCEPTION WHEN OTHERS THEN
    -- Trigger raised exception, continue searching
    RAISE NOTICE 'Conflict found for module %, trying next slot...', ex.module_id;
END;
```

This is the worst pattern in the entire V1 codebase:

1. **`EXCEPTION WHEN OTHERS`** catches *every* exception, not just constraint violations. A connection drop, an out-of-memory error, a lock timeout — all get swallowed and logged as "Conflict found".
2. Each `BEGIN ... EXCEPTION ... END` block creates a subtransaction (savepoint). With E×D×4×R attempts, this is thousands of subtransactions per run — see [[2.5. PL-pgSQL Anti-Patterns]] anti-pattern 2.
3. The `RAISE NOTICE` is logged but not visible to the user. The user sees only "X modules scheduled" with no diagnostic info.
4. The pattern trains developers to think exceptions are normal control flow, which leads to more exceptions, which leads to more subtransactions.

## The V2 policy: constraints where possible, Boolean functions otherwise

V2 uses three layers of integrity enforcement, in order of preference:

### Layer 1: Declarative constraints (CHECK, UNIQUE, EXCLUDE, FK)

Used whenever the rule can be expressed declaratively. Examples:

- `CHECK (capacite > 0)` on `rooms`.
- `UNIQUE (tenant_id, exam_id, room_id)` on `exam_allocations`.
- `EXCLUDE USING gist (lieu_id WITH =, periode_ts WITH &&)` on `examens` for time-range overlap.
- Partial `UNIQUE INDEX ... WHERE deleted_at IS NULL` for soft-delete aware uniqueness.

See [[3.8. Constraints vs Triggers When to Use Each]].

### Layer 2: A STABLE Boolean function for cross-row validation

When the rule needs to check multiple rows but cannot be expressed as a constraint, V2 uses a `STABLE` function that returns `BOOLEAN`:

```sql
CREATE OR REPLACE FUNCTION verify_allocation_validity(
    p_module_id UUID, p_timeslot_id UUID, p_room_id UUID
) RETURNS BOOLEAN AS $$
DECLARE v_has_conflict BOOLEAN;
BEGIN
    -- 1. Check room availability
    SELECT EXISTS (
        SELECT 1 FROM exam_allocations alloc
        JOIN exams e ON alloc.exam_id = e.id
        WHERE e.timeslot_id = p_timeslot_id AND alloc.room_id = p_room_id
    ) INTO v_has_conflict;
    IF v_has_conflict THEN RETURN FALSE; END IF;

    -- 2. Check student double-booking
    SELECT EXISTS (
        SELECT 1 FROM inscriptions ins_active
        JOIN exams e_active ON ins_active.module_id = e_active.module_id
        WHERE e_active.timeslot_id = p_timeslot_id
          AND ins_active.student_id IN (
              SELECT student_id FROM inscriptions WHERE module_id = p_module_id
          )
    ) INTO v_has_conflict;
    IF v_has_conflict THEN RETURN FALSE; END IF;

    RETURN TRUE;
END;
$$ LANGUAGE plpgsql STABLE;
```

The caller checks `IF verify_allocation_validity(...) THEN INSERT ...` — no exception, no subtransaction. The `STABLE` marker tells the planner the function is read-only and can be cached within a transaction.

### Layer 3: Triggers for genuine cross-table invariants

V2 keeps only 3 triggers total:

1. `trg_set_updated_at` — generic `updated_at` maintenance on every table.
2. `trg_check_prof_daily` — the professor daily limit (genuinely needs cross-row procedural logic).
3. `audit_trigger_fn` — writes to `audit_log` AFTER INSERT/UPDATE/DELETE.

Everything else moved to constraints or Boolean functions.

## Common junior developer mistakes

- **Using triggers to enforce business rules because "the DB should enforce them".** The DB *should* enforce them — with constraints, not triggers. Triggers are for cases where constraints are insufficient.
- **Exact-match checks for time conflicts.** Time conflicts are overlaps, not equalities. Use `EXCLUDE USING gist` with `&&` on `TSTZRANGE`.
- **`EXCEPTION WHEN OTHERS` for control flow.** This swallows real errors and creates subtransactions. Use atomic Boolean checks.
- **Forgetting that triggers fire per-row.** A bulk insert of 1,000 rows fires the trigger 1,000 times. Test with realistic batch sizes.
- **Not documenting trigger order.** If you have multiple triggers on the same table, the firing order matters. Postgres fires them alphabetically by name — easy to forget.
