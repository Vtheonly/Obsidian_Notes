# 2.5. PL/pgSQL Anti-Patterns

> [!abstract] What this note teaches you
> V1's `generate_schedule.sql` is a case study in PL/pgSQL anti-patterns: temp tables created and dropped inside loops (causing catalog bloat), `EXCEPTION WHEN OTHERS` blocks creating thousands of subtransactions, `SET LOCAL statement_timeout = 0` disabling safety rails, and an `EXTRACT(MILLISECONDS)` bug that silently corrupts benchmark numbers. This note catalogs each anti-pattern with the V2 fix.

## Anti-pattern 1: DROP/CREATE temp tables in a function body

**V1 code (verbatim):**

```sql
DROP TABLE IF EXISTS temp_module_stats;
CREATE TEMP TABLE temp_module_stats AS
SELECT m.id AS module_id, ... ;

DROP TABLE IF EXISTS temp_module_conflicts;
CREATE TEMP TABLE temp_module_conflicts AS
SELECT i1.module_id AS m1, i2.module_id AS m2
FROM inscriptions i1
JOIN inscriptions i2 ON i1.etudiant_id = i2.etudiant_id
WHERE i1.module_id < i2.module_id;

DROP TABLE IF EXISTS temp_student_daily_counts;
CREATE TEMP TABLE temp_student_daily_counts (...);

DROP TABLE IF EXISTS temp_module_students;
CREATE TEMP TABLE temp_module_students (...);
```

**Why it is bad:** PostgreSQL temp tables are *not* memory-only. Creating and dropping them writes records to the system catalogs `pg_class`, `pg_attribute`, `pg_type`. Under continuous multi-tenant admin use (100+ universities, each regenerating schedules regularly), this causes:

- **Catalog bloat** — `pg_class` and `pg_attribute` grow unboundedly.
- **Catalog lock contention** — concurrent `CREATE TEMP TABLE` calls contend on system table locks.
- **Autovacuum thrashing** — autovacuum struggles to keep up with the churn.
- **Name collision landmine** — `DROP TABLE IF EXISTS temp_module_stats` without `TEMP` will drop a *real* table named `temp_module_stats` if one exists in `public`.

**V2 fix:** The conflict matrix becomes a permanent materialized view (`mv_module_conflicts`) refreshed before each run. The per-student daily counts become a CP-SAT constraint inside the solver — no SQL table needed at all. See [[3.6. Materialized Views and Refresh Strategies]].

## Anti-pattern 2: PL/pgSQL EXCEPTION blocks in loops

**V1 code (Branch B, `univ_exam_optimizer/02_optimization_algo.sql`):**

```sql
FOREACH curr_time IN ARRAY ARRAY[
    '08:30:00'::TIME, '10:30:00'::TIME,
    '13:30:00'::TIME, '15:30:00'::TIME
] LOOP
    FOR r IN SELECT * FROM rooms ORDER BY capacity ASC LOOP
        -- ... checks ...
        BEGIN
            UPDATE exams
            SET room_id = r.id, date_exam = curr_date, start_time = curr_time, is_scheduled = TRUE
            WHERE id = ex.id;
            scheduled := TRUE;
            EXIT;
        EXCEPTION WHEN OTHERS THEN
            -- Trigger raised exception, continue searching
            RAISE NOTICE 'Conflict found for module %, trying next slot...', ex.module_id;
        END;
    END LOOP;
END LOOP;
```

**Why it is bad:** Every `BEGIN ... EXCEPTION WHEN OTHERS THEN ... END` block creates an internal **savepoint (subtransaction)**. With E exams × D dates × 4 times × R rooms attempted placements, the subtransaction count can balloon to **thousands per scheduling run**. Each subtransaction:

- Writes to the WAL (write-ahead log).
- Allocates a virtual transaction ID.
- Holds resources until the outer transaction commits.

At scale, this can exhaust the shared buffer pool and increase the risk of **transaction ID (XID) wraparound** — a Postgres-specific failure mode that requires single-user-mode cleanup.

**V2 fix:** Replace exception-driven control flow with atomic Boolean functions. The V2 `verify_allocation_validity(p_module_id, p_timeslot_id, p_room_id) RETURNS BOOLEAN` function is declared `STABLE` and returns `FALSE` instead of raising an exception. The caller checks the return value with a plain `IF`. See [[3.8. Constraints vs Triggers When to Use Each]].

## Anti-pattern 3: `SET LOCAL statement_timeout = 0`

**V1 code (verbatim):**

```sql
v_start_time := clock_timestamp();
SET LOCAL statement_timeout = 0;  -- Disables timeout for the entire transaction
```

And at the function definition:

```sql
$$ LANGUAGE plpgsql
SET statement_timeout = 0;  -- Per-function GUC, disables timeout for every call
```

**Why it is bad:** If the function hangs (deadlock, infinite loop, OOM), it hangs **forever**. There is no safety rail. Combined with no auth and no rate limiting (see [[2.8. Missing Security and Multi-Tenancy]]), this is a trivial denial-of-service vector: any visitor can click "Generate" repeatedly and tie up Postgres workers indefinitely.

**V2 fix:** The CP-SAT solver has its own `max_time_in_seconds = 30` parameter. The Laravel job has `timeout = 600` (10 minutes hard ceiling). The HTTP request has a 30-second gateway timeout, but the request returns immediately after dispatching the job — see [[7.2. The GenerateScheduleJob Lifecycle]].

## Anti-pattern 4: `EXTRACT(MILLISECONDS FROM ...)` bug

**V1 code (verbatim):**

```sql
INSERT INTO schedule_logs (session_id, action, details, execution_time_ms, success)
VALUES (
    p_session_id,
    'generate_schedule',
    jsonb_build_object(...),
    EXTRACT(MILLISECONDS FROM (clock_timestamp() - v_start_time))::INTEGER,  -- BUG
    TRUE
);
```

**Why it is bad:** `EXTRACT(MILLISECONDS FROM interval)` returns the **milliseconds component** of the interval (0–999), not the total milliseconds. For a 45-second run, `EXTRACT(MILLISECONDS FROM '45 seconds'::interval)` returns `0`, not `45000`. For a 45.5-second run, it returns `500`, not `45500`.

**The blast radius:** Every benchmark number V1 reported was wrong. The README claimed "< 45 second generation time" with no evidence, and the actual evidence (the `execution_time_ms` column in `schedule_logs`) was silently corrupted. A junior reading the logs would conclude the scheduler runs in < 1 second.

**V2 fix:**

```sql
(EXTRACT(EPOCH FROM (clock_timestamp() - v_start_time)) * 1000)::INTEGER
```

`EXTRACT(EPOCH FROM interval)` returns the total seconds as a float; multiplying by 1000 gives total milliseconds. This is the only correct idiom.

## Anti-pattern 5: OR in JOIN condition defeats indexes

**V1 code (verbatim):**

```sql
IF EXISTS (
    SELECT 1 
    FROM examens e
    JOIN temp_module_conflicts mc 
      ON (mc.m1 = v_module.module_id AND mc.m2 = e.module_id)
      OR (mc.m2 = v_module.module_id AND mc.m1 = e.module_id)
    WHERE e.creneau_id = v_creneau.id
      AND e.statut != 'annule'
) THEN
    v_conflicts := v_conflicts + 1;
    CONTINUE;
END IF;
```

**Why it is bad:** The `OR` across two join conditions defeats both `idx_temp_conflicts (m1, m2)` and `idx_temp_conflicts_rev (m2, m1)`. Postgres will likely seq-scan the temp table. This check runs once per (module, creneau) pair — for 1,000 modules × 64 creneaux = 64,000 executions per scheduling run.

**V2 fix:** Rewrite as `UNION` of two indexed queries, or store edges in both directions and use a single equality join:

```sql
-- Better: UNION of two indexed lookups
IF EXISTS (
    SELECT 1 FROM examens e
    JOIN temp_module_conflicts mc ON mc.m1 = v_module.module_id AND mc.m2 = e.module_id
    WHERE e.creneau_id = v_creneau.id AND e.statut != 'annule'
    UNION ALL
    SELECT 1 FROM examens e
    JOIN temp_module_conflicts mc ON mc.m2 = v_module.module_id AND mc.m1 = e.module_id
    WHERE e.creneau_id = v_creneau.id AND e.statut != 'annule'
) THEN ...
```

Or, in V2, the conflict graph lives in the CP-SAT model itself, not in SQL — so this query is not executed at all.

## Anti-pattern 6: `prof_rec RECORD` declared but never used

**V1 code (Branch B):**

```sql
DECLARE
    ex RECORD; r RECORD;
    curr_date DATE; curr_time TIME;
    scheduled BOOLEAN;
    prof_rec RECORD;  -- declared but NEVER USED
BEGIN
```

**Why it is bad:** Dead code. The V1 author intended to assign professors but never implemented it (the comment at L3474 literally says "Logic omitted for brevity"). The `prof_id` column is reset to NULL at the start and never set again. Every scheduled exam has `prof_id = NULL`.

**V2 fix:** The CP-SAT model has explicit `z[m, p, c]` decision variables for professor assignments, with hard constraint 6 requiring a professor be assigned whenever an exam is scheduled. See [[4.4. The 16 Hard Constraints]].

## Anti-pattern 7: Cross-table CHECK constraints missing

V1 has no constraint that `modules.semestre` matches `sessions_examen.semestre`, no constraint that `etudiants.formation_id` matches the module's formation, no constraint that creneau duration matches module duration. The schema allows placing an L1 student in an M2 exam, or a 90-minute exam in a 60-minute slot.

**V2 fix:** Cross-table invariants are enforced at the service layer (Laravel Form Requests + Policies) where they can be tested, and at the DB layer (CHECK constraints, EXCLUDE, partial UNIQUE) where they cannot be bypassed. See [[3.8. Constraints vs Triggers When to Use Each]].

## Common junior developer mistakes

- **"Temp tables are temporary, so they're free."** No. They write to system catalogs. Use CTEs for one-shot queries, or materialized views for repeated computation.
- **"EXCEPTION WHEN OTHERS is clean error handling."** In PL/pgSQL loops, it creates subtransactions that exhaust WAL. Use atomic Boolean checks.
- **"SET LOCAL statement_timeout = 0 prevents timeouts."** It also prevents safety. Always have a time budget.
- **"EXTRACT(MILLISECONDS) gives me milliseconds."** It gives you the millisecond *component*. Use `EXTRACT(EPOCH) * 1000` for total.
- **"OR in JOIN is fine, the planner will figure it out."** It won't. Rewrite as UNION.
- **Declaring variables "for later".** Dead code is a liability. Delete it.
