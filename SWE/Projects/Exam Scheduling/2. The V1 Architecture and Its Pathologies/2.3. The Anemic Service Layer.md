# 2.3. The Anemic Service Layer

> [!abstract] What this note teaches you
> V1 had a `services/` directory with `analytics_service.py` and `scheduling_service.py`. They looked like a service layer. They were not. Every method was a one-line forwarder to `db.some_function(...)`. This note explains what an anemic service layer is, why it is worse than no service layer at all, and how V2's `ScheduleService` does the job properly.

## What is an anemic service layer?

A real service layer encapsulates **business rules**: preconditions, postconditions, invariants, orchestration of multiple data operations, transaction boundaries, audit logging. It exists so that the UI can call `service.generate_schedule(...)` and trust that all the rules are enforced.

An **anemic service layer** has the class structure of a service layer but no behavior. Every method is a one-liner that delegates to the data access layer:

```python
def get_global_stats(self, session_id: int) -> Dict:
    return db.get_global_stats(session_id)
```

This is worse than having no service layer at all, because:
1. It gives the illusion of architectural layering without the substance.
2. It adds an extra layer to maintain and test for zero benefit.
3. It hides the fact that no business rules are being enforced.
4. It makes refactoring harder (you have to maintain the wrapper even when changing nothing).

## V1's anemic services, verbatim

### `AnalyticsService.get_global_stats` (Branch A)

```python
# bda_test_univ_exam/src/backend/services/analytics_service.py
class AnalyticsService:
    def get_global_stats(self, session_id: int) -> Dict:
        return db.get_global_stats(session_id)  # Zero-value wrapper
```

That is the entire method. No validation that `session_id` exists. No validation that the caller is authorized to see this session's stats. No caching. No logging. No transformation of the raw DB result. Just a forward.

### `SchedulingService.generate`

```python
class SchedulingService:
    def generate(self, session_id: int, max_exams_per_day: int = 1) -> Dict:
        return db.generate_schedule(session_id, max_exams_per_day)
```

What is missing here:
- No check that `session_id` exists.
- No check that the session is in `planification` status (you can call `generate` on a `termine` session).
- No check that no other generation is in progress.
- No idempotency check (calling `generate` twice creates duplicate exams if `clear_existing=False`).
- No audit log of who called it.
- No validation that `max_exams_per_day` is in `[1, 3]` (let alone `[1, 2]` per the brief).
- No retry on transient failures.
- No transaction wrapping.

### `AnalyticsService._calculate_health_score` (the one method with logic)

```python
def _calculate_health_score(self, stats: Dict, conflicts: Dict) -> int:
    """Calculate overall schedule health score (0-100)."""
    score = 100
    total_modules = stats.get("total_modules") or 0
    schedule_pct = stats.get("scheduling_rate") or 0
    avg_util = stats.get("avg_room_utilization") or 0

    if total_modules > 0:
        score -= (100 - schedule_pct) * 0.5            # penalty for unscheduled
    total_conflicts = sum(conflicts.values()) if conflicts else 0
    score -= min(total_conflicts * 2, 30)              # cap conflict penalty at 30
    if avg_util and avg_util < 50:
        score -= (50 - avg_util) * 0.2                 # penalty for low utilization
    return max(0, min(100, int(score)))
```

This is the **one** method in the entire V1 service layer with real logic. And it is a disaster:

- **Magic numbers everywhere.** `0.5`, `30`, `50`, `0.2`. No named constants, no comments, no tests.
- **Hidden complexity.** The `min(..., 30)` cap on the conflict penalty means a schedule with 100 conflicts scores the same as one with 15. That's a real policy decision buried in arithmetic.
- **Untestable.** You can't unit-test this method without mocking the entire `db` module, because it's a method on a class that imports `db` at module level.
- **Business logic in Python, not SQL.** The KPIs themselves are computed in PL/pgSQL (`get_global_stats`), but the *interpretation* of those KPIs as a "health score" is in Python. Two layers to maintain.

## What a real service layer looks like (V2 preview)

V2's `ScheduleService::generate` does what V1's should have done:

```php
// app/Modules/Scheduling/Services/ScheduleService.php
class ScheduleService
{
    public function __construct(
        private readonly SchedulerClient $scheduler,
        private readonly ConflictDetector $conflicts,
    ) {}

    public function generate(int $sessionId, int $userId, array $params): ScheduleRun
    {
        // 1. Validate session exists
        $session = Session::findOrFail($sessionId);

        // 2. Enforce status precondition
        throw_unless(
            $session->statut === 'planification',
            new BusinessException('La session doit être en statut "planification".')
        );

        // 3. Enforce no-concurrent-run invariant
        throw_if(
            ScheduleRun::where('session_id', $sessionId)
                ->whereIn('statut', ['en_attente', 'en_cours'])
                ->exists(),
            new BusinessException('Une génération est déjà en cours pour cette session.')
        );

        // 4. Create audit trail BEFORE the run
        $run = ScheduleRun::create([
            'session_id' => $sessionId,
            'triggered_by' => $userId,
            'algorithm' => $params['algorithm'] ?? 'cp_sat',
            'statut' => 'en_attente',
            'parameters' => $params,
        ]);

        // 5. Dispatch async job (acquires locks, calls solver, persists result)
        GenerateScheduleJob::dispatch($run);

        return $run;
    }
}
```

Every precondition that V1 skipped is now enforced. The service is testable (constructor injection of `SchedulerClient` and `ConflictDetector` mocks). The audit trail is created before the work starts, so even a crash leaves a record.

## Why V1's services existed at all

The most charitable interpretation: the V1 author knew that "good architecture has a service layer" and added one to look professional, without understanding what a service layer is *for*. The less charitable interpretation: they were placeholder classes that never got filled in.

Either way, the lesson is the same:

> [!important] A service layer that does not enforce business rules is not a service layer
> It is a folder with files in it. Deleting it would improve the codebase because at least then nobody would mistake it for architecture.

## The 19 one-liners

The V1 review counted **19 one-liner methods** across `AnalyticsService` and `SchedulingService`. Every one of them was `return db.X(...)`. The `db_manager` itself had 19 one-liner wrappers around `supabase.rpc(...)` or `supabase.table(...).select(...)`. So the call stack for `analytics_service.get_global_stats(42)` was:

```
analytics_service.get_global_stats(42)
  → db.get_global_stats(42)
    → db.supabase.rpc("get_global_stats", {"p_session_id": 42}).execute()
      → HTTP POST to Supabase PostgREST
        → PL/pgSQL function get_global_stats(42)
```

Four Python stack frames to add zero behavior. The entire Python service layer could have been deleted with no functional change.

## Common junior developer mistakes

- **Adding "service" classes that just forward calls.** If your service method is one line and that line is `return db.X(...)`, delete the method and call `db.X(...)` directly. Or — better — add the validation and audit logic that justifies the layer.
- **Business logic in Python (or PHP) when it belongs in SQL.** The "health score" is a derived metric. It should be a column in a view, computed once and cached, not recomputed in Python on every page load.
- **Magic numbers in scoring formulas.** `0.5`, `30`, `0.2` should be named constants (`PENALTY_PER_UNSCHEDULED_PCT = 0.5`, etc.) and documented.
- **Untestable service methods.** If your service imports `db` at module level, you cannot unit-test it without monkey-patching. Use constructor injection — see [[5.5. Dependency Injection and SOLID]].
- **No precondition checks.** "Trust your callers" is fine for internal helpers; it is criminal for an entry point that the UI calls directly.
