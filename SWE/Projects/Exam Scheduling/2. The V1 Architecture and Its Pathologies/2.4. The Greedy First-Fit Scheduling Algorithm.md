# 2.4. The Greedy First-Fit Scheduling Algorithm

> [!abstract] What this note teaches you
> V1's scheduler was a single PL/pgSQL function `generate_schedule(p_session_id, p_max_exams_per_day)` implementing greedy first-fit. This note walks through the algorithm step by step, shows its worst-case complexity, and explains why it cannot satisfy the brief's hard constraints.

## The algorithm in plain English

The V1 scheduler does this:

1. **Pre-compute** a temp table of module enrollment counts (`temp_module_stats`).
2. **Pre-compute** a temp table of pairwise module conflicts (`temp_module_conflicts`) — modules sharing ≥1 student.
3. **Pre-compute** a temp table of active inscriptions (`temp_module_students`).
4. **Initialize** an empty per-student per-day exam count table (`temp_student_daily_counts`).
5. **DELETE** all existing exams for this session (destructive wipe — see [[2.6. The Fatal UNIQUE Constraint]] and [[7.4. Transaction Safety and Concurrency]]).
6. **For each module** (sorted by enrollment DESC — largest first):
   - **For each creneau** (sorted by date, then time — earliest first):
     - Skip if any already-scheduled exam at this slot shares students with this module.
     - Skip if any student in this module already has `max_exams_per_day` exams on this date.
     - Find the smallest-fitting available room (`find_available_room`).
     - Find the least-loaded same-dept available professor (`find_available_professor`).
     - INSERT into `examens`.
     - Increment per-student per-day counters via `ON CONFLICT DO UPDATE`.
     - EXIT inner loop.
7. **Log** the result to `schedule_logs` (with a buggy execution-time calculation — see [[2.5. PL-pgSQL Anti-Patterns]]).
8. **Drop** the four temp tables.

## The complexity

Let:
- $M$ = number of modules (~1,200 at baseline)
- $C$ = number of creneaux (~64)
- $R$ = number of rooms (~50)
- $P$ = number of professors (~200)
- $S$ = average students per module (~100)
- $d$ = average degree in the module conflict graph (~20)

Setup phase: $O(E)$ for the inscriptions scans, $O(S \cdot k^2)$ for the conflict matrix where $k$ is avg modules per student (~8).

Main loop: $O(M \cdot C \cdot (d + k + R + P))$ — for each module, for each creneau, do a conflict check $O(d)$, an overload check $O(k)$, a room search $O(R)$, and a professor search $O(P)$.

Worst case at baseline: $1200 \cdot 64 \cdot (20 + 8 + 50 + 200) \approx 21$ million operations.

Worst case at max scale: $5000 \cdot 64 \cdot (50 + 8 + 200 + 1000) \approx 400$ million operations.

This is *per scheduling run*, and it does not include the conflict-matrix build (which is the real bottleneck — see [[10.1. The 130k to 800k Inscriptions Scaling Path]]).

## The defining weakness: no backtracking

The greedy loop commits to its first choice. If module A is placed in creneau 1, and that placement later prevents module B from being placed at all, the algorithm reports "B unscheduled" and moves on. It does **not** try moving A to creneau 2 to make room for B.

This is the defining weakness of all greedy algorithms on NP-hard problems — see [[4.1. Why Greedy Fails on NP-Hard Problems]] for the worked "Greedy Trap" example.

## Verbatim: the V1 main loop

```sql
-- (6) MAIN LOOP — modules sorted by enrollment DESC (largest first)
FOR v_module IN (
    SELECT * FROM temp_module_stats
    WHERE nb_inscrits > 0
    ORDER BY nb_inscrits DESC
) LOOP
    v_total := v_total + 1;
    v_nb_inscrits := v_module.nb_inscrits;
    v_dept_id := v_module.departement_id;

    -- (6a) INNER LOOP — creneaux ordered by date, time
    FOR v_creneau IN (
        SELECT * FROM creneaux
        WHERE session_id = p_session_id
        ORDER BY date_examen, heure_debut
    ) LOOP
        -- (6a-i) Skip if any already-scheduled exam at this slot shares students
        IF EXISTS (
            SELECT 1 
            FROM examens e
            JOIN temp_module_conflicts mc 
              ON (mc.m1 = v_module.module_id AND mc.m2 = e.module_id)
              OR (mc.m2 = v_module.module_id AND mc.m1 = e.module_id)
            WHERE e.creneau_id = v_creneau.id
              AND e.statut != 'annule'
        ) THEN
            v_conflicts := v_conflicts + 1;
            CONTINUE;
        END IF;
        
        -- (6a-ii) Skip if any student in this module already has p_max_exams_per_day on this date
        SELECT COUNT(*) INTO v_overload_count
        FROM temp_module_students tms
        JOIN temp_student_daily_counts tsdc ON tms.etudiant_id = tsdc.etudiant_id
        WHERE tms.module_id = v_module.module_id
          AND tsdc.exam_date = v_creneau.date_examen
          AND tsdc.exam_count >= p_max_exams_per_day
        LIMIT 1;
        IF v_overload_count > 0 THEN
            CONTINUE;
        END IF;
        
        -- (6a-iii) Find a room — best-fit by capacity ASC
        v_room_id := find_available_room(v_creneau.id, v_nb_inscrits);
        IF v_room_id IS NULL THEN
            CONTINUE;
        END IF;
        
        -- (6a-iv) Find a professor — same-dept priority, least-loaded
        v_prof_id := find_available_professor(v_creneau.id, v_dept_id);
        -- NOTE: v_prof_id may be NULL — exam inserted with no proctor, silently

        -- (6a-v) INSERT
        INSERT INTO examens (
            module_id, creneau_id, lieu_id, 
            surveillant_principal_id, nb_etudiants_prevus, statut
        ) VALUES (
            v_module.module_id, v_creneau.id, v_room_id,
            v_prof_id, v_nb_inscrits, 'planifie'
        );
        
        -- (6a-vi) Increment per-student per-day counters atomically
        INSERT INTO temp_student_daily_counts (etudiant_id, exam_date, exam_count)
        SELECT etudiant_id, v_creneau.date_examen, 1
        FROM temp_module_students
        WHERE module_id = v_module.module_id
        ON CONFLICT (etudiant_id, exam_date) 
        DO UPDATE SET exam_count = temp_student_daily_counts.exam_count + 1;
        
        v_scheduled := v_scheduled + 1;
        EXIT;  -- break inner creneau loop, move to next module
    END LOOP;
END LOOP;
```

## What this algorithm gets right

Credit where due — the V1 algorithm has a few genuinely good ideas:

1. **Largest-enrollment-first ordering** — standard bin-packing heuristic, gives better packing than random order. V2 keeps this as a tiebreaker.
2. **Pre-materialized conflict graph** — turning the O(students) shared-students check into O(1) index lookups is the right instinct. V2 makes this a permanent materialized view (`mv_module_conflicts`).
3. **Incremental per-student per-day counter with `ON CONFLICT DO UPDATE`** — atomic upsert, no read-modify-write race. Excellent pattern. V2 keeps this approach inside the CP-SAT model formulation.
4. **Best-fit room selection** — smallest-fitting-room-first maximizes utilization. V2 keeps this as soft constraint W6.

These four ideas are preserved in V2. The problem is everything else.

## What this algorithm gets wrong

1. **No backtracking.** The defining weakness. Once a module is placed, it stays placed even if moving it would unblock another module.
2. **No objective function.** The algorithm finds *a* feasible schedule. It does not try to find a *good* one. No student spread optimization. No weekend avoidance. No room size matching beyond best-fit. No fairness.
3. **No fairness.** The brief requires equalized professor workload across the session. The greedy "least-loaded today" heuristic actively harms session-level fairness — see [[1.3. Hard Constraints and Business Rules]] constraint 5.
4. **No split rooms.** The fatal `UNIQUE(module_id, creneau_id)` constraint makes splitting impossible — see [[2.6. The Fatal UNIQUE Constraint]].
5. **No fallback.** If a module can't be scheduled under strict rules, the algorithm gives up. No retry with relaxed constraints — see [[4.8. The Fallback Strategy]].
6. **OR in JOIN defeats indexes.** The `OR` in the conflict check (line `ON (mc.m1 = ... AND mc.m2 = ...) OR (mc.m2 = ... AND mc.m1 = ...)`) defeats both indexes on `temp_module_conflicts`. Postgres will likely seq-scan.
7. **Silently accepts NULL professors.** `v_prof_id := find_available_professor(...)` can return NULL, and the INSERT accepts it. Exams are scheduled with no proctor.
8. **`v_conflicts` counter is misleading.** It only counts student-time-conflict skips, not room/professor/capacity failures. The UI displays this as "Conflits Détectés", which is wrong.
9. **`EXTRACT(MILLISECONDS FROM ...)` bug.** The execution-time logging returns the milliseconds *component* of the interval, not the total. A 45-second run reports `0 ms`. See [[2.5. PL-pgSQL Anti-Patterns]].
10. **No advisory lock.** Concurrent calls interleave. See [[7.3. Distributed Locks Redis vs Advisory]].

## The V2 replacement

V2 replaces the entire PL/pgSQL function with a Python CP-SAT model dispatched as a Laravel job. The model has:

- 16 hard constraints (see [[4.4. The 16 Hard Constraints]]) including split rooms, fairness, department priority, equipment matching, professor unavailability.
- 7 weighted soft constraints (see [[4.5. The 7 Soft Constraints and Objective]]) for spread, fairness, room match, weekend avoidance, etc.
- Backtracking via lazy clause generation.
- A 5-level fallback strategy (see [[4.8. The Fallback Strategy]]) that relaxes soft constraints before giving up.
- A 30-second solver timeout that is *inside* the 45-second business budget (see [[1.5. Scale Targets and Performance Budget]]).

## Common junior developer mistakes

- **Choosing greedy because "it's simple".** Simplicity is a virtue, but greedy on NP-hard is not simple — it is wrong. The simplest *correct* approach is CP-SAT.
- **No objective function.** "Find any feasible schedule" is not a goal. You always have preferences (spread, fairness, utilization). Express them as a weighted objective.
- **Per-day fairness instead of session fairness.** The brief requires session-level fairness. Greedy heuristics optimize locally and fail globally.
- **Trusting the `v_conflicts` counter.** Counters lie. Record each conflict with type, severity, and entity ID in a real table — see `schedule_conflicts` in [[3.2. Schema Design Principles for SaaS]].
- **No timeout.** `SET LOCAL statement_timeout = 0` on a function that can run for minutes is a DoS vector. Always have a time budget.
