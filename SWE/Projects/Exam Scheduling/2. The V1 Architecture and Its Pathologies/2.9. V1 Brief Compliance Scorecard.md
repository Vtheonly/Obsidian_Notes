# 2.9. V1 Brief Compliance Scorecard

> [!abstract] What this note teaches you
> The original academic brief (`Projet-Num_Exam.pdf`) had 12 hard requirements. V1 met 4, partially met 3, and missed 5. This note is the final scorecard — the cold accounting that justifies the entire V2 redesign.

## The 12 hard requirements

The brief lists 5 "critical constraints to model" plus 7 other hard requirements (deliverables, scale, multi-actor workflow). Combining them:

| # | Brief requirement | V1 implementation | Status |
|---|---|---|---|
| 1 | Students: max 1 exam/day | `max_exams_per_day` default 1, but UI slider allows up to 3 with no warning | ⚠️ Partial |
| 2 | Professors: max 3 proctorings/day | `max_surveillances_jour` default 3, trigger enforces (but ignores `surveillances` table) | ✅ Done |
| 3 | Room capacity respected | Trigger `check_room_capacity` enforces (uses stored `nb_etudiants_prevus` which can be stale) | ✅ Done |
| 4 | Department proctoring priority | `find_available_professor` orders by same-dept first | ⚠️ Weak |
| 5 | All professors equal surveillance count | **Not implemented** | ❌ Missing |
| 6 | TD rooms ≤ 20 students | **Not implemented** — no `'TD'` type in CHECK, no CHECK tying type to capacity | ❌ Missing |
| 7 | < 45-second generation | No benchmark evidence (`benchmarks_performances.md` is empty) | ❓ Unverified |
| 8 | Multi-actor workflow (Vice-Doyen, Admin, Chef Dept, Student/Prof) | 4 Streamlit pages exist but validation workflow is fake (TODO comments) | ⚠️ Partial |
| 9 | Realistic dataset (130k inscriptions) | Seed generates 13k students × ~8 modules = 104k inscriptions | ✅ Close |
| 10 | Functional prototype | Streamlit app runs | ✅ Done |
| 11 | Technical report (10-15 pages PDF) | `rapport_technique.md` is **empty** | ❌ Missing |
| 12 | Performance benchmarks | `benchmarks_performances.md` is **empty** | ❌ Missing |

**Score: 4/12 met. 3/12 partially met. 5/12 missing or unverified.**

## What "partial" means

### Requirement 1: 1 exam per day (partial)

The scheduler's pre-check enforced the limit (default 1), but:
- The UI slider allowed values up to 3 with no warning.
- No DB-level constraint — manual INSERTs bypassed the check.
- The `temp_student_daily_counts` counter was per-scheduling-run, not persistent — a manual edit after scheduling could violate the rule.

### Requirement 4: Department priority (weak)

`find_available_professor` did order by same-dept first, but:
- No global objective to *minimize* cross-dept assignments — the greedy loop would pick a cross-dept prof early with no penalty.
- The check ignored the `surveillances` table (secondary surveillants), so it undercounted workload.

### Requirement 8: Multi-actor workflow (partial)

Four Streamlit pages existed for the four actor types, but:
- No auth, no RBAC — any visitor could access any page.
- The "Valider le planning" button on Chef Dept page was a fake stub (`# TODO: Update session status in DB`).
- The "Demander révision" button was also fake.
- No real state machine for session status — a stray UPDATE could corrupt history.

## What "missing" means

### Requirement 5: Equalized professor workload

This is the most consequential missing requirement. The brief explicitly says "Tous les enseignants doivent avoir le même nombre de surveillances." V1's `find_available_professor` picked the least-loaded prof *today*, which actively harms session-level fairness. See [[1.3. Hard Constraints and Business Rules]] constraint 5.

### Requirement 6: TD room 20-student cap

The brief mentions "salles limitées à 20 étudiants max (en période d'examen)" in the Contexte section. V1's schema had no `'TD'` type in `lieu_examen.type CHECK (type IN ('amphi', 'salle', 'labo'))` and no constraint tying type to capacity. The seeder set `capacite=20` for "Salle" rows as a data convention, but nothing in the schema enforced it. See [[1.3. Hard Constraints and Business Rules]] constraint 6.

### Requirements 11 and 12: Technical report and benchmarks

Both required deliverables were empty files. The brief explicitly states these are required for evaluation. A grader checking the submission would mark them as missing.

## The 20 biggest V1 mistakes (abridged)

The full review catalogued 20 "biggest mistakes". The top 10:

1. **No authentication or authorization** — anyone can do anything. (Critical)
2. **Supabase service key bundled in the client** — full admin access to anyone running the app. (Critical)
3. **The fatal `UNIQUE(module_id, creneau_id)` constraint** — large cohorts unschedulable. (Critical)
4. **Concurrent schedule generation race** — no advisory lock. (Critical)
5. **Destructive scheduler regeneration** — `DELETE FROM examens` before regen, no backup. (Critical)
6. **Greedy algorithm with no backtracking on an NP-hard problem**. (Critical)
7. **No professor workload fairness** — directly violates brief. (Critical)
8. **Synchronous blocking scheduler** — UI freezes, work lost on tab close. (High)
9. **PII (emails) publicly searchable** — GDPR/FERPA violation. (High)
10. **Two parallel codebases** — can't tell which is canonical. (High)

The remaining 10 cover PL/pgSQL anti-patterns, missing tests, missing docs, no observability, no multi-tenancy, no caching, N+1 queries, fake buttons, broken CSS, and `EXTRACT(MILLISECONDS)` bug.

The V2 redesign is what "being done" looks like.

## Common junior developer mistakes

- **Treating the brief as a feature checklist.** The brief is a constraint satisfaction problem. You cannot add "constraint X" as a feature; you must model the whole problem globally.
- **Empty deliverable files committed to look professional.** A grader (or reviewer) can `wc -l` your files. Empty `tests/` and `docs/` are worse than none.
- **Trusting the README's performance claims.** The README said "< 45 second generation time" but the benchmarks file was empty. Always back claims with executable evidence.
- **Sliders that silently violate business rules.** V1's `max_exams_per_day` slider allowed 3 with no warning. V2's Form Request rejects values > 2 with a French message explaining why.
- **TODO comments in production code.** `# TODO: Update session status in DB` next to a button that calls `st.success(...)` is theater. Either wire it or remove it.
