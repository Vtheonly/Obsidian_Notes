# 6.6. Audit Logging and Hash Chaining

> [!abstract] What this note teaches you
> V1's `schedule_logs` recorded *what* was done but not *who* did it. V2 has a dedicated `audit_log` table partitioned by year, with a generic trigger that captures every INSERT/UPDATE/DELETE on critical tables, plus hash chaining for tamper-evidence. This note is the V2 audit strategy.

## The `audit_log` table

```sql
CREATE TABLE audit_log (
    id              BIGINT GENERATED ALWAYS AS IDENTITY,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    university_id   BIGINT NOT NULL,
    user_id         BIGINT,
    action          TEXT NOT NULL,  -- 'create', 'update', 'delete', 'restore', 'login', 'logout'
    entity_type     TEXT NOT NULL,  -- 'etudiant', 'professeur', 'examen', 'session', ...
    entity_id       BIGINT,
    before_data     JSONB,
    after_data      JSONB,
    ip_address      INET,
    user_agent      TEXT,
    previous_hash   TEXT,           -- hash of the previous audit_log row
    row_hash        TEXT,           -- hash of this row's content
    PRIMARY KEY (id, created_at)
) PARTITION BY RANGE (created_at);
```

Partitioned by year for archival. Each row captures:
- **Who:** `user_id`, `ip_address`, `user_agent`.
- **What:** `action`, `entity_type`, `entity_id`, `before_data`, `after_data`.
- **When:** `created_at`.
- **Where (tenant):** `university_id`.
- **Integrity:** `previous_hash`, `row_hash` (for tamper-evidence).

## The generic audit trigger

```sql
CREATE OR REPLACE FUNCTION audit_trigger_fn() RETURNS TRIGGER AS $$
DECLARE
    v_user_id BIGINT;
    v_university_id BIGINT;
    v_prev_hash TEXT;
    v_row_hash TEXT;
BEGIN
    v_user_id := current_setting('app.current_user_id', true)::bigint;
    v_university_id := COALESCE(NEW.university_id, OLD.university_id);
    
    -- Get the previous row's hash (for chaining)
    SELECT row_hash INTO v_prev_hash
    FROM audit_log
    WHERE university_id = v_university_id
    ORDER BY id DESC
    LIMIT 1;
    
    -- Compute this row's hash
    v_row_hash := encode(
        digest(
            COALESCE(v_prev_hash, '') || '|' ||
            TG_OP || '|' ||
            TG_TABLE_NAME || '|' ||
            COALESCE(COALESCE(NEW.id, OLD.id)::text, '') || '|' ||
            COALESCE(to_jsonb(NEW)::text, '') || '|' ||
            COALESCE(to_jsonb(OLD)::text, ''),
            'sha256'
        ),
        'hex'
    );
    
    INSERT INTO audit_log (
        university_id, user_id, action, entity_type, entity_id,
        before_data, after_data, ip_address, user_agent,
        previous_hash, row_hash
    ) VALUES (
        v_university_id,
        v_user_id,
        TG_OP,
        TG_TABLE_NAME,
        COALESCE(NEW.id, OLD.id),
        CASE WHEN TG_OP IN ('DELETE', 'UPDATE') THEN to_jsonb(OLD) END,
        CASE WHEN TG_OP IN ('INSERT', 'UPDATE') THEN to_jsonb(NEW) END,
        NULL::inet,  -- set by application if available
        NULL,
        v_prev_hash,
        v_row_hash
    );
    
    RETURN COALESCE(NEW, OLD);
END;
$$ LANGUAGE plpgsql;

-- Attach to critical tables
CREATE TRIGGER audit_examens AFTER INSERT OR UPDATE OR DELETE ON examens
    FOR EACH ROW EXECUTE FUNCTION audit_trigger_fn();

CREATE TRIGGER audit_inscriptions AFTER INSERT OR UPDATE OR DELETE ON inscriptions
    FOR EACH ROW EXECUTE FUNCTION audit_trigger_fn();

CREATE TRIGGER audit_sessions AFTER INSERT OR UPDATE OR DELETE ON sessions_examen
    FOR EACH ROW EXECUTE FUNCTION audit_trigger_fn();
```

The trigger fires AFTER the operation, so it captures the final state. It uses `current_setting('app.current_user_id', true)` — the value set by `SetTenantContext` middleware — to record who did the action.

## Hash chaining for tamper-evidence

Each audit row's `row_hash` is the SHA-256 of:
- The previous row's `row_hash` (`previous_hash`).
- The operation, table, entity ID, before/after data.

This forms a chain. If anyone modifies an audit row, the next row's `previous_hash` won't match the modified row's `row_hash`, and verification fails.

Verification script:

```sql
CREATE OR REPLACE FUNCTION verify_audit_chain(p_university_id BIGINT)
RETURNS TABLE(broken_at BIGINT, expected_hash TEXT, actual_hash TEXT) AS $$
DECLARE
    v_prev_hash TEXT := '';
    v_row RECORD;
BEGIN
    FOR v_row IN
        SELECT id, row_hash, previous_hash
        FROM audit_log
        WHERE university_id = p_university_id
        ORDER BY id ASC
    LOOP
        IF v_row.previous_hash IS DISTINCT FROM v_prev_hash THEN
            RETURN QUERY SELECT v_row.id, v_prev_hash, v_row.previous_hash;
            RETURN;
        END IF;
        v_prev_hash := v_row.row_hash;
    END LOOP;
    
    -- Chain intact
    RETURN;
END;
$$ LANGUAGE plpgsql;
```

Run quarterly to detect tampering.

## The middleware-level audit (for API requests)

In addition to the DB trigger, V2 has an HTTP middleware that logs every mutating request:

```php
// app/Http/Middleware/AuditTrailLogger.php
class AuditTrailLogger
{
    public function handle(Request $request, Closure $next): Response
    {
        $response = $next($request);
        
        if (in_array($request->method(), ['POST', 'PUT', 'DELETE', 'PATCH'])) {
            try {
                $user = $request->user();
                $tenantId = $request->header('X-Tenant-ID') ?? $user?->tenant_id;
                
                if ($user && $tenantId) {
                    DB::table('audit_logs')->insert([
                        'tenant_id' => $tenantId,
                        'user_id' => $user->id,
                        'action' => $request->method() . ':' . $request->path(),
                        'entity_type' => 'API_REQUEST',
                        'entity_id' => gen_random_uuid(),
                        'payload_after' => json_encode(
                            $request->except(['password', 'password_confirmation', 'email', 'matricule'])
                        ),
                        'ip_address' => $request->ip(),
                        'created_at' => clock_timestamp(),
                    ]);
                }
            } catch (\Throwable $e) {
                Log::error("Failed to write to audit trail: " . $e->getMessage());
            }
        }
        
        return $response;
    }
}
```

This catches the HTTP-level metadata (method, path, IP, user agent) that the DB trigger cannot see. The DB trigger catches the row-level changes that the middleware cannot see. Together they provide complete coverage.

## Why V1's audit was insufficient

V1's `schedule_logs` table:

```sql
CREATE TABLE schedule_logs (
    id SERIAL PRIMARY KEY,
    session_id INTEGER REFERENCES sessions_examen(id),
    action VARCHAR(50) NOT NULL,  -- 'generate_schedule', 'clear_schedule'
    details JSONB,
    execution_time_ms INTEGER,
    success BOOLEAN DEFAULT TRUE,
    error_message TEXT,
    created_at TIMESTAMPTZ DEFAULT NOW()
);
```

Problems:
- No `user_id` — doesn't record who triggered the action.
- No `ip_address`, `user_agent` — no accountability.
- Only logs scheduling actions, not CRUD on students/modules/rooms.
- No hash chaining — anyone with DB access can modify the log undetected.
- No partitioning — grows unboundedly.
- `session_id` is nullable with no ON DELETE behavior — orphan rows if session is deleted.

V2 fixes all of these.

## Common junior developer mistakes

- **No `user_id` in audit log.** "Who did this?" is the #1 audit question. Always record it.
- **Logging in application code only.** A raw SQL UPDATE bypasses the application. Use DB triggers for critical tables.
- **No hash chaining.** An audit log that can be modified is not an audit log.
- **Logging PII.** Redact before writing — see [[6.5. PII Redaction and GDPR FERPA Compliance]].
- **No retention policy.** Audit logs grow forever. Partition by year and archive old partitions.
- **Synchronous audit writes blocking the request.** Use a queued listener or `AFTER` trigger to avoid blocking.
