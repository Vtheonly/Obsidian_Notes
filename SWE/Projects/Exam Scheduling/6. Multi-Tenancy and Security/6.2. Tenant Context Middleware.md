# 6.2. Tenant Context Middleware

> [!abstract] What this note teaches you
> V2's `SetTenantContext` middleware sets the `app.current_university_id` and `app.current_user_id` Postgres session variables on every authenticated request. These variables are read by RLS policies to enforce tenant isolation at the database layer. This note shows the middleware and explains the PgBouncer interaction.

## The middleware

```php
// app/Http/Middleware/SetTenantContext.php
declare(strict_types=1);

namespace App\Http\Middleware;

use Closure;
use Illuminate\Http\Request;
use Illuminate\Support\Facades\DB;
use Symfony\Component\HttpFoundation\Response;

class SetTenantContext
{
    public function handle(Request $request, Closure $next): Response
    {
        $user = $request->user();
        
        if ($user) {
            $universityId = $user->university_id;
            $userId = $user->id;
            
            // Set Postgres session variables for RLS policies
            DB::statement("SET app.current_university_id = ?", [$universityId]);
            DB::statement("SET app.current_user_id = ?", [$userId]);
        }
        
        return $next($request);
    }
}
```

## How it's registered

In `app/Http/Kernel.php`, the middleware is added to the `tenant` middleware group:

```php
protected $middlewareGroups = [
    'web' => [
        // ...
    ],
    'api' => [
        // ...
        'tenant',
    ],
    'tenant' => [
        SetTenantContext::class,
    ],
];
```

Every API route uses the `tenant` middleware:

```php
// routes/api.php
Route::middleware(['auth:sanctum', 'tenant'])->group(function () {
    Route::apiResource('sessions', SessionController::class);
    Route::post('sessions/{session}/generate', [SessionController::class, 'generate']);
    // ...
});
```

## How RLS policies use the variables

```sql
CREATE POLICY tenant_isolation_etudiants ON etudiants
    USING (university_id = current_setting('app.current_university_id', true)::bigint);
```

When a query runs:

```sql
SELECT * FROM etudiants WHERE matricule = 'ETU2024001';
```

Postgres silently rewrites it to:

```sql
SELECT * FROM etudiants
WHERE matricule = 'ETU2024001'
  AND university_id = current_setting('app.current_university_id', true)::bigint;
```

If `app.current_university_id` is set to 42, only etudiants with `university_id = 42` are returned. If it's not set (NULL), zero rows are returned — a safe default.

## The `current_setting(..., true)` second argument

The `true` argument means "return NULL if the variable is not set, instead of raising an exception". Without it, a missing variable would crash the query. With it, the policy matches zero rows (safe).

## The PgBouncer interaction

This is the tricky part. PgBouncer has three pooling modes:

| Mode | Session variables preserved? | V2 use |
|---|---|---|
| Session pooling | Yes — one backend per client | V2 web tier |
| Transaction pooling | No — backends recycled per transaction | V2 batch jobs |
| Statement pooling | No — backends recycled per statement | Not used |

For the Laravel web tier, V2 uses **session pooling**. Each Laravel worker holds a persistent Postgres backend; the `SET app.current_university_id` set in the middleware persists for the worker's lifetime.

But wait — Laravel workers handle multiple requests. If worker A handles request 1 (tenant 42) then request 2 (tenant 99), the session variable is still 42 when request 2 starts.

V2 solves this by re-issuing `SET app.current_university_id` on every request. The middleware always runs, overwriting the previous value. As long as the middleware runs before any DB query, the context is correct.

For batch jobs (queue workers), V2 uses transaction pooling with `SET LOCAL`:

```php
// Inside a queued job
DB::transaction(function () use ($tenantId) {
    DB::statement("SET LOCAL app.current_university_id = ?", [$tenantId]);
    // ... job logic ...
});
```

`SET LOCAL` scopes the variable to the current transaction, automatically resetting at COMMIT. This is safe with transaction pooling.

## Common junior developer mistakes

- **Forgetting to register the middleware.** If `SetTenantContext` isn't in the middleware group, no session variable is set, and RLS returns zero rows. The user sees an empty app, no error.
- **Using `SET` instead of `SET LOCAL` with transaction pooling.** `SET` persists for the session; with transaction pooling, the session is shared across tenants, leaking context.
- **Not handling unauthenticated requests.** The middleware checks `if ($user)`. Without this, a 401 response would crash.
- **Setting the variable after the first query.** The middleware must run before any DB query. If a controller does `User::find(1)` before the middleware runs, the query is unscoped.
- **Trusting the variable alone.** RLS is defense-in-depth. The app layer should also filter by `university_id` — see [[6.1. Multi-Tenancy Models Compared]].
