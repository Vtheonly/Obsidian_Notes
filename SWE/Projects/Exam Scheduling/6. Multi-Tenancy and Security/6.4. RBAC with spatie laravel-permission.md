# 6.4. RBAC with spatie/laravel-permission

> [!abstract] What this note teaches you
> V2 has 7 roles and a permission matrix that controls who can do what. This note is the full RBAC reference: roles, permissions, the `ExamSchedulePolicy` example, and how RBAC composes with RLS and token scopes for defense-in-depth.

## The 7 roles

| Role | Description | Typical user |
|---|---|---|
| `super_admin` | All permissions, all tenants | Platform operator |
| `vice_doyen` | View all, validate final, publish | Vice-dean of the faculty |
| `admin_planification` | Generate, clear, manual override | Scheduling office staff |
| `chef_dept` | View dept, validate dept | Department head |
| `professeur` | View own schedule, declare availability | Professor |
| `etudiant` | View own schedule | Student |
| `invigilateur` | View assigned exams, take attendance | Exam invigilator |

## The permission matrix

| Permission | super_admin | vice_doyen | admin_planification | chef_dept | professeur | etudiant | invigilateur |
|---|---|---|---|---|---|---|---|
| `scheduling.view` | ✅ | ✅ | ✅ | own dept | own | own | assigned |
| `scheduling.generate` | ✅ | ❌ | ✅ | ❌ | ❌ | ❌ | ❌ |
| `scheduling.validate_dept` | ✅ | ❌ | ❌ | own dept | ❌ | ❌ | ❌ |
| `scheduling.publish` | ✅ | ✅ | ❌ | ❌ | ❌ | ❌ | ❌ |
| `catalog.read` | ✅ | ✅ | ✅ | ✅ | own | ❌ | ❌ |
| `catalog.write` | ✅ | ❌ | ✅ | ❌ | ❌ | ❌ | ❌ |
| `enrollment.read` | ✅ | ✅ | ✅ | own dept | own | own | ❌ |
| `enrollment.write` | ✅ | ❌ | ✅ | ❌ | ❌ | ❌ | ❌ |
| `audit.read` | ✅ | ✅ | ❌ | own dept | ❌ | ❌ | ❌ |
| `analytics.view` | ✅ | ✅ | ✅ | own dept | ❌ | ❌ | ❌ |

"own" = the user can see only their own data. "own dept" = the user can see only their department's data. Enforced via Policies + RLS.

## The `spatie/laravel-permission` setup

```bash
composer require spatie/laravel-permission
php artisan vendor:publish --provider="Spatie\Permission\PermissionServiceProvider"
php artisan migrate
```

The package creates 5 tables: `roles`, `permissions`, `model_has_roles`, `model_has_permissions`, `role_has_permissions`.

## Defining roles and permissions

```php
// database/seeders/RolesAndPermissionsSeeder.php
public function run(): void
{
    // Reset cached roles and permissions
    app()[\Spatie\Permission\PermissionRegistrar::class]->forgetCachedPermission();

    // Create permissions
    Permission::firstOrCreate(['name' => 'scheduling.view']);
    Permission::firstOrCreate(['name' => 'scheduling.generate']);
    Permission::firstOrCreate(['name' => 'scheduling.validate_dept']);
    Permission::firstOrCreate(['name' => 'scheduling.publish']);
    Permission::firstOrCreate(['name' => 'catalog.read']);
    Permission::firstOrCreate(['name' => 'catalog.write']);
    // ...

    // Create roles and assign permissions
    Role::firstOrCreate(['name' => 'super_admin'])
        ->givePermissionTo(Permission::all());

    Role::firstOrCreate(['name' => 'vice_doyen'])
        ->givePermissionTo(['scheduling.view', 'scheduling.publish', 'catalog.read', 'enrollment.read', 'audit.read', 'analytics.view']);

    Role::firstOrCreate(['name' => 'admin_planification'])
        ->givePermissionTo(['scheduling.view', 'scheduling.generate', 'catalog.read', 'catalog.write', 'enrollment.read', 'enrollment.write', 'analytics.view']);

    Role::firstOrCreate(['name' => 'chef_dept'])
        ->givePermissionTo(['scheduling.view', 'scheduling.validate_dept', 'catalog.read', 'enrollment.read', 'audit.read', 'analytics.view']);

    Role::firstOrCreate(['name' => 'professeur'])
        ->givePermissionTo(['scheduling.view', 'catalog.read']);

    Role::firstOrCreate(['name' => 'etudiant'])
        ->givePermissionTo(['scheduling.view']);

    Role::firstOrCreate(['name' => 'invigilateur'])
        ->givePermissionTo(['scheduling.view']);
}
```

## The Policy pattern

Policies are Laravel's authorization layer for specific models. The `ExamSchedulePolicy`:

```php
// app/Policies/ExamSchedulePolicy.php
class ExamSchedulePolicy
{
    public function generate(User $user): bool
    {
        return $user->can('scheduling.generate');
    }

    public function view(User $user, ExamSchedule $schedule): bool
    {
        // Tenant isolation: user must be in the same university
        if ($user->university_id !== $schedule->university_id) {
            return false;
        }
        
        // Role-based: must have view permission
        if (!$user->can('scheduling.view')) {
            return false;
        }
        
        // Department scoping for chef_dept
        if ($user->hasRole('chef_dept')) {
            return $user->departement_id === $schedule->departement_id;
        }
        
        // Professor: only their own surveillances
        if ($user->hasRole('professeur')) {
            return $schedule->surveillant_principal_id === $user->professeur_id
                || $schedule->surveillances->contains('professeur_id', $user->professeur_id);
        }
        
        // Student: only their own exams
        if ($user->hasRole('etudiant')) {
            return $schedule->inscriptions->contains('etudiant_id', $user->etudiant_id);
        }
        
        // vice_doyen, admin_planification, super_admin: all
        return true;
    }

    public function validate(User $user, ExamSchedule $schedule): bool
    {
        return $user->can('scheduling.validate_dept')
            && $user->departement_id === $schedule->departement_id;
    }

    public function publish(User $user, ExamSchedule $schedule): bool
    {
        return $user->can('scheduling.publish');
    }
}
```

The policy is auto-resolved by Laravel when you type-hint it in the controller:

```php
public function generate(GenerateScheduleRequest $request, Session $session)
{
    $this->authorize('generate', $session);  // calls ExamSchedulePolicy::generate
    // ...
}
```

## Defense-in-depth: RBAC + RLS + token scopes

V2 enforces authorization at **three layers**:

1. **Token scopes (Sanctum):** the API token must have `schedule:write` scope. Checked in `GenerateScheduleRequest::authorize()`.
2. **RBAC (Policy):** the user must have the `scheduling.generate` permission. Checked in `$this->authorize('generate', $session)`.
3. **RLS:** the user's `university_id` must match the session's `university_id`. Enforced by the database.

If any one layer fails, the request is rejected. A bug in one layer doesn't compromise security.

## Common junior developer mistakes

- **Checking roles instead of permissions.** `$user->hasRole('admin')` is brittle — adding a new admin role breaks it. Use `$user->can('scheduling.generate')`.
- **No Policies, just inline checks.** `if (!$user->can('scheduling.generate')) abort(403)` scattered through controllers. Use Policies for centralization.
- **Forgetting tenant isolation in Policies.** A `chef_dept` from university A should not see university B's schedules. Always check `university_id`.
- **Super-admin bypasses RLS.** Don't give `BYPASSRLS` to application users. Filter explicitly in the Policy.
- **Not seeding roles and permissions.** A fresh database has no roles. Always run the seeder in migrations or deployments.
