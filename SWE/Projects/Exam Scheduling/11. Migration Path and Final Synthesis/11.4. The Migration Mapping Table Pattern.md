# 11.4. The Migration Mapping Table Pattern

> [!abstract] What this note teaches you
> V1 used `SERIAL` integer IDs; V2 uses UUIDs. To migrate data without losing referential integrity, V2 uses a temporary mapping table that translates legacy IDs to new UUIDs. This note shows the full migration SQL for reference and transactional data.

## The mapping table

```sql
-- database/migrations/v2_migration_temporary_holding.sql
CREATE TABLE temp_migration_mapping (
    legacy_id INT NOT NULL,
    new_uuid UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    entity_type VARCHAR(100) NOT NULL
);

CREATE INDEX idx_migration_legacy ON temp_migration_mapping (legacy_id, entity_type);
CREATE INDEX idx_migration_entity ON temp_migration_mapping (entity_type, new_uuid);
```

The table has three columns:
- `legacy_id` — V1's SERIAL integer.
- `new_uuid` — V2's UUID, generated automatically.
- `entity_type` — `'tenant'`, `'room'`, `'student'`, `'professor'`, `'module'`, etc.

The composite index on `(legacy_id, entity_type)` lets us look up "what's the new UUID for legacy room 42?".

## The migration in one transaction

```sql
-- database/migrations/v2_transformative_seeding_migration.sql
BEGIN;

-- 1. Populate temporary mappings for tenants (legacy departements → tenants)
INSERT INTO temp_migration_mapping (legacy_id, entity_type)
SELECT id, 'tenant' FROM departements;

-- 2. Populate tenants table using generated UUIDs
INSERT INTO tenants (id, name, subdomain, is_active)
SELECT 
    map.new_uuid, 
    old.nom, 
    LOWER(REPLACE(old.code, ' ', '-')), 
    TRUE
FROM departements old
JOIN temp_migration_mapping map ON old.id = map.legacy_id AND map.entity_type = 'tenant';

-- 3. Populate campuses (one per tenant, named "Main Campus")
INSERT INTO campuses (id, tenant_id, name)
SELECT 
    gen_random_uuid(), 
    tenant_map.new_uuid, 
    'Main University Campus'
FROM departements old
JOIN temp_migration_mapping tenant_map 
    ON old.id = tenant_map.legacy_id AND tenant_map.entity_type = 'tenant';

-- 4. Populate mappings for rooms (legacy lieu_examen → rooms)
INSERT INTO temp_migration_mapping (legacy_id, entity_type)
SELECT id, 'room' FROM lieu_examen;

-- 5. Populate rooms with the 20-seat TD cap rule
INSERT INTO rooms (id, campus_id, name, seating_capacity, exam_capacity, type, is_active)
SELECT 
    room_map.new_uuid, 
    (SELECT id FROM campuses LIMIT 1),  -- default campus
    old.nom, 
    old.capacite, 
    CASE 
        WHEN old.type = 'salle' THEN LEAST(old.capacite, 20)  -- TD 20-seat exam cap
        ELSE old.capacite 
    END,
    CASE 
        WHEN old.type = 'amphi' THEN 'amphitheater'
        WHEN old.type = 'labo' THEN 'computer_lab'
        ELSE 'classroom'
    END,
    TRUE
FROM lieu_examen old
JOIN temp_migration_mapping room_map 
    ON old.id = room_map.legacy_id AND room_map.entity_type = 'room';

-- 6. Populate mappings for students (legacy etudiants → student_profiles via users)
INSERT INTO temp_migration_mapping (legacy_id, entity_type)
SELECT id, 'student' FROM etudiants;

-- 7. Populate users + student_profiles
INSERT INTO users (id, tenant_id, email, password_hash, role, first_name, last_name)
SELECT 
    gen_random_uuid(),
    (SELECT tenant_map.new_uuid FROM temp_migration_mapping tenant_map 
     JOIN formations f ON f.id = old.formation_id
     JOIN departements d ON f.departement_id = d.id
     JOIN temp_migration_mapping tenant_map ON d.id = tenant_map.legacy_id 
     WHERE tenant_map.entity_type = 'tenant'),
    COALESCE(old.email, 'migrated_' || old.id || '@placeholder.univ.dz'),
    'MIGRATED_NEEDS_RESET',  -- force password reset on first login
    'student',
    old.prenom,
    old.nom
FROM etudiants old;

-- (student_profiles similar, joining on users via email)

-- 8. Migrate inscriptions (the bulk — 130k+ rows at baseline)
INSERT INTO inscriptions (id, tenant_id, student_id, module_id, academic_period_id, annee_universitaire, statut, created_at)
SELECT 
    gen_random_uuid(),
    -- tenant_id from the student's formation's department
    (SELECT tenant_map.new_uuid FROM temp_migration_mapping tenant_map 
     JOIN formations f ON i_old.formation_id = f.id  -- (this join is on etudiants, see below)
     ...),
    student_map.new_uuid,
    module_map.new_uuid,
    period_id,  -- resolved from annee_universitaire
    i_old.annee_universitaire,
    i_old.statut,
    i_old.created_at
FROM inscriptions i_old
JOIN temp_migration_mapping student_map ON i_old.etudiant_id = student_map.legacy_id AND student_map.entity_type = 'student'
JOIN temp_migration_mapping module_map ON i_old.module_id = module_map.legacy_id AND module_map.entity_type = 'module';

-- 9. Migrate examens → exams + exam_allocations (split the table)
INSERT INTO exams (id, tenant_id, module_id, academic_period_id, timeslot_id, is_locked)
SELECT 
    gen_random_uuid(),
    ...,
    module_map.new_uuid,
    ...,
    timeslot_map.new_uuid,  -- resolved from creneau_id
    FALSE
FROM examens e_old
JOIN temp_migration_mapping module_map ON e_old.module_id = module_map.legacy_id;

INSERT INTO exam_allocations (id, tenant_id, exam_id, room_id, allocated_students)
SELECT 
    gen_random_uuid(),
    ...,
    exam_map.new_uuid,  -- from the exams insert above
    room_map.new_uuid,
    e_old.nb_etudiants_prevus
FROM examens e_old
JOIN temp_migration_mapping room_map ON e_old.lieu_id = room_map.legacy_id AND room_map.entity_type = 'room';

-- 10. Migrate schedule_logs → audit_log
INSERT INTO audit_log (id, tenant_id, user_id, action, entity_type, entity_id, payload_after, created_at)
SELECT 
    gen_random_uuid(),
    NULL,  -- V1 didn't record tenant; can't recover
    NULL,  -- V1 didn't record user_id; can't recover
    'schedule_' || action,
    'session',
    session_id,
    details::jsonb,
    created_at
FROM schedule_logs;

COMMIT;
```

## Why one big transaction

The migration runs in a single `BEGIN; ... COMMIT;` so that either all data migrates or none does. If step 8 fails (e.g. a FK violation), the entire migration rolls back — no partial state.

For very large datasets (800k+ inscriptions), this transaction may be too large. In that case, batch the inserts:

```sql
-- Batch the inscriptions insert
DO $$
DECLARE
    batch_size INT := 10000;
    offset_val INT := 0;
BEGIN
    LOOP
        INSERT INTO inscriptions (...)
        SELECT ... FROM inscriptions_old
        OFFSET offset_val LIMIT batch_size;
        
        GET DIAGNOSTICS batch_size = ROW_COUNT;
        EXIT WHEN batch_size = 0;
        
        offset_val := offset_val + 10000;
        COMMIT;  -- commit each batch
    END LOOP;
END $$;
```

But this sacrifices atomicity. For V2's scale (130k baseline), a single transaction is fine.

## The 20-seat TD cap rule

V1's seed set `capacite = 20` for "Salle" rows as a data convention. The migration enforces this in the schema:

```sql
CASE 
    WHEN old.type = 'salle' THEN LEAST(old.capacite, 20)
    ELSE old.capacite 
END
```

If a V1 salle had `capacite = 40` (someone ignored the convention), the migration caps `exam_capacity` at 20. This fixes the V1 data quality issue during migration.

## Post-migration cleanup

```sql
-- Verify row counts
SELECT 'etudiants' AS table, COUNT(*) FROM etudiants
UNION ALL SELECT 'users (students)', COUNT(*) FROM users WHERE role = 'student'
UNION ALL SELECT 'inscriptions_old', COUNT(*) FROM inscriptions_old
UNION ALL SELECT 'inscriptions', COUNT(*) FROM inscriptions;

-- Drop the mapping table after verification
DROP TABLE temp_migration_mapping;

-- Drop the old V1 tables (after a backup)
DROP TABLE etudiants, professeurs, modules, formations, departements, 
         lieu_examen, inscriptions_old, examens_old, schedule_logs, creneaux, sessions_examen;
```

## Common junior developer mistakes

- **No mapping table.** Trying to migrate without a mapping table loses referential integrity. Always use one.
- **Migrating without a transaction.** Partial migration = broken state. Wrap in `BEGIN/COMMIT`.
- **Forgetting the 20-seat TD cap.** V1's data convention may not be enforced. Apply it during migration.
- **Not verifying row counts.** "It worked" — did it? Count rows before and after each table.
- **Dropping old tables too soon.** Keep them for 30 days as a fallback. Drop only after verification.
- **Forgetting to migrate audit logs.** Compliance requires historical audit data. Plan for it.
