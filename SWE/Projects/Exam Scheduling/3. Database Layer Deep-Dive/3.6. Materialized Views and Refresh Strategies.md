# 3.6. Materialized Views and Refresh Strategies

> [!abstract] What this note teaches you
> V1 computed the module conflict matrix as a temp table on every scheduling run — taking 5–30 seconds just for setup. V2 precomputes it as a materialized view (`mv_module_conflicts`) refreshed before each run. This note explains materialized views, the `CONCURRENTLY` refresh option, and the unique-index requirement that makes it possible.

## What a materialized view is

A regular view is a saved query — it executes fresh on every access. A **materialized view** is a saved query whose **result is stored on disk** and refreshed on demand.

```sql
CREATE MATERIALIZED VIEW mv_module_enrollments AS
SELECT
    m.id AS module_id,
    m.code AS module_code,
    m.formation_id,
    f.departement_id,
    m.university_id,
    i.annee_universitaire_id,
    COUNT(DISTINCT i.etudiant_id) FILTER (WHERE i.statut IN ('inscrit','rattrapage')) AS nb_inscrits_actifs,
    COUNT(DISTINCT i.etudiant_id) FILTER (WHERE i.statut = 'valide') AS nb_valides,
    m.duree_examen_minutes
FROM modules m
JOIN formations f ON m.formation_id = f.id
LEFT JOIN inscriptions i ON i.module_id = m.id AND i.deleted_at IS NULL
WHERE m.deleted_at IS NULL
GROUP BY m.id, m.code, m.formation_id, f.departement_id, m.university_id,
         i.annee_universitaire_id, m.duree_examen_minutes;

CREATE UNIQUE INDEX ON mv_module_enrollments (module_id, annee_universitaire_id);
CREATE INDEX ON mv_module_enrollments (university_id, departement_id);
```

Now `SELECT * FROM mv_module_enrollments WHERE module_id = 42` is an index scan, not a 5-table aggregation.

## The two V2 materialized views

### `mv_module_enrollments` — refreshed nightly

Precomputes per-module enrollment counts. Used by:
- The dashboard's "scheduled modules" KPI.
- The CP-SAT solver's input (avoids re-counting inscriptions).
- The chef-dept validation page (per-formation enrollment breakdown).

Refresh schedule: nightly at 02:00 via `pg_cron`:

```sql
SELECT cron.schedule(
    'refresh_enrollments',
    '0 2 * * *',
    'REFRESH MATERIALIZED VIEW CONCURRENTLY mv_module_enrollments'
);
```

### `mv_module_conflicts` — refreshed before each scheduling run

Precomputes the pairwise module conflict graph: every pair of modules sharing ≥1 student.

```sql
CREATE MATERIALIZED VIEW mv_module_conflicts AS
SELECT
    i1.module_id AS m1,
    i2.module_id AS m2,
    i1.university_id,
    i1.annee_universitaire_id,
    COUNT(DISTINCT i1.etudiant_id) AS shared_students
FROM inscriptions i1
JOIN inscriptions i2
    ON i1.etudiant_id = i2.etudiant_id
   AND i1.module_id < i2.module_id
   AND i1.university_id = i2.university_id
   AND i1.annee_universitaire_id = i2.annee_universitaire_id
WHERE i1.statut IN ('inscrit','rattrapage')
  AND i2.statut IN ('inscrit','rattrapage')
  AND i1.deleted_at IS NULL
  AND i2.deleted_at IS NULL
GROUP BY i1.module_id, i2.module_id, i1.university_id, i1.annee_universitaire_id;

CREATE UNIQUE INDEX ON mv_module_conflicts (annee_universitaire_id, m1, m2);
CREATE INDEX ON mv_module_conflicts (m1);
CREATE INDEX ON mv_module_conflicts (m2);
```

Refresh schedule: immediately before each scheduling run, inside `GenerateScheduleJob::handle`:

```php
DB::statement("REFRESH MATERIALIZED VIEW CONCURRENTLY mv_module_conflicts");
```

This is the V2 fix for V1's `temp_module_conflicts` temp table — see [[2.5. PL-pgSQL Anti-Patterns]] anti-pattern 1.

## `REFRESH MATERIALIZED VIEW CONCURRENTLY`

The plain `REFRESH MATERIALIZED VIEW mv` locks the view for the duration of the refresh, blocking all reads. This is unacceptable in production.

`REFRESH MATERIALIZED VIEW CONCURRENTLY mv` refreshes without blocking reads. It does this by building a new copy in the background, then atomically swapping it in.

**Requirement:** the view must have at least one `UNIQUE INDEX`. Without it, Postgres cannot track which rows to update in place, and the `CONCURRENTLY` keyword is rejected.

This is why both V2 materialized views have `CREATE UNIQUE INDEX ON ...` immediately after creation. The unique index is not just for query performance — it is a prerequisite for concurrent refresh.

```sql
-- This works:
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_module_enrollments;

-- This fails (no unique index):
REFRESH MATERIALIZED VIEW CONCURRENTLY some_view_without_unique_index;
-- ERROR: CONCURRENTLY cannot be used when the materialized view is not populated using a unique index
```

## Why V1's temp-table approach was bad

V1's `generate_schedule` function did this on every run:

```sql
DROP TABLE IF EXISTS temp_module_conflicts;
CREATE TEMP TABLE temp_module_conflicts AS
SELECT i1.module_id AS m1, i2.module_id AS m2
FROM inscriptions i1
JOIN inscriptions i2 ON i1.etudiant_id = i2.etudiant_id
WHERE i1.module_id < i2.module_id;
CREATE INDEX idx_temp_conflicts ON temp_module_conflicts (m1, m2);
```

Three problems:

1. **Catalog bloat** — temp table creation writes to `pg_class`, `pg_attribute`, `pg_type` on every run. See [[2.5. PL-pgSQL Anti-Patterns]].
2. **No reuse** — the conflict matrix is the same for any scheduling run on the same session, but it's recomputed every time.
3. **No cross-run caching** — even within the same session, regenerating the schedule re-builds the matrix from scratch.

The V2 materialized view:
- Has no catalog bloat (it's a permanent object, created once).
- Is reused across runs within the same academic year.
- Refreshes incrementally via `CONCURRENTLY`.

## Refresh strategy trade-offs

| Strategy | When to refresh | Pros | Cons |
|---|---|---|---|
| Nightly via `pg_cron` | Once a day at 02:00 | Cheap, predictable | Up to 24h stale |
| Before each scheduling run | Inside `GenerateScheduleJob` | Always current | Adds 5–30s to each run |
| On `AFTER INSERT/UPDATE` trigger | Real-time | Always current | High write amplification |
| Manual `REFRESH` button | On admin demand | Admin control | Admin forgets |

V2 uses nightly for `mv_module_enrollments` (enrollments change slowly) and before-each-run for `mv_module_conflicts` (must reflect the latest inscriptions at solve time).

## Common junior developer mistakes

- **Using a regular view when a materialized view is needed.** If the underlying query is expensive and the result doesn't need to be real-time, materialize it.
- **Forgetting the unique index.** `REFRESH ... CONCURRENTLY` will fail without it.
- **Using `REFRESH MATERIALIZED VIEW` (non-concurrent) in production.** It blocks reads. Always use `CONCURRENTLY`.
- **Refreshing too often.** A materialized view that refreshes every minute is basically a regular view with extra overhead. Find the right cadence.
- **Not refreshing at all.** A stale materialized view is worse than a regular view — it gives wrong answers confidently. Always have a refresh schedule.
