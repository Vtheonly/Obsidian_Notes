# 3.5. Table Partitioning: LIST and RANGE

> [!abstract] What this note teaches you
> V2 partitions `inscriptions` and `examens` by `LIST (annee_universitaire)` and `audit_log` by `RANGE (created_at)`. This note explains why each strategy is chosen, what constraints partitioned tables impose (the partition key must be in the PK), and how `pg_cron` auto-creates future partitions.

## What partitioning buys you

Partitioning splits a large logical table into smaller physical tables. Benefits:

1. **Partition pruning** — the planner skips partitions that cannot contain matching rows.
2. **Faster VACUUM** — each partition is vacuumed independently.
3. **Easier archival** — drop or detach old partitions instead of `DELETE`.
4. **Smaller indexes per partition** — B-Trees are O(log N); smaller N means faster lookups.

## LIST partitioning: `inscriptions` and `examens`

For tables where queries always filter by a categorical key (academic year, tenant ID), `LIST` partitioning is ideal.

```sql
CREATE TABLE inscriptions (
    id                      BIGINT GENERATED ALWAYS AS IDENTITY,
    university_id           BIGINT NOT NULL,
    etudiant_id             BIGINT NOT NULL,
    module_id               BIGINT NOT NULL,
    annee_universitaire_id  BIGINT NOT NULL,
    annee_universitaire     CHAR(9) NOT NULL,  -- partition key
    statut                  TEXT NOT NULL DEFAULT 'inscrit'
                            CHECK (statut IN ('inscrit','valide','rattrapage','abandonne','transfere')),
    note                    NUMERIC(4,2) CHECK (note IS NULL OR (note BETWEEN 0 AND 20)),
    created_at              TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at              TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    deleted_at              TIMESTAMPTZ,
    PRIMARY KEY (id, annee_universitaire),  -- partition key MUST be in PK
    UNIQUE (etudiant_id, module_id, annee_universitaire_id)
) PARTITION BY LIST (annee_universitaire);

CREATE TABLE inscriptions_2024_2025 PARTITION OF inscriptions FOR VALUES IN ('2024-2025');
CREATE TABLE inscriptions_2025_2026 PARTITION OF inscriptions FOR VALUES IN ('2025-2026');
CREATE TABLE inscriptions_2026_2027 PARTITION OF inscriptions FOR VALUES IN ('2026-2027');
CREATE TABLE inscriptions_default PARTITION OF inscriptions DEFAULT;
```

The `DEFAULT` partition catches any value not explicitly listed — important so that an unexpected year code doesn't fail the INSERT.

### Why LIST by `annee_universitaire` and not by `tenant_id`?

The source documents disagreed. CODE_REVIEW_AND_REDESIGN_02 partitions `inscriptions` by `LIST (tenant_id)`. CODE_REVIEW_AND_REDESIGN_01 partitions by `LIST (annee_universitaire)`. V2 picks `annee_universitaire` because:

- Queries always filter by year (scheduling runs against the current year).
- Each year's data is independent (no cross-year joins in the hot path).
- Old years can be archived by detaching the partition.
- Tenant isolation is already handled by RLS — see [[3.7. Row-Level Security for Multi-Tenancy]].

If you have 100+ tenants and only 5 years, partitioning by tenant makes more sense. V2's 100k-students-per-tenant / 5-year-retention profile favors year partitioning.

## RANGE partitioning: `audit_log`

For append-only time-series data, `RANGE` partitioning by time is the standard pattern.

```sql
CREATE TABLE audit_log (
    id              BIGINT GENERATED ALWAYS AS IDENTITY,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    university_id   BIGINT NOT NULL,
    user_id         BIGINT,
    action          TEXT NOT NULL,
    entity_type     TEXT NOT NULL,
    entity_id       BIGINT,
    before_data     JSONB,
    after_data      JSONB,
    ip_address      INET,
    user_agent      TEXT,
    PRIMARY KEY (id, created_at)  -- partition key MUST be in PK
) PARTITION BY RANGE (created_at);

CREATE TABLE audit_log_2025 PARTITION OF audit_log
    FOR VALUES FROM ('2025-01-01') TO ('2026-01-01');
CREATE TABLE audit_log_2026 PARTITION OF audit_log
    FOR VALUES FROM ('2026-01-01') TO ('2027-01-01');
CREATE TABLE audit_log_default PARTITION OF audit_log DEFAULT;
```

RANGE partitioning on `created_at` lets you:
- Drop or detach old partitions when the retention policy expires (e.g. "keep 7 years").
- Run `VACUUM FULL` on individual partitions without locking the whole table.
- Combined with BRIN index on `created_at`, get extremely compact indexes.

## Partitioned table constraints

Postgres imposes two key constraints on partitioned tables:

### 1. Partition key must be in the primary key

```sql
PRIMARY KEY (id, annee_universitaire)  -- NOT just (id)
```

This is because uniqueness must be enforceable per-partition. If `id` alone were the PK, two different partitions could theoretically have rows with the same `id`.

### 2. UNIQUE constraints must include the partition key

```sql
UNIQUE (etudiant_id, module_id, annee_universitaire_id)
-- NOT: UNIQUE (etudiant_id, module_id)
```

Same reason — uniqueness can only be enforced within a partition.

This is why V2's `inscriptions` unique constraint includes `annee_universitaire_id`: without it, the same student could be inscribed in the same module in different years (which is legitimate — a redoublant retakes the module).

## Indexes on partitioned tables

When you `CREATE INDEX` on a partitioned parent table, Postgres automatically creates the same index on every existing and future partition. This is the **partitioned index** feature.

```sql
CREATE INDEX idx_inscriptions_module
    ON inscriptions (module_id, etudiant_id)
    WHERE statut IN ('inscrit','rattrapage') AND deleted_at IS NULL;
```

This single statement creates a partial index on `inscriptions_2024_2025`, `inscriptions_2025_2026`, `inscriptions_2026_2027`, and the default partition — and on any future partitions automatically.

## Auto-creating future partitions with `pg_cron`

If you forget to create next year's partition before January 1, all INSERTs on January 1 go to the `DEFAULT` partition, which becomes a bottleneck. V2 prevents this with a `pg_cron` job:

```sql
-- Create next year's partitions on January 1st at midnight
SELECT cron.schedule(
    'create_next_year_partitions',
    '0 0 1 * *',
    $$ SELECT create_next_year_partitions(); $$
);
```

The `create_next_year_partitions()` function (defined in a migration) loops over `inscriptions`, `examens`, `audit_log` and creates the next year's partition if it doesn't exist.

See [[10.6. The pg-cron Scheduler for Background DB Jobs]] for the full `pg_cron` setup.

## Partition pruning in action

When a query filters by the partition key, the planner prunes partitions:

```sql
EXPLAIN SELECT COUNT(*) FROM inscriptions
WHERE annee_universitaire = '2025-2026'
  AND statut = 'inscrit';
```

The plan shows only `inscriptions_2025_2026` is scanned — not the 2024 or 2026 partitions. This is what makes partitioning worthwhile: at 800k inscriptions/year, scanning one year instead of all 5 years is a 5× speedup.

## When NOT to partition

- **Tables under 1M rows.** Partitioning adds overhead (catalog lookups, planning time) that isn't worth it for small tables.
- **Tables that don't have a natural partition key.** If queries don't filter by a consistent column, partition pruning won't help.
- **Tables with frequent cross-partition queries.** If you regularly need `SELECT * FROM inscriptions WHERE etudiant_id = ?` across all years, partitioning by year doesn't help.

V2 partitions only `inscriptions`, `examens`, and `audit_log` — the three tables that grow unboundedly and are always queried by year. Everything else stays unpartitioned.

## Common junior developer mistakes

- **Partitioning by a column you never query.** If queries don't filter by `tenant_id`, partitioning by it gives no pruning benefit.
- **Forgetting to include the partition key in the PK.** Postgres will refuse to create the table.
- **Relying on the `DEFAULT` partition in production.** The default partition catches unexpected values but becomes a bottleneck if it grows. Always create explicit partitions ahead of time.
- **Forgetting `pg_cron` to auto-create future partitions.** January 1 comes every year. Automate it.
- **Partitioning too aggressively.** 100 partitions on a 1M-row table is worse than no partitioning — the planning overhead dominates.
