# 3.4. EXCLUDE Constraints and btree_gist

> [!abstract] What this note teaches you
> V1 detected time-range overlaps with triggers that did exact-time matching — missing overlapping-but-not-equal slots. V2 uses PostgreSQL's `EXCLUDE USING gist` constraint with the `&&` (overlap) operator on `TSTZRANGE` columns. This note explains the constraint, the `btree_gist` extension it requires, and why it beats triggers.

## The problem V1 failed to solve

V1's `check_professor_availability` trigger detected conflicts using **exact (date, heure_debut) match**:

```sql
WHERE e.surveillant_principal_id = NEW.surveillant_principal_id
  AND c.date_examen = v_creneau_info.date_examen
  AND c.heure_debut = v_creneau_info.heure_debut   -- EXACT match
```

This misses the case where creneau 1 is 10:00–12:00 and creneau 2 is 11:00–13:00. The professor is double-booked from 11:00 to 12:00, but the trigger sees different `heure_debut` values and reports no conflict.

The correct check is **time-range overlap**: do the two time ranges intersect? Mathematically: `[start1, end1) ∩ [start2, end2) ≠ ∅`.

## The PostgreSQL solution: EXCLUDE USING gist

PostgreSQL has a declarative constraint for exactly this: `EXCLUDE USING gist`. It prevents two rows in the same table from satisfying a given predicate (typically overlap).

```sql
ALTER TABLE examens
    ADD CONSTRAINT excl_examen_room_slot
    EXCLUDE USING gist (
        lieu_id WITH =,
        periode_ts WITH &&
    ) WHERE (statut NOT IN ('annule','lock') AND deleted_at IS NULL);
```

This says: no two active (non-cancelled, non-deleted) rows in `examens` may have the same `lieu_id` AND overlapping `periode_ts` ranges. If you try to INSERT a conflicting row, Postgres raises:

```
ERROR: conflicting key value violates exclusion constraint "excl_examen_room_slot"
DETAIL: Key (lieu_id, periode_ts)=(42, ["2026-01-15 10:00:00+00","2026-01-15 12:00:00+00")) conflicts with existing key (lieu_id, periode_ts)=(42, ["2026-01-15 11:00:00+00","2026-01-15 13:00:00+00")).
```

## Why `btree_gist` is required

GIST indexes natively support range types (`TSTZRANGE`, `DATERANGE`, `INT4RANGE`) and geometric types. They do **not** natively support scalar types like `BIGINT` or `TEXT`.

The `excl_examen_room_slot` constraint mixes:
- `lieu_id BIGINT` (scalar) — needs `=` operator.
- `periode_ts TSTZRANGE` (range) — needs `&&` operator.

The `btree_gist` extension adds GIST support for scalar types, making the mixed constraint possible:

```sql
CREATE EXTENSION IF NOT EXISTS "btree_gist";
```

Without this extension, the `ALTER TABLE ... ADD CONSTRAINT EXCLUDE USING gist (lieu_id WITH =, periode_ts WITH &&)` will fail with:

```
ERROR: data type bigint has no default operator class for access method "gist"
```

## The `periode_ts` generated column

The `periode_ts TSTZRANGE` doesn't need to be inserted manually — it's a generated column:

```sql
CREATE TABLE creneaux (
    id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    session_id    BIGINT NOT NULL REFERENCES sessions_examen(id) ON DELETE RESTRICT,
    date_examen   DATE NOT NULL,
    heure_debut   TIME NOT NULL,
    heure_fin     TIME NOT NULL,
    periode_ts    TSTZRANGE GENERATED ALWAYS AS (
                    tstzrange((date_examen + heure_debut)::timestamptz,
                              (date_examen + heure_fin)::timestamptz)
                  ) STORED,
    ...
);
```

The `GENERATED ALWAYS AS (...) STORED` clause computes the range from `date_examen + heure_debut` and `date_examen + heure_fin` automatically on INSERT and UPDATE. You cannot write to it directly. See [[3.10. Generated Columns and CITEXT]].

The `examens` table then needs a way to expose `periode_ts` for the EXCLUDE constraint. Two options:

### Option A: Denormalize `periode_ts` onto `examens`

Add a `periode_ts TSTZRANGE` column to `examens` (also generated, but you'd need a JOIN to `creneaux` — generated columns can't reference other tables, so this requires a trigger to maintain).

### Option B: Use a simpler partial UNIQUE index

For the common case where every exam fits exactly in one creneau (no partial-slot exams), the EXCLUDE reduces to a partial UNIQUE:

```sql
CREATE UNIQUE INDEX uq_examen_lieu_creneau
    ON examens (lieu_id, creneau_id)
    WHERE statut NOT IN ('annule') AND deleted_at IS NULL;
```

V2 uses Option B as the production form because all creneaux are 2 hours and all exams are ≤ 120 minutes. If your institution has variable-length creneaux, implement Option A.

## EXCLUDE vs trigger: a comparison

| Property | EXCLUDE constraint | Trigger |
|---|---|---|
| Declarative | Yes — part of schema | No — procedural code |
| Visible in `\d+` constraints section | Yes | No (separate "Triggers" section) |
| Can be disabled by `ALTER TABLE` | No (requires `DROP CONSTRAINT`) | Yes (`DISABLE TRIGGER`) |
| Performance | Index-based, O(log N) | Per-row, often O(N) |
| Error message | Specific, mentions the conflicting key | Custom (whatever you RAISE) |
| Handles overlaps natively | Yes (`&&` operator) | No (you write the logic) |
| Can be bypassed by superuser | No (constraints always enforced) | Yes (`DISABLE TRIGGER`) |

EXCLUDE wins on every axis except flexibility — triggers can enforce arbitrarily complex rules. For time-range overlap, EXCLUDE is strictly better.

## Other EXCLUDE use cases

EXCLUDE is not just for rooms. V2 could also use it for:

### Professor time overlap

```sql
ALTER TABLE examens
    ADD CONSTRAINT excl_examen_prof_slot
    EXCLUDE USING gist (
        surveillant_principal_id WITH =,
        periode_ts WITH &&
    ) WHERE (surveillant_principal_id IS NOT NULL
             AND statut NOT IN ('annule')
             AND deleted_at IS NULL);
```

This replaces V1's `check_professor_availability` trigger entirely.

### Professor daily count (cannot use EXCLUDE)

The "max 3 proctorings per day" rule is a count, not an overlap. EXCLUDE cannot enforce counts. V2 keeps a trigger for this — see [[3.8. Constraints vs Triggers When to Use Each]].

## Common junior developer mistakes

- **Forgetting `btree_gist`.** The EXCLUDE will fail with a confusing error. Always `CREATE EXTENSION IF NOT EXISTS btree_gist` before adding mixed-type EXCLUDE constraints.
- **Using `=` instead of `&&` for ranges.** `WITH =` means "must be equal"; `WITH &&` means "must overlap". For overlap prevention you want `&&`.
- **Forgetting the `WHERE` clause.** Without `WHERE statut NOT IN ('annule') AND deleted_at IS NULL`, the constraint applies to cancelled and deleted rows too, preventing you from inserting a new exam in a slot previously held by a cancelled one.
- **Storing `periode_ts` as a regular column.** Use a generated column — it's always consistent with `date_examen` and `heure_debut/fin`. Manual maintenance is a bug source.
- **Trying to use EXCLUDE for counts.** It doesn't work. EXCLUDE is for pairwise conflicts, not aggregates.
