# 3.7. Row-Level Security (RLS) for Multi-Tenancy

> [!abstract] What this note teaches you
> V1 had no tenant isolation — every visitor saw every university's data. V2 enforces tenant isolation at the database layer using PostgreSQL Row-Level Security (RLS) policies scoped by `current_setting('app.current_university_id')`. This is defense-in-depth: even if the app layer forgets to filter, the database refuses to return cross-tenant rows.

## What RLS is

Row-Level Security is a PostgreSQL feature that silently appends a `WHERE` clause to every query on a table. The clause is defined by a **policy**, and the policy can reference session variables set by the application.

```mermaid
flowchart LR
    App[Laravel app] --> MW[SetTenantContext middleware]
    MW -->|SET app.current_university_id = 42| DB[(Postgres)]
    DB --> Policy[RLS Policy:<br/>USING university_id = current_setting<br/>app.current_university_id)]
    Policy --> Filter[Filter applied to every query]
    Filter --> Result[Only university 42 rows returned]
```

## The 3-step setup

### Step 1: Enable RLS on the table

```sql
ALTER TABLE etudiants ENABLE ROW LEVEL SECURITY;
ALTER TABLE professeurs ENABLE ROW LEVEL SECURITY;
ALTER TABLE modules ENABLE ROW LEVEL SECURITY;
ALTER TABLE inscriptions ENABLE ROW LEVEL SECURITY;
ALTER TABLE examens ENABLE ROW LEVEL SECURITY;
ALTER TABLE lieu_examen ENABLE ROW LEVEL SECURITY;
ALTER TABLE sessions_examen ENABLE ROW LEVEL SECURITY;
ALTER TABLE creneaux ENABLE ROW LEVEL SECURITY;
ALTER TABLE surveillances ENABLE ROW LEVEL SECURITY;
```

After this, **all rows are invisible** by default (except to table owners and roles with `BYPASSRLS`).

### Step 2: Create the policy

```sql
CREATE POLICY tenant_isolation_etudiants ON etudiants
    USING (university_id = current_setting('app.current_university_id', true)::bigint);

CREATE POLICY tenant_isolation_professeurs ON professeurs
    USING (university_id = current_setting('app.current_university_id', true)::bigint);

-- ... one policy per tenant-scoped table
```

The `USING` clause is silently appended to every `SELECT`, `UPDATE`, `DELETE` on the table. The `current_setting('app.current_university_id', true)` reads the Postgres session variable; the `true` argument means "return NULL if not set" (rather than raising an exception).

### Step 3: Set the session variable per request

The Laravel `SetTenantContext` middleware runs on every authenticated request:

```php
// app/Http/Middleware/SetTenantContext.php
class SetTenantContext
{
    public function handle(Request $request, Closure $next): Response
    {
        $universityId = $request->user()?->university_id;
        if ($universityId) {
            DB::statement("SET app.current_university_id = ?", [$universityId]);
            DB::statement("SET app.current_user_id = ?", [$request->user()->id]);
        }
        return $next($request);
    }
}
```

Now every query run during this request is automatically scoped to the user's university. No `WHERE university_id = ?` needed in application code — the policy enforces it.

## The `BYPASSRLS` escape hatch

Table owners and roles with the `BYPASSRLS` attribute skip RLS. This is necessary for:
- Migrations (need to write cross-tenant data).
- Backups (`pg_dump` reads all rows).
- The `super_admin` role (if you want them to see all tenants).

V2 reserves `BYPASSRLS` for the migration user only. Application users (including `super_admin`) get normal RLS-scoped access. A `super_admin` who needs cross-tenant visibility uses a separate read-only reporting connection with explicit `SET app.current_university_id = '*'` (and a policy that allows it).

## RLS with partitioned tables

`inscriptions` and `examens` are partitioned by `annee_universitaire`, but RLS filters by `university_id`. These are orthogonal:

- Partition pruning is a query-planner optimization (which physical table to scan).
- RLS is a security filter (which rows to return).

Both apply. A query for `university_id = 42 AND annee_universitaire = '2025-2026'` prunes to the `inscriptions_2025_2026` partition AND filters by `university_id = 42`. The two work together cleanly.

## RLS with `current_setting` and connection pooling

**The big caveat:** `SET app.current_university_id = ?` sets a session variable. With PgBouncer in **transaction pooling mode**, sessions are not preserved across transactions — each transaction may run on a different backend.

V2 handles this by:
1. Using PgBouncer in **session pooling mode** for the Laravel web tier (one persistent backend per Laravel worker).
2. Or re-issuing `SET LOCAL app.current_university_id = ?` inside each transaction (transaction-scoped, automatically reset at COMMIT).

The simpler production setup is session pooling for the web tier and transaction pooling for batch jobs (which set their own context per job).

## Why RLS alone is not enough

RLS is **defense-in-depth**, not the only security layer. A bug in `SetTenantContext` (e.g. forgetting to call it on a route) would leave `app.current_university_id` unset, and `current_setting(..., true)` returns NULL. The policy `WHERE university_id = NULL` matches zero rows — so the user sees nothing (not the wrong tenant's data, but also not their own).

To prevent this, V2 also:
- Filters by `university_id` explicitly in service-layer queries (belt).
- Enforces `university_id === session.university_id` in Laravel Policies (suspenders).
- Returns 403 if `app.current_university_id` is not set on an authenticated request (canary).

The principle: **never trust a single layer**. If any one layer fails, the others catch it.

## RLS performance

RLS adds a `WHERE university_id = ?` clause to every query. As long as `university_id` is indexed (which it always is in V2 — every tenant-scoped table has an index on `university_id`), the performance impact is negligible.

If you forget the index, every query becomes a seq scan filtered by RLS. Always index the RLS column.

## Common junior developer mistakes

- **Enabling RLS but not creating a policy.** All rows become invisible. Always test with `SELECT * FROM etudiants LIMIT 1` after enabling.
- **Using `current_setting('app.x')` without the `true` argument.** If the variable isn't set, this raises an exception. Use `current_setting('app.x', true)` to return NULL instead.
- **Forgetting to set the session variable in middleware.** RLS policies silently match zero rows. The user sees an empty app, no error.
- **Using `BYPASSRLS` for the application user.** This defeats the entire purpose. Reserve it for migrations and backups.
- **Not indexing the RLS column.** Every query becomes a seq scan.
- **Mixing RLS with manual `WHERE university_id = ?` filters.** It's not wrong (defense-in-depth), but make sure your tests cover both layers failing independently.
