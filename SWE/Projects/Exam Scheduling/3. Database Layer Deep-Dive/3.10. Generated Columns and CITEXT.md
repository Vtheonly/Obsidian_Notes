# 3.10. Generated Columns and CITEXT

> [!abstract] What this note teaches you
> V2 uses PostgreSQL generated columns to compute `jour`, `periode_ts`, and (recommended) `nb_inscrits_actifs` automatically — no trigger maintenance, no stale values. V2 also uses `CITEXT` for case-insensitive email uniqueness. This note explains both features and the V1 anti-patterns they replace.

## Generated columns: the idea

A **generated column** is a column whose value is computed from other columns in the same row. PostgreSQL supports two flavors:

- `STORED` — computed on write, stored on disk. Can be indexed. Cannot be written to directly.
- `VIRTUAL` — computed on read. Not yet supported in PostgreSQL 17 (planned for future versions).

V2 uses `STORED` exclusively.

```sql
column_name TYPE GENERATED ALWAYS AS (expression) STORED
```

The expression must be **immutable** — it cannot call functions like `NOW()` or reference other tables. It can only use deterministic functions of the same row's columns.

## V2 generated column 1: `jour` on `creneaux`

```sql
CREATE TABLE creneaux (
    id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    session_id    BIGINT NOT NULL REFERENCES sessions_examen(id) ON DELETE RESTRICT,
    date_examen   DATE NOT NULL,
    heure_debut   TIME NOT NULL,
    heure_fin     TIME NOT NULL,
    jour          SMALLINT GENERATED ALWAYS AS (EXTRACT(ISODOW FROM date_examen)::SMALLINT) STORED,
    ...
);
```

`jour` is the ISO day of week (1=Monday, 7=Sunday). It's used by the CP-SAT soft constraint W5 (weekend avoidance — see [[4.5. The 7 Soft Constraints and Objective]]) to identify Saturday (6) and Sunday (7) without re-computing from `date_examen` on every query.

Without the generated column, every weekend-avoidance query would call `EXTRACT(ISODOW FROM date_examen)` — fine for a single row, expensive in a GROUP BY. With the generated column, `WHERE jour IN (6, 7)` is a plain indexed lookup.

## V2 generated column 2: `periode_ts` on `creneaux`

```sql
periode_ts TSTZRANGE GENERATED ALWAYS AS (
    tstzrange((date_examen + heure_debut)::timestamptz,
              (date_examen + heure_fin)::timestamptz)
) STORED,
```

`periode_ts` is a `TSTZRANGE` (timestamp with time zone range) computed from `date_examen`, `heure_debut`, and `heure_fin`. It's used by the `EXCLUDE USING gist` constraint on `examens` to detect time-range overlap — see [[3.4. EXCLUDE Constraints and btree gist]].

Without the generated column, you'd need a trigger to maintain `periode_ts`, with all the trigger downsides (per-row firing, disable risk, visibility). The generated column is always consistent.

## V2 generated column 3 (recommended): `nb_inscrits_actifs` on `modules`

V1 had `examens.nb_etudiants_prevus INTEGER` — a stored count that could fall out of sync with actual `inscriptions` rows. The V1 review recommends:

> "Should be `INTEGER GENERATED ALWAYS AS (...) STORED` computing the count from `inscriptions`."

But generated columns can only reference the **same row's** columns, not other tables. So `nb_inscrits_actifs` on `modules` cannot be a generated column directly — it requires either:

- A trigger that updates `modules.nb_inscrits_actifs` whenever `inscriptions` changes, OR
- A materialized view (`mv_module_enrollments`) that precomputes it, OR
- A subquery in the CP-SAT input loader.

V2 uses option 2 — see [[3.6. Materialized Views and Refresh Strategies]]. The `mv_module_enrollments` view has `nb_inscrits_actifs` as a column, refreshed nightly.

## Why generated columns beat triggers

| Property | Generated column | Trigger-maintained column |
|---|---|---|
| Always consistent | Yes — computed on write | No — trigger can be disabled or forgotten |
| Visible in `\d+` | Yes (shown as "generated") | No (looks like a regular column) |
| Cannot be bypassed | Yes (writing to it raises an error) | No (trigger can be DISABLEd) |
| Performance | O(1) per row on write | O(N) if trigger queries other rows |
| Index support | Yes (can be indexed like any column) | Yes |
| Cross-table references | No (only same row) | Yes |

Generated columns are strictly better for single-row derivations. Triggers remain necessary for cross-row rules — see [[3.8. Constraints vs Triggers When to Use Each]].

## CITEXT: case-insensitive text

V1 stored emails as `VARCHAR(150)` with no uniqueness constraint. Two students could register with `user@example.com` and `USER@example.com` — same email, different rows.

V2 uses the `citext` extension:

```sql
CREATE EXTENSION IF NOT EXISTS citext;

CREATE TABLE etudiants (
    ...
    email CITEXT,  -- case-insensitive comparison
    ...
    UNIQUE (email) WHERE email IS NOT NULL
);
```

`CITEXT` behaves like `TEXT` but comparisons are case-insensitive:

```sql
INSERT INTO etudiants (email) VALUES ('user@example.com');
INSERT INTO etudiants (email) VALUES ('USER@example.com');
-- ERROR: duplicate key value violates unique constraint
```

Without `CITEXT`, you'd need:

```sql
email TEXT NOT NULL,
UNIQUE (LOWER(email))
```

And every query would need `WHERE LOWER(email) = LOWER(?)`. `CITEXT` handles this transparently.

## VARCHAR(N) vs TEXT + CHECK

V1 used `VARCHAR(N)` extensively:

```sql
nom VARCHAR(100) NOT NULL,
code VARCHAR(20) NOT NULL,
```

In PostgreSQL, `VARCHAR(N)` and `TEXT` have **identical performance** — `VARCHAR(N)` just adds a length check. The length check is also available as a `CHECK` constraint:

```sql
-- Equivalent:
nom VARCHAR(100) NOT NULL
nom TEXT NOT NULL CHECK (char_length(nom) <= 100)
```

V2 prefers `TEXT + CHECK` because:
- The `CHECK` is explicit and visible in `\d+` constraints.
- The `CHECK` can have a custom error message via `CHECK (char_length(nom) <= 100) NOT VALID` plus a separate `ALTER TABLE ... ADD CONSTRAINT ...` with a comment.
- `TEXT` is simpler — no length argument to remember.

For bounded codes (like `CHAR(9) CHECK (code ~ '^\d{4}-\d{4}$')` for academic year codes), V2 uses `CHAR(N)` with a regex CHECK.

## Common junior developer mistakes

- **Forgetting `STORED`.** `GENERATED ALWAYS AS (expr)` without `STORED` is rejected in PG 17. You need `STORED` for the column to be persisted.
- **Using non-immutable functions in generated columns.** `NOW()`, `CURRENT_USER`, `current_setting()` are not immutable. The generated column will be rejected.
- **Trying to write to a generated column.** `INSERT INTO creneaux (jour) VALUES (3)` raises an error. Generated columns are read-only.
- **Forgetting to index generated columns.** A generated column is just a column — if you query it, index it.
- **Using `VARCHAR(N)` for "documentation".** If you want documentation, use a `CHECK` constraint with a comment. `VARCHAR(N)` is a length check, not documentation.
- **Storing emails as `TEXT` without `CITEXT` or `LOWER()` index.** You'll get duplicate-email bugs from case differences.
