# Migration Strategies - Expand and Contract

## What it is

**Expand and Contract** (also called **Parallel Change**) is a migration strategy for evolving a schema **without downtime**. The idea: never make a change that breaks running code. Instead, expand the schema to support both old and new, deploy the new code, then contract the schema to remove the old.

The three phases:

1. **Expand** - add the new structure alongside the old. Both old and new code work.
2. **Migrate** - deploy the new code. Backfill data if needed.
3. **Contract** - remove the old structure. Only the new code is running.

## Worked example: rename a column

Suppose you want to rename `intern.name` to `intern.full_name`.

### Naive (breaks in production)

```sql
ALTER TABLE intern RENAME COLUMN name TO full_name;
```

The moment this runs, the old code (which queries `name`) breaks with `ORA-00904: invalid identifier`. You have to coordinate the schema change with the code deploy - and if the deploy fails, you've broken the app.

### Expand-and-contract

**Phase 1: Expand** (migration V1, deploy first)

```sql
ALTER TABLE intern ADD (full_name VARCHAR2(100));
-- Backfill
UPDATE intern SET full_name = name;
COMMIT;
-- Keep both columns in sync via trigger (or application code)
CREATE TRIGGER intern_sync_name BEFORE INSERT OR UPDATE ON intern
FOR EACH ROW
BEGIN
    :NEW.full_name := :NEW.name;
END;
/
```

Old code reads `name` (still there). New code can read `full_name`.

**Phase 2: Migrate** (deploy new code)

Deploy the new application version that reads and writes `full_name`. The old `name` column is still maintained by the trigger (or by the new code), so a rollback to old code would still work.

**Phase 3: Contract** (migration V2, after the new code is confirmed stable)

```sql
DROP TRIGGER intern_sync_name;
ALTER TABLE intern DROP COLUMN name;
```

Now the schema has only `full_name`, and only the new code is running.

## The principle

**Every migration should be backward-compatible with the currently running code.** Never deploy a schema change and a code change that depend on each other in the same step - deploy the schema change first (expand), then the code (migrate), then clean up (contract).

## Other examples

### Split a column

`intern.contact` -> `intern.email` + `intern.phone`.

1. **Expand**: add `email` and `phone` columns; backfill by parsing `contact`; trigger keeps them in sync.
2. **Migrate**: deploy code that reads `email`/`phone`.
3. **Contract**: drop `contact`.

### Change a column type

`intern.age NUMBER(3)` -> `intern.birth_date DATE`.

1. **Expand**: add `birth_date`; backfill from `age` (estimate birth year); trigger keeps them in sync.
2. **Migrate**: deploy code that uses `birth_date`.
3. **Contract**: drop `age`.

### Split a table

`intern` -> `intern` + `intern_contact`.

1. **Expand**: create `intern_contact`; backfill; triggers keep both in sync.
2. **Migrate**: deploy code that reads/writes both tables.
3. **Contract**: drop the contact columns from `intern`.

## Why it matters

Without expand-and-contract, every schema change requires downtime. With it, schema changes are invisible to users - the app keeps running through the entire migration.

This matters most for **24/7 systems**, but the discipline is valuable for any system: it forces you to think about backward compatibility, which makes rollbacks possible.

## Project Connection

The project's schema is small enough that downtime is acceptable - you could just drop and recreate. But the **principle** matters: if the project ever needs to evolve (add audit columns, switch to IDENTITY, add soft delete), doing it with expand-and-contract means no data loss and no downtime.

For example, the migration from `MAX(id)+1` to IDENTITY columns:

1. **Expand**: add `intern_id_new NUMBER GENERATED ALWAYS AS IDENTITY`; backfill by copying `intern_id` to `intern_id_new` (with `GENERATED BY DEFAULT` to allow explicit values).
2. **Migrate**: deploy code that uses `intern_id_new`.
3. **Contract**: drop `intern_id`, rename `intern_id_new` to `intern_id`.

See [[14 - Schema Evolution/02 - Backfill Migrations]] for the backfill pattern.

## Common pitfalls

- Skipping the contract phase - the schema accumulates "old" columns forever. Schedule the contract migration as a separate ticket, not "we'll do it later."
- Forgetting the trigger that keeps both columns in sync - the new column drifts from the old, and the contract migration reveals the mismatch.
- Running expand and contract in the same migration - defeats the point. They must be in separate migrations, deployed separately, with the code change in between.

## Trade-offs

- **Downtime vs. complexity**: expand-and-contract eliminates downtime but adds complexity (triggers, two columns, three deploys). For systems that can tolerate downtime, a direct change is simpler.
- **Storage vs. safety**: the expand phase temporarily doubles storage for the changed columns.
