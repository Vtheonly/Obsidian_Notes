# 03.00. Map of Content: Networking

## Overview

This section covers **03. Networking and Application Transport Protocols**. It is part of the unified backend engineering vault described in [[00.01. Master Architectural Mental Model]]. The notes below are organized by concept, not by framework. Each concept is taught once at the conceptual level, then implemented deeply in the Spring Boot anchor stack, then rapidly translated into Express, Django, Flask, and Laravel as deltas.

The vault teaches networking as the layer that sits *on top of* the kernel primitives from section 02 (sockets, file descriptors, `epoll_wait`, the TCP stack inside the Linux kernel) and *underneath* every framework in section 05 (Spring MVC, Express, Django, Flask, Laravel — they are all HTTP parsers and routers sitting on top of a socket). When you write `@GetMapping("/users/{id}")` in Spring or `@app.get("/users/:id")` in Express, what actually happens is: the NIC raises an interrupt on an incoming Ethernet frame, the kernel reassembles the IP packet, the in-kernel TCP state machine coalesces segments into a byte stream, the `accept()` syscall hands a connected socket to the runtime, the framework reads from that socket, parses the HTTP request line and headers, dispatches to your handler, and serializes the return value back through the same stack. Every "weird 502 from the load balancer", every "request hangs for 60 seconds then times out", every "TLS handshake fails only on mobile networks" is a defect at one of these layers.

The section is divided into five sub-sections that mirror the actual layering of the internet stack: TCP/IP transport (03.01) → HTTP framing (03.02) → TLS security (03.03) → real-time protocols layered on top of HTTP (03.04) → binary serialization and RPC frameworks that compress and structure the payload (03.05). Read in order, each sub-section assumes the one before it.

## Section Map

### 03.01. TCP IP Suite and Transport Layer Mechanics

- [[03.01.01. OSI vs. TCP IP Architectural Models]] — The seven-layer OSI reference model (Application, Presentation, Session, Transport, Network, Data Link, Physical) versus the four-layer TCP/IP model that the internet actually runs on. Explains why OSI succeeded as a teaching model but failed as an implementation, and walks through how a real HTTP packet is encapsulated: Ethernet header → IP header → TCP header → HTTP payload.
- [[03.01.02. The TCP Header and Connection State Machine]] — The 20-byte TCP header structure (Source Port, Dest Port, Sequence Number, Ack Number, Data Offset, the nine flag bits `CWR|ECE|URG|ACK|PSH|RST|SYN|FIN`, Window Size, Checksum, Urgent Pointer) and the 11-state connection state machine (`LISTEN`, `SYN_SENT`, `SYN_RCVD`, `ESTABLISHED`, `FIN_WAIT_1`, `FIN_WAIT_2`, `CLOSE_WAIT`, `CLOSING`, `LAST_ACK`, `TIME_WAIT`, `CLOSED`). Explains the Mitnick ISN-prediction attack of 1994 and why modern kernels cryptographically randomize ISNs.
- [[03.01.03. Deep Dive into the TIME_WAIT State]] — Why the active closer enters `TIME_WAIT` for 2×MSL (60–120 seconds on Linux), the two reasons (preventing delayed duplicate packets and ensuring the final ACK reaches the peer), the 4-tuple exhaustion problem, the `tcp_tw_reuse` / `tcp_tw_recycle` sysctls, why `tcp_tw_recycle` was removed in kernel 4.12 (it breaks NAT'd clients), and how load balancers hit port exhaustion at scale.
- [[03.01.04. TCP Flow Control and Congestion Control]] — Two independent mechanisms: receiver-driven flow control via the sliding window (`snd_wnd` vs `rcv_wnd`, zero-window probing, Clark's algorithm against silly window syndrome), and sender-driven congestion control via `cwnd` and `ssthresh` (slow start, congestion avoidance, fast retransmit, fast recovery). Compares Reno/Cubic (loss-based, the Linux default since 2.6.19) against Google's BBR (bandwidth-based, deployed on YouTube and google.com traffic in 2016).
- [[03.01.05. UDP Protocol Mechanics]] — The 8-byte UDP header (Source Port, Dest Port, Length, Checksum), no handshake, no sequence numbers, no acknowledgements, no flow control. Why DNS (port 53), NTP (123), DHCP (67/68), SNMP (161), QUIC (443), and WebRTC all chose UDP: either fire-and-forget semantics, multicast/broadcast, or the need to implement a custom reliability layer that the rigid kernel TCP stack cannot provide.

### 03.02. HTTP Protocol Evolution and Framing

- [[03.02.01. HTTP 1.1 Textual Protocol Specification]] — The ASCII text format defined by RFC 7230: request line (`METHOD SP PATH SP HTTP/1.1 CRLF`), headers (`Name: Value CRLF`), blank line, body. The mandatory `Host` header (new in 1.1, enables virtual hosting), `Transfer-Encoding: chunked` for streaming responses of unknown length, the `100 Continue` mechanism, and the 1xx/2xx/3xx/4xx/5xx status code classification.
- [[03.02.02. Connection Management in HTTP 1.1]] — Short-lived HTTP/1.0 connections versus persistent `Connection: keep-alive` (default in 1.1), the failed HTTP/1.1 pipelining experiment (nobody deployed it because of head-of-line blocking at the application layer), the per-host connection pool model in browsers (6 connections per origin in Chrome and Firefox), idle timeout tuning, and how `Connection: close` interacts with reverse proxies.
- [[03.02.03. HTTP 2 Binary Framing and Stream Multiplexing]] — The 9-byte binary frame header (`Length:24 | Type:8 | Flags:8 | Stream ID:31`), the ten frame types (`DATA`, `HEADERS`, `PRIORITY`, `RST_STREAM`, `SETTINGS`, `PUSH_PROMISE`, `PING`, `GOAWAY`, `WINDOW_UPDATE`, `CONTINUATION`), stream multiplexing over a single TCP connection, HPACK header compression (static table of 61 entries + per-connection dynamic table + Huffman coding), the deprecated server push, and how head-of-line blocking moved from the HTTP layer down to the TCP layer.
- [[03.02.04. HTTP 3 and QUIC UDP Transport]] — Why HTTP/3 (RFC 9114) replaces TCP with QUIC (RFC 9000) built on UDP: per-stream loss recovery eliminates TCP head-of-line blocking, the Connection ID allows IP migration (WiFi → cellular without dropping the connection), 0-RTT resumption for returning clients, TLS 1.3 integrated into the QUIC handshake (no separate TLS layer), and the entire transport implemented in user space — no kernel changes required, which is why Google and Cloudflare could deploy it unilaterally.

### 03.03. TLS Cryptographic Security and PKI

- [[03.03.01. Cryptographic Foundations]] — Symmetric encryption for bulk data (AES-256-GCM at ~1 GB/s with AES-NI, ChaCha20-Poly1305 for mobile devices without AES hardware), asymmetric encryption for key exchange (RSA-2048, ECDSA on P-256, Ed25519), cryptographic hash functions (SHA-256, SHA-3/Keccak, BLAKE2), HMAC for message authentication, and password hashing with key-derivation functions (PBKDF2 with 600,000 iterations, scrypt, Argon2id with 64 MB memory cost).
- [[03.03.02. Public Key Infrastructure and Certificates]] — X.509 v3 certificate structure (serial number, subject DN, issuer DN, validity period, public key, extensions, SAN list), the chain of trust from root CAs (DigiCert, Let's Encrypt ISRG Root X1) through intermediate CAs to leaf certificates, the CA/Browser Forum Baseline Requirements, certificate revocation via CRL vs OCSP vs OCSP stapling, wildcard vs SAN certificates, and the ACME protocol that powers Let's Encrypt automated issuance.
- [[03.03.03. The TLS 1.3 Handshake Protocol]] — The 1-RTT handshake (`ClientHello` with `key_share` + `supported_versions` + `supported_groups` → `ServerHello` + `EncryptedExtensions` + `Certificate` + `CertificateVerify` + `Finished` → client `Finished`), the 0-RTT early-data option for resumed sessions, mandatory ECDHE for forward secrecy, and what TLS 1.3 removed: RSA key exchange, static DH, CBC mode ciphers, RC4, MD5, compression (the CRIME attack), and renegotiation. Downgrade protection via the `supported_versions` extension and the `random` field marker.
- [[03.03.04. Mutual TLS (mTLS) for Microservices]] — The `CertificateRequest` message flow, the use case (service-to-service authentication in zero-trust networks where the network itself is untrusted), how Istio and Linkerd implement mTLS transparently via sidecar proxies (Envoy for Istio, linkerd2-proxy for Linkerd), the cert rotation problem (certificates expire in 24 hours by default in Istio), and SPIFFE/SPIRE as the identity framework (the SPIFFE ID `spiffe://prod.example.com/billing-service` is the workload identity, not the IP address).

### 03.04. Real-Time Bidirectional Protocols

- [[03.04.01. Short Polling vs. Long Polling]] — Short polling: client sends `GET /updates` every N seconds, most requests return `204 No Content`, latency is bounded by the poll interval. Long polling (the "Comet" pattern from 2006): server holds the request open for up to 30–60 seconds using a "hanging GET", responds when data arrives, client immediately re-requests. The reconnection gap where messages can be lost between the response and the next request, and why thread-per-connection servers (default Tomcat, default PHP-FPM) collapse under long-poll load.
- [[03.04.02. Server-Sent Events (SSE)]] — The `text/event-stream` MIME type, the `data:` / `event:` / `id:` / `retry:` field syntax, the browser `EventSource` API with automatic reconnection, the `Last-Event-ID` request header for resume-from-cursor, the 6-connection-per-browser limit over HTTP/1.1 (lifted under HTTP/2 because streams are multiplexed), and the unidirectional server→client constraint. SSE is the right choice for notifications, dashboards, and log streaming; WebSockets are needed only when the client must also send.
- [[03.04.03. The WebSocket Protocol RFC 6455]] — The HTTP Upgrade handshake (`Upgrade: websocket`, `Connection: Upgrade`, `Sec-WebSocket-Key`, response `101 Switching Protocols` with `Sec-WebSocket-Accept` = base64(SHA-1(key + "258EAFA5-E914-47DA-95CA-C5AB0DC85B11"))). The framing layer (opcode `0x1` text / `0x2` binary / `0x8` close / `0x9` ping / `0xA` pong, the FIN bit, the 7/16/64-bit payload length encoding with thresholds at 125 and 65535 bytes), client-to-server frame masking to prevent proxy cache poisoning, and why L7 proxies that don't speak WebSocket will silently break the upgrade.
- [[03.04.04. Scaling Real-Time State Across Nodes]] — The multi-node broadcast problem: one client publishes a message, N subscribers connected to M different server instances must all receive it. Solutions: Redis Pub/Sub as a backplane (every node subscribes to a channel, fanout is O(subscribers) per node), sticky sessions versus stateless socket gateways, presence tracking (who is online), and the CAP tradeoff in real-time systems (you cannot have both low latency and partition tolerance). Includes the thundering-herd reconnect storm problem and how to mitigate it with exponential backoff + jitter.

### 03.05. Binary Serialization and RPC Frameworks

- [[03.05.01. Data Serialization Formats Compared]] — Side-by-side comparison of JSON, MessagePack, CBOR, BSON, Protocol Buffers, Apache Thrift, and Apache Avro. A real `{"id":1,"name":"alice","active":true}` object serialized in each format with byte counts (JSON 35 bytes, MessagePack 18 bytes, Protobuf 12 bytes), schema enforcement (none for JSON, optional for MessagePack/CBOR, mandatory for Protobuf/Thrift/Avro), schema evolution rules, and the trade-off between human-readability and wire compactness.
- [[03.05.02. Protocol Buffers Internals]] — The `.proto3` schema language, the wire format with field tags encoded as `(field_number << 3) | wire_type`, the four wire types (0=varint, 1=fixed64, 2=length-delimited, 5=fixed32), varint encoding for compact small integers, ZigZag encoding for signed integers (`sint32`/`sint64`), the schema evolution rules (never reuse field numbers, add new fields as optional, deletion becomes implicit), and the proto3 simplifications over proto2 (no `required`, no `optional` keyword, no extensions, default values are zero/empty).
- [[03.05.03. gRPC Framework Architecture]] — HTTP/2 as the transport substrate (one TCP connection, many multiplexed streams), the `.proto` service contract, the four RPC modes (unary, server-streaming, client-streaming, bidirectional-streaming), the `protoc` code generation toolchain for Java/TypeScript/Python/PHP/Go, the metadata headers (binary-prefixed with `grpc-`), the 17 status codes (a richer set than HTTP — `OK`, `CANCELLED`, `UNKNOWN`, `INVALID_ARGUMENT`, `DEADLINE_EXCEEDED`, `NOT_FOUND`, `ALREADY_EXISTS`, `PERMISSION_DENIED`, `UNAUTHENTICATED`, `RESOURCE_EXHAUSTED`, `FAILED_PRECONDITION`, `ABORTED`, `OUT_OF_RANGE`, `UNIMPLEMENTED`, `INTERNAL`, `UNAVAILABLE`, `DATA_LOSS`), deadline propagation across service hops, and the interceptor model for cross-cutting concerns.

## Conceptual Roadmap

The five sub-sections form a strict bottom-up stack. **03.01** teaches the kernel-provided transport (TCP and UDP) that every higher layer sits on. The TCP state machine, the sliding window, and the congestion-control algorithms are not abstractions the framework owns — they live in the kernel (`net/ipv4/tcp_input.c`, `net/ipv4/tcp_output.c` in the Linux source) and are configured via sysctls in `/proc/sys/net/ipv4/`. Every `connect()` syscall from section 04's runtime notes triggers a SYN packet that traverses this state machine.

**03.02** teaches HTTP, which is a *framing convention layered on top of TCP byte streams*. HTTP/1.1 is text; HTTP/2 is binary frames on a single TCP connection; HTTP/3 abandons TCP entirely for QUIC. The reason this matters is that the framework in section 05 is *an HTTP parser and router* — nothing more. When you read `@PostMapping("/users")` in Spring or `@app.post("/users")` in Express, you are registering a handler that the framework will invoke after it has parsed the HTTP request line, headers, and body from the socket buffer.

**03.03** teaches TLS, which sits *between* TCP and HTTP. A server listening on port 443 accepts the TCP connection, immediately performs the TLS handshake, and only then can the HTTP parser read the request (which is now encrypted on the wire). The TLS layer is why you cannot naively `tcpdump` HTTPS traffic and read it — you need the session keys (set the `SSLKEYLOGFILE` environment variable in the client to export them, then load them into Wireshark).

**03.04** teaches real-time protocols (polling, SSE, WebSocket) that are *layered on top of HTTP* but then either upgrade out of it (WebSocket's `101 Switching Protocols`) or stretch its semantics (SSE's infinite `text/event-stream` response). These are how a chat app, a live dashboard, or a multiplayer game pushes data to the browser without polling.

**03.05** teaches binary serialization and RPC frameworks (Protobuf, gRPC) that *compress and structure the HTTP payload*. gRPC uses HTTP/2 as the transport and Protobuf as the body encoding, giving you a typed RPC interface that compiles down to native Java/TypeScript/Python/PHP stubs. This is the default for service-to-service communication inside microservice architectures at Google, Netflix, and Uber.

## How to Read This Section

1. **Read the concept notes first.** They establish the mental model. Do not skip ahead to the framework code in section 05 until you can explain, from memory, why a TCP connection has an 11-state machine and why HTTP/2 did not eliminate head-of-line blocking (it moved it from the application layer to the TCP layer).
2. **Implement the anchor.** The Spring Boot anchor note is where you build the real, load-tested implementation. For networking concepts, the anchor will typically be a TCP server, an HTTP/2 client, a TLS-terminating reverse proxy, or a WebSocket chat backend.
3. **Run the delta pass.** Open the other ecosystems and implement the same feature as a translation exercise. The networking stack is identical across ecosystems — only the runtime API surface differs (Java NIO vs Node's libuv vs Python's asyncio vs PHP's stream_select).
4. **Connect.** Follow the Related Notes links to reinforce the cross-ecosystem graph. Every concept note in this section links to its siblings and to the section MOC.

> [!tip] Reading order
> If you are new to this section, follow the numeric ordering. The sub-sections are sequenced bottom-up: transport (03.01) → framing (03.02) → security (03.03) → real-time (03.04) → serialization (03.05). If you are revising, jump directly to whichever concept you forgot — each note is self-contained.
