# 03.01.03. Deep Dive into the TIME_WAIT State

## What This Is

`TIME_WAIT` is the TCP state that the **active closer** enters after sending the final ACK in the 4-way teardown. It is the most operationally consequential state in the entire TCP state machine because it is the only state that *persists* for a fixed minimum duration regardless of whether anything is happening on the socket. The duration is 2×MSL (Maximum Segment Lifetime), which on Linux defaults to 60 seconds (`net.ipv4.tcp_fin_timeout` controls something different — see below — but the actual TIME_WAIT duration is `2 * MSL` where MSL is hardcoded to 30 seconds, giving 60 seconds total).

This note explains why TIME_WAIT exists (two distinct reasons, both of which are real), how it accumulates (the 4-tuple exhaustion problem), and how to mitigate it on high-throughput backend services that open many short-lived outbound connections — the canonical example being a microservice client or a load balancer proxy that opens a new upstream connection per request.

## The Details

### The critical necessity of `TIME_WAIT`: Preventing delayed duplicate packets from corrupting subsequent connections

`TIME_WAIT` is the state the **active closer** enters after sending the final ACK. It lasts for 2×MSL, where MSL is the Maximum Segment Lifetime — the longest time a packet is expected to survive in the network before being discarded. RFC 793 specifies MSL as 2 minutes, giving a TIME_WAIT of 4 minutes, but Linux uses a 30-second MSL, giving a 60-second TIME_WAIT (controlled implicitly — there is no sysctl for MSL itself).

The state exists for two independent reasons, both load-bearing:

**Reason 1: preventing delayed duplicate packets from corrupting a future connection that reuses the same 4-tuple.** A TCP segment can be delayed in the network for a surprisingly long time — a router under heavy load may queue a packet for seconds, a link-layer retransmission on a flaky WiFi connection may delay a frame, an ICMP redirect can cause a packet to take a detour. If a delayed packet from connection #1 (which has now been closed) arrives after connection #2 is established on the same 4-tuple `(src_ip, src_port, dst_ip, dst_port)`, the kernel of connection #2 would accept the stale data and deliver it to the application — silently corrupting the new connection. TIME_WAIT prevents this by keeping the 4-tuple reserved for 2×MSL after the close, so no new connection can reuse it until every in-flight packet from the old connection has had time to expire.

**Reason 2: ensuring the final ACK reaches the peer.** The final ACK in the 4-way teardown (the active closer's ACK of the passive closer's FIN) is sent unreliably — if it is lost in the network, the passive closer (in `LAST_ACK` state) will retransmit its FIN. The active closer, still in `TIME_WAIT`, can re-send the ACK. If the active closer had instead gone straight to `CLOSED` after sending the final ACK, the retransmitted FIN from the passive closer would arrive at a closed socket, causing the kernel to send a `RST` — which the passive closer would interpret as an error, surfacing `ECONNRESET` to its application. The TIME_WAIT duration is `2×MSL` because that is the maximum round-trip time for the final ACK to be lost and the FIN retransmission to arrive: at most 1×MSL for the lost ACK to expire from the network, plus at most 1×MSL for the retransmitted FIN to arrive.

```text
Active closer                          Passive closer
  TIME_WAIT                              LAST_ACK
   │                                       │
   │ ── ACK (final) ────────X (lost)       │
   │                                       │
   │ ◄──── FIN (retransmit) ───────────── │  (after RTO, e.g. 200ms)
   │                                       │
   │ ── ACK (retransmit) ────────────────► │  → CLOSED
   │                                       │
   │  (still in TIME_WAIT for ~59 more     │
   │   seconds, in case ANOTHER            │
   │   retransmitted FIN arrives)          │
   │                                       │
   │  (TIME_WAIT expires)                  │
   │  → CLOSED                             │
```

The dual necessity is what makes TIME_WAIT non-negotiable. Removing it (or shortening it aggressively) trades a 60-second resource reservation for the small but real chance of silent data corruption in a future connection — a chance that materializes rarely but catastrophically when it does, and is essentially impossible to debug after the fact because the corruption is silent.

### Acknowledgment delivery guarantees for the final `ACK`

The final ACK in the teardown is the only TCP segment that has no fallback if it is lost — every other segment in TCP is acknowledged, so loss triggers retransmission. But the final ACK acknowledges a FIN, and FINs do not themselves get ACKed in a separate message (the ACK of a FIN is the final ACK, which is what we are worried about losing). So TCP solves this with the TIME_WAIT state itself: the active closer stays alive for 2×MSL specifically so that if the passive closer retransmits its FIN, the active closer can retransmit its ACK.

The mechanics are tied to the kernel's retransmission timeout (RTO), computed from the smoothed round-trip time (SRTT) and round-trip time variation (RTTVAR) measured during the connection. The RTO for the FIN retransmission is the same RTO the connection used for data retransmission — typically 200ms on a LAN, 1 second on a cross-continent link, up to a cap of about 60 seconds. The passive closer will retransmit the FIN up to `tcp_retries2` times (default 15), with exponential backoff, before giving up and going to `CLOSED` unilaterally.

```text
Passive closer timeline in LAST_ACK:
  t=0     send FIN, wait for ACK
  t=RTO   (no ACK) retransmit FIN
  t=3*RTO (no ACK) retransmit FIN
  t=7*RTO (no ACK) retransmit FIN
  ... exponential backoff (doubles each time) ...
  t=tcp_retries2 limit reached → give up, transition to CLOSED

  If the active closer's TIME_WAIT expires before the passive closer
  gives up, the next retransmitted FIN hits a CLOSED socket and the
  kernel sends RST. The application on the passive-closer side sees
  ECONNRESET instead of a clean close.
```

The production failure mode here is asymmetric: if the active closer is on a fast link (LAN, 0.2ms RTT, RTO ~200ms) and the passive closer is on a slow link (mobile, 300ms RTT, RTO ~1s), the active closer's TIME_WAIT might be set assuming the default 60-second duration, which is plenty. But if you have *shortened* TIME_WAIT via a non-standard sysctl (some older guides recommended `tcp_fin_timeout=15`), the active closer's socket may close before a slow passive closer's retransmitted FIN arrives — causing intermittent `ECONNRESET` errors in your upstream services that are maddening to debug because they happen only on slow network paths.

A subtlety: `net.ipv4.tcp_fin_timeout` does *not* control TIME_WAIT duration despite the misleading name. It controls how long a socket stays in `FIN_WAIT_2` state waiting for the peer's FIN (the half-closed state). The actual TIME_WAIT duration is hardcoded at 60 seconds in the Linux kernel (`TCP_TIMEWAIT_LEN` in `include/net/tcp.h`, defined as 60×`HZ`). You cannot tune it without recompiling the kernel. This is intentional — the 2×MSL duration is a correctness invariant, not a performance knob.

### 2MSL (Maximum Segment Lifetime) duration and calculation

MSL is defined in RFC 793 as "the maximum time a TCP segment can exist in the internetwork system" — i.e., the longest a packet can survive in flight before some router's TTL expiry or link-layer retransmission cap discards it. RFC 793 sets MSL at 2 minutes (120 seconds), giving 2×MSL = 4 minutes for TIME_WAIT. This was reasonable in 1981 when the internet was slow and packets could legitimately be queued for tens of seconds on congested ARPANET links.

Linux uses a more aggressive MSL of 30 seconds (`TCP_TIMEWAIT_LEN / 2`), giving a TIME_WAIT of 60 seconds. This is a pragmatic compromise: 30 seconds is more than enough for any realistic packet to expire on modern networks (where the IP TTL field is set to 64 by default and decremented per hop, so a packet cannot survive more than ~64 hops × ~100ms per hop = ~6 seconds in the worst case). The BSDs and macOS use a 30-second MSL as well; Windows uses 240 seconds (4 minutes, the RFC default) by default, controlled by `TcpTimedWaitDelay` in the registry, with a minimum legal value of 30 seconds.

The reason you cannot reduce TIME_WAIT below 30 seconds without risking corruption is a back-of-the-envelope calculation:

```text
Worst-case delayed packet arrival:
  - IP TTL = 64 hops
  - Average per-hop queueing delay on a congested router: 100ms
  - Maximum network lifetime of a packet: 64 * 100ms = 6.4 seconds

  - But: link-layer retransmissions on WiFi can add 5-10 seconds
  - But: ICMP redirects can cause route flaps that add 10-30 seconds
  - But: a packet can be stuck in a NIC TX ring buffer during a kernel panic
        and then flushed when the kernel reboots — adding minutes

  Conservative upper bound: 30 seconds MSL → 60 seconds 2*MSL
  This is the value Linux, BSD, and macOS use.
```

The risk calculus is: with a 60-second TIME_WAIT, you accept a 60-second cost on every short-lived connection's 4-tuple, in exchange for an essentially-zero probability of stale-packet corruption. If you shortened it to 5 seconds, you would gain ~55 seconds of 4-tuple reuse per connection but accept a small (~1 in 100,000 on a typical network, much higher on a network with route flapping) probability of corrupting a future connection with a stale packet. The corruption would be silent and untraceable — the application would just see weird data and crash or produce wrong results. The expected cost of an untraceable production bug vastly exceeds the cost of 60 seconds of 4-tuple reservation, so every operating system ships with the conservative 60-second default.

### Mitigating `TIME_WAIT` socket exhaustion on high-throughput backend services

The operational problem with TIME_WAIT is that it accumulates. A backend service that opens many short-lived outbound TCP connections (a microservice client, a load balancer, a database proxy, a Redis client that does not pool) will accumulate one TIME_WAIT socket per connection. Each TIME_WAIT socket consumes ~1.5 KB of non-swappable kernel memory and reserves a 4-tuple for 60 seconds.

The math is brutal: if your proxy handles 10,000 requests per second and opens a new upstream connection per request, you generate 10,000 TIME_WAIT sockets per second, each persisting for 60 seconds. Steady state: 600,000 TIME_WAIT sockets, consuming ~900 MB of kernel memory, and crucially, *exhausting the ephemeral port range*. The default ephemeral port range on Linux is 32768–60999 (`net.ipv4.ip_local_port_range`), giving ~28,000 ports. Once all 28,000 are in TIME_WAIT for the same destination `(dst_ip, dst_port)`, no new outbound connection can be opened to that destination — `connect()` fails with `EADDRNOTAVAIL` ("Cannot assign requested address").

```bash
# Check current TIME_WAIT count
ss -tan state time-wait | wc -l

# Check ephemeral port range
sysctl net.ipv4.ip_local_port_range
# net.ipv4.ip_local_port_range = 32768   60999   (28,232 ports)

# Check how many TIME_WAIT sockets target a specific destination
ss -tan state time-wait '( dport = :8080 and dst 10.0.0.5 )' | wc -l
```

The mitigations, in order of preference:

**1. Connection pooling (the real fix).** Do not open a new TCP connection per request. Reuse a pool of N long-lived connections to each upstream. A pool of 50 connections can carry thousands of requests per second on HTTP keep-alive or gRPC multiplexing, generates zero TIME_WAIT sockets, and amortizes the handshake cost. Every modern HTTP client (Apache HttpClient, OkHttp, Node's `http.Agent`, Python's `requests.Session`, Go's `http.Transport`) supports pooling — turn it on and tune `maxConnectionsPerHost` to your throughput.

**2. Increase the ephemeral port range.** This is a stopgap that buys you headroom:

```bash
# Persist across reboots
echo 'net.ipv4.ip_local_port_range = 10000 65535' >> /etc/sysctl.conf
sysctl -p
# This gives ~55,000 ports instead of ~28,000 — about 2x headroom
```

**3. Enable `tcp_tw_reuse`.** This sysctl (`net.ipv4.tcp_tw_reuse`, default 0, set to 1 to enable) allows the kernel to reuse a TIME_WAIT socket for a *new outbound connection* — but only after the `timestamp` option has verified that the new connection's first packet's timestamp is strictly greater than the last packet seen on the old connection. This guarantees the new connection cannot receive stale packets from the old one. It is safe because it relies on TCP timestamps (RFC 7323), which are enabled by default on modern Linux. The catch: the remote side must also support timestamps (almost all modern stacks do), and `tcp_tw_reuse` only helps for *outbound* connections (you are the active closer opening a new connection to the same destination), not for inbound.

```bash
sysctl -w net.ipv4.tcp_tw_reuse=1
# Safe: relies on TCP timestamps to prevent stale packets
# Recommended in production for clients that open many short-lived outbound connections
```

**4. Do NOT enable `tcp_tw_recycle`.** This was a separate sysctl (`net.ipv4.tcp_tw_recycle`) that enabled a more aggressive TIME_WAIT recycling based on timestamp comparison. It was **removed in Linux kernel 4.12 (2017)** because it breaks connections from clients behind NAT. The mechanism: the kernel would record the timestamp of the most recent packet from each peer IP and refuse packets whose timestamp was older. Behind NAT, many clients share one source IP, but their timestamps are per-host (each client's clock is independent), so the kernel would silently drop legitimate packets from "the other" client behind the same NAT. This manifested as random connection failures affecting 1–10% of users on carrier-grade NAT (mobile networks, corporate WiFi). If you ever see `tcp_tw_recycle=1` recommended in a tuning guide, the guide is wrong; the option does not even exist on modern kernels.

**5. Let the *server* be the active closer.** TIME_WAIT falls on the active closer. If your load balancer is hitting port exhaustion because it is the active closer on every upstream connection, you can configure the upstream to send `Connection: close` and let the upstream close first — then TIME_WAIT accumulates on the upstream, not the load balancer. This is sometimes useful but usually just shifts the problem; the real fix is connection pooling.

The production failure mode looks like this: your microservice starts returning `502 Bad Gateway` intermittently under load. The proxy logs show `EADDRNOTAVAIL` or `Cannot assign requested address` on `connect()` calls to the upstream. `ss -tan state time-wait | wc -l` returns ~28,000 (or whatever your port range size is). The fix is to either enable connection pooling on the client (preferred) or expand the port range and enable `tcp_tw_reuse` (band-aid). NEVER enable `tcp_tw_recycle` — it no longer exists, and even if you find an old guide that suggests it, the symptom it caused (random NAT'd-client connection failures) is far worse than the symptom it solved.

## How This Connects to the Frameworks

Every HTTP client library in section 05's frameworks has TIME_WAIT implications:

- **Spring Boot** with `RestTemplate` or `WebClient`: by default, `HttpComponentsClientHttpRequestFactory` uses a connection pool of 25 connections per route. Increase `setMaxConnPerRoute(100)` and `setMaxConnTotal(200)` for high-throughput upstreams. If you bypass the pool with `new SimpleClientHttpRequestFactory()`, every request opens a new socket and you will hit TIME_WAIT exhaustion within minutes.
- **Express/Node.js**: the `http.Agent` class pools connections by default (`keepAlive: true` since Node 19; before that it was `false` and you had to opt in). Set `agent.maxSockets = 100` to allow 100 concurrent requests per origin on the pool.
- **Python `requests`**: `requests.Session()` pools; `requests.get()` does not. Always use a `Session` for high-throughput code.
- **PHP Guzzle**: `GuzzleHttp\HandlerStack` with `CurlMultiHandler` pools; verify `CURLMOPT_MAXCONNECTS` is set to a non-trivial value.

If any of these steps fails — a misconfigured pool, a leak, an aggressive timeout — the failure surfaces as TIME_WAIT exhaustion and intermittent `EADDRNOTAVAIL` on `connect()`. Knowing that TIME_WAIT falls on the active closer, that 60 seconds is the duration, and that `tcp_tw_reuse` is the safe sysctl — these are the difference between a 5-minute fix and a 5-hour incident.

## Hands-On Exercise

```bash
# Count sockets in TIME_WAIT state — this is the headline metric
ss -tan state time-wait | wc -l

# Count TIME_WAIT sockets targeting a specific upstream (the smoking gun for port exhaustion)
ss -tan state time-wait '( dport = :8080 and dst 10.0.0.5 )' | wc -l

# Check your ephemeral port range
sysctl net.ipv4.ip_local_port_range

# Check whether tcp_tw_reuse is on (should be 1 for clients with many outbound connections)
sysctl net.ipv4.tcp_tw_reuse

# Verify that tcp_tw_recycle does NOT exist (was removed in kernel 4.12)
sysctl net.ipv4.tcp_tw_recycle 2>&1
# Expected: "cannot stat /proc/sys/net/ipv4/tcp_tw_recycle: No such file or directory"

# Reproduce port exhaustion: open 28,000 connections to a single destination and close them all
for i in $(seq 1 28000); do
    nc -w 1 10.0.0.5 8080 < /dev/null &
done
wait
ss -tan state time-wait | wc -l   # should be ~28000, persisting for 60 seconds

# Generate load with Apache Bench using keep-alive (no TIME_WAIT) vs without (TIME_WAIT per request)
ab -n 10000 -c 100 -k http://localhost:8080/   # -k = keep-alive, ~0 TIME_WAIT
ab -n 10000 -c 100 http://localhost:8080/      # no -k, ~10000 TIME_WAIT
```
