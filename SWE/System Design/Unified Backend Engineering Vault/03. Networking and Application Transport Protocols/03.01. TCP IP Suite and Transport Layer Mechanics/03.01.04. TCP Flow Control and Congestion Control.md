# 03.01.04. TCP Flow Control and Congestion Control

## What This Is

TCP has two independent control mechanisms that are often confused because both involve "the sender slowing down". **Flow control** is receiver-driven and protects a single receiver from being overwhelmed by a faster sender — the receiver advertises its available buffer space via the Window Size field in the TCP header, and the sender must not send more unacknowledged data than the window allows. **Congestion control** is sender-driven and protects the *network itself* (the routers, switches, and links between sender and receiver) from being overwhelmed by too many senders at once — the sender maintains a private variable called `cwnd` (congestion window) that limits its sending rate independently of what the receiver advertises.

The effective send rate is the minimum of the two windows: `send_window = min(rwnd, cwnd)` where `rwnd` is the receiver's advertised window. This note explains both mechanisms, the algorithms that drive them, and the modern congestion-control variants (Reno, Cubic, BBR) that determine how TCP behaves on the long-haul and mobile links that dominate modern production traffic.

## The Details

### Sliding Window Protocol: Transmitter Window (`snd_wnd`) vs. Receiver Window (`rcv_wnd`)

TCP's flow control is a **sliding window** protocol. The receiver continuously advertises how much buffer space it has free for incoming data — this is the 16-bit `Window Size` field in the TCP header. The sender must keep the amount of unacknowledged in-flight data at or below this advertised window. As the receiver's application reads data out of the socket buffer, the buffer frees up, and the receiver advertises a larger window in its next ACK. As the receiver's application stops reading (slow consumer), the buffer fills, and the advertised window shrinks — eventually to zero.

```text
Sender's view of the byte stream (window slides right as ACKs arrive):

   already ACKed     |   in-flight (unacked, allowed by window)    |   not yet sendable
                     ←─────────── snd_wnd (advertised by receiver) ──────────→
   ──────────────────┬────────────────────────────────────────────┬──────────────────
   0               1000                                          5000               10000
                     ↑                                            ↑
                     │                                            │
                  send_base                                   send_base + snd_wnd
                  (oldest unacked byte)                     (next byte we can send)
```

When the receiver advertises a zero window (because the application is not draining the socket buffer), the sender cannot send any more data. It must probe: every few hundred milliseconds, the sender sends a single byte (a "zero window probe") to elicit a window update from the receiver. The receiver, on receipt of the probe, sends back an ACK with the current window size. If the application has now drained some buffer, the window is non-zero and the sender resumes; if not, the sender probes again. This is **Zero Window Probing** and it prevents deadlock when the receiver's window stays at zero for an extended period.

The 16-bit Window Size field can advertise at most 65535 bytes — far too small for modern high-bandwidth links. A 10 Gbps link with 100ms RTT has a *bandwidth-delay product* of 125 MB, which would be impossible to saturate with a 64 KB window. The **Window Scale option** (RFC 7323, sent in the SYN) multiplies the Window Size field by up to 2^14, allowing windows up to 1 GB. Both sides must send the option in the SYN for it to take effect — this is one reason a SYN without options (sent by a misconfigured client) gets a much smaller window and dramatically worse throughput.

```bash
# Verify that Window Scale is being negotiated
sudo tcpdump -i any -nn 'tcp[tcpflags] & tcp-syn != 0' -v | grep -i 'wscale'
# Typical: wscale 7 (multiply advertised window by 128)

# Inspect the actual snd_wnd and cwnd of an established connection
ss -ti -tan 'dport = :443'
# Output: ... cubic wscale:7 rto:204 rtt:0.125/0.062 mss:1448 pmtu:1500 rcvmss:1148
#         cwnd:10 bytes_acked:38108 bytes_received:20176 segs_out:33 segs_in:27
#         send 1.8Mbps lastsnd:48ms pacing_rate 3.6Mbps delivered:33 app_limited
```

The production failure mode tied to flow control is **the slow consumer**. If your microservice handler is slow to call `request.getInputStream().read()` (or equivalent in any framework), the kernel socket buffer fills, the kernel advertises a shrinking window to the peer, eventually zero, and the peer stalls — its `send()` blocks (or, for non-blocking sockets, its `epoll_wait` stops returning `EPOLLOUT`). The peer sees this as "the connection hung". From your side, you see no network traffic — `tcpdump` shows the kernel is just sitting on a full buffer. The fix is to read the request body fully and quickly, or to use a streaming consumer that processes data as it arrives. The metric to watch is `ss -ti`'s `rcv_space` versus `rcv_rtt` — if `rcv_space` is consistently at the buffer max, your application is the bottleneck.

### Zero Window Probing and Silly Window Syndrome mitigations (Clark's Algorithm, Nagle's Algorithm)

Two related pathologies arise from small writes interacting with the sliding window:

**Silly Window Syndrome (SWS)** occurs when the receiver advertises very small windows and the sender fills them with very small packets. Imagine the receiver's application reads 1 byte at a time: each read frees 1 byte, the receiver advertises a window of 1, the sender sends a 1-byte TCP segment (which carries 20+ bytes of headers — a 95% overhead). With 1-byte reads at 1000 ops/sec, you would send 1000 tiny packets per second, achieving ~1 KB/s of useful throughput while consuming the bandwidth of ~30 KB/s of header overhead. **Clark's Algorithm** (RFC 1122) solves this on the receiver side: the receiver does not advertise a new window until it can advertise at least either 1 MSS or half the maximum buffer size, whichever is smaller. Until then, it keeps advertising the previous (small or zero) window, forcing the sender to wait. The sender's data accumulates in its own send buffer until a real window opens.

**The Small-Packet Problem** occurs on the sender side when the application writes many small messages (e.g., a terminal echoing one keystroke at a time, or a chat protocol sending one character per message). Each small write becomes a separate TCP segment with 40+ bytes of IP+TCP headers — wildly inefficient. **Nagle's Algorithm** (RFC 896, named after John Nagle) solves this: if there is any unacknowledged data in flight, the sender holds small writes in its buffer until either (a) the outstanding data is acknowledged, or (b) the buffer accumulates a full MSS. This coalesces small writes into larger segments.

```text
Without Nagle (one keystroke per packet):
  t=0ms   send 1 byte   (header: 40B, payload: 1B — 97% overhead)
  t=1ms   send 1 byte
  t=2ms   send 1 byte
  ...1000 packets per second to send 1 KB/s of data

With Nagle (default on):
  t=0ms   send 1 byte   (first packet always goes out immediately)
  t=1ms   buffer 1 byte (held — outstanding data exists)
  t=2ms   buffer 1 byte (held)
  ...continue buffering until ACK arrives or MSS accumulated...
  t=200ms ACK arrives, flush buffer → send ~200 bytes in one packet
```

Nagle's algorithm is controlled by the `TCP_NODELAY` socket option. Setting `TCP_NODELAY=1` disables Nagle — small writes go out immediately as separate segments. This is essential for latency-sensitive interactive protocols: SSH, X11, Redis (single-message request-response), interactive multiplayer games, the WebSocket subprotocol of any chat app. Leaving Nagle on for these would add up to one RTT of latency to every small message.

The interaction between Nagle and delayed ACKs (RFC 1122 — the receiver can wait up to 200ms before ACKing, to coalesce ACKs) is a famous performance trap. If the sender has Nagle on and the receiver has delayed ACKs on (both defaults), a small write triggers: sender sends 1 byte (first packet always goes), sender buffers subsequent writes, sender waits for ACK that the receiver is delaying by 200ms, sender eventually times out and flushes the buffer. Result: up to 200ms of latency on every request-response cycle. The fix is to disable Nagle (`TCP_NODELAY=1`) on the client for request-response protocols, or to ensure the application writes the entire request in a single `send()` call (which avoids the Nagle small-write path entirely).

```bash
# Check whether TCP_NODELAY is set on a socket
ss -ti 'dport = :443' | grep -i nodelay

# In Python, set TCP_NODELAY on a socket:
# sock.setsockopt(socket.IPPROTO_TCP, socket.TCP_NODELAY, 1)

# In Java:
# socket.setTcpNoDelay(true);

# In Node.js, http.Agent sets TCP_NODELAY=true by default since Node 0.10
```

The production failure mode is **Nagle + Delayed ACK = 200ms latency**. Your microservice has a 5ms p99 latency budget but you are seeing 200ms p99. The cause is the framework's HTTP client writing the request line, headers, and body in three separate `write()` calls, with Nagle on (default on the server socket) and Delayed ACK on (default on the peer). The first write goes out, the second and third are held for Nagle, the peer delays the ACK. Fix: either set `TCP_NODELAY` on the client, or — better — use a single `writev()` / gather-write to send all parts of the request in one kernel call.

### Congestion Control phases: Slow Start, Congestion Avoidance, Fast Retransmit, and Fast Recovery

While flow control is about the receiver's buffer, congestion control is about the network's capacity. The sender maintains a private variable `cwnd` (congestion window) that it never tells the receiver about — `cwnd` is purely a sender-side state. The effective send window is `min(rwnd, cwnd)`. The classic congestion control algorithm (Jacobson 1988, standardized in RFC 5681) has four phases:

```text
cwnd growth over time (loss-based: Reno/Cubic)

cwnd
  ↑
  │                                            ╱──╲           ← Slow Start (exponential, double per RTT)
  │                                           ╱     ╲
  │                                          ╱       ╲──╲      ← Congestion Avoidance (linear, +1 per RTT)
  │                              ssthresh ─ ───────────────╲── ← multiplicative decrease on loss (cwnd/2)
  │                            ╱                       ╱   ╲
  │                          ╱                       ╱     ╲  ← Fast Recovery (cwnd = ssthresh, then linear)
  │                        ╱                       ╱
  │                      ╱                       ╱
  │                    ╱                       ╱
  │      initial ────╱                       ╱
  │      cwnd=10 MSS                       ╱
  │                                    ╱
  └─────────────────────────────────────────────────────────→ time (RTTs)
                ↑                       ↑              ↑
                Slow Start              Loss event     Fast Retransmit
                (exp growth)            cwnd ← cwnd/2  + Fast Recovery
```

**Phase 1 — Slow Start.** A new connection starts with `cwnd = initial cwnd` (default 10 MSS since RFC 6928, was 1–4 MSS before). For every ACK received, `cwnd` increases by 1 MSS — but because every ACK acknowledges one segment, and the sender is sending `cwnd` segments per RTT, the result is that `cwnd` doubles every RTT. This is exponential growth: 10 → 20 → 40 → 80 → 160 MSS over 4 RTTs. On a 100ms RTT link, that is 400ms to grow from 10 to 160 segments (about 230 KB of in-flight data). Slow start exits when `cwnd` reaches `ssthresh` (slow-start threshold).

**Phase 2 — Congestion Avoidance.** Once `cwnd >= ssthresh`, growth switches from exponential to linear: `cwnd` increases by 1 MSS per RTT (achieved by incrementing `cwnd` by `1 MSS / cwnd` on each ACK, which sums to 1 MSS over `cwnd` ACKs). The sender is now probing gently for additional capacity, growing the window by one segment per round trip.

**Phase 3 — Fast Retransmit.** When a segment is lost, the receiver's subsequent ACKs (for later segments that did arrive) all carry the same acknowledgment number — these are **duplicate ACKs** (dupACKs). After 3 dupACKs (the "3 dupACK rule"), the sender concludes the segment was lost and retransmits it immediately without waiting for the retransmission timeout (RTO). This is fast retransmit. The rationale: 3 dupACKs cannot be caused by reordering alone (a reordered segment would generate at most 1–2 dupACKs), so 3 is strong evidence of loss.

**Phase 4 — Fast Recovery.** After fast retransmit, the sender does not go back to slow start. Instead it sets `ssthresh = cwnd / 2`, sets `cwnd = ssthresh`, and re-enters congestion avoidance. This is "multiplicative decrease, additive increase" (MD-AI) — the AIMD principle that gives TCP its fairness property: competing TCP connections converge on a fair share of the bottleneck link because each backs off by half on loss and grows by one per RTT.

If no dupACKs arrive (because the loss happened when there was no further data to send, or because the loss was so heavy that even the dupACKs were lost), the sender must wait for the RTO timer to expire. An RTO expiry is treated as a more severe signal than 3 dupACKs — it triggers a full reset to slow start (`cwnd = initial cwnd`, `ssthresh = cwnd / 2`).

The production failure mode tied to congestion control is **the cold-start latency**. A new connection starts at `cwnd = 10 MSS` (~14 KB) and grows exponentially — but for the first few RTTs, the sender cannot fill the pipe. On a 1 Gbps link with 50ms RTT, the bandwidth-delay product is 6.25 MB; growing `cwnd` to fill that takes log2(6.25MB / 14KB) ≈ 9 RTTs = 450ms before the connection reaches full throughput. This is why short-lived connections (a single REST request) achieve only a fraction of the link bandwidth — the connection closes before `cwnd` has grown. The fix is connection pooling (so `cwnd` persists across requests) and the TCP Fast Open extension (RFC 7413, allows data in the SYN packet to skip the slow start).

### Modern Congestion Control Algorithms: Reno, Cubic, and Google BBR (Bottleneck Bandwidth and RTT)

The classic algorithm above is "TCP Reno" (1990). Modern Linux defaults to **Cubic** (since kernel 2.6.19, 2007) and the newer **BBR** (since kernel 4.9, 2016) is increasingly deployed. They differ in what signal they interpret as "congestion" and how they grow `cwnd`.

```text
Comparison of cwnd growth on a long-haul link (50ms RTT, 100 Mbps bottleneck)

  Reno:        AIMD. cwnd = cwnd + 1 MSS per RTT (linear up), cwnd = cwnd/2 on loss (multiplicative down).
               Problem: too conservative on high-BDP links. Linear growth means it takes
               O(BDP) RTTs to refill the pipe after a loss — seconds to minutes on long-haul.

  Cubic:       Cubic function of time since last loss. cwnd = C*(t-K)^3 + W_max,
               where W_max is the cwnd at the last loss, t is time since, K is a constant.
               The cubic curve grows fast initially (after backoff), slows near W_max,
               then grows fast again past W_max (probing for new capacity). Better than Reno
               on high-BDP links because the curve is time-based, not RTT-based, so high-RTT
               flows are not penalized. Default in Linux since 2.6.19.

  BBR:         Model-based, not loss-based. Measures the actual bottleneck bandwidth (max
               delivery rate over a windowed sample) and the minimum RTT, then sets the
               pacing rate to bandwidth * RTT (the BDP). Does NOT back off on packet loss
               (loss is treated as a signal, not a hard constraint). Probes periodically for
               more bandwidth. Default on Google's B4 backbone, YouTube, google.com traffic
               since 2016. Available in Linux as `net.ipv4.tcp_congestion_control=bbr`.
```

The fundamental insight of BBR is that **packet loss is not a reliable signal of congestion**. On modern networks with deep buffers (the "bufferbloat" problem), a congested link fills its queue with packets before it starts dropping them — so loss-based algorithms (Reno, Cubic) fill the buffer first, adding latency, then back off only after the buffer overflows. On networks with shallow buffers (cellular, satellite, some data-center fabrics), packets are dropped *before* the queue builds, so loss-based algorithms back off too aggressively and never fill the pipe. BBR sidesteps both by measuring the actual delivery rate rather than reacting to loss.

Bufferbloat is the legacy of the 1990s convention that "bigger buffers are better". A router with a 10-second queue under load adds 10 seconds of latency to every packet — the classic symptom is "my internet is fast (high throughput when measured) but every interactive application is laggy (high latency)". The fix is **active queue management** (AQM) — CoDel, FQ-CoDel, PIE — which drop packets deliberately *before* the queue fills, signalling senders to back off before latency degrades. Linux's `fq_codel` qdisc (default since kernel 3.17 in many distros) implements this.

```bash
# Check which congestion control algorithm your kernel is using
sysctl net.ipv4.tcp_congestion_control
# Typical: net.ipv4.tcp_congestion_control = cubic

# List available algorithms
sysctl net.ipv4.tcp_available_congestion_control
# Typical: net.ipv4.tcp_available_congestion_control = reno cubic bbr

# Switch to BBR (must be available, requires kernel >= 4.9)
sysctl -w net.ipv4.tcp_congestion_control=bbr

# Per-socket: setsockopt(TCP_CONGESTION, "bbr") in C, or
# socket.setsockopt(SOL_TCP, TCP_CONGESTION, b"bbr") in Python

# Inspect live cwnd, ssthresh, pacing rate of an established connection
ss -ti 'dport = :443'
# Output excerpt: cubic wscale:7 rto:204 rtt:0.125/0.062 mss:1448 cwnd:10
#                  pacing_rate 3.6Mbps delivered:33 app_limited
```

The BBR breakthrough at Google is documented in the 2017 ACM Queue paper "BBR: Congestion-Based Congestion Control" (Cardwell et al.). On Google's B4 backbone, replacing Cubic with BBR improved throughput by 2–25× on the shallow-buffered long-haul links between data centers. On YouTube's edge servers, BBR reduced median RTT by 11–53% on the worst 5% of connections (the ones suffering bufferbloat under Cubic). BBR is now the default on Google Cloud's load balancers and is being adopted by Cloudflare, Spotify, and Tumblr. The production deployment pattern is to enable BBR on edge servers that terminate many high-RTT mobile connections, where Cubic's loss-based backoff is most pathological.

The production failure mode tied to congestion control choice is **Cubic on a lossy mobile network**. Your mobile users see 10× worse throughput than your desktop users on the same backend. The cause is Cubic backing off on every packet loss (mobile networks drop 1–5% of packets routinely as devices move between cells), while BBR would ride through the loss and continue at the measured bandwidth. The fix is to enable BBR on the server (`net.ipv4.tcp_congestion_control=bbr`), verify it actually took effect on the connection (`ss -ti` showing `bbr` in the algorithm field), and watch the p99 latency metric for mobile clients drop.

## How This Connects to the Frameworks

Every framework in section 05 makes choices that interact with flow control and congestion control:

- **Spring Boot** with Tomcat: the connector's `maxThreads` (default 200) and `acceptCount` (default 100) determine how many concurrent requests the server can absorb. If the application is slow, the socket buffers fill, the kernel advertises a shrinking window, and clients experience request stalls. The fix is to either increase throughput or bound the queue with `acceptCount`.
- **Express/Node.js**: libuv's event loop reads from sockets on every tick. If a single request handler blocks the event loop (synchronous CPU-bound work), no socket reads happen, all socket buffers fill, all windows shrink, all clients stall. The metric to watch is the event loop lag (`monitorEventLoopDelay`).
- **Python/Django**: the WSGI server's thread pool (default 4 threads in `runserver`, 10+ in gunicorn `sync` worker) bounds concurrent reads. Use `gevent` or `uvicorn` (async) to multiplex thousands of slow-reading connections on few threads.
- **PHP/Laravel**: PHP-FPM workers are process-per-request. Each worker holds a socket; if the application is slow, the socket sits in `ESTABLISHED` with a full receive buffer, advertising a zero window. The client times out.

If any of these steps fails — a slow consumer, a missing `TCP_NODELAY`, a Cubic-on-mobile-network regression — the failure surfaces as either "the connection hangs" or "the throughput is much lower than expected". Knowing which window (`rwnd` or `cwnd`) is the bottleneck, and which algorithm (Cubic or BBR) is driving `cwnd`, is the difference between a 5-minute fix and a 5-hour incident.

## Hands-On Exercise

```bash
# Inspect the live cwnd, rwnd, pacing rate of a connection
ss -ti 'dport = :443'

# Check current congestion control algorithm
sysctl net.ipv4.tcp_congestion_control

# List available algorithms (Reno, Cubic, BBR if kernel >= 4.9)
sysctl net.ipv4.tcp_available_congestion_control

# Switch to BBR (requires the bbr module to be loaded)
sudo modprobe tcp_bbr
sudo sysctl -w net.ipv4.tcp_congestion_control=bbr

# Verify the algorithm on an established connection after the switch
curl -s https://example.com &
ss -ti 'dport = :443' | grep -i 'bbr\|cubic\|reno'

# Watch slow-start in action: a fresh connection's cwnd grows exponentially
# (run iperf3 against a remote host with high RTT)
iperf3 -c speedtest.server.example.com -t 30 -i 1
# In the first few seconds, throughput will ramp up exponentially — that's slow start

# Measure the impact of TCP_NODELAY on small-request latency
# (compare p99 latency with and without the flag on a request-response workload)
strace -e trace=setsockopt -p $(pgrep -f your_server)
```
