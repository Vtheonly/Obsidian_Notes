# 03.01.01. OSI vs. TCP IP Architectural Models

## What This Is

Every byte your framework writes to a socket traverses a stack of layers, each owned by a different piece of software: the application builds the payload, the runtime writes it to a file descriptor, the kernel's TCP/IP stack fragments it into segments and packets, the NIC driver turns those into Ethernet frames, and the wire carries them as electrical or optical signals. The OSI model and the TCP/IP model are two attempts to name these layers. OSI is the seven-layer reference model published as ISO/IEC 7498-1 in 1984 — a committee design that was never widely implemented but became the universal teaching vocabulary. TCP/IP is the four-layer model that actually runs the internet, developed by Cerf and Kahn in 1974 and refined through RFC 1122 and RFC 1123. Every networking conversation you will have in production ("the failure is at layer 3", "this is a layer 7 load balancer", "we need to terminate TLS at layer 6") implicitly references one of these two models.

This note sits between the OS notes in section 02 (the kernel owns layers 1–4) and the framework notes in section 05 (the framework owns layer 7). Knowing where a defect lives in the stack is the difference between a 5-minute fix and a 5-hour incident: a `Connection reset by peer` is layer 4, a `502 Bad Gateway` from your reverse proxy is layer 7, a `TLS handshake failure` is layer 6, and a `Destination Host Unreachable` is layer 3.

## The Details

### Detailed layer comparisons: Application, Presentation, Session, Transport, Network, Data Link, Physical

The OSI model defines seven layers, each with a single responsibility. The TCP/IP model collapses these into four layers because the designers found that three of the OSI layers (Presentation, Session, and the upper half of Application) are so thin in practice that they are better expressed as application-layer protocols than as separate OS services.

```text
OSI Model              TCP/IP Model          Example Protocols              Implementation
─────────────          ─────────────          ────────────────────          ───────────────
7. Application         4. Application         HTTP, gRPC, DNS, SSH           User-space app + framework
6. Presentation        (merged into 4)        TLS, JPEG, ASCII, protobuf     TLS lib, codec lib
5. Session             (merged into 4)        RPC handles, SOCKS             App-layer session logic
4. Transport           3. Transport           TCP, UDP, QUIC                 Kernel (net/ipv4/)
3. Network             2. Internet            IP, ICMP, OSPF                 Kernel (net/ipv4/)
2. Data Link           1. Link                Ethernet, WiFi, ARP            Kernel driver + NIC firmware
1. Physical            (not modeled)          1000BASE-T, 802.11ac           NIC hardware + the wire
```

Layer 7 (Application) is where your framework lives. Spring MVC, Express, Django, Flask, and Laravel are all layer-7 HTTP parsers and routers. Layer 6 (Presentation) is where data format conversion and encryption happen — TLS is conceptually a layer-6 protocol even though it runs over TCP (layer 4); Protobuf and JSON serialization are also layer-6 concerns. Layer 5 (Session) is the thinnest layer: it manages dialogue control (half-duplex vs full-duplex), session checkpointing, and session recovery. In modern stacks, the session layer is folded into the application — gRPC streams, HTTP/2 streams, and WebSocket connections all do "session management" without a separate layer-5 service.

Layer 4 (Transport) is the TCP/UDP layer. This is where the kernel provides reliable byte-stream delivery (TCP) or unreliable datagram delivery (UDP). The kernel owns this layer — your user-space code cannot change TCP's congestion control without sysctls. Layer 3 (Network) is IP. This is where packets are routed across networks. ICMP (ping, traceroute) lives here. Layer 2 (Data Link) is Ethernet or WiFi — frames are delivered between directly-connected hosts using MAC addresses, and ARP translates IP addresses to MAC addresses. Layer 1 (Physical) is the wire itself: voltage levels on copper, light pulses on fiber, radio waves for WiFi.

The reason OSI failed as an implementation is that the European governments tried to mandate it through "Government OSI Profiles" (GOSIP) in the late 1980s, but the actual OSI protocol stacks (X.400 for email, X.500 for directory, FTAM for file transfer) were over-engineered, late to ship, and lost to the simpler TCP/IP equivalents (SMTP, LDAP, FTP/HTTP). The internet's "rough consensus and running code" culture produced working software faster than the ISO committee process. But OSI's *vocabulary* — seven named layers — was so useful for teaching and debugging that it became the universal reference, even among engineers who had never read ISO/IEC 7498-1. When a network engineer says "layer 3 switch" or "layer 7 load balancer", they are using OSI numbering even though the device itself speaks TCP/IP.

### Packet encapsulation and decapsulation across network boundaries

When your framework calls `socket.write(b"GET / HTTP/1.1\r\n\r\n")`, the bytes do not go on the wire as-is. Each layer wraps the layer above it with its own header — a process called **encapsulation**. On the receiving side, each layer strips its header and hands the payload up — **decapsulation**. The result is that an HTTP request that fits in one TCP segment actually travels on the wire as an Ethernet frame containing an IP packet containing a TCP segment containing the HTTP bytes.

```text
Application (HTTP):
  GET /api/users/42 HTTP/1.1\r\nHost: api.example.com\r\n\r\n    (48 bytes)

Transport (TCP) adds 20-byte header:
  [src_port=54321 | dst_port=80 | seq=1000 | ack=0 | flags=PSH+ACK | win=64240 | ...]
  + HTTP payload                                                        (68 bytes total)

Internet (IP) adds 20-byte header:
  [version=4 | IHL=5 | TTL=64 | protocol=6 (TCP) | src=10.0.0.5 | dst=93.184.216.34 | ...]
  + TCP segment                                                         (88 bytes total)

Link (Ethernet) adds 14-byte header + 4-byte FCS:
  [dst_mac=aa:bb:cc:dd:ee:ff | src_mac=00:11:22:33:44:55 | ethertype=0x0800 (IPv4)]
  + IP packet
  + [FCS checksum]                                                      (106 bytes on wire)
```

Each layer's header references the layer above using a numeric protocol type: Ethernet's `ethertype` field is `0x0800` for IPv4 (or `0x86DD` for IPv6), IP's `protocol` field is `6` for TCP (or `17` for UDP, `1` for ICMP), and TCP's destination port `80` tells the kernel to hand the payload to the HTTP server process that has bound that port. This is how the receiver knows which layer to dispatch to next at every step of decapsulation.

The unit of data has a different name at each layer — a fact that confuses newcomers: at layer 4 it is a **segment** (TCP) or **datagram** (UDP), at layer 3 it is a **packet**, at layer 2 it is a **frame**, and at layer 1 it is a **bit** (or symbol). When a network engineer says "the packet was dropped at the L3 router", they mean the IP-layer forwarding decision failed. When they say "the frame was lost on the L2 switch", they mean the Ethernet frame did not make it between switch ports.

A real `tcpdump` capture of an HTTP request, annotated layer-by-layer, makes this concrete:

```text
$ sudo tcpdump -i any -nn -XX 'tcp port 80 and host 93.184.216.34'
14:23:01.123456 eth0  In  10.0.0.5.54321 > 93.184.216.34.80: Flags [P.], seq 1:25, ack 1, win 64240, length 24
        0x0000:  aabb ccdd eeff 0011 2233 4455 0800 4500   ← Ethernet header (dst, src, ethertype=IPv4)
        0x0010:  0040 1234 4000 4006 0000 0a00 0005 5db8   ← IP header (TTL=64, proto=6=TCP, src=10.0.0.5)
        0x0020:  d822 d431 0050 0000 03e8 0000 0001 5018   ← TCP header (src_port=54321, dst_port=80)
        0x0030:  fae0 0000 0000 4745 5420 2f61 7069 2f75   ← TCP payload starts: "GET /api/u"
        0x0040:  7365 7273 2f34 3220 4854 5450 2f31 2e31   ← "...sers/42 HTTP/1.1"
```

Read the hex dump column by column: the first 14 bytes are the Ethernet header (`aabb ccdd eeff` is the destination MAC, `0011 2233 4455` is the source MAC, `0800` is the ethertype for IPv4). The next 20 bytes are the IP header (`4500` is the version+IHL+TOS word, `0040` is total length 64, `4006` is TTL=64 and protocol=6=TCP, `0a00 0005` is source IP 10.0.0.5, `5db8 d822` is dest IP 93.184.216.34). The next 20 bytes are the TCP header (`d431` is source port 54321, `0050` is dest port 80, `0000 03e8` is sequence number 1000, `5018` is data offset 5 (20 bytes) plus flags PSH+ACK). The rest is the HTTP payload. This is the encapsulation layer cake made visible.

### Maximum Transmission Unit (MTU), Maximum Segment Size (MSS), and Path MTU Discovery

The Ethernet frame has a maximum payload size called the **MTU** (Maximum Transmission Unit). Standard Ethernet has an MTU of 1500 bytes. This 1500-byte limit includes the IP header (20 bytes) and the TCP header (20 bytes), leaving a **Maximum Segment Size (MSS)** of 1460 bytes for the TCP payload. If your application writes 10 KB to a socket, the kernel splits it into roughly seven TCP segments of ~1460 bytes each, each wrapped in its own IP packet and Ethernet frame.

```text
Ethernet frame on standard Ethernet:
┌──────────────────────────────────────────────────────────┐
│ Ethernet header (14B) │ IP header (20B) │ TCP hdr (20B) │ TCP payload (≤1460B) │ FCS (4B) │
└──────────────────────────────────────────────────────────┘
                        ←─────── MTU = 1500 bytes ────────→
                                          ←── MSS = 1460 ──→
```

MTU varies by link layer: standard Ethernet is 1500, jumbo frames in data centers are 9000, PPPoE (DSL) is 1492, GRE tunnels add 24 bytes of overhead (so 1476 inner MTU), VXLAN adds 50 bytes (so 1450). VPNs and tunnels stack these overheads — a packet that fits on the physical wire may not fit through the tunnel, which is why tunnel endpoints must fragment or run Path MTU Discovery.

**Path MTU Discovery (PMTUD)**, defined in RFC 1191, works as follows: the sender sets the IP `Don't Fragment` (DF) flag on every packet. If an intermediate router cannot forward the packet because its outgoing interface has a smaller MTU, the router drops the packet and sends back an ICMP `Fragmentation Needed` error containing the next-hop MTU. The sender then reduces its packet size and retries. This fails when overzealous firewalls block all ICMP — the classic symptom is "small packets work, large packets hang" because the sender never learns that it must reduce the segment size. The fix is **TCP MTU Probing** (RFC 4821, `net.ipv4.tcp_mtu_probing=1`), which detects black-hole PMTUD by trying progressively smaller segments until they get through.

The production failure mode is the **MSS clamping** problem on VPNs. A user on a corporate VPN cannot download files larger than ~1450 bytes — the connection hangs at exactly the moment the server sends the second TCP segment. The cause is that the VPN adds 50–100 bytes of encapsulation overhead, reducing the effective MTU to 1400, but PMTUD is broken because the VPN's firewall drops ICMP. The fix is to clamp the TCP MSS to a lower value at the VPN gateway: `iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN -o tun0 -j TCPMSS --clamp-mss-to-pmtu`.

## How This Connects to the Frameworks

Every framework in section 05 is a layer-7 HTTP parser and router sitting on top of a socket. When you write `@app.get('/users/:id')` in Express or `@GetMapping('/users/{id}')` in Spring, the framework:

1. Calls `accept()` on the listening socket (or returns from `epoll_wait` indicating the socket is readable).
2. Reads the HTTP request line and headers from the socket buffer using `recv()` (or `read()`).
3. Parses the request method, path, and headers — this is layer 7 work.
4. Matches the path against the registered routes.
5. Invokes your handler with the parsed request.
6. Serializes your handler's return value into an HTTP response.
7. Writes the response to the socket buffer using `send()`.
8. Either closes the connection (`Connection: close`) or keeps it alive for reuse (`Connection: keep-alive`).

If any of these steps fails — a malformed request, a slow client, a dropped packet — the failure surfaces at a different layer: a malformed request is a 400 at layer 7, a slow client triggers a layer-4 keepalive timeout, a dropped packet causes a layer-3 retransmission stall. Knowing which layer caused the failure is the difference between a 5-minute fix and a 5-hour incident.

## Hands-On Exercise

```bash
# See TCP states on your machine — these are layer-4 connection states
ss -tan | awk '{print $1}' | sort | uniq -c

# Capture and inspect an HTTP request layer-by-layer
# -nn: no name resolution, -XX: hex+ASCII dump, -s 0: full packet
sudo tcpdump -i lo -nn -XX -s 0 'tcp port 8080'

# Inspect a TLS handshake — TLS sits at layer 6, between TCP (4) and HTTP (7)
openssl s_client -connect example.com:443 -servername example.com

# Check HTTP/2 support — HTTP/2 multiplexes many layer-7 streams over one layer-4 connection
curl -v --http2 https://example.com 2>&1 | grep -i 'ALPN\|HTTP/2'

# Check the MTU of your interfaces — this is the layer-2 frame size limit
ip link show | grep mtu

# Disable PMTUD black-hole detection (then re-enable to see the difference)
sudo sysctl net.ipv4.tcp_mtu_probing
```
