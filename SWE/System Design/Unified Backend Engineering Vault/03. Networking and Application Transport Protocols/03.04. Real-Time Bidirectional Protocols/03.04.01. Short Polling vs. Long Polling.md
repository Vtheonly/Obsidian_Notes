# 03.04.01. Short Polling vs. Long Polling

## What This Is

Short polling and long polling are the two pre-WebSocket strategies for delivering "real-time" updates to a browser over the HTTP/1.1 protocol. They exist because HTTP/1.1 was designed as a request/response protocol — the client asks, the server answers, the connection closes — and there was no native way for the server to push data to a client that hadn't asked for it. Both polling techniques are workarounds layered on top of the request/response model; both have been superseded by Server-Sent Events (RFC 8259 territory) and WebSocket (RFC 6455) for new applications, but they persist in legacy code, in mobile push-notification delivery (where the OS itself uses long polling), and in environments where proxies strip WebSocket upgrades.

The notes in this sub-section sit between the socket primitives of [[03.03. TLS Cryptographic Security and PKI]] / [[02.04.03. The POSIX Socket Lifecycle]] (the layers that actually carry the bytes) and the framework abstractions of section 05 (which expose polling as a one-liner like `setInterval(fetchUpdates, 5000)`). Understanding the failure modes of polling — empty-request floods, thread-pool exhaustion, message-ordering races — is a prerequisite for diagnosing the production incidents that motivated SSE and WebSocket in the first place.

## The Details

### Short Polling: High HTTP request overhead, server resource consumption, and latency bounds

Short polling is the simplest possible push simulation: the client fires `GET /updates` on a fixed interval (typically every 1–15 seconds), the server responds immediately with either the latest data or an empty `204 No Content`, and the client sleeps for N seconds before repeating. There is no server-side state about which client has seen which message — every response is computed fresh from the current snapshot of the world.

The cost model is brutal. Every poll pays the full HTTP/1.1 tax: if the connection is not keep-alive, a fresh TCP three-way handshake (1 RTT, ~10 ms in a datacenter, ~50–100 ms cross-region), a TLS 1.3 handshake if HTTPS (~1 RTT after the resumption cache misses), the request headers (~800 bytes for a typical browser request with cookies and `User-Agent`), the route dispatch in the framework (regex match, middleware chain, JSON serialization), and the response headers (~300 bytes). For a 5-second poll interval with 10,000 connected clients, that is 2,000 requests per second hitting your server, of which ~95% return an empty `204 No Content` — pure overhead.

```text
Client                            Server
  │                                 │
  │── GET /updates ───────────────► │  (TLS handshake + HTTP headers ~800B)
  │◄─ 204 No Content ──────────────│  (response ~200B, "nothing new")
  │                                 │
  │  sleep(5s)                      │
  │                                 │  ← event M1 arrives at t=0.1s
  │                                 │     but no one is asking right now
  │                                 │
  │── GET /updates ───────────────► │  (at t=5s, finally asks)
  │◄─ 200 OK {M1} ──────────────────│  (event M1 delivered 4.9s late)
```

The latency floor is the poll interval: if data arrives at t=0.1 s but the client only polls at t=5 s, the user perceives 4.9 s of latency. The average latency across messages is N/2; the worst case is N. Real numbers: Gmail in 2004 used 30 s polling, giving users a 15 s average notification delay. Modern apps that require sub-second notifications (chat, trading dashboards) cannot meet their SLA with short polling regardless of how fast the server is — the bottleneck is the client's clock, not the server's CPU.

The connection churn is the secondary failure. Each closed TCP connection leaves a `TIME_WAIT` socket on the server for 60 seconds (RFC 793 §3.5; tunable via `net.ipv4.tcp_fin_timeout`). With 10,000 clients polling every 5 s and no keep-alive, you accumulate ~120,000 `TIME_WAIT` sockets, blowing past the default `net.ipv4.tcp_max_tw_buckets` of ~32768 and triggering kernel warnings in `dmesg`. The fix is HTTP/1.1 keep-alive (default in modern clients and servers), which keeps the TCP connection open across polls — but then you are holding 10,000 idle connections in memory, which is exactly the scalability problem long polling was invented to amortize.

Production failure mode: a marketing campaign email goes out, 50,000 users open the app within a 60-second window, the synchronized poll interval means every client polls at t=0, t=5, t=10 — synchronized request spikes that look like a DDoS. The mitigation is client-side jitter (randomize the interval ±20%) and server-side rate limiting, but the real fix is to abandon short polling for any latency target below 5 s.

### Long Polling (Comet): Holding open HTTP connections (`hanging GET`), server-side timeou...

Long polling (the "Comet" pattern, named by Alex Russell in 2006) inverts the request/response model: the client sends `GET /updates`, and the server holds the response open without writing anything. The TCP connection sits idle in `ESTABLISHED`. When data becomes available, the server writes the response and closes the connection (or sends `Transfer-Encoding: chunked` and keeps the stream open). The client immediately issues another `GET /updates` to re-enter the holding state. If no data arrives within a server-defined timeout (typically 30–55 s), the server responds with `204 No Content` and the client reconnects — this is the "hanging GET".

The architectural consequence is that the server can no longer be thread-per-connection. With a 200-thread Tomcat pool and a 30 s long-poll timeout, you can hold at most 200 concurrent clients — the 201st request queues in the accept queue (visible as `Recv-Q > 0` on `ss -tln`) and times out before its handler is even invoked. This is the historical reason Servlet 3.0 (JSR 315, 2009) added `AsyncContext.startAsync()` and Spring WebMvc added `DeferredResult` and `Callable` return types — they let an HTTP request be "parked" without consuming a request thread, freeing the thread to handle other requests while the long-poll waits for data. Netty, Undertow, Jetty Continuations, Node.js, and Python's asyncio were all designed around this same need.

```text
Time    Client                       Server                     Per-client buffer
 0.00   GET /updates?since=42   ──►  (park request, no thread)
 0.50                                event M43 arrives           [M43]
 0.50                                respond 200 {M43}            []
 0.51   GET /updates?since=43   ──►  (park request)
 0.60                                event M44 arrives           [M44]
 0.61                                respond 200 {M44}            []
 0.62   GET /updates?since=44   ──►  (park request)
 0.70                                events M45 + M46 arrive     [M45, M46]
 0.70                                respond 200 {[M45,M46]}      []
 0.71   GET /updates?since=46   ──►  (park request, idle)
 30.71                               timeout → 204 No Content     []
 30.72   GET /updates?since=46   ──►  (reconnect)
```

The message-ordering race is the classic Comet bug. When the server responds to the long-poll with message M1, the client receives it and fires a new poll. In the ~10 ms window between the response being written and the new poll arriving at the server, the server may produce message M2 — but there is no pending long-poll to receive it. Without a server-side buffer, M2 is silently dropped. The fix is the `?since=<seq>` parameter: every event carries a monotonic sequence number, the client sends `Last-Event-ID` (or `?since=`) on reconnect, and the server drains its per-client queue from that sequence forward. Without this, production manifests as "intermittent missed notifications" — the worst kind of bug to reproduce because it depends on sub-millisecond timing between the server's event producer and the client's reconnect.

Timeout arithmetic is a frequent production trap. The server's long-poll timeout must be shorter than every intermediary's idle timeout: nginx `proxy_read_timeout` defaults to 60 s, AWS ALB idle timeout is 60 s, Cloudflare free tier is 100 s, the browser's own fetch timeout varies. If your server waits 60 s and the ALB also gives up at 60 s, the ALB returns 502 to the client while your server is still mid-response — and the client's reconnect arrives at a server that thinks the previous request is still in flight. Always set `server_timeout < proxy_timeout < browser_timeout`, e.g. server 45 s, nginx 55 s, browser 60 s. The `X-Accel-Buffering: no` header is the escape hatch for nginx-specific buffering.

### Scalability limits: Thread and connection pool exhaustion under long polling architectures

The scalability ceiling of long polling is not bandwidth or CPU — it is open connections held in kernel memory. Every hanging GET consumes: (1) a TCP socket in `ESTABLISHED` state in the kernel's `tcp_hashinfo` table (~2 KB of `struct sock` state plus default 64 KB receive buffer + 16 KB send buffer = ~80 KB per connection at default `sysctl` settings), (2) a file descriptor in the process (counts against `ulimit -n` per process and `fs.file-max` system-wide), (3) in thread-per-connection servers, a blocked OS thread with its own 8 MB stack — a 4 GB-process can hold only ~500 such threads before OOM. The "C10K problem" (Dan Kegel, 1999) was specifically about exceeding these limits for Comet servers; modern event-driven servers (Netty, Undertow, Node.js, asyncio) were the answer.

```text
Thread-per-connection model (Tomcat default configuration):
  200 worker threads × 30 s long-poll timeout
  → max 200 concurrent hanging GETs
  → 201st client waits in accept queue → 30 s timeout → 504

Event-driven model (Netty/Undertow with epoll):
  4 worker threads × epoll_wait multiplexing
  → 10,000+ concurrent hanging GETs
  → bounded by FD limit (fs.file-max) and RAM (per-conn buffers)
```

The HTTP/1.1 browser connection limit compounds the problem. RFC 2616 §8.1.4 says a client SHOULD NOT open more than 2 concurrent connections per origin; modern browsers raised this to 6. If your dashboard dedicates one connection to long polling, you have consumed 1/6 of the client's available connections to your origin — open six dashboards in six tabs and zero connections remain for any other request, freezing the entire UI. HTTP/2 lifts this ceiling (one TCP connection, multiplexed streams), but the server-side per-connection memory cost remains.

Production failure mode: at 03:00 a marketing email triggers 50,000 simultaneous app opens, every client enters the long-poll loop within 30 s, and the server hits its 200-thread limit. `ss -tan state established '( sport = :8080 )' | wc -l` climbs linearly. `dmesg` starts emitting `TCP: out of memory -- consider tuning tcp_mem`. Tomcat logs `SEVERE: All threads (200/200) are busy`. HAProxy shows rising `cli_abrt` (clients gave up waiting) and `srv_abrt` (server closed mid-response). The dashboard goes blank for 5 minutes, then recovers as clients back off. The fix is one of: switch to async event-loop architecture (Spring WebFlux on Reactor Netty, Node.js with cluster, asyncio with uvloop), raise `ulimit -n` to 65536+ and `fs.file-max` to 1M+, or migrate to SSE / WebSocket which were designed for this exact failure mode. See [[03.04.02. Server-Sent Events (SSE)]] and [[03.04.03. The WebSocket Protocol RFC 6455]] for the modern solutions.

## How This Connects to the Frameworks

Every framework in section 05 either ships a polling helper or exposes the underlying async primitive that long polling requires. In Spring WebMvc (synchronous, thread-per-request), the long-poll endpoint is implemented with `DeferredResult<UserUpdate>` — the request thread is released, the servlet container parks the request, and a separate thread completes the `DeferredResult` when data arrives. In Spring WebFlux (reactive), the same endpoint returns `Flux<UserUpdate>` and the Reactor Netty server handles thousands of parked requests per worker thread. In Express (Node.js), the equivalent is `res.setTimeout(0)` plus an event listener that calls `res.json(data)` when the EventEmitter fires — Node's single-threaded event loop holds 10,000 parked responses trivially. In Django, the sync WSGI path requires `async_to_sync` wrapping or a switch to ASGI (Daphne/Uvicorn) to avoid the GIL-bound worker pool. In Laravel, the Octane server with Swoole or RoadRunner enables the same long-poll pattern. The concept is identical across all four; only the API surface differs.

## Hands-On Exercise

```bash
# 1. Watch TIME_WAIT accumulate on a short-polling server under load
#    (run a short-polling client in another terminal hitting /updates every 1s)
ss -tan state time-wait | wc -l
sysctl net.ipv4.tcp_max_tw_buckets net.ipv4.tcp_fin_timeout

# 2. Watch accept-queue overflow on a thread-per-connection server
#    (set backlog=10, fire 50 concurrent long-polls)
ss -tln  # Recv-Q > 0 means accept queue is filling

# 3. Inspect a hanging GET with curl --no-buffer
curl -N -i http://localhost:8080/long-poll
# You should see the response headers arrive immediately,
# then the body arrives 30s later (or whenever data is ready).

# 4. Reproduce the message-ordering race
#    Server: emit M1, M2, M3 at 1ms intervals
#    Client: long-poll, receive M1, sleep 50ms, long-poll again
#    Without ?since=: M2 is dropped (no poll pending when M2 was emitted)
#    With ?since=1: server drains M2, M3 from per-client buffer

# 5. Measure long-poll latency floor vs short polling
#    (use ab or wrk2 with 1000 concurrent clients)
ab -n 100000 -c 1000 -t 30 http://localhost:8080/short-poll
ab -n 100000 -c 1000 -t 30 http://localhost:8080/long-poll

# 6. Watch thread-pool saturation in Tomcat
#    (with 200 maxThreads and 500 concurrent long-polls)
jcmd <pid> Thread.print | grep -c "http-nio-8080-exec"
# If this equals maxThreads, the pool is saturated.
```
