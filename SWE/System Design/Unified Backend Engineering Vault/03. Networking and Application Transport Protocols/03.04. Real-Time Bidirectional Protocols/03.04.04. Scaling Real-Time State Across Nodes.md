# 03.04.04. Scaling Real-Time State Across Nodes

## What This Is

A single-node WebSocket or SSE server (see [[03.04.02. Server-Sent Events (SSE)]] and [[03.04.03. The WebSocket Protocol RFC 6455]]) is trivial: when client A sends a message addressed to client B, the server looks up B's connection object in an in-process `Map<UserId, WebSocket>` and writes the bytes to B's socket. With 10,000 concurrent clients on a single beefy EC2 box, this works fine — Netty can hold 100,000+ connections on a c5.2xlarge, and the in-process map lookup is O(1).

The moment you add a second server — for capacity, for availability, for rolling deploys — the in-process map stops working. Client A is connected to node-1; client B is connected to node-2; when A sends a message to B, node-1 has never heard of B because B's socket lives on node-2. This note covers the four sub-problems that arise at multi-node scale: the basic multi-node routing problem, the Pub/Sub backplane pattern that solves it, the sticky-session versus stateless-gateway architectural choice, and the thundering-herd reconnect storm that hits every rolling deploy. Each of these is a layer above the socket primitives of [[02.04.03. The POSIX Socket Lifecycle]] and a prerequisite for the real-time framework code in section 05.

## The Details

### The multi-node problem: Clients connected to different physical server instances cannot...

The multi-node problem is invisible at small scale and catastrophic the moment you provision a second backend. Consider: client A is on node-1, client B is on node-2. A sends `"hello"` to B. Node-1 receives the message, looks up B in its local `Map<UserId, WebSocket>`, finds nothing (because B's connection is on node-2), and silently drops the message. The delivery failure is not even logged — the local lookup returned `null`, the message handler returned `200 OK`, and everyone is happy except the user.

```text
                  ┌─────────────────────────────┐
                  │  Load Balancer (L4 / L7)    │
                  │  round-robin or sticky      │
                  └────────┬────────────────────┘
                           │
            ┌──────────────┴──────────────┐
            │                              │
   ┌────────▼────────┐         ┌──────────▼────────┐
   │  Node 1         │         │  Node 2           │
   │  clients: A, C  │         │  clients: B, D    │
   │  local map:     │         │  local map:       │
   │   {A → ws,      │         │   {B → ws,        │
   │    C → ws}      │         │    D → ws}        │
   └─────────────────┘         └───────────────────┘

   A wants to send to B.
   Node 1's local map has no entry for B.
   → Message is dropped silently. B never receives it.
```

The naive fix is **broadcast**: when any node receives a message addressed to any user, it forwards the message to every other node over an internal cluster bus. Each node checks its local map and either delivers or discards. This works, but the cost is O(N²) in node count — every message crosses every inter-node link. With 10 nodes each handling 1,000 msg/s of user traffic, each node receives 9,000 msg/s of forwarded messages from its peers, of which 8,900 are discarded (only 1/N find their target on any given node). At 100 nodes the math collapses entirely — 99,000 forwarded messages per node per second, of which 99% are wasted.

The right fix is a **routing layer**: each node publishes "client X connected to me" events to a shared registry (Redis, etcd, a gossip protocol like SWIM or HashiCorp Memberlist). When node-1 wants to send to user B, it queries the registry to discover that B is on node-2, and forwards the message directly to node-2 over a node-to-node channel (TCP, gRPC, NATS, AMQP — any reliable transport). This is O(1) per message: one lookup, one forward. The trade-off is that the registry itself becomes a coordination point with its own failure modes (split-brain during network partitions, registration lag during reconnects, the registry going down means no cross-node messaging at all).

A third pattern, used by Discord at scale (~5 million concurrent WebSocket connections), is **sharding by user ID**: hash(user_id) % N assigns each user to a deterministic node. A is always on node-1, B is always on node-2, and any node can compute "where is B?" locally without a registry lookup. The cost is rebalancing pain when N changes (every shard boundary moves) and hotspots if one user is disproportionately active. Discord solves rebalancing with a "virtual node" indirection layer (consistent hashing).

Production failure mode: a team ships a single-node WebSocket server, gets traction, adds a second node for capacity behind a round-robin load balancer, and within an hour users report "private messages sometimes don't arrive". Group chat (broadcast to all online users in a room) still works because every node has at least some members of every room. Direct messages fail because the sender and recipient are usually on different nodes. The fix is one of the three patterns above; broadcast is the easiest to implement and the first to break at scale.

### State distribution via Publish/Subscribe backplanes (Redis Pub/Sub, NATS)

The dominant pattern for multi-node real-time state is the Pub/Sub backplane. Each application node subscribes to a channel (e.g., `chat:room:42`) on a shared broker. When a client sends a message, the receiving node publishes it to the channel; every node subscribed to that channel (including the publisher) receives the message and delivers it to any local clients in that room. This decouples the publisher from the set of subscribers — the publisher does not need to know which nodes have which clients.

Redis Pub/Sub is the most common backplane for moderate scale (single Redis instance, ~100,000 messages/sec throughput, fan-out to thousands of subscribers). Redis also offers Sharded Pub/Sub (Redis 7.0+, splits channels across cluster slots) for horizontal scaling beyond a single Redis instance's CPU. The pattern is what Socket.IO, Spring's `RedisMessageBroker` (in `spring-websocket`), ASP.NET Core's `Redis Backplane`, and Phoenix's `Phoenix.PubSub.Redis` all use under the hood. The developer-facing API is "publish to a topic" / "subscribe to a topic"; the cross-node fan-out is invisible.

```text
              ┌─────────────────────────────────┐
              │  Redis Pub/Sub                  │
              │  channel: "chat:room:42"        │
              └──┬───────────┬───────────┬──────┘
                 │           │           │
        ┌────────┘           │           └────────┐
        │                     │                    │
   ┌────▼────┐          ┌─────▼────┐         ┌─────▼────┐
   │ Node 1  │          │  Node 2  │         │  Node 3  │
   │ A (sub) │          │  B (sub) │         │  C (sub) │
   └────┬────┘          └──────────┘         └──────────┘
        │
   A sends "hello" → Node 1 PUBLISH chat:room:42 "hello"
                   → Redis fans out to all subscribers
                   → Nodes 1, 2, 3 deliver to A, B, C respectively
```

NATS is the alternative for higher throughput (millions of msg/sec on a single NATS server) or when you need features Redis Pub/Sub lacks: durable subscriptions (NATS JetStream, similar to Kafka), subject hierarchies with wildcards (`chat.room.42.>` matches `chat.room.42.user.joined` and `chat.room.42.user.left`), and queue groups for load-balanced delivery (only one subscriber in a queue group receives each message — useful for worker pools). Apache Kafka is sometimes used as a backplane but is overkill for ephemeral fan-out — Kafka's strength is durable ordered logs, not fire-and-forget messaging; the operational cost of partition management and consumer-group rebalancing is rarely justified for real-time presence.

The backplane pattern has a subtle cost: every message hits the network twice (client → node, then node → backplane → node → client). With Redis on the same VPC this adds ~0.5–1 ms of latency per message (a `PUBLISH` round-trip plus the fan-out `SUBSCRIBE` delivery). Cross-AZ Redis adds 1–2 ms. Cross-region Redis adds 50–200 ms — at which point you should shard by region and accept that inter-region real-time messaging is slow, or use a backplane designed for geo-distribution (NATS Leaf nodes, Kafka MirrorMaker).

The CAP tradeoff in real-time systems is real and unavoidable. If the backplane goes down, every node can still serve its local clients — but cross-node messages cannot be delivered. This manifests as "private messages to users on other nodes fail silently" — the sender sees no error (the local node accepted the message), but the recipient never gets it. Mitigations: replicate the backplane (Redis Sentinel for failover, Redis Cluster for sharding, NATS cluster of 3+ nodes), fall back to client-side retry with idempotency (the client re-sends if no ACK arrives), or accept the degradation and surface it in the UI ("some messages may be delayed"). Most production systems accept temporary degradation during backplane outages rather than paying the latency cost of synchronous cross-node quorum on every message.

Production failure mode: a single Redis instance serving as the Pub/Sub backplane goes down at 02:00 for a routine failover to its replica. The failover takes 8 seconds. During those 8 seconds, every real-time message sent across nodes is lost — the publishing node's `PUBLISH` call returns an error, the message is dropped, and the user sees nothing. The fix is either: (a) make the publish synchronous and reject the user's send if the backplane is down (trades availability for consistency), (b) queue locally and retry (trades consistency for availability, risks duplicate delivery), or (c) use a backplane with built-in clustering and failover (Redis Cluster, NATS cluster) so the failure is invisible. Most chat systems choose (b) and accept at-most-once delivery with possible duplicates, which is why chat apps often have client-side deduplication.

### Sticky sessions vs. Stateless Socket Gateways

The sticky session pattern (also called "session affinity") is the architectural alternative to a backplane. The load balancer hashes on a cookie, a query parameter, or the client IP to route every connection from a given client to the same backend node. Once a WebSocket is open on node-2, all subsequent HTTP requests from that client also go to node-2 — including non-WebSocket REST calls. The local in-process state (the WebSocket connection, the user's session, the per-user message queue) stays local — no need to share it across nodes or hit a backplane.

Sticky sessions are implemented differently by different load balancers:
- **AWS ALB**: `lb_cookie` stickiness (ALB injects an `AWSALB` cookie with an expiration; subsequent requests carrying this cookie route to the same target).
- **HAProxy**: `balance source` (hash the source IP) or `cookie SERVERID insert indirect nocache` (HAProxy injects a cookie).
- **nginx**: `ip_hash` directive (hash source IP) or `sticky cookie srv_id expires=1h;` (nginx Plus only).
- **Envoy**: `hash_policy` with source IP or a specific cookie, in the `weighted_clusters` configuration.

```text
Sticky Session Model:
  Client A ──► LB ──► (always) ──► Node 2
                              │
                              └─ A's state lives only on Node 2
                                 Node 2 dies → A's state is gone
                                 A must reconnect, may lose messages

Stateless Gateway Model:
  Client A ──► LB ──► (any) ──► Node N
                              │
                              └─ A's state lives in Redis/etcd
                                 Any node can serve any request
                                 Node N dies → A reconnects to Node M,
                                   picks up state from Redis, no loss
```

The problems with sticky sessions are operational. (1) **Hotspots**: if your hash is on user ID and one user is a heavy chatter (a bot, a customer-support agent, a power user), their node gets disproportionate load. (2) **Rebalancing pain**: when a node dies, all its clients reconnect simultaneously and the rebalanced targets see a transient spike. (3) **State loss on deploy**: a rolling deploy takes a node out of the pool, all its WebSocket clients drop and reconnect — at scale this is a thundering-herd event (see the next H3). (4) **LB coupling**: the application now depends on LB behavior — testing locally is hard, switching LB vendors can break assumptions, and the LB itself becomes a single point of failure for routing decisions.

The stateless gateway pattern eliminates these problems by making every node identical and storing all shared state in an external store: Redis for presence (which user is on which node), Redis Streams or Kafka for per-user message queues, Postgres for durable state. When a client connects, the node registers the connection in Redis (`SET ws:conn:user:42 node-3` with a TTL of 60 s, refreshed by heartbeats). When any node wants to send to user 42, it looks up the node (`GET ws:conn:user:42` → `node-3`), then forwards the message to node-3 over a node-to-node channel (a gRPC stream, a Redis Pub/Sub channel scoped to node-3, a NATS subject like `node.3.inbox`). This is the dominant pattern at scale (Discord uses it for ~5 M concurrent connections; Slack uses a variant).

The trade-off is operational complexity. Every message now requires a Redis lookup (O(1), but adds 0.5–1 ms of latency) and the Redis cluster becomes a critical dependency — if it goes down, all real-time messaging stops. Most production systems accept this trade-off because the operational simplicity of stateless nodes (any node can be killed, restarted, or replaced at any time without losing user state) outweighs the latency cost and the Redis dependency. Sticky sessions are easier to reason about and acceptable for systems under ~50,000 concurrent connections where the backplane's complexity is not yet justified.

Production failure mode: a team starts with sticky sessions, grows to 30 nodes, and discovers that any single node restart drops 1/30 of their users for 5–10 seconds while they reconnect and the LB re-routes. The team adopts the stateless pattern with a Redis presence layer, but on the first deploy they discover that presence registration has a 2-second lag (the TTL is 60 s, so a dead node's registrations linger for up to 60 s before being cleared, causing messages to be forwarded to a dead node and dropped). The fix is a shorter TTL (5–10 s) with more frequent heartbeats, or an explicit deregister on graceful shutdown combined with a fallback TTL for ungraceful shutdowns.

### Handling mass reconnect storms (Thundering Herd) during deployments using exponential b...

When you deploy a new version of your real-time backend, the standard pattern is a rolling deploy: drain node-1's connections (send a Close frame with code `1001 Going Away`), wait for clients to disconnect, restart the process, move to node-2. At small scale this works fine. At large scale (100,000+ concurrent clients), the moment node-1 closes all its connections, 10,000 clients try to reconnect in the same second. The load balancer distributes them across the surviving nodes — which see a 10,000-connection spike, possibly pushing them over their memory or CPU limits. Then node-2's deploy starts, and another 10,000 clients reconnect. The cascade continues until either the deploy pauses or the entire fleet falls over.

This is the thundering herd problem, and the standard solution is client-side exponential backoff with jitter. When the client's WebSocket disconnects unexpectedly (Close frame `1001`, `1011`, or `1006` abnormal closure), the client waits a random duration before reconnecting:

```javascript
function reconnectDelay(attempt) {
  const base = 1000 * Math.pow(2, attempt);  // 1s, 2s, 4s, 8s, 16s
  const cap = 30000;                          // never wait more than 30s
  const jitter = Math.random() * 1000;        // 0-1s of random jitter
  return Math.min(base, cap) + jitter;
}
// Attempt 1: ~1s + jitter
// Attempt 2: ~2s + jitter
// Attempt 5: ~16s + jitter
// Attempt 6+: 30s + jitter (capped)
```

The jitter is the load-bearing part. Without jitter, every client reconnects at exactly t+1s, t+2s, t+4s — synchronized spikes that overwhelm the surviving nodes. With jitter, the reconnects spread out across the window, and the surviving nodes see a smooth ramp instead of a spike. AWS published a famous article ("Exponential Backoff and Jitter", March 2015) showing that "full jitter" (`random(0, base)`) outperforms "equal jitter" (`base/2 + random(0, base/2)`) for distributed systems because it maximizes the spread across the window.

```text
Without jitter (10k clients disconnect at t=0):
  t=1.0s: 10000 reconnect attempts → server overload → 5000 fail
  t=2.0s: 5000 retries + 5000 fresh attempts = 10000 → more overload
  t=4.0s: cascading failure, autoscaler cannot keep up

With full jitter (10k clients, base=2s):
  t=0.0-2.0s: reconnect attempts spread uniformly across window
  Peak load ≈ 10000 / 2s = 5000 req/s (sustainable)
  Failed clients back off further, spread even more
```

Server-side mitigations complement client-side backoff. **Gradual drain**: instead of closing all connections on a node at once, close them in batches (1,000 per second over 10 seconds) — the LB re-routes them gradually. **Connection rate limiting**: HAProxy `rate-limit sessions 1000/min`, nginx `limit_conn`, AWS ALB has no built-in rate limit (must use AWS WAF or app-level). **Lazy re-authentication**: skip the full OAuth flow on reconnect if the original token is still valid — saves 50–200 ms of CPU per reconnect. **Read-only mode during deploy**: if the deploy is breaking, set a flag that disables writes but allows reads, so clients don't see 500 errors. **Connection draining on the LB**: AWS ALB's "deregistration delay" lets in-flight requests complete before the target is removed; set this to 30 seconds for WebSocket workloads.

The most subtle failure mode is the **distributed reconnect trap**: a load balancer that does health checks every 10 seconds will continue routing to a node that has just been killed for up to 10 seconds. During those 10 seconds, every new connection attempt to that node fails with `ECONNREFUSED`, the client backs off, but the LB has already marked the node "healthy" from the previous check. The fix is to lower the LB health check interval to 2–3 seconds for real-time backends, or to use "active" health checks (TCP connect) rather than HTTP health checks (which can pass even when the WebSocket layer is wedged).

Production failure mode: a deploy at 03:00 rolls all 10 nodes over 30 minutes, and the metrics dashboard shows a sawtooth of 100,000 → 50,000 → 100,000 → 50,000 → 100,000 connection count over those 30 minutes. Without backoff and jitter, the surviving nodes hit OOM and the deploy auto-rolls back, leaving half the fleet on the old version and half on the new — a split-brain deployment. The fix is universally: implement client-side backoff with jitter before you hit scale, add server-side connection rate limiting as defense in depth, and use a deploy strategy that drains gradually (Kubernetes `maxUnavailable: 1` and `terminationGracePeriodSeconds: 60`) rather than killing nodes in batches.

## Cross-Ecosystem Implementation

| Concern | Spring Boot (Anchor) | Express + Socket.IO | Django Channels | Laravel WebSockets |
|---|---|---|---|---|
| Backplane | `spring-websocket` `RedisMessageBroker` or `ReactorNetty` cluster | Redis adapter (`@socket.io/redis-adapter`) | Redis channel layer (`channels_redis`) | Redis pub/sub driver |
| Presence | `SimpUserRegistry` + Redis | Socket.IO adapter's `allSockets()` | `AsyncJsonWebsocketConsumer` group tracking | Custom Redis hash |
| Sticky sessions required | No (stateless gateway) | No (Redis adapter) | No (channel layer) | No (Redis pub/sub) |
| Reconnect backoff | Built into Spring's STOMP client | Socket.IO client default (`reconnectionDelay`, `reconnectionDelayMax`) | Custom JS client | Custom JS client |
| Mass-reconnect mitigation | `SubProtocolHandler` rate limits | `connectionStateRecovery` (Socket.IO 4) | Daphne `--websocket-conn-limit` | Configurable connection limit |

## Hands-On Exercise

```bash
# 1. Spin up two backend nodes behind a single Redis backplane
#    Node 1: WEBSOCKET_PORT=8081 REDIS_URL=redis://localhost:6379 node server.js
#    Node 2: WEBSOCKET_PORT=8082 REDIS_URL=redis://localhost:6379 node server.js
#    Connect A to node 1, B to node 2. A sends "hello" to B via the backplane.

# 2. Watch the backplane traffic
redis-cli SUBSCRIBE chat:room:42
# In another terminal, send a message; observe the publish/fan-out.

# 3. Inspect presence in Redis
redis-cli KEYS "ws:conn:*"
redis-cli GET ws:conn:user:42     # → "node-3"
redis-cli TTL ws:conn:user:42     # → 47 (TTL counting down)

# 4. Reproduce the thundering herd
#    Start 10,000 WebSocket clients (use Artillery or a custom Node script).
#    Kill one backend node: kill -9 <pid>
#    Observe: all clients on that node reconnect within 1 second.
#    Watch the surviving node's CPU spike to 100%.

# 5. Test reconnect with backoff and jitter
#    In the client: console.log(reconnectDelay(attempt));
#    Observe: spread of reconnect times across the window.

# 6. Test graceful drain (Kubernetes)
#    kubectl delete pod backend-1 --grace-period=60
#    Watch: pod sends SIGTERM, app drains connections over 60s,
#    LB stops routing, clients reconnect gradually.

# 7. Reproduce the split-brain backplane failure
#    Block the Redis port between node 1 and Redis: iptables -A OUTPUT -p tcp --dport 6379 -j DROP
#    Observe: messages from node 1 to node 2 silently fail.
#    Watch: redis-cli PING returns "Could not connect" on node 1.

# 8. Test presence TTL and heartbeat
redis-cli SET ws:conn:user:42 node-3 EX 60
redis-cli TTL ws:conn:user:42     # 60
sleep 5
redis-cli TTL ws:conn:user:42     # 55 (counting down)
# A heartbeat that re-runs SET every 30s keeps the TTL topped up.
```
