# 03.04.02. Server-Sent Events (SSE)

## What This Is

Server-Sent Events (SSE) is a server-to-client streaming protocol specified as part of the HTML Living Standard (formerly HTML5, §9.2). It is the middle ground between the wastefulness of polling (see [[03.04.01. Short Polling vs. Long Polling]]) and the operational complexity of WebSocket (see [[03.04.03. The WebSocket Protocol RFC 6455]]). SSE keeps a single HTTP/1.1 (or HTTP/2) connection open and lets the server push incremental events as plain UTF-8 text. There is no Upgrade handshake, no binary framing layer, no masking — the wire format is human-readable.

SSE sits in the same layer of the mental model as WebSocket: above the socket primitives of [[02.04.03. The POSIX Socket Lifecycle]], below the framework abstractions of section 05. Its killer features are that it traverses every existing piece of HTTP infrastructure (proxies, load balancers, CDNs, auth middleware) without modification, and that the browser's `EventSource` API implements automatic reconnection with the `Last-Event-ID` header — something WebSocket does not provide natively. Its hard limit is that it is unidirectional: server-to-client only. For chat, multiplayer games, or any bidirectional low-latency use case, use WebSocket.

## The Details

### The SSE Protocol: Unidirectional server-to-client streaming over standard HTTP connections

The SSE protocol is a regular HTTP GET request with `Accept: text/event-stream`, and a regular HTTP response with `Content-Type: text/event-stream`. The novelty is that the response body never terminates — the server holds the connection open and writes newline-delimited event blocks as data becomes available. The browser's `EventSource` API parses each event block as it arrives over the `ReadableStream`, dispatching `MessageEvent` objects to JavaScript. There is no second round-trip, no Upgrade header, no protocol switch — what looked like a fetch on the wire becomes a long-lived push channel the moment the response headers arrive.

Because SSE is plain HTTP/1.1, it traverses every layer of infrastructure that was built for HTTP: nginx reverse proxies (with `proxy_buffering off`), AWS Application Load Balancers, Cloudflare, corporate firewalls, OAuth bearer tokens in the `Authorization` header, cookie-based session auth, TLS termination, gzip compression (with care), and HTTP/2 multiplexing (where one SSE stream is just one of many streams on a single TCP connection). WebSocket by contrast requires every intermediate proxy to understand and pass through the `Upgrade: websocket` mechanism — many older corporate proxies do not, which is why SSE sometimes works in restricted networks where WebSocket does not.

```text
Client                                Server
  │                                     │
  │── GET /events HTTP/1.1 ───────────► │
  │   Accept: text/event-stream         │
  │   Last-Event-ID: 42                 │
  │   Authorization: Bearer eyJ...      │
  │                                     │
  │◄── HTTP/1.1 200 OK ─────────────────│
  │    Content-Type: text/event-stream  │
  │    Cache-Control: no-cache          │
  │    Connection: keep-alive           │
  │    Transfer-Encoding: chunked       │
  │    X-Accel-Buffering: no            │
  │                                     │
  │◄── id: 43                          │
  │    data: {"ts":1699...}             │
  │                                     │
  │◄── id: 44                          │
  │    data: {"ts":1699...}             │
  │                                     │
  │   (connection stays open)           │
```

The protocol is strictly one-way. The client cannot send data back over the SSE connection — to send data to the server (typing indicators, presence pings, chat messages), the client must issue a separate HTTP request (`fetch('POST /messages', ...)`). This is fine for stock tickers, dashboards, notification feeds, log tails, and live sports scores — anywhere the data flow is mostly server-to-client. For bidirectional low-latency use cases, the cost of "open a second HTTP request for every client message" is unacceptable; that is what WebSocket solves.

### The `text/event-stream` MIME type

The MIME type `text/event-stream` is registered with IANA and is the protocol's load-bearing contract. When the browser's `EventSource` constructor receives an HTTP response with this `Content-Type`, it switches from "fetch a complete response body" mode to "stream incremental events" mode — internally, it uses the Fetch API's `ReadableStream` reader to consume the body byte by byte as it arrives, parsing event boundaries on the fly. Any other content type causes `EventSource` to fire `onerror` and abort the connection. This is the most common SSE bug: the server returns `application/json` because the events happen to be JSON, and the client silently fails.

The MIME type carries a charset parameter: `text/event-stream; charset=utf-8`. The HTML spec mandates UTF-8 decoding — setting `charset=iso-8859-1` is ignored, and non-UTF-8 bytes in the stream cause the parser to fire an error. The `Cache-Control: no-cache, no-transform` header is critical for two reasons: `no-cache` prevents intermediate caches from serving a stale snapshot of the stream, and `no-transform` tells mobile carrier proxies (Vodafone, T-Mobile, China Mobile) to stop trying to "optimize" the response by injecting JavaScript, compressing images, or rewriting URLs — all of which corrupt an SSE stream irrecoverably.

```http
HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache, no-transform
Connection: keep-alive
X-Accel-Buffering: no
```

The `X-Accel-Buffering: no` header is nginx-specific magic: it tells nginx to disable proxy buffering for this single response, even when `proxy_buffering on` is the global default in `nginx.conf`. Without it, nginx buffers the response body up to `proxy_buffer_size` × `proxy_buffers` (typically 8 × 4 KB = 32 KB or more) before forwarding anything to the client — symptoms are events arriving in 32 KB clumps every 30 seconds instead of one-per-second. AWS ALB has a fixed 60-second idle timeout that cannot be disabled; the SSE server must send a comment frame (`:keepalive\n\n`) every ~25 seconds to defeat it. Cloudflare's free tier has a 100-second timeout and will close idle SSE connections aggressively.

Production failure mode: a developer sets `Content-Type: application/json` because "the events are JSON, so the MIME type should reflect that", deploys to production, and the dashboard shows zero events — `EventSource` fired `onerror` immediately because the content type didn't match the expected `text/event-stream`. The fix is to always send the exact MIME type `text/event-stream`, even when the payload is JSON, XML, plain text, or anything else. The MIME type describes the framing protocol, not the payload.

### Message Framing: `id`, `event`, `data`, and `retry` field definitions

An SSE event is a block of one or more lines, terminated by a blank line (two consecutive `\n` characters, often written `\n\n`). Each line has the shape `field: value` where the space after the colon is optional but conventional. The spec defines four field names:

- **`data:`** — the payload. Multiple `data:` lines in one event are concatenated with `\n` between them, so `data: line1\ndata: line2\n\n` produces `MessageEvent.data === "line1\nline2"`. The data field is opaque UTF-8 text — by convention JSON, but the protocol itself does not care.
- **`event:`** — the event type. Sets `MessageEvent.type`, allowing the client to register type-specific listeners via `addEventListener('userJoined', handler)`. If omitted, the event fires the generic `onmessage` handler.
- **`id:`** — the event ID. Stored by the browser as `lastEventId` and replayed in the `Last-Event-ID` HTTP header on reconnect. This is the resume-from-where-you-left-off mechanism (see the next H3).
- **`retry:`** — the reconnection delay in milliseconds. The browser adopts this as the new default reconnect interval (replacing the previous value). Set this to `5000` to ask the client to wait 5 seconds before reconnecting after a drop.

Lines starting with `:` are comments — ignored by the parser but consumed by the network stack, which is the canonical keepalive trick: send `: ping\n\n` every 25 seconds to defeat intermediary idle timeouts without firing a `MessageEvent`. Lines without a colon are also treated as comments. Lines with a colon but an unknown field name are ignored for forward compatibility (so adding `priority:` in a future spec version doesn't break old parsers).

```text
event: userJoined
id: 42
data: {"user":"alice","room":"lobby"}

event: userLeft
id: 43
data: {"user":"alice"}

retry: 5000
data: this fires the generic onmessage handler

: keepalive comment — does NOT fire an event

data: line 1 of payload
data: line 2 of payload
data: line 3 of payload
```

The blank-line terminator is critical and is the most common SSE bug. An event is only dispatched to JavaScript when the parser sees `\n\n`. If the server writes `data: hello\n` without a trailing blank line, the browser holds the partial event in memory indefinitely and the JavaScript handler never fires. Developers new to SSE spend hours debugging "the server is writing events but the client never sees them" before discovering the missing `\n\n`. Always end every event with two newlines, and always flush the response buffer after writing (Node.js: `res.flushHeaders()` or `res.write(...)` on a non-buffered response; Spring: `SseEmitter.send()` flushes automatically).

### Automatic client-side reconnection, Last-Event-ID tracking, and state resumption

The `EventSource` API does something that the raw `fetch` API cannot: it auto-reconnects. When the underlying TCP connection drops — network blip, server restart, proxy idle timeout, mobile network handoff from WiFi to LTE — `EventSource` waits `retry` milliseconds (default browser-dependent, typically 3 seconds; the server can override this with the `retry:` field) and re-opens the connection. It does this indefinitely — there is no built-in max retry count, no exponential backoff, no jitter. On reconnect, the browser automatically includes the `Last-Event-ID` request header containing the most recent `id:` value it received, so the server can resume the stream from that point forward.

This is the protocol's killer feature versus WebSocket. With WebSocket, a dropped connection is a state-loss event: the client must reconnect, re-authenticate, re-subscribe to its topics, and ask the server "what did I miss?" via an application-level protocol. With SSE, the client just reconnects and the server uses the `Last-Event-ID` header to pick up where it left off — if the server is implemented to honor that header.

```javascript
const es = new EventSource("/events");

es.addEventListener("userJoined", (e) => {
  const data = JSON.parse(e.data);
  console.log("last event id:", e.lastEventId);
  // e.lastEventId is also available on the EventSource instance
});

es.onerror = (e) => {
  // EventSource will auto-reconnect; you do nothing.
  // readyState tells you what's happening:
  //   0 = CONNECTING (initial connection or reconnecting)
  //   1 = OPEN
  //   2 = CLOSED (only if .close() was called explicitly)
  console.log("readyState:", es.readyState);
};
```

Server-side resume implementation: maintain a per-stream monotonic sequence counter (never reused, never reset on restart). On every event, write `id: <seq>\n` before the `data:` line. On connection, read the `Last-Event-ID` header (Express: `req.headers['last-event-id']`, Spring: `request.getHeader("Last-Event-ID")`, Flask: `request.headers.get('Last-Event-ID')`). If present, look up events with `id > lastEventId` from your event log — Redis Stream `XRANGE`, Kafka offset seek, Postgres `SELECT ... WHERE id > $1`, or an in-memory ring buffer — and replay them as a burst before attaching the client to the live stream. If your events are short-lived (e.g., real-time stock ticks where only the latest price matters), you can skip the replay and just send the latest snapshot.

Failure mode: a server that does not honor `Last-Event-ID` produces one of two production bugs. (1) **Duplicate events** after every reconnect — the server starts the stream from "now" without knowing what the client already saw, so any event that was in-flight when the connection dropped is delivered twice. (2) **Missed events** — events produced during the disconnect window (which could be seconds or minutes) are never delivered. The fix is always one of: implement the replay log, make events idempotent so duplicates are safe (e.g., `{"type":"state","value":42}` where the latest state supersedes all earlier ones), or document the gap and let the client reconcile by fetching the full current state on reconnect.

### Browser native support (`EventSource` API) and proxy buffering hazards

The `EventSource` constructor is part of the HTML Living Standard and ships in every modern browser (Chrome, Firefox, Safari, Edge — even back to IE 11 via polyfills like `event-source-polyfill`). It is dramatically simpler than the WebSocket API because the protocol is plain HTTP: no handshake state machine, no binary frame parser, no masking, no opcode handling. The constructor takes a URL and an optional `{ withCredentials: true }` for cross-origin requests that need cookies. Cross-origin SSE requires the server to send the `Access-Control-Allow-Origin` header (the standard CORS dance).

The catch is proxy buffering. HTTP/1.1's spec allows intermediaries to buffer response bodies, and many do so by default — for performance, for compression, or simply because the proxy assumes the response is a complete document. Symptoms in production: events arrive in clumps of 5–10 every 30 seconds instead of one-per-second; the first event takes 60 seconds to arrive even though the server sent it immediately; the connection drops cleanly every 60 seconds (AWS ALB idle timeout) or 100 seconds (Cloudflare); mobile carrier proxies inject HTML or JavaScript into the stream and corrupt it.

```nginx
# nginx reverse proxy in front of an SSE backend
location /events {
    proxy_pass http://backend;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_buffering off;              # critical for SSE
    proxy_cache off;
    proxy_read_timeout 3600s;         # don't kill the connection
    chunked_transfer_encoding on;
    add_header X-Accel-Buffering no;  # backend can opt out per-response
}
```

```text
Buffering layer        What it does                              Fix
─────────────────────────────────────────────────────────────────────────────
nginx proxy_buffering  Buffers entire response in RAM            proxy_buffering off
AWS ALB idle timeout   Kills connection after 60s of no data     Send :keepalive every 25s
Cloudflare             100s timeout, aggressive buffering        Use "Cache: bypass" rule
gzip compression       Compresses, buffers the whole window      Set Content-Encoding: identity
Mobile carrier proxy   HTML/JS injection, 5min timeout           Use HTTPS (encrypted = invisible)
HTTP/1.1 conn limit    6 concurrent per origin                   Upgrade to HTTP/2 (multiplexed)
```

The 6-connection browser limit over HTTP/1.1 (RFC 2616 §8.1.4 originally said 2; modern browsers raised to 6) is a real ceiling: if you open six SSE streams to one origin, the seventh fetch to the same origin blocks until one of them closes. This is invisible in development (one tab, one stream) and brutal in production (operators with six monitoring dashboards open). HTTP/2 lifts the limit because a single TCP connection multiplexes unlimited streams — so enabling HTTP/2 on your CDN or load balancer often fixes SSE scaling issues "for free". SSE works on HTTP/1.1, HTTP/2, and HTTP/3 over QUIC; unlike WebSocket, it has no special connection negotiation.

Production failure mode: a developer sets up SSE locally, sees it working perfectly (localhost has no proxies, no ALB, no Cloudflare, no mobile carrier), deploys to production behind nginx, and the dashboard "updates every 30 seconds in clumps of ten events". The fix is `proxy_buffering off` (or the per-response `X-Accel-Buffering: no` header) plus a 25-second keepalive comment to defeat intermediary idle timeouts. The lesson: always test SSE through the real production proxy stack, never just against localhost.

## How This Connects to the Frameworks

Every framework in section 05 exposes an SSE helper that handles the wire format and the per-connection state. In Spring WebMvc, `SseEmitter` is the API — you return a `SseEmitter` from your controller method, the servlet container parks the request, and you call `sseEmitter.send(SseEmitter.event().id("42").name("userJoined").data(payload))` from any thread. In Spring WebFlux, the return type is `Flux<ServerSentEvent<UserUpdate>>` and Reactor handles backpressure. In Express (Node.js), you set the headers manually (`res.setHeader('Content-Type', 'text/event-stream')`, `res.setHeader('Cache-Control', 'no-cache')`, `res.setHeader('Connection', 'keep-alive')`, `res.flushHeaders()`) and write events with `res.write('data: ' + JSON.stringify(payload) + '\n\n')`. In Flask, `Response(generate(), mimetype='text/event-stream')` with a generator function is the idiom. In Django, the same pattern via `StreamingHttpResponse` with `content_type='text/event-stream'`. In Laravel, `response()->stream(function () { ... }, 200, ['Content-Type' => 'text/event-stream'])`. The shape is identical: set the MIME type, disable buffering, write `field: value\n` lines, terminate each event with `\n\n`, flush after every write.

```bash
# 1. Inspect a real SSE connection with curl --no-buffer
curl -N -i https://stream.example.com/events
# You should see:
#   HTTP/1.1 200 OK
#   Content-Type: text/event-stream
#   Cache-Control: no-cache
#   X-Accel-Buffering: no
#   <blank line>
#   id: 1
#   data: ...
#   <blank line>
#   id: 2
#   data: ...

# 2. Send a Last-Event-ID header to test reconnect
curl -N -i -H "Last-Event-ID: 41" https://stream.example.com/events
# Server should replay events 42, 43, 44, ... then live events.

# 3. Reproduce the proxy buffering bug locally
#    Run an SSE server with implicit flushing disabled, put nginx in front:
nginx -c nginx.conf  # with proxy_buffering on (default)
#    Observe: events arrive in 32KB clumps every ~30s

# 4. Test the 6-connection HTTP/1.1 browser limit
#    Open six tabs each running: new EventSource('/events')
#    The seventh fetch() to the same origin blocks.

# 5. Test HTTP/2 multiplexing lifting the limit
curl -v --http2 https://stream.example.com/events
#    With HTTP/2, the 6-connection limit disappears (one TCP conn, many streams).

# 6. Capture SSE wire bytes with tcpdump
sudo tcpdump -i lo -A 'tcp port 8080' | grep -E '^(id|data|event|retry|:)'

# 7. Test reconnect after server restart
#    Client: const es = new EventSource('/events');
#    Server: kill -9 <pid>; restart
#    Observe: es.readyState goes 1 → 0 → 1 (auto-reconnect)
#    Observe: Last-Event-ID header on the new request

# 8. Test the no-Cache-Control-transform header
#    (Mobile network simulation — disable WiFi, use cellular)
#    Without no-transform: carrier may inject HTML, breaking the stream.
```
