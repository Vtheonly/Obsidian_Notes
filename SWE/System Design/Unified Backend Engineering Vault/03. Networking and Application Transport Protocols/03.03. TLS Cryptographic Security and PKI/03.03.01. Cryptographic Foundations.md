# 03.03.01. Cryptographic Foundations

## What This Is

Every byte you send over the public internet is observable by every router, switch, and ISP between you and the destination. Without cryptography, anyone on the path can read your passwords, modify your responses, or impersonate your server. TLS (Transport Layer Security) is the protocol that prevents this, and it rests on three foundational cryptographic primitives: symmetric encryption (for bulk data confidentiality), asymmetric encryption (for key exchange and authentication), and hash functions (for integrity and authentication). Understanding which primitive solves which problem is the foundation for everything in section 03.03 — the TLS handshake, certificate chains, and mTLS all compose these primitives.

This note covers the primitives themselves at the level a backend engineer needs: what AES-GCM is and why it is the default cipher, what ChaCha20-Poly1305 buys you on mobile, what RSA and ECDSA and Ed25519 actually do, what SHA-256 versus HMAC versus PBKDF2 means, and why "encryption" and "authentication" are separate concerns that must both be addressed.

## The Details

### Symmetric Cryptography (AES-GCM, ChaCha20-Poly1305): Performance, speed, and shared key encryption

Symmetric encryption uses the **same key** for encryption and decryption. Both endpoints must already share the key — which is the hard part, solved by the asymmetric handshake (covered in the next H3). Once both sides have the key, symmetric encryption is fast: modern CPUs with AES-NI instructions encrypt and decrypt AES-GCM at 1–5 GB/s per core, fast enough that the cipher is essentially never the bottleneck.

The two symmetric ciphers used in TLS 1.3 are:

**AES-GCM** (Advanced Encryption Standard in Galois/Counter Mode). AES is the block cipher (RFC 19, FIPS 197, 2001); GCM is the mode of operation that turns AES into an Authenticated Encryption with Associated Data (AEAD) cipher. AES operates on 128-bit blocks; GCM turns it into a stream cipher by encrypting a counter (0, 1, 2, 3, ...) and XORing the keystream with the plaintext. GCM also produces a 128-bit authentication tag (the "GMAC") that allows the receiver to verify the ciphertext was not modified. The combination of encryption + authentication in one operation is what makes AES-GCM an AEAD cipher — you cannot have one without the other.

```text
AES-GCM encryption:
  Inputs:
    - 256-bit key K (the session key, negotiated during TLS handshake)
    - 96-bit nonce N (unique per record; in TLS 1.3, derived from the record sequence number)
    - plaintext P (the HTTP request/response bytes)
    - associated data A (the TLS record header — authenticated but not encrypted)

  Output:
    - ciphertext C (same length as P)
    - 128-bit authentication tag T

  Encryption:
    Keystream = AES_K(N || counter)  for counter = 0, 1, 2, ...
    C = P XOR Keystream
    T = GHASH(A, C) XOR AES_K(N || 0)

  Decryption:
    Recompute T' from A and C, compare with received T (constant-time comparison!)
    If T == T': decrypt C to recover P
    If T != T': REJECT the entire record (do not release any plaintext — this is critical)
```

**ChaCha20-Poly1305**. ChaCha20 is a stream cipher designed by Daniel Bernstein (RFC 7539); Poly1305 is a MAC designed by the same author. Combined, they form an AEAD cipher that does not require hardware acceleration to be fast — ChaCha20's design is optimized for software implementation and runs at ~1 GB/s on a generic CPU. This makes ChaCha20-Poly1305 the preferred cipher on mobile devices and older CPUs without AES-NI: ARM Cortex-A53 (Raspberry Pi 3) runs ChaCha20 at 700 MB/s but AES-GCM at only 200 MB/s without hardware AES.

```bash
# Check whether your CPU has AES-NI instructions
grep -o aes /proc/cpuinfo | head -1
# If "aes" is printed, you have AES-NI and AES-GCM will be fast.
# If empty, prefer ChaCha20-Poly1305.

# Check the symmetric ciphers your OpenSSL supports
openssl ciphers -v 'TLS 1.3' | head
# Typical output: TLS_AES_256_GCM_SHA384, TLS_CHACHA20_POLY1305_SHA256, TLS_AES_128_GCM_SHA256

# Benchmark AES-GCM vs ChaCha20-Poly1305 on your CPU
openssl speed -evp aes-256-gcm
openssl speed -evp chacha20-poly1305
```

The cipher names you see in TLS 1.3 configurations (`TLS_AES_256_GCM_SHA384`, `TLS_CHACHA20_POLY1305_SHA256`, `TLS_AES_128_GCM_SHA256`) follow a strict naming convention: `TLS_` + cipher name + `_` + hash function used for the handshake's PRF. The cipher does the encryption; the hash function (SHA-384 or SHA-256) is used separately for the key derivation. You cannot mix and match — the cipher suite is a fixed bundle.

The production failure mode tied to symmetric encryption is **the cipher that is slow because of missing hardware acceleration**. Your mobile users see 5× higher CPU usage on HTTPS requests than your desktop users. The cause is AES-GCM on a CPU without AES-NI (common on low-end Android devices and IoT hardware). The fix is to put `TLS_CHACHA20_POLY1305_SHA256` first in the server's cipher preference list, so the server picks ChaCha20 when the client supports it. Cloudflare and Google do exactly this — ChaCha20-Poly1305 is the most-used cipher on mobile traffic because they explicitly prefer it.

### Asymmetric Cryptography (RSA, ECC - Elliptic Curve Cryptography, ECDSA, Ed25519): Key pairs and digital signatures

Asymmetric cryptography uses a **key pair**: a public key (which can be freely shared) and a private key (which must be kept secret). Data encrypted with the public key can only be decrypted with the private key; data signed with the private key can be verified by anyone with the public key. This solves the key-distribution problem that symmetric cryptography cannot — you can publish your public key in a certificate, and anyone can encrypt to you or verify your signatures without ever sharing a secret.

Asymmetric cryptography is far slower than symmetric: RSA-2048 operations are about 1000× slower than AES-256. For this reason, asymmetric cryptography is used *only* during the handshake (to authenticate the server and negotiate a symmetric session key), and symmetric cryptography is used for all bulk data transfer. A typical TLS session does ~5 asymmetric operations in the handshake and then millions of symmetric operations for the data.

The three asymmetric algorithms you will encounter in modern TLS:

**RSA** (Rivest–Shamir–Adleman, 1977). The original public-key algorithm. Security rests on the difficulty of factoring large integers. RSA key sizes: 2048 bits (the current minimum, equivalent to ~112 bits of symmetric security), 3072 bits (~128 bits), 4096 bits (~150 bits). RSA can be used for both encryption (encrypt with public key, decrypt with private key) and signatures (sign with private key, verify with public key). RSA key exchange — where the client encrypts a shared secret with the server's public key — was removed in TLS 1.3 because it does not provide forward secrecy (covered in [[03.03.03. The TLS 1.3 Handshake Protocol]]).

**ECDSA** (Elliptic Curve Digital Signature Algorithm, FIPS 186-4). Uses elliptic curve cryptography to provide the same security as RSA at much smaller key sizes. An ECDSA P-256 key (256 bits) provides ~128 bits of security, equivalent to a 3072-bit RSA key. The smaller key size means faster operations (ECDSA signing is ~5× faster than RSA-2048 signing) and smaller certificates (~256 bytes vs ~2048 bytes for the public key). The downside: ECDSA signatures are non-deterministic (they require a high-quality random number generator per signature; a broken RNG can leak the private key, as happened to Sony's PlayStation 3 in 2010 — the fail0verflow team recovered the private key because Sony reused the RNG nonce across signatures).

**Ed25519** (Edwards-curve Digital Signature Algorithm on Curve25519, RFC 8032). A newer signature scheme designed by Daniel Bernstein, Niels Duif, Tanja Lange, Peter Schwabe, and Bo-Yin Yang. Ed25519 keys are 256 bits, signatures are 512 bits, and signing is deterministic (no RNG dependency — the signature is a function of the private key and the message only, eliminating the Sony PS3 vulnerability class). Ed25519 is faster than ECDSA P-256 (signing ~3× faster, verifying ~2× faster) and is the signature algorithm of choice for SSH keys (`ssh-keygen -t ed25519`), age encryption, and Signal's XEdDSA. It is supported in TLS 1.3 but adoption is still ramping — most production TLS still uses ECDSA P-256 or RSA-2048 for compatibility with older clients.

```bash
# Generate an RSA-2048 private key (legacy, but universally compatible)
openssl genrsa -out rsa-2048.key 2048

# Generate an ECDSA P-256 private key (smaller, faster, equivalent security)
openssl ecparam -name prime256v1 -genkey -noout -out ecdsa-p256.key

# Generate an Ed25519 private key (smallest, fastest, most modern)
openssl genpkey -algorithm Ed25519 -out ed25519.key

# Compare key sizes
wc -c rsa-2048.key ecdsa-p256.key ed25519.key
# rsa-2048.key:    1675 bytes
# ecdsa-p256.key:   241 bytes
# ed25519.key:      119 bytes

# Compare signing speed
openssl speed rsa2048
openssl speed ecdsap256
# (Ed25519 not benchmarkable via openssl speed in older versions; use libsodium's tests)

# For SSH keys, prefer Ed25519 (since OpenSSH 6.5, 2014)
ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519
```

The production failure mode tied to asymmetric cryptography is **the compromised RSA key**. If your server's RSA private key is leaked (through a misconfigured `.gitignore`, a debug log, a backup tape), every TLS session ever recorded with that key can be retroactively decrypted by anyone with the recording and the key — there is no forward secrecy. The fix is to use TLS 1.3 (which mandates ECDHE for forward secrecy — covered in [[03.03.03. The TLS 1.3 Handshake Protocol]]) and to rotate keys frequently (every 90 days, automated via ACME / cert-manager). The production incident this prevents is "Heartbleed 2.0" — a memory-disclosure vulnerability in OpenSSL or a similar library that leaks the private key, after which an attacker can decrypt all captured traffic retroactively.

### Cryptographic Hash Functions: SHA-256, SHA-3, and Keyed-Hash Message Authentication Codes (HMAC)

A **cryptographic hash function** takes an arbitrary-length input and produces a fixed-length output (the "digest" or "hash") with three properties: (1) pre-image resistance (you cannot find an input that hashes to a given output), (2) second pre-image resistance (you cannot find a different input that hashes to the same output as a given input), (3) collision resistance (you cannot find any two inputs that hash to the same output). Hash functions are one-way — you cannot recover the input from the output.

```text
Hash function families:

SHA-2 family (NIST, FIPS 180-4, 2001):
  - SHA-256: 32-byte digest, ~400 MB/s on modern CPU. Default for TLS 1.3.
  - SHA-384: 48-byte digest, ~300 MB/s. Used in TLS_AES_256_GCM_SHA384.
  - SHA-512: 64-byte digest, ~400 MB/s. Used in some signature algorithms.

SHA-3 family (NIST, FIPS 202, 2015, Keccak):
  - SHA3-256, SHA3-512: same digest sizes as SHA-2, different algorithm.
  - Used as a fallback in case SHA-2 is broken (no known breaks as of 2024).
  - Rarely used in TLS (SHA-2 is still the default).

BLAKE2 / BLAKE3 (community, RFC 7693, 2015 / 2020):
  - BLAKE3: ~6 GB/s on a single core (parallelizable, much faster than SHA-2/3).
  - Used in modern file systems (ZFS, Btrfs) and content-addressable storage (IPFS).

MD5 (Rivest, RFC 1321, 1992) — BROKEN:
  - Collisions found in 2004 (Wang et al.). DO NOT USE for security.
  - Still used for non-security checksums (file integrity, ETag in HTTP).

SHA-1 (NIST, 1995) — BROKEN:
  - SHAttered collision published 2017 (Google + CWI). DO NOT USE.
  - Removed from TLS 1.3. Browsers reject SHA-1 certificates.
```

A **MAC** (Message Authentication Code) is a keyed hash: a hash function that takes both the message and a secret key, producing a tag that proves the message was not modified and was sent by someone who knows the key. **HMAC** (Hash-based MAC, RFC 2104) is the standard construction: `HMAC(K, m) = H((K ⊕ opad) || H((K ⊕ ipad) || m))` where `K` is the key, `m` is the message, `H` is a cryptographic hash, and `opad`/`ipad` are fixed padding constants. HMAC-SHA-256 is the default MAC in TLS 1.3's record layer (actually, AES-GCM's built-in GMAC serves this role, but HMAC-SHA-256 is used elsewhere in the protocol for transcript hashing).

```text
Hash vs HMAC vs Digital Signature:

Hash         H(message)              → integrity (anyone can compute it, no key needed)
HMAC         HMAC(K, message)        → integrity + authenticity (requires shared key K)
Signature    Sign(sk, message)       → integrity + authenticity + non-repudiation (requires private key sk)

Use cases:
  Hash       - File checksums, content addressing (git SHA-1 of commits, Docker image digests)
             - TLS transcript hash (input to the Finished message)
  HMAC       - TLS record layer MAC (when not using AEAD)
             - JWT signing (HMAC-SHA-256 with HS256 algorithm)
             - AWS SigV4 request signing
  Signature  - TLS certificate signing (CA signs the leaf cert with its private key)
             - TLS handshake's CertificateVerify message (server proves it has the private key)
             - Git commit signing (GPG / SSH signatures)
```

```bash
# Compute SHA-256 of a file
sha256sum file.txt
# 9e107d9d372bb6826bd81d3542a419d6...  file.txt

# Compute HMAC-SHA-256 of a message with a key
echo -n "message" | openssl dgst -sha256 -hmac "secret-key"
# HMAC-SHA256(message)= 82554f1d...

# Sign a message with an RSA private key
echo -n "message" | openssl dgst -sha256 -sign rsa-2048.key > signature.bin

# Verify a signature with the public key
openssl dgst -sha256 -verify <(openssl rsa -in rsa-2048.key -pubout) -signature signature.bin <(echo -n "message")
# Verified OK

# Test JWT signing (HMAC-SHA-256, the HS256 algorithm)
echo -n '{"alg":"HS256","typ":"JWT"}' | base64 | tr -d '=' | tr '/+' '_-'
# eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9
```

The production failure mode tied to hash functions is **MD5 in security contexts**. Some legacy systems still use MD5 for password hashing, session tokens, or file integrity checking — all of which are broken because MD5 collisions can be computed in seconds on a modern GPU. The famous 2008 attack: researchers created a rogue CA certificate by exploiting MD5 collisions in the certificate's "serial number + validity period" fields — they could have impersonated any HTTPS site on the internet. The fix is to use SHA-256 (or better) for any security-relevant hash; MD5 may be retained only for non-security checksums (e.g., HTTP `ETag` for cache validation, where a collision is just a cache miss).

Closely related to hash functions are **password hashing and key derivation functions (KDFs)**, which convert a human-typed password (low entropy, possibly dictionary-attackable) into a fixed-length key suitable for symmetric encryption or for storage in an authentication database. SHA-256 alone is *too fast* for this — an attacker with a GPU can compute 10 billion SHA-256 hashes per second, brute-forcing any 8-character password in hours. The KDFs exist to be deliberately *slow* and *memory-hard*: PBKDF2 (RFC 2898, OWASP minimum 600,000 iterations of HMAC-SHA-256 as of 2023), scrypt (2009, requires both CPU and configurable memory, typically 64 MB), and Argon2id (2015 Password Hashing Competition winner, OWASP's recommended default — resistant to GPU/ASIC/side-channel attacks with typical settings of 64 MB memory, 3 iterations, 4 threads). The memory-hardness is the key defense: each hash requires 64 MB of RAM, so an attacker cannot parallelize across thousands of GPU cores because each one needs its own 64 MB. The trade-off: legitimate login takes 100ms (acceptable); brute-force attack takes 100ms × candidate count (prohibitive).

This same primitive backs every password-storage system in section 06's persistence notes (Spring Security's `PasswordEncoder`, Django's `make_password`, Laravel's `Hash::make` all use BCrypt, Argon2id, or PBKDF2 under the hood). It also appears in TLS when a pre-shared key (PSK) is derived from a password, though PSK-from-password is rare in production TLS (more common in IPsec and WPA2).

## How This Connects to the Frameworks

Every framework in section 05 inherits its cryptographic primitives from the runtime, not from the framework code itself:

- **Spring Boot**: uses the JVM's `javax.crypto` and `java.security` packages, which delegate to the JCE provider (typically Bouncy Castle or the JDK's built-in provider). TLS is handled by the JDK's `SSLSocket` / `SSLEngine`, which uses OpenSSL via the `conscrypt` or `jetty-alpn` providers.
- **Express/Node.js**: uses OpenSSL via `crypto` and `tls` modules. Node is compiled against a specific OpenSSL version; you must rebuild Node to upgrade OpenSSL.
- **Python**: uses OpenSSL via the `ssl` module (CPython) or `cryptography` (third-party). `hashlib` provides SHA-256; `hmac` provides HMAC; `ssl` provides TLS.
- **PHP/Laravel**: uses OpenSSL via the `openssl` extension. `password_hash()` uses bcrypt by default, with Argon2id available since PHP 7.3.

The framework's job is to expose the right configuration knobs (cipher preference list, key sizes, certificate paths) and to apply them consistently. If the framework misconfigures TLS — prefers a weak cipher, uses a too-short RSA key, accepts an expired certificate — the failure surfaces as a browser warning ("Your connection is not private"), a failed API call, or a security vulnerability. Knowing which primitive is at the root of each failure is the difference between a 5-minute fix and a 5-hour incident.

## Hands-On Exercise

```bash
# Check your CPU's AES-NI support (determines whether AES-GCM or ChaCha20 will be faster)
grep -o aes /proc/cpuinfo | head -1
grep -o sse4_2 /proc/cpuinfo | head -1   # required for fast software AES

# List the TLS 1.3 cipher suites your OpenSSL supports
openssl ciphers -v 'TLS 1.3'

# Benchmark AES-GCM vs ChaCha20-Poly1305 on your CPU
openssl speed -evp aes-256-gcm
openssl speed -evp chacha20-poly1305
openssl speed -evp aes-128-gcm

# Generate and compare key sizes across RSA, ECDSA, Ed25519
openssl genrsa -out rsa-2048.key 2048
openssl ecparam -name prime256v1 -genkey -noout -out ecdsa-p256.key
openssl genpkey -algorithm Ed25519 -out ed25519.key
wc -c rsa-2048.key ecdsa-p256.key ed25519.key

# Compute hashes
echo -n "message" | sha256sum
echo -n "message" | openssl dgst -sha3-256

# Compute HMAC-SHA-256
echo -n "message" | openssl dgst -sha256 -hmac "secret-key"

# Inspect which cipher your HTTPS connection actually used
openssl s_client -connect example.com:443 -servername example.com < /dev/null 2>&1 | grep -i 'cipher\|protocol'
# Expect: Protocol: TLSv1.3, Cipher: TLS_AES_256_GCM_SHA384
```
