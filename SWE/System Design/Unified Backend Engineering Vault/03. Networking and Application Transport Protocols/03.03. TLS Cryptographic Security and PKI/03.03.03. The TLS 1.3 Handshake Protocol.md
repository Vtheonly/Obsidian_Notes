# 03.03.03. The TLS 1.3 Handshake Protocol

## What This Is

TLS 1.3 (RFC 8446, August 2018) is the version of TLS that every modern HTTPS connection should be using. It is the result of a 4-year redesign that threw out everything in TLS 1.2 that was slow, weak, or buggy, and rebuilt the handshake from scratch. The headline improvements: the handshake completes in **1 round trip** (down from 2 in TLS 1.2), with an option for **0-RTT** early data on resumption; **forward secrecy is mandatory** (RSA key exchange was removed); the cipher suite list was pruned from ~30 to just 5 (all AEAD); compression was removed (the CRIME attack); renegotiation was removed (the Triple Handshake attack); and the entire handshake after the `ServerHello` is encrypted, hiding the certificate from passive eavesdroppers.

This note covers the 1-RTT handshake flow, the ECDHE key exchange that provides forward secrecy, what TLS 1.3 removed and why, and the downgrade protection mechanism that prevents attackers from forcing connections back to TLS 1.2.

## The Details

### The 1-RTT Handshake sequence: `ClientHello` (with Key Shares and Supported Ciphers) → `ServerHello` (with Server Key Share, Certificate, and Finished) → Encrypted Data flow

The TLS 1.3 handshake completes in one round trip — the client sends `ClientHello`, the server responds with `ServerHello` + `EncryptedExtensions` + `Certificate` + `CertificateVerify` + `Finished`, the client sends `Finished`, and application data can flow. Compared to TLS 1.2's 2-RTT handshake (ClientHello → ServerHello+Cert+ServerKeyExchange+ServerHelloDone → ClientKeyExchange+ChangeCipherSpec+Finished → ChangeCipherSpec+Finished), this is a 2× latency reduction.

```text
TLS 1.3 handshake (1-RTT):

Client                                         Server
  │                                              │
  │ ── ClientHello ────────────────────────────► │
  │    Extensions:                               │
  │      supported_versions: TLS 1.3             │
  │      key_share: X25519 public key            │  (ECDHE half-key, computed up-front)
  │      supported_groups: x25519, secp256r1     │
  │      signature_algorithms: ecdsa_secp256r1_sha256,
  │                            rsa_pss_rsae_sha256
  │      server_name: api.example.com (SNI)      │
  │      pre_shared_key: <ticket> (if resuming)  │
  │      early_data: <0-RTT data> (optional)     │
  │                                              │
  │ ◄── ServerHello ─────────────────────────── │
  │      supported_versions: TLS 1.3             │
  │      key_share: X25519 public key            │  (ECDHE half-key)
  │      pre_shared_key: <selected ticket>       │  (if resuming)
  │                                              │  ↓ from here on, EVERYTHING is encrypted
  │ ◄── {EncryptedExtensions} ───────────────── │  (server_name ack, ALPN result, etc.)
  │ ◄── {Certificate} ───────────────────────── │  (server's leaf cert + chain)
  │ ◄── {CertificateVerify} ─────────────────── │  (signature over handshake transcript,
  │                                              │   proving the server holds the cert's private key)
  │ ◄── {Finished} ──────────────────────────── │  (HMAC over the transcript, proving
  │                                              │   the server has the right handshake keys)
  │                                              │
  │ ── {Finished} ──────────────────────────────► │  (client's HMAC over the transcript)
  │                                              │
  │ ◄═══════ encrypted application data ═══════► │  (HTTP request/response, fully encrypted)
```

The crucial trick that enables 1-RTT: the client sends its **key share** (an X25519 public key) in the very first `ClientHello` message. The server can compute the shared ECDHE secret immediately upon receiving the `ClientHello`, derive the handshake encryption keys, and encrypt everything it sends back starting from `EncryptedExtensions`. This is why the certificate is encrypted on the wire — a passive eavesdropper sees the IP addresses, the SNI (server name, in plaintext until ECH is deployed), and the timing, but cannot see the certificate or anything that follows.

By contrast, in TLS 1.2 the client sent its key share (`ClientKeyExchange`) only in the *third* flight (after receiving the server's certificate), so the server's certificate was sent in plaintext. This let passive eavesdroppers and censorship devices see exactly which site you were connecting to — a privacy loss that TLS 1.3 fixes.

```bash
# Inspect a real TLS 1.3 handshake
openssl s_client -connect example.com:443 -servername example.com < /dev/null 2>&1 | head -30
# Look for:
#   SSL-Session: Protocol: TLSv1.3
#   Cipher: TLS_AES_256_GCM_SHA384

# Verify the handshake is 1-RTT by counting round trips
openssl s_client -connect example.com:443 -servername example.com -tls1_3 -msg < /dev/null 2>&1 | \
  grep -E 'ClientHello|ServerHello|Certificate|Finished'
# Expect to see:
#   >>> TLS 1.3 ... ClientHello
#   <<< TLS 1.3 ... ServerHello
#   <<< TLS 1.3 ... EncryptedExtensions
#   <<< TLS 1.3 ... Certificate
#   <<< TLS 1.3 ... CertificateVerify
#   <<< TLS 1.3 ... Finished
#   >>> TLS 1.3 ... Finished
# (one client flight, one server flight, then data — that's 1 RTT)

# Time the handshake
curl -w "tls_handshake=%{time_appconnect}\n" -o /dev/null -s https://example.com/
```

The production failure mode tied to the 1-RTT handshake is **the misconfigured client that still does 2-RTT**. Some older client libraries (Java 8 before 8u262, Python before 3.7 with old OpenSSL, certain IoT stacks) do not support TLS 1.3 and fall back to TLS 1.2, paying the extra round trip. The fix is to upgrade the client to a TLS 1.3-capable version. The recurring symptom is "API calls from our legacy Java service are 100ms slower than from our new Node service" — and the difference is the TLS handshake RTT, not the application logic.

### Ephemeral Diffie-Hellman Key Exchange (ECDHE): Mathematical mechanics and achieving Perfect Forward Secrecy (PFS)

The cryptographic core of the TLS 1.3 handshake is **Ephemeral Elliptic Curve Diffie-Hellman** (ECDHE), which provides **Perfect Forward Secrecy** (PFS): even if the server's long-term private key is compromised in the future, all past sessions recorded before the compromise remain confidential. This is the property that TLS 1.2 with RSA key exchange did *not* have, and it is the reason TLS 1.3 removed RSA key exchange.

The Diffie-Hellman key exchange works as follows (using the elliptic curve variant, X25519, as the example):

```text
Diffie-Hellman over Curve25519:

  Setup (publicly agreed):
    - Curve: Curve25519 (the curve y² = x³ + 486662x² + x over the field GF(2²⁵⁵ - 19))
    - Generator point: G = 9 (the standard base point, fixed by the curve definition)

  Client (ephemeral):
    - Picks a random secret integer a (32 bytes)
    - Computes public value A = a * G (a point on the curve, 32 bytes)
    - Sends A to the server in the ClientHello key_share extension

  Server (ephemeral):
    - Picks a random secret integer b (32 bytes)
    - Computes public value B = b * G
    - Sends B to the client in the ServerHello key_share extension
    - Computes shared secret S = b * A = b * (a * G) = (a * b) * G

  Client:
    - Computes shared secret S = a * B = a * (b * G) = (a * b) * G

  Both sides now have the same S, which no eavesdropper can compute:
    - Eavesdropper sees A and B but cannot recover a or b (this is the
      elliptic curve discrete logarithm problem — assumed hard).
    - Eavesdropper cannot compute S = (a * b) * G without knowing a or b.

  The handshake traffic keys are derived from S via HKDF:
    secret = HKDF-Extract(0, S)
    key = HKDF-Expand-Label(secret, "key", "", 32)
    iv  = HKDF-Expand-Label(secret, "iv",  "", 12)
```

The "**ephemeral**" part of ECDHE is what provides forward secrecy: the secrets `a` and `b` are generated fresh for each TLS session, used only for that session, and discarded after the session ends. They are never stored on disk and never reused. An attacker who records all encrypted traffic and then later compromises the server's long-term private key (the one in the certificate) cannot decrypt the recorded traffic, because the long-term private key was used only to *sign* the handshake (proving the server's identity), not to encrypt the data — the data was encrypted with keys derived from the ephemeral `a` and `b`, which have been destroyed.

```text
Why this is "Perfect Forward Secrecy":

  Recorded traffic: ClientHello (with A) + ServerHello (with B) + ciphertext
  Later compromise: server's long-term private key (in cert.pem) is leaked

  Can the attacker decrypt the recorded traffic?
  - They have A and B (from the recorded handshake).
  - They need S = a * b * G to derive the encryption keys.
  - To compute S, they need a or b.
  - a and b were ephemeral — generated per-session, used once, then discarded.
  - The long-term private key (now compromised) was used ONLY to sign the
    CertificateVerify message — it was never used to compute S.
  - Therefore: the attacker CANNOT decrypt the recorded traffic. Forward secrecy holds.

Compare to TLS 1.2 with RSA key exchange (removed in TLS 1.3):
  - Client encrypts the shared secret with the server's public key.
  - Server decrypts it with its private key.
  - If the private key is later leaked, all recorded traffic can be decrypted.
  - This is NOT forward secret — it is the design TLS 1.3 fixed.
```

TLS 1.3 supports three ECDHE groups: **X25519** (the default and recommended; designed by Daniel Bernstein, fast and constant-time in software), **P-256** (the NIST standard, ubiquitous but slower than X25519 in software and historically tied to potential NSA influence), and **P-384** (the higher-security NIST curve, used in some compliance-driven deployments). The client lists the groups it supports in `supported_groups`; the server picks one.

```bash
# Check which ECDHE group was used in your TLS 1.3 connection
openssl s_client -connect example.com:443 -servername example.com -tls1_3 < /dev/null 2>&1 | grep -i 'peer\|curve\|group'
# Typical: "Peer signing type: ... " or "Server Temp Key: X25519, 253 bits"

# Force a specific ECDHE group
openssl s_client -connect example.com:443 -servername example.com -groups X25519 < /dev/null
```

The production failure mode tied to ECDHE is the **incorrectly-deployed RSA cert with no forward secrecy fallback**. If a server runs TLS 1.2 with RSA-only cipher suites (no ECDHE), every recorded session is decryptable if the RSA private key is ever compromised. This was the design that made the Heartbleed vulnerability (CVE-2014-0160, April 2014) so terrifying — an attacker could read the server's memory and steal the RSA private key, then retroactively decrypt all recorded traffic. The fix in TLS 1.3 is structural: RSA key exchange is *removed*, so even an identical Heartbleed-class bug in a TLS 1.3 server cannot decrypt recorded traffic (it can still leak the session keys of *active* sessions, but those are limited).

### Deprecated mechanisms in TLS 1.3: Elimination of RSA key exchange, weak ciphers, and compression vulnerabilities (CRIME)

TLS 1.3 removed a long list of features that were either insecure, slow, or had attack surface. The removals are what make TLS 1.3 both faster (fewer round trips, no compression) and more secure (no weak primitives) than TLS 1.2.

```text
Removed in TLS 1.3 (and why):

RSA key exchange              — No forward secrecy. Replaced by mandatory ECDHE.
Static Diffie-Hellman         — No forward secrecy. Replaced by ephemeral (ECDHE).
DH_anon / ECDH_anon           — No authentication, vulnerable to MITM. Removed entirely.
3DES / RC4 / AES-CBC           — Weak ciphers. AES-CBC is vulnerable to padding oracle
                                attacks (Lucky 13, POODLE). Replaced by AEAD only
                                (AES-GCM, ChaCha20-Poly1305).
MD5 / SHA-1 in handshake      — Collisions. Replaced by SHA-256 / SHA-384 only.
Compression                   — CRIME attack (2012): compression ratio leaks
                                information about secret cookies. Removed.
Renegotiation                 — Triple Handshake attack (2014): renegotiation could
                                be used to bind one session's identity to another's,
                                enabling MITM. Removed.
ChangeCipherSpec message      — Vestigial in TLS 1.2, removed (handshake keys are
                                derived from the transcript directly).
Custom DHE groups             — Logjam attack (2015): a malicious server could
                                force a weak DHE group, enabling passive decryption.
                                Removed; only named curves (X25519, P-256, P-384) allowed.

What TLS 1.3 keeps:
  - Asymmetric signatures: RSA-PSS, ECDSA, Ed25519 (for signing the handshake)
  - Symmetric AEAD ciphers: AES-128-GCM, AES-256-GCM, ChaCha20-Poly1305
  - Hash functions: SHA-256, SHA-384 (for HKDF and transcript)
  - The X.509 certificate format and PKI (unchanged)
```

The five TLS 1.3 cipher suites (versus ~30 in TLS 1.2):

```text
TLS_AES_128_GCM_SHA256         — AES-128-GCM, SHA-256 PRF. Default, fast with AES-NI.
TLS_AES_256_GCM_SHA384         — AES-256-GCM, SHA-384 PRF. Higher security margin.
TLS_CHACHA20_POLY1305_SHA256   — ChaCha20-Poly1305, SHA-256 PRF. Fast without AES-NI (mobile).
TLS_AES_128_CCM_SHA256         — AES-128-CCM, SHA-256 PRF. Rare; for constrained devices.
TLS_AES_128_CCM_8_SHA256       — AES-128-CCM with 8-byte tag, SHA-256 PRF. Very rare; IoT.
```

Notice that the cipher suite names do *not* mention the key exchange or signature algorithm — those are negotiated separately via the `key_share` and `signature_algorithms` extensions. In TLS 1.2, the cipher suite was a bundle of (key exchange + authentication + cipher + MAC); in TLS 1.3, the cipher suite is just (cipher + PRF hash), and the other components are negotiated independently. This simplifies the negotiation and removes a class of downgrade attacks.

The compression removal deserves special attention. TLS compression (RFC 3749, optional in TLS 1.2) compressed the entire TLS record stream — including both attacker-controlled data (the URL path, which the attacker can choose) and secret data (the Cookie header). Because compression ratios depend on repeated substrings, an attacker who could insert chosen plaintext into the request and observe the compressed size could iteratively guess the cookie's contents one byte at a time. This is the **CRIME** attack (Compression Ratio Info-leak Made Easy, September 2012 by Duong and Rizzo). The fix is to disable TLS compression entirely, which TLS 1.3 does by removing it from the protocol. The same attack vector exists in HTTP gzip compression when applied to mixed secret/non-secret data (the **BREACH** attack, August 2013) — that requires application-level mitigations because HTTP compression is still useful.

```bash
# Verify your server does not offer TLS compression (it should not, in TLS 1.3)
openssl s_client -connect example.com:443 -servername example.com < /dev/null 2>&1 | grep -i 'compression'
# Expect: "Compression: NONE" (or nothing — compression was removed entirely in 1.3)

# Check that your server is TLS 1.3 only (or at least prefers it)
nmap --script ssl-enum-ciphers -p 443 example.com | grep -E 'TLSv|cipher'
```

The downgrade protection mechanism deserves its own attention. Even if both client and server support TLS 1.3, a man-in-the-middle attacker could tamper with the ClientHello to make the server think the client only supports TLS 1.2, forcing a downgrade to the weaker protocol. TLS 1.3 defends against this with a clever trick: the server, in its `ServerHello`, includes a special marker in the `random` field (bytes 24-27 set to `44 4F 57 4E` 47 52 44 01 — the ASCII for "DOWNGRD\1") if it agrees to use TLS 1.2. A TLS 1.3-capable client that sees this marker in a TLS 1.2 ServerHello knows the server *was* capable of 1.3 but is being downgraded — and aborts the connection. This forces the attacker to also tamper with the ServerHello, which they cannot do without the server's cooperation.

```text
TLS 1.3 downgrade protection:

  Client supports TLS 1.3 and 1.2. Sends ClientHello with supported_versions = [1.3, 1.2].

  Attacker tampers: changes supported_versions to [1.2], removes 1.3.

  Server (TLS 1.3-capable) sees only TLS 1.2 in ClientHello. Agrees to TLS 1.2.
  Server includes downgrade marker in ServerHello.random[24:28] = "DOWNGRD\1".

  Client receives TLS 1.2 ServerHello. Checks random[24:28].
  Sees "DOWNGRD\1" — server is TLS 1.3-capable but agreed to 1.2.
  Client ABORTS: "downgrade detected".

  Without the marker, the client would have accepted the downgrade silently.
  The marker makes the downgrade detectable.
```

The production failure mode tied to deprecated mechanisms is **the server still offering TLS 1.0 or 1.1 for "compatibility"**. As of June 2021, browsers and major CAs no longer trust TLS 1.0/1.1 (they are deprecated by RFC 8996). A server still offering them is providing an attack surface for any client that supports them, and the server is likely out of compliance with PCI-DSS, HIPAA, and other regulatory frameworks. The fix is to disable TLS 1.0 and 1.1 in the server configuration (`ssl_protocols TLSv1.2 TLSv1.3;` in nginx, `TLSv1.2+TLSv1.3` in Spring Boot's `server.ssl.enabled-protocols`).

## How This Connects to the Frameworks

Every framework in section 05 inherits TLS 1.3 support from the runtime:

- **Spring Boot**: Java 11+ supports TLS 1.3 by default (`jdk.tls.client.protocols=TLSv1.3,TLSv1.2`). Java 8 needs 8u262+ for TLS 1.3.
- **Express/Node.js**: Node 12+ supports TLS 1.3 if compiled against OpenSSL 1.1.1+.
- **Python**: CPython 3.7+ supports TLS 1.3 if the system OpenSSL is 1.1.1+. Ubuntu 20.04+ and macOS 10.15+ have this.
- **PHP/Laravel**: PHP 7.4+ supports TLS 1.3 if compiled against OpenSSL 1.1.1+.

The framework's job is to enable TLS 1.3 (it usually is by default), set the cipher preference (`ssl_prefer_server_ciphers` in nginx, the default cipher list in Spring Boot's `server.ssl.ciphers`), and ensure that the certificate's signature algorithm is supported (RSA-PSS or ECDSA — not RSA-PKCS1 v1.5, which is being phased out).

If any of these steps fails — a runtime too old for TLS 1.3, a certificate using a deprecated signature algorithm, a server offering TLS 1.0 for "compatibility" — the failure surfaces as a browser warning, a failed handshake, or a compliance audit finding. Knowing which primitive is at the root of each failure is the difference between a 5-minute fix and a 5-hour incident.

## Hands-On Exercise

```bash
# Inspect a real TLS 1.3 handshake
openssl s_client -connect example.com:443 -servername example.com -tls1_3 -msg < /dev/null 2>&1 | \
  grep -E 'ClientHello|ServerHello|Certificate|Finished|EncryptedExtensions'

# Time the handshake — compare TLS 1.3 (1-RTT) to TLS 1.2 (2-RTT)
curl -w "TLS 1.3: %{time_appconnect}s\n" -o /dev/null -s --tlsv1.3 https://example.com/
curl -w "TLS 1.2: %{time_appconnect}s\n" -o /dev/null -s --tlsv1.2 https://example.com/
# On a 100ms RTT link, expect TLS 1.3 to be ~100ms faster

# Verify forward secrecy by checking the ECDHE group used
openssl s_client -connect example.com:443 -servername example.com -tls1_3 < /dev/null 2>&1 | grep -i 'temp key\|curve\|group'
# Expect: "Server Temp Key: X25519, 253 bits" (or P-256, P-384)

# Verify the server does not offer deprecated TLS 1.0/1.1
nmap --script ssl-enum-ciphers -p 443 example.com | grep -E 'TLSv|cipher'

# Verify the cipher suite is AEAD only (no CBC, no RC4, no 3DES)
openssl ciphers -v 'TLS 1.3' | awk '{print $1, $2, $3}'
# Expect: TLS_AES_256_GCM_SHA384, TLS_CHACHA20_POLY1305_SHA256, TLS_AES_128_GCM_SHA256

# Test 0-RTT resumption (returning connection)
# (curl does not support 0-RTT directly; use a tool like quiche's http3-client)
# Or use OpenSSL's s_client with -sess_out / -sess_in to test session resumption
openssl s_client -connect example.com:443 -servername example.com -sess_out /tmp/sess < /dev/null
openssl s_client -connect example.com:443 -servername example.com -sess_in /tmp/sess < /dev/null 2>&1 | grep -i 'reused\|resumption'

# Test the downgrade protection (force TLS 1.2 from a TLS 1.3-capable client)
openssl s_client -connect example.com:443 -servername example.com -tls1_2 < /dev/null 2>&1 | grep -i 'protocol\|cipher'
```
