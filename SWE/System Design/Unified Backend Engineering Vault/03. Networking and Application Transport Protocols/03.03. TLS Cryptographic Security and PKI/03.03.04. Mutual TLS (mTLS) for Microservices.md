# 03.03.04. Mutual TLS (mTLS) for Microservices

## What This Is

Standard TLS authenticates the server to the client — the browser verifies that the server presenting `api.example.com`'s certificate actually owns the corresponding private key. The client is *not* authenticated at the TLS layer; if client authentication is needed, it is done at the application layer (e.g., an `Authorization: Bearer <token>` header). **Mutual TLS (mTLS)** adds the reverse: the server also authenticates the client by requiring the client to present its own certificate. Both sides verify each other's certificates, and the connection is bidirectionally authenticated at the transport layer.

mTLS is the cryptographic foundation of zero-trust service meshes. In a traditional "perimeter security" model, services inside the private network trust each other by virtue of being inside the network — any request from `10.0.0.5` is trusted because `10.0.0.5` is inside the firewall. In a zero-trust model, the network is assumed hostile (an attacker may have breached the perimeter and be running code inside), and every service-to-service call must authenticate cryptographically. mTLS is how this is implemented: every microservice has a certificate, every call presents the certificate, and the receiving service verifies the caller's identity before processing the request.

This note covers the `CertificateRequest` handshake flow, the zero-trust use case, how Istio and Linkerd implement mTLS via sidecar proxies, the certificate rotation problem, and the SPIFFE/SPIRE identity framework.

## The Details

### Standard TLS (Server Authentication) vs. Mutual TLS (Bidirectional Client & Server Authentication)

In standard TLS, only the server presents a certificate. The client verifies the server's identity; the server does not verify the client's. If client authentication is needed (e.g., "only Alice's service may call Bob's service"), it is done at the application layer via tokens, API keys, or basic auth — all of which are bearer tokens that can be stolen and replayed.

```text
Standard TLS handshake (server auth only):

  Client                                         Server
    │ ── ClientHello ────────────────────────────► │
    │ ◄── ServerHello + Certificate (server's) ─── │
    │ ◄── CertificateVerify (server proves key) ── │
    │ ◄── Finished ────────────────────────────── │
    │ ── Finished ────────────────────────────────► │
    │                                              │
    │ ◄═══════ encrypted application data ═══════► │
    │                                              │
    Server is authenticated. Client is anonymous
    (or authenticated at application layer via tokens).
```

In mTLS, the server sends a `CertificateRequest` message in its first flight, and the client must respond with a `Certificate` message containing its own certificate, followed by a `CertificateVerify` proving it holds the corresponding private key. The server verifies the client's certificate against its trust store and aborts if verification fails.

```text
mTLS handshake (TLS 1.3, bidirectional auth):

  Client                                         Server
    │ ── ClientHello (with client's key_share) ──► │
    │ ◄── ServerHello + {EncryptedExtensions} ─── │
    │ ◄── {CertificateRequest} ───────────────── │  ← "I want YOUR cert too"
    │ ◄── {Certificate} (server's) ────────────── │
    │ ◄── {CertificateVerify} ─────────────────── │
    │ ◄── {Finished} ──────────────────────────── │
    │ ── {Certificate} (client's) ────────────────► │  ← client presents its cert
    │ ── {CertificateVerify} ─────────────────────► │  ← client proves it has the private key
    │ ── {Finished} ──────────────────────────────► │
    │                                              │
    │ ◄═══════ encrypted application data ═══════► │
    │                                              │
    Server is authenticated (client verified server's cert).
    Client is authenticated (server verified client's cert).
    No application-layer token needed.
```

The key operational difference: in standard TLS, the server has one trust store (the public CA roots, for verifying server certs presented *to* it as a client — but if the server is only ever a server, this trust store is unused). In mTLS, the server has *two* trust stores: the public CA roots (for outbound connections where the server acts as a client) plus a **client CA trust store** (for verifying client certificates presented *to* it). The client CA trust store contains the CA that signed the client certificates — typically an internal CA, not a public CA, because client certificates issued by public CAs are rare and expensive.

```bash
# Configure nginx for mTLS — the ssl_client_certificate directive is the client CA trust store
# server {
#   listen 443 ssl;
#   ssl_certificate     /etc/nginx/server.pem;
#   ssl_certificate_key /etc/nginx/server.key;
#   ssl_client_certificate /etc/nginx/client-ca.pem;   ← trust store for client certs
#   ssl_verify_client on;                              ← require client cert
#   ssl_verify_depth 2;                                ← allow intermediate CAs
# }

# Test mTLS with curl — present a client certificate
curl --cert client.pem --key client.key --cacert server-ca.pem https://api.internal.example.com/

# Test what happens without a client cert (expect 400 Bad Request)
curl --cacert server-ca.pem https://api.internal.example.com/
# 400 No required SSL certificate was sent

# Inspect a client certificate
openssl x509 -in client.pem -noout -subject -issuer -ext extendedKeyUsage
# Expect: X509v3 Extended Key Usage: TLS Web Client Authentication
```

The production failure mode tied to mTLS is **the expired client certificate**. Client certificates have a `Not After` date just like server certificates. When a client cert expires, the server starts rejecting all calls from that client with a TLS handshake failure (not a 401 — the handshake never completes, so no HTTP response is returned). The symptom is "sudden 100% failure rate from one microservice" with logs showing `SSL handshake failed: certificate expired` on the receiving side. The fix is automated certificate rotation (covered in the rotation H3 below).

### The `CertificateRequest` handshake flow

The `CertificateRequest` message is what makes mTLS structurally different from standard TLS. In TLS 1.3, it is sent by the server in the first encrypted flight (after `EncryptedExtensions`), and it contains:

```text
CertificateRequest message (TLS 1.3):
  - certificate_request_context: 8 bytes of opaque data, echoed back in the
    client's Certificate message (to prevent replay across handshakes)
  - extensions:
    - signature_algorithms: which signature algorithms the server will accept
      from the client (e.g., ecdsa_secp256r1_sha256, rsa_pss_rsae_sha256)
    - certificate_authorities: list of CA DNs the server trusts
      (e.g., "CN=Internal Service CA,O=Example Corp,C=US")
    - (optionally) signature_algorithms_cert: hash algorithms for cert verification
```

The client receives the `CertificateRequest` and responds with a `Certificate` message containing its own certificate chain (leaf + intermediate), followed by a `CertificateVerify` message — a signature over the handshake transcript up to that point, made with the client's private key. The server verifies the signature against the public key in the client's certificate, proving the client holds the private key (not just the certificate).

The `certificate_authorities` extension is the server's way of telling the client "I will accept client certificates signed by these CAs". If the client has a certificate signed by a different CA, it does not even send it — it sends an empty Certificate message and the server either continues without client auth (if `ssl_verify_client optional`) or aborts (if `ssl_verify_client on`).

```text
TLS 1.2 vs TLS 1.3 CertificateRequest differences:

TLS 1.2 CertificateRequest:
  - Sent in plaintext (before encryption starts)
  - Contains a list of certificate types (RSA, DSS, ECDSA)
  - Contains a list of signature algorithms
  - Contains a list of CA DNs
  - Vulnerable to: CA DN list leaks internal CA names to passive eavesdropper

TLS 1.3 CertificateRequest:
  - Sent encrypted (after ServerHello, with handshake keys)
  - Contains certificate_request_context (anti-replay)
  - Contains extensions (signature_algorithms, certificate_authorities)
  - No leak of CA names to eavesdropper (encrypted)
  - More flexible extension model
```

In TLS 1.2, the `CertificateRequest` was sent in plaintext, which leaked the names of the internal CAs the server trusted. In TLS 1.3, the `CertificateRequest` is sent encrypted, hiding this information. This is a privacy improvement that matters in zero-trust networks where the list of trusted CAs might itself be sensitive.

The client-side configuration for mTLS in modern frameworks:

```bash
# Spring Boot (Java) — configure client keystore for outbound mTLS
# application.yml:
# server.ssl.key-store: classpath:server.p12
# server.ssl.key-store-password: ${KEYSTORE_PASSWORD}
# server.ssl.trust-store: classpath:truststore.p12
# server.ssl.trust-store-password: ${TRUSTSTORE_PASSWORD}
# server.ssl.client-auth: need   ← require client cert (mTLS)
#
# For outbound mTLS calls (RestTemplate / WebClient):
# -Djavax.net.ssl.keyStore=/path/to/client.p12
# -Djavax.net.ssl.keyStorePassword=...
# -Djavax.net.ssl.trustStore=/path/to/truststore.p12

# Express/Node.js — pass client cert in https.Agent
# const agent = new https.Agent({
#   cert: fs.readFileSync('client.pem'),
#   key:  fs.readFileSync('client.key'),
#   ca:   fs.readFileSync('server-ca.pem'),
# });
# https.request({ host: 'api.internal', agent, ... }, ...);

# Python requests — pass client cert
# requests.get('https://api.internal', cert=('client.pem', 'client.key'), verify='server-ca.pem')
```

The production failure mode tied to the `CertificateRequest` flow is **the truststore that does not contain the client CA**. The server's `ssl_client_certificate` (nginx) or `trust-store` (Spring Boot) points to the wrong CA file, so every client certificate is rejected with `unknown ca`. The symptom is "every mTLS call fails with handshake error" even though the client cert is valid and unexpired. The fix is to ensure the server's client trust store contains the *full chain* of CAs that signed the client certificates — typically the root CA + the intermediate CA, in a single PEM file.

### Enforcing zero-trust network architectures using mTLS inside private service meshes (Envoy, Istio)

The zero-trust model says: never trust the network. Every call, even between two services in the same Kubernetes pod, must be authenticated and encrypted. Implementing this manually — issuing certificates to every service, configuring each service to present its cert on every call, rotating certs periodically — is operationally intractable at scale. Service meshes solve this by automating the entire mTLS lifecycle via **sidecar proxies**.

In a service mesh like Istio or Linkerd, every pod runs two containers: the application container (your Spring Boot / Express / Python code) and a **sidecar proxy** (Envoy for Istio, linkerd2-proxy for Linkerd). The sidecar intercepts all inbound and outbound network traffic and handles mTLS transparently:

```text
Service mesh with sidecar proxies (Istio / Envoy):

  Pod A (caller)                                 Pod B (callee)
  ┌─────────────────────────────┐                ┌─────────────────────────────┐
  │  ┌─────────────────────┐    │                │    ┌─────────────────────┐  │
  │  │  Application (app)  │    │                │    │  Application (app)  │  │
  │  │  Plain HTTP request │    │                │    │  Plain HTTP response│  │
  │  │  to localhost:15001 │    │                │    │  on port 8080       │  │
  │  └──────────┬──────────┘    │                │    └──────────▲──────────┘  │
  │             │ (loopback)    │                │               │ (loopback)  │
  │  ┌──────────▼──────────┐    │                │    ┌──────────┴──────────┐  │
  │  │  Envoy sidecar      │    │                │    │  Envoy sidecar      │  │
  │  │  - Presents A's     │ ───┼──── mTLS ──────┼──► │  - Verifies A's     │  │
  │  │    client cert      │    │  (encrypted)   │    │    client cert      │  │
  │  │  - Verifies B's     │    │                │    │  - Presents B's     │  │
  │  │    server cert      │ ◄──┼──── mTLS ──────┼─── │    server cert      │  │
  │  └─────────────────────┘    │                │    └─────────────────────┘  │
  └─────────────────────────────┘                └─────────────────────────────┘

  Application code: writes plain HTTP. No certificate handling. No TLS code.
  Sidecar: handles all mTLS transparently. Rotates certs automatically.
```

The application code is completely unaware that mTLS is happening. It makes a plain HTTP request to `localhost:15001` (the sidecar's inbound port); the sidecar looks up the destination service in the service registry, opens an mTLS connection to the destination sidecar, presents Pod A's client certificate, verifies Pod B's server certificate, encrypts the request, sends it, receives the encrypted response, decrypts it, and returns the plain HTTP response to the application. The application sees plain HTTP; the wire sees encrypted mTLS.

The certificate lifecycle is also automated. The mesh's control plane (Istio's `istiod`, Linkerd's `linkerd-controller`) runs an internal CA. When a pod starts, the sidecar generates a private key, sends a certificate signing request to the control plane, and receives a certificate signed by the mesh's internal CA. The certificate is valid for a short period (Istio default: 24 hours) and is automatically rotated before expiry (typically at 80% of validity, so every ~19 hours). The application never sees the certificate; the sidecar manages it entirely.

```bash
# Check mTLS status in an Istio mesh
istioctl authn tls-check api.example.com
# Expect: "mTLS: STRICT" — all traffic to this service is mTLS

# Inspect the certificates being used by a pod's sidecar
istioctl proxy-config secret <pod-name>.<namespace>
# Output: the SPIFFE identity, the cert's expiry, the issuing CA

# Verify mTLS is actually happening on the wire
kubectl exec -it <pod-name> -c istio-proxy -- tcpdump -i any -A 'tcp port 8080' | head
# The traffic should be TLS-encrypted (binary, not readable HTTP)

# In Linkerd, check mTLS status
linkerd -n <namespace> edges deploy
# Output shows whether each edge is using mTLS
```

The production failure mode tied to service mesh mTLS is **the mesh's internal CA expiry**. The mesh's root CA certificate (used to sign all the per-pod certificates) has its own expiry, typically 10 years. If the root CA expires, every per-pod certificate it signed becomes invalid, and all mTLS handshakes across the mesh fail simultaneously — a total service mesh outage. The fix is to monitor the root CA's expiry (Istio exposes this as a metric) and rotate it well before expiry. The recurring symptom is "the mesh worked for 5 years and then suddenly stopped" — and the root cause is the root CA that was set up at install time and forgotten.

### Certificate rotation, revocation, and automated provisioning pipelines for internal service identities

In a microservices deployment with thousands of services and tens of thousands of pod instances, each pod has its own short-lived certificate. Manual certificate management is impossible — the system must automate the entire lifecycle: issuance, distribution, rotation, and revocation. This is the domain of **SPIFFE** (Secure Production Identity Framework for Everyone) and its reference implementation **SPIRE**.

**SPIFFE** (RFC draft, CNCF project) defines a standard for service identity. A **SPIFFE ID** is a URI of the form `spiffe://trust-domain/workload-identifier`, e.g., `spiffe://prod.example.com/billing-service`. The SPIFFE ID is the workload's cryptographic identity — not its IP address (which changes on every restart), not its hostname (which can be spoofed), but a stable identifier bound to a certificate. The certificate that carries this identity is in **SPIFFE Verifiable Identity Document (SVID)** format — either an X.509 certificate with the SPIFFE ID in a URI SAN, or a JWT signed by the trust domain's key.

```text
SPIFFE identity model:

  Trust Domain: prod.example.com (the boundary within which identities are trusted)
       │
       │ issues SVIDs (X.509 certs with URI SAN = spiffe ID)
       ▼
  SPIRE Server (the CA for the trust domain)
       │
       │ attests workloads (proves they are who they claim to be)
       ▼
  SPIRE Agent (runs on each node, attests workloads, fetches SVIDs)
       │
       │ delivers SVIDs to workloads via the Workload API
       ▼
  Workload (e.g., billing-service pod)
       │
       │ uses SVID for mTLS to other workloads
       │ SVID is short-lived (1 hour default), rotated automatically by the agent
       ▼
  Other Workload (e.g., inventory-service pod)
       │
       │ verifies the SVID against the trust domain's bundle (public keys)
       │ trusts the SPIFFE ID as the caller's identity
```

The **SPIRE Agent** runs on each Kubernetes node (or VM, or bare metal). It exposes a **Workload API** (a Unix socket) that workloads call to fetch their SVID. The agent attests the workload's identity (using Kubernetes service account tokens, node-attestation documents, or process signatures) before issuing an SVID, so a workload cannot request an SVID for an identity it does not own. The SVID is short-lived (typically 1 hour) and is automatically rotated by the agent before expiry — the workload just calls the Workload API again and gets a fresh SVID.

The advantage over per-mesh CAs (Istio's internal CA, Linkerd's identity service) is **federation**: two different trust domains (e.g., `prod.example.com` and `staging.example.com`, or `example.com` and `partner.com`) can be federated by exchanging their public key bundles, allowing workloads in one trust domain to verify SVIDs from the other. This is how multi-cluster, multi-cloud, and cross-organization mTLS is done.

```bash
# Install SPIRE in a Kubernetes cluster
helm install spire-crds spire/crds
helm install spire spire/spire --set spire-server.enabled=true

# Check the SVIDs issued to a workload
spire-agent api fetch x509 -socketPath /tmp/spire-agent/public/api.sock
# Output: a PEM-encoded X.509 SVID with URI SAN spiffe://prod.example.com/billing-service

# Configure Envoy to use SPIRE for mTLS
# (Envoy's SDS — Secret Discovery Service — can fetch certs from SPIRE)
# envoy.yaml:
# secrets_manager:
#   sds_config:
#     api_config_source:
#       api_type: GRPC
#       grpc_services:
#         - envoy_grpc:
#             cluster_name: spire_agent
#       set_node_on_first_message_only: false
#       transport_api_version: V3

# Istio can use SPIRE as its CA instead of the built-in istiod CA
# (for multi-cluster federation or compliance requirements)
```

The certificate rotation pattern in production:

```text
Rotation lifecycle (per workload SVID):

  t=0       SPIRE Agent issues SVID (valid 1 hour)
  t=30m     Workload's sidecar checks SVID freshness — still valid
  t=50m     SPIRE Agent pre-fetches a new SVID (at 80% of validity)
  t=55m     Workload's sidecar swaps to the new SVID for new connections
  t=58m     Old SVID's connections drain (no new connections use it)
  t=60m     Old SVID expires; any lingering connections using it fail

  No application downtime. No manual intervention. No expired-cert incidents.
```

The production failure mode tied to rotation is **the workload that holds a certificate in memory and never refreshes it**. A long-running Java process loads its client certificate from a file at startup, caches it in memory, and uses it for every outbound TLS connection — forever. When the certificate expires (after 24 hours, or 1 hour, or whatever the mesh's policy is), every outbound call fails. The fix is to either (a) use a sidecar proxy that handles rotation transparently (the sidecar always has a fresh cert; the application sees plain HTTP to localhost), or (b) use the runtime's certificate-refresh mechanism (Java's `X509ExtendedKeyManager` can be wrapped in a reloading implementation; Node's `tls.createSecureContext` can be re-called; Python's `ssl.SSLContext` can be rebuilt periodically). The recurring symptom is "the service worked fine for 24 hours and then every outbound call started failing" — and the root cause is a certificate that was loaded once and never refreshed.

## How This Connects to the Frameworks

mTLS in section 05's frameworks is typically handled by the service mesh, not the application code:

- **Spring Boot**: when running in Istio, the application listens on plain HTTP (port 8080); the Envoy sidecar terminates mTLS. Spring Security can be configured for X.509 client cert auth (`@EnableWebSecurity` + `x509()`), but this is rare in mesh-based deployments.
- **Express/Node.js**: same pattern — plain HTTP to the sidecar, sidecar does mTLS. For direct mTLS (no sidecar), use `https.createServer({ requestCert: true, rejectUnauthorized: true, ca: clientCA })`.
- **Python/Django**: same pattern — plain HTTP behind the sidecar. For direct mTLS, use `ssl.SSLContext(ssl.PROTOCOL_TLS_SERVER)` with `verify_mode = ssl.CERT_REQUIRED`.
- **PHP/Laravel**: almost always behind a sidecar or reverse proxy; PHP-FPM does not natively terminate TLS in production.

The shift in zero-trust architectures is that mTLS becomes an infrastructure concern, not an application concern. The application code does not change whether mTLS is enabled or not — the sidecar handles it. This is a significant operational simplification: the application team does not need to manage certificates, rotate keys, or debug TLS handshake failures; the platform team does.

If any of these steps fails — an expired client cert, a missing CA in the trust store, a misconfigured sidecar, a mesh CA that expired — the failure surfaces as "all calls from service A to service B fail with TLS handshake error". Knowing which layer (application vs sidecar vs mesh CA vs SPIRE) caused the failure is the difference between a 5-minute fix and a 5-hour incident.

## Hands-On Exercise

```bash
# Test mTLS with openssl (manually, without a service mesh)
# 1. Generate a client CA and a client cert
openssl genrsa -out client-ca.key 4096
openssl req -x509 -new -key client-ca.key -days 3650 -subj "/CN=Client CA" -out client-ca.pem
openssl genrsa -out client.key 2048
openssl req -new -key client.key -subj "/CN=client-service" -out client.csr
openssl x509 -req -in client.csr -CA client-ca.pem -CAkey client-ca.key -CAcreateserial -days 365 -out client.pem

# 2. Start an mTLS server (openssl s_server)
openssl s_server -accept 8443 -cert server.pem -key server.key -CAfile client-ca.pem -Verify 1

# 3. Connect with a client cert (mTLS)
openssl s_client -connect localhost:8443 -cert client.pem -key client.key -CAfile server-ca.pem

# 4. Connect without a client cert (expect rejection)
openssl s_client -connect localhost:8443 -CAfile server-ca.pem
# Expect: "peer did not return a certificate" or handshake failure

# Inspect a service mesh's mTLS configuration (Istio)
istioctl authn tls-check <service-name>.<namespace>

# Check the SVIDs issued by SPIRE
spire-agent api fetch x509 -socketPath /tmp/spire-agent/public/api.sock | openssl x509 -noout -text

# Verify mTLS is happening on the wire (capture should show TLS, not plain HTTP)
kubectl exec -it <pod-name> -c istio-proxy -- tcpdump -i any -A 'tcp port 8080' -c 5

# Check Istio's root CA expiry (the mesh-breaking failure mode)
kubectl get secret istio-ca-secret -n istio-system -o jsonpath='{.data.ca-cert\.pem}' | base64 -d | \
  openssl x509 -noout -enddate
```
