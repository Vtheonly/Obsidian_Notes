# 03.03.02. Public Key Infrastructure and Certificates

## What This Is

Symmetric encryption requires both sides to share a key, but how does the client know that the public key in the server's TLS handshake actually belongs to the server and not to an attacker performing a man-in-the-middle attack? This is the **authentication problem**, and it is solved by **Public Key Infrastructure (PKI)**: a hierarchical system of Certificate Authorities (CAs) that issue, sign, and revoke digital certificates binding public keys to identities. When your browser connects to `https://api.example.com`, the server presents a certificate that says "I am api.example.com, here is my public key, and DigiCert has signed this assertion". The browser verifies DigiCert's signature using DigiCert's root certificate (pre-installed in the OS or browser), and trusts the binding.

This note covers the X.509 certificate format, the chain of trust from root CAs to leaf certificates, the CA/Browser Forum rules that govern what CAs may do, certificate revocation (CRL vs OCSP vs OCSP stapling), wildcard and SAN certificates, and the ACME protocol that powers Let's Encrypt's automated certificate issuance.

## The Details

### The Trust Hierarchy: Root Certificate Authorities (Root CAs), Intermediate CAs, and Leaf/End-Entity Certificates

The PKI trust model is hierarchical. At the top are **Root CAs** — organizations that have demonstrated to operating system and browser vendors (Microsoft, Apple, Mozilla, Google) that they operate securely and follow the CA/Browser Forum Baseline Requirements. Their root certificates are pre-installed in the OS trust store and are the ultimate trust anchors for all TLS connections. There are currently ~140 root CAs in the major trust stores (Mozilla's `cacert.txt` is the canonical open-source list).

Below the root CAs are **Intermediate CAs**. A root CA's private key is too valuable to use directly for signing leaf certificates (if the root key is compromised, every certificate it ever signed becomes untrustworthy, and the root must be distrusted — a catastrophic outcome for the CA's business). Instead, the root signs one or more intermediate CA certificates, each with a more limited scope (e.g., "this intermediate may issue EV certificates" or "this intermediate may issue certificates only to domains owned by Company X"). The intermediate's private key, kept online and used for signing leaf certificates, is the operational signing key. If an intermediate is compromised, the root can revoke it without affecting the rest of the CA's business.

At the bottom are **Leaf certificates** (also called end-entity certificates). These are the certificates that web servers present to clients. Each leaf cert binds a domain name (or several, via Subject Alternative Names) to a public key. The leaf is signed by an intermediate CA's private key, and the client verifies the chain: leaf → intermediate → root.

```text
Trust hierarchy and the verification chain:

  Root CA Certificate (e.g., "ISRG Root X1", Let's Encrypt's root)
    - Self-signed (signed by its own private key)
    - Pre-installed in OS/browser trust stores
    - Private key kept offline, in a hardware security module (HSM)
       │
       │ signs
       ▼
  Intermediate CA Certificate (e.g., "Let's Encrypt R3")
    - Signed by the root CA's private key
    - Has the CA:TRUE basic constraint (can sign other certificates)
    - Private key kept online, used to sign leaf certs daily
       │
       │ signs
       ▼
  Leaf Certificate (e.g., "api.example.com")
    - Signed by the intermediate CA's private key
    - Has the CA:FALSE basic constraint (cannot sign other certificates)
    - Has the server's public key and the domain name in SAN
    - Private key held by the server (in a file, an HSM, or a KMS)

When the client connects:
  1. Server presents leaf cert + intermediate cert (the "chain")
  2. Client verifies leaf's signature using intermediate's public key
  3. Client verifies intermediate's signature using root's public key
  4. Client checks that root is in its trust store → TRUSTED
  5. Client checks that the domain in the leaf's SAN matches the URL → AUTHENTICATED
```

The root certs in your trust store are the load-bearing trust anchors of the entire internet PKI. Listing them reveals the trust landscape:

```bash
# List root CAs trusted by your OS (Linux)
ls /etc/ssl/certs/ | head
# Or via the ca-certificates bundle
awk -v cmd='openssl x509 -noout -subject' '/BEGIN/{close(cmd);print | cmd} {print | cmd}' /etc/ssl/certs/ca-certificates.crt | head

# List root CAs trusted by your browser (Chrome/Firefox)
# Chrome uses the OS trust store; Firefox uses its own (about:preferences#privacy → View Certificates)

# Inspect a website's certificate chain
openssl s_client -connect example.com:443 -servername example.com -showcerts < /dev/null 2>&1 | grep -E '^(s|i):'
# s: = subject of the certificate at this level
# i: = issuer (who signed it)
# Expect:
#   s:CN=www.example.org (leaf)
#   i:CN=R3 (intermediate)
#   s:CN=R3 (intermediate)
#   i:CN=Internet Security Research Group ISRG Root X1 (root)
```

The production failure mode tied to the trust hierarchy is **the missing intermediate certificate**. The server presents only its leaf cert, not the chain. The client has the root in its trust store but cannot verify the leaf because it does not have the intermediate. Modern browsers cache intermediates they have seen before, so the failure is intermittent — works in Chrome (which has the intermediate cached from a previous site), fails in curl (which does not cache), fails in mobile apps (which use a minimal trust store). The fix is for the server to send the full chain: leaf + intermediate, in that order, in the TLS handshake. nginx's `ssl_certificate` directive must point to a file containing both; Apache's `SSLCertificateChainFile` (deprecated in 2.4.8) used to be separate. The recurring production symptom is "the cert works in browsers but the API call from our backend fails" — and the fix is to ensure the server sends the intermediate.

### X.509 Certificate Structure: Serial Number, Subject, Issuer, Validity Period, Public Key, Extensions, Subject Alternative Names (SAN)

An X.509 v3 certificate (RFC 5280) is an ASN.1 DER-encoded data structure with the following fields:

```text
Certificate
├── Version (v1, v2, or v3 — v3 since 2008 is universal)
├── Serial Number (unique per issuer, max 20 octets; random in modern CAs)
├── Signature Algorithm (e.g., sha256WithRSAEncryption, ecdsa-with-SHA256)
├── Issuer (DN of the CA that signed this cert, e.g., "CN=R3,O=Let's Encrypt,C=US")
├── Validity
│   ├── Not Before (issue date, UTC)
│   └── Not After (expiry date, UTC — max 398 days for public certs since 2020)
├── Subject (DN of the entity this cert represents, e.g., "CN=api.example.com")
│   └── (Note: CN is deprecated; SAN is authoritative)
├── Subject Public Key Info
│   ├── Algorithm (e.g., rsaEncryption, id-ecPublicKey, id-Ed25519)
│   └── Subject Public Key (the actual key bytes)
├── Extensions (X.509 v3)
│   ├── Subject Alternative Name (SAN) — the list of domain names (CRITICAL)
│   ├── Basic Constraints (CA:TRUE for intermediates/roots, CA:FALSE for leaf)
│   ├── Key Usage (digitalSignature, keyEncipherment, etc.)
│   ├── Extended Key Usage (serverAuth, clientAuth, etc.)
│   ├── Authority Key Identifier (which key signed this cert)
│   ├── Subject Key Identifier (this cert's key fingerprint)
│   ├── CRL Distribution Points (URL where the CRL can be fetched)
│   ├── Authority Information Access (URL for OCSP responder)
│   └── Certificate Policies (CA-specific policy OIDs)
└── Signature (the CA's signature over all the above)
```

The **Subject Alternative Name (SAN)** extension is the load-bearing field for domain validation. The original X.509 design used the Subject DN's Common Name (CN) field for the domain name, but this was ambiguous (does `CN=api.example.com` mean the domain `api.example.com`, or a person named "api.example.com"?). Since 2012, browsers require the SAN extension; the CN field is ignored for domain matching. A single certificate can have many SANs — a "multi-domain" or "UCC" (Unified Communications Certificate) can cover `example.com`, `www.example.com`, `api.example.com`, `mail.example.com`, and unrelated domains like `other-site.net` all in one cert.

```bash
# Inspect a certificate's full structure
openssl s_client -connect example.com:443 -servername example.com < /dev/null 2>/dev/null | \
  openssl x509 -noout -text

# Key fields to verify:
#   Subject Alternative Name:
#       DNS:www.example.org, DNS:example.com, DNS:example.org
#       (every domain this cert is valid for — this is the authoritative list)
#   Validity:
#       Not Before: Sep 14 00:00:00 2023 GMT
#       Not After : Oct 14 23:59:59 2023 GMT  (max 398 days for public trust)
#   Subject Public Key Info:
#       Public Key Algorithm: rsaEncryption
#       Public-Key: (2048 bit)
#   X509v3 Basic Constraints: CA:FALSE  (this is a leaf, not a CA)
#   X509v3 Extended Key Usage: TLS Web Server Authentication, TLS Web Client Authentication
#   X509v3 Authority Information Access:
#       OCSP - URI:http://r3.o.lencr.org    (where to check revocation)
#       CA Issuers - URI:http://r3.i.lencr.org/  (where to fetch the intermediate)

# Check a local certificate file
openssl x509 -in cert.pem -noout -subject -issuer -dates -ext subjectAltName
```

**Wildcard certificates** are a special case of SAN: `*.example.com` matches any single-label subdomain (`api.example.com`, `www.example.com`, but not `api.staging.example.com` — wildcards do not span multiple levels). They were popular for covering many subdomains cheaply, but they are now discouraged because compromising one certificate compromises all subdomains, and they do not work with HTTP/2's connection coalescing (where the browser may reuse a connection for any SAN on the cert). The CA/Browser Forum's current guidance is to prefer a multi-SAN certificate over a wildcard.

The **CA/Browser Forum Baseline Requirements** (CA/B Forum BR, latest version at cabforum.org) are the rules that all public CAs must follow to remain in browser trust stores. The key rules:
- Domain validation must use one of three methods: DNS TXT record, HTTP-01 challenge, or TLS-ALPN-01 challenge. Email-based validation was deprecated.
- Certificates are valid for at most 398 days (was 5 years before 2015, 2 years before 2018, 1 year since 2020).
- Certificates must include the SCT (Signed Certificate Timestamp) extension proving they were logged to a Certificate Transparency log (see below).
- CAs must support OCSP stapling and revocation within 24 hours of a revocation request.

The production failure mode tied to certificate structure is **the SAN that does not match the requested hostname**. Your application connects to `api.example.com` but the certificate's SAN lists only `www.example.com`. The TLS handshake completes (the cert is valid), but the hostname verification fails. In Java, this throws `SSLPeerUnverifiedException: Hostname not verified`; in Node, `ERR_TLS_CERT_ALTNAME_INVALID`; in Python, `ssl.SSLCertVerificationError: hostname mismatch`. The fix is either (a) reissue the certificate with the correct SAN, or (b) fix the URL the client is connecting to. Never disable hostname verification to work around this — that defeats the entire purpose of TLS.

### Certificate Revocation: Certificate Revocation Lists (CRL) vs. Online Certificate Status Protocol (OCSP) and OCSP Stapling

Once a certificate is issued, it remains valid until its `Not After` date — unless the CA *revokes* it earlier. Revocation happens when the private key is compromised, when the certificate was issued in error, or when the domain ownership changes. The challenge is: how does the client learn that a certificate has been revoked?

**Certificate Revocation Lists (CRLs)** are the original mechanism (RFC 5280 §5). The CA publishes a signed list of revoked certificate serial numbers at a URL listed in the cert's `CRL Distribution Points` extension. The client fetches the CRL, checks if the cert's serial number is in it, and if so, rejects the cert. The problem: CRLs grow large (millions of revoked certs across a CA's entire installed base), and clients must download the entire list to check one certificate — a multi-megabyte download just to verify one site. Modern browsers have effectively abandoned CRLs; they are used only in some enterprise PKI deployments.

**Online Certificate Status Protocol (OCSP)** (RFC 6960) is the lightweight successor. Instead of downloading the entire CRL, the client makes an HTTP request to the CA's OCSP responder (URL in the cert's `Authority Information Access` extension) asking "is serial number X revoked?". The responder returns a signed response: `good`, `revoked`, or `unknown`. The problem: this creates a privacy leak — the CA now knows which sites you are visiting (you are asking it about every certificate you encounter). It also adds latency (one extra HTTP round trip per TLS connection) and a reliability dependency (if the OCSP responder is down, what does the client do? — "soft fail" and accept the cert, or "hard fail" and reject? Most browsers soft-fail, which means an attacker can DoS the OCSP responder to bypass revocation).

**OCSP Stapling** (RFC 6066, the `status_request` TLS extension) is the modern solution. Instead of the client fetching the OCSP response, the *server* fetches it (periodically, e.g., every 24 hours), caches it, and "staples" it to its TLS handshake. The client receives the cert + the OCSP response in one handshake, verifies the OCSP response's signature (signed by the CA), and accepts or rejects the cert without any extra round trips. Privacy preserved (the CA does not see your visits), latency preserved (no extra round trip), reliability preserved (the server has a cached response even if the CA's OCSP responder is down).

```text
Without OCSP stapling:
  Client                                 Server                       CA OCSP
    │ ── TLS handshake (cert) ──────────► │
    │ ◄── cert ────────────────────────── │
    │                                     │
    │ ── OCSP request (serial X) ──────────────────────────────────────► │
    │ ◄── OCSP response (good/revoked) ───────────────────────────────── │
    │                                     │
    │ ── Finished + HTTP request ────────► │  (extra round trip to CA)

With OCSP Stapling:
  Client                                 Server                       CA OCSP
    │                                     │ ── OCSP request ──────────► │
    │                                     │ ◄── OCSP response ────────── │
    │                                     │   (server fetches periodically, caches)
    │                                     │
    │ ── TLS handshake ──────────────────► │
    │ ◄── cert + OCSP response (stapled) ─ │
    │                                     │
    │ ── Finished + HTTP request ────────► │  (no extra round trip)
```

```bash
# Check whether a server is using OCSP stapling
openssl s_client -connect example.com:443 -servername example.com -status < /dev/null 2>&1 | grep -i 'ocsp\|status'
# Look for "OCSP Response Status: successful" — if absent, the server is NOT stapling

# Enable OCSP stapling in nginx
# ssl_stapling on;
# ssl_stapling_verify on;
# resolver 8.8.8.8 valid=300s;
# (must configure a DNS resolver so nginx can look up the OCSP responder URL)

# Enable in Apache
# SSLUseStapling On
# SSLStaplingCache shmcb:/var/run/ocsp(128000)

# Force a browser to check revocation strictly
# Chrome: chrome://flags/#allow-ocsp-fail-open-to-revoked → disable (treat soft-fail as revoked)
```

The production failure mode tied to revocation is **the revoked certificate that nothing noticed**. A CA issues a cert, the cert's private key leaks, the cert is revoked, but the server keeps serving it and clients keep accepting it because nobody checks revocation. The most famous case: the 2011 DigiNotar breach, where an attacker issued a wildcard certificate for `*.google.com` and used it to intercept Gmail traffic of 300,000 Iranian users. The cert was eventually revoked, but browsers had been accepting it for weeks because their CRL/OCSP checks were soft-failing. The lesson: revocation only works if clients check it, and clients only check it if the server staples the OCSP response. The fix is mandatory OCSP stapling on production servers.

### Automated Certificate Management Environment (ACME Protocol) and Let's Encrypt automated renewals

Before 2015, getting a TLS certificate meant: create a certificate signing request (CSR), send it to a CA (DigiCert, Symantec, GeoTrust), pay $50–$500, wait 1–7 days for validation, receive the cert by email, install it manually on the server. The result: most websites did not use HTTPS because it was expensive and operationally painful. The CA/Browser Forum's push for HTTPS-everywhere was blocked by the operational cost.

The **Automated Certificate Management Environment (ACME)** protocol (RFC 8555, 2019) changed this. ACME is an HTTPS-based API that lets a client (like `certbot`) automatically: prove control of a domain, request a certificate, receive the signed certificate, and renew it before expiry — all without human intervention. **Let's Encrypt**, launched in April 2015 by the Internet Security Research Group (ISRG), was the first CA to offer ACME. As of 2024, Let's Encrypt has issued over 3 billion certificates and powers ~50% of all HTTPS websites.

The ACME flow has four phases:

```text
1. Account registration:
   Client → ACME server: POST /acme/new-account
     { contact: ["mailto:admin@example.com"],
       termsOfServiceAgreed: true,
       publicKey: <client's account key> }
   Server → Client: 200 OK
     { status: "valid", orders: ".../orders" }

2. Order placement:
   Client → ACME server: POST /acme/new-order
     { identifiers: [{ type: "dns", value: "example.com" },
                     { type: "dns", value: "www.example.com" }] }
   Server → Client: 201 Created
     { status: "pending",
       authorizations: [".../authz/123", ".../authz/124"],
       finalize: ".../order/123/finalize" }

3. Domain validation (the "challenge"):
   For each authorization, the server offers challenges:
     - dns-01: prove control by creating a TXT record
         _acme-challenge.example.com. TXT <token>
     - http-01: prove control by serving a file at a known URL
         http://example.com/.well-known/acme-challenge/<token>
     - tls-alpn-01: prove control by serving a self-signed cert with the token
         (uses the tls-alpn extension on port 443)

   Client completes one challenge → tells the server → server verifies →
   authorization status becomes "valid".

4. Certificate issuance:
   Client → ACME server: POST /acme/order/123/finalize
     { csr: <CSR signed by client's private key> }
   Server → Client: 200 OK with the issued certificate (PEM chain).
```

```bash
# Issue a Let's Encrypt certificate with certbot (the canonical ACME client)
sudo certbot certonly --webroot -w /var/www/html -d example.com -d www.example.com

# Or with the DNS challenge (works behind firewalls, for wildcards)
sudo certbot certonly --dns-cloudflare --dns-cloudflare-credentials ~/.secrets/cloudflare.ini \
    -d example.com -d '*.example.com'

# Or with the standalone mode (certbot runs its own HTTP server on port 80)
sudo certbot certonly --standalone -d example.com

# Set up automatic renewal (certbot installs a systemd timer by default)
sudo systemctl status certbot.timer
sudo certbot renew --dry-run   # test the renewal without actually renewing

# Verify the cert was issued correctly
openssl x509 -in /etc/letsencrypt/live/example.com/cert.pem -noout -text | grep -E 'Subject:|Not After|DNS:'
```

The implications for backend engineering are profound:
- **No more "the cert expired and the site went down"** incidents — ACME clients renew automatically 30 days before expiry.
- **No more "I forgot to install the intermediate"** — ACME clients install the full chain.
- **No more "$300 per year per domain"** cost — Let's Encrypt is free.
- **No more manual CSR generation** — the ACME client generates the key, the CSR, and installs the cert.

The production failure mode tied to ACME is **the renewal that fails silently**. certbot's systemd timer runs `certbot renew` twice a day, but if the renewal fails (the challenge cannot be completed because port 80 is blocked, or the DNS API token expired, or the ACME account key was lost), the cert will eventually expire and the site will go down. The fix is to monitor certbot's exit code and alert on any non-zero status, plus to set up external monitoring of certificate expiry (UptimeRobot, Prometheus's `blackbox_exporter`'s `ssl_cert_expiry` probe). The recurring symptom is "the cert expired over the weekend and nobody noticed until Monday morning when customers complained".

## How This Connects to the Frameworks

Every framework in section 05 terminates TLS in production, and the framework's responsibility is to load the certificate and key files and present them during the handshake:

- **Spring Boot**: `server.ssl.key-store=classpath:keystore.p12`, `server.ssl.key-store-password=...`. Or use a sidecar (Envoy, Linkerd) to terminate TLS and forward plain HTTP to Spring Boot.
- **Express/Node.js**: `https.createServer({ key: fs.readFileSync('key.pem'), cert: fs.readFileSync('cert.pem') })`. Use `greenlock-express` for automatic Let's Encrypt integration.
- **Python/Django**: typically run behind nginx (which terminates TLS) or use `daphne --endpoint ssl:443:privateKey=key.pem:certKey=cert.pem`.
- **PHP/Laravel**: terminate TLS at nginx/Apache, forward plain HTTP to PHP-FPM.

In all cases, the framework does not implement cryptography — it loads the cert and key files and hands them to the runtime's TLS implementation (JSSE for Java, OpenSSL for Node/Python/PHP). The framework's job is configuration: pointing at the right files, setting the right cipher list, enabling OCSP stapling, and integrating with cert-manager (Kubernetes) or certbot (bare Linux) for automated renewal.

If any of these steps fails — the cert is expired, the SAN does not match, the intermediate is missing, OCSP is not stapling — the failure surfaces as a browser warning, an API call failure, or a security audit finding. Knowing which layer caused the failure is the difference between a 5-minute fix and a 5-hour incident.

## Hands-On Exercise

```bash
# Inspect a website's certificate chain
openssl s_client -connect example.com:443 -servername example.com -showcerts < /dev/null 2>&1 | grep -E '^(s|i):'

# View the full X.509 structure of a leaf certificate
openssl s_client -connect example.com:443 -servername example.com < /dev/null 2>/dev/null | openssl x509 -noout -text

# Check the SAN list (the authoritative list of domains this cert covers)
echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null | \
  openssl x509 -noout -ext subjectAltName

# Check OCSP stapling
openssl s_client -connect example.com:443 -servername example.com -status < /dev/null 2>&1 | grep -i 'ocsp\|status'

# Verify a certificate chain locally
openssl verify -CAfile /etc/ssl/certs/ca-certificates.crt -untrusted intermediate.pem cert.pem

# Issue a Let's Encrypt certificate with certbot
sudo certbot certonly --webroot -w /var/www/html -d example.com
sudo certbot renew --dry-run

# Check the Certificate Transparency log entries for a cert
# (every public CA cert must be logged to at least 2 CT logs since 2018)
curl -s "https://crt.sh/?q=example.com&output=json" | jq '.[] | {issuer_name, not_before, not_after}' | head -20

# Monitor certbot renewal failures (production hygiene)
journalctl -u certbot.service --since "1 day ago" | grep -i error
```
