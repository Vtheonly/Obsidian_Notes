# 03.05.03. gRPC Framework Architecture

## What This Is

gRPC (Google, 2015, open-sourced 2016) is a typed RPC framework built on HTTP/2 (RFC 7540) and Protocol Buffers (see [[03.05.02. Protocol Buffers Internals]]). A `.proto` file declares the service contract — methods, request/response types, streaming modes — and the `protoc` compiler generates a typed client stub and server interface in your target language. Every gRPC call is an HTTP/2 POST to a URL of the form `/{package}.{ServiceName}/{MethodName}` with a protobuf body. The framework handles connection management, deadline propagation, status codes, interceptors, retries, and load balancing — concerns that every RPC framework must solve but that gRPC solves uniformly across 11+ languages.

This note sits between the wire-format details in [[03.05.01. Data Serialization Formats Compared]] and [[03.05.02. Protocol Buffers Internals]] (which cover the serialization layer) and the framework-level service abstractions of section 05 (Spring `@GrpcService`, Express grpc-js, Django grpcio, Laravel grpc PHP extension). The five H3s below cover: the HTTP/2 transport substrate, the four RPC modes, metadata/deadlines/interceptors, the 17 status codes, and the code-generation toolchain. gRPC has become the default for service-to-service communication in microservices at Google, Netflix, Uber, Slack, Dropbox, and most CNCF projects — the trade-off versus REST+JSON is better performance and type safety, at the cost of requiring code generation and a protobuf-aware debugging toolchain (`grpcurl` instead of `curl`).

## The Details

### Transport substrate: gRPC over HTTP/2 (Multiplexing, binary framing, streaming)

gRPC is built directly on HTTP/2 (RFC 7540, May 2015). Every gRPC call is an HTTP/2 POST request to a URL like `/com.example.users.v1.UserService/GetUser`. The request body is a length-prefixed protobuf message; the response body is a length-prefixed protobuf message. The protobuf bytes are the entire body — there is no JSON, no form-encoding, no multipart wrapping. The HTTP/2 framing layer (DATA, HEADERS, SETTINGS, RST_STREAM, GOAWAY frames) carries the protobuf bytes between client and server.

```text
gRPC request (visible on the wire as HTTP/2 frames):

  :method  = POST
  :path    = /com.example.users.v1.UserService/GetUser
  :scheme  = https
  :authority = users.service.internal
  content-type = application/grpc
  te = trailers                              (gRPC requires trailers)
  grpc-timeout = 5S                          (5-second deadline)
  grpc-encoding = gzip                       (optional compression)
  grpc-accept-encoding = identity, gzip, deflate
  user-agent = grpc-node/1.24.11 grpc-c/8.0.0

  body (5-byte prefix + protobuf payload):
    00 00 00 00 07 0A 03 61 6C 69
    │  │  │  │  └─── protobuf bytes (GetUserRequest{id:"ali"})
    │  │  │  └── 7-byte payload length (big-endian uint32)
    │  └── 3 bytes of length high bits (here all zero)
    └── compressed-flag byte (0 = not compressed, 1 = compressed)
```

The 5-byte prefix on every message (1 byte compressed-flag + 4 bytes big-endian length) is the gRPC length-prefixed framing on top of HTTP/2. This lets a single HTTP/2 stream carry multiple messages — essential for streaming RPCs where the receiver reads the 5-byte prefix, knows the next message is N bytes, reads them, then reads the next 5-byte prefix for the following message. Without this prefix, the receiver would not know where one protobuf message ends and the next begins (protobuf does not self-delimit).

HTTP/2's contribution to gRPC is **multiplexing**: a single TCP connection carries hundreds of concurrent RPCs as independent streams. Each stream has a 31-bit stream ID (odd for client-initiated, even for server-initiated via PUSH_PROMISE). Streams are not blocked by each other — if RPC #5 is slow (long database query), RPCs #6, #7, #8 still flow on the same connection. This eliminates the HTTP/1.1 connection-pool problem, where you needed N concurrent TCP connections to get N concurrent requests, each consuming kernel memory (`struct sock` ~2 KB + 64 KB receive buffer + 16 KB send buffer = ~80 KB per connection at default `sysctl` settings) and TLS state (~50 KB per connection for the session cache and key material).

```text
HTTP/1.1: 100 concurrent RPCs = 100 TCP connections = 100 TLS handshakes
                              = ~8 MB of kernel memory just for sockets
HTTP/2:   100 concurrent RPCs = 1 TCP connection = 1 TLS handshake + 100 streams
                              = ~80 KB of kernel memory + 100 stream state objects
```

HTTP/2's HPACK header compression (RFC 7541) reduces the per-RPC header overhead from ~800 bytes (HTTP/1.1 with full headers) to ~30–50 bytes after the first few requests warm up the dynamic table. For a high-QPS internal service doing 50,000 RPCs/sec, this saves ~40 MB/sec of bandwidth — real money at AWS egress pricing ($0.09/GB). HPACK works by maintaining a static table of 61 common headers (`:method=POST`, `:path=/...`, `content-type=application/grpc`, etc.) and a dynamic table per connection that caches previously seen header values; only the differences from the table are sent on the wire.

The remaining head-of-line blocking is at the TCP layer: if a single packet is lost, the kernel blocks all HTTP/2 streams on that connection until the lost packet is retransmitted (TCP guarantees in-order delivery). On a clean datacenter network (<0.01% packet loss), this is invisible. On a lossy mobile network or cross-region link (1% packet loss), it can throttle throughput by 30–50%. HTTP/3 (over QUIC, RFC 9000, 2021) solves this by running each stream over its own reliability layer — but gRPC-over-HTTP/3 is not yet widely deployed. The de-facto production reality is gRPC over HTTP/2 over TCP, with all the limitations that implies at the transport layer.

### The four communication modes: Unary RPC, Server Streaming RPC, Client Streaming RPC, an...

gRPC defines four RPC types, declared in the `.proto` file by the presence or absence of the `stream` keyword on the request and response types. The four modes exist because they map to fundamentally different communication patterns, and forcing everything into unary (the way REST does) wastes either latency (round-tripping each message) or bandwidth (packing many small messages into one big one).

```protobuf
service UserService {
  // Unary: 1 request → 1 response (like a normal HTTP REST call)
  rpc GetUser(GetUserRequest) returns (User);

  // Server streaming: 1 request → stream of responses
  rpc ListUsers(ListUsersRequest) returns (stream User);

  // Client streaming: stream of requests → 1 response
  rpc UploadUsers(stream User) returns (UploadSummary);

  // Bidirectional streaming: stream ↔ stream
  rpc Chat(stream ChatMessage) returns (stream ChatMessage);
}
```

| RPC Type | Request | Response | Typical Use Case |
|---|---|---|---|
| Unary | 1 message | 1 message | CRUD operations, simple lookups (the 95% case) |
| Server streaming | 1 message | N messages | Pagination, log tails, live feeds (stock ticks), file download |
| Client streaming | N messages | 1 message | Bulk upload, aggregations (compute average of N values) |
| Bidirectional | N messages | N messages | Chat, multiplayer games, interactive shells, replication logs |

```text
Unary RPC timeline (1 req → 1 resp):
  Client ──┐
           │ HEADERS (req) ────────────────────► Server
           │ DATA (msg) ──────────────────────►
           │                                   (server processes)
           │ ◄──────────────── DATA (resp) ────
           │ ◄──────────────── HEADERS (trailers, status=OK)
  Done.

Server streaming timeline (1 req → N resp):
  Client ──┐
           │ HEADERS ──────────────────────────► Server
           │ DATA (req) ──────────────────────►
           │                                   (server starts query)
           │ ◄──────────────── DATA (resp 1) ──
           │ ◄──────────────── DATA (resp 2) ──
           │ ◄──────────────── DATA (resp 3) ──
           │ ◄──────────────── HEADERS (trailers, status=OK)
  Done.

Bidirectional streaming timeline (N req ↔ N resp):
  Client ──┐
           │ HEADERS (open stream) ────────────► Server
           │ DATA (msg A) ────────────────────►
           │ ◄──────────────── DATA (msg X) ───
           │ DATA (msg B) ────────────────────►
           │ DATA (msg C) ────────────────────►
           │ ◄──────────────── DATA (msg Y) ───
           │ ◄──────────────── DATA (msg Z) ───
           │ DATA (END_STREAM) ───────────────►
           │ ◄──────────────── HEADERS (trailers)
  Done.
```

Server streaming lets the server push updates without the client polling. Client streaming lets the client upload thousands of records without waiting for per-record ACKs — the server processes them as they arrive and returns a single summary at the end. Bidirectional streaming lets both sides push independently — essential for chat, where the client typing "hello" and the server pushing "user joined" should not be sequenced through a request/response cycle.

The generated client stub exposes each mode differently. In Java (grpc-java), there are three stub flavors: `BlockingStub` (synchronous, only unary and server-streaming-as-iterator), `FutureStub` (returns `ListenableFuture`, only unary), and `Stub` (fully async, supports all four modes via `StreamObserver`):

```java
UserServiceGrpc.UserServiceBlockingStub blocking = UserServiceGrpc.newBlockingStub(channel);
UserServiceGrpc.UserServiceFutureStub future = UserServiceGrpc.newFutureStub(channel);
UserServiceGrpc.UserServiceStub async = UserServiceGrpc.newStub(channel);

// Unary — blocking
User u = blocking.getUser(GetUserRequest.newBuilder().setId(42).build());

// Unary — async (ListenableFuture)
ListenableFuture<User> f = future.getUser(req);

// Server streaming — only available on async stub (or as blocking Iterator)
Iterator<User> it = blocking.listUsers(req);  // blocking iterator
async.listUsers(req, new StreamObserver<>() {
  public void onNext(User u) { /* handle each user */ }
  public void onError(Throwable t) { /* handle failure */ }
  public void onCompleted() { /* stream done */ }
});

// Bidirectional — only async, uses two StreamObservers (in and out)
StreamObserver<ChatMessage> out = async.chat(new StreamObserver<>() {
  public void onNext(ChatMessage m) { /* incoming message */ }
  public void onError(Throwable t) { /* */ }
  public void onCompleted() { /* server closed stream */ }
});
out.onNext(ChatMessage.newBuilder().setText("hello").build());
out.onCompleted();  // client closes its side
```

Production failure mode: a team uses server streaming for a "list users" endpoint that returns 100,000 records. The server streams them all in one RPC without any flow control, the client buffers them in memory, and the JVM OOMs at record 80,000. The fix is to use the `StreamObserver` flow-control API (`onNext` blocks when the HTTP/2 flow-control window is full, applying backpressure to the server) or to add pagination at the application level. Streaming is not a free lunch — it shifts memory pressure from the network layer to the application layer, and the client must consume messages as fast as the server produces them or apply backpressure.

### gRPC metadata, context cancellation, deadlines, and distributed timeout propagation

gRPC metadata is HTTP/2 headers, sent as part of the request or response. Custom metadata uses lowercase ASCII keys (HTTP/2 requires lowercase header names); the `grpc-` prefix is reserved for gRPC-defined headers (`grpc-timeout`, `grpc-encoding`, `grpc-status`, `grpc-message`). User-defined metadata travels with every RPC and is how clients and servers exchange out-of-band information: trace IDs (`traceparent`, W3C Trace Context), authentication tokens (`authorization: Bearer ...`), request IDs (`x-request-id`), tenant IDs, ABAC context.

The `grpc-timeout` header is a first-class citizen — it carries the deadline as a header value like `5S` (5 seconds), `100m` (100 milliseconds), `2H` (2 hours), `500u` (500 microseconds). The format is `<value><unit>` where unit is one of `H` (hour), `M` (minute), `S` (second), `m` (millisecond), `u` (microsecond), `n` (nanosecond). Deadlines in gRPC are not advisory — they are enforced. If the server does not respond within the deadline, the client cancels the RPC (sends an HTTP/2 `RST_STREAM` frame), the server receives a cancellation signal on its `Context`, and the server's handler should abort whatever it is doing.

```java
// Client side: set a 500ms deadline and attach metadata
Metadata metadata = new Metadata();
metadata.put(Metadata.Key.of("x-request-id", Metadata.ASCII_STRING_MARSHALLER),
             UUID.randomUUID().toString());
metadata.put(Metadata.Key.of("authorization", Metadata.ASCII_STRING_MARSHALLER),
             "Bearer " + token);

User u = UserServiceGrpc.newBlockingStub(channel)
    .withDeadlineAfter(500, TimeUnit.MILLISECONDS)
    .withCallCredentials(...)
    .getUser(request);
```

The difference from HTTP/1.1 REST is stark: in REST, a client-side timeout just closes the socket, and the server keeps doing the work (wasted CPU and database load); in gRPC, the cancellation propagates and the server can stop early. The cancellation signal travels through the `Context` object — `io.grpc.Context` in Java, `context.Context` in Go, `grpc.RpcContext` in Python — and is checked by every well-behaved downstream operation: database drivers (`PQcancel` in libpq, `KILL QUERY` in MySQL), HTTP clients (the `Context` cancels the in-flight request), downstream gRPC calls (the deadline is propagated as a `grpc-timeout` header on the outbound call).

```text
Distributed deadline propagation across a call graph:

  Client (deadline: 5s) ──► Service A ──► Service B ──► Service C
  t=0:    5s remaining     5s remaining  5s remaining  5s remaining
  t=2s:   3s remaining     3s remaining  3s remaining  3s remaining
  t=4s:   1s remaining     1s remaining  1s remaining  1s remaining
  t=5s:   CANCELLED        CANCELLED     CANCELLED     CANCELLED
                         (DEADLINE_EXCEEDED status code 4)
```

The propagation works because the gRPC client library automatically sets the `grpc-timeout` header on outgoing RPCs to `original_deadline - elapsed_time`. When Service A makes an outbound call to Service B at t=2s, the deadline it sends is 3s — not the original 5s. This means a slow upstream call cannot consume time that should belong to a downstream call. Without this propagation, a service at the top of a chain with a 5s deadline would call a downstream with a 30s timeout, the downstream would burn 25s of CPU on a result nobody will see, and the system would cascade into overload.

```go
// Go server side: respect the client deadline
func (s *server) GetUser(ctx context.Context, req *pb.GetUserRequest) (*pb.User, error) {
    select {
    case <-ctx.Done():
        return nil, ctx.Err()  // context.DeadlineExceeded or context.Canceled
    default:
    }
    user, err := s.db.GetUser(ctx, req.Id)  // pass ctx to Postgres driver
    if err != nil {
        return nil, status.Errorf(codes.Internal, "db error: %v", err)
    }
    return user, nil
}
```

**Interceptors** are the cross-cutting-concern mechanism. A client interceptor wraps every outbound RPC; a server interceptor wraps every inbound RPC. Use them for: tracing (inject/extract `traceparent` W3C header), metrics (record RPC duration per method), auth (validate JWT in `authorization` header), retry (with backoff and circuit breaker), logging, rate limiting. The Spring gRPC starter provides `@GrpcGlobalServerInterceptor` annotations for declarative interceptor registration. Express uses middleware-style interceptor chains. Python decorators serve the same role.

Production failure mode: a service calls a downstream service with a 30s timeout but no deadline propagation. The upstream client has a 5s deadline. At t=4s, the upstream call hits the downstream, which has 30s of budget. The downstream completes at t=20s. The upstream caller has long since given up (5s deadline expired at t=5s), but the downstream still spent 16s of CPU and a database query on a result nobody will see. Multiply by 1000 RPS and you have wasted 16,000 CPU-seconds per second — the equivalent of 16 idle cores doing nothing but discard work. Always propagate deadlines; never set downstream timeouts longer than the upstream deadline minus elapsed time.

### Error handling: Standard gRPC status codes (`OK`, `NOT_FOUND`, `UNAVAILABLE`, etc.) and...

gRPC defines 17 status codes (compared to HTTP's 41 in RFC 9110, though in practice REST APIs use only ~8). The codes are deliberately smaller and more semantic — they describe the failure mode in RPC terms rather than HTTP terms. Every gRPC response includes a status code in the trailers (`grpc-status` header) and an optional status message (`grpc-message`).

| Code | Number | Meaning | HTTP Equivalent | Retryable? |
|---|---|---|---|---|
| OK | 0 | Success | 200 | n/a |
| CANCELLED | 1 | Client cancelled (deadline, explicit cancel) | (none) | No |
| UNKNOWN | 2 | Server panic / unhandled exception | 500 | Maybe |
| INVALID_ARGUMENT | 3 | Bad request payload (client bug) | 400 | No |
| DEADLINE_EXCEEDED | 4 | Timeout (client or server) | 504 | Maybe |
| NOT_FOUND | 5 | Resource doesn't exist | 404 | No |
| ALREADY_EXISTS | 6 | Resource conflict (create conflict) | 409 | No |
| PERMISSION_DENIED | 7 | Authenticated but forbidden | 403 | No |
| RESOURCE_EXHAUSTED | 8 | Quota / rate limit exceeded | 429 | Yes (with backoff) |
| FAILED_PRECONDITION | 9 | App state wrong (e.g., file not empty) | 400 | No |
| ABORTED | 10 | Transaction conflict, retry | 409 | Yes |
| OUT_OF_RANGE | 11 | Value out of bounds | 400 | No |
| UNIMPLEMENTED | 12 | Method not implemented | 501 | No |
| INTERNAL | 13 | Internal bug (server crash) | 500 | No |
| UNAVAILABLE | 14 | Service down (transient) | 503 | Yes (with backoff) |
| DATA_LOSS | 15 | Unrecoverable data loss | 500 | No |
| UNAUTHENTICATED | 16 | No valid credentials | 401 | No |

```java
// Server side: return a typed error
public User getUser(GetUserRequest req) {
    if (req.getId() <= 0) {
        throw Status.INVALID_ARGUMENT
            .withDescription("id must be positive, got " + req.getId())
            .asRuntimeException();
    }
    User u = db.find(req.getId());
    if (u == null) {
        throw Status.NOT_FOUND
            .withDescription("user " + req.getId() + " not found")
            .asRuntimeException();
    }
    if (!req.getAuthToken().hasPermission("read:user")) {
        throw Status.PERMISSION_DENIED
            .withDescription("token lacks read:user scope")
            .asRuntimeException();
    }
    return u;
}

// Client side: switch on status code
try {
    User u = blocking.getUser(req);
} catch (StatusRuntimeException e) {
    switch (e.getStatus().getCode()) {
        case NOT_FOUND:        return ResponseEntity.status(404).body("not found");
        case INVALID_ARGUMENT: return ResponseEntity.badRequest().body(e.getMessage());
        case PERMISSION_DENIED: return ResponseEntity.status(403).body(e.getMessage());
        case UNAVAILABLE:      // retry with exponential backoff + jitter
                               return retryWithBackoff(() -> blocking.getUser(req));
        case DEADLINE_EXCEEDED: return ResponseEntity.status(504).body("upstream timeout");
        default:               return ResponseEntity.status(500).body("internal error");
    }
}
```

**Rich error model**: gRPC also supports attaching a structured `google.rpc.Status` proto to the error, carrying multiple `ErrorInfo` details. This lets a server return `INVALID_ARGUMENT` with a list of every field that was invalid, each with its own error code and metadata. The catch: not every language's gRPC library exposes this uniformly — Java and Go support it well, Python and Ruby less so. If you target cross-language clients, stick to the status code + message string. If your clients are all Java/Go, the rich error model is worth the investment for field-level validation errors.

```protobuf
import "google/rpc/error_details.proto";

// Server attaches rich details to the error:
status {
  code: INVALID_ARGUMENT
  message: "multiple field errors"
  details [
    { @type: "google.rpc.BadRequest"
      field_violations: [
        { field: "email", description: "already in use" },
        { field: "age",   description: "must be >= 18" },
        { field: "username", description: "contains invalid characters" }
      ]
    }
  ]
}
```

**Retry policy**: gRPC has built-in retry for `UNAVAILABLE` and `RESOURCE_EXHAUSTED` (configurable via a service config JSON, served by the name resolver or baked into the client). The default is no retry — you must opt in. The retry policy respects `grpc-retry-pushback-ms` (server tells client how long to wait before retrying, useful for rate-limit backoff) and supports hedging (sending a second request if the first hasn't responded within a threshold, racing them — useful for tail-latency reduction). For idempotent RPCs (GET-style), retries are safe; for non-idempotent RPCs (POST-style mutations like `CreateUser`), retries are dangerous and should be off by default. The `google.api.http` annotation in your `.proto` can declare idempotency for the grpc-gateway transcoder.

Production failure mode: a team maps every gRPC error to HTTP 500 in their grpc-gateway or REST proxy. Clients see "500 Internal Error" for `NOT_FOUND`, `INVALID_ARGUMENT`, and `UNAUTHENTICATED` — losing all the semantic information gRPC provides. The fix is the grpc-gateway project (or Envoy's gRPC-JSON transcoder), which maps gRPC codes to HTTP status codes per the table above. Another failure: a service treats `UNAVAILABLE` as fatal and surfaces it to the user, when it should retry with backoff (the upstream is restarting, will be back in 2s). Know the codes; the difference between `UNAVAILABLE` (retry) and `INTERNAL` (don't retry) is the difference between a self-healing system and a cascade failure.

### Code generation toolchains: `protoc` compiler plugins for Java, TypeScript, Python, and...

The `protoc` compiler is the canonical protobuf code generator. It is a C++ binary distributed by Google, available on most package managers (`apt install protobuf-compiler`, `brew install protobuf`, `choco install protoc`). It reads `.proto` files and emits language-specific code via plugins: `--java_out`, `--python_out`, `--go_out`, `--js_out`, `--php_out`, `--ruby_out`, `--csharp_out`, `--objc_out`, `--rust_out` (community). For gRPC, the `grpc_*_plugin` adds the service stubs: `--grpc_out` with `--plugin=protoc-gen-grpc=/path/to/grpc_java_plugin`.

```bash
# Generate Java + TypeScript code from a .proto file
protoc \
  --proto_path=./protos \
  --java_out=./java/src/main/java \
  --grpc_out=./java/src/main/java \
  --plugin=protoc-gen-grpc=/usr/bin/grpc_java_plugin \
  --js_out=import_style=commonjs,binary:./ts/src/generated \
  --grpc_out=./ts/src/generated \
  --plugin=protoc-gen-grpc=/usr/bin/grpc_node_plugin \
  --ts_out=./ts/src/generated \
  --plugin=protoc-gen-ts=./node_modules/.bin/protoc-gen-ts \
  ./protos/users/v1/users.proto
```

This is painful. Modern projects use build-tool plugins that hide `protoc`:

- **Java (Maven)**: `protobuf-maven-plugin` + `os-maven-plugin` (auto-detects OS/arch for the right `protoc` binary). Configures `protoc` binary download, runs `protoc` at the `generate-sources` phase, compiles generated code with the project.
- **Java (Gradle)**: `com.google.protobuf` plugin.
- **TypeScript/Node**: `grpc-tools` (npm package, bundles `protoc` for the host platform) + `ts-protoc-gen` for TypeScript types. Or `buf generate` with a `buf.gen.yaml`.
- **Python**: `grpcio-tools` package — `python -m grpc_tools.protoc -I./protos --python_out=./gen --grpc_python_out=./gen ./protos/users/v1/users.proto`.
- **Go**: `protoc-gen-go` + `protoc-gen-go-grpc` (or `buf` with remote plugins).
- **PHP**: `grpc_php_plugin` (generates a single `UsersServiceClient.php` file per service; PHP's lack of generics makes the generated code verbose).

The newer tool is **Buf** (`buf.build`), which replaces both `protoc` and the plugin management. Buf is faster (parallelized, cached, remote plugin execution), validates `.proto` files against best practices (the Buf lint rules — naming conventions, comments required, no `import public`), and manages breaking-change detection (`buf breaking` compares against a git remote or a Buf Schema Registry image). It uses a `buf.gen.yaml` file:

```yaml
# buf.gen.yaml
version: v1
plugins:
  - plugin: buf.build/protocolbuffers/java
    out: ./java/src/main/java
  - plugin: buf.build/grpc/java
    out: ./java/src/main/java
  - plugin: buf.build/protocolbuffers/go
    out: ./go/gen
    opt: paths=source_relative
  - plugin: buf.build/grpc/go
    out: ./go/gen
    opt: paths=source_relative
  - plugin: buf.build/bufbuild/es
    out: ./ts/src/gen
  - plugin: buf.build/connectrpc/es
    out: ./ts/src/gen
```

The generated code is always the same shape across languages: a `Stub` (client) for the service, a `Servicer` (server) base class to implement, and `Message` classes for each proto message. The client stub hides HTTP/2 entirely — you call `getUser(req)` and get back a `User` (or a Future, or a Stream, depending on language and RPC mode). The server stub provides an interface you implement.

```typescript
// Generated TypeScript client (using Connect-ES)
import { createClient } from "@connectrpc/connect";
import { UserService } from "./users/v1/users_pb";
import { createGrpcTransport } from "@connectrpc/connect-node";

const transport = createGrpcTransport({
  baseUrl: "https://users.internal:443",
  httpVersion: "2",
});
const client = createClient(UserService, transport);

const user = await client.getUser({ id: 42 });
console.log("user:", user.email);
```

```python
# Generated Python server (using grpcio)
import grpc
from concurrent import futures
from users.v1 import users_pb2_grpc, users_pb2

class UserService(users_pb2_grpc.UserServiceServicer):
    def GetUser(self, request, context):
        user = db.find(request.id)
        if user is None:
            context.abort(grpc.StatusCode.NOT_FOUND, f"user {request.id} not found")
        return users_pb2.User(id=user.id, email=user.email)

server = grpc.server(futures.ThreadPoolExecutor(max_workers=10))
users_pb2_grpc.add_UserServiceServicer_to_server(UserService(), server)
server.add_insecure_port("[::]:50051")
server.start()
server.wait_for_termination()
```

Why gRPC dominates microservice-to-service communication: (1) the schema is the contract, enforced at compile time — no "did you read the API docs?" failures; (2) HTTP/2 multiplexing eliminates the connection-pool tuning problem; (3) deadline propagation and cancellation prevent cascading slow-downs during partial failures; (4) code generation eliminates boilerplate HTTP client code; (5) the 17 status codes are more semantic than HTTP's overloaded 4xx/5xx; (6) cross-language support is uniform (a Go service calls a Java service calls a Python service — all from the same `.proto`); (7) interceptors provide a clean cross-cutting-concern model. The trade-off: browsers cannot speak gRPC natively (HTTP/2 trailers are not exposed to the Fetch API), so you need grpc-web (a JavaScript shim) or a REST gateway (grpc-gateway, Envoy gRPC-JSON transcoder) for browser-facing APIs. The trade-off is worth it for internal traffic.

Production failure mode: a team adopts gRPC without investing in code-generation tooling. Every developer runs `protoc` by hand with different flags; the generated code is checked into git inconsistently; PRs show massive diffs in generated code that obscure the actual change; CI doesn't regenerate so staging has stale stubs; one service uses proto3 v3.12, another uses v3.19, and the wire format subtly differs. The fix is to commit to either `buf generate` (modern, recommended) or the Maven/Gradle plugin (traditional), never commit generated code to git (or always commit it, but be consistent), and run `buf breaking` in CI to catch schema-incompatible changes before they ship. The other failure: teams new to gRPC forget to enable retries and circuit breakers — the gRPC client default is "no retry, no circuit breaker", so a slow upstream cascades into client thread-pool exhaustion. Configure the service config JSON with retry policies for `UNAVAILABLE` and `RESOURCE_EXHAUSTED` on day one.

## How This Connects to the Frameworks

Every framework in section 05 has a gRPC integration, with varying levels of polish. Spring Boot 3.4+ ships `spring-grpc` (GA in 2024) which auto-configures the gRPC server on port 9090 (configurable), exposes `@GrpcService` beans, and integrates with Spring's `@Transactional` and security stack. Older Spring versions use `grpc-spring-boot-starter` (LogNet/yidongnan). Express/Node uses `@grpc/grpc-js` (the C++-backed production client) or `@connectrpc/connect` (the pure-TypeScript, browser-compatible alternative). Django and Flask use `grpcio` (the C-based Python library that uses cygrpc under the hood); Django Channels can serve gRPC over ASGI but the threading model prefers the synchronous `grpc.server(futures.ThreadPoolExecutor(...))` pattern. Laravel uses the `grpc` PHP extension (C-based) plus `grpc_php_plugin` for code generation; PHP-FPM's request lifecycle makes long-lived gRPC servers unusual — the typical pattern is a Laravel console command running ReactPHP or Swoole, not a PHP-FPM endpoint. The interceptors in each framework align with the framework's middleware/aspect model: Spring uses `@GrpcGlobalServerInterceptor`, Express uses middleware chains, Django uses decorators, Laravel uses service providers. The gRPC contract (the `.proto` file) is the same in all four; only the language bindings differ.

## Hands-On Exercise

```bash
# 1. Install protoc, the gRPC plugin, and a language runtime
apt install protobuf-compiler
pip install grpcio grpcio-tools
# Or: npm install @grpc/grpc-js @grpc/proto-loader grpc-tools

# 2. Write a .proto with all four RPC modes
cat > user.proto <<'EOF'
syntax = "proto3";
package demo.v1;
service UserService {
  rpc GetUser(GetUserRequest) returns (User);
  rpc ListUsers(ListUsersRequest) returns (stream User);
  rpc UploadUsers(stream User) returns (UploadSummary);
  rpc Chat(stream ChatMessage) returns (stream ChatMessage);
}
message GetUserRequest { int64 id = 1; }
message User { int64 id = 1; string email = 2; }
message ListUsersRequest { int32 page_size = 1; }
message UploadSummary { int32 count = 1; }
message ChatMessage { string text = 1; }
EOF

# 3. Generate Python stubs
python -m grpc_tools.protoc -I. --python_out=. --grpc_python_out=. user.proto

# 4. Inspect a real gRPC call with grpcurl (the curl for gRPC)
grpcurl -plaintext -d '{"id": 42}' localhost:50051 demo.v1.UserService/GetUser
# List all services: grpcurl -plaintext localhost:50051 list
# Describe a service:  grpcurl -plaintext localhost:50051 describe demo.v1.UserService

# 5. Capture the HTTP/2 frames with tcpdump
sudo tcpdump -i lo -A 'tcp port 50051' | grep -E 'POST|/demo.v1|HTTP/2'
# Or use nghttp2: nghttp -v -H 'content-type: application/grpc' http://localhost:50051/demo.v1.UserService/GetUser

# 6. Test deadline propagation
# Client: deadline = 100ms
# Server: sleep(500ms) before responding
# Expected: client receives DEADLINE_EXCEEDED at 100ms, server receives cancellation.

# 7. Test the four RPC modes
# Unary:        grpcurl -d '{"id":42}' .../GetUser
# Server stream: grpcurl -d '{"page_size":10}' .../ListUsers
# Client stream: (requires a custom client — grpcurl does not support it)
# Bidi stream:   (requires a custom client)

# 8. Inspect status codes
# Server returns NOT_FOUND → grpc-status: 5
# Server returns INVALID_ARGUMENT → grpc-status: 3
# Server returns UNAVAILABLE → grpc-status: 14

# 9. Run the Buf linter and breaking-change detector
buf lint user.proto
buf breaking user.proto --against '.git#branch=main'

# 10. Test retry policy
# Configure the client to retry UNAVAILABLE with backoff:
# {
#   "methodConfig": [{
#     "name": [{ "service": "demo.v1.UserService" }],
#     "retryPolicy": {
#       "maxAttempts": 4,
#       "initialBackoff": "0.1s",
#       "maxBackoff": "1s",
#       "backoffMultiplier": 2,
#       "retryableStatusCodes": ["UNAVAILABLE"]
#     }
```
