# 03.05.01. Data Serialization Formats Compared

## What This Is

Every byte that crosses a network boundary must be serialized into bytes on the sender side and deserialized back into objects on the receiver side. The choice of serialization format governs three production-critical properties: wire size (bandwidth cost and AWS egress charges), parse speed (CPU cost per request, often the bottleneck at high QPS), and schema enforcement (whether a contract exists between sender and receiver, or whether they're trusting each other to send the right shape). The format also governs schema evolution — can you add a field without breaking old clients, or does every change require a coordinated deploy?

This note compares the seven formats you will actually encounter in production: JSON, XML, MessagePack, CBOR, BSON, Protocol Buffers, and Apache Avro (with FlatBuffers as a sidebar for zero-copy use cases). The same `{"id":42,"name":"alice","active":true}` object is encoded in each format below with concrete byte counts and parse-time measurements. The deep dive on Protocol Buffers is in [[03.05.02. Protocol Buffers Internals]] and the gRPC framework built on top of it is in [[03.05.03. gRPC Framework Architecture]]. The format sits in the same layer as the application transport protocols of section 03 — above the byte stream provided by [[02.04.03. The POSIX Socket Lifecycle]], below the framework routing and DI of section 05.

## The Details

### Textual Formats (JSON, XML): Human-readability, parsing CPU overhead, large payload foo...

JSON (JavaScript Object Notation, RFC 8259, December 2017 — though the format itself dates to Douglas Crockford's 2001 specification) is the de-facto wire format of the modern web. It is text-based, UTF-8 encoded, and supports exactly six data types: object (curly braces), array (square brackets), string (double-quoted with backslash escapes), number (IEEE 754 double-precision float — there is no distinct integer type, which is the root of countless production bugs), boolean (`true`/`false`), and `null`. Its dominance comes from being native to JavaScript (`JSON.parse` and `JSON.stringify` are in every browser's standard library) and from being human-readable: a developer can `curl` an endpoint and read the response without a decoder.

The cost of human-readability is real and quantifiable. A JSON number `1234567` is 7 ASCII bytes on the wire; the parser must read each byte, multiply the accumulated value by 10, and add the digit — roughly 50 ns per number on a modern CPU. The same integer in protobuf is a 5-byte varint parsed in ~5 ns. JSON strings carry their delimiters (`"`) and escape sequences (`\"`, `\\`, `\/`, `\b`, `\f`, `\n`, `\r`, `\t`, `\uXXXX`) — a 1 KB JSON string with 10% special characters costs 1.1 KB on the wire after escaping. Field names are repeated verbatim in every message: `{"user_id":42,"user_id":42,"user_id":42}` — three copies of the 7-character field name in a 35-byte payload. Binary formats eliminate this overhead either by encoding field names compactly (MessagePack uses a 1-byte length prefix for short strings) or by replacing them entirely with field numbers (protobuf, Avro).

```text
JSON encoding of {"id":42,"name":"alice","active":true}:

  7b 22 69 64 22 3a 34 32 2c 22 6e 61 6d 65 22 3a   {"id":42,"name":
  22 61 6c 69 63 65 22 2c 22 61 63 74 69 76 65 22   "alice","active"
  3a 74 72 75 65 7d                                  :true}

  Total: 38 bytes. Structural overhead (quotes, colons,
  commas, braces) is 16 bytes — 42% of the payload.
```

XML (eXtensible Markup Language, W3C Recommendation 1998, last revised 2008) is the older text format. It is dramatically more verbose than JSON because of its tag-closing syntax: `<user><id>42</id><name>alice</name><active>true</active></user>` is 58 bytes vs JSON's 38. XML's strengths are its schema languages (XSD for structure, DTD for entities, XSLT for transformation), its namespace support (`xmlns:foo="..."`), and its processing model (SAX for streaming, DOM for random access, XPath for querying). For backend service-to-service traffic it has been almost entirely displaced by JSON; XML survives in SOAP services (often wrapped in `application/soap+xml`), SAML assertions, SVG, OOXML, RSS/Atom feeds, Maven `pom.xml`, Spring `applicationContext.xml`, and configuration files for legacy enterprise tools.

The "lack of schema enforcement" critique is the biggest production headache with JSON. JSON itself has no schema — a server can return `{"id":42}` today and `{"id":"42"}` tomorrow, and the client's `json.loads()` succeeds on both. But `id + 1` works on the first form and throws `TypeError: can only concatenate str (not "int") to str` on the second. JSON Schema (Draft 2020-12, the latest as of 2022) exists to fill this gap, but adoption is uneven — most teams validate at the application layer using framework-specific tools (Zod in TypeScript, Pydantic in Python, Jackson `@JsonProperty` annotations in Java, Laravel FormRequest rules) rather than maintaining a separate JSON Schema file. Contract testing tools like Pact fill the gap by replaying consumer-defined expectations against the provider, but require CI integration that many teams skip.

Production failure mode: a microservice returns `{"timestamp":"2024-01-15T10:30:00Z"}` (ISO 8601 string) and the client parses it with `datetime.fromisoformat()`. Three months later, the service team switches to `{"timestamp":1705312200}` (Unix epoch int) for performance reasons, without bumping the API version or notifying consumers. Clients across the organization start throwing `TypeError` at runtime in production. The team rolls back the change, ships a new endpoint at `/v2/events` instead, and the v1 endpoint keeps returning strings forever. This is the canonical "JSON doesn't enforce schema" incident, and it has happened at every company with more than 10 services. Mitigations: contract testing (Pact, Spring Cloud Contract), JSON Schema validation at the gateway, or migrating internal traffic to a binary format with enforced schema like protobuf or Avro.

### Binary Formats (MessagePack, BSON, Protocol Buffers, FlatBuffers, Apache Avro): Compact...

Binary formats trade human-readability for compactness and parse speed. The same `{"id":42,"name":"alice","active":true}` payload, encoded in each format with concrete byte counts:

| Format | Bytes | Parse Time (relative) | Schema Required | Field Names on Wire | Schema Evolution |
|---|---|---|---|---|---|
| JSON | 38 | 1.0× | No | Yes (verbatim) | None |
| MessagePack | 21 | ~0.5× | No | Yes (verbatim) | None |
| CBOR | 22 | ~0.5× | No | Yes (verbatim) | None (deterministic encoding mode helps) |
| BSON | 27 | ~0.6× | No | Yes (null-terminated C strings) | None |
| Protocol Buffers | 11 | ~0.1× | Yes (`.proto`) | No (field numbers only) | Strict rules (add optional, never reuse) |
| FlatBuffers | 16 | ~0.0× (zero-copy) | Yes (`.fbs`) | No (offsets) | Strict rules |
| Avro | 8 | ~0.3× | Yes (`.avsc`, writer + reader) | No (resolved via schema) | Strict rules (add field with default) |

```text
Same object {"id":42,"name":"alice","active":true} in each format:

JSON:         7b 22 69 64 22 3a 34 32 ... 7d                    (38 bytes)
MessagePack:  83 a3 69 64 2a a4 6e 61 6d 65 a5 61 6c 69 63 65   (21 bytes)
              a6 61 63 74 69 76 65 c3
CBOR:         a3 63 69 64 18 2a 64 6e 61 6d 65 65 61 6c 69 63   (22 bytes)
              65 66 61 63 74 69 76 65 f5
BSON:         1b 00 00 00 10 69 64 00 2a 00 00 00 02 6e 61 6d   (27 bytes)
              65 00 06 00 00 00 61 6c 69 63 65 08 61 63 74 69
              76 65 00 01 00
Protobuf:     08 2a 12 05 61 6c 69 63 65 18 01                  (11 bytes)
Avro:         2a 0a 61 6c 69 63 65 01                            (8 bytes, single-object encoding)
```

**MessagePack** (2009, Sadayuki Furuhashi) is "JSON with binary types" — a near-drop-in replacement where every JSON value has a MessagePack equivalent. Small ints (0–127) take 1 byte; short strings (< 32 chars) have a 1-byte length prefix; binary data is sent as raw bytes rather than base64-encoded (saves 33% on binary blobs). Used by Redis internals (the RESP protocol is similar in spirit), msgpack-rpc, Fluentd, and Puppet. Parses 2–5× faster than JSON because it skips string-to-number conversion and delimiter parsing.

**CBOR** (Concise Binary Object Representation, RFC 8949, December 2020 — the successor to RFC 7049) is the IETF-standardized sibling of MessagePack. It adds 16-bit floats, decimal floats, dates, UUIDs, and bignums as first-class types, and supports "deterministic encoding" (RFC 7049 §3.1) — required for cryptographic signatures over JSON-like data, because every encoder produces identical bytes for the same logical value. Used by WebAuthn, COSE (CBOR Object Signing and Encryption), FIDO2, and the CoAP protocol (RFC 7252) for IoT.

**BSON** (Binary JSON, MongoDB's wire format) is JSON with extra types (Date, ObjectId, Binary, Regex, JavaScript code). Each document is prefixed with a 4-byte length so it can be traversed top-down without parsing every field. Larger on the wire than JSON for small documents (the length prefix and null-terminated field names add overhead), but supports in-place updates — MongoDB's `$set` operator can rewrite a single field in a 1 MB document without re-serializing the whole document, which is critical for write-heavy workloads on large documents.

**Protocol Buffers** (Google, internally since 2001, open-sourced 2008, proto3 released 2014) is schema-first: a `.proto` file defines the message, and the `protoc` compiler generates typed accessors for Java/Python/Go/C++/etc. The wire format encodes field numbers (not names), uses varints for compact ints, and supports schema evolution (add new optional fields, never reuse field numbers). See [[03.05.02. Protocol Buffers Internals]] for the full deep dive.

**FlatBuffers** (Google, 2014, originally for game development) is the zero-copy extreme: serialized data can be read without parsing. The wire format is a graph of offsets; you read field 5 by following an offset to its location, no parsing of fields 1–4 needed. Costs more to serialize than protobuf (the offset table is more complex to build) but reads are essentially free — there's no intermediate object allocation. Used in Android (the entire Android OS IPC), Facebook's `fbthrift`, and gaming (latency-critical rendering pipelines).

**Apache Avro** (Hadoop ecosystem, 2009) is schema-first like protobuf but the schema is sent with the data (in the file header, or exchanged during a wire handshake) rather than compiled into the client. This means you don't need code generation — a generic Avro reader can read any Avro data given the schema. Used in Kafka (with the Confluent Schema Registry), Hadoop file format, Apache Druid, and the Parquet+Avro stack. Schema evolution is strict: you can add fields with defaults, you can delete fields, you cannot change field types. The Schema Registry enforces backward/forward compatibility at the producer/consumer level — a producer trying to publish an incompatible schema is rejected at the registry, preventing the "JSON drift" incident at the broker level.

The dividing line is schema evolution. JSON has none — both sides guess at runtime. MessagePack/CBOR/BSON are JSON-shaped, so they inherit JSON's lack of schema (though CBOR's deterministic encoding helps with caching). Protobuf/Avro/FlatBuffers enforce schema evolution rules: you can add new optional fields, you can rename fields freely (only field numbers/positions matter), you can never change a field's type or reuse a field number. This is why they dominate service-to-service traffic in microservice architectures — schemas are contracts that the compiler enforces, and a breaking change is a compile error in every consumer of the schema.

Production failure mode: a team uses JSON internally because "it's simpler — no codegen step, no schema registry, no learning curve". They ship 50 microservices. Within a year they hit the schema-drift problem: service A returns `userId` as an int, service B expects `userId` as a string, integration tests pass because both formats are valid JSON and the test mocks use the same shape, production breaks at 03:00 when a real user with a long ID triggers the type mismatch. The migration to protobuf is painful (every service needs code generation added to its build, the `.proto` files need a central registry, debugging requires a protobuf-aware tool like `grpcurl` instead of `curl`), and the team loses two engineering quarters to the migration. The lesson: use JSON for public APIs (browser-facing, third-party integrations, webhooks) and protobuf/Avro for internal service-to-service. The investment pays back within six months at any scale above five services.

## How This Connects to the Frameworks

Every framework in section 05 has a default JSON serializer and a pluggable hook for binary formats. Spring Boot ships Jackson by default (`ObjectMapper` bean auto-configured, `@RestController` returns are serialized as JSON unless `produces = "application/x-protobuf"` is set); for protobuf, you add `protobuf-java-util` and register `ProtobufHttpMessageConverter`. Express uses the built-in `JSON.stringify` (fastest JSON parser in any runtime, thanks to V8); for protobuf, you generate TypeScript types with `ts-protoc-gen` and use `grpc-js`. Django REST Framework uses its own JSONRenderer (backed by Python's `json` module); for protobuf, you use `grpcio-tools` to generate Python stubs. Flask uses `flask.json` (which can be swapped for `orjson` for 3× faster parsing). Laravel uses `JsonResponse` and the `ext-json` PHP extension (PHP 8.1+ has a faster C implementation); for protobuf, use the `protobuf` PHP extension and `grpc_php_plugin`. The format is decoupled from the framework — the framework's job is HTTP routing and DI, the serializer is a pluggable layer below it. The choice of format should be a deliberate architectural decision, not a default inherited from the framework's tutorial.

## Hands-On Exercise

```bash
# 1. Compare wire sizes for the same object across formats
python3 -c "
import json, msgpack, cbor2, bson, struct
obj = {'id': 42, 'name': 'alice', 'active': True}
print('JSON:       ', len(json.dumps(obj)), 'bytes')
print('MessagePack:', len(msgpack.packb(obj)), 'bytes')
print('CBOR:       ', len(cbor2.dumps(obj)), 'bytes')
print('BSON:       ', len(bson.encode(obj)), 'bytes')
# Protobuf and Avro require schema; encode manually:
#   08 2a 12 05 61 6c 69 63 65 18 01  = 11 bytes (protobuf)
#   2a 0a 61 6c 69 63 65 01            = 8 bytes (Avro single-object)
"

# 2. Compare parse speed
python3 -c "
import json, msgpack, timeit
data = json.dumps({'id': 42, 'name': 'alice', 'active': True}).encode()
packed = msgpack.packb({'id': 42, 'name': 'alice', 'active': True})
print('JSON parse:       ', timeit.timeit(lambda: json.loads(data), number=100000), 's')
print('MessagePack parse:', timeit.timeit(lambda: msgpack.unpackb(packed), number=100000), 's')
"

# 3. Inspect protobuf wire bytes
echo -n '08 2a 12 05 61 6c 69 63 65 18 01' | xxd -r -p | protoc --decode_raw

# 4. Capture JSON vs protobuf traffic with tcpdump
sudo tcpdump -i lo -A 'tcp port 8080' | grep -E 'GET|POST|content-type'

# 5. Test JSON Schema validation
python3 -c "
import jsonschema
schema = {'type': 'object', 'properties': {'id': {'type': 'integer'}}, 'required': ['id']}
jsonschema.validate({'id': 42}, schema)         # passes
jsonschema.validate({'id': '42'}, schema)       # raises ValidationError
"

# 6. Reproduce the JSON schema-drift bug
#    Service A returns {'id': 42}
#    Service B returns {'id': '42'}
#    Client: print(data['id'] + 1)  # works on A, throws TypeError on B

# 7. Test Avro schema evolution
#    v1 schema: {"type":"record","name":"User","fields":[{"name":"id","type":"int"}]}
#    v2 schema: + {"name":"email","type":"string","default":""}
#    v1 reader can read v2 data (ignores email field).
#    v2 reader can read v1 data (uses default for email).

# 8. Compare HTTP/1.1 JSON vs gRPC over HTTP/2 throughput
#    Use ghz (gRPC benchmarking tool) vs wrk (HTTP/1.1 benchmarking tool)
#    ghz --concurrency=50 --total=100000 --proto=user.proto --call=UserService.GetUser
#    wrk -t 4 -c 50 -n 100000 http://localhost:8080/users/42
```
