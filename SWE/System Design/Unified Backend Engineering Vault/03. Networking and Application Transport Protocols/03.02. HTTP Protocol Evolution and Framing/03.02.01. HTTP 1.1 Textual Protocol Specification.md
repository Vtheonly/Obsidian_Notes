# 03.02.01. HTTP 1.1 Textual Protocol Specification

## What This Is

HTTP/1.1 is the textual, line-oriented protocol defined in RFC 7230–7235 (2014, obsoleting RFC 2616 from 1999). It is the protocol that every web framework in section 05 was originally built to parse, and even today — with HTTP/2 and HTTP/3 deployed on a large fraction of internet traffic — every framework still implements HTTP/1.1 because it is the *lingua franca* of the web. When you `curl` a server, when a load balancer health-checks a backend, when a microservice calls another microservice via `RestTemplate`, the request on the wire is almost always HTTP/1.1 unless both sides have explicitly negotiated something better.

This note covers the wire format of HTTP/1.1: the request line, the headers, the blank-line separator, the body, the status codes, and the header parsing rules. The framing is deliberately simple — a human can read it directly off a packet capture — but the details (the `Host` header requirement, the `Transfer-Encoding: chunked` mechanism, the `100 Continue` flow, the status code classes) are load-bearing for every production HTTP implementation.

## The Details

### The ASCII Text format: Request line (`METHOD /path HTTP/1.1`), Headers (`Key: Value\r\n`), and Message Body

HTTP/1.1 is a text protocol. A request is a sequence of ASCII lines terminated by CRLF (`\r\n`), with a blank line (`\r\n\r\n`) separating the headers from the optional body. The first line is the **request line** in the format `METHOD SP PATH SP HTTP-VERSION CRLF`. Subsequent lines are **headers** in the format `Name: SP Value CRLF`. The body, if any, follows the blank line and extends for `Content-Length` bytes (or until the chunked-stream terminator for chunked encoding).

```text
POST /api/users HTTP/1.1\r\n
Host: api.example.com\r\n
Content-Type: application/json\r\n
Content-Length: 42\r\n
Accept: application/json\r\n
User-Agent: curl/7.81.0\r\n
\r\n
{"email": "alice@example.com", "age": 30}
```

Dissecting the request line: `POST` is the method (token, no whitespace allowed), `/api/users` is the request target (the path component of the URL, plus optional query string), `HTTP/1.1` is the protocol version. The single space (`SP`) between each token is mandatory — multiple spaces are not allowed and many parsers reject them. The line ends with CRLF; bare LF (`\n`) is technically illegal but most parsers tolerate it.

Each header is a name, a colon, optional whitespace, a value, and CRLF. Header names are case-insensitive (`Content-Type` is the same as `content-type`), values may have leading/trailing whitespace (which is stripped), and the same header name may appear multiple times (`Set-Cookie: a=1\r\nSet-Cookie: b=2\r\n` is two cookies). The blank line is just CRLF CRLF — the parser sees the empty line and knows the headers are done.

The body for a request is determined by the `Content-Length` header (a decimal byte count). If there is no `Content-Length` and no `Transfer-Encoding: chunked`, the request has no body. The response body is determined by `Content-Length`, or by `Transfer-Encoding: chunked`, or — for HTTP/1.0 compatibility — by the server closing the connection (the client reads until EOF). For a request, the connection-close-to-delimit-body trick is illegal in HTTP/1.1 because connections are persistent by default; the request must have either `Content-Length` or `Transfer-Encoding: chunked` if it has a body.

The response format is symmetric: a **status line** (`HTTP/1.1 SP STATUS-CODE SP REASON-PHRASE CRLF`, e.g. `HTTP/1.1 200 OK\r\n`), headers, blank line, body:

```text
HTTP/1.1 200 OK\r\n
Content-Type: application/json\r\n
Content-Length: 28\r\n
Date: Wed, 01 Nov 2023 14:23:01 GMT\r\n
\r\n
{"id":42,"email":"alice@..."}
```

The reason phrase (`OK`, `Not Found`, `Internal Server Error`) is informational only — clients must use the numeric status code for branching. Many HTTP/2 implementations omit it entirely (it is not present in HTTP/2's binary framing).

The production failure mode tied to the textual format is **the slowloris attack**. Because the headers are line-oriented and the parser keeps reading until `\r\n\r\n`, a malicious client can open hundreds of connections and drip one byte per second into each, holding the server's worker threads or file descriptors indefinitely. The server cannot know whether the request is complete or merely slow until either the blank line arrives or the read timeout fires. The fix is `client_body_timeout` and `client_header_timeout` (in nginx: `client_header_timeout 30s`, `client_body_timeout 30s`) — bound the time the server will wait for the request to complete. Tomcat's `connectionTimeout`, Express's `server.requestTimeout`, and Apache's `Timeout` directive all serve the same purpose.

### HTTP Request Methods: Safe, Idempotent, and Cacheable classifications

HTTP defines a set of request methods, each with formal properties that determine how caches, proxies, and the server itself may treat the request. The properties are defined in RFC 7231 §4.2:

```text
Method    Safe  Idempotent  Cacheable  Typical use
──────    ────  ──────────  ─────────  ──────────────────────────────────
GET       yes   yes         yes        Retrieve a resource (no body in request)
HEAD      yes   yes         yes        Retrieve headers only (same as GET without body)
POST      no    no          yes*       Submit data (creates a resource, body in request)
PUT       no    yes         no         Replace a resource at a known URL
DELETE    no    yes         no         Remove a resource
PATCH     no    no          no         Partial modification of a resource
OPTIONS   yes   yes         no         Discover server capabilities (CORS preflight)
TRACE     yes   yes         no         Loopback test (disabled by default — XST attack)
CONNECT   no    no          no         Establish a tunnel (HTTPS proxying)
```
*POST is cacheable only with explicit `Cache-Control` and `Content-Location` headers; in practice, almost never cached.

**Safe** means the method is read-only: it does not modify server state. A crawler may issue safe methods without permission; an automatic pre-fetcher may issue safe methods speculatively. GET, HEAD, OPTIONS, TRACE are safe.

**Idempotent** means the client can issue the method N times and the resulting server state is the same as issuing it once. PUT (replace) and DELETE (remove) are idempotent — putting the same resource twice yields the same resource, deleting twice yields the same empty state. POST is *not* idempotent — posting "create order" twice creates two orders. This matters for retries: if a client sends a PUT and the connection drops before the response arrives, the client can safely retry the PUT; if it sends a POST and the connection drops, retrying may duplicate the operation, so the client must use an idempotency key (Stripe's `Idempotency-Key` header is the canonical example).

**Cacheable** means a cache may store the response and serve it for subsequent equivalent requests. GET and HEAD responses are cacheable by default unless the server explicitly forbids it (`Cache-Control: no-store`). POST responses are technically cacheable but practically never cached.

```bash
# Test method handling with curl
curl -X GET    http://localhost:8080/users/42    # safe + idempotent
curl -X POST   http://localhost:8080/users  -d '{"email":"a@b.com"}'  # not safe, not idempotent
curl -X PUT    http://localhost:8080/users/42 -d '{"email":"a@b.com"}'  # idempotent
curl -X DELETE http://localhost:8080/users/42    # idempotent
curl -X OPTIONS http://localhost:8080/users/42   # CORS preflight, returns Allow: header
```

The production failure mode tied to method semantics is **the double-submit bug**. A user clicks "Submit Order" on a slow connection, gets impatient, clicks again, and two orders are created. The cause is a POST that is not idempotent and has no idempotency key. The fix is either (a) use PUT with a client-generated ID (`PUT /orders/{uuid}` instead of `POST /orders`), or (b) keep POST but require an `Idempotency-Key` header that the server uses to deduplicate retries within a time window. Stripe, AWS API Gateway, and most payment APIs mandate the second approach.

### Standard Response Status Codes: 1xx, 2xx, 3xx, 4xx, and 5xx categories and semantics

HTTP status codes are three-digit integers grouped by their first digit into five classes, defined in RFC 7231 §6. The class tells you who is at fault; the specific code tells you what to do about it.

```text
Class   Meaning             Who is at fault     Examples
─────   ────────            ────────────────    ────────────────────────────────────────
1xx     Informational       (protocol)          100 Continue, 101 Switching Protocols
2xx     Success             (none)              200 OK, 201 Created, 204 No Content, 206 Partial
3xx     Redirection         (client follows)    301 Moved Permanently, 302 Found, 304 Not Modified
4xx     Client error        client              400 Bad Request, 401 Unauthorized, 403 Forbidden,
                                                 404 Not Found, 405 Method Not Allowed,
                                                 409 Conflict, 410 Gone, 429 Too Many Requests
5xx     Server error        server              500 Internal Server Error, 502 Bad Gateway,
                                                 503 Service Unavailable, 504 Gateway Timeout
```

The codes you will see most often in production:

- **200 OK** — the request succeeded. Used for GET, PUT, DELETE responses.
- **201 Created** — the request created a new resource. Used for POST responses when the server created something. The response should include a `Location` header pointing to the new resource's URL.
- **204 No Content** — the request succeeded but there is no body to return. Used for DELETE responses and PUT responses where the client already has the current state.
- **301 Moved Permanently** — the resource has a new permanent URL; the client should cache this and use the new URL directly going forward. Used for domain migrations (`http://` → `https://`).
- **302 Found** — the resource is temporarily at a different URL; do not cache. Used for login redirects.
- **304 Not Modified** — the resource has not changed since the client's cached version (conditional GET with `If-Modified-Since` or `If-None-Match`); the client should use its cached copy. Saves bandwidth, not latency.
- **400 Bad Request** — the server cannot parse the request (malformed JSON, missing required field, invalid query parameter). The client must fix the request.
- **401 Unauthorized** — actually means "Unauthenticated" — the request lacks valid authentication credentials. The response should include a `WWW-Authenticate` header describing how to authenticate.
- **403 Forbidden** — the client is authenticated but not authorized to perform this action. The identity is known but the permission is missing.
- **404 Not Found** — the resource does not exist. Crucially, this is *not* the right code for "the resource exists but you cannot see it" — that is 403. Returning 404 for hidden resources can leak existence information.
- **405 Method Not Allowed** — the URL exists but does not support this method. The response must include an `Allow` header listing the supported methods.
- **409 Conflict** — the request conflicts with the current state of the resource (e.g., creating a user with an email that already exists).
- **429 Too Many Requests** — the client has hit a rate limit. The response should include a `Retry-After` header indicating when to retry.
- **500 Internal Server Error** — the server failed to process the request due to an unexpected condition (unhandled exception, bug, downstream failure). The client cannot fix this; the server must.
- **502 Bad Gateway** — a proxy or gateway received an invalid response from an upstream server. The downstream is broken.
- **503 Service Unavailable** — the server is temporarily unable to handle the request (overloaded, starting up, draining). The response should include a `Retry-After` header.
- **504 Gateway Timeout** — a proxy did not receive a response from an upstream server within its timeout. The downstream is too slow.

```bash
# Test status code handling
curl -i http://localhost:8080/users/999999   # expect 404
curl -i -X POST http://localhost:8080/users -d '{}' # expect 400 (missing fields)
curl -i -H "Authorization: Bearer invalid" http://localhost:8080/me   # expect 401
curl -i -H "Authorization: Bearer valid-but-not-admin" http://localhost:8080/admin   # expect 403
```

The production failure mode tied to status codes is **the 5xx that should be a 4xx**. A classic mistake: the server returns 500 when the client sends a malformed request, because the handler threw an uncaught `IllegalArgumentException` that the global exception handler turned into a 500. The client cannot fix a 500 (it is the server's fault by definition), so the client retries — which fails the same way — and the operator gets paged. The fix is to map every input-validation exception to its correct 4xx (400 for malformed, 401 for unauthenticated, 403 for unauthorized, 404 for not found, 409 for conflict), so the client knows the request itself is the problem and will not retry.

### Header parsing mechanics: `Host` header enforcement, Content Negotiation (`Accept`, `Content-Type`)

Headers carry the metadata that surrounds the request body. Two are mandatory in HTTP/1.1: `Host` and (for requests with a body) `Content-Length` or `Transfer-Encoding`.

The **`Host` header** is the single most important header introduced in HTTP/1.1 (it did not exist in HTTP/1.0). It carries the host portion of the URL (`Host: api.example.com`), and its purpose is to enable **virtual hosting**: many websites can share a single IP address, and the server uses `Host` to determine which website to serve. Without `Host`, a server with 1000 websites on one IP would have no way to know which site the client wants. RFC 7230 §5.4 makes `Host` mandatory: a request without it is a `400 Bad Request`. Modern frameworks enforce this automatically, but if you write a raw socket client you must include it.

```text
GET / HTTP/1.1\r\n
Host: api.example.com\r\n     ← mandatory in 1.1, enables virtual hosting
\r\n
```

**Content negotiation** is the mechanism by which the client and server agree on the representation of a resource. The client sends `Accept` (what media types it can handle), `Accept-Language` (what languages), `Accept-Encoding` (what compression), `Accept-Charset` (what character sets). The server picks the best representation based on these and sets `Content-Type` (the actual media type of the response), `Content-Language`, `Content-Encoding`, etc.

```text
GET /users/42 HTTP/1.1
Host: api.example.com
Accept: application/json, application/xml;q=0.5      ← client prefers JSON, accepts XML as fallback
Accept-Encoding: gzip, br                            ← client can decode gzip or Brotli
Accept-Language: en-US, fr;q=0.7                     ← client prefers US English, accepts French

HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8        ← server chose JSON
Content-Encoding: br                                 ← server compressed with Brotli
Content-Language: en-US
```

The `q` parameter (0 to 1, default 1) is the client's preference weight — `application/xml;q=0.5` means "I will accept XML but I prefer JSON 2:1 over XML". The server uses these to pick the best representation.

**`Content-Type`** tells the receiver how to parse the body. Common values:

```text
application/json              — JSON (the de facto API standard)
application/xml               — XML
text/plain                    — Plain text
text/html                     — HTML
application/octet-stream      — Arbitrary binary data
multipart/form-data           — File uploads (form submissions with files)
application/x-www-form-urlencoded — Form submissions without files
application/x-protobuf        — Protocol Buffers (used by gRPC)
application/grpc+proto        — gRPC framing
```

The `charset` parameter on text types (`Content-Type: text/html; charset=utf-8`) tells the receiver how to decode the bytes to characters. Forgetting it on HTML causes the browser to guess (often incorrectly), which is why some old pages render as mojibake.

```bash
# Watch content negotiation happen
curl -v -H "Accept: application/json"  http://localhost:8080/users/42
curl -v -H "Accept: application/xml"   http://localhost:8080/users/42
curl -v -H "Accept-Encoding: gzip"     http://localhost:8080/users/42
# Note the Vary header in the response — it tells caches which request headers
# affect the response representation (so they do not serve a JSON response
# to a client that asked for XML)
```

The production failure mode tied to header parsing is **the missing `Content-Length` on a request with a body**. The client sends `POST /api/users` with a JSON body but no `Content-Length` and no `Transfer-Encoding: chunked`. The server reads the headers, sees no way to determine the body length, and either (a) hangs forever waiting for more bytes, (b) reads zero bytes and reports an empty body, or (c) returns 400. The behavior depends on the framework — Tomcat returns 400, Express hangs, Nginx returns 400. The fix is always on the client side: use a real HTTP client library that sets `Content-Length` automatically (every framework does this; the bug only appears when you write raw socket code or use a misconfigured low-level library).

## How This Connects to the Frameworks

Every framework in section 05 is an HTTP/1.1 parser and router. The pipeline is the same in all of them:

1. Accept a TCP connection (via `accept()` or `epoll_wait()`).
2. Read bytes from the socket into a buffer.
3. Parse the request line (extract method, path, version).
4. Parse headers line-by-line until the blank line.
5. Determine body length from `Content-Length` or `Transfer-Encoding: chunked`.
6. Read the body (possibly chunked).
7. Match the path against registered routes.
8. Invoke the handler with a request object that exposes method, path, headers, body.
9. Serialize the handler's return value into a response (status line, headers, body).
10. Write the response to the socket buffer using `send()`.
11. Either close the connection (`Connection: close`) or keep it alive (`Connection: keep-alive`).

Spring Boot's `DispatcherServlet`, Express's router middleware, Django's URL dispatcher, Flask's `app.route`, and Laravel's `Route::get` all do exactly this. The differences are syntactic, not semantic.

If any of these steps fails — a malformed request, a missing `Host`, a too-large body, a slow client — the failure surfaces as a 4xx status code (client's fault) or a connection reset (server gave up). Knowing which header was missing or which status code should have been returned is the difference between a 5-minute fix and a 5-hour incident.

## Hands-On Exercise

```bash
# Send a raw HTTP/1.1 request with nc — see the literal text format on the wire
printf 'GET / HTTP/1.1\r\nHost: example.com\r\nConnection: close\r\n\r\n' | nc example.com 80

# Send the same request with curl, viewing the full exchange
curl -v --http1.1 http://example.com/

# Capture and inspect an HTTP/1.1 request layer-by-layer
sudo tcpdump -i lo -A -s 0 'tcp port 8080'

# Test the Host header requirement — RFC 7230 says it is mandatory
printf 'GET / HTTP/1.1\r\n\r\n' | nc localhost 8080
# Expect: 400 Bad Request (Host header missing)

# Test status code semantics
curl -i http://localhost:8080/nonexistent         # 404
curl -i -X POST http://localhost:8080/users -d '' # 400 (missing body fields)

# Watch content negotiation in action
curl -v -H "Accept: application/json" http://localhost:8080/users/42
curl -v -H "Accept: application/xml"  http://localhost:8080/users/42

# Inspect what your framework sends as default headers
curl -v http://localhost:8080/health 2>&1 | grep -i '^>'
```
