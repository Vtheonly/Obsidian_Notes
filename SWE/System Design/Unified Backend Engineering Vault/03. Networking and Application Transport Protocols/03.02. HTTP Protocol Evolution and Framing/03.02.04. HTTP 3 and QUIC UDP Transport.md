# 03.02.04. HTTP 3 and QUIC UDP Transport

## What This Is

HTTP/3 (RFC 9114, June 2022) is the third major version of HTTP, and it differs from HTTP/1.1 and HTTP/2 in a fundamental way: it does not run over TCP. Instead, it runs over **QUIC** (Quick UDP Internet Connections, RFC 9000, May 2021), which is itself a reliable transport protocol implemented on top of UDP, entirely in user space. The reason for this radical departure is that HTTP/2's stream multiplexing solved HTTP/1.1's application-layer head-of-line blocking only to introduce a worse problem: TCP-layer head-of-line blocking, where a single lost packet stalls all multiplexed streams.

This note covers why HTTP/2's TCP foundation became a bottleneck, how QUIC rebuilds TCP's reliability and congestion control in user space on top of UDP, the connection migration feature that lets a phone switch from WiFi to cellular without dropping the connection, the 0-RTT resumption that eliminates the handshake cost for returning clients, and the user-space deployment model that let Google and Cloudflare ship QUIC to billions of users without waiting for kernel updates.

## The Details

### The fundamental limitation of HTTP/2: TCP Head-of-Line blocking on packet drop events

HTTP/2 multiplexes many streams over a single TCP connection. This solved HTTP/1.1's application-layer HoL blocking (where one slow response blocked the connection) but created a new, worse problem at the TCP layer. The kernel's TCP stack treats the byte stream as one continuous sequence; when a packet is lost, the kernel refuses to deliver bytes past the gap to the application until the gap is filled by retransmission. Because all HTTP/2 streams share the same byte stream, *all* streams stall — not just the stream whose packet was lost.

```text
HTTP/2 over TCP — packet loss stalls ALL streams:

  Client sends 3 streams' data interleaved on one TCP connection:
    [Stream 1, bytes 0-999][Stream 3, bytes 0-999][Stream 5, bytes 0-999]
                          ↑ this TCP packet is lost in the network

  Client's TCP stack:
    Sends Stream 1 bytes 0-999   → ACKed
    Sends Stream 3 bytes 0-999   → LOST
    Sends Stream 5 bytes 0-999   → received, but kernel holds it
                                   (gap at Stream 3 bytes 0-999)

  Server's kernel:
    Receives Stream 1 bytes 0-999 → delivers to HTTP/2 layer → processed
    Receives Stream 5 bytes 0-999 → HOLDS, does not deliver (gap before it)
    Retransmit timer fires after RTO (~200ms)
    Receives Stream 3 retransmit → delivers Stream 3 AND Stream 5 to HTTP/2 layer

  Result: Stream 5 is delayed by ~200ms even though its packets arrived fine.
  Under 1% packet loss, EVERY stream sees 200ms+ stalls on every loss event.
```

On a typical internet link with 0.5–1% packet loss, this means a few percent of HTTP/2 streams see 200ms+ stalls even when the application data is fine. On mobile networks with 2–5% packet loss, the problem is severe — every multiplexed stream sees frequent stalls.

```text
HTTP/2 over TCP (any packet loss affects all streams):
  Stream 1:  ████ ░░░░ ████   ← packet lost, ALL streams stall for RTO (~200ms)
  Stream 3:  ░░░░ ░░░░ ░░░░   ← Stream 3's data was fine but held back
  Stream 5:  ░░░░ ░░░░ ░░░░   ← Stream 5's data was fine but held back

HTTP/3 over QUIC (only the affected stream stalls):
  Stream 1:  ████ ░░░░ ████   ← only Stream 1 waits for retransmit
  Stream 3:  ████ ████ ████   ← Stream 3 continues normally
  Stream 5:  ████ ████ ████   ← Stream 5 continues normally
```

QUIC solves this by making reliability per-stream: each QUIC stream has its own sequence number space and its own retransmission logic. A lost packet carrying Stream 1's data does not hold back Stream 3 or Stream 5 — their data is delivered to the application as soon as it arrives, even if Stream 1's data is in transit. The retransmission timer fires for Stream 1 only.

The reason this is impossible to fix in TCP is that TCP's reliability is a contract at the byte-stream layer, not the message layer. The kernel's TCP implementation cannot know which bytes belong to which HTTP/2 stream — that information is in the HTTP/2 framing, which is one layer up. To get per-stream reliability, you need to push the framing down into the transport layer, which is what QUIC does.

### The QUIC Protocol: Re-implementing reliable stream transport on top of UDP in user space

QUIC is a transport protocol that provides the same services as TCP (reliable, ordered delivery; flow control; congestion control) plus several TCP cannot provide (per-stream reliability; connection migration; 0-RTT resumption; integrated TLS). It is implemented in user space, on top of UDP, because the alternative — modifying the kernel's TCP stack — would require waiting years for operating system updates to propagate.

```text
QUIC packet structure (simplified):
  +───────────────────────────────────────────────────────────────+
  | UDP header (8 bytes): src_port, dst_port (443), length, checksum |
  +───────────────────────────────────────────────────────────────+
  | QUIC packet header (variable, ~20-40 bytes):                   |
  |   - Flags (long vs short header form)                          |
  |   - Version (e.g., 0x00000001 for QUIC v1)                     |
  |   - Destination Connection ID (8-20 bytes)                      |
  |   - Source Connection ID (0-20 bytes)                           |
  |   - Packet Number (1-4 bytes, varint)                           |
  +───────────────────────────────────────────────────────────────+
  | Encrypted QUIC frames (variable, AEAD-encrypted):              |
  |   - STREAM frame: (stream_id, offset, length, data)             |
  |   - ACK frame: (ack_delay, ack_ranges)                          |
  |   - CRYPTO frame: (offset, data) — for TLS handshake           |
  |   - PING / PADDING / CONNECTION_CLOSE                           |
  |   - MAX_DATA / MAX_STREAM_DATA — flow control                   |
  |   - STREAMS_BLOCKED / DATA_BLOCKED — back-pressure signals      |
  +───────────────────────────────────────────────────────+
```

The connection ID is the most important architectural choice. TCP identifies a connection by the 4-tuple `(src_ip, src_port, dst_ip, dst_port)`. QUIC identifies a connection by an opaque 8–20 byte Connection ID chosen by the endpoints, which is *not* derived from the IP addresses. This means a QUIC connection can survive an IP address change — the client's packets just start arriving at the server from a new IP, but the Connection ID is the same, so the server associates them with the existing connection state. This is **connection migration**, the feature that lets your phone switch from WiFi to cellular mid-stream without dropping a download.

The packet number is monotonically increasing and never reused, even across retransmissions. This is a sharp departure from TCP, where a retransmitted segment has the same sequence number as the original. QUIC's strict monotonicity lets the receiver compute precise RTT measurements even when packets are retransmitted (TCP's ambiguous RTT measurement during retransmission was solved by Karn's algorithm, but QUIC avoids the ambiguity entirely).

```text
TCP retransmission (ambiguous):
  t=0    send seq=1000
  t=200ms RTO fires, resend seq=1000
  t=210ms ACK arrives — was this for the original or the retransmit?
         Karn's algorithm: don't update SRTT on retransmitted segments.

QUIC retransmission (unambiguous):
  t=0    send packet_number=42, carrying stream 1 data
  t=200ms RTO fires, resend same data as packet_number=43
  t=210ms ACK arrives for packet 43 — definitely the retransmit
         RTT = 210ms - 200ms = 10ms (correct), no Karn's algorithm needed.
```

The integrated TLS 1.3 (covered in [[03.03.03. The TLS 1.3 Handshake Protocol]]) is another key feature. In TCP+TLS, the transport handshake (3-way SYN) and the cryptographic handshake (TLS ClientHello/ServerHello) are separate, costing 2–3 RTTs before application data can flow. In QUIC, the transport handshake and the TLS handshake are merged: the ClientHello is carried in the first QUIC packet, the ServerHello in the response, and the entire handshake completes in 1 RTT. For returning connections with a cached session ticket, QUIC can carry application data in the very first packet (**0-RTT**), saving an entire round trip.

```text
TCP + TLS 1.3 (separate transport and crypto handshakes):
  RTT 1: TCP SYN → SYN+ACK → ACK              (transport handshake)
  RTT 2: TLS ClientHello → ServerHello+Cert+Finished → Finished  (crypto handshake)
  RTT 3: HTTP request → response              (application data)
  Total: 3 RTTs before first response byte

QUIC (merged transport + crypto handshake):
  RTT 1: ClientHello (in QUIC packet) → ServerHello+Cert+Finished (in QUIC packet)
  RTT 2: HTTP request → response
  Total: 2 RTTs before first response byte

QUIC with 0-RTT resumption (returning client, cached session):
  RTT 0: ClientHello + HTTP request → ServerHello+Finished + HTTP response
  Total: 1 RTT before first response byte
```

On a 100ms RTT link, that is a 100ms improvement over TCP+TLS for new connections and a 200ms improvement for returning connections — a perceptible user-experience win for any web application.

The user-space implementation is what made QUIC deployable. The kernel's TCP stack is essentially frozen — changes require a kernel patch, which requires years to propagate to all deployed servers. QUIC, implemented as a user-space library linked into the application or a sidecar, can be deployed by a single application update. Google shipped QUIC to Chrome and Google's frontends in 2013; Cloudflare shipped it in 2019; the IETF standardized it in 2021. None of these deployments required any kernel modifications on the server side. This is also why QUIC is built on UDP rather than as a new IP protocol number — UDP packets pass through existing NATs, firewalls, and middleboxes, while a new protocol number would be blocked.

### Connection IDs: Seamless connection migration across IP and network changes (e.g., WiFi to 5G)

A TCP connection is identified by its 4-tuple `(src_ip, src_port, dst_ip, dst_port)`. If any element of the 4-tuple changes — the client's IP changes because the phone switched from WiFi to cellular, or the source port changes because the NAT mapping expired — the connection is broken. The server's kernel sees the new 4-tuple as a brand-new connection and responds with `RST`. The client must re-establish the connection from scratch.

QUIC connections are identified by a **Connection ID** — an opaque 8–20 byte value chosen by the endpoints, carried in every QUIC packet header, and completely independent of the IP addresses. When the client's IP changes (WiFi → cellular, or the cellular tower hands off to a new tower with a new IP), the client simply starts sending QUIC packets from the new IP. The server receives them, sees the same Connection ID, associates them with the existing connection state, and continues serving.

```text
TCP connection — IP change breaks it:
  t=0   Client (WiFi IP 192.168.1.5:54321) ←→ Server (93.184.216.34:443)
        4-tuple: (192.168.1.5, 54321, 93.184.216.34, 443)
        Connection is ESTABLISHED, data flowing.

  t=10s Client switches from WiFi to cellular.
        Client's IP is now 100.64.10.20:54321
        4-tuple changed: (100.64.10.20, 54321, 93.184.216.34, 443)
        Server's kernel does not recognize this 4-tuple → sends RST
        Connection is dead. Client must reconnect, re-handshake, restart the download.

QUIC connection — IP change is transparent:
  t=0   Client (WiFi IP 192.168.1.5) ←→ Server (93.184.216.34)
        Connection ID: 0x83a4c2f1... (chosen by server in handshake)
        Data flowing.

  t=10s Client switches to cellular.
        Client's IP is now 100.64.10.20.
        Client sends next QUIC packet from 100.64.10.20,
        still carrying Connection ID 0x83a4c2f1...
        Server sees the same Connection ID → continues serving the existing connection.
        No RST, no re-handshake, no interrupted download.
```

The Connection ID also helps with **load balancer routing**. A TCP load balancer routes a connection by hashing the 4-tuple — but if it sees a packet from a new IP mid-connection, it cannot know which backend handled the original connection. A QUIC load balancer can route by Connection ID: the server encodes the backend ID into the Connection ID at handshake time, so any packet with that Connection ID routes to the correct backend regardless of source IP. Cloudflare and Google's load balancers do exactly this.

The production failure mode tied to connection migration is **the firewall that blocks QUIC**. Many corporate firewalls and some ISPs block UDP port 443 (or all UDP except port 53 for DNS) because they were designed in the TCP era. When the client attempts HTTP/3 over UDP/443 and the firewall drops the packets, the client falls back to HTTP/2 over TCP/443 after a timeout (typically 300ms — the browser's "happy eyeballs" timer). This fallback is invisible to the user but adds 300ms of latency to the first request from such a network. The fix is either (a) convince the firewall administrator to allow UDP/443, or (b) accept the fallback latency. Browsers' Alt-Svc header (`Alt-Svc: h3=":443"; ma=86400`) advertises HTTP/3 availability; the client tries it and falls back if it fails.

### 0-RTT Connection Establishment: Combining transport and cryptographic handshakes into a single round-trip

QUIC's headline feature is **0-RTT data** — the ability for a returning client to send application data in the very first packet, before the cryptographic handshake completes. This is a 1-RTT improvement over TCP+TLS 1.3 (which already achieves 1-RTT for new connections and 1-RTT for resumed connections, plus TCP's 1-RTT for the SYN/SYN-ACK/ACK).

```text
First connection to a server (1-RTT in QUIC):
  Client                                                Server
    │ ── ClientHello (in QUIC Initial packet) ─────────► │
    │    + key_share, supported_versions, SNI             │
    │                                                    │
    │ ◄── ServerHello + Cert + Finished ───────────────── │
    │     (in QUIC Initial + Handshake packets)           │
    │     + session ticket for future resumption          │
    │                                                    │
    │ ── Finished + HTTP request ───────────────────────► │  (0-RTT not used on first connection)
    │                                                    │
    │ ◄── HTTP response ───────────────────────────────── │

Returning connection with cached session ticket (0-RTT):
  Client                                                Server
    │ ── ClientHello + HTTP request (early data) ───────► │  ← application data in the FIRST packet!
    │    + session ticket from previous connection        │
    │    + 0-RTT key derived from the ticket              │
    │                                                    │
    │ ◄── ServerHello + Finished + HTTP response ──────── │
    │                                                    │
    │ (No additional round trip — server can process the  │
    │  HTTP request immediately upon receipt)             │
```

The 0-RTT mechanism works as follows: on the first connection, the server sends a session ticket (an encrypted blob containing the negotiated keys and parameters). The client caches this ticket. On a subsequent connection, the client uses the ticket to derive a 0-RTT key, encrypts the HTTP request with this key, and sends it in the very first QUIC packet along with the ClientHello. The server, upon receiving the ticket, decrypts it (proving it is a server that the client previously connected to), derives the same 0-RTT key, and decrypts the HTTP request immediately — without waiting for the round trip that would normally be required to establish fresh keys.

0-RTT has one important caveat: **replay attacks**. An attacker who captures the 0-RTT packet can replay it later, and the server will accept it (because the ticket is valid and the request decrypts correctly). This means 0-RTT data must be **idempotent** — a GET request for a static resource is safe; a POST that creates an order is not. The server should reject 0-RTT for non-idempotent requests, or the client should never send non-idempotent requests in 0-RTT. RFC 9000 §5.8 mandates that servers implement anti-replay defenses (single-use tickets, or a replay window with bounded memory).

The application-level pattern is:

```text
Safe for 0-RTT (idempotent, replay-tolerant):
  GET /api/users/42        — read-only, replaying it just returns the same data twice
  GET /static/style.css    — static asset, replay is harmless
  HEAD /api/health         — read-only

NOT safe for 0-RTT (non-idempotent):
  POST /api/orders         — replay creates duplicate orders
  POST /api/payments       — replay charges twice
  PUT /api/users/42        — replay may overwrite later changes
```

The browser handles this automatically: it sends only idempotent requests as 0-RTT data, deferring non-idempotent requests until the handshake completes. The application developer usually does not need to think about this — but if you build a custom HTTP/3 client, you must enforce the same discipline.

```bash
# Verify HTTP/3 / QUIC support in your browser
# Chrome: chrome://flags/#enable-quic (should be on by default)
# Visit https://cloudflare.com/cdn-cgi/trace and look for "http=3" or "http=h3"

# Test HTTP/3 from the command line with curl (8.0+ required, built with HTTP/3 support)
curl --http3 -v https://cloudflare.com/ 2>&1 | grep -i 'HTTP/3\|QUIC'
# Expect: "Using HTTP3" and connection information

# Or use the cloudflare/quiche project's h3load tool for load testing
h3load -n 100 https://example.com/

# Verify 0-RTT is being used (requires capturing the handshake)
# Look for "early data" or "0-RTT" in the QUIC handshake
sudo tcpdump -i any -w /tmp/quic.pcap 'udp port 443'
# Then: wireshark /tmp/quic.pcap → filter: quic
```

The production failure mode tied to 0-RTT is **the application that sends non-idempotent requests in 0-RTT**. If your custom HTTP/3 client sends `POST /api/orders` as 0-RTT data, and a MITM attacker captures the packet and replays it, you get duplicate orders. The fix is to either (a) never send non-idempotent requests in 0-RTT (let them wait for the handshake to complete), or (b) require an `Idempotency-Key` header on every non-idempotent request so the server can deduplicate replays.

### HTTP/3 Mapping: QPACK header compression and stream management over QUIC

HTTP/3 is the application-layer protocol that runs over QUIC. Its framing is similar to HTTP/2's (HEADERS frame, DATA frame, per-stream multiplexing) but adapted to QUIC's per-stream reliability model. The most significant adaptation is **QPACK** (RFC 9204), the HTTP/3 equivalent of HTTP/2's HPACK.

QPACK differs from HPACK because HPACK's dynamic table assumes in-order delivery of HEADERS frames — the decoder must update its dynamic table in the same order the encoder wrote to it. HTTP/2 runs over TCP, which guarantees in-order delivery, so HPACK can rely on this. HTTP/3 runs over QUIC, which delivers streams independently — Stream 5's HEADERS frame may arrive before Stream 3's, even though Stream 3 was sent first. QPACK must therefore handle out-of-order delivery.

The solution: QPACK adds explicit instructions to the dynamic table on a separate unidirectional stream (the encoder stream), and HEADERS frames reference the dynamic table state by index. If a HEADERS frame references a dynamic table entry that has not yet been processed (because the encoder-stream instruction is still in flight), the receiver cannot decode the header immediately — it must wait. This is QPACK's only remaining HoL blocking, and it is rare because most headers fit in the static table or are encoded inline.

```text
QPACK vs HPACK comparison:

HPACK (HTTP/2, in-order delivery guaranteed by TCP):
  - Dynamic table updates happen in HEADERS frames themselves
  - Decoder processes frames in order, table is always consistent
  - Simpler, but tied to TCP's in-order semantics

QPACK (HTTP/3, out-of-order delivery possible over QUIC):
  - Dynamic table updates happen on a separate encoder stream (always in-order)
  - HEADERS frames reference table entries by index
  - If a reference is not yet processed, decoder must wait (rare)
  - More complex, but compatible with QUIC's per-stream reliability
```

Both achieve roughly the same compression ratio (~16:1 over plain text for typical browser headers). QPACK adds a small amount of overhead for the reference mechanism but gains the ability to use QUIC's per-stream loss recovery.

```bash
# Capture HTTP/3 / QUIC traffic and decode in Wireshark
sudo tcpdump -i any -w /tmp/quic.pcap 'udp port 443'
# Wireshark 4.0+ has a built-in QUIC dissector that can decode QPACK frames

# Verify the HTTP/3 Alt-Svc advertisement
curl -I https://cloudflare.com/ | grep -i alt-svc
# Expect: alt-svc: h3=":443"; ma=86400, h3-29=":443"; ma=86400
# This tells the browser: "I also speak HTTP/3 on port 443, valid for 86400 seconds"

# Compare HTTP/2 vs HTTP/3 connection times
curl -w "%{time_connect} %{time_appconnect} %{time_starttransfer}\n" -o /dev/null -s --http2 https://example.com/
curl -w "%{time_connect} %{time_appconnect} %{time_starttransfer}\n" -o /dev/null -s --http3 https://example.com/
# HTTP/3 should have lower time_appconnect (merged transport + TLS handshake)
```

The major adopters of HTTP/3 are Google (Search, YouTube, Drive), Cloudflare (over 30% of HTTP/3 internet traffic as of 2023), Facebook (mobile apps), Discord (voice chat — they switched from WebRTC over TCP to QUIC for better mobile performance), and Uber (mobile apps). The pattern is consistent: companies with significant mobile traffic were the early adopters because mobile networks have the packet loss rates and IP address changes that make QUIC's per-stream reliability and connection migration most valuable.

## How This Connects to the Frameworks

HTTP/3 support in section 05's frameworks is still emerging as of 2024:

- **Spring Boot**: HTTP/3 support landed in Spring Boot 3.4 / Tomcat 11 via the `quiche` integration; or use Netty's HTTP/3 support directly.
- **Express/Node.js**: HTTP/3 is not yet built into Node's `http2` module; community packages like `node-quic` and `aioquic` exist but are not production-ready. Most Node apps terminate HTTP/3 at a reverse proxy (nginx, Cloudflare, AWS ALB).
- **Python**: `aioquic` is a pure-Python QUIC library; `hypercorn` supports HTTP/3 via aioquic.
- **PHP/Laravel**: PHP-FPM does not speak HTTP/3 directly; nginx terminates HTTP/3 and proxies to PHP-FPM over FastCGI.

The common deployment pattern is: terminate HTTP/3 at a reverse proxy (nginx with `--with-http_v3_module`, Cloudflare, AWS ALB, or Envoy), and have the proxy translate to HTTP/1.1 or HTTP/2 for the backend. This is because HTTP/3's user-space QUIC implementation is CPU-intensive (the kernel cannot help with UDP packet processing the way it can with TCP), so consolidating HTTP/3 termination at the edge is more efficient.

If HTTP/3 fails — a firewall blocks UDP/443, a QUIC implementation has a bug, an old client does not support it — the failure surfaces as a transparent fallback to HTTP/2 over TCP, usually invisible to the user but adding 300ms of "happy eyeballs" timer latency. Knowing that HTTP/3 is opportunistic and falls back is the difference between a 5-minute fix and a 5-hour incident.

## Hands-On Exercise

```bash
# Verify HTTP/3 support in your browser
# Visit https://cloudflare.com/cdn-cgi/trace — the "http=" field shows which version you used

# Test HTTP/3 from the command line (curl 8.0+ with HTTP/3 support)
curl --http3 -v https://cloudflare.com/ 2>&1 | grep -i 'HTTP/3\|QUIC\|h3'

# Compare HTTP/2 vs HTTP/3 connection timing
curl -w "HTTP/2: connect=%{time_connect} appconnect=%{time_appconnect} starttransfer=%{time_starttransfer}\n" \
     -o /dev/null -s --http2 https://cloudflare.com/
curl -w "HTTP/3: connect=%{time_connect} appconnect=%{time_appconnect} starttransfer=%{time_starttransfer}\n" \
     -o /dev/null -s --http3 https://cloudflare.com/

# Verify 0-RTT (returning connection — visit twice and watch the second)
curl --http3 -v -o /dev/null https://cloudflare.com/ 2>&1 | grep -i 'session\|resumption\|0-RTT'
curl --http3 -v -o /dev/null https://cloudflare.com/ 2>&1 | grep -i 'session\|resumption\|0-RTT'

# Check the Alt-Svc advertisement from a server
curl -I https://cloudflare.com/ | grep -i alt-svc
# alt-svc: h3=":443"; ma=86400

# Verify whether your network blocks UDP/443 (which would block HTTP/3)
nc -u -z -v cloudflare.com 443 -w 3
# If "Connection refused" or timeout, UDP/443 may be blocked on your network

# Capture QUIC traffic for analysis (Wireshark 4.0+ decodes QUIC + QPACK)
sudo tcpdump -i any -w /tmp/quic.pcap 'udp port 443'
```
