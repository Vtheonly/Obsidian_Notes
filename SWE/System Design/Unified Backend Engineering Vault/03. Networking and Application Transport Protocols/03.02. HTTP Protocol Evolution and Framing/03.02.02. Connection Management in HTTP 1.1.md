# 03.02.02. Connection Management in HTTP 1.1

## What This Is

HTTP/1.0 opened a new TCP connection per request, sent the request, read the response, and closed the connection. Every request cost one TCP handshake (1 RTT for the SYN/SYN-ACK/ACK) plus one teardown (with the active closer entering TIME_WAIT for 60 seconds). On a page that loads 50 sub-resources (CSS, JS, images), that is 50 handshakes and 50 TIME_WAITs — both expensive in latency and in kernel state. HTTP/1.1 (RFC 7230 §6.4, 1999) made **persistent connections** the default: the TCP connection is reused for multiple requests, amortizing the handshake cost across many requests and eliminating most TIME_WAIT accumulation.

This note covers HTTP/1.1's connection-management features: persistent connections (keep-alive), the failed pipelining experiment, the head-of-line blocking problem at the application layer, the per-host connection pool model that browsers use to work around pipelining's failure, and the idle timeout tuning that determines how long a connection stays open between requests.

## The Details

### Short-lived connections vs. Persistent Connections (`Connection: keep-alive`)

In HTTP/1.0, the default is short-lived: each request opens a new TCP connection, sends the request, reads the response, and closes. The `Connection: keep-alive` header opts in to persistence. In HTTP/1.1, the default is persistent: the connection stays open after the response unless the client or server explicitly sends `Connection: close`. To opt out of persistence in 1.1, you must send `Connection: close`.

```text
HTTP/1.0 (short-lived, default):
  Client                              Server
  ─────────────                       ──────
  TCP SYN ──────────────────────────►
  ◄──── SYN+ACK ────────────────────
  ACK ──────────────────────────────►  (3-way handshake: 1 RTT)
  GET /index.html HTTP/1.0\r\n\r\n ─►
  ◄──── HTTP/1.0 200 OK ... ─────────
  ◄──── <html>...</html> ───────────
  FIN ──────────────────────────────►  (close, server enters TIME_WAIT)
  ◄──── FIN ─────────────────────────

  Total: 1 RTT handshake + 1 RTT request/response = ~2 RTT for one resource

HTTP/1.1 (persistent, default):
  Client                              Server
  ─────────────                       ──────
  TCP SYN ──────────────────────────►
  ◄──── SYN+ACK ────────────────────
  ACK ──────────────────────────────►  (1 RTT handshake)
  GET /index.html HTTP/1.1\r\n        (keep-alive implicit)
       Host: example.com\r\n\r\n ───►
  ◄──── HTTP/1.1 200 OK ...
       Content-Length: 1234
       Connection: keep-alive\r\n
       \r\n
       <html>...</html> ─────────────
  GET /style.css HTTP/1.1\r\n         (reuse the same TCP connection!)
       Host: example.com\r\n\r\n ───►
  ◄──── HTTP/1.1 200 OK ...
       Content-Length: 4567
       \r\n
       body{...} ────────────────────
  ... many more requests on same connection ...
  Connection: close\r\n ────────────►  (only one TIME_WAIT at the end)
  ◄──── FIN ─────────────────────────

  Total for 50 resources: 1 RTT handshake + 50 RTT request/response = ~51 RTT
  vs HTTP/1.0's 50 * 2 = ~100 RTT — a 2x latency improvement.
```

The persistent connection eliminates the per-request handshake cost (1 RTT saved per request after the first) and the per-request TIME_WAIT (only one TIME_WAIT per persistent connection's lifetime, instead of one per request). For a page with 50 sub-resources on a 100ms RTT link, that is 50 × 100ms = 5 seconds of latency saved just on handshakes.

The `Connection: keep-alive` header in HTTP/1.1 also accepts optional parameters: `timeout` (how long the server will keep an idle connection open) and `max` (how many requests the server will allow on this connection before closing). These are informational, not authoritative — the server may close earlier. The format is `Connection: keep-alive\r\nKeep-Alive: timeout=5, max=100\r\n`.

```bash
# Verify keep-alive is being used
curl -v http://localhost:8080/ 2>&1 | grep -i 'connection'
# Look for "Connection: keep-alive" in the request and response

# Count TIME_WAIT sockets to a specific server — with keep-alive, this should be small
ss -tan state time-wait '( dport = :8080 )' | wc -l

# Use ab (Apache Bench) to compare keep-alive vs no-keep-alive throughput
ab -n 1000 -c 10 -k   http://localhost:8080/   # -k = keep-alive, fast
ab -n 1000 -c 10      http://localhost:8080/   # no -k, slower
```

The production failure mode tied to keep-alive is **the keepalive timeout mismatch between client and server**. The client thinks the connection is alive for 60 seconds; the server's load balancer closes idle connections after 30 seconds. The client sends a request on a connection the load balancer has already closed; the request reaches a closed socket; the kernel sends a `RST`; the client gets `ECONNRESET` and must retry. The symptom is intermittent `Connection reset by peer` errors at low rates that disappear under high load (because high load keeps the connection active). The fix is to set the client's keepalive timeout shorter than the server's idle timeout — typically `keepalive_timeout` (server) > `idle_timeout` (client) by 5–10 seconds.

### Keep-Alive parameters: `timeout` and `max` request counts

The `Keep-Alive` header (RFC 7230 §A.2, technically a "reserved" header in 1.1 but widely implemented) carries two parameters that hint at the server's idle and request-count limits:

```text
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 1234
Connection: keep-alive
Keep-Alive: timeout=5, max=100
                                              ← server will keep the connection open for 5s of idleness
                                              ← and allow up to 100 requests on this connection
```

`timeout=5` means: if no request arrives within 5 seconds, the server will close the connection. `max=100` means: after 100 requests have been served on this connection, the server will close it (and the client must open a new connection for the 101st). These are advisory — the server may close earlier (e.g., if it is under memory pressure and wants to free socket buffers) and the client must always be prepared for the connection to be closed.

Typical defaults in production servers:

```text
Server             keepalive_timeout    max_requests_per_connection
──────             ──────────────────   ────────────────────────────
nginx              75s                  unlimited (controlled by keepalive_requests, default 1000)
Apache httpd       5s                   100
Tomcat             20s                  unlimited (maxKeepAliveRequests default 100)
Node.js http       5s                   unlimited
Express            5s (server.keepAliveTimeout) unlimited
Spring Boot (Tomcat) 20s                100 (server.tomcat.max-keep-alive-requests)
AWS ALB            60s                  unlimited
HAProxy            1m (timeout http-keep-alive) unlimited
Envoy              300s                 unlimited
```

The interaction between client-side and server-side idle timeouts is the most common source of production connection-management bugs. If the client's idle timeout (how long it keeps a pooled connection before discarding it) is longer than the server's, the client will periodically try to send a request on a connection the server has already closed. The kernel on the server side will respond with `RST`, and the client will see `Connection reset by peer` — usually at low rates (a few percent of requests) and only on idle traffic patterns.

The fix is a deliberate mismatch: set the client's idle timeout shorter than the server's by a margin of 5–10 seconds. If the server closes at 30s, the client should close at 25s. This way the client always closes first, and the server never sees a request on a connection it has already torn down.

```text
Correct configuration:
  Server keepalive timeout: 30s
  Client pool idle timeout: 25s    ← shorter by 5s margin

  Client connects, sends request, server responds.
  Client waits up to 25s for next request.
  If no request arrives in 25s, client closes the connection (sends FIN).
  Server receives FIN, closes its side. No TIME_WAIT mismatch.

Incorrect configuration:
  Server keepalive timeout: 30s
  Client pool idle timeout: 60s    ← longer than server!

  Client connects, sends request, server responds.
  Server waits 30s, no request arrives, server closes (sends FIN).
  Client still thinks connection is alive at 30s.
  At 35s, client sends a new request on the closed connection.
  Server kernel responds with RST.
  Client sees ECONNRESET, must retry — adds 1 RTT of latency to the retry.
```

The `max` request count exists to bound the memory cost of a single long-lived connection. Some servers accumulate per-connection state (PHP-FPM's request log, mod_php's session data) that grows over time; closing the connection periodically lets the server release this state. For most modern frameworks (Spring Boot's Reactor Netty, Node's cluster, Python's uvicorn), per-connection state is minimal and `max` can be unlimited — but PHP-FPM traditionally sets `pm.max_requests = 500` to leak-proof against PHP's memory management quirks.

### Chunked Transfer Encoding (`Transfer-Encoding: chunked`): Streaming variable-length dynamic responses

When the server knows the length of the response body in advance, it sends `Content-Length: 1234` and the client knows exactly when the body is complete. When the server does *not* know the length in advance — because it is streaming a database result, generating the response on the fly, or proxying a chunked upstream — it uses `Transfer-Encoding: chunked` instead. The body is sent as a sequence of chunks, each prefixed with its size in hexadecimal, terminated by a zero-length chunk:

```text
HTTP/1.1 200 OK\r\n
Content-Type: text/plain\r\n
Transfer-Encoding: chunked\r\n
\r\n
4\r\n
Wiki\r\n
5\r\n
pedia\r\n
0\r\n
\r\n
```

Dissecting: the headers end with the blank line. Then the body begins. `4\r\n` is the chunk size in hex (4 bytes). `Wiki` is the chunk data (4 bytes). `\r\n` terminates the chunk. `5\r\n` is the next chunk size. `pedia` is the 5-byte chunk data. `\r\n` terminates. `0\r\n` is the zero-length chunk, marking end of body. `\r\n` terminates the trailer section (empty in this case).

The chunked encoding lets the server start sending the body before knowing its total length. This is essential for:
- **Server-Sent Events** (SSE) — the server holds the connection open indefinitely and pushes events as they occur; the total length is unknown because the stream may never end.
- **Streaming large database results** — the server starts sending rows as they come from the DB, without buffering the entire result in memory.
- **Proxying upstream chunked responses** — nginx proxies a chunked response from upstream without needing to buffer it first.

The trailer mechanism allows headers to be sent *after* the body. The sender includes `Trailer: Content-MD5` in the headers, then after the final zero chunk it sends additional headers (`Content-MD5: ...`). This is rarely used but useful for computing a checksum over the body as it streams.

```bash
# Test chunked encoding with curl
curl -v http://localhost:8080/stream 2>&1 | head -20
# Look for "Transfer-Encoding: chunked" in the response headers

# Watch a chunked response arrive byte-by-byte
curl -N http://localhost:8080/stream
# -N disables curl's output buffering so you can see chunks arrive

# A minimal chunked-encoding server in Python
python3 -c "
import http.server
class H(http.server.BaseHTTPRequestHandler):
    def do_GET(self):
        self.send_response(200)
        self.send_header('Content-Type', 'text/plain')
        self.send_header('Transfer-Encoding', 'chunked')
        self.end_headers()
        for chunk in [b'Hello', b', ', b'World', b'!']:
            self.wfile.write(f'{len(chunk):x}\r\n'.encode() + chunk + b'\r\n')
        self.wfile.write(b'0\r\n\r\n')
http.server.HTTPServer(('', 8080), H).serve_forever()
"
```

The production failure mode tied to chunked encoding is **the buffering proxy**. A reverse proxy (nginx, Cloudflare, AWS ALB) may buffer the entire chunked response before forwarding it to the client — destroying the streaming property. The symptom is that SSE events arrive in batches every 30 seconds instead of as they happen. The fix is to disable proxy buffering for streaming endpoints: nginx `proxy_buffering off;`, Cloudflare `Cache-Control: no-transform`, or to use a streaming-friendly protocol like WebSocket.

### Head-of-Line (HoL) Blocking at the Application Layer in HTTP/1.1 and the failure of HTTP Pipelining

HTTP/1.1's persistent connections solve the handshake cost but introduce a new problem: **head-of-line blocking at the application layer**. Because HTTP/1.1 is a strict request-response protocol on a single connection, the client must wait for the response to request 1 before it can send request 2 on the same connection. If the server is slow to respond to request 1 (a slow database query, a large file), every subsequent request on that connection is stuck behind it.

```text
HTTP/1.1 persistent connection without pipelining:
  Client                              Server
  ──────                              ──────
  GET /slow-query HTTP/1.1 ─────────►
                                (server takes 2 seconds to compute the response)
  ◄──── 200 OK (slow-query body) ────  ← request 2 must wait
  GET /style.css HTTP/1.1 ──────────►
  ◄──── 200 OK (style.css body) ─────

  Total: 2s + 0.1s = 2.1s for both requests. The fast request is held up by the slow one.
```

**HTTP pipelining** (RFC 7230 §6.3.2) was the 1999 attempt to solve this: the client sends multiple requests back-to-back without waiting for responses, and the server processes them in order and sends responses in order. Theoretically, this eliminates the RTT between requests:

```text
HTTP/1.1 pipelining (rarely deployed):
  Client                              Server
  ──────                              ──────
  GET /slow-query HTTP/1.1 ─────────►
  GET /style.css     HTTP/1.1 ─────►  (sent immediately, no waiting)
  GET /script.js     HTTP/1.1 ─────►
                                (server processes slow-query first, takes 2s)
  ◄──── 200 OK (slow-query body) ────
  ◄──── 200 OK (style.css body) ─────  (already computed, sent immediately)
  ◄──── 200 OK (script.js body) ─────
```

Pipelining failed in practice for three reasons:

**1. The server must respond in order.** Even if `style.css` is computed instantly, the server cannot send its response until `slow-query`'s response is sent. The fast response is still blocked behind the slow one. Pipelining saves the RTT between requests but does not save the head-of-line blocking.

**2. Many servers and proxies had bugs.** In 1999–2005, a significant fraction of deployed servers and proxies did not correctly handle pipelined requests — they would respond out of order, drop requests, or close the connection. A browser that sent pipelined requests to a buggy server would see broken pages.

**3. Idempotency concerns.** If the pipelined connection fails partway through (the server closes after sending response 2 of 3), the client must re-send request 3 — but if request 3 was a POST, retrying it could duplicate the operation. Browsers refused to pipeline non-idempotent requests, which limited the benefit.

As a result, no major browser ever enabled pipelining by default. Firefox had it behind a flag (`network.http.pipelining`), Chrome and Safari never shipped it at all. The de facto solution was the **connection pool**: instead of one connection per origin with pipelining, browsers open 6 connections per origin and send one request at a time on each. This works around HoL blocking for the parallel case (6 slow requests can run concurrently) but does not help the serial case (a fast request behind a slow request on the same connection is still blocked).

```text
Browser connection pool model (6 connections per origin, HTTP/1.1):
  Origin: https://api.example.com
  Conn 1: GET /slow-query ─── (2s) ────────────────── 200 OK
  Conn 2: GET /style.css ──── (0.1s) ──── 200 OK
  Conn 3: GET /script.js ──── (0.1s) ──── 200 OK
  Conn 4: GET /image1.png ─── (0.1s) ──── 200 OK
  Conn 5: GET /image2.png ─── (0.1s) ──── 200 OK
  Conn 6: GET /image3.png ─── (0.1s) ──── 200 OK
  Conn 7 (queued): GET /image4.png — must wait for one of the above to free up

  This is why browsers open 6 connections per origin — Chrome's default since 2008.
  HTTP/2's stream multiplexing makes this 6-connection pool unnecessary.
```

The 6-connection limit is the reason your `curl` against `https://api.example.com/users` from your laptop is fast but your load test with 100 concurrent requests against the same endpoint is slow — at 6 connections per origin, the 7th request waits in the connection pool's queue. The fix is either HTTP/2 (one connection, many streams) or spreading the load across multiple origin hostnames (sharding — `api1.example.com`, `api2.example.com`, etc., each gets its own 6-connection pool).

```bash
# Verify the browser's 6-connection limit
# Open Chrome DevTools → Network tab, load a page with 20 sub-resources from the same origin
# Watch the "Connection ID" column — you will see at most 6 distinct connection IDs in use simultaneously

# In curl, the equivalent limit is --max-concurrency (curl 7.66+)
curl -Z --parallel --parallel-immediate --parallel-max 6 http://localhost:8080/{1..20}
# Requests 7-20 will queue until one of connections 1-6 frees up

# Server-side, see how many concurrent connections your client opened
ss -tan 'sport = :8080' | grep ESTAB | wc -l
# A browser will show 6; curl --parallel will show up to 6; a misconfigured client will show 1 (slow!)
```

The production failure mode tied to HoL blocking is **the API client that uses a single connection per origin**. A microservice client configured with `maxConnectionsPerHost = 1` (sometimes the default in older libraries) will serialize all requests to that host — request 2 cannot start until request 1 completes. Throughput drops to `1 / response_time` per second. The fix is to configure the client's connection pool to allow N concurrent connections per host (typically 50–100 for high-throughput service-to-service traffic), or to upgrade to HTTP/2 where one connection carries many concurrent streams.

## How This Connects to the Frameworks

Every framework in section 05 has a connection-pool configuration:

- **Spring Boot + Apache HttpClient**: `PoolingHttpClientConnectionManager` with `setDefaultMaxPerRoute(50)` and `setMaxTotal(200)`. Without this, the default is 2 per route — fatal for any high-throughput client.
- **Spring Boot + Reactor Netty**: `HttpClient` with `.connectionProvider(provider.maxConnections(100))`. Reactor Netty's pool defaults to 2 * available processors, which is often too small for I/O-bound workloads.
- **Express/Node.js**: `http.Agent` with `agent.maxSockets = 100`. The default is `Infinity` for the global agent but `5` for `https.globalAgent` — a frequent surprise.
- **Python `requests`**: `HTTPAdapter(pool_connections=10, pool_maxsize=100)` mounted on a `Session`. Default `pool_maxsize=10` is too small for production.
- **PHP Guzzle**: `CurlMultiHandler` with `CURLMOPT_MAXCONNECTS` set; the default is unspecified and often small.

If any of these is misconfigured, the symptom is "my client is slow even though the server is fast" — the connection pool is the bottleneck, not the network or the server. Knowing that the pool size is the ceiling on concurrent in-flight requests is the difference between a 5-minute fix and a 5-hour incident.

## Hands-On Exercise

```bash
# Verify keep-alive is being used
curl -v http://localhost:8080/ 2>&1 | grep -i 'connection'
# Look for "Connection: keep-alive" in both request and response

# Compare keep-alive vs no-keep-alive throughput
ab -n 1000 -c 10 -k   http://localhost:8080/   # with keep-alive
ab -n 1000 -c 10      http://localhost:8080/   # without (1 new TCP connection per request)

# Inspect chunked encoding
curl -v -N http://localhost:8080/stream 2>&1 | head -20
# Look for "Transfer-Encoding: chunked" and watch chunks arrive

# See the 6-connection-per-host limit
ss -tan 'sport = :8080' | grep ESTAB | wc -l   # while loading a heavy page

# Reproduce the keepalive timeout mismatch
# 1. Configure a server with keepalive_timeout=2s (very short)
# 2. Configure a client with pool_idle_timeout=10s (longer than the server)
# 3. Send one request every 5 seconds — observe intermittent ECONNRESET
# 4. Fix: set client pool_idle_timeout=1s (shorter than server) — error disappears
```
