# 09.06.02. Structural Patterns in Backend Systems

## What This Is

Structural patterns govern *how classes and objects are composed into larger structures* — what wraps what, what delegates to what, which interface an object presents versus what it actually is. Where creational patterns answered "how is this object born?", structural patterns answer "how do these objects sit together so the caller can ignore the seams?". They are the patterns you reach for when an external API doesn't match your domain's vocabulary, when a cross-cutting concern (transactions, caching, metrics, security) needs to be applied to a service without rewriting it, or when a subsystem has grown too tangled to call directly and you need a single front door.

The GoF (Gamma, Helm, Johnson, Vlissides 1994) lists seven structural patterns: Adapter, Bridge, Composite, Decorator, Facade, Flyweight, Proxy. In modern backend code the same seven are everywhere, but most of them are now invisible — they are implemented by framework machinery rather than hand-rolled. Spring's `HandlerAdapter` is the Adapter pattern; Spring's CGLIB / JDK-dynamic-proxy around any `@Transactional`, `@Cacheable`, `@Async` method is the Decorator pattern (also known as Proxy in the GoF sense — the two collapse in practice); Spring's `@Service` class that orchestrates four repositories and three gateways is the Facade; Java's `Integer.valueOf` cache for −128..127 is the Flyweight. The pattern is the shape; the framework is the convenience.

The reason these patterns matter even when the framework implements them is that *you still have to design the seams*. The framework can wrap your class in a transactional proxy, but it can't decide whether your domain should define a `PaymentGateway` port (Adapter) or call Stripe's SDK directly. It can compose a service from five collaborators (Facade), but it can't decide whether the cart should be a `Composite` of `LineItem`s or a flat list. The patterns below are the vocabulary for those decisions.

## The Details

### Adapter Pattern: Translating third-party external APIs into clean domain driven ports

An Adapter sits between two interfaces that don't quite match and makes one look like the other. The GoF formulation: "convert the interface of a class into another interface clients expect." In a hexagonal / ports-and-adapters architecture, this is the pattern that lets the domain define a `PaymentGateway` port in its own vocabulary (`charge(Money, CustomerId)`) while the actual implementation calls Stripe's SDK (`ChargeCreateParams.builder().setAmount(cents).setCurrency("usd").setCustomer(stripeCustomerId).build()`). The domain never imports `com.stripe.*`; the adapter does the translation in both directions — Stripe's `Charge` object becomes your `PaymentReceipt`, Stripe's `CardDeclinedException` becomes your `PaymentRejected` domain event.

Spring's own `HandlerAdapter` is the canonical framework implementation. Spring MVC dispatches to controllers through a `HandlerAdapter` interface; the `RequestMappingHandlerAdapter` adapts `@RequestMapping`-annotated methods, the `SimpleControllerHandlerAdapter` adapts classes implementing `Controller`, the `HttpRequestHandlerAdapter` adapts `HttpRequestHandler`. The dispatcher doesn't know what kind of handler it has — it iterates the registered adapters and asks each `supports(handler)`. This is what lets Spring WebFlux and Spring MVC share the same dispatcher infrastructure while having radically different handler shapes (reactive vs blocking). It is also what lets old `Controller` implementations and new `@RestController` classes coexist in the same application.

```java
// Domain port — defined in domain layer, knows nothing about Stripe.
public interface PaymentGateway {
    PaymentReceipt charge(Money amount, CustomerId customer) throws PaymentRejected;
}

// Adapter — in infrastructure layer, depends on Stripe SDK AND on the domain port.
@Component
class StripePaymentGatewayAdapter implements PaymentGateway {
    private final StripeClient stripe;
    private final StripeCustomerResolver customers;   // local customerId → stripeCustomerId

    @Override
    public PaymentReceipt charge(Money amount, CustomerId customer) throws PaymentRejected {
        try {
            ChargeCreateParams params = ChargeCreateParams.builder()
                .setAmount(amount.toMinorUnits())           // Money → long cents
                .setCurrency(amount.getCurrency().getCurrencyCode())  // Currency → "USD"
                .setCustomer(customers.resolveStripeId(customer))    // CustomerId → "cus_abc123"
                .build();
            Charge ch = Charge.create(params);              // Stripe SDK call
            return new PaymentReceipt(                       // Stripe Charge → domain receipt
                ch.getId(),
                Money.of(ch.getAmount(), ch.getCurrency()),
                Instant.ofEpochSecond(ch.getCreated()));
        } catch (CardException e) {                          // Stripe exception → domain exception
            throw new PaymentRejected(customer, amount, e.getDeclineCode(), e);
        }
    }
}
```

```text
              Domain (knows nothing about Stripe)
              ───────────────────────────────────
              PaymentGateway.charge(Money, CustomerId) ◄── port (interface)
                            ▲
                            │ implements
              ──────────────┼────────────────────────────
              Infrastructure│ (depends on Stripe SDK)
              ──────────────┼────────────────────────────
              StripePaymentGatewayAdapter
                  │ uses
                  ▼
              Stripe.charge(ChargeCreateParams)  ──► Stripe API
```

The Bridge pattern is the closely-related sibling: where Adapter retrofits an existing class to a foreign interface, Bridge splits an abstraction and its implementation into separate hierarchies that can vary independently. The GoF example is a `Shape` abstraction (`Circle`, `Square`) bridged to a `Renderer` implementation (`VectorRenderer`, `RasterRenderer`) — you can add a new shape without touching the renderers, and a new renderer without touching the shapes. In backend code Bridge shows up when you have an orthogonal axis of variation: a `MessagePublisher` abstraction with implementations per transport (`KafkaPublisher`, `SqsPublisher`, `InMemoryPublisher`) bridged to a serialisation axis (`JsonSerializer`, `AvroSerializer`, `ProtobufSerializer`). Without the bridge you'd have `KafkaJsonPublisher`, `KafkaAvroPublisher`, `SqsJsonPublisher`, … — N × M classes; with the bridge, N + M.

```java
// Bridge: abstraction (publisher) and implementation (serializer) vary independently.
interface MessageSerializer { byte[] serialize(Object payload); }
class JsonSerializer  implements MessageSerializer { /* … */ }
class AvroSerializer   implements MessageSerializer { /* … */ }

abstract class MessagePublisher {
    protected final MessageSerializer serializer;   // the bridge
    protected MessagePublisher(MessageSerializer s) { this.serializer = s; }
    abstract void publish(String topic, Object payload);
}
class KafkaPublisher extends MessagePublisher {
    private final KafkaProducer<String, byte[]> producer;
    void publish(String topic, Object payload) {
        producer.send(new ProducerRecord<>(topic, serializer.serialize(payload)));
    }
}
// New serializer: add AvroSerializer — no publisher changes.
// New transport:  add SqsPublisher    — no serializer changes.
```

The production failure mode for the Adapter is *leaky translation*: an adapter that lets the wrapped library's types bleed through. If your `PaymentGateway.charge` signature includes `StripeChargeParams` as a parameter, or throws `StripeException`, you haven't actually adapted anything — you've just renamed. The leak is usually invisible at first (the code compiles, the tests pass) and shows up six months later when you try to swap Stripe for PayPal and discover that half your domain code is calling `stripeCharge.getBalanceTransaction()` directly. The defence is the dependency rule: the domain module's `build.gradle` must not contain `implementation 'com.stripe:stripe-java'`. If the import won't compile in the domain module, the leak can't happen.

For the Bridge, the failure mode is *failing to bridge when the axes are actually orthogonal*. The symptom is a class explosion: every new combination of transport × serialization × tenant × region spawns a new concrete class, the test suite grows quadratically, and the wiring code becomes a decision tree nobody understands. The fix is to recognise the second axis of variation and extract it into a separate hierarchy — but only after the second axis is real. Premature bridging (one axis of variation with a hypothetical second axis imagined for "future flexibility") is just as bad: you've added an interface for no reason, and the abstraction becomes noise.

### Decorator / Proxy Pattern: Dynamically adding cross-cutting concerns (Caching, Metrics, Logging, ...

The Decorator wraps an object with another object that implements the same interface but adds behaviour before, after, or around each delegated call. The GoF formulation: "attach additional responsibilities to an object dynamically." In Java I/O this is `new BufferedInputStream(new FileInputStream("f"))` — `BufferedInputStream` is a decorator that adds buffering to any `InputStream`, including another decorator. In backend services the same pattern is the entire mechanism behind Spring AOP: every `@Transactional`, `@Cacheable`, `@Async`, `@Retryable`, `@Timed`, `@PreAuthorize` annotation produces a proxy that wraps the original bean and intercepts calls to apply the cross-cutting concern. The caller thinks it's calling the service; it's actually calling a chain of decorators that happen to terminate in the real service.

The Proxy pattern is structurally identical to Decorator (same wrapping, same interface) but has a different *intent*: Proxy controls access (lazy initialisation, access control, remote, virtual), Decorator adds behaviour. In practice they collapse — Spring's `@Transactional` proxy both *adds behaviour* (transaction begin / commit / rollback) and *controls access* (it wouldn't make sense to call the inner method without the transaction). The reason the GoF separated them is intent, not implementation, and a senior engineer should be able to recognise either intent in the same code.

Spring produces these proxies in two flavours. JDK dynamic proxies are used when the target class implements an interface — the proxy is generated at runtime as a class implementing the same interface, delegating to an `InvocationHandler`. CGLIB proxies are used when there's no interface — the proxy is a *subclass* of the target class, with method overrides that call the interceptors. The difference matters at the call site: JDK proxies cannot be cast to the concrete class (only to the interface), CGLIB proxies cannot decorate `final` classes or `final` methods. Spring Boot 2.x switched the default from JDK proxies to CGLIB for `@Transactional` so that you can inject by concrete class as well as by interface — but `final` on a `@Transactional` method silently disables the transaction.

```java
// What you write:
@Service
class OrderService {
    @Transactional
    public void place(Order order) {
        orderRepo.save(order);
        eventPublisher.publish(new OrderPlaced(order.getId()));
    }
}

// What Spring generates at runtime (simplified — real Spring uses CGLIB or JDK proxies):
class OrderService$Proxy extends OrderService {
    private final TransactionTemplate tx;
    private final OrderService delegate;
    @Override
    public void place(Order order) {
        tx.executeWithoutResult(status -> {
            try {
                delegate.place(order);            // the real method
            } catch (RuntimeException e) {
                status.setRollbackOnly();         // decorator behaviour: rollback on throw
                throw e;
            }
        });
        // decorator behaviour: commit happens here on clean return
    }
}
```

```text
   Caller  ──►  OrderService$Proxy (decorator: @Transactional)
                       │  begins tx
                       │  delegates
                       ▼
                  OrderService$Proxy (decorator: @Cacheable, if applied)
                       │  checks cache
                       │  delegates on miss
                       ▼
                  OrderService$Proxy (decorator: @Timed / metrics)
                       │  starts timer
                       │  delegates
                       ▼
                  OrderService (the real bean)
                       │  calls repo, publishes event
                       ▼
                   orderRepo, eventPublisher
```

The Flyweight pattern is the third structural pattern about wrapping, with a different goal: sharing state to reduce memory. Instead of one object per occurrence, you keep one *canonical* object and many lightweight references to it. The classic Java example is `Integer.valueOf(-128..127)` — the JVM caches `Integer` instances for that range, so `Integer.valueOf(100) == Integer.valueOf(100)` returns `true` (same object) while `Integer.valueOf(1000) == Integer.valueOf(1000)` returns `false` (different objects, only the values are equal). In backend services the Flyweight shows up in string interning (the JVM's `String.intern()` pool, the `Integer`/`Long`/`Boolean` caches, the `Boolean.TRUE` constant), in HTTP header name normalisation (Spring's `HttpHeaders` interns common header names to avoid one `String` per request), in connection pool objects (each `Connection` is a heavyweight object reused across many requests rather than allocated per request), and in enum singletons (each enum constant is a single instance shared across the whole JVM).

```java
// Flyweight — canonical instances for the small, hot set; new instances for the long tail.
public final class Currency {
    private static final Map<String, Currency> CACHE = new ConcurrentHashMap<>();
    private final String code;
    private Currency(String code) { this.code = code; }
    public static Currency of(String code) {
        return CACHE.computeIfAbsent(code, Currency::new);  // shared instance for "USD"
    }
}
// Currency.of("USD") == Currency.of("USD") everywhere in the JVM — one object,
// no matter how many transactions reference it. The String "USD" is stored once.
```

The production failure mode for Decorator/Proxy is the *self-invocation* bug: a `@Transactional` method `place()` calls a `@Transactional` method `recordAudit()` on the *same* bean via `this.recordAudit()` — the call bypasses the proxy, runs in the original transaction (or no transaction), and the audit row is committed even when `place()` rolls back. The fix is either to extract the inner method into a separate bean (so the call goes through the proxy) or to inject the proxy as `self` and call `self.recordAudit()`. The failure mode for Flyweight is *over-sharing*: caching objects that turn out to be mutable, where one caller's modification corrupts every other caller's view. The defence is to make flyweight objects deeply immutable (final fields, defensive copies on construction) — the same contract as Java's `Integer`, `String`, and `BigDecimal`.

### Facade Pattern: Providing simplified unified interfaces over complex subsystem graphs

A Facade is a single front-door class that exposes a small, coherent API over a tangle of internal collaborators. The GoF formulation: "provide a unified interface to a set of interfaces in a subsystem." The caller asks `checkoutService.checkout(cart, customer)` and gets back an `OrderId`; behind the facade, the service orchestrates five repositories, two payment gateways, an inventory service, a tax calculator, a shipping estimator, and three event publishers. The caller doesn't know any of that. The facade isn't *hiding* the subsystem (the classes are still public, still injectable, still testable in isolation) — it's *deflecting* the casual caller away from having to learn the subsystem's internals in order to do the most common thing.

In Spring, the `@Service` stereotype is almost always a facade. A typical `OrderService` has five or six injected dependencies and a single public method like `place(OrderRequest)` that does the entire checkout dance: validate the cart, lock inventory, charge the card, persist the order, publish the event, send the confirmation email. The controller layer calls only `orderService.place(...)`; the controller doesn't know that there are five repos involved. This is the pattern that keeps controllers thin and lets you swap the entire orchestration logic (e.g. from synchronous to saga-based) without touching the controller.

The Composite pattern is the sibling that makes the facade possible when the subsystem is recursive: a tree of objects where every node — leaf or container — implements the same interface, and a container delegates to its children. The GoF example is a GUI widget tree where `Window` contains `Panel` contains `Button`, and calling `draw()` on the window draws everything. In backend code the Composite shows up in middleware pipelines (each middleware implements `handle(request, next)` and calls `next.handle()` — the chain is a linear composite), in content-negotiation chains (each `HttpMessageConverter` is asked `canRead`; the chain is tried in order), and in domain models where an `Order` contains `OrderLine`s contains `Discount`s, and `totalCost()` recursively sums down the tree.

```java
// Facade — one method, five collaborators, one coherent operation.
@Service
@Transactional
class CheckoutService {   // facade
    private final CartRepository carts;
    private final InventoryService inventory;
    private final PaymentGateway payments;
    private final TaxCalculator tax;
    private final OrderRepository orders;
    private final EventPublisher events;
    private final Mailer mailer;

    CheckoutService(/* … six dependencies injected … */) { /* … */ }

    public OrderId checkout(CartId cartId, CustomerId custId) {
        Cart cart = carts.find(cartId).orElseThrow(() -> new CartNotFoundException(cartId));
        inventory.lock(cart.lineItems());                    // reserve stock
        Money subtotal = cart.subtotal();
        Money taxAmount = tax.compute(subtotal, custId);     // tax calculation
        Money total = subtotal.add(taxAmount);
        PaymentReceipt receipt = payments.charge(total, custId);  // payment
        Order order = Order.placed(cart, taxAmount, total, receipt);
        orders.save(order);
        events.publish(new OrderPlaced(order.id(), custId));
        mailer.sendConfirmation(custId, order);
        return order.id();
    }
}
```

```java
// Composite — same interface for leaf and container; container recurses.
interface Priced { Money price(); }

record LineItem(String sku, Money unitPrice, int qty) implements Priced {
    public Money price() { return unitPrice.multiply(qty); }   // leaf
}

record Order(List<LineItem> items, List<Discount> discounts) implements Priced {
    public Money price() {                                       // container
        Money itemsSubtotal = items.stream().map(Priced::price).reduce(Money.ZERO, Money::add);
        Money discountsTotal = discounts.stream().map(Priced::price).reduce(Money.ZERO, Money::add);
        return itemsSubtotal.subtract(discountsTotal);
    }
}
// Order.price() recurses into LineItem.price(); a Discount wrapping an Order recurses back.
```

The Spring MVC request-handling pipeline is itself a Composite: `DispatcherServlet` calls `HandlerMapping` to find the handler, `HandlerAdapter` to invoke it, `HandlerInterceptor` chain to apply pre/post logic, `HandlerExceptionResolver` chain to handle errors, `ViewResolver` chain to render the response. Each chain is a composite of objects implementing the same interface; the dispatcher doesn't know what each link does, only that the chain handles the request end-to-end.

The production failure mode for the Facade is the *god service*: a facade that has accreted every operation the application ever needed, growing to 3 000 lines and 25 dependencies until it can't be tested, can't be reviewed, and can't be changed without breaking something. The defence is to recognise when a facade has grown beyond a single responsibility and split it — `CheckoutService` becomes `CheckoutService` + `RefundService` + `OrderHistoryService`, each with its own coherent API and its own subset of collaborators. The failure mode for the Composite is *incorrect recursion*: a tree where a parent accidentally includes itself in its children, or where a leaf is mistakenly treated as a container and tries to iterate an empty children list (or worse, an infinite one). The defence is to make the `Priced` interface sealed (Java 17+) or otherwise closed, so a leaf cannot accidentally grow a `children()` method.

## Cross-Ecosystem Code

The seven structural patterns expressed across ecosystems. The shape is the same; only the framework machinery differs.

```java
// Spring Boot — Adapter via @Component implementing a port interface; Decorator via @Transactional proxy.
interface PaymentGateway { Receipt charge(Money m, CustomerId c); }
@Component class StripeAdapter implements PaymentGateway { /* … */ }
@Service class OrderService {
    @Transactional @Cacheable("orders")
    public Order find(OrderId id) { return repo.find(id); }   // proxy = decorator
}
```

```typescript
// Express — Adapter via wrapper class; Decorator via higher-order function (middleware is itself the pattern).
class StripePaymentAdapter implements PaymentGateway {
  constructor(private readonly stripe: Stripe) {}
  charge(m: Money, c: CustomerId): Receipt { /* translate */ }
}
// Decorator as a higher-order function:
const withMetrics = <T extends object>(target: T): T => new Proxy(target, {
  get(t, prop, receiver) {
    if (typeof t[prop] === 'function') {
      return (...args: unknown[]) => { const t0 = Date.now(); const r = t[prop].apply(t, args); metrics.observe(Date.now() - t0); return r; };
    }
    return Reflect.get(t, prop, receiver);
  }
});
```

```python
# Django — Adapter as a class implementing a duck-typed interface; Decorator via functools.wraps.
class StripePaymentAdapter:   # Adapter
    def __init__(self, stripe): self._stripe = stripe
    def charge(self, money, customer): ...   # returns Receipt

import functools
def with_metrics(fn):           # Decorator (Python's decorator syntax *is* the pattern)
    @functools.wraps(fn)
    def wrapper(*args, **kwargs):
        t0 = time.perf_counter(); r = fn(*args, **kwargs); metrics.observe(time.perf_counter() - t0); return r
    return wrapper
```

```php
// Laravel — Adapter implementing an interface bound in the container; Decorator via middleware.
class StripePaymentAdapter implements PaymentGateway {
    public function __construct(private StripeClient $stripe) {}
    public function charge(Money $m, CustomerId $c): Receipt { /* … */ }
}
// Facade via Laravel Facades (literally the pattern's namesake): Cache::get() fronts the cache subsystem.
// Decorator via HTTP middleware:
Route::get('/orders', [OrderController::class, 'index'])->middleware(['auth', 'throttle:60,1', 'metrics']);
```

## How This Connects to the Frameworks

Spring's AOP subsystem is the structural-pattern engine. `@Transactional`, `@Cacheable`, `@Async`, `@Retryable`, `@Timed`, `@PreAuthorize` are all Decorator/Proxy patterns applied via bytecode weaving at bean-initialisation time. Spring's `HandlerAdapter`, `HandlerMapping`, `HandlerExceptionResolver`, `HttpMessageConverter`, `ViewResolver` chains are all Composite patterns. Spring's `@Service` classes are Facades. Spring's `Integer`/`Boolean`/`String` interning is Flyweight. In Laravel the HTTP middleware pipeline is the same Composite, the service container's contextual binding is the Adapter, and Laravel's own `Facade` class (Cache, Log, Mail — capital F) is literally the Facade pattern implemented as a static-method shortcut to a resolved instance. In Django the middleware stack and the `HttpRequest`/`HttpResponse` chain are the Composite; the ORM's `QuerySet` is a Flyweight (lazy, chainable, evaluated once). In Express the middleware chain `(req, res, next)` is the Composite and any wrapper class is the Adapter.

## How This Connects to the Runtimes

JDK dynamic proxies generate classes at runtime via `Proxy.newProxyInstance`, which uses `sun.misc.Unsafe` to define a class without going through the classloader's normal `defineClass` path — this is fast (~µs) but produces classes that aren't visible to tools that scan only the classpath at boot. CGLIB (and its successor ByteBuddy, which Spring Boot 2.x+ uses under the hood) generates bytecode via ASM, producing real `.class`-equivalent artifacts in memory. On Node, the `Proxy` global is a built-in language feature, not a runtime trick — every modern Express middleware is a function that returns a function, which is the structural equivalent. On CPython, decorators are a syntactic feature (`@decorator` desugars to `decorator(func)`), but they wrap at import time, not lazily. On PHP, the `__invoke` magic method and anonymous classes provide the same wrapping capability, but each PHP-FPM worker re-wraps on every request, which is why Laravel's container resolution is measurably slower than Spring's.

## Cross-Runtime Comparison

| Pattern | Spring (Java) | Express / NestJS (TS) | Django (Python) | Laravel (PHP) |
|---|---|---|---|---|
| Adapter | `@Component implements Port` | wrapper class | duck-typed class | `app()->bind(Interface, Impl)` |
| Bridge | two `@Component` hierarchies | two interface hierarchies | two ABCs | two contracts resolved by container |
| Composite | interceptor / converter chains | middleware chain | middleware stack | middleware pipeline |
| Decorator | AOP proxy (`@Transactional`, etc.) | higher-order function / `Proxy` | `@decorator` syntax | middleware + service container wrapping |
| Facade | `@Service` stereotype | orchestrator service class | service module | `Facade` base class + `@Service` |
| Flyweight | `Integer.valueOf`, `String.intern`, enum singletons | string pool, `Symbol` | small-int cache (−5..256), `intern` | `Str::of` cache, container singletons |
| Proxy | JDK dynamic proxy / CGLIB subclass | `Proxy` global | `__getattr__` descriptors | `__call` magic + container resolution |
