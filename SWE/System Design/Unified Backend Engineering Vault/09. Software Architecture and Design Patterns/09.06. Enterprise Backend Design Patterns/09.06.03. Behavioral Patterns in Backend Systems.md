# 09.06.03. Behavioral Patterns in Backend Systems

## What This Is

Behavioral patterns govern *how objects talk to each other* — who sends what to whom, in what order, with what coupling. Where creational patterns answered "how is this born?" and structural patterns answered "how do these sit together?", behavioral patterns answer "what is the protocol between them?". They are the patterns you reach for when the algorithm in question doesn't belong to any single object but is instead a conversation between several — a request that gets passed down a chain, a state transition that fires notifications, a strategy that gets picked based on a runtime argument, a traversal that visits every node in a structure.

The GoF (Gamma, Helm, Johnson, Vlissides 1994) catalogues eleven behavioral patterns: Chain of Responsibility, Command, Interpreter, Iterator, Mediator, Memento, Observer, State, Strategy, Template Method, Visitor. In modern backend code the most load-bearing are Strategy (every `@Qualifier`-selected implementation), Observer (every `ApplicationEventPublisher` + `@EventListener` pair), Chain of Responsibility (every middleware pipeline), Template Method (every `JdbcTemplate` / `RestTemplate` / `AbstractController`), and Command (every `Runnable`, `CommandLineRunner`, and CQRS write-side command). The remaining six show up less loudly but are still present: Iterator in every `ResultSet` cursor and every `for (X x : collection)`, Mediator in every service that knows about N collaborators that shouldn't know about each other, Memento in every `serializable` snapshot of an aggregate, Visitor in every AST walker, State in every order-status state machine.

The reason these patterns matter even when the framework provides them is that the *choice of pattern* changes the coupling structure of the codebase. Strategy keeps the call site dumb and pushes the choice into a delegate; State makes the choice a property of the object itself; Command packages the choice into a serialisable object that can cross thread, process, and time. They look similar from outside ("some object decides what to do") but the seams sit in different places, and getting the seam wrong produces a different maintenance disaster in each case.

## The Details

### Strategy Pattern: Decoupling and swapping business algorithms at runtime (e.g., dynamic payment p...

The Strategy pattern encapsulates a family of interchangeable algorithms behind a common interface, so the caller can swap one for another without changing its own code. The GoF formulation: "define a family of algorithms, encapsulate each one, and make them interchangeable. Strategy lets the algorithm vary independently from clients that use it." The caller has a reference to a `PricingStrategy` and calls `strategy.price(cart)`; whether the underlying object is `RegularPricing`, `DiscountPricing`, or `BulkPricing` is invisible to the caller. The choice of which concrete strategy to use is made once, at wiring time, and the call site never has to change.

In Spring, the canonical implementation is `@Component`-annotated strategies registered in the container and selected by `@Qualifier` at the injection point. Spring 4+ also supports `List<Strategy>` injection — every bean implementing the interface gets injected as a list, and the caller can pick at runtime by key (typically via a `Map<String, Strategy>` built from each bean's `getName()`):

```java
// Strategy interface — the contract.
public interface PricingStrategy {
    Money price(Cart cart);
    String handles();      // selector key, e.g. "regular" / "bulk" / "discount"
}

@Component class RegularPricing implements PricingStrategy {
    public Money price(Cart c) { return c.subtotal(); }
    public String handles()    { return "regular"; }
}
@Component class BulkPricing implements PricingStrategy {
    public Money price(Cart c) { return c.subtotal().multiply(c.totalQty() > 100 ? "0.9" : "1"); }
    public String handles()    { return "bulk"; }
}

// Caller — doesn't know which strategies exist; picks by runtime key.
@Service
class PricingService {
    private final Map<String, PricingStrategy> byKey;
    PricingService(List<PricingStrategy> all) {
        byKey = all.stream().collect(Collectors.toMap(PricingStrategy::handles, s -> s));
    }
    public Money price(Cart cart, String strategyKey) {
        var s = byKey.get(strategyKey);
        if (s == null) throw new IllegalArgumentException("unknown pricing: " + strategyKey);
        return s.price(cart);
    }
}
```

```java
// @Qualifier at the injection point — selection made at wiring time, not runtime.
@Service
class TaxService {
    private final TaxCalculator usTax;       // only one bean matches @Qualifier("us")
    TaxService(@Qualifier("us") TaxCalculator usTax) { this.usTax = usTax; }
}
```

The State pattern is the close cousin of Strategy — same structure (an interface with multiple implementations, a delegate held by the caller), different intent. Where Strategy's choice is made *externally* by the caller (or by the wiring), State's choice is made *internally* by the object itself as a function of its current state. The GoF example is a `TCPConnection` whose `open()` behaves differently depending on whether it's `TCPEstablished`, `TCPListening`, or `TCPClosed`. In backend code the State pattern is the natural fit for an order's lifecycle: `Order` in the `DRAFT` state accepts `addItem()` but rejects `ship()`; in the `PAID` state it accepts `ship()` but rejects `addItem()`; in the `SHIPPED` state it rejects both. The state machine is the structure; the State pattern is the implementation.

```java
// State pattern — the Order delegates to its current state object.
sealed interface OrderState permits Draft, Paid, Shipped, Cancelled {
    OrderState addItem(Order o, LineItem i);
    OrderState pay(Order o, Payment p);
    OrderState ship(Order o);
    String status();
}
final class Draft implements OrderState {
    public OrderState addItem(Order o, LineItem i) { o.itemsInternal().add(i); return this; }
    public OrderState pay(Order o, Payment p)     { o.recordPayment(p); return new Paid(); }
    public OrderState ship(Order o)               { throw new IllegalStateException("cannot ship unpaid order"); }
    public String status()                        { return "DRAFT"; }
}
final class Paid implements OrderState {
    public OrderState addItem(Order o, LineItem i) { throw new IllegalStateException("cannot modify paid order"); }
    public OrderState pay(Order o, Payment p)      { throw new IllegalStateException("already paid"); }
    public OrderState ship(Order o)                { o.markShipped(); return new Shipped(); }
    public String status()                         { return "PAID"; }
}
// Order transitions: state = state.addItem(...); — the call site is uniform.
```

The Command pattern is the third member of the behavior-selection family, and it differs by *packaging the request as an object*. Where Strategy picks an algorithm and State picks a behaviour, Command takes a request (with all its arguments) and turns it into a value that can be stored, queued, retried, undone, or logged. The GoF formulation: "encapsulate a request as an object." In Spring this is `Runnable` (a no-arg command), `CommandLineRunner` (a command that runs at app startup), `@Scheduled` methods (commands that run on a timer), and any CQRS write-side `CommandHandler` (a command that is part of the application's protocol). The value of packaging is that the *decision* to do something and the *execution* of that something can be separated in time and space — a request comes in over HTTP, becomes a `PlaceOrderCommand` object, gets pushed onto a Kafka topic, gets consumed by a worker ten seconds later, gets executed, gets logged for replay.

```java
// Command — a request as an object. Can be queued, logged, retried, undone.
public sealed interface OrderCommand permits PlaceOrder, CancelOrder, RefundOrder {}
public record PlaceOrder(UUID orderId, UUID customerId, List<LineItem> items, Instant at) implements OrderCommand {}
public record CancelOrder(UUID orderId, String reason, Instant at) implements OrderCommand {}

// Command handler — one per command type. Looked up by type, executes the command.
@Component
class PlaceOrderHandler {
    private final OrderRepository repo; private final EventPublisher events;
    PlaceOrderHandler(OrderRepository repo, EventPublisher events) { this.repo = repo; this.events = events; }
    @Transactional
    public void handle(PlaceOrder cmd) {
        var order = Order.place(cmd.orderId(), cmd.customerId(), cmd.items());
        repo.save(order);
        events.publish(new OrderPlaced(order.id(), cmd.at()));
    }
}

// Spring's CommandLineRunner is a Command — runs once at app startup.
@Component
class BootstrapData implements CommandLineRunner {
    public void run(String... args) { /* seed reference data */ }
}
```

The production failure mode for the family is *silent strategy drift*: a `@Component` strategy bean that is correctly selected at boot, but whose internal state was loaded from a config file that has since been rotated, so the bean keeps using stale parameters. This is the same failure as the "leaky factory" in creational patterns — the strategy is a singleton, it was constructed once, and the world has moved on. The fix is to either re-resolve the strategy on each call (return a `StrategyFactory` from the container, not a `Strategy`) or to make the strategy's `price()` method re-read its parameters from a `@RefreshScope`-annotated config bean. For State, the failure mode is *bypassing the state machine*: a developer who calls `order.setStatus("SHIPPED")` directly instead of `order.ship()`, leaving the state object out of sync with the status field. The fix is to make `setStatus` package-private and force all transitions through the State-typed methods.

### Observer Pattern: In-memory event dispatching and notification pipelines

The Observer pattern defines a one-to-many dependency between objects: when one object (the subject) changes state, all its dependents (the observers) are notified automatically. The GoF formulation: "define a one-to-many dependency between objects so that when one object changes state, all its dependents are notified and updated automatically." In modern backend code this is the in-process event bus — the publisher doesn't know how many listeners exist, what they do, or whether they succeeded; the listeners subscribe to event types and react when those types appear. The pattern is the foundation of decoupling in domain events, in UI frameworks (the original Smalltalk Model-View-Controller used Observer for view refresh), and in any "publish without caring who listens" seam.

In Spring, the pattern is implemented by `ApplicationEventPublisher` (the subject) and `@EventListener` / `ApplicationListener` (the observers). The publisher calls `publisher.publish(new OrderPlaced(orderId))`; the framework finds every bean with an `@EventListener`-annotated method that accepts `OrderPlaced` and calls it. By default the listeners run synchronously in the publisher's thread; `@TransactionalEventListener` defers the call until the current transaction commits (so a post-commit email isn't sent if the transaction rolls back); `@EventListener` + `@Async` runs the listener in a separate thread pool. The choice between these is significant — synchronous listeners share the transaction and can roll it back by throwing; async listeners don't, which means an async email failure won't roll back the order but also won't be retried unless you've added a queue.

```java
// Observer pattern — Spring's ApplicationEventPublisher + @EventListener.
public record OrderPlaced(UUID orderId, UUID customerId, Instant at) {}

@Service
class OrderService {   // subject
    private final ApplicationEventPublisher publisher;
    private final OrderRepository repo;
    OrderService(ApplicationEventPublisher p, OrderRepository r) { publisher = p; repo = r; }

    @Transactional
    public void place(Order order) {
        repo.save(order);
        publisher.publishEvent(new OrderPlaced(order.id(), order.customerId(), Instant.now()));
        // publisher doesn't know how many listeners exist or what they do
    }
}

@Component
class InventoryReservationListener {   // observer #1
    private final InventoryService inventory;
    @EventListener @Async   // run in a separate thread, doesn't block the order
    public void on(OrderPlaced e) { inventory.reserve(e.orderId()); }
}

@Component
class ConfirmationEmailListener {      // observer #2
    private final Mailer mailer;
    @EventListener @TransactionalEventListener(phase = AFTER_COMMIT)
    // runs AFTER the order transaction commits — won't fire on rollback
    public void on(OrderPlaced e) { mailer.sendConfirmation(e.customerId(), e.orderId()); }
}

@Component
class AnalyticsListener {              // observer #3
    @EventListener
    public void on(OrderPlaced e) { analytics.track("order_placed", e); }
}
```

```text
   OrderService (subject)
        │ publishEvent(OrderPlaced)
        ▼
   ApplicationEventPublisher  ──► multicast to all @EventListener beans that accept OrderPlaced
        │
        ├──► InventoryReservationListener  (async, separate thread)
        ├──► ConfirmationEmailListener     (after-commit, separate txn phase)
        └──► AnalyticsListener             (synchronous, same thread)
```

The Mediator pattern is the sibling of Observer with the direction of coupling inverted. Where Observer lets the subject broadcast without knowing its observers, Mediator centralises the communication between *peers* that would otherwise talk directly to each other. The GoF example is a dialog box where buttons, text fields, and list boxes all communicate through a `DialogMediator` rather than referencing each other directly. In backend code the Mediator is every `@Service` class that orchestrates a workflow between N collaborators that shouldn't know about each other: a `CheckoutService` that calls `InventoryService`, `PaymentGateway`, `ShippingService`, and `EventPublisher` is a mediator — none of those four know about each other; the mediator is the only one who knows the choreography. Spring Integration's `IntegrationFlow` and Apache Camel's `RouteBuilder` are explicit Mediator implementations for messaging workflows; the MediatR library in .NET is a Mediator pattern specialised for command/query dispatch.

```java
// Mediator — knows about all the peers; the peers don't know about each other.
@Service
class CheckoutMediator {   // the mediator
    private final CartRepository carts;
    private final InventoryService inventory;
    private final PaymentGateway payments;
    private final ShippingService shipping;
    private final EventPublisher events;
    // all five injected — the mediator owns the choreography

    @Transactional
    public OrderId checkout(CartId cartId, CustomerId custId, Address shipTo) {
        Cart cart = carts.find(cartId).orElseThrow();
        inventory.reserve(cart);                                  // peer 1
        var receipt = payments.charge(cart.total(), custId);      // peer 2
        var order = Order.placed(cart, receipt);
        var shipment = shipping.schedule(order, shipTo);          // peer 3
        events.publish(new OrderPlaced(order.id(), shipment.id()));// peer 4
        return order.id();
    }
    // inventory doesn't know about payments; payments doesn't know about shipping.
}
```

The production failure mode for Observer is *transactional surprise*: a developer adds a new `@EventListener` (synchronous, default) that calls a slow third-party API; suddenly every `place()` call takes 2 s instead of 50 ms because the publisher is blocked on the new listener. The fix is to audit every `@EventListener` and decide explicitly: synchronous (in-txn, can roll back), `@TransactionalEventListener` (after-commit, in-txn of its own), or `@EventListener @Async` (out-of-txn, separate thread pool). The failure mode for Mediator is the *god service*: the mediator that started as a checkout orchestrator accretes refund logic, return logic, exchange logic, and becomes a 2 000-line class with 15 dependencies. The defence is the same as for Facade — split when the responsibility broadens, and prefer one mediator per business transaction type.

### Chain of Responsibility: Linear request processing pipelines and middleware interceptor implement...

The Chain of Responsibility routes a request along a sequence of handlers, each of which can either handle the request, pass it to the next handler, or terminate the chain. The GoF formulation: "avoid coupling the sender of a request to its receiver by giving more than one object a chance to handle the request. Chain the receiving objects and pass the request along the chain until an object handles it." In modern backend code this is *every* middleware pipeline: Express `(req, res, next)`, Django middleware `__init__`/`__call__`, Laravel HTTP middleware `handle($request, $next)`, Spring's `HandlerInterceptor` chain (`preHandle` / `postHandle` / `afterCompletion`), Spring Security's `FilterChainProxy`, and the servlet `Filter` chain itself. The sender (the HTTP framework) doesn't know which filter will handle auth, which will handle logging, which will handle CORS — it just kicks off the chain.

```java
// Spring HandlerInterceptor — the canonical CoR member.
@Component
class AuthInterceptor implements HandlerInterceptor {
    private final TokenVerifier verifier;
    @Override
    public boolean preHandle(HttpServletRequest req, HttpServletResponse resp, Object handler) {
        var auth = req.getHeader("Authorization");
        if (auth == null || !auth.startsWith("Bearer ")) { resp.setStatus(401); return false; }
        var principal = verifier.verify(auth.substring(7));   // throws on invalid token
        req.setAttribute("principal", principal);
        return true;   // continue down the chain
    }
}
// Registered in WebMvcConfigurer:
@Override public void addInterceptors(InterceptorRegistry r) {
    r.addInterceptor(new LoggingInterceptor()).order(1);
    r.addInterceptor(new CorsInterceptor()).order(2);
    r.addInterceptor(new AuthInterceptor()).order(3);
    r.addInterceptor(new RateLimitInterceptor()).order(4);
}
```

```text
   Request ──►  LoggingInterceptor (preHandle: log the request)
                     │
                     ▼
                CorsInterceptor (preHandle: add CORS headers)
                     │
                     ▼
                AuthInterceptor (preHandle: verify token; 401 if invalid → chain stops)
                     │
                     ▼
                RateLimitInterceptor (preHandle: 429 if over limit → chain stops)
                     │
                     ▼
                HandlerAdapter → @RestController method
                     │
                     ▼  (response coming back up)
                RateLimitInterceptor.postHandle
                     │
                     ▼
                AuthInterceptor.postHandle
                     │
                     ▼
                CorsInterceptor.postHandle
                     │
                     ▼
                LoggingInterceptor.afterCompletion (log duration + status)
                     │
                     ▼
                Response ──► client
```

The Template Method pattern is the behavioural sibling that fixes the *algorithm skeleton* in a base class and lets subclasses override individual steps. The GoF formulation: "define the skeleton of an algorithm in an operation, deferring some steps to subclasses. Template Method lets subclasses redefine certain steps of an algorithm without changing the algorithm's structure." In Spring this is `JdbcTemplate` (the `execute` / `query` / `update` methods are the template; the `RowMapper` / `PreparedStatementCallback` / `ResultSetExtractor` you pass in are the overridable steps), `RestTemplate` (the `execute` method is the template; the `RequestCallback` / `ResponseExtractor` are the steps), `TransactionalRepository` / `AbstractRepository`, and `WebMvcConfigurer` (the framework calls the template methods; you override the ones you care about). The Python equivalent is the `@abstractmethod`-decorated method on an ABC; the Node equivalent is a function that takes callbacks or strategy objects.

```java
// Template Method — JdbcTemplate owns the skeleton (conn / prepare / execute / iterate / close);
// you supply the steps (SQL, parameter binding, row mapping).
List<Order> orders = jdbcTemplate.query(
    "SELECT id, customer_id, placed_at FROM orders WHERE customer_id = ?",
    (rs, rowNum) -> new Order(                       // the overridable step: RowMapper
        rs.getObject("id", UUID.class),
        rs.getObject("customer_id", UUID.class),
        rs.getTimestamp("placed_at").toInstant()),
    customerId);                                      // parameter binding
// JdbcTemplate internally: opens conn, prepares stmt, binds params, executes,
// iterates ResultSet calling your mapper, closes everything, handles SQLException → DataAccessException.
```

The Visitor pattern is the third structural-behavioural pattern that comes up in backend code, usually in surprising places. The GoF formulation: "represent an operation to be performed on the elements of an object structure. Visitor lets you define a new operation without changing the classes of the elements on which it operates." The dual-dispatch mechanism lets you add a new *operation* (a new Visitor) without modifying the element classes; the trade-off is that adding a new *element type* requires changing every Visitor. In backend code Visitor shows up in AST walkers (a SQL parser, a JSON schema validator, a rules engine), in serialisation frameworks (Jackson's `JsonSerializerVisitor`), and in event-sourcing projections (a projection that visits every event type and updates its read model). It is overkill for two-element hierarchies; it earns its keep at five-plus element types × five-plus operations.

```java
// Visitor — add operations without modifying the event classes.
sealed interface AccountEvent permits MoneyDeposited, MoneyWithdrawn {
    <R> R accept(AccountEventVisitor<R> v);
}
record MoneyDeposited(UUID id, BigDecimal amount) implements AccountEvent {
    public <R> R accept(AccountEventVisitor<R> v) { return v.visit(this); }
}
record MoneyWithdrawn(UUID id, BigDecimal amount) implements AccountEvent {
    public <R> R accept(AccountEventVisitor<R> v) { return v.visit(this); }
}
interface AccountEventVisitor<R> {
    R visit(MoneyDeposited e);
    R visit(MoneyWithdrawn e);
}
// New operation — no event classes touched.
class BalanceProjector implements AccountEventVisitor<Void> {
    BigDecimal balance = BigDecimal.ZERO;
    public Void visit(MoneyDeposited e)  { balance = balance.add(e.amount());    return null; }
    public Void visit(MoneyWithdrawn e)  { balance = balance.subtract(e.amount()); return null; }
}
// Another operation — still no event classes touched.
class JsonSerialiser implements AccountEventVisitor<String> {
    public String visit(MoneyDeposited e)  { return "{\"type\":\"dep\",\"amt\":" + e.amount() + "}"; }
    public String visit(MoneyWithdrawn e)  { return "{\"type\":\"wd\",\"amt\":" + e.amount() + "}"; }
}
```

The Iterator and Memento patterns are the quieter members of the family. Iterator (GoF: "provide a way to access the elements of an aggregate object sequentially without exposing its underlying representation") is so universal it has been absorbed into language syntax — every `for (X x : collection)` in Java, every `for x in collection` in Python, every `for (const x of collection)` in JavaScript is the Iterator pattern, with `Iterator` / `__iter__` / `Symbol.iterator` as the contract. In backend code the pattern shows up wherever a result set is too large to materialise: JDBC `ResultSet` is an iterator over database rows, MongoDB cursors are iterators, Kafka consumers are iterators over partition offsets, JPA `Stream<T>` results are iterators that hold a database connection open. Memento (GoF: "without violating encapsulation, capture and restore an object's internal state so that the object can be restored to this state later") is the pattern behind `Serializable` snapshots, `Object.clone()`, undo stacks in editors, and the snapshot table in event sourcing — see [[09.05.02. Event Sourcing Mechanics]] for the deep dive on how Memento composes with event log replay.

The production failure mode for Chain of Responsibility is *order-dependence*: an auth interceptor placed after a logging interceptor sees 401s logged as successful requests (the log was written before auth ran), or a rate limiter placed before auth lets any anonymous traffic exhaust the budget. The fix is to make the order explicit (`@Order(N)` / `addInterceptor().order(N)`) and to write a test that asserts the order on every release. For Template Method, the failure mode is *incomplete override*: a subclass that overrides `preHandle` but forgets `afterCompletion`, leaking a resource (an open file, an unclosed span). For Iterator, the failure mode is *unclosed cursor*: a JPA `Stream<T>` result that is never wrapped in try-with-resources, holding a database connection open until the next GC. For Visitor, the failure mode is *missing the sealed-interface discipline* in modern Java — if `AccountEvent` isn't `sealed`, the compiler can't prove that every Visitor handles every event type, and the runtime throws on the unhandled case.

## Cross-Ecosystem Code

The behavioral patterns expressed across ecosystems. The middleware chain (Chain of Responsibility) is the most visible — every framework has its own spelling.

```java
// Spring Boot — Strategy via @Qualifier / List<Strategy>; Observer via @EventListener;
// Chain of Responsibility via HandlerInterceptor; Template Method via JdbcTemplate.
@Service class PricingService {
    private final Map<String, PricingStrategy> byKey;
    PricingService(List<PricingStrategy> all) { byKey = all.stream().collect(toMap(PricingStrategy::handles, s->s)); }
    public Money price(Cart c, String k) { return byKey.get(k).price(c); }
}
@Component class AuthInterceptor implements HandlerInterceptor {
    @Override public boolean preHandle(HttpServletRequest r, HttpServletResponse s, Object h) {
        return /* verify */ true;
    }
}
```

```typescript
// Express — Chain of Responsibility via middleware; Strategy via dependency injection;
// Observer via EventEmitter; Template Method via higher-order function.
const auth = (req: Request, res: Response, next: NextFunction) => {
  const token = req.headers.authorization;
  if (!verify(token)) return res.status(401).json({ error: 'unauthorized' });
  next();
};
app.get('/orders', auth, rateLimit, async (req, res) => {
  const strategy = strategies[req.query.tier as string];
  res.json({ price: strategy.price(req.body.cart) });
});
// EventEmitter = Observer; strategy map = Strategy; middleware chain = CoR.
```

```python
# Django — middleware is Chain of Responsibility; signals are Observer; ABC is Template Method.
class AuthMiddleware:
    def __init__(self, get_response): self.get_response = get_response
    def __call__(self, request):
        if not verify(request.headers.get('Authorization', '')):
            return HttpResponse(status=401)
        return self.get_response(request)   # next()

from django.dispatch import receiver, Signal
order_placed = Signal()
@receiver(order_placed)   # Observer
def reserve_inventory(sender, **kwargs): InventoryService.reserve(sender.id)

# Template Method via ABC:
from abc import ABC, abstractmethod
class PricingStrategy(ABC):
    @abstractmethod
    def price(self, cart: Cart) -> Money: ...
```

```php
// Laravel — middleware is Chain of Responsibility; events are Observer;
// Service container + interface binding is Strategy; base controller is Template Method.
class AuthMiddleware {
    public function handle($request, Closure $next) {
        if (!verify($request->header('Authorization'))) return response('unauthorized', 401);
        return $next($request);
    }
}
// routes/api.php — the chain is the route's middleware list:
Route::get('/orders', [OrderController::class, 'index'])->middleware(['auth', 'throttle:60,1']);

// Observer via Event::listen / Event::dispatch
Event::listen(OrderPlaced::class, fn (OrderPlaced $e) => InventoryService::reserve($e->orderId));
```

## How This Connects to the Frameworks

Spring's `ApplicationEventPublisher` + `@EventListener` is the Observer pattern; its `HandlerInterceptor` chain and `Filter` chain are Chain of Responsibility; its `JdbcTemplate` / `RestTemplate` / `WebClient.Builder` are Template Method; its `@Qualifier` / `List<Strategy>` injection is Strategy; its `CommandLineRunner` / `ApplicationRunner` / `@Scheduled` are Command; its `WebMvcConfigurer` is Template Method at the framework level. In Express the middleware stack is Chain of Responsibility, the `EventEmitter` is Observer, the strategy pattern is a plain object literal keyed by request property. In Django the middleware stack and `dispatch.Signal` cover Chain of Responsibility and Observer; the `@abstractmethod` ABC covers Template Method and Strategy. In Laravel the HTTP middleware pipeline is Chain of Responsibility, the `Event` facade is Observer, the service container's interface binding is Strategy, and `Queue::push(ReusableCommand::class, $data)` is Command serialised to a queue.

## How This Connects to the Runtimes

The cost of behavioral patterns is dominated by *indirection*. Each strategy lookup is a map lookup (~10 ns), each event publish is a list iteration plus N method calls (~1 µs for a handful of listeners), each middleware hop is a method call into a closure that decides whether to call `next` (~100 ns). None of these are expensive in isolation, but they add up: a request that traverses 8 middleware filters, dispatches 3 events to 12 listeners, and uses a strategy map for routing is paying ~50 µs of pure indirection per request, which is fine at 10 000 req/s and noticeable at 100 000 req/s. The JVM mitigates this with JIT inlining of monomorphic call sites — a strategy field that always points to the same implementation gets inlined to a direct call after ~10 000 invocations. Node's V8 does the same. CPython does not — every method call goes through `__getattr__` lookup, which is part of why Python services have a per-request overhead floor of ~1 ms regardless of how little work the request does.

| Mediator | `@Service` orchestrator | orchestrator class | service module | `Bus::dispatch` (Laravel MediatR) |
| Chain of Responsibility | `HandlerInterceptor`, `Filter` | middleware `(req,res,next)` | middleware `__call__` | HTTP middleware `handle` |
| Template Method | `JdbcTemplate`, `RestTemplate` | higher-order function | ABC `@abstractmethod` | base controller / form |
| Iterator | `Iterator` / `Stream<T>` | `Symbol.iterator` | `__iter__` / `for x in` | `Iterator` / `Generator` |
| Visitor | sealed interface + `Visitor<R>` | discriminated union + switch | ABC + visitor class | interface + switch |
| Memento | `Serializable`, snapshot table | JSON snapshot | `pickle` / model snapshot | `Queue::later` payload |
