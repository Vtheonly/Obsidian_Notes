# 09.06.01. Creational Patterns in Backend Systems

## What This Is

Creational patterns govern *how objects come into existence* — who decides which concrete class to instantiate, when, and with what initial state. They sit between the call site (which asks for an object) and the constructor (which actually allocates one), and they exist because direct `new` calls leak implementation choices into the caller. When you write `new StripePaymentGateway(apiKey)` inside an order service, the service now knows about Stripe, about API keys, and about the gateway's constructor signature; you cannot swap to PayPal without recompiling. A creational pattern interposes a layer that hides those decisions, so the caller asks for an abstraction and the creational code decides what concrete thing to deliver.

In the GoF (Gamma, Helm, Johnson, Vlissides 1994) the creational patterns are five: Factory Method, Abstract Factory, Builder, Prototype, and Singleton. In modern backend systems the same five are still in play, but their centre of gravity has shifted: dependency injection containers (Spring's `ApplicationContext`, Laravel's service container, NestJS's providers) have *absorbed* most of the factory and singleton logic, so the patterns now show up either as framework annotations (`@Bean`, `@Component`, `@Scope("prototype")`) or as hand-rolled seams for cases the container cannot handle (test data builders, dynamic multi-tenant infrastructure, runtime-discovered plugin loading). Understanding the patterns matters because the framework conventions are themselves creational patterns — `@Bean` *is* a factory method, `@Scope("prototype")` *is* the prototype pattern, and the singleton scope is the singleton pattern with all the same hazards.

The cost of getting this wrong is coupling. A class that calls `new` everywhere is a class you cannot test in isolation (the test pulls in the real database, the real HTTP client, the real clock) and cannot extend without editing (every new variant requires a code change to the call site). The patterns below are the levers that let you keep the call site dumb and the wiring code smart — which is exactly the property a layered architecture needs to stay layered.

## The Details

### Factory Method and Abstract Factory: Dynamic instantiation of complex infrastructure adapters

A Factory Method is a method whose job is to return an object, where the *caller* doesn't know (and doesn't care) which concrete class will be returned. The classic GoF formulation is "define an interface for creating an object, but let subclasses decide which class to instantiate." In modern backend code the subclasses are usually gone — replaced by a single method that picks the implementation based on a runtime argument (a config key, a tenant id, a region tag). The Abstract Factory extends this to *families* of related objects: a `CloudInfrastructureFactory` returns a coherent set of `BlobStore` + `MessageQueue` + `KeyVault` objects that all belong to the same cloud, and you swap factories (AWS, Azure, GCP) to swap the whole family at once. The point of both patterns is the same: push the decision of *which concrete class to instantiate* out of the call site and into one place you can audit and change.

In Spring, the `@Bean`-annotated method *is* a factory method — the container calls it whenever something asks for the return type, and the body of the method is the creational logic. This is more powerful than it looks because the `@Bean` method has access to everything else in the container, the environment, and any runtime parameter you want to inject. The Abstract Factory shows up as a `@Configuration` class with several related `@Bean` methods that together form a coherent infrastructure family:

```java
// Abstract Factory: one @Configuration class per cloud, all beans swap together.
@Configuration
@Profile("aws")
class AwsInfrastructureFactory {
    @Bean BlobStore blobStore(S3Client s3)             { return new S3BlobStore(s3); }
    @Bean MessageQueue queue(SqsClient sqs)            { return new SqsMessageQueue(sqs); }
    @Bean KeyVault keyVault(KmsClient kms)             { return new KmsKeyVault(kms); }
}

@Configuration
@Profile("gcp")
class GcpInfrastructureFactory {
    @Bean BlobStore blobStore(Storage storage)         { return new GcsBlobStore(storage); }
    @Bean MessageQueue queue(Publisher publisher)      { return new PubSubMessageQueue(publisher); }
    @Bean KeyVault keyVault(KeyManagementService kms)  { return new KmsKeyVault(kms); }
}

// Call site — knows nothing about AWS vs GCP.
@Service
class InvoiceService {
    private final BlobStore store;
    private final MessageQueue queue;
    InvoiceService(BlobStore store, MessageQueue queue) { this.store = store; this.queue = queue; }
}
```

The hand-rolled Factory Method — without Spring — is still needed when the choice depends on a runtime argument the container can't see (tenant id, region, or a request-scoped header). The container will give you a single bean; you ask it for the *factory*, then call `factory.forTenant(tenantId)` to get the right implementation:

```java
interface PaymentGatewayFactory {
    PaymentGateway forRegion(String region);   // factory method
}

@Component
class RegionAwarePaymentGatewayFactory implements PaymentGatewayFactory {
    private final Map<String, PaymentGateway> byRegion;
    RegionAwarePaymentGatewayFactory(
            StripeGateway stripe, PayPalGateway paypal, AdyenGateway adyen) {
        byRegion = Map.of(
            "us", stripe, "eu", paypal, "apac", adyen);
    }
    @Override public PaymentGateway forRegion(String region) {
        var g = byRegion.get(region);
        if (g == null) throw new IllegalArgumentException("no gateway for region: " + region);
        return g;
    }
}
```

The Singleton pattern is the fifth GoF creational pattern and deserves a warning rather than a recipe. The GoF Singleton is "ensure a class has exactly one instance, and provide a global point of access to it" — typically implemented as a `static getInstance()` method with a private constructor. In a DI world this is an anti-pattern: it makes the class a global, hides the dependency from the constructor signature (so tests can't substitute it), and breaks in subtle ways under class loaders that aren't truly single-class-loader (OSGi, Spring Boot's nested jars, application servers). The modern equivalent is to make the class a `@Component` (or `@Singleton` in Jakarta, or a Laravel singleton binding) and let the container guarantee uniqueness — the *pattern* is preserved (one instance per application), but the *access* is via constructor injection, not via a global static call. The exception that still justifies a hand-rolled singleton is a process-wide resource that must exist before the DI container boots — typically a JVM-level cache (`Integer.valueOf` for −128..127, `Boolean.TRUE`), an in-process actor system root, or a global signal handler. Those have to be static because there is nothing else yet.

The Prototype pattern is "create new objects by copying a prototype instance" — `clone()` rather than `new`. In Spring it appears as `@Scope("prototype")`, which tells the container to return a fresh instance on every injection (versus the default singleton scope, which returns the same instance everywhere). The use case is a stateful, non-thread-safe object — a `StringBuilder`-style accumulator, a per-request `UserSession` holder, a JDBC `RowMapper` that holds transient column state — where sharing one instance across threads would corrupt state:

```java
@Component
@Scope("prototype")          // fresh instance every time it's injected
class OrderRowMapper implements RowMapper<Order> {
    private final Map<String, Integer> columnCache = new HashMap<>();  // mutable state
    @Override public Order mapRow(ResultSet rs, int rowNum) {
        // populates columnCache lazily on first call — NOT thread-safe across requests
        return /* … */;
    }
}
```

The production failure mode for the whole family is the *leaky factory*: a `@Bean` method that calls `new SomeClient(config)` where `config` is read from the environment once at boot, but the config changes at runtime (a rotated credential, a region failover). The bean was created once, holds the old client, and serves stale connections until the JVM restarts. The fix is to make the factory return a *delegate* that re-reads the config on each call, or to expose a `refresh()` endpoint that re-invokes the `@Bean` method and swaps the bean in the container — Spring Cloud's `@RefreshScope` does exactly this for Spring Cloud Config.

### Builder Pattern: Constructing immutable domain entities and complex query criteria objects

The Builder pattern separates the *specification* of a complex object from its *construction*. Instead of a constructor with twelve positional parameters — half of them nullable, half of them with default values you can't remember — you expose a builder object whose fluent methods (`withX`, `withY`, `build`) collect the parameters one at a time and then hand them to a private constructor in a single, validated, atomic call. The value is twofold: named parameters (the call site reads as English) and partial application (you can keep a half-built template around and call `build()` multiple times with one field changed).

The pattern is the standard way to construct immutable value objects in Java (where the language has no named-argument syntax) and is the dominant idiom for query criteria in every persistence framework — JPA's `CriteriaBuilder`, Hibernate's `JPAQuery`, jOOQ's `DSLContext`, Elasticsearch's `QueryBuilder`, MongoDB's `Bson` filters. All of them are builders: you chain `where`, `and`, `or`, `range`, `sort` calls and then call `fetch()` or `execute()` to materialise the result. The build step is the moment of truth — it validates that required fields are present, that conflicting options aren't both set, and that the resulting object is internally consistent.

```java
// Immutable order — only constructable through the builder.
public final class Order {
    public final UUID id;
    public final UUID customerId;
    public final List<LineItem> items;
    public final BigDecimal discount;
    public final ShippingAddress shipping;
    public final Instant placedAt;

    private Order(Builder b) {
        this.id         = requireNonNull(b.id,         "id");
        this.customerId = requireNonNull(b.customerId, "customerId");
        this.items      = List.copyOf(b.items);              // defensive copy
        this.discount   = b.discount == null ? ZERO : b.discount;
        this.shipping   = requireNonNull(b.shipping,   "shipping");
        this.placedAt   = b.placedAt == null ? now() : b.placedAt;
        if (discount.signum() < 0) throw new IllegalArgumentException("discount < 0");
        if (items.isEmpty())       throw new IllegalStateException("order has no items");
    }

    public static Builder builder() { return new Builder(); }
    public static final class Builder {
        private UUID id; private UUID customerId; private final List<LineItem> items = new ArrayList<>();
        private BigDecimal discount; private ShippingAddress shipping; private Instant placedAt;
        public Builder id(UUID v)                 { this.id = v; return this; }
        public Builder customerId(UUID v)         { this.customerId = v; return this; }
        public Builder addItem(LineItem v)        { this.items.add(v); return this; }
        public Builder discount(BigDecimal v)     { this.discount = v; return this; }
        public Builder shipping(ShippingAddress v){ this.shipping = v; return this; }
        public Builder placedAt(Instant v)        { this.placedAt = v; return this; }
        public Order build() { return new Order(this); }
    }
}

// Call site — reads as English, validates atomically at build().
Order o = Order.builder()
    .id(UUID.randomUUID())
    .customerId(custId)
    .addItem(new LineItem("SKU-1", 2, new BigDecimal("19.99")))
    .addItem(new LineItem("SKU-2", 1, new BigDecimal("5.00")))
    .discount(new BigDecimal("2.50"))
    .shipping(new ShippingAddress("1 Main St", "Springfield", "US"))
    .build();
```

Spring doesn't have a single "Builder" annotation — the pattern is convention-driven. Spring's own code uses it heavily (`org.springframework.boot.builder.SpringApplicationBuilder`, `RestTemplateBuilder`, `WebClient.Builder`) and Spring Boot auto-configuration exposes these builders as `@Bean` methods so application code can pick them up and customise them before calling `build()`. The Lombok `@Builder` annotation generates the boilerplate automatically; the IntelliJ "Replace Constructor with Builder" refactor does the same by hand. The class-level invariant to enforce is that the builder is the *only* public way to construct the object — the constructor is `private`, so callers can't bypass validation by calling `new Order(...)` with garbage arguments.

The query-criteria flavour of Builder shows up in every ORM. Here is the same "find orders placed this month, for a given customer, with at least one discounted item" expressed in three ecosystems; the shape is identical:

```java
// JPA CriteriaBuilder — programmatic, type-safe, no string concatenation.
CriteriaBuilder cb = em.getCriteriaBuilder();
CriteriaQuery<Order> q = cb.createQuery(Order.class);
Root<Order> o = q.from(Order.class);
q.where(
    cb.equal(o.get("customerId"), custId),
    cb.greaterThanOrEqualTo(o.get("placedAt"), firstOfMonth),
    cb.isNotEmpty(o.get("items")));
q.orderBy(cb.desc(o.get("placedAt")));
List<Order> results = em.createQuery(q).setMaxResults(50).getResultList();
```

```typescript
// Knex query builder (TypeScript / Node) — same shape, different syntax.
const results = await knex('orders')
    .where({ customer_id: custId })
    .where('placed_at', '>=', firstOfMonth)
    .whereRaw('jsonb_array_length(items) > 0')
    .orderBy('placed_at', 'desc')
    .limit(50);
```

```php
// Laravel Eloquent query builder — fluent, same composition.
$orders = Order::query()
    ->where('customer_id', $custId)
    ->where('placed_at', '>=', $firstOfMonth)
    ->whereRaw('jsonb_array_length(items) > 0')
    ->orderByDesc('placed_at')
    ->limit(50)
    ->get();
```

The Object Mother pattern is a specialised form of Builder for test data. The problem it solves is test setup bloat: every test needs an `Order`, but each test cares about one or two fields (the customer, the discount, the item count) and wants the rest to be reasonable defaults. An Object Mother is a class with methods like `OrderMother.withCustomer(custId)`, `OrderMother.withDiscount(amount)`, `OrderMother.paid()`, each of which returns a fully-built `Order` with sensible defaults filled in for the fields the test doesn't care about. Underneath, it uses a Builder — the difference is that the Object Mother *knows the domain semantics* ("what does a realistic order look like?") whereas the Builder only knows the structure. Combined with libraries like Instancio or EasyRandom (Java), faker.js (Node), Factory Boy (Python), or Laravel Factories (PHP), the Object Mother becomes a one-line test setup:

```java
// Object Mother — domain-aware defaults, test-friendly named factories.
public final class OrderMother {
    private static final Builder base() {
        return Order.builder()
            .id(UUID.randomUUID())
            .customerId(UUID.randomUUID())
            .addItem(new LineItem("SKU-DEFAULT", 1, new BigDecimal("10.00")))
            .shipping(new ShippingAddress("1 Test St", "Testville", "US"))
            .placedAt(Instant.now());
    }
    public static Order withCustomer(UUID custId)        { return base().customerId(custId).build(); }
    public static Order withDiscount(BigDecimal amount)  { return base().discount(amount).build(); }
    public static Order withItems(LineItem... items)     { Builder b = base(); for (var i : items) b.addItem(i); return b.build(); }
    public static Order paid()                            { return base().build(); /* + payment ref */ }
}

// Test call site — one line, reads as intent.
@Test void refuses_to_ship_to_blocked_customer() {
    Order o = OrderMother.withCustomer(BLOCKED_CUSTOMER_ID);
    assertThat(shipper.ship(o)).isInstanceOf(ShipmentRefused.class);
}
```

The production failure mode for the Builder pattern is the *mutable builder leak*: a builder that is shared across threads or stored in a field and reused, where one thread's `addItem` call corrupts another thread's `build()`. The defence is to make the builder itself effectively immutable after each `withX` call (return a new builder copy, not `this`), or to enforce the convention that builders are local variables only — never fields, never parameters, never cached. For the Object Mother, the failure mode is *test coupling through shared defaults*: fifty tests all use `OrderMother.paid()`, somebody changes the default customer id, and twenty unrelated tests break. The defence is to make the Object Mother's defaults *random per call* (use a UUID or faker for the fields the test doesn't assert on) so that tests cannot accidentally depend on a specific default value.

## Cross-Ecosystem Code

The five GoF creational patterns expressed in each ecosystem. Notice that the *pattern shape* is invariant — only the syntax differs.

```java
// Spring Boot — @Bean is Factory Method, @Scope("prototype") is Prototype,
// @Component + container singleton scope is the modern Singleton.
@Configuration
class PaymentConfig {
    @Bean @ConditionalOnProperty(name = "payments.provider", havingValue = "stripe")
    PaymentGateway stripeGateway(@Value("${stripe.api-key}") String key) {
        return new StripePaymentGateway(Stripe.builder().apiKey(key).build());
    }
    @Bean @ConditionalOnProperty(name = "payments.provider", havingValue = "paypal")
    PaymentGateway paypalGateway(@Value("${paypal.client-id}") String id,
                                  @Value("${paypal.secret}") String secret) {
        return new PayPalPaymentGateway(id, secret);
    }
    @Bean @Scope("prototype")
    OrderRowMapper orderRowMapper() { return new OrderRowMapper(); }
}
```

```typescript
// Express / TypeScript — hand-rolled factories, no container. NestJS has providers.
function makePaymentGateway(env: NodeJS.ProcessEnv): PaymentGateway {
  if (env.PAYMENTS_PROVIDER === 'stripe') return new StripePaymentGateway(env.STRIPE_API_KEY!);
  if (env.PAYMENTS_PROVIDER === 'paypal') return new PayPalPaymentGateway(env.PAYPAL_CLIENT_ID!, env.PAYPAL_SECRET!);
  throw new Error(`unknown payments provider: ${env.PAYMENTS_PROVIDER}`);
}
// Builder for query criteria via Knex; Prototype via fresh function call.
const buildOrderQuery = (customerId: string, since: Date) =>
  (knex: Knex) => knex('orders').where({ customer_id: customerId }).where('placed_at', '>=', since);
```

```python
# Django — factory functions, no DI container. Builder via Django ORM querysets.
def make_payment_gateway(settings) -> PaymentGateway:
    if settings.PAYMENTS_PROVIDER == 'stripe':
        return StripePaymentGateway(api_key=settings.STRIPE_API_KEY)
    if settings.PAYMENTS_PROVIDER == 'paypal':
        return PayPalPaymentGateway(client_id=settings.PAYPAL_CLIENT_ID, secret=settings.PAYPAL_SECRET)
    raise ValueError(f"unknown provider: {settings.PAYMENTS_PROVIDER}")

# Builder: queryset is a fluent, chainable, lazy criteria object.
Order.objects.filter(customer_id=cust_id).filter(placed_at__gte=first).order_by('-placed_at')[:50]
```

```php
// Laravel — the service container is itself an Abstract Factory. Prototype via ->bind().
$this->app->bind(PaymentGateway::class, function ($app) {
    $provider = config('payments.provider');
    return match ($provider) {
        'stripe' => new StripePaymentGateway(config('stripe.api_key')),
        'paypal' => new PayPalPaymentGateway(config('paypal.client_id'), config('paypal.secret')),
        default  => throw new RuntimeException("unknown provider: {$provider}"),
    };
});
// Prototype scope: bind() returns a new instance on every resolution (vs singleton()).
$this->app->bind(OrderRowMapper::class, fn () => new OrderRowMapper());
```

## How This Connects to the Frameworks

Spring's entire `@Configuration` / `@Bean` / `@Component` / `@Scope` machinery is a creational-pattern engine — the framework's job is to decide which concrete class to instantiate, when, with what dependencies, and how many to keep around. The five GoF patterns map directly: `@Bean` = Factory Method, `@Configuration` with multiple related beans = Abstract Factory, `@Scope("singleton")` (default) = Singleton done right, `@Scope("prototype")` = Prototype, and convention-based builders (Spring's own `RestTemplateBuilder`, `WebClient.Builder`) = Builder. In Laravel the service container plays the same role with `bind()` (prototype), `singleton()` (singleton), and closure-based resolvers (factory method). In NestJS the `providers` array and `useFactory` / `useClass` / `useValue` keys express the same decisions. In Django and Express there is no container by default, so the patterns are hand-rolled as module-level factory functions — which is fine for small applications and becomes painful once you need cross-cutting concerns (config refresh, conditional wiring, lifecycle hooks).

## How This Connects to the Runtimes

The runtime cost of creational patterns is usually negligible (one extra method call per object creation, lost in JIT / interpreter noise), but two cases matter. First, prototype-scoped beans in a hot path: every injection creates a new instance, and if the constructor does I/O (loads a config file, opens a socket), the prototype scope turns a one-time cost into a per-call cost. Second, builder-heavy query construction in a tight loop: building a JPA `CriteriaQuery` for each row of a million-row batch is significantly slower than reusing a parameterised query, because the builder allocates a tree of `Predicate` objects that the garbage collector then has to reclaim. The fix is to build the query once outside the loop and bind parameters per iteration — which is itself a creational decision (construct-once, mutate-state vs construct-per-call).

## Cross-Runtime Comparison

| Pattern | Spring (Java) | Express / NestJS (TS) | Django (Python) | Laravel (PHP) |
|---|---|---|---|---|
| Factory Method | `@Bean` method | `useFactory` provider | module-level function | `bind()` closure |
| Abstract Factory | `@Configuration` + `@Profile` | provider groups by env | settings-driven factory module | service container tags |
| Singleton | default `@Component` scope | `useClass` provider (default singleton) | module-level instance | `singleton()` binding |
| Prototype | `@Scope("prototype")` | `useFactory` per-resolve | factory function called per-use | `bind()` (vs `singleton()`) |
| Builder | Lombok `@Builder`, framework builders | fluent class methods | queryset chaining, dataclass builder | Eloquent query builder, factory classes |
| Object Mother | Instancio / EasyRandom + builder | faker.js + builder | Factory Boy | Laravel Factories |

## Hands-On Exercise

Spin up a Spring Boot application with two cloud profiles and watch the factory pick the right adapter:

```bash
# Create a minimal project
curl https://start.spring.io/starter.tgz \
  -d dependencies=web \
  -d type=gradle-project \
  -d language=java \
  -d bootVersion=3.3.0 \
  | tar -xzvf -

# Add the AwsInfrastructureFactory and GcpInfrastructureFactory classes above,
# plus a /health endpoint that prints which BlobStore implementation is wired.

# Run with AWS profile — observe S3BlobStore
./gradlew bootRun --args="--spring.profiles.active=aws"
curl -s localhost:8080/health   # → {"blobStore":"S3BlobStore"}

# Run with GCP profile — observe GcsBlobStore
./gradlew bootRun --args="--spring.profiles.active=gcp"
curl -s localhost:8080/health   # → {"blobStore":"GcsBlobStore"}

# Prototype scope: inject OrderRowMapper twice and prove they're different instances
curl -s localhost:8080/health   # → {"mapperInstance1":"#123","mapperInstance2":"#456"}
```

Try the production failure: rename a `@Bean` method so its Spring name collides with another bean, observe the `NoUniqueBeanDefinitionException`, and trace through the `BeanDefinitionRegistry` to see why the container refuses to guess.
