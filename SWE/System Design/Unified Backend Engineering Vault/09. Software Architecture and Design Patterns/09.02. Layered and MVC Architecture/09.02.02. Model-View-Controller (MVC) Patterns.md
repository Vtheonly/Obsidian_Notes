# 09.02.02. Model-View-Controller (MVC) Patterns

## What This Is

Model-View-Controller (MVC) is the 1979 Trygve Reenskaug pattern, originally designed at Xerox PARC for the Smalltalk-80 graphical user interface, that has become the default structural pattern of every mainstream web framework — Rails, Django, Flask, Laravel, Spring MVC, ASP.NET MVC, Phoenix, Play, Echo. The pattern partitions an application into three responsibilities: the **Model** holds state and the business rules that mutate that state; the **View** renders model state into an output form (HTML, JSON, CSV); the **Controller** translates user input (an HTTP request in the web variant, a keyboard event in the original Smalltalk variant) into model mutations and selects the next view to render. The pattern's persistence is explained by its clean separation of concerns: the same Model can be rendered by multiple Views (HTML view, JSON view, CSV export view), the same View can be driven by multiple Controllers (admin controller, customer controller, API controller), and the Model can be unit-tested without any View or Controller present.

The layered mental model connection: MVC is a specialised instance of the N-tier layered architecture from [[09.02.01. Classic N-Tier Layered Architecture]], with the Presentation layer split into View and Controller, and the lower three layers (Application, Domain, Data Access) fused into the Model. In a small CRUD application the Model is one Active Record class (Rails `ApplicationRecord`, Django `models.Model`, Laravel `Eloquent\Model`) that handles persistence, business rules, and query scopes. In a domain-rich application the Model is an aggregate of entities, value objects, and domain services, with the Active Record class demoted to a Data Access implementation detail — at which point the architecture is no longer MVC but hexagonal/Clean from [[09.03.01. The Hexagonal (Ports and Adapters) Architecture]]. The transition from "MVC with fat models" to "hexagonal with a service layer" is the topic of the third H3 below.

## The Details

### MVC Mechanics: Model (Data and Business Rules), View (Output formatting), Controller (Input orche...

The original Smalltalk-80 MVC (Reenskaug 1979, "Models-Views-Controllers") used the Observer pattern as the binding glue: a View registered itself as an observer of a Model via `Model.addObserver(view)`, the Model called `notifyObservers()` whenever its state changed, the View's `update()` method re-read the Model and repainted the screen, and the Controller translated keyboard and mouse events into method calls on the Model. The pattern was stateful — the Model lived in memory for the duration of the user's session, multiple Views could observe the same Model (a list view and a graph view of the same data), and a single user action could trigger cascading Model changes that automatically refreshed every dependent View. This is the MVC that the original Apple Lisa and Macintosh toolboxes implemented, that NeXTSTEP's Application Kit implemented, and that the Java Swing `Observer`/`Observable` mechanism implemented.

The web variant of MVC — Rails, Django, Laravel, Spring MVC, ASP.NET MVC, Phoenix — is structurally different in one crucial respect: **the Model does not live across requests, so the Observer pattern is gone.** Each HTTP request is a fresh world: the Controller instantiates or loads the Model, mutates it (or persists it), passes it to the View, the View renders it into HTML/JSON, the response is sent, and the Model is discarded. There is no long-lived subscription from View to Model because there is no long-lived View. What survived the translation from Smalltalk-80 to the web is the *separation of concerns*: input handling (Controller), state and business rules (Model), output rendering (View). What was lost is the *live update mechanism*, which had to be reinvented in the 2010s as WebSocket push (see [[03.04.03. The WebSocket Protocol RFC 6455]]) and Server-Sent Events (see [[03.04.02. Server-Sent Events (SSE)]]) for the cases where live updates matter.

```text
Smalltalk-80 MVC (stateful, Observer-bound):

   user input (keyboard/mouse)
            │
            ▼
   ┌────────────────┐    translate event to command    ┌──────────────┐
   │   Controller   │ ────────────────────────────────► │    Model     │
   └────────────────┘                                   │ (state +     │
            ▲                                           │  behaviour)  │
            │ view selection                                            │
            │                                                           │ notifyObservers()
            │                                                           ▼
   ┌────────┴────────┐    repaint on update()    ┌──────────────────────┐
   │      View       │ ◄──────────────────────── │  View registered as  │
   │ (screen region) │                           │  Observer of Model   │
   └─────────────────┘                           └──────────────────────┘

   Long-lived: Model lives across many user inputs. Multiple Views can
   observe one Model. One Model mutation cascades to N View repaints.


Web MVC (stateless, request-scoped):

   HTTP request (GET /orders/42)
            │
            ▼
   ┌────────────────────┐  load from DB   ┌──────────────────────┐
   │  Controller        │ ──────────────► │  Model               │
   │  @GetMapping("/{id}")                │  (loaded fresh from  │
   │                    │ ◄────────────── │   database, mutated,  │
   │                    │  mutated        │   saved)              │
   │                    │                 └──────────────────────┘
   │                    │  pass Model to View
   │                    ▼
   │            ┌─────────────┐
   │            │    View     │  render to HTML/JSON
   │            │ (template)  │ ──────► HTTP response
   │            └─────────────┘
   └────────────────────┘

   Stateless: Model is loaded, mutated, rendered, discarded per request.
   No Observer pattern — View cannot subscribe to Model changes.
   Live updates require WebSocket/SSE (see [[03.04.03]]).
```

The Spring Boot MVC implementation uses `@Controller` (not `@RestController`) for server-rendered HTML, with a Thymeleaf template as the View. The Controller method returns a `String` view name; Spring's `ViewResolver` resolves the name to a Thymeleaf template file under `src/main/resources/templates/`; the template engine renders the Model into HTML. The Model is a `Map<String, Object>` passed via `Model model` parameter:

```java
// Spring Boot MVC — server-rendered HTML with Thymeleaf
@Controller
@RequestMapping("/orders")
class OrdersController {

    private final OrderService service;

    OrdersController(OrderService service) { this.service = service; }

    @GetMapping("/{id}")
    String showOrder(@PathVariable Long id, Model model) {
        Order order = service.findById(id)
                             .orElseThrow(() -> new OrderNotFoundException(id));
        model.addAttribute("order", order);          // Model
        return "orders/show";                         // View name → templates/orders/show.html
    }

    @PostMapping("/{id}/cancel")
    String cancel(@PathVariable Long id, RedirectAttributes flash) {
        service.cancel(id);                           // Model mutation
        flash.addFlashAttribute("notice", "Order cancelled");
        return "redirect:/orders/" + id;              // PRG pattern (Post-Redirect-Get)
    }
}
```

```html
<!-- src/main/resources/templates/orders/show.html — Thymeleaf View -->
<!DOCTYPE html>
<html xmlns:th="http://www.thymeleaf.org">
<head><title>Order #<span th:text="${order.id}">42</span></title></head>
<body>
  <h1>Order #<span th:text="${order.id}">42</span></h1>
  <p>Status: <span th:text="${order.status}">PENDING</span></p>
  <p>Total: $<span th:text="${order.total}">0.00</span></p>

  <form th:action="@{/orders/{id}/cancel(id=${order.id})}" method="post">
    <button type="submit">Cancel order</button>
  </form>
</body>
</html>
```

The Django equivalent is the MVT variant — see the second H3 below for why Django uses different terminology. The Rails equivalent is `class OrdersController < ApplicationController; def show; @order = Order.find(params[:id]); end; end` plus `app/views/orders/show.html.erb`. The Laravel equivalent is `Route::get('/orders/{id}', [OrderController::class, 'show'])` plus `class OrderController { public function show($id) { return view('orders.show', ['order' => Order::findOrFail($id)]); } }` plus `resources/views/orders/show.blade.php`. The shape is identical across all four frameworks: Controller loads Model, passes to View, View renders. The Spring Boot choice of `@Controller` + Thymeleaf vs `@RestController` + JSON is what distinguishes server-rendered MVC from API-only MVC; both are MVC, the only difference is whether the View is a template or a JSON serializer.

The production failure mode of naive web MVC is the **god controller**: a `UserController` with 47 handler methods, each calling a different model method, growing into a 2000-line file that every frontend change touches. The fix is to keep controllers thin — one controller per resource, one method per action, delegate everything non-trivial to a service object (Rails `app/services/`, Spring `@Service`, Django `services.py`). The second failure mode is the **fat View**: logic creeping into templates (`{% if order.status == 'PAID' and order.total > 1000 %}`) until the template is half business rule and half HTML. The fix is the rule "templates render, they do not decide" — push every conditional into the Model as a method (`order.isHighValuePaid()` instead of the inline check) so the business rule is testable and reusable.

### Django's Model-View-Template (MVT) divergence

Django calls its MVC variant "Model-View-Template" (MVT) and uses the words in a way that confuses developers coming from Rails, Laravel, or Spring MVC. In Django: the **Model** is `class Order(models.Model)` — the Active Record class that owns the table mapping and the query scopes, identical to a Rails model. The **View** is `def order_detail(request, order_id):` — a function (or class-based view) that handles an HTTP request, loads a Model, and returns an HTTP response. This is what every other framework calls a Controller. The **Template** is `templates/orders/detail.html` — the HTML template that renders the Model into a response. This is what every other framework calls a View. Django's documentation explicitly acknowledges this: "Django appears to be a MVC framework, but you can see that the Controller is called the View, and the View is called the Template. ... Django doesn't really fit the MVC pattern perfectly." (Django FAQ). The justification is partly historical — Adrian Holovaty came from a journalism background where "view" meant "the way you view the data" (i.e., the rendered output), partly ideological — Django's designers felt that the framework's role was to provide Views (in their sense) of data, and the Template was a sub-component of the View, not a peer to it.

```python
# Django MVT — same shape as Rails/Laravel/Spring MVC, renamed

# myapp/models.py — the Django "Model" (Active Record)
from django.db import models

class Order(models.Model):
    user = models.ForeignKey(User, on_delete=models.CASCADE)
    status = models.CharField(max_length=20, default='PENDING')
    total = models.DecimalField(max_digits=10, decimal_places=2)
    created_at = models.DateTimeField(auto_now_add=True)

    class Meta:
        db_table = 'orders'

    def cancel(self):                          # business rule on the Model
        if self.status not in ('PENDING', 'PAID'):
            raise ValueError(f"Cannot cancel order in state {self.status}")
        self.status = 'CANCELLED'
        self.save()

# myapp/views.py — the Django "View" (what others call "Controller")
from django.shortcuts import get_object_or_404, render, redirect
from .models import Order

def order_detail(request, order_id):
    order = get_object_or_404(Order, pk=order_id)        # load Model
    return render(request, 'orders/detail.html',         # pass to Template
                  {'order': order})

def cancel_order(request, order_id):
    if request.method != 'POST':
        return HttpResponseNotAllowed(['POST'])
    order = get_object_or_404(Order, pk=order_id)
    order.cancel()                                        # mutate Model
    return redirect('order_detail', order_id=order.id)    # PRG

# myapp/urls.py — the routing layer (equivalent to Rails routes.rb)
from django.urls import path
from . import views

urlpatterns = [
    path('orders/<int:order_id>', views.order_detail, name='order_detail'),
    path('orders/<int:order_id>/cancel', views.cancel_order, name='cancel_order'),
]
```

```html
<!-- myapp/templates/orders/detail.html — the Django "Template" (the View) -->
<!DOCTYPE html>
<html>
<head><title>Order #{{ order.id }}</title></head>
<body>
  <h1>Order #{{ order.id }}</h1>
  <p>Status: {{ order.status }}</p>
  <p>Total: ${{ order.total }}</p>
  <form method="post" action="{% url 'cancel_order' order.id %}">
    {% csrf_token %}
    <button type="submit">Cancel order</button>
  </form>
</body>
</html>
```

The Django MVT is structurally identical to Rails MVC, Laravel MVC, and Spring MVC — same three responsibilities, same data flow (route → controller → model → view → response). The only difference is the labels. The practical implication is that when a Django developer and a Rails developer discuss "the View", they are talking about different things — and code review comments like "this logic belongs in the View" mean different things to each. The fix is to use the underlying responsibility words ("the request handler", "the template", "the model") when cross-team communication is happening, and to accept that the labels are baked into each framework's documentation and cannot be unified.

The Django MVT divergence matters in practice for two reasons beyond terminology. First, Django's class-based views (`class OrderDetailView(DetailView)`) live in `views.py` but provide reusable controller-style behaviour (automatic model loading, automatic template rendering, automatic context building) that other frameworks put in separate controller classes — Django fuses the controller into the view module, which is fine for small apps and confusing for large ones. Second, Django's templates are intentionally restricted: the template language forbids arbitrary Python expressions, multi-line function calls, and complex conditionals. The framework's philosophy is "templates should be dumb — if you need logic, put it in the view (the controller)". This is the opposite of PHP's "logic in the template" tradition and is the same stance as Rails' ERB (which allows arbitrary Ruby but discourages it) and Laravel's Blade (which allows arbitrary PHP but discourages it). The restriction forces business logic into either the controller (Django view) or the model, which is the topic of the third H3 below.

The production failure mode of Django's terminology is the **cross-framework hire**: a senior Rails developer joins a Django team, the team lead says "we need to move this logic out of the View", the Rails developer hears "move it out of the controller" (correct in Rails) but the team lead meant "move it out of the template" (correct in Django), and the refactor goes in the wrong direction. The second failure mode is the **class-based view inheritance hell**: a Django team builds a 7-deep class-based view inheritance hierarchy (`OrderDetailView(LoginRequiredMixin, StaffuserRequiredMixin, BaseOrderView, DetailView)`) and the next developer to debug a template rendering issue spends two days tracing which `get_context_data` override in which superclass is firing. The fix is to prefer function-based views for anything non-trivial, and to keep class-based view inheritance to ≤ 2 levels.

### The "Fat Model, Skinny Controller" paradigm and its eventual breakdown in complex enterprise domains

The "Fat Model, Skinny Controller" mantra originated in the Rails community around 2007 (DHH's "skinny controller, fat model" blog post) and is the dominant MVC convention in Rails, Laravel, and Django. The rule is: keep controllers thin (load a model, call one method on it, render), push all logic into models (business rules, validation, derived attributes, state transitions, callbacks). The justification has three parts. First, controllers are hard to unit-test (they require an HTTP context), while models are easy (they are plain objects). Second, models can be reused across controllers — the `User.ban()` method is called by both the admin controller and the API controller. Third, business logic that lives on the model is co-located with the data it operates on, which is the same argument as the "rich domain model" point from [[09.02.01. Classic N-Tier Layered Architecture]] H3 #3.

The convention works well for CRUD-shaped applications with simple per-entity logic. It breaks down in three predictable ways as the application grows. First, **models become god objects**: the Rails `User` model accumulates authentication (Devise), payment (Stripe), notification (ActionMailer), audit (PaperTrail), and feature-flagging logic until it is a 3000-line file that every team touches and every deploy risks breaking. Second, **business logic that spans multiple models has no natural home**: `place_order(order, payment_method, shipping_address)` is not a method on `Order` (it needs `Payment` and `Shipment`), not a method on `Payment` (it needs `Order` and `Shipment`), not a method on `Shipment` (it needs `Order` and `Payment`). The Rails community's first answer is "put it on the most central model" (Order), which makes Order a god object too. The second answer is "put it in a module and include it in Order" (`app/models/concerns/placeable.rb`), which just moves the god object into a module that nobody can find. The third answer is the **Service Object pattern**: a plain Ruby class (`class OrderSubmitService; def initialize(order, payment, shipping); ...; def call; ...; end; end`) that lives in `app/services/` and orchestrates the multi-model operation. This is the answer that scales.

```text
The breakdown trajectory — from fat model to service layer:

  Stage 1: CRUD app, "fat model" works fine
    class Order < ApplicationRecord
      def total; items.sum(:price); end
      def cancel; update!(status: :cancelled); end
    end

  Stage 2: Business logic spans multiple models — god object emerges
    class Order < ApplicationRecord
      def submit!
        # oh no, this needs Payment + Inventory + Shipping + Notification
        transaction do
          update!(status: :submitted)
          inventory.reserve!(items)             # ← order reaches into inventory
          payment.charge!(total)                # ← order reaches into payment
          shipping.schedule!(self)              # ← order reaches into shipping
          notify_customer                      # ← order reaches into mailer
        end
      end
    end
    # Order is now a god object: every team's code is in app/models/order.rb

  Stage 3: Extract service objects (Rails) / @Service (Spring) / services.py (Django)
    class OrderSubmitService                    # app/services/order_submit_service.rb
      def initialize(order, payment_method, shipping_address)
        @order, @payment, @shipping = order, payment_method, shipping_address
      end

      def call
        ActiveRecord::Base.transaction do       # tx boundary lives in service
          @order.submit!
          Inventory.reserve!(@order.items)
          Payment.charge!(@order, @payment)
          Shipping.schedule!(@order, @shipping)
          OrderMailer.with(order: @order).submitted_email.deliver_later
        end
      end
    end

    # Controller is now skinny again:
    class OrdersController < ApplicationController
      def create
        order = Order.new(order_params)
        OrderSubmitService.new(order, params[:payment_method_id],
                                    params[:shipping_address_id]).call
        redirect_to order
      end
    end
```

The Spring Boot equivalent of the service object is the `@Service`-annotated class — see the `OrderApplicationService` in [[09.02.01. Classic N-Tier Layered Architecture]] H3 #1. The Django equivalent is the `services.py` module pattern: a plain Python module with functions (`def submit_order(order, payment, shipping): with transaction.atomic(): ...`) that the view calls. The Laravel equivalent is the `app/Actions/` directory (`class SubmitOrderAction { public function __invoke(Order $order, ...): void { ... } }`), invoked as `SubmitOrderAction::run($order, ...)`. In every framework the trajectory is the same: controllers stay skinny, models stay thin (entity + per-entity rules only), and a service/action/use-case layer absorbs the multi-model orchestration. This is the transition from "MVC with fat models" to "layered architecture with a service layer", which is the topic of [[09.02.01. Classic N-Tier Layered Architecture]] and the entry point to hexagonal architecture from [[09.03.01. The Hexagonal (Ports and Adapters) Architecture]] and DDD tactical patterns from [[09.04.02. Tactical Domain Building Blocks]].

The MVP and MVVM variants are the same observation applied to the View side of MVC, both originating in the rich-client UI world. **Model-View-Presenter (MVP)**, introduced by Mike Potel at Taligent in 1996, splits the Controller into a Presenter that owns View logic and a thin View that just forwards user events to the Presenter. The Presenter updates the View through a fixed interface (`view.showOrder(order)`), enabling the Presenter to be unit-tested with a mock View. MVP is the pattern behind Android's traditional View layer, GWT's MVP framework, and Windows Forms. **Model-View-ViewModel (MVVM)**, introduced by John Gossman at Microsoft in 2005 (for WPF), goes further: the ViewModel is a Plain Object that exposes properties and commands, and the View is bound to the ViewModel via a declarative binding mechanism (`{Binding Order.Total}` in WPF, `[(ngModel)]="order.total"` in Angular, `v-model="order.total"` in Vue). The binding framework handles the synchronisation between ViewModel and View, eliminating the manual update code that MVP requires. MVVM is the pattern behind every modern JavaScript frontend framework (React with hooks is MVVM-with-a-different-name; Vue is MVVM; Angular is MVVM). Neither MVP nor MVVM applies directly to server-side web MVC — the server-side View is stateless and request-scoped, so there is no long-lived binding to maintain — but both appear when the backend serves a rich client: the backend's JSON API is the Model, the client-side ViewModel is the presentation state, and the View is the rendered DOM.

The production failure mode of "fat model, skinny controller" is the **3000-line model file that nobody can refactor**: every team is afraid to touch `User.rb` because every other team has logic in it, the test suite takes 20 minutes to run because every model test boots Rails, and a typo in one method breaks unrelated features in production. The second failure mode is the **callback hell**: `before_save :send_welcome_email`, `after_create :provision_billing_account`, `after_commit :sync_to_data_warehouse` — the model's lifecycle becomes a sequence of side effects that fire on every save, and a debug session requires tracing which callback fired in what order and whether the third one was supposed to halt the chain. The fix is to extract callbacks into explicit service objects that the controller calls (`OrderSubmitService.new(...).call` instead of `order.save` with implicit side effects), so the side effects are visible at the call site. The third failure mode is the **untestable model**: a model method that calls `Rails.cache.fetch`, `HTTParty.post`, `ActionMailer.deliver_later`, and `Order.transaction` cannot be unit-tested without booting the full Rails environment, the test takes 800 ms instead of 5 ms, and the team stops running tests locally. The fix is to inject collaborators (a cache interface, an HTTP client, a mailer interface) via constructor, so the test can pass mocks — which is the same dependency-inversion mechanism from [[09.02.01. Classic N-Tier Layered Architecture]] H3 #2, applied at the model layer instead of the controller layer. The trajectory always ends at the same place: the service layer becomes a first-class concern, the models become domain entities with behaviour but no infrastructure dependencies, and the architecture is recognisably layered — at which point the team is ready to read [[09.03.01. The Hexagonal (Ports and Adapters) Architecture]] and decide whether to formalise the boundaries with ports and adapters.

## Key Takeaways

1. **Smalltalk-80 MVC was stateful and Observer-bound; web MVC is stateless and request-scoped.** What survived the translation is the separation of input handling (Controller), state and business rules (Model), and output rendering (View). What was lost is the live update mechanism, which had to be reinvented as WebSocket/SSE.
2. **Django's MVT is the same pattern with renamed labels: Django "View" = everyone else's "Controller", Django "Template" = everyone else's "View".** The shape is identical; only the terminology differs. Use responsibility-words ("request handler", "template", "model") when communicating across frameworks.
3. **"Fat Model, Skinny Controller" works for CRUD and breaks for multi-model orchestration.** When a single business operation spans three models, it does not belong on any of them — it belongs in a service object. The trajectory is always toward a service layer, which is the bridge from MVC to layered/hexagonal architecture.
4. **MVP and MVVM are View-side refinements of MVC for rich-client UIs.** They do not apply directly to server-side web MVC but appear when the backend serves a rich client: the JSON API is the Model, the client-side ViewModel is the presentation state, the View is the rendered DOM.
