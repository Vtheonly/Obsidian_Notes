# 09.02.01. Classic N-Tier Layered Architecture

## What This Is

The classic N-tier (or layered) architecture is the oldest structural pattern in backend engineering: split the codebase into horizontal layers, each responsible for one concern, with dependencies pointing strictly in one direction. The four canonical layers are Presentation (controllers, REST endpoints, view rendering), Application (use case orchestration, transaction boundaries), Domain (entities, value objects, business invariants), and Data Access (repositories, ORM mappings, SQL). The pattern is what every mainstream framework defaults to — Spring Boot's `@Controller`/`@Service`/`@Repository` stereotypes map directly to it, Django's `views.py`/`services.py`/`models.py`/`managers.py` is the same shape, Rails' `controllers`/`models`/`active_record` is the same shape with the Domain and Data Access layers fused. The pattern's value is local reasoning: a bug in the request body parsing is in the Presentation layer, a bug in the business rule is in the Domain layer, a bug in the SQL is in the Data Access layer — you never have to grep across all three.

The layered mental model connection: this note sits on top of section 05's framework abstractions (which provide the routing, middleware, DI, and validation mechanisms that each layer uses) and section 06's persistence layer (which the Data Access layer wraps). It is the prerequisite for [[09.03.01. The Hexagonal (Ports and Adapters) Architecture]] and [[09.03.02. Clean Architecture and Onion Architecture Mapping]], both of which are restatements of the same dependency rule at a stricter level. The forward dependency rule is the load-bearing invariant: Presentation depends on Application, Application depends on Domain and Data Access, Domain depends on nothing. Break the rule and the layers collapse into a Big Ball of Mud where every class can reach every other class, the testability benefits evaporate, and the next refactor is a rewrite.

## The Details

### Layer definitions: Presentation Layer → Business Logic / Service Layer → Data Access / Persistenc...

The four canonical layers, with precise responsibility boundaries, are as follows. The **Presentation layer** (also called the transport layer, the API layer, or the controllers) is the only layer that knows about the wire protocol — HTTP verbs, status codes, JSON serialization, request body parsing, content negotiation. Its job is to translate an incoming HTTP request into a call on the Application layer and to translate the Application layer's response back into an HTTP response. It owns request DTOs (validated with `@Valid` from [[05.04.02. Deep Anchor Implementation Spring Boot Validation and Jackson]]) and response DTOs (never JPA entities — see the third H3 below). It owns exception-to-status-code mapping (`@ExceptionHandler(UserNotFoundException.class)` returns 404). It owns nothing else: no business rules, no SQL, no domain logic. The **Application layer** (also called the Service layer) is the orchestration layer: it implements use cases (`SubmitOrder`, `ChargePayment`, `ResetPassword`), defines transaction boundaries (`@Transactional` lives here and only here), and coordinates calls to multiple domain entities and repositories in service of a single use case. It does not contain business rules — those live in the Domain layer. It does not know about HTTP — that is the Presentation layer's concern. The **Domain layer** is the heart of the system: entities (objects with identity, e.g. `Order`), value objects (immutable objects defined by their attributes, e.g. `Money`, `EmailAddress`), aggregates (consistency boundaries, e.g. `Order` containing `OrderLine` items), and the business invariants that govern them (`Order.cancel()` is only legal from `PAID` state, throws `IllegalStateTransitionException` otherwise). The Domain layer has zero framework dependencies — no `@Entity`, no `@Autowired`, no `HttpServletRequest`. It is pure Java/Kotlin/Python/PHP. The **Data Access layer** (also called the Persistence layer) implements the repository interfaces declared by the Domain or Application layer, wrapping JPA/Hibernate, jOOQ, or raw JDBC. It owns entity-to-table mappings (`@Table`, `@Column`), SQL queries, and database connection management. It does not contain business rules.

The Spring Boot stereotype annotations map directly to these layers: `@Controller` and `@RestController` mark Presentation-layer classes; `@Service` marks Application-layer classes; `@Repository` marks Data Access classes. Spring's component scanner picks them up and registers them as beans in the application context (see [[05.03.02. Deep Anchor Implementation Spring Boot IoC Container]]). The Domain layer is unannotated — entities are plain classes that the JPA provider manages via reflection. The three-tier variant fuses Domain and Application (the `Service` layer holds both orchestration and business rules), which is what most small-to-medium Spring Boot applications do in practice. The four-tier variant splits them, which is what large domain-rich applications do when the business rules become too numerous to fit cleanly inside service classes.

```java
// ===== Presentation Layer =====
// src/main/java/com/example/orders/api/OrdersController.java
@RestController
@RequestMapping("/api/v1/orders")
@RequiredArgsConstructor
class OrdersController {

    private final OrderApplicationService service;   // depends on Application layer

    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    OrderResponse create(@Valid @RequestBody CreateOrderRequest req) {
        Order order = service.submit(req.toCommand());    // returns Domain entity
        return OrderResponse.from(order);                 // translate to response DTO
    }

    @GetMapping("/{id}")
    OrderResponse findById(@PathVariable Long id) {
        return service.findById(id)
                      .map(OrderResponse::from)
                      .orElseThrow(() -> new OrderNotFoundException(id));
    }

    @ExceptionHandler(OrderNotFoundException.class)
    @ResponseStatus(HttpStatus.NOT_FOUND)
    ProblemDetail notFound(OrderNotFoundException ex) {
        return ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
    }
}

// ===== Application Layer =====
// src/main/java/com/example/orders/application/OrderApplicationService.java
@Service
@Transactional
@RequiredArgsConstructor
class OrderApplicationService {

    private final OrderRepository orders;          // interface from Domain layer
    private final PaymentGateway payments;          // interface from Domain layer
    private final EventPublisher events;            // interface from Domain layer

    public Order submit(SubmitOrderCommand cmd) {
        Order order = Order.create(cmd.userId(), cmd.items());   // Domain logic
        orders.save(order);                                       // Data Access call
        payments.charge(order);                                   // outbound port
        events.publish(new OrderSubmitted(order.getId()));        // outbound port
        return order;
    }

    @Transactional(readOnly = true)
    public Optional<Order> findById(Long id) {
        return orders.findById(id);
    }
}

// ===== Domain Layer =====
// src/main/java/com/example/orders/domain/Order.java
// NO Spring annotations, NO JPA annotations — pure Java
public class Order {

    private OrderId id;
    private UserId userId;
    private List<OrderLine> lines;       // OrderLine is a Value Object
    private OrderStatus status;          // OrderStatus is an enum
    private Instant createdAt;

    // Factory method — enforces creation invariants
    public static Order create(UserId userId, List<OrderLine> lines) {
        if (lines.isEmpty()) throw new IllegalArgumentException("Order has no lines");
        Order o = new Order();
        o.id = OrderId.next();
        o.userId = userId;
        o.lines = new ArrayList<>(lines);     // defensive copy
        o.status = OrderStatus.PENDING;
        o.createdAt = Instant.now();
        return o;
    }

    // Business rule — only PAID orders can be cancelled
    public void cancel() {
        if (status != OrderStatus.PAID && status != OrderStatus.PENDING) {
            throw new IllegalStateTransitionException(status, OrderStatus.CANCELLED);
        }
        this.status = OrderStatus.CANCELLED;
    }

    // Getters — no setters. Mutations go through behaviour methods.
    public OrderId getId() { return id; }
    public OrderStatus getStatus() { return status; }
    // ...
}

// ===== Data Access Layer =====
// src/main/java/com/example/orders/infrastructure/OrderRepositoryImpl.java
@Repository
@RequiredArgsConstructor
class OrderRepositoryImpl implements OrderRepository {   // implements Domain interface

    private final OrderJpaRepository jpa;                // Spring Data JPA

    @Override
    public void save(Order order) {
        OrderJpaEntity row = OrderJpaEntity.fromDomain(order);
        jpa.save(row);
    }

    @Override
    public Optional<Order> findById(OrderId id) {
        return jpa.findById(id.value()).map(OrderJpaEntity::toDomain);
    }
}
```

The key distinction between the Domain entity `Order` (no annotations, pure Java) and the JPA entity `OrderJpaEntity` (annotated with `@Entity`/`@Table`/`@Column`) is what makes the layered architecture testable and refactor-safe. The Domain entity enforces business invariants; the JPA entity maps to a table. They are different classes, translated by the Data Access layer. In small applications the two are often the same class with `@Entity` annotations on a domain object — this is the "active record" pattern from [[06.07.02. The Active Record Pattern]] and it is acceptable for CRUD-shaped domains. In domain-rich applications the two are separate classes, with the Data Access layer translating between them — this is the "data mapper" pattern from [[06.07.03. The Data Mapper Pattern]] and it is necessary when the domain model diverges from the table schema (e.g. when an `Order` aggregate spans four tables but is loaded as a single object).

The production failure mode of fuzzy layer boundaries is the **leaky abstraction**: a controller that calls a repository directly (skipping the service layer), a service that returns a JPA entity which Jackson then serializes to JSON with every lazy-loaded relationship triggered (the N+1 problem from [[06.07.05. The N+1 Query Problem and Loading Strategies]]), or a domain entity that takes an `EntityManager` parameter (so the domain layer is now coupled to JPA and cannot be unit-tested without a database). The fix is the layer rule enforced at compile time: ArchUnit rules that fail the build if `OrdersController` imports `OrderRepository` directly, or if `Order` (the domain entity) imports anything from `javax.persistence` or `org.springframework`.

### The Forward Dependency Rule and unidirectional control flow

The forward dependency rule is the load-bearing invariant of layered architecture: **dependencies point in exactly one direction, from higher layers to lower layers, never the reverse.** Presentation depends on Application, Application depends on Domain and Data Access, Data Access depends on its own infrastructure (JDBC driver, JPA provider), Domain depends on nothing in the application. The rule is what makes the layers substitutable: you can swap PostgreSQL for MongoDB by replacing only the Data Access layer; you can swap REST for gRPC by replacing only the Presentation layer; you can unit-test the Domain layer in isolation because it has no dependencies on the layers above or below it. Break the rule and the substitutability evaporates: a domain entity that imports `HttpServletRequest` cannot be reused outside a servlet container, a repository that imports a controller's DTO cannot be reused outside that controller's request shape.

The rule is enforced by the Dependency Inversion Principle (the "D" in SOLID, Robert C. Martin 1996): *high-level policy should not depend on low-level details; both should depend on abstractions.* In Java terms, the Application layer declares an interface (`OrderRepository`) and depends on the interface; the Data Access layer provides the implementation (`OrderRepositoryImpl`); the DI container wires the implementation to the interface at runtime. The compile-time dependency of the Application layer points only at the interface — it never imports `OrderRepositoryImpl` or `javax.persistence`. The runtime dependency points the other way (the implementation is what gets called), but the compile-time dependency is what governs refactor safety. This is the same mechanism that makes hexagonal architecture from [[09.03.01. The Hexagonal (Ports and Adapters) Architecture]] physically possible: ports are interfaces declared by the inside, adapters are implementations provided by the outside, the inside never imports the outside.

```text
Forward dependency rule — dependencies point DOWNWARD only:

  ┌──────────────────────────────────────────────────────────────┐
  │  Presentation Layer                                          │
  │  OrdersController depends on → OrderApplicationService       │
  │                  depends on → CreateOrderRequest (DTO)       │
  │                  depends on → OrderResponse (DTO)            │
  └──────────────────────────┬───────────────────────────────────┘
                             │ depends on
                             ▼
  ┌──────────────────────────────────────────────────────────────┐
  │  Application Layer                                           │
  │  OrderApplicationService depends on → OrderRepository (iface)│
  │                              depends on → PaymentGateway (iface)
  │                              depends on → EventPublisher (iface)
  │                              depends on → Order (Domain)      │
  └──────────────────────────┬───────────────────────────────────┘
                             │ depends on
                             ▼
  ┌──────────────────────────────────────────────────────────────┐
  │  Domain Layer (zero framework dependencies)                  │
  │  Order depends on → OrderId, UserId, OrderLine, OrderStatus  │
  │  (all value objects / enums in the same layer)               │
  │  NO dependency on Application, Data Access, or Presentation  │
  └──────────────────────────────────────────────────────────────┘
                             ▲
                             │ implements interface declared above
  ┌──────────────────────────┴───────────────────────────────────┐
  │  Data Access Layer (infrastructure — outermost)              │
  │  OrderRepositoryImpl implements → OrderRepository (from App) │
  │                       depends on → OrderJpaRepository        │
  │                       depends on → javax.persistence.*       │
  └──────────────────────────────────────────────────────────────┘

  Compile-time dependency graph:
    Presentation ──► Application ──► Domain      (Domain has NO incoming edges from below)
                                  └► (interfaces)
                                       ▲
    DataAccess ──implements───────────┘   (the only edge that points "up" —
                                            this is the dependency INVERSION)
```

The Spring Boot DI container is the runtime mechanism that makes dependency inversion physically work. The Application layer declares `private final OrderRepository orders;` as a constructor parameter; Spring scans the classpath, finds the `OrderRepositoryImpl` class annotated `@Repository`, instantiates it, and injects it wherever an `OrderRepository` is required. The Application layer's bytecode never mentions `OrderRepositoryImpl`. This is what makes the layer substitutable: in tests, the test harness injects a `Mockito.mock(OrderRepository.class)` instead, and the Application layer runs without a database. The `@Profile("production")` / `@Profile("test")` mechanism is the standard way to swap implementations by environment.

The compile-time enforcement of the rule is what separates a layered architecture from a "we sort of have layers" architecture. Without enforcement, the rule erodes within months: a developer who needs a quick hack makes the Domain entity `@Configurable` so Spring can inject a repository into it, and now the Domain depends on Spring. The next developer makes a controller call a repository directly because "the service layer is just a thin wrapper anyway", and now the Presentation depends on Data Access. The third developer writes a JPA entity method that returns the controller's response DTO because "it's convenient for the JSON serializer", and now Data Access depends on Presentation — the dependency graph has cycles, and the next refactor is a rewrite. The fix is ArchUnit (Java/Kotlin) or equivalent static analysis:

```java
@AnalyzeClasses(packages = "com.example")
class LayerDependencyRuleTest {

    private static final String PRESENTATION = "com.example.orders.api..";
    private static final String APPLICATION  = "com.example.orders.application..";
    private static final String DOMAIN       = "com.example.orders.domain..";
    private static final String DATA_ACCESS  = "com.example.orders.infrastructure..";

    @ArchTest static final ArchRule domain_depends_on_nothing_outside_domain =
        classes().that().resideInAPackage(DOMAIN)
                 .should().onlyDependOnClassesThat().resideInAnyPackage(
                     DOMAIN, "java..");

    @ArchTest static final ArchRule data_access_does_not_depend_on_presentation =
        noClasses().that().resideInAPackage(DATA_ACCESS)
                   .should().dependOnClassesThat().resideInAPackage(PRESENTATION);

    @ArchTest static final ArchRule data_access_does_not_depend_on_application =
        noClasses().that().resideInAPackage(DATA_ACCESS)
                   .should().dependOnClassesThat().resideInAPackage(APPLICATION);

    @ArchTest static final ArchRule presentation_does_not_depend_on_data_access =
        noClasses().that().resideInAPackage(PRESENTATION)
                   .should().dependOnClassesThat().resideInAPackage(DATA_ACCESS);
}
```

The production failure mode of a violated dependency rule is the **circular dependency that breaks the build at 2 a.m.**. Two classes in different layers depend on each other; Spring's `BeanCurrentlyInCreationException` fires on startup because the bean graph has a cycle; the deploy fails; the on-call engineer has to choose between rolling back and hot-patching. The second failure mode is the **unit test that requires a database**: a domain entity that was given a `@PersistenceContext EntityManager` field cannot be tested without booting a JPA context, so what should be a 5 ms unit test becomes a 500 ms integration test, and the test suite goes from 10 seconds to 10 minutes. The third failure mode, the most insidious, is the **substitution that should have been a one-day refactor and became a six-month rewrite**: the team decides to swap PostgreSQL for MongoDB, discovers that the JPA annotations are smeared across the domain entities, and has to refactor every entity class to remove them before the new persistence layer can be built. The fix is to keep the domain layer pure from day one — never annotate domain entities with framework annotations, always translate between domain objects and persistence objects at the Data Access boundary.

### Anti-Pattern: Leaking database structures into presentation views or embedding business validatio...

The three most common anti-patterns that collapse a layered architecture are: (1) returning JPA entities directly from controllers, (2) embedding business validation in database constraints, and (3) the anaemic domain model. Each is a layer-boundary violation that looks like a shortcut on day one and becomes a multi-week cleanup project within a year.

**Anti-pattern 1: The controller returns a JPA entity.** A Spring Boot controller method annotated `@GetMapping("/{id}") public Order findById(@PathVariable Long id)` looks innocent. It is not. Jackson will serialize every public getter on the `Order` entity, including `getCustomer()` — which is a `@ManyToOne` lazy-loaded relationship. The first request triggers a SQL query for the order, then a second query for the customer (the N+1 problem from [[06.07.05. The N+1 Query Problem and Loading Strategies]]). Under load, a single endpoint can produce 100 SQL queries per request. Worse, every field on the entity is now part of the public API contract: renaming `customer` to `buyer` is a breaking change for every API consumer, even though the rename was a database refactor that should have been invisible. The fix is the response DTO pattern — controllers return `OrderResponse` (a class with exactly the fields the API contract specifies), and the controller translates from the domain entity to the DTO explicitly: `OrderResponse.from(order)`. The DTO is in the Presentation layer; the entity is in the Domain layer; the translation happens at the layer boundary.

```java
// ANTI-PATTERN 1: returning JPA entity directly from controller
@RestController
class BadOrdersController {
    @GetMapping("/{id}")
    Order findById(@PathVariable Long id) {        // ← leaks JPA entity to JSON
        return repo.findById(id).orElseThrow();    // ← lazy @ManyToOne triggers
                                                   //   SQL on serialization
    }
}

// CORRECT: explicit response DTO, translation at layer boundary
record OrderResponse(Long id, String status, BigDecimal total, String customerEmail) {
    static OrderResponse from(Order order) {
        return new OrderResponse(
            order.getId().value(),
            order.getStatus().name(),
            order.getTotal().amount(),
            order.getCustomerEmail().value()        // value object unwrapped
        );
    }
}

@RestController
class GoodOrdersController {
    @GetMapping("/{id}")
    OrderResponse findById(@PathVariable Long id) {
        return OrderResponse.from(service.findById(id));
    }
}
```

**Anti-pattern 2: Business validation in database constraints.** A `CHECK (status IN ('PENDING', 'PAID', 'CANCELLED'))` constraint on the `orders` table encodes a business rule (the set of valid order statuses) at the database layer. When the business decides to add a `REFUNDED` status, the change requires a database migration (`ALTER TABLE orders DROP CONSTRAINT orders_status_check, ADD CONSTRAINT orders_status_check CHECK (status IN ('PENDING', 'PAID', 'CANCELLED', 'REFUNDED'))`), a deploy of the new application code, and a coordinated cutover — when the rule should have been a one-line change in the `OrderStatus` enum. Worse, business rules that span multiple columns (`CHECK (cancelled_at IS NULL OR status = 'CANCELLED')`) or multiple tables (a trigger that prevents `INSERT INTO orders` if `users.is_banned = true`) cannot be unit-tested, cannot be debugged in isolation, and are invisible to application developers who joined the team last week. The fix is the rule "databases enforce integrity, applications enforce validity": foreign keys, NOT NULL, and unique constraints belong in the database (they protect against corrupted data from any writer, including ad-hoc SQL); business rules (which statuses are valid, which transitions are allowed, which combinations of fields are legal) belong in the Domain layer where they can be tested, debugged, and version-controlled with the application code.

**Anti-pattern 3: The anaemic domain model.** Martin Fowler's 2003 coinage: an entity that is just a bag of getters and setters, with all logic in service classes. `Order` has `setStatus("PAID")` (a setter) instead of `markPaid()` (a behaviour). `OrderLine` has `setQuantity(int)` (a setter) instead of `changeQuantity(int)` (a behaviour that recalculates the line total and may trigger a back-order). The smell is a service class with methods like `OrderService.markOrderPaid(Order order)` that mutate the entity's state directly via setters — the entity has no behaviour, the service has all the behaviour, and the entity is effectively a struct. The cost is that business rules are scattered across N service classes that all mutate the same entity, the rules are not co-located with the data they govern, and the next developer to add a new status transition has to grep across the entire service layer to find every place that touches the `status` field. The fix is to push behaviour onto the entity: `Order.markPaid()` validates the transition (must be from `PENDING`), sets the status, records the paid-at timestamp, and emits an `OrderPaid` domain event. The service layer's job becomes orchestration (call `order.markPaid()`, then `orders.save(order)`, then `events.publish(order.pullEvents())`) — not business rule enforcement.

```text
Anaemic vs Rich domain model — where does the "mark paid" logic live?

  ANAEMIC:
    Order entity: getStatus(), setStatus(String), getPaidAt(), setPaidAt(Instant)
    OrderService.markPaid(Long orderId) {
        Order o = repo.findById(orderId);
        o.setStatus("PAID");            // ← no validation
        o.setPaidAt(Instant.now());     // ← no coupling between fields
        repo.save(o);
    }
    // Risk: any code can setStatus("PAID") from any starting state.
    // Risk: paidAt may be set without status, status without paidAt.
    // Risk: the rule "only PENDING orders can be marked PAID" lives in
    //       whoever remembers to write the if-check.

  RICH:
    Order entity:
      markPaid() {
          if (status != PENDING)
              throw new IllegalStateTransitionException(status, PAID);
          this.status = PAID;
          this.paidAt = Instant.now();
          this.events.add(new OrderPaid(this.id));   // domain event
      }
    OrderService.markPaid(Long orderId) {
        Order o = repo.findById(orderId);
        o.markPaid();                 // ← rule enforced inside the entity
        repo.save(o);
        events.publish(o.pullEvents());
    }
    // Benefit: the invariant is co-located with the data it governs.
    // Benefit: the entity is unit-testable without any service or repo.
    // Benefit: any future caller of markPaid() gets the rule for free.
```

The production failure mode of the anaemic domain model is the **silent data corruption that nobody can trace**: a developer writes a new endpoint that calls `order.setStatus("PAID")` without setting `paidAt`, the order is now in `PAID` state with a null `paidAt`, the reporting query that joins on `paid_at` produces a wrong total, and the forensic investigation takes three days because the rule "paidAt must be set when status is PAID" was an implicit assumption in the original developer's head, not a code-enforced invariant. The second failure mode is the **impossible refactor**: when business rules are smeared across N service classes, every refactor requires reading every service class that touches the entity, because there is no single source of truth for the entity's invariants. The third failure mode is the **test suite that nobody runs**: a 500 ms integration test that boots Spring and a database to test a single business rule takes too long to run on every save, so developers stop running tests locally, CI catches regressions hours after they were introduced, and the team's velocity collapses. The fix for all three is the same: push behaviour onto the entities, keep the entities pure Java (no framework annotations), and let the service layer be a thin orchestration shell that the unit tests can skip entirely.

## Key Takeaways

1. **Four layers, one direction.** Presentation → Application → Domain → Data Access, with dependencies pointing strictly downward. The Domain layer has zero incoming dependencies from below — it is the innermost circle and depends on nothing in the application.
2. **Dependency inversion is the compile-time mechanism, DI is the runtime mechanism.** The Application layer declares interfaces (`OrderRepository`); the Data Access layer implements them; Spring wires them at runtime. The compile-time graph is acyclic; the runtime graph has the implementation pointing back at the interface, which is the only "upward" edge allowed.
3. **Three anti-patterns collapse the layers: returning JPA entities from controllers, business rules in CHECK constraints, and the anaemic domain model.** Each is a shortcut that becomes a multi-week cleanup. DTOs at every layer boundary, business rules in domain entities, and behaviour-rich entities (not bags of setters) are the fixes.
4. **ArchUnit (or equivalent) is the only enforcement mechanism that survives deadline pressure.** Developer discipline erodes within months; a CI-failing test does not.
