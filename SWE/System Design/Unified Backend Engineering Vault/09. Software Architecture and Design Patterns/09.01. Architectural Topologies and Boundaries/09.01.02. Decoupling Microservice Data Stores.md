# 09.01.02. Decoupling Microservice Data Stores

## What This Is

This note covers the single rule that distinguishes a real microservice architecture from a distributed monolith: **each service owns its own data, and no other service may touch that data directly.** Every other microservices property — independent deployment, polyglot stacks, blast-radius isolation — is a downstream consequence of this one rule. Break it and you have a distributed monolith no matter how many independent deploy pipelines you built. Keep it and you can survive the topology's other failure modes. The note covers the anti-pattern (one shared database that every service reads and writes), the correct pattern (one database per service, with cross-service data needs satisfied via API calls or event-subscribed materialised views), and the architectural consequences that fall out of the correct pattern — CQRS-style eventual consistency between services, the saga pattern for cross-service transactions, the materialised-view pattern for read aggregation, and the data-ownership contract that defines which service is the source of truth for which fact.

The layered mental model connection: this note is the bridge between [[09.01.01. Monoliths Modular Monoliths and Microservices]] (which defines the deployment topology) and the persistence layer from section 06 (which defines how a single service talks to its own database). It is also the bridge to [[08.02.02. The Saga Architectural Pattern]] (which defines how a cross-service business transaction works without a shared ACID transaction) and to [[07.05.02. The Transactional Outbox Pattern]] (which defines how a service atomically updates its own state and publishes the corresponding integration event). The cross-service consistency model is eventual, not linearizable — see [[06.11.03. Distributed Consistency and the CAP Theorem]] — and every architectural decision in this note is a trade against that constraint.

## The Details

### The Shared Database Anti-Pattern: Tight schema coupling, concurrent lock contention, compromised ...

The shared database anti-pattern is what you get when a team adopts microservices for the deployment topology but leaves the persistence layer as it was in the monolith: one PostgreSQL (or MySQL, or MongoDB) cluster, one database, one set of tables, with every service connecting to it as the same application user. The motivating instinct is reasonable-sounding — "we already have a perfectly good database, replication is set up, the connection pool is tuned, why would we build five more?" — and the cost is invisible on day one. The cost becomes visible on the day the first `ALTER TABLE` needs to ship.

The first failure mode is **schema coupling**. If the `OrderService` and the `InventoryService` both read and write the `inventory_items` table, any column rename, type change, or index addition on that table is a coordinated deployment: the team that owns the table ships the migration, then every other team that depends on the old shape ships their consumers, then the table owner ships the cutover. This is the same release-train coordination problem that drove the team away from a monolith in the first place, just relocated from the deploy pipeline to the migration pipeline. Worse, the coordination is often implicit: nobody knows which services touch which tables, so the team shipping the migration runs a search across every codebase for column names and prays. The `inventory_items.qty_on_hand` column rename ships at 2 a.m., the warehouse service breaks at 9 a.m. when the morning shift does the first stock-take query, and nobody connects the two incidents until the on-call engineer notices the timestamp correlation. The fix is per-service database ownership — only the owning service connects to those tables, every other service goes through the owning service's API.

The second failure mode is **lock contention across process boundaries**. Two services writing to the same table are two processes holding PostgreSQL locks against each other, with no shared transaction manager to detect the deadlock cycle. The PostgreSQL `pg_stat_activity` view shows two sessions in `idle in transaction` state, each waiting on a `tuple` lock held by the other, but neither process knows about the other — the deadlock detector (see [[06.04.02. Concurrency Anomalies and Phenomena Deep Dive]]) eventually fires after `deadlock_timeout` (default 1 second), one session gets `ERROR: deadlock detected`, and the application sees a stack trace that points to a row in a table it didn't think it was contending on. The fix is the same: per-service table ownership, so a write to `inventory_items.qty_on_hand` only ever comes from one process, and the locks are visible to that process's own transaction manager.

```text
Shared-database anti-pattern — three services, one DB user, one schema:

  ┌─────────────────┐  ┌─────────────────┐  ┌─────────────────┐
  │  Order Service  │  │ Inventory Svc   │  │  Pricing Svc    │
  │  (Spring Boot)  │  │  (Go)           │  │  (Python)       │
  └────────┬────────┘  └────────┬────────┘  └────────┬────────┘
           │ jdbc:postgresql...  │ pgx driver            │ psycopg
           │ user=app_user       │ user=app_user         │ user=app_user
           └─────────┬───────────┴───────────────────────┘
                     ▼
        ┌────────────────────────────────────┐
        │  PostgreSQL                        │
        │  tables: orders, order_items,      │
        │  inventory_items, prices, ...      │
        │  (all GRANTed to app_user)         │
        └────────────────────────────────────┘

  What breaks:
  1. ALTER TABLE inventory_items ADD COLUMN warehouse_code TEXT;
     → Order Service deploy must coordinate with Inventory + Pricing.
  2. Order Service holds row lock on inventory_items row X (decrement qty).
     Inventory Service holds row lock on inventory_items row Y (recount).
     Both want the other's row → deadlock detector fires in 1 s.
  3. Pricing Service runs SELECT * FROM inventory_items WHERE ... FOR UPDATE
     → blocks every Order Service write for the scan duration.
  4. Zero observability of who is hammering the DB: every connection
     looks the same in pg_stat_activity (user=app_user, app=undefined).
```

The third failure mode is **operational independence loss**. The whole point of microservices was that the Order team could ship a hotfix at 3 a.m. without waking up the Inventory team. But if the Order team's hotfix requires a column on `inventory_items` (because the order logic now needs to record the warehouse it was fulfilled from), the Inventory team owns that table, has to review the migration, has to schedule the deploy during their own maintenance window. The microservice boundary is fiction; the table boundary is the real one. The fourth failure mode is **observability collapse**: every service connects as the same database user, so `pg_stat_activity` cannot tell you which service is running which query, which means a slow-query incident requires correlating PostgreSQL query logs with five different service log streams before you can identify the culprit.

The fifth failure mode, and the one that finally pushes teams off the shared database, is **the silent schema drift that breaks on the next deploy**. Service A and Service B both read the `orders` table. Service A's team adds a NOT NULL column with a default. Service B's team doesn't notice because the column is optional from their perspective (they SELECT only the columns they need). Six months later Service B's team writes a new query that uses `SELECT *` for the first time, the ORM binds to the new column, the type doesn't match the entity, and the deploy fails in production with a `ColumnNotFound` or `TypeMismatch` error that nobody in Service B's team can explain because they don't know the schema ever changed. The fix — per-service database ownership with per-service database users and per-service schemas — eliminates an entire class of cross-team coordination costs that masquerade as "just one more migration to schedule".

### The Database-per-Service Pattern: Complete data isolation, access via public APIs/events only, re...

The database-per-service pattern is the rule that every microservice owns its own database, that no other service may connect to that database directly, and that all cross-service data needs are satisfied either by a network API call to the owning service or by subscribing to events that the owning service publishes. "Owns its own database" can mean a separate PostgreSQL cluster per service, a separate database within a shared cluster (`CREATE DATABASE orders_db; CREATE DATABASE inventory_db;`), or a separate schema within a shared database with separate users and GRANTs (`CREATE SCHEMA orders; CREATE USER orders_app; GRANT USAGE ON SCHEMA orders TO orders_app;`). The strongest form is a separate cluster — full physical isolation, independent backup/restore, independent scaling, independent hardware if budget allows. The weakest acceptable form is separate schemas with separate users; anything weaker (shared schema, shared user) is the anti-pattern above and is not database-per-service.

The immediate consequence is that **cross-service SQL JOINs are no longer possible**. A query that the monolith used to answer with `SELECT o.id, u.email, p.amount FROM orders o JOIN users u ON o.user_id = u.id JOIN payments p ON o.id = p.order_id` must now be answered in one of three ways. First, **API composition**: the OrderService makes parallel calls to `GET /users/{id}` and `GET /payments?order_id={id}`, then composes the results in memory. This is the right answer when the fan-out is small (≤ 5 downstream calls), the data volume per call is small, and the latency budget tolerates the slowest downstream's p99. Second, **materialised view via event subscription**: the OrderService subscribes to `UserCreated`, `UserEmailUpdated`, `PaymentRecorded` events from the other services, maintains a local `order_view` table that denormalises the data it needs, and queries that table locally. This is the right answer when the read volume is high, the join is wide, or the latency budget is tight — but it introduces eventual consistency between the source-of-truth and the read model, typically 50–500 ms of projection lag. Third, **CQRS with a dedicated read model**: build a dedicated query service whose only job is to maintain a pre-joined projection for this exact query, fed by events from every upstream service. This is the right answer when the read pattern is dominant and the schema is stable enough to make the projection worth building.

```text
Database-per-service — three services, three DBs, three users:

  ┌─────────────────┐  ┌─────────────────┐  ┌─────────────────┐
  │  Order Service  │  │ Inventory Svc   │  │   User Svc      │
  │  (Spring Boot)  │  │  (Go)           │  │   (Python)      │
  │  owns orders_db │  │ owns inv_db     │  │  owns users_db  │
  └────────┬────────┘  └────────┬────────┘  └────────┬────────┘
           │                      │                     │
           │ orders_db (PG)       │ inv_db (PG)         │ users_db (PG)
           │ user=orders_app      │ user=inv_app        │ user=users_app
           ▼                      ▼                     ▼
   ┌────────────────┐    ┌────────────────┐    ┌────────────────┐
   │  orders.orders │    │  inv.items     │    │  users.users   │
   │  orders.items  │    │  inv.reserved  │    │  users.emails  │
   └────────────────┘    └────────────────┘    └────────────────┘

  Cross-service "JOIN" is now impossible. The OrderService has three options:

  (a) API composition (synchronous, linearizable read):
      OrderService → GET /users/{id}            (User Service, ~2 ms)
                   → GET /payments?order_id={id} (Payment Service, ~3 ms)
                   → compose in memory
      Cost: 2 network calls + composition time. p99 ≈ max(downstream p99s).

  (b) Materialised view via event subscription (async, eventually consistent):
      OrderService maintains: CREATE TABLE order_view (
        order_id UUID PRIMARY KEY,
        user_email TEXT,           -- denormalised from users.emails
        payment_amount INT         -- denormalised from payments
      );
      Kafka consumer: on UserEmailUpdated → UPDATE order_view SET user_email=? WHERE user_id=?;
      Cost: 50–500 ms projection lag. Read is one local query, ~1 ms.

  (c) CQRS dedicated read model (heaviest, only for high-volume stable reads):
      A dedicated OrderQueryService subscribes to every relevant event
      and exposes only read APIs. See [[09.05.01. Command Query Responsibility
      Segregation (CQRS)]] for the full pattern.
```

The data ownership contract is the explicit, versioned, documented agreement that defines which service is the source of truth for which fact. For every piece of data in the system, exactly one service owns writes; other services may hold cached or denormalised copies, but the owning service is the canonical source. The contract is typically expressed as a table: "fact → owning service → read API → mutation API → integration events emitted". The `user.email` column is owned by the UserService; the UserService emits `UserEmailUpdated` events when it changes; the OrderService may hold a copy in its `order_view` table for read performance, but must never mutate it directly. The `inventory_items.qty_on_hand` column is owned by the InventoryService; the OrderService may decrement it via `POST /inventory/reserve {item_id, qty}`, which the InventoryService handles by atomically updating its own table and emitting an `InventoryReserved` event. The contract is the boundary; without it, every team makes ad-hoc assumptions about who owns what and the first cross-service bug turns into a fortnight-long forensic investigation.

The saga pattern is the mechanism for cross-service business transactions — sequences of mutations that must either all succeed or all roll back, but that span multiple services and therefore cannot use a single ACID transaction. A choreographed saga has each service emit an event that triggers the next step: `OrderCreated` → InventoryService consumes, emits `InventoryReserved` → PaymentService consumes, emits `PaymentCharged` → ShippingService consumes, emits `ShipmentDispatched` → OrderService consumes, marks order `FULFILLED`. If any step fails, compensating events flow back: `PaymentFailed` → InventoryService consumes, emits `InventoryReleased` → OrderService consumes, marks order `CANCELLED`. An orchestrated saga has a central orchestrator (typically a state machine in the OrderService) that calls each downstream synchronously or via commands and tracks the state to know when to fire compensations. The trade-offs are covered in depth in [[08.02.02. The Saga Architectural Pattern]]; the relevant point here is that **sagas are the price of database-per-service**, and any team adopting microservices without accepting that every cross-service business transaction is now a saga will ship data-inconsistency bugs in production within six months.

```java
// Spring Boot: dual-write-safe event publication via the Transactional Outbox
// pattern from [[07.05.02. The Transactional Outbox Pattern]]
@Service
public class OrderService {

    private final OrderRepository orders;
    private final OutboxRepository outbox;
    private final PaymentClient payments;   // Feign client, see [[09.01.01]]

    @Transactional
    public Order createOrder(CreateOrderCommand cmd) {
        // 1. Persist the order to orders_db (local ACID transaction)
        Order order = orders.save(new Order(cmd.userId(), cmd.items()));

        // 2. Append the integration event to the outbox table in the SAME
        //    transaction — atomic with the order insert. No dual-write window.
        outbox.save(new OutboxEntry(
            "OrderCreated",
            new OrderCreatedEvent(order.getId(), order.getUserId(), order.getTotal())
        ));

        return order;
        // 3. A separate OutboxPublisher polls the outbox table and publishes
        //    to Kafka. At-least-once; consumers must be idempotent.
        // 4. The PaymentService consumes OrderCreated, calls Stripe,
        //    emits PaymentCharged. The InventoryService reserves stock and
        //    emits InventoryReserved. These are saga steps — see [[08.02.02]].
    }
}

// Outbox table — guarantees order insert + event append are atomic
// (single ACID transaction against orders_db)
@Entity
@Table(name = "outbox")
class OutboxEntry {
    @Id @GeneratedValue
    private Long id;
    private String eventType;
    @Column(columnDefinition = "jsonb")
    private String payload;
    private Instant occurredAt = Instant.now();
    private Instant publishedAt;   // null until the publisher sends it
}
```

```sql
-- The publisher runs every 100 ms and publishes unpublished outbox rows
-- via the Kafka producer, then marks them as published.
-- SELECT ... FOR UPDATE SKIP LOCKED allows multiple publisher instances
-- to share the load without collision (see [[07.05.02]]).
SELECT id, event_type, payload
  FROM outbox
 WHERE published_at IS NULL
 ORDER BY id
 LIMIT 500
 FOR UPDATE SKIP LOCKED;
```

The failure mode of database-per-service is **inappropriate use of API composition for high-volume reads**. The team builds a "user dashboard" endpoint that fans out to 7 downstream services per request, each with a 5 ms p99, and wonders why the dashboard's p99 is 35 ms under load and 800 ms during a downstream incident. The fix is to recognise that high-volume reads with wide joins need a materialised view, not a fan-out — and to budget the engineering time to build the projection. The second failure mode is **treating eventual consistency as a bug**. A user updates their email, refreshes the page, sees the old email, files a bug report. The fix is UX: the user-facing confirmation page reads from the write side (the UserService API), not from the read model; downstream read models catch up asynchronously. The third failure mode is **the dual-write bug** — a service tries to update its own database and then publish an event to Kafka, the database commit succeeds, the Kafka publish fails (network blip), and the system is now in an inconsistent state where the order exists but no event was ever emitted to drive the saga forward. The fix is the transactional outbox pattern from [[07.05.02. The Transactional Outbox Pattern]] — write the event to a local `outbox` table in the same transaction as the business mutation, then a separate publisher process ships the event to Kafka with at-least-once semantics. The fourth failure mode, growing in frequency, is **the over-subscribed materialised view** — every team builds its own denormalised projection of every other team's data, the projections drift independently, and there are now seventeen sources of truth for "user email" each of which is correct under a different set of conditions. The fix is a single canonical event bus, a single canonical event schema per fact, and a published schema registry that every projection consumes from.

## Key Takeaways

1. **Database-per-service is the load-bearing rule.** Every other microservices property — independent deployment, blast-radius isolation, polyglot stacks — collapses if services share a database. A distributed monolith with shared tables is strictly worse than either a monolith or a well-designed microservice topology.
2. **Cross-service JOINs are gone for good.** Replace them with API composition (for low-volume, narrow reads) or materialised views built from event subscriptions (for high-volume, wide reads). Accept that the read model is eventually consistent and design the UX around the projection lag.
3. **Cross-service business transactions are sagas, not ACID transactions.** Every multi-service mutation must be modelled as a sequence of local transactions with compensating actions on failure. The transactional outbox pattern is the mechanism that makes the event publication atomic with the local mutation.
4. **The data ownership contract must be explicit and versioned.** For every fact in the system, exactly one service is the source of truth. Every other service's copy is a downstream projection with documented lag and a documented refresh mechanism. Without this contract, cross-service bugs become fortnight-long forensic investigations.
