# 09.01.01. Monoliths Modular Monoliths and Microservices

## What This Is

This note is the single decision that most shapes every other architectural choice: how many independently-deployable units own your backend code. The three points on the spectrum — monolith, modular monolith, microservices — are not three flavours of the same thing. They are three different physical systems with different latency budgets, different consistency models, different failure modes, different deployment cadences, and different team structures that produce them. Picking one is a one-way door. Moving from monolith to microservices is a multi-quarter extraction project (Segment's 2017–2020 microservices-to-monolith reversal, Amazon's periodic consolidations). Moving from microservices back to a monolith is also a multi-quarter project. The note assumes you have read the prerequisite runtime notes (sections 02–04: process boundaries, kernel IPC, thread/memory models) because the differences between these topologies are almost entirely a function of where the process boundaries fall.

The layered mental model connection: a monolith collapses everything into one process — the routing layer from [[05.01.01. Routing Data Structures and Algorithms]], the middleware pipeline from [[05.02.01. The Chain of Responsibility Pattern in Web Pipelines]], the persistence layer from section 06, and the messaging layer from section 07 all run inside the same JVM/Node.js/CPython process. A modular monolith is the same, with package-level boundaries. A microservice topology splits each layer into its own process — the routing layer is now a network call, the persistence layer is now a database owned by a different team, the messaging layer is now an actual Kafka cluster from section 07.02. Every in-process function call that crossed a module boundary inside a monolith becomes a network call that crosses a process boundary inside a microservice topology, with all the failure modes from [[08.01.01. Core Fallacies and Physical Realities]] suddenly in play.

## The Details

### The Monolithic Architecture: Single deployment unit, shared memory execution, simple operations, ...

A monolith is one deployable artifact — one Spring Boot fat JAR, one Node.js process, one PHP-FPM pool, one Rails application server — that contains every line of backend code, talks to one primary database (with one connection pool), and runs inside one process boundary. Every "call" between subsystems is a JVM method invocation or a Python function call: nanoseconds, no serialization, no network, no timeout, no retry, no circuit breaker. A transaction that mutates `users`, `orders`, `payments`, and `notifications` rows is one `BEGIN ... COMMIT` against one PostgreSQL connection, holding one set of locks, recoverable via one WAL replay from [[06.01.02. Write-Ahead Logging (WAL) and Crash Recovery]]. The operational surface area is one Docker image, one Kubernetes Deployment, one horizontal pod autoscaler, one log stream, one APM service entry, one deployment pipeline. This is why Stack Overflow can serve roughly a billion page views a month with nine web servers and a single SQL Server cluster, and why GitHub ran on a Rails monolith well past 100 million users.

The cost of the monolith is not performance or scale — it scales as far as a single primary database can scale, which is very far. The cost is *coupling along every axis except runtime*: every team that touches the codebase shares the same deployment cadence, the same release train, the same rollback blast radius. If the payments team needs to ship a hotfix on Tuesday and the search team just merged a risky refactor that takes 40 minutes to roll back, the payments hotfix waits. If one team's bug takes down the process, every team's feature is down. The deployment coordination cost grows super-linearly with team count: a 5-team monolith is manageable, a 20-team monolith is a calendar nightmare, a 100-team monolith is structurally impossible. The other cost is *piecewise scaling*: if the payment refund endpoint needs 50 pods to handle a Black Friday spike but the user-settings endpoint needs 2, you scale the whole artifact to 50 and pay for 48 idle pods of user-settings capacity. The failure mode is rarely "the monolith is too slow" — it is "the monolith cannot ship fast enough because the deploy coordination tax has eaten the dev cycle".

```text
Monolith deployment topology (one process, one DB):

  ┌──────────────────────────────────────────────────────────────┐
  │  Spring Boot fat JAR (one JVM process)                       │
  │  ┌────────────┐ ┌────────────┐ ┌──────────┐ ┌─────────────┐  │
  │  │ UserController│ OrderCtrl │ │PaymentCtrl│ NotifCtrl   │  │
  │  └─────┬──────┘ └─────┬──────┘ └─────┬─────┘ └──────┬──────┘  │
  │        │ in-proc fn    │ in-proc fn   │ in-proc fn  │         │
  │        ▼               ▼              ▼             ▼         │
  │  ┌────────────────────────────────────────────────────────┐  │
  │  │  Service layer (UserService, OrderService, ...)         │  │
  │  └────────────────────────┬───────────────────────────────┘  │
  │                           │ JDBC                              │
  │  ┌────────────────────────▼───────────────────────────────┐  │
  │  │  HikariCP pool (maxPoolSize=20, one pool, one DB)       │  │
  │  └────────────────────────┬───────────────────────────────┘  │

                  ┌───────────▼───────────┐

                  │  (users, orders,      │
                  │   payments, notifs)   │
                  └───────────────────────┘

  Call latency:        ~50 ns (JVM method invocation)
  Transaction:         BEGIN; UPDATE users...; UPDATE orders...; COMMIT;

  Deploy cadence:      one release train for every team
```

The Spring Boot version of the above is what you get from `spring init` with the Web, JPA, and PostgreSQL starters — one `@SpringBootApplication` class, one `application.yml`, one JDBC URL, one HikariCP pool. The deployment unit is `target/app.jar`. There is nothing architecturally wrong with this. It is the right answer for the vast majority of backend systems, and the engineer who reaches for microservices before feeling the pain of monolith coordination is the engineer who will spend the next two years debugging distributed-systems problems they didn't have to have. See [[09.01.02. Decoupling Microservice Data Stores]] for the specific reason most teams reach for microservices too early — they confuse deployment coupling (a monolith problem) with data coupling (a schema-design problem that the modular monolith solves without going distributed).

### The Modular Monolith: Strict in-process module boundaries, decoupled domain packages, shared infr...

The modular monolith is the answer to the question "what if we kept the single deployable but enforced the architectural discipline of microservices inside the codebase?" One JVM process, one fat JAR, one deployment pipeline, one database server — but inside the codebase, modules are bounded contexts. Each module owns its own database tables (or its own schema in the same PostgreSQL cluster), exposes a public in-process API (a Java interface, a Kotlin sealed class, a Ruby module), and is forbidden by build-time rule from reaching into another module's tables, repositories, or internal classes. Inter-module communication is in-process function calls through published interfaces, not SQL joins across tables.

The point of this topology is that it preserves the operational simplicity of the monolith (one deploy, one log stream, one APM service, ACID transactions across modules via a single `@Transactional` boundary) while creating the architectural preconditions for an eventual microservices extraction. When the payments module eventually does need to be extracted into its own service — because its scaling profile diverged from the rest, or because a separate team took ownership — the extraction is a mechanical refactoring: replace the in-process `PaymentService` interface with a Feign client or gRPC stub. If the modules were never disciplined, the extraction is a multi-year archaeological dig through every cross-module SQL join, every shared ORM entity, every private method call.

Shopify is the canonical reference. Shopify runs one of the largest Rails monoliths in the world (~3.5 million lines of Ruby, ~700K requests/sec at peak). Around 2019 they introduced the concept of "Components" — Ruby modules with strict ownership boundaries, each with its own schema, its own tests, its own team. They wrote `packwerk`, a static analysis tool that enforces boundary rules at CI time. The result is that Shopify gets microservices-shaped architectural discipline without paying the distributed-systems tax on every call. Basecamp, GitLab, and Stack Overflow follow the same pattern. The Spring Boot equivalent uses ArchUnit:

```java
// ArchUnit rule: enforce that no class in com.shop.payments
// may depend on com.shop.orders (or any other module)
@AnalyzeClasses(packages = "com.shop")
class ModuleBoundaryTest {

    private static final JavaClass PAYMENTS = JavaClass.PACKAGE_MATCHER("com.shop.payments..");
    private static final JavaClass ORDERS    = JavaClass.PACKAGE_MATCHER("com.shop.orders..");
    private static final JavaClass USERS     = JavaClass.PACKAGE_MATCHER("com.shop.users..");

    @ArchTest
    static final ArchRule payments_does_not_depend_on_orders =
        noClasses().that().resideInAPackage("com.shop.payments..")
                   .should().dependOnClassesThat().resideInAPackage("com.shop.orders..");

    @ArchTest
    static final ArchRule payments_does_not_depend_on_users =
        noClasses().that().resideInAPackage("com.shop.payments..")
                   .should().dependOnClassesThat().resideInAPackage("com.shop.users..");

    @ArchTest
    static final ArchRule modules_communicate_only_via_public_api =
        classes().that().resideInAPackage("com.shop..internal..")
                  .should().onlyBeAccessed().byClassesThat().resideInAnyPackage(
                      "com.shop..internal..", "com.shop..api..");
}
```

The failure mode of the modular monolith is boundary rot. Without an enforcement mechanism that fails the CI build on every cross-module dependency, the boundaries erode within six months. A developer who needs a quick lookup of an order's payment status writes `Order.joins(:payment).where(user_id: ...)` because it's "just one query" — and now the orders module and the payments module share a schema dependency that will haunt every future migration. ArchUnit (Java/Kotlin), `packwerk` (Ruby), `import-linter` (Python), and Depcheck (TypeScript/ESLint) exist precisely because developer discipline is not a sufficient enforcement mechanism. The second failure mode is the shared schema: if all modules share one database user with full DML privileges on every table, the boundary exists only in code, not in the data layer, and the first person to write a cross-module SQL join in a reporting query will discover this. The fix is per-module PostgreSQL roles with `GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA payments_schema TO payments_role;` — at which point a cross-module join physically fails with `permission denied`.

### The Microservices Architecture: Decentralized data ownership, independent deployment pipelines, p...

A microservice is a deployment unit that owns its own data, runs in its own process, exposes its functionality over a network API (REST, gRPC, GraphQL, or an event subscription), and can be deployed, scaled, rolled back, and rewritten independently of every other service. The defining property is not "small" — a microservice can be 50K lines of code. The defining property is *independent deployability on an independent cadence by an independent team*. Netflix's hundreds of services, Uber's thousands, Amazon's tens of thousands — these are all microservice topologies. The trade is explicit: you trade the operational simplicity and ACID guarantees of a monolith for the ability to scale teams past the Dunbar number of one deployment pipeline, to scale subsystems independently, to use polyglot stacks (Go for the high-throughput ingestion service, Python for the ML inference service, Java for the transactional core), and to contain blast radius (a memory leak in the recommendations service does not take down checkout).

The cost is the full distributed-systems tax. Every inter-service call is a network round trip: 0.5–2 ms intra-AZ, 5–20 ms cross-AZ, 50–150 ms cross-region (numbers from [[03.02.02. Connection Management in HTTP 1.1]] and [[08.01.01. Core Fallacies and Physical Realities]]). Every call has a timeout, a retry policy, a circuit breaker, and a fallback. Every cross-service business transaction (create order → reserve inventory → charge payment → emit shipping request) is a saga, not an ACID transaction — see [[08.02.02. The Saga Architectural Pattern]] for the choreography vs orchestration choice. Every read that used to be a `JOIN` is now either a fan-out of N parallel service calls (with the slowest one setting p99 latency) or a materialised view built from subscribed events. Every deployment is a coordinated schema evolution across two services: the producer that emits the event and the consumer that subscribes to it. Every bug investigation that used to be "grep the log file" is now distributed tracing across five services, three message queues, and two databases, with OpenTelemetry `traceparent` headers from [[11.02.02. Context Propagation and W3C TraceContext]] stitched through every hop.

```text
Microservices topology — N deploys, N DBs, network between:

  Client ──HTTPS──► API Gateway ──┬──► Orders Service ────► orders_db
                                  ├──► Payments Service ──► payments_db
                                  ├──► Inventory Service ─► inventory_db
                                  └──► Shipping Service ──► shipping_db
                                         ▲              │
                                         │ Kafka        │ Kafka
                                         │ order.placed │ shipment.created
                                         │              ▼
                                         └────  Notifications Service ──► notifications_db

  Inter-service call latency:   0.5–2 ms intra-AZ (REST/gRPC over TCP)
  Cross-service transaction:    Saga (orchestrated or choreographed) — see [[08.02.02]]
  Cross-service JOIN:           Forbidden. Aggregate in API gateway, or subscribe
                                to events and maintain a local materialised view.
  Failure isolation:            payments OOM does not affect orders read path
  Deployment cadence:           each service on its own release train
  Observability cost:           1 distributed tracer, 1 metrics backend, 1 log backend
                                per service (or one shared with multi-tenant labels)
  Schema evolution:             backward + forward compatible (Protobuf `reserved`,
                                JSON Schema additive-only, gRPC allow_unknown_fields)
```

```java
// Spring Boot microservice calling another microservice via Feign
// (instead of the in-process @Autowired PaymentService of the monolith)
@FeignClient(name = "payments-service", url = "${services.payments.url}",
             configuration = PaymentsClientConfig.class)
public interface PaymentsClient {

    @PostMapping(value = "/api/v1/charges", consumes = "application/json")
    ChargeResponse charge(@RequestBody ChargeRequest request);

    @GetMapping(value = "/api/v1/charges/{id}")
    ChargeResponse findById(@PathVariable("id") String id);
}

// Configuration: timeout, retry, circuit breaker (Resilience4j)
@Configuration
class PaymentsClientConfig {

    @Bean
    Request.Options options() {
        // connectTimeout = 500 ms, readTimeout = 2000 ms — see [[03.02.02]] for why
        return new Request.Options(500, 2000);
    }

    @Bean
    Retryer retryer() {
        // 3 attempts, 100 ms initial backoff, 1.5x multiplier, 500 ms max
        return new Retryer.Default(100, 500, 3);
    }

    @Bean
    CircuitBreaker circuitBreaker(CircuitBreakerRegistry registry) {
        CircuitBreakerConfig cfg = CircuitBreakerConfig.custom()
            .failureRateThreshold(50)               // open at 50% failures
            .slowCallRateThreshold(80)              // open at 80% slow calls
            .slowCallDurationThreshold(Duration.ofMillis(800))
            .waitDurationInOpenState(Duration.ofSeconds(30))
            .slidingWindowSize(20)
            .build();
        return registry.circuitBreaker("payments", cfg);
    }
}
```

The dominant failure mode of microservices is the *distributed monolith*: a system that has the operational complexity of microservices (N deploy pipelines, N tracing spans per request, N places for a timeout to fire) but the coupling of a monolith (services share a database, must be deployed together in a specific order, synchronously call each other in chains so deep that one slow downstream takes down the whole request path). A distributed monolith is strictly worse than either a monolith or a well-designed microservice topology. The second failure mode is *fan-out latency amplification*: an API gateway endpoint that calls 6 downstream services in parallel, where each downstream has a p99 of 50 ms, has a p99 of approximately 50 ms (the slowest) under normal load — but under sustained load with retries, the p99 amplifies to 200 ms+ because retry storms hit the same slow downstream. The third failure mode is *eventual consistency bugs that look like data loss*: a user creates an order, the inventory service has 80 ms of projection lag, the user refreshes the order page and sees "out of stock" for an item they just successfully bought. These are not bugs you can fix with a transaction — they are the architectural cost of going distributed, and the only mitigation is to design the UX around eventual consistency (show "processing" instead of "complete" until the read model catches up).

### Conway's Law and designing system topologies matching organizational team structures

Melvin Conway's 1968 observation, now called Conway's Law: "Organizations which design systems are constrained to produce designs which are copies of the communication structures of these organizations." The contrapositive, codified by Matthew Skelton and Manuel Pais in *Team Topologies* (2019) as the "Inverse Conway Maneuver", is the actionable version: *set up the team structure you want the architecture to mirror, and the architecture will follow*. A four-person startup will produce a monolith no matter how many times they read Sam Newman's *Building Microservices* — there is no team boundary for the architecture to mirror. A 500-engineer organisation with 50 stream-aligned teams will produce something that looks suspiciously like 50 microservices, regardless of whether the principal architect mandated a monolith. The architecture is downstream of the org chart, not the other way around.

The Team Topologies model defines four team types: **stream-aligned teams** (the product teams that own a vertical slice of business value — checkout, search, recommendations), **platform teams** (the team that builds the internal developer platform — the Kubernetes cluster, the CI/CD pipeline, the observability stack, the auth service — that the stream-aligned teams consume as a product), **enabling teams** (transient teams that help a stream-aligned team adopt a new technology or practice — "the Spring Boot to Quarkus migration enabling team" that exists for six months and disbands), and **complicated-subsystem teams** (teams that own a single hard subsystem requiring deep specialist expertise — the recommendation ranking model, the fraud-detection rules engine, the financial ledger). The interaction modes are: *collaboration* (high-bandwidth, two teams working closely for a short period), *x-as-a-service* (a stream-aligned team consumes a platform team's product via a stable API), and *facilitating* (an enabling team coaches a stream-aligned team through a transition).

```text
Conway's Law in action — same product, two org charts:

  Org A: 1 monolith team of 40 engineers           →  1 monolith
  ┌────────────────────────────────────────────────┐
  │  Checkout | Search | Users | Payments | Notif  │   all in one
  │  ← all one team, one standup, one deploy →     │   deployable
  └────────────────────────────────────────────────┘

  Org B: 5 stream-aligned teams                    →  5 services
  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐
  │ Checkout │ │ Search   │ │ Users    │ │ Payments │ │ Notif    │
  │  team    │ │  team    │ │  team    │ │  team    │ │  team    │
  │  (6 eng) │ │  (8 eng) │ │  (5 eng) │ │  (4 eng) │ │  (3 eng) │
  └────┬─────┘ └────┬─────┘ └────┬─────┘ └────┬─────┘ └────┬─────┘
       │            │            │            │            │
       └────────────┴────────────┴────────────┴────────────┘
                            │
                  ┌─────────▼──────────┐
                  │  Platform team     │  provides K8s, CI/CD,
                  │  (8 eng)           │  observability, auth
                  └────────────────────┘  as a service to all 5
```

The Amazon two-pizza-team rule (no team larger than can be fed by two pizzas, ~6–10 engineers) was a Conway's Law implementation: cap team size at the Dunbar number for tight collaboration, force teams to split when they exceed it, and accept that the architecture will fragment along the same lines. The Spotify "squad / tribe / chapter / guild" model was another. Both produced microservice topologies not because the architects mandated microservices but because the team structure made monolithic shared code ownership structurally impossible at that scale.

The production failure mode of ignoring Conway's Law is the *Conway's Law_penalty*: you mandate a microservice architecture but keep a single 80-engineer team organised by layer (frontend team, backend team, DBA team, QA team), and what you get is a distributed monolith where the "services" are layered — a Frontend service calls a Backend service calls a Database service — because that's the team structure. The second failure mode is the *platform team that is actually a bottleneck*: a platform team of 3 engineers supporting 40 stream-aligned teams becomes the gating factor on every new service launch, and the stream-aligned teams start building shadow infrastructure to bypass them. The fix is to staff the platform team at roughly 1 platform engineer per 8–10 stream-aligned engineers, treat the platform as a real product with a roadmap and a user research practice, and make the self-service portal good enough that the stream-aligned teams never need to talk to the platform team to ship a new service. The third failure mode is the *frozen org chart*: teams were reorganised six months ago but the service boundaries still mirror the previous org chart, and the new teams are now maintaining services whose boundaries no longer match their mission. The fix is to budget for architecture refactoring as a regular cost of org-chart changes, not an exception.

## Key Takeaways

1. **Topology choice is a one-way door and is dominated by team structure, not by technical requirements.** A 5-engineer team cannot operate a 30-service topology; a 500-engineer organisation cannot ship product on a single monolith. Match the topology to the team count, not to the request rate.
2. **The modular monolith is the default for any team under ~50 engineers.** It preserves single-deploy ACID transactions and nanosecond in-process calls while creating the boundary discipline that makes a future microservices extraction mechanical rather than archaeological. ArchUnit (or equivalent) is the only enforcement mechanism that survives contact with deadline pressure.
3. **The defining property of microservices is independent deployability, not "small".** A 50K-line service that is independently deployed by an independent team is a microservice; a 500-line service that must be deployed in lockstep with three other services is part of a distributed monolith and is strictly worse than either alternative.
4. **Conway's Law is descriptive, not prescriptive, but the Inverse Conway Maneuver is prescriptive.** Reorganise the teams to produce the architecture you want — do not mandate an architecture and hope the teams will figure out how to produce it.
