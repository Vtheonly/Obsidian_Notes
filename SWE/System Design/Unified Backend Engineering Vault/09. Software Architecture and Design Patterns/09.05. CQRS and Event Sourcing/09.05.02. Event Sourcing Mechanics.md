# 09.05.02. Event Sourcing Mechanics

## What This Is

Event sourcing inverts the usual storage contract. Instead of writing the *current* state of an entity to a row that you overwrite on every change, you write an append-only sequence of immutable *events* describing what happened to that entity, and you reconstruct the current state at read time (or projection time) by replaying them. The events are the source of truth — the row in `accounts` is just a cached projection that could be thrown away and rebuilt. This sits one layer above traditional persistence (you still need a durable log underneath — usually Postgres, EventStoreDB, or Kafka) and one layer below the application services that ask "what is the current balance of account 42?".

The pattern matters because it changes what you can ask of your data. A `balance` column can answer "what is the balance now"; an event log can answer "what was the balance at 14:37:02 last Tuesday, and how did it get there?" — and it answers it without a separate audit table, because the audit table *is* the primary store. It is the storage pattern underneath CQRS (the two together let you write in event form and read in any number of denormalised forms), and it is the storage pattern underneath domain events in DDD (the aggregate emits the event as part of its state transition, not as a side effect after the fact).

The cost is real. You pay in storage (you keep every change forever), you pay in rehydration latency (rebuilding a 10-year-old aggregate means replaying every event since creation), and you pay in versioning (every event schema change is a migration problem on an immutable log you cannot rewrite). The mechanics below — the append-only invariant, rehydration, snapshotting, projection, and temporal query — are exactly the levers that determine whether you pay those costs gracefully or get paged at 3 a.m. because rehydration of one customer's aggregate just took 18 seconds.

## The Details

### The Core Invariant: State is not stored as a mutable snapshot; state is stored as an append-only ...

The defining contract of event sourcing is that the only legal write to an aggregate's storage is `APPEND(event)`. There is no `UPDATE`, no `DELETE`, no in-place overwrite — those operations do not exist in the storage vocabulary. The current state is a *function* of the event stream, computed by replay; it is never itself stored as the authoritative record. Everything else (snapshots, projections, read models) is a cache, and caches can be dropped and rebuilt from the event log without information loss.

This invariant is what makes the log auditable and temporal. Because events are immutable and append-only, the log is a total order of every state transition that ever happened, signed with the timestamp at which it was recorded. You cannot tamper with history without leaving a visible gap — and because the log is the source of truth, tampering with the row that *looks* like the state (the projection) does not corrupt the real state, because the projection can be rebuilt. This is the same property that makes `git` objects immutable and WAL records immutable: the audit trail *is* the data.

Here is the smallest end-to-end implementation in Java that respects the invariant. The `Account` aggregate has `deposit` and `withdraw` *command* methods that validate the command and then *emit* `MoneyDeposited` / `MoneyWithdrawn` *events*; it never mutates a `balance` field directly. The `balance` field is only ever touched inside `apply(Event)`, which is called during both initial emission and replay.

```java
// Immutable events — past tense, named after the fact that occurred.
sealed interface AccountEvent permits MoneyDeposited, MoneyWithdrawn {}
record MoneyDeposited(UUID accountId, BigDecimal amount, Instant at) implements AccountEvent {}
record MoneyWithdrawn(UUID accountId, BigDecimal amount, Instant at) implements AccountEvent {}

// The aggregate. balance is derived; commands emit, never mutate.
final class Account {
    private final UUID id;
    private BigDecimal balance = BigDecimal.ZERO;   // derived, never persisted directly
    private long version = 0;                        // optimistic-concurrency token

    Account(UUID id) { this.id = id; }

    // Command — validates, then emits. Never mutates balance here.
    List<AccountEvent> withdraw(BigDecimal amount) {
        if (amount.signum() <= 0) throw new IllegalArgumentException("amount > 0");
        if (amount.compareTo(balance) > 0) throw new IllegalStateException("insufficient funds: have " + balance);
        return List.of(new MoneyWithdrawn(id, amount, Instant.now()));
    }
    List<AccountEvent> deposit(BigDecimal amount) {
        if (amount.signum() <= 0) throw new IllegalArgumentException("amount > 0");
        return List.of(new MoneyDeposited(id, amount, Instant.now()));
    }

    // State transition — only ever called from event application. Pure.
    void apply(AccountEvent e) {
        switch (e) {
            case MoneyDeposited d  -> balance = balance.add(d.amount());
            case MoneyWithdrawn w  -> balance = balance.subtract(w.amount());
        }
        version++;
    }
}
```

The event store itself is just an append-only table keyed by aggregate id and monotonically increasing sequence number. The classic Postgres schema uses a composite `(aggregate_id, sequence_number)` primary key and a `data JSONB` column for the payload:

```sql
CREATE TABLE event_store (
    aggregate_id   UUID        NOT NULL,
    sequence_number BIGINT     NOT NULL,
    event_type      TEXT       NOT NULL,
    data            JSONB      NOT NULL,
    recorded_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (aggregate_id, sequence_number)
);
-- Appends are O(1) at the tail of the index; updates don't exist.
```

The production failure mode for this invariant is the silent backslide: a team adds a `UPDATE accounts SET balance = balance - ?` "shortcut" for some hot path (often a performance "fix" for rehydration latency), the projection row drifts from what replay would produce, and the next time you rebuild the projection from the log you get a *different balance* than the live system showed yesterday. The symptom is an unreproducible reconciliation gap: finance reports don't match the dashboard, customer complaints don't match the database. The defence is structural — never grant the application role `UPDATE` on the projection tables, force every write through the append-only API, and run a nightly reconciliation job that re-derives the projection from the log and asserts equality within a tolerance.

### State Rehydration: Reconstructing current aggregate state by replaying its historical event strea...

Rehydration is the inverse of emission. Given an aggregate id, the repository loads every event for that id ordered by `sequence_number` and feeds them one by one into a freshly constructed aggregate's `apply(Event)` method. After the last event is applied, the in-memory `Account` object holds the current state — derived, never fetched. This is the same mechanism as `git checkout` rebuilding a working tree by walking commits, or a Kafka Streams `KTable` rebuilding its state store by replaying the changelog topic from earliest offset.

The mechanical cost is linear in the number of events since the aggregate's birth. Rehydrating an account with three events costs microseconds; rehydrating a shopping cart that has accumulated 50 000 events over five years costs seconds. This is the central tension of event sourcing: the longer an aggregate lives, the more expensive it becomes to load. Some domains naturally cap this (a checkout session lives for minutes and has <50 events; a payment ledger entry is append-only forever but each entry is a separate aggregate), others do not (a bank account, a user profile, a long-lived subscription all grow without bound).

Here is the rehydration path. The repository loads events in batches and applies them; the `version` field is used for optimistic concurrency on the next write:

```java
final class AccountRepository {
    private final JdbcTemplate jdbc;
    private final JsonCodec codec;

    // Rehydrate by replaying every event from sequence 1 onward.
    Account load(UUID id) {
        var acc = new Account(id);
        jdbc.query(
            "SELECT sequence_number, event_type, data FROM event_store " +
            "WHERE aggregate_id = ? ORDER BY sequence_number",
            rs -> {
                AccountEvent e = codec.decode(rs.getString("event_type"), rs.getString("data"));
                acc.apply(e);   // same apply() used at emission time
            },
            id);
        if (acc.version() == 0) throw new AccountNotFoundException(id);
        return acc;
    }

    // Persist new events atomically, with optimistic-concurrency check.
    void save(Account acc, List<AccountEvent> newEvents) {
        long expectedVersion = acc.version() - newEvents.size();
        jdbc.execute("BEGIN");
        int updated = jdbc.update(
            "INSERT INTO event_store (aggregate_id, sequence_number, event_type, data) " +
            "VALUES (?, ?, ?, ?::jsonb) " +
            "-- guarded by SELECT ... FOR UPDATE on a separate aggregate_version row",
            acc.id(), expectedVersion + 1 /* … per event */, /* … */);
        // The optimistic-concurrency guard: no other writer may have appended
        // between our load and our save. Implemented as a version lock row.
        jdbc.execute("COMMIT");
    }
}
```

The flow looks like this:

```text
   load(id=42)
        │
        ▼
   SELECT * FROM event_store WHERE aggregate_id=42 ORDER BY sequence_number
        │
        ▼  (events 1..N stream back)
   acc = new Account(42)        ──►  balance = 0,   version = 0
   acc.apply(MoneyDeposited(100))  ► balance = 100, version = 1
   acc.apply(MoneyWithdrawn(30))   ► balance = 70,  version = 2
   acc.apply(MoneyDeposited(5))    ► balance = 75,  version = 3
        │
        ▼
   return acc   ── in-memory state derived, ready for the next command
```

The production failure mode here is the *long-lived aggregate*: a bank account that the business refuses to split, accumulating tens of thousands of events over years. Rehydration latency crosses 100 ms, then 500 ms, then seconds; the API tier times out; the load balancer retries; the optimistic-concurrency check fails; the customer sees a 500. The fix is snapshotting (next section) — but the discipline is to design aggregates with bounded lifetimes in the first place. A customer is not an aggregate; a customer's *subscription period* is an aggregate, and a new one starts each billing cycle. See [[09.05.01. Command Query Responsibility Segregation (CQRS)]] for how the read side avoids rehydrating aggregates at all.

### Performance optimization: Creating Snapshots at fixed intervals to accelerate aggregate rehydration

A snapshot is a materialised partial result of the replay: every N events (or every T seconds, or on every aggregate state change of a "heavy" type), you serialise the in-memory aggregate state and write it to a `snapshots` table keyed by `(aggregate_id, last_sequence_number)`. The next time you rehydrate, you load the most recent snapshot, deserialise it to seed the aggregate, and replay only the events with `sequence_number > snapshot.last_sequence_number`. Replaying 3 events instead of 30 000 turns a 2-second load into a 2-millisecond load.

The trade-off is that snapshots introduce a second copy of state that must remain consistent with the event log. The snapshot is *derived* — you can always throw it away and rebuild it from the log — but if you write it inconsistently (snapshot says balance 75 but events 1..2000 actually sum to 80), the next load returns wrong state silently. The standard defence is to write the snapshot *inside the same database transaction* as the event append, so the snapshot's `last_sequence_number` is always a real committed event boundary. Never write snapshots asynchronously from a separate worker that races with the writer — that is the classic source of the silent drift.

```sql
CREATE TABLE snapshots (
    aggregate_id   UUID        NOT NULL,
    last_sequence  BIGINT      NOT NULL,
    snapshot_type  TEXT        NOT NULL,
    data           JSONB       NOT NULL,
    taken_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (aggregate_id, last_sequence)
);

-- Snapshot taken every 100 events; load reads latest, then replays the tail.
SELECT last_sequence, data FROM snapshots
  WHERE aggregate_id = ?
  ORDER BY last_sequence DESC LIMIT 1;
-- then
SELECT * FROM event_store
  WHERE aggregate_id = ? AND sequence_number > ?
  ORDER BY sequence_number;
```

```text
                Without snapshots                    With snapshots (every 100)
                ─────────────────                    ───────────────────────────
   load(42)  ──► replay 8 000 events                load(42) ──► load snapshot@7900
                ~1.6 s on a warm cache                          ~3 ms (one row fetch)
                ~6 s cold (page faults)              then replay 100 events (~25 ms)
                                                        total ~30 ms  (≈ 50× speedup)
```

The strategy for choosing N is a measured trade-off. Too small (every 5 events) and the snapshot table grows almost as fast as the event store and you've added a second write to every transaction. Too large (every 100 000 events) and the tail you have to replay is still long enough to matter. The pragmatic number for a typical CRUD-shaped aggregate is 100–500 events, chosen so the tail replay stays under 50 ms p99. For state-machine aggregates with rare but expensive transitions (e.g. an order with a long lineage of pricing adjustments), prefer time-based snapshots (every 24 h) so an idle aggregate never accrues an unbounded tail.

The production failure mode is the snapshot schema migration. You change the `Account` class to add an `overdraftLimit` field; the new code reads a snapshot serialised by the old code that has no `overdraftLimit` key; deserialisation fills in `null` or `0`; the aggregate now thinks overdrafts are forbidden; the customer's next legitimate transaction fails. The fix is either to invalidate all snapshots on schema change (delete from `snapshots where snapshot_type = 'Account-v1'` and accept one round of slow rehydrations) or to write a snapshot migrator that re-derives snapshots from the event log offline. Never let the deserialiser silently default missing fields — fail loudly, or version the snapshot type tag and refuse to load mismatched versions.

### Projections: Asynchronously projecting event streams into specialized read databases for query co...

A projection is a denormalised read model built by subscribing to the event stream and applying each event to update a query-optimised table. Where the event store is shaped for writes (append-only, one row per event), the projection is shaped for reads: a `customer_balances` table with one row per customer, an `accounts_by_holder` index, a materialised view of "top 10 customers by transaction count this month", a search index in Elasticsearch, a graph of relationships in Neo4j. Each projection consumes the same event log and presents it through a different lens; one log, N read models.

Projections are how event sourcing and CQRS compose. The write side commits events to the log; the read side runs projections that turn those events into whatever shape the query needs. Because the projections are derived, they can be dropped and rebuilt at any time — and because they are asynchronous, the write side never blocks on a slow query. The trade-off is eventual consistency between write and read: the moment a `MoneyDeposited` event is committed, the projection that updates `customer_balances` may lag by milliseconds (in-process synchronous projection) or by seconds (Kafka consumer lag). UI code has to handle "I just deposited but the balance doesn't show it yet" — usually with a write-token / read-your-own-writes hop on the write-side aggregate.

```java
// A projection: consumes events and updates a read-optimised table.
@Component
final class CustomerBalanceProjection {
    private final JdbcTemplate jdbc;

    @EventListener
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void on(MoneyDeposited e) {
        jdbc.update(
            "INSERT INTO customer_balances (account_id, balance, updated_at) " +
            "VALUES (?, ?, now()) " +
            "ON CONFLICT (account_id) DO UPDATE SET balance = customer_balances.balance + ?, updated_at = now()",
            e.accountId(), e.amount(), e.amount());
    }

    @EventListener
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void on(MoneyWithdrawn e) {
        int n = jdbc.update(
            "UPDATE customer_balances SET balance = balance - ?, updated_at = now() WHERE account_id = ?",
            e.amount(), e.accountId());
        if (n == 0) throw new ProjectionGapException(e);  // balance row missing — replay from log
    }
}
```

```text
                ┌────────────┐
                │ event_store│  (source of truth, append-only)
                └─────┬──────┘
                      │ subscribe
        ┌─────────────┼──────────────┬──────────────┐
        ▼             ▼              ▼              ▼
   customer_       daily_         fraud_         search_
   balances        summary        detector       index
   (Postgres)      (Postgres)     (Flink)        (Elasticsearch)
   read path A     read path B    analytics      full-text + filters
```

The temporal query is the other half of the projection story. Because the event log is a total order, you can project to *any point in time* by replaying only events with `recorded_at <= T`. "What was this customer's balance at the close of last quarter?" is a single SQL query against a projection rebuilt to that timestamp, or — for ad-hoc investigation — a one-off replay in a notebook:

```java
// Temporal query: state as of a past instant. Replays the prefix of the log up to T.
Account loadAsOf(UUID id, Instant when) {
    var acc = new Account(id);
    jdbc.query(
        "SELECT event_type, data FROM event_store " +
        "WHERE aggregate_id = ? AND recorded_at <= ? ORDER BY sequence_number",
        rs -> acc.apply(codec.decode(rs.getString("event_type"), rs.getString("data"))),
        id, when);
    return acc;
}
```

The production failure mode is projection drift — the projection says one thing, the event log says another, and nobody notices because the reconciliation job was never written. The drift can come from a missed event (the projection consumer crashed mid-batch and the offset wasn't committed, so the next restart skipped events), from a non-idempotent handler (the same event applied twice doubled a balance), or from a schema migration that touched the projection table but not the event handler. The defence is a periodic reconciliation: for a sample of aggregates (or for all of them, nightly), recompute the projection from the log and assert it matches the live projection within a tolerance. The metric to watch is `projection_lag_seconds` — the gap between the most recent event in the log and the most recent event the projection has processed — and the alert threshold is "any lag greater than your UI can paper over," typically 5–30 seconds for a synchronous UI projection, minutes for an analytics projection.

## Cross-Ecosystem Code

The mechanics are universal; the libraries differ. Spring Boot has Axon Framework (which provides `EventStore`, `AggregateLifecycle.apply()`, `@EventHandler` projections); Express has `event-store-js` and a hand-rolled pattern; Django has `django-eventstream` and the same hand-rolled pattern; Laravel has the `spatie/laravel-event-sourcing` package. The shape is identical: an aggregate that emits, a store that appends, a rehydration loop, and a projection subscriber.

```java
// Spring Boot with Axon — the @AggregateIdentifier and @EventHandler are Axon's hooks.
@Aggregate
class Account {
    @AggregateIdentifier private UUID id;
    private BigDecimal balance = BigDecimal.ZERO;

    @CommandHandler
    public Account(OpenAccountCommand cmd) {
        AggregateLifecycle.apply(new AccountOpened(cmd.accountId(), cmd.initialDeposit()));
    }
    @CommandHandler
    public void handle(WithdrawCommand cmd) {
        if (cmd.amount().compareTo(balance) > 0) throw new InsufficientFundsException();
        AggregateLifecycle.apply(new MoneyWithdrawn(id, cmd.amount(), Instant.now()));
    }
    @EventSourcingHandler public void on(MoneyDeposited e)  { balance = balance.add(e.amount()); }
    @EventSourcingHandler public void on(MoneyWithdrawn e)  { balance = balance.subtract(e.amount()); }
}
```

```typescript
// Express / TypeScript — hand-rolled, no framework. The same four primitives.
interface AccountEvent { type: string; aggregateId: string; sequence: number; data: any; at: string; }
class Account {
  private balance = 0;
  constructor(private readonly id: string, events: AccountEvent[]) { events.forEach(e => this.apply(e)); }
  private apply(e: AccountEvent) {
    if (e.type === 'MoneyDeposited')  this.balance += e.data.amount;
    if (e.type === 'MoneyWithdrawn')  this.balance -= e.data.amount;
  }
  withdraw(amount: number): AccountEvent[] {
    if (amount > this.balance) throw new Error('insufficient funds');
    return [{ type: 'MoneyWithdrawn', aggregateId: this.id, sequence: -1, data: { amount }, at: new Date().toISOString() }];
  }
}
```

```python
# Django — store events in a model, replay in a manager method.
class AccountEvent(models.Model):
    aggregate_id = models.UUIDField(db_index=True)
    sequence = models.BigIntegerField()
    event_type = models.TextField()
    data = models.JSONField()
    recorded_at = models.DateTimeField(auto_now_add=True)
    class Meta: unique_together = (('aggregate_id', 'sequence'),)

class Account:
    def __init__(self, id_: uuid.UUID, events: list['AccountEvent']):
        self.id, self.balance = id_, Decimal('0')
        for e in events: self._apply(e)
    def _apply(self, e: 'AccountEvent'):
        if e.event_type == 'MoneyDeposited':  self.balance += Decimal(e.data['amount'])
        if e.event_type == 'MoneyWithdrawn':  self.balance -= Decimal(e.data['amount'])
```

```php
// Laravel with spatie/laravel-event-sourcing — the framework provides the projection glue.
#[AutoAggregate]
class AccountAggregate
{
    protected string $aggregateUuid;
    protected int $balance = 0;

    #[CommandHandler]
    public function withdraw(int $amount): void
    {
        if ($amount > $this->balance) throw new InsufficientFundsException();
        $this->recordThat(new MoneyWithdrawn($amount));
    }
    #[Apply]
    public function onMoneyWithdrawn(MoneyWithdrawn $event): void { $this->balance -= $event->amount; }
}
```

## How This Connects to the Frameworks

Spring Boot's `ApplicationEventPublisher` is an in-process event bus, not an event store — it loses events on crash and does not survive restart. To do real event sourcing in Spring, you need either Axon Framework (which wires `EventStorageEngine` to Postgres or MongoDB and provides `@CommandHandler` / `@EventSourcingHandler` / `@EventHandler` separations) or a hand-rolled equivalent with a `JdbcTemplate` and a `TransactionalEventListener`. The mistake to avoid is conflating domain events (transient notifications, fine for `ApplicationEventPublisher`) with the persisted event log (the source of truth, must be in a transactional store).

In Express, Django, and Laravel the pattern is almost always hand-rolled because the ecosystems don't have a dominant event-sourcing library; you write a `events` table, an aggregate base class with `apply()` and `recordThat()`, and a projection subscriber that runs in a transaction after the event commit. The discipline of putting the append inside the same transaction as the optimistic-concurrency check is the part everyone gets wrong the first time — without it, two concurrent withdrawals both pass the balance check and both append, leaving the aggregate in a negative state.

## How This Connects to the Runtimes

Event sourcing sits above the persistence layer (it needs a transactional, durable, append-only log — typically Postgres, EventStoreDB, or Kafka with `acks=all` and `min.insync.replicas=2`). The JVM GC pressure from rehydrating many aggregates is non-trivial: each event is a small short-lived object, and rehydrating 10 000 aggregates per second creates ~1 GB/s of allocation. The mitigations are batched JDBC fetches (one `ResultSet` cursor, not 10 000 queries), reusable `Account` instances pooled per thread, and projection workers that process events in batches rather than one at a time. On Node, Python, and PHP runtimes the same concerns apply with different magnitudes (Python's per-object overhead is higher, PHP-FPM workers can't share projection state in memory so they must use a queue).

## Cross-Runtime Comparison

| Concern | JVM (Spring/Axon) | Node (Express) | Python (Django) | PHP (Laravel) |
|---|---|---|---|---|
| Default event store | Postgres / Axon `JpaEventStorageEngine` | Postgres / EventStoreDB via TCP client | Postgres (custom model) | Postgres / MySQL (Spatie package) |
| Rehydration cost | Low — JIT-warmed `apply()` ~1 µs/event | Medium — V8 is fast but JSON.parse per event ~3 µs | High — interpreter overhead ~8 µs/event | High — per-request model load, no in-process cache |
| Projection model | `@EventHandler` beans, in-process or via Axon Server | Worker pool subscribing to a `LISTEN/NOTIFY` channel | Celery / `signals.py` post-commit hook | Spatie's `Projector` + queue worker |
| Optimistic concurrency | Axon `@AggregateVersion` annotation | Manual `SELECT ... FOR UPDATE` on a version row | `select_for_update()` in a transaction | `DB::transaction` + lock-for-update row |
| Snapshotting | Axon `@AggregateSnapshotter` | Manual: separate `snapshots` table | Manual: `Snapshot` model + manager | Spatie `Snapshot` model |

## Hands-On Exercise

Spin up a Postgres container and walk through the full cycle:

```bash
docker run -d --name es-pg -e POSTGRES_PASSWORD=secret -p 5432:5432 postgres:16
docker exec -it es-pg psql -U postgres -c "$(cat <<'SQL'
CREATE TABLE event_store (
  aggregate_id UUID NOT NULL, sequence_number BIGINT NOT NULL,
  event_type TEXT NOT NULL, data JSONB NOT NULL,
  recorded_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (aggregate_id, sequence_number));
CREATE TABLE snapshots (
  aggregate_id UUID NOT NULL, last_sequence BIGINT NOT NULL,
  snapshot_type TEXT NOT NULL, data JSONB NOT NULL,
  taken_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (aggregate_id, last_sequence));
SQL
)"

# Append three events to aggregate 42
docker exec es-pg psql -U postgres -c "INSERT INTO event_store VALUES
  ('00000000-0000-0000-0000-000000000042', 1, 'MoneyDeposited',  '{\"amount\": 100}'),
  ('00000000-0000-0000-0000-000000000042', 2, 'MoneyWithdrawn', '{\"amount\": 30}'),
  ('00000000-0000-0000-0000-000000000042', 3, 'MoneyDeposited',  '{\"amount\": 5}');"

# Rehydrate: replay the events, summing amounts by event type
docker exec es-pg psql -U postgres -c "
  SELECT
    SUM(CASE WHEN event_type='MoneyDeposited'  THEN  (data->>'amount')::numeric ELSE 0 END) -
    SUM(CASE WHEN event_type='MoneyWithdrawn' THEN  (data->>'amount')::numeric ELSE 0 END) AS balance
  FROM event_store WHERE aggregate_id = '00000000-0000-0000-0000-000000000042';"
# Expected: 75

# Take a snapshot at sequence 3
docker exec es-pg psql -U postgres -c "INSERT INTO snapshots VALUES
  ('00000000-0000-0000-0000-000000000042', 3, 'Account-v1', '{\"balance\": 75}');"

# Append a 4th event; rehydrate from snapshot + tail
docker exec es-pg psql -U postgres -c "INSERT INTO event_store VALUES
  ('00000000-0000-0000-0000-000000000042', 4, 'MoneyWithdrawn', '{\"amount\": 20}');"
docker exec es-pg psql -U postgres -c "
  WITH snap AS (
    SELECT (data->>'balance')::numeric AS balance, last_sequence
    FROM snapshots WHERE aggregate_id='00000000-0000-0000-0000-000000000042'
    ORDER BY last_sequence DESC LIMIT 1)
  SELECT
    snap.balance +
    COALESCE(SUM(CASE WHEN event_type='MoneyDeposited'  THEN  (data->>'amount')::numeric ELSE 0 END), 0) -
    COALESCE(SUM(CASE WHEN event_type='MoneyWithdrawn' THEN  (data->>'amount')::numeric ELSE 0 END), 0) AS balance
  FROM snap LEFT JOIN event_store e
    ON e.aggregate_id='00000000-0000-0000-0000-000000000042' AND e.sequence_number > snap.last_sequence
  GROUP BY snap.balance;"
# Expected: 55
```

Try the production failure: delete the snapshot row, change the schema by adding a column to `data`, and observe what happens when you rehydrate an aggregate whose old events lack the new field.
