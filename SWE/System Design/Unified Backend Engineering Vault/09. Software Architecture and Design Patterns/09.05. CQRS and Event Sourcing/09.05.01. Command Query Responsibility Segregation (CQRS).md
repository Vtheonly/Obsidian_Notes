# 09.05.01. Command Query Responsibility Segregation (CQRS)

## What This Is

Command Query Responsibility Segregation (CQRS) — coined by Greg Young around 2010, building on Bertrand Meyer's Command-Query Separation principle from 1988 — is the architectural pattern of splitting the write model (commands: state-modifying operations that enforce business rules and strong consistency) from the read model (queries: optimized projections that return data without mutating state). In a traditional CRUD service, one `Order` entity serves both writes (validate, save) and reads (serialize for the API). In a CQRS service, the write side has `Order` aggregates and `PlaceOrderCommandHandler`; the read side has `OrderSummaryView` rows and `GetOrderHistoryQueryHandler`. The two models are different shapes, often in different databases, kept in sync by events emitted from the write side and projected into the read side.

In the vault's layered mental model, CQRS sits at the application layer of Clean/Hexagonal Architecture (see [[09.03.01. The Hexagonal (Ports and Adapters) Architecture]] and [[09.03.02. Clean Architecture and Onion Architecture Mapping]]). The write side is a hexagonal application with aggregates, repositories, and a command handler per use case. The read side is a thin query layer that reads from a denormalized view or a search index — it has no aggregates, no invariants, no business rules, just SQL or Elasticsearch queries. The two sides communicate via domain events: the write side emits `OrderPlaced` after a successful write; a projector consumes the event and updates the read model. This is the architectural seam that Event Sourcing builds on (see [[09.05.02. Event Sourcing Mechanics]]).

CQRS governs two failure modes: (1) the "fake CQRS" — a project that has separate `CommandHandler` and `QueryHandler` classes but both hit the same database table, so the architectural complexity is paid but the read-scaling benefit is not; and (2) the "stale read window" — a project with a real dual-database CQRS where the projector falls behind during a write spike, the read model is now 30 seconds stale, and the user submits an order and immediately sees the old order list (without their new order), concludes the order failed, and submits again — a duplicate-write incident. Both failure modes are addressed below.

## The Details

### Separation of Concerns: Splitting the write model (Commands: state-modifying operations enforcing...

The core observation of CQRS is that read workloads and write workloads have different shapes and benefit from different optimizations. A write to `POST /api/orders` must validate the customer exists, validate the products are in stock, check the customer's credit limit, compute the total, enforce the aggregate's invariants, persist atomically, and emit events. The write model is normalized (one row per order, one per line, one per customer) for consistency. A read from `GET /api/orders?customer=42&status=shipped&page=3` must join `orders`, `order_lines`, `products`, `customers`, paginate, sort, and serialize — five joins, one pagination, one sort. The read model would be much faster if it were a single denormalized table (`order_summaries` with `customer_name`, `total`, `line_count`, `status` as columns), queried without joins. Forcing one model to serve both forces compromises on both.

The CQRS split is structural. The write side has command classes (`PlaceOrderCommand`), command handlers (`PlaceOrderCommandHandler`), aggregates (`Order`), and repositories (`OrderRepository`). It accepts commands, enforces business rules, mutates state, emits events. The read side has query classes (`GetOrderHistoryQuery`), query handlers (`GetOrderHistoryQueryHandler`), and view repositories (`OrderSummaryViewRepository`). It accepts queries, returns DTOs, never mutates state, never enforces business rules. The two sides have no shared classes except the event types that flow from write to read.

A Spring Boot implementation, showing the command and query handlers side by side:

```java
// write side: application/usecase/PlaceOrderCommandHandler.java
package com.shop.write.usecase;

import com.shop.write.command.PlaceOrderCommand;
import com.shop.write.command.PlaceOrderResult;
import com.shop.write.port.in.PlaceOrderUseCase;
import com.shop.write.port.out.LoadCustomerPort;
import com.shop.write.port.out.SaveOrderPort;
import com.shop.write.port.out.PublishEventPort;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
@Transactional
public class PlaceOrderCommandHandler implements PlaceOrderUseCase {
    private final LoadCustomerPort loadCustomer;
    private final SaveOrderPort saveOrder;
    private final PublishEventPort publishEvent;

    public PlaceOrderCommandHandler(LoadCustomerPort loadCustomer,
                                    SaveOrderPort saveOrder,
                                    PublishEventPort publishEvent) {
        this.loadCustomer = loadCustomer;
        this.saveOrder = saveOrder;
        this.publishEvent = publishEvent;
    }

    @Override
    public PlaceOrderResult handle(PlaceOrderCommand cmd) {
        var customer = loadCustomer.load(cmd.customerId())
            .orElseThrow(() -> new CustomerNotFoundException(cmd.customerId()));
        var order = customer.placeOrder(cmd.items(), cmd.shippingAddress());
        saveOrder.save(order);
        order.pullEvents().forEach(publishEvent::publish);   // emit OrderPlaced
        return new PlaceOrderResult(order.id(), order.total());
    }
}

// read side: read/query/GetOrderHistoryQueryHandler.java
package com.shop.read.query;

import com.shop.read.view.OrderSummaryView;
import com.shop.read.view.OrderSummaryViewRepository;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
@Transactional(readOnly = true)
public class GetOrderHistoryQueryHandler implements GetOrderHistoryQuery {
    private final OrderSummaryViewRepository views;

    public GetOrderHistoryQueryHandler(OrderSummaryViewRepository views) {
        this.views = views;
    }

    @Override
    public Page<OrderSummaryView> handle(GetOrderHistoryQueryRequest req) {
        // One query, zero joins, denormalized. Returns in ~2ms on 10M rows
        // if order_summaries is indexed on (customer_id, status, placed_at).
        return views.findByCustomerIdAndStatusAndPlacedAtBetween(
            req.customerId(),
            req.status(),
            req.fromDate(),
            req.toDate(),
            PageRequest.of(req.page(), req.size(), Sort.by("placedAt").descending()));
    }
}
```

Note the asymmetry: the command handler is `@Transactional` (read-write), loads the aggregate, enforces invariants, emits events. The query handler is `@Transactional(readOnly = true)`, loads view rows directly, has no aggregate, has no invariants, has no events. The two classes share no state, no repository, no entity — they share only the event types that flow from the command side through the projector to the view table. The command side owns the business rules; the query side owns the read performance.

The production failure mode of the "read-side leak": a developer, under deadline pressure, needs to return the customer's name in the order summary, and the projector hasn't been updated to populate `customer_name` on `order_summaries`. The developer writes a query that joins `order_summaries` to `customers` to fetch the name — and the read side now has a JOIN, the read performance degrades from 2ms to 12ms, and the architectural benefit of CQRS is silently eroded. The fix is discipline: the read side never joins to the write side's tables. If the read model is missing a field, the projector is updated to populate it (replaying historical events if necessary), and the join stays out of the query path.

### Synchronous Single-Database CQRS vs. Asynchronous Dual-Database CQRS (Relational Write Store → El...

CQRS comes in two flavors with very different cost/benefit profiles. **Synchronous single-database CQRS** keeps the write model and the read model in the same database (typically Postgres); the write side writes to normalized tables (`orders`, `order_lines`), and the read side reads from denormalized views (`order_summaries` — a materialized view or a table maintained by triggers). The two models are kept in sync synchronously, inside the same transaction, so there is no eventual consistency window. The benefit is architectural clarity (separate command and query code paths, separate handlers, separate optimization opportunities) at low operational cost. The cost is that you cannot scale reads independently of writes — both share the same database CPU and IOPS budget.

**Asynchronous dual-database CQRS** puts the write model in one datastore (Postgres for transactions) and the read model in a different datastore (Elasticsearch for full-text search, Redis for low-latency lookup, a ClickHouse column store for analytics, a denormalized Postgres table for paginated reads). The write side writes to Postgres and emits an event (to Kafka, to RabbitMQ, to Postgres LISTEN/NOTIFY). A projector consumes the event and updates the read store. The two stores are kept in sync asynchronously, with a lag of typically 10ms–1s (event publication + projection). The benefit is read-scaling (the read store can be replicated, sharded, denormalized independently of the write store) and read-optimization (Elasticsearch for full-text, Redis for sub-millisecond lookups, ClickHouse for analytics aggregations). The cost is operational complexity (two datastores, an event bus, a projector that must be idempotent and replayable) and eventual consistency (the read store lags).

The dual-database projector is the load-bearing component. It consumes events from the bus and updates the read store. It must be **idempotent** — the same event delivered twice (Kafka's at-least-once) must produce the same read-store state as delivery once. The standard pattern is to use the event ID as a unique key in the read store's idempotency table: `INSERT INTO processed_events (event_id) VALUES (?) ON CONFLICT DO NOTHING` — if the insert returns 0 rows affected, the event was already processed, skip the projection. It must be **replayable** — if the read store is corrupted, you must be able to rebuild it by replaying all events from the beginning. This means the projector cannot have side effects other than updating the read store, and the projection logic must be deterministic (no `now()`, no `random()`, no external API calls). It must be **order-preserving** within an aggregate — events for the same aggregate must be processed in the order they were emitted, or the read store will be inconsistent. Kafka's per-partition ordering handles this if the producer uses `orderId` as the partition key.

```java
// read side projector: read/projector/OrderProjector.java
package com.shop.read.projector;

import com.shop.read.view.OrderSummaryView;
import com.shop.read.view.OrderSummaryViewRepository;
import com.shop.read.view.ProcessedEventRepository;
import org.springframework.kafka.annotation.KafkaListener;
import org.springframework.stereotype.Component;
import org.springframework.transaction.annotation.Transactional;

@Component
public class OrderProjector {
    private final OrderSummaryViewRepository views;
    private final ProcessedEventRepository processedEvents;

    public OrderProjector(OrderSummaryViewRepository views,
                          ProcessedEventRepository processedEvents) {
        this.views = views;
        this.processedEvents = processedEvents;
    }

    @KafkaListener(topics = "order-events", groupId = "order-read-model")
    @Transactional
    public void on(OrderPlaced event) {
        // Idempotency: skip if event already processed.
        if (!processedEvents.markProcessed(event.eventId())) {
            return;
        }
        views.save(new OrderSummaryView(
            event.orderId(),
            event.customerId(),
            event.total(),
            event.currency(),
            "PLACED",
            event.occurredAt(),
            event.lineItems().size()));
    }

    @KafkaListener(topics = "order-events", groupId = "order-read-model")
    @Transactional
    public void on(OrderCancelled event) {
        if (!processedEvents.markProcessed(event.eventId())) {
            return;
        }
        views.findById(event.orderId()).ifPresent(view -> {
            view.setStatus("CANCELLED");
            views.save(view);
        });
    }
}
```

The production failure mode is the "stale read window." The user submits an order (POST returns 200, the write store has the order, the event is on Kafka). The user immediately navigates to the order list (GET /api/orders) — and the order is not there, because the projector hasn't consumed the event yet. The user concludes the order failed and submits again — a duplicate order, a double charge, a customer support ticket. Three mitigations exist, in order of escalating complexity: (1) **accept eventual consistency in the UI** — after a successful POST, show a "your order is being processed" page; poll the GET endpoint after 1–2 seconds; (2) **read-your-writes via session affinity** — for N seconds after a write, route the user's reads to the write store (which has the data), then switch to the read store; (3) **version-token synchronization** — the write returns a `writeVersion` token; the GET endpoint passes the token to the read store, which blocks until its `appliedVersion >= writeVersion` (this is the "read-your-writes consistency" pattern used by DynamoDB Global Tables and CockroachDB). The choice depends on the user experience budget: option 1 is cheap and usually sufficient; option 3 is expensive and rarely justified outside financial trading.

A second failure mode is the "projector crash without recovery." The projector crashes mid-update — the event was consumed (Kafka offset advanced) but the read store was not updated. The read store is now missing rows, and there is no automatic reconciliation. The fix is twofold: (a) the projector commits the Kafka offset only after the read store transaction commits (so a crash mid-update leaves the offset uncommitted, and the event is redelivered); (b) a reconciliation job runs nightly, comparing write-store counts to read-store counts and replaying any missing events. The reconciliation is the safety net — the projector's idempotency guarantee makes replay safe, so the reconciliation can re-process large event ranges without fear of duplicates.
