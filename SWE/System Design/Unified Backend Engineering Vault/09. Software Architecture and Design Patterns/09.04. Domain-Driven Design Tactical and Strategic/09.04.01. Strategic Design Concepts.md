# 09.04.01. Strategic Design Concepts

## What This Is

Strategic Domain-Driven Design — the top half of Eric Evans' 2003 book — is the discipline of partitioning a large business domain into coherent, independently modelable pieces, and then governing the relationships between those pieces. Where tactical DDD (entities, value objects, aggregates — see [[09.04.02. Tactical Domain Building Blocks]]) operates at the scale of a single class, strategic DDD operates at the scale of a whole organization: which teams own which models, which models share which data, which models are downstream of which others. The three strategic tools are **Ubiquitous Language** (a single, rigorous vocabulary shared between developers and domain experts inside one boundary), **Bounded Contexts** (the boundaries themselves), and **Context Mapping** (the catalog of relationship patterns between contexts — Shared Kernel, Customer-Supplier, Anticorruption Layer, Open Host Service, and so on).

In the vault's layered mental model, strategic DDD sits above the application framework layer and below the organizational layer. A bounded context maps to a deployable unit (a service, a module, or a Maven submodule); the context map maps to the API contracts and integration patterns between those units. The Anticorruption Layer pattern, in particular, is the strategic counterpart of the hexagonal adapter from [[09.03.01. The Hexagonal (Ports and Adapters) Architecture]] — an ACL is a driven adapter that translates a foreign bounded context's model into your own, so your domain never sees the foreign model's quirks.

This note governs two failure modes: (1) the "one big model" — a single Product entity shared by Catalog, Inventory, and Shipping, where a schema change in one team's context breaks the other two teams' builds; and (2) the "translator impedance" — a business analyst who translates between developers and domain experts, silently substituting technical terms for business terms, so the code's vocabulary drifts from the business's vocabulary and the next developer has to relearn the domain from scratch.

## The Details

### Ubiquitous Language: Defining a rigorous, unambiguous shared domain vocabulary across software en...

Ubiquitous Language is the practice of building a single, rigorous, unambiguous vocabulary that is shared — verbatim, not translated — between domain experts and software engineers, and that surfaces identically in conversation, in code, in tests, and in documentation. If the domain expert says "fulfillment request," the code has a `FulfillmentRequest` class, the test method is `should_reject_fulfillment_request_when_out_of_stock`, the database table is `fulfillment_requests`, the API endpoint is `POST /fulfillment-requests`, and the Jira ticket type is "Fulfillment Request." If the developer hears "fulfillment request" and writes `OrderProcessor`, the translation gap is the place where bugs are born.

The construction of a ubiquitous language is a deliberate act. It begins with developers sitting with domain experts — on warehouse floors, in call centers, in the trading room — and recording the actual words the experts use to describe their work. The team builds a glossary: every noun becomes a candidate for a class or value object, every verb becomes a candidate for a method, every business phrase becomes a candidate for a domain event. Disagreements are not smoothed over — they are surfaced and resolved. If the warehouse manager says "pick list" and the customer service rep says "fulfillment request" for the same artifact, the team must decide which term is canonical (or whether they are actually two different artifacts that the business has conflated). The resolution goes into the glossary, and the glossary becomes the contract.

The translator role is the silent killer of ubiquitous language. A business analyst who sits between developers and domain experts will, under deadline pressure, paraphrase the expert's words into "developer-friendly" language: "the customer clicks submit" becomes "the client POSTs to /orders"; "the warehouse picks the items" becomes "the system updates the inventory." The developer never hears the expert's actual words, and the code's vocabulary drifts. The DDD prescription is to abolish the translator role: developers must speak to domain experts directly, even if the first ten conversations are uncomfortable. The alternative — letting the translator paraphrase — guarantees that the code's vocabulary diverges from the business's vocabulary within six months, and that every future change request requires a translation step.

```java
// Bad — the developer's word for the concept:
class OrderProcessor {
    void processOrder(OrderData data) { /* ... */ }
}

// Good — the domain expert's word for the concept:
class FulfillmentRequest {
    // a request to fulfill a customer's order from a specific warehouse
    void approve(WarehouseId warehouse) { /* ... */ }
    void reject(RejectionReason reason) { /* ... */ }
}

// The test reads like a business rule:
@Test
void should_reject_fulfillment_request_when_warehouse_out_of_stock() {
    var request = new FulfillmentRequest(customerOrder, items);
    var warehouse = warehouseWithNoStockFor(items);
    assertThatThrownBy(() -> request.approve(warehouse.id()))
        .isInstanceOf(OutOfStockException.class)
        .hasMessageContaining(items.first().sku());
}
```

The production failure mode is the "shadow language": the business calls a concept "fulfillment request," the code calls it `OrderProcessor`, and over twelve months the team develops a private mental mapping ("when the business says fulfillment request, they mean the OrderProcessor class with state=PENDING"). New hires take three months to learn the mapping. Bugs emerge from the gap: a support ticket says "fulfillment request 1234 failed," the developer searches the codebase for `FulfillmentRequest`, finds nothing, and wastes an hour. Worse, when two teams with different shadow languages integrate, every API contract becomes a translation exercise. The fix is to drive the code's vocabulary from the business's vocabulary, relentlessly, and to treat any divergence as a defect — a code review comment, not a stylistic preference.

### Bounded Contexts: Explicit boundaries within which a domain model applies; mapping Context Maps (...

A Bounded Context is an explicit boundary within which a single ubiquitous language and a single domain model are consistent. The boundary is the place where the meaning of every term is fixed: inside the Catalog context, "Product" means {sku, name, description, price, category}; inside the Inventory context, "Product" means {sku, stockLevel, warehouseLocation, reorderPoint}; inside the Shipping context, "Product" means {sku, weight, dimensions, hazmatCode}. The same word means different things in different contexts, and that is correct — forcing a single unified Product entity across all three contexts produces a "god object" with 40 fields, only 8 of which any one context cares about. The bounded context lets each team model its own slice of the world without compromise.

The boundary is enforced technically. In a monolith, it can be a Maven submodule or a package with an ArchUnit rule preventing cross-imports (`noClasses().that().resideInAPackage("..catalog..").should().dependOnClassesThat().resideInAPackage("..inventory..")`). In a distributed system, it is a separate deployable service with its own database — the canonical "database-per-service" pattern. The boundary is also enforced organizationally: a bounded context is owned by exactly one team (Conway's Law — the architecture will mirror the communication structure of the organization). Two teams sharing a bounded context will, over time, diverge in their understanding of the ubiquitous language, and the context will fracture.

The Context Map is the catalog of relationships between bounded contexts. Eric Evans defined nine patterns, each naming a specific kind of relationship:

The Anticorruption Layer is the most important pattern in practice. It is a driven adapter (in Hexagonal terms) that translates a foreign bounded context's model into your own. Suppose the legacy ERP exposes `MATERIAL_MASTER` with 200 columns; your Inventory context only needs `sku`, `stockLevel`, `warehouseLocation`. The ACL is a `MaterialMasterTranslator` that calls the ERP, parses the response, and returns a `Product` value object in your Inventory model. The Inventory domain never sees the 200-column structure, never sees the ERP's quirky status codes, never knows the ERP exists. If the ERP is replaced next year, only the ACL changes; the Inventory domain is untouched.

```java
// inventory/adapter/erp/MaterialMasterAcl.java  — the Anticorruption Layer
package com.shop.inventory.adapter.erp;

import com.shop.inventory.domain.Product;
import com.shop.inventory.domain.ProductSku;
import com.shop.inventory.port.out.LoadProductFromErpPort;

class MaterialMasterAcl implements LoadProductFromErpPort {
    private final ErpClient erp;

    @Override
    public Optional<Product> load(ProductSku sku) {
        return Optional.ofNullable(erp.fetchMaterialMaster(sku.value()))
                       .map(this::translate);
    }

    private Product translate(MaterialMasterDto dto) {
        // Translate the ERP's 200-column DTO into our 3-field domain Product.
        // ERP status code "AV" / "DC" / "OB" → our StockStatus enum.
        var status = switch (dto.getMaterialStatusCode()) {
            case "AV" -> StockStatus.AVAILABLE;
            case "DC" -> StockStatus.DISCONTINUED;
            case "OB" -> StockStatus.OBSOLETE;
            default   -> throw new IllegalStateException(
                "Unknown ERP status: " + dto.getMaterialStatusCode());
        };
        return new Product(
            new ProductSku(dto.getMaterialNumber()),
            dto.getAvailableStock(),
            status);
    }
}
```

The production failure mode is the "shared Product entity" — a single `products` table with 40 columns owned by no team in particular, where Catalog adds a `description` column, Inventory adds a `reorder_point` column, Shipping adds a `hazmat_code` column, and a year later the table has 80 columns, no team knows what half of them mean, and any schema change requires a coordination meeting of three teams. This is the canonical monolith-to-microservices migration failure: the team splits the deployable but leaves the shared database, and the bounded contexts collapse back into one because every team still reads and writes the same table. The fix is the database-per-service rule (each bounded context owns its own schema; cross-context access goes through an API, not a shared table) plus the Anticorruption Layer pattern for any legacy integration. The transition is painful — it requires an ETL job to split the shared table into per-context schemas — but the alternative is the slow heat-death of the god object.
