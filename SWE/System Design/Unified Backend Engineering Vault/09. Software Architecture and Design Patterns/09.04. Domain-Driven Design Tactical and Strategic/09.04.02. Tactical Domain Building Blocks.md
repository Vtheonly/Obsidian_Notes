# 09.04.02. Tactical Domain Building Blocks

## What This Is

Tactical Domain-Driven Design is the lower half of Eric Evans' 2003 book — the building blocks you use to model the inside of a single bounded context (see [[09.04.01. Strategic Design Concepts]] for the boundary itself). The blocks are: **Value Object** (immutable, no identity, defined by attributes), **Entity** (mutable, has identity, persists across state changes), **Aggregate** (a cluster of entities and value objects treated as a single consistency boundary, with one **Aggregate Root** as the only entry point), **Domain Event** (an immutable record of something that happened), **Domain Service** (a stateless operation that does not fit on an entity), **Repository** (a collection-like interface for loading and saving aggregates), and **Factory** (an object or method that constructs aggregates in valid initial state). Each block has a specific responsibility; misplacing logic across them is the most common DDD failure mode.

In the layered mental model of this vault, tactical DDD lives inside the domain circle of Clean Architecture (see [[09.03.02. Clean Architecture and Onion Architecture Mapping]]) and inside the hexagonal core (see [[09.03.01. The Hexagonal (Ports and Adapters) Architecture]]). Aggregates, entities, value objects, domain events, and domain services are pure Java/TypeScript/Python with no framework imports; repositories are interfaces declared in the domain and implemented in the infrastructure layer. The boundary between tactical DDD and the rest of the application is the same as the boundary between the domain and application layers in Clean/Hexagonal.

This note governs the recurring failure mode of "anemic domain model" — a project where the entities are bags of getters and setters, all business logic lives in service classes named `OrderService` and `UserService`, and the aggregate's invariants are enforced nowhere because there is no aggregate, just a tuple of entities that any code can modify in any order. The fix is to put the logic on the block that owns the invariant: `order.addLine(product, qty)` (aggregate root enforces total + line count) instead of `orderService.addLine(order, product, qty)` (service class enforces nothing because the entity's setters are public).

## The Details

### **Value Objects**: Immutable objects defined strictly by their attributes, containing zero identi...

A Value Object is an object defined entirely by the values of its attributes, with no identity of its own. Two `Money(amount=10, currency=USD)` instances are interchangeable — they are the same money. Two `Address(street="123 Main", city="Springfield", zip="62701")` instances are interchangeable — they are the same address. Equality is structural: `moneyA.equals(moneyB)` returns true iff `amountA == amountB && currencyA == currencyB`. There is no `id` field; if you need to distinguish two $10 USD amounts, you are not modeling money, you are modeling a transaction or a balance — and that thing is an entity, not a value object.

Immutability is the load-bearing property. A `Money` value object has no setters; `money.add(other)` returns a new `Money` instance, leaving the original unchanged. This means a function that takes a `Money price` parameter cannot modify the caller's `price` reference — there is no defensive copy needed, no aliasing bug, no concurrency hazard. A `Money balance` field on an `Account` entity can be replaced (`balance = balance.add(deposit)`), but the old `Money` instance is never mutated. This is the same immutability contract as `String` and `LocalDate` in Java — and `String` and `LocalDate` are both value objects in the DDD sense.

Self-validation in the constructor is the second load-bearing property. A `Money` constructor that accepts `(amount, currency)` must reject `null` amount, `null` currency, negative amounts (if your domain does not allow negative money), and mismatched scales (e.g. `amount=10.5` with `currency=JPY` which has zero decimal places). The constructor throws `IllegalArgumentException` at construction; a `Money` instance, once constructed, is guaranteed valid. There is no `validate()` method to forget to call; there is no invalid state to defend against later in the code.

```java
// domain/model/Money.java  — pure Java, no framework imports
package com.shop.domain.model;

import java.math.BigDecimal;
import java.math.RoundingMode;
import java.util.Currency;
import java.util.Objects;

public final class Money implements Comparable<Money> {
    private final BigDecimal amount;
    private final Currency currency;

    public Money(BigDecimal amount, Currency currency) {
        Objects.requireNonNull(amount, "amount must not be null");
        Objects.requireNonNull(currency, "currency must not be null");
        if (amount.signum() < 0) {
            throw new IllegalArgumentException("Money amount must be non-negative: " + amount);
        }
        // Normalize the scale to the currency's default fraction digits.
        this.amount   = amount.setScale(currency.getDefaultFractionDigits(), RoundingMode.HALF_EVEN);
        this.currency = currency;
    }

    public static Money usd(BigDecimal amount) {
        return new Money(amount, Currency.getInstance("USD"));
    }

    public Money add(Money other) {
        requireSameCurrency(other);
        return new Money(this.amount.add(other.amount), this.currency);
    }

    public Money multiply(int factor) {
        if (factor < 0) throw new IllegalArgumentException("factor must be non-negative: " + factor);
        return new Money(this.amount.multiply(BigDecimal.valueOf(factor)), this.currency);
    }

    private void requireSameCurrency(Money other) {
        if (!this.currency.equals(other.currency)) {
            throw new IllegalArgumentException(
                "Currency mismatch: " + this.currency + " vs " + other.currency);
        }
    }

    @Override public boolean equals(Object o) {
        return o instanceof Money m && amount.equals(m.amount) && currency.equals(m.currency);
    }
    @Override public int hashCode()     { return Objects.hash(amount, currency); }
    @Override public int compareTo(Money o) {
        requireSameCurrency(o);
        return this.amount.compareTo(o.amount);
    }
    @Override public String toString()  { return amount + " " + currency.getCurrencyCode(); }
}
```

The production failure mode of a non-immutable value object: a `Money` with `setAmount(BigDecimal)` mutates the instance in place. A function `applyDiscount(Money price, int percent)` calls `price.setAmount(price.getAmount().multiply(...))` — and now the caller's `cart.total` is also discounted, because the same `Money` instance is referenced from both the cart and the function parameter. The bug surfaces weeks later as "the customer's saved cart shows 20% off everything." The fix is immutability: `applyDiscount` returns a new `Money`, the caller assigns it where it belongs, and the original `Money` is untouched. The cost is one extra allocation per operation; the benefit is the elimination of an entire class of aliasing bugs.

### **Entities**: Objects possessing unique identities persisting across state mutations throughout t...

An Entity is an object whose identity persists across state changes and across time, even as its attributes change. Two `User` instances with the same `id=42` are the same entity, even if one has `name="Alice"` and the other has `name="Bob"` — one of them was renamed. Two `User` instances with different `id=42` and `id=43` are different entities, even if both have `name="Alice"` — they are two different people who happen to share a name. Equality is by identity, not by attributes: `userA.equals(userB)` returns true iff `userA.id.equals(userB.id)`.

Identity is assigned at creation and never changes. Common identity schemes: a database-generated `Long` (cheap, but requires a database round-trip before the entity has an ID); a UUID (assignable in memory, no round-trip, larger storage cost — 16 bytes binary or 36 chars string); a natural key (e.g. `sku` for a product — works only if the natural key is truly immutable, which it usually is not). For aggregates that emit domain events before persistence, UUID is the only choice that does not force a database round-trip in the constructor — the aggregate gets a UUID at construction, emits `OrderPlaced(orderId)`, and the event can be published before the aggregate is saved.

State mutations go through methods that enforce invariants. A `User` entity has methods `changeEmail(String newEmail)`, `archive()`, `reactivate()` — never `setEmail(String)` or `setStatus(Status)`. The `archive()` method enforces the invariant "an archived user cannot be archived again" (throws if `status == ARCHIVED`); the `reactivate()` method enforces "only archived users can be reactivated" (throws if `status != ARCHIVED`). Public setters bypass these checks: `user.setStatus(ARCHIVED)` lets you archive an already-archived user (silent no-op) or reactivate a deleted user (data corruption). The DDD prescription is no public setters — every state change goes through a method whose name describes the business operation.

```java
// domain/model/User.java
package com.shop.domain.model;

public final class User {
    private final UserId id;
    private EmailAddress email;
    private Status status;

    private enum Status { ACTIVE, ARCHIVED }

    // Factory method — constructs the entity in valid initial state.
    public static User register(UserId id, EmailAddress email) {
        return new User(id, email, Status.ACTIVE);
    }

    private User(UserId id, EmailAddress email, Status status) {
        this.id = id; this.email = email; this.status = status;
    }

    public void changeEmail(EmailAddress newEmail) {
        if (status == Status.ARCHIVED) {
            throw new IllegalStateException("Archived user cannot change email: " + id);
        }
        this.email = newEmail;     // invariant: only ACTIVE users can change email
    }

    public void archive() {
        if (status == Status.ARCHIVED) {
            throw new IllegalStateException("User already archived: " + id);
        }
        this.status = Status.ARCHIVED;
    }

    public void reactivate() {
        if (status != Status.ARCHIVED) {
            throw new IllegalStateException("Only archived users can be reactivated: " + id);
        }
        this.status = Status.ACTIVE;
    }

    // Equality by identity, NOT by attributes.
    @Override public boolean equals(Object o) {
        return o instanceof User u && this.id.equals(u.id);
    }
    @Override public int hashCode() { return id.hashCode(); }
}
```

The production failure mode of entity equality by attributes: a `Set<User>` that uses `equals/hashCode` based on `email` will silently drop a user when their email changes — the `HashSet.remove(oldUser)` fails because the hash bucket changed, the `HashSet.add(userWithNewEmail)` succeeds, and now the user appears twice in the database but only once in the in-memory set. The fix is identity-based equality: `equals` and `hashCode` use only `id`, never mutable fields. JPA/Hibernate enforces this convention by requiring `equals/hashCode` to be stable across entity state changes — the Hibernate documentation explicitly warns against attribute-based equality for exactly this reason.

### **Aggregates and Aggregate Roots**: Clusters of entities and value objects treated as a single tr...

An Aggregate is a cluster of entities and value objects treated as a single consistency boundary, with one designated **Aggregate Root** that is the only entry point. External code may hold a reference to the root, never to internal entities. All modifications go through root methods, which enforce the aggregate's invariants. The transactional boundary is the aggregate: a single transaction loads one aggregate, modifies it, saves it. Two aggregates modified in one transaction is a smell that suggests either they should be one aggregate (the consistency boundary is wrong) or the operation should be split into two transactions coordinated by a domain event.

The canonical example: an `Order` aggregate contains `OrderLine` entities (each line has a `productId`, `quantity`, `unitPrice`) and a `Money total` value object. The invariants are: (1) `total` equals the sum of `line.unitPrice * line.quantity`; (2) an order has at most 50 lines; (3) a line's `quantity` is between 1 and 99; (4) an order in `SUBMITTED` status cannot have lines added or removed. If external code could construct an `OrderLine` directly and add it to the order's internal list, all four invariants could be violated. The aggregate root enforces them: `order.addLine(productId, quantity, unitPrice)` checks the line count, validates the quantity, appends the line, and recomputes the total. `order.submit()` checks the order is in `DRAFT` status, transitions to `SUBMITTED`, and freezes the line collection.

Aggregate size is the most common design mistake. A common error is to make `Order` contain `Customer` and `Product` aggregates — so loading an order loads the customer (with all their addresses, order history, payment methods) and the product (with all its reviews, inventory levels, pricing tiers). The right model is references: `Order` contains `customerId` and a list of `OrderLine(productId, quantity, unitPrice)`. The customer and product are loaded separately, by their own repositories, when needed. The order's invariants (total = sum of lines, max 50 lines) do not require the customer or product to be in the same aggregate — they require only the snapshot of data captured at order time (`unitPrice` is a value object copied from the product's price at order time, not a reference to the live product price).

```java
// domain/model/Order.java  — the aggregate root
package com.shop.domain.model;

import java.util.ArrayList;
import java.util.Collections;
import java.util.List;

public final class Order {
    private static final int MAX_LINES = 50;

    private final OrderId id;
    private final CustomerId customerId;
    private final List<OrderLine> lines = new ArrayList<>();
    private Money total;
    private Status status;
    private final List<DomainEvent> events = new ArrayList<>();

    private enum Status { DRAFT, SUBMITTED, CANCELLED }

    public static Order draft(OrderId id, CustomerId customerId) {
        return new Order(id, customerId, Money.usd(BigDecimal.ZERO), Status.DRAFT);
    }

    private Order(OrderId id, CustomerId customerId, Money total, Status status) {
        this.id = id; this.customerId = customerId; this.total = total; this.status = status;
    }

    public void addLine(ProductId productId, int quantity, Money unitPrice) {
        requireDraft();
        requireLineCountUnderMax();
        requireValidQuantity(quantity);
        var line = new OrderLine(productId, quantity, unitPrice);   // internal entity
        lines.add(line);
        this.total = total.add(unitPrice.multiply(quantity));
    }

    public void submit() {
        requireDraft();
        if (lines.isEmpty()) throw new IllegalStateException("Cannot submit empty order: " + id);
        this.status = Status.SUBMITTED;
        this.events.add(new OrderPlaced(id, customerId, total, List.copyOf(lines)));
    }

    public void cancel() {
        if (status != Status.SUBMITTED) {
            throw new IllegalStateException("Only submitted orders can be cancelled: " + id);
        }
        this.status = Status.CANCELLED;
        this.events.add(new OrderCancelled(id));
    }

    public List<DomainEvent> pullEvents() {
        var snapshot = List.copyOf(events);
        events.clear();
        return snapshot;
    }

    // Internal entity — package-private, no external access.
    static final class OrderLine {
        private final ProductId productId;
        private final int quantity;
        private final Money unitPrice;
        // ... constructor + getters only, no public setters
    }

    private void requireDraft() {
        if (status != Status.DRAFT) throw new IllegalStateException("Order not in DRAFT: " + id);
    }
    private void requireLineCountUnderMax() {
        if (lines.size() >= MAX_LINES) {
            throw new IllegalStateException("Order cannot have more than " + MAX_LINES + " lines: " + id);
        }
    }
    private void requireValidQuantity(int quantity) {
        if (quantity < 1 || quantity > 99) {
            throw new IllegalArgumentException("Quantity must be 1..99, got: " + quantity);
        }
    }
}
```

Note the design: `OrderLine` is a package-private nested class. External code cannot construct one, cannot get a reference to one (the `getLines()` accessor returns an unmodifiable view, not the live list), cannot modify one. Every modification goes through `order.addLine(...)`, which enforces all four invariants atomically. The `events` list is the outbox — the aggregate records events as it mutates; the use case pulls them with `pullEvents()` after the save and publishes them through the `PublishEventPort`. This is the "domain event outbox" pattern that guarantees event publication after a successful transaction.

The production failure mode of a "god aggregate": `Order` contains `Customer` (with all their other orders) and `List<Product>` (with all their reviews). Loading one order triggers a query that joins `orders`, `customers`, `addresses`, `customer_orders`, `products`, `product_reviews`, and `inventory` — 8 tables, 50ms on a cold cache, 800ms on a warm cache with 10k products, and a `LazyInitializationException` if any collection is touched outside the transaction. The fix is to make `Order` small: it contains `customerId` (a value object reference, not the Customer aggregate) and `OrderLine(productId, quantity, unitPrice)` (the productId is a reference, the unitPrice is a snapshot value object). When the use case needs the customer's name for the order confirmation email, it loads `Customer` separately via `CustomerRepository`. The aggregate's transactional boundary stays small; the cross-aggregate read happens in the application layer.

### **Domain Events**: Immutable records representing business state mutations emitted by aggregates

A Domain Event is an immutable record that represents something that happened in the domain — `OrderPlaced`, `PaymentConfirmed`, `OrderShipped`, `InventoryDepleted`. Events are emitted by aggregates after a state change, published to anyone who cares (other aggregates, other bounded contexts, audit logs, read-model projectors), and stored as historical fact. An event is named in the past tense — `OrderPlaced` (the order was placed), not `PlaceOrder` (a command to place the order). The naming is the contract: a command says "please do X"; an event says "X has happened." A handler that receives `OrderPlaced` may safely assume the order is placed; a handler that receives `PlaceOrder` cannot — the command might fail validation.

Immutability is load-bearing. An event captures the state of the domain at the moment it occurred: `OrderPlaced(orderId, customerId, total, lineItems, occurredAt)`. Six months later, you can replay this event and the data is identical — `total` has the same value, `lineItems` has the same items at the same prices, `occurredAt` is the same instant. This is what makes event sourcing possible: the entire state of the system is the replay of all events in order. If an event were mutable (e.g. `lineItems` is a `List<OrderLine>` that the handler can modify), replay would give different state depending on the order of handlers, and the historical record would be unreliable.

Events are published through a port, never directly. The aggregate records events in an internal list (`order.recordEvent(new OrderPlaced(...))`); the use case pulls them after the save (`order.pullEvents()`) and publishes them via `PublishEventPort.publish(event)`. The aggregate does not depend on `ApplicationEventPublisher` (Spring's type) — it depends on nothing; the use case depends on the port; the infrastructure provides the implementation. This is the same hexagonal pattern as every other driven port.

```java
// domain/event/DomainEvent.java  — sealed interface, pure Java
package com.shop.domain.event;

import java.time.Instant;
import java.util.UUID;

public sealed interface DomainEvent {
    UUID eventId();
    Instant occurredAt();
    String aggregateId();
}

// domain/event/OrderPlaced.java
public record OrderPlaced(
    UUID eventId,
    Instant occurredAt,
    String orderId,
    String customerId,
    BigDecimal total,
    String currency,
    List<LineItem> lineItems
) implements DomainEvent {
    public OrderPlaced(String orderId, String customerId, Money total, List<OrderLine> lines) {
        this(UUID.randomUUID(), Instant.now(), orderId, customerId,
             total.amount(), total.currency().getCurrencyCode(),
             lines.stream().map(l -> new LineItem(l.productId().value(), l.quantity())).toList());
    }
    @Override public String aggregateId() { return orderId; }
}

// domain/event/OrderCancelled.java
public record OrderCancelled(UUID eventId, Instant occurredAt, String orderId) implements DomainEvent {
    public OrderCancelled(String orderId) { this(UUID.randomUUID(), Instant.now(), orderId); }
    @Override public String aggregateId() { return orderId; }
}

// application/usecase/PlaceOrderService.java  — pulls events and publishes
public class PlaceOrderService implements PlaceOrderUseCase {
    private final LoadCustomerPort loadCustomer;
    private final SaveOrderPort saveOrder;
    private final PublishEventPort publishEvent;

    @Override
    @Transactional
    public PlaceOrderResult place(PlaceOrderCommand cmd) {
        var order = Order.draft(OrderId.generate(), cmd.customerId());
        for (var line : cmd.items()) {
            order.addLine(line.productId(), line.quantity(), line.unitPrice());
        }
        order.submit();
        saveOrder.save(order);
        // Pull events AFTER the save, publish THROUGH the port.
        for (DomainEvent event : order.pullEvents()) {
            publishEvent.publish(event);
        }
        return new PlaceOrderResult(order.id().toString(), order.total());
    }
}
```

The production failure mode is the "command-disguised-as-event": an event named `SubmitOrder` that handlers receive and use to submit the order. The handler calls `order.submit()` — but the order may already be submitted (the event was emitted because the order was submitted), so the handler hits `IllegalStateException: Order not in DRAFT`. The fix is rigorous past-tense naming: `OrderPlaced` means the order is already placed; the handler reacts to the fact, it does not perform the action. A second failure mode is the "non-idempotent handler": the event is delivered twice (Kafka's at-least-once), the handler charges the customer's card twice. The fix is idempotency by event ID — the handler records `event_id` in a `processed_events` table and skips events it has already processed. A third failure mode is "event with mutable fields" — the `lineItems` list is mutable, one handler sorts it, the next handler sees a different order, the replay is non-deterministic. The fix is to make every event a `record` with `List.copyOf(...)` in the constructor — immutability enforced by the type system.

### **Domain Services**: Stateless operations that naturally belong to the domain but do not fit with...

A Domain Service is a stateless operation that contains domain logic but does not naturally belong to a single entity or value object. The canonical example: a money transfer between two `Account` aggregates. The operation `transfer(from, to, amount)` modifies both accounts (debit `from`, credit `to`) and enforces the invariant "the sum of all accounts' balances is conserved." This logic does not belong on `Account` because it operates on two accounts; it does not belong on `Money` because it requires account-level authorization and balance checks. It belongs on a stateless `TransferService` domain service.

The defining properties of a domain service: (1) it is stateless — no fields, no mutable state, no `@Autowired` collaborators that hold state; (2) it operates on domain objects (entities, value objects) — never on DTOs, never on framework types; (3) it enforces a domain invariant that spans multiple aggregates or that is a pure domain calculation; (4) it lives in the domain layer — no `@Service` annotation (that is a Spring stereotype that belongs on application services, not domain services). A domain service is typically a class with one or two methods, each taking domain objects as parameters and returning domain objects or events.

The distinction from an application service (use case) is critical and frequently muddled. An application service orchestrates a use case: it loads aggregates from repositories, calls domain services, saves aggregates, publishes events. A domain service contains pure domain logic that does not touch infrastructure. The application service is allowed to depend on ports (repositories, publishers); the domain service is not — it takes its inputs as parameters and returns its outputs as return values. A `TransferService.transfer(from, to, amount)` takes two `Account` objects and a `Money` amount; it does not load the accounts from a repository, does not save them, does not publish events. The application service does those things.

```java
// domain/service/TransferService.java  — pure domain logic, stateless
package com.shop.domain.service;

import com.shop.domain.model.*;

public final class TransferService {
    // Stateless: no fields, no collaborators.

    public TransferResult transfer(Account from, Account to, Money amount) {
        // Pure domain logic — operates on the two Account aggregates.
        from.debit(amount);          // Account enforces "balance cannot go negative"
        to.credit(amount);
        return new TransferResult(from.id(), to.id(), amount, Instant.now());
    }

    public record TransferResult(AccountId from, AccountId to, Money amount, Instant at) {}
}

// application/usecase/TransferMoneyService.java  — the application service (use case)
public class TransferMoneyService implements TransferMoneyUseCase {
    private final LoadAccountPort loadAccount;
    private final SaveAccountPort saveAccount;
    private final PublishEventPort publishEvent;
    private final TransferService transferService;   // injected domain service

    @Override
    @Transactional
    public void transfer(TransferCommand cmd) {
        var from = loadAccount.loadById(cmd.fromAccountId())
                .orElseThrow(() -> new AccountNotFoundException(cmd.fromAccountId()));
        var to   = loadAccount.loadById(cmd.toAccountId())
                .orElseThrow(() -> new AccountNotFoundException(cmd.toAccountId()));
        var result = transferService.transfer(from, to, cmd.amount());   // pure logic
        saveAccount.save(from);
        saveAccount.save(to);
        publishEvent.publish(new MoneyTransferred(result));
    }
}
```

The production failure mode is the "anemic domain model": all logic lives in `OrderService`, `UserService`, `AccountService` — classes that depend on repositories, call entity setters, and enforce invariants in procedural code. The entities are bags of getters and setters; the aggregate boundary is not enforced because there is no aggregate root, just a tuple of entities. The `OrderService.submit(order)` method sets `order.setStatus(SUBMITTED)`, calls `order.setTotal(computeTotal(order))`, calls `orderRepository.save(order)` — but nothing prevents `orderService.addLine(order, ...)` from being called after `submit`, because the order's `status` field has a public setter and no invariant check. The fix is to move the logic to the block that owns the invariant: `order.submit()` (aggregate root enforces status transition), `order.addLine(...)` (aggregate root enforces line count and total). The service becomes a thin orchestrator — load, call method, save, publish — and the entity becomes the place where the business rules live.

### **Repositories**: Collection-like interfaces abstracting the persistence and retrieval of aggrega...

A Repository is a collection-like interface that abstracts the persistence and retrieval of aggregate roots. The interface is declared in the domain layer; the implementation lives in the infrastructure layer. The interface is collection-like in the sense that it presents the persistence store as if it were an in-memory collection: `findById(id)` returns `Optional<Order>`, `save(order)` persists the aggregate (insert or update — the repository figures out which), `delete(order)` removes it. There is one repository per aggregate root, never per entity — there is no `OrderLineRepository`, because `OrderLine` is an internal entity of the `Order` aggregate and is loaded/saved only through the `OrderRepository`.

The "one repository per aggregate" rule is the load-bearing constraint. If you had an `OrderLineRepository`, external code could load an `OrderLine` independently of its `Order`, modify it (e.g. change the quantity), and save it — bypassing the `Order` aggregate's invariant enforcement. The total on the `Order` would no longer match the sum of its lines. The rule eliminates this failure mode by making the aggregate root the only entry point: every modification goes through `order.addLine(...)` or `order.removeLine(...)`, the order's invariants are enforced, and the order (with its lines) is saved as a unit. The repository's `save(order)` call writes the order and all its lines in a single transaction.

The interface belongs in the domain; the implementation belongs in infrastructure. The interface uses domain types only: `Optional<Order> findById(OrderId id)`, `void save(Order order)`, `void delete(Order order)`. It does not use JPA types (`EntityManager`, `Page`, `Pageable`), does not use Spring Data types (`JpaRepository`, `CrudRepository`), does not use collection types that leak JPA semantics (`Stream<Order>`, `Flux<Order>`). The interface is a port in the Hexagonal sense — see [[09.03.01. The Hexagonal (Ports and Adapters) Architecture]]. The implementation is an adapter: `JpaOrderRepository implements OrderRepository`, holds an `EntityManager`, maps between `Order` (domain) and `OrderJpaEntity` (persistence), and is annotated `@Component` so Spring DI can inject it.

```java
// domain/repository/OrderRepository.java  — the port (interface in domain)
package com.shop.domain.repository;

import com.shop.domain.model.Order;
import com.shop.domain.model.OrderId;
import java.util.Optional;

public interface OrderRepository {
    Optional<Order> findById(OrderId id);
    void save(Order order);
    void delete(Order order);
}

// infrastructure/persistence/OrderRepositoryAdapter.java  — the adapter (impl in infra)
package com.shop.infrastructure.persistence;

import com.shop.domain.model.Order;
import com.shop.domain.model.OrderId;
import com.shop.domain.repository.OrderRepository;
import org.springframework.stereotype.Component;
import java.util.Optional;

@Component
class OrderRepositoryAdapter implements OrderRepository {
    private final OrderJpaRepository jpa;   // Spring Data JPA generated interface

    OrderRepositoryAdapter(OrderJpaRepository jpa) { this.jpa = jpa; }

    @Override
    public Optional<Order> findById(OrderId id) {
        return jpa.findById(id.value()).map(OrderJpaEntity::toDomain);
    }

    @Override
    public void save(Order order) {
        var existing = jpa.findById(order.id().value());
        if (existing.isPresent()) {
            existing.get().updateFrom(order);    // merge into managed entity
        } else {
            jpa.save(OrderJpaEntity.fromDomain(order));   // insert new
        }
    }

    @Override
    public void delete(Order order) {
        jpa.deleteById(order.id().value());
    }
}

// infrastructure/persistence/OrderJpaRepository.java  — Spring Data JPA generated
interface OrderJpaRepository extends JpaRepository<OrderJpaEntity, String> {}
```

Queries beyond simple `findById` are a common source of interface pollution. The temptation is to add `findOrdersByCustomerAndStatusAndDateBetween(customerId, status, from, to)` to the repository — and within a year, the interface has 40 query methods, each one a leaky abstraction over SQL. The DDD prescription is to use the Specification pattern (Spring Data JPA's `Specification<Order>` interface) or to introduce a separate query service in the application layer (`OrderQueryService.findOrderSummaries(filter)` that returns read-optimized DTOs, not aggregates). The repository's job is to load and save aggregates; the query service's job is to answer read queries. This separation is the seed of CQRS (see [[09.05.01. Command Query Responsibility Segregation (CQRS)]]) — the write side (repository) is separated from the read side (query service) at the interface level.

The production failure mode is the "leaky repository": the interface returns `Page<Order>` (Spring Data type) instead of `List<Order>`, and now the domain depends on `spring-data-commons`. A migration to JOOQ or to a non-Spring DI container breaks the domain. A second failure mode is the "repository per entity": `OrderLineRepository`, `OrderAddressRepository`, `OrderStatusHistoryRepository` — five repositories for one aggregate, each one a hole in the aggregate boundary. The fix is one repository per aggregate root: `OrderRepository` saves the order, its lines, its address, its status history — all in one transaction, all through one method, all enforced by the order's invariants. A third failure mode is returning a JPA-managed entity from the repository: the domain calls `order.addLine(...)` which traverses a lazy collection, fires SQL outside the transaction, throws `LazyInitializationException`. The fix is `OrderJpaEntity.toDomain()` mapping inside the adapter — the returned `Order` is a pure domain object, fully loaded, detached from the persistence context.
