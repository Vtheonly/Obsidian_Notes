# 09.00. Map of Content: Software Architecture

## Overview

This section covers **09. Software Architecture and Design Patterns**. It is part of the unified backend engineering vault described in [[00.01. Master Architectural Mental Model]]. The notes below are organized by concept, not by framework. Each concept is taught once at the conceptual level, then implemented deeply in the Spring Boot anchor stack, then rapidly translated into Express, Django, Flask, and Laravel as deltas.

Section 09 sits at the top of the layered mental model. Sections 02–04 explain the runtime substrate (kernel, network, language runtime). Section 05 lifts that substrate into the framework layer (routing, middleware, DI, validation, security). Section 06 covers persistence, section 07 covers async messaging, section 08 covers distributed systems. Section 09 is where the *shape* of the entire system is decided: how many deployable units exist, where the boundaries between them run, which direction dependencies point, who owns which data, and which patterns you reach for when a single bounded context gets too rich to fit inside a CRUD controller.

The decisions made in 09 propagate everywhere. A microservices topology choice from [[09.01.01. Monoliths Modular Monoliths and Microservices]] dictates whether a request from section 05 crosses a network boundary (and therefore whether the timeout/retry math from section 03 matters). A database-per-service choice from [[09.01.02. Decoupling Microservice Data Stores]] forces the saga pattern from [[08.02.02. The Saga Architectural Pattern]] instead of a local ACID transaction from [[06.04.01. The ACID Mathematical Guarantees]]. A layered/MVC choice from 09.02 decides whether the `@Transactional` boundary lives in a service bean or leaks into a controller. The hexagonal/Clean decisions in 09.03 decide whether swapping PostgreSQL for MongoDB is a one-day refactor or a six-month rewrite. The DDD choices in 09.04 decide whether your domain language matches what the business actually says. CQRS in 09.05 decides whether you can read your own write 5 ms after issuing it. The GoF patterns in 09.06 are the load-bearing vocabulary that makes any of the previous choices expressible in code.

## Section Map

### 09.01. Architectural Topologies and Boundaries

- [[09.01.01. Monoliths Modular Monoliths and Microservices]] — Three deployment topologies compared on a single axis: how many independently-deployable units own your code. The monolith is one deployable, one process, one database, in-process function calls everywhere — operationally trivial, refactor-cheap, but impossible to scale piecewise and impossible to assign independent deployment cadences to subsystems. The modular monolith (Shopify's Rails monolith, Basecamp's Rails monolith, Stack Overflow's .NET monolith) keeps the single deployable but enforces module boundaries inside the codebase — each module owns its schema, exposes a public in-process API, and is forbidden from reaching into another module's tables. The microservice topology splits each bounded context into its own deployable with its own database, communicating only over network calls — unlocks polyglot stacks and independent deployment pipelines, but pays the full distributed-systems tax (network partitions, eventual consistency, distributed tracing, saga coordination, opentelemetry baggage propagation, schema-evolution coordination). The fourth H3 covers Conway's Law: any system's topology will mirror the org chart that builds it, so you either restructure teams to match the topology you want or accept the topology your existing teams will produce.
- [[09.01.02. Decoupling Microservice Data Stores]] — The single most-cited rule in microservice architecture: each service owns its own database and no other service may touch it directly. The anti-pattern (a shared `orders` database that both the `OrderService` and the `InventoryService` read and write) couples services at the schema layer, destroys independent deployment (any `ALTER TABLE` must be coordinated across N teams), and creates lock contention that nobody can debug because the lock waits cross process boundaries. The note walks through the database-per-service principle, the CQRS/eventual-consistency implications (you can no longer `JOIN` across services, so you either aggregate in the API gateway or maintain a materialised view via subscribed events), the saga pattern for cross-service transactions, and the data-ownership contract that says only the owning service may mutate a row.

### 09.02. Layered and MVC Architecture

- [[09.02.01. Classic N-Tier Layered Architecture]] — The oldest structural pattern in backend engineering: split the codebase into horizontal layers (Presentation → Application/Service → Domain → Data Access), with dependencies pointing strictly downward. The dependency rule is what makes this work — the data access layer may never call a controller, the controller may never embed SQL, the service layer is the only place `@Transactional` boundaries may live. The note walks through how Spring Boot's `@Controller`/`@Service`/`@Repository` stereotypes map to these layers, why the anaemic domain model anti-pattern (entities that are just bags of getters/setters with all logic in services) is the natural consequence of a naive N-tier implementation, and how layered architecture evolves into hexagonal/Clean architecture when the domain layer needs to be protected from framework churn.
- [[09.02.02. Model-View-Controller (MVC) Patterns]] — The original 1979 Smalltalk-80 UI pattern, adapted into every web framework. Model = state plus the business rules that mutate that state. View = the projection of model state into a rendered output (HTML, JSON, CSV). Controller = the input handler that translates an HTTP request into a model mutation and selects the next view. The note covers the Smalltalk-80 variant (where the View subscribed to Model changes via the Observer pattern and the Controller translated keyboard/mouse events), the web MVC variant that every modern framework uses (Rails, Django, Laravel, Spring MVC, ASP.NET MVC, Phoenix), the Django MVT divergence (Django calls its controller a "view" and its view a "template"), the MVP and MVVM variants used in rich-client UIs, and the "Fat Model, Skinny Controller" convention — plus why that convention collapses in complex enterprise domains where service objects become necessary.

### 09.03. Clean and Hexagonal Architecture

- [[09.03.01. The Hexagonal (Ports and Adapters) Architecture]] — Alistair Cockburn's 2005 pattern. The core insight is that business logic has no business knowing whether it's being driven by an HTTP request, a CLI invocation, a Kafka consumer, or a test harness — and it has no business knowing whether its state is persisted in PostgreSQL, MongoDB, a flat file, or an in-memory map for unit tests. The domain core exposes *ports* (interfaces) for inbound driving actions and outbound driven resources; *adapters* are the framework-specific implementations of those ports. The note covers the strict dependency rule (ports belong to the inside, adapters to the outside, the dependency rule points inward), the testability payoff (every domain test runs without touching a database or HTTP server), and the cost (more interfaces, more wiring, more files per feature).
- [[09.03.02. Clean Architecture and Onion Architecture Mapping]] — Robert C. Martin's 2012 Clean Architecture and Jeffrey Palermo's 2008 Onion Architecture are two restatements of the same core invariant as hexagonal: dependencies point inward toward the domain. The Clean Architecture expresses this as four concentric circles (Entities → Use Cases → Interface Adapters → Frameworks & Drivers); the Onion Architecture expresses it as concentric layers around a domain core. The note maps the three patterns (Hexagonal, Clean, Onion) onto each other, shows how Spring Boot's `@Service`/`@Repository`/`@Component` stereotypes blur the boundary between Use Cases and Interface Adapters in practice, and explains why the dependency-inversion principle (the "D" in SOLID) is the load-bearing mechanism that makes any of these patterns physically possible in a compiled language.

### 09.04. Domain-Driven Design Tactical and Strategic

- [[09.04.01. Strategic Design Concepts]] — Eric Evans's 2003 strategic toolkit for carving a business domain into manageable chunks. Bounded Contexts define the boundaries inside which a Ubiquitous Language is consistent — the word "Order" means one thing in the Sales context, a different thing in the Shipping context, and a third thing in the Billing context, and that is correct, not a bug to be fixed by building one universal Order entity. Context Maps describe the relationships between bounded contexts (Customer/Supplier, Conformist, Anticorruption Layer, Shared Kernel, Open Host Service, Published Language). The note covers how to identify bounded contexts from domain-event storming sessions, why "one database per service" from [[09.01.02. Decoupling Microservice Data Stores]] is the natural physical implementation of one database per bounded context, and the anti-pattern of the Big Ball of Mud (a single context that absorbed everything).
- [[09.04.02. Tactical Domain Building Blocks]] — The building-block vocabulary Evans defined for inside a bounded context: Entities (objects defined by identity, not attributes), Value Objects (immutable objects defined by their attributes, the backbone of a domain language), Aggregates (consistency boundaries around a cluster of Entities and Value Objects, with one Entity acting as the Aggregate Root and the only entry point), Repositories (collection-like interfaces for retrieving Aggregates), Domain Services (stateless operations that don't belong to any single Entity), Domain Events (things that happened in the past, used to decouple side effects), and Factories (encapsulations of complex construction). The note covers the difference between an anaemic domain model (just data) and a rich domain model (data + behaviour co-located), why the Aggregate Root is the unit of consistency, and how these blocks map onto Spring Boot stereotypes and JPA annotations.

### 09.05. CQRS and Event Sourcing

- [[09.05.01. Command Query Responsibility Segregation (CQRS)]] — Greg Young's 2010 pattern: split the read path from the write path. The write model accepts Commands (intentions, e.g. `SubmitOrder`) and emits Events (facts, e.g. `OrderSubmitted`); the read model is a set of projections built from those events, optimised for whatever query the UI needs to answer. The note covers why CQRS is not a top-level architecture but a tactical choice that applies *inside* a single bounded context (typically the few contexts with read/write ratio > 100:1 and divergent read/write schemas), the eventual-consistency trade-off (the read model lags the write model by the projection lag, usually tens of milliseconds), and the failure mode where teams adopt CQRS for a CRUD-shaped problem and pay a 3× complexity cost for zero benefit.
- [[09.05.02. Event Sourcing Mechanics]] — The core invariant: state is not stored as a mutable snapshot; state is stored as an append-only sequence of immutable domain events. The current state is a left-fold over the event stream. The note covers the event-store storage layout (an `events` table with `aggregate_id`, `sequence_number`, `event_type`, `payload`, `occurred_at` columns, with a unique constraint on `(aggregate_id, sequence_number)` for optimistic concurrency), the snapshot optimisation (every N events, persist a materialised fold so replay doesn't start from epoch), the difference between domain events and integration events (the former are inside-the-bounded-context and may carry rich payloads; the latter cross bounded contexts and should be small + versioned), and the dual-write problem from [[07.05.01. The Dual-Write Problem]] that event sourcing solves by making the event store the single source of truth and the read-model database a downstream projection.

### 09.06. Enterprise Backend Design Patterns

- [[09.06.01. Creational Patterns in Backend Systems]] — The GoF creational patterns as they actually appear in backend code: Factory Method (Spring's `FactoryBean<T>`, used when bean construction needs custom logic), Abstract Factory (used when you need to swap an entire family of related objects — e.g. AWS SDK vs Azure SDK vs GCP SDK adapters), Builder (Lombok `@Builder`, used for constructing DTOs with many optional fields), Singleton (Spring's default bean scope, backed by a `ConcurrentHashMap` in the `DefaultSingletonBeanRegistry`), and Prototype (rarely used directly, but `@Scope("prototype")` matters when you need a fresh instance per lookup). The note covers why the `new` keyword is the enemy of testability and how DI containers are essentially a fleet of factories wired together by configuration.
- [[09.06.02. Structural Patterns in Backend Systems]] — The GoF structural patterns as they appear in real backend code: Adapter (the single most-used pattern in integration code — wraps a third-party SDK behind your own port interface, the load-bearing mechanism behind hexagonal architecture from [[09.03.01. The Hexagonal (Ports and Adapters) Architecture]]), Decorator (Spring's `@Transactional`, `@Async`, `@Retryable` — all implemented as JDK dynamic proxies that wrap the target bean and intercept method calls), Facade (the `OrderService` that hides the coordination of `InventoryService` + `PaymentService` + `ShippingService` behind a single `placeOrder` method), Composite (the chain-of-responsibility middleware pipeline from [[05.02.01. The Chain of Responsibility Pattern in Web Pipelines]]), and Proxy (lazy-loading JPA entities, remote RPC stubs).
- [[09.06.03. Behavioral Patterns in Backend Systems]] — The GoF behavioral patterns: Strategy (the `PaymentProcessor` interface with `StripeProcessor`/`PaypalProcessor`/`AdyenProcessor` implementations, selected at runtime by a `Map<String, PaymentProcessor>` registry — the most idiomatic way to handle "the business wants to add a new payment provider"), Template Method (Spring's `JdbcTemplate`, `RestTemplate`, `TransactionalRepository` — defines the skeleton of an algorithm and lets subclasses override specific steps), Observer (Spring's `ApplicationEventPublisher` / `@EventListener`, the in-process analogue of the messaging patterns from section 07), Command (the `Runnable` / `Callable` abstractions, the CQRS `CommandHandler<T>` interface from [[09.05.01. Command Query Responsibility Segregation (CQRS)]]), Chain of Responsibility (Servlet `Filter` chain, Spring `HandlerInterceptor` chain), and State (the order-status state machine — `PENDING → PAID → SHIPPED → DELIVERED`, where each state has its own set of allowed transitions).

## Conceptual Roadmap

The seven sub-sections of section 09 are not a flat list — they form a decision tree that any senior backend engineer walks in order when shaping a new system. Read them in this order, not in numeric order, on a first pass:


**Layer 1 — Topology (09.01):** The first decision is structural. How many deployable units? Where do the boundaries between them run? Who owns which data? This decision is almost irreversible — moving from microservices back to a monolith is a multi-year rewrite (Amazon's "single tax return" consolidation, Segments's 2020 monolith reversal). Get it wrong and everything downstream is paying interest on a bad loan.

**Layer 2 — Inside the boundary (09.02 – 09.05):** Once you know where the boundaries are, you have to design the inside of each one. 09.02 (Layered/MVC) is the baseline — every framework defaults to it, it's what you get for free. 09.03 (Hexagonal/Clean) is the upgrade you make when the domain logic starts getting rich enough that framework coupling hurts. 09.04 (DDD) is the language-and-modelling discipline that decides whether your code matches what the business actually says. 09.05 (CQRS/Event Sourcing) is the heavy machinery you reach for when a single bounded context has read/write ratios > 100:1, audit requirements, or temporal-query requirements ("what did this order look like on Tuesday at 3pm?").

**Layer 3 — Vocabulary (09.06):** The GoF patterns are not a separate concern — they are the load-bearing vocabulary used to *implement* every choice in layers 1 and 2. A hexagonal port is the Strategy pattern. A repository is the Factory pattern. A `@Transactional` proxy is the Decorator pattern. A `PaymentProcessor` registry is the Strategy + Factory combination. You read 09.06 last not because it's least important but because the patterns are easier to motivate once you've seen the architectural problems they solve.

The cross-cutting thread is the **dependency rule**: dependencies point inward, toward the domain, away from infrastructure. Every note in section 09 is a restatement of that rule at a different level of granularity. Topology (09.01) is the dependency rule at the deployment-unit level. Layered/MVC (09.02) is the dependency rule at the source-code-package level. Hexagonal/Clean (09.03) is the dependency rule at the interface level. DDD (09.04) is the dependency rule at the language level — the domain doesn't depend on the database, the database depends on the domain. CQRS (09.05) is the dependency rule at the data level — the write side owns truth, the read side is a downstream projection. The GoF patterns (09.06) are the mechanisms that make the dependency rule physically enforceable in a compiled language.
