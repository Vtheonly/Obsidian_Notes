# 09.03.01. The Hexagonal (Ports and Adapters) Architecture

## What This Is

The Hexagonal Architecture — published by Alistair Cockburn in 2005 under the name "Ports and Adapters" — is an architectural pattern that isolates an application's domain logic from the infrastructure it touches. The application core (entities, use cases, domain services) defines interfaces called **ports**; concrete technologies (REST controllers, JPA repositories, Kafka producers, Stripe clients) implement those ports as **adapters**. The dependency direction is one-way: adapters depend on the core, never the reverse. The hexagon shape is incidental — Cockburn chose it to avoid implying "top" or "bottom" layers; any polygon with at least four sides would do.

In the layered mental model of this vault, hexagonal sits between the framework layer (sections 05–07) and the application domain. The ports are the seams across which the framework layer talks to the domain; the adapters are the framework-layer code that knows about HTTP, JPA, Kafka, and Stripe. The domain itself depends on neither — it is pure Java/Kotlin/TypeScript/Python, compilable and testable in isolation. This is the architectural pattern that lets you swap Spring for Quarkus, Postgres for MongoDB, or run the entire domain in a JUnit test without spinning up a database.

The pattern governs two specific failure modes: (1) the "framework-coupled domain" — a `Money` value object with `@Embeddable` JPA annotations, which forces a JPA version bump to ripple through business code; and (2) the "untestable use case" — a `PlaceOrderService` that autowires `EntityManager` directly, which means every unit test must bootstrap a Spring context and a real database. The hexagonal boundary eliminates both by pushing framework concerns behind interfaces that the domain owns.

## The Details

### Core Principle: Isolating pure domain business rules from frameworks, databases, network protocol...

The defining invariant of hexagonal is that the application core — the package that contains entities, value objects, aggregates, use cases, and domain services — has zero compile-time dependencies on any framework, database driver, message broker client, or third-party SDK. The test is mechanical: run `mvn dependency:tree -pl domain` on the domain module and the output must be empty (or contain only `org.slf4j` for logging, which is itself an abstraction). If the tree contains `org.springframework:*`, `jakarta.persistence:*`, `org.hibernate:*`, `org.apache.kafka:*`, or `com.stripe:*`, the boundary is broken. The `Money` value object must not have `@Embeddable`; the `Order` aggregate must not have `@Entity`; the `OrderPlaced` event must not import `org.springframework.context.ApplicationEvent`.

The justification is one of cadence mismatch. Business rules change on business cadence — quarters, sometimes years. Infrastructure changes on technology cadence — weeks for a Spring patch, months for a Postgres major upgrade, days for a CVE-driven Kafka client bump. When the domain depends on infrastructure, every infrastructure change forces a domain recompile, a domain retest, and a domain redeploy — even when the business rules have not changed. When the domain is isolated, infrastructure changes ripple only through the adapter layer, which is small and shallow. The same principle applies in reverse: when the business changes a rule, the change is confined to the domain package and cannot accidentally break a JPA mapping.

The enforcement mechanism in a Spring Boot codebase is the multi-module Maven build. The `domain` module is pure Java — no `spring-boot-starter-*` dependencies. The `application` module depends on `domain` and defines the port interfaces plus the use-case implementations; it may use `org.slf4j` but no framework. The `infrastructure-jpa` module depends on `application` and implements the driven ports using Spring Data JPA. The `infrastructure-web` module depends on `application` and provides the REST controllers. The `bootstrap` module is the only place `@SpringBootApplication` appears; it depends on all infrastructure modules and wires the adapters. The `maven-enforcer-plugin` enforces this at build time:

```xml
<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-enforcer-plugin</artifactId>
  <executions>
    <execution>
      <id>enforce-domain-purity</id>
      <goals><goal>enforce</goal></goals>
      <configuration>
        <rules>
          <bannedDependencies>
            <excludes>
              <exclude>org.springframework:*</exclude>
              <exclude>jakarta.persistence:*</exclude>
              <exclude>org.hibernate:*</exclude>
              <exclude>org.apache.kafka:*</exclude>
              <exclude>com.stripe:*</exclude>
            </excludes>
          </bannedDependencies>
        </rules>
        <fail>true</fail>
      </configuration>
    </execution>
  </executions>
</plugin>
```

The production failure mode is silent erosion: a developer adds `@Entity` to the `Order` class "just to make JPA mapping easier," the build still passes (because the enforcer plugin was never configured), and six months later a Hibernate 6 upgrade breaks the domain's `@GeneratedValue` annotation, which forces a domain recompile, which forces a full regression suite, which finds three other places where JPA annotations have leaked in. The fix is the enforcer plugin plus an ArchUnit test that asserts `noClasses().that().resideInAPackage("..domain..").should().dependOnClassesThat().resideInAPackage("..org.hibernate..")`. The enforcer plugin catches the dependency declaration; ArchUnit catches the transitive import.

### Driving / Inbound Ports: Interfaces defining use cases exposed to the outside world (Controllers,...

A driving (also called "primary" or "inbound") port is an interface declared inside the application core that names a use case the outside world can trigger. The interface is the contract: it specifies the input type (a command), the output type (a result or DTO), and the exception types the use case may throw. The driving adapter — a REST controller, a CLI command, a Kafka consumer, a gRPC service — depends on this interface, not on the use-case class itself. The use-case class implements the interface and lives in the application layer. The adapter is the only piece of code that knows about HTTP, CLI args, or Kafka records; the port is the seam across which the adapter hands a plain command object to the use case.

The swap test is the validation: can you replace the REST controller with a gRPC service without touching the use case? Can you add a CLI command that invokes the same use case in parallel with the REST controller? Can you write a unit test that calls the use case directly without any HTTP? If the answer is yes, the port is correctly designed. If the answer is no — if the use case signature contains `HttpServletRequest`, or if the controller calls private methods on the use-case class — the port is leaking. A correctly designed port takes a plain command record (a value object with no framework types), returns a plain result record, and throws plain domain exceptions.

A Spring Boot example, end to end:

```java
// application/port/in/PlaceOrderUseCase.java  (the port — pure Java)
package com.shop.application.port.in;

public interface PlaceOrderUseCase {
    PlaceOrderResult place(PlaceOrderCommand command);

    record PlaceOrderCommand(String customerId, List<OrderLineItem> items, Address shippingAddress) {}
    record PlaceOrderResult(String orderId, Money total) {}
}

// application/usecase/PlaceOrderService.java  (the implementation — pure Java)
package com.shop.application.usecase;

import com.shop.application.port.in.PlaceOrderUseCase;
import com.shop.application.port.out.LoadAccountPort;
import com.shop.application.port.out.SaveOrderPort;
import com.shop.application.port.out.PublishEventPort;

public class PlaceOrderService implements PlaceOrderUseCase {
    private final LoadAccountPort loadAccount;
    private final SaveOrderPort saveOrder;
    private final PublishEventPort publishEvent;

    public PlaceOrderService(LoadAccountPort loadAccount, SaveOrderPort saveOrder, PublishEventPort publishEvent) {
        this.loadAccount = loadAccount;
        this.saveOrder = saveOrder;
        this.publishEvent = publishEvent;
    }

    @Override
    public PlaceOrderResult place(PlaceOrderCommand command) {
        Customer customer = loadAccount.load(command.customerId());
        Order order = customer.placeOrder(command.items(), command.shippingAddress());
        saveOrder.save(order);
        publishEvent.publish(new OrderPlaced(order.id(), order.total()));
        return new PlaceOrderResult(order.id().toString(), order.total());
    }
}

// infrastructure/web/PlaceOrderController.java  (the driving adapter — Spring)
package com.shop.infrastructure.web;

import com.shop.application.port.in.PlaceOrderUseCase;
import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/api/orders")
class PlaceOrderController {
    private final PlaceOrderUseCase placeOrder;   // depends on the PORT, not the Service

    PlaceOrderController(PlaceOrderUseCase placeOrder) {
        this.placeOrder = placeOrder;
    }

    @PostMapping
    PlaceOrderResponse place(@RequestBody PlaceOrderRequest req) {
        var cmd = new PlaceOrderUseCase.PlaceOrderCommand(
            req.customerId(), req.toLineItems(), req.toAddress());
        var result = placeOrder.place(cmd);
        return PlaceOrderResponse.from(result);
    }
}
```

Note what the controller does NOT do: it does not call `new PlaceOrderService(...)`, it does not import any domain class, and it does not call any method on `PlaceOrderService` other than the one declared on the port. The Spring DI container wires the `PlaceOrderService` bean into the controller's constructor under the `PlaceOrderUseCase` interface. If tomorrow you replace the REST controller with a gRPC service that calls the same port, the use case, the domain, and the persistence layer are untouched.

The production failure mode is the "fat controller": a developer who bypasses the port and calls `placeOrderService.place(cmd, httpRequest)` — passing the HTTP request through to the use case so the use case can read a header. The use case now depends on `HttpServletRequest`, the domain layer transitively depends on Spring Web, the unit test must bootstrap a mock servlet context, and a future migration to gRPC (where there is no `HttpServletRequest`) breaks the use case. The fix is to extract the header in the controller and pass it as a plain field on the command: `new PlaceOrderCommand(customerId, items, address, correlationId)`.

### Driven / Outbound Ports: Interfaces defining infrastructure requirements needed by the domain (Re...

A driven (also called "secondary" or "outbound") port is an interface the application core declares for the infrastructure it needs. Where a driving port says "here is what you can ask me to do," a driven port says "here is what I need from you." Typical driven ports: `LoadAccountPort` (load a `Customer` aggregate by ID), `SaveOrderPort` (persist an `Order` aggregate), `PublishEventPort` (emit a domain event), `ChargeCardPort` (call the Stripe API). The interface is declared inside the application core; the implementation lives in an infrastructure module and is injected via Spring DI.

The critical rule for driven ports: the interface must describe WHAT the domain needs in domain-meaningful terms, never HOW infrastructure does it. A correct port: `Optional<Customer> loadById(CustomerId id)`. A broken port: `Customer findByIdUsingJpa(Long id, EntityManager em)`. The broken port leaks `EntityManager` — a JPA type — into the application core, which forces the application to depend on `jakarta.persistence-api`, which violates the dependency rule. The same leak happens with `KafkaTemplate`, `RestTemplate`, `RedisTemplate`, `S3Client`, `StripeClient`. The shape of the leak is always the same: an infrastructure type appears in a port method signature.

A second leak is more subtle: returning a JPA-managed entity from a port. If `LoadAccountPort.loadById(id)` returns a `Customer` that is a JPA `@Entity`, the returned object is still attached to the persistence context when the port returns. The domain calls `customer.placeOrder(...)`, which traverses a lazy-loaded `customer.addresses` collection, which fires a `SELECT` outside the transaction, which throws `LazyInitializationException` at runtime. The fix is to map the JPA entity to a pure domain object inside the adapter before returning it — the adapter converts `CustomerJpaEntity` to a `Customer` domain object, detaches it from the persistence context, and the domain never sees the JPA type.

A Spring Boot example of the port and its JPA adapter:

```java
// application/port/out/LoadAccountPort.java  (the port — pure Java)
package com.shop.application.port.out;

public interface LoadAccountPort {
    Optional<Customer> loadById(CustomerId id);
}

// infrastructure/persistence/JpaAccountRepository.java  (the adapter — Spring Data JPA)
package com.shop.infrastructure.persistence;

import com.shop.application.port.out.LoadAccountPort;
import com.shop.domain.*;
import org.springframework.stereotype.Component;

@Component
class JpaAccountRepository implements LoadAccountPort {
    private final CustomerJpaRepository jpa;

    JpaAccountRepository(CustomerJpaRepository jpa) {
        this.jpa = jpa;
    }

    @Override
    public Optional<Customer> loadById(CustomerId id) {
        return jpa.findById(id.value())
                  .map(CustomerJpaEntity::toDomain);   // detach + map to pure Customer
    }
}

// infrastructure/persistence/CustomerJpaEntity.java  (the JPA entity — NOT a domain object)
package com.shop.infrastructure.persistence;

import jakarta.persistence.*;
import com.shop.domain.*;

@Entity
@Table(name = "customers")
class CustomerJpaEntity {
    @Id private String id;
    private String name;
    @Embedded private AddressEmbeddable address;

    static Customer toDomain(CustomerJpaEntity e) {
        return new Customer(new CustomerId(e.id), e.name, e.address.toDomain());
    }
}
```

The `CustomerJpaEntity` lives in the `infrastructure-persistence` module, never in the `domain` module. The `Customer` domain class lives in the `domain` module and has no JPA annotations. The adapter does the mapping both ways: `toDomain()` on the way out, `fromDomain()` on the way in (in the save port). The domain is pure; the persistence layer is contaminated; the two never meet outside the adapter.

The production failure mode is the "leaky port" — a port whose signature includes a framework type. It looks harmless: `Page<Customer> findAll(Pageable pageable)` (Spring Data types in the port). The port now depends on `spring-data-commons`. A future migration to JOOQ or a non-Spring DI container breaks the port. The fix: the port takes plain domain parameters (`List<Customer> findAll(int offset, int limit)`), and the adapter does the `PageRequest.of(offset, limit)` translation. The performance cost is zero; the architectural cost saved is enormous.

### Adapters: Concrete implementations of ports (REST Controllers, JPA Repositories, Kafka Producers)

Adapters are the concrete classes that turn external requests into port calls (driving adapters) or turn port calls into external side effects (driven adapters). They are the outermost ring of the hexagon — the only code that knows about HTTP verbs, JSON serialization, SQL statements, Kafka topics, Stripe API keys, and S3 bucket names. An adapter does three things: (1) translate the external representation (HTTP request, Kafka record, JPA entity) into a domain representation (command, event, aggregate), (2) delegate to the appropriate port, (3) translate the domain result back into the external representation. None of this translation logic belongs in the domain; all of it belongs in the adapter.

The driving adapter pattern is consistent across technologies. A REST controller receives an HTTP request, validates the JSON payload, maps it to a `PlaceOrderCommand` (a record/value object with no framework types), calls `placeOrderUseCase.place(command)`, receives a `PlaceOrderResult`, maps it to a `PlaceOrderResponse` DTO, and returns it. A Kafka consumer receives a `ConsumerRecord<String, String>`, parses the JSON, maps it to a command, calls the same use case. A CLI command parses `argv`, maps it to a command, calls the same use case. The use case does not know which adapter invoked it — it just receives a command and returns a result. This is the swap-REST-for-gRPC promise made concrete.

The driven adapter pattern is the mirror image. A JPA adapter implements `SaveOrderPort` by mapping the `Order` aggregate to an `OrderJpaEntity`, calling `entityManager.persist(orderJpaEntity)`, and returning. A Kafka adapter implements `PublishEventPort` by serializing a domain event to JSON (or Avro, or Protobuf), calling `kafkaTemplate.send("order-events", key, value)`, and returning. A Stripe adapter implements `ChargeCardPort` by mapping a `Money` value to a Stripe `chargeCreateParams.amount()` (integer cents), calling `stripe.charges().create(...)`, mapping the Stripe `Charge` response to a domain `PaymentConfirmation`, and returning. The domain never sees `Charge`, `KafkaTemplate`, or `EntityManager`.

A complete Kafka-driven adapter example:

```java
// application/port/out/PublishEventPort.java
package com.shop.application.port.out;

public interface PublishEventPort {
    void publish(DomainEvent event);
}

// infrastructure/messaging/KafkaEventPublisher.java
package com.shop.infrastructure.messaging;

import com.shop.application.port.out.PublishEventPort;
import com.shop.domain.DomainEvent;
import com.shop.domain.OrderPlaced;
import com.fasterxml.jackson.databind.ObjectMapper;
import org.springframework.kafka.core.KafkaTemplate;
import org.springframework.stereotype.Component;

@Component
class KafkaEventPublisher implements PublishEventPort {
    private final KafkaTemplate<String, String> kafka;
    private final ObjectMapper json;

    KafkaEventPublisher(KafkaTemplate<String, String> kafka, ObjectMapper json) {
        this.kafka = kafka;
        this.json = json;
    }

    @Override
    public void publish(DomainEvent event) {
        String topic   = topicFor(event);
        String payload = serialize(event);
        String key     = event.aggregateId().toString();
        kafka.send(topic, key, payload);
    }

    private String topicFor(DomainEvent event) {
        return switch (event) {
            case OrderPlaced o      -> "order-events";
            case PaymentConfirmed p -> "payment-events";
            default -> throw new IllegalStateException("Unknown event type: " + event.getClass());
        };
    }

    private String serialize(DomainEvent event) {
        try {
            return json.writeValueAsString(event);
        } catch (Exception e) {
            throw new IllegalStateException("Failed to serialize event " + event, e);
        }
    }
}
```

Note the design: the port accepts a `DomainEvent` (a sealed interface in the domain), the adapter does the type-switch and topic-routing, the adapter does the JSON serialization, the adapter holds the `KafkaTemplate`. The domain sees none of this. If you swap Kafka for RabbitMQ tomorrow, you write a new `RabbitEventPublisher` that implements the same port; the domain does not change. If you add a new event type (`OrderShipped`), the domain adds it to the sealed interface; the adapter's `switch` fails to compile (because the sealed interface is exhaustive) until you add a case for `OrderShipped` — the compiler enforces the wiring.

The production failure mode is the "leaky mapper" — an adapter that passes the JPA entity up to the controller without converting to a domain object or DTO. The controller then serializes the JPA entity directly to JSON; the JSON serializer triggers lazy loading on `customer.orders`, fires 50 SQL queries during serialization, takes 800ms instead of 20ms, and either times out the request or saturates the database connection pool. The fix: every adapter must convert to a domain object (driven) or to a response DTO (driving) at the boundary; no framework type may cross the hexagon edge. A simple ArchUnit rule enforces this: `noClasses().that().resideInAPackage("..web..").should().dependOnClassesThat().resideInAPackage("..persistence..")` — the web adapter must not import from the persistence adapter; if it needs data from persistence, it goes through a use case.
