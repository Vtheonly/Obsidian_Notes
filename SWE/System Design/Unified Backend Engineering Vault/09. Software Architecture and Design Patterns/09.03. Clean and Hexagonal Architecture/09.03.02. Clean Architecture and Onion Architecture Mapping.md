# 09.03.02. Clean Architecture and Onion Architecture Mapping

## What This Is

Clean Architecture (Robert C. Martin, 2012) and Onion Architecture (Jeffrey Palermo, 2008) are two presentations of the same underlying insight as Hexagonal: the application's domain is the innermost, most stable code; infrastructure is the outermost, most volatile code; source code dependencies point inward. Where Cockburn drew a hexagon, Martin drew four concentric circles (Entities → Use Cases → Interface Adapters → Frameworks & Drivers), and Palermo drew concentric onion layers (Domain Services → Application Services → UI / Infrastructure). The three patterns are isomorphic: the hexagon's "domain core" is Clean's "Entities + Use Cases" circle, the hexagon's "ports" are Clean's "Interface Adapters" inner edge, the hexagon's "adapters" are Clean's "Interface Adapters" outer edge plus "Frameworks & Drivers."

In this vault's layered mental model, Clean Architecture's circles are the source-code analogue of the runtime layering taught in sections 02–04: just as the kernel does not depend on user-space libraries, the innermost source-code circle does not depend on the outermost. The "Dependency Rule" is the source-code counterpart of the syscall boundary — kernel code may not import libc types, and domain code may not import Spring types. Where Hexagonal focuses on the port/adapter seam, Clean focuses on the dependency-inversion enforcement of that seam. The two patterns are typically used together: hexagonal gives you the vocabulary (port, adapter), Clean gives you the enforcement mechanism (the dependency rule, ArchUnit tests).

This note governs two failure modes: (1) the "fake Clean Architecture" — a project that draws the four circles in a slide deck but has `@Entity` annotations on domain classes, so the dependency rule is violated in source code even though it is honored in the diagram; and (2) the "anemic use case layer" — a project that puts all business logic in service classes that depend on Spring, leaving the "Entities" circle as a bag of getters and setters with no behavior, which means the innermost circle is not the most stable, it is the most boring, and the architectural benefit is lost.

## The Details

### Concentric dependency circles: Entities (Core Domain) → Use Cases (Application Rules) → Interface...

Clean Architecture defines four concentric circles, each strictly enclosing the next. The innermost circle, **Entities**, holds the enterprise business rules: the `Order` aggregate, the `Money` value object, the `Customer` entity. These objects would exist even if there were no application — they are the long-lived business concepts. The next circle, **Use Cases**, holds application business rules: the `PlaceOrderService`, the `CancelOrderService`. These orchestrate entities to accomplish a use case; they would not exist without the application, but they do not depend on the delivery mechanism. The third circle, **Interface Adapters**, holds controllers, presenters, gateways, and repositories — code that converts data between the use-case format and the external format (JSON, SQL rows, Kafka records). The outermost circle, **Frameworks and Drivers**, holds the actual Spring, JPA, Kafka, Stripe SDK — the code you did not write and cannot change.

```text
  Clean Architecture (Robert C. Martin, 2012)
  ──────────────────────────────────────────────────────────────
                     ┌─────────────────────────┐
                     │   Frameworks & Drivers  │  ← Spring, JPA, Kafka, Stripe
                     │  ┌───────────────────┐  │
                     │  │ Interface Adapters│  │  ← Controllers, Presenters, Gateways, Repos
                     │  │  ┌─────────────┐  │  │
                     │  │  │  Use Cases  │  │  │  ← PlaceOrderService, CancelOrderService
                     │  │  │  ┌───────┐  │  │  │
                     │  │  │  │Entities│  │  │  │  ← Order, Money, Customer (pure business)
                     │  │  │  └───────┘  │  │  │
                     │  │  └─────────────┘  │  │
                     │  └───────────────────┘  │
                     └─────────────────────────┘
                                ▲
                                │  dependency direction (always inward)
                                │
   The Dependency Rule: source code dependencies may only point inward,
   toward higher-level policy. No dependency in any layer may name
   something in a more outer layer.
  ──────────────────────────────────────────────────────────────
  Onion Architecture (Jeffrey Palermo, 2008) — same idea, different rings:
  ──────────────────────────────────────────────────────────────
   Domain Services → Application Services → UI / Infrastructure
   (innermost ring holds the domain model + domain services;
    outermost ring holds UI, persistence, messaging, external services.)
```

In a Spring Boot codebase, the four circles map to Maven modules: `domain` (Entities), `application` (Use Cases + port interfaces), `adapter-web` + `adapter-persistence` + `adapter-messaging` (Interface Adapters), `bootstrap` (Frameworks & Drivers — the `@SpringBootApplication` class plus Spring Boot starter dependencies). The `domain` module's `pom.xml` declares no framework dependencies. The `application` module's `pom.xml` declares `domain` and nothing else. The `adapter-*` modules each declare `application` plus their framework dependency (`spring-boot-starter-web`, `spring-boot-starter-data-jpa`, `spring-kafka`). The `bootstrap` module aggregates everything.

| Clean Circle       | Hexagonal Equivalent     | Onion Equivalent      | Maven Module           | Example Classes                                  |
|--------------------|--------------------------|-----------------------|------------------------|--------------------------------------------------|
| Entities           | Domain core              | Domain Model          | `domain`               | `Order`, `Money`, `Customer`, `OrderPlaced`      |
| Use Cases          | Application core + ports | Domain/Application Svc| `application`          | `PlaceOrderService`, `PlaceOrderUseCase` (port)  |
| Interface Adapters | Adapters (driving+driven)| UI / Infra adapters   | `adapter-web`, `adapter-persistence` | `PlaceOrderController`, `JpaOrderRepository`     |
| Frameworks/Drivers | Infrastructure           | Infrastructure        | `bootstrap`            | `@SpringBootApplication`, Spring auto-config     |

The production failure mode is the "fat entity" — a domain class that secretly depends on a framework. The `Order` class is annotated `@Entity` (JPA), `@Table(name="orders")`, `@GeneratedValue(strategy=IDENTITY)` on its `id` field. A Hibernate 5 → 6 upgrade changes the semantics of `@GeneratedValue` (the `GenerationType.AUTO` default switches from `IDENTITY` to `SEQUENCE`), and now every insert into `orders` fails with "sequence does not exist." The fix is to keep the `Order` domain class pure (no JPA annotations) and define a separate `OrderJpaEntity` in the `adapter-persistence` module that the JPA adapter maps to and from. The cost is one extra class per aggregate; the benefit is that a Hibernate upgrade touches only the adapter module, not the domain.

### The Dependency Rule: Source code dependencies must point strictly inward toward higher-level poli...

The Dependency Rule is the single invariant that makes Clean Architecture enforceable: source code dependencies may only point inward. A class in `Use Cases` may import a class in `Entities`. A class in `Interface Adapters` may import a class in `Use Cases` or `Entities`. A class in `Frameworks & Drivers` may import anything. The reverse is forbidden: a class in `Entities` may not import from `Use Cases`, `Interface Adapters`, or `Frameworks & Drivers`. The rule is structural — it governs `import` statements, not runtime calls. A runtime call from `Entities` to `Frameworks` (e.g. an entity logging via SLF4J) is permitted because SLF4J is an abstraction; an `import org.springframework.*` in an entity is forbidden because Spring is the framework.

The enforcement mechanism in a Spring Boot project is twofold. First, the Maven multi-module build: each module declares only its allowed dependencies, so an `import org.springframework.web.bind.annotation.RestController` in the `domain` module fails at compile time because `spring-boot-starter-web` is not on the classpath. Second, an ArchUnit test that codifies the rule as a JUnit assertion. ArchUnit parses the compiled `.class` files and checks the dependency graph against rules:

```java
// src/test/java/com/shop/arch/DependencyRuleTest.java
import com.tngtech.archunit.junit.AnalyzeClasses;
import com.tngtech.archunit.junit.ArchTest;
import com.tngtech.archunit.lang.ArchRule;
import static com.tngtech.archunit.lang.syntax.ArchRuleDefinition.*;

@AnalyzeClasses(packages = "com.shop")
class DependencyRuleTest {

    @ArchTest
    static final ArchRule domainMustNotDependOnApplication =
        noClasses().that().resideInAPackage("..domain..")
                   .should().dependOnClassesThat().resideInAPackage("..application..");

    @ArchTest
    static final ArchRule domainMustNotDependOnSpring =
        noClasses().that().resideInAPackage("..domain..")
                   .should().dependOnClassesThat().resideInAPackage("..org.springframework..");

    @ArchTest
    static final ArchRule domainMustNotDependOnJpa =
        noClasses().that().resideInAPackage("..domain..")
                   .should().dependOnClassesThat().resideInAPackage("..jakarta.persistence..");

    @ArchTest
    static final ArchRule applicationMustNotDependOnWeb =
        noClasses().that().resideInAPackage("..application..")
                   .should().dependOnClassesThat().resideInAPackage("..web..");

    @ArchTest
    static final ArchRule webMustNotDependOnPersistence =
        noClasses().that().resideInAPackage("..web..")
                   .should().dependOnClassesThat().resideInAPackage("..persistence..");

    @ArchTest
    static final ArchRule useCasesMustImplementPorts =
        classes().that().resideInAPackage("..application.usecase..")
                 .and().areAnnotatedWith("..UseCase..")
                 .should().implementAnInterfaceThat().resideInAPackage("..application.port.in..");
}
```

Run on every `mvn test`, these rules fail the build the moment a developer adds a forbidden import. The test is cheap (under 1 second for a typical codebase), it surfaces violations in the PR that introduced them, and it makes the dependency rule a continuous invariant rather than an architectural aspiration.

The Dependency Inversion Principle (the "D" in SOLID) is the mechanism by which the dependency rule is upheld at the boundary between Use Cases and Interface Adapters. A use case needs to load an aggregate; if it directly depended on `JpaOrderRepository`, it would transitively depend on JPA, violating the rule. Instead, the use case depends on an interface `LoadOrderPort` declared in the `application` package, and the JPA adapter implements that interface. The interface is in the inner circle, the implementation is in the outer circle, and the dependency direction is preserved: the outer circle's class depends on the inner circle's interface (DIP), never the reverse. Spring's DI container wires the adapter into the use case at runtime — the runtime call direction is use-case → adapter, but the compile-time dependency direction is adapter → use-case (via the interface).

The production failure mode is a "circular dependency at compile time." A developer adds `@Autowired` to a domain entity (perhaps to inject an `EventPublisher` so the entity can publish events itself), and Spring throws `BeanCurrentlyInCreationException` because the entity is created by JPA's `EntityManager.find()` (which `new`s the entity reflectively, outside Spring's container) and so cannot be Spring-managed. The fix is to publish events from the use case or application service, not from the entity: the entity records the event in an internal list (`order.recordEvent(new OrderPlaced(...))`), the use case extracts the list (`order.pullEvents()`) after calling `order.place()`, and the use case publishes them via the `PublishEventPort`. The entity stays pure; the event publication is the use case's responsibility.
