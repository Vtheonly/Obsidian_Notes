# 00.01. Master Architectural Mental Model

## What This Is

This note is the **load-bearing mental model** of the entire vault. Every other note — every operating-system primitive in section 02, every networking layer in section 03, every runtime concurrency model in section 04, every framework abstraction in section 05, every persistence mechanism in section 06 — is a zoomed-in view of one slice of the picture drawn here. If you read only one note in the vault, read this one. If you cannot recite the four H3 sub-sections below from memory, the rest of the vault will not make sense.

The model has four faces, each of which is a different way of looking at the same underlying machine. The **Universal Request-Response Pipeline** is the temporal view: a single HTTP request as it travels through space and time, from the NIC's DMA ring buffer at t=0 to the response byte leaving the same NIC at t=20µs (or t=200ms if you hit the database). The **compute/network/storage plane decomposition** is the spatial view: every backend system, no matter how complex, decomposes into three orthogonal planes that you tune independently. **Systems Invariance** is the comparative view: why Spring Boot, Express, Django, Flask, and Laravel are syntactic translations of the same five syscalls. The **layered abstraction hierarchy** is the stratigraphic view: Silicon → Kernel → Syscalls → Runtimes → Frameworks, with each layer hiding the one below it. Learn to see all four faces simultaneously — that is what "having a mental model" means.

## The Details

### The Universal Request-Response Pipeline: From physical NIC to application code and back

Every HTTP request your backend has ever served has traveled through the same thirteen stages, in the same order. The framework you used (Spring Boot, Express, Django, Flask, Laravel) only changes stage 7 — the handler invocation — and the syntax of stages 5 and 6 (routing and middleware). Stages 1–4 and 9–13 are operating-system and hardware mechanisms that the framework cannot touch. Here is the full pipeline for a single `GET /api/users/42` against a Spring Boot server on a typical x86_64 Linux box with an Intel X710 NIC, kernel 6.1, JVM 21, and a Postgres backend on the same host. Latencies are p50 single-request numbers measured on warm caches; throughput-mode numbers under load are very different.

```text
                                                                                         Latency
                                                                                         (µs)
  [1] NIC RX interrupt ── DMA writes frame into rx_ring ───────────────────────────────     0.3
       │                                                                                  │
  [2] Kernel softirq (NET_RX) ── packet climbs netfilter → TCP stack ──────────────────     0.8
       │   TCP reassembles segments, ACKs the peer, writes into sk_buff                   │
       │                                                                                  │
  [3] TCP layer delivers bytes into socket receive buffer (sk->sk_rmem_alloc) ───────     1.5
       │   default rmem_default = 212 992 bytes, max rmem_max = 212 992                   │
       │                                                                                  │
  [4] Framework's reactor thread (epoll_wait on fd 23) wakes up ─────────────────────     2.0
       │   Java: Netty NioEventLoop / Tomcat NioEndpoint poller                          │
       │                                                                                  │
  [5] recv(fd, buf, len, 0) syscall ── copies bytes from kernel sk_buff ──────────────     3.0
       │   to user-space byte[] (or ByteBuffer.direct if zero-copy)                       │
       │                                                                                  │
  [6] HTTP parser (Netty HttpServerCodec / Tomcat Http11Processor) ───────────────────     5.0
       │   decodes request line, headers, chunked body                                    │
       │                                                                                  │
  [7] Router: DispatcherServlet.handlerMapping → UserController.get(42) ──────────────    10.0
       │   + interceptor chain (Spring Security filter, logging, tracing)                │
       │                                                                                  │
  [8] Controller calls UserService.find(42) → JPA Repository → JDBC ───────────────────   ~600
       │   Postgres call: socket connect (already pooled) → wire protocol                │
       │   → server parse → index lookup → tuple fetch → wire reply                      │
       │                                                                                  │
  [9] Return value serialized to JSON (Jackson ObjectMapper) ─────────────────────────     8.0
       │                                                                                  │
[10] HTTP response encoded (Http11Processor) ─────────────────────────────────────────     2.0
       │                                                                                  │
[11] send(fd, buf, len, MSG_NOSIGNAL) → kernel allocates sk_buff, copies from ───────     3.0
       │   user-space byte[] into sk_buff, queues to socket write buffer                  │
       │                                                                                  │
[12] TCP segments transmitted, NIC TX ring drained, DMA pushes bytes onto wire ───────     1.0
       │                                                                                  │
[13] NIC TX completion interrupt, skb freed, client receives response ───────────────     1.5
                                                                                         ──────
                                                                Total ≈ 640 µs (mostly step 8)
```

The pipeline is **asymmetric**: the response half (steps 9–13) is structurally a mirror of the request half (steps 1–5), but the *cost* is not mirrored — the request half is dominated by kernel and network-stack work (a few microseconds total), while the response half is dominated by serialization (Jackson reflection over entity graphs is brutally slow) and kernel TCP segmentation. The single biggest line item is step 8, the database round-trip — which is why every backend framework spends enormous effort on connection pooling, prepared-statement caching, and ORM N+1 prevention. The single most common production failure is **stage 4 blocking**: if your reactor thread pool (Tomcat's 200-thread default pool, or the Netty EventLoopGroup) is exhausted by slow handlers, the kernel keeps accepting connections into the socket accept queue (`somaxconn`, default 4096 on modern kernels, often still 128 on older distros) but no `accept()` is ever called, and clients see 502 from the reverse proxy after 60 seconds.

The second most common failure is **stage 3 buffer exhaustion**: a slow client that opens a connection but reads the response slowly causes the socket write buffer (`sk->sk_wmem_alloc`, default `wmem_default` = 16 384 bytes, `wmem_max` = 4 128 256 bytes) to fill, at which point `send()` blocks (in blocking mode) or returns `EAGAIN` (in non-blocking mode). If the framework's reactor then backpressures correctly, the connection sits in `ESTABLISHED` state with data queued; if it does not (a classic Netty `ChannelOption.AUTO_READ` misconfiguration), the JVM heap fills with `ByteBuf` instances waiting to be flushed, and you OOM at 4 GB even though your heap is set to 8 GB. The fix is to know that **the pipeline's stages are not independent** — backpressure at stage 11 must propagate back to stage 7 (handler must stop producing) and ultimately to stage 4 (the reactor must stop reading from the client). Every well-engineered framework implements this propagation; every poorly-engineered one has a CVE waiting to happen.

### Structural decomposition of the compute, network, and storage planes

Any backend system, regardless of scale — from a single Rails monolith on a $5 VPS to a 10 000-pod Kubernetes fleet backing a hyperscaler — can be decomposed into three orthogonal planes that you reason about, tune, and scale independently. This is the **only** decomposition that matters for capacity planning and incident triage; layer decompositions (frontend/backend/database) are organizational, not architectural.

```text
┌─────────────────────────── COMPUTE PLANE ───────────────────────────┐
│  What runs your code.                                               │
│  • Process model: JVM, V8, CPython, PHP-FPM workers                 │
│  • Threads / event loops: Tomcat NIO 200 threads, libuv 4 threads,  │
│    gevent greenlets, PHP-FPM static/dynamic pool                    │
│  • GC behaviour: G1, ZGC, V8 Orinoco, CPython refcount + GIL       │
│  • Schedulers: cfs, EEVDF, container cpu.shares, k8s requests       │
│  Capacity unit: CPU-seconds, vCPUs, millicores                      │
│  Failure mode: thread pool exhaustion, GC pause storms, OOM kill    │
│  Metric: cpu_usage, run_queue_depth, gc_pause_ms, rss_bytes         │
└─────────────────────────────────────────────────────────────────────┘

┌─────────────────────────── NETWORK PLANE ───────────────────────────┐
│  What moves bytes between processes.                                │
│  • L2/L3: NIC, kernel routing table, iptables, conntrack table      │
│  • L4: TCP/UDP, socket buffers (rmem/wmem), TIME_WAIT bucket        │
│  • L7: HTTP/1.1 keepalive, HTTP/2 multiplexed streams, gRPC, TLS    │
│  • Service mesh: Envoy, Linkerd, mTLS sidecars                      │
│  Capacity unit: bits/second, packets/second, concurrent connections │
│  Failure mode: conntrack table full, TIME_WAIT exhaustion, TLS      │
│    handshake CPU saturation, head-of-line blocking in HTTP/1.1      │
│  Metric: nic_rx_bytes, tcp_retranssegs, estab_conns, p99_rtt        │
└─────────────────────────────────────────────────────────────────────┘

┌─────────────────────────── STORAGE PLANE ───────────────────────────┐
│  What persists state across process restarts.                       │
│  • Block: page cache, fsync, O_DIRECT, NVMe queues                  │
│  • Filesystems: ext4, XFS, ZFS — journaling, CoW, ARC               │
│  • Databases: Postgres WAL + shared_buffers, MySQL InnoDB buffer    │
│    pool, Redis AOF + RDB, RocksDB LSM tree                          │
│  • Object stores: S3 (eventually consistent list), GCS, MinIO       │
│  Capacity unit: bytes, IOPS, sustained MB/s                         │
│  Failure mode: fsync latency spikes, WAL bloat, replication lag,    │
│    LSM compaction storms, S3 5xx during multi-AZ failover           │
│  Metric: disk_io_time, fsync_us, wal_bytes, repl_lag_seconds        │
└─────────────────────────────────────────────────────────────────────┘
```

The planes are **independent at tuning time** but **coupled at failure time**. You can add vCPUs to the compute plane without touching the network or storage plane. You can scale reads by adding Postgres replicas (storage plane) without changing your application servers (compute). You can front the whole system with a CDN (network plane) and your code does not change. But when the storage plane stalls — say, a Postgres `fsync` latency spike from 200µs to 50ms because the WAL is on a saturated EBS volume — the compute plane's thread pool drains within seconds (every handler is waiting on a JDBC query), the network plane's connection count climbs as new requests pile up, and you have a cascade failure across all three planes. The same cascade happens in reverse when the network plane stalls: connections back up, handler threads block on socket reads, the storage plane sees a sudden drop in load (because nothing is reaching it) and the on-call engineer gets paged for "database is down" when the database is perfectly fine.

The decomposition is the right mental model because it tells you **where to put the capacity, where to put the bulkhead, and where to look first when p99 latency spikes**. Rule of thumb: if p99 latency spikes but p50 is unchanged, the problem is on the network plane (a tail-latency issue — TLS renegotiation, conntrack eviction, GC pause on a sidecar). If p50 and p99 both spike together, the problem is on the compute or storage plane (CPU saturation, disk contention, lock contention). If you see increased error rates but unchanged latency, the problem is on the storage plane's consistency boundary (a uniqueness constraint, a deadlock, a replication conflict). This taxonomy eliminates 80% of the "we don't know what's wrong" incidents in the first five minutes.

### Systems Invariance: Why frameworks are syntactic translations of identical operating system mecha...

Systems Invariance is the empirical observation that **every mainstream backend framework ultimately calls the same six POSIX syscalls to do its job**: `socket()`, `bind()`, `listen()`, `accept()`, `recv()`/`read()`, `send()`/`write()`, plus `epoll_wait()` (Linux) or `kqueue()` (macOS/BSD) or `IOCP` (Windows) for multiplexing. Spring Boot's `Tomcat NioEndpoint`, Express's Node `http.Server` (which calls libuv's `uv_tcp_t`), Django's `WSGIServer` via `socketserver`, Flask's Werkzeug development server, and Laravel's `php artisan serve` (which under Octane + Swoole uses an event loop) all bottom out at the same kernel calls. The framework's job is to *wrap* those calls in nicer abstractions — request objects, middleware chains, DI containers, JSON serializers — but it cannot *replace* them, because the kernel owns the socket and the NIC.

Concrete example: when you call `app.get('/users/:id', handler)` in Express, you are registering a route in a JavaScript map. When a request arrives, libuv's event loop (running on the `uv__io_poll` backend, which on Linux is `epoll_wait`) wakes up the main thread, which calls `uv__stream_io` → `uv_read_start` → eventually `read(fd, buf, len)` on the listening socket's accepted child socket. The bytes flow into a V8 `Uint8Array` backing store, the HTTP parser (Node's `llhttp`) decodes them into a `request` object, the router matches the path, your handler runs, `res.json(...)` calls `JSON.stringify` and `write(fd, buf, len)` to push the response back through the kernel. The Java equivalent in Spring Boot: `NioEndpoint.Poller` runs `Selector.select()` (which is `epoll_wait` under the hood via the JDK's `EPollSelectorImpl`), an `NioChannel` is created from `SocketChannel.accept()`, the `Http11Processor` parses the bytes via the internal `HttpParser`, the `DispatcherServlet` dispatches to your `@GetMapping` method, the return value is serialized by Jackson, and `OutputBuffer.write` calls `NioChannel.write` → `SocketChannel.write` → eventually `sendto(fd, buf, len, ...)`. Different language, different runtime, different framework — **identical kernel calls in identical order**.

The implication is profound: **when a framework feature seems magical, it is always wrapping a syscall you can observe.** Spring's `@Transactional`? It opens a JDBC connection from the HikariCP pool, issues `BEGIN`, runs your code, and either `COMMIT` or `ROLLBACK` — all three are SQL commands sent over a `send()` on a socket to Postgres, which itself is doing `write()` to its WAL file before responding. Django's ORM `select_related`? It rewrites a single SQL `LEFT JOIN` query that the database executes via its planner, reading from shared_buffers (which is `mmap`'d anonymous memory) or falling back to `pread()` on the table file. Laravel's `Queue::dispatch`? It serializes the job via PHP's `serialize()`, opens a connection to Redis (a `connect()` syscall), and sends a `LPUSH jobs "{\"...\"}"` — Redis then forks a worker (via `fork()` + `execve()` if a background process is needed, or processes inline in its single-threaded event loop). Every abstraction in every framework is a thin wrapper over a syscall you can see with `strace -p <pid>`.

This invariance is what makes the **Δ-translation pass** possible. Once you have learned, deeply, how Spring Boot implements request handling — HikariCP pools 10 connections, Tomcat's `maxThreads` is 200, the `DispatcherServlet` runs through 8 stages of resolver → handler mapping → handler adapter → interceptor pre → handler → interceptor post → view resolver → response writer — translating that knowledge to Express is a matter of mapping each stage to its libuv/Node equivalent: the connection pool becomes `pg`'s `Pool` (default 10), the thread pool becomes the single event loop with `uv_default_loop()`, the dispatcher becomes the middleware chain `(req, res, next) => next()`, the handler adapter becomes direct function invocation, the interceptor chain becomes `app.use(middleware)` calls, and the view resolver becomes `res.json()`. **The stages are the same stages; only the names change.** The same is true for Django (WSGI -> ASGI translation is the only material difference), Flask (Werkzeug `Map.bind()` does the routing), and Laravel (the `Kernel` runs a `Pipeline` of middleware around a `Router` dispatch). The job of section 05 of the vault is to make this invariance *visible* — once you see it, you cannot unsee it, and every new framework becomes a 4-hour exercise instead of a 4-week one.

### The layered abstraction hierarchy: Silicon → Kernel → System Calls → Runtimes → Application Frame...

The vault is structured around a five-layer abstraction stack. Each layer **provides** specific capabilities to the layer above and **hides** specific complexity from the layer below. Knowing which layer owns a given concern is the difference between fixing a bug in 5 minutes and chasing it for 5 days.

```text
┌─────────────────────────────────────────────────────────────────────────┐
│  L5  APPLICATION FRAMEWORKS                                             │
│      Spring Boot, Express, Django, Flask, Laravel                       │
│      Provides: routing, middleware, DI, validation, ORM, serialization  │
│      Hides: HTTP parsing, socket I/O, thread lifecycle, JSON parsing    │
│      Failure: framework-specific (e.g. Spring circular DI, Express      │
│      middleware ordering, Django migration conflicts)                   │
├─────────────────────────────────────────────────────────────────────────┤
│  L4  RUNTIMES                                                           │
│      JVM (HotSpot), V8/Node, CPython, PHP/Zend                          │
│      Provides: GC, JIT, threads/green threads, FFI, stdlib              │
│      Hides: memory layout, register allocation, syscall invocation,     │
│      ABI calling conventions                                            │
│      Failure: GC pauses, JIT deoptimization, GIL contention,            │
│      PHP-FPM worker exhaustion                                          │
├─────────────────────────────────────────────────────────────────────────┤
│  L3  SYSTEM CALLS (POSIX surface)                                       │
│      socket, bind, listen, accept, recv, send, epoll_wait,              │
│      open, read, write, fsync, mmap, fork, execve, futex                │
│      Provides: the entire user-space API to kernel services             │
│      Hides: kernel-internal data structures (task_struct, files_struct, │
│      sk_buff, inode, page cache radix tree)                             │
│      Failure: EBADF, ENOMEM, EMFILE, EAGAIN, ETIMEDOUT, ECONNRESET      │
├─────────────────────────────────────────────────────────────────────────┤
│  L2  KERNEL                                                             │
│      Linux: scheduler (CFS/EEVDF), TCP/IP stack (tcp_input.c),          │
│      VFS, page cache, ext4/XFS, netfilter, conntrack, namespaces,       │
│      cgroups                                                            │
│      Provides: process isolation, file abstraction, networking stack,   │
│      memory management, device drivers                                  │
│      Hides: hardware registers, DMA rings, interrupt routing, MMU       │
│      page tables, TLB management, NUMA topology                         │
│      Failure: OOM killer, soft lockup, kernel panic, conntrack table    │
│      exhaustion, page cache thrashing                                   │
├─────────────────────────────────────────────────────────────────────────┤
│  L1  SILICON                                                            │
│      CPU cores (P-cores/E-cores), L1/L2/L3 caches, DRAM, NVMe SSDs,    │
│      NICs with DMA, NUMA interconnects (UPI, Infinity Fabric)           │
│      Provides: computation, storage, network I/O as physical operations │
│      Hides: nothing — this is the bottom                                │
│      Failure: thermal throttling, ECC-correctable bit flips, NIC        │
│      firmware bugs, NVMe wear-out, NUMA imbalance                       │
└─────────────────────────────────────────────────────────────────────────┘
```

Layer L5 is what you write code against and what most engineers spend their entire career inside. It is also the layer where **most debugging effort is wasted** because the bug is rarely there — when your Spring Boot app returns 500, the cause is usually in L4 (a JVM `OutOfMemoryError` from a heap set too small for the working set), L3 (a ` Too many open files` because `ulimit -n` is 1024 and Tomcat is leaking file descriptors), or L2 (the conntrack table filled because a misconfigured sidecar is opening connections per request). The discipline the vault teaches is: **when L5 fails, look down, not across.** Spring's `@Async` pool sizing is wrong? Look at L4 (the JVM's `ForkJoinPool` and thread scheduling). Express is dropping requests? Look at L3 (`ulimit -n`, `ECONNRESET` from `accept()` failing with `EMFILE`). Django migrations are slow? Look at L2 (the database's `shared_buffers`, the disk's `fsync` latency on the WAL device).

The boundaries between layers are **leaky by design**. A JVM GC pause (L4) shows up as a TCP retransmission storm (L2) because the kernel times out waiting for an ACK from the JVM's socket. A NIC firmware bug (L1) shows up as 502s from your reverse proxy (L5). An `fsync` that takes 50ms (L2) shows up as a Spring `@Transactional` method taking 50ms longer (L5). The vault's strategy is to make those leaks **observable** rather than invisible — every section after this one is, in part, about which tool exposes which leak: `strace` for L3, `perf` for L2, async-profiler for L4, the framework's own metrics for L5. Once you can see the leak, you can fix the root cause. Without the layered model, you are left applying framework-level workarounds (more retries, bigger pools, more caching) that paper over the symptom while the underlying L1/L2/L3 problem continues to degrade. This is the failure mode that kills production systems slowly and silently.

## Key Takeaways

1. **The Universal Request-Response Pipeline is thirteen stages, not three.** If you can only name "client → server → database," you are missing nine places where things break. Memorize the pipeline in [[00.01. Master Architectural Mental Model]] — every later note in the vault assumes you can.
2. **The compute/network/storage plane decomposition is the only decomposition that matters for incident triage.** When latency spikes, the first question is "which plane?" — and the answer dictates which metric to look at next.
3. **Systems Invariance is what makes the Δ-translation pass possible.** Every framework is a thin wrapper over the same six syscalls. The magic is always wrapping a syscall you can observe with `strace`.
