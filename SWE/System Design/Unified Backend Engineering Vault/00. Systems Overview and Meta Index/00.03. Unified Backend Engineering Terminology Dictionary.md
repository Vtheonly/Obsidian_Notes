# 00.03. Unified Backend Engineering Terminology Dictionary

## What This Is

This note is the **fixed lexicon** of the vault. Every downstream note — every operating-system concept in section 02, every networking concept in section 03, every persistence concept in section 06, every distributed-systems concept in section 08 — uses the terms defined here without re-defining them. The vault's claim is that backend engineering has a *small* core vocabulary (~30 terms) that, once internalized, lets you read code in any ecosystem and immediately understand which concept is being expressed. The glossary below is that core vocabulary. It is organized into three H3 sub-sections: the **universal lexicon** (the 30 terms themselves, each with a paragraph that defines the mechanism and points at the failure mode it exists to prevent), a **disambiguation index** (the cross-framework naming conflicts — what Laravel calls "middleware" is not what Express calls "middleware", and the difference matters), and a set of **formal engineering definitions** (state, idempotency, side effects, blocking vs. non-blocking, synchronous vs. asynchronous) that are notoriously misused in tutorials and that the vault uses in their precise formal sense throughout.

When a downstream note uses a term you cannot instantly define, the definition is here. When two ecosystems use the same word for different concepts, the disambiguation is here. When a downstream note describes a function as "synchronous" or "idempotent", the formal meaning is here. Bookmark this note — you will return to it more often than any other in section 00.

## The Details

### Universal lexicon of networking, operating systems, concurrency, database engines, and distribute...

The 30 terms below are grouped by the layer of the [[00.01. Master Architectural Mental Model|master layered model]] they belong to. Each definition names the mechanism, the layer, and the failure mode the term exists to prevent. Read the table once end-to-end; thereafter use it as a lookup.

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│  OPERATING SYSTEM / KERNEL LAYER  (vault section 02)                        │
├─────────────────────────────────────────────────────────────────────────────┤
│  socket              Kernel object pairing a file descriptor with a         │
│                      bidirectional byte stream. Created by socket(2).       │
│                      Failure if ignored: you cannot tune buffers, and       │
│                      "Too many open files" (EMFILE) will surprise you.      │
│                                                                             │
│  file descriptor     Integer index into the per-process files_struct.       │
│                      0/1/2 = stdin/out/err; 3+ = sockets, pipes, files.    │
│                      Default ulimit -n is 1024 on most distros — your      │
│                      framework will exhaust this under load unless you      │
│                      raise it to 65 535+ in /etc/security/limits.conf.     │
│                                                                             │
│  page cache          Kernel RAM cache of recently-read disk pages, 4 KiB    │
│                      each on x86_64. Reads via pread() hit the cache;       │
│                      misses trigger disk I/O. Writes accumulate as dirty    │
│                      pages until writeback (max 30s, vm.dirty_writeback).   │
│                      Failure if ignored: "fsync is slow" because the        │
│                      disk is actually flushing 200 MB of dirty pages,       │
│                      not your 4 KiB write.                                  │
│                                                                             │
│  fsync(fd)           Syscall forcing dirty pages for fd to be flushed to    │
│                      stable storage. Returns only after the device has     │
│                      acknowledged the write is durable. p99 latency on      │
│                      NVMe: 100µs–1ms; on EBS gp3: 1–50ms; on spinning      │
│                      rust: 5–20ms. Failure if ignored: data loss on        │
│                      power failure (your COMMIT lied to the client).        │
│                                                                             │
│  mmap                Maps a file into the process address space. Reads      │
│                      become memory loads; page faults trigger disk I/O.    │
│                      Used by Postgres for shared_buffers, by Kafka for      │
│                      the log segment cache, by RocksDB for SSTable reads.   │
│                      Failure if ignored: page-fault storms masquerading     │
│                      as GC pauses.                                          │
│                                                                             │
│  futex               Fast user-space mutex. The common case (uncontended    │
│                      lock) is resolved entirely in user space via atomic    │
│                      ops; only on contention does it call into the kernel   │
│                      via futex(2). Underlies every JVM ReentrantLock and    │
│                      every pthread_mutex_t. Failure if ignored: lock        │
│                      contention shows up as sys% CPU, not user%.            │
├─────────────────────────────────────────────────────────────────────────────┤
│  NETWORKING LAYER  (vault section 03)                                       │
├─────────────────────────────────────────────────────────────────────────────┤
│  TIME_WAIT           TCP state after active close, lasting 2*MSL (~60s on   │
│                      Linux, configurable via net.ipv4.tcp_fin_timeout).     │
│                      Exists so late packets can be safely discarded.        │
│                      Failure if ignored: client-side port exhaustion        │
│                      under high request rate (net.ipv4.ip_local_port_range  │
│                      = 28 232 usable ports; at 1000 RPS with 60s TIME_WAIT  │
│                      you saturate at 470 RPS — the 530 RPS gap fails).      │
│                                                                             │
│  conntrack           Kernel connection-tracking table for NAT. Default     │
│                      size net.netfilter.nf_conntrack_max = 65 536. When     │
│                      full, new connections are dropped with the famous       │
│                      log "nf_conntrack: table full, dropping packet".       │
│                      Failure if ignored: random connection drops under      │
│                      load, only visible in dmesg.                          │
├─────────────────────────────────────────────────────────────────────────────┤
│  DATABASE ENGINE LAYER  (vault section 06)                                  │
├─────────────────────────────────────────────────────────────────────────────┤
│  WAL                 Write-Ahead Log. Every modification is appended to     │
│                      the WAL *before* the data file is touched. On crash,   │
│                      the WAL is replayed forward from the last checkpoint.  │
│                      Postgres: pg_wal/WAL segment files (default 16 MB).    │
│                      MySQL: ib_logfile. RocksDB: .log files.                │
│                      Failure if ignored: silent data loss after crash.     │
│                                                                             │
│  MVCC                Multi-Version Concurrency Control. Each row write      │
│                      creates a new tuple version (xmin/xmax in Postgres).   │
│                      Readers see a snapshot consistent with their           │
│                      transaction's start time, never blocking writers.      │
│                      Failure if ignored: vacuum bloat in Postgres when      │
│                      dead tuples accumulate, lock-escalation storms in      │
│                      databases without MVCC.                                │
│                                                                             │
│  ACID                Atomicity (all-or-nothing via undo log + WAL),         │
│                      Consistency (constraints enforced post-commit),        │
│                      Isolation (concurrent txns appear serial — see         │
│                      isolation level below), Durability (fsync on WAL       │
│                      before COMMIT returns). The four properties a          │
│                      transactional database must provide.                   │
│                      Failure if ignored: partial writes, lost updates,     │
│                      non-repeatable reads, dirty reads.                     │
│                                                                             │
│  isolation level     READ UNCOMMITTED (dirty reads allowed), READ           │
│                      COMMITTED (no dirty reads, non-repeatable reads        │
│                      allowed — Postgres default), REPEATABLE READ (no       │
│                      non-repeatable reads, phantoms allowed — MySQL         │
│                      InnoDB default), SERIALIZABLE (no phantoms, but        │
│                      performance cost). Failure if ignored: lost updates    │
│                      in concurrent counters, double-spends, race           │
│                      conditions in financial code.                          │
├─────────────────────────────────────────────────────────────────────────────┤
│  DISTRIBUTED SYSTEMS LAYER  (vault section 08)                              │
├─────────────────────────────────────────────────────────────────────────────┤
│  CAP                 Consistency / Availability / Partition-tolerance.     │
│                      Pick two; in a real network you cannot drop P, so      │
│                      the choice is C or A during a partition. CP systems    │
│                      (e.g. Zookeeper, etcd, HBase) reject requests;        │
│                      AP systems (e.g. Cassandra, DynamoDB) return           │
│                      potentially-stale data.                                │
│                      Failure if ignored: choosing AP for a billing         │
│                      system; choosing CP for a social feed.                │
│                                                                             │
│  consensus           Algorithm for getting N nodes to agree on a single     │
│                      value despite crashes and unreliable networks.         │
│                      Raft (etcd, Consul, TiKV) and Paxos (Spanner,         │
│                      Chubby) are the two main families. Requires a         │
│                      majority quorum (N/2 + 1).                             │
│                      Failure if ignored: split-brain during network         │
│                      partition, dual-writes causing divergent state.        │
│                                                                             │
│  idempotency         f(f(x)) == f(x). An operation that can be repeated    │
│                      with the same effect as a single application.          │
│                      HTTP PUT is idempotent; POST is not. Critical for      │
│                      retries: only idempotent operations can be safely      │
│                      retried without risk of double-application.            │
│                      Failure if ignored: double-charged credit cards on     │
│                      retry, duplicate user rows.                            │
│                                                                             │
│  exactly-once        Delivery semantics where each message is applied to    │
│                      state exactly once, despite retries. Implemented      │
│                      via idempotent producers + transactional consumers     │
│                      (Kafka 0.11+ idempotent producer + transactional       │
│                      consumer offset commit). Strictly speaking,            │
│                      "exactly-once" is *effectively-once* — the message    │
│                      may be delivered multiple times on the wire, but      │
│                      applied to state once.                                 │
│                      Failure if ignored: duplicate side effects            │
│                      (charged twice, emailed twice).                        │
│                                                                             │
│  at-least-once       Delivery semantics where each message is applied at    │
│                      least once, possibly more. The default for most       │
│                      message queues (RabbitMQ, SQS, Kafka without          │
│                      idempotent producer). Requires the consumer to be      │
│                      idempotent.                                            │
│                      Failure if ignored: duplicate writes when the         │
│                      consumer is not idempotent.                            │
│                                                                             │
│  at-most-once        Delivery semantics where each message is applied at    │
│                      most once, possibly zero times. Achieved by            │
│                      fire-and-forget with no retry. Useful only for         │
│                      telemetry and metrics where loss is tolerable.         │
│                      Failure if ignored: lost orders, lost payments.       │
│                                                                             │
│  outbox              Pattern: instead of writing to a database AND          │
│                      publishing to a queue (dual-write problem, where      │
│                      one can succeed and the other fail), write the         │
│                      message into an outbox table IN THE SAME database      │
│                      transaction as the state change. A separate process    │
│                      polls the outbox and publishes to the queue.           │
│                      Failure if ignored: inconsistency between DB and       │
│                      queue — messages lost or sent for rolled-back txns.   │
│                                                                             │
│  CDC                 Change Data Capture. Streaming the database WAL or     │
│                      binlog to external consumers. Debezium + Kafka is      │
│                      the canonical stack. Solves the dual-write problem     │
│                      without an outbox table.                               │
│                      Failure if ignored: dual-write inconsistencies,        │
│                      tight coupling between services.                       │
│                                                                             │
│  saga                Distributed-transaction pattern: a long-running        │
│                      transaction is broken into a sequence of local        │
│                      transactions, each with a compensating action. No      │
│                      global lock; eventual consistency. Two flavors:        │
│                      choreography (events) and orchestration (central       │
│                      coordinator).                                          │
│                      Failure if ignored: 2PC (two-phase commit) locking    │
│                      across services, killing availability.                │
│                                                                             │
│  CQRS                Command Query Responsibility Segregation. Separate    │
│                      write model (commands) from read model (queries).     │
│                      Writes go through a normalized domain model; reads     │
│                      come from denormalized projections updated via         │
│                      events.                                                │
│                      Failure if ignored: read amplification killing the    │
│                      write path, or vice versa.                             │
│                                                                             │
│  event sourcing      Persisting state as a sequence of immutable events    │
│                      rather than mutable snapshots. Current state is the    │
│                      left-fold of the events. Enables time-travel           │
│                      debugging, audit, and CQRS.                            │
│                      Failure if ignored: write amplification, snapshot      │
│                      compaction needed to bound replay time.                │
├─────────────────────────────────────────────────────────────────────────────┤
│  RESILIENCE LAYER  (vault section 11)                                       │
├─────────────────────────────────────────────────────────────────────────────┤
│  backpressure        Upstream signal that a downstream component cannot      │
│                      accept more input. In TCP: the receive window          │
│                      shrinking to 0. In Reactive Streams: Subscription.     │
│                      request(n). In Node streams: readable.pause().         │
│                      Failure if ignored: OOM as buffers fill, cascade       │
│                      failure across the system.                             │
│                                                                             │
│  circuit breaker     Pattern: a proxy between caller and callee that        │
│                      opens after N consecutive failures, fast-failing       │
│                      for a cooldown period, then half-opens to probe.       │
│                      Resilience4j, Hystrix (deprecated), opossum (Node),    │
│                      django-circuit-breaker, laravel-circuit-breaker.       │
│                      Failure if ignored: cascade failure when a downstream  │
│                      is degraded — every caller ties up threads waiting.    │
│                                                                             │
│  bulkhead            Pattern: isolate resources (thread pools, connection   │
│                      pools) per tenant or per downstream so that a         │
│                      failure in one does not exhaust the resources of       │
│                      another. Named after ship compartments.                │
│                      Failure if ignored: a slow payment service starves    │
│                      the auth service of threads.                           │
│                                                                             │
│  retry               Re-attempting a failed operation. Safe only for        │
│                      idempotent operations. Without exponential            │
│                      backoff + jitter, retries amplify load on a            │
│                      degraded system (the "retry storm").                   │
│                      Failure if ignored: retry storm kills the             │
│                      downstream you were trying to recover.                 │
│                                                                             │
│  jitter              Random variation added to retry delays to              │
│                      de-synchronize clients. Without jitter, 1000 clients   │
│                      retrying on the same 1s schedule produce a 1000×      │
│                      spike every second. With ±20% jitter, the spike        │
│                      becomes a 2s-wide 500× plateau.                        │
│                      Failure if ignored: thundering herd on retry.         │
└─────────────────────────────────────────────────────────────────────────────┘
```

The terms above are not academic — every one of them is the name of a class of production incident the author has personally debugged at 3 a.m. The pattern across all of them is the same: the term names a *mechanism* (a kernel object, a protocol state, a database invariant, a delivery semantics, a resilience pattern), and the mechanism exists because *without it, a specific failure mode would occur*. `fsync` exists because without it, COMMIT lies. `MVCC` exists because without it, readers block writers. The circuit breaker exists because without it, a degraded downstream takes down every caller. When you encounter a term in a downstream note, ask "which failure mode does this prevent?" — that is the question that converts memorization into understanding. The vault's persistent claim is that 80% of production incidents can be diagnosed in the first 5 minutes if you know which failure mode each term names.

### Disambiguation index: Resolving conflicting framework naming conventions for identical patterns

Every ecosystem uses slightly different vocabulary for the same underlying concept, and worse, several ecosystems *reuse the same word for different concepts*. The most dangerous case is "middleware" — in Express it means a function `(req, res, next) => ...` that runs *before* the route handler; in Django it means a class with `process_request` / `process_view` / `process_response` hooks that wraps the *entire* view dispatch; in Spring it does not exist as a term at all (the equivalent is `HandlerInterceptor`); in Laravel it means a class with a `handle($request, Closure $next)` method that is closer to Express's definition than to Django's. An engineer who learned "middleware" in Express and then assumes Django middleware behaves the same will be wrong on at least three axes (lifecycle, ordering, async support).

The disambiguation table below covers the eight most-confused terms. Each row is a concept; each column is an ecosystem; each cell is the *specific implementation name and its key behavioral difference from the others*. When you do the Δ-translation pass from Spring Boot to another ecosystem, look up the term here first — never assume the name carries the same semantics.

The two cases that cause the worst production bugs are: (1) assuming Django middleware behaves like Express middleware — it does not; Django's `process_request` runs *before* URL resolution, so it cannot access `request.resolver_match`, while Express middleware runs *after* routing but *before* the handler, so it can access `req.route`. (2) Assuming Laravel's `User::find($id)` is the same as Spring's `userRepository.findById(id)` — they both execute `SELECT * FROM users WHERE id = ?`, but Laravel's static method is on the Model class (active record), so it returns an Eloquent Model instance with methods like `->save()` and `->delete()`, while Spring's `findById` returns an `Optional<User>` JPA entity that has no persistence methods on it. The shapes are different; the deltas matter.

### Formal engineering definitions of state, idempotency, side effects, blocking vs. non-blocking, an...

Five terms are notoriously misused in tutorials and Stack Overflow answers. The vault uses each in its precise formal sense throughout — when a downstream note says "this operation is idempotent", it means the formal definition below, not the loose tutorial definition. Misusing these terms is the root cause of a substantial fraction of production bugs, because the engineer who thinks `POST /charge` is idempotent because "it always charges the same amount" will retry it on timeout and double-charge the customer.

**State** is the totality of values stored in mutable memory locations (registers, heap, database rows, file contents) at any instant. A function is **stateful** if its output depends on state other than its inputs; it is **stateless** if its output depends only on its inputs. A backend service is **stateful** if it stores per-client state in its own memory (e.g. a session map in a JVM static field) such that routing a request from that client to a different instance would break correctness. Stateless services are trivially horizontally scalable (any instance can serve any request); stateful services require sticky routing, consistent hashing, or external state stores (Redis, Postgres). The formal definition matters because the line is sharper than tutorials suggest: a service that caches response data in process memory for 60 seconds is *operationally* stateful even if its data model is stateless — if you scale from 1 to 10 instances, your cache hit rate drops 10× and your database load spikes 10×. Production bug: "we added a cache, scaled out, and Postgres CPU doubled."

**Idempotency** is the formal property that `f(f(x)) == f(x)` for all valid inputs `x`. HTTP PUT and DELETE are idempotent by spec; POST and PATCH are not (PATCH can be, depending on the operation). The formal definition matters because it is the *only* property that makes an operation safe to retry on transient failure. A `POST /orders` that creates a new order with a server-generated ID is *not* idempotent: retrying creates two orders. A `POST /orders` with a client-supplied `Idempotency-Key` header (Stripe's pattern, RFC draft) *is* idempotent: the server stores the response keyed by the idempotency key, and a retry returns the stored response without re-executing. The pattern is essential for any payment, charge, or send-email endpoint. Production bug: "the user clicked submit twice; we charged them twice" — caused by treating non-idempotent POST as if it were safe to retry. The fix is *always* either (a) make the operation idempotent via a client-supplied key, or (b) use the outbox pattern so the operation is applied exactly once by a single consumer.

**Side effects** are modifications of state outside the function's return value: writes to a database, sends to a queue, writes to a file, mutation of an input argument, writes to `System.out`. A function with no side effects is **pure**: it can be replaced with its return value (referential transparency), memoized safely, retried safely, parallelized safely, and tested without mocks. A function with side effects has none of these properties — it must be tested with a real or mocked database, it cannot be retried safely unless it is also idempotent, and it cannot be parallelized unless the side effects commute. The formal definition matters because frameworks increasingly try to *make* side effects explicit (Scala's `IO`, Haskell's `IO` monad, React's effects, Spring's `@Transactional` boundary) — the goal is to make every side effect visible at the type or annotation level so the engineer can reason about them. Production bug: "we memoized `getUser(id)` and the user's balance updates stopped appearing" — caused by memoizing an impure function whose side effect was a balance refresh.

**Blocking vs. non-blocking** refers to the *mode of a file descriptor*, not to the function's apparent semantics. A file descriptor is opened in blocking mode by default: a `read(fd, buf, len)` call will sleep the calling thread until at least one byte is available. A file descriptor set to non-blocking mode (`fcntl(fd, F_SETFL, O_NONBLOCK)`) returns immediately: `read()` returns `EAGAIN` if no data is available, and the caller must use an event multiplexer (`epoll_wait`, `kqueue`, `IOCP`) to be notified when data becomes available. The two modes are mutually exclusive for a given operation: you cannot "make a blocking call non-blocking" without changing the file descriptor's mode or running the call on a separate thread. The formal definition matters because the performance characteristics are wildly different: a blocking server (Tomcat with default `maxThreads=200`) can serve at most 200 concurrent slow clients, while a non-blocking server (Netty, Node) can serve 10 000+ concurrent slow clients on a single thread. Production bug: "we set the JDBC connection to non-blocking and Postgres hung" — caused by mixing modes; JDBC drivers do not support non-blocking mode, you must use a thread pool or R2DBC instead.

**Synchronous vs. asynchronous** refers to the *control flow* of the calling code, not to the underlying I/O mode. A synchronous call returns its result via a return value: `int result = compute(x);` — the calling thread is busy until the result is available. An asynchronous call returns immediately with a *handle* to the future result: `Future<Integer> result = computeAsync(x);` — the calling thread is free to do other work, and the result is retrieved later via `result.get()` or a callback. The two terms are *independent* of blocking/non-blocking: you can have synchronous blocking I/O (classic JDBC), synchronous non-blocking I/O (rare; the caller spins in a `while (read() == EAGAIN)` loop — bad idea), asynchronous blocking I/O (a `Future` backed by a thread pool that itself blocks — common, e.g. Spring `@Async` on top of Tomcat's thread pool), or asynchronous non-blocking I/O (Netty, Node, asyncio — the gold standard). The formal definition matters because tutorials routinely conflate "async" with "non-blocking", leading engineers to believe that switching to `async/await` magically makes their code non-blocking — it does not. If the underlying I/O is blocking (e.g. Python's `requests` library called inside an `async def`), the event loop blocks and every other async task stalls. Production bug: "we converted all our Flask routes to async with Quart and p99 latency doubled" — caused by calling blocking `requests.post()` inside async handlers without `asyncio.to_thread()`.

## Key Takeaways

1. **The 30-term lexicon is the fixed vocabulary of the vault.** When a downstream note uses a term, it uses the definition in this note. Bookmark this page and return whenever a term is not instantly clear.
2. **Framework naming conflicts are the second-biggest source of cross-ecosystem bugs** (after concurrency model differences). Always check the disambiguation table before assuming a word carries the same semantics across ecosystems — "middleware" in particular means four different things.
3. **The five formal definitions (state, idempotency, side effects, blocking/non-blocking, sync/async) are independent axes.** Misusing any of them produces production bugs: non-idempotent POST retried = double charge; memoized impure function = stale data; "async" wrapping blocking I/O = stalled event loop.
