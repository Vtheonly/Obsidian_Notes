# 00.04. Cross-Ecosystem Equivalence Graph

## What This Is

This note is the **lookup table** the anchor-and-delta protocol operates on. After you have learned a concept deeply in the Spring Boot anchor, you need to translate it into Express, Django, Flask, or Laravel — and the question is always the same: "what is this concept called in ecosystem X, and which specific class/function/config-key implements it?" This note answers that question in O(1): find the row for the concept, scan across to the column for the target ecosystem, read the cell. The cell names the specific implementation, the relevant package/class, and (where it matters) the key behavioral delta from the anchor.

The graph is multi-dimensional: each row is a concept (routing, middleware, DI, validation, error handling, ORM, migrations, connection pooling, background jobs, auth, caching), each column is an ecosystem (Spring Boot, Express, Django, Flask, Laravel), and each cell carries not just a name but a one-line behavioral note. The graph does not replace reading the ecosystem's anchor or delta note in sections 05 onward — it compresses the *index* of those notes into a single screen so you can find the right deep-dive note in seconds. Treat it as the Rosetta Stone of the vault: read across a row to see the same concept in five syntaxes; read down a column to see the structure of one ecosystem's standard library.

## The Details

### Multi-dimensional reference matrix comparing Spring Boot, Express, Django, Flask, and Laravel

The matrix below covers the eleven concepts that every backend framework must implement. The rows are ordered by the request lifecycle: routing and middleware run first, then the controller, then validation, then the service layer (DI), then persistence (ORM + migrations + connection pool), then async side-effects (background jobs), then cross-cutting concerns (error handling, auth, caching). When you do a Δ-translation, work down the matrix in order — translating routing first gives you a working endpoint; translating persistence last gives you a working feature.

Reading across a row reveals Systems Invariance in action: the concept is the same, only the implementation name changes. Reading down a column reveals each ecosystem's *shape* — Spring Boot is verbose and annotation-driven; Express is minimal and library-driven; Django is batteries-included and convention-driven; Flask is micro and extension-driven; Laravel is elegant and facade-driven. The deltas that matter for production are not the names — they are the *defaults*: Spring Boot's HikariCP defaults to a pool of 10 (good for a small service, terrible for a high-throughput one); Django's `CONN_MAX_AGE=0` means *no connection pooling at all* by default, every request opens and closes a fresh TCP connection to Postgres (catastrophic under load); Laravel's `pool_size=5` is too small for most production workloads; Express's `pg.Pool` default of 10 is the same as Spring's, but the *event-loop* concurrency model means 10 connections can serve thousands of concurrent requests where Spring's 10 connections serve at most 200 concurrent Tomcat threads. The default values encode the framework's assumptions about your workload; mismatch those assumptions and you have a production incident.

### Cross-mapping of terminology: Routes, Controllers, Middleware/Filters, Service Containers/Beans, ...

The matrix in the previous H3 gives you the name. This H3 gives you the *behavior* — for the six most-confused concepts (Routes, Controllers, Middleware/Filters, Service Containers/Beans, ORM Entities, Migrations), the table below records the specific behavioral deltas that bite engineers during the Δ-translation pass. The behavioral deltas are categorized as: **(L)ifecycle** — when the concept runs in the request lifecycle; **(O)rdering** — what determines the execution order; **(A)sync support** — whether the concept can be async; **(D)efault** — what the framework's out-of-the-box behavior is.

```text
┌──────────────────┬─────────────────────────────────────────────────────────────────────────────────────────────────┐
│ Concept: ROUTING │ Behavioral deltas across ecosystems                                                              │
├──────────────────┼─────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Spring Boot      │ (L) DispatcherServlet dispatches after Filters and before Interceptors.                        │
│                  │ (O) @Order on Filter; interceptors in addPathPatterns registration order.                       │
│                  │ (A) Servlet 6+ supports async dispatch via AsyncContext; not default.                          │
│                  │ (D) Ant-style path matching: /api/** matches /api/users/42.                                     │
│                  │ Failure: Spring 5.x changed default path matcher to PathPatternParser;                          │
│                  │ trailing-slash matching changed in 6.x — breaks existing clients silently.                      │
├──────────────────┼─────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Express          │ (L) Router runs after app-level middleware, before route-specific middleware.                   │
│                  │ (O) Registration order: app.use() calls and router.METHOD() calls in source order.              │
│                  │ (A) Native async handlers; unhandled promise rejections crash the process unless wrapped.      │
│                  │ (D) path-to-regexp: /api/users/:id captures id. Order matters: /api/users/me MUST be           │
│                  │ registered before /api/users/:id or "me" matches as :id.                                         │
│                  │ Failure: route ordering bugs — /:foo/:bar matches /users/me too.                                │
├──────────────────┼─────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Django           │ (L) URLResolver runs after middleware process_request, before middleware process_view.          │
│                  │ (O) urlpatterns list order — first match wins.                                                  │
│                  │ (A) Sync in WSGI; async views supported in Django 3.1+ via async def. ASGI required.            │
│                  │ (D) Strict converter typing: path("users/<int:uid>") — uid must be an int or 404.               │
│                  │ Failure: <str:name> matches greedily including slashes; use <path:name> for that.               │
├──────────────────┼─────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Flask            │ (L) URL Map (Werkzeug) is built at app-run time from decorators.                                │
│                  │ (O) Registration order, but Werkzeug's Map sorts by specificity at bind time.                    │
│                  │ (A) Sync; Flask 2.0+ supports async def via Flask[async] (wraps in thread). Quart is pure async.│
│                  │ (D) /users/<int:uid> — converters: int, float, string, path, uuid.                              │
│                  │ Failure: <string:name> stops at slash; <path:name> includes slashes — pick the right one.        │
├──────────────────┼─────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Laravel          │ (L) Router runs after global middleware, before route-group middleware.                          │
│                  │ (O) Registration order in routes/api.php and routes/web.php.                                    │
│                  │ (A) Sync by default; Laravel Octane+Swoole/RoadRunner adds an event loop.                       │
│                  │ (D) Route model binding: Route::get('/users/{user}') auto-resolves {user} to User model         │
│                  │ by primary key, injecting the model instance into the controller method.                         │
│                  │ Failure: implicit binding fails silently if the ID doesn't exist → 404 looks like routing miss.  │
└──────────────────┴─────────────────────────────────────────────────────────────────────────────────────────────────┘

┌──────────────────┬─────────────────────────────────────────────────────────────────────────────────────────────────┐
│ Concept: MIDDLEWARE (most-confused term — see disambiguation in 00.03)                          │
├──────────────────┼─────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Spring Boot      │ Two layers: Filter (jakarta.servlet.Filter, runs BEFORE DispatcherServlet) and                 │
│                  │ HandlerInterceptor (runs AROUND the handler). FilterRegistrationBean sets order.                │
│                  │ Spring Security is implemented as a Filter chain — runs before interceptors.                     │
├──────────────────┼─────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Express          │ Single layer: app.use(fn) and router.use(fn). (req, res, next) signature.                       │
│                  │ MUST call next() or end the response; otherwise the request hangs.                              │
│                  │ Error middleware: (err, req, res, next) — registered LAST, only invoked on next(err).           │
├──────────────────┼─────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Django           │ Single layer: MIDDLEWARE list of classes. process_request runs BEFORE URL resolution;          │
│                  │ process_view runs AFTER URL resolution but BEFORE the view; process_response runs AFTER.        │
│                  │ process_template_response can modify the template context.                                      │
│                  │ ASGI middleware has different hooks: __call__(scope, receive, send).                            │
├──────────────────┼─────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Flask            │ Two layers: @app.before_request (funcs run before view, no chain) and                           │
│                  │ @app.after_request (funcs run after, can modify response).                                       │
│                  │ No next() — return value of before_request short-circuits if non-None.                          │
├──────────────────┼─────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Laravel          │ Single layer: middleware classes with handle($request, Closure $next).                          │
│                  │ $response = $next($request) — explicitly calls the next middleware in the pipeline.              │
│                  │ Terminate middleware has a terminate($request, $response) method called after response sent.    │
│                  │ Pipeline class is the underlying implementation — same pattern as Spring's interceptor chain.   │
└──────────────────┴─────────────────────────────────────────────────────────────────────────────────────────────────┘

┌──────────────────┬─────────────────────────────────────────────────────────────────────────────────────────────────┐
│ Concept: DI / SERVICE CONTAINER                                                              │
├──────────────────┼─────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Spring Boot      │ ApplicationContext is the container. @Component, @Service, @Repository, @Configuration           │
│                  │ stereotype annotations register beans. @Autowired injects by type (constructor injection         │
│                  │ is the recommended form since Spring 4.3). @Qualifier disambiguates by name.                    │
│                  │ CGLIB proxies intercept calls for @Transactional, @Async, @Cacheable, etc.                      │
│                  │ Bean lifecycle: instantiate → set properties → BeanNameAware → BeanFactoryAware →               │
│                  │ ApplicationContextAware → BeanPostProcessor.postProcessBeforeInitialization →                    │
│                  │ @PostConstruct → InitializingBean.afterPropertiesSet → init-method →                             │
│                  │ BeanPostProcessor.postProcessAfterInitialization → ready.                                        │
├──────────────────┼─────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Express          │ No first-class container. require() is the de-facto DI: Node caches modules so                   │
│                  │ require('./userService') returns the same instance every time — a process-level singleton.      │
│                  │ Libraries: tsyringe (reflect-metadata based), awilix (function-based), InversifyJS (heavy).     │
│                  │ Most Express codebases do NOT use a DI container at all — they pass dependencies as function     │
│                  │ arguments or attach to app.locals / req.app.locals.                                             │
├──────────────────┼─────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Django           │ No first-class container. Services are typically plain module-level functions or classes.       │
│                  │ django.apps.AppConfig is a registry of installed apps, not a DI container.                      │
│                  │ Third-party: python-dependency-injector (most popular), django-injector (Flask-Injector port).  │
│                  │ Most Django codebases construct dependencies inside views or via factory functions.            │
├──────────────────┼─────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Flask            │ No first-class container. Flask-Injector extension provides Guice-style DI on top of Flask.      │
│                  │ Otherwise: pass dependencies as function arguments or attach to app.config.                      │
│                  │ Application factory pattern: create_app(config) returns a configured app instance — used to     │
│                  │ inject test-vs-production config.                                                                │
├──────────────────┼─────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Laravel          │ Illuminate\Container is the Service Container. Auto-resolution via reflection: the container     │
│                  │ reads constructor type-hints and recursively resolves dependencies. app()->make(Foo::class).     │
│                  │ Bindings: $this->app->bind('key', fn() => new Foo) or ->singleton('key', fn() => new Foo).      │
│                  │ Service Providers (app/Providers/*.php) are the registration points.                             │
│                  │ Facades (Cache::, DB::, Auth::) are syntactic sugar for app()->make(...)->method().              │
│                  │ This is the closest ecosystem to Spring Boot's DI model — the only delta is annotations          │
│                  │ vs. reflection-on-constructor-args.                                                              │
└──────────────────┴─────────────────────────────────────────────────────────────────────────────────────────────────┘

┌──────────────────┬─────────────────────────────────────────────────────────────────────────────────────────────────┐
│ Concept: ORM / ENTITIES                                                                      │
├──────────────────┼─────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Spring Boot      │ JPA + Hibernate. @Entity classes are POJOs; EntityManager manages persistence.                  │
│                  │ Repository pattern: interface UserRepository extends JpaRepository<User, Long>.                 │
│                  │ Data-mapper: entity is plain data; repository persists. NO .save() on entity itself.             │
│                  │ @Transactional demarcates the unit of work; dirty checking auto-flushes at commit.              │
│                  │ Lazy loading via proxies: user.getOrders() triggers a SELECT on first access —                  │
│                  │ the famous LazyInitializationException if the session is closed.                                 │
├──────────────────┼─────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Express          │ No built-in ORM. Prisma (DSL + codegen, data-mapper style), TypeORM (decorator-based,           │
│                  │ Spring-JPA flavored), Sequelize (active-record + data-mapper mix, older).                       │
│                  │ Prisma: schema.prisma file → prisma generate → typed client. No @Entity annotations.             │
│                  │ TypeORM: @Entity classes, @InjectRepository — closest delta from Spring.                         │
├──────────────────┼─────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Django           │ Django ORM. Model subclasses django.db.models.Model. Active-record: instance.save()              │
│                  │ writes the row, instance.delete() removes it. Model.objects is the Manager (class-level).        │
│                  │ QuerySets are lazy: User.objects.filter(age__gt=18) doesn't execute until iterated.             │
│                  │ select_related (single-valued FK — LEFT JOIN), prefetch_related (multi-valued — second query).  │
│                  │ No persistence boundary like @Transactional — use with transaction.atomic().                    │
├──────────────────┼─────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Flask            │ Flask-SQLAlchemy wraps SQLAlchemy. Two modes: ORM (declarative models, data-mapper style)       │
│                  │ or Core (SQL expression language, no classes). Model.query is the session-bound interface.       │
│                  │ Sessions are explicit: db.session.add(obj); db.session.commit().                                  │
│                  │ Eager loading: joinedload(), contains_eager(), selectinload() — explicit, not annotation-based. │
├──────────────────┼─────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Laravel          │ Eloquent ORM (active-record). Models extend Illuminate\Database\Eloquent\Model.                 │
│                  │ Static methods: User::find($id), User::where('age', '>', 18)->get().                              │
│                  │ $user->save() inserts or updates based on exists flag. $user->delete() removes.                  │
│                  │ Relationships as methods: $user->orders() returns a HasMany; $user->orders invokes the magic    │
│                  │ __get → runs the query and caches the result.                                                    │
│                  │ N+1 prevention: User::with('orders')->get() eager-loads.                                         │
└──────────────────┴─────────────────────────────────────────────────────────────────────────────────────────────────┘

│ Concept: MIGRATIONS                                                                          │
├──────────────────┼─────────────────────────────────────────────────────────────────────────────────────────────────┤
```

The pattern across all six concepts is the same: Spring Boot *names and makes explicit* every concept via annotation and interface; the other ecosystems either (a) provide the concept with a thinner API (Laravel), (b) delegate to a third-party library (Express, Flask), or (c) provide the concept with batteries-included defaults that hide the mechanism (Django). This is why Spring Boot is the anchor — it forces you to see every concept's mechanism, after which the other ecosystems are recognizable as variations on a theme rather than as separate disciplines. When you do the Δ-translation pass, the six tables above are your map: find the row, find the column, read the cell, write the code.

### Structural analysis of ecosystem package management, dependency injection models, and runtime lif...

The matrix and the cross-map cover concepts; this H3 covers the *runtimes themselves*. The same five ecosystems differ along three structural axes that determine everything else: **(1) package management** — how dependencies are declared, resolved, and vendored; **(2) DI model** — where the IoC container lives (framework, library, or absent) and how wiring happens; **(3) runtime lifecycle** — process model, startup sequence, request lifecycle, shutdown. These axes are independent of the framework's feature set; they govern operational properties like cold-start time, memory footprint, and horizontal scalability.

The structural differences drive operational consequences that matter in production. Spring Boot's multi-threaded JVM has the highest memory footprint (each thread's stack is ~512 KB–1 MB by default; 200 Tomcat threads = ~200 MB just in stacks) but the lowest per-request CPU overhead (no GC pressure for short-lived requests because the new generation is large). Express's single-threaded model has the lowest memory footprint but the strictest latency requirement — a single slow handler blocks everything. Django and Flask share CPython's GIL, which means CPU-bound work in any request blocks every other request in the same worker process; the production pattern is `gunicorn --workers=N --worker-class=sync` with N = 2× vCPUs + 1. PHP-FPM's process-per-request model is the most memory-efficient per-request but the worst for connection reuse — every request opens a fresh Postgres connection unless you use an external pooler like PgBouncer or Octane's persistent process. Laravel Octane (Swoole or RoadRunner) fundamentally changes the runtime model — it converts PHP-FPM's process-per-request into a long-lived reactor like Node, with the consequence that static state (singletons, caches) survives across requests — which is a feature and a footgun.

The DI model axis is the deepest structural difference. Spring Boot's `ApplicationContext` is built *into* the framework and is mandatory — you cannot write idiomatic Spring without it. Laravel's `Illuminate\Container` is also built-in but is largely invisible (auto-wiring via reflection), so engineers often use it without realizing. Django and Flask have *no* built-in DI; services are typically module-level functions or singletons, and the consequence is that testability suffers (you cannot substitute a dependency without monkeypatching the module). Express's situation is similar — the `require()` cache provides accidental singletons, and the convention is to pass dependencies as function arguments or via `app.locals`. The Δ-translation lesson is: when porting Spring's `@Autowired UserService` to Django, you write `from .services import user_service` and call `user_service.find(id)` — there is no container to inject through, so the dependency is implicit via the import. This works fine until you need to substitute a mock in tests, at which point you discover the cost of the absent container.

## Cross-Ecosystem Code

The same minimal endpoint — `GET /api/users/:id` returning a JSON user object — implemented in all five ecosystems. Read them side by side; the shape is identical, only the syntax differs. This is the smallest possible Δ-translation exercise.

**Spring Boot (Anchor):**
```java
@RestController
@RequestMapping("/api/users")
class UserController {
    private final UserService service;
    UserController(UserService service) { this.service = service; }  // constructor injection

    @GetMapping("/{id}")
    ResponseEntity<UserDto> get(@PathVariable Long id) {
        return service.find(id)
            .map(ResponseEntity::ok)
            .orElseThrow(() -> new UserNotFoundException(id));
    }

    @ExceptionHandler(UserNotFoundException.class)
    ResponseEntity<ProblemDetail> notFound(UserNotFoundException ex) {
        return ResponseEntity.status(404)
            .body(ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage()));
    }
}
```

**Express (Delta):**
```typescript
import { Router, Request, Response, NextFunction } from "express";
import { userService } from "./userService";

const router = Router();

router.get("/api/users/:id", async (req: Request, res: Response, next: NextFunction) => {
  try {
    const user = await userService.find(Number(req.params.id));
    if (!user) return res.status(404).json({ detail: `user ${req.params.id} not found` });
    res.json(user);
  } catch (err) {
    next(err);  // hands off to error-handling middleware
  }
});

// Error handler — must be registered LAST
router.use((err: Error, _req: Request, res: Response, _next: NextFunction) => {
  res.status(500).json({ detail: err.message });
});

export default router;
```

**Django (Delta):**
```python
# urls.py
from django.urls import path
from . import views

urlpatterns = [
    path("api/users/<int:uid>", views.user_detail),
]

# views.py
import json
from django.http import JsonResponse, HttpResponseNotAllowed
from django.views.decorators.http import require_http_methods
from .services import user_service

@require_http_methods(["GET"])
def user_detail(request, uid: int):
    user = user_service.find(uid)
    if user is None:
        return JsonResponse({"detail": f"user {uid} not found"}, status=404)
    return JsonResponse(user)
```

**Flask (Delta):**
```python
from flask import Flask, jsonify
from werkzeug.exceptions import NotFound
from .services import user_service

app = Flask(__name__)

@app.get("/api/users/<int:uid>")
def get_user(uid: int):
    user = user_service.find(uid)
    if user is None:
        raise NotFound(description=f"user {uid} not found")
    return jsonify(user)

@app.errorhandler(NotFound)
def not_found(err):
    return jsonify({"detail": err.description}), 404
```

**Laravel (Delta):**
```php
<?php
// routes/api.php
use App\Http\Controllers\UserController;
use Illuminate\Support\Facades\Route;

Route::get('/users/{user}', [UserController::class, 'show']);

// app/Http/Controllers/UserController.php
class UserController extends Controller {
    public function __construct(private UserService $service) {}  // auto-wired

    public function show(int $id) {
        $user = $this->service->find($id);
        if (!$user) abort(404, "user {$id} not found");
        return response()->json($user);
    }
}
```

The deltas that matter: Spring uses a `ResponseEntity` wrapper and exception handlers; Express uses `res.status().json()` and error middleware; Django returns `JsonResponse` with a `status` kwarg; Flask returns a tuple `(body, status)` or raises an HTTP exception; Laravel uses `response()->json()` and the `abort()` helper. Each is a thin syntactic translation of the same underlying action — set the HTTP status code, write a JSON body to the response buffer, return. The thirteen-stage pipeline from [[00.01. Master Architectural Mental Model]] runs identically in all five cases.

## Key Takeaways

1. **The eleven-row matrix is the Rosetta Stone of the vault.** Every concept in every later note maps to a row; every ecosystem you encounter maps to a column. When in doubt, look it up here first.
2. **Behavioral deltas matter more than naming deltas.** "Middleware" means different things in different ecosystems — the *behavior* (when it runs, what it can do, whether it can be async) is the part that bites in production.
3. **The structural axis (process model, DI model, runtime lifecycle) determines operational properties.** Memory footprint, cold-start time, and horizontal scalability are all consequences of these axes, not of the framework's feature set.
