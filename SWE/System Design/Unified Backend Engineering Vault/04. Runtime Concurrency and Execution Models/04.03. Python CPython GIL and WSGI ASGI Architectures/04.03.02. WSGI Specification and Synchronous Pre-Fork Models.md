# 04.03.02. WSGI Specification and Synchronous Pre-Fork Models

## What This Is

**WSGI (Web Server Gateway Interface, PEP 3333)** is the contract that every synchronous Python web framework (Django, Flask, Pyramid, Bottle, CherryPy, Werkzeug-based apps) and every synchronous Python web server (gunicorn, uWSGI, mod_wsgi, waitress) implements. It is a tiny specification — about three pages of prose in PEP 3333 — but it is the load-bearing seam that decouples "what the framework does" from "how the server talks HTTP." WSGI is also the cleanest expression of the pre-fork concurrency model in any language: the server binds the listening socket, `fork()`s a fixed pool of worker processes, and each worker runs the same Python application synchronously, one request at a time, with the GIL guaranteeing that the worker's single Python thread cannot race itself. The model is older than ASGI, slower than ASGI for I/O-bound traffic, and dramatically easier to operate — there is no event loop to stall, no coroutine to leak, no `await` to forget. If you understand WSGI you understand ~80% of the Python deployments currently running on the public internet.

The forward link to section 05 is direct: every Django and Flask app you will write in the framework section is a WSGI callable, even though most of the time you never see the `environ` dict directly. The backward link to section 02 is the `socket()` / `bind()` / `listen()` / `accept()` family — a WSGI server is a thin layer over those four syscalls plus `fork()`. The reason WSGI is synchronous is the reason CPython needs the GIL (see [[04.03.01. CPython Execution and the Global Interpreter Lock]]): Python bytecode cannot run in parallel within one process, so the only way to use multiple cores is multiple processes, and WSGI's pre-fork model is the simplest implementation of that idea.

## The Details

### PEP 3333: Web Server Gateway Interface (WSGI) design and signatures (`environ`, `start_...

PEP 3333 (the Python 3 update of PEP 333 from 2003) defines a WSGI application as a callable with the signature `app(environ, start_response)` that returns an iterable of `bytes` chunks constituting the HTTP response body. The `environ` argument is a plain Python `dict` containing both the standard CGI variables (`REQUEST_METHOD`, `PATH_INFO`, `QUERY_STRING`, `SERVER_NAME`, `SERVER_PORT`, `REMOTE_ADDR`, `CONTENT_TYPE`, `CONTENT_LENGTH`, `HTTP_*` for every request header — so `Host:` becomes `environ["HTTP_HOST"]`, `User-Agent:` becomes `environ["HTTP_USER_AGENT"]`) and the WSGI-specific variables (`wsgi.version` = `(1, 0)`, `wsgi.url_scheme` = `"http"` or `"https"`, `wsgi.input` = a file-like object wrapping the socket's read side, `wsgi.errors` = a writable stream for error logging, `wsgi.multithread` / `wsgi.multiprocess` / `wsgi.run_once` = booleans describing the server's concurrency model). The `start_response` argument is a callable with the signature `start_response(status, response_headers, exc_info=None)` that the application invokes exactly once to commit the HTTP status line and headers — `status` is a string like `"200 OK"` or `"404 Not Found"`, `response_headers` is a list of `(name, value)` tuples, and `exc_info` is used only if the application is retrying `start_response` after an exception.

The simplest correct WSGI application is four lines: read `environ["PATH_INFO"]`, call `start_response("200 OK", [("Content-Type", "text/plain")])`, and `return [b"hello\n"]`. The iterable return is the body — by yielding chunks one at a time the application can stream a large response without buffering it in memory. The server iterates the result and writes each chunk to the socket. A common footgun is returning a `str` instead of `bytes`; PEP 3333 is strict that the response body chunks must be `bytes` (the Python 2 era allowed `str` because `str` was bytes; PEP 3333 was the Python 3 fix that split the type and required explicit `b"..."` literals or `.encode("utf-8")` calls). Another common footgun is forgetting `Content-Length` — without it, the server must use HTTP/1.1 chunked transfer encoding or close the connection after the body, which kills keep-alive throughput.

```python
# A minimal WSGI application — the entire PEP 3333 contract in 12 lines.
def app(environ, start_response):
    # environ["PATH_INFO"] is the URL-decoded path without the query string.
    # environ["QUERY_STRING"] is the raw query string (not parsed).
    path = environ.get("PATH_INFO", "/")
    method = environ["REQUEST_METHOD"]

    if path == "/healthz" and method == "GET":
        status = "200 OK"
        body = b'{"status":"ok"}\n'
        headers = [
            ("Content-Type", "application/json"),
            ("Content-Length", str(len(body))),
        ]
    else:
        status = "404 Not Found"
        body = b"not found\n"
        headers = [
            ("Content-Type", "text/plain"),
            ("Content-Length", str(len(body))),
        ]

    # start_response must be called exactly once before the first body chunk
    # is yielded. It returns a write() callable that PEP 3333 deprecates.
    start_response(status, headers)

    # The return value is an iterable of bytes. A list works; a generator
    # works and streams. The server iterates this and writes to the socket.
    return [body]

# Run it with: gunicorn -w 4 -b 127.0.0.1:8000 app:app
```

The reason WSGI uses two arguments (`environ` and `start_response`) instead of a single `Request` object is historical: in 2003 the Python community wanted a spec with zero dependencies — no `Request` class hierarchy, no framework types, no inheritance. A `dict` and a callable are the lowest-common-denominator Python types, and any framework can wrap them in its own `Request`/`Response` objects. Flask does exactly this: `flask.Request(environ)` reads `wsgi.input` lazily, parses form data on demand, and exposes `request.json` / `request.form` / `request.args` as property accessors over the `environ` dict. Django's `WSGIHandler.request_class(environ)` does the same thing. The WSGI contract is so small that real-world servers (gunicorn ~5k lines, uWSGI ~50k lines of C) are dominated by the HTTP parser, the worker management, and the protocol plumbing — the WSGI dispatch itself is about 50 lines.

The production failure mode of the WSGI spec is blocking `wsgi.input`. PEP 3333 says `wsgi.input` is a file-like object with a `read(n)` method that the application calls to consume the request body. If the application calls `environ["wsgi.input"].read()` with no argument (read-to-EOF) and the client is slow or hostile, the call blocks the worker until the client finishes sending — a slowloris attack against the worker pool. The fix is `environ["wsgi.input"].read(int(environ.get("CONTENT_LENGTH", 0)))` so the read is bounded by the announced body size, plus a request-body-size limit enforced by the server (gunicorn `--limit-request-line 8190`, `--limit-request-field_size 8190`, and the framework-level `DATA_UPLOAD_MAX_MEMORY_SIZE` in Django). The second failure mode is an application that yields chunks but never returns — the worker holds the socket open forever. gunicorn's `--timeout 30` kills workers that do not produce a response within 30 seconds (SIGKILL after `--graceful-timeout`).

### WSGI Servers: Gunicorn and uWSGI architectures

Gunicorn ("Green Unicorn", written by Benoit Chesneau in 2009, pure-Python) and uWSGI (written by Roberto De Ioris in C starting 2009) are the two production-grade WSGI servers. Both implement the same pre-fork master-worker model, but with very different internals and ecosystems. Gunicorn's master is a single Python process (the "arbiter") that calls `socket.socket()`, `bind()`, `listen()` on the listening FD, then `os.fork()`s N worker processes. Each worker inherits the listening FD via `fork()` and enters a `select()`/`poll()`/`epoll_wait()` loop calling `accept()` on the shared listener, then runs the WSGI application synchronously. The arbiter monitors workers via `waitpid()` and respawns any worker that dies (segfault, OOM, `--timeout` kill). uWSGI does the same in C, with an Emperor mode that manages multiple uWSGI "vassals" (one per app), a custom binary "uwsgi protocol" (not FastCGI — confusingly, the protocol shares the project name) over TCP or UNIX socket, and a large plugin system (Python, Ruby, Perl, Go, Lua plugins) — uWSGI is closer to an application server than a simple WSGI server.

Gunicorn's worker types are the most important decision when deploying a WSGI app. The `sync` worker (the default) is the simplest: one process, one thread, one request at a time — pure pre-fork. The `gthread` worker runs N OS threads inside the worker process; the GIL serialises the Python work, but I/O-bound requests (database calls, upstream HTTP calls) overlap on the threads because the C-level I/O releases the GIL. The `gevent` worker patches the stdlib with `gevent.monkey.patch_all()` and runs a greenlet-based event loop inside the worker — this turns synchronous `socket.recv` calls into cooperative context switches, allowing thousands of concurrent connections per worker. The `eventlet` worker does the same with eventlet instead of gevent. The `uvicorn` worker (a thin shim that runs the ASGI server uvicorn inside a gunicorn worker) is for ASGI apps, not WSGI — it appears in gunicorn's `--worker-class` list because gunicorn is sometimes used as a process manager for ASGI deployments. Choosing the wrong worker type is a common production mistake: a `sync` worker with `--workers 4` on a service that has 200ms of upstream HTTP latency will only handle 20 RPS (4 workers × 5 req/s each), while a `gthread` worker with `--workers 4 --threads 16` will handle ~320 RPS on the same hardware because the 16 threads overlap the I/O wait.

```text
  gunicorn architecture (sync worker, the default):

  ┌──────────────────────────────────────────────────────────────┐
  │  ARBITER (master process, runs as root, drops to app user)   │
  │  - binds 0.0.0.0:8000 (single listening FD)                 │
  │  - os.fork() × N  → spawns workers                          │
  │  - SIGTERM → graceful shutdown (workers finish in-flight)    │
  │  - SIGHUP → reload (gradually replaces workers)              │
  │  - SIGUSR1 → reopen log files (logrotate integration)        │
  │  - SIGUSR2 → upgrade gunicorn binary in place                │
  │  - waitpid() loop: respawn crashed workers                   │
  │  - kills workers exceeding --timeout (SIGABRT → SIGKILL)     │
  └────────────┬─────────────────────────────────────────────────┘
               │ listening FD inherited via fork()
       ┌───────┴───────┬─────────┬─────────┬─────────┐
       ▼               ▼         ▼         ▼         ▼
   ┌────────┐     ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐
   │Worker 1│     │Worker 2│ │Worker 3│ │Worker 4│ │Worker N│
   │accept()│     │accept()│ │accept()│ │accept()│ │accept()│
   │ ↓ req  │     │ ↓ req  │ │ ↓ req  │ │ ↓ req  │ │ ↓ req  │
   │ WSGI   │     │ WSGI   │ │ WSGI   │ │ WSGI   │ │ WSGI   │
   │ app()  │     │ app()  │ │ app()  │ │ app()  │ │ app()  │
   │ ↑ resp │     │ ↑ resp │ │ ↑ resp │ │ ↑ resp │ │ ↑ resp │
   └────────┘     └────────┘ └────────┘ └────────┘ └────────┘
   1 process       1 process  1 process  1 process  1 process
   1 thread        1 thread   1 thread   1 thread   1 thread

   (GIL is held by this worker while running Python)
```

The choice between gunicorn and uWSGI is usually organisational. Gunicorn is pure Python, ~5k lines, easy to read, has fewer features, and is the de-facto standard for Heroku-style PaaS deployments. uWSGI is C, much faster (the HTTP parser is hand-written, the protocol layer is zero-copy), has built-in caching, queues, signal routing, SNMP monitoring, and the Emperor mode for managing many apps — but is notorious for opaque config errors and a 200-page manual. The Python community has largely standardised on gunicorn + nginx (with nginx doing TLS termination, static files, and slow-client buffering, and gunicorn doing only the WSGI execution). uWSGI remains popular in legacy Django deployments and in markets where it was adopted early (Italian and Eastern European tech scenes, where the maintainers are based).

### The Master-Worker Pre-Fork Model: The Master process binds to socket ports; forked work...

The pre-fork model is the simplest concurrency design that can use multiple CPU cores for a Python web service. "Pre" means the workers are forked at startup, before any request arrives — the cost of `fork()` (typically 1–5 ms on Linux, copying the kernel's per-process structures) is paid once at boot, not on the request path. "Fork" means `os.fork()`, the POSIX syscall that creates an exact copy of the parent process — same memory layout (via copy-on-write, so the actual RAM duplication is minimal until the worker writes to it), same open file descriptors (the listening socket, log files, but `FD_CLOEXEC`-marked files are closed on `exec`), same signal handlers. The master holds the listening FD; each worker inherits it via `fork()` and calls `accept()` on it directly. The kernel's `accept_queue` (capped by `min(backlog, somaxconn)`, see [[02.04.03. The POSIX Socket Lifecycle]]) distributes incoming connections to whichever worker is currently in `accept()`.

The reason the master binds and the workers accept (rather than the master accepting and dispatching) is the `SO_REUSEPORT` socket option, which lets multiple sockets bind the same `(ip, port)` pair and the kernel load-balances incoming SYN packets across them via a 4-tuple hash. Without `SO_REUSEPORT` (the historical default, pre-Linux 3.9), all workers share one FD and the kernel's accept-queue serialises them with a single lock — this is the "thundering herd" problem where the kernel wakes all N workers from `accept()` for one incoming connection and N-1 go back to sleep. With `SO_REUSEPORT` (Linux 3.9+, 2013), each worker has its own listening socket and its own accept-queue, eliminating the contention. gunicorn added `--reuse-port` in 19.0; nginx added `listen ... reuseport` in 1.9.1. The same kernel feature underlies PHP-FPM's pre-fork model (see [[04.04.02. FastCGI Protocol and PHP-FPM Pool Architecture]]).

```text
  Pre-fork lifecycle, the gunicorn master loop:

  T0: master starts
      socket(AF_INET, SOCK_STREAM, 0)         → fd 3
      setsockopt(fd, SOL_SOCKET, SO_REUSEADDR) → ok
      setsockopt(fd, SOL_SOCKET, SO_REUSEPORT) → ok (Linux 3.9+)
      bind(fd, 0.0.0.0:8000)                   → ok
      listen(fd, 2048)                          → ok (accept_queue cap)
      drop privileges: setuid(www-data)

  T1: master forks workers
      for i in range(N):
          pid = os.fork()
          if pid == 0:
              # worker
              worker_loop(fd)

  T2: worker_loop (each worker, independently):
      while not stop:
          client_fd = accept(fd)          # blocks until a connection arrives
          recv(client_fd, request)        # blocking read of HTTP request
          environ = parse_http(request)
          response = app(environ, start_response)
          for chunk in response:
              send(client_fd, chunk)
          close(client_fd)

  T3: master waitpid() loop (forever):
      while True:
          pid, status = os.waitpid(-1, 0)
          if WIFSIGNALED(status):
              log("worker %d crashed (signal %d), respawning", pid, WTERMSIG(status))
          fork_new_worker()
```

The pre-fork model is the simplest concurrency design that survives CPython's GIL constraint because each worker is a separate process with its own GIL — there is no shared Python heap to race on, no locks between workers, no lock contention on the GIL across cores. The cost is memory duplication: each worker loads the full Python interpreter (~15 MB) plus the application's modules (Django ~30 MB, a large Flask app ~10 MB), so 4 workers on a Django app is ~180 MB of resident memory just for the worker pool, before any request is served. This is the PHP-FPM trade-off too (see [[04.04.01. Zend Engine and the Shared-Nothing Lifecycle]]), and it is why pre-fork services must be sized carefully: each worker is ~30–50 MB, the box has N GB of RAM, and `workers = (RAM - OS - other services) / per_worker_memory`. The COW (copy-on-write) optimisation means the RSS of each worker stays close to the master's at startup and only grows as the worker modifies Python objects — Django's ORM querysets and template cache are the usual sources of COW breakage, growing each worker by 5–15 MB over a few hours of traffic.

The production failure mode of pre-fork is request queueing behind a slow worker. If `workers = 4` and one worker is stuck in a slow database query (5 seconds), the server only has 3 workers for new requests — and a burst of 10 concurrent connections will saturate the accept-queue and start returning 502s to clients. The diagnostic is `gunicorn stats` (with `--statsd-host`) showing per-worker `requests`, `request_duration`, and `busy_workers`. The fix is either more workers (cheaper if the work is I/O-bound), `gthread` workers (more threads per worker, overlapping I/O), or moving the slow endpoint to a background queue (Celery, RQ, Dramatiq). The second failure mode is memory leaks across requests — a worker that grows 5 MB per request from a leaked cache will hit OOM in 200 requests, and the master's respawn (on SIGKILL from OOM) costs ~1 second of downtime for that worker. gunicorn's `--max-requests 1000 --max-requests-jitter 100` recycles workers proactively (the jitter spreads the recycle times so all workers do not restart simultaneously), which is the same idea as PHP-FPM's `pm.max_requests`.

### Sizing worker processes: Mathematical rules based on available CPU cores and RAM (`work...

The famous gunicorn sizing rule is `workers = 2 * CPU_cores + 1`. The arithmetic: if you have 4 CPU cores and run 4 workers, every worker is busy when the box is at 100% CPU, and any background task (the arbiter, the OS, log flushing) is starved. With `workers = 9`, the box is over-subscribed 2.25× but the OS scheduler time-slices fairly and the latency penalty is small (a few percent of throughput) — in exchange, when one worker blocks on I/O, the others can keep the CPU busy. The `+1` is a safety margin for the arbiter itself and any housekeeping work. This rule was popularised by the gunicorn documentation in 2010 and is correct for the `sync` worker on a CPU-light, I/O-medium workload. It is wrong for `gthread` (where each worker has 16 threads, so `workers = CPU_cores` is enough) and wrong for `gevent` (where a single worker can handle thousands of concurrent connections, so `workers = CPU_cores` is the right cap). The deeper rule, which the formula approximates, is: `workers × threads_per_worker × concurrency_per_thread ≈ CPU-bound_work + I/O-bound_concurrency_budget`, and the limit is `min(RAM / per_worker_size, max_FD_count, OS_thread_limit)`.

The real sizing exercise is a memory and latency budget, not a CPU-count formula. Suppose you have a 4-core / 8 GB box, Django with PostgreSQL, a typical request takes 50 ms (10 ms CPU + 40 ms DB wait), and peak traffic is 200 RPS. A `sync` worker handles `1 / 0.050 = 20 RPS`, so you need `200 / 20 = 10` workers — but the formula says `2*4+1 = 9`, close enough. Memory check: each Django worker is ~50 MB resident, 10 workers = 500 MB, fits comfortably in 8 GB leaving 7.5 GB for the database, OS, and buffer cache. If the same app takes 200 ms per request (slow DB), one worker handles `1 / 0.200 = 5 RPS`, and 200 RPS needs 40 workers — but 40 workers × 50 MB = 2 GB, and the box is now CPU-bound at 4 cores handling 40 worker processes that are mostly waiting on the database. The fix is `gthread`: 4 workers × 16 threads = 64 concurrent slots, all sharing 4 cores' worth of GIL time but overlapping the 40 ms DB waits, with memory cost ~4 × 60 MB = 240 MB. The general rule: `sync` is for CPU-bound + fast-I/O, `gthread` is for slow-I/O (DB, upstream HTTP) at modest concurrency (10s–100s of concurrent per box), and `gevent`/`eventlet` is for high concurrency (1000s of long-lived connections — but breaks C extensions that hold the GIL across I/O).

```text
  Worker sizing decision matrix (gunicorn):

  ┌─────────────────┬─────────────────┬────────────────┬─────────────────────┐
  │ Workload        │ Worker type     │ --workers      │ --threads / -k      │
  ├─────────────────┼─────────────────┼────────────────┼─────────────────────┤
  │ CPU-bound       │ sync            │ 2*CPU+1        │ 1 (default)         │
  │ <50ms I/O       │                 │                │                     │
  ├─────────────────┼─────────────────┼────────────────┼─────────────────────┤
  │ Slow I/O        │ gthread         │ CPU_cores      │ 8-16                │
  │ 50-500ms DB     │                 │                │                     │
  ├─────────────────┼─────────────────┼────────────────┼─────────────────────┤
  │ WebSockets      │ uvicorn         │ CPU_cores      │ --worker-connections│
  │ SSE, Comet      │ (ASGI, see      │                │ 1000 (per worker)   │
  │                 │ 04.03.03)       │                │                     │
  ├─────────────────┼─────────────────┼────────────────┼─────────────────────┤
  │ 1000s of long-  │ gevent          │ CPU_cores      │ --worker-connections│

```

The production config that most Django/Flask services converge on is `gunicorn -w 4 -k gthread --threads 8 -b 0.0.0.0:8000 --max-requests 1000 --max-requests-jitter 100 --timeout 30 --graceful-timeout 10 --keep-alive 5 app:app` behind nginx. The `--max-requests 1000` recycles workers every 1000 requests to flush any memory leaks (C extensions, leaked caches); the `--max-requests-jitter 100` randomises the recycle threshold by ±100 so all four workers do not recycle simultaneously and cause a request burst to queue. The `--timeout 30` kills a worker that has not produced a response in 30 seconds (the master sends SIGABRT, then SIGKILL after `--graceful-timeout`); the `--keep-alive 5` keeps idle HTTP keep-alive connections open for 5 seconds before the worker closes them. The `--preload` flag (often forgotten) loads the application code in the master before forking — this means the COW benefit is maximal because all workers share the same initially-loaded bytecode and module state, and it surfaces import-time errors at boot instead of in the first request of each worker. The downside of `--preload` is that database connections opened at import time are shared across workers (bad — PostgreSQL connection slots are limited) and the master must restart to reload any code change.

## Cross-Runtime Comparison

| Aspect | JVM (HotSpot) | Node.js (V8) | CPython | PHP (Zend) |
|---|---|---|---|---|
| Threading | OS threads (1:1) | Single thread + libuv pool | OS threads + GIL | Processes (shared-nothing) |
| Memory | GC (G1/ZGC) | GC (Scavenger + Mark-Sweep) | Ref counting + cyclic GC | Per-request cleanup |
| Concurrency model | Multi-threaded | Event loop (epoll) | GIL serializes bytecode | Process-per-request |
| Cold start | Slow (~2s) | Fast (~50ms) | Medium (~200ms) | Fast (~10ms) |
| Best for | CPU-bound, enterprise | I/O-bound, real-time | Scripts, ML, data | Web apps, CMS |

These differences are why the same algorithm performs differently in each runtime. When you read the anchor implementation in Spring Boot (JVM), keep in mind that the delta implementations in Node.js, Python, and PHP will exhibit different failure modes under load — only CPython has the GIL, and only CPython requires the multi-processing escape hatch for CPU parallelism.
