# 04.03.01. CPython Execution and the Global Interpreter Lock

## What This Is

**CPython Execution and the Global Interpreter Lock** is the runtime that executes every Python program in the world except PyPy, GraalPy, and the experimental free-threaded CPython. CPython compiles `.py` source to `.pyc` bytecode, then walks the bytecode in a giant `switch` statement in `Python/ceval.c` called `_PyEval_EvalFrameDefault`. The defining feature of this loop is the **Global Interpreter Lock (GIL)** — a single `pthread_mutex_t` (well, a more sophisticated lock since Python 3.2, but conceptually a mutex) that must be held by any thread that wants to execute Python bytecode. The GIL is what makes CPython thread-safe at the implementation level, and it is what makes CPython unable to use more than one CPU core for pure Python code, regardless of how many threads you spawn.

This note covers four things: the CPython execution pipeline (compile to bytecode, then `ceval` loop), the reference-counting memory model with the cyclic GC backstop, the GIL itself (what it is, why it exists, how the drop-GIL-and-wait pattern works), and the practical concurrency reality (multi-threading for I/O, multi-processing for CPU). The forward link to section 05 is that every Django and Flask service inherits the GIL — and the migration from WSGI to ASGI (next two notes) is fundamentally about whether to fight the GIL with threads or escape it with coroutines.

## The Details

### CPython execution pipeline: Compilation to Python Bytecode and the evaluation loop (`_PyEval_EvalFrameDefault`).

CPython's execution pipeline is two stages: an ahead-of-time (per-import) compile from `.py` source to `.pyc` bytecode, and a runtime evaluation loop that interprets the bytecode. The compile stage is invoked by `import` (or by `compile()` directly) and is implemented in `Python/compile.c`. It parses the source into a CST (concrete syntax tree) via `Python/parser.c`, transforms the CST into an AST via `Python/ast.c`, compiles the AST into a CFG of basic blocks, and emits bytecode for each block. The bytecode is cached as a `.pyc` file in `__pycache__/` (keyed by source mtime and Python magic number) so subsequent imports skip the compile step. The bytecode format is a stack-based instruction stream where each opcode is one byte followed by an optional `oparg` (1 or 4 bytes).

The evaluation loop is `_PyEval_EvalFrameDefault` in `Python/ceval.c`. This is the famous "giant switch" — a single function with a `switch(opcode)` inside a `for(;;)` loop. The loop reads the next opcode, dispatches via the switch, executes the opcode's handler, and repeats. The handler for `LOAD_FAST` (load a local variable) reads the local from the frame's `localsplus` array and pushes it onto the value stack; the handler for `BINARY_ADD` pops two values, adds them, and pushes the result. Each handler is a few lines of C, and the whole loop runs at ~30–50 ns per bytecode on modern hardware. The classic Python performance rule of thumb — "Python is 30–80× slower than C" — comes from this: a single Python `a + b` is ~50 ns of bytecode dispatch + ~5 ns of integer addition, where the equivalent C is ~1 ns.

```text
  CPython execution pipeline:

  ┌─────────────────┐  import foo (or compile() or python -c)
  │  Source: foo.py  │
  └────────┬─────────┘
           │  parser.c  (tokenizer + recursive descent)
           ▼
  ┌─────────────────┐
  │      CST         │  concrete syntax tree
  └────────┬─────────┘
           │  ast.c
           ▼
  ┌─────────────────┐
  │      AST         │  abstract syntax tree
  └────────┬─────────┘
           │  compile.c (CFG → bytecode)
           ▼
  ┌─────────────────┐
  │   Bytecode       │  co_code in code object, cached as .pyc
  │  (LOAD_FAST,     │
  │   BINARY_ADD,    │
  │   CALL_FUNCTION, │
  │   RETURN_VALUE)  │
  └────────┬─────────┘
           │  ceval.c  (_PyEval_EvalFrameDefault)
           │  for(;;) { switch(opcode) { case LOAD_FAST: ... } }
           ▼
  ┌─────────────────┐
  │  Native execution │  each handler is a few lines of C
  │  (compiled into   │  compiled into libpython3.X.so
  │   libpython)      │
  └─────────────────┘
```

The Python 3.11 "specialising adaptive interpreter" (PEP 659) added a layer on top of this: hot bytecode opcodes are *rewritten in place* to specialised variants (`LOAD_GLOBAL` becomes `LOAD_GLOBAL_MODULE` or `LOAD_GLOBAL_BUILTIN`, `BINARY_ADD` becomes `BINARY_ADD_INT` or `BINARY_ADD_FLOAT`) based on observed operand types. This is not a JIT — there is no machine code generation — but it cuts the dispatch overhead for common patterns by 20–40%. Python 3.12 added further specialisations (`LOAD_ATTR_SLOT`, `BINARY_OP_ADD_UNICODE`). These are still interpreted, but they skip the generic dispatch path. The "Faster CPython" project (PEPs 644, 657, 659, 703, 744) is the umbrella for this work, and it is why Python 3.12 is ~5× faster than Python 3.9 on the pyperformance benchmark suite without any JIT. The experimental JIT in Python 3.13 (PEP 744, "copy-and-patch" JIT) is the next step.

### Reference Counting and Garbage Collection: Tracking reference counts and the cyclic garbage collector (Generations 0, 1, 2).

CPython's primary memory management mechanism is **reference counting**. Every `PyObject` has a `Py_ssize_t ob_refcnt` field as its first member; the macros `Py_INCREF(obj)` and `Py_DECREF(obj)` increment and decrement this count, and when the count reaches zero the object is immediately deallocated (its `tp_dealloc` slot is called, which frees the object's memory and recursively decrefs its referenced objects). This is why Python is responsive on memory — there is no GC pause for normal object lifetimes, and `del obj` frees memory immediately. It is also why Python needs the GIL: every assignment `a = b` involves a `Py_DECREF` of the old `a` and a `Py_INCREF` of `b`, and if two threads did this concurrently on the same object the refcount would be corrupted (lost decrements → memory leak; lost increments → premature free → use-after-free).

Reference counting cannot handle reference cycles. If `a.x = b; b.x = a`, both `a` and `b` have refcount 1 (from each other), but neither is reachable from any root. The refcount will never reach zero, so they will never be freed. CPython handles this with a supplementary **cyclic garbage collector** (`gc` module), implemented in `Modules/gcmodule.c`. The cyclic GC walks the object graph periodically (every 700 allocations by default, configurable via `gc.get_threshold()`), identifies unreachable cycles, and breaks them. The collector is generational: there are three generations (0, 1, 2), and objects that survive a collection are promoted to the next generation, which is collected less frequently. Generation 0 holds newly allocated objects and is scanned on every collection; generation 2 holds long-lived objects and is scanned only when the threshold is exceeded.

```text
  Reference counting (immediate) + cyclic GC (periodic):

  ┌──────────────────────────────────────────────────────────────┐
  │  IMMEDIATE (Py_INCREF/Py_DECREF on every assignment)         │
  │  - ob_refcnt goes 0 → object freed right now                │
  │  - No GC pause; memory returned as soon as it is dead       │
  │  - Cannot handle cycles: a.x=b, b.x=a → both refcnt 1      │
  └──────────────────────────────────────────────────────────────┘
                          │
                          │ cycles accumulate
                          ▼
  ┌──────────────────────────────────────────────────────────────┐
  │  CYCLIC GC (gc.collect, runs every ~700 allocations)        │
  │  Generation 0: scanned most often, holds new objects        │
  │  Generation 1: scanned when gen-0 count exceeds threshold    │
  │  Generation 2: scanned when gen-1 count exceeds threshold    │
  │  Walks object graph, finds unreachable cycles, breaks them  │
  └──────────────────────────────────────────────────────────────┘

  gc.get_threshold() → (700, 10, 10)  by default
   - 700 allocations between gen-0 scans
   - 10 gen-0 scans between gen-1 scans
   - 10 gen-1 scans between gen-2 scans
```

The production failure mode of the cyclic GC is a long pause on a large object graph. A service that holds 10 million objects in memory (a large in-memory cache, a long-running ETL pipeline) will see cyclic GC pauses of 100+ ms when generation 2 is scanned. The diagnostic is `gc.get_stats()` (Python 3.10+) which prints per-collection timing; the fix is `gc.disable()` in performance-critical code paths (accepting the cycle leak), or `gc.set_threshold(10000, 50, 50)` to scan less frequently with longer individual pauses. The Python 3.12 incremental GC (PEP 683) walks the object graph in slices instead of all at once, dramatically reducing per-pause time but adding overhead to refcount operations.

### The Global Interpreter Lock (GIL): Mutex protecting CPython memory management and reference counts from concurrent corruption.

The GIL is a single lock that must be held by any thread executing Python bytecode. It exists because CPython's memory management is not thread-safe: `Py_INCREF` and `Py_DECREF` are not atomic (they are read-modify-write on `ob_refcnt`), and the cyclic GC's object graph traversal assumes no concurrent mutation. Without the GIL, two threads assigning to the same variable could race on the refcount and corrupt the heap. The GIL solves this by serialising bytecode execution: at any instant, at most one thread is inside `_PyEval_EvalFrameDefault`. Other threads that want to run Python block on the GIL.

The GIL is implemented in `Python/ceval_gil.c` (since Python 3.2, when it was rewritten to use a `pthread_cond_t` + `pthread_mutex_t` pair instead of a plain semaphore). The implementation is the "drop-GIL-and-wait" pattern: the holder periodically checks whether another thread is waiting (every `sys.getswitchinterval()` seconds, default 5 ms in Python 3.2+, configurable via `sys.setswitchinterval()`). If a waiter exists, the holder sets `gil.drop_request = 1`, signals the condition variable, and waits on a second condition variable for the waiter to acquire and signal back. The waiter wakes, acquires the GIL, and runs for its own interval. The switch interval was 100 bytecode instructions in Python 2 (set via the C function `_PyEval_SetInterval(ticks)` and the `sys.setcheckinterval()` Python-level knob), which was fragile under C extensions that did long C-level work without dropping the GIL — a tight `while (1) {}` in a C extension would never reach the 100-tick check, starving every other Python thread forever. Python 3.2 replaced tick counting with a wall-clock interval measured against `CLOCK_MONOTONIC` via `_PyEval_SetSwitchInterval(seconds)` (the C function behind `sys.setswitchinterval`); the new default is 5 ms, which gives smoother latency but means Python threads doing pure compute now switch at most every 5 ms.

A subtle point often mis-stated in interview answers: the GIL is **not a recursive mutex** in the formal sense — it does not maintain a per-thread acquisition count, and the same thread calling `PyThread_acquire_lock` twice would self-deadlock (which is why no CPython internal code path does that). What makes it *feel* recursive to application code is that the C-API convention is "the GIL is held by whoever is currently running bytecode; C functions do not re-acquire it." When the interpreter calls into a C extension (e.g. a `tp_call` slot), the calling thread already holds the GIL and the C function inherits it implicitly; when that C function calls back into the interpreter (e.g. via `PyObject_Call`), no second acquisition happens because the interpreter knows the GIL is already held. The only place a C extension ever touches the GIL is the explicit `Py_BEGIN_ALLOW_THREADS`/`Py_END_ALLOW_THREADS` macro pair, which is the formal "I am about to do work that does not touch Python objects; release the GIL so other threads can run" escape hatch. This is the operational invariant CPython relies on, and it is why the PEP 703 free-threaded build had to audit every C extension that ever called `Py_INCREF` without holding a lock — those calls are safe under the GIL because there is only ever one mutator thread, and become data races the moment the GIL is removed.

```text
  GIL state machine (Python 3.2+):

  Thread A (holding GIL, running Python):
   ┌─────────────────────────────────────────────────────────────┐
   │  while (running):                                          │
   │      execute bytecode for ~5 ms                            │
   │      if (gil.drop_request):                                │
   │          unlock(gil.mutex)                                 │
   │          signal(gil.cond, &gil.locked=0)   // tell waiters │
   │          wait(gil.cond, gil.mutex)         // block self    │
   │          // woken when another thread releases the GIL     │
   └─────────────────────────────────────────────────────────────┘
                            ▲
                            │ signals when dropping GIL
                            │
  Thread B (waiting for GIL):
   ┌─────────────────────────────────────────────────────────────┐
   │  lock(gil.mutex)                                           │
   │  set gil.drop_request = 1                                  │
   │  while (gil.locked):                                       │
   │      wait(gil.cond, gil.mutex)            // block         │
   │  set gil.locked = 1                                       │
   │  unlock(gil.mutex)                                         │
   │  // now running Python bytecode                            │
   └─────────────────────────────────────────────────────────────┘
```

The C-extension escape hatch is the `Py_BEGIN_ALLOW_THREADS` / `Py_END_ALLOW_THREADS` macro pair. A C extension that is about to do blocking work (call `read()` on a socket, sleep, compute in a tight C loop without touching Python objects) wraps the work in these macros: `Py_BEGIN_ALLOW_THREADS` saves the current thread state and releases the GIL; the work runs without holding the GIL; `Py_END_ALLOW_THREADS` reacquires the GIL and restores the thread state. This is why `requests.get` and `socket.recv` do not block other Python threads — the underlying C code releases the GIL while waiting for I/O. It is also why NumPy can use multiple cores for matrix multiplication: the inner C loop releases the GIL and uses OpenMP to parallelise across cores. The failure mode is C extensions that do *not* release the GIL during long computations — they hold the GIL for the duration, blocking every other Python thread. The diagnostic is `py-spy` or `py-objgraph` showing a single thread at 100% CPU while the others sit at 0%.

The **PEP 703 free-threaded CPython** (experimental in Python 3.13, off by default behind `--disable-gil` build flag, the so-called `nogil` build) removes the GIL entirely. It does this by making `Py_INCREF`/`Py_DECREF` atomic (using `atomic_int` with biased reference counting — most refcount changes happen on a single thread, so biased counting is fast in the common case), adding deferred reference counting for immortal objects (small integers, None, True, False), and replacing the cyclic GC with a concurrent version. The free-threaded build achieves 2–3× speedup on CPU-bound multi-threaded workloads but pays a ~10% single-thread overhead. As of Python 3.13 it is experimental and the build must be installed explicitly (e.g. `python3.13t` on Ubuntu, `pyenv install 3.13.0t`); from Python 3.13.1 onward a free-threaded build can also be toggled at interpreter startup with `PYTHON_GIL=0` (or the `-X gil=0` flag) without recompiling, provided the interpreter was built with the `--disable-gil` option. Production adoption is expected to take 3–5 years as the C-extension ecosystem migrates to thread-safe extensions — NumPy, Pillow, and a handful of others already ship free-threaded wheels, but the long tail of C extensions (notably older Cython-generated modules) still assumes the GIL and will segfault under `nogil`.

### Concurrency reality: Multi-threading achieves concurrent I/O, but executes single-core serialized compute on CPU-bound operations.

The practical consequence of the GIL is that Python threads are useful for I/O-bound concurrency (network calls, file reads, sleeping) and useless for CPU-bound parallelism. A web scraper that spawns 10 threads to fetch 10 URLs in parallel will be ~10× faster than sequential, because each thread releases the GIL while waiting for `socket.recv`. A numerical computation that spawns 10 threads to compute 10 chunks of a matrix in parallel will run at the same speed as a single thread, because each thread holds the GIL while executing Python bytecode (and the C-level `Py_BEGIN_ALLOW_THREADS` only helps if the work is in C, not in Python).

```python
# I/O-bound: threads work
import threading, requests
def fetch(url):
    requests.get(url)   # releases GIL during socket.recv
threads = [threading.Thread(target=fetch, args=(url,)) for url in urls]
for t in threads: t.start()
for t in threads: t.join()
# Wall time ≈ max(individual fetch times), not sum

# CPU-bound: threads do NOT help
def compute(n):
    total = 0
    for i in range(n):
        total += i * i   # holds GIL throughout
    return total
threads = [threading.Thread(target=compute, args=(10_000_000,)) for _ in range(8)]
# Wall time ≈ 8 × single-thread compute time (no parallelism)
```

For CPU-bound parallelism, the standard escape is `multiprocessing` (or `concurrent.futures.ProcessPoolExecutor`), which spawns separate Python processes (via `fork()` on Linux, `spawn()` on macOS/Windows) that each have their own GIL. The downside is that inter-process communication requires serialising arguments and results through `pickle`, which is slow for large data. For pure numerical work, NumPy + `Py_BEGIN_ALLOW_THREADS` (which most NumPy operations do internally) is faster than `multiprocessing` because it avoids serialisation. For async I/O concurrency (the third option), `asyncio` (see [[04.03.03. ASGI Specification and Python Asyncio]]) is a single-threaded event loop that achieves the I/O concurrency of threads without the GIL contention, because there is only one thread.

The diagnostic for "is my Python service GIL-bound" is `py-spy record -o profile.svg --pid <pid>` which produces a flamegraph showing where threads are. If most threads are inside `eval_frame_default` (executing Python bytecode), the service is GIL-bound and will not benefit from more threads — switch to `multiprocessing` or `asyncio`. If most threads are inside `read` or `recv` (system calls, with the GIL released), the service is I/O-bound and threads are working as intended. The `py-spy dump --pid <pid>` command shows the current Python stack of every thread, which is the equivalent of `jstack` for the JVM.

## Cross-Runtime Comparison

| Aspect | JVM (HotSpot) | Node.js (V8) | CPython | PHP (Zend) |
|---|---|---|---|---|
| Bytecode eval | JIT (C2 native code) | JIT (TurboFan native code) | `ceval.c` switch loop | Zend VM switch loop |
| Thread model | OS thread per Java thread | Single thread + worker pool | OS threads + GIL | Process per request |
| Locking | Per-object monitors | None (single thread) | GIL (single global mutex) | None (process isolation) |
| Memory mgmt | Generational GC | Orinoco GC | Refcount + cyclic GC | Per-request wipe |
| CPU parallelism | Yes (threads) | Only via `worker_threads` | No (GIL); use `multiprocessing` | Yes (processes) |

These differences are why the same algorithm performs differently in each runtime. When you read the anchor implementation in Spring Boot (JVM), keep in mind that the delta implementations in Node.js, Python, and PHP will exhibit different failure modes under load — only CPython has the GIL, and only CPython requires the multi-processing escape hatch for CPU parallelism.
