# 04.03.03. ASGI Specification and Python Asyncio

## What This Is

**ASGI (Asynchronous Server Gateway Interface)** is the asynchronous successor to WSGI, born in 2017 out of the Django Channels project to support WebSockets and HTTP/2 server push. Where WSGI is a single-callable-per-request synchronous spec (`app(environ, start_response)` returning a list of bytes), ASGI is a two-callable-per-connection asynchronous spec (`async def app(scope, receive, send)` entered once per connection and called many times to handle the protocol events of that connection). ASGI sits on top of Python's `asyncio` event loop — the standard-library event loop introduced in Python 3.4 (PEP 3156, "Tulip") and refined through 3.5's `async`/`await` syntax (PEP 492), 3.7's `asyncio.run()`, 3.11's `TaskGroup` and exception groups, and 3.12's eager task factories. Together, ASGI + asyncio let a single Python process handle thousands of concurrent I/O-bound connections (HTTP, WebSockets, SSE, gRPC) without threads — the same concurrency model Node.js has had since 2009, but using Python's native coroutine syntax instead of callbacks.

The reason ASGI exists is that WSGI cannot represent a long-lived connection. WSGI's `environ` dict and `start_response` callable are designed for "one request, one response, then close" — the synchronous call graph of HTTP/1.0. A WebSocket connection, by contrast, lives for hours, receives messages at unpredictable intervals, and the server must push messages back without an incoming request to "respond to." WSGI's `app(environ, start_response)` cannot model this because it returns once and the connection is over. ASGI's `async def app(scope, receive, send)` models it directly: `receive` is an `await`-able that yields the next event (`{"type": "websocket.connect"}`, `{"type": "websocket.receive", "text": "..."}`, `{"type": "websocket.disconnect"}`), and `send` is an `await`-able that emits an outbound event. The forward link to section 05 is FastAPI, Starlette, Django's ASGI handler, Litestar, and BlackSheep — all built on ASGI. The backward link to section 02 is the `epoll_wait` syscall that asyncio's default selector (`selectors.EpollSelector` on Linux) calls once per loop iteration.

## The Details

### Asynchronous Server Gateway Interface (ASGI): Lifespan, HTTP, and WebSocket protocol co...

The ASGI specification (version 3.0, the current and stable version) defines a single callable with the signature `async def app(scope, receive, send)`. The `scope` is a dict that describes the connection — for HTTP it contains `{"type": "http", "method": "GET", "path": "/users/42", "query_string": b"fields=name", "headers": [(b"host", b"api.example.com"), ...], "client": ("10.0.0.5", 54321), "server": ("api.example.com", 443), "scheme": "https", "asgi": {"version": "3.0", "spec_version": "2.3"}}`. For WebSockets it is `{"type": "websocket", "path": "/ws/chat", "headers": [...], ...}`. For the lifespan protocol it is `{"type": "lifespan"}`. The `receive` coroutine yields event dicts as they arrive from the network; for HTTP this is `{"type": "http.request", "body": b"...", "more_body": False}` (and possibly multiple chunks if `more_body` is True), followed by `{"type": "http.disconnect"}` when the client goes away. For WebSockets it is `{"type": "websocket.connect"}`, then zero or more `{"type": "websocket.receive", "text": "..." or "bytes": b"..."}`, then `{"type": "websocket.disconnect", "code": 1000}`. The `send` coroutine takes event dicts in the opposite direction — `{"type": "http.response.start", "status": 200, "headers": [...]}`, `{"type": "http.response.body", "body": b"...", "more_body": False}`, or for WebSockets `{"type": "websocket.accept"}`, `{"type": "websocket.send", "text": "..."}`, `{"type": "websocket.close", "code": 1000}`.

The Lifespan protocol is the third ASGI protocol, and it is what makes ASGI applications start-up- and shutdown-aware. When the server boots, it sends `{"type": "lifespan.startup"}` to the application; the application runs its startup code (open database pools, warm caches, register signal handlers) and replies `{"type": "lifespan.startup.complete"}` or `{"type": "lifespan.startup.failed", "message": "..."}`. On shutdown (SIGTERM), the server sends `{"type": "lifespan.shutdown"}` and waits for `{"type": "lifespan.shutdown.complete"}` before exiting. This is how FastAPI's `@app.on_event("startup")` and the modern `lifespan: asynccontextmanager` pattern work, and how Django's `async_ready()` ASGI apps register their startup hooks. Without the lifespan protocol, ASGI apps would have to open database connections lazily on the first request — which is what WSGI apps do, and it is why the first request after a deploy is always slow.

```python
# A minimal ASGI application that handles HTTP, WebSocket, and Lifespan.
async def app(scope, receive, send):
    if scope["type"] == "lifespan":
        while True:
            message = await receive()
            if message["type"] == "lifespan.startup":
                # Open DB pool, warm caches, etc.
                await send({"type": "lifespan.startup.complete"})
            elif message["type"] == "lifespan.shutdown":
                # Close DB pool, flush logs, etc.
                await send({"type": "lifespan.shutdown.complete"})
                return
    elif scope["type"] == "http":
        # Read the full request (one event for small bodies, multiple for large)
        body = b""
        more_body = True
        while more_body:
            message = await receive()
            body += message.get("body", b"")
            more_body = message.get("more_body", False)
        # Send the response: response.start then response.body
        await send({
            "type": "http.response.start",
            "status": 200,
            "headers": [(b"content-type", b"application/json")],
        })
        await send({
            "type": "http.response.body",
            "body": b'{"hello":"world"}\n',
        })
    elif scope["type"] == "websocket":
        # First event must be websocket.connect
        event = await receive()
        if event["type"] != "websocket.connect":
            return
        # Accept the handshake — this sends the HTTP 101 response
        await send({"type": "websocket.accept", "subprotocol": None})
        # Echo loop — runs forever until the client disconnects
        while True:
            event = await receive()
            if event["type"] == "websocket.disconnect":
                return  # connection is gone, this coroutine exits
            if event["type"] == "websocket.receive":
                text = event.get("text", "")
                await send({"type": "websocket.send", "text": f"echo: {text}"})

# Run with: uvicorn app:app --workers 4
```

The reason ASGI is the only Python spec that can do WebSockets is the receive/send event model. A WebSocket connection is fundamentally a bidirectional stream of frames, not a request/response — the client may send ten messages, the server may send five, in any interleaving, over a connection that lives for hours. WSGI's synchronous call graph cannot represent this; the only way to do WebSockets under WSGI is to give up on the WSGI app and run a separate protocol demultiplexer in the server (the old `gevent-websocket` hack, where a "WebSocket" upgrade short-circuits the WSGI app and hands the socket to a websocket handler). ASGI's `await receive()` / `await send()` model handles WebSockets natively because each `await` is a suspension point — the coroutine yields control to the event loop, which can run thousands of other coroutines on the same thread while this one waits for the next WebSocket frame. The same machinery handles SSE (Server-Sent Events, where the server emits a long unidirectional stream) and HTTP/2 server push.

The production failure mode of ASGI is forgetting to handle `http.disconnect`. If a client closes the connection mid-response and the application keeps calling `await send(...)`, the send raises `ConnectionClosedError` (or a similar runtime exception) — which, if uncaught, will crash the task and surface as a 500 in the logs even though the client never saw a response. The fix is `try: await send(...) except (ConnectionClosedError, ClientDisconnect): return` and to check the `http.disconnect` event between chunks when streaming large responses. The second failure mode is the lifespan startup failing — if the application raises an exception during `lifespan.startup`, the server replies `lifespan.startup.failed` and exits, which on Kubernetes means a CrashLoopBackOff. The diagnostic is `uvicorn --log-level debug app:app` to see the lifespan events, or `daphne -v 3 app:app`.

### The Python `asyncio` event loop: Coroutines, Tasks, and Futures

`asyncio` (the standard-library module, `Lib/asyncio/` in the CPython source) is built on three primitives: coroutines, Tasks, and Futures. A **coroutine** is a function declared `async def` — calling it does not execute the body, it returns a *coroutine object* that must be awaited or scheduled. A **Task** is a coroutine that has been scheduled to run on the event loop — `asyncio.create_task(coro)` wraps the coroutine in a Task and submits it; the loop will run it to completion on its next iteration. A **Future** is a low-level promise object with `set_result()` and `set_exception()` methods — Tasks are Futures with a coroutine driving them, but plain Futures are used by I/O libraries to bridge between callback-style C code and asyncio (e.g. `loop.sock_recv(sock, n)` returns a Future that the loop resolves when `epoll_wait` reports the socket readable). The event loop itself is a single Python object (`asyncio.BaseEventLoop`, concretely `_UnixSelectorEventLoop` on POSIX) with a `run_forever()` method that calls `select.select()` / `selectors.EpollSelector.select()` once per iteration, processes the ready callbacks, runs the ready Tasks' coroutines until they `await` again, then loops.

The key mechanics are `loop.create_task()` (schedules a coroutine to run concurrently with the caller — both run on the same thread, switching at `await` points), `asyncio.gather(*coros)` (runs N coroutines concurrently and returns a list of their results in order — equivalent to `Promise.all` in JavaScript), and `asyncio.wait_for(coro, timeout)` (runs a coroutine with a timeout, raising `asyncio.TimeoutError` if it does not complete in time). All three are non-preemptive: a coroutine runs until it `await`s, then control returns to the loop. This is why a single CPU-bound computation inside an async function blocks the entire loop — there is no `await` to yield at, so no other task can run. The fix is `await asyncio.to_thread(blocking_fn, *args)` (Python 3.9+, runs the function in a `ThreadPoolExecutor` and awaits the result) or `loop.run_in_executor(executor, fn, *args)` (the lower-level API), both of which push the blocking work to a worker thread and return an awaitable.

```python
import asyncio
import httpx
import time

async def fetch_one(client, url):
    # 'async with' is the async equivalent of 'with' — __aenter__ / __aexit__
    # Both await points yield control back to the event loop.
    async with client.get(url) as resp:
        return await resp.json()

async def main():
    # asyncio.gather runs N coroutines concurrently on ONE thread.
    # Total wall time ≈ max(individual fetches), not sum.
    async with httpx.AsyncClient() as client:
        urls = [f"https://api.example.com/users/{i}" for i in range(50)]
        start = time.monotonic()
        results = await asyncio.gather(*[fetch_one(client, u) for u in urls])
        elapsed = time.monotonic() - start
        print(f"fetched {len(results)} users in {elapsed:.2f}s")

# asyncio.run() creates a fresh event loop, runs main() to completion,
# then closes the loop. Use this for the top-level entry point only;
# never call asyncio.run() from inside a running loop.
asyncio.run(main())

# Contrast: doing the same work synchronously would take ~50x as long
# (50 sequential HTTP requests × 200ms each = 10s; concurrent = 200ms).

# CPU-bound work that must not block the loop:
def slow_hash(password: str) -> str:
    # bcrypt is C-extended and releases the GIL, but the loop doesn't know that
    import bcrypt
    return bcrypt.hashpw(password.encode(), bcrypt.gensalt(14)).decode()

async def signup(password: str):
    # Push the blocking bcrypt call to a thread — the loop keeps running
    hashed = await asyncio.to_thread(slow_hash, password)
    return hashed
```

The difference between async/await coroutines and OS threads is the difference between cooperative and preemptive multitasking. A coroutine yields only at `await` points; the event loop never preempts a running coroutine. An OS thread can be preempted by the kernel scheduler at any instruction — between two bytecode opcodes, between two machine instructions, between a function call and its return. This means coroutines are cheaper (no per-coroutine stack — Python uses a heap-allocated `Frame` object instead, ~1 KB vs. 1 MB for a default thread stack) and faster to switch (~200 ns vs. ~2 µs for a thread context switch), but they require the programmer to remember to `await` at every I/O point. The classic async bug is calling `requests.get(url)` inside an async function — `requests` is synchronous, so the call blocks the entire event loop until the HTTP response arrives, freezing every other coroutine on the loop for the duration. The diagnostic is `asyncio.get_event_loop().slow_callback_duration = 0.1` (logs any callback that takes >100ms) or `py-spy dump --pid <pid>` showing the loop stuck inside `socket.recv` inside `requests.models` inside an async function.

The reason ASGI scales to thousands of connections per worker is that each connection is a coroutine, and coroutines are ~1 KB each — 10,000 of them is 10 MB, vs. 10 GB for 10,000 OS threads at 1 MB stack each. The trade-off is that the application code must be async from top to bottom: every I/O call must be awaited, every library must be async-aware (the `httpx` async client, not `requests`; the `asyncpg` driver, not `psycopg2`; the `motor` MongoDB driver, not `pymongo`; the `aioredis` driver, now folded into `redis-py` 4.2+ as `redis.asyncio`). Mixing one synchronous library into an async app is enough to destroy the concurrency model — this is the same constraint Node.js has had since 2009, and it is why the Python async ecosystem took until ~2020 (when `httpx`, `asyncpg`, and FastAPI all reached maturity) to be production-viable.

### ASGI Servers: Uvicorn architecture (uvloop C-based libuv bindings for Python)

The three production ASGI servers are **uvicorn** (the most popular, ~7k stars, used by FastAPI and Starlette as the default), **daphne** (the Django Channels server, older, slower, but mature), and **hypercorn** (the feature-richest, supports HTTP/2 and HTTP/3 natively, used by Quart and Litestar). All three implement the same ASGI 3.0 spec; they differ in their HTTP parser, their event loop, and their protocol support. Uvicorn's distinguishing feature is `uvloop`, a drop-in replacement for `asyncio`'s default selector-based loop that is implemented in Cython on top of `libuv` (the same C library Node.js uses). Uvicorn with `--loop uvloop` is 2–4× faster than uvicorn with `--loop asyncio` (the default), and 4–6× faster than daphne, on the TechEmpark JSON benchmark. The `httptools` package (Python bindings to the Node.js `http-parser` C library) provides uvicorn's HTTP parser — also ~2× faster than the pure-Python `h11` parser that hypercorn uses. Uvicorn's standard production invocation is `gunicorn -k uvicorn.workers.UvicornWorker -w 4 app:app` — gunicorn manages the pre-fork worker pool, each worker runs a uvicorn server with its own uvloop.

The uvloop architecture is a Python-callable wrapper around `libuv`'s `uv_run()` C function. Where asyncio's default loop does `select.select()` (or `selectors.EpollSelector.select()` on Linux) once per iteration, uvloop calls `uv_run()` which calls `epoll_wait()` directly with batched I/O callbacks — the difference is that uvloop batches ready callbacks across multiple event types (timers, I/O, signals, async handles) into one `epoll_wait` syscall, while asyncio's selector loop often does separate syscalls per type. uvloop also implements its own `Task` and `Future` classes in Cython, bypassing Python's method-call overhead for the hot path. The `uvloop.install()` function (or `asyncio.set_event_loop_policy(uvloop.EventLoopPolicy())`) replaces the default `asyncio.SelectorEventLoop` with `uvloop.Loop` for the current thread. The downside of uvloop is that it is a C extension that must be compiled — on Alpine Linux (musl libc) this used to be a problem before wheels were widely available, and on Windows uvloop is not supported (Windows asyncio uses `ProactorEventLoop` based on IOCP, see [[02.05.05. High-Performance Event Architecture Patterns]] for the Reactor vs Proactor distinction).

The FastAPI/Starlette/Django ASGI stack is a layered architecture: the ASGI server (uvicorn/daphne/hypercorn) at the bottom parses HTTP and dispatches to the application's `async def app(scope, receive, send)` callable; the framework (FastAPI = Starlette + Pydantic + dependency injection) wraps that callable in middleware (CORS, GZip, exception handlers, sessions), routing (path matching → endpoint function), and serialisation (Pydantic models → JSON via `json.dumps` or `orjson.dumps`); Django 3.0+ has a parallel `ASGIHandler` that runs the same ORM/middleware/views as the WSGI handler but on the event loop. The compatibility constraint is "the whole stack must be async" — FastAPI requires async database drivers (`asyncpg`, `databases`, `tortoise-orm`), async template engines (rare — most are sync, run them with `asyncio.to_thread`), and async HTTP clients (`httpx.AsyncClient`). Django's async support is partial: ORM queries became awaitable in 4.1 but some operations (e.g. `Model.objects.create()` inside an `async def` view) still need `sync_to_async`. The litmus test is to run the app with `uvicorn --loop uvicorn --log-level info` and watch for "Async generator ignored" warnings or `RuntimeWarning: coroutine was never awaited` — both indicate a sync/async boundary violation that will silently break under load.

### Mixed execution hazards: Invoking blocking synchronous code inside async event loops an...

The single most common production failure in ASGI apps is calling a blocking synchronous function inside an `async def` view. The failure is invisible in development (the loop has one connection, the block takes 50 ms, nobody notices) and catastrophic in production (the loop has 5,000 connections, the block takes 50 ms, every one of the 5,000 connections stalls for 50 ms, the load balancer marks the box unhealthy, the cascade kills the service). The pattern is any synchronous I/O or CPU-bound call inside an async function: `requests.get(url)` (use `httpx.AsyncClient` instead), `psycopg2.connect(...).execute(...)` (use `asyncpg` or `psycopg` 3 in async mode), `time.sleep(1)` (use `await asyncio.sleep(1)`), `bcrypt.hashpw(pw, salt)` (use `await asyncio.to_thread(bcrypt.hashpw, pw, salt)`), `subprocess.run(...)` (use `asyncio.create_subprocess_exec(...)`), `open("file").read()` (use `aiofiles.open(...)`), and — the most insidious — `json.loads(huge_payload)` (no async equivalent; chunk the work or use `asyncio.to_thread`).

The `asyncio.to_thread()` function (Python 3.9+, the high-level wrapper around `loop.run_in_executor()`) is the standard escape hatch for "this library is synchronous but I must use it from async code." It pushes the call to a `ThreadPoolExecutor` (the loop's default, configurable via `loop.set_default_executor()`) and returns an awaitable that resolves when the thread finishes. The thread releases the GIL during any I/O syscall, so other coroutines on the loop's main thread continue to run — `requests.get` in a `to_thread` call works fine. The catch is CPU-bound Python: `bcrypt.hashpw` is C-extended and releases the GIL, so `to_thread` works; but `hashlib.sha256(data).hexdigest()` for a 100 MB `data` is pure C and does release the GIL, while a tight Python `for` loop does not. For CPU-bound Python code, the right escape is `ProcessPoolExecutor` (separate process, separate GIL, but pay serialisation cost) — or, more pragmatically, write the hot path in C/Rust/Cython and release the GIL with `Py_BEGIN_ALLOW_THREADS` (see [[04.03.01. CPython Execution and the Global Interpreter Lock]]).

```python
import asyncio
import requests  # synchronous!
import bcrypt    # C-extended, releases GIL
import json

# THE WRONG WAY — blocks the event loop:
async def bad_signup(payload: dict):
    # Each line below blocks the entire event loop:
    password = payload["password"]
    hashed = bcrypt.hashpw(password.encode(), bcrypt.gensalt(14))  # ~300ms
    resp = requests.post("https://api.example.com/users",
                         json={"password": hashed.decode()})  # ~200ms
    return resp.json()
# Total loop-stall: ~500ms per signup. 1000 signups/sec = 500s of stall/sec
# = the event loop is blocked 50000% of the time = service is dead.

# THE RIGHT WAY — offload to threads:
async def good_signup(payload: dict):
    password = payload["password"]
    # bcrypt.hashpw releases the GIL, so other coroutines keep running:
    hashed = await asyncio.to_thread(bcrypt.hashpw,
                                     password.encode(),
                                     bcrypt.gensalt(14))
    # requests is sync but the thread releases GIL on socket.recv:
    resp = await asyncio.to_thread(
        requests.post,
        "https://api.example.com/users",
        json={"password": hashed.decode()},
    )
    return resp.json()

# THE BEST WAY — use async-native libraries:
import httpx
import asyncpg

async def best_signup(payload: dict, db: asyncpg.Connection):
    password = payload["password"]
    hashed = await asyncio.to_thread(bcrypt.hashpw,
                                     password.encode(),
                                     bcrypt.gensalt(14))
    async with httpx.AsyncClient() as client:
        resp = await client.post("https://api.example.com/users",
                                  json={"password": hashed.decode()})
    # No threads involved — pure async I/O on the event loop.
    return resp.json()
```

The diagnostic for blocking code in production is `PYTHONASYNCIODEBUG=1` (enables asyncio's debug mode at startup, which logs any callback that takes longer than `loop.slow_callback_duration` — default 100 ms) and `py-spy record -o profile.svg --pid <pid>` (samples the process at 100 Hz and shows the flamegraph — if the hot path is inside `socket.recv` inside `requests` inside an `async def`, you have found the blocker). The fix is mechanical: replace the sync library with its async equivalent, or wrap the call in `asyncio.to_thread`. The rule of thumb is "if the function calls into the OS or the network, it must be `await`-able in async code; if it does pure computation, push it to `to_thread` only if it releases the GIL, otherwise use `ProcessPoolExecutor` or rewrite." The deeper architectural rule is "do not mix sync and async code in the same call graph" — pick one model per service, or per worker, and stick to it. This is why FastAPI's documentation is so emphatic about `async def` vs `def` for endpoint functions: a plain `def` endpoint in FastAPI is automatically run in a threadpool (Starlette's `run_in_threadpool`), which preserves correctness but loses the async advantage; an `async def` endpoint that calls blocking code silently destroys the event loop. The PEP 703 free-threaded CPython (see [[04.03.01. CPython Execution and the Global Interpreter Lock]]) may eventually make this less critical — if the GIL is gone, blocking calls in async code can run on other OS threads without the loop-stall problem — but the async/sync discipline will remain important for predictability and for not overwhelming thread pools.

## Cross-Runtime Comparison

| Aspect | JVM (HotSpot) | Node.js (V8) | CPython | PHP (Zend) |
|---|---|---|---|---|
| Threading | OS threads (1:1) | Single thread + libuv pool | OS threads + GIL | Processes (shared-nothing) |
| Memory | GC (G1/ZGC) | GC (Scavenger + Mark-Sweep) | Ref counting + cyclic GC | Per-request cleanup |
| Concurrency model | Multi-threaded | Event loop (epoll) | GIL serializes bytecode | Process-per-request |
| Cold start | Slow (~2s) | Fast (~50ms) | Medium (~200ms) | Fast (~10ms) |
| Best for | CPU-bound, enterprise | I/O-bound, real-time | Scripts, ML, data | Web apps, CMS |

These differences are why the same algorithm performs differently in each runtime. When you read the anchor implementation in Spring Boot (JVM), keep in mind that the delta implementations in Node.js, Python, and PHP will exhibit different failure modes under load — only CPython has the GIL, and only CPython requires the multi-processing escape hatch for CPU parallelism.
