# 04.00. Map of Content: Runtime Concurrency

## Overview

Section 04 covers the four runtimes that anchor every backend framework in the vault: the JVM (HotSpot), V8 (Node.js), CPython, and the Zend Engine (PHP). The OS kernel from section 02 hands you raw primitives — `clone()` for threads, `epoll_wait()` for readiness, `mmap()` for memory, `open()`/`read()` for files — but no user-space framework talks to those primitives directly. Each runtime is a user-space wrapper that decides how bytecode is executed, how memory is reclaimed, how concurrency is expressed, and how I/O is multiplexed. This section is the bridge between the kernel notes you read in section 02 and the framework abstractions you will build in section 05: when a Spring Boot handler takes 800 ms, the answer is almost never "Spring is slow" — it is somewhere in this section, whether as a GC pause, an event-loop stall, GIL contention, or FPM pool exhaustion.

The four runtimes make four deliberately different bets. The JVM bets on OS threads plus a generational garbage collector plus a tiered JIT — slow to start, fast at steady state, expensive per connection. Node.js bets on a single-threaded event loop plus a small worker pool — cheap at scale, fragile under CPU load. CPython bets on a single bytecode evaluator guarded by the GIL — simple, but you must escape it via `multiprocessing` or `asyncio` for real concurrency. PHP bets on shared-nothing process-per-request isolation — no cross-request memory leaks, but every request pays a bootstrap tax. Reading this section is reading the four answers to the same question: how do you make a kernel do useful work for thousands of concurrent HTTP clients?

## Conceptual Roadmap

The four sub-sections are not arbitrary — they are four different answers to the same three questions: how is code executed, how is memory reclaimed, and how is concurrency expressed?

```text
                       Execution          Memory           Concurrency
                       ─────────          ───────          ───────────
  JVM (04.01)          Tiered JIT         Generational GC   OS threads + locks
  Node.js (04.02)      V8 pipeline        Orinoco GC        Single-thread + pool
  CPython (04.03)      ceval + GIL        Refcount + cyclic Pre-fork OR asyncio
  PHP (04.04)          Zend VM + OPcache  Per-request wipe  Pre-fork processes
```

Read 04.01 first because the JVM has the most mature tooling (`jstack`, `jstat`, `jcmd`, GC logs) and the cleanest specification (the Java Memory Model). Then read 04.02 because Node's event loop is the cleanest example of the reactor pattern and is what every other runtime emulates when it adds async I/O. Then read 04.03 — CPython sits between the two: it has a GIL like Node has a single thread, but its WSGI/ASGI split mirrors the JVM's choice between thread-per-request and async. Finally, read 04.04 — PHP's shared-nothing model is the simplest of all, but the long-running PHP runtimes in 04.04.03 deliberately converge back toward the JVM/Node model, which is the unifying punchline of the section.
