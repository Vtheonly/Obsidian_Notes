# 04.04.01. Zend Engine and the Shared-Nothing Lifecycle

## What This Is

The **Zend Engine** is the C implementation that executes every PHP program in the world (except HHVM, which is now legacy). It was written by Zeev Suraski and Andi Gutmans in 1999 as a rewrite of PHP/FI 2.0's interpreter, shipped as PHP 4 in 2000, and has been the engine of every PHP release since — including the modern PHP 8.x line. The Zend Engine compiles PHP source into Zend opcodes (a stack-based bytecode), executes those opcodes on the Zend VM (a `switch`-dispatch loop in `Zend/zend_vm_execute.h` analogous to CPython's `_PyEval_EvalFrameDefault`), and on every HTTP request performs a complete teardown of all state — every variable, every object, every database connection, every static class property — before the next request begins. This **shared-nothing lifecycle** is the defining architectural choice of PHP, and it is why PHP scales horizontally by default: there is no in-process state to coordinate across workers, no cache to invalidate, no session lock to release (sessions live in files by default), no connection pool to grow without bound. Every request is a fresh bootstrap, every response is a clean shutdown.

The forward link to section 05 is Laravel and Symfony — every PHP framework you will see in the framework section runs inside this shared-nothing envelope, and every framework's design (Laravel's service container, Symfony's compiled DI container, Doctrine's ORM) is shaped by the constraint that the bootstrap cost is paid on every request. The backward link to section 02 is `fork()` (PHP-FPM workers are forked from a master, see [[04.04.02. FastCGI Protocol and PHP-FPM Pool Architecture]]) and the POSIX shared-memory APIs (`shmget`/`shmat` for OPcache's shared opcode cache). The contrast with the JVM (long-lived process, GC-managed heap, persistent connection pools) and with CPython (GIL-protected long-lived interpreter) is the deepest architectural split in backend engineering: PHP chose "short-lived process" and built an entire ecosystem around hiding the cost of that choice, while the JVM and Node chose "long-lived process" and built their ecosystems around managing the leaks that choice produces.

## The Details

### Compilation pipeline: Lexical Analysis → Abstract Syntax Tree → Zend Opcodes → Execution in Zend VM.

PHP's compilation pipeline is four stages, executed on every `include`/`require` whose source file is newer than its cached opcodes. The **lexer** (`Zend/zend_language_scanner.l`, a re2c input file) tokenises the PHP source into tokens — `T_OPEN_TAG` (`<?php`), `T_VARIABLE` (`$foo`), `T_STRING` (`bar`), `T_FUNCTION` (`function`), etc. The **parser** (`Zend/zend_language_parser.y`, a bison grammar) consumes the token stream and produces an Abstract Syntax Tree (`zend_ast` nodes). The AST was added in PHP 7.0 (2015); before that, the parser emitted opcodes directly, which made things like anonymous classes and complex type declarations hard to implement. The **compiler** (`Zend/zend_compile.c`) walks the AST and emits `zend_op` opcodes into an `op_array` (one per function or script). The **VM** (`Zend/zend_vm_execute.h`, auto-generated from `Zend/zend_vm_def.skl` by `Zend/zend_vm_gen.php`) executes the `op_array` via a `switch(opcode)` dispatch loop — exactly like CPython's `ceval.c`, but with the Zend opcode set (`ZEND_ASSIGN`, `ZEND_ADD`, `ZEND_FETCH_DIM_R`, `ZEND_DO_FCALL`, `ZEND_RETURN`).

Each `zend_op` is 32 bytes on a 64-bit system, holding an opcode byte, two operand structs (each 16 bytes — type + value), an `extended_value` for extra flags, a line number for error reporting, and a result operand. The operand types are `IS_CONST` (literal value, e.g. the integer `42` or the string `"hello"`), `IS_VAR` (a temporary with a refcount, returned from function calls), `IS_TMP_VAR` (a temporary without a refcount, e.g. the result of `1 + 2`), and `IS_CV` (compiled variable — a named local variable like `$foo`, stored in the frame's slot array). The Zend VM has two execution modes: the "CALL" handler (default, the most portable, uses C function calls between opcodes), the "SWITCH" handler (a single `switch(opcode)` loop, used by default on most platforms), the "GOTO" handler (uses computed `goto` labels, slightly faster on GCC), and the "HYBRID" handler (PHP 7.4+, a mix of SWITCH and GOTO tuned for branch prediction). The choice is made at compile time via `--enable-zend-signaling` and the `ZEND_VM_KIND` constant. The HYBRID handler is ~5–10% faster than SWITCH on modern CPUs because the hot opcodes (`ZEND_ASSIGN`, `ZEND_FETCH_OBJ_R`, `ZEND_DO_FCALL`) use direct threaded labels, eliminating the central `switch` branch mispredict.

```text
  PHP compilation pipeline (per script, cached by OPcache):

  ┌──────────────────┐
  │  Source: Foo.php  │  <?php class Foo { public function bar(): int { return 42; } }
  └────────┬──────────┘
           │  re2c lexer   (Zend/zend_language_scanner.l)
           ▼
  ┌──────────────────┐
  │  Token stream     │  T_OPEN_TAG T_CLASS T_STRING("Foo") "{" T_PUBLIC T_FUNCTION ...
  └────────┬──────────┘
           │  bison parser  (Zend/zend_language_parser.y)
           ▼
  ┌──────────────────┐
  │  AST              │  ZEND_AST_CLASS(name="Foo", flags=PUBLIC,
  │                   │                stmts=[ZEND_AST_METHOD(name="bar",
  │                   │                            returnType=IS_LONG,
  │                   │                            stmts=[ZEND_AST_RETURN(ZEND_AST_ZVAL(42))])])
  └────────┬──────────┘
           │  zend_compile.c → zend_op_array
           ▼
  ┌──────────────────┐  Stored in shared memory by OPcache:
  │  Zend Opcodes    │   - op1, op2, result, opcode, extended_value, lineno
  │  (zend_op[])     │   - ZEND_DECLARE_CLASS "Foo"
  │                   │   - ZEND_RETURN 42
  └────────┬──────────┘
           │  Zend VM (Zend/zend_vm_execute.h, HYBRID handler)
           │  for(;;) { switch(opcode) { case ZEND_RETURN: ... } }
           ▼
  ┌──────────────────┐
  │  Native execution │  Each handler is a few lines of C, compiled into libphp.so
  └──────────────────┘

  Without OPcache, steps 1-3 run on every request — a Symfony controller
  can be ~5,000 opcodes across ~50 files = ~50ms of compile time per request.
  With OPcache, steps 1-3 run once per file change; only step 4 runs per request.
```

The PHP 8.0 release (Nov 2020) added the JIT compiler (the Opcache JIT, written by Dmitry Stogov), which compiles hot Zend opcodes into native x86_64/arm64 machine code using a DynASM-derived code generator. The JIT has two modes: `opcache.jit=tracing` (the default in 8.0+, traces execution and specialises hot paths) and `opcache.jit=function` (compiles whole functions at first call). The tracing JIT can speed up CPU-bound PHP code by 1.5–3× (the Symfony benchmark showed ~20% RPS improvement, the Mandelbrot benchmark ~2.5×), but it does not help I/O-bound webapps much — the bottleneck is the database, not the PHP. The JIT is stored in `SHM` alongside the opcodes (configurable size via `opcache.jit_buffer_size=64M`). The failure mode is "JIT bugs": rare segfaults caused by incorrect native code generation, which is why many production deployments still ship with `opcache.jit=off` for safety. The diagnostic is to switch to `opcache.jit=1205` (tracing, on) vs `opcache.jit=off` and compare RPS — if the JIT is crashing, switch it off and report to bugs.php.net.

### OPcache: Caching compiled Zend Opcodes in shared memory to eliminate per-request file parsing.

OPcache (the `Zend OPcache` extension, enabled by default since PHP 5.5, configured in `php.ini` under the `opcache.*` namespace) is the single biggest PHP performance optimisation available. Without OPcache, every HTTP request re-reads every PHP file from disk, re-lexes it, re-parses it, and re-compiles it to opcodes — for a Laravel controller, that's ~200 files × ~3 ms = ~600 ms of compile time per request, before any business logic runs. With OPcache, the compiled `zend_op_array` for each file is stored in a shared-memory segment (`opcache.file_cache` fallback on disk if SHM is full), keyed by the file's full path and its mtime/inode, and every worker process `mmap`s this segment read-only. The compilation cost is paid once per file change; subsequent requests jump straight to the VM dispatch loop. The measured speedup is 2–5× for typical apps, 5–10× for apps with deep dependency trees (Symfony, Magento).

The OPcache shared-memory layout is a single large `mmap`'d region (default `opcache.memory_consumption=128` MB, raised to `256` or `512` MB on production Laravel/Symfony boxes). Internally it is a slab allocator with a hash table indexed by file path; each entry stores the `zend_op_array`, the strings and literal constants referenced by the opcodes, and the class entries (`zend_class_entry`) for declared classes. The key tuning parameters are `opcache.memory_consumption` (raise if the cache is full — check `opcache_get_status()["memory_usage"]["used_memory"]` and `["num_cached_keys"]`), `opcache.max_accelerated_files` (default 10000, raise to 40000 for Symfony — each PHP file is one entry), `opcache.validate_timestamps` (default 1, set to 0 in production for max performance and use `opcache_reset()` or `kill -USR2 <fpm-master>` to reload on deploy), `opcache.revalidate_freq` (when `validate_timestamps=1`, how often to `stat()` the file — default 2 seconds), and `opcache.save_comments` (default 1, keep doc comments for annotation readers — Doctrine and Symfony rely on this, set to 0 only if you use no annotation-based metadata). The `opcache.preload` directive (PHP 7.4+) allows pre-compiling a list of files at FPM startup — a Laravel `preload.php` script that includes all of `vendor/` and `app/` can cut 50 ms off the first-request latency.

```ini
; /etc/php/8.3/fpm/conf.d/10-opcache.ini — production OPcache config
zend_extension=opcache

opcache.enable=1                  ; master switch (CLI defaults to 0)
opcache.enable_cli=1              ; enable for 'php' CLI too (for tests, queue workers)

; Memory budget — raised from default 128 MB for Symfony/Laravel apps.
; Check opcache_get_status()["memory_usage"]["used_memory"] periodically;
; if used_memory > 90% of this, raise it or you'll get cache evictions.
opcache.memory_consumption=256

; Max cached files. Symfony 6 standard app: ~8000 files. Magento 2: ~30000.
; Each cached file uses ~20 KB average, so 40000 files × 20 KB ≈ 800 MB worst case.
opcache.max_accelerated_files=40000

; Production: validate timestamps off (no stat() per request) + manual reset on deploy.
; Staging/dev: validate_timestamps=1, revalidate_freq=0 (immediate).
opcache.validate_timestamps=0
opcache.revalidate_freq=0

; Save doc comments — Doctrine ORM, Symfony Validator, PHPUnit annotations all read these.
opcache.save_comments=1
opcache.save_pre_comments=1

; PHP 8.0+ JIT — tracing mode, on. Set buffer to 64 MB.
; Turn off if you see segfaults; report the bug.
opcache.jit_buffer_size=64M
opcache.jit=1255

; PHP 7.4+ preload — pre-compile the framework core at FPM startup.
; The preload script should require_once all of vendor/ and app/ classes.
opcache.preload=/var/www/app/preload.php
opcache.preload_user=www-data
```

The production failure mode of OPcache is **stale cache after deploy**. With `validate_timestamps=0` (the production setting for max throughput), PHP never checks the file's mtime — it trusts the cache forever. Deploy a new version of the code via `rsync` or `git pull`, and the workers continue serving the old cached opcodes until you explicitly clear the cache. The fix is a deploy hook that calls `opcache_reset()` via a small admin endpoint, or that sends `SIGUSR2` to the FPM master (which gracefully reloads the workers and their OPcache). A subtler failure is **partial cache population** — if you deploy a new file while a worker is mid-request, that worker may cache the new file while another worker still has the old version cached, leading to "method not found" errors that disappear on reload. The fix is to deploy atomically: symlink the document root to a new release directory (`/var/www/app/releases/2024-01-15-abc123` → `/var/www/app/current`), then `kill -USR2 <fpm-master>` to flush all caches simultaneously. This is the pattern Laravel Envoyer and Deployer use.

### The Shared-Nothing Principle: Clean initialization and complete teardown of all memory, variables, and resources on every HTTP request.

The shared-nothing principle is: at the start of every request, the PHP runtime state is byte-identical to a freshly booted interpreter; at the end of every request, every allocation is freed. Concretely, the request lifecycle in PHP-FPM is: (1) FastCGI worker receives a `BEGIN_REQUEST` record from nginx; (2) PHP-FPM calls `php_request_startup()` which initialises the superglobals (`$_GET`, `$_POST`, `$_COOKIE`, `$_SERVER`, `$_FILES`, `$_ENV`, `$_REQUEST`) from the FastCGI params, sets up the output buffering, calls the auto_prepend_file if configured; (3) the application's `index.php` is executed (typically `require __DIR__.'/../vendor/autoload.php'; $app = require_once __DIR__.'/../bootstrap/app.php'; $kernel = $app->make(Kernel::class); $response = $kernel->handle($request); $response->send();`); (4) the response body is flushed to the FastCGI STDOUT; (5) `php_request_shutdown()` runs — this calls all `register_shutdown_function` callbacks, calls all object destructors (every `zend_object`'s `dtor` and `free` handlers), closes all persistent resources (database connections opened with `PDO::ATTR_PERSISTENT` are returned to the per-process pool, but non-persistent connections are closed), runs the session `write` and `close` handlers (writing `$_SESSION` to `/var/lib/php/sessions/sess_<id>`), and finally `zend_deactivate()` destroys the entire symbol table and frees the request-bound memory arena.

The teardown is total: every variable that was set during the request is unset, every static class property is reset to its default value (unless the class is in OPcache's shared memory, in which case the class definition persists but the instance state does not), every open file handle is closed, every database connection is closed, every lock is released. There is no "next request" — the worker is in the same state it was in before this request arrived, modulo the per-worker connection pool (if persistent connections are used) and the per-worker APCu cache (if installed). This is the architectural invariant that lets PHP-FPM scale horizontally by just adding more workers and more boxes: there is no in-process state to replicate, no cache to invalidate, no warmup to perform, no consistency window. A load balancer can add a new PHP-FPM box to the pool and it will start serving traffic immediately, with no "warming up" period — the first request hits cold, OPcache populates on the first hit per file, and the second request is at full speed. Compare this to a JVM service that needs 30–60 seconds of JIT warmup before it hits steady-state throughput, or a Node.js service that needs to populate its in-memory cache before it can serve authenticated requests.

```text
  PHP-FPM worker request lifecycle (the shared-nothing envelope):

  T0: worker is idle, waiting on accept() in fcgi_accept_request()
      ┌─────────────────────────────────────────────────────────┐
      │  Worker state: clean slate                              │
      │   - No $_GET, $_POST, $_SERVER (will be populated)      │
      │   - No $app, no $kernel (will be created)               │
      │   - Static class properties: default values             │
      │   - Database connections: pool empty (or persistent)    │
      │   - OPcache SHM: shared with all workers (read-only)    │
      │   - APCu cache: per-worker (if installed)               │
      └─────────────────────────────────────────────────────────┘

  T1: BEGIN_REQUEST arrives from nginx via FastCGI
      → php_request_startup() populates $_GET/$_POST/$_SERVER/etc.
      → auto_prepend_file runs (if configured)

  T2: Application bootstrap
      → require vendor/autoload.php    (Composer's PSR-4 autoloader)
      → $app = new Application(...)    (framework constructor)
      → $kernel = $app->make(Kernel)   (DI container resolves)
      → $request = Request::capture()  (builds request from superglobals)

  T3: Application execution
      → $kernel->handle($request)      (routes → controller → response)
      → Database queries via PDO/Doctrine
      → $_SESSION updated if session active

  T4: Response
      → $response->send()              (echoes headers + body to FastCGI STDOUT)
      → FastCGI END_REQUEST sent to nginx

  T5: php_request_shutdown() — THE TEARDOWN
      → register_shutdown_function callbacks run
      → session_write_close() writes $_SESSION to /var/lib/php/sessions/sess_<id>
      → All object destructors called (every zend_object's dtor + free)
      → All non-persistent resources closed (DB connections, file handles)
      → All locks released (flock, sem_acquire)
      → zend_deactivate() destroys symbol table, frees request arena
      → Worker returns to T0 state, ready for next accept()
```

The superglobals are the application's only view of the request: `$_GET` (parsed from `QUERY_STRING`), `$_POST` (parsed from `php://input` based on `Content-Type`), `$_COOKIE` (parsed from `HTTP_COOKIE`), `$_SERVER` (CGI-style variables + `HTTP_*` headers, equivalent to WSGI's `environ`), `$_FILES` (uploaded files saved to temp dir, paths in the array), `$_ENV` (environment variables), `$_REQUEST` (merge of `$_GET` + `$_POST` + `$_COOKIE`, controllable via `request_order` ini). Sessions are the only cross-request state: `session_start()` reads `/var/lib/php/sessions/sess_<session_id>` (the default file handler; can be overridden to Redis/Memcached via `session_set_save_handler()`), populates `$_SESSION`, and on `session_write_close()` serialises `$_SESSION` back to the file with an exclusive `flock()` — which is why PHP sessions are a per-user serialisation point (one session, one concurrent request). The session file is a flat `key|serialized_value;key|serialized_value;` format; a 10 MB session file (yes, this happens with poorly-written apps) will block the user's second request for ~50 ms while the first releases the lock.

### Advantages: Total fault isolation and zero cross-request memory leaks

The shared-nothing model gives PHP three production properties that no long-lived runtime (JVM, Node, CPython-with-asyncio) can match without significant engineering. First, **total fault isolation**: a fatal error (`E_ERROR`, e.g. "Allowed memory size of 134217728 bytes exhausted") kills the current request and the worker process, but the next request is handled by a fresh worker forked by the FPM master — the bug does not propagate. There is no "the service is in a bad state and needs a restart" scenario; the service is in a clean state every request by construction. Compare this to a JVM service where an OutOfMemoryError leaves the JVM in an unpredictable state and the safe action is to restart the entire process, dropping all in-flight requests. Second, **zero cross-request memory leaks**: every allocation made during a request is freed at `php_request_shutdown()`. A leaky controller (one that creates 10 MB of objects per request and forgets to release them) leaks for one request, then the leak is gone — the next request starts fresh. The leak can never accumulate across requests because there is no "across requests" within a worker's memory model. The only accumulation is in OPcache (shared, read-only) and APCu (per-worker, explicit cache) — both of which have explicit size limits and LRU eviction. Third, **horizontal scalability by default**: because there is no in-process state, you can add PHP-FPM boxes behind a load balancer with no replication, no cache invalidation, no session affinity (assuming session storage is externalised to Redis). The capacity scales linearly with the number of boxes.

The fault-isolation property is what made PHP the dominant language for early-2000s shared hosting: a buggy WordPress plugin on one customer's blog could not affect another customer's blog on the same box, because each request ran in a fresh process with fresh memory. The CPanel / Apache mod_php era exploited this ruthlessly — a single box could host 1000 WordPress installs, each with different plugins, and a fatal error in one isolated to one request of one blog. The same property makes PHP attractive for multi-tenant SaaS today: a bug in one tenant's request cannot leak into another tenant's request, because there is no shared mutable state to leak through (assuming the database is correctly isolated — the application layer is automatically isolated). The contrast with the JVM is stark: a JVM multi-tenant app must carefully isolate classloaders, thread locals, and static state; a PHP multi-tenant app gets isolation for free, modulo the database.

The horizontal scalability property is what allowed Facebook, Wikipedia, Slack, and Etsy to reach internet scale on PHP (Facebook eventually wrote HHVM and Hack to escape PHP's per-request bootstrap cost, but Wikipedia, Slack, and Etsy still run on PHP-FPM in 2024). The operational simplicity is hard to overstate: there is no JVM warmup, no JIT deopt storm, no GC tuning, no `-Xmx` to set, no thread pool to size, no event loop to monitor for blocking. The deploy is `rsync + opcache_reset` (or a symlink swap + `kill -USR2`), the rollback is `symlink swap back + kill -USR2`, the scaling is `add more boxes`. The diagnostic surface is small: `tail -f /var/log/php-fpm.log` for the master log, `tail -f /var/log/php-slow.log` for the slow-request log (see [[04.04.02. FastCGI Protocol and PHP-FPM Pool Architecture]]), and `php-fpm -tt` to validate the config. The trade-off is performance — PHP-FPM at 200 RPS per worker is a fraction of what an async Node.js or ASGI server can do on the same hardware — but for the 95% of webapps that are I/O-bound on a database, that performance is irrelevant.

### Costs: Per-request bootstrapping overhead for large framework dependency graphs

The shared-nothing model's cost is that every request pays the bootstrap cost. For a "vanilla PHP" script (a single `index.php` with no framework), the bootstrap is ~1 ms — open the file, parse it, compile to opcodes (or fetch from OPcache), execute, return. For a Laravel application, the bootstrap is 30–80 ms: Composer's PSR-4 autoloader resolves ~200 class files, Laravel's service container registers ~150 bindings, the framework's bootstrappers load configuration from `config/*.php`, detect the environment, register middleware, and boot all service providers. For a Symfony application, the bootstrap is 50–150 ms: similar in structure to Laravel but with more service providers and a compiled DI container (which itself must be loaded and unserialised). This bootstrap cost is paid on every request — it is the price of the shared-nothing guarantee. A request that does 5 ms of actual work (a simple SELECT and a JSON response) takes 35–85 ms wall-clock on Laravel because the 30–80 ms of bootstrap dominates. This is why PHP framework RPS benchmarks always look bad against Node.js or Go: the benchmark measures bootstrap, not throughput.

The mitigations stack. **OPcache** eliminates the file-parsing and compilation cost — without it, Laravel's bootstrap is 200+ ms instead of 50 ms. **`opcache.preload`** (PHP 7.4+) pre-loads the framework's class definitions into the shared memory at FPM startup, eliminating the per-request autoloader lookup cost — can shave 10–20 ms off Laravel's bootstrap. **Laravel's `php artisan config:cache`** (and `route:cache`, `view:cache`, `event:cache`) merge the scattered config files into a single cached PHP file, replacing ~50 file reads with 1. **The compiled DI container** (Symfony's `ContainerBuilder::compile()`, Laravel's `PackageManifest`) pre-resolves the service definitions into a cached PHP array, eliminating the per-request reflection calls. **Persistent database connections** (PDO `ATTR_PERSISTENT`, or PHP-FPM's per-worker connection reuse) skip the TCP handshake + auth on every request — saving 1–5 ms per request. **APCu** (the per-worker in-memory key-value cache) lets the application cache the result of expensive bootstrap operations (e.g. the parsed `routes.php`, the loaded `config.php`) across requests within a worker. Together these cut a Laravel bootstrap from ~150 ms (cold, no caches) to ~30 ms (warm, all caches active).

```text
  Of 50 ms total: 7 ms (14%) is the actual business work + database.
  Of 50 ms total: 12 ms (24%) is the network (irreducible).
  → The shared-nothing model costs ~36% of the request's wall-clock time.
  → Long-running PHP (see 04.04.03) eliminates this 36% by bootstrapping once.
```

The bootstrap cost is the entire reason **long-running PHP runtimes** (Swoole, RoadRunner, FrankenPHP, Laravel Octane — see [[04.04.03. Long-Running In-Memory PHP Runtimes]]) exist. They break the shared-nothing model: the application bootstrap runs once at worker startup, the framework's service container and configuration persist across requests, and only the request-handling logic runs per request. The performance gain is dramatic (3–10× RPS improvement on Laravel, sometimes more), but the cost is the loss of the shared-nothing safety net — memory leaks now accumulate across requests, static state persists and must be reset manually, database connections can grow stale, and a fatal error in one request can corrupt the worker for subsequent requests. The decision is whether the bootstrap cost (30–80 ms per request) is significant enough to justify the operational complexity. For most apps serving < 100 RPS per box, the answer is no — buy more boxes. For apps at 1000+ RPS per box where the bootstrap is 50% of the request time, the answer is yes — adopt Octane or FrankenPHP, and accept the operational burden. This is the same trade-off the JVM, Node, and CPython-asyncio ecosystems made permanently, and PHP is now selectively adopting it for high-traffic deployments.

## Cross-Runtime Comparison

| Aspect | JVM (HotSpot) | Node.js (V8) | CPython | PHP (Zend) |
|---|---|---|---|---|
| Threading | OS threads (1:1) | Single thread + libuv pool | OS threads + GIL | Processes (shared-nothing) |
| Memory | GC (G1/ZGC) | GC (Scavenger + Mark-Sweep) | Ref counting + cyclic GC | Per-request cleanup |
| Concurrency model | Multi-threaded | Event loop (epoll) | GIL serializes bytecode | Process-per-request |
| Cold start | Slow (~2s) | Fast (~50ms) | Medium (~200ms) | Fast (~10ms) |
| Best for | CPU-bound, enterprise | I/O-bound, real-time | Scripts, ML, data | Web apps, CMS |

These differences are why the same algorithm performs differently in each runtime. When you read the anchor implementation in Spring Boot (JVM), keep in mind that the delta implementations in Node.js, Python, and PHP will exhibit different failure modes under load — only CPython has the GIL, and only CPython requires the multi-processing escape hatch for CPU parallelism.
