# 04.04.03. Long-Running In-Memory PHP Runtimes

## What This Is

**Long-running in-memory PHP runtimes** are a family of approaches (Swoole, RoadRunner, FrankenPHP, and the Laravel Octane wrapper that sits on top of any of them) that break PHP's shared-nothing lifecycle to keep the application bootstrapped in RAM across requests. In standard PHP-FPM (see [[04.04.01. Zend Engine and the Shared-Nothing Lifecycle]] and [[04.04.02. FastCGI Protocol and PHP-FPM Pool Architecture]]) every request pays the bootstrap cost — Composer's autoloader resolves ~200 files, Laravel's service container registers ~150 bindings, the framework's bootstrappers load configuration, register middleware, and boot service providers. This is 30–80 ms per request on Laravel, paid every time, even for a request that does 5 ms of actual work. Long-running runtimes pay this cost once at worker startup: the application is bootstrapped into a long-lived PHP interpreter, requests are dispatched into the already-bootstrapped container, and only the request-handling logic (route matching, controller invocation, response serialisation) runs per request. The performance gain is dramatic — Laravel on Octane typically delivers 3–10× the RPS of the same app on PHP-FPM, sometimes more — but the cost is the loss of the shared-nothing safety net. Memory leaks now accumulate across requests, static state persists and must be reset manually, database connections must be managed as a pool, and a fatal error in one request can corrupt the worker for subsequent requests.

The forward link to section 05 is direct: Laravel Octane (the official Laravel package that wraps Swoole/RoadRunner/FrankenPHP) is now the recommended high-performance deployment topology for Laravel, and Symfony has equivalent integrations with Swoole and RoadRunner via bundles. The backward link to section 02 is the same as Node.js's: a single long-lived process per core, an event loop (`epoll_wait` in Swoole's case), and non-blocking I/O via coroutines. The conceptual contrast with PHP-FPM is the same contrast Node.js has always had with PHP-FPM: long-running processes trade the operational simplicity of "fresh process per request" for the raw throughput of "bootstrapped container reused across requests." The reason this trade-off is now actively being made in PHP (it wasn't, in 2015) is that modern PHP frameworks have grown heavy enough that the bootstrap cost is the dominant request-latency component, and the PHP ecosystem has accumulated enough operational maturity (better observability, container orchestration, automated rollback) that the loss of shared-nothing safety is no longer a deal-breaker.

## The Details

### Breaking the shared-nothing model: Keeping the application bootstrap in RAM across requests.

In standard PHP-FPM, every request executes inside a freshly-bootstrapped PHP runtime. The `php_request_startup()` function populates the superglobals, the application's `index.php` runs Composer's autoloader and constructs the framework's service container, the request is handled, `php_request_shutdown()` destroys everything, and the worker returns to its idle state. The next request starts from a clean slate — no class definitions loaded (beyond what OPcache shares), no service container, no configuration parsed, no routes compiled. This is the "shared-nothing" guarantee: every request is independent, every request pays the bootstrap cost, every request ends with a total teardown. The model is operationally beautiful (no state to leak, no cache to invalidate, no warmup to perform) but performance-expensive — Laravel's bootstrap is 30–80 ms per request on a modern box, Symfony's is 50–150 ms, Magento 2's is 200–400 ms.

Long-running runtimes break this by separating the "application bootstrap" from the "request handling." The worker process boots PHP, runs Composer's autoloader once, constructs the framework's service container once, loads all configuration once, registers all middleware once — and then enters a loop that receives requests and dispatches them into the already-constructed container. The container, the loaded classes, the cached configuration, and any in-memory caches (Laravel's cache, Doctrine's metadata cache, the route collection) all persist across requests. Each request reuses the same interpreter, the same service container, the same database connection pool — only the per-request state (the Request object, the controller's local variables, the response) is created and destroyed per request. The bootstrap cost is amortised across thousands of requests instead of being paid per request. The savings on a Laravel app where bootstrap is 50 ms and the actual request work is 10 ms is the difference between 16 RPS per worker (60 ms total per request) and 100 RPS per worker (10 ms total per request) — a 6× improvement.

```text
  PHP-FPM request lifecycle (shared-nothing, bootstrap per request):

   Request 1:
   T=0ms   php_request_startup (superglobals, output buffering)
   T=1ms   require vendor/autoload.php           ┐
   T=2ms   $app = new Application(...)            │  BOOTSTRAP
   T=8ms   $kernel = $app->make(Kernel::class)    │  ~50ms
   T=10ms  $kernel->bootstrap()                   │  paid every

   T=60ms  $response->send()                      │  ~10ms
   T=61ms  php_request_shutdown()                 ┘
   Total: 61ms (50ms bootstrap + 10ms work + 1ms shutdown)

   Request 3: (same as Request 1, paid again)
   ...1000 requests × 61ms = 61 seconds of CPU time

  ─────────────────────────────────────────────────────────────────

  Long-running runtime (Octane/Swoole, bootstrap once):

   T=0     require vendor/autoload.php

   T=0     Clone the container (cheap — PHP copy-on-write)

   T=8       controller + service + DB query
   T=10    $response->send()
   T=11    Reset per-request state (sandbox flush)
   Total: 11ms (50ms bootstrap already paid + 10ms work + 1ms reset)

   Request 2: (same 11ms, no bootstrap)
   Request 3: (same 11ms, no bootstrap)
   ...1000 requests × 11ms = 11 seconds of CPU time

  Throughput per worker: 1000 RPS long-running vs 16 RPS PHP-FPM
  → 6× improvement, dominated by the eliminated bootstrap cost.
```

The mechanism by which long-running runtimes achieve this varies by implementation. **Swoole** (a PHP extension written in C++) adds coroutine support to PHP itself — `Swoole\Runtime::enableCoroutine()` patches PHP's blocking I/O functions (`mysqli_query`, `file_get_contents`, `curl_exec`) to use non-blocking equivalents that yield to a coroutine scheduler, allowing thousands of concurrent coroutines on a single PHP thread. **RoadRunner** (a Go application server) keeps a pool of long-lived PHP worker processes, communicates with them via an IPC protocol called `goridge` (a binary protocol over UNIX socket or TCP), and uses Go's HTTP server to handle the network layer — the PHP worker receives the request as a serialized message, runs the application, returns the response as another serialized message. **FrankenPHP** (a Caddy module written in Go that embeds the PHP interpreter via libphp) runs the PHP interpreter inside the Caddy process, handling HTTP requests directly without an intermediate protocol — the closest to "Node.js for PHP" in that there is no FastCGI hop at all. **Laravel Octane** is the unified abstraction: it wraps any of these three runtimes behind a single `php artisan octane:start --server=swoole|roadrunner|frankenphp` command, providing the application-level reset logic (clearing the container's resolved instances, resetting static state, flushing the request-scoped bindings) that the underlying runtime does not provide.

The architectural consequence is that the developer must now think about state that they did not have to think about under PHP-FPM. A static class property that holds a counter (`class Counter { public static int $count = 0; }`) increments across requests under Octane — the counter persists, which can be desirable (caching expensive computations) or catastrophic (a per-request user ID that leaks between users). A service registered as a singleton in Laravel's container (`$this->app->singleton(CartService::class)`) is constructed once at worker startup and reused for every request — if the CartService holds any per-request state (a `$currentUser` property, a `$cart` array), that state leaks between users. The application code must be audited for any state that was implicitly reset by `php_request_shutdown()` and is now persisted — this is the same audit the Node.js, JVM, and CPython ecosystems have always had to perform, and it is the cost of admission to long-running PHP.

### RoadRunner (Go-based application server and process manager) vs. FrankenPHP (Caddy-integrated Go application server) vs. Swoole (C++ async event-driven extension).

The three long-running PHP runtimes differ in their architecture, their integration depth, and their failure modes. **Swoole** is the deepest integration: it is a PHP extension (`ext-swoole` or the more recent `ext-openswoole` / `ext-swoole-ng` fork) that adds new PHP classes (`Swoole\Http\Server`, `Swoole\Coroutine`, `Swoole\WebSocket\Server`) and patches PHP's I/O layer to be coroutine-aware. The PHP worker is a single long-lived process that runs an event loop (`Swoole\Runtime::enableCoroutine()` + `Swoole\Coroutine\run()`); incoming HTTP connections are accepted by the loop, dispatched to a coroutine, and the coroutine runs the application code with blocking I/O calls transparently yielding to other coroutines. This is the same model as Python's `asyncio` (see [[04.03.03. ASGI Specification and Python Asyncio]]) and Node.js's event loop — except Swoole does the patching automatically, so synchronous-looking PHP code (`$pdo->query("SELECT ...")`) becomes async under the hood. Swoole is the fastest of the three (no IPC overhead, no Go-PHP marshalling, pure C++ coroutine scheduler) but requires writing code in the Swoole style and dealing with the Swoole/PHP version compatibility matrix (each PHP version requires a recompile of Swoole).

**RoadRunner** is a Go binary (`roadrunner`) that manages a pool of long-lived PHP worker processes. The Go process is the HTTP server (using `fasthttp`, a Go HTTP library ~10× faster than `net/http`); it accepts HTTP requests, serialises them via the `goridge` protocol (a binary RPC: 1 byte version, 1 byte flags, 4-byte payload length, 8-byte method CRC, then the MessagePack-encoded payload), sends them to a PHP worker over a UNIX socket, the PHP worker runs the application, and returns the serialised response. The PHP worker is a long-lived process running `RoadRunner\Worker->run()` which is a `while (true) { $payload = $this->goridge->receive(); $response = $this->handle($payload); $this->goridge->send($response); }` loop. RoadRunner is the most portable of the three (no C extension to install, just `composer require spiral/roadrunner`) and the most language-agnostic (the same Go binary can manage PHP, Python, or any worker that speaks goridge), but pays the IPC cost on every request (~0.5–1 ms for serialisation + UNIX socket round-trip). RoadRunner also supports queues, gRPC, and WebSockets natively, making it attractive for applications that need all of those.

**FrankenPHP** is the newest (released 2022, by Kévin Dunglas of API Platform fame), written in Go as a Caddy module. It embeds the PHP interpreter as a library (`libphp.so` linked into the Caddy binary via cgo), runs the PHP `php_execute_script()` function directly inside the Caddy request handler, and avoids any IPC entirely — the HTTP request, the PHP execution, and the response all happen in one process. FrankenPHP supports both worker mode (long-running, like Swoole/RoadRunner — `php artisan octane:start --server=frankenphp`) and traditional mode (CGI-style, one interpreter invocation per request, but with the embedded interpreter's reduced overhead vs PHP-FPM). FrankenPHP's distinguishing feature is automatic HTTP/2 and HTTP/3 support (inherited from Caddy), automatic HTTPS via Let's Encrypt (inherited from Caddy's `tls` directive), and a single-binary deployment (one ~30 MB Go binary contains the web server, the TLS stack, and the PHP interpreter). It is the easiest to deploy (single binary, no PHP-FPM to configure, no separate web server) but the youngest (still maturing in 2024).

Laravel Octane is the layer that makes these runtimes usable for a Laravel application without rewriting the application code. Octane provides a "sandbox" that clones the application container per request (using PHP's copy-on-write semantics to make this cheap), resets the `app('request')` binding, flushes the `RequestScoped` instances, and clears any state marked as `Octane::tick()` or `Octane::concurrent()`. The same application code that runs under PHP-FPM (where each request gets a fresh container for free) runs under Octane with the container refresh performed explicitly by the sandbox. The compatibility is high but not 100%: packages that hold static state, singletons that cache user-specific data, and libraries that mutate global state must be audited and either flushed per request or marked as incompatible. Octane ships with a list of known-compatible Laravel packages and a `php artisan octane:reload` command to restart workers after deploy.

### Architectural consequences: Managing memory leaks, resetting static state, and handling persistent database connections safely.

The architectural consequences of long-running PHP are the same consequences the JVM, Node.js, and CPython-asyncio ecosystems have lived with for two decades, now imported into PHP. **Memory leaks accumulate**. In PHP-FPM, a leak in `php-curl` or `Doctrine\ORM\EntityManager::clear()` not being called is bounded by `pm.max_requests = 1000` — the worker recycles every 1000 requests and the leak is reset. In long-running PHP, the worker never recycles (unless you configure Octane to do so), so the leak accumulates indefinitely until the worker hits `memory_limit` and dies. The fix is explicit: call `gc_collect_cycles()` periodically (Octane does this every 1000 requests by default), explicitly clear caches (`Cache::flush()` for testing, `EntityManager::clear()` after each request in Doctrine), and configure Octane's `octane.max_requests = 10000` to recycle workers proactively. The diagnostic is `memory_get_usage(true)` logged per request and graphed — a worker whose RSS grows 1 MB per 100 requests is leaking and needs recycling.

**Static state persists**. In PHP-FPM, `class Counter { public static int $count = 0; }` resets to 0 on every request because the class is reloaded. In long-running PHP, the class is loaded once at worker startup and `$count` persists across requests, accumulating forever. The same is true for `static` properties, `static` local variables, singletons (`getInstance()`), and any state stored on the service container without a `RequestScoped` binding. The fix is to either avoid static state (preferred) or to explicitly reset it in a `RequestReceived` listener. Octane provides `Octane::tick()` for periodic state reset and `Octane::flush()` for explicit cleanup. A specific Laravel footgun: the `Auth` facade caches the current user in a static property — Octane flushes this in its sandbox, but custom facades that cache state do not get the same treatment and must be audited. A specific Symfony footgun: the `Kernel`'s `Container`'s `private` services are not reset between requests — they must be marked `shared: false` or reset explicitly via `ResetInterface`.

**Database connections must be pooled**. In PHP-FPM, each worker opens one database connection per request (or uses `PDO::ATTR_PERSISTENT` for a per-worker persistent connection that lives across requests within that worker). In long-running PHP with hundreds of concurrent coroutines (Swoole) or a large worker pool (RoadRunner), the connection count can explode — each coroutine needs its own connection to avoid serialising queries. The fix is a connection pool: Swoole provides `Swoole\Database\PDOPool` (a fixed-size pool of PDO connections, borrowed and returned per request); Laravel Octane integrates with this via the `octane.database.persistent` config; RoadRunner provides its own pool abstraction. The pool must be sized to the database's `max_connections` (PostgreSQL default 100, MySQL default 151) divided by the number of workers across all boxes — a 10-box deployment with 16 workers each cannot have a pool size of 50 per worker (that's 8000 connections, far exceeding the database's capacity). The failure mode of an under-sized pool is request queueing behind connection acquisition (visible as latency spikes); the failure mode of an over-sized pool is `FATAL: sorry, too many clients already` from PostgreSQL.

The warm-reload problem is unique to long-running runtimes. In PHP-FPM, deploying new code is `rsync + kill -USR2 <master>` — workers gracefully finish their current request, exit (taking their cached container with them), and the master forks new workers that load the new code on first request. The deploy is atomic: either the worker is on the old code or the new code, never in between. In long-running PHP, the worker is alive before, during, and after the deploy — the cached container, the loaded classes, and any in-memory state all date from before the deploy. `php artisan octane:reload` sends a signal to the workers to gracefully finish their current request, then re-bootstrap the application (re-running the service container construction, re-loading the routes, re-caching the configuration). The reload takes 1–5 seconds per worker and is staggered across the pool to avoid total downtime — but during the reload, the worker is unavailable. The failure mode is forgetting to reload after deploy: the new code is on disk, but the workers are still serving the old code from their cached container — and the only way to know is to check the version via a `/version` endpoint or to look at the deploy timestamp in the response headers. The fix is to make `octane:reload` a mandatory step in the deploy script, after `artisan migrate` and before the health check.

The decision of when long-running PHP is worth it is a function of the bootstrap cost and the traffic volume. A Laravel app with a 50 ms bootstrap serving 20 RPS per box spends 1 second of CPU per second on bootstrap — 100% of one core, wasted. The same app on Octane spends 0 seconds on bootstrap and 0.2 seconds of CPU per second on actual work — 20% of one core. For a 4-core box, that's the difference between saturating at 80 RPS (PHP-FPM, 4 workers × 20 RPS each) and saturating at 400 RPS (Octane, 4 workers × 100 RPS each) — a 5× improvement that justifies the operational complexity. For a Laravel app serving 5 RPS per box, the bootstrap cost is 0.25 seconds of CPU per second — 25% of one core, not catastrophic — and the operational complexity of Octane (memory leak monitoring, static state audits, connection pool sizing, warm-reload scripts) is not justified. The rule of thumb: if your bootstrap cost is > 30% of the request time and your traffic is > 50 RPS per box, adopt long-running PHP; otherwise, stay on PHP-FPM and add more boxes. The future direction (PHP 8.3+ JIT, OPcache preload, framework-level optimisation) is steadily reducing the bootstrap cost, which makes the break-even point higher — but for high-traffic Laravel and Symfony deployments in 2024, Octane (or its equivalents) is the standard production topology.

## Cross-Runtime Comparison

| Aspect | JVM (HotSpot) | Node.js (V8) | CPython | PHP (Zend) |
|---|---|---|---|---|
| Threading | OS threads (1:1) | Single thread + libuv pool | OS threads + GIL | Processes (shared-nothing) |
| Memory | GC (G1/ZGC) | GC (Scavenger + Mark-Sweep) | Ref counting + cyclic GC | Per-request cleanup |
| Concurrency model | Multi-threaded | Event loop (epoll) | GIL serializes bytecode | Process-per-request |
| Cold start | Slow (~2s) | Fast (~50ms) | Medium (~200ms) | Fast (~10ms) |
| Best for | CPU-bound, enterprise | I/O-bound, real-time | Scripts, ML, data | Web apps, CMS |

These differences are why the same algorithm performs differently in each runtime. When you read the anchor implementation in Spring Boot (JVM), keep in mind that the delta implementations in Node.js, Python, and PHP will exhibit different failure modes under load — only CPython has the GIL, and only CPython requires the multi-processing escape hatch for CPU parallelism.
