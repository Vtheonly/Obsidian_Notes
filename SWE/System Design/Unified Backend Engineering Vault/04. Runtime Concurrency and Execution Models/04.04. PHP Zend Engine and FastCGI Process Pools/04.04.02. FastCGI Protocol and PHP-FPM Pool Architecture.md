# 04.04.02. FastCGI Protocol and PHP-FPM Pool Architecture

## What This Is

**FastCGI** is the binary protocol (defined in the original 1996 whitepaper by Mark Sgroi and Rob McCool of Open Market, later refined by the FastCGI specification at fastcgi.com) that lets a web server (nginx, Apache, lighttpd) hand HTTP requests to an external process (PHP-FPM, Python's flup, Ruby's fcgi) without re-executing the interpreter on every request. **PHP-FPM** (FastCGI Process Manager) is the daemon that maintains a pool of PHP worker processes, accepts FastCGI requests from the web server over a UNIX socket or TCP connection, dispatches them to free workers, and recycles workers when they hit `pm.max_requests` or memory limits. Together, FastCGI + PHP-FPM are the deployment topology for ~80% of the PHP applications on the public internet — and the architecture is the same one CPython WSGI uses (see [[04.03.02. WSGI Specification and Synchronous Pre-Fork Models]]): a master process binds the socket, forks N workers, each worker accepts one request at a time, and the web server (nginx) handles TLS, static files, and slow-client buffering. The protocol is binary and multiplexed, the process model is pre-fork, and the recycling model is per-worker max-requests.

The forward link to section 05 is that every Laravel, Symfony, WordPress, and Drupal app you deploy in production runs behind this FastCGI + FPM layer. The backward link to section 02 is the same as WSGI's: `socket()`, `bind()`, `listen()`, `accept()`, plus `fork()` and `SIGCHLD` handling in the master. The contrast with CPython's WSGI is small — the protocol (FastCGI vs HTTP-via-WSGI) and the worker config keys (`pm.*` vs gunicorn's `--workers`) differ, but the architecture is identical. The contrast with long-running runtimes (see [[04.04.03. Long-Running In-Memory PHP Runtimes]]) is large: those bypass FastCGI entirely, embedding the PHP interpreter into the web server process and keeping the application bootstrapped in RAM across requests.

## The Details

### The FastCGI binary protocol: Multiplexing web server communication over persistent Unix...

FastCGI is a binary, record-oriented protocol where the web server (the "responder") and the FastCGI application (PHP-FPM, the "responder-app") exchange typed records over a single persistent connection. Each record begins with an 8-byte header: a 1-byte `version` (always 1), a 1-byte `type` (the record type — `FCGI_BEGIN_REQUEST=1`, `FCGI_ABORT_REQUEST=2`, `FCGI_END_REQUEST=3`, `FCGI_PARAMS=4`, `FCGI_STDIN=5`, `FCGI_STDOUT=6`, `FCGI_STDERR=7`, `FCGI_DATA=8`, `FCGI_GET_VALUES=9`, `FCGI_GET_VALUES_RESULT=10`, `FCGI_UNKNOWN_TYPE=11`), a 2-byte `requestId` (allows multiplexing — multiple concurrent requests on one transport connection), a 2-byte `contentLength` (0–65535 bytes of payload), a 1-byte `paddingLength` (0–255 bytes of padding for alignment), and a 1-byte `reserved` field. The payload follows, then the padding bytes. The `FCGI_BEGIN_REQUEST` record carries a `FCGI_BeginRequestBody` (2 bytes: a 1-byte `role` — `FCGI_RESPONDER=1`, `FCGI_AUTHORIZER=2`, `FCGI_FILTER=3` — and a 1-byte `flags` field where bit 0 is `FCGI_KEEP_CONN` indicating whether to keep the transport connection alive after this request).

The request lifecycle is: web server sends `FCGI_BEGIN_REQUEST` (with requestId=1), then zero or more `FCGI_PARAMS` records (each containing encoded name-value pairs — `SCRIPT_FILENAME`, `REQUEST_METHOD`, `QUERY_STRING`, `HTTP_*` headers — encoded as length-prefixed `nameLen:valueLen:name:value`), then zero or more `FCGI_STDIN` records (the request body, chunked), then an empty `FCGI_STDIN` (contentLength=0) to signal end-of-input. The application (PHP-FPM) processes the request, sends back zero or more `FCGI_STDOUT` records (the HTTP response, including the `Status:` line and headers, then the body), zero or more `FCGI_STDERR` records (for error logging), and finally `FCGI_END_REQUEST` with a 4-byte `FCGI_EndRequestBody` (4 bytes `appStatus` — the application's exit code, 1 byte `protocolStatus` — `FCGI_REQUEST_COMPLETE=0`, `FCGI_CANT_MPX_CONN=1`, `FCGI_OVERLOADED=2`, `FCGI_UNKNOWN_ROLE=3`). The web server then either reuses the connection (if `FCGI_KEEP_CONN` was set) for another request or closes it. Multiplexing lets a single TCP connection carry multiple concurrent requests, each with its own `requestId` — but PHP-FPM historically did not support multiplexing (each worker handled one request at a time, so the web server opened N connections to N workers); nginx's FastCGI client does not multiplex either, opening one connection per concurrent request.

The reason FastCGI replaced CGI (Common Gateway Interface, RFC 3875) is the per-request process-spawn cost. CGI required the web server to `fork()` + `exec()` a new PHP interpreter for every request — a cold-start of ~50–200 ms per request just to bootstrap the interpreter, parse `php.ini`, load extensions, and compile the script (or fetch from OPcache). On a 100-RPS site that's 5–20 CPU-seconds of interpreter startup per second, which is why CGI-based PHP hosting (the original `mod_php` Apache handler, or the `php-cgi` binary) topped out at ~10 RPS per box. FastCGI keeps the worker alive: the interpreter boots once, then handles thousands of requests in a loop, paying the bootstrap cost only at FPM startup. The protocol's binary nature (vs CGI's text-based environment-variable passing) and the persistent-connection model (vs CGI's per-request `fork+exec`) together give FastCGI a 50–100× throughput advantage over CGI. The "fast" in FastCGI is genuinely earned.

The transport choice between UNIX socket and TCP is a real one. UNIX sockets (`fastcgi_pass unix:/var/run/php/php-fpm.sock;`) are 2–5× faster than TCP loopback because they skip the TCP/IP stack — no checksum, no acknowledgements, no Nagle, direct kernel buffer copy (see [[02.04.02. UNIX Domain Sockets vs. Network Sockets]]). Use UNIX sockets when the web server and PHP-FPM are on the same box. TCP (`fastcgi_pass 127.0.0.1:9000;` or `fastcgi_pass 10.0.0.5:9000;`) is required when they are on different boxes — useful for horizontally scaling PHP-FPM independently of nginx, or for running PHP-FPM in a sidecar container with nginx in another container (though in Kubernetes, the loopback TCP-over-localhost is usually fast enough and simpler than sharing a UNIX socket via an `emptyDir` volume). The PHP-FPM default since PHP 7.0 is to listen on a UNIX socket (`/var/run/php/php-fpm.sock` on Debian/Ubuntu); the older default was TCP on port 9000.

### PHP-FPM (FastCGI Process Manager): Master process management, signal handling (`SIGUSR1...

PHP-FPM is a single master process that manages one or more worker pools (each defined in `/etc/php/<version>/fpm/pool.d/<name>.conf`). The master process is the only one that binds the listening socket; workers are forked from the master and inherit the FD via `fork()`. The master's main loop is `while (true) { sigwaitinfo(&set, &info); /* handle signal */ }` — it spends its life blocked in `sigwaitinfo()`, waking only to handle signals or `SIGCHLD` from a worker that exited. This is a deliberate design: the master does no I/O, no PHP execution, no request handling — it is purely a supervisor. The signals it handles are: `SIGTERM` (immediate shutdown — send SIGTERM to all workers, wait up to `process_control_timeout` for them to finish, then SIGKILL stragglers, then exit), `SIGINT` (same as SIGTERM but typically sent by Ctrl-C), `SIGQUIT` (graceful shutdown — workers finish their current request, then exit, then master exits), `SIGUSR1` (reopen log files — workers close and reopen their `stdout`/`stderr` FDs, used by logrotate to release the old inode), `SIGUSR2` (graceful reload — send SIGQUIT to all workers, fork new workers from the master which has re-read its config; this is the zero-downtime deploy signal), `SIGCHLD` (a worker died — `waitpid()` it, log the exit reason, fork a replacement), and `SIGWINCH` (stop listening but finish in-flight requests — used in master/slave failover scenarios).

The signal semantics matter for operations. **`kill -USR2 <master-pid>`** is the canonical zero-downtime PHP-FPM reload: workers finish their current request, exit cleanly (releasing their memory and OPcache references), new workers are forked from the master which has re-read its config (so `pm.max_children` changes take effect, as does any new `php_value` setting). This is the signal your deploy script sends after `rsync`ing new code (with `opcache.validate_timestamps=0`, this is also how OPcache gets flushed — the new workers will re-compile the files they hit on first request). **`kill -USR1 <master-pid>`** is the logrotate signal: workers close and reopen their log FDs, releasing the rotated file's inode so `logrotate` can compress and delete it. Without this, `logrotate` would either leave the old file in place (filling the disk) or `gzip` it while PHP-FPM still holds the FD open (PHP-FPM keeps writing to the now-deleted inode, losing logs). **`kill -QUIT <master-pid>`** is graceful shutdown: workers finish in-flight requests (up to `process_control_timeout`, default 0 = unlimited), then exit, then master exits. This is the signal Kubernetes sends in a `preStop` hook (with `terminationGracePeriodSeconds` matching `process_control_timeout`).

Worker pools allow multiple independent configurations on the same FPM master. A common pattern is one pool per application (e.g. `pool.d/www.conf` for the main app, `pool.d/admin.conf` for the admin panel with different `php_admin_value[memory_limit]` and `php_admin_value[max_execution_time]` settings, `pool.d/queue.conf` for queue workers with `pm = static` and a small worker count). Each pool has its own listening socket (different UNIX socket path or different TCP port), its own user/group (so the admin pool can run as a privileged user and the public pool as `nobody`), its own `pm` settings, and its own log files. The master process supervises all pools; signals to the master affect all pools, but per-pool config changes (e.g. raising `pm.max_children` for the `www` pool) require `kill -USR2 <master>` to take effect. The diagnostic is `ps aux | grep php-fpm` showing the master and one row per worker, and `ss -xlp | grep fpm` showing the listening sockets per pool.

### Process management modes: `static` (fixed worker count), `dynamic` (`pm.max_children`, ...

PHP-FPM's `pm` (process manager) directive selects one of three worker-management modes. **`pm = static`** forks a fixed number of workers at startup (`pm.max_children`) and never changes the count — the simplest, most predictable mode, recommended for production where the box is dedicated to PHP-FPM and you know the steady-state load. The startup cost is paid once; there is no scaling lag; the memory budget is fixed. The trade-off is wasted RAM when the load drops (you keep N workers alive even if only 2 are busy). **`pm = dynamic`** (the default) is the adaptive mode: starts with `pm.start_servers` workers, scales up if there are fewer than `pm.min_spare_servers` idle workers, scales down if there are more than `pm.max_spare_servers` idle workers, and never exceeds `pm.max_children`. This is the right choice when the load varies (e.g. daytime peak, nighttime trough) and you want to free RAM at night. The trade-off is the scaling lag (a new worker takes 50–200 ms to fork and bootstrap) and the complexity of tuning four parameters in concert. **`pm = ondemand`** starts zero workers at startup and forks one on demand when a request arrives, killing idle workers after `pm.process_idle_timeout` seconds. This is the right choice for low-traffic sites (a staging box, an admin panel) where you want zero memory cost when idle. The trade-off is the cold-start latency for the first request after an idle period (a worker must fork, bootstrap, then handle the request — 100–500 ms).

The `pm = dynamic` scaling algorithm is: on every request completion, the master checks `idle = busy_workers - active_requests`. If `idle < min_spare_servers`, fork a new worker (up to `max_children`). If `idle > max_spare_servers`, send SIGQUIT to the most recently used idle worker (down to `min_spare_servers`). The algorithm runs at request granularity, not at a fixed interval — so the response to a sudden burst is immediate (workers fork as the burst arrives, up to `max_children`). When `max_children` is hit and all workers are busy, new connections queue at the listening socket's accept-queue (capped by `listen backlog` in the pool config, default 511). When the accept-queue fills, the web server (nginx) gets `ECONNREFUSED` on `connect()` to the FastCGI socket, returns 502 Bad Gateway to the client, and logs `*1 connect() to unix:/var/run/php/php-fpm.sock failed (11: Resource temporarily unavailable) while connecting to upstream`. The diagnostic is `tail -f /var/log/php-fpm.log` for the line `WARNING: [pool www] server reached pm.max_children setting (50), consider raising it` — this is the canonical "FPM is saturated" message and is the single most common PHP production incident.

```ini
; /etc/php/8.3/fpm/pool.d/www.conf — production dynamic pool

[www]
user = www-data
group = www-data

; Listen on a UNIX socket (faster than TCP loopback).
; nginx fastcgi_pass unix:/var/run/php/php-fpm.sock;
listen = /var/run/php/php-fpm.sock

; Set listen.owner/group/mode so nginx (running as www-data) can write.
listen.owner = www-data
listen.group = www-data
listen.mode = 0660

; Accept-queue cap. Raise if you see "Resource temporarily unavailable" in nginx.
; Kernel somaxconn is the upper bound (/proc/sys/net/core/somaxconn, default 4096).
listen.backlog = 1024

; pm = dynamic — adaptive worker count
pm = dynamic
pm.max_children = 50          ; hard cap; 50 * 50 MB = 2.5 GB worst-case RAM
pm.start_servers = 8          ; forked at startup
pm.min_spare_servers = 4      ; if idle < 4, fork more (up to max_children)
pm.max_spare_servers = 16     ; if idle > 16, SIGQUIT excess (down to max_spare)
pm.process_idle_timeout = 10s ; (ondemand only) kill idle workers after this

; Recycle workers to flush memory leaks. Jitter spreads the recycle times
; so all workers do not restart simultaneously.
pm.max_requests = 1000
pm.max_requests_jitter = 100

; Per-request limits
php_admin_value[memory_limit] = 256M
php_admin_value[max_execution_time] = 30
php_admin_value[upload_max_filesize] = 20M
php_admin_value[post_max_size] = 25M

; Slow log — capture stack traces of slow requests
request_slowlog_timeout = 5s
slowlog = /var/log/php-fpm/slow.log

; Access log with request URL, duration, memory, CPU
access.format = "%R - %u %t \"%m %r%Q%q\" %s %f %{mili}d %{kilo}M %C%%"
access.log = /var/log/php-fpm/access.log
```

The interaction between `min_spare_servers`, `start_servers`, and `max_spare_servers` is a footgun: PHP-FPM enforces `min_spare_servers <= start_servers <= max_spare_servers <= max_children`, and refuses to start otherwise (with a clear error in the master log). A common misconfiguration is setting `min_spare_servers` too low (e.g. 1) on a high-traffic site — under burst load, the master forks a new worker per request, the new worker takes 100 ms to boot, and during that 100 ms the request queue keeps growing. The fix is to size `min_spare_servers` to absorb your typical burst (4–8 is reasonable; for very bursty traffic, raise `start_servers` to match `min_spare_servers`). A second footgun is `pm.max_children` set too high for the box's RAM — if each worker peaks at 50 MB and you set `max_children = 200` on a 4 GB box, you have 10 GB of potential RAM commitment, the OOM killer fires, workers die unpredictably, and the master respawns them — a death spiral. The fix is to measure the actual per-worker memory (`ps -o rss,cmd --pid <worker-pid>` averaged across workers under load) and set `max_children = (box_RAM * 0.7) / per_worker_RAM` (the 0.7 leaves room for the OS, nginx, and the database).

### Sizing FPM pools to eliminate process swapping under high load

The sizing algorithm for a PHP-FPM pool is: measure per-worker peak RSS, calculate the safe `max_children` from the available RAM, and choose `pm` based on traffic pattern. Concretely: a Laravel worker peaks at ~40–60 MB (Symfony is similar, ~50–70 MB; WordPress with WooCommerce is ~80–120 MB; Magento 2 is ~150–250 MB). On a 4 GB box with nginx (200 MB), MySQL (1 GB), Redis (200 MB), the OS (500 MB), and 200 MB headroom, the available budget for PHP-FPM is ~2 GB. At 50 MB per worker, that's `max_children = 40`. Set `pm = dynamic`, `pm.max_children = 40`, `pm.start_servers = 8`, `pm.min_spare_servers = 4`, `pm.max_spare_servers = 12`. This config will serve ~80 RPS per box on a Laravel e-commerce site (40 workers × 2 RPS each, assuming 500 ms per request including the bootstrap). If you need more RPS, either add boxes (horizontal scaling) or adopt a long-running PHP runtime (see [[04.04.03. Long-Running In-Memory PHP Runtimes]]) which removes the bootstrap cost and lets each worker handle 5–10× more RPS.

The `pm.max_requests` setting is the proactive memory-leak mitigation. PHP's shared-nothing model (see [[04.04.01. Zend Engine and the Shared-Nothing Lifecycle]]) frees all per-request memory at `php_request_shutdown()`, but real-world applications have leaks that escape this: persistent database connections that grow their prepared-statement caches, APCu entries that accumulate without TTL, C extensions that allocate memory outside PHP's allocator (notably ImageMagick, gd, and some PDF libraries), and most importantly leaks in PHP itself (historically in `php-curl`, `php-gd`, and `php-mysqlnd` — usually fixed within a few releases but the long tail is long). Without `pm.max_requests`, a leaky worker grows unboundedly until the OOM killer fires; with `pm.max_requests = 1000`, the worker gracefully finishes its 1000th request, exits cleanly, and the master forks a fresh worker in its place — the leak is reset. The jitter (`pm.max_requests_jitter = 100`) randomises the threshold per-worker so all 40 workers do not recycle simultaneously (which would cause a momentary capacity drop and a request burst to queue). The cost of `pm.max_requests` is the 50–200 ms of cold-start for the recycled worker's first request — acceptable, because the recycling is amortised over 1000 requests. The setting is so universally recommended that it is essentially mandatory in production.

```text
  Worker sizing worksheet (4 GB box, Laravel e-commerce, ~80 RPS target):

  Box RAM budget:

```

The slow log (`request_slowlog_timeout = 5s`, `slowlog = /var/log/php-fpm/slow.log`) is the single most valuable PHP-FPM diagnostic. When a request takes longer than 5 seconds, PHP-FPM dumps the worker's PHP stack trace to the slow log — showing the exact function, file, and line where the request is currently stuck. The trace is captured via `zend_fetch_debug_backtrace()` (the same machinery `Exception::getTrace()` uses), which means it includes function arguments (configurable via `slowlog_trace_depth` and the `request_slowlog_trace_depth` ini) — but it does NOT include the database query text or the SQL state, because PHP-FPM doesn't know about those (they are in the PDO/mysqlnd layer). A typical slow-log entry looks like `[pool www] pid 12345, script /var/www/index.php, executing POST /api/checkout, slow request took 8.234s, user www-data, stack: #0 /var/www/app/Http/Controllers/CheckoutController.php(45): Stripe\\Charge::create(...) #1 /var/www/vendor/laravel/framework/src/Illuminate/Routing/Controller.php(54): CheckoutController->store() ...`. The fix is usually a slow external API call (Stripe, in this example) — wrap it in a timeout, or move it to a queue. The slow log is the PHP equivalent of Java's `jstack` and Node's `--prof` — it is the first thing to check when RPS drops mysteriously.

## How This Connects to the Frameworks

Every framework in section 05 is an HTTP parser and router sitting on top of a socket. When you write `Route::get('/users/{id}', [UserController::class, 'show'])` in Laravel or `@app.get('/users/<int:uid>')` in Flask, the framework:

1. Accepts a TCP connection from the web server (nginx → FastCGI for PHP, nginx → gunicorn's HTTP for Python).
2. Reads the HTTP request line and headers from the socket buffer.
3. Parses the request method, path, and headers into the framework's Request object (`Illuminate\Http\Request` in Laravel, `werkzeug.wrappers.Request` in Flask).
4. Matches the path against the registered routes.
5. Invokes your handler with the parsed request, via the DI container (Laravel's `app->make()`) or a direct call (Flask's `app.view_functions[name]`).
6. Serializes your handler's return value into an HTTP response (`JsonResponse`, `Response(json_encode($data))`).
7. Writes the response to the socket buffer.
8. Either closes the connection or keeps it alive for reuse.

If any of these steps fails — a malformed request, a slow client, a dropped packet — the failure surfaces as a connection reset, a 502 from your reverse proxy, or a timeout. Knowing which layer caused the failure is the difference between a 5-minute fix and a 5-hour incident.

## Hands-On Exercise

```bash
# 1. Inspect the FastCGI socket and FPM master/workers
ss -xlp | grep fpm                    # listening UNIX sockets
ps -eo pid,ppid,user,rss,cmd | grep -E 'php-fpm: (master|pool)' | grep -v grep

# 2. Send signals to the master and watch the effect
pgrep -f 'php-fpm: master'            # get master PID
sudo kill -USR1 <master>              # reopen log files (logrotate signal)
sudo kill -USR2 <master>              # graceful reload (zero-downtime)
sudo kill -QUIT <master>              # graceful shutdown

# 3. Watch the slow log in real time while load testing
tail -f /var/log/php-fpm/slow.log
# In another terminal, run: ab -n 1000 -c 50 https://localhost/api/slow

# 4. Inspect the accept queue during saturation
ss -xlt | grep fpm                    # Recv-Q = accept queue depth, Send-Q = backlog cap
cat /proc/sys/net/core/somaxconn      # kernel cap on listen() backlog

# 5. Capture the FastCGI protocol on the wire
sudo tcpdump -i lo -A -s 0 'tcp port 9000'   # if FPM is on TCP
sudo strace -f -e trace=read,write -p <worker-pid> 2>&1 | head -50  # per-worker syscalls

# 6. Watch OPcache memory usage (see [[04.04.01. Zend Engine and the Shared-Nothing Lifecycle]])
php -r 'var_dump(opcache_get_status(false)["memory_usage"]);'

# 7. Reproduce the "pm.max_children reached" error
ab -n 10000 -c 200 https://localhost/    # saturate the pool
tail -f /var/log/php-fpm.log              # look for "server reached pm.max_children setting"
```
