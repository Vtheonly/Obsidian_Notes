# 04.02.02. libuv Event Loop Architecture and Phases

## What This Is

**libuv Event Loop Architecture and Phases** is the reactor that powers Node.js. Where the JVM (section 04.01) gives you a thread per request and lets the OS scheduler interleave them, Node.js flips the model: one OS thread runs one event loop, and that loop multiplexes tens of thousands of concurrent I/O operations through a single `epoll_wait` (or `kqueue`, or IOCP) call. The event loop is the user-space equivalent of the kernel scheduler from section 02 — it decides which callback runs next, for how long, and in what order. Every `http.get`, every `fs.readFile`, every `setTimeout`, every `setImmediate` in your Express or Fastify handler ultimately becomes a callback registered with libuv, and the loop's job is to drain those callbacks in a well-defined order.

This note has two H3s: the high-level execution model (what the loop *is*) and the phase-by-phase cycle (what the loop *does* in each phase). The phase order is the part you need to memorise — the difference between `setTimeout(fn, 0)` and `setImmediate(fn)` is not "they are similar" but "they run in different phases, and which one fires first depends on whether you are inside an I/O callback or not." This is the question that has been on every Node.js interview for ten years, and the answer is below.

## The Details

### Single-threaded main event loop execution model

Node.js executes your JavaScript on a single OS thread. The libuv event loop, the V8 isolate, the microtask queues, the libuv thread pool's completion dispatch — all of this runs on that one main thread, with the exception of the libuv worker pool (covered in [[04.02.04. The libuv Worker Thread Pool]]) which handles blocking operations off-thread and posts results back. The single-threaded model is the source of Node's greatest strength (no locks, no data races, no cache-coherence overhead in your application code) and its greatest weakness (one blocking call stalls every connection).

The loop is implemented in `deps/uv/src/unix/core.c` (Linux/macOS) and `deps/uv/src/win/core.c` (Windows). The main entry point is `uv_run(loop, mode)`, which calls `uv__loop_alive` to check whether there is anything to do (timers pending, I/O handles registered, idle handles registered) and, if so, calls `uv__run_idle`, `uv__run_pending`, `uv__io_poll`, `uv__run_check`, and `uv__run_closing_handles` in order. The whole loop body is called a "tick" and Node runs ticks back-to-back until the loop is no longer alive (no more timers, no more I/O, no more `setImmediate`). The phase order is fixed; the loop does not skip phases, but it can early-exit a phase if there is nothing to do in it.

```text
   ┌───────────────────────────┐
   │   timers                  │  run callbacks whose setTimeout/setInterval fired
   │   (uv__run_timers)        │  fires in order of expiry time
   └─────────────┬─────────────┘
                 ▼
   ┌───────────────────────────┐
   │   pending callbacks       │  I/O errors / deferred to next loop iteration
   │   (uv__run_pending)       │  e.g. ECONNRESET, TCP errors delayed from poll
   └─────────────┬─────────────┘
                 ▼
   ┌───────────────────────────┐
   │   idle, prepare           │  internal only — used by libuv itself
   │   (uv__run_idle)          │  and by Node for some internal bookkeeping
   └─────────────┬─────────────┘
                 ▼
   ┌───────────────────────────┐
   │   poll                    │  THE big one: epoll_wait / kqueue
   │   (uv__io_poll)           │  blocks until I/O is ready OR a timer expires
   │                           │  then runs every ready I/O callback
   └─────────────┬─────────────┘
                 ▼
   ┌───────────────────────────┐
   │   check                   │  setImmediate callbacks
   │   (uv__run_check)         │  always runs after poll, before timers
   └─────────────┬─────────────┘
                 ▼
   ┌───────────────────────────┐
   │   close callbacks         │  socket.on('close'), fs.on('close')
   │   (uv__run_closing_handles)│  runs once per handle being closed
   └─────────────┬─────────────┘
                 │
                 ▼
            (next tick)
            microtasks drained between every phase (see 04.02.03)
```

The golden rule is "never block the event loop." A synchronous operation that takes 100 ms stalls every other connection for 100 ms — there is no other thread to pick up the slack. This is why Node services have a "soft 100 ms rule": if any synchronous operation takes longer than 100 ms, the event loop is considered stalled, and tools like `clinic doctor` or the `--event-loop-monitor` flag will flag it. The common offenders are `JSON.parse` on large payloads (50 MB JSON takes ~500 ms), `JSON.stringify` on deep object graphs, regular expressions with catastrophic backtracking, and large `for` loops over arrays. The fix is to either chunk the work (yield to the loop with `setImmediate` between chunks), move it to the libuv worker pool (`crypto.pbkdf2`, `zlib.gzip` — these are already on the pool), or move it to a `worker_thread` for true CPU parallelism.

### Detailed phase-by-phase execution cycle

The detailed walk through each phase is what every Node developer needs to internalise. Each phase has a specific responsibility, a specific queue of callbacks to drain, and specific rules about how it interacts with the microtask queue (covered in [[04.02.03. Microtask Queues and Execution Precedence]]).

**Timers phase (`uv__run_timers`):** The loop walks the timer heap (a binary min-heap ordered by expiry time) and runs every callback whose expiry time is `<= now`. If a timer was scheduled for `Date.now() + 100` and the loop reaches the timers phase at time `T+105`, the callback fires. Timers are not precise — they fire "at or after" the scheduled time, never before. If an earlier phase runs long, a timer scheduled for `T+100` may fire at `T+250`. The `process.hrtime.bigint()` value is the high-resolution clock libuv uses internally (it is `clock_gettime(CLOCK_MONOTONIC)` on Linux). The maximum timer delay is `2^31 - 1` ms (about 24.8 days) because the timer ID is a 32-bit signed integer; `setTimeout(fn, 2147483648)` is treated as `setTimeout(fn, 1)`.

**Pending callbacks phase (`uv__run_pending`):** This phase drains the `loop->pending_queue`, which holds I/O-related callbacks that were deferred from the previous tick. The classic case is a TCP `ECONNRESET` error that arrived during the poll phase of the previous tick — libuv queues the error callback here rather than running it inline, so the current tick's poll phase can finish draining. Some internal errors (like `uv__stream_destroy`'s callback) also land here. Most application code never directly interacts with this phase; it is the libuv-internal "stuff we deferred" queue.

**Idle / prepare phase (`uv__run_idle`):** Despite the name, this phase is not for "idle work" — it is a libuv-internal hook. The idle handles run on every tick (every iteration of the loop), and libuv uses them internally for things like the `uv_prepare_t` callbacks that some C++ add-ons register. Node itself uses the prepare phase for some bookkeeping (e.g., updating `process.hrtime()` caches). Application code rarely registers idle handles directly; the exception is `uv_tcp_keepalive` initialisation, which goes through an idle handle. This phase is mentioned for completeness — if you see it in a stack trace, it is libuv internals, not your code.

**Poll phase (`uv__io_poll`):** This is the heart of the loop. The implementation differs by platform: `uv__io_poll` on Linux uses `epoll_wait`, on macOS uses `kqueue`, on Windows uses IOCP. The poll phase computes the timeout to pass to `epoll_wait` as the time until the next timer fires (or `-1` to block indefinitely if no timers are pending and there is no `setImmediate` queued). It then calls `epoll_wait(epfd, events, maxevents, timeout)` and processes every returned event by invoking the associated `uv__io_t`'s callback. Network reads, network writes, `pipe(2)` activity, signal handlers (libuv converts signals to a pipe write), and TTY input all surface here. The poll phase is the only phase that can block; all other phases drain a finite queue and return. This is also why a long-running synchronous callback in the poll phase (e.g., inside a `socket.on('data', ...)` handler) blocks every other connection — `epoll_wait` cannot be called again until the callback returns.

**Check phase (`uv__run_check`):** This phase drains the `loop->check_handles` queue, which is where `setImmediate` callbacks live. `setImmediate` always runs in the check phase, which is *after* the poll phase and *before* the next tick's timers phase. This is the basis for the famous Node.js interview question: "Does `setTimeout(fn, 0)` or `setImmediate(fn)` fire first?" The answer is "it depends." Inside an I/O callback (i.e., during the poll phase), `setImmediate` fires first because the check phase runs before the next tick's timers phase. Outside an I/O callback (e.g., in the main module body), the order is non-deterministic because the poll phase may or may not have anything to do, and the loop may or may not enter the timers phase first depending on timing.

```javascript
// Inside an I/O callback — setImmediate always wins
fs.readFile('foo.txt', () => {
    setTimeout(() => console.log('timeout'), 0);
    setImmediate(() => console.log('immediate'));
});
// Output: immediate, then timeout

// In the main module — non-deterministic
setTimeout(() => console.log('timeout'), 0);
setImmediate(() => console.log('immediate'));
// Output: timeout/immediate order is not guaranteed
```

**Close callbacks phase (`uv__run_closing_handles`):** This phase runs the `close` callbacks for handles that were closed with `uv_close(handle, cb)` during the previous tick. `socket.destroy()` → `socket.on('close', cb)` and `server.close(cb)` both land here. The close phase is the last chance for cleanup; after it, the loop wraps around to the timers phase or exits if no handles remain.

```c
// Simplified uv_run loop body from deps/uv/src/unix/core.c
// (with the phases highlighted):

int uv_run(uv_loop_t* loop, uv_run_mode mode) {
    int r;
    while (r = uv__loop_alive(loop)) {
        uv__update_time(loop);                       // refresh loop->time
        uv__run_timers(loop);                        // 1. timers
        uv__run_pending(loop);                       // 2. pending callbacks
        uv__run_idle(loop);                          // 3. idle
        uv__io_poll(loop, timeout);                  // 4. poll (epoll_wait)
        uv__run_check(loop);                         // 5. check (setImmediate)
        uv__run_closing_handles(loop);               // 6. close callbacks
        // microtasks drained between every phase (via uv__run_check → v8)
    }
    return r;
}
```

The key production consequence: between every phase, Node drains the microtask queue (the `process.nextTick` queue and the Promise microtask queue — see [[04.02.03. Microtask Queues and Execution Precedence]] for the precedence rules). This is why a recursive `process.nextTick` starves the loop — it drains `nextTick`, but `nextTick` re-populates itself, so the drain never finishes, and the loop never advances to the next phase. A recursive `setImmediate` does not have this problem because `setImmediate` runs in the check phase, which is one phase per tick — each `setImmediate` callback yields and lets the loop continue. The diagnostic for "my event loop is stuck" is `node --inspect` and the Chrome DevTools Performance tab, which shows the phase each callback ran in; a single callback that spans the entire profile means the loop is blocked inside that callback.

## Cross-Runtime Comparison

| Aspect | JVM (HotSpot) | Node.js (V8) | CPython | PHP (Zend) |
|---|---|---|---|---|
| Concurrency model | OS thread per request | Single-threaded event loop | GIL + asyncio reactor | Process per request |
| Multiplexer | N/A (thread-per-conn) | epoll/kqueue/IOCP | select/poll/epoll (asyncio) | N/A |
| Phase structure | N/A | timers → pending → idle → poll → check → close | N/A (asyncio: single ready queue) | N/A |
| `setImmediate` analogue | N/A | check phase | `loop.call_soon` (next tick) | N/A |
| Stuck-loop detection | `jstack` | `--inspect` + Clinic Doctor | `gc.get_referrers` | N/A |

These differences are why the same algorithm performs differently in each runtime. When you read the anchor implementation in Spring Boot (JVM), keep in mind that the delta implementations in Node.js, Python, and PHP will exhibit different failure modes under load — only Node.js has the strict single-threaded event loop with this phase structure, and only Node.js has the `setTimeout`/`setImmediate` ordering subtlety.
