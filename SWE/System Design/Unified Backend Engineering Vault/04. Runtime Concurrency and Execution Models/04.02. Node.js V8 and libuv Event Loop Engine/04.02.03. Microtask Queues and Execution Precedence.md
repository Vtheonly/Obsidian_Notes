# 04.02.03. Microtask Queues and Execution Precedence

## What This Is

**Microtask Queues and Execution Precedence** is the rulebook that decides when each callback in a Node.js program runs. The libuv event loop from [[04.02.02. libuv Event Loop Architecture and Phases]] has six phases, but between every phase there is a hidden seventh concern: the microtask queue. Microtasks are callbacks that must run before the loop advances to the next phase, regardless of what is queued in the upcoming phase. They are how `Promise.then` callbacks and `process.nextTick` callbacks get their "run as soon as possible" semantics. Misunderstanding microtask precedence is the source of two of the most common Node.js bugs: the `process.nextTick` starvation bug (a recursive nextTick never lets the loop advance) and the "why does my `await` not run when I expect" confusion (the answer is that microtasks drain to empty between every macrotask, so the awaited continuation runs before any other macrotask even if a timer fired first).

This note covers four things: the distinction between macrotasks (the libuv phases) and microtasks (the V8/Node queues); the two separate microtask queues and their relative precedence; the drain-to-empty rule that decides when microtasks run; and the `process.nextTick` starvation hazard with the real-world bug pattern. After this, you should be able to predict — without running the code — what order a mixed batch of `setTimeout`, `setImmediate`, `Promise.then`, and `process.nextTick` callbacks will fire in.

## The Details

### Macrotasks (Task Queue) vs. Microtasks

A **macrotask** is any callback that the libuv event loop schedules into one of its six phases (see [[04.02.02. libuv Event Loop Architecture and Phases]]). `setTimeout` and `setInterval` callbacks are macrotasks in the timers phase; `setImmediate` callbacks are macrotasks in the check phase; I/O callbacks from `fs.readFile`, `http.get`, and `net.Socket` are macrotasks in the poll phase; close callbacks are macrotasks in the close phase. Each tick of the event loop runs at most one macrotask per phase (well — it drains the phase's queue, but each callback is a discrete macrotask), and between each macrotask the loop checks the microtask queues.

A **microtask** is any callback that must run before the loop advances to the next macrotask. `Promise.then(cb)`, `Promise.catch(cb)`, `queueMicrotask(cb)`, and `await` continuations (which are sugar for `Promise.then`) are microtasks. In Node.js, `process.nextTick(cb)` is *also* a microtask-like construct, but it has its own separate queue with stricter precedence — see the next H3. The crucial property of a microtask is that the loop drains the entire microtask queue before moving on, even if the microtask itself enqueues more microtasks (which is the basis of the starvation bug).

```text
  Event loop tick, showing macrotask/microtask interleaving:

   ┌──────────────────────────────────────────────────────────────┐
   │  1. timers phase                                             │
   │     macrotask: setTimeout cb A                               │
   │     ── drain microtasks ──                                   │
   │         microtask: Promise.then cb A1                        │
   │         microtask: nextTick cb A2                            │
   │         microtask: Promise.then cb A3 (enqueued by A1)       │
   │         microtask: nextTick cb A4 (enqueued by A2)           │
   │         ── keep draining until both queues are empty ──      │
   │     ── advance to next phase ──                              │
   ├──────────────────────────────────────────────────────────────┤
   │  2. pending callbacks phase                                  │
   │     macrotask: TCP error cb B                                │
   │     ── drain microtasks ──                                   │
   │         (none)                                               │
   │     ── advance ──                                            │
   ├──────────────────────────────────────────────────────────────┤
   │  3. poll phase                                               │
   │     macrotask: fs.readFile cb C                              │
   │     ── drain microtasks ──                                   │
   │         microtask: Promise.then cb C1                        │
   │     ── advance ──                                            │
   └──────────────────────────────────────────────────────────────┘
```

The reason for the macrotask/microtask split is to give Promise continuations predictable "run next" semantics without forcing them to wait for a full event loop tick. Without microtasks, `Promise.resolve().then(cb)` would have to wait for the timers phase of the next tick, which could be hundreds of milliseconds if a long poll phase is in flight. With microtasks, the continuation runs immediately after the current macrotask finishes — typically within microseconds. This is what makes `await` ergonomic: `const data = await readFile(); console.log(data);` runs the `console.log` synchronously in a microtask as soon as the read completes, with no perceptible delay.

### The Microtask Queue: `process.nextTick()` Queue vs. Promise (`Promise.then`, `async`/`await`) Queue.

Node.js actually has two microtask queues, not one. The `nextTickQueue` holds callbacks scheduled with `process.nextTick(cb)`. The `microtaskQueue` (managed by V8) holds callbacks scheduled with `Promise.then`, `queueMicrotask`, and `await` continuations. The two queues have different precedence: the `nextTickQueue` is drained *before* the `microtaskQueue` at every microtask checkpoint. So if you call `Promise.resolve().then(a); process.nextTick(b);` from a macrotask, `b` runs first, then `a`.

This is a Node-specific quirk. The HTML spec (which browsers follow) has only one microtask queue, and `queueMicrotask` is the only API. `process.nextTick` is a Node extension that predates the standardisation of microtasks; it exists because Node needed a "run this on the next turn of the loop" mechanism before Promises existed, and the name stuck. In modern code you should usually use `queueMicrotask` or `Promise.resolve().then` instead of `process.nextTick`, both because they are standard and because the higher precedence of `process.nextTick` makes it more likely to starve I/O. There are a few legitimate uses of `process.nextTick` — chiefly, scheduling cleanup after an error in an EventEmitter (where you want the cleanup to run before any other EventEmitter listener can attach), and emulating "synchronous" semantics in API design (where you want a callback to fire on the next tick even if the work is already done).

```text
  Microtask checkpoint drain order (after every macrotask in Node 11+):

  ┌─────────────────────────────────────────────────────────────┐
  │  while (nextTickQueue is not empty):                        │
  │      run next callback from nextTickQueue                   │
  │      (if it enqueues more nextTicks, they go to the back    │
  │       of nextTickQueue and run in this same loop)           │
  │                                                             │
  │  while (microtaskQueue is not empty):                       │
  │      run next callback from microtaskQueue                  │
  │      (if it enqueues more microtasks, they go to the back   │
  │       of microtaskQueue and run in this same loop)          │
  │                                                             │
  │  // Re-check nextTickQueue — Promise.then may have          │
  │  // enqueued more nextTicks!                                │
  │  if (nextTickQueue is not empty) goto top                   │
  └─────────────────────────────────────────────────────────────┘

  Concrete order:
    process.nextTick(a);  Promise.resolve().then(b);  process.nextTick(c);
    setTimeout(d, 0);

    Runs: a, c, b, d
    (nextTickQueue drained first, then microtaskQueue, then back to macrotasks)
```

The two queues have different performance characteristics, too. The `nextTickQueue` is a simple FIFO implemented in `node.cc` as a linked list; pushing and popping is O(1) and very cheap (~50 ns per call). The `microtaskQueue` is managed by V8 and integrates with V8's stack-switching machinery for async functions; pushing is also O(1) but the per-call overhead is slightly higher (~100 ns) because V8 must snapshot the calling context. Neither is expensive enough to worry about in normal code; the difference matters only in tight loops that schedule millions of microtasks.

### Execution rules: Draining the entire microtask queue between each macro task and after every phase of the event loop.

The rule that gives Node its microtask semantics is "drain to empty between every macrotask." Concretely: after every macrotask callback returns, the runtime performs a **microtask checkpoint** — it drains the `nextTickQueue` and then the `microtaskQueue`, repeatedly, until both are empty. Only then does the event loop advance to the next macrotask (or to the next phase, if the current phase's queue is empty).

This rule changed in Node 11. Before Node 11, the microtask queue was drained **once per phase**, not once per macrotask — so a `Promise.then` enqueued by the first `setTimeout` callback would not run until *all* `setTimeout` callbacks in the timers phase had fired. After Node 11 (and matching browser behaviour since 2014), the microtask queue is drained after **every macrotask callback**. This brings Node in line with the HTML spec and makes the order of `Promise.then` callbacks predictable across browsers and Node.

```javascript
// Node 11+ semantics — microtasks drain after every macrotask
setTimeout(() => {
    console.log('A1');
    Promise.resolve().then(() => console.log('A microtask'));
}, 0);
setTimeout(() => {
    console.log('B1');
    Promise.resolve().then(() => console.log('B microtask'));
}, 0);

// Node 11+ output (and browser output):
//   A1
//   A microtask
//   B1
//   B microtask

// Node 10 output (per-phase draining):
//   A1
//   B1
//   A microtask
//   B microtask
```

The microtask checkpoint is also called from C++ frame boundaries — every time C++ code calls into JavaScript and JavaScript returns, V8 runs a microtask checkpoint. This matters because some Node built-ins (e.g., `Buffer.from`, `crypto.createHash`) call into JavaScript from C++ internally, and a microtask scheduled during that call would run before the next macrotask. The flag `--no-flush-before-each-macrotask` (removed in Node 12) used to disable this; in modern Node the per-macrotask drain is mandatory and cannot be disabled. The `--unhandled-rejections=throw` flag is related: it controls what happens when a Promise rejects and no `.catch` is attached. The default in Node 15+ is `throw`, which means an unhandled rejection triggers a `process.exit(1)` on the next microtask checkpoint — this is why "my Node service died with no stack trace" is so often an unhandled Promise rejection.

### The `process.nextTick()` starvation hazard: Starving the event loop by recursive microtask scheduling.

The drain-to-empty rule has a dark side: if a microtask schedules another microtask, the loop keeps draining forever and never advances to the next macrotask. This is the `process.nextTick` starvation bug. A `process.nextTick` callback that calls `process.nextTick` recursively will keep the loop in the microtask checkpoint forever, and no I/O will ever be serviced. The same is true of `Promise.resolve().then` recursively, but the nextTick version is more common because `process.nextTick` is sometimes mistakenly used as a "deferred work" mechanism without appreciating its precedence.

The classic example is processing a large array element-by-element with `process.nextTick`:

```javascript
function processArray(arr, i = 0) {
    if (i >= arr.length) return;
    doWork(arr[i]);
    process.nextTick(() => processArray(arr, i + 1));
}

processArray(hugeArray);
// BUG: the loop never advances past the timers phase
// I/O callbacks never fire, the server stops accepting connections,
// health checks fail, the load balancer kills the pod.
```

The fix is to use `setImmediate` instead, which runs in the check phase (one callback per tick), so the loop advances between each iteration:

```javascript
function processArray(arr, i = 0) {
    if (i >= arr.length) return;
    doWork(arr[i]);
    setImmediate(() => processArray(arr, i + 1));
}
// OK: each iteration runs in a separate tick; the poll phase runs between
// iterations, so I/O is serviced. Slightly slower than nextTick but does
// not starve the loop.
```

The diagnostic for starvation is `node --inspect` plus the Chrome DevTools Performance tab — the flame chart will show a single `nextTick` callback running for the entire profile with no `epoll_wait` in between. Or, in production, a flat event-loop-delay metric (which `perf_hooks.monitorEventLoopDelay()` exposes) — if the delay climbs into seconds, something is starving the loop. The `--max-old-space-size` flag will not save you here, because the loop is not allocating — it is just stuck in a microtask checkpoint. The only recovery is a process restart, which is why health checks that exit the process on event-loop delay > 5s are the standard mitigation.

A subtler variant of the bug is the "Promise chain of death" — a long `.then().then().then()` chain where each `.then` is fast but the chain has 10 000 links. Each `.then` runs as a microtask, so the entire chain runs in one microtask checkpoint, blocking I/O for the duration. The fix is the same: `await setImmediate()` between groups of microtasks to yield to the loop. The `await` keyword desugars to `Promise.then`, so `await setImmediate()` is the canonical "yield to the loop" pattern in modern Node — it waits for a `setImmediate` macrotask, which lets the loop run a full tick before resuming.

## Cross-Runtime Comparison

| Aspect | JVM (HotSpot) | Node.js (V8) | CPython | PHP (Zend) |
|---|---|---|---|---|
| Macrotask source | Thread pool executor | libuv phases | `loop.call_soon` queue | N/A (process per request) |
| Microtask source | `CompletableFuture` callbacks | `Promise.then` + `queueMicrotask` | `loop.call_soon` (asyncio treats both as same) | N/A |
| `process.nextTick` analogue | N/A | nextTickQueue (higher precedence) | N/A | N/A |
| Drain rule | Per-task | Per-macrotask (Node 11+) | Per-step (asyncio) | N/A |
| Starvation risk | `CompletableFuture` chain | Recursive `nextTick` or `Promise.then` | Long `await` chain in single coroutine | N/A |

These differences are why the same algorithm performs differently in each runtime. When you read the anchor implementation in Spring Boot (JVM), keep in mind that the delta implementations in Node.js, Python, and PHP will exhibit different failure modes under load — only Node.js has the two-queue microtask system with the `process.nextTick` precedence quirk, and only Node.js has the explicit macrotask/microtask split at the runtime level.
