# 04.02.01. V8 Engine Architecture

## What This Is

**V8 Engine Architecture** is the JavaScript runtime Google built for Chrome and that Node.js adopted as its bytecode engine. V8 is the JavaScript equivalent of the JVM's HotSpot engine described in [[04.01.01. HotSpot Execution Engine and JIT Compilation]]: it parses JavaScript source, compiles it through a tiered pipeline, optimises hot functions aggressively, and reclaims memory with a generational garbage collector. The differences are that V8 must start in milliseconds (Chrome wants the first paint fast), must deal with JavaScript's dynamic typing (no static class hierarchy, so V8 invents "hidden classes" at runtime), and must run on every page in every tab without one tab starving another. Node.js inherits the same engine but runs without Chrome's tab isolation — a single Node process has one V8 isolate, and that isolate's behaviour governs every library in the npm ecosystem.

This note covers the four things that make V8 fast enough to run a backend: the four-tier execution pipeline (Ignition → Sparkplug → Maglev → TurboFan), the hidden-class (Map) system that gives V8 a fighting chance at optimising dynamic code, the inline cache (IC) tiers that record call-site shapes, and the Orinoco garbage collector that pauses for 1–50 ms instead of 100+ ms. The forward link to section 05 is that every Express/Fastify/NestJS handler runs in this engine, and every "why is my Node service slow on the first request after deploy" question comes down to V8's warmup behaviour — V8, like HotSpot, interprets first and optimises later.

## The Details

### V8 Pipeline: Parser → Ignition Interpreter (Bytecode) → Sparkplug (Baseline Compiler) → TurboFan (Optimizing Compiler).

V8's pipeline is conceptually identical to the JVM's tiered compilation but with different names and one extra tier. Source enters the **parser** (a hand-written recursive-descent parser, not a generated one — V8 trades parser-generator flexibility for speed), which produces an AST. The AST is consumed by **Ignition**, a register-based bytecode interpreter that compiles the AST to bytecode and then executes it. Ignition's bytecode is dense (one-byte opcodes plus variable-length operands) and the interpreter is a threaded-code switch loop written in C++. Ignition is fast for a bytecode interpreter — ~30–50 ns per opcode on modern hardware — but still 10–30× slower than native code. It also collects profiling data (the "feedback vector" attached to every function) recording which shapes appeared at each call site and which branch directions were taken.

After ~1 000 invocations of a function, V8 promotes it to **Sparkplug**, the baseline compiler (added in V8 9.1, 2021). Sparkplug is non-optimising: it simply compiles each bytecode opcode to a short fixed sequence of machine instructions, without inlining, without type specialisation, and without register allocation. The point of Sparkplug is to halve the interpreter overhead at near-zero compile cost — a typical Sparkplug compile takes ~0.5 ms per function. Before Sparkplug, V8 had a 30% throughput gap between Ignition and TurboFan; Sparkplug closes half of it.

The next tier, **Maglev** (added in V8 11.5, 2023, behind a flag, on by default in Node 22), is the mid-tier optimising compiler. Maglev builds a sea-of-nodes IR (like TurboFan) but skips many of TurboFan's expensive passes; it does inlining, type narrowing based on feedback, and some escape analysis, in ~5 ms per function. Maglev was added because the Ignition→TurboFan jump was too steep — TurboFan takes 50–200 ms per function and the JIT thread could not keep up under bursty load. Maglev fills the gap.

The top tier is **TurboFan**, the optimizing compiler (the equivalent of HotSpot's C2). TurboFan takes 50–200 ms per function but produces code that is competitive with equivalent C++. It does sea-of-nodes IR, escape analysis, loop unrolling, SIMD vectorisation, and inlining based on the feedback vector. TurboFan also performs **speculative optimisation**: it assumes that a call site that has only ever seen `String` arguments will continue to see `String` arguments, and emits a guard check (`if (typeof arg !== "string") deoptimize`) that, if it ever fires, throws away the compiled code and falls back to Ignition. The "deoptimise" in V8 is called `deopt`, and a deopt storm (caused by polymorphic call sites or changing argument shapes) is the V8 equivalent of the JVM's "made not entrant" flood.

```text
  JavaScript source
        │  Parser (recursive descent)
        ▼
  AST
        │  Ignition compiler
        ▼
  Bytecode (register-based, ~30 ns/op)
        │  Ignition interpreter executes
        │  Collects feedback vector (IC state)
        │
        ├── after ~1k calls ─► Sparkplug (baseline JIT, ~0.5 ms)
        │                       non-optimising, 2× interpreter speed
        │
        ├── after ~10k calls ─► Maglev (mid-tier, ~5 ms)
        │                       inlining + type narrowing + escape analysis
        │
        └── after ~100k calls ─► TurboFan (optimising JIT, ~50–200 ms)
                                 sea-of-nodes, SIMD, aggressive inlining
                                 speculative guards → deopt on mismatch
```

You can watch the tier-up happen with `node --trace-turbo` (logs TurboFan compilations) or `node --trace-opt --trace-deopt` (logs every optimisation and deoptimisation). A typical trace line looks like `Optimizing function foo took 12.3 ms` and a deopt looks like `DEOPT: foo at bailout reason: Insufficient type feedback for call`. The "bailout reason" tells you why TurboFan gave up — common reasons are `Insufficient type feedback for call` (the call site is too polymorphic), `Not a Smi` (an integer-typed variable became a float), and `HeapNumber` (a small integer overflowed into a heap-allocated number). When you see deopts in production traces, your handler is running in Ignition instead of TurboFan, which is the cause of the "first 100 requests are slow" pattern on a freshly-started pod.

### Hidden Classes (Maps) and Shapes: Dynamic property lookup optimizations

JavaScript is dynamically typed: an object is just a bag of properties, and you can add or remove properties at any time. Without help, every property access would be a hash-table lookup — O(1) amortised but with a 10–20× constant factor penalty compared to a C struct field access. V8's solution is **hidden classes** (called "Maps" internally — confusingly, the same word as JavaScript `Map`). Every V8 object has a pointer to its hidden class, and the hidden class describes the property layout: a list of (property name, offset, attribute) triples. When you do `obj.x`, V8 reads the hidden class pointer, looks up `x` in the hidden class's property table, finds the offset, and loads from `obj + offset`. This is essentially what a C compiler does at compile time; V8 just does it at runtime.

The trick is that hidden classes are *structural* — two objects with the same properties in the same insertion order share the same hidden class, even if they are different object instances. V8 maintains a hidden-class transition tree: starting from a root class (an empty object literal `{}`), each property addition transitions to a new class, and the transitions are cached so that the second time you build `{a: 1, b: 2}` you walk the same path through the tree and arrive at the same hidden class. This is why insertion order matters: `{a:1, b:2}` and `{b:2, a:1}` have different hidden classes, even though they represent the same data. The classic V8 performance advice "always initialise your object properties in the same order in the constructor" is a direct consequence.

```text
  Hidden class transition tree (V8 internal "Map" structure):

  RootMap (empty object {})
        │ add property "x"
        ▼
  Map1 {x: offset 0}
        │ add property "y"
        ▼
  Map2 {x: offset 0, y: offset 4}

  const a = {x: 1, y: 2};   // a.map == Map2
  const b = {x: 3, y: 4};   // b.map == Map2 (same shape, shared class)
  const c = {y: 2, x: 1};   // c.map != Map2 — different insertion order
  const d = {x: 1, z: 3};   // d.map != Map2 — different property set

  Each Map records:
   - property names (string table)
   - offsets into the object (in properties or in-object slots)
   - attribute bits (writable, enumerable, configurable)
   - pointer to parent Map (for transition back-tracking)
   - descriptor array (shared across all instances of this Map)
```

The production failure mode is "shape instability." If your function receives objects with different shapes from different callers (e.g., a database row from one query has 5 columns and from another has 6), V8 cannot share the hidden class, and every property access becomes polymorphic — the inline cache (next section) misses, the JIT cannot specialise, and the function falls back to Ignition. The diagnostic is `node --trace-maps <file.js>` to see the hidden-class transitions, or `node --prof` followed by `node --prof-process` to find functions that spend most of their time in property-access stubs. The fix is to declare all properties in the constructor (so the shape is fixed at allocation) and to avoid `delete obj.x` (which forces a hidden-class transition to a dictionary mode).

### Inline Caching (IC): Monomorphic, Polymorphic, and Megamorphic call sites.

Inline caching is the second half of V8's strategy for dynamic property access. A property access `obj.x` is compiled (in Ignition or TurboFan) to a stub that first checks "is `obj`'s hidden class the one I cached last time?" — if yes, it uses the cached offset (one load); if no, it falls back to the slow path (lookup the property in the hidden class's descriptor array, then cache the new offset). The cache is called the **inline cache (IC)** and it lives in the function's feedback vector, which is a per-function array of IC slots, one per bytecode operation that needs one.

ICs have three states. **Monomorphic**: the call site has only ever seen one shape; the IC stores that shape's hidden class pointer and the property offset, and the access is one comparison + one load. This is the fast path, and V8's TurboFan can specialise the access to a single offset, eliminating the comparison entirely. **Polymorphic**: the call site has seen 2–4 shapes; the IC stores an array of (hidden class, offset) pairs and the access is a linear search over the array. Performance degrades roughly linearly with the number of shapes. **Megamorphic**: the call site has seen 5+ shapes; V8 gives up caching and falls back to a hash-table lookup on every access. Megamorphic call sites are 10–50× slower than monomorphic ones, and they prevent TurboFan optimisation — TurboFan will not inline a call site that is megamorphic because it cannot pick a single shape to specialise to.

```text
  IC state transitions for a property read `obj.x`:

  ┌──────────┐   new shape   ┌──────────────┐  3rd shape  ┌──────────────┐
  │Uninitial-│ ─────────────►│  Monomorphic │ ──────────► │  Polymorphic │
  │  ised    │               │  (1 shape)   │             │  (2-4 shapes)│
  └──────────┘               └──────────────┘             └──────┬───────┘
                                                                  │ 5th shape
                                                                  ▼
                                                          ┌──────────────┐
                                                          │ Megamorphic  │
                                                          │ (hash lookup)│
                                                          └──────────────┘
```

The classic mistake that triggers megamorphic ICs is using the same function to process objects from different sources. A logger that accepts `{level, msg}` from one caller and `{lvl, message}` from another is now polymorphic on the first call; if three more shapes appear it becomes megamorphic, and the logger runs 10× slower than expected. The fix is to normalise the input shape at the function boundary: pick one canonical shape and convert everything to it on entry, so the rest of the function only sees monomorphic accesses. The diagnostic is `node --trace-ic` which prints every IC miss; a flood of `x (megamorphic)` lines on a hot function is the smoking gun. V8 also has a `--trace-generalization` flag that prints when a hidden class is generalised (a property's type widened from Smi to TaggedPointer, e.g., when a number field is later assigned a string), which is another shape-instability signal.

### V8 Garbage Collection: Scavenger (Semi-space young generation) and Major GC (Mark-Sweep-Compact).

V8's garbage collector is called **Orinoco** (named after the river, continuing the V8 tradition of water-themed GC names). Orinoco is a generational, parallel, concurrent collector that is the JavaScript equivalent of the JVM's G1 (see [[04.01.03. Garbage Collection Algorithms and Tuning]]). The heap is split into two generations: **young** (where new objects allocate, divided into a "from-space" and a "to-space" of equal size, each 1–8 MB) and **old** (where survivors of two minor GCs are promoted, sized 50 MB – 2 GB). There is also a **large object space** for objects larger than ~1 MB (they are allocated directly in old, never copied), and a **code space** for JIT-compiled machine code (executable memory, sized separately).

A **minor GC** (the "Scavenger") fires when young-gen is full. It walks the roots (registers, the stack, global objects), copies live objects from from-space to to-space (bumping the allocation pointer), and swaps the two spaces. The whole thing takes 1–5 ms on a typical Node service and runs on a dedicated GC thread that briefly stops the main thread. Objects that have survived two minor GCs are promoted to old-gen. A **major GC** (Mark-Sweep-Compact) fires when old-gen approaches its limit. The mark phase walks the entire object graph from the roots (concurrent with the mutator, with brief STW pauses for root scanning and remark), the sweep phase frees dead objects (concurrent), and the compaction phase moves live objects together to defragment (concurrent with mutator, with brief STW pauses for page evacuation). Orinoco's innovation is that all three phases are concurrent — major GC pauses on a 1 GB heap are typically 5–50 ms, not the 100+ ms they were before Orinoco.

```text
  V8 heap layout (single Isolate):

  ┌──────────────────────────────────────────────────────────────────┐
  │  YOUNG GENERATION (always compacted, copying collector)          │
  │  ┌──────────────────┐  ┌──────────────────┐                     │
  │  │   from-space     │  │   to-space       │   (each 1-8 MB)     │
  │  │  (allocating)    │  │  (copy target)   │                     │
  │  └──────────────────┘  └──────────────────┘                     │
  │  Minor GC: copy live from→to, swap. Promotion after 2 cycles.   │
  ├──────────────────────────────────────────────────────────────────┤
  │  OLD GENERATION (mark-sweep-compact, concurrent Orinoco)         │
  │  - Promoted objects, large arrays, long-lived maps               │
  │  - Major GC: concurrent mark + sweep + compact                   │
  │  - Pause: 5-50 ms on 1 GB heap (was 100+ ms pre-Orinoco)        │
  ├──────────────────────────────────────────────────────────────────┤
  │  LARGE OBJECT SPACE (objects > 1 MB, allocated directly in old)  │
  │  CODE SPACE (JIT-compiled machine code, executable, separate)    │
  └──────────────────────────────────────────────────────────────────┘
```

The Node flags you will actually use: `--max-old-space-size=2048` (sets the old-gen limit to 2 GB; default depends on available RAM, often 1.5–4 GB), `--max-semi-space-size=64` (sets each young-gen semi-space to 64 MB; useful for services that allocate large short-lived arrays), `--expose-gc` (lets you call `global.gc()` programmatically, useful for measuring), `--trace-gc` (logs every GC with timestamps and durations). The `--max-old-space-size` flag is the one that matters most in production — Node will OOM-kill the process if old-gen exceeds it (`FATAL ERROR: Ineffective mark-compacts near heap limit Allocation failed - JavaScript heap out of memory`), so set it to ~75% of your container's cgroup limit. The diagnostic for GC pressure is `--trace-gc-verbose` which prints the major/minor split and the promotion rate; if promotion rate is high (lots of objects surviving into old-gen), your service is allocating long-lived objects faster than the GC expects, and a major GC will fire sooner than the steady-state estimate suggests.

## Cross-Runtime Comparison

| Aspect | JVM (HotSpot) | Node.js (V8) | CPython | PHP (Zend) |
|---|---|---|---|---|
| Execution tiers | Interp → C1 → C2 (3) | Ignition → Sparkplug → Maglev → TurboFan (4) | `ceval` only | Zend VM only (+ OPcache) |
| Type model | Static (bytecode typed) | Dynamic (hidden classes + IC) | Dynamic (PyObject) | Dynamic (zval) |
| GC | Generational, region-based (G1/ZGC) | Generational, Orinoco (parallel+concurrent) | Refcount + cyclic | Per-request wipe |
| Pause time | 50–200 ms (G1), <1 ms (ZGC) | 5–50 ms (major), 1–5 ms (minor) | <5 ms | 0 |
| Flags | `-XX:+UseG1GC` | `--max-old-space-size`, `--trace-gc` | `gc.set_threshold()` | N/A |

These differences are why the same algorithm performs differently in each runtime. When you read the anchor implementation in Spring Boot (JVM), keep in mind that the delta implementations in Node.js, Python, and PHP will exhibit different failure modes under load — only the JVM and V8 have the JIT firepower to hide the cost of dynamic dispatch, and only V8 has the additional complexity of hidden classes and inline caches.
