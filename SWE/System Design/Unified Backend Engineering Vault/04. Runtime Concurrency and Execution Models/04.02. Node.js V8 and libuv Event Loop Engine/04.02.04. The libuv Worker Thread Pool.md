# 04.02.04. The libuv Worker Thread Pool

## What This Is

**The libuv Worker Thread Pool** is Node's answer to the question "if the event loop is single-threaded, how do I do CPU-bound or blocking-disk work without stalling every connection?" The answer is a fixed-size pool of OS threads, created lazily on the first blocking call, that libuv dispatches work to. The pool defaults to 4 threads, is configurable up to 1024 via the `UV_THREADPOOL_SIZE` environment variable, and is shared across every blocking operation in the process — every `fs.readFile`, every `dns.lookup`, every `crypto.pbkdf2`, every `zlib.gzip`. The pool is the second of Node's two execution lanes (the first being the single-threaded event loop itself); understanding which lane each operation runs in is the difference between a Node service that scales and one that mysteriously stalls under file-I/O load.

This note has four H3s: which operations actually use the pool (and which surprisingly do not), the pool size and how to tune it, the failure mode of pool exhaustion, and `worker_threads` as the escape hatch for true CPU parallelism with `SharedArrayBuffer`. The forward link to section 05 is that Express and Fastify rely on the worker pool transparently — your `fs.readFile` inside a request handler blocks a pool thread, not the event loop, but if every request does file I/O and you have 100 concurrent requests, 96 of them are queued behind the 4 pool threads and your p99 collapses.

## The Details

### Operations that cannot be executed non-blockingly via epoll: File system I/O, DNS lookups (`dns.lookup`), and Cryptographic operations (`crypto.pbkdf2`).

The libuv worker pool exists because not every I/O operation can be multiplexed by `epoll_wait`. Network sockets are the canonical epoll-friendly I/O: `socket()`, `connect()`, `read()`, `write()` all have non-blocking modes, and `epoll_wait` will tell you when a socket is ready to read or write. But three categories of operation do not have a non-blocking equivalent on Linux (or have one that is awkward enough that libuv chose not to use it):

**File system I/O** is the headline case. Linux's `read()` and `write()` system calls on regular files are documented as always blocking, but in practice the kernel usually copies data to/from the page cache synchronously and returns immediately — so a regular `read()` on a hot file is fast. The problem is when the file is not in cache (cold read from disk): the call blocks for milliseconds to seconds while the disk seeks. There is no `epoll` for regular files on Linux because the page cache does not have a "ready" notification mechanism. libuv therefore runs every `fs.readFile`, `fs.writeFile`, `fs.readdir`, `fs.stat`, etc. on a worker thread. The newer `io_uring` API (Linux 5.1+) does provide a true async file I/O path, and libuv has experimental `io_uring` support, but as of Node 22 it is not enabled by default.

**DNS lookups via `dns.lookup`** (the default `dns.lookup` function, not `dns.resolve`) use `getaddrinfo(3)`, which is a blocking libc function. `getaddrinfo` consults `/etc/hosts`, `/etc/resolv.conf`, and makes UDP/TCP queries to configured nameservers, all in a single blocking call. There is no `epoll`-friendly async version of `getaddrinfo` in libc, so libuv runs it on a worker thread. The newer `dns.resolve` family uses c-ares (a third-party async DNS library) and does go through `epoll` directly without the pool — this is why `dns.resolve` is faster than `dns.lookup` for high-volume DNS work, and why `http.request` (which uses `dns.lookup` by default for the URL's hostname) is sometimes a surprising bottleneck.

**Cryptographic operations** that are CPU-bound and have no async equivalent: `crypto.pbkdf2`, `crypto.scrypt`, `crypto.randomBytes` (in some configurations), and `crypto.randomFill` all run on the worker pool because they take milliseconds to seconds of CPU time. `crypto.randomBytes` is special: it calls `getrandom(2)` (Linux) or `urandom` (older), which is fast and non-blocking, so Node runs the synchronous version directly on the event loop; the asynchronous `crypto.randomBytes(size, cb)` version is dispatched to the pool to give the loop a chance to run between batches. `zlib.gzip` and `zlib.gunzip` are also CPU-bound and go through the pool, because the underlying zlib library is a synchronous C API.

```text
  What goes where in Node.js:

  ┌────────────────────────────────────────────────────────────┐
  │  EVENT LOOP (single thread)                                │
  │  - all V8 JavaScript execution                             │
  │  - network I/O (net, http, https, tls)  via epoll_wait     │
  │  - dns.resolve* family (c-ares, async)                     │
  │  - child_process IPC                                       │
  │  - timers, setImmediate, process.nextTick                  │
  │  - crypto.randomBytes (sync)                               │
  └────────────────────────────────────────────────────────────┘
                          ▲
                          │ posts results back via uv_async_send
                          │
  ┌────────────────────────────────────────────────────────────┐
  │  WORKER POOL (UV_THREADPOOL_SIZE threads, default 4)       │
  │  - fs.* (read, write, stat, readdir, ...)                  │
  │  - dns.lookup (getaddrinfo, blocking libc)                 │
  │  - crypto.pbkdf2, crypto.scrypt                            │
  │  - crypto.randomBytes (async variant)                      │
  │  - zlib.gzip, zlib.gunzip, zlib.deflate, ...               │
  │  - some user-supplied C++ add-ons                          │
  └────────────────────────────────────────────────────────────┘
```

The crucial non-obvious point: network I/O does *not* use the pool. A Node service handling 10 000 concurrent HTTP connections does not need `UV_THREADPOOL_SIZE=10000` — all 10 000 sockets are multiplexed through a single `epoll_wait` call on the event loop. The pool is only for the four categories above. This is what makes Node's concurrency model work: the cheap I/O (network) scales to tens of thousands of connections on one thread; the expensive I/O (disk, DNS, crypto) is capped at 4 concurrent operations by default and must be tuned if your workload is dominated by them.

### The libuv Thread Pool size: `UV_THREADPOOL_SIZE` environment variable (default: 4 threads, max: 1024).

The pool size is set by the `UV_THREADPOOL_SIZE` environment variable, read once at process startup (changing it later has no effect). The default is 4 threads; the maximum is 1024 (defined as `UV_THREADPOOL_MAX_SIZE` in `deps/uv/include/uv.h`). The pool is created lazily — the threads are not spawned until the first blocking call is made, which is why a freshly-started Node service shows only one thread (the main thread) in `top -H` until the first `fs.readFile` lands. Once created, the threads persist for the lifetime of the process; they are not destroyed when idle.

The pool size is the upper bound on concurrent blocking operations across the entire process. If `UV_THREADPOOL_SIZE=4` and five `fs.readFile` calls land simultaneously, four run on pool threads and the fifth waits in libuv's internal work queue until one of the four finishes. The queue is a simple FIFO implemented as an `uv_async_t` paired with a `uv_mutex_t` + `uv_cond_t` — pool threads block on `uv_cond_wait` when the queue is empty and are woken by `uv_async_send` when work is enqueued. The mechanism is straightforward and well-tested; the failure mode is when the queue grows unboundedly because the work arrives faster than the pool can drain it.

```bash
# Set the pool size before starting Node
UV_THREADPOOL_SIZE=8 node app.js

# Or in code (must be set before any blocking call)
process.env.UV_THREADPOOL_SIZE = 8;
```

The right value depends on the workload. The default of 4 is appropriate for a service that does mostly network I/O with occasional file reads. If your service is file-I/O-heavy (a static file server, a CDN origin, a media transcoder), bump it to 8 or 16. If your service is DNS-heavy (a crawler, a proxy), bump it but also consider switching from `dns.lookup` to `dns.resolve`. Going above `UV_THREADPOOL_SIZE=32` is rarely useful — you become limited by disk IOPS or DNS server rate limits, not by pool size, and the additional threads add context-switch overhead. The 1024 max is essentially a safety upper bound; real production values are 4–32.

```text
  Worker pool queue under load (UV_THREADPOOL_SIZE=4):

  Time  Queue              Pool thread 0   Pool thread 1   Pool thread 2   Pool thread 3
  ────  ─────────────────  ─────────────   ─────────────   ─────────────   ─────────────
   0ms  [F1, F2, F3, F4, F5]  F1 (10ms)       F2 (10ms)       F3 (10ms)       F4 (10ms)
   10ms [F5]                 F1 done→F5      F2 done         F3 done         F4 done
   20ms []                   F5 done         idle            idle            idle

  At 0ms, F5 is queued (no free thread). It waits until 10ms when a thread frees.
  If 100 reads arrive at once with each taking 10ms:
    - 4 run in parallel, 96 wait
    - Total time: (100/4) * 10ms = 250ms
  If UV_THREADPOOL_SIZE=8:
    - 8 run in parallel, 92 wait
    - Total time: (100/8) * 10ms = 125ms
```

The diagnostic for "is my pool size the bottleneck" is `node --inspect` and the Chrome DevTools Performance tab — the "Bottom-Up" view will show `uv__thread_pool_worker` frames dominating, and the "Event Log" will show `fs.readFile` callbacks queued for tens of milliseconds before they run. The simpler heuristic is to bump `UV_THREADPOOL_SIZE` from 4 to 16, restart the service, and watch p99 — if it improves, the pool was the bottleneck.

### Thread pool exhaustion failure modes and tuning strategies for high-I/O applications

Pool exhaustion is the failure mode where all pool threads are busy and the queue grows faster than it drains. The symptoms are subtle and easy to misdiagnose: the event loop is not stalled (it can still run network I/O and timers), but every `fs.readFile` callback takes 100 ms instead of 5 ms because it sat in the pool queue for 95 ms. A service that does 1 ms of CPU work and 5 ms of file I/O per request suddenly has a p99 of 200 ms because the file I/O is queueing behind the pool. The health check endpoint (which does not touch the pool) returns 200 OK in 1 ms; the actual request endpoints are slow. The load balancer thinks the service is healthy; the users know it is not.

The classic trigger is a "thundering herd" of file I/O. A cache invalidation event fires, 50 workers all call `fs.readFile('/etc/config.json')` simultaneously, the pool can only run 4 at a time, and 46 of them wait 12 ms each. Multiply by 100 000 such events per hour and the pool is permanently saturated. The second classic trigger is a slow DNS resolver — `http.request('https://api.example.com/...')` calls `dns.lookup('api.example.com')` on the pool, the DNS server is slow (50 ms per query), and 4 concurrent queries block the entire pool for 50 ms at a time. Every other file I/O in the process queues behind the DNS queries.

```javascript
// Diagnostic: measure pool queue wait time
const start = process.hrtime.bigint();
fs.readFile('/etc/config.json', () => {
    const elapsed = Number(process.hrtime.bigint() - start) / 1e6; // ms
    if (elapsed > 50) {
        console.warn(`pool queue wait: ${elapsed.toFixed(1)}ms`);
    }
});
```

The tuning strategies fall into three buckets. **Increase the pool size** (`UV_THREADPOOL_SIZE=16` or `32`) — appropriate if the workload is genuinely I/O-bound and the underlying resource (disk, DNS) can handle the parallelism. **Move DNS off the pool** — replace `http.request`'s default `lookup` function with `dns.resolve` (which uses c-ares and goes through epoll, not the pool), or pre-resolve hostnames at startup and cache them. **Move file I/O off the pool entirely** — use `io_uring` (experimental in Node 22 via `--experimental-io-uring`), use a memory-mapped file (`mmap` via a native add-on), or pre-load the file contents into memory at startup. The last is the most effective: if your config file is 10 KB, read it once at startup and serve it from a `Buffer` — no per-request pool usage at all.

The failure mode to watch for is **pool-induced cascading latency**. A service with 4 pool threads handling 1000 req/s, where each request does 5 ms of file I/O, is using 5 s of pool time per second of wall time — but the pool only provides 4 × 1 s = 4 s of pool time per second. The pool is over-subscribed by 25%, the queue grows, latency climbs, and eventually the load balancer's timeout fires and the request is retried, which adds more load. The fix is either more pool threads, less file I/O per request, or fewer requests (rate-limit at the edge). The metric to track is "pool queue wait time" — measure it with the diagnostic snippet above and alert if p99 > 10 ms.

### True CPU parallelism in Node.js: The `worker_threads` module and SharedArrayBuffer memory sharing

The worker pool solves the blocking-I/O problem, but it does not solve the CPU-bound problem. If your Node service needs to compute SHA-256 hashes of 1 GB files, or do JSON schema validation on huge payloads, or run a CPU-heavy ML inference, you cannot use the worker pool — the pool threads run libuv-internal C code, not V8 JavaScript. The escape hatch is the `worker_threads` module (stable since Node 12), which gives you true OS threads that each run their own V8 isolate, can execute JavaScript, and can share memory with the main thread via `SharedArrayBuffer`.

Each `worker_threads.Worker` is a separate V8 isolate with its own heap, its own event loop, and its own JavaScript context. Creating one is heavyweight (~10 ms, plus the cost of loading the worker script), so they are intended for long-lived worker pools, not per-request spawning. The standard pattern is to create a fixed pool of workers at startup (e.g., `WorkerPool` from libraries like `piscina`), and post tasks to them via `MessagePort`. The worker executes the task, posts the result back, and the main thread's event loop dispatches the result to the awaiting `Promise`.

The `SharedArrayBuffer` is the key to high-performance worker_threads usage. A `SharedArrayBuffer` is a chunk of memory allocated outside V8's heap (via `ArrayBuffer` with `SharedArrayBuffer` constructor) that is shared between all worker_threads and the main thread. Reads and writes go directly to the underlying memory; no copying. Atomics (`Atomics.load`, `Atomics.store`, `Atomics.compareExchange`) provide the synchronisation primitives to access shared memory safely. This is the JavaScript equivalent of `mmap(MAP_SHARED | MAP_ANONYMOUS)` plus `pthread_mutex` from section 02.

```javascript
// main.js
const { Worker } = require('worker_threads');
const shared = new SharedArrayBuffer(1024 * 1024 * 100); // 100 MB
const view = new Uint8Array(shared);

const worker = new Worker('./worker.js', { workerData: { shared } });
worker.on('message', (msg) => console.log('worker done:', msg));

// worker.js
const { parentPort, workerData } = require('worker_threads');
const view = new Uint8Array(workerData.shared);

// CPU-bound work — does not block the main thread's event loop
for (let i = 0; i < view.length; i++) {
    view[i] = compute(i);
}
parentPort.postMessage('done');
```

The failure mode to watch for is **`ArrayBuffer` transfer vs share**. When you `postMessage(buf)` a regular `ArrayBuffer`, V8 *transfers* ownership — the buffer is moved to the receiving thread and zeroed in the sender, which is O(1) but means the sender can no longer access it. When you `postMessage(buf, [buf])` with `buf` listed in the transfer list, the same happens explicitly. When you wrap the buffer in a `SharedArrayBuffer` (or list a regular `ArrayBuffer` in the transfer list of a `SharedArrayBuffer`'s `postMessage`), both threads can access it concurrently. The classic bug is to share a regular `ArrayBuffer` accidentally (by passing it through `workerData` without transferring), which works because Node copies it — but the copy is a full memcpy of the buffer, which for a 100 MB buffer is 50 ms. Always use `SharedArrayBuffer` for shared state, and always use the transfer list for one-way ownership transfer.

The diagnostic for worker_threads performance is the same as for the main thread: `--inspect-worker` opens a DevTools connection to a worker, and you can profile it independently. The `worker_threads` model has one significant limitation: V8 isolates do not share JIT code, so each worker recompiles hot functions from scratch. For a worker that runs a single function many times, this is fine (the JIT kicks in after ~1k calls); for a worker that runs many different functions, the JIT overhead per worker can be substantial. The mitigation is to use `worker_threads` only for genuinely CPU-bound work that is too heavy for the main thread, and to use the libuv pool for I/O-bound work.

## How This Connects to the Runtimes

Every runtime covered in section 04 is a user-space wrapper around these kernel primitives:

- **JVM**: Maps Java threads 1:1 to OS threads via NPTL. The JVM's memory model (section 04.01) is a specification layered on top of the kernel's virtual memory system described here.
- **Node.js / libuv**: The event loop (section 04.02) is a Reactor pattern built on `epoll_wait()`. The worker thread pool uses OS threads for operations that cannot be multiplexed (file I/O, DNS, crypto).
- **CPython**: The GIL (section 04.03) is a mutex that serializes Python bytecode execution across OS threads. Multi-processing in Python uses `fork()` to bypass the GIL.
- **PHP-FPM**: Each worker is a separate OS process (section 04.04). The shared-nothing model is a direct consequence of the process isolation described in the Linux Process Model note.

When you read those runtime notes, come back here and trace which kernel primitive each runtime feature maps to.
