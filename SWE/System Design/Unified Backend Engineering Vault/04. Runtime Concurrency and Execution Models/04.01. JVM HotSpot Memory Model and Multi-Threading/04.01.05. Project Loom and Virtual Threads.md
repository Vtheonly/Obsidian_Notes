# 04.01.05. Project Loom and Virtual Threads

## What This Is

**Project Loom and Virtual Threads** is the most consequential change to the JVM's concurrency model since `java.util.concurrent` in Java 5. Virtual threads (JEP 444, finalized in Java 21) are JVM-managed, user-space threads that multiplex millions of schedulable units onto a small pool of OS threads — the same model Erlang has had since the 1980s, Go has had since 2012, and Kotlin coroutines have had since 2018, but now built into the platform with no library and no special syntax. The motivation is that the thread-per-request model that has dominated Java web services since the servlet era does not scale to modern I/O-bound workloads: 10 000 concurrent HTTP requests, each blocked on a database call, would require 10 000 OS threads — ~80 GB of stack address space, hundreds of milliseconds of context-switch overhead per scheduling quantum, and an OOM kill long before you got there. Virtual threads let you write the same blocking, request-per-thread code with millions of concurrent requests, because each virtual thread costs a few hundred bytes (not 1 MB) and unmounts from its OS carrier when it parks on I/O.

This note covers the four things you need to know to use virtual threads correctly: why platform threads cap out around thousands, the M:N architecture that virtual threads use, the continuation mechanics that make parking cheap, and the pinning hazards that silently destroy the benefit. The forward link to section 05 is that Spring Boot 3.2+ has a `spring.threads.virtual.enabled=true` flag that flips Tomcat's request executor to virtual threads — the entire async/await machinery of `CompletableFuture` becomes unnecessary for plain I/O-bound controllers, and the migration from "Reactive Spring" back to "blocking Spring on virtual threads" is the current architectural trend.

## The Details

### The structural limits of Platform Threads (1:1 OS mapped)

A platform thread in the JVM is a 1:1 wrapper around an OS thread. Every `Thread.start()` ultimately calls `clone(CLONE_THREAD | CLONE_VM | CLONE_FILES | CLONE_SIGHAND)` (or the platform equivalent), and the kernel allocates a `task_struct`, schedules it on a CPU, and reserves a stack — typically 1 MB on Linux x86_64, configurable with `-Xss`. The OS thread is heavyweight because the kernel must be able to preempt it at any instruction (the timer interrupt fires, the scheduler saves the full register file to the `task_struct`, picks a new task, and restores its register file). That preemption is what makes thread-per-connection work, but it is also what makes it expensive: the register save/restore is ~1 µs, the cache pollution of switching to a different stack is ~5 µs of L1 miss penalty, and the kernel must hold a scheduler lock during the switch.

The structural limit is therefore memory, not scheduling. A 1 MB stack per thread means 1 000 threads = 1 GB of reserved address space (most of it not committed, but the kernel must reserve the virtual range), 10 000 threads = 10 GB, 100 000 threads = 100 GB which exceeds the cgroup limit of any reasonable container. On top of the stack, each `JavaThread` object in the JVM is ~1 KB of metadata, the `ObjectMonitor` list adds another few hundred bytes per contended lock, and the kernel's `task_struct` is ~10 KB. The practical ceiling on a 4 GB container is 2 000–4 000 threads before you hit either the cgroup, `ulimit -u`, or `vm.max_map_count`. For an I/O-bound service that needs 50 000 concurrent connections, this is a hard wall.

```text
  Platform thread cost (Linux x86_64, JDK 21 default):
  ┌────────────────────────────────────────────────────────────┐
  │  Stack reservation        1 048 576 bytes  (-Xss1m)        │
  │  JavaThread metadata          ~1 024 bytes                 │
  │  Internal C++ structs         ~4 096 bytes                 │
  │  Kernel task_struct          ~10 240 bytes                 │
  │  ─────────────────────────────────────                     │
  │  Total per thread            ~1 064 KB                     │
  │                                                           │
  │  Practical ceiling on 4 GB container:                     │
  │   ~3 500 threads before cgroup OOM                        │
  │   ~3 000 threads before ulimit -u                         │
  │   ~2 500 threads before GC pressure from JavaThread objs  │
  └────────────────────────────────────────────────────────────┘

  Virtual thread cost (same platform):
  ┌────────────────────────────────────────────────────────────┐
  │  Initial stack (continuation)  ~512 bytes (grows on demand)│
  │  VirtualThread object          ~256 bytes                  │
  │  Stack chunks (allocated as needed)  4 KB per chunk        │
  │  ─────────────────────────────────────                     │
  │  Total per virtual thread      ~1 KB at rest               │
  │                                                           │
  │  Practical ceiling on 4 GB container:                     │
  │   ~1 000 000 virtual threads (no kernel involvement)      │
  └────────────────────────────────────────────────────────────┘
```

The 1 MB stack is the killer. It exists because platform threads must be able to run arbitrary native code (JNI, the JVM's own C++ runtime, system calls) which needs a real, contiguous stack. Virtual threads do not need a 1 MB stack because they never run native code directly — they only run JVM bytecode, and the JVM can relocate their stack at will. This is the structural insight that makes virtual threads possible: they are not "lighter OS threads," they are a different abstraction that runs bytecode on a borrowed OS thread.

### Virtual Threads architecture: M:N user-space scheduling on top of a ForkJoinPool of Carrier Threads

Virtual threads implement an **M:N scheduler**: M virtual threads run on N OS threads (the carriers). The default carrier pool is a `ForkJoinPool` sized to `Runtime.getRuntime().availableProcessors()` (the same as `parallelStream`'s pool — they share it). A virtual thread is created with `Thread.ofVirtual().start(runnable)` or, more idiomatically, `Executors.newVirtualThreadPerTaskExecutor()` and `executor.submit(runnable)`. The virtual thread runs on whatever carrier the scheduler assigns it to; when it parks on a blocking I/O operation, the JVM **unmounts** it from the carrier (saving its continuation into a heap-allocated stack chunk) and the carrier is free to run another virtual thread. When the I/O completes, the JVM re-mounts the continuation on any free carrier and resumes execution.

The carrier pool's size is the ceiling on CPU-bound concurrency. If you have 8 CPUs and 8 carriers, then at most 8 virtual threads can be running CPU instructions at any instant — but millions can be parked on I/O, which is exactly the workload pattern of a web service. The scheduler is work-stealing: each carrier has a deque of ready virtual threads, and an idle carrier steals from the back of a busy carrier's deque. This is the same algorithm Go's runtime uses for goroutines, and it has the same property: work-stealing balances load without central coordination, and the cost of steal is ~100 ns. The migration from `CompletableFuture` to virtual threads is therefore mostly a deletion: replace `supplyAsync(..., pool).thenCompose(...)` with a plain blocking call inside a virtual thread, and the JVM does the same unmount/remount that the reactive runtime was doing manually.

```text
  M:N scheduling — virtual threads on carrier threads

  ┌────────────────── Virtual threads (M, in the millions) ───────────────┐
  │  VT#1 (parked on socket read)                                         │
  │  VT#2 (running on carrier A)    VT#3 (running on carrier B)           │
  │  VT#4 (parked on JDBC)          VT#5 (parked on JDBC)                 │
  │  VT#6 (parked on socket read)   VT#7 (queued, ready)                  │
  │  ... 1 000 000 more                                                    │
  └───────┬───────────────────────────────────────────────────┬───────────┘
          │ mount/unmount via continuation yield               │
          ▼                                                   ▼
  ┌──────────────── Carrier threads (N, default = CPU count) ─────────────┐
  │  Carrier A: [VT#2 running] [VT#7 queued]                              │
  │  Carrier B: [VT#3 running]                                            │
  │  Carrier C: idle (will steal VT#7 from A)                             │
  │  Carrier D: idle                                                      │
  └────────────────────────────────────────────────────────────────────────┘
                            │
                            ▼
                     OS scheduler (Linux CFS)
```

The key invariant is that virtual threads are cheap to create and cheap to park, but they are not free. Each virtual thread is a Java object (`java.lang.VirtualThread`) with a `Continuation` internal object that holds the stack chunks; each park/unmount copies the active stack chunk into the heap and each unpark/mount copies it back. The cost is ~1 µs per park/unmount pair, dominated by the memcpy of the stack chunk. This is comparable to a `CompletableFuture` callback chain and about 10× cheaper than a platform thread context switch. The takeaway is that the pattern "submit a virtual thread per request, do blocking I/O, return" is now the recommended Java idiom for I/O-bound services — it has the readability of synchronous code and the scalability of reactive code.

### Continuation mechanics: Freezing and unfreezing call stacks on non-blocking I/O system calls

The mechanism that makes virtual threads work is the **continuation**. A continuation is a reified call stack — a Java object that captures the full execution state (the bytecode PC, the operand stack, the local variables, the entire chain of caller frames) of a virtual thread at a yield point. When a virtual thread executes a blocking operation that the JVM knows how to handle (e.g., `Socket.read()` on a `java.nio` channel, `Thread.sleep()`, `LockSupport.park()`, `BlockingQueue.take()`), the operation does not actually block the carrier thread — instead it yields the continuation, which copies the stack frames from the carrier's stack into a heap-allocated `StackChunk`, parks the virtual thread on the I/O's completion future, and the carrier is free to run another virtual thread. When the I/O completes, the JVM re-mounts the continuation onto any carrier, copies the stack chunk back into the carrier's stack, and resumes execution at the yield point.

The yield point is the `Continuation.yield()` call, which the JVM intrinsifies. The trick is that the JVM's bytecode verifier and JIT co-operate to ensure that the stack at any yield point is "yieldable" — every frame on the stack must be a pure Java frame (no native frames, no pinned frames), and the JIT must have emitted deoptimisation metadata so the interpreter can reconstruct the stack from the compiled frame. This is why virtual threads were a multi-year project: the JVM already had most of the machinery (deoptimisation, stack walking, safepoints), but tying it all together for yield required touching every part of the runtime. The actual `Continuation` class is `jdk.internal.vm.Continuation` and is not part of the public API, but you can see it in a stack trace when a virtual thread is parked: the stack will end with `java.lang.VirtualThread.park` → `jdk.internal.vm.Continuation.yield0` → `jdk.internal.vm.Continuation.yield` and then the carrier's stack will be running a different virtual thread.

```text
  Virtual thread park / unmount flow (JDK 21):

  VT#42 calls socketChannel.read(buf)
   │
   ▼
  UnixChannel read returns 0 (no data) → registers with Selector
   │
   ▼
  VirtualThread.park() ──► Continuation.yield()
   │                          │
   │                          ▼
   │              copy VT#42's stack frames (carrier stack → StackChunk in heap)
   │                          │
   │                          ▼
   │              mark VT#42 as PARKED, add to selector's wakeup list
   │                          │
   │                          ▼
   │              carrier returns to its ForkJoinPool work queue
   │              picks another ready VT (say VT#7) and runs it
   │
   │   ... time passes, data arrives on socket ...
   │
  Selector wakes up
   │
   ▼
  VT#42 marked as RUNNABLE, enqueued on a carrier
   │
   ▼
  carrier picks up VT#42, calls Continuation.run()
   │
   ▼
  copy StackChunk back into carrier's stack
   │
   ▼
  resume execution at the yield point inside socketChannel.read
   │
   ▼
  read() now returns the data, VT#42 continues
```

The performance number to remember is that a virtual thread park/unmount is ~1 µs on modern hardware, and the equivalent `CompletableFuture` callback chain is ~1–2 µs (the callback allocation, the executor dispatch, the dep chain). So virtual threads do not make I/O-bound Java faster than reactive Java — they make it as fast, with synchronous code. The win is in maintainability: you read `String data = socket.read();` and you understand it; you read `socket.readAsync().thenApply(s -> ...)`, and you have to mentally reconstruct the continuation. The migration is asymmetric: `CompletableFuture` code still works on virtual threads (it just runs them on the carrier pool), so you can migrate incrementally. The trap is calling `.join()` on a `CompletableFuture` from a virtual thread — it works (the JDK detects the virtual thread and parks it) but it is slower than calling the underlying blocking API directly because the `CompletableFuture` machinery is unnecessary.

### Pinning hazards: Why `synchronized` blocks and native JNI calls can pin Virtual Threads to Carrier Threads and how to avoid it.

Pinning is the failure mode that silently destroys the virtual thread benefit. A virtual thread is **pinned** to its carrier when the JVM cannot unmount it at a yield point. While pinned, the carrier is blocked — it cannot run another virtual thread, and the scheduler effectively falls back to the platform-thread model. Pinning does not produce an error or a warning by default; it just produces worse-than-expected throughput and the symptom is "I enabled virtual threads and my service did not get faster."

There are two pinning causes. The first is `synchronized` blocks (or methods). When a virtual thread enters a `synchronized` block, the JVM uses the platform monitor (`pthread_mutex_t`) which is bound to the OS thread that acquired it — the monitor's owner is the carrier's TID, not the virtual thread. If the virtual thread parks inside the `synchronized` block (e.g., it does I/O while holding the lock), the JVM cannot unmount it because the monitor cannot be transferred to a different carrier. The fix is `ReentrantLock`, which is a Java-level lock that stores the owner as a `Thread` reference and can be transferred (or, more precisely, can be released and re-acquired across a yield). The JDK team chose not to make `synchronized` work with virtual threads because doing so would have required rewriting the monitor implementation and breaking the JNI native monitor contract. Instead, JEP 491 (in JDK 24) is finally removing this restriction.

The second pinning cause is JNI native calls. While a virtual thread is executing native code (a JNI method), the JVM has no yield point — the native code is opaque. If the native code blocks, the carrier blocks. The fix here is harder: the native code must be rewritten to use non-blocking I/O and to call back into the JVM to park the virtual thread (`JVM_VirtualThreadPark` and friends), which most legacy native libraries do not do.

```java
// BAD — virtual thread pins the carrier during socketRead
public synchronized String readSync() throws IOException {
    return socket.read();   // park inside synchronized = pin
}

// GOOD — ReentrantLock releases across the park
private final ReentrantLock lock = new ReentrantLock();
public String readLock() throws IOException {
    lock.lock();
    try {
        return socket.read();   // park releases the carrier
    } finally {
        lock.unlock();
    }
}
```

The diagnostic is the JVM flag `-Djdk.tracePinnedThreads=full` (or `=short`), which prints a stack trace every time a virtual thread is pinned. Run your integration test suite with this flag enabled before deploying virtual threads to production — if you see pinning traces, replace the offending `synchronized` with `ReentrantLock`. The metric to watch in production is the carrier pool's active thread count: if it equals the CPU count and stays there under load, you have pinning; if it varies and the queue of ready virtual threads drains, you do not. The `jcmd <pid> Thread.dump_to_file -format=json` output (JDK 21+) explicitly marks each virtual thread's state as `RUNNABLE`, `PARKED`, or `PINNED` — grep for `PINNED` to find offenders.

## How This Connects to the Runtimes

Every runtime covered in section 04 is a user-space wrapper around these kernel primitives:

- **JVM**: Maps Java threads 1:1 to OS threads via NPTL. The JVM's memory model (section 04.01) is a specification layered on top of the kernel's virtual memory system described here.
- **Node.js / libuv**: The event loop (section 04.02) is a Reactor pattern built on `epoll_wait()`. The worker thread pool uses OS threads for operations that cannot be multiplexed (file I/O, DNS, crypto).
- **CPython**: The GIL (section 04.03) is a mutex that serializes Python bytecode execution across OS threads. Multi-processing in Python uses `fork()` to bypass the GIL.
- **PHP-FPM**: Each worker is a separate OS process (section 04.04). The shared-nothing model is a direct consequence of the process isolation described in the Linux Process Model note.

When you read those runtime notes, come back here and trace which kernel primitive each runtime feature maps to.

## Hands-On Exercise

Open a terminal on a Linux machine and run the following commands to see these concepts in action:

```bash
# Start a Java 21+ app with virtual threads + pinning trace
java -Djdk.tracePinnedThreads=short \
     -Dspring.threads.virtual.enabled=true \
     -jar target/app.jar &

# Count virtual vs platform threads
jcmd $(jps | grep app | awk '{print $1}') Thread.print \
   | grep -c "java.lang.VirtualThread"

# Find pinned virtual threads (JDK 21+)
jcmd $(jps | grep app | awk '{print $1}') Thread.dump_to_file -format=json /tmp/tdump.json
jq '.threadDump.threads[] | select(.virtual == true and .state == "PINNED")' /tmp/tdump.json

# Push load and watch the carrier pool
wrk -t4 -c10000 -d60s http://localhost:8080/io-bound
top -H -p $(jps | grep app | awk '{print $1}')   # should show ~CPU-count carrier threads
```
