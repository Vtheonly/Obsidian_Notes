# 04.01.03. Garbage Collection Algorithms and Tuning

## What This Is

**Garbage Collection Algorithms and Tuning** is the most operationally consequential topic in the JVM sub-section. The garbage collector is the part of the JVM that reclaims memory the application no longer references, and the choice of algorithm — Serial, Parallel, CMS, G1, ZGC, or Shenandoah — directly governs your service's p99 latency, its throughput, and how big a heap you can run before pauses become unacceptable. Every Spring Boot service in production either ships with `-XX:+UseG1GC` (the default since JDK 9) or has consciously chosen ZGC/Shenandoah for sub-millisecond pauses or ParallelGC for batch throughput. The JVM is the only runtime in this section where GC tuning is a load-bearing skill: Node.js's Orinoco is mostly self-tuning, CPython's reference counting has no tunables, and PHP's per-request wipe sidesteps the question entirely. On the JVM, you will be asked to tune the GC, and the answer is in the GC log.

This note walks the GC stack from the bottom up: the generational hypothesis (why the heap is partitioned), the mark-sweep-compact algorithm (what a collector actually does), the write barrier and card tables (how it tracks cross-generational pointers), and then a head-to-head of every collector you will meet in production, with the real `-XX:` flags and the real log lines you read at 3 a.m.

## The Details

### The Generational Hypothesis: "Most objects die young."

The generational hypothesis is the empirical observation, validated across decades of real-world object lifetime traces, that the vast majority of allocated objects — typically 90–98% — become unreachable within one or two GC cycles. Iterator objects, intermediate `StringBuilder`s, temporary `Map.Entry` lists, lambda captures, request-scoped DTOs: all born, used, and dead in microseconds. The hypothesis is not a theorem; it is a measurement, and it justifies the entire structure of modern garbage collectors. If most objects die young, then partitioning the heap by age and collecting the young partition frequently (and cheaply) will reclaim most of the dead memory most of the time, without ever touching the long-lived objects that are expensive to scan.

Concretely, the JVM keeps the young generation small (typically 25–33% of the heap) and collects it with a copying collector. A copying collector walks the GC roots (static fields, thread stacks, JNI global references) and copies every reachable object out of Eden into a Survivor space, bumping the allocation pointer as it goes. Dead objects — the 90%+ that are unreachable — are never touched; they simply vanish when the survivor becomes the new Eden and Eden is reset. This is why a minor GC on a 2 GB young gen finishes in 5–20 ms while a major GC on a 10 GB old gen takes hundreds of milliseconds: the minor GC's cost is proportional to the *live* data, while a non-generational collector's cost would be proportional to the *total* data. The hypothesis turns a quadratic problem into a linear one.

```text
        Object lifetime distribution (typical web service)
        ─────────────────────────────────────────────────
   100% ┤■■■■■■■■■■■■■■■
        │              ╲
    10% ┤                ╲___
        │                    ╲___
     1% ┤                        ╲____
        │                             ╲___________
   0.1% ┤                                         ╲_________
        └──┬──────────┬───────────┬──────────────┬────→  age
        born     1 minor GC   2 minor GCs    tenured
              (90%+ die)    (most of rest)  (long-lived)
```

The hypothesis breaks down in two regimes. First, **caches** — `ConcurrentHashMap` entries that live for hours deliberately violate "die young" and will fill the old generation, forcing frequent major GCs. Second, **batch pipelines** that hold large working sets for the duration of a job (a Spark shuffle, a Lucene index build) also violate the hypothesis because nothing dies until the job ends. The diagnostic is `jstat -gcutil <pid> 1000` and watch the `O` (old gen utilisation) column: if `O` keeps growing and major GC (`YGC` versus `FGC`) frequency climbs, the hypothesis is not holding for your workload and you need either a bigger old gen (`-XX:NewRatio=3`), a different collector (ZGC handles huge tenured sets better), or an explicit off-heap cache (Caffeine's `OffHeap` builder).

### Mark-Sweep-Compact phases and Stop-The-World (STW) pauses

A tracing collector reclaims memory in three conceptual phases. **Mark** walks the object graph from the GC roots and tags every reachable object as live. **Sweep** scans the heap linearly and frees any object that was not marked (this phase is what gives the original Mark-Sweep algorithm its name and its fragmentation problem — freed memory leaves holes). **Compact** moves live objects together to eliminate fragmentation and restore bump-pointer allocation; this is the expensive phase because every moved object requires every reference to it to be updated, which means the mutator threads must be stopped for the duration. The combination is called **Mark-Sweep-Compact**, and almost every industrial collector is a variation of it.

The **stop-the-world** pause is the period during which all application threads are paused so the collector can safely mutate the object graph. Without STW, a mutator could overwrite a pointer the collector was about to update, leaving a dangling reference. Modern collectors (CMS, G1, ZGC, Shenandoah) all try to do as much of the mark and sweep concurrently with the mutator as possible, but at minimum the initial root scan and the final compaction require a STW pause. The trick is to make those STW pauses short and predictable: G1 pauses for 50–200 ms by collecting only a subset of regions per cycle, ZGC pauses for sub-millisecond by using coloured pointers and load barriers, and Shenandoah uses Brooks pointers (a forwarding pointer in every object header) to allow concurrent compaction.

```text
  Mutator timeline (single GC cycle, G1-style):

  ┌──────┬──┬───────────────────────────────┬──┬──────┐
  │ run  │ST│ concurrent mark + relocate     │ST│ run  │
  │      │W │  (mutator keeps running,       │W │      │
  │      │  │   reads through load barrier)  │  │      │
  └──────┴──┴───────────────────────────────┴──┴──────┘
   app    ↑   ↑ concurrent work              ↑   app
   runs  init  (most of the cycle)         final
        mark                              mark
        (root                              +
        scan)                            relocate
                                          (small STW)
```

The production consequence of STW is that every in-flight HTTP request stalls for the duration of the pause. A 200 ms G1 pause on a service with a 100 ms p99 budget means p99.9 jumps to 300+ ms for that cycle. The diagnostic is the GC log line that begins with `Pause Young (G1 Evacuation Pause)` and ends with `User=0.23s Sys=0.01s Real=0.05s` — the `Real` value is the wall-clock pause the application experienced. If `Real` exceeds your latency budget you need a different collector (ZGC, Shenandoah), a smaller young gen, or a smaller heap region size (`-XX:G1HeapRegionSize=4m` reduces the per-region cost but increases region count). The historical failure mode is `Pause Full (G1 Compaction Pause)` — the fallback full GC that G1 does when it cannot keep up. A `Pause Full` in the log is a red alert: G1 was not designed to do them and they take seconds.

### Garbage Collectors analyzed: Serial GC, Parallel GC, G1GC (Garbage-First GC), ZGC (Ultra-Low Latency Pauseless GC).

**Serial GC** (`-XX:+UseSerialGC`) is the simplest collector: one thread, mark-sweep-compact, full STW. It is the default on machines with a single CPU core and on small heaps (< 1.5 GB). It exists for embedded Java and for educational purposes — every other collector is a parallel or concurrent variant of it. Do not run it in production on a multi-core service; it will produce multi-second pauses.

**Parallel GC** (`-XX:+UseParallelGC`, also called "Throughput Collector") uses multiple GC threads for the mark-sweep-compact phases but is still fully STW. It is optimised for throughput — the goal is to minimise total GC time per unit of work, accepting that individual pauses will be long. It is the right choice for batch jobs (Spark, Hadoop, ETL pipelines) where you do not care about p99 because no human is waiting on a single request. The default pause target is `-XX:MaxGCPauseMillis=…` which the collector interprets as a hint and adjusts young-gen sizing to meet. A typical ParallelGC pause on a 16 GB heap is 500 ms–2 s.

**CMS** (`-XX:+UseConcMarkSweepGC`, the "Concurrent Mark-Sweep" collector) was the first widely deployed low-pause collector: it did the mark phase concurrently with the mutator and only stopped the world for an initial root scan and a final remark. CMS was deprecated in JDK 9 and removed in JDK 14 because it suffered from fragmentation (it never compacted, only swept) and "concurrent mode failures" where the mutator allocated faster than CMS could reclaim, forcing a STW Full GC. If you encounter CMS in production, the migration target is G1.

**G1GC** (`-XX:+UseG1GC`, default since JDK 9) divides the heap into 1–32 MB **regions** (the size is chosen automatically based on `-Xmx`) and tracks the garbage density of each. A G1 cycle collects a subset of regions — chosen to maximise garbage reclaimed per unit of pause time, hence "garbage first" — and evacuates live objects into empty regions. The young generation is not a contiguous space but a set of regions labelled "young"; the old generation is another set. G1 pauses are typically 50–200 ms and are bounded by `-XX:MaxGCPauseMillis=200` (the default). The tuning knob that matters most is `-XX:G1HeapRegionSize`: larger regions (32 MB) suit large heaps and large object allocation; smaller regions (1 MB) suit latency-sensitive services.

**ZGC** (`-XX:+UseZGC`, production-ready in JDK 15, generational in JDK 21) is the state-of-the-art low-latency collector. It uses **coloured pointers** — it steals 4 bits from the 64-bit pointer to encode metadata ("marked", "remapped", "finalisable") — and a **load barrier** in the interpreter and JIT-compiled code that synchronises the pointer with the current GC cycle every time a pointer is read from the heap. This lets ZGC do all of marking, relocation, and remapping concurrently with the mutator, with STW pauses of < 1 ms even on multi-terabyte heaps. The cost is ~10% throughput overhead (the load barrier runs on every heap read) and slightly higher native memory usage (the coloured pointers require multi-mapping). **Shenandoah** (`-XX:+UseShenandoahGC`, Red Hat's collector, also production-ready in JDK 15) achieves the same goal with a different mechanism: every object has a **Brooks pointer** (an extra word in the object header that points to itself or, after relocation, to its new location), and the load barrier follows the Brooks pointer. Both collectors trade throughput for pause time; both are suitable for latency-sensitive services on large heaps.

| Collector | Flag | Default? | Pause time (16 GB heap) | Best for |
|---|---|---|---|---|
| Serial | `-XX:+UseSerialGC` | single-core / <1.5 GB | 1–5 s | Embedded, teaching |
| Parallel | `-XX:+UseParallelGC` | JDK 8 default on server | 0.5–2 s | Batch, Spark, ETL |
| CMS | `-XX:+UseConcMarkSweepGC` | Deprecated JDK 9, removed JDK 14 | 50–200 ms (if no fail) | Legacy only — migrate to G1 |
| G1 | `-XX:+UseG1GC` | **JDK 9+ default** | 50–200 ms | General-purpose services |
| ZGC | `-XX:+UseZGC` | Generational in JDK 21 | < 1 ms | Large-heap latency-critical |
| Shenandoah | `-XX:+UseShenandoahGC` | Red Hat builds | < 10 ms | Large-heap latency-critical (RH) |

### Monitoring JVM memory: GC logging flags, `jstat`, `jmap`, `jcmd`, and analyzing heap dumps (`.hprof`) via Eclipse MAT.

GC observability is not optional. The JVM cannot tell you why it paused unless you asked it to log the pauses. The modern logging flag (JDK 9+) is `-Xlog:gc*:file=/var/log/app/gc.log:time,level,tags:filecount=10,filesize=100M` — this writes unified JVM logs to a rotating file. A typical G1 minor GC log line looks like:

```text
[2024-05-12T03:14:22.812+0000][info][gc,start] GC(42) Pause Young (Normal) (G1 Evacuation Pause)
[2024-05-12T03:14:22.812+0000][info][gc,task] GC(42) Using 8 workers of 8 for evacuation
[2024-05-12T03:14:22.834+0000][info][gc,phases] GC(42)   Pre Evacuate Collection Set: 0.1ms
[2024-05-12T03:14:22.834+0000][info][gc,phases] GC(42)   Evacuate Collection Set: 19.8ms
[2024-05-12T03:14:22.834+0000][info][gc,phases] GC(42)   Post Evacuate Collection Set: 1.2ms
[2024-05-12T03:14:22.834+0000][info][gc,phases] GC(42)   Other: 0.4ms
[2024-05-12T03:14:22.834+0000][info][gc,heap] GC(42) Eden regions: 124->0(124)
[2024-05-12T03:14:22.834+0000][info][gc,heap] GC(42) Survivor regions: 4->16(16)
[2024-05-12T03:14:22.834+0000][info][gc,heap] GC(42) Old regions: 220->221
[2024-05-12T03:14:22.834+0000][info][gc,metaspace] GC(42) Metaspace: 89M->89M(1088M)
[2024-05-12T03:14:22.834+0000][info][gc] GC(42) Pause Young (Normal) (G1 Evacuation Pause) 1024M->208M(2048M) 21.812ms
```

The line ending in `1024M->208M(2048M) 21.812ms` is the summary: heap went from 1024 MB used to 208 MB used, the heap capacity is 2048 MB, and the pause took 21.812 ms. The first number (`User=…` in the old log format) is the total CPU time across all GC threads; the last (`Real=…`) is the wall-clock pause the application experienced. Always read `Real`, not `User` — a 200 ms `User` time on 8 GC threads is only 25 ms `Real`, which is fine; a 200 ms `Real` is a real production incident.

The CLI tools complement the log. `jstat -gcutil <pid> 1000` prints a one-line-per-second summary of each generation's utilisation and the GC counts (`YGC` young, `FGC` full). `jcmd <pid> GC.heap_info` prints the region layout. `jmap -histo:live <pid>` triggers a Full GC and then prints a histogram of object counts by class — invaluable for finding the type that is leaking. `jcmd <pid> GC.heap_dump /tmp/heap.hprof` writes a heap dump that you load into Eclipse MAT (Memory Analyzer Tool); MAT's "Leak Suspects" report will find the GC root holding your leak (typically a `static final` map in a framework class that was never cleared).

The production playbook for a GC incident is: (1) `jcmd <pid> GC.heap_info` to confirm the heap is full, (2) `jcmd <pid> GC.heap_dump /tmp/heap.hprof` for offline analysis, (3) `jstat -gcutil <pid> 1000` to see if the leak is in young (allocation spike) or old (slow leak), (4) `jmap -histo:live <pid>` to see the class distribution. The MAT "Dominator Tree" view will show you, in bytes, which object retains which — usually the answer to "what is leaking" is the top dominator that is not a framework singleton.

## Cross-Runtime Comparison

| Aspect | JVM (HotSpot) | Node.js (V8) | CPython | PHP (Zend) |
|---|---|---|---|---|
| GC algorithm | Generational + region (G1/ZGC) | Generational (Scavenger + Mark-Sweep) | Refcount + cyclic gen-0/1/2 | None (per-request wipe) |
| Pause time | 50–200 ms (G1), <1 ms (ZGC) | 5–50 ms (young), 100+ ms (major) | <5 ms (rare, cyclic only) | 0 (no GC) |
| Tuning flags | 50+ `-XX:` flags | `--max-old-space-size`, `--expose-gc` | `gc.get_threshold()` | N/A |
| Heap dump | `.hprof` via `jcmd` | `.heapsnapshot` via `--inspect` | `tracemalloc` snapshot | N/A |
| Failure mode | Full GC, evacuation failure, OOM | Major GC pause, heap out of memory | Cyclic GC pause on huge graphs | N/A (memory wiped per request) |

These differences are why the same algorithm performs differently in each runtime. When you read the anchor implementation in Spring Boot (JVM), keep in mind that the delta implementations in Node.js, Python, and PHP will exhibit different failure modes under load — but only on the JVM does GC tuning have an entire sub-discipline with dedicated flags and dedicated tooling.
