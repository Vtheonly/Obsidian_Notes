# 04.01.04. Java Multi-Threading and Memory Concurrency

## What This Is

**Java Multi-Threading and Memory Concurrency** is the contract between the JVM and the developer about how threads see each other's writes. The kernel gives the JVM OS threads via `clone(CLONE_THREAD | CLONE_VM)` (see section 02), but OS threads alone do not give you a memory model — they give you raw x86_64/arm64 memory ordering, where the CPU is free to reorder loads and stores for performance and where each core's L1 cache may hold a stale value for arbitrarily long. The **Java Memory Model (JMM)**, formalised in JSR-133 and shipped in Java 5, is the specification that says which reorderings the JVM is allowed to perform and what you, the developer, must do to establish visibility guarantees. Every `synchronized`, `volatile`, `final`, and `Atomic*` you write is a contract with the JMM, and every concurrency bug that "works on my machine" but fails in production is a JMM violation the JIT was allowed to make.

This note covers the four layers of the JMM in increasing sophistication: the **happens-before** relationship (the formal model), the `synchronized` keyword and lock inflation (the most common synchronisation), the `volatile` keyword and memory fences (lightweight visibility), and the `java.util.concurrent.atomic` package and CAS (lock-free data structures). Above these primitives sit `ReentrantLock`, `ExecutorService`, and `CompletableFuture`, which are the building blocks Spring Boot and Netty actually use. Understanding the primitives is what lets you read `jstack` output and know whether a thread is parked on a monitor, a `LockSupport.park`, or a CAS spin.

## The Details

### The Java Memory Model (JMM): Visibility, Reordering, and Happens-Before guarantees

The JMM is defined in terms of two concepts: **actions** (reads, writes, lock acquires, lock releases, thread starts, thread joins, `volatile` reads/writes, `final` field writes in a constructor) and the **happens-before** partial order between them. The rule is: if action A *happens-before* action B, then the results of A are visible to B — A's writes have been flushed from the CPU store buffer to a state where B's CPU core can observe them, and A's CPU reordering cannot cause B to see an older value. Every concurrency primitive in Java is ultimately a way of establishing a happens-before edge.

The rules that create happens-before edges are: (1) program order within a single thread (each action happens-before every subsequent action in the same thread — this is what lets you write `x = 1; y = x + 1;` and expect `y` to be 2), (2) monitor lock — an unlock on a monitor happens-before every subsequent lock on the same monitor, (3) `volatile` field — a write to a `volatile` field happens-before every subsequent read of the same field, (4) `Thread.start()` — a call to `start()` happens-before any action in the started thread, (5) `Thread.join()` — every action in a thread happens-before another thread returns from `join()` on it, (6) `final` field — the write of a `final` field in a constructor happens-before the published reference to the object is visible to any other thread, (7) `synchronised`-with edges through the `java.util.concurrent` atomics and synchronisers. If you cannot trace a happens-before chain from a write in thread A to a read in thread B, the JMM does not guarantee that B will see A's write — and the JIT is free to cache the field in a register forever.

```text
  Thread A                            Thread B
  ────────                            ────────
  x = 42;
  ready = true;  (volatile write)     while (!ready) {}   (volatile read)
                                      assert x == 42;     ✓ guaranteed by HB
  ────── happens-before ──────────────►
   (a volatile write on a field
    happens-before a subsequent
    volatile read of the same field)

  Without the volatile, the JMM does NOT guarantee that B sees x == 42.
  The JIT may hoist `ready` into a register, the CPU may reorder
  the two stores, or B's core may serve `ready` from its stale L1.
```

The classic JMM bug is "double-checked locking" without `volatile`. The pattern:

```java
private static Singleton instance;   // BUG: missing volatile
public static Singleton getInstance() {
    if (instance == null) {
        synchronized (Singleton.class) {
            if (instance == null) instance = new Singleton();
        }
    }
    return instance;
}
```

Without `volatile` on `instance`, thread B may see a non-null `instance` that points to a partially constructed object — the constructor's writes have not been flushed, because there is no happens-before edge between A's write to `instance` (inside the `synchronized` block) and B's read (outside it). The fix is `private static volatile Singleton instance;`. The deeper lesson: if you find yourself reasoning about "is this safe without volatile," the answer is no; add the `volatile` and stop reasoning.

### Synchronizations: Intrinsic locks (`synchronized`), Object monitors, and lock inflation (Biased → Basic/Thin → Heavyweight OS Mutex).

The `synchronized` keyword is the oldest and most ergonomic Java synchronisation primitive. Every Java object has a **monitor** associated with it; entering a `synchronized` block on object `o` calls `monitorenter o` (compiled to a JVM instruction), and exiting calls `monitorexit o`. The monitor is reentrant — the same thread can enter it multiple times without deadlocking — and it is exclusive: only one thread can hold it at a time. The JMM happens-before rule for monitors is that an unlock on a monitor happens-before every subsequent lock on the same monitor, which is why `synchronized` is also a memory fence.

The clever part is **lock inflation**, the JVM's mechanism for making `synchronized` cheap in the uncontended case. The object header's **mark word** (see [[04.01.02. JVM Memory Layout and Allocation]]) is overloaded to encode the lock state, and the JVM transitions through three states as contention rises. The initial state, on by default in JDK 5–14 and controversial since, is **biased locking**: the mark word records the owning thread's ID, and entry/exit is a single compare-and-swap that only fires the first time. If no other thread ever contends, no real lock is taken — the biased lock is just metadata in the header. Biased locking was disabled by default in JDK 15 (JEP 374) because the cost of revocation (a safepoint) on heavily-contended workloads outweighed the benefit on modern code that uses `ReentrantLock` instead.

When a second thread tries to acquire a biased lock, the JVM **revokes** the bias (a safepoint), and the lock **inflates** to a **thin lock** (also called basic lock): the mark word now contains a CAS'd pointer to a per-thread stack-allocated lock record, and entry/exit is a CAS on the mark word. Thin locks are still fast — ~10 ns uncontended — because no OS primitive is involved. Only when the CAS starts failing repeatedly (a short spin fails to acquire) does the lock inflate to a **fat lock**: a `pthread_mutex_t` (or equivalent platform mutex) is allocated in the JVM's `ObjectMonitor` C++ structure, the mark word is updated to point to it, and further acquisitions go through the kernel `futex` syscall. Fat lock acquisition takes ~1 µs because it involves a syscall and a thread park; this is the price of contention.

```text
  Object header mark word (64 bits, compressed):
  ┌────────────────────────────────────────────────────────────────┐
  │  State          │  Encoding (low bits)  │  Stored data          │
  ├─────────────────┼───────────────────────┼───────────────────────┤
  │  Unlocked       │  001                  │  hash code + age      │
  │  Biased         │  101                  │  thread ID + epoch    │
  │  Thin (basic)   │  000                  │  ptr to lock record   │
  │  Fat            │  010                  │  ptr to ObjectMonitor │
  │  Marked for GC  │  011                  │  forwarding ptr       │
  └─────────────────┴───────────────────────┴───────────────────────┘

  Lock inflation state machine:
  Unlocked ──(first sync)──► Biased ──(2nd thread)──► Thin ──(contention)──► Fat
       ▲                       │                      │                       │
       └───────────────────────┴──────────────────────┴───── deflate ────────┘
```

The production failure mode of `synchronized` is **lock contention on shared state**. The `jstack <pid>` output marks a thread parked on a monitor with `BLOCKED (on object monitor)` and shows the lock address; `jcmd <pid> Thread.print` does the same. If many threads are BLOCKED on the same monitor, you have a bottleneck — typically a `static final Map` accessed under `synchronized`, a database connection pool with a single guard, or a `SimpleDateFormat` shared across threads (the classic Java bug). The fix is either to shard the lock (a `Striped<Lock>` from Guava), to switch to `ConcurrentHashMap` (which uses lock-free CAS internally), or to use `ReentrantLock` with `tryLock` and a timeout to surface deadlocks.

### The `volatile` keyword: Memory barriers/fences and preventing CPU cache incoherence

The `volatile` keyword is the lighter-weight alternative to `synchronized` for the case where you only need visibility, not mutual exclusion. A `volatile` field guarantees two things: (1) **visibility** — every write to the field is immediately flushed to main memory, and every read goes directly to main memory, bypassing the CPU's L1/L2 cache, so all threads see the same value; (2) **atomicity** for single reads/writes — a `volatile long` is guaranteed to be written atomically even on 32-bit JVMs where plain `long` writes can be torn. It does **not** make `i++` atomic, because `i++` is read-modify-write and the read and the write are two separate `volatile` operations that another thread can interleave between.

Under the hood, `volatile` is implemented with CPU memory barriers. On x86_64 a `volatile` write emits a `mov` followed by a `lock add %rsp` (a cheap way to issue a full memory fence); on arm64 it emits `stlr` (store-release). A `volatile` read on x86_64 is just a `mov` (x86 already has strong ordering, so plain reads are acquire), but on arm64 it emits `ldar` (load-acquire). The JIT inserts these barriers; the interpreter executes them through the template table. The result is that a `volatile` write is ~5–10 ns on x86_64 (the cost of the barrier, not the cache miss) and a `volatile` read is ~1 ns. This is dramatically cheaper than `synchronized` in the contended case, which is why `volatile boolean stop` is the canonical pattern for signaling a worker thread to stop.

```java
public class Worker implements Runnable {
    private volatile boolean stop = false;   // volatile: visibility to worker thread

    public void run() {
        while (!stop) {                     // JIT cannot hoist `stop` into a register
            doWork();
        }
    }

    public void shutdown() {
        this.stop = true;                   // happens-before worker's next read of stop
    }
}
```

Without `volatile` on `stop`, the JIT is allowed to hoist the read of `stop` out of the loop (the JIT sees that no write happens inside the loop, so it caches the value `false` in a register), and the worker never terminates. This is the same bug as the double-checked-locking example: without a happens-before edge, the JMM does not require visibility, and the JIT will exploit that for performance. The failure mode is "works in dev, hangs in prod" — dev runs with `-Xint` (interpreter only, no JIT) or with a small heap that prevents the JIT from kicking in, and the JIT in prod exposes the race. The diagnostic is to add `volatile` and see if the bug disappears; if it does, you had a JMM bug.

### Low-level primitives: Compare-And-Swap (CAS) operations, `java.util.concurrent.atomic`, and lock-free data structures.

CAS is the foundation of every lock-free data structure in the JVM. A CAS operation takes three arguments — a memory address, an expected value, and a new value — and atomically writes the new value to the address only if the current value equals the expected value, returning a boolean. On x86_64 it compiles to the `lock cmpxchg` instruction; on arm64 it compiles to `ldaxr`/`stlxr` (load-acquire exclusive / store-release exclusive). CAS is the universal primitive because it lets you implement any read-modify-write without a lock: read the value, compute the new value, CAS it in, retry if the CAS failed because another thread raced. The retry loop is called a **spin** and the pattern is the basis of `AtomicInteger.incrementAndGet()`, `ConcurrentHashMap.putIfAbsent()`, and `AtomicReference.compareAndSet()`.

The `java.util.concurrent.atomic` package (added in Java 5) wraps CAS in a usable API. `AtomicInteger`, `AtomicLong`, `AtomicReference`, `AtomicStampedReference` (which carries a version stamp to defeat the ABA problem), `LongAdder` (which shards across threads for high-contention counters), and `AtomicIntegerFieldUpdater` (which uses reflection to CAS a `volatile` field without changing its declared type) are the main types. They all delegate to `Unsafe.compareAndSwap*` (or, since Java 9, `VarHandle.compareAndSet`), which is the JVM's intrinsic that emits the platform CAS instruction. The `Unsafe` API is internal and unsupported, but it is what every JVM concurrency library is built on — Netty, JCTools, Akka, Disruptor, and even `java.util.concurrent` itself.

```text
  AtomicInteger counter = new AtomicInteger(0);
  Thread A:  counter.incrementAndGet();
             └─►  int old = counter.get();          // 0
                  int next = old + 1;                // 1
                  if (counter.compareAndSet(0, 1))   // CAS: if *ptr==0, write 1
                      return 1;                      // success
                  else
                      retry;                         // CAS failed → spin

  Thread B:  counter.incrementAndGet();              // races with A
             └─►  if (counter.compareAndSet(0, 1))   // fails if A already wrote 1
                      return 1;
                  else {                              // CAS failed
                      int old = counter.get();        // 1
                      int next = old + 1;             // 2
                      if (counter.compareAndSet(1, 2))// retry with new expected
                          return 2;
                  }
```

The production failure mode of CAS is **livelock under contention**. If 100 threads all try to CAS the same `AtomicInteger`, the success rate is ~1% per attempt, and the other 99 threads spin and burn CPU. The diagnostic is high CPU utilisation with low throughput — `top -H -p <pid>` shows many threads at 100% CPU but `jstack` shows them all in `Unsafe.compareAndSwapInt`. The fix is `LongAdder` (which uses a per-thread cell array and only sums on read, so writes never contend) for counters, or `ConcurrentHashMap` (which uses a striped lock array internally) for maps, or `ReentrantLock` (which uses an OS park instead of a spin when contention is high) for arbitrary critical sections. The Disruptor pattern (a single-writer, single-reader ring buffer) is the extreme solution for ultra-low-latency workloads where even CAS contention is too much.

## How This Connects to the Runtimes

Every runtime covered in section 04 is a user-space wrapper around these kernel primitives:

- **JVM**: Maps Java threads 1:1 to OS threads via NPTL. The JVM's memory model (section 04.01) is a specification layered on top of the kernel's virtual memory system described here.
- **Node.js / libuv**: The event loop (section 04.02) is a Reactor pattern built on `epoll_wait()`. The worker thread pool uses OS threads for operations that cannot be multiplexed (file I/O, DNS, crypto).
- **CPython**: The GIL (section 04.03) is a mutex that serializes Python bytecode execution across OS threads. Multi-processing in Python uses `fork()` to bypass the GIL.
- **PHP-FPM**: Each worker is a separate OS process (section 04.04). The shared-nothing model is a direct consequence of the process isolation described in the Linux Process Model note.

When you read those runtime notes, come back here and trace which kernel primitive each runtime feature maps to.

## Hands-On Exercise

Open a terminal on a Linux machine and run the following commands to see these concepts in action:

```bash
# Spin up a JVM under load and inspect it
java -XX:+PrintCompilation \
     -XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining \
     -Xlog:gc*:file=/tmp/gc.log:time,level,tags \
     -jar target/app.jar &

# Watch live GC
jstat -gcutil $(jps | grep app | awk '{print $1}') 1000

# Capture a thread dump — count BLOCKED threads
jcmd $(jps | grep app | awk '{print $1}') Thread.print | grep -c BLOCKED

# Find what they are blocked on
jcmd $(jps | grep app | awk '{print $1}') Thread.print | grep -A1 BLOCKED
```

Correlate each output with the bullets above. If you cannot match a row in the output to a concept in this note, re-read the relevant section.
