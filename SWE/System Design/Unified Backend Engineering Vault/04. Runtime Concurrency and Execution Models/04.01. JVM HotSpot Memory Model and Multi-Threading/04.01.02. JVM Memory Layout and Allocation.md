# 04.01.02. JVM Memory Layout and Allocation

## What This Is

**JVM Memory Layout and Allocation** is the map of every byte of memory the JVM process touches. The kernel from section 02 gives the JVM a single flat virtual address space (carved out via `mmap` and `mprotect`); the JVM then partitions that space into regions with different lifetimes, different allocation strategies, and different GC policies. Spring Boot, Netty, Hibernate, and every other framework in section 05 are ultimately just code that allocates into these regions — and when production goes sideways (an OOM kill, a 30-second GC pause, a `DirectByteBuffer` leak that the heap dump does not show), the answer almost always lives in this map. The most common diagnostic mistake is treating "JVM memory" as synonymous with "the heap" — it is not. The heap is one of six large regions, and several of the others (Metaspace, the code cache, direct buffers, thread stacks) can OOM the process without ever tripping a `-XX:HeapDumpOnOutOfMemoryError`.

This note walks through each region, the flag that controls it, and the production failure mode it produces. The flags `-Xms`, `-Xmx`, `-Xss`, `-XX:MetaspaceSize`, `-XX:MaxMetaspaceSize`, `-XX:ReservedCodeCacheSize`, and `-XX:MaxDirectMemorySize` together describe the entire committed and reserved footprint of a JVM process — and the sum must fit under the container's cgroup limit or the OOM killer will end the process without any Java-level warning.

## The Details

### Method Area / Metaspace: Class metadata, constant pools, method bytecodes (Native memory)

The Method Area is the region the JVM uses to store everything it knows about a loaded class: the class name, the parent class, the implemented interfaces, the runtime constant pool, the field and method metadata, and the method bytecode itself. In Java 7 and earlier, this region was called **PermGen** and lived inside the JVM heap, sized by `-XX:PermSize` and `-XX:MaxPermSize`. PermGen was a constant source of `java.lang.OutOfMemoryError: PermGen space` because every dynamic class loader (every webapp redeploy in Tomcat, every `Proxy.newProxyInstance` in Spring AOP, every `cglib` subclass generated by Hibernate for lazy loading) leaked into it. In Java 8, PermGen was removed and replaced with **Metaspace**, which is allocated from native memory (off-heap, via `mmap`) and grows automatically up to `-XX:MaxMetaspaceSize` (default unlimited — bounded only by the process address space and the container cgroup).

The constant pool deserves a callout. Each class file contains a constant pool table (entries `CONSTANT_Class`, `CONSTANT_Methodref`, `CONSTANT_String`, `CONSTANT_InvokeDynamic`, and so on) that the JVM resolves at load time. Resolved entries (the actual `Symbol*` or `oop` pointers) are stored in the runtime constant pool, which lives in Metaspace. This is why a class with a large `String.intern()` table can blow up Metaspace — interned strings in JDK 7+ are stored in the Java heap, but the symbol references that point to them are in Metaspace, and a runaway dynamic class generator (e.g., a custom DSL that emits thousands of classes per request) will eventually exhaust it.

The typical production failure mode is a class-loader leak after a hot redeploy. The diagnostic is `jcmd <pid> GC.class_stats | sort -k 5 -rn | head` to list classes by Metaspace usage, and async-profiler's `--event=alloc` to find the allocating call site. The fix is either to set `-XX:MaxMetaspaceSize=512m` so the JVM dies loudly with a `Metaspace OOM` instead of silently growing into the cgroup limit, or to fix the leak by ensuring the dynamic class loader is dereferenced. The `-verbose:class` flag prints every `class load` and `class unload` event so you can verify the unload actually happens.

### Java Heap: Young Generation (Eden, Survivor Space S0, Survivor Space S1) and Old / Tenured Generation.

The heap is where every `new Object()` lives until the garbage collector reclaims it. It is the largest region (typically 50–75% of total JVM memory) and the only one that the GC traverses. Its internal structure comes from the **generational hypothesis** — the empirical observation that ~90% of objects die in their first GC cycle, so the heap should be partitioned by object age and collected with age-appropriate algorithms. The young generation is split into three spaces: **Eden** (where `new` allocates), **Survivor 0**, and **Survivor 1**. Most allocations happen bump-pointer style at the top of Eden (a single `mov` of the allocation pointer, no free list); when Eden fills, a minor GC pauses the mutator threads, walks the GC roots, copies live objects from Eden into one Survivor space (and from the other Survivor space into the same target, bumping their age counter), and frees Eden in O(1) by simply resetting the allocation pointer. This is "copying collection," and it is what makes minor GCs cheap — typically 5–20 ms on a 4 GB young gen.

Objects that survive a configurable number of minor GCs (`-XX:MaxTenuringThreshold=15`, the default) are promoted to the **old generation** (also called the tenured generation). The old generation is collected less frequently because it is assumed to be mostly live; collection there is more expensive (a full mark-sweep-compact or, with G1, a region-by-region evacuation) and produces the long pauses that hurt p99 latency. The default ratio is `-XX:NewRatio=2` (old:young = 2:1) and `-XX:SurvivorRatio=8` (Eden:each survivor = 8:1), so a 3 GB young gen is roughly 2.67 GB Eden + 0.17 GB S0 + 0.17 GB S1.

```text
  ┌──────────────────────────────────────────────────────────┐
  │                       JAVA HEAP                          │
  │  (sized by -Xms initial, -Xmx maximum; both via mmap)    │
  │                                                          │
  │  ┌────────────────────────────────────────────────────┐  │
  │  │            YOUNG GENERATION                        │  │
  │  │  (-XX:NewSize, -XX:MaxNewSize, or -XX:NewRatio)    │  │
  │  │  ┌──────────────────┬──────────┬──────────┐        │  │
  │  │  │      EDEN        │    S0    │    S1    │        │  │
  │  │  │  new allocations │ survivor │ survivor │        │  │
  │  │  │  bump-pointer    │  (from)  │   (to)   │        │  │
  │  │  └──────────────────┴──────────┴──────────┘        │  │
  │  │   Minor GC: copy live Eden→S_to, age+1, promote    │  │
  │  └────────────────────────────────────────────────────┘  │
  │  ┌────────────────────────────────────────────────────┐  │
  │  │            OLD / TENURED GENERATION                │  │
  │  │  Promoted objects that survived MaxTenuringThreshold│  │
  │  │  Collected by major GC (G1/ZGC/CMS — see 04.01.03) │  │
  │  └────────────────────────────────────────────────────┘  │
  └──────────────────────────────────────────────────────────┘
```

The flags you will actually touch in production: `-Xms4g -Xmx4g` (set them equal so the JVM never wastes time growing or shrinking the heap and never trips the GC ratio recalculation that fires on resize), `-XX:NewRatio=2` to set the young:old ratio, or `-Xmn1g` to fix the young gen size directly. The failure mode of mis-sizing is "promotion failure" — a minor GC discovers that all the survivors do not fit in the target Survivor space and the JVM has to either promote directly to old (a "premature promotion" that bloats the old gen and triggers early major GCs) or, in the worst case, fall back to a full GC mid-minor. The diagnostic is the GC log line `GC locker; young GC ... (promotion failed)` or, with G1, `Evacuation Failure`.

### Java Thread Stacks: Native OS thread stacks, stack depth limits (`-Xss`), local variables, and frame pointers.

Every Java thread maps 1:1 to a kernel thread (NPTL `clone()` with `CLONE_THREAD | CLONE_VM`), and every kernel thread needs a stack. The JVM allocates this stack with `mmap(..., MAP_ANONYMOUS | MAP_STACK, ...)` and protects the top page with `mprotect(PROT_NONE)` so a stack overflow traps as `SIGSEGV` (which the JVM's signal handler turns into `StackOverflowError`) instead of corrupting neighbouring memory. The default size is platform-dependent — 1 MB on Linux x86_64, 512 KB on 32-bit, 256 KB on OpenJDK zero — and is tunable with `-Xss512k` (per-thread, set at thread creation, cannot be changed mid-life).

The stack is partitioned into **frames**, one per method invocation. A frame contains the local variable array (slot 0 is `this` for instance methods, then the parameters, then the locals declared inside the method), the operand stack (where bytecode pushes and pops intermediate values), and the frame metadata (the return PC, the previous frame pointer, the constant pool reference). The JIT-compiled version replaces the operand stack with native CPU registers and spills locals to the native stack as needed, but the conceptual layout is the same. The number of frames the stack can hold is bounded by `-Xss` divided by the average frame size — a method with many locals and deep call chains can blow the stack at surprisingly shallow recursion depth (typically 5000–10000 frames on the default 1 MB stack, fewer with large local arrays).

```text
  Thread stack (1 MB default on Linux x86_64, -Xss512k to shrink)
  ┌──────────────────────────────────────┐  ← high address
  │  guard page (PROT_NONE, 4 KB–32 KB)  │     StackOverflowError trap
  ├──────────────────────────────────────┤
  │  yellow zone / red zone              │     safety margin
  ├──────────────────────────────────────┤  ← stack pointer (grows down)
  │  frame N   (method com.app.Bar)      │
  │   locals: this, x, y, tmp            │
  │   operand stack (or spilled regs)    │
  ├──────────────────────────────────────┤
  │  frame N-1 (method com.app.Foo)      │
  │   ...                                │
  ├──────────────────────────────────────┤
  │  frame 0   (main / Thread.run)       │
  └──────────────────────────────────────┘  ← low address
```

The production failure mode of thread stacks is **OOM: unable to create new native thread**. Each thread costs ~1 MB of reserved address space (not all committed — only the touched pages fault in) plus kernel bookkeeping (`task_struct` is ~10 KB). On a 4 GB container you can theoretically create ~4000 threads before hitting the cgroup limit; in practice you hit the `ulimit -u` (max user processes) limit or the kernel `vm.max_map_count` limit first. The diagnostic is `jstack <pid> | grep "java.lang.Thread.State" | wc -l` to count live threads — if it is in the thousands, you have a thread-pool leak (typically a `new Thread()` in a tight loop, or a `CompletableFuture.supplyAsync` without a bound on the executor). The fix is to cap executors (`Executors.newFixedThreadPool(N)` not `newCachedThreadPool()`) and switch to virtual threads (see [[04.01.05. Project Loom and Virtual Threads]]) for unbounded request-per-thread workloads.

### Native Memory allocations and Direct Byte Buffers (`Unsafe`, NIO direct memory)

Off-heap memory is the escape hatch the JVM gives to libraries that need to bypass the garbage collector. The two main paths are **`java.nio.ByteBuffer.allocateDirect`** (the supported API) and **`sun.misc.Unsafe.allocateMemory`** (the internal API that `DirectByteBuffer` calls under the hood and that Netty, Cassandra, and Lustre-style allocators use directly). Both end up calling the C library's `malloc` (or, for large allocations, `mmap` with `MAP_ANONYMOUS`), which is not under GC control. The JVM tracks the total direct memory allocated via a phantom-reference cleaner that frees the native buffer when the `ByteBuffer` object is garbage-collected — but the native allocation is **counted against `-XX:MaxDirectMemorySize`** (default: equal to `-Xmx`), not against the heap.

This is the trap. A Netty `PooledByteBufAllocator` that allocates 16 MB arena chunks off-heap will not show up in a `jmap -histo` heap histogram, but it will blow up the cgroup. The diagnostic is `jcmd <pid> VM.native_memory summary` (requires `-XX:NativeMemoryTracking=summary` at startup), which prints a category breakdown:

```text
-  Internal (reserved=1048656KB, committed=1048656KB)
    ...
-  Direct (reserved=1048576KB, committed=1048576KB)
    (malloc=1048576KB #1024)
```

The `Direct` line tells you how much direct buffer memory is currently outstanding. If it is approaching `-XX:MaxDirectMemorySize`, you have a `DirectByteBuffer` leak — typically a Netty pipeline that forgot to call `ReferenceCountUtil.release(buf)` or a NIO channel that did not register a `cleaner`. The fix is either to cap direct memory (`-XX:MaxDirectMemorySize=256m` so the JVM dies loudly with `OutOfMemoryError: Direct buffer memory` instead of silently taking the cgroup), or to enable Netty's leak detector (`-Dio.netty.leakDetection.level=PARANOID`) which prints the allocation stack trace when a buffer is GC'd without being released.

The other native-memory category that bites production is **the code cache** — the region where the JIT stores emitted machine code (see [[04.01.01. HotSpot Execution Engine and JIT Compilation]]). It is sized by `-XX:ReservedCodeCacheSize=240m` (default on JDK 17+) and when full the JIT silently stops compiling, which collapses throughput 5–10×. The diagnostic is `jcmd <pid> Compiler.codecache` and `jcmd <pid> Compiler.codelist | wc -l`. The fix is to either raise the limit, disable tiered compilation (`-XX:-TieredCompilation` so only C2 runs and uses less code-cache space, at the cost of slower startup), or trim the application's class count. The code-cache sweeper periodically reclaims `nmethod`s that have become zombies (deoptimised and no longer referenced), but it cannot keep up if the application loads and discards classes faster than it can sweep.

## Cross-Runtime Comparison

| Region | JVM (HotSpot) | Node.js (V8) | CPython | PHP (Zend) |
|---|---|---|---|---|
| Heap | Young (Eden+S0+S1) + Old | Young (semi-space) + Old + Large object | One heap, gen-0/1/2 for cyclic GC | Per-request heap (`emalloc`) |
| Class metadata | Metaspace (native) | ReadOnly + writable snapshots | Types in interp state | Per-request class table |
| Code cache | `-XX:ReservedCodeCacheSize` | V8 code range | None (no JIT, except for `_PyEval_EvalFrameDefault` itself) | OPcache shared memory |
| Direct buffers | `ByteBuffer.allocateDirect` | `Buffer.allocUnsafeSlow` (slab) | `mmap` via `mmap` module | Stream wrappers |
| Thread stacks | `-Xss` (1 MB default) | N/A (single thread) | 8 MB OS thread default (via `threading`) | Per-FPM-worker, 8 MB |
| Tracking tool | `jcmd VM.native_memory` | `--v8-pool-stats` / heap snapshot | `tracemalloc` | `memory_get_usage(true)` |

These differences are why the same algorithm performs differently in each runtime. When you read the anchor implementation in Spring Boot (JVM), keep in mind that the delta implementations in Node.js, Python, and PHP will exhibit different failure modes under load — only the JVM exposes all six regions independently and lets you OOM each one separately.
