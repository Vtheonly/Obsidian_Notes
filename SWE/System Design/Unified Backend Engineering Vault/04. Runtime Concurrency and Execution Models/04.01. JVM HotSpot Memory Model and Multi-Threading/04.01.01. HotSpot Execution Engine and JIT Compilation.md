# 04.01.01. HotSpot Execution Engine and JIT Compilation

## What This Is

**HotSpot Execution Engine and JIT Compilation** is the part of the JVM that turns `.class` bytecode into running machine code. The name "HotSpot" comes from the runtime's central trick: it does not compile everything ahead of time, it watches the running program for hot spots (methods and loops that execute often) and only spends compiler cycles on those. Everything else is interpreted. This trades a small steady-state interpretive cost for two big wins — fast startup (no global compile phase) and adaptive optimisation (the compiler sees real runtime data, including which call sites are monomorphic and which branches are taken). The HotSpot engine is the reason JVM services are slow for the first 30 seconds of life and then frequently beat equivalent C++ code on steady-state throughput.

This note sits between the OS kernel (section 02 — the JIT ultimately emits x86_64/arm64 machine code that the CPU executes via the same `mmap()`/`mprotect()` primitives any native binary uses) and the framework layer (section 05 — Spring AOT and GraalVM Native Image are direct reactions to the JIT's slow startup). Understanding tiered compilation, on-stack replacement, and deoptimisation is what separates "the JVM is magic" from "I can read `-XX:+PrintCompilation` and know exactly why my p99 jumped at 03:00 when the daily batch warmed a different code path."

## The Details

### JVM Execution Modes: Interpreted execution, C1 Tiered Compiler (Client, fast startup), C2 Server Compiler (Aggressive optimization).

HotSpot ships not one but three execution tiers, and the JVM transparently moves a method up the ladder as it gets hotter. The bottom rung is the **template interpreter** — a C++ `TemplateTable` that has one hand-written assembly snippet per bytecode opcode. The interpreter is fast for a bytecode machine (it does not decode opcode streams every time; instead each opcode is a labelled assembly stub that directly manipulates the JVM's stack frame), but it is still roughly 10–50× slower than native code. Its job is to execute cold code cheaply and to collect profiling counters: how many times each method was called, how many times each branch was taken, and which receiver types appeared at each virtual call site. Those counters are the input to the JIT.

The middle rung is **C1** (historically the "Client" compiler). C1 is fast to compile (a few milliseconds per method) and applies cheap, high-value optimisations: method inlining up to a small byte-size budget, devirtualisation of monomorphic call sites, null-check folding, and a limited form of escape analysis that can elide allocation of small short-lived objects. C1 was designed for desktop Java applets where startup latency mattered more than peak throughput. The top rung is **C2** (the "Server" compiler). C2 is slow to compile — tens to hundreds of milliseconds per method — but it builds a sea-of-nodes IR and performs aggressive optimisations that C1 cannot afford: loop unrolling, SIMD vectorisation, aggressive lock elision, and the famous "escape analysis" that can stack-allocate entire object graphs. C2 is what produces the machine code that lets steady-state Java match or beat C in microbenchmarks.

Tiered compilation (`-XX:+TieredCompilation`, on by default since JDK 8u40, mandatory since JDK 21) glues the three together. A method starts in the interpreter. At ~10 000 invocations (or fewer if a back-edge loop counter trips) it gets promoted to C1 with profiling instrumentation. At ~20 000 invocations the profile is harvested and the method is recompiled by C2 with the type-feedback inlined into the IR. The promotion thresholds are tunable: `-XX:CompileThreshold=10000` controls the C1 trigger, `-XX:Tier4InvocationThreshold=20000` controls C2. The full pipeline looks like this:

```text
  Java source
      │  javac (ahead-of-time, no optimisation)
      ▼
  Bytecode (.class in classpath / modulepath)
      │  ClassLoader.loadClass → Method::build_interpreter_method
      ▼
  ┌─────────────────────────────────────────────────┐
  │  Tier 0/3: Template Interpreter                │
  │  - Asm stubs per opcode, ~10–50× slower than C │
  │  - Counts invocations + back-edges             │
  │  - Records receiver types at call sites        │
  └─────────────────┬───────────────────────────────┘
                    │ CompileThreshold hit (10k)
                    ▼
  ┌─────────────────────────────────────────────────┐
  │  Tier 1/4: C1 ("Client") compiler              │
  │  - Compile time ~5 ms/method                   │
  │  - Inline small methods, devirtualise, fold    │
  │  - Still carries profiling instrumentation     │
  └─────────────────┬───────────────────────────────┘
                    │ Tier4InvocationThreshold hit (20k)
                    ▼
  ┌─────────────────────────────────────────────────┐
  │  Tier 2/5: C2 ("Server") compiler              │
  │  - Sea-of-nodes IR, ~100 ms/method             │
  │  - Loop unroll, SIMD, escape analysis,         │
  │    aggressive lock elision                     │
  │  - Profile data stripped, max performance      │
  └─────────────────────────────────────────────────┘
```

You can watch the promotions happen live with `-XX:+PrintCompilation` (or, on JDK 9+, the unified `-Xlog:jit+compilation=info`). A typical log line looks like:

```text
  124   3 % b   com.example.Order::price @ 7 (29 bytes)
  125   3       com.example.Order::price (29 bytes)
  126   4       com.example.Order::price (29 bytes)
  127   3 %     com.example.Order::price @ 7 (29 bytes)   made not entrant
```

The columns are: timestamp in milliseconds since JVM start, compile ID, compilation level (3 = C1, 4 = C2, `%` = OSR), the method name and bytecode offset, and lifecycle events like `made not entrant` (deoptimisation). The `%` lines are on-stack replacement — the JVM recompiled a hot loop while it was still running. The "made not entrant" line is the inverse: an assumption failed and the old compiled code was invalidated. When you see a flood of "made not entrant" lines after a deployment, you are watching the JVM throw away C2 code and re-warm — this is what produces the p99 spike on a fresh pod for the first 60 seconds.

### JIT Optimization techniques: Method inlining, loop unrolling, dead code elimination, and Escape Analysis (allocating objects on stack)

The four optimisations named in this heading are the ones that produce the dramatic speed gap between interpreted bytecode and C2-compiled machine code. **Method inlining** is the single most valuable: instead of emitting a `call` instruction, C2 copies the body of the callee directly into the caller, removing call overhead and — crucially — exposing the combined code to every other optimisation. Inlining is gated by `-XX:MaxInlineSize=35` (bytecode size of methods that are always inlined) and `-XX:FreqInlineSize=325` (methods inlined only when hot). Without inlining, every other optimisation is crippled because it can only see one method at a time. This is why the JVM treats `final` methods, `final` classes, and devirtualised monomorphic call sites as gold — they let the compiler prove the inlining is safe.

**Loop unrolling** replicates the body of a loop two, four, or eight times so the CPU pipeline can fill and the loop overhead (counter increment, branch test) is amortised. Combined with SIMD vectorisation (`-XX:+UseSuperWord`, on by default), C2 can transform a scalar `for (int i = 0; i < 1024; i++) a[i] += b[i]` into AVX2 `vaddps` instructions that process 8 ints per cycle. **Dead code elimination** strips unreachable branches — once profiling says the `if (rareError)` branch was never taken in 20 000 invocations, C2 compiles the method as if the branch did not exist (it leaves an uncommon trap that deoptimises if the rare branch ever does fire). This is the same trick profile-guided optimisation uses in C++ (`-fprofile-generate`), except the JVM does it transparently at runtime.

**Escape analysis** (`-XX:+DoEscapeAnalysis`, on by default) is the trick that lets Java avoid heap allocation for short-lived objects. C2 walks the IR of a method and asks: does this object escape the method? If it is only passed to other methods that also do not let it escape, and it is not stored into a heap field or static, the object can be **scalar replaced** — its fields are treated as local variables and placed in CPU registers, with no allocation at all. The classic beneficiary is the `StringBuilder` that `+` string concatenation generates: pre-Java-9 it would always allocate a `StringBuilder` on the heap; with escape analysis the allocation disappears entirely. You can verify with `-XX:+PrintEscapeAnalysis`:

```text
  Hotness:
   71   4       java.lang.String::concat (15 bytes)
                      @ 9   java.lang.StringBuilder::<init> (7 bytes)   scalar replaced
                      @ 17  java.lang.StringBuilder::append (8 bytes)   inline
```

The failure mode of these optimisations is that they are speculative. If the assumption breaks — a "monomorphic" call site becomes polymorphic when a new subclass is loaded, a "never taken" branch suddenly fires — the JVM must **deoptimise**: discard the C2 code, fall back to the interpreter, recompile with the new information. A short burst of deoptimisations looks like latency spikes on the affected endpoints; a long burst (e.g., after loading a plugin that polymorphises every call site) can cut steady-state throughput in half. The diagnostic is `-XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining` to see which call sites failed to inline, and async-profiler with `--event=deopt` to count deoptimisation events per second.

### On-Stack Replacement (OSR) and Deoptimization mechanics

On-stack replacement is the mechanism that lets the JVM replace the code currently executing a method without waiting for the method to return. Without OSR, a long-running loop in the interpreter would stay interpreted forever, because the promotion trigger only fires on method entry. OSR solves this: when a back-edge counter (a counter on a loop branch) trips its threshold, the JVM pauses the loop, recompiles the method (or just the loop body) at the requested tier, copies the interpreter's stack frame into a compiled frame, and resumes execution inside the compiled code. The `%` marker in the `-XX:+PrintCompilation` log marks an OSR compilation. The compilation ID has the form `com.example.Foo::bar @ 17 (45 bytes)` where `@ 17` is the bytecode offset of the back-edge — the OSR entry point — not the method entry. The compiled code can only be entered at that exact bytecode index, which is why OSR-compiled code is sometimes less optimised than regular C2 code: the compiler cannot assume anything about the local variable state at the OSR point, so it must be conservative about which locals are alive.

Deoptimisation is the reverse operation, and it is the price the JVM pays for speculating. There are two flavours. **Uncommon trap deoptimisation** fires when a speculative guard fails — for example, the JIT assumed a call site was monomorphic and inlined `SubclassA.foo()`, but at runtime a `SubclassB` shows up. The compiled code contains a guard check (`if (klass != SubclassA) goto uncommon_trap`) and when it fires the JVM walks the compiled frame, reconstructs the interpreter frame from the deoptimisation metadata (the "scope" records stored alongside each compiled method), and resumes in the interpreter. **Class-loading deoptimisation** fires when a new class is loaded that invalidates a hierarchy assumption — for example, the JIT assumed `interface Foo` had one implementor and inlined it; loading a second implementor forces every compiled method that made that assumption to be marked `made not entrant` and recompiled lazily on next call.

The lifecycle of compiled code is tracked by the **method's `nmethod`** (the native method structure in `codeCache`). Each `nmethod` has a state: `in_use`, `made_not_entrant`, `made_not_zombie`, `zombie`. When deoptimisation hits, the `nmethod` moves to `made_not_entrant` — existing callers finish, but new entries go to the interpreter or to a fresh compilation. Once the last active frame unwinds, the `nmethod` becomes a `zombie` and its memory is reclaimed by the code-cache sweeper. You can watch this in `-Xlog:nmethod`:

```text
[0.234s][info][nmethod]  87   4 %  b  com.app.Heavy::loop @ 18 (62 bytes)
[0.891s][info][nmethod]  87   4 %     com.app.Heavy::loop @ 18 (62 bytes)   made not entrant
[0.905s][info][nmethod]  87   4 %     com.app.Heavy::loop @ 18 (62 bytes)   made zombie
```

The production failure mode is "deoptimisation storms." A classic trigger is a framework that reflectively loads many subclasses of a hot interface at startup — for the first 30 seconds every load invalidates previously compiled code and the service is back in the interpreter. The diagnostic is `-XX:+TraceDeoptimization` (or async-profiler `--event=deopt`) plus `jcmd <pid> Compiler.codecache` to check whether the code cache is filling up (`-XX:ReservedCodeCacheSize=256m` is the default on 64-bit; if it is full the JIT silently stops compiling and throughput collapses 5–10×).

## Cross-Runtime Comparison

| Aspect | JVM (HotSpot) | Node.js (V8) | CPython | PHP (Zend) |
|---|---|---|---|---|
| Interpreter | Template interpreter (asm stubs) | Ignition (register bytecode) | `ceval.c` switch loop | Zend VM (call-symbolic) |
| Baseline JIT | C1 (Client) | Sparkplug | — | — |
| Optimising JIT | C2 (Server, sea-of-nodes) | TurboFan (+ Maglev mid-tier) | — | — |
| Profile-guided | Counters + type profile | Inline caches + feedback vector | — | — |
| OSR | Yes (`%` in PrintCompilation) | Yes (tier-up inside loops) | — | — |
| Deoptimisation | Uncommon traps + class loading | Lazy deopt + eager deopt | — | — |
| Steady-state perf | 0.8–1.2× equivalent C++ | 0.7–1.0× equivalent C++ | 20–80× slower than C++ | 5–15× slower than C++ |

These differences are why the same algorithm performs differently in each runtime. When you read the anchor implementation in Spring Boot (JVM), keep in mind that the delta implementations in Node.js, Python, and PHP will exhibit different failure modes under load — and only the JVM and V8 have the JIT firepower to hide the cost of dynamic dispatch.
