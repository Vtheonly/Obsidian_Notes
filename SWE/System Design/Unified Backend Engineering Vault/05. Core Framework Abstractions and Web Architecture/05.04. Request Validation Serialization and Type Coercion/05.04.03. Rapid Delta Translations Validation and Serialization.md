# 05.04.03. Rapid Delta Translations Validation and Serialization

## What This Note Is

This is a **delta translation note**. It is intentionally short. Read it **after** completing the anchor implementation in the sibling Spring Boot note. The point is to answer one question:

> What is different in this ecosystem, and what is automatic that I had to do manually in the anchor?

If you find yourself re-learning the concept here, you have not finished the anchor. Go back.

## Implementation Deltas

The deltas to internalize:

- *TypeScript / Node.js*: Schema-first validation using Zod, Class-Validator with decorators, and parsing raw JSON into typed TypeScript types.
- *Python / Django & Flask*: Django REST Framework Serializers/ModelSerializers, Pydantic BaseModels in FastAPI/Flask, Marshmallow schemas.
- *PHP / Laravel*: Form Requests (`FormRequest`), the Validator facade, custom validation rules, and automatic validation redirect/JSON response formatting.

## The Details

### *TypeScript / Node.js*: Schema-first validation using Zod, Class-Validator with decorators, and parsing raw JSON into typed TypeScript types

TypeScript's runtime type system is erased — at runtime, a `UserDto` interface is gone, and `req.body` is `any`. To validate at runtime you need a schema library that captures the shape and the constraints. Zod is the dominant choice: it is structural (the schema IS the type), it composes (`.extend()`, `.pick()`, `.omit()`), and it produces TypeScript types via `z.infer<typeof Schema>` so the validated value is statically typed.

```typescript
// src/users/dto.ts
import { z } from "zod";

// Schema-first — the schema defines both the runtime validation and the TS type
export const CreateUserRequest = z.object({
    email: z.string().email("must be a well-formed email address"),
    password: z.string()
        .min(8, "size must be between 8 and 64")
        .max(64, "size must be between 8 and 64")
        .regex(/[A-Z]/, "must contain an uppercase letter")
        .regex(/[a-z]/, "must contain a lowercase letter")
        .regex(/\d/, "must contain a digit")
        .regex(/[^A-Za-z0-9]/, "must contain a symbol"),
    passwordConfirmation: z.string(),
    displayName: z.string().regex(/^[a-zA-Z]+$/),
    age: z.number().int().min(13).max(120),
    addresses: z.array(z.object({
        street: z.string().min(1),
        city: z.string().min(1),
        country: z.string().regex(/^[A-Z]{2}$/),
    })).max(3),
}).refine(d => d.password === d.passwordConfirmation, {
    message: "passwords must match",
    path: ["passwordConfirmation"],   // ← attaches the error to this field
});

export type CreateUserRequest = z.infer<typeof CreateUserRequest>;   // TS type derived from schema

// src/users/controller.ts
import { Router, Request, Response } from "express";
import { CreateUserRequest } from "./dto";

const router = Router();

router.post("/users", (req: Request, res: Response) => {
    const result = CreateUserRequest.safeParse(req.body);
    if (!result.success) {
        return res.status(400).json({
            type: "https://example.com/errors/validation",
            title: "Bad Request",
            status: 400,
            detail: "Validation failed for the request body",
            trace_id: (req as any).traceId,
            errors: result.error.issues.map(i => ({
                field: i.path.join("."),
                message: i.message,
                rejected: i.code === "invalid_type" ? "null" : undefined,
            })),
        });
    }
    const dto: CreateUserRequest = result.data;   // typed, validated
    const user = userService.create(dto);
    res.status(201).json({
        id: user.id,
        email: user.email,
        displayName: user.displayName,
        created_at: user.createdAt.toISOString(),
    });
});

export default router;
```

What is automatic here that was manual in the anchor: the schema IS the type — `z.infer<typeof CreateUserRequest>` derives the TypeScript type from the schema, so there is one source of truth (no separate Java class and `@NotNull` annotation to keep in sync). The `safeParse` API returns a discriminated union `{success: true, data} | {success: false, error}` — the type system forces you to handle both cases. `.refine()` lets you add cross-field constraints (password === passwordConfirmation) and attach the error to a specific field via `path`.

What is manual here that was automatic in the anchor: there is no `@Valid` annotation — you must call `schema.safeParse(req.body)` in every handler (or write a `validate(schema)` middleware factory to wrap it). There is no Jackson — `JSON.parse` is the default, and it does not coerce types (`"42"` stays a string). There is no `ObjectMapper` configuration — `Date` objects are serialised via `JSON.stringify`'s default `toISOString()`. There is no built-in RFC 7807 ProblemDetail — you construct the error shape by hand.

The runtime invariant exposed differently: Node's `JSON.parse` is implemented in V8 native code and is roughly 10x faster than Jackson for typical payloads (no reflection, no `BeanDeserializer` factory). The cost is paid in developer ergonomics — there is no `BeanDeserializer` to walk the type graph; you must declare every field in the schema explicitly.

### *Python / Django & Flask*: Django REST Framework Serializers/ModelSerializers, Pydantic BaseModels in FastAPI/Flask, Marshmallow schemas

Python has three dominant validation libraries, each tied to a different framework. Django REST Framework (DRF) ships `Serializer` and `ModelSerializer` — the DRF equivalent of Bean Validation + Jackson in one class. Flask has no built-in; `marshmallow` is the traditional choice, `pydantic` is the modern choice (especially with FastAPI).

```python
# Django REST Framework — serializer with field-level validation
# myapp/serializers.py
from rest_framework import serializers
from .models import User

class AddressSerializer(serializers.Serializer):
    street  = serializers.CharField(max_length=200)
    city    = serializers.CharField(max_length=100)
    country = serializers.CharField(max_length=2)   # ISO 3166-1 alpha-2

    def validate_country(self, value):
        if not value.isupper() or len(value) != 2:
            raise serializers.ValidationError("must be a 2-letter ISO country code")
        return value

class CreateUserSerializer(serializers.Serializer):
    email       = serializers.EmailField()
    password    = serializers.CharField(min_length=8, max_length=64)
    passwordConfirmation = serializers.CharField()
    displayName = serializers.CharField(max_length=100)
    age         = serializers.IntegerField(min_value=13, max_value=120)
    addresses   = AddressSerializer(many=True)   # ← cascades into AddressSerializer

    # Object-level validation — runs after all field-level validators
    def validate(self, attrs):
        if attrs["password"] != attrs["passwordConfirmation"]:
            raise serializers.ValidationError(
                {"passwordConfirmation": "passwords must match"})
        return attrs

    def create(self, validated_data):
        # Called by .save() — translates DTO → model and persists
        return User.objects.create_user(
            email=validated_data["email"],
            password=validated_data["password"],
            display_name=validated_data["displayName"],
            age=validated_data["age"],
        )

# myapp/views.py
from rest_framework.views import APIView
from rest_framework.response import Response
from rest_framework import status
from .serializers import CreateUserSerializer, UserSerializer

class UserList(APIView):
    def post(self, request):
        serializer = CreateUserSerializer(data=request.data)
        serializer.is_valid(raise_exception=True)   # → 400 with {email: ["message"]} on failure
        user = serializer.save()
        return Response(UserSerializer(user).data, status=status.HTTP_201_CREATED)

# DRF's default exception handler renders ValidationError as:
# 400 Bad Request
# {"email": ["This field is required."],
#  "password": ["Ensure this field has at least 8 characters."]}
```

```python
# Flask with Pydantic — modern, FastAPI-compatible
from flask import Flask, request, jsonify
from pydantic import BaseModel, EmailStr, Field, field_validator, model_validator
from typing import List
from datetime import date

app = Flask(__name__)

class Address(BaseModel):
    street: str = Field(min_length=1)
    city: str = Field(min_length=1)
    country: str = Field(pattern=r"^[A-Z]{2}$")

class CreateUserRequest(BaseModel):
    email: EmailStr
    password: str = Field(min_length=8, max_length=64, pattern=r".*[A-Z].*[a-z].*\d.*[^A-Za-z0-9].*")
    password_confirmation: str
    display_name: str = Field(pattern=r"^[a-zA-Z]+$")
    age: int = Field(ge=13, le=120)
    addresses: List[Address] = Field(max_length=3)

    @model_validator(mode="after")
    def passwords_match(self):
        if self.password != self.password_confirmation:
            raise ValueError("passwords must match")
        return self

@app.post("/users")
def create_user():
    try:
        dto = CreateUserRequest.model_validate(request.get_json())
    except Exception as err:   # ValidationError
        return jsonify({
            "type": "https://example.com/errors/validation",
            "title": "Bad Request",
            "status": 400,
            "errors": [{"field": ".".join(str(p) for p in e["loc"]),
                        "message": e["msg"]} for e in err.errors()],
        }), 400
    user = user_service.create(dto)
    return jsonify({"id": str(user.id), "email": user.email,
                    "display_name": user.display_name,
                    "created_at": user.created_at.isoformat()}), 201
```

What is automatic here that was manual in the anchor: DRF's `ModelSerializer` can auto-generate fields from a Django model — `class UserSerializer(serializers.ModelSerializer): class Meta: model = User; fields = ["email", "display_name", "age"]` produces a serializer with the right field types and constraints by reflecting on the model. Pydantic's `BaseModel` derives JSON schema automatically (`CreateUserRequest.model_json_schema()`), which can be exposed at `/openapi.json` for client codegen. The `@model_validator(mode="after")` decorator is the Pydantic equivalent of a class-level `@AssertTrue` constraint.

What is manual here that was automatic in the anchor: DRF's default error shape is `{field: [messages]}` — not RFC 7807. You must write a custom `exception_handler` to wrap it in `ProblemDetail` shape. Pydantic's `model_validate` raises `ValidationError` — you must catch it and render the response yourself (Flask has no equivalent of Spring's `@ControllerAdvice`; use `@app.errorhandler(ValidationError)`). Neither DRF nor Pydantic has `@JsonIgnore` — you must declare a separate response serializer/model.

The runtime invariant exposed differently: CPython's `model_validate` is ~10x slower than Jackson for the same payload because it does not have a JIT-optimised reflection layer — each field is a `getattr`/`setattr` call through `__init_subclass__`. Pydantic V2 (which uses a Rust core) closes most of this gap, but it is still slower than Jackson. Under gunicorn+gevent this is rarely the bottleneck (the GIL serialises anyway), but it shows up in flame graphs on CPU-bound endpoints.

### *PHP / Laravel*: Form Requests (`FormRequest`), the Validator facade, custom validation rules, and automatic validation redirect/JSON response formatting

Laravel's FormRequest is the closest thing to Spring's `@Valid @RequestBody` outside the JVM. A FormRequest is a class that declares `rules()` (returns an array of field → constraint strings) and is type-hinted on a controller method. Laravel's service container resolves it, runs the validator before the controller method is invoked, and on failure either redirects back (for web) or returns 422 JSON (for API) — automatically.

```php
<?php
// app/Http/Requests/CreateUserRequest.php
namespace App\Http\Requests;

use Illuminate\Foundation\Http\FormRequest;
use Illuminate\Validation\Rule;

class CreateUserRequest extends FormRequest
{
    public function authorize(): bool
    {
        // Authorization check — return false → 403 Forbidden
        return $this->user()?->can("create", User::class);
    }

    public function rules(): array
    {
        return [
            "email"                => ["required", "email", "max:254"],
            "password"             => ["required", "string", "min:8", "max:64",
                                       "regex:/[A-Z]/", "regex:/[a-z]/",
                                       "regex:/\d/", "regex:/[^A-Za-z0-9]/"],
            "password_confirmation"=> ["required", "same:password"],
            "display_name"         => ["required", "string", "regex:/^[a-zA-Z]+$/"],
            "age"                  => ["required", "integer", "between:13,120"],
            "addresses"            => ["array", "max:3"],
            "addresses.*.street"   => ["required", "string"],
            "addresses.*.city"     => ["required", "string"],
            "addresses.*.country"  => ["required", "string", "size:2", "regex:/^[A-Z]{2}$/"],
        ];
    }

    public function messages(): array
    {
        return [
            "email.required" => "email is required",
            "email.email"    => "email must be a well-formed email address",
            "password.regex" => "password must contain upper, lower, digit, and symbol",
            "password_confirmation.same" => "passwords must match",
        ];
    }

    // Custom rule object — encapsulates reusable constraint logic
    public function withValidator($validator): void
    {
        $validator->after(function ($validator) {
            if (User::where("email", $this->email)->exists()) {
                $validator->errors()->add("email", "email is already registered");
                // Note: this is a DB call inside validation — see anti-pattern below.
            }
        });
    }
}

// app/Http/Controllers/UserController.php
class UserController extends Controller {
    public function store(CreateUserRequest $req) {
        // If we reach here, validation has passed. $req->validated() returns
        // only the fields declared in rules(), preventing mass assignment.
        $user = User::create($req->validated());
        return response()->json([
            "id" => $user->id,
            "email" => $user->email,
            "display_name" => $user->display_name,
            "created_at" => $user->created_at->toISOString(),
        ], 201);
    }
}

// On validation failure, Laravel's exception handler automatically returns:
// 422 Unprocessable Entity
// {
//   "message": "The email field is required. (and 3 more errors)",
//   "errors": {
//     "email": ["email is required"],
//     "password": ["password must contain upper, lower, digit, and symbol"],
//     "password_confirmation": ["passwords must match"],
//     "age": ["The age must be between 13 and 120."]
//   }
// }

// Inline validation (without a FormRequest) — for simple cases
public function quickStore(Request $req) {
    $data = $req->validate([
        "email" => "required|email",
        "name"  => "required|string|max:100",
    ]);
    return User::create($data);
}
```

What is automatic here that was manual in the anchor: the FormRequest is resolved by the container before the controller method runs, so validation is automatic — no `@Valid` annotation needed. The error response is automatic — Laravel's `ValidationException` is rendered as 422 JSON by the framework's exception handler, no `@ControllerAdvice` needed. The `$req->validated()` method returns only the declared fields, preventing mass assignment by default. The `addresses.*.street` wildcard syntax is more concise than Java's nested `@Valid List<AddressDto>`.

What is manual here that was automatic in the anchor: there is no Jackson — `json_decode` is the default, and it does not coerce types (`"42"` stays a string unless you cast). Custom rule objects require a separate class (`Rule::class` implementing `passes` and `message`), which is more boilerplate than Java's `@Constraint(validatedBy = ...)`. The `withValidator` hook for cross-field validation is awkward compared to Pydantic's `@model_validator`.

The runtime invariant exposed differently: PHP-FPM's per-request process model means the validator is constructed fresh on every request — there is no validator cache. Under Laravel Octane (long-lived PHP), the validator is cached and reused, which is closer to Hibernate Validator's behaviour. The `withValidator` DB call anti-pattern is particularly costly under Octane because it runs synchronously on the event loop thread, blocking every other request.

## How This Connects to the Frameworks

Every framework in section 05 implements validation as a layer between the HTTP parser and the route handler. The shape is identical: parse JSON → coerce types → validate structural constraints → check business rules → invoke handler. The differences are in ergonomics (declarative vs imperative), in the error shape (RFC 7807 vs ad-hoc), and in where business rules run (validator vs service). When a 400 error surfaces, knowing which layer produced it tells you where to look: a parse error is in the JSON library, a structural error is in the validator, a business error is in the service.

## Hands-On Exercise

```bash
# Send a valid request to each ecosystem and observe the 201 response
curl -X POST http://localhost:8080/api/users -H "Content-Type: application/json" \
  -d '{"email":"alice@example.com","password":"Correct$Horse123","passwordConfirmation":"Correct$Horse123","displayName":"Alice","age":34,"addresses":[{"street":"1 Main","city":"NYC","country":"US"}]}'

# Send an invalid request and observe the 400 error shape — compare across ecosystems
curl -X POST http://localhost:8080/api/users -H "Content-Type: application/json" \
  -d '{"email":"not-an-email","password":"short","age":200}'

# Try the mass-assignment attack — should be rejected
curl -X POST http://localhost:8080/api/users -H "Content-Type: application/json" \
  -d '{"email":"x@x.com","password":"Password123$","passwordConfirmation":"Password123$","displayName":"x","age":20,"role":"ADMIN"}'
# Spring: 400 (FAIL_ON_UNKNOWN_PROPERTIES)
# Express with Zod: passes — Zod strips unknown fields by default unless .strict()
# Django with DRF: 400 (Serializer does not declare 'role')
# Laravel with FormRequest: passes — $req->validated() strips undeclared fields
```
