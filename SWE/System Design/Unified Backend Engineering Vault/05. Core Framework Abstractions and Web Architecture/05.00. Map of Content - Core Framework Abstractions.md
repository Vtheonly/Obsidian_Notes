# 05.00. Map of Content: Core Framework Abstractions

## Overview

Section 05 is the layer where the raw materials of the lower sections — POSIX sockets from section 02, TCP/HTTP from section 03, and the JVM/V8/CPython runtimes from section 04 — are shaped into the recurring architectural primitives that every backend engineer reaches for: routing, middleware, dependency injection, validation, exception boundaries, authentication, and authorization. None of these primitives exist in the kernel; they are all invented by frameworks. But every framework invents them in roughly the same shape, because they all solve the same problem: turning a raw HTTP byte stream into a typed, validated, authenticated, authorized call on a domain object, and turning the result back into an HTTP response.

The pedagogical thesis of this section is that the abstraction layer between "TCP socket accepted" and "your `createOrder` method returns" is identical across Spring Boot, Express, Django, Flask, and Laravel. What differs is the syntax, the defaults, and the runtime invariants each framework exposes. The Spring Boot anchor notes teach the concepts deeply with strict types, multi-threaded servlet containers, and reflection-driven proxies; the delta notes teach the same concepts in the simpler runtimes (Node's event loop, Python's GIL, PHP's shared-nothing process model) so that the reader sees the universal problem underneath the ecosystem-specific solution.

Reading order matters. The seven sub-sections form a pipeline that mirrors the actual lifecycle of an HTTP request: the request hits the routing engine (05.01), traverses the middleware pipeline (05.02), the handler is resolved through the IoC container (05.03), its arguments are coerced and validated (05.04), any thrown exception is caught at a boundary (05.05), the caller's identity is established (05.06), and finally the caller's authority over the resource is enforced (05.07). Skip ahead and you will not understand why a `@PreAuthorize` annotation on a controller method runs *after* the request body has been deserialized and *before* the service method is invoked.

## How to Read This Section

1. **Read the concept notes first.** They establish the mental model. Without the concept, the anchor is just syntax.
2. **Implement the anchor.** The Spring Boot anchor note is where you build the real, load-tested implementation. Do not skim — type it out, run it, hit it with `wrk` or `k6`, and reproduce the failure modes in the Break It section.
3. **Run the delta pass.** Open each ecosystem's delta note and implement the same feature as a translation exercise. The goal is not to relearn the concept but to internalize what changes when the runtime changes.
4. **Connect.** Follow the Related Notes links to reinforce the cross-ecosystem graph. Every framework note links down to the runtime and networking layers it sits on.

> [!tip] Reading order
> If you are new to this section, follow the numeric ordering 05.01 → 05.07 — that order mirrors the lifecycle of an HTTP request. If you are revising, jump directly to whichever concept you forgot; each note is self-contained.

## Conceptual Roadmap

The seven sub-sections form a layered pipeline. Read them as the journey of one HTTP request:

```text
  TCP SYN → [kernel accept queue]                       ← section 02
         → [HTTP parser, TLS termination]               ← section 03
         → [Routing engine: which handler?]             ← 05.01
         → [Middleware pipeline: auth, CORS, tracing]   ← 05.02
         → [IoC container: resolve handler + deps]      ← 05.03
         → [Validation: deserialize + validate body]    ← 05.04
         → [Handler runs, throws or returns]            ← your code
         → [Exception boundary: catch + map to HTTP]    ← 05.05
         → [AuthN: who is the caller?]                  ← 05.06
         → [AuthZ: are they allowed to do this?]        ← 05.07
         → [Serialize response, write to socket]        ← sections 03 + 04
```

05.06 (authentication) and 05.07 (authorization) are listed last because in most production stacks the auth *filter* runs early in the middleware pipeline (05.02), but the *concept* of authentication (proving who you are) only makes sense after you understand the request lifecycle, the IoC container that holds the `UserDetailsService`, and the exception boundary that maps an `AuthenticationException` to a 401. By the time you reach 05.07, every primitive you need — routing, middleware, DI, validation, exception handling, authentication — is already loaded into your mental cache, and authorization becomes a natural capstone.
