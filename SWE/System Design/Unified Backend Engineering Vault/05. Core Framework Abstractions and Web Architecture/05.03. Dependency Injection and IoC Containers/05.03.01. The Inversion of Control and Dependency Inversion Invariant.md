# 05.03.01. The Inversion of Control and Dependency Inversion Invariant

## What This Is

Dependency Injection is the practice of giving a class its collaborators from the outside rather than letting it construct them itself. The Inversion of Control container is the registry that knows how to construct every collaborator, recursively resolve their dependencies, and hand back a fully-wired instance. Without DI, every class reaches out into the world to grab what it needs (`new PostgresRepo()`, `RedisClient.getClient()`); with DI, every class declares what it needs (`OrderService(OrderRepository repo)`) and trusts the container to provide it.

This note teaches the universal concept: the Dependency Inversion Principle (SOLID's D), constructor vs setter vs field injection trade-offs, the container lifecycle, scopes, and circular-dependency detection. The anchor note (05.03.02) shows Spring Boot's `ApplicationContext`, stereotype annotations, `@Bean` configuration, and CGLIB proxying for `@Transactional`; the delta note (05.03.03) shows the same concept in Express, Django, Flask, and Laravel.

## The Details

### Decoupling high-level business policies from low-level infrastructure implementations

The Dependency Inversion Principle (the D in SOLID) states two things: (1) high-level modules should not depend on low-level modules; both should depend on abstractions; (2) abstractions should not depend on details; details should depend on abstractions. In a backend application, the "high-level module" is your domain service (`OrderService.placeOrder`), the "low-level module" is your infrastructure adapter (`PostgresOrderRepository`), and the "abstraction" is the `OrderRepository` interface. The service depends on the interface; the Postgres adapter implements the interface; the DI container wires them together at startup.

The motivation is change isolation. If `OrderService` directly calls `new PostgresOrderRepository()`, then changing the database from Postgres to DynamoDB requires editing `OrderService` — and `OrderService` is supposed to be the stable business-policy layer. If `OrderService` instead depends on the `OrderRepository` interface, you swap the implementation by changing one line in the container configuration (`bind(OrderRepository.class).to(DynamoOrderRepository.class)`) and `OrderService` is untouched. This is the same reason your router depends on the `HttpServletRequest` interface rather than on Tomcat's `CoyoteRequest` concrete class — you can swap Tomcat for Jetty or Undertow without touching application code.

```java
// BAD — class creates its own dependency (tight coupling)
class OrderService {
    private final PostgresRepo repo = new PostgresRepo();  // hard-coded
}

// GOOD — dependency is injected (loose coupling)
class OrderService {
    private final OrderRepository repo;  // interface, not concrete class
    OrderService(OrderRepository repo) { this.repo = repo; }  // injected
}
```

The IoC container is the registry that knows how to construct every dependency. When you ask it for an `OrderService`, it (1) looks up the constructor parameters (`OrderRepository`), (2) recursively resolves each parameter — for `OrderRepository` it looks up how to construct an implementation, which might need a `DataSource`, which needs connection-pool config, and so on — (3) constructs the leaf dependencies first, then works upward, (4) returns the fully-wired `OrderService`. The construction graph is a directed acyclic graph (DAG); the container walks it in topological order so each dependency is constructed exactly once (for singleton scope) before its dependents.

```text
  Dependency graph (DAG):

  OrderService ──requires──→ OrderRepository (interface)
                                    │
                                    ↓ bound to
                          PostgresOrderRepository
                                    │
                                    ↓ requires
                                DataSource
                                    │
                                    ↓ requires
                            HikariConfig (url, user, password)

  Container walks the DAG from leaves to root:
    1. Construct HikariConfig (from application.yml)
    2. Construct DataSource (HikariDataSource wrapping HikariConfig)
    3. Construct PostgresOrderRepository (with DataSource)
    4. Construct OrderService (with PostgresOrderRepository)

  Each singleton is constructed exactly once and cached by the container.
  Subsequent .getInstance(OrderService.class) returns the cached instance.
```

The production failure mode of tight coupling is the "untestable service" — `OrderService` with `new PostgresRepo()` cannot be unit-tested without a real Postgres running. The test must either spin up a Postgres container (slow, 30s+ per test) or use a mocking framework to stub the `new` call (which Java makes difficult without PowerMock). With DI, the test constructs `OrderService(mockOrderRepository)` directly and verifies behaviour in microseconds. The cost of skipping DI is paid every time you run the test suite.

### Injection strategies: Constructor Injection (immutability, testability) vs. Setter Injection vs. Field/Property Injection

There are three places a dependency can be handed to a class: the constructor, a setter method, or directly into a field. Each has trade-offs that show up in testability, immutability, and the order in which the container can wire things.

**Constructor injection** is the recommended strategy in Spring and in modern .NET. The class declares every collaborator as a constructor parameter; the container invokes the constructor reflectively with the resolved dependencies. The resulting fields can be `final` (immutable), which means the class is thread-safe by construction — no race can ever observe a half-constructed service. The class also cannot be instantiated without its dependencies, which prevents the "I forgot to set the repo" bug at runtime. Spring 4.3+ does not even require `@Autowired` on a single-constructor class — the constructor is implicitly the injection point.

**Setter injection** (e.g., `@Autowired public void setRepo(OrderRepository repo)`) is used for optional dependencies and for breaking circular dependencies. The class can be constructed without its dependencies, then have them set later. The fields cannot be `final`; the class is mutable; and you must guard against `repo == null` in every method. Spring's documentation recommends setter injection only for optional dependencies that have sensible defaults.

**Field injection** (`@Autowired private OrderRepository repo;` directly on the field) is the most concise but the most harmful. Spring uses reflection to set the field after construction, which means (a) the field cannot be `final`, (b) the class can be constructed in a half-wired state, (c) unit tests cannot inject a mock without reflection (`ReflectionTestUtils.setField`), and (d) the dependency graph is invisible from the constructor signature. Spring Framework 6 / Spring Boot 3 deprecates `@Autowired` field injection in favour of constructor injection; the IntelliJ inspection `Field injection is not recommended` flags it.

```java
// Constructor injection — recommended
@Service
class OrderService {
    private final OrderRepository repo;     // final → immutable
    private final PaymentGateway pay;       // final → immutable

    public OrderService(OrderRepository repo, PaymentGateway pay) {
        this.repo = repo;
        this.pay = pay;
    }
}

// Setter injection — for optional dependencies
@Service
class OrderService {
    private OrderRepository repo;
    private MetricsClient metrics;   // optional — may be null

    @Autowired
    public void setRepo(OrderRepository repo) { this.repo = repo; }

    @Autowired(required = false)
    public void setMetrics(MetricsClient metrics) { this.metrics = metrics; }
}

// Field injection — concise but discouraged
@Service
class OrderService {
    @Autowired private OrderRepository repo;     // not final, reflection-set
    @Autowired private PaymentGateway pay;       // not final, reflection-set
}
```

```text
  Injection strategy comparison:

  ┌──────────────────┬─────────────┬─────────────┬─────────────┐
  │ Property          │ Constructor │ Setter      │ Field       │
  ├──────────────────┼─────────────┼─────────────┼─────────────┤
  │ Immutability      │ Yes (final) │ No          │ No          │
  │ Required deps OK  │ Yes         │ Awkward     │ Yes         │
  │ Optional deps OK  │ No          │ Yes         │ Yes         │
  │ Testable w/o cont │ Yes (new)   │ Yes (set)   │ No (reflect)│
  │ Cycles breakable  │ No          │ Yes         │ Yes         │
  │ Spring default    │ Yes (>= 4.3)│ No          │ No          │
  │ Recommended       │ ✓           │ for optional│ deprecated  │
  └──────────────────┴─────────────┴─────────────┴─────────────┘
```

The production failure mode of field injection is the untestable service. A `@Service` class with five `@Autowired` fields cannot be unit-tested without `SpringExtension` — you must boot a full `ApplicationContext` (or at least a sliced one) to inject the mocks, which is 100x slower than a plain JUnit test. The migration from field injection to constructor injection is mechanical (IntelliJ has a "Replace @Autowired field with constructor parameter" refactoring) and is the single highest-ROI cleanup in legacy Spring codebases.

### The IoC Container Lifecycle: Registration, Reflection/Scanning, Dependency Graph construction (DAG), Instantiation, Wiring, Destruction

The container has a lifecycle that runs from application boot to application shutdown. Each phase has a distinct failure mode, and recognising which phase failed is the difference between a 5-minute fix and a 5-hour incident.

**Registration**: the developer declares which classes the container should manage. In Spring this is `@ComponentScan` on a `@Configuration` class plus stereotype annotations (`@Component`, `@Service`, `@Repository`, `@Controller`) on the managed classes; in Laravel it is `app()->bind(Interface::class, Implementation::class)` in a Service Provider; in TSyringe it is `container.register(Token, Class)`. The container holds a map of `(type → metadata)` — for Spring this includes the constructor, the field annotations, the scope, the init/destroy methods.

**Scanning / Reflection**: at boot the container walks the classpath (Spring) or the autoloader (Laravel) and reflects on each registered class to discover its constructor parameters and their types. Spring uses `ReflectionUtils.doWithMethods` and `BeanUtils.findPrimaryConstructor`; Laravel uses PHP's `ReflectionClass::getConstructor` and `ReflectionParameter::getType`. The cost of this phase is why Spring Boot startup is 3-10 seconds on a non-trivial app and why Laravel caches bindings via `php artisan config:cache`.

**Dependency Graph construction (DAG)**: the container builds a directed graph of dependencies — `OrderService → OrderRepository → DataSource → HikariConfig`. The graph must be acyclic; cycles (A → B → A) are detected here. Spring detects cycles eagerly and throws `BeanCurrentlyInCreationException`; Laravel detects them at resolution time and throws `CircularDependencyException`.

**Instantiation and Wiring**: the container walks the DAG in topological order (leaves first). For each bean: (1) invoke the constructor with the resolved dependencies, (2) set any `@Autowired` fields, (3) invoke any `@PostConstruct` method, (4) invoke any `BeanPostProcessor.postProcessBeforeInitialization`, (5) invoke any `InitializingBean.afterPropertiesSet`, (6) invoke any `BeanPostProcessor.postProcessAfterInitialization` (this is where AOP proxies wrap the bean). The result is cached in the singleton registry.

**Destruction**: on JVM shutdown (`SIGTERM` → Spring's shutdown hook), the container walks the singleton registry in reverse dependency order and invokes `@PreDestroy` methods and `DisposableBean.destroy()`. This is where HikariCP closes the connection pool, where RabbitMQ channels are closed, where in-memory caches flush to disk. A missed `@PreDestroy` is the source of the "killed process held a lock in Postgres" incident.

```text
  Spring ApplicationContext startup phases:

  1. BeanFactory creation          — empty DefaultListableBeanFactory
  2. BeanDefinition registration   — @Component scan reads class files
  3. BeanPostProcessor registration— AOP, @Autowired processors
  4. Bean instantiation (lazy or eager)
     For each singleton (in dependency order):
        a. instantiate (constructor invoked)
        b. populate properties (@Autowired fields set)
        c. BeanNameAware / BeanFactoryAware callbacks
        d. BeanPostProcessor.postProcessBeforeInitialization
        e. @PostConstruct
        f. InitializingBean.afterPropertiesSet
        g. custom init method
        h. BeanPostProcessor.postProcessAfterInitialization  ← AOP proxy wraps here
  5. ContextRefreshedEvent         — fully wired, ready to serve
  6. ...application runs...
  7. ContextClosedEvent (on SIGTERM)
  8. Singleton destruction (reverse dependency order)
     For each singleton:
        a. @PreDestroy
        b. DisposableBean.destroy()
        c. custom destroy method
```

The production failure mode of the lifecycle is the "missing `@PreDestroy`" bug. A service that holds a `java.util.concurrent.ThreadPoolExecutor` and does not register a shutdown hook will leak threads when the JVM exits — the next process to start finds port 8080 still bound (`BindException: Address already in use`) because the previous JVM's threads have not yet been reaped by the OS. The fix is either `@PreDestroy` on the executor's `shutdown()` method or registering the executor as a Spring bean (Spring manages the lifecycle for you).

### Lifecycle Scopes: Singleton (Application-wide), Transient/Prototype (New instance per lookup), Request/Scoped (Tied to the HTTP request lifecycle)

A scope is the rule that decides when the container returns a cached instance versus constructing a new one. The three universal scopes are singleton, prototype/transient, and request/scoped.

**Singleton** is the default in Spring, Laravel, and most DI containers. The container constructs the bean exactly once, caches it, and returns the same instance for every subsequent `getBean` call. Singletons are stateless (or hold only immutable state) and are safe to share across concurrent threads. Use cases: services, repositories, configuration, HTTP clients, connection pools.

**Prototype** (Spring) / **Transient** (Laravel) means the container constructs a new instance every time it is requested. Spring does not manage the full lifecycle of prototype beans — it constructs them, hands them over, and forgets about them; `@PreDestroy` is never called on a prototype bean. Use cases: stateful objects that should not be shared, such as a per-request `OrderBuilder` that accumulates state.

**Request** scope (Spring's `@Scope("request")` via `RequestContextHolder`) means the container constructs one instance per HTTP request and disposes it at the end of the request. Use cases: the current user's `SecurityContext`, a per-request DB transaction handle, a per-request correlation ID holder. Laravel has the same concept via `app()->scoped(Key::class, fn => ...)` (bound once per request).

```java
@Service
@Scope("singleton")            // default — one instance per ApplicationContext
class UserService { ... }

@Service
@Scope("prototype")            // new instance on every getBean() call
class OrderBuilder { ... }

@Component
@Scope(value = WebApplicationContext.SCOPE_REQUEST, proxyMode = ScopedProxyMode.TARGET_CLASS)
class RequestContext { ... }   // one instance per HTTP request
```

```text
  Scope comparison:

  ┌───────────┬───────────────────────┬──────────────────────────┬───────────────────────────┐
  │ Scope     │ Spring                │ Laravel                  │ Lifetime                  │
  ├───────────┼───────────────────────┼──────────────────────────┼───────────────────────────┤
  │ Singleton │ @Scope("singleton")   │ app()->singleton(K, fn)  │ Application boot → shutdown│
  │ Prototype │ @Scope("prototype")   │ app()->bind(K, fn)       │ Per getBean/resolve call  │
  │ Request   │ @Scope("request")     │ app()->scoped(K, fn)     │ HTTP request start → end  │
  │ Session   │ @Scope("session")     │ (custom)                 │ HTTP session start → end  │
  └───────────┴───────────────────────┴──────────────────────────┴───────────────────────────┘
```

The production failure mode of scopes is the "scoped bean injected into singleton" trap. If a `@Service` (singleton) has an `@Autowired` field of type `RequestContext` (request scope), Spring would normally inject the request-scoped bean at singleton construction time — but the request has not started yet. Spring solves this with a CGLIB proxy: the singleton holds a proxy that delegates to the current request's instance. If `proxyMode = ScopedProxyMode.NO` (the default for request scope), the wiring fails at startup with `ScopeNotActiveException`. The fix is `proxyMode = ScopedProxyMode.TARGET_CLASS` (or `INTERFACES` if the scoped bean has an interface).

### Detecting and resolving Circular Dependencies (A \to B \to A)

A circular dependency is when A's constructor needs B and B's constructor needs A. The container cannot construct either one — it needs B to construct A and A to construct B. The cycle must be broken.

Spring detects cycles eagerly. When `getBean(A)` is called, the container marks A as "currently in creation", recurses into `getBean(B)`, which marks B as "currently in creation", recurses into `getBean(A)`, which sees A is already in creation and throws `BeanCurrentlyInCreationException`. The error message is `Error creating bean with name 'a': Requested bean is currently in creation: Is there an unresolvable circular reference?`

For setter-injected cycles, Spring uses "early reference" exposure. When A is constructed (with an empty constructor) but not yet populated, Spring publishes an "early reference" to A in a `singletonFactories` map. When B's setter is invoked, B can ask the container for A's early reference (a half-constructed A). Once B is fully wired, the container returns to A's population, and A's setter for B is invoked with the now-fully-wired B. This only works for setter-injected cycles; constructor-injected cycles always fail because the constructor has not yet returned an instance to expose as an early reference.

Spring Boot 2.6+ disabled circular references by default (`spring.main.allow-circular-references=false`). The recommended fix is always to refactor: extract the shared logic into a third class C that both A and B depend on, breaking the cycle.

```java
// Circular: A needs B, B needs A
@Service class A { @Autowired B b; }   // field injection allows the cycle to be wired
@Service class B { @Autowired A a; }   // at runtime via early reference

// Refactored: A and B both depend on C, no cycle
@Service class A { A(C c) { ... } }
@Service class B { B(C c) { ... } }
@Service class C { ... }
```

```text
  Circular dependency detection (Spring):

  getBean(A)
   ↓ marks A as "in creation"
   ↓ getBean(B)  (A's dependency)
       ↓ marks B as "in creation"
       ↓ getBean(A)  (B's dependency)
           ↓ A is "in creation" → throw BeanCurrentlyInCreationException

  Fix options:
    1. Refactor — extract shared logic into C, both A and B depend on C.
    2. Setter injection on one side — Spring wires A with an early ref of B.
    3. @Lazy — Spring injects a proxy that resolves B on first use.
       @Service class A { A(@Lazy B b) { ... } }   // no cycle at boot
```

The production failure mode of circular dependencies is the silent performance regression from `@Lazy`. A `@Lazy`-injected dependency is a CGLIB proxy that resolves the real bean on first method invocation. If the dependency is called on every request, the proxy adds ~100ns per call (a `ThreadLocal` lookup plus a delegation). For a hot path, this shows up as a thin slice in the flame graph. The fix is to remove `@Lazy` by breaking the cycle properly — extract the shared logic into a third class.

## Cross-Ecosystem Code

The same DI concept — a service that depends on a repository, wired by a container — implemented side-by-side.

**Spring Boot (Anchor):**
```java
@Service
class OrderService {
    private final OrderRepository repo;
    private final PaymentGateway pay;

    public OrderService(OrderRepository repo, PaymentGateway pay) {
        this.repo = repo;
        this.pay = pay;
    }

    @Transactional
    public Order placeOrder(NewOrderCmd cmd) {
        Order o = new Order(cmd.userId(), cmd.total());
        repo.save(o);
        pay.charge(o.getId(), o.getTotal());
        return o;
    }
}

// Configuration: bind the interface to the concrete impl
@Configuration
class AppConfig {
    @Bean OrderRepository orderRepository(DataSource ds) {
        return new PostgresOrderRepository(ds);
    }
    @Bean PaymentGateway paymentGateway(RestClient http) {
        return new StripePaymentGateway(http);
    }
}
```

**Express (Delta) — TSyringe:**
```typescript
import { injectable, inject, container } from "tsyringe";

@injectable()
class OrderRepository {
  async save(o: Order): Promise<Order> { /* ... */ return o; }
}

@injectable()
class OrderService {
  constructor(@inject("OrderRepository") private repo: OrderRepository) {}
  async placeOrder(cmd: NewOrderCmd): Promise<Order> {
    const o = new Order(cmd.userId, cmd.total);
    await this.repo.save(o);
    return o;
  }
}

container.register("OrderRepository", OrderRepository);
const svc = container.resolve(OrderService);
```

**Django (Delta) — manual composition:**
```python
class OrderRepository:
    def save(self, o: Order) -> Order: ...

class OrderService:
    def __init__(self, repo: OrderRepository):
        self.repo = repo
    def place_order(self, cmd: NewOrderCmd) -> Order:
        o = Order(cmd.user_id, cmd.total)
        self.repo.save(o)
        return o

# Wiring at composition root (in apps.py ready() or a services module)
svc = OrderService(repo=OrderRepository())
```

**Laravel (Delta) — Service Container:**
```php
class OrderService {
    public function __construct(private OrderRepository $repo) {}
    public function placeOrder(NewOrderCmd $cmd): Order {
        $o = new Order($cmd->userId, $cmd->total);
        $this->repo->save($o);
        return $o;
    }
}

// In a Service Provider:
$this->app->bind(OrderRepositoryInterface::class, OrderRepository::class);

// Resolution — Laravel uses PHP reflection to auto-wire constructor args:
$svc = app(OrderService::class);
```
