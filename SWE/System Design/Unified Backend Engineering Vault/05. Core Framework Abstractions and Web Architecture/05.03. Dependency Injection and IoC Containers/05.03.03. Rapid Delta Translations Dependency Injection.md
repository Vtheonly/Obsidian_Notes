# 05.03.03. Rapid Delta Translations Dependency Injection

## What This Note Is

This is a **delta translation note**. It is intentionally short. Read it **after** completing the anchor implementation in the sibling Spring Boot note. The point is to answer one question:

> What is different in this ecosystem, and what is automatic that I had to do manually in the anchor?

If you find yourself re-learning the concept here, you have not finished the anchor. Go back.

## Implementation Deltas

The deltas to internalize:

- *PHP / Laravel*: The Laravel Service Container, Auto-wiring via PHP Reflection, binding interfaces to concrete implementations in Service Providers, Singletons vs. Scoped bindings.
- *TypeScript / Node.js*: Manual Dependency Injection vs. Container frameworks (InversifyJS, TSyringe) using TypeScript experimental reflection metadata (`reflect-metadata`).
- *Python / Django & Flask*: Pythonic composition patterns, module-level singletons, dependency injection via containers (`dependency-injector`), and overriding dependencies in unit tests.

## The Details

### *PHP / Laravel*: The Laravel Service Container, Auto-wiring via PHP Reflection, binding interfaces to concrete implementations in Service Providers, Singletons vs. Scoped bindings

Laravel's Service Container is the closest thing to Spring's `ApplicationContext` outside the JVM. It is a registry that maps "abstract" keys (interface FQCNs, string tokens) to "concrete" resolvers (closures, class names). On `app(Key::class)` it walks the dependency graph reflectively — `new ReflectionClass(Implementation)` → `getConstructor()` → `getParameters()` → resolve each parameter recursively — exactly the same algorithm as Spring's `DefaultListableBeanFactory.createBean`.

```php
<?php
// app/Providers/OrderServiceProvider.php
namespace App\Providers;

use Illuminate\Support\ServiceProvider;
use App\Contracts\OrderRepositoryInterface;
use App\Repositories\PostgresOrderRepository;
use App\Repositories\InMemoryOrderRepository;
use App\Services\OrderService;

class OrderServiceProvider extends ServiceProvider
{
    public function register(): void
    {
        // Bind interface to concrete implementation.
        // The closure runs every time app(OrderRepositoryInterface::class) is called.
        $this->app->bind(OrderRepositoryInterface::class, function ($app) {
            return match (config('orders.repo')) {
                'postgres' => new PostgresOrderRepository($app->make('db')->connection()),
                'memory'   => new InMemoryOrderRepository(),
            };
        });

        // Singleton — closure runs once, result is cached for the request lifetime
        // (and the process lifetime under Octane).
        $this->app->singleton(OrderService::class, function ($app) {
            return new OrderService($app->make(OrderRepositoryInterface::class));
        });

        // Scoped — closure runs once per request, cleared at request end.
        // Useful for per-request state like the current user's tenant context.
        $this->app->scoped('current.tenant', function ($app) {
            return Tenant::resolveFromRequest(request());
        });
    }

    public function boot(): void
    {
        // Runs after all providers' register() — safe to resolve other beans here.
    }
}

// Auto-wiring — Laravel uses PHP reflection to inspect constructor parameters.
// If a parameter is a concrete class (not an interface), Laravel new()s it
// recursively without an explicit binding.
class OrderService {
    public function __construct(
        private OrderRepositoryInterface $repo,   // ← resolved via bind() above
        private PaymentGateway $pay,              // ← auto-wired (concrete class)
        private LoggerInterface $log,             // ← auto-wired (Laravel binds Log)
    ) {}
}

// Resolution:
$svc = app(OrderService::class);
// Internally: Laravel reflects on OrderService.__construct, sees 3 params.
//   1. OrderRepositoryInterface → looks up bind() → PostgresOrderRepository
//   2. PaymentGateway → no bind, reflect on PaymentGateway.__construct,
//      recursively resolve its deps, new PaymentGateway(...)
//   3. LoggerInterface → Laravel's logging service provider binds this to a
//      Monolog instance, returned from the cache.

// In a controller — type-hinted constructor parameter is auto-resolved:
class OrderController extends Controller {
    public function __construct(private OrderService $orders) {}

    public function store(Request $req) {
        return response()->json($this->orders->placeOrder($req->all()), 201);
    }
}
```

What is automatic here that was manual in the anchor: PHP reflection-based auto-wiring is the default — you do not need `@Autowired` or `@Component`. Any class whose constructor parameters are resolvable (concrete classes or explicitly-bound interfaces) can be `app()`-resolved without registration. Laravel's service providers give a single `register()` method per package, which is simpler than Spring's `@Configuration + @Bean` for the same effect.

What is manual here that was automatic in the anchor: there is no `@Transactional` aspect in Laravel's container — use the `DB::transaction(fn => ...)` helper or the `Transactional` trait from a package. There is no CGLIB proxying — Laravel's container does not generate proxy classes, so self-invocation is not a trap (there is no aspect to bypass). There is no `@PostConstruct` / `@PreDestroy` — use the `boot()` method of a service provider for post-registration logic, and PHP's `__destruct` (which is unreliable under PHP-FPM because the process is killed).

The runtime invariant exposed differently: PHP-FPM's shared-nothing process model means the container is rebuilt on every request — `singleton` is "singleton for this request", not "singleton for the application lifetime". Under Laravel Octane (Swoole/RoadRunner), singletons persist across requests, which is closer to Spring's behaviour but introduces the cross-request leak bugs that Spring has and PHP-FPM does not.

### *TypeScript / Node.js*: Manual Dependency Injection vs. Container frameworks (InversifyJS, TSyringe) using TypeScript experimental reflection metadata (`reflect-metadata`)

JavaScript has no reflection API for inspecting a class's constructor parameters. TypeScript adds one (`design:paramtypes` metadata emitted when `emitDecoratorMetadata: true`), but it only records the TypeScript types — at runtime, the parameter types are JavaScript values, and TypeScript types are erased. To do DI in Node you either (a) wire by hand at the composition root, or (b) use a container library that reads the `reflect-metadata` and resolves by token.

```typescript
// Option A — manual composition at the composition root (no container library)
// src/compositionRoot.ts
import { OrderService } from "./orders/OrderService";
import { PostgresOrderRepository } from "./orders/PostgresOrderRepository";
import { StripePaymentGateway } from "./payments/StripePaymentGateway";
import { OrderController } from "./orders/OrderController";

// Build the graph from leaves to root, exactly like Spring's container would.
const repo = new PostgresOrderRepository(process.env.DATABASE_URL!);
const pay  = new StripePaymentGateway(process.env.STRIPE_API_KEY!);
const svc  = new OrderService(repo, pay);
const ctrl = new OrderController(svc);

export { ctrl };   // routes import this

// src/orders/OrderService.ts
export class OrderService {
    constructor(
        private readonly repo: OrderRepository,   // interface, injected
        private readonly pay: PaymentGateway,
    ) {}

    async placeOrder(cmd: NewOrderCmd): Promise<Order> {
        const o = new Order(cmd.userId, cmd.total);
        await this.repo.save(o);
        await this.pay.charge(o.id, o.total);
        return o;
    }
}

// src/orders/OrderController.ts
export class OrderController {
    constructor(private readonly orders: OrderService) {}
    async store(req: Request, res: Response) {
        const order = await this.orders.placeOrder(req.body);
        res.status(201).json(order);
    }
}
```

```typescript
// Option B — TSyringe container, closer to Spring's @Autowired
import { injectable, inject, container } from "tsyringe";

interface OrderRepository { save(o: Order): Promise<Order>; }

@injectable()
class PostgresOrderRepository implements OrderRepository {
    constructor(@inject("DATABASE_URL") private url: string) {}
    async save(o: Order): Promise<Order> { /* ... */ return o; }
}

@injectable()
class StripePaymentGateway {
    constructor(@inject("STRIPE_API_KEY") private key: string) {}
    async charge(orderId: string, amount: number): Promise<void> { /* ... */ }
}

@injectable()
class OrderService {
    constructor(
        @inject("OrderRepository") private repo: OrderRepository,
        @inject("PaymentGateway")  private pay:  StripePaymentGateway,
    ) {}
    async placeOrder(cmd: NewOrderCmd): Promise<Order> {
        const o = new Order(cmd.userId, cmd.total);
        await this.repo.save(o);
        await this.pay.charge(o.id, o.total);
        return o;
    }
}

// Registration — explicit, like Laravel's bind()
container.register("DATABASE_URL", { useValue: process.env.DATABASE_URL! });
container.register("STRIPE_API_KEY", { useValue: process.env.STRIPE_API_KEY! });
container.register("OrderRepository", { useClass: PostgresOrderRepository });
container.register("PaymentGateway",  { useClass: StripePaymentGateway });

// Resolution — TSyringe uses reflect-metadata to read OrderService's constructor
// params and resolves each by token.
const svc = container.resolve(OrderService);
```

What is automatic here that was manual in the anchor: nothing significant. TSyringe's `@injectable()` and `@inject(token)` decorators are the equivalents of `@Component` and `@Autowired`, but you must register every binding explicitly — there is no `@ComponentScan` equivalent (no classpath walking in Node). The manual composition approach (Option A) is more common in Node codebases because it requires no dependencies and the wiring is explicit.

What is manual here that was automatic in the anchor: there is no `@Transactional`, no `@Async`, no `@Cacheable` aspect system. There is no `@PostConstruct` (use the constructor). There is no `@PreDestroy` (register a `process.on("SIGTERM", ...)` handler). There is no proxy generation — JavaScript classes cannot be transparently subclassed with the same fidelity as Java (final methods, package-private access, etc. do not exist). The result is that the DI container in Node is "just a registry" — no AOP, no lifecycle management.

The runtime invariant exposed differently: Node's single-threaded event loop means singletons are shared across every concurrent request on the process. There is no per-request scope unless you implement it via `AsyncLocalStorage` (the Node equivalent of `ThreadLocal`). This is structurally different from Spring's per-thread model — a singleton in Node is truly shared, and a stateful singleton is a race condition waiting to happen.

### *Python / Django & Flask*: Pythonic composition patterns, module-level singletons, dependency injection via containers (`dependency-injector`), and overriding dependencies in unit tests

Python has no DI container in the standard library and neither Django nor Flask ships one. The Pythonic pattern is "composition at the module level": define a service in a module, instantiate it at module load time, and import the instance. This is not DI in the Spring sense — there is no container, no interface binding, no scope management — but it achieves the same decoupling for most applications.

```python
# Django — manual composition with override support
# myapp/services.py
from dataclasses import dataclass
from typing import Protocol

class OrderRepository(Protocol):
    def save(self, o: Order) -> Order: ...

class PostgresOrderRepository:
    def __init__(self, db_url: str):
        self.db_url = db_url
    def save(self, o: Order) -> Order:
        # ... actual DB call ...
        return o

@dataclass
class OrderService:
    repo: OrderRepository        # Protocol — any class with .save() works
    pay:  "PaymentGateway"

    def place_order(self, cmd: NewOrderCmd) -> Order:
        o = Order(cmd.user_id, cmd.total)
        self.repo.save(o)
        self.pay.charge(o.id, o.total)
        return o

# Composition root — module-level singletons, instantiated at import time
import os
from myapp.payments import StripePaymentGateway

_repo = PostgresOrderRepository(os.environ["DATABASE_URL"])
_pay  = StripePaymentGateway(os.environ["STRIPE_API_KEY"])
orders_service = OrderService(repo=_repo, pay=_pay)

# myapp/views.py
from myapp.services import orders_service
from django.http import JsonResponse

def store(request):
    cmd = NewOrderCmd(**request.json())
    order = orders_service.place_order(cmd)
    return JsonResponse({"id": str(order.id)}, status=201)

# Override for tests — patch the module-level singleton
# tests/test_orders.py
from unittest.mock import MagicMock
from myapp import services

def test_place_order_saves_and_charges(monkeypatch):
    mock_repo = MagicMock()
    mock_pay  = MagicMock()
    monkeypatch.setattr(services, "orders_service",
                        OrderService(repo=mock_repo, pay=mock_pay))

    from myapp import views
    request = ...  # build a request
    response = views.store(request)

    mock_repo.save.assert_called_once()
    mock_pay.charge.assert_called_once()
```

```python
# Flask with dependency-injector library — closer to Spring's container
from dependency_injector import containers, providers
from myapp.services import OrderService, PostgresOrderRepository, StripePaymentGateway

class Container(containers.DeclarativeContainer):
    config = providers.Configuration()
    db_url = config.db.url

    order_repository = providers.Singleton(
        PostgresOrderRepository,
        db_url=db_url,
    )
    payment_gateway = providers.Singleton(
        StripePaymentGateway,
        api_key=config.stripe.api_key,
    )
    order_service = providers.Factory(
        OrderService,
        repo=order_repository,
        pay=payment_gateway,
    )

# app.py
from flask import Flask
from .container import Container

app = Flask(__name__)
container = Container()
container.config.from_dict({"db": {"url": os.environ["DATABASE_URL"]},
                            "stripe": {"api_key": os.environ["STRIPE_API_KEY"]}})

@app.post("/orders")
def store():
    cmd = NewOrderCmd(**request.get_json())
    svc = container.order_service()   # Factory — new instance per call
    order = svc.place_order(cmd)
    return jsonify({"id": str(order.id)}), 201

# Override in tests
def test_place_order(monkeypatch):
    container.order_service.override(providers.Singleton(
        OrderService, repo=MagicMock(), pay=MagicMock()))
    # ... request hits the overridden service ...
```

What is automatic here that was manual in the anchor: Python's `Protocol` (PEP 544) provides structural typing — any class with the right method signatures satisfies the Protocol, no `implements` keyword needed. This is more flexible than Java's nominal interface system but provides less compile-time safety (mypy checks Protocols statically, but the runtime is duck-typed). The `monkeypatch.setattr(services, "orders_service", mock)` pattern is the Pythonic equivalent of `@MockBean` in Spring tests — and is more powerful, because it works for any module-level binding.

What is manual here that was automatic in the anchor: there is no `@Transactional`, no `@Async`, no `@Cacheable`. There is no lifecycle management (no `@PostConstruct` / `@PreDestroy`) — you write setup/teardown code in `__init__` and `__del__` (the latter is unreliable). There is no component scanning (you import the module explicitly). There is no proxy generation — Python's `unittest.mock.MagicMock` does proxying for tests, but there is no production equivalent for AOP.

The runtime invariant exposed differently: CPython's GIL means a single process handles one Python bytecode instruction at a time. A module-level singleton is shared across all requests on the process, but the GIL prevents concurrent access to Python objects — so a stateful singleton is mostly safe (the GIL serialises attribute writes), but not in the way you would want (a long I/O operation releases the GIL and another request can observe a half-updated state). The fix is the same as in Java: make singletons stateless, use immutable dataclasses.

## Cross-Ecosystem Code

The same DI concept — a service depending on a repository and a payment gateway, wired by a container — side-by-side.

**Spring Boot (Anchor):**
```java
@Service
class OrderService {
    private final OrderRepository repo;
    private final PaymentGateway pay;

    public OrderService(OrderRepository repo, PaymentGateway pay) {
        this.repo = repo;
        this.pay = pay;
    }

    @Transactional
    public Order placeOrder(NewOrderCmd cmd) {
        Order o = new Order(cmd.userId(), cmd.total());
        repo.save(o);
        pay.charge(o.getId(), o.getTotal());
        return o;
    }
}

// @Configuration + @Bean for the infrastructure wiring
@Configuration
class AppConfig {
    @Bean OrderRepository orderRepository(JdbcTemplate jdbc) {
        return new PostgresOrderRepository(jdbc);
    }
    @Bean PaymentGateway paymentGateway(@Value("${stripe.key}") String key) {
        return new StripePaymentGateway(key);
    }
}
```

## Delta Checklist

> [!tip] What to write down after the translation
> - What was automatic here that I had to do manually in the anchor? (Laravel: reflection-based auto-wiring, no `@Autowired` needed. Django: `Protocol` structural typing, no `implements`.)
> - What was manual here that was automatic in the anchor? (Express: no component scanning, no `@Transactional`, no `@PreDestroy`. Django/Flask: no AOP, no lifecycle, no container. Laravel: no `@Transactional` aspect.)
> - Which runtime invariant is exposed differently? (Node: single-threaded, singletons are globally shared, `AsyncLocalStorage` for per-request scope. Python: GIL serialises attribute writes. PHP-FPM: per-request container rebuild, singletons are per-request.)
> - Which failure mode is structurally impossible here? (Laravel under PHP-FPM: stale thread-local, because there is no thread. Express: proxy bypass from self-invocation, because there are no proxies.)
> - Which failure mode is new here? (Express: stateful singleton shared across all concurrent requests is a race. Django: `monkeypatch.setattr` leaking between tests if not cleaned up. Laravel Octane: cross-request leak because singletons persist.)
