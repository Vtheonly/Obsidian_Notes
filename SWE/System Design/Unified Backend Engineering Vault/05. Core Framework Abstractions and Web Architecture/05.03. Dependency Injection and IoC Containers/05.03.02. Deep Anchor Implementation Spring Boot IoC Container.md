# 05.03.02. Deep Anchor Implementation Spring Boot IoC Container

## Why This Is the Anchor

This note is the **deep anchor implementation** — the place where you build the IoC container concept in Spring Boot with production-grade depth. Per the Anchor and Delta protocol ([[00.02. The Anchor and Delta Learning Protocol]]), you must break this implementation before moving to the delta notes. The point is to acquire scars: real experience with the failure modes that this concept produces under load.

Spring Boot is the anchor for DI because its container is the most fully-featured of any mainstream backend framework: stereotype annotations, `@Configuration` + `@Bean` factory methods, constructor/setter/field injection, `@Qualifier` / `@Primary` / `@Profile` / `@Scope`, `BeanPostProcessor` for cross-cutting customisation, CGLIB proxying for AOP, and lifecycle callbacks (`@PostConstruct`, `@PreDestroy`, `InitializingBean`, `DisposableBean`). Express has nothing equivalent; Laravel has a subset; Django and Flask have none. Learning the full surface here means the deltas are trivial.

## What You Will Build

The implementation covers:

- `ApplicationContext` and `BeanFactory` internal architecture.
- Component scanning (`@Component`, `@Service`, `@Repository`, `@Configuration`, `@Bean`).
- Dynamic Bytecode Proxies: JDK Dynamic Proxies (Interface-based) vs. CGLIB Proxies (Subclass-based).
- Writing a decoupled Domain Service injecting outbound infrastructure adapters via Constructor Injection.

## Anchor Implementation (Spring Boot)

The code below is a complete, runnable Spring Boot 3.x DI example: a domain service depending on a repository interface, two alternative implementations selected by `@Profile`, a `@Configuration` class registering infrastructure beans, and a CGLIB-proxied `@Transactional` service.

```java
// src/main/java/com/example/orders/OrderRepository.java
package com.example.orders;

import java.util.Optional;
import java.util.UUID;

public interface OrderRepository {
    Optional<Order> findById(UUID id);
    Order save(Order order);
}

// src/main/java/com/example/orders/PostgresOrderRepository.java
package com.example.orders;

import org.springframework.boot.autoconfigure.condition.ConditionalOnProperty;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.stereotype.Repository;
import java.util.*;

@Repository
@ConditionalOnProperty(name = "orders.repo", havingValue = "postgres", matchIfMissing = true)
public class PostgresOrderRepository implements OrderRepository {
    private final JdbcTemplate jdbc;

    public PostgresOrderRepository(JdbcTemplate jdbc) {   // constructor injection
        this.jdbc = jdbc;
    }

    @Override
    public Optional<Order> findById(UUID id) {
        List<Order> r = jdbc.query("SELECT * FROM orders WHERE id = ?",
            (rs, i) -> new Order(rs.getObject("id", UUID.class), rs.getBigDecimal("total")),
            id);
        return r.isEmpty() ? Optional.empty() : Optional.of(r.get(0));
    }

    @Override
    public Order save(Order order) {
        jdbc.update("INSERT INTO orders (id, total) VALUES (?, ?) " +
                    "ON CONFLICT (id) DO UPDATE SET total = EXCLUDED.total",
                    order.getId(), order.getTotal());
        return order;
    }
}

// src/main/java/com/example/orders/InMemoryOrderRepository.java
package com.example.orders;

import org.springframework.boot.autoconfigure.condition.ConditionalOnProperty;
import org.springframework.stereotype.Repository;
import java.util.*;
import java.util.concurrent.ConcurrentHashMap;

@Repository
@ConditionalOnProperty(name = "orders.repo", havingValue = "memory")
public class InMemoryOrderRepository implements OrderRepository {
    private final Map<UUID, Order> store = new ConcurrentHashMap<>();

    @Override
    public Optional<Order> findById(UUID id) { return Optional.ofNullable(store.get(id)); }

    @Override
    public Order save(Order order) { store.put(order.getId(), order); return order; }
}

// src/main/java/com/example/orders/OrderService.java
package com.example.orders;

import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import java.math.BigDecimal;
import java.util.UUID;

@Service
public class OrderService {
    private final OrderRepository repo;
    private final PaymentGateway pay;
    private final OrderEventPublisher events;

    // Constructor injection — Spring resolves repo, pay, events from the container.
    // @Autowired is implicit on a single-constructor class since Spring 4.3.
    public OrderService(OrderRepository repo, PaymentGateway pay, OrderEventPublisher events) {
        this.repo = repo;
        this.pay = pay;
        this.events = events;
    }

    // @Transactional triggers CGLIB proxying: Spring subclasses OrderService and
    // wraps placeOrder() in a transaction begin/commit/rollback. The proxy is
    // what other beans receive when they @Autowired OrderService.
    @Transactional
    public Order placeOrder(UUID userId, BigDecimal total) {
        Order o = new Order(UUID.randomUUID(), total);
        repo.save(o);
        pay.charge(o.getId(), total);
        events.publish(new OrderPlaced(o.getId(), userId));
        return o;
    }
}

// src/main/java/com/example/orders/PaymentGateway.java  (interface)
package com.example.orders;
public interface PaymentGateway { void charge(UUID orderId, java.math.BigDecimal amount); }

// src/main/java/com/example/orders/StripePaymentGateway.java
package com.example.orders;

import org.springframework.beans.factory.annotation.Value;
import org.springframework.stereotype.Component;
import org.springframework.web.client.RestClient;

@Component
@org.springframework.context.annotation.Profile("prod")   // only active when "prod" profile is on
public class StripePaymentGateway implements PaymentGateway {
    private final RestClient http;
    private final String apiKey;

    public StripePaymentGateway(@Value("${stripe.api-key}") String apiKey) {
        this.apiKey = apiKey;
        this.http = RestClient.builder().baseUrl("https://api.stripe.com").build();
    }

    @Override
    public void charge(UUID orderId, java.math.BigDecimal amount) {
        http.post().uri("/v1/charges")
            .header("Authorization", "Bearer " + apiKey)
            .body(java.util.Map.of("amount", amount, "order_id", orderId.toString()))
            .retrieve().toBodilessEntity();
    }
}
```

## The Details

### `ApplicationContext` and `BeanFactory` internal architecture

`BeanFactory` is the core DI container interface — it owns the bean registry, the singleton cache, and the resolution algorithm. `ApplicationContext` is the superset: it adds resource loading (classpath, file system, URL), event publication (`ApplicationEvent` / `ApplicationListener`), environment abstraction (`@Profile`), and lifecycle integration (the `refresh()` method that drives the entire startup sequence). The default `ApplicationContext` implementation in Spring Boot is `AnnotationConfigServletWebServerApplicationContext`, which is itself a subclass of `GenericApplicationContext` plus `ServletWebServerApplicationContext`.

The internal data structures are: `beanDefinitionMap` (a `Map<String, BeanDefinition>` — the bean name to its metadata), `singletonObjects` (a `ConcurrentHashMap<String, Object>` — the singleton cache), `singletonFactories` (a `Map<String, ObjectFactory<?>>` — early references for circular dependency resolution), `singletonsCurrentlyInCreation` (a `Set<String>` — used for cycle detection). The resolution algorithm walks `beanDefinitionMap`, instantiates each singleton in dependency order, and caches the result in `singletonObjects`.

The startup sequence is orchestrated by `AbstractApplicationContext.refresh()`. The phases are: (1) `prepareRefresh()` — initialise environment, validate required properties; (2) `obtainFreshBeanFactory()` — load or refresh `BeanDefinition`s (this is where `@ComponentScan` runs); (3) `registerBeanPostProcessors()` — instantiate `BeanPostProcessor` beans like `AutowiredAnnotationBeanPostProcessor` (handles `@Autowired`) and `CommonAnnotationBeanPostProcessor` (handles `@PostConstruct`); (4) `initMessageSource()` and `initApplicationEventMulticaster()`; (5) `onRefresh()` — for web contexts, this starts the embedded Tomcat; (6) `registerListeners()`; (7) `finishBeanFactoryInitialization()` — instantiate all remaining singletons (this is the slow step, taking 80% of startup time); (8) `finishRefresh()` — publish `ContextRefreshedEvent`.

The `OrderService$$SpringCGLIB$$0` class name in the log is the giveaway: `OrderService` is proxied. CGLIB generated a subclass at runtime (the `$$SpringCGLIB$$0` suffix) so that the `@Transactional` aspect can wrap `placeOrder()` in a transaction. The original `OrderService` class still exists, but no other bean holds a reference to it — they all hold the proxy. This is why calling `this.placeOrder()` from inside `OrderService` does not start a transaction: the call goes to the original instance, not the proxy.

### Component scanning (`@Component`, `@Service`, `@Repository`, `@Configuration`, `@Bean`)

Spring discovers beans two ways: stereotype annotations and `@Bean` factory methods. Stereotype annotations are scanned on the classpath at startup; `@Bean` methods are invoked reflectively on `@Configuration` classes. The two mechanisms cover different use cases: stereotypes for application code (you wrote the class, so you can annotate it), `@Bean` for library code (you cannot annotate `RestClient.builder().build()`, so you write a `@Bean` method that returns it).

`@Component` is the base stereotype. `@Service`, `@Repository`, `@Controller`, `@RestController`, `@Configuration` are all meta-annotated with `@Component` and behave identically at the container level — they all register a singleton bean. The semantic distinction is for developers and for some framework features: `@Repository` enables automatic translation of persistence exceptions (`SQLException` → `DataAccessException`), `@Controller` + `@RequestMapping` enables handler mapping, `@Configuration` enables `@Bean` method processing via CGLIB.

`@ComponentScan` walks the classpath starting from the package of the `@SpringBootApplication` class. It uses ASM bytecode parsing (not class loading) to read each `.class` file's annotations, so it does not initialise the classes it scans — this matters because class initialisation runs `static {}` blocks which can have side effects. The scan finds every class annotated with a stereotype and registers a `BeanDefinition` for it. The `@ConditionalOnProperty`, `@Profile`, and `@ConditionalOnMissingBean` annotations are then evaluated to filter the candidates.

`@Bean` methods in `@Configuration` classes are processed by `ConfigurationClassPostProcessor`, a `BeanFactoryPostProcessor` that runs during `obtainFreshBeanFactory()`. The processor reflectively reads each `@Bean` method, registers a `BeanDefinition` for the return type, and records the method as the factory. When the bean is later instantiated, the container invokes the method reflectively. The `@Configuration` class itself is proxied by CGLIB so that `@Bean` method calls inside other `@Bean` methods are intercepted and return the cached singleton (the "full" mode), preventing duplicate bean instantiation.

```java
// @Configuration class with @Bean methods — Spring proxies this class so that
// restClient() is called only once even if multiple @Bean methods invoke it.
@Configuration
public class HttpClientConfig {

    @Bean
    RestClient restClient() {                          // singleton, cached
        return RestClient.builder().baseUrl("https://api.example.com").build();
    }

    @Bean
    PaymentGateway stripeGateway(RestClient restClient) {  // injected
        // The 'restClient' parameter is resolved from the container, NOT
        // by calling restClient() directly. Even if it did call restClient(),
        // the CGLIB proxy would intercept and return the cached singleton.
        return new StripePaymentGateway(restClient);
    }
}
```

The production failure mode of component scanning is the "scan too much" bug. `@SpringBootApplication` without a `scanBasePackages` attribute scans the package of the application class and every sub-package — if your test code is in a sibling package and contains a `@Service` annotated class, it gets registered in production. The fix is to either keep test code in `src/test/java` (which is not on the runtime classpath) or to scope the scan explicitly: `@SpringBootApplication(scanBasePackages = "com.example.orders")`.

### Dynamic Bytecode Proxies: JDK Dynamic Proxies (Interface-based) vs. CGLIB Proxies (Subclass-based)

Spring uses two proxying mechanisms, chosen automatically based on whether the target class implements an interface. JDK Dynamic Proxies (the `java.lang.reflect.Proxy` API, in the JDK since 1.3) generate a class at runtime that implements every interface the target implements, forwarding each method call to an `InvocationHandler`. CGLIB (Code Generation Library, now bundled as `byte-buddy` in Spring Boot 3) generates a subclass of the target class, overriding each non-final method to insert the aspect logic.

JDK proxies require at least one interface. If `OrderService` implements no interface, a JDK proxy cannot be created — the proxy would have no type to implement. Spring's `DefaultAopProxyFactory` falls back to CGLIB in this case. If `OrderService` does implement an interface, the choice depends on `@EnableAspectJAutoProxy(proxyTargetClass = true)` (force CGLIB) or the default (use JDK proxy if interface exists). Spring Boot 2+ defaults to `proxyTargetClass = true`, so CGLIB is used unless you opt out — this is why `OrderService$$SpringCGLIB$$0` shows up even when `OrderService` implements an interface.

CGLIB has limitations. It cannot proxy `final` classes (subclassing is impossible). It cannot proxy `final` methods (the override is silently skipped, so the aspect does not apply — `@Transactional` on a `final` method is a no-op). It cannot proxy `private` methods (overrides are only for visible methods). It cannot proxy package-private methods across packages. The Spring Framework team has been moving toward interface-based proxies for these reasons, but CGLIB remains the default in Spring Boot.

```text
  JDK Dynamic Proxy vs CGLIB:

  ┌────────────────────┬──────────────────────────────┬──────────────────────────────┐
  │ Property           │ JDK Dynamic Proxy            │ CGLIB (byte-buddy)           │
  ├────────────────────┼──────────────────────────────┼──────────────────────────────┤
  │ Mechanism          │ java.lang.reflect.Proxy      │ Runtime subclass generation  │
  │ Requirement        │ Target implements interface  │ Target class not final       │
  │ Final class OK?    │ Yes (if interface)           │ No                           │
  │ Final method OK?   │ Yes                          │ No (aspect silently skipped) │
  │ Private method?    │ N/A (interface methods only) │ No (not overridden)          │
  │ Self-invocation?   │ Broken (this.method bypass)  │ Broken (this.method bypass)  │
  │ Spring default     │ No (Boot 2+ uses CGLIB)      │ Yes                          │
  │ Class name suffix  │ $Proxy42                     │ $$SpringCGLIB$$0             │
  └────────────────────┴──────────────────────────────┴──────────────────────────────┘

  Self-invocation failure mode:
    @Service class OrderService {
        @Transactional public void placeOrder(...) { ... }
        public void batchPlace(List<...> cmds) {
            for (var c : cmds) this.placeOrder(c);   // ← bypasses the proxy!
            // Each call goes to the original instance, not the proxy subclass,
            // so @Transactional is NOT applied. Each save() runs in its own tx,
            // or no tx at all if no tx was active.
        }
    }

  Fix: inject self via the ApplicationContext, or use AopContext.currentProxy(),
  or refactor batchPlace to call the public API.
```

The production failure mode of proxying is the "transaction not applied" bug. A developer adds `@Transactional` to a method, writes a test, and the test passes (because the test invokes the method through the proxy). In production, another method in the same class calls `this.placeOrder()` and the transaction is silently skipped — the database writes succeed (auto-commit), but if one fails, the previous writes are not rolled back. The fix is either `@Transactional(propagation = REQUIRES_NEW)` plus self-injection (`@Autowired OrderService self; self.placeOrder(...)`), or `AopContext.currentProxy()` (requires `@EnableAspectJAutoProxy(exposeProxy = true)`).

### Writing a decoupled Domain Service injecting outbound infrastructure adapters via Constructor Injection

The `OrderService` above is the canonical example of a decoupled domain service. It depends on three interfaces — `OrderRepository`, `PaymentGateway`, `OrderEventPublisher` — not on any concrete implementation. The container resolves each interface to a concrete bean at startup, based on `@Profile` and `@ConditionalOnProperty` annotations. In production with `--spring.profiles.active=prod`, the wiring is: `OrderService(PostgresOrderRepository, StripePaymentGateway, KafkaOrderEventPublisher)`. In a unit test, the wiring is `OrderService(mockRepo, mockPay, mockEvents)` — no Spring context needed.

Constructor injection makes the dependency graph explicit. A developer reading `OrderService`'s constructor sees immediately that it needs a repository, a payment gateway, and an event publisher — there is no hidden `@Autowired` field to discover later. The class is also immutable: every field is `final`, so it is thread-safe by construction. And it is testable: a unit test constructs `new OrderService(mockRepo, mockPay, mockEvents)` in one line, with no `SpringExtension` and no application context startup.

```java
// Unit test — no Spring context needed, runs in milliseconds
@Test
void placeOrder_charges_payment_gateway_and_publishes_event() {
    var repo = mock(OrderRepository.class);
    var pay = mock(PaymentGateway.class);
    var events = mock(OrderEventPublisher.class);
    var svc = new OrderService(repo, pay, events);

    var cmd = new NewOrderCmd(UUID.randomUUID(), new BigDecimal("99.99"));
    var order = svc.placeOrder(cmd.userId(), cmd.total());

    verify(repo).save(any(Order.class));
    verify(pay).charge(eq(order.getId()), eq(new BigDecimal("99.99")));
    verify(events).publish(argThat(e -> e instanceof OrderPlaced op && op.orderId().equals(order.getId())));
}
```

The production failure mode of decoupled services is the "interface with one implementation" smell. A service with `OrderRepository` interface and `PostgresOrderRepository` as the only implementation looks decoupled but is not — the abstraction carries no information beyond "this is what PostgresOrderRepository implements". The fix is to wait until you have a second implementation (a test double, a DynamoDB adapter) before extracting the interface; until then, depend on the concrete class. The test still works because mocks are subclasses of the concrete class.

## How It Works

The container builds the dependency graph at startup. For `OrderService`, the graph is: `OrderService → (OrderRepository, PaymentGateway, OrderEventPublisher)`. Each of those has its own dependencies: `PostgresOrderRepository → JdbcTemplate → DataSource → HikariConfig`. The container walks this DAG in topological order: `HikariConfig` first (no dependencies), then `DataSource`, then `JdbcTemplate`, then `PostgresOrderRepository`, then `StripePaymentGateway` (needs `RestClient` and `@Value("${stripe.api-key}")`), then `OrderEventPublisher`, then finally `OrderService`.

When `OrderService` is instantiated, Spring invokes its constructor reflectively: `Constructor.newInstance(repo, pay, events)`. The `OrderService` instance is then passed to every registered `BeanPostProcessor.postProcessAfterInitialization` call. `AnnotationAwareAspectJAutoProxyCreator` (the post-processor that drives `@Transactional`) inspects the bean, sees the `@Transactional` annotation on `placeOrder`, generates a CGLIB subclass that wraps `placeOrder` in a `TransactionInterceptor` advice, and returns the proxy. The proxy — not the original instance — is what gets cached in `singletonObjects` and injected into every other bean that depends on `OrderService`.

When `OrderController` (annotated `@RestController`) is later instantiated, its `@Autowired OrderService service` field is resolved from the container — Spring returns the cached proxy. When the controller invokes `service.placeOrder(...)`, the call goes to the proxy, which begins a transaction, delegates to the real `OrderService.placeOrder`, commits the transaction on return, or rolls back on exception.

## Break It

> [!danger] Load-test failure modes you must reproduce
> Do not move on to the delta translations until you have personally reproduced each of the following in your anchor implementation:
>
> 1. **Self-invocation breaks `@Transactional`.** Add a method `batchPlace(List<NewOrderCmd> cmds)` to `OrderService` that loops and calls `this.placeOrder(c)`. Annotate it `@Transactional`. From a controller, call `batchPlace` with 10 commands. Throw an exception on the 5th — all 10 should roll back, but only the 5th does (the first 4 were committed individually because `this.placeOrder()` bypassed the proxy). Fix: inject self via `@Lazy @Autowired OrderService self;` and call `self.placeOrder(c)`.
> 2. **`@Profile` activation bug.** Run with `--spring.profiles.active=prod` but forget to set `--stripe.api-key`. Spring boots, finds `StripePaymentGateway` with `@Profile("prod")`, tries to construct it, `@Value("${stripe.api-key}")` resolves to `${stripe.api-key}` literally (no value), `StripePaymentGateway` calls `https://api.stripe.com/v1/charges` with `Bearer ${stripe.api-key}`, Stripe returns 401. Fix: add `@Value("${stripe.api-key:}")` with a default, or fail fast in the constructor: `if (apiKey == null || apiKey.isBlank()) throw new IllegalStateException("stripe.api-key required");`.
> 3. **`@PreDestroy` skipped on `SIGKILL`.** The container registers a JVM shutdown hook (`Runtime.getRuntime().addShutdownHook`) for `SIGTERM`. Send `kill -9 <pid>` (SIGKILL) — the JVM exits immediately, `@PreDestroy` is not called, HikariCP's connection pool is not closed, Postgres holds the connections until `idle_timeout` (default 4 minutes). Metric: `pg_stat_activity` shows N rows for the dead process. Fix: never use `kill -9` in production; use `kill -TERM` and wait for the JVM to exit cleanly (Spring Boot's `spring.lifecycle.timeout-per-shutdown-phase=30s` gives `@PreDestroy` 30s to run).
> 4. **Cycle via `@Lazy`.** Add `@Lazy @Autowired OrderAuditService audit;` to `OrderService` and `@Lazy @Autowired OrderService orders;` to `OrderAuditService`. Spring wires both with proxies — no `BeanCurrentlyInCreationException` because `@Lazy` defers resolution. Run a load test calling `placeOrder` 10k times/s — each call's `audit.log()` invocation goes through the `@Lazy` proxy, which does a `ThreadLocal` lookup on every call. Profile: ~100ns per call × 2 (both sides) × 10k = 2ms/s of CPU. Fix: break the cycle by extracting `OrderAuditLog` into a third class that both depend on.

## Profiling Hooks

While the load test runs, collect:

- **JVM**: `jstack <pid>` for thread dumps — look for threads in `BLOCKED` on `OrderService$$SpringCGLIB$$0.placeOrder` (the proxy's synchronisation); `jmap -dump:live,format=b,file=heap.hprof <pid>` for heap dumps — look for retained `$$SpringCGLIB$$` instances (one per proxied bean, expected) and for unexpected bean instances (more than one `OrderService` indicates a prototype scope leak); `jstat -gcutil <pid> 1000` for GC pressure — the per-proxy `AdvisedSupport` field set is ~400 bytes per proxied bean.
- **OS**: `pidstat -d -r -u -w 1` for per-process CPU/RSS/context-switches; `vmstat 1` for run-queue; `cat /proc/<pid>/status | grep Threads` for JVM thread count.
- **App**: `/actuator/beans` (lists every bean with its scope and type — look for unexpected singletons); `/actuator/metrics/tomcat.threads.busy`; `/actuator/threaddump` (formatted thread dump — look for `BLOCKED` threads holding transaction locks); `/actuator/configprops` (shows resolved `@Value` and `@ConfigurationProperties` — check that `stripe.api-key` is not literally `${stripe.api-key}`).
