# 05.06.03. Deep Anchor Implementation Spring Security

## Why This Is the Anchor

This note is the **deep anchor implementation** — the place where you build the concept in Spring Boot with production-grade depth. Per the Anchor and Delta protocol ([[00.02. The Anchor and Delta Learning Protocol]]), you must break this implementation before moving to the delta notes. The point is to acquire scars: real experience with the failure modes that this concept produces under load.

Spring Boot is the anchor because it forces you to confront strict types, multi-threading, reflection proxies, bytecode generation, the JVM memory model, and explicit architectural decisions. If you can build this in Spring Boot, you can build it anywhere.

## What You Will Build

The implementation covers:

- The Spring Security Filter Chain (`SecurityFilterChain`, `DelegatingFilterProxy`).
- Core components: `AuthenticationManager`, `AuthenticationProvider`, `UserDetailsService`, `SecurityContextHolder`.
- Implementing a custom JWT Authentication Filter parsing Bearer tokens and establishing security contexts.

## Anchor Implementation (Spring Boot)

The code below is a complete, compilable Spring Boot 3.2 resource server. It wires `SecurityFilterChain`, a `JwtAuthenticationFilter` registered before `UsernamePasswordAuthenticationFilter`, a `DaoAuthenticationProvider` backed by a `UserDetailsService` and a `BCryptPasswordEncoder`, an `AuthenticationManager` exposed as a bean, and a `/auth/login` endpoint that issues a JWT. Type it out, then run it against the load tests in the Break It section.

```java
// build.gradle (relevant deps)
// implementation 'org.springframework.boot:spring-boot-starter-security'
// implementation 'org.springframework.boot:spring-boot-starter-web'
// implementation 'io.jsonwebtoken:jjwt-api:0.12.5'
// runtimeOnly    'io.jsonwebtoken:jjwt-impl:0.12.5'
// runtimeOnly    'io.jsonwebtoken:jjwt-jackson:0.12.5'

package com.example.auth;

import io.jsonwebtoken.Claims;
import io.jsonwebtoken.Jws;
import io.jsonwebtoken.Jwts;
import io.jsonwebtoken.io.Decoders;
import io.jsonwebtoken.security.Keys;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.stereotype.Service;

import javax.crypto.SecretKey;
import java.time.Instant;
import java.util.Date;
import java.util.List;

@Service
public class JwtService {

    private final SecretKey key;
    private final long accessTtlMillis;
    private final String issuer;

    public JwtService(
            @Value("${jwt.secret}") String secret,
            @Value("${jwt.access-ttl:900}") long accessTtlSec,
            @Value("${jwt.issuer:https://auth.example.com}") String issuer) {
        this.key = Keys.hmacShaKeyFor(Decoders.BASE64.decode(secret));   // 256-bit HS256
        this.accessTtlMillis = accessTtlSec * 1000;
        this.issuer = issuer;
    }

    public String issue(String subject, List<String> roles) {
        Instant now = Instant.now();
        return Jwts.builder()
                .issuer(issuer)
                .audience().add("api").and()
                .subject(subject)
                .claim("roles", roles)
                .issuedAt(Date.from(now))
                .expiration(Date.from(now.plusMillis(accessTtlMillis)))
                .signWith(key, Jwts.SIG.HS256)
                .compact();
    }

    public Jws<Claims> parse(String token) {
        return Jwts.parser()
                .verifyWith(key)
                .requireIssuer(issuer)
                .requireAudience("api")
                .build()
                .parseSignedClaims(token);          // throws JwtException on any failure
    }
}
```

```java
package com.example.auth;

import jakarta.servlet.FilterChain;
import jakarta.servlet.ServletException;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import org.springframework.security.authentication.UsernamePasswordAuthenticationToken;
import org.springframework.security.core.authority.SimpleGrantedAuthority;
import org.springframework.security.core.context.SecurityContextHolder;
import org.springframework.security.web.authentication.WebAuthenticationDetailsSource;
import org.springframework.stereotype.Component;
import org.springframework.web.filter.OncePerRequestFilter;

import java.io.IOException;
import java.util.List;

@Component
public class JwtAuthenticationFilter extends OncePerRequestFilter {

    private final JwtService jwt;

    public JwtAuthenticationFilter(JwtService jwt) {
        this.jwt = jwt;
    }

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain chain) throws ServletException, IOException {
        String header = request.getHeader("Authorization");
        if (header == null || !header.startsWith("Bearer ")) {
            chain.doFilter(request, response);          // anonymous; let authz decide
            return;
        }
        String token = header.substring(7);
        try {
            var claims = jwt.parse(token).getPayload();
            var authorities = ((List<?>) claims.get("roles", List.class)).stream()
                    .map(Object::toString)
                    .map(r -> new SimpleGrantedAuthority("ROLE_" + r))
                    .toList();
            var auth = new UsernamePasswordAuthenticationToken(
                    claims.getSubject(), null, authorities);
            auth.setDetails(new WebAuthenticationDetailsSource().buildDetails(request));
            SecurityContextHolder.getContext().setAuthentication(auth);
        } catch (Exception e) {
            SecurityContextHolder.clearContext();
            response.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
            response.setContentType("application/json");
            response.getWriter().write("{\"error\":\"invalid_token\"}");
            return;
        }
        chain.doFilter(request, response);
    }
}
```

package com.example.auth;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.authentication.AuthenticationManager;
import org.springframework.security.authentication.dao.DaoAuthenticationProvider;
import org.springframework.security.config.annotation.authentication.configuration.AuthenticationConfiguration;
import org.springframework.security.config.annotation.method.configuration.EnableMethodSecurity;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.http.SessionCreationPolicy;
import org.springframework.security.core.userdetails.UserDetailsService;
import org.springframework.security.core.userdetails.UsernameNotFoundException;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.security.web.SecurityFilterChain;
import org.springframework.security.web.authentication.UsernamePasswordAuthenticationFilter;

@Configuration
@EnableMethodSecurity          // enables @PreAuthorize on controllers/services
public class SecurityConfig {

    private final JwtAuthenticationFilter jwtFilter;

    public SecurityConfig(JwtAuthenticationFilter jwtFilter) {
        this.jwtFilter = jwtFilter;
    }

    @Bean
    SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .csrf(csrf -> csrf.disable())                       // API uses Bearer, not cookies
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/auth/login", "/actuator/health").permitAll()
                .requestMatchers("/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated())
            .addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class);
        return http.build();
    }

    @Bean
    DaoAuthenticationProvider authProvider(UserDetailsService uds, PasswordEncoder encoder) {
        DaoAuthenticationProvider provider = new DaoAuthenticationProvider();
        provider.setUserDetailsService(uds);
        provider.setPasswordEncoder(encoder);
        return provider;
    }

    @Bean
    AuthenticationManager authenticationManager(AuthenticationConfiguration cfg) throws Exception {
        return cfg.getAuthenticationManager();
    }

    @Bean
    PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder(12);   // work factor 12 ≈ 250ms on 2023-era x86
    }
}

package com.example.auth;

import org.springframework.security.core.userdetails.User;
import org.springframework.security.core.userdetails.UserDetails;
import org.springframework.security.core.userdetails.UserDetailsService;
import org.springframework.security.core.userdetails.UsernameNotFoundException;
import org.springframework.stereotype.Service;

import java.util.Map;

@Service
public class JpaUserDetailsService implements UserDetailsService {

    private final UserRepository repo;   // your Spring Data JPA repository

    public JpaUserDetailsService(UserRepository repo) { this.repo = repo; }

    @Override
    public UserDetails loadUserByUsername(String email) throws UsernameNotFoundException {
        var u = repo.findByEmail(email)
                .orElseThrow(() -> new UsernameNotFoundException(email));
        return User.withUsername(u.getEmail())
                   .password(u.getPasswordHash())        // BCrypt hash, never the plaintext
                   .roles(u.getRoles().toArray(String[]::new))
                   .accountExpired(!u.isActive())
                   .accountLocked(u.isLocked())
                   .build();
    }
}

package com.example.auth;

import org.springframework.security.authentication.AuthenticationManager;
import org.springframework.security.authentication.UsernamePasswordAuthenticationToken;
import org.springframework.security.core.Authentication;
import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/auth")
public class AuthController {

    private final AuthenticationManager am;
    private final JwtService jwt;

    public AuthController(AuthenticationManager am, JwtService jwt) {
        this.am = am;
        this.jwt = jwt;
    }

    public record LoginRequest(String email, String password) {}
    public record LoginResponse(String accessToken, String tokenType, long expiresIn) {}

    @PostMapping("/login")
    public LoginResponse login(@RequestBody LoginRequest req) {
        Authentication auth = am.authenticate(
            new UsernamePasswordAuthenticationToken(req.email(), req.password()));
        var roles = auth.getAuthorities().stream()
                .map(a -> a.getAuthority().replace("ROLE_", ""))
                .toList();
        String token = jwt.issue(auth.getName(), roles);
        return new LoginResponse(token, "Bearer", 900);
    }
}

## What This Is

Spring Security is the deepest, most configurable, and most foot-gun-prone authentication framework in the JVM ecosystem. This note is the **deep anchor implementation** that builds JWT-based stateless authentication end-to-end in Spring Boot 3.2, covering the filter chain, the core component collaboration (`AuthenticationManager` → `AuthenticationProvider` → `UserDetailsService` → `PasswordEncoder`), the custom JWT filter that bridges the Bearer token to the `SecurityContext`, and the `@AuthenticationPrincipal` injection that surfaces the user in controllers. After you build this and break it under load, the delta translations to Express/Django/Flask/Laravel become trivial — every ecosystem solves the same problem with different syntax, but Spring forces you to make every architectural choice explicit.

## The Details

### The Spring Security Filter Chain (`SecurityFilterChain`, `DelegatingFilterProxy`)

Spring Security is implemented as a single servlet `Filter` registered in the servlet container under the name `springSecurityFilterChain`. That filter is a `DelegatingFilterProxy` — a thin Spring-provided class whose only job is to look up a bean named `springSecurityFilterChain` from the `ApplicationContext` and delegate `doFilter()` to it. The actual work happens in `FilterChainProxy`, which holds an ordered list of `SecurityFilterChain` beans. Each `SecurityFilterChain` is a matcher + a list of filters: when a request arrives, `FilterChainProxy` walks the list, finds the first chain whose `RequestMatcher` matches the request path, and runs that chain's filters in order. The default Spring Boot configuration installs one `SecurityFilterChain` matching `/**`; you can register multiple beans for path-segment-specific policies (e.g., a stateless chain for `/api/**` and a session-based chain for `/admin/**`).

The filter list inside a `SecurityFilterChain` is not arbitrary — it is a fixed sequence of Spring Security internals, and your custom filters slot into specific positions in that sequence. The order, in a typical stateless config, is: `DisableEncodeUrlFilter` → `ForceEagerSessionCreationFilter` → `ChannelProcessingFilter` (HTTPS) → `WebAsyncManagerIntegrationFilter` → `SecurityContextHolderFilter` → `HeaderWriterFilter` → `CorsFilter` → `CsrfFilter` (disabled for JWT APIs) → `LogoutFilter` → `JwtAuthenticationFilter` (your custom one, registered `addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class)`) → `UsernamePasswordAuthenticationFilter` → `DefaultLoginPageGeneratingFilter` → `DefaultLogoutPageGeneratingFilter` → `RequestCacheAwareFilter` → `SecurityContextHolderAwareRequestFilter` → `AnonymousAuthenticationFilter` → `ExceptionTranslationFilter` → `AuthorizationFilter` → the actual servlet/handler. Each filter calls `chain.doFilter(req, res)` to invoke the next; if any filter writes to the response and returns without calling `chain.doFilter`, the chain short-circuits and the request never reaches your controller.

```text
  HTTP Request
      │
      ▼
  Servlet Container (Tomcat)
      │
      ▼
  DelegatingFilterProxy("springSecurityFilterChain")
      │  looks up bean by name from ApplicationContext
      ▼
  FilterChainProxy
      │  iterates List<SecurityFilterChain>
      │  picks the first whose RequestMatcher.matches(request)
      ▼
  SecurityFilterChain (your @Bean)
      │  runs its List<Filter> in order:
      │
      │  CsrfFilter (skipped — disabled)
      │      │
      │      ▼
      │  JwtAuthenticationFilter  ←  your custom filter
      │      │  parses Authorization: Bearer, verifies signature,
      │      │  sets SecurityContextHolder.context.authentication
      │      ▼
      │  UsernamePasswordAuthenticationFilter (skipped — no form login)
      │      │
      │      ▼
      │  ExceptionTranslationFilter  ←  catches AuthenticationException
      │      │                          and AuthorizationException,
      │      │                          dispatches to EntryPoints
      │      ▼
      │  AuthorizationFilter  ←  checks authorizeHttpRequests rules
      │      │
      │      ▼
      └─► DispatcherServlet → @RestController handler
```

The production failure mode here is **filter ordering**. If you register your JWT filter with `addFilterAfter(jwtFilter, UsernamePasswordAuthenticationFilter.class)`, the `AuthorizationFilter` runs *before* your filter sets the authentication, and every request gets a 401. If you register it with `addFilterAt(jwtFilter, UsernamePasswordAuthenticationFilter.class)`, you replace Spring's form-login filter (probably what you want), but you also inherit its position-sensitive behavior around session fixation. The safe idiom is `addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class)` — your filter runs early enough that the `AuthorizationFilter` sees the populated `SecurityContext`, and Spring's form-login filter is preserved for non-API paths if you ever add them. The diagnostic when this goes wrong: enable `org.springframework.security=DEBUG` and read the filter chain log line that Spring prints at startup — it lists every filter in order, and your `JwtAuthenticationFilter` must appear before `UsernamePasswordAuthenticationFilter`.

### Core components: `AuthenticationManager`, `AuthenticationProvider`, `UserDetailsService`, `SecurityContextHolder`.

Spring Security splits authentication into four collaborating types, and understanding their division of labor is the difference between writing Spring Security config that compiles and writing Spring Security config that you can debug at 3 a.m. The **`AuthenticationManager`** is the entry point — a one-method interface: `Authentication authenticate(Authentication auth) throws AuthenticationException`. It is a router: it does not actually verify credentials; it iterates its list of `AuthenticationProvider`s and delegates to the first one that `supports()` the submitted `Authentication` subclass. The default implementation, `ProviderManager`, holds an ordered list of providers and returns the first non-null `Authentication` (with `authenticated=true` and the authorities populated).

The **`AuthenticationProvider`** does the actual work. The most common one is `DaoAuthenticationProvider` ("DAO" = Data Access Object), which: (1) takes a `UsernamePasswordAuthenticationToken` with raw credentials, (2) calls `UserDetailsService.loadUserByUsername(username)` to fetch the persisted `UserDetails` (which contains the password hash), (3) delegates to the `PasswordEncoder.matches(rawPassword, hashedPassword)` to verify, (4) on success, returns a new `UsernamePasswordAuthenticationToken` marked `authenticated=true` with the user's authorities; on failure, throws `BadCredentialsException`. You almost never write your own `AuthenticationProvider` — you wire `DaoAuthenticationProvider` with your `UserDetailsService` and your `PasswordEncoder`, and Spring does the rest. Custom providers are reserved for non-username/password flows (SMS OTP, WebAuthn, SAML).

```text
  am.authenticate(UsernamePasswordAuthenticationToken(email, password))
      │
      ▼
  ProviderManager.iterate providers
      │
      ├─ DaoAuthenticationProvider.supports(UsernamePasswordAuthenticationToken)? YES
      │
      ▼
  DaoAuthenticationProvider.authenticate(auth)
      │
      ├─ userDetailsService.loadUserByUsername(email)
      │      └─ JpaUserDetailsService → UserRepository.findByEmail(email) → UserDetails
      │
      ├─ passwordEncoder.matches(rawPassword, userDetails.password)
      │      └─ BCryptPasswordEncoder(12).matches(...)  ≈ 250ms per call
      │
      ├─ (on success) return new UsernamePasswordAuthenticationToken(
      │                   userDetails, null, userDetails.authorities)
      │
      └─ (on failure) throw BadCredentialsException
```

The **`UserDetailsService`** is your one integration point with the database. It is a single-method interface: `UserDetails loadUserByUsername(String username) throws UsernameNotFoundException`. Spring's contract: return a fully-populated `UserDetails` (username, password hash, authorities, accountNonExpired, accountNonLocked, credentialsNonExpired, enabled) or throw `UsernameNotFoundException`. The `DaoAuthenticationProvider` then compares the password hash; you never see the plaintext password. The spring-security-core `User.UserBuilder` (`User.withUsername(...).password(...).roles(...).build()`) is the convenient constructor. A common production bug: returning a `UserDetails` with `accountLocked=true` (e.g., because you mis-mapped your `users.locked` column to `accountNonLocked` — note the inversion!) silently rejects every login with `LockedException`, and the user sees a generic "invalid credentials" message because Spring merges auth failures into one error to avoid user-enumeration leakage.

The **`SecurityContextHolder`** is the bridge between authentication and the rest of the request. It is a thread-local holder of the `SecurityContext`, which in turn holds the `Authentication` object. After your `JwtAuthenticationFilter` (or Spring's `UsernamePasswordAuthenticationFilter`) sets `SecurityContextHolder.getContext().setAuthentication(auth)`, every subsequent component in the request — the `AuthorizationFilter`, your `@PreAuthorize` AOP advice, the `@AuthenticationPrincipal` method-argument resolver — reads the authentication from this same thread-local. The strategy defaults to `MODE_THREADLOCAL`, which means the context does *not* propagate to spawned threads or `@Async` methods; for async work, you must either set `MODE_INHERITABLETHREADLOCAL` (which leaks into thread pools and is unsafe for pooled executors), or use `DelegatingSecurityContextRunnable` to explicitly propagate the context across the executor boundary. The classic failure: a `@PreAuthorize("hasRole('ADMIN')")` method called from `@Async` throws `AccessDeniedException` because the thread-pool thread has no `SecurityContext`. The fix is `SecurityContextHolder.getContext()` capture in the calling thread + `DelegatingSecurityContextExecutor` wrapping the executor.

### Implementing a custom JWT Authentication Filter parsing Bearer tokens and establishing security contexts.

The `JwtAuthenticationFilter` is your hand-off point between the HTTP layer (where a Bearer token is just a string in a header) and the Spring Security layer (where an `Authentication` in the `SecurityContext` is what every downstream component expects). The contract: extend `OncePerRequestFilter` (which guarantees the filter runs exactly once per request, even under forwarded or error-dispatch paths that would otherwise re-invoke the chain), read the `Authorization` header, strip the `Bearer ` prefix, verify the JWT signature and claims via `JwtService.parse()`, and on success set the `SecurityContextHolder` context. On failure, clear the context (defense in depth — in case a previous filter left a stale one) and write a 401 response.

The subtlety that bites every team is **what to do when there is no `Authorization` header**. The wrong answer is to short-circuit with a 401 — that breaks public endpoints (`/auth/login`, `/actuator/health`, `/api/public/**`) which are configured `permitAll()` in the `SecurityFilterChain`. The correct answer is to call `chain.doFilter(req, res)` and let the request flow through to the `AuthorizationFilter`, which then applies the `permitAll`/`authenticated`/`hasRole` rules. Your JWT filter's job is to *authenticate when possible*, not to *authorize*. Another subtlety: filter exceptions must be handled inside the filter (catch + write 401), not thrown — the `ExceptionTranslationFilter` sits *after* your custom filter in the chain and cannot catch exceptions thrown above it. The third subtlety: the `SecurityContext` is a thread-local, and Tomcat reuses threads across requests, so you must clear the context either at the end of the request (via a `finally` block or by relying on Spring's `SecurityContextHolderFilter` which clears it after the chain returns) or risk cross-request authentication leakage.

```java
@Component
public class JwtAuthenticationFilter extends OncePerRequestFilter {

    private final JwtService jwt;

    public JwtAuthenticationFilter(JwtService jwt) { this.jwt = jwt; }

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {

        String header = req.getHeader("Authorization");
        if (header == null || !header.startsWith("Bearer ")) {
            chain.doFilter(req, res);                  // no token → anonymous; let authz decide
            return;
        }

        try {
            var claims = jwt.parse(header.substring(7)).getPayload();
            var authorities = ((List<?>) claims.get("roles", List.class)).stream()
                    .map(o -> new SimpleGrantedAuthority("ROLE_" + o))
                    .toList();
            var auth = new UsernamePasswordAuthenticationToken(
                    claims.getSubject(), null, authorities);
            auth.setDetails(new WebAuthenticationDetailsSource().buildDetails(req));
            SecurityContextHolder.getContext().setAuthentication(auth);
        } catch (JwtException | ClassCastException e) {
            SecurityContextHolder.clearContext();
            res.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
            res.setContentType("application/json");
            res.getWriter().write("{\"error\":\"invalid_token\"}");
            return;                                     // do NOT call chain.doFilter
        }

        chain.doFilter(req, res);
    }

    // Skip the filter for paths that never need JWT parsing — saves ~1ms per request
    @Override
    protected boolean shouldNotFilter(HttpServletRequest req) {
        String path = req.getRequestURI();
        return path.startsWith("/auth/login") || path.startsWith("/actuator/health");
    }
}
```

```text
  Production timing budget per request (HS256 JWT verify + filter overhead)
  ────────────────────────────────────────────────────────────────────────
  OncePerRequestFilter.doFilterInternal      ~5 µs   (servlet plumbing)
  JwtService.parse(token)                    ~50 µs  (HMAC-SHA256 verify)
  SecurityContextHolder.setAuthentication()  ~1 µs
  DispatcherServlet + handler dispatch        ~50-500 µs (controller + DB)
  ────────────────────────────────────────────────────────────────────────
  Total JWT overhead                          ~56 µs  (<0.2% of typical 25ms API call)
```

The production failure mode here is **cross-request authentication leakage**. If you set the `SecurityContext` and never clear it, Tomcat's thread pool reuses the thread for the next request, and that next request — which may not have sent a Bearer token — sees the *previous* user's `Authentication`. The bug is silent: the previous user was legitimate, the next request "succeeds" with the wrong identity, and the audit log shows the wrong `sub`. The fix is to ensure either (a) your filter always overwrites the context on entry (it does in the code above — but only if a token is present, so the leak still happens if a request without a token arrives on a thread whose previous request left a context), or (b) you rely on `SecurityContextHolderFilter` (a built-in Spring Security filter that clears the context after the chain returns). Spring Boot's default config includes (b), but if you disabled it or replaced the chain, you must clear manually. The diagnostic: hit `/me` twice in a row — once authenticated, once with the header stripped. The second should return 401; if it returns 200 with the first user's identity, you have a leak.

## How It Works

The `JwtService` constructs and parses tokens using JJWT 0.12. The `Keys.hmacShaKeyFor(Decoders.BASE64.decode(secret))` line enforces that the secret is at least 256 bits — JJWT throws if you pass a 16-byte string, which is the most common mistake. `Jwts.builder().signWith(key, Jwts.SIG.HS256)` pins the algorithm; if you ever want to switch to RS256, you change the `Key` and the `SecureDigestAlgorithm` together — there is no path where the verifier trusts the token's `alg` header. `Jwts.parser().verifyWith(key).requireIssuer(...).requireAudience(...).build().parseSignedClaims(token)` enforces signature, issuer, audience, and `exp`/`nbf`/`iat` validity in one call.

The `DaoAuthenticationProvider` is the bridge between `AuthenticationManager.authenticate()` (the entry point called from `AuthController.login`) and `UserDetailsService` + `PasswordEncoder`. It does the password check synchronously on the request thread; the BCrypt work factor of 12 costs ~250ms per login on a 2023-era CPU, which is fine for login but a disaster if you accidentally call `passwordEncoder.matches()` on every API request. The `@EnableMethodSecurity` annotation enables `@PreAuthorize` parsing via AOP proxies — every bean annotated with `@PreAuthorize` is wrapped in a CGLIB proxy that evaluates the SpEL expression before invoking the method.

## Break It

> [!danger] Load-test failure modes you must reproduce
> Do not move on to the delta translations until you have personally reproduced each of the following in your anchor implementation:
>
> 1. **Starve it.** Run `wrk -t8 -c200 -d60s http://localhost:8080/me` while logging in first to grab a token. Watch the Tomcat thread pool (`server.tomcat.threads.max=200` default) saturate; the metric is `tomcat_threads_busy_threads` hitting the max. The fix is either raising the pool or moving to a reactive (`WebFlux`) stack — but only after profiling.
> 2. **Leak it.** Comment out the `SecurityContextHolder.clearContext()` in the catch block. Hit `/me` with a valid token, then immediately hit `/me` without the `Authorization` header on the same Tomcat worker thread (use `wrk -H` with a single-threaded `-t1` to force thread reuse). The second request returns 200 with the previous user's identity. Restore the clear. Verify the leak is gone.
> 3. **Race it.** Spin up two threads that both call `AuthController.login` with the same email concurrently while you also run a DB migration that locks the `users` row. The `DaoAuthenticationProvider` blocks on `UserDetailsService.loadUserByUsername` until the lock releases; with enough concurrency, the Tomcat thread pool exhausts and downstream endpoints start timing out. The fix is a bounded `Semaphore` around login (one concurrent login per email) — a small-scale rate limiter.
> 4. **Fix it.** Restore the cleanup, add the semaphore, and re-run the load test. The graph should flatten. Keep both graphs.

## Profiling Hooks

While the load test runs, collect:

- **JVM**: `jstack <pid>` for thread dumps (look for threads stuck in `BCrypt.checkpw` — the work factor is the bottleneck); `jmap -dump:live,format=b,file=heap.hprof <pid>` for heap dumps; `jstat -gcutil <pid> 1000` for GC pressure.
- **OS**: `pidstat -d -r -u -w 1`, `vmstat 1`, `ss -tan state established | wc -l` (connection count — should stay below `server.tomcat.max-connections=8192`).
- **App**: `/actuator/metrics/tomcat.threads.busy`, `/actuator/metrics/tomcat.threads.current`, `/actuator/metrics/http.server.requests` (look for the 95th-percentile login latency — should be ~250ms, dominated by BCrypt), `/actuator/threaddump`.
