# 05.06.02. JSON Web Tokens (JWT) Architecture and Security

## What This Is

A **JSON Web Token (JWT)** is a compact, URL-safe, self-contained token format defined in RFC 7519 that lets a server statelessly prove the identity and claims of a client between two parties. It exists because HTTP is stateless: every request must independently prove who the caller is, and the historical alternative — a server-side session store keyed by a random cookie — requires either sticky sessions or a shared session DB (Redis, Memcached) behind every load balancer. A JWT moves that state into the token itself, so any backend replica can verify the caller without a database lookup. The cost is revocation: you cannot delete a JWT from a client's browser the way you can delete a session row server-side.

In the layered mental model, JWT sits in the framework layer (Section 05.06) directly above the cryptographic primitives in Section 03.03 (HMAC-SHA256, RSA-SHA256, ECDSA) and surfaces in every modern backend framework as either a hand-rolled filter (Spring Boot `OncePerRequestFilter`, Express `app.use((req,res,next)=>...)`, Django `BaseAuthentication`) or a framework-supplied module (`spring-boot-starter-oauth2-resource-server`, `djangorestframework-simplejwt`, Laravel Sanctum, `flask-jwt-extended`). The failure modes it governs are among the most exploited on the internet: the `alg: none` bypass, weak HMAC secret brute-forcing, key confusion between RS256 and HS256, token replay, and the inability to revoke an issued token before its `exp` claim fires. This note covers the structure, signing algorithms, vulnerability classes, and the refresh-token pattern that makes revocation tractable.

## The Details

### JWT Structure: Header (Algorithm, Type), Payload (Registered, Public, Private Claims), Signature.

A JWT is exactly three Base64URL-encoded JSON objects joined by dots — `header.payload.signature`. The **header** is a small JSON object with two mandatory fields, `alg` (the signing algorithm) and `typ` (almost always `"JWT"`). The **payload** is a JSON object of claims — statements about the subject (the user), the issuer (the auth server), and the token's lifetime. The **signature** is the cryptographic proof that the header and payload were not modified in transit. None of the three parts are encrypted: anyone with the token can `base64url-decode` the payload and read every claim. The signature only prevents *tampering*, not *disclosure*. If you need confidentiality, you must layer JWE (JSON Web Encryption, RFC 7516) on top, which most teams do not — they treat the JWT as a signed, public statement of identity and never put a secret inside it.

Base64URL encoding differs from standard Base64 in two ways: `+` is replaced with `-` (so the token is safe in a URL query string), `/` is replaced with `_`, and the `=` padding is stripped. This is why a JWT can be placed in an `Authorization: Bearer <token>` header, in a `?token=...` query parameter, or in a cookie value without further encoding. The encoding is reversible; it is not cryptographic. The three-part structure exists so a verifier can: (1) parse the header to learn which algorithm to use, (2) parse the payload to read the claims, (3) recompute the signature over `base64url(header) + "." + base64url(payload)` and compare it to the third segment. The verifier never trusts the payload until the signature matches.

The **registered claims** defined in RFC 7519 §4.1 are the load-bearing ones. `iss` (issuer) identifies who minted the token; `sub` (subject) is the user ID; `aud` (audience) names which API the token is for; `exp` (expiration time, seconds since epoch) is the hard kill date; `nbf` (not before) lets you mint a token that becomes valid in the future; `iat` (issued at) is the mint time, useful for detecting token reuse; `jti` (JWT ID) is a unique nonce per token — the only hook you have for server-side revocation. **Public claims** are IANA-registered names like `email` or `roles` that are collision-resistant. **Private claims** are app-specific names you invent (`x-tenant-id`, `sid`) — these are the source of integration pain when two apps both mint a JWT with a `role` claim that means different things.

```text
  eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9        ← {"alg":"HS256","typ":"JWT"}
  .
  eyJzdWIiOiIxMjM0IiwibmFtZSI6IkFsaWNlIi      ← {"sub":"1234","name":"Alice",
   LCJpYXQiOjE2OTk5OTk5OTksImV4cCI6MTcw        "iat":1699999999,
   MDAwMDAwMCwiYXVkIjoiYXBpIn0                  "exp":1700000000,
                                                "aud":"api"}
  .
  SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c   ← HMAC-SHA256(
                                                     base64url(header) + "." +
                                                     base64url(payload),
                                                     SECRET
                                                   )
```

The production failure mode here is treating the payload as confidential. If you put a `password_hash` or an internal `ssn` claim in a JWT, every JavaScript on every page the user opens can read it (`atob(token.split('.')[1])`), and every proxy in the request path logs it. The Capital One 2019 breach exposed this class of mistake at scale: tokens flowed through WAFs and were captured. The rule is ironclad: **a JWT is a signed postcard, not an envelope.** Anything you would not write on a postcard goes in a server-side store keyed by `sub`.

### Cryptographic Signing: Symmetric HMAC (HS256) vs. Asymmetric RSA/ECDSA (RS256/ES256) with public/private key pairs.

JWT signing algorithms split into two families. **Symmetric** algorithms (the `HS*` family — HS256, HS384, HS512) use one shared secret for both signing and verifying: the signer computes `HMAC-SHA256(secret, message)` and the verifier recomputes the same thing with the same secret. **Asymmetric** algorithms (the `RS*` and `ES*` families — RS256, RS384, RS512, ES256, ES384, ES512, plus EdDSA with Ed25519) use a private key to sign and a public key to verify: only the issuer holds the private key, and every verifier can use the freely-distributable public key. The choice is not aesthetic — it dictates who can mint tokens.

In a monolith with one auth server and one API server in the same codebase, HS256 with a 256-bit secret loaded from a vault is correct and fast. HMAC-SHA256 on a 1KB message runs in ~1µs on modern x86; RSA-2048 signing takes ~1ms (1000× slower) and verification ~0.1ms; ECDSA P-256 signs in ~0.2ms and verifies in ~0.5ms. In a microservice topology where ten services must each verify tokens, HS256 forces you to ship the same secret to all ten services — a compromise of any one service lets the attacker mint tokens for the entire fleet. RS256/ES256 lets you publish the public key as a JWKS (JSON Web Key Set) document at `https://auth.example.com/.well-known/jwks.json` and rotate the private key without touching the verifiers.

```text
  Topology: 1 issuer + N verifiers, all in one trust boundary
  ┌─────────┐    HS256 with shared 256-bit secret    ┌──────────┐
  │  Auth   │ ─────────────────────────────────────► │   API    │
  │ Service │            (both hold SECRET)          │  Service │
  └─────────┘                                         └──────────┘
  Pros: 1µs sign+verify, no key distribution
  Cons: any verifier can also mint tokens → no separation of duties

  Topology: 1 issuer + N verifiers, across trust boundaries
  ┌─────────┐  RS256: sign with PRIVATE key          ┌──────────┐
  │  Auth   │ ─────────────────────────────────────► │   API    │
  │ Service │  Verify with PUBLIC key (JWKS URL)     │  Service │
  └─────────┘                                         └──────────┘
  Pros: verifiers cannot mint; key rotation without redeploy
  Cons: 1000× slower sign, JWKS fetch + cache infra
```

The killer vulnerability that emerges from this split is the **algorithm confusion attack** (CVE-2015-9235 and its many rediscoveries). A server that accepts both HS256 and RS256 can be tricked if the verifier uses the public key *as the HMAC secret*. The attacker takes a token, changes `alg` from `RS256` to `HS256`, signs it with `HMAC-SHA256(public_key, message)`, and submits it. The server reads `alg: HS256`, fetches the same public key from its config, and verifies successfully — because the public key is not secret. Every modern library (the `jsonwebtoken` npm package, `jose`, `pyjwt`, `nimbus-jose-jwt`) now requires you to pin the accepted algorithms explicitly: `jwt.verify(token, key, { algorithms: ["RS256"] })`. Passing `algorithms: ["RS256", "HS256"]` together, or worse, omitting the parameter so the library trusts the token's own header, is the bug. The production failure mode is silent: tokens verify correctly, attackers authenticate as any user, and the only signal is an anomalous `alg` value buried in your access logs three weeks later.

### Vulnerabilities: The `none` algorithm attack, weak secret brute-forcing, claim tampering, token sidejacking.

The **`none` algorithm attack** is the canonical JWT disaster. RFC 7518 §3.1 permits `alg: "none"` for unsecured JWTs — tokens with no signature, intended for development or low-stakes contexts. The attack: an attacker takes a victim's token (or forges one from scratch), changes the payload's `sub` claim to `admin`, rewrites the header's `alg` to `none`, drops the signature segment entirely (leaving `header.payload.`), and submits it. A naive verifier reads `alg: none`, skips the signature check, and trusts the payload. The original `node-jsonwebtoken` library (CVE-2015-9235), `pyjwt` before 1.5.0, and several Ruby and Go libraries were all vulnerable. The fix is structural, not behavioral: never accept `none` in production, and *always* pass an explicit `algorithms` allow-list to the verifier. `jwt.verify(token, secret)` (no algorithms arg) is unsafe in old library versions because they fall back to trusting the header. `jwt.verify(token, secret, { algorithms: ["HS256"] })` is safe — the library rejects any other `alg` before it even looks at the signature.

```javascript
// VULNERABLE — trusts the header's alg field
const payload = jwt.verify(token, secret);

// VULNERABLE — accepts "none" if the header says so
const payload = jwt.verify(token, secret, { algorithms: ["HS256", "none"] });

// SAFE — pins the algorithm; "none" is structurally impossible
const payload = jwt.verify(token, secret, { algorithms: ["HS256"] });

// SAFE — also verifies the expected issuer/audience, not just the signature
const payload = jwt.verify(token, secret, {
  algorithms: ["HS256"],
  issuer: "https://auth.example.com",
  audience: "api",
});
```

**Weak secret brute-forcing** is the second class. HS256 with a 16-character ASCII secret has ~106 bits of entropy on paper, but in practice teams commit `JWT_SECRET=changeme` or derive the secret from a project name (`myapp-secret-2023`) which cracks in seconds on a GPU. The tool `jwt-cracker` (and the more capable `hashcat -m 16500`) brute-forces HS256 secrets at 500M guesses/sec on a single RTX 4090 — a 6-character alphanumeric secret falls in under a minute. The mitigation is twofold: generate the secret with `openssl rand -base64 48` (288 bits of entropy), and load it from a secret manager (AWS Secrets Manager, Vault, Doppler) rather than a `.env` file checked into git. If you ever see `JWT_SECRET=` in a repository's history, rotate the secret immediately — anyone with that history can forge every token your system has ever issued.

**Claim tampering** is what the signature is supposed to prevent, but it fails when verifiers trust claims they should re-derive. A common pattern: the auth server puts `role: "admin"` in the payload, and the API trusts it. An attacker who obtains any valid token cannot change `role` without invalidating the signature — but if they compromise the secret (via weak-secret brute-force, log leakage, or a compromised developer laptop), they can re-mint the token with any claim. The defense is the principle of least authority: the token should carry only identity (`sub`, `iss`, `aud`, `exp`), and the API should fetch authorization (`role`, `permissions`) from its own database on every request, keyed by `sub`. This costs one Redis GET per request (~0.2ms); it is the difference between a token compromise being a "forge any identity" event and a "forge identity, but the API still checks your role" event.

**Token sidejacking** is the client-side attack: an XSS payload in a third-party script steals `localStorage.getItem('jwt')` and exfiltrates it to `evil.com`. The token is then replayed from the attacker's machine for the rest of its lifetime. Mitigations: (1) store the access token in a JavaScript-inaccessible `HttpOnly; Secure; SameSite=Strict` cookie, accepting the CSRF implications; (2) bind the token to a **proof-of-possession** fingerprint (a random value set at login, stored in a cookie and sent in an `X-Token-Binding` header, with the server hashing them together and storing the hash in the payload); (3) keep access-token lifetime short (5-15 minutes) so a stolen token dies quickly. The production failure mode is a quiet one: there is no anomaly in your logs, because the attacker's requests look identical to the victim's. The only signal is impossible-concurrent-use — the same `jti` arriving from two IPs within a minute — which almost no one monitors.

### Refresh Token Pattern: Short-lived Access Tokens (5-15 mins) paired with rotating Refresh Tokens stored in secure data stores.

JWTs are stateless, which is their great strength and their great weakness: there is no server-side row to delete when you want to revoke one. Once issued, a JWT is valid until its `exp` claim fires, no matter what the server does afterward. If you discover at 14:00 that a token was stolen at 13:55, you have until the token's `exp` (typically 14:10) to watch the attacker operate — there is no `invalidate()` call. The **refresh token pattern** is the standard workaround. The auth server issues *two* tokens at login: a short-lived **access token** (5-15 minute `exp`) that the API verifies statelessly, and a long-lived **refresh token** (7-30 days) that is *stateful* — stored server-side in a Redis set or a database row keyed by `jti`. The access token carries identity into every API call; the refresh token is presented only to the auth server's `/token` endpoint to mint a new access token when the old one expires.

The rotation rule is what makes revocation tractable. On every successful refresh, the auth server (1) deletes the presented refresh token from the server-side store, (2) issues a new refresh token, (3) writes the new one back to the store. If a refresh token is presented twice — once by the legitimate client, once by an attacker who stole it — the second attempt finds the row already deleted, and the auth server revokes the *entire session*: it deletes every refresh token tied to that `sub`'s session ID and forces the user to log in again. This is called **refresh token reuse detection** and it is the only structural defense against a stolen refresh token short of dropping the user entirely. The OAuth 2.0 working group formalized this in RFC 6749 §10.4 and refined it in RFC 9700 (BCP for OAuth 2.0).

```text
  T=0   POST /login { user, password }
        → 200 OK
          Set-Cookie: refresh=xyz; HttpOnly; Secure; SameSite=Strict; Max-Age=2592000
          { "access": "eyJhbGc...", "expires_in": 900 }

  T=14m GET /api/orders  Authorization: Bearer eyJhbGc...
        → 200 OK   (access token still valid)

  T=16m GET /api/orders  Authorization: Bearer eyJhbGc...
        → 401 token_expired

  T=16m POST /token  Cookie: refresh=xyz
        → 200 OK
          Set-Cookie: refresh=abc; HttpOnly; ...   ← rotation: xyz deleted, abc issued
          { "access": "eyJhbGc...(new)", "expires_in": 900 }

  T=16m (attacker replays stolen xyz)
        POST /token  Cookie: refresh=xyz
        → 401 invalid_grant   ← reuse detected → revoke session, force re-login
```

Storage of the refresh token is the load-bearing decision. Storing it in `localStorage` exposes it to XSS — the same XSS that steals an access token now also steals a 30-day ticket. Storing it in an `HttpOnly; Secure; SameSite=Strict` cookie protects it from JavaScript but introduces CSRF risk on the `/token` endpoint, mitigated by requiring a custom header (`X-Requested-With`) that a cross-site form cannot set. For first-party SPAs (your frontend on `app.example.com` calling your API on `api.example.com`), the cookie approach with `SameSite=Lax` is the modern default — it is what Laravel Sanctum, Django's `django-rest-framework-simplejwt` with cookie storage, and Spring Security's `TokenEndpoint` all support. For third-party clients (a mobile app you ship, a partner integration), use an opaque refresh token returned in the JSON body and stored in the platform's secure storage (iOS Keychain, Android Keystore), never in a cookie.

The production failure mode here is **silent session fixation**. If you implement refresh tokens without rotation, a stolen refresh token is valid for 30 days, and reuse detection never fires. The auth server sees `refresh=xyz` presented every 14 minutes for a month, and every presentation looks legitimate because the same value is reused indefinitely. The attacker has the same lifetime as the legitimate user. The metric that reveals this is **refresh token cardinality**: count distinct `jti` values presented per `sub` per 24h. If it is more than 1, you have a reuse problem — either a bug in your rotation (the new token isn't being persisted) or an active attacker. Alert on it.

## Cross-Ecosystem Code

The same concept implemented in all four target ecosystems. Read them side by side — the shape is identical, only the syntax differs.

**Spring Security (Anchor) — JWT filter:**
```java
@Component
@RequiredArgsConstructor
class JwtAuthFilter extends OncePerRequestFilter {
    private final JwtService jwt;

    @Override
    protected void doFilterInternal(HttpServletRequest req,
                                    HttpServletResponse res,
                                    FilterChain chain) throws ServletException, IOException {
        String header = req.getHeader("Authorization");
        if (header != null && header.startsWith("Bearer ")) {
            String token = header.substring(7);
            try {
                Claims claims = jwt.parse(token);   // verifies signature + exp + aud
                UsernamePasswordAuthenticationToken auth =
                    new UsernamePasswordAuthenticationToken(
                        claims.getSubject(), null,
                        claims.get("roles", List.class).stream()
                              .map(r -> new SimpleGrantedAuthority("ROLE_" + r))
                              .toList());
                SecurityContextHolder.getContext().setAuthentication(auth);
            } catch (JwtException e) {
                res.setStatus(401);
                res.getWriter().write("{\"error\":\"invalid_token\"}");
                return;
            }
        }
        chain.doFilter(req, res);
    }
}
```

**Express (Delta):**
```typescript
import jwt, { JwtPayload } from "jsonwebtoken";

interface AuthenticatedRequest extends Request {
  user?: JwtPayload;
}

function authMiddleware(req: AuthenticatedRequest, res: Response, next: NextFunction) {
  const header = req.headers.authorization;
  if (!header?.startsWith("Bearer ")) return next();  // anonymous

  const token = header.slice(7);
  try {
    req.user = jwt.verify(token, process.env.JWT_SECRET!, {
      algorithms: ["HS256"],           // pin the algorithm
      issuer: "https://auth.example.com",
      audience: "api",
    });
    next();
  } catch (e) {
    res.status(401).json({ error: "invalid_token" });
  }
}

app.use(authMiddleware);
```

**Django (Delta):**
```python
# settings.py
REST_FRAMEWORK = {
    "DEFAULT_AUTHENTICATION_CLASSES": [
        "rest_framework_simplejwt.authentication.JWTAuthentication",
    ],
}
SIMPLE_JWT = {
    "ACCESS_TOKEN_LIFETIME": timedelta(minutes=15),
    "REFRESH_TOKEN_LIFETIME": timedelta(days=7),
    "ROTATE_REFRESH_TOKENS": True,
    "BLACKLIST_AFTER_ROTATION": True,
    "ALGORITHM": "HS256",
    "SIGNING_KEY": SECRET_KEY,  # load from env in prod, not settings.py
}

# Or a custom authentication class:
from rest_framework.authentication import BaseAuthentication
import jwt
from django.conf import settings

class JWTAuthentication(BaseAuthentication):
    def authenticate(self, request):
        header = request.headers.get("Authorization", "")
        if not header.startswith("Bearer "):
            return None
        token = header[7:]
        try:
            payload = jwt.decode(
                token,
                settings.SECRET_KEY,
                algorithms=["HS256"],          # explicit allow-list
                audience="api",
                issuer="https://auth.example.com",
            )
            user = User.objects.get(id=payload["sub"])
            return (user, None)
        except (jwt.InvalidTokenError, User.DoesNotExist):
            return None
```

**Laravel (Delta) — Sanctum:**
```php
<?php
// config/auth.php
"api" => [
    "driver" => "sanctum",
    "provider" => "users",
],

// Issue a token:
$token = $user->createToken("api", ["read", "write"], now()->addMinutes(15));
$plainText = $token->plainTextToken;          // shown once; sha256-hashed in DB

// In a controller:
Route::middleware("auth:sanctum")->get("/me", function (Request $req) {
    return $req->user();
});

// Custom JWT (when Sanctum's opaque token isn't enough):
use Firebase\JWT\JWT;
use Firebase\JWT\Key;

$payload = [
    "iss" => "https://auth.example.com",
    "aud" => "api",
    "sub" => $user->id,
    "iat" => time(),
    "exp" => time() + 900,
];
$jwt = JWT::encode($payload, config("jwt.secret"), "HS256");

// Verifying:
$decoded = JWT::decode($jwt, new Key(config("jwt.secret"), "HS256"));
```
