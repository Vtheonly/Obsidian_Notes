# 05.06.01. Stateful vs. Stateless Authentication Architectures

## What This Is

Authentication is the act of proving who a caller is. In a backend API, every request must prove its caller's identity because HTTP is stateless — the server has no built-in memory of "this connection belongs to Alice". There are two architectural answers to "how does the server remember the caller across requests": stateful sessions (the server stores a record keyed by a session ID, the client sends the ID in a cookie) and stateless tokens (the server signs a token containing the caller's identity, the client sends the token in an `Authorization` header, the server verifies the signature on each request without storing anything).

This note teaches the universal concept: session-based vs token-based auth, the session-store problem (in-memory doesn't scale horizontally), CSRF for session auth, CORS for token auth, and the session invalidation problem. The anchor note (05.06.03) shows Spring Security's implementation in depth; the delta note (05.06.04) shows Express, Django, Flask, and Laravel.

## The Details

### Stateful Sessions: Session IDs, server-side stores (Redis, Memcached), session stickiness, horizontal scaling trade-offs

Session-based auth works as follows. (1) The client sends credentials (username + password). (2) The server verifies them against the user database. (3) The server creates a session record keyed by a random session ID (`sess_abc123`), stores the user's identity and any session metadata (login time, IP, user agent) in the record, and sets the session ID in a cookie on the response. (4) On subsequent requests, the browser automatically includes the cookie; the server reads the session ID, looks up the session record, and identifies the caller.

The session store is the critical piece. In development, an in-memory `Map<String, Session>` works; in production, it must be shared across all server instances because the load balancer may route consecutive requests from the same user to different instances. Without a shared store, a request to instance B after a login on instance A sees no session and returns 401. The shared store is typically Redis (single-digit millisecond lookups, automatic expiry via `TTL`) or Memcached (similar performance, simpler feature set). Storing sessions in the database works but adds query load to the primary and risks contention.

Session stickiness (the load balancer routes all requests from a given client to the same instance) is a workaround that lets you use in-memory session stores in production. It works but it breaks horizontal scaling: a hot user (one who makes many requests) overloads their assigned instance while other instances sit idle. It also breaks failover: if the sticky instance dies, the user is logged out and must re-authenticate. The correct production design is a shared session store plus round-robin or least-connections load balancing.

```text
  Session-based auth — request flow:

  1. POST /login {email, password}
       ↓
  2. Server: verifyPassword(email, password) → user_id=42
       ↓
  3. Server: sessionId = randomUUID(); redis.set("sess:"+sessionId, {user_id:42, …}, TTL=86400)
       ↓
  4. Server: Set-Cookie: sid=sess_abc123; HttpOnly; Secure; SameSite=Lax; Max-Age=86400
       ↓
  5. (Subsequent request) GET /api/me, Cookie: sid=sess_abc123
       ↓
  6. Server: redis.get("sess:"+sessionId) → {user_id:42, …}
       ↓
  7. Server: request.user = user_id=42; handler runs

  Costs:
    - One Redis GET per request (~1-3ms p99 on Redis)
    - Cookie is ~30 bytes (just the session ID)
    - Server stores ~200 bytes per session (user_id, login time, IP, etc.)
    - For 1M concurrent sessions: 200MB Redis memory
```

The production failure mode of session auth is the "Redis down → everyone logged out" incident. If the session store is down, every request gets a 401, every user is bounced to the login page, and the login endpoint is hammered by 100% of users trying to re-authenticate simultaneously. The fix is to deploy Redis with a replica and automatic failover (Redis Sentinel or Redis Cluster), and to make the session lookup degrade gracefully (treat a Redis timeout as "session invalid, redirect to login" rather than "500 internal error").

### Stateless Tokens: Self-contained cryptographic assertions, zero server-side lookup requirements, revocation difficulties

Token-based auth works as follows. (1) The client sends credentials. (2) The server verifies them. (3) The server constructs a token containing the user's identity and a signature, and returns the token in the response body (not a cookie). (4) On subsequent requests, the client sends the token in the `Authorization: Bearer <token>` header. (5) The server verifies the signature cryptographically, extracts the user identity, and identifies the caller — with zero server-side state lookups.

The token is typically a JWT (JSON Web Token, see [[05.06.02. JSON Web Tokens (JWT) Architecture and Security]]). The signature is HMAC-SHA256 (symmetric, shared secret) or RSA-SHA256 (asymmetric, private key signs, public key verifies). The signature proves the token was issued by the server and has not been tampered with. The token's payload contains the user ID, the issue time, the expiry time, and any claims (roles, scopes).

The benefit of stateless tokens is horizontal scalability. Any server instance can verify any token because the verification key (the HMAC secret or the RSA public key) is the same across instances. There is no shared session store, no Redis dependency, no session lookup latency. The cost is revocation: a token, once issued, is valid until its `exp` claim, and there is no server-side way to revoke it before expiry without re-introducing state (a revocation list that every request must check, defeating the statelessness).

```text
  Token-based auth — request flow:

  1. POST /login {email, password}
       ↓
  2. Server: verifyPassword(email, password) → user_id=42
       ↓
  3. Server: token = base64(header) + "." + base64({sub:42, exp:1700000000, …})
       signature = HMAC-SHA256(header.payload, secret)
       token = header.payload.signature
       ↓
  4. Server: response body = {"access_token": token, "token_type": "Bearer"}
       (No Set-Cookie — the client stores the token in localStorage or memory)
       ↓
  5. (Subsequent request) GET /api/me, Authorization: Bearer <token>
       ↓
  6. Server: split token on "."; recompute HMAC of header.payload; compare to signature
       (No DB or Redis lookup — pure CPU work, ~0.1ms)
       ↓
  7. Server: check exp not expired; extract sub=42; request.user = user_id=42; handler runs

  Costs:
    - ~0.1ms HMAC verification per request (pure CPU, no I/O)
    - Token is ~500-1000 bytes (the full payload, base64-encoded)
    - Server stores NOTHING per session — all state is in the token
    - For 1M concurrent sessions: 0 bytes server memory
    - BUT: revoking a token before its exp requires a server-side revocation list
```

The production failure mode of token auth is the "stolen token cannot be revoked" incident. A user reports their laptop was stolen; the attacker has the user's access token, which is valid for the next 14 days (the refresh-token rotation window). The server cannot revoke the access token without re-introducing state (a revocation list, checked on every request). The fix is short access-token expiry (5-15 minutes) paired with refresh-token rotation (the refresh token is single-use; if it is reused, the entire session is revoked). The stolen access token expires in 15 minutes; the stolen refresh token, if used, triggers revocation.

### Secure Cookie Mechanics: `HttpOnly` (preventing XSS theft), `Secure` (HTTPS-only transmission), `SameSite=Strict/Lax/None` (CSRF prevention)

Cookies have three security flags that every backend engineer must know. Getting any one wrong produces a vulnerability class. `HttpOnly` prevents JavaScript from reading the cookie (mitigates XSS token theft). `Secure` prevents the cookie from being sent over HTTP (mitigates man-in-the-middle token interception). `SameSite` prevents the cookie from being sent on cross-site requests (mitigates CSRF).

`HttpOnly=true` means `document.cookie` in JavaScript does not include the cookie. Without it, a single XSS vulnerability lets an attacker steal the session ID and impersonate the user. With it, the attacker can make authenticated requests from the victim's browser (because the cookie is auto-attached) but cannot exfiltrate the cookie to their own server. This is a meaningful defence-in-depth — XSS is still a vulnerability, but the blast radius is reduced.

`Secure=true` means the browser only sends the cookie over HTTPS. Without it, an attacker on the same Wi-Fi network can intercept the cookie via a man-in-the-middle attack on the HTTP request. With it, the cookie is never transmitted in cleartext. The trap is that the cookie is set with `Secure=true` only if the response that sets it is itself HTTPS — setting `Secure` on an HTTP response is silently ignored by the browser.

`SameSite=Strict` means the cookie is sent only on requests whose origin matches the cookie's domain. A request from `https://attacker.com` to `https://yourbank.com/transfer?to=attacker&amount=1000` does not include the cookie — the CSRF attack fails. `SameSite=Lax` (the browser default since Chrome 80+) sends the cookie on top-level navigations (`<a href>`, `window.location`) but not on cross-site POST requests or iframe loads. This is a balance between security (blocks most CSRF) and usability (lets users follow links to your site while logged in). `SameSite=None` requires `Secure=true` and sends the cookie on all requests, including cross-site — useful only for third-party cookies (analytics, embedded widgets) and increasingly blocked by browsers.

```text
  Cookie security flags — what each prevents:

  ┌──────────────────┬──────────────────────────────────────────────────────────────┐
  │ Flag             │ Prevents                                                     │
  ├──────────────────┼──────────────────────────────────────────────────────────────┤
  │ HttpOnly         │ XSS-based cookie theft via document.cookie                  │
  │                  │ (Attacker can still CSRF, but cannot exfiltrate the token)  │
  │ Secure           │ MITM interception on HTTP (must use HTTPS for the cookie    │
  │                  │ to be set or sent)                                          │
  │ SameSite=Strict  │ All CSRF — cookie not sent on any cross-site request        │
  │ SameSite=Lax     │ Most CSRF — cookie sent only on top-level GET navigations  │
  │                  │ (browser default since Chrome 80)                           │
  │ SameSite=None    │ Nothing (cookie sent everywhere) — requires Secure=true    │
  │                  │ and is for third-party cookies only                          │
  │ __Host- prefix   │ Cookie must have Secure=true, Path=/, no Domain attribute   │
  │                  │ (defense against subdomain cookie injection)                │
  └──────────────────┴──────────────────────────────────────────────────────────────┘

  For session auth (cookie-based):
    Set-Cookie: sid=sess_abc123; HttpOnly; Secure; SameSite=Lax; Max-Age=86400; Path=/

  For token auth (header-based, no cookie):
    No Set-Cookie. The token is in the response body; the client stores it in
    localStorage (XSS-vulnerable) or in memory (lost on refresh). CSRF is not
    a concern because the browser does not auto-attach the Authorization header.
    XSS is the primary risk — a stolen token is fully usable until it expires.
```

The production failure mode of misconfigured cookies is the "CSRF works in production but not in test" incident. The test environment sets `SameSite=None` (because the test runner is on a different origin), and CSRF defences are absent because "we'll add them later". In production, the cookie is set with `SameSite=Lax` (the browser default) and CSRF on POST requests is blocked — but the team has not implemented CSRF tokens, so legitimate POST requests from a third-party integration partner are blocked too. The fix is to design CSRF defence explicitly: either use `SameSite=Strict` plus a CSRF token for the rare cross-site POST, or use token auth (no cookies, no CSRF).

### CSRF for session auth, CORS for token auth, and the session invalidation problem

CSRF (Cross-Site Request Forgery) is a vulnerability class that affects cookie-based auth but not header-based auth. The attack: a victim is logged in to `yourbank.com`; they visit `attacker.com`; `attacker.com` has a form that POSTs to `yourbank.com/transfer`; the browser auto-attaches the victim's cookie; the transfer succeeds. The defence: either `SameSite=Strict` (browser does not send the cookie on cross-site requests) or a synchronizer token (the server includes a random token in every form; the POST must include the token; the attacker's form does not have it).

CORS (Cross-Origin Resource Sharing) is a browser-enforced policy that affects header-based auth. The browser blocks JavaScript from reading the response of a cross-origin request unless the server explicitly allows it via the `Access-Control-Allow-Origin` header. For token auth, CORS is the defence against token theft via XSS — even if an attacker steals the token, they cannot exfiltrate the response data to their own server without the CORS policy allowing it. The trap is `Access-Control-Allow-Origin: *` (allows any origin) combined with `Access-Control-Allow-Credentials: true` (allows cookies) — this configuration is invalid and the browser blocks the request. The fix is to set `Access-Control-Allow-Origin` to a specific origin (or a small whitelist) when credentials are involved.

The session invalidation problem is the symmetric challenge for stateless tokens. Sessions can be invalidated instantly (delete the session record from Redis; the next request gets a 401). Tokens cannot be invalidated without a server-side revocation list (which defeats the statelessness). The compromise is refresh-token rotation: the long-lived refresh token is single-use; using it issues a new access token and rotates the refresh token; if a stolen refresh token is reused (the legitimate client and the attacker both have it), the server detects the reuse and revokes the entire session (invalidates the refresh token family).

```text
  CSRF vs CORS — when each matters:

  ┌──────────────────────┬─────────────────────────┬─────────────────────────┐
  │ Auth mechanism       │ CSRF risk               │ CORS concern            │
  ├──────────────────────┼─────────────────────────┼─────────────────────────┤
  │ Session (cookie)     │ HIGH — browser auto-    │ LOW — cookies are not   │
  │                      │ attaches cookie on      │ subject to CORS for the │
  │                      │ cross-site POST         │ request itself          │
  │                      │                         │                         │
  │ Defence:             │ SameSite=Strict +       │ N/A                     │
  │                      │ synchronizer token      │                         │
  ├──────────────────────┼─────────────────────────┼─────────────────────────┤
  │ Token (Authorization │ NONE — browser does     │ HIGH — cross-origin JS  │
  │ header)              │ not auto-attach header  │ cannot read the response│
  │                      │                         │ without CORS allowing   │
  │ Defence:             │ N/A                     │ Set specific origin,    │
  │                      │                         │ never "*"+credentials   │
  └──────────────────────┴─────────────────────────┴─────────────────────────┘
```

The production failure mode of confusing CSRF and CORS is the "we added CSRF tokens to a token-auth API" waste. A token-auth API does not need CSRF tokens because the browser does not auto-attach the `Authorization` header — the attacker's form has no way to include it. Adding CSRF tokens adds complexity without security benefit. The symmetric waste is "we relaxed CORS to `*` for a session-auth API" — the browser blocks `Access-Control-Allow-Origin: *` with `Access-Control-Allow-Credentials: true`, so the relaxation does not work and the team is confused.

## Cross-Ecosystem Code

The same authentication concept — verify credentials, issue a token or session, verify on subsequent requests — side-by-side.

**Spring Security (Anchor) — JWT filter:**
```java
@Component
class JwtAuthFilter extends OncePerRequestFilter {
    private final JwtService jwt;
    private final UserDetailsService users;

    @Override
    protected void doFilterInternal(HttpServletRequest req,
                                    HttpServletResponse res,
                                    FilterChain chain) throws ServletException, IOException {
        String header = req.getHeader("Authorization");
        if (header != null && header.startsWith("Bearer ")) {
            String token = header.substring(7);
            try {
                String username = jwt.extractUsername(token);
                UserDetails user = users.loadUserByUsername(username);
                if (jwt.isTokenValid(token, user)) {
                    UsernamePasswordAuthenticationToken auth =
                        new UsernamePasswordAuthenticationToken(user, null, user.getAuthorities());
                    SecurityContextHolder.getContext().setAuthentication(auth);
                }
            } catch (JwtException e) {
                res.setStatus(401);
                res.getWriter().write("{\"error\":\"invalid_token\"}");
                return;
            }
        }
        chain.doFilter(req, res);
    }
}
```

**Express (Delta):**
```typescript
import jwt from "jsonwebtoken";

function authMiddleware(req, res, next) {
  const header = req.headers.authorization;
  if (!header?.startsWith("Bearer ")) return next();  // anonymous
  try {
    req.user = jwt.verify(header.slice(7), process.env.JWT_SECRET);
    next();
  } catch (e) {
    res.status(401).json({ error: "invalid_token" });
  }
}

app.use(authMiddleware);
```

**Django (Delta):**
```python
# settings.py
REST_FRAMEWORK = {
    "DEFAULT_AUTHENTICATION_CLASSES": [
        "rest_framework_simplejwt.authentication.JWTAuthentication",
    ],
}

# Custom authentication class:
from rest_framework.authentication import BaseAuthentication
import jwt

class JWTAuthentication(BaseAuthentication):
    def authenticate(self, request):
        header = request.headers.get("Authorization", "")
        if not header.startswith("Bearer "): return None
        token = header[7:]
        try:
            payload = jwt.decode(token, SECRET_KEY, algorithms=["HS256"])
            user = User.objects.get(id=payload["sub"])
            return (user, None)
        except jwt.InvalidTokenError:
            return None
```

**Laravel (Delta) — Sanctum:**
```php
// config/auth.php
"api" => [
    "driver" => "sanctum",
    "provider" => "users",
],

// Issue a token:
$token = $user->createToken("api")->plainTextToken;

// In a controller:
Route::middleware("auth:sanctum")->get("/me", function (Request $req) {
    return $req->user();
});
```
