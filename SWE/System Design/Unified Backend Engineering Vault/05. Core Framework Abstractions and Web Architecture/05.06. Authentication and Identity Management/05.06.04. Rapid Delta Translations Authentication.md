# 05.06.04. Rapid Delta Translations Authentication

## What This Note Is

This is a **delta translation note**. It is intentionally short. Read it **after** completing the anchor implementation in the sibling Spring Boot note. The point is to answer one question:

> What is different in this ecosystem, and what is automatic that I had to do manually in the anchor?

If you find yourself re-learning the concept here, you have not finished the anchor. Go back.

## Implementation Deltas

The deltas to internalize:

- *TypeScript / Express*: Passport.js strategies, manual JWT verification middleware (`jsonwebtoken`), managing session stores (`express-session` + `connect-redis`).
- *Python / Django*: Django native session authentication, Django REST Framework SimpleJWT, writing custom `BaseAuthentication` classes.
- *PHP / Laravel*: Laravel Sanctum (SPA stateful cookie & API token authentication), Laravel Passport (Full OAuth2 server implementation).

## TypeScript / Express Implementation

Express ships with no authentication at all — `req` arrives with a body and headers, and what you do with them is your problem. The canonical stack is `passport` (a strategy engine that delegates to provider-specific modules — `passport-local` for username/password, `passport-jwt` for Bearer tokens, `passport-google-oauth20` for OAuth) plus `jsonwebtoken` for issuing and verifying JWTs, plus `express-session` with `connect-redis` for server-side session storage when you do not want JWTs. The key delta vs Spring: **there is no DI container and no filter chain abstraction** — you compose middleware by hand, and the order of `app.use(...)` calls is the order of execution. There is no `SecurityFilterChain` bean; you write `app.use(authMiddleware)` and that is the entire filter chain.

```typescript
// src/auth/jwt.ts
import jwt, { JwtPayload, SignOptions } from "jsonwebtoken";
import { promisify } from "util";

const signAsync = promisify<string | object | Buffer, Secret, SignOptions, string>(jwt.sign);

export interface AuthPayload extends JwtPayload {
  sub: string;
  roles: string[];
}

export async function issueAccessToken(userId: string, roles: string[]): Promise<string> {
  return signAsync(
    { roles } as object,
    process.env.JWT_SECRET!,
    {
      algorithm: "HS256",
      issuer: "https://auth.example.com",
      audience: "api",
      subject: userId,
      expiresIn: "15m",   // 900 seconds
    } as SignOptions,
  );
}

export function verifyAccessToken(token: string): AuthPayload {
  return jwt.verify(token, process.env.JWT_SECRET!, {
    algorithms: ["HS256"],          // explicit allow-list — never trust the header
    issuer: "https://auth.example.com",
    audience: "api",
  }) as AuthPayload;
}
```

```typescript
// src/auth/middleware.ts
import { Request, Response, NextFunction } from "express";
import { verifyAccessToken, AuthPayload } from "./jwt";

export interface AuthenticatedRequest extends Request {
  user?: AuthPayload;
}

export function requireAuth(req: AuthenticatedRequest, res: Response, next: NextFunction) {
  const header = req.headers.authorization;
  if (!header?.startsWith("Bearer ")) {
    return res.status(401).json({ error: "missing_token" });
  }
  try {
    req.user = verifyAccessToken(header.slice(7));
    next();
  } catch (err) {
    return res.status(401).json({ error: "invalid_token" });
  }
}

export function requireRole(role: string) {
  return (req: AuthenticatedRequest, res: Response, next: NextFunction) => {
    if (!req.user?.roles?.includes(role)) {
      return res.status(403).json({ error: "forbidden" });
    }
    next();
  };
}
```

```typescript
// src/auth/passport.ts — alternative: Passport-local + JWT strategies
import passport from "passport";
import { Strategy as LocalStrategy } from "passport-local";
import { Strategy as JwtStrategy, ExtractJwt } from "passport-jwt";
import bcrypt from "bcrypt";
import { userRepo } from "../db";
import { issueAccessToken } from "./jwt";

passport.use(
  new LocalStrategy({ usernameField: "email" }, async (email, password, done) => {
    const user = await userRepo.findByEmail(email);
    if (!user || !(await bcrypt.compare(password, user.passwordHash))) {
      return done(null, false, { message: "invalid_credentials" });
    }
    return done(null, user);     // attaches to req.user
  }),
);

passport.use(
  new JwtStrategy(
    {
      jwtFromRequest: ExtractJwt.fromAuthHeaderAsBearerToken(),
      secretOrKey: process.env.JWT_SECRET!,
      algorithms: ["HS256"],
      issuer: "https://auth.example.com",
      audience: "api",
    },
    (payload, done) => done(null, payload),
  ),
);
```

```typescript
// src/app.ts
import express from "express";
import passport from "passport";
import session from "express-session";
import RedisStore from "connect-redis";
import { createClient } from "redis";
import { requireAuth, requireRole } from "./auth/middleware";

const app = express();
app.use(express.json());

// Optional: server-side session storage for routes that need stateful auth
const redis = createClient({ url: process.env.REDIS_URL });
redis.connect();
app.use(
  session({
    store: new RedisStore({ client: redis }),
    secret: process.env.SESSION_SECRET!,
    cookie: { httpOnly: true, secure: true, sameSite: "strict", maxAge: 7 * 86400_000 },
    resave: false,
    saveUninitialized: false,
  }),
);
app.use(passport.initialize());          // must come after session if using session-based strategies

app.post(
  "/auth/login",
  passport.authenticate("local", { session: false }),
  (req, res) => {
    const token = issueAccessToken(req.user.id, req.user.roles);
    res.json({ accessToken: token, tokenType: "Bearer", expiresIn: 900 });
  },
);

app.get("/me", requireAuth, (req, res) => res.json({ user: req.user }));
app.delete("/admin/users/:id", requireAuth, requireRole("admin"), deleteUser);
```

What was automatic in the Spring anchor that is manual here? (1) **Filter chain composition** — Spring's `SecurityFilterChain` bean is a declarative ordered list with `addFilterBefore` semantics; in Express you compose by ordering `app.use` calls and middleware arrays, and there is no compile-time check that `requireAuth` runs before `requireRole`. (2) **Password encoding** — Spring's `BCryptPasswordEncoder` bean is injected everywhere; in Express you call `bcrypt.compare` manually and pick the work factor each time. (3) **Exception translation** — Spring's `ExceptionTranslationFilter` catches `AuthenticationException` and converts it to a 401; in Express, every middleware function must catch its own errors and call `res.status(401)` or use an error-handling middleware at the end of the chain. What is automatic here that was manual there? (1) **Single-file readability** — the entire auth stack is in `src/auth/*.ts`, no AOP proxies, no bean post-processing magic. (2) **JSON serialization** — `express.json()` parses and stringifies natively; Spring requires Jackson config. The runtime invariant exposed differently: Node's single-threaded event loop means there is no `SecurityContextHolder` thread-local — `req.user` is the equivalent, and it is per-request by construction. The failure mode structurally impossible here is the cross-thread `SecurityContext` leak from Spring; the failure mode *new* here is callback/promise-rejection swallowing — if `verifyAccessToken` throws asynchronously inside a middleware that does not `try/catch`, the rejection is unhandled and the response hangs until the client times out.

## Python / Django Implementation

Django ships with a complete session-based authentication system out of the box: `django.contrib.auth.models.User`, `django.contrib.auth.backends.ModelBackend`, the `login()` and `logout()` functions in `django.contrib.auth`, the `@login_required` decorator, and the `AuthenticationMiddleware` that populates `request.user`. For APIs you layer **Django REST Framework** on top, which provides the `DEFAULT_AUTHENTICATION_CLASSES` setting (a list of classes tried in order), `DEFAULT_PERMISSION_CLASSES`, and the `@permission_classes` decorator. For JWT specifically, the `djangorestframework-simplejwt` package gives you `JWTAuthentication`, `TokenObtainPairView`, `TokenRefreshView`, and `TokenBlacklistView` — the last one backed by a `django-rest-framework-simplejwt` `OutstandingToken`/`BlacklistedToken` table that implements refresh-token rotation + blacklist semantics out of the box.

```python
# settings.py

    "rest_framework",
    "rest_framework_simplejwt",
    "rest_framework_simplejwt.token_blacklist",

REST_FRAMEWORK = {
    "DEFAULT_AUTHENTICATION_CLASSES": [
        "rest_framework_simplejwt.authentication.JWTAuthentication",
    ],
    "DEFAULT_PERMISSION_CLASSES": [
        "rest_framework.permissions.IsAuthenticated",
    ],
}

SIMPLE_JWT = {
    "ACCESS_TOKEN_LIFETIME": timedelta(minutes=15),
    "REFRESH_TOKEN_LIFETIME": timedelta(days=7),
    "ROTATE_REFRESH_TOKENS": True,           # delete old, issue new on each refresh
    "BLACKLIST_AFTER_ROTATION": True,        # mark old refresh token as blacklisted

    "USER_ID_CLAIM": "sub",
}
```

```python
# Custom authentication class — when SimpleJWT isn't what you want
from rest_framework.authentication import BaseAuthentication
from rest_framework.exceptions import AuthenticationFailed
import jwt
from django.conf import settings
from django.contrib.auth import get_user_model

User = get_user_model()

class CustomJWTAuthentication(BaseAuthentication):
    """Verifies a Bearer JWT against the configured HS256 secret and audience."""
    def authenticate(self, request):
        header = request.headers.get("Authorization", "")
        if not header.startswith("Bearer "):
            return None                       # let the next authentication class try
        token = header[7:]
        try:
            payload = jwt.decode(
                token,
                settings.SECRET_KEY,
                algorithms=["HS256"],          # explicit; never trust the header
                audience="api",
                issuer="https://auth.example.com",
            )
        except jwt.PyJWTError as e:
            raise AuthenticationFailed(f"invalid_token: {e}")

        try:
            user = User.objects.get(pk=payload["sub"])
        except User.DoesNotExist:
            raise AuthenticationFailed("user_not_found")

        return (user, None)
```

What was automatic in the Spring anchor that is manual here? (1) **Authentication provider wiring** — Spring's `DaoAuthenticationProvider` + `UserDetailsService` is explicit; Django's `ModelBackend` is the default and the wiring lives in `settings.AUTHENTICATION_BACKENDS`. (2) **Filter chain** — Spring's `SecurityFilterChain` bean is declarative; Django's middleware (`AuthenticationMiddleware`, `SessionMiddleware`, `SecurityMiddleware`) is configured in `MIDDLEWARE` and runs in order, but DRF's `DEFAULT_AUTHENTICATION_CLASSES` is a *separate* list that runs at view dispatch. (3) **Method security** — Spring's `@PreAuthorize` is AOP; Django has no equivalent — you use `@permission_classes` per view or `@permission_required` per function. What is automatic here that was manual there? (1) **User model** — `django.contrib.auth.models.User` is provided, with `createsuperuser`, `check_password()`, and the admin interface all working out of the box. (2) **Refresh token rotation + blacklist** — `simplejwt.token_blacklist` gives you the rotation/blacklist table for free; in Spring you write the `RefreshTokenStore` yourself. (3) **CSRF middleware** — Django's `CsrfViewMiddleware` is on by default; Spring requires explicit `.csrf(csrf -> csrf.disable())` because JWT APIs do not need it. The runtime invariant exposed differently: Django's WSGI/ASGI process model is shared-nothing — every worker process has its own Python interpreter, so there is no `SecurityContextHolder` equivalent and no thread-local to leak. `request.user` is set on the WSGI request object and discarded when the response returns. The failure mode new here is **GIL contention** on a single async ASGI worker if the JWT verify + bcrypt hash check run synchronously inside an event loop — `bcrypt` is C-extension, releases the GIL, but a tight login storm can still starve the loop.

## PHP / Laravel Implementation

Laravel ships with **three** authentication systems, and choosing between them is the load-bearing decision. **Sanctum** is for first-party SPAs (your Vue/React frontend calling your Laravel API on the same domain family) and lightweight API tokens — it issues either a stateful cookie (when the frontend and API share a root domain) or a SHA-256-hashed opaque token stored in a `personal_access_tokens` table. **Passport** is a full OAuth2 server (authorization code grant, client credentials, refresh tokens, scopes) for when you must expose your API to third-party clients — it is much heavier and pulls in `league/oauth2-server`. **The `Auth` facade** (or the `auth()` helper) is the underlying primitive both build on — `Auth::attempt(['email' => $email, 'password' => $password])`, `Auth::user()`, `Auth::id()`, `Auth::guard('api')->user()`.

```php
<?php
// app/Http/Controllers/AuthController.php
namespace App\Http\Controllers;

use Illuminate\Http\Request;
use Illuminate\Support\Facades\Auth;
use Firebase\JWT\JWT;
use Firebase\JWT\Key;

class AuthController extends Controller
{
    public function login(Request $req)
    {
        $credentials = $req->validate([
            'email'    => ['required', 'email'],
            'password' => ['required', 'string'],
        ]);

        if (!Auth::attempt($credentials)) {
            return response()->json(['error' => 'invalid_credentials'], 401);
        }

        $user = Auth::user();

        // Sanctum SPA-cookie flow (for first-party frontends):
        // $req->session()->regenerate();        // fixes session fixation
        // return response()->json($user);

        // Sanctum API-token flow (for mobile/CLI clients):
        // $token = $user->createToken('api', ['read','write'], now()->addMinutes(15));
        // return response()->json(['token' => $token->plainTextToken]);

        // Custom JWT flow (when you need self-contained tokens):
        $jwt = $this->issueJwt($user);
        return response()->json([
            'access_token' => $jwt,
            'token_type'   => 'Bearer',
            'expires_in'   => 900,
        ]);
    }

    private function issueJwt($user): string
    {
        $now = time();
        return JWT::encode(
            [
                'iss'   => 'https://auth.example.com',
                'aud'   => 'api',
                'sub'   => (string) $user->id,
                'roles' => $user->roles->pluck('name')->all(),
                'iat'   => $now,
                'exp'   => $now + 900,
                'jti'   => bin2hex(random_bytes(16)),     // for server-side revocation
            ],
            config('jwt.secret'),
            'HS256',
        );
    }

    public function me(Request $req)
    {
        return response()->json($req->user());
    }
}
```

```php
<?php
// app/Providers/JwtServiceProvider.php — register a custom 'jwt' guard driver
namespace App\Providers;

use Illuminate\Support\Facades\Auth;
use Illuminate\Support\ServiceProvider;
use Firebase\JWT\JWT;
use Firebase\JWT\Key;
use App\Models\User;

class JwtServiceProvider extends ServiceProvider
{
    public function boot()
    {
        Auth::extend('jwt', function ($app, $name, array $config) {
            return Auth::createUserProvider($config['provider'])
                ? new \App\Auth\JwtGuard(
                    Auth::createUserProvider($config['provider']),
                    $app['request'],
                )
                : null;
        });
    }
}

// app/Auth/JwtGuard.php
namespace App\Auth;

use Illuminate\Contracts\Auth\Guard;
use Illuminate\Contracts\Auth\UserProvider;
use Illuminate\Http\Request;
use Firebase\JWT\JWT;
use Firebase\JWT\Key;
use App\Models\User;

class JwtGuard implements Guard
{
    protected ?User $user = null;

    public function __construct(protected UserProvider $provider, protected Request $request) {}

    public function user(): ?User
    {
        if ($this->user) return $this->user;

        $header = $this->request->header('Authorization', '');
        if (!str_starts_with($header, 'Bearer ')) return null;

        try {
            $payload = JWT::decode(
                substr($header, 7),
                new Key(config('jwt.secret'), 'HS256'),
            );
            $this->user = $this->provider->retrieveById($payload->sub);
        } catch (\Throwable) {
            return null;
        }
        return $this->user;
    }

    public function check(): bool   { return !is_null($this->user()); }
    public function guest(): bool   { return !$this->check(); }
    public function id()            { return $this->user()?->id; }
    public function validate(array $credentials = []): bool { return false; }
    public function setUser($user): void { $this->user = $user; }
}
```

What was automatic in the Spring anchor that is manual here? (1) **`SecurityFilterChain` bean** — Laravel's `auth` middleware (`auth:sanctum`, `auth:web`, `auth:jwt`) is registered in `app/Http/Kernel.php` (or `bootstrap/app.php` in Laravel 11+) and dispatched by the `Authenticate` middleware class; the chain ordering is fixed by Laravel's middleware priority list (`StartSession` → `ShareErrorsFromSession` → `Authenticate` → `Authorize`), so you cannot easily insert a custom filter at an arbitrary position. (2) **Filter implementation** — Spring's `OncePerRequestFilter` is a class you extend; Laravel's middleware is a closure-or-class with a `handle($request, $next)` signature, and you write it by hand. What is automatic here that was manual there? (1) **The `User` model** — Laravel's `App\Models\User` ships with `HasApiTokens` (Sanctum trait), password hashing via the `Hash` facade (BCrypt by default, work factor 10), and the `password` cast that automatically hashes on assignment. (2) **Session fixation defense** — `$req->session()->regenerate()` rotates the session ID on login automatically; in Spring you call `session.changeSessionId()` manually. (3) **CSRF tokens** — Laravel's `VerifyCsrfToken` middleware reads the `_token` field or `X-CSRF-TOKEN` header and matches it to the session; in Spring you must enable `CsrfFilter` and add the token to every form. The runtime invariant exposed differently: PHP-FPM is shared-nothing — every request is a fresh process state (modulo opcache), so there is no `SecurityContextHolder` thread-local and no cross-request leakage via threads. `Auth::user()` is resolved per-request and stored in the `AuthManager` singleton, which is reconstructed per request via the service container. The failure mode structurally impossible here is the Spring thread-reuse `SecurityContext` leak; the failure mode *new* here is **per-request bootstrap cost** — every PHP-FPM request re-instantiates the application, re-runs all service providers' `boot()` methods, and re-parses the routes file. With Sanctum's `personal_access_tokens` table, every authenticated API request costs one DB SELECT to look up the token; the JWT custom guard avoids that DB hit at the cost of revocation complexity.

## Cross-Ecosystem Code

The same concept implemented in all four target ecosystems. Read them side by side — the shape is identical, only the syntax differs.

**Spring Security (Anchor) — JWT filter:**
```java
@Component
class JwtAuthFilter extends OncePerRequestFilter {
    private final JwtService jwt;

    @Override
    protected void doFilterInternal(HttpServletRequest req,
                                    HttpServletResponse res,
                                    FilterChain chain) throws ServletException, IOException {
        String header = req.getHeader("Authorization");
        if (header != null && header.startsWith("Bearer ")) {
            String token = header.substring(7);
            try {
                String userId = jwt.verify(token);   // verify signature + expiry
                UsernamePasswordAuthenticationToken auth =
                    new UsernamePasswordAuthenticationToken(userId, null, List.of());
                SecurityContextHolder.getContext().setAuthentication(auth);
            } catch (JwtException e) {
                res.setStatus(401);
                return;
            }
        }
        chain.doFilter(req, res);
    }
}
```
