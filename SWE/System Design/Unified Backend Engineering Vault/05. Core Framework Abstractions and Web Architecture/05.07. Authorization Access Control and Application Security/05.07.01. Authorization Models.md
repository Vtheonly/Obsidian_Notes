# 05.07.01. Authorization Models

## What This Is

Authorization (commonly abbreviated AuthZ, pronounced "auth-zee") is the question *given that we know who you are (authentication, AuthN), what are you allowed to do?* It is the second half of the access-control equation and is structurally harder than the first, because authentication is a binary verified/not-verified check while authorization is a query against a potentially huge policy space: every (subject, action, resource) triple is its own answer. Every backend framework implements one or more authorization models, and the model you pick determines the schema, the latency profile, the auditability, and the blast radius of a misconfiguration.

This note covers the four canonical models — **DAC** (Discretionary Access Control, the Unix file-permissions model), **MAC** (Mandatory Access Control, the military clearances model), **RBAC** (Role-Based, the industry default), **ABAC** (Attribute-Based, the dynamic-policy model), and the modern fifth: **ReBAC** (Relationship-Based, the Google Zanzibar model that powers GitHub's "can user X push to repo Y" checks). It also covers the architectural separation between the **Policy Enforcement Point** (PEP, the filter/middleware that blocks the request) and the **Policy Decision Point** (PDP, the service that answers yes/no), which is the structural pattern that lets you centralize authorization across microservices. The failure mode of every one of these models is *role explosion* (RBAC) or *policy sprawl* (ABAC) — they all degrade into unmaintainable spaghetti if you let the schema evolve without rigorous review.

## The Details

### Role-Based Access Control (RBAC): Users, Roles, Permissions, Role Hierarchies

RBAC is the default authorization model in 95% of business software because it maps directly to the way humans talk about access: "Alice is an editor", "editors can edit articles", therefore Alice can edit articles. The schema is a many-to-many-through-many relationship: **users** are assigned **roles**, **roles** are granted **permissions**, and the check is `user.hasRole('editor') && role.hasPermission('article:edit')`. The ANSI INCITS 359-2004 standard formalized this in 2004; NIST published RBAC/AC in 2017. The four-level hierarchy — Flat RBAC (users→roles→permissions), Hierarchical RBAC (roles inherit from other roles), Constrained RBAC (separation-of-duties constraints prevent conflicts), Symmetric RBAC (permission-to-role queries are first-class) — is what every framework approximates with varying degrees of completeness.

The canonical SQL schema is three tables plus two join tables. `users(id, email, ...)`, `roles(id, name)`, `permissions(id, name)`, `user_roles(user_id, role_id)`, `role_permissions(role_id, permission_id)`. The query to check "can user 42 do `article:edit`?" is a single three-way join: `SELECT 1 FROM user_roles ur JOIN role_permissions rp ON rp.role_id = ur.role_id JOIN permissions p ON p.id = rp.permission_id WHERE ur.user_id = 42 AND p.name = 'article:edit'`. With indexes on both foreign keys, this is ~0.2ms on a 10M-row Postgres table. Every framework's RBAC implementation is a thin wrapper around this query: Spring Security's `JdbcUserDetailsManager`, Django's `auth.models.User.user_permissions` and `Group.permissions`, Laravel's `spatie/laravel-permission` package (the de-facto standard), Express's `CASL` or `accesscontrol` npm package.

```text
  RBAC Schema (ANSI INCITS 359-2004 flat + hierarchical)

       ┌─────────┐         ┌──────────────┐         ┌─────────────┐
       │  users  │◄────────│ user_roles   │────────►│   roles     │
       │  id     │         │ user_id      │         │  id         │
       │  email  │         │ role_id      │         │  name       │
       └─────────┘         └──────────────┘         └─────────────┘
                                                       │
                                                       │ inherits
                                                       ▼
       ┌──────────────┐         ┌──────────────┐    ┌─────────────┐
       │ permissions  │◄────────│role_perms    │───►│   roles     │
       │  id          │         │ role_id      │    │ (parent)    │
       │  name        │         │ perm_id      │    └─────────────┘
       │  e.g.        │         └──────────────┘
       │  article:edit│                            "editor" role
       │  article:del │                             inherits from
       │  user:create │                             "viewer" role
       └──────────────┘                             → editor gets
                                                     viewer's perms
                                                     automatically
```

**Role hierarchies** are the most error-prone part. Spring Security supports hierarchy via `RoleHierarchyImpl` configured with a string like `ROLE_ADMIN > ROLE_EDITOR > ROLE_VIEWER` — a `hasRole('ROLE_VIEWER')` check then succeeds for admins and editors too, because Spring walks the hierarchy before checking. Laravel's `spatie/laravel-permission` does the same via the `Role` model's `permissions` relation (no hierarchy in core; you simulate it by assigning the child role's permissions to the parent). Django has no native role hierarchy — you compose groups, with a user inheriting permissions from all their groups. The **separation-of-duties** constraint (a user cannot simultaneously hold `purchase_requester` and `purchase_approver` roles, to prevent fraud) is rare in practice; most RBAC implementations skip it and rely on policy review. The production failure mode of RBAC is **role explosion**: a SaaS that starts with 3 roles (admin, editor, viewer) grows, over five years, to 47 roles (`regional_editor_eu`, `regional_editor_apac`, `billing_admin_readonly`, `compliance_auditor_with_export`) because every edge case gets a new role. The cure is moving the edge cases to ABAC, where the rule "EU editors can only edit EU articles" becomes a policy attribute rather than a new role.

### Attribute-Based Access Control (ABAC): Evaluating dynamic policies based on Subject, Resource, Action, and Environment attributes.

ABAC answers the question "can subject S do action A on resource R in environment E?" by evaluating a policy expressed over the four attribute bags. The subject bag holds attributes of the caller (`role`, `department`, `clearance`, `country_of_residence`). The resource bag holds attributes of the target (`owner_id`, `classification`, `region`, `created_at`). The action bag is the verb (`read`, `write`, `delete`, `approve`). The environment bag holds the contextual state (`time_of_day`, `request_ip`, `mfa_verified`, `federation_partner`). A policy is a boolean expression: "permit if subject.role == 'editor' AND subject.department == resource.department AND action == 'write' AND environment.time_of_day in business_hours AND environment.mfa_verified == true". This is the model used by AWS IAM conditions, by OPA (Open Policy Agent)'s Rego policies, by XACML (the OASIS standard, almost nobody implements directly because the XML is unreadable), and by AuthZed's SpiceDB in ABAC mode.

The advantage over RBAC is **policy precision without role explosion**. The EU-editor example from the previous section becomes one ABAC rule: `permit if subject.role == 'editor' AND subject.region == resource.region`. No `regional_editor_eu`, `regional_editor_apac` roles; just an attribute. The disadvantage is **auditability**: in RBAC, the question "why can Alice edit this article?" has a clear answer ("she is an editor, editors can edit articles, role_id=7"). In ABAC, the answer is "the policy `editor-region-match` evaluated to true given subject.region=EU and resource.region=EU at 14:32:01 UTC on 2024-03-15" — you must log the full attribute snapshot at decision time to be able to reconstruct the decision later. ABAC policies also have a tendency to accrete conditions until they are unreadable; the OPA community's `conftest` and `opa test` tools exist precisely to keep policies maintainable.

```text
  ABAC decision flow (NIST SP 800-162)

  ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌────────────┐
  │ Subject  │    │ Resource │    │ Action   │    │ Environment│
  │ attrs    │    │ attrs    │    │ attrs    │    │ attrs      │
  └────┬─────┘    └────┬─────┘    └────┬─────┘    └─────┬──────┘
       │               │               │                │
       └───────┬───────┴───────────────┴────────────────┘
               │
               ▼
        ┌──────────────┐         ┌──────────────────────┐
        │  PEP (filter │────Q───►│  PDP (policy engine) │
        │  /middleware)│◄─A──────│  evaluates policies  │
        └──────────────┘  Permit │  against attrs       │
                         /Deny   └──────────────────────┘
                                         ▲
                                         │ loads
                                         │
                                 ┌───────────────┐
                                 │  PAP (admin   │
                                 │   policy repo)│
                                 └───────────────┘

  Example policy (Rego, OPA):
  ─────────────────────────────────────────────────────────
  package articles

  default allow := false

  allow if {
      input.action == "write"
      input.subject.role == "editor"
      input.subject.region == input.resource.region
      input.environment.mfa_verified
      time_in_business_hours(input.environment.timestamp)
  }
```

In real code, ABAC is usually layered on top of RBAC: roles are one attribute of the subject, but the policy also checks resource ownership, region, time-of-day, and MFA status. Spring Security exposes this via `@PreAuthorize("hasRole('EDITOR') and #article.author == authentication.principal.username and @timeService.isBusinessHours()")` — the SpEL expression is the policy, and the `@beanName.method()` syntax lets you call any Spring bean as a policy function. Laravel exposes it via Gate closures: `Gate::define('update-article', fn(User $u, Article $a) => $o->role === 'editor' && $o->region === $a->region && $o->mfa_verified)`. Express exposes it via `CASL`'s `ability.can('update', article)` rules. The production failure mode of ABAC is **performance**: every policy evaluation reads attributes from the database (the article's owner, region, classification) and from the request (MFA status, IP, time). Without aggressive caching of resource attributes, an ABAC check that should cost 0.5ms becomes a 5ms database round-trip — and every API request makes one. The fix is either (a) denormalize resource attributes into the JWT (`sub`, `role`, `region` from the user side; the resource side must still be fetched), or (b) move the PDP to a sidecar with an in-memory attribute cache.

### Policy Enforcement Points (PEP) vs. Policy Decision Points (PDP)

The PEP/PDP split is the most important architectural pattern in authorization, and most teams stumble into it backwards. The **Policy Enforcement Point** is the code that blocks the request when authorization fails — your Express middleware, your Spring `SecurityFilterChain`'s `AuthorizationFilter`, your Django `permission_classes`, your Laravel `can:` middleware. The **Policy Decision Point** is the code that answers "yes or no" — your `user.hasRole('admin')` check, your `Gate::allows('update-article', $article)` call, your `opa` query. In a monolith, the PEP and PDP are usually the same line of code; in a microservice topology, they must be separated, and the separation is what lets you centralize authorization without forcing every service to re-implement the policy.

The pattern comes from XACML (OASIS standard, 2013). The four roles are: **PAP** (Policy Administration Point — where administrators write policies, e.g., the OPA Bundle server, the AWS IAM console), **PDP** (Policy Decision Point — evaluates the policy given attributes, returns Permit/Deny/NotApplicable), **PEP** (Policy Enforcement Point — intercepts the request, calls the PDP, blocks on Deny), **PIP** (Policy Information Point — fetches missing attributes, e.g., "look up the article's owner_id from the database"). The **PRP** (Policy Retrieval Point) is the policy store the PDP loads from. The point of the split is **policy locality**: the policy is defined once (in the PAP), evaluated once (in the PDP), and enforced consistently across every service (via the PEPs). Without it, every microservice has its own `hasRole` check that drifts — service A checks `hasRole('admin')`, service B checks `hasRole('administrator')`, service C checks `hasAuthority('ROLE_ADMIN')`, and after three years nobody knows the complete answer to "what can user 42 do across the fleet?".

```text
  Monolith: PEP and PDP are the same code

       ┌────────────────────────────────────┐
       │  Spring @RestController            │
       │  ┌──────────────────────────────┐  │
       │  │ @PreAuthorize("hasRole(...)")│  │  ← PEP (filter/proxy blocks)
       │  │  deleteUser()                │  │
       │  │  ...                         │  │
       │  └──────────────────────────────┘  │
       │     PDP = Spring's Authz filter   │  ← PDP (same JVM, same call stack)
       └────────────────────────────────────┘

  Microservices: PEP and PDP are separated

       ┌─────────┐        ┌─────────┐        ┌─────────┐
       │  API A  │        │  API B  │        │  API C  │
       │ (PEP)   │        │ (PEP)   │        │ (PEP)   │
       └────┬────┘        └────┬────┘        └────┬────┘
            │ authorize Q     │ authorize Q     │ authorize Q
            ▼                 ▼                 ▼
       ┌─────────────────────────────────────────────┐
       │           PDP service (OPA / SpiceDB)       │
       │   evaluates policy against attributes       │
       │   returns Permit | Deny | NotApplicable     │
       └─────────────────────────────────────────────┘
            ▲                 ▲                 ▲
            │ fetch attrs     │ fetch attrs     │ fetch attrs
            ▼                 ▼                 ▼
       ┌─────────┐        ┌─────────┐        ┌─────────┐
       │ Postgres│        │   S3    │        │  Redis  │
       │ (PIP)   │        │ (PIP)   │        │ (PIP)   │
       └─────────┘        └─────────┘        └─────────┘
```

The production-grade implementations of PEP/PDP separation are: **Open Policy Agent (OPA)** as the PDP — deployed as a sidecar or a standalone service, policies written in Rego, queried via HTTP `POST /v1/data/<package>/allow` with a JSON body of attributes; **SpiceDB** (open source, AuthZed) as the PDP for ReBAC — a dedicated database for relationship tuples, queried via its gRPC API; **AWS IAM** as the PDP for AWS resources — every AWS API call goes through the IAM PEP, which calls the IAM PDP synchronously. The latency cost is real: a sidecar OPA call adds ~1-3ms per request, a remote OPA service adds 5-15ms. The benefit is **centralized audit**: every decision is logged in one place, every policy change is version-controlled, and a security review can verify the entire authorization surface by reading the Rego files. The production failure mode of PEP/PDP split is **PDP downtime = total outage**: if every service depends on the PDP and the PDP is down, no request can be authorized. The mitigations are (a) deploy the PDP as a sidecar (no network call), (b) cache Permit decisions for a short TTL (10-30 seconds — Deny must never be cached, or a revoked user retains access), (c) ship a "fail-closed" PEP that returns 503 when the PDP is unreachable, and (d) load-test the PDP in isolation before relying on it.

## Cross-Ecosystem Code

The same concept implemented in all four target ecosystems — authorization enforced at the controller layer for an `article:write` action.

**Spring Security (Anchor) — RBAC + ABAC via SpEL:**
```java
@RestController
@RequestMapping("/api/articles")
class ArticleController {

    @PreAuthorize("hasRole('EDITOR') and #article.authorId == authentication.principal.id")
    @PutMapping("/{id}")
    Article update(@PathVariable Long id, @RequestBody Article article) {
        return service.update(id, article);
    }

    @PreAuthorize("hasAuthority('article:delete') or hasRole('ADMIN')")
    @DeleteMapping("/{id}")
    void delete(@PathVariable Long id) { service.delete(id); }
}
```

**Express (Delta) — CASL ability check in middleware:**
```typescript
import { AbilityBuilder, createMongoAbility } from "@casl/ability";

function defineAbilityFor(user: { id: string; role: string }) {
  const { can, cannot, build } = new AbilityBuilder(createMongoAbility);
  if (user.role === "admin") {
    can("manage", "all");                  // full access
  } else if (user.role === "editor") {
    can("update", "Article", { authorId: user.id });   // ABAC: ownership predicate
    can("read", "Article");
  } else {
    can("read", "Article");
  }
  return build();
}

function authorize(action: string, subject: string) {
  return (req: AuthenticatedRequest, res: Response, next: NextFunction) => {
    const ability = defineAbilityFor(req.user!);
    if (!ability.can(action, subject)) {
      return res.status(403).json({ error: "forbidden" });
    }
    next();
  };
}

app.put("/api/articles/:id",
  authorize("update", "Article"),
  async (req, res) => { /* ... */ });
```

**Django (Delta) — DRF permission class:**
```python
from rest_framework.permissions import BasePermission, SAFE_METHODS

class IsEditorOrReadOnly(BasePermission):
    """ABAC: editors can edit their own; everyone else reads."""
    def has_permission(self, request, view):
        if request.method in SAFE_METHODS:
            return True
        return request.user and request.user.role == "editor"

    def has_object_permission(self, request, view, obj):
        if request.method in SAFE_METHODS:
            return True
        return obj.author_id == request.user.id

class ArticleViewSet(viewsets.ModelViewSet):
    permission_classes = [IsEditorOrReadOnly]
    # ...
```

**Laravel (Delta) — Policy class:**
```php
<?php
// app/Policies/ArticlePolicy.php
class ArticlePolicy
{
    public function update(User $user, Article $article): bool
    {
        return $user->role === "editor" && $article->author_id === $user->id
            || $user->hasRole("admin");
    }
}

// app/Providers/AuthServiceProvider.php
protected $policies = [
    Article::class => ArticlePolicy::class,
];

// In a controller:
public function update(Request $req, Article $article)
{
    $this->authorize("update", $article);   // throws 403 if denied
    // ...
}

// Or as middleware:
Route::put("/articles/{article}", [ArticleController::class, "update"])
     ->middleware("can:update,article");
```
