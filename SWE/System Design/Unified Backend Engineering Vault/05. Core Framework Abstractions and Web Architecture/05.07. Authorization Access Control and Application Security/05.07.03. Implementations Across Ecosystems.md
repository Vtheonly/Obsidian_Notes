# 05.07.03. Implementations Across Ecosystems

## What This Is

Authorization is implemented at the framework layer with five different idioms across the four target ecosystems. This note walks each ecosystem's idiomatic authorization surface: Spring Security's `@PreAuthorize`/`@Secured`/`hasRole()`/`hasAuthority()` annotations backed by SpEL expressions and AOP proxies; Laravel's `Gate` facade + `Policy` classes + `can:` middleware + `$this->authorize()` controller helper; Django's `@permission_required` decorator + `PermissionRequiredMixin` + DRF's `permission_classes`; Express's custom middleware chains or the `CASL` library. Every ecosystem solves the same problem — given an authenticated user and a request, decide permit or deny — and the differences are in *where* the policy lives (annotation vs class vs middleware vs closure) and *what* the policy can express (static role check vs dynamic SpEL vs object-based predicate).

The conceptual model unifying all four: a **Policy Enforcement Point** (the filter/middleware/decorator/AOP proxy that blocks the request) calls a **Policy Decision Point** (the role check, gate, policy class, or ability definition that returns true/false). The PEP is framework-specific; the PDP can be local (a method call) or remote (an OPA sidecar, a SpiceDB service). Read this note after the [[05.07.01. Authorization Models]] note — this is the "how does each framework actually spell it" follow-up. The production failure mode across all four ecosystems is the same: authorization checks added at the controller layer but skipped on internal service-to-service calls, leaving a backdoor where a malicious internal caller bypasses the policy.

## The Details

### *Spring Boot*: Method security via `@PreAuthorize("hasRole('ADMIN')")`, custom permission evaluators.

Spring Security's authorization surface is built on three primitives: the `AuthorizationFilter` (the PEP that runs at the end of the `SecurityFilterChain` and enforces URL-level `authorizeHttpRequests` rules), the `@PreAuthorize`/`@PostAuthorize` annotations (the method-level PEP backed by AOP proxies), and the `GrantedAuthority` collection on the `Authentication` object (the role/permission bag the PDP consults). URL-level rules are coarse: `.requestMatchers("/admin/**").hasRole("ADMIN")` is evaluated once per request before the controller is invoked. Method-level rules are fine-grained: `@PreAuthorize("hasRole('ADMIN')")` is evaluated by a CGLIB proxy that wraps the bean and short-circuits with `AccessDeniedException` before the method body runs.

The expression inside `@PreAuthorize` is **SpEL** (Spring Expression Language), which gives you method arguments, the authentication principal, and any Spring bean via the `@beanName.method()` syntax. The built-in functions are `hasRole(role)` (checks for `ROLE_<role>` authority — note the prefix), `hasAuthority(authority)` (checks for an exact authority string, no prefix), `hasAnyRole(...)`, `permitAll`, `denyAll`, `isAuthenticated`, `isAnonymous`, `principal` (the `Authentication.getPrincipal()` object). The pattern `@PreAuthorize("hasRole('ADMIN') or #article.authorId == authentication.principal.id")` is a complete ABAC policy: it permits admins and the article's owner, denies everyone else, and the check runs before the method body so the article need not be loaded yet (the `#article` is the method parameter, populated by Spring MVC from the request body or path variable).

```java
// 1. Enable method security (Spring Boot 3+)
@Configuration
@EnableMethodSecurity          // replaces @EnableGlobalMethodSecurity(prePostEnabled=true)
public class SecurityConfig { /* ... */ }

// 2. URL-level rules in the SecurityFilterChain
@Bean
SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    http.authorizeHttpRequests(auth -> auth
        .requestMatchers("/api/public/**").permitAll()
        .requestMatchers("/api/admin/**").hasRole("ADMIN")
        .requestMatchers(HttpMethod.GET, "/api/articles/**").hasAuthority("article:read")
        .requestMatchers(HttpMethod.POST, "/api/articles").hasAuthority("article:create")
        .anyRequest().authenticated());
    return http.build();
}

// 3. Method-level rules via @PreAuthorize (RBAC)
@RestController
@RequestMapping("/api/articles")
class ArticleController {

    @PreAuthorize("hasAuthority('article:create')")
    @PostMapping
    Article create(@RequestBody ArticleRequest req) { /* ... */ }

    // ABAC: admin OR the article's own author
    @PreAuthorize("hasRole('ADMIN') or @articleSecurity.isAuthor(authentication, #id)")
    @PutMapping("/{id}")
    Article update(@PathVariable Long id, @RequestBody ArticleRequest req) { /* ... */ }

    // @PostAuthorize evaluates AFTER the method returns — useful when you need
    // the loaded entity to decide. Returns the entity if permit, throws if deny.
    @PostAuthorize("hasRole('ADMIN') or returnObject.authorId == authentication.principal.id")
    @GetMapping("/{id}")
    Article get(@PathVariable Long id) { return service.find(id); }
}

// 4. Custom permission evaluator (PDP as a Spring bean)
@Component
class ArticleSecurity {
    public boolean isAuthor(Authentication auth, Long articleId) {
        Long userId = ((CustomUserDetails) auth.getPrincipal()).getId();
        return articleRepo.existsByIdAndAuthorId(articleId, userId);
    }
}
```

The `@Secured("ROLE_ADMIN")` annotation is the older, simpler alternative — it accepts only role names, no SpEL, no method arguments. The `@RolesAllowed("ADMIN")` annotation is the JSR-250 standard equivalent. Both require `@EnableMethodSecurity(securedEnabled = true)` and `@EnableMethodSecurity(jsr250Enabled = true)` respectively to activate. Use `@PreAuthorize` for new code; it is strictly more expressive. The **`hasRole('ADMIN')` vs `hasAuthority('ROLE_ADMIN')` distinction** is the most common Spring Security footgun: `hasRole` automatically prefixes the argument with `ROLE_`, so `hasRole('ADMIN')` looks for an authority named `ROLE_ADMIN`. If you stored your authorities as just `ADMIN` (no prefix), `hasRole('ADMIN')` will always return false. The fix is either to store with the prefix (the Spring convention) or use `hasAuthority('ADMIN')` (no prefix transformation).

The production failure mode is **AOP proxy bypass**: `@PreAuthorize` works only when the method is invoked *through the Spring proxy*. If a method in the same class calls another `@PreAuthorize`-annotated method directly via `this.otherMethod()`, the proxy is bypassed and the check does not run — the authorization is silently skipped. The same applies to `@Transactional`, `@Async`, `@Cacheable` — all the AOP annotations. The fixes: (a) split the methods into separate beans so the call goes through a proxy, (b) inject `AopContext.currentProxy()` and call through it (requires `@EnableAspectJAutoProxy(exposeProxy = true)`), (c) accept that internal calls are trusted and rely on the controller-layer check. Most teams pick (c) and document the rule "no internal service method assumes authorization was done — but it must be done at the controller". The diagnostic when this fails: a security audit finds that a sensitive method is callable from another service method without the check; the bug is silent because the call path through the controller does enforce the annotation, but the internal path bypasses it.

### *Laravel*: Gates and Policies (`Gate::define`, `make:policy`), authorizing controller actions via `$this->authorize()`.

Laravel's authorization surface is two parallel APIs that share the same backend: **Gates** (closures, for cross-resource policies like "can the user access the admin dashboard") and **Policies** (classes, for resource-specific policies like "can the user update this Article"). Both register their checks via `Gate::define()` (for gates) or via a `Policy` class with methods named after the action (`update`, `delete`, `create`). Both are queried via `Gate::allows('update-article', $article)`, the `@can('update-article', $article)` Blade directive, the `$user->can('update-article', $article)` User trait method, the `$this->authorize('update-article', $article)` controller helper, or the `can:update-article,article` route middleware.

The flow: at boot, `AuthServiceProvider` (Laravel 10-) or `AppServiceProvider` (Laravel 11+) maps models to policy classes via the `$policies` property. When a policy check is made, Laravel resolves the policy class for the resource type (e.g., `ArticlePolicy` for `Article`), calls the method matching the action name (e.g., `update(User $user, Article $article)`), and returns the boolean. The first argument is always the authenticated user; subsequent arguments are the resource instances passed to the check. If no policy is registered, Laravel falls back to the Gate of the same name. The `Gate::before()` callback lets you short-circuit — typically to allow admins through without further checks: `Gate::before(fn(User $u, string $ability) => $u->hasRole('super-admin') ? true : null)` (returning `null` means "let the normal policy decide").

```php
<?php
// 1. Generate a policy class
// php artisan make:policy ArticlePolicy --model=Article

// app/Policies/ArticlePolicy.php
namespace App\Policies;

use App\Models\User;
use App\Models\Article;

class ArticlePolicy
{
    // Called before EVERY policy method on this class; return true/false to
    // short-circuit, null to fall through to the specific method.
    public function before(User $user, string $ability): ?bool
    {
        return $user->hasRole('super-admin') ? true : null;
    }

    public function viewAny(User $user): bool
    {
        return true;     // any authenticated user can list
    }

    public function view(User $user, Article $article): bool
    {
        return true;
    }

    public function create(User $user): bool
    {
        return $user->role === 'editor' || $user->role === 'admin';
    }

    public function update(User $user, Article $article): bool
    {
        return $article->author_id === $user->id        // ABAC: ownership
            || $user->role === 'editor'                 // RBAC: editor override
            || $user->hasRole('admin');
    }

    public function delete(User $user, Article $article): bool
    {
        return $user->hasRole('admin');
    }
}

// 2. Register the policy
// app/Providers/AppServiceProvider.php (Laravel 11+) or AuthServiceProvider.php (Laravel 10-)
public function boot(): void
{
    Gate::policy(Article::class, ArticlePolicy::class);

    // Standalone Gate (not tied to a model) — useful for cross-cutting abilities
    Gate::define('access-admin', function (User $user) {
        return $user->hasRole('admin') || $user->hasRole('auditor');
    });
}

// 3. Enforce in a controller
// app/Http/Controllers/ArticleController.php
class ArticleController extends Controller
{
    public function update(Request $req, Article $article)
    {
        $this->authorize('update', $article);   // throws AuthorizationException → 403
        $req->validate(['title' => 'required|string']);
        $article->update($req->only('title', 'body'));
        return response()->json($article);
    }
}

// 4. Enforce via route middleware (the policy runs before the controller)
// routes/api.php
Route::put('/articles/{article}', [ArticleController::class, 'update'])
     ->middleware('can:update,article');

// 5. Enforce in Blade templates
// resources/views/articles/show.blade.php
@can('update', $article)
    <a href="{{ route('articles.edit', $article) }}">Edit</a>
@endcan
```

What is automatic in Laravel that is manual in Spring? (1) **Resource auto-resolution**: Laravel's route-model binding resolves `{article}` to an `Article` model instance before the policy runs, so the policy method receives the entity directly — no manual fetch. (2) **Policy auto-discovery**: if you do not register a policy explicitly, Laravel guesses the class name (`Article` → `App\Policies\ArticlePolicy`) and uses it if it exists. (3) **The 403 response translation**: `$this->authorize()` throws `AuthorizationException`, which Laravel's exception handler converts to a 403 with a default error payload. In Spring, `AccessDeniedException` is caught by `ExceptionTranslationFilter` and translated to a 403, but you must configure the `AccessDeniedHandler` yourself if you want a custom body. What is manual here that is automatic there? (1) **The "before" hook for super-admin**: Laravel's `before()` lets you short-circuit every policy with one closure; in Spring you write a custom `PermissionEvaluator` or use `@PreAuthorize("hasRole('SUPER_ADMIN') or ...")` on every method. (2) **Policy registration**: Laravel requires explicit `Gate::policy()` registration (or auto-discovery); Spring wires nothing automatically — every `@PreAuthorize` is a string the Spring AOP proxy parses at runtime. The runtime invariant exposed differently: Laravel's PHP-FPM shared-nothing model means every request re-resolves the policy class via the service container, so policy caching is per-request; Spring's `MethodSecurityExpressionHandler` caches the parsed SpEL expression across requests in the JVM heap, so the parsing cost is amortized.

### *Django*: Permission classes (`IsAuthenticated`, `DjangoModelPermissions`), user permission mappings.

Django authorization splits into two layers that are commonly conflated: the **Django auth backend** (the `ModelBackend` that powers `user.has_perm('articles.change_article')` checks for server-rendered views) and **Django REST Framework's permission classes** (the `BasePermission` subclasses that power `permission_classes` for API views). The two layers have different APIs and different defaults. The auth backend is permission-name-based (`app_label.action_model` like `articles.delete_article`), populated from the `auth_permission` table (auto-generated from each model's `Meta.default_permissions = ['add', 'change', 'view', 'delete']`), assigned to users via `Group.permissions` or `User.user_permissions`. The DRF layer is class-based: you write a `BasePermission` subclass with `has_permission(request, view)` (view-level) and `has_object_permission(request, view, obj)` (object-level) methods, and DRF calls them at the right points in the request lifecycle.

The split between `has_permission` and `has_object_permission` matters: `has_permission` runs *before* the view body, when DRF does not yet know which object is being acted on (it has only the URL pattern and the HTTP method). `has_object_permission` runs *after* `get_object()` retrieves the specific instance — typically inside `retrieve()`, `update()`, `destroy()` actions of a `ModelViewSet`. This means a check like "user can edit articles they own" must be split: `has_permission` checks "is this user an editor at all" (cheap, no DB), `has_object_permission` checks "is this article's author the current user" (DB lookup of the article). The classic bug: putting the ownership check in `has_permission`, which runs before the object is fetched, so the check cannot access the article — and the developer "solves" this by fetching the article inside `has_permission`, doing it twice, and doubling the DB load.

```python
# settings.py — DRF defaults
REST_FRAMEWORK = {
    "DEFAULT_PERMISSION_CLASSES": [
        "rest_framework.permissions.IsAuthenticated",   # default for all views
    ],
    "DEFAULT_AUTHENTICATION_CLASSES": [
        "rest_framework_simplejwt.authentication.JWTAuthentication",
    ],
}

# 1. Built-in DRF permission classes
from rest_framework.permissions import (
    IsAuthenticated,           # request.user.is_authenticated == True
    IsAdminUser,               # request.user.is_staff == True
    AllowAny,                  # no check
    DjangoModelPermissions,    # maps HTTP verb → app_label.action_model permission
    DjangoModelPermissionsOrAnonReadOnly,
)

# 2. Custom permission class — ABAC ownership check
from rest_framework.permissions import BasePermission, SAFE_METHODS

class IsEditorOrReadOnly(BasePermission):
    """Editors can write their own articles; anyone can read; admins can do anything."""
    message = "you must be the author or an editor to modify this article"

    def has_permission(self, request, view):
        # View-level: runs before get_object()
        if request.method in SAFE_METHODS:                # GET, HEAD, OPTIONS
            return True
        return bool(request.user and request.user.is_authenticated
                    and request.user.role in ("editor", "admin"))

    def has_object_permission(self, request, view, obj):
        # Object-level: runs after get_object() returns the specific Article
        if request.method in SAFE_METHODS:
            return True
        if request.user.is_staff:                          # admin override
            return True
        return obj.author_id == request.user.id            # ownership check

# 3. Apply via class attribute, decorator, or DEFAULT_PERMISSION_CLASSES
from rest_framework import viewsets

class ArticleViewSet(viewsets.ModelViewSet):
    queryset = Article.objects.all()
    serializer_class = ArticleSerializer
    permission_classes = [IsEditorOrReadOnly]

    # Per-action override
    def get_permissions(self):
        if self.action == "destroy":
            return [IsAdminUser()]                         # only admins can delete
        return [IsEditorOrReadOnly()]

# 4. Function-based view with @permission_required (Django auth backend, not DRF)
from django.contrib.auth.decorators import permission_required, login_required

@login_required
@permission_required("articles.change_article", raise_exception=True)
def edit_article(request, article_id):
    article = get_object_or_404(Article, pk=article_id)
    # ...

# 5. Class-based view with PermissionRequiredMixin
from django.contrib.auth.mixins import PermissionRequiredMixin, LoginRequiredMixin
from django.views.generic import UpdateView

class ArticleUpdateView(LoginRequiredMixin, PermissionRequiredMixin, UpdateView):
    model = Article
    fields = ["title", "body"]
    permission_required = "articles.change_article"
    raise_exception = True
```

The Django auth backend's permission naming convention is `app_label.action_model` — `articles.change_article`, `users.delete_user`, `blog.view_post`. The `action` part comes from `Model.Meta.default_permissions` (default `['add', 'change', 'view', 'delete']`) and `permissions` (custom, e.g., `permissions = [('publish', 'Can publish article')]` → `articles.publish_article`). These are auto-created by `makemigrations` + `migrate` and live in the `auth_permission` table. Assigning them to users is admin-only — the Django admin's "User change" page has a widget. For programmatic assignment: `user.user_permissions.add(Permission.objects.get(codename='change_article'))`. The check is `user.has_perm('articles.change_article')` — cached on the user instance after the first call within a request.

The production failure mode of Django authorization is **the `permission_required` decorator running before `get_object`**, so you cannot use it for object-level checks. Developers who want ownership checks on a function-based view often write `@permission_required('articles.change_article')` and then a manual `if article.author_id != request.user.id: raise PermissionDenied` inside the view body — which works but bypasses the framework's clean permission-class abstraction. The better pattern is to use DRF's `ModelViewSet` + `permission_classes` + `has_object_permission` even for non-API views (via `django-rest-framework`'s `APIView`), or to write a custom decorator that fetches the object and runs the ownership check explicitly. The diagnostic: grep for `raise PermissionDenied` outside of `permission_classes` — every hit is a place where the framework's authorization surface was bypassed.

### *Express*: Custom role-checking middleware chains, CASL authorization library

Express ships with no authorization primitive at all — there is no `@PreAuthorize`, no `Gate`, no `permission_classes`. The framework's position is that authorization is application code, and you compose it via middleware. The two idioms are: **custom middleware functions** for simple role checks (`function requireRole(role) { return (req, res, next) => req.user?.roles?.includes(role) ? next() : res.status(403).json({ error: 'forbidden' }); }`) and the **CASL library** (`@casl/ability`) for attribute-based policies. The two idioms compose: CASL defines the abilities (the PDP), middleware enforces them (the PEP).

CASL's model is **abilities** — a list of `can(action, subject, conditions?)` rules. The `defineAbilityFor(user)` function builds an `Ability` object from the user's roles and attributes. The `ability.can(action, subject)` method returns true/false. The `subject` is either a string (for class-level checks like `can('read', 'Article')`) or an object with a `__caslSubjectType__` field (for instance-level checks like `can('update', specificArticle)` where the article's `authorId` is matched against the rule's `conditions: { authorId: user.id }`). The conditions use MongoDB-style query syntax (`{ authorId: user.id, status: 'published' }`) which CASL evaluates against the subject object. The performance: a single `ability.can()` call is ~10µs, so checking per-request is cheap; building the ability from scratch per request is ~100µs and the recommended pattern (the ability is user-scoped, you cannot share it across requests safely).

```typescript
// src/auth/abilities.ts
import { AbilityBuilder, createMongoAbility, MongoAbility } from "@casl/ability";

export type Article = { id: string; authorId: string; status: "draft" | "published" };
export type AppAbility = MongoAbility<[string, string | Article]>;

export function defineAbilityFor(user: { id: string; role: "admin" | "editor" | "viewer" }): AppAbility {
  const { can, cannot, build } = new AbilityBuilder<AppAbility>(createMongoAbility);

  if (user.role === "admin") {
    can("manage", "all");                              // full access
  } else if (user.role === "editor") {
    can("read", "Article");                            // view all
    can("update", "Article", { authorId: user.id });   // edit own
    can("create", "Article");
    cannot("delete", "Article");                        // explicit deny (overrides can)
  } else {
    can("read", "Article", { status: "published" });   // only published
  }

  return build();
}

// src/auth/middleware.ts
import { Request, Response, NextFunction } from "express";
import { defineAbilityFor, AppAbility, Article } from "./abilities";

declare global {
  namespace Express {
    interface Request {
      user?: { id: string; role: "admin" | "editor" | "viewer" };
      ability?: AppAbility;
    }
  }
}

// PEP: build the ability per request and attach to req
export function loadAbility(req: Request, res: Response, next: NextFunction) {
  if (!req.user) return res.status(401).json({ error: "unauthenticated" });
  req.ability = defineAbilityFor(req.user);
  next();
}

// PEP: enforce a specific action on a subject class
export function authorize(action: string, subject: string) {
  return (req: Request, res: Response, next: NextFunction) => {
    if (!req.ability?.can(action, subject)) {
      return res.status(403).json({ error: "forbidden" });
    }
    next();
  };
}

// PEP: enforce on a loaded instance (for object-level ABAC)
export function authorizeObject(action: string, fetchSubject: (req: Request) => Article) {
  return async (req: Request, res: Response, next: NextFunction) => {
    const subject = await fetchSubject(req);
    if (!req.ability?.can(action, subject)) {
      return res.status(403).json({ error: "forbidden" });
    }
    next();
  };
}

// src/app.ts
import express from "express";
import { requireAuth } from "./auth/middleware";
import { loadAbility, authorize, authorizeObject } from "./auth/middleware";
import { articleRepo } from "./db";

const app = express();
app.use(express.json());
app.use(requireAuth);     // populates req.user
app.use(loadAbility);     // populates req.ability

// Class-level: any editor can create
app.post("/api/articles",
  authorize("create", "Article"),
  createArticle);

// Object-level: must be the author (or admin) to update
app.put("/api/articles/:id",
  authorizeObject("update", (req) => articleRepo.find(req.params.id)),
  updateArticle);

// Plain role-check middleware (simplest case, no CASL)
function requireRole(role: string) {
  return (req: Request, res: Response, next: NextFunction) => {
    if (!req.user?.roles?.includes(role)) {
      return res.status(403).json({ error: "forbidden" });
    }
    next();
  };
}

app.delete("/api/admin/users/:id",
  requireRole("admin"),
  deleteUser);
```

What is automatic in Spring/Laravel/Django that is manual here? (1) **The PEP**: every other framework provides a declarative PEP (annotation, gate, policy class) that runs at the right point in the request lifecycle. In Express you write the middleware by hand, register it in the right order, and remember to call it on every route. (2) **The object-loading sequence**: DRF's `has_object_permission` runs after `get_object()` by construction; in Express you must explicitly fetch the object inside the middleware (or pass a fetcher function), which means a database round-trip before the authorization check. (3) **The 403 response**: every framework translates authorization failure to a 403 automatically; in Express you write `res.status(403).json(...)` in every middleware, and inconsistency is the norm. What is automatic here that is manual there? (1) **Plain functions**: the entire authorization stack is plain TypeScript functions and arrays; no AOP proxies, no reflection, no compiled-then-runtime-parsed annotations. The debugger steps through every line. (2) **Composability**: middleware is composable by array concatenation — `[requireAuth, loadAbility, authorize("create", "Article")]` is the entire chain, and you can reorder or replace any element. The runtime invariant exposed differently: Node's single-threaded event loop means there is no per-thread `SecurityContext` (unlike Spring's thread-local); `req.user` and `req.ability` are per-request by construction, set in the request object that is garbage-collected when the response is sent. The failure mode structurally impossible here is the Spring AOP-proxy bypass (internal `this.method()` calls); the failure mode *new* here is **middleware-ordering bugs** — if `loadAbility` is registered after `authorize`, `req.ability` is undefined and every check returns 403 (or worse, if you `?.can()` it returns undefined and the check is silently skipped, granting access).

## Cross-Ecosystem Code

The same authorization requirement — "user can update an article only if they are an editor and the article is theirs, or they are an admin" — implemented in all four ecosystems.

**Spring Security (Anchor):**
```java
@PreAuthorize("hasRole('ADMIN') or (hasRole('EDITOR') and #article.authorId == authentication.principal.id)")
@PutMapping("/{id}")
Article update(@PathVariable Long id, @RequestBody ArticleRequest req) {
    return service.update(id, req);
}
```

**Express (CASL):**
```typescript
// Ability definition (once per user per request)
can("update", "Article", { authorId: user.id });   // editors, own articles
if (user.role === "admin") can("manage", "all");   // admins override

// Middleware (per route)
app.put("/api/articles/:id",
  authorizeObject("update", async (req) => await articleRepo.find(req.params.id)),
  updateArticle);
```

**Django (DRF):**
```python
class IsEditorOrReadOnly(BasePermission):
    def has_permission(self, request, view):
        if request.method in SAFE_METHODS:
            return True
        return request.user.role in ("editor", "admin")

    def has_object_permission(self, request, view, obj):
        if request.method in SAFE_METHODS:
            return True
        if request.user.role == "admin":
            return True
        return obj.author_id == request.user.id

class ArticleViewSet(viewsets.ModelViewSet):
    permission_classes = [IsEditorOrReadOnly]
```

**Laravel (Policy):**
```php
class ArticlePolicy {
    public function before(User $user, string $ability): ?bool {
        return $user->hasRole('admin') ? true : null;   // admin short-circuit
    }

    public function update(User $user, Article $article): bool {
        return $user->role === 'editor' && $article->author_id === $user->id;
    }
}

// Controller:
$this->authorize('update', $article);

// Or as middleware:
Route::put('/articles/{article}', [ArticleController::class, 'update'])
     ->middleware('can:update,article');
```
