# 05.01.03. Rapid Delta Translations Routing

## What This Note Is

This is a **delta translation note**. It is intentionally short. Read it **after** completing the anchor implementation in the sibling Spring Boot note. The point is to answer one question:

> What is different in this ecosystem, and what is automatic that I had to do manually in the anchor?

If you find yourself re-learning the concept here, you have not finished the anchor. Go back.

## Implementation Deltas

The deltas to internalize:

- *TypeScript / Express*: `path-to-regexp` linear compilation, router layering, and regex path matches.
- *Python / Django*: URLconf regex lists, path converters (`<int:id>`, `<str:slug>`), and recursive `include()` namespaces.
- *Python / Flask*: Werkzeug `Map`, `Rule` tree, and URL routing decorators.
- *PHP / Laravel*: FastRoute regex grouping, cached route arrays (`php artisan route:cache`), and Route Model Binding.

## The Details

### *TypeScript / Express*: `path-to-regexp` linear compilation, router layering, and regex path matches

Express's router is a linked list of "layers". Each layer is a `(regexp, keys, handler)` triple compiled at registration time by `path-to-regexp`. At request time the router iterates the layers in registration order, calls `regexp.exec(path)`, and invokes the first matching handler with `req.params` populated from the regex capture groups. There is no tree, no compiled cache, no startup-time route table; routes are added imperatively and held in memory for the life of the Node.js process.

```typescript
import { Router, Request, Response, NextFunction } from "express";

const router = Router();

// path-to-regexp compiles "/api/users/:id" to ^\/api\/users\/([^\/]+)\/?$
// at registration time. The capture group becomes req.params.id.
router.get("/api/users/:id", async (req: Request, res: Response, next: NextFunction) => {
  try {
    const id = Number(req.params.id);   // manual string → number coercion
    if (Number.isNaN(id)) return res.status(400).json({ error: "invalid_id" });
    const user = await userService.find(id);
    if (!user) return res.status(404).json({ error: "not_found" });
    res.json(user);
  } catch (err) {
    next(err);   // hand off to the error-handling middleware
  }
});

// Sub-routers compose via app.use("/api", router). path-to-regexp matches
// the prefix once, strips it, and hands the rest of the path to the sub-router.
// This is how you build /api/v1/users, /api/v2/users, etc.
import express from "express";
const app = express();
app.use("/api/v1", router);
app.use("/api/v2", v2router);
app.listen(8080);
```

What is automatic here that was manual in the anchor: nothing. Express has no `ConversionService`, no `@PathVariable` annotation, no `PathPattern` tree. Every coercion (`Number(req.params.id)`) is the developer's job. Every 400 on malformed input is the developer's job. Every "did this route even match?" question is answered by walking the layer list and checking `regexp.exec` — there is no introspection equivalent to Spring's `RequestMappingHandlerMapping.getHandlerMethods()`.

What is manual here that was automatic in the anchor: type coercion, validation, content negotiation, the 404-vs-400 distinction (Express will call `next()` with no match, which is a 404, but a malformed path variable that the handler parses to `NaN` is your problem to convert into a 400). The `next(err)` convention replaces Spring's `@ControllerAdvice` — an error passed to `next` is routed to the next middleware whose signature has 4 parameters `(err, req, res, next)`.

The runtime invariant exposed differently: Node's single-threaded event loop means there is no Tomcat-style thread pool to starve, but a synchronous regex match on a 5,000-route table will block the event loop and starve every other connection. The fix in Express is the same as in Spring — move to a tree-based router (the `find-my-way` package, used by Fastify, is a radix-tree router that is O(K)).

### *Python / Django*: URLconf regex lists, path converters (`<int:id>`, `<str:slug>`), and recursive `include()` namespaces

Django's router is a Python list of `path()` or `re_path()` entries. Each `path("users/<int:uid>/", views.user_detail)` compiles to a regex (`^users/(?P<uid>[0-9]+)/$`) and the regex is matched in list order. The `<int:uid>` syntax is a path converter — Django ships `str`, `int`, `slug`, `uuid`, `path`, and you can register custom converters via `register_converter(MyConverter, "my")`.

```python
# project/urls.py — root URLconf
from django.urls import path, include

urlpatterns = [
    path("api/v1/", include("orders.urls")),    # delegates /api/v1/* to orders/urls.py
    path("api/v2/", include(("orders.v2.urls", "orders_v2"), namespace="v2")),
    path("admin/", admin.site.urls),
]

# orders/urls.py — included by project/urls.py
from django.urls import path
from . import views

urlpatterns = [
    path("orders/<uuid:order_id>/", views.order_detail, name="order_detail"),
    path("orders/", views.order_list, name="order_list"),
    path("orders/<uuid:order_id>/items/<int:item_id>/",
         views.order_item_detail, name="order_item_detail"),
]

# orders/views.py
from django.http import JsonResponse
from django.shortcuts import get_object_or_404

def order_detail(request, order_id):       # order_id is already a UUID, coerced
    order = get_object_or_404(Order, id=order_id)
    return JsonResponse({"id": str(order.id), "total": order.total})
```

What is automatic here that was manual in the anchor: path-converter type coercion (`<int:uid>` is a Python `int`, `<uuid:order_id>` is a `UUID`, no `Number(req.params.id)` step). The `name=` attribute gives every route a stable identifier, and `{% url 'order_detail' order.id %}` in templates or `reverse('order_detail', args=[order.id])` in code generates the URL — Spring has no equivalent. The `namespace` parameter lets you distinguish `v1:order_detail` from `v2:order_detail` when both are included.

What is manual here that was automatic in the anchor: Django does not have content negotiation out of the box (use Django REST Framework for that). Django does not have `@Valid @RequestBody` (use DRF serializers or `django.forms`). The 404 from `get_object_or_404` is convenient but throws `Http404`, which Django's middleware catches and renders as the default 404 page — to return JSON you need a custom `handler404`.

The runtime invariant exposed differently: CPython's GIL means a single Django process handles one request at a time per worker. To handle 1,000 concurrent requests you run 1,000 gunicorn/gevent workers or 1,000 uwsgi processes. There is no equivalent to Tomcat's "200 threads sharing one JVM" model; Django's per-worker process model is closer to PHP-FPM's shared-nothing design than to Spring's.

### *Python / Flask*: Werkzeug `Map`, `Rule` tree, and URL routing decorators

Flask's router is Werkzeug's `Map`. Each `@app.route("/users/<int:uid>")` decorator adds a `Rule` to the `Map`. The `Map` builds an internal radix-tree-like structure (Werkzeug calls it a "rule set" — it groups rules by their static prefix and applies them in a sorted order). At request time `MapAdapter.match(path, method)` walks the rule set, returns `(endpoint, arguments)`, and Flask looks up the view function registered for that endpoint.

```python
from flask import Flask, jsonify, request, abort
from werkzeug.exceptions import NotFound

app = Flask(__name__)

# Werkzeug converters: <int:uid>, <uuid:trace_id>, <path:subpath>, <string:name>
# Custom converters can be registered via app.url_map.converters['my'] = MyConverter
@app.get("/api/users/<int:uid>")
def get_user(uid: int):
    user = user_service.find(uid)
    if user is None:
        raise NotFound(f"user {uid} not found")   # Flask maps to 404 JSON
    return jsonify(user)

@app.post("/api/users", defaults={"page": 0})
@app.post("/api/users/page/<int:page>")
def list_users(page: int):
    # Two routes share one view function — Werkzeug's "defaults" parameter
    return jsonify(user_service.list(page=page))

# Blueprint — equivalent to Express's sub-router, Django's include()
from flask import Blueprint
admin_bp = Blueprint("admin", __name__, url_prefix="/admin")

@admin_bp.route("/users/<int:uid>/delete")
def admin_delete_user(uid: int):
    user_service.delete(uid)
    return "", 204

app.register_blueprint(admin_bp)

# Reverse URL lookup — equivalent to Django's reverse()
with app.test_request_context():
    print(__import__("flask").url_for("get_user", uid=42))
    # → /api/users/42
```

What is automatic here that was manual in the anchor: Werkzeug's converter system (`<int:uid>`, `<uuid:trace_id>`) is the same idea as Django's path converters and Spring's `ConversionService`, but the syntax is in the route string itself rather than in a separate annotation. The `url_for("get_user", uid=42)` reverse-URL lookup is automatic and is the Flask equivalent of Django's `reverse()`. Werkzeug's `Rule` matching is O(N) in the worst case but the rule set is sorted by specificity at startup, so common cases are O(1)-ish.

What is manual here that was automatic in the anchor: content negotiation (`request.accept_mimetypes` parsing is your job), request body validation (use `marshmallow` or `pydantic`), `@Valid`-style declarative validation (no built-in equivalent). Flask's `abort(404)` and `raise NotFound` are the only built-in error responses — everything else is a manual `return jsonify(...), status_code`.

The runtime invariant exposed differently: same GIL constraint as Django. Flask is typically deployed under gunicorn+gevent, gunicorn+sync workers, or uWSGI. The dev server (`flask run`) is single-threaded and must never be used in production — under load it serialises every request.

### *PHP / Laravel*: FastRoute regex grouping, cached route arrays (`php artisan route:cache`), and Route Model Binding

Laravel's router is `FastRoute` under the hood. Routes are grouped by HTTP method, then within each method they are compiled into a single regex with alternation: `^(?|/users/([^/]+)|/orders/([^/]+))$`. The regex engine's NFA does the dispatching. `php artisan route:cache` persists the compiled regex to `bootstrap/cache/routes-v7.php` so PHP-FPM does not have to recompile on every request — critical for a shared-nothing process model where each worker process boots the framework fresh.

```php
<?php
// routes/api.php
use Illuminate\Support\Facades\Route;
use App\Http\Controllers\OrderController;
use App\Models\Order;

// Route Model Binding — Laravel resolves {order} to an Eloquent model
// by querying the database for Order::where("id", $value)->firstOrFail().
// {order:slug} resolves by the slug column instead of the primary key.
Route::get("/orders/{order:slug}", [OrderController::class, "show"]);
Route::post("/orders", [OrderController::class, "store"]);
Route::put("/orders/{order}", [OrderController::class, "update"]);
Route::delete("/orders/{order}", [OrderController::class, "destroy"]);

// Route grouping with shared middleware and prefix
Route::middleware(["auth:sanctum", "throttle:60,1"])
     ->prefix("/v1")
     ->group(function () {
         Route::get("/users/{id}", [UserController::class, "show"]);
         Route::post("/users", [UserController::class, "store"]);
     });

// app/Http/Controllers/OrderController.php
class OrderController extends Controller {
    public function show(Order $order) {       // ← Order is auto-resolved
        return response()->json($order);
    }
    public function store(Request $req) {
        $data = $req->validate([
            "user_id" => "required|uuid|exists:users,id",
            "total"   => "required|numeric|min:0",
        ]);
        return response()->json(Order::create($data), 201);
    }
}
```

```bash
# Cache the route table to disk — shaves 50-80ms off every cold PHP-FPM request
php artisan route:cache

# Inspect the compiled routes
php artisan route:list --path=api
# GET|HEAD  api/v1/users/{id}   v1 › UserController@show   auth:sanctum  throttle:60,1
# POST      api/v1/users         v1 › UserController@store  auth:sanctum  throttle:60,1
```

What is automatic here that was manual in the anchor: Route Model Binding. Spring's `@PathVariable UUID id` gives you the ID; Laravel's `Order $order` parameter type-hint gives you the fully-loaded Eloquent model, having queried the database for you. The `{order:slug}` syntax overrides the default resolution column. This is more powerful than Spring's equivalent and saves a `repository.findById(id)` call in every controller method.

What is manual here that was automatic in the anchor: nothing obvious. Laravel's `validate()` method is the equivalent of `@Valid` — it throws `ValidationException` on failure, which Laravel's exception handler maps to a 422 with a JSON error body. Laravel's `throttle:60,1` middleware is rate limiting built into the router (Spring requires a separate Resilience4j or Bucket4j dependency). Content negotiation is handled by `response()->json()` / `response()->xml()` etc.

The runtime invariant exposed differently: PHP-FPM's shared-nothing process model means every request bootstraps the framework from scratch — unless `route:cache`, `config:cache`, and `view:cache` are all run, the per-request startup cost is 80–150ms. This is structurally invisible on the JVM (Spring Boot boots once and serves forever) and is the reason Laravel Octane (a long-lived PHP process model, like Swoole or RoadRunner) exists — it keeps the framework in memory across requests and shaves 100ms off p99.

## Cross-Ecosystem Code

The same routing concept implemented side-by-side. The shape is identical: declare a path with a typed parameter, register a handler, coerce the parameter, return JSON.

**Spring Boot (Anchor):**
```java
@RestController
@RequestMapping("/api/users")
class UserController {
    @GetMapping("/{id}")
    User get(@PathVariable Long id) { return repo.findById(id).orElseThrow(); }

    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    User create(@Valid @RequestBody UserDto dto) { return repo.save(dto.toEntity()); }
}
```

**Express (Delta):**
```typescript
import { Router } from "express";
const r = Router();

r.get("/api/users/:id", (req, res) => {
  const id = Number(req.params.id);
  res.json(userRepo.find(id));
});

r.post("/api/users", (req, res) => {
  res.status(201).json(userRepo.create(req.body));
});
```

**Flask (Delta):**
```python
from flask import Flask, jsonify, request
app = Flask(__name__)

@app.get("/api/users/<int:uid>")
def get_user(uid): return jsonify(user_repo.find(uid))

@app.post("/api/users")
def create_user(): return jsonify(user_repo.create(request.get_json())), 201
```

**Laravel (Delta):**
```php
<?php
use Illuminate\Support\Facades\Route;
Route::get("/api/users/{user}", fn (User $user) => $user);   // Route Model Binding
Route::post("/api/users", [UserController::class, "store"]);
```

## Delta Checklist

> [!tip] What to write down after the translation
> - What was automatic here that I had to do manually in the anchor? (Laravel: Route Model Binding. Django/Flask: path converters. Express: nothing.)
> - What was manual here that was automatic in the anchor? (Express: type coercion, validation, content negotiation. Django: content negotiation. Flask: validation, content negotiation.)
> - Which runtime invariant is exposed differently? (Node: event loop. CPython: GIL. PHP-FPM: shared-nothing, per-request bootstrap. JVM: long-lived, multi-threaded.)
> - Which failure mode is structurally impossible here? (Express: thread-pool starvation, but event-loop starvation is the equivalent. Laravel: cross-request memory leaks, because each request is a fresh process — but per-request boot cost is the new failure.)
> - Which failure mode is new here? (Express: callback hell / unhandled promise rejections crashing the process. Django/Flask: GIL contention under CPU-bound handlers. Laravel: per-request bootstrap cost dominates p99.)
