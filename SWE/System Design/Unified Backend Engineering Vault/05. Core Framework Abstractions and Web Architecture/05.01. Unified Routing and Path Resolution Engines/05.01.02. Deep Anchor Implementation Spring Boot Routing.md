# 05.01.02. Deep Anchor Implementation Spring Boot Routing

## Why This Is the Anchor

This note is the **deep anchor implementation** — the place where you build the routing concept in Spring Boot with production-grade depth. Per the Anchor and Delta protocol ([[00.02. The Anchor and Delta Learning Protocol]]), you must break this implementation before moving to the delta notes. The point is to acquire scars: real experience with the failure modes that this concept produces under load.

Spring Boot is the anchor for routing because it exposes every layer of the request-resolution pipeline: the Servlet container (Tomcat) that accepts the TCP connection, the `DispatcherServlet` that drives the request, the `HandlerMapping` that resolves the controller method, the `HandlerAdapter` that invokes it, the `PathPatternParser` that matches the URL, and the `ConversionService` that coerces path variables to typed Java objects. Express and Flask hide most of this behind a single `app.get(path, handler)` call; Spring forces you to understand what is happening at each layer because each layer has a tunable knob and a distinct failure mode.

## What You Will Build

The implementation covers:

- Spring MVC dispatcher architecture: `DispatcherServlet`, `HandlerMapping`, `HandlerAdapter`.
- Radix tree implementation: `PathPatternParser` vs. legacy `AntPathMatcher`.
- Writing an enterprise REST endpoint with path variables, query params, and content-negotiation headers.

## Anchor Implementation (Spring Boot)

The code below is a complete, runnable Spring Boot 3.x REST controller for an Orders resource. It demonstrates typed path variables, query parameters with defaults, content negotiation, the `WebMvcConfigurer` extension point, and the load-test command that will starve Tomcat's thread pool.

```java
// src/main/java/com/example/orders/OrderController.java
package com.example.orders;

import java.util.List;
import java.util.UUID;
import org.springframework.http.HttpStatus;
import org.springframework.http.MediaType;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/api/v1/orders")
public class OrderController {

    private final OrderService service;

    // Constructor injection — Spring resolves OrderService from the ApplicationContext
    public OrderController(OrderService service) {
        this.service = service;
    }

    // GET /api/v1/orders/{id} — typed path variable (UUID)
    // Spring's PathPatternParser matches /api/v1/orders/{id}, captures the segment,
    // and ConversionService coerces it to java.util.UUID. Coercion failure → 400.
    @GetMapping(value = "/{id}", produces = MediaType.APPLICATION_JSON_VALUE)
    public OrderDto get(@PathVariable UUID id) {
        return service.find(id);
    }

    // GET /api/v1/orders?status=PENDING&page=0&size=20
    // Query params with defaults and required=false for optional filters.
    @GetMapping(produces = MediaType.APPLICATION_JSON_VALUE)
    public List<OrderDto> list(
            @RequestParam(name = "status", required = false) OrderStatus status,
            @RequestParam(name = "page", defaultValue = "0") int page,
            @RequestParam(name = "size", defaultValue = "20") int size) {
        return service.list(status, page, size);
    }

    // POST /api/v1/orders — JSON request body validated by @Valid
    // Content negotiation: Accept: application/json → JSON response
    @PostMapping(consumes = MediaType.APPLICATION_JSON_VALUE,
                 produces = MediaType.APPLICATION_JSON_VALUE)
    @ResponseStatus(HttpStatus.CREATED)
    public OrderDto create(@Valid @RequestBody CreateOrderRequest req) {
        return service.create(req);
    }

    // PUT /api/v1/orders/{id}/status — path variable + request body together
    @PutMapping(value = "/{id}/status",
                consumes = MediaType.APPLICATION_JSON_VALUE)
    public ResponseEntity<Void> updateStatus(@PathVariable UUID id,
                                             @Valid @RequestBody StatusUpdateRequest req) {
        service.updateStatus(id, req.status());
        return ResponseEntity.noContent().build();
    }
}
```

```java
// src/main/java/com/example/orders/OrderService.java
package com.example.orders;

import java.util.List;
import java.util.UUID;
import org.springframework.stereotype.Service;

@Service
public class OrderService {
    private final OrderRepository repo;

    public OrderService(OrderRepository repo) { this.repo = repo; }

    public OrderDto find(UUID id) {
        return repo.findById(id)
                   .map(OrderDto::from)
                   .orElseThrow(() -> new OrderNotFoundException(id));
    }

    public List<OrderDto> list(OrderStatus status, int page, int size) {
        return repo.list(status, page, size).stream().map(OrderDto::from).toList();
    }

    public OrderDto create(CreateOrderRequest req) {
        Order o = Order.newOrder(req.userId(), req.total());
        return OrderDto.from(repo.save(o));
    }

    public void updateStatus(UUID id, OrderStatus status) {
        Order o = repo.findById(id).orElseThrow(() -> new OrderNotFoundException(id));
        o.setStatus(status);
        repo.save(o);
    }
}
```

```java
// src/main/java/com/example/orders/WebConfig.java
package com.example.orders;

import org.springframework.context.annotation.Configuration;
import org.springframework.web.servlet.config.annotation.*;

// WebMvcConfigurer is the Spring MVC extension point. Override methods to
// customise path matching, argument resolvers, interceptors, CORS, etc.
@Configuration
public class WebConfig implements WebMvcConfigurer {

    // Pin the router to PathPatternParser (the default in Spring Boot 6).
    // AntPathMatcher is still used for some non-HTTP contexts (resource patterns).
    @Override
    public void configurePathMatch(PathMatchConfigurer configurer) {
        configurer.setPatternParser(new org.springframework.web.util.pattern.PathPatternParser());
    }

    // Trailing-slash matching: Spring Boot 6 disabled it by default
    // (GET /api/v1/orders/ no longer matches @GetMapping("/api/v1/orders")).
    // Re-enable if a legacy client depends on it.
    @Override
    public void configurePathMatch(PathMatchConfigurer configurer) {
        configurer.setUseTrailingSlashMatch(true);
    }
}
```


## The Details

### Spring MVC dispatcher architecture: `DispatcherServlet`, `HandlerMapping`, `HandlerAdapter`

`DispatcherServlet` is the single Servlet that Spring MVC registers in Tomcat. Every HTTP request that hits a `/*` URL pattern flows through it. The class itself is deceptively small — about 1,000 lines — but it orchestrates the entire request lifecycle: handler resolution, argument binding, invocation, view resolution, exception mapping. Understanding this orchestration is what separates a Spring user from a Spring engineer.

The dispatch sequence is: (1) `DispatcherServlet.doDispatch` is called by Tomcat's worker thread; (2) `getHandler(mappedRequest)` iterates the registered `HandlerMapping` beans in order — `RequestMappingHandlerMapping` (your `@RequestMapping` controllers), `BeanNameUrlHandlerMapping`, `RouterFunctionMapping` (functional endpoints), `WelcomePageHandlerMapping`; (3) the first mapping that returns a non-null `HandlerExecutionChain` wins, and the chain is augmented with the matching `HandlerInterceptor` instances; (4) `getHandlerAdapter(handler)` returns the `HandlerAdapter` that knows how to invoke this kind of handler — for `@RequestMapping` controllers this is `RequestMappingHandlerAdapter`; (5) interceptors' `preHandle` runs; (6) `HandlerAdapter.handle` invokes the controller method via reflection, having already resolved every `@PathVariable`, `@RequestParam`, `@RequestBody` argument; (7) interceptors' `postHandle` runs; (8) the return value is rendered (JSON for `@RestController`, view name for `@Controller`); (9) interceptors' `afterCompletion` runs, even if an exception was thrown.

`RequestMappingHandlerMapping` is initialised during `ApplicationContext.refresh()`. Its `afterPropertiesSet()` walks every `@Controller` bean, reflects on every method, finds `@RequestMapping`/`@GetMapping`/etc. annotations, and registers `(PathPattern, HandlerMethod)` pairs in `mappingRegistry`. The startup log line `Mapped "{[/api/v1/orders/{id}],methods=[GET]}" onto public com.example.orders.OrderDto com.example.orders.OrderController.get(java.util.UUID)` is the visible evidence. The full registry is held in a `Map<PathPattern, HandlerMethod>` and is immutable after startup — adding a route at runtime requires restarting the context. The `PathPattern` objects are built by `PathPatternParser` and stored as a sorted tree for O(K) lookup.

`RequestMappingHandlerAdapter` is the invoker. It holds a list of `HandlerMethodArgumentResolver` instances — `PathVariableMethodArgumentResolver`, `RequestBodyMethodArgumentResolver`, `RequestParamMethodArgumentResolver`, `@Autowired`-aware resolvers for `Principal`, `HttpServletRequest`, etc. When the adapter is asked to invoke `OrderController.get(UUID id)`, it walks the argument list, asks each resolver "can you resolve parameter 0 of type UUID annotated with @PathVariable?", and the matching resolver returns the coerced value. `PathVariableMethodArgumentResolver` reads the captured variable from `request.getAttribute(HandlerMapping.URI_TEMPLATE_VARIABLES_ATTRIBUTE)` (a `Map<String, String>`) and runs it through `ConversionService` to turn the string into a `UUID`. Coercion failure throws `MethodArgumentTypeMismatchException`, which the global exception handler maps to a 400 response.

```text
  Tomcat accept queue
        ↓
  Http11Processor parses HTTP/1.1 request line + headers
        ↓
  CoyoteAdapter wraps as HttpServletRequest/Response
        ↓
  FilterChain (servlet filters, Spring Security, etc.)
        ↓
  DispatcherServlet.doDispatch(req, res)
        ↓
  RequestMappingHandlerMapping.getHandler(req)         ← O(K) tree walk
        ↓ (returns HandlerExecutionChain)
  RequestMappingHandlerAdapter.handle(req, res, handlerMethod)
        ↓
  Argument resolvers bind @PathVariable, @RequestParam, @RequestBody
        ↓
  HandlerMethod.invoke() → OrderController.get(UUID id)
        ↓
  Return value → HttpMessageConverter (Jackson) → JSON bytes
        ↓
  HttpServletResponse.getOutputStream().write(jsonBytes)
        ↓
  Coyote flushes to socket, Tomcat recycles the request objects
```

### Radix tree implementation: `PathPatternParser` vs. legacy `AntPathMatcher`

`PathPatternParser` (introduced in Spring 5, made the default in Spring 6) parses a route string like `/api/v1/orders/{id}` into a linked list of `PathElement` nodes — `SeparatorPathElement`, `LiteralPathElement`, `CaptureVariablePathElement`, `WildcardPathElement`. Matching a request path is a single walk through these nodes, with no regex compilation and no heap allocation per request. The `PathPattern.match` method takes a `PathContainer` (a lightweight wrapper around the request path) and produces a `PathMatchInfo` containing the captured variables, or `null` if there is no match.

`AntPathMatcher` is the legacy implementation. It compiles each route to a regex (with `?` matching one character, `*` matching zero-or-more within a segment, `**` matching zero-or-more across segments) and uses `Matcher.matches()`. This is O(N) per request — every route's regex is tested in order. For a small route table this is fine; for a 5,000-route monolith the difference between O(N) regex matching and O(K) tree walking is 50µs vs 1µs per request, which at 10k req/s is 500ms vs 10ms of CPU per second.

The migration from `AntPathMatcher` to `PathPatternParser` is not free. `AntPathMatcher` allowed `**` in the middle of a path (`/api/**/users`), which `PathPatternParser` rejects because it cannot be expressed as a deterministic tree node. Spring Boot 6 made `PathPatternParser` the default for `RequestMappingHandlerMapping`, but `AntPathMatcher` is still used for resource handling (`/static/**`), WebSocket paths, and any code that calls `AntPathMatcher.match` directly.

```text
  Route: /api/v1/orders/{id}/items/{itemId}

  PathPatternParser builds:
    SeparatorPathElement("/")
    LiteralPathElement("api")
    SeparatorPathElement("/")
    LiteralPathElement("v1")
    SeparatorPathElement("/")
    LiteralPathElement("orders")
    SeparatorPathElement("/")
    CaptureVariablePathElement("id")     ← captures next segment as "id"
    SeparatorPathElement("/")
    LiteralPathElement("items")
    SeparatorPathElement("/")
    CaptureVariablePathElement("itemId") ← captures next segment as "itemId"

  Match against /api/v1/orders/550e8400/items/abc:
    Walks 10 nodes, captures {id=550e8400, itemId=abc}
    Zero heap allocation. ~1µs on a modern CPU.

  AntPathMatcher would compile the route to:
    ^/api/v1/orders/([^/]+)/items/([^/]+)$
  and call Matcher.matches() — regex NFA simulation, ~50µs.
```

### Writing an enterprise REST endpoint with path variables, query params, and content-negotiation headers

The `OrderController` above demonstrates every production-grade routing concern. `@PathVariable UUID id` shows typed path-variable coercion: Spring's `ConversionService` is registered with a `UUIDConverter` that calls `UUID.fromString(value)`, so a malformed UUID like `/api/v1/orders/not-a-uuid` produces a `MethodArgumentTypeMismatchException` that the exception handler maps to HTTP 400 with a clear message. `@RequestParam(name = "status", required = false) OrderStatus status` shows an optional query parameter coerced to a Java enum — Spring uses `StringToEnumConverterFactory` to convert the request string `"PENDING"` into `OrderStatus.PENDING`, and a typo like `?status=PENNDING` produces the same 400.

Content negotiation is driven by the `Accept` and `Content-Type` headers. `@GetMapping(produces = MediaType.APPLICATION_JSON_VALUE)` declares that this endpoint only produces JSON; if the client sends `Accept: application/xml`, Spring's `ContentNegotiationManager` returns 406 Not Acceptable without invoking the controller. `@PostMapping(consumes = MediaType.APPLICATION_JSON_VALUE)` declares that the endpoint only consumes JSON; a `Content-Type: application/x-www-form-urlencoded` POST returns 415 Unsupported Media Type. These failures happen in `AbstractMessageConverterMethodArgumentResolver.emptyBodyException` and surface as `HttpMediaTypeNotAcceptableException` / `HttpMediaTypeNotSupportedException` — both are handled by `ResponseEntityExceptionHandler` out of the box, returning the correct status code with a `ProblemDetail` body.

The production failure mode of content negotiation is the silent 406 when a reverse proxy (nginx, CloudFront) rewrites the `Accept` header. A client sending `Accept: application/json` through a proxy that strips the header to `Accept: */*` will work, but a proxy that rewrites it to `Accept: text/html` will get 406 on every JSON endpoint. The fix is to either (a) configure `ContentNegotiationConfigurer.favorParameter(true).parameterName("format")` so clients can request `/api/v1/orders?format=json` and bypass the header, or (b) configure the proxy to preserve the `Accept` header.

## How It Works

The `OrderController` is wired as follows. At startup, Spring Boot's `WebMvcAutoConfiguration` registers a `RequestMappingHandlerMapping` bean. During `ApplicationContext.refresh()`, the handler mapping's `afterPropertiesSet()` walks the context, finds `OrderController` (annotated `@RestController`), and reflects on its methods. Each `@GetMapping`/`@PostMapping`/`@PutMapping` annotation is parsed into a `RequestMappingInfo`, the path is compiled into a `PathPattern`, and the `(PathPattern, HandlerMethod)` pair is stored in the mapping registry.

At request time, Tomcat's `Http11Processor` parses the raw HTTP bytes into a `CoyoteRequest`, wraps it as `HttpServletRequest`, and hands it to the servlet filter chain. After the filters (Spring Security, tracing, etc.) run, the request reaches `DispatcherServlet.doDispatch`. The dispatcher asks `RequestMappingHandlerMapping.getHandler(request)` to resolve the handler; the mapping walks its `PathPattern` tree, matches `/api/v1/orders/{id}` against the request path `/api/v1/orders/550e8400-...`, and returns a `HandlerExecutionChain` wrapping `OrderController.get(UUID)`.

`RequestMappingHandlerAdapter.handle` then resolves the method arguments. For the `UUID id` parameter annotated with `@PathVariable`, `PathVariableMethodArgumentResolver` reads the captured `{id}` value from the request attribute, calls `conversionService.convert("550e8400-...", UUID.class)`, and passes the resulting `UUID` to the reflective method invocation. `OrderController.get` returns an `OrderDto`; the `RequestResponseBodyMethodProcessor` (the resolver for `@ResponseBody`/`@RestController` returns) finds `MappingJackson2HttpMessageConverter`, which calls `objectMapper.writeValueAsBytes(orderDto)`, and the bytes are written to the response output stream. Tomcat flushes the buffer to the socket, the request objects are recycled, and the worker thread is returned to the pool.

## Break It

> [!danger] Load-test failure modes you must reproduce
> Do not move on to the delta translations until you have personally reproduced each of the following in your anchor implementation:
>
> 1. **Starve the Tomcat thread pool.** Run `wrk -t12 -c500 -d30s http://localhost:8080/api/v1/orders/<uuid>`. Tomcat defaults to `server.tomcat.threads.max=200`, so 300 of the 500 concurrent connections wait in the accept queue. Watch `/actuator/metrics/tomcat.threads.busy` climb to 200 and stay there. Watch `/actuator/metrics/tomcat.threads.current` stay at 200. p99 will climb from 8ms to 250ms+. Fix: raise `server.tomcat.threads.max=1000` (but then watch the JVM heap — each thread's stack is 1MB by default) or switch to reactive WebFlux.
> 2. **Trigger a coercion storm.** Send 5,000 requests/sec with malformed path variables: `GET /api/v1/orders/not-a-uuid`. Each request throws `MethodArgumentTypeMismatchException`, which Spring catches and converts to a 400. The cost per request is ~50µs (exception construction, stack trace, `@ControllerAdvice` handler invocation, JSON serialisation of the ProblemDetail). At 5k req/s this is 250ms of CPU per second on one core, saturating it. The metric is `/actuator/metrics/http.server.requests{status=400}` rate. Fix: add a regex constraint to the path pattern: `@GetMapping("/{id:[0-9a-fA-F-]{36}}")` so malformed requests never reach the controller.
> 3. **Deadlock with `@Transactional` and a slow downstream.** Mark `OrderController.updateStatus` as `@Transactional` (it isn't, but add it). Have the underlying DB sleep 5s per call. Run 200 concurrent requests. All 200 Tomcat threads hold a DB connection from HikariCP (default `maximumPoolSize=10`); the other 190 threads wait for a connection, holding their Tomcat worker thread. Within seconds all 200 Tomcat threads are blocked on `HikariPool.getConnection`. Fix: set HikariCP `maximumPoolSize=200` (matches Tomcat threads), or use `@Transactional(propagation = NEVERS)` on read paths, or call the DB through a reactive client.
> 4. **The PathPattern `**` migration trap.** Add a route `@GetMapping("/api/**/orders")` — this compiles with `AntPathMatcher` but throws at startup with `PathPatternParser` ("Cannot use `**` in the middle of a path"). The migration from Spring Boot 2 to 6 silently breaks this. Fix: rewrite the route using explicit path segments or fall back to `AntPathMatcher` via `setPatternParser(null)`.

## Profiling Hooks

While the load test runs, collect:

- **JVM**: `jstack <pid>` for thread dumps — look for threads in `BLOCKED` state on `HikariPool.getConnection`; `jmap -dump:live,format=b,file=heap.hprof <pid>` for heap dumps (look for `PathPattern` instances, ~200 bytes each, multiplied by route count); `jstat -gcutil <pid> 1000` for GC pressure — the per-request `PathContainer` allocation (if you haven't switched to `PathPatternParser`) shows up as young-gen churn.
- **OS**: `pidstat -d -r -u -w 1` for per-process CPU, RSS, context switches; `vmstat 1` for run-queue length (if `r` > number of cores, threads are starving); `ss -tan state established | wc -l` for connection count; `ss -ltnp 'sport = :8080'` for the accept queue depth (the `Recv-Q` column).
- **App**: `/actuator/metrics/tomcat.threads.busy`, `/actuator/metrics/tomcat.threads.current`, `/actuator/metrics/tomcat.connections.current`, `/actuator/metrics/http.server.requests`, `/actuator/threaddump` (formatted thread dump with lock info).
