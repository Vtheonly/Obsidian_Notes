# 05.02.01. The Chain of Responsibility Pattern in Web Pipelines

## What This Is

Middleware is the architectural answer to one question: how do you compose cross-cutting concerns — authentication, logging, CORS, rate limiting, tracing, compression — without copy-pasting them into every route handler? The answer is the Chain of Responsibility pattern: each concern is a small, composable handler that wraps the next handler, forming a nested stack. The framework walks the stack inbound, invokes the route handler at the bottom, then walks the stack outbound as each handler completes. Every backend framework implements this pattern; they differ only in the API surface for registering and ordering the chain.

This note teaches the universal concept: the Russian-doll/onion model, the `next()` callback convention, request/response mutation, short-circuiting for early returns, the error pipeline, and the abstract middleware pseudocode that every framework implements. The anchor note (05.02.02) shows the Spring Boot implementation across the three layered boundaries (`Filter`, `HandlerInterceptor`, `@ControllerAdvice`); the delta note (05.02.03) shows the same concept in Express, Django, Flask, and Laravel.

## The Details

### The Russian Doll / Pipeline architectural pattern

The Russian-doll model (also called the onion or pipeline model) wraps each middleware around the next. The outermost middleware runs first on the inbound pass and last on the outbound pass; the innermost middleware (the route handler) runs in the middle. This nesting is what makes middleware composable: a logging middleware does not need to know whether the request will be authenticated, rate-limited, or rejected — it simply calls `next()`, waits for that call to return, and then logs the response.

The model is structurally a singly-linked list of handlers. Each handler holds a reference to the next handler (`chain` in Java, `next` in Express, `$next` in Laravel). The framework invokes the head of the list, the head invokes its successor, and so on down to the route handler. On the way back up, each handler can post-process the response, mutate headers, log timing, or short-circuit by not invoking the next handler. The pattern is identical to nested function calls in any programming language — `auth(cors(rateLimit(handler)))` — and middleware frameworks are essentially a way to build this nesting dynamically at runtime.

```text
  Inbound:                                Outbound:
  Request → [Auth]                        [Auth] → Response
               ↓                              ↑
            [CORS]                        [CORS]
               ↓                              ↑
            [RateLimit]                   [RateLimit]
               ↓                              ↑
            [Tracing]                     [Tracing]
               ↓                              ↑
            [Handler] ← ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─┘

  Equivalent nested function call:
  Auth(CORS(RateLimit(Tracing(Handler(request)))))

  The handler returns a response; each wrapper can inspect and mutate it
  on the way back out before handing it to its own caller.
```

The depth of the stack matters. A 10-middleware deep stack means 10 function frames on the call stack per request — this is fine for a 200-thread Tomcat (each thread can afford a few KB of stack) but can become significant on Node's event loop where the stack is shared across thousands of concurrent connections. The V8 engine has a default stack size of 984KB; a stack 50 middleware deep with closures capturing request state can exhaust it and throw `RangeError: Maximum call stack size exceeded`.

The production failure mode of the Russian-doll model is the "lost response" bug: a middleware modifies the response object after the handler has already written to the output stream. In Spring, calling `response.setHeader("X-Trace-Id", traceId)` after `chain.doFilter()` returns is safe (Tomcat has not flushed yet), but calling `response.getOutputStream().write(...)` after the handler has written is illegal and throws `IllegalStateException: getOutputStream() has already been called`. In Express, mutating `res.headersSent` after it becomes `true` silently does nothing, which is worse — the bug does not crash, it just does not work.

### Middleware execution phases: Pre-Processing (Inbound Request), Handler Invocation, Post-Processing (Outbound Response)

Every middleware has up to three execution phases: pre-processing (before `next()` is called), the handler invocation itself (the `next()` call), and post-processing (after `next()` returns). The pre-processing phase is where auth checks happen (the request has not reached the handler yet, so rejecting it saves the handler's CPU). The handler invocation is the actual route work. The post-processing phase is where response headers are added, response bodies are compressed, and access logs are emitted.

The split between pre and post is the source of most middleware ordering bugs. CORS must run before auth — otherwise a preflight `OPTIONS` request from the browser hits the auth middleware and gets a 401, but the browser never sends credentials on a preflight, so the auth check fails for the wrong reason. Tracing must run before everything else so that the trace ID is on the `MDC` (Mapped Diagnostic Context) when subsequent middleware log. Rate limiting must run after tracing (so the rejected request is counted) but before auth (so unauthenticated floods are rejected without hitting the auth DB).

```text
  Correct ordering (outermost → innermost):
    Tracing     (assigns trace_id, runs first, logs last on the way out)
    CORS        (handles OPTIONS preflight, never reaches auth)
    RateLimit   (rejects floods before they hit auth or handler)
    Auth        (verifies token, attaches req.user)
    Logging     (records authenticated user)
    Handler     (the route itself)

  Wrong ordering — auth runs before CORS:
    Auth        (rejects OPTIONS preflight with 401 because no Authorization header)
    CORS        (never runs — the chain short-circuited at Auth)

  Symptom: browser CORS preflight fails with 401; the actual GET works.
  Fix: declare CORS before Auth.
```

The abstract middleware pseudocode that every framework implements (the names change, the structure does not):

```text
  function Middleware(request, next):
      # Phase 1: pre-processing (inbound)
      mutatedRequest = preProcess(request)
      if shouldShortCircuit(mutatedRequest):
          return earlyResponse(mutatedRequest)        # never calls next()

      # Phase 2: handler invocation
      response = next(mutatedRequest)                  # delegate down the chain

      # Phase 3: post-processing (outbound)
      mutatedResponse = postProcess(response, mutatedRequest)
      return mutatedResponse
```

Spring's `Filter.doFilter(req, res, chain)` follows this exact shape: code before `chain.doFilter(req, res)` is pre-processing, the call itself is the handler invocation, code after is post-processing. Express's `(req, res, next) => { preCode; next(); postCode; }` is the same. Laravel's `handle($request, Closure $next) { $pre; $response = $next($request); $post; return $response; }` is the same. The pattern is invariant; only the syntax differs.

### Short-circuiting execution: Halting execution on authentication failures, CORS violations, or rate-limit saturation

Short-circuiting is the middleware's ability to end the request without invoking `next()`. The middleware writes a response directly to the output stream and returns — the chain unwinds, the handler is never called, and downstream middleware never see the request. This is how 401s from auth, 429s from rate limiters, and 204s from CORS preflight handlers are produced.

The mechanics differ across frameworks but the concept is identical. In Express, you `res.status(401).json({...}); return;` without calling `next()`. In Spring's `Filter`, you `res.setStatus(401); res.getWriter().write(...); return;` without calling `chain.doFilter()`. In Laravel, you `return response('unauthorized', 401);` without calling `$next($request)`. In Django, you `return JsonResponse({'error': 'unauthorized'}, status=401)` from `__call__` without calling `self.get_response(request)`.

The crucial subtlety is that short-circuiting bypasses every downstream middleware, including the ones that produce side effects you might want. If the tracing middleware runs after the auth middleware and auth short-circuits with a 401, the trace is never started — the rejected request is invisible in your tracing dashboard. The fix is to declare tracing as the outermost middleware so it always runs, even on rejected requests. This is why Spring Boot's `FilterRegistrationBean` has an `Order` field and why Express middleware order is determined by the order of `app.use()` calls.

```text
  Auth short-circuit, Tracing declared AFTER Auth:
    Request → [Auth: rejects → 401]  ← Tracing never sees this request
    Symptom: rejected requests do not appear in traces. You cannot see
             the attack pattern that is generating the 401s.

  Auth short-circuit, Tracing declared BEFORE Auth:
    Request → [Tracing: starts span] → [Auth: rejects → 401]
              ← [Tracing: ends span, records 401 status]
    Tracing dashboard shows the spike of 401s. You can see the attack.

  Lesson: cross-cutting observability middleware must always be outermost.
```

The error pipeline is the sibling of short-circuiting. When a middleware or handler throws an exception, the framework catches it and routes it to the next middleware that is registered as an "error handler" (a middleware with a 4-argument signature in Express, a `process_exception` method in Django middleware, an `@ExceptionHandler` method in Spring's `@ControllerAdvice`). The error handler can either convert the exception to a response or re-throw it to propagate to the next outer error handler. If no handler catches it, the framework returns a generic 500. The trap is that error-handling middleware must be registered *last* and after all "normal" middleware — otherwise it never sees the error.

### Request/Response context mutation vs. wrapping strategies

There are two strategies for letting middleware communicate state to the handler: mutate the request/response objects in place, or wrap them in a new object that carries the extra state. Mutation is simpler but thread-unsafe if the request object is shared (which it is not in most frameworks, because each request gets its own). Wrapping is cleaner but adds an allocation per middleware per request.

Express uses mutation: `req.user = jwt.verify(token, ...)` adds a `user` property to the request object, and the handler reads `req.user`. This works because Node is single-threaded and each request has its own `req` object. Spring uses a hybrid: `HttpServletRequest.setAttribute("user", principal)` mutates the request, but `SecurityContextHolder.getContext().setAuthentication(auth)` stores state in a `ThreadLocal` keyed by the current thread — this is necessary because the request object is recycled by Tomcat and re-used for the next request on the same thread, so storing state directly on it would leak across requests if not cleaned up. Django uses mutation (`request.user = ...`), Flask uses a per-request `g` object (`from flask import g; g.user = ...`).

```text
  Mutation strategy (Express, Django):
    function AuthMiddleware(req, res, next):
        req.user = verifyToken(req.headers.authorization)   # mutates req
        next()

    function Handler(req, res):
        return res.json({ id: req.user.id })                # reads mutation

  ThreadLocal strategy (Spring Security):
    class SecurityFilter:
        void doFilter(req, res, chain):
            Authentication auth = verify(req)
            SecurityContextHolder.getContext().setAuthentication(auth)  # ThreadLocal
            try { chain.doFilter(req, res); }
            finally { SecurityContextHolder.clearContext(); }           # critical cleanup

  Per-request context strategy (Flask):
    @app.before_request
    def auth():
        g.user = verify_token(request.headers.get("Authorization"))

    @app.route("/me")
    def me():
        return jsonify(g.user)        # g is per-request, thread-local

  Failure mode if ThreadLocal not cleared: thread returns to pool,
  next request on the same thread sees the previous request's SecurityContext.
  Result: user A is authenticated as user B. Catastrophic.
```

The production failure mode of mutation is the "stale thread-local" bug. Spring's `SecurityContextHolder` uses a `ThreadLocal` strategy by default (configurable to `InheritableThreadLocal` for child threads). If a filter sets the context and the `finally` block that clears it is missing or skipped (e.g., because of an `Error` thrown from `chain.doFilter`), the next request processed on the same Tomcat worker thread inherits the previous user's identity. The fix is to always use `try/finally` and to configure `SecurityContextHolderStrategy` to use `DelegatingSecurityContextRunnable` when spawning async work.

## Cross-Ecosystem Code

The same Chain-of-Responsibility concept implemented in all four target ecosystems. Each declares an auth middleware that short-circuits on missing token and a tracing middleware that wraps the response with a header.

**Spring Boot (Anchor):**
```java
@Component
@Order(1)
class TracingFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res,
                                    FilterChain chain) throws ServletException, IOException {
        String traceId = req.getHeader("X-Trace-Id");
        if (traceId == null) traceId = UUID.randomUUID().toString();
        MDC.put("trace_id", traceId);
        res.setHeader("X-Trace-Id", traceId);
        try {
            chain.doFilter(req, res);    // invoke next
        } finally {
            MDC.clear();                 // critical cleanup
        }
    }
}
```

**Express (Delta):**
```typescript
app.use((req, res, next) => {
  req.traceId = req.headers["x-trace-id"] ?? crypto.randomUUID();
  res.setHeader("x-trace-id", req.traceId);
  next();
});

// Error-handling middleware — Express detects it by the 4-arg signature
app.use((err, req, res, next) => {
  console.error(err);
  res.status(500).json({ error: "internal_error", trace_id: req.traceId });
});
```

**Django (Delta):**
```python
class TraceMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        request.trace_id = request.headers.get("X-Trace-Id", uuid.uuid4().hex)
        response = self.get_response(request)        # invoke next
        response["X-Trace-Id"] = request.trace_id
        return response
```

**Laravel (Delta):**
```php
<?php
// app/Http/Middleware/TraceHeader.php
class TraceHeader {
    public function handle(Request $req, Closure $next) {
        $traceId = $req->header("X-Trace-Id", Str::uuid()->toString());
        $req->headers->set("X-Trace-Id", $traceId);
        $response = $next($req);
        $response->header("X-Trace-Id", $traceId);
        return $response;
    }
}
```
