# 05.02.02. Deep Anchor Implementation Spring Boot Interception Pipeline

## Why This Is the Anchor

This note is the **deep anchor implementation** — the place where you build the middleware concept in Spring Boot with production-grade depth. Per the Anchor and Delta protocol ([[00.02. The Anchor and Delta Learning Protocol]]), you must break this implementation before moving to the delta notes. The point is to acquire scars: real experience with the failure modes that this concept produces under load.

Spring Boot is the anchor for middleware because it exposes three distinct interception boundaries — Servlet `Filter`, Spring MVC `HandlerInterceptor`, and AOP method interception — each running at a different point in the request lifecycle, with different access to Spring context, different performance characteristics, and different failure modes. Express and Flask have one boundary each (the `app.use` callback); Spring forces you to choose the right boundary for each concern, and the wrong choice produces subtle bugs (e.g., a `Filter` cannot read the matched `HandlerMethod`, so it cannot make decisions based on the controller's annotations).

## What You Will Build

The implementation covers:

- The layered boundary: Servlet Filters (`OncePerRequestFilter`) vs. Spring MVC `HandlerInterceptor` vs. AOP Method Interceptors.
- Implementing a high-precision Distributed Tracing and Timing Filter with MDC (Mapped Diagnostic Context) injection.
- A JWT authentication filter, a request-logging interceptor, and a global exception handler.

## Anchor Implementation (Spring Boot)

The code below is a complete, runnable Spring Boot 3.x interception pipeline. It registers three filters in order (tracing → CORS → JWT auth), one `HandlerInterceptor` (request logging with timing), and one `@ControllerAdvice` (global exception handling).

```java
// src/main/java/com/example/web/TracingFilter.java
package com.example.web;

import jakarta.servlet.*;
import jakarta.servlet.http.*;
import org.slf4j.MDC;
import org.springframework.core.annotation.Order;
import org.springframework.stereotype.Component;
import org.springframework.web.filter.OncePerRequestFilter;
import java.io.IOException;
import java.util.UUID;

@Component
@Order(1)   // outermost filter — runs before everything
public class TracingFilter extends OncePerRequestFilter {

    @Override
    protected void doFilterInternal(HttpServletRequest req,
                                    HttpServletResponse res,
                                    FilterChain chain) throws ServletException, IOException {
        String traceId = req.getHeader("X-Trace-Id");
        if (traceId == null || traceId.isBlank()) {
            traceId = UUID.randomUUID().toString();
        }
        // MDC is SLF4J's per-thread diagnostic context. Logback's %X{trace_id}
        // pattern in logback.xml will pull this into every log line on this thread.
        MDC.put("trace_id", traceId);
        MDC.put("method", req.getMethod());
        MDC.put("path", req.getRequestURI());
        res.setHeader("X-Trace-Id", traceId);

        try {
            chain.doFilter(req, res);    // hand off to next filter
        } finally {
            // CRITICAL: clear MDC because Tomcat recycles the worker thread.
            // Without this, the next request on this thread inherits our trace_id.
            MDC.clear();
        }
    }
}
```

```java
// src/main/java/com/example/web/JwtAuthFilter.java
package com.example.web;

import com.example.auth.JwtService;
import jakarta.servlet.FilterChain;
import jakarta.servlet.ServletException;
import jakarta.servlet.http.*;
import org.springframework.core.annotation.Order;
import org.springframework.security.authentication.UsernamePasswordAuthenticationToken;
import org.springframework.security.core.context.SecurityContextHolder;
import org.springframework.security.core.userdetails.UserDetails;
import org.springframework.security.core.userdetails.UserDetailsService;
import org.springframework.security.web.authentication.WebAuthenticationDetailsSource;
import org.springframework.stereotype.Component;
import org.springframework.web.filter.OncePerRequestFilter;
import java.io.IOException;

@Component
@Order(3)   // after CORS, before the handler
public class JwtAuthFilter extends OncePerRequestFilter {

    private final JwtService jwtService;
    private final UserDetailsService users;

    public JwtAuthFilter(JwtService jwtService, UserDetailsService users) {
        this.jwtService = jwtService;
        this.users = users;
    }

    @Override
    protected void doFilterInternal(HttpServletRequest req,
                                    HttpServletResponse res,
                                    FilterChain chain) throws ServletException, IOException {
        String header = req.getHeader("Authorization");
        if (header == null || !header.startsWith("Bearer ")) {
            chain.doFilter(req, res);   // anonymous request — let Spring Security deny it
            return;
        }
        try {
            String token = header.substring(7);
            String username = jwtService.extractUsername(token);   // verify signature + exp
            if (username != null && SecurityContextHolder.getContext().getAuthentication() == null) {
                UserDetails user = users.loadUserByUsername(username);
                if (jwtService.isTokenValid(token, user)) {
                    UsernamePasswordAuthenticationToken auth =
                        new UsernamePasswordAuthenticationToken(user, null, user.getAuthorities());
                    auth.setDetails(new WebAuthenticationDetailsSource().buildDetails(req));
                    SecurityContextHolder.getContext().setAuthentication(auth);
                }
            }
            chain.doFilter(req, res);
        } catch (Exception ex) {
            // Invalid token → 401, do NOT continue the chain
            res.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
            res.setContentType("application/json");
            res.getWriter().write("{\"error\":\"invalid_token\"}");
            // SecurityContext is not set, so downstream sees anonymous
        } finally {
            // SecurityContextHolder default strategy is ThreadLocal — clean it up
            // because the thread is reused for the next request.
            SecurityContextHolder.clearContext();
        }
    }
}
```

```java
// src/main/java/com/example/web/RequestLoggingInterceptor.java
package com.example.web;

import jakarta.servlet.http.*;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.stereotype.Component;
import org.springframework.web.servlet.HandlerInterceptor;
import org.springframework.web.servlet.ModelAndView;

// HandlerInterceptor runs AFTER routing has resolved the controller method.
// It can read HandlerMethod metadata (the controller class, the method name,
// the annotations) — Filter cannot.
@Component
public class RequestLoggingInterceptor implements HandlerInterceptor {

    private static final Logger log = LoggerFactory.getLogger(RequestLoggingInterceptor.class);
    private static final String START_ATTR = "RequestLoggingInterceptor.startTime";

    @Override
    public boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object handler) {
        req.setAttribute(START_ATTR, System.nanoTime());
        // handler is a HandlerMethod — we can log which controller method will run
        if (handler instanceof org.springframework.web.method.HandlerMethod hm) {
            log.info("→ {}.{}()",
                     hm.getBeanType().getSimpleName(),
                     hm.getMethod().getName());
        }
        return true;   // false would short-circuit the chain
    }

    @Override
    public void postHandle(HttpServletRequest req, HttpServletResponse res,
                           Object handler, ModelAndView mv) {
        // Runs after the handler returns but before the view is rendered.
        // For @RestController there is no view, so this is rarely useful.
    }

    @Override
    public void afterCompletion(HttpServletRequest req, HttpServletResponse res,
                                Object handler, Exception ex) {
        long start = (long) req.getAttribute(START_ATTR);
        long elapsedMs = (System.nanoTime() - start) / 1_000_000;
        log.info("← {} {} → {} ({} ms)",
                 req.getMethod(), req.getRequestURI(),
                 res.getStatus(), elapsedMs);
        // ex is non-null if the handler threw and no @ExceptionHandler caught it.
        // By the time afterCompletion runs, @ControllerAdvice has usually mapped
        // the exception to a response, so ex is null here.
    }
}
```

// src/main/java/com/example/web/WebConfig.java
package com.example.web;

import org.springframework.context.annotation.Configuration;
import org.springframework.web.servlet.config.annotation.InterceptorRegistry;
import org.springframework.web.servlet.config.annotation.WebMvcConfigurer;

@Configuration
public class WebConfig implements WebMvcConfigurer {

    private final RequestLoggingInterceptor loggingInterceptor;

    public WebConfig(RequestLoggingInterceptor loggingInterceptor) {
        this.loggingInterceptor = loggingInterceptor;
    }

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(loggingInterceptor)
                .addPathPatterns("/api/**")           // only intercept API routes
                .excludePathPatterns("/api/health");   // skip health checks
    }
}

```java
// src/main/java/com/example/web/GlobalExceptionHandler.java
package com.example.web;

import com.example.orders.OrderNotFoundException;
import org.springframework.http.*;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.*;
import org.springframework.web.context.request.WebRequest;
import org.springframework.web.servlet.mvc.method.annotation.ResponseEntityExceptionHandler;
import java.net.URI;
import java.time.Instant;
import java.util.stream.Collectors;

@ControllerAdvice   // applies to every @Controller/@RestController
public class GlobalExceptionHandler extends ResponseEntityExceptionHandler {

    // 404 — domain-specific not-found exception → RFC 7807 ProblemDetail
    @ExceptionHandler(OrderNotFoundException.class)
    public ResponseEntity<ProblemDetail> handleNotFound(OrderNotFoundException ex, WebRequest req) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
        pd.setType(URI.create("https://example.com/errors/not-found"));
        pd.setTitle("Order not found");
        pd.setProperty("timestamp", Instant.now());
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(pd);
    }

    // 400 — Bean Validation failure (@Valid @RequestBody)
    @Override
    protected ResponseEntity<Object> handleMethodArgumentNotValid(
            MethodArgumentNotValidException ex, HttpHeaders headers,
            HttpStatusCode status, WebRequest request) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, "Validation failed");
        pd.setProperty("errors", ex.getBindingResult().getFieldErrors().stream()
                .map(fe -> fe.getField() + ": " + fe.getDefaultMessage())
                .collect(Collectors.toList()));
        return handleExceptionInternal(ex, pd, headers, status, request);
    }

    // 500 — catch-all for anything not handled above
    @ExceptionHandler(Exception.class)
    public ResponseEntity<ProblemDetail> handleAll(Exception ex, WebRequest req) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.INTERNAL_SERVER_ERROR,
                "An unexpected error occurred");
        pd.setProperty("timestamp", Instant.now());
        // DO NOT include ex.getMessage() in the response — it may leak internals
        // (SQL strings, stack traces, internal hostnames). Log it server-side only.
        log.error("Unhandled exception", ex);
        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR).body(pd);
    }
}
```

## The Details

### The layered boundary: Servlet Filters (`OncePerRequestFilter`) vs. Spring MVC `HandlerInterceptor` vs. AOP Method Interceptors

Spring has three interception boundaries, each at a different layer of the request lifecycle. Understanding which one to use for which concern is the single most important middleware decision in a Spring Boot app.

**Servlet `Filter`** (the `jakarta.servlet.Filter` interface, implemented by `OncePerRequestFilter`) runs inside the servlet container, before Spring MVC. It sees the raw `HttpServletRequest` and `HttpServletResponse` but does not know which controller method will be invoked — routing has not happened yet. Filters are registered with `FilterRegistrationBean` or `@Component + @Order`. Use cases: tracing (must run before anything else logs), CORS (must run before auth rejects the preflight), request body compression, raw access logging. Spring Security is implemented as a chain of `Filter` instances wrapped in `DelegatingFilterProxy`.

**`HandlerInterceptor`** (the `org.springframework.web.servlet.HandlerInterceptor` interface) runs inside Spring MVC, after `DispatcherServlet` has resolved the handler. The `preHandle` method receives `Object handler` which is actually a `HandlerMethod` (for `@RequestMapping` controllers) — you can read `hm.getBeanType()` to see the controller class and `hm.getMethod().getAnnotations()` to make decisions based on annotations. Use cases: request logging with controller-method context, fine-grained auth checks (`@PreAuthorize` is implemented as an AOP interceptor, but a `HandlerInterceptor` reading custom annotations is a common alternative), response post-processing that needs the handler metadata. Interceptors are registered via `WebMvcConfigurer.addInterceptors`.

**AOP method interceptors** (Spring AOP `MethodInterceptor` or `@Around`-annotated aspect) run inside the controller method invocation itself, after the arguments are bound but before the method body executes. They are used for `@Transactional` (wraps the method in a transaction), `@Async` (delegates to a `TaskExecutor`), `@Cacheable`, `@PreAuthorize`. AOP interceptors work by CGLIB subclassing the controller and overriding the annotated method to insert the aspect logic. Use cases: cross-cutting concerns that should apply to specific methods based on annotations, regardless of whether they are controller methods, service methods, or repository methods.

```text
  Request lifecycle showing all three boundaries:

  TCP SYN → Tomcat accept queue
         → Http11Processor (HTTP parsing)
         → CoyoteAdapter wraps as HttpServletRequest
         → [Servlet Filter chain]                     ← Filters run here
              ├─ TracingFilter  (MDC trace_id)
              ├─ CorsFilter     (preflight handling)
              ├─ JwtAuthFilter  (SecurityContext)
              └─ SpringSecurityFilterChain (DelegatingFilterProxy)
         → DispatcherServlet.doDispatch
              → RequestMappingHandlerMapping.getHandler  (routing resolves)
              → [HandlerInterceptor.preHandle chain]    ← Interceptors run here
                   └─ RequestLoggingInterceptor
              → RequestMappingHandlerAdapter.handle
                   → Argument resolvers bind @PathVariable etc.
                   → [AOP @Around interceptors]         ← AOP runs here
                        └─ @Transactional aspect (begins tx)
                             └─ @PreAuthorize aspect (authz check)
                                  └─ OrderController.get(id)
              → [HandlerInterceptor.postHandle chain]
              → View rendering / Jackson serialisation
              → [HandlerInterceptor.afterCompletion chain]
         → @ControllerAdvice @ExceptionHandler (only if exception was thrown)
         → HttpServletResponse output flush
         → Tomcat recycles request/response objects, returns thread to pool
```

The choice of boundary matters because each layer has different visibility. A `Filter` cannot tell you which controller method will run (routing has not happened), so it cannot make per-method decisions. A `HandlerInterceptor` can read the `HandlerMethod` but cannot read the resolved argument values (those are bound by `HandlerAdapter`, which runs after `preHandle`). An AOP aspect can read the resolved arguments but runs inside the method invocation, so it cannot short-circuit the entire request — it can only throw an exception. The right boundary for a JWT auth check is `Filter` (run before Spring Security so the `SecurityContext` is set before `@PreAuthorize` runs); the right boundary for a request-logging concern that needs the controller method name is `HandlerInterceptor`; the right boundary for a transaction is AOP (it must wrap the method body).

### Implementing a high-precision Distributed Tracing and Timing Filter with MDC (Mapped Diagnostic Context) injection

The `TracingFilter` above does three things: it assigns a trace ID, it stores the trace ID in the SLF4J `MDC` so that every log line on the request's thread includes it, and it echoes the trace ID back as a response header so the caller can correlate. The `System.nanoTime()` measurement in `RequestLoggingInterceptor` captures the wall-clock duration from `preHandle` to `afterCompletion`.

The MDC is the key mechanism. SLF4J's `MDC` is a per-thread `Map<String, String>` backed by `ThreadLocal<Map>`. When you call `MDC.put("trace_id", traceId)`, the value is stored on the current thread. Logback's `%X{trace_id}` pattern in `logback.xml` reads from the MDC at log-emission time and inserts the value into the formatted log line. This means every log statement — from any library, on any code path — that runs on this thread during the request will include the trace ID, with zero code changes outside the filter.

```xml
<!-- src/main/resources/logback.xml -->
<configuration>
  <appender name="STDOUT" class="ch.qos.logback.core.ConsoleAppender">
    <encoder>
      <pattern>
        %d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] [%X{trace_id}] %-5level %logger{36} - %msg%n
      </pattern>
      <!--  ^^^^^^^^^^^^^^^^^^^^ MDC trace_id, "" if not set -->
    </encoder>
  </appender>
  <root level="INFO">
    <appender-ref ref="STDOUT" />
  </root>
</configuration>
```

The `try { chain.doFilter(); } finally { MDC.clear(); }` is the critical cleanup. Tomcat's worker threads are pooled — the same thread handles many requests over its lifetime. If `MDC.clear()` is missing, the next request on the same thread inherits the previous request's trace_id, and the log lines for two unrelated requests become interleaved under one trace ID. The same is true for `SecurityContextHolder.clearContext()` in `JwtAuthFilter`. This is the most common cross-request data-leak bug in Spring Boot, and it is invisible until you see "user A's data appearing in user B's response" in production.

For distributed tracing (OpenTelemetry, Zipkin, Jaeger), the same `Filter` propagates the trace context across HTTP hops. The `traceparent` header (W3C standard) carries `00-<trace-id>-<span-id>-<flags>`; the filter parses it, creates a span, and stores the span in the MDC so that downstream HTTP calls (made via `RestTemplate` / `WebClient` with the instrumented interceptor) carry the traceparent forward. This is how a single request through a load balancer → auth service → order service → payment service becomes one trace in Jaeger with five spans.

```text
  Trace propagation across services:

  Client → LB → Auth Service → Order Service → Payment Service

  HTTP headers on every hop:
    traceparent: 00-0af7651916cd43dd8448eb211c80319c-b7ad6b7169203331-01
                 │  │                                │                │
                 │  └── 32-char hex trace ID        │                │
                 │                                  │                │
                 └── version "00" (W3C)             │                │
                 └── 16-char hex span ID            │                │
                                                    └── flags (01 = sampled)

  Each service's TracingFilter reads traceparent, starts a child span,
  and propagates the traceparent on outbound calls. The full trace
  appears in Jaeger as a tree of spans with parent-child relationships.
```

The production failure mode of the timing filter is the `System.nanoTime()` call itself — it is not free. On Linux it is a `vDSO` call to `clock_gettime(CLOCK_MONOTONIC)`, which is ~20ns per call. With two calls per request (start in `preHandle`, end in `afterCompletion`) and 10k req/s, that is 0.4ms of CPU per second per core — negligible. But if you add a `System.currentTimeMillis()` call inside the controller for per-query timing, the cost grows: `currentTimeMillis()` is also a `vDSO` call but it has additional cache-line contention because the kernel updates the time every tick. The lesson: use `System.nanoTime()` for relative timing (durations), `Instant.now()` for absolute timestamps, and avoid `new Date()` (which is `System.currentTimeMillis()` plus an allocation).

## How It Works

The interception pipeline runs as follows. A request hits Tomcat's accept queue. Tomcat assigns it to a worker thread from its pool (default 200 threads). The thread runs the `Http11Processor` to parse HTTP, then the `CoyoteAdapter` to wrap the result as `HttpServletRequest`/`HttpServletResponse`. The filter chain runs in order: `TracingFilter` sets the MDC, `CorsFilter` handles preflight, `JwtAuthFilter` extracts the token and populates `SecurityContextHolder`. Each filter's `chain.doFilter()` call delegates to the next filter; the last filter delegates to `DispatcherServlet`.

`DispatcherServlet.doDispatch` asks `RequestMappingHandlerMapping` for the handler, gets back a `HandlerExecutionChain` containing `OrderController.get(UUID)` plus the registered `HandlerInterceptor` instances. It runs `preHandle` on each interceptor (in registration order), then asks `RequestMappingHandlerAdapter` to invoke the controller method. The adapter resolves arguments (`@PathVariable UUID id`, `@RequestBody`, etc.), applies AOP aspects (`@Transactional`, `@PreAuthorize`), and reflectively invokes the method. The return value is rendered by `HttpMessageConverter` (Jackson for JSON). Then `postHandle` runs on each interceptor (in reverse order), then `afterCompletion` (also reverse order). If any exception was thrown and not caught, the `@ControllerAdvice`'s `@ExceptionHandler` methods are tried in order until one matches the exception type.

The thread is then returned to the Tomcat pool. The `finally` blocks in the filters (`MDC.clear()`, `SecurityContextHolder.clearContext()`) have already run before the thread returns, ensuring the next request on the same thread starts with a clean slate.

## Break It

> [!danger] Load-test failure modes you must reproduce
> Do not move on to the delta translations until you have personally reproduced each of the following in your anchor implementation:
>
> 1. **Stale SecurityContext leak.** Comment out the `SecurityContextHolder.clearContext()` line in `JwtAuthFilter.finally`. Run two sequential requests on the same Tomcat thread: request 1 with a valid Bearer token for user A, request 2 with no Authorization header. Request 2 should be anonymous (401), but because the context was not cleared, it sees user A's identity. Reproduce with `for i in 1 2; do curl -s http://localhost:8080/api/me -H "Authorization: Bearer $TOKEN_A" ; curl -s http://localhost:8080/api/me ; done`. Fix: restore the `finally` block. Metric: `/actuator/metrics/http.server.requests{status=200,uri=/api/me}` should not include unauthenticated requests.
> 2. **Filter ordering trap.** Move `JwtAuthFilter` to `@Order(0)` so it runs before `TracingFilter`. Now every rejected request (401) is invisible in the tracing dashboard because the trace ID was never set. Reproduce: send 1,000 invalid-token requests, check the trace count in Jaeger — should be 1,000, is 0. Fix: `TracingFilter` must always be `@Order(1)` (outermost). Metric: trace count == request count.
> 3. **MDC leak across async.** Have a controller method annotated `@Async` log something. The `MDC.clear()` in the filter runs on the Tomcat thread, but the `@Async` work runs on a `TaskExecutor` thread that has no MDC — the log line shows `[trace_id=]`. Fix: configure `TaskDecorator` to copy MDC from the calling thread to the async thread: `executor.setTaskDecorator(runnable -> { Map<String,String> ctx = MDC.getCopyOfContextMap(); return () -> { if (ctx != null) MDC.setContextMap(ctx); try { runnable.run(); } finally { MDC.clear(); } }; });`.
> 4. **`HandlerInterceptor` short-circuit.** Return `false` from `RequestLoggingInterceptor.preHandle` for `/api/health`. Spring returns 200 with an empty body — but `afterCompletion` still runs, and `req.getAttribute(START_ATTR)` is null because `preHandle` returned early after setting it. `NullPointerException`. Fix: guard with `if (req.getAttribute(START_ATTR) == null) return;` in `afterCompletion`, or move the start-time attribute set before any early return.

## Profiling Hooks

While the load test runs, collect:

- **JVM**: `jstack <pid>` for thread dumps — look for threads in `WAITING` on `java.util.concurrent.locks.AbstractQueuedSynchronizer$ConditionObject` (waiting on a connection from HikariPool); `jmap -dump:live,format=b,file=heap.hprof <pid>` for heap dumps — look for retained `HttpServletRequest` instances (Tomcat recycles them, so more than ~2x the thread count indicates a leak); `jstat -gcutil <pid> 1000` for GC pressure — the per-request MDC `HashMap` allocation is ~80 bytes and shows up as young-gen churn.
- **OS**: `pidstat -d -r -u -w 1` for per-process CPU/RSS/context-switches; `vmstat 1` for run-queue; `ss -tan state established '( sport = :8080 )' | wc -l` for active connections; `cat /proc/<pid>/status | grep Threads` for JVM thread count (should be ~200 + background threads).
- **App**: `/actuator/metrics/tomcat.threads.busy`, `/actuator/metrics/tomcat.threads.current`, `/actuator/metrics/http.server.requests{status=500}` (should be 0), `/actuator/loggers` (tune levels at runtime), `/actuator/threaddump` (formatted thread dump with lock info — look for `BLOCKED` threads holding `SecurityContext`).
