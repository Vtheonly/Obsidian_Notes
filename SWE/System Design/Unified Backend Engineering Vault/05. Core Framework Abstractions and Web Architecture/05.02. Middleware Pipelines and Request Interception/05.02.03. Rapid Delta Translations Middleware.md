# 05.02.03. Rapid Delta Translations Middleware

## What This Note Is

This is a **delta translation note**. It is intentionally short. Read it **after** completing the anchor implementation in the sibling Spring Boot note. The point is to answer one question:

> What is different in this ecosystem, and what is automatic that I had to do manually in the anchor?

If you find yourself re-learning the concept here, you have not finished the anchor. Go back.

## Implementation Deltas

The deltas to internalize:

- *TypeScript / Express*: The `(req, res, next)` function signature, calling `next()` vs. ending the stream, error handling middleware (`(err, req, res, next)`).
- *Python / Django*: Class-based middleware implementing `__call__(request)`, `process_view()`, `process_exception()`, and `process_template_response()`.
- *Python / Flask*: Hook decorators (`@app.before_request`, `@app.after_request`, `@app.teardown_request`) and the `g` context object.
- *PHP / Laravel*: Pipeline class execution via `next(request)` closures, Terminable Middleware (`terminate()`), and Global vs. Route middleware groups.

## The Details

### *TypeScript / Express*: The `(req, res, next)` function signature, calling `next()` vs. ending the stream, error handling middleware (`(err, req, res, next)`)

Express middleware is a function with the signature `(req, res, next) => void`. The framework calls it with the request, the response, and a `next` callback that delegates to the next middleware in the chain. Calling `next()` continues; not calling it (and writing to `res` instead) short-circuits. Calling `next(err)` with an argument routes to the next error-handling middleware — recognised by its 4-argument signature `(err, req, res, next)`. There is no class hierarchy, no `FilterChain` object, no `HandlerMethod`; the chain is a plain array of functions composed at registration time.

```typescript
import express, { Request, Response, NextFunction } from "express";

const app = express();

// 1. Tracing middleware — outermost, always runs
app.use((req: Request, res: Response, next: NextFunction) => {
  const traceId = (req.headers["x-trace-id"] as string) ?? crypto.randomUUID();
  (req as any).traceId = traceId;          // mutation strategy
  res.setHeader("x-trace-id", traceId);
  next();                                   // continue the chain
});

// 2. CORS — handle OPTIONS preflight without invoking auth
app.use((req, res, next) => {
  res.setHeader("Access-Control-Allow-Origin", "*");
  res.setHeader("Access-Control-Allow-Headers", "Authorization, Content-Type");
  if (req.method === "OPTIONS") {
    res.status(204).end();                  // short-circuit: no next()
    return;
  }
  next();
});

// 3. Auth — short-circuits on missing/invalid token
app.use("/api", (req, res, next) => {
  const header = req.headers.authorization;
  if (!header?.startsWith("Bearer ")) {
    res.status(401).json({ error: "missing_token", trace_id: (req as any).traceId });
    return;                                 // short-circuit: no next()
  }
  try {
    (req as any).user = jwt.verify(header.slice(7), process.env.JWT_SECRET!);
    next();
  } catch (err) {
    next(err);                              // delegate to error middleware
  }
});

// 4. Route handler — the bottom of the chain
app.get("/api/me", (req, res) => {
  res.json((req as any).user);
});

// 5. Error-handling middleware — MUST be registered last, MUST have 4 args.
// Express detects it by the signature length (function.length === 4).
app.use((err: Error, req: Request, res: Response, next: NextFunction) => {
  console.error(`[trace=${(req as any).traceId}]`, err);
  if (err instanceof ValidationError) {
    res.status(400).json({ error: "validation_failed", details: err.details });
    return;
  }
  res.status(500).json({ error: "internal_error", trace_id: (req as any).traceId });
});

app.listen(8080);
```

What is automatic here that was manual in the anchor: nothing. Express has no `WebMvcConfigurer.addInterceptors`, no `@Order` annotation, no `FilterRegistrationBean`. The middleware order is exactly the order of `app.use()` calls. The error-handling middleware is automatically recognised by the 4-argument signature — there is no `@ExceptionHandler` annotation to forget.

What is manual here that was automatic in the anchor: there is no MDC equivalent (use `cls-hooked` or `async_hooks` to propagate request context across `await` boundaries), no `SecurityContextHolder` (just `req.user` mutation), no `@ControllerAdvice` (you write one error-handling middleware at the end of the chain), no separation of `Filter` vs `HandlerInterceptor` (everything is just middleware). The `res.status(204).end()` short-circuit must be explicit — there is no `return false` from `preHandle`.

The runtime invariant exposed differently: Node's single-threaded event loop means there is no Tomcat thread pool to leak state across. The `req` object is per-request and is garbage-collected when the response ends, so the "stale SecurityContext" bug is structurally impossible. The corresponding failure mode is the "unhandled promise rejection" — if a route handler does `await something()` and `something()` rejects without a `try/catch`, the rejection becomes an `unhandledRejection` event, which by default in Node 15+ crashes the process. The fix is the `express-async-errors` package (patches Express to forward async rejections to the error middleware) or wrapping every handler in `asyncHandler(fn)`.

### *Python / Django*: Class-based middleware implementing `__call__(request)`, `process_view()`, `process_exception()`, and `process_template_response()`

Django middleware is a class with `__init__(self, get_response)` and `__call__(self, request)`. The `get_response` callable is the next middleware in the chain (or the URL resolver + view, for the innermost middleware). Calling `self.get_response(request)` returns the response; code before that call is pre-processing, code after is post-processing. Additional hooks — `process_view(request, view_func, view_args, view_kwargs)` runs after URL resolution but before the view; `process_template_response(request, response)` runs if the view returned a `TemplateResponse`; `process_exception(request, exception)` runs if the view raised — give Django the most fine-grained interception hooks of any framework in this delta set.

```python
# myapp/middleware.py
import time
import uuid

class TraceMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response
        # One-time configuration at startup.

    def __call__(self, request):
        # Pre-processing (inbound)
        request.trace_id = request.headers.get("X-Trace-Id", uuid.uuid4().hex)

        response = self.get_response(request)   # delegate down the chain

        # Post-processing (outbound)
        response["X-Trace-Id"] = request.trace_id
        return response

    def process_view(self, request, view_func, view_args, view_kwargs):
        # Runs after URL resolution, before the view.
        # view_func is the resolved view callable.
        # Return None to continue; return HttpResponse to short-circuit.
        print(f"→ {view_func.__module__}.{view_func.__name__}()")
        return None

    def process_exception(self, request, exception):
        # Runs only if the view raised.
        # Return None to let Django's default handler render a 500.
        # Return HttpResponse to override.
        import logging
        logging.getLogger(__name__).exception(
            "trace_id=%s", request.trace_id, exc_info=exception)
        return None   # let the default 500 handler run


class RateLimitMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        # In-memory token bucket — replace with Redis for production.
        if not rate_limiter.allow(request.META["REMOTE_ADDR"]):
            from django.http import JsonResponse
            return JsonResponse(
                {"error": "rate_limited"},
                status=429,
                headers={"Retry-After": "60"},
            )
        return self.get_response(request)


# settings.py
MIDDLEWARE = [
    "django.middleware.security.SecurityMiddleware",
    "django.contrib.sessions.middleware.SessionMiddleware",
    "django.middleware.common.CommonMiddleware",
    "django.middleware.csrf.CsrfViewMiddleware",
    "django.contrib.auth.middleware.AuthenticationMiddleware",
    "django.contrib.messages.middleware.MessageMiddleware",
    # Custom middleware — order matters, outermost first
    "myapp.middleware.TraceMiddleware",       # outermost custom — runs first, logs last
    "myapp.middleware.RateLimitMiddleware",   # rejects floods before the view runs
]
```

What is automatic here that was manual in the anchor: `process_view` gives Django a hook that Spring has no direct equivalent for — it runs after routing has resolved the view function but before the view is invoked, so you can inspect `view_func`, replace it, or short-circuit. `process_template_response` is a hook for post-processing `TemplateResponse` objects (rare in JSON APIs, common in server-rendered Django). `process_exception` is the Django equivalent of `@ExceptionHandler`, but it is a method on the middleware class rather than a separate `@ControllerAdvice` bean.

What is manual here that was automatic in the anchor: there is no `MDC` equivalent built into Django's logging — you must configure a `logging.Filter` that pulls `request.trace_id` from a thread-local and injects it into the log record. There is no `SecurityContextHolder` — Django stores `request.user` after the `AuthenticationMiddleware` runs, and you access it as `request.user.is_authenticated` in views. There is no `@Order` annotation — middleware order is the order of entries in the `MIDDLEWARE` list.

The runtime invariant exposed differently: same GIL constraint as Django routing. Django middleware is loaded once at startup and held in memory for the life of the worker process. Under gunicorn+sync, each worker handles one request at a time, so per-request state on `request` is safe. Under gunicorn+gevent, the worker is cooperative multitasking — `request.user` is still safe (gevent switches are explicit at I/O points), but thread-local storage (Python's `threading.local`) is shared across greenlets and is the source of cross-request leak bugs. Use `greenlet.getcurrent().gr_context` or `werkzeug.local.LocalStack` instead.

### *Python / Flask*: Hook decorators (`@app.before_request`, `@app.after_request`, `@app.teardown_request`) and the `g` context object

Flask does not have a single "middleware" abstraction. Instead it exposes three hook decorators: `@app.before_request` runs before every view (pre-processing), `@app.after_request` runs after every view that produced a response (post-processing, can modify the response), `@app.teardown_request` runs at the end of every request regardless of exceptions (cleanup). The `g` object is a per-request namespace — `g.user = ...` in a `before_request` hook is visible in the view and in `after_request`. Flask also supports WSGI middleware (which runs before Flask itself, equivalent to a Servlet `Filter`) and the `@app.errorhandler(code_or_exception)` decorator for error handling.

```python
from flask import Flask, g, request, jsonify
import time, uuid, jwt

app = Flask(__name__)

# before_request — runs before every view. Multiple functions registered;
# they run in registration order.
@app.before_request
def assign_trace_id():
    g.trace_id = request.headers.get("X-Trace-Id", uuid.uuid4().hex)

@app.before_request
def authenticate():
    # Runs after assign_trace_id. g.trace_id is already set.
    header = request.headers.get("Authorization", "")
    if header.startswith("Bearer "):
        try:
            g.user = jwt.decode(header[7:], app.config["JWT_SECRET"], algorithms=["HS256"])
        except jwt.InvalidTokenError:
            return jsonify({"error": "invalid_token", "trace_id": g.trace_id}), 401
    # If we return None, the next before_request runs, then the view.
    # If we return a Response (like above), the chain short-circuits.

# after_request — runs after every view that returned a response.
# Each function receives the response and MUST return a response.
@app.after_request
def add_trace_header(response):
    response.headers["X-Trace-Id"] = getattr(g, "trace_id", "")
    return response

@app.after_request
def log_request(response):
    app.logger.info(f"trace={g.trace_id} {request.method} {request.path} → {response.status_code}")
    return response

# teardown_request — runs at the end of every request, even on exception.
# Use for cleanup: closing DB connections, releasing locks.
@app.teardown_request
def cleanup(exc):
    db_session = getattr(g, "_db_session", None)
    if db_session is not None:
        if exc is not None:
            db_session.rollback()
        else:
            db_session.commit()
        db_session.close()

# errorhandler — equivalent to Spring's @ExceptionHandler
@app.errorhandler(404)
def not_found(err):
    return jsonify({"error": "not_found", "trace_id": getattr(g, "trace_id", "")}), 404

@app.errorhandler(Exception)
def unhandled(err):
    app.logger.exception(f"trace={getattr(g, 'trace_id', '')}")
    return jsonify({"error": "internal_error"}), 500

@app.get("/api/me")
def me():
    return jsonify(g.user)   # set by authenticate()
```

What is automatic here that was manual in the anchor: the `g` object is automatically scoped to the request — Flask clears it between requests via the application context, so there is no "stale g.user" bug across requests on the same worker. The `@app.errorhandler(Exception)` catch-all is the equivalent of Spring's `@ExceptionHandler(Exception.class)` but is a single decorator, not a `@ControllerAdvice` class. `@app.teardown_request` is unique to Flask — Spring has no direct equivalent; cleanup in Spring is done in `try/finally` inside the filter or by registering a `RequestHandledEventListener`.

What is manual here that was automatic in the anchor: the before/after split means a single concern (e.g., tracing) is split across two functions, and you must manage the `g` namespace manually. Flask does not have an equivalent of `HandlerInterceptor.preHandle` returning `false` to short-circuit — you return a Response from `before_request`. Flask does not have `process_view` — you cannot inspect the resolved view function before it runs (use the `request.url_rule` attribute, which is set after routing, but it is read in `before_request` only on Flask 2.3+).

The runtime invariant exposed differently: same as Django. The `g` object is backed by `werkzeug.local.LocalProxy` which is greenlet-safe (uses `get_ident()` from `greenlet` or `threading`), so it works under gunicorn+gevent. But `threading.local` directly is not safe — use Flask's `g` or `werkzeug.local.LocalStack`.

### *PHP / Laravel*: Pipeline class execution via `next(request)` closures, Terminable Middleware (`terminate()`), and Global vs. Route middleware groups

Laravel middleware is a class with `public function handle(Request $request, Closure $next): Response`. The `$next` closure is the next middleware in the pipeline (or the route handler, for the innermost). Calling `$next($request)` returns a `Response`; code before that call is pre-processing, code after is post-processing. Laravel's `Illuminate\Pipeline\Pipeline` class composes the middleware stack into a single nested closure at request time — conceptually identical to Express's middleware array but expressed as a chain of closures.

```php
<?php
// app/Http/Middleware/TraceHeader.php
namespace App\Http\Middleware;

use Closure;
use Illuminate\Http\Request;
use Illuminate\Support\Facades\Log;
use Illuminate\Support\Str;

class TraceHeader
{
    public function handle(Request $req, Closure $next)
    {
        $traceId = $req->header("X-Trace-Id", Str::uuid()->toString());
        $req->headers->set("X-Trace-Id", $traceId);

        // Log context — Laravel's Log::withContext() is the equivalent of MDC.
        // Subsequent Log::* calls on this request include the context.
        Log::withContext(["trace_id" => $traceId, "method" => $req->method()]);

        $response = $next($req);              // delegate down the chain

        $response->header("X-Trace-Id", $traceId);
        return $response;
    }

    // Terminable middleware — runs AFTER the response is sent to the client.
    // Use for slow work that should not delay the response: analytics writes,
    // audit logs, metrics increments.
    public function terminate(Request $req, Response $response): void
    {
        Log::info("request_complete", [
            "status" => $response->status(),
            "duration_ms" => (microtime(true) - LARAVEL_START) * 1000,
        ]);
    }
}

// app/Http/Middleware/JwtAuth.php
class JwtAuth
{
    public function handle(Request $req, Closure $next)
    {
        $header = $req->header("Authorization", "");
        if (!str_starts_with($header, "Bearer ")) {
            return response()->json(["error" => "missing_token"], 401);
        }
        try {
            $claims = JWT::decode(substr($header, 7), new Key(config("jwt.secret"), "HS256"));
            $req->merge(["auth_user_id" => $claims->sub]);
        } catch (Exception $e) {
            return response()->json(["error" => "invalid_token"], 401);
        }
        return $next($req);
    }
}

// bootstrap/app.php (Laravel 11) — register global middleware
->withMiddleware(function (Middleware $middleware) {
    $middleware->append(TraceHeader::class);       // runs on every request
    $middleware->append(\App\Http\Middleware\Cors::class);
})

// routes/api.php — route-specific middleware
use App\Http\Middleware\JwtAuth;
Route::middleware([JwtAuth::class, "throttle:60,1"])->group(function () {
    Route::get("/me", fn (Request $req) => ["user_id" => $req->get("auth_user_id")]);
    Route::post("/orders", [OrderController::class, "store"]);
});

// app/Exceptions/Handler.php — global exception handler (Laravel 10)
// In Laravel 11 this lives in bootstrap/app.php with ->withExceptions(fn => ...)
class Handler extends ExceptionHandler
{
    public function render($req, Throwable $e)
    {
        if ($e instanceof ValidationException) {
            return response()->json([
                "error" => "validation_failed",
                "details" => $e->errors(),
            ], 422);
        }
        if ($e instanceof ModelNotFoundException) {
            return response()->json(["error" => "not_found"], 404);
        }
        return response()->json(["error" => "internal_error"], 500);
    }
}
```

What is automatic here that was manual in the anchor: Laravel's `Log::withContext()` is the MDC equivalent — context is automatically attached to every subsequent log line on this request and is automatically cleared at request end (PHP-FPM's shared-nothing process model means there is no thread pool to leak across). `terminate()` is unique to Laravel — Spring has no equivalent "run after response is flushed" hook (you would use `AsyncContext` or a `ServletContainerInitializer`-registered `AsyncListener`). Route Model Binding and the `throttle:60,1` middleware are automatic; Spring requires Bucket4j or Resilience4j.

What is manual here that was automatic in the anchor: the `terminate()` method runs after the response is sent, but in PHP-FPM's shared-nothing model the process is about to die — `terminate()` must finish before the process exits or its work is lost. Laravel Octane (long-lived PHP via Swoole/RoadRunner) makes this safer. The exception handler in Laravel 11 lives in `bootstrap/app.php` rather than a `@ControllerAdvice` class — there is exactly one global handler, not one-per-package.

The runtime invariant exposed differently: PHP-FPM's per-request process model means there is no shared state to leak — every request starts with a fresh `$_SERVER`, fresh `static` properties (unless using persistent process models like Octane), fresh DI container. The "stale SecurityContext" bug is structurally impossible. The corresponding failure mode is per-request bootstrap cost: every request re-registers middleware, re-resolves the DI container, re-builds the route table — unless `route:cache`, `config:cache`, and `view:cache` have run, this is 80-150ms of overhead per request, dominating p99.

## Cross-Ecosystem Code

The same middleware concept — assign a trace ID, log the request, handle errors — implemented side-by-side. The shape is identical; only the syntax differs.

**Spring Boot (Anchor) — Servlet Filter:**
```java
@Component
@Order(1)
class TracingFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res,
                                    FilterChain chain) throws ServletException, IOException {
        String traceId = req.getHeader("X-Trace-Id");
        if (traceId == null) traceId = UUID.randomUUID().toString();
        MDC.put("trace_id", traceId);
        res.setHeader("X-Trace-Id", traceId);
        try { chain.doFilter(req, res); } finally { MDC.clear(); }
    }
}
```

**Express (Delta):**
```typescript
app.use((req, res, next) => {
  (req as any).traceId = req.headers["x-trace-id"] ?? crypto.randomUUID();
  res.setHeader("x-trace-id", (req as any).traceId);
  next();
});

app.use((err: Error, req: Request, res: Response, next: NextFunction) => {
  console.error(err);
  res.status(500).json({ error: "internal_error", trace_id: (req as any).traceId });
});
```

> [!tip] What to write down after the translation
> - What was automatic here that I had to do manually in the anchor? (Laravel: `Log::withContext()` auto-clears; `terminate()` runs after flush. Django: `process_view` and `process_exception` hooks. Flask: `g` auto-scoped.)
> - What was manual here that was automatic in the anchor? (Express: no MDC, no security context, error middleware must be last. Flask: tracing concern split across before+after. Django: no content negotiation. Laravel: per-request bootstrap cost.)
> - Which runtime invariant is exposed differently? (Node: event loop, no thread pool. CPython: GIL, per-worker process. PHP-FPM: shared-nothing, per-request bootstrap.)
> - Which failure mode is structurally impossible here? (Express: stale thread-local. Laravel: cross-request leak in PHP-FPM. Flask: stale `g` between requests.)
> - Which failure mode is new here? (Express: unhandled promise rejection crashes process. Django/Flask: GIL contention under CPU work. Laravel: per-request bootstrap dominates p99 unless caches are warm. Flask: `before_request` short-circuit by returning Response is less obvious than `next()`.)
