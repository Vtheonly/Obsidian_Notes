# 05.05.01. Fault Tolerance and Exception Propagation

## What This Is

A fault-tolerant backend is one that keeps serving requests when its dependencies fail — when the database is down, when a downstream service times out, when a message broker drops a connection, when a disk fills up. The mechanisms are universal: timeouts at every layer, retries with exponential backoff and jitter, circuit breakers to stop cascading failures, bulkheads to isolate failing components, and exception boundaries that convert internal errors into structured HTTP responses without leaking implementation details.

This note teaches the universal concept: exceptions vs error codes, fail-fast vs fail-safe, the circuit breaker, retry with exponential backoff + jitter, the bulkhead pattern, and the timeout-everywhere rule. The anchor note (05.05.02) shows Spring Boot's `@ControllerAdvice` + `@ExceptionHandler` + `ProblemDetail` implementation; the delta note (05.05.03) shows the same concept in Express, Django, Flask, and Laravel.

## The Details

### Checked vs. Unchecked Exceptions and Error Bubbling across call stacks

Java is unusual among mainstream backend languages in having checked exceptions — exceptions that the compiler forces the caller to either catch or declare in `throws`. `IOException`, `SQLException`, `InterruptedException` are checked; `NullPointerException`, `IllegalArgumentException`, `RuntimeException` are unchecked. The intent was to force developers to handle recoverable errors; the practice is that checked exceptions are widely hated because they pollute method signatures and are usually re-thrown as `RuntimeException` ("wrapping").

The bubbling rule is: an exception propagates up the call stack until a `try/catch` matches its type (or a supertype), or until it reaches the top of the stack. In Spring MVC, the top of the stack is `DispatcherServlet.doDispatch`, which catches `Throwable` and delegates to `HandlerExceptionResolver` — which finds the matching `@ExceptionHandler` and renders a response. If no handler matches, Spring renders a generic 500 with the exception message (which is why you must always have a catch-all `@ExceptionHandler(Exception.class)` to prevent stack traces from leaking).

The error code versus exception debate is the dominant difference between Go and Java/Python. Go returns errors as values (`result, err := doSomething(); if err != nil { return err }`), forcing the developer to handle them at every call site. Java/Python throw exceptions, which bubble up automatically. The Go approach is more verbose but makes every error-handling decision explicit; the exception approach is more concise but makes it easy to forget error handling (a missing `try/catch` lets the exception propagate to the user as a 500).

```java
// Checked exception — compiler forces handling or declaration
public String readFile(String path) throws IOException {
    return Files.readString(Path.of(path));   // IOException is checked
}

// Caller must handle or declare
public String loadConfig(String path) {
    try {
        return readFile(path);
    } catch (IOException e) {
        // Wrap as unchecked — bubbling pattern
        throw new ConfigLoadException("Failed to load " + path, e);
    }
}

// Unchecked exception — bubbles automatically, no declaration needed
public User findUser(Long id) {
    return repo.findById(id).orElseThrow(() ->
        new UserNotFoundException(id));   // unchecked, no throws declaration
}
```

The production failure mode of the bubbling model is the "lost context" bug. An exception thrown deep in the call stack carries a message and a stack trace, but by the time it reaches the `@ExceptionHandler`, the original cause may be wrapped in three layers of `RuntimeException`. The fix is to always pass the original exception as the `cause` parameter (`new ConfigLoadException(msg, originalException)`) so the stack trace is preserved, and to log at the boundary (`log.error("Unhandled", ex)`) where you have the full request context (trace ID, user ID, path).

### Process-level unhandled errors: Crash-on-Error vs. Request-Level Fault Isolation

When an unhandled exception reaches the top of the request handling stack, the framework has two choices: crash the process or isolate the failure to the current request. The choice is governed by the runtime's process model.

In Node.js, an unhandled exception (or an unhandled promise rejection, since Node 15+) terminates the process. The rationale is that an unhandled exception leaves the process in an unknown state — maybe a connection was leaked, maybe a lock is held, maybe a half-written file exists — and continuing would be unsafe. The deployment must use a process manager (PM2, systemd, Kubernetes) that restarts the process. This is "crash-on-error" and is the Node.js philosophy.

In Java/Python/PHP, the framework catches the exception at the request boundary, renders a 500 response, and the process keeps serving subsequent requests. This is "request-level fault isolation" and is the JVM/CPython/PHP-FPM philosophy. The risk is that the process accumulates corrupt state from the failed request — a `ThreadLocal` not cleared, a connection not returned to the pool — and slowly degrades. The mitigation is aggressive cleanup in `finally` blocks and in the framework's request-recycling code.

```text
  Crash-on-Error (Node.js) vs Request-Level Fault Isolation (JVM):

  ┌────────────────────┬────────────────────────────┬────────────────────────────┐
  │ Property           │ Node.js                    │ JVM (Spring Boot)          │
  ├────────────────────┼────────────────────────────┼────────────────────────────┤
  │ Unhandled except   │ Process exits (code 1)     │ Caught by DispatcherServlet│
  │ After failure      │ Process restarts (PM2/k8s) │ Request returns 500,       │
  │                    │                            │ process keeps serving      │
  │ Risk               │ Restart cost (~1-3s)       │ Slow state accumulation    │
  │ Mitigation         │ Process manager restarts  │ finally blocks, filters    │
  │ Best for           │ Stateless microservices    │ Long-lived stateful apps   │
  └────────────────────┴────────────────────────────┴────────────────────────────┘

  Production implications:
  - Node.js: a single bug that throws in a hot path can crash the process
    repeatedly, causing a thundering herd of restarts. Use domains or
    process isolation (cluster mode) to limit blast radius.
  - JVM: a single bug that leaks resources eventually causes OOM or
    thread exhaustion, but the process limps along. Use health checks
    (Spring Boot Actuator /actuator/health) and a self-destruct threshold
    (reboot if 500 rate > 1% for 5 minutes).
```

The production failure mode of crash-on-error is the "thundering herd" restart. A bug that throws on every request causes the process to crash and restart 60 times per minute, each restart re-booting the framework (~3s), and the load balancer keeps sending requests to the restarting instance. The fix is a process manager that does exponential backoff on restarts and a load balancer that removes unhealthy instances. The failure mode of request-level isolation is the "slow death" — the process never crashes but accumulates leaked resources until it hits OOM, at which point the JVM's `OutOfMemoryError` is itself an unhandled exception and the process dies anyway. The fix is health checks that detect the leak early.

### Mapping internal exceptions to standard HTTP status codes without leaking stack traces or sensitive database topology

The exception boundary is the layer that converts internal exceptions into HTTP responses. The mapping is convention: `NotFoundException` → 404, `ValidationException` → 400, `ConflictException` → 409, `AuthenticationException` → 401, `AuthorizationException` → 403, `IllegalStateException` (and any uncaught exception) → 500. The boundary must do three things: (1) map the exception type to the right status code, (2) render a structured error body (RFC 7807 ProblemDetail), (3) prevent any internal detail from leaking to the client.

The leakage prevention is the security-critical part. A stack trace that reaches the client reveals the JVM version, the framework version, the class names of internal services, the SQL query that failed, the database connection string in some cases. This is reconnaissance gold for an attacker. The boundary must log the full stack trace server-side (where it is safe) and return a generic message client-side ("An internal error occurred") with a trace ID that the client can quote and the operator can look up in the logs.

```java
@ControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(Exception.class)
    public ResponseEntity<ProblemDetail> handleAll(Exception ex, WebRequest req) {
        // Log the full stack trace server-side with full request context
        log.error("Unhandled exception trace={} user={} path={}",
                  req.getHeader("X-Trace-Id"),
                  req.getUserPrincipal() != null ? req.getUserPrincipal().getName() : "anonymous",
                  req.getDescription(false),
                  ex);

        // Return a generic message client-side — DO NOT include ex.getMessage()
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(
            HttpStatus.INTERNAL_SERVER_ERROR,
            "An internal error occurred. Quote trace ID " + req.getHeader("X-Trace-Id")
            + " when reporting this issue."
        );
        pd.setType(URI.create("https://example.com/errors/internal"));
        pd.setTitle("Internal Server Error");
        pd.setProperty("trace_id", req.getHeader("X-Trace-Id"));
        pd.setProperty("timestamp", Instant.now());

        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR).body(pd);
    }
}
```

```text
  HTTP status code mapping (the convention every API follows):

  ┌──────────────────────────────────────────┬──────┬──────────────────────┐
  │ Internal exception type                  │ HTTP │ Example              │
  ├──────────────────────────────────────────┼──────┼──────────────────────┤
  │ NotFoundException                        │ 404  │ User 42 not found    │
  │ ValidationException (DTO failed)         │ 400  │ email is not valid   │
  │ MethodArgumentNotValidException          │ 400  │ (Bean Validation)    │
  │ HttpMessageNotReadableException          │ 400  │ malformed JSON       │
  │ ConflictException / DuplicateKeyException│ 409  │ email already used   │
  │ AuthenticationException                  │ 401  │ missing/invalid token│
  │ AccessDeniedException                    │ 403  │ not allowed          │
  │ HttpRequestMethodNotSupportedException   │ 405  │ POST to a GET route  │
  │ HttpMediaTypeNotSupportedException       │ 415  │ wrong Content-Type   │
  │ ThrottlingException                      │ 429  │ rate limit exceeded  │
  │ IllegalStateException / Throwable        │ 500  │ unhandled            │
  │ ServiceUnavailableException              │ 503  │ downstream down      │
  │ GatewayTimeoutException                  │ 504  │ downstream timed out │
  └──────────────────────────────────────────┴──────┴──────────────────────┘

  Rule of thumb:
  - 4xx = client made a mistake (retry with different input)
  - 5xx = server made a mistake or is broken (do not retry, or retry later)
```

The production failure mode of bad mapping is the "404 for everything" anti-pattern. A controller that catches `Exception` and returns 404 ("not found") for every internal failure hides bugs — the client retries forever (404 is a client error, supposedly permanent), and the operator never sees the 500 rate spike. The fix is to never use 4xx for internal failures; reserve 4xx for "the client did something wrong" and 5xx for "the server did something wrong". A 500 should be rare in production — if it is not, something is broken and needs fixing.

### Circuit Breaker, Retry with Exponential Backoff + Jitter, and Bulkhead Isolation

When a downstream dependency fails, three patterns protect the upstream service from cascading failure: retry (with backoff and jitter), circuit breaker, and bulkhead. Each addresses a different failure mode.

**Retry with exponential backoff and jitter** is the response to transient failures (network blips, momentary 503s). The caller retries the failed operation after a delay that doubles each time: 100ms, 200ms, 400ms, 800ms, capped at some maximum (e.g., 5 seconds). The jitter is a small random addition (±20%) to the delay — without jitter, every retry across every client happens at the same instant, causing thundering herd. With jitter, retries spread out. The retry count must be bounded (typically 3-5); unbounded retries are a denial-of-service amplifier.

**Circuit breaker** is the response to sustained failures. The breaker counts failures; when the count exceeds a threshold (e.g., 5 failures in 10 seconds), the breaker "opens" — subsequent calls fail immediately without hitting the downstream. After a cooldown (e.g., 30 seconds), the breaker enters "half-open" — one call is allowed through; if it succeeds, the breaker "closes" and normal operation resumes; if it fails, the breaker re-opens for another cooldown. The breaker protects the downstream from being hammered by a failing upstream, and it protects the upstream from waiting on timeouts for a downstream that is down.

**Bulkhead** is the response to resource exhaustion in one part of the system affecting the rest. The pattern isolates downstream calls into separate thread pools (or connection pools) so that a slow downstream cannot exhaust the pool used by other downstreams. Without bulkheads, a slow `PaymentService` call holds Tomcat worker threads, eventually exhausting the pool and causing the entire service to fail — including unrelated endpoints like `GET /health`. With bulkheads, the payment calls are isolated to a 50-thread pool; when payment is slow, those 50 threads saturate but the rest of the service keeps working.

```text
  Circuit breaker state machine:

        ┌─────────────────────────────────────────────────────────────┐
        │                                                             │
        ▼                                                             │
    ┌────────┐   failures >= threshold (e.g. 5 in 10s)    ┌──────┐  │
    │ CLOSED │ ──────────────────────────────────────────→ │ OPEN │  │
    └────────┘                                              └──────┘  │
        ▲                                                       │     │
        │ successful call in half-open                          │     │
        │                                                       │ cooldown
        │                                                       │ elapses
        │                                                       ▼     │
    ┌──────────┐                                         ┌───────────┐ │
    │ HALF_OPEN│ ←────────────────────────────────────── │   OPEN    │ │
    └──────────┘   timer expires (e.g. 30s)              └───────────┘ │
        │                                                          │
        │ failed call in half-open → back to OPEN                  │
        └──────────────────────────────────────────────────────────┘

    CLOSED: calls pass through, failures counted
    OPEN:   calls fail immediately (no downstream hit)
    HALF_OPEN: one trial call allowed; success → CLOSED, failure → OPEN
```

```text
  Retry with exponential backoff + jitter (Resilience4j-style):

    Attempt  Delay (ms)   With jitter (ms)
    1        (immediate)  0
    2        100          100 + random(-20, 20) = 80-120
    3        200          200 + random(-40, 40) = 160-240
    4        400          400 + random(-80, 80) = 320-480
    5        800          800 + random(-160, 160) = 640-960
    (cap at 5000ms; give up after max attempts = 5)

    Total worst-case time: 0 + 120 + 240 + 480 + 960 = 1800ms before giving up
    Without jitter: every client retries at 0, 100, 200, 400, 800 ms —
    thundering herd on the downstream when it recovers.
```

```text
  Bulkhead isolation:

  WITHOUT bulkheads (shared Tomcat pool of 200 threads):
    /api/orders → calls PaymentService → slow (5s each)
    40 concurrent /api/orders requests → 40 threads busy
    100 concurrent /api/orders requests → 100 threads busy
    200 concurrent /api/orders requests → ALL 200 threads busy
    /api/health → no threads available → 503 → k8s liveness probe fails → pod restarted

  WITH bulkheads (payment isolated to 50-thread pool):
    /api/orders → calls PaymentService via 50-thread bulkhead
    200 concurrent /api/orders requests → 50 in payment, 150 queued (rejected fast)
    /api/health → uses the main 150-thread pool → still serves 200 OK
    Pod stays alive; only the /api/orders endpoint degrades.
```

The production failure mode of missing circuit breakers is the "cascading failure" — service A depends on service B, B goes down, A's threads all block on timeouts to B, A becomes unavailable, every service that depends on A also blocks, and the entire system is down within 60 seconds. The fix is circuit breakers on every downstream call (Resilience4j in Spring, `opossum` in Node, `circuitbreaker` in Python) and timeouts at every layer (HTTP client timeout, database query timeout, message consumer timeout). The rule of thumb: every network call must have a timeout, and every timeout must have a circuit breaker.

## Cross-Ecosystem Code

The same fault-tolerance concept — circuit breaker + retry + global exception handler — side-by-side.

**Spring Boot (Anchor) — Resilience4j:**
```java
@Configuration
public class CircuitBreakerConfig {
    @Bean
    public CircuitBreaker paymentBreaker() {
        CircuitBreakerConfig config = CircuitBreakerConfig.custom()
            .failureRateThreshold(50)               // 50% failures → open
            .slowCallRateThreshold(50)              // 50% slow calls → open
            .slowCallDurationThreshold(Duration.ofSeconds(2))
            .waitDurationInOpenState(Duration.ofSeconds(30))
            .slidingWindowSize(10)
            .build();
        CircuitBreakerRegistry registry = CircuitBreakerRegistry.of(config);
        return registry.circuitBreaker("payment");
    }
}

@Service
class PaymentService {
    private final CircuitBreaker breaker;

    @Retry(name = "payment", fallbackMethod = "chargeFallback")
    @CircuitBreaker(name = "payment")
    public ChargeResult charge(UUID orderId, BigDecimal amount) {
        return http.post("/v1/charges", ...);   // may throw on timeout/5xx
    }

    public ChargeResult chargeFallback(UUID orderId, BigDecimal amount, Throwable t) {
        // Circuit is open or retries exhausted — degrade gracefully
        return ChargeResult.deferred(orderId);
    }
}

@ControllerAdvice
class GlobalExceptionHandler {
    @ExceptionHandler(Exception.class)
    public ResponseEntity<ProblemDetail> handleAll(Exception ex, WebRequest req) {
        log.error("Unhandled trace={}", req.getHeader("X-Trace-Id"), ex);
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(
            HttpStatus.INTERNAL_SERVER_ERROR, "An internal error occurred");
        pd.setProperty("trace_id", req.getHeader("X-Trace-Id"));
        return ResponseEntity.status(500).body(pd);
    }
}
```

**Express (Delta):**
```typescript
import circuitbreaker from "opossum";

const chargeBreaker = new circuitbreaker(chargePayment, {
    timeout: 2000,
    errorThresholdPercentage: 50,
    resetTimeout: 30000,
});

chargeBreaker.fallback(() => ({ status: "deferred" }));
chargeBreaker.on("open", () => console.warn("payment circuit OPEN"));

// Error-handling middleware (last)
app.use((err: Error, req: Request, res: Response, next: NextFunction) => {
    console.error(`trace=${(req as any).traceId}`, err);
    res.status(500).json({
        type: "https://example.com/errors/internal",
        title: "Internal Server Error", status: 500,
        trace_id: (req as any).traceId,
    });
});
```

**Laravel (Delta):**
```php
// app/Exceptions/Handler.php
class Handler extends ExceptionHandler {
    public function render($req, Throwable $e) {
        if ($e instanceof ModelNotFoundException)
            return response()->json(["error" => "not_found"], 404);
        if ($e instanceof ValidationException)
            return response()->json(["error" => "validation_failed",
                                     "errors" => $e->errors()], 422);
        Log::error("Unhandled", ["trace_id" => $req->header("X-Trace-Id"), "exception" => $e]);
        return response()->json([
            "type" => "https://example.com/errors/internal",
            "title" => "Internal Server Error", "status" => 500,
            "trace_id" => $req->header("X-Trace-Id"),
        ], 500);
    }
}
```
