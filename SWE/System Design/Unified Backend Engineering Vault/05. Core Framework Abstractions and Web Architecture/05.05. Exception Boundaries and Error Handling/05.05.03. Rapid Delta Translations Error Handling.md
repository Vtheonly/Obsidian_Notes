# 05.05.03. Rapid Delta Translations Error Handling

## What This Note Is

This is a **delta translation note**. It is intentionally short. Read it **after** completing the anchor implementation in the sibling Spring Boot note. The point is to answer one question:

> What is different in this ecosystem, and what is automatic that I had to do manually in the anchor?

If you find yourself re-learning the concept here, you have not finished the anchor. Go back.

## Implementation Deltas

The deltas to internalize:

- *TypeScript / Express*: Error-handling middleware parameters (`(err, req, res, next)`), capturing asynchronous promise rejections, avoiding unhandled rejections.
- *Python / Django & Flask*: Custom error handlers (`handler404`, `handler500`), Flask `@app.errorhandler`, writing custom DRF `exception_handler`.
- *PHP / Laravel*: The global Exception Handler (`app/Exceptions/Handler.php` or `bootstrap/app.php`), `report()` vs. `render()` methods, custom renderable exceptions.

## The Details

### *TypeScript / Express*: Error-handling middleware parameters (`(err, req, res, next)`), capturing asynchronous promise rejections, avoiding unhandled rejections

Express's error handling is built on a convention: a middleware function with four parameters (`(err, req, res, next)`) is an error handler. Express detects this by checking `fn.length === 4`. When `next(err)` is called with an argument, or when a synchronous exception is thrown in a middleware, Express skips all subsequent non-error middleware and invokes the next error-handling middleware. The error middleware must be registered last (after all route handlers and normal middleware) — otherwise it never sees the errors.

The trap is that Express 4 does not catch promise rejections from `async` middleware automatically. A handler like `app.get("/api/x", async (req, res) => { throw new Error("oops"); })` results in an unhandled promise rejection, which (in Node 15+) crashes the process. The fix is either to wrap every async handler in `try/catch` and call `next(err)`, or to use the `express-async-errors` package (patches Express to forward rejections), or to write an `asyncHandler(fn)` wrapper that catches and forwards.

```typescript
import express, { Request, Response, NextFunction, ErrorRequestHandler } from "express";

const app = express();

// Wrap async handlers so rejections are forwarded to the error middleware
function asyncHandler(fn: (req: Request, res: Response, next: NextFunction) => Promise<void>) {
    return (req: Request, res: Response, next: NextFunction) => {
        Promise.resolve(fn(req, res, next)).catch(next);
    };
}

// Domain exceptions — thrown by the service layer
class OrderNotFoundError extends Error {
    constructor(public orderId: string) { super(`Order ${orderId} not found`); }
}
class EmailConflictError extends Error {}
class ValidationError extends Error {
    constructor(public fields: { field: string; message: string }[]) {
        super("Validation failed");
    }
}

// Route handler — async errors are caught by asyncHandler and forwarded
app.get("/api/orders/:id", asyncHandler(async (req, res) => {
    const order = await orderService.find(req.params.id);
    if (!order) throw new OrderNotFoundError(req.params.id);
    res.json(order);
}));

app.post("/api/users", asyncHandler(async (req, res) => {
    const result = CreateUserSchema.safeParse(req.body);
    if (!result.success) {
        throw new ValidationError(
            result.error.issues.map(i => ({ field: i.path.join("."), message: i.message }))
        );
    }
    const user = await userService.create(result.data);
    res.status(201).json(user);
}));

// Error-handling middleware — MUST be registered LAST, MUST have 4 args.
// Express detects it by fn.length === 4.
const errorHandler: ErrorRequestHandler = (err, req, res, _next) => {
    const traceId = (req as any).traceId ?? crypto.randomUUID();
    console.error(`[trace=${traceId}]`, err);

    if (err instanceof OrderNotFoundError) {
        return res.status(404).json({
            type: "https://example.com/errors/order-not-found",
            title: "Order Not Found", status: 404,
            detail: err.message, trace_id: traceId,
        });
    }
    if (err instanceof EmailConflictError) {
        return res.status(409).json({
            type: "https://example.com/errors/email-conflict",
            title: "Email Already Registered", status: 409,
            detail: err.message, trace_id: traceId,
        });
    }
    if (err instanceof ValidationError) {
        return res.status(400).json({
            type: "https://example.com/errors/validation",
            title: "Bad Request", status: 400,
            detail: "Validation failed for the request body",
            trace_id: traceId, errors: err.fields,
        });
    }
    // Catch-all — generic 500, no internal details leaked
    return res.status(500).json({
        type: "https://example.com/errors/internal",
        title: "Internal Server Error", status: 500,
        detail: `An internal error occurred. Quote trace ID ${traceId} when reporting.`,
        trace_id: traceId,
    });
};

app.use(errorHandler);   // MUST be the last app.use() call

// Global unhandled rejection / uncaught exception handlers — last line of defence
process.on("unhandledRejection", (reason, promise) => {
    console.error("Unhandled Rejection at:", promise, "reason:", reason);
    // In Node 15+ this would crash the process; we log and continue.
    // In production, consider crashing: process.exit(1);
});

process.on("uncaughtException", (err) => {
    console.error("Uncaught Exception:", err);
    // CRASH — the process state is now unknown, must restart
    process.exit(1);
});

app.listen(8080);
```

What is automatic here that was manual in the anchor: the 4-argument signature detection is the only "magic" — Express automatically routes errors to the right middleware based on the function arity. The `asyncHandler` wrapper is a one-line utility that makes async error handling uniform across all route handlers. The `process.on("unhandledRejection")` and `process.on("uncaughtException")` handlers are automatic — Node calls them without you wiring anything.

What is manual here that was automatic in the anchor: every async handler must be wrapped (no equivalent of Spring's "throwing from a controller method is automatically caught"). The error shape is constructed by hand (no `ProblemDetail.forStatusAndDetail`). The `instance` URI must be set manually from `req.path`. There is no equivalent of `ResponseEntityExceptionHandler` for framework errors — `ERR_HTTP_HEADERS_SENT` (when a handler tries to write after the response has been sent) crashes the process rather than being catchable.

The runtime invariant exposed differently: Node's crash-on-error philosophy means an unhandled exception terminates the process. This is structurally different from Spring's request-level fault isolation — a single bug can take down the entire service. The mitigation is process management (PM2, Kubernetes) that restarts the process, and the `uncaughtException` handler that logs before exiting.

### *Python / Django & Flask*: Custom error handlers (`handler404`, `handler500`), Flask `@app.errorhandler`, writing custom DRF `exception_handler`

Django and Flask take different approaches. Django uses module-level callables (`handler404`, `handler500`, `handler403`) configured in `ROOT_URLCONF`; Flask uses the `@app.errorhandler(code_or_exception)` decorator. Django REST Framework (DRF) adds its own exception handler layer on top of Django's, sitting between the view and Django's `handler500`.

```python
# ─── Django ────────────────────────────────────────────────────────
# myapp/urls.py — root URLconf
from django.urls import path
from . import views

handler404 = "myapp.views.custom_404"
handler500 = "myapp.views.custom_500"
handler403 = "myapp.views.custom_403"

urlpatterns = [
    path("api/orders/<uuid:id>/", views.order_detail),
]

# myapp/views.py
import logging
import uuid
from django.http import JsonResponse, HttpRequest

log = logging.getLogger(__name__)

def _trace_id(request: HttpRequest) -> str:
    return request.headers.get("X-Trace-Id", uuid.uuid4().hex)

def custom_404(request: HttpRequest, exception=None):
    return JsonResponse({
        "type": "https://example.com/errors/not-found",
        "title": "Not Found", "status": 404,
        "detail": f"The path {request.path} was not found",
        "trace_id": _trace_id(request),
    }, status=404)

def custom_500(request: HttpRequest):
    log.exception("Unhandled 500 trace=%s path=%s", _trace_id(request), request.path)
    return JsonResponse({
        "type": "https://example.com/errors/internal",
        "title": "Internal Server Error", "status": 500,
        "detail": "An internal error occurred",
        "trace_id": _trace_id(request),
    }, status=500)

# View-level exceptions — Django catches Http404 and renders handler404;
# everything else bubbles to handler500.
from django.http import Http404
from django.shortcuts import get_object_or_404

def order_detail(request, id):
    order = get_object_or_404(Order, id=id)   # raises Http404 if not found
    return JsonResponse({"id": str(order.id), "total": order.total})

# ─── Django REST Framework ─────────────────────────────────────────
# myapp/exceptions.py — custom DRF exception handler
from rest_framework.views import exception_handler
from rest_framework.exceptions import NotFound, ValidationError, AuthenticationFailed

def custom_drf_exception_handler(exc, context):
    # First, call the default DRF handler to get the standard response
    response = exception_handler(exc, context)
    if response is None:
        # DRF did not handle it — fall back to a 500
        request = context["request"]
        log.exception("Unhandled DRF exception trace=%s", _trace_id(request))
        return JsonResponse({
            "type": "https://example.com/errors/internal",
            "title": "Internal Server Error", "status": 500,
            "detail": "An internal error occurred",
            "trace_id": _trace_id(request),
        }, status=500)

    # Wrap the standard DRF response in a ProblemDetail shape
    request = context["request"]
    response.data = {
        "type": f"https://example.com/errors/{response.status_code}",
        "title": response.status_text,
        "status": response.status_code,
        "detail": str(exc),
        "trace_id": _trace_id(request),
        "errors": response.data if isinstance(response.data, dict) else None,
    }
    return response

# settings.py
REST_FRAMEWORK = {
    "EXCEPTION_HANDLER": "myapp.exceptions.custom_drf_exception_handler",
}
```

```python
# ─── Flask ─────────────────────────────────────────────────────────
from flask import Flask, jsonify, request, g
import logging, uuid

app = Flask(__name__)
log = logging.getLogger(__name__)

class OrderNotFoundError(Exception):
    def __init__(self, order_id): self.order_id = order_id; super().__init__(f"Order {order_id} not found")

@app.errorhandler(404)
def not_found(err):
    return jsonify({
        "type": "https://example.com/errors/not-found",
        "title": "Not Found", "status": 404,
        "detail": f"The path {request.path} was not found",
        "trace_id": getattr(g, "trace_id", None),
    }), 404

@app.errorhandler(OrderNotFoundError)
def order_not_found(err):
    return jsonify({
        "type": "https://example.com/errors/order-not-found",
        "title": "Order Not Found", "status": 404,
        "detail": str(err),
        "trace_id": getattr(g, "trace_id", None),
    }), 404

@app.errorhandler(Exception)
def unhandled(err):
    # Catch-all — must be registered for Exception to catch all unhandled
    log.exception(f"trace={getattr(g, 'trace_id', '')} path={request.path}")
    return jsonify({
        "type": "https://example.com/errors/internal",
        "title": "Internal Server Error", "status": 500,
        "detail": "An internal error occurred",
        "trace_id": getattr(g, "trace_id", None),
    }), 500

@app.get("/api/orders/<uuid:oid>")
def get_order(oid):
    order = order_service.find(oid)
    if order is None:
        raise OrderNotFoundError(str(oid))   # caught by @app.errorhandler(OrderNotFoundError)
    return jsonify(order)
```

What is automatic here that was manual in the anchor: Django's `get_object_or_404` raises `Http404`, which Django automatically routes to `handler404` — no `try/catch` needed. Flask's `@app.errorhandler(Exception)` is the catch-all — Flask automatically routes any uncaught exception to it. DRF's `exception_handler` already handles DRF's own exceptions (`NotAuthenticated`, `PermissionDenied`, `ValidationError`) and renders them as JSON with the right status code; you just augment the shape.

What is manual here that was automatic in the anchor: there is no `@ControllerAdvice` aggregation — every Django/Flask app has one set of error handlers, not one per module. There is no equivalent of `ResponseEntityExceptionHandler` for framework exceptions — Django's `handler500` is the only framework-level hook, and it has no access to the exception type. Flask's `@app.errorhandler` is registered by exception type or HTTP code, not by annotation, so the resolution is simpler but less flexible.

The runtime invariant exposed differently: CPython's GIL means a single Django/Flask worker handles one request at a time, so a 500 in one request cannot corrupt another request's state — the worker survives. But the worker process may accumulate leaked state (an unclosed DB session, an unreleased lock) and slowly degrade. The mitigation is to recycle workers periodically (`--max-requests 1000` in gunicorn restarts each worker after 1000 requests).

### *PHP / Laravel*: The global Exception Handler (`app/Exceptions/Handler.php` or `bootstrap/app.php`), `report()` vs. `render()` methods, custom renderable exceptions

Laravel's exception handling is centred on a single class: `App\Exceptions\Handler` (Laravel 10 and earlier) or the `withExceptions` callback in `bootstrap/app.php` (Laravel 11). The handler has two methods: `report(Throwable $e)` (logs, sends to Sentry, etc. — does not affect the response) and `render($req, Throwable $e)` (returns a `Response` to the client). The split lets you log without rendering (e.g., report a 500 to Sentry but render a generic message) and render without logging (e.g., a 404 does not need to go to Sentry).

```php
<?php
// ─── Laravel 11: bootstrap/app.php ────────────────────────────────
use Illuminate\Foundation\Application;
use Illuminate\Foundation\Configuration\Exceptions;
use Illuminate\Foundation\Configuration\Middleware;
use Illuminate\Http\Request;
use Illuminate\Validation\ValidationException;
use Symfony\Component\HttpKernel\Exception\{NotFoundHttpException, MethodNotAllowedHttpException};

return Application::configure(basePath: dirname(__DIR__))
    ->withExceptions(function (Exceptions $exceptions) {
        // Custom rendering for specific exception types
        $exceptions->render(function (OrderNotFoundException $e, Request $req) {
            return response()->json([
                "type" => "https://example.com/errors/order-not-found",
                "title" => "Order Not Found", "status" => 404,
                "detail" => $e->getMessage(),
                "trace_id" => $req->header("X-Trace-Id"),
            ], 404);
        });

        $exceptions->render(function (EmailConflictException $e, Request $req) {
            return response()->json([
                "type" => "https://example.com/errors/email-conflict",
                "title" => "Email Already Registered", "status" => 409,
                "detail" => $e->getMessage(),
                "trace_id" => $req->header("X-Trace-Id"),
            ], 409);
        });

        // Custom rendering for framework exceptions
        $exceptions->render(function (NotFoundHttpException $e, Request $req) {
            return response()->json([
                "type" => "https://example.com/errors/not-found",
                "title" => "Not Found", "status" => 404,
                "detail" => "The path {$req->path()} was not found",
                "trace_id" => $req->header("X-Trace-Id"),
            ], 404);
        });

        // Validation failures are rendered automatically by Laravel as 422 JSON
        // with {message, errors:{field:[messages]}} — augment if you need RFC 7807
        $exceptions->render(function (ValidationException $e, Request $req) {
            return response()->json([
                "type" => "https://example.com/errors/validation",
                "title" => "Bad Request", "status" => 422,
                "detail" => "Validation failed for the request body",
                "trace_id" => $req->header("X-Trace-Id"),
                "errors" => collect($e->errors())->map(fn($msgs, $field) => [
                    "field" => $field,
                    "message" => $msgs[0],
                ])->values(),
            ], 422);
        });

        // Catch-all for unhandled — 500 with no internal details
        $exceptions->render(function (Throwable $e, Request $req) {
            // Log server-side with full stack trace
            logger()->error("Unhandled exception", [
                "trace_id" => $req->header("X-Trace-Id"),
                "exception" => $e,
            ]);

            // Generic message client-side
            return response()->json([
                "type" => "https://example.com/errors/internal",
                "title" => "Internal Server Error", "status" => 500,
                "detail" => "An internal error occurred. Quote trace ID "
                          . $req->header("X-Trace-Id", "unknown")
                          . " when reporting this issue.",
                "trace_id" => $req->header("X-Trace-Id"),
            ], 500);
        });

        // Report-only — send to Sentry, do not render
        $exceptions->report(function (OrderNotFoundException $e) {
            // 404s do not go to Sentry — they are normal client errors
            return false;   // false = do not use the default reporter
        });

        $exceptions->report(function (Throwable $e) {
            // Everything else goes to Sentry if it is configured
            if (app()->bound("sentry")) {
                app("sentry")->captureException($e);
            }
        });

        // Throttle 500 reports to avoid spamming Sentry on a cascade
        $exceptions->throttling(function ($e) {
            return $e instanceof \Illuminate\Database\QueryException
                ? \Illuminate\Cache\RateLimiter::for("db-errors", fn() => \Illuminate\Support\Facades\RateLimiter::allowPerMinute(5))
                : null;
        });
    })
    ->create();
```

```php
<?php
// ─── Custom renderable exception ──────────────────────────────────
// A class that implements its own render() method — Laravel calls it
// automatically; you do not need to register it in withExceptions.

namespace App\Exceptions;

class OrderNotFoundException extends \RuntimeException
{
    public function __construct(public readonly string $orderId)
    {
        parent::__construct("Order {$orderId} not found");
    }

    public function render(\Illuminate\Http\Request $req)
    {
        return response()->json([
            "type" => "https://example.com/errors/order-not-found",
            "title" => "Order Not Found", "status" => 404,
            "detail" => $this->getMessage(),
            "trace_id" => $req->header("X-Trace-Id"),
        ], 404);
    }

    public function report(): bool
    {
        // 404s are not bugs — do not send to Sentry
        return false;   // false = stop propagation to the default reporter
    }
}

// In a controller:
class OrderController extends Controller {
    public function show(string $id) {
        $order = Order::find($id);
        throw_unless($order, new OrderNotFoundException($id));
        return response()->json($order);
    }
}
```

What is automatic here that was manual in the anchor: Laravel's `ValidationException` is rendered automatically as 422 JSON — no `@ExceptionHandler` needed; the FormRequest throws it before the controller runs. The `render()` method on a custom exception class is called automatically by Laravel's handler — you do not need to register the exception anywhere. The `report()` / `render()` split is a clean separation of concerns that Spring does not have (Spring's `@ExceptionHandler` does both). The throttling API (`$exceptions->throttling`) limits how often an exception is reported, preventing Sentry cascade spam.

What is manual here that was automatic in the anchor: there is no `ResponseEntityExceptionHandler` base class — you must register every framework exception type explicitly. There is no `ProblemDetail` class — you construct the array by hand. The `report()` method's return value (`false` to stop, `true`/`null` to continue) is a convention that is easy to get wrong.

The runtime invariant exposed differently: PHP-FPM's per-request process model means there is no "stale exception handler" bug — the handler is constructed fresh on every request. The `render()` method on a custom exception is invoked via PHP reflection (`method_exists($e, "render")`), which is fast (~10µs) but is a per-request lookup. Under Laravel Octane (long-lived PHP), the handler is cached, which is closer to Spring's behaviour but introduces the cross-request leak risk.

## Cross-Ecosystem Code

The same error-handling concept — 404 not found, 500 internal, RFC 7807 shape — side-by-side.

**Spring Boot (Anchor):**
```java
@ControllerAdvice
class GlobalExceptionHandler {
    @ExceptionHandler(OrderNotFoundException.class)
    public ResponseEntity<ProblemDetail> handleNotFound(OrderNotFoundException ex, WebRequest req) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
        pd.setType(URI.create("https://example.com/errors/order-not-found"));
        pd.setTitle("Order Not Found");
        pd.setProperty("trace_id", req.getHeader("X-Trace-Id"));
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(pd);
    }

    @ExceptionHandler(Throwable.class)
    public ResponseEntity<ProblemDetail> handleAll(Throwable ex, WebRequest req) {
        log.error("Unhandled trace={}", req.getHeader("X-Trace-Id"), ex);
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.INTERNAL_SERVER_ERROR,
                "An internal error occurred");
        pd.setProperty("trace_id", req.getHeader("X-Trace-Id"));
        return ResponseEntity.status(500).body(pd);
    }
}
```
