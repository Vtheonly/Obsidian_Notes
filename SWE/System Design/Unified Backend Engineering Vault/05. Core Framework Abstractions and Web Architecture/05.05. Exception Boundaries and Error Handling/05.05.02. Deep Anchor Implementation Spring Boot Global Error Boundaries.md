# 05.05.02. Deep Anchor Implementation Spring Boot Global Error Boundaries

## Why This Is the Anchor

This note is the **deep anchor implementation** — the place where you build the exception boundary concept in Spring Boot with production-grade depth. Per the Anchor and Delta protocol ([[00.02. The Anchor and Delta Learning Protocol]]), you must break this implementation before moving to the delta notes. The point is to acquire scars: real experience with the failure modes that this concept produces under load.

Spring Boot is the anchor for error handling because its `@ControllerAdvice` + `@ExceptionHandler` mechanism is the most flexible of any framework: you can scope handlers globally (every controller) or per-package (only certain controllers), you can match by exception type or by response status, you can intercept framework-thrown exceptions (`MethodArgumentNotValidException`, `HttpMessageNotReadableException`) before they reach the client, and you can render RFC 7807 `ProblemDetail` natively (Spring 6+). Express, Django, Flask, and Laravel have simpler mechanisms that cover less surface area.

## What You Will Build

The implementation covers:

- Handling errors with `@ControllerAdvice` and `@ExceptionHandler`.
- Intercepting framework exceptions: `MethodArgumentNotValidException`, `HttpRequestMethodNotSupportedException`.
- Constructing a consistent RFC 7807 Error Response entity across all endpoints.

## Anchor Implementation (Spring Boot)

The code below is a complete, runnable Spring Boot 3.x exception boundary: a `@ControllerAdvice` that handles 404, 400, 409, 405, 415, 401, 403, and 500, rendering each as an RFC 7807 `ProblemDetail` body. The four canonical failure scenarios (404 not-found, 400 validation, 409 conflict, 500 internal) are demonstrated with real curl commands.

```java
// src/main/java/com/example/web/GlobalExceptionHandler.java
package com.example.web;

import com.example.orders.OrderNotFoundException;
import com.example.users.EmailAlreadyRegisteredException;
import jakarta.validation.ConstraintViolationException;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.dao.DataIntegrityViolationException;
import org.springframework.http.*;
import org.springframework.security.access.AccessDeniedException;
import org.springframework.security.core.AuthenticationException;
import org.springframework.web.*;
import org.springframework.web.bind.*;
import org.springframework.web.bind.annotation.*;
import org.springframework.web.context.request.WebRequest;
import org.springframework.web.servlet.mvc.method.annotation.ResponseEntityExceptionHandler;
import java.net.URI;
import java.time.Instant;
import java.util.*;
import java.util.stream.Collectors;

@ControllerAdvice
public class GlobalExceptionHandler extends ResponseEntityExceptionHandler {

    private static final Logger log = LoggerFactory.getLogger(GlobalExceptionHandler.class);

    // ───────── 404: domain not found ─────────
    @ExceptionHandler(OrderNotFoundException.class)
    public ResponseEntity<ProblemDetail> handleOrderNotFound(OrderNotFoundException ex, WebRequest req) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
        pd.setType(URI.create("https://example.com/errors/order-not-found"));
        pd.setTitle("Order Not Found");
        pd.setInstance(URI.create(req.getDescription(false)));
        pd.setProperty("trace_id", traceId(req));
        pd.setProperty("timestamp", Instant.now());
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(pd);
    }

    // ───────── 409: business rule violation (duplicate email) ─────────
    @ExceptionHandler(EmailAlreadyRegisteredException.class)
    public ResponseEntity<ProblemDetail> handleEmailConflict(EmailAlreadyRegisteredException ex, WebRequest req) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.CONFLICT, ex.getMessage());
        pd.setType(URI.create("https://example.com/errors/email-conflict"));
        pd.setTitle("Email Already Registered");
        pd.setProperty("trace_id", traceId(req));
        pd.setProperty("timestamp", Instant.now());
        return ResponseEntity.status(HttpStatus.CONFLICT).body(pd);
    }

    // ───────── 409: database-level constraint violation (catches the ones the service missed) ─────────
    @ExceptionHandler(DataIntegrityViolationException.class)
    public ResponseEntity<ProblemDetail> handleDataIntegrity(DataIntegrityViolationException ex, WebRequest req) {
        // Log the full exception — the constraint name and SQL are useful for debugging
        log.warn("Data integrity violation trace={} cause={}", traceId(req), ex.getRootCause() != null ? ex.getRootCause().getMessage() : ex.getMessage());

        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.CONFLICT,
                "A data integrity constraint was violated");
        pd.setType(URI.create("https://example.com/errors/data-integrity"));
        pd.setTitle("Conflict");
        pd.setProperty("trace_id", traceId(req));
        // DO NOT expose the constraint name or SQL to the client — they reveal schema topology
        return ResponseEntity.status(HttpStatus.CONFLICT).body(pd);
    }

    // ───────── 400: Bean Validation failure on @Valid @RequestBody ─────────
    @Override
    protected ResponseEntity<Object> handleMethodArgumentNotValid(
            MethodArgumentNotValidException ex, HttpHeaders headers,
            HttpStatusCode status, WebRequest request) {

        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST,
                "Validation failed for the request body");
        pd.setType(URI.create("https://example.com/errors/validation"));
        pd.setTitle("Bad Request");
        pd.setProperty("trace_id", traceId(request));
        pd.setProperty("timestamp", Instant.now());

        List<Map<String, String>> errors = ex.getBindingResult().getFieldErrors().stream()
                .map(fe -> {
                    Map<String, String> e = new LinkedHashMap<>();
                    e.put("field", fe.getField());
                    e.put("rejected", fe.getRejectedValue() == null ? "null" : fe.getRejectedValue().toString());
                    e.put("message", fe.getDefaultMessage());
                    return e;
                })
                .collect(Collectors.toList());
        pd.setProperty("errors", errors);

        return handleExceptionInternal(ex, pd, headers, status, request);
    }

    // ───────── 400: Bean Validation failure on @PathVariable / @RequestParam ─────────
    @ExceptionHandler(ConstraintViolationException.class)
    public ResponseEntity<ProblemDetail> handleConstraintViolation(ConstraintViolationException ex, WebRequest req) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST,
                "A path or query parameter failed validation");
        pd.setType(URI.create("https://example.com/errors/constraint-violation"));
        pd.setTitle("Bad Request");
        pd.setProperty("trace_id", traceId(req));
        List<Map<String, String>> errors = ex.getConstraintViolations().stream()
                .map(cv -> Map.of(
                        "field", cv.getPropertyPath().toString(),
                        "rejected", cv.getInvalidValue() == null ? "null" : cv.getInvalidValue().toString(),
                        "message", cv.getMessage()))
                .collect(Collectors.toList());
        pd.setProperty("errors", errors);
        return ResponseEntity.status(HttpStatus.BAD_REQUEST).body(pd);
    }

    // ───────── 400: malformed JSON / unknown field ─────────
    @Override
    protected ResponseEntity<Object> handleHttpMessageNotReadable(
            HttpMessageNotReadableException ex, HttpHeaders headers,
            HttpStatusCode status, WebRequest request) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST,
                "The request body is not valid JSON or violates the expected schema");
        pd.setType(URI.create("https://example.com/errors/malformed-body"));
        pd.setTitle("Bad Request");
        pd.setProperty("trace_id", traceId(request));
        // Do not include ex.getMessage() — it may include the full JSON payload
        return handleExceptionInternal(ex, pd, headers, status, request);
    }

    // ───────── 405: wrong HTTP method ─────────
    @Override
    protected ResponseEntity<Object> handleHttpRequestMethodNotSupported(
            HttpRequestMethodNotSupportedException ex, HttpHeaders headers,
            HttpStatusCode status, WebRequest request) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.METHOD_NOT_ALLOWED,
                "Method " + ex.getMethod() + " is not supported for this endpoint");
        pd.setType(URI.create("https://example.com/errors/method-not-allowed"));
        pd.setTitle("Method Not Allowed");
        pd.setProperty("trace_id", traceId(request));
        pd.setProperty("supported_methods", ex.getSupportedHttpMethods() != null
                ? ex.getSupportedHttpMethods().stream().map(HttpMethod::name).collect(Collectors.toList())
                : List.of());
        return handleExceptionInternal(ex, pd, headers, status, request);
    }

    // ───────── 401: authentication failure (from Spring Security) ─────────
    @ExceptionHandler(AuthenticationException.class)
    public ResponseEntity<ProblemDetail> handleAuthN(AuthenticationException ex, WebRequest req) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.UNAUTHORIZED,
                "Authentication is required or the provided credentials are invalid");
        pd.setType(URI.create("https://example.com/errors/unauthenticated"));
        pd.setTitle("Unauthorized");
        pd.setProperty("trace_id", traceId(req));
        // WWW-Authenticate header tells the client which auth scheme to use
        HttpHeaders headers = new HttpHeaders();
        headers.set(HttpHeaders.WWW_AUTHENTICATE, "Bearer realm=\"api\"");
        return new ResponseEntity<>(pd, headers, HttpStatus.UNAUTHORIZED);
    }

    // ───────── 403: authorization failure ─────────
    @ExceptionHandler(AccessDeniedException.class)
    public ResponseEntity<ProblemDetail> handleAuthZ(AccessDeniedException ex, WebRequest req) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.FORBIDDEN,
                "You do not have permission to perform this action");
        pd.setType(URI.create("https://example.com/errors/forbidden"));
        pd.setTitle("Forbidden");
        pd.setProperty("trace_id", traceId(req));
        return ResponseEntity.status(HttpStatus.FORBIDDEN).body(pd);
    }

    // ───────── 500: catch-all for any unhandled exception ─────────
    @ExceptionHandler(Throwable.class)
    public ResponseEntity<ProblemDetail> handleAll(Throwable ex, WebRequest req) {
        // Log the full stack trace server-side with full request context
        log.error("Unhandled exception trace={} path={}",
                  traceId(req), req.getDescription(false), ex);

        // Return a generic message client-side — no internals, no stack trace
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(
                HttpStatus.INTERNAL_SERVER_ERROR,
                "An internal error occurred. Quote trace ID " + traceId(req)
                + " when reporting this issue.");
        pd.setType(URI.create("https://example.com/errors/internal"));
        pd.setTitle("Internal Server Error");
        pd.setProperty("trace_id", traceId(req));
        pd.setProperty("timestamp", Instant.now());
        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR).body(pd);
    }

    private String traceId(WebRequest req) {
        String h = req.getHeader("X-Trace-Id");
        return h != null ? h : UUID.randomUUID().toString();
    }
}
```

## The Details

### Handling errors with `@ControllerAdvice` and `@ExceptionHandler`

`@ControllerAdvice` is a stereotype that marks a class as a cross-cutting exception handler for one or more controllers. Without arguments, it applies globally — every `@ExceptionHandler` method in the class handles exceptions thrown by any controller. With `@ControllerAdvice("com.example.orders")` it applies only to controllers in that package, allowing you to scope handlers per module. With `@ControllerAdvice(assignableTypes = {OrderController.class, UserController.class})` it applies to specific controllers.

`@ExceptionHandler(SomeException.class)` marks a method as the handler for that exception type. When an exception is thrown during request handling, Spring's `ExceptionHandlerExceptionResolver` walks the registered handlers in order, looking for one whose declared exception type matches (or is a supertype of) the thrown exception. The first match wins. If no `@ExceptionHandler` matches, Spring falls back to `ResponseStatusExceptionResolver` (which checks `@ResponseStatus` on the exception class) and then to `DefaultHandlerExceptionResolver` (which handles a fixed list of Spring framework exceptions).

The handler method's return type can be `ProblemDetail`, `ResponseEntity<ProblemDetail>`, `ResponseEntity<Void>` (for empty responses like 204), `ModelAndView` (for HTML responses), or any object that an `HttpMessageConverter` can serialise. The `WebRequest` parameter gives access to headers, request attributes, and the principal — useful for adding the trace ID to the response body. The exception parameter is the thrown exception; you can read `ex.getMessage()`, `ex.getCuse()`, `ex.getStackTrace()`, but be careful what you put in the response — anything you return is visible to the client.

```text
  @ExceptionHandler resolution order (most specific to least specific):

  1. @ExceptionHandler(OrderNotFoundException.class)   ← exact type match
  2. @ExceptionHandler(NoSuchElementException.class)    ← superclass match
  3. @ExceptionHandler(RuntimeException.class)          ← higher superclass
  4. @ExceptionHandler(Exception.class)                 ← catch-all
  5. @ExceptionHandler(Throwable.class)                ← absolute catch-all (catches Errors too)

  Spring walks this list and uses the FIRST match. If you have both
  @ExceptionHandler(RuntimeException.class) and @ExceptionHandler(Exception.class),
  a RuntimeException thrown will be handled by the RuntimeException handler —
  the Exception handler is for checked exceptions only.
```

The production failure mode of `@ControllerAdvice` is the "exception masking" bug. A handler declared `@ExceptionHandler(Exception.class)` catches everything, including `NullPointerException` from a bug in your own code — the 500 response is rendered cleanly, the client sees a generic error, and the operator never knows the bug exists because the exception was "handled". The fix is to log every exception in the catch-all handler (`log.error("Unhandled", ex)`) and to alert on the 500 rate (any sustained 500 rate > 0.1% is a bug).

### Intercepting framework exceptions: `MethodArgumentNotValidException`, `HttpRequestMethodNotSupportedException`

Spring throws a fixed set of framework exceptions when the request fails to match the controller contract. These are not your application's exceptions — they are Spring's — and they need the same RFC 7807 treatment as your domain exceptions. `ResponseEntityExceptionHandler` (the Spring base class) handles them out of the box, but the default response is a bare `ProblemDetail` with no `trace_id` and no extension fields. Subclassing it and overriding the `handle*` methods lets you add the trace ID and the consistent shape.

The most important framework exceptions to handle: `MethodArgumentNotValidException` (Bean Validation failure on `@Valid @RequestBody`), `ConstraintViolationException` (Bean Validation failure on `@PathVariable` / `@RequestParam` with `@Validated` on the controller), `HttpMessageNotReadableException` (malformed JSON or unknown field), `HttpRequestMethodNotSupportedException` (POST to a GET-only endpoint → 405), `HttpMediaTypeNotSupportedException` (wrong Content-Type → 415), `HttpMediaTypeNotAcceptableException` (Accept header cannot be satisfied → 406), `MissingServletRequestParameterException` (required `@RequestParam` missing), `TypeMismatchException` (e.g. `/users/not-a-uuid` against `@PathVariable UUID`), `NoHandlerFoundException` (no route matches → 404, requires `spring.mvc.throw-exception-if-no-handler-found=true` and `spring.web.resources.add-mappings=false`).

```java
// Spring framework exception → HTTP status code → ProblemDetail shape

@ExceptionHandler({
    MethodArgumentNotValidException.class,        // 400
    ConstraintViolationException.class,           // 400
    HttpMessageNotReadableException.class,        // 400
    MissingServletRequestParameterException.class,// 400
    TypeMismatchException.class,                  // 400
    HttpRequestMethodNotSupportedException.class, // 405
    HttpMediaTypeNotSupportedException.class,     // 415
    HttpMediaTypeNotAcceptableException.class,    // 406
    NoHandlerFoundException.class,                // 404
})
public ResponseEntity<ProblemDetail> handleFramework(Exception ex, WebRequest req) {
    // Spring already mapped these to the right status via ResponseEntityExceptionHandler;
    // we just add the trace_id and consistent shape.
    HttpStatus status = resolveStatus(ex);   // helper that maps ex type → HttpStatus
    ProblemDetail pd = ProblemDetail.forStatusAndDetail(status, ex.getMessage());
    pd.setType(URI.create("https://example.com/errors/" + status.name().toLowerCase()));
    pd.setTitle(status.getReasonPhrase());
    pd.setProperty("trace_id", traceId(req));
    pd.setProperty("timestamp", Instant.now());
    return ResponseEntity.status(status).body(pd);
}
```

The production failure mode of framework exceptions is the "default 500 for a 400 problem". Without a custom handler, `MethodArgumentNotValidException` is handled by `DefaultHandlerExceptionResolver`, which returns a `ProblemDetail` with status 400 but no `trace_id` and a Spring-default error format. Worse, `HttpMessageNotReadableException` from a malformed JSON body sometimes returns a 500 if not handled explicitly — the default resolver does not always handle the wrapped cause correctly. The fix is to override every `handle*` method in `ResponseEntityExceptionHandler` (or to declare `@ExceptionHandler` for each framework exception type) and to verify each one returns the expected status code with a `ProblemDetail` body via a contract test.

### Constructing a consistent RFC 7807 Error Response entity across all endpoints

RFC 7807 defines a JSON shape for HTTP error responses: `type`, `title`, `status`, `detail`, `instance`. Extension fields like `trace_id`, `timestamp`, `errors` are allowed. The benefit is uniformity — every endpoint, every status code, every error condition returns the same shape, so client-side error handling is one parser, not one per endpoint.

Spring 6's `ProblemDetail` class is the native representation. `ProblemDetail.forStatusAndDetail(status, detail)` creates one with `status` and `detail` set; you then call `setType(URI)`, `setTitle(String)`, `setInstance(URI)`, and `setProperty(key, value)` for extension fields. Spring serialises it as `application/problem+json` (the RFC 7807 media type) when you return it from a handler — the `Content-Type` header is set automatically by `HttpEntityMethodProcessor`.

The key invariant is: every error response from every endpoint must be a `ProblemDetail` with a `trace_id`. This means every handler — domain exceptions, framework exceptions, the catch-all — must construct a `ProblemDetail` and call `pd.setProperty("trace_id", traceId(req))`. The `traceId(req)` helper reads `X-Trace-Id` from the request, falling back to a generated UUID. Without this discipline, some endpoints return `ProblemDetail` with a `trace_id` and some without, and the client cannot reliably correlate errors to logs.

```text
  ProblemDetail shape (RFC 7807 + extensions):

  ┌──────────────────────────────────────────────────────────────────────────┐
  │ RFC 7807 standard fields:                                                │
  │   type      : URI  — identifies the problem type (e.g. /errors/not-found)│
  │   title     : str  — short summary ("Order Not Found")                   │
  │   status    : int  — HTTP status code (404)                              │
  │   detail    : str  — human-readable explanation ("Order 42 not found")   │
  │   instance  : URI  — identifies the specific occurrence (/api/orders/42) │
  ├──────────────────────────────────────────────────────────────────────────┤
  │ Extension fields (our convention):                                       │
  │   trace_id  : str  — UUID correlating to server logs                     │
  │   timestamp : str  — ISO-8601 instant the error was generated            │
  │   errors    : arr  — field-level violations [{field, rejected, message}] │
  │              (only present on validation failures, status 400)           │
  └──────────────────────────────────────────────────────────────────────────┘

  Client-side error handling pseudocode (one parser, every endpoint):
    try { response = fetch(url, ...) }
    catch (network_err) { show "network error"; return }

    if (response.status >= 400) {
        problem = await response.json()   // always ProblemDetail shape
        log(problem.trace_id)
        if (problem.errors) {
            // Validation failure — highlight each field
            for (e of problem.errors) highlightField(e.field, e.message)
        } else {
            show(problem.detail)
        }
    }
```

The production failure mode of inconsistent error shapes is the "client crash on unexpected response" bug. A frontend that expects `ProblemDetail` with `trace_id` receives a Spring-default `ProblemDetail` without `trace_id` from one endpoint, and the `problem.trace_id` lookup returns `undefined` — the logging call writes `trace_id=undefined`, and the operator cannot correlate. The fix is to never bypass the global handler: do not use `@ResponseStatus` on exceptions (it bypasses `@ControllerAdvice`), do not write to `HttpServletResponse` directly in a controller (it bypasses the resolver chain), do not throw `ResponseStatusException` without a matching `@ExceptionHandler` (its default rendering is sparse). Every error path must go through the `@ControllerAdvice`.

## How It Works

When a controller method throws an exception, the exception propagates up through `DispatcherServlet.doDispatch`, which catches it in a `try/catch` around `ha.handle(processedRequest, response, mappedHandler)`. The dispatcher calls `processHandlerException(request, response, handler, exception)`, which iterates the registered `HandlerExceptionResolver` beans: `ExceptionHandlerExceptionResolver` (your `@ControllerAdvice`), `ResponseStatusExceptionResolver` (`@ResponseStatus` on the exception class), `DefaultHandlerExceptionResolver` (Spring framework exceptions).

`ExceptionHandlerExceptionResolver` walks the `@ControllerAdvice` beans, finds the first one with an `@ExceptionHandler` matching the exception type, and invokes the handler method reflectively. The method's return value is processed by `HandlerMethodReturnValueHandler` — for `ProblemDetail` returns, `HttpEntityMethodProcessor` writes the response with `Content-Type: application/problem+json`. For `ResponseEntity<ProblemDetail>`, the same processor handles the entity wrapper and uses the explicit status code from the entity.

If no `@ExceptionHandler` matches, Spring falls through to `ResponseStatusExceptionResolver`, then `DefaultHandlerExceptionResolver`, then renders a default 500 with the Spring error page (or `application/problem+json` if Spring 6+ and `spring.mvc.problem-details.enabled=true`). The default rendering leaks the exception message — which is why the catch-all `@ExceptionHandler(Throwable.class)` is mandatory.

## Break It

> [!danger] Load-test failure modes you must reproduce
> Do not move on to the delta translations until you have personally reproduced each of the following in your anchor implementation:
>
> 1. **Stack trace leak via default 500.** Comment out the `@ExceptionHandler(Throwable.class)` catch-all. Throw `RuntimeException("Database password is postgres://admin:secret@db:5432/prod")` from a controller. The default `DefaultHandlerExceptionResolver` renders the message in the 500 response body — the database URL with credentials is now visible to the client. Reproduce with `curl -i http://localhost:8080/api/bug`. Fix: restore the catch-all; never include `ex.getMessage()` in the response.
> 2. **Exception masking by ordering.** Declare `@ExceptionHandler(Exception.class) handleAll(Exception ex)` BEFORE `@ExceptionHandler(OrderNotFoundException.class)`. The catch-all matches every exception including `OrderNotFoundException`, so the 404 handler never runs — every not-found becomes a 500. Fix: order handlers from most specific to least specific; Spring uses the first match.
> 3. **`@ResponseStatus` bypasses the global handler.** Annotate `OrderNotFoundException` with `@ResponseStatus(HttpStatus.NOT_FOUND)`. Spring's `ResponseStatusExceptionResolver` handles it before `ExceptionHandlerExceptionResolver` — the response is 404 but the body is empty (no ProblemDetail, no trace_id). Fix: do not use `@ResponseStatus` on exceptions that you want to render via `@ControllerAdvice`; let the handler method set the status via `ResponseEntity.status(...)`.
> 4. **Error rate spike from coercion storm.** Send 5,000 requests/sec with malformed path variables: `GET /api/orders/not-a-uuid`. Each request throws `MethodArgumentTypeMismatchException`, which your handler catches and renders as a 400 ProblemDetail. The catch is expensive: stack trace capture (~50µs), `ProblemDetail` construction (~10µs), Jackson serialisation (~30µs). At 5k req/s this is 450ms of CPU per second on one core, saturating it. Fix: add a regex constraint to the route pattern: `@GetMapping("/{id:[0-9a-fA-F-]{36}}")` so malformed requests never reach the controller.

## Profiling Hooks

While the load test runs, collect:

- **JVM**: `jstack <pid>` for thread dumps — look for threads in `RUNNABLE` on `org.springframework.web.method.annotation.ExceptionHandlerMethodResolver` (slow handler resolution); `jmap -dump:live,format=b,file=heap.hprof <pid>` for heap dumps — look for retained `ProblemDetail` instances (each ~400 bytes with the `errors` list) and retained `StackTraceElement[]` arrays (each exception captures ~32 frames × 50 bytes = 1.6 KB); `jstat -gcutil <pid> 1000` for GC pressure — exception construction is allocation-heavy.
- **OS**: `pidstat -d -r -u -w 1` for per-process CPU/RSS/context-switches; `vmstat 1` for run-queue; `ss -tan state established '( sport = :8080 )' | wc -l` for active connections.
- **App**: `/actuator/metrics/http.server.requests{status=400}` (validation failure rate — should be <1%), `/actuator/metrics/http.server.requests{status=404}` (not-found rate — should be <0.1% or you have a client bug), `/actuator/metrics/http.server.requests{status=500}` (unhandled rate — should be 0 in steady state; any non-zero rate is a bug to investigate), `/actuator/loggers/com.example.web` (tune to `DEBUG` at runtime to see handler resolution).
