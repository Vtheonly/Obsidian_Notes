# 06.08.02. Zero-Downtime Migration Patterns

## What This Is

Zero-downtime migration is the discipline of evolving a production database schema without taking the application offline. It is the operational answer to a hard constraint: in a 24/7 SaaS, you cannot `ALTER TABLE users DROP COLUMN email` while 5,000 users are logged in, because the column drop acquires an `ACCESS EXCLUSIVE` lock that blocks all reads and writes for the duration of the rewrite — and on a 100M-row table that rewrite takes 30 minutes, during which every API call returns 503. The patterns in this note exist to make any schema change safe to apply during business hours, with no user-visible interruption.

In the layered mental model these patterns sit at the intersection of the storage engine's DDL semantics (PostgreSQL lock modes: `ACCESS SHARE`, `ROW EXCLUSIVE`, `ACCESS EXCLUSIVE`) and the application's deploy semantics (rolling restart, dual-write, feature flag). The deep insight is that *zero-downtime is not a database property — it is an application+database co-design property*. The database cannot know that the new column is nullable because the old code cannot populate it; only the application can deploy the dual-write logic first, run the backfill, then deploy the read-switch. Every zero-downtime migration is therefore a *multi-deploy* sequence: deploy code change 1, apply DDL, run backfill, deploy code change 2, apply cleanup DDL. The naive alternative — one big migration in a maintenance window — is what produces the 3 a.m. outages that this note exists to prevent.

The failure mode these patterns prevent is the *table rewrite lock*. PostgreSQL `ALTER TABLE ... ALTER COLUMN ... TYPE`, MySQL `ALTER TABLE ... ADD COLUMN ... NOT NULL DEFAULT 'x'` (pre-8.0), and any `CREATE INDEX` without `CONCURRENTLY` all acquire an `ACCESS EXCLUSIVE` lock and rebuild the entire table. On a 1TB table this is hours of downtime. The two complementary solutions taught here are the **expand-and-contract pattern** (multi-deploy application code that bridges the schema change) and **non-blocking DDL primitives** (`CREATE INDEX CONCURRENTLY`, MySQL 8 `ALGORITHM=INPLACE`, the `gh-ost` and `pt-online-schema-change` tools for MySQL).

## The Details

### Dangerous DDL operations: Full table locks during column additions with defaults (in ol...

The defining property of a dangerous DDL is that it acquires an `ACCESS EXCLUSIVE` lock and rewrites every row of the table. PostgreSQL's lock hierarchy has eight levels; `ACCESS EXCLUSIVE` is the strongest — it conflicts with every other lock mode, including `SELECT`'s implicit `ACCESS SHARE`. While it is held, no transaction can read or write the table. The rewrite copies every row to a new copy of the table with the new schema, which on a 100M-row table is ~30 minutes of disk I/O and CPU. The classic dangerous operations:

```text
   ┌──────────────────────────────────────────────────────────────────────────┐
   │  DDL operation                  │  Lock acquired      │  Rewrites table? │
   ├──────────────────────────────────────────────────────────────────────────┤
   │  ALTER TABLE ADD COLUMN         │  SHARE (PG 11+)     │  No (metadata-   │
   │    (nullable, no default)       │  EXCLUSIVE (PG<11)  │   only on PG11+) │
   │  ALTER TABLE ADD COLUMN         │  ACCESS EXCLUSIVE   │  YES — fills     │
   │    NOT NULL DEFAULT 'x' (PG<11) │                     │   default value  │
   │  ALTER TABLE ADD COLUMN         │  EXCLUSIVE LOCK     │  NO if default   │
   │    NOT NULL DEFAULT 'x' (PG11+) │  briefly            │   is constant    │
   │  ALTER TABLE ALTER COLUMN TYPE  │  ACCESS EXCLUSIVE   │  YES — full copy │
   │  ALTER TABLE DROP COLUMN        │  ACCESS EXCLUSIVE   │  Yes (PG) / No   │
   │                                 │                     │   (PG13+ metadata)│
   │  CREATE INDEX                   │  SHARE (blocks      │  Yes (builds new │
   │                                 │   writes)           │   index)         │
   │  CREATE INDEX CONCURRENTLY      │  SHARE UPDATE       │  Yes (slower)    │
   │                                 │   EXCLUSIVE (writes │   but non-blocking│
   │                                 │   proceed)          │                  │
   │  MySQL ADD COLUMN (8.0 INPLACE) │  brief EXCLUSIVE    │  No (instant if  │
   │                                 │   for metadata      │   no default,    │
   │                                 │   change            │   else INPLACE)  │
   │  MySQL ADD COLUMN (5.7 COPY)    │  EXCLUSIVE          │  Yes — full copy │
   └──────────────────────────────────────────────────────────────────────────┘
```

A concrete example — the trap that catches every team once:

```sql
-- Intent: add a "deleted_at" column to soft-delete users.
-- WRONG — on PostgreSQL 10 and earlier, and on MySQL 5.7, this rewrites the table:
ALTER TABLE users ADD COLUMN deleted_at TIMESTAMPTZ NOT NULL DEFAULT NOW();

-- The database must:
--   1. Acquire ACCESS EXCLUSIVE lock (all SELECTs and UPDATEs block).
--   2. Allocate a new copy of the `users` table.
--   3. Copy every row, filling `deleted_at = NOW()` for each.
--   4. Replace the old table with the new one.
--   5. Release the lock.
-- On a 50M-row users table: ~10 minutes of total write lockout.

-- RIGHT — split into two steps:
ALTER TABLE users ADD COLUMN deleted_at TIMESTAMPTZ;        -- nullable, no default: instant
ALTER TABLE users ALTER COLUMN deleted_at SET DEFAULT NOW(); -- adds default, no rewrite
-- Then backfill in batches of 1000:
UPDATE users SET deleted_at = NOW() WHERE deleted_at IS NULL AND id BETWEEN 1 AND 1000;
UPDATE users SET deleted_at = NOW() WHERE deleted_at IS NULL AND id BETWEEN 1001 AND 2000;
-- ... 50,000 batches of 1,000 rows each, with a 100ms sleep between batches ...
-- Finally, add the NOT NULL constraint after the backfill completes:
ALTER TABLE users ALTER COLUMN deleted_at SET NOT NULL;     -- checks all rows, then metadata-only
```

The production failure mode is not just downtime — it is *replication cascade failure*. On a MySQL primary, a 10-minute `ALTER TABLE` blocks the binary log thread for 10 minutes, the replicas fall 10 minutes behind, and reads against replicas return stale data for any row in the affected table. On PostgreSQL streaming replication, the DDL is replicated as a single WAL record but the *rewrites* block the apply process on the replica too — the replica is unusable for failover during the migration window. Worse, on Aurora / RDS the storage layer may have less IOPS headroom than the compute layer expects, and a 10-minute rewrite on a bare-metal PostgreSQL becomes a 45-minute rewrite on a provisioned-IOPS Aurora instance that is throttling. The detection metric is `pg_locks` for `ACCESS EXCLUSIVE` waiters — `SELECT count(*) FROM pg_locks WHERE mode = 'AccessExclusiveLock' AND granted = false;` — and any non-zero count for more than a few seconds is a paging incident.

### The Expand and Contract (Parallel Run) Pattern

The expand-and-contract pattern is the canonical multi-deploy sequence that makes any schema change safe. The insight is that you cannot apply a breaking change in one step — you have to *expand* the schema to support both old and new shapes, *migrate* the data and the application code in stages, then *contract* the schema back to the new shape once nothing references the old. The four-phase pattern, applied to "rename `email` to `email_address`":

```text
   Phase 1 — EXPAND (deploy #1):
     Code: deployed version 1.1 — writes to BOTH `email` (old) and `email_v2` (new).
           Reads from `email` only.
     DDL:  ALTER TABLE users ADD COLUMN email_v2 VARCHAR(255);
           CREATE INDEX CONCURRENTLY idx_users_email_v2 ON users(email_v2);
     Backfill: UPDATE users SET email_v2 = email WHERE email_v2 IS NULL;
               (in batches of 1000, throttled, see below)

   Phase 2 — SWITCH READS (deploy #2):
     Code: deployed version 1.2 — still writes to both, now reads from `email_v2`.
     Verify: shadow-read both, log any divergence, fix data drift.
     Dwell time: 1–7 days — long enough to catch any code path still writing to `email` only.

   Phase 3 — SWITCH WRITES (deploy #3):
     Code: deployed version 1.3 — writes to `email_v2` ONLY. No longer writes `email`.
     Dwell time: 1–7 days — long enough to be sure no rollback to 1.2 is needed.

   Phase 4 — CONTRACT (deploy #4):
     DDL:  ALTER TABLE users DROP COLUMN email;
     Code: deployed version 2.0 — remove the dual-write code, remove the `email` field
           from the entity. Final clean state.
```

The dual-write logic is the load-bearing piece. In the application code (Spring service example):

```java
@Service
@Transactional
public class UserService {
    private final UserRepository repo;

    public void updateEmail(Long userId, String newEmail) {
        User u = repo.findById(userId).orElseThrow();
        u.setEmail(newEmail);            // old column — Phase 1, 2
        u.setEmailV2(newEmail);          // new column — Phase 1, 2, 3
        repo.save(u);                    // writes both
    }

    public String getEmail(Long userId) {
        User u = repo.findById(userId).orElseThrow();
        // Phase 1: return u.getEmail();
        // Phase 2: return u.getEmailV2();    // shadow-read both, log divergence
        // Phase 3: return u.getEmailV2();
        return u.getEmailV2();
    }
}
```

The backfill is the second load-bearing piece. It must be *resumable* (a crash halfway must not lose progress), *throttled* (must not saturate the database), and *observable* (must report progress so you know when to start Phase 2). A safe backfill script:

```sql
-- PostgreSQL — resumable, throttled backfill
WITH batch AS (
    SELECT id FROM users
    WHERE email_v2 IS NULL
    ORDER BY id
    LIMIT 1000
    FOR UPDATE SKIP LOCKED                -- skip rows being updated by another worker
)
UPDATE users SET email_v2 = email
WHERE id IN (SELECT id FROM batch);

-- Run in a loop with `SELECT pg_sleep(0.1)` between batches.
-- Track progress: SELECT count(*) FROM users WHERE email_v2 IS NULL;
-- Stop when count = 0, then proceed to Phase 2.
```

The `FOR UPDATE SKIP LOCKED` clause (PostgreSQL 9.5+, MySQL 8.0+) lets multiple backfill workers run concurrently without contending — each grabs a different 1000-row batch. The `pg_sleep(0.1)` between batches caps the backfill at ~10,000 rows/sec, leaving headroom for production traffic. The progress query `SELECT count(*) FROM users WHERE email_v2 IS NULL;` is the deploy gate for Phase 2 — never start Phase 2 until it returns 0.

The production failure mode of expand-and-contract is *skipping a phase*. The most common shortcut is to combine Phase 1 and Phase 4 into one deploy — "I'll add the new column, switch the code, and drop the old column in the same release." This works in dev, passes CI, and breaks catastrophically in production because the deploy is rolling — instance N+1 still has the old code that writes `email` only, but instance N just dropped the `email` column, and instance N+1's next `INSERT` fails with `column "email" does not exist`. The two-day dwell time between phases is not bureaucracy — it is the safety margin for partial deploys, rollbacks, and discovered edge cases. Skipping it is the single most common cause of multi-hour outages attributed to "schema migrations."

### Creating indexes concurrently in production without write-blocking (`CREATE INDEX CONCU...

Index creation is the DDL operation that most often surprises teams with downtime, because it *looks* safe — "it's just adding an index, what could go wrong?" The answer is that the default `CREATE INDEX` acquires a `SHARE` lock, which blocks all `INSERT`, `UPDATE`, and `DELETE` on the table for the entire build duration. On a 100M-row table, building a B-tree takes 5–10 minutes of blocked writes. The non-blocking alternatives are `CREATE INDEX CONCURRENTLY` (PostgreSQL) and `ALGORITHM=INPLACE` / `ALGORITHM=INPLACE, LOCK=NONE` (MySQL 8+); on older MySQL and on tables where even INPLACE is too slow, the third-party tools `gh-ost` and `pt-online-schema-change` shadow-copy the table.

```sql
-- PostgreSQL — non-blocking index creation
CREATE INDEX CONCURRENTLY idx_users_email_lower
  ON users (lower(email));

-- Internals:
--   1. Phase 1: take SHARE UPDATE EXCLUSIVE lock (writes proceed, only schema changes blocked).
--      Insert the index entry into pg_class with indisvalid=false, indisready=false.
--   2. Phase 2: build the index over the existing rows (slow scan, sorts, builds B-tree).
--      Writes during this phase are journaled to a side table for later replay.
--   3. Phase 3: take a brief SHARE UPDATE EXCLUSIVE lock, replay the journaled writes,
--      flip indisvalid=true. The index is now usable by the query planner.
--
-- Duration: 2-3× longer than a regular CREATE INDEX (because of the journal replay).
-- Locks: SHARE UPDATE EXCLUSIVE — never blocks INSERT/UPDATE/DELETE.
-- Failure mode: if the build fails (e.g. unique violation), the index is left in INVALID state.
--   Must be dropped and recreated: DROP INDEX CONCURRENTLY idx_users_email_lower;
```

```sql
-- MySQL 8.0 — non-blocking index creation
ALTER TABLE users ADD INDEX idx_users_email (email),
  ALGORITHM=INPLACE, LOCK=NONE;

-- ALGORITHM=INPLACE  → engine builds the index in-place (no table copy).
-- ALGORITHM=COPY     → legacy: copies the entire table (slow, blocking).
-- LOCK=NONE          → no lock held during the build (writes proceed).
-- LOCK=SHARED        → blocks writes but allows reads.
-- LOCK=EXCLUSIVE     → blocks both (default for ALGORITHM=COPY).
```

For MySQL versions before 8.0, or for operations that even INPLACE cannot do non-blocking (e.g. changing a column type), the industry-standard tools are **gh-ost** (GitHub's Online Schema Change, written in Go) and **pt-online-schema-change** (Percona Toolkit, written in Perl). Both work the same way:

```text
   gh-ost workflow (for: ALTER TABLE users ADD COLUMN deleted_at TIMESTAMPTZ):
   1. Create a "ghost" table: _users_gho with the new schema (the ALTER applied).
   2. Copy rows from users → _users_gho in batches of 200-1000, in the background.
      (SELECT ... chunkCopy → INSERT INTO _users_gho)
   3. Replay changes from the production binlog into _users_gho in real-time.
      (gh-ost connects as a MySQL replica, parses row events, applies to _users_gho)
   4. Once copy is complete and lag is zero:
        a. Briefly lock users (sub-second — RENAME time).
        b. RENAME TABLE users TO _users_del, _users_gho TO users;
        c. Unlock.
   5. Drop _users_del after a grace period.

   Total downtime: <1 second (just the RENAME).
   Total migration time: depends on table size — 1 hour per 100GB on a typical RDS instance.
   Throttle hooks: gh-ost supports throttle-on-replica-lag, throttle-on-master-load, panic file.
```

The key trade-off between `CREATE INDEX CONCURRENTLY` and `gh-ost`/`pt-osc` is *scope*. `CONCURRENTLY` only handles index creation — it cannot help you add a NOT NULL column or change a column type. `gh-ost` can handle any `ALTER TABLE` because it builds a full ghost table. The trade-off of `gh-ost` is operational complexity — it requires binlog access (the MySQL user needs `REPLICATION SLAVE` privilege), it doubles the table's storage during the migration (the ghost table is the same size as the original), and a failure halfway through leaves a ghost table that must be cleaned up manually. For a team that has not done it before, the first `gh-ost` run on a production table should be paired with someone who has done it before — the failure modes are subtle (a long-running transaction in another session blocks the final `RENAME`, and `gh-ost` waits silently until you cancel it).

The production failure mode of *all three* non-blocking strategies is the **long-running transaction interaction**. `CREATE INDEX CONCURRENTLY` cannot complete Phase 3 (flip `indisvalid=true`) while any transaction that started before Phase 2 is still open — it waits for all such transactions to commit, and if a `pg_dump` is running with a 6-hour snapshot, the index creation hangs for 6 hours. `gh-ost` cannot do the final `RENAME` while any transaction holds a lock on `users` — same hang. The detection is `SELECT pid, state, wait_event, query FROM pg_stat_activity WHERE wait_event IS NOT NULL;` showing the index-build or `gh-ost` worker blocked on `virtualxid` or `transactionid`. The fix is to set a `statement_timeout` on the migration session (`SET statement_timeout = '300s';`) so it fails loudly rather than hanging silently, and to ensure no admin `pg_dump` or long analytic query is running during the migration window. Schedule migrations in a low-traffic window even with non-blocking DDL — the *non-blocking* guarantee is for application traffic, not for ad-hoc DBA sessions.

## Cross-Ecosystem Implementation

Zero-downtime DDL primitives differ sharply between PostgreSQL and MySQL, and the third-party tools fill the gaps that the engine does not:

| Operation | PostgreSQL | MySQL 8.0 (InnoDB) | Older MySQL (5.7 and earlier) |
|---|---|---|---|
| Add nullable column | metadata-only (instant) | `ALGORITHM=INSTANT` (8.0.12+) | `ALGORITHM=COPY` (full table rewrite) |
| Add column with default | metadata-only since PG 11 | `ALGORITHM=INSTANT` for constant defaults | `ALGORITHM=COPY` (full table rewrite) |
| Add NOT NULL column | split: add nullable + backfill + SET NOT NULL | `ALGORITHM=INSTANT` (8.0+) if default is constant | full table rewrite — use `gh-ost` |
| Change column type | full table rewrite — use expand-contract | `ALGORITHM=INPLACE` only for compatible types, else COPY | use `gh-ost` or `pt-osc` |
| Create index | `CREATE INDEX CONCURRENTLY` (non-blocking) | `ALGORITHM=INPLACE, LOCK=NONE` | `gh-ost` or `pt-osc` |
| Drop column | metadata-only since PG 13 | `ALGORITHM=INSTANT` (8.0+) | full table rewrite — use `gh-ost` |
| Rename column | metadata-only (`RENAME COLUMN`) | `ALGORITHM=INSTANT` (8.0+) | full table rewrite — use `gh-ost` |

When you read the anchor implementation note, identify which PostgreSQL feature corresponds to each row above. The delta notes then show how the same operation is expressed on MySQL 8 (where `ALGORITHM=INPLACE` is the equivalent of `CONCURRENTLY`) and on older MySQL (where the engine cannot do it at all and you must reach for `gh-ost`). The key invariant is that the *application's expand-contract sequence* is identical across engines — only the DDL primitive used inside Phase 1 and Phase 4 changes.

## Hands-On Exercise

```bash
# 1. PostgreSQL — reproduce the ACCESS EXCLUSIVE lock on a dangerous DDL:
psql -d myapp -c "CREATE TABLE big (id BIGSERIAL PRIMARY KEY, payload TEXT);
                  INSERT INTO big SELECT g, md5(g::text) FROM generate_series(1, 10000000) g;"
# In session A: BEGIN; ALTER TABLE big ADD COLUMN deleted_at TIMESTAMPTZ NOT NULL DEFAULT NOW();
# In session B: SELECT * FROM big LIMIT 1;   -- HANGS until A commits.
# In session C: SELECT mode, granted FROM pg_locks WHERE relation='big'::regclass;
# Expected: AccessExclusiveLock granted=true in A's row.

# 2. PostgreSQL — observe the difference with the safe split:
psql -d myapp -c "ALTER TABLE big ADD COLUMN deleted_at TIMESTAMPTZ;"   # instant
# Session B's SELECT * FROM big LIMIT 1; does NOT block. Confirmed via pg_locks.

# 3. PostgreSQL — measure CREATE INDEX vs CREATE INDEX CONCURRENTLY:
\ timing on
CREATE INDEX idx_big_payload ON big(payload);                       -- ~30s, blocks writes
DROP INDEX idx_big_payload;
CREATE INDEX CONCURRENTLY idx_big_payload ON big(payload);          -- ~90s, writes proceed

# 4. PostgreSQL — reproduce the INVALID index state:
psql -d myapp -c "CREATE UNIQUE INDEX CONCURRENTLY idx_unique_email ON users(email);"
# If two users have the same email, this fails partway and leaves an INVALID index.
psql -d myapp -c "SELECT indexname, indisvalid FROM pg_indexes
                  JOIN pg_index ON indexname = indexrelname WHERE NOT indisvalid;"
# Recovery: DROP INDEX CONCURRENTLY idx_unique_email; then fix the duplicate rows, retry.

# 5. gh-ost — run a migration on a MySQL 5.7 replica (never on production first):
gh-ost --host=mysql-primary --user=ghost --password=... \
       --database=myapp --table=users \
       --alter="ADD COLUMN deleted_at DATETIME NULL" \
       --execute
# Watch the ghost table appear: SHOW TABLES LIKE '_users_%';
# Watch the lag: gh-ost prints "Copy: 10000/10000000 rows, 0.1%".

# 6. Observe the long-running-transaction interaction:
# Session A: BEGIN; SELECT * FROM users LIMIT 1; -- leave open for 5 minutes
# Session B: CREATE INDEX CONCURRENTLY idx_users_email ON users(email);
# Session B HANGS in phase 3, waiting for A to commit.
# Detection: SELECT pid, wait_event_type, wait_event, query
#            FROM pg_stat_activity WHERE wait_event IS NOT NULL;
# Expected: session B's wait_event = 'virtualxid'. Kill A, B completes within seconds.

# 7. Set a statement_timeout so migrations fail loud rather than hang:
psql -d myapp -c "SET statement_timeout = '300s';
                  CREATE INDEX CONCURRENTLY idx_orders_user_id ON orders(user_id);"
# If the build takes >5 min due to a long-running transaction, it aborts with
# ERROR: canceling statement due to statement timeout — and you know to investigate.
```
