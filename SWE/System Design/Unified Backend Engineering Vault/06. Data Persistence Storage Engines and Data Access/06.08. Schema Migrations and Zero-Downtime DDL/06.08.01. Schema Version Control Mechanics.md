# 06.08.01. Schema Version Control Mechanics

## What This Is

Schema version control is the discipline of treating your database schema the same way you treat your application code: as a series of ordered, reviewable, reversible changes that travel through your version control system, your CI pipeline, and your deploy pipeline as a single artefact with the code that depends on it. The migration file is the atomic unit of schema change — a script with an `up()` method that applies a change (CREATE TABLE, ALTER TABLE, CREATE INDEX) and a `down()` method that reverts it. The migration runner executes them in order against a target database, records what has been applied in a metadata table, and refuses to start the application if the database's schema version is out of sync with the code's expected version.

In the layered mental model this sits in the *operational* layer of the persistence stack — above the storage engine (PostgreSQL/MySQL know nothing about migrations; DDL is just SQL to them) and below the application's startup sequence (Spring Boot's Flyway autoconfig runs before the `EntityManagerFactory` bean is created, refusing to boot if migrations fail). The reason it exists as a separate concern from "running SQL files manually" is the **drift problem**: without a recorded, ordered migration history, two environments (staging and production) inevitably diverge — someone ran an `ALTER TABLE` by hand on staging to fix a bug, forgot to write it down, and now production has a different schema from staging. Migration tooling makes that drift impossible to ignore: the metadata table records `V14__add_user_last_login.sql` as applied on staging but not on production, and the next deploy to production runs the missing migration as part of the deploy.

The failure mode this prevents is the *untracked schema change*. A DBA logs in to production at 2 a.m. to add an index for a slow query, runs `CREATE INDEX idx_users_email ON users(email)`, and goes home. Three weeks later a migration adds the *same* index with a different name, a developer drops the old one because the new one "duplicates" it, and the migration history table now references an index that no longer exists. Migration tooling forces every schema change through a code-reviewed, version-controlled file — the DBA's manual change is detected as drift on the next deploy and either reverted or formalised. The four canonical tools are **Flyway** (Java ecosystem, simple, SQL-first), **Liquibase** (Java ecosystem, XML/YAML/JSON abstraction, more features), **Alembic** (Python/SQLAlchemy), and **Rails migrations / Django migrations / Prisma migrate** (each framework's built-in).

## The Details

### Migration files: Ordered sequential scripts (timestamped or integer versions) containin...

The migration file is a plain text artefact with three required properties: (1) a *deterministic name* that sorts lexicographically — usually `V{version}__{description}.sql` for Flyway or `{timestamp}_{description}.py` for Django/Alembic; (2) an `up` section that applies the change; (3) a `down` section that reverts it. The naming convention is load-bearing: the runner sorts files by name and applies them in order, so a file named `V2__add_users.sql` always runs after `V1__initial.sql`. Timestamps (Django `0001_initial.py`, Alembic `2024_03_15_1400_add_user_index.py`) are used when multiple developers may add migrations concurrently — the timestamp disambiguates without requiring a central version-number coordinator.

The four canonical file shapes:

```sql
-- Flyway: db/migration/V1__Create_users_table.sql
CREATE TABLE users (
    id BIGSERIAL PRIMARY KEY,
    email VARCHAR(255) UNIQUE NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Flyway: db/migration/V2__Add_user_last_login.sql
ALTER TABLE users ADD COLUMN last_login_at TIMESTAMPTZ;
```

```python
# Django: myapp/migrations/0002_user_last_login.py
from django.db import migrations, models

class Migration(migrations.Migration):
    dependencies = [("myapp", "0001_initial")]
    operations = [
        migrations.AddField(
            model_name="user",
            name="last_login_at",
            field=models.DateTimeField(null=True),
        ),
    ]
    # no down() — Django auto-generates the reverse by reversing operations
```

```python
# Alembic: migrations/versions/2024_03_15_1400_add_user_index.py
revision = "a1b2c3d4"
down_revision = "f9e8d7c6"      # builds a linked list of migrations

def upgrade():
    op.create_index("idx_users_email", "users", ["email"])

def downgrade():
    op.drop_index("idx_users_email", table_name="users")
```

```php
// Laravel: database/migrations/2024_03_15_140000_add_last_login_to_users_table.php
public function up(): void {
    Schema::table('users', function (Blueprint $table) {
        $table->timestamp('last_login_at')->nullable();
    });
}
public function down(): void {
    Schema::table('users', function (Blueprint $table) {
        $table->dropColumn('last_login_at');
    });
}
```

Two ordering strategies exist with sharp trade-offs. **Sequential integers** (Flyway `V1`, `V2`, `V3`) are human-readable but collide when two developers branch simultaneously and both pick `V15`. The Flyway solution is `sqlMigrationPrefix=V` plus a 4-digit zero-padded version, plus team discipline to rebase before merge. **Timestamps** (Django, Alembic, Laravel) eliminate the collision — two migrations created at different wall-clock times sort deterministically — but produce ugly filenames (`2024_03_15_140000_...`) and obscure the migration's logical order. The hybrid used by Flyway since 7.0 is `V{YYYY.MM.DD.HHMMSS}__name.sql` — timestamp versioning with the human-readable `V` prefix.

The `down` migration is the most-skipped and most-dangerous part. **Forward-only** advocates (Flyway's recommended mode for production) argue that down migrations are never tested, never match the actual schema state after a partial apply, and provide false confidence — better to write a *new* forward migration that reverses the change (`V3__undo_add_last_login.sql`) than to rely on a `down()` that has never been exercised. **Reversible** advocates (Django's default, Alembic's recommended) argue that down migrations are essential for local development (you `migrate 0001` to roll back to a known state) and for emergency production rollbacks. The pragmatic position: implement `down` for development convenience, never use it in production — production rollbacks are always forward migrations that undo the previous change, applied with the same review discipline as the original. The failure mode of trusting `down` in production is the *partial rollback*: `down()` runs `DROP TABLE orders`, but `up()` created `orders` *and* a foreign key from `line_items` — `down()` only drops `orders`, leaving `line_items.order_id` orphaned, and the next migration fails because the FK constraint was never recreated.

### The Schema Migrations Metadata Table: Tracking applied migrations directly in the targe...

The metadata table is the single source of truth for "what state is this database in?" It lives *inside* the database it tracks, queried at application startup, written to by the migration runner after each successful migration, and never edited by hand. Every tool has its own schema and naming convention, but the shape is universal: a row per applied migration with a version, a checksum, a timestamp, and an execution duration.

| Tool | Table name | Schema (key columns) |
|---|---|---|
| Flyway | `flyway_schema_history` | `installed_rank INT, version VARCHAR(50), description, type, script, checksum INT, installed_by, installed_on TIMESTAMPTZ, execution_time INT, success BOOL` |
| Liquibase | `databasechangelog` | `id, author, filename, dateexecuted, orderexecuted INT, exectype, md5sum, description, comments, tag, liquibase, contexts, labels, deployment_id` |
| Django | `django_migrations` | `id, app, name, applied` |
| Alembic | `alembic_version` | `version_num VARCHAR(32)` (single row! only the head) |
| Rails | `schema_migrations` | `version VARCHAR` (one row per applied migration) |
| Prisma | `_prisma_migrations` | `id, checksum, finished_at, migration_name, logs, rolled_back_at, started_at, applied_steps_count` |

The Flyway `checksum` column is the production-safety feature. When Flyway reads `V14__add_user_index.sql` from disk, it computes a CRC32 of the file contents and compares it to the stored checksum in `flyway_schema_history`. If they differ — someone edited the file after it was applied — Flyway refuses to boot the application with `FlywayValidateChecksumException`. This catches the *edited-migration* failure mode: a developer "tweaks" a migration that already ran in production, re-running it would be a no-op (the table already exists) but the next environment that runs the migration from scratch would get a different schema than production. The fix is always to add a *new* migration (`V15__fix_user_index.sql`) rather than edit an applied one; the checksum guard makes this discipline enforceable rather than aspirational.

```text
   Application startup sequence (Spring Boot + Flyway):

   1. Spring autoconfig creates DataSource bean (HikariCP pool).
   2. FlywayMigrationInitializer runs after DataSource, before EntityManagerFactory.
   3. Flyway connects, queries: SELECT * FROM flyway_schema_history ORDER BY installed_rank;
   4. Flyway scans classpath:db/migration for V*.sql files.
   5. For each file not in the metadata table:
        a. Open a transaction (if the DB supports DDL transactions — PostgreSQL yes, MySQL no).
        b. Execute the SQL.
        c. INSERT into flyway_schema_history (version, script, checksum, execution_time, success=true).
        d. Commit.
   6. If any checksum mismatch: throw FlywayValidateChecksumException, refuse to start.
   7. If all good: EntityManagerFactory bean initialises, app boots.
```

The critical operational detail is **DDL transaction support**. PostgreSQL wraps DDL inside the surrounding transaction (`CREATE TABLE` can be rolled back), so a failed migration leaves no schema debris and the metadata table stays consistent. MySQL's InnoDB does *not* support transactional DDL — `ALTER TABLE` is auto-committed, so a migration that fails halfway leaves the table in a partial state (column half-added, index half-built) and the metadata table does not record the migration as applied. On the next boot, Flyway tries to re-run it, fails on the half-applied `ALTER`, and the application is stuck in a boot loop until a DBA manually cleans up. The mitigation for MySQL-only environments is to keep migrations small and atomic (one `ALTER TABLE` per migration, never a sequence of interdependent DDL), and to test every migration on a MySQL staging database before production. Liquibase has a `<preConditions>` tag that lets a migration check "does this column already exist?" before running — useful for MySQL recovery but adds complexity. The forward-only school argues this is exactly why down migrations are pointless on MySQL: you cannot roll back an `ALTER TABLE` that has already partially applied, so the only safe path is forward to a known-good state.

The production failure mode of the metadata table itself is **manual tampering**. A common incident: an operator runs `DELETE FROM flyway_schema_history WHERE version = '14'` to "force Flyway to re-run" a migration that failed — and Flyway then tries to re-create a table that already exists, fails, and the metadata table is now permanently out of sync with the schema. The correct recovery is always `flyway repair` (recomputes checksums, marks failed migrations as deleted) or `flyway undo` (commercial feature), never hand-EDITS to the metadata table. Make the table read-only for application users (grant `SELECT`, `INSERT`, `UPDATE` only to the migration runner role), audit all writes, and back it up with the rest of the database — losing the metadata table means losing the entire migration history and having to reconstruct it by hand from the actual schema state, a multi-hour outage.

## Cross-Ecosystem Implementation

The migration tooling differs in language, file format, and metadata table name, but the underlying mechanics (ordered files, metadata table, checksum validation) are identical:

| Concept | Flyway | Liquibase | Django | Alembic | Prisma Migrate |
|---|---|---|---|---|---|
| File format | plain SQL `V*.sql` | XML / YAML / JSON changesets | Python ops (`migrations.Migration`) | Python `upgrade()`/`downgrade()` | `schema.prisma` + generated SQL |
| Naming convention | `V{version}__{desc}.sql` | arbitrary `id` + `author` | `{N:04d}_{desc}.py` | `{ts}_{desc}.py` + revision GUID | `migration.sql` per migration dir |
| Metadata table | `flyway_schema_history` | `databasechangelog` | `django_migrations` | `alembic_version` | `_prisma_migrations` |
| Checksum validation | CRC32 on file contents | MD5 on changeset content | none (file order only) | none (revision graph only) | SHA256 |
| Reversible | `down` SQL files (commercial) | `rollback` tag in changeset | auto-generated reverse ops | explicit `downgrade()` | shadow DB + reset |
| DDL transactional | yes if DB supports | yes if DB supports | no (Django runs DDL outside) | yes if DB supports | no (apply sequentially) |
| Generate from model diff | no (write SQL by hand) | no | yes (`makemigrations`) | yes (`alembic revision --autogenerate`) | yes (`prisma migrate dev`) |

When you read the anchor implementation note, identify which Flyway feature corresponds to each row above. The delta notes then show how the same migration mechanics are expressed in Django (`makemigrations` + `migrate`), in Alembic (`revision --autogenerate` + `upgrade head`), and in Prisma (`migrate dev` + `migrate deploy`). The key invariant across all of them is that the metadata table is the source of truth and must never be hand-edited.

## Hands-On Exercise

```bash
# 1. Flyway — initialise a fresh project and inspect the metadata table:
mkdir -p db/migration && cd db/migration
cat > V1__Create_users_table.sql <<'SQL'
CREATE TABLE users (id BIGSERIAL PRIMARY KEY, email VARCHAR(255) UNIQUE NOT NULL);
SQL
flyway -url=jdbc:postgresql://localhost/myapp -user=app migrate
psql -d myapp -c "SELECT installed_rank, version, description, success, execution_time
                  FROM flyway_schema_history ORDER BY installed_rank;"

# 2. Flyway — reproduce the checksum validation failure:
echo "-- extra comment" >> db/migration/V1__Create_users_table.sql   # edit applied file
flyway -url=jdbc:postgresql://localhost/myapp -user=app info
# Expected: "ERROR: Validate failed: Migration checksum mismatch for migration version 1"
# Fix: flyway repair   (recomputes checksum from current file content)
# Or: revert the file edit and re-run.

# 3. Django — autogenerate a migration from a model change:
#    Add to myapp/models.py:  last_login_at = models.DateTimeField(null=True)
python manage.py makemigrations myapp
# Creates myapp/migrations/0002_user_last_login_at.py with AddField operation.
python manage.py migrate myapp
psql -d myapp -c "SELECT app, name, applied FROM django_migrations ORDER BY applied DESC LIMIT 5;"

# 4. Alembic — autogenerate and inspect the revision graph:
alembic revision --autogenerate -m "add user index"
alembic history                      # shows the linked list of revisions
alembic current                      # shows the head applied to this DB
psql -d myapp -c "SELECT version_num FROM alembic_version;"

# 5. Reproduce the MySQL DDL transaction failure (in a disposable MySQL container):
docker run -d --name mysql-test -e MYSQL_ROOT_PASSWORD=pw mysql:8
# Create a migration with two ALTER statements where the second one fails:
cat > V2__broken.sql <<'SQL'
ALTER TABLE users ADD COLUMN deleted_at DATETIME;
ALTER TABLE non_existent_table ADD COLUMN x INT;   -- fails
SQL
flyway -url=jdbc:mysql://localhost/myapp -user=app migrate
# Result: column deleted_at IS added (auto-committed), metadata table does NOT have V2,
# next `flyway migrate` retries V2 and fails on the first statement (duplicate column).
# Recovery: drop the column by hand, then `flyway migrate` succeeds.

# 6. Verify the metadata table is being backed up with the database:
pg_dump -s -t flyway_schema_history myapp | head -20
# If empty: your backup is excluding the metadata table — fix the pg_dump command.
# A database restore without the metadata table is an unrecoverable migration disaster.
```
