# 06.00. Map of Content: Data Persistence

## Overview

This section covers **06. Data Persistence Storage Engines and Data Access**. It is part of the unified backend engineering vault described in [[00.01. Master Architectural Mental Model]]. The notes below are organized by concept, not by framework. Each concept is taught once at the conceptual level, then implemented deeply in the Spring Boot anchor stack, then rapidly translated into Express, Django, Flask, and Laravel as deltas.

Every backend system has to put data somewhere and get it back later — and "somewhere" is never just one place. A modern service talks to PostgreSQL for transactional state, Redis for low-latency caches, MongoDB for semi-structured documents, and a primary/replica topology that fans those engines out across machines. The single mental model this section teaches is that **databases are specialized file systems layered on the kernel primitives from section 02, accessed over the network from section 03, driven by the runtime from section 04, and wrapped by the ORM in the framework from section 05.** Once you see that, every "magic" feature — indexes, transactions, replication, sharding — becomes an optimization on top of `open() / read() / write() / fsync()` and the on-disk page.

The eleven sub-sections move from the bottom of the stack upward: hardware and on-disk structures (06.01), the two dominant relational engines PostgreSQL (06.02) and MySQL InnoDB (06.03), the ACID contract and its real-world anomalies (06.04), the indexing and query planning that make large tables usable (06.05), the connection pooling that bridges the runtime to the database (06.06), the ORM patterns that bridge the application to the database (06.07), the zero-downtime migration discipline that lets you change the schema without taking an outage (06.08), the NoSQL document-store model in MongoDB (06.09), the in-memory model in Redis (06.10), and finally the distributed-systems patterns of replication, sharding, and CAP-driven consistency trade-offs (06.11).

## Section Map

### 06.01. Storage Engine Mechanics and On-Disk Structures

- [[06.01.01. Disk Access Mechanics and Page-Based Storage]] — Hardware characteristics: HDD mechanical seek latency vs. SSD/NVMe flash block write/erase cycles, the kernel page cache, `O_DIRECT`, and why the 8 KB PostgreSQL page and 16 KB InnoDB page dominate the IOPS budget.
- [[06.01.02. Write-Ahead Logging (WAL) and Crash Recovery]] — The fundamental persistence invariant (write the WAL before the data page), `fsync` cost, the ARIES algorithm (Analysis → Redo → Undo), LSNs, and fuzzy checkpointing.
- [[06.01.03. B-Tree and B+ Tree Index Internals]] — Self-balancing M-way search trees, B+tree's leaf-only data and doubly-linked leaves for range scans, page splits/merges, and the fan-out math that makes a 3-level tree cover 8M rows.
- [[06.01.04. Log-Structured Merge-Trees (LSM-Trees)]] — Memtable + SSTable + commit log, size-tiered vs leveled compaction, Bloom filters, tombstones, and why Cassandra/RocksDB chose write amplification over read amplification.

### 06.02. Relational Database Mechanics and PostgreSQL Internals

- [[06.02.01. PostgreSQL Architecture and Process Model]] — Process-per-connection (`fork()` from the postmaster), shared memory (`shared_buffers`, WAL buffer, CLOG), and the utility processes (checkpointer, bgwriter, WAL writer, autovacuum launcher, stats collector).
- [[06.02.02. PostgreSQL Multi-Version Concurrency Control (MVCC)]] — Heap tuples with `xmin`/`xmax`/`t_ctid`/`infomask`, snapshot isolation, append-only UPDATE, dead tuples, `VACUUM`, and the `txid` wraparound cliff.

### 06.03. MySQL InnoDB Engine Internals and Locking

- [[06.03.01. MySQL Architecture and the InnoDB Engine]] — Single-process, thread-per-connection model, pluggable storage-engine API, the buffer pool, the doublewrite buffer, the redo log, and the undo log.
- [[06.03.02. InnoDB MVCC and Rollback Segments]] — In-place page mutation with undo logging, hidden `DB_TRX_ID`/`DB_ROLL_PTR`/`DB_ROW_ID` fields, read views, and the purge threads that reclaim undo pages.
- [[06.03.03. Granular Locking Mechanics in InnoDB]] — Shared/Exclusive/Intention locks, record/gap/next-key locks, `SELECT ... FOR UPDATE`, the `INSERT INTO ... SELECT` deadlock pattern, and `innodb_lock_wait_timeout`.

### 06.04. ACID Transactions and Isolation Anomaly Analysis

- [[06.04.01. The ACID Mathematical Guarantees]] — Atomicity via undo + WAL, Consistency via constraints and triggers, Isolation via the four ANSI levels, and Durability via `fsync`, battery-backed RAID, and replication.
- [[06.04.02. Concurrency Anomalies and Phenomena Deep Dive]] — Dirty read, non-repeatable read, phantom read, lost update, write skew, and read skew, each with a concrete SQL timeline and the isolation level that prevents it.
- [[06.04.03. ANSI SQL vs. Real-World Isolation Levels]] — Why PostgreSQL's `REPEATABLE READ` is really Snapshot Isolation, why MySQL InnoDB's `REPEATABLE READ` uses next-key locks, and why Oracle only exposes `READ COMMITTED` and `SERIALIZABLE`.

### 06.05. Indexing Theory and Query Plan Optimization

- [[06.05.01. Index Types and Physical Layouts]] — Clustered (InnoDB primary key) vs heap (PostgreSQL), the leftmost prefix rule, covering indexes, hash, GIN, GiST, BRIN, and the adaptive hash index.
- [[06.05.02. Query Parsing Planning and Execution Stages]] — Parser → rewriter → planner → executor, the cost-based optimizer, the statistics in `pg_class`/`pg_statistic`, and join order selection.
- [[06.05.03. Deconstructing Query Execution Plans]] — Reading `EXPLAIN (ANALYZE, BUFFERS)` output, the cost/rows/width columns, seq scan vs index scan vs bitmap scan, nested loop vs hash join vs merge join, and the telltale signs of stale statistics.

### 06.06. Database Connection Pooling and Socket Management

- [[06.06.01. The Cost of Database Connections]] — PostgreSQL forks a ~10 MB backend process per connection, MySQL spawns a ~1 MB thread, the `max_connections` ceiling, and why serverless functions can't each hold their own connection.
- [[06.06.02. Application-Level Connection Pools]] — HikariCP (Spring Boot default), the `maximumPoolSize`/`minimumIdle`/`connectionTimeout`/`idleTimeout`/`maxLifetime` knobs, the `(core_count * 2) + effective_spindle_count` formula, and Django's `CONN_MAX_AGE` (not a real pool).
- [[06.06.03. Server-Side Connection Proxies PgBouncer]] — Session vs transaction vs statement pooling, the `max_client_conn`/`pool_size` knobs, the prepared-statement problem in transaction mode, and why serverless needs PgBouncer.

### 06.07. Unified ORM Architecture and Mapping Patterns

- [[06.07.01. The Object-Relational Impedance Mismatch]] — Object graph vs relational table, the inheritance problem (single/class/concrete table), the identity problem (object address vs primary key), and the navigation problem (pointers vs joins).
- [[06.07.02. The Active Record Pattern]] — The entity IS the table, `save()`/`update()`/`delete()` on the entity, Laravel Eloquent and Django ORM as canonical examples, and the tight coupling that makes them hard to test in isolation.
- [[06.07.03. The Data Mapper Pattern]] — The entity is a plain POJO, the repository handles persistence, JPA/Hibernate/SQLAlchemy/Prisma as canonical examples, and the boilerplate cost of separation.
- [[06.07.04. The Identity Map and Unit of Work Patterns]] — Don't load the same row twice into different objects; track dirty entities and flush them all at commit; Hibernate's `PersistenceContext` and Django's implicit `UnitOfWork`.
- [[06.07.05. The N+1 Query Problem and Loading Strategies]] — 1 + N queries from lazy loading in a loop; `select_related` (JOIN), `prefetch_related` (batch IN), `@EntityGraph`, `with()`, `include`; the query-log diagnosis.

### 06.08. Schema Migrations and Zero-Downtime DDL

- [[06.08.01. Schema Version Control Mechanics]] — Migration files (timestamped or versioned), `up`/`down` methods, the `schema_migrations`/`flyway_schema_history`/`__diesel_schema_migrations__` tracking tables, and the forward-only vs reversible debate.
- [[06.08.02. Zero-Downtime Migration Patterns]] — Expand-and-contract, dangerous DDL (NOT NULL with default, type changes, blocking index creation), `CREATE INDEX CONCURRENTLY`, MySQL `ALGORITHM=INPLACE`, and `gh-ost`/`pt-online-schema-change` for large tables.

### 06.09. NoSQL Document Stores and MongoDB Internals

- [[06.09.01. Document Model vs. Relational Schema]] — The schemaless myth (schemas exist, they're enforced by the app), the schema-evolution advantage, the JOIN penalty, and the denormalization tradeoff.
- [[06.09.02. MongoDB WiredTiger Storage Engine]] — B-tree (default) vs LSM option, document-level locking, Snappy compression, the `--wiredTigerCacheSizeGB` knob, checkpoints, and journaling.
- [[06.09.03. MongoDB Read and Write Guarantees]] — Write concerns (`w:1`, `w:"majority"`, `j:true`), read concerns (`local`, `majority`, `linearizable`), read preferences, and the causal-consistency model.
- [[06.09.04. The Aggregation Pipeline Framework]] — `$match`/`$project`/`$group`/`$unwind`/`$lookup`/`$sort`/`$limit` stages, the 100 MB per-stage memory limit and `allowDiskUse`, multikey indexes, and `$facet`.

### 06.10. In-Memory Stores and Redis Architecture

- [[06.10.01. Redis Architecture and Single-Threaded Processing]] — The single-threaded event loop on `epoll`, per-command atomicity, why single-threaded is fast (no locks, no context switch), and Redis 6 io-threads for network I/O only.
- [[06.10.02. Core Data Structures and Algorithmic Complexities]] — String (SDS, 512 MB max), List (quicklist of ziplists), Hash (listpack + hashtable), Set (intset + hashtable), Sorted Set (listpack + skiplist + hashtable), Stream (radix tree), and the per-command complexity table.
- [[06.10.03. Durability and Persistence Mechanics in Redis]] — RDB (snapshot via `bgsave` fork), AOF (append-only log with `always`/`everysec`/`no` fsync policies), AOF rewrite (`BGREWRITEAOF`), and the hybrid RDB+AOF format.
- [[06.10.04. Caching Patterns and Failure Modes]] — Cache-aside, read-through, write-through, write-behind; cache stampede, thundering herd, dog-pile, probabilistic early expiration (XFetch), cache penetration, cache avalanche, and the "two hard problems" of cache invalidation.

### 06.11. Database Scaling Replication and Sharding

- [[06.11.01. Primary-Replica Replication Mechanics]] — Physical (PostgreSQL WAL streaming, byte-level) vs logical (PostgreSQL logical decoding, MySQL binlog row events) replication, statement-based vs row-based, sync vs async, replication lag, and read-your-writes consistency.
- [[06.11.02. Horizontal Partitioning and Sharding Architecture]] — Range-based, hash-based, directory-based sharding; consistent hashing; the resharding problem; the Vitess pattern (MySQL) and the Citus pattern (PostgreSQL); why sharding is the last resort.
- [[06.11.03. Distributed Consistency and the CAP Theorem]] — Pick two of C/A/P (you always get P, so really it's C vs A under partition); PACELC extension (else: latency vs consistency); CP systems (HBase, MongoDB with majority) vs AP systems (Cassandra, DynamoDB) vs configurable systems.

## How to Read This Section

1. **Read the concept notes first.** They establish the mental model. Start with 06.01 — every later note assumes you understand pages, WAL, B-trees, and LSM-trees. Then read the engine internals (06.02 and 06.03) before the ACID and isolation notes (06.04), because every anomaly example references concrete PostgreSQL or InnoDB behaviour.
2. **Implement the anchor.** The Spring Boot anchor note is where you build the real, load-tested implementation. For section 06 this means HikariCP tuning, JPA mapping with `@EntityGraph`, Flyway migrations, and `@Transactional` isolation-level experiments.
3. **Run the delta pass.** Open the other ecosystems and implement the same feature as a translation exercise. The Django and Prisma connection-pool defaults, the Eloquent and SQLAlchemy N+1 fixes, and the Laravel migration syntax are all deltas on the same conceptual core.
4. **Connect.** Follow the Related Notes links to reinforce the cross-ecosystem graph. Section 06 links back to section 02 (page cache, `fsync`), section 03 (TCP, TLS), section 04 (thread pools, event loops), and section 05 (ORM, DI, middleware).

> [!tip] Reading order
> If you are new to this section, follow the numeric ordering. If you are revising, jump directly to whichever concept you forgot — but always come back to 06.01 if the on-disk mechanics feel fuzzy, because every later section silently assumes them.
