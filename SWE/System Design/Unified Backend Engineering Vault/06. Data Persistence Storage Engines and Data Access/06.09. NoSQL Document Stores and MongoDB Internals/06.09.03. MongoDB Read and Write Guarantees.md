# 06.09.03. MongoDB Read and Write Guarantees

## What This Is

MongoDB's **read and write guarantees** — write concern, read concern, and read preference — are the three orthogonal knobs that determine *what* the database promises you about a returned result and *where* the database is allowed to read it from. They are MongoDB's equivalent of PostgreSQL's `synchronous_commit` setting plus its `default_transaction_isolation` levels plus its `READ ONLY` routing to standby servers, but expressed as per-operation parameters on every `insertOne`/`find`/`aggregate` call rather than as session or server defaults. Get them wrong and you get one of three production incidents: silent data loss after a primary failover (write concern too weak), stale reads that show users yesterday's data (read preference routing to a lagging secondary), or "phantom" reads where a user creates a record, refreshes, and sees it vanish (read concern that returns uncommitted data that later rolls back). Get them right and the database will tell you, synchronously and on every operation, exactly how durable your write is and how consistent your read is.

This note sits between [[06.09.02. MongoDB WiredTiger Storage Engine]] (which defines what the journal actually is and what `fsync` costs) and [[06.09.04. The Aggregation Pipeline Framework]] (which inherits these concerns as defaults on every pipeline). The three concerns are not independent — `w: "majority"` is meaningless without `j: true` on the secondaries (a secondary that has not flushed the journal cannot durably acknowledge a write), and `linearizable` read concern requires `w: "majority"` write concern on the writes that produced the data. The mental model is a 2×2 matrix: write concern answers *"how durable is my write?"*, read concern answers *"how consistent is my read?"*, and read preference answers *"which replica-set member serves my read?"*. The three together define the consistency contract your application actually has — which is almost always looser than the consistency contract your application *thinks* it has.

The crucial conceptual shift from relational databases is that in MongoDB these knobs are **per-operation, not per-session by default**. In PostgreSQL, you set `SET SESSION CHARACTERISTICS AS TRANSACTION ISOLATION LEVEL SERIALIZABLE` once and every statement in the session inherits it; in MongoDB, every `db.collection.insertOne(..., { writeConcern: { w: "majority", j: true } })` carries its own concern unless you override the collection-level default (`db.createCollection("c", { writeConcern: { w: "majority" } })`) or the database/server-level default. This per-operation flexibility is powerful but it is also a footgun — a single migration script that uses `w: 1` (the historical default before MongoDB 5.0) instead of `w: "majority"` can lose data during a failover that occurs between the write's acknowledgement and the next oplog replication. The MongoDB 5.0 default is now `w: "majority"` for all writes, which is safer but slower — the latency cost of a `majority` ack vs a `w: 1` ack is one extra round trip to the secondary plus the journal fsync on the secondary.

## The Details

### Write Concerns: `w: 1` (Primary memory acknowledgment), `w: "majority"` (Replication across replica set quorum), `j: true` (On-disk journal sync).

A write concern is the set of acknowledgements the primary must collect before it tells the client "your write succeeded". It has three independent components: **`w`** (how many replica-set members must acknowledge the write), **`j`** (whether those acknowledgements must be backed by an on-disk journal flush), and **`wtimeout`** (how long the client is willing to wait for the ack before returning a timeout error). The combination of these three determines the durability contract — and the latency cost — of every write.

The `w` value forms a strict hierarchy of durability. **`w: 0`** is *fire-and-forget*: the primary does not even wait for its own memory acknowledgment, the client gets a success response as soon as the network packet is sent. This is the fastest possible write and the most dangerous — a primary crash between receiving the write and applying it silently drops the write, and the client never knows. **`w: 1`** (the historical default through MongoDB 4.x) acknowledges after the primary has applied the write to its in-memory representation and written it to the oplog — but *not* necessarily after the journal has been flushed. If the primary crashes within the 100 ms journaling window (`storage.journal.commitIntervalMs`, see [[06.09.02. MongoDB WiredTiger Storage Engine]]), the write is lost despite the client having received an ack. **`w: "majority"`** acknowledges after a majority of replica-set members have applied the write to their oplogs and journaled it — this is the only level that survives the loss of any single member in a 3-node replica set, and it is the MongoDB 5.0+ default. The latency cost is one extra round trip to the secondary plus the secondary's journal fsync:

```javascript
// The five write concerns side by side, with their latency/durability tradeoffs
db.orders.insertOne({ ... }, { writeConcern: { w: 0 } });                 // ~0.1 ms — fire-and-forget
db.orders.insertOne({ ... }, { writeConcern: { w: 1 } });                 // ~1 ms — primary memory ack (loses on crash within 100ms)
db.orders.insertOne({ ... }, { writeConcern: { w: 1, j: true } });        // ~5 ms — primary fsync ack (survives crash)
db.orders.insertOne({ ... }, { writeConcern: { w: "majority" } });        // ~10 ms — majority oplog ack (survives primary loss)
db.orders.insertOne({ ... }, { writeConcern: { w: "majority", j: true, wtimeout: 5000 } });
// ~15 ms — majority + journal ack, fail loudly if a secondary is slow (wtimeout)
```

The `j: true` flag is the most misunderstood part of the model. Without it, `w: 1` acknowledges a write that exists *only in the primary's memory and the oplog's in-memory buffer* — a crash within `commitIntervalMs` (default 100 ms) loses the write. With it, the primary must `fsync` its journal before acknowledging, which guarantees the write survives a crash but adds the cost of one synchronous disk write (~50–200 µs on NVMe, ~5–10 ms on HDD). The same logic applies to secondaries acknowledging `w: "majority"`: without `j: true` on the secondaries, the majority ack only means "a majority of members have the write in memory", which does not survive a simultaneous crash of those members; with `j: true`, the secondaries must also fsync their journals before acknowledging. The replica-set-level setting `settings.getLastErrorDefaults` (set via `rs.reconfig`) controls the default write concern for the entire replica set — the recommended production setting is `{ w: "majority", j: true, wtimeout: 5000 }`.

`wtimeout` is the timeout for `w > 1` only — it does not apply to `w: 0` or `w: 1` (those ack immediately from the primary). If the primary cannot collect a majority ack within `wtimeout` milliseconds, it returns a `WriteConcernError` with code 64 (`WriteConcernFailed`) to the client, *but the write itself has already been applied on the primary* — the client sees an error for a write that did, in fact, succeed. This is a critical and frequently misdiagnosed failure mode: the application retries the write, producing a duplicate (mitigated only by an idempotent operation or a unique index). The correct response to a `wtimeout` is *not* to retry blindly; it is to query the database to check whether the write actually happened (`db.orders.findOne({_id: ...})`) before deciding to retry. The table below summarises the tradeoffs:

| Write concern | Latency (NVMe, same-DC) | Survives primary crash? | Survives primary + secondary crash? | When to use |
|---|---|---|---|---|
| `w: 0` | ~0.1 ms | No | No | Bulk ingest where you can tolerate loss; never for user data |
| `w: 1` | ~1 ms | No (loses within 100 ms journal window) | No | Pre-5.0 default; acceptable for logs/metrics that are replicated eventually |
| `w: 1, j: true` | ~5 ms | Yes | No | Single-node deployments; writes you need durable but cannot afford replication latency |
| `w: "majority"` | ~10 ms | Yes | No (need majority of N) | MongoDB 5.0+ default; the floor for user-facing writes |
| `w: "majority", j: true` | ~15 ms | Yes | Yes (if 3-node, survives 1 node loss) | Financial transactions, audit logs, anything you cannot lose |
| `w: 3, j: true` | ~20 ms | Yes | Yes (survives 1 node loss in 3-node) | Overkill for 3-node; useful in 5-node to require 3 acks |

The production failure mode is always one of two shapes. The **first** is "data loss after failover": a system running with the pre-5.0 default `w: 1` (no `j`) experiences a primary crash, the replica set elects a secondary, and the secondary is missing the last ~100 ms of writes that the primary acknowledged but never journaled. The on-call engineer sees a sudden drop in row count or a missing order, and the diagnosis is to grep the application logs for the timestamps and compare to the `mongod` log's failover timestamp. The fix is `w: "majority", j: true` on every user-data write. The **second** is "wtimeout retry storms": a system running with `w: "majority", wtimeout: 50` (too tight) under secondary replica lag hits wtimeout constantly, the application retries every timed-out write, the database is hit with duplicate writes that pile up because the originals are still in flight, and the system enters a feedback loop. The metric that reveals this is the `mongod` log's "wtimeout" entries combined with the application's retry counter; the fix is to raise `wtimeout` to comfortably exceed expected replication lag (5,000 ms is a safe default) and to make write operations idempotent so retries are safe.

### Read Concerns: `local`, `available`, `majority`, `linearizable`

A read concern is the *consistency* contract for a read: it tells MongoDB which versions of the data the read is allowed to see. It is orthogonal to read preference (which member to read from) and orthogonal to write concern (how durable the writes that produced the data are). The four read concerns form a hierarchy from most-permissive to most-strict, and the cost rises with strictness because the stricter concerns require coordination with the replica set.

**`local`** (the default) reads the node's most recent locally-applied data, including data that has *not* yet been replicated to a majority and may be rolled back if the node is a primary that loses an election. This is the fastest read concern because it requires no inter-node coordination, but it can return data that "disappears" after a failover — a primary that acknowledged a write with `w: 1` then crashed will have that write visible to `local` reads, but if the new primary was elected from a secondary that did not yet have the write, the write is gone. **`available`** is identical to `local` on a replica set, but on a sharded cluster it will return data from shards that are mid-migration (orphan documents); it exists for backward compatibility and should not be used in new code. **`majority`** reads only data that has been acknowledged by a majority of the replica set — it is the read-side counterpart of `w: "majority"` writes and guarantees that the data read will survive any single-node failure. **`linearizable`** is the strongest: it reads only majority-committed data *and* performs a read on the primary *after* confirming (via a no-op write with `w: "majority"`) that the node is still the primary. This guarantees that the read sees all writes that have been acknowledged before the read began, at the cost of one extra round trip.

```javascript
// The four read concerns, with their consistency vs latency tradeoffs
db.orders.findOne({ _id: orderId }, {}, { readConcern: { level: "local" } });
// ~1 ms — sees uncommitted-to-majority data (may roll back)

db.orders.findOne({ _id: orderId }, {}, { readConcern: { level: "available" } });
// ~1 ms — same as local on replica set; different on sharded cluster

db.orders.findOne({ _id: orderId }, {}, { readConcern: { level: "majority" } });
// ~2 ms — sees only majority-acknowledged data (survives any single node loss)

db.orders.findOne({ _id: orderId }, {}, { readConcern: { level: "linearizable" } });
// ~15 ms — majority + "am I still primary?" round-trip (strongest, slowest)
```

The most important subtlety is that **`majority` and `linearizable` only make sense on the primary** for the strictest reads — `majority` on a secondary returns data that was majority-committed at the time the secondary applied it, which may lag behind the primary by the replication lag (typically < 1 s in a healthy cluster but can be minutes under load). `linearizable` on a secondary is rejected with an error because only the primary can perform the no-op `w: "majority"` confirmation. This means linearizable reads force all reads to the primary, which sacrifices read scalability — you cannot use secondaries for linearizable reads.

The **causal consistency** model (added in MongoDB 3.6) builds on top of `majority` read concern and `majority` write concern to provide a stronger guarantee: if a client performs a write then a read using a *causally-consistent session*, the read is guaranteed to see the write. The mechanism is that the session carries an `operationTime` token from the write to the read; the read blocks until the member it is routed to has applied at least up to that `operationTime`. This is the closest MongoDB gets to the read-your-writes consistency that relational databases with synchronous replication provide by default. The cost is that the read may block waiting for the member to catch up — the `maxStalenessSeconds` parameter caps this wait:

```javascript
// Causal consistency — read-your-writes across a session
const session = db.getMongo().startSession({ causalConsistency: true });
const dbSession = session.getDatabase("shop");
// Write on the primary
dbSession.orders.insertOne({ _id: 1, status: "paid" }, { writeConcern: { w: "majority" } });
// Read on a secondary — guaranteed to see the write
dbSession.orders.findOne({ _id: 1 }, {}, {
  readConcern: { level: "majority" },
  readPreference: "secondary"
});
// Internally: the read blocks until the secondary has applied up to the write's operationTime.
session.endSession();
```

The production failure mode is the **"phantom read"** pattern: an application uses `local` read concern (the default) and routes reads to secondaries via `readPreference: "secondary"`. A user creates an order (`w: "majority"` write to the primary), the primary acknowledges, the user's next request is routed to a secondary that has not yet applied the write, the user sees "no such order", panics, and re-submits — creating a duplicate. The metric that reveals this is the gap between the application's "create" success rate and the "fetch after create" success rate; the fix is either (a) `readConcern: { level: "majority" }` on the read (adds ~1 ms), (b) `readPreference: "primary"` for the read-your-writes window after a write (loses read scalability), or (c) causal-consistent sessions (the proper fix, but requires the driver to support sessions — all official drivers do since 3.6). See [[06.09.02. MongoDB WiredTiger Storage Engine]] for how the MVCC snapshot retention enables `majority` reads without blocking writers.

### Read Preferences: `primary`, `primaryPreferred`, `secondary`, `secondaryPreferred`, `nearest`.

A read preference is the *routing* decision: which replica-set member is allowed to serve this read. It is the only one of the three concerns that affects *where* the read goes, not *what* it returns — the consistency of the returned data is governed by the read concern, regardless of which member served the read. The five read preferences form a strict preference order from "always primary" to "always nearest":

**`primary`** (the default) routes all reads to the current primary. This is the safest because the primary always has the most recent data and can serve any read concern including `linearizable`. It is also the least scalable — every read adds load to the primary, and the primary becomes the throughput ceiling. **`primaryPreferred`** reads from the primary when available, but falls back to a secondary during a failover (when there is no primary). This is the right choice for read-your-writes scenarios where you want reads to mostly hit the primary but want the application to remain available (with stale data) during a failover window. **`secondary`** *always* reads from a secondary — if no secondary is available, the read fails. This is the most aggressive read-scaling choice and the most dangerous: a secondary may lag arbitrarily behind the primary (replication lag is bounded only by the network and the secondary's apply rate, not by any hard deadline), so reads may return data that is minutes or hours stale. **`secondaryPreferred`** reads from a secondary if one is available, falling back to the primary if no secondary is reachable — this is the standard "scale-out reads" choice that lets the primary handle writes while secondaries absorb read load, with the primary as a safety net. **`nearest`** reads from the member with the lowest network latency, regardless of whether it is the primary or a secondary — useful in geographically distributed clusters where you want reads to be served from whichever datacenter is closest to the application.

```javascript
// The five read preferences, side by side
db.orders.find({}).readPref("primary");
// Always primary — safest, not horizontally scalable

db.orders.find({}).readPref("primaryPreferred");
// Primary normally, secondary during failover (stale reads possible)

db.orders.find({}).readPref("secondary");
// Always secondary — maximally scalable, always stale by replication lag

db.orders.find({}).readPref("secondaryPreferred");
// Secondary normally, primary as fallback — the standard scale-out choice

db.orders.find({}).readPref("nearest");
// Lowest-latency member (primary or secondary) — geo-distributed reads

// Combine with maxStalenessSeconds to bound the staleness
db.orders.find({}).readPref("secondaryPreferred", [], {
  maxStalenessSeconds: 90    // refuse to read from a secondary lagging > 90 s
});

// Combine with tag-based routing — read from secondaries in the "reporting" datacenter
db.orders.find({}).readPref("secondary", [{ dc: "use1-reporting" }]);
```

The **`maxStalenessSeconds`** parameter (added in MongoDB 3.4) is the single most important safety net for secondary reads. Without it, a secondary that is hours behind will happily serve reads — the client has no way to detect the staleness. With `maxStalenessSeconds: 90`, the driver estimates the secondary's lag (based on the primary's last `opTime` it has seen and the secondary's reported `opTime` via the `hello` command) and refuses to route the read to any secondary whose estimated lag exceeds the threshold; if all secondaries are too stale, it falls back to the primary (for `secondaryPreferred`) or returns a `NoSecondaryAvailable` error (for `secondary`). The minimum value is 90 seconds — MongoDB cannot reliably estimate lag below this threshold because the `hello` command only updates every 10 s. The maximum is the `heartbeatFrequencyMS` (default 10 s) minus 90 s, which works out to a hard floor of 90 s.

The **tag-based routing** mechanism lets you attach arbitrary key/value tags to replica-set members (`rs.conf().members[n].tags = { dc: "us-east-1a", role: "analytics", ssd: "true" }`) and route reads to members matching a tag set. This is how you keep analytics workloads off the primary-serving path: tag the analytics-optimised secondaries with `{ role: "analytics" }` and have your BI tool use `readPref("secondary", [{ role: "analytics" }])` so its heavy aggregation queries never land on the OLTP-serving primary or its hot replicas. Tags are evaluated in array order — `[{ role: "analytics" }, {}]` means "try the analytics tag first, fall back to any secondary if no analytics-tagged member is reachable".

The production failure mode is the **"replica lag avalanche"** pattern. An application uses `readPreference: "secondary"` to scale reads across 5 secondaries. The primary is hit by a write spike (e.g. a viral product launch), the oplog grows rapidly, and the secondaries start lagging behind because their apply rate (single-threaded oplog application per collection) cannot keep up with the primary's write rate. Replication lag climbs from 1 s to 30 s to 5 minutes. Users see stale data on every read — they place orders for items that are already sold out, they see "delivered" packages that haven't shipped, they complain. The application's retry logic kicks in, increasing load on the primary, which slows the primary's apply rate, which increases replica lag further. The metric that reveals this is `db.serverStatus().metrics.replication.executor` on the secondary combined with `rs.printSecondaryReplicationInfo()` from the primary:

```bash
mongosh --eval 'rs.printSecondaryReplicationInfo()'
# source: db1.example.com:27017
#         syncedTo: Thu Mar 15 2024 10:30:00 GMT+0000 (UTC)
#         0 secs (0 hrs) behind the primary
# source: db2.example.com:27017
#         syncedTo: Thu Mar 15 2024 10:25:00 GMT+0000 (UTC)
#         300 secs (0.08 hrs) behind the primary     ← 5 minutes lag!
```

The fix is three-fold: (1) use `readPreference: "secondaryPreferred"` with `maxStalenessSeconds: 90` so the application falls back to the primary when secondaries lag, (2) monitor `rs.printSecondaryReplicationInfo()` and alert when any secondary lags > 60 s, and (3) identify the write-heavy collection causing the apply bottleneck and consider sharding it (see [[06.09.01. Document Model vs. Relational Schema]] for the embedding-vs-referencing decisions that determine write amplification). The general principle is: secondary reads are a *throughput* optimisation, not a *consistency* one — never route user-facing "read your write" flows to secondaries without `majority` read concern and causal consistency, and never trust a secondary read without `maxStalenessSeconds` to bound the worst case.

## Cross-Ecosystem Implementation

The MongoDB driver exposes these concerns through the `writeConcern` and `readConcern`/`readPreference` options on every operation. The four target ecosystems express them as follows:

| Aspect | Spring Data MongoDB (anchor) | Node.js driver | PyMongo | Laravel MongoDB |
|---|---|---|---|---|
| Default write concern | `WriteConcern.MAJORITY` (5.0+) | `majority` (5.0+) | `majority` (5.0+) | `majority` (5.0+) |
| Per-op write concern | `mongoTemplate.setWriteConcern(...)` or `@WriteConcern` annotation | `{ writeConcern: { w: "majority", j: true } }` passed to `insertOne` | `wc = WriteConcern("majority", j=True); coll.insert_one(d, write_concern=wc)` | `DB::connection('mongodb')->collection('c')->where(...)->update([...], ['w' => 'majority'])` |
| Per-op read concern | `mongoTemplate.setReadConcern(ReadConcern.MAJORITY)` | `{ readConcern: { level: "majority" } }` passed to `find` | `rc = ReadConcern("majority"); coll.find({}, read_concern=rc)` | via raw `MongoDB\BSON` query options |
| Per-op read preference | `mongoTemplate.setReadPreference(ReadPreference.secondaryPreferred())` | `.withReadPreference('secondaryPreferred')` | `rp = ReadPreference("secondaryPreferred"); coll.find({}, read_preference=rp)` | `DB::connection('mongodb')->readPreference('secondary')` |
| Causal-consistent session | `clientSession = mongoClient.startSession(causalConsistency=true)` | `session = client.startSession({ causalConsistency: true })` | `with client.start_session(causal_consistency=True) as s:` | not directly exposed — use raw driver |
| Transaction with concerns | `session.startTransaction(readConcern=MAJORITY, writeConcern=MAJORITY_J)` | `session.startTransaction({ readConcern: { level: "majority" }, writeConcern: { w: "majority", j: true } })` | `s.with_transaction(callback, read_concern=rc, write_concern=wc)` | not directly exposed |

When you read the Spring Data MongoDB anchor implementation note, the patterns above map almost 1:1. The delta notes then show how the Node.js driver's chainable `.withReadPreference()` API, PyMongo's per-call parameter style, and Laravel's connection-level configuration express the same concerns. The key invariant that does not change across ecosystems is that **causal consistency requires `majority` read concern and `majority` write concern** — drop either one and the read-your-writes guarantee is lost.

## Hands-On Exercise

```bash
# 1. Inspect the replica set's current default write concern
mongosh --eval 'printjson(rs.conf().settings.getLastErrorDefaults)'

# 2. Set the replica-set default to majority + journal (the production recommendation)
mongosh --eval 'const cfg = rs.conf();
  cfg.settings.getLastErrorDefaults = { w: "majority", j: true, wtimeout: 5000 };
  rs.reconfig(cfg);'

# 3. Measure the latency cost of each write concern
mongosh shop --eval '
  const N = 1000;
  for (const wc of [{w:0}, {w:1}, {w:1,j:true}, {w:"majority"}, {w:"majority",j:true}]) {
    const t0 = Date.now();
    for (let i = 0; i < N; i++) {
      try { db.bench.insertOne({ n: i }, { writeConcern: wc }); }
      catch (e) {} // w:0 may return before apply, others should succeed
    }
    print(JSON.stringify(wc) + ": " + ((Date.now() - t0) / N).toFixed(2) + " ms/op");
  }'

# 4. Inspect replication lag from the primary
mongosh --eval 'rs.printSecondaryReplicationInfo()'

# 5. Reproduce the phantom-read failure mode
# Terminal 1: write with majority, then immediately read with local + secondaryPreferred
mongosh shop --eval '
  const sess = db.getMongo().startSession({ causalConsistency: false });
  const db2 = sess.getDatabase("shop");
  db2.orders.insertOne({_id: ObjectId(), status: "paid"}, {writeConcern:{w:"majority"}});
  // This read may NOT see the write if routed to a lagging secondary:
  printjson(db2.orders.find({status:"paid"}).readPref("secondaryPreferred").toArray().length);
  sess.endSession();'

# 6. Reproduce the wtimeout retry-storm failure mode
mongosh shop --eval '
  // Force a wtimeout by setting wtimeout too tight (1 ms) and w:"majority"
  try {
    db.orders.insertOne({ n: 1 }, { writeConcern: { w: "majority", wtimeout: 1 } });
  } catch (e) {
    print("error code: " + e.code + " — " + e.codeName);
    // → 64 (WriteConcernFailed) — but the write likely DID succeed on the primary
    print("check if write actually happened: " + db.orders.findOne({n:1}));
  }'

# 7. Use a causal-consistent session to fix the phantom read
mongosh shop --eval '
  const sess = db.getMongo().startSession({ causalConsistency: true });
  const db2 = sess.getDatabase("shop");
  db2.orders.insertOne({_id: ObjectId(), status: "paid"}, {writeConcern:{w:"majority"}});
  printjson(db2.orders.find({status:"paid"}).readPref("secondary").toArray().length);
  // → guaranteed to be ≥ 1 — the read blocks until the secondary catches up
  sess.endSession();'
```
