# 06.09.01. Document Model vs. Relational Schema

## What This Is

The choice between the **document model** and the **relational schema** is the first and most consequential data-modeling decision in any backend system. MongoDB popularized the document model: a single record (a *document*) is a self-contained tree of nested key/value pairs serialized in BSON, the binary superset of JSON that adds types like `ObjectId`, `Date`, `BinData`, `Decimal128`, and `Long`. A relational schema, by contrast, decomposes that same logical entity across multiple flat tables linked by foreign keys and reassembled at query time via `JOIN`. Neither model is strictly better — the document model trades *storage and query flexibility* for *cross-entity join efficiency*, while the relational model trades *normalization and ad-hoc query power* for *write-path simplicity and per-field integrity constraints*.

This note sits at the very top of the persistence layer (section 06) because every downstream concern — storage engine internals (06.09.02), replica-set read/write guarantees (06.09.03), the aggregation pipeline (06.09.04), and even how you wire ORMs in the framework layer (section 05) — is a downstream consequence of which data model you pick. A relational schema forces `JOIN` costs into the query planner and forces foreign-key enforcement into the storage engine; a document schema pushes the same concerns up into the application layer (where you write embedding/referencing decisions) and into the aggregation framework (where `$lookup` re-implements the join at query time). Understanding this note is what lets you predict *which* queries will be cheap and *which* will cause incidents before you write a line of application code.

The dominant myth to dispel up front is that MongoDB is *schemaless*. It is not. Every collection has a schema — it is just *implicit* and *enforced by the application* rather than *declared* and *enforced by the database*. Since MongoDB 3.2 you can attach a `jsonSchema` validator to a collection (`db.createCollection("users", { validator: { $jsonSchema: {...} } })`) and since 3.6 you get partial JSON Schema support; since 5.0 you get *collection-wide schema validation* with `validatorLevel: "strict"` and `validatorAction: "error"`. The default is still `validationLevel: "off"`, which is why the myth persists. The production failure mode is always the same: a developer ships a new field name with a typo, two microservices write different shapes to the same collection, and three weeks later an aggregation pipeline crashes at 3 a.m. with a `BSON field 'X.Y' is the wrong type 'string', expected type 'int32'` error.

## The Details

### Flexible Schemas: Storing complex, hierarchical, nested data structures in BSON (Binary...

A MongoDB document is a BSON object — a binary encoding of a JSON-like tree where every value carries a 1-byte type tag and a length-prefixed payload. The wire format is documented at [bsonspec.org](http://bsonspec.org/): each document starts with a 4-byte little-endian int32 total length, then a sequence of `(type byte, name CString, value)` triples, terminated by a single `0x00` null byte. The type tag is what gives BSON its richer type system than JSON: `0x01` float64, `0x02` UTF-8 string, `0x03` embedded document, `0x04` array, `0x07` ObjectId, `0x09` int64 milliseconds-since-epoch `Date`, `0x10` int32, `0x12` int64, `0x05` `BinData` (with a sub-type byte for UUID, MD5, user-defined), and `0x13` `Decimal128` (34-digit decimal added in 3.4 for financial data). This type richness is the single biggest reason the BSON wire format exists at all — pure JSON would force you to encode a date as an ISO-8601 string and an `ObjectId` as a 24-character hex string, and the loss of typed comparison would cripple index efficiency.

A document in a `users` collection typically looks like the following — note that nesting can be arbitrarily deep, arrays can hold heterogeneous documents, and `null` is a first-class value:

```javascript
// mongo shell — a single document is one tree
db.users.insertOne({
  _id: ObjectId("65a1f2c3b8d8e9a4f1b2c3d4"),
  email: "alice@example.com",                       // string
  createdAt: ISODate("2024-01-15T10:30:00Z"),       // Date (int64 ms)
  profile: {                                         // embedded sub-document
    displayName: "Alice",
    age: 32,                                         // int32
    addresses: [                                     // array of sub-docs
      { kind: "home", city: "Berlin", zip: "10115" },
      { kind: "work", city: "Munich", zip: "80331" }
    ]
  },
  preferences: { theme: "dark", notifications: true },
  balance: NumberDecimal("1234.56")                 // Decimal128 — money NEVER as float
});
```

The "flexible schema" claim really means three concrete things, and only three. First, **a collection has no declared columns** — you can insert `{a:1}` and `{b:"two"}` into the same collection and neither document rejects the other. Second, **fields can be added without a migration** — a new microservice release can write `profile.avatarUrl` to documents that already exist; old documents simply lack the field, and queries that reference it return `null` for them (use `{ "profile.avatarUrl": { $exists: true } }` to discriminate). Third, **field types can drift across documents** — `profile.age` can be `int32` in one document and `string` in another, and MongoDB will not complain unless a validator is attached. This drift is the actual source of the "schemaless myth": it is not that schemas are absent, it is that they are *implicit*, defined *by the union of all writes the application has ever done*, and enforced only *by code review and contract tests* — not by the storage engine.

The schema-evolution advantage is real but asymmetric. *Additive* changes (new field, new sub-document, new array element) are essentially free — old readers ignore the new field, new readers tolerate its absence via `$exists` or null checks. *Subtractive* and *type-changing* changes are *not* free: removing a field requires a backfill (`db.users.updateMany({}, { $unset: "legacyField" })`) that scans the entire collection; changing a field's type requires a backfill that rewrites every value (`db.users.updateMany({}, [{ $set: { age: { $toInt: "$ageStr" } } }, { $unset: "ageStr" }])`). Relational schemas pay this cost up front via `ALTER TABLE ... ALTER COLUMN TYPE` (which on PostgreSQL rewrites the entire table and acquires an `ACCESS EXCLUSIVE` lock); document schemas pay it later via the backfill. The cost is the same; the *timing* is different — and that is the entire reason the document model is preferred for early-stage products where the schema is changing weekly.

The production failure mode is *schema drift across microservices*. Two services write to the same `events` collection; service A writes `{ts: ISODate, payload: { kind: "click", url: "..." }}`, service B writes `{ts: ISODate, payload: "click|https://..."}` (a string instead of a sub-document). Neither write is rejected. Three weeks later, an analyst writes `db.events.aggregate([{$group: {_id: "$payload.kind"}}])` and gets back one group `_id: null` containing every event from service B — because `$payload.kind` on a string is `undefined`, which aggregates to `null`. The metric that reveals this is the `mongo.documentValidation.failed` counter and the `validate()` command output: `db.events.validate({full: true})` reports a "mismatched type" warning per offending document. The fix is to attach a validator *before* the split happens, not after — `db.runCommand({collMod: "events", validator: {$jsonSchema: {properties: {payload: {bsonType: "object"}}}}})`, with `validationAction: "warn"` first to detect drift without breaking writes, then promoted to `"error"` once clean. See [[06.09.04. The Aggregation Pipeline Framework]] for how `$lookup` and `$facet` react when their input documents have inconsistent shapes.

### Data Modeling: Embedding (Denormalization - fast single-read retrieval) vs. Referencing...

The document-model analog of relational normalization is the **embedding-vs-referencing** decision, and it is the single most important schema-design choice in MongoDB. **Embedding** means storing the child data as a nested sub-document or array inside the parent document — a one-to-few relationship where the child has no independent query life. **Referencing** means storing only the child's `_id` (or a denormalized subset) on the parent and storing the child in its own collection, then using `$lookup` (or a second application-level query) to assemble them at read time. The decision rests on three concrete axes: (1) the **read pattern** — do you always load parent and child together? (2) the **write pattern** — does the child mutate independently of the parent? (3) the **size bound** — does embedding blow past the 16 MB BSON document limit?

Embedding trades one fast read for many slow updates. A blog post with embedded comments is a single `findOne({_id: postId})` that returns the entire post plus all comments in one B-tree lookup, one page read, and zero joins — this is the canonical "fast single-read retrieval" case the heading names. But every new comment appends to an array, which on WiredTiger rewrites the entire document (the document grows, gets a new position on disk, and the old position becomes garbage). A 5,000-comment post that gets a new comment every minute will rewrite ~10 MB of BSON on every comment, fragmenting the collection and burning IOPS. The rule of thumb is: **embed if the embedded set grows slowly and is bounded below ~100 elements; reference if it can grow unboundedly or if it is queried independently.**

```javascript
// EMBED — one read, atomic update of parent+child
db.orders.insertOne({
  _id: ObjectId("..."),
  orderNo: "ORD-2024-0001",
  customer: {                          // denormalized snapshot — see failure mode below
    _id: ObjectId("..."),
    name: "Alice",
    email: "alice@example.com"
  },
  items: [                             // embedded array — bounded, ≤ ~50 line items typical
    { sku: "SKU-1", qty: 2, unitPrice: NumberDecimal("9.99") },
    { sku: "SKU-2", qty: 1, unitPrice: NumberDecimal("49.00") }
  ],
  status: "paid",
  createdAt: ISODate("...")
});
// One round trip loads the entire order. No JOIN, no $lookup, no second query.

// REFERENCE — unbounded set lives in its own collection
db.posts.insertOne({ _id: ObjectId("..."), title: "...", body: "..." });
db.comments.insertOne({ _id: ObjectId("..."), postId: ObjectId("..."), author: "...", body: "..." });
// Read post + comments with $lookup (the MongoDB JOIN):
db.posts.aggregate([
  { $match: { _id: postId } },
  { $lookup: { from: "comments", localField: "_id", foreignField: "postId", as: "comments" } }
]);
```

The **JOIN penalty** in MongoDB is real and asymmetric. A relational `SELECT * FROM posts p JOIN comments c ON c.post_id = p.id` runs once inside the database engine, which can choose hash-join vs nested-loop vs merge-join based on table statistics, and which streams results back to the client over a single connection. The MongoDB `$lookup` equivalent is always a *nested-loop join* executed per-parent-document: for each input document, WiredTiger does an index seek (if `foreignField` is indexed) or a collection scan (if it is not) on the foreign collection. `$lookup` with an `pipeline` parameter (added in 3.6) lets you push a sub-pipeline into the join — useful for filtering or sorting the joined documents — but it does not change the algorithmic shape. For a `posts`/`comments` join of 100k posts × 20 comments each, `$lookup` is fine. For a 10M-row `users`/`events` join, `$lookup` will run for minutes; you should denormalize a foreign-key summary field onto the parent instead (`db.users.updateOne({_id: u}, {$set: {eventCount: N, lastEventAt: ISODate(...)}})`).

The denormalization tradeoff surfaces most painfully in the **stale snapshot** failure mode. When you embed `customer: {name, email}` into an order, you are storing a *snapshot* of the customer at order time. If the customer later changes their email, the embedded snapshot in every historical order is now wrong — which may be *desirable* (orders should reflect the email used at purchase time) or *disastrous* (a reporting dashboard that counts distinct emails will now over-count). Relational schemas avoid this by always joining to the live `customers` table; document schemas pay the cost of a backfill (`db.orders.updateMany({"customer._id": custId}, {$set: {"customer.email": newEmail}})`) or accept the staleness as a feature. The production incident looks like: support says "the customer changed their email but the invoice PDF still shows the old one" — and the fix is *not* to make the storage engine consistent, it is to decide explicitly whether the order's `customer.email` is a historical snapshot or a live reference, and to backfill the chosen semantics.

The 16 MB BSON document hard limit (`maxBsonObjectSize` in `db.serverStatus()`, returns 16793600 bytes) is the absolute boundary that forces referencing. A typical pattern that hits this is a "thread" collection with embedded messages — at ~500 bytes per message, 16 MB holds ~32k messages, which sounds generous until you realize a popular thread can accumulate 100k+ messages and the document will fail to insert with `BSONObjTooLarge` (error code 17419). The fix is to switch the messages to a referenced collection *before* you hit the limit, not after — refactoring a 16 MB live document into two collections requires a downtime migration. The decision matrix below summarizes when each pattern wins:

| Relationship shape | Read pattern | Write pattern | Recommended model | Why |
|---|---|---|---|---|
| 1-to-few (≤~100), parent+child always read together | parent+child | child rarely mutates | **Embed** | One B-tree lookup, zero joins, atomic update of parent+child |
| 1-to-many (unbounded), child queried independently | parent-only or child-only | both mutate independently | **Reference** | Avoids 16 MB limit, allows independent indexing of child |
| Many-to-many | join in either direction | both sides mutate | **Reference** with a join collection | No equivalent of `JOIN` table in document model — must model explicitly |
| Slowly-changing snapshot (order → customer-at-time) | parent+snapshot | child changes, snapshot does not | **Embed snapshot** | Historical accuracy, no consistency cost |
| Hot-set, read-heavy, small denormalized field | parent+summary | child rarely mutates | **Embed summary field** (`eventCount`, `lastEventAt`) | Avoids `$lookup` cost on hot read path |

See [[06.09.02. MongoDB WiredTiger Storage Engine]] for how the storage engine handles the document growth and relocation that embedding causes, and [[06.09.04. The Aggregation Pipeline Framework]] for how `$lookup` and `$unwind` let you reassemble referenced data at query time when embedding is not an option.

## Cross-Ecosystem Implementation

The document-vs-relational choice is exposed very differently across the four target ORM ecosystems. The shape of the data-access code is identical — only the syntax and the implicit defaults differ.

| Aspect | Spring Data MongoDB (anchor) | Mongoose (Node) | MongoEngine (Python) | Laravel MongoDB |
|---|---|---|---|---|
| Document class | `@Document` + `@Field` POJO | `Schema` → `model.compile()` | `Document` subclass with `fields` | `Jenssegers\Mongodb\Eloquent\Model` |
| Nested sub-doc | `@Field(targetEntity=Address.class)` on a POJO field | `address: { street: String, city: String }` (sub-schema) | `EmbeddedDocumentField(AddressDoc)` | cast `array` or custom cast class |
| Array of sub-docs | `List<Address>` with `@Field` | `[subSchema]` | `ListField(EmbeddedDocumentField(...))` | cast `collection` |
| Reference (FK) | `@DBRef` or manual `ObjectId` field | `ref: 'User'` in schema (creates a manual ref) | `ReferenceField(User)` | `belongsTo` (Laravel-native, uses `_id`) |
| Schema validation | `JsonSchemaProvider` bean, `@JsonSchema` annotation | `schema.obj` validation on save | `Document.validate()` on save | Laravel `rules()` on save |
| Migration strategy | none by default; Mongock for scripted migrations | none; syncIndexes() to align indexes | none; manual `ensure_indexes()` | none; migration package optional |

When you read the Spring Data MongoDB anchor implementation note, the patterns above map almost 1:1. The delta notes then show how Mongoose's schema-on-save enforcement, MongoEngine's `EmbeddedDocument` pattern, and Laravel's cast-based approach express the same embedding-vs-referencing decisions in their own idioms.

## Hands-On Exercise

```bash
# 1. Inspect a BSON document at the wire level — install mongosh 1.10+ and dump a doc as hex
mongosh "mongodb://localhost:27017/shop" --quiet --eval '
  const doc = db.orders.findOne();
  const bson = BSON.serialize(doc);
  const hex = Array.from(new Uint8Array(bson))
                    .map(b => b.toString(16).padStart(2,"0")).join(" ");
  print(hex);
'
# Decode by hand against bsonspec.org: first 4 bytes = length, then (type,name,value) triples.

# 2. Attach a jsonSchema validator — observe rejected writes
mongosh shop --eval '
  db.createCollection("validated_users", {
    validator: { $jsonSchema: {
      bsonType: "object",
      required: ["email", "createdAt"],
      properties: {
        email:   { bsonType: "string", pattern: "^.+@.+\..+$" },
        age:     { bsonType: "int", minimum: 13, maximum: 130 },
        profile: { bsonType: "object", properties: { displayName: { bsonType: "string" } } }
      }
    } },
    validationLevel: "strict",
    validationAction: "error"
  });
  db.validated_users.insertOne({ email: "alice@example.com", createdAt: new Date(), age: 32 });
  // → acknowledged
  db.validated_users.insertOne({ email: "not-an-email", createdAt: new Date() });
  // → Document failed validation (error code 121)
'

# 3. Reproduce the schema-drift incident
mongosh shop --eval '
  db.events.insertOne({ ts: new Date(), payload: { kind: "click", url: "x" } });
  db.events.insertOne({ ts: new Date(), payload: "click|x" });           // drift!
  printjson(db.events.aggregate([{$group:{_id:"$payload.kind"}}]).toArray());
  // → [ { _id: "click" }, { _id: null } ]   ← the null bucket is service B
  printjson(db.events.validate({ full: true }).errors);
'

# 4. Measure the $lookup penalty
mongosh shop --eval '
  print(db.posts.aggregate([
    {$match:{_id: postId}},
    {$lookup:{from:"comments", localField:"_id", foreignField:"postId", as:"c"}}
  ]).explain().executionStats.executionTimeMillis);
'

# 5. Hit the 16 MB limit — generate a synthetic 17 MB document
mongosh shop --eval '
  const big = "x".repeat(16 * 1024 * 1024);     // 16 MB string
  try { db.bigt.insertOne({ _id: 1, big }); }
  catch (e) { print(e.codeName); }              // → BSONObjectTooLarge
'
```
