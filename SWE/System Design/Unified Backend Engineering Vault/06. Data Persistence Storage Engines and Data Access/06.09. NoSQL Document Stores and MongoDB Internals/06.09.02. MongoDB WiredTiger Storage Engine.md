# 06.09.02. MongoDB WiredTiger Storage Engine

## What This Is

**WiredTiger** is the storage engine that has powered MongoDB by default since version 3.2 (March 2016) and is the *only* storage engine shipped with MongoDB 4.2+ (MMAPv1 was removed in 4.2, December 2019). A storage engine is the layer that owns the on-disk file format, the in-memory cache, the concurrency control on individual documents, the compression of pages on disk, and the crash-recovery procedure that replays the journal on startup. Everything above it in MongoDB — the query planner, the aggregation framework, the replica-set oplog, the sharding `mongos` router — treats the storage engine as an opaque key/value interface and does not care whether a document is stored in a B-tree or an LSM. This note teaches the WiredTiger internals so you can reason about cache pressure, write amplification, lock contention, and the exact behaviour you observe when `db.serverStatus().wiredTiger` reports a spike in `write` tickets or `cache` evictions.

WiredTiger is the third-generation storage engine in MongoDB's history. The original engine (MMAPv1, 2009–2019) used `mmap()` to map collection files into the process address space and relied on the OS page cache — it had *collection-level* write locks, no compression, and catastrophic write amplification under document growth. The second engine, WiredTiger (acquired by MongoDB Inc. in 2014), uses a user-space buffer cache (default 50% of RAM, tunable via `--wiredTigerCacheSizeGB`), *document-level* MVCC concurrency, configurable compression (snappy default, also zlib, zstd, none), and a choice of two on-disk data structures: a B+ tree (default) or an LSM tree (`--wiredTigerEngineConfig="type=lsm"`). The WiredTiger source is open at [wiredtiger.com](http://source.wiredtiger.com/) — it is a C library that MongoDB links into `mongod`, and the same library is usable standalone (it is the storage engine underneath Amazon DynamoDB's on-demand mode and several other systems). Understanding its internals is understanding the substrate every MongoDB query lands on.

This note sits in the persistence layer (section 06) directly under [[06.09.01. Document Model vs. Relational Schema]] because the document-model decisions (embedding, growing arrays, schema drift) translate into concrete WiredTiger behaviour: an embedded array that grows forces the document to be relocated on disk, which burns IOPS; a 16 MB document with frequent updates causes cache thrashing because each rewrite dirties the whole page. The read/write concern knobs in [[06.09.03. MongoDB Read and Write Guarantees]] are also WiredTiger-aware: `j: true` is a `fsync` of the WiredTiger journal, `w: "majority"` requires the journal to be flushed on the secondaries before the primary acknowledges. Read this note before 06.09.03 — the failure modes of the durability knobs only make sense once you know what the journal actually is.

## The Details

### WiredTiger internals: B-Tree storage, memory caching, Snappy/Zlib data compression

The default on-disk data structure in WiredTiger is a **B+ tree** of pages — *internal* pages carry routing keys and child pointers, *leaf* pages carry the actual key/value pairs (in MongoDB, the key is the `_id` or indexed-field value and the value is the BSON document), and leaf pages are linked in a doubly-linked list for range scans. The page size is tunable via `--wiredTigerEngineConfig="leaf_page_max=32768"` (default 32 KB; internal page max defaults to 4 KB). Every page carries a 4-byte page-type tag, a checksum, and a "cell" array where each cell is `(type, length, payload)` — the BSON documents themselves are stored as cells of type `WT_CELL_VALUE_OVFL` (overflow) when they exceed a quarter of the page size, in which case the leaf cell holds a pointer to an overflow page in the `WiredTigerHS.wt` file. This overflow mechanism is how a 16 MB document can be stored in a B-tree whose leaf pages are 32 KB: the document lives in a chain of overflow pages and the B-tree leaf holds only the pointer.

The in-memory cache is the most important knob in the entire engine. By default, WiredTiger reserves 50% of system RAM (or 50% of RAM minus 1 GB on systems with > 4 GB RAM — see the `cacheSizeGB` calculation in `src/conn_cache.c`). The cache holds *clean* pages (identical to disk, can be evicted freely) and *dirty* pages (modified since the last checkpoint, must be written to disk before eviction). The eviction server thread (`wt_evict_server`) runs continuously and targets an eviction threshold of 95% full (`cache.used / cache.maximum ≥ 0.95`) by walking an LRU queue of pages; when it crosses 95%, application threads are *also* forced to perform eviction synchronously before their next write — this is the "application threads performing eviction" metric in `db.serverStatus().wiredTiger.cache` and it is the direct cause of p99 latency spikes on a cache-starved `mongod`. The single most important production command is:

```bash
# Tune the cache down on a co-located box (e.g. mongod + app server on the same host)
mongod --wiredTigerCacheSizeGB 4    # hard cap at 4 GB regardless of host RAM

# Verify the live cache size and current eviction behaviour
mongosh --eval 'const c = db.serverStatus().wiredTiger.cache;
  print("bytes currently in cache: " + c["bytes currently in cache"]);
  print("maximum bytes configured: " + c["maximum bytes configured"]);
  print("cache dirty %: " + (c["tracked dirty bytes in the cache"] /
                              c["maximum bytes configured"] * 100).toFixed(2));
  print("app threads evicting: " + c["application threads page written from cache");'
# If "app threads evicting" is non-zero and growing, your p99 write latency is
# dominated by eviction work — either raise cacheSizeGB, lower write rate,
# or fix the working-set so it fits in cache.
```

Compression is applied at the *block* level (whole pages) and optionally at the *prefix* level (the leading common bytes of keys in an index page). The default block compressor is **snappy** (Google's LZ77-style compressor, ~250 MB/s compress and ~500 MB/s decompress on a modern x86 core) — it trades a modest compression ratio (~50–60% of original size on typical BSON) for very low CPU overhead, which is critical because every page eviction and every checkpoint write goes through it. The alternatives are **zlib** (better ratio ~30–40% of original, ~5× slower than snappy), **zstd** (added in MongoDB 4.2, ratio ~25–35% of original, ~2× slower than snappy, much better than zlib at the same CPU), and **none** (no compression, useful for benchmarks and for collections of pre-compressed binary blobs). Compression is set per-collection at creation time and is **immutable** without a re-write:

```javascript
// Create a collection with zstd compression (better ratio than snappy for cold data)
db.createCollection("audit_log", {
  storageEngine: {
    wiredTiger: {
      configString: "block_compressor=zstd,allocation_size=4096"
    }
  }
});

// Override the compressor for an index (separate from the collection default)
db.orders.createIndex(
  { "customer.email": 1 },
  { name: "email_idx", wiredTiger: { configString: "block_compressor=zstd,prefix_compression=true" } }
);

// Inspect what compressor each collection is actually using
db.runCommand({ listCollections: 1, filter: {}, nameOnly: false })
  .cursor.firstBatch.forEach(c => {
    const opt = c.options?.storageEngine?.wiredTiger?.configString || "(default snappy)";
    print(`${c.name}: ${opt}`);
  });
```

The choice of compressor has a subtle interaction with the cache. Because WiredTiger caches *uncompressed* pages in memory and only compresses on disk I/O, a more aggressive compressor reduces the I/O bandwidth requirement (good for disk-bound systems) but does *not* reduce the memory footprint of the working set. This is a frequent source of confusion: switching snappy → zstd halves your disk usage but does *not* let you halve `--wiredTigerCacheSizeGB` — the cache still needs to hold the uncompressed pages. The production failure mode here is a 1 TB collection that fits on a 250 GB SSD (thanks to zstd) but does *not* fit in a 64 GB cache; the system becomes read-amplified (every random read is a 32 KB page read from disk, decompressed on the fly), and the `cache` read IOPS metric (`bytes read into cache`) climbs above the disk's random-read ceiling. The metric that reveals this is `db.serverStatus().wiredTiger.cache["pages read into cache"]` divided by uptime — if it exceeds ~20% of your disk's random-read IOPS rating, you are disk-bound and need more RAM, not more disk. The table below summarises the compressor tradeoffs:

| Compressor | Ratio (typical BSON) | Compress MB/s | Decompress MB/s | When to use | CPU cost on cache miss |
|---|---|---|---|---|---|
| snappy (default) | ~55% | ~250 | ~500 | Default — fast, low CPU | Negligible |
| zlib | ~35% | ~40 | ~120 | Cold data on disk-bound box | Noticeable on every read |
| zstd (4.2+) | ~30% | ~120 | ~300 | Best ratio/CPU tradeoff — audit logs, cold collections | Low |
| none | 100% | n/a | n/a | Pre-compressed blobs (images, videos) | None |

The B+ tree can also be swapped for an **LSM tree** via `--wiredTigerEngineConfig="type=lsm"` — this is rarely used in production MongoDB but is supported because WiredTiger was originally designed as a configurable engine for both workloads. An LSM tree writes new keys to an in-memory memtable, flushes it to an immutable SSTable on disk when full, and merges SSTables in the background. LSM trees are write-optimized (every write is a sequential append, no page splits) but read-pessimistic (every read may need to check the memtable plus every SSTable, mitigated by Bloom filters and a block cache). For MongoDB's typical read-heavy OLTP workload the B+ tree is faster; LSM trees win only for pure write-heavy ingest (e.g. a time-series collection that is written once and read rarely), and even there the time-series collection feature added in MongoDB 5.0 (`db.createCollection("metrics", { timeseries: { timeField: "ts" } })`) uses a B+ tree internally with a column-store optimization for the time bucket. See [[06.09.04. The Aggregation Pipeline Framework]] for how the aggregation pipeline interacts with these data structures — `$group` benefits from B+ tree range scans, while `$sort` on an unindexed field spills to disk regardless of the underlying structure.

### Concurrency: Ticket-based concurrency model, document-level locking

WiredTiger's concurrency model has three independent layers that together determine how many operations can run simultaneously and how they block each other: (1) **MVCC snapshot isolation** at the transaction level, (2) **document-level locking** at the row level (the headline improvement over MMAPv1's collection-level lock), and (3) a **ticket-based admission control** at the engine level that bounds the total number of concurrent read and write operations. Understanding all three is essential because each has a distinct failure mode and a distinct metric.

**MVCC (Multi-Version Concurrency Control)** is the foundation. Every WiredTiger transaction, at `BEGIN`, takes a *snapshot* of the globally ordered list of running transactions and is allowed to see only the versions of each page that were committed *before* its snapshot timestamp. Updates do not overwrite in place — they create a new version of the page cell (a new "update chain" linked list in memory) and mark the old version as superseded. Old versions are retained as long as any open transaction might still need them, which is the basis of MongoDB's `snapshot` and `linearizable` read concerns (see [[06.09.03. MongoDB Read and Write Guarantees]]). When a transaction commits, WiredTiger assigns it a globally monotonic commit timestamp (`stable_timestamp`) and writes the commit record to the journal; a background "lookaside" mechanism reconciles the snapshot timestamps across the replica set. The isolation level this provides is *snapshot isolation* — reads see a consistent point-in-time view, writes do not block reads, and the only conflicts are *write-write* conflicts on the same document (detected at commit time, causing one writer to abort with `WriteConflict` error code 112 and retry automatically).

**Document-level locking** is the user-visible consequence of MVCC. In MMAPv1, a write to any document in a collection took a collection-level `X` lock, serializing *all* writes to that collection — a single slow `updateOne` blocked every other writer, regardless of whether they touched the same document. In WiredTiger, the lock granularity is the *document* (more precisely, the B-tree cell holding the document): two writers touching different documents proceed in parallel, and a writer touching document A blocks only other writers touching document A. The practical implication is that MongoDB throughput on WiredTiger scales linearly with the *fan-out* of your write workload — a thousand concurrent users each updating their own `users` document runs ~1000× faster than MMAPv1, while a thousand concurrent writers all updating the same counter document (e.g. a global view counter) is *no faster* than MMAPv1 because they all contend on the same document's update chain. The fix for the counter pattern is to fan out the writes across `N` sub-counter documents and aggregate at read time:

```javascript
// ANTI-PATTERN — every writer contends on the same document's update chain
db.counters.updateOne({ _id: "page_views" }, { $inc: { count: 1 } });
// → under 1000 concurrent writers, 90%+ of updates hit WriteConflict retries

// BETTER — fan out across N shards, aggregate at read time
const N = 100;
const shard = Math.floor(Math.random() * N);
db.counters.updateOne(
  { _id: `page_views_${shard}` },
  { $inc: { count: 1 } },
  { upsert: true }
);
// Read: sum across all shards
db.counters.aggregate([
  { $match: { _id: /^page_views_/ } },
  { $group: { _id: null, total: { $sum: "$count" } } }
]).toArray()[0].total;
```

**Ticket-based admission control** is the third layer and the one most often misdiagnosed. WiredTiger maintains two pools of "tickets" — read tickets (default 128) and write tickets (default 128) — and every operation must acquire a ticket from its pool before it can begin executing against the engine. If all 128 read tickets are held, the 129th read operation *blocks* on the ticket queue until one is released; the same for writes. The intent is to prevent the cache from being overwhelmed by more concurrent operations than it can serve without thrashing — it is the engine's back-pressure mechanism. The metrics that reveal a ticket exhaustion are `db.serverStatus().wiredTiger.concurrentTransactions`:

```javascript
const t = db.serverStatus().wiredTiger.concurrentTransactions;
print("write: " + t.write.out + "/" + t.write.available + " tickets in use");
print("read:  " + t.read.out  + "/" + t.read.available  + " tickets in use");
// If "out" is consistently near "available", you are saturated — increase the
// pool size ONLY if you have first confirmed that the cache and the disk can
// sustain more concurrent work. Otherwise you trade ticket-blocking for cache
// thrashing, which is worse.
```

The default 128/128 is conservative for modern hardware. You can raise them via `--wiredTigerConcurrentWriteTransactions=256 --wiredTigerConcurrentReadTransactions=256` at startup, but this is the *last* knob to touch — raising tickets without raising cache size or disk throughput just moves the bottleneck from the ticket queue to the eviction server, which then forces application threads to evict synchronously, which is *strictly worse* than blocking on the ticket queue. The production failure mode is always the same shape: a write-heavy batch job (e.g. a nightly ETL that updates 10M documents) saturates the write tickets, *regular* writes from the application block for seconds, the application's MongoDB driver connection pool times out (`serverSelectionTimeoutMS` default 30s), the application returns 503s to users, and the on-call engineer sees the symptom (503s) rather than the cause (write ticket saturation). The metric to alert on is `wiredTiger.concurrentTransactions.write.available` dropping below 10 for > 1 minute — anything below 10 means writes are about to start blocking on the ticket queue.

### Checkpoints, Journaling, and Crash Recovery in MongoDB

WiredTiger's durability story has three independent mechanisms: the **journal** (a per-database write-ahead log of every modification), the **checkpoint** (a periodic consistent snapshot of all data files), and the **oplog** (a MongoDB-level — not WiredTiger-level — replication log). The three are easy to conflate because they all write to disk and they all participate in crash recovery, but they have distinct purposes, distinct write costs, and distinct failure modes.

The **journal** is a WiredTiger-level file (`WiredTigerLog.0000000001.<offset>`, rotating at 100 MB by default) that records every modification as a sequence of *log records*. Each log record is `(lsn, op_type, page_id, before_image, after_image, checksum)`. The journaling rule is the standard WAL contract: *before* a dirty page is allowed to be written to the data file, every modification to that page must first be in the journal file on disk and `fsync`'d. MongoDB's default journaling interval is 100 ms (`storage.journal.commitIntervalMs`, configurable down to 1 ms with `j: true` write concern at the cost of higher fsync overhead — each fsync on an NVMe SSD is ~50–200 µs, so 1 ms interval caps you at ~1000 fsync/s). The journal is a *circular* ring of files; once a checkpoint has been completed, all journal records older than the checkpoint are no longer needed for crash recovery and can be recycled. The `mongod` flag `--journal` is on by default (and has been since MongoDB 2.0); the only way to disable it is `--nojournal`, which is supported only for standalone (non-replica-set) servers and is a footgun — a crash mid-write with `--nojournal` will corrupt the data files because dirty pages can reach disk without their journal records being durable.

The **checkpoint** is WiredTiger's mechanism for taking a consistent on-disk snapshot of all data files. Every 60 seconds by default (`storage.wiredTiger.engineConfig.checkpointMs`) or every 2 GB of journal data — whichever comes first — WiredTiger runs a checkpoint: it walks every B-tree, writes all dirty leaf pages to the data files, writes a new root page, and atomically swaps the "live" root pointer in a special metadata file (`WiredTiger.wtmeta`). After the checkpoint completes, the journal records older than the checkpoint LSN can be deleted. A checkpoint is *not* a full file rewrite — it uses copy-on-write at the page level, so unchanged pages are not touched. The checkpoint is what makes crash recovery bounded: on startup, WiredTiger only needs to replay the journal records *after* the last completed checkpoint, which is at most 60 seconds (or 2 GB) of work. The checkpoint command can be triggered manually:

```bash
# Force a checkpoint immediately (useful before a backup that doesn't use mongodump)
mongosh admin --eval 'db.adminCommand({ fsync: 1 })'

# Inspect checkpoint timing and size
mongosh --eval 'const c = db.serverStatus().wiredTiger;
  print("last checkpoint: " + new Date(c.txn["transaction checkpoint most recent time"]).toISOString());
  print("checkpoint generation: " + c.txn["transaction checkpoint generation"]);
  print("checkpoint currently running: " + c.txn["transaction checkpoint currently running"]);
  print("total checkpoint time (ms): " + c.txn["transaction checkpoint total time (msecs)"]);'
```

The **oplog** is *not* part of WiredTiger — it is a MongoDB-level capped collection (`local.oplog.rs`) that records every write that must be replicated to secondaries. The oplog is implemented *on top of* WiredTiger as a regular collection (with the `capped` flag and a default size of 5% of free disk space, tunable via `--oplogSize`). This means every write in a replica set is written *twice* by WiredTiger: once to the journal (for crash recovery) and once to the oplog (for replication). The oplog write is part of the same WiredTiger transaction as the data write, so they commit atomically — if `w: 1` acknowledges the write, the oplog entry is durable to the same degree as the data. The distinction matters for read/write concern tuning: `j: true` flushes *both* the journal and the oplog to disk (because they share the journal); `w: "majority"` requires the oplog entry to be *applied* on a majority of replica-set members, which requires their journals to be flushed before they can acknowledge. See [[06.09.03. MongoDB Read and Write Guarantees]] for the full matrix.

Crash recovery on WiredTiger follows the standard ARIES-style redo algorithm: (1) **Analysis** — read `WiredTiger.wtmeta` to find the last completed checkpoint LSN, then read forward in the journal from that LSN to build a list of dirty pages and in-flight transactions; (2) **Redo** — for each log record from the checkpoint LSN forward, reapply the modification to the corresponding page in memory (because WiredTiger uses MVCC, the redo is idempotent — re-applying a record that was already applied has no effect); (3) **Undo** — for transactions that had *not* committed at crash time, walk their update chains and roll back the modifications (WiredTiger retains the before-images needed for this in the journal's undo records). On a healthy NVMe SSD, recovery of a 60-second journal takes < 5 seconds; on a spinning disk it can take minutes — another reason never to run a production database on HDD. The crash-recovery sequence at `mongod` startup is visible in the log:

```text
2024-03-15T10:30:00.123+0000 I  STORAGE  [initandlisten] WiredTiger opening session
2024-03-15T10:30:00.234+0000 I  STORAGE  [initandlisten] WiredTiger message: 
  WT_VERB_RECOVERY_PROGRESS: recovery starting at LSN 1/12345678
2024-03-15T10:30:00.567+0000 I  STORAGE  [initandlisten] WiredTiger message: 
  WT_VERB_RECOVERY_PROGRESS: recovery complete (1.2 seconds, 89 pages, 12 transactions)
2024-03-15T10:30:00.789+0000 I  STORAGE  [initandlisten] WiredTiger message: 
  WT_VERB_CHECKPOINT: checkpoint complete: 1.3 MB written
```

The production failure mode here is the **dirty cache at crash** scenario. If `mongod` crashes while a large fraction of the cache is dirty (e.g. a bulk insert was running and pushed `tracked dirty bytes in the cache` above 20%), the journal contains a lot of work to redo, and recovery can take *minutes* instead of seconds. During recovery, the `mongod` is unavailable — it is still listening on port 27017 but rejecting all operations with `NotWritablePrimary` or `ShutdownInProgress`. A replica set will fail over to a secondary during this window if the crash was on the primary, but if the recovery takes longer than `electionTimeoutMillis` (default 10 s) on *all* members, the cluster is down. The metric to alert on is `wiredTiger.cache["tracked dirty bytes in the cache"]` as a fraction of `maximum bytes configured` — if it exceeds 20% sustained, you are running too write-heavy for your cache size and a crash will produce a long recovery. The fix is either to raise cache size, lower write rate, or batch writes more aggressively so dirty pages are flushed by the eviction server before they accumulate. See [[06.09.03. MongoDB Read and Write Guarantees]] for how `j: true` interacts with the journal flush interval — the answer is that `j: true` *forces* an immediate journal flush regardless of `commitIntervalMs`, which is why it is expensive under high write load.

## Cross-Ecosystem Implementation

The WiredTiger engine is MongoDB-specific — there is no equivalent in JPA/Hibernate or Eloquent or Prisma, because those ORMs are relational-only. The closest analogues are the storage-engine choices in other databases. The table below maps the concepts across engines so you can transfer intuition:

| Concept | MongoDB (WiredTiger) | PostgreSQL | MySQL (InnoDB) | Redis |
|---|---|---|---|---|
| Default page size | 32 KB leaf, 4 KB internal | 8 KB | 16 KB | n/a (in-memory only) |
| Cache | 50% RAM, user-space | shared_buffers default 128 MB, OS page cache as second tier | innodb_buffer_pool default 128 MB | maxmemory, all in RAM |
| WAL name | `WiredTigerLog.*` | `pg_wal/` (WAL segments, 16 MB) | `ib_logfile*` (redo log) | AOF (`appendonly.aof`) |
| Checkpoint interval | 60 s or 2 GB | `checkpoint_timeout` 5 min, `max_wal_size` 1 GB | `innodb_io_capacity` triggers flush | `BGSAVE` forks a child for RDB snapshot |
| Default compression | snappy (zstd available) | TOAST (LZ4 in PG14+, optional per-column) | `innodb_compression` (zlib) | n/a (in-memory only) |
| Lock granularity | document | row (tuple) | row (index record) | single-threaded, no locks |
| MVCC retention | until no snapshot needs it | until no active transaction needs it (`vacuum`) | until no active read view needs it (`purge`) | n/a |
| Concurrency admission | 128 read + 128 write tickets | `max_connections` (default 100) | `innodb_thread_concurrency` (default 0 = infinite) | single-threaded, no admission |

When you read the MongoDB notes alongside the PostgreSQL notes in this vault, the conceptual mapping is: `--wiredTigerCacheSizeGB` ≈ `shared_buffers`, `commitIntervalMs` ≈ `wal_writer_delay` (200 ms default), the 60 s checkpoint ≈ PostgreSQL's 5 min `checkpoint_timeout`. The numbers differ because MongoDB's defaults assume a single-process-per-host deployment with a large dedicated cache, while PostgreSQL assumes the OS page cache will share the box with other processes.

## Hands-On Exercise

```bash
# 1. Inspect the live cache behaviour under load
mongosh --eval 'const c = db.serverStatus().wiredTiger.cache;
  for (let i = 0; i < 5; i++) {
    print(JSON.stringify({
      used_pct: (c["bytes currently in cache"] / c["maximum bytes configured"] * 100).toFixed(1),
      dirty_pct: (c["tracked dirty bytes in the cache"] / c["maximum bytes configured"] * 100).toFixed(1),
      evict_app: c["application threads page written from cache"],
      read_into: c["pages read into cache"]
    }));
    sleep(2000);
  }'

# 2. Inspect the journal files and checkpoint timing
ls -la /var/lib/mongodb/journal/        # WiredTigerLog.0000000001.<offset>
mongosh --eval 'printjson(db.serverStatus().wiredTiger.txn)'

# 3. Measure the fsync cost on your disk — direct fio test
fio --name=fsync-test --filename=/tmp/fio-test --size=1G --rw=write \
    --fsync=1 --ioengine=sync --runtime=10 --time_based --group_reporting
# Look at "fsync/s" — this is your hard ceiling for j:true write throughput.

# 4. Force a checkpoint and time it
mongosh admin --eval 'const t0 = Date.now();
  printjson(db.adminCommand({ fsync: 1 }));
  print("checkpoint took " + (Date.now() - t0) + " ms");'

# 5. Reproduce the ticket-saturation failure mode
# In one terminal: hammer writes against an indexed collection
mongosh shop --eval 'for (let i=0; i<1_000_000; i++) db.events.insertOne({ts: new Date(), n: i});' &
# In another: watch the ticket pool
mongosh --eval 'while(true){const t=db.serverStatus().wiredTiger.concurrentTransactions;
  print("write " + t.write.out + "/" + (t.write.out + t.write.available));
  sleep(500);}'
# When write.out saturates (out ≈ out+available), regular app writes start blocking.

# 6. Reproduce dirty-cache growth before a crash
mongosh --eval 'for (let i=0; i<5_000_000; i++) db.bulk.insertOne({_id:i, data:"x".repeat(1000)});' &
# Watch: db.serverStatus().wiredTiger.cache["tracked dirty bytes in the cache"]
# Kill mongod (kill -9) while dirty% > 20%, restart, observe the recovery time in the log.
```
