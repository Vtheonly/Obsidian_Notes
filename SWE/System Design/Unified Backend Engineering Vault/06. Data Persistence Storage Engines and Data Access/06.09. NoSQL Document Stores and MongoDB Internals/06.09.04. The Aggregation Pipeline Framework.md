# 06.09.04. The Aggregation Pipeline Framework

## What This Is

The **Aggregation Pipeline** is MongoDB's query language for analytical operations — the equivalent of SQL's `SELECT ... GROUP BY ... HAVING ... ORDER BY ... LIMIT` plus `JOIN` and `UNION ALL`, expressed as a sequence of *stages* that each take a stream of documents in, transform them, and emit a stream of documents out. It is the single most powerful feature in MongoDB and the one that distinguishes a database from a key-value store: without it, MongoDB is a fancy document store with rich single-document atomicity but no analytical capability; with it, MongoDB can do rollups, joins, pivots, time-bucketed aggregations, and graph traversals inside the database engine, avoiding the latency of shipping data to the application for post-processing. The pipeline is conceptually identical to a Unix pipeline (`cat foo | grep bar | sort | uniq -c`) — each stage is a pure function on a stream, the planner can reorder and fuse stages, and the operator's job is to pick the right stages in the right order to minimise work.

This note sits between [[06.09.03. MongoDB Read and Write Guarantees]] (which provides the `readConcern`/`readPreference` defaults the pipeline inherits) and [[06.10.01. Redis Architecture and Single-Threaded Processing]] (the next layer up in the cache hierarchy — Redis often holds the *result* of an expensive aggregation to avoid re-running it). The pipeline is the boundary where MongoDB stops being a single-document CRUD store and starts being a real analytical engine; it is also where most production MongoDB incidents live, because each stage has a distinct failure mode (memory blow-up on `$group`, fan-out explosion on `$unwind`, missing-index scans on `$match` in the wrong position, OOM on `$facet` with multiple sub-pipelines). Understanding the pipeline is understanding which stages are cheap, which are expensive, and how to read an `explain()` plan to see which is which.

The crucial conceptual shift from SQL is that **the pipeline is explicit about ordering** — you write the stages in the order you want them executed, and the planner respects that order (with a few well-defined optimisations like moving `$match` ahead of `$group` when possible). There is no query optimizer that picks between hash-join and nested-loop-join the way PostgreSQL's does; the join algorithm in `$lookup` is always a nested loop, and it is your job to put a `$match` before the `$lookup` to reduce the number of outer documents that drive the join. This explicitness is a feature — you can reason about performance by reading the pipeline top-to-bottom — but it is also a footgun, because a poorly-ordered pipeline can be 1000× slower than the same stages in the right order.

## The Details

### Multi-stage pipeline processing: `match`, `project`, `group`, `unwind`, `lookup` (Left Outer Join), `sort`, `$limit`.

Every aggregation pipeline is a JSON array of stage operators, executed left-to-right, with each stage receiving the output of the previous stage as its input. The first stage is almost always `$match` — the equivalent of SQL's `WHERE` — because putting `$match` first lets the planner use indexes to satisfy it (an "indexed query" stage), which reduces the number of documents that flow into every subsequent stage. The planner will *try* to move `$match` stages earlier in the pipeline (the `$match` pushdown optimisation), but only when it is safe — a `$match` after a `$group` cannot be pushed down because the grouped documents have different shapes from the input documents, and a `$match` after a `$lookup` cannot be pushed down because the joined fields do not exist before the lookup. The cardinal rule of pipeline performance is: **filter early, project early, group late**.

The seven core stages and their SQL equivalents:

| MongoDB stage | SQL equivalent | Cost | Index usage | Notes |
|---|---|---|---|---|
| `$match` | `WHERE` | Low (with index) | Yes | Always put first if possible; can use covered index |
| `$project` | `SELECT col1, col2` | Very low | n/a | Trims the document shape — reduces downstream work |
| `$sort` | `ORDER BY` | Medium (with index), High (without) | Yes if first stage | Spills to disk if > 100 MB |
| `$limit` | `LIMIT` | Very low | n/a | Combined with `$sort` for top-K queries |
| `$skip` | `OFFSET` | Low | n/a | Always paired with `$limit` for pagination |
| `$group` | `GROUP BY ... SUM/COUNT/AVG` | High | No (in-memory hash) | 100 MB limit per stage by default |
| `$unwind` | `JOIN ... ON UNNEST(array)` | High (fan-out) | No | N documents in → M*N documents out |
| `$lookup` | `LEFT OUTER JOIN` | Very high | Yes if `foreignField` indexed | Nested-loop algorithm, no hash-join alternative |

A concrete end-to-end example — "for the last 7 days, find the top 5 customers by total order value, including their email":

```javascript
db.orders.aggregate([
  // 1. $match — filter early, uses index on createdAt
  { $match: { createdAt: { $gte: ISODate("2024-03-08T00:00:00Z") } } },

  // 2. $unwind — fan out the items array (one doc per line item)
  { $unwind: "$items" },

  // 3. $group — roll up by customer, sum the line totals
  { $group: {
      _id: "$customer._id",                              // group key = customer ID
      customerName: { $first: "$customer.name" },        // carry-along denormalized field
      totalValue: { $sum: { $multiply: ["$items.qty", "$items.unitPrice"] } },
      orderCount: { $sum: 1 }
  }},

  // 4. $sort — order by totalValue descending
  { $sort: { totalValue: -1 } },

  // 5. $limit — keep only top 5
  { $limit: 5 },

  // 6. $lookup — fetch the live customer record (Left Outer Join)
  { $lookup: {
      from: "customers",
      localField: "_id",
      foreignField: "_id",
      as: "customerDoc"
  }},

  // 7. $unwind — lookup returns an array; flatten it (preserving nulls via preserveNullAndEmptyArrays)
  { $unwind: { path: "$customerDoc", preserveNullAndEmptyArrays: true } },

  // 8. $project — final shape for the API consumer
  { $project: {
      _id: 0,
      customerId: "$_id",
      name: "$customerDoc.name",
      email: "$customerDoc.email",
      totalValue: 1,
      orderCount: 1
  }}
]);
```

The SQL equivalent of the above is `SELECT c._id, c.name, c.email, SUM(i.qty * i.unit_price) AS total_value, COUNT(*) AS order_count FROM orders o JOIN UNNEST(o.items) AS i LEFT JOIN customers c ON c._id = o.customer._id WHERE o.created_at >= '2024-03-08' GROUP BY c._id, c.name, c.email ORDER BY total_value DESC LIMIT 5` — but the SQL version assumes the database supports `UNNEST` on a JSON array column (PostgreSQL does, with `jsonb_array_elements`; MySQL does not natively). The MongoDB version is portable across every MongoDB version since 3.2 (when `$lookup` was added; `$unwind` and `$group` have existed since 2.2).

The two stages that deserve the most caution are **`$unwind`** and **`$lookup`**, because both can blow up the document count. `$unwind` on an array of N elements produces N output documents per input document — a collection of 1M orders each with 50 line items produces 50M intermediate documents, which can exhaust the 100 MB stage memory limit (see the next H3) or take minutes to process. `$lookup` is a nested-loop join: for each of the M input documents, it does one index seek on the foreign collection (if `foreignField` is indexed) or one full collection scan (if it is not). For M = 1M input documents and a foreign collection of 1M documents, the indexed case is 1M index seeks (~seconds), the unindexed case is 1M × 1M = 10^12 comparisons (~weeks). The fix for the unindexed case is always to create an index on the `foreignField`:

```javascript
// ALWAYS index the foreignField of a $lookup — the cost of NOT doing so is catastrophic
db.customers.createIndex({ _id: 1 });          // _id is indexed by default — free
db.products.createIndex({ sku: 1 });           // for $lookup from order_items to products
db.users.createIndex({ "profile.email": 1 });  // for $lookup by email

// Verify the lookup uses the index — look for "IXSCAN" not "COLLSCAN" in the stage
db.orders.aggregate([
  { $match: { status: "paid" } },
  { $lookup: { from: "customers", localField: "customer._id", foreignField: "_id", as: "c" } }
]).explain(true).stages
  .filter(s => s.$lookup)
  .map(s => s.$lookup.stage.inputStage.stage);  // → "IXSCAN" if indexed, "COLLSCAN" if not
```

The `$facet` stage (added in 3.4) lets you run multiple sub-pipelines on the same input — the canonical use case is a search-results page that needs to show both the total count and the facet counts (e.g. group by category, group by brand) alongside the paginated results. `$facet` runs all sub-pipelines in parallel on the same input, but each sub-pipeline is subject to the 100 MB memory limit independently. The production failure mode here is that `$facet` multiplies the memory cost — if your input is 50 MB and you have 3 sub-pipelines, the total memory used is 50 MB (input) + 3 × (sub-pipeline output) — and any one sub-pipeline hitting the 100 MB limit fails the entire `$facet` with error code 292 (`ExceededMemoryLimit`). See the next H3 for the `allowDiskUse` fix.

The pipeline optimiser does a fixed set of rewrites: `$match` moves before `$group`/`$project`/`$unwind`/`$lookup` when safe; `$project` is fused into `$group` when only the carry-along fields are needed; `$sort` is fused with `$limit` into a top-K operator; consecutive `$match` stages are merged. The optimiser does *not* reorder stages across `$group` or `$lookup` boundaries, and it does *not* push `$match` into the `pipeline` parameter of `$lookup`'s sub-pipeline — that is your job. To see what the optimiser did, run `.explain()` and look at the `stages` array — the *parsed* pipeline (what you wrote) is in `explain.command.parsedQuery`, the *optimised* pipeline (what runs) is in `explain.stages`. The difference between them is the optimiser's work.

### Memory limits: 100MB RAM stage thresholds and using `allowDiskUse`

Every aggregation stage has a hard memory limit of **100 MB** by default (`internalQueryMaxBlockingSortMemoryUsageBytes` for `$sort`; `internalDocumentSourceGroupMaxMemoryBytes` for `$group`; the same 100 MB cap applies to `$lookup`'s hash table, `$facet`'s sub-pipelines, and `$unionWith`'s accumulation buffer). When a stage exceeds this limit, MongoDB returns error code 292 (`QueryExceededMemoryLimitNoDiskUseAllowed`) and aborts the entire pipeline — no partial results are returned. The fix is the `allowDiskUse: true` option on the `aggregate()` call, which tells the engine that stages exceeding the 100 MB in-memory threshold may spill to temporary on-disk files in the `dbPath/_tmp` directory:

```javascript
// The pipeline that will OOM without allowDiskUse
db.events.aggregate([
  { $match: { ts: { $gte: ISODate("2024-01-01") } } },     // ~10M docs match
  { $group: { _id: "$userId", count: { $sum: 1 } } },       // ~1M unique users → ~150 MB hash
  { $sort: { count: -1 } },
  { $limit: 100 }
], { allowDiskUse: true });                                  // ← the fix

// The pipeline that will succeed WITHOUT allowDiskUse (because $limit caps it early)
db.events.aggregate([
  { $match: { ts: { $gte: ISODate("2024-01-01") } } },
  { $sort: { ts: 1 } },                                      // sort uses index if available
  { $limit: 1000 },                                          // cap at 1000 docs
  { $group: { _id: "$userId", count: { $sum: 1 } } }         // now groups only 1000 docs → tiny
]);
// The second pipeline is ~1000× faster AND uses less memory.
```

The `allowDiskUse` option (and the equivalent `cursor.allowDiskUse` field) was changed in MongoDB 4.2: prior to 4.2, `allowDiskUse` defaulted to `false` and had to be explicitly enabled; from 4.2 onward it is *still* `false` by default for backward compatibility, but the error message is clearer and the spill is to a WriteTiger-managed temporary collection rather than to bare files. From 4.4, the spill uses an internal ` WiredTiger`-backed temporary collection which is much faster than the old file-based spill (because it benefits from the WiredTiger cache). The performance implication of `allowDiskUse: true` is that the stage may now take *minutes* instead of *seconds* — spilling to disk is 100–1000× slower than staying in memory, and a `$group` that spills to disk can dominate the entire pipeline's runtime. The metric that reveals a spill is the `explain()` output's `usedDisk: true` field on each stage:

```javascript
const plan = db.events.aggregate([...], { allowDiskUse: true }).explain(true);
plan.stages.forEach((s, i) => {
  for (const op in s) {
    if (s[op].usedDisk) {
      console.log(`Stage ${i} (${op}) spilled to disk — consider pre-filtering`);
    }
  }
});
```

The 100 MB limit is per-stage, not per-pipeline — a pipeline with 10 stages can use up to 10 × 100 MB = 1 GB of memory total if every stage hits its limit. This is important when running multiple pipelines concurrently: if your `mongod` has 4 GB of cache and you run 10 concurrent `$group` pipelines that each spill, you can exhaust the cache and cause eviction pressure on the operational workload. The production failure mode here is the **"analytical query OOMs the operational database"** pattern: a BI analyst runs a heavy aggregation against the production OLTP database, the aggregation spills to disk and consumes 80% of the cache, the operational read latency climbs from 1 ms to 50 ms, and users see slow API responses. The fix is one of three: (1) run analytical workloads on a hidden secondary (a replica-set member with `priority: 0, hidden: true` that no operational traffic reaches), (2) use the `$lookup` sub-pipeline to push filtering into the join rather than materialising the full joined result, or (3) pre-aggregate the data into a separate collection via a periodic job (e.g. a nightly `$merge` that writes daily rollups into a `daily_metrics` collection) and have the analytical queries hit the rollups instead of the raw events.

The `$facet` stage has a particularly nasty interaction with the memory limit. Each sub-pipeline of a `$facet` has its own independent 100 MB budget — but the *input* to the `$facet` is shared across all sub-pipelines, so if the input is 80 MB and you have 3 sub-pipelines, the total memory used is 80 MB + 3 × (sub-pipeline working set). If any sub-pipeline exceeds 100 MB, the entire `$facet` fails — you cannot set `allowDiskUse` per sub-pipeline, only per pipeline. The workaround for a `$facet` that needs to spill is to split the `$facet` into multiple separate `aggregate()` calls, each with `allowDiskUse: true`, executed in parallel from the application. This loses the atomicity of the `$facet` (the sub-pipelines no longer see the same input snapshot if the underlying collection is being written to) but gains the ability to spill each one independently.

```javascript
// $facet — multi-faceted search (e.g. e-commerce search results + facet counts)
db.products.aggregate([
  { $match: { category: "electronics", price: { $lte: 500 } } },
  { $facet: {
      "results": [
        { $sort: { price: 1 } },
        { $limit: 20 },
        { $project: { name: 1, price: 1, brand: 1 } }
      ],
      "brands": [
        { $group: { _id: "$brand", count: { $sum: 1 } } },
        { $sort: { count: -1 } },
        { $limit: 10 }
      ],
      "priceRanges": [
        { $bucket: {
            groupBy: "$price",
            boundaries: [0, 100, 200, 300, 400, 500],
            default: "other",
            output: { count: { $sum: 1 } }
        }}
      ]
  }}
], { allowDiskUse: true });
// Returns: { results: [...20 products...], brands: [...10 brand counts...], priceRanges: [...6 buckets...] }
// Each sub-pipeline has its own 100 MB budget; if any one exceeds it, the whole $facet fails.
```

The general principle is: **the 100 MB limit is a deliberate back-pressure mechanism**. It exists to prevent a single runaway aggregation from consuming unbounded memory and destabilising the `mongod` for operational traffic. When you hit it, the right response is *not* to blindly set `allowDiskUse: true` — it is to ask why your pipeline needs that much memory and whether restructuring (filtering earlier, projecting narrower, pre-aggregating) can keep it under the limit. See [[06.09.02. MongoDB WiredTiger Storage Engine]] for how the cache eviction interacts with a heavy aggregation — the eviction server will start forcing application threads to evict synchronously when the cache crosses 95% full, which manifests as p99 latency spikes on the operational workload while the aggregation is running.

### Compound indexing and Multikey indexes for array fields

MongoDB uses B-tree indexes (WiredTiger's default; see [[06.09.02. MongoDB WiredTiger Storage Engine]]) with one critical extension over relational indexes: the **multikey** index, which indexes every element of an array field as a separate entry in the same B-tree. This is what makes MongoDB's array fields first-class queryable citizens — `db.products.find({ tags: "electronics" })` returns documents where `tags` is an array containing `"electronics"`, and it uses the multikey index on `tags` to do so in O(log N) instead of O(N). Without multikey indexes, you would have to denormalise array membership into a join table (the relational pattern) or use a full-text index (which has different semantics).

A compound index on `{ a: 1, b: 1, c: 1 }` is a B-tree whose keys are tuples `(a, b, c)`, sorted lexicographically — the same data structure as PostgreSQL's `CREATE INDEX ON t (a, b, c)`. The MongoDB-specific rule that governs when a compound index can be used is the **ESR rule** (Equality, Sort, Range), which dictates the optimal field ordering for a compound index that will serve both equality predicates and range scans and sort operations on the same query:

- **E (Equality)**: Fields tested with `{ field: value }` (exact match) go first. These can be used as a prefix for any subsequent field.
- **S (Sort)**: Fields used in `$sort` go second. The index can satisfy the sort without an explicit `$sort` stage only if the sort fields come immediately after the equality fields in the index.
- **R (Range)**: Fields tested with `{ $gte, $lte, $ne, $in }` go last. Once the index hits a range predicate, it cannot use the index for any subsequent field's sort order — only for further filtering.

```javascript
// The ESR rule in action — a query that benefits from a well-ordered compound index
db.events.find({
  userId: ObjectId("..."),                  // E — equality on userId
  ts: { $gte: ISODate("2024-01-01"),        // R — range on ts
        $lt:  ISODate("2024-02-01") }
}).sort({ type: 1 });                       // S — sort by type

// Optimal compound index: { userId: 1, type: 1, ts: 1 }
//   E (userId) → S (type) → R (ts)
db.events.createIndex({ userId: 1, type: 1, ts: 1 });

// Verify it is used — look for "IXSCAN" and "sortDefaultsFromIndex: true" in the plan
db.events.find({...}).sort({type: 1}).explain(true).queryPlanner;
//   winningPlan.stage = "IXSCAN"
//   winningPlan.indexName = "userId_1_type_1_ts_1"
//   winningPlan.direction = "forward"          ← sort served by index, no in-memory sort

// ANTI-PATTERN — wrong index order (R before S)
db.events.createIndex({ userId: 1, ts: 1, type: 1 });
// The query above will use this index for the equality + range, but will need
// an in-memory SORT stage — which costs memory and can hit the 100 MB limit.
```

The multikey index is created automatically the first time you index a field that contains an array — MongoDB detects the array at insert time and creates a multikey index instead of a regular B-tree. There is no command to force a multikey index; it is a property of the index that emerges from the data. Once an index is multikey, it stays multikey even if all arrays are later removed from the collection (you must drop and recreate the index to revert). The multikey index cannot be a *covered* index for a query that projects a non-array field of the same document — because the index entry is per-array-element, projecting any field that is not the indexed array requires fetching the full document from the collection. This is a subtle but important performance gotcha: a query that uses a multikey index for filtering but projects other fields will always have a `FETCH` stage after the `IXSCAN`, which doubles the work.

Compound indexes that include an array field have a stricter limitation: **at most one array field per compound index**. If you try to create `db.products.createIndex({ tags: 1, categories: 1 })` where both `tags` and `categories` are arrays, MongoDB will return error 121 (`IndexOptionsConflict`) at the first insert that has both fields as arrays — the cross-product of array elements would produce an unbounded number of index entries per document, which the engine refuses. The workaround is to create two separate single-field multikey indexes and let the query planner intersect them (`stage: "AND_HASH"` or `"AND_SORTED"` in the explain output), which is less efficient than a single compound index but is the only option for multi-dimensional array queries.

```javascript
// Multikey index — one index entry per array element
db.products.insertMany([
  { _id: 1, name: "Widget", tags: ["electronics", "gadget", "sale"] },
  { _id: 2, name: "Gizmo",  tags: ["electronics", "premium"] },
  { _id: 3, name: "Doohickey", tags: ["gadget"] }
]);

db.products.createIndex({ tags: 1 });
// Index entries (logically): "electronics"→1, "electronics"→2, "gadget"→1, "gadget"→3,
//                             "premium"→2, "sale"→1

// Query: find all products tagged "gadget"
db.products.find({ tags: "gadget" }).explain(true).queryPlanner.winningPlan;
//   stage: "IXSCAN"
//   indexName: "tags_1"
//   indexBounds: { tags: ["[\"gadget\", \"gadget\"]"] }   ← tight scan

// Query: find products with BOTH "electronics" AND "gadget"
db.products.find({ tags: { $all: ["electronics", "gadget"] } })
  .explain(true).queryPlanner.winningPlan;
//   stage: "IXSCAN"  with AND_SORTED stage
//   → does two index scans (one per tag) and intersects the results
//   → returns docs that appear in BOTH scans: just _id:1

// Covered query — projection can be served from the index alone (no FETCH)
db.products.createIndex({ name: 1, tags: 1 });
db.products.find({ tags: "gadget" }, { _id: 0, name: 1 })
  .explain(true).queryPlanner.winningPlan;
//   stage: "IXSCAN", indexName: "name_1_tags_1"
//   AND stage: "PROJECTION_COVERED"   ← no FETCH, the index alone answers the query
```

The production failure mode is the **"missing index on `$match`"** pattern, which is the MongoDB equivalent of SQL's `Seq Scan` on a billion-row table. An application adds a new query `db.events.find({ "user.country": "DE", "user.tier": "premium" })` without creating the corresponding compound index `{ "user.country": 1, "user.tier": 1 }`. The query planner falls back to a `COLLSCAN` (collection scan), reading every document in the collection to filter — on a 100M-document collection this takes minutes, during which the cache is filled with the scanned documents, eviction pressure builds, and operational queries slow down. The metric that reveals this is the `explain()` output's `winningPlan.stage === "COLLSCAN"` (vs the desired `"IXSCAN"`), and the `totalDocsExamined` field in `executionStats` — for a well-indexed query, `totalDocsExamined` should be approximately equal to `nReturned`; if it is orders of magnitude larger, you are missing an index. The fix is to add the index (`db.events.createIndex({ "user.country": 1, "user.tier": 1 })`), which is online in MongoDB 4.2+ (the index build does not block reads or writes, courtesy of the WiredTiger online index build feature) but which does consume disk and CPU during the build — schedule it during off-peak hours. See [[06.09.01. Document Model vs. Relational Schema]] for how the embedding-vs-referencing decision affects index design — embedded sub-documents can be indexed directly (`"user.country"`), while referenced documents require `$lookup` or denormalised summary fields.

## Cross-Ecosystem Implementation

The aggregation pipeline is MongoDB-specific — there is no direct equivalent in JPA/Hibernate, Eloquent, or Prisma, all of which are relational ORMs. The closest cross-ecosystem analogues are: Spring Data MongoDB's `MongoTemplate.aggregate(...)`, Mongoose's `Model.aggregate(...)`, PyMongo's `collection.aggregate(...)`, and Laravel MongoDB's `DB::connection('mongodb')->collection('c')->aggregate(...)`. The shape is identical — a list of stage operators passed to a single method call — only the syntax differs.

| Aspect | Spring Data MongoDB (anchor) | Mongoose (Node) | PyMongo (Python) | Laravel MongoDB |
|---|---|---|---|---|
| Pipeline builder | `Aggregation.match(...)`, `Aggregation.group(...)`, `Aggregation.project(...)` | `[{$match: {...}}, {$group: {...}}]` (plain JS objects) | `[{"$match": {...}}, {"$group": {...}}]` (plain dicts) | `DB::connection('mongodb')->collection('c')->raw(function($c){ return [...]; });` |
| Type-safe stages | Yes — `Aggregation` static methods with typed arguments | No — JS object literals | No — Python dict literals | No — array of arrays |
| `allowDiskUse` | `AggregationOptions.builder().allowDiskUse(true).build()` | `Model.aggregate(stages, { allowDiskUse: true })` | `coll.aggregate(stages, allowDiskUse=True)` | via raw command options |
| `explain()` | `mongoTemplate.aggregate(...).explain()` returns `Document` | `Model.aggregate(stages).explain()` | `coll.aggregate(stages).explain()` | via raw `command` |
| `$lookup` helper | `Aggregation.lookup("customers", "_id", "_id", "c")` | `{$lookup: {from: "customers", localField: "_id", foreignField: "_id", as: "c"}}` | same as Mongoose | same shape |
| `$facet` helper | `Aggregation.facet().facet(match, group).as("results")` | `{$facet: {results: [...], brands: [...]}}` | same as Mongoose | same shape |

When you read the Spring Data MongoDB anchor implementation note, the patterns above map almost 1:1 — the type-safe `Aggregation` builder produces the same wire-level aggregation command that the other drivers produce from plain dictionaries. The delta notes then show how Mongoose's chainable `.aggregate().match().group()` style, PyMongo's plain-dict style, and Laravel's `raw()` escape hatch express the same pipeline in their own idioms. The key invariant that does not change across ecosystems is that **the pipeline is executed by the MongoDB server, not by the driver** — the driver is just a serialiser for the JSON command. This means `explain()` plans are identical across drivers, and the same optimisations apply.

## Hands-On Exercise

```bash
# 1. Run a basic pipeline and inspect its plan
mongosh shop --eval '
  const plan = db.orders.aggregate([
    { $match: { status: "paid" } },
    { $group: { _id: "$customer._id", total: { $sum: "$items.qty" } } },
    { $sort: { total: -1 } },
    { $limit: 10 }
  ]).explain(true);
  print("stages: " + plan.stages.length);
  print("docsExamined: " + plan.executionStats.totalDocsExamined);
  print("docsReturned: " + plan.executionStats.nReturned);
  print("usedDisk: " + plan.stages.some(s => s.$group?.usedDisk || s.$sort?.usedDisk));
'

# 2. Reproduce the 100 MB OOM and the allowDiskUse fix
mongosh shop --eval '
  try {
    db.events.aggregate([ { $group: { _id: "$userId", c: { $sum: 1 } } } ]);
  } catch (e) {
    print("OOM: " + e.code + " — " + e.codeName);   // 292 — QueryExceededMemoryLimitNoDiskUseAllowed
  }
  // Fix:
  db.events.aggregate([ { $group: { _id: "$userId", c: { $sum: 1 } } } ], { allowDiskUse: true });
'

# 3. Verify the ESR rule — measure IXSCAN vs COLLSCAN
mongosh shop --eval '
  db.events.createIndex({ userId: 1, type: 1, ts: 1 });
  const q = { userId: ObjectId("65a1f2c3b8d8e9a4f1b2c3d4"),
```
