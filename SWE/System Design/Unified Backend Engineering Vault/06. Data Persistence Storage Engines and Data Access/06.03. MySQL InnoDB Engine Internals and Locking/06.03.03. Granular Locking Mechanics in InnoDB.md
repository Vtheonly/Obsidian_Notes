# 06.03.03. Granular Locking Mechanics in InnoDB

## What This Is

InnoDB's locking model is the most complex part of the engine, and the source of most production MySQL outages that are not hardware failures. Unlike PostgreSQL (which uses MVCC for reads and only locks on writes), InnoDB under `REPEATABLE READ` (the default) uses locking reads extensively — every `SELECT ... FOR UPDATE`, every range predicate, every foreign-key check acquires locks that can block other transactions. The locks come in four types (record, gap, next-key, intention) and they interact in non-obvious ways that produce deadlocks, lock wait timeouts, and the dreaded "INSERT blocked by a SELECT" surprise. This note covers the lock types, the explicit locking operations, deadlock detection, and the configuration knobs that govern lock waits. Every section ends with the production failure mode it causes.

## The Details

### Lock types: Shared Locks (S), Exclusive Locks (X), Intention Locks (IS, IX)

InnoDB uses a multi-granular locking scheme with two basic modes (shared and exclusive) at three granularities (table, page, row). The four combinations produce four lock types that the engine acquires internally based on the SQL statement.

```text
InnoDB lock compatibility matrix:
─────────────────────────────────────────────────────────────
                 Requested:  IS      IX      S       X
Currently held:
  IS                          ✓       ✓       ✓       ✗
  IX                          ✓       ✓       ✗       ✗
  S                           ✓       ✗       ✓       ✗
  X                           ✗       ✗       ✗       ✗

Lock types:
  IS  (Intention Shared)   — table-level, indicates this transaction
                             intends to take S locks on rows.
  IX  (Intention eXclusive) — table-level, indicates this transaction
                              intends to take X locks on rows.
  S   (Shared)             — row-level, used by SELECT ... FOR SHARE
                             and foreign-key checks. Allows other
                             readers, blocks writers.
  X   (eXclusive)          — row-level, used by INSERT, UPDATE, DELETE,
                             SELECT ... FOR UPDATE. Blocks everything.
```

The **intention locks** (IS, IX) are table-level markers that exist to make deadlock detection efficient. Without them, a transaction trying to take an X lock on the entire table (e.g. `LOCK TABLES users WRITE`) would have to scan every row's lock list to confirm no row was locked. With intention locks, the table-level lock just checks the table's intention lock — if any IX exists, some transaction holds row-level X locks, and the table-level lock must wait. Intention locks do not block each other (IS is compatible with IX); they only conflict with full-table S and X locks. You will almost never see intention locks directly in production — they are an internal optimisation.

The **shared lock (S)** is acquired by `SELECT ... FOR SHARE` (or `LOCK IN SHARE MODE` in older MySQL), by foreign-key checks (the parent row gets an S lock when a child row is inserted), and by `REPEATABLE READ` locking reads in some scenarios. An S lock allows other transactions to also take S locks on the same row, but blocks X locks. Multiple readers can coexist; writers must wait.

The **exclusive lock (X)** is acquired by every `INSERT`, `UPDATE`, `DELETE`, `SELECT ... FOR UPDATE`, and `LOCK TABLES ... WRITE`. It blocks both S and X locks from other transactions on the same row. The lock is held until the transaction commits or rolls back — there is no early release.

```sql
-- Two transactions demonstrating S vs X blocking:

-- Session 1:
BEGIN;
SELECT * FROM accounts WHERE id = 1 FOR SHARE;   -- acquires S lock on row 1

-- Session 2:
BEGIN;
UPDATE accounts SET balance = balance + 10 WHERE id = 1;   -- waits for S lock

-- Session 1:
COMMIT;   -- releases S lock

-- Session 2 (now proceeds):
-- Query OK, 1 row affected (3.21 sec)
```

The production failure mode here is **foreign-key lock contention**. When you `INSERT` into a child table with a foreign key to a parent table, InnoDB takes an S lock on the parent row (to prevent it from being deleted while the child references it). If the parent table is hot (many concurrent inserts into the child), these S locks can pile up and block writers to the parent. The fix is to ensure the parent's primary key lookups are fast (the S lock is a record lock, taken on the index entry) and to consider disabling foreign-key checks during bulk loads.

### Row-Level Locking algorithms

InnoDB's row-level locks are not stored with the rows they lock — they are stored in a separate in-memory structure called the lock system, indexed by `(space_id, page_no)` and then by the index record within the page. The locks are not bit flags on the records themselves; they are entries in a hash table that the engine consults on every record access. This design avoids bloating the page format and makes lock acquisition O(1) for the common case (no existing lock on the page).

There are three "flavours" of row-level lock, distinguished by what they lock: the record itself, the gap before the record, or both. The choice is made by the engine based on the isolation level, the query type, and the predicate. Under `READ COMMITTED`, only record locks are used (no gap locks). Under `REPEATABLE READ` (the InnoDB default), gap and next-key locks are used to prevent phantom reads.

```text
Lock record structure (in the lock system hash table):
┌─────────────────────────────────────────────────────────────┐
│ Lock entry:                                                 │
│   space_id, page_no   ← which page                          │
│   heap_no              ← which record within the page        │
│   trx_id              ← which transaction holds this lock    │
│   mode                ← S, X, or intention                  │
│   type                ← RECORD, GAP, NEXT_KEY                │
│   waiting             ← is this transaction waiting for it?  │
└─────────────────────────────────────────────────────────────┘

The lock system is a hash table keyed by (space_id, page_no),
with each bucket containing a linked list of lock entries for
that page. Acquiring a lock is: hash the page, walk the list,
check compatibility. O(page lock count) per access.
```

The lock system has a fixed-size buffer (`innodb_buffer_pool_size` includes it) and can run out of space on workloads with millions of locks. The error `ERROR 1206 (HY000): The total number of locks exceeds the lock table size` is the symptom; the fix is to raise `innodb_buffer_pool_size` (because the lock table scales with the buffer pool). This is rare in practice — most workloads acquire at most thousands of locks per transaction — but it does happen on bulk updates that touch many rows.

### Record Locks: Locking specific index records

A **record lock** locks a single index record. It is the simplest lock type and the only type used under `READ COMMITTED`. A record lock on the entry for `id=1` in the primary key index prevents any other transaction from updating or deleting row 1, but does not prevent inserting new rows with adjacent IDs.

```text
Record lock on id=10 (under READ COMMITTED):

Index:  [ 10 | 20 | 30 | 40 ]
              ↑
              X record lock held by T1

T2 can:   INSERT id=15  (allowed — no lock on the gap)
T2 can:   INSERT id=10  (allowed only if T1's lock is S not X)
T2 cannot: UPDATE id=10 (blocked by X lock)
T2 cannot: DELETE id=10 (blocked by X lock)
```

Record locks are taken on the index entry, not on the heap row. This means a `SELECT ... FOR UPDATE WHERE id = 10` that uses the primary key index acquires one record lock on the primary key index entry — fast and cheap. The same query without an index on `id` would do a full table scan and acquire a record lock on every row of the table — a disaster. This is why `SELECT ... FOR UPDATE` without a matching index is so dangerous: it locks the entire table.

### Gap Locks: Locking the open space between index records to eliminate phantom inserts

A **gap lock** locks the space between two index records (or before the first, or after the last), preventing inserts into that gap. Gap locks exist to prevent phantom reads under `REPEATABLE READ`. If transaction T1 does `SELECT * FROM t WHERE id BETWEEN 10 AND 20 FOR UPDATE`, InnoDB locks the gaps `(−∞, 10), (10, 20), (20, +∞)` so that no other transaction can insert a row with id=15 (which would be a phantom when T1 re-reads the range).

```text
Gap locks (under REPEATABLE READ):

Index:  [ 10 | 20 | 30 | 40 ]
         ↑    ↑    ↑    ↑
Gap locks:
  (−∞, 10)   — gap before the first record
  (10, 20)   — gap between 10 and 20
  (20, 30)   — gap between 20 and 30
  (30, 40)   — gap between 30 and 40
  (40, +∞)   — gap after the last record

T1: SELECT * FROM t WHERE id BETWEEN 15 AND 25 FOR UPDATE
    → acquires gap locks on (10, 20), (20, 30), and next-key
      locks on records 20 and 30.

T2: INSERT INTO t (id) VALUES (17)
    → blocked (would go into gap (10, 20) which is locked)

T2: INSERT INTO t (id) VALUES (50)
    → allowed (gap (40, +∞) is not locked by T1's predicate)
```

Gap locks are surprising because they can block inserts that do not match any existing row. A transaction that does `SELECT * FROM users WHERE email = 'alice@example.com' FOR UPDATE` (under `REPEATABLE READ`) acquires a gap lock on the gap around where `'alice@example.com'` would go — even if that email does not exist in the table. This is necessary for phantom prevention: if the row does not exist now, the lock prevents another transaction from inserting it. But it means a `SELECT ... FOR UPDATE` on a non-existent row can block inserts of that row.

Gap locks are mutually compatible: two transactions can both hold gap locks on the same gap (because a gap lock's purpose is to prevent inserts, and neither transaction is trying to insert). The conflict only arises when one transaction tries to insert into a gap that another transaction has locked. This is why a `SELECT ... FOR UPDATE` on a range rarely blocks another `SELECT ... FOR UPDATE` on the same range — they both acquire gap locks, but gap locks don't conflict with each other. The conflict shows up when one transaction tries to INSERT.

### Next-Key Locks: Record Lock + Gap Lock combined (InnoDB default in Repeatable Read)

A **next-key lock** is the combination of a record lock on a record and a gap lock on the gap before that record. It is InnoDB's default locking granularity under `REPEATABLE READ`. The name comes from the fact that it locks "the next key" — the record and the gap before it, so that no insert can occur in the gap and no modification can occur on the record.

```text
Next-key locks (InnoDB REPEATABLE READ default):

Index:  [ 10 | 20 | 30 | 40 ]
          ↓    ↓    ↓    ↓
Next-key:  [10] [20] [30] [40]
          =   =    =    =
        rec+gap rec+gap rec+gap rec+gap
        before  before before before
         10     20     30     40
       (i.e. (−∞,10]) (i.e. (10,20]) ...

T1: SELECT * FROM t WHERE id = 25 FOR UPDATE
    → acquires next-key lock on [30] (which covers gap (20,30)
      and record 30).

T2: INSERT INTO t (id) VALUES (25)
    → blocked (gap (20, 30) is locked)

T2: UPDATE t SET x = 1 WHERE id = 30
    → blocked (record 30 is locked)

T2: INSERT INTO t (id) VALUES (15)
    → allowed (gap (10, 20) is not locked by T1's predicate)
```

Next-key locking is what makes InnoDB's `REPEATABLE READ` actually prevent phantom reads — a deviation from the SQL standard, which says `REPEATABLE READ` allows phantoms. PostgreSQL's `REPEATABLE READ` (which is really Snapshot Isolation) prevents phantoms differently — by giving each transaction a snapshot of the data, so newly-inserted rows are invisible. The trade-off: InnoDB's approach uses locks and can cause contention; PostgreSQL's approach uses snapshots and can cause write skew (06.04.02).

The production failure mode of next-key locks is **insert contention on a sequential key**. If two transactions concurrently do `INSERT INTO orders (...) VALUES (...)` where `orders.id` is `AUTO_INCREMENT`, they both try to take next-key locks on the rightmost gap of the index. InnoDB serialises these with a special `AUTO-INC` lock (controlled by `innodb_autoinc_lock_mode`, default 2 in MySQL 8 = "interleaved" mode, which avoids the table-level lock for simple inserts). With the default mode, bulk inserts and single-row inserts can interleave safely, but `INSERT ... SELECT` with a large result set may still take the table-level AUTO-INC lock.

### Explicit locking operations: `SELECT ... FOR UPDATE` (Pessimistic Write Lock) vs. `SELECT ... FOR SHARE` (Pessimistic Read Lock)

InnoDB provides explicit locking SELECTs that acquire X or S locks on the matched rows. These are the locking reads, and they are the mechanism for pessimistic concurrency control — the application explicitly locks rows it intends to modify, ensuring no other transaction can interfere.

```sql
-- Pessimistic write lock: use when you intend to update the row
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;   -- X lock
-- ... application computes new balance ...
UPDATE accounts SET balance = 400 WHERE id = 1;
COMMIT;

-- Pessimistic read lock: use when you need to read consistent
-- data and prevent others from modifying it (rare in OLTP)
BEGIN;
SELECT COUNT(*) FROM accounts WHERE balance > 1000 FOR SHARE;   -- S lock
-- ... guaranteed no transaction can change a balance to/from
--     >1000 while we hold the lock ...
COMMIT;

-- SKIP LOCKED: skip rows that are already locked (queue pattern)
SELECT * FROM jobs WHERE status = 'pending' LIMIT 1 FOR UPDATE SKIP LOCKED;
-- Returns immediately with the first unlocked pending job.
-- Used for concurrent work-queue consumption.

-- NOWAIT: fail immediately if any row is locked
SELECT * FROM accounts WHERE id = 1 FOR UPDATE NOWAIT;
-- ERROR 3572 (HY000): Statement aborted because lock(s) could
-- not be acquired immediately and NOWAIT is set.
```

`SELECT ... FOR UPDATE` is the most common explicit lock. Its semantics: take X locks on every row that matches the WHERE clause, hold them until COMMIT. If the WHERE clause does not match an index, this locks the entire table (because the engine must scan every row, and each scanned row gets a lock). This is the source of countless production outages: a developer writes `SELECT ... FOR UPDATE WHERE non_indexed_column = 'x'`, runs it on a million-row table, and locks the whole table for the duration of the transaction.

The `SKIP LOCKED` clause (MySQL 8.0+, PostgreSQL 9.5+) is the modern way to build a work queue inside the database. Multiple worker processes can each call `SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1` on the jobs table; each gets a different unlocked row, with no contention. Without `SKIP LOCKED`, the workers would block each other on the first row.

### Deadlock Detection: Wait-For Graphs, transaction cost comparisons, and automatic victim rollback

A **deadlock** is a cycle in the lock-wait graph: T1 holds a lock that T2 is waiting for, and T2 holds a lock that T1 is waiting for. Neither can proceed; without intervention, both would wait forever. InnoDB detects deadlocks automatically and breaks them by rolling back one of the transactions (the "victim"). The detection runs in a background thread that periodically builds the wait-for graph and searches for cycles.

```text
Deadlock scenario:

T1: BEGIN;
    UPDATE accounts SET balance = balance - 100 WHERE id = 1;
    -- T1 holds X lock on row 1

T2: BEGIN;
    UPDATE accounts SET balance = balance - 100 WHERE id = 2;
    -- T2 holds X lock on row 2

T1: UPDATE accounts SET balance = balance + 100 WHERE id = 2;
    -- T1 waits for T2's X lock on row 2

T2: UPDATE accounts SET balance = balance + 100 WHERE id = 1;
    -- T2 waits for T1's X lock on row 1
    -- DEADLOCK detected!

InnoDB picks the victim (the transaction that has done less work,
measured by rows modified). Let's say T2 is the victim:

T2: ERROR 1213 (40001): Deadlock found when trying to get lock;
    try restarting transaction
    -- T2 is rolled back automatically.

T1: -- T1's UPDATE now proceeds (T2 released its locks).
```

The victim selection is based on the transaction's "weight" — the number of rows modified, plus a small constant. The lighter transaction is rolled back because it has less work to redo. This is a heuristic that minimises total wasted work, but it can surprise developers who expect "first writer wins" — instead, "smaller writer loses." The victim selection can be influenced by `innodb_deadlock_detect` (default ON, can be turned off on high-throughput systems where the detection overhead itself becomes a bottleneck) and by `innodb_lock_wait_timeout` (default 50 seconds — how long a transaction waits before giving up on a single lock, which is *different* from deadlock detection).

The classic deadlock pattern in production is `INSERT INTO ... SELECT`. If T1 runs `INSERT INTO archive SELECT * FROM current WHERE date < '2024-01-01'`, it acquires shared locks (or gap locks) on every row in `current` that matches. If T2 concurrently runs `INSERT INTO current VALUES (...)`, it may need a lock on a gap that T1 holds — deadlock. The fix is to use `INSERT INTO archive SELECT * FROM current WHERE date < '2024-01-01' FOR UPDATE` (taking X locks upfront so T2 waits cleanly) or to process the rows in smaller batches with `LIMIT` and `ORDER BY id`.

The production discipline for InnoDB deadlocks has three parts. First, **always lock rows in a consistent order** — if every transaction that touches rows 1 and 2 locks them in the order 1 then 2, no deadlock cycle can form. Second, **make sure `SELECT ... FOR UPDATE` predicates match indexes** — a non-indexed FOR UPDATE is a table lock and a deadlock factory. Third, **handle deadlock errors in the application** — the error 1213 is retryable, and any well-written transactional application should retry the whole transaction on this error. Frameworks like Spring's `@Retryable` and Rails' `transaction(requires_new: true)` provide this out of the box.

```text
Key InnoDB locking tunables:
─────────────────────────────────────────────────────────────
innodb_lock_wait_timeout = 50          (seconds; how long a
                                        transaction waits for a
                                        single row lock before
                                        giving up with error
                                        1205 LOCK_WAIT_TIMEOUT)
innodb_deadlock_detect = ON            (background cycle
                                        detection; turn OFF only
                                        on very high-throughput
                                        systems where the
                                        detection itself is the
                                        bottleneck — then set
                                        innodb_lock_wait_timeout
                                        low to catch deadlocks)
innodb_print_all_deadlocks = OFF       (set ON to log every
                                        deadlock to the error
                                        log, not just the last)
innodb_status_output_locks = OFF       (include lock info in
                                        SHOW ENGINE INNODB STATUS)
```

## Cross-Ecosystem Implementation

| Aspect | InnoDB | PostgreSQL |
|---|---|---|
| Default isolation | REPEATABLE READ (with next-key locks) | READ COMMITTED |
| Phantom prevention | Next-key gap locks | Snapshot isolation (no locks) |
| Deadlock detection | Automatic wait-for graph | Automatic (at lock acquisition time) |
| Lock wait timeout | 50 sec (innodb_lock_wait_timeout) | 1 sec (deadlock_timeout) |
| SKIP LOCKED | MySQL 8.0+ | PostgreSQL 9.5+ |
| NOWAIT | MySQL 8.0+ | PostgreSQL 9.5+ |
| Work-queue pattern | `SELECT ... FOR UPDATE SKIP LOCKED` | Same |

## Hands-On Exercise

```sql
-- Inspect current locks (MySQL 8)
SELECT * FROM performance_schema.data_locks;
-- INDEX_NAME, LOCK_TYPE, LOCK_MODE, LOCK_STATUS, LOCK_DATA

-- See what each transaction is waiting for
SELECT r.trx_id, r.trx_state, r.trx_started,
       r.trx_mysql_thread_id, r.trx_query,
       b.trx_id AS blocking_trx_id, b.trx_query AS blocking_query
  FROM information_schema.INNODB_TRX r
  LEFT JOIN information_schema.INNODB_TRX b
    ON b.trx_id = (
        SELECT blocking_trx_id
          FROM information_schema.INNODB_LOCK_WAITS
          WHERE requesting_trx_id = r.trx_id LIMIT 1);

-- Force a deadlock (two sessions):
-- Session 1:
BEGIN;
UPDATE accounts SET balance = balance - 10 WHERE id = 1;
-- Session 2:
BEGIN;
UPDATE accounts SET balance = balance - 10 WHERE id = 2;
-- Session 1:
UPDATE accounts SET balance = balance + 10 WHERE id = 2;
-- Session 2:
UPDATE accounts SET balance = balance + 10 WHERE id = 1;
-- → One session gets error 1213, the other succeeds.

-- See the last deadlock in detail
SHOW ENGINE INNODB STATUS\G
-- Look under "LATEST DETECTED DEADLOCK" for the cycle.

-- Work queue with SKIP LOCKED
SELECT id, payload FROM jobs
  WHERE status = 'pending'
  ORDER BY id
  LIMIT 1
  FOR UPDATE SKIP LOCKED;
-- Multiple workers can call this concurrently without blocking.
```
