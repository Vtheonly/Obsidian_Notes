# 06.03.02. InnoDB MVCC and Rollback Segments

## What This Is

InnoDB implements MVCC differently from PostgreSQL. Where PostgreSQL appends a new row version to the table on every UPDATE (06.02.02), InnoDB updates the row **in place** and writes the old row image to a separate on-disk structure called the **undo log** (or rollback segment). Readers that need an older version follow a chain of undo log records to reconstruct the row as it was at their snapshot. This design trades read-side work (reconstructing old versions on demand) for write-side simplicity (a single in-place update) and storage compactness (old versions live in the undo log, not bloating the main table). This note covers the in-place update mechanism, the hidden row fields that anchor the version chain, the read view mechanism that decides visibility, and the purge threads that reclaim undo log space when no one needs it anymore.

## The Details

### In-place mutation with Undo Logging: InnoDB updates data pages in-place and writes reverse delta records to the Undo Log

When `UPDATE accounts SET balance = balance + 100 WHERE id = 1` executes, InnoDB does not insert a new row into the `accounts` table. Instead, it (a) reads the existing row's page into the buffer pool if it is not already there, (b) takes an exclusive lock on the row, (c) writes the *old* row image to the undo log as a reverse-delta record, (d) modifies the row's `balance` column in place on the page, and (e) writes a redo log record covering both the undo log append and the data page modification. The page is now "dirty" and will be flushed to disk later by the page cleaner threads.

```text
InnoDB UPDATE sequence:

  T1: UPDATE accounts SET balance = balance + 100 WHERE id = 1;

  Step 1: Read page 42 (containing row id=1) into buffer pool.
  Step 2: Acquire X lock on row id=1 (record lock on the index entry).
  Step 3: Write undo log record:
          undo_record = { trx_id=T1, type=UPDATE,
                          old_row_image = { id=1, balance=500, ... },
                          rollback_ptr = previous_undo_ptr }
  Step 4: Modify the row in place on page 42:
          balance column: 500 → 600
          row's DB_TRX_ID: previous_xid → T1
          row's DB_ROLL_PTR: → undo_record (from step 3)
  Step 5: Write redo log record:
          redo = { LSN=N, page=42, offset=K, new_bytes=... }
          (covers both the undo log page write AND the data page
           write — both must be redo-logged for crash safety)
  Step 6: On commit, write commit record to redo log, fsync.
          The undo log record stays until purge reclaims it.
```

The undo log is a sequence of "reverse operations" — for an UPDATE, it stores the old row image so that recovery can roll back; for an INSERT, it stores a "delete this row" marker; for a DELETE, it stores the deleted row image so recovery can re-insert it. These undo records form a chain anchored at the row's `DB_ROLL_PTR`. A reader that needs an older version of the row starts at the current row, follows `DB_ROLL_PTR` to the first undo record, checks if that record's `trx_id` is visible to the reader's snapshot; if not, follows the record's `rollback_ptr` to the previous undo record, and so on back through history until a visible version is found.

This design has three consequences that differ from PostgreSQL's append-only MVCC. First, the main table does not bloat with old versions — only the undo log does, and the undo log can be in its own tablespace (since MySQL 8) and truncated when it grows too large. Second, the read path can be slower for transactions that need old versions: instead of a single row read, the reader must follow the undo chain, potentially reading multiple undo pages from disk. Third, the write path is simpler and faster for a single-row update: one in-place page modification plus one undo log append, vs. PostgreSQL's insert-new-tuple-plus-update-indexes (though HOT updates reduce that cost).

### Hidden row fields: `DB_TRX_ID` (Transaction ID), `DB_ROLL_PTR` (Pointer to Undo Log record), `DB_ROW_ID`

Every InnoDB row has three hidden fields that the engine uses for MVCC and indexing. They are not visible in `SELECT *` output, but they are present in the row's on-disk format and they are visible through `SHOW EXTENDED COLUMNS` or by inspecting the page directly.

```text
InnoDB row layout (in a 16 KB page):
┌──────────────────────────────────────────────────────────────┐
│ Record header (variable, ~5 bytes per row)                  │
│   - next_rec offset (linked list of records in the page)    │
│   - info flags (deleted, min_rec, etc.)                     │
├──────────────────────────────────────────────────────────────┤
│ DB_TRX_ID   (6 bytes): xid of the transaction that last     │
│                        modified this row.                   │
│ DB_ROLL_PTR (7 bytes): pointer to the most recent undo log  │
│                        record for this row. Format:         │
│                        (segment_id, page_no, offset).       │
│ DB_ROW_ID   (6 bytes): only present if the table has no     │
│                        explicit primary key. InnoDB uses    │
│                        this as a hidden clustered key.      │
├──────────────────────────────────────────────────────────────┤
│ User column data (variable)                                 │
└──────────────────────────────────────────────────────────────┘

Total MVCC overhead per row: 6 + 7 = 13 bytes (DB_ROW_ID only
present if no explicit primary key — another reason to always
declare a primary key).
```

`DB_TRX_ID` is the 6-byte transaction ID of the transaction that last modified the row. InnoDB's transaction IDs are 48-bit (not 32-bit like PostgreSQL's), so they never wrap around — InnoDB does not have PostgreSQL's `txid` wraparound problem. A reader compares the row's `DB_TRX_ID` against its read view's list of visible transactions to decide whether the current version of the row is visible.

`DB_ROLL_PTR` is a 7-byte pointer to the most recent undo log record for this row. The format is `(undo_segment_id, page_number_within_segment, offset_within_page)`. Following this pointer leads to the previous version of the row, encoded as an undo record. The undo record itself contains a `rollback_ptr` to the undo record before it, forming the version chain.

`DB_ROW_ID` is the hidden primary key that InnoDB generates if you create a table without an explicit primary key. It is a 6-byte monotonically increasing integer. **This is a production footgun**: a table without an explicit primary key gets a hidden one, and InnoDB's replication (statement-based and row-based) and the change buffer both work less efficiently on hidden-key tables. Always declare a primary key — even an `id BIGINT AUTO_INCREMENT` is better than letting InnoDB generate `DB_ROW_ID`.

The visibility algorithm mirrors PostgreSQL's:

```text
def innodb_visible(row, read_view):
    trx_id = row.DB_TRX_ID
    if trx_id == read_view.creator_trx_id:
        # This row was modified by us. Visible (within our own
        # transaction's changes).
        return True
    if trx_id < read_view.up_limit_id:
        # The modifying transaction committed before our read
        # view was taken. Visible.
        return True
    if trx_id >= read_view.low_limit_id:
        # The modifying transaction started after our read view
        # was taken. Invisible.
        return False
    if trx_id in read_view.active_trx_ids:
        # The modifying transaction was active when our read view
        # was taken. Invisible.
        return False
    return True  # committed before our snapshot
```

If the current version is invisible, the reader follows `DB_ROLL_PTR` to the undo log, reconstructs the previous row version, and repeats the visibility check on that version. This loop terminates because every row has an original INSERT version whose `DB_TRX_ID` is either visible (the INSERT committed before our snapshot) or invisible (the INSERT happened after, in which case the row should not exist for us at all).

### Purge Threads: Asynchronously garbage-collecting undo log pages when oldest active read snapshots no longer reference them

The undo log grows monotonically with every UPDATE and DELETE. Without a cleanup mechanism, it would consume all available disk space within hours on a busy server. **Purge threads** are InnoDB's background workers that reclaim undo log space when it is no longer needed.

```text
Purge thread logic:

  Periodically (every innodb_purge_rseg_truncate_frequency seconds,
  default 128):
    1. Find the oldest active read view's trx_id — call it
       "purge_trx_id".
    2. For each undo log record:
       - If the record's trx_id < purge_trx_id, the modifying
         transaction committed before the oldest active read view.
         No active transaction needs this undo record. Reclaim it.
       - If the record's trx_id >= purge_trx_id, an active
         transaction might still need it. Stop purging this
         segment.
    3. When an undo segment's pages are all reclaimable, the
       segment can be truncated (MySQL 8: innodb_undo_log_truncate
       = ON by default).
```

The key invariant: **the undo log can only be purged up to the oldest active transaction's snapshot.** A single long-running `SELECT` (or a connection that is `IDLE IN TRANSACTION`) blocks all purge for all tables, and the undo log grows until disk fills up. This is the InnoDB equivalent of PostgreSQL's "long-running query kills the server" — same root cause (MVCC needs old versions for old snapshots), different storage location (undo log vs. dead tuples in the table).

The history list length, visible in `SHOW ENGINE INNODB STATUS` under `TRANSACTIONS`, is the count of unpurged undo log records. A steady-state value below 1000 is healthy; a value growing past 100,000 means purge is falling behind, usually because of a long-running transaction. The query `SELECT * FROM information_schema.INNODB_TRX ORDER BY trx_started ASC LIMIT 5;` shows the oldest active transactions, which are the culprits.

```text
InnoDB purge-related metrics and tunables:
─────────────────────────────────────────────────────────────
SHOW ENGINE INNODB STATUS\G
---
TRANSACTIONS
------------
Trx id counter 12345678
Purge done for trx's n:o < 12340000 undo n:o < 0 state: running
History list length 1500      ← unpurged undo records
LIST OF TRANSACTIONS FOR EACH SESSION:
---TRANSACTION 12339999, ACTIVE 3500 sec   ← long-running tx!
mysql tables in use 1, locked 0
MySQL thread id 42, OS thread handle 0x..., query id 12345 ...
0000 SELECT /* long running report */ ...

Tunables:
  innodb_purge_batch_size (default 300) — undo log pages per purge batch
  innodb_purge_threads (default 4) — parallel purge workers
  innodb_max_purge_lag (default 0, unlimited) — delay DML when
    history list exceeds this; protects against runaway purge lag.
  innodb_max_purge_lag_delay (default 300000, microseconds) — max
    delay per DML operation.
```

The purge threads are also responsible for removing the "delete-marked" rows from secondary indexes. When you `DELETE FROM users WHERE id = 1`, InnoDB does not immediately remove the row from each secondary index — it marks the row's `info_flags` as deleted, and the purge thread physically removes the index entry later. This deferred cleanup is what allows the delete to be fast (one in-place modification + one undo log record) and what allows the row to remain visible to existing read views. Without purge, the indexes would bloat with delete-marked entries just as PostgreSQL's tables bloat with dead tuples — same problem, different storage.

The production failure mode is the same in both engines: **MVCC bloat from a long-running transaction.** The fix is identical: monitor for long-running transactions (`INNODB_TRX` for InnoDB, `pg_stat_activity` for PostgreSQL), kill them when they exceed a threshold, and use a connection pool that closes idle connections. The architectural difference (append-only table vs. undo log) is invisible to the operator — both produce the same operational headache, and both respond to the same operational discipline.

## Cross-Ecosystem Implementation

| Aspect | InnoDB | PostgreSQL |
|---|---|---|
| Old row version stored in | Undo log (separate tablespace) | Same table (dead tuple) |
| Update mechanism | In-place mutation | Append new tuple |
| Hidden row fields | DB_TRX_ID, DB_ROLL_PTR, DB_ROW_ID | xmin, xmax, t_ctid, infomask |
| Transaction ID size | 48-bit (no wraparound) | 32-bit (must freeze) |
| Cleanup mechanism | Purge threads (asynchronous) | VACUUM / autovacuum |
| Cleanup trigger | History list exceeds threshold | Dead tuples exceed threshold |
| Long-running query impact | Undo log grows (separate space) | Table grows with dead tuples |
| Default isolation | REPEATABLE READ (with next-key locks) | READ COMMITTED |

## Hands-On Exercise

```sql
-- See the hidden columns via the InnoDB internals
-- (requires the InnoDB_sample plugin or mysqlbinlog for undo inspection)

-- See active transactions and how long they have been running
SELECT trx_id, trx_state, trx_started, trx_mysql_thread_id,
       trx_weight, trx_rows_modified, trx_query
  FROM information_schema.INNODB_TRX
  ORDER BY trx_started ASC;

-- See the history list length (unpurged undo records)
SHOW ENGINE INNODB STATUS\G
-- Look under "TRANSACTIONS" for "History list length N"
-- N < 1000 is healthy. N > 100000 is a problem.

-- See the metadata lock waits (when DDL is blocked by a transaction)
SELECT * FROM performance_schema.metadata_locks
  WHERE object_schema = 'your_db';

-- Force a purge by killing a long-running transaction
KILL <thread_id>;

-- See purge thread activity
SELECT * FROM performance_schema.threads
  WHERE NAME LIKE '%/thread/%/innodb/%purge%';

-- Configure undo log truncation
SHOW VARIABLES LIKE 'innodb_undo_log_truncate';
SHOW VARIABLES LIKE 'innodb_max_undo_log_size';
-- Default: 1 GB. When undo tablespace exceeds this, purge truncates it.
```

```bash
# See the undo log files
ls -la /var/lib/mysql/undo*
# undo001  undo002

# See the redo log files
ls -la /var/lib/mysql/ib_logfile*

# Watch the history list length over time
watch -n 1 "mysql -e 'SHOW ENGINE INNODB STATUS\G' | grep 'History list'"
```
