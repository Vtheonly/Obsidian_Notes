# 06.03.01. MySQL Architecture and the InnoDB Engine

## What This Is

MySQL is a single `mysqld` process that allocates one OS thread per client connection (unlike PostgreSQL's process-per-connection from 06.02.01). Inside that process, MySQL is structured as a layered architecture: the connection handler, the SQL parser, the optimizer, and a pluggable storage-engine API that hands the actual row data off to whichever engine the table was created with — InnoDB, MyISAM, Memory, CSV, Archive, NDB, or any custom engine. Since MySQL 5.5 (2010), InnoDB has been the default engine, and for production OLTP it is effectively the only choice. This note covers the top-level MySQL architecture, the InnoDB memory structures (buffer pool, change buffer, adaptive hash index, log buffer), and the InnoDB disk structures (system tablespace, file-per-table `.ibd` files, doublewrite buffer, redo log, undo log). Understanding this layering is the prerequisite for the MVCC and locking notes that follow.

## The Details

### Multi-threaded architecture: Single process allocating threads per connection

A single `mysqld` process listens on TCP port 3306 (and a Unix socket). For each client connection, it spawns a thread (via `pthread_create` on Linux, mapped 1:1 to OS threads via NPTL). The thread runs the connection's query loop: parse, plan, execute, return. When the client disconnects, the thread is returned to the thread cache (default `thread_cache_size=16`) rather than destroyed, so the next connection reuses it without paying the ~50 µs thread-creation cost.

```text
MySQL process and thread model:

  ┌──────────────────────────────────────────────────────┐
  │                  mysqld (single process)              │
  │                                                       │
  │  ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐    │
  │  │ thread  │ │ thread  │ │ thread  │ │ thread  │    │
  │  │ conn 1  │ │ conn 2  │ │ conn 3  │ │ conn 4  │    │
  │  └────┬────┘ └────┬────┘ └────┬────┘ └────┬────┘    │
  │       │           │           │           │          │
  │       └───────────┴───────────┴───────────┘          │
  │                    │                                 │
  │             ┌──────┴───────┐                         │
  │             │ SQL layer    │  (parser, optimizer,    │
  │             │ (shared)     │   executor)             │
  │             └──────┬───────┘                         │
  │                    │                                 │
  │             ┌──────┴───────┐                         │
  │             │ Storage Eng. │  (pluggable: InnoDB,    │
  │             │ API           │   MyISAM, Memory, ...)  │
  │             └──────┬───────┘                         │
  │                    │                                 │
  │             ┌──────┴───────┐                         │
  │             │ InnoDB       │  (buffer pool, B+tree,  │
  │             │              │   redo log, undo log)   │
  │             └──────────────┘                         │
  │                                                       │
  │  Background threads:                                  │
  │   - Master thread (checkpoint + purge)                │
  │   - IO read threads (default 4)                       │
  │   - IO write threads (default 4)                      │
  │   - Purge threads (default 4)                         │
  │   - Page cleaner threads (default 1)                  │
  └──────────────────────────────────────────────────────┘
```

Compared to PostgreSQL's process-per-connection, MySQL's thread-per-connection uses dramatically less memory (~256 KB of stack per thread vs. PostgreSQL's ~5-10 MB of RSS per backend), can scale to thousands of connections without exhausting RAM, and has cheaper context switches (thread switches are ~5× faster than process switches on Linux). The cost is shared failure: a thread that segfaults takes the whole mysqld process down, losing every connection. PostgreSQL's process model isolates crashes; MySQL's thread model pays for scalability with crash vulnerability. The MySQL team's response is the "thread pool" plugin (commercial / enterprise feature) which limits the number of active threads and queues the rest — functionally equivalent to a connection pool, but inside the server.

The pluggable storage-engine API is MySQL's distinctive architectural choice. A `CREATE TABLE ... ENGINE=InnoDB` (or `MyISAM`, or `Memory`) decides which engine stores the table's bytes; the SQL layer above is the same for all engines. This was a 1990s decision to let users pick the right engine per table — InnoDB for transactions, MyISAM for read-heavy tables with no transactions, Memory for ephemeral data. In practice, InnoDB has won: it has transactions, row-level locking, foreign keys, and crash recovery, and since 5.5 it is the default. MyISAM's table-level locks and lack of crash recovery make it unsuitable for anything but read-only archives. The lesson: pluggable engines sound great in theory, but the network effects of one good engine (InnoDB) dominate, and the others become legacy.

### InnoDB Memory Structures: Buffer Pool (data pages, index pages, change buffer, adaptive hash index), Log Buffer

InnoDB's memory is dominated by the **buffer pool** — a large region of RAM that caches data and index pages from disk. The buffer pool is the single most important InnoDB tunable; the standard advice is to give it 50-75% of system RAM on a dedicated server. Inside the buffer pool, four logical sub-structures cooperate:

```text
InnoDB buffer pool internal structure:
┌────────────────────────────────────────────────────────────┐
│ Buffer Pool (innodb_buffer_pool_size, default 128 MB)      │
│                                                            │
│  ┌──────────────────────────────────────────────────────┐  │
│  │ LRU list (modified clock algorithm):                 │  │
│  │   ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐               │  │
│  │   │ old  │→│ old  │→│ new  │→│ new  │ → ... (MRU)   │  │
│  │   │ (3/8)│ │      │ │ (5/8)│ │      │               │  │
│  │   └──────┘ └──────┘ └──────┘ └──────┘               │  │
│  │   ↑                                       ↑          │  │
│  │   insert here                     promoted after      │  │
│  │   (newly read pages)              innodb_old_blocks_  │  │
│  │                                   time (1 sec)        │  │
│  └──────────────────────────────────────────────────────┘  │
│                                                            │
│  ┌──────────────────────┐  ┌─────────────────────────┐    │
│  │ Change Buffer        │  │ Adaptive Hash Index     │    │
│  │ (buffers changes to  │  │ (auto-built hash index  │    │
│  │  non-unique secondary│  │  on frequently-accessed │    │
│  │  index pages, merges │  │  pages, bypasses B-tree │    │
│  │  them lazily)        │  │  lookup)                │    │
│  └──────────────────────┘  └─────────────────────────┘    │
└────────────────────────────────────────────────────────────┘

Log Buffer (innodb_log_buffer_size, default 16 MB)
  - Holds redo log records before they are flushed to the redo
    log file.
  - Flushed every second (master thread), or on transaction
    commit (controlled by innodb_flush_log_at_trx_commit), or
    when half full.
```

The LRU list uses a midpoint insertion strategy: newly-read pages go into the "old" sublist (the last 3/8 of the LRU), not the head. A page is promoted to the "new" sublist only if it is accessed again after `innodb_old_blocks_time` (default 1 second). This prevents a full table scan from blowing out the buffer pool — the scan's pages go to old, get evicted before they reach new, and the hot working set stays cached. PostgreSQL's clock-sweep buffer achieves the same effect with different mechanics.

The **change buffer** is an InnoDB-specific optimisation for non-unique secondary index updates. When a `INSERT`/`UPDATE`/`DELETE` modifies a secondary index page that is not currently in the buffer pool, InnoDB does not read the page from disk — it records the change in the change buffer and merges it later, when the page is next read for some other reason. This converts a random read-modify-write into a deferred sequential merge, dramatically speeding up insert-heavy workloads on tables with many secondary indexes. The change buffer is stored in the system tablespace (`ibdata1`) and survives restarts.

The **adaptive hash index** (AHI) is InnoDB's runtime self-tuning. When it notices that a particular index page is being accessed by equality lookups many times, it builds an in-memory hash table mapping the lookup key directly to the page's buffer pool address — bypassing the B-tree descent. The AHI is automatic and requires no configuration, but it has a contested reputation: on high-concurrency workloads, the AHI's internal mutex becomes a contention point, and disabling it (`innodb_adaptive_hash_index=off`) sometimes improves throughput. The lesson: nothing in a database is free, and "automatic" optimisations have their own failure modes.

### InnoDB Disk Structures: System Tablespace, File-Per-Table Tablespaces (`.ibd`), Doublewrite Buffer, Redo Log files, Undo Log files

InnoDB's on-disk layout is a mix of shared and per-table files. The defaults have changed over MySQL versions; modern MySQL 8 uses `innodb_file_per_table=ON` by default, so each new table gets its own `.ibd` file. The shared system tablespace (`ibdata1`) holds the data dictionary, the change buffer, the doublewrite buffer, and (in older versions) the undo log.

```text
InnoDB on-disk files (typical MySQL 8 layout):

/var/lib/mysql/
├── ibdata1                  System tablespace
│                            - data dictionary
│                            - change buffer
│                            - doublewrite buffer
│                            - (optionally) undo log
├── ib_logfile0              Redo log file 1 (circular)
├── ib_logfile1              Redo log file 2 (circular)
│                            (innodb_log_files_in_group, default 2)
│                            (innodb_log_file_size, default 48 MB;
│                             MySQL 8 default 4 GB total)
├── ib_buffer_pool           Buffer pool dump on shutdown (warm restart)
├── mysql/                   System database (users, grants)
│   └── *.ibd
├── your_db/
│   ├── users.ibd            File-per-table tablespace for users
│   ├── orders.ibd           File-per-table tablespace for orders
│   └── ...
├── undo001                  Undo log files (MySQL 8 default:
├── undo002                  innodb_undo_tablespaces=2)
└── #ib_*.ibd                System schemas (data dictionary in MySQL 8)
```

The **doublewrite buffer** is a peculiar InnoDB feature that exists to defend against partial page writes. The problem: if the database crashes while writing a 16 KB page to disk, the disk may end up with only the first 8 KB written (a "torn page"). The WAL redo log cannot fix this because redo is idempotent only if the page is consistent — applying redo to a half-written page produces garbage. InnoDB's solution: before writing a dirty page to its final location in the `.ibd` file, write it first to a contiguous area in `ibdata1` called the doublewrite buffer, then `fsync` that, then write it to the `.ibd` file. If a crash happens during the second write, recovery can read the intact copy from the doublewrite buffer and apply redo to it. The cost is one extra write per dirty page (write amplification ~2×), but the data integrity guarantee is worth it on most workloads. PostgreSQL has a similar concept called `full_page_writes` — at the first modification of a page after a checkpoint, the entire page image is written to the WAL, so recovery can restore the page to a consistent state before applying redo.

The **redo log** is InnoDB's WAL (covered in 06.01.02). It is a pair of fixed-size files that wrap around: `ib_logfile0` and `ib_logfile1`, each `innodb_log_file_size` bytes (default 48 MB on MySQL 5.7, 4 GB on MySQL 8). When the write position catches up to the read position (the oldest unflushed data), InnoDB must flush dirty pages to make room — this is the source of the famous "InnoDB write stall" under heavy write load. The `innodb_log_file_size` should be large enough to hold 1-2 hours of WAL at peak write rate; the standard query to check is `SHOW ENGINE INNODB STATUS` and look at the "Log sequence number" vs "Log flushed up to" delta.

The **undo log** is where InnoDB stores the old versions of rows for MVCC. Unlike PostgreSQL (which leaves old versions in the table itself, see 06.02.02), InnoDB updates rows in place and writes the old row image to the undo log. This is the architectural difference between the two engines: PostgreSQL's append-only MVCC vs InnoDB's in-place-with-undo MVCC. The undo log is consumed by readers (transactions that need to see old versions) and reclaimed by purge threads (when no transaction needs the old version anymore). The undo log size matters because a long-running transaction can grow it unboundedly — same failure mode as PostgreSQL's "idle in transaction", different mechanism. In MySQL 8, the undo log can be in its own tablespaces (`undo001`, `undo002`) and truncated when it grows too large, which mitigates the bloat problem that older MySQL versions had.

The crash recovery procedure on startup is: (a) read the redo log, (b) for each redo record, apply it to the corresponding data page if the page's LSN is older than the record's LSN (this is the redo phase — same as ARIES from 06.01.02), (c) for each uncommitted transaction found in the undo log, roll it back using the undo records (this is the undo phase). The doublewrite buffer is consulted first to repair any torn pages. The whole procedure is automatic and is what makes `kill -9 mysqld; service mysqld start` safe — every committed transaction is preserved, every uncommitted transaction is rolled back.

## Cross-Ecosystem Implementation

| Aspect | MySQL InnoDB | PostgreSQL | MongoDB WiredTiger |
|---|---|---|---|
| Concurrency unit | Thread per connection | Process per connection | Thread per connection |
| Buffer cache name | Buffer pool | shared_buffers | WiredTiger cache |
| Page size | 16 KB | 8 KB | 32 KB default |
| MVCC strategy | In-place + undo log | Append-only (no undo) | In-place + per-document MVCC |
| WAL name | Redo log (ib_logfile) | WAL (pg_wal/ segments) | Journal (WiredTigerLog.*) |
| Torn page defense | Doublewrite buffer | full_page_writes | WiredTiger checksums |
| Default engine since | MySQL 5.5 (2010) | n/a (only one engine) | MongoDB 3.2 (2016) |

## Hands-On Exercise

```sql
-- See InnoDB buffer pool size and hit ratio
SHOW VARIABLES LIKE 'innodb_buffer_pool_size';
SHOW STATUS LIKE 'Innodb_buffer_pool_read_requests';  -- total page requests
SHOW STATUS LIKE 'Innodb_buffer_pool_reads';          -- disk reads (misses)
-- Hit ratio = 1 - reads / read_requests. Should be > 99% in production.

-- See redo log configuration
SHOW VARIABLES LIKE 'innodb_log_file_size';
SHOW VARIABLES LIKE 'innodb_log_files_in_group';
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';
-- 1 = fsync every commit (default, ACID). 2 = fsync every second.
-- 0 = never (let OS decide). 2 and 0 lose data on crash.

-- Inspect the InnoDB internals
SHOW ENGINE INNODB STATUS\G
-- Look at:
--   LOG: Log sequence number, log flushed up to, log checkpoint
--   BUFFER POOL AND MEMORY: Total memory, buffer pool size, free
--     buffers, database pages, modified db pages, read hits
--   LATEST DETECTED DEADLOCK: (when present)
--   TRANSACTIONS: Trx id counter, purge done, history list length,
--     list of active transactions

-- See per-table .ibd file sizes
SELECT table_schema, table_name,
       ROUND(data_length/1024/1024, 1) AS data_mb,
       ROUND(index_length/1024/1024, 1) AS index_mb
  FROM information_schema.TABLES
  WHERE table_schema NOT IN ('mysql','information_schema','performance_schema')
  ORDER BY data_length DESC LIMIT 10;

-- See background threads
SELECT * FROM information_schema.INNODB_METRICS
  WHERE name LIKE 'thread%';
```

```bash
# See the actual files
ls -la /var/lib/mysql/your_db/
# users.ibd  orders.ibd  ...

# See the redo log files
ls -la /var/lib/mysql/ib_logfile*
# ib_logfile0  ib_logfile1

# Watch InnoDB I/O in real time
iostat -xmy 1
# Watch %util on the device holding /var/lib/mysql during a write-heavy load.
```
