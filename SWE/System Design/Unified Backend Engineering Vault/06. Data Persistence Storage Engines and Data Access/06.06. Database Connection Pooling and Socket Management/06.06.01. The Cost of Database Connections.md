# 06.06.01. The Cost of Database Connections

## What This Is

A database connection is not a cheap resource. Each connection holds an OS process (PostgreSQL) or thread (MySQL) on the server, occupies 5–10 MB of RAM, requires a TCP handshake and a TLS handshake to establish, and consumes a slot in the server's `max_connections` limit. Treating connections as cheap — opening one per request, or letting every serverless function instance open its own — is the most common cause of database production outages. This note covers the physical cost of a connection (memory, CPU, network), the failure mode of running out of connections, and why serverless functions cannot each hold a pooled connection. The fixes (application-level pools and PgBouncer) are covered in the next two notes.

## The Details

### The physics of a connection: OS Process/Thread allocation, memory overhead (5-10MB per backend in PostgreSQL), TCP 3-way handshake, TLS exchange, auth handshake

Establishing a single database connection involves four distinct costs, each of which is measurable and each of which adds up when you have thousands of connections.

```text
Cost breakdown of a single PostgreSQL connection establishment:
─────────────────────────────────────────────────────────────

1. TCP 3-way handshake                  ~1 ms (LAN), ~50 ms (cross-region)
   - Client → SYN → Server
   - Server → SYN-ACK → Client
   - Client → ACK → Server
   - Plus TCP keepalive negotiation (TCP_NODELAY, SO_KEEPALIVE).

2. TLS handshake (if used)              ~5-20 ms (TLS 1.2), ~5-10 ms (TLS 1.3)
   - TLS 1.2: 2 round trips
   - TLS 1.3: 1 round trip (major speedup)
   - Plus certificate verification (client validates server cert)
   - Plus optional client cert authentication (mTLS).

3. PostgreSQL auth + startup            ~5-10 ms
   - Client sends StartupMessage with user, database, options
   - Server challenges with auth method (md5, scram-sha-256, cert)
   - Client responds with credentials
   - Server validates against pg_shadow, sends AuthOk + ParameterStatus
   - Server sends ReadyForQuery

4. Backend process fork (PostgreSQL)    ~1-5 ms + 5-10 MB RAM
   - postmaster calls fork()
   - Child process inherits shared memory segment
   - Child initialises: relcache, catalog cache, snapshot, etc.
   - Child connects its socket to the client
   - Total private RSS: 5-10 MB on first query, growing with use

   (MySQL uses pthread_create, ~256 KB stack per thread, no fork.)

Total cold-connect time: ~15-35 ms on LAN, ~70-100 ms cross-region.
Total RAM cost (PostgreSQL): ~10 MB per connection at idle,
                             growing to 50+ MB with active queries.
Total RAM cost (MySQL): ~1 MB per connection at idle.

For a serverless function that opens a fresh connection on every
invocation, this is 15-100 ms of pure overhead per request, before
any query runs. This is why serverless needs connection pooling.
```

The fork cost in PostgreSQL is what makes connection pooling non-negotiable for that engine. A `fork()` on Linux is ~1 ms (the kernel copies the page table, marks all pages copy-on-write, allocates a new task_struct). The child process then has to initialise its private state: load the system catalog caches, set up the snapshot, parse the user's first query. The 5–10 MB of RSS is mostly the catalog cache (information about every table, column, type, and function the backend has touched) and the per-backend workspace (sort memory, hash memory, query execution state).

MySQL's thread model has a much lower per-connection memory cost (~1 MB per thread), which is why MySQL can scale to a few thousand connections without exhausting RAM, where PostgreSQL starts struggling at a few hundred. But both engines share the CPU cost: every active connection is a runnable thread/process that the scheduler must context-switch among, and once the active connection count exceeds the CPU core count by ~10×, the context-switch overhead dominates query execution time.

The default `max_connections` setting is the first wall teams hit. PostgreSQL ships with `max_connections = 100` out of the box (set in `postgresql.conf`, requires a restart to change because the engine pre-allocates shared-memory structures sized by this value). MySQL ships with `max_connections = 151`. These defaults were chosen for single-server deployments of the 2000s — a few application instances with a few worker threads each. They are catastrophically low for any modern deployment that multiplies connections across instances. The arithmetic is unforgiving: 4 Spring Boot pods × `maximumPoolSize=20` = 80 connections, leaving only 20 slots for `psql` admin sessions, backup jobs, migration scripts, and monitoring agents. Add a fifth pod and the next connection attempt fails with `FATAL: sorry, too many clients already` (PostgreSQL error code 53300). The fix is either raising `max_connections` (PostgreSQL: `ALTER SYSTEM SET max_connections = 300; SELECT pg_reload_conf();` — but this requires a restart) or putting PgBouncer in front to multiplex client connections onto a smaller server pool.

Serverless functions cannot each hold a pooled connection for three structural reasons. First, **isolation**: each Lambda/Cloud Function/Cloud Run instance is a separate micro-VM with its own address space; there is no shared pool across instances. Second, **concurrency**: AWS Lambda scales to 1,000 concurrent executions by default (10,000 with a quota increase); if each execution holds even one connection, that is 1,000 PostgreSQL backend processes = 10 GB of RAM and total CPU thrashing. Third, **lifecycle**: even with Lambda "warm" reuse (where the same micro-VM handles multiple invocations sequentially), the function only handles one request at a time — a per-instance pool would never have more than 1 connection, which provides no multiplexing benefit. The connection setup cost is paid on every cold start, and there is no way to amortise it. This is why serverless database access requires a server-side proxy (PgBouncer, RDS Proxy, Cloud SQL Connector, Supavisor) — the proxy is the only component with a long-enough lifetime and a wide-enough fan-in to make pooling worthwhile.

### Connection thrashing: Context switching and lock contention when connection counts exceed physical CPU cores

A server with 8 CPU cores can execute at most 8 threads simultaneously. Everything beyond 8 is multiplexed by the scheduler — each thread runs for its time slice (~1-10 ms), then is preempted and another thread runs. The cost of a context switch is ~5 µs on modern Linux (saving/restoring registers, TLB flush, cache pollution). When you have 1000 active connections on an 8-core server, the scheduler is constantly switching among them, and the cache pollution from the switches means each query runs slower than it would alone.

```text
Context switch cost vs. active connection count (8-core server):
─────────────────────────────────────────────────────────────

Active   Context switches   CPU spent in scheduler   Query latency
connections per second       (% of total CPU)         (median)
────────────────────────────────────────────────────────────────
8         ~0                  <1%                     baseline
32        ~5,000              3%                      +10%
100       ~20,000             10%                     +30%
500       ~100,000            35%                     +200%
1000      ~250,000            60%                     +500% (thrashing)
5000      ~1,000,000          90%                     +2000% (catastrophic)

The "thrashing" point is typically around 10× the CPU core count.
Beyond that, adding connections makes every query slower —
including the ones that were running fine before.
```

This is the curve that connection pools exist to flatten. A pool of 20 connections on an 8-core server has 2.5× oversubscription — small enough that the scheduler overhead is minimal. The pool queues incoming requests when all 20 connections are busy, rather than letting 1000 connections all try to run simultaneously. The trade-off is latency: a queued request waits longer than a request that gets an immediate connection. But the wait is bounded by the pool's queue depth, and the steady-state throughput is higher because each running query is faster.

The second cost of excessive connections is **lock contention on shared data structures**. PostgreSQL's proc array (the list of active transactions, used for MVCC snapshots) is a shared-memory structure protected by a latch. Every transaction that takes a snapshot acquires the latch briefly; every commit updates the array. With 1000 active transactions, the latch becomes a hot spot — even read-only queries contend on it. Similarly, InnoDB's lock system is a hash table protected by a mutex; high connection counts cause mutex contention that shows up as `Innodb_row_lock_waits` and `Innodb_row_lock_time_avg` in `SHOW STATUS`.

```sql
-- PostgreSQL: see the connection count and wait events
SELECT count(*), state, wait_event_type, wait_event
  FROM pg_stat_activity
  GROUP BY state, wait_event_type, wait_event
  ORDER BY count DESC;
--  count | state  | wait_event_type | wait_event
-- -------+--------+-----------------+------------
--    837 | idle   |                 |
--    142 | active |                 |
--     12 | active | LWLock          | ProcArrayLock
--      3 | active | Lock            | transactionid

-- If you see many connections waiting on ProcArrayLock, you have
-- too many connections. Reduce the pool size or use PgBouncer.

-- MySQL: see the thread count
SHOW STATUS LIKE 'Threads_connected';
SHOW STATUS LIKE 'Threads_running';
-- Threads_connected: 850
-- Threads_running:    42    ← this is the number that matters

-- See InnoDB row lock contention
SHOW STATUS LIKE 'Innodb_row_lock_waits';
SHOW STATUS LIKE 'Innodb_row_lock_time_avg';
```

The production failure mode is a slow degradation: as connection count grows, average query latency rises, which causes applications to open more connections (because each one is slow), which makes the problem worse. The positive feedback loop eventually hits `max_connections` and the database starts rejecting new connections, which the application interprets as a database outage. The fix is hard caps: a connection pool with a small `maximumPoolSize` (e.g. 2× CPU cores), and PgBouncer in front of the database to multiplex client connections onto the pool.

## Cross-Ecosystem Implementation

| Engine | Per-connection cost | Default `max_connections` | Practical limit (8-core, 16 GB) |
|---|---|---|---|
| PostgreSQL | ~10 MB + 1 fork | 100 | ~200-300 active connections |
| MySQL InnoDB | ~1 MB + 1 thread | 151 | ~500-1000 active connections |
| MongoDB | ~1 MB + 1 thread | 1 million (connection limit) | ~1000 active connections |
| Redis | ~50 KB + 1 client (no fork) | 10,000 (maxclients) | ~10,000 active connections |

## Hands-On Exercise

```sql
-- PostgreSQL: see the connection count and what each is doing
SELECT count(*) AS total,
       count(*) FILTER (WHERE state = 'active') AS active,
       count(*) FILTER (WHERE state = 'idle') AS idle,
       count(*) FILTER (WHERE state = 'idle in transaction') AS idle_in_txn
  FROM pg_stat_activity;

-- See the longest-running connections (potential pool leaks)
SELECT pid, application_name, client_addr, state,
       now() - state_change AS state_duration,
       now() - query_start AS query_duration,
       query
  FROM pg_stat_activity
  WHERE state != 'active'
  ORDER BY state_change ASC
  LIMIT 20;

-- See the connections that are waiting (lock contention)
SELECT pid, wait_event_type, wait_event, state, query
  FROM pg_stat_activity
  WHERE wait_event IS NOT NULL
  ORDER BY wait_event_type, wait_event;

-- Check the configured limit
SHOW max_connections;

-- See who holds each connection
SELECT application_name, client_addr, count(*)
  FROM pg_stat_activity
  GROUP BY application_name, client_addr
  ORDER BY count DESC;
```

```bash
# OS-level: see the postgres processes and their memory
ps -eo pid,rss,cmd | grep postgres | sort -k2 -n -r | head -20

# See context switch rate
vmstat 1 5
# cs column = context switches per second
# us/sy/id = user/system/idle CPU percentages
# If sy (system CPU) is > 30%, you have scheduler overhead.

# See the TCP connections to the database
ss -tnp | grep ':5432' | head
ss -tn state established '( sport = :5432 )' | wc -l

# MySQL equivalent
mysql -e "SHOW STATUS LIKE 'Threads_connected'; \
          SHOW STATUS LIKE 'Threads_running'; \
          SHOW VARIABLES LIKE 'max_connections';"
```
