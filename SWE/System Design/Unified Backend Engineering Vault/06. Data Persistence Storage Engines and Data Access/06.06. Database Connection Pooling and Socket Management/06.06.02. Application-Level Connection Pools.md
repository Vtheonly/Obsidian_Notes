# 06.06.02. Application-Level Connection Pools

## What This Is

An application-level connection pool keeps a set of open database connections in the application's memory and reuses them across requests, instead of opening and closing a connection per request. Every JVM application uses HikariCP by default (Spring Boot ships it); Python's Django uses `CONN_MAX_AGE` (a weak pool); Prisma has a built-in pool; Laravel's framework pool is configured per-environment. This note covers HikariCP's internal architecture and tuning, the pool sizing formula, the lifecycle parameters, the leak detection mechanism, and the differences between real pools (HikariCP, Prisma) and pseudo-pools (Django's `CONN_MAX_AGE`). The production failure mode of an over-sized pool is connection thrashing on the database (06.06.01); the failure mode of an under-sized pool is request latency.

## The Details

### HikariCP (Java) Internals: Bytecode optimizations, FastList, concurrent bag structures, zero-overhead locks

HikariCP is the de facto JDBC connection pool, shipped as the default in Spring Boot 2.x and later. Its design philosophy is "do less" — every micro-optimisation matters when a pool can serve 100,000 queries per second. The internal architecture reflects this:

```text
HikariCP internal data structures:
─────────────────────────────────────────────────────────────

ConcurrentBag<T> — the pool's core data structure
  - A hand-rolled, lock-free bag of connection wrappers.
  - Each thread tries to borrow a connection from a thread-local
    list first (fast path), then from the shared list (slow path).
  - Borrowing uses CAS (compare-and-swap), not locks.
  - If no connection is available, the thread "steals" from
    another thread's list — also CAS, no locks.
  - If still nothing, the thread waits on a SynchronousQueue
    until another thread returns a connection or the
    connectionTimeout expires.

FastList — replacement for ArrayList
  - Removes the range-check on every get() (the JIT can't
    elide it because of the ArrayList contract).
  - Removes the iterator allocation in forEach loops.
  - Used for the list of statements that must be closed when
    a connection is returned to the pool.

ProxyConnection / InvocationHandler
  - Every connection handed to the application is a JDK
    dynamic proxy that intercepts every method call.
  - The proxy records open statements so they can be closed
    on connection return, even if the application forgot.
  - The proxy tracks the "last user" (which thread borrowed)
    for leak detection.

Clock-pool pattern for maxLifetime enforcement
  - A single scheduled thread checks all connections every 30s.
  - Connections past their maxLifetime are evicted asynchronously,
    not on the borrow path (which would add latency).
```

The reason HikariCP is faster than older pools (c3p0, DBCP, Tomcat JDBC) is not one big optimisation but a thousand small ones: avoiding iterator allocation, avoiding lambda capture in hot paths, using `volatile` instead of locks where possible, hand-rolling collections to avoid contract overhead. The performance difference is real — HikariCP can borrow/return a connection in under 1 µs, where older pools take 5-10 µs. At 100,000 queries per second, that is the difference between 10% and 50% CPU spent in the pool.

The configuration knobs that actually matter:

```yaml
# Spring Boot application.yml
spring:
  datasource:
    hikari:
      maximum-pool-size: 20              # hard cap on connections
      minimum-idle: 20                   # always keep this many open
                                         # (set equal to maximum for fixed-size pool)
      connection-timeout: 30000          # ms to wait for a connection (30 sec)
      idle-timeout: 600000               # ms before an idle connection is closed (10 min)
                                         # (only applies if minimum-idle < maximum-pool-size)
      max-lifetime: 1800000              # ms before a connection is force-closed (30 min)
                                         # MUST be less than the database's wait_timeout
      leak-detection-threshold: 60000    # ms a connection can be checked out before
                                         # a leak warning is logged (60 sec)
      connection-test-query: "SELECT 1"  # only used if driver doesn't support isValid()
      validation-timeout: 5000           # ms to wait for validation query
```

The `max-lifetime` setting is the most commonly misconfigured. It must be **less than the database's `idle_session_timeout` (PostgreSQL) or `wait_timeout` (MySQL)** — typically by 30-60 seconds, to provide a safety margin. If `max-lifetime` is longer than the database's timeout, the database will close the connection while the pool still thinks it is open, and the next borrow will return a dead connection (producing `Connection is closed` errors). The standard pattern is `wait_timeout = 28800` (8 hours, MySQL default) and `max-lifetime = 1800000` (30 minutes) — the pool cycles connections well before the database would close them.

### Sizing the pool: The optimal connection formula (Connections = ((Core\_Count * 2) + Effective\_Spindle\_Count))

The HikariCP wiki popularised a formula for pool sizing that comes from a 2010 Performance Asia paper:

```text
connections = (core_count * 2) + effective_spindle_count
```

The reasoning: a thread that is processing a query is either using the CPU (computing, parsing, formatting) or waiting on I/O (the database's response). The optimal number of concurrent threads is the number that keeps the CPU busy without idle gaps. With one connection per core, every CPU is busy when queries are CPU-bound, but there are idle gaps when queries wait for I/O. With two connections per core, one connection can be using the CPU while the other is waiting for I/O — the I/O wait of one fills the CPU gap of the other.

```text
Pool sizing worked example:
─────────────────────────────────────────────────────────────

Server: 8 CPU cores, 1 NVMe SSD (no HDD)
Formula: (8 * 2) + 1 = 17 connections → round to 20.

Server: 4 CPU cores, 1 HDD (spinning disk)
Formula: (4 * 2) + 1 = 9 connections → round to 10.

Server: 16 CPU cores, RAID 10 of 8 SSDs
Formula: (16 * 2) + 8 = 40 connections.

If you have multiple application instances, divide the pool
size by the instance count:
  - 20 application instances, each with pool of 10 → 200 server
    connections. With PostgreSQL, that's 200 processes = 2 GB of
    RAM, manageable.
  - 20 application instances, each with pool of 50 → 1000 server
    connections. PostgreSQL will thrash (06.06.01).
```

The `effective_spindle_count` is the number of independent disk I/O channels — 1 for a single SSD, 4 for a RAID 10 of 4 disks, 0 for a fully cached workload (everything in `shared_buffers`). On modern NVMe, the formula's HDD assumption is outdated; the rule of thumb today is `core_count * 2` for I/O-bound workloads, `core_count + 1` for CPU-bound workloads (e.g. heavy in-memory computation with little I/O).

The formula has been criticised (notably by the PostgreSQL team) for being too simplistic — the right answer depends on the query mix, the cache hit ratio, and the network latency. But the formula's main value is as a *default*: it produces a pool size that is far smaller than the "let's set it to 100" default that many applications ship with, and small pools are almost always better than large pools for throughput (because they avoid database thrashing). Start with `core_count * 2`, measure with `pg_stat_activity` or `SHOW PROCESSLIST`, and adjust.

### Pool lifecycle parameters: `maximumPoolSize`, `minimumIdle`, `connectionTimeout`, `idleTimeout`, `maxLifetime`

The five HikariCP lifecycle parameters control how the pool grows, shrinks, and recycles connections. Each has a specific failure mode if set wrong.

```text
maximumPoolSize — the hard cap.
  - Too small: requests queue, latency rises. When the queue
    fills, requests fail with `SQLTransientConnectionException`.
  - Too large: database thrashes (06.06.01). Pool grows, but
    each connection is slow because the database is overloaded.
  - Default: 10 (Spring Boot). Often too small for production.

minimumIdle — the steady-state pool size.
  - If equal to maximumPoolSize: fixed-size pool. No
    resizing overhead. Best for production.
  - If less than maximumPoolSize: pool grows under load and
    shrinks when idle. Saves resources at low load, but the
    growth requires new connections (TCP + auth + fork cost).
  - Default: same as maximumPoolSize.

connectionTimeout — how long a borrow can wait.
  - Too short: requests fail under transient load spikes.
  - Too long: requests pile up, application threads are
    exhausted, the whole app becomes unresponsive.
  - Default: 30 seconds. Reasonable for most apps.

idleTimeout — when to close an idle connection (if minimumIdle
              is less than maximumPoolSize).
  - Too short: pool thrashes (open/close/open/close).
  - Too long: idle connections hold database resources.
  - Default: 10 minutes. Reasonable.

maxLifetime — when to force-close a connection.
  - Too short: connections cycle too often (overhead).
  - Too long: connections may be closed by the database first
    (causing "connection is closed" errors).
  - Default: 30 minutes. MUST be < database's idle timeout.
```

The pattern to internalise: `minimumIdle = maximumPoolSize` (fixed-size pool) for production. A fixed-size pool eliminates the open/close churn, the borrow latency is consistent, and the database's connection count is stable. The cost is holding idle connections when the application is not under load — but idle connections are cheap (a few MB of RAM each, no CPU), so this is a good trade. Variable-size pools make sense for autoscaling deployments where the application's instance count varies widely and you want each instance's pool to scale with its load.

### Connection leak detection and mitigation

A connection leak happens when the application borrows a connection from the pool and never returns it. The classic pattern: a method that opens a connection, runs a query, and throws an exception before the `close()` call — the connection stays checked out, the pool slowly drains, and eventually `connectionTimeout` fires and every request fails.

```java
// Leaky pattern
public User findUser(Long id) {
    Connection conn = dataSource.getConnection();  // borrowed
    Statement stmt = conn.createStatement();
    ResultSet rs = stmt.executeQuery("SELECT * FROM users WHERE id = " + id);
    if (!rs.next()) {
        throw new UserNotFoundException(id);  // LEAK: conn never returned
    }
    User u = mapRow(rs);
    rs.close(); stmt.close(); conn.close();  // only reached on success
    return u;
}

// Correct pattern: try-with-resources (Java 7+)
public User findUser(Long id) throws SQLException {
    try (Connection conn = dataSource.getConnection();
         Statement stmt = conn.createStatement();
         ResultSet rs = stmt.executeQuery("SELECT * FROM users WHERE id = " + id)) {
        if (!rs.next()) {
            throw new UserNotFoundException(id);  // conn returned via try-with-resources
        }
        return mapRow(rs);
    }
}
```

HikariCP's leak detection works by tracking the call stack of every borrow. When a connection is checked out for longer than `leak-detection-threshold` (default 0 = disabled), HikariCP logs a warning with the stack trace of the borrow — pointing you at the code that forgot to close. Set `leak-detection-threshold: 60000` (60 seconds) in production; if you see leak warnings, fix the code. The warning does not force the connection back — it just tells you there is a problem.

```text
Sample HikariCP leak warning:
─────────────────────────────────────────────────────────────
WARN  com.zaxxer.hikari.pool.ProxyLeakTask -- Apparent connection
leak detected. Connection trace:
  java.lang.Thread.getStackTrace(Thread.java:1564)
  com.zaxxer.hikari.pool.HikariPool.getConnection(HikariPool.java:169)
  com.zaxxer.hikari.pool.HikariDataSource.getConnection(HikariDataSource.java:100)
  com.example.UserService.findUser(UserService.java:42)   ← THE LEAK
  com.example.UserController.getUser(UserController.java:23)
  ...
```

The non-HikariCP pools have similar features. Apache DBCP2 has `removeAbandonedOnBorrow` and `removeAbandonedTimeout`. The Tomcat JDBC pool has `suspectTimeout` and `logAbandoned`. Prisma's pool logs long-running queries. Django's `CONN_MAX_AGE` has no leak detection — if a Django view leaks a connection, it is silently re-used by the next request on the same worker, which can produce cross-request state contamination (a transaction started in one request affecting the next).

The deeper point about leak detection: it is a debugging tool, not a production safety net. The right production pattern is try-with-resources (Java), `with` blocks (Python), `defer` (Go), or `using` (C#) — the language's automatic resource management ensures the connection is returned even on exception. Frameworks like Spring JdbcTemplate and JPA wrap every query in this pattern, so the application code rarely touches connections directly. The leak detection is for the cases where the framework is bypassed (raw JDBC, raw psycopg2) and for catching framework bugs.

## Cross-Ecosystem Implementation

| Pool | Default `maximumPoolSize` | Leak detection | Default `maxLifetime` | Notes |
|---|---|---|---|---|
| HikariCP (Java/Spring) | 10 | `leak-detection-threshold=0` (off) | 30 min | Fastest JVM pool |
| Prisma (Node.js) | `num_cpus * 2 + 1` | Built-in slow query log | 30 min | Built into Prisma Client |
| Django (Python) | n/a (`CONN_MAX_AGE=0`) | None | n/a | NOT a real pool — see below |
| SQLAlchemy QueuePool (Python) | 5 | `pool_recycle` (closes old conns) | 1 hour (recycle) | Standard for Flask/FastAPI |
| Laravel (PHP) | 64 (per `config/database.php`) | None | 5 min (`lifetime`) | Per-FPM-worker pool |
| Ruby on Rails ActiveRecord | 5 (per `database.yml`) | None | 5 min (`reaping_frequency`) | Per-process pool |

Django's `CONN_MAX_AGE` deserves special mention because it is not a real pool. Setting `CONN_MAX_AGE = 60` means each Django request reuses the same connection for 60 seconds, then closes it. There is no pool — each worker process holds at most one connection, and there is no borrowing across workers. For a Django deployment with 100 FPM/uWSGI workers, `CONN_MAX_AGE = 60` means 100 connections to the database, with no upper bound on how many can be active simultaneously. The right pattern for Django is to add a real pool (PgBouncer on the server side, or a package like `django-db-geventpool` for application-side). The deeper lesson: `CONN_MAX_AGE > 0` is a per-worker persistent connection, not a pool — do not assume it gives you pool semantics.

## Hands-On Exercise

```java
// Spring Boot: inspect the HikariCP pool via the actuator endpoint
// GET /actuator/metrics/hikaricp.connections.active
// GET /actuator/metrics/hikaricp.connections.idle
// GET /actuator/metrics/hikaricp.connections.pending
// GET /actuator/metrics/hikaricp.connections.max

// In code, access the pool metrics directly:
@Autowired HikariDataSource dataSource;

public void printPoolStats() {
    HikariPoolMXBean pool = dataSource.getHikariPoolMXBean();
    System.out.printf("Active: %d, Idle: %d, Pending: %d, Total: %d%n",
        pool.getActiveConnections(),
        pool.getIdleConnections(),
        pool.getThreadsAwaitingConnection(),
        pool.getTotalConnections());
}

// Trigger a leak intentionally to see the warning
public void leakyMethod() throws SQLException {
    Connection conn = dataSource.getConnection();  // never closed
    // wait for leak-detection-threshold to fire
}
```

```python
# Prisma: see pool stats (in the Prisma Client log)
# Set log level to query in schema.prisma:
#   generator client { ... }
#   datasource db { ... }
# Then in code:
import { PrismaClient } from '@prisma/client'
const prisma = new PrismaClient({ log: ['query', 'info', 'warn'] })

# SQLAlchemy: inspect the pool
from sqlalchemy import create_engine
engine = create_engine("postgresql://...", pool_size=20, max_overflow=10, pool_recycle=1800)
print(engine.pool.status())  # <QueuePool ... 5/20>

# Django: see how many connections are open per worker
# (not directly inspectable; check the database side instead)
SELECT application_name, count(*) FROM pg_stat_activity
  GROUP BY application_name;
```

```sql
-- PostgreSQL: see who is holding connections
SELECT application_name, client_addr, state, count(*)
  FROM pg_stat_activity
  GROUP BY application_name, client_addr, state
  ORDER BY count DESC;
-- Expect application_name to identify the pool (set in HikariCP
-- via dataSource.setPoolName("my-app-pool")).
```
