# 06.06.03. Server-Side Connection Proxies PgBouncer

## What This Is

PgBouncer is a lightweight, single-binary connection pooler for PostgreSQL that sits between clients and the database server. It accepts many inbound client TCP connections (typically thousands) and multiplexes them onto a small, fixed pool of outbound server connections (typically 10–100). The application connects to PgBouncer on port 6432 instead of PostgreSQL on port 5432; PgBouncer forwards the queries to a real PostgreSQL backend and returns the results. From the application's perspective, PgBouncer *is* PostgreSQL — it speaks the wire protocol (libpq v3) and answers `SELECT version()`. From PostgreSQL's perspective, PgBouncer is the only client it ever sees.

This note covers when application-level pools (06.06.02) are insufficient and a server-side proxy becomes necessary, the three PgBouncer pooling modes (session, transaction, statement), the `max_client_conn` / `default_pool_size` / `pool_size` configuration knobs, why transaction pooling is the default for serverless workloads, and the prepared-statement problem that bites teams the first time they switch from session to transaction mode. The production failure mode this note prevents is exhaustion of PostgreSQL's `max_connections` when application instances multiply beyond what their individual pools can keep under control. The architectural fix is to insert PgBouncer as the single fan-in point: N applications × M client connections → 1 PgBouncer → K server connections, where K is bounded by `default_pool_size × number_of_databases × number_of_users`.

## The Details

### When application pooling is insufficient (e.g., PHP-FPM thousands of workers, Serverles...

Application-level pools (HikariCP, Prisma, SQLAlchemy QueuePool — see [[06.06.02. Application-Level Connection Pools]]) are per-process. Every process holds its own pool, and there is no coordination across processes. This is fine when you have one JVM with one HikariCP instance and `maximumPoolSize = 20` — PostgreSQL sees 20 connections total. It breaks down in three common architectures.

The first is **PHP-FPM**. A PHP-FPM pool with `pm.max_children = 200` runs 200 separate PHP worker processes, each with its own address space and its own PDO connection. There is no shared pool — each worker opens at most one connection via `PDO::__construct` and closes it (or lets it die at request end). With 200 workers and `pm.max_requests = 1000`, you have 200 concurrent connections to PostgreSQL at peak, each one cycling through `fork → auth → catalog cache load → query → close`. PostgreSQL's `max_connections = 100` default is blown instantly. The arithmetic: 200 FPM workers × 1 connection = 200 server processes × 10 MB RSS = 2 GB of RAM just for connection backends, plus the CPU cost of 200 fork+auth cycles per FPM reload.

The second is **serverless**. AWS Lambda scales to 1,000 concurrent executions by default; each execution is an isolated micro-VM with its own connection pool (if any). Even if each Lambda opens only one connection, 1,000 concurrent executions = 1,000 PostgreSQL backend processes = `FATAL: sorry, too many clients already` (error 53300). The same is true for Cloud Run, Cloud Functions, Vercel Functions, and any other scale-to-zero platform. The function lifetime is too short and the concurrency is too high for application-side pooling to help.

The third is **microservice fan-out**. A modest deployment might have 10 Spring Boot services, each running 4 replicas, each replica with `maximumPoolSize = 10`. Total server connections: 10 × 4 × 10 = 400. PostgreSQL's `max_connections = 100` is blown by a factor of 4×. Even raising `max_connections = 500` does not help — the CPU thrashing kicks in at ~10× core count (see [[06.06.01. The Cost of Database Connections]]).

```text
Without PgBouncer — fan-out catastrophe:

  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐
  │ PHP-FPM      │  │ 4× Spring    │  │ 1000× Lambda │
  │ 200 workers  │  │ Boot pods    │  │ instances    │
  │ 200 conns    │  │ 40 conns     │  │ 1000 conns   │
  └──────┬───────┘  └──────┬───────┘  └──────┬───────┘
         │                 │                 │
         └─────────────────┼─────────────────┘
                           ▼
                  ┌────────────────┐
                  │  PostgreSQL    │
                  │  max_conn=100  │  ← FATAL: too many clients
                  └────────────────┘

With PgBouncer — single fan-in point:

  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐
  │ PHP-FPM      │  │ 4× Spring    │  │ 1000× Lambda │
  │ 200 conns    │  │ 40 conns     │  │ 1000 conns   │
  └──────┬───────┘  └──────┬───────┘  └──────┬───────┘
         │                 │                 │
         └─────────────────┼─────────────────┘
                           ▼
                  ┌────────────────┐
                  │   PgBouncer    │
                  │ max_client=2000│  ← multiplexes clients
                  │ pool_size=25   │  ← fixed server pool
                  └────────┬───────┘
                           ▼
                  ┌────────────────┐
                  │  PostgreSQL    │
                  │  sees 25 conns │  ← manageable
                  └────────────────┘
```

The fundamental insight: application pools reduce *per-process* connection churn, but they cannot reduce the *total* connection count across processes. Only a server-side proxy can do that, because it is the one component that sits in front of all clients and can arbitrate the server connection count. This is why PgBouncer (or its managed equivalents — AWS RDS Proxy, Google Cloud SQL Connector, Supabase Supavisor, Yugabyte YB-TServer) is a near-universal fixture in any deployment with more than a handful of application instances.

### PgBouncer Pooling Modes

PgBouncer's core job is to map N client connections onto K server connections, where N >> K. The decision of *when* to return a server connection to the pool is called the **pooling mode**, and PgBouncer supports three: session, transaction, and statement. The mode is set globally in `pgbouncer.ini` via `pool_mode = session|transaction|statement`, or per-database via the connection string in the `[databases]` section.

```ini
# /etc/pgbouncer/pgbouncer.ini
[databases]
postgres = host=127.0.0.1 port=5432 dbname=postgres
analytics = host=10.0.0.5 port=5432 dbname=analytics pool_mode=session

[pgbouncer]
listen_addr = 0.0.0.0
listen_port = 6432
auth_type = scram-sha-256
auth_file = /etc/pgbouncer/userlist.txt
pool_mode = transaction              ; default mode for all databases
max_client_conn = 1000               ; hard cap on client TCP connections
default_pool_size = 25               ; server connections per (db, user) pair
min_pool_size = 5                    ; keep this many warm even when idle
reserve_pool_size = 5                ; extra servers under load
reserve_pool_timeout = 3             ; seconds before tapping reserve pool
server_idle_timeout = 600            ; close idle server conns after 10 min
server_lifetime = 3600               ; recycle server conns after 1 hour
query_wait_timeout = 120             ; kill clients queued > 2 min
```

The `max_client_conn` setting caps the number of client TCP connections PgBouncer accepts (default 100, typically raised to 1000–10000). It is a soft cap — when hit, new connections are rejected with `FATAL: no more connections allowed`. Crucially, this number is independent of PostgreSQL's `max_connections`: PgBouncer can accept 10,000 clients while PostgreSQL only sees 25. The `default_pool_size` setting controls how many server connections PgBouncer opens per (database, user) pair — this is the number that *does* count against PostgreSQL's `max_connections`. With 4 databases × 5 users × `default_pool_size = 25`, the total server connection count is 4 × 5 × 25 = 500, which must be ≤ PostgreSQL's `max_connections`.

| Mode | Server conn returned when | Session features (SET, LISTEN, temp tables, prepared stmts) | Best for |
|---|---|---|---|
| `session` | Client disconnects | All work | Long-lived sessions, admin tools, psql, migrations |
| `transaction` | Transaction commits or aborts | None (or `max_prepared_statements` in 1.21+) | Serverless, web apps, microservices — **the default** |
| `statement` | Each statement completes | None; transactions broken | Read-only single-statement queries only |

The choice of mode is the single biggest decision in a PgBouncer deployment. Session mode is the most compatible (it is transparent to the client — anything that works against PostgreSQL works against session-mode PgBouncer) but provides the least multiplexing benefit, because each client holds a server connection for its entire lifetime. Transaction mode is the production default: it multiplexes aggressively and works for ~95% of workloads, but breaks session-level features that assume a stable backend. Statement mode is essentially never appropriate. The next three sections explain each mode in depth.

### Session Pooling: Dedicated server connection per client lifetime

In session pooling mode, PgBouncer assigns one server connection to each client connection at login time and holds that assignment until the client disconnects. The server connection is not shared with any other client while the client is connected, even if the client is idle. This mode is functionally equivalent to a direct connection to PostgreSQL — every session-level feature works exactly as documented, because the client really does have a dedicated backend process for the entire session.

```text
Session pooling timeline:
─────────────────────────────────────────────────────────────

Client A connects         Server pool state
   │
   ├─ LOGIN (auth)  ─────▶ borrows server conn #1 ─────────▶ postgres backend 1
   ├─ SET statement_timeout = 5000;
   ├─ PREPARE find AS SELECT * FROM users WHERE id = $1;
   ├─ BEGIN;
   ├─ EXECUTE find(1);
   ├─ COMMIT;
   ├─ (idle 30 seconds)
   ├─ EXECUTE find(2);        ← prepared statement still alive
   ├─ LISTEN channel_x;
   ├─ (idle again)
   └─ LOGOUT          ─────▶ returns server conn #1 to pool

Client B connects during A's idle period:
   ├─ LOGIN  ─────────────▶ must wait for a free server conn
   │                        (or opens a NEW one if pool < max)
```

Session mode supports every PostgreSQL session-level feature: `SET`/`RESET` for runtime parameters, `PREPARE`/`EXECUTE`/`DEALLOCATE` for named prepared statements, `CREATE TEMP TABLE` for session-local tables, `LISTEN`/`NOTIFY` for pub/sub, session-level advisory locks (`pg_advisory_lock`), `WITH HOLD` cursors that survive commit, and `SET ROLE`/`SET SESSION AUTHORIZATION` for privilege escalation. This is the mode to use for `psql` interactive sessions, schema migration tools (Flyway, Liquibase, `pg_dump`, `pg_restore`), and admin/observability queries that rely on session state.

The cost is that session mode provides very little multiplexing benefit. A client that logs in, runs one query, and goes idle for an hour holds a server connection for that entire hour. If you have 1,000 clients connected in session mode, you need 1,000 server connections — which is exactly the problem PgBouncer was supposed to solve. The only savings come from connection-setup amortisation: the client's TCP+TLS+auth is paid once per session instead of once per query. For a long-running admin session that issues thousands of queries, this is a real win; for a serverless function that issues one query and exits, it provides no benefit at all. The production failure mode in session mode is `query_wait_timeout`: when `max_client_conn` exceeds `default_pool_size`, new clients queue waiting for a server connection, and if they queue past `query_wait_timeout` (default 120 s), PgBouncer kills them with `FATAL: query_wait_timeout reached`. Inspect this with the PgBouncer admin command `SHOW POOLS;` — the `cl_waiting` column shows how many clients are currently queued.

### Transaction Pooling: Connection returned to pool the moment a transaction commits/abort...

In transaction pooling mode, PgBouncer assigns a server connection to a client only for the duration of an explicit transaction. When the client sends `BEGIN` (or PgBouncer detects the start of an implicit transaction), a server connection is borrowed; when the client sends `COMMIT` or `ROLLBACK`, the server connection is returned to the pool. Between transactions, the client has no server connection at all — its next query will borrow a *different* server connection (possibly one that just served a different client). This is the mode that makes PgBouncer worth running: 1,000 clients can be multiplexed onto 25 server connections, because at any instant most clients are between transactions (idle, doing CPU work, or waiting for user input).

```text
Transaction pooling timeline:
─────────────────────────────────────────────────────────────

Client A           Client B           Client C       Server pool
   │                  │                  │            (25 conns)
   ├─ BEGIN           │                  │
   ├─ UPDATE...       │                  │       A borrows #7
   │                  ├─ BEGIN           │       B borrows #3
   │                  │                  ├─ SELECT  C borrows #14
   ├─ COMMIT          │                  │       A returns #7
   │                  ├─ UPDATE...       │       B still on #3
   │                  │                  ├─ COMMIT  C returns #14
   │                  ├─ COMMIT          │       B returns #3
   │                  │                  │
   ▼                  ▼                  ▼
 (idle — no server conn held — borrows fresh on next BEGIN)
```

Transaction mode is the default for serverless because each Lambda invocation typically executes one transaction and exits. The function borrows a server connection for the duration of its DB work, returns it on commit, and the next Lambda invocation (possibly on a different micro-VM) gets to reuse that same server connection. This collapses 1,000 concurrent Lambda connections onto ~25 server connections — exactly the multiplexing benefit application-side pools cannot provide.

The catch is that transaction mode breaks every session-level feature. The most common production surprise is **prepared statements**. PostgreSQL's `PREPARE name AS sql` / `EXECUTE name(args)` / `DEALLOCATE name` are session-scoped — the prepared statement lives in the backend process's memory and is referenced by name. When client A prepares `stmt_foo` on server connection #7, returns the connection, and later client B borrows server connection #7 and tries `EXECUTE stmt_foo(1)`, the result depends on whether *anyone* previously prepared a statement named `stmt_foo` on that backend — which is undefined behaviour. The two clients have clobbered each other's namespace.

JDBC drivers make this worse with automatic server-side prepared statements. The PostgreSQL JDBC driver, after `prepareThreshold = 5` executions of the same `PreparedStatement`, switches from parse-on-every-execution to a server-side `PREPARE`/`EXECUTE` cycle. In transaction mode, this corrupts silently — the driver prepares `S_1`, `S_2`, etc., but each preparation may land on a different backend, and the EXECUTE may find a different (or no) prepared statement under that name. Symptoms include `ERROR: prepared statement "S_3" does not exist`, `ERROR: wrong number of parameters for prepared statement "S_2"`, and silent data corruption when two statements happen to share a name.

PgBouncer 1.21+ (released 2023) added `max_prepared_statements` to fix this. When set to a non-zero value (e.g. `max_prepared_statements = 100`), PgBouncer tracks each client's prepared statements internally and silently re-issues `PREPARE` on the new server connection the first time the client executes it on a fresh backend. The trade-off is per-client memory in PgBouncer (~1 KB per tracked statement) and a small latency bump on first EXECUTE after a connection switch. For older PgBouncer, the workaround is `prepareThreshold = 0` in JDBC (disabling server-side prepared statements) or rewriting the application to use `PREPARE` explicitly only inside transactions.

Other session features that break in transaction mode: `SET` (the parameter is reset to default when the connection returns to the pool, so `SET statement_timeout = 5000` followed by a query in a separate transaction has no effect — use `SET LOCAL` inside the transaction instead); `LISTEN`/`NOTIFY` (the listener is on a specific backend, and the next transaction may be on a different backend — PgBouncer 1.20+ supports this with `ignore_startup_parameters = extra_float_digits`); `CREATE TEMP TABLE` (the table is gone when the backend returns to the pool, because temp tables are session-scoped); session-level advisory locks (`pg_advisory_lock` — held by a specific backend, lost on return); `WITH HOLD` cursors (cursors that survive commit — PgBouncer closes them on return). The pre-flight check before enabling transaction mode is to grep your application for these features; if you find them, either rewrite the code or keep that database on session mode.

### Statement Pooling: Single statement granularity (deprecated/anti-pattern for multi-quer...

Statement pooling is the most aggressive mode: PgBouncer returns the server connection to the pool after *every* statement, regardless of transaction state. This is essentially transaction pooling with `BEGIN`/`COMMIT` disabled. A multi-statement transaction like `BEGIN; UPDATE accounts SET ...; INSERT INTO audit_log ...; COMMIT;` is impossible — the four statements would borrow four different server connections, and `COMMIT` would have nothing to commit (it would borrow a fresh backend whose transaction state is `idle`, not `in transaction`).

```text
Statement pooling — what happens to a multi-statement transaction:
─────────────────────────────────────────────────────────────

Client sends:
   BEGIN;                    ← borrows server #3, runs BEGIN, returns #3
   UPDATE accounts ...;      ← borrows server #11, runs UPDATE, returns #11
                              (server #3's BEGIN is now orphaned —
                               it holds a transaction open until idle_timeout
                               or until another client borrows #3 and sees
                               "ERROR: there is already a transaction in
                                progress" on its first query)
   INSERT INTO audit_log...; ← borrows server #7, runs INSERT, returns #7
   COMMIT;                   ← borrows server #19, COMMITs nothing,
                              returns #19

Result: UPDATE is committed or rolled back depending on what server #11
        does when it next gets reused. INSERT ditto. The data is
        silently inconsistent. This is why statement mode is unsafe
        for any workload that involves writes.
```

Statement mode is rarely appropriate. The only legitimate use case is read-only, single-statement queries against a database where every query is wrapped in its own implicit transaction (PostgreSQL auto-commits single statements outside an explicit `BEGIN`/`COMMIT` block). A read-only analytics dashboard that issues `SELECT count(*) FROM events WHERE ...` per page load is a candidate. Even then, transaction mode is preferable, because the implicit per-statement transaction in transaction mode produces identical behaviour without the multi-statement breakage risk. PgBouncer's documentation itself recommends transaction mode over statement mode for almost all workloads.

The one place statement mode shows up in practice is misconfiguration. A team sets `pool_mode = statement` thinking "smaller pool granularity = more multiplexing = better", deploys, and the application starts producing mysterious data inconsistency bugs — orders without their audit log entries, balances that don't match their transaction history, `ERROR: there is already a transaction in progress` on connections that the application thinks are fresh. The diagnostic is `SHOW POOLS;` in PgBouncer — the `sv_active` count is much lower than expected (because statements are too short to keep servers busy), and `SHOW STATS;` shows a very high `server_assignment_count` (connections are being reassigned per statement). The fix is `pool_mode = transaction`, full stop. Statement mode is preserved as a configurable option mostly for historical reasons and for the narrow read-only-dashboard case; it is an anti-pattern for anything else.

## Cross-Ecosystem Implementation

The same concept maps differently across the four target ecosystems. PgBouncer is PostgreSQL-specific, but every ecosystem has either a built-in equivalent or a deployment pattern that achieves the same multiplexing.

| Ecosystem | Connection proxy | How it is wired in | Default port |
|---|---|---|---|
| Spring Boot / JVM | PgBouncer (external) | `spring.datasource.url=jdbc:postgresql://pgbouncer:6432/db` + HikariCP `maximumPoolSize=10` per pod | 6432 |
| Node.js / Prisma | PgBouncer (external) or Prisma Data Proxy | `DATABASE_URL=postgresql://pgbouncer:6432/db?pgbouncer=true&connection_limit=1` | 6432 |
| Python / Django | PgBouncer (external) | `DATABASES['default']['HOST'] = 'pgbouncer'` + `CONN_MAX_AGE=0` (PgBouncer handles pooling) | 6432 |
| PHP / Laravel | PgBouncer (external) | `DB_HOST=pgbouncer` in `.env`, `DB_PORT=6432` | 6432 |
| MySQL ecosystems | ProxySQL / AWS RDS Proxy | Same role as PgBouncer but for MySQL protocol | 6032 (ProxySQL admin) |

Note the Prisma-specific URL parameter `?pgbouncer=true`. This disables Prisma's internal driver behaviour that conflicts with transaction mode (specifically, it switches from `PREPARE` to text protocol). For Django, `CONN_MAX_AGE = 0` is mandatory in front of PgBouncer — otherwise Django holds a persistent connection per worker, defeating PgBouncer's multiplexing (the worker's connection sits idle in Django's pool instead of being returned to PgBouncer's pool between requests).

## Hands-On Exercise

```bash
# Install PgBouncer on Debian/Ubuntu
sudo apt install pgbouncer

# /etc/pgbouncer/pgbouncer.ini — minimal transaction-mode config
cat > /tmp/pgbouncer.ini <<'EOF'
[databases]
postgres = host=127.0.0.1 port=5432 dbname=postgres

[pgbouncer]
listen_addr = 127.0.0.1
listen_port = 6432
auth_type = scram-sha-256
auth_file = /etc/pgbouncer/userlist.txt
pool_mode = transaction
max_client_conn = 1000
default_pool_size = 25
query_wait_timeout = 120
admin_users = postgres
EOF

# Generate the auth file (PostgreSQL scram-sha-256 passwords)
# The format is: "username" "scram-sha-256-<hash>"
# Pull the hash from PostgreSQL:
psql -c "SELECT usename, passwd FROM pg_shadow WHERE usename='postgres';"
# Copy the passwd into /etc/pgbouncer/userlist.txt as:
#   "postgres" "SCRAM-SHA-256$4096:base64salt$base64storedkey:base64serverkey"

# Start PgBouncer
sudo pgbouncer -d /tmp/pgbouncer.ini

# Connect through PgBouncer (note port 6432, not 5432)
psql -h 127.0.0.1 -p 6432 -U postgres postgres

# Inside that psql session, switch to the PgBouncer admin database
\c pgbouncer
SHOW POOLS;          -- per (db, user) pool stats: cl_active, cl_waiting, sv_active, sv_idle, sv_used, sv_tested, sv_login, maxwait
SHOW CLIENTS;        -- list of connected clients with their state and pool
SHOW SERVERS;        -- list of server connections PgBouncer has opened
SHOW STATS;          -- total_xact_count, total_query_count, total_received, total_sent, total_xact_time, total_query_time, avg_query_time
SHOW CONFIG;         -- current value of every config knob
SHOW MEM;            -- PgBouncer's own memory usage by pool
RELOAD;              -- reload config without restart (most settings)
PAUSE;               -- pause all client connections (for maintenance)
RESUME;              -- resume after PAUSE
```

```sql
-- Demonstrate the prepared-statement problem in transaction mode
-- Connect via psql -p 6432 (PgBouncer in transaction mode)
PREPARE find_user AS SELECT * FROM users WHERE id = $1;
EXECUTE find_user(1);
-- works the first time

-- Now end the transaction and start a new one
BEGIN;
EXECUTE find_user(2);
-- ERROR: prepared statement "find_user" does not exist
-- Because the new transaction landed on a different server connection
-- that never saw the PREPARE.
ROLLBACK;

-- Fix: use SET LOCAL inside the transaction, or upgrade PgBouncer to 1.21+
-- and set max_prepared_statements = 100 in pgbouncer.ini
```

```bash
# Load test: simulate 500 concurrent clients through PgBouncer
# (requires pgbench, which is in postgresql-contrib)
pgbench -h 127.0.0.1 -p 6432 -U postgres -c 500 -j 4 -T 60 postgres
# -c 500: 500 concurrent clients
# -j 4:   4 threads
# -T 60:  run for 60 seconds

# While pgbench is running, in another terminal:
watch -n 1 'psql -h 127.0.0.1 -p 6432 -d pgbouncer -c "SHOW POOLS;"'
# You'll see cl_active climb to 500, but sv_active stays at ~25.

# Compare to direct connection (no PgBouncer):
pgbench -h 127.0.0.1 -p 5432 -U postgres -c 500 -j 4 -T 60 postgres
# This will fail with "FATAL: sorry, too many clients already" at 100 clients
# unless you've raised max_connections on PostgreSQL.
```
