# 06.10.04. Caching Patterns and Failure Modes

## What This Is

A cache is a lie agreed upon between the application and the database: "I will tell you the answer is X; you trust me until I tell you otherwise, and the database is the only source of truth you can fall back to when I am wrong." Caching patterns codify the *who-writes-the-cache-and-when* of that agreement — cache-aside, write-through, write-behind, read-through — and the failure modes describe the specific ways the lie breaks down: stampede, penetration, avalanche, dog-pile, thundering herd. Every production cache incident is one of these patterns misapplied or one of these failure modes unmitigated.

In the layered mental model, caching sits between the framework's data-access layer (Spring's `@Cacheable`, Django's cache framework, Laravel's `Cache::remember`) and the underlying Redis/Memcached client. The framework annotations are thin wrappers around five primitive operations: `GET`, `SET` (with TTL), `DEL`, `EXISTS`, and the conditional `SETNX`. The cache itself sits on top of the same TCP/socket primitives from section 02.03 and the same RESP/ASCII protocols from section 03.05 — it is a stateful network service with millisecond timeouts and failure semantics all its own. This note covers the canonical topologies, the Redis eviction policies that govern what gets thrown away when memory fills, and the production failure modes that every on-call engineer eventually meets.

## The Details

### Caching Topologies: Cache-Aside (Lazy Loading), Write-Through, Write-Behind (Write-Back)

**Cache-aside** (a.k.a. lazy loading) is the default pattern in 95% of applications. The application talks to the cache and the database independently: on read, it tries `GET cache:<id>`; on miss, it queries the database, calls `SET cache:<id> <value> EX 300`, and returns. On write, it writes to the database and then immediately `DEL cache:<id>` so the next read sees fresh data. The "aside" in the name refers to the cache sitting *beside* the database, not in front of it. The advantage is simplicity and graceful degradation — if the cache is down, the application reads from the database directly. The disadvantage is *stale-on-write*: between the database write and the cache `DEL`, a concurrent read can still serve the old value. Spring's `@Cacheable` / `@CacheEvict` annotations implement this exact pattern.

**Write-through** puts the cache *between* the application and the database — every write goes to the cache first, and the cache synchronously writes through to the database before returning. The application never talks to the database directly. Read is trivially `GET cache:<id>` and the cache is guaranteed consistent because every write passes through it. The advantage is no stale reads ever — the cache is the single source of truth for the application. The disadvantage is doubled write latency (cache write + db write must both succeed before ack) and a hard failure mode: if the cache is down, *writes are impossible*, not just slower. This pattern is rare in web backends and common in hardware (CPU caches are write-through to L2/L3) and in CDNs (CloudFront writes-through to S3).

**Write-behind** (write-back) is the most aggressive: writes go to the cache only, and the cache asynchronously flushes to the database in the background — batched, coalesced, optionally durable. The application sees write latency equal to the cache write (sub-ms for Redis) regardless of database health. The advantage is enormous write throughput — a Redis cluster can absorb 100k writes/sec even if the database is a single Postgres instance that caps at 5k writes/sec, because the cache coalesces 20 `INCR`s into one `UPDATE`. The disadvantage is data loss risk: if the cache crashes before flushing, committed writes vanish. Memcached explicitly does *not* support write-behind because it has no persistence; Redis with AOF `everysec` is the usual substrate; the database's `wal_level=logical` plus a worker replaying the Redis stream is the canonical implementation. Spring Cache does not ship this; you build it with a `BlockingDeque` + scheduled executor or a Kafka topic + consumer.

```text
  Cache-Aside (lazy loading)        Write-Through               Write-Behind

  App ──► Cache                     App ──► Cache               App ──► Cache
   │ miss    │ miss                  │        │                  │        │
   │         ▼                       │        ▼ (sync)           │        ▼ (async, batched)
   ▼       DB                       ▼       DB                  ▼       DB

  read: cache OR db                 read: cache only             read: cache only
  write: db, then DEL cache         write: cache→db (sync)       write: cache only; flush later
  stale window: db-write..DEL       stale window: never          stale window: until flush
  cache down: degraded reads        cache down: writes fail      cache down: data loss
```

The production failure mode specific to cache-aside is the **double-read inconsistency under concurrent write**. Thread A reads cache (miss), queries DB (gets v1), is about to `SET cache v1`. Thread B writes DB v2, then `DEL cache`. Thread A now `SET`s v1, which is stale. The cache holds v1 forever (until TTL) even though the DB has v2. The fix is the **read-through with versioned value** pattern: store `{"value": v, "version": n}` in the cache and use `SETNX` or a Lua compare-and-set to ensure a stale write does not overwrite a fresher one. For write-through, the failure mode is **cache-down = total write outage** — you must have a circuit breaker that falls back to direct-DB writes, accepting that the cache must be rewarmed later. For write-behind, the failure mode is **acknowledged-but-lost writes on cache crash** — which is why every write-behind system needs a durable redo log (Redis AOF) and a startup replay path, and why you should never use write-behind for financial transactions.

### Eviction Algorithms: `volatile-lru`, `allkeys-lru`, `volatile-lfu`, `allkeys-lfu`, `volatile-ttl`, `noeviction`

When Redis hits `maxmemory`, it must throw something away before accepting the next write. The `maxmemory-policy` directive chooses the algorithm. Six policies ship in the box:

- **`noeviction`** — refuse writes with `OOM command not allowed when used memory > 'maxmemory'`. Reads still work. Use this for databases-that-happen-to-be-in-Redis; never for caches. The right answer when an OOM is a bug to investigate, not a behaviour to mask.
- **`allkeys-lru`** — evict the least-recently-used key across the entire keyspace. Classic cache behaviour. Approximate LRU (sampled, default 5 keys) since exact LRU requires a global linked-list mutation on every access which kills single-threaded throughput.
- **`volatile-lru`** — same LRU but only over keys with a TTL set. Use when you have a mix of cached (TTL'd) and persistent (non-TTL'd) keys in the same instance and you want the cache portion to absorb eviction pressure.
- **`allkeys-lfu`** (4.0+) — least-frequently-used. Tracks a logarithmic counter of access frequency per key; a key accessed 100 times survives longer than one accessed once 100 hours ago. Better than LRU for scan-heavy workloads where a one-time `KEYS *` would otherwise pollute the LRU.
- **`volatile-lfu`** — LFU over TTL'd keys only.
- **`volatile-ttl`** — evict the key with the shortest remaining TTL. Approximates "this key is about to expire anyway, may as well reclaim now."

The LRU/LFU implementations are **approximate**, not exact. Redis samples `maxmemory-samples` (default 5) random keys per eviction and picks the best candidate from the sample. Bumping `maxmemory-samples` to 10 brings the approximation within 1% of true LRU at the cost of ~50% more CPU per eviction — usually worth it on a busy cache. LFU's counter is a Morris-style probabilistic counter: it increments with probability `1 / (counter * lfu_log_factor + 1)` so it saturates slowly; a counter at 255 represents somewhere between 100k and 10M accesses. Decay is handled by `lfu-decay-time` (default 1 minute): every `lfu-decay-time` minutes, the counter is halved, so an idle hot key eventually cools.

```text
  Memory pressure timeline (allkeys-lru, maxmemory-samples=5):

  T0: Redis at 99% maxmemory
  T1: SET newkey → triggers eviction
       Redis samples 5 random keys: [A,B,C,D,E]
       Picks least-recently-used of the 5 (say B)
       DEL B; SET newkey
       (B may not be the true LRU — but statistically close enough)
  T2: Another SET → samples 5 different keys, evicts the worst
  ...
  T3: Steady state — eviction rate = new-key ingress rate

  maxmemory-samples 5  → ~80% as good as true LRU
  maxmemory-samples 10 → ~95% as good as true LRU
  maxmemory-samples 20 → ~99% as good, but 4× eviction CPU
```

The production failure mode unique to eviction is the **cache warm-up cliff**. A freshly-restarted Redis instance with `allkeys-lru` will absorb every write for the first few minutes, then hit `maxmemory` and start evicting aggressively — but it has no real LRU signal yet, so the "least recently used" is effectively random. The working set is not yet resident, so every read is a miss, so every read triggers a database round-trip, so the database melts. The mitigations: (1) warm the cache from a snapshot (`redis-cli --rdb dump.rdb` then `redis-cli --pipe` replay) before opening traffic; (2) use `volatile-lfu` instead of LRU — LFU's frequency counter converges to the true distribution in a few thousand accesses, much faster than LRU's tail; (3) cap the database's `max_connections` during cache warm-up so the thundering herd caps at the pool size, not at the connection backlog.

### Critical Failure Modes and Mitigations

There is a famous saying that "there are only two hard problems in computer science: cache invalidation and naming things." Cache failure modes are all variants of the invalidation problem — the cache says one thing, the database says another, and the application must decide which to believe. The four canonical failure modes are **stampede**, **penetration**, **avalanche**, and **bigkey eviction**, each with a specific mitigation.

| Failure mode | What happens | Tell-tale metric | Mitigation |
|---|---|---|---|
| Stampede (thundering herd) | Hot key expires; 1000s of requests miss simultaneously, all hit DB | DB QPS 10× normal for 1 TTL window | Mutex lock, probabilistic early expiration (XFetch) |
| Penetration | Queries for non-existent keys bypass cache (every miss = DB hit); attacker can DoS by random keys | Cache hit ratio drops below 60% with no traffic spike | Cache null values with short TTL, or Bloom filter pre-check |
| Avalanche | Many keys expire at the same time; bulk DB spike | DB QPS spike aligns with `:00` minute boundary | TTL jitter (`EX ttl + rand(0, 60)`) |
| Bigkey eviction | A single 1 MB String gets evicted under memory pressure; sudden 1 MB alloc/free churns allocator | `evicted_keys` spikes; `mem_fragmentation_ratio` rises | Split big values; use `UNLINK` not `DEL`; raise `maxmemory` |

The deeper insight is that **every cache failure mode is a herd coordination problem**. N concurrent threads all see the same miss and all independently decide to fetch, compute, and write — but only one of them needed to. The fix in every case is to break the symmetry: a mutex lock makes one thread the "winner" and the rest wait; probabilistic early expiration makes a random subset of threads refresh early; a Bloom filter makes the herd *see* the negative answer in the cache so there is no miss to coordinate. This is the same herd-coordination pattern as the **thundering-herd problem in accept()** from section 02.04 — multiple processes woken on the same listening socket, only one accepts, the rest go back to sleep. The fix in both cases is the same: serialize the herd.

The mitigation hierarchy, from least to most invasive: (1) **jitter the TTL** — every `SET` becomes `EX ttl + rand(0, ttl/10)`. Costs nothing, prevents 90% of avalanche scenarios. (2) **Cache null values with short TTL** — `SET user:nonexistent "__NULL__" EX 60`. Costs a few extra cache entries, prevents penetration. (3) **Probabilistic early expiration (XFetch)** — see next section. Costs ~1 ms per request for the probability calc, prevents stampede for hot keys. (4) **Per-key mutex lock** — `SETNX lock:<key> 1 EX 5` and the loser polls `GET cache:<key>`. Costs one extra round-trip per miss, the only fully-correct stampede fix. (5) **Bloom filter as a negative cache** — a separate Redis structure (or RedisBloom module) tracks "definitely-not-in-DB" keys. Costs ~10 bits per key, prevents penetration at scale. (6) **Read-through wrapper** — the application only ever calls `cache.get(key, loader=...)` and the cache itself handles the miss+fill atomically. Costs framework complexity, eliminates the entire class of bugs at the API boundary.

### Cache Stampede / Thundering Herd: Mutex locking, probabilistic early expiration (XFetch)

The cache stampede is the most expensive failure mode in production. The scenario: a hot key (say, `homepage:featured_products`) is cached with `EX 300`. At the moment of expiry, 1000 concurrent requests are in-flight — all of them see the miss, all of them query the database, all of them compute the same expensive result, all of them `SET` the cache. The database sees a 1000× spike for the duration of the rebuild. If the rebuild takes 500 ms and the database cap is 200 concurrent queries, the database pool exhausts and the entire site times out for that 500 ms. Repeat every 5 minutes.

The **mutex lock** is the textbook fix. The first thread to see a miss acquires a per-key lock (`SETNX lock:homepage:featured_products 1 EX 5`), rebuilds the cache, releases the lock (`DEL lock:homepage:featured_products`), and returns. Every other thread that sees a miss polls `GET cache:homepage:featured_products` in a short sleep loop (10 ms × 50 retries); when the lock holder finishes, all the pollers get the cached value without touching the database. The downside: if the lock holder crashes, the lock is held for `EX 5` seconds and every request polls for that full 5 seconds. The fix is `SET ... NX PX 5000` (millisecond precision) plus a watchdog that extends the lock if the rebuild is still running — which is exactly what Redisson's `RLock` does in the Java ecosystem.

The **probabilistic early expiration** algorithm (XFetch, from Vattani et al. 2015) is the elegant fix that requires no lock and no extra round-trips. Each thread, before reading the cached value, computes a probability of refreshing early based on how close the key is to expiry and how long the rebuild takes. The formula in pseudocode: `if (now - ttl_set_at > ttl - rebuild_time) and rand() < early_refresh_probability, then refresh`. Specifically:

```python
import random, time

def xfetch_get(cache, key, loader, ttl, beta=1.0):
    val, exp = cache.get_with_expiry(key)   # one round-trip
    if val is None:
        # hard miss — rebuild under lock (rare path)
        return _locked_rebuild(cache, key, loader, ttl)
    now = time.time()
    remaining = exp - now
    if remaining <= 0:
        # expired — rebuild under lock
        return _locked_rebuild(cache, key, loader, ttl)
    # XFetch: probabilistically refresh early
    # beta=1 means "as soon as the average rebuild time would overlap expiry"
    # higher beta = more aggressive early refresh
    if random.random() < beta * (rebuild_time_avg / remaining):
        # race to rebuild — loser sees the new value, no lock needed
        try:
            new_val = loader()
            cache.set(key, new_val, ex=ttl)
            return new_val
        except Exception:
            return val   # rebuild failed, return stale
    return val
```

The beauty is that the *rate* of early refreshes is automatically tuned by `beta` and the rebuild-time estimate. With `beta=1` and a 50 ms average rebuild, a key with 5 s remaining TTL refreshes with probability ~1%; with 100 ms remaining, ~50%; at expiry, ~100%. The herd does not coordinate, but the math coordinates them — only ~1 thread out of the 1000 will refresh early because only 1% × 1000 = 10 refreshes happen in the last 5 seconds, distributed roughly uniformly. Netflix deployed XFetch across their API tier in 2016 and reported a 90% reduction in cache-stampede incidents. The production failure mode: if `rebuild_time_avg` is mis-estimated (say, set to 50 ms when actual is 5 s), the formula dramatically under-refreshes and the stampede returns. Always measure rebuild time with a moving average, never a static config value.

### Cache Penetration: Storing null values, Bloom Filters

Cache penetration is the opposite failure: instead of a popular key expiring, the cache is *never* populated because the keys do not exist in the database. Every `GET user:<random_id>` is a miss, every miss queries the database, every database query returns nothing, and the cache is never written (because there is nothing to write). An attacker (or a buggy client iterating a deleted range) can DoS the database by hammering random IDs. The hit ratio collapses; the database CPU saturates.

The simple fix is **caching null values with a short TTL**: when the database returns nothing, write `SET user:<id> "__NULL__" EX 60`. The next request for the same ID hits the cache, sees the null marker, and skips the database. Two production gotchas: (1) the null marker must be distinct from a real value — use a sentinel like `"__NULL__"` or a separate `null:` prefix key, never cache the literal `null` (it is indistinguishable from a JSON-serialised null value); (2) the TTL must be short (60–300 seconds) so that when the database eventually gets the row (e.g. a user is created), the cache converges quickly. The memory cost is bounded by the rate of unique-not-found queries times the TTL — typically a few MB even under attack.

The scalable fix for high-volume penetration is a **Bloom filter** as a negative cache. A Bloom filter is a bit array of `m` bits and `k` hash functions. To insert a key, set bits `[h1(key), h2(key), ..., hk(key)]` to 1. To test membership, check that all `k` bits are 1; if any is 0, the key is definitely not in the set; if all are 1, it is probably in the set (with false positive rate `p ≈ (1 - e^(-kn/m))^k`). For 10M database IDs, a 14.3 MiB Bloom filter with `k=7` gives a 1% false positive rate — so 99% of penetration queries are intercepted before the database. The RedisBloom module ships `BF.ADD` / `BF.EXISTS` natively; without the module you build it in application memory (Guava `BloomFilter` in Java, `pybloom-live` in Python) and refresh it periodically from a database scan.

```text
  Cache penetration with Bloom filter pre-check:

  Request: GET user:999999999
       │
       ▼
  ┌─────────────────────┐
  │ Bloom filter check  │
  │  BF.EXISTS users    │
  │  999999999          │
  └──────────┬──────────┘
             │
   ┌─────────┴─────────┐
   │ false             │ true (maybe — 1% FPR)
   ▼                   ▼
  return 404         ┌──────────────────────┐
  (no DB hit)        │ Cache GET user:...   │
                     └──────────┬───────────┘
                                │
                                ├── hit ──► return value
                                └── miss ─► DB lookup → return value, SET cache
```

The production failure mode of the Bloom filter is the **stale-filter problem**. When a new row is inserted in the database, the Bloom filter must be updated — but if the application code that inserts the row forgets to `BF.ADD`, the new row is invisible to the cache layer (every read says "probably not in set" and the application returns 404). The fix is to make the `BF.ADD` part of the same database transaction (or a transactional outbox) so it cannot be skipped. The second failure mode is **Bloom filter sizing**: a filter sized for 1M keys at 1% FPR that grows to hold 100M keys degrades to ~100% FPR (every bit becomes 1). The filter must be sized for the projected growth, or rebuilt periodically (RedisBloom supports `BF.RESERVE` with capacity and `BF.SCANDUMP` / `BF.LOADCHUNK` for serialised rebuilds).

### Cache Avalanche: Randomizing TTL expirations with jitter

Cache avalanche is the bulk version of stampede: many keys expire at the same instant, all of them rebuild simultaneously, and the database sees a synchronized spike. The classic trigger is **bulk warmup with identical TTLs**: an application boots, calls `Cache::put(k, v, 300)` for 10,000 keys in a loop, and 300 seconds later all 10,000 keys expire at the same millisecond. The database QPS graph shows a flat baseline punctuated by a 10,000× spike every 5 minutes. A second trigger is **deployment with TTL alignment**: a deploy at 12:00:00 warms the cache, every instance writes the same `EX 300`, and at 12:05:00 every instance's cache expires simultaneously.

The fix is **TTL jitter**: every `SET` adds a small random offset to the TTL so that expirations distribute across the window. `EX 300 + rand(0, 30)` spreads expirations across 300–330 seconds, turning a 10,000× spike into a ~330× sustained bump over 30 seconds. The math: if N keys are warmed in a window of W seconds with TTL T, jitter of `T/10` reduces the peak spike by roughly a factor of 10. Every framework exposes this differently:

```python
# Django — explicit jitter
import random
cache.set(key, value, timeout=300 + random.randint(0, 30))

# Spring — SpEL or custom RandomKeyGenerator
@Cacheable(value="users", key="#id")
// default TTL from config; jitter requires a custom RedisCacheWriter:
class JitteredRedisCacheWriter extends DefaultRedisCacheWriter {
    @Override
    public void put(String name, byte[] key, byte[] value, Duration ttl) {
        long jitterMs = ThreadLocalRandom.current().nextLong(0, ttl.toMillis() / 10);
        super.put(name, key, value, ttl.plusMillis(jitterMs));
    }
}

# Express (ioredis)
const ttl = 300 + Math.floor(Math.random() * 30);
await redis.set(key, value, 'EX', ttl);

# Laravel
Cache::put($key, $value, now()->addSeconds(300 + rand(0, 30)));
```

The subtle variant of avalanche is **dog-pile on a single hot key with multiple instances**. Suppose `config:feature_flags` is cached with `EX 60`. Three app instances each maintain their own Redis cache (or, worse, their own in-process cache in front of Redis). At 12:00:00 all three write the same key with `EX 60`. At 12:01:00 all three miss simultaneously, all three query the database, all three `SET` again. Repeat every minute. Jitter alone does not fix this because the jitter is applied at write time, and all three instances write at the same time. The fix is to **jitter the read-check** as well: each instance, before declaring a miss, checks `TTL cache:key` and if `TTL < 5` seconds, *probabilistically* decides to refresh early (XFetch from the previous section). This breaks the symmetry between the three instances because each sees a different random outcome. Avalanche and stampede collapse into the same problem — coordination of concurrent rebuilds — and XFetch solves both.

The final avalanche flavour is **cold-start avalanche** after a Redis restart. The cache is empty, every request is a miss, the database melts. The only robust fix is **cache warm-up before traffic**: load the RDB snapshot, run a background rewarmer that pre-fetches the top 10,000 keys by traffic, and only then open the load balancer. AWS ElastiCache's "snapshots" feature and Redis Cluster's `CLUSTER FAILOVER` command both support this — a failover takes 10–30 seconds, but the new primary inherits the warm cache from the snapshot, so traffic resumes without a cold-start spike.

## Cross-Ecosystem Implementation

Every framework's cache abstraction supports the four caching topologies through annotations or explicit calls. The differences are in the default topology and the failure-mode mitigations shipped out of the box.

| Topology / Fix | Spring (`@Cacheable`) | Express (ioredis) | Django (`cache`) | Laravel (`Cache`) |
|---|---|---|---|---|
| Cache-aside | `@Cacheable` + `@CacheEvict` | manual `get/set/del` | `cache.get_or_set` | `Cache::remember` |
| Write-through | custom `CachePutAdvice` | manual `set` + `db.update` | manual `cache.set` + `model.save` | manual `Cache::put` + `Model::save` |
| Write-behind | Redisson `RBlockingQueue` | BullMQ + worker | Celery task + `cache.set` | Laravel Queue + `Cache::put` |
| TTL jitter | custom `RedisCacheWriter` | inline `Math.random()` | `random.randint()` | `rand()` |
| Mutex on miss | `@Cacheable(sync=true)` | `redlock` npm | `cache.lock()` (django-cacheops) | `Cache::lock()` |
| Bloom filter | Guava `BloomFilter` | `bloom-filters` npm | `pybloom_live` | `bloom` package |

Spring's `@Cacheable(sync=true)` is the only one of the four that ships a per-key mutex out of the box — it uses `synchronized` on the cache key so concurrent misses block on the lock and only one thread loads. The others require explicit locking. Laravel's `Cache::lock($key, $ttl)->block($wait, fn() => ...)` is the most ergonomic — it implements a Redis-backed RedLock with auto-release. Django and Express typically reach for `redis-py`'s `Lock` or the `redlock` npm package respectively.

## Hands-On Exercise

```bash
# Observe the stampede live — set up a hot key and let it expire
redis-cli SET hotkey "v1" EX 5
# in 4 other terminals, run this loop:
for i in $(seq 1 100); do
  redis-cli GET hotkey
  # when miss, simulate DB rebuild:
  redis-cli SET hotkey "v$(date +%s)" EX 5
  sleep 0.05
done
# watch the DB-hit rate spike at each expiry — then add a mutex and watch it flatten

# Build a per-key mutex with SETNX
redis-cli SETNX lock:hotkey 1 EX 5    # returns 1 = acquired, 0 = held by someone else
# holder: rebuild, then DEL
redis-cli DEL lock:hotkey
# pollers: short sleep loop on GET hotkey until non-nil

# Bloom filter (RedisBloom module required)
redis-cli BF.RESERVE users 10000000 0.01     # 10M capacity, 1% FPR
redis-cli BF.ADD users 42
redis-cli BF.EXISTS users 42                  # 1 (definitely yes)
redis-cli BF.EXISTS users 99999               # 0 (definitely no)
redis-cli BF.EXISTS users 12345               # 1 (probably yes — false positive ~1%)

# TTL jitter — watch expirations spread
for i in $(seq 1 1000); do
  redis-cli SET "k:$i" "v" EX $((300 + RANDOM % 30)) > /dev/null
done
redis-cli DEBUG SLEEP 305
# now scan and confirm expirations are spread across 30s, not bunched at 0

# Cache null marker
redis-cli SET user:9999999 "__NULL__" EX 60
redis-cli GET user:9999999   # "__NULL__" — skip the DB
# tell real value from null marker in your app:
#   if value == "__NULL__": return None
#   else: return value

# Production monitor — hit ratio, eviction, key count
redis-cli INFO stats | grep -E "keyspace_hits|keyspace_misses|evicted_keys|expired_keys"
redis-cli INFO memory | grep -E "used_memory_human|maxmemory_human|mem_fragmentation_ratio"
```
