# 06.10.02. Core Data Structures and Algorithmic Complexities

## What This Is

Redis is not a hash map with a network port glued on. Each of its five core types (String, List, Hash, Set, Sorted Set) plus the four extended types (Bitmap, HyperLogLog, Geo, Stream) is backed by a different in-memory encoding, and Redis will transparently swap encodings as data grows. The choice of structure is a choice about *which operations are O(1)* and which degrade to O(N) — and because Redis is single-threaded for command execution, an O(N) command with the wrong structure is not just slow, it blocks every other client on the box. This note covers the encodings, the algorithmic complexities, and the encoding thresholds that govern the swap from compact (listpack/intset) to verbose (hashtable/skiplist/quicklist) representations.

In the layered mental model, Redis data structures sit one layer above the raw memory allocator (jemalloc) and one layer below the RESP protocol parser. They are the direct descendants of the kernel primitives in section 02 — `mmap`-backed shared pages during fork, `memcpy` for snapshot persistence, and the same pointer-chase-friendly layouts you would write in C if you were implementing a B-tree by hand. Every Spring Boot / Express / Django / Laravel cache abstraction in section 05 ultimately surfaces these structures: `RedisTemplate.opsForList()` in Spring, `redis.lpush()` in Node ioredis, `cache.lpush()` in Laravel — they are all thin RESP wrappers around the same five native types.

## The Details

### Strings (SDS - Simple Dynamic Strings), Lists (QuickLists / ZipLists), Sets (IntSets / Hash Tables), Hashes (ZipLists / Dicts), Sorted Sets (SkipLists + Hash Tables)

**Strings** are the most overloaded type in Redis. Internally they are SDS — Simple Dynamic Strings — which prepend a header (`len`, `alloc`, `flags`, `sdshdr5..sdshdr64`) before the payload so `STRLEN` is O(1) and binary-safe `\\0` bytes are legal. The payload is capped at 512 MiB (`proto-max-bulk-len`). A String is not just text: it is also a counter (`INCR`/`INCRBY`/`INCRBYFLOAT` operate on the same byte buffer interpreted as an integer/float), a bit-field (`BITCOUNT`, `BITOP`, `SETBIT` — backed by the SDS buffer directly), and a serialized object blob (`SET user:1 "{...}"`). The same 8 bytes can be parsed as a string, a long, or a bit array depending on the command — this is why `SET counter 10` followed by `APPEND counter 0` produces `"100"` and not an error.

**Lists** are doubly-linked lists of ziplist nodes — Redis calls this `quicklist`. Each node is a contiguous ziplist (a length-prefixed, variable-length-integer packed array) holding up to `list-max-ziplist-size` entries (default 8 KiB or -2 = 8 KiB). LPUSH/RPUSH/LPOP/RPOP are O(1) at the head/tail ziplist; LRANGE is O(S+N) where S is the distance to skip. The old "ziplist only" encoding (pre-3.2) had a `O(N^2)` rewrite on large lists; quicklist fixed this. **Sets** start life as `intset` — a sorted, contiguous array of `int16_t`/`int32_t`/`int64_t` — when all elements are integers and the count is under `set-max-intset-entries` (default 512). intset gives binary-search O(log N) lookups and zero per-element pointer overhead; past the threshold Redis promotes the set to a hashtable for O(1) operations.

**Hashes** use listpack (Redis 7.0+, formerly ziplist) when both field count ≤ `hash-max-listpack-entries` (default 128) and any single value ≤ `hash-max-listpack-value` (default 64 bytes). Listpack is the modern replacement for ziplist with a saner encoding and no cascading-update problem; HGET/HSET are O(N) on listpack but the constant factor is tiny because the whole thing fits in a few cache lines. Past the threshold, the hash is promoted to a real hashtable (separate chaining, jemalloc-allocated dictEntry nodes) where HGET/HSET become O(1) average. **Sorted Sets** are the most intricate type: they are *two* data structures held together — a skiplist for range queries (ZRANGE, ZRANGEBYSCORE) and a hashtable for point lookups (ZSCORE). The skiplist has an expected height of `log2(N)` and O(log N) insert/lookup; the hashtable gives O(1) ZSCORE. Memory cost is roughly 32 bytes per element on the skiplist plus 16 bytes in the dict. Small zsets (under `zset-max-listpack-entries` = 128 and `zset-max-listpack-value` = 64 bytes) use listpack instead and are 5–10× smaller.

```text
Encoding thresholds (Redis 7.x defaults):

  Hash       listpack  ──►  hashtable       when  > 128 entries  OR  value > 64 B
  ZSet       listpack  ──►  skiplist+dict    when  > 128 entries  OR  value > 64 B
  List       quicklist (always; each node is a listpack, max 8 KiB/node)
  Set        intset    ──►  hashtable       when  > 512 entries   OR  any non-int member
  Hash       listpack  ──►  hashtable       (same as above)
```

The production failure mode here is the **bigkey encoding flip**. A Hash sitting at exactly 128 fields with 64-byte values uses ~25 KiB as a listpack; one extra field of 65 bytes triggers promotion to a hashtable, which is 4–8× larger and causes a single ms-level latency spike during the `dictAdd` migration. On a 100 GB Redis instance with millions of borderline hashes, this manifests as `used_memory_rss` jumping 30% overnight as traffic pushes hashes over the threshold. The fix is to monitor `INFO memory` for `mem_fragmentation_ratio` and to use `MEMORY USAGE key SAMPLES 0` on borderline keys during off-peak — and to set the thresholds deliberately (`hash-max-listpack-entries 256`) if your access pattern is read-heavy and never iterates the full hash.

| Type | Compact encoding | Verbose encoding | Flip threshold (default) | Headline complexity |
|---|---|---|---|---|
| String | SDS (always) | SDS embstr/raw | 44-byte boundary | O(1) GET/SET |
| List | quicklist (listpack nodes) | same | none | O(1) LPUSH/RPOP, O(S+N) LRANGE |
| Hash | listpack | hashtable | 128 entries / 64 B | O(1) HSET/HGET after promotion |
| Set | intset | hashtable | 512 entries / non-int | O(log N) SISMEMBER intset, O(1) hashtable |
| ZSet | listpack | skiplist + dict | 128 entries / 64 B | O(log N) ZADD, O(1) ZSCORE |

### Advanced structures: Bitmaps, HyperLogLogs (probabilistic cardinality counting), Geospatial indexes, Streams

**Bitmaps** are not a separate type — they are a String viewed through `SETBIT`/`GETBIT`/`BITCOUNT`/`BITOP` commands. The underlying SDS buffer is grown lazily as bits are set: `SETBIT user:login:2024-01-15 1234567 1` allocates a ~154 KiB String if it does not exist. The killer use case is daily-active-user counting: one bit per user ID, one bitmap per day, `BITOP OR` over 30 bitmaps to get the 30-day unique set, `BITCOUNT` for the cardinality. For 100M users this is 12.5 MiB per day — a quarter the size of a HyperLogLog with the same error budget, and exact instead of approximate. The production gotcha: `BITOP` on N large bitmaps allocates an N×bitmap-size scratch buffer under the hood; `BITOP OR` across 365 daily bitmaps of 12 MiB each allocates 4 GiB transiently and will OOM a small instance. Pre-shard by month or use `BITOP NOT`-free incremental unions via Lua.

**HyperLogLog** is a probabilistic cardinality estimator — a fixed 12 KiB structure (16,384 6-bit registers) that estimates the number of distinct elements with standard error ~0.81%. `PFADD user:uniq:2024-01 <id1> <id2> ...` adds elements; `PFCOUNT user:uniq:2024-01` returns the estimate; `PFMERGE month_uniq day1 day2 ... day31` fuses registers. Internally it is a String (the dense representation is `0x00 48 59 50 4c 4c ...` magic + sparse/dense register bytes), so it persists, replicates, and is RDB-snapshotted like any other String. The trade-off: HLL gives you cardinality in 12 KiB for *any* number of distinct elements (1 or 1 billion), but you cannot ask "is this element in the set" — it is a one-way hash. Use it for `uv`, `unique_visitors`, `distinct_users`; never for membership tests.

**Geospatial indexes** areSorted Sets in a clever disguise. `GEOADD points -122.41 37.78 "SF" -73.99 40.71 "NYC"` actually does `ZADD points:geohash <geohash(SF)> SF` where the score is a 52-bit interleaved-bit geohash of (lon, lat). `GEORADIUS points -122.41 37.78 100 km` is implemented as a ZRANGEBYSCORE over a computed geohash box plus a great-circle distance filter on the results. This is why geospatial commands have the same complexity as ZSet commands (O(log N + R) where R is result count) and why you cannot mix raw `ZADD` and `GEOADD` on the same key without corrupting the geohash invariant. The failure mode: geohash boxes near the poles and near ±180° longitude wrap around — `GEORADIUS` queries spanning the antimeridian return partial results unless you issue two queries. For global-scale geo, use PostGIS with GiST indexes instead (see [[06.07.02. B-Tree Variants, GiST, SP-GiST, GIN, and BRIN Indexes]]).

**Streams** are the newest (5.0) and most structurally interesting type — a log-structured radix tree of `(timestamp-sequence, field-value-pairs)` entries. `XADD logs * topic orders event created` appends an entry with an auto-generated ID `<ms>-<seq>`; `XRANGE logs - +` reads all; `XREAD COUNT 10 STREAMS logs 0` reads from offset; consumer groups (`XGROUP CREATE`, `XREADGROUP`, `XACK`) give Kafka-like at-least-once semantics with a pending-entries-list (PEL) tracking unacked deliveries. The radix tree means `XRANGE` over a time range is O(log N + R), not O(N) — you can hold a year of events and still seek to any timestamp in microseconds. Caps to know: max ID is `18446744073709551615-18446744073709551615`; stream length is bounded only by memory; `MAXLEN ~ N` (the tilde) trims approximately and is much faster than exact `MAXLEN N` because it skips the radix-tree rebuild. Production gotcha: streams do not auto-trim — an `XADD`-only workload grows memory unbounded; you must explicitly `XADD ... MAXLEN ~ 1000000` or run `XTRIM` on a schedule.

```text
Stream entry layout (radix tree leaf):

  ID: 1700000000000-0    Fields: [topic=orders, event=created, user_id=42]
       │                      │
       │                      └── listpack-encoded key/value pairs
       └── 64-bit ms timestamp + 64-bit sequence ( densely packed in radix key )

Consumer group state per stream:
  ┌─────────────────────────────────────────────┐
  │ last-delivered-id   : <ms>-<seq>            │
  │ pending-entries-list: radix tree of         │
  │   { entry-id, consumer, delivery-time,      │
  │     delivery-count }                        │
  │ consumers           : hashtable name → PEL  │
  └─────────────────────────────────────────────┘
```

The failure mode unique to advanced structures is **mistaking approximate for exact**. HyperLogLog's 0.81% error means `PFCOUNT` returns 1,008,100 when the truth is 1,000,000 — fine for dashboards, catastrophic for billing. Bitmap `BITCOUNT` is exact but only counts *set* bits, not distinct IDs across multiple days unless you `BITOP OR` first (which is the 4 GiB scratch problem above). Streams' `XPENDING` shows unacked entries but does not redeliver automatically — you must call `XCLAIM` or `XAUTOCLAIM` from a watchdog process or stuck consumers leak memory forever. Every advanced structure trades exactness, memory, or compute for a specific operation; if you cannot name the trade-off out loud, you should not be shipping it to production.

## Cross-Ecosystem Implementation

The five core Redis types surface nearly identically across all four target ecosystems — the abstraction is the RESP wire protocol, not the language. What differs is connection pooling, serialization, and the type-safe wrapper each framework provides.

| Operation | Spring (`RedisTemplate`) | Express (`ioredis`) | Django (`django-redis`) | Laravel (`Cache::redis`) |
|---|---|---|---|---|
| String | `opsForValue().set(k,v)` | `redis.set(k,v)` | `cache.set(k,v)` | `Cache::put(k,v)` |
| Hash | `opsForHash().put(k,f,v)` | `redis.hset(k,f,v)` | `cache.set(k, v, version=N)` (no native hash) | `Cache::put("k:f", v)` (no native hash) |
| List | `opsForList().leftPush(k,v)` | `redis.lpush(k,v)` | raw `client.lpush(k,v)` | `Cache::tags([...])` (workaround) |
| Set | `opsForSet().add(k,v)` | `redis.sadd(k,v)` | raw `client.sadd(k,v)` | not exposed |
| ZSet | `opsForZSet().add(k,v,s)` | `redis.zadd(k,s,v)` | raw `client.zadd(k,s,v)` | not exposed |
| Stream | `opsForStream().add(k,fields)` | `redis.xadd(k,"*",fields)` | raw `client.xadd(...)` | not exposed |

Spring's `RedisTemplate` is the only one of the four that exposes all five types as first-class templated APIs. Express's `ioredis` exposes them as raw commands (which is fine — the commands are the API). Django and Laravel's cache backends deliberately *only* expose String-equivalent `get/set` and serialize everything else — Hash, List, ZSet, Stream require dropping to the raw client. This is because the framework cache abstraction predates Redis-specific structures; the framework was designed to be backend-agnostic (file/memcached/redis all look the same). If you need ZSET semantics in Django or Laravel, you must bypass the cache abstraction and use `redis-py` / `predis` directly.

## Hands-On Exercise

```bash
# Watch encodings flip in real time as data crosses thresholds
redis-cli CONFIG SET hash-max-listpack-entries 4
redis-cli HSET h1 f1 v1 f2 v2 f3 v3 f4 v4
redis-cli OBJECT ENCODING h1          # -> "listpack"
redis-cli HSET h1 f5 v5               # crosses threshold
redis-cli OBJECT ENCODING h1          # -> "hashtable"

# Measure the memory cost of the encoding flip
redis-cli MEMORY USAGE h1             # before vs after
redis-cli DEBUG OBJECT h1             # serializedlength, type, encoding

# Bigkey audit — find any key whose encoding flip is imminent
redis-cli --bigkeys                   # samples SCAN, reports largest of each type
redis-cli --memkeys                   # Redis 7.4+, samples for memory usage

# HyperLogLog vs exact Bitmap — same cardinality, different cost
redis-cli PFADD hll_test $(seq 1 1000000)
redis-cli PFCOUNT hll_test            # ~1,008,100 (0.81% error)
redis-cli MEMORY USAGE hll_test       # ~12 KiB
redis-cli SETBIT bmp_test 1000000 1
redis-cli BITCOUNT bmp_test           # 1 (exact — but only one bit)
redis-cli MEMORY USAGE bmp_test       # ~125 KiB (only covers up to bit 1M)

# Stream consumer group lifecycle
redis-cli XADD orders '*' id 1 amount 50
redis-cli XGROUP CREATE orders order_grp '$'
redis-cli XREADGROUP GROUP order_grp consumer-1 COUNT 1 STREAMS orders '>'
redis-cli XPENDING orders order_grp    # see unacked entries
redis-cli XAUTOCLAIM orders order_grp consumer-2 0 0-0   # reclaim stuck
```
