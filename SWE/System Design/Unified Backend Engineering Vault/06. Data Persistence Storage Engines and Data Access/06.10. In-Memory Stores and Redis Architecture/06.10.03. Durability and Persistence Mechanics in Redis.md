# 06.10.03. Durability and Persistence Mechanics in Redis

## What This Is

Redis is an in-memory data store, but "in-memory" is not the same as "volatile". Since 1.1 (2009) Redis has shipped two persistence mechanisms — RDB snapshots and AOF (Append-Only File) — and since 4.0 it can combine them into a hybrid format that takes the best of both. The choice between RDB-only, AOF-only, hybrid, or "no persistence at all" is the single most consequential configuration on a Redis deployment: it directly determines how much data you lose on crash (Recovery Point Objective, RPO) and how fast each write returns (write latency). A misconfigured `appendfsync` policy is the difference between sub-millisecond writes with 1-second worst-case data loss, and 10-millisecond writes with zero data loss.

In the layered mental model, Redis persistence sits at the same layer as PostgreSQL's WAL and MySQL's InnoDB redo log (see [[06.04.01. ACID Properties and Transaction Isolation Levels]]). The same OS primitives — `fork(2)`, `fsync(2)`, `write(2)` — are in play. The difference is that Redis does not have a per-page WAL with redo/undo like a relational database; it has either (a) a coarse-grained binary snapshot of the entire keyspace or (b) a fine-grained append-only log of *commands* (not page mutations). This makes Redis persistence dramatically simpler than InnoDB's, but also makes some failure modes unique — most notably the "rewriting an AOF is a fork-and-replay, not a copy" surprise.

## The Details

### RDB (Redis Database Snapshotting): Point-in-time binary dumps generated via background child process fork (`bgsave`)

RDB is the original Redis persistence mechanism: a compact, binary, point-in-time snapshot of the entire keyspace written to `dump.rdb`. The mechanism is `fork(2)` + copy-on-write. The parent Redis process calls `fork()`, the child inherits the entire address space as read-only shared pages, and the child walks the keyspace serializing each key/value into the RDB format while the parent continues serving live traffic. Any write the parent does to a shared page triggers the kernel's COW (copy-on-write) fault and allocates a private page for the parent — so memory usage during `bgsave` can briefly spike to 2× the working set if the write rate is high.

The RDB file format is opaque but well-documented: a magic header (`REDIS0011`), a sequence of opcodes (`SELECTDB`, `RESIZEDB`, `EXPIRETIME_MS`, key-type-value tuples), a CRC64 checksum, and an EOF marker. Type-specific encodings are dense: a small hash is written as a listpack blob; an intset is written as a single typed blob; a String is `[length][bytes]`. A typical 10 GiB Redis instance produces a 4–6 GiB RDB file (compression from int/intset/listpack encodings) and the dump takes 30–90 seconds depending on disk throughput. Triggers: `save 900 1` (save if ≥1 key changed in 900s), `save 300 10`, `save 60 10000` — three overlapping rules. Disable with `save ""`.

```text
  Trigger fires (e.g. 10000 writes in 60s)
       │
       ▼
  ┌────────────┐   fork(2)
  │ parent     │ ────────────┐
  │ (serves    │             │
  │  live I/O) │        ┌────▼─────────┐
  └────────────┘        │ child        │
       ▲  COW fault      │ walk dict,   │
       │  on each        │ write rdb,   │
       │  dirty page     │ fsync,       │
       └─────────────────│ exit()       │
                          └────┬─────────┘
                               │ SIGCHLD
                               ▼
                       parent renames
                       temp-1234.rdb
                       → dump.rdb (atomic)
```

The headline trade-off of RDB is **RPO granularity**. A snapshot taken every 5 minutes means a crash can lose up to 5 minutes of writes. The headline advantage is **startup speed**: loading a 5 GiB RDB is 5–10× faster than replaying the equivalent AOF, because it is a sequential binary read rather than a command-by-command replay. RDB is also dramatically more compact than AOF on disk — often 3–5× smaller. Production deployment pattern: enable RDB as the long-term backup mechanism (one snapshot per hour, copied to S3 by a cron `bgsave && cp`), and use AOF for short-RPO durability. The failure mode to know: **`fork()` on a 100 GiB Redis instance blocks the main thread for 200–500 ms** while the kernel duplicates the page table — even though no pages are copied yet. On a busy box this manifests as a single latency spike at the top of every hour; the fix is `vm.overcommit_memory=1` (so fork never fails with ENOMEM), `transparent_hugepage=never` (THP doubles fork time), and `latency-monitor-threshold 100` to catch the spike in `LATENCY HISTORY event-loop`.

### AOF (Append-Only File): Logging every write command; `fsync` policies (`always`, `everysec`, `no`)

AOF is the operational inverse of RDB: instead of periodic snapshots, every write command (`SET`, `LPUSH`, `EXPIRE`, `DEL`, `HSET`, …) is appended to `appendonly.aof` *after* it executes in memory but *before* the response is sent to the client. The file is a plain-text stream of RESP-formatted commands — you can `cat appendonly.aof` and read it: `*3\r\n$3\r\nSET\r\n$3\r\nfoo\r\n$3\r\nbar\r\n`. On restart, Redis replays the file command by command, rebuilding the in-memory state exactly as it was at the last fsynced byte. This gives RPO bounded by the fsync policy, not by the snapshot interval.

The `appendfsync` policy is the single most important durability knob in Redis. Three choices:

- **`always`** — call `fsync(2)` after every command append. Zero data loss on crash (RPO=0). Cost: every write blocks on an fsync, which on NVMe is ~50–200 µs, on SATA SSD ~200–500 µs, on spinning disk 5–10 ms. Throughput drops to a few thousand writes/sec regardless of CPU.
- **`everysec`** (default) — fsync once per second from a background thread. Worst-case RPO = 1 second. The main thread never blocks on fsync; the background thread's fsync is independent. This is the sweet spot for 99% of deployments: sub-ms write latency with bounded 1-second loss.
- **`no`** — never call fsync explicitly; let the kernel's `dirty page writeback` (controlled by `vm.dirty_background_ratio` / `vm.dirty_ratio`) flush whenever it feels like it, usually every 30 seconds. Fastest writes, but RPO can be up to 30 seconds and you can lose acknowledged writes if the kernel has not flushed.

```text
  appendfsync = everysec  (the 99% case)

  main thread:                  background aio thread:
  ┌─────────────────────────┐   ┌────────────────────────┐
  │ SET foo bar             │   │ loop:                  │
  │ append to aof buffer    │   │   sleep until 1s tick   │
  │ write(2) to aof fd  ────┼───┼─► fsync(aof fd)        │
  │ reply +OK to client     │   │   (does not block      │
  │ (no fsync — proceeds)   │   │    main thread)        │
  └─────────────────────────┘   └────────────────────────┘

  Crash scenarios (everysec):
   • Crash between writes        → lose last sub-second of buffered writes
   • Crash between write+fsync   → lose ≤1s of writes (the in-flight fsync'd batch)
   • Power loss with FUA off     → lose ≤1s + whatever the disk cache held
```

The hybrid trick that turns everysec into near-zero RPO is `aof-use-rdb-preamble yes` (default since Redis 4.0). When this is on, an AOF rewrite produces a file with an RDB-encoded snapshot at the head (fast binary load) followed by incremental text AOF commands at the tail (fine-grained replay). You get RDB's fast startup *and* AOF's bounded RPO in one file. The failure mode to fear with AOF is **disk-full stall**: when the disk fills, `write(2)` returns ENOSPC, Redis blocks on every write command, and the latency graph flatlines at your `timeout` value. The mitigation is monitoring `aof_pending_bio_fsync` and `aof_buffer_length` in `INFO persistence`, alerting on `aof_delayed_fsync > 0`, and configuring `stop-writes-on-bgsave-error no` so a backup-disk-full does not take down the live cache. See [[06.04.03. Crash Recovery and the ARIES Algorithm]] for how a true redo-log database handles the same disk-full scenario with much more machinery.

### AOF Rewrite: Background compaction of historical commands into a minimal write sequence

An AOF file grows monotonically — `INCR counter` logged 1 million times is a 12 MiB file representing a single integer. The rewrite solves this: a background child process forks, walks the *current* in-memory keyspace, and emits the *minimal* sequence of commands that would reconstruct it. `INCR counter` × 1M becomes `SET counter 1000000`. A hash with 10,000 fields that was built up by 10,000 individual `HSET` commands becomes a single `HMSET` (or a sequence of `HMSET`s with 64 fields each to keep command size bounded). The rewrite typically shrinks the AOF by 70–95%.

The mechanism is identical to `bgsave`'s COW fork — same `fork(2)`, same page-table duplication cost, same memory spike risk. The difference is what the child emits: instead of binary RDB opcodes, it emits RESP text commands to `temp-rewriteaof-bg-<pid>.aof`. While the child works, the parent keeps serving live traffic and *also* keeps appending new write commands to a small in-memory **AOF rewrite buffer**. When the child finishes, the parent atomically renames the temp file to `appendonly.aof`, then appends the contents of the rewrite buffer to the tail — so no writes during the (potentially minutes-long) rewrite are lost. Triggers: `auto-aof-rewrite-percentage 100` (rewrite when file is 100% larger than the previous rewrite's size) and `auto-aof-rewrite-min-size 64mb` (do not bother rewriting tiny files). Manual trigger: `BGREWRITEAOF`.

```text
  T0: parent has 10 GB aof, 1 GB in-memory keyspace
       │
       │ BGREWRITEAOF (or auto trigger)
       ▼
  ┌─────────────────┐                    ┌──────────────────────┐
  │ parent          │     fork(2)        │ child                │
  │ - serve live    │ ──────────────────►│ - walk dict          │
  │ - append new    │                    │ - emit minimal SET/  │
  │   writes to     │                    │   HMSET/ZADD/etc     │
  │   aof_buf  AND  │                    │ - write to           │
  │   to rewrite_   │                    │   temp-<pid>.aof     │
  │   buf (in-mem)  │                    │ - fsync, exit()      │
  └─────────────────┘                    └──────────┬───────────┘
       ▲                                            │ SIGCHLD
       │  1. rename temp-<pid>.aof → appendonly.aof │
       │  2. append rewrite_buf bytes to aof         │
       │  3. resume normal append                    │
       └────────────────────────────────────────────┘
```

The headline failure mode of AOF rewrite is **memory amplification during the rewrite window**. The child inherits the parent's RSS via COW; if the parent is write-heavy, every dirty page becomes a private copy in the parent. A 10 GiB Redis with 50% write churn during a 60-second rewrite can balloon to 14–15 GiB RSS — which OOMs a 16 GiB box. The mitigations are: (1) cap the rewrite buffer so a runaway rewrite does not accumulate unbounded in-memory state (`aof-rewrite-incremental-fsync yes` fsyncs incrementally so the child's file does not pile up); (2) schedule rewrites during low-traffic windows (the `auto-aof-rewrite-percentage` trigger often fires during traffic spikes, the worst possible time — override with a cron that calls `BGREWRITEAOF` at 03:00 local); (3) leave 30–50% memory headroom on the box specifically for fork-COW, never pack Redis to 95% RSS. The second failure mode is **truncated AOF on crash mid-rewrite**: if Redis crashes while the rewrite buffer is being appended to the new file, the AOF can end with a half-written command. The fix is `aof-load-truncated yes` (default), which tells Redis on startup to log a warning and truncate the file at the last well-formed command — but the lost bytes are real writes. The final failure mode is the inverse: **`KEYS *` during the rewrite window** — the rewrite child holds the dict open, but a `KEYS *` in the parent scans the same dict; if the rewrite is mid-fork, the page-fault pattern causes the kernel to copy pages the parent only meant to read. Always use `SCAN` in production, never `KEYS`.

## Cross-Ecosystem Implementation

Redis persistence is configured at the Redis server (in `redis.conf`), not in the application — but every framework exposes "wait for the write to be durable" differently. The table below maps the four ecosystems' write-durability knobs.

| Ecosystem | How you wait for durability | Default behaviour |
|---|---|---|
| Spring (`RedisTemplate`) | `redisTemplate.waitForConnection(); connection.flush()` + `RedisCallback` returning server's `+OK` | Fire-and-forget; the RESP `+OK` is your ack |
| Express (`ioredis`) | `await redis.set(k, v)` — promise resolves on `+OK` | Same — RESP `+OK` ack |
| Django (`django-redis`) | `cache.set(k, v)` — synchronous, returns after `+OK` | Same |
| Laravel (`Cache::put`) | `Cache::put(k, v, $ttl)` — synchronous, returns `bool` | Same; bool reflects ack not fsync |

The crucial invariant: none of these frameworks know which `appendfsync` policy is configured on the Redis server. They all surface "the server replied `+OK`", which means the command is in the AOF buffer — not necessarily on disk. If you need application-level proof of fsync, you must call `WAIT numreplicas timeout` after the write — which is a Redis extension that blocks until N replicas have acknowledged the write, and is the only way to enforce strong durability across a Redis cluster from the client side. See [[06.10.01. Redis Architecture and Single-Threaded Processing]] for why `WAIT` works despite the single-threaded model.

## Hands-On Exercise

```bash
# Show current persistence config
redis-cli CONFIG GET save
redis-cli CONFIG GET appendonly
redis-cli CONFIG GET appendfsync
redis-cli CONFIG GET aof-use-rdb-preamble

# RDB round-trip — measure fork cost and file size
redis-cli DEBUG SET-ACTIVE-EXPIRE 0      # quiet the box
redis-cli DBSIZE
redis-cli MEMORY USAGE                    # rough working set
time redis-cli BGSAVE
redis-cli INFO persistence                # rdb_bgsave_in_progress, last_save_time
ls -lh /var/lib/redis/dump.rdb

# AOF — turn it on, measure write latency at each fsync policy
redis-cli CONFIG SET appendonly yes
redis-cli CONFIG SET appendfsync always
redis-benchmark -t set -n 100000 -c 10   # expect ~2-5k ops/sec (fsync-bound)
redis-cli CONFIG SET appendfsync everysec
redis-benchmark -t set -n 100000 -c 10   # expect ~80-120k ops/sec
redis-cli CONFIG SET appendfsync no
redis-benchmark -t set -n 100000 -c 10   # expect ~150-200k ops/sec

# Force an AOF rewrite and watch the file shrink
redis-cli SET counter 1
for i in $(seq 1 100000); do redis-cli INCR counter > /dev/null; done
ls -lh /var/lib/redis/appendonly.aof     # ~12 MB (100k * ~120 bytes)
redis-cli BGREWRITEAOF
ls -lh /var/lib/redis/appendonly.aof     # ~50 bytes (one SET command)

# Inspect the AOF — see the rdb preamble + tail commands
head -c 100 /var/lib/redis/appendonly.aof | xxd | head -5    # REDIS magic = rdb preamble
tail -c 200 /var/lib/redis/appendonly.aof | xxd              # text RESP commands

# Crash recovery test — kill Redis ungracefully and restart
redis-cli SET crash_test "this should survive"
redis-cli CONFIG SET appendfsync everysec
sleep 0.5  # ensure fsync happens
pkill -9 redis-server
redis-server /etc/redis/redis.conf
redis-cli GET crash_test                # should return "this should survive"
redis-cli GET counter                   # should return 100001
```
