# 06.10.01. Redis Architecture and Single-Threaded Processing

## What This Is

**Redis** is an in-memory key/value store that achieves its headline throughput numbers — 100,000+ operations per second on a single core, sub-millisecond p99 latency — by making three architectural choices that, at first glance, look insane and that turn out to be exactly right for an in-memory workload. First, **all data lives in RAM** (with optional disk persistence via RDB snapshots or append-only-file journaling, covered in [[06.10.03. Durability and Persistence Mechanics in Redis]]); the storage hierarchy has only one level — the main memory — and there is no disk on the hot path. Second, **all command execution happens on a single thread**; there are no locks, no mutex acquisition costs, no context switches between worker threads, and no memory-ordering surprises. Third, **all I/O is multiplexed** via `epoll_wait()` (Linux) / `kqueue` (BSD/macOS) / `WSAPoll` (Windows) — a single system call watches every connected client socket simultaneously and wakes up the Redis main thread only when one of them has data ready. The combination is what produces the throughput: every cycle the CPU spends is spent on actual work, not on coordination.

This note sits in section 06 (persistence) because Redis *is* a persistence layer — it is the L1/L2 cache that sits between the application and the OLTP database in nearly every modern backend, and its durability knobs (RDB vs AOF, `appendfsync` settings) determine what data survives a Redis crash. But the note also reaches back to section 02 (OS primitives) because the single-threaded event loop is the textbook application of the **Reactor pattern**: register every file descriptor with the kernel, call `epoll_wait` once, dispatch the ready events to handler functions, repeat forever. Node.js's libuv event loop, Nginx's worker loop, and Redis's main loop are all implementations of the same pattern — the differences are in what the handler functions do, not in the dispatch mechanism. Understanding Redis is understanding the extreme case of the Reactor pattern, where the entire server is one thread with no exceptions.

The single-threaded model is *not* a limitation that Redis 6 had to work around — it is the source of the speed. The misconception that "Redis is single-threaded, therefore it cannot use multiple cores" is wrong in a subtle but important way: a Redis *process* uses one core for command execution, but a typical production box runs 8–16 Redis processes (one per core, sharded by key hash via a client-side twemproxy or Redis Cluster), and each one of them runs at line rate. The alternative — one multi-threaded process that uses locks to protect shared data structures — would have *worse* p99 latency because of lock contention and context-switch overhead, even if the theoretical throughput on a contended workload were higher. The Redis authors chose single-threaded for the same reason Nginx chose multi-process-single-thread-per-worker: for the latency-bound cache workload, predictable low latency beats high average throughput every time.

## The Details

### Why Redis is fast: In-memory data access, single-threaded execution eliminating lock contention, non-blocking I/O multiplexing via `epoll`.

The three pillars of Redis's speed are independent and stack multiplicatively. Take any one away and the throughput drops by an order of magnitude; take all three and you have a normal multi-threaded disk-backed database that struggles to break 10k ops/sec. Understanding each pillar in isolation is what lets you reason about when Redis *stops* being fast — because each pillar has a distinct failure mode that breaks the model.

**Pillar 1: In-memory data access.** A Redis `GET` is, at its essence, a hash-table lookup in the process's own virtual memory. The hash table is a `dict` struct (see `src/dict.c` in the Redis source) with an array of `dictEntry` pointers; each `dictEntry` holds a `key` (an SDS — *simple dynamic string*, Redis's binary-safe string type), a `value` (a `redisObject` with a type tag and a pointer to the actual data), and a `next` pointer for collision chaining. The lookup is `hash(key) & mask` to find the bucket, then a linear scan of the chain comparing keys with `sdscmp()`. On a 100M-key hash table with a 1.5× load factor, the average chain length is 1.5 entries, so the average lookup is one hash, one mask, one cache-line read of the bucket, one pointer-chase to the entry, one `sdscmp` of the key (which is 8–32 bytes for typical keys) and one pointer-chase to the value. The total is ~5 cache-line accesses, ~200–400 ns on a modern x86 with L3 cache hits. The same lookup against a B-tree on disk is 3–5 disk reads at 100 µs each (NVMe) — three to four orders of magnitude slower. The comparison is not even close.

```c
// Redis dict lookup — the heart of GET (simplified from src/dict.c)
dictEntry *dictFind(dict *d, const void *key) {
    unsigned long h, idx, table;
    dictEntry *he;

    if (dictSize(d) == 0) return NULL;
    for (table = 0; table <= 1; table++) {           // rehash-aware: check both tables during rehash
        idx = d->hashFunction(key) & d->ht[table].sizemask;
        he = d->ht[table].table[idx];
        while (he) {
            if (key == he->key || dictCompareKeys(d, key, he->key))
                return he;
            he = he->next;                            // collision chain walk
        }
        if (!dictIsRehashing(d)) return NULL;          // not rehashing → done after table 0
    }
    return NULL;
}
// Average case: 1 hash + 1 mask + 1 cache-line read + 1 sdscmp + 1 pointer-chase
// → ~200-400 ns total. Compare to ~300 µs for a B-tree lookup on NVMe.
```

**Pillar 2: Single-threaded execution.** Because there is exactly one thread executing commands, there is no need for any lock, mutex, or atomic operation on the data structures. A `SET key value` is: hash-table lookup for `key` → if found, free the old value, set the new value, return `+OK\r\n` to the client. There is no `pthread_mutex_lock`, no `__sync_fetch_and_add`, no memory barrier — every one of which costs 10–100 ns on modern x86 (the L1 cache-line lock cost for a contended mutex is ~25 ns; an uncontended atomic is ~5 ns; a `futex` syscall on contention is ~1 µs). A multi-threaded Redis would pay these costs on every data-structure access; the single-threaded Redis pays zero. The tradeoff is that the single thread must do *everything* — accept new connections, parse commands, execute them, write responses, persist to disk, run the eviction policy, send replication traffic — and any one of these that blocks the main thread blocks the entire server. This is why Redis refuses to ship commands that block: `KEYS *` was deprecated for `SCAN` because `KEYS` walks the entire keyspace synchronously; `FLUSHALL ASYNC` was added so a destructive flush does not block; the `DEBUG SLEEP` command exists only for testing and would never be sent by a real client.

**Pillar 3: Non-blocking I/O multiplexing via `epoll`.** A single thread can serve thousands of concurrent client connections because it never *blocks* on any one of them. The Linux `epoll` API (the BSD/macOS equivalent is `kqueue`) lets the kernel register interest in "this FD is readable" or "this FD is writable" events, then a single `epoll_wait(epfd, events, maxevents, timeout)` call returns the set of FDs that are currently ready. The kernel's `epoll_wait` implementation walks the ready list (a doubly-linked list of FDs that have data waiting, populated by interrupt handlers) and copies the events into a user-space buffer. The Redis main loop calls `epoll_wait` once per iteration, dispatches each ready FD to the appropriate handler (read handler for client command input, write handler for queued responses), executes any commands that became ready, and loops back:

```text
  Redis main event loop (src/server.c, aeMain):

  ┌────────────────────────────────────────────────────────────────┐
  │  while (!eventLoop->stop) {                                    │
  │    aeProcessEvents(eventLoop, AE_ALL_EVENTS);                  │
  │      │                                                         │
  │      ├─ beforeSleep():                                         │
  │      │   ├─ flush AOF write buffer to disk (if appendonly yes) │
  │      │   ├─ send replication ack to replicas                   │
  │      │   └─ handle blocked clients with ready results          │
  │      │                                                         │
  │      ├─ aeApiPoll():                                           │
  │      │   └─ epoll_wait(epfd, events, 1024, tvp)                │
  │      │      → returns N ready FDs                              │
  │      │                                                         │
  │      ├─ for each ready FD:                                     │
  │      │   ├─ if readable: readQueryFromClient()                 │
  │      │   │   └─ parse INLINE or MULTIBULK protocol             │
  │      │   │   └─ processCommand() → lookupCommand()             │
  │      │   │   └─ command->proc(c)  ← THE SINGLE-THREADED EXEC   │
  │      │   │   └─ addReply() → queue response to client buf      │
  │      │   └─ if writable: sendReplyToClient()                   │
  │      │                                                         │
  │      ├─ afterSleep():                                          │
  │      │   └─ (io-threads do read parsing here if enabled)       │
  │      └─ run timed events (active expiry, etc.)                 │
  │  }                                                             │
  └────────────────────────────────────────────────────────────────┘
```

The single-threaded + `epoll` combination is what makes Redis a *soft real-time* system. Every iteration of the main loop is bounded: `epoll_wait` returns in at most `tvp` milliseconds (the time until the next timed event), the dispatch loop processes every ready FD in turn, and each command handler is O(1) or O(log N) for the vast majority of commands (the exceptions are documented as "dangerous" — `KEYS`, `SMEMBERS` on large sets, `SORT` without `LIMIT`, `HGETALL` on huge hashes). The p99 latency is therefore approximately `epoll_wait wakeup latency` + `longest command in the batch` + `response write time`. On a 1 Gbps network with a 1 kB value, this works out to ~50 µs (epoll wakeup) + ~200 ns (hash lookup) + ~10 µs (TCP write) = ~60 µs p99. Compare to a multi-threaded database where the p99 includes mutex contention spikes that can push it to milliseconds.

```bash
# Measure Redis latency under load — the gold standard is redis-benchmark
redis-benchmark -h 127.0.0.1 -p 6379 -t set,get -n 1000000 -c 50 -d 100 -q
# SET: 125000.00 requests per second, p50=0.1ms, p99=0.3ms
# GET: 142857.14 requests per second, p50=0.08ms, p99=0.25ms

# Measure intrinsic event-loop latency (without network roundtrip)
redis-cli --intrinsic-latency 10
# Max latency so far: 18 microseconds.   ← the loop's own scheduling jitter

# Measure end-to-end latency from a client
redis-cli --latency -h 127.0.0.1 -p 6379
# min: 0, max: 1, avg: 0.10 (1000 samples)   ← sub-ms on a healthy box
```

The production failure mode is the **slow command** pattern. Redis's single-threaded model means *any* command that takes 10 ms blocks every other client for those 10 ms — there is no other thread to pick up the slack. The classic offender is `KEYS *` on a 100M-key Redis (which scans the entire keyspace synchronously, taking 30+ seconds and effectively pausing the server). The fix is to use `SCAN` (which yields back to the event loop between batches), `HSCAN`/`SSCAN`/`ZSCAN` for the equivalent of `HGETALL`/`SMEMBERS`/`ZRANGE` on large collections, and to monitor the `slowlog` (the Redis built-in slow-query log, configured via `slowlog-log-slower-than` default 10 ms — set it to 1 ms in production to catch latency outliers). The metric that reveals a slow-command problem is `latency doctored` (the `LATENCY` framework added in Redis 2.8.13) and the `redis_commands_total` counter combined with p99 latency — if p99 is high but throughput is low, a slow command is the prime suspect.

### Redis threading model evolution: Background I/O threads for socket reading/writing while maintaining a single core execution engine.

Redis 6.0 (May 2020) introduced the `io-threads` feature, which is the most misunderstood change in Redis's history. The release notes say "Redis 6.0 ships with multi-threading for I/O" and a casual reader concludes "Redis is finally multi-threaded for commands" — which is *wrong*. The `io-threads` feature parallelises only the *socket I/O and protocol parsing*, not the command execution. The single main thread still executes every command sequentially, with no locks on the data structures, exactly as before. The change is purely about the read-from-socket and write-to-socket cost, which on a 1 Gbps network with many clients becomes the bottleneck before the command execution does.

The motivation: on a 10 Gbps network with 1000 concurrent connections each doing `SET key value` with a 100-byte payload, the main thread spends most of its time in `read()` syscalls (one per ready FD per loop iteration) and `write()` syscalls, not in the `dictAdd` that actually executes the `SET`. The kernel spends time copying bytes from the kernel network buffer to user space (via `recv()`) and back (via `send()`), and on a single core this saturates around ~200k ops/sec for small values. With `io-threads 4`, three additional threads handle the `recv()` and protocol parsing in parallel — they each pull a batch of ready FDs from a shared work queue, call `recv()`, parse the Redis protocol into a `client` struct's argv array, and queue the parsed client for the main thread to execute. The main thread executes commands one at a time (no locks needed), then queues the response buffers, which the I/O threads pick up and `send()` to the clients in parallel.

```text
  Redis 6 io-threads model — I/O is parallel, execution is serial:

  ┌──────────────────┐    ┌──────────────────┐    ┌──────────────────┐
  │  I/O Thread 1    │    │  I/O Thread 2    │    │  I/O Thread 3    │
  │  recv() + parse  │    │  recv() + parse  │    │  recv() + parse  │
  │  ↓ clients list  │    │  ↓ clients list  │    │  ↓ clients list  │
  └────────┬─────────┘    └────────┬─────────┘    └────────┬─────────┘
           │                       │                       │
           └───────────────────────┼───────────────────────┘
                                   ▼
                       ┌────────────────────────┐
                       │   Main Thread (core)   │
                       │   executeCommand()     │   ← single-threaded,
                       │   dictAdd / dictFind   │     no locks, no atomics
                       │   reply buffers queued │
                       └────────────┬───────────┘
                                    │
                       ┌────────────┼────────────┐
                       ▼            ▼            ▼
                  I/O Thread 1  I/O Thread 2  I/O Thread 3
                  send()        send()        send()
```

The configuration is in `redis.conf`:

```bash
# Enable io-threads (default off)
io-threads 4

# Whether I/O threads also do the read (default off — they only do write)
# Reading in parallel is more controversial because the parse phase touches
# the client struct. Enable only on big boxes with > 4 cores.
io-threads-do-reads yes

# Redis 7+ adds a separate thread for lazy-free of large objects:
# when DEL deletes a 1 GB hash, the actual free work happens on a worker
# thread, not on the main thread.
lazyfree-lazy-eviction yes
lazyfree-lazy-expire yes
lazyfree-lazy-server-del yes
lazyfree-lazy-user-del yes
```

The benchmark results on a 10 Gbps network with 1000 connections doing `SET` of a 100-byte value are illustrative: with `io-threads 1` (off), Redis plateaus around 200k ops/sec; with `io-threads 4`, it climbs to ~600k ops/sec; with `io-threads 8`, ~700k ops/sec (diminishing returns because the main thread becomes the new bottleneck). The p99 latency is unchanged (~0.3 ms) because the command execution is still single-threaded — the I/O threads do not affect latency, only throughput. For a workload with larger values (1 kB+), the I/O threads help less because the main thread's `dictAdd` becomes the bottleneck, not the I/O. The recommendation in the Redis docs is: enable `io-threads` only when you have measured that your workload is I/O-bound (network-bound, not CPU-bound), and start with 4 threads.

Redis 7.0 (June 2022) added the **`SHUTDOWN`**-safe `lazyfree` extension and the **multi-part AOF** mechanism, but the threading model is unchanged — the main thread is still the single executor. Redis 7.4 (July 2024) added *truly* multi-threaded execution for a small set of commands (`ACLCMD`, `WAIT`, `DEBUG`) via the `enable-protected-configs` mechanism, but the data-access commands (`GET`, `SET`, `HGET`, etc.) are still single-threaded. The Redis maintainers' stated position is that the single-threaded model is correct for the *cache* workload and that workloads requiring multi-threaded execution should use Redis Cluster (which shards across multiple single-threaded Redis processes) rather than multi-threading within a single process.

The production failure mode of the io-threads feature is the **CPU affinity misconfiguration**. If the four io-threads and the main thread are not pinned to specific cores (via `taskset` or `numactl`), the Linux scheduler may migrate them between cores under load, which thrashes the L1/L2 cache and can drop throughput below the single-threaded baseline. The fix is to pin each thread to a specific core using `taskset -c 0 ./redis-server` for the main thread and rely on the kernel's natural per-core scheduling for the io-threads (Redis uses `pthread_setaffinity_np` internally if `__GLIBC__` is available). The metric that reveals this is `perf stat -e cache-misses` on the `redis-server` process — if `cache-misses` per instruction retired exceeds ~5%, you have a cache thrash problem and should pin the threads. See [[06.10.03. Durability and Persistence Mechanics in Redis]] for how the AOF and RDB persistence (which fork a child process that shares copy-on-write memory with the parent) interact with the single-threaded model — the child does disk I/O while the parent continues serving traffic, but any *write* by the parent during the fork triggers a copy-on-write page duplication that consumes additional memory, which is why RDB saves on a write-heavy Redis can cause OOM.

## How This Connects to the Runtimes

Every runtime covered in section 04 is a user-space wrapper around the kernel primitives that Redis uses directly. The single-threaded event loop in Redis is the *same pattern* as the event loop in Node.js (libuv), the event loop in Python's `asyncio`, and the worker loop in Nginx — they all multiplex FDs via `epoll_wait` and dispatch to handler functions. The differences are in what the handlers do:

- **Node.js / libuv**: Event loop is a Reactor pattern built on `epoll_wait()` (Linux), `kqueue` (BSD/macOS), or `IOCP` (Windows). The worker thread pool (`uv_default_loop()->wq` default 4 threads) handles operations that cannot be multiplexed — file I/O (because `read()` on a regular file does not raise `EPOLLIN` on Linux, since file I/O is always "ready"), DNS resolution (because `getaddrinfo` is blocking), and CPU-bound crypto (`crypto.pbkdf2`). Redis has no equivalent — it does file I/O via a `fork()`ed child process (for RDB) or a sequential write buffer (for AOF), never via a worker thread.

- **JVM**: Threads are 1:1 OS threads (via NPTL on Linux, `pthread_create`). The JVM's memory model is layered on top of the kernel's virtual memory system, and Java's `synchronized` and `java.util.concurrent` use kernel futexes under contention. Redis's choice to avoid threads entirely is the *opposite* of the JVM's choice to expose them as a first-class primitive — both choices are correct for their respective workloads (Redis for in-memory cache, JVM for CPU-bound mixed workload).

- **CPython**: The GIL (Global Interpreter Lock) is a mutex that serialises Python bytecode execution across OS threads — analogous to Redis's single-threaded model, but accidental (a side effect of CPython's reference-counting memory management) rather than deliberate. The difference is that Redis's single-threaded model applies only to command execution (I/O is parallel in 6.0+); CPython's GIL applies to all bytecode execution including I/O syscall setup, which is why multi-threaded Python for I/O-bound work is no faster than single-threaded Python with `asyncio`.

- **PHP-FPM**: Each worker is a separate OS process (section 04.04). The shared-nothing model is a direct consequence of the process isolation — there is no in-process state to share. Redis's choice of a single process with shared state is the *opposite* of PHP-FPM's model; the two coexist well because PHP-FPM is stateless and Redis holds the shared state, which is the canonical LAMP-stack-plus-cache architecture.

When you read the runtime notes in section 04, come back here and trace which kernel primitive each runtime feature maps to — `epoll_wait` is the universal substrate, and every event-loop runtime is a thin wrapper around it.

## Hands-On Exercise

```bash
# 1. Confirm Redis is single-threaded for command execution
redis-cli INFO threads
# io_threads_active:0     ← default off
redis-cli CONFIG GET io-threads
# io-threads:1            ← single-threaded I/O

# 2. Measure throughput with and without io-threads
redis-cli CONFIG SET io-threads 1
redis-benchmark -t set,get -n 1000000 -c 100 -d 100 -q
redis-cli CONFIG SET io-threads 4
redis-benchmark -t set,get -n 1000000 -c 100 -d 100 -q
# On a 10 Gbps NIC with 8+ cores, the second run should be 2-3x faster.

# 3. Measure intrinsic event-loop latency — kernel scheduling jitter
redis-cli --intrinsic-latency 10
# Look for "Max latency" — if > 1 ms, you have CPU contention or NUMA issues.

# 4. Inspect the slowlog to find slow commands blocking the main thread
redis-cli SLOWLOG GET 10
redis-cli CONFIG SET slowlog-log-slower-than 1000   # log everything > 1 ms
redis-cli CONFIG SET slowlog-max-len 128             # keep last 128 entries

# 5. Reproduce the slow-command failure mode
# Terminal 1: hammer Redis with GET
redis-benchmark -t get -n 1000000 -c 50 -q &
# Terminal 2: run a slow command
redis-cli DEBUG SLEEP 1
# Terminal 3: watch the latency spike
redis-cli --latency
# → you will see p99 jump from <1ms to >1000ms while DEBUG SLEEP runs

# 6. Verify the main thread's CPU affinity on Linux
REDIS_PID=$(pgrep redis-server)
cat /proc/$REDIS_PID/status | grep Cpus_allowed_list
# → 0-7 (or whatever the box allows)
# Pin it to a single core:
taskset -pc 0 $REDIS_PID

# 7. Measure the kernel's view of Redis syscalls
perf stat -e syscalls:sys_enter_epoll_wait,syscalls:sys_enter_recvfrom,syscalls:sys_enter_sendto \
  -p $REDIS_PID -- sleep 5
# → epoll_wait count = number of event loop iterations in 5 s
# → recvfrom/sendto counts = number of socket I/O syscalls

# 8. Confirm that io-threads only do I/O, not command execution (Redis 6+)
strace -f -e trace=futex -p $REDIS_PID 2>&1 | head -20
# You will see futex calls from the io-threads coordinating with the main thread,
# but NOT from command execution — that is the proof that data structures are lock-free.
```
