# 06.07.02. The Active Record Pattern

## What This Is

The Active Record pattern is an Object-Relational Mapping strategy in which a domain object wraps a single row in a database table, exposes that row's columns as instance attributes, and encapsulates the persistence operations (`save`, `update`, `delete`, `reload`, `find`) as instance or class methods on the entity itself. The `User` class is at once the domain object (with `email`, `name`, `last_login` attributes and domain methods like `activate()`) and the data-access object (with `User.find(42)` and `user.save()`). The pattern was named by Martin Fowler in *Patterns of Enterprise Application Architecture* (2002) and was popularised by Ruby on Rails (2004), which made it the default ORM idiom for an entire generation of web frameworks. Laravel Eloquent, Django ORM, Rails ActiveRecord, and Bookshelf.js are all Active Record implementations.

This note covers the architectural definition (the entity IS the table row), the trade-offs (rapid development velocity vs. tight coupling of domain logic to persistence schema), and the two canonical target implementations (Laravel Eloquent and Django ORM). The sister note [[06.07.03. The Data Mapper Pattern]] covers the alternative — JPA/Hibernate, SQLAlchemy ORM, Prisma — where the domain object is a plain object with no persistence methods and a separate `Repository` handles database access. The choice between Active Record and Data Mapper is the single biggest architectural decision in an ORM selection, and it has downstream effects on testability, refactor velocity, and team structure that persist for the life of the codebase.

## The Details

### Architectural definition: An object represents a single database row and encapsulates b...

In the Active Record pattern, every instance of an entity class corresponds to exactly one row in a database table. The class itself is the schema declaration: each attribute on the class maps to a column, and the framework introspects the class (via reflection, decorators, or metaclass magic) to generate the SQL for CRUD operations. The instance carries both the data (the column values) and the behaviour (the persistence methods), with no separation between the domain layer and the data-access layer.

The four canonical persistence methods are `find` (class method, returns a single instance or collection), `save` (instance method, INSERTs if the primary key is null, UPDATEs if it is set), `delete` (instance method, DELETEs the row), and `reload` (instance method, re-fetches from DB to overwrite in-memory changes). Associations are exposed as method calls that lazily fire a query: `user.posts` returns a collection of `Post` instances, fetched from the database the first time the method is called and cached on the instance thereafter. There is typically no separate "repository" object — the entity class plays all the roles.

```php
// Laravel Eloquent — canonical Active Record

// app/Models/User.php — the model class IS the schema and the data-access object
namespace App\Models;

use Illuminate\Database\Eloquent\Model;
use Illuminate\Database\Eloquent\Relations\HasMany;

class User extends Model {
    protected $table = 'users';              // table name (inferred from class name by default)
    protected $fillable = ['email', 'name']; // mass-assignment whitelist (security)
    protected $hidden = ['password'];        // omit from JSON serialization
    protected $casts = ['email_verified_at' => 'datetime', 'is_admin' => 'boolean'];

    // Associations — declared as methods, lazily evaluated
    public function posts(): HasMany {
        return $this->hasMany(Post::class);
    }
}

// Usage — class methods for find/create, instance methods for save/delete
$u = User::find(42);                         // SELECT * FROM users WHERE id = 42
$u = User::where('email', 'a@x.com')->first(); // SELECT * FROM users WHERE email = ? LIMIT 1
$u = User::create(['email' => 'b@x.com', 'name' => 'Bob']);  // INSERT
$u->name = 'Robert';
$u->save();                                  // UPDATE users SET name = ? WHERE id = ?
$u->delete();                                // DELETE FROM users WHERE id = ?

foreach (User::all() as $user) {             // SELECT * FROM users
    echo $user->posts->count();              // SELECT * FROM posts WHERE user_id = ? (N+1!)
}

// Fix the N+1 with eager loading:
$users = User::with('posts')->get();         // SELECT * FROM users; SELECT * FROM posts WHERE user_id IN (...)
foreach ($users as $user) {
    echo $user->posts->count();              // 0 extra queries
}
```

The key invariant is that `$u` *is* the row. Calling `$u->save()` does not pass `$u` to a separate `UserRepository` — the entity itself knows its table name, its primary key, its dirty fields, and its connection, and it constructs and executes the UPDATE statement directly. This is what makes Active Record feel "magic": you write `class User extends Model { protected $fillable = ['email']; }` and you instantly have a working CRUD layer for the `users` table. The cost of that magic is the tight coupling — see the trade-offs section below.

```python
# Django ORM — same pattern, slightly different surface

# myapp/models.py
from django.db import models

class User(models.Model):
    email = models.EmailField(unique=True)
    name = models.CharField(max_length=200)
    is_active = models.BooleanField(default=True)
    created_at = models.DateTimeField(auto_now_add=True)

    class Meta:
        db_table = 'users'                   # custom table name
        indexes = [models.Index(fields=['email'])]

    def __str__(self):
        return self.email

    # Domain logic can live on the model
    def activate(self):
        self.is_active = True
        self.save(update_fields=['is_active'])   # UPDATE only the named column

# Usage — the Manager (objects) is the class-level API; instance methods do persistence
u = User.objects.get(pk=42)                  # SELECT * FROM users WHERE id = 42
u = User.objects.filter(email='a@x.com').first()
u = User.objects.create(email='b@x.com', name='Bob')   # INSERT
u.name = 'Robert'
u.save()                                     # UPDATE users SET name=?, is_active=?, ... WHERE id=?
u.save(update_fields=['name'])               # UPDATE users SET name=? WHERE id=? (skips other columns)
u.delete()                                   # DELETE FROM users WHERE id = ?

for u in User.objects.all():                 # SELECT * FROM users
    print(u.post_set.count())                # SELECT COUNT(*) FROM posts WHERE user_id = ? (N+1!)

# Fix the N+1:
users = User.objects.prefetch_related('post_set')  # see 06.07.05 for the full N+1 treatment
```

The Django variant differs in surface details — `User.objects` (a `Manager`) plays the role that Laravel's static `User::` methods play; the migration framework (`makemigrations` / `migrate`) auto-generates SQL from the model definitions rather than letting you write the schema by hand; the `save(update_fields=[...])` optimisation lets you skip writing unchanged columns — but the architectural shape is identical: the entity is the row, persistence methods live on the entity, there is no separate repository.

### Trade-offs: Rapid development velocity vs. tight coupling of domain logic to persistenc...

The Active Record pattern's central trade-off is speed-to-first-working-endpoint against long-term architectural flexibility. The same `class User extends Model` declaration that gives you a working CRUD layer in 5 lines also fuses your domain model to your database schema, and that fusion has compounding costs as the application grows.

The wins are real and immediate. **Velocity**: a developer can scaffold a complete CRUD resource (model, controller, migration, views) in minutes — Laravel's `php artisan make:model -mcr User` generates all four files. **Convention over configuration**: the framework infers the table name from the class name (`User` → `users`), the primary key from convention (`id`), and the foreign key from the association (`User hasMany Post` → `posts.user_id`). **Less code to read**: there is one file per entity, not two (entity + repository). **Built-in features**: validations, scopes, accessors/mutators, attribute casting, soft deletes, and eager loading all come standard. For a CRUD app where the domain logic is mostly "load row, edit field, save row," these wins compound across dozens of entities.

The costs are deferred but compound. **Testability**: because `User::find()` and `$user->save()` make direct database calls, any test that exercises a model method needs a database. You cannot unit-test a domain rule like `User::isActive()` in isolation — to construct a `User` instance, the model class's constructor may require a DB connection (Django models can be instantiated without a DB, but invoking `.save()` requires one; Laravel Eloquent models can be instantiated without a DB but `.save()` and associations require one). The standard workaround is an in-memory SQLite database for tests, which has subtly different SQL semantics from production PostgreSQL — a test passes on SQLite and fails on PostgreSQL, or worse, vice versa. **Single Responsibility violation**: the `User` class does domain logic (validate email, check password), persistence (save, delete, find), serialization (toJson, toArray), and sometimes HTTP concerns (form request validation). Each of these is a reason for the class to change, and they accumulate. **Schema coupling**: changing the database schema requires changing the model class, even if the domain logic doesn't care. Splitting the `users` table into `users` + `user_profiles` (because the table got too wide) requires rewriting every `User` model method that touched the moved columns. **No domain model evolution**: in a complex domain (insurance claims, order fulfilment, billing), the in-memory representation of an "order" may not correspond to any single table — it might be assembled from `orders`, `order_items`, `shipments`, `invoices`, and `payments`. Active Record forces you to either (a) pick one table as the "primary" and lazily load the rest (which N+1s everything), or (b) create a "view model" that is not an Active Record at all — at which point you have re-invented Data Mapper.

```text
The Active Record testability problem:

  ┌──────────────────────────────────────────────────────┐
  │ class User extends Model {                           │
  │   fn isEligibleForDiscount(): bool {                 │
  │     return this.orders()                             │
  │       .where('total', '>', 1000)                     │  ← DB query inside
  │       .count() > 5;                                  │  ← domain rule
  │   }                                                  │
  │ }                                                    │
  └──────────────────────────────────────────────────────┘

  To test isEligibleForDiscount(), you need:
   1. A database (real or in-memory SQLite)
   2. Schema migrations run
   3. A User row inserted
   4. 6 Order rows inserted (5 above threshold, 1 below)
   5. Call the method, assert true

  Compare to Data Mapper, where the domain object is plain:

  ┌──────────────────────────────────────────────────────┐
  │ class User {                  // plain POJO          │
  │   private List<Order> orders;                         │
  │   fn isEligibleForDiscount(): bool {                  │
  │     return orders.count { it.total > 1000 } > 5;      │  ← pure logic
  │   }                                                   │
  │ }                                                     │
  └───────────────────────────────────────────────────────┘

  To test: new User(orders=[Order(1001), Order(1002), ...]).isEligibleForDiscount()
  No DB. No migrations. No fixtures. Just constructor + assert.
```

The production failure mode of Active Record is the "fat model" anti-pattern. As the application grows, business logic that has no natural home accumulates on the model classes — `User::calculateLoyaltyTier()`, `User::sendWelcomeEmail()`, `User::generateInvoicePdf()`. The `User` class grows to 2000 lines, depends on 30 other classes, takes 5 seconds to load in the test suite (because every test boots the framework), and any change to it risks breaking unrelated features. The fix is the "service layer" pattern: keep the model thin (only persistence + simple domain rules), put complex logic in `UserService`, `BillingService`, etc. But this is a discipline the framework does not enforce — and the temptation to put the next method "where the data is" is constant. Teams that start with Active Record and grow into a complex domain often refactor to Data Mapper (or to a hybrid: Active Record for CRUD entities, service layer for complex logic) after 2–3 years. Teams that start with Data Mapper rarely switch back.

### Target Implementations: Laravel Eloquent and Django ORM

Laravel Eloquent and Django ORM are the two most widely-deployed Active Record implementations in production today. They share the architectural shape (entity = row, persistence methods on entity, associations as lazy-loaded method calls) but differ in surface API, schema management, and a few sharp corners.

```text
Side-by-side: the same CRUD operations in Laravel Eloquent and Django ORM

  Operation              Laravel Eloquent                    Django ORM
  ─────────────────────  ──────────────────────────────      ──────────────────────────────────
  Define model           class User extends Model {          class User(models.Model):
                           protected $fillable = ['email'];    email = models.EmailField()
                         }                                    class Meta: db_table = 'users'

  Find by PK             User::find(42)                      User.objects.get(pk=42)
                         (returns User or null)              (returns User or raises DoesNotExist)

  Find by field          User::where('email', $e)->first()   User.objects.filter(email=e).first()
                         (null if not found)                 (None if not found)

  Find all               User::all()                         User.objects.all()
                         (returns Collection)                (returns QuerySet — lazy!)

  Create                 User::create(['email' => $e])       User.objects.create(email=e)
                         (INSERT, returns User)              (INSERT, returns User)

  Update                 $u->email = $e; $u->save();         u.email = e; u.save()
                                                             (UPDATE all columns)

  Partial update         $u->save(['email']);                u.save(update_fields=['email'])
                         (UPDATE only 'email' column)        (UPDATE only 'email' column)

  Delete                 $u->delete()                        u.delete()
                         (DELETE row, return int)            (DELETE row, return count)

  Count                  User::count()                       User.objects.count()
                         (SELECT COUNT(*))                   (SELECT COUNT(*))

  Where clause           User::where('active', true)         User.objects.filter(active=True)
                              ->where('age', '>', 18)                .filter(age__gt=18)
                              ->get()                           (QuerySet — lazy, evaluated on iteration)

  Order / limit          User::orderBy('created_at', 'desc') User.objects.order_by('-created_at')
                              ->limit(10)                          [:10]
                              ->get()

  Has-many association   $this->hasMany(Post::class);        posts = models.ForeignKey(Post,
                                                                on_delete=models.CASCADE)
                         $user->posts                        (reverse: u.post_set or u.posts)

  Eager load             User::with('posts')->get()          User.objects.prefetch_related('posts')
                         (single IN query)                   (single IN query)

  Join for filter        User::whereHas('posts',             User.objects.filter(
                                   fn($q) => $q                   posts__title__icontains='hello')
                                   ->where('title','like','%h%'))
                         (EXISTS subquery)                   (real JOIN — different SQL shape!)

  Transactions           DB::transaction(fn() => {           with transaction.atomic():
                              $u->save();                        u.save()
                              $p->save();                        p.save()
                          });                                 }

  Raw SQL escape hatch   DB::select('SELECT ...', [$id])    User.objects.raw('SELECT ...', [id])
```

The differences worth knowing: **Laravel's `Collection` vs. Django's `QuerySet`**. Laravel's `->get()` returns a `Collection` — an eager-evaluated list of model instances, with rich functional methods (`map`, `filter`, `reduce`, `pluck`). Django's `objects.all()` returns a `QuerySet` — a lazy iterator that does not execute SQL until you iterate, slice, or call `list()`. This means `User.objects.all()` in Django is essentially free (it builds a query but doesn't run it); `User::all()` in Laravel runs `SELECT * FROM users` immediately and loads every row into memory. **Migration strategy**: Laravel migrations are hand-written PHP files (`php artisan make:migration`); Django migrations are auto-generated by inspecting model changes (`python manage.py makemigrations`). The Django approach is faster for schema evolution but produces migrations that are sometimes opaque; the Laravel approach is more verbose but more transparent. **Mass assignment protection**: Laravel requires you to declare `$fillable` (or `$guarded`) on every model — a security feature born from a 2014 GitHub mass-assignment vulnerability. Django has no equivalent; the `objects.create()` call accepts any keyword argument, which means a malicious POST body can set fields the developer didn't intend to expose. **Where-clause semantics**: Laravel's `whereHas` produces an `EXISTS` subquery (`WHERE EXISTS (SELECT * FROM posts WHERE posts.user_id = users.id AND ...)`); Django's `posts__title__icontains='hello'` produces a real JOIN (`INNER JOIN posts ON posts.user_id = users.id WHERE posts.title ILIKE '%hello%'`). The JOIN is faster for small result sets, but can produce duplicate parent rows that the ORM must de-duplicate — the EXISTS subquery is slower but never duplicates. **Transaction ergonomics**: Laravel's `DB::transaction(fn() => {...})` automatically commits on return and rolls back on exception; Django's `with transaction.atomic():` does the same. Both close the transaction at the boundary, which is the correct behaviour — but neither prevents the developer from accidentally opening a second nested transaction with different semantics.

Both frameworks have the same blind spots inherited from Active Record itself: no identity map (calling `User::find(42)` twice returns two distinct objects, so in-process mutations to one don't reflect in the other), no Unit of Work (every `save()` is an immediate `UPDATE` — there's no batched commit at end of request), and no separation between domain and persistence layers (the model class plays both roles). These are the gaps that Data Mapper fills — see [[06.07.03. The Data Mapper Pattern]] for the JPA/Hibernate and SQLAlchemy ORM implementations that fill them.

## Cross-Ecosystem Implementation

The same concept maps differently across the four target ORMs:

| Concept | JPA / Hibernate | Django ORM | Eloquent | Prisma |
|---|---|---|---|---|
| Pattern | Data Mapper | Active Record | Active Record | Data Mapper |
| Lazy loading | Proxy objects (Hibernate intercepts field access) | `select_related` needed (no implicit lazy) | `load()` needed (lazy by default for relations) | `include` needed (no implicit lazy) |
| N+1 fix | `@EntityGraph` or `JOIN FETCH` | `select_related` (join) or `prefetch_related` (separate query) | `with()` (eager load) | `include` |
| Migration | Flyway / Liquibase (versioned SQL files) | `makemigrations` (auto-detects model changes) | `migrate` (similar to Django) | `prisma migrate` (schema-first) |
| Connection pool | HikariCP | Django's CONN_MAX_AGE | Laravel pool | Prisma pool |

When you read the anchor implementation note, identify which ORM feature corresponds to each concept above. The delta notes then show how the same feature is expressed in the other ecosystems.

## Hands-On Exercise

```sql
-- See the query plan that an ORM generates (the cost of abstraction)
EXPLAIN ANALYZE SELECT * FROM users WHERE email = 'alice@example.com';

-- Compare to the same query with eager loading of posts:
EXPLAIN ANALYZE
  SELECT u.*, p.*
  FROM users u
  LEFT JOIN posts p ON p.user_id = u.id
  WHERE u.email = 'alice@example.com';

-- Check active transactions and locks
SELECT pid, state, wait_event, query FROM pg_stat_activity;

-- Check table size and dead tuples
SELECT relname, n_live_tup, n_dead_tup FROM pg_stat_user_tables;

-- Force a deadlock to see how the engine handles it
-- (run in two separate transactions)
BEGIN;
UPDATE accounts SET balance = balance - 10 WHERE id = 1;
UPDATE accounts SET balance = balance + 10 WHERE id = 2;
-- in another session, do the reverse...
```
