# 06.07.05. The N+1 Query Problem and Loading Strategies

## What This Is

The N+1 query problem is the most common ORM performance bug and the single biggest reason production systems get paged at 3 a.m. after a "trivial" code change. The shape is universal: you fetch N parent records in one query, then for each parent you lazily fetch one child relationship — issuing N additional queries, for a total of N+1 round-trips to the database. For N=1,000 users this is 1,001 queries instead of 1 or 2; each query costs ~1ms of network round-trip plus parse/plan/optimize overhead, so the page that should take 5ms takes 5 seconds. The defect is invisible in development (small data, fast local DB, no monitoring) and only surfaces under realistic load against a remote database with non-trivial latency.

In the layered mental model, N+1 is a *persistence abstraction layer* failure — the ORM is doing exactly what the code told it to do, but the developer did not see the query count because the abstraction hid it. Every major ORM has the same defect because every major ORM defaults to *lazy loading* for relationships (Hibernate `@ManyToOne(fetch = LAZY)`, Django `ForeignKey`, Eloquent `belongsTo`, Prisma relations). Lazy loading is the right default for the single-entity case — `user.getProfile()` should not always fetch the profile if half the callers don't need it. The bug is *lazy loading inside an iteration loop*, where the per-entity fetch dominates. The fixes are taught in this note: `JOIN FETCH` / `select_related` (one query, JOIN), `@BatchSize` / `prefetch_related` (two queries, batched `IN`), and `@EntityGraph` for dynamic per-query control.

The failure mode is not just slowness. N+1 also produces *connection pool exhaustion*: if each query takes a connection from HikariCP (maxPoolSize=10) and the loop holds a connection for 5 seconds, the 11th concurrent request blocks waiting for a connection, the 12th times out at the `connectionTimeout`, and the user sees a 500. It also produces *replication lag* on read replicas: 1,001 small `SELECT`s binlog more verbosely than one JOIN, the replica falls behind, and the next request that reads from the replica gets stale data. The diagnostic is always the same: count queries per request, set a hard ceiling (e.g. 50), alert when it is exceeded.

## The Details

### Root Cause: Lazy loading relationships inside an iteration loop, generating 1 parent qu...

The root cause is the combination of three things, each individually defensible: (1) lazy loading as the default fetch strategy for relationships — the ORM does not fetch `user.profile` until `user.getProfile()` is called; (2) a *proxy object* that pretends to be the loaded relationship but is actually a placeholder that triggers a database query on first access; (3) an iteration loop that calls the getter once per parent. The proxy is the seductive part — it makes the code look like normal object navigation, and the database round-trip is completely invisible at the call site.

The canonical example, in Django ORM:

```python
# views.py — list users with their profile bio
def user_list(request):
    users = User.objects.all()[:1000]              # 1 query: SELECT * FROM users LIMIT 1000
    payload = []
    for u in users:
        payload.append({
            "email": u.email,
            "bio": u.profile.bio,                  # ← N queries: one SELECT * FROM profiles WHERE user_id=?
        })
    return JsonResponse(payload, safe=False)
# Total: 1 + 1000 = 1001 queries. At 1ms each = ~1 second of pure round-trip.
```

The Django query log captured by `django.db.connection.queries` shows the pathology plainly:

```text
(0.001) SELECT id, email FROM users LIMIT 1000;              args=()
(0.001) SELECT id, user_id, bio FROM profiles WHERE user_id=1;  args=()
(0.001) SELECT id, user_id, bio FROM profiles WHERE user_id=2;  args=()
(0.001) SELECT id, user_id, bio FROM profiles WHERE user_id=3;  args=()
... 996 more SELECT statements ...
(0.001) SELECT id, user_id, bio FROM profiles WHERE user_id=1000; args=()
Total queries: 1001   Total time: 1.02s
```

The proxy mechanism is what makes this bug *invisible*. In Hibernate, `@ManyToOne(fetch = FetchType.LAZY)` returns a `Proxy` subclass of `Profile` whose `getBio()` method is intercepted — the interceptor issues `SELECT * FROM profiles WHERE id=?` on the first call, populates the proxy's fields, and returns the value. In Django the proxy is the `ForeignKey` descriptor's `__get__` method; in Eloquent it is the `BelongsTo` relation's lazy-loading guard; in Prisma it doesn't exist (Prisma relations are never auto-loaded — you must explicitly `include` them, which is why Prisma cannot have an N+1 inside a loop the same way).

The defect is *structural*: the loop does not know it is issuing queries, the getter does not know it is being called N times, and the ORM does not know the calls are correlated. Each component is correct in isolation; only their composition is wrong. The fixes in the next H3s all share the same shape — make the eager load *explicit at the query site* so the ORM can fetch all the data up-front in one or two round-trips.

### Mitigations

The mitigation space for N+1 has three axes, and choosing the wrong one for the data shape will make performance *worse*. The axes are: (1) fetch all data in one JOIN (duplicates parent rows for each child); (2) fetch all data in two queries with a batched `IN` (preserves parent cardinality, requires dedup on the client); (3) lazy-load but batched — fetch in groups of N children at a time rather than one-by-one. The right choice depends on the cardinality of the relationship and the fanout.

```text
                       ┌──────────────────────────────────────────────────┐
   Relationship        │  Recommended mitigation                         │
   cardinality         │                                                  │
   ────────────▶       │                                                  │
                       │  1:1 (user → profile)                            │
                       │    → JOIN FETCH / select_related                 │
                       │      (1 query, no row duplication)               │
                       │                                                  │
                       │  1:N small (user → 2-5 orders)                   │
                       │    → JOIN FETCH / select_related                 │
                       │      (1 query, acceptable duplication)           │
                       │                                                  │
                       │  1:N large (user → 1000s of comments)            │
                       │    → prefetch_related / selectinload / include   │
                       │      (2 queries, IN clause, client-side join)    │
                       │                                                  │
                       │  N:N via join table (user → tags)                │
                       │    → prefetch_related / selectinload             │
                       │      (2-3 queries, never JOIN — cartesian risk)  │
                       │                                                  │
                       │  lazy but bounded (1000s parents, 1 child each)  │
                       │    → @BatchSize(size=50) / batch_size            │
                       │      (1 + N/size queries, ~20 instead of 1001)   │
                       └──────────────────────────────────────────────────┘
```

A second class of mitigations is *architectural*: instead of fixing the ORM query, change the data shape. The two most common are: (1) *denormalise* — store `profile_bio` directly on `users` if it is read 100× more than written (eliminating the join entirely); (2) *cache* — put the per-user profile in Redis keyed by `user:{id}:profile`, with a TTL and a write-through invalidation hook in the repository. These trade schema purity for read latency and should only be reached for after the query-level mitigations are exhausted. A third architectural option is *read-model projection* — maintain a separate `user_list_view` table populated by a trigger or a CDC stream, so the list endpoint issues a single `SELECT * FROM user_list_view` with no joins at all. This is the CQRS pattern applied to the N+1 problem and is the standard solution for high-traffic dashboards.

The universal detection layer is *query counting middleware*. In Django, drop this into `MIDDLEWARE`:

```python
# middleware.py — fail loud in development if a view issues > N queries
from django.db import connection

class QueryCountMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        n_before = len(connection.queries)
        response = self.get_response(request)
        n_after = len(connection.queries)
        n_queries = n_after - n_before
        response["X-Query-Count"] = str(n_queries)
        if n_queries > 50:
            logger.warning(f"{request.path}: {n_queries} queries — possible N+1")
        return response

# settings.py
if DEBUG:
    MIDDLEWARE += ["myapp.middleware.QueryCountMiddleware"]
```

In Spring Boot the equivalent is the `datasource-proxy` library with a `ProxyDataSourceListener` that logs query count per HTTP request, or p6spy with `#logSlowQuery` and a `MultiLineFormat`. Without this kind of monitoring in CI, N+1 regressions ship to production undetected — code review cannot catch them because the defect is in the *combination* of code paths, not in any single line.

### Eager Loading via `JOIN` (fetching parent and children in a single round-trip)

The JOIN-based eager load is the simplest and most aggressive fix: collapse N+1 queries into 1 by `LEFT OUTER JOIN`-ing the child table in the original `SELECT`. It is the right choice when the relationship is 1:1 or 1:few (a parent with at most a handful of children), because the row duplication from the JOIN is bounded. It is the *wrong* choice for 1:many with high fanout (a user with thousands of orders) — the JOIN produces a result set of size N×M, transferring M times the data the application actually needs, and the cost can exceed the N+1 it was meant to fix.

The four idiomatic forms:

```python
# Django — select_related: uses LEFT OUTER JOIN, 1 query
users = User.objects.select_related("profile").all()[:1000]
# SELECT * FROM users LEFT OUTER JOIN profiles ON profiles.user_id = users.id LIMIT 1000;
```

```php
// Eloquent — with(): uses LEFT JOIN, 1 query
$users = User::with('profile')->limit(1000)->get();
// select * from users left join profiles on profiles.user_id = users.id limit 1000;
```

```java
// JPA/Hibernate — JOIN FETCH: 1 query
TypedQuery<User> q = em.createQuery(
    "SELECT DISTINCT u FROM User u LEFT JOIN FETCH u.profile", User.class);
List<User> users = q.getResultList();
// SELECT DISTINCT u.* FROM users u LEFT JOIN profiles p ON p.user_id = u.id;
```

```typescript
// Prisma — include: 1 query with a JOIN
const users = await prisma.user.findMany({
  take: 1000,
  include: { profile: true },
});
// SELECT * FROM "User" LEFT JOIN "Profile" ON "Profile"."userId" = "User"."id";
```

The query log before and after the fix tells the story:

```text
BEFORE (N+1):
(0.001) SELECT id, email FROM users LIMIT 1000;
(0.001) SELECT * FROM profiles WHERE user_id = 1;
(0.001) SELECT * FROM profiles WHERE user_id = 2;
... 998 more ...
Total: 1001 queries, 1.02s

AFTER (JOIN FETCH):
(0.002) SELECT u.id, u.email, p.id, p.bio FROM users u
        LEFT JOIN profiles p ON p.user_id = u.id LIMIT 1000;
Total: 1 query, 2ms
```

Three subtleties trip up developers. First, *pagination breaks* — `SELECT * FROM users JOIN profiles LIMIT 10` limits the joined rows, not the users, so a user with 5 profiles might consume the entire limit. Always paginate on the parent (`User`), never on the joined rowset. Second, `SELECT DISTINCT` is needed to dedup parent rows in JPA — without it, a user with 3 orders appears 3 times in the result list. Third, *cartesian explosion* — joining two 1:N collections (`User → Orders` and `User → Tags`) produces a result of size `|orders| × |tags|` per user, which can be 100s of rows for a single user. Never JOIN two 1:N collections at once; use the batched `IN` strategy of the next H3 for the second collection. The production failure mode is the *slow dashboard*: an admin view that JOINs `users → orders → line_items → products` takes 30 seconds because the cartesian result has 50,000 rows for 100 users, and the network transfer dominates. The fix is to switch to `prefetch_related` / `selectinload` for the deep relationships, keeping JOIN only for the first level.

### Eager Loading via Subquery / Batch `IN (...)` (fetching all child records for the N par...

The batched-IN strategy splits the load into two queries: first fetch the N parents, then fetch `WHERE parent_id IN (id1, id2, ..., idN)` for the children, and join them in application memory. This avoids the row duplication of JOIN and is the right choice for high-fanout 1:N relationships. The trade-off is two round-trips instead of one, and the application (or ORM) must build a `Map<parentId, List<Child>>` and inject it into each parent.

The four idiomatic forms:

```python
# Django — prefetch_related: 2 queries, IN clause
users = User.objects.prefetch_related("orders").all()[:1000]
# Q1: SELECT * FROM users LIMIT 1000;
# Q2: SELECT * FROM orders WHERE user_id IN (1, 2, 3, ..., 1000);
# Django then builds {user_id: [orders...]} in Python and attaches to each user.
```

```java
// Hibernate — @BatchSize: lazy but batched, ~N/size queries
@OneToMany(mappedBy = "user")
@BatchSize(size = 50)
private List<Order> orders;
// When orders is accessed for the first time on user 1, Hibernate issues:
// SELECT * FROM orders WHERE user_id IN (1, 2, ..., 50);
// -- loading the orders for the next 50 users all at once.
```

```typescript
// Prisma — include with where, 2 queries
const users = await prisma.user.findMany({
  take: 1000,
  include: { orders: true },
});
// Q1: SELECT * FROM "User" LIMIT 1000;
// Q2: SELECT * FROM "Order" WHERE "userId" IN (1, 2, ..., 1000);
```

```python
# SQLAlchemy — selectinload: 2 queries, modern 1.4+ idiom
from sqlalchemy.orm import selectinload
users = session.scalars(
    select(User).options(selectinload(User.orders)).limit(1000)
).all()
# Q1: SELECT * FROM users LIMIT 1000;
# Q2: SELECT * FROM orders WHERE user_id IN (?, ?, ..., ?)  -- driven by client-side IN
```

The query count drops from N+1 to exactly 2, regardless of N:

```text
BEFORE (N+1):
1001 queries, 1.02s

AFTER (prefetch_related / selectinload / include):
(0.001) SELECT * FROM users LIMIT 1000;
(0.005) SELECT * FROM orders WHERE user_id IN (1,2,...,1000);
Total: 2 queries, 6ms   — 170× faster
```

The `@BatchSize` Hibernate approach is different in shape — it does not eliminate lazy loading, it just batches it. The first call to `user.getOrders()` on user 1 triggers a load of orders for users 1 through 50 (size=50), so the loop over 1,000 users issues 20 `IN` queries instead of 1,000 single-row queries. This is a half-measure: it reduces query count by 50× but does not eliminate it, and it requires the access pattern to be sequential (if you access users 1, 50, 100, 150 first, you get 4 queries each loading 50 users you didn't need). The right place for `@BatchSize` is when you cannot change the query (legacy code) but can annotate the entity — it is a fallback, not a first-class strategy.

The production failure mode of the IN-clause strategy is *parameter list overflow*. PostgreSQL has a hard limit on bind parameters per query (`PG_MAX_ARGUMENTS`, default 100 in older versions, raised to 65535 in PostgreSQL 14+); MySQL's `max_allowed_packet` limits the total query string size. A prefetch over 100,000 users with `IN (1, 2, ..., 100000)` exceeds the parameter limit and throws `PreparedStatementException` / `IllegalArgumentException`. The fix is *chunked prefetch*: Django's `Prefetch('orders', queryset=Order.objects.all(), to_attr='_orders')` plus manual chunking, or SQLAlchemy's `selectinload` which automatically chunks at 500 (the internal `SQLA_SELECTIN_LIMIT` constant). Always check the ORM's chunk size — and never assume "IN with 100k parameters" is fine because it works in dev with 10 users.

### Dynamic Entity Graphs, Fetch Profiles, and Join Fetching

Real applications do not have one canonical "load shape" per entity — a user-list endpoint needs `profile`, a user-detail endpoint needs `profile + orders + orders.items`, and a user-export endpoint needs *everything*. Static fetch strategies (the `fetch = EAGER` annotation, the `@Fetch(FETCHMODE.JOIN)`) are wrong for all three use cases because they fix the load shape at the entity level. The dynamic strategies let the *query site* decide which relationships to load.

JPA 2.1's `@EntityGraph` is the canonical solution. You declare a named graph on the entity:

```java
@Entity
@NamedEntityGraphs({
    @NamedEntityGraph(
        name = "User.withProfile",
        attributeNodes = @NamedAttributeNode("profile")
    ),
    @NamedEntityGraph(
        name = "User.withOrders",
        attributeNodes = @NamedAttributeNode(value = "orders", subgraph = "orders.items"),
        subgraphs = @NamedSubgraph(
            name = "orders.items",
            attributeNodes = @NamedAttributeNode("items")
        )
    )
})
public class User { ... }
```

And then the repository picks the graph per query:

```java
public interface UserRepository extends JpaRepository<User, Long> {

    @EntityGraph(value = "User.withProfile")           // 1 query, JOIN profile
    List<User> findAllBy();                              // for the list endpoint

    @EntityGraph(value = "User.withOrders")            // 1 query, JOIN orders + items
    Optional<User> findDetailById(Long id);              // for the detail endpoint
}
```

The dynamic, ad-hoc form (no `@NamedEntityGraph` declaration) builds the graph in code:

```java
EntityGraph<User> graph = em.createEntityGraph(User.class);
graph.addAttributeNodes("profile");
graph.addAttributeNodes("orders");
Subgraph<Order> orderSubgraph = graph.addSubgraph("orders");
orderSubgraph.addAttributeNodes("items");

Map<String, Object> hints = Map.of("javax.persistence.fetchgraph", graph);
User u = em.find(User.class, 42L, hints);
```

Django's equivalent is `Prefetch`, which lets you customise the queryset used for each relationship:

```python
from django.db.models import Prefetch

users = User.objects.prefetch_related(
    Prefetch('orders', queryset=Order.objects.select_related('shipping_address')),
    Prefetch('orders__items', queryset=LineItem.objects.filter(qty__gt=0)),
).all()
# 3 queries: users, orders (filtered by parent), line_items (filtered by parent + qty)
```

The deep advantage of entity graphs and `Prefetch` over static `fetch = EAGER` is that the *same entity class* serves multiple endpoints with different performance profiles. A common production incident: a developer adds `@ManyToOne(fetch = EAGER)` to `User.profile` because the user-list view needs it — and the user-export batch job, which loads 1M users, now JOINs profile whether it needs it or not, doubling the row width and blowing the job's memory budget from 4GB to 8GB. The dynamic graph makes the eager load *per-query*, not per-entity, so the batch job can opt out and the list view can opt in. Hibernate's *fetch profiles* (`@FetchProfile`) are an older, less-flexible variant of the same idea — they let you toggle a named fetch strategy at the session level (`session.enableFetchProfile("user-with-orders")`) but do not support arbitrary nesting. The modern recommendation is `@EntityGraph` for all new code; fetch profiles are a legacy Hibernate-specific feature that pre-dates JPA 2.1.

The production failure mode of *not* using dynamic graphs is *entity-level EAGER creep*: over years of feature additions, every relationship that any one endpoint needs gets marked `EAGER`, until loading a single `User` issues 17 JOINs and pulls 50MB of data. The diagnostic is Hibernate's `org.hibernate.SQL` logger plus a query-count middleware; the fix is to convert every `fetch = EAGER` to `fetch = LAZY` and add `@EntityGraph` annotations at the query site for the endpoints that actually need the data. This is a one-day refactor that has measurably cut p99 latency by 5–10× on every team that has done it.

## Cross-Ecosystem Implementation

The N+1 fix surfaces in every ORM under a different method name, but the underlying strategies are the same two: JOIN-based (one query) or batch-IN-based (two queries):

| Strategy | Hibernate / JPA | Django ORM | Eloquent | Prisma | SQLAlchemy |
|---|---|---|---|---|---|
| Eager load via JOIN | `JOIN FETCH` / `@EntityGraph` | `select_related()` | `with()` (single relation) | `include` (1:1 relation) | `joinedload()` |
| Eager load via batch IN | `@BatchSize(size=N)` / `@EntityGraph` with subgraph | `prefetch_related()` | `with()` (collection) | `include` (1:N relation) | `selectinload()` |
| Lazy load mechanism | Proxy class (subclass) | `ForeignKey` descriptor `__get__` | `BelongsTo` lazy guard | none (must explicitly `include`) | `LazyLoader` callable |
| Per-query override | `@EntityGraph(value="...")` on repo method | `Prefetch(rel, queryset=...)` | closure in `with()` | nested `include` object | `.options()` chain |
| Default fetch strategy | LAZY for `@ManyToOne` / `@OneToMany` | LAZY (no auto-join) | LAZY (no auto-join) | not loaded unless `include` | LAZY |

When you read the anchor implementation note, identify which Hibernate feature corresponds to each row above. The delta notes then show how the same N+1 fix is expressed in the other ecosystems — most importantly, where the default fetch strategy is LAZY (Hibernate, Django, Eloquent) the N+1 risk is *latent* and needs explicit opt-in eager loading; where the default is "not loaded at all" (Prisma), the N+1 risk is *replaced* by a compile-time obligation to declare what you want.

from django.db import connection, reset_queries
from myapp.models import User
reset_queries()
for u in User.objects.all()[:100]:
    _ = u.profile.bio
print(f'queries: {len(connection.queries)}')
for q in connection.queries[:5]:
    print(q['sql'][:120])
"
# Expected: queries: 101 (1 + 100). Each SELECT * FROM profiles WHERE user_id=? is logged.

from django.db import connection, reset_queries

    _ = u.profile.bio

"
