# 06.07.01. The Object-Relational Impedance Mismatch

## What This Is

The Object-Relational Impedance Mismatch is the structural friction between the object-oriented programming model (objects, identity, inheritance, bidirectional references, encapsulation) and the relational database model (flat tuples, primary keys, foreign keys, set-based operations, normalisation). The two models were invented independently — Codd's relational algebra in 1970, Smalltalk-style OO in the 1970s — and they make incompatible assumptions about how data is shaped, how it is identified, and how it is navigated. An ORM (Object-Relational Mapper) is the layer that bridges these two models, translating between them at runtime; the impedance mismatch is the set of irreducible compromises the ORM has to make.

This note covers the four facets of the mismatch: structural (object graph vs relational table), inheritance (single-table / class-table / concrete-table mapping), identity (object identity by memory address vs primary key by value), and navigation (object pointers vs foreign keys + joins). It then covers the spectrum of solutions — raw SQL, query builders, Active Record, Data Mapper — that trade off control against abstraction. The downstream notes [[06.07.02. The Active Record Pattern]] and [[06.07.03. The Data Mapper Pattern]] dive into the two most common ORMs; [[06.07.04. The Identity Map and Unit of Work Patterns]] covers the change-tracking machinery that ORMs use to paper over the identity facet; [[06.07.05. The N+1 Query Problem and Loading Strategies]] covers the most common production failure mode that the navigation facet produces.

## The Details

### Structural divergence: Relational algebra and set theory vs. Object Graphs, Pointers, a...

The relational model is built on set theory. A table is a set of tuples; each tuple is an unordered collection of column values drawn from atomic domains (first normal form). Relationships between tuples are expressed as *values* — a `user_id` foreign key column in the `posts` table holds the integer primary key of a row in the `users` table, and to find a user's posts you run `SELECT * FROM posts WHERE user_id = 42`. There are no pointers, no embedded objects, and no implicit ordering. Two tuples are "the same" if and only if their column values are equal (and the relational purist would say a table with no primary key has no notion of tuple identity at all — it is a bag, not a set).

The object model is built on graphs. An object is a node; references (pointers) between objects form edges. A `User` object holds a direct memory reference to a `List<Post>`, and to find a user's posts you write `user.getPosts()` — the runtime follows the pointer. Objects have *identity* independent of their value: two `User` objects with the same `email` field are still distinct objects (different memory addresses), and `user1 == user2` is reference equality unless you override `equals()`. Inheritance and polymorphism — central to OO design — have no direct relational equivalent. Encapsulation means an object's internal state is private; a relational table's columns are public and addressable by any query.

```text
The same logical data, in two models:

  OBJECT GRAPH                              RELATIONAL SCHEMA

  ┌──────────────┐                          users                posts
  │   User       │                          ┌─────┬────────┐     ┌─────┬─────────┬─────────┐
  │  id: 42      │◄────┐                    │ id  │ email   │     │ id  │ user_id │ title   │
  │  email: ...  │     │                    │─────┼─────────│     │─────┼─────────┼─────────│
  │  posts ──────┼─────┤                    │ 42  │ a@x.com │     │ 1   │ 42      │ Hello   │
  └──────────────┘     │                    │ 99  │ b@x.com │     │ 2   │ 42      │ World   │
                       │                    └─────┴─────────┘     │ 3   │ 99      │ Other   │
  ┌──────────────┐     │                                          └─────┴─────────┴─────────┘
  │   Post       │     │
  │  id: 1       │─────┘  ← direct pointer         ↑
  │  title: ...  │                                No pointer — only a value (user_id=42)
  └──────────────┘                                that must be matched against users.id
                                                  via a JOIN.
  Navigation: user.posts[0].title                 Navigation: SELECT p.title
                                                     FROM posts p JOIN users u ON p.user_id = u.id
                                                     WHERE u.id = 42
```

This structural divergence has four sub-problems, each of which an ORM must paper over.

**The inheritance problem.** OO languages let a `Manager` class extend `Employee`; SQL has no concept of inheritance. The ORM must choose one of three mapping strategies, each with sharp trade-offs. *Single-table inheritance* maps the whole class hierarchy to one table, with a `type` discriminator column and NULLable columns for subclass-specific fields — fast queries, but the table has many nullable columns and grows wide, and a NOT NULL constraint on a subclass field cannot be enforced at the DB level. *Class-table inheritance* maps each class to its own table, with the subclass table holding a foreign key to the parent — clean schema, but loading a subclass instance requires a JOIN across the hierarchy, and the ORM must decide whether to use JOINs or separate SELECTs (the "fetching strategy" problem). *Concrete-table inheritance* maps each concrete subclass to its own table, with the parent's columns duplicated in each — polymorphic queries (`SELECT * FROM employees` returning a mix of Manager and Engineer rows) require `UNION ALL` across all subclass tables, which is expensive and brittle.

**The identity problem.** In OO, two `new User(42)` calls produce two distinct objects — `user1 != user2` by reference equality, and mutating `user1.setName("X")` does not affect `user2`. In SQL, there is exactly one row with `id = 42`; an UPDATE changes that single row, and any subsequent SELECT sees the new value. If an ORM loads the same database row into two separate Java objects within one transaction and the application mutates both, the ORM cannot know which mutation to persist — it may write one and silently drop the other, or write them in some order and produce a state that matches neither. The fix is the *Identity Map* pattern (see [[06.07.04. The Identity Map and Unit of Work Patterns]]): the ORM maintains a `Map<PrimaryKey, Object>` per session/transaction and returns the same Java object on every `find(42)` call within that scope. Without this, you get the "lost update" anomaly even within a single transaction.

**The navigation problem.** OO objects navigate by following pointers: `user.getPosts().get(0).getComments().get(0).getAuthor().getName()` is a four-hop traversal that, if naively translated to SQL, becomes four separate queries (one per hop) — the classic N+1 query problem (see [[06.07.05. The N+1 Query Problem and Loading Strategies]]). The ORM must decide, at the moment `user.getPosts()` is called, whether to (a) issue `SELECT * FROM posts WHERE user_id = ?` immediately (eager loading), (b) defer the query until the collection is actually iterated (lazy loading), or (c) join it into the original query (fetch join). Each choice has different latency and memory characteristics, and the wrong choice either N+1s the database into the ground (lazy when the data is always needed) or loads megabytes of unused data (eager when the data is rarely needed). This is the single most common ORM-induced production incident.

**The granularity problem.** Some OO objects are finer-grained than tables (a `User` object with an embedded `Address` value object maps to one row in `users` plus columns like `street`, `city`, `zip` — the ORM must flatten the value object into columns and reconstitute it on load). Other objects are coarser-grained (a `User` object that aggregates the user's posts, comments, and audit log — the ORM must decide whether to load all of it on `find()` or only on demand). There is no universal right answer; the ORM exposes knobs (`@Embedded` in JPA, `select_related` in Django, `with()` in Laravel) and the application chooses per use-case.

The production failure mode of the structural mismatch is silent data corruption or performance collapse. Silent corruption happens when the ORM's identity map is bypassed (e.g., raw SQL queries that return new objects instead of reusing session-cached ones) and the application mutates two copies of "the same" row. Performance collapse happens when the navigation problem is mishandled — a single endpoint that loads 100 users and lazily fetches each user's posts produces 101 queries instead of 2, and at 100 RPS that is 10,100 queries per second to PostgreSQL, which manifests as `pg_stat_activity` showing 1000+ active connections all running `SELECT * FROM posts WHERE user_id = $1`.

### The Mapping Spectrum: Raw SQL vs. Query Builders vs. Active Record vs. Data Mapper

The impedance mismatch is irreducible — no library can make objects and tables structurally identical — so the engineering choice is *how much* of the mismatch the library papers over, and how much it leaves to the application. This produces a spectrum of four approaches, trading off control against abstraction.

```text
The mapping spectrum:

  Less abstraction ◄─────────────────────────────────────► More abstraction

  ┌─────────────────┐  ┌─────────────────┐  ┌─────────────────┐  ┌─────────────────┐
  │     Raw SQL     │  │  Query Builder  │  │  Active Record  │  │   Data Mapper   │
  │                 │  │                 │  │                 │  │                 │
  │ "SELECT * FROM  │  │ db.select('id', │  │ User.where(...) │  │ repo.find(id)   │
  │  users WHERE    │  │  'email')       │  │   .first()      │  │   → User POJO   │
  │  id = ?"        │  │  .from('users') │  │   .save()       │  │ repo.save(user) │
  │                 │  │  .where('id=?') │  │                 │  │                 │
  │ driver.exec()   │  │  .execute()     │  │                 │  │                 │
  └─────────────────┘  └─────────────────┘  └─────────────────┘  └─────────────────┘
  • Full SQL control   • SQL with fluent  • Entity IS the row • Domain object is
  • No mapping magic   • No entity graph  • save()/find() on  • Repository handles
  • No entity reuse    • Still SQL-shaped   the class itself   persistence
  • Manual every time  • Easier to compose • Coupled to schema • Decoupled domain
  • Best for: DBAs,    • Best for: dynamic • Best for: CRUD   • Best for: complex
    perf-critical      queries, reporting   apps, prototypes    domains, enterprise
    paths, migrations  • Knex, jOOQ, SQLAlchemy • Django, Eloquent,    • JPA/Hibernate,
                                            Rails AR             SQLAlchemy ORM
```

**Raw SQL** (JDBC `PreparedStatement`, node-postgres `client.query`, PHP `PDO::query`, Python `psycopg2.cursor.execute`) is the lowest abstraction. The application writes SQL strings, binds parameters, iterates `ResultSet` rows, and manually constructs objects (or just returns JSON). There is no mapping magic — what you write is what runs — but there is also no entity reuse, no change tracking, no lazy loading, and every query is hand-written. Raw SQL is the right choice for performance-critical paths (where you need to control the exact SQL plan), for migrations (where the ORM's schema model gets in the way), and for reporting queries that join many tables in ways the ORM doesn't expose. The cost is verbosity: a typical CRUD app needs ~6 queries per entity (find, findAll, insert, update, delete, count), and writing each by hand is hundreds of lines per entity.

**Query builders** (Knex.js, jOOQ, SQLAlchemy Core, Laravel's `DB::table()`) wrap SQL syntax in a fluent, composable API: `db.select('id', 'email').from('users').where('active', true).orderBy('created_at', 'desc').limit(10)`. The output is still a flat result set — there is no entity graph, no change tracking, no lazy loading. The win over raw SQL is composability: building a query conditionally (`if (filterByEmail) query.where('email', email)`) is natural in a query builder and awkward in raw SQL string concatenation (which is also a SQL-injection vector). Query builders are the right choice for dynamic queries (search filters, reporting), for SQL-shaped logic that doesn't map cleanly to entities, and as a layer under ORMs (Hibernate's HQL, Eloquent's query builder, SQLAlchemy's Core are all query builders used internally).

**Active Record** (Laravel Eloquent, Django ORM, Rails ActiveRecord, Prisma) maps a class directly to a table — the entity *is* the row. The `User` class has static methods like `User.find(1)`, `User.where(active: true)`, and instance methods like `user.save()`, `user.delete()`, `user.posts()` (which lazily loads related records). The mapping is one-to-one: one column = one attribute, one row = one instance, one foreign key = one association. This makes Active Record the fastest path to a working CRUD app — define a class, declare associations, and the ORM generates all the SQL. The cost is tight coupling: the domain object knows how to persist itself, which makes it hard to test in isolation (you can't instantiate a `User` without a database connection, because `User.save()` calls into the DB) and hard to evolve the domain model independently of the schema. See [[06.07.02. The Active Record Pattern]] for the full treatment.

**Data Mapper** (JPA/Hibernate, SQLAlchemy ORM in classical mode, Prisma, TypeORM with repositories) separates the domain object from the persistence layer. The `User` class is a plain POJO/POCO/POPO with no persistence methods — it has only fields, getters, setters, and domain logic (`user.activate()`, `user.changePassword()`). A separate `UserRepository` object handles persistence: `repo.find(id)`, `repo.save(user)`, `repo.findByEmail(email)`. The ORM tracks changes via a Unit of Work (see [[06.07.04. The Identity Map and Unit of Work Patterns]]) — when the transaction commits, the ORM diffs the working copy against the original snapshot and issues only the necessary UPDATEs. This decoupling lets the domain model evolve independently of the schema and makes the domain objects trivially testable (instantiate a `User` in memory, call methods, assert on field values — no DB required). The cost is verbosity: every entity needs a repository interface, the change-tracking machinery adds memory and CPU overhead, and the abstraction sometimes hides SQL inefficiencies (the classic N+1 from lazy loading).

| Approach | Coupling | Testability | Lines of code per entity | SQL control | When to use |
|---|---|---|---|---|---|
| Raw SQL | None (you write SQL) | High (no DB needed for non-DB logic) | ~200 (every query by hand) | Full | Perf-critical, migrations, reporting |
| Query Builder | Low (returns rows, not entities) | High | ~80 | Full (still SQL-shaped) | Dynamic queries, search filters |
| Active Record | Tight (entity = table) | Low (entity calls DB) | ~30 (declarations only) | Limited (ORM generates SQL) | CRUD apps, prototypes, MVPs |
| Data Mapper | Loose (entity is plain object) | High (entity has no DB) | ~60 (entity + repository) | Limited (ORM generates SQL, but `@Query` escape hatches) | Complex domains, enterprise apps |

The downstream notes dive into the two most common ORM patterns: [[06.07.02. The Active Record Pattern]] (Laravel Eloquent, Django ORM) and [[06.07.03. The Data Mapper Pattern]] (JPA/Hibernate, SQLAlchemy ORM). The choice between them is rarely "which is better" — it is "which fits my domain's complexity". A CRUD app with simple entities and lots of boilerplate-perfected controllers is well-served by Active Record; a domain with complex business rules (where the entity has methods that don't map to any single table) needs Data Mapper to keep the domain logic clean.

## Cross-Ecosystem Implementation

The same concept maps differently across the four target ORMs:

| Concept | JPA / Hibernate | Django ORM | Eloquent | Prisma |
|---|---|---|---|---|
| Pattern | Data Mapper | Active Record | Active Record | Data Mapper |
| Inheritance mapping | `@Inheritance(SINGLE_TABLE \| JOINED \| TABLE_PER_CLASS)` | Multi-table inheritance (implicit joined) | Single-table only (using a trait) | No inheritance — composition only |
| Identity map | `@Id` + `PersistenceContext` (per EntityManager) | None (each `User.objects.get()` returns fresh object) | None (each `User::find()` returns fresh object) | None (each `prisma.user.findUnique` returns fresh object) |
| Lazy loading | Proxy objects (Hibernate intercepts field access) | `select_related` needed (no implicit lazy) | `load()` needed (lazy by default for relations) | `include` needed (no implicit lazy) |
| N+1 fix | `@EntityGraph` or `JOIN FETCH` | `select_related` (join) or `prefetch_related` (separate query) | `with()` (eager load) | `include` |
| Migration | Flyway / Liquibase (versioned SQL files) | `makemigrations` (auto-detects model changes) | `migrate` (similar to Django) | `prisma migrate` (schema-first) |
| Connection pool | HikariCP (external) | Django's `CONN_MAX_AGE` (pseudo-pool, see [[06.06.02. Application-Level Connection Pools]]) | Laravel pool (per FPM worker) | Prisma pool (built into client) |

When you read the anchor implementation note, identify which ORM feature corresponds to each concept above. The delta notes then show how the same feature is expressed in the other ecosystems.

## Hands-On Exercise

```sql
-- See the query plan that an ORM generates (the cost of abstraction)
EXPLAIN ANALYZE SELECT * FROM users WHERE email = 'alice@example.com';

-- Compare to the same query with eager loading of posts:
EXPLAIN ANALYZE
  SELECT u.*, p.*
  FROM users u
  LEFT JOIN posts p ON p.user_id = u.id
  WHERE u.email = 'alice@example.com';

-- Check active transactions and locks (where the identity-map bypass shows up)
SELECT pid, state, wait_event, query FROM pg_stat_activity
  WHERE state != 'idle' ORDER BY query_start;

-- Enable query logging in PostgreSQL to see what the ORM actually sends
ALTER SYSTEM SET log_statement = 'all';
SELECT pg_reload_conf();
-- Then watch /var/log/postgresql/postgresql-*.log:
--   tail -f /var/log/postgresql/postgresql-*.log | grep -E 'LOG:|statement:'
```

```python
# Demonstrate the N+1 query problem (navigation facet of the mismatch)
# In Django ORM:
from myapp.models import User
users = User.objects.all()[:100]   # 1 query: SELECT * FROM users LIMIT 100
for u in users:
    print(u.posts.count())          # 100 queries: SELECT COUNT(*) FROM posts WHERE user_id = ?
# Total: 101 queries.

# Fix with prefetch_related:
users = User.objects.prefetch_related('posts')[:100]
for u in users:
    print(u.posts.count())          # 0 queries — already prefetched
# Total: 2 queries (one for users, one for all their posts in a single IN clause).
```

```java
// Demonstrate the identity problem in JPA
EntityManager em = emf.createEntityManager();
User u1 = em.find(User.class, 42L);   // SELECT — loads from DB
User u2 = em.find(User.class, 42L);   // NO SELECT — returns same instance
assert u1 == u2;                       // true — identity map returns the same object

// Without the identity map (e.g., raw JDBC):
User u1 = findByRawSql(42L);           // SELECT
User u2 = findByRawSql(42L);           // SELECT again
assert u1 == u2;                       // false — two distinct objects, even though same row
u1.setName("Alice");
u2.setName("Bob");
// Which one wins? Without an identity map, this is undefined.
```
