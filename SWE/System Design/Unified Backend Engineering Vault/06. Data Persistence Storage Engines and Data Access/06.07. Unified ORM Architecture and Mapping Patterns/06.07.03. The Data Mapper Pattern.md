# 06.07.03. The Data Mapper Pattern

## What This Is

The Data Mapper pattern is the architectural answer to one question: *where does persistence logic belong?* Martin Fowler defined it in *Patterns of Enterprise Application Architecture* (2003) as "a layer of mappers that moves data between objects and a database while keeping them independent of each other and the mapper itself." The pattern sits between the in-memory domain model — the objects that hold business state — and the storage engine — the file-system-plus-concurrency-control layer taught in [[06.00. Map of Content - Data Persistence]]. The mapper translates between two worlds that share no common data model: object graphs with identity-by-reference, inheritance, and bidirectional pointers vs. flat tables with primary keys, foreign keys, and CHECK constraints (see [[06.07.01. The Object-Relational Impedance Mismatch]]).

The distinguishing property of the Data Mapper is that the domain entity knows nothing about how it is persisted. A `User` POJO has fields, getters, setters, and business methods like `changeEmail()` — but no `save()`, no `delete()`, no `find()` methods. Persistence is the responsibility of a separate `Repository` object that depends on the entity, never the other way around. This is the inverse of [[06.07.02. The Active Record Pattern]], where `User.find(1)` returns a `User` instance that knows how to persist itself. The Data Mapper trades one-line simplicity for two things you cannot get any other way: (1) a domain model that can be unit-tested in isolation, instantiated without a database connection, and evolved independently of the schema; (2) a single place where SQL/HQL/JPQL is concentrated, which makes query optimisation, N+1 fixes, and connection pooling tractable.

In the layered mental model, the Data Mapper sits in the *persistence abstraction* layer — above the storage engine (PostgreSQL, MySQL, MongoDB) and below the application service layer. JPA/Hibernate, SQLAlchemy in its classical `mapper()` mode, Prisma, and Doctrine ORM all implement it; Django ORM, Eloquent, and Rails ActiveRecord do not (they are Active Record). The failure mode the pattern exists to prevent is the *bleeding of SQL into business logic*: when a domain object owns its persistence, every refactor of the schema touches the domain model, and every domain decision risks triggering a database query at the wrong moment. The Data Mapper draws a hard line at the repository boundary so that the domain model can be reasoned about as pure behaviour.

## The Details

### Architectural definition: Complete separation of the in-memory domain model from the da...

The defining property of the Data Mapper is that the entity class has zero persistence imports. In JPA/Hibernate this is approximately true — `@Entity`, `@Id`, `@Column` are *mapping* annotations, not persistence operations; the class has no `EntityManager` reference, no `save()` method, no transaction-awareness. In Prisma it is literally true — the generated TypeScript types are pure data shapes with no methods at all, and every database interaction goes through a separate `prisma.user.findUnique()` client call. In SQLAlchemy's classical Data Mapper mode (used with `mapper()` configuration rather than the declarative `Base` subclass) the domain class is a plain Python object and the mapper is wired separately.

The diagram below shows the dependency direction. Note that arrows only point inward — the database and mapper depend on the entity interface, but the entity depends on nothing:

```text
   ┌────────────┐         ┌──────────────┐         ┌─────────────────┐
   │  Service   │ ──────▶ │ Repository   │ ──────▶ │ EntityManager   │
   │  (domain)  │         │ (interface)  │         │ / Session       │
   └────────────┘         └──────┬───────┘         └────────┬────────┘
                                │ implements                │
                                ▼                           ▼
                         ┌──────────────┐         ┌─────────────────┐
                         │ Mapper       │ ──────▶ │ JDBC / DBAPI    │
                         │ (DataAccess) │         │  driver         │
                         └──────────────┘         └────────┬────────┘
                                                           │
                         ┌──────────────┐                  ▼
                         │  User (POJO) │           ┌─────────────────┐
                         │  no imports  │ ◀──────── │ PostgreSQL      │
                         └──────────────┘           └─────────────────┘
```

A concrete example: a Spring Boot `User` entity with a `changeEmail()` business method.

```java
@Entity
@Table(name = "users")
public class User {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(unique = true, nullable = false)
    private String email;

    @Embedded
    private AuditTrail auditTrail;

    // business logic lives here — no SQL, no EntityManager reference
    public void changeEmail(String newEmail) {
        if (!isValid(newEmail)) throw new IllegalArgumentException("...");
        this.email = newEmail;
        this.auditTrail.touch();
    }
}

// the repository is the only place that talks to the database
public interface UserRepository extends JpaRepository<User, Long> {
    Optional<User> findByEmail(String email);
}
```

The production failure mode this prevents is the *Active Record god-object*: a Django `Model` subclass that grows to 2,000 lines because it accumulates `send_welcome_email()`, `recompute_streak()`, `archive()`, and twelve `@property` methods that each issue a query. Refactoring any of that is dangerous because the same class is also the persistence contract — the migration file references its `db_table`, the ORM references its field list, and the unit tests require `pytest-django` with a real PostgreSQL fixture. The Data Mapper entity, by contrast, is unit-testable with `new User()` in plain JUnit — no Spring context, no database, no mock — because nothing on the class touches I/O.

### Core components: Entity, Repository, Data Mapper, Identity Map, Unit of Work

The Data Mapper is not a single class — it is a collaboration of five cooperating components. Each one carries a specific responsibility, and missing one of them collapses the pattern back into Active Record.

| Component | Responsibility | JPA/Hibernate concrete class | Prisma concrete class |
|---|---|---|---|
| Entity | Holds domain state and business methods; no persistence logic | `@Entity` annotated POJO | generated TS interface |
| Repository | Domain-facing query API; returns entities; hides SQL | `JpaRepository<T, ID>` | `prisma.user` (the delegate) |
| Data Mapper | Translates between entity fields and table columns; issues SQL | `EntityPersister` (Hibernate internal) | `PrismaClient` engine (Rust core) |
| Identity Map | Ensures one row → one object per session; prevents stale duplicates | `PersistenceContext` (`Map<EntityKey, Object>`) | not exposed (query-level caching only) |
| Unit of Work | Tracks dirty entities; orders INSERT/UPDATE/DELETE; flushes at commit | `ActionQueue` inside `SessionImpl` | transaction buffer (implicit) |

The Repository is the *domain-facing* surface — its method names are domain verbs (`findByEmail`, `findActiveSubscribers`, `save`). The Data Mapper is the *engine-facing* surface — it knows that `User.email` maps to `users.email` column, that `@Embedded AuditTrail` maps to `created_at` + `updated_at` columns, and how to bind a JDBC `PreparedStatement`. In JPA these two are split across `JpaRepository` (Spring Data) and `EntityPersister` (Hibernate); in Prisma they are fused into the `PrismaClient` but conceptually you can still see the split — the TypeScript-typed `prisma.user.findUnique()` is the repository, the Rust query-builder that turns it into SQL is the mapper.

The Identity Map and Unit of Work are taught in depth in [[06.07.04. The Identity Map and Unit of Work Patterns]]. Their role in the Data Mapper collaboration is to make the *transaction-scoped* behaviour correct: if `repo.findById(1L)` is called twice in the same Hibernate `Session`, the Identity Map returns the same Java object reference both times (preventing the bug where two copies of "user 1" diverge in memory); the Unit of Work records that the returned object's `email` field changed during the transaction, and at `commit()` time it issues a single `UPDATE users SET email=? WHERE id=?` — without the application having called `repo.save()` at all. That *automatic dirty checking* is the single biggest productivity feature the Data Mapper stack gives you, and it only works because all five components cooperate inside one transactional context.

### Trade-offs: High decoupling, enterprise maintainability, and domain purity vs. initial ...

The Data Mapper's signature cost is configuration boilerplate. A Spring Boot + JPA setup needs: a `DataSource` bean (HikariCP pool sizing), a `LocalContainerEntityManagerFactoryBean` wired with `HibernateJpaVendorAdapter`, a `JpaTransactionManager`, `@EnableJpaRepositories` pointing at the repository package, a `persistence.xml` or `application.yml` `spring.jpa.*` block, and `@Entity` classes with explicit `@Table` / `@Column` mappings. A Django model needs one line: `class User(models.Model): email = models.EmailField()`. For a greenfield CRUD app with five tables, that boilerplate-to-value ratio is unjustifiable — use Active Record.

Where the trade-off inverts is at the inflection point of *domain complexity*. Once the business logic in `User` exceeds simple field-accessors — once you have `applyDiscount()` that depends on `subscription.tier`, `region.tax_rate`, and `coupon.usage_count` — the Active Record model develops database queries inside its methods, and those queries execute synchronously on whatever request thread instantiated the model. Testing `applyDiscount()` now requires a database fixture; calling it from a Celery task without a Django `DB` connection crashes; refactoring the `subscriptions` table touches the model that owns the business logic. The Data Mapper avoids all three by keeping the entity pure — it receives its `Subscription` and `Region` as constructor arguments (injected by the service layer from repository calls), does the math, and the repository writes the result back at the end.

```text
                        ┌──────────────────────────────┐
   Project size         │   Domain logic complexity    │
   ─────────▶           │   ───────────────────────▶   │
                        │                              │
   CRUD prototype       │   Active Record wins         │
   (5 tables, no logic) │   - 1-line models            │
                        │   - zero config              │
                        │   - ship in a day            │
                        │                              │
   SaaS with rules      │   inflection point           │
   (multi-tenant,       │   ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─   │
    billing, audit)     │   Data Mapper wins           │
                        │   - testable domain          │
                        │   - schema-independent       │
                        │   - query surface area 1/N   │
                        └──────────────────────────────┘
```

A second cost is *latent N+1 risk*. Because the entity does not load its relationships eagerly (loading is the repository's job), naive iteration over a collection of entities will lazily fetch each child — see [[06.07.05. The N+1 Query Problem and Loading Strategies]]. Active Record has the same risk, but it is more visible because `User.find(1).posts` reads as "two queries." In the Data Mapper, `user.getPosts()` returns a Hibernate proxy that looks like a loaded collection and silently issues a query on first access — the bug is invisible until production traffic lights up the slow-query log. The mitigation is explicit eager-loading declarations at the query site (`@EntityGraph`, `select_related`, `with()`), which puts the burden back on the developer to know up-front which relationships each query needs. That is a fair price for decoupling, but it must be paid deliberately, not by accident.

### Target Implementation: Java JPA / Hibernate, Python SQLAlchemy (Data Mapper mode)

The two canonical Data Mapper implementations are JPA/Hibernate (Java) and SQLAlchemy in classical / non-declarative mode (Python). They differ in *where* the mapping is declared — JPA annotates the entity class itself with `@Entity`, `@Table`, `@Column`; SQLAlchemy classical mode keeps the mapping in a separate `mapper()` call so the entity class is truly pure. Prisma goes furthest — the entity is a generated TypeScript interface, and the mapping lives in a `schema.prisma` file that the Prisma engine reads at startup.

JPA/Hibernate example — the entity, the repository, and the service:

```java
// 1. Entity — pure domain object with mapping annotations
@Entity
@Table(name = "orders")
public class Order {
    @Id @GeneratedValue
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY)        // lazy by default
    @JoinColumn(name = "user_id")
    private User user;

    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL)
    private List<LineItem> items = new ArrayList<>();

    @Column(name = "total_cents")
    private long totalCents;

    // business method — no SQL, no EntityManager
    public void addItem(Product p, int qty) {
        LineItem item = new LineItem(this, p, qty);
        items.add(item);
        this.totalCents += p.getPriceCents() * qty;
    }
}

// 2. Repository — Spring Data generates the implementation at startup
public interface OrderRepository extends JpaRepository<Order, Long> {
    List<Order> findByUserIdOrderByCreatedAtDesc(Long userId);
}

// 3. Service — orchestrates repository + transaction
@Service
@Transactional
public class OrderService {
    private final OrderRepository orders;
    private final ProductRepository products;

    public OrderService(OrderRepository o, ProductRepository p) {
        this.orders = o; this.products = p;
    }

    public Order createOrder(Long userId, Long productId, int qty) {
        User u = users.findById(userId).orElseThrow();
        Product p = products.findById(productId).orElseThrow();
        Order o = new Order(u);
        o.addItem(p, qty);
        return orders.save(o);             // save() returns the managed instance
    }
}
```

SQLAlchemy classical Data Mapper — note how the `Order` class has no SQL, no `Base`, no `session`:

```python
from sqlalchemy import Table, Column, Integer, ForeignKey, Numeric, String
from sqlalchemy.orm import registry, relationship

mapper_registry = registry()

class Order:                # pure Python class — no persistence imports
    def __init__(self, user):
        self.user = user
        self.items = []
        self.total_cents = 0

    def add_item(self, product, qty):
        item = LineItem(self, product, qty)
        self.items.append(item)
        self.total_cents += product.price_cents * qty

order_table = Table(
    "orders", mapper_registry.metadata,
    Column("id", Integer, primary_key=True),
    Column("user_id", Integer, ForeignKey("users.id")),
    Column("total_cents", Integer),
)

mapper_registry.map_imperatively(Order, order_table, properties={
    "user": relationship(User),
    "items": relationship(LineItem, back_populates="order"),
})

# usage — the Session is the Unit of Work + Identity Map
from sqlalchemy.orm import Session
with Session(engine) as session:
    with session.begin():
        u = session.get(User, 42)
        p = session.get(Product, 100)
        order = Order(u)
        order.add_item(p, 3)
        session.add(order)                # registered with UoW, not yet INSERTed
    # on context exit: flush() issues INSERT INTO orders ... + INSERT INTO line_items ...
```

The two implementations share the same shape: entity has no I/O, mapper declares field↔column, repository/session is the only thing that talks to the driver. The difference is that Hibernate's `@Entity` annotation couples the entity to the JPA spec (you cannot reuse the class in a non-JPA project without the jar), while SQLAlchemy's classical mapping leaves the entity class import-clean. Prisma pushes this further still — the entity is generated code, regenerated from `schema.prisma` on every `prisma generate`, so the entity and the schema literally cannot drift. The production failure mode to watch for in all three is the *open-session-in-view* anti-pattern (Hibernate) / *lazy-load-outside-session* (SQLAlchemy): if the entity escapes the transactional context and the template layer calls a lazy getter, you get a `LazyInitializationException` (Hibernate) or `DetachedInstanceError` (SQLAlchemy) in production — fix it by eagerly loading at the repository call site, never by re-opening the session in the view layer.

## Cross-Ecosystem Implementation

The same Data Mapper concept maps differently across the four target ORMs:

| Concept | JPA / Hibernate | SQLAlchemy (classical) | Prisma | Doctrine (PHP) |
|---|---|---|---|---|
| Entity declaration | `@Entity` POJO + `@Table`/`@Column` | `class User: pass` + `mapper()` | `model User { ... }` in `schema.prisma` | `#[Entity]` PHP class + XML/YAML mapping |
| Repository | `JpaRepository<T, ID>` | `Session.query(User)` | `prisma.user` delegate | `EntityRepository` |
| Identity Map | `PersistenceContext` | `Session.identity_map` | per-query, not exposed | `UnitOfWork` identity map |
| Dirty checking | snapshot + bytecode-enhanced | snapshot comparison | none (writes explicit) | snapshot comparison |
| Mapping location | on the entity (annotations) | external `Table()` + `mapper()` | `schema.prisma` file | XML/YAML or attributes |
| Unit of Work | `ActionQueue` in `SessionImpl` | `Session` itself | implicit transaction buffer | `EntityManager::flush()` |

When you read the anchor implementation note, identify which ORM feature corresponds to each concept above. The delta notes then show how the same feature is expressed in the other ecosystems — most importantly, where the mapping lives (entity annotations vs external file vs generated code) determines how easy it is to keep the entity class import-clean.

## Hands-On Exercise

```bash
# 1. Hibernate — confirm the entity is import-clean. After compiling, inspect the .class:
javap -p target/classes/com/example/User.class
# You should see fields and methods, but NO javax.persistence.EntityManager reference.
# If you see $$_hibernate_* methods, bytecode enhancement has been applied.

# 2. Hibernate — verify the PersistenceContext holds one instance per key:
#    Add this to a service method and watch the identity hashcodes:
@Transactional
public void demonstrateIdentityMap(Long id) {
    User a = repo.findById(id).orElseThrow();
    User b = repo.findById(id).orElseThrow();
    log.info("a==b: {}, a hash: {}, b hash: {}",
             a == b, System.identityHashCode(a), System.identityHashCode(b));
    // Expected: a==b: true, identical hashcodes — Identity Map returned the same instance.
}

# 3. SQLAlchemy classical — verify the entity has no persistence imports:
python -c "from myapp.domain import User; import inspect; print(inspect.getsource(User))"
# Should print a class with no `Base` subclass, no `__tablename__`, no `Column` calls.

# 4. Prisma — confirm the entity is a generated interface:
cat node_modules/.prisma/client/index.d.ts | grep -A 5 "export type User"
# Should show: export type User = { id: number; email: string; ... }
# Plain data shape, no methods, no `save()`.

# 5. Hibernate — observe automatic dirty checking (no explicit save() call):
#    Set log level: logging.level.org.hibernate.SQL=DEBUG
#    In a @Transactional method, load a User, mutate its email, do NOT call repo.save().
#    At method exit, watch the log: "update users set email=? where id=?" is issued anyway.

# 6. Confirm the lazy-loading failure mode — call user.getPosts() after the session closes:
docker exec -it app java -jar app.jar    # with spring.jpa.open-in-view=false
# Hit an endpoint that returns a User without @EntityGraph on posts.
# Expect: org.hibernate.LazyInitializationException: could not initialize proxy - no Session
# This is the Data Mapper's strict boundary — you must declare eager loading at the query site.
```
