# 06.07.04. The Identity Map and Unit of Work Patterns

## What This Is

The Identity Map and Unit of Work are two cooperating patterns that sit *inside* the Data Mapper (see [[06.07.03. The Data Mapper Pattern]]) and answer two questions: *given a row, how do I make sure I have exactly one in-memory object representing it?* (Identity Map); and *given a graph of in-memory objects that have been mutated, how do I turn that into the minimum set of SQL statements, executed in the right order, in a single transaction?* (Unit of Work). Together they are what separates a real ORM from a thin query-result hydration library. Without them, calling `repo.findById(1L)` twice returns two Java objects whose fields can drift apart, and saving a list of 1,000 dirty entities issues 1,000 separate `BEGIN; UPDATE; COMMIT;` round-trips — slow, deadlock-prone, and inconsistent.

In the layered mental model these patterns sit one layer below the repository interface and one layer above the JDBC/DBAPI driver. Hibernate's `org.hibernate.engine.spi.PersistenceContext` is the Identity Map; its `org.hibernate.engine.spi.ActionQueue` is the Unit of Work. Django's ORM does not expose these names, but the implicit `TransactionAtomic` context manager and the per-`QuerySet` `_result_cache` play the same roles. SQLAlchemy's `Session` *is* both the Identity Map and the Unit of Work, fused into one object — `session.identity_map` is a public `dict`-like instance of `IdentityMap`, and `session._flush` is the unit-of-work flush procedure. The failure mode they exist to prevent is the *lost update* and the *phantom write*: two in-memory copies of "user 1" both call `setEmail()` and only one survives to disk, or a single logical change gets split across two transactions with a crash window between them.

The deep insight is that these patterns only work if you respect the *transactional context boundary*. A Hibernate `Session` is not thread-safe and is not meant to span multiple HTTP requests. A Django `transaction.atomic()` block must exit before the response is sent. The reason is that the Identity Map and Unit of Work are *mutable state*, and that state must be discarded at the end of each logical unit of work — otherwise the Identity Map grows unbounded (memory leak), and the Unit of Work's `UPDATE` queue accumulates writes from unrelated business operations (data corruption). Spring's `OpenSessionInViewInterceptor` and Django's `ATOMIC_REQUESTS = True` are the two most common ways to get this wrong in production.

## The Details

### Identity Map: Maintaining an in-memory dictionary of all database entities loaded withi...

The Identity Map is, at its core, a `Map<EntityKey, Entity>` where `EntityKey` is `(EntityType, Identifier)`. Every time the ORM hydrates a row, it computes the key and checks the map before constructing a new object: if the key already exists, the existing object is returned and the freshly-read row is discarded; if not, a new object is constructed and registered. This guarantees that within one transactional context, `repo.findById(1L)` called from the controller, `repo.findByEmail("a@b.com")` called from the service, and a `JOIN FETCH` that hydrates user 1 as a side effect all return the *same* Java reference. Mutations to that reference are visible everywhere — no risk of writing back a stale version.

The Hibernate `PersistenceContext` is implemented as a combination of three structures: `entitiesByKey` (the main map), `entityEntries` (the per-entity snapshot used by dirty checking — see the next H3), and `proxiesByKey` (uninitialised lazy proxies). The following diagram shows what happens when a single `SELECT u FROM User u WHERE u.id IN (1,2,1)` is executed inside one `Session`:

```text
   JPQL query:  SELECT u FROM User u WHERE u.id IN (1, 2, 1)
                ↓
   Hibernate translates to SQL:  SELECT * FROM users WHERE id IN (1,2,1)
                ↓
   JDBC ResultSet returns 3 rows:  row{ id=1, email='a@b.com' }
                                    row{ id=2, email='c@d.com' }
                                    row{ id=1, email='a@b.com' }   ← duplicate
                ↓
   PersistenceContext.entitiesByKey lookup per row:
       row 1: key=(User, 1) not in map → create User(id=1), put in map, return
       row 2: key=(User, 2) not in map → create User(id=2), put in map, return
       row 3: key=(User, 1) ALREADY in map → discard row, return existing instance
                ↓
   List<User> returned to caller:  [User@4f2a (id=1), User@8c11 (id=2)]
                                   note: only 2 distinct objects, NOT 3
```

The concrete Hibernate code path is `DefaultLoadEventListener.loadFromSecondLevelCache → loadFromSession → persistenceContext.getEntity()` — a `HashMap` lookup, O(1). The cost is negligible. The benefit is enormous: it makes the *graph of loaded objects* behave like an in-memory mirror of the database state for the duration of the transaction. Without it, the following bug is inevitable:

```java
// WITHOUT an Identity Map (hypothetical)
User a = repo.findById(1L);              // new User object A
User b = repo.findById(1L);              // new User object B — different reference!
a.setEmail("x@example.com");
b.setEmail("y@example.com");
repo.save(a);                            // UPDATE users SET email='x@...' WHERE id=1
repo.save(b);                            // UPDATE users SET email='y@...' WHERE id=1 — wins
// a.getEmail() now returns "x@..." but the database says "y@..." — stale in-memory state
```

The production failure mode of misusing the Identity Map is *letting it survive across requests*. If a Hibernate `Session` is stored in a static field or in an HTTP session, the Identity Map grows by every entity the user ever touches — easily tens of thousands of objects for a busy user — and the JVM heap blows up over hours. Worse, the snapshot copy stored for dirty checking (see next H3) means each entity occupies 2× its naive size. The fix is the standard pattern: one `Session` per HTTP request, opened in a `OncePerRequestFilter`, closed in a `try-finally` even if an exception is thrown. Spring's `OpenEntityManagerInViewFilter` does this for you; just verify it is actually installed and that `spring.jpa.open-in-view` is not simultaneously disabled in `application.yml` (a common misconfiguration that produces `LazyInitializationException`).

### Unit of Work: Accumulating database insert, update, and delete mutations in memory, com...

The Unit of Work is the write-side counterpart to the Identity Map's read-side. It records every entity that has been registered with the session as `insertable`, `updateable`, or `deletable`, and at flush time it computes the *minimal* set of SQL statements that materialise the in-memory state to the database. "Minimal" matters: if you call `order.addItem(p, 2)` and `order.removeItem(otherItem)` in the same transaction, Hibernate's `ActionQueue` does not blindly save the entire `orders` + `line_items` graph — it diffs the in-memory state against the snapshot, identifies that `order.totalCents` changed, that one `line_item` row needs INSERT and another needs DELETE, and emits exactly three SQL statements in dependency order (INSERT child, DELETE child, UPDATE parent), all inside one transaction.

The Hibernate `ActionQueue` orders operations to honour referential integrity without needing a database-level deferred constraint. The canonical ordering is:

```text
   1. INSERT orphans-then-parents in dependency order
        - collection-orphan-removal (DELETE children no longer referenced)
        - INSERT new entities in topological order (parent before child)
        - INSERT collection elements (line_items, tags)
   2. UPDATE entities (in any order — same table)
        - including collection updates (link table inserts/deletes)
   3. DELETE in reverse dependency order (children before parents)

   The full algorithm is AbstractFlushingEventListener.performExecutions() →
   ActionQueue.executeActions() which calls:
       executeInserts() → executeUpdates() → executeRemovals() → executeCollections()
```

A worked example: a transaction that creates a new `Order` for `User#1`, adds two `LineItem`s, and updates the user's `last_order_at`:

```java
@Transactional
public void placeOrder(Long userId, Long productId) {
    User u = users.findById(userId).orElseThrow();        // SELECT user, register in Identity Map
    Product p = products.findById(productId).orElseThrow();
    Order o = new Order(u);                                // not yet in UoW
    o.addItem(p, 2);                                       // mutates o.items, o.totalCents
    orders.save(o);                                        // UoW registers INSERT Order + 2 INSERT LineItem
    u.setLastOrderAt(Instant.now());                      // UoW registers UPDATE User
    // -- method returns, transaction proxy commits, flush() runs --
}
```

On flush, Hibernate issues exactly:

```sql
INSERT INTO orders (user_id, total_cents) VALUES (1, 1998);   -- 1
INSERT INTO line_items (order_id, product_id, qty) VALUES (42, 7, 2);   -- 2
UPDATE users SET last_order_at = '2024-...' WHERE id = 1;   -- 3
COMMIT;
```

Three statements, one transaction, correct dependency order. No `repo.save(u)` was necessary — the Unit of Work tracked `u` as dirty via the Identity Map (it was loaded through the session), compared `u.lastOrderAt` against the snapshot taken at load time, and queued the `UPDATE` automatically. This is the *automatic dirty checking* feature that makes JPA feel magical and that Django ORM does *not* have (in Django you must call `u.save()` explicitly — the Unit of Work is implicit but the dirty tracking is field-level not graph-level).

The production failure mode is the *long-running session*: a `Session` kept open across multiple user interactions accumulates dirty entities that the developer forgot about, and a single `flush()` at the end issues dozens of unexpected `UPDATE`s — including ones on entities loaded in a previous request that are now stale relative to the database. The classic symptom is `StaleObjectStateException` after a deploy: a code change renamed a field, the in-memory snapshot from the old code is still in the Identity Map, and the flush tries to write to a column that no longer exists. The fix is strict session-per-request discipline; never reuse a `Session` across transactions.

### Dirty Checking mechanisms: Snapshot comparisons vs. Bytecode enhancement state trackers

Dirty checking is the mechanism the Unit of Work uses to decide which entities need an `UPDATE`. Without it, every flush would `UPDATE` every loaded entity — even the ones that were only read — which would lock rows, defeat optimistic-concurrency versions, and pollute replication logs. The naïve algorithm is *snapshot comparison*: when an entity is loaded, the ORM deep-copies its persistent field values into a separate `Object[]`; at flush time it iterates every loaded entity, deep-compares current fields against the snapshot, and queues an `UPDATE` for any entity with a mismatch.

Hibernate's default dirty-checking uses snapshot comparison with a per-class `EntityPersister` that knows the property names and types. For a `User` with 10 fields, every flush walks every loaded `User` and does 10 `equals()` calls — O(N×F) per flush, where N is entities-in-session and F is fields-per-entity. For a request that loads 5,000 `User` records this is 50,000 comparisons, each of which may invoke `Arrays.equals` on `byte[]` or `String.equals` on email addresses — measurable, ~5–10ms of CPU on a modern CPU. The deep-copy snapshot also doubles the heap footprint of every loaded entity: each `User` occupies its own field storage *plus* the snapshot's `Object[10]`.

```text
   Per-entity memory in Hibernate (default mode):
   ┌─────────────────────────────────────────────┐
   │  User instance (10 fields, ~80 bytes)       │  ← live state, mutated by code
   ├─────────────────────────────────────────────┤
   │  loadedState: Object[10]                    │  ← snapshot, taken at hydration
   │    [0] Long id                              │      time, used only for dirty check
   │    [1] String email                         │
   │    ... 8 more                               │
   └─────────────────────────────────────────────┘
   Total per loaded User: ~160 bytes (2× the field cost)
```

Hibernate's optional `@DynamicUpdate` annotation changes the *SQL shape* (only changed columns appear in the `SET` clause) but does not change the dirty-check algorithm — the snapshot walk still happens. To eliminate the snapshot cost entirely, Hibernate offers **bytecode enhancement** with `enableDirtyTracking=true`. The Hibernate enhancer (run at build time via `hibernate-enhance-maven-plugin` or the Gradle plugin) rewrites the entity's bytecode so that every setter writes to a `boolean[] dirty` array and notifies an interceptor. At flush time, the persister asks the interceptor "is this entity dirty?" — an O(1) check, no snapshot walk.

```java
// Before enhancement — vanilla POJO, snapshot-based dirty check
public void setEmail(String email) {
    this.email = email;
}

// After bytecode enhancement — the setter is rewritten to track the change
public void setEmail(String email) {
    if (!Objects.equals(this.email, email)) {
        this.$$_hibernate_getInterceptor().attributeChanged("email", this.email, email);
    }
    this.email = email;
}
```

The trade-off: bytecode enhancement is a build-time operation that modifies your `.class` files, which complicates debuggers (step-through shows synthetic `$$_hibernate_*` fields in the variables view), confuses some serialisation frameworks (the `PersistentAttributeInterceptor` is not `Serializable`), and is silent if the plugin is misconfigured — you ship the un-enhanced bytecode, dirty checking falls back to snapshot mode, and nobody notices until a heap dump reveals the 2× memory cost. The production failure mode is the *memory surprise*: a service that loads 50,000 entities per request (a batch job) sees 100MB of snapshot arrays in the heap, GC pressure triples, and the 5-minute job takes 40 minutes. The diagnostic is `jmap -histo <pid> | grep -E "Object\[\]|User"` showing a 1:1 ratio of `Object[]` to `User` instances — that ratio is the signature of snapshot dirty checking. The fix is either bytecode enhancement (one-time setup) or restructuring the job to use a stateless `StatelessSession` that has no Identity Map and no dirty checking (every write is explicit `session.update(entity)`).

## Cross-Ecosystem Implementation

The Identity Map and Unit of Work surface differently in each ORM — some expose them as named objects, others fold them into a single Session concept:

| Concept | Hibernate | SQLAlchemy | Django ORM | Eloquent |
|---|---|---|---|---|
| Identity Map concrete type | `PersistenceContext.entitiesByKey` (`HashMap`) | `Session.identity_map` (`WeakIdentityMap`) | implicit per-QuerySet `_result_cache` | none (re-query always re-hydrates) |
| Unit of Work concrete type | `ActionQueue` inside `SessionImpl` | `Session` itself (it IS the UoW) | `transaction.atomic()` block | none (each `save()` is its own transaction) |
| Dirty checking | snapshot + bytecode-enhanced option | snapshot comparison | field-level (`save()` writes only changed fields) | field-level (only changed attributes in UPDATE) |
| Auto-flush on commit | yes (no explicit `save()` needed) | yes (no explicit `save()` needed) | no (must call `model.save()` per instance) | no (must call `->save()` per model) |
| Transaction-scoped | `@Transactional` boundary | `Session.begin()` context | `transaction.atomic()` context | `DB::transaction()` closure |

When you read the anchor implementation note, identify which Hibernate feature corresponds to each row above. The delta notes then show how the same concept is expressed in the other ecosystems — most importantly, where the Identity Map is implicit (Django, Eloquent) you must remember that the *same row queried twice in the same request* will be a different object, and you cannot rely on mutations propagating between them without an explicit `save()`.

## Hands-On Exercise

```bash
# 1. Hibernate — observe the Identity Map returning the same instance:
#    Add to a @Transactional service method:
#       User a = repo.findById(1L).orElseThrow();
#       User b = repo.findById(1L).orElseThrow();
#       log.info("a==b: {}", a == b);
#    Expected: a==b: true. The Identity Map returned the cached instance on the second call.
#    If you see false, your @Transactional boundary is wrong (two separate sessions).

# 2. Hibernate — observe automatic dirty checking (no save() call needed):
#    Enable SQL logging:
export SPRING_JPA_SHOW_SQL=true
export LOGGING_LEVEL_ORG_HIBERNATE_SQL=debug
export LOGGING_LEVEL_ORG_HIBERNATE_TYPE_DESCRIPTOR_SQL_BASICBINDER=trace
#    Then in a @Transactional method, load a User, mutate its email, do NOT call save().
#    At method exit, the log shows:
#       update users set email=? where id=?

# 3. Hibernate — verify snapshot dirty checking's 2x memory cost:
#    Load 50,000 users in one transaction, then:
jmap -histo:live <pid> | grep -E "User|Object\[\]" | head -20
#    Expect: roughly 50,000 User instances AND 50,000 Object[] instances (the snapshots).
#    Ratio 1:1 = snapshot mode. After enabling bytecode enhancement, the Object[] count drops to ~0.

# 4. SQLAlchemy — inspect the Identity Map directly:
python -c "
from sqlalchemy.orm import Session
from myapp.models import User
s = Session(engine)
u1 = s.get(User, 1)
u2 = s.get(User, 1)
print(f'u1 is u2: {u1 is u2}')           # True — Identity Map
print(f'identity_map keys: {list(s.identity_map.iter_keys())}')
"

# 5. Django — confirm the LACK of an Identity Map:
python manage.py shell -c "
from myapp.models import User
a = User.objects.get(id=1)
b = User.objects.get(id=1)
print('a is b:', a is b)                  # False — Django re-hydrates each query
a.email = 'x@y.com'
print('b.email:', b.email)                # original — a and b are independent objects
"

# 6. Reproduce the long-running session memory leak:
#    Store a Hibernate Session in HttpSession attributes, then load 100 entities per request.
#    After 100 requests, jmap -histo shows ~10,000 entities retained in the old generation.
#    Fix: never store Session in HttpSession; use OpenEntityManagerInViewFilter for per-request scope.
```
