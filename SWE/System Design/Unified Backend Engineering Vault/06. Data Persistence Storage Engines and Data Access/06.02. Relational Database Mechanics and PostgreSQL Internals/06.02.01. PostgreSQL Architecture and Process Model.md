# 06.02.01. PostgreSQL Architecture and Process Model

## What This Is

PostgreSQL uses a **process-per-connection** architecture: every client connection is served by a dedicated OS process, forked from the postmaster parent. This is in deliberate contrast to MySQL's thread-per-connection model (06.03.01) and to the thread-pool/event-loop designs of most modern servers. The choice was made in the 1980s when Berkeley POSTGRES was designed, and it has held up because process isolation gives the engine crash-safety for free (a backend that segfaults does not take the others down), the SQL executor can use a straightforward blocking I/O model (no callbacks), and shared memory provides the coordination point for the buffer pool and WAL. This note covers the postmaster, the per-connection backend, the shared memory regions, and the utility processes that run in the background. Every later PostgreSQL note (MVCC, replication, connection pooling) assumes this architecture.

## The Details

### The Process-based concurrency model: Postmaster parent process and dedicated backend processes per client connection

When PostgreSQL starts, the `postmaster` process begins listening on TCP port 5432 (and a Unix socket at `/var/run/postgresql/.s.PGSQL.5432`). When a client connects, the postmaster calls `fork()` to spawn a child process — the **backend** — which inherits the shared memory segment and the open file descriptors for the data directory. The backend performs the auth handshake, then enters the query loop: read a query, parse it, plan it, execute it, return the result. The backend lives for the lifetime of the connection; when the client disconnects, the backend exits.

```text
PostgreSQL process tree (ps -ef --forest output):

postgres──┬─postgres: checkpointer
          ├─postgres: background writer
          ├─postgres: walwriter
          ├─postgres: autovacuum launcher
          ├─postgres: stats collector
          ├─postgres: logical replication launcher
          ├─postgres: my_db(user) 10.0.0.5(54321)   ← client 1's backend
          ├─postgres: my_db(user) 10.0.0.6(54322)   ← client 2's backend
          └─postgres: my_db(user) 10.0.0.7(54323)   ← client 3's backend

Each "backend" is a forked child of the postmaster. Each has its own
private address space (~5-10 MB RSS minimum) plus the shared segment.
```

The decision to fork (rather than `pthread_create`) has three consequences that ripple through the rest of the engine. First, **crash isolation**: if a backend hits a null pointer dereference, the OS kills that backend with SIGSEGV; the postmaster sees the SIGCHLD, logs the crash, and continues serving other connections. The shared memory is intact because the dead backend's private state died with it. MySQL's thread model cannot do this — a segfault in one thread crashes the whole mysqld process. Second, **memory cost**: every backend has its own private `CatalogCache`, `relcache`, and query workspace. A connection holding 10 MB of RSS × 1000 connections = 10 GB, which is the dominant memory consumer on a heavily-connected PostgreSQL server. Third, **context-switch cost**: 1000 active backends on an 8-core machine means the scheduler is constantly switching among them, and `vmstat 1` will show tens of thousands of context switches per second. This is why PostgreSQL performance falls off a cliff past a few hundred active connections — see 06.06 on connection pooling.

The backend's query loop is a straightforward blocking I/O design: `recv()` from the socket, parse, plan, execute, `send()` the result. There are no callbacks, no event loops, no async/await in the executor — the backend blocks on disk I/O while waiting for a page read, which is fine because each backend has only one query in flight and the OS scheduler handles the multiplexing. This is the same model as a CGI script or a PHP-FPM worker, and it has the same scaling characteristic: linear in connection count until the scheduler saturates, then performance collapses. The fix in every ecosystem is the same: pool the connections so that the number of active backends stays near the number of CPU cores.

### Shared Memory Regions: Shared Buffers (database page cache), WAL Buffers, CLOG (Commit Log status)

The forked backends share state through a single System V shared memory segment (created with `shmget()` on startup, sized by `shared_buffers` plus a few other parameters). The shared segment holds four major regions, each of which is critical to understanding the engine's behaviour.

```text
PostgreSQL shared memory layout (simplified):
┌─────────────────────────────────────────────────────────────┐
│ shared_buffers  (default 128 MB; recommended 25% of RAM)    │
│   The page cache. 8 KB pages, organised as a hash table    │
│   keyed by (relation, fork, block number) → buffer.        │
│   Uses a clock-sweep algorithm (approximation of LRU).     │
│                                                             │
│ wal_buffers      (default -1, auto-sized to 1/32 of         │
│                   shared_buffers, min 64 KB, max 16 MB)     │
│   Holds WAL records waiting to be flushed to pg_wal.        │
│   No need for it to be large; commits force-flush it.       │
│                                                             │
│ CLOG             (Commit LOG — the per-transaction status)  │
│   2 bits per xid: IN_PROGRESS, COMMITTED, ABORTED,          │
│   SUBCOMMITTED. Stored in pg_xact/ as 8 KB pages.           │
│   Cached in shared memory for fast visibility checks.       │
│                                                             │
│ Other: lock tables, proc array (active transactions),       │
│        predicate lock table (for SERIALIZABLE),             │
│        per-backend stats counters, etc.                     │
└─────────────────────────────────────────────────────────────┘
```

`shared_buffers` is the most important tunable. It defaults to 128 MB, which is far too small for production. The PostgreSQL documentation recommends 25% of system RAM as a starting point, with the understanding that the OS page cache will hold the rest. The reason for not giving all RAM to `shared_buffers` is that the OS page cache caches the same pages (the data files are read via normal `read()` calls), and PostgreSQL's buffer pool eviction is less sophisticated than the kernel's working-set-aware page replacement. The standard advice: `shared_buffers = 25% of RAM`, then let the kernel cache the rest.

The CLOG is a deceptively important data structure. Every transaction's commit status is recorded as 2 bits in a single shared file (`pg_xact/0001`, `pg_xact/0002`, ...). When a backend checks whether transaction `T` is committed (which it does on every row read, to apply MVCC visibility rules — see 06.02.02), it consults the CLOG. The CLOG is small (2 bits × max xid), hot, and always cached. Without it, MVCC visibility checks would have to scan the WAL — catastrophically slow. The CLOG is also why transaction IDs are 32-bit integers in PostgreSQL: with 2 bits per xid, the CLOG is 1 GB maximum, fitting on disk.

The proc array (`ProcArrayGlobal`) is the list of all active backends and their current `xid`. It is the data structure that a new transaction consults to take its MVCC snapshot — "which transactions are currently in progress, so I can ignore their effects." A snapshot is therefore cheap: read the proc array once, copy the list of in-flight xids, and you have your visibility window. This is why `BEGIN; SELECT; ...` is fast in PostgreSQL even on a busy server — the snapshot is a single shared-memory read.

### Utility processes: Checkpointer, Background Writer, WAL Writer, Autovacuum Launcher, Stats Collector

In addition to the per-connection backends, the postmaster forks a fixed set of utility processes at startup. These are the engine's maintenance crew — they keep the buffer pool flushed, the WAL written, the dead tuples reclaimed, and the statistics current. They are visible in `ps` and named with their function, so an operator can immediately see what is happening.

```text
Utility processes and their jobs:
═══════════════════════════════════════════════════════════════════

CHECKPOINTER
  - Wakes every checkpoint_timeout (5 min) or when WAL volume
    exceeds max_wal_size (1 GB).
  - Writes all dirty shared_buffers pages to the OS page cache
    via write(), then calls fsync() on each data file.
  - Appends a CHECKPOINT record to the WAL and fsync()s the WAL.
  - Old WAL segments before the checkpoint LSN become recyclable.

BACKGROUND WRITER (bgwriter)
  - Continuously scans shared_buffers for dirty pages that have
    not been recently used, and writes them to the OS page cache.
  - Goal: reduce the work the checkpointer has to do at the next
    checkpoint, smoothing I/O.
  - Tuned by bgwriter_lru_maxpages (default 100) and
    bgwriter_delay (default 200 ms).

WAL WRITER (walwriter)
  - Flushes the wal_buffers to the pg_wal/ files on disk, even
    for transactions that have not yet committed.
  - Goal: keep the WAL file position ahead of the buffer pool's
    dirty state, so commits can be fast (just write a commit
    record and fsync — the data is already there).
  - Runs every wal_writer_delay (default 200 ms) or when
    wal_buffers is more than half full.

AUTOVACUUM LAUNCHER
  - Spawns autovacuum worker processes (up to
    autovacuum_max_workers, default 3) that reclaim dead tuples
    from tables whose dead-tuple count exceeds the threshold.
  - See 06.02.02 for the deep dive on why this is critical.

STATS COLLECTOR  (PG14+: replaced by shared-memory stats, but
                  the concept is the same)
  - Receives UDP messages from backends about table accesses,
    index accesses, and sequence usage.
  - Aggregates them into pg_stat_activity, pg_stat_user_tables,
    pg_stat_user_indexes — the views the planner consults.

LOGICAL REPLICATION LAUNCHER
  - Spawns workers for each subscription defined with
    CREATE SUBSCRIPTION.
  - These workers apply logical change events from a publisher.

ARCHIVER (when archive_mode is on)
  - Copies completed WAL segment files to archive_command
    (e.g. to S3 for point-in-time recovery).
```

The checkpointer and bgwriter share the job of flushing dirty pages to disk, but at different cadences. The bgwriter is a steady trickle (a few pages per second) to keep the steady-state dirty-page count low; the checkpointer is a periodic bulk flush (every 5 minutes by default) to bound recovery time. If you see write I/O spikes every 5 minutes in `iostat`, you are seeing the checkpointer. If you see continuous low-level writes, that is the bgwriter. The `checkpoint_completion_target=0.9` setting spreads the checkpoint's flush over 90% of the interval, smoothing the spike — a critical production tuning knob.

The autovacuum launcher is the most operationally important utility process. PostgreSQL's MVCC (06.02.02) creates dead tuples on every UPDATE and DELETE, and these dead tuples accumulate until a VACUUM reclaims them. Without autovacuum, tables grow without bound, indexes bloat, and eventually the transaction ID wraps around and the database shuts down to protect itself. Autovacuum is on by default since PostgreSQL 8.1 (2005); turning it off is one of the most common ways to break a production PostgreSQL deployment.

The failure mode that ties all these together is **connection exhaustion**: each backend is a process that holds private memory and a slot in the proc array. The default `max_connections=100` is a soft limit — the engine will accept more if asked — but the practical limit is set by RAM (`shared_buffers` + 10 MB × connections) and by the OS process limit. When the proc array fills, new connections hang waiting for a slot, and the application sees timeouts. This is the problem PgBouncer solves (06.06.03) by multiplexing many client connections onto a small pool of server connections, keeping the backend count near the CPU count.

## How This Connects to the Runtimes

Every runtime covered in section 04 has to deal with the cost of a PostgreSQL connection:

- **JVM + HikariCP**: pools connections at the application layer; each pooled connection is a long-lived backend. The pool size is the steady-state backend count. Spring Boot's default `maximum-pool-size=10` is conservative for an 8-core server.
- **Node.js / pg library**: opens connections per query unless explicitly pooled; the `pg.Pool` class is the standard pool. Node's single-threaded event loop means a single connection can serve many concurrent JS callbacks if they share a transaction context.
- **CPython + psycopg2 / psycopg3**: synchronous; each thread holds a connection. `psycopg2.pool.ThreadedConnectionPool` is the standard pool. AsyncPG goes further by multiplexing many queries over a single connection via PostgreSQL's pipeline mode.
- **PHP-FPM + PDO**: each FPM worker process holds its own connection; with 1000 FPM workers, you need PgBouncer to multiplex them onto ~20 server connections.

When you read those runtime notes, come back here and trace which kernel primitive each runtime feature maps to.

## Hands-On Exercise

Open a terminal on a Linux machine with PostgreSQL running and run the following commands:

```bash
# See the postmaster and all its child processes
ps -ef | grep postgres | grep -v grep
# Or with a process tree:
ps -ef --forest | grep -A 30 postgres

# See how much memory each backend uses
ps -eo pid,rss,cmd | grep postgres | sort -k2 -n -r | head
# RSS is in KB; expect ~10-50 MB per backend depending on workload

# See the shared memory segment
ipcs -m
# Look for a segment owned by postgres with a large size

# Query the live state from inside the database
sudo -u postgres psql
\l                                       -- list databases
SELECT count(*) FROM pg_stat_activity;   -- active backends
SELECT pid, application_name, state, query, query_start
  FROM pg_stat_activity
  WHERE state != 'idle';                  -- what is each backend doing?

# Watch autovacuum in action
SELECT pid, relid::regclass, phase, heap_blks_total, heap_blks_scanned
  FROM pg_stat_progress_vacuum;

# Force a checkpoint and watch the I/O
sudo -u postgres psql -c "CHECKPOINT;"
iostat -xmy 1     # in another terminal
```

Correlate each output with the bullets above. If you cannot match a row in the output to a concept in this note, re-read the relevant section.
