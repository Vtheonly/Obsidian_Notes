# 06.02.02. PostgreSQL Multi-Version Concurrency Control (MVCC)

## What This Is

PostgreSQL's MVCC is the reason a long-running analytical query does not block inserts into the table it is scanning, and the reason a transaction that runs for an hour does not block vacuuming of the rows it has already read. The core idea: every UPDATE creates a new row version instead of overwriting the old one, and every transaction sees only the row versions that were committed at the moment the transaction took its snapshot. Readers don't take locks; writers don't block readers; the cost is paid in dead tuples that must be reclaimed by VACUUM. This note covers the on-disk tuple format, the snapshot mechanism, the UPDATE path, the resulting table bloat, and the autovacuum tuning that prevents the engine from slowly dying. Get this note wrong in production and your database will eventually hit the transaction-ID wraparound cliff and shut itself down — every PostgreSQL operator has a story about that 3 a.m. page.

## The Details

### Row Versioning: Heap tuples containing system attributes (`xmin`, `xmax`, `t_ctid`, `infomask`)

Every row in a PostgreSQL heap table is a tuple with a header containing four system attributes that encode the row's version history. These are not columns you can `SELECT` by name in normal usage, but they are present on every row and they are what MVCC uses to decide whether a given transaction can see a given row.

```text
PostgreSQL heap tuple layout (in the slotted page from 06.01.01):
┌──────────────────────────────────────────────────────────────┐
│ HeapTupleHeader (23 bytes + padding):                       │
│   t_xmin     (4 B): xid of the transaction that INSERTed    │
│                     this version of the row.                │
│   t_xmax     (4 B): xid of the transaction that DELETEd or  │
│                     UPDATEd this version (0 = still live).  │
│   t_cid      (4 B): command id within the inserting         │
│                     transaction (for intra-transaction       │
│                     visibility).                             │
│   t_ctid     (6 B): ItemPointer to the next version of the  │
│                     row (self-pointer if this is the latest  │
│                     version, or pointer to the new row if    │
│                     this row was UPDATEd).                   │
│   t_infomask (2 B): bit flags — committed, aborted, locked, │
│                     etc. (HEAP_XMIN_COMMITTED, HEAP_XMAX_    │
│                     INVALID, ...).                           │
│   t_infomask2 (2 B): more bit flags (number of attributes,  │
│                     HOT update, etc.).                       │
│   t_hoff     (1 B): offset to user data (after null bitmap).│
├──────────────────────────────────────────────────────────────┤
│ Null bitmap (variable, only if any column is nullable).     │
├──────────────────────────────────────────────────────────────┤
│ User data (column values, aligned per type).                │
└──────────────────────────────────────────────────────────────┘

Total header overhead: 23 bytes minimum per row.
For a row with one int4 column, that's 23+4 = 27 bytes per row,
of which 23 bytes is MVCC overhead — a 6× storage inflation.
```

The visibility rule is: a row version is visible to transaction `T` if and only if (a) `t_xmin` was committed before `T`'s snapshot was taken AND `t_xmin` is not in `T`'s in-progress list, AND (b) `t_xmax` is either 0 (not deleted), or `t_xmax` was not committed before `T`'s snapshot, or `t_xmax` is in `T`'s in-progress list. The `t_infomask` bits cache the commit status of `t_xmin` and `t_xmax` so that the visibility check usually does not need to consult the CLOG (which would be a shared-memory lookup). A single bit check, then a comparison against the snapshot's xmin/xmax — that's all the per-row overhead of MVCC.

You can inspect these system columns directly:

```sql
SELECT xmin, xmax, ctid, * FROM users WHERE id = 42;
--   xmin  | xmax | ctid  | id | email
--  123456 |    0 | (3,5) | 42 | alice@example.com

-- xmin = 123456: this row version was inserted by transaction 123456
-- xmax = 0: it has not been deleted or updated
-- ctid = (3,5): it lives on page 3, slot 5 of the table file

-- Update the row, then look again
UPDATE users SET email = 'alice@new.com' WHERE id = 42;
SELECT xmin, xmax, ctid, * FROM users WHERE id = 42;
--   xmin  |  xmax  | ctid  | id | email
--  123460 |      0 | (3,6) | 42 | alice@new.com   ← NEW version

-- The old version is still in the table, now with xmax set:
SELECT xmin, xmax, ctid, * FROM users WHERE id = 42;
-- but you can see the dead version with a special scan:
SET enable_seqscan = on;  -- ensure we scan the heap
VACUUM users;             -- until this runs, the old tuple is still on disk
```

The `t_ctid` field is what makes UPDATE work without breaking indexes. When you UPDATE a row, PostgreSQL writes a new tuple somewhere (typically on the same page if there is room — a HOT update, Heap-Only Tuple, which avoids updating indexes). The old tuple's `t_ctid` is updated to point to the new tuple. Indexes that point at `(page, slot)` of the old tuple still work: a lookup finds the old tuple, follows `t_ctid` to the new tuple, and checks the new tuple's visibility. If the new tuple is invisible to the current transaction, the old one (which may still be visible) is returned. This chain is what `ctid` columns show — the physical address, which can change as the row is updated.

### Snapshot isolation mechanics: Transaction visibility algorithms based on active transaction lists and commit status

A **snapshot** is a transaction's view of the database at a single instant. PostgreSQL takes a snapshot when a transaction executes its first non-trivial statement (the isolation level determines *which* snapshot rule applies — see 06.04.03). The snapshot is a struct containing:

```text
Snapshot data (in shared memory, copied into the backend):
  - xmin: the earliest xid that is still in-progress. Anything
          older than this is either committed (visible) or
          aborted (invisible) — no need to check.
  - xmax: one past the latest xid that has been assigned. Any
          xid >= xmax is from a future transaction (invisible).
  - xip[]: the list of xids in [xmin, xmax) that are still
           in-progress at snapshot time. These are invisible.
  - curcid: the command counter of the current statement, for
            intra-transaction visibility.
```

The visibility check for a row with `t_xmin = X` against a snapshot `(xmin, xmax, xip)` is:

```text
def visible(X, snapshot, clog):
    if X < snapshot.xmin:
        # Transaction X started before our snapshot's earliest in-progress.
        # Its commit status is settled: either committed (visible) or
        # aborted (invisible). Consult the clog or the cached hint bits.
        return clog.is_committed(X)
    elif X >= snapshot.xmax:
        # Transaction X started after our snapshot was taken. Invisible.
        return False
    elif X in snapshot.xip:
        # Transaction X was in-progress when we took the snapshot. Invisible.
        return False
    else:
        # Transaction X started after snapshot.xmin, completed before
        # snapshot.xmax, and was not in the in-progress list at snapshot
        # time. It must have committed. Visible.
        return True
```

At the default `READ COMMITTED` isolation level, the snapshot is retaken at the start of every statement. So a `SELECT` at 10:00:00 sees the database as of 10:00:00, and a second `SELECT` at 10:00:05 sees it as of 10:00:05 — including any commits that happened in between. This is what makes `READ COMMITTED` prone to non-repeatable reads (06.04.02). At `REPEATABLE READ` (which in PostgreSQL is really Snapshot Isolation — see 06.04.03), the snapshot is taken once at the first statement of the transaction and held for the transaction's lifetime. Every statement in the transaction sees the same view of the database, regardless of what other transactions commit.

The snapshot is cheap to take: it is a single read of the proc array (the shared-memory list of active backends and their xids), copied into the backend's private memory. The expensive part is keeping the snapshot valid — which is why long-running transactions are problematic. As long as a transaction holds a snapshot, the engine cannot reclaim any dead tuple created after that snapshot's `xmin`, because the dead tuple might still be visible to that transaction. A single long-running `SELECT` on a busy table can cause gigabytes of dead tuples to accumulate, bloating the table and indexes. This is the classic "long-running query kills PostgreSQL" failure mode — and `pg_stat_activity`'s `state = 'idle in transaction'` is its smoking gun.

### The Update operation: Writing a newly created row version and updating the pointer chain without in-place mutation

PostgreSQL does not update rows in place. `UPDATE accounts SET balance = balance + 100 WHERE id = 1` does not modify the existing row on its page. Instead, it (a) writes a new row version with the new balance somewhere in the table (possibly on the same page if there is room, possibly on a different page), (b) sets the old row version's `t_xmax` to the current transaction's xid, (c) sets the old row version's `t_ctid` to point to the new version, and (d) updates the indexes — usually just the primary key index, if the update is a HOT update (Heap-Only Tuple, which happens when no indexed column changes and there is room on the page).

```text
UPDATE accounts SET balance = balance + 100 WHERE id = 1;

Before:
  Page 7, slot 2: [xmin=100, xmax=0, balance=500]    ← live version
                  ↑ indexes point here: (7,2)

After:
  Page 7, slot 2: [xmin=100, xmax=200, ctid=(7,9), balance=500]  ← dead
  Page 7, slot 9: [xmin=200, xmax=0, balance=600]                ← live
                  ↑ if HOT update, indexes still point at (7,2)
                    and the engine follows ctid to find (7,9).
                  ↑ if not HOT (an indexed column changed), the
                    index is updated to point at (7,9) directly.

The dead version at (7,2) is now reclaimable — but only after
every transaction that started before xid=200 has finished.
Until then, it stays in the table, taking up space.
```

The HOT optimisation is significant: it avoids updating every secondary index on the table when the update doesn't change any indexed column. Without HOT, an `UPDATE accounts SET balance = balance + 100` would have to update every index on `accounts` (because each index points to the row's physical location, which has changed). With HOT, the index entry still points to the old physical location, and the engine follows the `t_ctid` chain to find the live version. This makes narrow updates (changing one non-indexed column) almost as cheap as a no-op. HOT updates are reported in `pg_stat_user_tables.n_tup_hot_upd`.

The downside of this design is unavoidable: every UPDATE creates a dead tuple. A table that has 10 million UPDATEs per day, each on a 200-byte row, generates 2 GB of dead tuples per day. Without VACUUM, the table file grows monotonically — `pg_relation_size` keeps increasing, scans get slower, indexes bloat. This is the operational tax of PostgreSQL's MVCC: write amplification is built into the storage model, and the only mitigation is aggressive vacuuming.

### Table Bloat and Dead Tuples: The critical role of `VACUUM` and `ANALYZE`

`VACUUM` scans a table, identifies dead tuples (those whose `t_xmax` is committed and older than every active snapshot's `xmin`), and marks their space as reusable. It does not shrink the file — the dead tuple's slot becomes a free slot that future inserts can reuse, but the file size stays the same. `VACUUM FULL` (or `pg_repack`, or `pg_squeeze`) actually rewrites the table to compact it and return space to the OS, but it takes an `ACCESS EXCLUSIVE` lock that blocks everything.

```text
VACUUM lifecycle on a table:
─────────────────────────────────────────────────────────────
1. Scan the table's pages. For each page:
2. Build a list of dead tuple offsets (xmax committed, older
   than OldestXmin).
3. For each index on the table:
   - Remove index entries pointing at the dead tuple offsets.
4. Mark the dead tuple slots in the page as available for
   reuse (the page's free space map is updated).
5. If a page becomes entirely empty, mark it in the visibility
   map so future vacuums can skip it.

VACUUM does NOT shrink the file. To shrink, use VACUUM FULL
(blocks the table) or pg_repack (uses triggers, no block).
```

The visibility map is the key optimisation. It is a per-table bitmap with one bit per page, indicating "all rows on this page are visible to everyone." A page that has not had an UPDATE or DELETE since the last VACUUM has its visibility bit set; future VACUUMs and future index-only scans can skip the page entirely. This is why the first VACUUM after a burst of updates is slow (every page must be scanned) and subsequent VACUUMs are fast (most pages are skipped).

`ANALYZE` is a separate operation that updates the planner's statistics: the number of rows, the number of distinct values per column, the most common values, and a histogram of value distribution. These statistics live in `pg_statistic` and are what the planner consults to choose between a sequential scan and an index scan. `ANALYZE` is cheap and can be run as often as you like; the standard advice is to run it after large bulk loads or whenever the data distribution changes significantly. `VACUUM ANALYZE` runs both.

The visible failure mode of inadequate VACUUM is **table bloat**: a table that should be 10 GB grows to 100 GB because dead tuples are not being reclaimed fast enough. Symptoms: `pg_stat_user_tables.n_dead_tup` is large (>10% of `n_live_tup`), sequential scans take longer than they should, the buffer pool hit ratio drops, and disk usage grows without bound. The cure is more aggressive autovacuum tuning (see the next H3) or, in the worst case, a `VACUUM FULL` during a maintenance window.

### Autovacuum tuning: `autovacuum_vacuum_scale_factor`, `autovacuum_vacuum_threshold`, and preventing transaction ID wraparound (`txid`)

PostgreSQL's transaction IDs are 32-bit unsigned integers — they wrap around at 2^32 = 4.3 billion. When they wrap, old transactions' xids would appear to be in the future, breaking the visibility math. To prevent this, PostgreSQL periodically "freezes" old rows: a VACUUM that finds a row whose `t_xmin` is older than `vacuum_freeze_min_age` (default 50 million) replaces the `t_xmin` with a special `FrozenXID` (2) that is always considered committed. Once a row is frozen, its `t_xmin` no longer matters, and the xid can be reused.

The wraparound cliff is at `autovacuum_freeze_max_age` (default 200 million transactions). When the oldest unfrozen xid in the database approaches this number, PostgreSQL forces an autovacuum to freeze old rows — even if autovacuum is otherwise disabled. If the database reaches 2 billion transactions since the last freeze, it shuts itself down to prevent data corruption, refusing to start until you run `VACUUM FREEZE` in single-user mode. This is the most catastrophic PostgreSQL failure mode — and it is entirely preventable by leaving autovacuum on and monitoring `pg_stat_database.n_dead_tup` and `age(datfrozenxid)`.

```text
Critical autovacuum tunables (postgresql.conf):
─────────────────────────────────────────────────────────────
autovacuum = on                          (default — never disable)
autovacuum_max_workers = 3               (raise if many tables need vacuuming)
autovacuum_naptime = 1min                (how often the launcher checks)
log_autovacuum_min_duration = 0          (log every autovacuum)

# Threshold for triggering a vacuum on a table:
autovacuum_vacuum_scale_factor = 0.2     (default: 20% dead tuples)
autovacuum_vacuum_threshold = 50         (plus this many dead tuples)

# So a table with 1,000,000 rows gets vacuumed when it has
# 0.2 * 1,000,000 + 50 = 200,050 dead tuples.

# For large, frequently-updated tables, override per-table:
ALTER TABLE big_table SET (
  autovacuum_vacuum_scale_factor = 0.05,
  autovacuum_analyze_scale_factor = 0.02
);

# Wraparound protection:
autovacuum_freeze_max_age = 200000000    (force freeze vacuum)
vacuum_freeze_min_age = 50000000         (rows older than this get frozen)
vacuum_freeze_table_age = 150000000      (when to scan whole table for freezing)
```

The scale-factor default of 0.2 is too high for large tables. A table with 100 million rows accumulates 20 million dead tuples before autovacuum triggers — that is gigabytes of bloat. The standard production tuning is to set `autovacuum_vacuum_scale_factor` to 0.05 or 0.02 for large tables, or to use `autovacuum_vacuum_insert_scale_factor` (PG13+) to vacuum on inserts as well as updates. For very hot tables, the rule of thumb is: autovacuum should run often enough that `n_dead_tup` never exceeds a few percent of `n_live_tup`.

The deeper production failure mode is autovacuum **not keeping up** on a single very hot table. With `autovacuum_max_workers=3`, if three workers are all vacuuming three different tables, a fourth hot table has to wait. The fix is to raise `autovacuum_max_workers` (each worker is a separate process), and to lower the per-table thresholds so that vacuums run more often and finish faster (because there are fewer dead tuples to reclaim per run). The 3 a.m. page about "PostgreSQL is slow" is almost always traceable to either an `idle in transaction` connection holding an old snapshot, or autovacuum falling behind on a hot table — both areMVCC problems, and both are diagnosed with `pg_stat_activity` and `pg_stat_user_tables`.

## Cross-Ecosystem Implementation

| Concept | PostgreSQL | MySQL InnoDB | MongoDB WiredTiger |
|---|---|---|---|
| Old row versions stored in | Same table (heap) | Undo log (separate) | Per-collection B-tree, old versions in memory |
| Vacuum / cleanup | VACUUM (autovacuum) | Purge threads (automatic) | WiredTiger's internal MVCC |
| Snapshot taken | First statement (RC) / first txn statement (RR) | Statement (RC) / transaction (RR) | Per-operation |
| Wraparound risk | Yes (32-bit xid, must freeze) | No (6-byte trx_id) | No |
| Long-running query impact | Blocks vacuum for its snapshot's tables | Grows undo log (purge blocked) | None visible at query level |

## Hands-On Exercise

```sql
-- See the system columns on a row
SELECT xmin, xmax, ctid, * FROM users LIMIT 5;

-- See dead tuple accumulation
SELECT relname, n_live_tup, n_dead_tup,
       round(n_dead_tup::numeric / NULLIF(n_live_tup,0), 3) AS dead_ratio,
       last_autovacuum, last_autoanalyze
  FROM pg_stat_user_tables
  ORDER BY n_dead_tup DESC LIMIT 10;

-- See transactions that are blocking vacuum (long-running or idle-in-transaction)
SELECT pid, age(backend_xmin) AS xmin_age, state, query, query_start
  FROM pg_stat_activity
  WHERE state != 'idle'
  ORDER BY backend_xmin DESC NULLS LAST;

-- Check how close each database is to wraparound
SELECT datname, age(datfrozenxid) AS xid_age,
       round(100.0 * age(datfrozenxid) / 2000000000, 1) AS pct_to_emergency
  FROM pg_database ORDER BY xid_age DESC;

-- Manually trigger an aggressive vacuum with verbose output
VACUUM (VERBOSE, ANALYZE) big_table;

-- See HOT update ratio (should be high for narrow updates)
SELECT relname, n_tup_upd, n_tup_hot_upd,
       round(100.0 * n_tup_hot_upd / NULLIF(n_tup_upd,0), 1) AS hot_pct
  FROM pg_stat_user_tables WHERE n_tup_upd > 0;

-- Trigger a wraparound-protection freeze vacuum manually
VACUUM FREEZE ANALYZE small_table;
```
