# 06.01.03. B-Tree and B+ Tree Index Internals

## What This Is

Almost every relational index you have ever used — PostgreSQL's default `CREATE INDEX`, MySQL InnoDB's primary key, MongoDB's default `_id` index, Oracle's B-tree index — is a B+tree. The B+tree is the data structure that makes point lookups and range scans on disk-bound data fast enough to be useful: a 3-level B+tree can index a billion rows with at most three random disk reads, and a 4-level tree can index a trillion. This note covers why the B+tree is shaped the way it is (data only in leaves, leaves linked horizontally, internal nodes are pure routing), how page splits and merges keep the tree balanced under churn, and how the fan-out math works out. The LSM-tree in the next note (06.01.04) is the write-optimised alternative; the B+tree is the read-optimised workhorse.

## The Details

### Algorithmic properties: Self-balancing M-way search trees, guaranteed O(log N) search, insertion, and deletion

A B-tree (Bayer & McCreight, 1970) is a multi-way search tree where each node holds up to `M-1` keys and `M` child pointers. The "B" is not officially defined — Knuth says it stands for "Boeing" where the algorithm was invented, Bayer says it stands for "broad", and McCreight says "the more you think about what the B in B-trees means, the better you understand B-trees." The defining property is height balance: every leaf is at the exact same depth from the root, guaranteed by splitting nodes when they are full and merging them when they are underfull.

The complexity argument is direct. If each node holds up to `M-1` keys, then a tree of height `h` holds at least `2 * (M/2)^(h-1)` keys (the minimum fill factor is 50%) and at most `M^h - 1` keys. For a database page of 16 KB holding ~200 keys (M ≈ 200), a height-3 tree holds between 4,000 and 8,000,000 rows. Every point lookup visits exactly `h` pages — three 16 KB reads for the worst case, or zero reads if those three pages are already in the buffer pool (which they almost always are for the upper levels). This is the B-tree's central claim: **disk I/O count is bounded by tree height, which grows logarithmically with row count, and the constant factor is small enough that for any practical database the height stays at 3 or 4.**

```text
B-tree height vs row count (page size 16 KB, ~200 keys per page):
─────────────────────────────────────────────────────────────────
Height    Min rows       Max rows       I/Os per lookup
1         1              200            1
2         100            40,000         2
3         20,000         8,000,000      3
4         4,000,000      1,600,000,000  4
5         800,000,000    320,000,000,000,000  5

For comparison, a balanced binary tree (1 key per node) holding
1,000,000 rows has height ~20, requiring 20 random I/Os per lookup.
This is why binary search trees are not used for on-disk indexes.
```

Insertion maintains balance by **splitting**. When a leaf fills up (reaches `M-1` keys) and a new key must be inserted, the leaf splits at its median into two leaves with `(M-1)/2` keys each, and the median key is promoted up to the parent. If the parent is full, it splits too, promoting a key to its parent — and so on up to the root. When the root splits, a new root is created with two children, and the tree height grows by one. This is the only way the height increases, so it happens rarely and uniformly across the tree. Deletion is the mirror: when a leaf drops below `M/2` keys, it tries to borrow from a sibling; if both siblings are at minimum, it merges with one, demoting a key from the parent. If the root ends up with only one child, the child becomes the new root and height shrinks by one.

### Structural difference: Why B+ Trees store all data records in leaf nodes and use internal nodes strictly as routing pointers

The plain B-tree (rare in databases) stores both keys and data in every node — internal nodes carry data records, leaves carry data records. The **B+tree** (Comer, 1979) is the variant every database actually uses: internal nodes hold only routing keys, and all data lives in the leaves. This single change has three cascading consequences that make the B+tree dominant for storage.

First, internal nodes are much smaller per key. With no data, each routing entry is just a key plus a child pointer — say 12 bytes for a 64-bit key and a 64-bit page number. A 16 KB InnoDB page then holds ~1300 routing entries, giving a branching factor of ~1300 instead of ~200. The same 3-level tree now indexes 1300^3 ≈ 2.2 billion rows. That is roughly the population of the Chinese internet user base, on three random reads.

Second, range scans become sequential. Because all data is in leaves and the leaves are linked in a doubly-linked list, a query like `SELECT * FROM orders WHERE order_date BETWEEN '2024-01-01' AND '2024-01-31'` does: (a) descend the tree once to find the leftmost qualifying leaf, then (b) walk the leaf chain forward, reading consecutive pages in sequential I/O. This is dramatically faster than revisiting the upper tree for every row.

Third, the upper levels of the tree are extremely cacheable. The root and the top two levels of a 3-level tree total perhaps a few hundred KB, which fits easily in the buffer pool. So a point lookup on a warm cache hits the leaf in a single disk read, not three.

```text
B+tree structure (InnoDB-style, page size 16 KB):

                  Root page (level 2)
                  ┌──────────────────────┐
                  │ 100 | 200 | 300 | .. │   ← routing keys only
                  └─┬─────┬──────┬───────┘
            ┌───────┘     │      └────────┐
            ▼             ▼               ▼
     ┌────────────┐  ┌────────────┐  ┌────────────┐
     │ 50 100 150 │  │ 200 250    │  │ 350 400    │  ← leaves (data + keys)
     │ [row 1..]  │  │ [row 4..]  │  │ [row 7..]  │
     └─────┬──────┘  └─────┬──────┘  └─────┬──────┘
           ←─────────────────→─────────────────→    ← doubly-linked leaf chain
```

Why do B-trees (with data in internals) exist at all? Because they have a small advantage for *point* lookups when the data is small: a hit on an internal node returns the data without descending further. For databases where every leaf is a full 16 KB page of row data, this advantage evaporates — the data is too big to fit usefully in routing nodes — and the B+tree's range-scan and fan-out advantages dominate. So almost every production engine uses B+tree, and the term "B-tree" in database documentation colloquially means B+tree.

### Leaf node structure: Doubly-linked horizontal leaf chains enabling high-performance range scans

The leaf chain is what makes a B+tree a database index rather than just a search tree. Each leaf page has two extra pointers in its header: `next_leaf` and `prev_leaf`, holding the page number of the adjacent leaf in key order. A range query descends the tree once, finds the first leaf containing a key ≥ the lower bound, then follows `next_leaf` pointers forward, reading each leaf sequentially, until it reaches a key > the upper bound.

```text
Range scan: SELECT * FROM orders WHERE id BETWEEN 150 AND 350

Step 1: descend from root to find leftmost leaf containing id >= 150
        Root:    [100 | 200 | 300] → first key > 150 is 200, descend right
        Level 1: [100 | 150 | 200] → first key > 150 is 200, but key 150
                 is here, so descend to leaf at offset of key 150.
        Leaf:    [..140, 150, 160, 170..] → start emitting rows with id>=150.

Step 2: walk forward through leaves
        Read leaf → emit rows up to id=200
        Follow next_leaf pointer → next leaf
        Read leaf → emit rows up to id=300
        Follow next_leaf pointer → next leaf
        Read leaf → emit rows up to id=350 (or stop if id>350)

Each "read leaf" is a single 16 KB sequential I/O if the next leaf
is physically adjacent on disk, or a 16 KB random I/O otherwise.
B+tree leaf pages are usually allocated roughly in key order, so
the I/O pattern is mostly sequential.
```

The doubly-linked nature (both `next` and `prev`) supports backward scans (`ORDER BY ... DESC`) with the same efficiency as forward scans. The links are stored as 4-byte page numbers, so they survive buffer pool eviction — the chain is a structural property of the index, not a transient cache state. The chain is maintained during splits: when a leaf splits into two, the new leaf inserts itself into the chain by updating the `next_leaf` of the original leaf and the `prev_leaf` of the original's right neighbour.

The downside of the leaf chain is that it stores row data *twice* in a sense — once as the leaf's primary payload, and again (as a primary key) inside every secondary index that points to the row. In InnoDB, where the primary key IS the table (a clustered index), secondary indexes store the primary key value rather than a row pointer, so that a secondary index lookup can find the row via the primary B+tree. This is why adding a secondary index on a wide primary key (e.g. a UUID) bloats every other index.

### Page Splitting and Page Merging: Rebalancing mechanics during high-frequency insertions and deletions

Splits and merges are the operations that keep the tree balanced and are the main source of write amplification in a B+tree. A **leaf split** happens when a leaf has `M-1` keys and a new key must be inserted. The leaf is divided at its median: the lower half stays, the upper half moves to a new leaf, and the median key is promoted to the parent. If the parent is also full, it splits too, and so on up the tree. Each split writes one new page (the new sibling) and updates the parent — so a single row insert can dirty up to `h` pages, where `h` is the tree height.

The split pattern matters for performance. A **median split** (50/50) keeps the tree balanced for random insertions. A **sequential split** (90/10, keeping 90% in the original leaf and 10% in the new one) is used by some engines when inserts are monotonically increasing, because the rightmost leaf is the one that grows and a median split would waste half the original leaf's space. PostgreSQL calls this the "fast path" for monotonically-increasing inserts into a B-tree.

```text
Leaf split when inserting key=25 into leaf [10,20,30,40] (max 4 keys):

Before:   parent: [... | 30 | ...]
                  ↓
          leaf:  [10, 20, 30, 40]   (FULL — cannot accept 25)

After:    parent: [... | 25 | 30 | ...]      ← new key promoted
                  ↓           ↓
          leaf:  [10, 20]      leaf:  [25, 30, 40]   ← split 50/50

Cost: 1 new page allocated, 2 leaves rewritten, 1 parent page updated.
If the parent was also full, it splits too, propagating up.
```

A monotonically increasing primary key (like `BIGSERIAL` or `AUTO_INCREMENT`) is the optimal case: every new row goes into the rightmost leaf, and splits happen only when that leaf is full. The new leaf is allocated at the end of the file (sequential I/O), and the upper levels of the tree are rarely touched because the rightmost path is the only one that grows. A random primary key (like UUID v4) is the worst case: every insert goes to a random leaf, causing splits all over the tree, fragmenting the physical layout, and turning sequential scans into random I/O. This is why UUID v7 (time-ordered) was introduced — it gives the uniqueness of a UUID with the insert pattern of a serial.

Merges are the inverse of splits, triggered on delete. When a leaf drops below `M/2` keys, the engine first tries to **borrow** a key from a sibling (rotating one key through the parent). If both siblings are also at minimum, it **merges** the leaf with a sibling, demoting the separating key from the parent. If the parent then drops below minimum, it merges with its sibling, and so on. Merges are rare in practice because most workloads have inserts, deletes, and updates in roughly equal proportion, and the tree tends toward a steady-state fill factor of about 70%. PostgreSQL and InnoDB both have a "deletion cleanup" pass that lazily removes empty pages rather than aggressively merging — this avoids write amplification on workloads with bursts of deletes followed by inserts in the same range.

The production failure mode here is **index bloat** on a UUID primary key. A table with 100 million rows inserted in random order can have a B+tree 60% full instead of 70%, requiring 15% more pages to scan and 15% more buffer pool to keep warm. The fix is `REINDEX INDEX CONCURRENTLY` (PostgreSQL) or rebuilding the table (MySQL), but the better fix is to use a time-ordered key in the first place. The deeper lesson is that the choice of primary key is not just a schema decision — it determines the physical layout of every page in the table and every secondary index.

## Cross-Ecosystem Implementation

| Engine | Default index type | Page size | Clustered? | Notes |
|---|---|---|---|---|
| PostgreSQL | B-tree (B+tree variant) | 8 KB | No (heap table) | Secondary indexes store (key, heap TID) |
| MySQL InnoDB | B+tree | 16 KB | Yes (PK is table) | Secondary indexes store (key, PK) |
| MongoDB WiredTiger | B-tree (default) or LSM | 32 KB default | Yes (`_id` is clustered) | Configurable per collection |
| Oracle | B+tree | 8 KB default | Optional (IOT) | Index-organised tables available |
| SQLite | B+tree | 4 KB default | Yes (rowid is PK) | `WITHOUT ROWID` tables use different layout |

## Hands-On Exercise

```sql
-- PostgreSQL: inspect the B-tree structure of an index
CREATE TABLE t (id serial PRIMARY KEY, payload text);
INSERT INTO t (payload) SELECT md5(random()::text) FROM generate_series(1, 1000000);

-- See index size and depth
SELECT pg_size_pretty(pg_relation_size('t_pkey')) AS index_size;
-- 21 MB  (a million int4 keys + row pointers in 8 KB pages)

-- Force the planner to use the index, see the plan
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM t WHERE id = 500000;
-- Index Cond: (id = 500000)  Buffers: shared hit=4  ← 4 pages = root+branch+leaf+heap

-- Inspect index page contents (contrib extension)
CREATE EXTENSION pageinspect;
SELECT * FROM bt_page_items('t_pkey', 1) LIMIT 5;
-- itemoffset | ctid  | itemlen | data
-- 1           | (0,1) | 16      | 00 00 00 00 ...

-- MySQL InnoDB: see the index depth via the data dictionary
SELECT INDEX_NAME, INDEX_TYPE, STATS_PAGE_SIZE, NUM_PAGES
FROM information_schema.INNODB_SYS_INDEXES i
JOIN information_schema.INNODB_SYS_TABLES t USING (TABLE_ID)
WHERE t.NAME = 'your_db/t';

-- Force a split with a random-key insert pattern
CREATE TABLE uuid_test (id uuid PRIMARY KEY DEFAULT gen_random_uuid(), x int);
INSERT INTO uuid_test (x) SELECT 1 FROM generate_series(1, 1000000);
SELECT pg_size_pretty(pg_relation_size('uuid_test_pkey'));
-- 56 MB  ← 2.5x larger than the serial-key equivalent, due to splits and low fill factor
```
