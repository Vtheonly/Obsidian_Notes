# 06.01.01. Disk Access Mechanics and Page-Based Storage

## What This Is

Every database engine — PostgreSQL, MySQL InnoDB, MongoDB's WiredTiger, RocksDB, Cassandra's storage layer — is at bottom a program that calls `open()`, `read()`, `write()`, `lseek()`, and `fsync()` against files that live on a filesystem that the kernel manages. The whole edifice of indexes, transactions, MVCC, replication, and query planning is a set of optimizations layered on top of those five system calls and the physics of the storage device behind them. This note covers the lowest layer: how storage hardware actually behaves, how the kernel caches it, and how engines organize bytes on disk into the page-based structures every later note takes for granted. Without this layer, statements like "PostgreSQL uses 8 KB pages" or "InnoDB's buffer pool is the L1 cache of the database" have no anchor.

## The Details

### Hardware characteristics: HDD mechanical seek latency vs. SSD/NVMe flash block write/erase cycles

A spinning hard disk is a magnetic platter rotating under a movable actuator arm. Reading byte `N` requires (a) seeking the arm to the right track (~5–10 ms), (b) waiting for the platter to rotate the target sector under the head (~half a rotation, ~3 ms at 7200 RPM), and (c) the actual read (~100 MB/s sustained). The cost is dominated by the mechanical motion, not the data transfer, which is why sequential reads are roughly 100× faster than random reads on HDD. The kernel exposes this asymmetry through `/sys/block/sdX/queue/rotational` (1 = rotational, 0 = SSD).

A NAND flash SSD has no moving parts. Reads are random-access at ~50–100 µs for SATA SSDs, ~10 µs for NVMe over PCIe, and ~1 µs for Optane-class NVDIMMs. Writes, however, are constrained by the erase-block rule: flash can only write in 4 KB pages, but can only erase in much larger blocks (typically 128 KB or 256 KB). Updating a single 4 KB page requires reading the whole erase block, modifying the page in memory, erasing the entire block, and writing it back — unless the SSD's firmware lies with a log-structured FTL (Flash Translation Layer) that always writes to a fresh page and garbage-collects the old one in the background. This is why SSDs have write-amplification factors of 1.5×–3× and why consumer SSDs slow down dramatically under sustained random writes when their SLC cache fills up.

```text
Operation              HDD        SATA SSD    NVMe       Optane
─────────────────────────────────────────────────────────────────
4 KB random read       5–10 ms    100 µs      10–50 µs   1–2 µs
4 KB random write      5–10 ms    100 µs      10–50 µs   1–2 µs
Sequential read        100 MB/s   550 MB/s    3 GB/s     5 GB/s
Sequential write       100 MB/s   500 MB/s    2 GB/s     4 GB/s
fsync latency          ~10 ms     ~100 µs     ~50 µs     ~5 µs
IOPS (random 4 KB)     ~100       ~50,000     ~500,000   ~5,000,000
```

The practical consequence: a database running on a single NVMe drive can sustain 50,000+ commits/sec through `fsync`, while the same database on a 7200 RPM HDD tops out around 100 commits/sec. The `fsync` latency ceiling, not CPU, is the binding constraint on write throughput for OLTP databases. This is why no production database should ever run on spinning disks for the WAL — and why cloud providers charge a premium for "provisioned IOPS" EBS volumes.

### Sequential vs. Random Disk I/O throughput performance profiles

The sequential-vs-random gap defines every storage-engine design choice. On an HDD, sequential reads deliver ~100 MB/s while random 4 KB reads deliver ~100 × 4 KB = 400 KB/s — a 250× difference. On an SSD the gap narrows but does not disappear: a single NVMe queue can serve ~500 K random 4 KB reads/sec (2 GB/s) but sequential reads can hit ~3 GB/s, and writes are even more asymmetric because of the erase-block FTL cost. The kernel reports the gap through `iostat -x 1`: `r/s` (reads per second), `rkB/s` (kilobytes read), `await` (average wait in milliseconds), and `%util`.

This asymmetry drives three architectural patterns. First, **B+ trees** (06.01.03) cluster data into 8–16 KB pages so a single random read fetches many rows — converting random row lookups into page-granular random I/O, which is the smallest unit the hardware handles efficiently. Second, **LSM trees** (06.01.04) and the Redis AOF convert random writes into sequential appends, because writing a new SSTable at the end of a file is one large sequential write instead of N small random page updates. Third, **WAL files** (06.01.02) are always written sequentially, which is why commit throughput is bounded by `fsync` latency and not by the WAL write itself.

```bash
# Measure sequential vs random I/O on a device
# Sequential 1 MB writes, queue depth 1:
fio --name=seq --filename=/tmp/test --rw=write --bs=1M --size=1G --iodepth=1 --direct=1
# Random 4 KB writes, queue depth 1:
fio --name=rnd --filename=/tmp/test --rw=randwrite --bs=4k --size=1G --iodepth=1 --direct=1

# Real-time device statistics while a database is running:
iostat -xmy 1
# r/s    w/s   rkB/s  wkB/s  await  %util  device
# 0.00   1240  0.00   4960   0.12   98.5   nvme0n1
```

The `%util` column is misleading on multi-queue NVMe — a device can show 100% utilisation and still have spare capacity because the kernel is issuing from multiple queues. Look at `await` (latency) and `r/s`+`w/s` (IOPS) instead. If `await` rises above the device's spec latency under load, you have saturation.

### The Slotted-Page Storage Architecture: Page Headers, Slot Arrays (Offsets and Lengths), and Variable-Length Tuple Storage

A database table is not a flat array of rows. It is a sequence of fixed-size **pages** (8 KB in PostgreSQL, 16 KB in InnoDB, 32 KB default in MongoDB WiredTiger), and each page internally uses a **slotted page** layout so variable-length rows can be inserted, updated, and deleted without rewriting the whole page. The slotted-page structure has three regions:

```text
  ┌────────────────────────────────────────────────┐  ← offset 0
  │ Page Header (24 B in PostgreSQL)               │
  │   pd_lsn, pd_checksum, pd_lower, pd_upper,     │
  │   pd_special, pd_pagesize_version              │
  ├────────────────────────────────────────────────┤
  │ ItemId Array (4 B per slot, grows downward)    │
  │   slot 0: [offset, length, flags]              │
  │   slot 1: [offset, length, flags]              │
  │   ...                                          │
  ├────────────────────────────────────────────────┤
  │                                                │
  │              Free space (grows up)             │
  │                                                │
  ├────────────────────────────────────────────────┤
  │ Tuples (heap rows, grow upward from bottom)    │
  │   tuple N: [header + data]                     │
  │   tuple N-1                                    │
  │   ...                                          │
  │   tuple 0                                      │
  └────────────────────────────────────────────────┘  ← offset page_size
```

The page header holds the page's LSN (so the WAL can decide whether the page is older or newer than a given log record), a checksum, and the offsets that bound the free space. The **item-id array** at the top is a directory of slot pointers — each slot is 4 bytes containing a tuple's offset, length, and status flags. The actual tuple data grows upward from the bottom of the page. Inserting a row adds a slot at the top of the item-id array and a tuple at the bottom of the free space; the two grow toward each other.

This layout exists because rows are variable length (a `VARCHAR(255)` holding "hi" is 2 bytes plus header, not 255). If rows were stored as a flat array, deleting a row would require shifting all subsequent rows or leaving a hole. The slotted page makes the slot array the stable address: a secondary index points at `(page_number, slot_number)`, and the slot's offset can change when the tuple is updated or compacted without breaking the index. PostgreSQL's heap, InnoDB's `.ibd` files, and SQLite's b-tree pages all use variants of this scheme.

The page size is not arbitrary. It must be a power of two so the kernel can map it directly to the hardware page (4 KB on x86_64, 64 KB on some ARM) and to the filesystem block (4 KB on ext4, up to 64 KB on XFS). PostgreSQL uses 8 KB — chosen in the 1990s as a compromise between the cost of a single I/O and the granularity of buffer-pool management. InnoDB uses 16 KB, on the theory that a single random I/O on a spinning disk cost the same for 4 KB or 16 KB, so 16 KB amortised the seek cost better. MongoDB's WiredTiger defaults to 32 KB because documents tend to be larger than rows. These choices are baked into the file format and cannot be changed without a major version upgrade.

### Row-Oriented Storage (OLTP: fast transactional single-record lookups) vs. Column-Oriented Storage (OLAP: high-throughput vectorized aggregations)

In a row-oriented store, all columns of a row are stored contiguously in the same page. PostgreSQL, InnoDB, and MongoDB all use this layout. It optimises for the OLTP access pattern: `SELECT * FROM users WHERE id = 42` reads one page, gets the whole row, and returns. The cost is paid by analytical queries: `SELECT AVG(balance) FROM users` must read every page of the table even though it only uses one column, because the column data is interleaved with all the other columns on the same pages.

In a column-oriented store, each column is stored in its own file (or its own set of pages). A columnar scan for `AVG(balance)` reads only the `balance` column's pages — a 10× to 100× reduction in bytes read for a 10-column table. Columnar stores also compress aggressively: a column of timestamps or country codes has low cardinality and run-length-encoding can shrink it 10×. The cost is paid by single-row reads: reconstructing a full row requires reading one page from each column's file and stitching them together, which is many random reads.

```text
Row-oriented (PostgreSQL heap page):       Column-oriented (ClickHouse / Parquet):
┌────────────────────────────┐             users.id.bin     users.email.bin
│ row 1: [id|email|balance] │             ┌──────────┐     ┌──────────┐
│ row 2: [id|email|balance] │             │ 1        │     │ a@x.com  │
│ row 3: [id|email|balance] │             │ 2        │     │ b@y.com  │
│ row 4: [id|email|balance] │             │ 3        │     │ c@z.com  │
└────────────────────────────┘             │ 4        │     │ ...      │
                                           └──────────┘     └──────────┘
SELECT AVG(balance) reads ALL columns.    SELECT AVG(balance) reads only balance.bin.
```

Real systems are hybrid. PostgreSQL 11+ supports **columnar partitioning** via extensions like Citus and TimescaleDB compressed chunks. ClickHouse is pure columnar. Snowflake stores data in micro-partitions that are columnar within each partition. The HTAP (Hybrid Transactional/Analytical Processing) engines — TiDB with TiFlash, MySQL HeatWave, SingleStore — keep a row-oriented primary for OLTP and replicate to a columnar replica for OLAP. The choice is always the same trade-off: optimise the read path for single-row point lookups (row-oriented) or for bulk aggregations over many rows (column-oriented). You cannot optimise both with one physical layout.

## How This Connects to the Runtimes

Every runtime covered in section 04 calls down to the same Linux I/O syscalls:

- **JVM**: `FileChannel.read()` and `FileChannel.write()` map to `pread()`/`pwrite()`; `FileChannel.force(true)` calls `fsync()`. The JVM's `ByteBuffer.allocateDirect()` is required for `O_DIRECT` because aligned off-heap memory is what the kernel can hand to the device without a bounce-buffer copy.
- **Node.js / libuv**: `fs.readFile()` and `fs.writeFile()` run on the libuv thread pool (4 threads by default) because the libuv event loop is single-threaded but the kernel can do I/O in parallel. `fs.promises.open()` with the `O_DIRECT` flag requires the buffer to be aligned; Node's `Buffer.allocUnsafe()` does not guarantee alignment.
- **CPython**: `open(..., 'rb').read()` and the `os` module expose `pread`, `pwrite`, `os.fsync`. The `mmap` module maps a file into the process address space and lets you treat it as a bytearray — the kernel handles the page faults that fetch pages from disk on demand.
- **PHP-FPM**: `fread()`/`fwrite()` go through PHP's stream layer. PHP's `opcache.file_cache` writes compiled PHP bytecode to disk using the same `write()`+`fsync()` pattern that every other persistent application uses.

When you read those runtime notes, come back here and trace which kernel primitive each runtime feature maps to.

## Hands-On Exercise

Open a terminal on a Linux machine and run the following commands to see these concepts in action:

```bash
# Inspect a block device's physical characteristics
lsblk -o NAME,ROTA,SIZE,TYPE,MOUNTPOINT
# ROTA=1 means rotational (HDD), ROTA=0 means SSD/NVMe

# See the kernel page cache for a file
vmtouch /var/lib/postgresql/15/main/base/16384/2619
# shows how many pages of the file are resident in RAM

# Drop the page cache (forces the next read to go to disk)
echo 3 | sudo tee /proc/sys/vm/drop_caches

# Trace every I/O syscall a program makes
strace -e trace=openat,read,pread64,write,pwrite64,fsync,fdatasync -f -p $(pgrep -n postgres) 2>&1 | head -50

# Watch device-level I/O statistics in real time
iostat -xmy 1

# Measure the fsync latency of your storage device
sudo hdparm -tT /dev/nvme0n1
# or, for a more accurate database-relevant test:
fio --name=fsync --filename=/tmp/fsynctest --rw=write --bs=4k --size=4k \
    --end_fsync=1 --direct=1 --fsync=1 --group_reporting --loops=1000
```
