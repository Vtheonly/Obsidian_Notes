# 06.01.02. Write-Ahead Logging (WAL) and Crash Recovery

## What This Is

Write-Ahead Logging is the single non-negotiable rule that makes a database crash-safe. Without it, a power loss in the middle of a transaction would corrupt the database — some pages would be flushed to disk, others would not, and there would be no record of which was which. With it, the database can be killed at any point — `kill -9`, kernel panic, power yank — and on restart every committed transaction is preserved and every uncommitted transaction is rolled back. Every transactional engine (PostgreSQL's WAL, InnoDB's redo log, MongoDB's journal, Oracle's redo log, SQLite's WAL) implements the same invariant, and the recovery algorithm they all run is a forty-year-old design called ARIES. This note covers the rule, the record format, the checkpoint mechanism, and the recovery algorithm — and connects them to the `fsync` cost that dominates OLTP throughput.

## The Details

### The fundamental persistence invariant: Write the log record to non-volatile disk before modifying in-memory database pages

The WAL rule is one sentence: **before a database page may be modified in memory, the log record describing the modification must be written and `fsync`'d to non-volatile storage.** This single ordering constraint is what makes crash recovery possible. If the database crashes after the WAL is durable but before the page is flushed, recovery replays the WAL. If it crashes after the page is flushed but the WAL is gone — impossible, because the WAL was written first. The rule converts "is this data safe across a crash?" into "is this WAL record on disk?", which is a single `fsync` call.

```text
  Normal commit sequence (single transaction):
  ────────────────────────────────────────────────────────────
  T1: BEGIN
  T1: UPDATE accounts SET balance = balance - 100 WHERE id = 1;
       │
       ├─ 1. Append WAL record: [LSN=42, xid=T1, undo=<old balance=500>,
       │                          redo=<new balance=400, page=42, offset=12>]
       ├─ 2. Modify in-memory page 42: balance now 400 in shared_buffers
       │    (page 42 is now "dirty" — differs from on-disk version)
       │
  T1: COMMIT
       │
       ├─ 3. Append WAL commit record: [LSN=43, xid=T1, COMMIT]
       ├─ 4. fsync(WAL file)  ← blocks ~50 µs on NVMe, ~10 ms on HDD
       │    AFTER this returns, "commit succeeded" is returned to the client
       │
  ... later, asynchronously, the background writer flushes page 42 to disk ...
       (this can happen seconds or minutes after the commit)
```

The commit is durable at step 4, not when the page is written. The page write can be deferred because the WAL contains enough information to reconstruct it. This is why a database with `fsync=off` (or `innodb_flush_log_at_trx_commit=0`) can lose committed transactions on crash — the WAL record is in the OS page cache but never forced to disk, so a power loss wipes it. The trade-off is steep: turning off `fsync` on commit can improve write throughput 10×, at the cost of being able to lose data. Most production databases accept the latency cost.

The WAL is also the source of truth for replication. PostgreSQL's streaming replication ships WAL records over a TCP socket to replicas, which apply them in LSN order. MongoDB's oplog is a capped collection of operations that secondaries tail. MySQL's binlog (separate from the InnoDB redo log) is used for both replication and point-in-time recovery. The WAL is therefore overloaded: it serves crash recovery, replication, and point-in-time backup, all from the same byte stream.

### WAL Record Structure: Log Sequence Numbers (LSN), Transaction IDs, Redo Info, Undo Info

Every WAL record carries a **Log Sequence Number (LSN)** — a monotonically increasing 64-bit byte offset into the WAL stream. PostgreSQL's LSN is displayed as `0/170D9D0` (a 32-bit high word and a 32-bit low word); InnoDB's LSN is a plain integer; MongoDB's oplog uses a BSON Timestamp with a 32-bit seconds field and a 32-bit counter. The LSN is what makes recovery deterministic: each data page stores the LSN of the most recent WAL record that modified it (`pd_lsn` in PostgreSQL, `FIL_PAGE_LSN` in InnoDB), and during recovery the engine compares the page LSN with each WAL record's LSN to decide whether to apply the record (page LSN < record LSN → apply) or skip it (page LSN ≥ record LSN → already applied).

A single WAL record contains four pieces of information:

```text
┌──────────────────────────────────────────────────────────────┐
│ Header: LSN, prev_lsn, xid (transaction id), rmgr (resource │
│ manager — heap, btree, sequence, etc.), info flags          │
├──────────────────────────────────────────────────────────────┤
│ Redo info: enough to re-apply the modification             │
│   e.g. "on page 42 at offset 12, write these 4 bytes: 0x190"│
│   (or the full new row image, depending on the engine)     │
├──────────────────────────────────────────────────────────────┤
│ Undo info: enough to reverse the modification              │
│   e.g. "on page 42 at offset 12, write these 4 bytes: 0x1F4"│
│   (InnoDB stores undo in a separate undo log; PostgreSQL    │
│    stores undo implicitly via the old row version)          │
├──────────────────────────────────────────────────────────────┤
│ Trailer: CRC32C checksum over the whole record              │
└──────────────────────────────────────────────────────────────┘
```

PostgreSQL's WAL records are physically logged (the redo info is "write these bytes to this page at this offset") and the undo is implicit (the old row version is left in place as a dead tuple, since PostgreSQL uses MVCC rather than in-place updates). InnoDB's redo log is also physical, but the undo log is a separate on-disk structure that records logical reverse operations ("increment this column by 100"). MongoDB's WiredTiger journal uses a similar physical-redo scheme. The choice between physical, logical, and physiological (a hybrid) logging affects what can be recovered: physical redo can replay any page modification; logical redo can only replay operations the engine understands.

The LSN also drives the WAL segment file. PostgreSQL writes WAL to 16 MB segment files in `pg_wal/` named `000000010000000000000001`, `000000010000000000000002`, etc. (the name encodes the timeline, the high 32 bits of LSN, and the low 32 bits of LSN). InnoDB's redo log is a fixed pair of `ib_logfile0` and `ib_logfile1` that wrap around. MongoDB's oplog is a capped collection of BSON documents in `local.oplog.rs`. The segment size matters: a larger segment amortises `fsync` overhead but loses more data on a single segment loss; PostgreSQL defaults to 16 MB but can be configured up to 1 GB.

### Checkpoint mechanisms: Non-blocking fuzzy checkpointing and dirty page flushing

Without checkpoints, recovery would require replaying the entire WAL from database creation — impossible for a database that has been running for years. A **checkpoint** is a moment in time where the engine guarantees that all data pages modified before the checkpoint LSN have been flushed to disk. Recovery then only needs to replay the WAL from the checkpoint LSN forward. PostgreSQL logs a checkpoint record at LSN `X` saying "all dirty pages older than `X` are now on disk"; on restart, recovery scans backward to find the last checkpoint record, then scans forward from there.

A naive checkpoint would block: stop accepting writes, flush every dirty page, write the checkpoint record, resume. This is unacceptable in production. Instead, engines use **fuzzy checkpointing**: the checkpoint starts at LSN `X`, dirty pages are flushed in the background while writes continue, and when the flush completes the checkpoint record is written with a small "redo-start" LSN that may be earlier than `X` to cover pages dirtied during the flush. The result is a checkpoint that never blocks writes but produces a slightly longer redo range during recovery.

```text
PostgreSQL checkpoint lifecycle:
─────────────────────────────────────────────────────────────
1. Checkpointer process decides to checkpoint (every checkpoint_timeout
   seconds, default 5 min, or when wal_buffers fills, default 64 MB).
2. Records the current LSN as the checkpoint's "redo-start" point.
3. Iterates shared_buffers, writes all dirty pages to disk via OS
   write() (NOT fsync — just writes to the page cache).
4. Calls fsync() on each data file. (Can be parallelised since PG12
   with checkpoint_flush_after and max_worker_processes.)
5. Appends a CHECKPOINT WAL record at the current LSN.
6. fsync()s the WAL. The checkpoint is now durable.
7. Old WAL segments before the redo-start LSN can be recycled.
```

The relevant tunables are `checkpoint_timeout` (default 5 min — how often a timed checkpoint runs), `max_wal_size` (default 1 GB — the soft limit before a checkpoint is forced), `checkpoint_completion_target` (default 0.9 — spread the flush over 90% of the timeout to avoid I/O spikes), and `checkpoint_flush_after` (how much data to write before forcing an OS flush). For InnoDB, the equivalent is `innodb_io_capacity` (how many IOPS the storage can sustain — controls flush rate) and `innodb_max_dirty_pages_pct` (default 90% — forces aggressive flushing when buffer pool is 90% dirty). MongoDB's WiredTiger checkpoints every 60 seconds by default (`--wiredTigerCheckpointIntervalSecs`).

### The ARIES Recovery Algorithm: Analysis Phase → Redo Phase (repeating history) → Undo Phase (rolling back uncommitted active transactions)

ARIES (Algorithm for Recovery and Isolation Exploiting Semantics) is the recovery algorithm designed by Mohan et al. at IBM in 1992. Every major transactional engine implements a variant. The algorithm has three phases that run sequentially on startup after a crash:

```text
ARIES crash recovery:
═══════════════════════════════════════════════════════════════════

PHASE 1 — ANALYSIS
──────────────────
  Scan WAL forward from the last checkpoint record.
  Build three tables:
    • Transaction table: every xid that appears in the WAL,
      its current status (active/committed/aborted), and
      its last LSN.
    • Dirty page table: every page that appears in the WAL,
      its recLSN (the LSN of the first record that dirtied it
      after the last checkpoint).
    • Identify the "end of WAL" — the LSN of the last valid
      record (a torn page or a half-written record after this
      point is truncated).
  This phase tells the engine what work was in flight.

PHASE 2 — REDO (repeating history)
───────────────────────────────────
  Scan WAL forward from the minimum recLSN across all dirty pages.
  For each record, IF the record's LSN > the page's on-disk LSN:
    apply the redo info to the page.
  ELSE:
    skip (the page is already up-to-date).
  This phase makes the on-disk state match what the WAL says,
  including uncommitted changes that will be undone next.

PHASE 3 — UNDO
──────────────
  Scan the transaction table for transactions that were active
  (not committed) at the time of the crash.
  For each, scan the WAL backward and apply the undo info.
  Stop when all uncommitted transactions are fully rolled back.
  Write a compensation log record (CLR) for each undo so that
  even undo itself is recoverable if the database crashes again
  during recovery.
```

The "repeating history" property of phase 2 is what makes ARIES robust: it redoes *every* modification, including ones that will be immediately undone, because the redo log is idempotent (applying the same record twice produces the same page state). The page LSN comparison is the idempotence check. This is why a recovery that crashes halfway through can simply restart from the beginning of phase 2 — already-applied records will be skipped by the LSN check.

```text
Concrete timeline of a recovery:
─────────────────────────────────────────────────────────────
WAL records (in order):
  LSN=100  BEGIN T1
  LSN=101  UPDATE page 42, balance 500→400   (redo + undo info)
  LSN=102  BEGIN T2
  LSN=103  UPDATE page 43, balance 100→50
  LSN=104  COMMIT T1
  LSN=105  UPDATE page 44, qty 10→8          (T2 still active)
  ← CRASH HERE, before T2 commits →

On restart:
  ANALYSIS: T1 committed. T2 was active. Dirty pages: 42, 43, 44.
  REDO:
    LSN=101: page 42 on-disk LSN=80 < 101 → apply → page 42 now
             has balance=400, on-disk LSN=101.
    LSN=103: page 43 on-disk LSN=95 < 103 → apply → balance=50.
    LSN=105: page 44 on-disk LSN=99 < 105 → apply → qty=8.
  UNDO:
    T2 was active. Roll back LSN=105: page 44 → qty=10 (the old
    value from the undo info). Write CLR at LSN=106.
    T2 has no other records. Mark T2 rolled back.
  Recovery complete. Database is now consistent: T1's commit is
  preserved, T2's partial work is gone.
```

The recovery time is bounded by the distance from the last checkpoint to the end of the WAL, times the IOPS available for the redo and undo I/O. A too-infrequent checkpoint makes recovery slow; a too-frequent checkpoint makes normal operation slow. The default `checkpoint_timeout=5min` and `max_wal_size=1GB` on PostgreSQL are tuned for a recovery under 60 seconds on typical hardware — long enough to amortise the checkpoint cost, short enough to keep recovery time acceptable for an automated failover.

The fsync cost on every commit is the price of this guarantee. PostgreSQL's default `synchronous_commit=on` calls `fsync(WAL)` on every commit; setting it to `off` lets the WAL stay in the OS page cache for a few hundred milliseconds, which can lose data on crash but improves throughput dramatically. `synchronous_commit=remote_write` waits for the replica to receive the WAL but not fsync it. These knobs are how the operator trades durability for latency — and they are exactly the knobs that turn a database from "ACID" to "almost ACID".

## Cross-Ecosystem Implementation

The WAL concept maps to specific files and configuration in every major engine:

| Engine | WAL name | File location | Default size | fsync default |
|---|---|---|---|---|
| PostgreSQL | WAL (a.k.a. xlog) | `pg_wal/` (16 MB segments) | 16 MB × N segments | `synchronous_commit=on` |
| MySQL InnoDB | Redo log | `ib_logfile0`, `ib_logfile1` | 48 MB each (MySQL 8 default 4 GB total) | `innodb_flush_log_at_trx_commit=1` |
| MongoDB (WiredTiger) | Journal | `WiredTigerLog.*` | 100 MB files | `journal:true` with `j:true` writes |
| MongoDB (replication) | Oplog | `local.oplog.rs` (capped collection) | 5% of free disk | n/a (replication is async) |
| SQLite | WAL | `*-wal` file | grows as needed | `PRAGMA wal_autocheckpoint=1000` |

The names differ; the invariant is identical: log first, page second, fsync between.

## Hands-On Exercise

```bash
# PostgreSQL: see the current WAL position
sudo -u postgres psql -c "SELECT pg_current_wal_lsn();"
# 0/170D9D0

# Force a checkpoint and watch it happen
sudo -u postgres psql -c "CHECKPOINT;"
sudo -u postgres tail -f /var/log/postgresql/postgresql-15.log
# LOG:  checkpoint complete: wrote 42 buffers (0.3%); 0 WAL file(s) ...

# See WAL segments currently in pg_wal/
ls -la /var/lib/postgresql/15/main/pg_wal/
# 000000010000000000000001  000000010000000000000002  archive_status/

# InnoDB: see redo log size
SHOW VARIABLES LIKE 'innodb_log_file_size';
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';
# 1 = fsync every commit (default). 2 = fsync every second. 0 = never.

# MongoDB: see the journal files
ls -la /var/lib/mongo/journal/
# WiredTigerLog.0000000017  WiredTigerPreplog.0000000018  WiredTigerWt.backup

# Crash test: simulate a hard crash and recovery
sudo -u postgres psql -c "CREATE TABLE t (x int); INSERT INTO t VALUES (1);"
sudo kill -9 $(pgrep -u postgres -f "postgres:.*checkpointer")
# Then restart PostgreSQL; watch the recovery log:
# LOG:  database system was not properly shut down; automatic recovery in progress
# LOG:  redo starts at 0/170D9D0
# LOG:  redo done at 0/170DA30 system usage: CPU 0.00s/0.00u sec elapsed 0.00 sec
# LOG:  database system is ready to accept connections
```
