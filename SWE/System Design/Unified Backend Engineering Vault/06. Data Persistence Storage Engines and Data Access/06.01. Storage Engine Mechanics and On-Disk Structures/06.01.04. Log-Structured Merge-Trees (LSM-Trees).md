# 06.01.04. Log-Structured Merge-Trees (LSM-Trees)

## What This Is

The B+tree (06.01.03) is the read-optimised index. The LSM-tree is its write-optimised counterpart, designed by O'Neil et al. in 1996 to convert every random write into a sequential append. The trade-off is fundamental: LSM-trees accept slower and more complex reads (you may have to check multiple files) in exchange for dramatically higher write throughput, because writes go to memory first and only hit disk as large sequential flushes. Cassandra, RocksDB, LevelDB, HBase, ScyllaDB, InfluxDB, and WiredTiger's LSM mode all use LSM-trees or close variants. This note covers the memtable/SSTable structure, the compaction strategies that bound read amplification, the Bloom-filter optimisation that makes reads tolerable, and the tombstone problem that makes deletes expensive. The mental model to carry forward: LSM-trees are the engine of choice when write throughput matters more than read latency, which is why they dominate time-series, event-log, and IoT workloads.

## The Details

### The write-optimization trade-off: Converting random writes into sequential disk appends

A B+tree's write cost is dominated by random I/O. Each insert must descend the tree to find the leaf, modify the leaf page, and write the leaf back — a random 16 KB write at the leaf's physical location. Under heavy write load, the device's random-write IOPS ceiling (a few thousand on SATA SSDs, a few hundred thousand on NVMe) is hit long before the device's sequential-write bandwidth (several GB/sec). The B+tree is read-optimised but write-bound.

The LSM-tree solves this by changing the write pattern. Every write — insert, update, delete — goes to an in-memory structure called the **memtable** (a skip-list or red-black tree, kept sorted by key). The memtable is just RAM: writes are fast because they never touch disk. When the memtable fills up (typically a few MB), it is flushed to disk as an immutable **SSTable** (Sorted String Table) — a single large sequential write. The result is that every disk write is sequential, and the device's sequential bandwidth, not its random IOPS, becomes the throughput limit. A single NVMe drive can sustain 2 GB/sec of sequential writes — equivalent to ~500,000 4 KB row inserts per second.

```text
LSM write path:
─────────────────────────────────────────────────────────────

Client ──WRITE k=42,v='hi'──►  WAL (append-only, sequential)
                                  │
                                  ▼
                              Memtable (in-memory, sorted)
                              { k=1, k=42, k=99, ... }
                                  │
                                  │ (when memtable is full)
                                  ▼
                              Flush: one big sequential write
                                  │
                                  ▼
                          SSTable L0-001 (immutable, on disk)
                          [k=1, k=42, k=99, ...]

Cost per write: 1 WAL append (sequential) + 1 memtable insert (RAM).
Disk I/O is amortised: only every N writes does a flush happen.
Disk I/O is sequential: the flush writes one file from start to end.
```

The catch is on the read side. A point lookup for key `42` must check: (a) the memtable, (b) every immutable memtable waiting to flush, (c) every SSTable at L0 (where SSTables may overlap in key range), (d) the relevant SSTable at each subsequent level (where key ranges are disjoint). Without help, this is N random reads per lookup — far worse than a B+tree's 3-level descent. The LSM-tree mitigates this with **Bloom filters** (skip SSTables that definitely don't contain the key), **compaction** (merge SSTables so reads don't have to check many of them), and **caching** (hot SSTables live in the OS page cache). The trade is asymmetric: writes are dramatically faster, reads are somewhat slower and have higher tail latency.

### Core components: MemTable (in-memory skiplist/red-black tree), Commit Log (durability), Immutable MemTables, SSTables (Sorted String Tables)

The four components of an LSM-tree form a pipeline: a write enters the commit log and memtable, the memtable becomes immutable when full, the immutable memtable is flushed to an SSTable, and SSTables are merged into larger SSTables by compaction. Each component has a specific role and a specific failure mode.

```text
LSM component pipeline:
═══════════════════════════════════════════════════════════════════

1. COMMIT LOG (a.k.a. WAL, journal, write-ahead log)
   - Append-only sequential file
   - Written BEFORE the memtable insert (so a crash can replay)
   - fsync policy: every write (Cassandra), every commit (RocksDB),
     or batched (configurable)
   - Truncated when the corresponding memtable is flushed
   - Failure mode: if fsync is off, a crash loses recent writes

2. MEMTABLE (active, in-memory, mutable)
   - Sorted structure: skiplist (Cassandra, RocksDB) or red-black tree
   - Held in process RAM (not the page cache)
   - Writes go here AFTER the commit log
   - Reads check here FIRST
   - Failure mode: OOM if memtable size is set too high;
     write stall if memtable is full and cannot be flushed

3. IMMUTABLE MEMTABLES (queued for flush)
   - When the active memtable reaches its size limit, it is sealed
     and becomes immutable, and a new active memtable starts
   - A background thread flushes each immutable memtable to disk
   - Failure mode: if flush cannot keep up with writes, the queue
     grows and the engine must apply backpressure (block new writes)

4. SSTABLES (on-disk, immutable, sorted files)
   - Each SSTable contains a sorted run of key-value pairs
   - Plus a sparse index (every Nth key) at the end for binary search
   - Plus a Bloom filter for fast negative lookups
   - Plus a min-key and max-key for the file's range
   - Organised into levels: L0 (overlapping, recently flushed),
     L1, L2, ... (non-overlapping, larger at each level)
   - Failure mode: too many L0 files slow reads; compaction must
     keep up
```

Each SSTable on disk looks like:

```text
┌────────────────────────────────────────────────┐
│ Data block 0  (sorted KV pairs, compressed)    │
│ Data block 1                                  │
│ Data block 2                                  │
│ ...                                           │
│ Data block N                                  │
├────────────────────────────────────────────────┤
│ Index block (sparse: every 4 KB block's first  │
│               key + offset)                    │
├────────────────────────────────────────────────┤
│ Bloom filter block (bit array for membership)  │
├────────────────────────────────────────────────┤
│ Metadata block (min key, max key, count)       │
├────────────────────────────────────────────────┤
│ Footer (offsets of all blocks, magic number)   │
└────────────────────────────────────────────────┘
```

A read for key `K` opens the SSTable, reads the footer (cached), binary-searches the index block to find the candidate data block, reads the Bloom filter (cached) to skip if `K` is not present, and finally reads the data block (potentially a disk I/O). The index and Bloom filter are small enough to be kept permanently in memory — for a 100 MB SSTable, the index is about 100 KB and the Bloom filter about 1 MB.

The memtable choice matters too. A skiplist (used by Cassandra and RocksDB) gives O(log N) inserts and lookups with a small constant, supports range scans (which a hash table does not), and is concurrency-friendly (readers don't block writers). A red-black tree is similar but with slightly worse cache behaviour. A hash table would be O(1) but would not support ordered iteration, which LSM-trees need for compaction merges.

### Compaction Strategies: Size-Tiered Compaction vs. Leveled Compaction

Without compaction, an LSM-tree accumulates unbounded SSTables — every flush adds one, and after a million writes you have a million files, every read checks every file, and the engine grinds to a halt. **Compaction** is the background process that merges multiple SSTables into fewer, larger ones, discarding overwritten and deleted entries in the process. The choice of compaction strategy is the second-most-important LSM tuning decision (after memtable size) because it determines the read/write/space trade-off.

**Size-tiered compaction** (STCS, Cassandra's original default) keeps roughly N SSTables of similar size at each tier. When the tier has N SSTables of size S, they are merged into one SSTable of size N×S at the next tier. The tiers form a geometric progression: 4 files of 50 MB → 1 file of 200 MB → 4 files of 200 MB → 1 file of 800 MB → ...

```text
Size-tiered compaction (Cassandra default):
─────────────────────────────────────────────────────────────
Tier 0:  50 MB  50 MB  50 MB  50 MB   (4 SSTables, recently flushed)
                          │
                          ▼ merge
Tier 1:  200 MB                      (1 SSTable)
Tier 1:  200 MB  200 MB  200 MB  200 MB  (after 4 more flushes)
                          │
                          ▼ merge
Tier 2:  800 MB
...

Pros: Low write amplification (each key is rewritten ~N times
      total, where N is the number of tiers).
Cons: High space amplification (during a merge, the old SSTables
      are kept until the new one is verified, so disk usage
      spikes to 2× the steady state).
Cons: Read amplification grows with the number of tiers (a key
      may be in any tier's SSTables).
```

**Leveled compaction** (LCS, RocksDB's default, Cassandra's option) keeps each level's SSTables non-overlapping in key range, with each level being ~10× the size of the level above. L0 has overlapping files (just-flushed memtables); L1 has files of size ~10 MB each, totalling 100 MB; L2 has files of size ~10 MB each, totalling 1 GB; L3 totals 10 GB; and so on. When L1's total size exceeds its budget, one L1 file is selected and merged with the L2 files it overlaps, producing new L2 files.

```text
Leveled compaction (RocksDB default):
─────────────────────────────────────────────────────────────
L0:  [10-50] [20-60] [30-70] [40-80]    (overlapping, just flushed)
L1:  [00-10][10-20][20-30]...[90-100]   (disjoint, total 100 MB)
L2:  [00-10][10-20]...                  (disjoint, total 1 GB)
L3:  [00-10][10-20]...                  (disjoint, total 10 GB)
...

Pros: Low read amplification (a point lookup checks at most one
      SSTable per level, plus L0 files).
Pros: Low space amplification (~10% overhead, since merges
      replace files in place).
Cons: High write amplification (a key may be rewritten 10× per
      level, so total WA is ~10× the number of levels — for
      L6, that's 60× write amplification).
```

The trade is brutal and unavoidable: size-tiered minimises write amplification but maximises read amplification and space amplification; levelled minimises read and space amplification but maximises write amplification. Production deployments spend a lot of tuning effort finding the right balance — Cassandra's `TimeWindowCompactionStrategy` (TWCS) for time-series data, RocksDB's `OptimizeLevelStyleCompaction` with configurable level multipliers, ScyllaDB's `incremental compaction`. The universal observation: write-heavy workloads (time-series, event logs) prefer size-tiered; read-heavy workloads prefer levelled.

### Read performance challenges: Multi-file lookups, Bloom Filters (probabilistic set membership testing), and read amplification

A point lookup in an LSM-tree without help would check every SSTable — a 10-file L0 plus one file per level could be 15 random reads for a single lookup. Two optimisations bring this down to typically 1 read in the hot case.

**Bloom filters** are the first line of defence. A Bloom filter is a bit array of size `m` bits with `k` hash functions. To insert a key, compute all `k` hashes, set those `k` bits in the array. To test membership, compute the `k` hashes and check the bits — if any bit is 0, the key is definitely not in the set; if all bits are 1, the key *might* be in the set (with a false-positive rate that depends on `m`, `k`, and the number of keys). For 10 bits per key and 7 hash functions, the false-positive rate is ~1%. Before opening an SSTable to look for key `K`, the LSM checks the Bloom filter; 99% of the time it can skip the SSTable entirely. The Bloom filter is small (~1 MB per 100 MB SSTable) and kept permanently in memory.

**Block caching** is the second line. The index block and Bloom filter block of every SSTable are kept in RAM (these are small); the data blocks of recently-accessed SSTables are kept in an LRU cache (the `block_cache`, typically a few GB). A read that hits the cache does zero disk I/O. A read that misses does one disk I/O (the data block) plus the in-memory Bloom filter check. So the typical point lookup is 1 disk I/O, comparable to a B+tree.

```text
LSM point lookup cost (with Bloom + cache):
─────────────────────────────────────────────────────────────

read(K):
  1. Check memtable.                  ← RAM, ~1 µs
  2. Check immutable memtables.       ← RAM, ~1 µs each
  3. For each L0 SSTable (overlap):
     a. Check Bloom filter (cached). ← RAM, ~1 µs
     b. If positive, binary-search
        index (cached), read block. ← possible disk I/O
  4. For each level L1+:
     a. Find the one SSTable whose
        range covers K.              ← RAM (metadata cached)
     b. Check Bloom filter (cached). ← RAM, ~1 µs
     c. If positive, read block.     ← possible disk I/O

Typical case (Bloom filters mostly return negative):
  1 memtable check + a few cached Bloom checks = ~10 µs, 0 disk I/O.
Worst case (Bloom false positives on every SSTable):
  N data-block reads = N random I/Os.
```

**Tombstones** are the dark side of LSM deletes. A delete is not a delete — it is an insert of a special "tombstone" record. The tombstone shadows the original key, so reads return "not found" if they see the tombstone. But the original key-value pair is still in the older SSTable, taking up space, until compaction physically merges the tombstone with the original and discards both. Until then, every read for that key pays the cost of reading the original (then seeing the tombstone and discarding the result). On a workload that deletes a lot of keys (e.g. a TTL-based time-series), tombstones can dominate read latency. The mitigation is to run compaction more aggressively on tombstone-heavy tables — Cassandra's `tombstone_compaction_interval` and RocksDB's `CompactionOptionsFIFO` are the relevant knobs.

The production failure mode here is **read latency spikes** on an LSM store under write pressure. When compaction cannot keep up with writes (because the device is saturated, or the compaction strategy is wrong for the workload), the L0 file count grows, and every read must check more files. The fix is to apply backpressure (block writes when L0 reaches a threshold — RocksDB's `level0_slowdown_writes_trigger` and `level0_stop_writes_trigger`) and to tune the compaction strategy for the workload. The deeper lesson is that LSM-trees trade read latency for write throughput — you cannot optimise both simultaneously, and pretending otherwise leads to the Cassandra集群 that was fast until the compaction storm hit and reads went from 1 ms to 100 ms overnight.

## Cross-Ecosystem Implementation

| Engine | Compaction default | Memtable default | Bloom filter | Use case |
|---|---|---|---|---|
| RocksDB | Leveled (LCS) | 64 MB | yes (10 bits/key) | High-throughput KV, embedded |
| Cassandra | Size-tiered (STCS), TWCS for time-series | configurable per table | yes (per SSTable) | Wide-column, write-heavy |
| HBase | Size-tiered | configurable | yes | Hadoop ecosystem |
| LevelDB | Leveled | 4 MB | yes | Embedded (Chrome's IndexedDB) |
| WiredTiger (MongoDB LSM mode) | Leveled | configurable | yes | Optional MongoDB mode |
| InfluxDB TSM | Time-based, similar to TWCS | configurable | yes | Time-series |

## Hands-On Exercise

```bash
# RocksDB: inspect LSM state via the ldb tool
ldb --db=/path/to/rocksdb dump_manifest --verbose
# shows every SSTable, its level, its key range, its size

# Cassandra: see SSTable counts per table
nodetool cfstats your_keyspace.your_table
# Space used (live): 12.5 GB
# SSTable count: 47
# Memtable cell count: 1.2M
# Bloom filter false positives: 0.3%

# Trigger a compaction manually
nodetool compact your_keyspace your_table

# See compaction in progress
nodetool compactionstats
# pending tasks: 3
# Compaction Type   Keyspace.Table   Bytes
# Standard          ks.users          2.5 GB

# Measure write amplification: write 1 GB of data, watch disk writes
iostat -xmy 1   # observe w/s and wkB/s during the write
# If you write 1 GB and the device shows 5 GB of writes, WA = 5×.
```
