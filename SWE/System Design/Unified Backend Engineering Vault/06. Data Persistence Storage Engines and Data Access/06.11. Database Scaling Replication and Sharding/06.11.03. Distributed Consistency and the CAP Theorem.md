# 06.11.03. Distributed Consistency and the CAP Theorem

## What This Is

The CAP theorem is the most-cited and most-misunderstood result in distributed systems. In its modern form (Gilbert & Lynch 2002), it says: in a distributed system that can suffer network partitions, you cannot simultaneously guarantee linearizable consistency and total availability. Because network partitions are an unavoidable fact of real networks (a switch fails, a cable gets unplugged, a router misbehaves), the realistic choice is not "which of C/A/P do I want" but "when a partition happens, do I refuse requests (CP) or serve possibly-stale responses (AP)?". The PACELC theorem extends this: even when there is no partition, you must still choose between latency and consistency — there is no free lunch in replication. This note covers the CAP theorem precisely, the PACELC extension, and the spectrum of consistency models (linearizable, sequential, causal, eventual, read-your-writes) that real systems expose as configurable knobs.

In the layered mental model, CAP sits one layer above replication (see [[06.11.01. Primary-Replica Replication Mechanics]]) — the replication mechanism *implements* the consistency model, and CAP tells you which models are achievable under partition. Below CAP sit the consensus protocols (Paxos, Raft) covered in [[08.01.03. Consensus Algorithms — Paxos and Raft]] — these are the algorithms that achieve CP (linearizable) in practice. Above CAP sits the application layer, where Spring's `@Transactional` isolation level and Cassandra's `consistency: LOCAL_QUORUM` are both projections of the same consistency-vs-latency trade-off. Every framework in section 05 that uses a distributed store (Redis Cluster, MongoDB replica set, Cassandra, DynamoDB, CosmosDB) is making a CAP choice on the developer's behalf; this note gives you the vocabulary to recognise and reason about that choice.

## The Details

### The CAP Theorem: Consistency (Linearizable), Availability, Partition Tolerance

The CAP theorem names three properties of a distributed system. **Consistency** in CAP means *linearizability* — a strict, real-time ordering of operations where every read returns the value written by the most recent write, and where "most recent" is defined in real wall-clock time across all nodes. This is a stronger property than the "C" in ACID transactions (which is about constraint-preservation within a transaction) and stronger than "serializable" isolation (which allows the serial order to differ from real-time order). Linearizability is what most people *think* they are getting from a database, and what almost no distributed database actually provides by default. **Availability** means every non-failing node eventually responds to a request — not necessarily with the latest data, but with *some* valid response. **Partition tolerance** means the system continues to operate despite network partitions — arbitrary message loss or delay between any subset of nodes.

The theorem says you can have at most two of these three. The crucial insight that is often missed: **partition tolerance is not a choice — it is a fact of the network**. Real networks partition, period. So the real choice is between C and A *under partition*: do you refuse requests that cannot reach a quorum (CP — you keep linearizability, you sacrifice availability for the partitioned minority), or do you serve requests from any partition (AP — you keep availability, you sacrifice linearizability because the partitioned minority may be serving stale data)? The misleading formulation "pick two of three" suggests you can choose "CA" — but a CA system is just a single-node database with no network, which is not a distributed system at all.

```text
  CAP under partition — the actual choice:

  Network partition splits 5 nodes into [A,B,C] and [D,E]:

  CP (e.g., HBase, MongoDB with majority write concern):
    A,B,C form a quorum (3/5) → continue serving reads/writes
    D,E are a minority (2/5) → REFUSE all requests
       (or serve reads but reject writes — depends on implementation)
    Client connected to D,E sees: "QuorumNotReachable" error
    Linearizability preserved: any acknowledged write is on the majority

  AP (e.g., Cassandra, DynamoDB):
    A,B,C continue serving reads/writes
    D,E ALSO continue serving reads/writes (with whatever data they have)
    When the partition heals, D,E's writes are merged via conflict resolution
       (last-write-wins, vector clocks, CRDTs, application merge)
    Client connected to D,E sees: stale reads (D,E may not have A,B,C's writes)
    Linearizability violated: a write on A and a write on D can both be acknowledged
       but cannot be linearly ordered
```

The **CP systems** refuse requests under partition to preserve linearizability. HBase (via ZooKeeper quorum), MongoDB with `writeConcern: { w: "majority" }`, PostgreSQL with synchronous replication, and etcd/Consul/ZooKeeper (Paxos/Raft underneath) are all CP. When the partition isolates a minority, that minority refuses writes — the client sees an error, not stale data. The trade-off: writes can fail even when the data is intact, because the quorum is unreachable. The **AP systems** serve requests from any partition, accepting divergence and resolving it on heal. Cassandra, DynamoDB, Riak, CouchDB, and Redis Cluster (in its default mode) are AP. The trade-off: reads can return stale data, and conflicting writes can lose data (last-write-wins is the default in Cassandra and DynamoDB — set your clock skew budget carefully).

The **configurable systems** let the developer choose per-operation. Cassandra's `consistency: ONE` is AP (any one replica responds); `consistency: QUORUM` is closer to CP (majority responds, linearizable reads with `SERIAL` consistency); `consistency: ALL` is fully CP (all replicas respond — but loses availability if any one is down). DynamoDB's `-consistent-read` flag is the same knob: default is AP (eventually consistent reads), set the flag for CP (strongly consistent reads from the leader). MongoDB's per-operation `writeConcern` and `readConcern` are the same pattern. The lesson: **CAP is not a property of the database, it is a property of the operation**. A Cassandra cluster with `consistency: ONE` writes and `consistency: QUORUM` reads is AP for writes and closer to CP for reads — the same cluster, same data, different trade-off per query.

The production failure mode of CP is **false availability loss**: the network has a transient blip, the quorum drops to 2/3 for 500 ms, the CP system rejects every write for that 500 ms, and the application's error rate spikes. The mitigation is a retry-with-jitter at the client (`spring-retry` in Spring, `tenacity` in Node, `backoff` in Python) so transient quorum loss is invisible to the user. The production failure mode of AP is **silent data loss**: the network partitions, both sides accept writes to the same key, on heal the last-write-wins resolution discards one side's writes. The mitigation is never to use last-write-wins for conflictable data — use CRDTs (counters, sets, OR-trellis), application-level merge functions, or just refuse to write during partition (which makes you CP for that operation). The deeper mitigation is to recognise that **AP is appropriate when the data is replaceable** (cache, telemetry, session state) and **CP is appropriate when the data is irreplaceable** (financial transactions, identity, configuration).

### The PACELC Theorem: If Partition (P) → choose Availability (A) or Consistency (C); Else (E) → choose Latency (L) or Consistency (C)

PACELC (pronounced "pack-elk") was formulated by Abadi in 2010 to address the question CAP leaves unanswered: what does the system do *when there is no partition*? CAP only constrains the partitioned case; the no-partition case is where most systems spend 99.9% of their time, and the trade-off there is between **latency** (how fast the system responds) and **consistency** (how strong the ordering guarantee is). PACELC says: if there is a partition (P), choose A or C; else (E), choose L or C. The full taxonomy is PA/EL, PA/EC, PC/EL, PC/EC.

**PA/EL** systems prioritise availability under partition and latency when no partition — they are the "fast and loose" systems. Cassandra, DynamoDB, and Riak default to PA/EL: under partition they accept writes on any side (PA), and when there is no partition they respond as soon as the first replica acknowledges (EL — `consistency: ONE`). This gives sub-millisecond writes but eventual consistency — the data may not be on a majority for several hundred milliseconds. **PC/EC** systems prioritise consistency in both cases — they are the "strict" systems. BigTable, HBase, MongoDB with majority, and Spanner are PC/EC: under partition they refuse writes that cannot reach a quorum (PC), and when there is no partition they wait for the quorum to ack (EC — adds quorum round-trip latency to every write). Spanner is the unusual case: it is PC/EC but achieves single-digit-millisecond writes by using atomic clocks (TrueTime) to make the consistency cheap.

```text
  PACELC quadrant (Abadi 2010):

                                  Under Partition (P)
                            ┌────────────────────────┬────────────────────────┐
                            │  Choose A (Available)  │  Choose C (Consistent) │
                  No PA     │                        │                        │
                  Partit-   │  Cassandra (default)   │  Spanner               │
   Else (E)       ion (no   │  DynamoDB (default)    │  MongoDB (majority)    │
                 partition) │  Riak                  │  HBase                 │
                            │  Redis Cluster         │  etcd / Consul / ZK    │
                            │                        │                        │
                            ├────────────────────────┼────────────────────────┤
                            │  Choose L (Low Latency)│  Choose C (Consistency)│
                            │                        │                        │
                            │  Cassandra (default)   │  Spanner               │
                            │  DynamoDB (default)    │  MongoDB (majority)    │
                            │  Riak                  │  HBase                 │
                            │  Redis Cluster         │  etcd / Consul / ZK    │
                            │                        │                        │
                            └────────────────────────┴────────────────────────┘
                                  PA/EL (fast, loose)     PC/EC (slow, strict)

  Configurable systems (per-operation):
    Cassandra: PA/EL by default, but QUORUM/ALL = PC/EC for that op
    DynamoDB:  PA/EL by default, but consistent_read=true = PC/EC for that op
    MongoDB:   PA/EL with w:1, PC/EC with w:majority
    Redis:     PA (cluster) with WAIT 0, PC with WAIT N
```

The **PA/EL → PC/EC trade-off per operation** is the actionable insight. A social-media "like" counter can be PA/EL — eventual consistency is fine, last-write-wins on a counter is acceptable (Cassandra counter type, DynamoDB atomic counter). A bank balance must be PC/EC — strong consistency is non-negotiable, latency be damned. The same application can use Cassandra for the like counter (`consistency: ONE`) and PostgreSQL for the balance (`synchronous_commit = on`) — the database choice is the consistency choice. The misconfiguration that causes production incidents is **using a PA/EL system for PC/EC data** — putting a bank balance in Cassandra with `consistency: ONE` and discovering, after a network blip, that two withdrawals both succeeded against a stale balance. The deeper lesson is that **consistency is not a global property** — it is per-data-item, per-operation. A well-designed system uses the weakest consistency that the data can tolerate, because weaker consistency is faster and more available.

The production failure mode unique to PC/EC is **tail latency amplification under quorum stress**: a PC/EC write waits for the slowest of N/2+1 replicas, so the 99th-percentile write latency is set by the slowest replica's 99th-percentile fsync, which is much worse than the average. The mitigation is **hedged requests** (send to N+1 replicas, take the first N/2+1 acks) and **tail-latency-tolerant quorum** (Cassandra's `speculative_retry = '99PERCENTILE'` triggers a retry to a second replica after the p99 latency). The failure mode unique to PA/EL is the **long-unresolved conflict**: two partitions accept writes to the same key, the partition heals, and the conflict-resolution function cannot decide (e.g., two different updates to a JSON document). The standard fixes are CRDTs (which always converge) and application-level merge (which the developer must write). Both are expensive; the cheapest fix is to design the schema so conflicts are impossible — e.g., append-only events instead of mutable state, and compute state by replaying events.

### Consistency Models: Strong / Linearizable Consistency, Sequential Consistency, Causal Consistency, Eventual Consistency, Read-Your-Own-Writes Consistency

CAP and PACELC frame the trade-off at the system level; consistency models are the *knobs* the developer actually turns per operation. The hierarchy, from strongest to weakest, is:

- **Linearizability** (strong consistency): every operation appears to occur atomically at a single point in real time between its invocation and response. Reads return the value of the most recent write in real-time order. This is the strongest single-object consistency model — it is what a single-threaded program sees. Achieved by Raft/Paxos consensus (etcd, Spanner) or by single-leader replication with sync commit (PostgreSQL with `synchronous_commit = on`). Cost: every write requires a quorum round-trip (1–5 ms typical).
- **Sequential consistency**: every operation appears to occur in some total order that respects each client's program order, but the order may differ from real time. Client A writes `x=1`, then `x=2`. Client B may read `x=2` and then `x=1` — sequentially consistent because each client's view is a valid permutation, but not linearizable because the order differs from real time. Cost: cheaper than linearizability but rarely exposed by real databases.
- **Causal consistency**: operations that are causally related (a write followed by a read of that write followed by another write based on the read) appear in causal order; concurrent operations can appear in any order. Achieved by vector clocks (Riak, Dynamo) or version vectors. Cost: requires tracking causal dependencies (one timestamp per client), so memory grows with client count.
- **Read-your-own-writes** (session consistency): a client's reads always reflect their own prior writes, but other clients' writes may be stale. The classic web pattern — after a user posts a comment, they immediately see it (their own write), but other users may not see it for a few seconds. Achieved by sticky-session routing or by client-side LSN tracking (see [[06.11.01. Primary-Replica Replication Mechanics]]). Cost: minimal — just one extra routing decision per request.
- **Eventual consistency**: if no new writes occur, eventually all replicas converge. No ordering guarantees, no freshness guarantees — just eventual convergence. Achieved by async replication with last-write-wins (Cassandra default, DynamoDB default). Cost: zero — fastest and most available, weakest guarantee.

```text
  Consistency hierarchy (strongest to weakest):

  Linearizable  ⊃  Sequential  ⊃  Causal  ⊃  Read-your-writes  ⊃  Eventual

  Example: client A writes x=1, then x=2; client B reads x:

  Linearizable:   B sees 1 then 2 (real-time order)        or 2 (if read after A's write of 2)
  Sequential:     B may see 2 then 1 (any order respecting A's program order is invalid!)
                  actually: B may see 1 then 2, or just 2 (but not 2 then 1 because that
                  would violate A's write-then-write order)
  Causal:         B may see 1 then 2, or 2 then 1 (no causal relation between B's reads)
  RYW:            A always sees 1 then 2; B may see anything
  Eventual:       B may see 1, 2, or empty — eventually all B reads see 2

  ┌─────────────────────┬───────────────────────────────┬───────────────────────────────┐
  │ Model               │ Mechanism                     │ Real systems                  │
  ├─────────────────────┼───────────────────────────────┼───────────────────────────────┤
  │ Linearizable        │ Raft/Paxos; sync replication  │ etcd, Spanner, PG sync, Mongo │
  │                     │                               │ majority, CockroachDB         │
  │ Sequential          │ Single-leader with FIFO order │ (rarely exposed)              │
  │ Causal              │ Vector clocks, version vectors│ Riak, CouchDB, geo-replicated │
  │                     │                               │ DynamoDB streams              │
  │ Read-your-writes    │ Sticky session, LSN tracking  │ Every web app with cache+DB   │
  │ Eventual            │ Async replication, LWW        │ Cassandra default, DynamoDB   │
  │                     │                               │ default, Redis Cluster        │
  └─────────────────────┴───────────────────────────────┴───────────────────────────────┘
```

The **read-your-writes** consistency model is the most practically important for web applications. The pattern is: the application maintains a per-session "read timestamp" (or LSN, or vector clock) and refuses to serve a read from a replica whose `last_applied_lsn < session_read_lsn`. In practice this is implemented by routing the user's reads to the primary for the first 1–5 seconds after their last write (the simplest approach), or by passing the LSN in a request header and having the replica block until it has replayed past that LSN (the rigorous approach). Spring's `@Transactional(readOnly=true)` plus a session-scoped "last write LSN" achieves this; Django's database router can do the same via `request.session`; Laravel's `Cache::lock` plus a session LSN check is the same pattern. The cost is one extra primary read (or one replica block) per user write — a few milliseconds, well worth the UX win of "I posted, I see it."

The production failure mode of consistency models is the **silent downgrade**: a developer writes `INSERT INTO orders` against PostgreSQL with default `synchronous_commit = on` (linearizable), then the ops team "optimises" by setting `synchronous_commit = off` to improve write throughput — and the application now has eventual consistency for financial data. The fix is to assert the consistency model in code: PostgreSQL's `SET LOCAL synchronous_commit = on` inside the transaction; MongoDB's `writeConcern: { w: "majority", j: true }` per operation; Cassandra's `consistency: ALL` for the critical write. Never let the consistency model be a global default that ops can change — make it explicit per operation, in code, so the trade-off is visible in the PR review. The deeper lesson is that **consistency is a feature, not a configuration** — the application's correctness depends on a specific consistency guarantee, and weakening that guarantee is a behavioural change that requires the same review as any other code change.

## Cross-Ecosystem Implementation

Every framework exposes the consistency model through a different API surface, but the underlying knob is always the same: a per-operation flag that chooses between strong and eventual consistency.

| Operation | Spring | Express (ioredis/mongodb) | Django | Laravel |
|---|---|---|---|---|
| Strong write (linearizable) | `@Transactional` + `synchronous_commit = on` (PG) | `collection.insertOne(doc, { w: "majority", j: true })` (Mongo) | `transaction.atomic()` + `SET LOCAL synchronous_commit = on` | `DB::transaction(...)` + `DB::statement("SET LOCAL synchronous_commit = on")` |
| Strong read (linearizable) | route to primary | `collection.findOne({ readConcern: "majority" })` | `Model.objects.using('default')` (primary) | `DB::connection('pgsql::write')` |
| Eventual write (AP) | async replica fan-out (custom) | `collection.insertOne(doc, { w: 1 })` | `transaction.on_commit(lambda: ...)` (async) | `dispatch(new Job)->afterResponse()` |
| Eventual read (AP) | `@Transactional(readOnly=true)` (replica) | `collection.findOne({ readPreference: "nearest" })` | `Model.objects.using('replica1')` | `DB::connection('pgsql::read')` |
| Read-your-writes | session LSN + routing | session LSN + readPreference | session LSN + router | session LSN + connection |

The pattern is universal: every distributed store exposes a per-operation "how strong" knob, and every framework wraps it in a slightly different annotation or call. The cross-ecosystem difference is in the *default* — Spring and Django default to strong (single-DB assumption), Express and Laravel default to whatever the underlying client default is (often eventual for Mongo/Cassandra, strong for Postgres). Always check the default; never assume.

## Hands-On Exercise

```bash
# Demonstrate CAP trade-offs with Cassandra (AP) vs MongoDB (CP) side by side

# Cassandra: default is PA/EL — eventual consistency
docker run -d --name cass -p 9042:9042 cassandra:4.1
cqlsh localhost
CREATE KEYSPACE demo WITH replication = {'class': 'SimpleStrategy', 'replication_factor': 3};
USE demo;
CREATE TABLE counters (id text PRIMARY KEY, count counter);
UPDATE counters SET count = count + 1 WHERE id = 'x';

# Observe consistency levels per query
CONSISTENCY;                          # default: ONE (PA/EL)
CONSISTENCY QUORUM;                   # PC/EC for next query
CONSISTENCY ALL;                      # strongest, slowest, least available
CONSISTENCY ONE;
UPDATE counters SET count = count + 1 WHERE id = 'x';   # acks after 1 replica

# Simulate partition: stop one Cassandra node, observe behavior
docker stop cass-node3
# writes still succeed with CL=ONE (PA)
# writes fail with CL=ALL (would be PC if we had set it)
# writes succeed with CL=QUORUM (2/3 is still quorum)

# MongoDB: default is PA/EL with w:1, switchable to CP/EC with w:majority
docker run -d --name mongo -p 27017:27017 mongo:7
mongosh
use demo
db.orders.insertOne({ user: 42, amount: 100 })                    # w:1 default (PA)
db.orders.insertOne({ user: 42, amount: 100 }, { writeConcern: { w: "majority", j: true } })  # PC/EC
db.orders.findOne({}, { readConcern: { level: "majority" } })      # linearizable read

# Compare latencies
db.runCommand({
  profile: 1, slowms: 0
})
db.orders.insertMany([...Array(1000).keys()].map(i => ({ user: i })))   # w:1, fast
db.orders.insertMany([...Array(1000).keys()].map(i => ({ user: i })),
   { writeConcern: { w: "majority", j: true } })                         # w:majority, slow

# Read-your-writes: simulate with sticky session
# (in app code: after write, route reads to primary for 5s)
SESSION_LSN=$(psql -h primary -tAc "SELECT pg_current_wal_lsn()")
# replica blocks until it has replayed past SESSION_LSN:
psql -h replica -c "SELECT pg_wal_replay_lsn();" # poll until >= SESSION_LSN

# Demonstrate the consistency hierarchy with etcd (linearizable) vs Redis Cluster (eventual)
etcdctl put k v                       # Raft consensus — linearizable
etcdctl get k                         # linearizable read

redis-cli -c SET k v                  # async replication — eventual
# kill a replica, write to primary, observe the other replicas don't see it for ~ms
redis-cli -c WAIT 2 1000              # explicitly wait for 2 replicas (move toward CP)
```
