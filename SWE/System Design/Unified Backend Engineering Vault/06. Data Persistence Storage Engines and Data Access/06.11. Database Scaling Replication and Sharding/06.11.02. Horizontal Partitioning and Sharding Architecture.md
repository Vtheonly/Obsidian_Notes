# 06.11.02. Horizontal Partitioning and Sharding Architecture

## What This Is

Sharding is the technique of splitting a single logical dataset across multiple physical database instances, each owning a disjoint subset of the data. It is the last-resort scaling technique for write throughput — when you have exhausted vertical scaling (bigger box), read replicas (which only scale reads, not writes), and connection pooling, the only remaining knob is to split the write load across N primaries. Every shard is an independent database with its own WAL, its own memory, its own CPU — and the application is responsible for routing each query to the correct shard based on a shard key. There is no cross-shard JOIN, no cross-shard transaction (without 2PC), and no global uniqueness constraint; every guarantee the application relied on in a single-database world becomes an application-level concern in a sharded world.

In the layered mental model, sharding sits one layer above replication (see [[06.11.01. Primary-Replica Replication Mechanics]]) — each shard is itself a primary with its own replicas. The application's data access layer (Spring's `@ShardAware` or a custom `ShardingDataSource`, Django's `db_router` extended to shards, Laravel's multi-DB connections) becomes a query router that hashes the shard key to a shard index. Beneath each shard sit the same PostgreSQL/MySQL storage engines covered in [[06.04.02. B-Tree Index Mechanics and Page Layout]]. The OS primitives are identical to a non-sharded database; the difference is purely in the application's routing logic and in the operations tooling. The three canonical sharding topologies — range, hash, directory — differ in how the shard key maps to a shard, and each has a distinct failure mode and a distinct resharding cost.

## The Details

### Sharding Topologies: Range-Based Sharding, Hash-Based Sharding, Directory-Based / Lookup Sharding

**Range-based sharding** partitions the shard key's domain into contiguous ranges and assigns each range to a shard. Shard 0 owns `user_id ∈ [0, 1M)`, shard 1 owns `[1M, 2M)`, shard 2 owns `[2M, 3M)`, and so on. The advantage is that range queries (`WHERE user_id BETWEEN 500000 AND 1500000`) are efficient — they touch at most two shards. The disadvantage is the **hotspot problem**: if `user_id` is auto-incremented, all new writes go to the highest-numbered shard, which becomes the write hotspot while the other shards sit idle. This is the original sin of MongoDB's default `_id` (an auto-incrementing counter in early versions) — a single shard absorbed 100% of writes. The fix is to use a non-monotonic shard key (a UUID, or a hash of a natural key), which destroys the range-query efficiency. Range sharding is appropriate when the shard key has natural, well-distributed ranges and you genuinely need range queries — e.g. time-series data sharded by day (each day's data lives on a different shard, queries for "yesterday" hit one shard, queries for "last 30 days" fan out to 30).

**Hash-based sharding** computes `shard_index = hash(shard_key) mod N` where `hash` is a uniform hash function (MD5, MurmurHash3, FNV-1a). Each shard owns `1/N` of the hash space, which (for a good hash function) is also `1/N` of the keys. The advantage is **perfect write distribution** — even monotonic keys hash to a uniform spread across all shards. The disadvantage is the **resharding problem**: if N changes from 4 to 5, every key's `hash mod N` changes and ~80% of keys must move. Naive resharding of a 1 TB database means moving 800 GB of data, which can take days. The mitigations are (a) **consistent hashing** (see below), which reduces the data movement to ~1/N per shard addition; (b) **pre-splitting** — provision 1024 virtual shards on day 1, map them to 4 physical databases, and reshard by remapping virtual-to-physical without moving data; (c) **Vitess-style vindexes** — the hash function is parameterized so the same hash can be re-mapped to a different shard count with minimal data movement.

```text
  Range-based sharding (hotspot on auto-increment):
  Shard 0: [0, 1M)        ── write rate: 0 (cold)
  Shard 1: [1M, 2M)       ── write rate: 0 (cold)
  Shard 2: [2M, 3M)       ── write rate: 0 (cold)
  Shard 3: [3M, 4M)       ── write rate: 100% (all new IDs land here)

  Hash-based sharding (even distribution):
  Shard 0: hash(id) ∈ [0, 2^62)            ── write rate: 25%
  Shard 1: hash(id) ∈ [2^62, 2*2^62)       ── write rate: 25%
  Shard 2: hash(id) ∈ [2*2^62, 3*2^62)     ── write rate: 25%
  Shard 3: hash(id) ∈ [3*2^62, 4*2^62)     ── write rate: 25%

  Resharding 4 → 5 shards:
  Naive (hash mod N): ~80% of keys move (every key whose mod-4 ≠ mod-5)
  Consistent hashing: ~20% of keys move (only keys in the new shard's range)
  Vitess vindex:     ~0% of keys move (only the vindex mapping changes)
```

**Directory-based sharding** uses a lookup service — a separate database, a Redis hash, a ZooKeeper node — that maps each shard key to its shard. The application queries the directory (`SELECT shard FROM shard_map WHERE user_id = 42`), then queries the shard (`SELECT * FROM users WHERE id = 42` on shard 3). The advantage is **maximum flexibility** — you can move any single key to any shard at any time without affecting any other key, and you can shard by any criterion (geography, customer tier, creation date) regardless of hashability. The disadvantage is the **directory is a single point of failure and a bottleneck**: every query requires a directory lookup, which adds a round-trip and a dependency. The standard mitigations are (a) **cache the directory in the application** — fetch the entire shard map at startup and refresh on change; (b) **use a replicated directory** — Redis Cluster, etcd, or a Postgres table with logical replication; (c) **hybrid with hashing** — use hash-based as the default, with a directory override for the rare "this user must live on shard 5" case. Directory sharding is what Citus, Vitess, and MongoDB's config server all do internally — the difference between them is whether the directory is exposed to the application (Citus exposes it via the coordinator) or hidden behind a proxy (Vitess's vtgate does the lookup transparently).

The production failure mode unique to range sharding is the **monotonic-key hotspot** described above; for hash sharding, the **resharding storm**; for directory sharding, the **directory outage**. The Citus pattern (`SELECT create_distributed_table('users', 'user_id')`) is hash-based with a directory maintained by the coordinator — the application issues a single SQL statement and the coordinator parses, routes, fans-out, and merges. The Vitess pattern (`-vschema` with a `hash` vindex) is hash-based with consistent hashing underneath, so resharding is a `VReplication` workflow that copies a shard range in the background and atomically cuts over. Both hide sharding from the application — the application sees one logical database; the routing happens below.

### Shard Keys: Selecting optimal shard keys to eliminate data hotspots and avoid cross-shard queries

The shard key is the most consequential schema decision in a sharded system — it is essentially immutable once data is distributed, because changing it means moving every row. A good shard key has three properties: **high cardinality** (many distinct values, so the hash distributes evenly), **low skew** (no single value dominates — `country = 'US'` would put 80% of users on one shard), and **co-located access patterns** (queries that always filter by the shard key hit one shard, not many). A great shard key has all three; a poor shard key has none, and the system cannot be saved by adding more shards.

The cardinality test: if your shard key has fewer distinct values than shards, some shards will be empty. Skew test: if one value's frequency is > 1/N of total, that shard is a hotspot. Co-location test: list the top 10 queries the application will run; how many of them filter by the shard key? If fewer than 80%, you will be doing cross-shard fan-out on most queries, which destroys the throughput benefit of sharding.

```text
  Shard key decision matrix:

  Use case                              Good shard key         Bad shard key
  ─────────────────────────────────────────────────────────────────────────────
  Multi-tenant SaaS                     tenant_id              user_id
   (queries always WHERE tenant_id=)                          (every tenant's users
                                                              scatter across all shards)

  E-commerce orders                     user_id                order_id
   (queries: "show me user X's orders")                        (queries by user_id
                                                              fan out to all shards)

  Time-series metrics                   (host, metric, day)    timestamp alone
   (queries: "last 1h for host H metric M")                    (range query fans out to
                                                              all shards holding the range)

  Social graph                          user_id                friend_id
   (queries: "user X's friends")                               (the wrong user's friends
                                                              are co-located)

  IoT telemetry                         (device_id, day)       device_id alone
   (queries: "device D's last 24h")                            (one device's full history
                                                              overflows its shard)
```

The **compound shard key** is the answer to most real workloads. A single shard key optimises for one access pattern; a compound key `(tenant_id, user_id)` co-locates all of a tenant's users on the same shard, so queries by `tenant_id` hit one shard and queries by `(tenant_id, user_id)` also hit one shard. The hash function operates on the compound key, so `hash(tenant_id, user_id) mod N` distributes evenly across tenants but co-locates within a tenant. Vitess calls this a "multi-column vindex"; Citus calls it the distribution column with a co-located table group; MongoDB calls it a compound shard key with the same co-location semantics. The rule of thumb: the leftmost column of the shard key is the one that determines co-location, so put the most selective, most-queried column first.

The production failure mode is the **wrong shard key chosen early, discovered late**. A startup shards by `user_id` (because that was the natural primary key). Three years later, the application has grown to support multi-tenant enterprise accounts, and queries like "show me all users in Acme Corp" fan out to every shard — taking 5 seconds instead of 50 ms. Re-sharding by `(tenant_id, user_id)` requires moving every row in the database and rewriting every query. The mitigations are: (1) **choose the shard key based on the *future* access patterns, not the current ones** — if you ever plan to support multi-tenant, shard by tenant_id from day 1; (2) **use a logical shard key** that maps to a physical shard via a directory, so re-sharding is a directory update, not a data move; (3) **use a sharding middleware that supports vindex remapping** (Vitess) so the shard key can be changed without rewriting data. The deeper lesson: **sharding is the last resort because the schema decision is quasi-permanent**. Try vertical scaling, read replicas, materialised views, denormalisation, and a separate analytics warehouse first. Only shard when you have benchmarked every alternative and the write throughput is genuinely capped by a single primary.

### Cross-Shard Joins and Distributed Query Routing

A cross-shard query is any query that cannot be routed to a single shard by the shard key. `SELECT * FROM orders WHERE user_id = 42` routes to one shard (assuming `user_id` is the shard key); `SELECT count(*) FROM orders WHERE created_at > now() - interval '1 day'` must fan out to every shard. The fan-out query has fundamentally different performance characteristics: it is N× the latency of a single-shard query (the slowest shard sets the latency), N× the connection count (one connection per shard), and the coordinator must merge results — which for `count(*)` is a sum, but for `JOIN` is a hash-join across all shard results.

```text
  Distributed query execution (Citus / Vitess / CockroachDB):

  Client: SELECT count(*) FROM orders WHERE created_at > '2024-01-01';

  Coordinator:
   1. Parse query, identify that 'orders' is distributed by user_id
   2. The WHERE clause does not include user_id → fan-out query
   3. For each of N shards, send a sub-query:
        SELECT count(*) FROM orders WHERE created_at > '2024-01-01'
   4. Wait for all N shards to respond (slowest sets latency)
   5. Sum the N counts
   6. Return single integer to client

  Latency breakdown (4 shards, 5ms each, 1ms network RTT):
    fan-out (parallel): 5ms  (max of N)
    merge:              0.1ms
    coordinator RTT:    1ms
    total:              ~6ms   (vs 5ms single-shard — overhead is small)

  Latency breakdown for JOIN (4 shards, 5ms each, hash-join merge):
    fan-out (parallel): 5ms
    merge hash-join:    20ms   (transferring N×10MB result sets to coordinator)
    coordinator RTT:    1ms
    total:              ~26ms  (vs 5ms single-shard — overhead is 5×)
```

The **co-located JOIN** is the optimisation that makes sharded joins tolerable: if two tables are sharded by the same key, a join between them on that key is executed independently on each shard and the partial results merged. `SELECT * FROM users JOIN orders ON users.id = orders.user_id WHERE users.id = 42` — both `users` and `orders` are sharded by `user_id`, so the entire join runs on shard 3 (where user 42 lives) and the coordinator returns the result with no merge. This is why **co-locating tables by the same shard key is the single most important optimisation in a sharded database**. Citus calls this a "co-located distributed table" (`SELECT create_distributed_table('orders', 'user_id')` with the same `user_id` column as `users`); Vitess calls it a "lookup vindex" or "owned vindex"; CockroachDB and Spanner do it implicitly via interleaved tables. The application developer must explicitly choose the same shard key for related tables — the database does not infer this.

The **broadcast join** is the fallback for joining a small table against a sharded table: the small table is replicated to every shard (or broadcast per-query), and each shard joins against its local copy. `SELECT * FROM orders JOIN countries ON orders.country_code = countries.code` — `countries` has 250 rows, so it is broadcast to every shard and the join is local. This is what Citus calls a "reference table" (`SELECT create_reference_table('countries')`) and what Vitess calls an "unsharded table" stored on a primary that all shards can read from. The cost of a broadcast join is bounded by the size of the broadcast table — if it fits in memory on each shard, the join is fast; if it must be streamed per query, it is expensive.

The production failure mode is the **accidental cross-shard query that should have been co-located**. A developer writes `SELECT u.name, count(o.id) FROM users u JOIN orders o ON u.id = o.user_id GROUP BY u.name` — and the query takes 30 seconds instead of 50 ms because the coordinator is performing a distributed hash join over millions of rows. The fix is the `EXPLAIN` plan: if you see "Distributed Join" or "Broadcast" or "Gather" in the plan, you have a cross-shard operation. The deeper fix is **schema review at PR time** — a query plan check that fails the build if a query fans out unnecessarily. Spring's `@Query` annotation can be combined with a custom `QueryInterceptor` that runs `EXPLAIN` on every query in test and asserts single-shard routing; Django's `assertNumQueries` can be extended to assert single-shard routing via Citus's `citus.explain_distributed_query()`. The final failure mode is the **distributed transaction** — `BEGIN; INSERT INTO orders ...; UPDATE users SET last_order_at = ...; COMMIT` where `orders` and `users` are on different shards. This requires 2PC (two-phase commit) which has the blocking-failure mode covered in [[08.02.01. Two Phase Commit and the Blocking Failure Problem]]. The fix is to design the schema so that a transaction never spans shards — co-locate everything that must be transactional on the same shard key.

## Cross-Ecosystem Implementation

Sharding is implemented at the database layer (Citus, Vitess, CockroachDB, MongoDB sharded cluster) or at the application layer (Spring `AbstractRoutingDataSource` extended, Django multi-DB router, Laravel `DB::connection` per shard). The application-layer approach gives maximum control but requires the developer to write routing logic; the database-layer approach is transparent but locks you into the sharding middleware.

| Approach | Example | Routing decision | Cross-shard JOIN | Resharding |
|---|---|---|---|---|
| Application-routed | Spring `AbstractRoutingDataSource` with N pools | Per-method `ThreadLocal` lookup | Manual fan-out + merge | Manual ETL |
| Django multi-DB | `DATABASES = {'shard_0': {}, 'shard_1': {}}` + router | `db_for_read(model, **hints)` | Manual | Manual ETL |
| Laravel multi-DB | `DB::connection("shard_{$shardId}")` | Per-query explicit | Manual | Manual ETL |
| Citus (Postgres extension) | `create_distributed_table('users', 'user_id')` | Coordinator parses SQL | Automatic (co-located or broadcast) | `master_add_node` + rebalancer |
| Vitess (MySQL proxy) | vtgate + `-vschema` | vtgate parses SQL | Automatic (vindex lookup) | `SplitShard` + VReplication |
| CockroachDB (native) | `CREATE TABLE ... PARTITION BY ...` | Range-based on PK | Automatic (DistSQL) | `ALTER TABLE ... RELOCATE` |

The Citus and Vitess patterns are the gold standards because they hide sharding from the application — the developer writes standard SQL and the middleware handles routing, fan-out, and merge. The application-layer approach (multi-DB in Django/Laravel, multi-pool in Spring) is appropriate when you have a small number of shards (< 10), a simple shard key (single hash column), and no cross-shard JOINs — typical of a multi-tenant SaaS where `tenant_id` is the shard key and every query filters by `tenant_id`. For more complex sharding (geo-distributed, multi-key, resharding-prone), use a sharding middleware — the engineering investment of building and operating your own router is rarely worth it.

## Hands-On Exercise

```bash
# Citus (Postgres sharding extension) — the easiest way to learn sharding

# Set up a coordinator + 2 workers (Docker)
docker run -d --name citus-coordinator -p 5432:5432 -e POSTGRES_PASSWORD=secret citusdata/citus:12.1
docker run -d --name citus-worker-1 -p 5433:5432 -e POSTGRES_PASSWORD=secret citusdata/citus:12.1
docker run -d --name citus-worker-2 -p 5434:5432 -e POSTGRES_PASSWORD=secret citusdata/citus:12.1

# On the coordinator:
psql -h localhost -U postgres
SELECT * from citus_set_coordinator_host('citus-coordinator', 5432);
SELECT * from citus_add_node('citus-worker-1', 5432);
SELECT * from citus_add_node('citus-worker-2', 5432);
SELECT * FROM citus_active_nodes();

# Create and distribute a table
CREATE TABLE users (id bigint primary key, name text, tenant_id bigint);
SELECT create_distributed_table('users', 'id');

# Insert data and watch it scatter
INSERT INTO users SELECT i, 'user_' || i, i % 100 FROM generate_series(1, 10000) i;
SELECT * FROM citus_shards WHERE table_name = 'users';
# observe: shard_102008 on worker-1, shard_102009 on worker-2, etc.

# Single-shard query (fast — routes by shard key)
EXPLAIN SELECT * FROM users WHERE id = 42;
# -> Custom Scan (Citus Adaptive Router) — single shard

# Cross-shard query (slow — fan-out)
EXPLAIN SELECT count(*) FROM users;
# -> Custom Scan (Citus Adaptive) — fan-out to all shards, merge

# Co-located JOIN — same shard key on both tables
CREATE TABLE orders (id bigint, user_id bigint, amount numeric);
SELECT create_distributed_table('orders', 'user_id');
EXPLAIN SELECT u.name, count(o.id)
  FROM users u JOIN orders o ON u.id = o.user_id
  WHERE u.id = 42
  GROUP BY u.name;
# -> single-shard join (both tables co-located by user_id)

# Cross-shard JOIN (different shard key)
EXPLAIN SELECT u.name, count(o.id)
  FROM users u JOIN orders o ON u.id = o.user_id
  GROUP BY u.name;
# -> Distributed Join with repartition (expensive — data reshuffles)

# Reference table (broadcast to all shards)
CREATE TABLE countries (code text primary key, name text);
SELECT create_reference_table('countries');
EXPLAIN SELECT * FROM users u JOIN countries c ON u.country = c.code;
# -> join runs locally on each shard (countries broadcast)

# Add a shard (reshard)
docker run -d --name citus-worker-3 -p 5435:5432 -e POSTGRES_PASSWORD=secret citusdata/citus:12.1
SELECT * from citus_add_node('citus-worker-3', 5432);
SELECT rebalance_table_shards('users');
# observe data moving from worker-1/2 to worker-3 with minimal movement
```
