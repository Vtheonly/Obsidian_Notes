# 06.11.01. Primary-Replica Replication Mechanics

## What This Is

Replication is the mechanism by which a single source of truth — the primary — propagates its writes to one or more followers — the replicas. It is the foundational technique behind every horizontally-scaled read workload, every high-availability failover, every geo-distributed database, and every read-after-write consistency trade-off. Every relational database (PostgreSQL, MySQL, Oracle, SQL Server) and most NoSQL systems (MongoDB, Cassandra, Elasticsearch) implement some flavor of primary-replica replication. The mechanics differ — physical WAL streaming in PostgreSQL, logical decoding for cross-version replication, MySQL binlog with statement/row/mixed formats, MongoDB oplog — but the underlying invariants are identical: writes happen at the primary in a strict order, that order is transmitted to replicas as a log, replicas apply the log in order, and the gap between "primary committed" and "replica applied" is the replication lag.

In the layered mental model, replication sits at the same layer as the WAL itself (see [[06.04.03. Crash Recovery and the ARIES Algorithm]]). The primary's WAL is the durable record of every mutation; the replica is simply a second process consuming that WAL as a stream and applying it to its own storage. The OS primitives in play are TCP keepalive for the replication connection, `sendfile(2)` or `recv(2)` for shipping bytes, and `fsync(2)` for the replica's own WAL durability. The application layer sees replication through the lens of connection routing — Spring's `@Transactional(readOnly=true)` routes to a replica via a `LazyConnectionDataSourceProxy`; Django's database router does the same with `db_for_read`; Laravel's `->onReadConnection()` and Prisma's `$replica()` client expose the same primitive. This note covers the four canonical sub-concepts: physical vs logical, sync vs async, lag monitoring, and read-write splitting.

## The Details

### Physical Replication (Byte-level WAL streaming) vs. Logical Replication (Row-level mutation events)

**Physical replication** ships the database's write-ahead log byte-for-byte from primary to replica. PostgreSQL's streaming replication (since 9.0) is the canonical example: the primary exposes a TCP port (default 5432, the same as client connections) and the replica connects with the `replication=database` protocol parameter. The primary then streams WAL segments — 16 MiB by default, configurable via `wal_segment_size` — as fast as the replica can `recv()` and `fsync()` them. The replica applies each WAL record by replaying the page-level mutation: "set bytes 0x42-0x46 of page 0x1F3 of file `base/16384/16387` to `0x01020304`". Because the replica is byte-identical to the primary (same page layout, same file structure), the replica is a *physical* twin — same block addresses, same indexes, same free-space map. The configuration is minimal: on the replica, `primary_conninfo = 'host=primary_ip port=5432'` in `postgresql.conf`, a `standby.signal` file in the data directory, and that is it.

```text
  PostgreSQL physical streaming replication:

  Primary                                    Replica
  ┌──────────────────────────┐               ┌──────────────────────────┐
  │ INSERT INTO users ...    │               │                          │
  │   → WAL record (XLOG)    │──stream ────► │ recv WAL bytes           │
  │   → fsync(WAL)           │  TCP 5432     │   → write to pg_wal/     │
  │   → modify buffer        │               │   → fsync                │
  │   → COMMIT ack to client │               │   → apply (redo to page) │
  │   → continue serving     │               │   → ready for next WAL   │
  └──────────────────────────┘               └──────────────────────────┘
              │                                            │
              └─────── shared WAL byte sequence ───────────┘
                       (LSN = Log Sequence Number)

  Replica setup:
    # in postgresql.conf:
    primary_conninfo = 'host=10.0.0.10 port=5432 application_name=replica1'
    hot_standby = on            # allow read queries while in recovery
    # touch standby.signal in $PGDATA:
    touch $PGDATA/standby.signal
    # base backup to seed the replica:
    pg_basebackup -h 10.0.0.10 -D $PGDATA -U replicator -P -R
```

**Logical replication** ships *decoded* mutations — not raw page bytes, but row-level events: "INSERT into table `users` with values (id=42, name='Alice')". PostgreSQL's logical replication (since 10.0) uses the same WAL stream but feeds it through a *logical decoding output plugin* (`pgoutput` is the built-in; `wal2json`, `test_decoding` are alternatives) that decodes the page-level mutations into row-level change events. The replica subscribes via the `CREATE SUBSCRIPTION` SQL command and applies the events through normal `INSERT`/`UPDATE`/`DELETE` statements — exactly as if a client were issuing them. The replica can have different physical layout: different tables, different indexes, different page sizes, even a different major version of PostgreSQL. Logical replication is how you upgrade from PG 13 to PG 16 with zero downtime (replicate from 13 → 16, then promote the 16).

The trade-offs are profound. Physical replication is fast, simple, and operationally bulletproof — but it cannot cross major versions, cannot replicate a subset of tables, and cannot replicate to a different schema. Logical replication is flexible — cross-version, cross-schema, subset-of-tables, even cross-database (Postgres → Kafka → ClickHouse via Debezium) — but it is slower (the decoding step adds CPU), it cannot replicate schema changes (DDL must be applied manually on both sides), and sequences are not replicated (you must configure `ALTER SUBSCRIPTION ... SET (origin = none)` and use sequence ranges to avoid collisions). The failure mode unique to physical is the **WAL-block corruption** — a single bad byte in a WAL segment is unrecoverable on the replica without a full `pg_basebackup` resync, which can take hours on a 1 TB database. The failure mode unique to logical is the **replication slot retention** — if the replica is offline, the primary retains WAL indefinitely to avoid losing unreplicated changes, which can fill the primary's disk; the fix is monitoring `pg_replication_slots` and dropping stuck slots with `pg_drop_replication_slot()`.

| Aspect | Physical (streaming) | Logical (decoding) |
|---|---|---|
| What is shipped | Raw WAL bytes | Decoded row events (INSERT/UPDATE/DELETE) |
| Cross-version | Same major version only | Cross-major, even cross-DBMS via plugins |
| Replica schema | Identical to primary | Can differ (subset of tables, different indexes) |
| DDL replication | Yes (it is in WAL) | No (must apply manually on subscriber) |
| Sequences | Replicated | Not replicated (manual range allocation needed) |
| Setup | `standby.signal` + `primary_conninfo` | `CREATE PUBLICATION` + `CREATE SUBSCRIPTION` |
| Failover | `pg_promote()` — instant | Re-point subscriber, may need resync |
| Typical use | HA, read replicas, DR | Upgrades, partial sync, ETL, CDC to Kafka |

### Synchronous vs. Asynchronous Replication trade-offs: Zero data loss vs. write latency overhead

**Asynchronous replication** is the default in both PostgreSQL and MySQL: the primary commits the transaction locally, returns `COMMIT` to the client, and only then ships the WAL to the replica. If the primary crashes between the local commit and the replica receiving the WAL, those committed transactions are lost — the RPO is "whatever was in the primary's WAL but not yet streamed". For PostgreSQL with default `wal_sender_timeout = 60s` and a LAN replica, this is typically 10–100 ms of writes (a few hundred to a few thousand transactions). The advantage is write latency = local fsync only (100–500 µs on NVMe); the disadvantage is the explicit RPO > 0.

**Synchronous replication** blocks the commit until the replica acknowledges. PostgreSQL's `synchronous_commit = on` (the default for the *local* fsync) plus `synchronous_standby_names = 'FIRST 1 (replica1)'` makes the primary wait for `replica1` to flush the WAL to disk before returning `COMMIT` to the client. The RPO becomes exactly 0 — if the primary crashes, every committed transaction is on the replica. The cost is write latency = local fsync + network round-trip + replica fsync. On a same-AZ replica with sub-millisecond network and NVMe on both sides, this adds ~1–2 ms to every commit. On a cross-AZ replica with 2 ms network, this adds ~4 ms. On a cross-region replica with 50 ms network, this adds ~100 ms — and at that point your write throughput is capped by the round-trip time.

```text
  Async replication timeline (default):
  T=0ms   client: BEGIN; UPDATE accounts SET bal=bal-10 WHERE id=1; COMMIT
  T=0.2ms primary: fsync(WAL) — durable locally
  T=0.2ms primary: reply COMMIT to client   ← client sees success
  T=0.5ms primary: stream WAL bytes to replica
  T=1.0ms replica: recv WAL, write to pg_wal, fsync, apply
  T=1.0ms replica: ready for next

  Crash at T=0.7ms: replica has not received the WAL yet → tx LOST (RPO ~0.5ms)

  ─────────────────────────────────────────────────────────────────────────

  Sync replication timeline (synchronous_standby_names = 'replica1'):
  T=0ms   client: BEGIN; UPDATE accounts SET bal=bal-10 WHERE id=1; COMMIT
  T=0.2ms primary: fsync(WAL) — durable locally
  T=0.5ms primary: stream WAL bytes to replica — WAIT for ack
  T=1.0ms replica: recv WAL, write to pg_wal, fsync, apply
  T=1.1ms replica: send ack
  T=1.6ms primary: reply COMMIT to client   ← client sees success
  Crash at any point after T=1.0ms: tx is on replica — RPO = 0
  Crash between T=0 and T=1.0: tx is ABORTED, client sees error, no data loss
```

The middle ground is **`synchronous_commit = remote_write`** (wait for the replica to `write(2)` but not `fsync(2)` — slightly faster, RPO = "replica kernel crash between write and fsync") and **`synchronous_commit = local`** (wait for local fsync only, same as async but explicit). PostgreSQL also supports quorum-based sync: `synchronous_standby_names = 'ANY 2 (replica1, replica2, replica3)'` waits for any 2 of 3 replicas — the durability-vs-latency knob can be tuned per-transaction with `SET LOCAL synchronous_commit = remote_apply` inside a transaction, so a financial transfer can demand sync replication while a log-insert can use async.

MySQL exposes the same knob via `rpl_semi_sync_source_enabled = ON` and `rpl_semi_sync_source_wait_for_slave_count = N`. MongoDB uses `writeConcern: { w: "majority", j: true, wtimeout: 5000 }` per operation. Cassandra uses `consistency: ALL` or `LOCAL_QUORUM` per query. The unifying concept: **every distributed write is a quorum write**, and the question is always "how many replicas must ack, and how durable must their ack be (fsynced vs kernel-buffered), before the client sees success". The production failure mode of synchronous replication is **write throughput collapse under replica stress** — if the replica is slow (CPU-busy, disk-busy, network-busy), every commit waits; primary write latency follows replica fsync latency 1:1. The mitigation is to monitor `pg_stat_replication.replay_lag` and remove a slow replica from `synchronous_standby_names` automatically when its lag exceeds a threshold — accepting brief RPO > 0 over total write outage.

### Replication Lag: Causes, monitoring mechanisms, and handling stale read phenomena

Replication lag is the wall-clock time between "primary committed transaction T" and "replica has applied transaction T". It is composed of three components: (1) **network transmission lag** — bytes in flight on the TCP connection, typically sub-millisecond on LAN, tens of milliseconds cross-region; (2) **replica fsync lag** — the replica's own `fsync(WAL)` cost, identical to the primary's fsync cost (100–500 µs on NVMe); (3) **replica apply lag** — the CPU time to redo the WAL records into pages, which for OLTP workloads is typically equal to the primary's apply time but can balloon for large batch operations (a single `UPDATE table SET ... WHERE id IN (1M ids)` produces a 100 MB WAL record that takes seconds to apply on the replica).

PostgreSQL exposes lag in three ways in `pg_stat_replication` on the primary: `write_lag` (time between primary flush and replica write), `flush_lag` (time between primary flush and replica fsync), `replay_lag` (time between primary flush and replica apply). The most actionable is `replay_lag` because that is what the application actually sees as "stale reads". On the replica, `pg_stat_wal_receiver` shows bytes received and applied. In MySQL, `SHOW REPLICA STATUS` exposes `Seconds_Behind_Master` (a coarse counter) and the more precise `replication_applier_status_by_worker` table. The crucial metric to alert on is not "lag is non-zero" — lag is always non-zero under async replication — but "lag is growing" or "lag exceeds X seconds for Y minutes". A static alert at "lag > 5s" will fire constantly on a busy replica and be ignored.

```text
  Stale read window — the read-your-writes problem:

  T=0ms    client: POST /api/users  →  primary commits user id=42
  T=2ms    primary returns 201 Created to client
  T=5ms    client: GET /api/users/42  →  routed to replica (read-write split)
  T=5ms    replica: replay_lag = 8ms  (has not yet applied tx T=0)
  T=5ms    replica: SELECT ... returns 404 (row not yet visible)
  T=5ms    client sees: 404 for the user it just created

  Mitigations (in order of preference):
  1. Read-your-writes window: route reads to primary for 1-2s after a write
     (sticky session, or token-based: client sends "last-write-lsn" header)
  2. Causal consistency: replica refuses to serve a read until it has
     replayed past the client's last write LSN
     (Postgres: SELECT pg_current_wal_lsn() on primary; replica polls
      pg_wal_lsn_diff(pg_last_wal_replay_lsn(), client_lsn) >= 0)
  3. Just use the primary for the user's own data; replicas for aggregate reads
```

The mitigations for stale reads fall into a hierarchy. The simplest is the **read-your-writes window**: the application routes the user's own reads to the primary for a short window (1–5 seconds) after their last write. This is implemented in Django's database router (override `db_for_read` to check `request.session['last_write_at']`), in Spring's `@Transactional(readOnly=true)` (use the primary transaction manager instead of the replica one for the user's own data), and in Laravel's `DB::connection('pgsql::write')` for sticky reads. The middle ground is **causal consistency via LSN**: the client receives the primary's commit LSN as a response header (`X-Last-LSN: 0/16B3748`), sends it back on subsequent reads, and the replica blocks the read until `pg_wal_replay_lsn() >= client_lsn`. The most rigorous is **linearizable reads via quorum**: the read goes to the primary (or to a quorum of replicas that includes the primary's latest WAL), guaranteeing the read sees all committed writes — at the cost of primary round-trip latency on every read.

The production failure mode is **lag-spike-induced incident cascade**. A replica's lag spikes to 30 seconds during a batch update. The application's stale-read window (5 seconds) is exceeded, so users see stale data. The application's lag monitor alerts. The on-call engineer triggers a failover to a *different* replica — but that replica is also lagged (the same batch hit all replicas). The failover succeeds but the new primary is 60 seconds behind the old primary. The application reads from the new primary and sees 60-second-old data. The fix is to monitor **lag growth rate**, not absolute lag, and to never fail over to a replica with `replay_lag > 1 second` — wait for the replica to catch up first (`SELECT pg_wal_replay_lsn()` matches primary's `pg_current_wal_lsn()`). The deeper fix is to make the batch operation *throttle itself* — `UPDATE` in 10,000-row chunks with a 100 ms sleep between chunks, so the replica can keep up.

### Read-Write Splitting: Routing mutations to the Primary instance and distributing read traffic across Read Replicas

Read-write splitting is the application-side mechanism that sends `INSERT`/`UPDATE`/`DELETE` queries to the primary and `SELECT` queries to one of N replicas. The motivation is asymmetric load: in most web applications the read-to-write ratio is 10:1 to 100:1, and a single primary can handle the writes but cannot handle the reads. Adding read replicas scales the read capacity linearly with replica count — at the cost of the stale-read window discussed above. Every framework implements this differently, but the underlying primitive is the same: a routing layer that inspects the query (or the transaction annotation) and picks a connection.

```text
  Connection routing topology (Spring AbstractRoutingDataSource):

  App Service Layer
       │
       ▼
  ┌─────────────────────────────────┐
  │ RoutingDataSource              │
  │  determineCurrentLookupKey()   │
  └───┬─────────────┬───────────────┘
      │             │
      │ write       │ read
      ▼             ▼
  ┌────────┐   ┌───────────────────────────────┐
  │ Primary│   │ Replica Load Balancer         │
  │ (R/W)  │   │  ┌────┐  ┌────┐  ┌────┐       │
  └────────┘   │  │R1  │  │R2  │  │R3  │ round │
               │  └────┘  └────┘  └────┘ robin │
               └───────────────────────────────┘

  Spring config:
    @Transactional(readOnly = true)  → RoutingDataSource returns "read"
    @Transactional                   → RoutingDataSource returns "write"
    (readOnly hint propagated via TransactionSynchronizationManager)
```

The Spring Boot implementation uses `AbstractRoutingDataSource` — a DataSource that delegates to one of N underlying DataSources based on a thread-local key. `@Transactional(readOnly = true)` sets the thread-local to `"read"`, which the router maps to a round-robin over the replica DataSources. The gotcha is that the routing decision is made *at connection acquisition time*, not at statement execution time — so a `@Transactional` method that does one `INSERT` followed by ten `SELECT`s uses the primary connection for all eleven queries. If you want fine-grained per-statement routing, you must split the method or use `@DataSource(readOnly=true)` at the method level for read-only methods. Django's database router (`db_for_read(model, **hints)`) is per-query but per-model — it picks the database based on the model class, not the query type, so you typically route `User.objects.using('replica')` explicitly or via a custom router that inspects `hints.get('instance')`. Laravel's `DB::connection('pgsql::read')` is the most explicit — you must call it per-query.

The deeper failure mode of read-write splitting is the **cross-replica fan-out problem**. A query like `SELECT count(*) FROM orders WHERE user_id = 42` runs on one replica; a follow-up `SELECT * FROM orders WHERE user_id = 42 LIMIT 10` runs on a different replica — and the two replicas have slightly different lag, so the count is 1003 on the first and 998 on the second. The user sees "Showing 10 of 998" but the count endpoint said 1003. This is the *session consistency* problem and the fix is *replica affinity*: hash the session ID to a specific replica and stick to it for the duration of the session. HAProxy's `balance source`, Nginx's `ip_hash`, and AWS Aurora's reader-endpoint-with-affinity all implement this. The trade-off is uneven load — if one user is heavy, their replica is hot — so affinity windows must be short (5–15 minutes) and reassigned. The final failure mode is the **connection-pool multiplication**: N app instances × M replicas × P pool-size-per-target = N×M×P connections, which can exhaust Postgres's default `max_connections = 100` quickly. Use PgBouncer in transaction-pooling mode in front of each replica to amortise, and cap the application pool at 5–10 connections per target.

## Cross-Ecosystem Implementation

The four ecosystems expose read-write splitting at different layers of abstraction — Spring at the transaction manager, Django at the database router, Laravel at the connection facade, Prisma at the client object.

| Pattern | Spring (`AbstractRoutingDataSource`) | Django (`DATABASES` + router) | Laravel (`DB::connection`) | Prisma (`$replica()`) |
|---|---|---|---|---|
| Define replica | `@Bean DataSource readDataSource()` | `DATABASES = {'replica1': {...}}` | `config('database.connections.pgsql.read')` | `new PrismaClient({ datasources: { db: { url: '...' } }, replicaUrl: '...' })` |
| Mark read-only | `@Transactional(readOnly=true)` | `Model.objects.using('replica1')` | `DB::connection('pgsql::read')` | `prisma.$replica().user.findMany()` |
| Auto route | yes (via AOP) | yes (custom router) | no (manual per-query) | yes (auto for `find*` queries) |
| Replica affinity | via `ThreadLocal` + session-id hash | via `request.session` router | via `DB::connection` per request | via `$transaction` context |
| Failover to primary | yes (if replica down) | manual | manual | yes (auto fallback) |

Spring's auto-routing via `@Transactional(readOnly=true)` is the most ergonomic — the developer writes a single annotation and the framework handles the routing. Django's router is the most flexible — you can route by model, by hints, by session. Laravel's explicit `DB::connection('read')` is the most visible — you always know which database a query hits. Prisma's `$replica()` is the newest — automatic read-routing with replica fallback, but only for `find*` queries; writes always go to the primary. Each exposes the same underlying primitive: pick a connection per query.

## Hands-On Exercise

```bash
# PostgreSQL: set up streaming replication, observe lag, force a failover

# On primary (10.0.0.10):
sudo -u postgres psql
CREATE ROLE replicator WITH REPLICATION LOGIN PASSWORD 'secret';
# in pg_hba.conf:
#   host replication replicator 10.0.0.0/24 md5
# in postgresql.conf:
#   wal_level = replica
#   max_wal_senders = 10
#   synchronous_commit = on
#   synchronous_standby_names = 'FIRST 1 (replica1)'
sudo systemctl restart postgresql

# On replica (10.0.0.11):
sudo -u postgres pg_basebackup -h 10.0.0.10 -D /var/lib/postgresql/data \
  -U replicator -P -R
touch /var/lib/postgresql/data/standby.signal
# in postgresql.conf:
#   hot_standby = on
#   primary_conninfo = 'host=10.0.0.10 application_name=replica1'
sudo systemctl start postgresql

# On primary: monitor replication
sudo -u postgres psql
SELECT application_name, state, sync_state, write_lag, flush_lag, replay_lag
  FROM pg_stat_replication;
SELECT slot_name, active, restart_lsn, retained_wal_bytes
  FROM pg_replication_slots;        # check for stuck slots filling disk

# Generate write load, watch the replica lag grow
pgbench -i -s 100 mydb              # scale factor 100 = ~1.4 GB
pgbench -c 8 -j 4 -T 60 mydb        # 8 clients, 60 seconds
# in another terminal:
watch -n 1 "psql -h 10.0.0.10 -c \"SELECT replay_lag FROM pg_stat_replication\""

# Force a failover to the replica
sudo -u postgres psql -h 10.0.0.11
SELECT pg_promote();                # replica becomes primary
# (the old primary is now orphaned; needs pg_rewind to rejoin)

# MySQL: same exercise
# On primary: my.cnf
#   server-id = 1
#   log_bin = mysql-bin
#   binlog_format = ROW              # row-based for crash-safe replication
#   gtid_mode = ON                   # global tx IDs for easy failover
# CREATE USER 'repl'@'%' IDENTIFIED BY 'secret';
# GRANT REPLICATION SLAVE ON *.* TO 'repl'@'%';
# On replica:
# CHANGE REPLICATION SOURCE TO SOURCE_HOST='10.0.0.10',
#   SOURCE_USER='repl', SOURCE_PASSWORD='secret',
#   SOURCE_AUTO_POSITION=1;
# START REPLICA;
# SHOW REPLICA STATUS\G              # Seconds_Behind_Master, Relay_Log_Pos

# Application-side: confirm read-write split is working
# Spring: enable SQL logging, observe "Routing to read DataSource" for @Transactional(readOnly=true)
# Django: print(db.connections.databases[router.db_for_read(User)]['NAME'])
# Laravel: DB::connection()->getName();  // 'pgsql::read' vs 'pgsql::write'
```
