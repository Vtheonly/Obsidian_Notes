# 06.04.02. Concurrency Anomalies and Phenomena Deep Dive

## What This Is

The four ANSI SQL isolation levels (READ UNCOMMITTED, READ COMMITTED, REPEATABLE READ, SERIALIZABLE) exist to prevent specific concurrency anomalies — observable incorrect results that occur when two transactions read and write the same data concurrently. This note walks through each anomaly with a concrete SQL timeline, shows which isolation levels prevent it, and explains the real-world failure it produces. The anomalies are: dirty read, non-repeatable read, phantom read, lost update, write skew, and read skew. The first three are the "classic" ANSI anomalies; the last three are the "real" anomalies that bite production systems, and they are the reason SERIALIZABLE isolation exists even though most production deployments never use it.

## The Details

### **Dirty Read**: Transaction reads uncommitted state mutated by a concurrent transaction that subsequently rolls back

A dirty read happens when transaction T2 reads a row that transaction T1 has modified but not yet committed. If T1 then rolls back, T2 has read data that never officially existed — a "dirty" value. This is the most obvious anomaly, and the only one prevented by every isolation level above READ UNCOMMITTED.

```sql
-- Dirty read example (only possible under READ UNCOMMITTED):

-- Session 1:
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
-- balance is now 400 (was 500), uncommitted

-- Session 2:
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
BEGIN;
SELECT balance FROM accounts WHERE id = 1;
-- Returns 400 — DIRTY READ of uncommitted data
COMMIT;

-- Session 1:
ROLLBACK;   -- balance reverts to 500

-- Session 2 has now made decisions based on balance=400, but
-- the actual balance is 500. The decisions are wrong.
```

The classic real-world failure: a banking app reads an account balance mid-transfer (during the brief window when the source account has been debited but the destination has not been credited), sees the artificially low balance, and rejects a concurrent transfer due to "insufficient funds." Under READ COMMITTED (PostgreSQL's default, MySQL's default for some configurations), this cannot happen — T2 sees only the committed balance of 500.

In practice, no production database runs under READ UNCOMMITTED. PostgreSQL still accepts the syntax (`SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED`) but silently treats it as READ COMMITTED — the engine does not implement true dirty reads, on the grounds that no one wants them. MySQL InnoDB does implement READ UNCOMMITTED, but the only sensible use case is a monitoring query that explicitly accepts potentially-wrong data in exchange for zero lock overhead.

### **Non-Repeatable (Fuzzy) Read**: Transaction re-reads a row and finds modified column data committed by a concurrent transaction

A non-repeatable read happens when transaction T2 reads a row, then transaction T1 modifies and commits that row, then T2 re-reads the row and sees a different value. The same query, within the same transaction, returns different results. This is prevented by REPEATABLE READ (which gives each transaction a snapshot that does not change) but allowed by READ COMMITTED (which takes a fresh snapshot per statement).

```sql
-- Non-repeatable read example (allowed by READ COMMITTED):

-- Session 1 (T2 in the description):
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
BEGIN;
SELECT balance FROM accounts WHERE id = 1;
-- Returns 500

-- Session 2 (T1 in the description):
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;
-- balance is now 400, committed

-- Session 1:
SELECT balance FROM accounts WHERE id = 1;
-- Returns 400 — different from the first read!
COMMIT;
```

The classic real-world failure: a report transaction that reads the same row twice (once to compute a total, once to display a detail) shows inconsistent numbers — the total says 500, the detail says 400, the report is internally inconsistent. Under READ COMMITTED, this is legal; under REPEATABLE READ, the second read would return 500 (the snapshot's value), making the report consistent.

The fix is to either (a) use REPEATABLE READ for transactions that need a stable view of the data, or (b) use `SELECT ... FOR UPDATE` / `SELECT ... FOR SHARE` to take an explicit lock that prevents other transactions from modifying the row. Option (b) is heavier (it blocks other writers), but it is the only option under READ COMMITTED if you need to read the *current* committed value and prevent concurrent modification while you make a decision based on it.

### **Phantom Read**: Transaction re-executes a range query and discovers newly inserted rows matching the predicate committed by a concurrent transaction

A phantom read is the range-query analogue of a non-repeatable read. Transaction T2 runs `SELECT COUNT(*) FROM orders WHERE date = '2024-01-15'`, gets 100, then transaction T1 inserts a new order for that date and commits, then T2 re-runs the same query and gets 101. The new row is a "phantom" — it was not there before, it is there now, and T2's transaction sees different results on re-execution.

```sql
-- Phantom read example (allowed by READ COMMITTED, allowed by
-- REPEATABLE READ in the SQL standard, prevented by REPEATABLE
-- READ in InnoDB via next-key locks):

-- Session 1 (T2):
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
BEGIN;
SELECT COUNT(*) FROM orders WHERE date = '2024-01-15';
-- Returns 100

-- Session 2 (T1):
BEGIN;
INSERT INTO orders (date, amount) VALUES ('2024-01-15', 50);
COMMIT;

-- Session 1:
SELECT COUNT(*) FROM orders WHERE date = '2024-01-15';
-- Returns 101 — PHANTOM READ
COMMIT;
```

Under PostgreSQL's REPEATABLE READ (which is really Snapshot Isolation), the second query returns 100 — T2's snapshot was taken at the start of the transaction and does not see T1's insert. Under MySQL InnoDB's REPEATABLE READ (the default), the second query also returns 100, but for a different reason: InnoDB's next-key locks (06.03.03) on the range prevent T1 from inserting the phantom row in the first place (T1 blocks until T2 commits). Under SQL Server's READ COMMITTED, phantoms are allowed; under SQL Server's SERIALIZABLE, they are prevented by range locks.

The real-world failure of phantom reads is in audit and reporting transactions: a transaction that sums up the day's orders and writes the total to a summary table might miss an order that was inserted concurrently, producing a summary that is off by one or more orders. The fix is REPEATABLE READ (in PostgreSQL) or SERIALIZABLE (in MySQL InnoDB to use locking reads, or in PostgreSQL with SSI).

### **Lost Update**: Two concurrent transactions read identical state, compute updates locally, and write back, with the second write blindly overwriting the first

Lost update is the most pernicious anomaly, because it is silent — no error is raised, but the data is wrong. T1 reads balance=500, computes 500-100=400, writes 400. T2 reads balance=500 (before T1's commit), computes 500+50=550, writes 550. Final balance: 550. The 100 debit is lost. The bank just gave away 100.

```sql
-- Lost update example (allowed by READ COMMITTED in PostgreSQL
-- and MySQL InnoDB):

-- Session 1 (T1):
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
BEGIN;
SELECT balance FROM accounts WHERE id = 1;   -- reads 500
-- ... application computes 500 - 100 = 400 ...

-- Session 2 (T2):
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
BEGIN;
SELECT balance FROM accounts WHERE id = 1;   -- also reads 500
-- ... application computes 500 + 50 = 550 ...
UPDATE accounts SET balance = 550 WHERE id = 1;
COMMIT;

-- Session 1 (T1):
UPDATE accounts SET balance = 400 WHERE id = 1;
COMMIT;

-- Final balance: 400. T2's +50 is LOST.
```

The four standard fixes:

```sql
-- Fix 1: SELECT ... FOR UPDATE (pessimistic locking, all engines)
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;   -- X lock
-- ... compute 500 - 100 = 400 ...
UPDATE accounts SET balance = 400 WHERE id = 1;
COMMIT;
-- T2's SELECT ... FOR UPDATE blocks until T1 commits.

-- Fix 2: REPEATABLE READ with conflict detection
-- In PostgreSQL: REPEATABLE READ gives each transaction a snapshot.
-- When T2 tries to UPDATE, PostgreSQL detects that the row was
-- modified by T1 after T2's snapshot, and aborts T2 with:
-- ERROR: could not serialize access due to concurrent update
-- The application retries T2.

-- Fix 3: Atomic update (no read-modify-write cycle)
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
-- The expression "balance = balance - 100" is evaluated by the
-- engine atomically with the row lock held. No lost update possible.

-- Fix 4: Optimistic concurrency control with a version column
BEGIN;
SELECT balance, version FROM accounts WHERE id = 1;   -- version=5
-- ... compute 500 - 100 = 400 ...
UPDATE accounts SET balance = 400, version = version + 1
  WHERE id = 1 AND version = 5;
-- If 0 rows affected, someone else modified the row; retry.
COMMIT;
```

The real-world failure of lost update is everywhere: shopping cart totals, account balances, inventory counts, like counts. Any "read-modify-write" pattern under READ COMMITTED is vulnerable. The fix is one of the four patterns above, chosen by the workload: `FOR UPDATE` for high-contention rows, atomic updates for simple arithmetic, version columns for optimistic patterns. The deeper lesson: never write `SELECT ... UPDATE` under READ COMMITTED without one of these protections — the test suite will pass (because tests usually run serially), but production will silently lose data.

### **Write Skew**: Two concurrent transactions evaluate disjoint data sets against a common business constraint and make non-conflicting modifications that collectively violate the global domain invariant

Write skew is the anomaly that Snapshot Isolation (which is what PostgreSQL's REPEATABLE READ and InnoDB's REPEATABLE READ both approximate) cannot prevent. The pattern: T1 reads data set A, T2 reads data set B, A and B are disjoint (so there is no write-write conflict — the transactions do not modify the same row), both transactions commit, but the combined effect violates a business invariant that spans both data sets.

```sql
-- Write skew example (the classic "doctor on call" scenario):

-- Business rule: at least one doctor must be on call at all times.
-- Current state: Alice and Bob are both on call.

-- Session 1 (T1, Alice removing herself):
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
BEGIN;
SELECT COUNT(*) FROM doctors WHERE on_call = true AND shift = 'night';
-- Returns 2 — Alice and Bob. Safe to remove Alice.
UPDATE doctors SET on_call = false WHERE name = 'Alice';
COMMIT;

-- Session 2 (T2, Bob removing himself, concurrently):
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
BEGIN;
SELECT COUNT(*) FROM doctors WHERE on_call = true AND shift = 'night';
-- Returns 2 — Alice and Bob. Safe to remove Bob.
UPDATE doctors SET on_call = false WHERE name = 'Bob';
COMMIT;

-- Final state: NO doctors on call for the night shift.
-- Business rule violated. Both transactions committed successfully.
```

Write skew cannot occur under Two-Phase Locking (because the SELECT would take a shared lock on the range, blocking the other transaction's UPDATE). It can occur under Snapshot Isolation because the transactions do not modify the same row — there is no write-write conflict for the engine to detect. The only standard isolation level that prevents write skew is SERIALIZABLE, which in PostgreSQL is implemented via Serializable Snapshot Isolation (SSI) — a runtime monitor that tracks read-write dependencies and aborts transactions that would create a dangerous structure.

The real-world failure of write skew is in any application with a "at least N" or "no more than N" business rule that is checked via a COUNT query: bank withdrawal limits, conference room double-booking, inventory oversell, race conditions in account creation. The fixes are: (a) use SERIALIZABLE isolation (correct but slow, and requires retry logic), (b) use explicit locking (`SELECT COUNT(*) ... FOR UPDATE` to lock the range, preventing concurrent updates), or (c) restructure the schema so the constraint becomes a single-row update (e.g. a `shifts` table with a `doctor_count` column that is updated atomically). Option (c) is the most robust — it converts the multi-row invariant into a single-row invariant that the database can enforce.

### **Read Skew**: Transaction observes an inconsistent snapshot because it reads across a concurrent transaction's partial commit

Read skew (also called "inconsistent analysis") is a less common anomaly that occurs when a transaction reads two related rows that are being modified by a concurrent transaction, and sees one in the old state and the other in the new state. It is distinct from non-repeatable read because the inconsistency is *between* rows in the same statement, not between two reads of the *same* row.

```sql
-- Read skew example (allowed by READ COMMITTED):

-- T2 wants to transfer 100 from account 1 to account 2.
-- Initial state: account 1 = 500, account 2 = 100. Total = 600.

-- Session 1 (T1, the transfer):
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;  -- now 400
UPDATE accounts SET balance = balance + 100 WHERE id = 2;  -- now 200
COMMIT;

-- Session 2 (T2, reading the total) runs between T1's two UPDATEs:
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
BEGIN;
SELECT balance FROM accounts WHERE id = 1;   -- reads 400 (T1 committed)
SELECT balance FROM accounts WHERE id = 2;   -- reads 200 (T1 committed)
-- Total: 600. Correct!
COMMIT;

-- But if T2 runs between T1's first UPDATE (committed under
-- READ COMMITTED's autocommit semantics if T1 hadn't started
-- a transaction) and T1's second UPDATE, T2 would see 400 and
-- 100 = 500, missing the 100 in transit. This is read skew.
```

In practice, read skew within a single transaction under READ COMMITTED is rare because the transaction's reads happen one after another, and a concurrent transaction's commit window is short. The more common variant is **streaming read skew**: an analytical query that scans a large table while concurrent updates are happening sees some rows in the old state and some in the new state. PostgreSQL's REPEATABLE READ (snapshot isolation) prevents this — the scan sees a consistent snapshot of the table, taken at the scan's start. MySQL InnoDB's REPEATABLE READ does the same.

The real-world failure of read skew is in financial reports that sum across rows: if the report reads row 1 in the old state and row 2 in the new state, the total can be off by the amount of the in-flight transfer. The fix is REPEATABLE READ (which gives a snapshot) or `SET TRANSACTION READ ONLY` (which some engines use as a hint to take a snapshot at first read and hold it).

The deeper pattern across all six anomalies: **each anomaly is a specific way that concurrent transactions can produce incorrect results, and each is prevented by a specific isolation level or locking pattern.** The choice of isolation level is a trade-off: higher isolation prevents more anomalies but reduces concurrency. READ COMMITTED is the default in most engines because it prevents the obvious anomalies (dirty reads, mostly) at low cost, but it leaves the subtle ones (lost update, write skew) to the application. Production applications that handle money or inventory cannot stop at READ COMMITTED — they must add explicit locking or use SERIALIZABLE for the specific transactions that need it.

## Cross-Ecosystem Implementation

| Anomaly | Prevented by | Example failure |
|---|---|---|
| Dirty read | READ COMMITTED | Banking app reads mid-transfer balance |
| Non-repeatable read | REPEATABLE READ | Report reads inconsistent totals |
| Phantom read | REPEATABLE READ (PG), SERIALIZABLE (standard) | Audit report misses concurrent inserts |
| Lost update | REPEATABLE READ + retry, or FOR UPDATE, or atomic UPDATE, or version column | Concurrent debits lose one |
| Write skew | SERIALIZABLE only | "At least N" rule violated |
| Read skew | REPEATABLE READ (snapshot) | Cross-row total is off |

## Hands-On Exercise

```sql
-- Set up a test table
CREATE TABLE accounts (id int PRIMARY KEY, balance int);
INSERT INTO accounts VALUES (1, 500), (2, 100);

-- Demonstrate lost update (open two psql sessions)
-- Session 1:
BEGIN;
SELECT balance FROM accounts WHERE id = 1;  -- 500

-- Session 2:
BEGIN;
SELECT balance FROM accounts WHERE id = 1;  -- 500
UPDATE accounts SET balance = 550 WHERE id = 1;
COMMIT;

-- Session 1:
UPDATE accounts SET balance = 400 WHERE id = 1;
COMMIT;

SELECT balance FROM accounts WHERE id = 1;  -- 400 (550 lost)

-- Demonstrate write skew under REPEATABLE READ (PostgreSQL)
CREATE TABLE doctors (name text, on_call boolean, shift text);
INSERT INTO doctors VALUES ('Alice', true, 'night'), ('Bob', true, 'night');

-- Session 1:
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT count(*) FROM doctors WHERE on_call AND shift = 'night';  -- 2
UPDATE doctors SET on_call = false WHERE name = 'Alice';
COMMIT;

-- Session 2 (concurrent):
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT count(*) FROM doctors WHERE on_call AND shift = 'night';  -- 2
UPDATE doctors SET on_call = false WHERE name = 'Bob';
COMMIT;

-- Both committed. Now no doctor is on call.

-- Demonstrate that SERIALIZABLE prevents it:
RESET doctors to (Alice, true, night), (Bob, true, night).
-- Session 1:
BEGIN ISOLATION LEVEL SERIALIZABLE;
SELECT count(*) FROM doctors WHERE on_call AND shift = 'night';
UPDATE doctors SET on_call = false WHERE name = 'Alice';
-- Session 2:
BEGIN ISOLATION LEVEL SERIALIZABLE;
SELECT count(*) FROM doctors WHERE on_call AND shift = 'night';
UPDATE doctors SET on_call = false WHERE name = 'Bob';
-- Session 1: COMMIT;
-- Session 2: COMMIT;
-- ERROR: could not serialize access due to read/write dependencies
-- One transaction is aborted. Retry it.
```
