# 06.04.01. The ACID Mathematical Guarantees

## What This Is

ACID — Atomicity, Consistency, Isolation, Durability — is the four-property contract that a transactional database guarantees. The acronym was coined by Andreas Reuter and Theo Härder in 1983 as a pedagogical device, and it has stuck because every one of the four properties is independently meaningful and independently breakable. Each property is enforced by a specific mechanism: atomicity by the undo log, durability by the WAL and `fsync`, isolation by locks or snapshots, consistency by constraints and triggers. This note covers each property as a distinct engineering commitment, with the concrete mechanism and the production failure mode that results when the commitment is broken. The 06.04.02 and 06.04.03 notes drill into the isolation anomalies and the gap between ANSI SQL's spec and what real engines implement.

## The Details

### Atomicity: Indivisibility of state modifications via Undo logs and WAL

Atomicity is the guarantee that a transaction's effects are all-or-nothing: either every modification the transaction made is durable, or none of them are. There is no "half-applied" state. The mechanism is the WAL (write-ahead log, see 06.01.02) plus the undo log: the WAL records every modification as it happens, the undo log records the reverse operation, and on crash recovery the engine replays the WAL forward (redo) and then reverses any uncommitted transactions (undo).

```text
Atomicity timeline:
─────────────────────────────────────────────────────────────
T1: BEGIN;
    UPDATE accounts SET balance = balance - 100 WHERE id = 1;
    UPDATE accounts SET balance = balance + 100 WHERE id = 2;
    INSERT INTO transfers (from, to, amount) VALUES (1, 2, 100);
    -- CRASH here, before COMMIT --

On restart:
  WAL contains:
    LSN=100: BEGIN T1
    LSN=101: UPDATE accounts id=1, balance 500→400
    LSN=102: UPDATE accounts id=2, balance 100→200
    LSN=103: INSERT transfers (1, 2, 100)
    -- No COMMIT record for T1 --

  Recovery (ARIES):
    ANALYSIS: T1 has no COMMIT record → was active at crash.
    REDO: replay LSNs 101, 102, 103 to make on-disk state
          match what the WAL says (including T1's changes).
    UNDO: T1 was not committed. Reverse:
          - DELETE the transfers row (LSN=103 reverse)
          - UPDATE accounts id=2, balance 200→100 (LSN=102 reverse)
          - UPDATE accounts id=1, balance 400→500 (LSN=101 reverse)
          - Write CLRs (compensation log records) so undo is
            itself recoverable.

  Final state: as if T1 never ran. Atomicity preserved.
```

The WAL rule is what makes atomicity cheap: because the WAL is written before the data pages, and because the WAL is sequential (one fsync per commit, not one per page), the per-transaction overhead of atomicity is roughly one fsync. The undo log adds some additional disk I/O for storing the reverse operations, but undo records are also written sequentially to the WAL or a dedicated undo log.

The production failure mode is `fsync` being silently broken. On Linux, ext4 with `data=ordered` (the default) journals metadata but writes data blocks without journaling, and a power loss can leave the data file in a state where the WAL says "we wrote X" but the actual page on disk does not have X. The fix is `data=journal` (slower but fully journaled) or `fsync()` on the data file (which InnoDB does via `O_DIRECT` and explicit `fsync`). The deeper lesson: a database cannot be more durable than the underlying filesystem's `fsync` actually is, and `fsync` is a lie on some configurations — test it with `pg_test_fsync` (PostgreSQL) or the equivalent.

### Consistency: Guaranteeing all database state transitions adhere to defined schemas, constraints, and valid rules

Consistency is the guarantee that the database moves from one valid state to another — every constraint, trigger, and cascade is satisfied after every transaction. Where atomicity and durability are properties of the *storage engine* (enforced by WAL and fsync), consistency is a property of the *schema* (enforced by constraints) and the *application* (which must write transactions that respect business invariants). The database enforces the structural constraints; the application enforces the semantic ones.

```sql
-- Consistency enforced by the database:

-- Primary key uniqueness
ALTER TABLE users ADD PRIMARY KEY (id);

-- Foreign key referential integrity
ALTER TABLE orders
  ADD CONSTRAINT fk_orders_user
  FOREIGN KEY (user_id) REFERENCES users(id)
  ON DELETE RESTRICT ON UPDATE CASCADE;

-- CHECK constraints (PostgreSQL 9.6+, MySQL 8.0.16+)
ALTER TABLE accounts ADD CONSTRAINT positive_balance
  CHECK (balance >= 0);

-- NOT NULL constraints
ALTER TABLE users ALTER COLUMN email SET NOT NULL;

-- UNIQUE constraints
ALTER TABLE users ADD CONSTRAINT unique_email UNIQUE (email);

-- Triggers (when constraints can't express the rule)
CREATE TRIGGER enforce_max_transfer
  BEFORE INSERT ON transfers
  FOR EACH ROW
  WHEN (NEW.amount > 10000)
  SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Transfer too large';
```

When a transaction violates a constraint, the database rejects the offending statement (not the whole transaction — only the statement that failed). The application can catch the error and either retry with corrected data, or ROLLBACK the transaction and abort. The constraint check happens at statement end (or at COMMIT for deferrable constraints), so intermediate states within a transaction may violate constraints as long as the final state satisfies them.

The production failure mode is **constraint violations during bulk loads**. Loading a million rows with `INSERT INTO ... SELECT` or `LOAD DATA INFILE` runs every constraint check on every row, which can be slow. Some engines let you disable constraints for the load (`SET CONSTRAINTS ALL DEFERRED` in PostgreSQL, `SET FOREIGN_KEY_CHECKS = 0` in MySQL) — but this shifts the consistency burden to the application, which must verify the data after the load. The deeper lesson: consistency is not free, and the cost scales with the number of constraints and the number of rows. Schema design that adds constraints the application does not actually need (e.g. a CHECK constraint on a column that is always set by a trigger) wastes cycles on every insert.

The deeper point about consistency is that **the database can only enforce structural consistency** — primary keys, foreign keys, check constraints, uniqueness. It cannot enforce business invariants like "a user cannot transfer more money than they have earned this month" or "an order's shipping address must be in the user's country." Those are application-layer concerns, expressed in the transaction logic. The ACID "C" is therefore narrower than the everyday meaning of "consistency" — it is structural validity, not business correctness.

### Isolation: The degree to which concurrently executing transactions are invisible to one another

Isolation is the guarantee that concurrent transactions appear to execute serially — as if one ran completely before the other started. Full isolation is expensive (it requires locking everything, killing concurrency), so the SQL standard defines four levels of isolation that trade off isolation for concurrency. The four levels — READ UNCOMMITTED, READ COMMITTED, REPEATABLE READ, SERIALIZABLE — are covered in detail in 06.04.03. Here we cover the *mechanisms* the engine uses to implement isolation: locks and snapshots.

```text
Two implementation strategies for isolation:

1. TWO-PHASE LOCKING (2PL) — the classic approach
   - Each transaction acquires locks on rows it reads or writes.
   - "Growing phase": acquire locks, never release.
   - "Shrinking phase": after the transaction decides to commit
     (or abort), release all locks.
   - Strict 2PL: write locks held until commit; read locks may
     be released earlier (under READ COMMITTED).
   - Strong isolation, but locks cause blocking and deadlocks.

2. MULTI-VERSION CONCURRENCY CONTROL (MVCC) — the modern approach
   - Each transaction takes a snapshot of the database at start.
   - Readers see the snapshot; they don't take locks.
   - Writers create new versions; old versions are kept for
     in-flight snapshots.
   - No read locks, so reads never block writes.
   - Weaker than 2PL for some anomalies (write skew), but much
     better concurrency.

PostgreSQL: uses MVCC for reads (no read locks) + X locks for writes.
MySQL InnoDB: uses MVCC for reads + X locks + gap locks for writes
              under REPEATABLE READ; record locks only under
              READ COMMITTED.
Oracle: MVCC only (no read locks); READ COMMITTED and SERIALIZABLE
        only (no REPEATABLE READ option).
SQL Server: configurable — pessimistic (locking) or optimistic
            (snapshot, MVCC).
```

The isolation level is set per transaction in standard SQL: `SET TRANSACTION ISOLATION LEVEL READ COMMITTED;`. The level controls which anomalies are prevented (06.04.02 enumerates them): READ UNCOMMITTED prevents nothing, READ COMMITTED prevents dirty reads, REPEATABLE READ prevents non-repeatable reads, SERIALIZABLE prevents phantoms and write skew. The choice is a trade-off between correctness and concurrency: SERIALIZABLE is correct but slow; READ UNCOMMITTED is fast but can produce wrong results.

The production failure mode is choosing too low an isolation level and silently getting wrong data. A classic example: a banking app under READ COMMITTED where two concurrent transactions both read a balance of 500, both compute 500 - 100 = 400, both write 400 — the balance lost 100 instead of 200. This is the "lost update" anomaly (06.04.02), and it is prevented by REPEATABLE READ (in some engines) or by explicit `SELECT ... FOR UPDATE` (in all engines). The deeper lesson: READ COMMITTED is the default in PostgreSQL and SQL Server, but it is *not safe* for read-modify-write patterns. Use REPEATABLE READ with retry, or use explicit row locks.

### Durability: Unconditional persistence guarantees via disk sync (`fsync`) and non-volatile journals

Durability is the guarantee that once a transaction's COMMIT returns success, the transaction's effects survive every subsequent event — power loss, kernel panic, hardware failure — short of physical destruction of the storage media. The mechanism is the WAL (write-ahead log) plus `fsync`, plus physical redundancy.

```text
Durability stack (from bottom up):
┌────────────────────────────────────────────────────────────┐
│ 1. The storage device's write cache                        │
│    - SSDs have a small volatile DRAM cache (~1 GB).        │
│    - If the device's capacitor does not flush this cache   │
│      to NAND on power loss, fsync is a lie.                │
│    - Enterprise SSDs have "power loss protection" (PLP)    │
│      capacitors; consumer SSDs usually do not.             │
├────────────────────────────────────────────────────────────┤
│ 2. The filesystem's journal                                │
│    - ext4 with data=journal: every write is journaled.     │
│    - ext4 with data=ordered (default): metadata journaled, │
│      data written before metadata commits.                 │
│    - ext4 with data=writeback: metadata only; data may be  │
│      lost on crash. NEVER use for databases.               │
│    - XFS: similar to ext4 data=writeback by default.       │
├────────────────────────────────────────────────────────────┤
│ 3. The database's WAL                                      │
│    - Every commit writes a WAL record + fsync.             │
│    - The WAL is the source of truth for durability.        │
│    - PostgreSQL: synchronous_commit=on (default).          │
│    - InnoDB: innodb_flush_log_at_trx_commit=1 (default).   │
├────────────────────────────────────────────────────────────┤
│ 4. Replication                                             │
│    - Synchronous replication: commit waits for the replica │
│      to acknowledge. Zero data loss, higher latency.       │
│    - Asynchronous replication: commit returns immediately; │
│      replica catches up later. Lower latency, data loss    │
│      if primary fails before replica catches up.           │
├────────────────────────────────────────────────────────────┤
│ 5. Backup                                                  │
│    - Periodic full backup + continuous WAL archive.        │
│    - Restore: replay WAL from backup to any point in time. │
│    - This is the last line of defense; use it.             │
└────────────────────────────────────────────────────────────┘
```

The key tunables that trade durability for performance:

```sql
-- PostgreSQL: turn off fsync (NEVER in production)
SET synchronous_commit = off;   -- commits return without fsync
-- Can lose up to a few hundred ms of committed transactions on crash.

-- InnoDB: relax commit fsync
SET GLOBAL innodb_flush_log_at_trx_commit = 2;  -- fsync every second
-- Can lose up to 1 second of commits on crash.

-- InnoDB: relax the doublewrite buffer (NEVER in production)
SET GLOBAL innodb_doublewrite = 0;  -- skip doublewrite, faster but torn-page risk

-- MongoDB: write concern
db.users.insertOne({...}, { writeConcern: { w: 1, j: false } })
-- w: 1 = primary acknowledged (in memory); j: false = no journal fsync.
-- Default in MongoDB 4.0+ is w: 1, j: true (with journaling enabled).
```

The production discipline for durability has three parts. First, **test your `fsync`**: run `pg_test_fsync` (PostgreSQL) or `fio --end_fsync=1` to measure actual fsync latency; if it is much faster than the device spec, your fsync is being lies. Second, **use enterprise SSDs with power-loss protection** for the WAL device — the capacitor flushes the DRAM cache to NAND on power loss, making fsync actually durable. Third, **replicate synchronously to a second AZ** for the data that cannot be lost — the latency cost of synchronous replication is the price of "if the primary data center burns down, we still have the data." Most cloud databases (RDS, Cloud SQL, Aurora) offer this as a one-click option, and it should be the default for any data with regulatory or business value.

## Cross-Ecosystem Implementation

| Property | PostgreSQL | MySQL InnoDB | MongoDB |
|---|---|---|---|
| Atomicity mechanism | WAL + undo (in old tuple) | WAL + undo log | Journal (WiredTiger) |
| Durability default | `synchronous_commit=on` | `innodb_flush_log_at_trx_commit=1` | `j: true` per write concern |
| Consistency (constraints) | CHECK, FK, UNIQUE, triggers | CHECK (8.0.16+), FK, UNIQUE, triggers | Validator JSON schema, application-level |
| Default isolation | READ COMMITTED | REPEATABLE READ | Single-document: snapshot; multi-doc: none (transactions in 4.0+) |
| Serializable isolation | SSI (true serializable) | SERIALIZABLE (locking) | Multi-doc transactions, snapshot isolation |

## Hands-On Exercise

```sql
-- Set the isolation level for a transaction
BEGIN ISOLATION LEVEL READ COMMITTED;
-- or
BEGIN ISOLATION LEVEL REPEATABLE READ;
-- or
BEGIN ISOLATION LEVEL SERIALIZABLE;

-- Check the current isolation level
SHOW transaction_isolation;          -- PostgreSQL
SELECT @@transaction_isolation;      -- MySQL

-- Test durability: commit, then kill the database, then restart
BEGIN;
INSERT INTO accounts (id, balance) VALUES (99, 1000);
COMMIT;
-- Now: sudo kill -9 $(pgrep -u postgres)
-- Then: sudo systemctl restart postgresql
-- Then: SELECT * FROM accounts WHERE id = 99; -- the row should be there

-- Test atomicity: crash before commit
BEGIN;
INSERT INTO accounts (id, balance) VALUES (100, 1000);
-- Now: sudo kill -9 $(pgrep -u postgres)
-- Then: sudo systemctl restart postgresql
-- Then: SELECT * FROM accounts WHERE id = 100; -- the row should NOT be there

-- Test fsync performance
-- On the database server:
sudo pg_test_fsync
-- Compare the reported numbers against your storage device's spec.
-- If fsync is much faster than spec, your fsync is not actually
-- durable (caching somewhere is lying).
```
