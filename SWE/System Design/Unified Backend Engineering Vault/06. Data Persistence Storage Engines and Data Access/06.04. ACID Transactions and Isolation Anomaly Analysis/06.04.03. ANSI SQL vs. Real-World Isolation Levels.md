# 06.04.03. ANSI SQL vs. Real-World Isolation Levels

## What This Is

The ANSI SQL standard defines four isolation levels — READ UNCOMMITTED, READ COMMITTED, REPEATABLE READ, SERIALIZABLE — and specifies which anomalies each prevents. The catch is that no real database implements the standard exactly as written. PostgreSQL's `REPEATABLE READ` is really Snapshot Isolation (which prevents phantoms that the standard says RR should allow). MySQL InnoDB's `REPEATABLE READ` uses next-key locks (which also prevents phantoms). Oracle does not offer `REPEATABLE READ` at all — only `READ COMMITTED` and `SERIALIZABLE`. SQL Server has both `SNAPSHOT` and `SERIALIZABLE` as separate levels. This note covers what each level means in the standard, what each major engine actually implements, and the gap that catches production systems — particularly the write-skew anomaly that Snapshot Isolation (and therefore PostgreSQL's and InnoDB's `REPEATABLE READ`) does not prevent.

## The Details

### **Read Uncommitted**: Dirty reads permitted; no shared locks acquired

READ UNCOMMITTED is the SQL standard's lowest isolation level. The standard says: a transaction at this level can read data that another transaction has modified but not yet committed (dirty read). The engine takes no shared locks for reads; it reads whatever is in the buffer pool, committed or not.

```text
ANSI SQL READ UNCOMMITTED semantics:
─────────────────────────────────────────────────────────────
  Dirty read?              ALLOWED
  Non-repeatable read?     ALLOWED
  Phantom read?            ALLOWED
  Lost update?             ALLOWED
  Write skew?              ALLOWED

What engines actually do:
  PostgreSQL:        Silently treats as READ COMMITTED (no
                     dirty reads implemented).
  MySQL InnoDB:      Implements true dirty reads (reads
                     uncommitted rows from other transactions).
                     No locks acquired on reads.
  Oracle:            Not supported (READ COMMITTED is the floor).
  SQL Server:        Implements true dirty reads.
```

In practice, READ UNCOMMITTED is never used in production. The only legitimate use case is a monitoring or debug query that explicitly accepts potentially-wrong data in exchange for zero lock overhead — for example, a `SELECT COUNT(*) FROM big_table` to estimate row count where the exact count does not matter. Even in that case, the operator can usually get the same effect with `READ COMMITTED` plus `SET LOCAL statement_timeout = '100ms'` to bound the query's impact.

The reason no one uses READ UNCOMMITTED is that dirty reads produce nonsense data: a transaction that reads a row mid-update might see the new value of one column and the old value of another (if the update was not atomic at the row level — though in practice InnoDB's row updates are atomic). Even worse, a transaction that reads a row that is later rolled back has read a value that never officially existed. The ANSI standard includes READ UNCOMMITTED for completeness, but the engineering community has effectively rejected it.

### **Read Committed**: Dirty reads blocked; reads see snapshot taken at statement start (PostgreSQL) or read lock released immediately (MySQL)

READ COMMITTED is the default isolation level in PostgreSQL, SQL Server, and Oracle. The standard says: a transaction at this level cannot read uncommitted data (no dirty reads), but it can see committed data from concurrent transactions that committed during its execution (non-repeatable reads and phantoms are allowed).

```text
ANSI SQL READ COMMITTED semantics:
─────────────────────────────────────────────────────────────
  Dirty read?              PREVENTED
  Non-repeatable read?     ALLOWED
  Phantom read?            ALLOWED
  Lost update?             ALLOWED (the dangerous one)
  Write skew?              ALLOWED

Engine implementations:
  PostgreSQL:  Each statement takes a fresh snapshot at start.
               Reads see the latest committed values as of the
               statement's start. No read locks.
               Write locks (X locks) held until commit.
  MySQL InnoDB: Each consistent read uses the latest committed
               version of each row. Read locks released immediately
               after the statement completes (under READ COMMITTED,
               no gap locks are used).
               Write locks held until commit.
  Oracle:      Default. Statement-level snapshot, similar to PG.
  SQL Server:  Default. Uses locking by default; can be configured
               to use snapshot (RCSI — Read Committed Snapshot
               Isolation) which is MVCC-based like PostgreSQL.
```

The two implementations of READ COMMITTED — locking (InnoDB by default under RC, SQL Server without RCSI) and MVCC (PostgreSQL, Oracle, SQL Server with RCSI) — behave identically with respect to the standard's anomalies but differ in concurrency characteristics. The MVCC implementations do not take read locks at all, so reads never block writes. The locking implementations take read locks that are released immediately, so the blocking is brief but present.

The production significance of READ COMMITTED is that it is the level under which most applications run by default, and it is the level under which the **lost update** anomaly is possible (see 06.04.02). Any read-modify-write pattern under READ COMMITTED without explicit `SELECT ... FOR UPDATE` is vulnerable to lost update. This is the most common concurrency bug in production database applications, and it is the reason many teams upgrade specific transactions to REPEATABLE READ (with retry) or SERIALIZABLE.

### **Repeatable Read**: Non-repeatable reads blocked; reads see snapshot taken at transaction start (PostgreSQL) or Next-Key locks prevent gap inserts (MySQL)

REPEATABLE READ is where the implementations diverge most sharply from the standard. The SQL standard says: a transaction at this level cannot see non-repeatable reads (re-reading a row gives the same value), but phantoms are allowed (re-running a range query may return new rows). The standard's REPEATABLE READ is what is technically called "Cursor Stability" — read locks are held until the end of the transaction, but no range locks are taken.

```text
ANSI SQL REPEATABLE READ semantics (per the standard):
─────────────────────────────────────────────────────────────
  Dirty read?              PREVENTED
  Non-repeatable read?     PREVENTED
  Phantom read?            ALLOWED
  Lost update?             PREVENTED (under strict 2PL)
  Write skew?              ALLOWED

But what engines actually do:
─────────────────────────────────────────────────────────────
  PostgreSQL:  "REPEATABLE READ" is actually Snapshot Isolation.
               Each transaction takes a snapshot at the first
               statement and holds it for the transaction's
               lifetime. Sees a consistent view of the database
               as of the snapshot time. Phantoms are PREVENTED
               (because new rows inserted after the snapshot
               are invisible). Lost update is PREVENTED via
               first-committer-wins (the second transaction to
               commit a row update gets an error and must retry).
               Write skew is ALLOWED (this is the famous gap).

  MySQL InnoDB: "REPEATABLE READ" uses MVCC for consistent reads
               (snapshot at first read, like PostgreSQL) PLUS
               next-key locks for locking reads (SELECT FOR UPDATE,
               UPDATE, DELETE). Next-key locks prevent phantoms
               for locking reads (because the gap is locked).
               Lost update is PREVENTED (X locks serialise).
               Write skew is PREVENTED for locking reads (gap
               locks), but still possible for non-locking reads
               followed by writes.

  Oracle:      Does not offer REPEATABLE READ. The level
               between READ COMMITTED and SERIALIZABLE simply
               does not exist. Applications that need RR-level
               guarantees must use SERIALIZABLE.

  SQL Server:  Implements standard RR with locking. Has a
               separate SNAPSHOT level that is Snapshot Isolation
               (like PostgreSQL's RR).
```

The big surprise: PostgreSQL's `REPEATABLE READ` prevents phantoms, even though the SQL standard says RR should allow them. This is because PostgreSQL implements RR as Snapshot Isolation, which is *stronger* than the standard's RR. An application written to the standard's RR expectations would still work correctly under PostgreSQL's RR — it would just see fewer phantoms than expected, which is a strict improvement.

The bigger surprise: MySQL InnoDB's `REPEATABLE READ` also prevents phantoms, but via a completely different mechanism (next-key locks) that has very different concurrency characteristics. PostgreSQL's RR has no locks on reads, so reads never block writers — but write skew is possible. InnoDB's RR uses gap locks on locking reads, which prevents write skew but blocks concurrent inserts into the locked range. The two engines' "REPEATABLE READ" are not the same isolation level, even though both prevent phantoms.

### **Serializable**: Total anomaly elimination via Two-Phase Locking (2PL) or Serializable Snapshot Isolation (SSI)

SERIALIZABLE is the highest isolation level. The standard says: a transaction at this level sees a view of the database equivalent to having run serially (one at a time, in some order). All anomalies are prevented. The cost is the highest possible contention — under naive 2PL, the entire database is effectively serialised, killing concurrency.

```text
ANSI SQL SERIALIZABLE semantics:
─────────────────────────────────────────────────────────────
  Dirty read?              PREVENTED
  Non-repeatable read?     PREVENTED
  Phantom read?            PREVENTED
  Lost update?             PREVENTED
  Write skew?              PREVENTED

Engine implementations:
  PostgreSQL:  SSI (Serializable Snapshot Isolation). Uses
               MVCC for reads (no read locks) plus a runtime
               predicate-lock monitor that tracks read-write
               dependencies between transactions. Aborts any
               transaction that would create a "dangerous
               structure" — a cycle in the serialization graph.
               Performance: 10-30% slower than REPEATABLE READ
               on write-heavy workloads, near-zero overhead on
               read-heavy workloads. The only true serializable
               implementation that does not block reads.

  MySQL InnoDB: SERIALIZABLE converts all plain SELECTs to
               SELECT ... LOCK IN SHARE MODE (takes S locks).
               Effectively strict 2PL. Reads block writes,
               writes block reads. High contention. Most MySQL
               deployments never use SERIALIZABLE.

  Oracle:      SERIALIZABLE is snapshot-based (like PostgreSQL's
               RR) with conflict detection. A transaction that
               modifies a row modified by a concurrent
               transaction after its snapshot was taken gets
               ORA-08177 and must retry.

  SQL Server:  SERIALIZABLE uses range locks (key-range locks
               on indexes) to prevent phantoms. High contention.
               Has a separate SNAPSHOT level that is Snapshot
               Isolation without serializable guarantees.
```

The PostgreSQL SSI implementation is worth understanding because it is the only major engine that provides true serializability without locking reads. The idea (from Cahill et al., 2008): track "predicate locks" (really, read-write dependencies) and abort transactions whose dependency graph contains a cycle. A transaction that reads `WHERE balance > 1000` records a predicate lock on that range; if another transaction writes to a row in that range and commits, the first transaction's read is now "stale" relative to a serial order — and if a third transaction's writes would make the cycle complete, one of them is aborted. The performance cost is a 10-30% throughput reduction on write-heavy workloads, but no read blocking.

The production decision is rarely "use SERIALIZABLE everywhere" — the contention cost is too high for most OLTP workloads. The more common pattern is "use SERIALIZABLE for the specific transactions that need it" — e.g. the doctor-on-call write skew example from 06.04.02, where the business invariant is hard to enforce with constraints and the transaction count is low. Most production deployments stay at READ COMMITTED for the bulk of transactions and add explicit locking (`SELECT ... FOR UPDATE`) for the read-modify-write patterns that need protection.

### Comparative anomaly matrix across PostgreSQL vs. MySQL engines

The matrix below summarises what each engine actually prevents at each level. "✓" = prevented, "✗" = allowed, "△" = prevented for some access patterns. This is the table to consult when choosing an isolation level for a specific transaction.

```text
Isolation level implementation comparison:
═══════════════════════════════════════════════════════════════════

Engine         Level            Dirty  NonRep  Phantom  LostUpd  WriteSkew
─────────────────────────────────────────────────────────────────
PostgreSQL     READ UNCOMMITTED  ✓      ✗       ✗        ✗        ✗
               (silently = READ COMMITTED)

PostgreSQL     READ COMMITTED    ✓      ✗       ✗        ✗        ✗

PostgreSQL     REPEATABLE READ   ✓      ✓       ✓        ✓        ✗
               (= Snapshot Isolation)

PostgreSQL     SERIALIZABLE      ✓      ✓       ✓        ✓        ✓
               (= SSI)

MySQL InnoDB   READ UNCOMMITTED  ✗      ✗       ✗        ✗        ✗

MySQL InnoDB   READ COMMITTED    ✓      ✗       ✗        △        ✗
               (record locks only, no gap locks)

MySQL InnoDB   REPEATABLE READ   ✓      ✓       ✓        ✓        △
               (next-key locks prevent phantoms for
                locking reads; write skew possible for
                non-locking reads + writes)

MySQL InnoDB   SERIALIZABLE      ✓      ✓       ✓        ✓        ✓
               (all SELECTs → LOCK IN SHARE MODE)

Oracle         READ COMMITTED    ✓      ✗       ✗        ✗        ✗

Oracle         SERIALIZABLE      ✓      ✓       ✓        ✓        ✓
               (snapshot-based with conflict detection)
               -- no REPEATABLE READ option --

SQL Server     READ UNCOMMITTED  ✗      ✗       ✗        ✗        ✗

SQL Server     READ COMMITTED    ✓      ✗       ✗        ✗        ✗
               (locking) or RCSI (MVCC, no read locks)

SQL Server     REPEATABLE READ   ✓      ✓       ✗        ✓        ✗

SQL Server     SNAPSHOT          ✓      ✓       ✓        ✓        ✗
               (= Snapshot Isolation, opt-in)

SQL Server     SERIALIZABLE      ✓      ✓       ✓        ✓        ✓
               (range locks)
```

The three things to take from this matrix:

**1. PostgreSQL's REPEATABLE READ is stronger than the SQL standard requires.** It prevents phantoms (the standard says RR should allow them) and lost updates (the standard says RR may prevent them). This means an application written to the standard can run under PostgreSQL's RR and get *better* guarantees than expected — but the application still needs to handle the "could not serialize access due to concurrent update" error that PostgreSQL raises when it detects a lost-update conflict.

**2. MySQL InnoDB's REPEATABLE READ is also stronger than the standard, but in a different way.** It prevents phantoms for locking reads via next-key locks, at the cost of blocking concurrent inserts into the locked range. This means an application that runs under InnoDB's RR will see less write skew than under PostgreSQL's RR — but only if it uses locking reads (`SELECT ... FOR UPDATE`). Plain `SELECT`s under InnoDB RR use MVCC and have the same write-skew risk as PostgreSQL's RR.

**3. Write skew is the anomaly that REPEATABLE READ cannot prevent in any engine.** If your transaction has a "check a count, then write" pattern (at least N doctors on call, no more than N items in cart, no two users with the same email), you need SERIALIZABLE or explicit locking. This is the most common concurrency bug in production database applications, and the most common cause of "we got duplicate records" or "we oversold the inventory" incidents.

The production discipline: pick the lowest isolation level that prevents the anomalies your application cares about, and add explicit locking for the specific transactions that need more. READ COMMITTED is the right default for most transactions; REPEATABLE READ for transactions that need a consistent view across multiple statements; SERIALIZABLE (or `SELECT ... FOR UPDATE`) for transactions with check-then-write patterns. Never assume that "the default isolation level" is correct for every transaction — the default is a compromise, and your specific transaction may need more.

## Cross-Ecosystem Implementation

| Engine | Default level | True serializable? | Write-skew prevention at default |
|---|---|---|---|
| PostgreSQL | READ COMMITTED | Yes (SSI) | No (need SERIALIZABLE) |
| MySQL InnoDB | REPEATABLE READ | Yes (locking) | Partial (locking reads only) |
| Oracle | READ COMMITTED | Yes (snapshot) | No (need SERIALIZABLE) |
| SQL Server | READ COMMITTED | Yes (range locks) | No (need SERIALIZABLE) |
| MongoDB (multi-doc) | SNAPSHOT | No | No |

## Hands-On Exercise

```sql
-- Check the default isolation level
SHOW default_transaction_isolation;          -- PostgreSQL
SELECT @@global.transaction_isolation;       -- MySQL

-- Set the isolation level for a single transaction
BEGIN ISOLATION LEVEL SERIALIZABLE;
-- ... work ...
COMMIT;

-- Set the default for the session
SET SESSION CHARACTERISTICS AS TRANSACTION ISOLATION LEVEL SERIALIZABLE;

-- Set the default for the database (PostgreSQL)
ALTER DATABASE mydb SET default_transaction_isolation = 'serializable';

-- Demonstrate the write-skew gap under PostgreSQL REPEATABLE READ
-- (See 06.04.02 for the SQL — same example, but verify the outcome)

-- Demonstrate that SERIALIZABLE in PostgreSQL prevents write skew
-- Run the same two transactions as in 06.04.02, but with
-- BEGIN ISOLATION LEVEL SERIALIZABLE. One of them will get:
--   ERROR: could not serialize access due to read/write dependencies
--   among transactions
--   DETAIL: Reason code: Canceled on identification of a critical
--   relation during conflict detection.
-- Catch this error and retry the transaction.

-- In Java/Spring, the retry pattern is:
-- @Retryable(value = PessimisticLockingFailureException.class,
--            maxAttempts = 3, backoff = @Backoff(delay = 100))
-- @Transactional(isolation = Isolation.SERIALIZABLE)
-- public void removeDoctorFromCall(String name) { ... }

-- Demonstrate that InnoDB REPEATABLE READ with locking reads
-- also prevents write skew:
-- Session 1:
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
BEGIN;
SELECT COUNT(*) FROM doctors WHERE on_call = true FOR UPDATE;
-- Session 2 (concurrent):
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
BEGIN;
SELECT COUNT(*) FROM doctors WHERE on_call = true FOR UPDATE;
-- Session 2 BLOCKS (gap lock held by Session 1) until Session 1
-- commits. No write skew possible.
```
