# 06.05.02. Query Parsing Planning and Execution Stages

## What This Is

When a client sends `SELECT * FROM users WHERE email = 'alice@example.com'` to PostgreSQL, that string passes through five distinct stages before any data is returned: parsing (turn the string into an AST), semantic analysis (resolve table and column names to OIDs), rewriting (apply rules and views), planning (choose the cheapest execution plan), and execution (run the plan and return rows). The planner — the cost-based optimizer — is the most complex stage and the one whose decisions dominate query performance. This note covers the SQL lifecycle, the statistics the planner consults, the join order selection, and the join algorithms the planner chooses between. The next note (06.05.03) shows how to read the `EXPLAIN` output that exposes these decisions.

## The Details

### The SQL Lifecycle: Parsing → Semantic Analysis → Query Rewriting → Cost-Based Optimizer (CBO) → Execution Engine

Every SQL statement follows the same pipeline. The separation of stages is more than academic — each stage has its own data structure (parse tree, query tree, plan tree) and its own optimisations, and understanding the boundaries helps you reason about what the engine can and cannot do.

```text
PostgreSQL SQL statement lifecycle:
═══════════════════════════════════════════════════════════════════

1. PARSING (raw parser + analyzer)
   Input:  "SELECT * FROM users WHERE email = 'alice@example.com'"
   Output: Parse tree (a List of RangeVar, ColumnRef, A_Const nodes)
   
   The raw parser is a yacc-generated grammar that turns the
   string into a syntax tree. The analyzer (semantic analysis)
   resolves names: it looks up "users" in pg_class to get its
   OID, looks up "email" in pg_attribute to get its column
   number, resolves "*" to the list of columns, and checks
   types. Output: a Query tree.

2. REWRITING (rule system)
   Input:  Query tree
   Output: Query tree (possibly modified)
   
   Applies view expansion (a SELECT on a view becomes a SELECT
   on the underlying table), rule rewrites (CREATE RULE), and
   INSTEAD OF triggers. For a plain table SELECT, this stage is
   a no-op.

3. PLANNING (cost-based optimizer)
   Input:  Query tree
   Output: Plan tree
   
   The planner explores possible execution plans:
     - Which index to use (if any)?
     - What join order? (A⋈B⋈C or A⋈C⋈B or ...)
     - What join algorithm? (nested loop, hash, merge)
     - Where to sort, where to aggregate?
   It estimates the cost of each plan (in arbitrary "cost
   units") and picks the cheapest. The cost model uses
   statistics about the data (row counts, value distributions)
   stored in pg_class and pg_statistic.

4. EXECUTION (executor)
   Input:  Plan tree
   Output: Result rows (streamed to the client)
   
   The executor is a Volcano-style iterator model: each plan
   node has a `next()` function that returns one row at a
   time. The top-level node (e.g. a Sort) calls next() on its
   child, which calls next() on its child, and so on down to
   the leaves (Seq Scan, Index Scan). Each node transforms
   the rows it receives and returns them to its parent.
```

The Volcano execution model is the reason PostgreSQL can stream large result sets without buffering them in memory: a `SELECT * FROM billion_row_table` returns the first row before the last row is read, because the executor pipelines rows from leaf to root one at a time. The cost is per-row overhead — each row's transit through the plan tree involves function calls at every node, which adds up. Vectorised execution (which processes batches of rows at a time) is the modern alternative, used by ClickHouse, DuckDB, and others — PostgreSQL added vectorised aggregation in PG14 but is otherwise row-at-a-time.

The MySQL lifecycle is structurally similar: parser → name resolver → pre-processor → optimiser → executor. The optimiser differs in detail — MySQL has a smaller set of join strategies and a simpler cost model — but the conceptual pipeline is the same. MongoDB's aggregation pipeline is the analogous structure: each stage (`$match`, `$group`, `$lookup`) is a plan node, and the executor streams documents through them.

### Database Statistics: Histograms, correlation factors, distinct value counts (`n_distinct`), and `ANALYZE`

The planner's decisions are only as good as the statistics it consults. PostgreSQL stores per-table and per-column statistics in three system catalogs: `pg_class` (table-level: row count, page count), `pg_statistic` (column-level: most common values, histogram, correlation), and `pg_stats` (a user-readable view over `pg_statistic`). These statistics are populated by the `ANALYZE` command, which samples a random subset of rows and computes the statistics.

```text
Key statistics in pg_class and pg_statistic:
─────────────────────────────────────────────────────────────

pg_class (per table):
  relpages:  number of disk pages the table occupies
  reltuples: estimated number of rows
             (these two together give rows-per-page, used to
              estimate the cost of a sequential scan)

pg_statistic (per column, identified by (relid, attnum)):
  stadistinct: number of distinct values. Can be a positive
               integer (exact count) or a negative fraction
               (e.g. -0.5 means "half of the rows are distinct").
               Used to estimate the selectivity of an equality
               predicate: selectivity = 1 / stadistinct.
  most_common_vals (MCV): an array of the most frequent values.
  most_common_freqs: the frequencies of the MCVs.
              Together these estimate the selectivity of an
              equality on a common value (which is much higher
              than the average).
  histogram_bounds: an array of values that divide the column's
              distribution into N buckets of equal frequency.
              Used to estimate the selectivity of range predicates
              (<, >, BETWEEN).
  correlation: a number between -1 and 1 indicating how
              physically ordered the column is. +1 means the
              table is sorted in the column's order; 0 means
              random; -1 means reverse-sorted. Used to estimate
              the cost of an index scan (high correlation =
              fewer random heap reads).
```

```sql
-- Inspect the statistics for a table
SELECT relpages, reltuples FROM pg_class WHERE relname = 'users';
-- relpages | reltuples
--    12543 | 1.2e+06

-- Inspect the statistics for a column
SELECT * FROM pg_stats WHERE tablename = 'users' AND attname = 'email';
-- schemaname | tablename | attname | inherited | null_frac | n_distinct |
--   most_common_vals | most_common_freqs | histogram_bounds | correlation
-- public      | users      | email   | f         | 0.0        | -1        |
--   {alice@x.com,bob@y.com} | {0.001, 0.0008} | {a@..., m@..., z@...} | 0.95

-- Translation:
--   null_frac = 0:       no NULLs
--   n_distinct = -1:     every value is distinct (unique column)
--   MCV: top 2 values cover 0.18% of rows (column is near-unique)
--   histogram: 3 buckets
--   correlation = 0.95:  table is nearly sorted by email
```

The `correlation` statistic is what makes the planner choose between an index scan and a bitmap scan. If the table is highly correlated with the index (correlation near 1), an index scan reads the heap pages in roughly index order, which is sequential I/O — cheap. If the correlation is near 0 (random physical layout), an index scan reads the heap pages in random order — expensive. The planner then prefers a **bitmap scan**, which collects all the matching TIDs into a bitmap, sorts them by page number, and then reads the heap pages in physical order — converting random I/O back to sequential.

`ANALYZE` is what refreshes these statistics. It runs automatically via autovacuum (see 06.02.02), but it can also be run manually. The standard advice is to run `ANALYZE` after bulk loads or whenever the data distribution changes significantly. The `default_statistics_target` (default 100) controls how detailed the statistics are — higher means more accurate histograms but slower ANALYZE. For columns with skewed distributions, you can set per-column targets: `ALTER TABLE users ALTER COLUMN email SET STATISTICS 1000;`.

The production failure mode is **stale statistics**. After a bulk load or a large update, the statistics may not reflect the current data distribution, and the planner will choose bad plans — typically a seq scan on a table that should use an index, or a bad join order. The symptom: a query that was fast yesterday is slow today. The fix: `ANALYZE` the relevant tables, and check `pg_stat_user_tables.last_analyze` to see how recently it ran.

### Join order selection: The dynamic programming search over join orderings

When a query joins N tables, the planner must choose the order in which to join them. The number of possible join orderings is `(2N-2)! / ((N-1)! × 2^(N-1))` — for 3 tables, 12 orderings; for 5 tables, 1,035; for 10 tables, 17 billion. Searching all of them is infeasible for N > ~7. PostgreSQL uses dynamic programming (for N ≤ ~12) and a genetic algorithm (for larger N) to find a near-optimal order.

```text
Join order search (PostgreSQL dynamic programming):
─────────────────────────────────────────────────────────────

For a query joining tables A, B, C:

Level 1 (single tables):
  Cost(A) = scan cost of A
  Cost(B) = scan cost of B
  Cost(C) = scan cost of C

Level 2 (pairs):
  Cost(A⋈B) = Cost(A) + Cost(B) + join cost
  Cost(A⋈C) = ...
  Cost(B⋈C) = ...

Level 3 (all three):
  Cost((A⋈B)⋈C) = Cost(A⋈B) + Cost(C) + join cost
  Cost((A⋈C)⋈B) = ...
  Cost((B⋈C)⋈A) = ...

Choose the cheapest at level 3.

For each pair, the planner considers:
  - Join algorithm: nested loop, hash, merge
  - Join direction: outer vs inner
  - Whether to materialise the inner
  - Whether to sort for a merge join
```

The join cost depends on the join algorithm (next H3) and on the cardinality estimates — how many rows the planner thinks each intermediate result will have. If the cardinality estimate is wrong (because the statistics are stale or because the predicate is correlated in a way the planner cannot model), the chosen join order may be bad. The classic failure: the planner estimates a join will produce 1000 rows when it actually produces 1 million, then chooses a nested-loop join that does 1 million index lookups instead of a hash join that would have done one hash table build.

The `geqo_threshold` (default 12) parameter controls when PostgreSQL switches from exhaustive dynamic programming to the genetic algorithm. For queries with fewer than 12 tables, the planner explores all orders; for more, it samples. The genetic algorithm is usually within a few percent of optimal but can occasionally pick a very bad plan — set `geqo_threshold` higher if you have enough memory and CPU to afford exhaustive search.

### Join Algorithms: Nested Loop Join, Hash Join, Merge Join — when each is optimal

The three join algorithms have different cost characteristics. The planner chooses between them based on the cardinality estimates and the available indexes.

```text
NESTED LOOP JOIN
─────────────────────────────────────────────────────────────
for each row r in outer:
    for each row s in inner:
        if r.k = s.k: emit (r, s)

Cost: O(|outer| × |inner|) comparisons.

Best when:
  - outer is small (|outer| < ~1000)
  - inner has an index on the join key (so inner loop is
    O(log |inner|), not O(|inner|))
  - join condition is an equality or inequality

Worst when:
  - both sides are large (e.g. 1M × 1M = 1 trillion comparisons)

PostgreSQL EXPLAIN: "Nested Loop"
MySQL EXPLAIN: "NL" or "Nested Loop" in the "Extra" column


HASH JOIN
─────────────────────────────────────────────────────────────
build phase: read inner, hash each row on the join key, store in
             an in-memory hash table.
probe phase: read outer, hash each row on the join key, look up
             in the hash table, emit matches.

Cost: O(|inner| + |outer|), assuming the hash table fits in
memory (work_mem, default 4 MB).

Best when:
  - both sides are large
  - join condition is an equality (no range joins)
  - inner fits in work_mem (if not, the planner uses a "batched"
    hash join that spills to disk)

Worst when:
  - join condition is an inequality (cannot hash)
  - inner is much larger than work_mem (multiple batches, slow)

PostgreSQL EXPLAIN: "Hash Join" + "Hash"
MySQL EXPLAIN: "Hash join" (MySQL 8.0.18+; before that, MySQL
               only had nested loop, which is why PG was faster
               on analytics for years)


MERGE JOIN
─────────────────────────────────────────────────────────────
Both inputs must be sorted on the join key.
Scan both in parallel, emit matches.

Cost: O(|outer| log |outer| + |inner| log |inner|) if sorting
needed, or O(|outer| + |inner|) if both inputs are already
sorted (e.g. from indexed scans).

Best when:
  - both inputs are already sorted (e.g. from index scans)
  - the result must be sorted anyway (e.g. ORDER BY)
  - join condition is an equality or range

Worst when:
  - inputs are not sorted and the result need not be (then hash
    is usually faster than sort + merge)

PostgreSQL EXPLAIN: "Merge Join"
MySQL EXPLAIN: rare; usually appears as a sort + nested loop
```

The planner's choice between these three algorithms is the single most impactful decision in a multi-table query plan. A query that joins three large tables can be 100× faster with hash joins than with nested loops, or 10× faster with a merge join if the inputs are pre-sorted. The choice depends on cardinality estimates, which depend on statistics, which depend on `ANALYZE` having been run recently.

The production failure mode is a "plan regression": a query that was fast for months suddenly becomes slow because the planner's estimate of some intermediate cardinality changed (usually because of stale statistics or a data distribution shift). The symptom: the EXPLAIN output shows a Nested Loop where it used to show a Hash Join. The fix: run `ANALYZE` on the relevant tables; if that does not help, the statistics may need a higher `default_statistics_target` or per-column `SET STATISTICS`. The deeper fix is to use prepared statements carefully — the planner can use generic plans that ignore specific parameter values, which may be bad for some values.

## Cross-Ecosystem Implementation

| Stage | PostgreSQL | MySQL | MongoDB |
|---|---|---|---|
| Parser | yacc grammar | yacc grammar | MongoDB Query Language parser |
| Statistics catalog | pg_statistic, pg_class | InnoDB persistent stats, mysql.stats | $indexStats, collection metadata |
| Optimizer | Cost-based (dynamic programming + GEQO) | Cost-based (simpler) | Cost-based (rule + cost hybrid) |
| Execution | Volcano (row-at-a-time) | Volcano (row-at-a-time) | Document-at-a-time |
| Join algorithms | Nested loop, hash, merge | Nested loop (hash since 8.0.18) | $lookup (nested loop) |
| Auto-stats | autovacuum (ANALYZE) | Auto-stats (innodb_stats_auto_recalc) | Manual (collStats) |

## Hands-On Exercise

```sql
-- See the parse tree (PostgreSQL)
SET debug_print_parse = on;
SET client_min_messages = log;
SELECT * FROM users WHERE id = 1;
-- Look at the log output for the parse tree.

-- See the plan tree
SET debug_print_plan = on;
SELECT * FROM users WHERE id = 1;
-- The log shows the plan tree structure.

-- See statistics for a table
SELECT relname, relpages, reltuples FROM pg_class WHERE relname = 'users';

-- See statistics for a column
SELECT attname, n_distinct, null_frac, correlation,
       array_length(most_common_vals, 1) AS mcv_count
  FROM pg_stats WHERE tablename = 'users';

-- Force ANALYZE to refresh statistics
ANALYZE users;
ANALYZE (VERBOSE) users;

-- See when statistics were last refreshed
SELECT relname, last_analyze, last_autoanalyze
  FROM pg_stat_user_tables ORDER BY last_analyze DESC NULLS LAST;

-- Force the planner to use a specific join algorithm (for debugging)
SET enable_nestloop = off;
SET enable_hashjoin = on;
SET enable_mergejoin = off;
EXPLAIN SELECT * FROM users u JOIN orders o ON u.id = o.user_id;

-- See the cost of a plan with TIMING
EXPLAIN (ANALYZE, BUFFERS, TIMING)
  SELECT * FROM users u JOIN orders o ON u.id = o.user_id WHERE u.email = 'a@x.com';

-- Tune statistics target for a skewed column
ALTER TABLE users ALTER COLUMN status SET STATISTICS 1000;
ANALYZE users;

-- MySQL: see optimizer trace
SET optimizer_trace = "enabled=on";
SELECT * FROM users u JOIN orders o ON u.id = o.user_id WHERE u.email = 'a@x.com';
SELECT * FROM information_schema.OPTIMIZER_TRACE;
```
