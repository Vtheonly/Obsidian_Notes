# 06.05.03. Deconstructing Query Execution Plans

## What This Is

`EXPLAIN` is the engine's way of telling you what it plans to do; `EXPLAIN ANALYZE` is its way of telling you what it actually did. The output is dense and intimidating on first read, but it follows a fixed structure: each line is one plan node, indented to show parent-child relationships, annotated with cost and cardinality estimates (and, with ANALYZE, actual timings and row counts). This note walks through real EXPLAIN output, explains each node type (seq scan, index scan, bitmap scan, sort, hash aggregate, nested loop, hash join, merge join), and shows the patterns that reveal a missing index, a stale statistic, or a bad join order. The skill of reading EXPLAIN output is the single most valuable database performance skill — every production slowdown eventually requires reading one.

## The Details

### Generating plans: `EXPLAIN` (Estimated cost) vs. `EXPLAIN ANALYZE` (Actual execution run)

`EXPLAIN` shows the planner's *estimate* of what a query will cost, without running it. It is fast (just planning) and safe to run on production. `EXPLAIN ANALYZE` actually runs the query and reports the actual timings and row counts, alongside the estimates — this is more useful for debugging but it has side effects (the query runs, so any INSERT/UPDATE/DELETE actually modifies data; for safety, wrap in a transaction and ROLLBACK). `EXPLAIN (ANALYZE, BUFFERS)` adds buffer-pool hit/miss counts, which reveal whether the query is I/O-bound.

```sql
-- EXPLAIN: estimated plan, no execution
EXPLAIN SELECT * FROM users WHERE email = 'alice@example.com';
--                        QUERY PLAN
-- -----------------------------------------------------------
--  Seq Scan on users  (cost=0.00..25.00 rows=1 width=128)
--    Filter: (email = 'alice@example.com'::text)

-- EXPLAIN ANALYZE: actual execution with timing
EXPLAIN ANALYZE SELECT * FROM users WHERE email = 'alice@example.com';
--                            QUERY PLAN
-- -----------------------------------------------------------------
--  Seq Scan on users  (cost=0.00..25.00 rows=1 width=128)
--                    (actual time=0.020..1.234 rows=1 loops=1)
--    Filter: (email = 'alice@example.com'::text)
--    Rows Removed by Filter: 9999
--  Planning Time: 0.124 ms
--  Execution Time: 1.245 ms

-- EXPLAIN (ANALYZE, BUFFERS): add buffer hit/miss info
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM users WHERE email = 'alice@example.com';
--  Seq Scan on users  (cost=0.00..25.00 rows=1 width=128)
--                    (actual time=0.020..1.234 rows=1 loops=1)
--    Filter: (email = 'alice@example.com'::text)
--    Rows Removed by Filter: 9999
--    Buffers: shared hit=1245        ← all pages were in buffer pool
--  Planning Time: 0.124 ms
--  Execution Time: 1.245 ms
```

The key columns to read on every line:

```text
cost=0.00..25.00     Two numbers: startup cost (time to first row)
                     and total cost (time to last row). Units are
                     arbitrary "cost units" — by default,
                     seq_page_cost = 1.0 (one 8 KB page read
                     sequentially), so a cost of 25 means roughly
                     25 sequential page reads.

rows=1               The planner's estimate of how many rows this
                     node will produce. Compare to "actual rows"
                     to spot estimation errors.

width=128            Average row width in bytes. Used to estimate
                     memory usage for sorts and hashes.

actual time=X..Y     (ANALYZE only) Actual time to first row and
                     to last row, in milliseconds.

actual rows=1        (ANALYZE only) Actual rows produced. Compare
                     to estimated rows.

loops=1              (ANALYZE only) Number of times this node was
                     executed. For nested-loop inner nodes, this
                     can be much higher than 1.

Buffers: shared hit=N     (BUFFERS only) Number of buffer-pool
                          hits (no disk I/O).
        shared read=N     Number of buffer-pool misses (disk I/O).
        shared dirtied=N  Number of pages dirtied.
        shared written=N  Number of pages written.
```

The first comparison to make: **estimated rows vs. actual rows**. If the estimate is wildly off (estimated 1, actual 1,000,000), the planner made a bad decision based on bad statistics. The fix is usually `ANALYZE` on the relevant tables. The second comparison: **estimated cost vs. actual time**. The cost is unitless but should correlate with time; if a node has cost 1000 but actual time 0.1 ms, the cost model is miscalibrated for this query (often because the table fits in cache but the planner assumed disk reads).

### Scan Nodes: Sequential Scan (Table Scan), Index Scan, Index Only Scan, Bitmap Index Scan + Bitmap Heap Scan

The leaf of every plan is a scan node — the operation that reads rows from a table. The four scan types form a hierarchy of speed and selectivity.

```text
SEQ SCAN (Sequential Scan)
─────────────────────────────────────────────────────────────
Reads every page of the table, top to bottom, and applies the
filter to each row.

Best when:
  - The query returns a large fraction of the table (> ~10%)
  - The table is small (fits in cache)
  - No useful index exists

EXPLAIN: "Seq Scan on users (cost=0.00..25.00 rows=1 width=128)"
         "  Filter: (email = 'alice@example.com'::text)"
         "  Rows Removed by Filter: 9999"

Cost model: seq_page_cost × relpages = 1.0 × 25 = 25.


INDEX SCAN
─────────────────────────────────────────────────────────────
Descends the index B+tree to find matching entries, then for
each entry reads the heap page to fetch the row data.

Best when:
  - The query returns a small fraction of the table (< ~5%)
  - An index matches the predicate
  - The table is not highly correlated with the index
    (otherwise Index Only Scan is better)

EXPLAIN: "Index Scan using users_email_idx on users
            (cost=0.29..8.31 rows=1 width=128)"
         "  Index Cond: (email = 'alice@example.com'::text)"

Cost model: random_page_cost × index_pages + random_page_cost ×
            matched_rows (for heap lookups).
            random_page_cost defaults to 4.0 (4× seq_page_cost),
            reflecting the random/sequential I/O asymmetry on HDD.
            On SSD, set random_page_cost = 1.1 (random and sequential
            are nearly equal).


INDEX ONLY SCAN
─────────────────────────────────────────────────────────────
Descends the index B+tree, returns matching entries, and does
NOT visit the heap — because all needed columns are in the
index AND the visibility map says the pages are all-visible
(recently vacuumed).

Best when:
  - The query uses only columns that are in the index
  - The table has been vacuumed recently (visibility map is
    up to date)

EXPLAIN: "Index Only Scan using users_email_name_idx on users
            (cost=0.29..4.31 rows=1 width=64)"
         "  Index Cond: (email = 'alice@example.com'::text)"
         "  Heap Fetches: 0"     ← no heap lookups!

Cost model: random_page_cost × index_pages (no heap reads).


BITMAP INDEX SCAN + BITMAP HEAP SCAN
─────────────────────────────────────────────────────────────
Two-phase scan: first, the index is scanned and matching TIDs
are collected into a bitmap; second, the heap is scanned in
physical-page order (the bitmap is sorted by page number),
so the heap reads are sequential instead of random.

Best when:
  - The query returns a moderate fraction of the table (~5-25%)
  - The table is large and poorly correlated with the index
    (random heap reads would be expensive)
  - Multiple indexes can be combined (BitmapAnd, BitmapOr)

EXPLAIN: "Bitmap Heap Scan on users (cost=12.29..30.31 rows=10)"
         "  Recheck Cond: (status = 'active')"
         "  Filter: (created_at > '2024-01-01')"
         "  -> Bitmap Index Scan on users_status_idx"
         "        Index Cond: (status = 'active')"

Cost model: random_page_cost × index_pages (build bitmap) +
            seq_page_cost × pages_with_matches (read heap
            sequentially, deduplicating pages).
```

The planner's choice between these scan types is the most important decision in a single-table query. A query that should use an index but instead does a seq scan is the classic "missing index" symptom. A query that does an index scan but should do an index-only scan is the classic "missing covering index" symptom. A query that does a bitmap scan when an index scan would be better is the classic "stale statistics" symptom (the planner thinks the result is large when it is actually small).

The `enable_seqscan = off` (and similar for the other scan types) settings force the planner to prefer other scan types. This is a debugging tool, not a production setting — if disabling seq scan makes the query faster, you have found a missing index or a stats problem; fix the underlying issue rather than leaving the setting off.

### Join Algorithms

When the query joins two or more tables, the plan tree has a join node at each level. The join algorithm (nested loop, hash, merge) determines the shape of the tree and the cost.

```text
NESTED LOOP JOIN
─────────────────────────────────────────────────────────────
For each row of the outer, scan the inner for matches.

  Nested Loop
    -> Seq Scan on outer
    -> Index Scan on inner   (one lookup per outer row)

The inner is typically an index scan, so each iteration is a
single index lookup. Cost: O(|outer| × log|inner|).

EXPLAIN shape:
  Nested Loop  (cost=... rows=N width=...)
    -> Seq Scan on users u  (outer)
    -> Index Scan using orders_user_id_idx on orders o
         Index Cond: (user_id = u.id)

HASH JOIN
─────────────────────────────────────────────────────────────
Build a hash table on the inner, then probe with the outer.

  Hash Join
    -> Seq Scan on outer (probe side)
    -> Hash
         -> Seq Scan on inner (build side)

Cost: O(|inner| + |outer|), assuming hash fits in work_mem.

EXPLAIN shape:
  Hash Join  (cost=... rows=N width=...)
    Hash Cond: (u.id = o.user_id)
    -> Seq Scan on users u
    -> Hash
          -> Seq Scan on orders o

MERGE JOIN
─────────────────────────────────────────────────────────────
Both inputs must be sorted on the join key. Scan in parallel.

  Merge Join
    -> Sort
         -> Seq Scan on outer
    -> Index Scan on inner  (already sorted by index)

Cost: O(|outer| × log|outer| + |inner| × log|inner|) if sort
needed; O(|outer| + |inner|) if both inputs are pre-sorted
(indexed).

EXPLAIN shape:
  Merge Join  (cost=... rows=N width=...)
    Merge Cond: (u.id = o.user_id)
    -> Index Scan using users_pkey on users u   (sorted by id)
    -> Index Scan using orders_user_id_idx on orders o  (sorted)
```

### Nested Loop Join: Optimal for small inner sets with index lookups

The nested loop join is the simplest: for each row of the outer, look up matching rows in the inner. Its cost is `O(|outer| × cost_of_inner_lookup)`. If the inner has an index on the join key, each lookup is `O(log |inner|)`, making the total cost `O(|outer| × log |inner|)`. If the inner does not have an index, the inner must be fully scanned for each outer row — `O(|outer| × |inner|)` — which is catastrophic for large tables.

```sql
-- Nested loop with index lookup (fast)
EXPLAIN ANALYZE
  SELECT * FROM users u
  JOIN orders o ON u.id = o.user_id
  WHERE u.email = 'alice@example.com';
--                       QUERY PLAN
-- ----------------------------------------------------------------
--  Nested Loop  (cost=0.85..16.93 rows=1 width=128)
--                (actual time=0.025..0.028 rows=3 loops=1)
--    -> Index Scan using users_email_idx on users u
--         Index Cond: (email = 'alice@example.com'::text)
--         (actual time=0.013..0.014 rows=1 loops=1)
--    -> Index Scan using orders_user_id_idx on orders o
--         Index Cond: (user_id = u.id)
--         (actual time=0.008..0.011 rows=3 loops=1)
--  Execution Time: 0.052 ms
```

The `loops=1` on the outer Index Scan and `loops=1` on the inner Index Scan (because the outer returned 1 row) means the inner was executed once. If the outer had returned 1000 rows, the inner would have `loops=1000` — the actual time per loop is `actual time / loops`, which is what to compare to the cost estimate.

The production failure mode of nested loop is when the planner *thinks* the outer will return 1 row (so nested loop is cheap) but the outer actually returns 1 million rows. The inner is then executed 1 million times, each doing an index lookup, and the query takes seconds instead of milliseconds. This is usually caused by stale statistics on the outer table — `ANALYZE` is the fix.

### Hash Join: Building an in-memory hash table on the smaller set and probing with the larger set

The hash join is the workhorse for joining two large tables on an equality predicate. It builds an in-memory hash table on the smaller input (the "build side"), then streams the larger input (the "probe side") through, hashing each row and looking it up in the hash table. The cost is `O(|build| + |probe|)`, which beats nested loop's `O(|outer| × |inner|)` whenever both sides are large.

```sql
-- Hash join (both sides large, equality predicate)
EXPLAIN ANALYZE
  SELECT * FROM users u
  JOIN orders o ON u.id = o.user_id
  WHERE o.created_at > '2024-01-01';
--                          QUERY PLAN
-- -----------------------------------------------------------------
--  Hash Join  (cost=1000..25000 rows=50000 width=128)
--              (actual time=1.2..45.3 rows=48213 loops=1)
--    Hash Cond: (o.user_id = u.id)
--    -> Seq Scan on orders o
--         Filter: (created_at > '2024-01-01'::date)
--         Rows Removed by Filter: 5000
--         (actual time=0.1..20.0 rows=48213 loops=1)
--    -> Hash
--         (actual time=0.5..0.5 rows=10000 loops=1)
--         Buckets: 16384  Batches: 1  Memory Usage: 1024kB
--         -> Seq Scan on users u
--              (actual time=0.01..0.3 rows=10000 loops=1)
--  Execution Time: 47.8 ms
```

The hash join's `Batches: 1` means the hash table fit in `work_mem` (default 4 MB). If the hash table does not fit, the planner uses multiple batches: the build side is partitioned into N batches on disk, and the probe side is also partitioned, so each probe only needs to look in its own partition's hash table. Multi-batch hash joins are slower (disk I/O) but work on arbitrarily large inputs. Raising `work_mem` for the session (`SET work_mem = '64MB';`) before running the query can convert a 5-batch hash join into a 1-batch hash join, often a 5-10× speedup.

The production failure mode of hash join is running out of work_mem and spilling to disk excessively. The symptom in EXPLAIN ANALYZE is `Batches: 50` (or some high number) and a high actual time relative to the row count. The fix is raising `work_mem` (per-session, not globally — globally high `work_mem` × max_connections can exhaust RAM).

### Merge Join: Sorting both inputs and scanning linearly (optimal for large, pre-indexed sets)

The merge join requires both inputs to be sorted on the join key. If they are already sorted (e.g. from an index scan), the merge is `O(|outer| + |inner|)` — one pass through each. If they are not sorted, the planner inserts a Sort node, making the cost `O(|outer| log |outer| + |inner| log |inner|)`. Merge join is the only join algorithm that supports range predicates (`<`, `>`, `BETWEEN`) — hash join requires equality, nested loop supports anything but is slow for large inputs.

```sql
-- Merge join with both inputs pre-sorted by index
EXPLAIN ANALYZE
  SELECT * FROM users u
  JOIN orders o ON u.id = o.user_id
  ORDER BY u.id;
--                       QUERY PLAN
-- ----------------------------------------------------------------
--  Merge Join  (cost=0.56..12345.67 rows=100000 width=128)
--               (actual time=0.02..45.6 rows=100000 loops=1)
--    Merge Cond: (u.id = o.user_id)
--    -> Index Scan using users_pkey on users u
--         (actual time=0.01..5.2 rows=10000 loops=1)
--    -> Index Scan using orders_user_id_idx on orders o
--         (actual time=0.01..25.3 rows=100000 loops=1)
--  Execution Time: 50.1 ms
```

The merge join is optimal when both inputs are pre-sorted and the result must be sorted anyway (the merge preserves the sort order, so no separate Sort node is needed). It is also the right choice for very large joins that do not fit in `work_mem` (hash join would spill, merge join streams).

The diagnostic patterns to recognise in EXPLAIN output:

```text
MISSING INDEX (Seq Scan on a large table with a selective filter):
  Seq Scan on users  (cost=0.00..50000.00 rows=1 width=128)
    Filter: (email = 'alice@example.com'::text)
    Rows Removed by Filter: 9999999
  → The filter is selective (returns 1 row out of 10 million),
    but no index exists. Create one:
    CREATE INDEX idx_users_email ON users(email);

STALE STATISTICS (estimated rows wildly off from actual):
  Seq Scan on users  (cost=0.00..500.00 rows=1000000 width=128)
                      (actual time=0.1..50.0 rows=42 loops=1)
  → The planner estimated 1 million rows and chose a seq scan.
    The actual count was 42. An index would have been faster.
    Run ANALYZE users; to refresh statistics.

BAD JOIN ORDER (nested loop with a large outer):
  Nested Loop  (cost=... rows=1 ...)
               (actual time=0.1..15000.0 rows=1 loops=1)
    -> Seq Scan on big_table   (actual rows=1000000 loops=1)
    -> Index Scan on small_table  (loops=1000000)
  → The planner thought the outer would return 1 row but it
    returned 1 million, so the inner was executed 1 million
    times. This is a stats problem on big_table.

EXCESSIVE SORT (Sort spilling to disk):
  Sort  (cost=100000..102000 rows=100000 width=128)
        (actual time=500..5000 rows=100000 loops=1)
    Sort Key: created_at
    Sort Method: external merge  Disk: 128000kB
  → The sort did not fit in work_mem and spilled to disk.
    Raise work_mem:
    SET work_mem = '64MB';
```

The deeper skill in reading EXPLAIN is recognising these patterns quickly. The rule of thumb: read the plan bottom-up (innermost scans first, joins above, sort/aggregate above that, the root at the top). For each node, compare estimated rows to actual rows; if they differ by more than 10×, the planner was misled, and you should `ANALYZE` the relevant tables. Compare the cost of sibling nodes — the planner chose the cheaper one, but if you think it chose wrong, try disabling the chosen algorithm (`SET enable_nestloop = off`) and see if the alternative is actually faster.

## Cross-Ecosystem Implementation

| Concept | PostgreSQL | MySQL | MongoDB |
|---|---|---|---|
| Show estimated plan | `EXPLAIN` | `EXPLAIN` | `db.coll.find().explain()` |
| Show actual plan | `EXPLAIN ANALYZE` | (no equivalent; EXPLAIN always estimates) | `explain("executionStats")` |
| Show buffer I/O | `EXPLAIN (BUFFERS)` | (no direct equivalent; use PERFORMANCE_SCHEMA) | `explain("executionStats")` includes docsExamined |
| Show planning time | `EXPLAIN` includes "Planning Time" | (not shown) | (not shown) |
| Force join algorithm | `SET enable_hashjoin = off` | (no equivalent; optimizer hint `/*+ NO_HASH_JOIN */`) | (none) |

## Hands-On Exercise

```sql
-- Compare estimated vs. actual
EXPLAIN SELECT * FROM users WHERE email = 'alice@example.com';
EXPLAIN ANALYZE SELECT * FROM users WHERE email = 'alice@example.com';

-- See buffer I/O
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM users WHERE email = 'alice@example.com';

-- See verbose output (shows full schema, output columns)
EXPLAIN (VERBOSE) SELECT * FROM users WHERE email = 'alice@example.com';

-- Identify a missing index
EXPLAIN ANALYZE SELECT * FROM users WHERE lower(email) = 'alice@example.com';
-- If this is a Seq Scan, create a functional index:
-- CREATE INDEX idx_users_email_lower ON users(lower(email));

-- Identify a stale statistic
EXPLAIN ANALYZE SELECT * FROM big_table WHERE status = 'active';
-- If estimated rows is wildly different from actual rows:
ANALYZE big_table;
-- Re-run EXPLAIN ANALYZE to confirm the plan improved.

-- Identify excessive sort spilling
EXPLAIN ANALYZE SELECT * FROM big_table ORDER BY created_at;
-- If "Sort Method: external merge  Disk: NkB":
SET work_mem = '64MB';
EXPLAIN ANALYZE SELECT * FROM big_table ORDER BY created_at;
-- Should now be "Sort Method: quicksort  Memory: NkB"

-- Force a different join algorithm for debugging
SET enable_nestloop = off;
EXPLAIN ANALYZE SELECT * FROM users u JOIN orders o ON u.id = o.user_id;
RESET enable_nestloop;

-- Save the plan to a file
EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)
  SELECT * FROM users u JOIN orders o ON u.id = o.user_id;
-- The JSON output is suitable for visualisation in tools like
-- explain.depesz.com or Dalibo's pev2.

-- MySQL equivalent
EXPLAIN FORMAT=TREE
  SELECT * FROM users u JOIN orders o ON u.id = o.user_id;
EXPLAIN ANALYZE
  SELECT * FROM users u JOIN orders o ON u.id = o.user_id;
-- MySQL 8 EXPLAIN ANALYZE is similar to PostgreSQL's.
```
