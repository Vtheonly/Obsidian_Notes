# 06.05.01. Index Types and Physical Layouts

## What This Is

An index is a secondary data structure that trades write cost and storage space for read speed. The default B+tree index (covered in 06.01.03) is the right answer for most columns, but databases offer a zoo of specialised index types for cases the B+tree handles badly: hash indexes for equality-only lookups, GIN for full-text and JSONB, GiST for spatial and range, BRIN for massive ordered time-series, and the clustered index that makes InnoDB's primary key the table itself. This note covers each type, the physical layout it produces on disk, and the workload that justifies choosing it over a plain B+tree. The wrong index choice produces either a slow query (no index) or slow writes (too many indexes) — both are production failures you can avoid with the right physical layout decision.

## The Details

### Clustered Index (MySQL InnoDB Primary Key) vs. Non-Clustered / Heap Table with Secondary Indexes (PostgreSQL)

The fundamental architectural choice between MySQL InnoDB and PostgreSQL is how rows are stored on disk. InnoDB stores every table as a B+tree keyed by the primary key — the **clustered index**. The leaf pages of this B+tree contain the actual row data. There is no separate "heap" file; the table *is* the primary key index. PostgreSQL stores every table as a heap (an unordered sequence of pages), and every index — including the primary key — is a separate B+tree whose leaves contain pointers `(page_number, slot_number)` into the heap.

```text
InnoDB clustered index (the table IS the primary key B+tree):

Primary key B+tree on users.id:
                      [ 1000 | 2000 | 3000 ]
                     /        |       \       \
              [10..900]  [1000..1900]  [2000..2900]  [3000..3900]
                  ↓           ↓             ↓             ↓
   leaf: [id=10, name=..., email=..., ...]   ← actual row data
   leaf: [id=11, name=..., email=..., ...]   ← actual row data
   ...

Secondary index on users.email:
              [ a@x | f@k | p@q ]
                  ↓
   leaf: [email='alice@x.com', PK=42]   ← stores the PK, not a row pointer
   leaf: [email='bob@y.com',   PK=17]
   ...

To find a row by email:
   1. Look up 'alice@x.com' in the email index → get PK=42
   2. Look up PK=42 in the primary key index → get the row data
   (Two B+tree lookups. The second is called the "clustered
    index lookup" or "table lookup" or "bookmark lookup".)
```

```text
PostgreSQL heap table + secondary indexes:

Heap (no particular order):
   page 0, slot 0: [id=10, name=..., email=...]
   page 0, slot 1: [id=42, name=..., email=...]
   page 0, slot 2: [id=17, name=..., email=...]
   ...

Primary key index on users.id:
   leaf: [id=10, TID=(0,0)]   ← TID = (page, slot)
   leaf: [id=17, TID=(0,2)]
   leaf: [id=42, TID=(0,1)]
   ...

Secondary index on users.email:
   leaf: [email='alice@x.com', TID=(0,1)]
   leaf: [email='bob@y.com',   TID=(0,2)]
   ...

To find a row by email:
   1. Look up 'alice@x.com' in the email index → get TID=(0,1)
   2. Read page 0, slot 1 from the heap → get the row data
   (One index lookup + one heap read. No second index needed.)
```

The clustered design has two consequences. First, **range scans on the primary key are sequential**: `SELECT * FROM users WHERE id BETWEEN 100 AND 200` walks the primary B+tree's leaf chain, which is laid out in id order, and reads the rows directly — one sequential scan. In PostgreSQL, the same query walks the primary index's leaf chain (getting TIDs) and then randomly accesses the heap for each row — potentially many random reads if the heap is not in id order. Second, **secondary indexes are larger in InnoDB** because they store the primary key value (which can be a wide UUID) instead of a compact TID. A UUID primary key in InnoDB bloats every secondary index by 16 bytes per entry; a 100-million-row table with 5 secondary indexes pays 8 GB extra for the UUIDs.

The production lesson: in InnoDB, choose a narrow, monotonically increasing primary key (an `INT` or `BIGINT AUTO_INCREMENT`). A UUID primary key in InnoDB is the most common cause of index bloat and insert slowdowns — the random insert pattern causes page splits throughout the clustered B+tree, and the wide key bloats every secondary index. If you must use UUIDs, use UUID v7 (time-ordered) which gives the uniqueness of a UUID with the insert pattern of a serial. In PostgreSQL, the choice is less critical because the heap is unordered — but a monotonically increasing primary key still helps the heap pages cluster naturally.

### The Leftmost Prefix Rule in Composite (Multi-Column) Indexes

A composite index on `(last_name, first_name, birth_date)` is a B+tree whose keys are the tuple `(last_name, first_name, birth_date)`, sorted lexicographically. The index can be used for any query that constrains a leftmost prefix of these columns: `(last_name)` alone, `(last_name, first_name)`, or all three. It cannot be used for `(first_name)` alone or `(birth_date)` alone — those columns are not a leftmost prefix.

```text
Composite index on (last_name, first_name, birth_date):

Index entries (sorted):
  ('Adams', 'Alice', '1990-01-01')
  ('Adams', 'Alice', '1992-03-15')
  ('Adams', 'Bob',   '1985-06-20')
  ('Brown', 'Alice', '1991-07-07')
  ('Brown', 'Charlie', '1988-09-09')
  ('Smith', 'Dave', '1995-12-25')

Queries that USE the index:
  WHERE last_name = 'Adams'                       ✓ (1 column prefix)
  WHERE last_name = 'Adams' AND first_name = 'Bob' ✓ (2 column prefix)
  WHERE last_name = 'Adams' AND first_name = 'Bob'
    AND birth_date = '1985-06-20'                 ✓ (3 column prefix)
  WHERE last_name = 'Adams' AND birth_date > '1990' ✓ (uses last_name,
                                                     birth_date is a filter
                                                     on the matched range)
  WHERE last_name BETWEEN 'A' AND 'M'             ✓ (range scan on first column)

Queries that CANNOT use the index:
  WHERE first_name = 'Alice'                      ✗ (not a leftmost prefix)
  WHERE birth_date = '1990-01-01'                 ✗ (not a leftmost prefix)
  WHERE first_name = 'Alice' AND birth_date = ...  ✗ (skips last_name)
```

The leftmost prefix rule has three subtle behaviours worth knowing. First, **the order of columns in the WHERE clause does not matter** — the planner reorders predicates to match the index. `WHERE first_name = 'Alice' AND last_name = 'Adams'` uses the index `(last_name, first_name)` fine. Second, **a range predicate on a column breaks the index's usefulness for subsequent columns**: `WHERE last_name = 'Adams' AND first_name > 'A' AND birth_date = '1990-01-01'` uses the index for `last_name` and the range on `first_name`, but `birth_date` is a filter applied after fetching the matched rows — it cannot be used to narrow the index scan because the index is sorted by `birth_date` only within a fixed `first_name`, which is a range. Third, **an equality predicate on a column allows the index to be used for subsequent columns** — that is the common case.

The production lesson: order composite index columns by `equality, then range, then order-by`, with the most selective equality column first. For `WHERE status = 'active' AND created_at > '2024-01-01' ORDER BY created_at`, the right index is `(status, created_at)` — `status` is equality (uses the index fully), `created_at` is range (uses the index for the range scan within the matched status) and also satisfies the ORDER BY (the index is sorted by `created_at` within `status`). Getting this wrong means a seq scan or a sort, both of which kill performance on large tables.

### Covering Indexes and Index-Only Scans (eliminating table heap lookups via visibility maps)

A **covering index** is an index that contains all the columns a query needs, so the engine can answer the query from the index alone without visiting the heap. This is the fastest possible SELECT: one index scan, no random heap lookups. PostgreSQL calls this an "Index-Only Scan" and reports it in `EXPLAIN` as `Index Only Scan`; InnoDB reports it as `Using index` in the `Extra` column of `EXPLAIN`.

```sql
-- Covering index example (PostgreSQL)
CREATE INDEX idx_users_email_name ON users(email, name);

-- This query can be answered from the index alone:
SELECT name FROM users WHERE email = 'alice@example.com';
-- EXPLAIN: Index Only Scan on idx_users_email_name
--          Heap Fetches: 0   ← no heap lookups!

-- This query needs the heap (because 'created_at' is not in the index):
SELECT name, created_at FROM users WHERE email = 'alice@example.com';
-- EXPLAIN: Index Scan on idx_users_email_name
--          Heap Fetches: 1   ← one heap lookup to get created_at

-- InnoDB equivalent: include columns without indexing them
ALTER TABLE users ADD INDEX idx_email_name (email) INCLUDE (name);
-- MySQL 8.0+ supports "invisible" columns and functional indexes,
-- but the INCLUDE syntax is not native — emulate by adding name
-- as a second column in the index.
```

There is a catch in PostgreSQL: an index-only scan is only possible if the engine can verify that the indexed row is visible to the current transaction without consulting the heap. PostgreSQL's visibility information lives on the heap page (in the `infomask` bits of each tuple, see 06.02.02). The **visibility map** is a per-table bitmap that records "all rows on this page are visible to all transactions" — when this bit is set for a page, the engine can answer index-only scans for that page without consulting the heap. The visibility map is updated by VACUUM; pages that have not been vacuumed since their last modification have the bit clear, forcing heap fetches even for covering-index queries.

The production lesson: a covering index can be 10-100× faster than a non-covering index for a hot query, because it eliminates the random heap reads. The cost is write amplification (every INSERT/UPDATE/DELETE must update the wider index) and storage (the index is larger). The trade-off is worth it for queries that run thousands of times per second on a hot table. The `INCLUDE` clause in PostgreSQL 11+ and the equivalent functional-index trick in MySQL 8 let you add non-key columns to an index without them affecting the sort order — useful for queries that filter on one column and project a few others.

### Specialized Indexes

Beyond B+tree, databases offer specialised index types for workloads the B+tree handles poorly. Each type has a specific data structure and a specific use case where it dramatically outperforms a B+tree.

```text
Specialised index types in PostgreSQL:
─────────────────────────────────────────────────────────────
Hash index:        O(1) equality lookups, no range support.
                   Rebuilt from scratch on crash (pre-PG10,
                   they were unsafe after crashes; PG10+
                   they are WAL-logged and crash-safe).
                   Use case: `WHERE key = 'value'` with no
                   range scans. Smaller than B+tree for
                   fixed-width keys.

GIN index:         Generalized Inverted Index. Maps each
                   element (word, array element, JSONB key)
                   to a list of row TIDs that contain it.
                   Use case: full-text search
                   (`WHERE to_tsvector(content) @@ to_tsquery('postgres & index')`),
                   array containment (`WHERE tags @> ARRAY['red']`),
                   JSONB containment (`WHERE data @> '{"role":"admin"}'`).
                   Slow to update (each insert touches many
                   postings), fast to query.

GiST index:        Generalized Search Tree. A balanced tree
                   structure that can implement any
                   "balanced tree" semantics (not just
                   ordering). Used for spatial (PostGIS),
                   range types (tsrange, int4range), and
                   full-text (with trigrams).
                   Use case: `WHERE point <@ polygon`,
                   `WHERE tsrange && tsrange` (overlaps).

BRIN index:        Block Range Index. Stores the min and max
                   value of a column for each range of
                   consecutive pages (default 128 pages).
                   Tiny (a few KB for a multi-GB table).
                   Use case: massive, physically-ordered
                   time-series tables where you scan by
                   time range. `WHERE timestamp > '2024-01-01'`
                   can skip whole block ranges whose max
                   timestamp is older.

SP-GiST index:     Space-Partitioned GiST. For unbalanced
                   data structures like tries, quadtrees,
                   k-d trees. Use case: prefix matching
                   on text, IP address routing tables.
```

```text
Specialised index types in MySQL / MongoDB:
─────────────────────────────────────────────────────────────
MySQL InnoDB:
  Adaptive Hash Index: Built automatically by InnoDB when it
    detects hot equality lookups. A hash table mapping key →
    buffer pool address. Bypasses B+tree descent. Can be
    disabled (innodb_adaptive_hash_index=OFF) if it causes
    contention.
  FULLTEXT index: Inverted index for MATCH AGAINST queries.
    Uses a stopword list and the Porter stemmer.
  SPATIAL index (R-tree): For GEOMETRY columns. Used for
    `WHERE ST_Contains(polygon, point)`.

MongoDB:
  Single-field index: B+tree on one field.
  Compound index: B+tree on multiple fields (leftmost prefix
    rule, same as relational).
  Multikey index: Index on an array field; one index entry
    per array element.
  Text index: Full-text with stemming and stop words.
  2dsphere index: Geospatial, supports GeoJSON points/polygons.
  Wildcard index: Index all fields matching a pattern
    (`{$**: 1}`). Useful for polymorphic schemas.
```

The choice of index type is workload-driven. For point lookups on a hashable key, a hash index is smaller and faster than a B+tree. For full-text search, GIN (PostgreSQL) or FULLTEXT (MySQL) is the only option that scales — a `LIKE '%word%'` query without a full-text index is a sequential scan. For spatial, GiST (PostgreSQL with PostGIS) or a spatial index (MySQL/MongoDB) is mandatory. For massive ordered time-series, BRIN (PostgreSQL) gives index-assisted scans with almost no index storage overhead.

### Hash Indexes: O(1) exact equality lookups, no range support

A hash index uses a hash table to map keys to row locations. Lookups are O(1) on average (one hash, one bucket lookup, one comparison), which is asymptotically faster than a B+tree's O(log N). The catch is that hash indexes support *only* equality predicates (`=`, `IS`, sometimes `<>`) — they cannot do range scans (`<`, `>`, `BETWEEN`) or ordering (`ORDER BY`), because the hash function destroys the ordering of the keys.

```text
Hash index structure:

Hash function h(key) → bucket number
  Bucket 0: [key1 → TID1] → [key5 → TID5] → ...
  Bucket 1: [key2 → TID2] → ...
  Bucket 2: (empty)
  Bucket 3: [key3 → TID3] → [key7 → TID7] → ...
  ...

To find key=5:
  1. Compute h(5) = 0
  2. Walk bucket 0's chain, comparing keys: key1 (no), key5 (yes!)
  3. Return TID5.

To find key BETWEEN 1 AND 5:
  Cannot. The hash function scattered keys 1..5 across buckets;
  there is no way to find them without scanning every bucket.
```

PostgreSQL hash indexes were unsafe before version 10 (they were not WAL-logged and could be corrupted by a crash). Since PG10, they are crash-safe and a viable choice for pure equality lookups. They are still rarely used in practice because the B+tree's O(log N) is fast enough that the constant-factor improvement of hash is rarely worth giving up range support. The case for hash is when the keys are very wide (long strings or complex composite keys) and the B+tree's per-key storage cost becomes a problem — a hash index stores only the hash, not the key.

MongoDB does not have a separate hash index type by default; it has hashed sharding (which uses a hash of the shard key for distribution) but the underlying index is a B+tree. Redis uses hash tables internally for its SET and HASH data types but does not expose them as a "hash index" in the database sense.

The production lesson: hash indexes are a niche optimisation. Reach for them only when you have profiled a hot equality-lookup query, confirmed that the B+tree's depth (typically 3-4 levels) is the bottleneck, and the workload has no range scans. Otherwise, the B+tree is the right default — it handles equality and range with the same data structure.

### GIN (Generalized Inverted Indexes): JSONB, full-text search arrays

A GIN index is an inverted index: it stores, for each value (or token), the list of row TIDs that contain that value. This is the data structure that makes full-text search and JSONB containment queries fast. Without GIN, a query like `WHERE data @> '{"role":"admin"}'` would scan every row of the table and parse each JSONB document to check the containment.

```text
GIN index structure (for JSONB containment):

Table rows:
  Row 1: {"role": "admin", "name": "Alice"}
  Row 2: {"role": "user",  "name": "Bob"}
  Row 3: {"role": "admin", "name": "Charlie", "active": true}

GIN index (inverted):
  Posting list
  ─────────────
  "role"       → [1, 2, 3]   ← rows where "role" key exists
  "name"       → [1, 2, 3]
  "active"     → [3]
  "admin"      → [1, 3]      ← rows where any value is "admin"
  "user"       → [2]
  "Alice"      → [1]
  "Bob"        → [2]
  "Charlie"    → [3]
  "true"       → [3]

Query: WHERE data @> '{"role":"admin"}'
  → look up posting list for ("role", "admin")
  → intersection of "role" postings and "admin" postings = [1, 3]
  → fetch rows 1 and 3.
```

GIN indexes are slow to update because each insert touches every element of the inserted value: inserting `{"role": "admin", "name": "Alice"}` updates the posting lists for `"role"`, `"admin"`, `"name"`, and `"Alice"` — four index modifications for one row insert. PostgreSQL mitigates this with "pending lists" (the `gin_pending_list_limit` setting) that batch updates and merge them into the main index periodically. The trade-off: GIN is fast to query, slow to update, and benefits from a workload that is read-mostly.

The production use cases for GIN: full-text search (`to_tsvector(content) @@ to_tsquery('postgres & index')`), array containment (`WHERE tags @> ARRAY['red', 'large']`), JSONB containment (`WHERE data @> '{"role":"admin"}'`), and trigram similarity (`WHERE content % 'postgres'` for fuzzy matching). All of these are O(N) without GIN (full table scan with per-row evaluation) and O(1) or O(log N) with GIN. A 100-million-row JSONB table without GIN is unusable for ad-hoc queries; with GIN, it is fast.

### GiST (Generalized Search Tree): Geometric, spatial (PostGIS), and range types

GiST is a balanced tree framework that can implement any "balanced search tree" semantics — not just the strict ordering of a B+tree. A GiST index defines two operations: `consistent(key, query)` returns true if a row in the subtree *might* match the query, and `union(key1, key2)` computes the key that covers both subtrees. With these, you can index any data structure that has a meaningful "might contain" predicate.

```text
GiST index for spatial data (PostGIS geometry):

Each index entry is a bounding box (a rectangle). The tree
organises rectangles so that each node's bounding box covers
all the rectangles in its subtree. A spatial query like
"find all points inside this polygon" descends the tree,
skipping subtrees whose bounding box does not intersect the
query polygon.

Index:
                 [bbox covering all points]
                /            |            \
       [NW quadrant]   [NE quadrant]   [SW quadrant]
        /     \          /     \         /     \
     point   point    point   point   point   point

Query: WHERE ST_Contains(polygon, geom)
  1. Test root bbox vs polygon — intersects, descend.
  2. Test NW quadrant vs polygon — no intersection, SKIP.
  3. Test NE quadrant vs polygon — intersects, descend.
  4. ... etc.
```

The classic GiST use case is PostGIS: spatial queries on geographic data. `SELECT * FROM restaurants WHERE ST_DWithin(location, ST_Point(-122.4, 37.8), 1000)` (find restaurants within 1 km of a point) is fast with a GiST index on `location`, and is a sequential scan without one. GiST also supports range types (`tsrange`, `int4range`, `daterange`) — queries like `WHERE availability && tsrange('[2024-01-01, 2024-01-31]')` (overlaps) benefit.

### BRIN (Block Range Index): Ultra-compact indexes for massive, physically ordered append-only time-series data

BRIN is the most underused index type in PostgreSQL. It stores, for each range of consecutive pages (default 128 pages = 1 MB), the minimum and maximum value of the indexed column. The index is tiny — a few KB for a multi-GB table — because it stores only two values per MB of table data.

```text
BRIN index structure for a time-series table:

Table pages (each 8 KB, ~200 rows of timestamps):
  Page 0:   rows with timestamp in [2024-01-01, 2024-01-02]
  Page 1:   rows with timestamp in [2024-01-02, 2024-01-03]
  Page 2:   rows with timestamp in [2024-01-03, 2024-01-04]
  ...
  Page 127: rows with timestamp in [2024-04-30, 2024-05-01]
  Page 128: rows with timestamp in [2024-05-01, 2024-05-02]
  ...

BRIN index (one entry per 128 pages = 1 MB):
  Block range 0 (pages 0-127):    min=2024-01-01, max=2024-04-30
  Block range 1 (pages 128-255):  min=2024-05-01, max=2024-08-31
  Block range 2 (pages 256-383):  min=2024-09-01, max=2024-12-31
  ...

Query: WHERE timestamp > '2024-07-01'
  1. Scan BRIN entries:
     Block range 0: max=2024-04-30 < 2024-07-01 → SKIP (no rows match)
     Block range 1: max=2024-08-31 ≥ 2024-07-01 → must read these pages
     Block range 2: max=2024-12-31 ≥ 2024-07-01 → must read these pages
  2. Read pages in block ranges 1 and 2, filter individual rows.
```

BRIN only works when the table is physically ordered by the indexed column. This is naturally true for time-series data appended in arrival order: the timestamps increase monotonically as rows are inserted, so the physical page order matches the timestamp order. If the table is unordered (e.g. UUID-keyed with random inserts), BRIN is useless — every block range has a wide min-max, and every query must read every block.

The production use case: a multi-terabyte time-series table where you cannot afford a full B+tree index (which would be tens of GB). BRIN gives you index-assisted range scans for almost no storage cost. The trade-off is that BRIN does not help with point lookups — `WHERE timestamp = '2024-07-15 14:23:01'` still scans all the pages in the matching block range, because BRIN only tells you the min and max, not which specific pages have which values. For point lookups, you still need a B+tree; for range scans on ordered data, BRIN is dramatically more space-efficient.

## Cross-Ecosystem Implementation

| Index type | PostgreSQL | MySQL InnoDB | MongoDB |
|---|---|---|---|
| B+tree (default) | btree | BTREE | 1 (ascending) / -1 (descending) |
| Hash | hash | (use InnoDB AHI) | hashed sharding only |
| Clustered | (heap; no clustered) | Yes (PK is table) | Yes (`_id` and any `clustered: true`) |
| Full-text | GIN (tsvector) | FULLTEXT | text index |
| Spatial | GiST (PostGIS) | SPATIAL (R-tree) | 2dsphere |
| JSONB | GIN (`@>`, `?`, `?|`) | (functional, JSON_VALUE) | wildcard, multikey |
| Range/block | BRIN | (none) | (none) |
| Covering | INCLUDE clause | (clustered covers; or use functional) | covered queries |

## Hands-On Exercise

```sql
-- PostgreSQL: see all indexes on a table
SELECT indexname, indexdef FROM pg_indexes WHERE tablename = 'users';

-- See index size and usage
SELECT relname, indexrelname, idx_scan, idx_tup_read, idx_tup_fetch,
       pg_size_pretty(pg_relation_size(indexrelid)) AS size
  FROM pg_stat_user_indexes
  WHERE relname = 'users';

-- Create a covering index
CREATE INDEX idx_users_email_include_name ON users(email) INCLUDE (name);
EXPLAIN (ANALYZE, BUFFERS)
  SELECT name FROM users WHERE email = 'alice@example.com';
-- "Index Only Scan" with "Heap Fetches: 0" means the index covered.

-- Create a GIN index on JSONB
CREATE INDEX idx_users_data ON users USING gin (data);
EXPLAIN SELECT * FROM users WHERE data @> '{"role":"admin"}';

-- Create a BRIN index on time-series
CREATE INDEX idx_events_ts_brin ON events USING brin (timestamp)
  WITH (pages_per_range = 128);
EXPLAIN SELECT * FROM events WHERE timestamp > '2024-07-01';

-- MySQL: see index usage
SELECT index_name, rows_read FROM information_schema.INNODB_SYS_INDEXES i
  JOIN information_schema.INNODB_SYS_TABLES t USING (TABLE_ID)
  WHERE t.NAME = 'your_db/users';

-- MySQL: covering index (extra column appended)
ALTER TABLE users ADD INDEX idx_email_name (email, name);
EXPLAIN SELECT name FROM users WHERE email = 'alice@example.com';
-- "Extra: Using index" means covering.

-- MongoDB: see index info
db.users.getIndexes()
db.users.createIndex({ email: 1 }, { unique: true })
db.users.createIndex({ "address.city": 1, "address.state": 1 })
db.users.createIndex({ "$**": 1 })  -- wildcard
```
