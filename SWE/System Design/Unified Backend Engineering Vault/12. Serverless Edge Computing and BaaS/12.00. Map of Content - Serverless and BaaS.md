# 12.00. Map of Content: Serverless and BaaS

## Overview

This section covers **12. Serverless Edge Computing and BaaS**. It is part of the unified backend engineering vault described in [[00.01. Master Architectural Mental Model]]. The notes below are organized by concept, not by framework. Each concept is taught once at the conceptual level, then implemented deeply in the Spring Boot anchor stack, then rapidly translated into Express, Django, Flask, and Laravel as deltas.

Section 12 is the layer where compute stops being something you babysit and starts being something you invoke. Sections 02–04 taught the kernel, the runtime, and the threading primitives that an always-on server is built on. Section 05 taught the framework abstractions (routing, middleware, DI) that run on top of that server. Section 10 taught the container, the orchestrator, and the ingress load balancer that run the always-on server in production. Section 11 taught how to observe it. **Section 12 inverts the model**: instead of an always-on process inside a container inside a pod, you get a function that exists only for the duration of one invocation, billed by the millisecond, scaled by the cloud provider, with no server to babysit and no scale to plan for.

The trade-offs introduced here are real and frequently underestimated. **Cold starts** add 50ms–3s of latency to the first invocation after an idle period — a budget that breaks the sub-100ms p99 SLO of an interactive web app. **Ephemeral state** means in-process caches, in-memory sessions, and long-lived database connections are all forbidden — every invocation may hit a different instance. **Connection limits** become a hard ceiling: 1000 concurrent Lambda invocations × 1 Postgres connection each = 1000 connections, and Postgres dies at ~100. **Vendor lock-in** is structural: a Cloudflare Worker written against the `FetchEvent` API cannot run on AWS Lambda without a rewrite, because the runtime model is different.

This MOC indexes four sub-sections. **12.01** covers the execution lifecycle and the architectural constraints of ephemeral compute. **12.02** covers V8 isolates — the lightweight alternative to containers that powers Cloudflare Workers and Vercel Edge Functions, with sub-millisecond cold starts. **12.03** covers Backend-as-a-Service platforms (Supabase, Firebase) that push the entire backend into a managed platform with client-to-database direct access. **12.04** covers the architectural decision matrix — when to choose serverless, when to choose BaaS, when to choose a traditional server, and how to solve the connection-limit problem that kills naive serverless + Postgres deployments.

## Section Map

### 12.01. Ephemeral Compute Models and Cold Starts

- [[12.01.01. Serverless Execution Lifecycle]] — The end-to-end lifecycle of a serverless invocation: event arrives → provider provisions a sandbox (Firecracker MicroVM on AWS Lambda, gVisor on Cloud Run, V8 isolate on Cloudflare Workers) → runtime boots → function code loads (imports evaluated, global initializers run, DB connections opened) → handler executes → handler returns → runtime freezes (no CPU, no memory cost to customer on most platforms) → next event thaws the same sandbox → handler re-runs without cold start. Covers cold-start numbers per runtime (Node.js ~50ms, Python ~200ms, JVM ~2–3s, Go ~50ms, Rust ~20ms, V8 isolate <5ms), the per-invocation + per-GB-second billing model, and the mitigation patterns: provisioned concurrency (AWS), min instances (Cloud Run), and warm instances.
- [[12.01.02. Architectural Constraints of Ephemeral Compute]] — The four hard constraints that change how you write code for serverless: (1) no in-process state — every invocation may hit a different instance, so caches and sessions must move to Redis or the DB; (2) no long-lived connections — a Postgres pool of 10 connections per instance × 1000 instances = 10,000 connections, killing the DB (use PgBouncer, RDS Proxy, or an HTTP driver); (3) no background threads — the runtime freezes between invocations, so a `setTimeout` after `return` never fires; (4) hard ceiling on execution time (Lambda 15 min, Cloud Run 60 min, Workers 30s CPU) and on package size (Lambda 250MB unzipped, Cloud Run 8GB, Workers 10MB after bundling). Each constraint has a production failure mode that this note names.

### 12.02. Edge Compute and V8 Isolates

- [[12.02.01. V8 Isolates vs. Container Virtualization]] — Why Cloudflare Workers and Vercel Edge Functions run JavaScript in a V8 isolate (a V8 engine instance with its own heap, ~50KB memory overhead, startup in microseconds) instead of a container (a Linux namespace + cgroup, ~MBs memory overhead, startup in seconds). Covers the isolation boundary trade-off (V8's sandbox vs Linux namespaces — V8 isolates share the same kernel and the same process, so a V8 escape is a kernel-level compromise while a container escape is also a kernel-level compromise but at least starts from a separate namespace), and the API limitation (no Node.js native modules, no `fs`, no `child_process`, no TCP/UDP sockets — only Web Standard APIs like `fetch`, `Request`, `Response`, `TransformStream`, `Crypto`).
- [[12.02.02. Edge Runtime Platforms Vercel and Cloudflare]] — Concrete deep dive on the three production edge platforms. **Cloudflare Workers**: 300+ global POPs, V8 isolates, KV for eventually-consistent state, Durable Objects for strongly-consistent coordination, R2 for S3-compatible object storage, D1 for SQL. **Vercel Edge Functions**: V8 isolates, runs at the edge in 18+ regions, integrates natively with Next.js middleware. **Deno Deploy**: V8 isolates, Deno runtime, TypeScript native, runs globally. Real code for each platform (`addEventListener('fetch', ...)` for Workers, `export default function handler(req: Request) {...}` for Vercel Edge), and the production use cases: auth at edge (validate JWT before hitting origin), A/B testing (route by cookie), geo-routing (serve from nearest region), and image optimization (transform on the way through).

### 12.03. Backend-as-a-Service Architecture

- [[12.03.01. Supabase Architecture]] — The open-source Firebase alternative built on PostgreSQL. Architecture is: Postgres DB → PostgREST (auto-generates a REST API from the schema) → GoTrue (JWT-issuing auth service) → Realtime (Elixir Phoenix cluster that tails Postgres WAL via logical replication and broadcasts row changes over WebSocket) → Storage (S3-compatible, signed URLs) → Edge Functions (Deno V8 isolates for server-side logic). The killer feature: Row-Level Security (RLS) policies written in SQL are enforced by Postgres itself on every query, so a client SDK talking directly to PostgREST cannot read another user's rows even though no application server validates the request. Real SQL for a typical `posts` table with `auth.uid() = user_id` RLS policies.
- [[12.03.02. Firebase Architecture]] — Google's BaaS, the original. Architecture is: Cloud Firestore (NoSQL document DB, real-time sync, offline persistence, proprietary sync protocol over WebSocket) + Firebase Auth (email/password, OAuth, phone, anonymous) + Cloud Storage (object storage) + Cloud Functions (Node.js, Python, Go runtimes — full containers, not V8 isolates) + Cloud Messaging (FCM push notifications) + Analytics + Crashlytics. The Firebase SDK is embedded in the client app and talks directly to Firestore, bypassing any backend server you control. Security Rules — a declarative JSON-like language evaluated on every Firestore/Storage operation — replace application-layer authorization. Real Security Rules code for a `messages` collection.

### 12.04. Architectural Decision Trade-Offs

- [[12.04.01. The Backend Architecture Selection Matrix]] — The decision tree for choosing between (a) traditional long-running server (high sustained traffic, full control, low latency, predictable cost), (b) serverless function (event-driven, sparse or bursty traffic, simple request-response, sub-15-minute jobs), (c) BaaS (frontend-only team, simple CRUD, real-time sync, mobile-first), (d) edge function (geographic distribution, sub-100ms p99 globally, simple logic, no heavy deps). Includes a worked cost comparison: 100M requests/month on Lambda + API Gateway (~$250) vs a $50/month EC2 t3.small that handles the same load — and the inflection point where the curve flips. Covers the vendor lock-in trade-off: serverless locks you into an event schema, BaaS locks you into a data model, edge functions lock you into a runtime subset.
- [[12.04.02. Solving Serverless Database Connection Limits]] — The hardest production problem in serverless: 1000 concurrent Lambda invocations × 1 Postgres connection each = 1000 connections, and Postgres' default `max_connections=100` dies long before that. Four solutions, with real config: (1) PgBouncer in transaction pooling mode (`pool_mode = transaction`, `max_client_conn = 1000`, default `pool_size = 25`) — multiplexes 1000 client connections onto 25 server connections; (2) HTTP-based DB drivers (Supabase's PostgREST, Neon's HTTP driver, Prisma Accelerate) — no connection concept at all, each query is one HTTP request; (3) managed pooler as a service (AWS RDS Proxy, Cloudflare Hyperdrive) — drop-in replacement, no ops; (4) the DynamoDB / Aurora Serverless pattern — the DB itself speaks HTTP, no connection concept exists. Real PgBouncer config for serverless.

## Conceptual Roadmap

The four sub-sections form a progression from "how does serverless work" to "how do you decide whether to use it." Read them in order:

```
   12.01 Lifecycle & Constraints      ← the mechanical truth of one invocation
              │
              │  (every constraint here drives every choice in 12.02–12.04)
              ▼
   12.02 V8 Isolates & Edge          ← the lightest-weight serverless option,
              │                        solves the cold-start constraint by
              │                        switching isolation mechanism entirely
              ▼
   12.03 Backend-as-a-Service        ← solves the no-connection-pool constraint
              │                        by removing the application server
              │                        entirely; client talks to DB directly
              ▼
   12.04 Decision Matrix &           ← when each pattern wins, and how to fix
        Connection Limits              the connection problem when you cannot
                                         move to BaaS
```

**12.01** is the foundation. The serverless execution lifecycle (cold start → init → handler → freeze → thaw) and the four architectural constraints (no state, no connections, no background threads, hard timeout ceiling) are the rules of the game. Every other note in this section either works within those constraints (12.02, 12.03) or solves a problem created by them (12.04.02).

**12.02** is the escape hatch for cold starts. V8 isolates are a different isolation mechanism — not a container, not a VM, just a V8 heap with a sandbox. They cold-start in microseconds because there is no kernel, no namespace, no cgroup, no runtime boot — just a JavaScript context spawned inside an already-running process. The trade-off is that you cannot do anything that requires a process: no `fs`, no `child_process`, no TCP socket, no Node.js native modules. You get `fetch` and the Web Standard APIs, and that is it. This makes edge functions ideal for "logic in front of an HTTP API" (auth checks, A/B routing, geo routing, response transformation) and terrible for "logic that needs a database connection" (which is most backend code).

**12.03** is the radical answer to the connection problem: remove the backend server entirely. Supabase puts Postgres behind PostgREST so the client SDK talks SQL-or-REST directly to the database, with RLS policies enforced at the DB layer. Firebase puts a NoSQL document store behind a real-time sync protocol so the client SDK subscribes to documents directly. Either way, there is no application server to keep warm, no connection pool to tune, no scaling to plan — the BaaS provider absorbs all of it. The trade-off is that the database schema and the security model are now coupled to the client SDK, and migrating away means rewriting both.

**12.04** closes the loop. 12.04.01 gives you the decision matrix: when to use a traditional server, when serverless, when BaaS, when edge. 12.04.02 solves the specific problem that kills most early serverless + RDS deployments — the connection limit — with four practical fixes ranked from "drop-in pooler" (PgBouncer) to "switch to a serverless-native DB" (DynamoDB, Aurora Serverless, Neon HTTP).

A unifying theme across the whole section: **serverless shifts work from your code to your platform**, and the cost of that shift is a set of constraints (no state, no connections, no background work, hard timeouts) that you must design around. The architectures in 12.02 and 12.03 exist because those constraints are unforgiving, and the trade-offs in 12.04 exist because the constraints are sometimes wrong for the workload.

## How to Read This Section

1. **Read the concept notes first.** They establish the mental model. Start with 12.01.01 (lifecycle) and 12.01.02 (constraints) — every later note assumes you have internalized both.
2. **Read 12.02 before 12.03.** V8 isolates are the conceptual bridge from "function in a container" to "function with no container at all"; BaaS is the next step past that.
3. **End with 12.04.** The decision matrix only makes sense after you understand the lifecycle, the edge runtime, and the BaaS architecture. The connection-limit note (12.04.02) is the single most useful page in this section if you are about to put a serverless function in front of a Postgres database.
4. **Connect.** Follow the Related Notes links to reinforce the cross-ecosystem graph — particularly the link back to [[10.00. Map of Content - Infrastructure and Networking]] (containers) and [[04.00. Map of Content - Runtime Concurrency]] (the threading model that serverless replaces).

> [!tip] Reading order
> If you are new to this section, follow the numeric ordering. If you are revising, jump directly to whichever concept you forgot — but always come back to 12.01.02 (Architectural Constraints) before making an architectural choice, because every constraint there has a production failure mode associated with it.
