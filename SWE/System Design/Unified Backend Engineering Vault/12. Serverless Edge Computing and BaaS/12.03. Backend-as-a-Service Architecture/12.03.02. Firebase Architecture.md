# 12.03.02. Firebase Architecture

## What This Is

Firebase is Google's Backend-as-a-Service — the original BaaS, launched in 2011, acquired by Google in 2014, and now the default mobile-app backend for the Android ecosystem. Where Supabase (covered in [[12.03.01. Supabase Architecture]]) gives you a managed Postgres with auto-generated REST APIs and SQL-based RLS, Firebase gives you a managed NoSQL document database (Cloud Firestore) with a proprietary real-time sync protocol and a declarative Security Rules language for authorization. The architectural bet is different: instead of "Postgres is the right database and we will expose it over HTTP," Firebase bets that "real-time sync from the database to the client is the right primitive, and we will build a database that does it natively." This note walks through the architecture: the Firestore NoSQL document model, the proprietary sync protocol that pushes changes to clients in real time, the Security Rules engine, the offline persistence that lets mobile apps work without a network connection, and the other Firebase services (Auth, Cloud Functions, Cloud Storage, Cloud Messaging, Analytics, Crashlytics) that compose the full BaaS stack.

The architectural model is similar to Supabase in one way — the client SDK talks directly to the database, no application server in the path — but different in almost every other. The Firebase SDK is embedded in the mobile/web app and maintains a persistent WebSocket to Firestore's backend. Reads and writes go over the WebSocket, not over HTTP. The SDK caches documents locally in IndexedDB (web) or SQLite (mobile), so reads are instant from the cache and writes queue locally if the network is down. When the network comes back, the SDK syncs pending writes to the server and pulls down any changes that happened while offline. This makes Firebase uniquely well-suited to mobile apps with flaky networks — a use case that traditional HTTP-based backends handle poorly.

## The Details

### Structural decomposition: Google Cloud managed NoSQL document store (Cloud Firestore) + Cloud Fun...

The Firebase platform is a composition of seven services, all hosted on Google Cloud, all accessed via the Firebase client SDK or via Google Cloud APIs. The architectural principle is "everything a mobile app needs, in one SDK" — auth, database, file storage, push notifications, analytics, crash reporting, and server-side logic. Each service is a separate Google Cloud product under the hood (Firestore is its own GCP product, Cloud Functions for Firebase is a wrapper around Google Cloud Functions, Cloud Storage for Firebase is a wrapper around Google Cloud Storage), and the Firebase SDK provides a unified API surface that abstracts over them.

**Cloud Firestore** is the heart of the platform. It is a NoSQL document database — data is stored as JSON-like documents grouped into collections, with no schema enforcement and no JOINs. A `users` collection contains documents like `{ id: "abc", name: "Alice", email: "alice@example.com", lastLogin: Timestamp(...) }`. A `posts` collection contains documents like `{ id: "post1", authorId: "abc", title: "Hello", body: "World", createdAt: Timestamp(...) }`. Documents can have subcollections — `posts/post1/comments` is a subcollection of comments under a specific post, allowing hierarchical data without denormalization. Queries are indexed by default — Firestore automatically creates single-field indexes for every field, and you can create composite indexes for multi-field queries. There are no JOINs; if you need data from two collections, you either do two reads or denormalize the data into a single document.

The sync protocol is what makes Firestore different from every other database in this section. The client SDK opens a persistent WebSocket (or HTTP/2 stream on platforms without WebSocket support) to Firestore's backend. When you call `onSnapshot(collection(db, 'posts'), callback)`, the SDK sends a `Listen` request over the WebSocket that says "I want to subscribe to all documents in the posts collection matching this query." The backend registers the subscription, sends the initial results, and then for every subsequent change to any matching document — INSERT, UPDATE, DELETE — the backend pushes a `TargetChange` message over the WebSocket to the client. The client SDK applies the change to its local cache and invokes the callback. This is real-time push, not polling — the moment a document changes server-side, every subscribed client receives the change in tens of milliseconds.

```javascript
// Client-side real-time subscription with the Firebase SDK
import { initializeApp } from 'firebase/app';
import { getFirestore, collection, onSnapshot, query, where } from 'firebase/firestore';

const app = initializeApp(firebaseConfig);
const db = getFirestore(app);

// Subscribe to all messages in a chat room — receives initial state + all future changes
const q = query(collection(db, 'messages'), where('roomId', '==', 'room-123'));

const unsubscribe = onSnapshot(q, (snapshot) => {
  snapshot.docChanges().forEach((change) => {
    if (change.type === 'added') {
      console.log('New message:', change.doc.data());
    }
    if (change.type === 'modified') {
      console.log('Modified message:', change.doc.data());
    }
    if (change.type === 'removed') {
      console.log('Deleted message:', change.doc.data());
    }
  });
});

// Later: stop listening
unsubscribe();
```

**Firebase Auth** handles all the auth flows a mobile app needs. Email/password is built in. OAuth providers (Google, Apple, Facebook, Twitter, GitHub, Microsoft) are built in — the SDK opens a sign-in flow, exchanges the OAuth code for a Firebase ID token, and stores the token in the SDK's persistence layer (IndexedDB on web, Keychain on iOS, Keystore on Android). Phone authentication uses SMS OTP (often requires Google Play Services on Android, requires APNs setup on iOS). Anonymous authentication creates a temporary user that can later be upgraded to a permanent account. The Firebase ID token is a JWT signed by Google's keys, included on every Firestore/Storage request as `Authorization: Bearer <token>`, and verified by the Security Rules engine (see next H3). The token is refreshed automatically every hour by the SDK.

**Cloud Functions for Firebase** is the server-side escape hatch. It is a wrapper around Google Cloud Functions (which itself runs on the same infrastructure as Cloud Run) that adds Firebase-specific triggers: `onDocumentWrite`, `onDocumentCreated`, `onDocumentUpdated`, `onDocumentDeleted` (Firestore triggers); `onUserCreate`, `onUserDelete` (Auth triggers); `onObjectFinalized`, `onObjectDeleted` (Storage triggers); `onMessagePublished` (Pub/Sub triggers); `onRequest`, `onCall` (HTTP and callable triggers); `onSchedule` (cron triggers). Functions are written in Node.js, Python, Go, or Java — full runtimes, not V8 isolates — and they have the cold-start characteristics of Cloud Run (1–2s for Node.js, 3–5s for Java). The architectural role is the same as Supabase Edge Functions: complex business logic, external API calls, scheduled jobs, and webhook handlers that cannot be expressed as a Firestore read or write.

**Cloud Storage for Firebase** is the file upload service. It is backed by Google Cloud Storage (GCS), with a Firebase SDK that handles resumable uploads (essential for mobile networks where a 50MB video upload will be interrupted multiple times). Security Rules apply to Storage objects just as they do to Firestore documents, so you can write rules like "only the user who uploaded a file can read it" or "anyone can read objects in the public bucket." Uploads go directly from the client SDK to GCS via a signed URL — they do not pass through a Firebase server, so they do not count against your Cloud Function execution quota or your Cloud Function memory limit.

**The production failure mode** of the Firebase architecture is the **NoSQL impedance mismatch when the data model needs JOINs**. A common scenario: a chat app stores messages in a `messages` collection, each message has an `authorId` field, and the UI wants to display the author's name and avatar next to each message. In SQL, this is a single JOIN. In Firestore, you have three options, all bad: (1) do one read per message to fetch the author — 100 messages × 1 read = 100 reads per screen view, expensive and slow; (2) denormalize the author's name and avatar into each message document — fast reads, but if the author changes their name, you have to update every message they ever wrote (a multi-document write that requires a Cloud Function trigger); (3) maintain a `users` cache in the client and update it on user-profile changes — complex client-side code, hard to keep in sync. The architectural answer is that **Firestore is the wrong database for query-heavy workloads** — it is the right database for write-heavy workloads with simple, indexed reads (chat, activity feeds, real-time dashboards). If your app needs JOINs, transactions across multiple records, or SQL aggregation, you should use Supabase/Postgres or a traditional SQL backend, not Firebase. The metric that reveals this is the Firestore read count in the GCP billing dashboard — if a single screen view generates 100+ reads, your data model is wrong for Firestore, and you will hit the pricing ceiling ($0.036 per 100K reads sounds cheap until you have 100K users each generating 100 reads per screen view = $360 per screen view per 100K users).

### Security Rules engine for client authorization

Because the Firebase client SDK talks directly to Firestore and Storage, the authorization boundary must be enforced at the database/storage layer — there is no application server to check permissions. Firebase's answer is **Security Rules** — a declarative, JSON-like language that you write and deploy alongside your data, evaluated by the Firestore/Storage backend on every read and write. Rules look like JavaScript but are not — they are a custom language designed for one purpose: deciding whether a given operation should be allowed, given the user's auth state and the document's contents.

The Security Rules language is intentionally limited. There are no loops, no functions (only built-in helpers like `request.auth`, `resource.data`, `exists()`, `get()`), no side effects. The evaluation is synchronous and pure — given `(request, resource)`, return `true` or `false`. The limitation is the security: a Turing-complete rules language would be a Turing-complete attack surface, so Firebase deliberately keeps it minimal. The trade-off is that any logic too complex for Security Rules must move to a Cloud Function — which means giving up direct client-to-database access for that operation.

```javascript
// Firestore Security Rules — chat app example
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {

    // Helper function: is the user signed in?
    function isSignedIn() {
      return request.auth != null;
    }

    // Helper function: does the user own this document?
    function isOwner(userId) {
      return isSignedIn() && request.auth.uid == userId;
    }

    // Users collection: a user can read any profile, but only update their own
    match /users/{userId} {
      allow read: if true;  // public profiles
      allow create: if isOwner(userId);
      allow update: if isOwner(userId);
      allow delete: if false;  // never allow delete (use a 'deleted' flag)
    }

    // Posts collection: published posts are public, drafts are owner-only
    match /posts/{postId} {
      allow read: if resource.data.published == true || isOwner(resource.data.authorId);

      // Create: must be signed in, author must be the current user, body must be < 10K chars
      allow create: if isSignedIn()
                    && request.resource.data.authorId == request.auth.uid
                    && request.resource.data.body.size() < 10000;

      // Update: only the author, and they cannot change the authorId
      allow update: if isOwner(resource.data.authorId)
                    && request.resource.data.authorId == resource.data.authorId;

      // Delete: only the author
      allow delete: if isOwner(resource.data.authorId);

      // Subcollection: comments on a post
      match /comments/{commentId} {
        // Anyone can read comments (post is already public if you got here)
        allow read: if true;

        // Create: signed in, comment must reference the post's postId, body < 1K chars
        allow create: if isSignedIn()
                      && request.resource.data.postId == postId
                      && request.resource.data.body.size() < 1000;

        // Update: only the comment author
        allow update: if isOwner(resource.resource.data.authorId);

        // Delete: comment author or post author
        allow delete: if isOwner(resource.data.authorId)
                      || isOwner(get(/databases/$(database)/documents/posts/$(postId)).data.authorId);
      }
    }

    // Messages collection: only participants of a chat room can read or write
    match /messages/{messageId} {
      allow read: if isSignedIn()
                  && request.auth.uid in resource.data.participants;
      allow create: if isSignedIn()
                    && request.auth.uid in request.resource.data.participants
                    && request.auth.uid == request.resource.data.senderId;
    }
  }
}
```

The evaluation model is **per-document**. When a client issues `db.collection('posts').get()` (a query for many documents), the Security Rules engine evaluates the read policy against each matching document individually — if 50 documents match the query but only 30 satisfy the policy, the client receives only 30 documents and never knows the other 20 existed. This is the same as Postgres RLS (covered in [[12.03.01. Supabase Architecture]]), but with two important differences: (1) Firestore Security Rules cannot reference other documents except via the `get()` helper, which does a separate read and is slow (one extra read per evaluation, billed at the Firestore read rate); (2) the rules are evaluated client-side as well as server-side — the SDK uses the rules to optimize its local cache (it knows it does not need to ask the server for documents the user cannot read), which is a performance optimization but also a security consideration (the client knows the rules, so an attacker can read your rules and design attacks around them — but they still cannot bypass them, because the server enforces them).

The Security Rules language has two key contexts: `request` (what the client is trying to do) and `resource` (the existing document on the server). For `read` operations, only `resource` is relevant (the document being read). For `create` operations, only `request.resource` is relevant (the document being created — `resource` does not exist yet). For `update` operations, both are relevant — `resource.data` is the existing document, `request.resource.data` is the new version, and you can compare them to enforce invariants like "you cannot change the authorId field." For `delete` operations, only `resource` is relevant (the document being deleted).

The `get()` helper is the way to reference other documents. `get(/databases/$(database)/documents/posts/$(postId)).data.authorId` reads the post document and returns its `authorId` field. This is necessary for hierarchical authorization (the comment's parent post's author can delete the comment), but it is expensive — each `get()` is a billable Firestore read. A common performance pitfall is a list query that triggers a `get()` per document — if you query 50 comments and each comment's policy does a `get()` on the parent post, that's 50 reads billed, even though the parent post is the same for all of them. Firebase added rules optimization to cache `get()` results within a single request, but it is still a significant cost factor.

```text
  Security Rules evaluation model:

  ┌────────────────────────────────────────────────────────────────────┐
  │ Client issues: db.collection('posts').get()                       │
  │                                                                   │
  │ Firestore backend:                                                │
  │  1. Authenticates the user (verifies the ID token)                │
  │  2. Runs the query (finds all documents in 'posts' collection)   │
  │  3. For each matching document:                                  │
  │     - Evaluate the 'read' policy against (request, resource)     │
  │     - If policy returns true: include the document in results    │
  │     - If policy returns false: exclude the document silently     │
  │  4. Return the filtered results to the client                    │
  │                                                                   │
  │ Security properties:                                              │
  │  - Client never sees documents they're not allowed to read       │
  │  - Client cannot bypass the policy (no API for "ignore rules")   │
  │  - Policy is evaluated server-side, every time, on every doc     │
  │  - get() calls in the policy do billable reads                   │
  │  - Policy is also evaluated client-side for cache optimization   │
  │    (so the client knows the policy — security by obscurity does  │
  │     not work, the policy must be correct)                         │
  └────────────────────────────────────────────────────────────────────┘
```

**The production failure mode** of Security Rules is the **overly permissive rule that opens a data breach**. The most famous example is the Firebase rule that ships as the default when you create a new Firestore database: `allow read, write: if true;` — this means anyone in the world can read and write any document in your database, with no authentication required. Thousands of mobile apps have shipped to production with this default rule still in place, exposing their entire database to the public internet. The fix is to never deploy with the default rules — always write specific rules before going to production. A subtler failure is the **rule that references `request.resource.data` incorrectly**: a developer writes `allow create: if request.resource.data.userId == request.auth.uid` thinking they are enforcing "user can only create documents where they are the owner," but the field name is wrong (`userId` instead of `authorId`), the rule always returns false, and no client can create any document — until a frustrated developer "fixes" it by changing to `allow create: if true;`, which lets any client create any document with any `userId`, opening the breach. The metric that reveals a Security Rules breach is unexpected read/write volume in the GCP billing dashboard — if your database suddenly starts serving 10× the normal read volume, an attacker may have found an open collection. The deeper mitigation is to use the Firebase Rules Simulator (built into the Firebase console) to test every rule against realistic scenarios before deploying, and to set up billing alerts on Firestore read volume that page you if it exceeds 2× the daily average.

### Client-side offline persistence and real-time document listeners via proprietary protocols

The third architectural pillar of Firebase — the one that distinguishes it most sharply from Supabase and from any HTTP-based backend — is **offline persistence**. The Firebase SDK maintains a local cache of every document the client has read, in IndexedDB on web and in SQLite on mobile. When the client reads a document, the SDK returns the cached version instantly (sub-millisecond) and simultaneously checks the server for updates. When the client writes a document, the SDK writes to the local cache immediately (so the UI updates instantly) and queues the write for delivery to the server when the network is available. When the network is down, the SDK keeps serving reads from cache and queuing writes locally; when the network comes back, the SDK sends the queued writes and pulls down any changes that happened on the server while the client was offline.

This makes Firebase uniquely well-suited to mobile apps. A traditional HTTP-based mobile app (Spring Boot backend + Retrofit client) fails when the network is down — every API call returns a network error, the UI shows an error state, the user cannot do anything. A Firebase mobile app keeps working: reads come from the local cache, writes go to the local queue, and the user can continue to use the app normally. When the network comes back, the app syncs automatically, and any conflicts are resolved by Firestore's last-write-wins policy (or by a custom conflict resolver in Cloud Functions).

```text
  Traditional HTTP backend (online-only):

  User opens app →
  ┌─────────────────────────────────────────────────────┐
  │ App makes GET /api/posts                            │
  │  ↓                                                  │
  │ Retrofit → OkHttp → server                          │
  │              ↓                                      │
  │              server unavailable (no network)        │
  │              ↓                                      │
  │ OkHttp throws IOException                           │
  │  ↓                                                  │
  │ App catches exception, shows "No internet" screen   │
  │  ↓                                                  │
  │ User cannot use the app                             │
  └─────────────────────────────────────────────────────┘

  Firebase (offline-persistent):

  User opens app →
  ┌─────────────────────────────────────────────────────┐
  │ App calls db.collection('posts').get()              │
  │  ↓                                                  │
  │ Firebase SDK checks local SQLite cache              │
  │  ↓                                                  │
  │ Cache has the data from last session                │
  │  ↓                                                  │
  │ App renders UI instantly from cache                 │
  │  ↓                                                  │
  │ SDK attempts to sync with server                    │
  │  ↓                                                  │
  │ Network unavailable — sync queued for later         │
  │  ↓                                                  │
  │ User continues to use the app                       │
  │  ↓                                                  │
  │ User writes a new post →                            │
  │   SDK writes to local cache immediately             │
  │   UI shows the new post                             │
  │   Write queued for server delivery                  │
  │  ↓                                                  │
  │ Network comes back (user walks into wifi) →         │
  │   SDK syncs: sends queued writes, pulls server      │
  │   changes, updates local cache                      │
  │   UI updates to reflect server-side changes         │
  └─────────────────────────────────────────────────────┘
```

The mechanism behind offline persistence is the SDK's **local cache + write queue + sync protocol**. The cache is a SQLite database (on Android/iOS) or IndexedDB store (on web) that mirrors the documents the client has subscribed to. The write queue is a separate SQLite table that holds pending writes, ordered by the time they were issued. The sync protocol is the **Firestore Watch stream** — a bidirectional gRPC-over-WebSocket stream that the SDK maintains with the Firestore backend. When the SDK has a pending write, it sends a `Write` request over the stream; the backend applies the write and responds with a `WriteResponse` containing the new server-side version of the document. When the backend detects a change to a document the client is subscribed to, it pushes a `TargetChange` message over the stream; the SDK updates its local cache and invokes any registered `onSnapshot` callbacks.

The conflict resolution policy is **last-write-wins by server timestamp**. When the client sends a write, the server assigns it a timestamp based on the server's clock (which is synchronized via Google's TrueTime infrastructure across regions). If two clients write to the same document while offline, both writes are queued locally; when they sync, the server applies them in timestamp order — the write with the later server timestamp wins. This is simple but not always correct: if Alice and Bob are both editing the same document while offline, and Alice saves at 10:00:00 and Bob saves at 10:00:05, Bob's write overwrites Alice's, and Alice's edits are lost. The Firebase docs recommend using **field-level transforms** (`serverTimestamp()`, `arrayUnion()`, `increment()`) for collaborative-editing scenarios — these are commutative operations that compose correctly regardless of order, instead of full-document overwrites that clobber each other.

```javascript
// Offline-aware writes with field-level transforms (correct for collaborative editing)
import { collection, doc, setDoc, serverTimestamp, arrayUnion, increment } from 'firebase/firestore';

// BAD — full-document overwrite, loses concurrent edits:
await setDoc(doc(db, 'documents', 'doc-1'), {
  title: 'My Document',
  body: 'New body content',
  lastEditedBy: 'alice',
  lastEditedAt: serverTimestamp(),  // ← server assigns this, but the whole document is overwritten
});

// GOOD — field-level transforms, composes correctly with concurrent edits:
await setDoc(doc(db, 'documents', 'doc-1'), {
  body: 'New body content',
  lastEditedBy: 'alice',
  lastEditedAt: serverTimestamp(),
  viewCount: increment(1),          // ← atomic increment, no read-modify-write
  tags: arrayUnion('important'),    // ← atomic array append, no read-modify-write
}, { merge: true });                // ← merge: only update the specified fields, don't overwrite
```

The real-time listeners are the other half of the offline-persistence story. When you call `onSnapshot(query, callback)`, the SDK subscribes to that query via the Watch stream. The backend sends the initial results, then keeps the subscription open and pushes changes. The SDK applies changes to its local cache and invokes the callback. This means the UI is always up-to-date — if another user edits a document that this user is viewing, the change appears in the UI within tens of milliseconds, with no polling, no manual refresh, no application server. The architectural consequence is that **the Firebase SDK replaces the application server's pub/sub layer** — instead of a Spring Boot app that listens to a Kafka topic and pushes updates to clients via WebSocket, the Firestore backend itself is the pub/sub broker, and the client SDK is the WebSocket consumer.

The trade-off for offline persistence is **disk space and cache size**. The local SQLite cache can grow large — every document the client has ever read is cached, and the cache is only evicted when the SDK runs out of its configured cache size (default 40 MB on web, 100 MB on mobile). A user who browses thousands of documents will have a large local cache, which slows down the SDK's startup time (it must load the cache metadata into memory) and consumes device storage. The Firebase SDK exposes a `clearPersistence()` method to wipe the cache, but it is rarely called in production apps because clearing the cache logs the user out (the auth tokens are stored alongside the data). The deeper trade-off is the **lock-in to the Firestore sync protocol** — the offline persistence only works because the SDK speaks Firestore's proprietary protocol, which means you cannot replace Firestore with another database without losing offline persistence entirely. There is no standard for offline-capable sync protocols (the closest is the proposed Sync standard, which has not been adopted), so Firebase's offline persistence is a unique feature that locks you in.

**The production failure mode** of offline persistence is **the "ghost write" — a queued write that the user thinks they cancelled, but the SDK delivers it days later**. A common scenario: a user opens a draft email on Monday, types for a while, the network goes down, the SDK queues the write. The user closes the app without explicitly saving, assuming the draft is lost. On Wednesday, the user opens the app on a different network, the SDK syncs the queued write, and the draft appears — but the user has already moved on, and the now-irrelevant draft overwrites whatever they had been working on. The fix is to call `db.disableNetwork()` when the user explicitly cancels an operation, then `db.enableNetwork()` after clearing the write queue — but this is fiddly and easy to forget. The deeper failure is the **last-write-wins conflict that loses user data**: Alice and Bob both edit a document while offline, Alice saves at 10:00:00, Bob saves at 10:00:05, the server applies Bob's write last, and Alice's edits are silently lost — no error, no merge conflict UI, just gone. The metric that reveals this is user complaints about "lost work" — theFirestore backend has no way to detect this; only the user notices. The mitigation is to use field-level transforms (`arrayUnion`, `increment`, `serverTimestamp`) for any field that might be edited concurrently, and to use full-document writes only for fields that have a single writer. The deeper mitigation is to use a CRDT library (Yjs, Automerge) on top of Firestore for true collaborative editing — but this is complex and rarely worth the effort for non-collaborative apps.
