# 12.03.01. Supabase Architecture

## What This Is

Supabase is the open-source Backend-as-a-Service built on PostgreSQL. Where Firebase (covered in [[12.03.02. Firebase Architecture]]) gives you a managed NoSQL document store with a proprietary sync protocol, Supabase gives you a managed Postgres database with auto-generated REST and Realtime APIs on top, plus auth, storage, and edge functions. The architectural bet is that Postgres is already the right database for most applications — it has SQL, it has JSON columns, it has Row-Level Security, it has logical replication, it has 30 years of tooling — and what developers actually want is not a new database but a faster way to put Postgres behind an HTTP API that a frontend client can call directly, without writing a backend server. This note walks through the architecture: how PostgREST exposes the database as a REST API, how GoTrue handles auth and issues JWTs, how the Realtime engine (built in Elixir/Phoenix) tails the Postgres WAL and broadcasts changes over WebSocket, how Storage handles file uploads with signed URLs, and how Edge Functions (Deno V8 isolates) extend the platform with server-side logic.

The architectural model inverts the traditional three-tier web app. Instead of `client → backend server (Spring Boot) → Postgres`, you have `client SDK → Supabase API gateway (PostgREST/GoTrue/Realtime/Storage) → Postgres`. The backend server is gone — the client SDK talks directly to the database, mediated by Supabase's auto-generated APIs and protected by Row-Level Security policies enforced inside Postgres itself. This eliminates the per-tenant connection problem from [[12.04.02. Solving Serverless Database Connection Limits]] (the PostgREST server holds a small pool of connections, not the client), and it eliminates the cold-start problem from [[12.01.01. Serverless Execution Lifecycle]] (PostgREST is always-on, not serverless). The trade-off is that your database schema, your security model, and your API surface are now all coupled — there is no application server to add custom business logic that the database cannot express.

## The Details

### Structural decomposition: Direct client-to-database communication mediated by automated API gateways

The defining architectural choice of Supabase is that **the client SDK talks directly to the database** — there is no application server in the path. The browser-side `supabase-js` SDK makes HTTP requests to PostgREST (for CRUD operations), to GoTrue (for auth), to the Realtime WebSocket endpoint (for live updates), and to the Storage API (for file uploads). Each of these is a thin gateway in front of Postgres, holding a small connection pool and translating HTTP requests into SQL queries that Postgres executes.

The contrast with a traditional Spring Boot app is sharp. In a Spring Boot app, the request path is: `browser → NGINX → Spring Boot app (Tomcat + HikariCP) → Postgres`. The Spring Boot app holds business logic (the `@Service` beans), validates input (the `@Valid` annotations), enforces authorization (the `@PreAuthorize` checks), opens a HikariCP connection, runs a JPA query, maps the result to a DTO, and returns JSON. In Supabase, the request path is: `browser → supabase-js SDK → PostgREST → Postgres`. PostgREST holds no business logic — it inspects the database schema, generates a REST API from it (`GET /rest/v1/posts?author_id=eq.123` becomes `SELECT * FROM posts WHERE author_id = 123`), and runs the query. Business logic that cannot be expressed in SQL must move to either a Postgres function (a stored procedure), a database trigger, or a Supabase Edge Function (a separate Deno V8 isolate, not in the request path).

The connection pool advantage is the most measurable. A Spring Boot fleet of 20 pods with HikariCP `maximumPoolSize=10` holds 200 Postgres connections — close to Postgres' default `max_connections=100` ceiling. PostgREST holds a single pool of 10–25 connections for the entire Supabase project, regardless of how many clients are making requests — the HTTP requests are multiplexed onto the pool, each request borrowing a connection for the duration of one query (typically <10ms) and returning it. This is the same pattern as PgBouncer in transaction pooling mode (see [[12.04.02. Solving Serverless Database Connection Limits]]), but built into the API gateway. The same Supabase project can handle 10,000 concurrent HTTP clients with the same 25-connection pool, because each query is so short.

The architectural cost is that **the database schema becomes the API contract**. A column rename in Postgres is now a breaking API change for every client — `GET /rest/v1/posts?author_name=eq.foo` breaks if you rename `author_name` to `author_full_name`, with no application server to translate the old name to the new. PostgREST does support API versioning via database schemas (`rest/v1/` maps to the `api` schema; you can add `api_v2` with different views), but the principle holds: schema changes are API changes. This is fine for a startup with a single client app and a fast-deploy cycle, painful for an enterprise with multiple client apps on different release schedules.

The second cost is that **business logic that cannot be expressed in SQL must move to either a Postgres function or an Edge Function**. Postgres functions (PL/pgSQL stored procedures) are powerful but ugly — they are written in a procedural language inside the database, they are hard to unit test, they are hard to version, and they cannot easily call external services (you can use `pg_http` extensions but they are clunky). Edge Functions are Deno V8 isolates that you write in TypeScript, deploy to Supabase, and invoke via `POST /functions/v1/<function-name>` — they are not in the direct request path of PostgREST, but you can use them as webhooks, as scheduled jobs, or as the handler for endpoints that need to orchestrate multiple database operations or call external services. The architectural principle is: simple CRUD goes through PostgREST (no code needed); complex business logic goes in an Edge Function (TypeScript, full control, but now you are back to writing a backend).

```text
  Decision flow for "where does this code go?" in Supabase:

  Is it a simple CRUD operation (read, insert, update, delete on one table)?
   → Yes: use PostgREST directly from the client SDK
   → Example: const { data } = await supabase.from('posts').select('*').eq('published', true)

  Is it a CRUD operation with a JOIN or aggregation?
   → Yes: create a Postgres VIEW, expose it through PostgREST
   → Example: CREATE VIEW published_posts_with_author AS SELECT p.*, u.name FROM posts p JOIN users u ...

  Is it a multi-step transaction (insert order, decrement inventory, charge card)?
   → Yes: write a Postgres function (PL/pgSQL) and expose via PostgREST RPC
   → Example: CREATE FUNCTION create_order(...) RETURNS orders AS $$ BEGIN ... END $$ LANGUAGE plpgsql;
            await supabase.rpc('create_order', { ... })

  Does it need to call an external service (Stripe, SendGrid, another API)?
   → Yes: write a Supabase Edge Function (Deno V8 isolate)
   → Example: POST /functions/v1/create-payment-intent → Deno code that calls Stripe API,
            writes to Postgres, returns client secret

  Does it need to run on a schedule (every night at midnight)?
   → Yes: write an Edge Function + configure a cron trigger via pg_cron extension
```

**The production failure mode** of direct client-to-database communication is **the schema-change-as-breaking-API change**. A common scenario: a team decides to refactor the `users` table to split `name` into `first_name` and `last_name`. They run the migration in Postgres, the column `name` is dropped, and within minutes the mobile app starts failing on `GET /rest/v1/users?select=name` — every client that requested the `name` field now gets a 400 error. In a traditional Spring Boot app, the application server could continue to return `name` as a derived field (`name = first_name + ' ' + last_name`) while the underlying schema changed, giving the client team time to migrate. In Supabase, there is no application server — the schema is the API. The fix is to use Postgres VIEWS as the API surface (the client queries `users_view` which initially maps to the underlying `users` table; when the schema changes, the view is redefined to compute `name` from `first_name + ' ' + last_name`, and the client does not see the change). The metric that reveals this failure is the API error rate immediately after a migration — if it spikes, you broke the API contract.

None of them are Supabase's invention — they are existing open-source projects that Supabase integrates, hosts, and augments with a unified client SDK and dashboard. The architectural principle is "compose, don't build" — and the choice of components reveals the architectural priorities:

**PostgREST** is the heart of the platform. It is a Haskell web server that connects to Postgres as a regular client (with a dedicated `authenticator` role), introspects the database schema via the `information_schema` views, and exposes every table, view, and function in the exposed schemas (default: `public`) as a REST API. The mapping is mechanical: `GET /rest/v1/posts` becomes `SELECT * FROM public.posts`; `GET /rest/v1/posts?id=eq.42&select=id,title` becomes `SELECT id, title FROM public.posts WHERE id = 42`; `POST /rest/v1/posts` with a JSON body becomes `INSERT INTO public.posts (...) VALUES (...)`; `PATCH /rest/v1/posts?id=eq.42` becomes `UPDATE public.posts SET ... WHERE id = 42`. The mapping is so faithful that you can do almost anything in the REST API that you can do in SQL — JOINs (`/rest/v1/posts?select=*,author:users(*)`), aggregations (`/rest/v1/posts?select=count()`), full-text search (`/rest/v1/posts?body=fts.supabase`), even RPC calls to Postgres functions (`POST /rest/v1/rpc/my_function`). PostgREST holds a connection pool (default 10, configurable) and translates each request into a single SQL query that runs in <10ms for indexed lookups.

**GoTrue** is the auth service. It is a Go binary that handles email/password signup, email confirmation, OAuth (Google, GitHub, Apple, etc.), magic links, phone OTP, and JWT issuance. The user table lives in the `auth` schema inside the same Postgres database — GoTrue creates a `auth.users` table with columns like `id`, `email`, `encrypted_password`, `email_confirmed_at`, `created_at`. On login, GoTrue issues a JWT signed with the project's JWT secret; the JWT contains the user's `sub` (user ID), `email`, and `role`. The client SDK includes this JWT in the `Authorization: Bearer <jwt>` header on every subsequent request. PostgREST reads the JWT, extracts the `sub`, sets a Postgres session variable `request.jwt.claim.sub` to that value, and runs the query — at which point RLS policies (covered in the next H3) can use `auth.uid()` (which reads `request.jwt.claim.sub`) to filter rows by the current user.

**Realtime** is the most architecturally interesting component. It is an Elixir/Phoenix application that maintains a WebSocket connection to each subscribed client and broadcasts Postgres changes to clients in real time. The mechanism: Postgres has a feature called **logical replication** (the WAL — Write-Ahead Log — is a stream of row-level changes that can be consumed by an external process). Realtime connects to Postgres as a logical replication subscriber using the `wal2json` plugin (or Postgres' built-in `pgoutput` in newer versions), tails the WAL stream, decodes each change into a JSON payload (`{ "type": "INSERT", "table": "posts", "record": { "id": 1, "title": "Hello" } }`), and broadcasts it to all WebSocket subscribers who have permission to see that row (RLS policies are checked against each subscriber's JWT before broadcasting). This means a client app can subscribe to `supabase.channel('posts').on('INSERT', ...)`, and the moment any other client inserts a row into `posts`, the WebSocket receives the new row — no polling, no application server, no manual pub/sub.

```javascript
// Client-side Realtime subscription — receives INSERT/UPDATE/DELETE as they happen
import { createClient } from '@supabase/supabase-js';

const supabase = createClient('https://xyz.supabase.co', 'anon-key');

const channel = supabase
  .channel('public:posts')
  .on('postgres_changes',
    { event: '*', schema: 'public', table: 'posts' },
    (payload) => {
      console.log('Change received!', payload);
      // payload.eventType === 'INSERT' | 'UPDATE' | 'DELETE'
      // payload.new === the new row (for INSERT/UPDATE)
      // payload.old === the old row (for DELETE/UPDATE with replica identity FULL)
    }
  )
  .subscribe();
```

**Storage** is an S3-compatible object storage service. Files are stored in an S3 bucket (or locally on the Supabase VM for self-hosted), and metadata (bucket name, object key, owner, mimetype, size) is stored in the `storage` schema inside Postgres. Uploads go directly to the Storage API (which streams them to S3), and downloads use **signed URLs** — time-limited URLs that grant read access to a specific object without requiring the client to have permanent credentials. RLS policies on `storage.objects` control which user can upload to which bucket and which user can read which object — the same security model as the rest of Supabase, applied to files.

**Edge Functions** are Deno V8 isolates (the same isolation mechanism as Cloudflare Workers, described in [[12.02.01. V8 Isolates vs. Container Virtualization]]) that you write in TypeScript and deploy to Supabase. They are invoked via `POST /functions/v1/<name>`, run with a 150-second wall-clock limit, and can use the Web Standard APIs plus Deno APIs. Edge Functions are the escape hatch when you need server-side logic that cannot be expressed in SQL — calling external APIs (Stripe, Twilio, SendGrid), orchestrating multiple database operations in a transaction, doing CPU-heavy work (image processing, ML inference), or running scheduled jobs (via `pg_cron` extensions that invoke Edge Functions on a schedule).

**The production failure mode** of the component composition is **cascading failure when one component misbehaves**. The most common pattern: GoTrue becomes slow (a database query on `auth.users` starts taking 5 seconds because of a missing index on the `email` column), and every login request hangs for 5 seconds. Because the client SDK calls GoTrue on every login, every login fails — but worse, the JWT-issuing path is on the critical path of every session start, so the entire app feels broken even though PostgREST and the database are fine. The metric that reveals this is per-service latency in the Supabase dashboard (GoTrue p99 vs PostgREST p99 vs Realtime connection count) — if GoTrue p99 is 5s and the others are 10ms, GoTrue is the bottleneck. The deeper failure is **the single-Postgres bottleneck**: all five components share one Postgres instance, and if Postgres becomes slow (a slow query locks a table, autovacuum stalls, the connection pool fills up), every component fails simultaneously — there is no isolation between auth, REST, and Realtime. The mitigation is to monitor Postgres aggressively (`pg_stat_activity`, `pg_stat_statements`, connection count, replication lag) and to use Supabase's read replicas (launched 2024) for read-heavy workloads so that Realtime and PostgREST reads can hit a replica while GoTrue writes hit the primary.

### PostgreSQL Row-Level Security (RLS): Defining programmatic authorization policies directly on dat...

The security model of Supabase rests on **Postgres Row-Level Security (RLS)** — a Postgres feature that enforces per-row authorization policies on every query, evaluated inside the database, with no way for the client to bypass. This is what makes direct client-to-database communication safe: even though the client SDK can send any SQL-equivalent request to PostgREST, the database itself refuses to return rows the user is not authorized to see. There is no application server checking permissions — Postgres itself is the enforcement point, on every query, including `SELECT`, `INSERT`, `UPDATE`, and `DELETE`.

RLS is enabled per table with `ALTER TABLE ... ENABLE ROW LEVEL SECURITY`. Once enabled, every query against that table is filtered by the policies defined on it — a `SELECT * FROM posts` returns only the rows where at least one `USING` policy evaluates to true for the current user. The "current user" is determined by session variables set by PostgREST from the JWT — when PostgREST receives a request with `Authorization: Bearer <jwt>`, it verifies the JWT, extracts the `sub` claim (the user ID), and runs `SET LOCAL request.jwt.claim.sub = '<user-id>'` before executing the query. The Postgres function `auth.uid()` reads this session variable, so RLS policies can reference `auth.uid()` to filter by the current user.

```sql
-- Set up a posts table with RLS
CREATE TABLE posts (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  author_id UUID REFERENCES auth.users(id) NOT NULL,
  title TEXT NOT NULL,
  body TEXT NOT NULL,
  published BOOLEAN NOT NULL DEFAULT false,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Enable RLS
ALTER TABLE posts ENABLE ROW LEVEL SECURITY;

-- Policy 1: anyone (even unauthenticated) can read published posts
CREATE POLICY "Published posts are readable by everyone"
  ON posts FOR SELECT
  USING (published = true);

-- Policy 2: users can read their own unpublished posts
CREATE POLICY "Users can read their own posts"
  ON posts FOR SELECT
  USING (auth.uid() = author_id);

-- Policy 3: users can insert posts where they are the author
CREATE POLICY "Users can create their own posts"
  ON posts FOR INSERT
  WITH CHECK (auth.uid() = author_id);

-- Policy 4: users can update their own posts
CREATE POLICY "Users can update their own posts"
  ON posts FOR UPDATE
  USING (auth.uid() = author_id)
  WITH CHECK (auth.uid() = author_id);

-- Policy 5: users can delete their own posts
CREATE POLICY "Users can delete their own posts"
  ON posts FOR DELETE
  USING (auth.uid() = author_id);
```

The mechanics of how RLS is enforced: PostgREST connects to Postgres as the `authenticator` role, then for each request it runs `SET LOCAL role = 'anon'` (for unauthenticated requests) or `SET LOCAL role = 'authenticated'` (for JWT-bearing requests) and `SET LOCAL request.jwt.claim.sub = '<user-id>'`. Postgres evaluates the RLS policies for the current role — the `auth.uid()` function reads `request.jwt.claim.sub`, returns NULL for unauthenticated requests (where the role is `anon`), and returns the user's UUID for authenticated requests. The policies are combined with OR for the same command (e.g., two SELECT policies means a row is visible if either policy passes), and the `USING` clause controls which rows are visible (for SELECT, UPDATE, DELETE) while the `WITH CHECK` clause controls which rows can be inserted or updated to (for INSERT, UPDATE).

```text
  How a request flows through RLS:

  1. Browser sends: GET /rest/v1/posts
     Authorization: Bearer <jwt with sub=user-123>

  2. PostgREST receives the request
     - Verifies the JWT signature against the project JWT secret
     - Extracts sub=user-123 from the JWT
     - Acquires a connection from the pool

  3. PostgREST runs setup SQL on the connection:
     SET LOCAL role = 'authenticated';
     SET LOCAL request.jwt.claim.sub = 'user-123';

  4. PostgREST runs the query:
     SELECT * FROM public.posts;

  5. Postgres evaluates the query with RLS:
     -- Combines all SELECT policies with OR:
     -- Policy 1: published = true  (returns true for published posts)
     -- Policy 2: auth.uid() = author_id  (returns true for user-123's posts)
     -- Effective query:
     SELECT * FROM public.posts
     WHERE published = true OR auth.uid() = author_id;
     -- ^^^ this is INVISIBLE to the client — the client just sees "GET /posts"
     --     returns only the rows they're allowed to see

  6. Postgres returns the filtered rows to PostgREST

  7. PostgREST returns the rows as JSON to the client
     — the client never sees the RLS policies, never sees the rows they're
       not allowed to see, has no way to bypass the filter
```

The key insight is that **RLS is enforced by Postgres, not by PostgREST**. PostgREST is just a translator — it converts HTTP into SQL, but the security boundary is at the database. This means: (1) even if PostgREST has a bug that lets the client send arbitrary SQL, the RLS policies still apply (the client cannot `SELECT * FROM auth.users` because the `auth` schema is not exposed and the `authenticator` role does not have SELECT permission on `auth.users`); (2) if you connect to Postgres directly with `psql` using the `anon` or `authenticated` role, the same RLS policies apply — there is no way to bypass them without escalating to the `postgres` superuser; (3) if you write a Postgres function (`CREATE FUNCTION ...`) with `SECURITY DEFINER`, the function runs as its owner (typically the `postgres` superuser) and can bypass RLS — this is the escape hatch for operations that need to see all rows (e.g., an admin function), but it is also the security hole if you write the function carelessly.

The trade-off of RLS is **performance**. Every query against an RLS-enabled table has the policy predicates added to its WHERE clause, which means the query planner must evaluate the policy on every row. If the policy is `auth.uid() = author_id` and there is an index on `author_id`, the query is fast (index scan for the current user's rows). If the policy is something complex like `EXISTS (SELECT 1 FROM team_members WHERE team_members.user_id = auth.uid() AND team_members.team_id = posts.team_id)`, the query becomes a correlated subquery that can be slow without careful indexing. The Supabase dashboard shows query plans for RLS-affected queries — if a query that should take 1ms takes 100ms, the RLS policy is likely the culprit, and you need to add an index on the columns the policy references.

```text
  RLS performance pitfalls:

  ┌────────────────────────────────────────────────────────────────────┐
  │ Bad policy (slow — full table scan):                              │
  │   CREATE POLICY ... USING (                                       │
  │     EXISTS (SELECT 1 FROM team_members tm                        │
  │            WHERE tm.user_id = auth.uid()                         │
  │              AND tm.team_id = posts.team_id)                     │
  │   );                                                              │
  │  → Postgres evaluates the EXISTS subquery for every row in posts │
  │  → O(N*M) where N=posts, M=team_members                          │
  │  → 1M posts × 100 team_members = 100M operations per query       │
  ├────────────────────────────────────────────────────────────────────┤
  │ Good policy (fast — uses indexes):                               │
  │   CREATE POLICY ... USING (                                       │
  │     team_id IN (SELECT team_id FROM team_members                 │
  │                WHERE user_id = auth.uid())                       │
  │   );                                                              │
  │  + CREATE INDEX ON team_members(user_id);                        │
  │  + CREATE INDEX ON posts(team_id);                               │
  │  → Postgres builds the set of team_ids for the current user once │
  │  → Then does an index scan on posts for those team_ids           │
  │  → O(log M + K) where K = number of matching teams               │
  └────────────────────────────────────────────────────────────────────┘
```

**The production failure mode** of RLS is the **policy that does not match the application's intent, allowing access the developer did not mean to allow**. The most common pattern: a developer adds a SELECT policy `USING (true)` ("let anyone read this table") for testing, then forgets to remove it before launch — every row in the table is now publicly readable, including rows that should be private. The fix is to never use `USING (true)` in production policies, and to use the Supabase dashboard's "Policies" view to audit which policies are defined on each table. A subtler failure is the **`SECURITY DEFINER` function that leaks data**: a developer writes a Postgres function `get_user_posts(user_uuid)` that returns all posts by a given user, marks it `SECURITY DEFINER` (so it can read all rows regardless of RLS), and forgets to check that the calling user is allowed to see the requested user's posts — any client can now call `supabase.rpc('get_user_posts', { user_uuid: 'someone-else' })` and read another user's private posts. The metric that reveals this is the access log on Supabase — if you see requests for `rpc/get_user_posts` from a user who should not be calling it, the function is leaking. The deeper fix is to write `SECURITY DEFINER` functions with explicit `IF auth.uid() != requested_user THEN RAISE EXCEPTION 'unauthorized'` checks at the top, and to use `SECURITY INVOKER` (the default) wherever possible so the function inherits the caller's RLS context.
