# 12.01.01. Serverless Execution Lifecycle

## What This Is

A serverless function is not a process. It is a handler function that exists only for the duration of one invocation, hosted inside a sandbox managed by the cloud provider. There is no `main()` loop that runs forever waiting for requests — the function is dormant until an event arrives, and the cloud provider is responsible for materializing a sandbox, loading the handler, running it, returning the result, and then freezing (or destroying) the sandbox. This note walks through that lifecycle in mechanical detail: what happens between "event arrives" and "response returned," what the difference between a cold start and a warm invocation actually is, what the cold-start numbers look like per runtime, and how the billing model reflects the lifecycle.

This sits in the layered mental model as an evolution of the container runtime from [[10.00. Map of Content - Infrastructure and Networking]]. Where a container runs a process that listens on a socket indefinitely, a serverless function runs a handler that the platform invokes on demand — the platform owns the socket, the platform owns the lifecycle, and the developer owns only the function body. The four architectural constraints that follow from this lifecycle (no in-process state, no long-lived connections, no background threads, hard execution timeout) are covered in [[12.01.02. Architectural Constraints of Ephemeral Compute]].

## The Details

### The Serverless Paradigm: Event-driven execution, scaling from zero to thousands of instances, per...

A traditional server — a Spring Boot JAR inside a Kubernetes pod behind an NGINX ingress — is a process that is always running. It listens on a socket, accepts TCP connections, dispatches requests to a thread pool, and the same process handles request after request until the pod is restarted. The process owns the socket, owns the thread pool, owns the connection pool, owns the in-process cache. Scaling means adding more pods behind the load balancer; the pods stay warm because requests keep arriving.

The serverless model inverts this. There is no always-on process. There is no socket the function owns. There is no thread pool the function manages. Instead, the cloud provider runs a **front-end dispatcher** (AWS Lambda's Invoke Frontier, Google Cloud Run's request router, Cloudflare Workers' edge POP runtime) that accepts the incoming event — an HTTP request, an S3 PUT, a DynamoDB stream record, a cron tick — and **materializes a sandbox on demand** to run the handler. When the handler returns, the sandbox is either frozen (kept warm for a few minutes to absorb the next invocation) or destroyed. The unit of scaling is not "a pod behind a load balancer" — it is "one invocation in one sandbox."

The key consequence: **scaling is per-invocation, not per-instance**. A traditional server that handles 100 requests per second needs N pods; doubling traffic to 200 req/s needs 2N pods (after autoscaler kicks in, after a few minutes of warmup). A serverless function that handles 100 invocations per second needs 100 concurrent sandboxes; doubling traffic to 200 invocations per second needs 200 concurrent sandboxes, **immediately, with no autoscaler delay**, because the provider creates one sandbox per concurrent invocation. The same function can go from 0 invocations/hour to 10,000 invocations/second in a single tick — Lambda has been measured scaling from 0 to 3,000 concurrent executions in under 30 seconds. The provider, not you, absorbs the capacity planning.

The invocation model is strictly **event-driven and request-response**. Every serverless platform supports two invocation styles: **synchronous** (the caller waits — API Gateway → Lambda, HTTP request → Cloud Run, `fetch` → Worker) and **asynchronous** (the caller drops the event on a queue and leaves — S3 PUT event → Lambda via EventBridge, SNS → Lambda, Pub/Sub → Cloud Function). Synchronous invocations bill wall-clock time and are bounded by the platform's timeout (Lambda 15 min, Cloud Run 60 min, Workers 30s CPU). Asynchronous invocations bill CPU time, can retry on failure (Lambda retries async events twice by default), and decouple the caller from the function's execution time. A third style — **stream/batch** — is the variant where the platform batches many records into one invocation (Kinesis → Lambda with up to 10,000 records per batch, DynamoDB Streams → Lambda with up to 100 records per batch).

The billing model is the third inversion. A traditional server bills for the instance whether it serves 0 req/s or 1000 req/s — you pay $50/month for the t3.small whether or not anyone hits it. Serverless bills **per-invocation + per-GB-second**: each invocation costs a flat fee (Lambda $0.20 per million requests, Cloud Run $0.40 per million requests, Workers $0.30 per million requests on the paid plan) plus a duration fee proportional to memory × time (Lambda $0.0000166667 per GB-second). An idle function that handles 0 invocations costs $0. A function that handles 100M invocations/month with an average 100ms duration at 512MB costs roughly $0.20×100 + $0.0000166667×100M×0.1×0.5 ≈ $20 + $83 = ~$103/month. The cost curve is linear in traffic, not flat — which is good at low traffic and bad at high sustained traffic (see [[12.04.01. The Backend Architecture Selection Matrix]] for the cost crossover).

```text
  Traditional server model:
  ┌─────────────┐
  │ Pod (always-on)
  │  socket:3000│←──── request 1 ──── client
  │  thread pool│←──── request 2 ──── client
  │  HikariCP   │←──── request 3 ──── client
  │  100MB heap │←──── request 4 ──── client
  └─────────────┘  (one process handles all; bill is per-pod-hour regardless of traffic)

  Serverless model:
  ┌─────────────┐
  │ Sandbox #1  │←──── request 1 ──── client    (cold-start: 250ms)
  └─────────────┘
  ┌─────────────┐
  │ Sandbox #2  │←──── request 2 ──── client    (cold-start: 250ms — different sandbox)
  └─────────────┘
  ┌─────────────┐
  │ Sandbox #1  │←──── request 3 ──── client    (warm: 10ms — reuses #1)
  └─────────────┘
  ┌─────────────┐
  │ Sandbox #3  │←──── request 4 ──── client    (cold-start: 250ms — new sandbox)
  └─────────────┘
  (provider materializes a sandbox per concurrent invocation; bill is per-invocation + per-GB-second)
```

**The production failure mode** of the event-driven model is **"the function that was supposed to be invoked was not invoked."** Because there is no always-on process, there is no health check that tells you the function is alive — only the absence of a successful invocation log tells you something is wrong. Misconfigured event-source mappings (a Lambda permission on the wrong S3 bucket ARN, an EventBridge rule with a stale event-pattern match, a Cloud Run service with `--max-instances=1` capping concurrent execution) silently drop events. The metric that reveals this is `Invocations` per function on CloudWatch / Cloud Logging — if it drops to zero during traffic you expect, the wiring is broken upstream. The mitigation is dead-letter queues on async events (Lambda `DestinationConfig.OnFailure`, Cloud Run dead-letter topic) and alarm-on-zero-invocations alerts.

### The Cold Start Lifecycle

A cold start is the latency between "event arrives at the provider's front-end" and "handler code begins executing" for an invocation that lands on a fresh sandbox. It is the single most visible cost of the serverless model — every other trade-off in this section traces back to it.

The cold start has four phases, and each phase has a different cost depending on the runtime:

```text
  Cold start lifecycle (AWS Lambda, Node.js, 512MB):

  ┌────────────────────────────────────────────────────────────────────────┐
  │ T=0       Event arrives at Lambda Invoke Frontier                     │
  │ T=0+125ms Firecracker MicroVM provisioned                             │  ← Phase 1: Sandbox
  │           (AWS Firecracker: KVM-based MicroVM, ~125ms typical cold)   │     ~125ms
  │           (Cloud Run: gVisor sandbox, ~1-2s first-time, ~200ms warm)  │
  │           (Cloudflare Workers: V8 isolate, <5ms — no kernel)          │
  │                                                                        │
  │ T=125ms   Runtime boots in the MicroVM                                │  ← Phase 2: Runtime boot
  │ T=175ms   Node.js event loop initialized                              │     ~50ms (Node.js)
  │           (JVM: ~2-3s — class loading, JIT warmup)                    │     ~2-3s (Java)
  │           (Python: ~200ms — interpreter + imports)                    │     ~200ms (Python)
  │           (Go: ~50ms — already-compiled binary, no runtime)           │     ~50ms (Go, Rust)
  │                                                                        │
  │ T=175ms   Lambda Runtime Interface Client (RIC) loads function code   │  ← Phase 3: Init
  │ T=200ms   Lambda loads handler module from /var/task                 │     ~50-500ms
  │ T=220ms   Module-level imports execute (require('pg'), require('aws-sdk'))
  │ T=280ms   Handler's outer scope runs (DB pool created, secrets fetched)
  │                                                                        │
  │ T=300ms   Handler invoked with event                                  │  ← Phase 4: Execute
  │ T=310ms   Handler returns                                             │     ~10ms
  │                                                                        │
  │ Total cold-start latency: 310ms                                       │
  │ Total warm latency (next request, same sandbox): 10ms                 │
  └────────────────────────────────────────────────────────────────────────┘
```

The four phases cost very different amounts of time depending on the runtime. **Phase 1 (sandbox provisioning)** is dominated by the isolation mechanism — Firecracker MicroVM (KVM-based, ~125ms) for Lambda, gVisor userspace sandbox (~1–2s first-time, ~200ms warm) for Cloud Run, V8 isolate (<5ms — no kernel involvement at all) for Cloudflare Workers and Vercel Edge Functions. **Phase 2 (runtime boot)** is dominated by the language runtime — Node.js initializes its V8 engine and libuv event loop in ~50ms; CPython starts the interpreter, loads builtins, and starts processing imports in ~200ms; the JVM is the catastrophe here, requiring ~2–3 seconds because it loads hundreds of core classes (`rt.jar` in Java 8, modules in Java 11+), initializes the garbage collector, and starts the JIT compiler cold. **Phase 3 (init code)** is dominated by your application's imports — `require('aws-sdk')` adds ~50ms, importing Spring's `ApplicationContext` adds 1–2 seconds, loading a heavy ORM can add 500ms. **Phase 4 (handler execution)** is your code, ~10ms for a typical CRUD handler.

The cold-start numbers per runtime, measured on AWS Lambda at 512MB (numbers from the Cloudflare blog's 2023 benchmark, AWS's re:Invent 2022 talk, and independent measurements):

```text
  ┌────────────────────┬───────────────────┬──────────────────┬───────────────────┐
  │ Runtime            │ Cold start (p50)  │ Cold start (p99) │ Warm (p50)        │
  ├────────────────────┼───────────────────┼──────────────────┼───────────────────┤
  │ Rust               │ ~20 ms            │ ~80 ms           │ ~1 ms             │
  │ Go                 │ ~50 ms            │ ~150 ms          │ ~5 ms             │
  │ Node.js            │ ~50 ms            │ ~250 ms          │ ~5 ms             │
  │ Python             │ ~200 ms           │ ~600 ms          │ ~10 ms            │
  │ .NET C#            │ ~600 ms           │ ~2 s             │ ~15 ms            │
  │ Java (JVM)         │ ~2-3 s            │ ~8 s             │ ~30 ms            │
  │ Java (GraalVM)     │ ~50 ms            │ ~200 ms          │ ~10 ms            │
  │ Cloudflare Worker  │ <5 ms             │ <10 ms           │ <1 ms             │
  │ (V8 isolate)       │                   │                  │                   │
  └────────────────────┴───────────────────┴──────────────────┴───────────────────┘
```

The JVM's 2–3 second cold start is why Java is rarely used for latency-sensitive serverless functions, despite being the dominant enterprise backend language. **GraalVM native-image** is the fix: ahead-of-time compilation turns the JVM application into a standalone ELF binary, eliminating class loading and JIT warmup. Quarkus and Micronaut both have first-class GraalVM support, and AWS's Lambda SnapStart (launched November 2023 for Java 11/17) takes a different approach — it snapshots the initialized JVM memory after init and restores it on cold start, dropping the cold-start time from ~2s to ~200ms. SnapStart works by `mmap`-ing a pre-init memory snapshot, which is why it does not work for runtimes like Node.js that already start fast enough to not justify the complexity.

The mitigation for cold starts is **provisioned concurrency** (the same idea under different names on each platform). AWS Lambda Provisioned Concurrency keeps N sandboxes warm and ready to invoke — you pay for the provisioned capacity whether or not you use it (about $0.000009708 per GB-hour for the provisioned capacity, plus the normal per-invocation fee when requests actually arrive), and the cold-start cost is paid once at provisioning time instead of on every cold invocation. Google Cloud Run's `--min-instances=N` flag achieves the same effect — the platform keeps N instances warm and bills you for them at the regular per-instance-second rate. Cloudflare Workers does not have a "cold start" worth mitigating because V8 isolates cold-start in microseconds, so it does not offer a provisioned-concurrency knob; Cloudflare Workers Unbound (the paid tier) just keeps the isolates warm in the runtime process indefinitely.

```text
  Cold-start mitigation trade-off:

  No mitigation:           Provisioned concurrency = 10:
  ┌─────────────────┐      ┌─────────────────┐
  │ p50 latency 10ms│      │ p50 latency 10ms│  (warm invocations)
  │ p99 latency 3s  │      │ p99 latency 10ms│  (no cold starts visible to user)
  │ cost: $0 idle   │      │ cost: $70/mo    │  (provisioned capacity fee)
  └─────────────────┘      └─────────────────┘
                            ↑ you pay $70/mo to convert p99=3s into p99=10ms
```

**The production failure mode** of the cold-start lifecycle is **tail-latency violations on first-load traffic**. A common pattern: a marketing site launches, gets a burst of organic traffic at 9am, the Lambda scales from 0 to 500 concurrent invocations in 30 seconds — every one of those 500 is a cold start, p99 jumps to 2s, users see a blank page for 2 seconds, bounce rate spikes, the marketing team asks why. The metric to watch is `Duration` (CloudWatch) p99 split by `InitType=cold` vs `InitType=warm` — Lambda emits the `initType` dimension; if cold-start p99 exceeds your SLO, enable provisioned concurrency on the affected alias. The subtler failure is **cold-start timeout cascade**: an upstream service has a 1s timeout, your Lambda's cold start is 1.2s, the upstream times out and retries, the retry lands on a different sandbox that also cold-starts at 1.2s, the upstream times out again, and you get a thundering herd of cold starts. The fix is to make the upstream timeout longer than your cold-start p99, or to keep the function warm with a cron-based synthetic invocation every 5 minutes.

### Warm Invocations: Reusing initialized sandboxes for subsequent requests

A warm invocation is one that lands on a sandbox which has already executed at least one previous invocation within the platform's idle window. AWS Lambda keeps sandboxes warm for **5–15 minutes** of idle time (the exact value is undocumented and varies by region and load); Cloud Run keeps them warm for ~15 minutes; Cloudflare Workers keeps V8 isolates warm indefinitely inside the running workerd process, with no documented idle timeout. The first invocation pays the full cold-start cost (sandbox + runtime + init + handler); every subsequent invocation that lands on the same warm sandbox pays only the handler cost (~5–10ms).

The mechanism is that the platform's front-end maintains a **routing table** mapping `(function-ARN, sandbox-id) → sandbox-state`. When a new invocation arrives, the front-end checks whether a warm sandbox is available for that function ARN; if yes, the invocation is routed to it (warm path); if no, a new sandbox is provisioned (cold path). The sandbox on the warm path is unfrozen (the Firecracker MicroVM was `SIGSTOP`-ed after the previous invocation returned; now it is `SIGCONT`-ed), the Lambda Runtime Interface Client (RIC) loop polls the Lambda Invoke API for the next event, the event arrives, the handler is invoked, the response is returned, the sandbox is re-frozen. The unfreeze/refreeze cycle is sub-millisecond — Linux suspend-to-RAM is fast because the memory pages are already resident, no disk I/O is required.

The key architectural insight is that **warm sandboxes preserve global state between invocations**. Anything you initialize in the module scope — database connection pools, in-memory caches, pre-loaded secrets, parsed config files — survives across invocations on the same warm sandbox. This is the entire reason serverless functions are usable at all for database-backed workloads: instead of opening a fresh DB connection per invocation (which would cost 50–200ms of TCP+TLS+auth handshake per request, dwarfing the actual query time), you open the connection pool once in module scope and reuse it across thousands of invocations on the same warm sandbox.

```javascript
// Lambda handler (Node.js) — warm-invocation optimization
const { Pool } = require('pg');          // ← module scope: runs ONCE per sandbox (cold start)

const pool = new Pool({                  // ← connection pool created once, reused on every warm invocation
  host: process.env.DB_HOST,
  max: 5,                                // small pool per sandbox — many sandboxes × 5 connections
  idleTimeoutMillis: 30000,
});

const cachedSecrets = {};                // ← in-memory cache: also reused on warm invocations

async function getSecret(name) {
  if (cachedSecrets[name]) return cachedSecrets[name];   // ← warm path: no AWS Secrets Manager call
  const secret = await fetchSecretFromSM(name);
  cachedSecrets[name] = secret;          // ← cold path: cached for next invocation on same sandbox
  return secret;
}

exports.handler = async (event) => {     // ← handler scope: runs on every invocation (cold AND warm)
  const client = await pool.connect();   // ← reuses the pool created in module scope
  const result = await client.query('SELECT NOW()');
  client.release();
  return { statusCode: 200, body: JSON.stringify(result.rows[0]) };
};
```

The trap with warm invocations is that **the platform may destroy the sandbox at any time** — Lambda's idle timeout is not a contract, and under memory pressure on the host the platform will evict warm sandboxes. Anything in module scope is therefore a cache, not a store: it can disappear between two invocations that you assumed would land on the same sandbox. The pool you opened may be closed; the secret you cached may need to be re-fetched; the in-progress multi-request transaction you tried to keep in a module-scoped variable does not exist (you cannot do that — each invocation must commit before returning, because the next invocation may be on a different sandbox). The four architectural constraints in [[12.01.02. Architectural Constraints of Ephemeral Compute]] follow directly from this: no in-process state survives reliably across invocations, so any state must live in a service that does (Redis, S3, the database).

The warm invocation also exposes a subtle **per-sandbox statefulness** that breaks naïve assumptions about concurrency. Each warm sandbox executes **one invocation at a time** (Lambda, Cloud Run, Cloudflare Workers all default to single-request-per-sandbox — the exception is Cloud Run's `--concurrency` flag, which can multiplex up to 1000 concurrent requests onto a single instance). The platform spreads concurrent invocations across multiple sandboxes: 100 concurrent invocations → 100 sandboxes, each handling one request. This is why the database connection problem in [[12.04.02. Solving Serverless Database Connection Limits]] exists — 1000 concurrent invocations means 1000 sandboxes, each with its own module-scoped connection pool, and even a `max=5` pool per sandbox yields 5000 connections to the database. The mitigation patterns (PgBouncer transaction pooling, HTTP drivers, RDS Proxy) all exist because the warm-invocation model makes per-sandbox connection pools unavoidable and the per-sandbox count scales linearly with concurrent invocations.

**The production failure mode** of warm invocations is **stale state in module scope causing silent inconsistency**. A common pattern: a Lambda reads a feature flag from AWS AppConfig at module-scope init (`const featureFlags = await fetchFlags()`), caches it in a module-scoped variable, and the flag is never re-read because the sandbox stays warm for hours. The ops team flips the flag in AppConfig, expecting the change to take effect immediately, but 80% of invocations still see the old value because they land on warm sandboxes that loaded the old flag at cold-start time. The fix is to read feature flags inside the handler (paying the AppConfig latency cost per invocation, mitigated by Lambda Extensions' local cache) or to refresh them on a timer (`setInterval` does not work — see the no-background-threads constraint in 12.01.02 — but a timestamp check inside the handler does: `if (Date.now() - lastRefresh > 60000) { refresh(); }`). The metric that reveals stale-state bugs is the divergence between what the ops team believes the system is doing and what the invocation logs show — and the only durable fix is to treat all module-scoped state as a write-through cache, never as a source of truth.
