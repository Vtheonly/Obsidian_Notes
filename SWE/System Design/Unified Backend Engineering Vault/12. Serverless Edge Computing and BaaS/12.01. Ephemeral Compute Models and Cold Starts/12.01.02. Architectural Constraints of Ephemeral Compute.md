# 12.01.02. Architectural Constraints of Ephemeral Compute

## What This Is

The serverless execution lifecycle described in [[12.01.01. Serverless Execution Lifecycle]] — cold start, handler, freeze, thaw — produces four hard constraints that change how you write code. This note names those constraints and explains the production failure mode that each one governs. These are not preferences; they are properties of the platform that you cannot negotiate around. A function that violates any one of them will fail in production, and the failure mode is rarely a clean error — it is usually a silent stall, a leaked connection, or a timeout that appears only under load.

The four constraints are: (1) **no in-process state across invocations** — every invocation may land on a different sandbox, so anything you keep in module scope is a cache, not a store; (2) **no long-lived database connections** — 1000 concurrent sandboxes × 5 connections per sandbox = 5000 connections to Postgres, which Postgres cannot handle, so you need a pooler or an HTTP driver; (3) **no background threads** — the runtime freezes between invocations, so any work you schedule after returning to the caller is silently dropped; (4) **hard execution timeout ceilings and package size limits** — Lambda 15 min, Cloud Run 60 min, Workers 30s CPU, and 250MB / 8GB / 10MB code packages respectively. These constraints are why serverless is a poor fit for many workloads — see [[12.04.01. The Backend Architecture Selection Matrix]] for the decision tree.

## The Details

### Complete statelessness: Absence of persistent local disk across execution invocations

The fundamental architectural difference between a serverless function and a long-running server is that **the function has no disk it owns**. A Spring Boot pod in Kubernetes has a `/data` directory backed by a PersistentVolumeClaim — files written there survive pod restarts. A Lambda function has a `/tmp` directory backed by an ephemeral EBS volume, scoped to the sandbox: files written there survive warm invocations on the same sandbox, but disappear the moment the platform evicts the sandbox after the idle window (5–15 minutes for Lambda, ~15 minutes for Cloud Run). A Cloudflare Worker has no filesystem at all — V8 isolates do not expose `fs`, only Web Standard APIs.

The first consequence is that **in-process caches are write-through caches, never the source of truth**. Suppose you cache a user's session in a module-scoped `Map`:

```javascript
// Lambda handler — broken in-process session cache
const sessions = new Map();              // ← module scope: survives warm invocations, dies on eviction

exports.handler = async (event) => {
  const sessionId = event.headers.Cookie;
  if (sessions.has(sessionId)) {
    return { statusCode: 200, body: JSON.stringify(sessions.get(sessionId)) };
  }
  const session = await fetchSessionFromDB(sessionId);
  sessions.set(sessionId, session);       // ← cached on THIS sandbox only
  return { statusCode: 200, body: JSON.stringify(session) };
};
```

This works on a single warm sandbox. It silently fails on a fleet of warm sandboxes: the platform load-balances invocations across many sandboxes, so request N may land on sandbox A (which has the session cached), request N+1 may land on sandbox B (which does not), and request N+2 may land on a brand-new sandbox C that was just provisioned because the platform scaled up. The user sees intermittent logouts — some requests find their session in cache, others do not, and the failure is statistically worse under high load (more sandboxes = lower cache hit rate). The fix is to move the cache to a service that all sandboxes share: Redis (ElastiCache, Upstash Redis HTTP API), DynamoDB, or a CDN like Cloudflare KV. The cost of moving the cache out of process is one extra network hop (~1ms for Redis in-VPC, ~50ms for DynamoDB cross-region), but the correctness is durable.

The second consequence is that **the local `/tmp` filesystem cannot be used for durable storage**. Lambda's `/tmp` is an EBS-backed ephemeral volume of up to 10GB (configurable via `EphemeralStorage`), Cloud Run's `/tmp` is a tmpfs backed by memory up to the instance's memory limit. Both exist for working files — image processing intermediates, downloaded model weights, video transcode buffers — not for state that must survive across invocations. The pattern is: download the input to `/tmp`, process it, upload the output to S3, return. If you try to use `/tmp` as a cache that should survive cold starts, you will discover that the platform evicts the sandbox at the worst possible moment (during a traffic burst, when you most need the cache), and the cache hit rate is unmeasurable because the eviction is opaque.

The third consequence is the most subtle: **each invocation may hit a different instance**. The platform's front-end load-balances invocations across sandboxes without regard for which sandbox handled the previous invocation from the same user. There is no session affinity, no sticky routing, no "send this user's requests to the same sandbox." (Cloud Run has a `sessionAffinity` flag in beta, but it is best-effort and breaks on instance eviction — do not rely on it.) This means anything you might be tempted to keep in process — a `WebSocket` connection to a downstream service, an in-flight transaction, a partial computation — is unsafe. Every invocation must be **idempotent and self-contained**: it loads what it needs, does what it does, writes the result to durable storage, and returns. The next invocation starts from scratch.

```text
  ┌────────────────────────────────────────────────────────────────────────┐
  │                       (no sticky routing)                              │
  │                                                                        │
  │   user A request 1 ──→ Sandbox #1  (caches A's session)                │
  │   user A request 2 ──→ Sandbox #2  (does NOT have A's session cached)  │
  │   user A request 3 ──→ Sandbox #1  (still has A's session — warm)      │
  │   user A request 4 ──→ Sandbox #3  (brand new sandbox, no cache)       │
  │                                                                        │
  │   → in-process cache hit rate ≈ 1/N where N is the number of           │
  │     concurrent warm sandboxes (which scales with traffic)              │
  │   → at 1000 concurrent invocations, cache hit rate ≈ 0.1%              │
  │   → effectively no cache at all                                        │
  └────────────────────────────────────────────────────────────────────────┘
```

**The production failure mode** of complete statelessness is **silent data loss when developers treat module scope as durable**. A common pattern: a developer reads a configuration from AWS Secrets Manager at cold-start time and stores it in a module-scoped constant `const DB_PASSWORD = await getSecret()`. This works in dev (one sandbox, never evicted). In prod, the sandbox is evicted, a new sandbox is provisioned, the new sandbox reads the secret again — fine — but in the meantime the ops team has **rotated the secret** in Secrets Manager. The new sandbox gets the new password. The old sandbox (if it had not yet been evicted when the rotation happened) still has the old password cached. The old password stops working when the database enforces the rotation; some invocations succeed (those on the new sandbox), some fail with `authentication failed for user X` (those on the old sandbox). The metric that reveals this is a sudden authentication-error rate that grows over the rotation window. The durable fix is to fetch the secret inside the handler on every invocation (paying the ~50ms Secrets Manager latency, mitigated by the Lambda Extension's local cache) or to use the Lambda Extension's automatic refresh, which keeps the module-scoped secret fresh without code changes.

### Maximum execution timeout boundaries (e.g., 10-15 second API gateway limits)

Every serverless platform imposes a hard ceiling on how long a single invocation may run. The ceilings are not arbitrary — they exist because the platform's billing model, autoscaling model, and front-end dispatcher all assume invocations are short. A function that runs forever would tie up a sandbox forever, breaking the per-invocation scaling model. The ceilings differ by platform and by invocation style:

```text
  ┌────────────────────────────────┬──────────────────────┬─────────────────────────┐
  │ Platform                      │ Max execution time   │ Notes                   │
  ├────────────────────────────────┼──────────────────────┼─────────────────────────┤
  │ AWS Lambda (sync)             │ 15 minutes (900s)    │ Hard limit, configurable│
  │ AWS Lambda (async)            │ 15 minutes           │ Same limit, retried 2×  │
  │ AWS Lambda @ Edge             │ 5 seconds            │ Must run in us-east-1   │
  │ AWS API Gateway (integration) │ 29 seconds           │ HTTP API: 30s, REST API:│
  │                               │                      │ 29s — sync Lambda bound │
  │ Google Cloud Run              │ 60 minutes (3600s)   │ Per-request timeout     │
  │ Google Cloud Functions (gen2) │ 60 minutes           │ Same as Cloud Run       │
  │ Google Cloud Functions (gen1) │ 9 minutes            │ Legacy                  │
  │ Azure Functions (Consumption) │ 10 minutes           │ Configurable up to 10m  │
  │ Azure Functions (Premium)     │ unlimited            │ But billed per-instance │
  │ Cloudflare Workers            │ 30 seconds CPU       │ Wall-clock can be longer│
  │ Cloudflare Workers (Cron)     │ 15 minutes wall      │ Cron triggers, no CPU   │
  │                               │                      │ limit                   │
  │ Vercel Edge Functions         │ 30 seconds (free)    │ Pro plan: 5 min CPU     │
  │                               │                      │ on streaming responses  │
  └────────────────────────────────┴──────────────────────┴─────────────────────────┘
```

The **API Gateway timeout** is the most commonly hit ceiling. AWS API Gateway's REST API integration has a hard 29-second timeout — even if your Lambda is configured for 15 minutes, API Gateway will return `504 Gateway Timeout` to the client after 29 seconds and the client sees a failure, while Lambda keeps running and you keep paying. This is a frequent source of confusion: the Lambda function succeeds (you see a 200 in the CloudWatch logs), but the client gets a 504 because API Gateway already gave up. The fix is to make the Lambda return within 29 seconds — if the work takes longer, return a 202 with a polling URL or a job ID and have the client poll, or push the work to a queue and have a separate async Lambda process it.

The ceiling shapes what workloads are even possible. **Sub-15-minute jobs**: file format conversions, image processing, webhook fan-out, scheduled data syncs, ML inference on small batches — all good fits for Lambda. **30-minute jobs**: video transcoding, large ETL pipelines, ML training — these exceed Lambda's ceiling and need Cloud Run (60 min) or a container on ECS/Fargate (no limit) or a Kubernetes Job (no limit). **Multi-hour jobs**: anything that runs longer than an hour is structurally a bad fit for serverless; use AWS Batch, ECS Fargate, or a Kubernetes Job. **Infinite jobs** (WebSocket servers, gRPC streaming servers, MQTT brokers): completely impossible on serverless — the model does not support long-lived connections from the client to the function. (Cloudflare Durable Objects is a partial exception — they support WebSocket connections from clients — but they are not the same as a Lambda function and have their own constraints.)

Memory limits compound the time limits. AWS Lambda caps at **10 GB** of memory (configurable from 128 MB to 10,240 MB in 1-MB increments); Cloud Run caps at **32 GB** (configurable from 128 MB to 32,768 MB); Cloudflare Workers caps at **128 MB** of memory per isolate (Workers Unbound). Memory and CPU are coupled on Lambda: more memory means more CPU (the vCPU-to-memory ratio is roughly 1 vCPU per 1,769 MB, so a 1,769 MB Lambda gets 1 vCPU and a 10,240 MB Lambda gets ~6 vCPUs). Cloud Run allows independent CPU and memory configuration. The deployment package size limits are the third axis: **Lambda 250 MB unzipped** (50 MB zipped for direct upload, 250 MB unzipped for container-image deployments including the base image), **Cloud Run 8 GB** container image, **Cloudflare Workers 10 MB** of compressed JavaScript after bundling (1 MB on the free plan).

```text
  AWS Lambda limits (consolidated):
  ┌─────────────────────────────────────┬────────────────────┐
  │ Memory                              │ 128 MB – 10,240 MB │
  │ Timeout                             │ 1s – 900s (15 min) │
  │ Deployment package (zip)            │ 50 MB              │
  │ Deployment package (container img)  │ 10 GB              │
  │ Unzipped code size (incl /tmp)      │ 250 MB             │
  │ Ephemeral disk (/tmp)               │ 512 MB – 10,240 MB │
  │ Concurrent executions (account)     │ 1,000 default      │
  │ /tmp storage                        │ Up to 10 GB        │
  │ Environment variables size          │ 4 KB               │
  │ Payload size (sync)                 │ 6 MB               │
  │ Payload size (async)                │ 256 KB             │
  └─────────────────────────────────────┴────────────────────┘
```

**The production failure mode** of timeout ceilings is the **long-running handler that exceeds the limit and gets killed mid-transaction**. A Lambda that processes a batch of 10,000 records from Kinesis, calls a downstream API per record (200ms each = 2,000 seconds total), hits the 15-minute ceiling at record 4,500, gets `SIGKILL`-ed by the platform — and the records that were "in flight" (called the downstream API but did not commit the offset back to Kinesis) get re-delivered on the next batch. If the downstream API is not idempotent (e.g., it charges a credit card), you have just double-charged 4,500 customers. The fix is to design batch handlers to be **time-aware**: check `context.getRemainingTimeInMillis()` before processing each record and stop with enough time to commit the processed records' offsets back to Kinesis, leaving the unprocessed ones for the next batch. The metric that reveals this is `Errors` on CloudWatch with `Reason=Timeout`, combined with Kinesis `IteratorAgeMilliseconds` rising (the lag between the newest record in the stream and the oldest record the function has processed). The deeper fix is to make every downstream operation idempotent — see [[07.02.03. Exactly-Once Semantics and Idempotency]] for the pattern — so that retries are safe.

### Concurrency models: Single-request concurrency per container vs. multiplexed instances

The default concurrency model on serverless platforms is **one invocation per sandbox at a time**. AWS Lambda, Cloudflare Workers, and Vercel Edge Functions all execute exactly one handler invocation inside a single sandbox at any given moment — when the handler returns, the sandbox is free to accept the next invocation. To handle 1000 concurrent invocations, the platform provisions 1000 sandboxes. This is the simplest possible model: no shared state between concurrent invocations (each is in its own sandbox), no head-of-line blocking (each gets its own sandbox), no thread-safety requirements on the handler code (no other invocation is running in the same process).

The trade-off is **resource waste at low concurrency**. If each invocation needs 100MB of memory and you handle 1000 concurrent invocations, you have 100GB of memory allocated across 1000 sandboxes — even if each invocation only does 10ms of work and the other 990ms of the second the sandbox is alive, it is doing nothing. The platform bills you for the duration of each invocation (per-GB-second), so you pay for 1000 × 100MB × 10ms = 1,000 GB-ms of compute, but you have allocated 100GB of capacity across the fleet at peak. Cloud Run is the exception: it supports **multi-request concurrency** via the `--concurrency` flag (default 80, max 1000), allowing up to 1000 concurrent HTTP requests to be multiplexed onto a single sandbox.

```text
  Single-request-per-sandbox (Lambda, Workers, Edge Functions):
  ┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────┐
  │Sandbox#1│  │Sandbox#2│  │Sandbox#3│  │Sandbox#4│   4 concurrent invocations → 4 sandboxes
  │ req A   │  │ req B   │  │ req C   │  │ req D   │   each sandbox has its own:
  │         │  │         │  │         │  │         │   - runtime (Node.js, V8, etc.)
  └─────────┘  └─────────┘  └─────────┘  └─────────┘   - module scope (DB pool, cache)
                                                          - memory allocation

  Multi-request-per-sandbox (Cloud Run --concurrency=80):
  ┌─────────────────────────────────────────────┐
  │ Sandbox #1                                  │   4 concurrent invocations → 1 sandbox
  │  ┌──────┐  ┌──────┐  ┌──────┐  ┌──────┐    │   shared:
  │  │req A │  │req B │  │req C │  │req D │    │   - one runtime process
  │  └──────┘  └──────┘  └──────┘  └──────┘    │   - one module scope (DB pool shared!)
  │   (all multiplexed onto the same process)  │   - one memory allocation
  └─────────────────────────────────────────────┘
```

The Cloud Run multi-request model has two big advantages. First, **resource efficiency**: one Node.js process with one connection pool can serve 80 concurrent requests, instead of 80 processes with 80 connection pools. For database-backed workloads, this is the difference between 5 connections to Postgres (one shared pool of 5) and 400 connections (80 sandboxes × 5 per pool) — see [[12.04.02. Solving Serverless Database Connection Limits]] for why this matters. Second, **cold-start amortization**: one cold start serves 80 concurrent requests, instead of 80 cold starts. Under burst traffic, this is dramatic — a sudden spike of 1000 requests on Cloud Run with `--concurrency=80` needs 13 sandboxes (one cold start × 13), while Lambda needs 1000 sandboxes (1000 cold starts unless provisioned concurrency is enabled).

The trade-off is that **the handler code must be thread-safe** when multi-request concurrency is enabled. A Cloud Run Node.js handler runs each request on the libuv event loop (effectively single-threaded, with `await` yielding control between requests), so concurrent requests interleave at every `await` point — anything in module scope is shared, and you must not mutate it without synchronization. A Cloud Run Python handler using `asyncio` is the same. A Cloud Run Go handler using goroutines is truly concurrent (multiple OS threads if `GOMAXPROCS > 1`), so you must protect shared state with mutexes. A Cloud Run Java handler using Spring Boot's Tomcat is multi-threaded with a thread pool, and your `@Service` beans are singletons shared across threads — the same as any Spring Boot app. The default `--concurrency=80` is therefore safe for code that was already designed for a multi-threaded servlet container (Spring Boot, Express, Django, Rails) but unsafe for code that assumed single-request isolation (most Lambda handlers).

```text
  Concurrency trade-off (Cloudflare Workers, for comparison):

  Workers uses a different model entirely — each isolate handles one request,
  but isolates are so cheap (~50 KB, microseconds to spawn) that the platform
  spawns one per request without the cost concern. The "concurrency" is
  achieved by having thousands of isolates per workerd process, each running
  its own request. The trade-off is that V8 isolates within the same process
  share the same JS engine and the same OS process, but each has its own
  heap — so they cannot share module-scoped state at all (no in-process
  cache benefit) but they also cannot interfere with each other's memory.

  ┌──────────────────────────────────────────────────────────────┐
  │ workerd process (single OS process, single V8 engine)        │
  │  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐         │
  │  │Isolate #1│ │Isolate #2│ │Isolate #3│ │Isolate #4│  ...     │
  │  │ req A    │ │ req B    │ │ req C    │ │ req D    │  1000s  │
  │  │  (heap)  │ │  (heap)  │ │  (heap)  │ │  (heap)  │         │
  │  └──────────┘ └──────────┘ └──────────┘ └──────────┘         │
  │  (each isolate has its own heap — no shared module scope)    │
  └──────────────────────────────────────────────────────────────┘
```

**The production failure mode** of the single-request-per-sandbox model is the **database connection explosion** described in [[12.04.02. Solving Serverless Database Connection Limits]]: 1000 concurrent Lambda invocations × 5 connections per sandbox = 5000 connections to Postgres, which dies at ~100 connections. The fix is one of: (1) use Cloud Run with `--concurrency=80` to share a single pool across 80 concurrent requests; (2) put PgBouncer in front of Postgres to multiplex 5000 client connections onto 25 server connections; (3) use an HTTP-based DB driver (Supabase, Neon) that has no connection concept; (4) use a serverless-native DB (DynamoDB, Aurora Serverless Data API) that speaks HTTP. The production failure mode of the multi-request model is **thread-safety bugs that did not manifest on Lambda** — a handler that mutated a module-scoped `Map` worked fine on Lambda (no concurrency), breaks on Cloud Run (race condition corrupts the map under concurrent access). The metric that reveals this is intermittent `undefined is not a function` / `ConcurrentModificationException` errors that appear only at high concurrency and disappear at low concurrency. The fix is either to make the shared state thread-safe (mutex, `ConcurrentHashMap`, etc.) or to set `--concurrency=1` on Cloud Run to force Lambda-style isolation.
