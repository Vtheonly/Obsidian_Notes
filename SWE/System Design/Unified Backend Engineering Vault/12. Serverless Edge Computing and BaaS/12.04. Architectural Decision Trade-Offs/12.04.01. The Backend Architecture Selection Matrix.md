# 12.04.01. The Backend Architecture Selection Matrix

## What This Is

There are four mainstream ways to host a backend today: the **traditional long-running server** (a Spring Boot JAR in a Kubernetes pod, an Express app on an EC2 instance, a Django app on a VPS), the **serverless function** (AWS Lambda, Google Cloud Run, Azure Functions — covered in [[12.01.01. Serverless Execution Lifecycle]]), the **Backend-as-a-Service** (Supabase, Firebase — covered in [[12.03.01. Supabase Architecture]] and [[12.03.02. Firebase Architecture]]), and the **edge function** (Cloudflare Workers, Vercel Edge Functions — covered in [[12.02.01. V8 Isolates vs. Container Virtualization]]). Each is the right answer for some workloads and the wrong answer for others, and the wrong choice will cost you — either in latency, in operational pain, in vendor lock-in, or in cold hard money. This note gives you the decision matrix: when each pattern wins, when each loses, what the cost crossover points are, and what the lock-in trade-off looks like.

The decision is rarely obvious because the four patterns are not strict substitutes — they sit on different axes. The traditional server optimizes for control and predictable cost at the expense of operational overhead. The serverless function optimizes for scale-to-zero and operational simplicity at the expense of cold starts and per-invocation cost. The BaaS optimizes for frontend-developer productivity at the expense of vendor lock-in and schema rigidity. The edge function optimizes for global latency at the expense of API surface restrictions. The right pattern depends on which axis matters most for your workload, and that often changes over the lifetime of a product — many systems start on BaaS (fast prototype), migrate to serverless (scale-out), migrate to traditional servers (cost optimization at high traffic), and add edge functions for specific latency-sensitive paths. This note gives you the framework for making each of those decisions deliberately rather than by accident.

## The Details

### Multi-dimensional quantitative evaluation: Monolith vs. Microservices vs. Serverless vs. BaaS

The four options are not interchangeable — they make different assumptions about the workload, and the wrong choice will manifest as a specific failure mode under load. The decision tree for picking the right pattern:

```text
  DECISION TREE — Which backend pattern?

  Q1: Is the team primarily frontend/mobile developers (no backend expertise)?
   → YES: BaaS (Supabase or Firebase)
        → If you need SQL and JOINs: Supabase
        → If you need real-time sync and offline: Firebase
   → NO: continue to Q2

  Q2: Is the workload event-driven (cron, queue, stream, webhook) with sparse or bursty traffic?
   → YES: Serverless function (Lambda or Cloud Run)
        → If you need >15min execution: traditional server
        → If you need to handle 10K+ req/s sustained: traditional server
   → NO: continue to Q3

  Q3: Do you need sub-100ms p99 latency for globally-distributed users, with simple logic?
   → YES: Edge function (Cloudflare Workers or Vercel Edge)
        → For complex logic: edge function as a routing/auth layer in front of
          a regional serverless function or traditional server
   → NO: continue to Q4

  Q4: Is the traffic sustained and high (>10 req/s average, predictable growth)?
   → YES: Traditional server (Spring Boot on K8s, Express on EC2, Django on ECS)
        → Cheapest at scale, most control, most operational overhead
   → NO: continue to Q5

  Q5: Is this an internal tool or low-traffic MVP (<10 req/s, <1000 users)?
   → YES: Serverless function (no ops, scales to zero, free tier covers it)
   → NO: Re-evaluate — your workload does not fit any pattern cleanly; consider
         a hybrid (edge + serverless, or BaaS + serverless for the complex parts)
```

A real-world worked example: a SaaS API with three workloads — (1) a high-traffic `/api/transactions` endpoint handling 500 req/s sustained with complex business logic, (2) a low-traffic `/api/webhooks/stripe` endpoint handling 5 req/s bursty with simple idempotent processing, (3) a `/api/dashboard` endpoint that needs to be fast for users in 30 countries. The right pattern for each: (1) **traditional server** — 500 req/s sustained is too expensive on serverless (would cost ~$5000/month on Lambda vs ~$200/month on a 4-pod K8s deployment), and the business logic benefits from JVM warmup; (2) **serverless function** — 5 req/s bursty is perfect for Lambda, scales to zero between bursts, free tier covers most of it, and the webhook handler is simple; (3) **edge function** — global users need <100ms p99, the dashboard handler is mostly "fetch from cache, render JSON," and the cache lives in Cloudflare KV. This hybrid architecture is more common than any single-pattern deployment — most production systems mix at least two of the four patterns, with the edge function as the global front door, the serverless function for bursty/event-driven work, and the traditional server for sustained high-traffic business logic.

**The production failure mode** of pattern selection is the **"we chose BaaS for speed-to-market and now we cannot scale"** trap. A startup builds its MVP on Firebase — auth, Firestore, Cloud Functions, the whole stack — and ships in 3 weeks instead of 3 months. Six months later, the user base has grown 10×, Firestore reads are costing $15,000/month (because every screen view generates 50 reads and the team did not optimize the data model), the team wants to add a feature that requires SQL JOINs (impossible on Firestore), and the mobile team is blocked because every backend change requires redeploying the Firebase Security Rules and the client SDK. The migration to a traditional backend is painful — 6 months of work, a data migration from Firestore to Postgres, a rewrite of the client SDK calls, a new auth system. The metric that reveals this is the cost-per-user curve: if Firestore cost grows faster than revenue per user, you are on the wrong side of the BaaS scale curve. The deeper mitigation is to choose BaaS only for products that have a clear "graduation plan" — know in advance when you will migrate off (e.g., "at 100K MAU we will move to Supabase + serverless"), and architect the client SDK calls so they can be redirected to a different backend without a full client rewrite. The deeper truth is that **no backend pattern is forever** — the right choice at MVP stage is rarely the right choice at scale, and the cost of migrating should be priced into the original decision.

### Economic Analysis: Fixed monthly infrastructure costs vs. Pay-per-invocation usage curves

The cost model of each backend pattern is structurally different, and the right choice depends on the traffic profile. The traditional server bills a **fixed monthly cost** regardless of traffic — you pay $200/month for an EC2 instance whether it serves 0 req/s or 1000 req/s. The serverless function bills **per-invocation + per-GB-second** — you pay $0 for 0 invocations, and the cost scales linearly with traffic. The BaaS bills **per-request + per-GB-stored + per-read** — Firestore bills $0.036 per 100K reads, $0.18 per 100K writes, $0.026 per GB/month stored; Supabase bills $25/month flat for the Pro tier plus $0.125 per GB of database storage over 8GB. The edge function bills **per-request + per-CPU-time** — Cloudflare Workers bills $0.30 per million requests plus $0.02 per million CPU-seconds on the Standard plan.

The cost curves cross at different points depending on the workload. The key insight is that **serverless is cheap at low traffic and expensive at high traffic**, while **traditional servers are expensive at low traffic and cheap at high traffic**. The crossover point is roughly where the per-invocation cost equals the per-server cost — for AWS Lambda vs an EC2 t3.small, the crossover is around 100M invocations/month at 100ms duration with 512MB memory.

```text
  Worked example: 100M requests/month, 100ms duration, 512MB memory

  ┌────────────────────────────────────────────────────────────────────┐
```

The cost crossover at higher traffic is even more dramatic. At 1 billion requests/month, Lambda costs ~$2,800/month while a single EC2 t3.medium (~$30/month) still handles the load — the cost ratio is 100× in favor of the traditional server. At 10 billion requests/month (rare, but real for high-traffic APIs), Lambda costs $28,000/month while a 4-pod EKS deployment costs ~$200/month — a 140× cost difference. This is why high-traffic APIs (Stripe, Twilio, GitHub) are not on serverless — the economics do not work at scale.

The BaaS cost curve is different again — it is dominated by the database read/write cost, not the compute cost. Firestore charges $0.036 per 100K document reads and $0.18 per 100K writes, which sounds cheap but adds up: an app where each user views 10 screens per session, each screen does 20 reads, with 100K daily active users = 100K × 10 × 20 = 20M reads/day = 600M reads/month = $216/month just for reads. If the same app does 5 writes per session, that's 50M writes/month = $90/month for writes. Add storage ($0.108/GB/month, 100GB = $10.80), bandwidth, Cloud Functions executions, and the total is ~$400/month for a 100K DAU app — a cost that scales linearly with users. By comparison, a Supabase Pro plan with the same workload would cost $25/month plus Edge Function invocations — Supabase bills per Edge Function invocation, not per database read, so the cost curve is much flatter for read-heavy workloads.

The cost analysis must include **operational cost** — the cost of the engineer-hours to keep the system running. A traditional server fleet needs monitoring, alerting, on-call rotations, capacity planning, security patching, certificate renewal, log rotation, backup verification — typically 0.5–2 FTE of devops work for a fleet of 10–50 servers. A serverless deployment needs almost none of that — the cloud provider handles scaling, patching, and capacity planning. A BaaS deployment needs even less — the provider handles the database too. The cost of an engineer at $150K/year fully loaded is $12,500/month — a fleet that needs 0.5 FTE of devops costs $6,250/month in human time, which is far more than the $200/month EC2 bill. The economics shift: at small scale, serverless and BaaS are dramatically cheaper once you include ops cost; at large scale, the per-invocation cost overtakes the ops cost and traditional servers win again.

**The production failure mode** of the economic analysis is the **"serverless bill shock"** — a startup deploys a Lambda function, the traffic grows 10×, the AWS bill grows 10× linearly, and the team realizes they are paying $20,000/month for a workload that would cost $200/month on EC2. The fix is to set billing alarms on serverless spend (CloudWatch billing alarm at 80% of budget) and to migrate workloads off serverless when the per-invocation cost exceeds the per-server cost — typically around 100M invocations/month for Lambda. The deeper mitigation is to architect for portability from day one: keep the Lambda handler logic in a framework that can also run on Express (the Serverless Framework, Architect, or plain `http.handle()`), so the migration is "deploy the same code on EC2/ECS" instead of "rewrite the entire backend." The metric that reveals the cost curve problem is `cost per million requests` over time — if it is flat (you are paying the same per request as at low traffic, just more of them), the curve is linear and you should consider migration; if it is decreasing (you negotiated volume discounts, or moved to Workers which has flat pricing), you are fine.

### Operational Overhead vs. Vendor Lock-In risk assessments

The third axis of the decision is the trade-off between **operational overhead** (the work you do to keep the system running) and **vendor lock-in** (the cost of migrating off the chosen platform). These two axes are inversely correlated: patterns with low operational overhead tend to have high vendor lock-in, and patterns with high operational overhead tend to have low vendor lock-in. The traditional server has the highest operational overhead and the lowest lock-in — you can migrate from AWS EC2 to Google Compute Engine to your own datacenter in days, because you own the entire stack. The BaaS has the lowest operational overhead and the highest lock-in — migrating from Firebase to anything else requires rewriting the client SDK calls (which use Firebase's proprietary sync protocol), migrating the database (Firestore's NoSQL data model does not map directly to SQL), and rewriting the Security Rules (Firebase's declarative language has no equivalent in Postgres or any other database).

The lock-in dimension is more subtle than it first appears. There are **four kinds of lock-in**, and each pattern locks you in on a different axis:

1. **Infrastructure lock-in** — the platform's specific APIs and resource types. AWS Lambda locks you into the `event` schema (S3 events, API Gateway events, etc.) and the IAM permissions model. Cloudflare Workers locks you into the `FetchEvent` API and the KV/R2/D1 service bindings. Supabase locks you into the PostgREST API schema and the `supabase-js` SDK calls. Firebase locks you into the Firestore SDK calls and the Security Rules language. Mitigation: write a thin abstraction layer over the platform SDK, so the migration is "swap the adapter" instead of "rewrite every call site."

2. **Data lock-in** — the data is stored in a format that is expensive to migrate. Firebase Firestore's NoSQL document model does not map cleanly to SQL — a `users/{userId}/posts/{postId}` hierarchical structure becomes two SQL tables with a foreign key, but the denormalized fields (e.g., `authorName` copied into each post) need to be re-normalized, and the array fields (e.g., `tags: ["foo", "bar"]`) need to become junction tables. A 100GB Firestore database can take months to migrate to Postgres. Supabase's Postgres database is portable (it is just Postgres — you can `pg_dump` and restore to any Postgres), so Supabase has low data lock-in. Cloudflare D1 is SQLite-based, also portable. AWS DynamoDB has high data lock-in (the proprietary NoSQL API does not map to any open-source database).

3. **Runtime lock-in** — the code depends on runtime features that are not portable. Cloudflare Workers' V8 isolate runtime does not support Node.js APIs — a Worker written against `fetch` and WebCrypto can be ported to Vercel Edge or Deno Deploy with minor changes, but porting it to AWS Lambda requires rewriting every API call (no `fetch` natively in Lambda Node.js — must use `https` module or install `node-fetch`). Supabase Edge Functions (Deno) and Cloudflare Workers (workerd) are mostly source-compatible but have small differences in their platform-specific APIs (Supabase's `serve()` vs Cloudflare's `fetch` handler).

4. **Skill lock-in** — the team has invested in learning the platform's quirks. Firebase Security Rules, Cloudflare Workers' Durable Objects, AWS Lambda's event source mappings — these are platform-specific skills that do not transfer. A team that has spent 2 years mastering Firebase Security Rules will resist migrating to Postgres RLS even if it is technically equivalent, because the team's expertise is on the Firebase side. This is the hardest lock-in to overcome — it is human, not technical.

The risk-mitigation pattern is **portability layers**. For serverless: use the Serverless Framework or AWS SAM to define the function abstractly, so the same code can deploy to Lambda, Cloud Run, or Azure Functions. For BaaS: use a thin data-access layer in the client SDK so the calls can be redirected; for Supabase, this is easy (PostgREST is standard REST); for Firebase, this is hard (the real-time sync protocol is proprietary). For edge: write the handler against the Web Standard APIs only (no platform-specific extensions), so the same code runs on Workers, Vercel Edge, and Deno Deploy. For traditional servers: use Docker from day one, so migration between clouds is a redeploy.

The deepest trade-off is the **inverse relationship between operational overhead and lock-in**. The patterns with the lowest ops overhead (BaaS) have the highest lock-in, and the patterns with the lowest lock-in (traditional servers) have the highest ops overhead. You cannot optimize both — you must choose which axis matters more for your organization. A startup with 3 engineers should optimize for low ops overhead and accept the lock-in — they cannot afford to spend half their time on devops, and they will likely pivot before the lock-in matters. An enterprise with 50 engineers and a 10-year horizon should optimize for low lock-in and accept the ops overhead — they will be on the platform long enough that lock-in compounds, and they have the headcount to absorb the ops work.

**The production failure mode** of the lock-in trade-off is the **"we are stuck and cannot migrate"** trap, which manifests years after the original decision. A startup chose Firebase in 2018 because they had 2 engineers and needed to ship fast. By 2024, they have 30 engineers, 5M MAU, and a $40,000/month Firebase bill — but they cannot migrate because: the client SDK calls are embedded in 4 mobile apps and 2 web apps (each with thousands of Firestore query calls), the data model is deeply denormalized (every document has 5 copied fields for performance), the Security Rules are 2000 lines of complex logic that has no direct equivalent in Postgres RLS, and the team's expertise is in Firebase's quirks (the write-batch size limit, the offline-cache behavior, the Security Rules simulator). The migration is estimated at 18 months of work and a 6-month freeze on new features. The metric that reveals this is the **percentage of backend logic that uses platform-specific APIs** — if 80% of the code is `firebase.firestore().collection(...)` calls, you have 80% lock-in. The deeper mitigation is to architect for portability from day one: wrap every Firebase call in a data-access function (`function getPosts(userId) { return firebase.firestore().collection('posts').where('authorId', '==', userId).get(); }`), so the migration is "rewrite the function body" instead of "find and replace across 10,000 call sites." The deeper truth is that **lock-in is not a moral failing** — it is a trade-off you make consciously, in exchange for the productivity gains. The trap is not lock-in itself; it is lock-in without a migration plan. The teams that survive are the ones that document the migration plan up front ("at $X monthly bill or Y MAU, we will begin migrating to Postgres + Spring Boot") and revisit it annually.
