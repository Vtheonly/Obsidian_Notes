# 12.02.02. Edge Runtime Platforms Vercel and Cloudflare

## What This Is

Three production-grade platforms run serverless compute on V8 isolates at the global edge: Cloudflare Workers (300+ POPs, the largest edge network), Vercel Edge Functions (18+ regions, the tightest Next.js integration), and Deno Deploy (35+ regions, the only one with a TypeScript-native runtime out of the box). All three use the same isolation mechanism described in [[12.02.01. V8 Isolates vs. Container Virtualization]] — a V8 isolate per request, sub-millisecond cold starts, ~100 KB memory overhead per isolate — but they differ in their platform services, their API surface, and their target use case. This note walks through each platform's architecture, the concrete code you write against each, the storage and coordination services each provides, and the production use cases that make the edge model compelling.

The edge model inverts the traditional server topology. Instead of one origin server in us-east-1 serving users in São Paulo with 150ms RTT, you have 300+ edge POPs each running the function 5–20ms from the user. The user's first request hits the nearest POP (e.g., São Paulo), the function executes there, and the function's downstream calls (to the database, to internal APIs) cross the long-distance network only once. The function itself runs in <5ms cold start + <5ms execution; the round-trip to the user is <20ms; the cross-region call to the origin database is 80–150ms. Total user-perceived latency: ~100–180ms instead of 300+ms. The trade-off is that the function cannot use Node.js APIs (no `fs`, no `child_process`, no TCP sockets — see 12.02.01), and the storage layer is constrained (you can read from edge KV stores in <5ms, but you cannot run a SQL query against Postgres in <5ms — the Postgres is in us-east-1 and the function is in São Paulo).

## The Details

### Running compute globally distributed across edge PoPs adjacent to end users

The "edge" in edge compute means **points of presence (POPs) physically close to the user**. Cloudflare operates 300+ POPs in 100+ countries (every major city has one — São Paulo, Mumbai, Singapore, Sydney, Lagos, Johannesburg); Vercel operates 18+ edge regions (smaller network, but tightly integrated with their CDN); Deno Deploy operates 35+ regions. When a user makes an HTTP request, DNS resolves to the nearest POP based on the user's IP geolocation (typically using EDNS Client Subnet to pass the user's /24 prefix to the authoritative DNS), and the request lands at that POP's edge server. The server runs the user's Worker isolate in-process, executes the handler, and returns the response — all without ever touching the origin server.

The key insight is that the edge network was originally built for **CDN caching** (Cloudflare's CDN, Vercel's CDN, Fastly's CDN) — static files served from POPs close to users. Edge compute is the natural extension: instead of just serving static files from the POP, run a small piece of code at the POP that can transform requests, route them, do auth checks, and call out to backends. The CDN infrastructure (the anycast routing, the global DNS, the POP servers, the SSL termination, the cache layer) was already deployed — the platforms just added a V8 runtime on top of it to make the POPs programmable.

The latency advantage scales with the user's distance from the origin. A user in us-east-1 hitting a us-east-1 origin sees no benefit from edge compute (the POP is in the same city as the origin, so the only saving is the cold-start delta). A user in Mumbai hitting a us-east-1 origin sees a dramatic benefit (the Mumbai POP runs the function 5ms from the user, then makes one cross-region call to us-east-1 at 250ms RTT, instead of the user making a 250ms RTT to us-east-1 and then the function adding 10ms).

The three platforms differ in their POP count and routing model. **Cloudflare Workers** has the largest network (300+ POPs) and the most aggressive anycast routing — a request from any user in the world hits the nearest POP within 50ms RTT. **Vercel Edge Functions** runs on a smaller network (18+ regions) but is deeply integrated with Next.js — every Next.js page can opt into edge rendering via `export const runtime = 'edge'`, and the function is deployed to all 18 regions simultaneously. **Deno Deploy** runs on 35+ regions using the Deno runtime (which includes TypeScript compilation natively, no separate build step), and is unique in exposing a `Deno.serve()` API that is the simplest of the three to write against.

The platform services each provides are the second differentiator. **Cloudflare Workers** offers: `KV` (eventually-consistent key-value store, replicated to all POPs, ~10ms read latency, ~60s propagation delay for writes), `Durable Objects` (strongly-consistent stateful objects with single-threaded execution, used for coordination — chat rooms, rate limiters, distributed locks), `R2` (S3-compatible object storage with no egress fees), `D1` (SQLite-based SQL database, eventually replicated to all POPs), `Queues` (managed message queues), `Hyperdrive` (connection pooler for Postgres — solves the connection-limit problem from [[12.04.02. Solving Serverless Database Connection Limits]] at the edge). **Vercel Edge Functions** offers: `Edge Config` (low-latency key-value config, ~5ms read), `KV` (backed by Upstash Redis), `Postgres` (backed by Neon, with an HTTP driver for edge compatibility). **Deno Deploy** offers: `Deno KV` (built-in key-value store, eventually consistent, ACID transactions within a single key).

```text

  ┌───────────────────┬──────────────────┬──────────────────┬──────────────────┐
```

**The production failure mode** of edge compute is **the edge-database mismatch**: the user's request lands at a POP 5ms away, the function runs in 5ms, and then the function makes a cross-region database call that takes 80–250ms — undoing the latency advantage. The function is fast, but the data is far away. The three solutions, in increasing order of complexity: (1) cache aggressively at the edge using KV — read-once from origin, cache for 60 seconds in KV, subsequent reads are 10ms from any POP; (2) move the data to the edge using D1 (read replicas at every POP, ~10ms read latency, ~100ms write latency — works for read-heavy workloads); (3) accept the cross-region hop and use Hyperdrive (or the Supabase REST API, or Neon's HTTP driver) to make the hop as cheap as possible. The metric that reveals the mismatch is the p99 of the function's `fetch()` calls to the origin database — if it exceeds your SLO, you need to either cache more or move the data closer. The deeper failure is **architectural**: if your workload is database-heavy and your users are globally distributed, edge compute is the wrong choice — you should use a multi-region database (CockroachDB, YugabyteDB, Aurora Global Database) with a traditional server in each region, not edge compute.

### Web Standard APIs at the edge: `fetch`, `Request`, `Response`, `TransformStream`, `Crypto`

The API surface available inside a V8 isolate is the **Web Standard API set** — the same APIs available in a web browser, defined by the WHATWG and W3C specifications. This is a deliberate design choice by Cloudflare, Vercel, and Deno: by exposing only standardized browser APIs, they ensure that code written for the edge is portable across platforms (a Worker that uses only `fetch` and `Response` runs on Cloudflare Workers, Vercel Edge, Deno Deploy, and the browser with no changes). The trade-off is that none of the Node.js-specific APIs are available — no `fs`, no `child_process`, no `net`, no `http`, no `crypto` (Node's crypto, that is — WebCrypto is available), no `Buffer` (use `Uint8Array`), no `process` (use the platform-specific `env` parameter), no `require` (use ES module `import`).

The concrete API surface, with the typical use case for each:


The concrete code for each platform shows the API in action. A Cloudflare Worker uses the `FetchEvent` model — register a listener for `fetch` events:

```javascript
// Cloudflare Worker — minimal "Hello, World"
export default {
  async fetch(request, env, ctx) {
    const url = new URL(request.url);

    // Routing
    if (url.pathname === '/api/hello') {
      const name = url.searchParams.get('name') || 'world';
      return Response.json({ message: `Hello, ${name}!` });
    }

    if (url.pathname === '/api/proxy') {
      // Use fetch() to call a downstream service
      const upstream = await fetch('https://api.example.com/data', {
        headers: { 'Authorization': `Bearer ${env.API_KEY}` },
      });
      const data = await upstream.json();
      return Response.json({ proxied: data });
    }

    if (url.pathname === '/api/hash') {
      // WebCrypto is async — must await
      const data = new TextEncoder().encode('hello world');
      const hash = await crypto.subtle.digest('SHA-256', data);
      const hex = [...new Uint8Array(hash)].map(b => b.toString(16).padStart(2, '0')).join('');
      return Response.json({ sha256: hex });
    }

    return new Response('Not Found', { status: 404 });
  },
};
```

A Vercel Edge Function uses a request-handler export — same API, slightly different shape:

```typescript
// Vercel Edge Function — runs at the edge in Next.js
// File: app/api/edge/route.ts
import { NextRequest } from 'next/server';

export const runtime = 'edge';  // opt into edge runtime
export const dynamic = 'force-dynamic';

export async function GET(request: NextRequest) {
  const country = request.geo?.country || 'unknown';

  // Geo-routing: serve different content based on user's country
  if (country === 'BR') {
    return Response.json({ greeting: 'Olá!', country });
  }
  if (country === 'JP') {
    return Response.json({ greeting: 'こんにちは!', country });
  }
  return Response.json({ greeting: 'Hello!', country });
}

export async function POST(request: NextRequest) {
  // Verify a JWT from the Authorization header — at the edge,
  // before the request ever reaches the origin
  const auth = request.headers.get('Authorization') || '';
  const token = auth.replace('Bearer ', '');

  try {
    // WebCrypto verifies the JWT signature — async, but ~1ms
    const isValid = await verifyJwt(token, process.env.JWT_PUBLIC_KEY!);
    if (!isValid) {
      return new Response('Unauthorized', { status: 401 });
    }
    // Forward the request to the origin
    const upstream = await fetch('https://api.example.com/secure', {
      method: 'POST',
      headers: request.headers,
      body: await request.text(),
    });
    return upstream;
  } catch (err) {
    return new Response('Invalid token', { status: 400 });
  }
}

async function verifyJwt(token: string, publicKey: string): Promise<boolean> {
  const [headerB64, payloadB64, sigB64] = token.split('.');
  const key = await crypto.subtle.importKey(
    'spki',
    Uint8Array.from(atob(publicKey), c => c.charCodeAt(0)),
    { name: 'RSASSA-PKCS1-v1_5', hash: 'SHA-256' },
    false,
    ['verify']
  );
  const data = new TextEncoder().encode(`${headerB64}.${payloadB64}`);
  const sig = Uint8Array.from(atob(sigB64), c => c.charCodeAt(0));
  return crypto.subtle.verify('RSASSA-PKCS1-v1_5', key, sig, data);
}
```

A Deno Deploy handler uses `Deno.serve()` — the simplest of the three:

```typescript
// Deno Deploy — runs globally on 35+ regions
Deno.serve(async (req: Request) => {
  const url = new URL(req.url);

  if (url.pathname === '/kv') {
    // Deno KV — strongly consistent within a key, eventually consistent across keys
    const kv = await Deno.openKv();
    await kv.set(['visits', url.pathname], (await kv.get(['visits', url.pathname])).value ?? 0 + 1);
    const count = await kv.get(['visits', url.pathname]);
    return Response.json({ visits: count.value });
  }

  // Streaming response — TransformStream for chunked output
  if (url.pathname === '/stream') {
    const stream = new ReadableStream({
      async start(controller) {
        for (let i = 0; i < 10; i++) {
          controller.enqueue(new TextEncoder().encode(`chunk ${i}\n`));
          await new Promise(r => setTimeout(r, 100));
        }
        controller.close();
      },
    });
    return new Response(stream, {
      headers: { 'Content-Type': 'text/plain' },
    });
  }

  return new Response('Not Found', { status: 404 });
});
```

The platform differences are subtle but real. Cloudflare Workers exposes `request`, `env`, and `ctx` (the `ctx.waitUntil()` method lets you schedule background work that runs after the response is sent — within the request's CPU budget). Vercel Edge Functions exposes a `NextRequest` object that adds `request.geo` (country, city, latitude, longitude from Cloudflare's IP-to-geo database) and integrates with Next.js's routing. Deno Deploy exposes `Deno.serve()` and `Deno.openKv()` — the only platform with a built-in strongly-consistent KV store. The Web Standard APIs (`fetch`, `Request`, `Response`, `crypto.subtle`, `TextEncoder`) work identically across all three; only the platform-specific extensions differ.

**The production failure mode** of the Web Standard API restriction is the **silent dependency on a Node.js API** that breaks at deploy time. The classic case is a Next.js app that uses a third-party auth library (NextAuth.js v3, for example) which imports `crypto` from Node.js — this works on Vercel's Node.js serverless functions but fails on Vercel Edge Functions with `Module not found: Can't resolve 'crypto'`. The fix is to either use the edge-compatible version of the library (NextAuth.js v4 + has edge support via `jose` instead of `jsonwebtoken`), or accept that the function must run on Node.js Lambda (with the 250ms cold start), or rewrite the auth code to use WebCrypto directly. The deeper failure is the **performance cliff when the function does too much**: a Worker that runs 5ms of logic + 1 `fetch()` call is fast (10ms total); a Worker that runs 50ms of logic + 5 `fetch()` calls in sequence is slow (200ms+ total, dominated by the downstream calls). The metric that reveals this is the function's CPU time vs wall-clock time — if wall-clock is 10× CPU, the function is I/O-bound and the downstream calls are the bottleneck, not the edge runtime itself.

### The Edge Database Dilemma: Executing compute at the global edge while storage remains a...

The central architectural tension of edge compute is that **the function runs at the edge (close to the user) but the data lives in a region (close to nothing)**. The user in São Paulo hits the São Paulo POP in 5ms, the function runs in 5ms, and then the function needs to read a row from Postgres — which is in us-east-1, 80ms away. The round-trip is 5ms + 5ms + 80ms + 80ms + 5ms = 175ms. Without the edge function, the user would have hit the origin directly: 150ms (user→origin) + 10ms (function) + 150ms (origin→user) = 310ms. So the edge function still wins (175ms vs 310ms), but the win is much smaller than the theoretical 2× speedup that comes from running the function 5ms from the user — most of the latency is now the database hop, not the function execution.

This is the **edge database dilemma**: you have moved compute to the edge, but you have not moved storage. The function is fast, but the data is far. Three architectural patterns address this, each with a different trade-off:

```text
  Pattern 1: Origin database, single cross-region hop (most common)
  ┌──────────┐     ┌──────────────┐     ┌──────────────────┐
  │ User     │ ──→ │ Edge POP     │ ──→ │ Postgres in      │
  │ São Paulo│     │ São Paulo    │     │ us-east-1 (origin)│
  │ RTT 5ms  │     │ Function 5ms │     │ Query 10ms       │
  └──────────┘     └──────────────┘     └──────────────────┘
   User-perceived: 5 + 5 + 80 + 10 + 80 + 5 = 185ms
   Pro: simple, single source of truth
   Con: 80ms cross-region hop dominates; no read scaling

  Pattern 2: Read replicas at the edge (e.g., Cloudflare D1, Supabase read replicas)
  ┌──────────┐     ┌──────────────┐     ┌──────────────────┐
  │ User     │ ──→ │ Edge POP     │ ──→ │ D1 read replica  │
  │ São Paulo│     │ São Paulo    │     │ (in São Paulo)   │
  │ RTT 5ms  │     │ Function 5ms │     │ Query 10ms       │
  └──────────┘     └──────────────┘     └──────────────────┘
                           │
                           └──→ (writes go to origin, ~80ms)
   User-perceived: 5 + 5 + 10 + 5 = 25ms (reads); 5 + 5 + 80 + 10 + 80 + 5 = 185ms (writes)
   Pro: read latency is amazing — sub-30ms for global users
   Con: eventual consistency (60s lag for D1), writes still slow, schema migrations complex

  Pattern 3: Cache aggressively at the edge (Workers KV, Edge Config)
  ┌──────────┐     ┌──────────────┐     ┌──────────────────┐
  │ User     │ ──→ │ Edge POP     │ ──→ │ KV cache (local) │
  │ São Paulo│     │ São Paulo    │     │ Read 10ms        │
  │ RTT 5ms  │     │ Function 5ms │     └──────────────────┘
  └──────────┘     └──────────────┘
                           │
                           (cache miss → origin fetch, ~80ms;
                            cache refreshed every 60s by a cron Worker)
   User-perceived: 5 + 5 + 10 + 5 = 25ms (cache hit, ~99% of traffic)
                   5 + 5 + 80 + 10 + 80 + 5 = 185ms (cache miss, ~1% of traffic)
   Pro: best latency for read-heavy workloads
   Con: stale data (up to 60s), cache invalidation is hard, writes still slow

  Pattern 4: HTTP-native database (Supabase REST, Neon HTTP driver, PlanetScale)
  ┌──────────┐     ┌──────────────┐     ┌──────────────────┐
  │ User     │ ──→ │ Edge POP     │ ──→ │ PostgREST HTTP   │
  │ São Paulo│     │ São Paulo    │     │ API in us-east-1 │
  │ RTT 5ms  │     │ Function 5ms │     │ Query 10ms       │
  └──────────┘     └──────────────┘     └──────────────────┘
   User-perceived: 5 + 5 + 80 + 10 + 80 + 5 = 185ms
   Pro: no connection concept, no PgBouncer needed, fits edge runtime model
   Con: same latency as Pattern 1, but simpler ops
```

The choice between these patterns depends on the read/write ratio and the staleness tolerance. A read-heavy workload with a high staleness tolerance (a marketing site, a blog, a docs site) is perfect for Pattern 3 (KV caching) — 99% of reads hit the cache in <30ms, the 1% misses fall through to the origin in <200ms, and writes propagate to the cache within 60s. A read-heavy workload with low staleness tolerance (a banking app showing account balances) cannot use Pattern 3 — it needs Pattern 1 (single source of truth, accept the cross-region hop) or Pattern 2 with strong consistency (CockroachDB, which is not edge-native but can run in multiple regions). A write-heavy workload (chat, collaborative editing, gaming) needs Pattern 4 or Durable Objects — Pattern 3 does not work because the cache invalidation on writes is too expensive, and Pattern 2 does not work because writes are still slow.

Cloudflare's Durable Objects are the most architecturally interesting answer to the dilemma. A Durable Object is a single-threaded, strongly-consistent, stateful object that lives at one POP at a time (the POP closest to the first request that created it, or a POP chosen by an `idFromName()` routing function). All requests for that object are routed to the same POP, where they execute single-threaded against the object's in-memory state (which is persisted to a transactional storage layer). This gives you a strongly-consistent, low-latency store for objects that have a natural partition key — a chat room (keyed by room ID), a rate-limiter (keyed by user ID), a multiplayer game session (keyed by game ID). The trade-off is that all requests for the same object go to the same POP, which may be far from some users — a user in Mumbai hitting a Durable Object in São Paulo sees 250ms RTT. The pattern works when the object is regional (a chat room with mostly Brazilian users) and fails when the object is global (a chat room with users on every continent).

```javascript
// Cloudflare Durable Object — rate limiter
export class RateLimiter {
  constructor(state, env) {
    this.state = state;  // DurableObjectState — provides storage and transactional semantics
    this.env = env;
  }

  async fetch(request) {
    // Single-threaded execution — only one request in this method at a time
    const count = (await this.state.storage.get('count')) || 0;
    const windowStart = (await this.state.storage.get('windowStart')) || Date.now();

    if (Date.now() - windowStart > 60_000) {
      // Reset window
      await this.state.storage.put('count', 1);
      await this.state.storage.put('windowStart', Date.now());
      return Response.json({ allowed: true, remaining: 99 });
    }

    if (count >= 100) {
      return Response.json({ allowed: false, remaining: 0 }, { status: 429 });
    }

    await this.state.storage.put('count', count + 1);
    return Response.json({ allowed: true, remaining: 100 - count - 1 });
  }
}

// Worker that routes requests to the right Durable Object
export default {
  async fetch(request, env) {
    const userId = getUserIdFromRequest(request);
    // idFromName routes by user ID — same user always hits the same Durable Object
    const id = env.RATE_LIMITER.idFromName(userId);
    const stub = env.RATE_LIMITER.get(id);
    return stub.fetch(request);
  },
};
```

**The production failure mode** of the edge database dilemma is the **"we moved to edge and our p99 got worse"** surprise. A team migrates an API from Lambda (us-east-1) to Cloudflare Workers, expecting a latency improvement. For US users, p99 goes from 200ms to 50ms — great. For European users, p99 goes from 350ms to 80ms — great. For Asian users, p99 goes from 500ms to 300ms — and the team is confused, because they expected <100ms. The reason is that the Asian users' Workers are making `fetch()` calls to the Postgres in us-east-1, and the cross-region hop from Singapore to us-east-1 is ~250ms RTT — there is no way to get below ~500ms round-trip without moving the database. The metric that reveals this is the function's external `fetch()` latency, broken down by the user's region — if Asian users' `fetch()` calls take 250ms and US users' take 10ms, the database location is the bottleneck. The fix is either (1) deploy read replicas closer to users (Supabase read replicas in eu-west-1 and ap-southeast-1, Cloudflare D1 in every POP, CockroachDB multi-region), (2) cache aggressively (move read-heavy data into KV, accept up to 60s staleness), or (3) accept that some workloads cannot be served from the edge and use a traditional multi-region server deployment instead. The decision matrix in [[12.04.01. The Backend Architecture Selection Matrix]] covers this trade-off explicitly.
