# 13.04.06. Failure Injection and Rebalance Resilience Verification

## Purpose

The Transactional Outbox pipeline built in [[13.04.02. Primary Engine Spring Boot Producer and Debezium CDC]] — [[13.04.05. Invoice Generator Worker PHP Laravel Queue]] is not trustworthy until you have watched it break. Every Kafka-based system ships with a long list of "should" guarantees: *consumers should rebalance in seconds, offsets should commit on shutdown, the broker should survive a rolling restart, the producer should retry on transient failures*. None of these are true by default — they are configured to be true, and the configuration is the part that breaks in production. The purpose of this note is to **deliberately inject the failures that production will eventually deliver anyway**, observe the pipeline's response, and turn each observation into a hardening change in code or config.

The chaos scenarios below are not hypotheticals. They are the four most common root causes of Kafka-pipeline outages as recorded in public post-mortems (GitLab 2017, Shopify 2019, Cloudflare 2020) plus the disk-fill failure that every operator encounters within their first year of running Kafka in production. Each scenario names the injection command, the metric you must watch, the acceptable threshold, and the failure mode the threshold is designed to catch. Run them against your local `docker compose` stack first; once you trust the local behaviour, run them against a staging cluster with three brokers and real cross-AZ network latency to expose the cases the single-broker local setup hides (notably the controller failover race and the under-replicated-partition cliff).

The deliverable is a **Resilience Verification Matrix** (below) with measured numbers for each scenario, plus a written post-mortem for every scenario that violated its threshold. The matrix is the artifact an SRE reviewer asks for during a launch review — "show me the worst-case rebalance time" and "show me the message-loss count under broker kill" are questions you must answer with data, not assertions. If you cannot reproduce a failure mode locally, that is itself a finding: either your local topology does not match production (single broker vs. three brokers is the most common gap), or your instrumentation is blind to that failure class (the most common gap is no consumer-lag metric per partition, only per topic).

## Resilience Verification Matrix

The matrix below is the contract. Each row is a chaos scenario; each column is an observable metric. Run every scenario against every consumer group (analytics-python, broadcaster-node, invoice-php). A cell that says "≤ 30 s" means the system is considered healthy if the metric returns below that threshold within 30 seconds of the injection. "Msg loss" and "Msg dup" must always be zero for an exactly-once-configured pipeline; any non-zero value is a bug, not a degradation.

| # | Scenario | Injection command | Consumer lag spike | Rebalance time | Throughput drop | Msg loss | Msg dup | Recovery time |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | Kill the Kafka broker | `docker compose kill kafka` | ≤ 5 K msgs | n/a (no broker) | 100 % during outage | 0 | 0 | ≤ 15 s after `docker compose start kafka` |
| 2 | Kill one consumer (group rebalance) | `docker compose kill analytics-consumer-1` | ≤ 1 K msgs | ≤ 10 s | ≤ 30 % for 10 s | 0 | ≤ 5 (in-flight redeliveries) | ≤ 12 s |
| 3 | Inject 5 s producer latency | `tc qdisc add dev eth0 root netem delay 5s` in producer container | ≤ 2 K msgs | n/a | ≤ 80 % for 5 s | 0 | 0 | immediate on `tc qdisc del dev eth0 root` |
| 4 | Pause a single partition | `docker exec kafka kafka-partitions.sh --alter --topic orders.events --partitions 6 --pause --partition 3` (or stop one consumer) | grows on partition 3 only | ≤ 10 s for partitions 0,1,2,4,5 to redistribute | ≤ 16 % (1 of 6 partitions) | 0 | 0 | immediate on resume |
| 5 | Fill the disk on the broker | `docker exec kafka fallocate -l 9G /var/lib/kafka/big.bin` until `log.retention.bytes` exhausted | ∞ (broker halts) | n/a | 100 % on produce (OOM or `NOT_LEADER_OR_FOLLOWER`) | 0 if producer acks=all + idempotence; else data loss | 0 | ≤ 30 s after `rm big.bin` + log segment roll |
| 6 | Partition reassignment under load | `kafka-reassign-partitions.sh --execute ...` | ≤ 2 K msgs | n/a | ≤ 10 % throttle | 0 | 0 | depends on replication factor × throttle |

Run order matters. Run scenarios 2, 3, 4 first — they are non-destructive and exercise the consumer-rebalance and producer-retry paths. Run scenario 1 only after you have validated that `acks=all`, `enable.idempotence=true`, and `min.insync.replicas=2` are set on the producer and broker respectively; otherwise scenario 1 will lose data and the failure is in the configuration, not the chaos injection. Run scenario 5 only on a throwaway broker — the disk-fill leaves the broker in a state where log segments must be manually truncated before restart, which is the production incident you do not want to debug under load.

### Scenario 1 — Kill the Kafka broker

```bash
# 1. Pre-flight: confirm producer config
docker compose exec producer env | grep -E 'ACKS|IDEMPOTENCE|RETRIES'
#   → KAFKA_PRODUCER_ACKS=all
#   → KAFKA_PRODUCER_ENABLE_IDEMPOTENCE=true
#   → KAFKA_PRODUCER_RETRIES=2147483647
# 2. Confirm broker config
docker compose exec kafka cat /etc/kafka/server.properties | grep -E 'min.insync|default.replication'
#   → min.insync.replicas=2  (requires RF=3 — local single-broker stack must use RF=1 + min.insync=1)
#   → default.replication.factor=3
# 3. Load the pipeline at 1 K msgs/s for 60 s before killing
k6 run --vus 50 --duration 60s loadtest.js &
# 4. Kill the broker
docker compose kill kafka
# 5. Watch the producer error rate and consumer lag
docker compose exec kafka-exporter curl -s localhost:9308/metrics | grep kafka_consumergroup_lag
docker compose exec producer curl -s localhost:9400/metrics | grep kafka_producer_error_rate
# 6. Restart the broker
docker compose start kafka
# 7. Wait for the controller to elect, ISR to rebuild, and consumers to rejoin
docker compose logs kafka | grep -E '\[KafkaServer id=1\] started|rebalance'
```

The expected output is a 100 % throughput drop for the duration the broker is down (typically 8–15 s in a single-broker local stack, 5–10 s for controller election in a three-broker cluster), zero message loss if idempotence is enabled (the producer buffers in-flight batches and retries after the broker rejoins), and zero duplicates if the consumer's `enable.auto.commit=false` plus a manual commit-after-process pattern is in place. If you observe non-zero duplicates, the consumer committed offsets before processing completed — the fix is the **commit-after-ack** pattern documented in [[13.04.03. Analytics Consumer Python with confluent-kafka]]. If you observe non-zero message loss, the producer's `acks` setting is `1` or `0` rather than `all`; with `acks=1` and a single-broker kill, every in-flight batch whose leader was the killed broker is lost.

The non-obvious failure mode is the **producer block**. With `acks=all` and `max.in.flight.requests.per.connection=5`, the producer will keep accepting `send()` calls into its internal buffer for up to `delivery.timeout.ms` (default 120 s) before raising a `TimeoutException`. During this window the producer appears healthy from the application's perspective — no exception is thrown — but every batch is silently queued. The metric that exposes this is `kafka_producer_record_queue_time_ms` p99; it should remain below 1 000 ms. If it climbs above 10 000 ms during the kill, the producer is silently backpressuring and the application must propagate the backpressure (e.g. reject HTTP requests at the checkout endpoint with HTTP 503 rather than accepting them into the outbox where they will be invisible to the user for 120 s).

### Scenario 2 — Kill one consumer (rebalance)

```bash
# 1. Scale the analytics consumer to 3 instances (one per partition, 6 partitions)
docker compose up -d --scale analytics-consumer=3
# 2. Confirm partition assignment is balanced
docker compose exec kafka kafka-consumer-groups.sh \
  --bootstrap-server kafka:9092 --group analytics-python --describe
# PARTITION 0 → analytics-consumer-1
# PARTITION 1 → analytics-consumer-1
# PARTITION 2 → analytics-consumer-2
# PARTITION 3 → analytics-consumer-2
# PARTITION 4 → analytics-consumer-3
# PARTITION 5 → analytics-consumer-3
# 3. Kill one consumer mid-stream
docker compose kill analytics-consumer-1
# 4. Watch the cooperative-sticky rebalance unfold
docker compose logs -f analytics-consumer-2 | grep -E 'Revoke|Assign|rebalance'
# 5. Measure the wall-clock time from SIGTERM to the first poll() on the reassigned partitions
```

The rebalance time budget is governed by three settings, all on the consumer: `session.timeout.ms` (default 45 s in Kafka 3.x — the time the broker waits without a heartbeat before declaring the consumer dead), `heartbeat.interval.ms` (default 3 s — how often the consumer heartbeats), and `max.poll.interval.ms` (default 5 min — the upper bound between two `poll()` calls). A clean `docker compose kill` (SIGTERM by default) lets the consumer leave the group gracefully via `LeaveGroup`, which triggers an immediate rebalance without waiting for the session timeout — expected wall-clock 1–3 s. A `docker compose kill -s SIGKILL` (or a JVM hard crash) skips `LeaveGroup`, so the rebalance waits for `session.timeout.ms` to expire — expected wall-clock 45 s with defaults, 10 s if you tune `session.timeout.ms=10000` + `heartbeat.interval.ms=2000`.

The hardening pattern is the **cooperative-sticky assignor** plus the **shutdown hook**. With `partition.assignment.strategy=org.apache.kafka.clients.consumer.CooperativeStickyAssignor` (set in the consumer config), only the partitions owned by the killed consumer are revoked and reassigned; the surviving consumers keep their partitions and continue processing throughout the rebalance. The default `RangeAssignor` is "eager" — every consumer in the group revokes all partitions, stops processing, waits for the rebalance to complete, then re-acquires its new assignment. The eager rebalance produces a 5–15 s total throughput gap; the cooperative rebalance produces a 1–2 s gap on only the reassigned partitions. The shutdown hook (in Python: `signal.signal(signal.SIGTERM, handler)` calling `consumer.close()`) is what triggers the graceful `LeaveGroup` — without it, even a SIGTERM looks like a SIGKILL to the broker and you pay the full session timeout.

### Scenario 3 — Inject 5 s producer latency

```bash
# 1. Enter the producer container's network namespace
docker compose exec producer bash
# 2. Confirm the eth0 interface name (container might use eth0 or ens3)
ip addr | grep -E 'eth0|ens3'
# 3. Apply the netem qdisc — 5 s one-way delay on every packet
tc qdisc add dev eth0 root netem delay 5s
# 4. From outside, watch the producer's record-queue-time metric climb
docker compose exec producer curl -s localhost:9400/metrics | \
  grep kafka_producer_record_queue_time_ms
# 5. Watch the broker-side receive rate collapse
docker compose exec kafka kafka-run-class.sh \
  kafka.tools.GetOffsetShell --broker-list kafka:9092 --topic orders.events
# 6. After 60 s, remove the qdisc — recovery must be immediate
tc qdisc del dev eth0 root
```

The 5 s delay pushes every producer `send()` past its `request.timeout.ms` (default 30 s) — but only barely. The producer will keep retrying within `delivery.timeout.ms` (default 120 s) and the batches will eventually land once the qdisc is removed. The metric that reveals the failure is `kafka_producer_record_queue_time_ms` p99, which climbs from ~50 ms to ~5 000 ms within 10 s of the qdisc being applied. The throughput graph on the broker shows a 100 % collapse during the delay window because no `Produce` RPC reaches the broker; the consumer graph shows a slow decline in lag (the consumers drain the topic's existing backlog) followed by a lag spike that grows linearly with the duration of the injection.

The hardening change is the **producer timeout budget**. The default `delivery.timeout.ms=120000` is too generous for a user-facing checkout endpoint — the HTTP request that triggers the produce call will have already timed out (typically at 30 s by the load balancer) long before the producer raises. The correct configuration for a synchronous produce (where the HTTP request waits for the produce ack) is `delivery.timeout.ms=10000`, `request.timeout.ms=5000`, `acks=all` — this gives the producer 10 s total to deliver the batch, fails fast, and lets the application return HTTP 503 to the caller, who can retry with the same idempotency key. For an asynchronous produce (where the HTTP request returns 202 immediately and the outbox relay handles delivery), the longer 120 s budget is correct because the application is no longer on the request path.

### Scenario 4 — Pause a single partition

```bash
# Kafka does not have a first-class partition-pause, so the cleanest way to
# pause partition 3 is to stop the consumer that owns it (with cooperative
# assignor, only partition 3 is reassigned).
# 1. Identify which consumer owns partition 3
docker compose exec kafka kafka-consumer-groups.sh \
  --bootstrap-server kafka:9092 --group analytics-python --describe | \
  awk '$5 == "3" {print $4}'
# 2. Pause that consumer (SIGSTOP, not SIGTERM — keep its session alive)
docker compose exec analytics-consumer-2 kill -STOP 1
# 3. Watch cooperative rebalance NOT trigger (session is still alive)
#    — partition 3 will accumulate lag, partitions 0,1,2,4,5 keep draining
docker compose exec kafka-exporter curl -s localhost:9308/metrics | \
  grep -E 'kafka_consumergroup_lag.*partition="3"'
# 4. To force a partition-level reassignment, use the pause API in the consumer
#    client — confluent-kafka-python exposes consumer.pause([TopicPartition("orders.events", 3)])
# 5. Resume
docker compose exec analytics-consumer-2 kill -CONT 1
```

The partition-pause scenario exposes the gap between **per-partition consumer lag** and **topic-level consumer lag**. The topic-level metric `kafka_consumergroup_lag_sum` shows a slow linear growth; the per-partition metric `kafka_consumergroup_lag{partition="3"}` shows a fast linear growth. If your dashboard only shows the sum, the lag spike looks like a normal traffic burst and the operator misses the partition-specific failure (which is typically a poison-pill message on partition 3, a deserialization error on a single key, or a hot-key skew). The hardening change is to always alert on the **maximum per-partition lag**, not the sum or average — a single stuck partition is a more actionable signal than an aggregate that averages a stuck partition down to a non-event.

The non-obvious failure mode is the **poison pill**. If the consumer on partition 3 throws an unhandled exception during `poll()` processing, the default behaviour is for the consumer to crash, restart (under a process supervisor), rejoin the group, fetch the same offset, and crash again — a tight infinite loop. The lag on partition 3 grows linearly while the lag on partitions 0,1,2,4,5 stays at zero. The hardening pattern is a **dead-letter topic (DLT)** plus a **max-retries-then-skip** policy: after N retries on a single message, the consumer writes the message to `orders.events.dlt`, logs the offset and exception, commits the offset, and continues. The DLT is reviewed by a human; the partition is no longer stuck. The Spring Boot anchor implements this with `DefaultErrorHandler` + `DeadLetterPublishingRecoverer`; the Python delta must implement it manually because `confluent-kafka-python` does not ship a default error handler.

### Scenario 5 — Fill the disk on the broker

```bash
# 1. Find the Kafka data directory
docker compose exec kafka ls /var/lib/kafka/data
# 2. Allocate a 9 GB file (assuming a 10 GB volume) to force the disk to ~90 % full
docker compose exec kafka fallocate -l 9G /var/lib/kafka/data/big.bin
# 3. Keep producing at 5 MB/s — log segments roll every 1 GB by default
#    (log.segment.bytes=1073741824). Within ~3 min the disk is exhausted.
# 4. Watch the broker halt with: java.io.IOException: No space left on device
docker compose logs -f kafka | grep -i 'No space left'
# 5. The producer starts seeing NOT_LEADER_OR_FOLLOWER or REQUEST_TIMED_OUT
docker compose exec producer curl -s localhost:9400/metrics | \
  grep kafka_producer_error_rate
# 6. Delete the artificial file and let the log cleaner reclaim
docker compose exec kafka rm /var/lib/kafka/data/big.bin
# 7. The broker does NOT recover automatically — restart it
docker compose restart kafka
```

The disk-fill scenario is the failure mode that is most likely to actually happen in production (log retention misconfigured, a topic with `retention.ms=-1` growing unbounded, a compaction topic whose key space exploded). The broker's behaviour on `ENOSPC` is to halt the log writer for the affected partition, log the `IOException`, and within seconds the controller marks the partition's leader as `--offline`. Producers see `NOT_LEADER_OR_FOLLOWER` (error code 6) and retry against the new leader — but in a single-broker stack there is no other leader, so they queue in the producer buffer until `delivery.timeout.ms` expires, then raise `TimeoutException`. With `acks=all` and idempotence enabled, no messages are lost (the producer's inflight batches are retried once the broker is restarted). Without idempotence, every retried batch risks a duplicate on the broker because the broker cannot deduplicate a `Produce` request whose previous incarnation it never durably wrote.

The hardening change is a **disk-pressure alert** at 70 % and 85 %, plus a **log.retention.bytes** cap that is well below the disk size. The broker does not gracefully degrade on disk pressure — there is no "soft" mode where it slows produce throughput to buy time. The first signal is the `kafka_log_log_size` metric on each partition; the second is the OS-level `node_filesystem_avail_bytes` from node-exporter. The 70 % alert gives the operator a 20-minute window to act (delete an off-topic file, expand the volume, or trigger a compaction); the 85 % alert pages immediately because the broker is minutes from halting.

## Observations

The five chaos scenarios produce three findings that are common to every ecosystem and four findings that are ecosystem-specific. The common findings are: (1) the cooperative-sticky assignor is non-negotiable for any consumer group with more than one instance — the eager assignor's full-revoke-on-rebalance produces a 5–15 s throughput gap that is unacceptable for any user-facing pipeline; (2) the consumer must commit offsets **after** processing, never before — the `enable.auto.commit=true` default in KafkaJS and Laravel-Kafka is a footgun that produces duplicates on every rebalance; (3) the producer's `delivery.timeout.ms` must be tuned for the calling context — synchronous callers (HTTP request) need 10 s, asynchronous callers (outbox relay) can keep the 120 s default.

The ecosystem-specific findings are the value of this milestone. The Spring Boot anchor's `DefaultErrorHandler` is the only consumer error handler in the four ecosystems that ships with a built-in DLT publisher; the Python, Node, and PHP deltas all required manual implementation. The Node KafkaJS library is the only client that does not support cooperative-sticky assignment (as of v2.2.4) — this is a known limitation that forces the broadcaster to accept a 3 s rebalance gap. The PHP Laravel queue worker's model is fundamentally incompatible with Kafka's long-running-poll model — Laravel's queue worker is designed for Redis/SQS where each job is a discrete message; Kafka's stream-of-records model requires the worker to poll continuously, which conflicts with Laravel's `stop_when_empty` and `--max-jobs` lifecycle knobs.

## What the Anchor Taught That the Deltas Did Not

The Spring Boot anchor forced confrontation with three problems the delta implementations hid behind library convenience. The first is the **KafkaTransactionsTemplate** — Spring's `@Transactional` plus `ChainedKafkaTransactionManager` makes it possible to atomically commit a database row and a Kafka produce offset in a single transaction. This is the only correct way to implement the Transactional Outbox relay without a separate polling job; the Python and PHP deltas both fell back to the polling-relay pattern because their Kafka clients do not support transactions. The second is the **`KafkaListenerContainerRegistry`** — Spring's managed lifecycle for consumer containers exposes a single `stop(Runnable callback)` hook that gracefully drains in-flight records, commits offsets, and leaves the group. The Python delta required a hand-rolled `signal.signal(SIGTERM, ...)` handler that called `consumer.close()` — workable but error-prone, and the Laravel delta required `queue:work --max-time=60` plus an external supervisor to achieve the same effect. The third is the **micrometer-registry-prometheus** integration — Spring Boot's actuator exposes `kafka_producer_record_queue_time_ms`, `kafka_consumer_lag`, and `kafka_consumer_records_consumed_total` automatically once `micrometer-registry-prometheus` is on the classpath; the Python, Node, and PHP deltas all required manual registration of the same metrics against `prometheus_client`, `prom-client`, and `prometheus/client-php` respectively.

## What the Deltas Taught That the Anchor Hid

The Python and Node deltas exposed three conveniences that the Spring Boot anchor's strict typing and DI container had trained the reader to tolerate. The first is the **schemaless consumer record** — `confluent-kafka-python`'s `msg.value()` returns `bytes` that the consumer deserialises with whatever codec it wants; Spring's `@KafkaListener` requires a `Deserializer<SpecificRecord>` configured up front, which makes Avro-schema-evolution a compile-time concern rather than a runtime one. The second is the **single-file consumer** — the entire Python analytics consumer fits in 284 lines including DLT, retry loop, metrics, and graceful shutdown; the equivalent Spring Boot consumer is 612 lines spread across `@Configuration`, `@KafkaListener`, `ConsumerFactory`, `ConcurrentKafkaListenerContainerFactory`, and `DefaultErrorHandler` beans. The third is the **WebSocket fan-out natural fit** — Node.js's single-threaded event loop is the natural runtime for the broadcaster (500 WebSocket clients × 5 KB broadcast = 2.5 MB per broadcast, delivered in a single tick); the Spring Boot equivalent would require a `WebFlux` reactive pipeline or a Servlet 3.1 async dispatch, both of which are more complex than the Node implementation for the same problem.

The PHP Laravel delta exposed one convenience that the other three ecosystems all hid: the **`failed_jobs` table** is a built-in DLT. Laravel's queue worker writes any job that throws after `--tries=3` to the `failed_jobs` table automatically, with the payload, exception, and failed-at timestamp. The Python and Node deltas required manual DLT implementation; the Spring Boot anchor required a `DeadLetterPublishingRecoverer` bean. Laravel's `failed_jobs` table is a database table rather than a Kafka topic, which makes it easier to query (`SELECT * FROM failed_jobs WHERE queue = 'invoices'`) but harder to replay into a Kafka pipeline (the `queue:retry` command re-enqueues to the original queue, which may not be what you want if the original queue is Kafka).
