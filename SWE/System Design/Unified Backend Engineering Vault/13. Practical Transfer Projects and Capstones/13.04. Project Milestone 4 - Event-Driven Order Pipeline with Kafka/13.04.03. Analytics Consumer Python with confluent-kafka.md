# 13.04.03. Analytics Consumer Python with confluent-kafka

## Scope

This is the **Python delta** for Milestone 4 — a standalone consumer that reads `OrderCreated` events from the `orders.events` topic produced by the Spring Boot anchor in `[[13.04.02. Primary Engine Spring Boot Producer and Debezium CDC]]`, aggregates them into 1-minute tumbling windows of order count and gross revenue by `currency`, and writes the aggregates to a separate analytics Postgres database. It is the downstream consumer that exercises two patterns the anchor never touches: **manual offset commit after a successful downstream write** (so a crash mid-aggregate never marks a message as processed) and **idempotent UPSERT** (so a redelivered event after a consumer restart does not double-count revenue).

The choice of `confluent-kafka` (the librdkafka C bindings) over the pure-Python `kafka-python` is deliberate and load-bearing. `kafka-python` is single-threaded, GIL-bound, and tops out around 5,000 messages/sec per process even on trivial deserialization; `confluent-kafka` runs the librdkafka consumer poll loop in a C thread and only crosses into Python for the message callback, sustaining 50,000+ messages/sec with the same handler. For an analytics pipeline that has to keep up with a producer doing 1,000 RPS, the difference between 5k and 50k msgs/sec is the difference between "lag stays at zero" and "lag climbs unboundedly at peak."

The lesson this note teaches that the anchor cannot is **idempotency without a framework**. The Spring Boot anchor has JPA `@Transactional` and a unique-indexed `idempotency_keys` table; the Python consumer has neither, and must implement deduplication manually with a `processed_events` table queried before each insert. This is the universal reality of cross-system consumers — the producer's transactional guarantees do not cross the Kafka boundary, and every consumer has to defend itself.

### Step 3 — Models (pydantic, validates event shape)

```python
# src/analytics_consumer/models.py
from pydantic import BaseModel, Field, ValidationError
from datetime import datetime
from typing import Literal

class OrderItem(BaseModel):
    sku: str
    qty: int = Field(gt=0)
    unit_price_cents: int = Field(ge=0)

class OrderCreatedEvent(BaseModel):
    event_id: str = Field(pattern=r"^evt_[0-9a-f-]{36}$")
    event_type: Literal["OrderCreated"]
    aggregate_id: str                          # ord_3f8a9c1e2b4d6f8a
    occurred_at: datetime
    buyer_id: str
    seller_id: str
    total_cents: int = Field(gt=0)
    currency: str = Field(min_length=3, max_length=3)
    items: list[OrderItem]
    trace_id: str | None = None

    @property
    def window_start(self) -> datetime:
        """Floor to 1-minute tumbling window."""
        epoch = int(self.occurred_at.timestamp())
        return datetime.fromtimestamp(epoch - (epoch % 60), tz=self.occurred_at.tzinfo)
```

### Step 4 — Store (Postgres idempotent UPSERT)

The idempotency contract is the heart of the consumer. Two tables: `revenue_minute` (the aggregate) and `processed_events` (the deduplication ledger). A redelivered event must hit the `processed_events` unique constraint and be silently dropped — no double-counting.

```python
# src/analytics_consumer/store.py
from psycopg_pool import ConnectionPool
from psycopg.rows import dict_row
from contextlib import contextmanager
import json

CREATE_TABLES = """
CREATE TABLE IF NOT EXISTS revenue_minute (
    window_start  TIMESTAMPTZ NOT NULL,
    currency      CHAR(3)     NOT NULL,
    order_count   BIGINT      NOT NULL DEFAULT 0,
    gross_cents   BIGINT      NOT NULL DEFAULT 0,
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (window_start, currency)
);

CREATE TABLE IF NOT EXISTS processed_events (
    event_id      TEXT        PRIMARY KEY,
    processed_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    trace_id      TEXT
);

CREATE INDEX IF NOT EXISTS idx_processed_at
    ON processed_events (processed_at);
"""

UPSERT_AGGREGATE = """
INSERT INTO revenue_minute (window_start, currency, order_count, gross_cents, updated_at)
VALUES (%(window_start)s, %(currency)s, 1, %(gross_cents)s, now())
ON CONFLICT (window_start, currency)
DO UPDATE SET
    order_count = revenue_minute.order_count + 1,
    gross_cents = revenue_minute.gross_cents + EXCLUDED.gross_cents,
    updated_at  = now()
"""

INSERT_PROCESSED = """
INSERT INTO processed_events (event_id, trace_id) VALUES (%s, %s)
ON CONFLICT (event_id) DO NOTHING RETURNING event_id
"""

class AnalyticsStore:
    def __init__(self, dsn: str, min_size: int = 2, max_size: int = 10):
        self.pool = ConnectionPool(dsn, min_size=min_size,
                                   max_size=max_size, kwargs={"row_factory": dict_row})
        with self.pool.connection() as conn:
            conn.execute(CREATE_TABLES)

    @contextmanager
    def aggregate_event(self, evt) -> bool:
        """
        Single-transaction UPSERT of aggregate + dedup ledger.
        Returns True if the event was newly processed, False if duplicate.
        Caller commits the Kafka offset only when this returns True.
        """
        with self.pool.connection() as conn:
            with conn.transaction():
                # 1. Idempotency check — within the same transaction
                row = conn.execute(INSERT_PROCESSED,
                                   (evt.event_id, evt.trace_id)).fetchone()
                if row is None:
                    # event_id already in processed_events → duplicate, skip
                    yield False
                    return
                # 2. Aggregate update
                conn.execute(UPSERT_AGGREGATE, {
                    "window_start": evt.window_start,
                    "currency":     evt.currency,
                    "gross_cents":  evt.total_cents,
                })
                yield True

    def close(self):
        self.pool.close()
```

The `aggregate_event` context manager is the unit of consistency. The Kafka offset commit happens AFTER this block exits with `True`, never inside it. If the consumer crashes between the UPSERT and the offset commit, the offset is stale on restart, the event is redelivered, the `processed_events` INSERT returns no row, and the aggregate is untouched. That is at-least-once + idempotency = effectively-once.

### Step 5 — Consumer (librdkafka poll loop)

```python
# src/analytics_consumer/consumer.py
from confluent_kafka import Consumer, KafkaError, KafkaException, TopicPartition
from structlog import get_logger
from .metrics import MESSAGES_PROCESSED, MESSAGES_DUPLICATE, MESSAGES_ERROR, LAG_PARTITIONS
from .models import OrderCreatedEvent
from .store import AnalyticsStore
from contextvars import ContextVar
import signal, sys, json

log = get_logger()
trace_id_var: ContextVar[str | None] = ContextVar("trace_id", default=None)

class OrderCreatedConsumer:
    def __init__(self, cfg, store: AnalyticsStore):
        self.cfg = cfg
        self.store = store
        self.consumer = Consumer(cfg.kafka_conf)
        self.running = True

        # Rebalance callbacks — cooperative-sticky minimizes partition movement
        self.consumer.subscribe(
            [cfg.kafka_topic],
            on_assign=self._on_assign,
            on_revoke=self._on_revoke,
            on_lost=self._on_lost,
        )

    def _on_assign(self, consumer, partitions):
        log.info("partitions_assigned",
                 count=len(partitions),
                 partitions=[f"{p.topic}-{p.partition}" for p in partitions])
        for p in partitions:
            LAG_PARTITIONS.labels(topic=p.topic, partition=p.partition).set(0)

    def _on_revoke(self, consumer, partitions):
        log.info("partitions_revoking",
                 count=len(partitions),
                 partitions=[f"{p.topic}-{p.partition}" for p in partitions])
        # COMMIT BEFORE REVOKE — otherwise redelivered events after rebalance
        consumer.commit(asynchronous=False)
        for p in partitions:
            LAG_PARTITIONS.labels(topic=p.topic, partition=p.partition).set(-1)

    def _on_lost(self, consumer, partitions):
        # Partition was lost (broker died) — cannot commit. Just log.
        log.warning("partitions_lost", count=len(partitions))

    def run(self):
        signal.signal(signal.SIGINT,  self._stop)
        signal.signal(signal.SIGTERM, self._stop)
        try:
            while self.running:
                msg = self.consumer.poll(timeout=1.0)
                if msg is None:               continue
                if msg.error():
                    if msg.error().code() == KafkaError._PARTITION_EOF:
                        continue
                    raise KafkaException(msg.error())
                self._handle(msg)
        finally:
            self.consumer.close()
            self.store.close()

    def _handle(self, msg):
        # Extract trace_id from Kafka headers (set by Debezium SMT)
        headers = dict(msg.headers() or [])
        trace_id = headers.get("trace_id", b"").decode() or None
        trace_id_var.set(trace_id)

        try:
            payload = json.loads(msg.value())
            evt = OrderCreatedEvent.model_validate(payload)
        except Exception as e:
            MESSAGES_ERROR.labels(reason="parse").inc()
            log.error("parse_failed", err=str(e),
                      offset=msg.offset(), partition=msg.partition())
            # Commit past the bad message — poison-pill handling
            self.consumer.commit(message=msg, asynchronous=False)
            return

        try:
            with self.store.aggregate_event(evt) as newly_processed:
                if newly_processed:
                    MESSAGES_PROCESSED.inc()
                    log.info("event_aggregated",
                             event_id=evt.event_id,
                             order_ref=evt.aggregate_id,
                             window_start=evt.window_start.isoformat(),
                             currency=evt.currency,
                             total_cents=evt.total_cents)
                else:
                    MESSAGES_DUPLICATE.inc()
                    log.info("event_deduplicated", event_id=evt.event_id)
            # Commit only AFTER the aggregate transaction succeeded
            self.consumer.commit(message=msg, asynchronous=False)
        except Exception as e:
            MESSAGES_ERROR.labels(reason="store").inc()
            log.error("store_failed", err=str(e), event_id=evt.event_id)
            # DO NOT COMMIT — message will be redelivered on next poll
            raise

    def _stop(self, signum, frame):
        log.info("shutdown_requested", signal=signum)
        self.running = False
```

```python
# src/analytics_consumer/logging_setup.py
import structlog, logging
from contextvars import ContextVar
trace_id_var: ContextVar[str | None] = ContextVar("trace_id", default=None)

def configure_logging():
    structlog.configure(
        processors=[
            structlog.contextvars.merge_contextvars,
            _inject_trace_id,
            structlog.processors.TimeStamper(fmt="iso"),
            structlog.processors.add_log_level,
            structlog.processors.JSONRenderer(),
        ],
        wrapper_class=structlog.make_filtering_bound_logger(logging.INFO),
        logger_factory=structlog.PrintLoggerFactory(),
    )

def _inject_trace_id(_, __, event_dict):
    tid = trace_id_var.get()
    if tid: event_dict["trace_id"] = tid
    return event_dict
```

Expected behavior: at 1,000 events/sec, the consumer's `consumer_processing_seconds` p99 stays under 5 ms (the Postgres UPSERT is the bottleneck, ~2 ms each); `consumer_lag_partitions` stays bounded by the librdkafka `fetch.max.wait.ms=100ms` × batch size; the `consumer_messages_processed_total{outcome="ok"}` counter rises at ~1,000/s; `outcome="duplicate"` rises only when you intentionally replay; `outcome="error"` stays at 0. If lag climbs, the fix is to either (a) scale horizontally by adding consumer instances to the same group (cooperative-sticky rebalances partition assignment without stopping the world), or (b) batch the UPSERTs — accumulate 100 events in memory and do one multi-row INSERT, which trades latency for throughput.

## What This Teaches

This delta teaches three lessons the Spring Boot anchor hides:

**1. Idempotency at the consumer boundary is a manual discipline, not a framework feature.** The anchor's `OrderService` gets idempotency "for free" via JPA `@Transactional` and a unique-indexed `idempotency_keys` table — both transparent to the application code. The Python consumer has no such luxury. The `aggregate_event` context manager has to manually check `processed_events` and decide whether to update the aggregate, all within one explicit `with conn.transaction():` block. This is the universal reality of every Kafka consumer in every language: the producer's transaction does not cross the Kafka boundary, and at-least-once delivery means duplicates will arrive. If you don't defend against them with a unique constraint + an UPSERT, your aggregates are wrong.

**2. Manual offset commit is the only correct commit strategy.** `enable.auto.commit=false` is non-negotiable in this codebase. Auto-commit commits the last polled offset every 5 seconds regardless of whether the handler finished — which means a crash mid-aggregate silently loses the in-flight event. Manual commit-after-success means the offset only advances when the Postgres transaction has committed, which means a crash redelivers the event, which means the idempotency check above absorbs it. The pattern is: process → commit downstream → commit Kafka offset. Reversing any two of these gives you either data loss or unbounded duplicates.

**3. `confluent-kafka` (librdkafka) over `kafka-python` is a 10× throughput decision.** The pure-Python `kafka-python` library is fine for development and for low-throughput control-plane topics, but it cannot sustain producer-side RPS in production. The reason is the GIL: `kafka-python` deserializes, parses, and dispatches every byte in Python, and the GIL serializes those operations across the consumer thread, the producer thread, and any background asyncio loop. `confluent-kafka` does all network I/O and protocol parsing in librdkafka's C thread pool, only crossing into Python for the `on_message` callback with an already-parsed `Message` object. For this milestone's 1,000 RPS target the difference is invisible; at 10,000 RPS it is the difference between a system that works and one that doesn't. Every production Python Kafka consumer at scale uses `confluent-kafka` for this reason — and the choice is irreversible once you've written handler code against the `confluent_kafka.Message` API, because `kafka-python` has a different (and incompatible) `Message` shape.
