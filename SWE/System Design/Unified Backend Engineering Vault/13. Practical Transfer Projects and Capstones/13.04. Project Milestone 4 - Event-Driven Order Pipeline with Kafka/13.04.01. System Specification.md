# 13.04.01. System Specification

## Project Goal

Build an **event-driven order pipeline** in which a single checkout operation triggers four downstream effects in four different ecosystems without any of them holding a request thread open against the others. The pipeline is the canonical showcase for the Transactional Outbox pattern: a Spring Boot producer writes the order row and an outbox row in the same ACID transaction; Debezium tails the Postgres WAL and emits the outbox row as a Kafka `OrderCreated` event; three independent consumers — a Python analytics aggregator, a Node.js WebSocket broadcaster, and a PHP invoice-generation worker — each consume from the same topic and do their work in parallel. The user-perceived checkout latency is bounded by the Postgres commit, not by any downstream service. That decoupling is the entire point of the milestone.

The "transferable" lesson is the one every senior backend engineer eventually scars themselves on: if you publish a message to Kafka from inside your transaction and the publish succeeds but the transaction rolls back, you have announced an event that never happened. If you publish after the commit and the publish fails, you have lost an event that did happen. Both are data-corruption bugs. The Outbox pattern resolves the paradox by writing the event into the same transaction as the business state change and letting a separate process (Debezium, or a polling relay) do the cross-system publish with at-least-once delivery semantics. The consumer side then has to be idempotent to absorb duplicates — and that idempotency contract is the second thing this milestone forces you to design correctly.

You are done when you can show a Grafana dashboard with: the checkout endpoint returning in <50 ms p99 under 1000 RPS; the four consumers each processing the same stream at their own pace with consumer-lag visible and bounded; a chaos test killing the Python consumer for 60 seconds and watching the others continue unaffected; and a duplicate-injection test proving each consumer deduplicates by `order_id`.

## Requirements

- **R1 — Transactional Outbox.** The Spring Boot producer must write the `orders` row and the `outbox` row in a single `SERIALIZABLE` Postgres transaction. There must be no `kafka.send()` call inside that transaction. The outbox table has columns `id UUID PRIMARY KEY, aggregate_type TEXT, aggregate_id TEXT, event_type TEXT, payload JSONB, created_at TIMESTAMPTZ, processed_at TIMESTAMPTZ NULL`. A `processed_at IS NULL` predicate is the only correct way for a relay to find unpublished events; deleting rows after publish is also acceptable and is what Debezium's tombstone-on-delete mode enables.
- **R2 — Debezium CDC relay.** A Debezium source connector (Postgres connector, `plugin.name=pgoutput`) tails the WAL and writes one Kafka record per outbox insert. The connector config must set `tombstones.on.delete=true`, `snapshot.mode=schema_only`, and a Single Message Transforms (SMT) chain that extracts `event_type` and `aggregate_id` from the row payload and uses them as the Kafka record key and topic-name-prefix. The Kafka topic is `orders.events` with 6 partitions, replication factor 3, `cleanup.policy=compact,delete`, and `retention.ms=604800000` (7 days).
- **R3 — Python analytics consumer.** Consumes from `orders.events` consumer group `analytics-aggregator`, computes rolling 1-minute tumbling windows of order count and gross revenue by `currency`, and writes the aggregates to a `revenue_minute` table in a separate analytics Postgres database. Must use `confluent-kafka` (librdkafka bindings, not the pure-Python `kafka-python`), manual commit after each successful DB write, and idempotent UPSERT keyed by `(window_start, currency)`.
- **R4 — Node.js WebSocket broadcaster.** Consumes from `orders.events` consumer group `ws-broadcaster`, maintains an in-memory map of connected WebSocket clients keyed by `user_id`, and pushes a JSON `order.created` event to every client subscribed to the order's buyer or seller. Must use `kafkajs` (the only production-grade pure-JS Kafka client) and the `ws` library. Must handle rebalance by closing affected client subscriptions gracefully (send `{"type":"rebalance","reason":"partition_revoked"}` and let the client reconnect).
- **R5 — PHP Laravel invoice worker.** Consumes from `orders.events` consumer group `invoice-worker`, generates a PDF invoice via `barryvdh/laravel-dompdf`, uploads it to S3, and writes an `invoices` row with `order_id`, `s3_url`, `generated_at`. Must run via `php artisan queue:work kafka --tries=3 --backoff=10,30,60`. Must be idempotent on `order_id` — a second delivery of the same event must not regenerate the PDF or overwrite the S3 object.
- **R6 — Observability.** Every service emits Prometheus metrics on `/metrics`: `orders_created_total`, `consumer_lag_partitions`, `consumer_messages_processed_total{outcome="ok|duplicate|error"}`, `consumer_processing_seconds_bucket`. Every log line has a `trace_id` field propagated end-to-end via the W3C `traceparent` header on HTTP and a `trace_id` field in the Kafka record headers.
- **R7 — Chaos resilience.** Killing any single consumer for 60 seconds must not lose events (other consumers continue; the killed consumer catches up on restart via committed-offset replay). Killing the Postgres primary for 30 seconds (with a synchronous standby promoted) must not produce duplicate `OrderCreated` events — Debezium's WAL position is checkpointed in its `offset.storage` topic and resumes exactly where it left off.

Each requirement is non-negotiable. If you skip one, you have completed a tutorial, not a milestone. R1 + R2 together are the heart of the Outbox pattern; R3–R5 are deliberately in three different ecosystems to prove the pattern is portable; R6 + R7 are what separate a demo from a system you would run on call.

The four services (Spring Boot, Python, Node, PHP) share zero runtime state. Their only coordination is the Kafka topic and the W3C `traceparent` header propagated through every hop. The Debezium connector is the linchpin — it is the only component that turns "a row in Postgres" into "a record in Kafka," and its WAL-position checkpointing is what gives the pipeline its at-least-once guarantee without a distributed transaction.

## API Contract

The contract has three surfaces: the HTTP endpoint the Spring Boot producer exposes, the Kafka record Debezium emits, and the WebSocket event the Node.js broadcaster pushes. All three are versioned and frozen for the lifetime of the milestone.

**HTTP — order creation:**

```http
POST /api/orders HTTP/1.1
Host: producer.local:8080
Content-Type: application/json
Idempotency-Key: 7f9e3a2b-1c4d-4e5f-8a9b-2c3d4e5f6a7b
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01

{
  "buyer_id":  "usr_8x13",
  "seller_id": "usr_4z91",
  "items": [
    { "sku": "SKU-1001", "qty": 2, "unit_price_cents": 1999, "currency": "USD" },
    { "sku": "SKU-2049", "qty": 1, "unit_price_cents": 4999, "currency": "USD" }
  ],
  "currency": "USD"
}
```

```http
HTTP/1.1 201 Created
Content-Type: application/json
Location: /api/orders/ord_3f8a...
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-7a2b3c4d5e6f7081-01

{
  "order_id":     "ord_3f8a9c1e2b4d6f8a",
  "buyer_id":     "usr_8x13",
  "seller_id":    "usr_4z91",
  "total_cents":  8997,
  "currency":     "USD",
  "status":       "CREATED",
  "created_at":   "2025-01-15T14:22:31.482Z",
  "trace_id":     "4bf92f3577b34da6a3ce929d0e0e4736"
}
```

Status codes: `201` on first creation; `409 Conflict` with the original order body on a replayed `Idempotency-Key` (the producer stores `idempotency_key → order_id` in a unique-indexed table); `422` on validation failure; `503` if Postgres is unreachable. The endpoint never blocks on Kafka — by design the response is sent before Debezium has emitted the event.

**Kafka record — `OrderCreated` (emitted by Debezium):**

```text
Topic:     orders.events
Partition: hash(seller_id) % 6
Key:       {"aggregate_type":"Order","aggregate_id":"ord_3f8a9c1e2b4d6f8a"}
Headers:
  event_type:    OrderCreated
  trace_id:      4bf92f3577b34da6a3ce929d0e0e4736
  schema_version: 1
  produced_by:   debezium-postgres-source
  produced_at:   2025-01-15T14:22:31.491Z

Value (JSON, post-SMT):
{
  "event_id":      "evt_2c4e9a1b-3d5f-4e6f-8a9b-1c2d3e4f5a6b",
  "event_type":    "OrderCreated",
  "aggregate_id":  "ord_3f8a9c1e2b4d6f8a",
  "occurred_at":   "2025-01-15T14:22:31.482Z",
  "buyer_id":      "usr_8x13",
  "seller_id":     "usr_4z91",
  "total_cents":   8997,
  "currency":      "USD",
  "items": [
    { "sku": "SKU-1001", "qty": 2, "unit_price_cents": 1999 },
    { "sku": "SKU-2049", "qty": 1, "unit_price_cents": 4999 }
  ],
  "trace_id":      "4bf92f3577b34da6a3ce929d0e0e4736"
}
```

The `event_id` is a fresh UUID generated by the producer at outbox-insert time; it is what consumers use for deduplication. The `aggregate_id` is the Kafka record key — this guarantees all events for the same order land on the same partition and are delivered in order to any single consumer. The `trace_id` header is propagated from the original HTTP `traceparent` and is what lets you follow one order from browser → producer → Postgres → Debezium → all three consumers in a single Jaeger trace.

**WebSocket — `order.created` (emitted by Node.js broadcaster):**

```text
Client → Server:
  GET /ws/orders?user_id=usr_8x13&token=... HTTP/1.1
  Upgrade: websocket
  Connection: Upgrade
  Sec-WebSocket-Protocol: v1

Server → Client (on connection):
  {"type":"hello","client_id":"ws_4f8a","subscriptions":["usr_8x13"]}

Server → Client (on OrderCreated where buyer or seller matches):
  {
    "type":        "order.created",
    "order_id":    "ord_3f8a9c1e2b4d6f8a",
    "buyer_id":    "usr_8x13",
    "seller_id":   "usr_4z91",
    "total_cents": 8997,
    "currency":    "USD",
    "occurred_at": "2025-01-15T14:22:31.482Z",
    "trace_id":    "4bf92f3577b34da6a3ce929d0e0e4736"
  }

Server → Client (on partition revocation during rebalance):
  {"type":"rebalance","reason":"partition_revoked","partitions":[3,4]}
  (client should expect to miss events for affected user_ids until reconnect)
```

The WebSocket protocol is deliberately minimal — one `type` discriminator per message, no nested envelope. The `rebalance` message is the contract with the client: it tells the client "I may stop receiving events for some user_ids; if you need them, reconnect and re-subscribe." Clients that ignore this message will silently miss events after every broker rebalance.

## Acceptance Criteria

1. All four target ecosystems implement the contract above byte-for-byte. The Spring Boot producer is the anchor (`[[13.04.02. Primary Engine Spring Boot Producer and Debezium CDC]]`); the three consumers are the deltas (`[[13.04.03. Analytics Consumer Python with confluent-kafka]]`, `[[13.04.04. Real-Time WebSocket Broadcaster Node.js with KafkaJS]]`, `[[13.04.05. Invoice Generator Worker PHP Laravel Queue]]`).
2. All four pass the same automated test suite: a Postman collection that posts 100 orders and asserts the 201/409 idempotency behavior; a pytest suite that injects 1000 events into `orders.events` and asserts each consumer processes all 1000 with `consumer_messages_processed_total{outcome="ok"}` = 1000 and `outcome="duplicate"` = 0 after deduplication; and a k6 load test asserting 1000 RPS at p99 < 50 ms on the producer.
3. At least one ecosystem is load-tested to failure, with a captured metric showing the failure and the fix. The default failure target is the Node.js broadcaster — under 10,000 connected WebSocket clients with 10,000 events/sec, the V8 event loop saturates and the `consumer_lag_partitions` metric climbs unboundedly until the broadcaster is horizontally scaled to a second instance with `consumer_group=ws-broadcaster` rebalancing partitions across both.
4. The post-mortem note (`[[13.04.06. Failure Injection and Rebalance Resilience Verification]]`) is filled in with concrete observations: the exact RPS at which each consumer's lag began climbing, the exact rebalance duration when one consumer was killed, the exact number of duplicate events observed when Debezium was restarted from a stale offset (must be ≥0 due to at-least-once; must be absorbed by consumer idempotency).

## Deliverables

- Source code for each ecosystem in a separate subfolder: `producer-springboot/`, `consumer-python/`, `broadcaster-nodejs/`, `worker-php/`. Each has its own `Dockerfile` and a `README.md` with run instructions.
- A `docker-compose.yml` at the project root that brings up: Postgres 16 (with `wal_level=logical` and a replication slot for Debezium), Kafka 3.7 (KRaft mode, single broker for dev, 3 brokers for the load-test profile), ZooKeeper disabled, Kafka Connect with the Debezium Postgres connector installed, the Spring Boot producer, and the three consumers. One `docker compose up -d` brings the whole system up.
- A `README.md` at the project root with: the architecture diagram from this spec, the API contract from this spec, the run command, the test command, the load-test command, and a screenshot of the Grafana dashboard mid-load-test showing all four services' metrics.
- A post-mortem note in this folder (`[[13.04.06. Failure Injection and Rebalance Resilience Verification]]`) with the four chaos-test results, the metric tables, and the lessons learned.
- A `debezium/register-postgres-source.json` file containing the Kafka Connect PUT payload that registers the source connector with the SMT chain described in R2.
