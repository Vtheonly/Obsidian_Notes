# 13.04.02. Primary Engine Spring Boot Producer and Debezium CDC

## Scope

This is the **anchor implementation** for Milestone 4 — the Spring Boot service that owns the `POST /api/orders` endpoint, the Postgres `orders` and `outbox` tables, and the ACID transaction that writes both rows atomically. It is also where the Debezium CDC connector is wired up so that outbox inserts become Kafka records without the application ever calling `kafka.send()`. The three downstream consumers (Python, Node, PHP) in `[[13.04.03. Analytics Consumer Python with confluent-kafka]]`, `[[13.04.04. Real-Time WebSocket Broadcaster Node.js with KafkaJS]]`, and `[[13.04.05. Invoice Generator Worker PHP Laravel Queue]]` are pure deltas against this anchor — they read from the topic this producer populates and they have to honor the event schema and Kafka headers defined here.

The reason this is the anchor and not, say, the Python consumer is that the producer is the component that defines the contract. The Outbox table layout, the `OrderCreated` event JSON shape, the W3C `trace_id` propagation through Kafka headers, the `Idempotency-Key` deduplication strategy — all of these are decided once, here, in Java, and the consumers conform. Spring Boot is also the only ecosystem in the milestone that has first-class JPA `@Transactional` semantics, a mature connection pool (HikariCP), and a clean story for declarative input validation (`@Valid` + Bean Validation). The downstream consumers in dynamic languages have to implement the same guarantees manually, which is exactly the lesson the deltas are designed to teach.

## What You Are Building

A Spring Boot 3.3 application (Java 21, Spring Boot Web, Spring Data JPA, Spring Boot Actuator, PostgreSQL JDBC driver, Micrometer + Prometheus registry) that exposes one HTTP endpoint, owns two Postgres tables, and runs no Kafka client library of its own. The Kafka emission is delegated entirely to a Debezium source connector running in a separate Kafka Connect container. The application's responsibility ends at "commit the transaction"; everything after that is Debezium's job.

## Implementation Steps

### Step 1 — Schema (Flyway migration)

The schema is the contract. Get it right before writing any Java.

```sql
-- src/main/resources/db/migration/V1__init.sql

CREATE TYPE order_status AS ENUM ('CREATED', 'PAID', 'SHIPPED', 'CANCELLED');

CREATE TABLE orders (
    id              BIGSERIAL    PRIMARY KEY,
    order_ref       TEXT         NOT NULL UNIQUE,             -- ord_3f8a9c1e2b4d6f8a
    buyer_id        TEXT         NOT NULL,
    seller_id       TEXT         NOT NULL,
    total_cents     BIGINT       NOT NULL CHECK (total_cents > 0),
    currency        CHAR(3)      NOT NULL,
    status          order_status NOT NULL DEFAULT 'CREATED',
    trace_id        TEXT,                                     -- W3C trace_id
    created_at      TIMESTAMPTZ  NOT NULL DEFAULT now()
);
CREATE INDEX idx_orders_seller ON orders (seller_id, created_at DESC);
CREATE INDEX idx_orders_buyer  ON orders (buyer_id,  created_at DESC);

CREATE TABLE order_items (
    order_id        BIGINT       NOT NULL REFERENCES orders(id) ON DELETE CASCADE,
    sku             TEXT         NOT NULL,
    qty             INT          NOT NULL CHECK (qty > 0),
    unit_price_cents BIGINT      NOT NULL CHECK (unit_price_cents >= 0),
    PRIMARY KEY (order_id, sku)
);

-- Idempotency: a replayed Idempotency-Key must return the original order.
CREATE TABLE idempotency_keys (
    key              TEXT        PRIMARY KEY,
    order_id         BIGINT      NOT NULL REFERENCES orders(id),
    response_json    JSONB       NOT NULL,
    created_at       TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- The Outbox. Debezium tails this table via the WAL.
CREATE TABLE outbox (
    id              UUID         PRIMARY KEY,
    aggregate_type  TEXT         NOT NULL,                     -- 'Order'
    aggregate_id    TEXT         NOT NULL,                     -- order_ref
    event_type      TEXT         NOT NULL,                     -- 'OrderCreated'
    payload         JSONB        NOT NULL,
    trace_id        TEXT,
    created_at      TIMESTAMPTZ  NOT NULL DEFAULT now()
);
CREATE INDEX idx_outbox_unprocessed ON outbox (created_at) WHERE created_at < now();
-- Debezium reads via replication slot; no application query ever touches this index.
-- It exists only as a fallback for the polling-relay variant.

-- Replication slot + publication for Debezium (run as superuser).
SELECT pg_create_logical_replication_slot('debezium_slot', 'pgoutput');
CREATE PUBLICATION dbz_publication FOR TABLE outbox;
ALTER TABLE outbox REPLICA IDENTITY FULL;   -- so Debezium sees full row on UPDATE
```

### Step 3 — Service (the transactional core)

This is the heart of the Outbox pattern: the order, the outbox event, and the idempotency-key row are all written in one `SERIALIZABLE` transaction. There is no Kafka client here. There is no `applicationEventPublisher.publishEvent` either — that would publish after commit and is the antipattern this milestone exists to cure.

```java
// src/main/java/com/example/producer/service/OrderService.java
package com.example.producer.service;

import com.example.producer.api.CreateOrderRequest;
import com.example.producer.api.CreateOrderResponse;
import com.example.producer.domain.*;
import com.example.producer.repo.*;
import com.fasterxml.jackson.core.JsonProcessingException;
import com.fasterxml.jackson.databind.ObjectMapper;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.security.SecureRandom;
import java.time.Instant;
import java.util.List;

@Service
public class OrderService {

    private final OrderRepository        orderRepo;
    private final OutboxRepository       outboxRepo;
    private final IdempotencyKeyRepository idemRepo;
    private final ObjectMapper           json;
    private final SecureRandom           rng = new SecureRandom();

    public OrderService(OrderRepository o, OutboxRepository b,
                        IdempotencyKeyRepository i, ObjectMapper j) {
        this.orderRepo = o; this.outboxRepo = b;
        this.idemRepo  = i; this.json      = j;
    }

    @Transactional(isolation = Isolation.SERIALIZABLE)
    public CreateOrderResponse createOrder(CreateOrderRequest req, String idemKey, String traceId) {
        // 1. Idempotency replay — if we've seen this key, return the cached response.
        return idemRepo.findById(idemKey)
            .map(k -> CreateOrderResponse.replayed(k.getResponseJson()))
            .orElseGet(() -> createNew(req, idemKey, traceId));
    }

    private CreateOrderResponse createNew(CreateOrderRequest req, String idemKey, String traceId) {
        // 2. Build the order aggregate.
        Order order = new Order();
        order.setOrderRef(generateOrderRef());
        order.setBuyerId(req.buyerId());
        order.setSellerId(req.sellerId());
        order.setCurrency(req.currency());
        order.setTraceId(traceId);

        long total = 0;
        for (var item : req.items()) {
            OrderItem oi = new OrderItem();
            oi.setSku(item.sku());
            oi.setQty(item.qty());
            oi.setUnitPriceCents(item.unitPriceCents());
            order.getItems().add(oi);
            total += (long) item.qty() * item.unitPriceCents();
        }
        order.setTotalCents(total);
        orderRepo.save(order);   // INSERT into orders, order_items

        // 3. Build the outbox event — same transaction, same commit.
        OutboxEvent evt = new OutboxEvent();
        evt.setAggregateType("Order");
        evt.setAggregateId(order.getOrderRef());
        evt.setEventType("OrderCreated");
        evt.setTraceId(traceId);
        try {
            evt.setPayload(json.writeValueAsString(new OrderCreatedPayload(
                "evt_" + UUID.randomUUID(), "OrderCreated", order.getOrderRef(),
                Instant.now(), req.buyerId(), req.sellerId(), total, req.currency(),
                req.items(), traceId)));
        } catch (JsonProcessingException e) {
            throw new IllegalStateException("payload serialization failed", e);
        }
        outboxRepo.save(evt);    // INSERT into outbox — Debezium will pick this up

        // 4. Cache the idempotency key with the response.
        CreateOrderResponse resp = new CreateOrderResponse(
            order.getOrderRef(), req.buyerId(), req.sellerId(),
            total, req.currency(), "CREATED", order.getCreatedAt(), traceId);
        try {
            idemRepo.save(new IdempotencyKey(idemKey, order.getId(),
                       json.writeValueAsString(resp)));
        } catch (JsonProcessingException e) {
            throw new IllegalStateException(e);
        }
        return resp;
    }

    private String generateOrderRef() {
        byte[] b = new byte[8];
        rng.nextBytes(b);
        StringBuilder s = new StringBuilder("ord_");
        for (byte x : b) s.append(String.format("%02x", x));
        return s.toString();        // ord_3f8a9c1e2b4d6f8a
    }

    // Inner DTO used only for the JSON payload
    public record OrderCreatedPayload(
        String event_id, String event_type, String aggregate_id,
        Instant occurred_at, String buyer_id, String seller_id,
        long total_cents, String currency, List<CreateOrderRequest.Item> items,
        String trace_id) {}
}
```

### Step 4 — Controller + W3C trace_id filter

```java
// src/main/java/com/example/producer/api/OrderController.java
package com.example.producer.api;

import com.example.producer.service.OrderService;
import io.micrometer.core.instrument.Counter;
import io.micrometer.core.instrument.MeterRegistry;
import jakarta.validation.Valid;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/api/orders")
public class OrderController {

    private final OrderService svc;
    private final Counter ordersCreated;

    public OrderController(OrderService svc, MeterRegistry reg) {
        this.svc = svc;
        this.ordersCreated = Counter.builder("orders_created_total")
            .description("Total orders created")
            .register(reg);
    }

    @PostMapping
    public ResponseEntity<CreateOrderResponse> create(
            @Valid @RequestBody CreateOrderRequest req,
            @RequestHeader("Idempotency-Key") String idemKey,
            @RequestHeader(value = "traceparent", required = false) String traceparent) {

        String traceId = extractTraceId(traceparent);
        CreateOrderResponse resp = svc.createOrder(req, idemKey, traceId);
        ordersCreated.increment();

        return resp.replayed()
            ? ResponseEntity.status(409).body(resp)         // idempotent replay
            : ResponseEntity.status(201).body(resp);        // fresh creation
    }

    private static String extractTraceId(String tp) {
        if (tp == null || tp.length() < 55) return null;
        return tp.substring(3, 35);   // 00-<32 hex chars>-...
    }
}
```

```java
// src/main/java/com/example/producer/trace/TraceIdFilter.java
package com.example.producer.trace;

import jakarta.servlet.*;
import jakarta.servlet.http.*;
import org.springframework.core.annotation.Order;
import org.springframework.stereotype.Component;
import java.io.IOException;

@Component
@Order(1)
public class TraceIdFilter implements Filter {

    @Override
    public void doFilter(ServletRequest rq, ServletResponse rs, FilterChain chain)
            throws IOException, ServletException {
        HttpServletRequest  req = (HttpServletRequest) rq;
        HttpServletResponse res = (HttpServletResponse) rs;

        String tp = req.getHeader("traceparent");
        String traceId = (tp != null && tp.length() >= 55)
            ? tp.substring(3, 35)
            : java.util.UUID.randomUUID().toString().replace("-", "");

        // Echo back so the client can correlate
        if (tp == null) {
            String newTp = "00-" + traceId + "-"
                + java.util.UUID.randomUUID().toString().replace("-", "").substring(0, 16)
                + "-01";
            res.setHeader("traceparent", newTp);
        }
        MDC.put("trace_id", traceId);
        try { chain.doFilter(rq, rs); }
        finally { MDC.clear(); }
    }
}
```

Register it with: `curl -X PUT -H "Content-Type: application/json" --data @debezium/register-postgres-source.json http://connect:8083/connectors/orders-postgres-source/config`. ## Load-Test It

```bash
# k6 against the producer — 1000 RPS for 60s, asserts p99 < 50ms
k6 run --env TARGET=http://localhost:8080 loadtests/producer-load.js

# verify consumer lag stayed bounded during the run
docker exec kafka kafka-consumer-groups \
  --bootstrap-server localhost:9092 \
  --describe --all-groups
```

The expected behavior under load: `orders_created_total` rises at ~1000/s; Postgres `pg_stat_database.xact_commit` rises at the same rate; HikariCP `hikaricp.connections.active` settles around 8–12 (well below the 20-pool ceiling); Kafka `orders.events` partition byte-rate rises ~150 KB/s (each event ~150 bytes); consumer lag for all three downstream consumers stays bounded by their own processing capacity, not by the producer's commit rate. If the producer's p99 climbs above 50 ms, the bottleneck is almost always HikariCP `connection-timeout` (pool too small) or Postgres WAL fsync (storage IOPS bound), never Kafka.

## What This Teaches

This anchor teaches three lessons the deltas cannot:

**1. The Outbox pattern is a transaction design, not a Kafka feature.** Spring's `@Transactional(isolation = SERIALIZABLE)` is the only reason this works. The `OrderService.createNew` method writes three rows — order, outbox event, idempotency key — and they all commit atomically. If you removed the `@Transactional` annotation, you would have a publish-after-commit race: the order could commit, the outbox insert could fail, and Debezium would never see the event. The pattern's correctness lives in the transaction boundary, which is why the Python consumer has no analogous concept to teach — Python consumers just receive events; they don't have to originate them transactionally.

**2. Debezium is the cleanest way to bridge Postgres to Kafka, and it's worth the operational cost.** The alternative is a polling relay (`SELECT * FROM outbox WHERE processed_at IS NULL ORDER BY created_at LIMIT 100 FOR UPDATE SKIP LOCKED` in a loop). The polling relay is simpler to deploy but has three problems the CDC approach avoids: (a) it polls even when there's nothing to do, wasting DB resources; (b) it cannot deliver sub-second latency without an aggressive poll interval that compounds the waste; (c) it requires the application to mark rows as processed, which means another write and another transaction. Debezium tails the WAL — zero application impact, ~100 ms latency, and the offset-storage topic means it survives its own crashes without losing or duplicating events. The cost is operating Kafka Connect, which is non-trivial, but it's a one-time cost amortized across every table you ever want to stream.

**3. W3C `traceparent` propagation is a contract you enforce at the framework boundary.** The `TraceIdFilter` runs once per request, extracts or generates the trace_id, stashes it in MDC for log correlation, and the `OrderController` passes it down to the service which writes it into both the `orders.trace_id` column and the `outbox.trace_id` column. Debezium propagates it into the Kafka record headers (via a custom Single Message Transform, not shown here for brevity). The downstream consumers read the header and use it in their own logs. This is the only way to follow one order from browser → producer → Postgres → Debezium → all three consumers in a single Jaeger trace, and it requires the producer to set the convention. The deltas have to conform; the anchor defines.
