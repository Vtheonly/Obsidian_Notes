# 13.04.05. Invoice Generator Worker PHP Laravel Queue

## Scope

This is the **PHP delta** for Milestone 4 — a Laravel 11 queue worker that consumes `OrderCreated` events from the `orders.events` topic, generates a PDF invoice via `barryvdh/laravel-dompdf`, uploads the PDF to S3, and writes an `invoices` row with `order_id`, `s3_url`, `generated_at`. It is the only consumer in the milestone that produces a **side effect on the filesystem and on S3** rather than on a database row — and that distinction is what makes its idempotency story harder than the Python aggregator's. The Python consumer deduplicates with a single `processed_events` table and a unique constraint; the PHP worker has to deduplicate across three independent systems (the database row, the S3 object, and the filesystem path where the PDF is staged before upload) none of which share a transaction.

The choice of PHP for this role is deliberate. Laravel's `queue:work` daemon is the most mature job-runner in any of the four ecosystems: it has built-in retry with exponential backoff, dead-letter queues via `failed_jobs` table, signal handling for graceful shutdown, and a Horizon dashboard for visibility. The Spring Boot anchor could have done this work in a `@KafkaListener` method, but the PHP/Laravel queue worker is the canonical pattern for "background job that takes 5–30 seconds and might fail" — it's the shape every email-sender, report-generator, and PDF-renderer in production PHP-land takes. Doing it in PHP teaches the pattern in its native idiom rather than forcing it into a JVM-shaped hole.

The lesson this delta teaches that the anchor and the other deltas hide is **idempotency across multiple side-effecting systems**. The PDF is written to `/tmp/invoices/ord_xxx.pdf`, uploaded to `s3://invoices/ord_xxx.pdf`, and the `invoices` table row is inserted. If the worker crashes between the S3 upload and the DB insert, the next run must NOT regenerate the PDF (wasted CPU) and must NOT re-upload to S3 (overwriting a perfectly good object is fine, but incurs egress cost and clobbers the object's version history if versioning is on). The fix is to use S3's `If-None-Match: *` conditional PUT, which atomically refuses to overwrite an existing object — this gives the worker a single idempotency check that spans both the S3 and the DB layers without requiring a distributed transaction.

The `invoices.order_id` UNIQUE constraint is the database-level idempotency guarantee. A second INSERT with the same `order_id` raises `SQLSTATE[23505]: Unique violation` — which the job catches and treats as "already done."

### Step 3 — Idempotency guard

```php
<?php
// app/Services/IdempotencyGuard.php
namespace App\Services;

use App\Models\Invoice;
use App\Models\ProcessedEvent;
use Illuminate\Support\Facades\DB;
use App\Exceptions\InvoiceAlreadyExists;

class IdempotencyGuard
{
    /**
     * Check whether this event has already been processed.
     * Returns true if newly claimed (caller should proceed),
     * false if already processed (caller should skip silently).
     */
    public function claimEvent(string $eventId, string $orderId, ?string $traceId): bool
    {
        try {
            ProcessedEvent::create([
                'event_id'   => $eventId,
                'order_id'   => $orderId,
                'trace_id'   => $traceId,
            ]);
            return true;     // newly claimed
        } catch (\Illuminate\Database\QueryException $e) {
            if ($e->getCode() === '23505') {  // unique violation
                return false;                  // already processed — skip
            }
            throw $e;
        }
    }

    /**
     * Insert the invoice row — idempotent on order_id.
     * Throws InvoiceAlreadyExists if the order already has an invoice.
     */
    public function insertInvoice(array $attrs): Invoice
    {
        try {
            return DB::transaction(function () use ($attrs) {
                return Invoice::create($attrs);
            });
        } catch (\Illuminate\Database\QueryException $e) {
            if ($e->getCode() === '23505') {
                throw InvoiceAlreadyExists::forOrder($attrs['order_id']);
            }
            throw $e;
        }
    }
}
```

The `claimEvent` method is the first line of defense: it inserts into `processed_events` with the unique `event_id` as the primary key. A redelivered event hits the unique constraint, raises `23505`, and is silently dropped. This is the PHP equivalent of the Python `INSERT ... ON CONFLICT DO NOTHING RETURNING` pattern, expressed via Laravel's exception-based control flow rather than SQL syntax.

### Step 4 — Invoice storage (S3 with If-None-Match)

```php
<?php
// app/Services/InvoiceStorage.php
namespace App\Services;

use Illuminate\Support\Facades\Storage;
use Illuminate\Contracts\Filesystem\Filesystem;
use App\Exceptions\InvoiceAlreadyExists;

class InvoiceStorage
{
    private Filesystem $disk;

    public function __construct()
    {
        $this->disk = Storage::disk('s3');
    }

    /**
     * Upload the PDF to S3 idempotently.
     * Uses PutObject with If-None-Match: "*" so the upload is rejected
     * if an object already exists at this key — this is the S3-level
     * idempotency check that survives a crash between upload and DB insert.
     */
    public function upload(string $orderId, string $pdfContent): string
    {
        $key = "invoices/{$orderId}.pdf";
        $bucket = config('filesystems.disks.s3.bucket');

        // Flysystem doesn't expose conditional PUTs, so we drop to the
        // underlying AWS SDK directly.
        $client = Storage::disk('s3')->getClient();
        try {
            $client->putObject([
                'Bucket'        => $bucket,
                'Key'           => $key,
                'Body'          => $pdfContent,
                'ContentType'   => 'application/pdf',
                'IfNoneMatch'   => '*',   // <<< THE IDEMPOTENCY ANCHOR
                'Metadata'      => [
                    'order-id' => $orderId,
                ],
            ]);
        } catch (\Aws\S3\Exception\S3Exception $e) {
            // 412 Precondition Failed = object already exists — that's fine,
            // it means a previous run already uploaded this invoice.
            if ($e->getStatusCode() === 412) {
                throw InvoiceAlreadyExists::forOrder($orderId);
            }
            throw $e;
        }
        return "s3://{$bucket}/{$key}";
    }

    public function exists(string $orderId): bool
    {
        return $this->disk->exists("invoices/{$orderId}.pdf");
    }
}
```

The `IfNoneMatch: '*'` parameter on `putObject` is the S3 equivalent of a SQL UNIQUE constraint. If the object already exists, S3 returns `412 Precondition Failed` and the upload is rejected — without this, every retry would overwrite the existing PDF, clobbering its version history if S3 versioning is on and consuming egress bandwidth on every retry. The 412 is the idempotency signal: "this invoice was already uploaded, don't try again."

### Step 6 — The Job (orchestrates render → upload → insert)

```php
<?php
// app/Jobs/GenerateInvoiceJob.php
namespace App\Jobs;

use App\Services\IdempotencyGuard;
use App\Services\InvoiceRenderer;
use App\Services\InvoiceStorage;
use App\Exceptions\InvoiceAlreadyExists;
use Illuminate\Bus\Queueable;
use Illuminate\Contracts\Queue\ShouldQueue;
use Illuminate\Foundation\Bus\Dispatchable;
use Illuminate\Queue\InteractsWithQueue;
use Illuminate\Queue\SerializesModels;
use Illuminate\Support\Facades\Log;
use Illuminate\Support\Facades\Storage;

class GenerateInvoiceJob implements ShouldQueue
{
    use Dispatchable, InteractsWithQueue, Queueable, SerializesModels;

    public int $tries     = 3;
    public int $backoff   = 10;             // seconds; overridden per-attempt below
    public int $timeout   = 60;             // Laravel job timeout

    public function __construct(
        public readonly array $event,        // the OrderCreated payload
    ) {}

    public function handle(
        IdempotencyGuard $guard,
        InvoiceRenderer  $renderer,
        InvoiceStorage   $storage,
    ): void {
        $evt = $this->event;
        $orderId = $evt['aggregate_id'];
        $traceId = $evt['trace_id'] ?? null;

        Log::info('invoice_job_started', [
            'order_id' => $orderId,
            'event_id' => $evt['event_id'],
            'trace_id' => $traceId,
        ]);

        // 1. Idempotency check #1: processed_events table.
        //    If we've already claimed this event_id, skip silently.
        if (!$guard->claimEvent($evt['event_id'], $orderId, $traceId)) {
            Log::info('invoice_job_deduplicated', [
                'event_id' => $evt['event_id'],
                'order_id' => $orderId,
            ]);
            return;
        }

        try {
            // 2. Render the PDF (CPU-bound, 100-500ms).
            $pdfBytes = $renderer->render($evt);

            // 3. Upload to S3 with If-None-Match (idempotency check #2).
            $s3Url = $storage->upload($orderId, $pdfBytes);

            // 4. Insert the invoices row (idempotency check #3 — unique order_id).
            $guard->insertInvoice([
                'order_id'    => $orderId,
                'buyer_id'    => $evt['buyer_id'],
                'seller_id'   => $evt['seller_id'],
                'total_cents' => $evt['total_cents'],
                'currency'    => $evt['currency'],
                's3_url'      => $s3Url,
                'status'      => 'GENERATED',
                'trace_id'    => $traceId,
            ]);

            Log::info('invoice_job_completed', [
                'order_id' => $orderId,
                's3_url'   => $s3Url,
                'trace_id' => $traceId,
            ]);
        } catch (InvoiceAlreadyExists $e) {
            // Already done by a previous run — log and exit cleanly.
            Log::info('invoice_already_exists', [
                'order_id' => $orderId,
                'reason'   => $e->getMessage(),
            ]);
        }
    }

    /**
     * Exponential backoff: 10s, 30s, 60s for the 3 attempts.
     */
    public function backoff(): array
    {
        return [10, 30, 60];
    }

    /**
     * Determine if the job should retry on this exception.
     * InvoiceAlreadyExists is NOT retriable — it means we succeeded already.
     */
    public function shouldRetry(\Throwable $e): bool
    {
        return !($e instanceof InvoiceAlreadyExists);
    }
}
```

### Step 7 — The Kafka consumer command (wraps rdkafka)

```php
<?php
// app/Console/Commands/ConsumeOrdersCommand.php
namespace App\Console\Commands;

use App\Jobs\GenerateInvoiceJob;
use Illuminate\Console\Command;
use Illuminate\Support\Facades\Log;
use RdKafka\Conf;
use RdKafka\KafkaConsumer;
use RdKafka\Message;

class ConsumeOrdersCommand extends Command
{
    protected $signature = 'orders:consume
                            {--topic=orders.events}
                            {--group=invoice-worker}
                            {--commit=sync}';
    protected $description = 'Consume OrderCreated events and dispatch invoice jobs';

    public function handle(): int
    {
        $conf = new Conf();
        $conf->set('bootstrap.servers',     config('kafka.brokers'));
        $conf->set('group.id',              $this->option('group'));
        $conf->set('auto.offset.reset',     'earliest');
        $conf->set('enable.auto.commit',    'false');   // MANUAL COMMIT ONLY
        $conf->set('session.timeout.ms',    '45000');
        $conf->set('max.poll.interval.ms',  '300000');
        $conf->set('partition.assignment.strategy', 'cooperative-sticky');

        $conf->setRebalanceCb(function (KafkaConsumer $k, $err, array $partitions = null) {
            switch ($err) {
                case RD_KAFKA_RESP_ERR__ASSIGN_PARTITIONS:
                    $this->info("Assigned: " . count($partitions) . " partitions");
                    $k->assign($partitions);
                    break;
                case RD_KAFKA_RESP_ERR__REVOKE_PARTITIONS:
                    $this->info("Revoking: " . count($partitions) . " partitions");
                    // COMMIT BEFORE REVOKE — same pattern as Python consumer
                    $k->commitSync();
                    $k->assign(null);
                    break;
            }
        });

        $consumer = new KafkaConsumer($conf);
        $consumer->subscribe([$this->option('topic')]);

        $this->info("Consuming from {$this->option('topic')} as group {$this->option('group')}");

        pcntl_signal(SIGTERM, fn() => $this->info('SIGTERM received, draining...'));
        pcntl_signal(SIGINT,  fn() => $this->info('SIGINT received, draining...'));

        while (true) {
            pcntl_signal_dispatch();
            $msg = $consumer->consume(1000);    // 1s timeout

            switch ($msg->err) {
                case RD_KAFKA_RESP_ERR_NO_ERROR:
                    $this->handleMessage($consumer, $msg);
                    break;
                case RD_KAFKA_RESP_ERR__PARTITION_EOF:
                case RD_KAFKA_RESP_ERR__TIMED_OUT:
                    break;
                default:
                    $this->error("Kafka error: {$msg->errstr()}");
                    break;
            }
        }
    }

    private function handleMessage(KafkaConsumer $consumer, Message $msg): void
    {
        $payload = json_decode($msg->payload, true);
        if (!$payload || ($payload['event_type'] ?? null) !== 'OrderCreated') {
            $consumer->commitSync($msg);   // poison pill — skip
            return;
        }

        try {
            // DISPATCH the job — does not block. The job runs on the queue worker,
            // which is a separate `php artisan queue:work` process. This separation
            // means the consumer can keep up with high event rates even though
            // PDF rendering is slow (100-500ms per invoice).
            GenerateInvoiceJob::dispatch($payload);

            // COMMIT AFTER DISPATCH — if dispatch fails (queue broker down),
            // we don't commit, and the event is redelivered on next poll.
            $consumer->commitSync($msg);
        } catch (\Throwable $e) {
            Log::error('dispatch_failed', [
                'err'      => $e->getMessage(),
                'order_id' => $payload['aggregate_id'] ?? null,
            ]);
            // DO NOT COMMIT — let the event be redelivered
            throw $e;
        }
    }
}
```

### Step 8 — Run the worker

The Kafka consumer and the queue worker are deliberately two separate processes. The consumer is fast (just dispatches the job) and keeps up with the producer's RPS; the queue worker is slow (renders PDFs) and runs in as many parallel processes as you need to drain the queue.

```bash
# Terminal 1: the Kafka consumer (dispatches jobs to the queue)
php artisan orders:consume --topic=orders.events --group=invoice-worker

# Terminal 2 (or N terminals, one per CPU): the queue worker (runs the jobs)
php artisan queue:work redis --tries=3 --backoff=10,30,60 --timeout=60

# Or use Supervisor to run N parallel workers:
# /etc/supervisor/conf.d/invoice-worker.conf
# [program:invoice-worker]
# command=php /app/artisan queue:work redis --tries=3 --backoff=10,30,60
# numprocs=8
# process_name=%(program_name)s_%(process_num)02d
# autostart=true
# autorestart=true
# stopwaitsecs=70        # must exceed job timeout (60s) for graceful drain
```

## Test It

```bash
# Pest tests — the modern PHP test runner
./vendor/bin/pest tests/Feature/GenerateInvoiceJobTest.php
./vendor/bin/pest tests/Feature/IdempotencyTest.php
./vendor/bin/pest tests/Unit/InvoiceStorageTest.php
```

The most important test is `IdempotencyTest::test_redelivered_event_does_not_regenerate_pdf`. It dispatches `GenerateInvoiceJob` twice with the same event payload and asserts: only one `invoices` row exists, only one S3 PUT succeeded (the second raised `412 Precondition Failed`), only one `processed_events` row was inserted, and the job's second invocation exited cleanly without throwing. If any of those four assertions fails, your worker is not idempotent and you will silently double-render and double-upload on every rebalance.

## Load-Test It

```bash
# produce 1000 events/sec for 60s
k6 run --env TARGET=http://producer:8080 --env RATE=1000 --env DURATION=60s \
  loadtests/producer-flood.js

# monitor the queue depth (should drain within ~5 min after k6 finishes)
docker exec redis redis-cli LLEN queues:default

docker exec postgres psql -U ledger -d ledger -c \
  "SELECT count(*) FROM failed_jobs;"

# monitor the invoices table (should grow at 1000/s × worker parallelism)
docker exec postgres psql -U ledger -d ledger -c \
  "SELECT count(*), max(generated_at) FROM invoices;"
```

The expected behavior at 1,000 events/sec: the consumer keeps up with no lag (dispatch is <5 ms per event); the `queues:default` Redis list grows at the rate `producer_RPS - worker_parallelism / pdf_render_seconds` (i.e., at 1,000 RPS with 8 workers averaging 300 ms per PDF, the queue grows at 1000 - 8/0.3 ≈ 973/s — you need ~270 workers to drain in real time, or you accept that the queue grows during the load test and drains over the next 5 minutes); `failed_jobs` stays at 0; `invoices` row count grows linearly. The fix for the queue growing during the load test is to spin up more worker processes via Supervisor — `numprocs=32` or `numprocs=64` depending on available CPU.

## What This Teaches

This delta teaches three lessons the other consumers hide:

**1. Idempotency across multiple side-effecting systems is harder than idempotency on a single database row.** The Python aggregator writes to one Postgres table — one transaction, one unique constraint, done. The PHP worker writes to three systems: the `invoices` Postgres table, the S3 bucket (a separate API with its own consistency model), and the `processed_events` Postgres table. There is no distributed transaction spanning Postgres and S3, so the worker has to defend each system independently: `processed_events` for the dedup ledger, `If-None-Match: *` for S3, and `invoices.order_id UNIQUE` for the DB row. The pattern is "defend every side effect with its own idempotency anchor, and treat the failure of any one as a signal that the work is already done." This is the universal pattern for any worker that touches multiple systems — Stripe, Mailgun, Twilio, every external-API-calling job.

**2. Decouple the consumer from the worker when the per-event work is slow.** The Kafka consumer (`orders:consume`) and the queue worker (`queue:work`) are two separate processes, connected by Redis. The consumer is fast (just `dispatch()`s a job, <5 ms) and never falls behind the producer; the worker is slow (renders PDFs, 100-500 ms per job) and is horizontally scaled by running more processes via Supervisor. This separation means the consumer's Kafka offset commits are not gated on PDF rendering — if the consumer committed only after the PDF was uploaded, a slow render would hold the offset back, the consumer's session would time out (45 s default), and a rebalance would redeliver every in-flight event. By dispatching to a queue, the consumer commits the offset immediately after dispatch, the worker processes at its own pace, and the queue depth is the load-test metric you watch instead of consumer lag. This is the Laravel-shaped version of the "ingest fast, process slow" pattern that every batch-processing system eventually rediscovers.

**3. PHP's `ext-rdkafka` is the only choice, and it shares librdkafka with the Python and Node consumers — the protocol layer is universal.** The same librdkafka C library powers `confluent-kafka` (Python), `node-rdkafka` (Node, though this milestone uses pure-JS `kafkajs` for portability), `ext-rdkafka` (PHP), `confluent-kafka-go` (Go), and `librdkafka` itself (Rust via bindings). The protocol bytes on the wire are identical across all of them — a consumer group with `group.id=invoice-worker` joined from PHP is indistinguishable from one joined from Python. This is why the four ecosystems can interoperate in this milestone at all: they all speak the same Kafka wire protocol, just through different language bindings. The lesson is that the Kafka protocol is the universal contract, not the language ecosystem; choose the binding that fits your runtime, but never let the binding choice dictate the protocol.
