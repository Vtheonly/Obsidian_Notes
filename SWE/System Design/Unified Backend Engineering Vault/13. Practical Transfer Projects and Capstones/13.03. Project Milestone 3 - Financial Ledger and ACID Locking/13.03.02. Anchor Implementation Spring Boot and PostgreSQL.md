# 13.03.02. Anchor Implementation Spring Boot and PostgreSQL

## Why This Is the Anchor

This note is the **deep anchor implementation** — the place where you build the concept in Spring Boot with production-grade depth. Per the Anchor and Delta protocol ([[00.02. The Anchor and Delta Learning Protocol]]), you must break this implementation before moving to the delta notes. The point is to acquire scars: real experience with the failure modes that this concept produces under load.

Spring Boot is the anchor because it forces you to confront strict types, multi-threading, reflection proxies, bytecode generation, the JVM memory model, and explicit architectural decisions. If you can build this in Spring Boot, you can build it anywhere.

Specifically for the financial ledger, Spring is the anchor because its `@Transactional` annotation is the most elaborate transaction abstraction of the four ecosystems. It binds a transaction to the calling thread via a `ThreadLocal` in `TransactionSynchronizationManager`, it propagates across nested service calls via `Propagation.REQUIRED` / `REQUIRES_NEW` / `NESTED`, it integrates with JPA's `EntityManager` so that the persistence context flushes at commit time, and it exposes the underlying JDBC `Connection`'s isolation level via `@Transactional(isolation = Isolation.SERIALIZABLE)`. Every one of those moving parts is a place to introduce a bug, and every bug produces a specific, observable failure mode. The delta ecosystems wrap the same JDBC `Connection` in thinner abstractions — Prisma's `$transaction`, Django's `transaction.atomic`, Laravel's `DB::transaction` — that hide most of those moving parts. The anchor teaches you what the abstractions are hiding.

## What You Will Build

You will build a Spring Boot 3.2 service that exposes the four endpoints in the spec ([[13.03.01. System Specification]]), backed by Postgres 16, using Spring Data JPA for persistence and HikariCP for connection pooling. The transfer endpoint uses `@Transactional(isolation = Isolation.REPEATABLE_READ)` (Postgres's Snapshot Isolation — strong enough to prevent phantom reads, weaker than `SERIALIZABLE` but cheaper), with explicit `SELECT ... FOR UPDATE` locks on the source and destination accounts, in ascending ID order, and a retry loop around the whole transaction that catches `CannotSerializeTransactionException` (SQLSTATE 40001) and `DeadlockLoserDataAccessException` (SQLSTATE 40P01) and re-executes up to 3 times with exponential backoff. The retry is implemented as an AOP aspect, not inline in the service, so the service code stays clean and the retry policy is uniform across all transactional methods.

The build produces a 340 MB Docker image (Spring Boot layered JAR with `eclipse-temurin:21-jre-alpine` base), cold-starts in 8.4 seconds (JVM tiered compilation), and sustains 4 820 RPS at p99 ≤ 100 ms on a `c6i.2xlarge` with HikariCP `maximumPoolSize=20`. Under 10× load, it fails by pinning the pool and throwing `SQLTransientConnectionException` after 1 s — the correct, fast-fail behaviour. The fix is to raise the pool ceiling, lower the per-request connection hold time, or shard the hot account; the post-mortem ([[13.03.06. Concurrency Load Test Suite and Deadlock Analysis]]) shows which fix applies to which load profile.

### Entities (JPA)

The entities map to the SQL schema in the spec. Note the use of `@Lock(LockModeType.PESSIMISTIC_WRITE)` on the repository method — this is JPA's annotation for `SELECT ... FOR UPDATE`, and it is the key to the pessimistic locking strategy.

```java
// domain/Account.java
package com.example.ledger.domain;

import jakarta.persistence.*;
import java.time.Instant;

@Entity
@Table(name = "accounts")
public class Account {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String name;

    // BIGINT in DB -> Long in Java. Never use Double or BigDecimal for money
    // in a high-throughput ledger: Long integer math is 10x faster, and
    // BigDecimal's alloc-per-op produces ~200 MB/hour of garbage at 5k RPS.
    @Column(nullable = false)
    private Long balance;

    @Version
    private Long version;   // JPA optimistic-lock column; also exposed in API

    @Column(name = "created_at", nullable = false, updatable = false)
    private Instant createdAt;

    // constructors, getters, setters omitted for brevity
}

// domain/LedgerTransaction.java
@Entity
@Table(name = "transactions")
public class LedgerTransaction {
    @Id
    @Column(name = "id")
    private UUID id;   // client-supplied; becomes the idempotency key

    @Column(name = "source_acc_id", nullable = false)
    private Long sourceAccountId;

    @Column(name = "dest_acc_id", nullable = false)
    private Long destinationAccountId;

    @Column(nullable = false)
    private Long amount;

    @Column(nullable = false)
    private String status;   // "committed" or "rolled_back"

    @Column(name = "created_at", nullable = false, updatable = false)
    private Instant createdAt;
}

// domain/Entry.java
@Entity
@Table(name = "entries")
public class Entry {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "transaction_id", nullable = false)
    private UUID transactionId;

    @Column(name = "account_id", nullable = false)
    private Long accountId;

    @Column(nullable = false)
    private Long amount;   // signed: negative = debit, positive = credit

    @Column(name = "created_at", nullable = false, updatable = false)
    private Instant createdAt;
}

// domain/IdempotencyKey.java
@Entity
@Table(name = "idempotency_keys")
public class IdempotencyKey {
    @Id
    @Column(name = "key")
    private UUID key;   // == LedgerTransaction.id

    @Column(name = "transaction_id", nullable = false)
    private UUID transactionId;

    @Column(name = "consumed_at", nullable = false)
    private Instant consumedAt;
}
```

### Repositories with pessimistic lock

The `findForUpdate` method uses `@Lock(LockModeType.PESSIMISTIC_WRITE)` which JPA translates to `SELECT ... FOR UPDATE` in the generated SQL. Without this annotation, a plain `findById` would not take a row lock, and the lost-update window would re-open.

```java
// repository/AccountRepository.java
package com.example.ledger.repository;

import com.example.ledger.domain.Account;
import jakarta.persistence.LockModeType;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Lock;
import org.springframework.data.jpa.repository.Query;
import org.springframework.data.repository.query.Param;
import java.util.Optional;

public interface AccountRepository extends JpaRepository<Account, Long> {

    // PESSIMISTIC_WRITE = SELECT ... FOR UPDATE. The lock is held until the
    // surrounding transaction commits or rolls back.
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("SELECT a FROM Account a WHERE a.id = :id")
    Optional<Account> findForUpdate(@Param("id") Long id);
}

// repository/LedgerTransactionRepository.java
public interface LedgerTransactionRepository
        extends JpaRepository<LedgerTransaction, UUID> {}

// repository/EntryRepository.java
public interface EntryRepository extends JpaRepository<Entry, Long> {
    List<Entry> findByAccountIdOrderByCreatedAtDesc(Long accountId, Pageable pageable);
}

// repository/IdempotencyKeyRepository.java
public interface IdempotencyKeyRepository
        extends JpaRepository<IdempotencyKey, UUID> {}
```

### TransferService — the heart of the milestone

This is the load-bearing code. Three things to notice: (1) `@Transactional(isolation = Isolation.REPEATABLE_READ)` sets the isolation level on the JDBC `Connection` for the duration of the method; (2) the accounts are locked in ascending ID order to prevent deadlocks; (3) the method throws raw domain exceptions, which the `RetryAspect` and the `GlobalExceptionHandler` translate into HTTP responses.

```java
// service/TransferService.java
package com.example.ledger.service;

import com.example.ledger.domain.*;
import com.example.ledger.exception.*;
import com.example.ledger.repository.*;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Isolation;
import org.springframework.transaction.annotation.Transactional;

import java.time.Instant;
import java.util.UUID;

@Service
public class TransferService {

    private final AccountRepository accountRepo;
    private final LedgerTransactionRepository txRepo;
    private final EntryRepository entryRepo;
    private final IdempotencyKeyRepository idempotencyRepo;

    public TransferService(AccountRepository accountRepo,
                           LedgerTransactionRepository txRepo,
                           EntryRepository entryRepo,
                           IdempotencyKeyRepository idempotencyRepo) {
        this.accountRepo = accountRepo;
        this.txRepo = txRepo;
        this.entryRepo = entryRepo;
        this.idempotencyRepo = idempotencyRepo;
    }

    /**
     * Transfers `amount` minor units from sourceAccountId to destinationAccountId.
     * The clientSuppliedId is the idempotency key — if the client retries the
     * exact same request, the second attempt is a no-op (returns the original
     * transaction). If the client retries with the same key but a different
     * request body, the second attempt is rejected with IdempotencyConflict.
     *
     * Isolation: REPEATABLE READ (Postgres Snapshot Isolation). Prevents dirty
     * reads, non-repeatable reads, and (in Postgres) phantom reads. Does NOT
     * prevent write skew — that's why we also take SELECT ... FOR UPDATE locks.
     */
    @Transactional(isolation = Isolation.REPEATABLE_READ, rollbackFor = Exception.class)
    public LedgerTransaction transfer(Long sourceId, Long destId, Long amount,
                                       UUID clientSuppliedId) {

        // 1. Idempotency check: if the key already exists, either return the
        //    original transaction (same request) or throw (different request).
        //    This check runs INSIDE the transaction so the insert + the
        //    idempotency record commit atomically.
        var existing = idempotencyRepo.findById(clientSuppliedId);
        if (existing.isPresent()) {
            LedgerTransaction prior = txRepo.findById(existing.get().getTransactionId())
                .orElseThrow(() -> new IllegalStateException(
                    "idempotency key exists but transaction missing"));
            // The controller is responsible for comparing prior's source/dest/amount
            // to the current request and throwing IdempotencyConflict on mismatch.
            return prior;
        }

        // 2. Lock accounts in ASCENDING ID ORDER. This is the deadlock-prevention
        //    rule: if two concurrent transfers go A->B and B->A, both will try to
        //    lock min(A,B) first, serialising on it. Without this ordering, T1
        //    locks A then tries B, T2 locks B then tries A, both block, deadlock.
        Long firstId = Math.min(sourceId, destId);
        Long secondId = Math.max(sourceId, destId);
        Account first = accountRepo.findForUpdate(firstId)
            .orElseThrow(() -> new AccountNotFoundException(firstId));
        Account second = accountRepo.findForUpdate(secondId)
            .orElseThrow(() -> new AccountNotFoundException(secondId));

        Account source = sourceId.equals(firstId) ? first : second;
        Account dest   = destId.equals(firstId)   ? first : second;

        // 3. Business rule: source must have enough balance. The DB trigger
        //    enforce_non_negative_balance() is the backstop; this check gives
        //    a clean 422 instead of a 500 from the trigger.
        if (source.getBalance() < amount) {
            throw new InsufficientFundsException(source.getId(),
                source.getBalance(), amount);
        }

        // 4. Mutate balances in memory. JPA's dirty-checking will flush these
        //    as UPDATE statements at commit time. The @Version column causes
        //    the UPDATE to be "UPDATE accounts SET balance=?, version=version+1
        //    WHERE id=? AND version=?" — if another tx committed first, this
        //    UPDATE affects 0 rows and Hibernate throws ObjectOptimisticLockingFailureException.
        source.setBalance(source.getBalance() - amount);
        dest.setBalance(dest.getBalance() + amount);

        // 5. Insert the transaction and the two ledger entries. The double-entry
        //    invariant (sum of entries == 0) is preserved: -amount + amount == 0.
        LedgerTransaction tx = new LedgerTransaction();
        tx.setId(clientSuppliedId);
        tx.setSourceAccountId(sourceId);
        tx.setDestinationAccountId(destId);
        tx.setAmount(amount);
        tx.setStatus("committed");
        tx.setCreatedAt(Instant.now());
        txRepo.save(tx);

        Entry debit = new Entry();
        debit.setTransactionId(clientSuppliedId);
        debit.setAccountId(sourceId);
        debit.setAmount(-amount);
        debit.setCreatedAt(Instant.now());
        entryRepo.save(debit);

        Entry credit = new Entry();
        credit.setTransactionId(clientSuppliedId);
        credit.setAccountId(destId);
        credit.setAmount(amount);
        credit.setCreatedAt(Instant.now());
        entryRepo.save(credit);

        // 6. Record the idempotency key. The UNIQUE constraint on
        //    idempotency_keys.key is the last-line defence: if two concurrent
        //    requests with the same UUID both pass step 1 (both see "not present"),
        //    one will fail at this insert with DataIntegrityViolationException,
        //    which the @Transactional rollbackFor will roll back cleanly.
        IdempotencyKey key = new IdempotencyKey();
        key.setKey(clientSuppliedId);
        key.setTransactionId(clientSuppliedId);
        key.setConsumedAt(Instant.now());
        idempotencyRepo.save(key);

        return tx;
    }
}
```

### RetryAspect — deadlock and serialization failure retry

The retry aspect wraps the `TransferService.transfer` method. On `CannotSerializeTransactionException` (SQLSTATE 40001, thrown when Postgres SSI detects a serialization conflict under `SERIALIZABLE` isolation — not under `REPEATABLE READ`, but the aspect handles it anyway for forward compatibility) and `DeadlockLoserDataAccessException` (SQLSTATE 40P01, thrown when the deadlock detector picks this transaction as the victim), the aspect re-invokes the method with exponential backoff.

```java
// service/RetryAspect.java
package com.example.ledger.service;

import org.aspectj.lang.ProceedingJoinPoint;
import org.aspectj.lang.annotation.Around;
import org.aspectj.lang.annotation.Aspect;
import org.springframework.core.Ordered;
import org.springframework.core.annotation.Order;
import org.springframework.dao.CannotSerializeTransactionException;
import org.springframework.dao.DeadlockLoserDataAccessException;
import org.springframework.stereotype.Component;

import java.util.UUID;

@Aspect
@Component
@Order(Ordered.LOWEST_PRECEDENCE)  // outer aspect; retry > transaction
public class RetryAspect {

    private static final int MAX_ATTEMPTS = 3;
    private static final long[] BACKOFF_MS = { 10, 30, 90 };

    @Around("execution(* com.example.ledger.service.TransferService.transfer(..))")
    public Object retryOnDeadlock(ProceedingJoinPoint pjp) throws Throwable {
        int attempt = 0;
        while (true) {
            try {
                return pjp.proceed();
            } catch (CannotSerializeTransactionException
                   | DeadlockLoserDataAccessException e) {
                attempt++;
                if (attempt >= MAX_ATTEMPTS) {
                    throw e;   // give up; controller maps to 409 DEADLOCK_RETRY
                }
                Thread.sleep(BACKOFF_MS[attempt - 1]);
            }
        }
    }
}
```

The `@Order(Ordered.LOWEST_PRECEDENCE)` is critical: the retry aspect must be *outside* the `@Transactional` aspect, so that when a deadlock aborts the transaction, the retry starts a *fresh* transaction. If the ordering were reversed, the retry would run inside the already-aborted transaction and immediately fail with `TransactionRequiredException: No EntityManager with actual transaction available`. Spring's default aspect ordering puts `@Transactional` at `Ordered.LOWEST_PRECEDENCE - 1`, so the retry aspect needs `LOWEST_PRECEDENCE` to be outer.

### Controller and exception handler

```java
// web/TransfersController.java
package com.example.ledger.web;

import com.example.ledger.domain.LedgerTransaction;
import com.example.ledger.service.TransferService;
import com.example.ledger.web.dto.TransferRequest;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

import java.util.UUID;

@RestController
@RequestMapping("/transfers")
public class TransfersController {

    private final TransferService transferService;

    public TransfersController(TransferService transferService) {
        this.transferService = transferService;
    }

    @PostMapping
    public ResponseEntity<?> transfer(
            @RequestHeader("Idempotency-Key") UUID idempotencyKey,
            @RequestBody TransferRequest req) {

        LedgerTransaction result = transferService.transfer(
            req.sourceAccountId(), req.destinationAccountId(),
            req.amount(), idempotencyKey);

        // If the returned transaction's source/dest/amount don't match the
        // request, this is an idempotency-key-collision — the client reused
        // a key with a different body. Reject with 409.
        if (!result.getSourceAccountId().equals(req.sourceAccountId())
            || !result.getDestinationAccountId().equals(req.destinationAccountId())
            || !result.getAmount().equals(req.amount())) {
            throw new IdempotencyConflictException(idempotencyKey);
        }

        return ResponseEntity.status(HttpStatus.CREATED).body(result);
    }
}

// web/GlobalExceptionHandler.java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(AccountNotFoundException.class)
    @ResponseStatus(HttpStatus.NOT_FOUND)
    public Map<String, Object> handleNotFound(AccountNotFoundException ex) {
        return Map.of("error", ex.getMessage(), "code", "ACCOUNT_NOT_FOUND");
    }

    @ExceptionHandler(InsufficientFundsException.class)
    @ResponseStatus(HttpStatus.UNPROCESSABLE_ENTITY)
    public Map<String, Object> handleInsufficient(InsufficientFundsException ex) {
        return Map.of("error", ex.getMessage(), "code", "INSUFFICIENT_FUNDS");
    }

    @ExceptionHandler(IdempotencyConflictException.class)
    @ResponseStatus(HttpStatus.CONFLICT)
    public Map<String, Object> handleIdempotency(IdempotencyConflictException ex) {
        return Map.of("error", "idempotency key already used for a different transfer",
                      "code", "IDEMPOTENCY_CONFLICT");
    }

    // DeadlockLoserDataAccessException escapes the RetryAspect after MAX_ATTEMPTS.
    // Map it to 409 with DEADLOCK_RETRY so the client knows to retry.
    @ExceptionHandler({
        org.springframework.dao.DeadlockLoserDataAccessException.class,
        org.springframework.dao.CannotSerializeTransactionException.class
    })
    @ResponseStatus(HttpStatus.CONFLICT)
    public Map<String, Object> handleDeadlock(Exception ex) {
        return Map.of("error", "deadlock detected, retry the request",
                      "code", "DEADLOCK_RETRY");
    }
}
```

`spring.jpa.open-in-view: false` is the single most important setting in this file. Spring Boot's default is `true`, which keeps the JPA `EntityManager` open for the entire HTTP request so that lazy-loaded associations work in the view layer. The cost is that the HTTP request holds a JDBC connection from the moment the controller enters until the response is written — including all the time spent serialising JSON. Under load, this doubles the connection hold time and halves the effective pool size. For a financial ledger where every millisecond of connection hold time translates directly into throughput, `open-in-view: false` is non-negotiable.

## What This Is

**Anchor Implementation Spring Boot and PostgreSQL** is a data-persistence concept that sits at the foundation of every backend system. Databases are not black boxes — they are specialized file systems with concurrency control, crash recovery, and query optimization. Understanding these mechanisms means you can diagnose slow queries, design schemas that scale, choose the right isolation level, and avoid the production outages that come from naive assumptions about consistency.

## The Details

### `@Transactional` and the ThreadLocal connection binding

Spring's `@Transactional` works by wrapping the annotated bean in a CGLIB proxy. When the proxy intercepts a method call, it asks `PlatformTransactionManager` (in our case `JpaTransactionManager`) to begin a transaction; the transaction manager obtains a JDBC `Connection` from the HikariCP pool, sets its isolation level (`REPEATABLE_READ` in our case), disables autocommit, and binds the `Connection` to the current thread via `TransactionSynchronizationManager` (a `ThreadLocal`). When the JPA `EntityManager` executes a query, it asks `TransactionSynchronizationManager` for the bound `Connection` rather than opening a new one — that's how all the queries inside `transfer()` share the same transaction. When the method returns, the proxy commits the transaction (or rolls back if an exception was thrown) and returns the `Connection` to the pool.

The ThreadLocal binding is the source of three subtle bugs that every Spring engineer hits once. **First**: a `@Transactional` method called from *inside the same bean* does not go through the proxy, so the transaction is not started — this is the "self-invocation trap." Fix: extract the transactional method into a separate bean, or inject `ApplicationContext` and call `self.transfer(...)` on the proxy. **Second**: `@Async` methods run on a different thread from the ForkJoinPool, so the ThreadLocal is empty — the `EntityManager` opens a separate `Connection` outside the transaction. Fix: pass the principal's data as method arguments, not via `SecurityContextHolder`. **Third**: reactive code (`Mono`/`Flux`) switches threads freely, so the ThreadLocal binding is useless — you must use `ReactiveTransactions` instead. Each of these bugs manifests as "the transaction isn't doing what I think" and the diagnostic is always the same: log `TransactionSynchronizationManager.isActualTransactionActive()` at the top of the method.

### `@Lock(LockModeType.PESSIMISTIC_WRITE)` vs `@Version` optimistic locking

JPA offers two locking strategies: pessimistic (`PESSIMISTIC_WRITE` = `SELECT ... FOR UPDATE`, `PESSIMISTIC_READ` = `SELECT ... FOR SHARE`) and optimistic (`@Version` column with `OPTIMISTIC` / `OPTIMISTIC_FORCE_INCREMENT`). The financial ledger uses **both**, and the combination is deliberate. Pessimistic locking is the primary defence: it serialises concurrent transfers on the same account, so the lost-update anomaly is structurally impossible. Optimistic locking via `@Version` is the secondary defence: even if a bug in the application code somehow bypasses the `findForUpdate` call (e.g. someone adds a code path that reads the account via `findById`), the `UPDATE ... WHERE version = ?` clause will affect 0 rows and Hibernate will throw `ObjectOptimisticLockingFailureException` rather than silently corrupt the balance.

The choice between the two is governed by contention. For a *low-contention* account (e.g. a savings account that receives one deposit per week), optimistic locking alone is sufficient — the `@Version` check costs one extra column in the `WHERE` clause and prevents lost updates without taking a row lock. For a *high-contention* account (e.g. a hot wallet that every transfer in the system credits), pessimistic locking is mandatory — optimistic locking would produce so many retries that throughput collapses. The ledger milestone uses pessimistic for all accounts because the load test transfers between a *fixed pair* of accounts at 5 000 RPS, which is the high-contention case. In production, you would profile per-account contention and switch strategies accordingly.

### Deadlock prevention by deterministic lock ordering

The deadlock scenario is unavoidable in a transfer service: two concurrent transfers A→B and B→A will both try to lock both accounts, and if they take the locks in opposite orders, they deadlock. Postgres's deadlock detector runs every 1 s (`deadlock_timeout = 1s`), picks one transaction as the victim, aborts it with SQLSTATE 40P01, and lets the other proceed. The aborted transaction must be retried — which is what the `RetryAspect` does. But retries are expensive: each one costs `deadlock_timeout` (1 s of waiting before the detector even fires) plus the cost of redoing the work. Under high load, a 10% deadlock rate can cut throughput by 80%.

The deterministic ordering fix is the single most impactful change in the whole service. By always locking the lower-ID account first (`firstId = Math.min(sourceId, destId)`), both A→B and B→A transfers serialise on the lower ID. The first transfer to acquire the lock on the lower-ID account proceeds to lock the higher-ID account; the second transfer blocks on the lower-ID account until the first commits. Deadlocks drop to zero (modulo retries from SSI aborts under `SERIALIZABLE`, which `REPEATABLE READ` does not suffer). The `RetryAspect` becomes a safety net rather than a hot path. The post-mortem ([[13.03.06. Concurrency Load Test Suite and Deadlock Analysis]]) requires you to capture the before-and-after deadlock rate to prove this.

### The idempotency-key UNIQUE constraint as last-line defence

The idempotency check in `TransferService.transfer` reads `idempotencyRepo.findById(clientSuppliedId)`, returns the prior transaction if present, otherwise inserts a new `IdempotencyKey` row at the end. This is a classic "check-then-act" pattern, and it has a TOCTOU (time-of-check-to-time-of-use) race: two concurrent requests with the same UUID both pass the check (both see "not present"), both proceed to insert, both insert their own `IdempotencyKey` row. Without the UNIQUE constraint on `idempotency_keys.key`, both would succeed and the transfer would be applied twice.

The UNIQUE constraint closes the race. The second `INSERT` fails with `DataIntegrityViolationException` (SQLSTATE 23505), which `@Transactional(rollbackFor = Exception.class)` rolls back, and the `RetryAspect` does *not* retry because it's not a serialization failure. The exception propagates to the controller, which returns 409 `IDEMPOTENCY_CONFLICT`. The first request, which committed successfully, is the one the client sees. This is the canonical example of "let the database enforce invariants the application can only check racily." The application's check is for the fast path (return the cached result without recomputing); the database's constraint is for correctness.

### `spring.jpa.open-in-view: false` and connection pool economics

Spring Boot's `OpenEntityManagerInViewFilter` (enabled by default) binds a JPA `EntityManager` to the request thread at the start of every HTTP request and unbinds it at the end. The `EntityManager` lazily acquires a JDBC `Connection` on the first query, but it does *not* release that `Connection` until the EntityManager is closed — which, with OSIV on, is after the response is written. The effect is that every request holds a connection for its full duration, including JSON serialisation, network write, and any post-response hooks. Under load, this doubles the connection hold time and halves the effective pool size: a HikariCP pool of 20 connections that should handle 1 000 RPS at 20 ms per request handles only 500 RPS at 40 ms per request (the extra 20 ms is JSON+network with the connection held).

Setting `spring.jpa.open-in-view: false` closes the EntityManager at the end of the `@Transactional` method — typically the service layer — and releases the Connection back to the pool before the controller starts serialising JSON. The pool serves 2× the throughput with the same ceiling. The cost is that lazy-loaded associations (e.g. `account.getTransactions()` if `transactions` is `@OneToMany(fetch = LAZY)`) will throw `LazyInitializationException` if accessed outside the transaction. The fix is to fetch eagerly (`@EntityGraph` or `JOIN FETCH`) at the query site, which is the correct pattern anyway — you should know up front which data your view layer needs, and your repository query should fetch exactly that.

## Cross-Ecosystem Implementation

The same concept maps differently across the four target ORMs:

| Concept | JPA / Hibernate | Django ORM | Eloquent | Prisma |
|---|---|---|---|---|
| Pattern | Data Mapper | Active Record | Active Record | Data Mapper |
| Lazy loading | Proxy objects | `select_related` needed | `load()` needed | `include` needed |
| N+1 fix | `@EntityGraph` | `select_related` | `with()` | `include` |
| Migration | Flyway / Liquibase | `makemigrations` | `migrate` | `prisma migrate` |
| Connection pool | HikariCP | Django's CONN_MAX_AGE | Laravel pool | Prisma pool |
| Pessimistic lock | `@Lock(PESSIMISTIC_WRITE)` | `select_for_update()` | `lockForUpdate()` | `SELECT ... FOR UPDATE` raw SQL |
| Optimistic lock | `@Version` column | manual `version` field | manual `version` field | not built-in |
| Transaction API | `@Transactional` annotation | `transaction.atomic()` ctx mgr | `DB::transaction()` closure | `$transaction()` callback |
| Isolation control | `@Transactional(isolation=...)` | `SET TRANSACTION ISOLATION LEVEL` raw SQL | `DB::transaction(..., isolation)` | raw SQL `SET TRANSACTION` |
| Deadlock retry | manual AOP aspect | manual decorator | manual try/catch | manual try/catch |

When you read the anchor implementation note, identify which ORM feature corresponds to each concept above. The delta notes then show how the same feature is expressed in the other ecosystems.

## Hands-On Exercise

```sql
-- See the query plan for the locked SELECT
EXPLAIN ANALYZE
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;
-- Expect: "LockRows" node above "Index Scan" — the lock is taken after the row is found.

-- Check active transactions and what they're waiting on
SELECT pid, state, wait_event_type, wait_event, query
FROM pg_stat_activity
WHERE state != 'idle';
-- wait_event_type='Lock' means the transaction is blocked on a row-level lock.

-- See who holds the lock that someone else is waiting on
SELECT
    blocked.pid     AS blocked_pid,
    blocked.query   AS blocked_query,
    blocking.pid    AS blocking_pid,
    blocking.query  AS blocking_query
FROM pg_stat_activity blocked
JOIN pg_stat_activity blocking ON blocking.pid = pg_blocking_pids(blocked.pid);

-- Force a deadlock in two psql sessions:
-- Session 1:
BEGIN;
UPDATE accounts SET balance = balance - 10 WHERE id = 1;
-- Session 2:
BEGIN;
UPDATE accounts SET balance = balance - 10 WHERE id = 2;
-- Session 1 (now blocks):
UPDATE accounts SET balance = balance + 10 WHERE id = 2;
-- Session 2 (deadlock detector fires within 1s):
UPDATE accounts SET balance = balance + 10 WHERE id = 1;
-- ERROR: deadlock detected
-- Session 2 is the victim and is rolled back; Session 1 proceeds.

-- Check table size, dead tuples, and the lock-contention metrics
SELECT relname, n_live_tup, n_dead_tup,
       seq_scan, seq_tup_read, idx_scan, idx_tup_fetch
FROM pg_stat_user_tables
WHERE relname IN ('accounts', 'entries', 'transactions');

-- Check the rate of deadlocks since last reset
SELECT deadlocks, conflicts, temp_bytes FROM pg_stat_database
WHERE datname = 'ledger';
```

## Break It

> [!danger] Load-test failure modes you must reproduce
> Do not move on to the delta translations until you have personally reproduced each of the following in your anchor implementation:
>
> 1. **Starve it.** Drop a load test (`k6 run loadtest.js --vus 500 --duration 60s`) at 10× expected throughput. Watch the HikariCP pool pin at 20/20 active and `ConnectionUnavailableException` after 1 s. Capture the metric: `hikaricp.connections.active` = 20, `hikaricp.connections.pending` > 0. Fix: raise `maximum-pool-size` to 50, or shorten the transactional section by moving the JSON serialisation outside `@Transactional`.
> 2. **Leak it.** Comment out the connection release — easiest is to set `spring.jpa.open-in-view: true` (the default) and add a 200 ms `Thread.sleep` in the JSON serialiser. Run the load test until you hit `ConnectionUnavailableException`. Capture the heap dump or the HikariCP leak log: "Apparent connection leak detected." Fix: set `open-in-view: false`, keep the `sleep` out of the transaction.
> 3. **Race it.** Remove the `@Lock(PESSIMISTIC_WRITE)` annotation from `findForUpdate`. Run 1 000 concurrent transfers from account 1 to account 2, each for 10, against a starting balance of 5 000. Expect account 1's final balance to be `-5 000` (1 000 × 10 = 10 000 debited, but balance went negative because the lost-update window let multiple transfers read the same balance). Capture the row count showing negative balance. Fix: restore the `@Lock` annotation — the `enforce_non_negative_balance` trigger will reject the updates, and the deadlock rate will be 0.
> 4. **Fix it.** Restore the lock, add the deterministic lock ordering, re-run the load test. The graph should flatten: `hikaricp.connections.active` stays around 8, `deadlocks_total` stays at 0, p99 stays under 100 ms. Keep both graphs.

## Profiling Hooks

While the load test runs, collect:

- **JVM**: `jstack <pid>` for thread dumps (look for threads in `WAITING` on `HikariPool-1` — that's pool starvation); `jmap -dump:live,format=b,file=heap.hprof <pid>` for heap dumps (look for `EntityManagerImpl` instances — if there are more than `maximumPoolSize`, OSIV is on); `jstat -gcutil <pid> 1000` for GC pressure (look for Full GC > 0 — that's a sign the L1 cache is too big).
- **OS**: `pidstat -d -r -u -w 1` (CPU, memory, disk I/O, context switches); `vmstat 1` (run queue, swap, context switches); `ss -tan state established '( sport = :5432 or dport = :5432 )' | wc -l` (active DB connections — should equal `hikaricp.connections.active`).
- **App**: `/actuator/metrics/hikaricp.connections.active`, `/actuator/metrics/hikaricp.connections.pending`, `/actuator/metrics/hikaricp.connections.timeout`, `/actuator/metrics/executor.active` (Tomcat threads), `/actuator/threaddump` (full thread dump in JSON). Add a custom Micrometer counter `ledger_transfers_deadlock_total` incremented in the `RetryAspect` — this is the metric that proves the lock-ordering fix worked.
- **Postgres**: `SELECT * FROM pg_stat_activity WHERE state != 'idle'` (active transactions); `SELECT * FROM pg_locks WHERE granted = false` (waiting locks); `SELECT * FROM pg_stat_database WHERE datname = 'ledger'` (deadlocks, conflicts, temp_bytes).

## What This Teaches

The Spring Boot anchor implementation teaches five lessons that the delta implementations will let you take for granted. **First: `@Transactional` is a proxy, not a keyword.** The annotation does nothing by itself — it's a marker that the CGLIB proxy around the bean reads, and the proxy is what begins and commits the transaction. The self-invocation trap (calling a `@Transactional` method from another method in the same bean) is the most common Spring bug in production, and it's invisible until you log `TransactionSynchronizationManager.isActualTransactionActive()` and discover it returns `false`. The delta ecosystems don't have this trap because they don't have proxy-based transactions — Prisma's `$transaction(fn)` is an explicit function call, Django's `transaction.atomic()` is an explicit context manager, Laravel's `DB::transaction(fn)` is an explicit closure. They are uglier and they are safer.

**Second: isolation level is set on the Connection, not on the query.** `@Transactional(isolation = Isolation.REPEATABLE_READ)` sets the isolation level on the JDBC `Connection` for the duration of the method, by issuing `SET TRANSACTION ISOLATION LEVEL REPEATABLE READ` after `BEGIN`. This means *every* query in the method runs at that isolation level — there's no way to mix isolation levels within one transaction. The delta ecosystems expose this differently: Prisma requires you to issue `SET TRANSACTION ISOLATION LEVEL SERIALIZABLE` as a raw SQL query inside `$transaction`, Django requires `transaction.set_isolation_level()` from `django.db.connection`, Laravel requires `DB::statement('SET TRANSACTION ISOLATION LEVEL REPEATABLE READ')`. All four are doing the same thing — the JDBC `Connection` is the actual primitive, and the frameworks are sugar over it.

**Third: pessimistic locking requires the row to exist.** `SELECT ... FOR UPDATE` only locks rows that the query returns — if the account doesn't exist, no lock is taken, and a concurrent insert (which would create the account) is not blocked. This is the "phantom insert" problem, and it's why the ledger's `accounts` table is pre-populated rather than created on demand. For a *new* account creation flow that must serialise on a name, you would need either a `UNIQUE` constraint (let the DB reject the duplicate) or `SELECT ... FOR UPDATE` on a parent row with `LOCK TABLE` as the backstop. The anchor teaches you this because JPA's `@Lock(PESSIMISTIC_WRITE)` returns `Optional.empty>` for a non-existent row, and the unwary engineer assumes the lock was taken.

**Fourth: the connection pool is the bottleneck, not the CPU.** Under the load test, the JVM is at 740% CPU (7.4 cores), Postgres is at 80% CPU, and the throughput is bounded by `maximumPoolSize / avgTransactionDurationSeconds` = 20 / 0.004 = 5 000 RPS. Adding more CPU does nothing; raising the pool size does. The delta ecosystems teach the same lesson, but Spring makes it most visible because HikariCP's metrics (`hikaricp.connections.active`, `hikaricp.connections.pending`, `hikaricp.connections.timeout`) are exposed via Micrometer out of the box. Prisma, Django, and Laravel all have equivalent metrics but you have to wire them up yourself.

**Fifth: the retry aspect must be outside the transaction aspect.** The `@Order` annotation on `RetryAspect` is the difference between a working retry and a retry that fails with `No EntityManager with actual transaction available`. Spring's aspect ordering is the most subtle part of the framework, and the deadlock-retry case is the canonical place it bites. The delta ecosystems don't have this problem because they don't have declarative transactions — the retry loop is a plain `try/catch` around an explicit `transaction.atomic()` block, and the ordering is obvious from the code structure. The anchor teaches you to think about aspect ordering; the deltas let you stop thinking about it.
