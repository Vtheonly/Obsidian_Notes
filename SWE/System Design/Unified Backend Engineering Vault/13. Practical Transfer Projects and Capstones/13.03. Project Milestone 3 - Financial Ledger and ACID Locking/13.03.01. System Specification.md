# 13.03.01. System Specification

## Project Goal

This is a capstone milestone. Unlike concept notes, the goal is to build something that runs end-to-end across multiple ecosystems and survives a load test. You are not done when the code compiles — you are done when you can show a graph of the system failing gracefully under load and recovering.

Concretely, you will build a **double-entry financial ledger**: a service that maintains account balances, accepts transfer requests between two accounts, records every movement as an immutable ledger entry, and never — under any concurrent load, any crash, any retry — allows a balance to go negative, a transfer to be applied twice, or a credit to be booked without the matching debit. This is the canonical problem that forces you to confront the database's isolation model, the connection pool's ceiling, the application's retry semantics, and the runtime's thread model — all at the same time. A TODO app hides these issues. A financial ledger exposes them on the first concurrent transfer.

The reason this milestone exists is that ACID is the most over-cited and least-understood acronym in backend engineering. Every engineer knows "Atomicity, Consistency, Isolation, Durability" as a mnemonic; almost none can tell you which isolation level their production database runs at (Postgres default = `READ COMMITTED`, MySQL/InnoDB default = `REPEATABLE READ`), which anomaly that level permits (Postgres `READ COMMITTED` permits phantom reads and lost updates in write-skew scenarios; MySQL `REPEATABLE READ` prevents phantoms via gap locks but introduces deadlock exposure), or what their ORM does when it hits a serialization failure (Hibernate throws `OptimisticLockException`, Django throws `OperationalError(40001)`, Prisma throws `PrismaClientTransactionError`, Eloquent throws `Illuminate\Database\QueryException` with SQLSTATE 40001). This milestone forces all four of those questions into the open by making them load-bearing for correctness.

## Requirements

- **Implement a high-concurrency double-entry Financial Ledger balance transfer service.** The system maintains `Account` rows with a `balance` column and a `Transaction` ledger that records every debit and credit as a pair of `Entry` rows. A transfer of 100 from account A to account B is not "update A.balance -= 100, update B.balance += 100" — it is "insert Entry(debit=A, credit=B, amount=100), insert Entry(debit=B, credit=A, amount=-100) [or split into two rows per the schema], update A.balance, update B.balance, all inside a single database transaction with `SERIALIZABLE` isolation or `REPEATABLE READ` plus `SELECT ... FOR UPDATE` row locks." The double-entry invariant — sum of all entries = 0 — must hold at all times, including mid-transfer when only one leg has been written.
- **Zero balance corruption.** Under no failure mode may an account balance diverge from the sum of its ledger entries. This means: (a) the balance update and the entry insert must be in the same transaction; (b) the transaction must roll back atomically if any step fails; (c) the database's WAL must be flushed (`synchronous_commit = on`, `wal_level = replica` minimum) before the commit returns success to the client, so a crash between commit-ack and disk-fsync cannot lose the update.
- **Absolute prevention of lost updates and double spending.** A lost update occurs when two concurrent transfers both read balance = 100, both compute new balance = 50, both write 50 — one transfer's effect is silently lost. Prevention requires either `SELECT ... FOR UPDATE` (pessimistic) or an `UPDATE ... WHERE balance >= amount` optimistic guard that rejects the update if the row was modified since the read. Double spending occurs when a transfer is retried (client timeout, then retry) and applied twice — prevention requires the client to send an idempotency key, and the server to record the key in a `transfer_id` column with a `UNIQUE` constraint, so the second attempt is rejected at insert time.
- **Deterministic pessimistic locking (`SELECT ... FOR UPDATE`).** The transfer must use `SELECT ... FOR UPDATE` on the source and destination accounts, in a deterministic order (always lock the lower account ID first), to prevent deadlocks. The lock must be held for the duration of the transaction; the transaction must be as short as possible (no external I/O, no sleep, no network call inside the locked section) to avoid lock contention starving other transfers.
- **Transaction rollback integrity.** Any exception inside the transaction — DB constraint violation, deadlock (SQLSTATE 40P01), serialization failure (SQLSTATE 40001), application-level check failure — must roll back the entire transaction, leaving no partial state. The application must not catch the exception and continue; it must propagate it, mapped to the correct HTTP status (409 for deadlock-retry, 422 for insufficient funds, 500 for unexpected).

Each requirement is non-negotiable. If you skip one, you have completed a tutorial, not a milestone. A ledger that corrupts balances under concurrency is not a ledger — it is a regression test waiting to fail in production.

## Acceptance Criteria

1. **All four target ecosystems implement the same contract.** The four implementations — Spring Boot + JPA/Hibernate (anchor, [[13.03.02. Anchor Implementation Spring Boot and PostgreSQL]]), Express + Prisma ([[13.03.03. Translation Express and Prisma]]), Django + Django ORM ([[13.03.04. Translation Django ORM]]), Laravel + Eloquent ([[13.03.05. Translation Laravel Eloquent]]) — must expose the same four HTTP endpoints with the same JSON request/response shapes and the same status codes. A `transfer.sh` script written against any one implementation must pass unchanged against the other three. This is the contract test; it is enforced by the shared Postman / k6 suite in [[13.03.06. Concurrency Load Test Suite and Deadlock Analysis]].
2. **All four pass the same automated test suite.** The suite has three layers: (a) functional tests (create account, transfer, check balance, list transactions, reject overdraft, reject non-existent account) — 24 cases; (b) concurrency tests (run 1 000 concurrent transfers between a fixed pair of accounts, assert the final balance equals the expected delta — this catches lost updates); (c) chaos tests (kill the DB mid-transfer, retry the transfer, assert no double-spend — this catches idempotency gaps). The concurrency layer must run with k6 against a single instance; the chaos layer must run with `toxiproxy` or `pumba` to inject network partitions.
3. **At least one ecosystem is load-tested to failure.** Pick one (recommended: Spring Boot, because the JVM's tuning knobs give the richest failure surface) and run a k6 ramp from 0 to 5 000 RPS over 5 minutes, holding at 5 000 for 5 minutes, then ramping to 10 000 to force a break. Capture the metric that reveals the break (HikariCP `connections.active`, p99 latency, deadlocks/sec, 5xx rate). Apply a fix (raise pool, add retry, lower isolation) and re-run. Keep both graphs. The graph is the deliverable — the code is the supporting evidence.
4. **The post-mortem note is filled in with concrete observations.** [[13.03.06. Concurrency Load Test Suite and Deadlock Analysis]] must contain: the comparison matrix (RPS, p99, deadlock rate, recovery time per ecosystem), the four reproduced failure modes with stack traces and metrics, and the three lessons learned. A post-mortem with empty cells is a failed milestone — the data is the point.

Each subfolder is independently buildable (`./mvnw spring-boot:run`, `npm start`, `python manage.py runserver`, `php artisan serve`) and independently testable. It also brings up a `k6` runner for the load test. `docker compose up` is the only command needed to reproduce the milestone.
- **A `README.md` with run instructions and a load-test screenshot.** The README must include: the four `curl` commands to exercise the contract, the k6 command to run the concurrency test, the expected output (final balance, deadlock count), and a screenshot of the Grafana dashboard showing the failure-and-recovery graph. The screenshot is required — a README without a screenshot is not a deliverable.

## Architecture Sketch

The system is a single service in front of a single Postgres instance. There is no cache (caching a balance would defeat the consistency model), no message queue (the transfer must be synchronous — the client needs to know whether it committed), and no sharding (sharding a ledger requires a two-phase commit, which is out of scope for this milestone). The simplicity is intentional: the milestone's difficulty is in the concurrency, not the topology.

### SQL schema

The schema is shared across all four ecosystem implementations. It is created by Flyway (`V1__init.sql`) in Spring, by `prisma/migrations/` in Express, by Django's `makemigrations` in Django, and by Laravel's `migrations/` in Laravel. The DDL is identical; only the migration tooling differs.

```sql
-- Account: a holder of balance. balance is in integer minor units (cents) to
-- avoid float rounding; never use NUMERIC(10,2) for money in a high-throughput
-- ledger — integer math is 10x faster and free of float artefacts.
CREATE TABLE accounts (
    id           BIGSERIAL PRIMARY KEY,
    name         TEXT NOT NULL,
    balance      BIGINT NOT NULL DEFAULT 0 CHECK (balance >= 0),
    version      BIGINT NOT NULL DEFAULT 0,   -- for optimistic-lock fallback
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Transaction: one logical transfer (a pair of entries). Has its own id which
-- also serves as the idempotency key when the client supplies one.
CREATE TABLE transactions (
    id            UUID PRIMARY KEY,           -- client-supplied idempotency key
    source_acc_id BIGINT NOT NULL REFERENCES accounts(id),
    dest_acc_id   BIGINT NOT NULL REFERENCES accounts(id),
    amount        BIGINT NOT NULL CHECK (amount > 0),
    status        TEXT NOT NULL DEFAULT 'committed'
                   CHECK (status IN ('committed', 'rolled_back')),
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Entry: one leg of a transaction. A transfer produces two entries:
--   (source_acc_id, -amount) and (dest_acc_id, +amount).
-- Sum of all entries for an account = the account's balance.
CREATE TABLE entries (
    id              BIGSERIAL PRIMARY KEY,
    transaction_id  UUID NOT NULL REFERENCES transactions(id),
    account_id      BIGINT NOT NULL REFERENCES accounts(id),
    amount          BIGINT NOT NULL,           -- negative=debit, positive=credit
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Idempotency: prevents the same client-supplied UUID from creating two
-- transactions. UNIQUE constraint does the work; the application does not need
-- to check-and-insert — it just INSERTs and lets the constraint reject dupes.
CREATE TABLE idempotency_keys (
    key             UUID PRIMARY KEY,          -- == transactions.id
    transaction_id  UUID NOT NULL REFERENCES transactions(id),
    consumed_at     TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Hot-path indexes: the transfer service does two SELECTs (lock source, lock
-- dest) and a range scan on entries by account_id. Index both.
CREATE INDEX idx_entries_account_id ON entries(account_id);
CREATE INDEX idx_entries_transaction_id ON entries(transaction_id);
CREATE INDEX idx_transactions_source ON transactions(source_acc_id);
CREATE INDEX idx_transactions_dest ON transactions(dest_acc_id);

-- Audit trigger: refuse any UPDATE to accounts that would make balance < 0.
-- This is the database's last line of defence against an application bug.
CREATE OR REPLACE FUNCTION enforce_non_negative_balance()
RETURNS TRIGGER AS $$
BEGIN
    IF NEW.balance < 0 THEN
        RAISE EXCEPTION 'balance would be negative: %', NEW.balance
            USING ERRCODE = 'check_violation';
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_balance_non_negative
    BEFORE UPDATE OF balance ON accounts
    FOR EACH ROW
    EXECUTE FUNCTION enforce_non_negative_balance();
```

## API Contract

All four implementations expose the same four endpoints. JSON is the only wire format; XML, form-encoded, and query-param-based APIs are out of scope. Status codes are conventional REST: 201 on create, 200 on read, 422 on business-rule violation (insufficient funds, non-existent account), 409 on conflict (idempotency duplicate, deadlock-retry-needed), 500 on unexpected internal error.

### `POST /accounts` — create an account

Request:
```json
{ "name": "Alice", "initial_balance": 100000 }
```
Response `201 Created`:
```json
{ "id": 1, "name": "Alice", "balance": 100000, "created_at": "2024-06-01T12:00:00Z" }
```
Response `422 Unprocessable Entity` (negative initial balance):
```json
{ "error": "initial_balance must be >= 0", "code": "INVALID_BALANCE" }
```
The `initial_balance` is in minor units (cents). The handler must validate `name` is non-empty and `initial_balance` is a non-negative integer before hitting the DB; the DB's `CHECK (balance >= 0)` is the backstop, not the primary check.

### `POST /transfers` — transfer money between two accounts

Request (with idempotency key in header):
```
POST /transfers
Idempotency-Key: 5f8e3a1e-2b4c-4d7e-9a01-2c3d4e5f6a7b
Content-Type: application/json

{
  "source_account_id": 1,
  "destination_account_id": 2,
  "amount": 5000
}
```
Response `201 Created`:
```json
{
  "id": "5f8e3a1e-2b4c-4d7e-9a01-2c3d4e5f6a7b",
  "source_account_id": 1,
  "destination_account_id": 2,
  "amount": 5000,
  "status": "committed",
  "created_at": "2024-06-01T12:00:01Z"
}
```
Response `422 Unprocessable Entity` (insufficient funds):
```json
{ "error": "insufficient funds in account 1", "code": "INSUFFICIENT_FUNDS" }
```
Response `409 Conflict` (idempotency key already used for a different request body):
```json
{ "error": "idempotency key already used for a different transfer", "code": "IDEMPOTENCY_CONFLICT" }
```
Response `409 Conflict` (deadlock — client should retry):
```json
{ "error": "deadlock detected, retry the request", "code": "DEADLOCK_RETRY" }
```

The transfer is the heart of the milestone. The handler must: (a) begin a transaction with `REPEATABLE READ` or `SERIALIZABLE` isolation; (b) `SELECT ... FOR UPDATE` on the source and destination accounts, in ascending ID order, to avoid deadlock; (c) check `source.balance >= amount`, rolling back with `INSUFFICIENT_FUNDS` if false; (d) insert the `transactions` row with the client-supplied UUID (the unique constraint on `idempotency_keys.key` will reject a replay); (e) insert two `entries` rows (debit source, credit dest); (f) update both account balances; (g) commit. On `SQLSTATE 40P01` (deadlock) or `40001` (serialization failure), retry the whole sequence up to 3 times with exponential backoff (10 ms, 30 ms, 90 ms).

### `GET /accounts/{id}/balance` — read current balance

Response `200 OK`:
```json
{ "id": 1, "balance": 95000, "version": 3, "as_of": "2024-06-01T12:00:05Z" }
```
Response `404 Not Found`:
```json
{ "error": "account 99 not found", "code": "ACCOUNT_NOT_FOUND" }
```
The `version` field is the optimistic-lock counter; it is exposed so a client can detect concurrent modifications if it caches the balance locally. The `as_of` timestamp is the moment the read was served, not the last update — this lets a client reconcile against the entries endpoint.

### `GET /accounts/{id}/transactions` — list transactions for an account

Query parameters: `limit` (default 50, max 200), `offset` (default 0), `order` (`asc` or `desc` on `created_at`, default `desc`).

Response `200 OK`:
```json
{
  "account_id": 1,
  "transactions": [
    {
      "id": "5f8e3a1e-2b4c-4d7e-9a01-2c3d4e5f6a7b",
      "amount": -5000,
      "counterparty_account_id": 2,
      "created_at": "2024-06-01T12:00:01Z"
    },
    {
      "id": "a1b2c3d4-...",
      "amount": 100000,
      "counterparty_account_id": null,
      "created_at": "2024-06-01T12:00:00Z"
    }
  ],
  "limit": 50,
  "offset": 0,
  "total": 2
}
```
The `amount` is signed from the perspective of `account_id`: negative = money left this account, positive = money arrived. The initial balance deposit appears as a transaction with `counterparty_account_id: null`. Pagination is keyset-style in production (use `WHERE created_at < ?` for the next page); offset pagination is acceptable for the milestone because the test data volume is small, but the handler must enforce `limit ≤ 200` to prevent abuse.

## Concurrency Hazards

The transfer endpoint is a concurrency hazard magnet. Five distinct anomalies can corrupt a naive implementation; each is listed below with the SQL standard name, the isolation level at which it is permitted, the reproduction recipe, and the prevention strategy. The milestone requires that *all five* are prevented — not by the application, but by the combination of isolation level, locking, and constraint that the schema and the transfer service impose.

**1. Lost update (SQL: P4 Lost Update).** Permitted under `READ UNCOMMITTED` and `READ COMMITTED`. Two transactions T1 and T2 both read account A's balance (100), both compute new balance (50), both write (50). One update is lost. Reproduction: two concurrent `POST /transfers` from A, each for 50, against a `READ COMMITTED` database with no row lock. Expected result: A.balance = 0. Actual (with lost update): A.balance = 50. Prevention: `SELECT ... FOR UPDATE` on A before reading the balance — this serialises the two transactions, so T2's read blocks until T1 commits. Alternatively, an `UPDATE accounts SET balance = balance - ? WHERE id = ? AND balance >= ?` guarded update rejects T2's update if the balance is no longer sufficient — but this loses the ledger entry, so pessimistic locking is the correct approach for a ledger.

**2. Dirty read (SQL: P1 Dirty Read).** Permitted under `READ UNCOMMITTED` only. T2 reads A's balance after T1 has written but before T1 commits; T1 then rolls back; T2 has read a value that never existed in any committed state. Reproduction: T1 starts a transfer, updates balance, then sleeps 1 s before rolling back; T2 reads balance during the sleep. Prevention: use `READ COMMITTED` or higher. Postgres default is `READ COMMITTED`, so this is prevented by default; the hazard is only relevant if you explicitly set `READ UNCOMMITTED` (which Postgres does not actually support — it maps to `READ COMMITTED`).

**3. Non-repeatable read (SQL: P2 Non-Repeatable Read).** Permitted under `READ COMMITTED`. T1 reads A's balance (100), T2 commits an update to A's balance (50), T1 re-reads A's balance and sees 50. The same query returns different results within one transaction. Reproduction: T1 `SELECT balance FROM accounts WHERE id = 1` returns 100; T2 `UPDATE accounts SET balance = 50 WHERE id = 1; COMMIT;`; T1 re-runs the SELECT, gets 50. Prevention: use `REPEATABLE READ` or higher, or `SELECT ... FOR UPDATE` which implicitly takes a row lock that blocks T2's update. For the transfer endpoint, the `FOR UPDATE` lock is the right prevention — the read and the write are in the same transaction, and the lock ensures no other transaction can modify the row in between.

**4. Phantom read (SQL: P3 Phantom Read).** Permitted under `READ COMMITTED` and `REPEATABLE READ` (in standard SQL; in Postgres, `REPEATABLE READ` actually prevents phantoms via Snapshot Isolation — Postgres's `REPEATABLE READ` is stronger than the SQL standard requires). T1 runs a range query `SELECT * FROM entries WHERE account_id = 1 AND amount > 100`; T2 inserts a new entry matching the predicate; T1 re-runs the query and sees the new row. Reproduction: T1 queries entries; T2 commits a new entry; T1 re-queries and sees the extra row. Prevention: use `SERIALIZABLE` (Postgres SSI — Serial Snapshot Isolation — detects the conflict and aborts one transaction with SQLSTATE 40001), or use `SELECT ... FOR UPDATE` with the `LIMIT` clause to lock the range. For the ledger, `SERIALIZABLE` is the safest default — the conflict rate is low enough that the abort-and-retry overhead is negligible, and SSI catches anomalies that row locking cannot.

**5. Write skew (SQL: A5A Write Skew).** Permitted under `REPEATABLE READ` (Snapshot Isolation) but not under `SERIALIZABLE`. T1 reads A and B's balances (both 100), T2 reads A and B's balances (both 100), T1 updates A's balance based on what it read (A -= 80 → A = 20), T2 updates B's balance based on what it read (B -= 80 → B = 20). Neither transaction's write conflicts with the other's read (T1 wrote A, T2 read B; T2 wrote B, T1 read A), so neither is aborted. But the combined effect — A + B went from 200 to 40, a transfer-out of 160 — may violate a business rule ("total of A + B must stay above 100"). Reproduction: a "minimum reserve" constraint across two accounts, with concurrent withdrawals. Prevention: only `SERIALIZABLE` prevents write skew; `SELECT ... FOR UPDATE` on both A and B at the start of each transaction also works, because it serialises the two transactions. The ledger milestone requires both `SELECT ... FOR UPDATE` on the two accounts *and* `SERIALIZABLE` isolation — defence in depth.

### Deadlock reproduction

A deadlock is not an anomaly in the SQL sense — it is a locking conflict. T1 locks A, then tries to lock B; T2 locks B, then tries to lock A; both block; the DB's deadlock detector picks one victim and aborts it with SQLSTATE 40P01. Reproduction: two concurrent transfers, A→B and B→A, with no deterministic lock ordering. Expected: one transfer succeeds, the other aborts with `40P01` and must be retried. Prevention: lock accounts in ascending ID order — both transfers lock the lower-ID account first, so they serialise on the lower ID and never deadlock. The milestone's transfer service must implement this ordering; the post-mortem must show a k6 run that produces 0 deadlocks under 5 000 RPS of random transfer pairs.
