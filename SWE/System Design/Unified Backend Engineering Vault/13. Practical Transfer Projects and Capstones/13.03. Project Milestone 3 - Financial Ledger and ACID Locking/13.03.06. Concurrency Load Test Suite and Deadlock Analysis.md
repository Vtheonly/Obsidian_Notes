# 13.03.06. Concurrency Load Test Suite and Deadlock Analysis

## Purpose

This file is the **test suite + post-mortem** for Milestone 3 (Financial Ledger and ACID Locking). The anchor implementation in `[[13.03.02. Anchor Implementation Spring Boot and PostgreSQL]]` builds a `POST /api/transfers` endpoint that moves money between two `accounts` rows inside a serializable transaction with row-level locks. That endpoint is only "correct" until you point a load generator at it. Under concurrency, three classes of failure become visible that are invisible at single-threaded Q=1: **(1) deadlocks** when two transfers cross paths between the same two accounts in opposite directions, **(2) lost updates** when an isolation-level downgrade or a missing `SELECT ... FOR UPDATE` lets two concurrent writers both read the same stale balance, and **(3) connection-pool starvation** when the pool size is smaller than the active transaction count and threads block on `HikariPool.getConnection()` while holding nothing.

This note contains the k6 scripts that reproduce all three failure modes, the SQL queries you run against `pg_locks` / `pg_stat_activity` to diagnose a deadlock in flight, and the metrics you must collect to argue from data rather than vibes. The delta implementations (`[[13.03.03. Translation Express and Prisma]]`, `[[13.03.04. Translation Django ORM]]`, `[[13.03.05. Translation Laravel Eloquent]]`) reuse the same k6 scripts unchanged — the test harness is ecosystem-agnostic by design, because the failure modes it exposes live in the database, not the application runtime.

The discipline this note teaches is the difference between "the test passes" and "the system is correct." A transfer endpoint that returns 200 to 100 sequential requests can still hemorrhage money at 50 concurrent users. The load test is the only artifact that catches this before production does.

## Test Scenarios

Three scenarios, each isolating one concurrency pathology. Run them in order; each one's failure mode is a prerequisite for understanding the next.

**Scenario A — Deadlock (crossed transfers).** Pick two accounts `A` and `B` with balances high enough that no transfer is rejected for insufficient funds. Fire N/2 transfers `A → B` and N/2 transfers `B → A` concurrently. If the application acquires row locks in the order it reads them, half the transactions will lock `A` first and half will lock `B` first. Two transactions going in opposite directions form a wait-for cycle: `T1` holds `A`, waits for `B`; `T2` holds `B`, waits for `A`. Postgres's deadlock detector runs every `deadlock_timeout` (default 1 second) and aborts one of them with `ERROR: deadlock detected`. The client sees a 500. The metric you want is `deadlock_count` — it should be 0 with a correct lock-ordering fix and nonzero without.

**Scenario B — Lost update (one-to-many fan-out).** Pick one source account `S` with balance `$1,000,000` and 1,000 destination accounts each starting at `$0`. Fire 1,000 concurrent transfers of `$100` from `S` to each destination. If the transaction uses `READ COMMITTED` isolation and reads the balance with a plain `SELECT` (no `FOR UPDATE`), two transactions can both read `$1,000,000`, both compute `$999,900`, and both write `$999,900` — one transfer's $100 is gone. The correct final balance of `S` is `$900,000`. If you observe anything else, you have a lost update. The metric is `final_balance_deviation_dollars` — must be exactly 0.

**Scenario C — Pool starvation (high throughput).** Fire 500 concurrent transfers against random pairs of accounts, holding the transaction open for 200 ms (simulated with `pg_sleep(0.2)` in the application code or a `before_commit` hook). If HikariCP's `maximumPoolSize` is 10, the 11th through 500th requests block on `ConnectionPoolTimeoutException` after `connectionTimeout` (default 30 s). The metric is `pool_wait_p99_ms` — it should be <50 ms at steady state and will spike to `connectionTimeout` when saturated. The fix is either to raise `maximumPoolSize`, lower `pg_sleep`, or both — but raising the pool size past `max_connections/N_app_instances` will then trip Postgres's own connection limit, so the fix must be reasoned, not just incremented.

## k6 Load Test Scripts

Install k6 (`brew install k6` on macOS, `sudo apt install k6` on Debian, or `docker pull grafana/k6`). Each scenario is a separate k6 script so you can run them independently and compare the output metrics. The scripts below all assume the application is running on `http://localhost:8080` and that `/api/accounts/seed` has populated the test data.

**Scenario A — `deadlock.js`:**

```javascript
// deadlock.js — Scenario A: crossed transfers between two accounts
import http from 'k6/http';
import { check, sleep } from 'k6';
import { Counter } from 'k6/metrics';

const deadlocks = new Counter('deadlock_count');
const rollbacks = new Counter('rollback_count');

export const options = {
  scenarios: {
    a_to_b: {
      executor: 'constant-vus', vus: 50, duration: '30s',
      env: { DIRECTION: 'A_TO_B' },
    },
    b_to_a: {
      executor: 'constant-vus', vus: 50, duration: '30s',
      env: { DIRECTION: 'B_TO_A' },
    },
  },
  thresholds: {
    // With correct lock ordering (sorted account IDs), deadlocks must be 0.
    'deadlock_count': ['count==0'],
    'http_req_failed{error:deadlock}': ['rate==0'],
    'http_req_duration{scenario:a_to_b}': ['p(99)<200'],
    'http_req_duration{scenario:b_to_a}': ['p(99)<200'],
  },
};

const A_ID = __ENV.A_ID || 1;
const B_ID = __ENV.B_ID || 2;

export default function () {
  const dir = __ENV.DIRECTION;
  const from = dir === 'A_TO_B' ? A_ID : B_ID;
  const to   = dir === 'A_TO_B' ? B_ID : A_ID;

  const payload = JSON.stringify({
    from_account_id: from,
    to_account_id: to,
    amount: '1.00',
    currency: 'USD',
    idempotency_key: `k6-${__VU}-${__ITER}-${Date.now()}`,
  });

  const res = http.post('http://localhost:8080/api/transfers',
    payload,
    { headers: { 'Content-Type': 'application/json' } });

  const isDeadlock = res.status === 500 &&
    res.json('error')?.toLowerCase().includes('deadlock');

  if (isDeadlock) {
    deadlocks.add(1);
    rollbacks.add(1);
  }

  check(res, {
    'status 200 or 409 (idempotent replay)': r =>
      r.status === 200 || r.status === 409,
    'no deadlock leaked to client': r => !isDeadlock,
  });

  sleep(0.01); // 100 req/s per VU
}
```

**Scenario B — `lost_update.js`:**

```javascript
// lost_update.js — Scenario B: one-to-many fan-out from a single source
import http from 'k6/http';
import { check, group } from 'k6';
import { Counter, Trend } from 'k6/metrics';

const balanceDeviations = new Trend('final_balance_deviation_dollars');
const lostUpdates = new Counter('lost_update_count');

export const options = {
  scenarios: {
    fanout: {
      executor: 'per-vu-iterations', vus: 1000, iterations: 1,
      maxDuration: '60s',
    },
  },
  thresholds: {
    'lost_update_count': ['count==0'],
    'final_balance_deviation_dollars': ['value==0'],
  },
};

const SOURCE_ID = __ENV.SOURCE_ID || 1;
const START_BALANCE = 1_000_000_00; // cents
const TRANSFER_CENTS = 100_00;

export default function () {
  const destId = 1000 + (__VU % 1000); // destinations 1000..1999

  const res = http.post('http://localhost:8080/api/transfers',
    JSON.stringify({
      from_account_id: SOURCE_ID,
      to_account_id: destId,
      amount: `${TRANSFER_CENTS / 100}.00`,
      currency: 'USD',
      idempotency_key: `fanout-${__VU}`,
    }),
    { headers: { 'Content-Type': 'application/json' } });

  check(res, { 'transfer succeeded': r => r.status === 200 });
}

export function teardown() {
  // After all 1000 transfers, fetch source balance and compare to expected.
  const expected = START_BALANCE - (1000 * TRANSFER_CENTS);
  const res = http.get(`http://localhost:8080/api/accounts/${SOURCE_ID}`);
  const actual = Math.round(res.json('balance_cents'));
  const deviation = Math.abs(actual - expected);

  balanceDeviations.add(deviation / 100);
  if (deviation !== 0) lostUpdates.add(deviation / TRANSFER_CENTS);

  console.log(`Expected=${expected/100} Actual=${actual/100} Deviation=$${deviation/100}`);
}
```

**Scenario C — `pool_starvation.js`:**

```javascript
// pool_starvation.js — Scenario C: pool exhaustion under latency inflation
import http from 'k6/http';
import { check, sleep } from 'k6';
import { Counter, Trend } from 'k6/metrics';

const poolWaits = new Trend('pool_wait_ms');
const poolTimeouts = new Counter('pool_timeout_count');

export const options = {
  stages: [
    { duration: '10s', target: 50 },
    { duration: '20s', target: 200 },
    { duration: '20s', target: 500 },   // exceeds typical pool size of 10-50
    { duration: '10s', target: 500 },
    { duration: '10s', target: 0 },
  ],
  thresholds: {
    'pool_timeout_count': ['count<10'],
    'pool_wait_ms': ['p(99)<5000'],
    'http_req_failed{error:pool_timeout}': ['rate<0.01'],
  },
};

export default function () {
  const t0 = Date.now();
  const res = http.post('http://localhost:8080/api/transfers?simulate_latency_ms=200',
    JSON.stringify({
      from_account_id: 1 + (__VU % 100),
      to_account_id:   100 + (__VU % 100),
      amount: '1.00',
      currency: 'USD',
      idempotency_key: `starvation-${__VU}-${__ITER}`,
    }),
    { headers: { 'Content-Type': 'application/json' },
      responseType: 'text' });

  poolWaits.add(Date.now() - t0);

  const body = res.body ? res.body.toString() : '';
  const isPoolTimeout = body.includes('ConnectionPoolTimeoutException') ||
                        body.includes('HikariPool-1 - Connection is not available');

  if (isPoolTimeout) {
    poolTimeouts.add(1);
    check(res, { 'pool exhausted (expected at >pool_size VUs)': () => true });
  } else {
    check(res, { 'status 200 or 409': r => r.status === 200 || r.status === 409 });
  }
}
```

Run all three with `k6 run deadlock.js`, `k6 run lost_update.js`, `k6 run pool_starvation.js`. Pipe the JSON output to `k6 run --out json=results.json` for post-mortem analysis. The threshold blocks deliberately fail the run when a pathology is observed — CI should treat a green k6 run as proof the system is concurrency-safe, not just that it returned 200s.

## Deadlock Reproduction

To reproduce a deadlock deterministically (not just probabilistically under load), use the following `psql` recipe with two open sessions against the same Postgres database. This is the canonical two-transaction deadlock and is what Scenario A produces at scale.

```sql
-- Session 1                          -- Session 2
BEGIN ISOLATION LEVEL SERIALIZABLE;   BEGIN ISOLATION LEVEL SERIALIZABLE;
UPDATE accounts
   SET balance = balance - 100
 WHERE id = 1;                        -- holds lock on account 1
                                      UPDATE accounts
                                         SET balance = balance - 100
                                       WHERE id = 2;  -- holds lock on account 2
UPDATE accounts
   SET balance = balance + 100
 WHERE id = 2;                        -- BLOCKS, waiting for Session 2's lock
                                      UPDATE accounts
                                         SET balance = balance + 100
                                       WHERE id = 1;  -- BLOCKS, waiting for Session 1's lock
                                      -- ERROR:  deadlock detected
                                      -- DETAIL:  Process waits for ShareLock on
                                      -- transaction; blocked by process.
                                      -- HINT:  See server log for query details.
```

The Postgres deadlock detector is a background process that wakes every `deadlock_timeout` (default 1000 ms). When it finds a wait-for cycle in the lock graph, it picks a victim (the transaction that has done the least work, by XID ordering) and aborts it with SQLSTATE `40P01`. The victim's client sees a 500; the surviving transaction proceeds. The fix in the application is **deterministic lock ordering**: always lock the lower `account_id` first, then the higher. With that ordering, two crossed transfers both lock `account_id=1` first — one of them wins, the other waits, no cycle ever forms.

The application-level fix in the Spring Boot anchor is a one-line change in `TransferService.execute`:

```java
// BEFORE (deadlock-prone — locks in caller-specified order):
Account from = accountRepo.findByIdForUpdate(req.fromAccountId());
Account to   = accountRepo.findByIdForUpdate(req.toAccountId());

// AFTER (deadlock-free — locks in canonical order):
long lo = Math.min(req.fromAccountId(), req.toAccountId());
long hi = Math.max(req.fromAccountId(), req.toAccountId());
Account firstLocked = accountRepo.findByIdForUpdate(lo);
Account secondLocked = accountRepo.findByIdForUpdate(hi);
Account from = req.fromAccountId() == lo ? firstLocked : secondLocked;
Account to   = req.toAccountId()   == lo ? firstLocked : secondLocked;
```

## Deadlock Analysis SQL

When a deadlock has happened (or while one is brewing), the following queries against `pg_locks`, `pg_stat_activity`, and `pg_stat_database` are the diagnostic toolkit. Run them from a fourth `psql` session while the load test is in flight.

**Who is waiting on what right now?**

```sql
-- blocked.sql — find every blocked transaction and its blocker
SELECT
    blocked.pid     AS blocked_pid,
    blocked.query   AS blocked_query,
    blocking.pid    AS blocking_pid,
    blocking.query  AS blocking_query,
    blocked.xact_start,
    now() - blocked.xact_start AS blocked_for
FROM pg_stat_activity blocked
JOIN pg_stat_activity blocking
  ON blocking.pid = ANY (
    SELECT unnest(pg_blocking_pids(blocked.pid))
  )
WHERE blocked.wait_event_type = 'Lock';
```

The `pg_blocking_pids(pid)` function (Postgres 9.6+) returns the array of PIDs holding a lock that the given PID is waiting on. The join above turns this into a flat `blocker → blocked` table. A wait-for cycle of length ≥2 in this output is a deadlock in progress that the detector has not yet aborted.

**What locks does each transaction hold?**

```sql
-- locks.sql — full lock table with relation names
SELECT
    pid,
    locktype,
    relation::regclass AS table_name,
    mode,              -- RowExclusiveLock, ShareLock, RowShareLock, ...
    granted,           -- true = holder, false = waiter
    transactionid,
    virtualxid,
    virtualtransaction
FROM pg_locks
WHERE locktype = 'relation'
   OR locktype = 'transactionid'
ORDER BY relation::regclass, granted DESC, pid;
```

For a transfer transaction you expect to see `RowExclusiveLock` on `accounts` (granted) and a waiting `ShareLock` on the other transaction's `transactionid` (not granted). The `transactionid` lock is how Postgres serializes writes that depend on a not-yet-committed other transaction — it's the canonical signature of a write-write conflict.

**Deadlock counts at the database level:**

```sql
-- deadlocks.sql — cumulative deadlock count since DB start
SELECT datname, deadlocks, conflicts, xact_commit, xact_rollback
FROM pg_stat_database
WHERE datname = 'ledger';
```

`deadlocks` is a monotonically increasing counter; snapshot before and after a load test run to compute the delta. `xact_rollback` should equal `deadlocks` plus any explicit `ROLLBACK` issued by application retry logic; if `xact_rollback - deadlocks` is large, you have a retry storm (the app is treating transient errors as fatal).

**Live long-running transactions (the ones most likely to deadlock):**

```sql
-- long_txns.sql — transactions open longer than 5 seconds
SELECT pid, xact_start, now() - xact_start AS duration,
       state, wait_event_type, wait_event,
       left(query, 80) AS query_preview
FROM pg_stat_activity
WHERE state != 'idle'
  AND now() - xact_start > interval '5 seconds'
ORDER BY xact_start;
```

A transfer that takes >5 seconds is almost certainly stuck on a lock. In production this query is your first response to a "transfers are slow" alert — the slow part is rarely the SQL itself; it's the wait for some other transaction to commit.

## Metrics Collected

The k6 output and the Postgres `pg_stat_*` counters give you eight metrics that together fully characterize the system's concurrency behavior. Capture them all into a single Grafana dashboard per load-test run; the post-mortem in `[[13.04.06. Failure Injection and Rebalance Resilience Verification]]` (different milestone, same dashboard layout) uses the same panel structure.

| Metric | Source | Healthy | Unhealthy | Action if unhealthy |
| --- | --- | --- | --- | --- |
| `http_reqs` (TPS) | k6 | ≥ target | < target | Investigate pool starvation |
| `http_req_duration{p(99)}` | k6 | < 200 ms | > 1 s | Lock wait or pool wait |
| `deadlock_count` | k6 + `pg_stat_database.deadlocks` | 0 | >0 | Fix lock ordering |
| `xact_rollback` | `pg_stat_database` | = deadlocks | >> deadlocks | Retry storm, fix retry logic |
| `final_balance_deviation_dollars` | k6 teardown | $0 | ≠ $0 | Lost update, raise isolation |
| `pool_wait_p99_ms` | k6 trend | < 50 ms | > 1 s | Raise pool size or lower txn latency |
| `pool_timeout_count` | k6 counter | 0 | >0 | Pool saturated, raise `maximumPoolSize` |
| `active_connections` | `pg_stat_activity` | ≤ pool×N | at `max_connections` | Pool too big or app instances too many |

The single most revealing chart is `http_req_duration{p(99)}` overlaid with `deadlock_count` and `active_connections`. When `p(99)` spikes and `active_connections` is at `max_connections` but `deadlock_count` is zero, you have pool saturation. When `p(99)` spikes and `deadlock_count` rises with it, you have lock contention. When `p(99)` is flat but `final_balance_deviation_dollars` is nonzero, you have a silent lost-update bug that no latency alert will ever catch — only an end-of-run invariant check will. This is why Scenario B's `teardown()` is non-negotiable: a load test that does not check post-run invariants is theater.

## Failure Modes Observed

The three scenarios produce three distinct failure signatures. Memorize them — they are the load-test fingerprints you will see in every ACID system, regardless of ecosystem.

**Signature 1: Deadlock storm.** Symptom: `deadlock_count` rises linearly with concurrency; `p(99)` is bimodal (either fast or 1 s = `deadlock_timeout`); `xact_rollback` ≈ `deadlocks`. Cause: lock ordering depends on caller input. Fix: canonical lock ordering by sorted primary key. The fix is mechanical — one `Math.min/max` — and once applied, `deadlock_count` drops to exactly 0 across all concurrency levels. This is the cleanest possible load-test result: a binary signal that flips when the fix lands.

**Signature 2: Silent lost update.** Symptom: `final_balance_deviation_dollars > 0`; all HTTP responses are 200; no errors in logs; no deadlocks; `p(99)` is fine. Cause: `READ COMMITTED` isolation with a plain `SELECT` followed by an `UPDATE balance = ?` (write-the-whole-value, not `UPDATE balance = balance - ?`). Two concurrent transactions both read `$1,000,000`, both compute `$999,900`, both write `$999,900`; the second transaction's `$100` debit never happened. Fix: either use `SELECT ... FOR UPDATE` (pessimistic) or `UPDATE accounts SET balance = balance - ? WHERE id = ? AND balance >= ?` (optimistic with a check clause) or raise the isolation level to `SERIALIZABLE` and retry on `40001 serialization_failure`. This is the most dangerous failure mode because no alert fires — only an invariant check after the load test catches it.

**Signature 3: Pool starvation.** Symptom: `pool_timeout_count` rises above 0 once concurrency exceeds `maximumPoolSize × (1 / txn_latency_seconds)`; `p(99)` = `connectionTimeout` (30 s default); `active_connections` pinned at `max_connections`; `http_reqs` plateaus. Cause: the application holds a DB connection for the full transaction duration including non-DB work (HTTP calls, sleeps, slow compute). Fix: do all non-DB work before opening the transaction (move the `@Transactional` annotation down the call stack to wrap only the SQL writes) or raise `maximumPoolSize` — but never past `max_connections / app_instance_count` or you'll trip Postgres's own limit and produce a worse failure (Postgres refuses new connections with `FATAL: too many connections`). The reasoning is: the right pool size is `target_TPS × average_txn_seconds`, not "as big as possible."

A fourth signature worth knowing, though it appears only when Scenario C is run at extreme concurrency against a misconfigured Postgres, is `LockAcquisitionException` with `wait_event_type = 'Lock'` and `wait_event = 'transactionid'` on every transaction. This is not a pool problem — it is lock contention on a single hot row (e.g., a "system account" that every transfer touches). The fix is to remove the hot row: shard it, batch updates to it asynchronously, or move it out of the transactional path entirely. This is the same pathology as a single Redis key becoming the throughput ceiling, and the remedy is the same: spread the writes.

## What This Suite Does Not Cover

This load test exercises the database layer's concurrency guarantees. It does not exercise: idempotency under network retries (covered by replaying the same `idempotency_key` in Scenario A and asserting a 409), replication lag (covered by reading from a replica immediately after a write and asserting staleness), or partial-failure recovery (covered by killing the app process mid-transaction and verifying the database rolled back). Those are separate test suites for separate failure modes — see the sibling milestone `[[13.04. Project Milestone 4 - Event-Driven Order Pipeline with Kafka]]` for the message-delivery equivalents (at-least-once, exactly-once, consumer-group rebalance).

The discipline this note enforces is that **a load test is only as good as the invariants it checks after the run**. Throughput and latency numbers without a balance check are a vanity metric. The `teardown()` function in `lost_update.js` is the most important 15 lines in this file.
