# 13.03.03. Translation Express and Prisma

## Scope

This is a single-ecosystem implementation file inside a capstone milestone. It is a reference implementation to reproduce, not a tutorial to copy.

The reference anchor is [[13.03.02. Anchor Implementation Spring Boot and PostgreSQL]]. Read that first. This note shows the same financial ledger expressed in Express 4 + Prisma 5 against the same Postgres 16 schema, with the same four endpoints, the same pessimistic-locking transfer service, and the same deadlock-retry semantics. The delta from the anchor is small in *what it does* (identical SQL hits the wire) and large in *how the developer expresses it* (Prisma's `$transaction` callback versus Spring's `@Transactional` annotation; raw `$queryRaw` for `SELECT ... FOR UPDATE` versus JPA's `@Lock(PESSIMISTIC_WRITE)`).

The point of the delta pass is to see what the anchor's abstractions were hiding. Prisma hides the JDBC `Connection` entirely — you never touch one. It hides the `EntityManager` flush cycle — Prisma's client flushes each operation eagerly. It hides the proxy-based transaction — `$transaction(async (tx) => {...})` is a plain JavaScript closure. And it hides the deadlock-retry mechanism — there is no built-in equivalent, you write the retry loop by hand. Each of these "hidings" is a place where Prisma is simpler than Spring, and a place where you must re-learn what Spring was doing for you.

## What You Are Building

A single-file (plus Prisma schema) Express 4 service that exposes the same four endpoints as the Spring Boot anchor: `POST /accounts`, `POST /transfers`, `GET /accounts/:id/balance`, `GET /accounts/:id/transactions`. The service uses Prisma 5 as the ORM, runs on Node 20, and connects to the same Postgres 16 instance as the anchor. The transfer endpoint uses `prisma.$transaction(async (tx) => {...}, { isolationLevel: 'RepeatableRead' })`, issues `$queryRaw` `SELECT ... FOR UPDATE` calls to lock the source and destination accounts in ascending ID order, and is wrapped in a hand-written retry loop that catches Prisma's `PrismaClientTransactionError` for SQLSTATE 40P01 (deadlock) and 40001 (serialization failure).

```prisma
generator client {
  provider = "prisma-client-js"

datasource db {
  provider = "postgresql"
  url      = env("DATABASE_URL")
}

model Account {
  id         BigInt   @id @default(autoincrement())
  name       String
  balance    BigInt   @default(0)
  version    BigInt   @default(0)
  createdAt  DateTime @default(now()) @map("created_at")

  @@map("accounts")
}

model LedgerTransaction {
  id              String   @id @db.Uuid
  sourceAccountId BigInt   @map("source_acc_id")
  destAccountId   BigInt   @map("dest_acc_id")
  amount          BigInt
  status          String   @default("committed")
  createdAt       DateTime @default(now()) @map("created_at")

  @@map("transactions")
}

model Entry {
  id             BigInt   @id @default(autoincrement())
  transactionId  String   @map("transaction_id") @db.Uuid
  accountId      BigInt   @map("account_id")
  amount         BigInt
  createdAt      DateTime @default(now()) @map("created_at")

  @@index([accountId])
  @@index([transactionId])
  @@map("entries")
}

model IdempotencyKey {
  key            String   @id @db.Uuid
  transactionId  String   @map("transaction_id") @db.Uuid
  consumedAt     DateTime @default(now()) @map("consumed_at")

  @@map("idempotency_keys")
}
```

```typescript
// src/service/retry.ts
import { Prisma } from "@prisma/client";

// Prisma's transaction errors carry the SQLSTATE code. P2034 = transaction
// failed due to a write conflict or deadlock (covers 40001 and 40P01).
const RETRIABLE = [Prisma.TransactionRolledBackError, "P2034"];

export async function withRetry<T>(
  fn: () => Promise<T>,
  maxAttempts = 3,
  backoffMs: number[] = [10, 30, 90]
): Promise<T> {
  let attempt = 0;
  // eslint-disable-next-line no-constant-condition
  while (true) {
    try {
      return await fn();
    } catch (err: any) {
      const isRetriable =
        RETRIABLE.some((cls) => err instanceof cls) ||
        (err?.code && RETRIABLE.includes(err.code));
      if (!isRetriable || ++attempt >= maxAttempts) throw err;
      await new Promise((r) => setTimeout(r, backoffMs[attempt - 1]));
    }
  }
}
```

```typescript
// src/service/transferService.ts
import { Prisma, PrismaClient } from "@prisma/client";
import { withRetry } from "./retry";
import { IdempotencyConflictError, InsufficientFundsError,
         AccountNotFoundError } from "../middleware/error";

// Prisma does not have a built-in SELECT ... FOR UPDATE primitive. We drop to
// raw SQL via $queryRaw, which returns plain JS objects (not typed models).
// The row type after the lock:
type AccountRow = {
  id: bigint;
  name: string;
  balance: bigint;
  version: bigint;
};

export async function transfer(
  prisma: PrismaClient,
  sourceId: bigint,
  destId: bigint,
  amount: bigint,
  idempotencyKey: string
): Promise<{ id: string; status: string }> {

  // The retry wraps the whole $transaction. Each retry starts a fresh
  // transaction — there is no "resume" semantics. The idempotency-key
  // UNIQUE constraint means a retry that overlaps with a committed prior
  // attempt will see the existing transaction and return it (handled below).
  return withRetry(async () => {
    return prisma.$transaction(
      async (tx) => {
        // 1. Idempotency check. Runs inside the transaction so the insert
        //    and the key record commit atomically.
        const existing = await tx.idempotencyKey.findUnique({
          where: { key: idempotencyKey },
          include: { transaction: true } as any, // relation not declared in schema; use raw
        });
        // Prisma doesn't know the relation; do a separate query:
        const existingKey = await tx.$queryRaw`
          SELECT t.id, t.source_acc_id, t.dest_acc_id, t.amount, t.status
          FROM idempotency_keys k
          JOIN transactions t ON t.id = k.transaction_id
          WHERE k.key = ${idempotencyKey}::uuid
          LIMIT 1
        ` as any[];
        if (existingKey.length > 0) {
          const prior = existingKey[0];
          // Caller (route handler) compares prior's source/dest/amount to
          // the request and throws IdempotencyConflictError on mismatch.
          return {
            id: prior.id,
            status: prior.status,
            source: prior.source_acc_id,
            dest: prior.dest_acc_id,
            amount: prior.amount,
          };
        }

        // 2. Lock accounts in ASCENDING ID ORDER. This is the same
        //    deterministic ordering rule as the Spring anchor. $queryRaw
        //    parameterises via tagged-template literals — safe from SQL
        //    injection because Prisma escapes ${firstId} as a bind parameter.
        const firstId  = sourceId < destId ? sourceId : destId;
        const secondId = sourceId < destId ? destId  : sourceId;

        const firstRows = await tx.$queryRaw<AccountRow[]>`
          SELECT id, name, balance, version
          FROM accounts WHERE id = ${firstId} FOR UPDATE
        `;
        const secondRows = await tx.$queryRaw<AccountRow[]>`
          SELECT id, name, balance, version
          FROM accounts WHERE id = ${secondId} FOR UPDATE
        `;
        if (firstRows.length === 0)  throw new AccountNotFoundError(firstId);
        if (secondRows.length === 0) throw new AccountNotFoundError(secondId);

        const source = (sourceId === firstId ? firstRows[0]   : secondRows[0]);
        const dest   = (destId   === firstId ? firstRows[0]   : secondRows[0]);

        // 3. Business rule: source.balance >= amount. BigInt math, no float.
        if (source.balance < amount) {
          throw new InsufficientFundsError(sourceId, source.balance, amount);
        }

        // 4. Mutate balances via raw SQL. Prisma's update() would also work,
        //    but raw SQL lets us add the optimistic-lock WHERE clause:
        //    UPDATE ... WHERE id = ? AND version = ?. If 0 rows affected,
        //    another tx committed first and we should retry.
        const newSourceBalance = source.balance - amount;
        const newDestBalance   = dest.balance   + amount;
        const updated = await tx.$executeRaw`
          UPDATE accounts
          SET balance = ${newSourceBalance}, version = version + 1
          WHERE id = ${sourceId} AND version = ${source.version}
        `;
        if (updated === 0) {
          // Optimistic lock failure — force a retry by throwing.
          throw new Prisma.PrismaClientUnknownRequestError(
            "optimistic lock conflict",
            { clientVersion: "5.x", code: "P2034" } as any
          );
        }
        await tx.$executeRaw`
          UPDATE accounts
          SET balance = ${newDestBalance}, version = version + 1
          WHERE id = ${destId} AND version = ${dest.version}
        `;

        // 5. Insert the transaction row + the two entry rows.
        await tx.$executeRaw`
          INSERT INTO transactions (id, source_acc_id, dest_acc_id, amount, status, created_at)
          VALUES (${idempotencyKey}::uuid, ${sourceId}, ${destId}, ${amount},
                  'committed', now())
        `;
        await tx.$executeRaw`
          INSERT INTO entries (transaction_id, account_id, amount, created_at)
          VALUES
            (${idempotencyKey}::uuid, ${sourceId}, ${-amount}, now()),
            (${idempotencyKey}::uuid, ${destId},   ${amount}, now())
        `;

        // 6. Idempotency record. The UNIQUE constraint on idempotency_keys.key
        //    is the last-line defence against a TOCTOU race between two
        //    concurrent requests with the same UUID. Prisma will throw
        //    PrismaClientKnownRequestError with code P2002 (unique constraint
        //    violation) — the caller's error middleware maps P2002 to 409.
        await tx.$executeRaw`
          INSERT INTO idempotency_keys (key, transaction_id, consumed_at)
          VALUES (${idempotencyKey}::uuid, ${idempotencyKey}::uuid, now())
        `;

        return {
          id: idempotencyKey,
          status: "committed",
          source: sourceId,
          dest: destId,
          amount,
        };
      },
      {
        isolationLevel: Prisma.TransactionIsolationLevel.RepeatableRead,
        timeout: 5000,   // ms; Prisma rolls back if the callback doesn't finish
      }
    );
  });
}
```

### Route handlers and error middleware

```typescript
// src/routes/transfers.ts
import { Router } from "express";
import { prisma } from "../lib/prisma";
import { transfer } from "../service/transferService";
import { IdempotencyConflictError, ApiError } from "../middleware/error";

const router = Router();

router.post("/", async (req, res, next) => {
  try {
    const idempotencyKey = req.header("Idempotency-Key");
    if (!idempotencyKey) throw new ApiError(400, "MISSING_IDEMPOTENCY_KEY",
      "Idempotency-Key header is required");

    const { source_account_id, destination_account_id, amount } = req.body;
    if (!source_account_id || !destination_account_id || !amount) {
      throw new ApiError(400, "INVALID_REQUEST", "missing fields");
    }
    if (amount <= 0) {
      throw new ApiError(422, "INVALID_AMOUNT", "amount must be > 0");
    }

    const result = await transfer(
      prisma,
      BigInt(source_account_id),
      BigInt(destination_account_id),
      BigInt(amount),
      idempotencyKey
    );

    // Idempotency collision: same UUID, different body.
    if (result.source !== BigInt(source_account_id)
        || result.dest !== BigInt(destination_account_id)
        || result.amount !== BigInt(amount)) {
      throw new IdempotencyConflictError(idempotencyKey);
    }

    res.status(201).json({
      id: result.id,
      source_account_id: source_account_id,
      destination_account_id: destination_account_id,
      amount: amount,
      status: result.status,
    });
  } catch (err) {
    next(err);
  }
});

export default router;
```

```typescript
// src/middleware/error.ts
import { Request, Response, NextFunction } from "express";
import { Prisma } from "@prisma/client";

export class ApiError extends Error {
  constructor(public status: number, public code: string, msg: string) {
    super(msg);
  }
}
export class AccountNotFoundError extends ApiError {
  constructor(id: bigint) { super(404, "ACCOUNT_NOT_FOUND", `account ${id} not found`); }
}
export class InsufficientFundsError extends ApiError {
  constructor(id: bigint, bal: bigint, amt: bigint) {
    super(422, "INSUFFICIENT_FUNDS",
      `insufficient funds in account ${id}: balance=${bal}, requested=${amt}`);
  }
}
export class IdempotencyConflictError extends ApiError {
  constructor(key: string) { super(409, "IDEMPOTENCY_CONFLICT",
    `idempotency key ${key} already used for a different transfer`); }
}

export function errorHandler(err: Error, _req: Request, res: Response, _next: NextFunction) {
  if (err instanceof ApiError) {
    return res.status(err.status).json({ error: err.message, code: err.code });
  }
  // Prisma's P2002 = unique constraint violation (the idempotency-key race).
  if (err instanceof Prisma.PrismaClientKnownRequestError && err.code === "P2002") {
    return res.status(409).json({
      error: "idempotency key already used for a different transfer",
      code: "IDEMPOTENCY_CONFLICT",
    });
  }
  // Prisma's P2034 = transaction conflict (deadlock or serialization failure
  // that escaped the retry loop). Tell the client to retry.
  if (err instanceof Prisma.PrismaClientKnownRequestError && err.code === "P2034") {
    return res.status(409).json({
      error: "deadlock detected, retry the request",
      code: "DEADLOCK_RETRY",
    });
  }
  console.error("unexpected error", err);
  res.status(500).json({ error: "internal server error", code: "INTERNAL" });
}
```

### What is automatic here that was manual in the anchor

Prisma generates the entire client from the `schema.prisma` file. There is no `Account.java` entity to write, no `AccountRepository` interface to declare, no `EntityManager` to inject. The Prisma client (`prisma.account.findUnique(...)`, `prisma.entry.create(...)`) is a fully-typed JavaScript object whose methods are inferred from the schema. The cost is one `prisma generate` step at build time and one `prisma migrate dev` step when the schema changes; the benefit is that the schema, the TypeScript types, and the runtime client can never drift apart — they are all derived from one source of truth.

Prisma's `$transaction(async (tx) => {...})` callback is the equivalent of Spring's `@Transactional`. The `tx` object is a Prisma client scoped to the transaction — every operation on it runs in the same database transaction, and the transaction commits when the callback resolves (or rolls back when it throws). There is no proxy, no self-invocation trap, no `@Order` to worry about — the transaction is a literal JavaScript closure, and the ordering is obvious from the lexical structure of the code. The isolation level is set via the `isolationLevel` option on `$transaction`, which issues `SET TRANSACTION ISOLATION LEVEL REPEATABLE READ` after `BEGIN`. This is the same SQL the JDBC `Connection` would issue; Prisma just hides it.

### What is manual here that was automatic in the anchor

**Deadlock retry.** Spring's `RetryAspect` is one AOP annotation; Prisma has no equivalent, so the `withRetry` wrapper is hand-written. It is short (~20 lines), but it must be applied to every transactional method that touches contended rows. A team that forgets to wrap one of those methods will see deadlocks surface as 500 errors instead of 409-with-retry. The lesson: in Spring, the retry is part of the framework; in Prisma, the retry is part of the application code, and the codebase must enforce its use.

**Pessimistic locking.** Prisma does not have a `selectForUpdate()` method on its client. The `FOR UPDATE` clause must be issued via `$queryRaw`, which returns plain JavaScript objects (not typed models) and bypasses Prisma's type inference. The cost is that the locked `Account` is a `{ id: bigint, name: string, balance: bigint, version: bigint }` object, not a Prisma `Account` model, so subsequent code can't use Prisma's type-safe accessors. The benefit is that the raw SQL is exactly what hits the wire — there's no abstraction layer to debug through when something goes wrong. For a financial ledger where the locking semantics are the whole point, the raw SQL is arguably clearer than JPA's `@Lock(PESSIMISTIC_WRITE)` annotation.

**Optimistic locking.** Prisma does not have a `@Version` annotation. The `version` column exists in the schema, but Prisma will not automatically increment it or check it in `UPDATE` statements. The application must manually add `WHERE version = ${prior.version}` to the `UPDATE` and check that the affected-rows count is non-zero — which is what the `updated === 0` check in the transfer service does. This is more verbose than Hibernate's `@Version` but more transparent: the engineer can see exactly what the SQL is doing, and there's no surprise `ObjectOptimisticLockingFailureException` to handle.

**Idempotency-key relation.** Prisma's schema does not declare the relation between `IdempotencyKey.transactionId` and `LedgerTransaction.id` (it would normally be `transactionId  LedgerTransaction @relation(fields: [transactionId], references: [id])`). The relation is omitted deliberately to keep the schema simple and to show the raw-SQL approach — in a real codebase you would declare it and use `include: { transaction: true }` for the idempotency check.

## Implementation Steps

1. **Bootstrap.** Run `npm init -y`, then `npm install express @prisma/client helmet pino zod`, then `npm install -D prisma typescript @types/express tsx`. Initialise the Prisma schema with `npx prisma init`. Set `DATABASE_URL=postgresql://ledger:ledger@localhost:5432/ledger` in `.env`.
2. **Wire dependencies.** Copy the Prisma schema from above into `prisma/schema.prisma`. Add the CHECK constraint and trigger to the generated migration SQL by hand (`prisma migrate dev --create-only`, edit the file, then `prisma migrate dev`). Run `npx prisma generate` to produce the typed client.
3. **Implement the contract.** Create `src/lib/prisma.ts`, `src/service/retry.ts`, `src/service/transferService.ts`, `src/routes/accounts.ts`, `src/routes/transfers.ts`, `src/middleware/error.ts`, `src/server.ts` per the code above. Run `npx tsx src/server.ts` and verify `curl localhost:8080/health` returns `{"status":"ok"}`.
4. **Wire observability.** The `pino-http` middleware logs every request with a `req.id` (use `asyncLocalStorage` to propagate a `trace_id` header if you want cross-service tracing). For Prometheus metrics, add `prom-client` and expose `/metrics` — the must-have counter is `ledger_transfers_deadlock_total`, incremented in the `withRetry` catch block. A gauge `ledger_db_connections_active` is the early-warning metric for pool saturation; Prisma does not expose pool metrics natively, so instrument it via a wrapper.
5. **Containerise.** Write a multi-stage Dockerfile: stage 1 (`node:20-alpine`) installs deps and runs `npx prisma generate`; stage 2 copies the built `dist/` and `node_modules/` into a slim `node:20-alpine` image. Final image size ~110 MB.
6. **Test.** Write integration tests with `supertest` + `@testcontainers/postgresql`. The concurrency test uses `Promise.all(Array.from({length:1000}, () => supertest(app).post("/transfers")...))` and asserts the final balance equals the expected delta. The chaos test uses `toxiproxy` to kill the DB connection mid-transfer and verifies the idempotency-key constraint prevents a double-application on retry.

## What This Teaches

The Express + Prisma implementation teaches four lessons that complement the Spring anchor. **First: schema-as-source-of-truth is a real productivity win.** Prisma's `schema.prisma` is the only place the data model lives — the TypeScript types, the runtime client, and the migration SQL are all derived from it. Spring's JPA entities, by contrast, are written by hand and must be kept in sync with the Flyway migration SQL by convention. In a team of 10 engineers, the Prisma approach saves real time (no entity/migration drift bugs) at the cost of one limitation (no CHECK constraints or triggers in the schema — those go in hand-edited migration SQL). For a financial ledger where the schema is the contract, the schema-as-source-of-truth approach is the right trade.

**Second: `$transaction` callback is the right level of abstraction.** Prisma's `prisma.$transaction(async (tx) => {...})` is a plain JavaScript closure. There is no proxy, no self-invocation trap, no `@Order` to worry about. The transaction begins when the callback starts and commits when it resolves — this is exactly what `@Transactional` does, but without the indirection. The cost is that the callback must be passed the `tx` object explicitly (you can't just call `prisma.account.update` inside the callback and expect it to be in the transaction — you must call `tx.account.update`). The benefit is that the lexical scope of the transaction is visible in the code, which makes the "is this in a transaction?" question trivially answerable. Spring engineers who move to Prisma often report that they finally understood what `@Transactional` was doing, because Prisma makes the mechanism visible.

**Third: raw SQL is not a failure of the ORM — it's a feature.** The transfer service uses `$queryRaw` for `SELECT ... FOR UPDATE`, `UPDATE ... WHERE version = ?`, and the `INSERT INTO idempotency_keys` with the `::uuid` cast. These are raw SQL because Prisma does not have a typed API for them. In Spring, the equivalent operations would be `@Lock(PESSIMISTIC_WRITE)`, `@Version`, and `JpaRepository.save()` — all typed, all elegant. But the typed APIs hide the SQL, and when the SQL matters (as it does for a ledger), the hiding is a cost. The Prisma engineer who writes `$queryRaw` knows exactly what SQL is hitting the wire, can `EXPLAIN ANALYZE` it directly, and can tune it without fighting the ORM. The lesson: an ORM that lets you drop to raw SQL when you need to is more useful than one that tries to abstract the SQL away entirely.

**Fourth: the retry loop is the application's responsibility.** Spring's `RetryAspect` is one annotation; Prisma's `withRetry` is a hand-written wrapper. The wrapper is short, but it must be applied to every transactional method that touches contended rows — and the codebase must enforce this. A team that forgets to wrap one method will see deadlocks surface as 500 errors instead of 409-with-retry. The lesson: in a system where the framework does not provide the retry, the application must have a lint rule or a code-review checklist that verifies the wrapper is applied. The `withRetry` function should be the only way to call `prisma.$transaction` in the codebase — wrap it, ban direct calls, and the discipline is enforced by the type system.
