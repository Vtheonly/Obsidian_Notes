# 13.03.04. Translation Django ORM

## Scope

This is a single-ecosystem implementation file inside a capstone milestone. It is a reference implementation to reproduce, not a tutorial to copy.

The reference anchor is [[13.03.02. Anchor Implementation Spring Boot and PostgreSQL]]. Read that first. This note shows the same financial ledger expressed in Django 4.2 + Django ORM against the same Postgres 16 schema, with the same four endpoints, the same pessimistic-locking transfer service, and the same deadlock-retry semantics. The delta from the anchor is small in *what it does* (identical SQL hits the wire) and large in *how the developer expresses it* (Django's `transaction.atomic()` context manager versus Spring's `@Transactional` annotation; `select_for_update()` on a `QuerySet` versus JPA's `@Lock(PESSIMISTIC_WRITE)`; Python's `try/except OperationalError as e: if e.code == '40p01': retry` versus Spring's AOP aspect).

The point of the delta pass is to see what the anchor's abstractions were hiding. Django hides the JDBC `Connection` behind a per-thread `django.db.connection` proxy. It hides the `EntityManager` flush cycle — Django ORM flushes each `save()` immediately (no dirty checking, no batch-at-commit). It hides the proxy-based transaction — `transaction.atomic()` is a context manager that issues `BEGIN`/`COMMIT`/`ROLLBACK` directly. And it hides the deadlock-retry mechanism — there is no built-in equivalent, you write the retry loop by hand. Each of these "hidings" is a place where Django is more transparent than Spring, and a place where you must think about what Spring was doing for you.

## What You Are Building

A Django 4.2 project (`ledger_django/`) with one app (`ledger/`) that exposes the same four endpoints as the Spring Boot anchor: `POST /accounts`, `POST /transfers`, `GET /accounts/:id/balance`, `GET /accounts/:id/transactions`. The service uses Django ORM with `select_for_update()` for pessimistic row locks, runs under `gunicorn --workers=4 --worker-class=sync` on Python 3.12, and connects to the same Postgres 16 instance as the anchor. The transfer endpoint is wrapped in `transaction.atomic()` using a `postgreSQL.REPEATABLE READ` isolation level set via `connection.set_isolation_level()` (Django does not expose isolation-level control on `atomic()` directly — you must set it on the connection before entering the atomic block), and the whole thing is wrapped in a hand-written `retry_on_deadlock` decorator that catches `OperationalError` with `pgcode == '40p01'` (deadlock) or `pgcode == '40001'` (serialization failure) and re-invokes up to 3 times with exponential backoff.

```python
# ledger/models.py
import uuid
from django.db import models
from django.utils import timezone


class Account(models.Model):
    name = models.TextField()
    # BigIntegerField maps to BIGINT in Postgres. Never use FloatField or
    # DecimalField for money in a high-throughput ledger — DecimalField
    # allocates a Python decimal.Decimal per read, which is 20× slower than
    # int math and produces ~150 MB/hour of garbage at 5k RPS.
    balance = models.BigIntegerField(default=0)
    version = models.BigIntegerField(default=0)
    created_at = models.DateTimeField(default=timezone.now)

    class Meta:
        db_table = "accounts"
        # Django's CheckConstraint replicates the DB-level CHECK. The DB
        # constraint (added in the migration's RunSQL) is the real backstop;
        # this is for the test framework's schema validation.
        constraints = [
            models.CheckConstraint(
                check=models.Q(balance__gte=0),
                name="balance_non_negative",
            ),
        ]

    def __str__(self) -> str:
        return f"Account(id={self.id}, name={self.name!r}, balance={self.balance})"


class LedgerTransaction(models.Model):
    # UUIDField with primary_key=True makes this the PK. The client supplies
    # the UUID via the Idempotency-Key header; we use it directly as the row's
    # primary key, so the UNIQUE constraint on idempotency_keys.key and the
    # PK on transactions.id together enforce the idempotency invariant.
    id = models.UUIDField(primary_key=True, default=uuid.uuid4, editable=False)
    source_account = models.ForeignKey(
        Account, on_delete=models.PROTECT, related_name="transactions_as_source",
        db_column="source_acc_id",
    )
    destination_account = models.ForeignKey(
        Account, on_delete=models.PROTECT, related_name="transactions_as_dest",
        db_column="dest_acc_id",
    )
    amount = models.BigIntegerField()
    status = models.TextField(default="committed")
    created_at = models.DateTimeField(default=timezone.now)

    class Meta:
        db_table = "transactions"


class Entry(models.Model):
    transaction = models.ForeignKey(
        LedgerTransaction, on_delete=models.CASCADE,
        related_name="entries", db_column="transaction_id",
    )
    account = models.ForeignKey(
        Account, on_delete=models.CASCADE,
        related_name="entries", db_column="account_id",
    )
    amount = models.BigIntegerField()  # signed: negative = debit, positive = credit
    created_at = models.DateTimeField(default=timezone.now)

    class Meta:
        db_table = "entries"
        indexes = [
            models.Index(fields=["account"], name="idx_entries_account_id"),
            models.Index(fields=["transaction"], name="idx_entries_transaction_id"),
        ]


class IdempotencyKey(models.Model):
    key = models.UUIDField(primary_key=True, editable=False)
    transaction = models.ForeignKey(
        LedgerTransaction, on_delete=models.PROTECT, db_column="transaction_id",
    )
    consumed_at = models.DateTimeField(default=timezone.now)

    class Meta:
        db_table = "idempotency_keys"
```

### Migration with raw SQL for trigger

Django's migration framework cannot express CHECK constraints that fire on UPDATE only, nor triggers. The migration uses `RunSQL` to add them after `CreateModel` builds the base tables.

```python
# ledger/migrations/0001_initial.py
from django.db import migrations, models
import django.utils.timezone


class Migration(migrations.Migration):
    initial = True
    dependencies = []

    operations = [
        migrations.CreateModel(name="Account", fields=[...]),
        migrations.CreateModel(name="LedgerTransaction", fields=[...]),
        migrations.CreateModel(name="Entry", fields=[...]),
        migrations.CreateModel(name="IdempotencyKey", fields=[...]),
        # The CHECK constraint Django generates is column-level (balance >= 0
        # at INSERT). Add the trigger that fires on UPDATE too:
        migrations.RunSQL(
            sql="""
                CREATE OR REPLACE FUNCTION enforce_non_negative_balance()
                RETURNS TRIGGER AS $$
                BEGIN
                    IF NEW.balance < 0 THEN
                        RAISE EXCEPTION 'balance would be negative: %',
                            NEW.balance USING ERRCODE = 'check_violation';
                    END IF;
                    RETURN NEW;
                END;
                $$ LANGUAGE plpgsql;

                CREATE TRIGGER trg_balance_non_negative
                    BEFORE UPDATE OF balance ON accounts
                    FOR EACH ROW
                    EXECUTE FUNCTION enforce_non_negative_balance();

                CREATE INDEX IF NOT EXISTS idx_transactions_source
                    ON transactions(source_acc_id);
                CREATE INDEX IF NOT EXISTS idx_transactions_dest
                    ON transactions(dest_acc_id);
            """,
            reverse_sql="""
                DROP TRIGGER IF EXISTS trg_balance_non_negative ON accounts;
                DROP FUNCTION IF EXISTS enforce_non_negative_balance();
                DROP INDEX IF EXISTS idx_transactions_source;
                DROP INDEX IF EXISTS idx_transactions_dest;
            """,
        ),
    ]
```

### Retry decorator + transfer service

```python
# ledger/services/retry.py
import functools
import logging
import time
from django.db import OperationalError, transaction

log = logging.getLogger(__name__)

# Postgres pgcodes for retriable errors. These come from psycopg / psycopg2
# as e.__cause__.pgcode or as the django.db.utils wrapper's .pgcode attribute.
DEADLOCK_PGCODE = "40P01"      # deadlock_detected
SERIALIZATION_PGCODE = "40001" # serialization_failure


def retry_on_deadlock(max_attempts: int = 3, backoff_ms=(10, 30, 90)):
    """Decorator that retries the wrapped function on Postgres deadlock (40P01)
    or serialization failure (40001). The function must be idempotent within
    a single retry (i.e. either it commits fully or it rolls back fully and
    a re-run produces the same outcome). For the transfer service this holds
    because the idempotency-key UNIQUE constraint rejects duplicate inserts."""
    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            attempt = 0
            while True:
                try:
                    return func(*args, **kwargs)
                except OperationalError as e:
                    pgcode = getattr(getattr(e, "pgcode", None), "__str__",
                                     lambda: None)()
                    if pgcode is None and e.__cause__ is not None:
                        pgcode = getattr(e.__cause__, "pgcode", None)
                    if pgcode not in (DEADLOCK_PGCODE, SERIALIZATION_PGCODE):
                        raise
                    attempt += 1
                    if attempt >= max_attempts:
                        log.warning(
                            "transfer retried %d times, giving up: %s",
                            attempt, e,
                        )
                        raise
                    log.info(
                        "deadlock/serialization on attempt %d, retrying in %dms",
                        attempt, backoff_ms[attempt - 1],
                    )
                    time.sleep(backoff_ms[attempt - 1] / 1000.0)
        return wrapper
    return decorator
```

```python
# ledger/services/transfer_service.py
from django.db import transaction, connection, IntegrityError
from django.utils import timezone
from psycopg2.extensions import ISOLATION_LEVEL_REPEATABLE_READ

from ledger.models import Account, LedgerTransaction, Entry, IdempotencyKey
from ledger.exceptions import (
    AccountNotFoundError, InsufficientFundsError, IdempotencyConflictError,
)
from ledger.services.retry import retry_on_deadlock


@retry_on_deadlock()
def transfer(source_id: int, dest_id: int, amount: int,
             idempotency_key: str) -> LedgerTransaction:
    """Transfers `amount` minor units from source to dest. Uses
    transaction.atomic() for the transaction boundary and select_for_update()
    for pessimistic row locks. Isolation level is set to REPEATABLE READ
    (Postgres Snapshot Isolation) on the connection before the atomic block.

    Note: the @retry_on_deadlock decorator wraps the whole function, so each
    retry starts a fresh atomic block. The idempotency-key UNIQUE constraint
    ensures that if a prior attempt actually committed before the deadlock
    detector reported the abort (rare but possible), the retry will hit the
    unique constraint and be mapped to IdempotencyConflictError."""

    # Django does not expose isolation level on atomic(). Set it on the
    # connection before entering the atomic block. The connection's
    # isolation level is reset to its default (READ COMMITTED) at the end of
    # the request by Django's request-finished signal, OR by the next call
    # to connection.set_isolation_level().
    connection.set_isolation_level(ISOLATION_LEVEL_REPEATABLE_READ)

    try:
        with transaction.atomic():
            # 1. Idempotency check inside the transaction. If the key exists,
            #    return the prior transaction (the route will compare fields
            #    and raise IdempotencyConflictError on mismatch).
            try:
                prior_key = IdempotencyKey.objects.select_related("transaction").get(
                    key=idempotency_key
                )
                return prior_key.transaction
            except IdempotencyKey.DoesNotExist:
                pass  # first time we've seen this UUID — proceed

            # 2. Lock accounts in ASCENDING ID ORDER. This is the deterministic
            #    lock-ordering rule: both A→B and B→A transfers will lock
            #    min(A,B) first, serialising on the lower ID.
            first_id, second_id = sorted([source_id, dest_id])

            # select_for_update() issues SELECT ... FOR UPDATE. The of=()
            # parameter is omitted because we're locking the rows we selected,
            # which is the default behaviour. skip_locked=False (default) so
            # concurrent transfers block instead of skipping.
            try:
                first = Account.objects.select_for_update().get(id=first_id)
            except Account.DoesNotExist:
                raise AccountNotFoundError(first_id)
            try:
                second = Account.objects.select_for_update().get(id=second_id)
            except Account.DoesNotExist:
                raise AccountNotFoundError(second_id)

            source = first if source_id == first_id else second
            dest = second if source_id == first_id else first

            # 3. Business rule: source.balance >= amount.
            if source.balance < amount:
                raise InsufficientFundsError(source.id, source.balance, amount)

            # 4. Mutate balances. Django ORM flushes each save() immediately —
            #    no dirty-checking, no batch-at-commit. The UPDATE is issued
            #    right here, holding the row lock. We add an optimistic-lock
            #    WHERE clause by filtering on version:
            updated = Account.objects.filter(
                id=source.id, version=source.version,
            ).update(
                balance=source.balance - amount,
                version=source.version + 1,
            )
            if updated == 0:
                # Optimistic-lock failure: another tx committed first. Force
                # a retry by raising OperationalError with a synthetic pgcode.
                # In practice this should not happen under SELECT FOR UPDATE,
                # because the lock prevents the concurrent update — but it's
                # a safety net for code paths that bypass select_for_update.
                raise OperationalError("optimistic lock conflict on source account")
            Account.objects.filter(
                id=dest.id, version=dest.version,
            ).update(
                balance=dest.balance + amount,
                version=dest.version + 1,
            )

            # 5. Insert the transaction and the two entry rows. Django ORM's
            #    save() issues INSERT immediately. The transaction's UUID PK
            #    is the idempotency_key passed in.
            tx = LedgerTransaction.objects.create(
                id=idempotency_key,
                source_account=source,
                destination_account=dest,
                amount=amount,
                status="committed",
            )
            Entry.objects.create(
                transaction=tx, account=source, amount=-amount,
            )
            Entry.objects.create(
                transaction=tx, account=dest, amount=amount,
            )

            # 6. Idempotency record. The UNIQUE constraint on
            #    idempotency_keys.key is the last-line defence: if two
            #    concurrent requests with the same UUID both pass step 1
            #    (both see DoesNotExist), one will fail at this insert with
            #    IntegrityError, which atomic() rolls back cleanly.
            try:
                IdempotencyKey.objects.create(
                    key=idempotency_key, transaction=tx,
                )
            except IntegrityError:
                # The other concurrent request won. Roll back our transaction
                # and re-raise as IdempotencyConflictError so the caller maps
                # it to 409 instead of 500.
                raise IdempotencyConflictError(idempotency_key)

            return tx
    finally:
        # Reset the connection's isolation level to the default (READ COMMITTED)
        # so the next query on this connection runs at the expected level. The
        # Django connection is per-thread and is reused for the next request,
        # so failing to reset would leak REPEATABLE READ into unrelated queries.
        connection.set_isolation_level(
            ISOLATION_LEVEL_READ_COMMITTED
        )
```

```python
# ledger/views.py
import uuid
from django.http import JsonResponse, HttpRequest
from django.views.decorators.http import require_http_methods
from django.views.decorators.csrf import csrf_exempt

from ledger.services.transfer_service import transfer
from ledger.exceptions import (
    AccountNotFoundError, InsufficientFundsError, IdempotencyConflictError,
    ApiError,
)
from ledger.models import Account, Entry
import json


@csrf_exempt
@require_http_methods(["POST"])
def create_account(request: HttpRequest):
    body = json.loads(request.body)
    name = body.get("name")
    initial_balance = int(body.get("initial_balance", 0))
    if not name:
        return JsonResponse({"error": "name is required", "code": "INVALID_REQUEST"},
                            status=422)
    if initial_balance < 0:
        return JsonResponse({"error": "initial_balance must be >= 0",
                             "code": "INVALID_BALANCE"}, status=422)
    account = Account.objects.create(name=name, balance=initial_balance)
    return JsonResponse({
        "id": account.id, "name": account.name, "balance": account.balance,
        "created_at": account.created_at.isoformat(),
    }, status=201)


@csrf_exempt
@require_http_methods(["POST"])
def create_transfer(request: HttpRequest):
    idempotency_key = request.headers.get("Idempotency-Key")
    if not idempotency_key:
        return JsonResponse({"error": "Idempotency-Key header is required",
                             "code": "MISSING_IDEMPOTENCY_KEY"}, status=400)
    try:
        key_uuid = uuid.UUID(idempotency_key)
    except ValueError:
        return JsonResponse({"error": "Idempotency-Key must be a UUID",
                             "code": "INVALID_IDEMPOTENCY_KEY"}, status=400)

    body = json.loads(request.body)
    source_id = int(body["source_account_id"])
    dest_id = int(body["destination_account_id"])
    amount = int(body["amount"])

    tx = transfer(source_id, dest_id, amount, key_uuid)

    # Idempotency collision: same UUID, different body.
    if (tx.source_account_id != source_id
            or tx.destination_account_id != dest_id
            or tx.amount != amount):
        raise IdempotencyConflictError(idempotency_key)

    return JsonResponse({
        "id": str(tx.id),
        "source_account_id": tx.source_account_id,
        "destination_account_id": tx.destination_account_id,
        "amount": tx.amount,
        "status": tx.status,
        "created_at": tx.created_at.isoformat(),
    }, status=201)


@require_http_methods(["GET"])
def get_balance(request: HttpRequest, account_id: int):
    try:
        account = Account.objects.get(id=account_id)
    except Account.DoesNotExist:
        raise AccountNotFoundError(account_id)
    return JsonResponse({
        "id": account.id, "balance": account.balance,
        "version": account.version, "as_of": account.created_at.isoformat(),
    })


@require_http_methods(["GET"])
def list_transactions(request: HttpRequest, account_id: int):
    try:
        Account.objects.get(id=account_id)
    except Account.DoesNotExist:
        raise AccountNotFoundError(account_id)
    limit = min(int(request.GET.get("limit", 50)), 200)
    offset = int(request.GET.get("offset", 0))
    entries = Entry.objects.filter(account_id=account_id).select_related(
        "transaction"
    ).order_by("-created_at")[offset:offset + limit]
    return JsonResponse({
        "account_id": account_id,
        "transactions": [
            {
                "id": str(e.transaction_id),
                "amount": e.amount,
                "counterparty_account_id": (
                    e.transaction.destination_account_id
                    if e.transaction.source_account_id == account_id
                    else e.transaction.source_account_id
                ),
                "created_at": e.created_at.isoformat(),
            }
            for e in entries
        ],
        "limit": limit, "offset": offset,
    })
```

```python
# ledger/middleware.py
import logging
from django.http import JsonResponse
from django.db import OperationalError
from ledger.exceptions import ApiError, IdempotencyConflictError

log = logging.getLogger(__name__)


class ExceptionMiddleware:
    """Catches ApiError subclasses and maps them to JSON responses. Catches
    OperationalError (which escapes the retry decorator after MAX_ATTEMPTS)
    and maps it to 409 DEADLOCK_RETRY so the client knows to retry."""
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        return self.get_response(request)

    def process_exception(self, request, exception):
        if isinstance(exception, IdempotencyConflictError):
            return JsonResponse(
                {"error": exception.message, "code": exception.code},
                status=exception.status,
            )
        if isinstance(exception, ApiError):
            return JsonResponse(
                {"error": exception.message, "code": exception.code},
                status=exception.status,
            )
        if isinstance(exception, OperationalError):
            # Check if it's a deadlock that escaped the retry loop.
            pgcode = getattr(getattr(exception, "pgcode", None), "__str__",
                             lambda: None)()
            if pgcode in ("40P01", "40001"):
                return JsonResponse(
                    {"error": "deadlock detected, retry the request",
                     "code": "DEADLOCK_RETRY"},
                    status=409,
                )
        log.exception("unexpected error: %s", exception)
        return JsonResponse(
            {"error": "internal server error", "code": "INTERNAL"},
            status=500,
        )
```

### What is automatic here that was manual in the anchor

Django's ORM is an Active Record — `Account.objects.create(name=...)` both inserts the row and returns a model instance, with no separate repository interface. The `select_for_update()` method on `QuerySet` is the equivalent of JPA's `@Lock(PESSIMISTIC_WRITE)` but expressed as a fluent method chain rather than an annotation. There is no proxy, no `EntityManager`, no flush-at-commit: each `save()` issues its `INSERT` or `UPDATE` immediately, holding the row lock for the duration of the atomic block. This is more transparent than JPA (you can see exactly when each SQL statement fires) but less efficient (no batch flush, no dirty-checking).

Django's `transaction.atomic()` context manager is the equivalent of Spring's `@Transactional`. It issues `BEGIN` on enter and `COMMIT` on clean exit (or `ROLLBACK` on exception). There is no proxy, no self-invocation trap — `atomic()` is a Python context manager, and the transaction boundary is the lexical scope of the `with` block. The isolation level is *not* exposed on `atomic()` — you must set it on `connection.set_isolation_level()` before entering the block. This is a real API gap: in Spring, `@Transactional(isolation = Isolation.REPEATABLE_READ)` is one line; in Django, it's three (set isolation, atomic block, reset isolation in finally).

### What is manual here that was automatic in the anchor

**Deadlock retry.** Django has no equivalent of Spring's `RetryAspect`. The `retry_on_deadlock` decorator is hand-written and must be applied to every transactional service method. The decorator inspects the exception's `pgcode` (which Django surfaces via `OperationalError.__cause__.pgcode` when psycopg2 is the driver) and retries on `40P01` and `40001`. The decorator pattern is cleaner than Spring's AOP (no proxy, no `@Order`), but it is also more fragile — a developer who forgets to apply the decorator gets 500 errors instead of retries, with no compile-time warning.

**Optimistic locking.** Django ORM does not have a `@Version` column. The `version` field exists in the model, but `Account.objects.update()` does not automatically check or increment it. The application must explicitly add `version=source.version` to the `filter()` clause and `version=source.version + 1` to the `update()` call, then check the return value (number of rows affected). The Spring equivalent — `@Version private Long version;` — does this transparently. The Django approach is more verbose but more transparent.

**Isolation level.** Django does not expose isolation-level control on `atomic()`. The application must call `connection.set_isolation_level(ISOLATION_LEVEL_REPEATABLE_READ)` before the atomic block and reset it in a `finally`. The reset is critical because Django's connections are per-thread and reused across requests — failing to reset leaks `REPEATABLE READ` into unrelated queries on subsequent requests, which can cause subtle bugs (a `GET /accounts/:id/balance` running at `REPEATABLE READ` will return a stale balance if a previous request on the same thread opened a transaction that has not yet been committed). This is the kind of footgun Spring's `@Transactional(isolation=...)` is designed to prevent.

## Implementation Steps

1. **Bootstrap.** Run `django-admin startproject ledger_django`, then `python manage.py startapp ledger`. Install dependencies: `pip install django==4.2.* psycopg[binary] gunicorn`. Add `ledger` to `INSTALLED_APPS` in `settings.py`.
2. **Wire dependencies.** Copy the models into `ledger/models.py`. Run `python manage.py makemigrations` to generate `0001_initial.py`, then hand-edit it to add the `RunSQL` operation for the trigger and the extra indexes. Run `python manage.py migrate` against the Postgres 16 instance.
3. **Implement the contract.** Create `ledger/services/transfer_service.py`, `ledger/services/retry.py`, `ledger/views.py`, `ledger/exceptions.py`, `ledger/middleware.py` per the code above. Wire the URLs in `ledger_django/urls.py`. Run `python manage.py runserver 8080` and verify `curl localhost:8080/health` (add a `/health` view) returns `{"status":"ok"}`.
4. **Wire observability.** Add `django-structlog` for structured logging with `trace_id` propagation. Add `django-prometheus` for metrics — the must-have counter is `ledger_transfers_deadlock_total`, incremented in the `retry_on_deadlock` decorator's catch block. The connection-pool gauge is harder in Django (there's no HikariCP-equivalent metrics surface); instrument it via a custom middleware that reads `connection.connection` and exposes `pg_stat_activity` counts.
5. **Containerise.** Write a multi-stage Dockerfile: stage 1 (`python:3.12-slim`) installs deps with `pip install --user -r requirements.txt`; stage 2 copies the app and the installed deps into a slim `python:3.12-slim` image. Final image size ~140 MB. Use `gunicorn --workers=4 --worker-class=sync --timeout=30 --bind=0.0.0.0:8080 ledger_django.wsgi:application` as the CMD.
6. **Test.** Write integration tests with `pytest-django` + `pytest-postgresql` (or `@testcontainers/postgresql`). The concurrency test uses `concurrent.futures.ThreadPoolExecutor(max_workers=50)` to fire 1 000 transfers in parallel and asserts the final balance equals the expected delta. The chaos test uses `toxiproxy` to kill the DB connection mid-transfer and verifies the idempotency-key constraint prevents a double-application on retry.

## What This Teaches

The Django implementation teaches four lessons that complement the Spring anchor. **First: Active Record is more transparent but less efficient than Data Mapper.** Django's `Account.objects.create(...)` and `account.save()` issue SQL immediately — there is no dirty checking, no batch-at-commit, no `EntityManager` flush cycle. This means you can `print(connection.queries)` and see exactly what SQL fired, in what order, when — which is invaluable for debugging. The cost is that a loop of 1 000 `save()` calls issues 1 000 `INSERT` statements, where Hibernate would batch them into one. For a ledger where each transfer does exactly two `INSERT`s, the difference is negligible; for a bulk-import path, the Django engineer must reach for `bulk_create()` explicitly.

**Second: `transaction.atomic()` is the right primitive, but isolation level is a second-class citizen.** Django's `atomic()` is a clean context manager — no proxy, no self-invocation trap, no `@Order` to worry about. The transaction boundary is the lexical scope of the `with` block, and the commit/rollback semantics are obvious. But the isolation level is *not* exposed on `atomic()` — you must call `connection.set_isolation_level()` before the block and reset it in a `finally`. This API gap is a real footgun: a developer who sets `REPEATABLE READ` and forgets to reset it leaks the isolation level into the next request on the same thread, which can cause subtle correctness bugs (a `GET /balance` returning a stale snapshot). The lesson: in Django, the discipline of "always reset isolation in finally" must be enforced by code review, because the framework will not catch the omission.

**Third: `select_for_update()` is the most ergonomic pessimistic-lock API of the four ecosystems.** Django's `Account.objects.select_for_update().get(id=...)` reads as English: "select this account for update." Compare to Prisma's `$queryRaw\`SELECT ... FOR UPDATE\``, which is raw SQL with no type safety, or Spring's `@Lock(LockModeType.PESSIMISTIC_WRITE)` annotation on a repository method, which is one layer of indirection removed from the call site. Django's API is the cleanest of the four. The `of=()` parameter (lock only the rows from specified tables) and `skip_locked=True` (return immediately if locked) are optional parameters that cover the common variations. The lesson: when a framework makes the right thing easy and the wrong thing hard, the codebase trends toward correctness; Django's `select_for_update()` is a good example.

**Fourth: the retry decorator is a Python idiom that fits the language.** Django's `@retry_on_deadlock()` decorator is a Python decorator — a higher-order function that wraps the original. This is the same mechanism Django uses for `@login_required`, `@csrf_exempt`, `@require_http_methods`. The retry decorator fits the language's idiom; it doesn't feel like a foreign concept grafted on (the way Spring's AOP aspect can feel in a Java codebase that doesn't use AOP elsewhere). The cost is that the retry must be applied to every method that needs it — there's no global "retry all transactional methods" switch. The lesson: in a Python codebase, the decorator pattern is the natural way to add cross-cutting concerns, and the codebase should standardise on a small set of well-tested decorators (`@retry_on_deadlock`, `@cache_result`, `@audit_log`) rather than reaching for a general-purpose AOP framework.
