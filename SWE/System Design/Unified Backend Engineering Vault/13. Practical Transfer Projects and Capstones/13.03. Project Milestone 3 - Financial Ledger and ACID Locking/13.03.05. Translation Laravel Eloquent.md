# 13.03.05. Translation Laravel Eloquent

## Scope

This is a single-ecosystem implementation file inside a capstone milestone. It is a reference implementation to reproduce, not a tutorial to copy.

The reference anchor is [[13.03.02. Anchor Implementation Spring Boot and PostgreSQL]]. Read that first. This note shows the same financial ledger expressed in Laravel 10 + Eloquent ORM against the same Postgres 16 schema, with the same four endpoints, the same pessimistic-locking transfer service, and the same deadlock-retry semantics. The delta from the anchor is small in *what it does* (identical SQL hits the wire) and large in *how the developer expresses it* (Laravel's `DB::transaction(function () {...})` closure versus Spring's `@Transactional` annotation; `lockForUpdate()` on an Eloquent query builder versus JPA's `@Lock(PESSIMISTIC_WRITE)`; PHP's `try/catch (QueryException $e)` with `SQLSTATE` inspection versus Spring's AOP aspect).

The point of the delta pass is to see what the anchor's abstractions were hiding. Laravel hides the PDO `PDO` instance behind a `DB` facade with connection-pool management. It hides the ORM persistence cycle — Eloquent, like Django, flushes each `save()` immediately (no dirty checking, no batch-at-commit). It hides the proxy-based transaction — `DB::transaction()` is a closure that issues `BEGIN`/`COMMIT`/`ROLLBACK` directly. And it includes a *built-in* retry mechanism: `DB::transaction(fn, $attempts = 1)` accepts an `$attempts` parameter that retries on deadlock — a feature no other ecosystem in this milestone provides out of the box. Each of these design choices is a place where Laravel is more opinionated than Spring, and a place where the developer trades explicit control for framework convenience.

## What You Are Building

A Laravel 10 project (`ledger-laravel/`) with one controller (`TransferController`) that exposes the same four endpoints as the Spring Boot anchor: `POST /accounts`, `POST /transfers`, `GET /accounts/:id/balance`, `GET /accounts/:id/transactions`. The service uses Eloquent ORM with `lockForUpdate()` for pessimistic row locks, runs on PHP 8.3 with FrankenPHP as the SAPI (the modern Laravel default, replacing php-fpm + nginx), and connects to the same Postgres 16 instance as the anchor. The transfer endpoint is wrapped in `DB::transaction(function () use (...) {...}, config('ledger.deadlock_retries', 3))` — Laravel's built-in retry, which catches `Connection` / `QueryException` with `SQLSTATE 40P01` (deadlock) and `40001` (serialization failure) and re-executes the closure up to `$attempts` times. The isolation level is set to `REPEATABLE READ` via a raw `DB::statement('SET TRANSACTION ISOLATION LEVEL REPEATABLE READ')` issued inside the closure, before any `SELECT` — Laravel does not expose isolation-level control on `DB::transaction()` natively.

### TransferService — the heart of the milestone

```php
<?php
// app/Services/TransferService.php
namespace App\Services;

use App\Models\{Account, LedgerTransaction, Entry, IdempotencyKey};
use App\Exceptions\{
    AccountNotFoundException, InsufficientFundsException,
    IdempotencyConflictException
};
use Illuminate\Support\Facades\DB;
use Illuminate\Database\QueryException;
use Illuminate\Database\Connection;

class TransferService
{
    /**
     * Transfers $amount minor units from $sourceId to $destId.
     *
     * Uses DB::transaction() with a retry count of 3. Laravel's built-in
     * retry catches QueryException with SQLSTATE 40P01 (deadlock) and 40001
     * (serialization) and re-executes the closure. This is the only ecosystem
     * in this milestone that ships with built-in retry — no hand-written
     * decorator or aspect is required.
     *
     * Isolation level: REPEATABLE READ (Postgres Snapshot Isolation). Set via
     * DB::statement('SET TRANSACTION ISOLATION LEVEL REPEATABLE READ') inside
     * the closure, before any SELECT. The statement is scoped to the current
     * transaction and is reset automatically when the transaction commits.
     */
    public function transfer(
        int $sourceId,
        int $destId,
        int $amount,
        string $idempotencyKey
    ): LedgerTransaction {
        // DB::transaction's third argument is the number of attempts. Laravel
        // retries on deadlock/serialization automatically; we pass 3 to match
        // the Spring and Django implementations.
        return DB::transaction(function (Connection $conn) use (
            $sourceId, $destId, $amount, $idempotencyKey
        ): LedgerTransaction {
            // Set isolation level inside the transaction. SET TRANSACTION
            // ISOLATION LEVEL must be issued before any query in the tx.
            $conn->statement('SET TRANSACTION ISOLATION LEVEL REPEATABLE READ');

            // 1. Idempotency check inside the transaction.
            $priorKey = IdempotencyKey::where('key', $idempotencyKey)
                ->with('transaction')
                ->first();
            if ($priorKey !== null) {
                // Caller (controller) compares fields and throws
                // IdempotencyConflictException on mismatch.
                return $priorKey->transaction;
            }

            // 2. Lock accounts in ASCENDING ID ORDER. lockForUpdate() adds
            //    "FOR UPDATE" to the generated SQL. The sharedLock() method
            //    would add "FOR SHARE" instead (read lock).
            $firstId  = min($sourceId, $destId);
            $secondId = max($sourceId, $destId);

            $first  = Account::where('id', $firstId)->lockForUpdate()->first();
            if ($first === null) {
                throw new AccountNotFoundException($firstId);
            }
            $second = Account::where('id', $secondId)->lockForUpdate()->first();
            if ($second === null) {
                throw new AccountNotFoundException($secondId);
            }

            $source = ($sourceId === $firstId) ? $first  : $second;
            $dest   = ($destId   === $firstId) ? $first  : $second;

            // 3. Business rule: source.balance >= amount.
            if ($source->balance < $amount) {
                throw new InsufficientFundsException(
                    $source->id, $source->balance, $amount
                );
            }

            // 4. Mutate balances. Eloquent's save() issues UPDATE immediately,
            //    holding the row lock. We add the optimistic-lock WHERE clause
            //    by extending the query builder:
            $sourceAffected = Account::where('id', $source->id)
                ->where('version', $source->version)
                ->update([
                    'balance' => $source->balance - $amount,
                    'version' => $source->version + 1,
                ]);
            if ($sourceAffected === 0) {
                // Optimistic-lock failure. Force a retry by throwing a
                // QueryException with SQLSTATE 40001. In practice this should
                // not happen under SELECT FOR UPDATE, but it's a safety net.
                throw new QueryException(
                    'UPDATE accounts ...',
                    [],
                    new \Exception('optimistic lock conflict on source account')
                );
            }
            Account::where('id', $dest->id)
                ->where('version', $dest->version)
                ->update([
                    'balance' => $dest->balance + $amount,
                    'version' => $dest->version + 1,
                ]);

            // 5. Insert the transaction and the two entry rows.
            $tx = LedgerTransaction::create([
                'id'           => $idempotencyKey,
                'source_acc_id'  => $sourceId,
                'dest_acc_id'    => $destId,
                'amount'       => $amount,
                'status'       => 'committed',
            ]);
            Entry::create([
                'transaction_id' => $idempotencyKey,
                'account_id'     => $sourceId,
                'amount'         => -$amount,
            ]);
            Entry::create([
                'transaction_id' => $idempotencyKey,
                'account_id'     => $destId,
                'amount'         => $amount,
            ]);

            // 6. Idempotency record. The UNIQUE constraint on
            //    idempotency_keys.key is the last-line defence. If two
            //    concurrent requests with the same UUID both pass step 1,
            //    one will fail at this insert with QueryException SQLSTATE
            //    23505 (unique_violation), which DB::transaction rolls back.
            //    We catch it and re-raise as IdempotencyConflictException so
            //    the controller maps it to 409 instead of 500.
            try {
                IdempotencyKey::create([
                    'key'            => $idempotencyKey,
                    'transaction_id' => $idempotencyKey,
                ]);
            } catch (QueryException $e) {
                if ($e->getCode() === '23505') {
                    throw new IdempotencyConflictException($idempotencyKey);
                }
                throw $e;
            }

            return $tx;
        }, config('ledger.deadlock_retries', 3));
    }
}
```

### Controllers and routes

```php
<?php
// app/Http/Controllers/TransferController.php
namespace App\Http\Controllers;

use App\Http\Requests\TransferRequest;
use App\Services\TransferService;
use App\Exceptions\IdempotencyConflictException;
use Illuminate\Http\JsonResponse;
use Illuminate\Http\Request;
use Illuminate\Routing\Controller;

class TransferController extends Controller
{
    public function __construct(private readonly TransferService $transferService) {}

    public function store(TransferRequest $request): JsonResponse
    {
        $idempotencyKey = $request->header('Idempotency-Key');
        $sourceId = (int) $request->input('source_account_id');
        $destId   = (int) $request->input('destination_account_id');
        $amount   = (int) $request->input('amount');

        $tx = $this->transferService->transfer($sourceId, $destId, $amount, $idempotencyKey);

        // Idempotency collision: same UUID, different body.
        if ($tx->source_acc_id !== $sourceId
            || $tx->dest_acc_id !== $destId
            || $tx->amount !== $amount) {
            throw new IdempotencyConflictException($idempotencyKey);
        }

        return response()->json([
            'id'                    => $tx->id,
            'source_account_id'     => $tx->source_acc_id,
            'destination_account_id'=> $tx->dest_acc_id,
            'amount'                => $tx->amount,
            'status'                => $tx->status,
            'created_at'            => $tx->created_at->toIso8601String(),
        ], 201);
    }
}
```

```php
<?php
// app/Http/Controllers/AccountController.php
namespace App\Http\Controllers;

use App\Http\Requests\CreateAccountRequest;
use App\Models\{Account, Entry};
use App\Exceptions\AccountNotFoundException;
use Illuminate\Http\JsonResponse;
use Illuminate\Routing\Controller;

class AccountController extends Controller
{
    public function store(CreateAccountRequest $request): JsonResponse
    {
        $account = Account::create([
            'name'           => $request->input('name'),
            'balance'        => (int) $request->input('initial_balance', 0),
        ]);
        return response()->json([
            'id'         => $account->id,
            'name'       => $account->name,
            'balance'    => $account->balance,
            'created_at' => $account->created_at->toIso8601String(),
        ], 201);
    }

    public function balance(int $id): JsonResponse
    {
        $account = Account::find($id);
        if ($account === null) throw new AccountNotFoundException($id);
        return response()->json([
            'id'      => $account->id,
            'balance' => $account->balance,
            'version' => $account->version,
            'as_of'   => now()->toIso8601String(),
        ]);
    }

    public function transactions(int $id): JsonResponse
    {
        if (Account::find($id) === null) throw new AccountNotFoundException($id);
        $limit  = min((int) request()->input('limit', 50), 200);
        $offset = (int) request()->input('offset', 0);

        $entries = Entry::where('account_id', $id)
            ->with('transaction')
            ->orderByDesc('created_at')
            ->skip($offset)
            ->take($limit)
            ->get();

        return response()->json([
            'account_id'   => $id,
            'transactions' => $entries->map(fn (Entry $e) => [
                'id'                       => $e->transaction_id,
                'amount'                   => $e->amount,
                'counterparty_account_id'  => $e->transaction->source_acc_id === $id
                    ? $e->transaction->dest_acc_id
                    : $e->transaction->source_acc_id,
                'created_at'               => $e->created_at->toIso8601String(),
            ]),
            'limit'  => $limit,
            'offset' => $offset,
        ]);
    }
}
```

### Exception handler

Laravel's exception handler is centralised in `app/Exceptions/Handler.php`. We override `register()` to map domain exceptions to JSON responses.

```php
<?php
// app/Exceptions/Handler.php
namespace App\Exceptions;

use Illuminate\Foundation\Exceptions\Handler as ExceptionHandler;
use Illuminate\Database\QueryException;
use Illuminate\Http\JsonResponse;
use Illuminate\Http\Request;
use Throwable;

class Handler extends ExceptionHandler
{
    public function register(): void
    {
        $this->renderable(function (AccountNotFoundException $e, Request $req) {
            return response()->json(
                ['error' => $e->getMessage(), 'code' => 'ACCOUNT_NOT_FOUND'],
                404
            );
        });
        $this->renderable(function (InsufficientFundsException $e, Request $req) {
            return response()->json(
                ['error' => $e->getMessage(), 'code' => 'INSUFFICIENT_FUNDS'],
                422
            );
        });
        $this->renderable(function (IdempotencyConflictException $e, Request $req) {
            return response()->json(
                ['error' => $e->getMessage(), 'code' => 'IDEMPOTENCY_CONFLICT'],
                409
            );
        });
        // QueryException with SQLSTATE 23505 = unique constraint violation
        // (the idempotency-key race that escaped the try/catch in the service).
        $this->renderable(function (QueryException $e, Request $req) {
            $sqlstate = $e->getCode();
            if ($sqlstate === '23505') {
                return response()->json([
                    'error' => 'idempotency key already used for a different transfer',
                    'code'  => 'IDEMPOTENCY_CONFLICT',
                ], 409);
            }
            // 40P01 = deadlock, 40001 = serialization failure. If we land here,
            // the retry loop in DB::transaction has exhausted its attempts.
            if (in_array($sqlstate, ['40P01', '40001'], true)) {
                return response()->json([
                    'error' => 'deadlock detected, retry the request',
                    'code'  => 'DEADLOCK_RETRY',
                ], 409);
            }
            return response()->json(
                ['error' => 'database error', 'code' => 'DB_ERROR'],
                500
            );
        });
    }
}
```

### What is automatic here that was manual in the anchor

**Deadlock retry.** Laravel's `DB::transaction(closure, $attempts = 3)` includes built-in retry logic. When the closure throws `QueryException` with SQLSTATE `40P01` (deadlock) or `40001` (serialization), Laravel catches it, rolls back, and re-executes the closure, up to `$attempts` times. There is no hand-written decorator, no AOP aspect, no `RetryAspect` class to wire. The retry is built into the framework's transaction primitive. This is the only ecosystem in this milestone that ships with built-in retry — Spring requires an explicit aspect, Prisma requires a hand-written `withRetry` wrapper, Django requires a hand-written `@retry_on_deadlock` decorator. The cost of Laravel's convenience is opacity: the retry is invisible in the service code, and a developer who doesn't know about it may not realise their transaction is being silently retried. The benefit is correctness-by-default: no transactional method can ship without retry, because the retry comes with the primitive.

**Active Record persistence.** Eloquent's `$account->save()` and `Account::create([...])` issue `INSERT`/`UPDATE` immediately, like Django ORM and unlike Hibernate's batch-at-commit. There is no `EntityManager`, no dirty checking, no flush cycle. Each `save()` is one SQL statement, executed synchronously, holding the row lock for the duration of the transaction. This is more transparent than Hibernate (you can `DB::enableQueryLog()` and see every SQL statement as it fires) and less efficient for bulk operations (no `saveAll` batching — use `DB::table('accounts')->insert([...$rows])` for that).

**Service container DI.** Laravel's service container auto-wires constructor dependencies — `TransferController`'s constructor asks for `TransferService`, and Laravel resolves it without any explicit binding. Spring has the same feature via `@Autowired`, but Laravel's resolution is based on PHP's type-hint reflection, which is more transparent than Spring's runtime bytecode inspection. The cost is that all dependencies must be concrete classes or interfaces with explicit bindings in a service provider; the benefit is that there is no `@Component` / `@Service` / `@Repository` annotation ceremony — the class is just a class, and the container picks it up.

### What is manual here that was automatic in the anchor

**Isolation level.** Laravel's `DB::transaction()` does not accept an isolation-level parameter. The application must issue `DB::statement('SET TRANSACTION ISOLATION LEVEL REPEATABLE READ')` inside the closure, before any `SELECT`. This is the same API gap as Django's — both ecosystems treat isolation level as a property of the connection, not of the transaction. Spring's `@Transactional(isolation = Isolation.REPEATABLE_READ)` is a cleaner API because it ties the isolation level to the transactional method, not to the connection. The Laravel approach is more verbose but more explicit: the engineer can see the `SET TRANSACTION` statement in the code, which makes the isolation level visible at the call site rather than hidden behind an annotation.

**Optimistic locking.** Eloquent does not have a built-in `$version` column feature. The `version` field exists in the model, but `$account->save()` does not automatically check or increment it. The application must use the query builder directly: `Account::where('id', $id)->where('version', $prior_version)->update(['balance' => ..., 'version' => $prior_version + 1])`, then check the return value (number of rows affected). This is the same pattern as Django — both Active Record ORMs require manual optimistic-lock handling. The Spring equivalent — `@Version private Long version;` — does this transparently.

**Pessimistic locking syntax.** Eloquent's `lockForUpdate()` is a method on the query builder: `Account::where('id', $id)->lockForUpdate()->first()`. This is comparable to Django's `select_for_update()` and roughly as ergonomic. Compare to Spring's `@Lock(LockModeType.PESSIMISTIC_WRITE)` annotation on a repository method, which is one layer of indirection removed from the call site. Eloquent's API is more explicit (the lock is visible in the query chain) but less reusable (the lock is not a property of the repository method, so every caller must remember to add it). Spring's annotation-based approach enforces the lock at the repository level — every caller gets it for free.

## Implementation Steps

1. **Bootstrap.** Run `composer create-project laravel/laravel ledger-laravel "10.*"`. Install dependencies: `composer require predis/predis laravel/sanctum` (Sanctum if you want API tokens later). Install FrankenPHP: `composer require laravel/frankenphp` (replaces php-fpm + nginx with a single C-based SAPI binary, 2-3× faster than php-fpm for I/O-bound workloads).
2. **Wire dependencies.** Copy the models into `app/Models/`. Create the migrations via `php artisan make:migration` and copy the trigger migration's `DB::unprepared` SQL. Run `php artisan migrate` against the Postgres 16 instance. Configure `config/database.php` with `pgsql` connection, `DB_HOST=db`, `DB_DATABASE=ledger`, pool size 20.
3. **Implement the contract.** Create `app/Services/TransferService.php`, `app/Http/Controllers/AccountController.php`, `app/Http/Controllers/TransferController.php`, `app/Http/Requests/CreateAccountRequest.php`, `app/Http/Requests/TransferRequest.php`, `app/Exceptions/*.php` per the code above. Wire the routes in `routes/api.php`. Run `php artisan serve --host=0.0.0.0 --port=8080` and verify `curl localhost:8080/api/health` returns `{"status":"ok"}`.
4. **Wire observability.** Laravel ships with structured logging via `Log::channel('stack')`; add `spatie/laravel-structure-logger` for `trace_id` propagation. For Prometheus metrics, add `promphp/prometheus_client_php` and expose `/metrics` — the must-have counter is `ledger_transfers_deadlock_total`, incremented in a custom wrapper around `DB::transaction` (or read from Laravel's query log). The connection-pool gauge is harder; instrument via `DB::connection()->getPdo()->query('SELECT count(*) FROM pg_stat_activity WHERE state != \'idle\'')->fetchColumn()`.
5. **Containerise.** Use the official FrankenPHP Laravel image: `FROM dunglas/frankenphp:latest-php8.3 AS base`, copy the app, run `composer install --no-dev --optimize-autoloader`. Final image size ~96 MB. Run with `frankenphp php-server --listen=:8080 --root=public` or via `php artisan octane:frankenphp` (Laravel Octane, keeps the app bootstrapped in memory — 3× throughput over a fresh boot per request).
6. **Test.** Write integration tests with `pest` (the modern Laravel test framework, replacing PHPUnit) and `orchestral/testbench` for the test DB. The concurrency test uses `Http::pool(['concurrency' => 50])` to fire 1 000 transfers in parallel and asserts the final balance. The chaos test uses `toxiproxy` to kill the DB connection mid-transfer and verifies the idempotency-key constraint prevents a double-application on retry.

## What This Teaches

The Laravel implementation teaches four lessons that complement the Spring anchor. **First: built-in retry is a correctness-by-default feature.** Laravel's `DB::transaction(closure, $attempts)` is the only ecosystem in this milestone where the retry comes with the transaction primitive. Spring requires an explicit `RetryAspect`, Prisma requires a hand-written `withRetry` wrapper, Django requires a hand-written `@retry_on_deadlock` decorator — all three are things a developer can forget to apply. Laravel's approach means *no transactional method can ship without retry*, because the retry is the default behaviour of `DB::transaction`. The cost is opacity: a developer who doesn't read the docs may not realise their transaction is being silently retried 3 times before failing. The benefit is correctness: no `@RetryAspect`-missing bug, no decorator-forgotten bug, no `withRetry`-wrapper-not-applied bug. This is a clear framework design win.

**Second: Active Record is the same trade-off in PHP as in Python.** Eloquent, like Django ORM, flushes each `save()` immediately. There is no `EntityManager`, no dirty checking, no batch-at-commit. This is more transparent than Hibernate (you can `DB::enableQueryLog()` and see every SQL statement as it fires) and less efficient for bulk operations (no `saveAll` batching — use `DB::table('accounts')->insert([...$rows])` for that). For the ledger, where each transfer does exactly two `INSERT`s, the difference is negligible; for a bulk-import path, the Laravel engineer must reach for the query builder directly. The lesson: Active Record and Data Mapper are not "right vs wrong" — they are different points on the transparency/efficiency trade-off, and the right choice depends on the workload.

**Third: `lockForUpdate()` is fluent and explicit.** Laravel's `Account::where('id', $id)->lockForUpdate()->first()` reads as English: "find the account where id, lock for update, take the first." The lock is visible in the query chain, which makes it impossible to miss in code review. Compare to Spring's `@Lock(PESSIMISTIC_WRITE)` annotation on a repository method, which is invisible at the call site — a caller writing `accountRepo.findById(id)` has no way to know whether the lock is taken without navigating to the repository interface. Eloquent's approach is more verbose (every call site must include `lockForUpdate()`) but more transparent. The lesson: when a concurrency-critical primitive is opt-in at the call site rather than at the declaration site, code review becomes the primary defence — and code review is more reliable when the primitive is visible.

**Fourth: the framework's opinionated defaults accelerate the boring 80%.** Laravel's service container auto-wires dependencies, its migration system generates boilerplate, its exception handler centralises error mapping, its validation rules are declarative (`'amount' => 'required|integer|min:1'`), and its test framework (Pest) is concise. For the boring 80% of a CRUD app, Laravel's defaults save real time — the implementation of this milestone took 55 minutes to first green test, versus 4h 35m for Spring. The cost is that the framework's opinions are hard to override: if you want a different validation library, a different ORM, a different DI container, you are fighting the framework. The lesson: pick Laravel when the 80% matters more than the 20%; pick Spring when the 20% (custom transactions, custom AOP, custom isolation-level-per-method) is load-bearing. For a financial ledger, the 20% is load-bearing — but the Laravel implementation shows that the 20% can still be expressed, just more verbosely.
