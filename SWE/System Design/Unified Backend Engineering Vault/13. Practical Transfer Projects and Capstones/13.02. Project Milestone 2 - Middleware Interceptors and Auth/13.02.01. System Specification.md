# 13.02.01. System Specification

## Project Goal

This is a capstone milestone. Unlike concept notes, the goal is to build something that runs end-to-end across multiple ecosystems and survives a load test. You are not done when the code compiles — you are done when you can show a graph of the system failing gracefully under load and recovering.

Milestone 2 layers **authentication, authorization, and cross-cutting middleware** on top of the Organization & Membership API built in [[13.01.01. System Specification]]. Milestone 1 produced an open REST API: any caller could `GET /orgs/{id}`, `POST /orgs`, `DELETE /orgs/{id}/members/{userId}` with no questions asked. That is fine for a prototype and unacceptable for anything shipped past a firewall. This milestone closes the loop: every endpoint that mutates state now requires a verified identity, every endpoint that reads private data now requires a role check, and every request flowing through the system now carries a distributed-tracing header so that when (not if) something breaks in production you can follow one request across all four implementations.

The four target implementations are Spring Boot with Spring Security ([[13.02.02. Anchor Implementation Spring Security]]), Express/TypeScript ([[13.02.03. Translation Express TypeScript Middleware]]), Django ([[13.02.04. Translation Python Django Middleware]]) and Laravel ([[13.02.05. Translation PHP Laravel Middleware]]). All four must implement the same JWT + RBAC contract specified in the API Contract section below, and all four must survive the same `k6` load profile. The post-mortem lives in [[13.02.06. Architectural Comparison and Post-Mortem]].

## Requirements

- Secure the Organization API with JWT authentication, role-based authorization (RBAC), distributed tracing headers, and execution timers.
Each requirement is non-negotiable. If you skip one, you have completed a tutorial, not a milestone.

**JWT authentication.** Every protected endpoint must accept an `Authorization: Bearer <token>` header, verify the token's HS256 signature against a shared secret (`JWT_SECRET` env var, 32+ bytes, loaded once at boot), and verify the token has not expired (`exp` claim must be in the future with at least 60 seconds of slack). Access tokens have a 15-minute lifetime. Refresh tokens have a 7-day lifetime, are stored hashed (SHA-256) in a `refresh_tokens` table, and are rotated on every use — presenting a refresh token issues a new access+refresh pair and invalidates the old refresh token. If a refresh token is presented twice (the second presentation is rejected because the hash no longer matches), the entire refresh-token family is revoked and the user is force-logged-out, because reuse is the signature of a stolen-token attack.

**Role-based authorization (RBAC).** Three roles are defined in a strict hierarchy: `ADMIN > MEMBER > VIEWER`. An `ADMIN` can do anything within their organization (create/update/delete the org, add/remove members, change member roles). A `MEMBER` can read org data and update their own membership record (e.g., change display name) but cannot add or remove other members. A `VIEWER` can read org data and list members but cannot mutate anything. Roles are scoped per-organization: a user who is `ADMIN` of org A may be only `VIEWER` of org B. The JWT carries `sub` (user id), `email`, `org_id`, `role`, `iat`, `exp`; the role in the JWT is checked against the endpoint's required role (see API Contract). If the JWT's `org_id` does not match the `{id}` path parameter on an org endpoint, the request is `403 Forbidden` even if the role would otherwise permit it — this prevents a member of org A from accessing org B's data even if they somehow obtained a valid token for A.

**Distributed tracing headers.** Every request must read `X-Request-Id` (if present; otherwise generate a UUIDv4), `X-Trace-Id`, and `X-Span-Id` from the incoming headers, propagate them to all downstream calls (DB, internal HTTP), and include them in every structured log line. The middleware runs **before** the auth middleware so that 401/403 responses are also traced — an unauthenticated request is still a request you want to be able to debug. The trace ID is also echoed back in the `X-Trace-Id` response header so that the caller can correlate. If your ecosystem has native OpenTelemetry support (Spring Boot's `micrometer-tracing`, Express's `@opentelemetry/api`, Django's `django-structlog`, Laravel's `nova` packages), use it; otherwise hand-roll the three headers in middleware — the contract is the headers, not the library.

**Execution timers.** Every request must record `request.duration_ms` (wall-clock from middleware entry to response send), `request.db_ms` (time spent in DB calls during this request), and `request.handler_ms` (time spent in the route handler, excluding middleware). These are emitted as structured log fields and as a Prometheus histogram `http_request_duration_seconds{method,route,status}`. The middleware must record the start time using the runtime's monotonic clock (`System.nanoTime()` in Java, `performance.now()` in Node, `time.monotonic()` in Python, `hrtime(true)` in PHP with `microtime(true)` fallback), not the wall clock, because wall clock can jump on NTP sync and corrupt the histogram. The timer wraps the handler so that 500 errors are also timed — you want to know how slow your failures are, not just your successes.

## Acceptance Criteria

1. All four target ecosystems implement the same contract.
2. All four pass the same automated test suite (k6, pytest, or Postman).
3. At least one ecosystem is load-tested to failure, with a captured metric showing the failure and the fix.
4. The post-mortem note ([[13.02.06. Architectural Comparison and Post-Mortem]]) is filled in with concrete observations.

The shared test suite is a Postman collection (`milestone-2.postman_collection.json`) plus a `k6` script (`load.js`) checked into the project root. The Postman collection exercises every endpoint in the API Contract below, including the negative cases (expired token, wrong role, wrong org, refresh-token reuse detection). The `k6` script ramps from 50 → 5 000 VUs over 5 minutes against the `/auth/login` + `GET /orgs/{id}` happy path, with a 5 % rate of `/auth/refresh` calls mixed in. An ecosystem passes the load test if p99 latency on `GET /orgs/{id}` stays below 100 ms and the 5xx error rate stays below 0.1 % throughout the ramp. The post-mortem must include the captured `k6` summary output (p50, p90, p99, RPS, error rate) for each ecosystem and a screenshot of the Grafana panel showing the failure mode that was reproduced and fixed.

## Deliverables

- Source code for each ecosystem in a separate subfolder.
- A `docker-compose.yml` at the project root.
- A `README.md` with run instructions and a load-test screenshot.
- A post-mortem note in this folder.

The `docker-compose.yml` runs Postgres 16, Redis 7 (for token blacklist / rate limiting if you implement it), and the four ecosystem apps behind an `nginx` ingress on port 8080. Each ecosystem app is built with a multi-stage Dockerfile and exposes a `/health` endpoint that the ingress uses for readiness probes. The `README.md` documents the `JWT_SECRET` generation command (`openssl rand -base64 32`), the seed-script command (`docker compose run --rm seeder`), and the load-test command (`k6 run --env BASE_URL=http://localhost:8080 load.js`). The post-mortem is the capstone deliverable — without it, the milestone is incomplete.

## Architecture Sketch

The auth flow has four actors: the **Client** (curl, browser, or mobile app), the **App** (Spring Boot / Express / Django / Laravel — the implementation that runs the middleware pipeline), the **DB** (Postgres 16, holding `users`, `organizations`, `memberships`, `refresh_tokens` tables), and the **Ingress** (`nginx` reverse proxy on port 8080 that fans out to the right ecosystem app based on the `X-Ecosystem` header in the test harness). The diagram below shows the login flow (which produces a JWT), the protected-request flow (which consumes a JWT), and the refresh flow (which rotates the refresh token).

```text
                       ┌─────────┐
                       │ Client  │  (curl / browser / mobile)
                       └────┬────┘
                            │
            ┌───────────────┼──────────────────────────────────┐
            │               │                                  │
            │  POST /auth/login                                │
            │  {email, password}                               │
            │               │                                  │
            │               ▼                                  │
            │       ┌───────────────┐                          │
            │       │  Ingress:8080 │  (nginx reverse proxy)   │
            │       └───────┬───────┘                          │
            │               │                                  │
            │               ▼                                  │
            │   ┌───────────────────────────┐                  │
            │   │  App (middleware chain)   │                  │
            │   │  1. TraceMiddleware       │                  │
            │   │  2. TimerMiddleware       │                  │
            │   │  3. BodyParser            │                  │
            │   │  4. AuthController.login  │                  │
            │   └────────────┬──────────────┘                  │
            │                │                                  │
            │                ▼                                  │
            │       ┌────────────────┐                          │
            │       │  Postgres DB   │                          │
            │       │  SELECT user   │                          │
            │       │  WHERE email=? │                          │
            │       │  bcrypt.verify │                          │
            │       └────────┬───────┘                          │
            │                │                                  │
            │                ▼                                  │
            │   ┌───────────────────────────┐                  │
            │   │  Issue tokens             │                  │
            │   │  access  = HS256(sub,email,│                  │
            │   │            org_id,role,   │                  │
            │   │            iat,exp=+15m)  │                  │
            │   │  refresh = random 32B     │                  │
            │   │  store SHA256(refresh)    │                  │
            │   │  in refresh_tokens        │                  │
            │   └────────────┬──────────────┘                  │
            │                │                                  │
            │                ▼                                  │
            │   200 OK {accessToken, refreshToken, user}        │
            └────────────────┼─────────────────────────────────┘
                             │
                             │  GET /orgs/{id}
                             │  Authorization: Bearer <accessToken>
                             │  X-Trace-Id: <uuid>
                             │
                             ▼
   ┌─────────────────────────────────────────────┐
   │  App (middleware chain for protected route) │
   │  1. TraceMiddleware  ── propagate trace_id  │
   │  2. TimerMiddleware  ── start nanoTime      │
   │  3. JwtAuthMiddleware                       │
   │     a. extract Bearer token                 │
   │     b. HS256 verify + exp check             │
   │     c. parse claims → principal             │
   │     d. load user from DB (cache 60s)        │
   │     e. attach principal to request          │
   │  4. RbacMiddleware                          │
   │     a. read required role from route meta   │
   │     b. compare principal.role vs required   │
   │     c. compare principal.org_id vs path id  │
   │  5. OrgController.getOrg                    │
   │     SELECT * FROM organizations WHERE id=?  │
   └────────────────────┬────────────────────────┘
                        │
                        ▼
   200 OK {id, name, ...}      X-Trace-Id: <echoed>
                                (or 401 if JWT invalid)
                                (or 403 if role insufficient)
                                (or 403 if org_id mismatch)


   ── Refresh flow (rotates tokens, detects reuse) ──

   POST /auth/refresh {refreshToken}
                │
                ▼
   ┌─────────────────────────────────────────────┐
   │  AuthController.refresh                     │
   │  1. SHA256(refreshToken) → lookup in DB     │
   │  2. if not found  → REVOKE ENTIRE FAMILY    │
   │                    (stolen-token detected)  │
   │  3. if expired   → 401                      │
   │  4. issue new access + new refresh          │
   │  5. mark old refresh as used (delete row)   │
   │  6. store SHA256(new refresh) with same     │
   │     family_id                               │
   └─────────────────────────────────────────────┘
```

The middleware chain runs in strict order: **Trace → Timer → Auth → RBAC → Handler**. Trace first so that 401/403 are traced; Timer second so that auth overhead is included in the duration histogram; Auth before RBAC because RBAC needs a principal to check; Handler last. Reordering this chain is the single most common bug in this milestone — putting RBAC before Auth crashes with a null principal; putting Timer after Auth loses the auth-failure timings; putting Trace after Auth loses the trace context on 401s. The order is the contract.

## API Contract

All endpoints accept and return `application/json`. All error responses use the Problem Details for HTTP APIs shape (RFC 9457): `{"type": "https://http.cat/401", "title": "Unauthorized", "status": 401, "detail": "...", "instance": "/orgs/42", "trace_id": "..."}`. Status codes are part of the contract — a 200 where the spec says 201 is a bug.

### Auth endpoints (public, no JWT required)

| Method | Path | Request body | Response 200/201 | Error cases |
| --- | --- | --- | --- | --- |
| `POST` | `/auth/register` | `{email, password, name}` | `201 {id, email, name, role: "VIEWER", created_at}` | `400` invalid email / password < 8 chars; `409` email already exists |
| `POST` | `/auth/login` | `{email, password}` | `200 {accessToken, refreshToken, user: {id, email, name, role, org_id}}` | `401` invalid credentials; `429` rate-limited (5 attempts / 60s / email) |
| `POST` | `/auth/refresh` | `{refreshToken}` | `200 {accessToken, refreshToken}` (rotated) | `401` expired / not found; `401` reuse detected → family revoked |
| `GET` | `/auth/me` | — (JWT required) | `200 {id, email, name, role, org_id, memberships: [...]}` | `401` no/invalid JWT |

The access token's JWT payload is `{"sub": <user_id>, "email": "...", "org_id": <int|null>, "role": "ADMIN|MEMBER|VIEWER", "iat": <epoch>, "exp": <epoch+900>}`, signed with HS256 using `JWT_SECRET`. The header is `{"alg": "HS256", "typ": "JWT"}`. Refresh tokens are opaque 32-byte random strings (base64url-encoded, 43 chars), not JWTs — they carry no claims because their only purpose is to be looked up in the DB.

### Protected organization endpoints (JWT required, role-gated)

| Method | Path | Required role | Notes |
| --- | --- | --- | --- |
| `GET` | `/orgs` | `VIEWER` (any authenticated user) | Paginated list of orgs the user is a member of. `?page=1&size=20`. |
| `POST` | `/orgs` | `ADMIN` (system-level, must have `is_system_admin=true` on user) | Creates a new org; creator becomes ADMIN of the new org. |
| `GET` | `/orgs/{id}` | `VIEWER` (must be member of `{id}`) | Returns org + role of the calling user. |
| `PATCH` | `/orgs/{id}` | `ADMIN` (of org `{id}`) | Partial update; only `name`, `description` mutable. |
| `DELETE` | `/orgs/{id}` | `ADMIN` (of org `{id}`) | Soft-delete (`deleted_at` set); cascades to memberships. |
| `GET` | `/orgs/{id}/members` | `VIEWER` (of org `{id}`) | Paginated member list with role per member. |
| `POST` | `/orgs/{id}/members` | `ADMIN` (of org `{id}`) | Body `{user_id, role: "VIEWER|MEMBER"}`. Cannot add ADMIN via this endpoint — ADMINs are promoted via `PATCH /memberships/{id}`. |
| `PATCH` | `/orgs/{id}/members/{userId}` | `ADMIN` (of org `{id}`) | Change a member's role. To grant ADMIN, the caller must themselves be `is_system_admin=true`. |
| `DELETE` | `/orgs/{id}/members/{userId}` | `ADMIN` (of org `{id}`) | Remove member. Self-removal returns `400`. Last ADMIN cannot be removed (returns `409`). |

The role check is two-layered: first the JWT's `role` claim must be `>=` the required role (using the hierarchy `ADMIN > MEMBER > VIEWER`), and second the JWT's `org_id` must match the `{id}` path parameter on every `/orgs/{id}/*` route. The second check is what prevents cross-org access — without it, a `VIEWER` of org 1 could call `GET /orgs/2` and the role check alone would pass. The check is enforced in the RBAC middleware, not in the controller, so that a controller author who forgets to add a role annotation still gets the org_id check for free.

### Cross-cutting headers (in / out)

| Header | Direction | Purpose |
| --- | --- | --- |
| `Authorization: Bearer <jwt>` | in (protected routes) | The JWT access token. Missing on a protected route → `401`. |
| `X-Request-Id` | in (optional) / out (always) | Caller-supplied request ID. If absent, server generates UUIDv4. Echoed in response. |
| `X-Trace-Id` | in (optional) / out (always) | Distributed trace ID. If absent, server generates UUIDv4. Echoed. Propagated to DB span attributes. |
| `X-Span-Id` | in (optional) / out (always) | Span ID for OpenTelemetry-compatible tracing. |
| `X-RateLimit-Remaining` | out | On `/auth/login` only — number of remaining attempts before `429`. |
| `Content-Type: application/json` | in/out | Only accepted content type. `Accept: application/json` recommended but not required. |
