# 13.02.02. Anchor Implementation Spring Security

## Why This Is the Anchor

This note is the **deep anchor implementation** — the place where you build the concept in Spring Boot with production-grade depth. Per the Anchor and Delta protocol ([[00.02. The Anchor and Delta Learning Protocol]]), you must break this implementation before moving to the delta notes. The point is to acquire scars: real experience with the failure modes that this concept produces under load.

Spring Boot is the anchor because it forces you to confront strict types, multi-threading, reflection proxies, bytecode generation, the JVM memory model, and explicit architectural decisions. If you can build this in Spring Boot, you can build it anywhere. For authentication specifically, Spring Security adds four more confrontations that no other ecosystem forces: the `SecurityFilterChain` runs **before** the DispatcherServlet (so your `@ControllerAdvice` does not catch its exceptions), the `SecurityContextHolder` is a `ThreadLocal` (so it does not propagate across `@Async` boundaries without a `DelegatingSecurityContextExecutor`), method security (`@PreAuthorize`) is implemented via CGLIB proxies (so calling a secured method from another method on the same bean bypasses the proxy), and the filter chain order is non-obvious (your custom JWT filter must run after `SecurityContextHolderFilter` and before `UsernamePasswordAuthenticationFilter`).

## What You Will Build

A Spring Boot 3.3 application that secures the Milestone 1 Organization API with the JWT + RBAC contract from [[13.02.01. System Specification]]. The deliverable is a `mvn spring-boot:run`-able project with: a `JwtAuthenticationFilter` (extracts `Authorization: Bearer`, verifies HS256, loads user, attaches principal to the `SecurityContext`), an `AuthController` (`/auth/register`, `/auth/login`, `/auth/refresh`, `/auth/me`), a `RoleRequired` annotation + `MethodSecurityExpressionHandler` for RBAC, the original `OrgController` now annotated with `@PreAuthorize`, a `RefreshToken` entity with family-based rotation + reuse detection, and a `TraceContextFilter` + `RequestTimerFilter` that satisfy the cross-cutting requirements. Schema is migrated by Flyway; tests use Testcontainers + Postgres; load test uses `k6`.

## What This Is

**Anchor Implementation Spring Security** is the reference implementation of the Milestone 2 contract. Every other ecosystem's implementation in this milestone ([[13.02.03. Translation Express TypeScript Middleware]], [[13.02.04. Translation Python Django Middleware]], [[13.02.05. Translation PHP Laravel Middleware]]) is a delta from this code. Read this note first, type the code out yourself, run it, break it (see Break It section), and only then read the deltas — they will be obvious to you because you will see what each ecosystem compresses away.

The hard parts in this implementation are not the JWT signing (JJWT library does that in 3 lines) or the BCrypt verification (Spring's `PasswordEncoder` does that in 1 line). The hard parts are: (a) wiring the `JwtAuthenticationFilter` into the `SecurityFilterChain` at the correct position so it runs before the controller but after the trace filter, (b) making the `SecurityContext` propagate correctly when you use `@Async` or `CompletableFuture` for parallel DB lookups, (c) implementing the refresh-token family rotation without a race condition (two concurrent refresh requests with the same token must not both succeed — the second must trigger reuse detection), and (d) writing a `@PreAuthorize` expression that checks both the role hierarchy AND the org_id path binding in one annotation. Each of those four is a 2-3 hour debugging session the first time you hit it. This note shows you the working version and explains why each piece is shaped the way it is.

## The Details

### The middleware pipeline: filter ordering, the SecurityFilterChain, and why your JWT filter must run after SecurityContextHolderFilter

Spring Security's `SecurityFilterChain` is a linked list of `Filter` instances that run **before** the DispatcherServlet. The default chain (in Spring Boot 3.3) has 15 filters in this order, abbreviated: `DisableEncodeUrlFilter` → `WebAsyncManagerIntegrationFilter` → `HeaderWriterFilter` → `SecurityContextHolderFilter` → `RequestCacheFilter` → `SecurityContextHolderAwareRequestFilter` → `AnonymousAuthenticationFilter` → `ExceptionTranslationFilter` → `AuthorizationFilter` → `...custom filters...` → `UsernamePasswordAuthenticationFilter` → ... → `FilterSecurityInterceptor`. Your custom `JwtAuthenticationFilter` must run **after** `SecurityContextHolderFilter` (so the `SecurityContextHolder` is initialised) and **before** `AuthorizationFilter` (so the role check has a principal to read). Get the order wrong and you spend an afternoon wondering why `@PreAuthorize("hasRole('ADMIN')")` returns 403 even when the JWT has `role: "ADMIN"`.

The reason for this rigidity is that Spring Security was originally designed for session-based form login, and the JWT case is grafted on. In a session-based flow, `UsernamePasswordAuthenticationFilter` populates the `SecurityContext` from the `HttpSession` on every request — the session is the source of truth. In a JWT flow, there is no session, so your `JwtAuthenticationFilter` must do the equivalent work: read the token, build an `Authentication` object, and call `SecurityContextHolder.getContext().setAuthentication(auth)`. The `AuthorizationFilter` (which is what backs `@PreAuthorize`) reads from the `SecurityContextHolder`, so it must run after your filter.

```java
@Configuration
@EnableWebSecurity
@EnableMethodSecurity   //  turns on @PreAuthorize
public class SecurityConfig {

    private final JwtAuthenticationFilter jwtFilter;
    private final TraceContextFilter traceFilter;
    private final RequestTimerFilter timerFilter;
    private final ObjectMapper objectMapper;

    public SecurityConfig(JwtAuthenticationFilter jwtFilter,
                          TraceContextFilter traceFilter,
                          RequestTimerFilter timerFilter,
                          ObjectMapper objectMapper) {
        this.jwtFilter = jwtFilter;
        this.traceFilter = traceFilter;
        this.timerFilter = timerFilter;
        this.objectMapper = objectMapper;
    }

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        return http
            .csrf(csrf -> csrf.disable())              // JWT, no cookies → CSRF N/A
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/auth/register", "/auth/login", "/auth/refresh").permitAll()
                .requestMatchers("/health", "/actuator/health/**").permitAll()
                .anyRequest().authenticated())
            //  Order matters: trace → timer → jwt.  Each is registered with
            //  an order relative to a known Spring Security filter so the
            //  chain is: ...SecurityContextHolderFilter → trace → timer → jwt → AuthorizationFilter
            .addFilterAfter(traceFilter,  SecurityContextHolderFilter.class)
            .addFilterAfter(timerFilter,  TraceContextFilter.class)
            .addFilterAfter(jwtFilter,    RequestTimerFilter.class)
            .exceptionHandling(eh -> eh
                .authenticationEntryPoint((req, res, ex) ->
                    writeProblem(res, 401, "Unauthorized", ex.getMessage(), req))
                .accessDeniedHandler((req, res, ex) ->
                    writeProblem(res, 403, "Forbidden", ex.getMessage(), req)))
            .build();
    }

    private void writeProblem(HttpServletResponse res, int status, String title,
                              String detail, HttpServletRequest req) throws IOException {
        res.setStatus(status);
        res.setContentType("application/problem+json");
        objectMapper.writeValue(res.getWriter(), java.util.Map.of(
            "type",     "https://http.cat/" + status,
            "title",    title,
            "status",   status,
            "detail",   detail == null ? "" : detail,
            "instance", req.getRequestURI(),
            "trace_id", req.getAttribute("traceId")));
    }

    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder(12);   //  cost factor 12 → ~250 ms per verify
    }
}
```

Two subtleties in that config: (1) `SessionCreationPolicy.STATELESS` is mandatory — without it Spring will still create `JSESSIONID` cookies and the `SecurityContextHolderAwareRequestFilter` will read auth from the session, causing weird caching of the principal across requests. (2) The `addFilterAfter` calls chain — `timerFilter` is added after `TraceContextFilter` (which was just added after `SecurityContextHolderFilter`), so the final order is `SecurityContextHolderFilter → TraceContextFilter → RequestTimerFilter → JwtAuthenticationFilter → AuthorizationFilter`. If you used `addFilterBefore` you would have to compute the inverse order mentally, which is harder to read.

The failure mode if you get this wrong is subtle: a 401 on every protected route even with a valid token, because `AuthorizationFilter` runs before `JwtAuthenticationFilter` populates the context. The fix is to dump the filter chain at startup with `logback`'s `org.springframework.security=DEBUG` and read the actual order. Spring Boot 3.3 also exposes the chain at `/actuator/mappings` for the controllers but not for the security filters — for the security filters you need `-Dlogging.level.org.springframework.security.web=DEBUG` and to look for the "Will not secure" / "Secure" log lines.

### JwtService: HS256 sign/verify with JJWT, claim schema, expiry slack, and the clock-skew trap

The `JwtService` is the only place that touches the JJWT library directly. It encapsulates three responsibilities: signing a new access token from a `Principal`, verifying a presented token's signature and expiry, and parsing the claims into a typed `JwtPrincipal` record. The verification step is where the bugs live — JJWT's default `JWT.require(algorithm).build().verify(token)` accepts a 60-second clock skew by default, which is what the spec wants, but if you use `JWT.parser().setSigningKey(key).parseClaimsJws(token)` instead you get zero clock skew and your tests will fail intermittently because the JWT issued at `T` is rejected at `T+0.001s` by a verifier whose clock is one millisecond ahead. Always use the `JWT.require()` builder.

```java
@Component
public class JwtService {

    private final SecretKey key;
    private final Clock clock;            //  inject for testability
    private static final long ACCESS_TTL_SECONDS = 900;     //  15 min
    private static final long EXPIRY_SLACK_SECONDS = 60;    //  accept tokens up to 60s past exp

    public JwtService(@Value("${jwt.secret}") String secret, Clock clock) {
        this.key = Keys.hmacShaKeyFor(secret.getBytes(StandardCharsets.UTF_8));
        this.clock = clock;
    }

    public String issueAccessToken(User user) {
        Instant now = clock.instant();
        return Jwts.builder()
            .subject(user.id().toString())
            .claim("email",  user.email())
            .claim("org_id", user.orgId())         //  null if no current org selected
            .claim("role",   user.role().name())
            .claim("name",   user.name())
            .issuedAt(Date.from(now))
            .expiration(Date.from(now.plusSeconds(ACCESS_TTL_SECONDS)))
            .signWith(key, Jwts.SIG.HS256)
            .compact();
    }

    public JwtPrincipal verify(String token) {
        try {
            Claims c = Jwts.parser()
                .verifyWith(key)
                .clockSkewSeconds(EXPIRY_SLACK_SECONDS)
                .build()
                .parseSignedClaims(token)
                .getPayload();
            return new JwtPrincipal(
                Long.parseLong(c.getSubject()),
                c.get("email", String.class),
                c.get("name",  String.class),
                c.get("org_id", Long.class),
                Role.valueOf(c.get("role", String.class)));
        } catch (ExpiredJwtException e) {
            throw new AuthException("token expired");
        } catch (JwtException e) {
            throw new AuthException("invalid token: " + e.getMessage());
        }
    }
}
```

The `JwtPrincipal` record is what gets attached to the `SecurityContext`:

```java
public record JwtPrincipal(Long userId, String email, String name,
                           Long orgId, Role role) {}
```

Three non-obvious decisions in this code: (1) `orgId` is `Long` not `long` because a freshly registered user has not yet selected an organization — `null` is a valid claim value and the RBAC check must handle it. (2) `Role` is an `enum {ADMIN, MEMBER, VIEWER}` so that the role comparison is `ordinal`-based — `ADMIN.ordinal()=0`, `MEMBER.ordinal()=1`, `VIEWER.ordinal()=2`, so `principal.role().ordinal() <= required.ordinal()` is the "principal has at least the required privilege" check. (3) The `Clock` is injected, not `Clock.systemUTC()` hardcoded, so that tests can advance the clock past `exp` and exercise the expired-token path without `Thread.sleep(900_000)`.

The failure mode if you skip the `clockSkewSeconds(60)` is intermittent 401s in production when the load balancer routes the verify call to a pod whose NTP is 1 second ahead of the pod that issued the token. The metric is `http_server_requests_seconds_count{status="401"}` rising from ~0 to ~2 % of traffic. The fix is the clock skew — the deeper fix is to issue tokens with `exp = now + 14min` and accept them up to `exp + 60s`, giving a 1-minute grace window that absorbs NTP drift.

### JwtAuthenticationFilter: extracting the Bearer header, DB lookup, caching, and SecurityContext propagation

The filter is the heart of the milestone. It runs on every request, extracts the `Authorization` header, strips the `Bearer ` prefix, calls `JwtService.verify()`, loads the user from the DB, and stores a `JwtAuthenticationToken` in the `SecurityContext`. The DB lookup is the expensive part — at 5 000 RPS, 5 000 user lookups per second is a non-trivial fraction of Postgres's `max_connections` budget — so it must be cached. The cache key is `userId`, the TTL is 60 seconds, and the cache is invalidated on `/auth/refresh` (which can change `role` and `org_id`) and on `PATCH /orgs/{id}/members/{userId}` (which can change a user's role).

```java
@Component
public class JwtAuthenticationFilter extends OncePerRequestFilter {

    private final JwtService jwt;
    private final UserRepository users;
    private final Cache<Long, User> userCache;

    public JwtAuthenticationFilter(JwtService jwt, UserRepository users) {
        this.jwt = jwt;
        this.users = users;
        this.userCache = Caffeine.newBuilder()
            .maximumSize(10_000)
            .expireAfterWrite(Duration.ofSeconds(60))
            .recordStats()             //  expose hit/miss to /actuator/metrics
            .build();
    }

    @Override
    protected void doFilterInternal(HttpServletRequest req,
                                    HttpServletResponse res,
                                    FilterChain chain) throws ServletException, IOException {
        String header = req.getHeader(HttpHeaders.AUTHORIZATION);
        if (header == null || !header.startsWith("Bearer ")) {
            chain.doFilter(req, res);    //  no token → anonymous; AuthorizationFilter will 401
            return;
        }
        String token = header.substring(7);
        try {
            JwtPrincipal principal = jwt.verify(token);
            User user = userCache.get(principal.userId(),
                id -> users.findById(id)
                    .orElseThrow(() -> new AuthException("user not found")));
            //  Always re-check role from DB-loaded user, not from JWT claim,
            //  so a revoked/updated role is honoured within 60s.
            JwtPrincipal fresh = new JwtPrincipal(
                user.id(), user.email(), user.name(), user.orgId(), user.role());
            SecurityContext ctx = SecurityContextHolder.createEmptyContext();
            ctx.setAuthentication(new JwtAuthenticationToken(fresh, token,
                List.of(new SimpleGrantedAuthority("ROLE_" + user.role().name()))));
            SecurityContextHolder.setContext(ctx);
            req.setAttribute("principal", fresh);   //  for controllers that don't want Spring Security
        } catch (AuthException e) {
            //  Don't throw — let the request continue as anonymous so the
            //  AuthorizationFilter's 401 path is taken, which produces the
            //  ProblemDetail response via the configured authenticationEntryPoint.
            log.debug("JWT verification failed: {}", e.getMessage());
            SecurityContextHolder.clearContext();
        }
        chain.doFilter(req, res);
    }
}
```

Two design decisions in that filter deserve explanation. First, the **DB-loaded user overrides the JWT claim** for `role` and `org_id`. The JWT is a snapshot of the user at issue time, but a user's role can change (admin demotes them) or the user can be disabled (`enabled=false`) between issue and verify. Always loading from DB would defeat the purpose of JWT (statelessness), but always trusting the claim means revocation takes up to 15 minutes (the access-token TTL). The compromise is the 60-second cache: revocation lands within 60 seconds, which is acceptable for most threat models. For higher-security deployments, you add a `revoked_tokens` table that the filter checks on every request — that is the spec's "token blacklist" extension and is out of scope for this milestone.

Second, the **`JwtAuthenticationToken` carries `ROLE_ADMIN` / `ROLE_MEMBER` / `ROLE_VIEWER` as granted authorities**. Spring Security's `hasRole('ADMIN')` expression checks for `ROLE_ADMIN` (it auto-prepends the `ROLE_` prefix), so this is what makes `@PreAuthorize("hasRole('ADMIN')")` work. If you forget the `ROLE_` prefix and put `ADMIN` as the authority, `hasRole('ADMIN')` looks for `ROLE_ADMIN` and silently fails. This is the single most common Spring Security mistake and the cause of 80 % of the "why is my `@PreAuthorize` not working" Stack Overflow questions.

The failure mode under load: at 5 000 RPS the user-cache hit rate should be >95 %. If it is not (visible via `/actuator/metrics/cache.gets{result=hit}` and `{result=miss}`), the cache is being evicted too aggressively. Check `cache.evictions{cause=size}` — if non-zero, the `maximumSize(10_000)` is too small for your active-user count. Bump to `100_000` and re-test. The cache miss path is one Postgres `SELECT` per request, so a 10 % miss rate at 5 000 RPS is 500 extra `SELECT`s/sec, which is what blew up HikariCP in the load test (see Break It section).

### RBAC: @PreAuthorize with custom expressions, org_id binding, and the proxy-bypass trap

Spring Security's `@PreAuthorize` annotation accepts a SpEL expression that has access to `authentication`, `principal`, and any registered `MethodSecurityExpressionRoot` methods. The default methods (`hasRole`, `hasAuthority`, `hasAnyRole`, `permitAll`, `denyAll`) cover the simple cases. The complex case in this milestone is: "the principal's role must be at least `MEMBER` AND the principal's `org_id` must equal the path variable `id`." That requires a custom expression root.

```java
@PreAuthorize("@rbac.canAccessOrg(#id, T com.example.auth.Role.MEMBER)")
@GetMapping("/orgs/{id}")
public OrgResponse getOrg(@PathVariable Long id) { ... }

@PreAuthorize("@rbac.canAccessOrg(#id, T com.example.auth.Role.ADMIN)")
@DeleteMapping("/orgs/{id}")
public void deleteOrg(@PathVariable Long id) { ... }
```

The `@rbac` is a Spring bean registered under the name `rbac`:

```java
@Component("rbac")
public class RbacService {

    public boolean canAccessOrg(Long orgId, Role required) {
        Authentication auth = SecurityContextHolder.getContext().getAuthentication();
        if (!(auth.getPrincipal() instanceof JwtPrincipal p)) {
            return false;   //  anonymous
        }
        //  ROLE check: ADMIN.ordinal=0 < MEMBER.ordinal=1 < VIEWER.ordinal=2
        //  "principal has at least required privilege" → ordinal <= required.ordinal
        if (p.role().ordinal() > required.ordinal()) {
            return false;
        }
        //  ORG binding: principal's org must match the path's org
        //  (unless the user is a system admin, who can access any org)
        if (p.userId() != null && p.role() == Role.ADMIN && p.isSystemAdmin()) {
            return true;
        }
        return orgId != null && orgId.equals(p.orgId());
    }
}
```

The trap: `@PreAuthorize` is enforced by a CGLIB proxy around the controller bean. When controller method A calls controller method B on the same bean, the proxy is bypassed and B's `@PreAuthorize` is **not checked**. This is the same proxy-bypass trap as `@Transactional`. The fix is to never call one `@PreAuthorize` method from another on the same bean — refactor so the security-relevant method is on a different bean, or use `AopContext.currentProxy()` (ugly, slow, and fragile). The clean pattern is: controllers call services, services have the `@PreAuthorize`, controllers do not call each other.

The other trap: SpEL expressions are evaluated at runtime, and a typo in `T com.example.auth.Role.MEMBER` (e.g. wrong package) throws `SpelEvaluationException` at request time, not at boot. There is no compile-time check. Always write an integration test for every `@PreAuthorize` annotation — one positive case (right role → 200) and one negative case (wrong role → 403). The test is the only safety net.

### AuthController: login (BCrypt + JWT issue), refresh (token rotation + reuse detection), and the family-revocation race

The `AuthController` has three non-trivial endpoints: `/auth/login` (BCrypt verify + JWT issue + refresh token store), `/auth/refresh` (rotate refresh token, detect reuse, revoke family), and `/auth/me` (return the principal). The login endpoint is straightforward; the refresh endpoint is where the security model lives.

```java
@RestController
@RequestMapping("/auth")
public class AuthController {

    private final UserRepository users;
    private final RefreshTokenStore refreshStore;
    private final PasswordEncoder encoder;
    private final JwtService jwt;

    public AuthController(UserRepository users, RefreshTokenStore refreshStore,
                          PasswordEncoder encoder, JwtService jwt) {
        this.users = users;
        this.refreshStore = refreshStore;
        this.encoder = encoder;
        this.jwt = jwt;
    }

    @PostMapping("/register")
    @ResponseStatus(HttpStatus.CREATED)
    public RegisterResponse register(@Valid @RequestBody RegisterRequest req) {
        if (users.findByEmail(req.email()).isPresent()) {
            throw new ConflictException("email already exists");
        }
        User u = users.save(new User(null, req.email(),
            encoder.encode(req.password()), req.name(),
            null, Role.VIEWER, false, Instant.now()));
        return new RegisterResponse(u.id(), u.email(), u.name(), u.role(), u.createdAt());
    }

    @PostMapping("/login")
    public LoginResponse login(@Valid @RequestBody LoginRequest req) {
        User u = users.findByEmail(req.email())
            .orElseThrow(() -> new AuthException("invalid credentials"));
        if (!u.enabled()) {
            throw new AuthException("account disabled");
        }
        if (!encoder.matches(req.password(), u.passwordHash())) {
            throw new AuthException("invalid credentials");
        }
        String access  = jwt.issueAccessToken(u);
        String refresh = refreshStore.issue(u.id());   //  stores SHA256(refresh) in DB
        return new LoginResponse(access, refresh, new UserDto(u));
    }

    @PostMapping("/refresh")
    public LoginResponse refresh(@Valid @RequestBody RefreshRequest req) {
        //  Rotation is atomic: SELECT FOR UPDATE the row by SHA256(token),
        //  if found mark as used (delete) and issue new token in same family,
        //  if not found check if it was ever part of a family → revoke family.
        RefreshResult r = refreshStore.rotate(req.refreshToken());
        if (r == RefreshResult.REUSE_DETECTED) {
            //  Critical: someone is presenting an already-used refresh token.
            //  Revoke the entire family and force re-login everywhere.
            refreshStore.revokeFamilyByToken(req.refreshToken());
            throw new AuthException("refresh token reuse detected — family revoked");
        }
        if (r == RefreshResult.NOT_FOUND || r == RefreshResult.EXPIRED) {
            throw new AuthException("invalid refresh token");
        }
        User u = users.findById(r.userId())
            .orElseThrow(() -> new AuthException("user not found"));
        String access = jwt.issueAccessToken(u);
        return new LoginResponse(access, r.newRefreshToken(), new UserDto(u));
    }

    @GetMapping("/me")
    public UserDto me(@AuthenticationPrincipal JwtPrincipal p) {
        return new UserDto(users.findById(p.userId()).orElseThrow());
    }
}
```

The `RefreshTokenStore.rotate()` method is the only place where reuse is detected, and it must be atomic — two concurrent `POST /auth/refresh` calls with the same token must not both succeed. The implementation uses a Postgres `SELECT ... FOR UPDATE` inside a transaction:

```java
@Repository
public class RefreshTokenStore {

    private final JdbcTemplate jdbc;

    public RefreshResult rotate(String presentedToken) {
        String hash = sha256(presentedToken);
        return jdbc.execute(new ConnectionCallback<>() {
            @Override public RefreshResult doInConnection(Connection con) throws SQLException {
                con.setTransactionIsolation(Connection.TRANSACTION_REPEATABLE_READ);
                //  Row-level lock on the presented token's row.
                Long familyId = jdbc.queryForList(
                    "SELECT family_id FROM refresh_tokens WHERE token_hash = ? FOR UPDATE",
                    Long.class, hash).stream().findFirst().orElse(null);
                if (familyId == null) {
                    //  Was this token ever valid? If so, reuse → revoke family.
                    boolean wasValid = jdbc.queryForObject(
                        "SELECT EXISTS(SELECT 1 FROM refresh_tokens_history WHERE token_hash = ?)",
                        Boolean.class, hash);
                    return wasValid ? RefreshResult.REUSE_DETECTED : RefreshResult.NOT_FOUND;
                }
                //  Atomically delete the old token and insert the new one in the same family.
                jdbc.update("DELETE FROM refresh_tokens WHERE token_hash = ?", hash);
                String newToken = generateSecureRandom(32);
                String newHash  = sha256(newToken);
                jdbc.update("INSERT INTO refresh_tokens(token_hash, family_id, user_id, expires_at) " +
                            "VALUES (?, ?, ?, NOW() + INTERVAL '7 days')",
                            newHash, familyId, /* userId */ getUserIdForFamily(familyId));
                //  Move old hash to history for future reuse detection.
                jdbc.update("INSERT INTO refresh_tokens_history(token_hash, family_id, revoked_at) " +
                            "VALUES (?, ?, NOW())", hash, familyId);
                return new RefreshResult(familyId, /* userId */ getUserIdForFamily(familyId), newToken);
            }
        });
    }

    public void revokeFamilyByToken(String presentedToken) {
        String hash = sha256(presentedToken);
        jdbc.update("DELETE FROM refresh_tokens WHERE family_id = " +
                    "(SELECT family_id FROM refresh_tokens_history WHERE token_hash = ?)",
                    hash);
    }

    private String sha256(String s) {
        try {
            byte[] h = MessageDigest.getInstance("SHA-256").digest(s.getBytes(UTF_8));
            return Base64.getUrlEncoder().withoutPadding().encodeToString(h);
        } catch (NoSuchAlgorithmException e) { throw new IllegalStateException(e); }
    }
}
```

Two design points worth highlighting. First, `TRANSACTION_REPEATABLE_READ` is required, not `READ_COMMITTED`. Under `READ_COMMITTED` two concurrent transactions can both see the row, both `SELECT FOR UPDATE` (the second blocks), the first deletes and commits, the second unblocks and sees an empty `SELECT` — wrong. `REPEATABLE_READ` makes the second transaction's snapshot include the original row state, so when it unblocks it sees the row as still-present and proceeds — also wrong, but in a different way. The correct fix is to make `DELETE FROM refresh_tokens WHERE token_hash = ?` the source of truth: only one transaction's `DELETE` will affect 1 row; the other will affect 0 rows, and that 0-row result is the reuse signal. The implementation above checks `familyId != null` after the `SELECT FOR UPDATE`, which is correct under `REPEATABLE_READ` because the snapshot is consistent. Always test this with a `CountDownLatch`-synchronised pair of threads.

Second, `refresh_tokens_history` is append-only and grows unboundedly. In production, prune it with a nightly job: `DELETE FROM refresh_tokens_history WHERE revoked_at < NOW() - INTERVAL '30 days'`. 30 days is long enough to catch a stolen-token attack (the attacker will reuse within hours, not weeks) and short enough to keep the table under a million rows.

### Cross-cutting filters: TraceContextFilter and RequestTimerFilter using the monotonic clock

The trace and timer filters run before auth so that 401s are traced and timed. Both must use the monotonic clock (`System.nanoTime()`), not the wall clock (`System.currentTimeMillis()`), because NTP can shift the wall clock backward by up to 500 ms and corrupt the histogram. The trace filter reads `X-Request-Id` and `X-Trace-Id` from the request (generating UUIDv4 if absent), stores them in the request attributes (so the controller can read them) and in an MDC (so the logger includes them automatically).

```java
@Component
public class TraceContextFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res,
                                    FilterChain chain) throws ServletException, IOException {
        String requestId = firstNonBlank(req.getHeader("X-Request-Id"), UUID.randomUUID().toString());
        String traceId   = firstNonBlank(req.getHeader("X-Trace-Id"),   UUID.randomUUID().toString());
        String spanId    = UUID.randomUUID().toString();
        req.setAttribute("requestId", requestId);
        req.setAttribute("traceId",   traceId);
        req.setAttribute("spanId",    spanId);
        MDC.put("request_id", requestId);
        MDC.put("trace_id",   traceId);
        res.setHeader("X-Request-Id", requestId);
        res.setHeader("X-Trace-Id",   traceId);
        try { chain.doFilter(req, res); }
        finally { MDC.clear(); }   //  critical: ThreadLocal cleanup
    }
}

@Component
public class RequestTimerFilter extends OncePerRequestFilter {
    private final MeterRegistry meters;

    public RequestTimerFilter(MeterRegistry meters) { this.meters = meters; }

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res,
                                    FilterChain chain) throws ServletException, IOException {
        long start = System.nanoTime();      //  monotonic
        try {
            chain.doFilter(req, res);
        } finally {
            long durationNs = System.nanoTime() - start;
            double durationSec = durationNs / 1_000_000_000.0;
            String route = (String) req.getAttribute(HandlerMapping.BEST_MATCHING_PATTERN_ATTRIBUTE);
            if (route == null) route = "unknown";
            meters.timer("http_request_duration_seconds",
                    "method", req.getMethod(),
                    "route",  route,
                    "status", Integer.toString(res.getStatus()))
                  .record(Duration.ofNanos(durationNs));
            res.setHeader("X-Response-Time-ms", Long.toString(durationNs / 1_000_000));
        }
    }
}
```

The MDC cleanup in the `finally` block is non-negotiable. Tomcat reuses threads from its pool, and an uncleared MDC leaks the previous request's `trace_id` into the next request's log lines. The symptom is two unrelated requests appearing in the log under the same `trace_id`, which makes debugging impossible. The same applies to the `SecurityContextHolder` — Spring Security clears it for you in `SecurityContextHolderFilter`, but only if you do not overwrite the context in your own filter. Our `JwtAuthenticationFilter` does overwrite it, so it must also clear it in a `finally` block (omitted from the snippet above for brevity — add it).

## What This Teaches

Building JWT auth in Spring Boot teaches five things that no other ecosystem forces you to confront in the same way:

1. **Filter-chain ordering is the security model.** The `SecurityFilterChain` is not a "middleware list" you can reorder freely — the order encodes security guarantees (trace before auth so 401s are traced; auth before RBAC so RBAC has a principal; auth-failure handling at the chain's `ExceptionTranslationFilter` not in the controller). Reorder at your peril. The deltas (Express, Django, Laravel) have analogous order dependencies but they are spelled out in app code, not encoded in a framework DSL.

2. **`SecurityContextHolder` is a `ThreadLocal`.** It does not propagate across `@Async`, `CompletableFuture.supplyAsync`, or reactor's `publishOn`. If you do parallel DB lookups inside a request handler, the child threads have an empty `SecurityContext` and `@PreAuthorize` on the called service method silently passes (no principal = "anonymous" = 401/403). You must use `DelegatingSecurityContextExecutor` or `SecurityContextHolder.getContext()` in the parent thread and re-set it in the child. This trap does not exist in single-threaded runtimes (Node, PHP-FPM before Octane).

3. **CGLIB proxies and `@PreAuthorize` self-invocation.** Calling a secured method from another method on the same bean bypasses the proxy. This is identical to the `@Transactional` trap and is the most common Spring Security bug. The fix is structural: controllers call services, services have `@PreAuthorize`, controllers do not call each other.

4. **Refresh-token rotation is a concurrency problem, not a crypto problem.** The HS256 signing is trivial (3 lines with JJWT). The hard part is making `rotate()` atomic under concurrent refresh requests. Postgres `SELECT FOR UPDATE` + `REPEATABLE_READ` is the correct tool; an in-memory lock (like `synchronized` or `ReentrantLock`) does not survive a multi-instance deployment.

5. **Monotonic clock vs wall clock.** `System.nanoTime()` for duration measurement, `System.currentTimeMillis()` for timestamps. NTP can move the wall clock backward by up to 500 ms, which makes `end - start` negative, which corrupts Prometheus histograms. This is universal across runtimes — Node has `performance.now()`, Python has `time.monotonic()`, PHP has `hrtime(true)`. Spring Boot is where you learn it because the JVM's `System.currentTimeMillis()` is the most obviously wrong choice.

## Cross-Ecosystem Code

The same JWT-auth middleware expressed in all four target ecosystems. The shape is identical: extract Bearer → verify signature → load user → attach principal → check role. The deltas (Express, Django, Laravel) are explored in depth in their own notes — these snippets are for side-by-side comparison.

**Spring Boot (Anchor):**
```java
// JwtAuthenticationFilter — see "The Details" above for the full implementation
String header = req.getHeader(HttpHeaders.AUTHORIZATION);
if (header == null || !header.startsWith("Bearer ")) { chain.doFilter(req, res); return; }
JwtPrincipal p = jwt.verify(header.substring(7));
User u = userCache.get(p.userId(), id -> users.findById(id).orElseThrow());
SecurityContextHolder.getContext().setAuthentication(
    new JwtAuthenticationToken(p, header.substring(7),
        List.of(new SimpleGrantedAuthority("ROLE_" + u.role().name()))));
chain.doFilter(req, res);
```

**Express (Delta) — full implementation in [[13.02.03. Translation Express TypeScript Middleware]]:**
```typescript
// auth.middleware.ts
export const authenticate = (req: Request, _res: Response, next: NextFunction) => {
  const header = req.header("authorization") ?? "";
  if (!header.startsWith("Bearer ")) { return next(); }
  try {
    const claims = jwt.verify(header.slice(7), process.env.JWT_SECRET!) as JwtClaims;
    const user   = userCache.get(claims.sub) ?? await loadUser(claims.sub);
    (req as AuthedRequest).user = user;
    next();
  } catch (e) { next(); }   //  anonymous; route-level check returns 401
};
```

**Django (Delta) — full implementation in [[13.02.04. Translation Python Django Middleware]]:**
```python
# middleware.py
class JwtAuthMiddleware:
    def __call__(self, request):
        header = request.headers.get("Authorization", "")
        if header.startswith("Bearer "):
            try:
                payload = jwt.decode(header[7:], settings.JWT_SECRET,
                                     algorithms=["HS256"])
                request.user = user_cache.get(payload["sub"]) or load_user(payload["sub"])
            except jwt.InvalidTokenError:
                request.user = AnonymousUser()
        return self.get_response(request)
```

**Laravel (Delta) — full implementation in [[13.02.05. Translation PHP Laravel Middleware]]:**
```php
// app/Http/Middleware/JwtAuth.php
public function handle(Request $req, Closure $next) {
    $header = $req->header('Authorization', '');
    if (str_starts_with($header, 'Bearer ')) {
        try {
            $claims = JWT::decode(substr($header, 7),
                new Key(env('JWT_SECRET'), 'HS256'));
            $req->setUserResolver(fn() =>
                Cache::remember("user.{$claims->sub}", 60, fn() =>
                    User::findOrFail($claims->sub)));
        } catch (Throwable) { /* anonymous */ }
    }
    return $next($req);
}
```

The structural lesson from the side-by-side: Spring Boot's `SecurityContextHolder` is a `ThreadLocal` that requires explicit cleanup, while the other three attach the principal to the request object directly. The thread-local approach is what makes `@PreAuthorize` work on any method in any bean (the proxy reads from the thread-local); the request-object approach requires explicit plumbing of `req.user` through every function call. Spring's approach is more flexible but more magical; the deltas' approach is more verbose but more debuggable. Neither is universally better — they trade magic for debuggability.

## Break It

> [!danger] Load-test failure modes you must reproduce
> Do not move on to the delta translations until you have personally reproduced each of the following in your anchor implementation:
>
> 1. **Starve it.** Drop a load test (wrk, k6, ab) at 10x expected throughput. Watch the thread pool, connection pool, or event loop saturate. Capture the metric that proves the saturation. For Spring Boot specifically: disable the `userCache` (comment out the `Caffeine` lookup so every request hits Postgres), ramp k6 to 5 000 VUs against `GET /orgs/{id}`, and watch HikariCP's `connections.pending` metric spike from 0 to 80+. Capture the actuator graph. Then re-enable the cache and watch it drop back to 0.
> 2. **Leak it.** Comment out the `finally { MDC.clear(); }` in `TraceContextFilter` and the `finally { SecurityContextHolder.clearContext(); }` in `JwtAuthenticationFilter`. Run the load test for 10 minutes. Heap usage climbs steadily as the `ThreadLocal` map on each Tomcat worker thread accumulates orphaned `SecurityContext` and MDC maps. Capture the `jmap -histo:live` output showing `ThreadLocalMap$Entry[]` as a top-10 heap consumer. Restore the cleanup; the graph should flatten.
> 3. **Race it.** Write a test that issues one refresh token, then concurrently calls `POST /auth/refresh` with that token from 10 threads (use `CountDownLatch` to synchronise the start). Without `SELECT FOR UPDATE` + `REPEATABLE_READ`, both threads succeed and you get two new refresh tokens, both valid, both in different families — the reuse-detection logic is bypassed. Capture the test failure. Add the `SELECT FOR UPDATE` and the test should pass (one thread gets 200, the other gets 401 reuse-detected).
> 4. **Fix it.** Restore the cleanup, add the `SELECT FOR UPDATE`, re-enable the cache, and re-run the load test. All four metrics (HikariCP pending, heap growth, refresh-token reuse, p99 latency) should be green. Keep both before/after graphs — they are the proof you completed the milestone.

## Profiling Hooks

While the load test runs, collect:

- **JVM**: `jstack <pid>` for thread dumps; `jmap -dump:live,format=b,file=heap.hprof <pid>` for heap dumps; `jstat -gcutil <pid> 1000` for GC pressure.
- **OS**: `pidstat -d -r -u -w 1`, `vmstat 1`, `ss -tan state established | wc -l`.
- **App**: `/actuator/metrics/*` and `/actuator/threaddump`.

The specific metrics to watch for this milestone are: `hikaricp_connections_pending` (pool exhaustion), `cache_gets_total{result="hit",cache="userCache"}` vs `{result="miss"}` (cache effectiveness), `http_server_requests_seconds{status="401"}` (auth failure rate — should be <1 % under normal load), `http_server_requests_seconds_max` (p99 — should be <100 ms at 5 000 RPS), and `jdbc_connections_active` (DB pool utilisation — should be <80 % of `maximumPoolSize`). For the refresh-token race, watch `pg_locks` for the `refresh_tokens` table during the test — if you see `AccessExclusiveLock` you have a problem (your `SELECT FOR UPDATE` is escalating to a table lock, which means you are missing the index on `token_hash`).
