# 13.00. Map of Content: Practical Projects

## Overview

This section covers **13. Practical Transfer Projects and Capstones**. It is part of the unified backend engineering vault described in [[00.01. Master Architectural Mental Model]]. The notes below are organized by concept, not by framework. Each concept is taught once at the conceptual level, then implemented deeply in the Spring Boot anchor stack, then rapidly translated into Express, Django, Flask, and Laravel as deltas.

Section 13 is the capstone. Sections 00 through 12 teach individual layers of the backend stack in isolation: the kernel, the network, the runtime, the framework, the database, the message broker, the orchestrator. Section 13 forces you to assemble those layers into a single shipping system and survive the consequences. Every milestone here is structured the same way: a specification note (`XX.01`) fixes the contract, an anchor implementation note (`XX.02`) builds the reference in Spring Boot with real load-test failure modes, three translation notes (`XX.03` / `XX.04` / `XX.05`) reproduce the contract in Express, Django, and Laravel, and a post-mortem note (`XX.06`) records the metric tables, the failure-mode observations, and the engineering trade-offs that survived the load test. You are not done with a milestone until the post-mortem is filled in with concrete numbers — a milestone that ships without a captured failure graph is a tutorial, not a milestone.

The milestones are deliberately ordered by the failure surface they expose. Milestone 1 covers the synchronous request/response path that every backend engineer must internalise first. Milestone 2 layers cross-cutting concerns (authentication, tracing, structured logging) onto that path. Milestone 3 introduces contention and the ACID guarantee. Milestone 4 breaks the synchronous assumption with event-driven flow. Milestone 5 packages everything for production deployment and observability. Milestone 6 re-implements the same business contract under the radically different constraints of serverless execution. Each milestone assumes you have the scars from the previous one — if you skip ahead, the failure modes will not make sense.

### 13.01. Project Milestone 1 - The Universal HTTP API

- [[13.01.01. System Specification]] — Build an enterprise Organization and Membership REST API. The spec fixes the contract: eight endpoints (CRUD on `/orgs` plus member sub-resource), RFC 7807 ProblemDetail error bodies, the `ADMIN`/`MEMBER`/`VIEWER` role enum, the 1-100 character org-name validation, and the full status-code matrix (200/201/204/400/401/403/404/409/422/500). Architecture sketch, API contract table, and acceptance criteria live here.
- [[13.01.02. Anchor Implementation Spring Boot]] — The reference implementation. Full `pom.xml` (Spring Boot 3.3 + Spring Data JPA + Hibernate + HikariCP + PostgreSQL driver + validation starter + actuator), `Organization` and `Member` JPA entities, `OrganizationController`, `OrganizationService` with `@Transactional` boundaries, `OrganizationRepository extends JpaRepository`, `GlobalExceptionHandler` with `@ControllerAdvice` emitting ProblemDetail, `application.yml` with HikariCP pool sizing, and `docker-compose.yml` for local Postgres. Includes the four failure-mode load tests: starve HikariCP, leak connections, race on concurrent member add, fix and re-test.
- [[13.01.03. Translation Express TypeScript]] — The Node.js translation. `package.json` with Express 4 + Zod + Prisma + TypeScript 5, `tsconfig.json` with strict mode, `src/index.ts` entry, `src/routes/orgs.ts` router, `src/services/orgService.ts` service layer, `src/db.ts` Prisma client singleton, `prisma/schema.prisma` with the same two models, and the `tsx watch` dev command vs `tsc && node dist/index.js` prod build. Includes the Delta from Spring Boot analysis (Zod replaces Bean Validation, Prisma replaces JPA, the event loop replaces Tomcat's thread-per-request).
- [[13.01.04. Translation Python Django]] — The Python translation built on Django REST Framework. `pyproject.toml`, `manage.py`, `myproject/settings.py` with DATABASES pointing at Postgres, `orgs/models.py` (`Organization`, `Member` with role choices), `orgs/serializers.py` (DRF ModelSerializer with field-level validation), `orgs/views.py` (DRF ModelViewSet with `@action` for member sub-resource), `orgs/urls.py` wired through DRF DefaultRouter. Includes the makemigrations + migrate + runserver loop, the pytest test command, and the Delta from Spring Boot analysis.
- [[13.01.05. Translation PHP Laravel]] — The PHP translation built on Laravel 11. `composer.json`, `bootstrap/app.php` with routing config, `app/Http/Controllers/OrgController.php` with form requests, `app/Models/Organization.php` and `app/Models/Member.php` Eloquent models with `BelongsToMany` polymorphic membership, `routes/api.php` resource routes, `database/migrations/xxxx_create_orgs_table.php` and `database/factories/OrganizationFactory.php`. Includes `php artisan serve`, `php artisan test`, and the Delta from Spring Boot analysis (Form Requests replace `@Valid`, Eloquent replaces JPA, the PHP-FPM worker model replaces Tomcat threads).
- [[13.01.06. Architectural Comparison and Post-Mortem]] — Side-by-side comparison of the four implementations across request latency at p50/p95/p99, requests-per-second at saturation, cold-start time, lines of code, memory footprint, and the specific failure mode each ecosystem hit first under `wrk`. Includes the resolution table: which fix was applied where, and which fix was impossible without re-architecting.

### 13.02. Project Milestone 2 - Middleware Interceptors and Auth

- [[13.02.01. System Specification]] — Secure the Organization API with JWT authentication, role-based authorization (RBAC), distributed tracing headers, and a request-scoped correlation ID propagated end-to-end through the middleware chain.
- [[13.02.02. Anchor Implementation Spring Security]] — The reference implementation in Spring Security 6: `SecurityFilterChain` bean with stateless JWT, custom `OncePerRequestFilter` for the JWT decoder, `@PreAuthorize` method security with role expressions, the `MDC`-based correlation ID filter, and the thread-local handoff to `@Async` executors. Break-It tests: token replay, missing role on a sensitive endpoint, slow filter blocking the chain.
- [[13.02.03. Translation Express TypeScript Middleware]] — Express middleware chain with `jsonwebtoken`, a custom `authMiddleware` that decorates `req.user`, and the `correlationId` middleware that reads `X-Request-Id` or generates a UUID v4. Shows the explicit `next(err)` propagation that replaces Spring's `HandlerExceptionResolver`.
- [[13.02.04. Translation Python Django Middleware]] — DRF permission classes (`IsAuthenticated`, custom `IsOrgAdmin`), Django middleware for correlation ID, and the `@action(permission_classes=[IsOrgAdmin])` decorator. Shows how DRF's permission chain composes vs Spring Security's filter chain.
- [[13.02.05. Translation PHP Laravel Middleware]] — Laravel HTTP middleware (`auth:api`, custom `role:admin` middleware alias), the `$request->user()` resolver, and the `LogContext` shared state. Shows the PHP-FPM-per-request isolation that makes thread-local correlation unnecessary.
- [[13.02.06. Architectural Comparison and Post-Mortem]] — Latency overhead of each middleware chain, JWT verification cost comparison, and the production incident where a misconfigured filter order caused a 30% latency regression.

### 13.03. Project Milestone 3 - Financial Ledger and ACID Locking

- [[13.03.01. System Specification]] — Implement a high-concurrency double-entry Financial Ledger balance transfer service. Every transfer debits one account and credits another inside a single ACID transaction; the spec fixes the isolation level (`SERIALIZABLE` for the transfer, `READ COMMITTED` for balance reads), the `SELECT ... FOR UPDATE` row-locking strategy, and the idempotency-key contract.
- [[13.03.02. Anchor Implementation Spring Boot and PostgreSQL]] — Spring Boot + Spring Data JPA with explicit `EntityManager` lock modes (`LockModeType.PESSIMISTIC_WRITE`), the `@Transactional(isolation = Isolation.SERIALIZABLE)` boundary, and the deadlock retry interceptor. The Break-It suite forces a real deadlock between two transfer workers and captures the `SQLSTATE 40P01` from PostgreSQL.
- [[13.03.03. Translation Express and Prisma]] — Prisma's `$transaction` serial callback with `SELECT FOR UPDATE` via raw SQL, since Prisma's type-safe client does not yet expose row-level locks. Shows the impedance mismatch between ORM ergonomics and pessimistic locking.
- [[13.03.04. Translation Django ORM]] — Django's `transaction.atomic()` block with `select_for_update()` on the queryset, the `transaction.on_commit()` hook for the audit-log write, and the `IntegrityError` retry decorator. Shows how Django exposes the same Postgres primitives through a Pythonic API.
- [[13.03.05. Translation Laravel Eloquent]] — Laravel's `DB::transaction()` closure with `lockForUpdate()` on the Eloquent query builder, the `retry()` helper for deadlock backoff, and the `WithoutOverlapping` middleware for job-level locking. Shows how Laravel's fluent API hides the SQL but exposes the same Postgres locks.
- [[13.03.06. Concurrency Load Test Suite and Deadlock Analysis]] — A `k6` script that spawns 200 concurrent transfer workers against a 10-account pool, the deadlock log parser, and the metric table showing throughput collapse at `SERIALIZABLE` vs `READ COMMITTED` vs `REPEATABLE READ`.

### 13.04. Project Milestone 4 - Event-Driven Order Pipeline with Kafka

- [[13.04.01. System Specification]] — Build an asynchronous E-Commerce checkout pipeline utilizing the Transactional Outbox pattern. Orders are written transactionally with outbox events; a Debezium connector streams events to Kafka; downstream consumers (analytics, real-time dashboard, invoice worker) subscribe to the `orders.created` topic with different consumer groups.
- [[13.04.02. Primary Engine Spring Boot Producer and Debezium CDC]] — Spring Boot with the outbox table, `KafkaTemplate` for direct fallback publishing, Debezium source connector config in `register-postgres.json`, and the schema-registry integration. The anchor implementation produces the events that the three downstream consumers read.
- [[13.04.03. Analytics Consumer Python with confluent-kafka]] — Python consumer using `confluent-kafka` (librdkafka bindings) with manual commit, the `on_commit` callback for exactly-once-ish semantics, and the backpressure-aware `consume()` loop. Shows how a non-JVM client joins a Kafka cluster.
- [[13.04.04. Real-Time WebSocket Broadcaster Node.js with KafkaJS]] — Node.js service using `kafkajs` to consume `orders.created`, transform each event into a WebSocket frame, and broadcast to connected dashboard clients. Shows the event-loop-aware consumer that batches `consume()` calls to amortise the librdkafka overhead.
- [[13.04.05. Invoice Generator Worker PHP Laravel Queue]] — Laravel queue worker pulling `orders.created` events off an internal Redis queue (fed by a Kafka-to-Redis bridge) and generating PDF invoices via the `dompdf` package. Shows how PHP's request/execution model forces a queue-and-worker pattern instead of a long-lived consumer.
- [[13.04.06. Failure Injection and Rebalance Resilience Verification]] — A test harness that kills consumers mid-rebalance, injects poison messages, and verifies the `__consumer_offsets` topic compaction behaviour under partition reassignment.

### 13.05. Project Milestone 5 - Distributed Tracing and Docker Deployment

- [[13.05.01. System Specification]] — Package the entire multi-language system into production-grade multi-stage container images. The spec fixes the image layering contract (builder image, runtime image, distroless base), the OpenTelemetry trace-context propagation requirement, and the Prometheus + Grafana observability stack.
- [[13.05.02. Production Docker Compose and Multi-Stage Dockerfiles]] — One multi-stage Dockerfile per service (Spring Boot, Express, Django, Laravel, all four consumers) plus the `docker-compose.yml` wiring them together with healthchecks, dependency ordering, and named volumes for Postgres / Kafka / Redis / OTel collector.
- [[13.05.03. Nginx Ingress Configuration and Upstream Buffering]] — Nginx reverse proxy with `proxy_buffering on`, `proxy_request_buffering on` for slow-client protection, and the upstream keepalive pool. Shows the production pattern that prevents slowloris-style resource exhaustion at the application layer.
- [[13.05.04. OpenTelemetry Tracing Integration Across All Services]] — OTel SDK configuration in each ecosystem: Spring Boot's `otel-spring-boot-starter`, Node.js's `@opentelemetry/sdk-node`, Python's `opentelemetry-distro`, PHP's `opentelemetry-instrumentation-auto`. All services export to the same Jaeger instance and propagate the W3C `traceparent` header.
- [[13.05.05. Prometheus Scraping and Grafana Dashboard Setup]] — Prometheus scrape configs with relabelling rules, the four Grafana dashboards (RED metrics per service, JVM heap, Postgres connections, Kafka consumer lag), and the alerting rules wired through Alertmanager.

### 13.06. Project Milestone 6 - Serverless Migration and BaaS Comparison

- [[13.06.01. System Specification]] — Re-implement the Organization and Membership core API using Serverless Edge Functions and BaaS. The spec fixes the cold-start budget (< 200 ms at the edge), the per-request cost ceiling, and the constraint that no server-side long-lived process is allowed.
- [[13.06.02. Implementation Vercel Serverless and Edge Functions]] — Vercel Edge Functions running on V8 isolates (Cloudflare Workers under the hood), Postgres accessed through Prisma Data Proxy, and the `export const config = { runtime: 'edge' }` declaration. Shows the cold-start characteristics and the WebCrypto API replacing Node's `crypto`.
- [[13.06.03. Implementation Supabase PostgreSQL and Row-Level Security]] — Supabase as the BaaS layer: Postgres RLS policies that enforce org membership at the database level, the Supabase JS client as the data access layer, and Edge Functions for the small amount of business logic that cannot live in RLS policies.
- [[13.06.04. Implementation Firebase Cloud Functions and Firestore]] — Firebase Cloud Functions (Node.js runtime) backed by Firestore's NoSQL document model. Shows the impedance mismatch between the original relational schema and Firestore's sub-collection model, plus the eventual-consistency tradeoff of Firestore's multi-region replication.
- [[13.06.05. Architectural Benchmarks and Final Engineering Assessment]] — Final benchmark table: cost per million requests, p99 latency, cold-start distribution, and the engineering trade-off matrix (relational vs document, self-managed vs BaaS, stateful vs serverless). The closing note that ties the entire vault back to the [[00.01. Master Architectural Mental Model]].

## Conceptual Roadmap

The six milestones are not independent. They form a dependency chain where each milestone introduces a new failure surface that the next milestone must tame:

```
M1 HTTP API ──▶ M2 Middleware+Auth ──▶ M3 ACID/Locking
      │                                      │
      │                                      ▼
      │                                 M4 Event-driven Kafka
      │                                      │
      ▼                                      ▼
M5 Tracing + Docker ◀──────────── M4 → M5 (containers + traces)
      │
      ▼
M6 Serverless / BaaS (re-implement M1's contract under new constraints)
```

**Milestone 1 (HTTP API)** establishes the baseline contract: a synchronous REST API over HTTP with strict DTO validation and a structured error format. Every subsequent milestone reuses this contract. Milestone 2 layers auth on top of it. Milestone 3 wraps parts of it in transactions. Milestone 4 splits it into async pieces. Milestone 6 re-implements it under a radically different execution model. If you skip Milestone 1, none of the later milestones have a stable target to extend.

**Milestone 2 (Middleware + Auth)** layers cross-cutting concerns onto the synchronous path. JWT verification, RBAC, and correlation IDs are introduced as a filter/interceptor chain that runs before the controller. This is where you first encounter the trade-off between filter chain depth (more security checks) and per-request latency. The scars from Milestone 2 — a filter that calls the database on every request, a misordered chain that lets an unauthenticated request through to a `@PreAuthorize`d method — directly inform Milestone 5's observability stack, because you need distributed tracing to debug a chain that crosses five filters.

**Milestone 3 (ACID/Locking)** breaks the synchronous-request-isolation assumption. Until now, each request was independent. Now two concurrent transfers contend on the same row, and you must choose between `READ COMMITTED` + `SELECT FOR UPDATE`, `REPEATABLE READ`, and `SERIALIZABLE`. The Break-It suite forces a real PostgreSQL deadlock (`SQLSTATE 40P01`) and teaches you to design retry logic that is idempotent at the application layer. The idempotency-key pattern from Milestone 3 is reused in Milestone 4's outbox consumer.

**Milestone 4 (Event-driven Kafka)** breaks the synchronous-request assumption entirely. The Order API writes to a transactional outbox table inside the same database transaction as the order; a Debezium connector streams the outbox rows to Kafka; downstream consumers (analytics in Python, WebSocket broadcaster in Node, invoice worker in PHP) process the events asynchronously. The failure mode shifts from "request timed out" to "consumer lag is growing" — a fundamentally different operational problem that requires the Prometheus + Grafana stack from Milestone 5 to even observe.

**Milestone 5 (Tracing + Docker)** packages everything from Milestones 1-4 into production-grade containers and wires up OpenTelemetry tracing across all of them. The trace context (W3C `traceparent` header) propagates from the Nginx ingress through the Spring Boot API, through the Kafka producer, into the Kafka consumer headers, and out to the PHP invoice worker. This is the milestone where you finally see the entire system as a single distributed call graph — and discover that the PHP invoice worker's 800 ms latency was hiding behind the synchronous 200 ms API response the whole time.

**Milestone 6 (Serverless / BaaS)** re-implements Milestone 1's contract under the radically different execution model of serverless edge functions. The cold-start budget, the per-request cost ceiling, and the inability to hold a long-lived database connection force a complete re-architecture: connection pooling via Prisma Data Proxy or Supabase's PgBouncer, business logic pushed into database RLS policies, and the eventual-consistency tradeoff of Firestore's multi-region replication. The point of Milestone 6 is not to replace Milestone 1 — it is to show that the same contract, under different runtime constraints, produces a fundamentally different system. The closing benchmark table in `13.06.05` is the final integration moment of the entire vault.
