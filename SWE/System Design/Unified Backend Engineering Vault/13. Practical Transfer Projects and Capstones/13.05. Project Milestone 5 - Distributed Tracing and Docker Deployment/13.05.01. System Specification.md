# 13.05.01. System Specification

## Project Goal

Milestones 1–4 built the four universal backend systems — HTTP API, middleware/auth, ACID ledger, and Kafka pipeline — as four separately runnable projects. Each had its own `docker compose up` invocation, its own port assignments, and its own ad-hoc logging format. That shape is fine for learning; it is unacceptable for production. Milestone 5 takes those four systems and **forges them into a single deployable unit**: one `docker compose up` brings up the entire platform behind one Nginx ingress, every service emits OpenTelemetry traces to a shared collector, and every service exposes Prometheus metrics scraped by a shared Prometheus instance whose dashboards live in a shared Grafana. The capstone is complete when you can read one Grafana panel, click through to one Jaeger trace, and follow a single user request as it hops from Nginx → Spring Boot order API → Postgres → Kafka → Python analytics consumer → Node WebSocket broadcaster → PHP invoice worker, all correlated by a single `trace_id`.

The deliverable is not a new application — there is no new business logic in this milestone. The deliverable is the **operating environment**: a `docker-compose.yml` that wires every service from Milestones 1–4 into one network with consistent observability hooks, a set of multi-stage Dockerfiles that produce slim production images per service, an `nginx.conf` that terminates TLS and routes by path prefix, an OTel Collector pipeline that accepts OTLP from every service and exports to Jaeger + Loki + Prometheus, a Prometheus scrape config that discovers every service's `/actuator/prometheus` or `/metrics` endpoint, and a Grafana dashboard JSON that visualises the order pipeline end-to-end. Each of those five artifacts gets its own implementation note ([[13.05.02]] through [[13.05.05]]); this note is the contract those implementations must satisfy.

You are done when you can: (1) `docker compose up --build` from a clean clone, (2) send `POST /api/orders` through Nginx on port 443 and observe it succeed end-to-end, (3) open Grafana at `http://localhost:3000` and see the order pipeline dashboard showing the request you just sent, (4) click the trace link in Grafana and land on a Jaeger trace showing eight spans across six services, (5) kill any one service with `docker compose kill` and watch the dashboard's health panel flip from green to red within 15 seconds. If any of those five steps fails, the milestone is not done — you have built a tutorial, not a deployable platform.

## Requirements

The four hard requirements below are non-negotiable. Each one names the artifact that satisfies it and the failure mode it is designed to prevent.

- **Package the entire multi-language system into production-grade multi-stage container images.** Every service ships in its own image, built by a multi-stage Dockerfile that compiles in a `builder` stage and copies only the runtime artifacts into a slim final stage. The final image must be ≤ 250 MB for JVM services (using `eclipse-temurin:21-jre-alpine`), ≤ 150 MB for Node services (using `node:20-alpine` + production deps only), ≤ 120 MB for Python services (using `python:3.12-slim` + multi-stage wheel build), and ≤ 200 MB for PHP services (using `php:8.3-fpm-alpine` + opcache preload). The failure mode this prevents is the 2 GB "builder image shipped to production" anti-pattern that exhausts disk on every node in a Kubernetes cluster within weeks of deployment. Satisfied by [[13.05.02. Production Docker Compose and Multi-Stage Dockerfiles]].

- **Configure an Nginx reverse proxy with SSL termination and path-based routing.** A single Nginx instance on ports 80 (redirect to 443) and 443 (TLS termination) routes by URL prefix: `/api/orders/*` → spring-order-service:8080, `/api/users/*` → spring-user-service:8080, `/api/ledger/*` → spring-ledger-service:8080, `/ws/*` → node-broadcaster:3000 (WebSocket upgrade), `/admin/*` → php-invoice-admin:80 (static + PHP-FPM). Nginx must enable upstream response buffering for the non-streaming endpoints (so a slow PHP backend does not hold an Nginx worker open for 30 s) and must disable buffering for the WebSocket upgrade (so frames are proxied byte-by-byte without buffering). The failure mode this prevents is the "every request to the slow PHP admin blocks a Tomcat thread" anti-pattern where one slow service cascades into total platform unavailability. Satisfied by [[13.05.03. Nginx Ingress Configuration and Upstream Buffering]].

- **Instrument the entire pipeline with OpenTelemetry context propagation (`traceparent`) verified via Jaeger.** Every inbound HTTP request — regardless of which service received it — must extract the W3C `traceparent` header from the incoming request, create a span as the child of that trace, and propagate the trace context to every outbound call (HTTP client, Postgres query, Kafka produce, Redis command). Every cross-service hop must appear as a child span of the parent trace in Jaeger, with the service.name resource attribute set correctly per service. The failure mode this prevents is the "five disconnected log streams from five services, no way to follow a single request" anti-pattern that turns every production incident into a forensic archaeology dig. Satisfied by [[13.05.04. OpenTelemetry Tracing Integration Across All Services]].

- **Scrape metrics from every service with Prometheus and visualise in Grafana.** Every service must expose a `/metrics` (or `/actuator/prometheus` for Spring Boot) endpoint in Prometheus text exposition format, scraped by a shared Prometheus instance at 15-second intervals. Grafana must provision one dashboard JSON for the order pipeline (showing end-to-end request rate, p50/p95/p99 latency, error rate, consumer lag, JVM/Node/PHP-FPM resource utilisation) and one for the Kafka pipeline (showing produce rate, consumer-lag-per-partition, rebalance events, DLT message count). The failure mode this prevents is the "we have logs but no graphs, so we cannot tell whether the system is healthy until a user complains" anti-pattern. Satisfied by [[13.05.05. Prometheus Scraping and Grafana Dashboard Setup]].

Each requirement is non-negotiable. If you skip one, you have completed a tutorial, not a milestone.

## Architecture Sketch

The platform topology is a hub-and-spoke: Nginx is the single ingress point; behind it sit seven application services (three Spring Boot, one Node, one Python, one PHP-FPM, one Laravel queue worker) plus four stateful services (Postgres, Kafka, Redis, MinIO for S3-compatible invoice storage) and three observability services (OTel Collector, Prometheus, Grafana, Jaeger). All fifteen containers sit on a single `appnet` Docker bridge network; only Nginx (443), Grafana (3000), Jaeger (16686), and Prometheus (9090) publish ports to the host.

The key topological decisions encoded in this sketch are: (1) **no service publishes a port to the host except Nginx and the three observability tools** — every inter-service call stays on the Docker bridge network, which means TLS between services is unnecessary (the network is trusted) and DNS resolution is automatic (Docker Compose service names resolve via the embedded DNS at 127.0.0.11); (2) **the OTel Collector is the single observability ingress** — services emit OTLP to the collector, and the collector fans out to Jaeger (traces), Loki (logs), and Prometheus (metrics via the collector's `prometheus_remote_write` exporter, or services expose `/metrics` directly and Prometheus scrapes them, which is the simpler pattern used here); (3) **stateful services have no sidecars** — Postgres, Kafka, Redis, and MinIO run as plain containers with named volumes, and their metrics are exposed by separate `*_exporter` sidecar containers rather than embedded in the stateful process (Postgres does not have a built-in Prometheus endpoint, Kafka ships one but it is incomplete, so we run the canonical exporters).

## Observability Contract

The observability contract is what every service in the platform must implement to participate in the shared traces, metrics, and logs. The contract has three layers — traces, metrics, logs — and every service must satisfy all three. Services that do not satisfy the contract are visible in Grafana as "missing panels" and in Jaeger as "broken trace chains"; their absence is the signal that instrumentation is incomplete.

**Trace propagation contract.** Every inbound HTTP request handler must extract the W3C `traceparent` header (`version-trace_id-parent_id-trace_flags`, e.g. `00-0af7651916cd43dd8448eb211c80319c-b7ad6b7169203331-01`) and start a server span as the child of the extracted trace context. If no `traceparent` header is present (the request originated from outside the platform, e.g. a user's browser), the service must generate a new trace context and start a root server span. Every outbound call — HTTP client, Postgres query, Kafka produce, Redis command, MinIO put-object — must be wrapped in a client span whose parent is the inbound server span, and the outbound call must inject the current trace context into the protocol's propagation channel (HTTP header for HTTP, Kafka header for Kafka, connection-level for Postgres via the `pg_tracing` extension or the OTel-JDBC wrapper). The result in Jaeger is a single trace with N spans per service hop; clicking any span shows the service.name, the operation name, the duration, and any span attributes (HTTP method, status code, Kafka topic, partition, offset).

| Service | OTel SDK | Auto-instrumentation package | Manual spans required |
| --- | --- | --- | --- |
| Spring Boot order / user / ledger | `io.opentelemetry:opentelemetry-spring-boot-starter` | `opentelemetry-spring-boot-starter` (auto-instruments Spring MVC, Tomcat, JDBC, Kafka client, Redis Lettuce) | None for HTTP/JDBC/Kafka; manual `@WithSpan` for business-logic spans (e.g. `OrderService.placeOrder`) |
| Node broadcaster | `@opentelemetry/sdk-node` | `@opentelemetry/auto-instrumentations-node` (auto-instruments Express, HTTP, KafkaJS via `@opentelemetry/instrumentation-kafkajs`, `ioredis`, `pg`) | None for HTTP/Kafka/Redis; manual `tracer.startActiveSpan('broadcast-to-clients')` for the WebSocket fan-out |
| Python analytics | `opentelemetry-distro` + `opentelemetry-instrumentation-confluent-kafka`, `-postgresql`, `-requests` | `opentelemetry-instrument` CLI auto-instruments at import time | None for Kafka/Postgres; manual `tracer.start_as_current_span('aggregate-rollup')` for the rollup computation |
| PHP invoice | `open-telemetry/sdk` + `open-telemetry/opentelemetry-auto-slim` (or Laravel auto-instrumentation) | Composer package auto-instruments Slim routes, PDO, Laravel Queue, Guzzle | None for HTTP/PDO/Queue; manual `Span::setCurrent('render-invoice-pdf')` for the DOMPDF render |

**Metrics contract.** Every service must expose a `/metrics` (or `/actuator/prometheus` for Spring Boot) endpoint in Prometheus text exposition format, returning 200 with `Content-Type: text/plain; version=0.0.4; charset=utf-8`. The minimum metric set per service is: `http_server_duration_seconds` (histogram, labels `http_method`, `http_route`, `http_status_code`), `http_server_request_count` (counter, same labels), `process_resident_memory_bytes` (gauge), `process_cpu_seconds_total` (counter). Spring Boot services get these automatically from micrometer-registry-prometheus; Node services use `prom-client` with the `defaultMetrics` collector; Python services use `prometheus_client`'s `generate_latest` plus `CONTENT_TYPE_LATEST`; PHP services use `prometheus/client_php`'s `RenderTextFormat`. The Prometheus scrape config must include every service's `/metrics` endpoint plus the four `*_exporter` endpoints (postgres_exporter:9187, kafka_exporter:9308, redis_exporter:9121, minio:9000 with `MINIO_PROMETHEUS_AUTH_TYPE=jwt`).

**Logs contract.** Every service must emit structured JSON logs to stdout, with the following fields on every log line: `timestamp` (ISO 8601 with milliseconds and timezone), `level` (one of `trace`, `debug`, `info`, `warn`, `error`, `fatal`), `service.name` (matching the OTel resource attribute), `trace.id` and `span.id` (extracted from the OTel `Span.current()` context — this is the field that lets Loki correlate a log line to a Jaeger trace via `{trace_id="..."}` queries), `message` (the human-readable log line), plus arbitrary structured fields per log call. The OTel Collector's `filelog` receiver tails the Docker container logs (`/var/lib/docker/containers/*/*-json.log`) and exports to Loki; the trace.id field is automatically indexed by Loki so the "logs for this trace" query is `logs |= "trace_id=0af7651916cd43dd8448eb211c80319c"` or, with Loki 3.0's structured metadata, `{service_name="spring-order"} | trace_id="0af7651916cd43dd8448eb211c80319c"`.

**Dashboards required.** Two dashboards are non-negotiable deliverables: (1) **Order Pipeline Dashboard** — panels for end-to-end request rate, p50/p95/p99 latency per service, error rate per service, consumer-lag-per-partition, DLT message count, JVM/Node/PHP-FPM resource utilisation, and a "trace deep-link" panel that takes the `trace_id` from a clicked data point and links to `http://jaeger:16686/trace/<trace_id>`; (2) **Kafka Pipeline Dashboard** — panels for produce rate per topic, consumer-lag-per-partition per consumer group, rebalance events counter, broker ISR shrink/grow, broker disk usage, and broker network throughput. Both dashboards are provisioned as JSON in the Grafana container's `/etc/grafana/provisioning/dashboards/` directory; the JSON is committed to the project repo so it is version-controlled with the code.

## Acceptance Criteria

1. **All four target ecosystems implement the same observability contract.** Spring Boot, Node, Python, and PHP services all emit OTLP traces to the collector, expose `/metrics` in Prometheus format, and emit structured JSON logs with `trace.id`. The verification command is `curl http://localhost:16686/api/services` returning a JSON list with all seven service names; `curl http://localhost:9090/api/v1/targets` returning all scrape targets in the `up` state; and `docker compose logs spring-order | jq .trace.id | head -1` returning a non-null value.
2. **All four pass the same automated test suite (k6, pytest, or Postman).** The k6 load test sends 1000 `POST /api/orders` requests through Nginx over 60 seconds; the test passes if the p99 latency is ≤ 500 ms, the error rate is ≤ 0.1 %, and every request's `trace_id` (returned in the `X-Trace-Id` response header by Nginx) appears in Jaeger with ≥ 6 spans.
3. **At least one ecosystem is load-tested to failure, with a captured metric showing the failure and the fix.** The k6 test is rerun with `--vus 500 --duration 5m` to drive the platform to its throughput ceiling; the failure mode (typically PHP-FPM worker pool exhaustion, Kafka producer backpressure, or Postgres connection-pool exhaustion) is captured in a Grafana screenshot, the fix (tune `pm.max_children`, `max.in.flight.requests.per.connection`, or HikariCP `maximumPoolSize`) is applied, and the post-failure rerun shows the metric returning to baseline.
4. **The post-mortem note is filled in.** [[13.04.06. Failure Injection and Rebalance Resilience Verification]] style: every chaos scenario from the Resilience Verification Matrix has measured numbers, every threshold violation has a written root-cause-and-fix entry, and the comparison matrix across the four ecosystems is populated with measured values rather than placeholder `_fill_` cells.

## Deliverables

- **Source code for each ecosystem in a separate subfolder.** Repo layout: `services/spring-order/`, `services/spring-user/`, `services/spring-ledger/`, `services/node-broadcaster/`, `services/python-analytics/`, `services/php-invoice/`. Each subfolder contains its own Dockerfile, source, tests, and a `README.md` with run instructions specific to that service.
- **A `docker-compose.yml` at the project root.** Declares all 15 containers (7 app + 4 stateful + 3 observability + 1 nginx) on a single `appnet` network with named volumes for stateful services. See [[13.05.02. Production Docker Compose and Multi-Stage Dockerfiles]].
- **An `nginx/` directory with `nginx.conf` and TLS certificates.** Self-signed certs generated by `openssl req -x509 -newkey rsa:2048 -keyout nginx.key -out nginx.crt -days 365 -nodes -subj "/CN=localhost"` for local; Let's Encrypt for staging. See [[13.05.03. Nginx Ingress Configuration and Upstream Buffering]].
- **An `otel-collector/` directory with `otel-collector-config.yaml`.** Declares the OTLP receiver, the Jaeger/Loki/Prometheus exporters, and the trace/metric/log pipelines. See [[13.05.04. OpenTelemetry Tracing Integration Across All Services]].
- **A `prometheus/` directory with `prometheus.yml` and a `grafana/` directory with `dashboards/` JSON and `provisioning/` YAML.** See [[13.05.05. Prometheus Scraping and Grafana Dashboard Setup]].
- **A `README.md` with run instructions and a load-test screenshot.** The README's first 30 lines must be enough for a fresh clone to `docker compose up --build` and have a working platform in under 5 minutes on a machine with 16 GB RAM.
- **A post-mortem note in this folder.** Currently this milestone folder has no `13.05.06. Architectural Comparison and Post-Mortem.md`; the post-mortem is folded into the acceptance criteria above and into the failure-injection observations in [[13.04.06. Failure Injection and Rebalance Resilience Verification]].
