# 13.05.03. Nginx Ingress Configuration and Upstream Buffering

## Scope

This note is the single point of ingress for the entire Milestone 5 platform. Every byte that enters or leaves the platform crosses Nginx — TLS terminates here, requests are routed by URL prefix to one of five upstream service groups, WebSocket upgrades are passed through to the Node broadcaster, slow upstream responses are buffered to disk so a wedged PHP-FPM worker cannot hold an Nginx worker thread open for 30 seconds, and per-route rate limits prevent one noisy client from starving everyone else. The `nginx.conf` below is the complete reference implementation; it is mounted into the `nginx` container at `/etc/nginx/nginx.conf` by the compose file in [[13.05.02. Production Docker Compose and Multi-Stage Dockerfiles]] and reloaded with `docker compose exec nginx nginx -s reload` after every edit (Nginx validates the config with `nginx -t` first, refusing to reload if the config is broken, so a bad edit cannot take the platform down).

The Nginx here is configured as a **layer-7 reverse proxy**, not a load balancer in the LVS/HAProxy sense — every connection terminates at Nginx and a fresh connection is opened to the upstream. This is the correct shape for a single-host Docker Compose deployment where every upstream is a single container; the `upstream` blocks declare one server each, but the syntax scales to N rows when the deployment grows to a Swarm or Kubernetes cluster (each upstream becomes multiple `server` lines, and Nginx's default round-robin load balancing takes over). The reference implementation does not use `ngx_http_upstream_keepalive` for connection pooling to the upstreams — that is left as an exercise because it requires the upstream to support HTTP/1.1 keep-alive (Spring Boot does by default, PHP-FPM does not, Node does, Python's uvicorn does), and the configuration is per-upstream rather than global.

## What You Are Building

The deliverable is one `nginx.conf` file (below) plus a directory of TLS certificates. The Nginx container listens on host ports 80 (HTTP, permanent redirect to 443) and 443 (HTTPS, TLS termination + reverse proxy + WebSocket upgrade). The routing table is:

| URL prefix | Upstream | Backend port | Protocol | Buffering | Timeout |
| --- | --- | --- | --- | --- | --- |
| `/api/orders/*` | `spring-order` | 8080 | HTTP/1.1 | enabled | 30 s |
| `/api/users/*` | `spring-user` | 8080 | HTTP/1.1 | enabled | 30 s |
| `/api/ledger/*` | `spring-ledger` | 8080 | HTTP/1.1 | enabled | 30 s |
| `/ws/*` | `node-broadcaster` | 3000 | WebSocket | **disabled** | 3600 s |
| `/admin/*` | `php-invoice-admin` | 80 | HTTP/1.0 (PHP-FPM) | enabled | 60 s |
| `/health` | `spring-order` | 8080 | HTTP/1.1 | enabled | 5 s |
| `/grafana/*` | `grafana` | 3000 | HTTP/1.1 | enabled | 30 s |
| `/` | static | n/a | HTTP/1.1 | n/a | 5 s (404) |

The two non-obvious decisions encoded in this table are: (1) **WebSocket gets its own routing rule with buffering disabled** — Nginx's default behaviour is to buffer upstream responses to disk, which is correct for HTTP but breaks WebSocket because WebSocket frames must be proxied byte-by-byte the instant they arrive (a 5-second buffering delay on a price-tick stream is unacceptable); (2) **PHP-FPM gets a 60-second timeout instead of the 30-second default** — Laravel's invoice-rendering endpoint can take 15-20 seconds for a 200-page PDF, and a 30-second Nginx timeout would cut it off mid-render and leave orphaned `wkhtmltopdf` processes consuming memory on the PHP container.

## Implementation Steps

1. **Bootstrap.** Generate self-signed TLS certificates for local development: `openssl req -x509 -newkey rsa:2048 -keyout nginx/certs/nginx.key -out nginx/certs/nginx.crt -days 365 -nodes -subj "/CN=localhost"`. For staging, use Let's Encrypt via certbot in a sidecar container; for production, terminate TLS at the cloud load balancer (ALB, Cloud Load Balancing) and have Nginx listen on plain HTTP behind it.
2. **Wire dependencies.** The compose file in [[13.05.02]] mounts `./nginx/nginx.conf` and `./nginx/certs/` as read-only volumes into the nginx container. The Nginx image is the official `nginx:1.27-alpine` — no custom Nginx build is needed because every directive used below (`proxy_pass`, `proxy_buffering`, `proxy_http_version`, `limit_req`, `ssl_certificate`) ships in the standard image.
3. **Implement the contract.** The `nginx.conf` below defines one `http` block, one `upstream` per backend service, two `server` blocks (port 80 redirect, port 443 HTTPS), and one `location` per URL prefix. Each `location` block sets its own `proxy_read_timeout`, `proxy_buffering`, and `proxy_pass` to match the routing table above.
4. **Wire observability.** Nginx emits access logs in a structured JSON format (defined by the `log_format` directive) that the OTel Collector's `filelog` receiver tails and ships to Loki. Nginx also exposes a `/nginx_status` endpoint at `127.0.0.1:8080/nginx_status` (via the `stub_status` module) that a separate `nginx-exporter` sidecar can scrape — but for the Milestone 5 reference implementation we rely on Spring Boot's micrometer-registry-prometheus for HTTP metrics, and Nginx's own metrics are omitted because the application-level metrics already capture the same information (request rate, latency, error rate).
5. **Containerize.** The nginx container in the compose file is `nginx:1.27-alpine` with no custom Dockerfile — the config is mounted as a volume, so the only artifact is the `nginx.conf` file itself. This is the correct shape for a config-only container; building a custom Nginx image just to `COPY nginx.conf /etc/nginx/nginx.conf` adds a build step that breaks the "edit and reload" workflow.
6. **Test.** Validate the config with `docker compose exec nginx nginx -t` before every reload. Run `curl -sk https://localhost/health` to verify the route to spring-order. Run `curl -sk https://localhost/api/users/me` to verify the route to spring-user. Open `wss://localhost/ws/orders` in a browser to verify the WebSocket upgrade. Run `ab -n 1000 -c 50 https://localhost/api/orders/1234` to verify Nginx holds up under load (the p99 should be ≤ 100 ms for Nginx itself; anything higher is the upstream). Run `docker compose kill spring-order && curl -sk https://localhost/api/orders/1234` to verify Nginx returns a 502 Bad Gateway (not a hang) when the upstream is down — the `proxy_next_upstream off` default plus `proxy_connect_timeout 2s` is what produces the fast 502.

## The nginx.conf

The complete reference configuration. Save it as `nginx/nginx.conf` at the project root. The file has six sections: `main` (process model), `events` (connection model), `http` (defaults, logging, SSL, gzip, rate limiting), five `upstream` blocks, the port-80 redirect `server`, and the port-443 HTTPS `server` with seven `location` blocks.

```nginx
# nginx/nginx.conf — Milestone 5 ingress, single source of truth
# Validate with: docker compose exec nginx nginx -t
# Reload with:    docker compose exec nginx nginx -s reload

user  nginx;
worker_processes  auto;
worker_rlimit_nofile 65535;
pid /var/run/nginx.pid;

events {
    worker_connections  8192;
    multi_accept on;
    use epoll;
}

http {
    include       /etc/nginx/mime.types;
    default_type  application/octet-stream;

    # ─── structured JSON access log (tailable by OTel Collector filelog receiver) ──
    log_format json_combined escape=json
        '{'
            '"time":"$time_iso8601",'
            '"remote_addr":"$remote_addr",'
            '"request_method":"$request_method",'
            '"request_uri":"$request_uri",'
            '"server_name":"$server_name",'
            '"status":$status,'
            '"body_bytes_sent":$body_bytes_sent,'
            '"request_time":$request_time,'
            '"upstream_response_time":"$upstream_response_time",'
            '"upstream_addr":"$upstream_addr",'
            '"upstream_status":"$upstream_status",'
            '"http_referer":"$http_referer",'
            '"http_user_agent":"$http_user_agent",'
            '"trace_id":"$http_traceparent",'
            '"request_id":"$request_id"'
        '}';
    access_log /var/log/nginx/access.log json_combined;
    error_log  /var/log/nginx/error.log warn;

    sendfile        on;
    tcp_nopush      on;
    tcp_nodelay     on;
    keepalive_timeout  65;
    keepalive_requests 1000;
    client_max_body_size 25m;
    client_body_buffer_size 128k;
    large_client_header_buffers 4 8k;
    server_tokens off;

    # ─── gzip ────────────────────────────────────────────────────────────────
    gzip on;
    gzip_vary on;
    gzip_min_length 1024;
    gzip_proxied any;
    gzip_comp_level 4;
    gzip_types text/plain text/css application/json application/javascript application/xml application/xml+rss text/javascript image/svg+xml;

    # ─── rate-limit zones ────────────────────────────────────────────────────
    # 10 req/s per IP for the API, 5 req/s for admin (PHP-FPM cannot take more)
    limit_req_zone $binary_remote_addr zone=api_zone:10m rate=10r/s;
    limit_req_zone $binary_remote_addr zone=admin_zone:10m rate=5r/s;
    limit_req_zone $binary_remote_addr zone=auth_zone:10m rate=2r/s;
    limit_req_status 429;

    # ─── TLS defaults (modern, requires nginx 1.17+ and a modern client) ────
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:ECDHE-ECDSA-CHACHA20-POLY1305:ECDHE-RSA-CHACHA20-POLY1305;
    ssl_prefer_server_ciphers off;
    ssl_session_cache shared:SSL:50m;
    ssl_session_timeout 1d;
    ssl_session_tickets off;
    ssl_stapling on;
    ssl_stapling_verify on;
    resolver 127.0.0.11 valid=30s;  # Docker embedded DNS
    resolver_timeout 5s;

    # ─── proxy defaults (applied to every location unless overridden) ────────
    proxy_http_version 1.1;
    proxy_set_header Host              $host;
    proxy_set_header X-Real-IP         $remote_addr;
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Request-Id      $request_id;
    # Pass W3C traceparent through so OTel traces survive the proxy hop
    proxy_set_header traceparent       $http_traceparent;
    proxy_connect_timeout 2s;
    proxy_send_timeout    30s;
    proxy_read_timeout    30s;
    proxy_buffering       on;
    proxy_buffer_size     16k;
    proxy_buffers         16 16k;
    proxy_busy_buffers_size 32k;
    proxy_temp_file_write_size 128k;
    proxy_next_upstream   error timeout http_502 http_503 http_504;
    proxy_next_upstream_tries 2;

    # ─── upstreams (one per backend service) ─────────────────────────────────
    upstream spring_order {
        server spring-order:8080 max_fails=3 fail_timeout=10s;
        keepalive 32;
    }
    upstream spring_user {
        server spring-user:8080 max_fails=3 fail_timeout=10s;
        keepalive 32;
    }
    upstream spring_ledger {
        server spring-ledger:8080 max_fails=3 fail_timeout=10s;
        keepalive 32;
    }
    upstream node_broadcaster {
        server node-broadcaster:3000 max_fails=3 fail_timeout=10s;
        keepalive 16;
    }
    upstream php_invoice_admin {
        server php-invoice-admin:80 max_fails=2 fail_timeout=15s;
        # No keepalive — PHP-FPM is HTTP/1.0 by default
    }
    upstream grafana_ui {
        server grafana:3000 max_fails=3 fail_timeout=10s;
        keepalive 16;
    }

    # ─── port 80: permanent redirect to 443 ──────────────────────────────────
    server {
        listen 80 default_server;
        listen [::]:80 default_server;
        server_name _;
        return 301 https://$host$request_uri;
    }

    # ─── port 443: TLS termination + reverse proxy + WebSocket + rate limit ──
    server {
        listen 443 ssl;
        listen [::]:443 ssl;
        http2 on;
        server_name localhost;

        ssl_certificate     /etc/nginx/certs/nginx.crt;
        ssl_certificate_key /etc/nginx/certs/nginx.key;

        # Security headers
        add_header Strict-Transport-Security "max-age=63072000; includeSubDomains; preload" always;
        add_header X-Frame-Options "DENY" always;
        add_header X-Content-Type-Options "nosniff" always;
        add_header Referrer-Policy "no-referrer" always;

        # ─── /health → spring-order (fast, no rate limit, no buffering) ──────
        location = /health {
            proxy_pass http://spring_order/actuator/health;
            proxy_buffering off;
            access_log off;
        }

        # ─── /api/orders/* → spring-order (rate-limited, buffered) ───────────
        location /api/orders/ {
            limit_req zone=api_zone burst=20 nodelay;
            proxy_pass http://spring_order;
            proxy_read_timeout 30s;
            proxy_buffering on;
        }

        # ─── /api/users/* → spring-user ──────────────────────────────────────
        location /api/users/ {
            limit_req zone=api_zone burst=20 nodelay;
            proxy_pass http://spring_user;
            proxy_read_timeout 30s;
        }

        # ─── /api/users/login → stricter rate limit (auth endpoint) ──────────
        location = /api/users/login {
            limit_req zone=auth_zone burst=5 nodelay;
            proxy_pass http://spring_user;
            proxy_read_timeout 10s;
        }

        # ─── /api/ledger/* → spring-ledger ───────────────────────────────────
        location /api/ledger/ {
            limit_req zone=api_zone burst=20 nodelay;
            proxy_pass http://spring_ledger;
            proxy_read_timeout 30s;
        }

        # ─── /ws/* → node-broadcaster (WebSocket: buffering OFF, timeout 1h) ─
        location /ws/ {
            proxy_pass http://node_broadcaster;
            proxy_http_version 1.1;
            proxy_set_header Upgrade    $http_upgrade;
            proxy_set_header Connection "upgrade";
            proxy_buffering off;            # critical for WebSocket
            proxy_cache off;
            proxy_read_timeout 3600s;       # keep the upgrade alive for 1 hour
            proxy_send_timeout 3600s;
            # WebSockets bypass rate limiting — they are long-lived connections, not requests
            limit_req off;
        }

        # ─── /admin/* → php-invoice-admin (slow PHP-FPM, longer timeout) ─────
        location /admin/ {
            limit_req zone=admin_zone burst=10 nodelay;
            proxy_pass http://php_invoice_admin;
            proxy_read_timeout 60s;         # PDF render can take 15-20 s
            proxy_buffering on;             # buffer to disk so slow PHP doesn't pin an Nginx worker
            proxy_buffers 32 16k;
            proxy_busy_buffers_size 64k;
        }

        # ─── /grafana/* → Grafana UI (no rate limit, buffered) ───────────────
        location /grafana/ {
            proxy_pass http://grafana_ui/;
            proxy_read_timeout 30s;
            proxy_buffering on;
            # Grafana uses HTTP/1.1 keep-alive and long-poll for live dashboards
            proxy_set_header Connection "";
        }

        # ─── / → 404 (no public root) ────────────────────────────────────────
        location / {
            return 404;
        }
    }
}
```

### Reverse-proxy mechanics: the per-location directive layering

The `http` block at the top defines proxy defaults that apply to every `location` — `proxy_http_version 1.1`, `proxy_buffering on`, `proxy_connect_timeout 2s`, the `Host`/`X-Real-IP`/`X-Forwarded-For`/`X-Forwarded-Proto`/`X-Request-Id` headers, and the W3C `traceparent` pass-through. Each `location` block then overrides only the directives that need to differ: `/ws/` flips `proxy_buffering` to `off` and adds the `Upgrade`/`Connection: upgrade` headers required by the WebSocket handshake; `/admin/` extends `proxy_read_timeout` to 60 s and bumps the buffer sizes; `/health` disables buffering so the actuator health probe is not delayed by Nginx's buffer-fill wait; `/api/users/login` swaps the rate-limit zone from `api_zone` (10 r/s) to `auth_zone` (2 r/s) to prevent credential-stuffing attacks.

The directive layering is the part most engineers get wrong. A common mistake is to set `proxy_buffering off` globally "for debugging" and forget to turn it back on — every upstream response then streams directly to the client, which means a slow client can hold the upstream connection open for minutes, exhausting the upstream's connection pool. The correct pattern is to default `proxy_buffering on` (so Nginx reads the upstream response into memory/disk as fast as the upstream can produce it, then drains to the client at whatever speed the client supports), and disable it only for the routes that genuinely need streaming: WebSocket upgrades, server-sent events (`text/event-stream`), and large file downloads where you want the client to receive bytes as the upstream produces them (e.g. video streaming).

### Load balancing: the upstream block and the keepalive pool

Each `upstream` block declares one or more `server` lines plus an optional `keepalive` directive. The `server spring-order:8080 max_fails=3 fail_timeout=10s` directive tells Nginx to mark the server as down after 3 failed connection attempts within 10 seconds — once marked down, Nginx stops sending traffic to it for `fail_timeout` seconds, then probes with one request to see if it has recovered. In a single-host Docker Compose deployment there is only one server per upstream, so a failed server means 502 Bad Gateway to the client — but the syntax scales to multi-server upstreams without changes, which is the value of using `upstream` blocks instead of bare `proxy_pass http://spring-order:8080`.

The `keepalive 32` directive opens a pool of 32 idle TCP connections to the upstream and reuses them for subsequent HTTP requests (HTTP/1.1 keep-alive). Without it, every `proxy_pass` opens a fresh TCP connection (3-way handshake) and closes it after the response — at 1 000 requests/second to spring-order, that is 1 000 TCP handshakes/second, which adds 1-2 ms of latency per request and burns ephemeral ports on both sides. The keepalive pool eliminates the handshake: the first request opens the connection, the next 1 000 requests reuse it, and the connection is only closed when it has been idle for `keepalive_timeout` (default 65 s). The catch is that the upstream must support HTTP/1.1 keep-alive — Spring Boot (Tomcat) does by default, Node (Express) does, Python (uvicorn) does, but PHP-FPM does not (it speaks HTTP/1.0 or FastCGI, not HTTP/1.1), which is why the `php_invoice_admin` upstream has no `keepalive` directive.

### Upstream buffering: the proxy_buffer family

The `proxy_buffering on` directive plus the `proxy_buffer_size 16k` / `proxy_buffers 16 16k` / `proxy_busy_buffers_size 32k` family control how Nginx holds the upstream response before sending it to the client. The mechanism is: Nginx reads the first part of the upstream response into `proxy_buffer_size` (the headers, plus the first chunk of the body), then reads the body into the `proxy_buffers` pool (16 buffers × 16 KB = 256 KB total). Once the buffers fill past `proxy_busy_buffers_size` (32 KB), Nginx starts flushing to the client while continuing to read from the upstream. If the response exceeds the total buffer capacity (256 KB), Nginx spills to a temporary file at `proxy_temp_path` (default `/var/lib/nginx/proxy`).

The buffering protects the upstream from slow-client backpressure. Without buffering, a client on a 3 G connection downloading a 5 MB JSON response would hold the upstream connection open for 14 seconds (5 MB / 3 Mbps = 14 s) — and the upstream (Spring Boot's Tomcat thread pool) cannot process any other requests on that thread for 14 seconds. With buffering, Nginx reads the 5 MB response from the upstream in 50 ms (gigabit network), releases the upstream connection back to the pool, and then dribbles the 5 MB to the slow client over 14 seconds from Nginx's buffer. The upstream thread is freed in 50 ms instead of 14 000 ms — a 280× improvement in upstream throughput under slow-client load.

The `proxy_busy_buffers_size 32k` setting is the threshold at which Nginx starts flushing to the client while still reading from the upstream — it must be less than the total `proxy_buffers` size minus one buffer (so one buffer is always available for the upstream's next read). Setting it too high (e.g. `proxy_busy_buffers_size 256k` when `proxy_buffers` is 16 × 16k = 256k) means Nginx fills all buffers before flushing, which delays the first byte sent to the client and produces a "time to first byte" regression. Setting it too low (e.g. `4k`) means Nginx flushes on every buffer fill, which produces excessive syscalls. The default `proxy_busy_buffers_size 32k` is a reasonable balance for most workloads.

### Rate limiting: the limit_req_zone family

The `limit_req_zone $binary_remote_addr zone=api_zone:10m rate=10r/s` directive creates a shared-memory zone (10 MB, holds ~160 K unique IP addresses) that tracks request rate per client IP. The `location /api/orders/ { limit_req zone=api_zone burst=20 nodelay; }` directive applies the limit: requests beyond 10 per second per IP are queued up to a burst of 20, then rejected with HTTP 429 (configurable via `limit_req_status 429`). The `nodelay` flag means queued requests are served immediately (not delayed to enforce the average rate); without `nodelay`, Nginx would delay each queued request by 100 ms to enforce the 10 r/s average, which is the correct behaviour for an API with strict rate limits but produces a poor user experience for legitimate bursts.

The three zones (`api_zone`, `admin_zone`, `auth_zone`) are deliberately separate so a single IP cannot exhaust the global rate limit by hitting one endpoint. The auth zone (`/api/users/login`) is the strictest at 2 r/s burst 5 — credential-stuffing attacks typically hit the login endpoint with thousands of password guesses per second, and a 2 r/s limit cuts the attack rate by 99.95 %. The admin zone (`/admin/`) is 5 r/s burst 10 because PHP-FPM cannot handle more than ~5 r/s per worker without queueing requests, and a 503 from PHP-FPM is a worse experience than a 429 from Nginx. The API zone (`/api/orders/`, `/api/users/`, `/api/ledger/`) is 10 r/s burst 20 — generous enough for legitimate clients (a browser making 10 concurrent API calls on page load), strict enough to stop a runaway script.

### TLS termination and security headers

The `listen 443 ssl; http2 on;` directive enables TLS and HTTP/2 on port 443. The `ssl_protocols TLSv1.2 TLSv1.3;` directive disables the legacy SSLv3, TLSv1.0, and TLSv1.1 protocols (all broken). The `ssl_ciphers` list restricts to the modern AEAD cipher suites (AES-256-GCM and CHACHA20-POLY1305 with ECDHE key exchange) and rejects everything else. The `ssl_prefer_server_ciphers off;` directive lets the client pick the cipher (correct for TLS 1.3, where the cipher list is fixed by the protocol and the directive is a no-op; correct for TLS 1.2 because modern clients pick the right cipher anyway). The `ssl_session_cache shared:SSL:50m;` directive caches TLS session resumption tickets in a 50 MB shared memory region so repeat connections skip the full TLS handshake (saving ~100 ms per connection).

The security headers (`Strict-Transport-Security`, `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`) are added via `add_header ... always` on every response, including error responses. The `always` flag is critical — without it, Nginx only adds headers to 2xx responses and silently omits them from 4xx/5xx, which means a 404 response would not include the HSTS header, and a man-in-the-middle could downgrade the client to HTTP on the 404 page. The `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload` header tells the browser to use HTTPS exclusively for 2 years, including subdomains, and to opt into the HSTS preload list (a one-way door — once you are on the list, you cannot remove yourself for months; only enable this in production after you are certain every subdomain supports HTTPS).

## Run It

```bash
# 1. Validate the config (always do this before reloading)
docker compose exec nginx nginx -t
#   → nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
#   → nginx: configuration file /etc/nginx/nginx.conf test is successful

# 2. Hot-reload the config (zero downtime — Nginx master spawns new workers, old workers drain)
docker compose exec nginx nginx -s reload

# 3. Verify each route end-to-end
curl -sk https://localhost/health                              # → spring-order /actuator/health
curl -sk https://localhost/api/orders/1234 | jq .              # → spring-order OrderDto
curl -sk https://localhost/api/users/me | jq .                 # → spring-user UserDto
curl -sk https://localhost/api/ledger/accounts | jq .          # → spring-ledger accounts list
curl -sk https://localhost/admin/invoices | jq .               # → php-invoice-admin invoice list

# 4. Verify the WebSocket upgrade
#    (use websocat for CLI, or browser DevTools for interactive test)
echo '{"subscribe":"orders.events"}' | websocat -1 wss://localhost/ws/orders

# 5. Verify the rate limit (10 r/s with burst 20 = 30 requests before 429)
for i in $(seq 1 50); do
  curl -sk -o /dev/null -w "%{http_code}\n" https://localhost/api/orders/1234
done | sort | uniq -c
#   → 30 200
#   → 20 429

# 6. Verify the 80→443 redirect
curl -sI http://localhost/health
#   → HTTP/1.1 301 Moved Permanently
#   → Location: https://localhost/health

# 7. Verify the traceparent pass-through (Nginx forwards the W3C header to upstream)
TRACE_ID=$(openssl rand -hex 16); SPAN_ID=$(openssl rand -hex 8)
curl -sk -H "traceparent: 00-${TRACE_ID}-${SPAN_ID}-01" \
     https://localhost/api/orders/1234
# Then check Jaeger: open http://localhost:16686/trace/${TRACE_ID}
# You should see a span from nginx (proxy_pass) and a child span from spring-order
```

The most common failure at this point is `nginx: [emerg] host not found in upstream "spring-order"`. This means Nginx started before the `spring-order` container was registered with Docker's DNS — Nginx resolves upstream names at config-load time, not at request time, so a missing upstream at startup is fatal. The fix is the `depends_on: { condition: service_healthy }` chain in the compose file (Nginx does not start until every upstream is healthy) plus the `resolver 127.0.0.11 valid=30s;` directive in the `http` block (which tells Nginx to re-resolve upstream names every 30 seconds, so a restarted upstream is picked up without an Nginx reload). The `valid=30s` is the part that makes dynamic upstream discovery work — without it, Nginx caches the DNS resolution forever and a restarted container with a new IP is invisible to Nginx until you reload.

## What This Teaches

The first lesson this note teaches is the **buffer-vs-stream decision** that every reverse proxy must make per route. The default (`proxy_buffering on`) is correct for 95 % of routes because it decouples the upstream's write speed from the client's read speed — a slow client on a 3 G connection cannot backpressure a fast upstream. The exceptions (`proxy_buffering off`) are the routes where the upstream produces data incrementally and the client must receive it as it is produced: WebSocket upgrades (server pushes frames continuously), server-sent events (the server holds the connection open and pushes events), long-poll endpoints, and large file downloads where the client wants to start rendering before the full response is buffered. The lesson is to make this decision per route, not globally — a global `proxy_buffering off` is a footgun that produces upstream connection pool exhaustion under slow-client load.

The second lesson is the **rate-limit zone granularity** that protects each endpoint class independently. A single global rate limit is wrong because it lets one noisy client exhaust the limit for every other client on every endpoint. The correct granularity is per-endpoint-class: API endpoints share a zone (10 r/s) because they are called together by the same client (browser page load fires 5-10 concurrent API calls); auth endpoints get a separate stricter zone (2 r/s) because they are the target of credential-stuffing attacks; admin endpoints get a separate zone sized to the backend's capacity (PHP-FPM at 5 r/s). The zones are defined in shared memory (`zone=api_zone:10m`) so they are shared across all Nginx worker processes — without the shared memory, each worker would track its own counter and the effective limit would be `worker_processes × rate`, which on an 8-core machine would be 80 r/s instead of 10 r/s.

The third lesson is the **TLS termination pattern** that puts the cryptographic work at the edge of the network. Terminating TLS at Nginx means the upstreams speak plain HTTP on the internal Docker network — no certificate management per service, no CPU spent on TLS handshakes in Spring Boot or PHP-FPM, and the security boundary is the Docker network itself (trusted). The trade-off is that traffic between Nginx and the upstream is unencrypted — if an attacker can sniff the Docker bridge network, they can read the plaintext. In production on Kubernetes with mTLS via Istio or Linkerd, this trade-off is avoided (mTLS between every pod, Nginx still terminates the user-facing TLS); in single-host Docker Compose, the bridge network is trusted and the trade-off is acceptable. The lesson is to make the trade-off explicit: TLS at the edge for performance, TLS everywhere for security, and never accidentally ship the "TLS nowhere" configuration that some tutorials suggest.
