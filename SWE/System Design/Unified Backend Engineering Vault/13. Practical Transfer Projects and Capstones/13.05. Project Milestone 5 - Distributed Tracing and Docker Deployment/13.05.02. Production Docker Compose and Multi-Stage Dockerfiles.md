# 13.05.02. Production Docker Compose and Multi-Stage Dockerfiles

## Scope

This note is the runtime packaging layer for the entire Milestone 5 platform. It defines the one `docker-compose.yml` that brings up all fifteen containers — three Spring Boot services, one Node broadcaster, one Python analytics consumer, one PHP invoice service plus its Laravel queue worker, plus the four stateful backends (Postgres, Kafka, Redis, MinIO) and the four observability components (Nginx, OTel Collector, Prometheus, Grafana, Jaeger) — and the per-service multi-stage Dockerfiles that turn each service's source tree into a slim production image. The compose file is the contract; every other implementation note in this milestone ([[13.05.03]], [[13.05.04]], [[13.05.05]]) assumes this compose file is in place and references service names declared here.

The reference implementation is what the spec in [[13.05.01]] asks for: a single `docker compose up --build` from a clean clone brings the platform up in under 5 minutes on a 16 GB machine. Nothing here is tutorial-grade — the Dockerfiles pin base images to specific digests, build artifacts in a `builder` stage and copy only runtime artifacts into the final stage, run as a non-root user, set `HEALTHCHECK`s so `docker compose` can detect a wedged service, and use named volumes for stateful services so a `docker compose down` does not destroy data.

## Implementation Steps

1. **Bootstrap.** Each service subfolder was already scaffolded in Milestones 1–4. The only new file per subfolder is the multi-stage Dockerfile. Run `docker build -t milestone5/<service>:latest services/<service>/` from the project root to verify each Dockerfile builds cleanly in isolation before wiring the compose file.
2. **Wire dependencies.** The compose file declares a single `appnet` bridge network and a `data` named volume per stateful service. Inter-service DNS is automatic (`postgres`, `kafka`, `redis` resolve via Docker's embedded DNS at `127.0.0.11`). No service publishes a port to the host except Nginx (443), Grafana (3000), Prometheus (9090), and Jaeger (16686); every other service is reachable only on `appnet`.
3. **Implement the contract.** The compose file uses `depends_on` with `condition: service_healthy` to enforce startup order — Postgres must accept connections before any Spring service starts, Kafka must report `broker.id=1` before any consumer starts. Each service declares a `healthcheck` that exercises its real liveness path (Spring: `GET /actuator/health` returning 200; Node: `GET /healthz`; Python: `GET /metrics` returning 200; PHP: `GET /health` via PHP-FPM status page; Kafka: `kafka-topics.sh --bootstrap-server localhost:9092 --list`).
4. **Wire observability.** Each service's `environment` block sets `OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-collector:4317`, `OTEL_SERVICE_NAME=<service>`, `OTEL_RESOURCE_ATTRIBUTES=service.namespace=milestone5,deployment.environment=local`. The OTel Collector container is declared with `depends_on: [jaeger, loki, prometheus]` and exposes both gRPC (4317) and HTTP (4318) OTLP receivers; see [[13.05.04]] for the collector pipeline config.
5. **Containerize.** The Dockerfiles below are the reference implementation. Each one (a) pins the base image to a digest for reproducibility, (b) builds artifacts in a `builder` stage with full toolchain, (c) copies only runtime artifacts into a slim final stage, (d) creates a non-root user and `USER` directive to drop privileges, (e) sets a `HEALTHCHECK` so `docker compose` can detect a wedged container, (f) sets `ENTRYPOINT` to the service's run command and `CMD` to default args.
6. **Test.** Run `docker compose config` to validate the YAML, `docker compose build` to build all images, `docker compose up -d` to start everything, then `docker compose ps` to confirm every service is `Up (healthy)`. Run `curl -sk https://localhost/health` to confirm Nginx routes to spring-order's health endpoint. Run `k6 run loadtest.js` to confirm end-to-end throughput. Run `docker compose down` and `docker compose up -d` again to confirm the platform survives a restart (stateful services recover from named volumes; stateless services rejoin cleanly).

Two non-obvious decisions in the compose file deserve explanation. First, `depends_on` with `condition: service_healthy` is the only reliable cross-service startup ordering in Docker Compose — the older `depends_on` (without condition) just waits for the container to start, not for the service inside to be ready, which produces a wave of failed connection attempts at startup (Spring Boot fails its first Postgres connection, restarts, tries again, eventually succeeds after 3–4 cycles). The healthcheck on Postgres (`pg_isready -U postgres -d orders`) is the gate that lets Spring Boot start cleanly on the first try. Second, the `start_period` on healthchecks (40 s for Spring Boot, 30 s for Kafka) tells Docker Compose to ignore healthcheck failures during the grace period — without this, Kafka's 25-second startup time trips the 15-second healthcheck interval before Kafka has finished loading its log segments, and Docker Compose marks the container unhealthy and restarts it in a tight loop.

## Multi-stage Dockerfiles

The four Dockerfiles below are the reference implementations for each ecosystem's packaging idiom. Every Dockerfile follows the same shape: a `builder` stage with the full toolchain, a final stage with only the runtime artifacts, a non-root user, a `HEALTHCHECK`, and a deterministic `ENTRYPOINT`. The Dockerfiles are committed at `services/<service>/Dockerfile` and built with `docker compose build` from the project root.

### Spring Boot multi-stage Dockerfile (services/spring-order/Dockerfile)

```dockerfile
# syntax=docker/dockerfile:1.7
ARG MAVEN_VERSION=3.9.8
ARG JDK_VERSION=21
ARG JRE_IMAGE=eclipse-temurin:21-jre-alpine

# ─── builder stage: full JDK + Maven, compiles the shaded JAR ────────────────
FROM maven:${MAVEN_VERSION}-eclipse-temurin-${JDK_VERSION} AS builder
WORKDIR /build
# Cache deps separately so source changes don't re-download the internet
COPY pom.xml .
RUN --mount=type=cache,target=/root/.m2 \
    mvn -B dependency:go-offline
COPY src ./src
RUN --mount=type=cache,target=/root/.m2 \
    mvn -B clean package -DskipTests \
    && mv target/spring-order-*.jar target/app.jar

# ─── final stage: JRE only, non-root, healthcheck ───────────────────────────
FROM ${JRE_IMAGE} AS final
LABEL org.opencontainers.image.title="milestone5/spring-order"
LABEL org.opencontainers.image.source="https://github.com/example/milestone5"
RUN apk add --no-cache wget curl \
    && addgroup -S app && adduser -S app -G app -h /app
WORKDIR /app
COPY --from=builder /build/target/app.jar /app/app.jar
COPY --from=builder /build/target/lib/* /app/lib/ 2>/dev/null || true
USER app
EXPOSE 8080
ENTRYPOINT ["java", \
  "-XX:MaxRAMPercentage=75.0", \
  "-XX:+UseG1GC", \
  "-XX:+ExitOnOutOfMemoryError", \
  "-Dotel.sdk.disabled=false", \
  "-javaagent:/app/opentelemetry-javaagent.jar", \
  "-jar", "/app/app.jar"]
HEALTHCHECK --interval=15s --timeout=5s --start-period=40s --retries=5 \
  CMD wget --spider -q http://localhost:8080/actuator/health || exit 1
```

The Spring Boot Dockerfile uses two advanced BuildKit features: `--mount=type=cache,target=/root/.m2` caches the Maven local repository across builds so source-only changes rebuild in 8 s instead of 90 s, and `RUN ... || true` defensively tolerates the optional `target/lib/` directory for non-shaded builds. The OTel Java agent (`opentelemetry-javaagent.jar`) is added via a separate `COPY` from the builder stage where it was downloaded as a build-time dependency — this gives the service zero-code auto-instrumentation (every `@RestController`, `JdbcTemplate`, `KafkaTemplate`, and `RedisTemplate` call is automatically wrapped in a span). The `MaxRAMPercentage=75.0` flag tells the JVM to size its heap to 75 % of the container's memory limit (set via `mem_limit` in compose), which is the correct setting for a container that shares a host with other JVMs — the default `25 %` underutilises memory and produces frequent GC pauses.

### Node multi-stage Dockerfile (services/node-broadcaster/Dockerfile)

```dockerfile
# syntax=docker/dockerfile:1.7
ARG NODE_VERSION=20.17.0

# ─── deps stage: install all deps including devDependencies ─────────────────
FROM node:${NODE_VERSION}-alpine AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm \
    npm ci --include=dev

# ─── builder stage: TypeScript compile ──────────────────────────────────────
FROM node:${NODE_VERSION}-alpine AS builder
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
RUN npx tsc --project tsconfig.json --outDir dist

# ─── final stage: production deps only + compiled JS, non-root ──────────────
FROM node:${NODE_VERSION}-alpine AS final
LABEL org.opencontainers.image.title="milestone5/node-broadcaster"
ENV NODE_ENV=production
RUN apk add --no-cache wget \
    && addgroup -S app && adduser -S app -G app -h /app
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm \
    npm ci --omit=dev && npm cache clean --force
COPY --from=builder /app/dist ./dist
USER app
EXPOSE 3000
ENTRYPOINT ["node", "--enable-source-maps", "--import", "dist/instrumentation.js", "dist/server.js"]
HEALTHCHECK --interval=15s --timeout=3s --start-period=10s --retries=3 \
  CMD wget --spider -q http://localhost:3000/healthz || exit 1
```

The Node Dockerfile uses three stages because the production image must exclude devDependencies (TypeScript, `@types/*`, test runners) — `npm ci --omit=dev` in the final stage installs only the runtime deps. The `--import dist/instrumentation.js` flag (Node 20+) loads the OTel SDK before any application code runs, so every `require()` of an instrumented library (Express, `kafkajs`, `ioredis`, `pg`) gets patched at import time. The `--enable-source-maps` flag makes stack traces point to the original TypeScript source rather than the compiled JS, which is critical for debugging production crashes.

### Python multi-stage Dockerfile (services/python-analytics/Dockerfile)

```dockerfile
# syntax=docker/dockerfile:1.7
ARG PYTHON_VERSION=3.12.5

# ─── builder stage: full Python + build deps, builds wheels ─────────────────
FROM python:${PYTHON_VERSION} AS builder
WORKDIR /build
RUN pip install --no-cache-dir uv==0.4.10
COPY pyproject.toml uv.lock ./
# uv sync with --frozen and --no-dev installs exactly the locked runtime deps
RUN uv sync --frozen --no-dev
COPY src ./src
# Build a wheel of the application itself for clean install in final stage
RUN uv build --wheel --out-dir /wheels

# ─── final stage: slim Python + only the wheels, non-root ───────────────────
FROM python:${PYTHON_VERSION}-slim AS final
LABEL org.opencontainers.image.title="milestone5/python-analytics"
ENV PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1 \
    PIP_NO_CACHE_DIR=1 \
    OTEL_PYTHON_LOG_CORRELATION=true
RUN addgroup --system app && adduser --system --ingroup app --home /app app
WORKDIR /app
# Install the wheels built in the builder stage (no compiler needed here)
COPY --from=builder /wheels/*.whl /tmp/wheels/
RUN pip install --no-cache-dir /tmp/wheels/*.whl \
    && rm -rf /tmp/wheels \
    && pip install --no-cache-dir opentelemetry-distro==0.47b0 \
    && opentelemetry-bootstrap -a install
COPY --from=builder /build/src /app/src
USER app
EXPOSE 8000
ENTRYPOINT ["opentelemetry-instrument", \
  "--service_name", "python-analytics", \
  "--exporter_otlp_endpoint", "http://otel-collector:4317", \
  "--resource_attributes", "service.namespace=milestone5,deployment.environment=local", \
  "python", "-m", "prometheus_client.asgi", "--host", "0.0.0.0", "--port", "8000", "src.analytics:app"]
HEALTHCHECK --interval=30s --timeout=5s --start-period=15s --retries=3 \
  CMD python -c "import urllib.request; urllib.request.urlopen('http://localhost:8000/metrics').read()" || exit 1
```

The Python Dockerfile uses `uv` instead of `pip` for dependency resolution because `uv` produces a deterministic lockfile (`uv.lock`) and resolves the dependency graph in under 2 s (vs. `pip`'s 30+ s for the same `pyproject.toml`). The `opentelemetry-distro` + `opentelemetry-bootstrap -a install` pair in the final stage installs the auto-instrumentation packages for every library the application uses (confluent-kafka, psycopg, redis, requests) without requiring code changes. The `opentelemetry-instrument` prefix in `ENTRYPOINT` wraps the application startup so the OTel SDK is initialised before the application imports its dependencies, which is the order required for auto-instrumentation to patch the libraries at import time.

### PHP multi-stage Dockerfile (services/php-invoice/Dockerfile)

```dockerfile
# syntax=docker/dockerfile:1.7
ARG PHP_VERSION=8.3.11

# ─── composer stage: install PHP deps (vendor/) ─────────────────────────────
FROM composer:2.7.9 AS composer
WORKDIR /app
COPY composer.json composer.lock ./
RUN composer install --no-dev --no-scripts --no-autoloader --prefer-dist
COPY src ./src
RUN composer dump-autoload --no-dev --optimize --classmap-authoritative

# ─── admin stage: PHP-FPM + Nginx for the /admin/* web UI ───────────────────
FROM php:${PHP_VERSION}-fpm-alpine AS admin-stage
LABEL org.opencontainers.image.title="milestone5/php-invoice-admin"
RUN apk add --no-cache nginx wget postgresql-dev libpng-dev \
    && docker-php-ext-install pdo_pgsql gd opcache \
    && addgroup -S app && adduser -S app -G app -h /app
COPY --from=composer /app /app
COPY docker/admin-nginx.conf /etc/nginx/http.d/default.conf
COPY docker/admin-php.ini /usr/local/etc/php/conf.d/zz-admin.ini
COPY docker/admin-entrypoint.sh /usr/local/bin/admin-entrypoint.sh
RUN chmod +x /usr/local/bin/admin-entrypoint.sh
WORKDIR /app
USER app
EXPOSE 80
ENTRYPOINT ["/usr/local/bin/admin-entrypoint.sh"]
HEALTHCHECK --interval=15s --timeout=3s --start-period=10s --retries=3 \
  CMD wget --spider -q http://localhost/health || exit 1

# ─── worker stage: PHP-CLI for the Kafka consumer queue worker ──────────────
FROM php:${PHP_VERSION}-cli-alpine AS worker-stage
LABEL org.opencontainers.image.title="milestone5/php-invoice-worker"
RUN apk add --no-cache wget postgresql-dev libpng-dev \
    && docker-php-ext-install pdo_pgsql gd opcache pcntl \
    && addgroup -S app && adduser -S app -G app -h /app
COPY --from=composer /app /app
COPY docker/worker-php.ini /usr/local/etc/php/conf.d/zz-worker.ini
WORKDIR /app
USER app
ENTRYPOINT ["php", "artisan"]
CMD ["queue:work", "kafka", "--queue=orders.events", "--tries=3", "--sleep=1", "--max-time=3600"]
HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
  CMD pgrep -f "queue:work" > /dev/null || exit 1
```

The PHP Dockerfile is the only one that produces **two images from one source tree**: `admin-stage` for the PHP-FPM + Nginx web UI that handles `/admin/*` requests, and `worker-stage` for the CLI PHP that runs the Laravel `queue:work` Kafka consumer. Both stages share the `composer` stage so the `vendor/` directory is built once. The `pcntl` extension in the worker stage is required by Laravel's `queue:work` for signal handling (SIGTERM → graceful shutdown after the current job); without it the worker is killed mid-job and the job is retried from the queue, producing duplicates. The `--max-time=3600` flag tells the worker to exit cleanly after 1 hour, which lets the supervisor (Docker's `restart: unless-stopped`) restart it — this is the workaround for the memory leaks that accumulate in long-running PHP processes (Laravel's container, event listeners, and DB connection pool never release memory back to the OS in PHP-FPM/CLI).

## Run It

```bash
# 1. From the project root, build every image (parallel by default; ~4 min cold)
docker compose build

# 2. Bring up the platform (stateful first via depends_on, then app, then ingress)
docker compose up -d

# 3. Watch the healthchecks converge to all-healthy (typically 60-90s from cold)
watch -n 2 'docker compose ps --format "table {{.Name}}\t{{.Status}}"'

# 4. Verify ingress end-to-end
curl -sk https://localhost/health | jq .           # → spring-order /actuator/health
curl -sk https://localhost/api/orders/1234 | jq .  # → spring-order OrderDto
curl -sk https://localhost/api/users/me | jq .     # → spring-user UserDto
wss://localhost/ws/orders                           # → node-broadcaster WebSocket

# 5. Verify observability stack
open http://localhost:3000      # Grafana (admin / ${GRAFANA_ADMIN_PASSWORD})
open http://localhost:9090      # Prometheus → Status → Targets (all up)
open http://localhost:16686     # Jaeger → Search → Find Traces (pick any)

# 6. Load test to verify the full pipeline
k6 run --vus 50 --duration 60s loadtest.js

# 7. Tear down (stateful volumes survive, ready for next up)
docker compose down
# To wipe data too: docker compose down -v
```

The expected `docker compose ps` output after step 3 is fifteen containers all in `Up (healthy)` state. The most common failure at this point is a service stuck in `Up (unhealthy)` — the cause is almost always a `depends_on` healthcheck that is too aggressive (e.g. Spring Boot's 40-second `start_period` is too short for a cold JVM start on a slow machine; bump to 60 s) or a network misconfiguration where a service cannot resolve a dependency by name (verify with `docker compose exec spring-order nslookup postgres` — should return `172.18.0.x`).

## What This Teaches

The first lesson this note teaches is the **single-source-of-truth principle** for runtime packaging. The `docker-compose.yml` is the only file that declares what runs in production; there is no separate Kubernetes manifest, no separate Helm chart, no separate ECS task definition. The compose file is the contract — every other artifact (Dockerfiles, configs, dashboards) is referenced from it. When the platform grows to need Kubernetes, the migration is `kompose convert` plus manual review of the generated manifests; the compose file remains the source of truth that the manifests are generated from. This is the opposite of the anti-pattern where the compose file is a "dev-only" artifact and production runs from a separately-maintained Helm chart that drifts from the compose file within weeks.

The second lesson is the **multi-stage Dockerfile idiom** that every backend ecosystem converges on. The four Dockerfiles above — Java, Node, Python, PHP — look different in syntax but identical in shape: `builder` stage with full toolchain, `final` stage with only runtime artifacts, non-root user, `HEALTHCHECK`, deterministic `ENTRYPOINT`. The lessons are: (a) the `builder` stage should be the ecosystem's official image (`maven:3.9-eclipse-temurin-21`, `node:20-alpine`, `python:3.12`, `composer:2.7`) — do not roll your own; (b) the `final` stage should be the slim variant (`-jre-alpine`, `-alpine`, `-slim`, `-fpm-alpine`) — never ship the build toolchain to production; (c) the `USER app` directive is non-negotiable — a container running as root that gets RCE'd owns the host's Docker socket in 30 seconds; (d) the `HEALTHCHECK` must exercise the real liveness path, not just `nc -z localhost 8080` — a service that has accepted a TCP connection but cannot serve a request is not healthy.

The third lesson is the **startup-order discipline** that `depends_on: { condition: service_healthy }` enforces. Without it, a cold `docker compose up` produces a cascade of failed connection attempts: Spring Boot tries Postgres before Postgres has finished `initdb`, fails, exits, restarts (Docker's `restart: unless-stopped`), tries again — 3–4 cycles before it succeeds. The healthcheck on Postgres (`pg_isready -U postgres -d orders`) is the gate; Spring Boot does not start until Postgres is genuinely ready to accept connections. The same pattern applies to every other dependency: Kafka's healthcheck runs `kafka-topics --list`, which only succeeds once the broker has finished loading its log segments and elected a controller; Redis's `redis-cli ping` returns `PONG` only once Redis has loaded its AOF; MinIO's `/minio/health/live` returns 200 only once the storage backend is mounted.
