# 13.05.04. OpenTelemetry Tracing Integration Across All Services

## Scope

This note wires OpenTelemetry (OTel) context propagation into every service in the Milestone 5 platform. The contract is the W3C `traceparent` header: every inbound HTTP request extracts it (or generates a new trace context if absent), every outbound call injects it, and every span is exported via OTLP to the OTel Collector, which fans out to Jaeger (traces), Loki (logs with `trace.id` field), and Prometheus (metrics via the collector's `prometheus exporter` or by direct scrape of each service's `/metrics`). The deliverable is the OTel Collector configuration file plus the per-ecosystem instrumentation code for Spring Boot, Express, Django, and Laravel — four different SDKs, four different auto-instrumentation packages, one shared trace context.

The reason this note exists as a separate file from the compose/Dockerfile work in [[13.05.02]] is that OTel instrumentation is the part of the milestone where each ecosystem's idioms diverge most sharply. Spring Boot gets tracing for free with a single `-javaagent` flag and two environment variables; Express requires an `instrumentation.ts` file imported before the server boots; Django requires a `manage.py opentelemetry-instrument` wrapper command; Laravel requires a Composer package plus a middleware registration. The shape of the trace in Jaeger is identical across all four (every service emits `server` spans for inbound calls and `client` spans for outbound calls), but the wiring code is different enough that each ecosystem gets its own subsection below.

## What You Are Building

The deliverable has two halves. The first is the **OTel Collector pipeline** — a single `otel-collector-config.yaml` file that declares the receivers (OTLP on gRPC 4317 and HTTP 4318), the processors (batch, memory_limiter, resource, attributes), and the exporters (Jaeger via `otlp/jaeger`, Loki via `loki`, Prometheus via `prometheus` remote-write, plus a `debug` exporter for local troubleshooting). The Collector is the single ingress point for all observability data — services emit OTLP, the Collector transforms and fans out, and the downstream tools (Jaeger, Loki, Prometheus) each receive exactly the data they need in the format they expect.

The second half is the **per-service instrumentation code**. Each of the seven application services must initialize the OTel SDK at process startup, register the auto-instrumentation packages for the libraries it uses (HTTP server, HTTP client, database driver, Kafka client, Redis client), and export spans to the Collector. The initialization code is short (10-30 lines per service) but ecosystem-specific — the four subsections below show the exact code for each ecosystem, plus the `traceparent` header propagation verification that proves the wiring is correct end-to-end.

```
                              OTLP/gRPC :4317
   spring-order  ───┐         OTLP/HTTP :4318
   spring-user   ───┤                ▼
   spring-ledger ───┤      ┌──────────────────┐    ┌────────┐  traces
   node-broadcaster──┼────►│  OTel Collector  │───►│ Jaeger │  (otlp/jaeger)
   python-analytics──┤      │  - batch         │    └────────┘
   php-invoice-admin─┤      │  - memory_limiter│    ┌────────┐  logs
   php-invoice-worker┘      │  - resource      │───►│  Loki  │  (loki exporter,
                           │  - attributes    │    │        │   trace.id injected)

                                    │                ┌────────────┐  metrics
                                    └───────────────►│ Prometheus │  (scraped by
                                                      │   :9090    │   prometheus
                                                      └────────────┘   directly)
```

## Implementation Steps

1. **Bootstrap.** Add the OTel SDK dependency to each service: Spring Boot adds `io.opentelemetry:opentelemetry-spring-boot-starter` plus the `-javaagent`; Node adds `@opentelemetry/sdk-node` and `@opentelemetry/auto-instrumentations-node`; Python installs `opentelemetry-distro` and runs `opentelemetry-bootstrap -a install`; PHP requires `open-telemetry/sdk` and `open-telemetry/opentelemetry-auto-slim` (or the Laravel-specific auto-instrumentation package).
2. **Wire dependencies.** Each service's environment sets `OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-collector:4317`, `OTEL_SERVICE_NAME=<service>`, `OTEL_RESOURCE_ATTRIBUTES=service.namespace=milestone5,deployment.environment=local`. These three environment variables are the entire configuration surface for the OTel SDK in its default mode — no code changes required for the basic "export every span to the Collector" behaviour.
3. **Implement the contract.** For services where auto-instrumentation covers the full request path (Spring Boot, Node, Python), no code changes are required beyond the SDK initialization. For services where auto-instrumentation is incomplete (Laravel's Kafka client, the WebSocket fan-out in Node), add manual `tracer.startActiveSpan('span-name')` calls around the uninstrumented code paths.
4. **Wire observability.** The OTel Collector itself exports its own metrics at `:8888/metrics` (scraped by Prometheus) and exposes a health endpoint at `:13133/` (used by the compose file's healthcheck). The Collector's `service.telemetry.metrics.address` setting controls the metrics port; the `service.telemetry.logs.level` setting controls the Collector's own log verbosity (`debug` for local, `info` for production).
5. **Containerize.** The OTel Collector image is `otel/opentelemetry-collector-contrib:0.107.0` (the `-contrib` variant includes the Loki exporter, which the core image omits). The config file is mounted as a read-only volume; no custom Dockerfile is needed.
6. **Test.** Verify trace propagation end-to-end with a synthetic `traceparent` header: `TRACE_ID=$(openssl rand -hex 16); curl -H "traceparent: 00-${TRACE_ID}-$(openssl rand -hex 8)-01" https://localhost/api/orders/1234`. Open `http://localhost:16686/trace/${TRACE_ID}` in Jaeger; you should see a trace with ≥ 6 spans across 4 services (nginx → spring-order → postgres → kafka → python-analytics → node-broadcaster). If any service is missing from the trace, its instrumentation is broken; if any span has a different `trace_id`, the context propagation is broken (usually a missing `traceparent` injection in an outbound HTTP client or Kafka producer).

## The OTel Collector pipeline

The Collector config below is the single pipeline definition that every service's OTLP export targets. Save it as `otel-collector/otel-collector-config.yaml` at the project root. The file has four sections: `receivers` (where data comes in), `processors` (how data is transformed), `exporters` (where data goes out), and `service.pipelines` (which receivers → processors → exporters chains are active).

```yaml
# otel-collector/otel-collector-config.yaml
# Mounted into the otel-collector container at /etc/otel-collector-config.yaml

receivers:
  otlp:
    grpc:
      endpoint: 0.0.0.0:4317
      max_recv_msg_size_mib: 16
    http:
      endpoint: 0.0.0.0:4318
      cors:
        allowed_origins: ["http://localhost:3000", "https://localhost"]
  # The hostmetrics receiver scrapes CPU/memory/disk from the collector's own
  # container — useful for debugging the collector itself, not for app metrics.
  hostmetrics:
    collection_interval: 30s
    scrapers:
      cpu: {}
      memory: {}
      filesystem: {}

processors:
  # memory_limiter: drop spans when the collector is under memory pressure
  # rather than OOM-killing the collector and losing ALL data.
  memory_limiter:
    check_interval: 1s
    limit_mib: 512
    spike_limit_mib: 128
  # batch: aggregate spans into batches before export. 10,000 spans/s becomes
  # ~100 batches/s of 100 spans each, which is what Jaeger prefers to ingest.
  batch:
    timeout: 5s
    send_batch_size: 1000
    send_batch_max_size: 2000
  # resource: ensure every span has service.name, service.namespace,
  # deployment.environment — even if the SDK forgot to set them.
  resource:
    attributes:
      - key: service.namespace
        value: milestone5
        action: upsert
      - key: deployment.environment
        value: local
        action: upsert
  # attributes: drop high-cardinality span attributes that would explode Jaeger's
  # storage (e.g. http.request_body — never put the request body in a span).
  attributes:
    actions:
      - key: http.request_body
        action: delete
      - key: http.response_body
        action: delete
      - key: db.statement
        action: hash
  # tail_sampling: keep 100% of error traces, 10% of slow traces (>1s),
  # 1% of fast traces. This is what keeps Jaeger's storage bounded over months.
  tail_sampling:
    decision_wait: 10s
    num_traces: 50000
    expected_new_traces_per_sec: 100
    policies:
      - name: errors
        type: status_code
        status_code:
          status_codes: [ERROR]
      - name: slow
        type: latency
        latency:
          threshold_ms: 1000
      - name: fast_sampled
        type: probabilistic
        probabilistic:
          sampling_percentage: 1

exporters:
  # Jaeger via OTLP (Jaeger 1.35+ accepts OTLP natively, no Jaeger thrift needed)
  otlp/jaeger:
    endpoint: jaeger:4317
    tls:
      insecure: true
  # Loki: export logs with trace_id as a structured metadata field so Loki
  # can correlate log lines to Jaeger traces via {trace_id="..."} queries.
  loki:
    endpoint: http://loki:3100/loki/api/v1/push
    default_labels_enabled:
      exporter: false
      job: true
    headers:
      # X-Scope-OrgID is required for multi-tenant Loki; single-tenant uses "fake"
      X-Scope-OrgID: fake
  # Prometheus: the collector exposes scraped metrics at :8889/metrics, which
  # Prometheus then scrapes. This is the "pull" model — alternative is
  # remote_write, which pushes metrics directly to Prometheus.
  prometheus:
    endpoint: 0.0.0.0:8889
    namespace: otel_collector
    const_labels:
      collector: milestone5
  # debug: log every span to the collector's stdout — invaluable for local
  # debugging when you cannot tell whether the SDK or the collector is broken.
  debug:
    verbosity: basic
    sampling_initial: 1
    sampling_thereafter: 100

service:
  telemetry:
    logs:
      level: info
    metrics:
      address: 0.0.0.0:8888
  pipelines:
    traces:
      receivers: [otlp]
      processors: [memory_limiter, resource, attributes, tail_sampling, batch]
      exporters: [otlp/jaeger, debug]
    metrics:
      receivers: [otlp, hostmetrics]
      processors: [memory_limiter, resource, batch]
      exporters: [prometheus]
    logs:
      receivers: [otlp]
      processors: [memory_limiter, resource, attributes, batch]
      exporters: [loki, debug]

  extensions: [health_check]
extensions:
  health_check:
    endpoint: 0.0.0.0:13133
```

The `tail_sampling` processor is the most consequential decision in this config. Without it, every span is exported to Jaeger, and Jaeger's storage grows unboundedly — at 1000 requests/s × 6 spans/request × 86400 s/day = 518 million spans/day, a Jaeger backend with 100 GB of storage fills up in 4 days. The `tail_sampling` processor buffers each trace for 10 seconds (the `decision_wait`), then applies the policies: 100 % of error traces (any span with `status_code=ERROR`), 100 % of slow traces (any span with duration > 1 s), and 1 % of fast successful traces. This typically reduces Jaeger's storage by 95 % while keeping every trace that an operator would actually want to investigate. The trade-off is that the collector must buffer 10 seconds of traces in memory — at 6000 spans/s × 10 s = 60 K spans buffered, which is ~30 MB, well within the `memory_limiter` budget.

The `attributes` processor's `db.statement: hash` action is the second most consequential decision. By default, the OTel JDBC instrumentation records the full SQL query as the `db.statement` span attribute — `SELECT id, email, name FROM users WHERE email = 'alice@example.com'`. This is great for debugging a single trace, but it means every distinct email address produces a distinct span attribute value, and Jaeger's index explodes. The `hash` action replaces the SQL with a hash, preserving the ability to correlate "this trace ran the same query as that trace" without recording the actual parameter values. The unhashed SQL is still available in the application's structured logs (which go to Loki) — the trace is for shape analysis, the logs are for content analysis.

## Spring Boot OTel integration (the anchor)

Spring Boot is the anchor ecosystem for OTel because the JVM's `-javaagent` mechanism makes auto-instrumentation zero-code: drop the agent JAR into the image, add `-javaagent:/app/opentelemetry-javaagent.jar` to the `ENTRYPOINT`, set `OTEL_EXPORTER_OTLP_ENDPOINT` and `OTEL_SERVICE_NAME` as environment variables, and every Spring component (`@RestController`, `JdbcTemplate`, `KafkaTemplate`, `RedisTemplate`, `WebClient`) is automatically wrapped in spans. No source code changes. The agent patches the bytecode of the supported libraries at class-load time, which is the same mechanism that New Relic, AppDynamics, and Dynatrace have used for years — OTel just makes it open-source and vendor-neutral.

The `Dockerfile` change is the only required artifact. The agent JAR is downloaded during the builder stage and copied into the final image alongside the application JAR:

```dockerfile
# In the builder stage of services/spring-order/Dockerfile
RUN curl -L -o /build/opentelemetry-javaagent.jar \
    https://github.com/open-telemetry/opentelemetry-java-instrumentation/releases/download/v2.8.0/opentelemetry-javaagent.jar

# In the final stage
COPY --from=builder /build/opentelemetry-javaagent.jar /app/opentelemetry-javaagent.jar

# In the ENTRYPOINT
ENTRYPOINT ["java", \
  "-javaagent:/app/opentelemetry-javaagent.jar", \
  "-Dotel.service.name=spring-order", \
  "-Dotel.exporter.otlp.endpoint=http://otel-collector:4317", \
  "-Dotel.exporter.otlp.protocol=grpc", \
  "-Dotel.traces.exporter=otlp", \
  "-Dotel.metrics.exporter=otlp", \
  "-Dotel.logs.exporter=otlp", \
  "-Dotel.instrumentation.spring-web.enabled=true", \
  "-Dotel.instrumentation.spring-data.enabled=true", \
  "-Dotel.instrumentation.jdbc.enabled=true", \
  "-Dotel.instrumentation.kafka.enabled=true", \
  "-Dotel.instrumentation.lettuce.enabled=true", \
  "-Dotel.instrumentation.logback-appender-1.0.enabled=true", \
  "-XX:MaxRAMPercentage=75.0", \
  "-XX:+UseG1GC", \
  "-XX:+ExitOnOutOfMemoryError", \
  "-jar", "/app/app.jar"]
```

For the rare cases where auto-instrumentation does not cover a code path (a custom `Callable` that makes an external HTTP call without going through Spring's `RestTemplate`/`WebClient`), add a manual span using the `@WithSpan` annotation:

```java
import io.opentelemetry.instrumentation.annotations.WithSpan;
import io.opentelemetry.instrumentation.annotations.SpanAttribute;

@Service
public class OrderService {

    private final JdbcTemplate jdbc;
    private final KafkaTemplate<String, OrderEvent> kafka;

    public OrderService(JdbcTemplate jdbc, KafkaTemplate<String, OrderEvent> kafka) {
        this.jdbc = jdbc;
        this.kafka = kafka;
    }

    // @WithSpan creates a span named "OrderService.placeOrder" as a child of
    // the inbound HTTP server span. The span is automatically ended when the
    // method returns. The @SpanAttribute annotations record method parameters
    // as span attributes — useful for filtering in Jaeger.
    @WithSpan("OrderService.placeOrder")
    public Order placeOrder(
            @SpanAttribute("order.customer_id") String customerId,
            @SpanAttribute("order.total_cents") long totalCents) {

        // jdbc.execute is auto-instrumented: a child span "SELECT" is created
        // with db.statement, db.user, db.connection_string attributes.
        Order order = jdbc.queryForObject(
            "INSERT INTO orders(customer_id, total_cents) VALUES(?, ?) RETURNING *",
            new Object[]{customerId, totalCents},
            (rs, n) -> Order.fromRow(rs));

        // kafka.send is auto-instrumented: a child span "orders.events send"
        // is created with messaging.system=kafka, messaging.destination=orders.events.
        kafka.send("orders.events", order.getId().toString(), OrderEvent.from(order));

        return order;
    }
}
```

The `@WithSpan` annotation is the only Spring-Boot-specific code change in this milestone. The trace in Jaeger for a single `POST /api/orders` request shows five spans: (1) `GET /api/orders` server span from Tomcat instrumentation, (2) `OrderService.placeOrder` from `@WithSpan`, (3) `INSERT orders` client span from JDBC instrumentation, (4) `orders.events send` client span from Kafka instrumentation, (5) `Redis SET` client span from Lettuce instrumentation (for the idempotency key). Every span has the same `trace_id`, every child span's `parent_span_id` points to its parent, and the trace is a tree rooted at the Tomcat server span.

## Express OTel integration (Node)

Node does not have a `-javaagent` equivalent, so OTel instrumentation requires an `instrumentation.ts` file that imports and initializes the SDK before any application code runs. The `--import` flag (Node 20+) is the cleanest way to ensure this file runs first — it is loaded before `server.ts`, so by the time Express's `app.listen()` runs, every required instrumentation patch is already in place.

```typescript
// services/node-broadcaster/src/instrumentation.ts
// MUST be imported before any other code. Loaded via:
//   node --import ./dist/instrumentation.js dist/server.js

import { NodeSDK } from '@opentelemetry/sdk-node';
import { getNodeAutoInstrumentations } from '@opentelemetry/auto-instrumentations-node';
import { OTLPTraceExporter } from '@opentelemetry/exporter-trace-otlp-grpc';
import { OTLPMetricExporter } from '@opentelemetry/exporter-metrics-otlp-grpc';
import { OTLPLogExporter } from '@opentelemetry/exporter-logs-otlp-grpc';
import { PeriodicExportingMetricReader } from '@opentelemetry/sdk-metrics';
import { BatchLogRecordProcessor } from '@opentelemetry/sdk-logs';
import { resourceFromAttributes } from '@opentelemetry/resources';
import { semanticConventions } from '@opentelemetry/semantic-conventions';
import { diag, DiagConsoleLogger, DiagLogLevel } from '@opentelemetry/api';

// Only enable diag logging in development — it is verbose.
if (process.env.NODE_ENV !== 'production') {
  diag.setLogger(new DiagConsoleLogger(), DiagLogLevel.info);
}

const resource = resourceFromAttributes({
  [semanticConventions.SERVICE_NAME]: 'node-broadcaster',
  [semanticConventions.SERVICE_NAMESPACE]: 'milestone5',
  [semanticConventions.DEPLOYMENT_ENVIRONMENT]: process.env.NODE_ENV ?? 'local',
});

const traceExporter = new OTLPTraceExporter({
  url: process.env.OTEL_EXPORTER_OTLP_ENDPOINT ?? 'http://otel-collector:4317',
});

const metricReader = new PeriodicExportingMetricReader({
  exporter: new OTLPMetricExporter({
    url: process.env.OTEL_EXPORTER_OTLP_ENDPOINT ?? 'http://otel-collector:4317',
  }),
  exportIntervalMillis: 15000,
});

const logExporter = new OTLPLogExporter({
  url: process.env.OTEL_EXPORTER_OTLP_ENDPOINT ?? 'http://otel-collector:4317',
});

const sdk = new NodeSDK({
  resource,
  traceExporter,
  metricReader,
  logRecordProcessor: new BatchLogRecordProcessor(logExporter),
  // getNodeAutoInstrumentations() enables every instrumentation in the
  // @opentelemetry/auto-instrumentations-node package: express, http, https,
  // kafkajs, ioredis, pg, mysql, grpc, dns, fs, net, etc.
  instrumentations: [
    getNodeAutoInstrumentations({
      // Disable fs instrumentation — it is noisy and produces spans for every
      // require() call, which is not actionable.
      '@opentelemetry/instrumentation-fs': { enabled: false },
      // kafkajs instrumentation needs explicit consumer group config
      '@opentelemetry/instrumentation-kafkajs': {
        // Enable consumer span creation (default is producer-only).
        consumerSpanEnabled: true,
      },
    }),
  ],
});

sdk.start();

// The WebSocket fan-out is not auto-instrumented (ws library is not in the
// auto-instrumentations package), so wrap it manually in server.ts:
//   import { trace } from '@opentelemetry/api';
//   const tracer = trace.getTracer('node-broadcaster');
//   ws.on('message', (msg) => {
//     const span = tracer.startSpan('broadcast-to-clients', { attributes: { 'ws.clients': clients.size } });
//     for (const client of clients) client.send(msg);
//     span.end();
//   });

process.on('SIGTERM', () => {
  sdk.shutdown()
    .then(() => console.log('OTel SDK shut down cleanly'))
    .catch((err) => console.error('OTel SDK shutdown error', err))
    .finally(() => process.exit(0));
});
```

The auto-instrumentations package covers the entire standard Node web stack — Express, HTTP/HTTPS, every major database driver (pg, mysql, mongodb, redis, ioredis), every major message queue (kafkajs, amqplib), and gRPC. The single gap that matters for this milestone is the `ws` library (WebSocket server), which has no auto-instrumentation as of `@opentelemetry/auto-instrumentations-node@0.50.0`. The fix is the manual `tracer.startSpan('broadcast-to-clients')` call shown in the comment — it produces a span as a child of the inbound Kafka consumer span, which is what links the broadcaster's WebSocket fan-out to the original `POST /api/orders` request that triggered the chain.

## Django OTel integration (Python)

Python's OTel story is split across two packages: `opentelemetry-distro` (the SDK + common exporters) and `opentelemetry-instrumentation-*` (one per library — `instrumentation-django`, `instrumentation-psycopg2`, `instrumentation-confluent-kafka`, `instrumentation-redis`, `instrumentation-requests`). The `opentelemetry-bootstrap -a install` command inspects the project's `pyproject.toml` and installs the right instrumentation packages for every dependency it finds — no manual package list to maintain.

The instrumentation is applied via the `opentelemetry-instrument` CLI wrapper, which sets up the SDK and patches the libraries at import time. The `ENTRYPOINT` in the Dockerfile becomes `opentelemetry-instrument python -m ...`:

```dockerfile
ENTRYPOINT ["opentelemetry-instrument", \
  "--service_name", "python-analytics", \
  "--exporter_otlp_endpoint", "http://otel-collector:4317", \
  "--exporter_otlp_protocol", "grpc", \
  "--resource_attributes", "service.namespace=milestone5,deployment.environment=local", \
  "--traces_exporter", "otlp", \
  "--metrics_exporter", "otlp", \
  "--logs_exporter", "otlp", \
  "--auto_instrumentation_enabled", "true", \
  "python", "-m", "analytics.consumer"]
```

The Python analytics consumer does no manual instrumentation — the `opentelemetry-instrument` wrapper patches `confluent_kafka.Consumer.poll()`, `psycopg2.connect()`, `redis.Redis.get()`, and `requests.get()` at import time, so every call automatically produces a span as a child of the inbound Kafka consumer span. The only manual code is for the analytics rollup computation, which is application logic that no library can auto-instrument:

```python
# services/python-analytics/src/analytics/rollup.py
from opentelemetry import trace

tracer = trace.get_tracer(__name__)

class RollupService:
    def __init__(self, db):
        self.db = db  # psycopg2 connection, auto-instrumented

    def aggregate_hourly(self, hour_start: datetime) -> dict:
        # start_span creates a child span of the currently-active span
        # (which is the Kafka consumer span from the auto-instrumentation).
        with tracer.start_as_current_span(
            "RollupService.aggregate_hourly",
            attributes={
                "rollup.hour_start": hour_start.isoformat(),
                "rollup.window": "1h",
            },
        ) as span:
            # psycopg2 execute is auto-instrumented: child span "INSERT rollups"
            with self.db.cursor() as cur:
                cur.execute("""
                    INSERT INTO hourly_rollups(hour_start, order_count, total_cents)
                    SELECT %s, COUNT(*), SUM(total_cents)
                    FROM orders WHERE created_at >= %s AND created_at < %s
                    ON CONFLICT (hour_start) DO UPDATE SET
                      order_count = EXCLUDED.order_count,
                      total_cents = EXCLUDED.total_cents
                """, (hour_start, hour_start, hour_start + timedelta(hours=1)))
                rowcount = cur.rowcount

            span.set_attribute("rollup.rows_written", rowcount)
            return {"hour_start": hour_start, "rows": rowcount}
```

The Python OTel SDK's `start_as_current_span` context manager is the idiomatic equivalent of Java's `@WithSpan` — it creates a span, makes it the active span for the duration of the `with` block (so any auto-instrumented calls within the block become children of this span), and ends the span when the block exits. The `attributes` dict on `start_as_current_span` and the `span.set_attribute()` call inside the block are both ways to attach structured data to the span that becomes filterable in Jaeger.

## Laravel OTel integration (PHP)

PHP's OTel story is the most manual of the four ecosystems because PHP-FPM's process model (fork-per-request, no long-lived process) makes auto-instrumentation harder — every request must re-initialize the SDK, which adds ~5 ms to request latency. The `open-telemetry/sdk` Composer package plus `open-telemetry/opentelemetry-auto-slim` (or `open-telemetry/opentelemetry-auto-laravel` for Laravel) provides auto-instrumentation via PHP's `ext-opentelemetry` extension, which hooks into the framework's event system at bootstrap time.

```php
// services/php-invoice/src/bootstrap/app.php
// Add to the Laravel bootstrap configuration

use OpenTelemetry\SDK\Trace\TracerProviderFactory;
use OpenTelemetry\SDK\Trace\SpanExporter\OtlpGrpcExporter;
use OpenTelemetry\SDK\Trace\SpanProcessor\BatchSpanProcessorBuilder;
use OpenTelemetry\SDK\Common\Attribute\Attributes;
use OpenTelemetry\SDK\Resource\ResourceInfo;
use OpenTelemetry\SemConv\ResourceAttributes;
use OpenTelemetry\API\Trace\TracerInterface;
use Grpc\Channel;

return Application::configure(basePath: dirname(__DIR__))
    ->withRouting(
        web: __DIR__.'/../routes/web.php',
        api: __DIR__.'/../routes/api.php',
        commands: __DIR__.'/../routes/console.php',
        health: '/up',
    )
    ->withMiddleware(function (Middleware $middleware) {
        // The auto-instrumentation package registers its own middleware to
        // create a server span for every inbound request. We just need to
        // ensure the SDK is bootstrapped before the middleware runs.

        $resource = ResourceInfo::create(Attributes::create([
            ResourceAttributes::SERVICE_NAME => 'php-invoice-admin',
            ResourceAttributes::SERVICE_NAMESPACE => 'milestone5',
            ResourceAttributes::DEPLOYMENT_ENVIRONMENT => env('APP_ENV', 'local'),
        ]));

        $exporter = new OtlpGrpcExporter(
            env('OTEL_EXPORTER_OTLP_ENDPOINT', 'http://otel-collector:4317')
        );

        $spanProcessor = (new BatchSpanProcessorBuilder($exporter))
            ->setExportTimeout(2000)  // 2s timeout per batch export
            ->setMaxQueueSize(2048)  // max spans buffered before flush
            ->build();

        $provider = (new TracerProviderFactory())
            ->setResource($resource)
            ->addSpanProcessor($spanProcessor)
            ->build();

        \OpenTelemetry\SDK\Common\GlobalLoggerHolder::initializer()
            ->setLogger(app(\Psr\Log\LoggerInterface::class));

        // Register the provider globally so the auto-instrumentation middleware
        // can pick it up.
        \OpenTelemetry\API\Common\Instrumentation\Globals::tracerProviderProvider()
            ->set($provider);
    })
    ->create();
```

For the Laravel queue worker (the Kafka consumer that processes invoice-generation jobs), the auto-instrumentation does not cover the `queue:work` command — the package auto-instruments HTTP requests via middleware, not CLI commands. The worker requires manual span creation around the job-processing loop:

```php
// services/php-invoice/src/app/Listeners/TraceJobProcessing.php
namespace App\Listeners;

use Illuminate\Queue\Events\JobProcessing;
use Illuminate\Queue\Events\JobProcessed;
use Illuminate\Queue\Events\JobFailed;
use OpenTelemetry\API\Trace\TracerInterface;
use OpenTelemetry\API\Trace\SpanInterface;
use OpenTelemetry\Context\Context;

class TraceJobProcessing
{
    private TracerInterface $tracer;
    private static array $spans = [];

    public function __construct(TracerInterface $tracer)
    {
        $this->tracer = $tracer;
    }

    public function handleJobProcessing(JobProcessing $event): void
    {
        // Extract the traceparent from the Kafka message headers (injected by
        // the producer's auto-instrumentation). Laravel's Kafka adapter exposes
        // raw headers via $event->job->payload()['headers'].
        $headers = $event->job->payload()['headers'] ?? [];
        $traceparent = null;
        foreach ($headers as $h) {
            if ($h['key'] === 'traceparent') { $traceparent = $h['value']; break; }
        }

        $context = $traceparent
            ? \OpenTelemetry\API\Trace\Propagation\TraceContextPropagator::getInstance()
                ->extract(['traceparent' => $traceparent])
            : Context::getCurrent();

        $span = $this->tracer
            ->spanBuilder("process {$event->job->resolveName()}")
            ->setParent($context)
            ->setSpanKind(\OpenTelemetry\API\Trace\SpanKind::KIND_CONSUMER)
            ->setAttribute('messaging.system', 'kafka')
            ->setAttribute('messaging.destination', $event->job->getQueue())
            ->startSpan();

        self::$spans[$event->job->getJobId()] = $span;
        // Make this span the active span so any PDO calls within the job
        // handler become children of it.
        $span->activate();
    }

    public function handleJobProcessed(JobProcessed $event): void
    {
        if (isset(self::$spans[$event->job->getJobId()])) {
            self::$spans[$event->job->getJobId()]->end();
            unset(self::$spans[$event->job->getJobId()]);
        }
    }

    public function handleJobFailed(JobFailed $event): void
    {
        if (isset(self::$spans[$event->job->getJobId()])) {
            $span = self::$spans[$event->job->getJobId()];
            $span->setStatus(\OpenTelemetry\API\Trace\StatusCode::ERROR, $event->exception->getMessage());
            $span->recordException($event->exception);
            $span->end();
            unset(self::$spans[$event->job->getJobId()]);
        }
    }
}
```

Register the listener in `EventServiceProvider`:

```php
protected $listen = [
    JobProcessing::class => [TraceJobProcessing::class . '@handleJobProcessing'],
    JobProcessed::class  => [TraceJobProcessing::class . '@handleJobProcessed'],
    JobFailed::class     => [TraceJobProcessing::class . '@handleJobFailed'],
];
```

The trace-context extraction from Kafka headers is the part that makes the trace actually span the Kafka boundary. The Spring Boot producer's `KafkaTemplate.send()` is auto-instrumented to inject `traceparent` as a Kafka message header; the Laravel worker must extract that header and use it as the parent context for the consumer span. Without this extraction, every Kafka consumer span starts a new trace — the chain is broken at the queue boundary, and Jaeger shows disconnected traces for each side of the queue. The same pattern applies to the Python `confluent-kafka` consumer (which is auto-instrumented to extract `traceparent` from headers) and the Node `kafkajs` consumer (also auto-instrumented); only Laravel requires manual extraction because the auto-instrumentation package does not cover the Laravel-Kafka adapter.

## Trace propagation verification

The end-to-end verification is a single curl command that injects a known `traceparent` and a Jaeger query that confirms the trace has the expected span count:

```bash
# 1. Generate a known trace ID
TRACE_ID=$(openssl rand -hex 16)
SPAN_ID=$(openssl rand -hex 8)
TRACEPARENT="00-${TRACE_ID}-${SPAN_ID}-01"
echo "Searching for trace_id=$TRACE_ID in Jaeger"

# 2. Send a request through Nginx with the traceparent header
curl -sk -H "traceparent: $TRACEPARENT" \
     -H "Content-Type: application/json" \
     -X POST -d '{"customer_id":"alice","total_cents":4200,"items":[{"sku":"A1","qty":1}]}' \
     https://localhost/api/orders

# 3. Wait for the OTel Collector's batch processor to flush (5s default)
sleep 6

# 4. Query Jaeger for the trace
curl -s "http://localhost:16686/api/traces/${TRACE_ID}" | jq '
  .data[0].spans | map({name, service: .process.serviceName, parent: .parentSpanID})'

# Expected output: 8+ spans across 6 services:
#   ┌─ nginx (proxy_pass /api/orders)
#   ├─ spring-order (GET /api/orders)
#   │  ├─ spring-order (OrderService.placeOrder)
#   │  │  ├─ spring-order (INSERT orders)        ← JDBC
#   │  │  ├─ spring-order (orders.events send)   ← Kafka producer
#   │  │  └─ spring-order (Redis SET idempotency)
#   │  ├─ python-analytics (poll orders.events)  ← Kafka consumer
#   │  │  └─ python-analytics (INSERT rollups)   ← psycopg2
#   │  ├─ node-broadcaster (poll orders.events)  ← Kafka consumer
#   │  │  └─ node-broadcaster (broadcast-to-clients)  ← manual span
#   │  └─ php-invoice-worker (process invoice job)  ← Laravel listener
#   │     └─ php-invoice-worker (INSERT invoices)  ← PDO
```

If the trace has fewer than 8 spans or is missing a service, the instrumentation for that service is broken. The most common breakages are: (a) the Kafka consumer's `traceparent` header extraction is missing — the consumer's poll span starts a new trace instead of joining the producer's trace; (b) the OTel Collector's `tail_sampling` policy dropped the trace because it was fast and successful and the 1 % probabilistic sampling missed it — re-run with the `OTEL_TRACES_SAMPLER=parentbased_always_on` environment variable on the producer to force 100 % sampling; (c) the service's `OTEL_EXPORTER_OTLP_ENDPOINT` points to the wrong port (4318 is HTTP, 4317 is gRPC — they are not interchangeable).

## What This Teaches

The first lesson this note teaches is the **zero-code-instrumentation ideal** that the JVM `-javaagent` model achieves and every other ecosystem aspires to. Spring Boot's OTel integration is two lines in a Dockerfile (`COPY` the agent, add `-javaagent` to `ENTRYPOINT`) and zero source code changes — every library call becomes a span automatically. Node, Python, and PHP all require an SDK initialization file (10-30 lines) plus an import/wrapper, but the auto-instrumentation packages still cover the vast majority of code paths without source changes. The lesson is that instrumentation should be a property of the runtime, not the application — when every library call is instrumented by default, the application code stays focused on business logic and the observability is "free" (in code; the runtime cost is 5-10 % CPU).

The second lesson is the **trace-context propagation as the contract** that every cross-service hop must honor. The W3C `traceparent` header is the lingua franca: every HTTP client must inject it, every HTTP server must extract it, every Kafka producer must inject it as a message header, every Kafka consumer must extract it from headers, every Redis command propagates it via connection-level context (the OTel Redis instrumentation handles this automatically), and every Postgres query propagates it via the `pg_tracing` extension or the JDBC wrapper. The lesson is that any cross-service boundary that does not propagate `traceparent` breaks the trace chain — a single missing injection point produces two disconnected traces in Jaeger, and the operator cannot tell which side of the boundary the bug is on without reading the code.

The third lesson is the **OTel Collector as the single observability ingress** that decouples the services from the backends. Services emit OTLP to the Collector; the Collector transforms and fans out to Jaeger, Loki, and Prometheus. When you swap Jaeger for Tempo, or Loki for Elasticsearch, or Prometheus for Mimir, the services do not change — only the Collector's exporter configuration changes. The lesson is that emitting OTLP from services is a one-time investment that pays off every time you change your observability backend; emitting backend-specific formats (Zipkin JSON, InfluxDB line protocol, Elasticsearch bulk API) is a recurring cost that you pay every time you migrate.
