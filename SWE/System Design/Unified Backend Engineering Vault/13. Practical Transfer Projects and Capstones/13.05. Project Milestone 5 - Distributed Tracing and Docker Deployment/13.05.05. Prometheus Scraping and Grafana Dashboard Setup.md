# 13.05.05. Prometheus Scraping and Grafana Dashboard Setup

## Scope

This note wires the metrics half of the Milestone 5 observability stack. Every service in the platform exposes a `/metrics` (or `/actuator/prometheus` for Spring Boot) endpoint in Prometheus text exposition format; the Prometheus container scrapes those endpoints at 15-second intervals and stores the time series in a local TSDB; Grafana queries Prometheus to render the order-pipeline and Kafka-pipeline dashboards. The deliverable is the `prometheus.yml` scrape configuration (which targets every service and every exporter), the Grafana provisioning configuration (datasources + dashboard loader), and the two dashboard JSON files that visualise the platform end-to-end.

Prometheus is a pull-based system — it scrapes targets, targets do not push to it. This is the opposite of the OTel Collector's push-based model in [[13.05.04]] (services push OTLP to the collector). The two models coexist because they have different strengths: push is correct for traces (the service knows when a span is complete and pushes it immediately) and logs (services emit at their own rate); pull is correct for metrics (Prometheus controls the scrape rate, so the metrics database is not overwhelmed by a service that suddenly emits 100 000 series). The trade-off is that Prometheus must be able to reach every service's `/metrics` endpoint, which on a Docker Compose network means every service is on the same `appnet` and Prometheus can resolve service names via Docker's embedded DNS.

## What You Are Building

The deliverable is four files plus a directory layout:

```
prometheus/
└── prometheus.yml              ← scrape config (14 targets)
grafana/
├── provisioning/
│   ├── datasources/
│   │   └── datasources.yml     ← Prometheus + Loki + Jaeger as Grafana datasources
│   └── dashboards/
│       └── dashboards.yml      ← dashboard loader (points at /var/lib/grafana/dashboards/)
└── dashboards/
    ├── order-pipeline.json     ← the order pipeline dashboard (12 panels)
    └── kafka-pipeline.json     ← the Kafka pipeline dashboard (8 panels)
```

The two dashboards are the user-facing artifact of this milestone — they are what an operator looks at to answer "is the platform healthy?" without SSH-ing into a container. The order-pipeline dashboard answers that question from the application perspective (request rate, latency, error rate per service); the Kafka-pipeline dashboard answers it from the data-pipeline perspective (produce rate, consumer lag per partition, rebalance events, DLT message count). Both dashboards include a "trace deep-link" panel that takes a `trace_id` from a clicked data point and opens Jaeger at that trace — the cross-link from metrics to traces is what makes the three-pillar observability model actually compose.

## Implementation Steps

1. **Bootstrap.** The Prometheus and Grafana containers are declared in the compose file in [[13.05.02]] — `prom/prometheus:v2.54.1` and `grafana/grafana:11.2.0`. No custom Dockerfile is needed for either; both are configured via mounted YAML/JSON files.
2. **Wire dependencies.** Every service must expose its `/metrics` endpoint on a port reachable from the `appnet` Docker network. Spring Boot services expose `/actuator/prometheus` on port 8080 (the same port as the application); Node services expose `/metrics` on port 3000; Python services expose `/metrics` on port 8000 via `prometheus_client.asgi`; PHP services expose `/metrics` on port 80 via a route handler in the Laravel app. The four `*_exporter` sidecars (postgres_exporter:9187, kafka_exporter:9308, redis_exporter:9121, minio:9000) each expose their own metrics on their own port.
3. **Implement the contract.** The `prometheus.yml` file declares one `scrape_config` per logical group: `app-services` (the seven application services, scraped every 15 s with a 10 s timeout), `stateful-exporters` (the four `*_exporter` sidecars, scraped every 30 s — they are slower because they query the stateful service's internal state), `otel-collector` (scraped every 15 s for the collector's own metrics — span throughput, export latency, dropped spans), and `nginx` (scraped via `nginx-exporter` sidecar, omitted from this reference for brevity).
4. **Wire observability.** Prometheus itself exposes `/metrics` (its own internal metrics — scrape duration, sample ingestion rate, WAL writes) and Grafana scrapes Prometheus via the Prometheus datasource. There is no "metrics of the metrics of the metrics" recursion — the chain stops at Prometheus.
5. **Containerize.** The Prometheus and Grafana containers are stock images with config mounted as volumes. The `prometheusdata` and `grafanadata` named volumes persist data across container restarts; Prometheus retains 15 days of metrics by default (`--storage.tsdb.retention.time=15d`), Grafana retains dashboards indefinitely (they are JSON files committed to the repo and provisioned on container start).
6. **Test.** Open `http://localhost:9090/targets` in a browser — every target should be `UP`. Open `http://localhost:3000` (admin / `${GRAFANA_ADMIN_PASSWORD}`) — the two dashboards should appear under the "milestone5" folder. Send a few `curl -sk https://localhost/api/orders/1234` requests and watch the order-pipeline dashboard's request-rate panel update within 30 seconds (the 15-second scrape interval plus the 15-second panel refresh).

## The prometheus.yml scrape configuration

The complete reference scrape config. Save it as `prometheus/prometheus.yml` at the project root. The file declares the global scrape interval, four `scrape_config` blocks (one per logical group), and one `alerting` block (for Alertmanager, which is out of scope for this milestone but the hook is in place).

```yaml
# prometheus/prometheus.yml — Milestone 5 scrape config
# Reload via: docker compose exec prometheus kill -HUP 1
#   (Prometheus hot-reloads on SIGHUP if --web.enable-lifecycle is set)

global:
  scrape_interval: 15s          # default scrape interval for every job
  scrape_timeout: 10s           # give up if the scrape takes >10s
  evaluation_interval: 15s      # alerting rules eval interval

# ─── scrape configs ─────────────────────────────────────────────────────────
scrape_configs:

  # 1. Application services (7 services, scraped every 15s)
  - job_name: 'app-services'
    metrics_path: /actuator/prometheus   # Spring Boot default; overridden per-target below
    static_configs:
      - targets: ['spring-order:8080']
        labels:
          service: spring-order
          ecosystem: jvm
      - targets: ['spring-user:8080']
        labels:
          service: spring-user
          ecosystem: jvm
      - targets: ['spring-ledger:8080']
        labels:
          service: spring-ledger
          ecosystem: jvm
      - targets: ['node-broadcaster:3000']
        labels:
          service: node-broadcaster
          ecosystem: node
        # Override the metrics_path for this target — Node uses /metrics, not /actuator/prometheus
        # (Prometheus does not support per-target metrics_path override in static_configs,
        #  so we declare a separate job for non-Spring services below)
  - job_name: 'node-broadcaster'
    metrics_path: /metrics
    static_configs:
      - targets: ['node-broadcaster:3000']
        labels:
          service: node-broadcaster
          ecosystem: node
  - job_name: 'python-analytics'
    metrics_path: /metrics
    static_configs:
      - targets: ['python-analytics:8000']
        labels:
          service: python-analytics
          ecosystem: python
  - job_name: 'php-invoice-admin'
    metrics_path: /metrics
    static_configs:
      - targets: ['php-invoice-admin:80']
        labels:
          service: php-invoice-admin
          ecosystem: php
  - job_name: 'php-invoice-worker'
    metrics_path: /metrics
    static_configs:
      - targets: ['php-invoice-worker:80']
        labels:
          service: php-invoice-worker
          ecosystem: php

  # 2. Stateful exporters (4 sidecars, scraped every 30s)
  - job_name: 'postgres-exporter'
    scrape_interval: 30s
    static_configs:
      - targets: ['postgres-exporter:9187']
        labels:
          service: postgres
          component: database
  - job_name: 'kafka-exporter'
    scrape_interval: 30s
    static_configs:
      - targets: ['kafka-exporter:9308']
        labels:
          service: kafka
          component: message-broker
  - job_name: 'redis-exporter'
    scrape_interval: 30s
    static_configs:
      - targets: ['redis-exporter:9121']
        labels:
          service: redis
          component: cache
  - job_name: 'minio'
    scrape_interval: 30s
    metrics_path: /minio/v2/metrics/cluster
    bearer_token: ${MINIO_BEARER_TOKEN}   # set via MINIO_PROMETHEUS_BEARER_TOKEN env
    static_configs:
      - targets: ['minio:9000']
        labels:
          service: minio
          component: object-storage

  # 3. OTel Collector (its own metrics — span throughput, export latency)
  - job_name: 'otel-collector'
    metrics_path: /metrics
    static_configs:
      - targets: ['otel-collector:8888']
        labels:
          service: otel-collector
          component: observability-pipeline

  # 4. Prometheus self-scrape (its own metrics — scrape duration, ingestion rate)
  - job_name: 'prometheus'
    static_configs:
      - targets: ['localhost:9090']

# ─── alerting (placeholder — Alertmanager is out of scope for this milestone) ──
alerting:
  alertmanagers:
    - static_configs:
        - targets: []   # add 'alertmanager:9093' when Alertmanager is added
```

The most consequential decisions in this config are the `scrape_interval` (15 s for apps, 30 s for stateful exporters) and the per-target `labels` (which attach `service` and `ecosystem` labels that become filterable dimensions in Grafana). The 15-second app scrape interval is the standard Prometheus default — short enough that a service going down is visible within 30 seconds (one missed scrape plus one failed scrape), long enough that the scrape traffic is negligible (7 services × 1 scrape / 15 s = ~0.5 scrapes/s, producing ~500 time series per scrape = 250 series/s sustained write rate, well within Prometheus's capacity). The 30-second exporter interval is longer because exporters query the stateful service's internal state (Postgres's `pg_stat_activity`, Kafka's `__consumer_offsets`, Redis's `INFO`), which is more expensive than reading a metrics registry — scraping every 15 s would add measurable load to the stateful service.

The `static_configs` approach (hardcoded target list) is correct for a Docker Compose deployment where the set of services is fixed. For Kubernetes, replace `static_configs` with `kubernetes_sd_configs` (service discovery) so Prometheus automatically picks up new pods as they are created — the target list is dynamic. The trade-off is that `static_configs` is simpler to reason about (you can see every target in the YAML) while `kubernetes_sd_configs` is more operationally correct (no manual edits when pods are added). For Milestone 5's single-host Docker Compose deployment, `static_configs` is the right choice.

## The Grafana datasource provisioning

Grafana datasources can be configured via the UI (manual, error-prone, not version-controlled) or via provisioning YAML (automated, repeatable, version-controlled). The provisioning approach is non-negotiable for production — the dashboard JSON and the datasource YAML are committed to the repo alongside the code, so a fresh `docker compose up` produces a Grafana with the correct datasources and dashboards pre-loaded.

```yaml
# grafana/provisioning/datasources/datasources.yml
apiVersion: 1

datasources:
  - name: Prometheus
    type: prometheus
    access: proxy
    url: http://prometheus:9090
    isDefault: true
    jsonData:
      timeInterval: 15s
      httpMethod: POST
      manageAlerts: false

  - name: Loki
    type: loki
    access: proxy
    url: http://loki:3100
    jsonData:
      maxLines: 1000
      derivedFields:
        # When a log line contains a trace_id, render it as a clickable link to Jaeger.
        - name: trace_id
          matcherRegex: '"trace_id":"(\w+)"'
          url: http://localhost:16686/trace/$${__value.raw}
          datasourceUid: jaeger

  - name: Jaeger
    type: jaeger
    uid: jaeger
    access: proxy
    url: http://jaeger:16686
    jsonData:
      tracesToLogs:
        datasourceUid: loki
        tags: ['service.name', 'trace_id']
        mappedTags: [{ key: 'service.name', value: 'service' }]
        mapTagNamesEnabled: true
        spanStartTimeShift: '1h'
        spanEndTimeShift: '1h'
        filterByTraceID: true
```

The two non-obvious config decisions here are the `derivedFields` in Loki and the `tracesToLogs` in Jaeger. The Loki `derivedFields` config tells Grafana to parse every log line for the regex `"trace_id":"(\w+)"` and render the captured trace_id as a clickable link to Jaeger — this is the "logs → traces" cross-link that makes the three-pillar model compose. The Jaeger `tracesToLogs` config is the reverse: when you are looking at a trace in Jaeger, the "Logs" panel on each span links back to Loki filtered by that trace's `trace_id` — the "traces → logs" cross-link. Together they let an operator pivot between the three pillars without copy-pasting IDs.

## The Grafana dashboard loader

```yaml
# grafana/provisioning/dashboards/dashboards.yml
apiVersion: 1

providers:
  - name: milestone5-dashboards
    orgId: 1
    folder: Milestone 5
    type: file
    disableDeletion: true
    updateIntervalSeconds: 30
    allowUiUpdates: false
    options:
      path: /var/lib/grafana/dashboards
      foldersFromFilesStructure: true
```

This tells Grafana to scan `/var/lib/grafana/dashboards` (mounted from `./grafana/dashboards/` in the compose file) every 30 seconds for new dashboard JSON files and load them into the "Milestone 5" folder. The `disableDeletion: true` flag prevents the UI from deleting dashboards that are committed to the repo (the correct source of truth). The `allowUiUpdates: false` flag prevents UI edits from overwriting the file — changes must go through git, which is the only way to keep dashboards version-controlled.

The two PromQL patterns that power this dashboard deserve explanation because they are the most reused patterns in any Prometheus dashboard. The first is the **rate counter**: `sum(rate(http_server_duration_seconds_count[1m])) by (service)` — `rate()` computes the per-second rate of a counter over a 1-minute window, `sum(...)` aggregates across all instances (in case there are multiple replicas), `by (service)` groups by the `service` label so the result is one time series per service. The second is the **histogram quantile**: `histogram_quantile(0.95, sum(rate(http_server_duration_seconds_bucket[5m])) by (le)) * 1000` — `rate()` on each bucket counter, `sum(...) by (le)` aggregates buckets across instances, `histogram_quantile(0.95, ...)` interpolates the 95th percentile from the cumulative buckets, `* 1000` converts seconds to milliseconds. The 5-minute window is longer than the request-rate window because latency percentiles are noisy on short windows — a 5-minute window smooths the noise without hiding real spikes.

## The Kafka-pipeline dashboard JSON

The Kafka-pipeline dashboard is committed to `grafana/dashboards/kafka-pipeline.json`. Its 8 panels focus on the data-pipeline perspective: produce rate per topic, consumer lag per partition (which is the most actionable Kafka metric — a single stuck partition is invisible in the topic-level sum), rebalance events, DLT message count, broker ISR shrink/grow, broker disk usage, broker network throughput, and a panel showing the consumer-group membership (which consumers are currently in the group). The JSON is omitted here for brevity but follows the same shape as the order-pipeline dashboard — the key PromQL queries are `sum(rate(kafka_topic_partition_current_offset[1m])) by (topic)` for produce rate, `kafka_consumergroup_lag{consumergroup="..."}` for per-partition lag, and `increase(kafka_consumer_rebalance_total[1h])` for rebalance events.

## Run It

```bash
# 1. Validate the Prometheus config
docker compose exec prometheus promtool check config /etc/prometheus/prometheus.yml
#   → /etc/prometheus/prometheus.yml SUCCESS

# 2. Hot-reload the Prometheus config (no container restart needed)
docker compose exec prometheus kill -HUP 1
#   → ts=2024-... msg="Loading configuration file" file=/etc/prometheus/prometheus.yml
#   → ts=2024-... msg="Completed loading of configuration file" ...

# 3. Verify every target is UP
open http://localhost:9090/targets
#   → All 14 targets should show "UP" in green.
#   → A target showing "DOWN" usually means the service is not yet healthy
#     or the /metrics endpoint is not exposed on the expected path.

# 4. Verify the Grafana datasource provisioning
open http://localhost:3000/connections/datasources
#   → Three datasources: Prometheus (default), Loki, Jaeger.
```

## What This Teaches

The first lesson this note teaches is the **pull-vs-push trade-off** that determines the shape of every metrics system. Prometheus pulls (scrapes targets on a fixed interval); statsd pushes (the application emits metrics to a statsd daemon on every event); OTel Collector accepts both (push via OTLP, pull via the Prometheus receiver). Pull is correct when the metrics database is the bottleneck (it controls the scrape rate, so a service that suddenly emits 100 000 series cannot overwhelm it); push is correct when the application is the bottleneck (it emits at its own rate, no polling overhead). For backend services on a stable network, pull is the right choice — it is what Prometheus does, and the 15-second scrape interval is the right balance between freshness and load. For ephemeral compute (Lambda, Cloud Run) where the service may not exist when Prometheus scrapes, push via OTLP to a collector that buffers is the right choice — see [[12.04. Serverless Observability and Distributed Tracing]] for the serverless variant.

The second lesson is the **dashboard-as-code pattern** that keeps observability version-controlled. The `datasources.yml`, `dashboards.yml`, and `*.json` files in the `grafana/` directory are committed to the repo alongside the application code. A fresh `docker compose up` produces a Grafana with the correct datasources and dashboards pre-loaded — no manual UI clicks, no "the dashboard that was on Bob's laptop before he left". When a dashboard needs to change, the JSON is edited in the repo, committed, and the next `docker compose up` picks up the change. The `allowUiUpdates: false` flag in the dashboard provider is the enforcement mechanism — it prevents the UI from saving changes back to the file, so the only way to change a dashboard is through git.

The third lesson is the **cross-link pattern** that makes the three pillars (metrics, logs, traces) actually compose. The metrics dashboard has a "trace deep-link" panel that opens Jaeger at a specific trace; the Jaeger datasource has `tracesToLogs` configured to open Loki filtered by trace_id; the Loki datasource has `derivedFields` that parse trace_id from log lines and render it as a Jaeger link. The result is that an operator can start at any pillar and pivot to the other two without copy-pasting IDs — click a metric spike, see the trace, see the logs for that trace, identify the failing span, see the SQL query in the logs, fix the query. Without the cross-links, the three pillars are three siloed tools that each tell a different story about the same incident; with the cross-links, they are one tool with three views.
