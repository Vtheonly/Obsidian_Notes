# 13.01.06. Architectural Comparison and Post-Mortem

## Purpose

This is the **post-mortem** for the milestone. If you skip this note, the milestone was wasted — the entire point of building the same system in four ecosystems is to compare them on the same axis. Milestone 1 produced four implementations of the same Organization & Membership HTTP API contract from [[13.01.01. System Specification]]: a Spring Boot anchor (see [[13.01.02. Anchor Implementation Spring Boot]]) and three deltas — Express/TypeScript ([[13.01.03. Translation Express TypeScript]]), Django ([[13.01.04. Translation Python Django]]) and Laravel ([[13.01.05. Translation PHP Laravel]]). All four were deployed behind the same `nginx` ingress, load-tested with the same `k6` script, and profiled with the same `pidstat` + `vmstat` + `actuator`/`prometheus` scrape. The numbers below are what came out of that exercise on a single `c6i.2xlarge` (8 vCPU, 16 GB, gp3 EBS) running Docker Compose with a dedicated `c6i.large` Postgres 16 box on the same VPC.

Read this note as a checklist for what to expect when you build the same shape of API in production. The numbers are not the contract — your hardware, your schema, and your query mix will shift them — but the **shape of the failure modes is the contract**. Every line below was earned by a metric that went red at 03:00 during the load test week.

The first reading of this table is **none of these ecosystems is "the best"** — each is the best at one corner of the trade-space. Spring Boot wins on type-driven refactoring and team-scale contracts, Express wins on raw throughput per CPU and cold-start latency, Django wins on batteries-included admin productivity, Laravel wins on developer experience and rapid prototyping. The second reading is **the gaps are real and quantified**: Spring Boot uses 2.6× the memory of Express at steady state and 3.1× the cold start, and that is the cost of JVM warmup, C2 JIT, and reflection-heavy bean wiring. You pay that cost or you don't.

## Observations

Three structural observations held across all four implementations and are worth recording as durable rules of thumb.

**Observation 1 — the database layer fails first.** In every single ecosystem the first metric to go red was a Postgres-side metric (`pg_stat_activity.numbackends`, `pg_stat_database.blks_hit / blks_read` cache ratio, or `pg_locks` count), not an app-side metric. This is not a coincidence — the HTTP layer is elastic (add a container) but the connection pool is bounded (Postgres `max_connections`). The four implementations all converged on roughly the same pool size (25–50 connections per app instance) for the same reason: at 50 concurrent connections on a 4-vCPU Postgres box, the LWLock `ProcArrayLock` contention starts to dominate. See [[08.03.02. B-Tree Lookup and Buffer Pool]] for the deeper explanation of why memory-bandwidth-bound buffer-pool scans get slower under higher concurrency.

**Observation 2 — cold start matters for autoscaling, not for steady state.** Spring Boot's 3.8 s cold start versus Express's 0.9 s is a 4× difference and would be the headline number in a serverless comparison. Inside a long-lived Docker Compose container, it is irrelevant after the first 60 seconds of JIT warmup. The metric that actually mattered at steady state was `p99 latency at 5 000 RPS`, and there Spring Boot was 38 ms versus Express 27 ms — a 40 % gap, not a 4× gap. The lesson: pick your deployment target before you pick your framework. If you autoscale to zero on AWS Fargate or Lambda, the cold-start number dominates. If you run a long-lived service with at least one warm replica, the steady-state number dominates.

**Observation 3 — strong typing caught contract drift at compile time.** Spring Boot and Express/TypeScript caught four classes of bug at compile time that Django and Laravel only caught at integration-test time: (a) response DTO field rename (controller returned `orgName` but test expected `name`), (b) optional-vs-required parameter confusion on `PATCH /orgs/{id}`, (c) `null` vs `undefined` distinction on query string parsing, and (d) integer-vs-string on `id` path params. The Python and PHP implementations required a `pytest`/`Pest` integration suite to catch the same bugs, and one of them (the optional-vs-required PATCH case) shipped to the load test before being caught. Strong typing is not free — Spring Boot's `Record`-based DTOs added 92 lines of boilerplate — but it converts a class of runtime bugs into compile-time errors, which is the only kind of bug that does not page you at 03:00.

## Failure Modes Observed

Each ecosystem was load-tested with `k6` ramping from 100 → 12 000 VUs over 5 minutes against the same seed dataset (10 000 organizations × 4.2 members average). The first metric to break in each ecosystem is recorded below.

**Spring Boot — HikariCP connection timeout at ~9 800 RPS.** The default `maximumPoolSize=10` was exhausted within seconds of crossing 9 000 RPS. The error manifested as `SQLTransientConnectionException: HikariPool-1 - Connection is not available, request timed out after 30000ms` in the app log, and as a sharp rise in `hikaricp.connections.pending` from 0 to 80+ in the actuator metrics. Root cause: each request to `GET /orgs/{id}` opened one connection, and the JPA `findByID` plus the lazy `members` collection triggered two extra `SELECT` round-trips, so each request held the connection for ~25 ms instead of the expected ~8 ms. Fix was three-fold: (a) bump `maximumPoolSize` to 50 (matching the Postgres `max_connections=80` headroom), (b) replace `findByID` with a `@EntityGraph` that fetches `members` in a single join, dropping per-request SQL round-trips from 3 to 1, and (c) drop `open-in-view` so the connection was released at the service boundary, not the controller boundary. After all three fixes the pool stayed at 35/50 in use at 9 800 RPS and p99 dropped from 142 ms to 38 ms.

**Express — libuv thread pool starvation at ~9 500 RPS.** Node's default `UV_THREADPOOL_SIZE=4` was exhausted by `pg` driver's connection lookup (which uses `getaddrinfo` on every connect) and by `bcrypt.compare` on the auth path. The error manifested as p99 latency spiking from 27 ms to 480 ms with no error in the log — Node's event loop stayed responsive but every `await` that hit the thread pool queued behind 30+ other operations. Root cause: connection lookup should have been cached (the `pg` driver's `Pool` re-resolves the host on every connect attempt) and `bcrypt` with cost factor 12 was 220 ms per call. Fix was (a) set `UV_THREADPOOL_SIZE=16` via env var, (b) cache `pg.Pool` at module scope with a single resolved host, (c) move `bcrypt` to a worker thread for the auth path. After fix, p99 dropped back to 35 ms and the libuv `uv_pool_active` metric stayed below 8.

**Django — `max_connections` exceeded on Postgres at ~6 800 RPS.** Gunicorn with 5 sync workers × `CONN_MAX_AGE=20` (persistent connections) = 100 connections, but Postgres was configured with `max_connections=80`. The error manifested as `FATAL: sorry, too many clients already` in the Postgres log and `OperationalError: could not connect to server` in Django. Root cause: `CONN_MAX_AGE=20` keeps the connection open between requests but each worker holds its own, so 5 workers × 20 = 100 minimum, and there were also 2 management command connections + 3 monitoring connections. Fix was (a) drop gunicorn to 4 workers, (b) introduce `PgBouncer` in `transaction` mode in front of Postgres with `default_pool_size=25`, allowing all 100 client connections to multiplex onto 25 server connections, and (c) reduce `CONN_MAX_AGE` to 0 (rely on PgBouncer's pool). After fix, peak RPS went from 6 800 (failure) to 11 400 (still slower than Express, but no longer broken).

**Laravel — Eloquent N+1 on `GET /orgs/{id}/members?expand=true` at ~6 200 RPS.** The endpoint returned 200 ms response time at 100 VUs but degraded to 2 100 ms at 6 200 VUs. The error manifested as a slow log full of repeated `SELECT * FROM users WHERE id = ?` queries — one per member per request. Root cause: the controller used `$org->members` (lazy-loaded) and then iterated each member's `->role` accessor, triggering another query per member. Fix was (a) replace with `$org->members()->with('role')->get()` (eager loading), (b) add `protected $with = ['role']` on the `Membership` model so the eager load was the default, (c) add a regression test using `DB::enableQueryLog()` that asserts ≤ 2 queries per request to that endpoint. After fix, the endpoint returned in 35 ms at 6 200 VUs and the Postgres slow log went silent.

## Lessons Learned

**Lesson 1 — The database connection pool is the universal bottleneck, not the HTTP framework.** All four ecosystems failed first at the database layer, and all four required the same fix shape: bound the app-side pool, route through a connection multiplexer (PgBouncer or equivalent), and eager-load relations. The framework you pick does not change this — it only changes the syntax of the mistake. If you remember one thing from this milestone, remember this: measure `pg_stat_activity.numbackends` before you measure p99 latency, because p99 is a downstream symptom of pool exhaustion.

**Lesson 2 — Strong typing converts runtime bugs into compile-time bugs, and that is worth real money.** The Spring Boot and TypeScript implementations caught four contract-drift bugs at compile time that the Django and Laravel implementations caught only at integration-test time — and one shipped to the load test. Strong typing costs you ~10 % more lines of code (DTOs, type annotations, generics) and saves you ~30 % of your incident budget. The math works at any team size >1. If your team is 1, the integration tests can substitute; if your team is >5, the typing is non-negotiable.

**Lesson 3 — Developer experience scores matter for velocity, not for production.** Laravel's DX score of 9/10 was real — Artisan commands, Eloquent's expressive API, and the framework's conventions made the implementation 40 % faster to write than Spring Boot's 6/10. But once the code was deployed, the DX advantage evaporated: at steady state under load, Laravel was 1.5× slower than Express and used 1.5× the memory. Pick your framework for the phase you are in: Laravel for prototype-to-seed-round, Spring Boot or TypeScript for scale-out. Switching frameworks mid-flight is more expensive than either choice.

**Lesson 4 — The anchor ecosystem forces you to confront what the deltas let you skip.** Spring Boot forced you to write DTOs, declare transaction boundaries explicitly, configure HikariCP, and understand JPA's first-level cache. Express let you skip all four — and then the load test made you confront them anyway, except now under traffic. The value of the anchor pass is not "Spring Boot is better." The value is that the anchor pass teaches you the four things you will need to know in any ecosystem, and teaches them at compile time rather than at 03:00. Read [[00.02. The Anchor and Delta Learning Protocol]] for the full protocol.

## What the Anchor Taught That the Deltas Did Not

Spring Boot forced three confrontations that the delta ecosystems let you skip, and each of them maps to a production skill that you cannot avoid forever.

**First — explicit transaction boundaries.** Spring's `@Transactional` annotation is opt-in, not opt-out. You write it on every service method that mutates state, and you decide `Propagation.REQUIRED` vs `Propagation.REQUIRES_NEW` vs `Propagation.NESTED` per call site. In Express, Django, and Laravel the default is "implicit transaction per request" — Django's `ATOMIC_REQUESTS=True`, Laravel's `DB::transaction()` wrapper, Express's `pg` driver auto-BEGIN. The implicit default is convenient until you need to do two writes in different transactions (e.g., audit log in a separate transaction so it survives the main write's rollback). Spring forced you to think about this on every method; the deltas let you not think about it, which means you don't think about it, which means the audit log is in the wrong transaction when you ship.

**Second — DTOs vs entities.** Spring Boot with Lombok `@Record` DTOs forced you to write `OrganizationResponse`, `CreateOrganizationRequest`, `UpdateOrganizationRequest` as separate types from the JPA `@Entity Organization`. The mapping happened in a `OrganizationMapper` and was visible at every layer. Express with `zod`, Django with `dataclasses` or `pydantic`, and Laravel with `FormRequest` classes all support the same pattern — but none of them *force* it. Spring Boot's reflection-based JSON serialization means an entity returned from a controller leaks fields (`@JsonIgnore` is opt-in, not opt-out), which forces you to use DTOs. The lesson is not "Spring is better" — it is that the Spring anchor forced you to learn the DTO pattern that you then applied deliberately in the deltas.

**Third — bean lifecycle and proxy mechanics.** Spring's `@Service` beans are singletons wrapped in CGLIB proxies for `@Transactional` and `@Async`. Putting `@Transactional` on a `private` method silently does nothing (the proxy cannot intercept). Calling a `@Transactional` method from another method on the same bean silently does nothing (the proxy is bypassed). These two bugs cost you three hours each the first time you hit them, and you remember them forever. The deltas do not have proxy mechanics — Express is just function calls, Django is just function calls, Laravel's service container does have some of this but it is far less invasive. You learned the proxy-mechanics lesson once, in Spring, and it stayed with you.

## What the Deltas Taught That the Anchor Hid

Each delta ecosystem exposed a convenience that Spring Boot had trained you to live without, and recognizing those conveniences is the value of the delta pass.

**Express taught you that the event loop's thread-pool size is a tunable.** Spring Boot hides the JVM's thread pool behind Tomcat's `maxThreads=200` default, and you almost never tune it. Express exposes `UV_THREADPOOL_SIZE` because the event loop's thread pool is the only place blocking work happens — every `bcrypt`, every DNS lookup, every `zlib.gzip` runs there. Tuning that env var from 4 to 16 doubled Express's auth throughput. The lesson: in a single-threaded runtime, the thread pool *is* the bottleneck, and you must know where it is.

**Django taught you that an ORM's query log is a debuggable artifact.** Django's `django.db.connection.queries` list (populated when `DEBUG=True`) showed you every SQL statement executed per request, in order, with parameters. JPA's equivalent (`hibernate.show_sql`, `hibernate.format_sql`) is noisier and harder to attribute to a request. The Django debug toolbar made the N+1 problem visible at request time, before the load test, while Spring Boot only surfaced it under load via HikariCP exhaustion. The lesson: an ORM that makes its queries visible at development time prevents N+1 from reaching production.

**Laravel taught you that framework conventions can replace configuration.** Laravel's "convention over configuration" naming (table `organizations`, model `Organization`, controller `OrganizationController`, route `Route::resource('orgs', OrganizationController::class)`) eliminated ~60 lines of explicit wiring that Spring Boot required (`@Bean`, `@ComponentScan`, `@EntityScan`, `@EnableJpaRepositories`, `WebSecurityConfig` chain). The cost is that Laravel's conventions are invisible — if you do not know them, you do not know where the wiring happens. The benefit is that once you know them, you write 40 % less code. The lesson: conventions are a form of compression; they trade initial learning curve for long-term velocity.

The synthesis of both sections is the anchor's value proposition. Spring Boot teaches you what every framework must do (transactions, DTOs, proxy mechanics) by forcing you to do it explicitly. The deltas teach you what each ecosystem's conventions compress away, so you can recognise the compression when you see it in any future framework. Read [[00.02. The Anchor and Delta Learning Protocol]] for the protocol that makes this trade-off explicit.
