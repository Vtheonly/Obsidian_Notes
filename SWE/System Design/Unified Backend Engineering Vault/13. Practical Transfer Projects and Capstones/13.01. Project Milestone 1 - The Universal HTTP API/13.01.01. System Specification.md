# 13.01.01. System Specification

## Project Goal

This is a capstone milestone. Unlike concept notes, the goal is to build something that runs end-to-end across multiple ecosystems and survives a load test. You are not done when the code compiles — you are done when you can show a graph of the system failing gracefully under load and recovering.

The concrete business domain is an **Organization and Membership REST API**: a service that lets a platform create organizations (think Slack workspaces, GitHub organizations, or Stripe accounts), list them, update their metadata, soft-delete them, and manage their members. The same eight-endpoint contract is implemented four times — once in Spring Boot (the anchor) and three more times in Express, Django, and Laravel (the deltas). The contract is fixed here; the implementations must match it byte-for-byte at the HTTP layer.

Why this domain: it is small enough to fit in a single milestone, but it forces every cross-cutting concern that a real backend must handle — path parameters, query strings, request-body validation, sub-resource routing, status-code discipline, soft-delete semantics, partial updates (PATCH semantics), uniqueness constraints, role enums, and a structured error format. If your ecosystem can express this contract idiomatically, it can express any CRUD-with-membership contract.

## Requirements

### Requirement 1 — Eight fixed endpoints, no more, no less

The API surface is exactly eight endpoints. Three are on `/orgs` (list, create, retrieve), two mutate a single org (patch, soft-delete), and three are on the `/orgs/{id}/members` sub-resource (list members, add member, remove member). The fixed set is:

- `GET /orgs` — list all organizations (paginated, `?page=1&size=20`).
- `POST /orgs` — create an organization.
- `GET /orgs/{id}` — retrieve a single organization by primary key.
- `PATCH /orgs/{id}` — partially update an organization (only the supplied fields).
- `DELETE /orgs/{id}` — soft-delete an organization (set `deleted_at`, do not row-delete).
- `GET /orgs/{id}/members` — list the members of one organization.
- `POST /orgs/{id}/members` — add a user to an organization with a role.
- `DELETE /orgs/{id}/members/{userId}` — remove a user from an organization.

This is non-negotiable because the four implementations must pass the same test suite (k6, pytest, or Postman). If one ecosystem invents a ninth endpoint (say, `PUT /orgs/{id}` for full replace), the test suite passes on that ecosystem alone and the cross-ecosystem comparison in [[13.01.06. Architectural Comparison and Post-Mortem]] becomes meaningless. PATCH is chosen over PUT deliberately: PUT implies full-replace semantics, which forces the client to send every field; PATCH implies partial update, which is what real UIs want and what exposes the ecosystem's "patch vs merge" convention most clearly.

### Requirement 2 — Dynamic route parameters and query string parsing

Every framework parses path templates like `/orgs/{id}` differently. Spring Boot uses `@PathVariable Long id`; Express uses `req.params.id` (a string that must be coerced); Django's DefaultRouter produces `org_pk`; Laravel's implicit route-model binding resolves the org Eloquent model before the controller runs. The spec requires that `id` and `userId` be treated as **64-bit integers** at the application layer — a non-numeric `id` must produce a 400 response with a structured ProblemDetail body, never a 500 from a deserialization crash, and never a silent 404 that hides the type error.

Query string parsing must distinguish between absent and present-but-empty. `GET /orgs` returns the first page with default `size=20`. `GET /orgs?page=2&size=50` returns the second page of 50. `GET /orgs?size=` (empty value) must be rejected with 400, not silently coerced to 0 or 20. `GET /orgs?foo=bar` (unknown query parameter) must be ignored, not rejected — strict whitelist rejection is a common production misconfiguration that breaks clients the moment they add a new optional parameter.

### Requirement 3 — Strict DTO schema validation with named constraints

The request body for `POST /orgs` is `{ "name": string, "slug": string }`. The `name` constraint is non-negotiable:

- **Length: 1 to 100 characters.** Empty string is invalid. 101 characters is invalid. The 100-character ceiling is a database-column-width proxy: the underlying `name` column is `VARCHAR(100)`, and the application-layer validation must fail before the database returns a `value too long for type character varying(100)` error.
- **No XSS payload.** The string `<script>alert(1)</script>` as a name must be rejected. The validation is a regex denylist of `<`, `>`, `&`, and the NUL byte. This is application-layer defense-in-depth, not a substitute for output escaping on the read path — but a missing application-layer check means the XSS payload reaches the database, and a downstream system that reads from the database without escaping (an analytics dashboard, a Slack notification webhook) becomes the XSS sink.
- **No control characters.** `\n`, `\r`, `\t`, `\u0000` through `\u001F` are rejected. This is what catches the classic log-injection attack where a malicious name like `acme\n[INFO] payment succeeded` poisons downstream log parsers.

The `slug` constraint is `[a-z0-9-]{3,50}` — lowercase alphanumeric with hyphens, 3 to 50 chars. The `role` enum on the member sub-resource is exactly three values: `ADMIN`, `MEMBER`, `VIEWER`. Uppercase only — `admin` (lowercase) is invalid. The role enum is enforced at the DTO layer, the service layer, and the database CHECK constraint, in that order; the defence-in-depth exists because each layer has a different bug surface (DTO validation can be skipped by an internal service call, the database CHECK can be disabled by a migration).

### Requirement 4 — Structured error mapping with RFC 7807 ProblemDetail

Every error response is an `application/problem+json` body per RFC 7807. The body shape is fixed:

```json
{
  "type": "https://errors.example.com/organization-not-found",
  "title": "Organization not found",
  "status": 404,
  "detail": "Organization with id 42 does not exist or was deleted",
  "instance": "/orgs/42",
  "trace_id": "a1b2c3d4e5f6"
}
```

The `type` field is a stable URI that the client can look up in documentation. The `title` is a short human-readable summary that is the same for every instance of this error class. The `detail` is the instance-specific message. The `instance` is the request path. The `trace_id` is the correlation ID propagated through the middleware chain (it becomes load-bearing in Milestone 2 and Milestone 5).

This is non-negotiable because client SDKs are written against this shape. A Spring Boot default error body looks like `{"timestamp": "...", "status": 404, "error": "Not Found", "path": "/orgs/42"}` — usable, but not RFC 7807. A Django default looks like `{"detail": "Not found."}` — also usable, but missing the `type` and `trace_id` fields. The four implementations must produce the same ProblemDetail body for the same logical error, or the post-mortem comparison is invalid.

### Requirement 5 — Status-code matrix

The 10 status codes used by this API are 200, 201, 204, 400, 401, 403, 404, 409, 422, 500. Each has a precise meaning in this API:

- **200 OK** — successful GET, PATCH, or list response. Body is the resource representation.
- **201 Created** — successful POST to `/orgs` or `/orgs/{id}/members`. Body is the created resource. `Location` header is set to the canonical URL of the new resource.
- **204 No Content** — successful DELETE. Empty body.
- **400 Bad Request** — malformed JSON, non-numeric path parameter, missing required field in body.
- **401 Unauthorized** — missing or invalid auth token. (Auth is stubbed in Milestone 1 with a fixed dev token; real JWT arrives in Milestone 2.)
- **403 Forbidden** — authenticated but lacking the role for this operation. Example: a `VIEWER` trying to delete a member.
- **404 Not Found** — the path parameter references an org or user that does not exist or was soft-deleted.
- **409 Conflict** — uniqueness violation. The slug is unique; creating two orgs with the same slug returns 409.
- **422 Unprocessable Entity** — JSON is well-formed and types are correct, but a business rule fails. Example: trying to add a member to a soft-deleted org.
- **500 Internal Server Error** — unhandled exception. The ProblemDetail body's `detail` field must **not** leak the stack trace to the client (it must be logged server-side with the `trace_id`).

The 422 vs 400 distinction matters: 400 means "I cannot parse this request", 422 means "I parsed it fine but the business rule rejects it". Many APIs collapse both into 400 — that is a mistake because clients cannot then distinguish "fix your JSON" from "fix your business logic".

### Requirement 6 — Soft-delete semantics on the organization resource

`DELETE /orgs/{id}` does not row-delete. It sets `deleted_at = NOW()` (a nullable timestamp). All subsequent reads of `/orgs/{id}` return 404. All subsequent reads of `GET /orgs` exclude the soft-deleted row. All subsequent `POST /orgs/{id}/members` return 422 with a ProblemDetail `type` of `https://errors.example.com/organization-deleted`.

This is non-negotiable because row-delete breaks referential integrity: an invoice row that references the deleted org becomes an orphan, and an analytics job that joins on `org_id` returns null. Soft-delete preserves the foreign key at the cost of every query needing a `WHERE deleted_at IS NULL` filter. Every ecosystem implements this filter at the repository/query layer — it must not leak into the controller layer.

The slug of a soft-deleted org **can** be reused. The uniqueness constraint on `slug` is partial: `UNIQUE (slug) WHERE deleted_at IS NULL`. This is a Postgres partial index; the spec mandates Postgres as the database so the partial-index syntax is the same across all four implementations.

The four implementations are structurally identical: router → validation → controller → service → repository → pool → Postgres. The differences are in how each ecosystem names those layers (Spring `@RestController` vs Express `app.get` vs DRF `ViewSet` vs Laravel `Route::get`), how validation is declared (`@Valid` + Bean Validation annotations vs Zod schemas vs DRF serializers vs Form Requests), and how the connection pool is configured (HikariCP bean vs `pg` Pool vs Django's `CONN_MAX_AGE` vs Laravel's `database.php` pool). The architecture sketch is the contract that those names hide.

## API Contract

### `GET /orgs` — list organizations

- **Query parameters:** `page` (int, default 1), `size` (int 1-100, default 20).
- **Response 200:**
```json
{
  "data": [
    { "id": 1, "name": "Acme", "slug": "acme", "deleted_at": null }
  ],
  "page": 1,
  "size": 20,
  "total": 1
}
```
- **Errors:** 400 (invalid `page` or `size`).

### `POST /orgs` — create organization

- **Request body:**
```json
{ "name": "Acme Corp", "slug": "acme-corp" }
```
- **Response 201:**
```json
{ "id": 1, "name": "Acme Corp", "slug": "acme-corp", "deleted_at": null }
```
- **Headers:** `Location: /orgs/1`.
- **Errors:** 400 (malformed JSON), 409 (slug already exists), 422 (name or slug validation failed).

### `GET /orgs/{id}` — retrieve organization

- **Path parameter:** `id` (int64).
- **Response 200:**
```json
{ "id": 1, "name": "Acme Corp", "slug": "acme-corp", "deleted_at": null }
```
- **Errors:** 400 (non-numeric `id`), 404 (not found or soft-deleted).

### `PATCH /orgs/{id}` — partially update organization

- **Path parameter:** `id` (int64).
- **Request body:** any subset of `{ "name": string, "slug": string }`.
- **Response 200:** the full updated resource.
- **Errors:** 400 (malformed JSON), 404 (not found), 409 (slug collision), 422 (validation failed).
- **PATCH semantics:** only the supplied fields are written. A `null` value for a field is treated as "do not change", not "clear the field". (This is the merge-patch semantics from RFC 7396, restricted to the two mutable fields.)

### `DELETE /orgs/{id}` — soft-delete organization

- **Path parameter:** `id` (int64).
- **Response 204:** empty body.
- **Errors:** 404 (not found or already deleted).
- **Side effects:** sets `deleted_at = NOW()`. All members of this org remain in the database but are unreachable through the API.

### `GET /orgs/{id}/members` — list members

- **Path parameter:** `id` (int64).
- **Response 200:**
```json
{
  "data": [
    { "user_id": 1, "role": "ADMIN" },
    { "user_id": 2, "role": "MEMBER" }
  ]
}
```
- **Errors:** 400 (non-numeric `id`), 404 (org not found).

### `POST /orgs/{id}/members` — add member

- **Path parameter:** `id` (int64).
- **Request body:**
```json
{ "user_id": 3, "role": "MEMBER" }
```
- **Response 201:**
```json
{ "user_id": 3, "role": "MEMBER" }
```
- **Headers:** `Location: /orgs/1/members/3`.
- **Errors:** 400 (malformed JSON), 404 (org not found), 409 (user already a member), 422 (role not in enum, org is soft-deleted).

### `DELETE /orgs/{id}/members/{userId}` — remove member

- **Path parameters:** `id` (int64), `userId` (int64).
- **Response 204:** empty body.
- **Errors:** 404 (org or membership not found).
- **Side effects:** row-deletes the membership row. The org itself is not affected. Removing the last `ADMIN` is allowed at this layer (the spec does not mandate "must have at least one admin" — that is a Milestone 2 RBAC concern).

## Acceptance Criteria

1. All four target ecosystems implement the same contract — verified by running the same `curl` test script against each and getting byte-identical JSON response bodies (modulo the `trace_id` field, which is per-request).
2. All four pass the same automated test suite — the suite is a Postman collection with 32 cases (4 cases per endpoint × 8 endpoints) covering the happy path plus one error case per endpoint.
3. At least one ecosystem is load-tested to failure with `wrk` — the failure graph is captured and the fix is documented. The Spring Boot anchor in [[13.01.02. Anchor Implementation Spring Boot]] is the default load-test target; the `wrk -t8 -c200 -d30s http://localhost:8080/orgs` command is the standard.
4. The post-mortem note ([[13.01.06. Architectural Comparison and Post-Mortem]]) is filled in with concrete observations — a metric table comparing the four implementations on p50/p95/p99 latency, requests-per-second at saturation, cold-start time, lines of code, and the specific failure mode each hit first under load.

## Deliverables

- Source code for each ecosystem in a separate subfolder: `anchor-spring-boot/`, `delta-express/`, `delta-django/`, `delta-laravel/`.
- A `docker-compose.yml` at the project root that brings up Postgres and the four application services on ports 8081-8084.
- A `README.md` with run instructions and a load-test screenshot (a `wrk` TTY capture is acceptable; a Grafana panel exported as PNG is better).
- A post-mortem note in this folder ([[13.01.06. Architectural Comparison and Post-Mortem]]) with the metric tables and failure-mode observations.
