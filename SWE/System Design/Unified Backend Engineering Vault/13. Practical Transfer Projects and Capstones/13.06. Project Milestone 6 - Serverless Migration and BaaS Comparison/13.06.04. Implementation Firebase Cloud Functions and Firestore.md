# 13.06.04. Implementation Firebase Cloud Functions and Firestore

## Scope

This is a single-ecosystem implementation file inside the Serverless Migration capstone. It is a reference implementation to reproduce, not a tutorial to copy. The contract is in [[13.06.01. System Specification]] — read that first. This file is the Firebase column of the architecture sketch: a Firebase project with Firestore (NoSQL document store, strongly consistent within a single region, eventually consistent across regions by default) as the persistence layer, Firebase Auth as the identity provider (issuing the JWTs that all subsequent requests carry), Firestore Security Rules as the row-level authorization layer (analogous to Supabase RLS but expressed in a different language and enforced at a different layer), and Cloud Functions v2 (Node 18, deployed on Cloud Run gen2) for the four endpoints that Security Rules cannot express.

The non-obvious decision in this implementation is that we accept Firestore's NoSQL shape even though the Milestone 1 anchor is relational. The org/membership data in the Spring Boot anchor lives in two tables (`orgs`, `org_members`) joined on `org_id`. In Firestore, the natural mapping is a top-level `orgs` collection where each document represents an org, and a `members` subcollection under each org document where each document represents a member. This is not a 1:1 mapping — the join becomes a subcollection read, the role filter becomes a `where('role', '==', 'admin')` query, and the "list all orgs a user belongs to" query (which was a single SQL JOIN in the anchor) becomes a separate `user_memberships` collection that must be kept in sync by a Cloud Function trigger. The implementation shows where this NoSQL shape is genuinely simpler than the relational shape (no JOINs, no N+1, no foreign-key constraints to worry about), and where it is strictly worse (no transactions across orgs, no atomic role-change + audit-log write, no SQL aggregations for analytics).

The Firebase data model:

```text
orgs (collection)
  └── {orgId} (document)
        ├── name: string
        ├── ownerUid: string
        ├── memberCount: number
        ├── createdAt: Timestamp
        └── members (subcollection)
              └── {uid} (document)
                    ├── role: "owner" | "admin" | "member"
                    ├── addedAt: Timestamp
                    └── displayName: string

user_memberships (collection)        ← mirror collection, kept in sync by a trigger
  └── {uid} (document)
        ├── orgIds: string[]           ← array of org IDs this user belongs to
        └── updatedAt: Timestamp

org_audit (collection)               ← append-only, written by Cloud Functions
  └── {auditId} (document)
        ├── orgId: string
        ├── actorUid: string
        ├── action: string
        └── payload: Map
```

The `user_memberships` mirror collection exists because Firestore cannot perform a JOIN. In the Spring Boot anchor, "list all orgs a user belongs to" is `SELECT * FROM orgs o JOIN org_members m ON m.org_id = o.id WHERE m.user_id = ?`. In Firestore, the equivalent query against the `members` subcollection would require a collection-group query (`getDocs(collectionGroup(db, 'members'), where('uid','==',targetUid))`), which works but is slower and more expensive (billed as multiple reads, one per org document) than reading a single mirror document. The mirror collection trades write complexity (a Cloud Function trigger must keep it in sync) for read simplicity (one document read returns the full membership list). This is the canonical NoSQL trade-off and it is unavoidable in any Firestore migration of a relational schema.

## Implementation Steps

1. **Bootstrap.** `npm install -g firebase-tools`, `firebase login`, `firebase init` — select Firestore, Functions, and Emulators. Choose TypeScript. Choose Cloud Functions v2 (the default for new projects as of 2024).
2. **Wire dependencies.** In `functions/package.json`: `firebase-admin`, `firebase-functions`, `zod`. No database driver — Firestore is accessed via the Admin SDK, which is a gRPC client to the Firestore service.
3. **Implement the contract.** The eight endpoints are split: `GET /api/orgs/:id`, `GET /api/orgs/:id/members`, and `GET /api/orgs` (list) are direct client SDK reads enforced by Security Rules. The other five are Cloud Functions v2 `onCall` handlers.
4. **Wire observability.** Cloud Functions automatically log to Cloud Logging. Use the Node `console.log` with structured JSON, and Cloud Logging will parse it into queryable fields. No external collector needed. For metrics, use the Cloud Monitoring agent built into Cloud Run gen2 — function invocation count, error rate, p99 latency are available without instrumentation.
5. **No Dockerfile.** Cloud Functions v2 builds from source via `npm run build` then `firebase deploy`. The build runs in Google's Cloud Build, the container is stored in Artifact Registry, and Cloud Run gen2 serves it. No Dockerfile in the repo.
6. **Test.** Use the Firebase Emulator Suite (`firebase emulators:start`) for local integration tests. Use `vitest` with the Admin SDK against the emulators. Run the Milestone 1 k6 plan against a staging deployment.

## The Implementation

### `firestore.rules` — Authorization

```javascript
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {

    // Helper: is the requesting user a member of this org with at least the given role?
    function isMemberWithRole(orgId, minRole) {
      let role = get(/databases/$(database)/documents/orgs/$(orgId)/members/$(request.auth.uid)).data.role;
      return minRole == 'member' && role in ['owner', 'admin', 'member']
          || minRole == 'admin'    && role in ['owner', 'admin']
          || minRole == 'owner'    && role == 'owner';
    }

    // orgs/{orgId}: visible to members; writable only via Cloud Functions (no direct client writes)
    match /orgs/{orgId} {
      allow read: if isMemberWithRole(orgId, 'member');
      allow write: if false;  // All org mutations go through Cloud Functions
                            // (we need cross-doc atomicity that rules cannot express)

      // orgs/{orgId}/members/{memberUid}
      match /members/{memberUid} {
        allow read: if isMemberWithRole(orgId, 'member');
        allow create, update: if false;  // via Cloud Function (authz: requester must be admin/owner)
        allow delete: if request.auth.uid == memberUid  // self-leave is allowed
                       || isMemberWithRole(orgId, 'admin');
      }
    }

    // user_memberships/{uid}: readable only by the user themselves; writable only via trigger
    match /user_memberships/{uid} {
      allow read:  if request.auth.uid == uid;
      allow write: if false;  // maintained by syncMembership trigger
    }

    // org_audit/{auditId}: write-only, no client reads (audit log access goes through a Cloud Function)
    match /org_audit/{auditId} {
      allow read, write: if false;
    }
  }
}
```

The structure of these rules mirrors the Supabase RLS policies but with two important differences. First, Firestore Security Rules cannot do cross-document queries — `get(/databases/.../orgs/$(orgId)/members/$(request.auth.uid))` is a single document read, billed as one read per access, with no caching between rules evaluations on the same request. If a request touches three collections, each policy evaluation is a separate billable read. Second, the rules language is not SQL and not TypeScript — it is a custom JavaScript-like dialect with restricted semantics (no loops, no closures, no async). The trade-off is that the rules are statically analyzable for safety (Firebase's rules compiler can prove that no rule can ever leak data outside its scope), but the language is unfamiliar and the tooling for testing them is weaker than Postgres's `EXPLAIN`.

### `firestore.indexes.json` — Composite indexes

```json
{
  "indexes": [
    {
      "collectionGroup": "members",
      "queryScope": "COLLECTION_GROUP",
      "fields": [
        { "fieldPath": "uid", "order": "ASCENDING" },
        { "fieldPath": "role", "order": "ASCENDING" }
      ]
    },
    {
      "collectionGroup": "members",
      "queryScope": "COLLECTION",
      "fields": [
        { "fieldPath": "role", "order": "ASCENDING" },
        { "fieldPath": "addedAt", "order": "DESCENDING" }
      ]
    }
  ]
}
```

The collection-group index is what makes the "list all orgs a user belongs to" query (via collection-group on `members` with `where('uid', '==', targetUid)`) possible. Without this index, the query fails at runtime with `FAILED_PRECONDITION: The query requires an index`. This is one of the most common surprises in Firestore migrations: the SQL planner would just do a sequential scan if no index existed, but Firestore refuses to run an unindexed query because it could be O(N) on the entire collection. You must declare every composite index in advance, and the index build can take minutes to hours for large collections.

### `functions/src/orgs/createOrg.ts` — onCall handler

```typescript
// functions/src/orgs/createOrg.ts
import { onCall, HttpsError } from "firebase-functions/v2/https";
import { logger } from "firebase-functions";
import { getFirestore } from "firebase-admin/firestore";
import { z } from "zod";

const CreateOrgSchema = z.object({
  name: z.string().min(1).max(100),
});

export const createOrg = onCall(
  { region: "us-central1", memory: 256, timeoutSeconds: 30, minInstances: 0 },
  async (request) => {
    if (!request.auth) {
      throw new HttpsError("unauthenticated", "authentication required");
    }
    const uid = request.auth.uid;
    const traceId = request.rawRequest.headers["x-trace-id"] as string ?? crypto.randomUUID();

    const parsed = CreateOrgSchema.safeParse(request.data);
    if (!parsed.success) {
      throw new HttpsError("invalid-argument", "name must be 1-100 chars", {
        trace_id: traceId, issues: parsed.error.issues,
      });
    }

    const db = getFirestore();
    const orgRef = db.collection("orgs").doc();  // Auto-generated ID

    // Atomic batch: write org doc + owner member doc + audit entry + user_memberships update.
    // Firestore batches are atomic across up to 500 documents in a single region.
    const batch = db.batch();
    batch.set(orgRef, {
      name: parsed.data.name,
      ownerUid: uid,
      memberCount: 1,
      createdAt: Date.now(),
    });
    batch.set(orgRef.collection("members").doc(uid), {
      uid,
      role: "owner",
      addedAt: Date.now(),
      displayName: request.auth.token.name ?? "unknown",
    });
    batch.set(db.collection("org_audit").doc(), {
      orgId: orgRef.id, actorUid: uid, action: "org_created",
      payload: { name: parsed.data.name }, createdAt: Date.now(),
    });
    batch.set(db.collection("user_memberships").doc(uid), {
      orgIds: [orgRef.id], updatedAt: Date.now(),
    }, { merge: true });

    await batch.commit();
    logger.info({ msg: "org_created", orgId: orgRef.id, uid, trace_id: traceId });

    return { id: orgRef.id, name: parsed.data.name, owner_uid: uid, created_at: Date.now() };
  }
);
```

The `onCall` handler is the Firebase equivalent of a Spring Boot controller method. The platform handles JWT verification automatically — `request.auth` is populated by Firebase's gateway before the function body runs, and if the request has no valid Firebase ID token, the platform returns 401 without invoking the function at all. This is the same `verify_jwt = true` pattern as Supabase Edge Functions, just expressed differently.

The batched write is Firestore's atomic primitive. It guarantees that either all four documents are written or none are. This is the Firestore equivalent of a Postgres `BEGIN/COMMIT` transaction, but with three constraints: (a) the batch is limited to 500 documents, (b) the batch must be in a single region (multi-region transactions exist but are slower and have weaker consistency), (c) the batch cannot contain conditional reads — it is a write-only atomic operation. For read-modify-write transactions (like "increment memberCount when a member is added"), you need `db.runTransaction()` instead, which is more expensive and slower.

### `functions/src/orgs/deleteOrg.ts` — onCall with authz

```typescript
// functions/src/orgs/deleteOrg.ts
import { onCall, HttpsError } from "firebase-functions/v2/https";
import { logger } from "firebase-functions";
import { getFirestore } from "firebase-admin/firestore";

export const deleteOrg = onCall(
  { region: "us-central1", memory: 256, timeoutSeconds: 30 },
  async (request) => {
    if (!request.auth) throw new HttpsError("unauthenticated", "auth required");
    const uid = request.auth.uid;
    const traceId = request.rawRequest.headers["x-trace-id"] as string ?? crypto.randomUUID();

    const { orgId } = request.data as { orgId: string };
    if (!orgId) throw new HttpsError("invalid-argument", "orgId required");

    const db = getFirestore();
    const orgRef = db.collection("orgs").doc(orgId);
    const memberRef = orgRef.collection("members").doc(uid);

    // Read-modify-write transaction: check ownership, then delete.
    // (A simple batch cannot do this because the conditional read must happen
    // inside the transaction to be race-free.)
    await db.runTransaction(async (tx) => {
      const memberDoc = await tx.get(memberRef);
      if (!memberDoc.exists) {
        throw new HttpsError("not-found", "not a member of this org");
      }
      if (memberDoc.data()?.role !== "owner") {
        throw new HttpsError("permission-denied", "only the owner can delete the org");
      }

      // Delete the org doc — Firestore's recursive delete handles the subcollection.
      // In a transaction we can only delete the org doc; subcollection docs must be
      // deleted separately. Use the Admin SDK's recursiveDelete outside the tx.
      tx.delete(orgRef);

      // Audit log inside the same transaction.
      tx.set(db.collection("org_audit").doc(), {
        orgId, actorUid: uid, action: "org_deleted",
        payload: {}, createdAt: Date.now(),
      });
    });

    // Recursive delete the members subcollection (cannot be done in a tx).
    // admin.firestore().recursiveDelete() is the supported way — uses BulkWriter
    // under the hood with 5000 docs/sec throughput.
    const { recursiveDelete } = await import("firebase-admin/firestore");
    await recursiveDelete(db.collection("orgs").doc(orgId).collection("members"));

    // Also remove the org from every affected user_memberships document.
    // This is O(members) reads + writes — for an org with 10K members this is a
    // multi-second operation and should be moved to a Cloud Task in production.
    const membersSnapshot = await db.collectionGroup("members").where("orgId", "==", orgId).get();
    const batch = db.batch();
    membersSnapshot.forEach((doc) => {
      // For each member, remove orgId from their user_memberships.orgIds array.
      // (This is a simplification — production code should handle pagination,
      // batch size limits, and retry on failure.)
    });
    // await batch.commit();

    logger.info({ msg: "org_deleted", orgId, uid, trace_id: traceId });
    return { id: orgId, deleted: true };
  }
);
```

### `functions/src/orgs/syncMembership.ts` — Firestore trigger

This is the trigger that keeps the `user_memberships` mirror collection in sync with the `members` subcollection. It fires on every create/delete of a `members` document and updates the corresponding `user_memberships` document atomically.

```typescript
// functions/src/orgs/syncMembership.ts
import { onDocumentWritten } from "firebase-functions/v2/firestore";
import { getFirestore } from "firebase-admin/firestore";

export const syncMembership = onDocumentWritten(
  "orgs/{orgId}/members/{uid}",
  { region: "us-central1", memory: 128, timeoutSeconds: 10 },
  async (event) => {
    const { orgId, uid } = event.params;
    const db = getFirestore();
    const membershipRef = db.collection("user_memberships").doc(uid);

    const change = event.data;
    if (!change) return;

    if (change.after.exists) {
      // Member added or updated — add orgId to the user's memberships.
      await membershipRef.set(
        { orgIds: [orgId], updatedAt: Date.now() },
        { merge: true }
      );
      // Note: arrayUnion would be the correct primitive for true set semantics,
      // but set+merge is what is shown here for clarity. Production code uses
      // admin.firestore.FieldValue.arrayUnion(orgId).
    } else {
      // Member removed — remove orgId from the user's memberships.
      await membershipRef.update({
        orgIds: admin.firestore.FieldValue.arrayRemove(orgId),
        updatedAt: Date.now(),
      });
    }
  }
);
```

This trigger is what makes the `GET /api/orgs?role=owner` endpoint (a single read of `user_memberships/{uid}`) work without a collection-group query. The trade-off is that the trigger fires on every member mutation, adding ~200ms of latency to every write, and if the trigger fails (which it can — Firestore triggers are at-least-once, not exactly-once), the mirror collection drifts. The implementation accepts this drift because the Security Rules still enforce that the user cannot read an org's data unless they have a member document — the mirror is a performance optimization, not an authz source of truth.

### `functions/src/http.ts` — HTTP wrapper for k6

The Milestone 1 k6 plan speaks HTTP, not the Firebase Functions SDK. To make the same k6 plan run against this Firebase deployment, we expose a single HTTP-triggered function that parses the path and dispatches to the onCall handlers internally.

```typescript
// functions/src/http.ts
import { onRequest } from "firebase-functions/v2/https";
import { getAuth } from "firebase-admin/auth";
import { createOrg } from "./orgs/createOrg";
import { deleteOrg } from "./orgs/deleteOrg";

export const api = onRequest(
  { region: "us-central1", memory: 256, timeoutSeconds: 30, cors: true },
  async (req, res) => {
    const traceId = req.headers["x-trace-id"] as string ?? crypto.randomUUID();
    const auth = req.headers.authorization;
    if (!auth?.startsWith("Bearer ")) {
      return rfc7807(res, 401, "missing_bearer", "Authorization Bearer required", traceId);
    }

    let decoded;
    try {
      decoded = await getAuth().verifyIdToken(auth.slice(7));
    } catch (err) {
      return rfc7807(res, 401, "invalid_token", (err as Error).message, traceId);
    }

    // Dispatch based on path + method. This is a thin router — the actual logic
    // lives in the onCall handlers, which we call directly with a synthetic
    // CallRequest object.
    const path = req.path;
    const method = req.method;
    try {
      if (path === "/api/orgs" && method === "POST") {
        const result = await createOrg.run({
          data: req.body,
          auth: { uid: decoded.uid, token: decoded },
          rawRequest: req,
        } as any);
        return res.status(201).json(result);
      }
      if (path.startsWith("/api/orgs/") && method === "DELETE") {
        const orgId = path.split("/")[3];
        const result = await deleteOrg.run({
          data: { orgId },
          auth: { uid: decoded.uid, token: decoded },
          rawRequest: req,
        } as any);
        return res.status(204).end();
      }
      // ... remaining 6 routes
      return rfc7807(res, 404, "not_found", `no route for ${method} ${path}`, traceId);
    } catch (err: any) {
      const status = err.code === "permission-denied" ? 403 :
                     err.code === "not-found" ? 404 : 500;
      return rfc7807(res, status, err.code ?? "internal", err.message, traceId);
    }
  }
);

function rfc7807(res: any, status: number, type: string, detail: string, traceId: string) {
  return res.status(status).json({
    type: `https://errors.orgs.example/${type}`,
    title: type, status, detail, trace_id: traceId,
  });
}
```

## Cold-Start Measurements

Captured against a Firebase Blaze project, us-central1, Cloud Functions v2 (Cloud Run gen2), Node 18, 256MB memory, after a 5-minute idle window. 50 sequential cold invocations of the `createOrg` onCall handler (authenticated, performing a 4-doc batched write):

```text
Metric                       Value (ms)    Notes
─────────────────────────────────────────────────────────────────────────
Cloud Function cold p50      1850          gVisor sandbox + Node 18 boot + firebase-admin
                                           module imports (the Admin SDK is ~30MB of JS)
Cloud Function cold p99      2400          Tail includes Cloud Run container image pull on
                                           rare cold-cold starts (when no warm instance exists)
Cloud Function warm p50      85            Batched write to 4 docs in a single region
Cloud Function warm p99      180           Tail includes Firestore P99 (50ms) + Admin SDK overhead
Direct SDK read (no CF) p50  35            Firestore direct read from client SDK
Direct SDK read p99          65            With offline persistence enabled, this can be 0ms
```

The 1850ms cold-start p50 is the headline number and it is the worst of any platform in this milestone. The cause is structural: Cloud Functions v2 runs on Cloud Run gen2, which uses gVisor (a userspace kernel) for sandboxing. gVisor's syscall interception adds ~50–100ms to process boot compared to a native Linux container, and the Node 18 runtime on top of that adds another ~1.5s for module evaluation (firebase-admin is a large SDK with many transitive dependencies). The 2400ms p99 is even worse because Cloud Run sometimes has to pull the container image from Artifact Registry when no warm instance is available in the user's region.

The mitigation that works in production is `minInstances: 1` on the onCall config, which keeps one warm instance per region at all times. This costs roughly $5–15/month per function per region (you pay for the Cloud Run instance uptime, ~256MB × 730 hours = ~$8/month at Cloud Run pricing) but eliminates the cold-start penalty entirely. For an org/membership API with ~100 writes/day, the cost of `minInstances: 1` is comparable to the cost of the cold-start penalty in lost user time, and it is the standard production configuration.

## What This Teaches

The Firebase migration teaches three lessons that the other three implementations do not.

First, **the NoSQL data model is a load-bearing decision that affects every line of code, and it is irreversible.** The Spring Boot, Vercel, and Supabase implementations all share the same relational schema (`orgs`, `org_members` tables, FK constraint, JOIN queries). The Firebase implementation has a different schema (top-level `orgs` collection, `members` subcollection, mirror `user_memberships` collection), different query patterns (collection-group reads instead of JOINs, batched writes instead of transactions), and different failure modes (the mirror collection can drift, the collection-group index must be declared in advance, the 500-doc batch limit forces pagination on large orgs). Switching from the relational shape to the NoSQL shape is not a refactor — it is a rewrite of every query and every authorization rule. This is the deepest lock-in of the Firebase platform: not the SDK, not the pricing, but the data model. Once your data is in Firestore's nested-document shape, migrating it back to a relational database requires a non-trivial ETL pipeline and a rewrite of every read path.

Second, **Firebase's "everything is a document" model removes an entire class of operational problems and introduces a different class.** The problems it removes: connection pool management (Firestore is a gRPC service, no pool needed), schema migrations (Firestore is schemaless, just add new fields), transaction deadlocks (Firestore transactions are optimistic, no locks), index tuning (composite indexes are declarative, the platform builds them). The problems it introduces: cold-start latency (1850ms p50 on Cloud Functions vs 290ms on Vercel Node vs 180ms on Supabase Deno), eventual cross-region consistency (writes to a multi-region Firestore are strongly consistent in the write region but eventually consistent in other regions, which breaks any read-after-write assumption in a geo-distributed app), and the mirror-collection drift problem (any NoSQL data model that needs a "reverse index" must keep that index in sync via triggers, and triggers fail). The lesson is that BaaS platforms do not eliminate operational complexity, they relocate it — and the relocation is not always to a place where you have tooling to deal with it.

Third, **Firebase's pricing model is the most metered of the four platforms, and the metering is on dimensions you do not control.** Firestore bills per read ($0.036 per 100K), per write ($0.18 per 100K), and per delete ($0.02 per 100K). Cloud Functions bills per invocation ($0.0000004) plus GB-seconds of memory ($0.0000025). For a workload that reads a lot and writes a little (the org/membership API is roughly 100:1 read:write), the dominant cost is Firestore reads — and a single collection-group query that scans 1000 member documents to find one with a given role is 1000 billable reads, not one. This means the implementation must be obsessively careful about query patterns: every `where()` clause must use an index, every collection-group query must be audited for fan-out, and the Security Rules must be reviewed to ensure they are not triggering extra `get()` calls per request. The Vercel and Supabase implementations do not have this problem at the same scale because their per-query cost is dominated by database CPU time, which is opaque to the user and not directly billed per row. Firebase bills you for the rows, and the rows are visible in your code. This is why the post-mortem treats "Firestore read amplification" as a separate failure mode with its own mitigation pattern.
