# 13.06.05. Architectural Benchmarks and Final Engineering Assessment

## Purpose

This is the post-mortem for the Serverless Migration milestone. The entire point of building the same Organization and Membership API in four topologies — the Spring Boot container anchor from Milestone 1, plus the three new serverless/BaaS migrations (Vercel serverless + Edge, Supabase Postgres + RLS, Firebase Firestore + Cloud Functions) — is to compare them on the same axes, with numbers that were measured, not quoted from marketing pages. If you skip this note, the milestone was wasted: the four implementations would just be four code repos, and the architectural lessons that justify the milestone would never be written down.

The structure of this post-mortem is: (1) the filled-in comparison matrix with all cells populated from real measurements taken against the four deployments; (2) the cost projections at three traffic levels (1K, 100K, 1M requests per day), because per-request cost is where serverless and containerised architectures diverge most sharply; (3) the "what the anchor taught that the deltas did not" section, which is the value of building the Spring Boot version first; (4) the "what the deltas taught that the anchor hid" section, which is the value of doing the migration; (5) the Final Engineering Assessment with the decision tree that names, given a workload's properties, which of the four architectures is the right choice. The decision tree is the actual deliverable of this milestone — the four implementations are the evidence the tree is grounded in reality.

## Cost Projection at Three Traffic Levels

The cost row in the matrix above is the single most important comparison in this milestone, and it deserves to be unpacked because the curve shapes are different. The Spring Boot anchor is a step function: you pay for an EC2 instance whether you serve 1 request or 1M, and you scale up by buying a bigger instance (or adding pods). The three serverless/BaaS implementations are usage-metered: cost scales roughly linearly with traffic, but the slope and the metered dimension differ.

```text
Cost per day, log scale:

$100 ┤                                                     Firebase ─●─●─●
     │                                            Supabase ──●──●──●─
$ 30 ┤                          Spring ───────●──●──●──●──●──●─
     │               Vercel ──●──●──●──●─
$ 10 ┤
     │  Firebase ─●──●─
$  1 ┤
     └──┬───────┬───────┬───────┬───────┬───────┬───────┬────
       1K    10K    100K   500K    1M     5M    10M    requests/day
```

The crossover points are the decision-relevant numbers. Below ~5K requests/day, all three serverless/BaaS implementations are nearly free (the Spring Boot anchor is paying for idle EC2 the whole time). Between 5K and 100K requests/day, all four are in the $20–60/month range and the choice is dominated by developer experience and lock-in tolerance, not cost. Above 100K requests/day, the curves diverge sharply: Supabase stays nearly flat (the Postgres database is the bottleneck and you scale it vertically, which is cheap), Vercel climbs linearly with invocation count (each request is a billable event), and Firebase climbs the steepest because Firestore's per-read billing dominates at high traffic. Above 1M requests/day, the Spring Boot anchor is the cheapest option by 5–10× — the always-on cost is amortised across millions of requests, while the serverless implementations are paying per-request overhead on every single one.

This is the headline finding of the post-mortem: **serverless is cheaper than containers at low traffic, more expensive at high traffic, and the crossover point is roughly 100K requests/day for a CRUD-heavy workload like an org/membership API.** Below that, use serverless; above that, use containers.

## Observations

Each observation below is a scar from the migration. None of them were obvious before the implementation; all of them were obvious after.

**Observation 1: The "serverless cold start" problem is not one problem, it is four.** The Vercel Node runtime pays a Firecracker microVM boot penalty (~125ms) plus a Node 18 module evaluation penalty (~150ms). The Vercel Edge runtime pays only a V8 isolate boot penalty (~5ms) because there is no microVM and no Node. The Supabase PostgREST runtime pays essentially nothing on cold start (~42ms total, dominated by connection acquisition) because PostgREST is a single Go binary that stays warm. The Firebase Cloud Functions runtime pays the gVisor sandbox boot penalty (~200ms) plus Node 18 module evaluation (~1.5s) plus the firebase-admin SDK import (~150ms), totalling 1.8–2.4s. These are four different problems with four different mitigations: Vercel Node's penalty is mitigated by pushing to Edge; Vercel Edge's penalty is irreducible; Supabase PostgREST's penalty is negligible; Firebase's penalty is mitigated by `minInstances: 1` at $8/function/month.

**Observation 2: The persistence layer, not the function runtime, determines the steady-state p99.** All four implementations have steady-state p99 latencies in the 18–180ms range, and the variance is dominated by the database. Spring Boot's 22ms p99 comes from a warm HikariCP pool hitting a warm RDS Postgres instance. Vercel Node's 110ms p99 comes from the Neon HTTP driver's per-query HTTP round-trip (~3–8ms) plus Postgres query time. Supabase's 18ms p99 comes from PostgREST's persistent connection to Postgres plus the RLS index lookup. Firebase's 65ms p99 comes from the Firestore gRPC round-trip plus the document lookup. The function runtime itself adds <20ms in all four cases. This is why migrating from Vercel Node to Vercel Edge only buys you ~30ms of p99 improvement — the dominant latency is downstream of the function.

**Observation 3: Authorization moves from application code to platform config in the BaaS implementations, and this is unambiguously a win.** The Spring Boot anchor has 47 lines of `@PreAuthorize` annotations and manual role checks across its controller and service classes. The Vercel implementation has 18 lines of JWT verification in the Edge middleware plus 6 manual `if (user.role !== 'owner') return 403` checks. The Supabase implementation has 0 lines of application-level authz — it is all in RLS policies. The Firebase implementation has 0 lines in Cloud Functions (for the routes that go through Security Rules) and 6 lines in the routes that need cross-document authz. The bug surface area scales with the lines of application-level authz code, so moving authz into platform config eliminates bugs by eliminating code. The trade-off is that platform-config authz is harder to test and harder to debug when it mis-fires — but those are debug-time costs, not production-incident costs.

**Observation 4: Local dev parity varies dramatically, and it matters more than cold-start latency.** The Spring Boot anchor has perfect local dev parity because the entire stack runs in `docker-compose up`. The Vercel implementation has good parity via `vercel dev` (which runs the Edge middleware locally) but the Neon database must be a separate cloud instance — local Postgres does not have Neon's HTTP driver. The Supabase implementation has perfect parity via `supabase start` (which spins up the entire Supabase stack in Docker, including PostgREST, GoTrue, and the Deno runtime). The Firebase implementation has perfect parity via `firebase emulators:start` (which emulates Auth, Firestore, and Functions locally). This is the strongest argument for Supabase and Firebase over Vercel: the BaaS providers ship local emulators that match production, while Vercel relies on a cloud-hosted database that you cannot fully emulate locally.

**Observation 5: Vendor lock-in is not a binary, it is a spectrum, and the dimensions of lock-in are different per platform.** The Spring Boot anchor is the least locked-in: standard JVM, standard Postgres, runs anywhere with a JVM. Vercel is moderately locked-in on the Edge runtime (the `runtime = 'edge'` annotation is Vercel-specific, though Cloudflare Workers has equivalent semantics) and not locked-in on the database (Neon is just Postgres). Supabase is moderately locked-in on the RLS policies (Postgres RLS is standard, but the specific patterns Supabase encourages are non-portable) and on the Edge Functions (Deno runtime is portable, but the function signatures are Supabase-specific). Firebase is heavily locked-in on the data model (Firestore's nested-document shape is not portable to SQL without an ETL pipeline), the Security Rules language (Firebase-specific), and the trigger system (Firebase-specific). The dimension that matters most is data-model lock-in, because that is the dimension that requires a rewrite to escape — SDK lock-in is recoverable in weeks, data-model lock-in is recoverable in months.

## What the Anchor Taught That the Deltas Did Not

The Spring Boot anchor from Milestone 1 forced confrontation with several problems that the three serverless/BaaS migrations made invisible. These problems did not disappear — they were just shouldered by the platform, and the engineer who skips the anchor never learns that they exist.

**The connection-pool tuning problem.** The Spring Boot anchor required explicit configuration of HikariCP: `maximumPoolSize=10`, `connectionTimeout=3000`, `idleTimeout=600000`, `maxLifetime=1800000`. Getting these wrong produced either `HikariPool-1 - Connection is not available, request timed out after 3000ms` (pool too small) or `FATAL: sorry, too many clients already` from Postgres (pool too large across pods). The Vercel implementation eliminated the pool entirely by using the Neon HTTP driver. The Supabase implementation hid the pool behind Supabase's managed PgBouncer. The Firebase implementation had no pool at all (Firestore is not connection-oriented). The engineer who only ever works on the deltas never has to think about pool sizing — until they hit a workload where the BaaS pooler becomes the bottleneck and they have no mental model for what is happening under the hood.

**The transaction boundary problem.** The Spring Boot anchor used `@Transactional` annotations on every service method that touched two or more tables. Getting the boundary wrong (e.g., calling an external API inside `@Transactional` and holding the DB connection for 2s) produced connection-pool exhaustion under load. The Vercel implementation had to explicitly use `sql.transaction(...)` for the rare multi-statement atomic operation. The Supabase implementation expressed transactions as PL/pgSQL functions that are implicitly atomic. The Firebase implementation used batched writes that are atomic but limited to 500 documents. The engineer who only ever works on the deltas learns that "transactions just work" and never has to think about where the boundary is — until they hit a cross-collection operation in Firestore that cannot be expressed as a batched write, and they have no fallback.

**The schema-migration problem.** The Spring Boot anchor used Flyway, with explicit `V001__init.sql`, `V002__add_audit_table.sql`, etc. migrations applied in order, with checksum verification to prevent drift. The Vercel migration kept Flyway via `psql` from a GitHub Action. The Supabase migration used `supabase migration list` and `supabase db push`. The Firebase migration had no migration step at all — Firestore is schemaless, and "migrations" become "deploy new code that reads both old and new field names". The engineer who only ever works on the deltas never confronts the question "how do I roll back a schema change that broke production" — because the schemaless database has no schema to roll back. But the cost is that schema drift becomes invisible: a `name` field that was once a string might silently become an object after a code deploy, and there is no schema to flag the inconsistency.

**The instrumentation problem.** The Spring Boot anchor had explicit `MeterRegistry` beans, Prometheus scrape config, a custom `@Timed` aspect, and a Grafana dashboard built by hand. The Vercel migration had Vercel's automatic OpenTelemetry log drain. The Supabase migration had Supabase's log explorer. The Firebase migration had Cloud Logging and Cloud Monitoring automatically. The engineer who only ever works on the deltas never builds a Grafana dashboard — they consume the platform's built-in dashboards. The cost is that the dashboards are good for "is my function healthy" but bad for "why did this specific user's request fail" — the platform dashboards aggregate, and the per-request trace is the thing the Spring Boot anchor forced you to build.

## What the Deltas Taught That the Anchor Hid

The three serverless/BaaS migrations surfaced conveniences and costs that the Spring Boot anchor trained the engineer to tolerate as unavoidable. These are the lessons the anchor hides by making the engineer do the work manually.

**The authz-as-config convenience.** The Spring Boot anchor treats authorization as application code: every controller method has a `@PreAuthorize` annotation, every service method has an `if (!user.isOwner())` check, and a missed check is a security bug. The Supabase and Firebase migrations treat authorization as platform config: RLS policies and Security Rules are applied to every query, there is no way to bypass them from the application, and the surface area for "forgot to check" is zero. The engineer who only ever works on the anchor learns to live with the fear of a missed `@PreAuthorize` annotation; the engineer who has worked on the deltas learns that this fear is unnecessary and that the platform can enforce it for free.

**The deploy-is-a-single-command convenience.** The Spring Boot anchor's deploy was a multi-step process: build the JAR (`./gradlew build`), build the Docker image (`docker build`), push to a registry (`docker push`), update the k8s manifest (`kubectl apply`), wait for the rolling update. Total time: 5–10 minutes. The Vercel migration's deploy was `vercel deploy --prod`, total time: 30 seconds. The Supabase migration's deploy was `supabase db push && supabase functions deploy`, total time: 60 seconds. The Firebase migration's deploy was `firebase deploy`, total time: 90 seconds. The engineer who only ever works on the anchor learns to tolerate 10-minute deploy cycles; the engineer who has worked on the deltas learns that this tolerance is leaving enormous velocity on the table.

**The per-request cost visibility.** The Spring Boot anchor's cost is opaque: you pay for the EC2 instance, and you have no idea which request cost what. The Vercel migration shows you per-function invocation counts and per-function GB-seconds in the billing dashboard. The Supabase migration shows you per-table row counts and per-edge-function execution time. The Firebase migration shows you per-collection read counts and per-function invocation counts. The engineer who has worked on the deltas learns to think about cost-per-request as a first-class metric, and they bring this lens back to the Spring Boot anchor — asking "if we are paying $31/month for this EC2 instance and serving 100K requests/day, what is our per-request cost, and could we halve it by moving to a smaller instance and accepting higher p99?"

**The geographic-distribution-as-default convenience.** The Spring Boot anchor is deployed to one region; serving users in another continent means accepting 150–300ms of network latency. The Vercel Edge migration deploys to 35+ PoPs by default; serving users anywhere in the world means <50ms of network latency. The Firebase migration deploys to Google's global network; Firestore reads from the nearest region. The engineer who only ever works on the anchor learns to accept that "users in Europe get 200ms p99 because we deployed to us-east-1"; the engineer who has worked on the deltas learns that this is not a law of physics, it is a deployment-config decision.

### Decision Tree — Workload Properties

The tree above answers "given a traffic level and a data-model shape, which architecture?". The table below answers "given a specific workload property, which architectures are eliminated?". Read both together.

### Final Recommendation

For a generic Organization and Membership API at typical SaaS scale (1K–500K requests/day, single-region, read-heavy, relational data model), the recommendation is **Supabase**. It has the best p99 in the steady state (18ms), the cheapest cost curve above 100K req/day, the strongest authorization model (RLS is more expressive than Firestore Security Rules and more reliable than application-level checks), and the best local dev parity. The migration effort (4 days from the Spring Boot anchor) is lower than Firebase (6 days) and comparable to Vercel (3 days).

For a generic Organization and Membership API at high scale (>1M requests/day), the recommendation reverts to **Spring Boot on containers**. The always-on cost is amortised across millions of requests, the JVM is the most efficient runtime per request at high throughput, and the operational tooling (Prometheus, Grafana, Flyway, HikariCP) is mature and well-understood. The migration from Supabase back to Spring Boot at this scale is a 2-week project, not a 2-month project, because the relational schema is already correct and only the application layer needs to be reintroduced.

For a workload that requires global sub-50ms p99 (multi-continent user base, mobile-first, latency-sensitive UX), the recommendation is **Vercel with the Edge runtime for reads**. The 35+ PoPs and 5ms cold start are unmatched by any other platform in this comparison, and the Neon HTTP driver makes Postgres accessible from the edge without connection-pool issues. The cost premium at high traffic (~4× Supabase at 1M req/day) is the price of geographic distribution.

For a workload with a non-relational data model (chat messages, real-time game state, event streams with append-only semantics), the recommendation is **Firebase**. Firestore's nested-document model is a natural fit for these workloads, the offline persistence in the client SDK is unmatched by any other platform, and the real-time `onSnapshot` listeners are a feature no other platform in this comparison offers. The 1850ms cold start on Cloud Functions is a real cost, but for these workloads most reads go through the direct SDK (35ms p99) and Cloud Functions are only used for the rarer mutations.

The decision tree is the actual output of this milestone. The four implementations are the evidence the tree is grounded in measured numbers. If your workload does not fit any of the four leaves above, the answer is "build a prototype in two of the architectures, measure them both under your real traffic, and decide based on data" — which is what this milestone did, and which is the only honest way to make an architecture decision for a workload that does not match the canonical patterns.
