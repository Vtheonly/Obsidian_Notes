# 13.06.01. System Specification

## Project Goal

This milestone takes the Organization and Membership REST API built in [[13.01.02. Anchor Implementation Spring Boot]] and migrates it away from a long-running Spring Boot container into three distinct serverless/BaaS topologies: Vercel (serverless functions + Edge functions backed by Postgres), Supabase (Postgres + Row-Level Security + Deno Edge Functions), and Firebase (Firestore + Cloud Functions v2). The point is not to prove serverless is better. The point is to discover, by building the same API three times, which classes of problems disappear when the platform owns scaling/identity/storage, which classes of problems move to a different layer (auth becomes an HTTP header check instead of a Spring Security filter chain; persistence becomes RLS or Firestore rules instead of `@Transactional` boundaries), and which problems become strictly worse (cold starts, database connection management, local dev parity, vendor lock-in).

The deliverable is a migration, not a rewrite. The HTTP contract — paths, status codes, JSON shapes, role semantics — must be byte-identical to the Milestone 1 anchor so that the same k6 load-test plan and the same Postman collection run unmodified against all three target platforms. The internal architecture changes; the wire contract does not. This is what a real serverless migration looks like: the cost surface shifts from "EC2 instances + JVM heap tuning + Nginx worker_processes" to "cold-start p99 + per-platform invocation pricing + connection-pool proxy math", but the product team does not see a difference, and the client SDKs do not need to be touched.

You are done with this milestone when you can show three production deployments, a captured cold-start p99 for each, a captured steady-state p99 for each, a load test that pushed at least one of them to a documented failure mode (rate limit, function timeout, RLS policy mis-firing, Firestore contention), and a written decision tree that says — given a workload with these properties — which of the four architectures (Spring Boot container, Vercel, Supabase, Firebase) is the right choice. The decision tree is the actual deliverable; the code is the evidence the decision tree is grounded in reality.

## Requirements

- **Re-implement the Organization and Membership core API using Serverless Edge Functions and BaaS.** The "core API" is the eight endpoints defined in the Milestone 1 contract: `POST /api/orgs`, `GET /api/orgs/:id`, `GET /api/orgs` (list, paginated, with `?role=owner|admin|member` filter), `PATCH /api/orgs/:id`, `DELETE /api/orgs/:id`, `POST /api/orgs/:id/members`, `GET /api/orgs/:id/members`, `DELETE /api/orgs/:id/members/:userId`. Every endpoint must enforce the role matrix from Milestone 1: only the org owner can delete the org or change another member's role; admins can invite/remove members but cannot delete the org; members can read but cannot mutate membership. The API must continue to accept a `Bearer <jwt>` header issued by a separate identity provider — Vercel deployments use Auth0 or NextAuth, Supabase uses its built-in GoTrue, Firebase uses Firebase Auth. The JWT claim shape is platform-specific, but the same user must reach the same role on the same org across all three deployments.
- **Evaluate cold-start latency, connection pool behaviors, developer velocity, and operational cost curves against the containerized architecture.** "Evaluate" means: capture the cold-start p99 with at least 50 invocations after a 5-minute idle window; capture the steady-state p99 with a 2-minute k6 ramp from 0 to 200 virtual users; capture the cost-per-1M-requests figure using each platform's published pricing (Vercel Pro $40/mo + $40 per 100GB-sec, Supabase Pro $25/mo flat + $10 per 1GB additional DB, Firebase Blaze pay-per-invocation at $0.0000004 per Cloud Function invocation + Firestore $0.036 per 100K reads); and document at least one production-shaped failure mode per platform. The numbers must be measured, not quoted from the docs — the docs lie about p99 by about 3× because they measure the happy path.
- Each requirement is non-negotiable. If you skip one, you have completed a tutorial, not a milestone.

## Acceptance Criteria

1. **All four target ecosystems implement the same contract.** The Spring Boot anchor from Milestone 1 (kept as-is, deployed to a long-running EC2 or fly.io container) and the three new serverless/BaaS deployments (Vercel, Supabase, Firebase) must all serve the same OpenAPI spec. Validate this by running the same Postman collection against each deployment URL; if any collection item fails on any platform, the milestone is not complete.
2. **All four pass the same automated test suite (k6, pytest, or Postman).** The k6 plan from Milestone 1 must run unmodified against all four deployments. The test plan must include at minimum: (a) a smoke test that creates an org, lists members, deletes the org; (b) an authz test that asserts a non-owner cannot delete an org (expect HTTP 403); (c) a load test that ramps to 200 VUs over 2 minutes and reports p50/p95/p99 latency.
3. **At least one ecosystem is load-tested to failure, with a captured metric showing the failure and the fix.** "Failure" means a non-200 response rate above 1% under load, or a p99 above the platform's published SLO. The captured metric must be a Grafana screenshot, a Datadog trace, or a k6 summary JSON — not a vibe. The "fix" must be a concrete code or config change (raise `maxDuration`, switch from Vercel serverless function to Edge function, add a Supabase RLS policy index, move a Firestore write batch out of a Cloud Function trigger).
4. **The post-mortem note ([[13.06.05. Architectural Benchmarks and Final Engineering Assessment]]) is filled in with concrete observations.** Empty cells in the comparison matrix are not acceptable. The decision tree at the end of the post-mortem must be a real tree (with branches, leaves, and named workload properties), not a one-line recommendation.

## Deliverables

- **Source code for each ecosystem in a separate subfolder.** The repo structure is `13.06/serverless-migration/{vercel,supabase,firebase}/` plus the Milestone 1 anchor checked out at `13.06/anchor-springboot/`. Each subfolder has its own `package.json` or `pyproject.toml` or `requirements.txt` and its own deploy script. The Spring Boot anchor is unchanged from Milestone 1 — do not "fix" it. The point of keeping it untouched is to give the post-mortem an honest baseline.
- **A `docker-compose.yml` at the project root.** Used only for local Postgres + Supabase local emulator + Firebase emulator. The deployments themselves run on the real hosted platforms; `docker-compose` exists so that local development matches the hosted RLS rules and Firestore security rules. Do not put the production deploy targets in `docker-compose` — that defeats the purpose of the milestone.
- **A `README.md` with run instructions and a load-test screenshot.** The README must have, for each platform: the bootstrap command, the local-dev command, the deploy command, the URL of the live deployment, and the screenshot of the k6 summary showing p99. The screenshot is the receipt — without it, the milestone is anecdote.
- **A post-mortem note in this folder.** This is [[13.06.05. Architectural Benchmarks and Final Engineering Assessment]]. It must contain: the filled-in comparison matrix, the "what the anchor taught that the deltas did not" section, the "what the deltas taught that the anchor hid" section, and the decision tree.

The Spring Boot anchor — kept as the baseline against which all three are measured — is the simplest path: client → Nginx (TLS, gzip, keepalive to upstream) → Spring Boot on JVM (Tomcat thread pool, HikariCP connection pool, JPA/Hibernate, Spring Security filter chain) → Postgres on RDS. There is exactly one long-running process per AZ, the JVM holds 256–512MB of heap, the HikariCP pool holds 10 connections per pod, and the JVM has been warm for hours so cold-start p99 is essentially the TLS handshake. This is what "no cold starts, no serverless primitives" buys you — and what you give up is per-request cost (you pay for the EC2 instance whether or not it is handling traffic), scale-to-zero (the JVM is always-on), and per-region geographic distribution (you deploy to one region and accept the latency for users elsewhere).

## Migration Contract

The Milestone 1 anchor has a specific feature surface. Some of it carries over unchanged, some of it changes shape, and some of it is explicitly dropped because the target platform either handles it for you or makes it impossible. The table below is the migration contract — every row is a decision, not a recommendation.

| Milestone 1 feature | Vercel migration | Supabase migration | Firebase migration |
| --- | --- | --- | --- |
| `POST /api/orgs` create | Kept. Vercel serverless function inserts via Neon HTTP driver. | Kept as PostgREST `POST /rest/v1/orgs`. Becomes a single SQL insert with RLS enforcing `auth.uid()` is set as owner. | Kept as Cloud Function `onCall`. Function writes a Firestore doc with `owner: uid`. |
| `GET /api/orgs/:id` | Kept. Edge function reads Neon via HTTP driver. | Kept as PostgREST `GET /rest/v1/orgs?id=eq.X`. RLS policy allows read if `auth.uid()` is a member. | Kept as direct client `getDoc()` — no Cloud Function needed because Firestore Security Rule enforces membership. |
| `GET /api/orgs?role=owner` filter | Kept. Edge function builds SQL string with parameterized role. | Kept. PostgREST query syntax: `?role=eq.owner`. RLS still applies on top. | Kept as client `where('owner','==',uid)` query. |
| `DELETE /api/orgs/:id` | Kept. Serverless function checks `owner_id == auth.sub` before issuing DELETE. | Kept as PostgREST `DELETE`. RLS policy `USING (auth.uid() = owner_id)`. | Kept as Cloud Function (cannot do this from client SDK because Security Rules don't support conditional deletes on a doc you can already read). |
| `POST /api/orgs/:id/members` | Kept. Atomic INSERT in a transaction. | Kept. PostgREST RPC call to `add_member()` PL/pgSQL function (cross-table atomicity). | Kept as Cloud Function — writes to a `members` subcollection with a batched write to update the org's `member_count`. |
| `PATCH /api/orgs/:id/members/:userId` (change role) | Kept. Serverless function: UPDATE with WHERE. | Kept as PostgREST RPC `change_member_role()` (because only the owner can run this, enforced in PL/pgSQL). | Kept as Cloud Function (Security Rules can't express "only owner can write to this field"). |
| Spring Security filter chain (Bearer JWT) | Replaced by `verifyJwt` from `@vercel/jwt` in an Edge function middleware. | Replaced by GoTrue issuing Supabase JWTs; PostgREST consumes the JWT automatically and `auth.uid()` is populated. | Replaced by Firebase Admin SDK `verifyIdToken()` in Cloud Functions, or by Firestore Security Rules using `request.auth.uid` directly. |
| `@Transactional` rollback on partial failure | Kept via Postgres `BEGIN/COMMIT` over HTTP driver — Neon supports this. | Native — a PL/pgSQL function is implicitly atomic. | Changed semantics — Firestore `writeBatch()` is atomic for up to 500 docs, but cross-collection transactions need a Cloud Function. |
| Spring `@Valid` DTO validation | Manual Zod schema in the Vercel function. | Native — PostgREST validates against the Postgres column types and constraints. | Manual — `joi` or `zod` in the Cloud Function. Firestore Security Rules can validate types but not business rules. |
| Spring ProblemDetail RFC 7807 errors | Manual in each function. Same JSON shape. | PostgREST returns its own error shape — translated by a small Edge Function shim if RFC 7807 is required. | Cloud Functions SDK error → client gets a Google-formatted error. Acceptable divergence, documented in post-mortem. |
| HikariCP connection pool (10 conns/pod) | Eliminated — Neon HTTP driver has no pool, one HTTP request per query. | Replaced by Supabase-managed PgBouncer (transaction-pooling, 200 server-side conns). | Eliminated — Firestore is not a connection-pool protocol. |
| Prometheus `/actuator/prometheus` scrape | Replaced by Vercel's OpenTelemetry-compatible log drain. | Replaced by Supabase's built-in `pg_stat_statements` + log explorer. | Replaced by Cloud Functions `console.log` → Cloud Logging → Cloud Monitoring. |
| k6 load test plan (200 VU, 2min) | Kept byte-identical. URL changes only. | Kept byte-identical. URL changes only. | Kept byte-identical. URL changes only. |
| Long-running migrations (Flyway) | Dropped on Vercel — run migrations from a GitHub Action with `psql` against Neon. | Kept — Supabase has a `supabase migration` CLI. | Dropped — Firestore is schemaless, so there is no migration step. Document this as a divergence. |
| Local dev via `docker-compose` | Partial — Vercel CLI (`vercel dev`) provides local function runtime; Postgres in compose. | Full — `supabase start` runs the entire stack locally via compose. | Full — `firebase emulators:start` runs Auth, Firestore, Functions locally. |

The contract is: every row that says "Kept" must produce a byte-identical HTTP response to the Spring Boot anchor when called with the same input. Rows that say "Changed semantics" or "Dropped" must be documented in [[13.06.05. Architectural Benchmarks and Final Engineering Assessment]] with the user-visible consequence. Rows that say "Replaced by" are implementation details — the wire contract does not change, only the layer that performs the work changes.
