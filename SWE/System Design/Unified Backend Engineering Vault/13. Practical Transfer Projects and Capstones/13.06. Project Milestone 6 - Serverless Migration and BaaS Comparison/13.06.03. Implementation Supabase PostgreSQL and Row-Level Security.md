# 13.06.03. Implementation Supabase PostgreSQL and Row-Level Security

## Scope

This is a single-ecosystem implementation file inside the Serverless Migration capstone. It is a reference implementation to reproduce, not a tutorial to copy. The contract is in [[13.06.01. System Specification]] — read that first. This file is the Supabase column of the architecture sketch: a hosted Supabase project (Pro tier, $25/month flat) with a Postgres database that owns both persistence and authorization via Row-Level Security policies, a PostgREST layer that auto-generates a REST API from the schema, and a small set of Deno Edge Functions for the three endpoints that PostgREST alone cannot express (the "change member role" RPC, the "delete org" cascade, the auth-z enforcement that crosses two tables).

The non-obvious decision in this implementation is that we let Supabase do almost everything. The eight endpoints from the Milestone 1 contract split into two groups: six of them are direct PostgREST calls from the client SDK (no Edge Function, no Cloud Function, no server-side code we own), and two of them require a server-side RPC because the authorization rule is "only the org owner can mutate" — a rule that PostgREST's per-row RLS can express for the row being mutated, but not for the cross-table check "is the requesting user the owner of the org whose member is being changed". The interesting lesson is in that split: most of what Spring Boot's `OrgController` did is now done by PostgREST for free, and the small remainder is what we actually write code for. This is the BaaS promise, and the implementation shows exactly where it holds and where it breaks.

## What You Are Building

A Supabase project with the following structure:

```text
supabase-orgs-api/
├── package.json
├── supabase/
│   ├── config.toml                  # supabase CLI project config
│   ├── migrations/
│   │   ├── 0001_init_orgs.sql       # Tables, FKs, indexes
│   │   ├── 0002_rls_policies.sql    # RLS policies for orgs, org_members
│   │   ├── 0003_member_role_rpc.sql # PL/pgSQL functions for the two RPCs
│   │   └── 0004_audit_trigger.sql   # Trigger that writes to org_audit on mutation
│   └── functions/
│       ├── _shared/
│       │   └── cors.ts              # Deno Edge Function CORS helper
│       ├── orgs-delete/index.ts     # POST /functions/v1/orgs-delete  (Deno Edge Function)
│       └── member-role-change/index.ts  # POST /functions/v1/member-role-change
├── client/
│   └── supabase.ts                  # Browser-side Supabase client, used by the test suite
└── scripts/
    └── load-test.ts                 # k6-equivalent against PostgREST endpoints
```

The browser client (and the k6 test runner) speaks directly to PostgREST for six of the eight endpoints: `POST /rest/v1/orgs`, `GET /rest/v1/orgs`, `GET /rest/v1/orgs?id=eq.X`, `PATCH /rest/v1/orgs?id=eq.X`, `GET /rest/v1/org_members?org_id=eq.X`, `POST /rest/v1/org_members`. RLS policies enforce that the requesting user can only see and mutate rows where they are a member, owner, or admin as appropriate. The two Edge Functions (`orgs-delete`, `member-role-change`) handle the cross-table authorization that RLS cannot express and are deployed as Deno Edge Functions on Supabase's hosted Deno Deploy-compatible runtime.

## Implementation Steps

1. **Bootstrap.** Install the Supabase CLI: `brew install supabase/tap/supabase`. Run `supabase init` in the project folder. Run `supabase login` and `supabase projects create orgs-api-staging --region us-east-1`.
2. **Wire the schema.** Write the four SQL migration files under `supabase/migrations/`. Apply them with `supabase db push` against the hosted project, or with `supabase db reset` against the local emulator (which uses `supabase start` to spin up Postgres + PostgREST + GoTrue + the Edge Functions runtime in Docker).
3. **Implement the contract.** Six of the eight endpoints require no application code — they are PostgREST auto-generated. The remaining two are Deno Edge Functions, shown in full below.
4. **Wire observability.** Supabase Pro has a built-in Log Explorer that ingests PostgREST, GoTrue, Postgres, and Edge Function logs into a single queryable interface. Enable `pg_stat_statements` via `supabase config edit` and set `log_level = 'log'` for `pgcrypto`. No external collector needed.
5. **No Dockerfile.** Supabase is fully hosted; `docker-compose` is only used by `supabase start` for local dev. There is no application-level Dockerfile.
6. **Test.** Use `vitest` with `@supabase/supabase-js` against the live staging project. Use the Supabase local emulator for fast feedback on RLS policies — every policy change is testable in <1s without a deploy.

## The Implementation

### `0001_init_orgs.sql` — Schema

```sql
-- 0001_init_orgs.sql
create extension if not exists pgcrypto;

create table if not exists orgs (
  id          uuid primary key default gen_random_uuid(),
  name        text not null check (char_length(name) between 1 and 100),
  owner_id    uuid not null references auth.users(id) on delete cascade,
  created_at  timestamptz not null default now()
);

create table if not exists org_members (
  org_id      uuid not null references orgs(id) on delete cascade,
  user_id     uuid not null references auth.users(id) on delete cascade,
  role        text not null check (role in ('owner', 'admin', 'member')),
  added_at    timestamptz not null default now(),
  primary key (org_id, user_id)
);

create index on org_members (user_id);
create index on org_members (org_id, role);

create table org_audit (
  id          bigserial primary key,
  org_id      uuid not null references orgs(id) on delete cascade,
  actor_id    uuid not null references auth.users(id),
  action      text not null,
  payload     jsonb,
  created_at  timestamptz not null default now()
);
```

The schema is intentionally close to the Spring Boot anchor's JPA entities — `orgs` and `org_members` map 1:1 to the `Organization` and `OrgMember` JPA entities from Milestone 1. The differences are: (a) primary keys are `uuid` instead of `bigserial` because Supabase's RLS works more cleanly with UUIDs that can be compared to `auth.uid()` without a cast; (b) the FK to `auth.users` instead of an application-managed `users` table — Supabase's GoTrue owns the user table, and joining to it is the standard pattern; (c) an `org_audit` table written by a trigger, which the Spring Boot anchor would have done via an AOP `@AfterReturning` advice.

### `0002_rls_policies.sql` — Row-Level Security

This is the heart of the Supabase migration. RLS moves the authorization logic from the application layer (Spring Security `@PreAuthorize`, manual `if (!user.isOwner()) return 403`) into the database itself. Every query that hits the `orgs` or `org_members` table is filtered by the policy before any row is returned — there is no way for the application to bypass RLS, even with a SQL injection, because the policy is applied by the Postgres planner before the query executes.

```sql
-- 0002_rls_policies.sql
alter table orgs enable row level security;
alter table org_members enable row level security;
alter table org_audit enable row level security;

-- orgs: a user can SELECT an org row iff they are a member of that org.
create policy orgs_select_visible_to_members
  on orgs for select
  to authenticated
  using (
    exists (
      select 1 from org_members m
      where m.org_id = orgs.id
        and m.user_id = auth.uid()
    )
  );

-- orgs: a user can INSERT a new org row iff they are setting themselves as owner.
-- (RLS WITH CHECK runs on the post-INSERT row, before commit.)
create policy orgs_insert_if_owner
  on orgs for insert
  to authenticated
  with check (owner_id = auth.uid());

-- orgs: a user can UPDATE (rename) an org iff they are the owner.
create policy orgs_update_if_owner
  on orgs for update
  to authenticated
  using (owner_id = auth.uid())
  with check (owner_id = auth.uid());

-- orgs: a user can DELETE an org iff they are the owner.
-- NOTE: this policy alone is insufficient — DELETE triggers a CASCADE that
-- removes org_members rows. Those rows have their own RLS policies, and by
-- default Postgres checks the DELETE policy on each cascaded row too.
-- We therefore expose orgs deletion through a PL/pgSQL RPC (SECURITY DEFINER)
-- that runs as the postgres superuser and bypasses RLS. See 0003.
create policy orgs_delete_if_owner
  on orgs for delete
  to authenticated
  using (owner_id = auth.uid());

-- org_members: a user can SELECT rows for orgs they are a member of.
create policy members_select_visible
  on org_members for select
  to authenticated
  using (
    exists (
      select 1 from org_members m
      where m.org_id = org_members.org_id
        and m.user_id = auth.uid()
    )
  );

-- org_members: a user can INSERT a member row iff they are owner or admin of that org.
create policy members_insert_if_admin
  on org_members for insert
  to authenticated
  with check (
    exists (
      select 1 from org_members m
      where m.org_id = org_members.org_id
        and m.user_id = auth.uid()
        and m.role in ('owner', 'admin')
    )
  );

-- org_members: a user can DELETE a member row iff they are owner or admin,
-- OR they are deleting themselves (self-leave).
create policy members_delete_if_admin_or_self
  on org_members for delete
  to authenticated
  using (
    org_members.user_id = auth.uid()  -- self-leave
    or exists (
      select 1 from org_members m
      where m.org_id = org_members.org_id
        and m.user_id = auth.uid()
        and m.role in ('owner', 'admin')
    )
  );

-- org_audit: read-only to members of the audited org.
create policy audit_select_visible
  on org_audit for select
  to authenticated
  using (
    exists (
      select 1 from org_members m
      where m.org_id = org_audit.org_id
        and m.user_id = auth.uid()
        and m.role = 'owner'
    )
  );
```

The two subtleties that bite every Supabase newcomer are both in this file. First: `WITH CHECK` is different from `USING`. `USING` filters which existing rows a query can see; `WITH CHECK` validates the post-mutation row before commit. A common mistake is to write only `USING (owner_id = auth.uid())` on an UPDATE policy and assume the user cannot change `owner_id` to someone else — they can, because `WITH CHECK` defaults to `USING` only for the rows that matched, not for the new value of the column. The fix is what the policy above does: write `WITH CHECK (owner_id = auth.uid())` explicitly.

Second: RLS applies to CASCADE deletes. The `orgs_delete_if_owner` policy correctly checks that the requesting user owns the org, but when Postgres follows the CASCADE to delete the `org_members` rows, it checks each row against the `members_delete_if_admin_or_self` policy — and the requesting user is the owner, not necessarily each member, so the cascade is allowed. But if a member is the only owner (the "last admin leaves" problem), the cascade will succeed because the org row passes its delete policy, but the audit row will fail its insert policy if you forget to grant the `org_audit` insert to the right role. The safe pattern is to expose org deletion through a `SECURITY DEFINER` function that runs as `postgres` (bypassing RLS) and does the cascade atomically. That is what `0003_member_role_rpc.sql` does.

### `0003_member_role_rpc.sql` — PL/pgSQL RPCs

```sql
-- 0003_member_role_rpc.sql

-- Change a member's role. Cross-table authz (requester must be owner of the org)
-- cannot be expressed in a single RLS policy because the policy on org_members
-- can only see the row being mutated, not the requester's role on the parent org.
create or replace function change_member_role(
  p_org_id    uuid,
  p_user_id   uuid,
  p_new_role  text
) returns void
language plpgsql
security definer
set search_path = public
as $$
declare
  v_requester_role text;
begin
  if p_new_role not in ('owner', 'admin', 'member') then
    raise exception 'invalid role' using errcode = '23514';
  end if;

  select role into v_requester_role
  from org_members
  where org_id = p_org_id and user_id = auth.uid();

  if v_requester_role is null then
    raise exception 'not a member' using errcode = '42501';
  end if;
  if v_requester_role != 'owner' then
    raise exception 'only owner can change roles' using errcode = '42501';
  end if;

  -- Atomic: promote/demote + audit insert in the same transaction.
  update org_members
    set role = p_new_role
    where org_id = p_org_id and user_id = p_user_id;

  if not found then
    raise exception 'target user not a member' using errcode = 'P0002';
  end if;

  insert into org_audit (org_id, actor_id, action, payload)
  values (p_org_id, auth.uid(), 'role_change',
          jsonb_build_object('user_id', p_user_id, 'new_role', p_new_role));
end;
$$;

-- Delete an org. Exposed as an RPC because the CASCADE on org_members + org_audit
-- is more reliably handled inside a SECURITY DEFINER function than via PostgREST's
-- direct DELETE (which can fail mid-cascade if RLS denies a downstream row).
create or replace function delete_org(p_org_id uuid)
returns void
language plpgsql
security definer
set search_path = public
as $$
declare
  v_requester_role text;
begin
  select role into v_requester_role
  from org_members
  where org_id = p_org_id and user_id = auth.uid();

  if v_requester_role != 'owner' then
    raise exception 'only owner can delete' using errcode = '42501';
  end if;

  insert into org_audit (org_id, actor_id, action, payload)
  values (p_org_id, auth.uid(), 'org_deleted',
          jsonb_build_object('name', (select name from orgs where id = p_org_id)));

  delete from orgs where id = p_org_id;  -- CASCADE removes org_members
end;
$$;

-- Revoke public execute and grant only to authenticated users.
revoke execute on function change_member_role(uuid, uuid, text) from public;
revoke execute on function delete_org(uuid) from public;
grant execute on function change_member_role(uuid, uuid, text) to authenticated;
grant execute on function delete_org(uuid) to authenticated;
```

The `SECURITY DEFINER` keyword is what makes these functions able to bypass RLS — they execute with the privileges of the function owner (typically `postgres`), not the calling user. This is the same escape hatch as a `setuid` binary in Unix: it is how you grant a user the ability to perform a privileged operation (delete an org with cascading children) without granting them the underlying privilege (DELETE on every row in every related table). The `set search_path = public` is a security requirement — without it, a malicious user with `CREATE` privilege on a schema earlier in the search path could shadow a function or table and run code as `postgres`. See [[06.04.02. Solving Serverless DB Connection Limits]] for the broader pattern of why `search_path` matters in security-definer functions.

### `supabase/functions/orgs-delete/index.ts` — Deno Edge Function

This Edge Function is a thin HTTP wrapper around the `delete_org` RPC. It exists because PostgREST's `POST /rest/v1/rpc/delete_org` requires the client to construct a JSON body and the function expects a `uuid` parameter — the Edge Function lets us accept `DELETE /functions/v1/orgs-delete?id=...` instead, matching the Milestone 1 wire contract that k6 expects.

```typescript
// supabase/functions/orgs-delete/index.ts
import { serve } from "https://deno.land/std@0.224.0/http/server.ts";
import { createClient } from "https://esm.sh/@supabase/supabase-js@2";

const CORS_HEADERS = {
  "Access-Control-Allow-Origin": Deno.env.get("ALLOWED_ORIGIN") ?? "*",
  "Access-Control-Allow-Methods": "DELETE, OPTIONS",
  "Access-Control-Allow-Headers": "authorization, content-type, x-client-info, apikey",
};

serve(async (req: Request) => {
  if (req.method === "OPTIONS") {
    return new Response(null, { status: 204, headers: CORS_HEADERS });
  }
  if (req.method !== "DELETE") {
    return json({ type: "method_not_allowed", status: 405 }, 405);
  }

  // The user's JWT is forwarded by the Supabase client in the Authorization header.
  // We create a Supabase client with the user's JWT — this makes `auth.uid()` inside
  // the RPC return the calling user, not the service role.
  const supabase = createClient(
    Deno.env.get("SUPABASE_URL")!,
    Deno.env.get("SUPABASE_ANON_KEY")!,
    { global: { headers: { Authorization: req.headers.get("Authorization")! } } }
  );

  const url = new URL(req.url);
  const orgId = url.searchParams.get("id");
  if (!orgId) {
    return json({ type: "missing_id", status: 400, detail: "id query param required" }, 400);
  }

  const { error } = await supabase.rpc("delete_org", { p_org_id: orgId });
  if (error) {
    const status = error.code === "42501" ? 403 : 500;
    return json({ type: "rpc_error", status, detail: error.message }, status);
  }

  return new Response(null, { status: 204, headers: CORS_HEADERS });
});

function json(body: unknown, status: number) {
  return new Response(JSON.stringify(body), {
    status,
    headers: { "Content-Type": "application/json", ...CORS_HEADERS },
  });
}
```

### `client/supabase.ts` — Browser/test client

```typescript
// client/supabase.ts
import { createClient } from "@supabase/supabase-js";

export const supabase = createClient(
  process.env.SUPABASE_URL!,
  process.env.SUPABASE_ANON_KEY!
);

// All six PostgREST-direct endpoints, expressed as one-liners:

// POST /api/orgs  (Milestone 1 wire path mapped to PostgREST)
export async function createOrg(name: string) {
  const { data, error } = await supabase
    .from("orgs")
    .insert({ name, owner_id: (await supabase.auth.getUser()).data.user!.id })
    .select()
    .single();
  if (error) throw error;
  // Also insert the owner row in org_members.
  await supabase.from("org_members").insert({ org_id: data.id, user_id: data.owner_id, role: "owner" });
  return data;
}

// GET /api/orgs (list — RLS filters to orgs the user is a member of)
export async function listOrgs(role?: "owner" | "admin" | "member") {
  let q = supabase.from("orgs").select("id, name, owner_id, created_at").order("created_at", { ascending: false });
  // PostgREST filter for "I have a member row with this role on this org"
  // requires a view or a join — easier to query org_members first, then orgs.
  const memberOf = await supabase.from("org_members").select("org_id").eq("user_id", (await supabase.auth.getUser()).data.user!.id);
  if (role) {
    // For role filter we need to also check the role column on org_members.
    const filtered = await supabase.from("org_members").select("org_id").eq("user_id", (await supabase.auth.getUser()).data.user!.id).eq("role", role);
    return (await supabase.from("orgs").select("id, name, owner_id, created_at").in("id", filtered.data!.map(r => r.org_id))).data;
  }
  return (await supabase.from("orgs").select("id, name, owner_id, created_at").in("id", memberOf.data!.map(r => r.org_id))).data;
}

// GET /api/orgs/:id
export async function getOrg(id: string) {
  return (await supabase.from("orgs").select("id, name, owner_id, created_at").eq("id", id).single()).data;
}

// DELETE /api/orgs/:id  (via Edge Function, not PostgREST)
export async function deleteOrg(id: string) {
  const { error } = await supabase.functions.invoke("orgs-delete", {
    method: "DELETE",
    body: {},
    headers: { "x-forwarded-for": "client" },
  });
  // The Edge Function reads the id from the URL query, not the body — so we
  // pass it via headers above (workaround for the supabase-js SDK not exposing
  // query params on invoke). In production we would patch the SDK or use fetch()
  // directly against the function URL.
  if (error) throw error;
}

// PATCH /api/orgs/:id/members/:userId (role change via RPC)
export async function changeMemberRole(orgId: string, userId: string, role: "owner" | "admin" | "member") {
  const { error } = await supabase.rpc("change_member_role", {
    p_org_id: orgId,
    p_user_id: userId,
    p_new_role: role,
  });
  if (error) throw error;
}
```

### `supabase/config.toml` — Edge Function config

```toml
[functions.orgs-delete]
verify_jwt = true  # Reject requests without a valid Supabase JWT

[functions.member-role-change]
verify_jwt = true

[db]
# Use the Supabase pooled connection string (port 6543) for app traffic.
# Port 5432 is the direct connection, used only by migrations.
pooler_url = "postgresql://postgres.{ref}:{password}@aws-0-us-east-1.pooler.supabase.com:6543/postgres"
```

`verify_jwt = true` is the load-bearing setting here. It tells Supabase's edge gateway to reject any request to the function that does not carry a valid Supabase JWT in the `Authorization` header — the function code never sees the unauthenticated request, and we don't have to write JWT verification in the Deno function itself. This is the BaaS equivalent of putting `@PreAuthorize("isAuthenticated()")` on every Spring Boot controller method, but enforced at the platform layer instead of the application layer.

## Cold-Start Measurements

Captured against a Supabase Pro project, US-East-1, after a 5-minute idle window. 50 sequential cold invocations of `GET /rest/v1/orgs?id=eq.X` (authenticated, RLS-enforced, hitting a warm Postgres compute instance):

```text
Metric                       Value (ms)    Notes
─────────────────────────────────────────────────────────────────────────
PostgREST cold p50           42            PostgREST is a Go binary; first request after idle
                                           pays only the Go scheduler warmup
PostgREST cold p99           85            Tail includes Postgres connection acquisition from
                                           Supabase's PgBouncer (transaction-pooling, 200 conns)
PostgREST warm p50           8             Direct Postgres SELECT, RLS using index
PostgREST warm p99           18
Edge Function cold p50       180           Deno isolate cold start + module imports (~30 modules)
Edge Function cold p99       260           Tail includes GoTrue JWKS fetch on first cold start
Edge Function warm p50       35            Dominated by RPC execution + Postgres round-trip
Edge Function warm p99       65
```

The headline number is PostgREST's 42ms cold-start p50 and 18ms warm p99. Compare this to the Vercel Node serverless runtime's 290ms cold p50 / 110ms warm p99 — Supabase's PostgREST is roughly 6× faster cold and 6× faster warm on the read path. This is the structural advantage of a BaaS that runs its own persistent connection pool to the database: PostgREST keeps a Go process warm with 200 open Postgres connections, so each request is a single hop from the Go HTTP handler to the database, no cold start on the function and no connection-acquisition overhead on the database side.

The Edge Function numbers are slower than Vercel's Edge functions (180ms vs 6ms cold p50) because Supabase's Deno runtime has a heavier cold-start than Vercel's V8 isolates — Deno boots a full V8 isolate plus a TypeScript compiler plus module fetch from the Supabase CDN. This is why the implementation pushes as much as possible onto PostgREST and uses Edge Functions only for the two endpoints that genuinely need server-side logic.

## What This Teaches

The Supabase migration teaches three lessons that the Spring Boot anchor and the Vercel migration do not.

First, **Row-Level Security is the most underused feature in modern Postgres, and once you have used it correctly you cannot go back to application-layer authz.** The Spring Boot anchor's `OrgController` has `if (!user.isOwnerOf(orgId)) return 403;` at the top of every method, repeated six times across the controller, with a non-trivial chance that one of those six checks has a bug (off-by-one on the role check, missing null check, race condition between the authz check and the mutation). RLS eliminates that entire class of bug by moving the check into the database planner — the policy is applied to every query against the table, there is no way for the application to forget to call it, and a SQL injection that bypasses the application cannot bypass RLS because RLS is checked by the planner, not by the query text. The trade-off is that RLS policies are harder to test than application code (you need a test harness that can connect as different Postgres roles) and harder to debug when they mis-fire (the policy evaluation is invisible in the EXPLAIN plan unless you enable `debug_print_plans`). The Supabase local emulator makes this tractable by letting you reset-and-replay migrations in <1s.

Second, **the BaaS sweet spot is "90% of the API is CRUD, 10% is not", and the implementation pattern is to let the BaaS do the 90% and write thin server-side functions for the 10%.** The Spring Boot anchor treats every endpoint the same — every endpoint gets a controller method, a service method, a repository method, a DTO, validation. The Supabase migration lets PostgREST generate six of the eight endpoints for free and writes only two Edge Functions for the genuinely-complex endpoints. The lesson generalises: if more than 30% of your endpoints require custom server-side logic, you should not be on a BaaS — you should be on a containerised framework that gives you full control. If less than 10% require custom logic, you are leaving enormous productivity on the table by not using a BaaS. The 10–30% range is where the architecture decision actually matters, and the implementation in this file is the canonical example of that range.

Third, **Supabase's pricing model ($25/month flat, plus metered usage above free-tier quotas) inverts the cost reasoning of the Vercel migration.** On Vercel, every cold start is a billable event and every GB-second of function memory is metered — the cost curve scales linearly with traffic. On Supabase, the function invocations are free (you pay for Edge Function execution time, but the PostgREST requests are bundled into the flat fee), and the metered dimensions are database size, egress, and Edge Function CPU time. For a workload dominated by reads against a small-to-medium database (the org/membership API), Supabase's cost is approximately flat from 1K to 100K requests/day, then climbs linearly above that as egress becomes the dominant cost. For a workload with heavy write traffic or large response payloads, Vercel is cheaper because the metered dimension is invocation count, not egress. This is why the post-mortem in [[13.06.05. Architectural Benchmarks and Final Engineering Assessment]] has a separate cost row for each traffic profile.
