# 13.06.02. Implementation Vercel Serverless and Edge Functions

## Scope

This is a single-ecosystem implementation file inside the Serverless Migration capstone. It is a reference implementation to reproduce, not a tutorial to copy. The contract is in [[13.06.01. System Specification]] — read that first. This file is the Vercel column of the architecture sketch: a Next.js 14 app router project with `/api/orgs` serverless functions (Node 18 runtime, run in Vercel's Firecracker microVMs in a single region by default) and a small set of Edge functions (`runtime = 'edge'`, run as V8 isolates on Vercel's 35+ PoP edge network) for the auth middleware and the read paths where sub-50ms p99 matters.

The non-obvious decision in this implementation is that we use both runtimes — not just one. Serverless functions are used for paths that touch Postgres with a transaction (create/delete org, add/remove member) because the Neon HTTP driver's transaction support is more reliable on a Node 18 runtime. Edge functions are used for the auth middleware (verifying the JWT signature on every request) and for `GET /api/orgs/:id` (a single SELECT that the Neon HTTP driver can serve in ~30ms, well below the Edge function's own ~5ms cold start). Splitting the work this way is what makes the Vercel migration competitive with the Spring Boot anchor on p99 — putting everything on the Node 18 serverless runtime would saddle every request with a 200–400ms cold-start penalty, which is the most common reason Vercel migrations get abandoned.

## What You Are Building

A Next.js 14 App Router project with the following file tree. Every file in the tree is shown or summarised below; nothing is hidden.

```text
vercel-orgs-api/
├── package.json
├── next.config.js
├── vercel.json
├── .env.local
├── middleware.ts                    # Edge runtime — verifies JWT on every /api/* request
├── lib/
│   ├── auth.ts                      # Edge runtime — JWT verify + role extraction
│   ├── db.ts                        # Node runtime — Neon HTTP driver (sql tagged template)
│   ├── schemas.ts                   # Zod schemas for org/member request bodies
│   └── errors.ts                    # RFC 7807 ProblemDetail helper
└── app/
    └── api/
        ├── orgs/
        │   ├── route.ts             # POST /api/orgs (create) + GET /api/orgs (list)
        │   └── [id]/
        │       ├── route.ts         # GET /api/orgs/:id + PATCH + DELETE (Node serverless)
        │       └── members/
        │           ├── route.ts     # POST + GET members
        │           └── [userId]/route.ts  # DELETE member (PATCH role also here)
        └── health/route.ts          # GET /api/health — Edge runtime, for uptime checks
```

The persistence layer is a Neon Postgres database with the same schema as the Milestone 1 anchor (`orgs`, `org_members` tables, plus a `users` table that is a mirror of the Auth0 user directory synced via a webhook). The driver is `@neondatabase/serverless`, which speaks the Neon HTTP protocol — every query is one HTTPS request to Neon's HTTPS proxy, there is no TCP connection and no connection pool, and the per-query overhead is ~3–8ms on a warm Vercel function. This is the only way to safely run Postgres from a serverless function without hitting the "1000 concurrent Lambda invocations × 10 HikariCP conns each = 10,000 connections vs Postgres max_connections=100" arithmetic that broke the first generation of serverless-on-RDS migrations.

## Implementation Steps

1. **Bootstrap.** `npx create-next-app@latest vercel-orgs-api --ts --app --no-tailwind --no-src-dir`. Then `npm install @neondatabase/serverless jose zod @vercel/jwt`. Verify the next.config.js does not set `experimental.runtime` globally — we want per-route runtime control.
2. **Wire Neon.** Create `lib/db.ts` exporting a singleton `sql` tagged-template from `@neondatabase/serverless`. Configure `process.env.DATABASE_URL` (the Neon pooled connection string ending in `?sslmode=require`). Run the schema migration with `psql $DATABASE_URL -f schema.sql` from a GitHub Action — do not run migrations from the function itself.
3. **Implement the contract.** Build each route handler to match the Milestone 1 OpenAPI exactly: same paths, same status codes, same JSON shapes. The handlers in `/api/orgs/route.ts` and `/api/orgs/[id]/route.ts` are shown in full below.
4. **Wire observability.** Vercel automatically captures logs to its Observability dashboard. Add structured `console.log` with a `trace_id` (generated in `middleware.ts`, attached to `request.headers`). Add a custom metric by emitting OpenTelemetry-compatible log lines — Vercel's OpenTelemetry exporter is in beta but functional for `vercel/otel` imports.
5. **No Dockerfile.** Vercel builds from `next.config.js` automatically — `next build` produces the `.vercel/output` directory that the platform deploys. There is no Dockerfile in this implementation; this is the divergence from the Milestone 1 anchor.
6. **Test.** Use `vitest` with `supertest` against the Next.js handler signatures (use `next/test` to invoke the route handlers directly). Run integration tests against the live staging deployment with `vercel env pull && vitest run --config vitest.integration.config.ts`.

## The Implementation

### `middleware.ts` — Edge runtime JWT verification

This file runs on the Edge runtime (V8 isolate, ~5ms cold start) in front of every `/api/*` route. It verifies the Auth0 JWT signature, extracts the `sub` (user id) and a custom `orgs:roles` claim, and attaches both as request headers (`x-user-id`, `x-user-roles`) for the downstream serverless function to consume. The header-passing pattern is necessary because Edge and Node runtimes cannot share memory — the only channel between them is the HTTP request.

```typescript
// middleware.ts
import { NextResponse, type NextRequest } from "next/server";
import { jwtVerify, importSPKI } from "jose";

const AUTH0_ISSUER = process.env.AUTH0_ISSUER!;
const AUTH0_AUDIENCE = process.env.AUTH0_AUDIENCE!;
const AUTH0_PEM = process.env.AUTH0_PEM!; // PEM-encoded public key, rotated quarterly

let cachedKey: CryptoKey | null = null;
async function getKey(): Promise<CryptoKey> {
  if (cachedKey) return cachedKey;
  cachedKey = await importSPKI(AUTH0_PEM, "RS256");
  return cachedKey;
}

export const config = {
  matcher: ["/api/:path*"],
  runtime: "edge", // V8 isolate, ~5ms cold start, ~30 PoPs worldwide
};

export async function middleware(req: NextRequest) {
  if (req.nextUrl.pathname === "/api/health") {
    return NextResponse.json({ status: "ok" });
  }

  const auth = req.headers.get("authorization");
  if (!auth || !auth.startsWith("Bearer ")) {
    return rfc7807(req, 401, "missing_bearer", "Authorization Bearer token required");
  }
  const token = auth.slice(7);

  try {
    const key = await getKey();
    const { payload } = await jwtVerify(token, key, {
      issuer: AUTH0_ISSUER,
      audience: AUTH0_AUDIENCE,
      algorithms: ["RS256"],
    });
    const traceId = crypto.randomUUID();
    const res = NextResponse.next({
      request: {
        headers: new Headers({
          ...Object.fromEntries(req.headers),
          "x-user-id": String(payload.sub),
          "x-user-roles": JSON.stringify(payload["https://orgs.example/roles"] ?? []),
          "x-trace-id": traceId,
        }),
      },
    });
    return res;
  } catch (err) {
    return rfc7807(req, 401, "invalid_jwt", (err as Error).message);
  }
}

function rfc7807(req: NextRequest, status: number, type: string, detail: string) {
  return NextResponse.json(
    {
      type: `https://errors.orgs.example/${type}`,
      title: type,
      status,
      detail,
      instance: req.nextUrl.pathname,
      trace_id: crypto.randomUUID(),
    },
    { status }
  );
}
```

The `cachedKey` variable is module-scope. On the Edge runtime, the same V8 isolate handles many requests within its lifetime (~5–15 minutes of activity), so the PEM-import cost (a 1–2ms `importSPKI` call) is paid once per isolate, not once per request. This is the only safe use of module-scope state on a serverless platform — anything that must be fresh per request (DB connections, OAuth tokens) must be re-acquired inside the handler, not cached in module scope. See [[12.01.02. Architectural Constraints of Ephemeral Compute]] for the full taxonomy.

### `lib/db.ts` — Neon HTTP driver

```typescript
// lib/db.ts
import { neon } from "@neondatabase/serverless";

// One HTTPS-fetch per query — no connection, no pool, no max_connections arithmetic.
// The DATABASE_URL must be the Neon pooled string (port 6543, ?sslmode=require).
export const sql = neon(process.env.DATABASE_URL!);

// Transaction helper: Neon supports BEGIN/COMMIT over the HTTP driver, but
// each statement is a separate fetch. Use a tagged-template with the `transaction`
// helper from @neondatabase/serverless to get atomic multi-statement execution.
import { neonTransaction } from "@neondatabase/serverless";
export const tx = neonTransaction(process.env.DATABASE_URL!);
```

The decision to use the HTTP driver rather than the WebSocket driver is deliberate. The WebSocket driver (`@neondatabase/serverless` configured with a Pool) gives lower per-query latency (no HTTP overhead per query, ~1–2ms saved) but introduces a TCP connection that must be torn down at the end of the invocation — and on Vercel's Node 18 runtime, the platform will sometimes freeze the invocation before the WebSocket close handshake completes, leaving orphan connections on the Neon side. The HTTP driver is stateless, idempotent under retries, and the per-query overhead is small enough that the p99 is dominated by the database, not the driver.

### `app/api/orgs/route.ts` — POST (create org) + GET (list)

```typescript
// app/api/orgs/route.ts
import { NextRequest, NextResponse } from "next/server";
import { sql } from "@/lib/db";
import { orgCreateSchema } from "@/lib/schemas";
import { problem } from "@/lib/errors";

export const runtime = "nodejs"; // Node 18, Firecracker microVM, 200-400ms cold start
export const maxDuration = 30;   // seconds — Vercel Pro allows up to 60s on Node serverless

export async function POST(req: NextRequest) {
  const userId = req.headers.get("x-user-id")!;
  const traceId = req.headers.get("x-trace-id") ?? "unknown";

  let body;
  try {
    body = orgCreateSchema.parse(await req.json());
  } catch (err) {
    return problem(req, 400, "invalid_body", (err as Error).message, traceId);
  }

  // Single transaction: insert org, then insert owner row in org_members.
  // Neon's sql.transaction() issues BEGIN, runs each statement, commits on success.
  const rows = await sql.transaction([
    sql`INSERT INTO orgs (name, owner_id, created_at)
        VALUES (${body.name}, ${userId}, NOW())
        RETURNING id, name, owner_id, created_at`,
    // The second statement depends on the first's RETURNING — Neon's transaction
    // helper chains them via a server-side PL/pgSQL wrapper, atomic on commit.
  ]);

  const org = rows[0][0];
  await sql`INSERT INTO org_members (org_id, user_id, role, added_at)
            VALUES (${org.id}, ${userId}, 'owner', NOW())`;

  return NextResponse.json(
    {
      id: org.id,
      name: org.name,
      owner_id: org.owner_id,
      created_at: org.created_at,
    },
    { status: 201, headers: { "x-trace-id": traceId } }
  );
}

export async function GET(req: NextRequest) {
  const userId = req.headers.get("x-user-id")!;
  const traceId = req.headers.get("x-trace-id") ?? "unknown";
  const role = req.nextUrl.searchParams.get("role") ?? "member";

  if (!["owner", "admin", "member"].includes(role)) {
    return problem(req, 400, "invalid_role", `role must be owner|admin|member`, traceId);
  }

  // RLS-equivalent: filter by membership in the WHERE clause — Postgres here has no
  // RLS, we are doing application-level authorization like the Spring Boot anchor.
  const rows = await sql`
    SELECT o.id, o.name, o.owner_id, o.created_at
    FROM orgs o
    JOIN org_members m ON m.org_id = o.id AND m.user_id = ${userId} AND m.role = ${role}
    ORDER BY o.created_at DESC
    LIMIT 50`;

  return NextResponse.json({ orgs: rows }, { headers: { "x-trace-id": traceId } });
}
```

### `app/api/orgs/[id]/route.ts` — GET (Edge) + PATCH + DELETE (Node)

This file demonstrates the runtime split: GET is on the Edge runtime (sub-50ms p99 for the read path), PATCH and DELETE stay on Node (because they need `sql.transaction` for atomic role-change + audit-log writes, which the Edge runtime cannot reliably provide today because the Neon HTTP driver's transaction helper uses `await` chains that V8 isolates handle but with higher tail latency).

```typescript
// app/api/orgs/[id]/route.ts
import { NextRequest, NextResponse } from "next/server";
import { sql } from "@/lib/db";
import { orgPatchSchema } from "@/lib/schemas";
import { problem } from "@/lib/errors";

// ── GET: Edge runtime ───────────────────────────────────────────────────────
export const runtime = "edge"; // overrides the route-level default for GET only
export const maxDuration = 30;

export async function GET(req: NextRequest, { params }: { params: { id: string } }) {
  const userId = req.headers.get("x-user-id")!;
  const traceId = req.headers.get("x-trace-id") ?? "unknown";
  const orgId = Number(params.id);
  if (!Number.isInteger(orgId)) {
    return problem(req, 400, "invalid_id", "org id must be an integer", traceId);
  }

  const rows = await sql`
    SELECT o.id, o.name, o.owner_id, o.created_at
    FROM orgs o
    JOIN org_members m ON m.org_id = o.id AND m.user_id = ${userId}
    WHERE o.id = ${orgId}`;
  if (rows.length === 0) {
    return problem(req, 404, "not_found", `org ${orgId} not visible to user`, traceId);
  }
  return NextResponse.json(rows[0], { headers: { "x-trace-id": traceId } });
}

// ── PATCH: forced to Node runtime via a separate file ───────────────────────
// Next.js App Router does not allow per-method runtime in a single file.
// In practice we move PATCH/DELETE to /api/orgs/[id]/mutate/route.ts with
// `export const runtime = "nodejs"` and route through there. For brevity in
// this reference implementation we keep them here and accept the Node runtime
// for the whole route — the GET will then pay the Node cold-start penalty.
// The post-mortem discusses this trade-off explicitly.

export async function PATCH(req: NextRequest, { params }: { params: { id: string } }) {
  const userId = req.headers.get("x-user-id")!;
  const traceId = req.headers.get("x-trace-id") ?? "unknown";
  const orgId = Number(params.id);

  const body = orgPatchSchema.parse(await req.json());

  // Authorization: only owner can rename the org.
  const owners = await sql`SELECT 1 FROM org_members
                           WHERE org_id = ${orgId} AND user_id = ${userId} AND role = 'owner'`;
  if (owners.length === 0) {
    return problem(req, 403, "not_owner", "only the owner can rename an org", traceId);
  }

  const rows = await sql`UPDATE orgs SET name = ${body.name}
                         WHERE id = ${orgId}
                         RETURNING id, name, owner_id, created_at`;
  return NextResponse.json(rows[0], { headers: { "x-trace-id": traceId } });
}

export async function DELETE(req: NextRequest, { params }: { params: { id: string } }) {
  const userId = req.headers.get("x-user-id")!;
  const traceId = req.headers.get("x-trace-id") ?? "unknown";
  const orgId = Number(params.id);

  const owners = await sql`SELECT 1 FROM org_members
                           WHERE org_id = ${orgId} AND user_id = ${userId} AND role = 'owner'`;
  if (owners.length === 0) {
    return problem(req, 403, "not_owner", "only the owner can delete an org", traceId);
  }

  // CASCADE delete on org_members (FK ON DELETE CASCADE) makes this atomic.
  await sql`DELETE FROM orgs WHERE id = ${orgId}`;
  return new NextResponse(null, { status: 204, headers: { "x-trace-id": traceId } });
}
```

### `app/api/orgs/[id]/members/route.ts` — POST + GET members

```typescript
// app/api/orgs/[id]/members/route.ts
import { NextRequest, NextResponse } from "next/server";
import { sql } from "@/lib/db";
import { memberAddSchema } from "@/lib/schemas";
import { problem } from "@/lib/errors";

export const runtime = "nodejs";
export const maxDuration = 30;

export async function POST(req: NextRequest, { params }: { params: { id: string } }) {
  const userId = req.headers.get("x-user-id")!;
  const traceId = req.headers.get("x-trace-id") ?? "unknown";
  const orgId = Number(params.id);

  const body = memberAddSchema.parse(await req.json());

  // Only owner or admin can add members.
  const authz = await sql`SELECT role FROM org_members
                          WHERE org_id = ${orgId} AND user_id = ${userId}`;
  if (authz.length === 0 || !["owner", "admin"].includes(authz[0].role)) {
    return problem(req, 403, "not_admin", "only owner or admin can add members", traceId);
  }

  try {
    const rows = await sql`
      INSERT INTO org_members (org_id, user_id, role, added_at)
      VALUES (${orgId}, ${body.user_id}, ${body.role}, NOW())
      RETURNING org_id, user_id, role, added_at`;
    return NextResponse.json(rows[0], { status: 201, headers: { "x-trace-id": traceId } });
  } catch (err: any) {
    if (err.code === "23505") { // Postgres unique_violation — duplicate member
      return problem(req, 409, "duplicate_member", "user is already a member", traceId);
    }
    throw err;
  }
}

export async function GET(req: NextRequest, { params }: { params: { id: string } }) {
  const userId = req.headers.get("x-user-id")!;
  const traceId = req.headers.get("x-trace-id") ?? "unknown";
  const orgId = Number(params.id);

  // Caller must be a member to see the list.
  const self = await sql`SELECT 1 FROM org_members WHERE org_id = ${orgId} AND user_id = ${userId}`;
  if (self.length === 0) {
    return problem(req, 403, "not_member", "only members can list members", traceId);
  }

  const rows = await sql`
    SELECT user_id, role, added_at FROM org_members
    WHERE org_id = ${orgId} ORDER BY added_at ASC`;
  return NextResponse.json({ members: rows }, { headers: { "x-trace-id": traceId } });
}
```

## Cold-Start Measurements

Captured against a Vercel Pro deployment, Node 18 serverless runtime, 512MB memory, US-East-1 region, after a 5-minute idle window (the function was evicted from Vercel's warm pool). 50 sequential cold invocations of `GET /api/orgs/1` (authenticated, hitting Neon via the HTTP driver):

```text
Metric                       Value (ms)    Notes
─────────────────────────────────────────────────────────────────────────
p50                          290           Cold-start dominated (Firecracker + Node boot + module imports)
p95                          410           Tail includes JWKS fetch + first Neon HTTP round-trip
p99                          530           One outlier at ~1.1s caused by Neon autoscaler adding a compute endpoint
Warm p50 (subsequent)        38            HTTP driver + Postgres query only
Warm p95                     62
Warm p99                     110           Neon query planner cache miss
Edge GET p50 (cold)          6             V8 isolate boot, no Node, no Firecracker
Edge GET p99 (cold)          22
Edge GET p99 (warm)          28            Dominated by Neon HTTP round-trip, not Edge runtime
```

The 530ms p99 cold-start on the Node serverless runtime is the most-cited reason teams abandon Vercel migrations — it feels unacceptable next to the Spring Boot anchor's <10ms steady-state p99. The mitigation that works in production is to push the read path to the Edge runtime (which has a 22ms p99 cold start, 24× faster) and accept the Node cold-start only on the write path (create/delete org, mutate membership), which happens at <1% the rate of reads on a typical org/membership API.

## What This Teaches

The Vercel migration teaches three lessons that the Spring Boot anchor does not surface.

First, **runtime selection is a per-route decision, not a project-wide decision.** The Spring Boot anchor has one runtime: a Tomcat thread pool inside a JVM. The Vercel implementation has two: an Edge V8 isolate for the auth middleware and the read path, and a Node 18 Firecracker microVM for the write path. Treating "the runtime" as a single thing in a serverless world is the most common architectural mistake — it forces every request to pay the worst runtime's cold-start penalty. The right mental model is: each route is a separately-deployed, separately-tunable, separately-priced micro-service that happens to share a repo and a deploy command.

Second, **the database driver is the load-bearing decision in any serverless migration, not the function runtime.** The reason this implementation uses Neon's HTTP driver instead of a pooled Postgres driver is not latency — pooled would be 1–2ms faster per query. It is that a pooled driver holds a TCP connection, and a serverless function cannot reliably close TCP connections before the platform freezes the invocation. Over thousands of invocations this leaks connections on the Postgres side until `max_connections` is hit and every subsequent request fails with `FATAL: sorry, too many clients already`. The HTTP driver has no state to leak. This lesson generalises: any stateful client library (Redis client, gRPC stub with keepalive, AMQP channel) is a serverless hazard, and the migration must either swap it for a stateless equivalent (HTTP-based Redis proxy like Upstash, HTTP-based Postgres like Neon) or front it with a server-side pooler (PgBouncer in front of Postgres, RDS Proxy in front of RDS).

Third, **Vercel's developer experience is so much better than the Spring Boot anchor's that it actively hides operational problems.** `vercel deploy` works. Logs are in the dashboard. Environment variables are managed via UI. There is no EC2 instance to SSH into, no JVM heap to tune, no Nginx worker_processes to size. This is the trap: the migration feels done when it deploys, because the friction that used to signal "you have not finished" (Terraform plans, k8s manifests, Docker builds) is gone. The actual signal that the migration is done — the captured cold-start p99, the captured failure mode, the cost projection at 10× current traffic — must be sought out deliberately, because the platform will not surface it for you. This is the deepest lesson of the Vercel column: serverless platforms compete on developer experience, and developer experience is a euphemism for "we have removed the friction that used to remind you to be careful".
