# 08.01.02. Consensus Protocols Raft and Paxos

## What This Is

Consensus is the problem of getting multiple independent processes to agree on a single value — or, more usefully, on an ordered log of values — despite crashes, packet loss, reordering, and arbitrary delays. It is the load-bearing primitive underneath every replicated state machine: every etcd key update, every Kafka controller failover, every ZooKeeper znode change, every SQL primary/replica promotion, every Kubernetes API-server write is, at the bottom, a consensus round. The two production-grade answers are **Paxos** (Lamport 1989/1998, mathematically proven but notoriously hard to implement correctly) and **Raft** (Ongaro & Ousterhout 2014, designed from the start for understandability and now the algorithm of choice in etcd, Consul, Kafka KRaft, CockroachDB, TiKV, and Cockroach's successor systems).

This note sits in section 08 because consensus is the boundary between "what one process can do" (sections 02–07) and "what a cluster of processes must coordinate to do" (sections 08–10). It depends on the networking layer (03 — RPC primitives, network partitions) and the OS layer (02 — fsync semantics, fsync-on-WAL persistence) and it underpins the messaging layer (07 — Kafka ISR and RabbitMQ quorum queues both run Raft underneath), the distributed-transaction layer (08.02 — every Saga orchestrator needs a durable state machine, which is usually backed by a Raft-replicated log), and the orchestration layer (10 — Kubernetes controller-manager and API-server both run on top of etcd's Raft).

## The Details

### The Consensus Problem: Agreeing on a single data value or state transition across untru...

Consensus, formally, is the problem of getting N processes (of which up to F may crash, where N ≥ 2F+1) to agree on a single value `v` from a proposed set `{v1, v2, ..., vk}`. The agreement must satisfy three properties: **validity** (the chosen value was actually proposed by some process — the algorithm cannot invent a value), **integrity** (no process decides twice), and **termination** (every non-faulty process eventually decides). The FLP impossibility result (Fischer, Lynch, Paterson 1985) proves that no asynchronous algorithm can satisfy all three properties if even one process can fail — termination cannot be guaranteed in the presence of arbitrary message delay. Real systems escape FLP by giving up on full asynchrony: they assume eventual message delivery (with timeouts) and accept that liveness can stall during a partition, prioritizing safety over liveness.

The classic solution is **single-decree Paxos** (Lamport 1998, "The Part-Time Parliament" original 1989). The protocol defines three roles — **proposers** (which propose values), **acceptors** (which vote on proposals and form the quorum), and **learners** (which receive the chosen value but do not vote). A proposer drives two phases. **Phase 1 (Prepare/Promise)**: the proposer picks a unique proposal number `n` — typically a `(round_counter, node_id)` tuple compared lexicographically — and sends `Prepare(n)` to a quorum of acceptors. An acceptor replies `Promise(n, accepted_value)` if `n` is greater than any proposal number it has already promised, and includes in the promise the highest-numbered proposal it has already accepted (if any). If the acceptor has already promised a higher number, it silently ignores the Prepare or replies NACK. **Phase 2 (Accept/Accepted)**: once the proposer has gathered a quorum of promises, it must adopt the value from the highest-numbered accepted proposal among the promises (or its own value if no acceptor reported an accepted value) and sends `Accept(n, v)` to a quorum. An acceptor accepts the proposal — writes `(n, v)` to its durable log, fsyncs, replies `Accepted(n)` — only if it has not promised a higher number since. Once the proposer has received `Accepted` from a quorum, the value is **chosen**, and the proposer notifies the learners.

```text
Single-decree Paxos message flow (5 acceptors, proposer P, learner L):

  Phase 1 — Prepare/Promise (proposer learns what, if anything, is already locked in):
    P ──Prepare(n=5.1)──▶ A1, A2, A3, A4, A5    (sent to a quorum; 3 of 5 suffices)
                          A1: never promised         → Promise(5.1, none)
                          A2: never promised         → Promise(5.1, none)
                          A3: previously promised 4.7, accepted (4.7, "X")
                                                     → Promise(5.1, (4.7,"X"))
    P now knows: a majority has promised 5.1; one of them previously accepted value "X"
    at proposal 4.7. P MUST adopt value "X" — this rule is what gives Paxos its safety.

  Phase 2 — Accept/Accepted (proposer drives the value to chosen):
    P ──Accept(5.1, "X")──▶ A1, A2, A3, A4, A5
                            A1: not promised higher → write (5.1,"X") to WAL, fsync → Accepted(5.1)
                            A2: not promised higher → write (5.1,"X") to WAL, fsync → Accepted(5.1)
                            A3: not promised higher → write (5.1,"X") to WAL, fsync → Accepted(5.1)
    P has Accepted from a majority (A1, A2, A3) → value "X" is CHOSEN.
    P ──Chosen("X")──▶ L   (learner applies "X" to its state machine)

  Key invariant: any two quorums overlap in at least one acceptor, so two different values
  cannot both reach a majority — that overlapping acceptor would have to accept both, which
  the promise-then-accept handshake forbids. This is Paxos's safety proof in one sentence.
```

**Multi-Paxos** is the optimization that turns single-decree Paxos into a usable log-replication protocol. The observation: if the same proposer stays in charge across many consensus instances (one per log entry), Phase 1 becomes redundant — the stable leader already knows that a quorum of acceptors has promised to it, so it can skip Prepare/Promise and go straight to Accept for every new entry. The leader runs Phase 1 once at startup (or after a leader change) to "pre-promise" a quorum, then drives a sequence of Phase 2 rounds, one per log entry, each with a monotonically increasing proposal number `n`. This collapses the per-entry latency from two round-trips to one. The catch: if the leader fails, the new leader must run Phase 1 again to re-establish the promise, and during that window the log stalls. Multi-Paxos is what every "Paxos-based" production system actually runs — Google's Chubby, Apache ZooKeeper (ZAB, a Paxos variant with the leader-election phase folded into the protocol), and Microsoft's Azure Cosmos DB multi-master Paxos. The protocol is correct, but the implementation complexity is ferocious, which is the bridge to the next paragraph.

Why is Paxos so hard to implement correctly? The original Lamport paper is famously opaque (it is written as a parable about a fictional Greek island, with the algorithm buried in pseudocode), and even the "Paxos Made Simple" restatement leaves dozens of implementation decisions unspecified: how to pick proposal numbers (must be monotonic and unique across leaders — usually `(round_counter, node_id)`), how to handle log gaps (a new leader must fill in missing entries before serving new ones), how to do configuration changes (joint-consensus, which Lamport published as a separate paper), how to handle disk corruption (the acceptor's durable log must be write-ahead and fsynced before replying, but a torn write requires a recovery procedure). Google's 2007 paper "Paxos Made Live — An Engineering Perspective" (Chandra, Griesemer, Redstone) documents the gap between Paxos-the-algorithm and Paxos-the-shipped-system: the Chubby team spent two years implementing multi-Paxos, encountered "many subtle and not-so-subtle bugs" in their first implementation, and had to add a "master lease" on top of the basic protocol to handle a partitioned master that didn't realize it was deposed. Diego Ongaro's PhD thesis (2014) catalogues similar bugs in his own reference implementation. The pattern is consistent: every team that ships a Paxos implementation rediscovers the same set of edge cases that the original paper elides. This is precisely the failure mode that Raft was designed to eliminate by being explicit about every state transition.

Raft takes a different decomposition: it elects a leader (which Ongaro proves is equivalent to single-decree Paxos for the leader-election instance), then has the leader drive log replication directly through `AppendEntries` RPCs without a separate Accept phase. Both algorithms are state-machine-replication engines — given the same input log, every replica applies the same state transitions in the same order, so the replicas converge to identical state.

```text
State machine replication (Schneider 1990):

    Client          Leader         Follower A      Follower B
      │  propose      │                │                │
      │──────────────▶│                │                │
      │               │  replicate     │                │
      │               │───────────────▶│                │
      │               │───────────────────────────────▶│
      │               │  ack           │                │
      │               │◀───────────────│                │
      │               │◀───────────────────────────────│
      │               │  (majority acked → commit)     │
      │  ack          │                │                │
      │◀──────────────│                │                │
      │               │  commit (AppendEntries with new commitIndex)
      │               │───────────────▶│                │
      │               │───────────────────────────────▶│
      │               │                │  apply(entry)  │  apply(entry)

    Safety:    every committed entry is on a majority of replicas.
    Liveness:  progress as long as a majority can communicate with the leader.
```

The production failure mode for consensus is split-brain — two leaders claiming to be primary, both accepting writes, and the replicas diverging. This is exactly what the FLP result and the quorum rule are designed to prevent, and it is what every consensus protocol spends its complexity budget on. The other production failure mode is unavailability: a cluster of 5 nodes that loses 3 cannot make progress, even though 2 are still alive. The tradeoff is fundamental — there is no protocol that survives F+1 failures with N=2F+1 nodes, because doing so would risk split-brain. The metric that reveals either failure is `raft_state{state="leader"}` returning either 2 (split-brain) or 0 (no quorum); the recovery procedure is to bring back a majority of nodes or, in the disaster scenario, to use the cluster's force-reconfigure command (e.g., `etcdctl member remove`) and accept that any writes accepted by the deposed partition are lost.

### The Raft Consensus Algorithm

Raft was published by Diego Ongaro and John Ousterhout in 2014 ("In Search of an Understandable Consensus Algorithm," USENIX ATC). The design goal was explicit: produce an algorithm that is as correct as Paxos but that a typical graduate student can re-derive from memory after one careful read. The paper decomposes consensus into three sub-problems — leader election, log replication, and safety — and addresses each one in isolation. This decomposition is the reason Raft has displaced Paxos in nearly every new system built since 2015: etcd, Consul, Kafka KRaft (which replaced ZooKeeper for Kafka metadata in KIP-500, GA in Kafka 3.3+), CockroachDB, TiKV, and RethinkDB all run Raft.

A Raft cluster has an odd number of nodes (typically 3, 5, or 7); the leader is the single node that handles all client writes and drives log replication. Each node is in one of three states: **follower** (passive, accepts AppendEntries and RequestVote RPCs), **candidate** (active, soliciting votes to become leader), or **leader** (active, sending AppendEntries heartbeats every `electionTimeout / 2`). Time is divided into **terms** — monotonically increasing integers, like Lamport timestamps for the leader-election sub-protocol; a term begins when a candidate solicits votes and ends when the next candidate starts a new term. Every RPC carries the sender's `currentTerm`, and any node that sees a higher term immediately reverts to follower — this is the mechanism that prevents a deposed leader from continuing to act.

```text
Raft node state machine:

                    ┌─────────────┐
       start ──────▶│   follower  │◀───── receives AppendEntries from valid leader
                    └──────┬──────┘
                           │ election timeout (random 150-300 ms)
                           ▼
                    ┌─────────────┐
                    │  candidate  │── wins majority of votes ──▶ leader
                    │  term++     │
                    │  vote self  │── sees higher term ──▶ follower
                    │  send RV    │── election timeout, no winner ──▶ term++, retry
                    └─────────────┘

  RequestVote RPC:   { term, candidateId, lastLogIndex, lastLogTerm }
  AppendEntries RPC: { term, leaderId, prevLogIndex, prevLogTerm,
                       entries[], leaderCommit }
```

The election timeout is randomized in a window (default 150–300 ms in etcd, configurable via `--election-timeout`); the randomization is what prevents two candidates from perpetually tying — with high probability, one candidate's timer fires first and it wins before the other even starts. The leader sends empty AppendEntries heartbeats at an interval shorter than the election timeout (default 50–100 ms in etcd, configurable via `--heartbeat-interval`); if a follower does not receive a heartbeat within its election timeout, it transitions to candidate and starts a new term. The whole mechanism is simple enough that the original Raft paper is 18 pages including the proof, compared to Paxos papers that are notoriously opaque ("Paxos Made Simple," "Paxos Made Live," "Paxos Made Moderately Complex," "Paxos Made Practical" — the proliferation of these titles is itself evidence of the understandability problem).

Why did etcd, Consul, and Kafka KRaft all standardize on Raft rather than multi-Paxos? Three convergent engineering reasons. **Understandability-driven correctness**: etcd v0.x originally used a custom protocol and shipped with split-brain bugs that surfaced under network partitions — the 2015 Jepsen analysis by Aphyr found data loss under partition; the team replaced it with Raft in etcd 2.0 specifically because the protocol's invariants could be exhaustively tested against the reference implementation in `go-raft/raft`. Consul inherited the same HashiCorp Raft library. Kafka KRaft (KIP-500, GA in Kafka 3.3+, October 2022) replaced the ZooKeeper dependency with an internal Raft log for controller metadata — the explicit motivation in the KIP is "operational simplicity" (one fewer distributed system to operate) and "scaling ceiling" (ZooKeeper hit a hard limit around 200k partitions; KRaft targets millions). **Library reuse**: the HashiCorp `raft` Go library and etcd's `go.etcd.io/raft` are battle-tested open-source implementations that any Go project can embed; CockroachDB and TiKV both ship their own Go Raft libraries derived from the etcd one. There is no equivalent canonical open-source multi-Paxos library — every multi-Paxos implementation ends up specialized enough that it isn't reusable (Chubby's is internal to Google; ZooKeeper's ZAB is not actually Paxos; Spanner's Paxos is internal to Google). **Operational debuggability**: Raft's term-based leadership is trivially observable — `etcdctl endpoint status -w table` shows the current term, leader ID, and raft index in one line, and the leader/follower distinction is binary. Paxos's multi-proposer / multi-decree state is much harder to expose in a single metrics line, which makes operational triage slower and postmortems harder.

The production failure mode for Raft configuration is a too-short election timeout. If `electionTimeout < heartbeatInterval × RTT × 2`, the followers will frequently miss heartbeats during a transient network blip, start elections, and depose the current leader — producing a flapping cluster where no leader holds office long enough to commit any entries. The fix is to set `electionTimeout` to at least 10× the p99 network RTT, and to ensure that disk fsync latency (which can spike to 100 ms under write pressure on a slow SSD) does not exceed the heartbeat interval. The metric that reveals flapping is `raft_leader_elections_per_minute` — anything above 0 in steady state is a bug.

### Leader Election: Randomized election timeouts, RequestVote RPCs

Leader election in Raft is the process of choosing exactly one leader per term. A follower becomes a candidate when its election timer fires — a randomized duration between `T_min` and `T_max` (default 150–300 ms in etcd). The candidate (1) increments `currentTerm`, (2) votes for itself, (3) resets its election timer, and (4) sends `RequestVote` RPCs in parallel to all other nodes. The `RequestVote` carries the candidate's `term`, `candidateId`, `lastLogIndex`, and `lastLogTerm`. A node grants its vote if (a) the candidate's term is at least as high as the node's, (b) the node has not already voted in this term, and (c) the candidate's log is at least as up-to-date as the node's — where "at least as up-to-date" means the candidate's `lastLogTerm` is higher, or the terms are equal and the candidate's `lastLogIndex` is ≥ the node's. The candidate wins as soon as it receives a majority (N/2 + 1) of votes; it then immediately sends an empty `AppendEntries` heartbeat to establish authority and prevent further elections.

```text
Leader election timeline (5-node cluster, candidate C):

  t=0     C's election timer fires (random between 150-300 ms)
  t=0     C: term 5 → 6, vote self=1, send RequestVote(term=6, lastLogIdx=42, lastLogTerm=4)
  t=1ms   Node A receives RequestVote → grants vote (vote self=2) → reply RequestVoteResponse(term=6, voteGranted=true)
  t=1ms   Node B receives RequestVote → grants vote (vote self=3) → reply RequestVoteResponse(term=6, voteGranted=true)
  t=2ms   C has 3/5 votes (majority) → becomes leader of term 6
  t=2ms   C sends AppendEntries heartbeat (empty entries) to all followers
  t=3ms   A, B, D, E receive heartbeat, reset their election timers, become followers of term 6

  C is now leader. Subsequent AppendEntries (every ~50-100 ms) keep the followers' timers from firing.
```

The up-to-date log check is what guarantees the **Leader Completeness** safety property: a candidate whose log is missing committed entries cannot become leader, because at least one node that holds the committed entries (which is in the winning majority) will refuse to vote for it. This is subtle — it is the only place where the election protocol interacts with the log, and getting it wrong is a common bug in Raft implementations. The original Raft paper's Figure 8 demonstrates the precise failure mode if you skip the up-to-date check: a leader can be elected that does not hold committed entries, those entries get overwritten, and committed data is silently lost.

The randomized election timeout is what breaks ties. If all nodes had the same timeout, they would all become candidates simultaneously, split the vote, and the term would end with no leader — repeating forever. With random timeouts, the probability of two candidates firing within the same round-trip drops exponentially with the spread of the window: a 150 ms window with 5 nodes has a ~30% chance of a tie in any given election, while a 150 ms window with 50 nodes has a near-100% chance. This is why large Raft clusters (CockroachDB deployments of 9+ nodes, for example) widen the window — 500–1000 ms — to keep the tie probability low. The tradeoff is that a wider window means slower leader failover; with a 1000 ms window, failover takes at least 1 second plus the new leader's election round.

The production failure mode is the "no-quorum" outage: a 5-node cluster that loses 3 nodes cannot elect a leader and stops accepting writes. The metric is `raft_state{state="leader"}` returning zero across the cluster. The recovery procedure is to bring back at least 3 nodes (the majority) — either by restarting the crashed nodes, or, in a disaster scenario, by force-removing the dead nodes from the cluster configuration using `etcdctl member remove` and re-forming with the survivors. Force-removal is destructive: if the "dead" nodes are not actually dead (network partition, not crash), they will continue to accept writes locally that will be discarded when they rejoin — a split-brain scenario that the protocol is specifically designed to prevent, but that an operator can cause by being too eager with `member remove`.

### Log Replication: AppendEntries RPCs, commit indices

Once a leader is elected, it owns the log. The Raft log is an ordered sequence of entries, each containing a term number, an index, and a command. The leader receives a client write, appends the entry to its local log (with `term = currentTerm` and `index = lastLogIndex + 1`), and sends an `AppendEntries` RPC to each follower carrying the new entry plus the `prevLogIndex` and `prevLogTerm` of the entry immediately preceding it. Each follower checks that its log contains an entry at `prevLogIndex` with `prevLogTerm`; if so, it appends the new entry, persists it to disk (fsync on the WAL), and replies with success. If the consistency check fails — the follower's log diverges — the follower replies with the index of the first mismatching entry, and the leader decrements `nextIndex` for that follower and retries with an earlier `prevLogIndex`. This backward walk is how Raft brings a follower's log into sync with the leader's after a network partition or a restart.

```text
AppendEntries consistency check (5-node cluster, leader L, follower F is behind):

  Leader log:    [1:1] [1:2] [1:3] [2:4] [3:5] [3:6] [3:7]   ← entry [term:index]
  Follower log:  [1:1] [1:2] [1:3] [2:4] [2:5]               ← diverged at index 5

  L sends AppendEntries(prevLogIdx=6, prevLogTerm=3, entries=[idx 7])
  F checks: my entry at idx 6 has term 2, not 3 → REJECT, reply { conflictIdx=5, conflictTerm=2 }
  L decrements nextIndex[F] to 5, sends AppendEntries(prevLogIdx=4, prevLogTerm=2, entries=[idx 5,6,7])
  F checks: my entry at idx 4 has term 2, matches → truncate my log from idx 5, append [3:5] [3:6] [3:7]
  F persists to WAL (fsync), replies success
  L marks nextIndex[F] = 8, matchIndex[F] = 7
```

An entry is **committed** when the leader has replicated it to a majority of followers. The leader tracks `matchIndex[i]` for each follower — the highest log index known to be replicated on that follower — and computes `commitIndex = max(matchIndex values such that a majority of matchIndex[i] ≥ N)`. The leader includes its current `commitIndex` in every subsequent `AppendEntries`, which lets followers apply entries to their state machines in order. The commit rule is conservative: a leader can only commit entries from its **current** term (the original Raft paper's Figure 8 problem again — a leader cannot commit entries from previous terms directly, only by committing a new entry from its own term, which transitively commits the prior entries).

The `AppendEntries` RPC doubles as a heartbeat — when there are no new entries to send, the leader sends an empty `AppendEntries` with the same `prevLogIndex`, `prevLogTerm`, and `leaderCommit` fields. This is why the heartbeat interval (typically 50–100 ms) must be shorter than the election timeout (typically 150–300 ms): if followers go too long without an `AppendEntries`, they assume the leader is dead and start an election.

The production failure mode for log replication is fsync-stall-induced unavailability. The follower must persist the entry to its WAL before replying success; if the WAL fsync takes 500 ms (because of a slow disk, a RAID controller flush, or a competing IO workload), the leader's RPC times out, the leader retries, the follower eventually replies with success for a duplicated entry, and the system throughput collapses. The metric is `raft_append_entries_latency_p99` rising above the RPC timeout, combined with `raft_log_fsync_latency_p99` rising above the heartbeat interval. The fix is faster disks (NVMe with explicit `fdatasync` barriers, not consumer SSDs that lie about flush), or lowering the WAL durability to "ack without fsync" — which is unsafe and loses committed data on power loss. The proper fix is to provision the WAL on dedicated low-latency storage; etcd's `--data-dir` should be on NVMe, not on the same EBS volume as your application data.

### Safety: Election safety, Leader Append-Only, Log Matching, Leader Completeness

Raft's safety properties are five invariants that, taken together, guarantee that the replicated state machines converge: every node applies the same log entries in the same order, and a committed entry is never lost. The original Raft paper proves each invariant by induction on the protocol's execution, and any correct Raft implementation must preserve all five.

```text
The five Raft safety properties:

  1. Election Safety        At most one leader per term.
                           (Proof: a candidate needs N/2+1 votes; only one candidate
                            can reach majority in a given term, since each node votes once.)

  2. Leader Append-Only     A leader never overwrites or deletes entries in its log.
                           (Proof: the leader only appends; the AppendEntries consistency
                            check never modifies the leader's own log, only followers' logs.)

  3. Log Matching           If two logs contain an entry with the same index and term,
                           then the logs are identical in all entries up through that index.
                           (Proof: by induction on AppendEntries's prevLogIndex/prevLogTerm
                            consistency check — a successful append implies the prior entry matched.)

  4. Leader Completeness    If a log entry is committed in a given term, that entry is
                           present in the logs of the leaders of all higher-numbered terms.
                           (Proof: by induction on terms, using the up-to-date-log voting
                            constraint — a candidate cannot win without holding all committed entries.)

  5. State Machine Safety   If a server has applied a log entry at a given index to its
                           state machine, no other server will ever apply a different log
                           entry for the same index.
                           (Proof: follows from Leader Completeness + Log Matching.)
```

The most subtle of the five is Leader Completeness, and it is the property that the original Raft paper's Figure 8 demonstrates is broken by a naive commit rule. The problem: a leader cannot directly commit entries from previous terms. Suppose leader L1 in term 1 writes entry `e1` at index 5 and replicates it to one follower (not yet committed); L1 crashes; L2 in term 2 writes entry `e2` at index 5 (overwriting `e1`) and replicates it to a different follower; L2 crashes; L3 in term 3 collects votes from a majority that includes followers holding `e1` and `e2` respectively — neither has been committed, but the leader has both. If L3 commits its own new entry `e3` at index 6 and uses that to transitively commit `e2` at index 5, then the follower holding `e1` will be brought into sync by truncating `e1` — but `e1` was on a majority of nodes briefly (during L1's term) and could have been applied by a state machine that read it. The fix is the "commit only entries from the current term" rule: L3 can commit `e3` (its own term), and that transitively commits `e2` (now on a majority), but neither `e1` nor `e2` was previously committed so no state machine has applied either. The protocol is safe.

Log Matching is what makes the AppendEntries consistency check correct: the `prevLogIndex` / `prevLogTerm` pair acts as a cryptographic-style hash chain on the log. If two logs agree at `(index, term)`, they must agree on every prior entry — by induction, each prior append required its own consistency check, so the entire prefix is identical. This is what lets the leader safely overwrite a divergent follower's log: once the leader finds the first point of agreement (by walking `nextIndex` backward), everything after that point can be truncated and re-replicated, because everything before that point is provably identical.

The production failure mode for safety-property violations is silent data loss — the worst kind of bug, because the cluster appears healthy but committed data is gone. The most common cause in real Raft implementations is incorrect `matchIndex` bookkeeping after a leader change (the new leader must re-initialize `nextIndex[i] = lastLogIndex + 1` for all followers, which forces a backward walk on the first AppendEntries; getting this wrong can cause the new leader to skip entries it believes are already replicated). Jepsen has found variations of this bug in etcd, Consul, and CockroachDB at different points in their history. The mitigation is rigorous testing under network partitions and process kills (Jepsen's specialty — see the `elle` checker for transactional consistency) and avoiding "optimizations" that the original Raft paper does not justify.

### Quorum calculations (N/2 + 1) and Split-Brain prevention

The quorum rule in Raft (and Paxos, and every majority-based consensus protocol) is that any decision — leader election, log entry commit, configuration change — must be acknowledged by a strict majority of N/2 + 1 nodes. The arithmetic is what guarantees split-brain prevention: two disjoint majorities cannot exist simultaneously, because their combined size would exceed N. For a 5-node cluster, the majority is 3; two disjoint sets of 3 would have 6 members, but the cluster only has 5 — so any two majorities must share at least one node, and that shared node cannot have voted for both. The same argument holds for any odd N: 3 needs 2, 5 needs 3, 7 needs 4. Even N is wasteful: a 4-node cluster has the same majority size (3) as a 3-node cluster, but tolerates the same number of failures (1) — you might as well run 3 nodes and save the hardware.

```text
Quorum sizes and failure tolerance:

  N (nodes)   Quorum (N/2+1)   Tolerates F failures   Notes
  ─────────   ──────────────   ─────────────────────   ──────────────────────────────
  1           1                0                       No HA — single point of failure.
  2           2                0                       USELESS — same tolerance as N=1,
                                                     but twice the hardware. Never deploy.
  3           2                1                       Minimum HA cluster. Survives 1 node loss.
  4           3                1                       Same tolerance as N=3, more cost. Avoid.
  5           3                2                       Sweet spot for production. Survives 2.
  7           4                3                       Large deployments, multi-AZ.
  9           5                4                       Used by CockroachDB region-spanning clusters.

  Split-brain prevention:
    Cluster N=5, partition splits 2+3.
    Side A (2 nodes): cannot reach majority (3), cannot elect leader, blocks.
    Side B (3 nodes): has majority, elects leader, accepts writes.
    Side A stays unavailable → no split-brain. ✅

    Cluster N=4, partition splits 2+2:
    Side A (2 nodes): cannot reach majority (3), blocks.
    Side B (2 nodes): cannot reach majority (3), blocks.
    Whole cluster unavailable → no split-brain, but worse availability than N=3.
```

The split-brain scenario that the quorum rule prevents is the classic two-datacenter failure: the link between DC1 and DC2 fails, both datacenters are still alive, and without a quorum rule both would elect their own leader and accept conflicting writes. With Raft and N=5 (say 3 nodes in DC1, 2 in DC2), DC1 has 3 nodes and can form a quorum; DC2 has 2 nodes and cannot, so it blocks. When the link heals, DC2's nodes rejoin as followers, the leader brings their logs into sync, and no data was lost. This is the entire reason etcd, Consul, and Kafka KRaft all recommend odd cluster sizes — the math of majority voting requires it.

The production failure mode for quorum misconfiguration is the "deployed 4 nodes for safety" mistake. A team that thinks 4 nodes is safer than 3 has actually made the cluster less available: the same number of nodes must be alive (3) to make progress, and the cluster can no longer tolerate the loss of 2 nodes (where 3 nodes can). The other production failure mode is uneven placement: a 5-node cluster with 3 nodes in DC1 and 2 in DC2 has DC1 as a single point of failure — if DC1 loses power, the cluster cannot reach quorum even though DC2 is healthy. The fix is to spread the cluster across 3 zones or 3 regions (5 nodes across 3 AZs: 2-2-1) so that losing one AZ still leaves a quorum; CockroachDB and Spanner do this by default for their multi-region deployments.

## How This Connects to the Frameworks

Consensus protocols surface in the application stack in three places. **Service discovery and configuration**: Spring Cloud Kubernetes ConfigMap controller, Spring Cloud Consul Config, and Spring Cloud Zookeeper all read from a Raft-replicated key-value store; the application sees eventual consistency but the underlying store is CP. **Distributed coordination**: Spring Integration's `LeaderEventPublisher`, Kafka Connect's worker coordination, and Kafka Streams's consumer-group rebalancing all use consensus (Kafka's `__consumer_offsets` topic plus the KRaft controller for group metadata) to elect a leader among the workers. **Distributed transactions**: a Saga orchestrator (Temporal, Camunda, AWS Step Functions) is itself a state machine that must survive crashes, and the orchestrator's state is replicated via Raft or a similar log-replication protocol — Temporal uses its own Raft-like replicated log for the visibility store; Camunda 8 (Zeebe) is built directly on Raft for partition leadership.

The framework abstraction is the same in every ecosystem: the developer calls a "leader elect" or "lock" API (Spring Cloud Kubernetes `LeaderInitiator`, Express `redlock` against Redis with the Redlock algorithm, Django `django-celery-beat` scheduler with a Redis lock, Laravel `Cache::lock()`), and the framework hides the consensus round-trip. The framework does not hide the failure modes — a misconfigured election timeout will flap regardless of ecosystem, and a network partition will block writes regardless of language. Understanding Raft's mechanics is what lets you read the framework's metrics (`leader_elections_total`, `commit_index_lag`, `apply_latency`) and diagnose "why is my orchestrator slow?" without blaming the framework.

## Hands-On Exercise

```bash
# 1. Start a 3-node etcd cluster locally (each on a different port)
#    (requires etcd binary; install via `brew install etcd` or your package manager)
etcd --name node1 --data-dir /tmp/etcd1 \
  --listen-client-urls http://127.0.0.1:2379 \
  --advertise-client-urls http://127.0.0.1:2379 \
  --listen-peer-urls http://127.0.0.1:2380 \
  --initial-cluster node1=http://127.0.0.1:2380,node2=http://127.0.0.1:2381,node3=http://127.0.0.1:2382 \
  --initial-cluster-state new --initial-cluster-token etcd-cluster-1 &

etcd --name node2 --data-dir /tmp/etcd2 \
  --listen-client-urls http://127.0.0.1:3379 \
  --advertise-client-urls http://127.0.0.1:3379 \
  --listen-peer-urls http://127.0.0.1:2381 \
  --initial-cluster node1=http://127.0.0.1:2380,node2=http://127.0.0.1:2381,node3=http://127.0.0.1:2382 \
  --initial-cluster-state new --initial-cluster-token etcd-cluster-1 &

etcd --name node3 --data-dir /tmp/etcd3 \
  --listen-client-urls http://127.0.0.1:4379 \
  --advertise-client-urls http://127.0.0.1:4379 \
  --listen-peer-urls http://127.0.0.1:2382 \
  --initial-cluster node1=http://127.0.0.1:2380,node2=http://127.0.0.1:2381,node3=http://127.0.0.1:2382 \
  --initial-cluster-state new --initial-cluster-token etcd-cluster-1 &

# 2. Inspect the cluster status and leader
ETCDCTL_API=3 etcdctl --endpoints=127.0.0.1:2379,127.0.0.1:3379,127.0.0.1:4379 endpoint status -w table
# Output columns: Endpoint, ID, Version, DB size, Is leader, Raft term, Raft index

# 3. Write a key — this triggers a Raft commit round to a majority of nodes
ETCDCTL_API=3 etcdctl --endpoints=127.0.0.1:2379 put /foo bar

# 4. Kill the leader and watch a new election happen within ~150-300 ms
LEADER_EP=$(ETCDCTL_API=3 etcdctl --endpoints=127.0.0.1:2379,127.0.0.1:3379,127.0.0.1:4379 endpoint status -w json | jq -r '.[] | select(.Status.header.member_id==.Status.leader) | .Endpoint')
pkill -f "$(echo $LEADER_EP | sed 's/127.0.0.1://')"
sleep 1
ETCDCTL_API=3 etcdctl --endpoints=127.0.0.1:3379,127.0.0.1:4379 endpoint status -w table
#   → new leader elected, term incremented

# 5. Simulate a network partition: drop traffic to 2 of 3 nodes
#    (use iptables on the leader's port — the cluster should become unavailable
#    for writes, because the surviving node cannot reach majority)
sudo iptables -A INPUT -p tcp --dport 2380 -j DROP
sudo iptables -A INPUT -p tcp --dport 2381 -j DROP
ETCDCTL_API=3 etcdctl --endpoints=127.0.0.1:4379 put /foo baz  # times out → split-brain prevented
sudo iptables -F

# 6. Inspect the Raft log on disk — the entries are in the WAL at /tmp/etcd1/member/wal/
ls -la /tmp/etcd1/member/wal/
hexdump -C /tmp/etcd1/member/wal/0000000000000001-0000000000000001.wal | head -20

# 7. Tune the election timeout and observe flapping under simulated network delay
sudo tc qdisc add dev lo root netem delay 200ms 100ms
# Now the heartbeat interval (default 100ms) is exceeded → followers call elections → flapping
sleep 5
ETCDCTL_API=3 etcdctl --endpoints=127.0.0.1:2379 endpoint status -w table  # watch term increment rapidly
sudo tc qdisc del dev lo root
```
