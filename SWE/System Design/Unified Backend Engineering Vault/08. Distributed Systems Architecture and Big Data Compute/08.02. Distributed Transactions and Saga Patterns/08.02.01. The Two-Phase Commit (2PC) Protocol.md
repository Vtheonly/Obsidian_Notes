# 08.02.01. The Two-Phase Commit (2PC) Protocol

## What This Is

The Two-Phase Commit protocol is the textbook answer to the question "how do I atomically update data across multiple databases or resource managers?" A single database transaction is atomic because the database can write a single WAL record that says "commit this transaction or roll it back, all-or-nothing." When the data spans two databases — say, a debit on `accounts_db` and a credit on `ledger_db` — there is no single WAL; the two databases are independent processes that can fail independently, and a crash of one in the middle of a coordinated commit leaves the system in an inconsistent state. 2PC solves this by introducing a **coordinator** process that drives the two databases (the **cohorts** or **participants**) through an explicit agreement protocol: Phase 1 asks each cohort "can you commit?", and Phase 2 — only if every cohort voted yes — tells them all to commit.

The protocol was standardized in the late 1980s as X/Open XA (the protocol used by Java's `javax.transaction.UserTransaction` and the JTA API, by Spring's `JtaTransactionManager`, by PostgreSQL's `PREPARE TRANSACTION` syntax, and by Microsoft DTC). It is correct in the sense that it guarantees atomicity — either all cohorts commit or none do — but it is also **blocking**: if the coordinator crashes at the wrong moment, the cohorts are stuck holding locks on the prepared data indefinitely, unable to commit or roll back without the coordinator's verdict. This is why 2PC is rare in modern microservices: the coupling is too tight, the lock durations are too long, and the failure mode (a stuck prepared transaction) is too painful. The Saga pattern ([[08.02.02. The Saga Architectural Pattern]]) was invented as the engineering answer to 2PC's blocking problem.

## The Details

### The Coordinator and Cohort Participants

A 2PC deployment has two roles. The **coordinator** (sometimes called the transaction manager) is the process that drives the protocol; in JTA terms, this is the `TransactionManager` bean, instantiated by Spring's `JtaTransactionManager` or by Narayana standalone. The **cohorts** (also called participants or resource managers) are the databases, message brokers, or other resource managers that actually hold the data being modified — Postgres, MySQL, Oracle, Kafka (with transactional producer), IBM MQ, etc. Each cohort must implement the XA interface: `xa_start`, `xa_end`, `xa_prepare`, `xa_commit`, `xa_rollback`. The coordinator communicates with each cohort over a control channel (separate from the data channel that the application uses to issue SQL), and the cohort writes its prepare/commit decisions to its own local WAL so it can recover them after a crash.

```text
2PC topology — coordinator drives N cohorts through two phases:

              ┌──────────────────┐
              │   Coordinator    │  (TransactionManager)
              │  (e.g. Narayana, │      ┌─────────────────────────────────┐
              │   Atomikos,      │      │  Phase 1: PREPARE                │
              │   Spring JTA)    │─────▶│  → ask each cohort "can you commit?"
              │                  │      │  → cohort writes prepare record to WAL
              │                  │      │  → cohort votes YES or NO         │
              │                  │      └─────────────────────────────────┘
              └──┬─────┬─────┬───┘
                 │     │     │      control channel (XA protocol)
              ┌──▼─┐ ┌─▼──┐ ┌▼───┐
              │ C1 │ │ C2 │ │ C3 │   Cohorts (ResourceManagers)
              │PG  │ │MQ  │ │Kafk│   ┌─────────────────────────────────┐
              │    │ │    │ │a   │   │  Phase 2: COMMIT (if all YES)   │
              │acct│ │emai│ │tx  │   │  or ABORT (if any NO)            │
              │db  │ │l_q │ │log │   │  → cohort applies verdict         │
              └────┘ └────┘ └────┘   │  → cohort releases locks           │
                                      └─────────────────────────────────┘

  Locks held: from PREPARE received until COMMIT/ABORT applied.
  During this window, the cohort's row locks block all other transactions on the locked rows.
```

The coordinator itself must be durably stateful: it writes a `prepare` record to its own log when it starts Phase 2, a `committing` record when it decides to commit, and a `done` record when all cohorts have acknowledged. This log is what lets the coordinator recover after a crash — without it, on restart the coordinator would not know which cohorts it had already told to prepare, and the cohorts would be stuck in their prepared state forever. In a JTA deployment the coordinator's log is usually a file on local disk (Narayana's `ObjectStore`) or a database table; in a distributed coordinator like Google's Percolator or FoundationDB, the coordinator's state is itself replicated via Paxos/Raft.

The cohort must also be durably stateful: on receiving `PREPARE`, it writes a prepare record to its local WAL (in Postgres this is the `pg_prepared_xacts` table; the WAL entry is `XLOG_XACT_PREPARE`), flushes the WAL with `fsync`, and only then votes YES. The fsync is what guarantees that the cohort can recover its YES vote after a crash — if the cohort crashes before fsync, on restart it has no record of the prepare and must vote NO (effectively aborting). The fsync is also what makes 2PC slow: every prepare round costs at least one WAL flush per cohort, plus one more on commit. A cross-region 2PC transaction touching 3 cohorts in 3 regions can easily spend 600 ms in fsync alone, before any of the application logic runs.

The XA wire protocol uses a global transaction identifier (XID) — a 128-byte structure (`formatID` + `gtrid` + `bqual` + `transactionID`) that uniquely identifies the distributed transaction across all cohorts. The XID is what lets a cohort correlate a `PREPARE` from the coordinator with the local work it did on behalf of the application's branch of that transaction. The XID is also what the operator uses for manual recovery: `ROLLBACK PREPARED '<xid_string>'` in Postgres, `XA RECOVER` then `XA ROLLBACK '<xid>'` in MySQL. The wire protocol itself is XA-spec (X/Open CAE Specification, 1992), but each database driver implements it differently — Postgres `org.postgresql.xa.PGXADataSource`, MySQL `MysqlXADataSource`, Oracle `OracleXADataSource` — and the JTA layer (`javax.transaction.xa.XAResource`) abstracts over all of them. The abstraction is leaky: known correctness bugs in MySQL's XA implementation (MySQL bug #71313 — `XA PREPARE` after a DDL statement can leave the resource manager in an inconsistent state on crash recovery) make MySQL XA unsafe for production; Postgres's implementation is correct but suffers from the same blocking failure mode as the protocol itself.

The production failure mode here is resource exhaustion from stuck prepared transactions. If the coordinator crashes between Phase 1 and Phase 2 and never recovers, every cohort that voted YES holds its locks forever (or until a DBA manually runs `ROLLBACK PREPARED 'txid'`). On Postgres this surfaces as `pg_prepared_xacts` rows that never disappear, `pg_locks` rows with mode `ShareLock` on the affected tables, and a steadily rising count of `idle in transaction` connections. The fix is the coordinator's recovery log: when the coordinator restarts, it reads its log, finds the in-flight transactions, and either re-issues COMMIT (if its log says "committing") or ABORT (if its log says only "prepare" with no commit decision). Without that log — for example, if the coordinator was a stateless pod that crashed and was replaced — the cohorts are stuck and the DBA has to clean up by hand.

### Phase 1 (Prepare): Coordinator sends `PREPARE`; cohorts write to local undo/redo logs a...

Phase 1, the **prepare** or **voting** phase, is where the coordinator asks each cohort "can you commit this transaction?" The cohort has already been executing work on behalf of the application — SQL `INSERT`s, `UPDATE`s, message publishes — under a branch of the global XA transaction. When the coordinator sends `PREPARE`, each cohort must (1) write a prepare record to its WAL containing all the undo and redo information needed to either commit or roll back the transaction, (2) `fsync` the WAL to durable storage, (3) take a vote: YES if it can guarantee it will be able to commit on demand, NO if it cannot (e.g., a constraint violation, a deadlock, a timeout), and (4) reply to the coordinator with its vote. While the cohort is in the "prepared" state, it holds all the row locks it took during the transaction — no other transaction can modify those rows until the cohort receives a final COMMIT or ABORT.

```text
Phase 1 timeline (3 cohorts, 1 coordinator):

  t=0      Coordinator sends PREPARE to C1, C2, C3 (parallel)
  t=0      C1: write XLOG_XACT_PREPARE to WAL → fsync (5 ms local NVMe, 50 ms EBS gp3)
  t=0      C2: same, 5 ms fsync
  t=0      C3: same, 5 ms fsync
  t=5ms    C1 replies YES (vote reached coordinator)
  t=5ms    C2 replies YES
  t=5ms    C3 replies YES
  t=5ms    Coordinator has all 3 YES votes → write "committing" record to its own log → fsync
  t=10ms   Coordinator advances to Phase 2

  Failure scenarios during Phase 1:
  - C3 crashes before fsync:     C3 loses its prepare record. On restart, it has no
                                 prepared txn in pg_prepared_xacts → effectively votes NO.
                                 Coordinator receives 2 YES + 1 timeout → global ABORT.
  - C3 votes NO (e.g. deadlock): Coordinator immediately broadcasts ABORT (Phase 2 abort path).
                                 Cohorts that voted YES roll back, release locks.
  - Coordinator crashes after   Cohorts are in prepared state holding locks. They cannot
   receiving YES but before      commit or abort — they wait for the coordinator to recover
   writing "committing":         and tell them. This is THE blocking failure mode of 2PC.
```

The cohort's vote is a promise: once it has voted YES and fsynced its prepare record, it **must** be able to commit on demand, no matter what — even if a disk fails, the cohort must be able to recover the prepared state from its WAL and apply the eventual COMMIT. This is why the prepare record contains the full redo information, not just the changes: the cohort must be able to apply the commit even if the in-memory transaction state has been lost. Postgres achieves this by writing the full transaction changes to the WAL at prepare time, marking the transaction as `prepared` in `pg_prepared_xacts`, and keeping all the locks held. On `COMMIT PREPARED`, Postgres simply marks the transaction as committed in the WAL and releases the locks — the actual data changes were already applied at prepare time.

The decision rule at the coordinator is strict: if even one cohort votes NO, the global decision is ABORT. This is the atomicity guarantee — no partial commits. The tradeoff is latency: the coordinator must wait for the slowest cohort to vote (or timeout) before deciding. A single slow cohort — for example, one running on a heavily loaded database with a 5-second fsync stall — blocks the entire transaction for 5 seconds, holding locks on all the other cohorts' prepared rows for that duration. This is the "tail latency amplification" problem that makes 2PC impractical for user-facing microservices: a 99th-percentile 5-second stall on one service becomes a 5-second stall on every service in the transaction.

The production failure mode during Phase 1 is the "lock storm" caused by a slow or dead cohort. The coordinator's prepare-timeout (`com.arjuna.ats.arjuna.coordinator.defaultTimeout` in Narayana, default 60 seconds) is the upper bound on how long the cohorts will hold their prepared locks waiting for the straggler. If a cohort is unresponsive, the coordinator will eventually time out and broadcast ABORT, but the 60-second window during which all the other cohorts held locks is a 60-second window of degraded throughput on those databases. The metric that reveals this is `xa_prepare_latency_p99` rising above the SLA, combined with `pg_locks_count` rising on the prepared tables. The fix is to set the prepare-timeout low enough to fail fast (5–10 seconds for user-facing transactions), accept the abort, and retry — but this only works if the application is idempotent, which most 2PC-using applications are not.

### Phase 2 (Commit/Abort): Coordinator evaluates votes and issues global `COMMIT` or `ROLL...

Phase 2, the **completion** phase, is where the coordinator tells the cohorts what to do. If every cohort voted YES in Phase 1, the coordinator writes a `committing` record to its own log (with fsync), then broadcasts `COMMIT` to every cohort. If any cohort voted NO, or if any cohort timed out, the coordinator broadcasts `ABORT` (which the cohorts interpret as "roll back the prepared transaction"). Each cohort applies the verdict — `COMMIT PREPARED` or `ROLLBACK PREPARED` in Postgres syntax — writes the corresponding WAL record, fsyncs, releases the locks, and replies with `ACK`. Once the coordinator has received ACKs from all cohorts (or from a quorum, depending on the variant), it writes a `done` record to its log and the transaction is complete.

```text
Phase 2 timeline — COMMIT path (all cohorts voted YES in Phase 1):

  t=0      Coordinator writes "committing" record → fsync
  t=5ms    Coordinator broadcasts COMMIT to C1, C2, C3 (parallel)
  t=5ms    C1: write XLOG_XACT_COMMIT_PREPARED → fsync → release locks → ACK
  t=10ms   C2: same
  t=10ms   C3: same
  t=15ms   Coordinator has all ACKs → write "done" record → fsync
  t=20ms   Transaction complete, locks released on all cohorts

  Phase 2 — ABORT path (at least one cohort voted NO or timed out):

  t=0      Coordinator decides ABORT (no need to write "committing" record)
  t=0      Coordinator broadcasts ROLLBACK to all cohorts (including those that voted YES)
  t=0      Cohorts that voted YES: ROLLBACK PREPARED → fsync → release locks → ACK
  t=0      Cohorts that voted NO or didn't prepare: already rolled back, ACK immediately
  t=10ms   Coordinator writes "done" record → fsync
  t=15ms   Transaction rolled back, no partial commits
```

The Phase 2 commit is the irrevocable point. Once the coordinator has written its `committing` record and fsynced, the transaction is committed from the coordinator's perspective — even if the coordinator crashes before broadcasting COMMIT, on restart it will read its log, see the `committing` record, and re-broadcast COMMIT to any cohorts that have not yet ACKed. This is the source of the "presumed abort" optimization (Mohan 1986): an aborting cohort can simply roll back and forget, because if the coordinator crashes and restarts, it can ask "did you prepare?" and if no cohort remembers preparing, the coordinator can safely decide ABORT. But a committing cohort cannot forget until it has ACKed — the coordinator needs the ACK to know it can move to the `done` state. This asymmetry is why 2PC's failure handling is biased toward abort: in doubt, abort.

The COMMIT broadcast is parallel — the coordinator sends COMMIT to all cohorts simultaneously — but the coordinator must wait for all ACKs before transitioning to `done`. If a cohort is slow to ACK (long fsync, GC pause, network blip), the coordinator's `done` record is delayed, but the cohorts that have already ACKed have already released their locks — so the slow cohort does not extend the lock-holding window for the others. This is a meaningful improvement over Phase 1, where the slowest cohort determined the lock-holding duration for all. In Phase 2, each cohort's lock-holding window ends as soon as that cohort ACKs.

The production failure mode in Phase 2 is the "phantom commit." If the coordinator crashes after writing `committing` but before broadcasting COMMIT, the cohorts are stuck in the prepared state holding locks — same as the Phase 1 blocking failure. But this time the eventual outcome is COMMIT, not ABORT: when the coordinator recovers, it will re-broadcast COMMIT, and the cohorts will commit. The window between "coordinator decided to commit" and "coordinator recovered and re-broadcast" is a window during which the application believes the transaction is committed (because the coordinator acknowledged the commit) but the cohorts have not yet applied it. If a read query hits a cohort during this window, it sees the pre-commit state — a read-after-commit anomaly. The fix is for the coordinator to wait for at least a quorum of ACKs before acknowledging commit to the application, which is what most production coordinators do — but this adds another round-trip to the latency budget.

### Failure modes: Coordinator crash during commit phase leaves cohort resources locked ind...

The defining failure mode of 2PC is the **blocking** behavior when the coordinator crashes at the wrong moment. Consider: the coordinator has sent PREPARE to all cohorts, all cohorts have voted YES and fsynced their prepare records and are holding locks. The coordinator is about to write its `committing` record and broadcast COMMIT — but it crashes. The cohorts are now in limbo: they have promised to commit, they hold locks on the affected rows, and they have no way to know whether the coordinator decided COMMIT or ABORT before crashing. They cannot unilaterally decide — if they all guessed ABORT but the coordinator actually decided COMMIT, the system would lose atomicity; if they all guessed COMMIT but the coordinator decided ABORT, same problem. So they wait. And wait. And hold their locks. Until either the coordinator recovers and tells them the verdict, or a DBA manually runs `ROLLBACK PREPARED` and accepts the risk of breaking atomicity.

```text
Blocking failure mode — coordinator crashes after Phase 1, before Phase 2 verdict:

  t=0     Coordinator sends PREPARE to C1, C2, C3
  t=5ms   C1, C2, C3 vote YES, fsync prepare records, hold row locks
  t=6ms   Coordinator receives all YES votes
  t=7ms   Coordinator CRASHES before writing "committing" record
          ↓
  t=7ms   Cohorts C1, C2, C3 are stuck in "prepared" state
          - Cannot commit (don't know if coordinator decided COMMIT)
          - Cannot abort (don't know if coordinator decided ABORT)
          - Hold row locks → no other transaction can modify those rows
          ↓
  t=∞     Cohorts wait forever, OR until:
          - Coordinator recovers and reads its (empty) log → decides ABORT → broadcasts ABORT
          - DBA manually runs ROLLBACK PREPARED 'txid' (breaking atomicity if coordinator
            had actually decided to commit)
          - Operator declares the coordinator dead and reconfigures the system,
            abandoning the prepared transactions

  Real-world observable on Postgres:
    SELECT * FROM pg_prepared_xacts;            -- shows stuck prepared transactions
    SELECT * FROM pg_locks WHERE locktype='transactionid';
                                                  -- shows the held locks
    -- The application is blocked on row updates; throughput collapses.
```

The 3PC (Three-Phase Commit) protocol was invented by Skeen 1981 to solve this blocking problem. 3PC adds an extra phase — `CanCommit` (Phase 1, like 2PC prepare), `PreCommit` (Phase 2, coordinator tells cohorts "I'm about to commit, get ready"), `DoCommit` (Phase 3, cohorts actually commit). The key property: after Phase 2, every cohort knows the coordinator decided to commit, so if the coordinator crashes, the cohorts can hold an election, learn that the decision was "commit," and proceed to commit themselves. 3PC is **non-blocking** under the assumption of synchronous failure detection (i.e., the network does not partition — a node is either up or down, not "unreachable because of a partition"). Under a network partition, 3PC can still block or even produce split-brain: two partitions can both think the coordinator is dead and both proceed with their own commit decisions, breaking atomicity. This is the FLP impossibility resurfacing — there is no fully asynchronous non-blocking commit protocol.

Because of this fundamental limitation, 3PC is rarely deployed in practice. The Paxos Commit protocol (Gray & Lamport 2006, "Consensus on Transaction Commit") is the modern alternative: it uses Paxos to replicate the coordinator's decision, so that even if the coordinator crashes, the cohorts can recover the decision from the Paxos cluster. This is what Spanner, CockroachDB, and FoundationDB do for their distributed transactions — they layer 2PC's prepare/commit semantics on top of a Paxos-replicated log per cohort, getting the atomicity of 2PC with the availability of Paxos. The cost is one Paxos round per cohort per transaction, which adds 10–30 ms of latency per cohort and makes the system slower than a single-database transaction but non-blocking under any failure mode.

Why is 2PC rarely used in microservices? Four reasons, in rough order of importance. **First**, it is synchronous and slow: every cohort's prepare must round-trip and fsync before the transaction can commit, so a 3-cohort transaction takes at least 3 × (RTT + fsync) ≈ 3 × 5 ms = 15 ms minimum on fast NVMe, easily 100–500 ms in cross-region or cloud deployments. **Second**, it is tightly coupled: every service in the transaction must hold a database lock for the full duration of the protocol, so a slow service stalls every other service in the transaction. **Third**, the failure mode is catastrophic: a stuck prepared transaction holds locks that can cascade into a full database outage, and the recovery procedure requires DBA intervention. **Fourth**, it requires homogeneous infrastructure: every participant must support XA, which rules out most NoSQL databases, most SaaS APIs (Stripe, Twilio, SendGrid), and most message brokers except Kafka (with transactional producer) and IBM MQ. The Saga pattern trades atomicity for availability — each service commits locally and publishes an event, and if a later step fails, a compensating transaction undoes the earlier ones. This is eventually consistent rather than ACID, but it is what microservices actually run.

The production failure mode for 2PC is the "stuck prepared transaction" incident. A canonical real-world example: a Spring Boot service running Narayana JTA with three XA cohorts (Postgres for accounts, Oracle for billing, IBM MQ for notification). The service is deployed as a stateless pod behind a Kubernetes deployment. The pod crashes (OOMKill) mid-transaction — Narayana's ObjectStore was on an `emptyDir` volume, which is destroyed when the pod dies. On restart, a new pod comes up with an empty ObjectStore, so Narayana has no record of the in-flight transaction. The cohorts are still holding the prepared locks: `pg_prepared_xacts` on Postgres, `DBA_2PC_PENDING` on Oracle, the XA transaction on IBM MQ. Application throughput on the locked rows drops to zero. The DBA must manually `ROLLBACK PREPARED` on each cohort (or `XA ROLLBACK` on MQ), accepting that any in-flight business state is lost. The postmortem fixes are: (a) put Narayana's ObjectStore on a persistent volume (`PersistentVolumeClaim`), not `emptyDir`; (b) configure a sane `defaultTimeout` (5–10 seconds for user-facing transactions, not 60); (c) alert on `pg_prepared_xacts_count > 0` for more than 30 seconds; (d) migrate the next quarter to a Saga orchestrator (Temporal) so the protocol-level blocking cannot recur. The metric that reveals the incident is `pg_prepared_xacts_count > 0` for more than a few seconds, combined with a rising count of `pg_locks` for the affected tables and a falling transaction throughput. The recovery procedure is: (1) identify the stuck transaction ID from `pg_prepared_xacts`, (2) check whether the coordinator is alive and recovering, (3) if the coordinator is permanently dead, manually `ROLLBACK PREPARED 'txid'` on each cohort and accept that any data the transaction was supposed to commit is now lost, (4) file a postmortem on why the coordinator was not durably stateful. This is unpleasant enough that most teams move off 2PC after their first incident.

## How This Connects to the Frameworks

2PC surfaces in the framework layer as the JTA (Java Transaction API) in Spring — `JtaTransactionManager`, `@Transactional` with a JTA-aware `PlatformTransactionManager`, and `UserTransaction` for explicit programmatic control. Spring's `JtaTransactionManager` delegates to the underlying JTA provider (Narayana, Atomikos, Bitronix) which implements the coordinator logic. The cohort side is implemented by the JDBC driver's `XADataSource` (Postgres `org.postgresql.xa.PGXADataSource`, MySQL `MysqlXADataSource`), the JMS provider's `XAConnectionFactory` (ActiveMQ, IBM MQ), or the Kafka producer with `transactional.id` set. The framework hides the XA wire protocol but does not hide the failure modes — a stuck prepared transaction is just as visible in Spring as in raw XA, and the recovery log location is just as important to back up.

In the other ecosystems, 2PC is rare. Express and Django have no native JTA equivalent; Node.js applications that need distributed transactions typically use a Saga orchestrator (Temporal, Restate) rather than XA. PHP has `pdo_xa` but it is widely considered unsafe — MySQL's XA implementation has known correctness bugs (see the MySQL bug tracker for `XA PREPARE` + crash recovery issues). Laravel has no native XA support. This is not a deficiency in those ecosystems — it reflects the industry-wide shift away from 2PC toward Sagas. The Spring/JTA path is the right place to learn 2PC deeply, because it is the ecosystem that still uses it in production (typically in legacy banking, insurance, and ERP systems where the cost of refactoring to Sagas exceeds the cost of operating 2PC).

## Hands-On Exercise

```bash
# 1. On Postgres, observe the XA prepare/commit protocol directly.
#    Enable prepared transactions (default is off in some distributions).
psql -c "SHOW max_prepared_transactions;"
psql -c "ALTER SYSTEM SET max_prepared_transactions = 10;"
pg_ctl restart  # or systemctl restart postgresql

# 2. Open two psql sessions. In session 1, run a 2PC prepare:
psql -c "BEGIN;"
psql -c "INSERT INTO accounts (id, balance) VALUES (42, 100);"
psql -c "PREPARE TRANSACTION 'tx_42';"
# Session 1 now has a prepared transaction holding locks.
# In another shell, verify the prepared transaction exists:
psql -c "SELECT * FROM pg_prepared_xacts;"
#   gid  | gid | prepared | owner  | database
#  tx_42 | ... | 2023-... | ...    | mydb

# 3. Try to update the locked row from session 2 — it should block:
psql -c "UPDATE accounts SET balance = 200 WHERE id = 42;" &
# Block observed. The lock is held by the prepared transaction.

# 4. Simulate the "coordinator crashed" failure mode:
#    DO NOT commit or roll back the prepared transaction.
#    Instead, kill the psql session that issued PREPARE:
kill -9 <psql_session_1_pid>
# Inspect: the prepared transaction is STILL there, locks STILL held.
psql -c "SELECT * FROM pg_prepared_xacts;"
psql -c "SELECT pid, mode, granted FROM pg_locks WHERE relation = 'accounts'::regclass;"

# 5. Manual recovery — DBA intervention:
psql -c "ROLLBACK PREPARED 'tx_42';"
# Locks released. Session 2's UPDATE now proceeds.
# Note: in production, you must be sure the coordinator is truly dead and
# would not have decided to COMMIT. Otherwise this breaks atomicity.

# 6. Run a Spring Boot JTA demo to see the protocol from the application side.
#    Spring Boot + Narayana starter:
#    spring-boot-starter-jta-narayana
#    Set: spring.jta.enabled=true, spring.jta.log-dir=/var/log/narayana
#    Then annotate a service method with @Transactional and have it write to
#    two XA-aware DataSources. Watch the Narayana ObjectStore for the prepare
#    and commit records:
ls /var/log/narayana/ShadowNoFileLockStore/defaultStore/
#    You will see files like xid_<hash> for each in-flight transaction.

# 7. Reproduce the lock-storm: deliberately crash the JVM running the Spring
#    Boot app mid-transaction (kill -9 the JVM, no graceful shutdown).
#    The cohorts will hold prepared locks. Restart the JVM — Narayana will
#    read its ObjectStore on startup and recover (re-broadcast COMMIT or ABORT).
#    If the ObjectStore is empty (you deleted it), Narayana cannot recover,
#    and you are in the manual-recovery scenario above.
```
