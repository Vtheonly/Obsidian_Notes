# 08.02.02. The Saga Architectural Pattern

## What This Is

A Saga is a sequence of local transactions, each executed by a single service on its own database, where each step has a paired **compensating transaction** that semantically undoes its effect if a later step fails. The pattern was originally articulated by Hector Garcia-Molina and Kenneth Salem in their 1987 paper "Sagas" as a way to model long-running transactions in database systems — a "long-running" transaction being one that holds locks long enough that blocking other transactions becomes unacceptable. The microservices community rediscovered Sagas in the 2010s as the alternative to [[08.02.01. The Two-Phase Commit (2PC) Protocol]]: where 2PC holds all cohorts' locks for the duration of a synchronous protocol, a Saga releases each service's locks as soon as its local transaction commits, accepting that a later failure requires calling explicit compensation logic rather than rolling back a 2PC prepare.

The trade-off is fundamental. Sagas sacrifice ACID isolation (intermediate states are visible to other services during the saga) in exchange for availability and decoupling. Each step is a short local transaction — fast, no cross-service locks — but the global outcome is only eventually consistent: either the saga completes all steps (success) or the orchestrator drives compensation in reverse order for every step that already committed (semantic rollback). This note covers the decomposition principle, the compensation semantics, the two implementation topologies (choreography and orchestration), and the production-grade code patterns in Temporal and Camunda 8 that most teams adopt once their sagas grow beyond three steps.

## The Details

### Decomposing distributed transactions into a sequence of local ACID transactions across service bo...

The first step in designing a saga is decomposing the global transaction into a sequence of local transactions, each owned by exactly one service and each committable independently. The decomposition is driven by the business workflow — "book a vacation" becomes "reserve car, reserve hotel, reserve flight, charge credit card, emit ticket," and each of those steps is a single-service operation. The constraint is that each step must be **locally atomic** — the service's own database transaction commits or rolls back as a unit — but the steps themselves are only loosely ordered: step N+1 starts after step N's local transaction commits and publishes its event (in choreography) or after the orchestrator sends step N+1's command (in orchestration).

```text
Decomposition example — Book Vacation Saga (4 services, 4 steps):

  Step  Service         Forward action         Compensating action
  ────  ──────────────  ─────────────────────  ──────────────────────────────
   1    Car Service     reserve_car(user_id)   cancel_car_reservation(res_id)
   2    Hotel Service   reserve_hotel(...)     cancel_hotel_reservation(...)
   3    Flight Service  charge_card_and_book   refund_card_charge(txn_id)
   4    Email Service   send_ticket_email      (none — compensation is a no-op
                                               or a "your booking failed" email)

  Happy path:        1 → 2 → 3 → 4 → done
  Failure at step 3: 1 → 2 → 3 (FAIL) → 2-compensate → 1-compensate → 4 is skipped
  Failure at step 4: 1 → 2 → 3 → 4 (FAIL) → 3-compensate → 2-compensate → 1-compensate

  Each step's forward action and compensation are local ACID transactions
  on the service's own database. There is no global 2PC.
```

The compensation order is the reverse of the forward order — last-in-first-out, like a stack unwind. This is necessary because of dependencies: if step 3 (charge card) consumed the reservation ID created by step 1 (reserve car), then compensating step 1 before step 3 would orphan the card charge. The orchestrator must keep a record of which steps have completed and in what order, so that on failure it can walk the completed-steps list in reverse and invoke each step's compensating action. This record is the **saga state**, and its durability is the orchestrator's primary correctness requirement — if the orchestrator crashes mid-compensation, on restart it must resume from the exact step it was on, not start over and double-compensate.

The decomposition often surfaces hidden coupling. The "charge credit card" step looks independent, but it depends on the total amount computed from the car + hotel + flight prices — so the orchestrator must aggregate those values and pass them as parameters to step 3. The "send ticket email" step depends on a confirmation number generated by step 3 — so the orchestrator must propagate that confirmation number forward. The pattern that emerges is that the orchestrator owns the **saga context**: a JSON document that starts empty, accumulates each step's outputs (reservation IDs, confirmation numbers, prices), and supplies each subsequent step's inputs. The context is the saga's "shared memory" — there is no global database, but there is a global JSON document that flows through the steps.

The production failure mode for bad decomposition is the "stuck saga": a step whose forward action succeeded but whose compensation is impossible — for example, a step that calls a third-party API (Stripe charge) with no idempotency key, so a retry double-charges the customer. The fix is to design every step as idempotent (use a deterministic ID like `saga_id + step_id` as the Stripe idempotency key) and to design every compensation as best-effort (a refund may fail if the card is closed; the saga must record the failed compensation and surface it for human intervention rather than block forever). The metric that reveals stuck sagas is `saga_age_seconds_p99` rising — a healthy saga completes in seconds; a stuck saga sits in `RUNNING` state for hours.

### Compensating Transactions: Explicit forward or backward undo actions compensating for failed down...

A compensating transaction is not a database rollback. It is a **semantic undo** — a business-level operation that returns the system to a state that is, from the business's perspective, equivalent to "this never happened," even if it is not bit-for-bit identical to the pre-saga state. The canonical example: you cannot un-charge a credit card. Once the charge has been captured by the payment processor, the only way to undo it is to issue a refund — which creates a new financial transaction (a credit to the customer's card statement) rather than erasing the original charge. The refund is the compensating transaction; it does not roll back the charge, it semantically cancels it.

```text
Compensation is not rollback:

  Original (local ACID):
    BEGIN;
    UPDATE accounts SET balance = balance - 100 WHERE id = 'alice';
    UPDATE accounts SET balance = balance + 100 WHERE id = 'bob';
    COMMIT;
  -- Failure: ROLLBACK; both updates vanish. No record of the attempt.

  Saga step (local ACID + compensating action):
    -- Step 3: charge card
    BEGIN;
    INSERT INTO charges (id, user, amount, status) VALUES ('ch_123', 'alice', 100, 'captured');
    UPDATE users SET lifetime_value = lifetime_value + 100 WHERE id = 'alice';
    COMMIT;
    -- Forward action done. Card is charged.

  -- If a later step fails, the compensating action:
    BEGIN;
    INSERT INTO refunds (id, charge_id, amount) VALUES ('re_456', 'ch_123', 100);
    UPDATE charges SET status = 'refunded' WHERE id = 'ch_123';
    UPDATE users SET lifetime_value = lifetime_value - 100 WHERE id = 'alice';
    COMMIT;
  -- The refund is a NEW transaction. The original charge record is preserved
  -- (with status='refunded'), not erased. This is the audit trail.

  Business semantics: Alice's net balance change is 0, but the system
  retains a record that a charge was attempted and refunded.
```

Compensations come in three flavors. **Backward compensation** (the common case) undoes the forward action — cancel a reservation, refund a charge, delete a created record. **Forward compensation** (also called "recovery" or "reconciliation") accepts that the forward action cannot be undone and instead pushes the saga forward to a different valid state — for example, if a shipment has already been dispatched, the compensation is "return-to-sender" or "issue a pickup request," not "undo the shipment." **No-op compensation** is for steps whose effects are immutable and acceptable to leave in place — sending a "your order is confirmed" email is followed by a fulfillment failure; the email cannot be un-sent, and the compensation is to send a follow-up "your order failed, refund issued" email rather than to undo the original.

The hardest part of compensation design is **idempotency and retry safety**. Compensation may be invoked multiple times — the orchestrator might crash after sending the compensation command but before recording that it did so, and on restart it sends the command again. The compensating service must recognize the duplicate and treat it as a no-op rather than refunding twice. The pattern is to use a deterministic compensation ID (typically `saga_id + step_id + "compensate"`) as the idempotency key in the compensating service's database — `INSERT ... ON CONFLICT (compensation_id) DO NOTHING`. Without this, a single orchestrator restart can produce double refunds, which is the kind of incident that gets a team on the front page of Hacker News.

The production failure mode is the "non-compensatable step" — a step whose forward action is irreversible (you sent a wire transfer; the recipient's bank does not support recalls) and whose failure therefore strands the saga in a state that requires manual intervention. The fix is to identify non-compensatable steps during design and either (a) move them to the end of the saga so they execute only after all compensatable steps have succeeded, or (b) accept them as "pivot" steps where the saga transitions from "rollback is possible" to "rollback is not possible, must commit forward." The pivot pattern is documented in the original Microsoft microservices e-book (Richardson 2018) and is the standard way to handle the "charge card and ship physical goods" workflow — the card charge is the pivot, and everything before it is compensatable, everything after it is "must succeed or human intervene."

### Implementation Topologies

A saga can be implemented in two topologies, and the choice is architectural: **choreography** (each service emits a domain event; the next service reacts) or **orchestration** (a central orchestrator service sends commands and tracks state). The trade-off is between decentralized simplicity and centralized debuggability. Most teams start with choreography for 2–3 step sagas and migrate to orchestration when the chain grows past 4 steps or when compensation logic becomes non-trivial.

```text
Choreography topology (event-driven, no central coordinator):

  Car Service ──CarReserved──▶ Event Bus ──┐
                                            ▼
                                       Hotel Service
                                            │
                                            ──HotelReserved──▶ Event Bus
                                                                 │
                                                                 ▼
                                                            Flight Service
                                                                 │
                                                                 ──FlightBooked──▶ ...

  Failure: Flight Service emits FlightBookingFailed
  Hotel Service listens → cancels reservation → emits HotelCancelled
  Car Service listens → cancels reservation → emits CarCancelled
  Saga implicitly unwinds via event chain.

Orchestration topology (central orchestrator owns state machine):

  Orchestrator (Temporal Workflow / Camunda / Step Functions)
      │
      │ 1. reserveCar(user_id) ──────────────▶ Car Service
      │ ◀────────────── res_id=car_42 ────────
      │ 2. reserveHotel(res_id, dates) ──────▶ Hotel Service
      │ ◀────────────── hotel_id=h_99 ────────
      │ 3. chargeCard(amount=500) ───────────▶ Payment Service
      │ ◀────────────── FAIL: card_declined ─
      │
      │ Compensation (reverse order):
      │ 2c. cancelHotel(hotel_id=h_99) ──────▶ Hotel Service
      │ 1c. cancelCar(res_id=car_42) ────────▶ Car Service
      │
      └─ Saga state persisted in orchestrator's DB. Crash-safe.
```

The topology choice has operational consequences that show up in production. **Choreography** is a publisher-subscriber graph — debuggability requires tracing events through the bus (Kafka topic offsets, RabbitMQ exchanges, EventBridge traces), which is harder than reading a single orchestrator's log. **Orchestration** centralizes the state machine, which makes the saga's progress directly queryable (`saga_id=42 is at step 3, status=COMPENSATING`), but the orchestrator itself becomes a critical piece of infrastructure that must be highly available (Temporal alone runs a Postgres-backed replicated log; Camunda 8 runs Zeebe on Raft).

The hybrid pattern that some teams adopt is "orchestrated choreography": a lightweight orchestrator that exists only to track saga state and emit the first command for each step, but each service still publishes events that the orchestrator listens for to advance the state machine. This avoids the "spaghetti of event subscriptions" problem in pure choreography while preserving the event-driven nature of the services. AWS Step Functions implements this pattern with its `WaitForTaskToken` integration — the orchestrator emits a task token, the service does its work and calls back with the token, and the orchestrator advances the state machine. The Step Functions pricing model ($0.025 per million state transitions, $1.00 per million for Express Workflows) means each saga step costs a fraction of a cent, which is fine for low-volume business workflows but expensive for high-volume streaming pipelines.

The production failure mode for topology choice is the "invisible saga" — a choreography saga where no single component knows the overall state, so when a step fails and compensation cascades through 5 services, the operator cannot easily see "what's the state of saga 42?" without correlating logs across all 5 services. The fix is either to migrate to orchestration (preferred once sagas grow past 3-4 steps) or to add a saga-state-tracking service that subscribes to all saga events and maintains a queryable projection. The metric that reveals the pain is `mean_time_to_resolution` for saga-related incidents — it should be minutes, not hours.

### Choreography-Based Sagas: Services listen to domain events and execute local transactions indepen...

In a choreography saga, there is no central coordinator. Each service subscribes to the events that should trigger its step, executes its local transaction when the event arrives, and publishes its own event when the transaction commits. The saga is implicit in the event-subscription graph: the Car Service publishes `CarReserved`, the Hotel Service subscribes to `CarReserved` and publishes `HotelReserved`, the Flight Service subscribes to `HotelReserved` and publishes `FlightBooked` (or `FlightBookingFailed`), and the compensation chain unwinds through the same event mechanism in reverse.

```text
Choreography saga — Book Vacation, happy path:

  CarSvc: reserveCar()
    └─ COMMIT local txn
    └─ PUBLISH event: {type: "CarReserved", saga_id: 42, res_id: "car_99", ...}
         │
         ▼
  HotelSvc: subscribed to "CarReserved"
    └─ reserveHotel(saga_id=42, ...)
    └─ COMMIT local txn
    └─ PUBLISH event: {type: "HotelReserved", saga_id: 42, hotel_id: "h_77", ...}
         │
         ▼
  FlightSvc: subscribed to "HotelReserved"
    └─ chargeCardAndBookFlight(saga_id=42, amount=500)
    └─ COMMIT local txn
    └─ PUBLISH event: {type: "FlightBooked", saga_id: 42, conf: "ABC123"}
         │
         ▼
  EmailSvc: subscribed to "FlightBooked"
    └─ sendTicketEmail(saga_id=42, conf="ABC123")
    └─ COMMIT local txn
    └─ PUBLISH event: {type: "TicketEmailSent", saga_id: 42}
         │
         ▼
  Saga complete. No orchestrator was involved.

Failure path — FlightSvc chargeCard fails:
  FlightSvc: subscribed to "HotelReserved"
    └─ chargeCard(saga_id=42, amount=500) → CARD_DECLINED
    └─ local txn NOT committed (rolled back)
    └─ PUBLISH event: {type: "FlightBookingFailed", saga_id: 42, reason: "card_declined"}
         │
         ▼
  HotelSvc: subscribed to "FlightBookingFailed"
    └─ cancelHotel(saga_id=42, hotel_id="h_77")  ← compensation
    └─ COMMIT local txn
    └─ PUBLISH event: {type: "HotelCancelled", saga_id: 42}
         │
         ▼
  CarSvc: subscribed to "HotelCancelled"
    └─ cancelCar(saga_id=42, res_id="car_99")  ← compensation
    └─ COMMIT local txn
    └─ PUBLISH event: {type: "CarCancelled", saga_id: 42}
         │
         ▼
  EmailSvc: subscribed to "CarCancelled" (or to "FlightBookingFailed")
    └─ sendFailureEmail(saga_id=42, reason: "card_declined")
    └─ Saga unwound, customer notified.
```

The strengths of choreography are simplicity and decoupling. Adding a new service to the saga (say, a Loyalty Service that awards points on flight booking) is just subscribing the new service to `FlightBooked` — no orchestrator code change. Each service owns its own state and its own retry/idempotency logic; the failure of one service does not block the others. The event bus (Kafka, RabbitMQ, EventBridge) provides at-least-once delivery, and each service must be idempotent — process each event exactly once even if the bus redelivers it. The standard pattern is a `processed_events` table in each service's database with the event ID as primary key; before processing an event, the service checks whether it has already processed that ID and skips if so.

The weaknesses are observability and cyclic dependency. There is no single place to ask "what is the state of saga 42?" — the operator must query each service's saga-state table or correlate logs across all services via the `saga_id`. The dependency graph can develop cycles: A subscribes to B's events, B subscribes to C's events, C subscribes to A's events, and a single event triggers an infinite loop. The fix is to use distinct event types for forward and compensation actions (never re-publish the same event type as a side effect of handling it) and to enforce a strict DAG in the event-subscription graph during code review. The "spaghetti of event subscriptions" anti-pattern is real and is the primary reason teams migrate to orchestration once their sagas exceed 3-4 steps.

The production failure mode for choreography is "lost event" — a service commits its local transaction but fails to publish the event (the local transaction and the event publish are not atomic without transactional outbox). The next service never receives the trigger, and the saga stalls. The fix is the **transactional outbox pattern**: the service writes the event to an `outbox` table in the same local transaction as its business data, commits, and then a separate process (Debezium, a polling publisher, or a CDC stream) reads the outbox and publishes to the event bus. This guarantees that the event is published exactly once, eventually — the saga cannot stall because of a publish failure.

### Orchestration-Based Sagas: A centralized Orchestrator service manages state machines, sends comma...

In an orchestration saga, a central orchestrator service owns the state machine. The orchestrator sends a command to the first service, waits for the response, sends the next command, and so on; on failure, the orchestrator sends compensation commands in reverse order. The orchestrator persists its state after every step, so a crash mid-saga is recoverable — on restart, the orchestrator reads its state, sees "step 3 was sent, response was FAIL," and resumes by sending the compensation for steps 2 and 1.

```java
// Temporal workflow — Book Vacation saga
// (Temporal is the dominant orchestration engine for production sagas in 2024+)
@WorkflowInterface
public interface BookVacationWorkflow {
    @WorkflowMethod
    VacationResult bookVacation(VacationRequest request);
}

public class BookVacationWorkflowImpl implements BookVacationWorkflow {

    private final CarActivities    car = Workflow.newActivityStub(CarActivities.class);
    private final HotelActivities  hotel = Workflow.newActivityStub(HotelActivities.class);
    private final FlightActivities flight = Workflow.newActivityStub(FlightActivities.class);
    private final EmailActivities  email = Workflow.newActivityStub(EmailActivities.class);

    @Override
    public VacationResult bookVacation(VacationRequest req) {
        // Step 1: reserve car
        CarReservation carRes = car.reserve(req.userId(), req.dates());
        try {
            // Step 2: reserve hotel
            HotelReservation hotelRes = hotel.reserve(req.userId(), req.dates(), carRes.id());
            try {
                // Step 3: charge card and book flight (PIVOT step — no compensation after this)
                FlightConfirmation flightConf = flight.chargeAndBook(
                    req.userId(), req.cardToken(), carRes.total() + hotelRes.total());
                try {
                    // Step 4: send confirmation email (non-compensatable, idempotent)
                    email.sendTicket(req.userId(), flightConf);
                } catch (Exception e) {
                    // Email failed — log and continue, or send via alternate channel.
                    // We do NOT compensate the flight booking because the customer has paid.
                    Workflow.getLogger().warn("Email send failed for saga " +
                        Workflow.getInfo().getWorkflowId() + ": " + e.getMessage());
                }
                return new VacationResult(carRes, hotelRes, flightConf);
            } catch (Exception e) {
                // Step 3 failed — compensate step 2 (hotel) and step 1 (car).
                // Step 3's charge was never captured, so no compensation needed for it.
                hotel.cancel(hotelRes.id());
                car.cancel(carRes.id());
                throw e;  // saga fails
            }
        } catch (Exception e) {
            // Step 2 failed — compensate step 1 (car).
            car.cancel(carRes.id());
            throw e;
        }
    }
}
// Activity definitions omitted — each @ActivityMethod is an RPC stub
// to the corresponding service (CarActivities.reserve → POST /cars/reserve).
// Temporal persists the workflow state after every activity invocation,
// so a crash of the workflow worker resumes from the last completed activity.
```

The orchestrator's primary correctness guarantee is **durable state**. Temporal persists every workflow state transition to its database (Postgres, MySQL, or Cassandra) after every activity invocation; on a worker crash, the workflow is replayed from the event log, with activities re-invoked only if they did not complete. Camunda 8 (Zeebe) achieves the same with Raft-replicated log streams per partition. AWS Step Functions achieves it with a managed service that charges per state transition. The cost is one database write per step — typically 5–20 ms per step on Temporal, which is acceptable for most business workflows but is too slow for sub-100 ms user-facing transactions.

**Camunda 8 (Zeebe)** takes a different approach: the saga is defined as a BPMN 2.0 XML diagram rather than imperative code, and the Zeebe engine interprets the diagram at runtime. The advantage is that the diagram is directly renderable by Camunda Operate (the visual monitoring UI), so operators can see saga state as a graph rather than as code; business analysts can read the diagram even if they cannot read Java. The disadvantage is that BPMN XML is verbose and the developer loses the familiar imperative control flow. A minimal Camunda 8 saga for the same Book Vacation workflow:

```xml
<bpmn:process id="bookVacation" isExecutable="true">
  <bpmn:startEvent id="start" />
  <bpmn:serviceTask id="reserveCar" name="Reserve Car">
    <bpmn:extensionElements>
      <zeebe:taskDefinition type="reserve-car" />
    </bpmn:extensionElements>
    <bpmn:boundaryEvent id="compensateCar" attachedToRef="reserveCar">
      <bpmn:compensateEventDefinition />
    </bpmn:boundaryEvent>
    <bpmn:serviceTask id="cancelCar" isForCompensation="true">
      <bpmn:extensionElements>
        <zeebe:taskDefinition type="cancel-car" />
      </bpmn:extensionElements>
    </bpmn:serviceTask>
  </bpmn:serviceTask>
  <bpmn:serviceTask id="reserveHotel" name="Reserve Hotel">
    <bpmn:extensionElements>
      <zeebe:taskDefinition type="reserve-hotel" />
    </bpmn:extensionElements>
  </bpmn:serviceTask>
  <bpmn:endEvent id="success" />
  <bpmn:boundaryEvent id="errorHandler" attachedToRef="reserveHotel">
    <bpmn:compensateEventDefinition />
  </bpmn:boundaryEvent>
</bpmn:process>
```

Each `serviceTask` is implemented by a worker (Java, Node.js, Go, Python) that polls Zeebe for jobs of that type via the `zeebe-client` library, executes the local transaction, and calls back with `Complete` or `Fail`. Zeebe's `compensateEventDefinition` and `isForCompensation="true"` attributes tell the engine that on failure of the parent saga, the compensation tasks should be invoked in reverse order — the same LIFO unwind as Temporal's try/catch blocks. The tradeoff vs Temporal is: Camunda's BPMN is more visual and discoverable by non-engineers (analysts, ops, support can read the diagram); Temporal's imperative Java/Go code is more familiar to backend developers and more flexible for complex control flow (loops, dynamic branching, child workflows). Both run on Raft-replicated logs (Zeebe is built on Raft natively; Temporal uses its own replicated log over MySQL/Postgres/Cassandra) and both persist saga state after every step. The choice is largely organizational: teams with a strong business-analyst presence lean Camunda; teams of pure backend engineers lean Temporal.

The orchestrator handles retries and idempotency at the activity level. Each activity invocation gets a deterministic activity ID; the called service must use that ID as its idempotency key. Temporal's activity retry policy (`ActivityOptions.Builder().setRetryOptions(...)`) controls the retry behavior — max attempts, backoff, retryable exception types. The orchestrator re-invokes an activity if it did not receive a successful response, and the service's idempotency check ensures that the duplicate invocation is a no-op. This is the same idempotency pattern as in choreography, but enforced by the orchestrator rather than by each service's event handler.

The production failure mode for orchestration is "orchestrator unavailability" — if Temporal is down, no new sagas can start and in-flight sagas cannot progress. The mitigation is to run Temporal as a highly available service (multi-AZ Postgres or Cassandra, multiple workflow workers across AZs) and to make the orchestrator's state database the most reliable component in your stack. The other failure mode is "stuck saga" — an activity that never returns (the called service is down) and the retry policy exhausts. Temporal exposes these as `WorkflowExecution` rows with `status=RUNNING` and a stale `last_updated_at`; the operator can either query the workflow state via the Temporal UI / `tctl workflow show` or terminate the workflow and trigger manual compensation.

## Key Takeaways

1. **A Saga is the production answer to distributed transactions when 2PC is too blocking.** Each step is a short local ACID transaction; the global saga is only eventually consistent. The trade is ACID isolation for availability and decoupling.
2. **Compensation is semantic, not a rollback.** You cannot un-charge a card, un-send an email, or un-dispatch a shipment — you issue a refund, send a follow-up email, or schedule a return. Compensation must be idempotent (deterministic `saga_id + step_id` key) and best-effort (failed compensations surface for human intervention).
3. **Choreography for ≤3 steps, orchestration for ≥4 steps.** Choreography is simpler to start with but degrades into spaghetti as the chain grows. Orchestration (Temporal, Camunda 8, Step Functions) centralizes the state machine and makes sagas queryable, at the cost of one more piece of critical infrastructure.
