# 08.03.01. Batch vs. Stream Processing Foundations

## What This Is

Every distributed data-processing workload falls into one of two paradigms. **Batch processing** operates on **bounded data** — a finite, known-size dataset (yesterday's parquet files, last month's CSV exports, a one-time backfill of a database table). The job starts, processes the entire dataset, writes its output, and terminates. **Stream processing** operates on **unbounded data** — an infinite, continuously-arriving sequence of events (Kafka topic `user_clicks`, an IoT telemetry feed, a payment processor's transaction stream). The job starts and runs forever, continuously processing new events as they arrive and producing continuously-updated output. The two paradigms share the same conceptual primitives (partition, transform, aggregate, join) but diverge sharply on the questions of windowing, time semantics, and state management.

This note sits in section 08 because the batch/stream distinction is the conceptual foundation for the entire 08.03 Spark sub-section. The same Spark engine handles both paradigms — [[08.03.02. Apache Spark Architecture and Compute Engine]] describes the unified compute substrate, [[08.03.03. Spark Operations Partitioning and Shuffling]] describes the partition-level mechanics that both paradigms rely on, and [[08.03.04. Spark Structured Streaming]] describes the streaming-specific abstractions (micro-batch vs. continuous engine, event-time windows, watermarks, output modes) that this note introduces. The reason 08.03.01 comes first is that you cannot reason about Structured Streaming without first understanding why unbounded data requires windowing, why windowing requires event-time semantics, and why event-time requires watermarks — and those are all concepts that the batch/stream divide forces into existence.

## The Details

### Bounded Data (Batch) vs. Unbounded Data (Stream) paradigms

A bounded dataset has a known, finite size at the moment processing starts. A nightly ETL job that reads yesterday's 50 GB of parquet logs and writes aggregated metrics to a warehouse is bounded: the engine can plan the workload in advance (split into 200 partitions of 250 MB each, schedule across 10 executors, estimate runtime), it can sort the entire dataset on disk if a wide transformation requires it, and it knows the job is done when the last partition's output is committed. The boundedness is what enables classic batch optimizations: a sort-merge join can spill to disk because both sides are finite; a global sort can be done with `sort by` because the data fits in a known number of sorted runs; the engine can produce a single final output (a written file, a committed table partition) that downstream consumers read after the job completes.

An unbounded dataset has no known size — events keep arriving forever. A fraud-detection job that consumes from Kafka topic `transactions` and emits alerts to topic `alerts` is unbounded: the engine cannot plan the workload in advance (it does not know how many events will arrive in the next hour), it cannot spill the entire dataset to disk (the dataset is infinite), and it cannot produce a single final output (the job never finishes). Every operation that batch takes for granted becomes a design question: how do you "sort" an infinite stream? (You don't — you sort within a window.) How do you "join" two unbounded streams? (You join within a window and drop data that arrives too late.) How do you "commit" the output? (You commit incrementally, every micro-batch or every trigger.)

```text
Bounded vs. unbounded — the practical consequences:

  Property                  Bounded (batch)              Unbounded (stream)
  ──────────────────────    ─────────────────────────    ─────────────────────────────
  Dataset size              Known, finite                Unknown, infinite
  Job lifetime              Runs to completion           Runs forever (until killed)
  Output                    Single final result          Continuous incremental updates
  Sort                      Global sort feasible         Sort only within window
  Join                      Full table joins             Windowed joins (drop late data)
  Aggregation               Group-by over full dataset   Group-by within window
  State                     None (or local to task)      Required across windows
  Failure recovery          Re-run from start            Resume from last checkpoint
  Latency                   Minutes to hours             Milliseconds to seconds
  Throughput                MB/s to GB/s (high)          Typically lower than batch
  Example                   Nightly ETL                  Real-time fraud alerts
  Spark API                 SparkSession.read().parquet  spark.readStream.format("kafka")
```

The same Spark DataFrame API handles both paradigms — the only syntactic difference is `spark.read` (batch) vs. `spark.readStream` (streaming). Under the hood, the batch path compiles to a one-shot DAG that executes and terminates; the streaming path compiles to a continuously-running query that re-executes on every trigger interval. The reason Spark can unify the two is the **micro-batch** model: a stream is treated as a series of small bounded batches (one per trigger interval, e.g., every 10 seconds). Each micro-batch is processed exactly like a batch job — the same DAG, the same Catalyst optimizer, the same Tungsten code generation — and the results are appended to the output sink. The cost of this unification is latency: a micro-batch cannot complete faster than the trigger interval plus the per-batch processing time, which gives Structured Streaming a practical floor of ~100 ms — fast enough for most business use cases but too slow for high-frequency trading or sub-millisecond telemetry.

The continuous processing engine (added in Spark 2.3, experimental) is the alternative for sub-100 ms latency. In continuous mode, long-running tasks process events as they arrive without batching — each task is a Rust-style event loop that reads from the source, applies the operator, and writes to the sink in a single thread. Continuous mode achieves sub-millisecond latency but supports only a restricted operator set (no stateful aggregations, no shuffles — only map-like transformations) because the long-running-task model cannot easily checkpoint state across a network shuffle. The trade-off is fundamental: the more an engine batches, the higher its throughput (amortized overhead) and the higher its latency; the less it batches, the lower its latency and the lower its throughput. Every stream processing engine picks a point on this curve — Spark defaults to micro-batch for throughput, Flink defaults to continuous for latency, Kafka Streams is continuous-only.

The production failure mode for bounded/unbounded confusion is treating a stream as if it were bounded. A common pattern: a team writes a Spark batch job that reads from Kafka with `spark.read.format("kafka")`, processes the entire topic in one shot, and exits — then schedules it as a "streaming job" via cron every 5 minutes. This works until the topic grows faster than 5 minutes of polling can keep up with, at which point the job's runtime exceeds 5 minutes, the next cron invocation overlaps, the consumer-group rebalances mid-job, and the team is paged at 3 AM. The fix is to use `spark.readStream` with a trigger interval that matches the schedule, so the engine manages the consumer-group offsets, the checkpointing, and the backpressure correctly. The metric that reveals the failure is `consumer_lag` rising on the Kafka topic — a healthy stream keeps lag bounded; a misconfigured "streaming" batch job lets it grow without limit.

### High-latency massive dataset transforms vs. Low-latency continuous stream computations

The latency/throughput trade-off is the central engineering decision in any data pipeline. **Throughput** is events processed per unit time — MB/s for batch, events/s for streaming. **Latency** is the time from event arrival to event processed-output-visible — minutes to hours for batch, milliseconds to seconds for streaming. The two are in tension: optimizing for throughput requires amortizing per-event overhead across many events (large batches, large buffers, fewer commits), while optimizing for latency requires processing each event as soon as it arrives (small batches, small buffers, frequent commits). A batch job that processes 10 TB in 1 hour has high throughput (2.8 GB/s) and high latency (1 hour from first event to output); a stream job that processes 10 events per second with 50 ms end-to-end latency has low throughput and low latency. There is no engine that simultaneously maximizes both — the workload characteristics dictate which to optimize.

```text
Latency vs. throughput — the engineering decision tree:

  Question                                  If "yes" → batch           If "yes" → stream
  ──────────────────────────────────────    ────────────────────       ──────────────────────
  Is the data source a finite file/table?   Use batch                  —
  Is the data source a Kafka topic?         —                          Use stream
  Can the output be a day-old snapshot?     Use batch                  —
  Must the output reflect the last second?  —                          Use stream
  Is the workload multi-TB / multi-hour?    Use batch                  —
  Is the workload <10k events/s?            —                          Use stream
  Are you okay with micro-batch latency?    Batch or micro-batch       Micro-batch
  Do you need sub-100 ms latency?           —                          Continuous engine
  Do you need global sort over the data?    Use batch                  —
  Do you need windowed aggregation?         Batch or stream            Stream

  Concrete numbers:
    Batch (Spark, 200 executor cluster, 10 TB parquet):
      Throughput: ~5-10 GB/s aggregate
      Latency:    30-60 min (job runtime)
      Use case:   Nightly warehouse ETL

    Micro-batch (Structured Streaming, 10s trigger):
      Throughput: ~1M events/s aggregate
      Latency:    10-100 s end-to-end (trigger + processing)
      Use case:   Real-time dashboards, hourly billing

    Continuous (Flink, Kafka Streams, Spark continuous):
      Throughput: ~100k events/s per core
      Latency:    1-50 ms end-to-end
      Use case:   Fraud detection, real-time alerting

    Lambda architecture (batch + speed layer in parallel):
      Batch:    recomputes authoritative view every hour
      Speed:    approximates view in real-time
      Merge:    client reads both, prefers batch when available
      Trade-off: complexity of maintaining two pipelines
```

Windowing is the mechanism that makes unbounded data tractable. Without windows, you cannot aggregate an infinite stream — the group-by-key operation would have to hold state for every key forever. A **window** is a finite subset of the stream defined by a time range (or, less commonly, a count range). The four windowing strategies are **tumbling** (fixed-size, non-overlapping — `[0:00, 0:05)`, `[0:05, 0:10)`, ...), **hopping** (fixed-size, overlapping, advanced by a hop — 5-minute windows hopping every 1 minute: `[0:00, 0:05)`, `[0:01, 0:06)`, `[0:02, 0:07)`, ...), **sliding** (windows defined by a max-size and a slide that triggers as new events arrive — each event belongs to multiple windows), and **session** (windows defined by a gap-of-inactivity — events that are within `gap` of each other belong to the same window, windows close when no event arrives for `gap`).

```text
Window types for a stream of events (event-time, 1-minute axis):

  Tumbling windows (5 min, no overlap):
    ┌──[0:00, 0:05)──┐ ┌──[0:05, 0:10)──┐ ┌──[0:10, 0:15)──┐
    ● ● ● ● ●          ● ● ● ●             ● ● ● ● ● ●

  Hopping windows (5 min size, 1 min hop):
    ┌─[0:00,0:05)─┐
    ┌─[0:01,0:06)─┐
    ┌─[0:02,0:07)─┐     (each event belongs to up to 5 windows)
    ┌─[0:03,0:08)─┐
    ┌─[0:04,0:09)─┐
    ┌─[0:05,0:10)─┐

  Sliding window (size 5 min, slide per event):
    Each new event triggers a window [event_time - 5min, event_time].
    Useful for "moving average over last 5 min."

  Session window (gap = 2 min):
    ● ● ●     (gap)     ● ● ● ● ●           (gap)      ● ●
    [0:00, 0:04]        [0:06, 0:14]                   [0:18, 0:20]
    Window closes when no event arrives for 2 minutes after the last event.
```

The window type choice has performance and correctness implications. Tumbling windows are cheapest (each event belongs to exactly one window) but cannot answer "average over the last 5 minutes as of right now." Hopping windows are more flexible but multiply state by the overlap factor (a 5-min window hopping every 1 min keeps 5× the state of a tumbling window). Sliding windows are the most expressive but the hardest to implement efficiently — a true sliding window requires keeping the last `window_size` of events in memory and re-aggregating on every new arrival. Session windows are ideal for user-behavior analytics (a "session" is a period of activity) but their variable size makes them unpredictable for capacity planning.

**Event time vs. processing time** is the second conceptual hurdle. **Event time** is the moment the event occurred at its source — the timestamp embedded in the event by the producing device or application (e.g., the time the user clicked the button, recorded in the click event). **Processing time** is the moment the event arrived at the processing engine — the wall-clock time when Spark read the event from Kafka. The two are almost never equal: a click event generated at 12:00:00 on a mobile device may not arrive at the Kafka broker until 12:00:03 (3 seconds of network delay), and may not be processed by Spark until 12:00:13 (10 seconds of queueing in the consumer). The skew between event time and processing time is called **event-time skew**, and it varies wildly — seconds for in-region traffic, minutes for cross-region, hours for IoT devices on flaky cellular networks.

```text
Event time vs. processing time:

  Source device           Kafka broker            Spark engine
  ──────────────          ──────────────          ──────────────
  t=12:00:00.000          t=12:00:03.500          t=12:00:13.200
  (event_time)            (broker receipt)        (processing_time)

  Event-time skew = 13.2 seconds for this event.
  Another event from the same source might arrive 60 seconds later
  but have an event_time of 12:00:01 (older). This is "out-of-order" data.

  Windowing by processing_time:
    - 12:00:00-12:00:05 window contains events processed between those times.
    - An event generated at 12:00:00 but processed at 12:00:10 lands in 12:00:10-12:00:15 window.
    - Output reflects when the engine saw events, not when they happened. Wrong for analytics.

  Windowing by event_time:
    - 12:00:00-12:00:05 window contains events whose event_time is in that range.
    - The same event lands in the correct window regardless of processing delay.
    - BUT: the engine cannot know when to "close" the window — late events may still arrive.
    - Solution: watermark (next paragraph).
```

The **watermark** is the mechanism that lets an event-time windowed stream make progress despite not knowing whether more late events will arrive. A watermark is a threshold — "I will not accept any event with `event_time < watermark`" — that the engine advances as it processes events. The most common watermark strategy is **bounded-out-of-orderness**: `watermark = max_event_time_seen - max_lateness_allowed`, where `max_lateness_allowed` is a configuration parameter (e.g., 10 minutes). When the watermark crosses a window's end, the engine finalizes the window, emits the result, and frees the window's state. Events that arrive after the watermark has crossed their window are **late data** and are either dropped (default) or routed to a side output for separate handling. The watermark trade-off is fundamental: a large `max_lateness_allowed` (1 hour) means late events are tolerated but window state is held for 1 hour; a small `max_lateness_allowed` (10 seconds) means state is freed quickly but events delayed by more than 10 seconds are dropped.

The production failure mode for windowing and watermark misconfiguration is silent data loss. A team configures `withWatermark("event_time", "10 seconds")` on a stream whose events routinely arrive 30 seconds late (because of upstream queueing), and 90% of the events are dropped — the engine logs nothing, the dashboard shows a steep drop in throughput, and nobody notices for a week. The metric that reveals it is `num_dropped_records` (a Spark Structured Streaming metric) or `dropped_records_total` (Flink). The fix is to set the watermark based on observed event-time skew (measure the 99th-percentile skew from production data, multiply by 2-3 for safety), and to monitor the drop rate as a leading indicator that the upstream pipeline is degrading. The other failure mode is state explosion: a large watermark means windows are held in state for a long time, and if the window cardinality (number of distinct keys) is high, the state backend fills up and the job OOMs. The fix is to use RocksDB state backend (Spark's `StateStore.provider=rocksdb`, Flink's default for state > 1 GB), which spills to disk rather than holding everything in JVM heap.

## How This Connects to the Runtimes

The batch/stream distinction is implemented at the runtime layer as the difference between a one-shot JVM process and a long-running JVM process. A Spark batch job is a JVM that the cluster manager starts, runs to completion, and terminates — typical lifetimes are 5–60 minutes, and the JVM's heap is sized for the working set (50–100 GB is common on a YARN cluster). A Spark Structured Streaming job is a JVM that the cluster manager starts and expects to run forever — typical lifetimes are weeks to months, the heap must be sized for steady-state operation (not the entire dataset), and the JVM's GC must be tuned for low-pause (G1 or ZGC, not the default ParallelGC) because a 5-second GC pause causes the Kafka consumer to time out and the consumer group to rebalance. The same JVM-level concerns (heap sizing, GC tuning, off-heap allocation) apply to both paradigms, but the streaming case is far less forgiving — a batch job can tolerate a 30-second GC pause at the end; a streaming job will be killed by its consumer-group heartbeat timeout.

The framework connection is that every runtime covered in section 04 can host a stream processor. The JVM (Spark, Flink, Kafka Streams) is the dominant runtime for production stream processing because of its mature GC tuning, off-heap memory, and the JVM's ability to host long-running networked services. Node.js (with KafkaJS + custom windowing) is used for lighter-weight stream processing in TypeScript shops. Python (with Faust, or with PySpark Structured Streaming) is used where the data science team is more comfortable in Python than in Java/Scala. PHP and Ruby are essentially absent from production stream processing — neither has a mature stream-processing library, and neither runtime is well-suited to long-running memory-heavy workloads. The choice of runtime for stream processing is constrained by the streaming-engine library you want to use, not by your team's primary language.

## Hands-On Exercise

```bash
# 1. Install PySpark (pip) and verify version
pip install pyspark==3.5.0
python -c "import pyspark; print(pyspark.__version__)"

# 2. Run a BOUNDED batch job — word count over a local file
python -c "
from pyspark.sql import SparkSession
spark = SparkSession.builder.appName('batch-wc').getOrCreate()
df = spark.read.text('/etc/passwd')              # bounded: file is finite
counts = df.groupBy('value').count()             # global group-by OK on bounded data
counts.show(5)
spark.stop()
"

# 3. Run an UNBOUNDED streaming job — word count over a netcat socket stream
#    (terminal 1: start netcat)
nc -lk 9999
#    (terminal 2: start the stream job)
python -c "
from pyspark.sql import SparkSession
from pyspark.sql.functions import explode, split, current_timestamp
spark = SparkSession.builder.appName('stream-wc').getOrCreate()
lines = spark.readStream.format('socket').option('host','localhost').option('port',9999).load()
words = lines.select(explode(split(lines.value,' ')).alias('word'))
counts = words.groupBy('word').count()           # unbounded: state grows per distinct word
query = counts.writeStream.outputMode('complete').format('console').start()
query.awaitTermination()
"
# Type words in terminal 1 → watch counts update every trigger in terminal 2.

# 4. Observe event-time vs processing-time skew on a Kafka topic
#    (requires a Kafka broker; assumes topic 'events' with timestamped events)
python -c "
from pyspark.sql import SparkSession
from pyspark.sql.functions import col, current_timestamp
spark = SparkSession.builder.appName('skew').getOrCreate()
df = spark.read.format('kafka').option('kafka.bootstrap.servers','localhost:9092') \\
        .option('subscribe','events').option('startingOffsets','earliest').load()
df.selectExpr('CAST(value AS STRING) as event','timestamp as kafka_time') \\
  .withColumn('processing_time', current_timestamp()) \\
  .selectExpr('(unix_timestamp(processing_time) - unix_timestamp(kafka_time)) as skew_seconds') \\
  .describe().show()
# Mean / stddev / max of skew_seconds tells you how much event-time lag your pipeline has.
"

# 5. Configure a watermark and observe late-data drops
python -c "
from pyspark.sql import SparkSession
from pyspark.sql.functions import window, col
spark = SparkSession.builder.appName('watermark').getOrCreate()
stream = spark.readStream.format('kafka') \\
    .option('kafka.bootstrap.servers','localhost:9092').option('subscribe','events').load() \\
    .selectExpr('CAST(value AS STRING) as json','timestamp as event_time') \\
    .withWatermark('event_time','10 minutes') \\
    .groupBy(window(col('event_time'),'5 minutes'),col('json')).count()
# Events with event_time more than 10 minutes behind the latest seen will be dropped.
# Watch the Structured Streaming UI: 'numDroppedRows' metric.
query = stream.writeStream.outputMode('append').format('console').start()
query.awaitTermination()
"

# 6. Inspect the Structured Streaming UI for the watermark and state metrics
#    Open http://localhost:4040/StreamingQuery/ in a browser while query runs.
#    Look at: inputRows-per-second, processingRows-per-second, numTotalStateRows,
#             numDroppedRows, eventTime.watermark.

# 7. Compare micro-batch vs continuous engine (continuous is experimental, restricted)
spark.conf.set("spark.sql.streaming.continuous.enabled", "true")
# Then add .trigger(continuous='1 second') to your writeStream — only map-only queries work.
```
