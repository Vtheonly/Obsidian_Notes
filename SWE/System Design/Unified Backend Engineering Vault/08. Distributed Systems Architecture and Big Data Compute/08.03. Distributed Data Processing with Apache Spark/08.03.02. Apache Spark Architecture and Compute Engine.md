# 08.03.02. Apache Spark Architecture and Compute Engine

## What This Is

Apache Spark is a distributed data-processing engine that decomposes a query into a Directed Acyclic Graph (DAG) of stages, schedules each stage's tasks onto JVM executors running across a cluster, and pipelines those tasks in-memory to avoid the disk round-trips that made Hadoop MapReduce slow. The engine has two halves. The **driver** is a single JVM that holds the `SparkContext` (or, since Spark 2.0, the `SparkSession` that wraps it), builds the logical plan from the user's DataFrame/RDD code, compiles it to a physical DAG of stages via the `DAGScheduler`, and dispatches the resulting `TaskSet`s to executors through the `TaskScheduler`. The **executors** are JVM worker processes launched by the cluster manager on worker nodes — each holds a `BlockManager` that registers with the driver's `BlockManagerMaster`, runs `TaskRunner` threads (one per `spark.executor.cores`, default 1 in dynamic allocation, 4 in static), caches RDD partitions and shuffle blocks in its `MemoryStore`, and reports a heartbeat RPC to the driver every `spark.executor.heartbeatInterval` (default 10 s).

Between driver and executors sits a **cluster manager** — Standalone, YARN, Mesos, or Kubernetes — whose only job is to allocate containers and restart them on failure. Spark does not know which cluster manager it is talking to; it talks to all of them through the same `ExternalClusterManager` SPI, and the choice changes only the binary-launch mechanism (a YARN container, a K8s pod, a Standalone worker slot) and the resource-isolation semantics. This note sits between [[08.03.01. Batch vs. Stream Processing Foundations]] (which establishes why bounded vs. unbounded data forces different execution models) and [[08.03.03. Spark Operations Partitioning and Shuffling]] (which drills into the partition-level mechanics of narrow vs. wide transformations). The reason the architecture note comes second is that the shuffle story only makes sense once you understand that the driver converts every job into stages delimited by shuffle boundaries, that each stage is a wave of identical tasks running one per partition, and that executors are stateful JVMs whose cached RDD partitions and shuffle outputs the driver tracks via the `BlockManagerMaster`. The structured streaming model in [[08.03.04. Spark Structured Streaming]] is then just this same architecture re-invoked every micro-batch trigger, with a `StreamExecution` thread on the driver that calls the batch `execute()` method once per trigger and writes incremental output to the sink.

## The Details

### Cluster Architecture: Driver Program, Cluster Manager (YARN, Kubernetes, Standalone), Worker Nodes, Executors, Tasks.

The driver is the brain of a Spark application. It is a JVM process the user launches with `spark-submit` (or interactively with `spark-shell` / `pyspark`); inside it, the `SparkContext` is the entry point that connects to the cluster manager and acquires executor resources. Two schedulers live on the driver. The `DAGScheduler` takes a user action (such as `collect()` on a DataFrame) and walks the RDD dependency graph backward to find shuffle boundaries, producing a topologically ordered list of `Stage` objects. Each stage corresponds to a "shuffle map" phase (its tasks write shuffle files for the next stage) or a "result" phase (its tasks compute the final output). The `TaskScheduler` then takes each `Stage`, converts it into a `TaskSet` of one `Task` per partition, and dispatches those tasks to executors based on data locality preferences (`NODE_LOCAL` preferred, then `RACK_LOCAL`, then `ANY`), retrying failed tasks up to `spark.task.maxFailures` (default 4) and launching speculative copies for straggler tasks when `spark.speculation=true`.

Executors are long-lived JVMs that do the actual work. Each executor runs `spark.executor.cores` `TaskRunner` threads in a shared thread pool, holds a slice of the application's memory (sized by `spark.executor.memory`, e.g., `8g`), and exposes a `BlockManager` that registers with the driver's `BlockManagerMaster` on startup. The executor's `MemoryStore` holds cached RDD partitions (when `df.cache()` is called) and broadcast variables; the rest of the heap is split between execution memory (shuffles, joins, sorts) and user structures. Executors also write shuffle output to `spark.local.dir` (default `/tmp` — a serious production footgun if left at default, since `/tmp` is often a small tmpfs). When an executor's heartbeat misses three intervals (~60 s, controlled by `spark.network.timeout`), the driver marks it lost, re-launches its tasks elsewhere, and re-computes any cached partitions from lineage.

The cluster manager choices have real, observable differences:

```text
Cluster manager comparison:
  Manager     Driver runs as          Executor unit           Isolation             Resource model
  ─────────   ────────────────────    ────────────────────    ──────────────────    ───────────────────────
  Standalone  Spark Master process    Worker JVM              Process-level         Manual cores+memory
  YARN        ApplicationMaster       YARN container          cgroup CPU + memory   Scheduler queue + fairshare
  Kubernetes  Driver pod              Executor pod            Linux namespace+cgroup K8s scheduler + requests/limits
  Mesos       Spark framework         Mesos task              cgroup                Fine-grained (revocable) or coarse
```

YARN is the most common production choice in Hadoop shops because it integrates with HDFS-aware locality and reuses existing Kerberos auth; Kubernetes is now the default for greenfield deployments because executors become first-class pods that participate in node-affinity, tolerations, and the cluster's observability stack. A real `spark-submit` against K8s looks like:

```bash
spark-submit \
  --master k8s://https://k8s-api:6443 \
  --name etl-user-events \
  --conf spark.kubernetes.namespace=analytics \
  --conf spark.kubernetes.authenticate.driver.serviceAccountName=spark \
  --conf spark.kubernetes.container.image=registry/ops/spark:3.5.0 \
  --conf spark.executor.instances=20 \
  --conf spark.executor.cores=4 \
  --conf spark.executor.memory=16g \
  --conf spark.executor.memoryOverhead=4g \
  --conf spark.driver.memory=8g \
  --conf spark.sql.shuffle.partitions=400 \
  --conf spark.shuffle.service.enabled=true \
  --class com.example.UserEventsJob \
  s3://artifacts/etl-1.4.2.jar /inputs/2024-03-15 /outputs
```

The production failure mode for the cluster architecture is driver loss. Unlike executors (which are disposable — the driver re-launches tasks elsewhere), the driver is a single point of failure: if it dies, the entire application dies, all in-flight tasks are lost, and any non-checkpointed streaming state is gone. YARN can auto-restart the ApplicationMaster via `--conf spark.yarn.maxAppAttempts=4`; K8s can use a `Deployment` or `RestartPolicy=Always` on the driver pod. The metric that reveals an unhealthy driver is `jvm.heap.usage` on the driver crossing 90% — the driver's heap holds the `BlockManagerMaster` registry, the `LiveListenerBus` event queue, and all `AccumulatorV2` snapshots, and any of these can OOM it under skew. The other common failure is the executor going silent under a long GC pause: `spark.executor.heartbeatInterval=10s` plus `spark.network.timeout=120s` gives the JVM 2 minutes to recover; a ZGC or G1 tuning that keeps pauses under 200 ms is essential for streaming jobs that cannot tolerate task retry storms.

### Resilient Distributed Datasets (RDDs): Immutability, Lineage Graphs (fault recovery), Partitioning

An `RDD[T]` is Spark's lowest-level abstraction: a read-only, partitioned, fault-tolerant collection of objects of type `T`. An RDD is defined by four pieces of state: a list of `Partition` objects, a `compute(partition: Partition, context: TaskContext): Iterator[T]` function that knows how to compute any partition on demand, a list of parent RDDs (`dependencies`), and an optional `Partitioner` (which is `None` for narrow-source RDDs, `HashPartitioner` for `reduceByKey`, `RangePartitioner` for `sortBy`). Every RDD is constructed either from a stable storage source — `sc.textFile("hdfs:///path")` creates an RDD whose `compute` function opens an HDFS block read-stream — or by transforming an existing RDD — `rdd.map(f)` creates an RDD whose `compute` calls the parent's `compute` and applies `f` to each element. Immutability means transformations produce *new* RDDs rather than mutating; the original is forever a node in the dependency graph.

The lineage graph is what makes RDDs fault-tolerant without replication. When you write `sc.textFile("in").filter(_.nonEmpty).map(_.split("\t")).cache().count()`, the chain `textFile → filter → map → cache` is recorded as a DAG of RDD references. If an executor holding a cached `map` partition dies, the driver's `BlockManagerMaster` discovers the loss on the next heartbeat miss, looks at the cached RDD's `dependencies`, finds that the parent is the `filter` RDD whose parent is the `textFile` RDD (which reads from HDFS — a stable source), and submits a recompute task that runs `textFile.compute → filter.apply → map.apply` for just that partition. The cost of a partition recompute is proportional to the depth of the lineage, which is why long chains of `map`/`filter` without `cache()` are slow to recover from failure. `checkpoint()` truncates the lineage by writing the RDD to stable storage (HDFS/S3) and replacing the parents with a `ReliableCheckpointRDD` — necessary for jobs with hundreds of transformations (e.g., iterative ML algorithms like ALS or LDA) where the lineage would otherwise be unbounded.

The dependency types govern how the `DAGScheduler` cuts stages:

```text
Narrow dependencies (parent partition → exactly one child partition):
  map, filter, flatMap, mapPartitions, union, coalesce (decreasing),
  mapPartitionsWithIndex.   → tasks pipelined in one stage.

Wide dependencies (parent partition → many child partitions):
  groupByKey, reduceByKey, aggregateByKey, join (if not co-partitioned),
  distinct, repartition, sortByKey, intersection.   → new stage boundary,
                                                      shuffle required.
```

```scala
val raw   = sc.textFile("hdfs:///events/2024-03-15")     // parent: HDFS
val clean = raw.filter(_.startsWith("{"))                 // narrow: 1:1
val pairs = clean.map(l => parseKey(l) -> 1)              // narrow: 1:1
val counts = pairs.reduceByKey(_ + _)                     // WIDE:   M:N  → new stage
val top10  = counts.top(10)(Ordering.by(_._2))            // action: triggers DAG
// Inspect the structure:
println(pairs.dependencies.head.getClass.getName)         // OneToOneDependency
println(counts.dependencies.head.getClass.getName)        // ShuffleDependency
println(counts.partitioner.get.getClass.getName)          // HashPartitioner
```

Partitioning is the unit of parallelism. The number of partitions defaults to `spark.default.parallelism` (total core count) for `sc.parallelize`, and is derived from the input format for sources — HDFS reads produce one partition per HDFS block (default 128 MB), parquet files produce one partition per row-group (typically 128 MB). `repartition(n)` round-trips through a hash shuffle to redistribute; `coalesce(n)` (narrow, no shuffle) only merges adjacent partitions down — useful for writing a small number of output files without paying shuffle cost. The production failure mode for partitioning is a misconfigured `spark.default.parallelism` of 200 on a 1000-core cluster: only 200 tasks run, 800 cores idle, the job takes 5× as long as it should. The other classic is a single-partition RDD produced by `df.collect().head` followed by a `parallelize` of a list — every downstream operation runs in one task, defeating the cluster. The metric that reveals it is the Spark UI's "Tasks: completed/200" line for a stage that should have thousands.

### Spark DataFrames and Datasets: Unified structured APIs and typed operations

A `DataFrame` is conceptually an `RDD[Row]` plus a `StructType` schema (column names, types, nullability). The schema is the crucial addition over plain RDDs: it lets the Catalyst optimizer see inside the data, push filters down to the parquet reader, prune unused columns, and choose between `SortMergeJoin` and `BroadcastHashJoin` based on estimated row counts. A `Dataset[T]` (Scala/Java only — Python and R have no compile-time types) is a `DataFrame` paired with an `Encoder[T]` that knows how to convert between `T` (a case class or Java bean) and Tungsten's binary row format. The same query in Scala/Java/Python/R produces the same Catalyst plan and runs at the same speed for native operations — the language binding is just a thin serialization layer over the JVM SparkSession.

The unified Structured API means the same `SparkSession` (Spark 2.0+) is the entry point for batch (`spark.read.parquet(...)`), streaming (`spark.readStream.format("kafka")...`), and SQL (`spark.sql("SELECT ... FROM ...")`). All three build a `LogicalPlan` that Catalyst optimizes identically. PySpark's DataFrame operations cross a Py4J bridge to invoke the JVM `Dataset` API; the Python process holds only a handle to the JVM-side plan, not the data. This is why Python DataFrame performance is within a few percent of Scala for plan-bound operations (filter, groupBy, join) — the actual execution is JVM-only — but degrades sharply for Python UDFs, which must serialize each row to a Python worker process via a socket, evaluate the function in Python, and serialize the result back. A Python UDF over 1 billion rows takes 5-10× as long as the equivalent Catalyst expression (`df.withColumn("y", upper($"x"))` vs. `udf(lambda s: s.upper())`).

```scala
// Same SparkSession for batch, streaming, SQL — unified Structured API
import spark.implicits._

val batchDF = spark.read.parquet("s3://lake/events/2024-03-15")
val streamDF = spark.readStream.format("kafka")
  .option("kafka.bootstrap.servers","broker:9092")
  .option("subscribe","events").load()

// Typed Dataset[T] in Scala — Encoder[T] auto-derived from the case class
case class Event(user: String, amount: Double, ts: java.sql.Timestamp)

val events: Dataset[Event] = batchDF.as[Event]
val totals: Dataset[(String, Double)] =
  events.groupByKey(_.user).agg(typed.sum(_.amount))   // type-safe aggregation
```

Encoders are the bridge between typed Scala objects and Tungsten's binary format. For a case class `Event(user: String, amount: Double, ts: Timestamp)`, the `ExpressionEncoder[Event]` generates bytecode at compile time that knows the exact byte offsets of each field in an `UnsafeRow` and can read/write them without any Java object allocation in the hot path. This is dramatically cheaper than Java serialization (which would allocate a full `Event` object per row plus a `String` plus a `Timestamp` plus a char array) — Tungsten rows are 4-10× more compact than their Java-object equivalents. The catch is that encoders are only auto-generated for product types (case classes, tuples); for arbitrary types you must hand-write an `Encoder[T]` or accept reflection-based fallback. The production failure mode is calling `df.rdd` on a DataFrame to "just do a quick map" — this escapes Catalyst entirely, drops the schema, and reverts to Java-object-per-row performance. The fix is to express the transformation as a column expression (`df.withColumn("y", expr("..."))`) or a Pandas UDF (`pandas_udf` with `ArrowEvalPythonExec`, which vectorizes the Python call rather than row-by-row). The metric that reveals the regression is `executor.cpuTime` staying low while `executor.deserializeTime` climbs — a sign of object-allocation pressure from RDD fallback.

### The Catalyst Optimizer: Logical Plan generation, Optimized Logical Plan, Physical Planning, and W...

Catalyst is a Scala-based query optimizer built on tree-transformation rules. Every DataFrame operation constructs a node in a `LogicalPlan` tree: `df.filter($"age" > 21)` builds a `Filter` node, `df.groupBy($"country").agg(sum($"amount"))` builds an `Aggregate` node, `df.join(other, $"id" === other.id)` builds a `Join` node. The plan starts **unresolved** — column names are just strings, types unknown, table references are names not yet bound to catalog entries. Catalyst's job is to walk this tree through four phases and produce a physical execution plan that the executors can run.

The four phases are: (1) **Analysis** — the `Analyzer` walks the tree bottom-up, looks up each `UnresolvedRelation` in the `Catalog` (the session's table-and-function registry, populated by `CREATE TABLE`, `registerTempTable`, etc.), resolves each `UnresolvedAttribute` to a typed `AttributeReference` by matching the column name against the schema, and throws `AnalysisException` if a name is ambiguous or missing; (2) **Logical optimization** — the `Optimizer` applies roughly 200 rule-based transformations (predicate pushdown moves `Filter` below `Join`, projection pruning drops columns the projection doesn't reference, constant folding evaluates `1+1` at plan time, boolean simplification rewrites `a AND TRUE` to `a`); (3) **Physical planning** — `SparkPlanner` generates one or more `PhysicalPlan` candidates for each logical node, e.g., for a `Join` it considers `BroadcastHashJoin` (small side < `spark.sql.autoBroadcastJoinThreshold`, default 10 MB), `SortMergeJoin` (default for large equi-joins since Spark 2.3), `ShuffleHashJoin` (faster than SMJ but requires a build-side hash table that fits in execution memory), and `BroadcastNestedLoopJoin`/`CartesianProduct` (the fallbacks for non-equi-joins); (4) **Code generation** — `WholeStageCodegenExec` wraps the physical operator chain in a single generated Java source file, Janino compiles it to bytecode at runtime, and the executor calls the generated `processNext()` method that fuses Filter + Project + Aggregate into one pass over each row.

```text
Catalyst pipeline for: events.filter($"amount" > 100).groupBy($"user").agg(sum("amount"))

  Parsed logical plan:        Filter (amount > 100)  →  Aggregate [user] [sum(amount)]
                                          (unresolved: 'amount, 'user)

  Analyzed logical plan:      Filter (amount#12 > 100) → Aggregate [user#11] [sum(amount#12)]
                                          (resolved: real attribute references)

  Optimized logical plan:     Aggregate [user#11] [sum(amount#12)]
                                → Filter (amount#12 > 100)        (predicate pushed below agg)
                                  → Relation events[user#11, amount#12, ...] (cols pruned to 2)

  Physical plan:              HashAggregate(keys=[user#11], functions=[sum])
                                ↳ Exchange hashpartitioning(user#11, 200)        (shuffle)
                                  ↳ HashAggregate(keys=[user#11], functions=[partial_sum])
                                    ↳ Filter (amount#12 > 100)
                                      ↳ ColumnarToRow
                                        ↳ FileScan parquet [user, amount] Batched: true,
                                                                       PushedFilters: [GreaterThan(amount,100)]
```

Cost-based optimization (CBO) is opt-in: `spark.sql.cbo.enabled=true` plus `ANALYZE TABLE events COMPUTE STATISTICS FOR COLUMNS user, amount` populates row counts and per-column histograms in the Hive metastore. With CBO, Catalyst picks join orderings (smaller side build-side for SHJ), picks `BroadcastHashJoin` when the estimated row count of one side is below the broadcast threshold, and reorders a chain of filters to apply the most selective first. Without CBO, Catalyst falls back to rule-based heuristics: filter order follows source order, join reordering uses the `ReorderJoin` rule that only swaps adjacent joins for which one side is broadcastable. The production failure mode is missing or stale statistics: a table that grew from 1 GB to 1 TB since the last `ANALYZE` makes Catalyst pick `BroadcastHashJoin` on what it thinks is a 1 GB table, which causes the driver to OOM collecting the broadcast variable. The fix is to schedule `ANALYZE TABLE` after every load job and to set `spark.sql.statistics.fallBackToHdfs=true` (use HDFS file size as a row-count estimate when stats are missing). The other failure mode is escaping Catalyst: `df.rdd`, `df.collect().map(...).toDF()`, Python non-Pandas UDFs, and `df.mapPartitions` with a custom function all break the optimizer's visibility into the operation — the resulting plans show up in `df.explain(true)` with `*(1) Scan ExistingRDD` instead of `FileScan parquet`, and there is no pushed filter, no column pruning, and no codegen.

### The Tungsten Execution Engine: Off-heap memory management, binary cache-aware data layouts

Tungsten is the execution backend that takes Catalyst's physical plan and runs it with off-heap memory, a compact binary row format, and runtime code generation. Its motivation is JVM object overhead. A Java `String` of 10 characters occupies 48 bytes (12-byte object header + 12-byte `char[]` header + 12-byte `byte[]` for compact strings + alignment), versus the 10 bytes of actual UTF-8 payload. A `java.lang.Long` is 16 bytes (header + 8-byte value) vs. the 8 bytes of the underlying `long`. A `Tuple3[String, Long, Double]` with the above String takes roughly 24 (tuple) + 16 (Long box) + 24 (Double box) + 48 (String) = 112 bytes for what is logically 26 bytes of data. Spark processes billions of records per job; this 4× overhead is fatal for shuffle, sort, and join performance.

Tungsten's binary row format, `UnsafeRow`, is a fixed-length byte buffer (allocated via `sun.misc.Unsafe` for on-heap or `Platform.allocateDirectMemory` for off-heap) containing: a fixed-length header with a null-bit-set (1 bit per nullable field), a fixed-length region for fixed-size fields (8 bytes per `Long`/`Double`/`Int`/pointer-to-variable), and a variable-length region for strings, arrays, and binary blobs. Fields are accessed via `Unsafe.getLong(rowAddr + offset)` and `Unsafe.putLong(rowAddr + offset, value)` — no Java object allocation, no autoboxing. A row `(String, Long, Double)` with a 10-byte string takes 8 (null bits) + 24 (3 fixed slots: pointer+length for the string, long, double) + 10 (string bytes) = 42 bytes, vs. 112 as Java objects. The compactness also improves cache locality — a 64-byte cache line holds 1.5 such rows vs. 0.5 Java objects, so a hash-table probe hits L1 cache 3× more often.

The unified memory manager governs how executor heap is split. `spark.memory.fraction=0.6` reserves 60% of the JVM heap (`-Xmx`) for Spark's use (the other 40% is for user objects, UDF state, Python worker buffers); of that 60%, `spark.memory.storageFraction=0.5` is reserved for cached RDD blocks and broadcast variables, and the remaining 50% is execution memory (shuffles, joins, sorts, aggregations). Storage and execution can borrow from each other — if execution needs more, it evicts cached blocks; if storage needs more and execution is under pressure, blocks are spilled to disk rather than evicted. Off-heap memory (`spark.memory.offHeap.enabled=true`, `spark.memory.offHeap.size=2g`) allocates a separate byte buffer outside the JVM heap that the `TaskMemoryManager` carves into per-task pages; this is essential for large shuffles because it completely eliminates GC pressure on the shuffle data — a 10 GB shuffle that would otherwise trigger 30-second G1 pauses runs without any GC.

```text
Executor memory layout (spark.executor.memory=16g, overhead=4g, offHeap=2g):

  ┌─ JVM process (20 GB total = 16g heap + 4g overhead) ─────────────────┐
  │                                                                      │
  │  JVM heap (16 GB)                                                    │
  │  ┌───────────────────────────────────────────────────────────────┐  │
  │  │ Reserved (40%, ~6.4 GB)  — user objects, Python workers, UDFs │  │
  │  │ Spark usable (60%, ~9.6 GB)                                   │  │
  │  │  ┌─────────────────────────────────────────────────────────┐ │  │
  │  │  │ Storage (~50% of 9.6 = ~4.8 GB) — cached blocks, bcast  │ │  │
  │  │  │ Execution (~50% of 9.6 = ~4.8 GB) — shuffle, join, sort │ │  │
  │  │  │   (these two pools borrow from each other)              │ │  │
  │  │  └─────────────────────────────────────────────────────────┘ │  │
  │  └───────────────────────────────────────────────────────────────┘  │
  │  Off-heap (2 GB) — Tungsten pages, off-heap column vectors          │
  │  Overhead (4 GB — netty direct buffers, thread stacks, JNI)         │
  └──────────────────────────────────────────────────────────────────────┘
```

Whole-stage code generation is the final Tungsten trick. At physical planning, Catalyst's `CollapseCodegenStages` rule looks for chains of operators that support codegen (most do — `Filter`, `Project`, `HashAggregate`, `SortMergeJoin`'s scan side) and wraps them in a `WholeStageCodegenExec`. This operator generates a single Java source file containing one `processNext()` method whose body is the inlined code for all the wrapped operators — the filter predicate is inlined into the loop, the projection expressions are inlined, the aggregate update is inlined. Janino (a fast Java compiler) compiles this source to bytecode at runtime, the resulting class is loaded into the executor JVM, and the operator's `processNext()` runs as a single JIT-inlined method. The performance gain is roughly 2× over the non-codegen path because virtual calls are eliminated, branch prediction works better, and the JIT can inline the entire operator chain. The production failure mode for Tungsten is silent disablement: setting `spark.sql.tungsten.enabled=false` for "debugging" drops throughput 3-5×, and Python UDFs bypass codegen entirely because the Python worker call is opaque to the Java generator. The metric that reveals a codegen failure is the Spark UI's SQL plan graph showing operators tagged `*(1)` (codegen-supported) vs. `+- Exchange` (shuffle, always separate stage) vs. operators without the `*` prefix (no codegen — investigate why). `df.explain("formatted")` (Spark 3.0+) shows the codegen-supported chain explicitly.

```bash
# 1. Launch a local Spark cluster (1 driver, executors in-process) on your laptop
spark-submit --master "local[4]" --driver-memory 2g \
  --class org.apache.spark.examples.SparkPi \
  $SPARK_HOME/examples/jars/spark-examples_*.jar 1000

# 2. Inspect the driver / executor / cluster manager in the Spark UI
#    Open http://localhost:4040 while the above job runs:
#      - "Jobs" tab shows DAGScheduler output (stages per job, task counts)
#      - "Stages" tab shows task-level metrics (locality, GC time, shuffle bytes)
#      - "Executors" tab shows per-executor heap / off-heap / shuffle bytes
#      - "Storage" tab shows cached RDD partitions and memory usage

# 3. Submit the same job against YARN in cluster mode
spark-submit --master yarn --deploy-mode cluster \
  --num-executors 10 --executor-cores 4 --executor-memory 8g \
  --driver-memory 4g --conf spark.shuffle.service.enabled=true \
  --class com.example.UserEventsJob ./etl.jar /in /out

# 4. Submit against Kubernetes (driver and executors as pods)
spark-submit --master k8s://https://k8s:6443 --deploy-mode cluster \
  --conf spark.kubernetes.container.image=registry/spark:3.5.0 \
  --conf spark.executor.instances=20 --executor-memory=16g \
  --class com.example.UserEventsJob local:///opt/app.jar

# 5. Inspect Catalyst's plan for a real query
python -c "
from pyspark.sql import SparkSession, functions as F
spark = SparkSession.builder.appName('explain').getOrCreate()
df = spark.read.parquet('/opt/spark/examples/src/main/resources/users.parquet') \
        .filter(F.col('age') > 21) \
        .groupBy('country').agg(F.sum('salary').alias('total'))
df.explain(True)        # prints parsed, analyzed, optimized, physical plans
df.explain('formatted') # Spark 3.0+: shows codegen-supported chain
"

# 6. Reproduce the broadcast-join OOM failure mode
#    Set the broadcast threshold artificially low and join a large table:
python -c "
from pyspark.sql import SparkSession
spark = SparkSession.builder \\
  .config('spark.sql.autoBroadcastJoinThreshold', '1') \\
  .appName('no-broadcast').getOrCreate()
# Now even a 1 MB dimension table forces SortMergeJoin — watch the
# Spark UI show Exchange hashpartitioning() instead of BroadcastExchange.
"
```

## Key Takeaways

1. **The driver is a single point of failure; size it generously and enable YARN/K8s auto-restart.** A driver OOM kills the whole application; `--conf spark.yarn.maxAppAttempts=4` or a K8s `Deployment` is the recovery primitive. Heap must hold `BlockManagerMaster` registry + `LiveListenerBus` queue + accumulators; 8 GB is a sane floor for any non-trivial job.
2. **Catalyst only sees what you let it see — RDD escapes, Python UDFs, and `df.collect().toDF()` are all performance cliffs.** Check `df.explain("formatted")` for operators missing the `*(N)` codegen marker; that is the signal you have escaped the optimizer.
3. **Tungsten's binary row format and off-heap memory are why Spark is 5-10× faster than naive JVM code.** `spark.memory.offHeap.enabled=true` is non-negotiable for shuffle-heavy jobs > 100 GB; without it, the GC pauses cause task retries, which cause stragglers, which cause `spark.network.timeout` kills.
