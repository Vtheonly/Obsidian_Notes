# 08.03.04. Spark Structured Streaming

## What This Is

Spark Structured Streaming is the streaming API built on top of the DataFrame/SQL stack. It models an unbounded data source (a Kafka topic, a directory of arriving parquet files, a Kinesis stream, a socket) as an **unbounded table** — new events arrive as appended rows, and the same DataFrame operations (`filter`, `groupBy`, `join`, `withColumn`) that work on bounded DataFrames work on the unbounded one. Under the hood, the engine translates this logical "unbounded table" view into a sequence of **micro-batches**: a `StreamExecution` thread on the driver wakes up at every trigger interval (`Trigger.ProcessingTime(10s)`), constructs a batch DataFrame from the new source data since the last committed offset, runs the user's query as a regular batch job through Catalyst and Tungsten, writes the result to the sink, and commits the offset to the checkpoint location. The result is a streaming engine that gets to use the exact same optimizer, codegen, and shuffle machinery as batch Spark — at the cost of a latency floor set by the trigger interval (typically 100 ms-seconds).

This note sits on top of [[08.03.02. Apache Spark Architecture and Compute Engine]] (the executor/task/cluster machinery) and [[08.03.03. Spark Operations Partitioning and Shuffling]] (the partition mechanics that every micro-batch inherits), and it operationalizes the conceptual framework from [[08.03.01. Batch vs. Stream Processing Foundations]] — specifically the event-time vs. processing-time distinction, the windowing strategies (tumbling, sliding, session), and the watermark for late data. The four sub-sections below cover: (1) the micro-batch vs. continuous engine tradeoff, (2) the Kafka source/sink integration that is the dominant production pattern, (3) the windowing primitives and how they interact with output modes, and (4) the watermark mechanism that lets an event-time stream make progress despite late-arriving data.

## The Details

### Processing streaming data via micro-batches and continuous processing engines

The micro-batch engine is the default and is the only engine that supports the full Structured Streaming operator set. Its execution model is straightforward: a `StreamExecution` thread on the driver sleeps until the next trigger boundary (`Trigger.ProcessingTime(10s)`), then calls `source.getBatch(startOffset, endOffset)` to construct a batch DataFrame representing the new source data, runs the user's query (which is identical to a batch DataFrame query — same Catalyst plan, same Tungsten codegen, same shuffle mechanics), calls `sink.addBatch(batchId, batchDF)` to write the output, and commits `endOffset` to the checkpoint. If the batch takes longer than the trigger interval (e.g., trigger is 10 seconds, batch takes 30 seconds), the engine does not overlap batches — the next batch starts immediately after the previous one commits, so throughput is sustained but latency grows to "batch duration + trigger interval." `Trigger.Once()` is a special case that runs exactly one batch covering all available source data and then exits — useful for backfill, testing, or running a "streaming" job as a periodic cron task.

The continuous processing engine (added in Spark 2.3, still experimental) is the alternative for sub-100 ms latency. With `Trigger.Continuous("1 second")` (the `"1 second"` is the **checkpoint epoch interval**, not the processing latency), the driver launches long-running tasks that process events as they arrive without batching — each task is essentially a Rust-style event loop that calls `source.get()` for one record, applies the operator chain in-thread, and calls `sink.put()`. The achievable end-to-end latency is sub-millisecond, dominated only by the source's poll latency and the operator chain's per-record cost. The catch is that continuous mode supports only a restricted operator set: stateless map-like transformations (`map`, `filter`, `flatMap`, `select`) and a small subset of sources/sinks (Kafka source, Kafka sink, console sink, memory sink). Stateful aggregations, joins, and windowed computations are not supported because the long-running-task model cannot easily checkpoint operator state across a network shuffle. Continuous mode also has weaker consistency — it is at-least-once within an epoch (a task failure may re-emit records since the last epoch barrier) rather than the exactly-once guarantee that micro-batch provides via offset commit + idempotent sink.

```text
Micro-batch vs. continuous engine tradeoff:

  Engine         Latency         Throughput        Operator set          Consistency
  ───────────    ────────────    ──────────────    ──────────────────    ──────────────────
  Micro-batch    100ms - sec     High (batching)   Full (stateful)       Exactly-once
                 (trigger +      (amortized        (windows, joins,      (offset commit +
                  process time)   per-record cost)  aggregations,         idempotent sink)
                                                    deduplication)
  Continuous     < 1 ms - 10 ms  Lower (no         Stateless only        At-least-once
                 (per-record     batching          (map, filter,         (epoch-barrier
                  processing)     amortization)     flatMap, select)      checkpointing)
  Use micro-batch when: latency tolerance > 1 second, you need stateful aggregations
  Use continuous when:  latency tolerance < 100 ms, the query is map-only, you can
                        tolerate at-least-once (or build idempotency at the sink)
```

Checkpointing is what makes either engine recoverable. Every micro-batch (or every epoch in continuous mode) writes two things to the checkpoint location (a path on HDFS/S3/local-disk specified via `option("checkpointLocation", "/path/")`): (1) the **offsets** file, recording the source offset up to which the query has processed; (2) the **commit log** file, recording the batch IDs that have been fully written to the sink. On restart, `StreamExecution` reads the latest committed offset from the checkpoint, seeks the source to that offset, and resumes. Stateful operators (windowed aggregations, stream-stream joins, `mapGroupsWithState`) also write a third thing — the **state store** — which is a versioned key-value store backed by the local disk of the executor running the stateful operator (`StateStore.provider = HDFSBackedStateStoreProvider` by default; `= RocksDBStateStoreProvider` in Spark 3.2+ for state > 1 GB). The state store is checkpointed every micro-batch; on restart, it is reloaded from the checkpoint directory.

```python
from pyspark.sql import SparkSession
from pyspark.sql.streaming import Trigger

spark = SparkSession.builder.appName("streaming-engines").getOrCreate()

# Micro-batch — the default, supports all operators
micro = (spark.readStream.format("kafka")
         .option("kafka.bootstrap.servers", "broker:9092")
         .option("subscribe", "events").load()
         .groupBy("topic").count())

micro_query = (micro.writeStream
    .outputMode("complete")
    .format("console")
    .trigger(Trigger.ProcessingTime("10 seconds"))    # micro-batch every 10s
    .option("checkpointLocation", "/chk/micro")
    .start())

# Continuous — sub-100ms latency, map-only queries
spark.conf.set("spark.sql.streaming.continuous.enabled", "true")
cont = (spark.readStream.format("kafka")
        .option("kafka.bootstrap.servers", "broker:9092")
        .option("subscribe", "events").load()
        .selectExpr("CAST(value AS STRING) AS raw"))

cont_query = (cont.writeStream
    .format("console")
    .trigger(Trigger.Continuous("1 second"))          # epoch interval, not latency
    .option("checkpointLocation", "/chk/cont")
    .start())
```

The production failure mode for the engine choice is two-sided. The first failure is **trigger too small** — setting `Trigger.ProcessingTime("100ms")` on a query whose per-batch overhead (scheduler latency, sink commit, checkpoint write) is 200 ms means the engine spends 100% of its time on overhead and zero on actual data processing; throughput collapses to a few records per second. The rule of thumb is `trigger >= 5 × per-batch overhead`; measure the overhead with `Trigger.Once()` on a representative batch and multiply. The second failure is **continuous mode misapplied** — using it for a stateful aggregation that the engine silently downgrades (or rejects at runtime with `Continuous processing is not supported for the current query`). The metric that reveals the failure is the Structured Streaming UI's `processingRows-per-second` vs. `inputRows-per-second` ratio: if processing can never catch up with input, the trigger is too small or the cluster is undersized; if the query is in continuous mode and `numTotalStateRows` is climbing unboundedly, the operator is silently accumulating state because no watermark is configured.

### Source integration: Reading and writing streams directly to Apache Kafka topics

Kafka is the dominant source and sink for Structured Streaming in production. Reading from Kafka uses `spark.readStream.format("kafka")` with required options `kafka.bootstrap.servers` (a comma-separated broker list) and either `subscribe` (a comma-separated topic list) or `subscribePattern` (a Java regex matching topic names) or `assign` (a JSON string mapping topic → partition list for fine-grained control). The returned DataFrame has a fixed schema: `key` (binary), `value` (binary), `topic` (string), `partition` (int), `offset` (long), `timestamp` (timestamp), `timestampType` (int — 0 for `CreateTime`, 1 for `LogAppendTime`). The `timestamp` column is the Kafka record's timestamp, which is the producer's `CreateTime` by default — this is the column you typically pass to `withWatermark()` for event-time processing.

The offset management model is what makes the integration exactly-once. On the first start of a query, Structured Streaming uses `startingOffsets` to decide where in the topic to begin: `"earliest"` (from the beginning of the topic's retained log), `"latest"` (from the current tail, the default), or a JSON string `"""{"topicA":{"0":23,"1":-1},...}"""` (`-1` means "latest", `-2` means "earliest", any other number is an absolute offset). On subsequent restarts, the checkpoint overrides `startingOffsets` — the query resumes from the last committed offset, ignoring whatever you pass. The Kafka source maintains its own consumer group (named `<query-id>` by default, override with `option("kafka.consumer.group.id", "...")` in Spark 3.x+) for the purpose of rebalancing when partitions are added to the topic, but it does **not** commit offsets to Kafka's `__consumer_offsets` topic — it commits them to its own checkpoint. This is why running a "batch" Kafka consumer in the same consumer group as a Structured Streaming query is undefined behavior — the two offset-tracking mechanisms fight.

```python
# Kafka source — full option set
raw = (spark.readStream
    .format("kafka")
    .option("kafka.bootstrap.servers", "broker1:9092,broker2:9092,broker3:9092")
    .option("subscribe", "events,alerts")                  # multiple topics OK
    .option("kafka.security.protocol", "SASL_SSL")         # SASL/SSL auth
    .option("kafka.sasl.mechanism", "SCRAM-SHA-512")
    .option("kafka.sasl.jaas.config",
            "org.apache.kafka.common.security.scram.ScramLoginModule required "
            'username="svc" password="***";')
    .option("startingOffsets", "earliest")                  # FIRST START ONLY
    .option("failOnDataLoss", "true")                      # throw if retention expired
    .option("maxOffsetsPerTrigger", 100000)                # backpressure cap
    .option("kafka.consumer.group.id", "etl-events-v2")
    .load())

# Kafka sink — write a stream back to Kafka
out = (aggregated.writeStream
    .format("kafka")
    .option("kafka.bootstrap.servers", "broker1:9092")
    .option("topic", "events-aggregated")                  # OR set 'topic' column per-row
    .option("checkpointLocation", "/chk/kafka-sink")
    .option("kafka.acks", "all")                           # required for exactly-once
    .option("kafka.retries", "2147483647")
    .option("kafka.enable.idempotence", "true")
    .option("kafka.max.in.flight.requests.per.connection", "5")
    .start())
```

`failOnDataLoss` is the option that prevents the silent-data-loss failure mode. The default is `true`, which throws `StreamingQueryException` if the source is missing data the query expects to process — this happens when Kafka's retention has expired old segments before the query caught up (e.g., the streaming job was down for 8 hours, the topic retention is 6 hours, the first 2 hours of data is gone). Setting `failOnDataLoss=false` suppresses the exception and logs a warning, which means the query silently skips the missing data and continues from the current earliest offset — the dashboard looks healthy, but the data is gone. The default is correct for production; teams that flip it to `false` "to stop the alerts" are the same teams that discover three months later that a regulatory report is missing a day of data. The companion option is `maxOffsetsPerTrigger`, which caps the number of records fetched per micro-batch — this is Structured Streaming's backpressure mechanism, preventing a fast producer from overwhelming a slow consumer and causing unbounded batch sizes. Without it, a burst of 100 million Kafka records while the streaming job is restarting causes the next batch to scan all 100 million in one go, blowing past the executor's execution memory and OOMing.

The Kafka sink requires the DataFrame to have a `value` column (binary) and optionally `key` (binary), `topic` (string), `partition` (int), `headers` (array of structs), all of which control the corresponding Kafka producer field per-record. For exactly-once delivery, the sink uses Kafka's transactional producer API (`kafka.transactional.id` is auto-set per query) and commits the transaction after the checkpoint is written — downstream consumers reading with `isolation.level=read_committed` see only fully-committed batches. This means the Kafka sink requires `kafka.acks=all`, `kafka.retries>0`, and `kafka.enable.idempotence=true` (or a transactional id); any of these mis-configured silently downgrades to at-least-once. For sinks that have no native Structured Streaming writer (JDBC, Elasticsearch, Delta Lake pre-3.0, custom REST APIs), `foreachBatch((batchDF, batchId) => ...)` is the escape hatch — each micro-batch's DataFrame is exposed as a regular batch DataFrame that can be written with any batch sink. The catch is that `foreachBatch` callbacks must be **idempotent** — on restart, the last batch may be re-executed, so writing to a non-idempotent sink (e.g., an `INSERT` without an `ON CONFLICT` clause) produces duplicates.

```python
# foreachBatch — JDBC sink pattern (must be idempotent!)
def upsert_to_postgres(batch_df, batch_id):
    (batch_df.write
        .format("jdbc")
        .option("url", "jdbc:postgresql://db/events")
        .option("dbtable", "events")
        .option("user", "etl").option("password", "***")
        # Postgres UPSERT — idempotent on restart
        .option("query",
                "INSERT INTO events (event_id, user, amount, ts) "
                "VALUES (?, ?, ?, ?) ON CONFLICT (event_id) DO UPDATE "
                "SET amount = EXCLUDED.amount, ts = EXCLUDED.ts")
        .mode("append").save())

(joined.writeStream
    .foreachBatch(upsert_to_postgres)
    .option("checkpointLocation", "/chk/pg")
    .trigger(Trigger.ProcessingTime("30 seconds"))
    .start())
```

The production failure mode for Kafka integration is `startingOffsets=latest` on the first deploy of a new streaming job: the query starts from the current tail of the topic, skipping all backlog. If the upstream producer has been writing for hours and the backlog is a day's worth of events, those events are silently never processed — the checkpoint records "latest at deploy time" as the start, and the topic retention eventually expires them. The fix is to always set `startingOffsets=earliest` for a brand-new query and only switch to `latest` once you've confirmed the backlog is drained. The other failure is a non-idempotent `foreachBatch` sink on a JDBC database without an `ON CONFLICT` clause: on every restart, the last committed batch is re-written, producing duplicates that compound over weeks of rolling restarts. The metric that reveals this is row count in the sink table growing faster than the source topic's message count — a clear sign of duplicates.

### Windowed Computations: Tumbling Windows, Sliding Windows, Session Windows

Windowing is what makes aggregation on an unbounded stream tractable — without it, a `groupBy($"user").count()` would have to hold state for every distinct `user` forever, and the state store would grow unboundedly until the executor OOM'd. A window is a finite time range (or, less commonly, a count range) that bounds the aggregation's state. Spark Structured Streaming provides three window types via the `window(timeCol, windowDuration, slideDuration)` function (and `session_window(timeCol, gapDuration)` for session windows, added in Spark 3.2). The window column is a struct with two fields, `start` and `end`, both timestamps; it can be used in `groupBy` like any other column. The windowing is **event-time** by default — the time column you pass to `window()` is the event's timestamp as recorded in the data, not the wall-clock time at which Spark processed the event.

```python
from pyspark.sql import SparkSession, functions as F
from pyspark.sql.streaming import Trigger

spark = SparkSession.builder.appName("windows").getOrCreate()

events = (spark.readStream.format("kafka")
    .option("kafka.bootstrap.servers","broker:9092")
    .option("subscribe","events").load()
    .selectExpr("CAST(value AS STRING) AS json",
                "timestamp AS event_time"))    # Kafka record timestamp = event_time

# 1. Tumbling window — 5-minute non-overlapping
tumbling = (events
    .withWatermark("event_time", "10 minutes")
    .groupBy(F.window(F.col("event_time"), "5 minutes"), F.col("json"))
    .count())

# 2. Sliding (hopping) window — 10-minute window, advance every 5 minutes
sliding = (events
    .withWatermark("event_time", "10 minutes")
    .groupBy(F.window(F.col("event_time"), "10 minutes", "5 minutes"), F.col("json"))
    .count())

# 3. Session window (Spark 3.2+) — close after 5 minutes of inactivity per key
session = (events
    .withWatermark("event_time", "10 minutes")
    .groupBy(F.session_window(F.col("event_time"), "5 minutes"), F.col("json"))
    .count())
```

```text

  Tumbling  (window="5 minutes"):
    [00:00, 00:05)  [00:05, 00:10)  [00:10, 00:15)  [00:15, 00:20)
       ●●●●●           ●●●             ●●●●●●           ●●●
    One window per event. Cheapest. Use for fixed-period reporting
    ("requests per 5 minutes"). Closes 5 minutes + watermark after 00:00.

  Sliding  (window="10 minutes", slide="5 minutes"):
    [00:00, 00:10)         [00:05, 00:15)         [00:10, 00:20)
       ●●●●●●●●●●             ●●●●●●●●●●             ●●●●●●●●●●
    Each event belongs to up to ceil(10/5)=2 windows.
    Use for "moving average over the last 10 minutes, updated every 5."

  Session  (session_window="5 minutes"):
    User A: ●●●  (gap 7m)  ●●●●●          (gap 6m)  ●●
            [00:00, 00:02]  [00:09, 00:14]          [00:20, 00:22]

```

The **output mode** is the second key decision after the window type, and it controls what the sink sees:

- **`append`** (default for non-aggregation queries) — a row is emitted only once, after it can no longer change. For aggregations with watermarks, this means the row is emitted only when the window closes (when the watermark crosses the window's end). Latency = window duration + watermark delay; throughput = "rows per closed window per trigger."
- **`update`** — only rows that have changed since the last trigger are emitted. For aggregations, the running count is emitted every trigger (e.g., every 10 seconds), and a final update is emitted when the window closes. Latency = trigger interval; throughput = "changed rows per trigger." This is the right mode for real-time dashboards that want a live count.
- **`complete`** — the entire result table is emitted every trigger, regardless of what changed. Only feasible for low-cardinality aggregations (e.g., `groupBy($"country")` with 200 countries); for high-cardinality aggregations (`groupBy($"user_id")` with 10 million users), the state grows unboundedly and the executor OOMs within minutes.

```text
Output mode × aggregation × watermark interaction:

  Aggregation?   Watermark?   Output mode   Behavior
  ────────────   ──────────   ───────────   ──────────────────────────────────────
  No             —            append        (default) emit each input row once
  Yes            Yes          append        emit window result ONLY when window closes
  Yes            Yes          update        emit changed rows every trigger + final
  Yes            Yes          complete      emit full result every trigger (low-card only)
  Yes            No           append        ERROR — engine cannot know when window closes
  Yes            No           update        works but state grows unboundedly → OOM eventually
  Yes            No           complete      works but state grows unboundedly → OOM eventually
```

The interaction with watermark is what makes `append` mode work — without a watermark, the engine has no way to know that a window's last event has arrived, so it cannot emit a "final" result and must hold the window's state forever. The protocol enforces this: `append` mode on an aggregation query without a watermark throws `AnalysisException: Detected pattern of "append" output mode without watermark. StreamWithoutWatermark`. The production failure mode is the other direction: `complete` mode on a high-cardinality aggregation — the engine accepts it, runs fine in dev with 100 keys, then in production with 10 million keys the state store fills the executor heap in 30 seconds and OOMs. The fix is to use `update` mode + watermark, which limits state retention to (window duration + watermark delay) × cardinality. The other failure is **sliding-window state multiplication**: a sliding window of 60 minutes advancing every 1 minute keeps `ceil(60/1) = 60` active windows per key at any time, multiplying the state by 60×. The metric that reveals it is the Structured Streaming UI's `numTotalStateRows` — if it climbs past `expected_keys × active_windows × 2`, your sliding window is over-provisioned; consider a larger slide interval or a tumbling window instead.

### Watermarking: Handling out-of-order and late-arriving network data

The watermark is the mechanism that lets an event-time stream make progress despite the certainty that some events will arrive out of order. A watermark is a threshold the engine maintains: "I will not accept any event whose `event_time` is older than `watermark`." The engine computes the watermark as `max_event_time_seen - max_lateness_allowed`, where `max_lateness_allowed` is the duration you pass to `withWatermark("event_time", "10 minutes")`. As the engine processes events, it tracks the maximum `event_time` it has seen so far (`max_event_time_seen`); the watermark advances as `max_event_time_seen` advances. When the watermark crosses a window's end timestamp, the engine knows no more events for that window will be accepted (any event arriving with `event_time < watermark` is dropped, optionally routed to a side output), so it can finalize the window, emit the final result (in `append` mode), and free the window's state.

```text
Watermark computation, 5-minute tumbling windows, withWatermark("et", "10 min"):

  Event arrives  Event_time     max_seen      watermark = max - 10min   Action
  ───────────    ──────────     ────────      ──────────────────────    ──────────────
  e1 (12:00:30)  12:00:30       12:00:30      11:50:30                  accept; window [12:00,12:05)
  e2 (12:01:15)  12:01:15       12:01:15      11:51:15                  accept; window [12:00,12:05)
  e3 (12:06:00)  12:06:00       12:06:00      11:56:00                  accept; window [12:05,12:10)
  e4 (12:11:00)  12:11:00       12:11:00      12:01:00                  accept; CLOSES window [12:00,12:05)
                                                            (watermark 12:01:00 > window end 12:05:00? NO — wait)
  e5 (12:16:00)  12:16:00       12:16:00      12:06:00                  accept; CLOSES window [12:00,12:05)
                                                            (watermark 12:06:00 ≥ window end 12:05:00 → emit + free state)
  e6 (12:17:00)  event_time=12:00:30 — LATE!  12:06:00 watermark        DROPPED (event_time 12:00:30 < watermark 12:06:00)

  Window [12:00,12:05) is held open until watermark ≥ 12:05:00,
  i.e., until an event with event_time ≥ 12:15:00 arrives (12:05 + 10min watermark).
  This is the "late event tolerance" — events up to 10 minutes late are accepted.
```

The output-mode interaction matters because it changes when the engine emits results. In `append` mode, the engine emits the window's final result only when the watermark crosses the window's end — the dashboard sees the count for `[12:00, 12:05)` at 12:16:00 (when `e5` arrives with `event_time=12:16:00` and pushes the watermark to `12:06:00`), which is 11 minutes after the window nominally closed. This is the cost of late-event tolerance: result latency = window duration + watermark delay. In `update` mode, the engine emits the running count every trigger — the dashboard sees partial counts for `[12:00, 12:05)` at 12:00:30, 12:01:15, etc., and a final update at 12:16:00 when the window closes. `update` mode is the right choice for live dashboards; `append` mode is right for downstream consumers that need the final, never-to-change number (e.g., a billing record).

Choosing the watermark threshold is the most consequential tuning decision in a streaming pipeline. Too tight (e.g., `withWatermark("event_time", "10 seconds")` when the upstream pipeline has a 5-minute tail latency) and the engine drops most events as late — the dashboard shows a steep throughput drop, the `numDroppedRows` metric climbs, and nobody notices for a week because no error is logged. Too loose (e.g., `withWatermark("event_time", "1 hour")` when the actual skew is 30 seconds) and the engine holds every window's state for 1 hour × window-duration × cardinality — for a 5-minute window with 1 million distinct keys, that's 12 active windows × 1 million keys = 12 million state entries, each potentially a few hundred bytes, easily 5-10 GB of state, which OOMs the executor. The correct method is empirical: run a query that measures `(processing_time - event_time)` for the source stream over 24 hours of production traffic, take the 99th percentile, multiply by 2-3 for safety, and use that as the watermark. The 2-3× safety factor accounts for the fact that the 99th percentile is itself an estimate and that pipeline degradation under load can push latencies above the steady-state P99.

```python
# Measure event-time skew in production before setting the watermark
skew = (spark.read.format("kafka")
    .option("kafka.bootstrap.servers","broker:9092")
    .option("subscribe","events")
    .option("startingOffsets","earliest")
    .load()
    .selectExpr("timestamp AS kafka_time")
    .withColumn("processing_time", F.current_timestamp())
    .selectExpr("(unix_timestamp(processing_time) - unix_timestamp(kafka_time)) AS skew_seconds"))

skew.describe("skew_seconds").show()
#  +-------+------------------+
#  |summary|      skew_seconds|
#  +-------+------------------+
#  |  mean |           12.345|
#  | stddev|            5.678|
#  |    min |              0.1|
#  |    max |          1876.5|   ← 99th percentile around 30 seconds → watermark = 2 minutes
#  +-------+------------------+

# Then set the watermark based on the measurement:
streamed = (events
    .withWatermark("event_time", "2 minutes")    # P99 skew × 4
    .groupBy(F.window(F.col("event_time"), "5 minutes"), F.col("user"))
    .count())
```

The multi-stream watermark stall is the subtle failure mode that bites teams with stream-stream joins. If a query reads from two Kafka topics (e.g., `impressions` and `clicks` to join them), each with its own `withWatermark`, the global watermark is the **minimum** of the per-stream watermarks — the engine cannot make progress on the join past the slower stream's watermark, because the slower stream might still produce an event that matches a buffered event from the faster stream. If one stream stalls (the producer goes down, the consumer group rebalances, the network partitions), the global watermark stalls, every window in both streams stays open, and the state store grows until OOM. The fix is monitoring: alert on `eventTime.watermark` flatlining for more than N minutes. The metric that reveals the failure is the Structured Streaming UI's `eventTime.watermark` graph — under normal operation it advances monotonically with the trigger; a flat line for more than the watermark duration is a stalled query that will OOM within the hour. The other watermark failure is silent drops on a too-tight threshold: monitor `numDroppedRows` per trigger and alert if it exceeds 0.1% of `inputRows` — anything higher means the watermark is wrong or the upstream pipeline is degraded.

## Hands-On Exercise

```bash
# 1. Run a Kafka-to-Kafka pipeline with windowed aggregation
python -c "
from pyspark.sql import SparkSession, functions as F
from pyspark.sql.streaming import Trigger
```

## Key Takeaways

1. **The trigger interval is a latency-vs-overhead dial; the watermark is a completeness-vs-memory dial.** A trigger of `ProcessingTime("10s")` gives 10-20 second latency at ~5% overhead; smaller triggers spend their budget on scheduler overhead. A watermark of `"2 minutes"` accepts events up to 2 minutes late but holds state for `window_duration + 2 minutes` per key — measure P99 skew with `df.describe()` and multiply by 2-3× rather than guessing.
2. **Kafka integration requires `failOnDataLoss=true`, `startingOffsets=earliest` on first deploy, and `kafka.enable.idempotence=true` on the sink — flipping any of these "to stop the alerts" silently loses data.** The Kafka source does not commit offsets to `__consumer_offsets`; the checkpoint is the source of truth, and the checkpoint must be on reliable storage (HDFS/S3, not local disk).
3. **`complete` output mode on a high-cardinality aggregation is the most common streaming OOM; `append` mode without a watermark is the most common streaming AnalysisException.** Use `update` mode + watermark for live dashboards (low latency, bounded state), `append` mode + watermark for downstream consumers that need final numbers (higher latency, smallest sink traffic).
