# 08.03.03. Spark Operations Partitioning and Shuffling

## What This Is

Every Spark job is a graph of operations on partitioned data. The **partition** is the atomic unit of parallelism — a slice of a distributed collection that one task processes end-to-end on one executor. Spark's operations come in two flavors: **transformations**, which return a new partitioned collection and record an edge in the dependency graph but execute nothing, and **actions**, which trigger the driver to walk that dependency graph backward, cut it into stages delimited by shuffle boundaries, and submit one wave of tasks per stage. The fundamental performance question in any Spark job is *how many shuffles does it require*, because a shuffle is the only operation that moves data across the network, serializes records to disk, and forces downstream stages to wait on upstream completion. This note drills into the partition → transformation → shuffle pipeline that [[08.03.02. Apache Spark Architecture and Compute Engine]] set up at the executor level, and that [[08.03.04. Spark Structured Streaming]] will re-invoke every micro-batch trigger.

A **narrow transformation** (map, filter, flatMap, union, mapPartitions, coalesce) is one where each parent partition contributes to exactly one child partition — no network I/O, no disk spill, fully pipelined into a single stage. A **wide transformation** (groupByKey, reduceByKey, join without co-partitioning, distinct, repartition, sortByKey) is one where each parent partition may contribute to many child partitions — this forces a **shuffle**: the parent stage writes its output to local disk sorted by reducer partition, and the child stage fetches its partition from every parent task across the network. The DAGScheduler finds every wide dependency in the lineage graph and cuts a stage boundary at it; the resulting stages run sequentially (parent must finish before child starts), and within a stage all narrow transformations are fused into a single task per partition. This is why a job with one `join` has two stages and a job with two sequential `join`s has three — the wide dependencies are the cost.

## The Details

### Transformations (Lazy Evaluation) vs. Actions (Triggering computation)

Spark's API distinguishes **transformations** (which build up a logical plan but execute nothing) from **actions** (which submit the plan to the `DAGScheduler` for execution). A transformation returns a new `RDD` or `DataFrame` whose `dependencies` list records the parent; an action returns a non-RDD value (`Array`, `Long`, `Unit`) or writes external output and forces the entire upstream chain to materialize. The laziness is not a stylistic preference — it is the property that lets Catalyst see the entire query before executing, push filters below joins, prune columns at the source read, and choose the cheapest join strategy based on the full predicate structure. If transformations were eager, every `df.filter(...)` would trigger a full scan, every `df.select(...)` would re-read the source, and the optimizer would have no opportunity to compose the operations.

The common transformations and actions:

```text
Transformations (lazy, return new DataFrame/RDD):
  map, flatMap, filter, mapPartitions, mapPartitionsWithIndex   (narrow)
  union, intersection, distinct, subtract                       (narrow / wide*)
  join, leftOuterJoin, rightOuterJoin, fullOuterJoin            (wide unless co-part)
  groupBy, groupByKey, reduceByKey, aggregateByKey              (wide)
  repartition, coalesce, sortBy, orderBy                        (wide / narrow)
  select, withColumn, drop, alias, distinct                     (narrow)
  cache, persist, checkpoint                                    (control plane)

Actions (eager, trigger DAG):
  collect()                       → Array[Row]    (driver memory!)
  count()                         → Long
  take(n), head(n), first()       → Array[Row]
  reduce(f)                       → T
  foreach(f)                      → Unit          (per-row side effect on executor)
  foreachBatch(f)                 → Unit          (streaming: per-microbatch DataFrame)
  write.format(...).save(path)    → Unit          (commit to external sink)
  show(n)                         → Unit          (prints to driver stdout)
```

The DAG construction process works as follows. When an action is called, the `SparkSession` calls `DataFrame.queryExecution.executedPlan.execute()` which walks the physical plan, and the `RDD` layer's `DAGScheduler.submitJob` is invoked with the final RDD's `partitions` array and a `partitionFunc` for each. The `DAGScheduler` walks backward from the final RDD to the source, asking each RDD for its `dependencies`; each `ShuffleDependency` becomes a stage boundary, each `NarrowDependency` is left in the same stage. The result is a list of `Stage` objects where each stage's `parents` are the upstream shuffle-map stages it depends on. Within a stage, all the narrow transformations are *pipelined* — a single `Task` per partition reads the source partition, applies the chain of `map`/`filter`/`mapPartitions` calls, and writes the output (either to the next shuffle, or to the result handler). The action is what triggers this whole cascade; without it, the plan sits idle.

```scala
val rdd = sc.textFile("hdfs:///events")           // lazy: creates a HadoopRDD
  .filter(_.nonEmpty)                              // lazy: creates a FilteredRDD
  .map(_.split("\t"))                              // lazy: creates a MappedRDD
  .filter(_.length >= 3)                           // lazy: another FilteredRDD
  .map(parts => (parts(0), parts(2).toInt))        // lazy: MappedRDD
  .groupByKey()                                    // lazy: ShuffledRDD (wide dep!)
  .map { case (k, vs) => k -> vs.sum }             // lazy: MappedRDD

// NOTHING HAS RUN YET — Spark has just built the lineage graph.
// The DAGScheduler has not been called. No tasks have been launched.

rdd.count()    // ACTION — now the DAGScheduler walks the lineage,
               // cuts at the groupByKey() ShuffleDependency, builds two stages,
               // submits Stage 0 (textFile→filter→map→filter→map→shuffleWrite),
               // waits for it to finish, then submits Stage 1 (shuffleRead→map→count).
```

The production failure mode for laziness is two-sided. The first failure is *accidental eager evaluation*: calling `df.count()` "just to check it loaded" on a 10 TB DataFrame triggers a full scan, wasting an hour of cluster time; calling `df.show()` (which by default shows 20 rows) triggers full DAG execution up to and including a `take(20)`, which on a skewed dataset may scan a whole partition to find 20 valid rows. The fix is to use `df.printSchema()` for schema checks (no execution) and `df.limit(20).show()` only after you have confirmed the source is bounded. The second failure is *long lineage chains*: a job that does 50 transformations without `cache()` builds a 50-deep lineage; if an executor fails mid-job, the driver re-computes the lost partition by walking all 50 transformations from the last cached ancestor, multiplying runtime by the recompute factor. The fix is to call `df.cache()` after each major sub-result and `df.unpersist()` when done with it — but note that `cache()` is itself lazy; you must call an action (`df.count()`) to materialize the cache. The metric that reveals a long-lineage problem is the Spark UI's "Task Retry" count climbing after a single executor loss — each retried task takes the full stage depth to recompute.

### Narrow Dependencies (map, filter - no data exchange across partitions) vs. Wide Dependencies (groupByKey, join - requiring data shuffling).

The narrow-vs-wide distinction is the single most important property of an RDD dependency because it determines whether the `DAGScheduler` can pipeline operations into one stage or must cut a stage boundary. **Narrow dependencies** are those where each parent partition contributes to exactly one child partition: `map(f)` (1:1, partition `i` of parent → partition `i` of child), `filter(p)` (1:1, but the child partition may be smaller), `flatMap(f)` (1:1, but the child partition may have more elements), `union(other)` (N:1 — child partition `i` is the union of parent-1 partition `i` and parent-2 partition `i`, both at the same index), `mapPartitions(f)` (1:1, function sees the whole partition as an iterator), and `coalesce(n)` when n is smaller than the current partition count and `shuffle=false` (N:1, adjacent partitions merged). Narrow dependencies require **no network I/O** and **no disk spill** — the child partition lives on the same executor as its parent, the task reads the parent's iterator and writes the child's iterator in the same JVM thread.

**Wide dependencies** are those where each parent partition may contribute to many child partitions: `groupByKey()` (every parent partition may contain records for every key in every child partition), `reduceByKey(f)` (same, but with a map-side combine to reduce volume), `aggregateByKey`, `join` (when the two sides are not co-partitioned — the join requires shuffling both sides to the same partitioner), `distinct` (shuffles to deduplicate across partitions), `repartition(n)` (always shuffles to redistribute), `sortByKey` (shuffles to a `RangePartitioner`), `intersection` (shuffles both sides). Wide dependencies require a **shuffle**: each parent task writes its output to local disk sorted by (reducer partition ID, key), and each reducer task fetches its partition's data from every parent task across the network.

```text
Narrow dependency — pipelined in one stage, no shuffle:

  Parent RDD partitions              Child RDD partitions (same stage)
  ┌──────────────┐                   ┌──────────────┐
  │ Partition 0  │ ─── map(f) ───▶   │ Partition 0  │   (1:1, same executor)
  ├──────────────┤                   ├──────────────┤
  │ Partition 1  │ ─── filter(p) ─▶  │ Partition 1  │   (1:1, subset of rows)
  ├──────────────┤                   ├──────────────┤
  │ Partition 2  │ ─── flatMap ───▶  │ Partition 2  │   (1:1, more rows)
  └──────────────┘                   └──────────────┘

Wide dependency — stage boundary, shuffle required:

  Stage 0 (map-side):                  Stage 1 (reduce-side):
  ┌──────────────┐    write to local    ┌──────────────┐
  │ Partition 0  │ ──┐ disk sorted by  ┌─▶ Partition 0 │  (keys hash to 0)
  ├──────────────┤   │   reducer ID   │  ├──────────────┤
  │ Partition 1  │ ──┼──────────────▶ ├──▶ Partition 1 │  (keys hash to 1)
  ├──────────────┤   │  fetch via     │  ├──────────────┤
  │ Partition 2  │ ──┘  Netty/HTTP    └─▶ Partition 2 │  (keys hash to 2)
  └──────────────┘                     └──────────────┘
   (every parent task writes         (every child task fetches from
    data for every reducer)            every parent task)
```

The classic antipattern is `groupByKey` for an aggregation. `rdd.groupByKey()` shuffles *every record* across the network — for a 1 TB dataset with 1 billion records and 10 million distinct keys, all 1 TB of data crosses the network and lands in reducer memory before the user's aggregation function runs. `rdd.reduceByKey(_ + _)` does the same shuffle but performs a **map-side combine** first — each parent task locally aggregates records with the same key before writing to shuffle, so only `(key, partial_sum)` pairs cross the network. For sum/min/max/count aggregations, `reduceByKey` is 10-100× cheaper than `groupByKey` because the shuffle volume drops from O(records) to O(distinct_keys_per_partition). The `groupByKey` version is only correct when the aggregation is non-associative (e.g., building a list per key where the list order matters), which is rare.

```scala
// WRONG: ships every record across the network
val totals = pairs.groupByKey().mapValues(_.sum)

// RIGHT: map-side combine reduces shuffle volume by ~100x for high-cardinality keys
val totals = pairs.reduceByKey(_ + _)

// The plans differ visibly:
//   reduceByKey:  ShuffledRDD[reduce at ...] (with MapSideCombine=true)
//   groupByKey:   ShuffledRDD[group at ...]  (MapSideCombine=false)
```

The other optimization is the **co-partitioned join**. If two RDDs already share the same `Partitioner` (e.g., both were produced by `reduceByKey` with the same number of partitions, or both had `repartition(200, $"key")` called on them with the same key), then `rdd1.join(rdd2)` becomes a **narrow** dependency — partition `i` of `rdd1` joins with partition `i` of `rdd2` locally, no shuffle. Without co-partitioning, both sides must be shuffled to a common partitioner, doubling the shuffle cost. The production failure mode is the opposite: a join on two large tables where one side was loaded with `repartition(2000)` and the other with `repartition(4000)` — Catalyst cannot know they share a partitioner, so it inserts two shuffles. The fix is to use `df1.repartition(4000, $"key")` and `df2.repartition(4000, $"key")` explicitly, then join; or use `df.hint("broadcast")` if one side fits in `spark.sql.autoBroadcastJoinThreshold`. The metric that reveals a missed co-partitioning is the Spark UI's Stage graph showing two `Exchange` nodes feeding into a `SortMergeJoin` when one `Exchange` should suffice.

### The Shuffling Bottleneck: Network I/O and disk serialization during wide transformations

A shuffle is the most expensive operation in Spark, and the reason is that it touches every scarce resource simultaneously: network bandwidth, disk I/O, JVM heap (for sort buffers), and executor CPU (for serialization). The mechanics are split into **shuffle write** (the map side) and **shuffle read** (the reduce side). On the map side, each parent task iterates its partition, hashes each record's key to a reducer partition ID in `[0, numPartitions)`, and appends the serialized `(partition ID, key, value)` to an in-memory buffer for that reducer. When the buffer fills (default `spark.shuffle.file.buffer=32 KB`), it is spilled to a file in `spark.local.dir` (default `/tmp` — change this in production!). When the task finishes, all spilled files for one reducer are merged into a single sorted run, and an index file records the byte offset for each reducer partition. The output is one `shuffle_<mapId>_0.data` file plus one `shuffle_<mapId>_0.index` file per map task — for `M` map tasks and `R` reducers, that's `M` data files and `M` index files (the "M files" model, post-Spark-1.6 sort-based shuffle; pre-1.6 it was `M × R` files, which broke NameNode on large jobs).

On the reduce side, each reducer task knows which map outputs it needs (the driver's `MapOutputTrackerMaster` tells it). The reducer opens `M` parallel HTTP/Netty connections to fetch its slice from each map task's data file — the byte range is read from the index file, the slice is streamed over the network, and the reducer's `ExternalAppendOnlyMap` or `Sorter` merges them with a priority queue keyed by `(partition ID, key)`. If the merge exceeds `spark.sql.shuffle.partitions × record_size` > execution memory, the reducer spills its intermediate merge state to disk and does a final merge pass at the end. The combined cost is `M × R` byte-range reads from disk on the map side, `M` network fetches per reducer on the reduce side, and one or more spill-merge passes on both sides. For a 1 TB shuffle with 200 mappers and 400 reducers, that's 200 × 400 = 80,000 disk reads on the map side and 400 × 200 = 80,000 network fetches on the reduce side.

The **external shuffle service** (ESS) is the production-grade solution to the "executor dies mid-shuffle" problem. ESS is a long-running daemon process (on YARN: a `spark-<version>-yarn-shuffle.jar` registered as a YARN auxiliary service named `spark_shuffle` on every NodeManager; on K8s: a `DaemonSet` running the same jar) that serves shuffle files independently of the executor that wrote them. With `spark.shuffle.service.enabled=true`, the map-side executor writes shuffle files to its local disk as before, but the reduce-side fetches go to the ESS daemon (which reads from the same local disk) rather than to the executor's Netty server. If the map-side executor is killed (YARN preemption, K8s pod eviction, OOM), the ESS daemon continues serving its shuffle files — the reducer task is unaffected. Without ESS, losing a map-side executor mid-shuffle forces the driver to re-launch the lost map tasks and re-write their shuffle output, which can double the wall-clock time of a job under cluster pressure. ESS is mandatory for dynamic allocation (`spark.dynamicAllocation.enabled=true`), because dynamic allocation freely kills idle executors — without ESS, killing an idle executor that still had shuffle output would break every downstream reducer.

```text
Shuffle with external shuffle service (YARN):

  NodeManager (YARN daemon)
  ├─ ESS process (spark_shuffle auxiliary service, port 7337)
  ├─ Executor 1 (JVM)             Executor 2 (JVM)
  │   ├─ Task 0 writes            │   ├─ Task 0 writes
  │   │   shuffle_0_0.data ─┐     │   │   shuffle_1_0.data ─┐
  │   │   shuffle_0_0.index │     │   │   shuffle_1_0.index │
  │   └─ Task 1 ...          │     │   └─ Task 1 ...          │
  │                          ▼     ▼                          ▼
  │  Local disk: /yarn/nm-local-dir/usercache/.../app-attempt-1/
  │     shuffle_0_0.data, shuffle_0_0.index,
  │     shuffle_1_0.data, shuffle_1_0.index, ...
  │                              ▲
  └─ ESS reads from local disk ──┘
                              │
                              │ HTTP/Netty fetch
                              ▼
  Reducer task on another NodeManager:
    fetch http://nm-1:7337/shuffle/...?offset=...&length=...
```

The shuffle partition count is the most-tuned knob in Spark SQL: `spark.sql.shuffle.partitions` (default 200). Too few and each reducer handles too much data — the reducer's `ExternalAppendOnlyMap` spills constantly, or worse, OOMs; too many and each task processes only a few records, the per-task overhead (scheduling, JVM warmup, serialization round-trip) dominates, and the NameNode pressure from `M × R` small index files becomes visible on HDFS-backed jobs. The rule of thumb is `shuffle.partitions ≈ total_executor_cores × 2-4` so that each task processes 100-500 MB of shuffle data. For a 1 TB shuffle on a 200-core cluster, that's `200 × 4 = 800` partitions → ~1.25 GB per partition, which fits comfortably in a 16 GB executor's execution memory.

```text
Shuffle cost breakdown (1 TB shuffle, 200 mappers, 800 reducers, 10 Gbps network):

  Phase                       Bytes moved          Time
  ───────────────────────     ──────────────       ──────────────
  Map-side write to disk      1 TB (serialized)    ~15 min (disk-bound at 200 MB/s/task)
  Network transfer            1 TB (compressed)    ~10 min (10 Gbps × 200 = 2 Tbps aggregate)
  Reduce-side merge           1 TB (read+write)    ~15 min (disk-bound)
  Total wall-clock            —                    ~40 min if pipeline is well-balanced
                                                              ~2 hr if any task is a straggler
```

The production failure mode is **data skew** — one reducer partition receives 80% of the records because the key distribution is not uniform (e.g., a `groupByKey` on a `user_id` column where one user has 100× the activity of any other). The straggler reducer takes 10× as long as its peers, and the whole stage waits for it. The Spark UI shows this as a task duration histogram with a long right tail — 199 tasks finish in 5 minutes, one task takes 50 minutes. The fixes, in order of preference: (1) **broadcast join** — if one side of the join is small enough (`< spark.sql.autoBroadcastJoinThreshold`, default 10 MB, raise to `1g` if you have driver headroom), Catalyst broadcasts it to every executor and skips the shuffle entirely; (2) **salting** — add a random suffix `0..9` to the skew key on both sides of the join, so the skew is distributed across 10 partitions, then aggregate the partial results; (3) **Adaptive Query Execution (AQE)** in Spark 3.0+ — `spark.sql.adaptive.enabled=true` plus `spark.sql.adaptive.skewJoin.enabled=true` lets Catalyst detect skew at runtime (after the map side finishes and the actual per-partition sizes are known) and split the oversized partition into sub-partitions dynamically. AQE is the single biggest shuffle-skew win in modern Spark; enable it by default unless you have a specific reason not to.

## Hands-On Exercise

```bash
# 1. Observe narrow vs wide stages in the Spark UI
python -c "
from pyspark.sql import SparkSession, functions as F
spark = SparkSession.builder.appName('stages').getOrCreate()
df = spark.read.parquet('/data/events')            # 1 stage: scan
filtered = df.filter(F.col('amount') > 100)        # fused with scan (narrow)
grouped = filtered.groupBy('user').agg(F.sum('amount').alias('total'))  # wide!
grouped.write.parquet('/out/totals')               # action: triggers 2-stage DAG
# Open http://localhost:4040 → Stages tab → observe 2 stages, the second
# has an 'Exchange' node indicating a shuffle.
"

# 2. Compare groupByKey vs reduceByKey shuffle volume
python -c "
from pyspark.sql import SparkSession, functions as F
spark = SparkSession.builder.appName('shuffle-volume').getOrCreate()
pairs = spark.read.parquet('/data/events').select('user','amount').rdd \\
        .map(lambda r: (r.user, r.amount))
# reduceByKey: map-side combine
rbk = pairs.reduceByKey(lambda a,b: a+b)
# groupByKey: no combine, ships every record
gbk = pairs.groupByKey().mapValues(sum)
rbk.count()  # note 'Shuffle Bytes' in Spark UI
gbk.count()  # note 'Shuffle Bytes' — should be ~100x larger
"

# 3. Reproduce data skew
python -c "
from pyspark.sql import SparkSession, functions as F
spark = SparkSession.builder.appName('skew').getOrCreate()
# 1 million rows for user 'a', 100 rows each for users 'b'..'z'
skewed = spark.range(1000000).select(F.lit('a').alias('user'),'1.0'.cast('double').alias('amount')) \\
    .union(spark.range(100).select(F.lit('b').alias('user'),'1.0'.cast('double').alias('amount')))
skewed.groupBy('user').agg(F.sum('amount')).collect()
# Watch the Stages tab: one reducer task takes seconds, the rest take milliseconds.
"

# 4. Enable Adaptive Query Execution to auto-fix skew
spark.conf.set('spark.sql.adaptive.enabled', 'true')
spark.conf.set('spark.sql.adaptive.skewJoin.enabled', 'true')
spark.conf.set('spark.sql.adaptive.advisoryPartitionSizeInBytes', '128m')
# Now re-run the above — the skewed partition is split at runtime into sub-partitions.

# 5. Inspect shuffle files on disk
ls -lh /tmp/blockmgr-*/   # default spark.local.dir — change this in production!
# Look for: shuffle_<mapId>_0.data and shuffle_<mapId>_0.index files.

# 6. Enable the external shuffle service
spark-submit --conf spark.shuffle.service.enabled=true \\
  --conf spark.dynamicAllocation.enabled=true \\
  --conf spark.dynamicAllocation.minExecutors=5 \\
  --conf spark.dynamicAllocation.maxExecutors=50 \\
  --class com.example.Job ./app.jar
# Verify in the Spark UI: idle executors are killed, shuffle output continues to be served.
```

## Key Takeaways

1. **The number of shuffles is the single biggest predictor of job wall-clock.** Each wide dependency cuts a stage boundary and forces a network + disk round-trip. Rewrite `groupByKey` as `reduceByKey`, use `broadcast` joins for small dimensions, and co-partition tables that join repeatedly — these three changes typically cut a 2-hour job to 20 minutes.
2. **Data skew is invisible until you look at the task-duration histogram.** The Spark UI's Stages tab shows min/median/max task time; if `max / median > 3`, you have skew. Enable AQE (`spark.sql.adaptive.skewJoin.enabled=true`) as the default fix; salt skew keys explicitly when AQE cannot apply (e.g., custom aggregations).
3. **The external shuffle service is non-negotiable for production YARN/K8s deployments.** Without it, executor preemption or dynamic-allocation kills break mid-shuffle reducers, and the driver must re-launch the lost map tasks — wall-clock doubles under cluster pressure. ESS + dynamic allocation lets the cluster elastically scale between `minExecutors` and `maxExecutors` without breaking shuffle correctness.
