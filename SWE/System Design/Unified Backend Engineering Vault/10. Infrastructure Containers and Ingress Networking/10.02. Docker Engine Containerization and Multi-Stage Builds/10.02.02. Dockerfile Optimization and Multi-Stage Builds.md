# 10.02.02. Dockerfile Optimization and Multi-Stage Builds

## What This Is

A Dockerfile is a recipe for building a container image: each instruction (`FROM`, `RUN`, `COPY`, `ENV`, `CMD`) produces one read-only layer that the Docker daemon stacks on top of the previous layers via OverlayFS. The choices you make in that recipe decide the image's size, its build time on the 50th rebuild, the attack surface that escapes to production, and whether your CI pipeline takes 9 seconds or 9 minutes per push. This note is the engineering discipline of writing Dockerfiles that produce small, cacheable, secure images — and the multi-stage build technique that makes that discipline achievable in practice.

The deep insight is that the toolchain required to *compile* an artifact is rarely the toolchain required to *run* it. A Spring Boot service needs Maven, the JDK, git, and possibly a build cache to produce a 40 MB `app.jar`, but only a JRE to run that same jar. A Go service needs the entire Go toolchain (~500 MB) to compile a statically-linked binary, but only `FROM scratch` (literally 0 MB of base image) to run it. A Python service needs `pip`, `gcc`, and `-dev` headers to install wheels that contain compiled C extensions, but at runtime only needs the wheels themselves. Multi-stage builds exploit this asymmetry by declaring one `FROM` for the build stage and a second `FROM` for the runtime stage, then using `COPY --from=build` to transplant just the artifact.

This sits at the top of the container layer of the mental model (introduced in [[10.02.01. Docker Engine Architecture]]): the Docker engine takes this Dockerfile, hands each `RUN` to `runc` to execute inside a container, captures the resulting filesystem diff as an OverlayFS upperdir, and stacks it as a new layer in the image manifest. The runtime layer above — your Spring Boot / Express / Django process — sees only the final flattened filesystem, never the layers that composed it. The failure modes this note governs are: 2 GB images that take 8 minutes to push on every commit, dependency reinstallations that bust the layer cache because you copied source code before `npm install`, root-running containers that turn a path-traversal bug into full host takeover, and alpine-based JVMs that crash with `Native memory allocation (mmap) failed` because musl libc does not implement the glibc memory layout the JVM expects.

## The Details

### Multi-Stage Builds: Compiling within heavy build images and copying production artifacts into min...

A multi-stage build declares two or more `FROM` lines in a single Dockerfile. The first stage pulls in a heavy image — say `maven:3.9-eclipse-temurin-21` (~600 MB) — and runs the full build chain: dependency resolution, compilation, test execution, jar packaging. The second stage pulls in a minimal runtime image — say `eclipse-temurin:21-jre-alpine` (~190 MB) — and uses `COPY --from=build` to transplant *only* the compiled artifact. Everything from the build stage that was not explicitly copied is discarded by the daemon when the build finishes. The final image manifest contains only the runtime stage's layers; the build stage never leaves the build cache.

```dockerfile
# Stage 1 — build (heavy: JDK + Maven + git, ~600 MB)
FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /app
COPY pom.xml .
RUN mvn -B dependency:go-offline           # cache deps; only reruns when pom.xml changes
COPY src ./src
RUN mvn -B package -DskipTests

# Stage 2 — runtime (minimal: JRE only, ~190 MB)
FROM eclipse-temurin:21-jre-alpine
WORKDIR /app
COPY --from=build /app/target/*.jar app.jar
USER 1001                                   # non-root
EXPOSE 8080
ENTRYPOINT ["java", "-XX:MaxRAMPercentage=75", "-jar", "app.jar"]
```

The `AS build` clause names the stage so the runtime stage can reference it. The `COPY --from=build` syntax is the only way to cross stage boundaries; nothing else leaks. You can have more than two stages — a common pattern is a third `FROM` stage that runs `trivy` or `grype` to scan the built artifact before the runtime image is finalized.

| Single-stage build | Multi-stage build |
|---|---|
| Final image includes Maven (~80 MB), JDK (~330 MB), git, bash | Final image includes only JRE (~190 MB) |
| Source code shipped in image (reverse-engineering risk) | Source code stays in build stage |
| `apt-get install` build deps (`gcc`, `libc-dev`) shipped to prod | Build deps never leave build stage |
| Image size ~750 MB | Image size ~210 MB |
| `docker push` takes ~45 s on 50 Mbps uplink | `docker push` takes ~12 s |
| Pull time on cold pod start ~25 s | Pull time on cold pod start ~7 s |

The `--target` flag lets you build only one stage of a multi-stage Dockerfile. `docker build --target build -t myapp:build .` produces an image that contains the build artifacts (useful for CI to extract the jar for a Maven repository). `docker build --target test -t myapp:test .` builds a stage that bundles test dependencies so you can run integration tests inside the container. The default `docker build` with no `--target` builds every stage up to the last `FROM` and tags the final image.

The production failure mode of skipping multi-stage is the 1.2 GB image that gets pushed on every commit. Each push saturates your registry's egress, fills nodes' local image caches, and slows every cold pod start by 30-60 seconds. Worse, shipping the JDK in your runtime image means a `log4shell`-class vulnerability in `org.apache.logging.log4j:log4j-core` exposes the entire `javax.naming` JNDI lookup machinery plus a full Java compiler to an attacker — when all the attacker needed at runtime was the `log4j-api` interface. Multi-stage removes that escape vector by construction.

### Layer Caching mechanics: Ordering Dockerfile instructions from least-frequently changed to most-f...

Each Dockerfile instruction produces one layer. The daemon caches each layer keyed on (parent-layer-ID, instruction-text, input-file-hashes). On a rebuild, the daemon walks the Dockerfile top-to-bottom and asks, for each instruction, "is the cache key the same as last time?" If yes, the daemon reuses the cached layer. If no — *and from this point downward for every subsequent instruction* — the cache is invalidated and the daemon re-executes every remaining instruction. The cache is a prefix match: the first changed instruction poisons everything below it.

The practical consequence is that the *order* of `COPY` and `RUN` instructions decides whether a rebuild takes 8 seconds or 8 minutes. The canonical mistake is copying source code first, then running dependency installation:

```dockerfile
# BROKEN: source copy invalidates npm install on every code change
COPY . .                                  # source changes → cache miss
RUN npm ci                                # reinstalls 1200 packages every time
```

The fix is to copy *only* the dependency manifest first, install deps (cache hit unless manifest changed), then copy the rest of the source:

```dockerfile
# CORRECT: deps install only reruns when package-lock.json changes
COPY package-lock.json package.json ./
RUN npm ci                                # cached across ~99% of commits
COPY . .                                  # source changes invalidate here only
```

| Instruction | Cache invalidation trigger | Frequency |
|---|---|---|
| `FROM base:tag` | Base image digest changes | Weekly (base image rebuild) |
| `RUN apt-get install` | Instruction text changes (e.g. add a package) | Monthly |
| `COPY package*.json` | package.json or lock file content changes | Weekly |
| `RUN mvn dependency:go-offline` | Recompute only if previous layer (pom.xml) changed | Weekly |
| `COPY src/` | Any source file changes | Every commit |
| `RUN mvn package` | Recompute if source changed | Every commit |

The cache is also busted silently by the build context: if your `docker build` context includes `target/` or `node_modules/` or `.git/`, every build uploads those dirs and every `COPY . .` instruction sees different content hashes — even if you did not touch source — because `target/app.jar` got rewritten by the previous build. The `.dockerignore` file is the mandatory fix. It sits next to the Dockerfile and lists paths excluded from the build context:

```text
# .dockerignore — do NOT ship these into the build context
.git
node_modules
target
build
.idea
.vscode
*.log
.env
Dockerfile*
docker-compose*.yml
```

Without `.dockerignore`, a 50 MB `.git` directory ships into the daemon on every `docker build`, even though no `COPY` instruction ever references it. The daemon receives the entire context tarball before it reads the Dockerfile.

The `dive` tool (github.com/wagoodman/dive) inspects layers interactively: `dive myapp:latest` shows a left pane of layers and a right pane of the filesystem diff that layer introduced. You can see exactly which `RUN` added 90 MB to the image (often `apt-get install` without `--no-install-recommends` and without `rm -rf /var/lib/apt/lists/*`). It also flags "wasted space" — files that were written in one layer and deleted in a later layer, but whose bytes still live in the image because layer deletion is a whiteout file, not actual erasure.

The production failure mode is the "8 minute CI pipeline" that developers start skipping. The fix is rarely "throw more compute at it" — it is almost always "reorder the Dockerfile so deps install before source copy, and add a `.dockerignore`." Once the reorder lands, CI drops from 8 minutes to 25 seconds and the team stops batching commits.

### Base Image selection: Distroless vs. Alpine vs. Debian Slim images

The base image is the `FROM` line of the runtime stage. It decides three things simultaneously: image size, attack surface (number of CVEs in shipped binaries), and libc compatibility (whether your binary's native dependencies will load). There is no globally correct choice; there is only the correct choice for your specific runtime.

| Base image | Size | libc | Shell? | pkg mgr? | Use case |
|---|---|---|---|---|---|
| `alpine:3.19` | ~7 MB | musl | yes (busybox ash) | apk | Static binaries (Go), or runtimes with first-class alpine support |
| `debian:bookworm-slim` | ~80 MB | glibc | yes (bash) | apt | JVMs, Python with C extensions, anything that needs glibc |
| `eclipse-temurin:21-jre-alpine` | ~190 MB | musl | yes | apk | JVMs that do not need glibc |
| `eclipse-temurin:21-jre-jammy` | ~260 MB | glibc | yes | apt | JVMs that need glibc (most) |
| `gcr.io/distroless/java21-debian12` | ~210 MB | glibc | **no** | **no** | Production JVMs — minimal attack surface |
| `scratch` | 0 MB | none | none | none | Statically-linked binaries (Go, Rust) |

The alpine-vs-debian-slim trade-off is fundamentally the musl-vs-glibc trade-off. Alpine uses musl libc, which is smaller and simpler than glibc but has subtly different behavior in three areas that bite JVMs: `malloc` returns memory to the OS less aggressively (visible as RSS that never drops after a GC), DNS resolution uses a different resolver that does not read `/etc/nsswitch.conf` the same way (visible as `UnknownHostException` for hosts that resolve fine from a debian container), and the default thread stack size is 80 KB instead of glibc's 1 MB (visible as `StackOverflowError` in deeply recursive Java code). The JVM team at Eclipse Temurin ships alpine variants but recommends debian-slim variants for production JVMs.

Distroless takes the opposite philosophy: start from debian-slim, then strip out everything that is not the runtime. The `gcr.io/distroless/java21-debian12` image has glibc (so all native libraries work) but no `bash`, no `ls`, no `cat`, no `apk` or `apt`. You cannot `docker exec` into a distroless container and poke around — there is no shell to exec into. The advantage is that an attacker who exploits your app gets a JVM and nothing else; no shell to spawn, no package manager to install tools, no `/usr/bin/find` to enumerate the filesystem.

```dockerfile
# Distroless JVM — final stage
FROM gcr.io/distroless/java21-debian12:nonroot
WORKDIR /app
COPY --from=build /app/target/app.jar /app/app.jar
USER nonroot
EXPOSE 8080
ENTRYPOINT ["java", "-XX:MaxRAMPercentage=75", "-jar", "/app/app.jar"]
```

The `:nonroot` tag bakes in UID 65532, so `USER nonroot` works without you having to `useradd` first. For non-JVM runtimes: `gcr.io/distroless/nodejs20`, `gcr.io/distroless/python3`, and the base `cc-distroless/base` (just glibc + ca-certificates + timezone data) cover most production use cases.

The production failure mode of choosing alpine for a JVM is the 3 a.m. page where the new microservice in staging has 30% lower throughput than the same code running in the debian-based monolith, RSS plateaus at the cgroup limit and never drops, and the GC log shows full collections every 2 seconds because musl's malloc returns fragmented free lists that the JVM cannot reclaim. The fix is not "tune the GC" — it is "switch the base image to debian-slim or distroless."

### Rootless containers: Creating and enforcing non-root execution users (`USER 1001`) for vulnerabil...

By default, a process running as root inside a container has UID 0 inside the container's user namespace — and if user namespaces are not configured, that UID 0 maps directly to UID 0 on the host. A container escape vulnerability (a kernel bug in `runc`, a misconfigured volume mount, a `--privileged` flag) then grants the attacker root on the host. The `USER` directive in the Dockerfile is the cheapest mitigation: it sets the UID the entrypoint runs as, and it is enforced by the container runtime regardless of who invokes `docker run`.

```dockerfile
# Debian-slim base — create a non-root user and switch to it
FROM debian:bookworm-slim
RUN groupadd --system --gid 1001 app \
 && useradd  --system --uid 1001 --gid app --home-dir /app --shell /usr/sbin/nologin app
WORKDIR /app
COPY --chown=1001:1001 app.jar /app/app.jar
USER 1001
EXPOSE 8080
ENTRYPOINT ["java", "-XX:MaxRAMPercentage=75", "-jar", "/app/app.jar"]
```

Note the numeric UID `1001` rather than the name `app`. Inside the container, name-to-UID resolution requires `/etc/passwd` to be present and readable; some minimal images (scratch, distroless) have no `/etc/passwd` at all. A numeric UID works regardless. The `--chown` flag on `COPY` ensures the file is owned by the runtime user, so the JVM can read its own jar without you having to `chmod 644` after the copy.

For binding to port 80 or 443: Linux requires `CAP_NET_BIND_SERVICE` to bind ports below 1024, which the non-root user does not have by default. Three fixes: (a) bind the app to port 8080 inside the container and publish to 80 on the host with `-p 80:8080` (the Docker daemon, running as root, does the port forwarding); (b) use `setcap 'cap_net_bind_service=+ep' /usr/bin/java` in the build stage to grant the capability to the binary; (c) run Nginx or Envoy as the root-binding front door and have it proxy to your non-root app on 8080. Option (c) is what production does — see [[10.04.01. Nginx Architecture and Event Model]] for the front door.

The deeper mitigation is user namespace remapping (`userns-remap`). With `"userns-remap": "default"` in `/etc/docker/daemon.json`, the daemon creates a subordinate UID range (default 100000-165535) and maps container UID 0 → host UID 100000. Even if an attacker escapes the container as root, they are UID 100000 on the host — they cannot read `/etc/shadow`, cannot write to `/etc`, cannot `kill` host processes. The cost is that bind-mounted host files now have surprising ownership: a file owned by host UID 1000 appears inside the container as owned by UID 0 (because of the offset), which breaks naive `chown` scripts.

| Defense | Layer | Cost | What it stops |
|---|---|---|---|
| `USER 1001` in Dockerfile | Image build | Free | App exploit that assumes UID 0 |
| `--cap-drop=ALL --cap-add=NET_BIND_SERVICE` | `docker run` | Free | Kernel exploit that needs CAP_SYS_ADMIN |
| `--security-opt=no-new-privileges` | `docker run` | Free | setuid escalation inside container |
| `--read-only` + `--tmpfs /tmp` | `docker run` | Free | Persistence: attacker cannot write a backdoor to disk |
| userns-remap | daemon.json | Per-file ownership headaches | Container escape that gets root on host |
| `--network=none` | `docker run` | App cannot reach other services | Lateral movement from compromised container |

The production failure mode of running as root is the container escape CVE of the year (CVE-2019-5736 `runc`, CVE-2022-0185 `kernel`, CVE-2024-21626 `runc` again) turning into "the attacker has root on every node in the Kubernetes cluster." `USER 1001` is not sufficient on its own — but it is the floor below which you should never ship.
