# 10.02.01. Docker Engine Architecture

## What This Is

Docker is not one program. It is a stack of five cooperating components — the Docker CLI, the Docker daemon (`dockerd`), the high-level runtime `containerd`, the low-level OCI runtime `runc`, and the Container Runtime Interface (CRI) plugin that lets Kubernetes talk to `containerd` without going through `dockerd`. When you type `docker run nginx`, that command flows through all five components in sequence, and the actual container process is born from `runc` calling `clone(CLONE_NEWPID | CLONE_NEWNET | CLONE_NEWNS | CLONE_NEWUTS | CLONE_NEWIPC, ...)` — the exact kernel primitives from Section 10.01. Understanding this stack is what lets you diagnose why `docker ps` works but `docker run` hangs (the daemon is alive but `containerd` is wedged), why `docker logs` shows output that `kubectl logs` does not (different log drivers), and why a Kubernetes cluster installed with `containerd` instead of `dockerd` behaves subtly differently in production.

The two H3s below cover the architecture of the stack itself and the Open Container Initiative (OCI) specifications that define the image format and the runtime contract. The architecture walk-through follows a single `docker run` command from your shell to the running container process, naming each component, the gRPC/REST API between them, and the kernel primitives each invokes. The OCI section explains why Docker images and `runc` containers are interchangeable with Podman, CRI-O, containerd, and every other OCI-compliant runtime — and why that interchangeability is the only reason Kubernetes was able to drop Docker as a dependency in 1.24 without breaking every cluster in the world.

## The Details

### Architecture: Docker CLI → REST API → Docker Daemon (`dockerd`) → `containerd` → `runc` (OCI Runt...

The Docker CLI is a thin Go binary that does no work itself. When you type `docker run nginx`, the CLI constructs an HTTP POST to the Docker daemon's REST API (by default on a Unix socket at `/var/run/docker.sock`, or on `tcp://localhost:2375` if TCP is enabled — `2376` for TLS). The API version is negotiated in the request URL: `POST /v1.43/containers/create` returns a container ID; `POST /v1.43/containers/<id>/start` starts it. The CLI then waits for the container's logs to flow back over the same socket. Every `docker` subcommand is a REST call; you can verify this with `curl --unix-socket /var/run/docker.sock http://localhost/v1.43/info | jq .` — the entire daemon surface is HTTP.

`dockerd` is the long-running daemon process (PID typically ~1200 on a fresh systemd host) that owns the image cache, the network bridges, the volume mounts, and the container lifecycle. It listens on the socket, parses the request, does the bookkeeping (allocate a container ID, set up the cgroup path, reserve a veth pair, prepare the overlay mount), and then hands the actual container creation off to `containerd` over a gRPC socket at `/run/containerd/containerd.sock`. `dockerd` is also the component that runs `docker build`, `docker pull`, `docker push` — it talks to the registry, downloads layers into `/var/lib/docker/overlay2/`, and assembles the image graph. Crucially, `dockerd` does *not* know how to start a container process — it delegates that to `containerd`.

`containerd` is the high-level runtime. It manages the container's entire lifecycle: it calls `runc` to actually fork the container process, supervises it while it runs, handles `exec` into the container, captures stdout/stderr, manages snapshots (the overlay2 layers), and exposes a gRPC API that the CRI plugin speaks. `containerd` was originally an internal Docker Inc. component; it was donated to the CNCF in 2017 and graduated in 2019. It is what Kubernetes runs directly (without `dockerd`) on every modern cluster — the so-called "containerd as the container runtime" pattern that became the default in Kubernetes 1.24 when Docker shim support was removed. `containerd`'s command-line tool is `ctr` (rough, low-level) and `nerdctl` (Docker-CLI-compatible).

`runc` is the low-level OCI runtime — the only component in the stack that actually calls `clone(2)` with namespace flags. It reads a `config.json` file (the OCI Runtime Specification, see the next H3) describing the container's desired namespaces, cgroups, mounts, process, and capabilities, and then executes those kernel calls in the right order: create the namespaces, set up the cgroup, mount the overlay, `pivot_root`, drop capabilities, set the `uid`/`gid`, and finally `execve` the container's entrypoint. `runc` then exits and the container process is left running under `containerd`'s supervision via a `--pid-file` and a control FIFO. `runc` is the reference implementation of the OCI Runtime Specification; alternatives include `crun` (a C implementation, used by Podman by default), `runsc` (Google gVisor, a userspace kernel), and `kata-runtime` (Kata Containers, a VM-per-container runtime).

The image storage lives at `/var/lib/docker/overlay2/` and is structured as one directory per layer plus a per-container writable layer. Each layer directory contains a `diff/` subdirectory with the layer's actual file content, a `link` file with a short name (used for `lowerdir=` references), a `lower` file listing the colon-separated parents, and (for the upper layer) a `merged/` mountpoint, a `work/` OverlayFS workdir, and a `committed` file written when the container stops. The image graph itself is stored in `/var/lib/docker/image/overlay2/imagedb/` (one JSON file per image, keyed by content hash) and `/var/lib/docker/image/overlay2/layerdb/` (one directory per layer, with `cache-id`, `diff`, `parent`, `size` files). When you `docker pull nginx`, `dockerd` downloads each layer tarball from the registry, extracts it into `/var/lib/docker/overlay2/<cache-id>/diff/`, and writes the layerdb entry — `containerd` then mounts the stack when a container starts.

```bash
# Inspect the running stack.
ps -ef | grep -E 'dockerd|containerd|runc' | grep -v grep
# root  1183     1  /usr/bin/dockerd -H fd:// --containerd=/run/containerd/...
# root  1243     1  /usr/bin/containerd
# root  5621  1243  /usr/bin/containerd-shim-runc-v2 ...
# (runc is short-lived: it starts the container, then exits; the shim
#  keeps the container supervised via a FIFO.)

# The containerd CLI (ctr) shows what containerd actually sees:
ctr -n moby containers list
# CONTAINER    IMAGE                             RUNTIME ...
# 1a2b3c4d...  docker.io/library/nginx:latest    io.containerd.runc.v2

# Inspect a container's storage layout:
docker run -d --name demo alpine sleep 3600
CID=$(docker inspect -f '{{.Id}}' demo)         # full container ID
ls /var/lib/docker/overlay2/<layer-hash>/        # the upper layer
# diff/  link  lower  merged/  work/

# What's the full lowerdir= stack for this container?
cat /var/lib/docker/overlay2/<layer-hash>/lower
# l/7H2K...:l/A8B5...:l/Q9W4...

# The CRI plugin is what Kubernetes uses (Kubernetes 1.24+ talks to
# containerd directly, skipping dockerd entirely):
crictl --runtime-endpoint unix:///run/containerd/containerd.sock ps
# CONTAINER   IMAGE    CREATED    STATE    NAME    ATTEMPT
# 1a2b3c...   nginx    5m ago     Running  web     1
```

Container stdout/stderr capture works through a pair of FIFOs (named pipes) that `containerd` creates in `/var/lib/docker/containers/<id>/`. The container's stdout is wired to `/var/lib/docker/containers/<id>/<id>-json.log` via the containerd shim, which reads from the FIFO and writes the JSON-formatted log line `{"log":"...","stream":"stdout","time":"..."}`. `docker logs <ctr>` reads this file; `kubectl logs` reads the same file via the CRI plugin. The default log driver is `json-file` with no rotation, which is a disk-exhaustion footgun — a verbose container can fill `/var/lib/docker` in hours. The fix in production is `{"log-driver": "json-file", "log-opts": {"max-size": "10m", "max-file": "3"}}` in `/etc/docker/daemon.json`, or switching to `journald`/`fluentd`/`syslog` drivers that externalise the log stream. The `docker0` bridge (Linux bridge device, default subnet `172.17.0.0/16`, gateway `172.17.0.1`) is created by `dockerd` on first start and is where every container's veth pair lands unless you create a user-defined network with `docker network create`.

The production failure mode for this architecture is the **`dockerd` single-point-of-failure and resource leak**. `dockerd` is one process holding one socket; if it crashes or is OOM-killed (it is itself subject to host memory pressure and has historically leaked goroutines on long-running hosts), every `docker` command hangs indefinitely, even though the underlying containers keep running because `containerd` is still supervising them. The diagnostic is `systemctl status docker` and `journalctl -u docker --since '10 min ago'` looking for `level=error` lines. The deeper failure is **leaked containers and images accumulating in `/var/lib/docker`** — `docker ps -a` shows stopped containers that were never removed, `docker images` shows dangling images (`<none>:<none>` tags), and over weeks the disk fills. The operational discipline is scheduled `docker container prune --filter "until=24h"` and `docker image prune -a --filter "until=24h"`, plus monitoring `node_filesystem_avail_bytes{mountpoint="/var/lib/docker"}`. On Kubernetes clusters the answer is to skip `dockerd` entirely and run `containerd` directly — fewer moving parts, no daemon to wedge.

### Open Container Initiative (OCI): Image Specification and Runtime Specification

The Open Container Initiative is the Linux Foundation working group (founded 2015, in the wake of Docker's commercial pivot that worried the broader container ecosystem) that standardises two things: the **Image Specification** (what a container image *is* on disk and in a registry) and the **Runtime Specification** (how a runtime *starts* a container from an image and a configuration). Before OCI, every runtime had its own image format (Docker v1, v2, AppC) and its own runtime configuration; OCI made them interoperable. The practical consequence is that a Docker image (`docker pull nginx`) and a Podman image (`podman pull nginx`) and a CRI-O image pull from the same registry, store the same layers in different on-disk paths, and produce a container with the same observable behaviour — because they all implement the same two specifications.

The **OCI Image Specification** defines three artefacts: the *manifest*, the *config*, and the *layers*. The manifest is a JSON document listing the layers (each by SHA256 digest) and a reference to the config document. The config is a JSON document describing the image: the entrypoint, the env vars, the working directory, the default user, the exposed ports, the volumes, the history (the Dockerfile instructions that built each layer). The layers are gzipped tar archives of filesystem deltas — each layer is a tarball of the files that layer added, modified, or deleted (deletions encoded as whiteout files). When you `docker pull nginx`, the runtime fetches the manifest first, then the config, then each layer tarball; stores them in the local image store; and assembles them into a stack at runtime. The on-disk layout under `/var/lib/docker/` is Docker-specific (the `image/overlay2/imagedb` and `layerdb` directories), but the wire format pulled from the registry is OCI — which is why any OCI-compatible registry (Harbor, Quay, GitHub Container Registry, AWS ECR, Google Artifact Registry) works with any OCI-compatible runtime.

```bash
# Inspect the OCI image format directly.
docker pull nginx:alpine
docker image inspect nginx:alpine | jq '.[0].RootFS.Layers'
# "sha256:9c6655a6...",
#  "sha256:a3ee7c8b...",
#  "sha256:7f1c8b3e...",
#  "sha256:4e9d2b8f..."

# Pull the manifest directly from the registry (no Docker needed):
curl -sSL -H "Accept: application/vnd.oci.image.manifest.v1+json" \
    https://registry-1.docker.io/v2/library/nginx/manifests/alpine | jq .
# {
#   "schemaVersion": 2,
#   "mediaType": "application/vnd.oci.image.manifest.v1+json",
#   "config": {
#     "mediaType": "application/vnd.oci.image.config.v1+json",
#     "digest": "sha256:bef258c5...",
#     "size": 7892
#   },
#   "layers": [
#     { "mediaType": "application/vnd.oci.image.layer.v1.tar+gzip",
#       "digest": "sha256:9c6655a6...", "size": 3482003 },
#     ...
#   ]
# }

# Inspect a layer's contents (a tar.gz of filesystem deltas):
docker save nginx:alpine -o /tmp/nginx.tar
tar tf /tmp/nginx.tar | head
# 0d7[...].json          <-- the config document
# manifest.json          <-- the manifest
# 9c6655a6.../layer.tar  <-- the layers
# ...

# The OCI image layout on disk (Docker's overlay2 driver):

# bef258c5...    <-- one file per image, content = JSON config
cat /var/lib/docker/image/overlay2/imagedb/content/sha256/bef258c5... | jq .config
# {
#   "User": "",
#   "ExposedPorts": { "80/tcp": {} },
#   "Env": ["PATH=..."],
#   "Entrypoint": ["/docker-entrypoint.sh"],
#   "Cmd": ["nginx", "-g", "daemon off;"],
#   "WorkingDir": ""
# }
```

The **OCI Runtime Specification** defines the `config.json` document that `runc` reads to start a container. The spec covers: `ociVersion`, `process` (the command to run, arguments, env vars, cwd, capabilities, rlimits, user, no-new-privileges flag), `root` (the path to the root filesystem and whether it is read-only), `hostname`, `mounts` (the list of mount points to set up, including the overlay mount, `/proc`, `/sys`, bind mounts for volumes), `linux` (the namespace list, cgroup path, resources block, devices, seccomp, sysctl, masked and readonly paths). When you `docker run`, `dockerd` and `containerd` translate the Docker CLI flags into a `config.json` and hand it to `runc`. When you `kubectl run`, the kubelet calls the CRI plugin, which calls `containerd`, which generates the same `config.json` and calls `runc`. The runtime spec is the contract that makes the entire stack substitutable.

```bash
# Generate and inspect an OCI runtime spec (the config.json runc reads).
mkdir /tmp/oci-demo && cd /tmp/oci-demo
runc spec                       # writes a default config.json
head -50 config.json
# {
#   "ociVersion": "1.0.2-dev",
#   "process": {
#     "terminal": true,
#     "user": { "uid": 0, "gid": 0 },
#     "args": [ "sh" ],
#     "env": [ "PATH=/usr/local/sbin:...", "TERM=xterm" ],
#     "cwd": "/",
#     "capabilities": {
#       "bounding": ["CAP_AUDIT_WRITE", "CAP_KILL", "CAP_NET_BIND_SERVICE", ...],
#       "effective": [...],
#       "permitted": [...]
#     },
#     "noNewPrivileges": true
#   },
#   "root": { "path": "rootfs", "readonly": true },
#   "hostname": "runc",
#   "mounts": [

#     { "destination": "/dev", "type": "tmpfs", "source": "tmpfs" },
#     ...
#   ],
#   "linux": {
#     "namespaces": [
#       { "type": "pid" },
#       { "type": "ipc" },
#       { "type": "uts" },

# Compare OCI runtimes — they all read the same config.json:
#   runc        — reference implementation (Go), Docker's default
#   crun        — C implementation, Podman's default, faster startup
#   runsc       — Google gVisor, userspace kernel (syscall filtering)
#   kata-runtime— Kata Containers, one lightweight VM per container
#   youki       — Rust implementation, experimental

# Kubernetes talks to any of them via the CRI (Container Runtime Interface):
crictl info | jq '.status.conditions'
# Inspect a Pod's runtime details:
crictl inspect <container-id> | jq '.info.runtimeType'
# "io.containerd.runc.v2"
```

The CRI (Container Runtime Interface) is the Kubernetes-side counterpart to OCI. CRI is a gRPC API defined in `kubelet/pkg/remote` that the kubelet calls to manage pods and containers — `RunPodSandbox`, `CreateContainer`, `StartContainer`, `StopContainer`, `RemoveContainer`, `ListContainers`, `ContainerStatus`. The implementation is a shim that translates CRI calls into `containerd` calls (the `cri` plugin built into `containerd`), or into `dockerd` calls (the now-deprecated `dockershim` that Kubernetes removed in 1.24), or into CRI-O calls (the Red Hat-led runtime that skips both Docker and `containerd`'s broader feature set and implements only the CRI surface). The combination of OCI Image + OCI Runtime + CRI is what lets you swap Docker for Podman for CRI-O for containerd without touching a single line of Kubernetes YAML — and it is why the container ecosystem, despite Docker Inc.'s commercial turbulence, has remained stable for the better part of a decade.

The production failure mode for the OCI layer is the **runtime-version mismatch**. A `config.json` written against runtime spec v1.0 may include fields that an older `runc` does not understand (or vice versa); the symptom is `runc: config.json: schema version mismatch` on container start. The fix is to align `dockerd`, `containerd`, and `runc` versions to a single release epoch (e.g. Docker 24.x with containerd 1.6.x with runc 1.1.x) — distro packages usually handle this, but mixed-source installs (Docker's official repo + a hand-compiled `runc`) drift. The other classic failure is the **image-spec v1 vs v2 manifest** problem: registries that serve only the older Docker v2 schema 1 manifest break against modern runtimes that speak OCI v1; the symptom is `failed to do request: Head https://registry...: unsupported media type`. The fix is to use a current registry (Harbor 2.x, ECR, GCR, GHCR all serve OCI v1) and to re-push old images from a modern client if a registry is stuck on an old schema.
