# 10.05.01. Domain Name System (DNS) Resolution

## What This Is

The Domain Name System is the globally distributed, eventually-consistent database that maps human-readable hostnames (`api.example.com`) to the IP addresses that the kernel's TCP stack actually needs (`203.0.113.42`). It is hierarchical, delegated, and cached at every layer — a single lookup typically touches four distinct server roles (recursive resolver, root, TLD, authoritative) and is then remembered for the duration of a TTL. DNS is the first failure mode of any internet-facing system: if resolution breaks, no amount of healthy backends, well-tuned load balancers, or fast databases will save you — the client cannot even open a TCP connection to begin with. DNS outages are also the slowest to recover from, because every layer caches negative results (`NXDOMAIN`) for the duration of the SOA TTL, which is typically 1 hour.

This note sits between the kernel networking layer (section 02) and the application framework layer (section 05). The framework calls `gethostbyname()` / `InetAddress.getAllByName()` / `dns.lookup()`, which calls into the C library's resolver, which reads `/etc/resolv.conf`, which lists the recursive resolvers to query. Understanding this chain is the difference between "my app can't reach the database" being a 5-minute fix (the recursive resolver is wedged; flip to 1.1.1.1) and a 5-hour incident (you suspect the database, the network, the firewall, and only at hour 4 think to check DNS). This note covers the resolution hierarchy, the record types that flow over it, and the TTL/caching/Anycast model that makes the system both fast and fragile.

## The Details

### The Hierarchical Resolution tree: Root Nameservers (`.`), TLD Nameservers (`.com`), Aut...

DNS resolution is a four-role dance: the **stub resolver** in the client OS, the **recursive resolver** operated by the user's ISP or a public resolver (Google `8.8.8.8`, Cloudflare `1.1.1.1`, Quad9 `9.9.9.9`), the **root nameservers** at the top of the tree, the **TLD nameservers** for each top-level domain (`.com`, `.org`, `.io`), and the **authoritative nameservers** for the specific domain. The recursive resolver is the only one that does the full walk; the client stub asks the recursive resolver a single question and waits for the answer.

The flow for resolving `api.example.com` from scratch (cold cache) is:

```text
Client                Recursive             Root              .com TLD          example.com auth
  |                       |                   |                  |                    |
  |--api.example.com?---->|                   |                  |                    |
  |                       |--api.example.com? |                  |                    |
  |                       |  (cold cache)     |                  |                    |
  |                       |--"who serves .com?"------------------>                    |
  |                       |                   |                  |                    |
  |                       |<--"ask a.gtld-servers.net"-----------|                    |
  |                       |--api.example.com?-------------------->|                    |
  |                       |                   |                  |                    |
  |                       |<--"ask ns1.example.com"---------------|                    |
  |                       |--api.example.com?---------------------------------------->|
  |                       |                   |                  |                    |
  |                       |<--A 203.0.113.42 (TTL 300)--------------------------------|
  |<--203.0.113.42--------|                   |                  |                    |
```

The recursive resolver caches the answer (and the intermediate NS delegations) for their respective TTLs — the next lookup of `api.example.com` is served from cache in microseconds, and the next lookup of anything under `.com` skips the root-server step entirely. The root server "13 logical instances" (`a.root-servers.net` through `m.root-servers.net`) is a historical artifact of the original 13 IPv4 addresses that fit in a 512-byte UDP DNS packet; in practice each letter is operated by a different organisation and fronted by hundreds of physical servers via **Anycast** (the same IPv4 address advertised from many locations; BGP routes the packet to the nearest). This is why the root nameservers survive DDoS attacks that would flatten any single server — the attack traffic is distributed across the planet.

DNS queries are **UDP port 53** by default, with each query and response fitting in a single UDP datagram (capped at 512 bytes by RFC 1035 for compatibility with old resolvers). When a response would exceed 512 bytes — typically because a domain returns many A records or a DNSSEC signature chain — the server sets a `TC` (TrunCation) bit in the UDP response and the resolver retries the same query over **TCP port 53**, which has no 512-byte limit. Zone transfers between primary and secondary authoritative servers always use TCP (`AXFR` / `IXFR` messages can be hundreds of kilobytes). The 512-byte UDP cap is also why **EDNS0** (Extension Mechanisms for DNS, RFC 6891) exists — it lets the client advertise "I can handle 4096-byte UDP packets, please don't truncate" via an `OPT` pseudo-record in the additional section. Without EDNS0, DNSSEC-enabled responses get truncated and fall back to TCP, adding a round-trip to every signed lookup.

The failure modes of this hierarchy are subtle. A recursive resolver that loses connectivity to the root servers (rare, but happens during BGP hijacks) appears "fine" until the cache drains — then every uncached domain starts failing. An authoritative server that is unreachable causes the recursive resolver to return `SERVFAIL` to clients, but only after retrying for the duration of the SOA record's `Retry` interval (typically 10 minutes) — so a 30-second outage at the authority can stretch into a 10-minute outage at the resolver. And the most pernicious failure is **negative caching**: when an authoritative server returns `NXDOMAIN` (the domain does not exist), the recursive resolver caches that negative answer for the duration of the SOA record's `TTL` field (typically 1 hour, sometimes 24 hours). If a misconfigured authority returns NXDOMAIN for a domain that actually exists (a transient misconfiguration during a DNS migration), the recursive resolver remembers "does not exist" for an hour, and you cannot fix it faster by correcting the authority — you have to wait for the negative TTL to expire across the world's resolvers.

### Resource Record Types: `A` (IPv4), `AAAA` (IPv6), `CNAME` (Canonical Name alias), `ALIA...

DNS records are typed — a single name can have multiple records of different types, each carrying different information. The type system is what makes DNS a database rather than just a hostname→IP lookup. The commonly-encountered types:

| Type | Purpose | Example value | Typical TTL |
|---|---|---|---|
| `A` | IPv4 address | `203.0.113.42` | 300s (5 min) for dynamic, 3600s for static |
| `AAAA` | IPv6 address | `2001:db8::1` | Same as A |
| `CNAME` | Alias to another name | `api.example.com → example-com.azureedge.net` | 300s |
| `MX` | Mail exchange (with priority) | `10 mail1.example.com` | 3600s |
| `TXT` | Free-form text (SPF, DKIM, DMARC, verification tokens) | `"v=spf1 include:_spf.google.com ~all"` | 3600s |
| `NS` | Delegation to a child zone's authority | `ns1.example.com` | 86400s |
| `SOA` | Start of authority (primary NS, contact, serial, refresh/retry/expire TTLs) | `ns1.example.com admin.example.com 2024011501 7200 600 1209600 3600` | 3600s |
| `SRV` | Service locator (priority/weight/port/target) | `10 60 5060 sipserver.example.com` | 3600s |
| `PTR` | Reverse DNS (IP → name) | `42.113.0.203.in-addr.arpa → api.example.com` | 3600s |
| `CAA` | Certificate Authority Authorization (which CAs may issue certs) | `0 issue "letsencrypt.org"` | 3600s |

The **`A` record** is the bread and butter — it maps a name to an IPv4 address. A single name can have multiple A records (`api.example.com A 203.0.113.42; api.example.com A 203.0.113.43`), and the recursive resolver returns all of them in a single response; the client (or the kernel's round-robin selector) picks one. This is "DNS round-robin load balancing" — crude but stateless, and the basis for many global load-balancing products. The **`AAAA`** record is the IPv6 equivalent ("quad-A"); the four `A`s are a pun on the 16 bytes of an IPv6 address. Modern dual-stack clients issue `A` and `AAAA` queries in parallel (a feature called "Happy Eyeballs", RFC 8305) and race the responses, picking whichever address family answers first — this avoids the IPv6-path-is-broken-but-the-client-still-waits-75-seconds failure mode that plagued early IPv6 deployments.

The **`CNAME`** record aliases one name to another: `cdn.example.com CNAME example-com.azureedge.net`. The resolver then chases the alias — it queries for `example-com.azureedge.net` and returns its A record. This indirection is what lets a CDN own the IP-address-to-edge-POP mapping and update it without your involvement. CNAMEs have one hard rule: **a CNAME cannot coexist with any other record type at the same name**. So `example.com CNAME example-com.azureedge.net` is illegal, because `example.com` must have `SOA` and `NS` records to be a zone apex. The workarounds are `ALIAS` (a non-standard but widely-implemented pseudo-record that the authority resolves server-side and returns as an A record to the client — supported by Route53, DNSimple, Cloudflare) or `ANAME` (the same idea, different vendor names). The **`MX`** record directs email — the priority field (lower = preferred) lets you specify primary and backup mail servers. The **`TXT`** record is the catch-all: SPF (`v=spf1 include:_spf.google.com ~all`), DKIM public keys (`k=rsa; p=MIIBIjANBg...`), DMARC policy (`v=DMARC1; p=reject; rua=mailto:dmarc@example.com`), and domain-verification tokens issued by SaaS providers (`google-site-verification=abc123`). The **`SRV`** record generalises MX to arbitrary services — it carries priority, weight, port, and target, and is how Active Directory locates domain controllers (`_ldap._tcp.example.com SRV 10 60 389 dc1.example.com`). The **`PTR`** record is the reverse — given an IP, what's its name? Used by mail servers (a sending IP without a matching PTR is almost certainly spam) and by SSH servers that do reverse-DNS checks for access control. The **`CAA`** record restricts which Certificate Authorities may issue TLS certificates for a domain — modern CAs check it before issuing, so it's a defense against the "a mis-issued cert from a CA you've never heard of lets someone MITM your domain" failure that hit Symantec in 2017.

The diagnostic tools every backend engineer must know:

```bash
# dig — the universal DNS query tool.
# Default: query A record from the system resolver.
dig api.example.com

# Query a specific record type from a specific resolver
dig @1.1.1.1 api.example.com AAAA
dig @8.8.8.8 example.com MX
dig @8.8.8.8 example.com TXT

# Trace the full resolution path (recursive resolver walking root→TLD→auth)
dig +trace api.example.com

# Show the full response including TTL
dig api.example.com +noall +answer

# host — simpler output, useful in scripts
host -t MX example.com
host -t SRV _ldap._tcp.example.com

# getent — query the system resolver via NSS (honours /etc/hosts + nsswitch.conf)
getent hosts api.example.com

# Inspect the local resolver config
cat /etc/resolv.conf
# nameserver 10.0.0.2          # the recursive resolver to query
# search example.com           # auto-append this domain to single-label names
# options timeout:1 attempts:3 # 1s per try, 3 tries total before giving up
```

### Time-to-Live (TTL) values, DNS caching layers, and Anycast routing

Every DNS record carries a **TTL** — the number of seconds that any caching layer may remember the answer before re-asking. TTLs cascade through four caching layers, each of which can serve a lookup from cache or escalate to the layer above. The layers, from closest to the client to closest to the source of truth:

```text
┌──────────────────────────────────────────────────────────────────────────────┐
│ 1. Application cache   — JVM InetAddress cache (default 30s positive, 10s neg)│
│    Node.js dns.lookup() does NOT cache by default — must wrap in cache        │
│    Browser DNS cache — Chrome ~1min, Firefox ~60s, capped by actual TTL       │
├──────────────────────────────────────────────────────────────────────────────┤
│ 2. OS stub resolver    — getaddrinfo() result cached by nscd / systemd-resolved│
│    Honours /etc/hosts FIRST (skips DNS entirely) per /etc/nsswitch.conf       │
├──────────────────────────────────────────────────────────────────────────────┤
│ 3. Recursive resolver  — 8.8.8.8 / 1.1.1.1 / corporate resolver              │
│    Largely shared cache — all clients behind it see the same answers           │
│    Caches positive answers for the record TTL                                  │
│    Caches NXDOMAIN for the SOA minimum TTL (often 1h, sometimes 24h)          │
├──────────────────────────────────────────────────────────────────────────────┤
│ 4. Authoritative server — ns1.example.com (the source of truth)              │
│    No caching — answers from the zone file or dynamic backend                 │
└──────────────────────────────────────────────────────────────────────────────┘
```

The TTL value is a tradeoff between agility and load. A 5-second TTL means you can move traffic to a new IP almost instantly (good for failover), but every client re-queries every 5 seconds (bad for resolver load and latency). A 1-hour TTL means one cached lookup serves 3,600 requests (good for load), but a DNS change takes up to 1 hour to fully propagate (bad for failover). The standard production pattern is: short TTL (60–300s) on records you intend to fail over (the apex, the API hostname, anything fronting a global LB), long TTL (3600–86400s) on records that never change (static asset hostnames, MX records, NS delegations). When you plan a migration, lower the TTL to 60s a day in advance, wait for the old TTL to expire across the world, then make the change with a 1-minute propagation window.

**DNS-based load balancing** exploits the fact that one name can have multiple A records. `api.example.com A 203.0.113.42; api.example.com A 203.0.113.43; api.example.com A 203.0.113.44` — the recursive resolver returns all three in a rotated order on each query (this is called "round-robin DNS"), and the client picks one. This is crude (no health checks — a dead IP stays in rotation until manually removed), stateless (no per-client affinity), and uneven (clients behind one recursive resolver all share the same cached ordering for the TTL window). The smarter version is a managed DNS service (Route53, Cloudflare, NS1) that returns different A records based on the geographic location of the querying resolver (geo-DNS), the latency to each backend (latency-based routing), or weighted health-checked endpoints. These services use very short TTLs (typically 60s) so changes propagate fast.

**Split-horizon DNS** is the practice of returning different answers depending on who asks. The classic pattern: internal users querying `intranet.example.com` from inside the corporate network get `10.0.0.5` (a private IP, unreachable from the internet); external users querying the same name get `203.0.113.42` (a public IP). Implemented by running two authoritative servers (one internal, one external) and configuring the recursive resolver to forward to the right one based on the source IP. In Kubernetes, the cluster-DNS service (`kube-dns` or CoreDNS) does this implicitly — `kubernetes.default.svc.cluster.local` resolves to the service ClusterIP from inside the cluster, and is meaningless from outside.

**Anycast routing** is how the root nameservers and the major public resolvers (8.8.8.8, 1.1.1.1) achieve global availability and DDoS resistance. The same IP address is announced from dozens of locations worldwide via BGP; the Internet's routing infrastructure delivers each query to the topologically nearest announcer. An attacker trying to DDoS 8.8.8.8 finds their traffic split across hundreds of Cloudflare points of presence, none of which saturates. Anycast is also the basis for the global load balancers (AWS Route53 + CloudFront, Cloudflare's edge) — they're not "load balancing" in the L4 sense, they're "routing the DNS query to a nearby edge that then handles the request." The failure mode of Anycast is **BGP route flapping** — if an announcer's BGP session flaps, traffic that was being delivered to it gets rerouted mid-connection, and any TCP connection that was anchored to that POP breaks. This is why Anycast is mostly used for UDP services (DNS, NTP) where mid-connection rerouting is invisible.

```bash
# The two local files that override or steer DNS resolution:

# /etc/hosts — checked FIRST per /etc/nsswitch.conf "hosts: files dns"
# Use for: pinning a hostname to a specific IP during testing
#         blocking a domain by pointing it at 127.0.0.1
#         bootstrapping DNS for a brand-new server before DNS is configured
cat /etc/hosts
# 127.0.0.1   localhost
# 10.0.0.11   api.local api
# 203.0.113.42 api.example.com  # pinned for load test

# /etc/resolv.conf — the stub resolver config (read by getaddrinfo)
# Generated by systemd-resolved / NetworkManager / DHCP — hand-edits get overwritten
cat /etc/resolv.conf
# nameserver 10.0.0.2          # the recursive resolver IP
# search example.com prod.example.com   # try foo.example.com then foo.prod.example.com
# options timeout:1 attempts:3          # 1s per attempt, 3 attempts, give up after 3s
# options rotate                        # round-robin across multiple nameserver lines
# options single-request                # avoid the A/AAAA race that breaks some firewalls
```

The production failure mode that catches every backend engineer once: the JVM caches DNS lookups by default. `networkaddress.cache.ttl=30` (30 seconds for successful lookups) and `networkaddress.cache.negative.ttl=10` (10 seconds for failures) in the JVM's `java.security` file. A Java service that runs for weeks holds onto a cached IP for 30 seconds, which is fine in steady state but means a DNS failover takes up to 30 seconds to be visible to a long-running JVM. Worse, if a SecurityManager is installed the positive cache becomes permanent (`cache.ttl=-1`), so the JVM never re-resolves — a DNS change is invisible until you restart the JVM. Node.js has the opposite default: `dns.lookup()` does NOT cache at all, every call goes to `getaddrinfo()`, which means a Node app making 10,000 outbound HTTP requests per second hammers the system resolver 10,000 times per second unless you wrap it in a caching layer (`cacheable-lookup` or `dnscache`). Python's `socket.getaddrinfo()` similarly does not cache — the caching happens in the OS resolver (nscd, systemd-resolved). Knowing your runtime's DNS caching default is essential to predicting how fast DNS changes propagate to your running services.

## How This Connects to the Frameworks

Every framework in section 05 calls DNS at the moment it opens an outbound TCP connection — a database connection, an HTTP call to a downstream service, an S3 upload. The frameworks differ in how they cache the result, which determines how fast a DNS change propagates to running services.

| Framework / Runtime | DNS caching default | How to tune |
|---|---|---|
| JVM (Spring Boot, etc.) | `networkaddress.cache.ttl=30s` (or `-1` with SecurityManager) | `-Dnetworkaddress.cache.ttl=10` for faster failover |
| Node.js | No caching — every `dns.lookup()` calls `getaddrinfo()` | Wrap with `cacheable-lookup` or set `http.globalAgent.keepAlive=true` to reuse connections |
| Python (CPython) | No caching in `socket` — relies on nscd / systemd-resolved | Configure nscd positive-time-to-live; or use `aiodns` with explicit caching for async |
| Go | `net.Resolver` caches per-process via `net.DefaultResolver` — short TTL (5–10s) | Tune via custom `Resolver.Dial` if needed; Go's defaults are sane |
| glibc / musl | nscd caches `getaddrinfo` per host (configurable TTL) | `nscd -i hosts` to flush; musl does NOT cache at all (common Alpine gotcha) |

The framework-level connection: when your Spring Boot app calls `repo.findById(id)` over a JDBC connection, the JDBC driver resolves the database hostname once at pool-creation time and reuses that IP for every connection in the pool. A DNS-based database failover (RDS multi-AZ promotion, Aurora writer change) does NOT take effect for your app until the connection pool cycles — even if you've set `networkaddress.cache.ttl=1`, the existing pool connections hold the old IP. The fix is either (a) use the JDBC connection URL with a fresh-DNS-on-each-connect option (MySQL `rewriteBatchedStatements` and `autoReconnect=true` — buggy; prefer (b)), (b) configure HikariCP's `maxLifetime` to less than the failover propagation window so connections cycle, or (c) put a TCP proxy (HAProxy, PgBouncer) in front of the database and let it handle failover transparently, so the JDBC URL points at a stable HAProxy address.

## Hands-On Exercise

```bash
# 1. Watch the full iterative resolution — see root, TLD, and authority each answer
dig +trace api.example.com

# 2. Query your system resolver vs the public resolvers and compare answers
dig api.example.com +short
dig @1.1.1.1 api.example.com +short
dig @8.8.8.8 api.example.com +short

# 3. Inspect the record types for a domain you own (or example.com)
dig example.com ANY          # note: ANY is deprecated, often refused; query types individually
dig example.com A
dig example.com AAAA
dig example.com MX
dig example.com TXT
dig example.com NS
dig example.com SOA
dig example.com CAA

# 4. Measure TTL decay — query the same name twice and watch the second number drop
dig example.com +noall +answer    # note the TTL (e.g. 3600)
sleep 5
dig example.com +noall +answer    # TTL should be ~3595

# 5. See the local resolver config and what's overriding DNS
cat /etc/resolv.conf
cat /etc/hosts
cat /etc/nsswitch.conf | grep hosts   # show "files dns" or "files mdns dns"

# 6. Resolve via the system (honours /etc/hosts + nsswitch.conf)
getent hosts api.example.com

# 7. Reverse-DNS an IP — what name does the world see for this address?
dig -x 8.8.8.8 +short
#  dns.google.

# 8. Inspect what your JVM thinks the cache TTL is
java -XshowSettings:properties 2>&1 | grep -i cache
# Or in a running JVM: ManagementFactory.getRuntimeMXBean().getSystemProperties()
#   .get("networkaddress.cache.ttl")
```
