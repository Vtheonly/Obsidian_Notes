# 10.05.02. Content Delivery Networks (CDN) and Edge Caching

## What This Is

A Content Delivery Network is a globally distributed fleet of caching reverse proxies operated by a single company (Cloudflare, Fastly, AWS CloudFront, Akamai, Google Cloud CDN). Each cache node, called a Point of Presence or POP, sits in a data centre close to a population of end users — Cloudflare runs 300+ POPs, Akamai 4,000+ — and serves cached responses directly from the edge without touching the customer's origin servers. The motivation is purely the speed-of-light tax: a request from São Paulo to an origin in Virginia is a ~110ms RTT minimum (the packet physically cannot travel faster than c through the fibre), and a typical web page needs 20–50 separate requests, each paying that latency. Serving the static assets from a São Paulo POP drops each RTT to single-digit milliseconds, and the page renders in 200ms instead of 3 seconds.

A CDN takes over the DNS for the hostnames it serves: `cdn.example.com` is a CNAME into the CDN's domain (`example-com.cloudflare.com` or `examplecom.cloudfront.net`), the CDN's authoritative DNS resolves that CNAME to the IP of the nearest POP via EDNS Client Subnet (the resolver tells the CDN which subnet the user is in, so the CDN picks a topologically-close POP, not just one close to the resolver). The CDN then either serves the response from its edge cache (a "cache HIT") or forwards the request to the origin server (a "cache MISS"), caches the origin's response, and serves it. This note covers the POP architecture, the cache key and invalidation model, the `Cache-Control` directives that govern cacheability, and the conditional-request validators that let a client avoid re-downloading unchanged content.

## The Details

### CDN Architecture: Origin Servers vs. Globally Distributed Edge Points of Presence (PoPs)

The architecture is two-tier: the **origin** (your application servers, sitting in one or two data centres) and the **edge** (the CDN's POPs, distributed worldwide). The CDN's value proposition is that, for cacheable content, the origin never sees the request at all — the POP serves it from local RAM or NVMe. The CDN's contractual value is measured by the **cache hit ratio**: the percentage of requests served from the edge without touching the origin. A well-tuned CDN for a static-asset-heavy site achieves 99%+ hit ratio; the origin sees only 1% of the actual user traffic, and is sized for that 1% (not for peak).

The DNS takeover is how the CDN intercepts traffic. Without a CDN, `www.example.com` resolves directly to your origin's IP. With a CDN, `www.example.com` is configured (at your DNS provider) as a CNAME into the CDN's domain — `www.example.com CNAME www.example.com.cdn.cloudflare.net`. The CDN's authoritative DNS now answers all queries for that name. Crucially, the CDN uses **EDNS Client Subnet (ECS)** to learn the user's subnet: when the user's recursive resolver queries the CDN's authority, it includes the user's /24 in the additional section, and the CDN responds with an A record pointing at the POP closest to that /24 (not closest to the recursive resolver — this is the difference between a Berlin user querying a Frankfurt recursive and getting a Frankfurt POP, vs the same user accidentally getting a London POP because their recursive was in London). Without ECS, all Cloudflare users behind Google's 8.8.8.8 would appear to be at Google's AS, and would all hit the same POP — defeating the purpose of a distributed edge.

The edge cache is typically a tiered LRU/LFU cache backed by NVMe (Fastly uses SSD-backed Varnish; Cloudflare uses a custom in-RAM cache plus on-disk spill). Each POP maintains its own cache — there is no global cache coherence — so a cache miss at one POP does not populate any other POP. A new piece of content goes "viral" by sequentially warming each POP as users in each region request it. The cache hit ratio therefore depends on per-POP traffic volume: a São Paulo POP with 1000 rps warms content much faster than a Lagos POP with 5 rps. CDNs mitigate this with the **origin shield** — a second-tier cache sitting between the edges and the origin (Cloudflare "Argo Tiered Caching", Fastly "Origin Shielding", CloudFront "Origin Shield"). All POPs fetch through the shield, so a cache miss at Lagos, Frankfurt, and Tokyo results in only one fetch to the origin (the shield serves the other two). The shield is also where the CDN's DDoS-mitigation layer is most aggressive — if a coordinated attack overwhelms one POP, traffic is rerouted to the shield rather than the origin.

Beyond static caching, modern CDNs offer three additional edge services. **TLS termination at the edge** — the CDN holds the certificate, terminates the user's TLS, and re-establishes a new TLS connection to the origin. This pushes the ~50ms TLS handshake cost off the origin's CPU and onto the CDN's fleet. **WAF (Web Application Firewall)** — the CDN inspects request patterns at the edge and blocks SQL-injection / XSS / known-bad-user-agent signatures before they reach the origin (Cloudflare WAF, AWS WAF). **Edge compute** — Cloudflare Workers (V8 isolates), Fastly Compute@Edge (WebAssembly), CloudFront Lambda@Edge — runs JavaScript / WASM at the POP itself, so A/B testing, auth checks, and personalisation happen without touching the origin. WebSocket support is supported by all major CDNs (Cloudflare, Fastly, CloudFront) by establishing a persistent bidirectional connection from user→POP and POP→origin and bridging the two — but with the caveat that the connection is anchored to that specific POP; if the POP fails the WebSocket breaks, unlike the stateless HTTP case where the user just retries against another POP.

The production failure mode is the **origin take-down via cache stampede**. A new deploy ships a CSS bundle with a new hashed filename (`main.a1b2c3.css`); every user's browser requests the new file simultaneously; the cache is cold at every POP; every POP simultaneously sends a request to the origin; the origin handles 1000x its normal load and falls over. The mitigations are: pre-warm the cache (`curl -H 'Host: cdn.example.com' https://edge-1.cdn.example.com/main.a1b2c3.css` from a script that walks every POP) before the deploy goes live; configure `stale-while-revalidate` so the CDN serves the old content while asynchronously fetching the new (covered in H3 #3); or use a small origin-shield window that collapses simultaneous misses into a single origin request (request coalescing — Fastly and Cloudflare both do this at the shield).

### Edge Caching Mechanics: Static asset caching, dynamic content acceleration, Origin Shie...

The cache key is the identifier the CDN uses to look up a cached response. The default cache key is the URL — `Host + path + query string`. Anything not in the key is invisible to the cache: two requests with different `Accept-Language` headers will share a cache entry unless `Vary: Accept-Language` is set on the response (then the CDN stores separate entries per language). Cache-key design is the single most important CDN configuration decision. Too narrow (include user-specific query params like `?session_id=abc`) and the hit ratio collapses to zero because every request has a unique key. Too broad (ignore `?variant=mobile` vs `?variant=desktop`) and you serve the wrong variant to the wrong device. The standard pattern: normalise the URL — strip analytics params (`utm_*`, `fbclid`, `gclid`), drop the `?` if no query remains, lowercase the host — and use that as the cache key. Cloudflare does this via "Cache Rules"; Fastly via VCL `hash_data()` calls; CloudFront via "Cache key policy" in a Cache Behavior.

```text
                       CACHE-KEY NORMALISATION
Request URL:    /products/42?utm_source=email&variant=mobile&fbclid=abc123
                         │
                         ▼  Strip tracking params (utm_*, fbclid, gclid)
                /products/42?variant=mobile
                         │
                         ▼  Sort remaining params alphabetically
                /products/42?variant=mobile
                         │
                         ▼  Cache key: host + path + sorted query
Cache key:      shop.example.com/products/42?variant=mobile
                         │
                         ▼  Lookup in edge cache
              ┌─────────────────────┐
              │ HIT  → serve cached │
              │ MISS → fetch origin │
              └─────────────────────┘
```

The cache lookup returns one of four states, each of which surfaces in the response's `CF-Cache-Status` (Cloudflare), `X-Cache` (Fastly: `HIT` / `MISS` / `PASS` / `STALE`), or `X-Cache` (CloudFront: `Hit from cloudfront` / `Miss from cloudfront`) header:

- **HIT** — the response is in cache and fresh (within `max-age`). Serve from edge RAM in <1ms.
- **MISS** — not in cache. Forward to origin (or origin shield), cache the response, serve it.
- **EXPIRED / STALE** — in cache but past `max-age`. The CDN revalidates with the origin (conditional request — see H3 #4). If `stale-while-revalidate` is set, the CDN serves the stale response immediately and fetches the fresh one asynchronously for the next request.
- **BYPASS / PASS** — the response is not cacheable (`Cache-Control: no-store`, or the URL matched a "do not cache" rule). The CDN forwards every request to the origin.

Cache invalidation — removing content from the cache before its TTL expires — is the most operationally delicate CDN feature. Three mechanisms exist, in order of granularity. **Purge by URL** — `POST /zones/{zone_id}/purge_cache` with `{"files": ["https://cdn.example.com/main.a1b2c3.css"]}` removes that exact URL from every POP. Fine-grained but requires you to enumerate every URL you want purged, which is impractical when a database change invalidates 10,000 product pages. **Purge by tag / surrogate key** — the origin stamps each response with `Cache-Tag: product-42,category-shoes` (Cloudflare) or `Surrogate-Key: product-42 category-shoes` (Fastly). A purge request with `{"tags": ["product-42"]}` then invalidates every cached response carrying that tag across the entire edge, in seconds. This is the production-grade invalidation pattern for dynamic content. **Purge everything** — nuclear option, removes every cached object from every POP. Used in emergencies only; the next wave of user traffic is 100% cache misses and hammers the origin. Cloudflare's purge-everything API endpoint is rate-limited to once per 5 minutes for exactly this reason.

The **origin shield** is a second-tier cache that sits between the edges and the origin. Without a shield, every edge POP fetches directly from the origin on a miss — a single viral URL can produce 300 simultaneous origin requests (one per POP). With a shield, all edges fetch through the shield, which collapses simultaneous misses into a single origin request (request coalescing) and serves the cached response to all the other edges. This reduces origin load by a factor of (number of POPs) in the worst case. Cloudflare's shield is "Argo Tiered Caching" (paid add-on); Fastly's is "Origin Shielding" (select a single shield POP); CloudFront's is "Origin Shield" (a designated regional edge cache that all POPs fetch through). The shield also enables longer origin-side timeouts — if the origin is slow, the shield holds the connection while the edges time out and serve stale.

Static asset optimisation runs at the edge as well: **minification** (strip whitespace from JS/CSS), **compression** (Brotli for modern browsers, gzip for legacy, negotiated via `Accept-Encoding`), **image optimisation** (convert PNG/JPEG to WebP or AVIF for browsers that accept them, resize to the device's viewport width, strip EXIF metadata). Cloudflare's "Polish", Fastly's "Image Optimizer", CloudFront's "Lambda@Edge" image-transform functions all do this. The edge is the right place for these transforms because the optimised bytes are then cached and served to every subsequent request for that asset — the origin never re-pays the CPU cost. The failure mode is when the transform is non-deterministic (a different `Accept-Encoding` produces a different output) and the cache key doesn't include the variant dimension — the CDN serves a Brotli response to a browser that only accepts gzip, and the browser fails to decode it. The fix is the `Vary: Accept-Encoding` response header, which tells the CDN to store separate cache entries per `Accept-Encoding` value.

### Cache-Control Directives: `public`, `private`, `no-cache`, `no-store`, `max-age`, `s-ma...

The `Cache-Control` HTTP response header is the contract between the origin and every cache in the path (browser, CDN, corporate proxy) about how long to cache and when to revalidate. It is the single most important header for CDN performance. The directives, in order of importance:

| Directive | Meaning | Effect on browser cache | Effect on CDN |
|---|---|---|---|
| `public` | Any cache may store | Cacheable | Cacheable |
| `private` | Only the end-user's browser may store | Cacheable | NOT cacheable (origin meant this is per-user) |
| `no-cache` | Cache MAY store but MUST revalidate before serving | Stores, revalidates | Stores, revalidates |
| `no-store` | Do NOT store at all | Not stored | Not stored |
| `max-age=N` | Fresh for N seconds | Fresh for Ns | Fresh for Ns |
| `s-maxage=N` | (Shared caches only) Fresh for N seconds; overrides `max-age` for CDNs | Ignored | Fresh for Ns |
| `stale-while-revalidate=N` | Serve stale for up to Ns while fetching fresh in background | (Modern browsers) | Serve stale + async refresh |
| `stale-if-error=N` | Serve stale for up to Ns if origin returns 5xx | (Some clients) | Serve stale on origin failure |
| `must-revalidate` | Once stale, MUST revalidate; never serve stale | Revalidate | Revalidate |
| `proxy-revalidate` | Like must-revalidate but only for shared caches | (Browsers may serve stale) | Revalidate |

The `s-maxage` directive is the CDN's best friend. `Cache-Control: max-age=60, s-maxage=3600` tells the browser "you may cache for 60s" but tells the CDN "you may cache for 3600s." This asymmetry is the standard pattern for content that changes occasionally but where you want the browser to re-check frequently while the CDN absorbs the bulk of the load. Without `s-maxage`, the CDN falls back to `max-age`, and you cannot decouple "how long the browser caches" from "how long the CDN caches." Real examples:

```http
# Static asset with content hash in filename (immutable — never changes)
Cache-Control: public, max-age=31536000, immutable
# → Browser caches for 1 year; CDN caches for 1 year; never revalidates.
#   The "immutable" flag tells the browser not even to send a conditional
#   request on reload — useful for hashed filenames like main.a1b2c3.css.

# HTML page that can change without notice (news article)
Cache-Control: public, max-age=60, s-maxage=600, stale-while-revalidate=300
# → Browser caches 60s, CDN caches 600s. After 600s CDN serves stale for up
#   to 300s while fetching fresh in background. So total staleness ceiling
#   is 600s + 300s = 15 minutes from first cache population.

# API response that is per-user (JWT-authenticated dashboard data)
Cache-Control: private, max-age=30
# → Browser caches 30s; CDN does NOT cache (private). Every CDN request
#   is a PASS to the origin. This is the correct behaviour for user-specific
#   data — you do not want one user's dashboard data served to another.

# API response that is shared but volatile (product catalogue — shared, but
# changes on inventory updates)
Cache-Control: public, s-maxage=10, stale-while-revalidate=60
# → CDN caches 10s, then serves stale for up to 60s while revalidating.
#   Browser cache is not used (no max-age for browser). This gives a soft
#   10-second freshness SLA with a 60-second staleness ceiling.

# Response that must NEVER be cached (real-time stock price)
Cache-Control: no-store
# → Neither browser nor CDN stores. Every request hits the origin.
#   Use sparingly — kills CDN benefit entirely.
```

The **`Vary`** header extends the cache key with request-header dimensions. `Vary: Accept-Encoding` means "store separate cache entries per `Accept-Encoding` value" so a Brotli response and a gzip response coexist in the cache. `Vary: Accept-Language` does the same for `Accept-Language`. The `Vary: *` header means "the response varies on something the cache cannot represent; do not cache at all." The `Vary` failure mode is "Vary header pollution" — an origin that adds `Vary: Cookie` (correctly, because the response depends on whether the user is logged in) prevents the CDN from caching anything for logged-in users, because the Cookie header is unique per session. The fix is the **`Cache-Key` normalisation** mentioned above — strip the auth cookie from the cache key when the response is a public resource that happens to set a `Set-Cookie` for analytics purposes.

CDN-specific directives extend `Cache-Control` with non-standard but widely-supported directives. Cloudflare uses `Cache-Tag` for purge-by-tag (see H3 #2). Fastly uses `Surrogate-Control: max-age=3600` as a separate directive that overrides `Cache-Control` for the CDN only — letting you set a longer TTL for the CDN than for the browser without using `s-maxage`. CloudFront has no equivalent and you must use `s-maxage`. These directives are stripped before the response is sent to the browser — they should never leak to the client.

The production failure mode is the inverted `Cache-Control`: an origin that returns `Cache-Control: public, max-age=0` (intended as "do not cache") actually means "you may cache this, but revalidate every time" — which causes every CDN request to issue a conditional revalidation to the origin, defeating the purpose of the CDN. The correct "do not cache" directive is `no-store` (or `private, no-cache` for user-specific data). The metric that reveals the mistake: `origin_request_rate` is equal to `cdn_request_rate` — every request is reaching the origin, either via miss or via revalidation. The expected ratio for a well-cached static site is `origin_request_rate < 1% × cdn_request_rate`.

### Cache Validation: Strong validators (`ETag`) vs. Weak validators (`Last-Modified`) and ...

Once a response is in cache past its `max-age`, the cache must revalidate with the origin before serving it — unless `stale-while-revalidate` covers it. Revalidation is a conditional request: the cache sends a request with a header that says "I have version X; do you have anything newer?" The origin either responds `304 Not Modified` (with an empty body — saving the bandwidth of re-sending the full response) or `200 OK` with the new full body. The validator that identifies "version X" is either a strong validator (the `ETag` header) or a weak validator (the `Last-Modified` header).

**`ETag`** (entity tag) is an opaque string that uniquely identifies the bytes of the response — typically a hash of the body, a file inode+mtime+size, or a versioned revision ID. `ETag: "a1b2c3d4e5f6"` is a "strong" ETag — the bytes are byte-for-byte identical. `ETag: W/"a1b2c3d4e5f6"` (with the `W/` prefix) is a "weak" ETag — semantically equivalent but not byte-identical (e.g. whitespace normalised, comments stripped). The client sends `If-None-Match: "a1b2c3d4e5f6"` on the next request; the origin compares it to the current ETag and returns 304 if they match. ETags are stronger than `Last-Modified` because two writes within the same second produce the same `Last-Modified` but different ETags. The Apache httpd default ETag is `inode-size-mtime` — which breaks across servers in a load-balanced pool (the same file has different inodes on different servers), causing the cache to thrash between 304s and 200s. The fix is `FileETag INode MTime Size` → `FileETag MTime Size` (or, in modern Apache, `FileETag DocumentHash`).

**`Last-Modified`** is a timestamp — the time the resource last changed, to 1-second resolution. `Last-Modified: Wed, 15 Jan 2025 09:28:00 GMT`. The client sends `If-Modified-Since: Wed, 15 Jan 2025 09:28:00 GMT`; the origin returns 304 if the resource has not been modified since that time. The 1-second resolution is the weakness — a resource modified twice within the same second produces the same `Last-Modified`, but the client's cached copy might be the older of the two writes. For static files this rarely matters; for dynamically-generated content it can.

```http
# First request — origin returns full response with validators
GET /products/42 HTTP/1.1
Host: shop.example.com

HTTP/1.1 200 OK
Content-Type: text/html
Cache-Control: public, max-age=60
ETag: "abc123def456"
Last-Modified: Wed, 15 Jan 2025 09:28:00 GMT
Content-Length: 8421

<html>... (8421 bytes of product page) ...</html>


# Subsequent request after max-age expiry — cache revalidates with both validators
GET /products/42 HTTP/1.1
Host: shop.example.com
If-None-Match: "abc123def456"
If-Modified-Since: Wed, 15 Jan 2025 09:28:00 GMT

HTTP/1.1 304 Not Modified
ETag: "abc123def456"
Last-Modified: Wed, 15 Jan 2025 09:28:00 GMT
Cache-Control: public, max-age=60
# No body — cache serves its cached copy. Saved 8421 bytes of bandwidth
# and the origin avoided regenerating the page.
```

The two validators are not redundant — they cooperate. A modern cache sends BOTH `If-None-Match` and `If-Modified-Since`; the origin returns 304 only if both pass (RFC 7232 §6). The CDN's intermediate revalidation follows the same protocol: the CDN's POP sends `If-None-Match` to the origin on every expired cache entry, and serves its cached copy if the origin returns 304. This is the "browser-side conditional request" pattern: even a cache that has expired can serve its cached body if the origin confirms it's still fresh, paying only a tiny 304 round-trip instead of the full body transfer.

The `Vary` header interacts with validators in a subtle way. When a cache stores multiple variants (e.g. one per `Accept-Encoding`), each variant has its own ETag and `Last-Modified`. The cache stores them in a single cache slot keyed by URL + `Vary` dimension. On revalidation, the cache sends `If-None-Match` for the specific variant it has cached. The origin's ETag therefore must encode the variant — a common bug is an origin that returns the same ETag for both gzip and Brotli responses, causing the cache to serve the gzip body to a Brotli-accepting client. The fix is to derive the ETag from the body bytes (so a gzipped body and a Brotli body naturally have different ETags) rather than from the underlying resource state.

The production failure mode is the **stale-forever** incident. An origin returns `Cache-Control: max-age=31536000` (1 year) with a stable `ETag` based on a file path that doesn't change. The CDN caches the response for a year. The origin deploys a new version of the resource but does not change the URL or the ETag (e.g. an in-place edit of a static file without renaming it). The CDN continues serving the stale cached copy for the full year, because no `max-age` expiry triggers a revalidation. The mitigations are: (a) use content-hashed filenames (`main.a1b2c3.css` instead of `main.css`) so a new version has a new URL, naturally invalidating the old cache; (b) use short `max-age` (e.g. 60s) with `s-maxage` longer and rely on `stale-while-revalidate` for the freshness window; (c) use cache-tag-based purging (H3 #2) on every deploy. The metric that reveals this: `cache_hit_ratio` stays high (good) but `user_complaints_about_stale_content` rises (bad) — the cache is "working" but serving yesterday's content.

## How This Connects to the Frameworks

Every backend framework that serves HTTP can emit `Cache-Control` headers. The mechanism differs by framework but the underlying contract is identical — the framework sets the header, the CDN reads it, the CDN caches accordingly. The four ecosystems:

```java
// Spring Boot — set Cache-Control on the ResponseEntity
@GetMapping("/products/{id}")
public ResponseEntity<Product> get(@PathVariable Long id) {
    Product p = service.find(id);
    return ResponseEntity.ok()
        .cacheControl(CacheControl.maxAge(60, TimeUnit.SECONDS)
                                  .sMaxAge(600, TimeUnit.SECONDS)
                                  .staleWhileRevalidate(300, TimeUnit.SECONDS)
                                  .cachePublic())
        .eTag("\"" + p.getVersion() + "\"")     // strong ETag from versioned entity
        .lastModified(p.getUpdatedAt().toEpochMilli())
        .body(p);
}

// Conditional request handling — Spring's ShallowEtagHeaderFilter does this
// automatically, comparing the If-None-Match header to a hash of the response
// body and returning 304 if they match.
```

```typescript
// Express — set headers on the Response
import express from "express";
const app = express();

app.get("/products/:id", (req, res) => {
  const product = service.find(Number(req.params.id));
  res.set("Cache-Control", "public, max-age=60, s-maxage=600, stale-while-revalidate=300");
  res.set("ETag", `"${product.version}"`);
  res.set("Last-Modified", product.updatedAt.toUTCString());
  res.json(product);
});

// Conditional handling — express has no built-in; use the 'fresh' check or
// a middleware like 'etag' that hashes the response body.
app.get("/products/:id", (req, res) => {
  const product = service.find(Number(req.params.id));
  res.set("ETag", `"${product.version}"`);
  if (req.headers["if-none-match"] === `"${product.version}"`) {
    return res.status(304).end();   // 304 — body already cached
  }
  res.json(product);
});
```

```python
# Django — use the cache_page decorator + vary_on_headers
from django.views.decorators.cache import cache_page, vary_on_headers
from django.views.decorators.http import condition

@condition(last_modified_func=lambda r, id: Product.objects.get(pk=id).updated_at,
            etag_func=lambda r, id: f'"{Product.objects.get(pk=id).version}"')
@cache_page(60)                                    # browser-side cache 60s
@vary_on_headers("Accept-Encoding")                # store separate entries per encoding
def product_detail(request, id: int):
    p = Product.objects.get(pk=id)
    response = JsonResponse(p.to_dict())
    response["Cache-Control"] = "public, max-age=60, s-maxage=600, stale-while-revalidate=300"
    response["Cache-Tag"] = f"product-{id}"         # for CDN purge-by-tag
    return response
```

```php
<?php
// Laravel — set headers on the Response, use ETag middleware
Route::get("/products/{id}", function (int $id) {
    $product = Product::findOrFail($id);
    return response()
        ->json($product)
        ->header("Cache-Control", "public, max-age=60, s-maxage=600, stale-while-revalidate=300")
        ->header("ETag", '"' . $product->version . '"')
        ->header("Last-Modified", $product->updated_at->toRfc1123String())
        ->header("Cache-Tag", "product-{$id}");
})->middleware("etag");   // etag middleware: hashes response body, returns 304 on match
```

The cross-cutting concern: frameworks differ in whether conditional-request handling (returning 304) is automatic or manual. Spring Boot has `ShallowEtagHeaderFilter` (computes ETag from response body, handles `If-None-Match` automatically — at the cost of buffering the entire response). Django has the `@condition` decorator (you provide `last_modified_func` and `etag_func`, the decorator handles 304s). Express and Laravel require you to either write the conditional logic by hand or install a middleware. The "automatic" approaches trade CPU (hashing the response body) for developer convenience; the "manual" approaches require you to maintain a version field on the entity but skip the body-hash cost on every request. For high-traffic endpoints, the version-field approach wins because it lets the framework short-circuit the 304 before serialising the response at all.
