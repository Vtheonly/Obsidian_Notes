# 10.03.02. Container Storage and Persistence

## What This Is

Container storage is the discipline of deciding where a process inside a container can write data that survives the container's removal. The default answer — and the trap — is "nowhere": every write a container makes lands in its writable layer, an OverlayFS upperdir that lives in `/var/lib/docker/overlay2/<id>/diff/` on the host. That directory is deleted when the container is removed (`docker rm`), restarted from a different image, or recreated by `docker compose down && up`. A Postgres database running in a container with no volume loses every row when the operator runs `docker compose down` to "clean up."

This note covers the four storage options Docker provides — the ephemeral writable layer, bind mounts, named volumes, and `tmpfs` mounts — and the persistence problem they exist to solve. Each option has a different ownership model (who controls the path: the host admin, Docker, or the kernel), a different portability story (does it survive a host migration?), and a different performance profile (does it go through OverlayFS, the host filesystem, or RAM).

The deep insight is that "stateless containers" is a goal, not a fact — every non-trivial backend has state somewhere (database, session store, file uploads, logs), and the only question is whether that state lives *inside* the container (wrong) or *outside* the container (right, via one of the three volume mechanisms). This sits at the storage layer of the mental model, directly above the filesystem and block-layer primitives from section 02: a named volume backed by the `local` driver is just a directory on the host's filesystem, mounted into the container's mount namespace by `mount --bind`. The runtime layer above (Spring Boot, Postgres, Redis) issues `write()` syscalls that flow through the container's VFS, into the bind mount, and land on the host's ext4/xfs/btrfs.

The failure modes this note governs are: the "I ran `docker compose down` and lost the prod database" disaster (no volume declared for the data directory), the "container can read but not write my host file" permission error (UID mismatch between container process and host file owner), the "database is 3× slower in the container than on bare metal" performance regression (OverlayFS upperdir amplifies every `fsync`), and the "logs fill the host disk" surprise (logs going to the writable layer, which lives on the host root partition).

## The Details

### Ephemeral Container Layers: Data destruction on container removal

Every container is a writable layer stacked on top of the read-only image layers. The writable layer is the OverlayFS `upperdir`; it is where every `write()`, `mkdir()`, `unlink()` from inside the container lands. When you `docker rm` the container, the daemon deletes the upperdir. There is no trash, no snapshot, no recovery — `rm -rf /var/lib/docker/overlay2/<id>/diff/` is the implementation.

```text
  Container's filesystem view (what `ls /` shows inside the container)
  ┌──────────────────────────────────────────────┐
  │  /  (the merged view)                        │
  │  ├── bin  ─┐                                 │
  │  ├── etc  ─┤── read-only: lower layers       │
  │  ├── lib  ─┤   (the image layers)            │
  │  ├── usr  ─┘                                 │
  │  ├── app/  ── writable: upperdir             │
  │  │   └── uploads/image.png  ← write lands here│
  │  └── tmp/  ── writable: upperdir             │
  └──────────────────────────────────────────────┘
        ▲
        │ OverlayFS mount
        │
  Host filesystem: /var/lib/docker/overlay2/<container-id>/
  ├── diff/          ← upperdir (writable, deleted on `docker rm`)
  ├── merged/        ← the merged view (mounted read-only into container)
  ├── lower          ← text file listing the read-only lowerdirs
  └── work/          ← OverlayFS internal work directory
```

This is great for stateless processes — the container starts clean every time, you cannot accumulate cruft, and a redeploy is a guaranteed reset. It is catastrophic for stateful processes. A Postgres container with no volume writes its `data/` directory into the upperdir; `docker rm` of that container is equivalent to `rm -rf /var/lib/postgresql/data` — every table, every index, every transaction log, gone.

```bash
# Prove the layer is ephemeral
docker run --name ephemeral-test alpine sh -c 'echo "important data" > /tmp/data.txt && cat /tmp/data.txt'
# important data
docker start -a ephemeral-test cat /tmp/data.txt
# important data   (still there — same container, same upperdir)
docker rm ephemeral-test
docker run --rm alpine cat /tmp/data.txt
# cat: can't open '/tmp/data.txt': No such file or directory
```

Even restarting the *same* container preserves the layer (`docker stop` + `docker start` keeps the upperdir; only `docker rm` deletes it). But in practice, containers are removed constantly: `docker compose down` removes them, Kubernetes pod eviction removes them, autoscaling removes them, `docker system prune` removes them. Treat the writable layer as scratch space that disappears the moment the container does.

OverlayFS also has a write amplification problem: the first write to a file in a lower layer triggers a copy-up — the entire file is copied from the lowerdir to the upperdir before the write is applied. For a 1 GB SQLite database, the first `UPDATE` copies 1 GB up. For a database doing random writes, every write goes through OverlayFS's copy-up machinery rather than directly to the host filesystem. Production databases should never run on the writable layer — bind mounts or named volumes bypass OverlayFS entirely.

The production failure mode is the operator who treats containers like VMs: they `docker exec` in, see a working Postgres, write some test data, run a load test, and call it good. Two weeks later, an autoscaler evicts the pod, Kubernetes reschedules it onto a different node, and the database is empty — because the data lived in the writable layer of a container that no longer exists. The metric that reveals this is "container restart count" plus "database row count" — if restart count > 0 and row count drops, you have the bug.

### Bind Mounts: Mapping host filesystem paths directly into container directories

A bind mount is the simplest form of persistent storage: `docker run -v /host/path:/container/path image` takes a directory on the host (or a single file) and mounts it into the container's mount namespace at the specified path. The host directory exists before, during, and after the container's lifetime. The container's writes land directly on the host filesystem (no OverlayFS in the path). This is the developer's primary tool for live-reload workflows: bind-mount your source code into the container, and edits you make in your editor are immediately visible to the process inside.

```bash
# Bind mount: host source → container source for live reload
docker run -d \
  --name spring-dev \
  -p 8080:8080 \
  -v /home/me/projects/myapp/src:/app/src:ro \
  -v /home/me/projects/myapp/target:/app/target \
  myapp:dev

# Bind mount a single config file
docker run -v /etc/myapp/application.yml:/etc/myapp/application.yml:ro myapp

# Read-write bind mount for a database (NOT recommended in prod — see below)
docker run -d \
  --name postgres-dev \
  -e POSTGRES_PASSWORD=secret \
  -v /home/me/pgdata:/var/lib/postgresql/data \
  postgres:16
```

The `:ro` (read-only) flag is critical for security-sensitive mounts. Configuration files, TLS certificates, and source code that the container should never modify should always be mounted `:ro`. Without `:ro`, a container escape means the attacker can write to your host's `/etc` directory.

The two sharp edges of bind mounts are **UID/GID mismatch** and **portability**. UID inside the container is the same UID on the host — there is no remapping (unless userns-remap is enabled). If your container process runs as UID 1001 (per the `USER 1001` directive in the Dockerfile) and the host directory is owned by UID 1000 (your laptop user), the container gets `Permission denied` on every write. The fix is either `chown -R 1001:1001 /host/path` on the host, or run the container with `--user $(id -u):$(id -g)` to match the host user.

| Concern | Bind mount | Named volume |
|---|---|---|
| Who controls the path? | You (the host admin) | Docker daemon |
| Where on disk? | Exactly where you say | `/var/lib/docker/volumes/<name>/_data/` |
| Survives `docker compose down`? | Yes (it is your path) | Yes |
| Survives `docker system prune -a --volumes`? | Yes | **No** — named volumes are pruned |
| Portable across hosts? | No (host path is hardcoded) | Yes (recreate on new host) |
| Works on Docker Desktop (macOS/Windows)? | Slower (gRPC FUSE VirtioFS) | Fast (lives in the VM) |
| Initial content | Empty unless host dir has files | Copied from image's path on first mount |
| Backup | `tar` the host dir | `docker run --rm -v <vol>:/data alpine tar czf - /data` |

The portability problem is the killer for production. A bind mount to `/data/pgdata` works on host A but means nothing on host B unless you also copy the data. Named volumes solve this by abstracting the host path: the Compose file says `volumes: pgdata:`, and the daemon decides where on the host that lives. Migrating to a new host means `docker volume export pgdata | ssh hostB docker volume import pgdata` (or, in practice, switching to a network-attached volume driver).

The production failure mode is bind-mounting a host directory into a Postgres container on macOS Docker Desktop. The gRPC FUSE layer that translates between the macOS host filesystem and the Linux VM is ~10× slower than native ext4 for `fsync`-heavy workloads. A Postgres doing 1000 TPS on a Linux host drops to 80 TPS on macOS Docker Desktop with a bind-mounted data directory. The fix is to use a named volume (which lives inside the Linux VM, bypassing the FUSE translation) and accept that the data is harder to inspect from the macOS side.

### Docker Named Volumes: Fully Docker-managed persistent storage outside container lifecycles

A named volume is Docker-managed persistent storage. You create it explicitly (`docker volume create pgdata`), reference it by name in `docker run -v pgdata:/var/lib/postgresql/data`, and Docker takes care of where on the host it lives (`/var/lib/docker/volumes/pgdata/_data/` on Linux). The volume exists until you explicitly remove it with `docker volume rm pgdata` or `docker volume prune`. `docker compose down` does not remove volumes — only `docker compose down -v` does. This is the single most important fact about Compose: the `-v` flag is destructive and easy to type by accident.

```bash
# Create and inspect a named volume
docker volume create pgdata
docker volume inspect pgdata
# [
#     {
#         "CreatedAt": "2024-...",
#         "Driver": "local",
#         "Labels": null,
#         "Mountpoint": "/var/lib/docker/volumes/pgdata/_data",
#         "Name": "pgdata",
#         "Options": null,
#         "Scope": "local"
#     }
# ]

# Use it
docker run -d --name pg -v pgdata:/var/lib/postgresql/data -e POSTGRES_PASSWORD=secret postgres:16

# Back it up
docker run --rm -v pgdata:/data -v $(pwd):/backup alpine \
  tar czf /backup/pgdata-$(date +%F).tar.gz -C /data .

# Restore to a new volume
docker volume create pgdata-restored
docker run --rm -v pgdata-restored:/data -v $(pwd):/backup alpine \
  tar xzf /backup/pgdata-2024-01-15.tar.gz -C /data
```

A subtle but powerful feature: when a named volume is first mounted into a container and the volume is empty, Docker copies the contents of the image's path *into* the volume. If your Postgres image has `/var/lib/postgresql/data` populated with seed data (because you baked it into a custom image), the first container that mounts the named volume gets that seed data. Subsequent mounts see the volume's existing content, not the image's. This is why the first `docker compose up` initializes the database, and the second `docker compose up` starts from where the first left off.

Volume drivers extend named volumes beyond the local disk. The `local` driver is the default and just uses the host filesystem. Third-party drivers add network-attached storage:

| Driver | What it does | Use case |
|---|---|---|
| `local` (default) | Bind-mounts a host directory under `/var/lib/docker/volumes/` | Single-host dev/test, prod on a single node |
| `local` with NFS options | Mounts an NFS share as the volume backing | Shared storage across multiple Docker hosts |
| `local` with `--opt type=tmpfs` | Backs the volume with tmpfs | Fast scratch space that survives container restarts but not host reboots |
| `rexray/ebs` | Provisions an AWS EBS volume per Docker volume | Multi-host Docker Swarm with persistent block storage |
| `azurefile` | Mounts Azure Files share | Azure-based Docker deployments |
| `portworx-volume` | Distributed block storage with replication | Production stateful containers on Kubernetes |

```bash
# NFS-backed named volume
docker volume create --driver local \
  --opt type=nfs \
  --opt o=addr=10.0.0.50,rw \
  --opt device=:/export/pgdata \
  nfs_pgdata
```

The production failure mode is the `docker compose down -v` typo. An operator means to clean up the dev environment, types `docker compose down -v` instead of `docker compose down`, and the `-v` flag wipes every named volume declared in the Compose file. There is no confirmation prompt. The fix is to never declare prod-precious volumes in the same Compose file as ephemeral services — keep the database volume in a separate Compose project with a name that does not match the dev project's naming convention. The second failure mode is forgetting that named volumes are not backed up by `docker save` (which only saves images, not volumes). A backup strategy must explicitly `tar` the volume's contents to external storage on a schedule.

### In-Memory Mounts (`tmpfs`): Fast volatile storage bypassing disk writes

A `tmpfs` mount is a RAM-backed filesystem that Docker mounts into the container. Writes go to memory, not disk; reads are at RAM speed; the contents vanish when the container stops. The flag is `--tmpfs /path` or `--mount type=tmpfs,destination=/path,tmpfs-size=1g`. The kernel enforces a size limit (default 50% of host RAM); exceeding it returns `ENOSPC` (no space left on device).

```bash
# tmpfs for scratch space — fast, ephemeral, never touches disk
docker run -d \
  --name cache \
  --tmpfs /tmp:rw,size=512m,mode=1777 \
  --tmpfs /var/cache/nginx:rw,size=256m \
  nginx:1.25

# Equivalent --mount syntax (more explicit, preferred in scripts)
docker run -d \
  --mount type=tmpfs,destination=/tmp,tmpfs-size=512m,tmpfs-mode=1777 \
  --mount type=tmpfs,destination=/var/cache/nginx,tmpfs-size=256m \
  nginx:1.25
```

```text
  Where writes actually land (per storage type)
  ┌──────────────────┬──────────────────────────────────────────┐
  │ Writable layer   │ host disk → OverlayFS upperdir           │
  │ Bind mount       │ host disk → host filesystem (ext4/xfs)   │
  │ Named volume     │ host disk → host filesystem (ext4/xfs)   │
  │ tmpfs mount      │ host RAM (swappable under pressure)      │
  └──────────────────┴──────────────────────────────────────────┘
```

The canonical use cases for `tmpfs` are: (1) **secrets you do not want on disk** — mount a tmpfs at `/run/secrets/`, write the API key there from an init container, and the secret never touches the host filesystem (so a disk-image forensic snapshot cannot recover it). (2) **Hot caches that should not survive restarts** — Nginx's `/var/cache/nginx`, Redis's swap area, an in-process L1 cache directory. The container restarts clean with no stale cache to invalidate. (3) **Performance** — a build step that writes 4 GB of intermediate artifacts (Maven `target/`, Node `node_modules/.cache/`) runs 5-10× faster on tmpfs than on disk, and you do not want those artifacts persisting anyway.

The `tmpfs-size` limit is the critical knob. If you do not set it, the mount can grow to 50% of host RAM before the kernel starts returning `ENOSPC`. A runaway process writing to a tmpfs can OOM the host. Always set an explicit size: `--tmpfs /scratch:size=1g`. The `tmpfs-mode` flag controls the permissions of the mount point (`1777` for world-writable sticky, `0700` for owner-only).

The interaction with swap is subtle: tmpfs pages are swappable. Under memory pressure, the kernel can write tmpfs contents to swap, which means a tmpfs is not strictly "in RAM" — it is "in RAM until evicted." For workloads that absolutely must not touch disk (cryptographic keys, GDPR-protected data), use `--mount type=tmpfs,...,tmpfs-noswap` (available in Docker 25.0+) or mount with the kernel's `noswap` mount option.

The production failure mode is using tmpfs for data that should be persistent. A developer, impressed by tmpfs speed, configures Redis to persist its RDB snapshots to a tmpfs at `/data`. The container restarts (Kubernetes pod reschedule), the tmpfs is empty, Redis has lost everything. The fix is to read the storage-type table above and match it to the data's persistence requirement: durable data → named volume; cache data → tmpfs; never the other way around. The second failure mode is tmpfs OOM: a Spring Boot app writes its heap dump to `/tmp/heapdump.hprof` on a tmpfs, the heap dump is 4 GB, the tmpfs is 512 MB, the write fails mid-way with `ENOSPC`, and the support engineer cannot get the heap dump they need to debug the original OOM.
