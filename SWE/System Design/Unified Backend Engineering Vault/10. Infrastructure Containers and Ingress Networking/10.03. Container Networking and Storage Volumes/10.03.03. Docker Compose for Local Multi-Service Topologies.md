# 10.03.03. Docker Compose for Local Multi-Service Topologies

## What This Is

Docker Compose is a YAML-driven orchestrator for multi-container applications on a single host. You write a `docker-compose.yml` that declares the services (Postgres, Redis, your Spring Boot app, a worker), the networks that connect them, the volumes that persist their data, and the environment variables and healthchecks that govern their startup order. Then `docker compose up` brings the entire stack up with one command, `docker compose down` tears it down, and `docker compose logs -f app` tails a single service's output. It is the developer's local-datacenter-in-a-file: the same YAML works on every laptop, every CI runner, and every staging host that has Docker installed.

The deep insight is that Compose is not a production orchestrator — it is a *declarative* replacement for the shell script that would otherwise `docker run` six containers in the right order with the right `--network`, `-v`, `-e`, and `--depends-on` flags. Compose parses the YAML, materializes the equivalent `docker run` invocations, and tracks the resulting containers as a single project. It is the same primitives as `docker run` (see [[10.03.01. Docker Networking Mechanics]] and [[10.03.02. Container Storage and Persistence]]), just collected into a versioned file. What Compose adds beyond convenience is (a) cross-service DNS via the user-defined bridge, (b) declarative dependency ordering with health-gated `depends_on`, and (c) reproducibility — the YAML file is the source of truth for "what does the local environment look like."

This sits at the same container layer of the mental model as the previous two notes. The runtime layer above (your Spring Boot app) reads its `SPRING_DATASOURCE_URL` env var, which Compose injected from the `environment:` block, which points at `jdbc:postgresql://db:5432/app` — and `db` resolves via the embedded DNS at `127.0.0.11` to the Postgres container's IP on the Compose-created user-defined bridge. The failure modes this note governs are: race conditions where the app starts before Postgres is ready (no healthcheck, no `depends_on` condition), env var drift between Compose and prod ("works on my laptop" because the YAML hardcodes a secret that prod does not have), volume confusion between `docker compose down` and `docker compose down -v`, and the "Compose file grew to 800 lines and no one understands it" maintenance disaster.

## The Details

### Declaring multi-container architectures: Services, Networks, Volumes, Healthchecks, Environment v...

A Compose file has three top-level keys: `services` (the containers to run), `networks` (the user-defined bridges or overlays to attach them to), and `volumes` (the named volumes to create). Each service is a dictionary whose keys mirror `docker run` flags: `image` or `build`, `ports`, `environment`, `volumes`, `networks`, `depends_on`, `healthcheck`, `command`, `entrypoint`. The full reference for a realistic Spring Boot + Postgres + Redis + Kafka stack:

```yaml
# docker-compose.yml — local dev stack for a Spring Boot + Postgres + Redis + Kafka service
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_DB: appdb
      POSTGRES_USER: app
      POSTGRES_PASSWORD: ${DB_PASSWORD:-devonly}
    volumes:
      - pgdata:/var/lib/postgresql/data
      - ./db/init:/docker-entrypoint-initdb.d:ro
    ports:
      - "127.0.0.1:5432:5432"           # only localhost — never expose DB to network
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d appdb"]
      interval: 5s
      timeout: 3s
      retries: 10
      start_period: 10s
    networks: [appnet]

  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    volumes:
      - redisdata:/data
    ports:
      - "127.0.0.1:6379:6379"
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 2s
      retries: 5
    networks: [appnet]

  kafka:
    image: confluentinc/cp-kafka:7.6.0
    environment:
      KAFKA_NODE_ID: 1
      KAFKA_PROCESS_ROLES: "broker,controller"
      KAFKA_LISTENERS: "PLAINTEXT://0.0.0.0:9092,CONTROLLER://0.0.0.0:9093"
      KAFKA_ADVERTISED_LISTENERS: "PLAINTEXT://kafka:9092"
      KAFKA_CONTROLLER_LISTENER_NAMES: "CONTROLLER"
      KAFKA_CONTROLLER_QUORUM_VOTERS: "1@kafka:9093"
      KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: "CONTROLLER:PLAINTEXT,PLAINTEXT:PLAINTEXT"
      KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1
      KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR: 1
      CLUSTER_ID: "MkU3OEVBNTcwNTJENDM2Qk"
    volumes:
      - kafkadata:/var/lib/kafka/data
    ports:
      - "127.0.0.1:9092:9092"
    healthcheck:
      test: ["CMD", "kafka-broker-api-versions", "--bootstrap-server", "localhost:9092"]
      interval: 10s
      timeout: 5s
      retries: 8
      start_period: 30s
    networks: [appnet]

  app:
    build:
      context: .
      dockerfile: Dockerfile
      target: runtime
    environment:
      SPRING_DATASOURCE_URL: jdbc:postgresql://db:5432/appdb
      SPRING_DATASOURCE_USERNAME: app
      SPRING_DATASOURCE_PASSWORD: ${DB_PASSWORD:-devonly}
      SPRING_DATA_REDIS_HOST: redis
      SPRING_KAFKA_BOOTSTRAP_SERVERS: kafka:9092
      SPRING_PROFILES_ACTIVE: dev
    ports:
      - "8080:8080"
    depends_on:
      db:      { condition: service_healthy }
      redis:   { condition: service_healthy }
      kafka:   { condition: service_healthy }
    networks: [appnet]

  worker:
    build:
      context: .
      dockerfile: Dockerfile
      target: runtime
    command: ["java", "-jar", "app.jar", "--worker"]
    environment:
      SPRING_DATASOURCE_URL: jdbc:postgresql://db:5432/appdb
      SPRING_DATASOURCE_USERNAME: app
      SPRING_DATASOURCE_PASSWORD: ${DB_PASSWORD:-devonly}
      SPRING_KAFKA_BOOTSTRAP_SERVERS: kafka:9092
      SPRING_PROFILES_ACTIVE: dev,worker
    depends_on:
      db:    { condition: service_healthy }
      kafka: { condition: service_healthy }
    networks: [appnet]

volumes:
  pgdata:
  redisdata:
  kafkadata:

networks:
  appnet:
    driver: bridge
```

Three things in this file deserve emphasis. First, the `127.0.0.1:5432:5432` port binding on the database: the leading `127.0.0.1:` binds the published port only to the host's loopback interface, so the database is reachable from the host (for `psql` debugging) but not from the network (so a misconfigured cloud security group cannot expose it to the internet). Without the `127.0.0.1:` prefix, Docker binds to `0.0.0.0` and the database is reachable from any IP that can reach the host.

Second, every service with state has a named volume. The volume names (`pgdata`, `redisdata`, `kafkadata`) are declared in the top-level `volumes:` block. Compose prefixes them with the project name (default: the directory name), so the actual volume on disk is `myproject_pgdata`. This is why `docker compose down` (no `-v`) preserves data and `docker compose down -v` deletes it: the `-v` flag tells Compose to remove the named volumes declared in the YAML.

Third, environment variables use the `${VAR:-default}` shell-expansion syntax. `${DB_PASSWORD:-devonly}` reads `DB_PASSWORD` from the host environment (or from a `.env` file next to the Compose file); if unset, it falls back to `devonly`. The `.env` file is the standard way to keep secrets out of the YAML:

```bash
# .env — gitignored, lives next to docker-compose.yml
DB_PASSWORD=correct-horse-battery-staple
JWT_SIGNING_KEY=base64-encoded-key-here
STRIPE_API_KEY=sk_test_...
```

The Compose CLI commands you use daily:

```bash
docker compose up -d                  # build (if needed), create, start, detach
docker compose up -d --build          # force rebuild of services with `build:`
docker compose up -d app              # start only the app service (and deps)
docker compose down                   # stop + remove containers, keep volumes
docker compose down -v                # stop + remove containers AND volumes (DESTRUCTIVE)
docker compose logs -f app            # tail app's logs
docker compose logs -f --tail=200     # tail all services' last 200 lines, follow
docker compose exec db psql -U app appdb    # run psql inside the running db container
docker compose exec app sh            # shell into the running app container
docker compose run --rm app mvn test  # one-off: run mvn test in a fresh app container
docker compose ps                     # status of all services in the project
docker compose restart app            # restart just the app service (no rebuild)
docker compose pull                   # pull latest images for all services
```

The production failure mode is using Compose in production. Compose is single-host: if the host dies, every service dies, and there is no rescheduling, no rolling update, no horizontal scaling. Production multi-service topologies belong in Kubernetes, Nomad, or Docker Swarm (which uses the same Compose file format via `docker stack deploy` — but Swarm itself is largely abandoned). The second failure mode is the YAML growing to 800 lines as services accumulate; the fix is to split into multiple Compose files (`docker-compose.yml` for the core app, `docker-compose.obs.yml` for observability sidecars, loaded with `docker compose -f docker-compose.yml -f docker-compose.obs.yml up`) and use `extends:` or `include:` (Compose 2.20+) to share service definitions.

### Dependency orchestration: `depends_on` with explicit healthcheck condition evaluation

The `depends_on` key is the Compose mechanism for startup ordering. Without it, Compose starts all services concurrently — the app, the database, the cache, the broker all start at once, racing each other to readiness. The app typically loses this race: it boots in 4 seconds, tries to open a JDBC connection to Postgres, and Postgres is still 8 seconds away from accepting connections. The app crashes with `Connection refused`, the operator gets paged, and the lesson is learned: declare `depends_on`.

The short-form `depends_on: [db, redis, kafka]` only waits for the *container to start* — not for the service inside to be ready. A Postgres container that has just printed its first log line is not yet accepting connections; it still has to recover WAL, initialise shared buffers, and bind to the port. The short form gives you a false sense of safety. The long form with `condition:` is what actually solves the race:

```yaml
services:
  app:
    depends_on:
      db:
        condition: service_healthy     # wait for db's healthcheck to report "healthy"
      redis:
        condition: service_healthy
      kafka:
        condition: service_healthy
      # service_started is the short-form default; service_healthy is the real fix
      # (legacy Compose v2 also had service_completed_successfully for one-shot init containers)
```

The `condition: service_healthy` form requires the dependency to have a `healthcheck` block, and Compose will not start the dependent service until the dependency's healthcheck reports `healthy` for at least one interval. The healthcheck syntax mirrors Docker's:

```yaml
healthcheck:
  test: ["CMD-SHELL", "pg_isready -U app -d appdb"]
  interval: 5s           # how often to run the check (default 30s)
  timeout: 3s            # max time the check may take (default 30s)
  retries: 10            # consecutive failures before "unhealthy" (default 3)
  start_period: 10s      # grace period — failures here don't count (default 0s)
```

The `start_period` is the critical knob for slow-starting services. Kafka takes 20-30 seconds to form a cluster and accept connections; without `start_period: 30s`, the healthcheck starts failing at t=0 and Compose might mark Kafka unhealthy before it has had a chance to finish starting. With `start_period: 30s`, the first 30 seconds of failures are ignored; only failures after the grace period count toward the `retries` threshold.

```text
  Startup timeline with depends_on: condition: service_healthy
  ────────────────────────────────────────────────────────────────────► t (s)
  t=0   Compose starts db, redis, kafka in parallel
  t=2   redis healthcheck passes → redis=healthy
  t=4   db healthcheck passes → db=healthy
  t=12  app still waiting (kafka not healthy yet)
  t=28  kafka healthcheck passes → kafka=healthy
  t=29  Compose starts app → app boots → connects to all deps successfully

  Without healthcheck conditions:
  t=0   Compose starts db, redis, kafka, app in parallel
  t=4   app boots, tries jdbc:postgresql://db:5432 → Connection refused (db not ready)
  t=5   app crashes, Compose restarts it (if restart: on-failure is set)
  t=8   app boots, tries again → Connection refused (db still not ready)
  ...   repeat until db is ready, then succeeds by brute force
```

The `restart:` policy is the complementary defense. `restart: on-failure` (or `restart: unless-stopped`) tells Compose to restart the container if it exits with a non-zero code, with exponential backoff (`100ms, 200ms, 400ms, ...` capped at 60s). This is the belt-and-suspenders approach: `depends_on: condition: service_healthy` is the primary defense (do not start the app until deps are healthy), `restart: on-failure` is the secondary defense (if the app starts but the dep goes unhealthy later, restart the app and try again).

For one-shot initialization (migrate the database before starting the app), Compose's modern pattern is an init service that runs to completion, with the app depending on it via `condition: service_completed_successfully`:

```yaml
services:
  migrate:
    image: myapp/migrate:latest
    command: ["flyway", "migrate", "-url=jdbc:postgresql://db:5432/appdb", "-user=app", "-password=${DB_PASSWORD}"]
    depends_on:
      db: { condition: service_healthy }
    restart: "no"                       # do not restart — failure should stop the whole stack

  app:
    depends_on:
      db:       { condition: service_healthy }
      migrate:  { condition: service_completed_successfully }
```

The production failure mode of the short-form `depends_on: [db]` is the 5% of cold starts where the app loses the race and crashes. In dev this is a nuisance — `docker compose up` again and it works. In CI it is a flaky test that fails 5% of pipeline runs for no apparent reason, eats engineering time, and gets worked around with `sleep 10` in the test runner. The fix is always the long form with `condition: service_healthy` plus a real healthcheck on every dependency. The deeper failure mode is the healthcheck that lies — `pg_isready` returns success when Postgres is accepting connections, but if you are running logical replication, the replica might be hours behind the primary. A "ready" healthcheck for one workload is not "ready" for another; the healthcheck's `test:` command must check the readiness property your specific app depends on.
