# 10.04.04. Load Balancing Algorithms

## What This Is

A load balancer distributes incoming requests across a pool of backend servers. The algorithm it uses decides which server receives each request, and that decision controls three production properties: fairness (does every backend carry equal load?), locality (does the same client keep hitting the same backend, so caches and sessions stay warm?), and resilience (when a backend fails, how quickly does the balancer route around it?). Nginx exposes six algorithms through a single `upstream { ... }` block — pick one by writing a directive at the top of the block (`least_conn;`, `ip_hash;`, `hash $key;`, `random;`, or nothing at all for the default round-robin). Each algorithm has a clear use case and a clear failure mode; mixing them up produces the kind of incident where "we added a third server and throughput went down."

The pool itself is configured with one `server` line per backend, decorated with `weight`, `max_fails`, `fail_timeout`, `backup`, `down`, and `slow_start`. Health checking in the open-source build is passive — Nginx watches the success/failure of real proxied requests and removes a server from rotation once it crosses the failure threshold. Active probing (synthetic `/healthz` checks independent of user traffic) is Nginx Plus only; the open-source equivalent is to drive rotation externally (consul-template rewriting the upstream, kube-proxy updating Endpoints, or AWS ALB target-group health checks feeding an upstream via `resolve` + a dynamic DNS name). This note covers the six algorithms, the per-server modifiers, and the health-check model.

## The Details

### Round Robin (Default), Weighted Round Robin, Least Connections (`least_conn`), IP Hash (`ip_hash`...

Nginx's six load-balancing algorithms are selected by writing one directive at the top of the `upstream` block. If you write nothing, you get plain round-robin. Each algorithm makes a different tradeoff between fairness, locality, and computational cost.

**Round-robin** (default) hands requests to servers in declaration order: server1, server2, server3, server1, server2, server3, … It is the cheapest possible choice — no shared state, no hash computation, just a per-worker rotation through the upstream list. The failure mode is that it assumes all servers are identical in capacity. If you have one c5.2xlarge and one c5.large, round-robin hands them equal traffic and the small one saturates first. **Weighted round-robin** fixes this: `server 10.0.0.11:8080 weight=3; server 10.0.0.12:8080 weight=1;` gives the first server 75% of the traffic and the second 25%, proportional to their capacity. Weights are integers; the algorithm distributes 4 requests as 1→2→1→1 in a deterministic round, so weighting is approximate but stable.

**Least-connections** (`least_conn;`) picks the upstream with the fewest currently-active connections. This is the right choice when request durations vary widely (a fast `/healthz` next to a slow `/api/report/generate`) — round-robin would assign the next report-request to whichever server's turn it is, even if that server is already running three reports, while `least_conn` sends it to whichever server has the lightest queue. The cost is a per-request scan of the server list (cheap, but not free at 100k rps). The interaction with HTTP keepalive: each upstream keepalive connection counts as zero active requests when idle (the `keepalive` pool is separate from the active-connection counter), so `least_conn` makes sensible decisions even when the pool is warm.

**IP-hash** (`ip_hash;`) hashes the client's IPv4 address (first three octets) and uses the hash to pick a server — the same client always lands on the same backend. This is the "sticky session without cookies" pattern. The use case is a backend that stores session state in process-local memory (a Node app using `express-session` with `MemoryStore`, a Python app with `flask-session` filesystem store on a shared volume, a Java app without distributed sessions). The failure mode is twofold. First, hashing by client IP collapses when traffic comes through a corporate NAT or a mobile carrier — thousands of users behind one egress IP all hash to the same backend, producing severe skew. Second, when a backend is added or removed, every client's hash bucket may shift, invalidating every session at once. The fix is to use `consistent` hashing instead (the `hash` directive with `consistent` keyword), which only remaps ~1/N of clients on pool changes.

**Generic hash** (`hash $request_uri consistent;`) hashes any Nginx variable — `$request_uri`, `$http_authorization`, `$arg_user_id` — and is the workhorse for cache-locality. Pair it with `consistent` so adding a backend only remaps a small slice of keyspace. A CDN-style setup: `hash $request_uri consistent;` ensures the same URL always lands on the same backend, so a per-backend in-memory cache (Varnish, Nginx's own `proxy_cache`) stays warm with no duplication across the pool. **Random** (`random;` or `random two least_conn;`) picks a server at random — useful when the cost of scanning the pool outweighs the fairness benefit (very large pools at very high rps). The `random two least_conn` variant picks two servers at random then chooses the least-connected of those two — a cheap approximation of `least_conn` that avoids the full scan.

The `keepalive` directive (separate from the load-balancing algorithm but lives in the same `upstream` block) opens a pool of idle upstream connections that Nginx reuses instead of doing a TCP handshake per request. `keepalive 32;` means "keep up to 32 idle connections warm per worker." Combined with `proxy_http_version 1.1; proxy_set_header Connection "";` in the location block (see 10.04.03), this saves the ~1ms LAN handshake and TLS setup per request — at 10k rps that's 10 saved seconds of CPU per second of wall time across the pool. The failure mode is setting `keepalive` too high for the pool size — `keepalive 100;` with a 3-server pool and 200 rps means most connections are never reused (they time out at `keepalive_timeout` on the backend side first), wasting file descriptors.

```nginx
upstream app_backend {
    # Pick ONE of the following:
    # (default — round-robin)
    # least_conn;
    # ip_hash;
    # hash $request_uri consistent;
    # random two least_conn;

    server 10.0.0.11:8080 weight=3 max_fails=3 fail_timeout=30s;
    server 10.0.0.12:8080 weight=3 max_fails=3 fail_timeout=30s;
    server 10.0.0.13:8080 weight=1 max_fails=3 fail_timeout=30s;   # smaller instance
    server 10.0.0.14:8080 backup;                                   # only on pool failure
    server 10.0.0.15:8080 down;                                     # manual maintenance drain

    keepalive 32;                                                   # idle upstream pool
    keepalive_timeout 60s;                                          # idle timeout
    keepalive_requests 1000;                                        # recycle after 1000 reqs
}
```

| Algorithm | Directive | State needed | Locality | Use case | Failure mode |
|---|---|---|---|---|---|
| Round-robin | (default) | None | None | Homogeneous pool, uniform requests | Skew on heterogeneous capacity |
| Weighted RR | `weight=N` | None | None | Heterogeneous capacity | Wrong weights → hotspots |
| Least-conn | `least_conn;` | Active conn count | None | Variable request duration | Skew under heavy keepalive |
| IP-hash | `ip_hash;` | None | By client IP | In-process session state | NAT/CGNAT collapses hash; pool change invalidates all sessions |
| Generic hash | `hash $k consistent;` | None | By chosen key | Cache locality | Hash distribution skew on hot keys |
| Random | `random [two least_conn];` | None or 2-sample | None | Very large pools | Statistical unfairness at low rps |

### Upstream Health Checks: Passive health checks (`max_fails`, `fail_timeout`) vs. Active synthetic ...

Health checking answers two questions: "is this server dead?" and "how fast do we route around it?" Open-source Nginx answers the first question **passively** — it instruments the success and failure of real proxied requests, and once a server crosses a failure threshold it is removed from rotation. There is no separate probe; the user's traffic is the probe. Active probing (synthetic `/healthz` requests on a timer, independent of user traffic) is the Nginx Plus `health_check` directive, which is closed-source. The open-source workaround is to drive the upstream from an external service-discovery layer (Consul, Kubernetes Endpoints, AWS ALB target groups) whose own health checks remove the server from DNS or from the Endpoints object that Nginx watches via `resolver` + a dynamic upstream.

The passive model uses two per-server parameters: `max_fails=3` (the number of failed proxied requests within the `fail_timeout` window that triggers removal) and `fail_timeout=30s` (the duration of that window, AND the duration the server is marked down before Nginx retries it). A `server 10.0.0.11:8080 max_fails=3 fail_timeout=30s;` line means: if Nginx sees 3 failed requests to this server within 30 seconds, mark it down for 30 seconds; after 30 seconds, send one request to it (the "probe") and either restore it (success) or extend the down period (failure). What counts as a "failed request" is configured by `proxy_next_upstream error timeout http_502 http_503 http_504;` — the directive names the conditions under which Nginx considers the upstream response a failure, increments the fail counter, and transparently retries the request against a different upstream server (so the client never sees the failure, as long as another server is healthy).

```nginx
upstream app_backend {
    server 10.0.0.11:8080 max_fails=3 fail_timeout=30s;
    server 10.0.0.12:8080 max_fails=3 fail_timeout=30s;
    server 10.0.0.13:8080 max_fails=3 fail_timeout=30s;
    server 10.0.0.14:8080 backup;       # only when all 3 primaries are down
}

server {
    location / {
        proxy_pass http://app_backend;

        # What counts as a "failure" — both for retry AND for the max_fails counter:
        proxy_next_upstream      error timeout http_502 http_503 http_504;
        proxy_next_upstream_tries   3;          # don't retry more than 3 servers
        proxy_next_upstream_timeout 10s;        # cap total retry time

        # OPTIONAL (Nginx Plus only — open-source Nginx -t will REJECT this directive):
        # health_check interval=5s fails=2 passes=2 uri=/healthz match=ok;
    }

    # Open-source workaround: a /healthz location that returns 200 from Nginx itself.
    # External monitoring (Prometheus blackbox_exporter, Consul, kubelet) pings this
    # and updates service discovery. Nginx reloads with the new upstream when needed.
    location = /healthz {
        access_log off;
        return 200 'ok\n';
        add_header Content-Type text/plain;
    }
}
```

The `backup` flag marks a server that is only used when all non-backup servers are down (or marked `down`). Typical use: a static "sorry page" server that returns a 503 with a branded error page when the entire backend pool is unreachable. The `down` flag is the manual drain switch — Nginx skips this server entirely, even though it is still in the config. The standard deploy workflow is: edit the config to add `down` to the server you want to drain, run `nginx -t && nginx -s reload`, watch the active connections on that server's `/metrics` endpoint drain to zero over the next 30–60 seconds, then terminate the instance. This is the "graceful drain" pattern that lets you restart backends for security patches without dropping any in-flight requests.

The `slow_start=30s` parameter (Nginx Plus only, but worth knowing because cloud LBs have equivalents — AWS ALB's "deregistration delay" + "slow ramp" is the open-source analogue) gradually increases the weight of a newly-recovered server from 0 to its configured weight over 30 seconds, preventing the "thundering herd" where a server that just finished booting gets hammered with full traffic before its JIT-compiled code, connection pools, and caches are warm. The open-source workaround is to bring the server up with `weight=1` initially, then reload to bump it to `weight=3` after a warm-up period — manually scripted via a deploy hook.

The production failure mode that catches every team once: a backend takes 10 seconds to respond (a slow database query), and `proxy_next_upstream` is configured to retry on `timeout`. The first request times out at `proxy_read_timeout` (say 60s), Nginx retries the same request against the next server, which also takes 10s… and meanwhile the original request is still running on the original backend. The result is **request amplification** — one user request becomes three concurrent backend requests, each holding a database connection and running the same expensive query. The database connection pool saturates, every request now takes 60s, Nginx retries everything, and the system collapses in a feedback loop. The fix is `proxy_next_upstream_tries 1` for non-idempotent POST/PUT requests (set in a `location ~* \.(POST|PUT|PATCH)` block) and `proxy_next_upstream_tries 2` only for GET. The deeper fix is to ensure the backend's request timeout is shorter than `proxy_read_timeout` so the backend cleanly 504s before Nginx gives up — the backend's own 504 is then NOT a transient failure worth retrying.
