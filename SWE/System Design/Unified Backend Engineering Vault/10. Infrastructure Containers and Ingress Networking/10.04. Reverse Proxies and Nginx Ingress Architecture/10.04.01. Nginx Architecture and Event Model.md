# 10.04.01. Nginx Architecture and Event Model

## What This Is

Nginx (pronounced "engine-x") is an event-driven HTTP server, reverse proxy, and load balancer. It is the front door of a substantial fraction of the internet — somewhere between 30% and 40% of all web traffic crosses an Nginx instance on its way to an origin server. This note covers the *architecture* of Nginx: its master-and-workers process model, its single-threaded `epoll` event loop, why that design lets it handle tens of thousands of concurrent connections with megabytes of RAM where Apache's thread-per-connection model hits a wall at hundreds, and the difference between a forward proxy and a reverse proxy (a distinction that is older than Nginx but that Nginx's design surfaces in sharp relief).

The deep insight is that Nginx is the canonical example of the reactor pattern: a single thread blocks on `epoll_wait`, the kernel wakes it when any of thousands of sockets is readable or writable, the thread processes exactly the I/O that is ready, then goes back to `epoll_wait`. No thread-per-connection, no context switches, no per-connection stack allocation. Memory per connection is ~2 KB (a connection record in Nginx's connection pool) versus Apache's ~8 MB (a pthread stack). This is why Nginx scales to 50,000 concurrent connections on a 1 GB VM where Apache prefork exhausts memory at 1,000.

This sits at the network layer of the mental model, directly above the kernel's socket and `epoll` primitives from section 02. The runtime layer above (your Spring Boot app on port 8080) speaks HTTP to Nginx over a loopback or container-network socket; Nginx speaks HTTP/HTTPS to the client and translates between the two. The failure modes this note governs are: the "50,000 connections and Nginx is at 99% CPU because `worker_processes` is 1 on an 8-core box" misconfiguration, the "uploads above 1 MB fail" silent `client_max_body_size` default, the "TLS handshake takes 300 ms because Nginx is doing it on the worker thread without session resumption" performance regression, and the "one slow client ties up a backend thread" head-of-line blocking that Nginx's buffering exists to solve.

## The Details

### Forward Proxy vs. Reverse Proxy configurations

A proxy is a server that sits between a client and an origin server, terminating one TCP connection and opening another. The direction of the trust relationship decides whether it is a *forward* proxy or a *reverse* proxy — and the two are mirror images of each other.

```text
  FORWARD PROXY (the client's proxy)
  ─────────────────────────────────────────────────
  Client ──► [Forward Proxy] ──► Internet ──► Origin (anywhere)
                ▲
                │ The client KNOWS about the proxy.
                │ The proxy is configured in the client's settings.
                │ The origin does NOT know who the real client is.
                │ Use: corporate egress filtering, anonymity (Tor),
                │      caching for an organization, geo-spoofing.

  REVERSE PROXY (the origin's proxy)
  ─────────────────────────────────────────────────
  Client ──► Internet ──► [Reverse Proxy] ──► Origin (specific backend)
                              ▲
                              │ The client does NOT know about the proxy.
                              │ The client thinks it is talking to the origin.
                              │ The origin does NOT know who the real client is
                              │   (until the proxy adds X-Forwarded-For).
                              │ Use: TLS termination, load balancing,
                              │      rate limiting, static file serving,
                              │      canary deploys, blue/green deploys.
```

The forward proxy sits on the *client side* and acts on behalf of the client. When you set `http_proxy=http://proxy.corp:3128` in your shell, every outbound request from your laptop goes to `proxy.corp:3128`, which then opens a connection to the real destination. The destination sees the request coming from the proxy's IP, not your laptop's. Corporate networks use this to filter egress (block requests to known-bad domains), cache large downloads (a Linux ISO downloaded once is served to every employee from cache), and log traffic (which employee accessed which site). The forward proxy is configured in the client (browser, shell, OS) — the destination server has no idea it exists.

The reverse proxy sits on the *server side* and acts on behalf of the origin. When you visit `https://example.com`, your browser connects to example.com's reverse proxy (which is what owns the public IP and the TLS certificate). The proxy terminates TLS, inspects the request, decides which backend to forward to (based on URL path, Host header, cookie, weight), opens a plain-HTTP connection to that backend, gets the response, and ships it back to your browser. Your browser never sees the backend's IP address. The reverse proxy is configured in the server infrastructure — the client has no idea it exists (except that the `Server` response header sometimes says `nginx`).

| Dimension | Forward proxy | Reverse proxy |
|---|---|---|
| Sits on which side? | Client | Server |
| Who configures it? | Client (browser/OS) | Server ops team |
| Client aware of it? | Yes (must be configured) | No (transparent) |
| Origin aware of it? | No (sees proxy IP) | No (sees proxy IP, needs `X-Forwarded-For`) |
| Use cases | Egress filtering, anonymity, geo-spoofing, corporate caching | TLS termination, load balancing, rate limiting, canary deploys, static files, API gateway |
| Common software | Squid, TinyProxy, corporate ZTNA agents | Nginx, HAProxy, Envoy, Traefik, Caddy, AWS ALB |
| Default port | 3128, 8080 | 80, 443 |

Nginx can do both, but it is overwhelmingly used as a reverse proxy. The configuration difference is fundamental: a forward proxy uses `proxy_pass http://$http_host$request_uri;` (forward to whatever host the client requested), while a reverse proxy uses `proxy_pass http://backend;` (forward to a specific named upstream). The forward proxy must support `CONNECT` for HTTPS tunneling (because the client wants end-to-end TLS to the real origin, and the proxy cannot decrypt it without a MITM CA installed on the client). The reverse proxy terminates TLS itself (because the client expects TLS to terminate at the proxy's hostname, which is the origin's public hostname).

The production failure mode of confusing the two is the "I configured my Nginx as a forward proxy and now it is an open relay" disaster. A misconfigured `proxy_pass` that uses `$http_host` (the client-supplied Host header) instead of a fixed upstream turns your Nginx into an open proxy that anyone on the internet can use to launder traffic through your IP. Within hours you are on every IP blocklist, your cloud provider has suspended the account for abuse, and your outbound bandwidth bill has quadrupled. The fix is to never use `$http_host` in `proxy_pass` unless you are explicitly building a forward proxy with authentication in front of it.

### Nginx Process Model: Master Process (Privileged operations, configuration loading) + Single-Threa...

Nginx runs as one master process plus N worker processes (plus a couple of optional helper processes for cache loading and cache management). The master is the privileged parent; the workers are the unprivileged children that actually handle traffic. This split exists for two reasons: (1) binding to port 443 or 80 requires `CAP_NET_BIND_SERVICE`, which on most Linux distributions means root, and (2) you want the worker that handles untrusted client traffic to drop privileges as fast as possible so that a memory-corruption bug in the worker cannot be turned into host takeover.

```text
  Nginx process tree (visible with `ps -ef | grep nginx`)

  UID    PID  PPID  CMD
  root   1234   1   nginx: master process /usr/sbin/nginx -c /etc/nginx/nginx.conf
  nginx  1235 1234  nginx: worker process
  nginx  1236 1234  nginx: worker process
  nginx  1237 1234  nginx: worker process
  nginx  1238 1234  nginx: worker process
  nginx  1239 1234  nginx: cache loader process
  nginx  1240 1234  nginx: cache manager process
```

The master's responsibilities are narrow: read and parse `nginx.conf`, validate it (`nginx -t`), bind to the configured `listen` ports while still root, fork the worker processes, drop privileges to the `nginx` user inside the workers, and watch the workers. If a worker dies (crash, OOM), the master forks a replacement. If the master receives `SIGHUP`, it re-reads the config, forks new workers with the new config, and signals the old workers to drain and exit — this is Nginx's zero-downtime config reload (`nginx -s reload`). If the master receives `SIGTERM`, it signals workers to stop accepting new connections, finishes in-flight requests, and exits.

```nginx
# /etc/nginx/nginx.conf — the master's view

user  nginx;                              # drop to this UID in workers
worker_processes auto;                    # one worker per CPU core (auto = nproc)
worker_rlimit_nofile 65535;               # max FDs per worker (must be >= worker_connections)
error_log /var/log/nginx/error.log warn;
pid       /var/run/nginx.pid;

events {
    worker_connections 8192;              # max concurrent connections per worker
    use epoll;                            # event multiplexer: epoll on Linux, kqueue on BSD
    multi_accept on;                      # accept all pending connections at once per epoll_wait
}

http {
    # ... (all server/location blocks live here — see 10.04.02 for the hierarchy)
    sendfile      on;
    tcp_nopush    on;
    tcp_nodelay   on;
    keepalive_timeout  65;
    keepalive_requests 1000;
    client_max_body_size 10m;
    include /etc/nginx/conf.d/*.conf;
}
```

`worker_processes auto` is the single most important tuning directive. It tells Nginx to fork one worker per CPU core. With 4 cores you get 4 workers; with 32 cores you get 32 workers. Each worker is single-threaded and runs its own `epoll` loop, so they do not contend on each other's connections — they each own a disjoint subset of the listening sockets' accept queue. The kernel's `SO_REUSEPORT` option (which Nginx can enable with `listen 80 reuseport;`) goes further: each worker gets its own kernel-level accept queue, eliminating the thundering-herd problem where multiple workers wake up on the same connection arrival and one wins while the others waste a context switch.

`worker_connections` caps the number of concurrent connections a single worker will handle. The default is 512 (ancient); production values are 4096 to 65536. The formula for max clients is `worker_processes × worker_connections / 2` (divide by 2 because each client connection uses two FDs if Nginx is proxying: one for the client, one for the backend). So 4 workers × 8192 connections / 2 = 16,384 concurrent proxied clients. The `worker_rlimit_nofile` must be at least `worker_connections × 2` to allow for the dual-FD usage, and the host's `ulimit -n` (in `/etc/security/limits.conf` or the systemd unit) must be at least that high — otherwise Nginx logs `accept4() failed (24: Too many open files)` and stops accepting connections.

The production failure mode is `worker_processes 1` on a multi-core box. Nginx scales linearly with worker count up to the number of cores; one worker on an 8-core machine leaves 7 cores idle. The metric that reveals this is per-CPU utilization: `mpstat -P ALL 1` shows one core at 99% (the worker) and seven cores near 0% (idle). The fix is `worker_processes auto`. The opposite failure mode is `worker_processes 32` on a 4-core machine — workers thrash on the same 4 cores, context-switch overhead dominates, and total throughput is worse than `worker_processes 4`. The `auto` setting is almost always correct.

### Non-blocking architecture: Processing tens of thousands of concurrent connections with minimal me...

The reason a single Nginx worker can handle 8,192 concurrent connections is that it never blocks on I/O. Every socket operation is non-blocking: `read()` returns `EAGAIN` if no data is available, `write()` returns `EAGAIN` if the kernel buffer is full, and the worker registers interest in each socket with `epoll_ctl(EPOLL_CTL_ADD, fd, EPOLLIN|EPOLLOUT|EPOLLET)`. The worker then calls `epoll_wait()` once and blocks until the kernel reports that at least one of the registered sockets is ready. The kernel does the multiplexing; the worker does the work.

```text
  Nginx worker's event loop (single thread, no locking, no context switches)

  ┌────────────────────────────────────────────────────────────────┐
  │ while (1) {                                                    │
  │   events = epoll_wait(epfd, &ready_list, -1, timeout);         │
  │   for (ev in ready_list) {                                     │
  │     conn = ev.data;                                            │
  │     if (ev.events & EPOLLIN)  conn->read_handler(conn);        │
  │     if (ev.events & EPOLLOUT) conn->write_handler(conn);       │
  │   }                                                            │
  │ }                                                              │
  └────────────────────────────────────────────────────────────────┘

  For each connection, the read_handler / write_handler runs a small
  state machine:

    ngx_http_wait_request_handler    → read request line
    ngx_http_process_request_line    → parse headers
    ngx_http_process_request_headers → dispatch to location handler
    ngx_http_upstream_handler        → connect to backend, forward request
    ngx_http_upstream_process_header → read backend response headers
    ngx_http_upstream_process_non_buffered_downstream → stream to client

  Each handler does as much work as it can without blocking, then returns
  control to the event loop. If a handler needs more data (e.g. only
  half the request body has arrived), it re-registers interest in EPOLLIN
  and returns. The next epoll_wait will wake the worker when more data
  arrives.
```

The contrast with Apache's prefork MPM (one process per connection, blocking I/O) and worker MPM (one thread per connection, blocking I/O) is stark:

| Property | Apache prefork | Apache worker | Nginx |
|---|---|---|---|
| Concurrency unit | Process | Thread | epoll event |
| Memory per connection | ~2 MB (process) | ~64 KB (thread stack) | ~2 KB (connection record) |
| 10k concurrent connections | ~20 GB RAM | ~640 MB RAM | ~20 MB RAM |
| Blocking syscall on slow client | Blocks the whole process/thread | Blocks the thread | Returns `EAGAIN`, worker serves others |
| TLS handshake cost | On the worker thread (blocks) | On the worker thread (blocks) | On the worker, but workers are many and cheap |
| Default deploy for "lots of slow clients" | Falls over | Falls over | Handles it |

The single sharp edge of the event-loop model is that *any* blocking operation inside a worker stalls every connection that worker is handling. If your Nginx module (or your Lua script via `ngx_http_lua_module`, or your `proxy_pass` to a backend that hangs) blocks for 100 ms on a synchronous syscall, every one of the 8,192 connections on that worker waits 100 ms. This is why Nginx's own modules are obsessively non-blocking: the disk I/O for static file serving uses `aio` (asynchronous I/O on Linux) or `sendfile` (zero-copy kernel-to-socket), the upstream module uses non-blocking connect with `EPOLLOUT` to detect connection establishment, and even the DNS resolver is async (a worker that needs to resolve `backend.example.com` registers a timer, fires off the UDP query, and goes back to the event loop; the response wakes it via `EPOLLIN` on the DNS socket).

The `proxy_pass` directive is where the reverse-proxy use case meets the event loop. A request arrives, the worker reads the request line and headers, matches a `location` block, executes the `proxy_pass` directive — which opens a non-blocking TCP connection to the upstream, forwards the request, and registers interest in the upstream's response. While waiting for the upstream, the worker is free to handle other connections' I/O. When the upstream responds, the worker reads its headers, optionally buffers the body to disk (if `proxy_buffering on`, the default), and writes the response back to the client at whatever rate the client can accept. A slow client on a 3G mobile connection does not tie up the upstream's connection — Nginx drains the upstream fast, closes the upstream connection (returning it to the backend's pool), and trickles the response to the slow client over seconds or minutes.

The production failure mode is the custom module or Lua script that does a synchronous `gethostbyname()` or a blocking file read. The symptom is "Nginx is at 100% CPU on one worker but the other workers are idle" — the stuck worker is busy-waiting or sleeping on a syscall instead of returning to `epoll_wait`. The metric that reveals this is `nginx_connections_active` (high) combined with `nginx_connections_reading` or `nginx_connections_writing` (also high) on one worker — those connections are parked, waiting for the worker to come back to the event loop. The fix is to use only Nginx's built-in async primitives: the `resolver` directive for async DNS, `aio` for async file I/O, and `proxy_pass` (which is async by construction) instead of custom upstream logic.
