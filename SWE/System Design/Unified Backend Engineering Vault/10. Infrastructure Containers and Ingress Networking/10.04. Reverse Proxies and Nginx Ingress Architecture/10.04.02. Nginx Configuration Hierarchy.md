# 10.04.02. Nginx Configuration Hierarchy

## What This Is

Nginx is configured through a single declarative file (`/etc/nginx/nginx.conf`) that is parsed into a tree of nested **contexts**. Each context is a brace-delimited block that scopes a family of directives: `worker_processes` only makes sense at the process level, `keepalive_timeout` only at the HTTP level, `proxy_pass` only inside a `location`. The hierarchy is fixed — `main` → `events` / `http` → `server` → `location`, with `upstream` blocks hanging off `http` for backend pools. Misplacing a directive (for example `proxy_pass` directly in `http`) fails `nginx -t` with `"proxy_pass" directive is not allowed here`; the parser refuses to start. That strictness is the feature — it makes the configuration a typed schema rather than a flat bag of keys.

In production the single `nginx.conf` file is almost never used directly. It contains one or more `include` directives that pull in fragments from `conf.d/*.conf` (RHEL/CentOS convention) or `sites-enabled/*` (Debian/Ubuntu convention, with `sites-available` storing the source of truth and `sites-enabled` storing symlinks). The operator's workflow is: edit a fragment, run `nginx -t` to validate the whole tree, then `nginx -s reload` to send `SIGHUP` to the master process — the master spawns new workers with the new config, while old workers finish in-flight requests and exit. This note walks the full hierarchy and the validation/reload lifecycle.

## The Details

### Directives and Contexts: `main`, `events`, `http`, `server`, `location`, `upstream`

Nginx parses `nginx.conf` top-down into six nested contexts. The `main` context is the implicit top-level scope — anything written outside a brace block lives in `main` and applies to the master process and all workers. The `events` block configures the connection-processing substrate that 10.04.01 covered in depth (the `epoll`/`kqueue` event loop, `worker_connections` per worker, `use epoll` to force the backend). The `http` block is where the HTTP parser lives — every directive at this level is shared by all virtual hosts, so `sendfile on`, `tcp_nopush on`, `keepalive_timeout 65s`, `gzip on`, and `include /etc/nginx/mime.types` all sit here. Inside `http` you declare one `server` block per virtual host (each with its own `listen` and `server_name`), and inside `server` you declare one `location` block per URL pattern.

The `upstream` block is the odd one out — it lives in `http` but is not nested inside any `server`. It names a pool of backend servers so that `server`/`location` blocks can refer to the pool by name (`proxy_pass http://app_backend;`). This separation is what lets a single upstream be shared across multiple virtual hosts (e.g. the API on `api.example.com` and the dashboard on `dashboard.example.com` both proxying to the same `app_backend` upstream). The full annotated tree:

```nginx
# main context — runs as root master, workers drop privileges
user  nginx;
worker_processes  auto;             # one per CPU core; matches the event-model note
error_log  /var/log/nginx/error.log warn;
pid        /var/run/nginx.pid;

# events context — the epoll loop substrate
events {
    worker_connections  1024;       # per-worker FD ceiling; 1024 × N workers
    use epoll;                       # force Linux epoll (BSD would use kqueue)
    multi_accept on;                 # accept all pending connections per epoll wake
}

# http context — global HTTP parser settings
http {
    include       /etc/nginx/mime.types;
    default_type  application/octet-stream;

    sendfile        on;              # zero-copy sendfile(2) for static files
    tcp_nopush      on;              # cork until full MSS — works with sendfile
    keepalive_timeout  65;           # client→nginx keepalive (NOT upstream keepalive)
    client_max_body_size 25m;        # body buffer ceiling before 413 Payload Too Large

    gzip  on;
    gzip_types text/plain application/json application/javascript text/css;

    log_format  main  '$remote_addr - $remote_user [$time_local] '
                      '"$request" $status $body_bytes_sent '
                      '"$http_referer" "$http_user_agent"';
    access_log  /var/log/nginx/access.log  main;

    # upstream block — backend pool, referred to by name from any server/location
    upstream app_backend {
        server 10.0.0.11:8080 max_fails=3 fail_timeout=30s;
        server 10.0.0.12:8080 max_fails=3 fail_timeout=30s;
        server 10.0.0.13:8080 backup;     # only used when primaries fail
        keepalive 32;                      # idle upstream connection pool
    }

    # server block — one per virtual host
    server {
        listen      80;
        listen      443 ssl http2;
        server_name api.example.com;

        ssl_certificate     /etc/ssl/api.example.com.fullchain.pem;
        ssl_certificate_key /etc/ssl/api.example.com.key;

        # location block — one per URL pattern
        location / {
            proxy_pass http://app_backend;
            proxy_set_header Host              $host;
            proxy_set_header X-Real-IP         $remote_addr;
            proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
        }

        location /static/ {
            root /var/www/api.example.com;     # serves /var/www/api.example.com/static/...
            expires 1h;
            add_header Cache-Control "public";
        }
    }

    include /etc/nginx/conf.d/*.conf;         # RHEL/CentOS: extra virtual hosts here
    # include /etc/nginx/sites-enabled/*;     # Debian/Ubuntu: symlinks into sites-available
}
```

The two layout conventions differ in how they treat the "enabled" set. RHEL/CentOS uses `conf.d/*.conf` — every file present is loaded, period; to disable a site you rename or remove the file. Debian/Ubuntu uses `sites-available/` (the source of truth) plus `sites-enabled/` (a directory of symlinks); to disable a site you `rm /etc/nginx/sites-enabled/foo` and the `sites-enabled/*` include no longer picks it up. Both work; the Debian pattern is friendlier to configuration management tools (Puppet/Chef/Ansible can ship every site definition to `sites-available` and toggle the symlink per environment), while the RHEL pattern is one less moving part.

The validation/reload lifecycle is the contract that lets you change config without dropping connections. `nginx -t` parses the entire tree (every included file) and runs schema checks — wrong context, unknown directive, unbalanced braces, missing semicolons — without touching the running master. If it prints `syntax is ok` and `test is successful`, the config is safe to apply. `nginx -s reload` then sends `SIGHUP` to the master, which (1) re-reads `nginx.conf`, (2) spawns a fresh generation of workers with the new config, and (3) signals old workers to stop accepting new connections but finish their in-flight requests before calling `exit(0)`. The reload is therefore graceful — no 502s, no dropped keepalives — provided you remembered the `nginx -t` step. Skipping `nginx -t` and going straight to reload means a typo in a vhost fragment tears down the entire nginx (the master fails to start new workers, the old workers are already winding down, and you have a full outage); this is the classic "I edited one site and broke them all" incident. The mitigation is a deploy hook that runs `nginx -t && nginx -s reload` as one atomic command.

### Location block matching precedence: Exact (`=`), Prefix with highest priority (`^~`), Regex case-...

When Nginx receives a request URI, the `server` block is chosen by `Host` header vs `server_name`, then the `location` inside that server is chosen by matching the URI against the registered patterns. The match algorithm is NOT first-match-wins or longest-match-wins in the naive sense — it runs in four passes with strict precedence. Knowing the order is the difference between a request hitting your reverse proxy and hitting the wrong static file handler.

The precedence, highest to lowest, is:

1. **Exact match** — `location = /healthz { ... }`. If the URI is byte-identical to `/healthz`, this location wins and no other matching happens. Use it for health-check endpoints where you want zero overhead (no regex evaluation, no prefix walk) and a fixed 200-OK response. A typical trick: `location = /healthz { access_log off; return 200 'ok'; add_header Content-Type text/plain; }` — health-check traffic is constant and high-volume, and routing it through the normal location tree pollutes access logs and burns CPU.
2. **Highest-priority prefix** — `location ^~ /static/ { ... }`. The `^~` modifier means "if this prefix matches, stop — do not evaluate regexes." Use it for paths where you know no regex should override (static asset trees). Without `^~`, a regex match would still outrank a plain prefix match even if the prefix was longer.
3. **Regex** — `location ~ \.php$ { ... }` (case-sensitive) or `location ~* \.(jpg|png|gif)$ { ... }` (case-insensitive). Regexes are evaluated in declaration order; the first match wins. They are expensive — every request URI is run through PCRE — so order them hot-to-cold and prefer prefix locations where possible.
4. **Plain prefix** — `location /api/ { ... }`. The longest matching prefix wins, but only after exact, `^~`, and regex have all failed. Plain prefix matches are the workhorse of API routing.

The trap that catches every operator once: a regex location silently shadows a plain prefix you intended to catch a broader URL space. Suppose you write:

```nginx
location /api/    { proxy_pass http://app_backend; }   # plain prefix, low priority
location ~ \.php$ { proxy_pass http://legacy_php; }     # regex, higher priority
```

A request to `/api/upload.php` will hit the **regex** location and proxy to `legacy_php`, not to `app_backend`, even though `/api/` looks like it should match. The fix is either `location ^~ /api/` (skip regex evaluation for that prefix) or restructure the routes. The matching table makes the precedence concrete:

| Modifier | Example URI pattern | Match type | Priority | Use case |
|---|---|---|---|---|
| `=` | `= /healthz` | Exact byte match | 1 (highest) | Health checks, robots.txt |
| `^~` | `^~ /static/` | Prefix, skip regex | 2 | Static asset directories |
| `~` | `~ \.php$` | Regex, case-sensitive | 3 | File-extension routing |
| `~*` | `~* \.(jpg\|png)$` | Regex, case-insensitive | 3 | Case-insensitive extension routing |
| (none) | `/api/` | Longest prefix | 4 (lowest) | API gateways, default reverse proxy |

Another subtle point: `location` matching operates on the **decoded URI**. A request to `/api/users%2F42` is decoded to `/api/users/42` before location matching, which means a `location ~ /users/(\d+)$` regex would match even though the wire path was URL-encoded. This is usually what you want, but it is a security-relevant behavior — if you have a `location ^~ /admin/` block guarding an admin panel, an attacker cannot bypass it with `/admin%2F` because the decoded form `/admin/` still matches the prefix. The failure mode is the inverse: forgetting that decoding happens and writing a regex that over-matches. The fix is `nginx -t` (catches syntax errors) plus `tail -f /var/log/nginx/access.log` while you test a new location set with `curl` against the exact URIs you expect.
