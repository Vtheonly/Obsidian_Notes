# 10.04.03. Reverse Proxy Routing and Buffering

## What This Is

A reverse proxy is a server that accepts client HTTP requests and forwards them to one or more backend application servers, then returns the backend's response to the client. Nginx is the canonical implementation; the same model exists in HAProxy, Traefik, Envoy, and the cloud load balancers (AWS ALB, GCP HTTP(S) LB). Two concerns dominate the design: **routing** (where the request goes, what headers it carries, how the URL is rewritten) and **buffering** (how the response body flows back through the proxy). Routing governs correctness — does the backend see the right `Host`, the right client IP, the right scheme? Buffering governs performance — does a slow mobile client hold a Tomcat worker thread open for 30 seconds, or does Nginx absorb the slow write while the worker immediately handles the next request?

The mental model: every reverse proxy is a translator between two TCP connections. The client→proxy connection speaks one dialect (slow, mobile, behind NAT, possibly HTTP/2 over TLS 1.3); the proxy→upstream connection speaks another (fast, data-centre LAN, often HTTP/1.1 keepalive). The proxy's job is to bridge the dialects without either side blocking the other. This note covers the four header transformations that make upstreams behave correctly behind a proxy, and the buffering configuration that decides whether slow clients can starve your backend of workers.

## The Details

### `proxy_pass` mechanics and header transformations (`Host`, `X-Real-IP`, `X-Forwarded-Fo...`...

The `proxy_pass` directive is the workhorse of the reverse proxy. Inside a `location` block it tells Nginx "instead of serving this from the local filesystem, open a new connection to the named upstream (or literal URL) and forward the request." A trivial example: `location /api/ { proxy_pass http://app_backend; }` — every request matching `/api/` is forwarded to the `app_backend` upstream pool. Two syntactic details matter. First, if `proxy_pass` ends without a URI (just `http://host`), Nginx forwards the **original request URI** unchanged. Second, if it ends with a URI (`http://host/internal/`), Nginx replaces the matched `location` prefix with the proxy_pass URI — `location /api/ { proxy_pass http://app_backend/internal/; }` rewrites `/api/users/42` to `/internal/users/42`. Get this wrong and the backend sees 404s on every request, even though `nginx -t` is happy.

The forward direction (client → upstream) is half the work. The other half is making sure the upstream sees the correct request metadata. By default, when Nginx opens the upstream connection it sets the `Host` header to the upstream's hostname (e.g. `app_backend`), not the original `Host` the client sent (e.g. `api.example.com`). A backend that does virtual-host routing on `Host` will then route every request to the wrong vhost. The fix is `proxy_set_header Host $host;`. Similarly, by default the upstream sees `remote_addr = 10.0.0.1` (the proxy's IP) instead of the real client IP — every access log, every rate limiter, every audit record shows the proxy. The four-header recipe every reverse proxy must set:

```nginx
location /api/ {
    proxy_pass http://app_backend;

    proxy_set_header Host              $host;
    proxy_set_header X-Real-IP         $remote_addr;
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;

    # Optional but common:
    proxy_set_header X-Request-ID      $request_id;        # for distributed tracing
    proxy_http_version 1.1;                                 # enables upstream keepalive
    proxy_set_header Connection        "";                  # clear hop-by-hop "close"
}
```

Each header has a specific job. **`Host`** lets the upstream pick the right virtual host and generate correct absolute URLs. **`X-Real-IP`** carries the immediate client IP (the TCP peer of Nginx) — simple but lossy when there are multiple proxy hops. **`X-Forwarded-For`** (XFF) is the chain-of-custancy header: `$proxy_add_x_forwarded_for` expands to "the existing XFF (if the client sent one) plus `$remote_addr` appended" — so a request that already passed through Cloudflare arrives at Nginx with `X-Forwarded-For: 198.51.100.7` and Nginx appends its own peer IP, sending `X-Forwarded-For: 198.51.100.7, 10.0.0.1` to the backend. The backend takes the **leftmost** (or, if configured to trust N proxies, the Nth-from-the-right) entry as the real client. **`X-Forwarded-Proto`** records whether the client spoke HTTPS to Nginx — without it, the backend has no idea TLS was terminated upstream and generates `http://` redirect URLs, which the browser dutifully follows back to Nginx over plain HTTP, which redirects back to HTTPS — an infinite redirect loop that shows up as `ERR_TOO_MANY_REDIRECTS` in the browser. Setting `proxy_http_version 1.1` and clearing the `Connection` header are required for upstream keepalive — Nginx defaults to HTTP/1.0 for `proxy_pass`, which adds `Connection: close` and tears down the upstream TCP connection after every request. With 1.1 + cleared `Connection`, the `keepalive 32;` from the upstream block (covered in 10.04.02) becomes effective — Nginx reuses 32 idle upstream connections, saving the ~1ms TCP handshake and TLS setup per request.

The production failure mode is silent: a backend running behind a freshly-installed Nginx sees all traffic as coming from `127.0.0.1` / `10.0.0.1`. Rate limiters keyed on `request.getRemoteAddr()` (Spring's `RemoteAddr` filter, Express's `express-rate-limit` with default `keyGenerator`) collapse to a single bucket for the whole internet — one malicious client can DoS the entire user base by exhausting the shared limit, while legitimate clients see "429 Too Many Requests". Audit logs become useless ("every action was performed by 10.0.0.1"). Geo-IP lookups return the data-centre's location instead of the user's. The fix at the backend is to read `X-Forwarded-For` from a **trusted proxy only** — Spring Boot's `server.forward-headers-strategy=framework` + `server.tomcat.remoteip.trusted-proxies=10\\.0\\.0\\.\\d`, Express's `app.set('trust proxy', 'loopback, 10.0.0.0/8')`, Django's `SECURE_PROXY_SSL_HEADER = ('HTTP_X_FORWARDED_PROTO', 'https')` paired with `ipware` or a custom middleware. The trust boundary is critical: if you accept XFF from any client without verifying the immediate peer is a trusted proxy, an attacker sets `X-Forwarded-For: 1.2.3.4` in their request and bypasses your IP-based rate limiter or geo-block trivially.

### Proxy Buffering: Buffering slow client reads in Nginx RAM/disk buffers to release upstr...

`proxy_buffering` (default `on`) is the single most impactful Nginx directive for backend throughput. When on, Nginx reads the upstream's response as fast as the upstream can write it, into a chain of in-memory buffers (`proxy_buffer_size` for the first part of the response — typically the HTTP headers and the start of the body — plus `proxy_buffers 8 4k` for the rest). The upstream worker (Tomcat request thread, Node event-loop turn, Python WSGI worker) is freed the moment it finishes writing the response — typically in a few milliseconds. Nginx then dribbles those bytes to the client at whatever pace the client can sustain — a mobile phone on a flaky 3G connection might take 30 seconds to drain a 2MB JSON response. The backend worker has long since moved on to the next request. Without buffering, that backend worker would be parked in `write()` for the full 30 seconds, holding a thread, a database connection, a transaction, and ~50MB of heap memory — and your 200-worker pool would saturate at ~6 concurrent slow clients, a load you would otherwise handle at 10,000 rps.

The buffer geometry is two-level. `proxy_buffer_size` (default 4K on 64-bit systems) holds the response headers — must be large enough for the largest header set your backend produces (a backend that emits a 16KB `Set-Cookie` chain will overflow the 4K buffer and Nginx returns 502 "upstream sent too big header"). `proxy_buffers` (default `8 4k` = 32K total) holds the body. `proxy_busy_buffers_size` (default 8K) is the threshold at which Nginx stops waiting and starts sending to the client while still buffering — it is the "buffer is busy, start flushing" watermark. When the response exceeds the in-memory capacity, Nginx spills to disk at `proxy_temp_path` (default `/var/lib/nginx/proxy/` or `/var/cache/nginx/proxy_temp/`). Disk spill is slower but still correct; the failure mode is when the disk fills up — Nginx returns 502 Bad Gateway and writes `writev() failed (28: No space left on device)` to the error log. A common incident: a backend starts returning a 500MB error page (e.g. a Java stack trace dump embedded in HTML) instead of the usual 2KB JSON, Nginx tries to buffer 500MB per request across 200 concurrent requests, fills `/var`, and the whole proxy goes down. The fix is `proxy_max_temp_file_size 100m;` (cap disk spill at 100MB; larger responses stream straight through) plus monitoring `proxy_temp_path` disk usage.

```nginx
# Buffering defaults — protects backends from slow clients
location /api/ {
    proxy_pass http://app_backend;

    proxy_buffering           on;
    proxy_buffer_size         4k;            # response header buffer
    proxy_buffers             8 4k;          # 8 × 4K body buffers = 32K in RAM
    proxy_busy_buffers_size   8k;            # start flushing past this watermark
    proxy_max_temp_file_size  100m;          # cap disk spill; bigger → stream through
    proxy_temp_path           /var/cache/nginx/proxy_temp 1 2;  # 2-level subdir hash

    proxy_read_timeout        60s;           # upstream has 60s to send first byte / between bytes
    proxy_send_timeout        60s;           # client has 60s to ack each proxy→client chunk

    client_max_body_size      25m;           # request body cap — 413 above this
    client_body_buffer_size   128k;          # in-RAM request body threshold before disk spill
}
```

The two timeouts — `proxy_read_timeout` (time Nginx waits for the upstream to send more response bytes) and `proxy_send_timeout` (time Nginx waits for the client to acknowledge each chunk it sends) — are different from `keepalive_timeout` (which is connection-level). A backend that hangs mid-response (a database deadlock, a frozen GC) trips `proxy_read_timeout` after 60s and Nginx returns 504 Gateway Timeout. A client that disappears (mobile user enters a tunnel) trips `proxy_send_timeout` and Nginx closes both connections. The 60s defaults match the typical backend SLA; for long-poll endpoints bump both to 600s.

Turning **`proxy_buffering off`** is the right move for streaming responses where Nginx must pass bytes through synchronously rather than accumulating them. The two canonical use cases are Server-Sent Events (SSE) and WebSockets. With SSE, the backend holds the connection open indefinitely, sending `data: ...` events as they happen; if Nginx buffers, the client receives the entire stream in one burst at the end instead of as live events. With WebSockets, the protocol upgrade from HTTP/1.1 to RFC 6455 requires Nginx to be a transparent byte-pipe after the `Upgrade: websocket` handshake — buffering would break the bidirectional framing. The recipe:

```nginx
# SSE — disable buffering, bump timeout to allow infinite stream
location /events/ {
    proxy_pass http://app_backend;
    proxy_buffering off;
    proxy_cache off;                          # never cache streaming responses
    proxy_read_timeout 86400s;                # 24h — SSE streams can last hours
    proxy_set_header Connection '';           # required for HTTP/1.1 upstream
    proxy_http_version 1.1;
    chunked_transfer_encoding on;             # SSE uses Transfer-Encoding: chunked
}

# WebSocket — upgrade handshake, then transparent pipe
location /ws/ {
    proxy_pass http://app_backend;
    proxy_http_version 1.1;
    proxy_set_header Upgrade    $http_upgrade;
    proxy_set_header Connection "upgrade";    # literal "upgrade" — not $connection
    proxy_read_timeout 3600s;                 # idle WS connections survive 1h
}
```

The buffering-off failure mode is the inverse of the buffering-on failure mode: every slow client now holds a backend worker open for the full duration of the response transfer. A SSE endpoint that serves 5,000 concurrent mobile clients with `proxy_buffering off` means 5,000 backend connections held open — fine if the backend is async (Node, Netty, Spring WebFlux), catastrophic if it is sync (Tomcat with a 200-thread pool — you saturate at 200 SSE clients and the 201st gets 503). The general rule: buffer for the request-response web (HTML pages, JSON APIs, file downloads), stream for the long-lived-connection web (SSE, WS, gRPC streaming). The metric that reveals a buffering misconfiguration is backend worker-pool saturation: `tomcat_threads_busy` pinned at max, or Node's `eventLoopDelay` climbing, while `nginx_upstream_response_time` stays low — the workers are parked in `write()` waiting for slow clients. Turning `proxy_buffering on` immediately drops `tomcat_threads_busy` by an order of magnitude.

## Cross-Ecosystem Code

How each framework consumes the proxy headers that Nginx sets. The shape is identical — read `X-Forwarded-For` from a trusted peer only, derive scheme from `X-Forwarded-Proto`, generate absolute URLs using the original `Host`.

**Spring Boot (Anchor):**
```java
// application.yml
// server:
//   forward-headers-strategy: framework      // enables RemoteIpValve
//   tomcat:
//     remoteip:
//       trusted-proxies: "10\\.0\\.0\\.\\d"   // only trust Nginx's XFF
//       remote-ip-header: "X-Real-IP"
//       protocol-header: "X-Forwarded-Proto"

@RestController
@RequestMapping("/api/users")
class UserController {
    @GetMapping("/{id}")
    UserDto get(@PathVariable Long id, HttpServletRequest req) {
        // req.getRemoteAddr() now returns the real client IP, not 10.0.0.1
        String clientIp = req.getRemoteAddr();
        log.info("user {} fetched by {}", id, clientIp);
        return service.find(id);
    }

    @PostMapping
    ResponseEntity<UserDto> create(@Valid @RequestBody CreateUserRequest dto,
                                   UriComponentsBuilder b) {
        UserDto saved = service.create(dto);
        // b is auto-configured with the original Host + scheme from X-Forwarded-Proto
        URI location = b.path("/api/users/{id}").buildAndExpand(saved.id()).toUri();
        return ResponseEntity.created(location).body(saved);
    }
}
```

**Express (Delta):**
```typescript
import express from "express";
import rateLimit from "express-rate-limit";

const app = express();
// Trust only the Nginx reverse proxy in the 10.0.0.0/8 subnet.
// Without this, req.ip is "10.0.0.1" and rate-limit buckets collapse.
app.set("trust proxy", "loopback, 10.0.0.0/8");

const limiter = rateLimit({
  windowMs: 60_000,
  max: 100,
  keyGenerator: (req) => req.ip ?? "anon",   // now resolves to real client IP
  standardHeaders: true,
});
app.use("/api/", limiter);

app.get("/api/users/:id", (req, res) => {
  console.log(`${req.ip} → GET /api/users/${req.params.id}`);
  res.json({ id: Number(req.params.id) });
});
```

**Flask (Delta):**
```python
from flask import Flask, request, jsonify
from werkzeug.middleware.proxy_fix import ProxyFix

app = Flask(__name__)
# x_for=1 means trust one hop of X-Forwarded-For (the Nginx layer).
# x_proto=1 means trust one hop of X-Forwarded-Proto.
app.wsgi_app = ProxyFix(app.wsgi_app, x_for=1, x_proto=1, x_host=1, x_prefix=1)

@app.get("/api/users/<int:uid>")
def get_user(uid: int):
    # request.remote_addr is the real client IP, not 10.0.0.1
    app.logger.info("%s → GET /api/users/%d", request.remote_addr, uid)
    return jsonify({"id": uid})
```

**Django (Delta):**
```python
# settings.py
SECURE_PROXY_SSL_HEADER = ("HTTP_X_FORWARDED_PROTO", "https")
USE_X_FORWARDED_HOST = True                    # use Host header set by Nginx
USE_X_FORWARDED_PORT = True

# MIDDLEWARE += ["django.middleware.common.CommonMiddleware"]   # already in defaults

# Custom rate limiter reading X-Forwarded-For correctly
def get_client_ip(request):
    xff = request.META.get("HTTP_X_FORWARDED_FOR", "")
    if xff:
        # leftmost is the original client (Nginx appended itself to the right)
        return xff.split(",")[0].strip()
    return request.META.get("REMOTE_ADDR", "")
```

**Laravel (Delta):**
```php
<?php
// app/Http/Middleware/TrustProxies.php — Laravel ships this; configure it:
namespace App\Http\Middleware;

use Fideloper\Proxy\TrustProxies as Middleware;
use Illuminate\Http\Request;

class TrustProxies extends Middleware {
    protected $proxies = "10.0.0.0/8";                  // trust only Nginx
    protected $headers = Request::HEADER_X_FORWARDED_FOR |
                         Request::HEADER_X_FORWARDED_PROTO |
                         Request::HEADER_X_FORWARDED_HOST;
}

// Now $request->ip() returns the real client IP, and url()->current()
// generates HTTPS URLs when Nginx terminates TLS.
Route::get("/api/users/{id}", function (int $id, Request $req) {
    Log::info("{$req->ip()} → GET /api/users/{$id}");
    return response()->json(["id" => $id]);
});
```
