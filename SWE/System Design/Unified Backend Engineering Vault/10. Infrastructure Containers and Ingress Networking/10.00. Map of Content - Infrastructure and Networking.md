# 10.00. Map of Content: Infrastructure and Networking

## Overview

This section covers **10. Infrastructure Containers and Ingress Networking**. It is part of the unified backend engineering vault described in [[00.01. Master Architectural Mental Model]]. The notes below are organized by concept, not by framework. Each concept is taught once at the conceptual level, then implemented deeply in the Spring Boot anchor stack, then rapidly translated into Express, Django, Flask, and Laravel as deltas.

Section 10 sits on top of Section 02 (Operating Systems and POSIX Kernel Foundations) and Section 03 (Networking and Application Transport Protocols). Everything here is what the kernel actually does when you type `docker run` or when an Nginx worker accepts a connection — namespaces, cgroups, OverlayFS, bridge networking, `epoll` event loops, DNS resolution. If you skipped Sections 02 and 03, the failure modes in this section will look magical. They are not magical; they are syscalls and file descriptors all the way down.

The section is intentionally ordered so that the conceptual bottom is taught first: kernel primitives that make isolation possible (10.01), then the Docker engine that orchestrates those primitives (10.02), then how containers are wired together with networking and storage (10.03), then how traffic enters from the outside via reverse proxies (10.04), and finally how traffic is routed at planetary scale via DNS and CDN edges (10.05). By the end you should be able to trace a single HTTP request from a London laptop through a CDN edge, through Nginx ingress, through the Docker bridge, into a container's port 8080, and into a Spring Boot `@GetMapping` handler — naming every kernel subsystem and every network hop along the way.

## Section Map

### 10.01. Linux Kernel Virtualization Primitives

- [[10.01.01. Virtual Machines vs. Containers]] — The fundamental isolation trade-off: a VM virtualizes hardware and runs a full guest kernel (Type 1 hypervisors like ESXi and KVM run on bare metal; Type 2 like VirtualBox and VMware Workstation run on a host OS), while a container shares the host kernel and uses namespaces for visibility isolation plus cgroups for resource limits. Compares memory overhead (GBs vs MBs), boot time (minutes vs milliseconds), and the cloud-native hybrid where containers run inside VMs to get both isolation boundaries.
- [[10.01.02. Linux Namespaces Isolation Primitives]] — The eight Linux namespaces (`mnt`, `pid`, `net`, `ipc`, `uts`, `user`, `cgroup`, `time`) that together create the illusion of a private system for a process group. Covers the `clone(CLONE_NEW*)`, `unshare(2)`, and `setns(2)` syscalls, the `/proc/<pid>/ns/` magic symlinks, the `nsenter` tool, and a working `unshare --pid --fork --mount-proc /bin/bash` example that gives you a hand-rolled container with no Docker installed.
- [[10.01.03. Linux Control Groups (cgroups v1 and v2)]] — The kernel subsystem that meters and limits resource use. Covers the v1 multi-tree model (one hierarchy per controller — `cpu`, `memory`, `blkio`, `pids`, `devices`, `net_cls`) versus the v2 unified hierarchy that systemd has made the default on modern distros. Includes real `mkdir /sys/fs/cgroup/...`, `echo <pid> > cgroup.procs`, `echo 1G > memory.max` workflows and the OOM-killer path that produces `OOMKilled` exit code 137.
- [[10.01.04. Union Filesystems and OverlayFS]] — How Docker assembles an image from stacked read-only layers and a writable container layer. Covers the OverlayFS `lowerdir` + `upperdir` + `workdir` → `merged` mount, the copy-up operation triggered on first write, whiteout files for deletions, and why OverlayFS displaced AUFS as the kernel-native default.

### 10.02. Docker Engine Containerization and Multi-Stage Builds

- [[10.02.01. Docker Engine Architecture]] — The five-component stack that turns `docker run nginx` into a running container: the Docker CLI (gRPC/REST client), the Docker daemon `dockerd` (lifecycle manager), `containerd` (high-level runtime supervising containers and snapshots), `runc` (the low-level OCI runtime that actually calls `clone` with namespace flags), and the CRI plugin that lets Kubernetes swap engines. Walks the full call chain and the `/var/lib/docker/overlay2` image storage layout.
- [[10.02.02. Dockerfile Optimization and Multi-Stage Builds]] — How to write Dockerfiles that produce small, cacheable, secure images. Covers the layer-cache implications of instruction ordering, the `COPY` vs `ADD` distinction, multi-stage `FROM ... AS builder` patterns that let you compile in a fat JDK image and copy the JAR into a `gcr.io/distroless/java-base` runtime, and the `--target` flag for shipping debug vs production variants from one file.

### 10.03. Container Networking and Storage Volumes

- [[10.03.01. Docker Networking Mechanics]] — The four built-in network drivers and when each applies: `bridge` (the default `docker0` NAT bridge for single-host containers), `host` (no isolation, container shares host netns, fastest but no port collision protection), `none` (loopback only, for offline batch), `overlay` (VXLAN-tunnelled multi-host networking powered by a key-value store). Plus `macvlan` for giving containers their own MAC addresses on the physical network.
- [[10.03.02. Container Storage and Persistence]] — Why the container's writable layer dies when the container dies, and the three persistence escape hatches: `tmpfs` mounts (RAM-backed, for secrets and scratch), bind mounts (host directory mounted 1:1, simple but portability-hostile), and named volumes (Docker-managed, driver-pluggable, the right answer for databases). Covers the failure mode where a database is silently storing its datafiles in the writable OverlayFS layer and IO throughput collapses.
- [[10.03.03. Docker Compose for Local Multi-Service Topologies]] — How `docker-compose.yml` declares a multi-container topology: services (image + ports + volumes + environment), networks (custom bridge networks for service-to-service DNS), volumes (named volumes for persistent state), healthchecks (the `HEALTHCHECK` directive and `depends_on: condition: service_healthy` for startup ordering). The file that turns a four-service stack (app + Postgres + Redis + Nginx) into `docker compose up`.

### 10.04. Reverse Proxies and Nginx Ingress Architecture

- [[10.04.01. Nginx Architecture and Event Model]] — The single-master, many-worker process model where the master binds `:80` and the workers share the listening FD via `SO_REUSEPORT` and compete on `accept4`. Each worker runs a single-threaded `epoll` event loop that handles thousands of keep-alive connections without thread-per-connection overhead. Why Nginx scales horizontally by setting `worker_processes auto` to match CPU count.
- [[10.04.02. Nginx Configuration Hierarchy]] — The directive context tree: `main` (global) → `events` (worker tuning) → `http` (server-wide HTTP defaults) → `server` (a virtual host) → `location` (a URL pattern) → nested `location`. How Nginx picks the matching `location` using the prefix-match-then-regex priority rule, and why `location /api/v1/` and `location ^~ /api/v1/` behave differently when both could match.
- [[10.04.03. Reverse Proxy Routing and Buffering]] — The `proxy_pass` directive: how Nginx forwards upstream, rewrites `Host`, appends `X-Real-IP` and `X-Forwarded-For`, sets `X-Forwarded-Proto`, and buffers the upstream response before flushing to the client (the `proxy_buffering on` default that protects slow mobile clients from holding backend connections open).
- [[10.04.04. Load Balancing Algorithms]] — The `upstream` block algorithms: round-robin (the default, even distribution), weighted round-robin (`server x weight=3`), least-connections (`least_conn` for long-lived connections like WebSockets), IP-hash (`ip_hash` for naive session affinity — broken behind NAT), and the commercial-only `hash` and `random` directives. When each is appropriate and the sticky-session alternatives using cookies.

### 10.05. Edge Networking DNS and Content Delivery Networks

- [[10.05.01. Domain Name System (DNS) Resolution]] — The hierarchical resolution tree: root nameservers (`.`) → TLD nameservers (`.com`) → authoritative nameservers (`example.com`). Covers the iterative resolver query path, the recursive resolver caching tiers (browser → OS → upstream DNS), the TTL-must-be-respected rule for cache invalidation, and the `dig +trace example.com` command that walks the tree from the root.
- [[10.05.02. Content Delivery Networks (CDN) and Edge Caching]] — Origin servers vs globally distributed edge Points of Presence (PoPs). Covers the CDN edge pulling content on cache miss, TTL-based cache eviction, cache-key design (why `?v=42` query strings matter for asset busting), and the TTL-vs-freshness trade-off that makes a 60-second CDN TTL feel real-time while keeping origin load survivable.

## Conceptual Roadmap

The five sub-sections of Section 10 form a vertical stack. At the bottom (10.01) is the kernel substrate — namespaces give you visibility isolation, cgroups give you resource isolation, and OverlayFS gives you filesystem isolation. Without those three kernel features, "container" is just a marketing word. Section 10.02 then shows how Docker packages those primitives into a usable product: the Dockerfile, the image format, the daemon that supervises containers, and the OCI runtime that actually calls `clone(CLONE_NEWPID | CLONE_NEWNET | ...)`. Section 10.03 is the lateral dimension: how containers talk to each other (network drivers, the `docker0` bridge, overlay networking) and how they persist state across restarts (volumes). Section 10.04 lifts you above the container — now you have many containers across many hosts, and you need a reverse proxy to terminate TLS, route by hostname, and load balance. Section 10.05 takes you to the planet scale: DNS resolves names to your proxy IPs, and a CDN sits in front of everything to keep traffic off your origin.

A useful mental exercise is to trace a single HTTPS request end to end. The user types `api.example.com/users/42`. The browser asks the OS resolver, which queries the recursive resolver, which walks the DNS tree (10.05.01). The DNS answer points at a CDN edge (10.05.02). The CDN serves from cache on a hit; on a miss it forwards to the origin IP, which is a load balancer in front of Nginx (10.04.01). Nginx terminates TLS, matches the `server` block (10.04.02), selects an `upstream` via `proxy_pass` (10.04.03), and load-balances across backend pods (10.04.04). Each backend pod is a container scheduled by some orchestrator (10.02.01), wired into an overlay network (10.03.01), reading its stateful data from a named volume (10.03.02). Inside that container, the process is isolated by namespaces (10.01.02), limited by cgroups (10.01.03), and sees a merged filesystem built from image layers (10.01.04). Every hop in that trace is a separate file in this section.

The failure modes compound across the stack. A misconfigured `proxy_buffering off` (10.04.03) lets slow mobile clients hold backend connections open until the cgroup memory limit (10.01.03) trips and the kernel OOM-kills your container (exit 137). A wrong CDN TTL (10.05.02) means a deploy never reaches users because the edge keeps serving the old version. A misconfigured `dns` resolution in the Docker bridge (10.03.01) means the app container cannot find the database container by name and crashes on boot. Read the notes top to bottom, then come back and trace your own production request path through them.
