# 10.01.02. Linux Namespaces Isolation Primitives

## What This Is

A Linux namespace is a kernel feature that wraps a global system resource — the process table, the mount tree, the network stack, the hostname, the IPC keys, the UID space, the cgroup membership, the system clock — and presents a process inside the namespace with the illusion that it has its own private instance of that resource. Six namespaces shipped in mainline by 2008 (`mnt`, `uts`, `ipc`, `pid`, `net`, `user`); `cgroup` was added in kernel 4.6 (2016) and `time` arrived in kernel 5.6 (2020). Together they are the isolation half of "container" — the part that decides what a process can *see*. The other half is cgroups (covered in [[10.01.03. Linux Control Groups (cgroups v1 and v2)]]), which decides what a process is *allowed to use*. OverlayFS (covered in [[10.01.04. Union Filesystems and OverlayFS]]) is the third leg, which decides what a process *sees on disk*.

This note walks each namespace in detail. The pattern is the same for all of them: there are three syscalls that move a process into a namespace (`clone(2)` for new processes, `unshare(2)` for the calling process, `setns(2)` for joining an existing namespace via a `/proc/<pid>/ns/*` magic symlink), there is a per-namespace file under `/proc/<pid>/ns/` that uniquely identifies the namespace by inode number, and there is the `nsenter` userspace tool that calls `setns` for you. The Docker daemon and the `runc` OCI runtime do not invent any new isolation primitive — they call these exact syscalls with these exact flags. Once you understand namespaces at the syscall level, "container" stops being a magical black box and becomes a process tree with six or seven namespace pointers set differently from your shell's.

## The Details

### `pid` Namespace: Process ID virtualization (Container process runs as PID 1 inside, dis...

The PID namespace virtualizes the process-ID number space. Inside a PID namespace, the first process gets PID 1, the next gets PID 2, and so on — independent of the host's global PID counter. The kernel still maintains the host-side PID for the same task (visible in `/proc/<host_pid>/` on the host), but it layers a per-namespace PID on top. A process can therefore have multiple PIDs simultaneously: one in its own namespace, one in each ancestor namespace. The `task_struct->pids[PIDTYPE_PID]` is a linked list of `struct pid` entries, one per namespace level. When the process calls `getpid()`, the kernel returns the PID entry for whichever namespace the *caller* is in — a process outside the namespace sees the host PID; a process inside sees the namespace-local PID.

PID 1 inside a namespace is special in three ways that bite production teams. First, it inherits the same signal-handling rules as host init: signals that have not been explicitly installed via `sigaction` are *ignored* by default for PID 1, including `SIGTERM` and `SIGINT`. This is why `docker stop` sends `SIGTERM` and then, after a 10-second grace period (`--stop-timeout`), escalates to `SIGKILL` — many container processes ignore `SIGTERM` because they are PID 1 and never installed a handler, so the only way to kill them is the unignorable `SIGKILL`. Second, PID 1 is the *reaper* of orphaned children: any process in the namespace whose parent dies is reparented to namespace PID 1, which must call `waitpid` to reap the resulting zombie. A naive Java or Node.js entrypoint that does not call `waitpid` (and most don't) leaks zombies in long-running containers. Third, killing PID 1 kills the namespace: the kernel sends `SIGKILL` to every remaining process in the namespace and the namespace itself is torn down.

```bash
# Hand-roll a PID namespace with no Docker installed.
# --pid        : new PID namespace
# --fork       : fork before exec so the child becomes PID 1 of the new ns
#                (without --fork, unshare itself stays in the old PID ns
#                 and only its child is in the new one — which would make
#                 the child PID 1 but unshare couldn't exec into it cleanly)
# --mount-proc : remount /proc so ps/top see only namespace processes
sudo unshare --pid --fork --mount-proc /bin/bash

# Inside the new namespace:
ps aux
# USER  PID  %CPU %MEM   VSZ   RSS  COMMAND
# root    1  0.0  0.0  12188  3232  bash       <-- this bash is PID 1
# (nothing else is visible — the host's 300 processes are hidden)

# From the host, the same bash has a different PID:
ps -ef | grep "bash$"
# root  28412 28410  0 10:14 pts/0  00:00:00 /bin/bash

# The kernel's namespace link for this bash:
ls -la /proc/28412/ns/pid
# pid -> pid:[4026532785]   <-- inode number identifies the namespace
```

The reason Docker uses `clone(2)` rather than `unshare(2)` is that `clone` lets the runtime set the namespace flags *and* the new process's stack, file descriptors, and cgroup membership in one atomic syscall. `runc` issues `clone(CLONE_NEWPID | CLONE_NEWNET | CLONE_NEWNS | CLONE_NEWUTS | CLONE_NEWIPC | CLONE_NEWUSER, ...)` so the container's init process is born already inside all six namespaces. `unshare` is the convenient tool for ad-hoc inspection; `clone` is the production primitive.

The production failure mode for PID namespaces is the **PID 1 zombie leak**. A container running a JVM as PID 1 with no init shim will, over weeks, accumulate `Z` state processes from `Runtime.exec` children whose parents have died. The fix is to put a tiny init like `tini` or `dumb-init` as PID 1 and let it reap zombies — which is why Docker added `docker run --init` in 1.13, which injects `tini` as PID 1 transparently. The other classic failure is the **`SIGTERM` ignored** symptom: a service that takes 10 seconds to "stop" because it ignored the term signal and waited for `SIGKILL` — fixed by either installing a JVM shutdown hook (`Runtime.addShutdownHook`) or by adding `--init` so that `tini` re-parents the JVM and forwards signals correctly.

### `net` Namespace: Virtualized network stacks, private routing tables, loopback, and virt...

A network namespace is a full copy of the kernel's networking state: its own loopback `lo` interface, its own routing table (`/proc/net/route`, `ip route`), its own ARP neighbour table, its own iptables rules (filter, nat, mangle, raw), its own socket hash tables, its own `/proc/net/` directory, and its own port space — meaning two containers can each bind `:8080` simultaneously without conflict because each namespace's port space is independent. A process inside a netns cannot see or use interfaces in the host netns unless those interfaces are explicitly moved into the namespace with `ip link set <dev> netns <ns>` or bridged via a `veth` pair.

The `veth` (virtual ethernet) pair is the pipe that connects two netns. It is always created as a linked pair: packets sent in one end come out the other. The standard Docker pattern is: create a `veth0`/`veth1` pair, move `veth1` into the container's netns, rename it to `eth0` inside the container, attach `veth0` to the host's `docker0` Linux bridge, and assign `eth0` an IP from the bridge's subnet. NAT via the host's `iptables -t nat POSTROUTING -j MASQUERADE` rule then lets the container reach the internet. The container's traffic to the outside world appears, to upstream servers, to come from the host's IP — that is the `MASQUERADE` doing SNAT.

```bash
# Create a netns and a veth pair by hand, no Docker involved.
sudo ip netns add demo
sudo ip link add veth-host type veth peer name veth-ns
sudo ip link set veth-ns netns demo

# Inside the new netns, veth-ns now exists; rename and address it.
sudo ip netns exec demo ip link set lo up
sudo ip netns exec demo ip link set veth-ns name eth0
sudo ip netns exec demo ip addr add 172.20.0.2/24 dev eth0
sudo ip netns exec demo ip link set eth0 up
sudo ip netns exec demo ip route add default via 172.20.0.1

# On the host, attach the other end to a bridge and address it.
sudo ip link add br-demo type bridge
sudo ip link set veth-host master br-demo
sudo ip addr add 172.20.0.1/24 dev br-demo
sudo ip link set br-demo up
sudo ip link set veth-host up

# Verify connectivity from inside the namespace:
sudo ip netns exec demo ping 172.20.0.1
# PING 172.20.0.1 (172.20.0.1) 56(84) bytes of data.
# 64 bytes from 172.20.0.1: icmp_seq=1 ttl=64 time=0.071 ms

# Two containers can each bind :80 — they are in different namespaces:
sudo ip netns exec demo python3 -m http.server 80 &
sudo python3 -m http.server 80 &
# Both succeed. From the host's perspective only the host-namespace one is visible.
```

Each `docker run` creates a fresh netns. The default bridge `docker0` (subnet typically `172.17.0.0/16`) holds all container `veth` ends on a single-host install. When you `docker network create` a user-defined bridge, Docker creates a *new* Linux bridge, a new subnet, and an embedded DNS server (127.0.0.11) that resolves container names — that is how `docker run --network my-net --name api` lets other containers reach `api:8080` by name. The overlay driver (used by Docker Swarm and Kubernetes via Calico/Cilium) extends the same model across hosts using VXLAN or Geneve tunnels; the per-netns mechanics on each host are unchanged.

The production failure mode for netns is the **`docker0` MTU mismatch**. A host on AWS with a 9001-byte jumbo-frame `eth0` will, by default, give its containers a 1500-byte `docker0` — so the host can talk to other AWS hosts at 9001 bytes but container traffic is fragmented down to 1500. Symptoms are mysterious TCP throughput collapses and intermittent large-packet failures (small `curl` requests succeed; large file uploads stall). The fix is `dockerd --mtu=9001` in `daemon.json` (or per-network `docker network create -o com.docker.network.driver.mtu=9001`). The other classic failure is **port exhaustion** in NAT mode: a busy container opening many outbound connections can exhaust the host's ephemeral port range (`net.ipv4.ip_local_port_range`, default 32768–60999 ≈ 28K ports) because every container connection consumes one host port via SNAT — visible as `nf_conntrack: table full, dropping packet` in `dmesg`.

### `mnt` Namespace: Isolated filesystem mount point views

The mount namespace was the *first* namespace added to Linux (in kernel 2.4.19, 2002). It virtualises the kernel's mount tree — the linked list of `struct mount` (formerly `struct vfsmount`) entries that the kernel walks when resolving a path. When a process calls `unshare(CLONE_NEWNS)` or `clone(CLONE_NEWNS)`, the kernel deep-copies the parent's mount tree and gives the child its own copy. Subsequent mounts and unmounts inside the child namespace are invisible to the parent (and the parent's subsequent mounts are invisible to the child, depending on propagation flags). This is what lets a container have its own `/etc/resolv.conf`, `/etc/hostname`, and `/proc` without leaking those mounts back to the host or to sibling containers.

Mount propagation is the subtle part. Every mountpoint has a propagation type: `MS_PRIVATE` (mounts/unmounts do not propagate either direction — the safest default), `MS_SHARED` (events propagate to and receive from a peer group), `MS_SLAVE` (receives from master but does not propagate back), and `MS_UNBINDABLE` (cannot be the source of a bind mount, used to prevent loops). Docker's `runc` runs `mount --make-rslave /` early in container setup so that the container's mount events do not leak to the host's root. Getting this wrong in hand-rolled setups produces weird symptoms — mounts that appear in `mountinfo` for processes that should not see them, or `umount` operations that succeed in one shell and fail in another.

```bash
# Demonstrate mount-namespace isolation.
sudo unshare --mount /bin/bash

# Inside the new mnt ns, make a private mount invisible to the host:
mkdir /tmp/secret
mount -t tmpfs none /tmp/secret
echo "container-only" > /tmp/secret/note
mount | grep secret
# none on /tmp/secret type tmpfs (rw,relatime)

# From a host shell while this is still running:
ls /tmp/secret
# (empty — the tmpfs mount is invisible outside the mnt ns)

# Bind-mount a per-container resolv.conf, the way Docker does:
mount --bind /etc/docker/containers/<id>/resolv.conf /etc/resolv.conf
# Now /etc/resolv.conf inside this ns points at the container's resolver,
# but the host's /etc/resolv.conf is untouched.

# Propagation flags in /proc/self/mountinfo — 4th colon-separated field:
findmnt -o TARGET,PROPAGATION
# TARGET       PROPAGATION
# /            private,slave
# /proc        private
# /tmp/secret  private
```

The `pivot_root(2)` syscall is the partner to the mount namespace. `pivot_root(new_root, put_old)` swaps the process's root directory and the previous root, moving the old root under `put_old`. `runc` uses it (rather than `chroot`) because `chroot` only changes the root *directory* but leaves the old root mounted and reachable via file descriptors; `pivot_root` actually unmounts the old root, closing the escape hatch. Combined with a fresh mount namespace, `pivot_root` is what makes the container's `/` look like a real filesystem root rather than a chroot jail.

The production failure mode for mount namespaces is the **bind-mount leak**. A common mistake is to bind-mount a host directory into a container for development (`docker run -v $HOME:/home/host ...`) and then let a compromised container traverse out — bind mounts do not respect the container's user-namespace remapping unless explicitly configured, so a file written as root in the container is owned by root on the host. Worse, `docker run -v /:/host` mounts the entire host filesystem into the container, which is essentially equivalent to giving the container root on the host. The defensive posture is to never bind-mount host paths in production (use named volumes — see [[10.03.02. Container Storage and Persistence]]), and where bind mounts are unavoidable, run with `--userns-remap` so container root maps to an unprivileged host UID.

### `ipc` Namespace: Isolating System V IPC and POSIX message queues

The IPC namespace isolates three distinct SysV IPC mechanisms plus POSIX message queues. The SysV trio is: shared memory segments (`shmget`/`shmat`/`shmdt`/`shmctl`), semaphore arrays (`semget`/`semop`/`semctl`), and message queues (`msgget`/`msgsnd`/`msgrcv`). POSIX message queues (`mq_open`/`mq_send`/`mq_receive`) live in their own little filesystem at `/dev/mqueue`. Each IPC namespace has its own independent kernel table for all four, indexed by integer keys that are independent across namespaces — so a container's `shmget(0x1234, ...)` is unrelated to the host's `shmget(0x1234, ...)`.

The relevance to containers is twofold. First, isolation: without an IPC namespace, a container could attach to the host's `shm` segments (or another container's), which would be both a security hole and a correctness hazard. Second, resource limits: SysV shared memory is accounted against the `kernel.shmmax` and `kernel.shmall` sysctls on the host; an IPC namespace lets each container have its own quota so that a misbehaving container cannot starve the host's shm pool. The `ipcs` and `ipcmk` tools operate within the caller's IPC namespace, so `docker exec <ctr> ipcs -m` shows only that container's segments.

```bash
# Inside a container with its own IPC namespace:
docker run --rm -it --ipc=private alpine sh
ipcs -m
# ------ Shared Memory Segments --------
# key        shmid  owner  perms  bytes  nattch  status
# (empty)

# Create a 16 MB shared segment:
ipcmk -M 16777216
# Shared memory id: 0
ipcs -m
# key 0x00000000 shmid 0 root 644 16777216 1

# From the host, that segment is invisible:
ipcs -m   # on the host
# (empty — different IPC namespace)

# Two containers can share an IPC namespace (--ipc=container:<other>),
# used for X11 shared-memory rendering between a server and a client:
docker run --name ipc-server --ipc=shareable alpine ipcmk -M 1048576
docker run --rm -it --ipc=container:ipc-server alpine ipcs -m
# key 0x00000000 shmid 1 root 644 1048576 2  <-- visible, nattch=2
```

In practice the IPC namespace matters most for two workloads: (1) **PostgreSQL** uses SysV shared memory for its inter-backend communication buffer, and historically needed `--shm-size=64m` raised from Docker's default 64 MB to match `shared_buffers` — modern PostgreSQL (9.3+) uses `mmap` with `MAP_HUGETLB` instead and is less sensitive, but the IPC namespace still gates the segment. (2) **Browser-like renderers** (Chrome, Electron) share image buffers between GPU and renderer processes via SysV `shm`; running an Electron app in a container without `--ipc=host` (or without raising the limit) can crash on first paint with `Failed to map shared memory`.

The production failure mode for the IPC namespace is the **`shm-size` underrun**. A PostgreSQL container with `shared_buffers = 256MB` but Docker's default `--shm-size=64m` will fail to start, with `FATAL: could not create shared memory segment: Invalid argument` in the container logs. The fix is either `docker run --shm-size=256m` (preferred) or mounting `tmpfs` at `/dev/shm` with the right size. The deeper failure mode — sharing the host IPC namespace (`--ipc=host`) — opens the container to the host's `shm` segments and is a known privilege-escalation vector; treat it like `--privileged` and avoid it.

### `uts` Namespace: Isolating hostnames and domain names

The UTS namespace — named after the `struct utsname` returned by the `uname(2)` syscall, which in turn inherits its name from the UNIX Time-Sharing system — isolates two strings: `nodename` (returned by `gethostname(2)` and visible in `hostname`) and `domainname` (returned by `getdomainname(2)`). It is the simplest namespace: a single struct of two character arrays (`char nodename[__NEW_UTS_LEN + 1]` and `char domainname[__NEW_UTS_LEN + 1]`, where `__NEW_UTS_LEN` is 64) per namespace. The other fields of `struct utsname` (`sysname`, `release`, `version`, `machine`) are global kernel constants and are *not* isolated — those reflect the actual kernel, which is shared.

The reason UTS gets its own namespace is operational rather than security-related. A container's hostname shows up in shell prompts, in syslog entries, in `ps` output (`<user>@<host>`), in Prometheus `instance` labels if the scrape target reports its hostname, and in `gethostname()`-based clustering for tools like Cassandra and Elasticsearch that use the hostname as a node identifier. Without UTS isolation, every container on a host would report the host's hostname, and these tools would either fail to form a cluster (duplicate node names) or route traffic incorrectly. The UTS namespace lets `docker run --name api-1 --hostname api-1` give the container its own hostname so that `gethostname()` returns `api-1` inside the container while the host's hostname is unchanged.

```bash
# Without UTS isolation, hostname is global:
hostname            # on host
# prod-host-01

# Hand-roll a UTS namespace:
sudo unshare --uts /bin/bash
hostname            # still 'prod-host-01' — inherited from parent
hostname api-1      # change inside the ns only
hostname
# api-1

# From a host shell:
hostname
# prod-host-01      # unchanged

# What Docker actually does (visible in runc's config.json):
# "namespaces": [
#   { "type": "uts" }
# ]
# combined with hostname/api-1 in the runtime spec.
docker run --rm --hostname api-1 alpine hostname
# api-1
```

The UTS namespace is also where the `domainname` lives — used by NIS/YP (a 1990s network directory service, almost extinct in modern setups but still present in some enterprise environments). Setting `domainname` inside a UTS namespace is local to that namespace and does not affect the host. The hostname field is what most software cares about; the domainname field is rarely touched on modern Linux but is still part of the `struct utsname` and is therefore still namespace-isolated.

The production failure mode is **hostname collision in service discovery**. Without `--hostname` set explicitly, Docker assigns the container's hostname from its container ID (e.g. `a3b2c1d4e5f6`), which is a 12-character hex string — useless in logs and brittle in tooling that uses hostname for clustering. The fix is to always set `--hostname` (or `hostname:` in `docker-compose.yml`) to a stable, meaningful value, especially for stateful workloads like databases and brokers. A subtler failure is the **`uname -a`-based kernel-version check** in installers: `uname -r` returns the *host's* kernel version (because the kernel is shared), so a container running on a host with kernel 5.4 but advertised as running Ubuntu 22.04 (which ships kernel 5.15) will confuse installers that gate on `uname -r`. The container's userspace is 22.04; the kernel is whatever the host is running.

### `user` Namespace: Mapping container root UID (0) to unprivileged host UIDs for enhanced...

The user namespace is the security breakthrough that makes rootless containers possible. It decouples the UID/GID a process *thinks* it has (visible to the process via `getuid()`, `ls -l`, `/proc/self/status`) from the UID/GID the kernel *actually* uses for permission checks on the host. Inside a user namespace, a process can be UID 0 (root) and exercise all the privileges that implies *within the namespace* — binding ports below 1024, `chown`ing files to arbitrary UIDs, creating device nodes — while the kernel maps those operations to an unprivileged host UID (say, 100000) for any interaction with resources outside the namespace. The mapping is one-to-one and contiguous, defined by writing to `/proc/<pid>/uid_map` and `/proc/<pid>/gid_map` in the format `<inside_first> <outside_first> <count>`.

The mapping chain works like this. A process in a user namespace with `uid_map = "0 100000 65536"` means: UIDs 0 through 65535 inside the namespace correspond to UIDs 100000 through 165535 on the host. When the container process calls `getuid()`, it returns 0. When it does `open("/etc/passwd", O_RDONLY)`, the kernel checks the file's owner against UID 100000 (the mapped host UID), not UID 0. When the container writes a new file, the file is created owned by host UID 100000 — visible on the host as `ls -l` showing `100000 100000`. The container is root inside its bubble; outside its bubble, it is an unprivileged user, and a container escape gives the attacker UID 100000, not UID 0 — which on most production hosts can do almost nothing.

```bash
# Hand-roll a user namespace:
#   --user           new user namespace
#   --map-root-user  map container UID 0 -> caller's UID (e.g. 1000)
unshare --user --map-root-user /bin/bash

# Inside:
whoami              # root
id                  # uid=0(root) ... but only inside the ns
echo $$             
ls -la /proc/self/uid_map
#          0       1000          1     <-- inside UID 0 ↔ host UID 1000

# Touch a file:
touch /tmp/from-inside
# On the host:
ls -la /tmp/from-inside
# -rw-r--r-- 1 1000 1000 0 ...   <-- owned by host UID 1000, NOT root

# Docker's userns-remap mode does the same thing at daemon level:
# /etc/docker/daemon.json:
# { "userns-remap": "default" }
# This creates a 'dockremap' user and shifts every container's UID by
# 100000 (the default range start) — so container root is host UID 100000.
docker run --rm alpine id
# uid=0(root) ...
ls -la /var/lib/docker/overlay2/<hash>/diff/etc/passwd
# -rw-r--r-- 1 100000 100000 ...    <-- owned by mapped UID
```

The user namespace is the only namespace that can be created without `CAP_SYS_ADMIN` — by design, because the whole point is that an unprivileged user can create one. This is what enables **rootless Docker**, **Podman**, **Buildah**, and **Kubernetes UserNS** (KEP-127, alpha in 1.25, beta in 1.29): the entire container runtime can run as an unprivileged user on the host, with the daemon and every container mapped to a high-UID range that the host kernel treats as a nobody. Combined with `--userns-remap`, even a container that escapes via a kernel bug lands on host UID 100000–165535, which (on a properly configured host) cannot read `/etc/shadow`, cannot write to system binaries, and cannot `ptrace` other processes.

The production failure mode is the **UID collision**. If you set `userns-remap` with the default range `100000:65536` and your host already has a user at UID 100000 (perhaps an automated backup user), the container's files become readable/writable by that user — breaking the isolation the user namespace was supposed to provide. The fix is to pick a UID range that is genuinely unused on the host (`subuid` and `subgid` files in `/etc/` control this; Podman and Docker both read these). The other classic failure is **filesystem permission breakage**: when you enable `userns-remap` on an existing Docker install, every existing image layer and named volume is now owned by the wrong UID — `docker run` against an old volume fails with permission denied because the container's UID 0 maps to host UID 100000, but the volume's files are owned by host UID 0. The migration requires either `chown`-ing every volume's contents or recreating volumes from scratch.

## Cross-Ecosystem Implementation

Different container runtimes expose the same eight namespaces with different defaults and ergonomics. The underlying syscalls (`clone`, `unshare`, `setns`) are identical — what varies is which namespaces are unshared by default, whether user-namespace remapping is on, and how the runtime surfaces namespace inspection to the operator.

| Runtime | Default namespaces unshared | Userns by default | Inspection tooling |
|---|---|---|---|
| Docker (`runc`) | mnt, pid, net, ipc, uts | No (opt-in via `--userns-remap`) | `docker inspect <ctr>` → `.State.Pid` then `ls /proc/<pid>/ns/` |
| Podman | mnt, pid, net, ipc, uts, user | Yes (rootless by default) | `podman inspect <ctr>`; same `/proc` trick |
| systemd-nspawn | mnt, pid, net, ipc, uts | Optional (`--private-users`) | `machinectl status <ctr>` |
| LXC | mnt, pid, net, ipc, uts, user | Yes (configurable) | `lxc-info -n <ctr>` |
| Raw `unshare` | Whatever you ask for | Whatever you ask for | `ls -la /proc/self/ns/` |

When you read the anchor implementation note in Section 10.02, identify which namespaces `runc` unshares by default and how the OCI runtime spec's `"namespaces"` array is populated. The delta notes for Podman (`podman run` is a near drop-in for `docker run`) and systemd-nspawn show how the same six-namespace isolation is expressed with different CLI flags and different default stances on the user namespace. The runtime-invariant being exposed is the same: a container is a process tree with a different set of namespace pointers than the host's init.

## Hands-On Exercise

```bash
# 1. Inspect your own shell's namespaces.
ls -la /proc/self/ns/
# total 0
# lrwxrwxrwx ... cgroup -> cgroup:[4026531835]
# lrwxrwxrwx ... ipc    -> ipc:[4026531839]
# lrwxrwxrwx ... mnt    -> mnt:[4026531841]
# lrwxrwxrwx ... net    -> net:[4026531840]
# lrwxrwxrwx ... pid    -> pid:[4026531836]
# lrwxrwxrwx ... user   -> user:[4026531837]
# lrwxrwxrwx ... uts    -> uts:[4026531838]
# Each inode number is a unique namespace identifier.

# 2. Hand-roll a container with no Docker installed.
sudo unshare --pid --net --mnt --uts --ipc --fork --mount-proc /bin/bash
# Inside: you are PID 1, you have your own loopback, your own hostname.
hostname hand-rolled
ip link set lo up
ip addr show        # only lo
ps aux              # only your bash

# 3. Enter an existing container's namespaces with nsenter.
docker run -d --name demo alpine sleep 3600
PID=$(docker inspect -f '{{.State.Pid}}' demo)
sudo nsenter --target $PID --mount --uts --ipc --net --pid /bin/sh
# You are now inside demo's namespaces, as if you had done docker exec,
# but using only kernel primitives (setns under the hood).

# 4. Demonstrate user-namespace UID remapping.
unshare --user --map-root-user sh -c 'id; touch /tmp/userns-test; exit'
ls -la /tmp/userns-test
# -rw-r--r-- 1 <your-uid> <your-uid> 0 ...   <-- owned by your host UID, not root

# 5. Compare two containers' netns inode numbers (they should differ).
docker run -d --name c1 alpine sleep 3600
docker run -d --name c2 alpine sleep 3600
P1=$(docker inspect -f '{{.State.Pid}}' c1)
P2=$(docker inspect -f '{{.State.Pid}}' c2)
readlink /proc/$P1/ns/net      # net:[4026532188]
readlink /proc/$P2/ns/net      # net:[4026532191]  ← different namespace

# 6. Two containers sharing a netns (--network=container:).
docker run --rm --network=container:c1 alpine ip addr
# Shows c1's eth0 IP because both are in the same netns now.
```
