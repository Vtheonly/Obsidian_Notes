# 10.01.01. Virtual Machines vs. Containers

## What This Is

This note is the conceptual fork in the road for everything in Section 10. There are exactly two ways to give a workload its own isolated execution environment on a shared physical host: virtualize the hardware (VMs) or virtualize the operating system (containers). Every higher-level abstraction — Docker, Kubernetes, Firecracker, gVisor, AWS Nitro — is a configuration of one of these two primitives, or a hybrid of both. The choice between them is not aesthetic; it governs your boot time, your memory tax, your blast radius on a kernel exploit, and your operational complexity. Get this fork wrong and you will pay for it in either cost (VM sprawl) or security incidents (container escapes).

The two H3s below cover the two halves of the trade-off. The first explains hypervisor virtualization in detail — what a Type 1 vs Type 2 hypervisor actually is, how `KVM` is just a kernel module that turns Linux into a Type 1 hypervisor, why each VM ships a full guest kernel and a guest init system, and what that costs in memory and boot time. The second explains OS-level virtualization — the Linux kernel features (namespaces + cgroups + OverlayFS) that let a process believe it has its own system while sharing the host kernel, why this drops memory overhead by 100× and boot time by 1000×, and what you give up in exchange (kernel shared across all containers).

## The Details

### Hypervisor Virtualization (Type 1 Bare-Metal, Type 2 Hosted): Virtualizing physical hardware, run...

A hypervisor — also called a Virtual Machine Monitor (VMM) — is a thin software layer that intercepts the guest's privileged CPU instructions (`CPUID`, `WRMSR`, `INVLPG`, port I/O) and either emulates them or passes them through to the real hardware via hardware-assisted virtualization (Intel VT-x / AMD-V with Extended Page Tables). The hypervisor exposes a fictitious hardware surface to the guest: a virtual CPU (`vCPU`), virtual RAM backed by host pages, a virtual NIC (`virtio-net`, `e1000`), and a virtual disk (`virtio-blk`, `qcow2`, `vmdk`). The guest kernel boots believing it owns bare metal. It does not. Every register write to "the disk controller" is intercepted by the hypervisor and translated into a host-side operation.

There are two architectural flavours. **Type 1 (bare-metal)** hypervisors run directly on the hardware with no host OS underneath — VMware ESXi, Microsoft Hyper-V, Xen, and the open-source KVM (which is technically a Linux kernel module that *turns* Linux into a Type 1 hypervisor; the host userspace is still there, but the kernel's `kvm.ko` + `kvm-intel.ko` modules own the CPU's virtualization extensions). **Type 2 (hosted)** hypervisors run as ordinary processes on top of a host OS — VirtualBox, VMware Workstation, VMware Fusion, Parallels, QEMU in pure-emulation mode. Type 1 is what cloud providers use (AWS Nitro is a custom Type 1 hypervisor built on KVM; Google Compute Engine uses KVM; Azure uses a modified Hyper-V); Type 2 is what developers use on their laptops.

| Property | Type 1 (ESXi, KVM, Hyper-V) | Type 2 (VirtualBox, VMware Workstation) |
|---|---|---|
| Runs on | Bare metal | Host OS (Windows/macOS/Linux) |
| Performance overhead | 1–5% (hardware-assisted) | 10–30% (extra scheduling layer) |
| Used by | Cloud providers, production datacenters | Developer laptops, CI test rigs |
| Failure mode | Whole physical host takes down all VMs | Host kernel panic takes down all VMs |
| Typical boot time | 30–120 seconds per VM (full guest kernel + init) | 30–120 seconds per VM (same) |
| Memory tax | ~256 MB hypervisor + full guest RAM | ~1 GB host OS + full guest RAM |

The defining cost of hypervisor virtualization is that **every VM ships a full guest operating system**. A Ubuntu 22.04 VM, even stripped, idles at 400–800 MB of resident RAM because the guest kernel has its own page cache, its own slab allocator, its own systemd, its own journald, its own OpenSSH daemon, its own cron, its own apt/dpkg database. Boot that VM and you wait 30–120 seconds while the guest kernel enumerates virtual devices, mounts its root filesystem, and runs `multi-user.target`. Multiply by 100 VMs and you have spent 40–80 GB of RAM just on guest kernels, plus several minutes of boot wall-clock time. The compensation is **strong isolation**: a kernel exploit inside the guest (say, CVE-2024-1086 in nf_tables) cannot directly escape into the host because the guest kernel runs in a different address space, with its own page tables managed by the hypervisor's Extended Page Tables. Escaping a VM into the host requires a hypervisor bug, not a guest kernel bug — and those are far rarer.

```bash
# Inspect a running KVM/QEMU VM: the host sees a qemu-system-x86_64 process
ps -ef | grep qemu-system
# root  1234  1  /usr/bin/qemu-system-x86_64 -name guest=vm-01 \
#   -machine pc-q35-6.2 -accel kvm -cpu host -smp 4 -m 8192 \
#   -drive file=/var/lib/libvirt/images/vm-01.qcow2,if=virtio \
#   -netdev user,id=net0 -device virtio-net-pci,netdev=net0

# The VM's vCPUs are host threads; check their scheduling class
chrt -p 1234
# pid 1234's current scheduling policy: SCHED_FIFO
# pid 1234's current scheduling priority: 50

# Memory: the guest's 8 GB is backed by host anonymous memory + KVM EPT
grep -E 'VmRSS|VmSize' /proc/1234/status
# VmSize:   8589935 kB
# VmRSS:    8390912 kB   <-- actual host RAM consumed by this VM
```

The production failure mode for hypervisor virtualization is **VM sprawl and boot latency**. A team that bootstraps a new VM per CI job spends 60–90 seconds of every test run waiting for the guest to come up. A platform team that runs 2000 microservices as 2000 VMs burns 1.6 TB of RAM on guest kernels alone. The cloud-native answer to this is not to abandon VMs — it is to run *many containers per VM*, which is the hybrid the next H3 covers.

### Containerization (OS-Level Virtualization): Sharing the host Linux kernel, isolating user-space p...

A container is not a virtual machine. There is no second kernel. The container's processes are scheduled by the *host* kernel, run on the *host* CPU, share the *host* page cache, and use the *host* syscall table. What makes them "containers" rather than "ordinary processes" is that the host kernel has been told — via three kernel subsystems — to lie to them about what they can see and what they can use. Those three subsystems are **namespaces** (covered in [[10.01.02. Linux Namespaces Isolation Primitives]]), **cgroups** (covered in [[10.01.03. Linux Control Groups (cgroups v1 and v2)]]), and **union filesystems** (covered in [[10.01.04. Union Filesystems and OverlayFS]]).

Namespaces make the process *see* a private world: its own PID 1, its own loopback interface, its own mount tree, its own hostname. Cgroups make the process *be allowed to use* only a slice of the host: at most 2 CPUs, at most 512 MB of RAM, at most 1000 PIDs. Union filesystems give the process a *filesystem view* assembled from stacked read-only image layers plus a thin writable layer. None of these subsystems virtualize hardware. None of them run a second kernel. The container's processes make ordinary syscalls (`open`, `read`, `write`, `fork`, `exec`) and the host kernel services them — it just services them under namespaces and cgroup limits that the process cannot perceive.

The payoff is dramatic. A minimal container image (`alpine:3.18`, 7 MB on disk; `gcr.io/distroless/java-base`, 170 MB) boots in 50–500 milliseconds because there is no kernel init sequence to run — the kernel is already up. The container's memory tax is the memory tax of the process itself plus a few hundred KB for the namespace bookkeeping. A 100-container deployment on a single host routinely fits in 16 GB of RAM, where the equivalent 100-VM deployment would need 80–160 GB. The trade-off is **kernel sharing**: every container runs the same kernel as the host, so a kernel exploit inside any container is an exploit against the host kernel and against every other container on that host. This is why production deployments of untrusted workloads (multi-tenant SaaS, code-execution platforms like Lambda) run containers *inside* VMs — the VM gives the strong isolation boundary, the container gives the cheap density, and you get both.

```text
                     VM                          Container
                     ──                          ──────────
  ┌──────────────────────────────┐    ┌──────────────────────────────┐
  │  Guest user-space (process)  │    │  Container user-space        │
  │  Guest kernel  (full OS)     │    │  ───── host kernel ─────     │
  │  Hypervisor (KVM/QEMU)       │    │  (shared across all          │
  │  Host kernel                 │    │   containers on the host)    │
  │  Physical hardware           │    │  Physical hardware           │
  └──────────────────────────────┘    └──────────────────────────────┘
   Boot: 30–120 s                      Boot: 50–500 ms
   RAM tax: 400–800 MB                 RAM tax: ~1 MB
   Isolation: very strong              Isolation: weaker (shared kernel)
   Density: ~10–20 per host            Density: ~100–500 per host
```

The cloud-native production topology is the **hybrid**: a Type 1 hypervisor (KVM on AWS Nitro, KVM on GCP, Hyper-V on Azure) runs many VMs per physical host, and inside each VM a container runtime (Docker, containerd, cri-o) runs many containers per VM. AWS Fargate, Google Cloud Run, and Azure Container Instances all internalise this pattern — you hand them a container image and they place it inside a fresh micro-VM (Firecracker, with a 125 ms boot and 5–10 MB memory tax) so that two customers' containers are isolated by both a VM boundary *and* a container boundary. This is the only safe topology for running untrusted code at scale; a pure-container topology (no VM underneath) is fine inside a single trust domain but is unacceptable for multi-tenant workloads.

```bash
# Confirm the kernel-sharing claim: a container's kernel version
# matches the host's exactly because it IS the host's kernel.
docker run --rm alpine uname -r
# 6.5.0-21-generic            <-- same as host

uname -r                       # on the host
# 6.5.0-21-generic            <-- identical

# Memory footprint comparison
docker stats --no-stream --format 'table {{.Name}}\t{{.MemUsage}}\t{{.CPUPerc}}'
# NAME                MEM USAGE        CPU %
# nginx-proxy         12.4MiB / 8GiB   0.13%
# api-svc-1           184MiB / 8GiB    1.20%
# postgres            98.3MiB / 8GiB   0.05%
# Total for 3 containers: <300 MB
# Equivalent 3 VMs would consume 2–3 GB just in guest kernels.
```

The production failure mode for containerization is the **kernel-shared exploit chain**. CVE-2019-5736 (`runc` container escape), CVE-2022-0185 (`fsconfig` heap overflow in `open_fs_context`), and CVE-2024-21626 (`runc` leak via `execve` file descriptor) all demonstrated that a privileged attacker inside a container could, with the right kernel or runtime bug, break out into the host and access every other container's filesystem and memory. The defensive response is layered: run containers as non-root (`USER 1000` in the Dockerfile), enable user-namespace remapping (`userns-remap` in `daemon.json` so container root maps to host UID 100000), drop capabilities (`--cap-drop=ALL --cap-add=NET_BIND_SERVICE`), apply seccomp profiles (`--security-opt seccomp=default.json`), and on multi-tenant clusters put the whole container inside a micro-VM so that even a kernel exploit gives you a VM boundary, not a host boundary. The layered defense is what "container security" actually means in production — not the container boundary itself, which is a convenience, not a security wall.
