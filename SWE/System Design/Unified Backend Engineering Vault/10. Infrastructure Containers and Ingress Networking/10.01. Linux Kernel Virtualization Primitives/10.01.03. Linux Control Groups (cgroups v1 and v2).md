# 10.01.03. Linux Control Groups (cgroups v1 and v2)

## What This Is

Control groups (cgroups) are the kernel subsystem that limits, accounts for, and isolates the resource usage of a collection of processes. Where namespaces (covered in [[10.01.02. Linux Namespaces Isolation Primitives]]) decide what a process can *see*, cgroups decide what a process is *allowed to use* — how many CPU seconds, how many bytes of RAM, how many I/O operations per second, how many PIDs it can fork, which device nodes it can open. Every container runtime (Docker, containerd, cri-o, Podman) wires each container's process tree into a cgroup at creation time, and the cgroup — not the runtime — is what actually enforces `--memory=512m` and `--cpus=2`. If cgroups did not exist, a runaway container could consume 100% of host CPU and RAM and bring down every other container on the host.

Cgroups come in two architectural versions. **v1** (merged in kernel 2.6.24, 2008) uses a separate hierarchy per controller — one tree for `cpu`, another for `memory`, another for `blkio`, another for `pids`, etc. A process is in exactly one cgroup per hierarchy, but the hierarchies are independent, which leads to coordination problems (a CPU-throttled process can still blow the memory limit and the controller cannot see each other's state). **v2** (merged in kernel 4.5, 2016, made default by systemd in 2019) uses a single unified hierarchy where every controller is mounted on the same tree. A process is in exactly one cgroup, full stop, and all controllers see the same process grouping. The v2 model is what modern Kubernetes and modern Docker use by default on any current distro. The three H3s below cover the general mechanism, the memory controller (the one that kills containers), and the v2 unified hierarchy that resolves v1's coordination problems.

## The Details

### Resource Metering and Limiting: Constraining process group access to CPU shares, CPU hard quotas,...

A cgroup is a directory in a special pseudo-filesystem that the kernel mounts at `/sys/fs/cgroup`. Creating a cgroup is literally `mkdir`. The kernel populates that directory with control files — `cgroup.procs` (newline-separated list of PIDs in this cgroup), `tasks` (v1 only — per-thread variant), `cpu.shares` (relative CPU weight), `cpu.cfs_quota_us` and `cpu.cfs_period_us` (hard CPU quota), `memory.limit_in_bytes`, `pids.max`, and so on. Moving a process into a cgroup is `echo <pid> > cgroup.procs`. Setting a limit is `echo 512M > memory.limit_in_bytes`. There is no daemon, no IPC, no userspace tool in the critical path — cgroups are a kernel filesystem and the kernel reads the limit on every allocation.

The CPU controller offers two complementary dials. `cpu.shares` is a *relative* weight: a cgroup with `cpu.shares=512` gets half the CPU of a cgroup with `cpu.shares=1024` when both are contending for the same CPU, but if there is no contention, either cgroup can use 100% of the CPU. This is what Kubernetes `requests.cpu` translates to — a share weight, not a hard cap. `cpu.cfs_quota_us` and `cpu.cfs_period_us` together define a *hard* cap: with `cpu.cfs_period_us=100000` (100 ms) and `cpu.cfs_quota_us=50000` (50 ms), the cgroup is allowed 50 ms of CPU every 100 ms — i.e. 0.5 CPU. This is what Kubernetes `limits.cpu` translates to. The CFS bandwidth throttler enforces it by adding the cgroup's threads to a runqueue throttled list when the quota is exhausted, which is why CPU-throttled pods show `nr_throttled` increasing in `cpu.stat`.

```bash
# v1: create a cgroup, put a process in it, limit it (root required).
mkdir /sys/fs/cgroup/memory/demo
echo 256M > /sys/fs/cgroup/memory/demo/memory.limit_in_bytes
echo 0 > /sys/fs/cgroup/memory/demo/memory.swappiness   # disable swap
echo $$ > /sys/fs/cgroup/memory/demo/cgroup.procs        # put this shell in
cat /sys/fs/cgroup/memory/demo/memory.usage_in_bytes
# 1234567    <-- current usage

# CPU hard cap: 0.5 CPU (50 ms per 100 ms period)
mkdir /sys/fs/cgroup/cpu/demo
echo 100000 > /sys/fs/cgroup/cpu/demo/cpu.cfs_period_us
echo  50000 > /sys/fs/cgroup/cpu/demo/cpu.cfs_quota_us
echo $$ > /sys/fs/cgroup/cpu/demo/cgroup.procs

# Verify by running a CPU-burner and watching top — it caps at ~50%.
python3 -c 'while True: pass' &
top -p $!    # CPU% hovers around 50, not 100

# What Docker does for `docker run --memory=256m --cpus=0.5`:
#   1. runc creates /sys/fs/cgroup/memory/docker/<container-id>/
#   2. Writes 268435456 (= 256*1024*1024) to memory.limit_in_bytes
#   3. Writes the container's init PID to cgroup.procs
#   4. The kernel now enforces the limit. The runtime is no longer involved.
docker run --rm --memory=256m --cpus=0.5 alpine cat /sys/fs/cgroup/memory/memory.limit_in_bytes
# 268435456
```

The accounting side of cgroups is what observability tools scrape. Every controller exports counter files: `cpuacct.usage` (nanoseconds of CPU consumed), `memory.usage_in_bytes`, `memory.max_usage_in_bytes`, `blkio.throttle.io_service_bytes`, `pids.current`. cAdvisor reads these and exposes them as Prometheus metrics (`container_cpu_usage_seconds_total`, `container_memory_working_set_bytes`); kubelet reads them to make scheduler decisions and to enforce eviction thresholds. The same files that the runtime uses to *enforce* limits are what the monitoring stack uses to *observe* usage — there is one source of truth and it is the cgroup filesystem.

The production failure mode for the CPU controller is the **`cpu.cfs_quota_us` throttle spiral**. A Java service with `limits.cpu=500m` (half a CPU) starts up, hits its JIT compilation burst, burns through 50 ms of quota in 8 ms, gets throttled for 92 ms, falls further behind, and never catches up — startup time goes from 5 seconds to 90 seconds, readiness probes start failing, and Kubernetes restarts the pod, which starts the cycle over. The diagnostic is `cat /sys/fs/cgroup/cpu/cpu.stat` showing `nr_throttled` increasing rapidly. The fix is either to raise `limits.cpu` to cover the startup burst, to remove the limit entirely (rely on `requests.cpu` and node-level isolation), or in Kubernetes 1.25+ to enable the `cpu.cfs_quota_us=-1` opt-out via the `resources.limits.cpu: "0"` workaround. The deeper lesson: `cpu.shares` (requests) is safe; `cpu.cfs_quota_us` (limits) is a hard cap that will throttle you the moment you exceed it, with no burst credit.

### Memory cgroups: Enforcing hard limits and handling out-of-memory container termination (`OOMKilled`)

The memory controller is the cgroup that kills containers. It tracks every page of memory — anonymous (heap, stack), file-backed (page cache from reads/writes), swap, and kernel slab (when accounting is enabled) — attributed to the cgroup that allocated it. When usage exceeds `memory.limit_in_bytes`, the kernel's cgroup-aware OOM killer fires: it picks the largest process in the cgroup (by RSS plus young-anonymous-page weighting) and sends it `SIGKILL`. The killed process exits with code 137 (128 + 9, the standard "killed by signal 9" exit), and `docker inspect` reports `OOMKilled: true` in the container's state. The kill is unconditional — there is no `SIGTERM` first, no graceful shutdown, no chance for the process to flush buffers or close sockets cleanly.

The subtle distinction is between `memory.limit_in_bytes` (the hard cap that triggers OOM kill) and `memory.soft_limit_in_bytes` (a hint the kernel uses to reclaim pages under global memory pressure but does not enforce under normal operation). Soft limits are how Kubernetes implements `requests.memory` — a hint to the scheduler and to the kernel's reclaim path that this cgroup should be squeezed first when memory is tight. Hard limits implement `limits.memory` and are what produce `OOMKilled`. A common misconfiguration is to set `requests.memory=256Mi` and `limits.memory=256Mi` identically — this means no burst headroom, and any transient spike (a large query result set, a JIT compilation, a JSON parse of a big payload) kills the pod.

```bash
# Watch a process get OOM-killed under cgroup memory pressure (v1).
mkdir /sys/fs/cgroup/memory/oom-demo
echo 50M > /sys/fs/cgroup/memory/oom-demo/memory.limit_in_bytes
# Disable swap-accounting escape (only works if swap is also limited
# via memory.memsw.limit_in_bytes — otherwise the kernel will swap).
echo 0 > /sys/fs/cgroup/memory/oom-demo/memory.swappiness

# Run an allocation bomb inside this cgroup:
echo $$ > /sys/fs/cgroup/memory/oom-demo/cgroup.procs
python3 -c 'x = bytearray(10**9)'    # try to grab 1 GB
# (process dies)
echo $?                              # in parent shell
# 137                                 <-- 128 + 9 = SIGKILL

# Check the cgroup's OOM counters:
cat /sys/fs/cgroup/memory/oom-demo/memory.oom_control
# oom_kill_disable 0
# under_oom 0
# oom_kill 1                          <-- one OOM kill happened

# Docker equivalent — same kernel mechanism, wrapped:
docker run --rm --memory=50m python:3-slim python -c 'x = bytearray(10**9)'
# Status: download complete
# ...
docker inspect <container-id> | grep -E 'OOMKilled|ExitCode'
# "OOMKilled": true,
# "ExitCode": 137
```

The classic production trap is the **JVM `-Xmx` vs container `--memory` mismatch**. A JVM started with `-Xmx2g` inside a container with `--memory=2g` will reliably OOM-kill, because the JVM's heap is only one component of its total memory: there is also metaspace (class metadata, default 1 GB cap on Java 8), code cache (JIT-compiled methods, default 240 MB), thread stacks (1 MB × thread count), direct byte buffers (NIO, unbounded by default), GC overhead, and the JVM's own native allocator. The rule of thumb is `--memory = 1.5 × -Xmx + 512 MB`. Java 10+ (and 8u191+) added `-XX:+UseContainerSupport` (on by default) and `-XX:MaxRAMPercentage=75` so the JVM reads `memory.limit_in_bytes` from the cgroup and sizes its heap accordingly — eliminating the need to pass `-Xmx` explicitly.

The deeper failure mode is the **page-cache double-count**. Linux uses free RAM as page cache for file I/O; that cache is accounted to the cgroup that did the I/O. A service that reads a 4 GB file in a container with `--memory=1g` will be OOM-killed partway through the read because the cached pages are charged to its cgroup, even though the kernel could in principle reclaim them under pressure. The `memory.kmem.limit_in_bytes` (kernel memory) and `memory.memsw.limit_in_bytes` (RAM + swap combined) files exist to bound these, but the cleanest mitigation is to design workloads that stream large files rather than reading them fully into memory. When debugging an `OOMKilled` pod, the diagnostic chain is: `kubectl describe pod` → look for `Last State: Terminated, Reason: OOMKilled, Exit Code: 137` → `kubectl top pod` to see the memory usage trend → compare against `resources.limits.memory` → check the process's RSS at crash time with `cat /sys/fs/cgroup/memory/memory.max_usage_in_bytes`.

### cgroups v2 unified hierarchy: Resolving resource contention conflicts in modern systemd environments

The original cgroups v1 design let each controller have its own hierarchy. This was flexible but incoherent: a process could be in `/sys/fs/cgroup/cpu/bursty/` for CPU scheduling and `/sys/fs/cgroup/memory/leaky/` for memory accounting, and the two controllers had no way to coordinate. The result was the **coordinated-throttling problem** — a process that was both CPU-throttled and under memory pressure would thrash, with neither controller knowing about the other's state. Worse, a process could be in different leaves of the CPU and memory trees, so the CPU controller saw it as belonging to one sibling group and the memory controller as belonging to another, making resource accounting inconsistent across controllers.

Cgroups v2 fixes this with a single unified hierarchy. There is one cgroup tree, mounted at `/sys/fs/cgroup` (no per-controller subdirectories). Every controller is available on every node in the tree, but each controller must be explicitly enabled on a node by writing its name to the parent's `cgroup.subtree_control` file. This means a node can have `+memory +cpu +pids` enabled for its children while a sibling node has `+io +rdma` — but every process in the tree has one and only one cgroup, and all enabled controllers see the same process grouping. The tree is also exclusively process-leaf: internal nodes cannot contain processes directly (except for the root), which enforces clean accounting boundaries.

```bash
# v2 layout — single tree, controllers enabled per-subtree.
mount | grep cgroup
# cgroup2 on /sys/fs/cgroup type cgroup2 (rw,nosuid,nodev,noexec)

ls /sys/fs/cgroup/
# cgroup.controllers      cgroup.stat              cpu.pressure
# cgroup.subtree_control  cpu.max                  io.pressure
# cgroup.threads          cpu.stat                 memory.pressure
# cpu.weight              init                     sys-a.slice
# cpu.weight.nice         io.weight                system.slice
# dev-hugepages.mount     memory.current           user.slice
# dev-mqueue.mount        memory.max               user@1000.service
# ...

# Available controllers (read at the root):
cat /sys/fs/cgroup/cgroup.controllers
# cpuset cpu io memory hugetlb pids rdma misc

# Enable memory + cpu + pids for a new sub-tree:
mkdir /sys/fs/cgroup/demo
echo "+memory +cpu +pids" > /sys/fs/cgroup/cgroup.subtree_control

# Now /sys/fs/cgroup/demo has the v2 controller files:
ls /sys/fs/cgroup/demo/
# cgroup.controllers      cpu.max           memory.swap.max
# cgroup.subtree_control  cpu.stat          pids.current
# cgroup.threads          io.max            pids.max
# cpu.pressure            memory.current    ...
# cpu.weight              memory.max

# Set limits (note v2 file names differ from v1):
echo 256M > /sys/fs/cgroup/demo/memory.max
echo "50000 100000" > /sys/fs/cgroup/demo/cpu.max   # quota period (50% CPU)
echo 100  > /sys/fs/cgroup/demo/pids.max

# Put a process in (replaces cgroup.procs in v1):
echo $$ > /sys/fs/cgroup/demo/cgroup.procs

# The unified hierarchy means systemd uses cgroups v2 natively.
# `systemctl status` shows the cgroup path:
systemctl status sshd | head -5
# ● ssh.service - OpenBSD Secure Shell server
#      Loaded: loaded (/lib/systemd/system/ssh.service; enabled)
#      Active: active (running) since ...
#        Docs: man:sshd(8)
#        CGroup: /system.slice/ssh.service   <-- the cgroup path
#                └─1234 /usr/sbin/sshd -D
```

The systemd integration is what made v2 the de facto default. systemd places every unit (service, slice, scope) into a cgroup at startup, names the cgroup after the unit, and lets you set resource limits directly in the unit file: `MemoryMax=512M`, `CPUQuota=50%`, `TasksMax=512`. `systemd-run --uid=1000 -p MemoryMax=256M -p CPUQuota=10% --slice=user.slice stress --vm 1 --vm-bytes 1G` is a one-liner that puts `stress` into a cgroup capped at 256 MB and 10% CPU — and it gets OOM-killed the moment it exceeds 256 MB. Kubernetes (1.25+ by default) and Docker (20.10+ with `--cgroup-version=2`) both run on v2 on modern distros, which means the per-container cgroup paths under `/sys/fs/cgroup/system.slice/docker-<id>.scope/` are visible to systemd-cgls and controllable by systemctl.

The production failure mode for v2 is the **controller-not-enabled surprise**. A pod with `resources.limits.memory` but no `resources.limits.cpu` may appear to not be CPU-limited, but if the kubelet was started without `--cgroup-driver=systemd` or on a host where `cpu` is not in `cgroup.subtree_control`, the CPU limit silently does nothing. The diagnostic is `cat /sys/fs/cgroup/kubepods.slice/kubepods-besteffort.slice/.../cgroup.controllers` — if `cpu` is missing from the list, the limit is unenforced. The other classic v2 migration failure is **breakage of tools that hard-code v1 paths**: older versions of `cadvisor`, `node_exporter`, and `heapster` read `/sys/fs/cgroup/memory/memory.usage_in_bytes` (v1) rather than `/sys/fs/cgroup/memory.current` (v2) and report zero memory usage — silently breaking dashboards. The fix is to keep cAdvisor and node_exporter versions current; the v2 paths have been supported since 2019.
