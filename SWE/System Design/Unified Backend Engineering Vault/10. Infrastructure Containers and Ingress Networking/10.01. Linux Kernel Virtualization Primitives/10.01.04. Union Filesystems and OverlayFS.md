# 10.01.04. Union Filesystems and OverlayFS

## What This Is

A union filesystem (also called a *union mount*) is a kernel feature that takes multiple underlying directories and presents them as a single merged directory tree. Files in the lower directories appear alongside files in the upper directory; reads transparently walk the stack from top to bottom and return the first match; writes go to the uppermost layer only, leaving the lower layers untouched. This is the storage primitive that makes Docker images work: each `Dockerfile` instruction (`FROM`, `RUN apt-get install`, `COPY app.jar`) produces a new read-only layer, the layers are stacked with the newest on top, and a running container adds one final writable layer on top of the stack. Without union filesystems, every container would have to copy the entire image to a writable location on start — a 700 MB image × 100 containers would be 70 GB of copies. With union filesystems, the same 100 containers share 700 MB of read-only layers and each consumes only the few megabytes that they actually modify.

The Linux kernel has gone through three generations of union filesystem. **UnionFS** (2004) was the original academic implementation, never merged. **AUFS** (Another UnionFS) was a rewrite that Docker used as its first default storage driver in 2013; it remained out-of-tree and was never accepted into mainline. **OverlayFS** (merged in kernel 3.18, 2014) is the modern, kernel-native implementation that Docker switched to by default in 1.12 (2016). All three implement the same logical model — lower + upper = merged — but OverlayFS is the only one you will encounter in production today. The three H3s below cover the union concept, the OverlayFS mount mechanics, and the copy-on-write operation that is the heart of how containers stay cheap.

## The Details

### Layered Filesystems: Combining multiple directories into a single unified virtual filesystem view

A union mount is conceptually a stack of directories presented as one. Each layer in the stack is an ordinary directory on disk — there is nothing special about the underlying filesystem, it can be ext4, xfs, btrfs, anything. What is special is the kernel's *view* of those directories: the kernel walks the stack from top to bottom on every `lookup`, returns the first matching entry, and reports the union as if it were a single directory. The lower layers are read-only (in OverlayFS they are formally read-only; in AUFS they could be marked writable but Docker always mounted them read-only). The upper layer is read-write. A read of `/etc/passwd` in the merged view returns whichever version is highest in the stack — if the container wrote a new `/etc/passwd`, the upper layer's copy is returned; otherwise the lower layer's copy from the base image is returned.

Docker's image format is the canonical application of this model. A Docker image is a stack of layers; each layer corresponds to one Dockerfile instruction that modified the filesystem. The `Dockerfile` `FROM ubuntu:22.04` produces the base layer (~78 MB). Each subsequent `RUN apt-get install -y curl` produces another layer containing only the files that `apt` added or modified — typically a few megabytes. `COPY app.jar /app/` produces a layer containing just the JAR. None of the layers contains the others; they are *deltas*. When the container starts, Docker stacks all the image's layers as read-only lower directories plus a fresh empty upper directory for the container's writes, mounts the union, and `pivot_root`s into it. The total disk usage is the sum of the layer sizes — sharing the base ubuntu layer across 100 images costs 78 MB once, not 7.8 GB.

```text
A docker image as a layered filesystem:

  +-----------------------------+  ← container writable layer (UpperDir)
  |  /etc/hostname              |     (only the files this container wrote)
  |  /etc/hosts                 |
  |  /tmp/app.log               |
  +-----------------------------+
  |  /app/spring-boot-app.jar   |  ← layer: COPY app.jar (image layer 3)
  +-----------------------------+
  |  /usr/bin/curl              |  ← layer: RUN apt-get install curl (layer 2)
  |  /usr/lib/...curl.so...     |
  +-----------------------------+
  |  /bin, /lib, /usr, /etc ... |  ← layer: FROM ubuntu:22.04 (layer 1, base)
  +-----------------------------+

  Merged view (what the container sees):
    /etc/hostname           ← from UpperDir (container's own)
    /etc/hosts              ← from UpperDir (Docker rewrote it on start)
    /etc/passwd             ← from base image (no override)
    /app/spring-boot-app.jar← from layer 3
    /usr/bin/curl           ← from layer 2
    /bin/bash               ← from base layer

  Disk usage:
    Base layer: 78 MB   (shared across every ubuntu-based image on host)
    Layer 2:     4 MB   (shared across every image that apt-installed curl)
    Layer 3:    35 MB   (the JAR)
    Container:   2 MB   (the few files this container modified)
    Total:     119 MB   (not 78 + 4 + 35 + 2 = 119, but shared with siblings)
```

The history of Docker's storage drivers is worth knowing because old documentation still references them. **AUFS** was Docker's first default (2013–2016) and is still available as `--storage-driver=aufs` on systems that have the out-of-tree module. **devicemapper** was Docker's default on RHEL/CentOS for several years because Red Hat refused to ship AUFS; it used thin-provisioned LVM snapshots rather than a true union filesystem and was notoriously buggy (the `loopback` mode corrupted on host crashes; `direct-lvm` mode was correct but required manual setup). **Btrfs** and **ZFS** subvolume drivers use those filesystems' native snapshot capabilities to implement layers — fast and reliable, but require the host to be formatted with that filesystem. **OverlayFS** (`overlay2` driver) is the modern default on every modern Linux distribution and what 99% of production Docker installs use. The `docker info` command's `Storage Driver: overlay2` line confirms this.

The production failure mode for layered filesystems is the **`/var/lib/docker` disk exhaustion**. Every layer ever pulled accumulates in `/var/lib/docker/overlay2/`, and Docker only garbage-collects a layer when no image references it and no container is using it. A CI host that pulls thousands of images without periodic `docker system prune -a` will fill its root partition; the symptom is `no space left on device` mid-`docker pull`, and on OverlayFS this can leave a half-written layer that future pulls refuse to clean up. The fix is scheduled `docker image prune --filter "until=24h"` and monitoring `/var/lib/docker` disk usage. The deeper failure mode is **inode exhaustion** — OverlayFS creates a `link` file (a hardlink to the lower layer's file) for every unchanged file in the upper layer's `diff` directory, so a host running thousands of containers with deep image stacks can exhaust the inode pool of the underlying filesystem even when bytes are available; the diagnostic is `df -i /var/lib/docker`.

### OverlayFS architecture: `LowerDir` (Read-only base image layers), `UpperDir` (Read-write containe...

OverlayFS exposes four directories to the kernel's mount API: `lowerdir`, `upperdir`, `workdir`, and the mount target (which becomes the merged view). `lowerdir` is one or more colon-separated read-only directories, ordered left-to-right from top to bottom of the stack — so `lowerdir=/l3:/l2:/l1` means `/l3` is checked first, then `/l2`, then `/l1`. `upperdir` is a single read-write directory where all writes land. `workdir` is an internal scratch directory OverlayFS uses to atomically prepare copy-up operations before they become visible — it must be on the same filesystem as `upperdir` and is never directly visible to userspace. The mount target — the path you pass to `mount -t overlay overlay -o ...` — becomes the merged view that the container sees as its root.

The kernel's overlay inode (`struct ovl_inode` in `fs/overlayfs/inode.c`) is a thin wrapper that holds a pointer to the upper inode (if it exists in the upper layer) and the lower inode (whichever lower layer supplied it). On `lookup`, the kernel walks the lower layers in order and caches the first match; if a matching entry also exists in the upper layer, the upper wins. On `stat`, the kernel reports the upper inode's metadata if the upper has the file, otherwise the lower's. On `readdir`, OverlayFS merges directory entries from all layers (deduplicating by name) and presents the union. The cost is one extra pointer-chase per syscall compared to a plain filesystem — typically a few microseconds, which is why OverlayFS feels native-speed for almost all workloads.

```bash
# Build the merge by hand, no Docker involved.
mkdir -p /tmp/ovl/{lower1,lower2,upper,work,merged}

# Populate the lowers (simulating two image layers):
echo "from lower1" > /tmp/ovl/lower1/file-a
echo "from lower1" > /tmp/ovl/lower1/file-b
echo "from lower2" > /tmp/ovl/lower2/file-b    # overrides lower1's file-b
echo "from lower2" > /tmp/ovl/lower2/file-c

# Mount the overlay (must be root; lowerdir is colon-separated):
mount -t overlay overlay \
    -o lowerdir=/tmp/ovl/lower2:/tmp/ovl/lower1,upperdir=/tmp/ovl/upper,workdir=/tmp/ovl/work \
    /tmp/ovl/merged

# Inspect the merged view:
ls /tmp/ovl/merged
# file-a  file-b  file-c

cat /tmp/ovl/merged/file-b
# from lower2   <-- topmost lower wins (lower2 is first in lowerdir=)

# Docker exposes the same data through /proc/<pid>/mountinfo:
docker run -d --name demo alpine sleep 3600
PID=$(docker inspect -f '{{.State.Pid}}' demo)
grep overlay /proc/$PID/mountinfo
# 1234 5678 0:42 / / rw,relatime - overlay overlay rw,lowerdir=...,upperdir=...,workdir=...

# The on-disk layout of /var/lib/docker/overlay2/:
ls /var/lib/docker/overlay2/
# <layer-hash>-init   <-- the init layer (Docker adds /etc/hostname, /etc/hosts, ...)
# <layer-hash>        <-- the container's writable upper layer
# <image-layer-hash>  <-- one per image layer, referenced via the link file

ls /var/lib/docker/overlay2/<container-upper-hash>/
# diff/      <-- the upperdir contents (the container's writes)
# work/      <-- the workdir (OverlayFS scratch)
# merged/    <-- the merged view mounted when the container is running
# link       <-- a short name used in lowerdir= references (e.g. "2KQT5G...")
# lower      <-- the colon-separated list of layer links that form the lowerdir
# committed  <-- exists only after the container stops; used by docker commit

cat /var/lib/docker/overlay2/<container-upper-hash>/lower
# l/7H2K...:l/A8B5...:l/Q9W4...   <-- colon-separated layer links
```

The `link` and `lower` files are how Docker implements efficient stacking without absurdly long pathnames. Each layer directory under `/var/lib/docker/overlay2/` contains a `link` file with a short, randomly-generated name (e.g. `2KQT5G...`), and the directory itself is referenced through `/var/lib/docker/overlay2/l/2KQT5G...` (the `l/` directory holds hardlinks to each layer's root). When Docker mounts a container, the `lowerdir=...` option is built by reading the layer's `lower` file and resolving each link. This avoids the kernel's per-mount option length limit (one page, typically 4096 bytes) that a long stack of absolute paths would otherwise hit.

The production failure mode for OverlayFS is the **`Storage Driver: overlayfs` kernel-version mismatch**. OverlayFS gained features across kernel versions — `lowerdir+upperdir` mounted read-write in 3.18, multiple lowerdirs in 4.0, `redirect_dir` (for renaming directories across layers) in 4.10, `metacopy` (metadata-only copy-up) in 4.12. A Docker install on a kernel older than 4.0 can only use a single lowerdir, which breaks the multi-layer model. A kernel with `redirect_dir` disabled will fail `docker build` steps that rename directories with `EXDEV: cross-device link not permitted` — the symptom is `RUN mv /app/dist /var/www/html` failing mid-build. The fix is to enable `redirect_dir` in the kernel config or to avoid cross-layer renames in Dockerfiles. The other classic failure is **NFS-backed `upperdir`**: OverlayFS requires `upperdir` and `workdir` to be on a filesystem that supports `trusted.*` extended attributes (`xattr`s). NFS does not, by default, so an attempt to mount an OverlayFS with `upperdir` on an NFS mount fails with `overlayfs: filesystem on 'upperdir' does not support file handles` or silently corrupts. The fix is to keep `upperdir` on local ext4/xfs and use a bind mount or volume for any shared storage.

### The Copy-on-Write (CoW) operation: Duplicating read-only files to the `UpperDir` upon mutation

Copy-on-write is the mechanism that keeps the upper layer small and the lower layers immutable. When a process inside the container opens a file from a lower (read-only) layer for reading, OverlayFS simply passes the read through to the lower layer — no copy, no overhead. When the same process opens the file for writing (or truncates it, or `chmod`s it, or `utimes`s it), OverlayFS intercepts the write, copies the entire file from the lower layer to the upper layer, and then applies the modification to the upper-layer copy. From that point on, the file *exists* in the upper layer, and subsequent reads return the upper-layer version. The lower layer's copy is never modified — which is what allows a hundred containers to share the same base image layer on disk simultaneously, each with its own private modifications.

The cost of the copy-up is proportional to the size of the file being modified. A 100 KB config file costs ~100 microseconds (one disk read, one disk write, both cached). A 5 GB database file costs seconds — the entire 5 GB must be copied before the first byte is written, which is why running a database on the container's writable layer is a performance disaster. The standard mitigation is to put database datafiles in a named volume (see [[10.03.02. Container Storage and Persistence]]) — volumes are mounted directly into the container's mount namespace and bypass OverlayFS entirely, so writes go straight to the underlying filesystem with no copy-up penalty. The OverlayFS documentation calls the upper layer "thin" precisely because it is supposed to stay small; a container whose upper layer grows to gigabytes is a sign that the workload is using OverlayFS for the wrong kind of data.

```bash
# Demonstrate the copy-up with file sizes visible.
mkdir -p /tmp/cow/{lower,upper,work,merged}
dd if=/dev/urandom of=/tmp/cow/lower/big.bin bs=1M count=10 2>/dev/null
mount -t overlay overlay \
    -o lowerdir=/tmp/cow/lower,upperdir=/tmp/cow/upper,workdir=/tmp/cow/work \
    /tmp/cow/merged

# Before any write, the upper dir is empty:
ls -la /tmp/cow/upper/   # empty
du -sh /tmp/cow/upper/   # 0

# Modify one byte of the 10 MB file:
printf '\x00' | dd of=/tmp/cow/merged/big.bin bs=1 seek=5 count=1 conv=notrunc 2>/dev/null

# After the write, the upper dir has the full 10 MB copy:
ls -la /tmp/cow/upper/
# -rw-r--r-- 1 root root 10485760 ... big.bin
du -sh /tmp/cow/upper/   # 10M  <-- entire file copied up, not just the modified byte

# Deletions: OverlayFS uses whiteout files (character device 0/0):
rm /tmp/cow/merged/big.bin
ls -la /tmp/cow/upper/
# c--------- 1 root root 0, 0 ... big.bin   <-- whiteout marker
ls /tmp/cow/merged/   # empty — the lower file is hidden by the whiteout
# But the lower file is untouched:
ls /tmp/cow/lower/   # big.bin still there

# Whole-directory replacement uses an opaque marker (xattr):
rm -rf /tmp/cow/merged/subdir
mkdir /tmp/cow/merged/subdir
getfattr -d -m trusted /tmp/cow/upper/subdir
# trusted.overlay.opaque="y"   <-- tells OverlayFS to ignore lower-dir subdir/
```

The whiteout mechanism is the counterpart to copy-up for *deletions*. When a container deletes a file that exists only in a lower layer (so there is nothing in the upper layer to actually delete), OverlayFS creates a character device with major:minor `0:0` in the upper layer at the same path. The kernel's overlay lookup sees the whiteout, hides the lower-layer file, and reports the file as not-existing in the merged view. The lower-layer file is untouched — only the whiteout marker in the upper layer exists. For whole-directory replacements, OverlayFS uses an extended attribute `trusted.overlay.opaque=y` on the upper-layer directory, which tells the kernel to ignore all lower-layer entries with that name. These mechanisms are why a Dockerfile's `RUN rm -rf /var/lib/apt/lists/*` does not actually shrink the image — the deletion only adds whiteouts to the new layer; the deleted files still exist in the lower layer and still consume disk and bandwidth on `docker pull`. The standard fix is the multi-stage build pattern (see [[10.02.02. Dockerfile Optimization and Multi-Stage Builds]]) where the deletion is irrelevant because only the final minimal stage is shipped.

The production failure mode for copy-on-write is the **silent throughput collapse**. A workload that opens a large lower-layer file for append (a log writer appending to `/var/log/app.log` where the log file came from the image) triggers a full copy-up on the first append — a 500 MB log file is copied to the upper layer, taking 2–5 seconds, during which the writer appears hung. After the copy-up, subsequent appends are fast (the file is now in the upper layer), but the disk space doubles. Worse, every container on the same image does the same copy-up independently — 10 containers × 500 MB = 5 GB of upper-layer copies of a file that should have been in a volume from the start. The diagnostic is `du -sh /var/lib/docker/overlay2/*/diff` after a container has been running, looking for unexpectedly large `diff` directories. The fix is universal: **stateful data — logs, databases, uploads, caches — does not belong in the container's writable layer.** It belongs in a named volume (which bypasses OverlayFS) or a bind mount (which also bypasses OverlayFS). The container's writable layer is for ephemeral scratch only.
