# 11.00. Map of Content: Observability and Ops

## Overview

This section covers **11. Observability Telemetry and Operations** — the discipline of running a system in production and knowing, at every moment, what it is actually doing. Observability is not "logging plus monitoring"; it is the engineering answer to a single uncomfortable question: *when a user reports that "the app is slow", how do you find the cause before they finish typing the support ticket?* Answering that question requires three kinds of telemetry — logs, metrics, and traces — plus the operational discipline to ship code without taking the system down. This section teaches all four.

The vault treats observability as a layered concept, not a vendor product. Layered mental model: at the bottom is the OS (Section 02 — `futex`, `epoll`, `write(2)`, `clock_gettime`), and the network (Section 03 — TCP, HTTP). On top of that sits the runtime (Section 04 — JVM, libuv, GIL). On top of that sits the framework (Section 05 — request/response pipeline, filters, middleware). Observability instruments every layer: structured logs are written by application code but flow through runtime I/O, shipped by host agents, and indexed by cluster-scale search engines. Traces cross process boundaries via HTTP headers, but each span is recorded against the runtime's clock. Metrics are pulled over HTTP from `/metrics` endpoints that the framework exposes. CI/CD is the operational loop that lets you fix what telemetry tells you is broken.

The notes below are organized by concept, not by framework. Each concept is taught once at the conceptual level, then implemented deeply in the Spring Boot anchor stack, then rapidly translated into Express, Django, Flask, and Laravel as deltas.

## Section Map

### 11.01. Structured Logging and Log Aggregation

- [[11.01.01. The Fallacy of Unstructured Text Logs]] — Why `System.out.println("user " + userId + " did " + action)` is a production liability: free-form strings force downstream parsers to guess field boundaries with regex, break silently when developers rephrase the message, and cannot be filtered or aggregated without a parsing layer. This note establishes the structured-logging contract: every log line is a JSON object with stable field names (`timestamp`, `level`, `logger`, `message`, `trace_id`, `user_id`, `event`), emitted by SLF4J + Logback + `logstash-logback-encoder` in Java, `structlog` in Python, and `Log::info('...', $context)` in Laravel.
- [[11.01.02. Contextual Logging and Mapped Diagnostic Context (MDC)]] — How to make every log line in a request carry `trace_id`, `user_id`, and `tenant_id` *without* manually passing those values into every `log.info()` call. Covers the SLF4J `MDC` thread-local map, the Logback `%X{userId}` pattern, Spring Boot servlet filters that populate MDC at request entry, the `@Async` propagation problem (thread-local state does not cross executor boundaries — solved by `TaskDecorator`), and the cross-runtime equivalents: Node.js `AsyncLocalStorage`, Python `contextvars` (PEP 567), Go `context.Context`.
- [[11.01.03. High-Throughput Log Shipping Architectures]] — How to move 100k+ log events per second per host from application memory to a queryable index without blocking the request thread and without losing data when the index is down. Compares three architectures: agent-based (Filebeat/Fluent Bit tails files → Kafka → Elasticsearch), app-direct (HTTP push to Loki/CloudWatch), and buffer-at-edge (Kafka as the spool between agents and the indexer). Covers the throughput math (events/sec × avg bytes = bandwidth), the backpressure spool-to-disk contract, and the Elasticsearch index-pattern model vs. the Loki label-based query model.

### 11.02. Distributed Tracing and OpenTelemetry

- [[11.02.01. Distributed Tracing Foundations]] — The trace/span/parent data model that lets you reconstruct a single user request that hit 50 services. Defines *trace* (a tree of spans, one per service hop), *span* (a unit of work with start/end timestamps, operation name, tags, events, status), *trace ID* (propagated across all services), *span ID* (unique per span), and *parent span ID* (forms the tree). Covers the Google Dapper paper (2010), the OpenTracing + OpenCensus merge into OpenTelemetry, and why tracing is mandatory in microservices: without it, a 500 ms p99 latency across 50 services is unattributable.
- [[11.02.02. Context Propagation and W3C TraceContext]] — How the trace ID and span ID actually cross the process boundary: the `traceparent` HTTP header (`00-<trace-id>-<parent-id>-<trace-flags>`), the `tracestate` vendor extension header, baggage propagation, and the B3/Zipkin header format that pre-dates the W3C standard. Covers the inject/extract API, the failure mode of a single un-instrumented intermediary (a load balancer, a queue) breaking the trace tree, and the `traceflags` sampled bit that controls whether a trace is recorded at all.
- [[11.02.03. The OpenTelemetry (OTel) Framework]] — The OTel API (instrumentation standard — `Tracer`, `Span`, `SpanContext`), the OTel SDK (implementation — `BatchSpanProcessor`, `OTLPSpanExporter`), the OTel Collector (the daemon that receives, processes, batches, and exports telemetry to backends like Jaeger, Zipkin, Datadog, Tempo), and the language-specific auto-instrumentation that wraps HTTP clients, JDBC, Kafka producers, and gRPC stubs without code changes. Covers the resource model (`service.name`, `service.instance.id`, `host.name`) that tags every span with its origin.

### 11.03. Application Metrics and Prometheus Monitoring

- [[11.03.01. Metrics Data Model and Dimensionality]] — Why metrics are not logs: a metric is a single floating-point value identified by (name, label-set, timestamp), not a free-form string. Defines the four metric types — counter (monotonic, `http_requests_total`), gauge (bidirectional, `jvm_memory_used_bytes`), histogram (bucketed, `http_request_duration_seconds_bucket` with explicit `le` boundaries), summary (client-side quantiles, deprecated in Prometheus) — and explains why labels are cardinality budget, not freeform tags.
- [[11.03.02. Prometheus Architecture and Pull Model]] — The pull model (Prometheus server scrapes `/metrics` on each target every 15–60 s) vs. the push model (StatsD, InfluxDB). Covers service discovery (Kubernetes `endpoints`, Consul, EC2, DNS), the scrape config, the time-series database internals (mmap-ed chunks of 120 samples each, goroutine-per-scrape, WAL for durability), the Alertmanager integration, and the pushgateway exception for batch jobs that exit before the next scrape.
- [[11.03.03. PromQL and Alerting Engineering]] — PromQL syntax: instant vectors (`http_requests_total`), range vectors (`rate(http_requests_total[5m])`), offset modifiers, the `histogram_quantile(0.99, rate(...))` pattern for p99 latency, recording rules to pre-compute heavy queries, and the alerting rule contract (`for: 5m`, `labels: { severity: page }`, `annotations: { runbook: <url> }`). Covers the count-vs-rate footgun and the absent-series alerting pattern.

### 11.04. CI CD Pipelines and Zero-Downtime Deployments

- [[11.04.01. Continuous Integration and Artifact Building]] — The pipeline that runs on every push: lint → type-check → unit tests → integration tests with Testcontainers → SAST/security scan → build OCI image → push to registry → sign with Cosign. Covers the build-vs-purchase decision (GitHub Actions, GitLab CI, Jenkins, Buildkite), the hermetic build contract (reproducible from `pom.xml`/`package.json` lockfile, no host-installed dependencies), and the artifact-promotion model (dev → staging → prod, each stage a signed image digest).
- [[11.04.02. Zero-Downtime Deployment Strategies]] — Rolling (sequentially replace old pods behind the load balancer, `maxSurge=25%`, `maxUnavailable=0`), Blue/Green (two full environments, flip the router), Canary (route 1% → 10% → 50% → 100% based on error-rate SLO gates), and Shadow (mirror production traffic to the new version, compare outputs but never serve them). Covers the readiness probe contract, the rollback trigger (error rate > 0.1% for 2 minutes), and the database-migration problem that makes "zero-downtime" a lie without backward-compatible schema changes.
- [[11.04.03. Graceful Shutdown Lifecycles]] — The Linux signal sequence (`SIGTERM` → app drains → `SIGKILL` after `terminationGracePeriodSeconds=30s`), the Spring Boot `PreDestroy` / `SmartLifecycle` hook ordering, the Tomcat `threadPool.shutdown()` + `awaitTermination(20s)` pattern, the in-flight request drain problem, the Kafka consumer `commitSync` before exit, and the connection-pool drain that prevents the "502 right after deploy" incident. Covers `SO_LINGER`, the kubelet `preStop` sleep, and why `SIGINT` ≠ `SIGTERM` in container contexts.

## How to Read This Section

1. **Read the concept notes first.** They establish the mental model — what telemetry is, why each type exists, and what each one cannot tell you on its own.
2. **Implement the anchor.** The Spring Boot anchor note is where you build the real, load-tested implementation: Logback JSON appenders, MDC filters, the OTel SDK wired into the Spring Boot autoconfiguration, the `/metrics` endpoint, the readiness/liveness probes.
3. **Run the delta pass.** Open the other ecosystems and implement the same feature as a translation exercise. Note where the ecosystem's runtime changes the answer — Python's GIL changes the async appender story, Node's single-threaded event loop changes the MDC story, Go's `context.Context` is an explicit first-class parameter rather than a thread-local.
4. **Connect.** Follow the Related Notes links to reinforce the cross-ecosystem graph. Observability connects upward to Section 13 (project notes that require a working `/metrics` and `/healthz` endpoint) and downward to Section 02 (the `clock_gettime` clock that every span's start timestamp depends on) and Section 03 (the HTTP headers that propagate trace context).

> [!tip] Reading order
> If you are new to this section, follow the numeric ordering. The three pillars — logs, metrics, traces — are taught in that order because each one builds on the previous: structured logs give you per-event context; metrics give you aggregated rates and distributions; traces give you the cross-service causal chain. CI/CD is taught last because it is the operational loop that lets you *act* on what telemetry tells you. If you are revising, jump directly to whichever concept you forgot.

## Conceptual Roadmap

The four sub-sections of Section 11 form a closed feedback loop that maps to the operating cycle of any production system:

```
        ┌─────────────────────────────────────────────────────────────┐
        │                   11.04. CI / CD                            │
        │   (the action: ship a fix based on what telemetry showed)   │
        └─────────────────────────────────────────────────────────────┘
          ▲                                                       │
          │ "what to fix"                                         │ "new code,
          │                                                       │  new signals"
          ▼                                                       ▼
        ┌──────────────────┐    ┌──────────────────┐    ┌─────────────────────┐
        │  11.01. Logs     │    │ 11.03. Metrics   │    │  11.02. Traces      │
        │  (event-level    │    │ (aggregated      │    │  (cross-service     │
        │   context: who,  │    │  rates over      │    │   causal chain:     │
        │   what, when,    │    │  time: how       │    │   which service,    │
        │   with what      │    │  much, how       │    │   which span, in    │
        │   trace_id)      │    │  fast)           │    │   what order)       │
        └──────────────────┘    └──────────────────┘    └─────────────────────┘
              ▲   ▲                    ▲                       ▲   ▲
              │   │                    │                       │   │
              │   └────── trace_id ─────┼───────────────────────┘   │
              │       propagated via     │                           │
              │       MDC / context      │   p99 latency            │
              │                          │   = a span's duration    │
              │                          │   at the 99th percentile │
              └──────── event counts ────┘                           │
                          become                                       │
                          counter increments                           │
                                                                       │
                                  one user request ────────────────────┘
                                  produces one trace,
                                  many spans, many logs,
                                  many metric increments.
```

The three pillars are not redundant — each answers a question the others cannot:

- **Logs** answer *"what happened, in detail?"* — but only for the events you logged, and only within a single process. Use them when you need the full text of an error, the values of variables at the point of failure, or the audit trail of a state change.
- **Metrics** answer *"how is the system doing, in aggregate?"* — but only along the dimensions you predefined, and only at scrape-interval granularity. Use them for alerting (error rate, p99 latency, saturation), for capacity planning (QPS growth, queue depth), and for SLI/SLO computation.
- **Traces** answer *"why is this request slow, and whose fault is it?"* — but only for sampled requests, and only at the granularity of span boundaries. Use them for cross-service attribution, for finding the long-tail outlier, and for reconstructing the causal chain of a specific incident.

The single most important architectural decision in this section is the **shared trace ID**. Every log line must carry the trace ID in a field (not embedded in the message text). Every span's attributes must include the host and service that emitted it. Every metric label set must be joinable on `service.name`. When these three things are true, the three pillars compose: a metric alert fires → you find the affected trace in Jaeger → you pivot to the logs for that trace ID in Loki. When they are not true, you have three siloed tools that each tell you a different story about the same incident, and you spend the incident reconciling them by hand.
