# 11.03.03. PromQL and Alerting Engineering

## What This Is

PromQL is the query language used to extract meaning from the time-series database that sits at the heart of a Prometheus server. Every dashboard panel in Grafana, every alert rule evaluated by `prometheus-tsdb`, every SLO burn-rate calculation, and every autoscaling decision made by a KEDA scaler ultimately compiles down to a PromQL expression. This note covers the four literal types PromQL operates on, the functions that turn raw counters into rates and raw histograms into quantiles, the way SLIs and SLOs are constructed and alerted on, and the Alertmanager routing layer that decides who gets paged at 03:00.

In the layered mental model, PromQL sits one layer above the metrics data model (see [[11.03.01. Metrics Data Model and Dimensionality]]) and one layer above the Prometheus pull architecture (see [[11.03.02. Prometheus Architecture and Pull Model]]). The data model defines what a `Sample{label=value}` actually is; the pull model defines how those samples got into the TSDB; PromQL defines how a human or an alerting engine asks the TSDB a question. The output of a PromQL query is what feeds Grafana, Alertmanager, the Kubernetes Horizontal Pod Autoscaler v2 (`/apis/external.metrics.k8s.io`), and Thanos query frontends. Get PromQL wrong and you get silent dashboards that lie, alerts that fire on stale data or never fire at all, and autoscalers that thrash.

## The Details

### PromQL Syntax: Instant vectors, range vectors, offset modifiers

PromQL has four literal types: **string**, **scalar**, **instant vector**, and **range vector**. A string is rare in practice — used mainly as arguments to functions like `label_replace()` — and looks like `"5xx"`. A scalar is a single floating-point number with no labels, written as `42` or `0.99`; scalars appear as the right-hand side of comparisons (`http_requests_total > 100`) and as function arguments (`histogram_quantile(0.99, ...)`). The two vector types are where PromQL earns its keep.

An **instant vector** is a set of time series, each identified by its full label set, all evaluated at a single timestamp `t`. When you write `http_requests_total`, PromQL returns one sample per matching series at the evaluation timestamp — so a service with 8 pods and 5 routes produces 40 series, each with its own `{pod, route, status, method}` labels. A **range vector** adds a time dimension: `http_requests_total[5m]` returns, for every matching series, every sample that fell in the half-open window `(t-5m, t]`. Range vectors cannot be graphed directly — they are inputs to functions like `rate()` that collapse the window back down to a scalar per series. This is the fundamental PromQL pipeline: instant vector → range vector via `[...]` → instant vector via `rate()`/`increase()`/`aggregation`.

Label matchers refine which series are selected. Four operators exist: `=` (exact), `!=` (negation), `=~` (regex), `!~` (negated regex). The regex matchers are anchored on both ends by default, so `status=~"5.."` matches `503` but not `1503`. A common mistake is writing `method=~"GET|POST"` and expecting substring matching — you actually get what you want here because `^GET$` and `^POST$` are the right anchors, but `path=~"/users/.*"` is the only way to match a prefix, not `path="/users/"`.

```text
# Selector               Meaning
http_requests_total                           # all series, instant vector at t
http_requests_total{job="api"}                # only job="api" series
http_requests_total{status=~"5.."}            # 500, 501, ... 599
http_requests_total{job="api",status!="200"}  # job=api AND status != 200
http_requests_total[5m]                       # range vector, last 5 min of samples
http_requests_total[5m] offset 1h             # same range, but 1 hour ago
http_requests_total @ 1700000000              # instant vector at a specific unix time
rate(http_requests_total[5m] offset 1h)       # "what was the rate 1h ago?"
rate(http_requests_total[5m:1m])              # subquery: evaluate rate every 1m for 5m
```

The `offset` modifier shifts the evaluation window back in time — invaluable for week-over-week comparisons (`rate(http_requests_total[5m] offset 7d) / rate(http_requests_total[5m])` shows growth ratio). The `@` modifier (Prometheus 2.25+) pins evaluation to an absolute Unix timestamp — useful for post-incident forensics. Subqueries (`[5m:1m]`) evaluate an inner expression at every `1m` step across a `5m` window, allowing `max_over_time(rate(http_requests_total[1m])[10m:1m])` to compute "max 1-minute rate seen in the last 10 minutes" — a fundamental primitive for burn-rate alerts.

The production failure mode here is **stale series matching**. If a pod restarts, its `instance` label changes from `pod-abc123` to `pod-def456`, and the old series stops getting new samples. For `rate()` this is fine because `rate()` requires at least two samples in the window. But for `count(http_requests_total)` (no `[5m]` window) the result still includes the stale series for 5 minutes (the default `--query.lookback-delta=5m`), inflating counts. Worse, an alert rule `http_requests_total == 0` (looking for "no traffic") will fire for the stale series because the last sample value is whatever it was when the pod died — not zero. Mitigation: always use `rate()` or `increase()` over a window for any alert involving counters, and explicitly filter with `unless on(instance) up{job="api"} == 1` to drop stale instances. This connects up to the alerting layer in [[11.03.03. PromQL and Alerting Engineering#Visualizing telemetry via Grafana Dashboards and dispatching alerts via Prometheus Alertmanager]] below.

### Core Functions: `rate()`, `irate()`, `increase()`, `histogram_quantile()`

`rate(v[5m])` is the workhorse function for counters. It computes the per-second average rate of increase over the window, accounting for counter resets (when a process restarts and the counter drops from 1,000,000 to 0). The algorithm: for each series, take all samples in `(t-5m, t]`, find successive pairs, compute `(v[i+1] - v[i]) / (t[i+1] - t[i])`, sum them, divide by the total time range. If `v[i+1] < v[i]` (counter reset), it assumes `v[i+1]` reset to 0 and adds `v[i]` instead of subtracting. The output is in **per-second** units regardless of how often Prometheus scrapes — `rate(http_requests_total[5m])` on a service handling 600 requests/minute returns `10.0`, not `600`.

`irate(v[5m])` is the **instantaneous** rate — it uses only the last two samples in the window. This makes it responsive but noisy: a single slow scrape or a counter that ticks once per minute will produce wild swings. Use `irate()` only for short, high-resolution graphs (1-2 minute panels); use `rate()` for everything else, including alerts. `increase(v[5m])` is `rate(v[5m]) * 5m` — the absolute count of events in the window. Useful for "how many 5xx in the last 5 minutes" without mental division.

```text
# Requests per second, smoothed over 5 min
rate(http_requests_total{job="api"}[5m])

# Requests per second, last 2 samples only (noisy but responsive)
irate(http_requests_total{job="api"}[5m])

# Total errors in the last 5 min
increase(http_requests_total{status=~"5.."}[5m])

# 99th percentile latency, averaged over 5 min, per route
histogram_quantile(0.99,
  sum by (le, route) (rate(http_request_duration_seconds_bucket[5m]))
)

# Top 5 routes by request rate
topk(5,
  sum by (route) (rate(http_requests_total[5m]))
)

# Median request rate (not average!) across all routes
quantile(0.5,
  sum by (route) (rate(http_requests_total[5m]))
)
```

`histogram_quantile(q, bucket_vector)` is the most misused function in PromQL. It computes quantile `q` from cumulative histogram buckets. The critical detail: the input must be a **cumulative** bucket vector with the `le` label (less-than-or-equal). The standard call is `histogram_quantile(0.99, sum by (le) (rate(http_request_duration_seconds_bucket[5m])))`. The `sum by (le)` is mandatory — without it, `histogram_quantile` operates per-series and you get quantile-of-quantiles, which is meaningless. The order of operations also matters: `sum(rate(...)) by (le)` first, then `histogram_quantile` on the aggregated result. Calling `histogram_quantile` on raw per-pod buckets and then `avg()`-ing the quantiles underestimates tail latency by 20-50% because averaging cannot reconstruct the long tail that was never observed in any single pod.

Aggregation operators — `sum`, `avg`, `min`, `max`, `count`, `stddev`, `stdvar`, `topk`, `bottomk`, `count_values`, `quantile` — reduce many series to fewer series along label dimensions. The `by` clause keeps listed labels in the output; `without` drops them. `sum(http_requests_total) by (job)` keeps `job` in the output; `sum(http_requests_total) without (pod, instance)` strips pod/instance but keeps everything else (job, route, status, method). The `without` form is preferred when you want to aggregate away per-instance details but preserve the cardinality you actually care about — adding a new label like `version` later will silently be included in `without(pod, instance)` aggregations but lost in `by (job)` aggregations.

Binary operators (`+ - * / % ^`, `== != > < >= <=`, `and or unless`) operate pairwise on instant vectors. They match series by full label set by default; use `ignoring(label_list)` or `on(label_list)` to relax the matching. `http_requests_total{status="500"} / ignoring(status) http_requests_total` computes the per-route error ratio by dividing the 500-series counter by the total counter, matching on everything except `status`. This is how SLI ratios are constructed — see the next H3.

The production failure mode is **histogram_quantile on the wrong shape of input**. If you call `histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m]))` (no `sum by (le)`), Prometheus happily returns one quantile per pod and your Grafana panel plots the per-pod p99s — which look fine because the max pod p99 is still under your SLO, but the global p99 (the one your users actually experience) is 3× worse because no single pod saw the slow tail. The fix is structural: every histogram_quantile call must be wrapped as `histogram_quantile(q, sum by (le) (rate(...)))` or `histogram_quantile(q, sum by (le, <dim>) (rate(...)))` if you want per-dimension quantiles. Audit every dashboard panel that uses `histogram_quantile` for this shape.

### Constructing Service Level Indicators (SLIs) and Service Level Objectives (SLOs)

An **SLI** is a measurement of the service level being provided. It is always a ratio: "good events / total events" or "bad events / total events". A well-formed SLI has three components: a **count of good events**, a **count of total events**, and a **time window**. For an HTTP API: `good = http_requests_total{status!~"5.."}`, `total = http_requests_total`, window = `5m` or `30d`. The SLI value is `sum(rate(good[5m])) / sum(rate(total[5m]))`. An **SLO** is a target for that ratio: "99.9% of requests succeed over 30 days" — that is, `SLI >= 0.999` over a 30-day window. The 0.1% of allowed failures is the **error budget**.

The error budget is the most useful operational concept in SLO engineering. A 99.9% SLO over 30 days gives you 43.2 minutes of allowed downtime (or 0.1% of 43200 minutes). Once you spend that budget, any further failures breach the SLO. This converts "is the service up?" from a binary question into a budgeting question: can I afford to deploy a risky change right now, or have I already spent this month's budget? Multi-window multi-burn-rate alerting (Google SRE Workbook) makes this operational: alert when the burn rate is high enough that you'll exhaust the budget before a human can react.

```yaml
# rules.yml — Prometheus alerting and recording rules
groups:
  - name: slo-http-api
    interval: 30s
    rules:
      # Recording rule: precompute the 5m error rate so dashboards/alerts are cheap
      - record: job:http_requests:error_rate5m
        expr: |
          sum(rate(http_requests_total{job="api",status=~"5.."}[5m]))
          /
          sum(rate(http_requests_total{job="api"}[5m]))

      # 30m window burn-rate alert — page
      - alert: HighErrorRate
        expr: |
          (
            job:http_requests:error_rate5m > 14.4 * 0.001
            and ignoring()
            job:http_requests:error_rate1h > 14.4 * 0.001
          )
        for: 2m
        labels:
          severity: page
          team: payments
        annotations:
          summary: "API burning error budget 14.4x fast (page)"
          runbook: "https://runbooks.example.com/api-high-error-rate"

      # 6h window burn-rate alert — ticket
      - alert: HighErrorRateBudget
        expr: |
          (
            job:http_requests:error_rate30m > 6 * 0.001
            and ignoring()
            job:http_requests:error_rate6h > 6 * 0.001
          )
        for: 15m
        labels:
          severity: ticket
          team: payments
        annotations:
          summary: "API burning error budget 6x slow (ticket)"

      # p99 latency SLO — 99% of requests under 300ms over 28d
      - record: job:http_request_duration:p99_5m
        expr: |
          histogram_quantile(0.99,
            sum by (le) (rate(http_request_duration_seconds_bucket{job="api"}[5m]))
          )
      - alert: HighLatencyP99
        expr: job:http_request_duration:p99_5m > 0.3
        for: 10m
        labels:
          severity: page
          team: payments
```

The 14.4× burn rate for the page alert is not arbitrary. A 99.9% SLO over 30 days allows 43.2 minutes of errors. Burning 14.4× means you exhaust the 30-day budget in `30d / 14.4 = 2 days` — fast enough to page, slow enough that a 5-minute blip doesn't wake someone up. The 6× burn rate for the ticket alert exhausts in 5 days — slow enough to wait for business hours. The two-window `and` (5m AND 1h, 30m AND 6h) suppresses flapping: a single slow scrape won't satisfy both windows. The `for: 2m` clause requires the condition to hold for two evaluation cycles, adding further debounce.

The `record:` rules are an optimization that matters at scale. A naive `rate(http_requests_total[5m])` alert re-evaluated every 30s for 200 services each with 1000 series is 200,000 series evaluations per minute — fine. But the same query joining with `histogram_quantile` over 28-day windows is expensive. Recording rules materialize the inner expression into a new time series (`job:http_requests:error_rate5m`) once per evaluation interval, and downstream alerts/dashboard queries read that pre-computed series. Without recording rules, a Grafana dashboard with 20 panels each computing `histogram_quantile(0.99, sum(rate(...)))` over a 7-day range will OOM-kill your Prometheus. Always record SLI primitives; alert off the recorded series.

The production failure mode is **SLO alerting on the wrong window**. A common mistake is `error_rate > 0.001 [30d]` — PromQL doesn't support range vectors on the output of a ratio like that. The right pattern is the burn-rate formula: short window AND long window, both compared to `target_error_rate × burn_rate`. The second failure mode is **alerting on absolute thresholds** ("error rate > 1%") which pages during a deploy when traffic is low — even 1 error out of 10 requests is 10%, but it's not a budget problem. Burn-rate alerts are dimensionless (relative to budget) and handle low-traffic correctly.

### Visualizing telemetry via Grafana Dashboards and dispatching alerts via Prometheus Alertmanager

Grafana is the visualization layer that sits in front of Prometheus. A dashboard is a JSON document describing panels, each panel is a PromQL query plus a visualization type (time series, stat, gauge, heatmap, table). Variables (`$environment`, `$service`, `$pod`) parameterize the dashboard — the variable query `$service` runs `label_values(http_requests_total, service)` against Prometheus to populate the dropdown, then `${service}` is substituted into every panel query. This is what makes a dashboard reusable across services: one dashboard, parameterized by `$service`, serves 50 teams.

The single most important Grafana feature for SRE work is the **recording-rule-backed panel**. A panel that runs `rate(http_requests_total{job="api",status=~"5.."}[5m])` over a 7-day range asks Prometheus to evaluate that expression ~2000 times (once per pixel). The same panel running `job:http_requests:error_rate5m` asks for one pre-aggregated series — 1000× cheaper. Recording rules are not just an optimization for alerts; they are a prerequisite for usable dashboards at scale.

```json
// Grafana panel: API error rate with SLO threshold
{
  "type": "timeseries",
  "title": "API Error Rate (5m)",
  "datasource": "Prometheus",
  "targets": [
    { "expr": "job:http_requests:error_rate5m", "legendFormat": "error rate" },
    { "expr": "0.001", "legendFormat": "SLO (0.1%)" }
  ],
  "thresholds": [
    { "value": 0.001, "colorMode": "warning" },
    { "value": 0.0144, "colorMode": "critical" }
  ],
  "fieldConfig": {
    "defaults": { "unit": "percentunit", "max": 0.05 }
  }
}
```

Alertmanager is the routing layer that receives alerts fired by Prometheus (via the `/api/v2/alerts` HTTP endpoint) and decides who to notify, via what channel, with what deduplication. The routing is a tree: each alert has labels, and Alertmanager walks the tree matching labels against `matchers` at each node. The root route catches everything; child routes narrow by `severity`, `team`, `service`. Each leaf route has a `receiver` (Slack, PagerDuty, email, webhook), a `group_by` (which labels group alerts into one notification), `group_wait` (how long to wait before sending the first notification of a group, to allow siblings to coalesce), `group_interval` (how long to wait before sending updates about an already-notified group), and `repeat_interval` (how long to wait before re-sending an unresolved alert).

```yaml
# alertmanager.yml — production routing tree
route:
  receiver: default-slack
  group_by: ['alertname', 'service', 'team']
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h
  routes:
    # Pages go to PagerDuty, grouped tighter
    - matchers: ['severity="page"']
      receiver: pagerduty-oncall
      group_wait: 0s
      group_interval: 1m
      repeat_interval: 1h
      routes:
        - matchers: ['team="payments"']
          receiver: pagerduty-payments
        - matchers: ['team="platform"']
          receiver: pagerduty-platform
    # Tickets go to Slack
    - matchers: ['severity="ticket"']
      receiver: slack-tickets
      group_wait: 5m
      repeat_interval: 24h
    # Devs get info in their team channel
    - matchers: ['severity="info"']
      receiver: slack-dev
      group_wait: 30m

inhibit_rules:
  # If a cluster is down, suppress per-node alerts for that cluster
  - source_matchers: ['alertname="ClusterDown"']
    target_matchers: ['alertname=~"NodeDown|PodCrashLooping"']
    equal: ['cluster']

receivers:
  - name: default-slack
    slack_configs:
      - api_url: 'https://hooks.slack.com/services/...'
        channel: '#alerts'
  - name: pagerduty-oncall
    pagerduty_configs:
      - service_key: '${PAGERDUTY_SERVICE_KEY}'
        severity: critical
  - name: pagerduty-payments
    pagerduty_configs:
      - service_key: '${PAGERDUTY_PAYMENTS_KEY}'
  - name: slack-tickets
    slack_configs:
      - api_url: 'https://hooks.slack.com/services/...'
        channel: '#payments-tickets'
```

Two Alertmanager features are essential for not getting paged at 03:00 for nothing. **Inhibition** suppresses downstream alerts when an upstream one fires: if `ClusterDown` is firing, do not also page for `NodeDown` for every node in that cluster — the operator already knows. **Silences** are temporary suppressions with an expiry, set via the UI or `amtool silence add` for planned maintenance. **Grouping** collapses alerts sharing the `group_by` labels into one notification — `group_by: ['alertname','service']` means "page me once for `HighErrorRate` on `payments`, not 40 times for each pod's error rate".

The production failure mode here is **alert storms from missing inhibition**. Without the inhibit rule above, a cluster network partition fires `ClusterDown` for the cluster, `NodeDown` for 20 nodes, `PodCrashLooping` for 200 pods, `HighLatency` for 50 services — 271 pages to the on-call, PagerDuty deduplication collapses maybe half, and the on-call gets 130 pages in 5 minutes. The fix is to design inhibition rules alongside alert rules: every "root cause" alert (cluster down, dependency down, deploy in progress) should inhibit the downstream symptoms. The second failure mode is **noisy alerts from `group_wait: 0s`** at the root — without a wait, every evaluation that satisfies the alert condition triggers an immediate notification, and a 30s scrape interval produces 120 notifications per hour for a flapping alert. The `for: 2m` clause in the Prometheus rule provides the first layer of debounce; `group_wait` provides the second.

## Key Takeaways

1. **PromQL is a typed functional language.** Instant vectors become range vectors via `[5m]`, range vectors become instant vectors via `rate()`/`increase()`/`histogram_quantile()`, and instant vectors are combined via binary operators with `on()`/`ignoring()` for label matching. Getting the type chain right is the difference between a query that returns data and one that returns an empty result with no error.
2. **`histogram_quantile(q, sum by (le) (rate(...)))` is the only correct shape.** Missing the `sum by (le)` aggregation gives per-pod quantiles that systematically understate global tail latency. Audit every dashboard panel and alert that uses `histogram_quantile` for this exact pattern.
3. **SLOs are budgeted, not thresholded.** Burn-rate alerts (`short_window AND long_window`, both compared to `target_rate × burn_factor`) are dimensionless and handle low-traffic correctly. Absolute-threshold alerts page during deploys when traffic is low and miss real budget exhaustion during steady-state high traffic.
