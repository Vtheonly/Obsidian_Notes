# 11.03.02. Prometheus Architecture and Pull Model

## What This Is

Prometheus is the dominant metrics system for cloud-native backend engineering, and the architectural decision that defines it is the **pull model**: Prometheus, the scraper, reaches out to your services over HTTP on a `/metrics` endpoint and reads the current values, rather than your services pushing data into a sink. This inverts the model used by StatsD, Datadog Agent, InfluxDB Telegraf, New Relic, and most older APM systems, and it has far-reaching consequences for service discovery, firewall rules, retention, and the operational patterns you build around it. This note covers the pull model itself (mechanics, scrape interval, the `/metrics` HTTP exposition format, the Pushgateway escape hatch for batch jobs), the local TSDB storage with its retention model, remote-write for long-term storage (Thanos, Cortex, Mimir), the recording rules that precompute heavy PromQL, the alerting rules that fire into Alertmanager, the service discovery mechanisms that find scrape targets (static, file, DNS, Kubernetes, Consul, EC2, relabeling), and the real Spring Boot `micrometer-registry-prometheus` setup that exposes `/actuator/prometheus`.

It builds on [[11.03.01. Metrics Data Model and Dimensionality]] (which defines the time-series model that Prometheus scrapes and stores) and feeds into [[11.03.03. PromQL and Alerting Engineering]] (which covers the query and alert expression layer that runs on top of the TSDB). The production failure mode of the pull model is the **scrape timeout cascade**: when a service's `/metrics` endpoint takes 30 seconds to render (because of a high-cardinality leak or an expensive Gauge callback), Prometheus marks the scrape as failed, the metric values go stale for that target, and any alert that depends on those metrics fires false-positive "service down" pages — at 3 a.m., on the on-call's first night.

## The Details

### Pull Model (Prometheus server scrapes HTTP `/metrics` endpoints) vs. Push Model (StatsD push daem...

The pull model says: Prometheus is the active party, your services are passive. Every `scrape_interval` (default 15 seconds — configurable per-job), Prometheus opens an HTTP GET to `<target>:<port>/metrics`, reads the text-format exposition, parses it into samples, and appends them to the TSDB. The target exposes a single endpoint that returns ALL its metrics in one response — there is no per-metric RPC, no streaming, no partial scrape. The exposition format is line-oriented text: `# HELP`, `# TYPE` metadata lines followed by `metric_name{label="value"} <float>` sample lines, terminated by `\n`. The `Content-Type` is `text/plain; version=0.0.4; charset=utf-8` — the `version=0.0.4` is the format version negotiation mechanism (a future Prometheus could ship 0.0.5 with new features, and old scrapers would still understand 0.0.4).

The reason Prometheus chose pull over push is operational leverage. With pull, **Prometheus knows what it can see** — the `up` metric is `0` if the scrape failed and `1` if it succeeded, which gives you a free liveness signal that works even when the application's own metrics are broken. With push, you never know if a target stopped sending because it crashed or because it's idle; you have to add a separate heartbeat metric, and now every push client must implement heartbeats correctly. Pull also makes Prometheus the rate-limiter: a Prometheus scraping 10,000 targets at 15 s intervals controls its own ingestion rate (666 scrapes/sec) and can back off without coordinating with clients. Push systems have to deal with thundering-herd ingestion when 10,000 services restart simultaneously after a deploy. The third reason is debuggability: a developer can `curl http://service:8080/metrics` and see exactly what Prometheus sees — there is no agent between them hiding or transforming the data.

```text
                  Pull model (Prometheus)              Push model (StatsD / Datadog)
                  ──────────────────────               ──────────────────────────────
   Direction      Prometheus → service (GET /metrics)  service → agent → sink
   Who knows      Prometheus (via up=0/1)              sink (if no data → ??)
    liveness?
   Rate control   Prometheus (scrape_interval)         each client (must self-limit)
   Failure mode   scrape timeout → up=0, alert fires   silent — no data, no signal
   Network        Prometheus must reach targets        targets must reach sink
   requirements   (egress from Prom, ingress to app)   (egress from app, ingress to sink)
   Firewall       permissive toward service network    permissive toward sink (often
                   (egress from Prometheus subnet)      internet for SaaS agents)
   Debug          curl service:8080/metrics             ssh to host, run `statsd -d`
```

The pull model's escape hatch is the **Pushgateway**, used for batch jobs and cron-style workers that don't live long enough to be scraped. A batch job runs for 5 seconds, exits, and never has an HTTP server for Prometheus to scrape — so it pushes its final metric values to the Pushgateway (`/metrics/jobs/<job>/instances/<instance>`), and Prometheus scrapes the Pushgateway instead. The Pushgateway is a stateful intermediary: it remembers the last pushed value per job/instance pair until explicitly deleted or overwritten. The rule is "use Pushgateway only for service-level batch jobs, never for long-running services" — because the Pushgateway loses Prometheus's `up=0` liveness signal (a crashed batch job that never pushes leaves stale metrics that look fresh), and because Pushgateway doesn't auto-expire metrics (a job that gets renamed leaves orphan series forever).

The Prometheus TSDB is the local storage layer — a custom on-disk format (introduced in 2.0, replacing the old LevelDB-backed v1 format) optimized for the append-heavy, mostly-immutable, time-ordered access pattern of metrics data. Samples are buffered in a 2-hour in-memory "head block", then flushed to disk as an immutable block of compressed chunks (each chunk holds ~120 samples in 1-2 bytes/sample via Gorilla XOR compression of float64 deltas). An index per block maps `(metric_name, labelset) → chunk file offsets`. The default retention is `--storage.tsdb.retention.time=15d` (or `--storage.tsdb.retention.size=the smaller of 15 days and the disk size` if you prefer). Production deployments typically run 15-30 day retention locally and rely on remote-write for long-term storage. The TSDB's worst-case behavior is the "head compaction stall" — every 2 hours the head block is cut and compacted, which is a CPU- and I/O-intensive operation that can cause scrape timeouts for 30-60 seconds; production Prometheis with high series counts often schedule compaction for off-peak hours via the `--storage.tsdb.min-block-duration`/`max-block-duration` flags.

**Remote write** is the bridge to long-term storage. Prometheus's `remote_write` feature (stable since 2.0) streams every ingested sample to a remote endpoint as a protobuf-over-Snappy HTTP POST. The receivers are: **Thanos** (CNCF, sidecar pattern — a Thanos Sidecar runs alongside Prometheus, uploads blocks to S3/GCS every 2 hours, and serves long-range queries via Thanos Query which federates across all Prometheus instances and the object store); **Cortex** (CNCF, multi-tenant horizontally-scalable Prometheus-compatible storage, originally built by Weaveworks); **Mimir** (Grafana Labs' fork of Cortex, shipped 2022, marketed as the successor). All three speak the same `remote_write` protocol and the same PromQL — the differences are in scale model (Thanos is "horizontal Prometheus federation", Cortex/Mimir are "BigTable/DynamoDB-backed microservices"). The production failure mode of remote write is the **WAL replay storm**: when Prometheus restarts, it replays its Write-Ahead Log (WAL) to recover in-flight samples; if remote_write was down for an hour, the queue is hours of samples deep, and Prometheus spends the first 30 minutes of uptime trying to drain it while new scrapes pile up. The metric to watch is `prometheus_remote_storage_highest_timestamp_in_seconds` lagging `prometheus_remote_storage_queue_highest_sent_timestamp_seconds` by more than ~5 minutes.

**Recording rules** precompute heavy PromQL expressions into new time-series that are stored in the TSDB and queried directly. The pattern is: a PromQL expression like `histogram_quantile(0.99, sum by (le)(rate(http_request_duration_seconds_bucket[5m])))` is expensive to evaluate at query time (it scans every bucket series across every instance for the last 5 minutes, every time the dashboard refreshes). A recording rule `record: job:http_request_duration_seconds:p99` with the same expression evaluates once per evaluation interval (default 15s in the `rule_eval` loop), stores the result as a new series named `job:http_request_duration_seconds:p99{job="checkout"}`, and dashboards query the cheap new series directly. The naming convention for recording rules is `<level>:<metric>:<operation>` (e.g., `job:http_request_duration_seconds:p99`, `instance:node_cpu:rate5m`) — the `:` separator is reserved for recording rules and prevents collisions with raw metric names.

**Alerting rules** are recording rules with an `alert:` name and a `for:` duration. The expression evaluates periodically; if it returns any series, the alert enters `pending` state; if it stays firing for the `for` duration (e.g., `for: 5m`), it transitions to `firing` and Prometheus POSTs the alert to Alertmanager at the next notification cycle. Alertmanager then routes by label (`route.match`), groups (`group_by: [alertname, service]`), inhibits (`inhibit_rules` — if `NodeDown` is firing, suppress `ServiceDown` for that node), and dispatches to PagerDuty/Slack/email/Opsgenie per the receiver config. The `for:` duration is critical for noise reduction: a 5-minute `for` window on a CPU spike alert filters out 30-second GC pauses; without it, you page the on-call 20 times an hour for transient spikes.

# prometheus.yml — real production config

The Spring Boot setup is the canonical example of "pull done right." Add `micrometer-registry-prometheus` as a dependency, enable the actuator endpoint, and you have a fully functional `/actuator/prometheus` endpoint exposing JVM, Tomcat, Hikari, Logback, and HTTP request metrics out of the box. The production failure mode of the pull model in Spring Boot is the **expensive Gauge callback**. Micrometer's `Gauge.builder(name, ref, valueFunction)` registers a callback that Prometheus invokes on every scrape (15s by default). If the callback is expensive (walking a 100k-entry map, running a database query, calling an external API), every scrape takes seconds instead of milliseconds, scrapes time out, and the metrics for that instance go stale. The fix is to cache the value with a short TTL (e.g., compute the gauge value every 30s into a regular field, have the Gauge callback just return the field) or to use a `TimeGauge` with explicit update semantics. The metric to watch on the Prometheus side is `scrape_duration_seconds{job="spring-boot"}` — if it exceeds `scrape_timeout` (10s by default), the scrape fails and `up=0`.

### Service Discovery mechanisms: Kubernetes API, Consul, DNS discovery

Static target configs (`static_configs: - targets: ["host1:9100", "host2:9100"]`) are how every Prometheus deployment starts and how every long-running bare-metal deployment stays. But static configs require manual updates whenever a target is added or removed — which in a Kubernetes world happens every few minutes during a rolling deploy. Service discovery (SD) is the answer: Prometheus queries an external system (the Kubernetes API, Consul's catalog, DNS SRV records, EC2's API, Azure's API, GCE's API, OpenStack's API, DigitalOcean's API, Hetzner's API) at regular intervals to discover the current set of scrape targets, then dynamically updates its scrape target list without restart. The list of supported SD mechanisms is one of Prometheus's biggest competitive advantages — no other monitoring system has this many native integrations.

The Kubernetes SD is the most-used and the most complex. It connects to the Kubernetes API server (using the pod's service account token, mounted at `/var/run/secrets/kubernetes.io/serviceaccount/`) and watches one of four roles: `pod` (every pod IP, filtered by annotation), `service` (every Service's ClusterIP, for blackbox-style probes), `node` (every Node's IP, for node-exporter), or `endpoints` (every Endpoint behind every Service — the right role for scraping service-level metrics because it auto-handles replicas). For each discovered object, Prometheus exposes `__meta_kubernetes_*` labels that you then filter on with `relabel_configs` — for example, "only scrape pods with the annotation `prometheus.io/scrape=true`" or "only scrape the metrics port specified in `prometheus.io/port`". The relabel_configs are where the real configuration logic lives; the SD just produces candidate targets, and relabeling decides which to keep and how to rewrite their address/path/labels.

```text
  Kubernetes API                  Prometheus
  ──────────────                  ──────────
  Watch /api/v1/pods     ───►    __meta_kubernetes_pod_ip="10.0.3.45"
                                 __meta_kubernetes_pod_name="checkout-7b9d..."
                                 __meta_kubernetes_pod_namespace="prod"
                                 __meta_kubernetes_pod_annotation_prometheus_io_scrape="true"
                                 __meta_kubernetes_pod_annotation_prometheus_io_port="8080"
                                 __meta_kubernetes_pod_annotation_prometheus_io_path="/actuator/prometheus"
                                 __meta_kubernetes_pod_label_app="checkout"
                                 __meta_kubernetes_pod_node_name="node-3"
                                            │
                                            ▼  relabel_configs:
                                            1. keep only pods with annotation scrape=true
                                            2. rewrite __metrics_path__ from annotation
                                            3. rewrite __address__ to pod_ip:port
                                            4. set job label to "spring-boot"
                                            5. set app label from pod label app
                                            ▼
                                            Final scrape target:
                                            http://10.0.3.45:8080/actuator/prometheus
                                            {job="spring-boot", app="checkout", namespace="prod"}
```

**Consul SD** queries Consul's HTTP catalog (`GET /v1/catalog/service/<name>`) at the configured interval and produces one target per registered service instance. This is the right choice for non-Kubernetes service mesh environments (HashiCorp stack, DC/OS, legacy bare-metal with Consul for service registry). **DNS SD** does SRV or A record lookups — `dns_sd_configs: - names: ["node-exporter.service.consul"]` queries SRV records and produces one target per record, with the SRV port used as the scrape port. This is the simplest SD and works in any environment with a service-discovery-capable DNS (Consul DNS, SkyDNS, CoreDNS with k8s plugin). **EC2 SD** queries the AWS EC2 API (`DescribeInstances`) and produces one target per running instance, with `__meta_ec2_instance_id`, `__meta_ec2_availability_zone`, `__meta_ec2_tag_<key>` labels available for relabeling. **file_sd** is the meta-SD: it reads a JSON/YAML file (typically written by an external process — Nomad, a custom service registry, a config management tool) and reloads it on file-change via SIGHUP. file_sd is the escape hatch when none of the native SDs fit — it lets you glue Prometheus to any service discovery system by writing a small adapter.

```yaml
# Consul SD example
scrape_configs:
  - job_name: "consul-services"
    consul_sd_configs:
      - server: "consul:8500"
        services: ["checkout", "inventory", "billing"]
    relabel_configs:
      - source_labels: [__meta_consul_service]
        target_label: service
      - source_labels: [__meta_consul_node]
        target_label: node
      - source_labels: [__meta_consul_tags]
        regex: ".*,prod,.*"
        action: keep

# DNS SRV SD example
scrape_configs:
  - job_name: "dns-discovered"
    dns_sd_configs:
      - names: ["_metrics._tcp.service.consul", "_metrics._tcp.prometheus.io"]
        type: SRV
        refresh_interval: 30s

# File-based SD example (the escape hatch)
scrape_configs:
  - job_name: "file-discovered"
    file_sd_configs:
      - files: ["/etc/prometheus/targets/*.yml"]
        refresh_interval: 30s
# /etc/prometheus/targets/app.yml:
# - targets: ["10.0.1.5:8080", "10.0.1.6:8080"]
#   labels: { env: prod, region: us-east-1 }
```

**Relabeling** is the configuration layer that sits between SD and scraping. There are two stages: `relabel_configs` runs after discovery but before scrape (it can drop targets, rewrite addresses, set labels); `metric_relabel_configs` runs after scrape but before ingestion (it can drop specific metrics, rename labels, scrub PII from label values). The relabel-config DSL is the same in both stages: a list of rules with `source_labels`, `regex`, `target_label`, `replacement`, and `action` (`keep`, `drop`, `replace`, `labelmap`, `labelkeep`, `labeldrop`). The `__address__` meta-label is the target's `host:port`; the `__metrics_path__` meta-label is the path to scrape (default `/metrics`); the `__scheme__` meta-label is `http` or `https`; the `__param_*` meta-labels become URL query params. These all start with double underscore and are stripped from the final sample unless explicitly preserved.

```yaml
# Common relabel patterns:

# 1. Only scrape pods with the prometheus.io/scrape=true annotation
relabel_configs:
  - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_scrape]
    regex: "true"
    action: keep

# 2. Use the annotation-specified port (instead of the default pod port)
  - source_labels: [__address__, __meta_kubernetes_pod_annotation_prometheus_io_port]
    regex: "([^:]+)(?::\\d+)?;(\\d+)"
    target_label: __address__
    replacement: "$1:$2"

# 3. Drop metrics with high cardinality at scrape time
metric_relabel_configs:
  - source_labels: [__name__]
    regex: "go_.*|process_.*"     # drop Go runtime / process metrics we don't need
    action: drop
  - source_labels: [request_id]   # never let request_id land in Prometheus
    regex: ".+"
    action: drop

# 4. Label-map all Kubernetes pod labels to Prometheus labels
relabel_configs:
  - action: labelmap
    regex: "__meta_kubernetes_pod_label_(.+)"

# 5. Drop targets in the dev namespace
  - source_labels: [__meta_kubernetes_namespace]
    regex: "dev|staging"
    action: drop
```

The production failure mode of service discovery is the **SD outage that silently empties the target list**. If the Kubernetes API server is unreachable (network partition, expired service account token, kube-apiserver OOM), Prometheus's Kubernetes SD returns zero targets, every existing target is dropped, and `up=0` fires on every alert. The Kubernetes API server being unreachable is itself the emergency — your cluster is broken — so the symptom (every Prometheus alert firing simultaneously) is actually correct, but the noise obscures the root cause. The mitigation is `relabel_configs` with `action: keep` on a stable label (so transient SD failures don't immediately drop targets) and the `--scrape-discovery-refresh-interval` flag (default 60s for most SDs — set longer to ride out brief API server hiccups). The other failure mode is **label cardinality from labelmap** — the `labelmap` action that promotes every Kubernetes label to a Prometheus label is convenient but dangerous: any team that adds `pod-template-hash: abc12345` (auto-managed by Deployments) or `pod-template-generation: 5` to their pods creates a new time-series for every metric on every rolling deploy. The fix is `labelkeep` with a regex allowlist (`labelkeep: "app|version|team|env"`), or selective labelmap with `regex: "__meta_kubernetes_pod_label_(app|version|team|env)"`.

## Cross-Ecosystem Code

The `/metrics` endpoint exposed by each ecosystem — same pull model, different plumbing:

**Spring Boot (Anchor — Actuator + Micrometer):**
```java
// pom.xml:
// spring-boot-starter-actuator + micrometer-registry-prometheus
// application.yml:
// management.endpoints.web.exposure.include: prometheus,health,metrics
// management.metrics.tags.application: ${spring.application.name}
// No Java code needed — /actuator/prometheus is auto-exposed.
// Custom metrics via Micrometer:
@RestController
class OrderController {
    private final Counter orders;
    private final Timer processTime;
    OrderController(MeterRegistry registry) {
        this.orders = Counter.builder("orders_created_total")
            .description("Total orders created")
            .register(registry);
        this.processTime = Timer.builder("orders_processing_duration")
            .publishPercentileHistogram().sla(Duration.ofMillis(500))
            .register(registry);
    }
    @PostMapping("/orders")
    Order create(@RequestBody Req r) {
        orders.increment();
        return processTime.recordCallable(() -> service.create(r));
    }
}
```

**Express (Delta — `prom-client` + `express-prom-bundle`):**
```typescript
import express from "express";
import { Registry, collectDefaultMetrics } from "prom-client";

const app = express();
const registry = new Registry();
collectDefaultMetrics({ register: registry, prefix: "node_" });

app.get("/metrics", async (_req, res) => {
  res.set("Content-Type", registry.contentType);
  res.end(await registry.metrics());
});
app.listen(8080);
// Prometheus scrapes http://service:8080/metrics every 15s.
```

**Flask (Delta — `prometheus_client`):**
```python
from flask import Flask, Response
from prometheus_client import Counter, generate_latest, CONTENT_TYPE_LATEST

app = Flask(__name__)
orders = Counter("orders_created_total", "Total orders created")

@app.post("/orders")
def create_order():
    orders.inc()
    return service.create(request.json)

@app.get("/metrics")
def metrics():
    return Response(generate_latest(), mimetype=CONTENT_TYPE_LATEST)
# mimetype MUST be exactly "text/plain; version=0.0.4; charset=utf-8"
# (CONTENT_TYPE_LATEST constant provides this) — version=0.0.4 is the

```

**Django (Delta — `django-prometheus`):**

The Spring Boot version is the most "magic" — Actuator + Micrometer give you `/actuator/prometheus` plus ~200 JVM/Tomcat/Hikari/Logback metrics with zero application code. The Express and Flask versions require you to write the `/metrics` endpoint handler and call `registry.metrics()` / `generate_latest()` yourself. The Django version splits onto a separate port (8001) to keep `/metrics` off the public internet without an ingress rule — a pattern worth adopting in any ecosystem. The runtime invariant exposed: Spring Boot's `/actuator/prometheus` is implemented as a regular Spring MVC endpoint and competes for the same request threads as business traffic — under heavy load a slow `/metrics` scrape can starve business requests unless you dedicate a separate executor (configurable via `management.endpoints.web.exposure` + a custom `TaskExecutor`).

## How This Connects to the Runtimes

The pull model is runtime-agnostic at the wire level — any process that can speak HTTP and emit `text/plain; version=0.0.4` can be a Prometheus target. What differs per runtime is the default exposition library and the auto-instrumentation surface. JVM has Micrometer + Actuator (the richest auto-instrumentation, covering JVM internals, GC, thread pools, Hikari, Tomcat, Logback, HTTP requests, cache hit rates). Node has `prom-client` + `express-prom-bundle` (covers Node.js event loop, GC, HTTP, but you wire it yourself). Python has `prometheus_client` + `django-prometheus`/`starlette-exporter` (covers process metrics + HTTP). Go has `client_golang/promhttp` (the canonical implementation — Prometheus itself is written in Go, so this is the reference). The runtime's concurrency model also affects scrape latency: JVM Gauges are often lazy callbacks invoked synchronously on the scrape thread (slow callbacks block the scrape); Node and Python Gauges are typically eagerly updated on the main thread (no scrape-time cost but slightly stale values).

## Cross-Runtime Comparison

| Runtime | Exposition library | Auto-instrumentation | Default port | `/metrics` content type |
|---|---|---|---|---|
| JVM (Spring) | `micrometer-registry-prometheus` via Actuator | ~200 metrics (JVM, GC, Hikari, Tomcat, Logback, HTTP) | 8080 (same as app) | `text/plain;version=0.0.4;charset=utf-8` |
| Node.js | `prom-client` + `express-prom-bundle` | ~30 metrics (event loop, GC, HTTP) | 8080 or 9100 | same |
| Python | `prometheus_client` + `django-prometheus`/`starlette-exporter` | ~20 metrics (process, HTTP) | 8000 or 8001 | same |
| Go | `client_golang/promhttp` | None by default — you wire `prometheus.MustRegister` | 8080 or `http.Handle("/metrics", ...)` | same |

# 1. Run Prometheus with a static config scraping a Spring Boot service:
docker run -d -p 9090:9090 -v $PWD/prometheus.yml:/etc/prometheus/prometheus.yml \
    prom/prometheus:v2.51.0 --config.file=/etc/prometheus/prometheus.yml

# 2. Verify Prometheus can reach the target (Status → Targets):
open http://localhost:9090/targets    # up=1 means scrape succeeded

# 3. Simulate a scrape timeout: add an artificial 20s delay to /actuator/prometheus
#    in your Spring Boot service, set scrape_timeout: 5s, watch the target go down.
curl 'http://localhost:9090/api/v1/query?query=up'

# 4. Inspect the TSDB:
curl 'http://localhost:9090/api/v1/status/tsdb' | jq '.data.seriesCountByMetricName | top(10)'

promtool check rules rules/alerting.yml
promtool check config prometheus.yml
