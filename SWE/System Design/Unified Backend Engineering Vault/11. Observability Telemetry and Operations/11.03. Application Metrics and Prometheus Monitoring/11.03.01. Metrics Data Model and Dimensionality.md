# 11.03.01. Metrics Data Model and Dimensionality

## What This Is

A metric is a numeric measurement of some aspect of your system, sampled at a point in time, identified by a name and a set of labels, and stored as a time-series so you can ask "how is this changing?" The model is deceptively simple — `(name, labels) → [(timestamp, value), ...]` — but every production observability disaster in the metrics space (cardinality explosions, OOM-killed Prometheis, dashboards that won't load, alerts that never fire) traces back to misunderstanding one corner of that model. This note covers the time-series data model that Prometheus uses, the four fundamental metric types it exposes (Counter, Gauge, Histogram, Summary), the label as a dimension rather than a tag, the cardinality explosion that follows from misusing labels, and the Prometheus naming convention that makes queries across teams possible.

It builds on the conceptual foundation in [[11.02.01. Distributed Tracing Foundations]] (a metric answers "how many / how fast / how big" while a trace answers "why is this slow") and feeds directly into [[11.03.02. Prometheus Architecture and Pull Model]] (which covers how the time-series defined here actually get scraped and stored) and [[11.03.03. PromQL and Alerting Engineering]] (which covers how to query them). The production failure mode of the metrics data model is the **cardinality explosion**: a single label with high cardinality (user_id, request_id, session_id, error_message) multiplies against every other label, and the Prometheus TSDB allocates one series per (name, labelset) tuple — a million series at 1 KB of overhead each is 1 GB of RAM just for the index, the scrape takes 30 seconds instead of 200 ms, the Prometheus OOMs, and every alert in the org goes silent.

## The Details

### Time-Series Metrics: Metric Name, Labels (Key-Value dimensions), Timestamp, Floating-Point Value

The Prometheus data model is the simplest possible thing that can answer "what is the value of X for slice Y at time T" — and the simplicity is the source of both its power and its hazards. A single time-series is identified by the **tuple** `(metric_name, labelset)` where `metric_name` is a string like `http_requests_total` and `labelset` is a sorted set of `key="value"` pairs like `{method="POST", path="/checkout", status="200"}`. The series itself is a sequence of **samples**: `(timestamp_ms, float64_value)` pairs. There is no "event" abstraction in Prometheus — if you want event-level data, you want logs or traces; metrics are an aggregation layer that drops individual identity in exchange for cheap long-term storage and fast queries.

The model's three rules are: (1) every unique `(name, labelset)` tuple is a distinct series, allocated once at first-seen and held in memory for the retention window; (2) labels are dimensions — adding `status="200"` and `status="500"` to the same metric creates two series, and you can slice by status in PromQL with `http_requests_total{status="500"}`; (3) the value is always a `float64`, never a string, never a struct — if you need to record a string, you need a label (with cardinality cost) or a log. The Prometheus exposition format makes this concrete on the wire:

```text
# HELP http_requests_total Total HTTP requests received
# TYPE http_requests_total counter
http_requests_total{method="POST",path="/checkout",status="200"}  14891
http_requests_total{method="POST",path="/checkout",status="500"}  3
http_requests_total{method="POST",path="/users",   status="200"}  92301
http_requests_total{method="POST",path="/users",   status="201"}  1240
```

The naming convention matters more than it looks. Prometheus documents the convention as `<namespace>_<subsystem>_<name>_<unit>[_total|_count|_sum|_bucket]` — `http_requests_total` (namespace=http, subsystem=requests, type=counter suffix _total), `node_memory_MemAvailable_bytes` (namespace=node, subsystem=memory, name=MemAvailable, unit=bytes), `http_request_duration_seconds_bucket` (the bucket series of a histogram named `http_request_duration_seconds`). The `_total` suffix is mandatory for counters in the OpenMetrics standard and is appended automatically by most client libraries. The unit suffix (`_seconds`, `_bytes`, `_ratio`) makes unit-aware alerting possible — the rule "alert when p99 latency > 200 ms" becomes `histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m])) > 0.2` (0.2 because the unit is seconds). Teams that skip the convention end up with dashboards mixing seconds and milliseconds because nobody remembers whether `latency` is in ms or s.

The cardinality explosion is the direct mathematical consequence of rule (1). If you have a metric with labels `{method, path, status, user_id}` where `method` has 4 values, `path` has 100, `status` has 5, and `user_id` has 100,000 active users, the metric defines up to 4 × 100 × 5 × 100,000 = 200 million series. At ~1 KB per series for the labelset storage and chunk metadata, that's 200 GB of RAM just for one metric — and Prometheus will OOM long before that. The rule of thumb is: **labels must have ≤10 distinct values, and the cross-product of all label cardinalities on a single metric must be ≤10,000 series**. `user_id`, `session_id`, `request_id`, `trace_id`, `email`, `error_message`, and raw SQL queries are forbidden as labels — those belong in logs (where you can filter post-hoc) or traces (where each value is its own event), not in metrics (where each value is its own RAM-resident series).

```text
                  Safe label cardinality       Unsafe label cardinality
                  ───────────────────────       ────────────────────────
method            4 (GET/POST/PUT/DELETE)       4
path              100 (templated routes)        100
status            5 (2xx/3xx/4xx/5xx + "0")     5
user_id           ─                             100,000
                  ────────                      ─────────────
                  2,000 series ✓                200,000,000 series ✗ OOM

  Fix: drop user_id from the metric. Put it in a log line:
       logger.info("checkout_complete", user_id=req.user_id, latency_ms=42)
       Then aggregate by user in Loki/ELK if you need per-user analytics.
```

The production failure mode here is slow and silent: a developer adds `path={request.path}` (raw URL with query params) instead of `path={route.template}` (templated), and within 24 hours Prometheus has 2 million series and is OOM-restarting every few hours. The metric to watch is `prometheus_tsdb_head_series` — if it grows monotonically past your team's threshold (typically 1M series per Prometheus instance), you have a cardinality leak. The fix is in the application: relabel at scrape time (`metric_relabel_configs` in `prometheus.yml`) to drop high-cardinality labels, or fix the instrumentation to use templated routes. The cardinality explosion is the single most common cause of production Prometheus outages and the reason every team should run `promtool tsdb analyze` on their data directory quarterly.

### The Four Fundamental Metric Types

Prometheus defines exactly four metric types, and the choice of type determines what you can do with the data in PromQL. The four types exist because the time-series model alone (name + labels + float) is too weak to express common questions — "what's the rate of change?" needs a Counter, "what's the current value?" needs a Gauge, "what's the p99?" needs a Histogram or Summary. Each type maps to a specific wire format on the `/metrics` endpoint, and the PromQL functions that operate on each type are different.

```text
┌──────────────┬──────────────────────────┬─────────────────────────────────────┬───────────────────────────┐
│ Type         │ Wire format              │ Use case                            │ PromQL                    │
├──────────────┼──────────────────────────┼─────────────────────────────────────┼───────────────────────────┤
│ Counter      │ _total suffix            │ cumulative count since process boot │ rate(), increase()        │
│ Gauge        │ single value             │ current snapshot value              │ direct, delta(), deriv()  │
│ Histogram    │ _bucket{le="..."} +      │ bucketed observations for quantiles │ histogram_quantile(       │
│              │ _count, _sum             │                                     │   0.99, rate(_bucket[]))  │
│ Summary      │ {quantile="0.99"} +      │ client-side quantiles               │ direct (no aggregation    │
│              │ _count, _sum             │                                     │   across instances)       │
└──────────────┴──────────────────────────┴─────────────────────────────────────┴───────────────────────────┘
```

The decision tree for picking a type is: if the value only goes up (and resets to zero on process restart), use a **Counter** — this is the right type for request counts, error counts, bytes sent, rows inserted, messages consumed. If the value can go up and down arbitrarily, use a **Gauge** — current queue depth, active connections, JVM heap used, CPU%, in-flight requests, replica count. If you want to compute quantiles (p50, p95, p99) of a distribution (request latency, response size, queue wait time), use a **Histogram** unless you specifically cannot afford server-side aggregation, in which case use a **Summary** and accept that you cannot aggregate across instances.

The reason Histogram is the default recommendation over Summary is that Summaries compute quantiles client-side and only expose the pre-computed quantile values — `http_request_duration_seconds{quantile="0.99"} 0.42` is one series per quantile, and there is no way to compute the p99 across 10 instances from 10 such series (because the underlying distribution is gone). Histograms expose bucket counts — `http_request_duration_seconds_bucket{le="0.5"} 14891` is the count of observations that fell in the `[0, 0.5]` bucket — and PromQL's `histogram_quantile()` interpolates across the buckets at query time, which means you can sum buckets across instances with `sum by (le)(rate(...))` and then call `histogram_quantile()` on the result. The tradeoff is bucket cardinality: a Histogram with 10 buckets produces 12 series (10 `_bucket` + 1 `_count` + 1 `_sum`) per labelset, vs a Summary's 4 (3 quantile series + `_count` + `_sum`). See the Histogram and Summary H3s below for the deep dive on each.

| Question | Metric type | Example PromQL |
|---|---|---|
| How many requests per second is this service handling? | Counter | `rate(http_requests_total[5m])` |
| What's the current queue depth? | Gauge | `kafka_consumer_lag` (direct) |
| What's the p99 latency over the last 5 minutes? | Histogram | `histogram_quantile(0.99, sum by (le)(rate(http_request_duration_seconds_bucket[5m])))` |
| What's the per-instance p99 latency (no aggregation)? | Summary | `http_request_duration_seconds{quantile="0.99"}` |
| What's the average request size? | Histogram (via _sum/_count) | `rate(http_request_size_bytes_sum[5m]) / rate(http_request_size_bytes_count[5m])` |
| How many errors in the last hour? | Counter | `increase(http_requests_total{status=~"5.."}[1h])` |

### **Counter**: Monotonically increasing cumulative value (e.g., total requests received)

A Counter is a number that only goes up — every observation adds a non-negative delta, and the counter resets to zero only when the process restarts. The wire format is the bare metric name with a `_total` suffix (mandated by OpenMetrics, automatic in modern client libraries), and the value is the cumulative total since process start. Counters are the right metric for anything cumulative: requests received, bytes sent, errors emitted, rows inserted, messages consumed, retries attempted. They are wrong for anything that can decrease (queue depth, active connections, in-flight requests) — use a Gauge for those.

The defining PromQL function for Counters is `rate()`. `rate(http_requests_total[5m])` returns the per-second rate of increase, computed by linear regression over the samples in the 5-minute window. The reason `rate()` exists (rather than just `value / time`) is the **counter reset**: when the process restarts, the counter jumps from 14891 back to 0, and a naive `value2 - value1` would produce `-14891`. `rate()` detects this — if `value2 < value1`, it assumes a reset happened and treats the reset as `(2^64 - value1) + value2` to recover the "true" delta. The related function `increase(http_requests_total[1h])` returns the total increase over the window (i.e., `rate() * window_seconds`), which is what you want for "how many 5xx errors in the last hour?".

```text
   Counter value
       ▲
 15000 │                                          ┌── (process restarted,
       │                                       ╱ │     counter reset to 0)
 10000 │                                  ┌──╱   │
       │                             ┌──╱       │       ┌──
  5000 │                        ┌──╱            │   ┌──╱
       │                   ┌──╱                 └──╘
     0 └───────────────────╲────────────────────────╲──────► time
       │              ╲                       ╱
       │               ╲                    ╱
                          ← rate() sees this delta
                            and recovers from the reset
```

The production failure mode of Counters is **using `value` directly in alerts** instead of `rate()` or `increase()`. An alert like `http_requests_total{status=~"5.."} > 100` will fire forever once the counter crosses 100, because the counter never decreases — you must write `increase(http_requests_total{status=~"5.."}[5m]) > 100` ("more than 100 errors in any 5-minute window"). The other failure mode is **labeling a Counter with the value as a label** — `http_requests_total{value="100"}` instead of incrementing a single counter — which creates a new series for every distinct value and triggers the cardinality explosion. The fix is one series per logical counter, value in the metric, not in a label.

```java
// Spring Boot / Micrometer — Counter usage
@Bean
Counter checkoutCounter(MeterRegistry registry) {
    return Counter.builder("checkout.requests")
        .description("Total checkout requests received")
        .tag("endpoint", "/checkout")
        .register(registry);
}
// In handler:
checkoutCounter.increment();                              // +1
checkoutCounter.increment(2.5);                           // +2.5 (rare; usually integer)
// Micrometer adds the _total suffix automatically on Prometheus.
// Exposed on /actuator/prometheus as:
//   checkout_requests_total{endpoint="/checkout"} 14891
```

### **Gauge**: Instantaneous fluctuating value (e.g., memory usage, active connection count)

A Gauge is a number that can go up or down at any time, sampled at the current moment. There is no `rate()` semantic — `gauge_value` is the value at the most recent scrape, full stop. Gauges are the right metric for anything that is a snapshot: current queue depth, active connections, in-flight requests, JVM heap used, CPU%, replica count, room temperature, bitcoin price. They are wrong for cumulative counts — use a Counter for those, because `rate()` on a Gauge is meaningless.

The Gauge's API is `set(value)`, `inc()`, `dec()`, `inc(delta)`, `dec(delta)`. Most client libraries also expose `gauge.trackSize(collection)` or `gauge.setTime(supplier)` convenience methods that poll the value on scrape rather than requiring you to push updates. The PromQL operations on Gauges are direct (`queue_depth` is the current value), `delta(gauge[5m])` (change over the window — positive or negative), `deriv(gauge[5m])` (per-second rate of change), `predict_linear(gauge[1h], 3600)` (linear extrapolation — useful for "will this disk fill in the next hour?" alerts), and `avg_over_time(gauge[1h])` / `max_over_time` / `quantile_over_time` (rolling-window aggregates of the gauge samples themselves).

```text
   Gauge value
       ▲
   500 │       ╱╲       ╱──╲     ╱──
       │      ╱  ╲     ╱    ╲   ╱
   250 │  ───╱    ╲───╱      ╲─╱
       │
     0 └──────────────────────────────► time
       Each scrape samples the current value;
       no rate(), no reset semantics.
       PromQL: queue_depth, max_over_time(queue_depth[1h]),
               predict_linear(queue_depth[1h], 3600)
```

The production failure mode of Gauges is **treating them like Counters in alerts** — `rate(queue_depth[5m])` is syntactically valid but semantically meaningless (it returns the per-second rate of change of an instantaneous value, which is dominated by noise). The correct alert for "queue is growing without bound" is `predict_linear(queue_depth[30m], 1800) > 10000` ("at the current rate, queue depth will exceed 10,000 within 30 minutes"). The other failure mode is **using a Gauge for a cumulative count** — `total_requests` as a Gauge loses the ability to compute rate of change accurately across process restarts (because the reset to 0 looks like a real decrease). If the value can only increase, use a Counter; if it can decrease, use a Gauge; the type encodes the semantics.

```java
// Spring Boot / Micrometer — Gauge usage
@Bean
Gauge activeConnections(DataSource ds, MeterRegistry registry) {
    return Gauge.builder("db.connections.active", ds, d -> {
        HikariPoolMXBean pool = ((HikariDataSource) d).getHikariPoolMXBean();
        return pool.getActiveConnections();
    }).register(registry);
}
// The lambda is invoked on every scrape — no manual push needed.
// Exposed on /actuator/prometheus as:
//   db_connections_active 7
```

### **Histogram**: Samples observations into configurable buckets and provides cumulative counts and sum

A Histogram buckets observations into a configurable set of upper bounds (`le` for "less than or equal") and exposes one `_bucket` series per bound, plus `_count` (total observations) and `_sum` (sum of all observations). The buckets are **cumulative** — `http_request_duration_seconds_bucket{le="0.5"} 14891` means 14,891 observations had a value ≤ 0.5 seconds, including all the ones that were also ≤ 0.1 seconds. The `+Inf` bucket (`le="+Inf"`) is always equal to `_count`. The bucket boundaries are configurable per-metric, and the right choice is critical: too few buckets loses resolution (you can't tell p99 from p95), too many buckets inflates series count (each bucket is a separate time-series).

The default buckets in most Prometheus client libraries are `[0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5, 10, +Inf]` (seconds) — these are tuned for HTTP request latency in the 10 ms–10 s range. For a sub-millisecond gRPC service, you'd use `[0.0001, 0.0005, 0.001, 0.005, 0.01, 0.05, 0.1, +Inf]`. For a batch job that takes minutes, you'd use `[10, 30, 60, 120, 300, 600, 1800, +Inf]`. The buckets are linear in log-space by convention because latency distributions are typically log-normal. Custom buckets are set in the client library: `Histogram.buckets(0.005, 0.01, 0.025, ...)` in Java Micrometer, `Histogram(buckets=(0.005, 0.01, ...))` in Python prometheus_client.

```text
  http_request_duration_seconds_bucket (cumulative)
       ▲
  1500 │                                          ┌── +Inf = _count
       │                                     ┌──╱
  1489 │                                ┌──╱      (le="1.0")
       │                           ┌──╱
  1456 │                      ┌──╱                  (le="0.5")
       │                 ┌──╱
  1234 │            ┌──╱                         (le="0.1")
       │       ┌──╱
   500 │  ───╱                              (le="0.05")
       │
     0 └─────────────────────────────────────────► le
       0    0.05   0.1    0.5    1.0   +Inf

  histogram_quantile(0.99, ...) interpolates within the bucket
  that contains the 99th percentile observation.
  If 99th percentile falls in [0.5, 1.0], it computes:
    0.5 + (rank_within_bucket / bucket_count) * (1.0 - 0.5)
```

The killer feature of Histograms is **server-side aggregation across instances** via `sum by (le)(rate(...))`. If you have 10 instances each exposing `http_request_duration_seconds_bucket`, the PromQL `histogram_quantile(0.99, sum by (le)(rate(http_request_duration_seconds_bucket[5m])))` sums the bucket counts across all 10 instances (because they share the same `le` boundaries) and then computes the p99 of the combined distribution. This is impossible with Summaries — see the next H3. The tradeoff is bucket precision: a Histogram's p99 estimate is approximate, bounded by the bucket containing the 99th percentile (you can interpolate linearly within the bucket, but you cannot know the true distribution within the bucket). For 0.1% accuracy in p99, you need buckets fine enough that the bucket containing the 99th percentile is narrow.

The production failure mode of Histograms is **wrong bucket boundaries for the workload**. If your service has a 50 ms p99 but you use the default buckets where the lowest non-zero bucket is 100 ms, every observation lands in the same bucket and `histogram_quantile(0.99, ...)` returns 100 ms regardless of whether the true p99 is 5 ms or 95 ms. The fix is to look at your actual latency distribution first (use a tracing system or log the raw values) and then choose buckets that put the SLO boundary inside a narrow bucket — if your SLO is "p99 < 200 ms", you want buckets at 100, 150, 200, 250, 300, 500, 1000 ms so that crossing the SLO is visible as a step change in the 200 ms bucket. The other failure mode is **too many buckets** — each bucket is a separate time-series, so a Histogram with 50 buckets and 100 labelsets produces 5,100 series per metric, which adds up. Stick to 10–15 buckets.

```java
// Spring Boot / Micrometer — Histogram with custom buckets
@Bean
Timer requestTimer(MeterRegistry registry) {
    return Timer.builder("http.request.duration")
        .description("HTTP request duration")
        .publishPercentileHistogram()         // use Micrometer's sla-buckets
        .sla(Duration.ofMillis(50), Duration.ofMillis(100),
             Duration.ofMillis(200), Duration.ofMillis(500),
             Duration.ofSeconds(1), Duration.ofSeconds(5))
        .minimumExpectedValue(Duration.ofMillis(1))
        .maximumExpectedValue(Duration.ofSeconds(10))
        .register(registry);
}
// In handler:
requestTimer.record(() -> service.process(req));
// Exposed on /actuator/prometheus as:
//   http_request_duration_seconds_bucket{le="0.05"} 1234
//   http_request_duration_seconds_bucket{le="0.1"}  1456
//   http_request_duration_seconds_bucket{le="0.2"}  1489
//   ...
//   http_request_duration_seconds_bucket{le="+Inf"} 1500
//   http_request_duration_seconds_count 1500
//   http_request_duration_seconds_sum 123.45
```

### **Summary**: Client-side sliding-window quantile calculations (p50, p95, p99)

A Summary computes quantiles client-side using a streaming algorithm (typically Dunning's t-Digest or Cormode's GK algorithm) and exposes one series per configured quantile. The wire format is `http_request_duration_seconds{quantile="0.99"} 0.42` — there is no `_bucket` series, no `_le` label. The client library maintains a sliding window of recent observations (default 10 minutes in Prometheus's Go client, configurable) and recomputes the quantiles on each scrape from that window. The benefit is precision: the p99 value reported is the actual 99th percentile of the observed distribution within the window, not an interpolation across buckets. The cost is the streaming algorithm's memory (proportional to the number of quantiles × the inverse of the error bound) and the inability to aggregate across instances.

The reason cross-instance aggregation is impossible is that the Summary's quantile series exposes only the final computed value, not the underlying distribution. If instance A has p99 = 0.42s (computed from 1000 observations, 990 of which were under 0.42) and instance B has p99 = 0.51s (computed from 100 observations, 99 of which were under 0.51), there is no mathematical way to compute "the p99 of A+B combined" from those two numbers — the underlying 1,100 observations are gone. The best you can do is `avg(http_request_duration_seconds{quantile="0.99"})` which computes the average of the per-instance p99s — a meaningless statistic for most distributions.

```text
                   Summary (client-side)              Histogram (server-side)
                   ─────────────────────              ──────────────────────
  Series exposed   {quantile="0.99"}                  _bucket{le="..."}
                   {quantile="0.95"}                  _count, _sum
                   {quantile="0.50"}
                   _count, _sum                       (12 series per labelset
                                                       for 10 buckets)
  p99 computation  Client library (t-Digest)          Server-side
                                                       histogram_quantile()
  Cross-instance   ✗ IMPOSSIBLE                       ✓ sum by (le)(rate(...))
  aggregation                                         then histogram_quantile()
  Memory cost      ~50 obs × N quantiles              12 series per labelset
                   per client                         (cheap on client, more on server)
  Precision        Exact within window                Approximate (interpolated
                                                       within bucket)
  When to use      Single-instance, low-cardinality   Default choice — always
                   legacy systems                     prefer this unless you have
                                                       a specific reason not to
```

The modern recommendation is **never use Summary for new code**. The Prometheus team's official position (in the exposure format docs and in the OTel metrics spec) is that Histograms are the right default for two reasons: (1) cross-instance aggregation is the most common query pattern in any multi-replica service, and Summaries can't do it; (2) the OTel native Histogram format (introduced 2023, supported in Prometheus 3.x) reduces the series count from "12 per labelset" to "1 per labelset" by using exponential buckets encoded in a single series, eliminating the only argument Summary ever had. The remaining legitimate use case for Summary is when you need exact quantiles of a single-instance metric and cannot afford the bucket series cost — but this is rare enough that the rule "use Histogram" is right 99% of the time.

The production failure mode of Summaries is **the team that picks Summary, then scales to 10 replicas, then can't build a dashboard that shows aggregate p99** — they end up with 10 separate p99 lines on the chart and have to explain to the SRE team why "average of per-instance p99s" is not a real p99. The other failure mode is the **10-minute window mismatch**: the Summary's sliding window is client-side (default 10 min in Go client, 5 min in some Python configs), so `http_request_duration_seconds{quantile="0.99"}` at scrape T reflects the distribution over the past 10 minutes, not "right now" — if latency has just spiked, the Summary takes 10 minutes to fully reflect it. Histograms don't have this problem because their bucket counts are cumulative and the `rate(...[5m])` window is chosen at query time.

```python
# Python prometheus_client — Summary (legacy, prefer Histogram)
from prometheus_client import Summary

request_duration = Summary(
    "http_request_duration_seconds",
    "HTTP request duration",
    ["method", "path"],
)
# Use:
with request_duration.labels("POST", "/checkout").time():
    handle(request)
# Exposes:
#   http_request_duration_seconds{method="POST",path="/checkout",quantile="0.5"} 0.05
#   http_request_duration_seconds{method="POST",path="/checkout",quantile="0.9"} 0.12
#   http_request_duration_seconds{method="POST",path="/checkout",quantile="0.99"} 0.42
#   http_request_duration_seconds_count{method="POST",path="/checkout"} 14891
#   http_request_duration_seconds_sum{method="POST",path="/checkout"} 123.45

# Modern equivalent — Histogram (preferred):
from prometheus_client import Histogram
request_duration_h = Histogram(
    "http_request_duration_seconds",
    "HTTP request duration",
    ["method", "path"],
    buckets=(0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5, 10),
)
with request_duration_h.labels("POST", "/checkout").time():
    handle(request)
```

## Cross-Ecosystem Code

Side-by-side: recording a Counter, a Gauge, and a Histogram in each of the four ecosystems.

**Spring Boot (Anchor — Micrometer):**
```java
import io.micrometer.core.instrument.*;

@RestController
class TelemetryController {
    private final Counter requests;
    private final Gauge activeConn;
    private final Timer latency;

    TelemetryController(MeterRegistry registry, DataSource ds) {
        this.requests = Counter.builder("http.requests")
            .tag("endpoint", "/checkout").register(registry);
        this.activeConn = Gauge.builder("db.connections.active",
            ds, d -> ((HikariDataSource) d).getHikariPoolMXBean().getActiveConnections())
            .register(registry);
        this.latency = Timer.builder("http.request.duration")
            .publishPercentileHistogram()
            .sla(Duration.ofMillis(200)).register(registry);
    }

    @PostMapping("/checkout")
    Response checkout(@RequestBody Req r) {
        requests.increment();
        return latency.recordCallable(() -> service.handle(r));
    }
}
```

**Express (Delta — `prom-client`):**
```typescript
import { Counter, Gauge, Histogram, register } from "prom-client";

const requests = new Counter({
  name: "http_requests_total",
  help: "Total HTTP requests",
  labelNames: ["endpoint"],
});
const activeConn = new Gauge({
  name: "db_connections_active",
  help: "Active DB connections",
  collect() { this.set(pool.activeCount); },
});
const latency = new Histogram({
  name: "http_request_duration_seconds",
  help: "HTTP request duration",
  labelNames: ["endpoint"],
  buckets: [0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5, 10],
});

app.post("/checkout", async (req, res) => {
  const end = latency.labels("/checkout").startTimer();
  requests.labels("/checkout").inc();
  try { res.json(await service.handle(req.body)); }
  finally { end(); }
});
app.get("/metrics", async (_req, res) => res.end(await register.metrics()));
```

The Spring Boot version uses **Micrometer** as the abstraction layer — Micrometer is a vendor-neutral metrics facade (analogous to SLF4J for logging) that exposes a `MeterRegistry` interface with implementations for Prometheus, Atlas, Datadog, NewRelic, Graphite, and others. Switching backends is a one-line config change (`management.metrics.export.prometheus.enabled=true`). The Express and Flask versions use `prom-client` and `prometheus_client` directly — they are Prometheus-specific (though both can be wrapped in OTel Metrics API for vendor-neutrality). The Django version uses `django-prometheus` middleware which auto-instruments request count + latency + size and exposes `/metrics` — the closest equivalent to Spring Boot Actuator's `/actuator/prometheus` endpoint.

## How This Connects to the Runtimes

The metrics data model is runtime-agnostic — every runtime (JVM, V8, CPython, Go runtime, .NET CLR) exposes the same four metric types because they all speak the Prometheus text exposition format. What differs per runtime is the **instrumentation surface**: Spring Boot has Micrometer (the facade) + Actuator (the `/actuator/prometheus` endpoint + JVM/thread/tomcat/Hikari auto-instrumentation); Node has `prom-client` + `express-prom-bundle` middleware; Python has `prometheus_client` + `starlette-exporter` / `django-prometheus` middleware; Go has `promhttp` from the official `client_golang` library. The runtime's memory model also affects the Gauge pattern — JVM Gauges are typically `MeterBinder` instances that register a callback invoked on scrape (lazy), while Python and Node Gauges are typically set imperatively on every change (eager). Both work; the lazy pattern is more efficient when the value is expensive to compute (e.g., walking a heap histogram).

## Cross-Runtime Comparison

| Runtime | Default client library | Auto-instrumentation | `/metrics` endpoint | Gauge pattern |
|---|---|---|---|---|
| JVM (Spring) | `micrometer-registry-prometheus` | Spring Boot Actuator (JVM, threads, Hikari, Tomcat, HTTP) | `/actuator/prometheus` | Lazy callback (`Gauge.builder(..., ds, d -> ...)`) |
| Node.js | `prom-client` | `express-prom-bundle` or `@autometrics/opentelemetry` | Manual `app.get("/metrics", ...)` | Eager `gauge.set(value)` |
| Python | `prometheus_client` | `starlette-exporter` / `django-prometheus` | Manual `@app.route("/metrics")` returning `generate_latest()` | Eager `gauge.set(value)` |
| Go | `github.com/prometheus/client_golang/promhttp` | None (you wire it) | `http.Handle("/metrics", promhttp.Handler())` | Lazy via `prometheus.NewGaugeFunc` or eager via `gauge.Set` |
