# 11.01.03. High-Throughput Log Shipping Architectures

## What This Is

A logging call that blocks the request thread is a logging call that costs you SLO budget. When `log.info()` writes synchronously to a file, the syscall (`write(2)`) takes 5–50 microseconds on a hot SSD and 1–10 milliseconds on a networked filesystem — and during that window, the user's HTTP request is stalled. Multiply by 10 log lines per request and 1000 requests per second per host, and the application is spending more time logging than doing actual work. The first half of this note covers the in-process solution: asynchronous, non-blocking appenders that use a ring buffer (often the LMAX Disruptor pattern) to decouple the call site from the I/O. The developer's `log.info()` becomes a memory write to a pre-allocated slot; a dedicated background thread drains the ring buffer to disk or socket.

The second half covers the out-of-process solution: getting the logs from the host's filesystem to a queryable index without losing data when the index is down, without saturating the network, and without buffering unbounded in application memory. Three architectures are compared — agent-based (Filebeat/Fluent Bit tails files → Kafka → Elasticsearch), app-direct (application pushes via HTTP to Loki/CloudWatch), and buffer-at-edge (Kafka as the spool between agents and the indexer). The throughput math is constant across all three: events-per-second × average bytes-per-event = required bandwidth, with a 2× safety margin and a 4× burst headroom. The backpressure contract — what the system does when downstream is slower than the producer — is what separates a log pipeline that survives a 10× traffic spike from one that drops 90% of its events on the floor.

## The Details

### Asynchronous non-blocking log appenders (Ring Buffers / LMAX Disruptor)

The synchronous log appender is the original sin of logging. Logback's default `FileAppender` calls `OutputStream.write(bytes)` on the calling thread, which calls `FileChannel.write(ByteBuffer)` (or `write(2)` via JNI), which may block on disk I/O. If the disk is slow (a networked EBS volume under head-of-line blocking, a shared SAN, a log file rotated by a concurrent process), the calling thread — which is servicing a user request — stalls. The p99 latency of the request becomes coupled to the p99 latency of the disk, which is the worst possible coupling in a backend system. The fix is to insert a queue between the caller and the I/O, and a single dedicated thread that drains the queue.

The naive queue is a `LinkedBlockingQueue`, which is what Logback's `AsyncAppender` uses by default. The problem with `LinkedBlockingQueue` is that every `offer()` and `poll()` allocates a `Node` object on the heap, which triggers GC pressure under high throughput. A 100k-events-per-second producer generates 200k short-lived `Node` objects per second, and the young-generation collector pauses eat the latency savings. The LMAX Disruptor — the high-performance inter-thread messaging library that LMAX Exchange open-sourced in 2011 — replaces the queue with a fixed-size pre-allocated array (the "ring buffer") of `Event` slots. The producer claims the next slot via a CAS on a monotonic sequence counter, writes the payload into the pre-existing slot (no allocation), and publishes by advancing the sequence. The consumer reads up to the published sequence, processes the events, and advances its own cursor. The result is 10–100 million messages per second on a single core, with zero allocation on the hot path.

Log4j2's `AsyncLogger` (the canonical production choice for high-throughput Java services) is built directly on the Disruptor. Logback's `AsyncAppender` is the lower-throughput fallback (`LinkedBlockingQueue`-based, default `queueCapacity=1024`). Spring Boot's default Logback config does not enable async by default; switching to Log4j2 is a one-line change in `pom.xml` (`spring-boot-starter-logging` excluded, `spring-boot-starter-log4j2` included) plus a `log4j2.xml` that enables `<AsyncLogger>` and `<AsyncRoot>`.

```xml
<!-- log4j2.xml — Disruptor-backed async logging -->
<Configuration status="INFO">
  <Appenders>
    <Console name="STDOUT" target="SYSTEM_OUT">
      <JsonTemplateLayout eventTemplateUri="classpath:JsonTemplateLayout.json"/>
    </Console>
  </Appenders>
  <Loggers>
    <AsyncLogger name="com.example" level="INFO" includeLocation="false"/>
    <AsyncRoot level="INFO" includeLocation="false">
      <AppenderRef ref="STDOUT"/>
    </AsyncRoot>
  </Loggers>
</Configuration>
<!-- JVM flag: -Dlog4j2.asyncLoggerRingBufferSize=262144  (must be power of 2) -->
<!-- JVM flag: -Dlog4j2.asyncLoggerWaitStrategy=Timeout   (default: Block) -->
```

The ring buffer's lifecycle has two failure modes that the operator must understand. First: when the producer is faster than the consumer, the ring fills up. The default policy is to **discard** the new event and increment a `dropped` counter (Log4j2's `DefaultAsyncQueueFullPolicy`); the alternative is to **block** the caller until a slot frees (the `BlockingAsyncQueueFullPolicy`, which reintroduces the latency coupling the async appender was supposed to eliminate). Production systems almost always pick "discard with a metric" — losing a log line is preferable to stalling a user request — but they must alert on `log4j2.async.loggers.dropped > 0`. Second: the ring buffer size is fixed at startup (default 256 KB for Log4j2, must be a power of 2). A buffer too small for the burst tolerance will discard under load spikes; a buffer too large will delay log visibility by minutes and increase steady-state memory by hundreds of MB.

```
Producer (request thread)            Ring Buffer (pre-allocated)        Consumer (logger thread)
─────────────────────────           ───────────────────────────         ─────────────────────────
                                                                          
  log.info("x", ctx)                  ┌──┬──┬──┬──┬──┬──┬──┬──┐        while (true) {
  ──> offer(event)                    │E0│E1│E2│E3│E4│E5│E6│E7│           long seq = cursor.acquire();
       │                              └──┴──┴──┴──┴──┴──┴──┴──┘           for (long s = lastRead; s < seq; s++) {
       │  CAS on sequence ─────────>     producerCursor = 5                  write(ring[s & mask]);
       │                                                                       lastRead = s;
       v                                                                  }
  CAS succeeds → slot[5] = event                                          publish consumerCursor = 5;
  (no allocation, no syscall)                                            }
```

The throughput numbers worth memorising: a synchronous `FileAppender` on a hot SSD tops out around 50k events/sec/core before disk I/O dominates. Logback's `AsyncAppender` (LinkedBlockingQueue) reaches 200k events/sec/core before GC pauses dominate. Log4j2's `AsyncLogger` (Disruptor) sustains 2–5 million events/sec/core. The crossover point — where async is no longer optional — is around 5k events/sec per host, which a mid-traffic Java service hits easily. Beyond that, the synchronous appender is stealing p99 latency budget from the request path. The layered mental model here: the ring buffer is an application-tier construct, but the producer/consumer pattern, the CAS sequence, and the pre-allocated array all map directly onto the JVM's memory model (Section 04 — happens-before, volatile reads, false sharing) which in turn maps onto the CPU cache hierarchy (Section 02 — L1/L2/L3 lines, cache-line padding to prevent false sharing on the sequence counter).

### Ingestion Pipelines: Shipping logs via lightweight agents (FluentBit, Vector) → Message Buffers →...

Once the application writes logs to a file (or to stdout, captured by the container runtime into a JSON log file under `/var/log/containers/`), the in-process job is done. The remaining problem is moving those log files from every host to a queryable index, without loss, without saturating the network, and without unbounded buffering in application memory. The architectural choice is between three patterns, each with a different trade-off between operational simplicity, throughput ceiling, and resilience to downstream outages.

The **agent-based architecture** is the historical default. A lightweight agent — Filebeat (Elastic), Fluent Bit (CNCF, the C-language rewrite of Fluentd), or Vector (Datadog, Rust-based) — runs on every host (or as a DaemonSet in Kubernetes). The agent tails the log files using `inotify` for file rotation events and a per-file offset cursor persisted to a registry file (Filebeat's `registry.yml`, Fluent Bit's `storage.path` database). The agent batches events in memory, optionally parses them (Fluent Bit's `Parser` filter, Vector's `remap` VRL transform), and ships them downstream over TCP, HTTP, or Kafka. The application is decoupled from the shipping layer: a new indexer is a config change in the agent, not a redeploy of every service.

The **app-direct architecture** is the modern alternative, enabled by hosted log backends with HTTP ingestion APIs. The application's log appender writes directly over HTTP/HTTPS to the backend — Loki's `/loki/api/v1/push`, CloudWatch Logs' `PutLogEvents`, Datadog's `/v1/input`. The advantage is operational simplicity: no agent to deploy, no registry to maintain, no tailing logic to debug. The disadvantage is that the application is now coupled to the backend's availability — if Loki is down, the appender blocks or drops, and there is no local buffer to absorb the outage. Most HTTP-based appenders implement a small in-memory retry queue (Loki's `loki-logback-appender` defaults to 1000 events with exponential backoff), but this only buys minutes, not hours.

The **buffer-at-edge architecture** is the production-grade hybrid. Agents on every host ship to a Kafka cluster (or a Redis Stream, or a Kinesis stream) running locally or in the same region; the indexer (Logstash, Fluentd, Vector) consumes from Kafka and writes to the search engine. Kafka acts as a multi-hour buffer: if Elasticsearch is down for maintenance, the agents keep shipping to Kafka, the consumers stop reading, and the log backlog grows in Kafka's `log.dirs` instead of being dropped. When Elasticsearch recovers, the consumers catch up. This is the architecture used at scale by every company running >10 TB/day of logs.

```
                Agent-based              App-direct              Buffer-at-edge
                ────────────             ──────────              ──────────────

  Host          Filebeat                 App                     Filebeat
   │             │ (tails files)         │  (HTTP appender)       │ (tails files)
   │             ▼                       │                       ▼
   │           ship:5044                 ▼                     ship:9092
   │             │              HTTPS push to Loki              Kafka (buffer, hours-days)
   │             │                       │                       │
   │             ▼                       ▼                       ▼
  Central     Logstash / Vector         Loki                  Logstash (consumer)
   │             │                       │                       │
   │             ▼                       ▼                       ▼
   │          Elasticsearch            Loki (index)          Elasticsearch (index)
   │             │                       │                       │
   ▼             ▼                       ▼                       ▼
              Kibana                   Grafana                 Kibana

  Throughput    ~50k/s per agent         ~5k/s per app          ~50k/s per agent
  Buffer        none (in-memory)         ~1k in-app retry       hours-days in Kafka
```

```yaml
# filebeat.yml — real production config shipping to Kafka
filebeat.inputs:
  - type: container
    paths:
      - /var/lib/docker/containers/*/*.log
    processors:
      - decode_json_fields:
          fields: ["message"]
          target: ""
      - add_kubernetes_metadata:
          host: ${NODE_NAME}
          matchers:
            - logs_path: { logs_path: "/var/lib/docker/containers/" }

output.kafka:
  hosts: ["kafka-0.logs:9092", "kafka-1.logs:9092", "kafka-2.logs:9092"]
  topic: "logs.raw"
  partition.round_robin:
    reachable_only: true
  required_acks: 1
  compression: gzip
  max_message_bytes: 1000000     # Kafka default max is 1 MB

queue.mem:
  events: 4096                   # in-memory queue before Kafka acks
  flush.min_events: 1024
  flush.timeout: 1s

logging.metrics.enabled: true
```

The throughput math is the same regardless of architecture. A single host producing 10k events/sec at 500 bytes per event averages 5 MB/sec of log volume — well under a 1 Gbps NIC's ceiling, but a real concern on a 100 Mbps link or across an inter-AZ AWS backbone that charges $0.01/GB. The indexer's write throughput is the usual bottleneck: a single Elasticsearch node sustains 30–80k documents/sec indexed (SSD-dependent, shard-count-dependent), and a single Loki ingester sustains 10–20k streams/sec. The backpressure contract is what determines whether a downstream slowdown becomes a backlog or a data-loss event: Filebeat's `queue.mem.events=4096` plus `spool_size` spills to a local file when full; Vector's `disk_buffer` is a configurable on-disk queue with a `max_size` cap (defaults to 1 GB per host); the Kafka buffer-at-edge pattern pushes the backpressure all the way back to Kafka's retention policy (`retention.hours=72`, typical).

The Elasticsearch-vs-Loki query model is the final architectural decision. Elasticsearch indexes **every field** of every document on ingestion — a per-field inverted index per shard, ~10× storage overhead, but O(1) lookup for any field. Loki indexes **only the label set** (typically `app`, `env`, `tenant`) — the log line itself is stored compressed but not indexed, ~1× storage overhead, but queries that match a label are fast and queries that search the line content require a full scan (`rate({app="api"} |= "error" [5m])` is a brute-force grep). The trade-off is storage cost vs. query latency. Elasticsearch is the right choice when you query many fields at high frequency (security analytics, audit log search). Loki is the right choice when you query a few labels at high frequency and grep the line occasionally (application debugging, trace ID lookup). The production failure mode is picking Elasticsearch for everything, watching the index storage cost balloon to 50× the raw log volume, and then being unable to afford the retention you actually need.

## Key Takeaways

1. **Synchronous logging steals p99 latency from the request path.** Any service above ~5k log events/sec/host must use an async appender. Log4j2's `AsyncLogger` (Disruptor-backed, 2–5M events/sec/core) is the production default; Logback's `AsyncAppender` (LinkedBlockingQueue, ~200k events/sec/core) is the fallback. Alert on the dropped-events metric, not on the log volume.
2. **The buffer-at-edge architecture is the only one that survives a multi-hour indexer outage.** Agents ship to Kafka; Kafka buffers for days; indexers consume at their own pace. Agent-direct and app-direct architectures drop after a minutes-to-hours outage. The cost is one Kafka cluster; the benefit is zero log loss.
3. **Elasticsearch and Loki answer different questions.** Elasticsearch indexes every field (10× storage, O(1) field lookup) — pick it for audit, security, high-cardinality search. Loki indexes only labels (1× storage, full-scan grep) — pick it for application debugging, trace ID lookup, low-cardinality queries. Picking the wrong one shows up as either a $500k/yr storage bill or a query that takes 60 seconds to grep a day of logs.
