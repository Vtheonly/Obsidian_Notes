# 11.01.02. Contextual Logging and Mapped Diagnostic Context (MDC)

## What This Is

Structured logging solves the *format* problem (see [[11.01.01. The Fallacy of Unstructured Text Logs]]). Contextual logging solves the *repetition* problem. Without it, every `log.info()` call site that wants to attach `trace_id`, `user_id`, `tenant_id`, `request_id` to the log line must repeat those four values as explicit arguments — and the moment a developer forgets one, that log line loses its join key and becomes unfindable in production. The Mapped Diagnostic Context (MDC) eliminates this by stashing the per-request context in a thread-local map at request entry; the logging framework reads from that map on every log call and merges the entries into the JSON output automatically. The developer writes `log.info("order placed")` and the emitted line still carries `trace_id`, `user_id`, and `tenant_id`.

This note covers the MDC mechanism in the Java/SLF4J/Logback stack (where it originated), the Logback `%X{}` pattern, the Spring Boot servlet-filter integration that populates MDC at request entry, and the cross-runtime equivalents: Node.js `AsyncLocalStorage`, Python `contextvars` (PEP 567), Go `context.Context`. The hard part — and the part that causes the most production incidents — is that MDC is thread-local, and modern applications do not stay on one thread. `@Async`, `CompletableFuture`, reactor streams, and Kafka consumer polls all hop threads, and the MDC does not follow unless you explicitly propagate it. The second H3 covers that failure mode and the `TaskDecorator` / `MDCContext` fixes.

## The Details

### ThreadLocal Context Tracking (MDC in Java/Logback, AsyncLocalStorage in Node.js, contextvars in P...

MDC is, mechanically, a `ThreadLocal<Map<String,String>>` per runtime. In the SLF4J API, the `org.slf4j.MDC` class exposes `put(String key, String value)`, `get(String key)`, `remove(String key)`, and `clear()`. Internally, the Logback implementation (`LogbackMDCAdapter`) stores the map in a `ThreadLocal` that is initialised lazily on first `put()` and removed on `clear()`. When the logger writes a record, the encoder reads the current thread's MDC map and merges every entry into the JSON object as a top-level field. The map is a `Map<String,String>` (not `Map<String,Object>`) because MDC values must serialise to text cheaply and because the SLF4J API predates Java 5 generics in its original design — the `String` constraint is historical but durable.

The Logback pattern that exposes MDC entries in a non-JSON layout is `%X{key}` — the `X` conversion word reads from the MDC. In a JSON encoder (`LogstashEncoder`), MDC entries are emitted as top-level fields by default; the `<includeMdcKeyName>` filter in `logback-spring.xml` controls which entries are emitted (a defence against leaking sensitive context into logs). The pattern matches the layered model: MDC is implemented in the logging library (application-tier), but it builds on `ThreadLocal` which is a JVM primitive (Section 04 runtime), and `ThreadLocal` in turn builds on the OS thread (Section 02 — a `task_struct` in the kernel scheduler).

```java
// Java — SLF4J MDC, the canonical pattern
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;

Logger log = LoggerFactory.getLogger("order");
MDC.put("trace_id", requestId);
MDC.put("user_id", String.valueOf(userId));
MDC.put("tenant_id", tenantCode);
try {
    log.info("placing order");           // emits trace_id, user_id, tenant_id automatically
    orderService.place(order);
    log.info("order placed", kv("order_id", order.getId()));
} finally {
    MDC.clear();                          // mandatory: the thread is pooled
}
// Logback pattern (non-JSON): "%d %-5level [%X{trace_id}] %logger - %msg%n"
// Output: 2024-01-15 INFO  [a1b2c3d4] order - placing order
```

The cross-runtime equivalents differ in implementation but share the same shape: a per-execution-context bag that the logger reads on every call.

| Runtime | API | Backing primitive | Async-safe? |
|---------|-----|--------------------|-------------|
| Java / SLF4J | `MDC.put / get / clear` | `ThreadLocal<Map<String,String>>` | No — does not propagate to `@Async` threads |
| Node.js | `AsyncLocalStorage#run(context, fn)` | V8 async hooks (per-microtask) | Yes — propagates across `await`, `setTimeout`, `Promise` |
| Python 3.7+ | `contextvars.ContextVar.set / get` | PEP 567 context (per-coroutine) | Yes — propagates across `await` (with `contextvars.copy_context()`) |
| Go | `context.Context` passed as first arg | Explicit first parameter | Yes — propagates by construction (you pass it) |

```typescript
// Node.js — AsyncLocalStorage, the equivalent of MDC
import { AsyncLocalStorage } from "node:async_hooks";
import { pino } from "pino";

const log = pino({ level: "info" });
const requestContext = new AsyncLocalStorage<Map<string, string>>();

// middleware
app.use((req, res, next) => {
  const ctx = new Map<string, string>([
    ["trace_id", req.headers["traceparent"]?.split("-")[1] ?? crypto.randomUUID()],
    ["user_id", req.user?.id ?? "anonymous"],
    ["tenant_id", req.tenant?.code ?? "default"],
  ]);
  requestContext.run(ctx, () => next());
});

// logger child binds to the current context
const logger = () => log.child(Object.fromEntries(requestContext.getStore() ?? new Map()));
logger().info({ event: "placing_order" }, "placing order");
// {"level":30,"time":1705315845123,"trace_id":"a1b2c3d4","user_id":"42","tenant_id":"acme","event":"placing_order","msg":"placing order"}
```

```python
# Python — contextvars, the equivalent of MDC (PEP 567)
import contextvars, structlog

trace_id_var: contextvars.ContextVar[str] = contextvars.ContextVar("trace_id", default="")
user_id_var:  contextvars.ContextVar[str] = contextvars.ContextVar("user_id",  default="")

structlog.configure(
    processors=[
        structlog.contextvars.merge_contextvars,  # merges all ContextVars into every event
        structlog.processors.add_log_level,
        structlog.processors.JSONRenderer(),
    ],
)
log = structlog.get_logger("order")

# FastAPI dependency
async def request_context(request: Request):
    trace_id_var.set(request.headers.get("traceparent", "").split("-")[1] or uuid4().hex)
    user_id_var.set(str(request.user.id))
    yield  # context is scoped to this request — restored on exit automatically
```

The Go model is the outlier: rather than an implicit thread-local, Go makes the context an explicit first parameter (`func PlaceOrder(ctx context.Context, order Order) error`). The logger is constructed per call with `log.With("trace_id", traceIDFromContext(ctx))`. This is more verbose but eliminates the propagation failure mode entirely — if `ctx` is not passed, the code does not compile. The Java/Node/Python model trades compile-time safety for ergonomics, and pays for it with the propagation bugs covered in the next H3.

### Automatically injecting global metadata into all log lines emitted within a request context: `ten...

The use case for MDC is narrow but universal: every log line emitted while servicing a single HTTP request must carry the same set of metadata, so that all of them can be filtered to "this request" with one query. The metadata is typically `trace_id` (for joining with traces, see [[11.02.02. Context Propagation and W3C TraceContext]]), `request_id` (for joining with access logs and the client-side correlation ID), `user_id` (for tenant-scoped audit), and `tenant_id` (for multi-tenant isolation). These four fields should never appear as explicit arguments to `log.info()` — they should be set once, at request entry, and forgotten.

In Spring Boot, the right place to set them is a servlet filter registered before the dispatcher servlet. The filter reads the incoming `traceparent` header (or generates a new trace ID if absent), extracts the authenticated user from the security context, looks up the tenant from the request path or header, puts all four values into the MDC, runs `chain.doFilter()`, and clears the MDC in a `finally` block. The `finally` is critical: Tomcat reuses threads from its pool, and an uncleared MDC leaks context from the previous request into the next one — the worst possible failure mode for a multi-tenant system, because user-A's logs start appearing under user-B's `user_id`.

```java
// Spring Boot — the MDC-populating filter
@Component
@Order(Ordered.HIGHEST_PRECEDENCE)
public class RequestContextFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse resp,
                                    FilterChain chain) throws ServletException, IOException {
        String traceId = extractOrGenerateTraceId(req);   // from traceparent header
        String requestId = req.getHeader("X-Request-Id") != null
            ? req.getHeader("X-Request-Id") : UUID.randomUUID().toString();
        MDC.put("trace_id", traceId);
        MDC.put("request_id", requestId);
        MDC.put("user_id", currentUserId());              // from SecurityContextHolder
        MDC.put("tenant_id", currentTenantCode());        // from TenantContext
        resp.setHeader("X-Request-Id", requestId);        // echo back to client
        try {
            chain.doFilter(req, resp);
        } finally {
            MDC.clear();                                   // mandatory: thread is pooled
        }
    }
}
```

The async-propagation failure mode is the hard part. When the request thread hands work off to another thread — via `@Async`, `CompletableFuture.supplyAsync()`, a `ThreadPoolTaskExecutor`, a Kafka `@KafkaListener`, or a reactor `publishOn()` — the new thread does not inherit the MDC. The `ThreadLocal` was set on the request thread, and the worker thread has its own (empty) `ThreadLocal`. The symptom: log lines emitted from inside `@Async` methods show `trace_id` as missing, breaking the join with the rest of the request's logs. In a reactor pipeline the symptom is worse: the MDC appears and disappears seemingly at random, because reactor hops threads on every `publishOn`/`subscribeOn` boundary.

The fix in Spring is a `TaskDecorator` installed on every `TaskExecutor`. The decorator captures the caller's MDC map at submit time and restores it on the worker thread before the task runs, then clears it after. Spring Boot 2.0+ ships `MdcTaskDecorator` as a built-in; for reactor, the equivalent is `Hooks.enableAutomaticContextPropagation()` (reactor-core 3.5+) which integrates with the `ContextPropagation` SPI introduced in Micrometer 1.10. For Java's `CompletableFuture`, you must write the decorator manually or use `ContextSnapshotFactory` from `context-propagation` (the successor to Micrometer's API).

```java
// Spring Boot — TaskDecorator that propagates MDC to @Async threads
public class MdcTaskDecorator implements TaskDecorator {
    @Override
    public Runnable decorate(Runnable runnable) {
        Map<String, String> contextMap = MDC.getCopyOfContextMap();   // capture on caller
        return () -> {
            Map<String, String> previous = MDC.getCopyOfContextMap();
            if (contextMap != null) MDC.setContextMap(contextMap);    // restore on worker
            try {
                runnable.run();
            } finally {
                if (previous != null) MDC.setContextMap(previous);    // restore pool default
                else MDC.clear();
            }
        };
    }
}

@Configuration
@EnableAsync
public class AsyncConfig implements AsyncConfigurer {
    @Override
    public Executor getAsyncExecutor() {
        ThreadPoolTaskExecutor exec = new ThreadPoolTaskExecutor();
        exec.setCorePoolSize(8);
        exec.setMaxPoolSize(32);
        exec.setQueueCapacity(200);
        exec.setTaskDecorator(new MdcTaskDecorator());   // <-- the fix
        exec.initialize();
        return exec;
    }
}
```

```python
# Python — contextvars propagate across `await` automatically,
# but NOT across `loop.run_in_executor(None, blocking_fn)` —
# you must copy the context explicitly:

import contextvars

async def call_blocking_in_pool(blocking_fn, *args):
    ctx = contextvars.copy_context()              # snapshot current ContextVars
    loop = asyncio.get_running_loop()
    return await loop.run_in_executor(None, lambda: ctx.run(blocking_fn, *args))
```

The production incident this prevents is the "phantom request" debug session: an `@Async` payment-processor method throws an exception, the error log line is emitted without `trace_id`, and when the on-call engineer searches Loki for `trace_id=a1b2c3d4` they see every log line from the request except the one that actually failed. The fix is one `TaskDecorator` line; the cost of not having it is hours of guessing which async path the request took. This is the layered-model surface again: the failure is invisible at the framework layer (Spring happily runs the `@Async` method), invisible at the runtime layer (the JVM correctly does not propagate `ThreadLocal` across threads — that is its contract), and only visible at the observability layer when the join fails. The `TaskDecorator` is the explicit bridge across the runtime-layer boundary that the framework layer was hiding from you.

## Key Takeaways

1. **MDC is a thread-local map, and threads are pooled.** Every `put()` must be paired with a `clear()` in a `finally` block, or the next request on that thread inherits the previous request's `user_id` and `tenant_id`. A leaked MDC in a multi-tenant system is a security incident waiting to happen.
2. **MDC does not cross thread boundaries.** `@Async`, `CompletableFuture.supplyAsync`, reactor `publishOn`, and `loop.run_in_executor` all hop threads, and the MDC stays behind. Install a `TaskDecorator` (Spring), use `contextvars.copy_context()` (Python), or rely on `AsyncLocalStorage`'s automatic propagation (Node.js). The failure mode is silent: log lines simply lose their `trace_id`.
3. **The four required fields are `trace_id`, `request_id`, `user_id`, `tenant_id`.** Set them once in a servlet filter at request entry, never as explicit `log.info()` arguments. If you find yourself writing `log.info("x", kv("trace_id", traceId))` more than once, you have a missing MDC filter — fix the filter, not the call site.
