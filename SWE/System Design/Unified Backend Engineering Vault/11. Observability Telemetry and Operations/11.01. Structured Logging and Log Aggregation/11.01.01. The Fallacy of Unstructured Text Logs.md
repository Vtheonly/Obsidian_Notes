# 11.01.01. The Fallacy of Unstructured Text Logs

## What This Is

A log line is the most basic telemetry primitive: a string emitted by an application, written to a file or a socket, eventually searchable by a human. The mistake — the *fallacy* this note dismantles — is treating that string as prose for humans rather than as data for machines. Once a system has more than one service, more than one developer, and more than one user, every log line is consumed by machines a thousand times more often than by humans: ingestion parsers, indexers, alert rules, dashboards, trace joiners, audit pipelines. A free-form text log is opaque to all of them.

Structured logging is the contract that fixes this: every log line is a JSON object (or a key-value record in some other deterministic format) with stable, named, typed fields. The message string still exists, but it sits inside the JSON as one field among many. The fields are first-class — indexable, filterable, aggregatable — and the message is demoted to a human-readable label. This note covers the failure mode of unstructured logs in detail, then walks through the structured-logging stack as it actually ships in Java (SLF4J + Logback + `logstash-logback-encoder`), Python (`structlog`), and PHP/Laravel (`Log::info($message, $context)`). The contextual-MDC and high-throughput-shipping stories are taught in [[11.01.02. Contextual Logging and Mapped Diagnostic Context (MDC)]] and [[11.01.03. High-Throughput Log Shipping Architectures]] respectively.

## The Details

### Unstructured string outputs: High parsing overhead, brittle regex ingestion pipelines, impossibil...

The prototypical bad log line is `System.out.println("user " + userId + " did " + action)`. To the developer who wrote it, the meaning is obvious. To every machine downstream, it is a hostile string. To parse out `userId` and `action`, the ingestion pipeline must apply a regex like `^user (\d+) did (\w+)$` — and that regex breaks the instant a developer rewrites the line as `"user " + userId + " performed action " + action` (now the regex matches nothing and the field disappears silently), or as `"user=" + userId + " action=" + action` (now a different regex is needed). There is no schema, no type information, no contract; the format is whatever the developer typed that day, and any change is a breaking change to every downstream consumer.

The parsing overhead is the second cost. A real production system can emit 100,000 log lines per second per host. Parsing each one with a regex costs on the order of 1–10 microseconds per line on a modern CPU, which is 0.1–1.0 CPU-seconds per real second — a meaningful fraction of a core, spent purely on guessing what the developer meant. Compare this to JSON parsing with a streaming parser (Jackson, `simdjson`, `encoding/json`): 50–500 nanoseconds per line for a small record, with no ambiguity about field boundaries. Worse, the regex parses are usually attempted on the *ingestion* side — in Logstash, Fluentd, Vector — which means the parsing cost is paid by the centralised pipeline, not the application, and the pipeline becomes the bottleneck. A single ill-formed line (an exception stack trace interleaved with a log message, say) can crash a regex parser and stall the entire pipeline.

The third and most painful cost is the impossibility of deterministic querying. With unstructured logs, the question "show me every login from IP 10.0.0.1 in the last hour" requires a full-text search across every field of every log line, followed by a regex extraction of the IP, followed by a filter — and the result is only as accurate as the regex. With structured logs, the same question is `{"event":"user_login","ip":"10.0.0.1"}` indexed on the `ip` field — a single indexed lookup, returning in milliseconds, with no false positives.

```text
# The same event, four ways the developer might phrase it next quarter:

  2024-01-15 10:30:45 INFO  User 42 logged in from 10.0.0.1
  2024-01-15 10:30:45 INFO  user_id=42 ip=10.0.0.1 event=login
  2024-01-15 10:30:45 INFO  [login] user=42 src=10.0.0.1
  2024-01-15 10:30:45 INFO  42 logged in (10.0.0.1)

# Every one of these breaks the original regex `^User (\d+) logged in from (.*)$`.
# The structured equivalent is one JSON shape, stable forever:

  {"ts":"2024-01-15T10:30:45Z","level":"INFO","logger":"auth",
   "event":"user_login","user_id":42,"ip":"10.0.0.1",
   "trace_id":"a1b2c3d4","duration_ms":45}
```

The production incident this causes looks like this: an alert rule fires on `error_count > 100 per minute`. The rule works because the word "ERROR" appears in the line. But when a developer refactors the error path and starts logging `"FATAL: payment gateway timeout"` instead of `"ERROR: payment gateway timeout"`, the alert stops firing — silently, with no deploy warning, no test failure, no review flag. The first time anyone notices is when a customer reports that payments have been failing for six hours. The structured equivalent — `{"level":"ERROR","event":"payment_gateway_timeout"}` — is robust to message rewording because the alert rule keys off the `event` field, not the message string. This is the layered mental model surfacing: the alert rule lives in the observability layer (Section 11.03), the log format lives in the framework layer (Section 05), but the contract that binds them is the schema, and a schema is only enforceable on structured data.

### Structured Logging: Emitting machine-readable JSON payloads containing explicit key-value pairs (...

Structured logging redefines the log line as a record, not a sentence. The record has a fixed set of core fields (`timestamp`, `level`, `logger`, `thread`, `message`) and an open set of contextual fields (`trace_id`, `user_id`, `tenant_id`, `request_id`, `duration_ms`, `event`). The core fields are populated by the logging framework; the contextual fields are populated by application code or, better, by the MDC (see [[11.01.02. Contextual Logging and Mapped Diagnostic Context (MDC)]]). The wire format is JSON — one object per line, newline-delimited, so the file is both human-greppable and machine-parseable.

In Java, the production stack is SLF4J as the API façade, Logback as the implementation, and `logstash-logback-encoder` as the JSON encoder. The Logback config replaces the default `PatternLayoutEncoder` with `LogstashEncoder`, which emits each log call as a JSON object containing the MDC entries, the marker, the structured arguments, and the stack trace (as a JSON array of strings, not a multi-line blob). The same code that wrote `log.info("User {} logged in", userId)` now writes `log.info("User logged in", kv("user_id", userId), kv("event", "user_login"))` — the message becomes a constant string (no parameterisation, no regex breakage) and the variable data moves into typed fields.

```xml
<!-- logback-spring.xml — the production Logback config -->
<configuration>
  <appender name="JSON" class="ch.qos.logback.core.ConsoleAppender">
    <encoder class="net.logstash.logback.encoder.LogstashEncoder">
      <fieldNames>
        <timestamp>@timestamp</timestamp>      <!-- matches Elasticsearch convention -->
        <version>[ignore]</version>            <!-- drop the logstash version field -->
      </fieldNames>
      <includeMdcKeyName>trace_id</includeMdcKeyName>
      <includeMdcKeyName>user_id</includeMdcKeyName>
      <includeMdcKeyName>tenant_id</includeMdcKeyName>
      <includeContext>false</includeContext>   <!-- drop logger-context noise -->
    </encoder>
  </appender>
  <root level="INFO">
    <appender-ref ref="JSON"/>
  </root>
</configuration>
```

```java
// Java — the call site stays clean; the framework does the heavy lifting
import static net.logstash.logback.argument.StructuredArguments.kv;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;

Logger log = LoggerFactory.getLogger("auth");
try (MDC.MDCCloseable c = MDC.putCloseable("user_id", String.valueOf(userId))) {
    log.info("user logged in", kv("event", "user_login"), kv("ip", clientIp));
}
// Emits: {"@timestamp":"2024-01-15T10:30:45.123Z","level":"INFO",
//         "logger_name":"auth","message":"user logged in",
//         "event":"user_login","user_id":"42","ip":"10.0.0.1",
//         "trace_id":"a1b2c3d4"}
```

In Python, the production stack is `structlog` over the standard `logging` module. `structlog` replaces the `log.info("User %s logged in", user_id)` call with `log.info("user_logged_in", user_id=user_id, ip=client_ip)` — the first positional argument is the event name (a stable string, not a format template), and every other argument is a keyword that becomes a JSON field. `structlog` is configured with a chain of processors (`add_log_level`, `TimeStamper(fmt="iso"), `JSONRenderer()`) that transform the event dictionary into the final JSON line.

```python
# Python — structlog configured for JSON output
import structlog
structlog.configure(
    processors=[
        structlog.contextvars.merge_contextvars,    # bind request-scoped context
        structlog.processors.add_log_level,
        structlog.processors.TimeStamper(fmt="iso"),
        structlog.processors.StackInfoRenderer(),
        structlog.processors.format_exc_info,
        structlog.processors.JSONRenderer(),
    ],
)
log = structlog.get_logger("auth")
log.info("user_logged_in", user_id=user_id, ip=client_ip, duration_ms=45)
# {"event":"user_logged_in","user_id":42,"ip":"10.0.0.1",
#  "duration_ms":45,"level":"info","timestamp":"2024-01-15T10:30:45.123Z"}
```

In Laravel/PHP, structured logging is built into the framework via the `Log::info($message, $context)` pattern. The `$context` array is merged into the log record as fields, and the default Monolog driver can be configured with a `JsonFormatter` to emit JSON instead of the default `LineFormatter`. Spring Boot achieves the same thing with the `logstash-logback-encoder` dependency on the classpath — once present, the default console appender switches to JSON automatically.

```php
// Laravel — context array becomes JSON fields
use Illuminate\Support\Facades\Log;
Log::info('User logged in', [
    'event'    => 'user_login',
    'user_id'  => $userId,
    'ip'       => $request->ip(),
    'duration_ms' => $durationInMs,
]);
// config/logging.php — switch the default channel to JSON
'stderr' => [
    'driver'     => 'monolog',
    'handler'    => StreamHandler::class,
    'formatter'  => Monolog\Formatter\JsonFormatter::class,
    'with'       => ['stream' => 'php://stderr'],
],
```

The cross-ecosystem invariant is the same: the *message* is a stable constant string (often an event name like `user_logged_in`), and the *variable* data lives in named fields. Once that invariant holds, the downstream pipeline can index on `event`, `user_id`, `trace_id` directly — no regex, no guessing, no silent breakage on refactor. The failure mode shifts from "the parser broke" to "the field is missing", which is detectable by a schema validator (like the `ecs-logging` spec for Elasticsearch or the OTel semantic conventions for OTLP logs) and alertable. That is the entire point: structured logging converts a class of silent failures into loud, detectable, schema-violation failures.

## Key Takeaways

1. **The log line is data, not prose.** Every field that downstream code needs to read must be a named, typed field in a JSON object — never embedded in a free-form message string. The message is a constant label; the variable data is in fields.
2. **The schema is the contract between the application and the alerting layer.** Change the message string freely; never change a field name without coordinating with every consumer (the alert rules in [[11.03.03. PromQL and Alerting Engineering]], the trace joiner in [[11.02.02. Context Propagation and W3C TraceContext]], the audit pipeline). Treat field names with the same gravity as a public API.
3. **The unstructured-log incident is silent.** There is no test that catches "the developer rephrased the log message and the alert stopped firing" — only a customer complaint six hours later. Structured logging makes the contract explicit, versioned, and machine-checkable.
