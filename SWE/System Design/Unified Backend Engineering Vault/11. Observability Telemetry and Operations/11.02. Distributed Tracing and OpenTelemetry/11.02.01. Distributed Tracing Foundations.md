# 11.02.01. Distributed Tracing Foundations

## What This Is

A single user request in a modern microservice backend touches dozens of services before returning. A typical e-commerce "place order" request: the API gateway receives the HTTP call, authenticates against the identity service, calls the cart service to fetch items, calls the inventory service to reserve stock, calls the pricing service to compute totals, calls the payment service to charge the card, calls the order service to persist the order, publishes a `OrderPlaced` event to Kafka that is consumed by the shipping service, the notification service, and the loyalty-points service. Fifty services, hundreds of network hops, several queue boundaries. When the request takes 800 ms instead of the usual 200 ms, the question is: *which of the fifty services is responsible for the extra 600 ms?* Logs cannot answer this — they are siloed per process and have no causal link between them. Metrics cannot answer this — they are aggregated and lose the per-request identity. Only distributed tracing can.

This note covers the conceptual foundation: the *need* that tracing addresses, the *data model* (trace, span, span ID, parent span ID, trace ID), and how that data model is propagated across process boundaries. The propagation mechanism itself — the W3C `traceparent` header, the inject/extract API — is the subject of [[11.02.02. Context Propagation and W3C TraceContext]]. The OTel SDK implementation, the Collector, and the auto-instrumentation are the subject of [[11.02.03. The OpenTelemetry (OTel) Framework]]. Here we establish the abstract model that both of those notes implement.

## The Details

### The Need: Tracing the lifecycle of an end-user action across dozens of independent asynchronous n...

Distributed tracing exists because the alternative is forensic reconstruction by hand. Before tracing, the on-call engineer investigating a slow request would `grep` the access logs of every service for the request ID, correlate timestamps across services by hand, count the gap between "service A received request" and "service A called service B", and hope the clocks were synchronised. In a fifty-service system this takes hours per incident, depends on NTP precision that is rarely better than 10 ms, and breaks entirely when the call crosses a queue boundary (the consumer's log has no link to the producer's log). The mental cost is invisible until you experience the alternative: open a trace in Jaeger, see the span tree, see that the payment service's `chargeCard` span took 540 ms while every other span was under 20 ms, and know within seconds where to look.

The academic foundation is the Google Dapper paper ("Dapper, a Large-Scale Distributed Systems Tracing Infrastructure", Sigcomm 2010). Dapper was built to answer exactly the question above — Google's search pipeline in 2010 crossed dozens of services, and the company needed a way to attribute latency and failures to specific RPC hops. The paper established three things that every subsequent tracing system has copied: (1) the trace is a tree of spans, with each span representing one unit of work; (2) the trace context (trace ID + parent span ID) is propagated in band with the RPC, typically as an HTTP header or RPC metadata; (3) the instrumentation is split between a small per-service library that does the propagation and a central collector that assembles the tree. The Dapper paper reported that the overhead was 3% of CPU and that Google was sampling 1 in 1024 traces in production — the sampling rate that has become the default in most modern deployments.

The standardisation history is worth knowing because the fragmentation cost real money for years. From 2012 to 2019 there were three competing APIs: OpenTracing (CNCF, vendor-neutral API), OpenCensus (Google, API + SDK + exporter in one), and proprietary SDKs from Datadog, Lightstep, New Relic, AppDynamics. A service instrumented with OpenTracing could not export to a collector that spoke OpenCensus, and vice versa; switching vendors meant re-instrumenting every service. In 2019 the two projects merged into OpenTelemetry (OTel), which is now the CNCF standard for logs, metrics, and traces. The merge preserved the OpenTracing API shape (Tracer, Span, SpanContext) and the OpenCensus SDK shape (BatchSpanProcessor, OTLP exporter). The backends — Jaeger (CNCF, born at Uber, originally Zipkin-compatible), Zipkin (born at Twitter, pre-Dapper paper influence), Tempo (Grafana Labs), Datadog APM, AWS X-Ray — all now ingest OTLP, the OpenTelemetry Protocol, and the choice of backend is independent of the choice of instrumentation.

| Era | API | SDK | Backends |
|-----|-----|-----|----------|
| 2010 | Dapper (internal Google) | Dapper (internal) | Dapper (internal) |
| 2012–2015 | Zipkin (Thrift) | Brave (Java), py_zipkin | Zipkin |
| 2016–2019 | OpenTracing *or* OpenCensus | Per-vendor SDK | Jaeger, Zipkin, Datadog, Lightstep |
| 2019–present | OpenTelemetry API | OpenTelemetry SDK | Jaeger, Zipkin, Tempo, Datadog, X-Ray, Honeycomb, etc. — all via OTLP |

The reason tracing is *essential* rather than *nice-to-have* in microservices is the combinatorial explosion of hops. A monolith has one log stream per request — the application log — and you can read it top-to-bottom. A fifty-service system has fifty log streams per request, and the only thing that lets you reassemble them into a single narrative is the trace ID that propagates across all of them. Without tracing, you are not debugging a fifty-service system; you are debugging fifty separate one-service systems and trying to infer the cross-service causality by timestamp. With tracing, the cross-service causality is encoded in the data model itself — which is what the next three H3s cover.

### Data Model

The distributed tracing data model has five primitives: the **trace** (the end-to-end transaction), the **span** (one unit of work within the trace), the **trace ID** (the 128-bit identifier shared by every span in the trace), the **span ID** (the 64-bit identifier unique within the trace), and the **parent span ID** (the span ID of the calling span, which forms the tree). Every span carries all four identifiers; the (trace_id, span_id) pair uniquely identifies a span globally, and the (trace_id, parent_span_id) relationship defines the tree structure. There is no separate "trace object" — a trace is materialised only by querying the backend for every span with a given trace ID and reconstructing the tree from the parent_span_id pointers.

```
  Trace ID: 0af7651916cd43dd8448eb211c80319c  (128 bits, hex)

  Span tree (each box is one span; arrows are parent→child):

  ┌──────────────────────────────────────────────────────────┐
  │ span_id=01  parent=ROOT  op=HTTP GET /checkout           │   0 ms ─── 800 ms
  │  service=api-gateway                                     │
  └──┬───────────────────────┬───────────────────────────────┘
     │                       │
     ▼                       ▼
  ┌──────────────┐     ┌─────────────────────────────────────┐
  │ id=02  p=01  │     │ id=03  p=01  op=cart.fetch          │   5 ms ─ 15 ms
  │ op=auth.verify│    │ service=cart                        │
  │ svc=auth      │    └─────────────────────────────────────┘
  │ 5 ms ─ 10 ms  │
  └──────────────┘             ┌──────────────────────────────┐
                               │ id=04  p=01  op=pay.charge   │   20 ms ── 580 ms  ← bottleneck
                               │ service=payment              │
                               └──────────────────────────────┘
                                             │
                                             ▼
                               ┌──────────────────────────────┐
                               │ id=05  p=04  op=stripe.api   │   21 ms ── 570 ms
                               │ service=payment              │
                               └──────────────────────────────┘
```

The identifiers are random, not sequential — a span ID is a 64-bit random integer formatted as 16 hex characters, and a trace ID is a 128-bit random integer formatted as 32 hex characters. Random IDs allow every service to generate its own span ID without coordination, and the 64-bit space is large enough that collisions within a single trace are negligible (a fifty-span trace has a ~10⁻¹⁶ probability of any collision). The W3C TraceContext specification (RFC in progress, widely deployed) mandates these lengths and the canonical lowercase-hex encoding; the older B3 header format used by Zipkin allowed variable-length IDs but is now considered legacy.

The propagation contract is what makes the model distributed. When service A calls service B, A creates a new span for the call (with A's current span as the parent), and the HTTP client injects the trace context — `trace_id`, the new span's `parent_span_id` (which is A's current span ID), and the `trace_flags` byte — into the outgoing request as headers. Service B's HTTP server extracts those headers on receipt, creates its own span (with the injected span ID as the parent), and continues the trace. The header format is the W3C `traceparent` header: `00-<trace_id>-<parent_id>-<flags>`, e.g. `00-0af7651916cd43dd8448eb211c80319c-00f067aa0ba902b7-01`. The `00` is the version byte; the `01` at the end is the `trace_flags` byte, where bit 0 is the *sampled* flag (whether this trace should be recorded at all). The full propagation mechanism is covered in [[11.02.02. Context Propagation and W3C TraceContext]].

```python
# Pseudocode for the inject/extract contract — the heart of distributed tracing
def http_call_with_trace(url, payload):
    span = tracer.start_span(f"HTTP POST {url}")          # child of current span
    headers = {}
    # inject: serialise the span context into headers
    tracer.inject(span.context, format=Format.HTTP_HEADERS, carrier=headers)
    # headers now contains: {"traceparent": "00-0af7...-00f0...-01"}
    response = http.post(url, payload, headers=headers)
    span.end()
    return response

def http_server_handler(request):
    # extract: parse the trace context from headers
    ctx = tracer.extract(format=Format.HTTP_HEADERS, carrier=request.headers)
    # ctx contains trace_id and parent_span_id from the caller's span
    span = tracer.start_span(f"HTTP {request.method} {request.path}", child_of=ctx)
    with span:
        return handle_request(request)
```

The data model deliberately omits one thing that newcomers expect: a *list* of spans, in order, with timestamps. The model stores a set of spans, each with its own start time, duration, and parent pointer. The temporal ordering is reconstructed by the backend at query time, by sorting spans by start time within the tree walk. This is what makes the model tolerant of clock skew between services — the parent-child relationship is structural (encoded in the parent_span_id at injection time), not temporal (derived from timestamp comparison). A 100 ms clock skew between the cart service and the payment service might make the payment span appear to start before the cart span, but the tree structure remains correct because the parent pointer was set when the call was made, not inferred from the timestamp. The one place clock skew still bites is in the duration attribution: if you ask "how long was the call from cart to payment?", the answer is `payment_span.start_time - cart_span.start_time`, and that subtraction is only as accurate as the NTP sync between the two hosts. Modern deployments use `clock_gettime(CLOCK_REALTIME)` with NTP precision of 1–10 ms, which is acceptable for second-scale attribution but unreliable for sub-millisecond hop analysis.

### **Trace**: A complete Directed Acyclic Graph (DAG) representing an end-to-end transaction

A trace is the unit of causality. It groups every span that participated in servicing a single end-user action — every HTTP hop, every queue publish/consume, every database query, every cache lookup — into one logical transaction identified by a single 128-bit trace ID. The shape of a trace is, in the strictest sense, a directed acyclic graph (DAG): each span has exactly one parent span, and there are no cycles. In the common case of synchronous request/response, the trace is a tree — the root span is the entry point (the HTTP server span at the gateway), every internal span has exactly one parent, and the leaves are the leaf operations (database queries, cache gets). The DAG terminology covers the less-common case where a single span has multiple parents (a span that joins the work of two upstream spans), which some tracing systems support but OTel's spec does not — OTel traces are strictly trees.

The trace ID is generated once, at the entry point of the request, and never changes for the lifetime of the request. The W3C specification mandates a 128-bit (16-byte) random trace ID, encoded as 32 lowercase hex characters. The randomness is critical: if trace IDs are sequential or timestamp-derived, an attacker who observes one trace ID can predict past or future trace IDs and exfiltrate other users' request data by querying the trace backend. The 128-bit space is large enough that brute-force enumeration is infeasible (2¹²⁸ ≈ 3.4 × 10³⁸ possible IDs). When the entry-point service does not generate a trace ID (because it is un-instrumented — a load balancer, a CDN edge, a legacy service), the first instrumented service downstream generates one and the trace simply starts there, missing the upstream latency.

```
  Trace ID generation and propagation:
                                                            
  Browser ──HTTP──> API Gateway ──HTTP──> Cart Service       
                                                            
   no traceparent           generates trace_id=T1            
   header sent               span_id=S1 (root)               
                            ┌───────────────────────┐        
                            │ trace_id = T1         │        
                            │ span_id   = S1        │        
                            │ parent    = (none)    │        
                            └───────────────────────┘        
                                       │                     
                                       │ inject(T1, S1)      
                                       ▼                     
                            ┌───────────────────────┐        
                            │ trace_id = T1         │        
                            │ span_id   = S2        │        
                            │ parent    = S1        │        
                            └───────────────────────┘        
                                                            
  The HTTP request from gateway to cart carries:            
    traceparent: 00-T1-S1-01                                
    (version-traceid-parentid-flags)                        
```

The trace is materialised only at query time. During execution, each service emits its own spans to the collector independently — there is no "trace builder" process that assembles them in flight. The backend (Jaeger, Tempo, Elasticsearch APM) stores spans indexed by `trace_id`, and when you query for a trace, the backend fetches every span with that `trace_id`, sorts them by start time within the parent-child tree walk, and renders the tree. This decoupling is what makes the system horizontally scalable: spans from a single trace can be emitted by fifty services running on five hundred hosts, collected by ten collector replicas, stored in a sharded backend, and reassembled into a tree on demand. The cost is that the trace is only complete once every span has been ingested — if a service is slow to flush its batch (the OTel `BatchSpanProcessor` defaults to a 5-second flush), the trace will appear incomplete in the UI for those 5 seconds.

The trace-level metadata that the backend stores separately from spans: the **service map** (which services called which other services, aggregated across all traces), the **trace statistics** (p50/p90/p99 latency per trace shape, error rate per trace shape), and the **slowest traces** view (the top N traces by duration, for finding long-tail outliers). These are derived quantities, computed by the backend from the underlying span data. They are the answer to "is this service slow in aggregate?" — but the answer to "why is this specific request slow?" requires opening the trace and walking the span tree, which is the subject of the next H3.

### **Span**: A single contiguous block of work executed within a service, containing Start Time, Dur...

The span is the atomic unit of tracing. A span represents a single named operation: an HTTP request handler, a database query, a Kafka producer send, a Redis `GET`, a gRPC unary call, a section of business logic explicitly bracketed by the developer. Every span has six mandatory fields and four optional ones. The mandatory fields are: (1) **trace_id** — the 128-bit trace identifier, inherited from the parent; (2) **span_id** — the 64-bit unique identifier, generated by the emitting service; (3) **parent_span_id** — the span ID of the calling span, or null for the root; (4) **operation name** — a human-readable string like `HTTP GET /checkout` or `cart.fetch`; (5) **start time** — a microsecond-precision timestamp from `clock_gettime(CLOCK_REALTIME)`; (6) **end time** — same. The optional fields are: (7) **attributes (tags)** — key-value pairs of typed data (`http.status_code=200`, `db.system="postgresql"`, `messaging.destination="orders"`); (8) **events (logs)** — timestamped annotations within the span, each with its own key-value attributes (`acquired_lock` at T+12 ms, `released_lock` at T+45 ms); (9) **status code** — `UNSET`, `OK`, or `ERROR`; (10) **links** — references to other spans, used when a span has multiple causal inputs (rare; for fan-in from multiple traces).

The span lifecycle in code is bracketed by `startSpan()` and `span.end()`. The OTel API exposes this as a try-with-resources pattern in Java (`try (Span span = tracer.spanBuilder("op").startSpan()) { ... }`) and a `with` block in Python (`with tracer.start_as_current_span("op") as span: ...`). The span's start timestamp is captured at `startSpan()`; the end timestamp at `end()`. Between those two calls, the developer may add attributes (`span.setAttribute("user_id", userId)`), events (`span.addEvent("cache.miss", attributes)`), or record exceptions (`span.recordException(ex)` — which adds an event with the exception's class name, message, and stack trace as attributes, and sets the status to `ERROR`). The OTel SDK's `BatchSpanProcessor` collects ended spans in a batch (default `maxQueueSize=2048`, `maxExportBatchSize=512`, `exportTimeout=30s`) and exports them via OTLP to the collector, which forwards to the configured backend.

The semantic conventions — the standard attribute names like `http.method`, `db.system`, `messaging.destination` — are what make spans queryable across services. Without conventions, every service invents its own attribute names (`http_verb` vs `httpMethod` vs `method`), and cross-service queries become impossible. The OTel semantic conventions are a long, versioned specification maintained by the OTel project; the production-grade auto-instrumentation libraries (`opentelemetry-java-agent`, `opentelemetry-python-instrumentation`) apply them automatically — the developer does not need to set `http.method` themselves, the agent does it by intercepting the servlet call. The developer's job is to add the business-logic attributes that the auto-instrumentation cannot know about: `order.id`, `cart.item_count`, `payment.amount`. These are the attributes that let you answer "show me all traces where the order total was > $1000 and the payment took > 500 ms" — the question that turns tracing from a debugging tool into a business analytics tool.

The failure mode of bad span design is the "fat span" anti-pattern: a single span that wraps an entire request handler without any child spans for the expensive sub-operations. The trace shows `HTTP GET /checkout: 800 ms` and nothing else — you know the request was slow, but you cannot tell whether the 800 ms was spent in the database, the cache, the payment gateway, or the business logic. The fix is to create child spans for every expensive operation: `tracer.spanBuilder("db.query.orders").startSpan()` around the database call, `tracer.spanBuilder("http.call.payment").startSpan()` around the outgoing HTTP call. The OTel auto-instrumentation does this for known libraries (JDBC, the HTTP client, the Kafka producer); the developer must do it for their own business logic. A good rule of thumb: if an operation takes more than 1% of the request's p99, it deserves a span. The corollary failure mode is "span noise": creating spans for every method call, including the 10-microsecond ones, which floods the backend with low-value spans and inflates the storage cost. The line is judgment, but the auto-instrumentation libraries have already drawn it for the standard libraries — follow their lead.

## Key Takeaways

1. **A trace is a tree of spans, identified by a 128-bit trace ID that propagates across every service hop.** Without the trace ID, fifty services' logs are fifty siloed streams. With it, they are one narrative that can be reassembled in seconds. The trace ID is generated at the entry point and propagated in band via the `traceparent` header — see [[11.02.02. Context Propagation and W3C TraceContext]].
2. **A span is a named operation with start/end timestamps, attributes, events, status, and a parent pointer.** The parent pointer is what forms the tree — not the timestamps, which are subject to clock skew. Span attributes follow the OTel semantic conventions so that cross-service queries ("all spans where `db.system=postgresql` and `db.operation took > 100 ms`") are possible.
3. **Tracing is mandatory in microservices because the alternative is hand-reconstruction.** The Dapper paper established the model in 2010; OpenTelemetry standardised the API in 2019; the backends (Jaeger, Zipkin, Tempo, Datadog, X-Ray) all ingest OTLP today. The choice of backend is now independent of the choice of instrumentation, which was not true five years ago and is the single biggest reason tracing adoption has accelerated.
