# 11.02.02. Context Propagation and W3C TraceContext

## What This Is

A distributed trace is only as useful as the chain of parent–child span relationships that connects it. The instant a request leaves one process — an HTTP client closing the TCP socket, a producer pushing a record onto a Kafka topic, a gRPC stub serializing the next hop — that parent–child chain must be carried out-of-band, in protocol-specific headers or message metadata, and reconstructed on the other side. **Context propagation** is the discipline of injecting trace identifiers into the carrier at the sender, and extracting them back out at the receiver so that the downstream span opens as a child of the upstream span rather than as a new root.

This note covers the W3C TraceContext specification (the `traceparent` and `tracestate` headers), the related W3C Baggage spec (cross-cutting key-value context for non-tracing concerns), the per-protocol carrier mappings (HTTP headers, gRPC metadata, Kafka record headers, AMQP message properties), and the asynchronous propagation problem that bites every Java `CompletableFuture`, Python `asyncio`, and Go goroutine implementation. It sits directly on top of [[11.02.01. Distributed Tracing Foundations]] (which defines span, trace, and parent–child) and feeds into [[11.02.03. The OpenTelemetry (OTel) Framework]] (which provides the `Propagator` API that implements all of this). The failure mode is the **broken trace**: a request appears in Jaeger as 12 disjoint trees instead of one, p99 latency attribution is impossible, and the on-call engineer ends up grepping logs by timestamp because the trace ID stopped propagating at the message queue boundary.

## The Details

### Injecting and extracting trace contexts across process boundaries

Every propagator in OpenTelemetry implements two operations: `inject(context, carrier, setter)` runs on the sender side, taking the active `Context` (which holds the current `Span`) and writing its trace ID, span ID, and flags into a carrier; `extract(context, carrier, getter)` runs on the receiver side, reading the carrier and producing a `Context` containing a `RemoteSpan` that the receiver then uses as the parent of its first span. The carrier is protocol-specific: a `Map<String, String>` of HTTP headers, a gRPC `Metadata` object, a Kafka `Headers` iterable, or an AMQP `BasicProperties` map. The setter/getter abstractions exist precisely so that the same propagator code can target any carrier — the OTel Java SDK ships `TextMapGetter`, `HttpRequest`-aware getters, and so on.

The crucial invariant is that **extraction must be the first thing the inbound middleware does, and injection must be the last thing the outbound client does**. In Spring Boot, the `WebMvcFilter` registered by `OpenTelemetrySpringWebMvcAutoConfiguration` extracts `traceparent` before the dispatcher servlet runs and stores the resulting `Context` in a request-scoped bean. The same auto-configuration registers `RestTemplate`/`WebClient` interceptors that inject on the outbound side. If you bypass these (raw `HttpURLConnection`, a hand-rolled gRPC `ClientInterceptor`, a Kafka producer that builds its own `ProducerRecord` without a `TracingProducer` decorator), the trace breaks at that hop. The breakage is silent: no exception, no warning log, just a downstream root span with no parent.

```text
┌─────────────────────────────────────────────────────────────────┐
│ Service A (root span)                                            │
│  span_id=00f067aa0ba902b7  trace_id=4bf92f3577b34da6a3ce929d0e0e│
│  └─ HTTP GET /checkout                                           │
│     │  INJECT traceparent into carrier                           │
│     ▼                                                            │
│   [HTTP request with header: traceparent=00-4bf9..-00f0..-01]    │
│     │                                                            │
│     ▼  EXTRACT on inbound filter                                │
│ Service B (child span)                                           │
│  parent_span_id=00f067aa0ba902b7  (links to A's span)            │
│  └─ HTTP GET /inventory                                          │
└─────────────────────────────────────────────────────────────────┘
```

The production failure mode is the **"trace ID changes at hop N"** bug, almost always caused by an auto-instrumented client calling a manually-instrumented server (or vice-versa). The client injects `traceparent` correctly; the server calls `tracer.spanBuilder("handle").startSpan()` without first extracting the remote context, so the SDK mints a fresh trace ID and the chain is severed. The symptom in Jaeger is that the same request produces two unrelated traces with overlapping timestamps. The fix is to wrap extraction explicitly: `Context extracted = propagator.extract(Context.current(), exchange, getter); Span span = tracer.spanBuilder("handle").setParent(extracted).startSpan();`. Every OTel auto-instrumentation library does this for you; every hand-rolled integration that skips it is a landmine.

### The W3C TraceContext standard

Before 2019 there was no standard trace propagation header. Every vendor had their own: Zipkin popularized B3 (`X-B3-TraceId`, `X-B3-SpanId`, `X-B3-ParentSpanId`, `X-B3-Sampled`, `X-B3-Flags`), Jaeger used its own Uber-style headers (`uber-trace-id`), AWS X-Ray used `X-Amzn-Trace-Id`, Google Cloud Trace used `X-Cloud-Trace-Context`, DataDog used `x-datadog-trace-id`. The consequence was that any heterogeneous system — say a Java service using Jaeger talking to a Python service using Zipkin — lost the trace at the language boundary unless each side was taught to speak the other's dialect. The W3C Distributed Tracing Working Group published the TraceContext Recommendation in February 2020 to collapse this into one header (`traceparent`) plus one optional vendor-extension header (`tracestate`).

W3C TraceContext standardizes three things, and only three things. First, the carrier key: the literal string `traceparent` (case-insensitive on the wire for HTTP, but the canonical form is lowercase). Second, the value format: a hyphen-separated tuple `version-trace_id-parent_id-trace_flags` described in detail under the next H3. Third, the propagation rules: if a receiver sees a malformed `traceparent`, it MUST start a new trace but SHOULD log the rejection; if a receiver sees a valid one, it MUST use the `trace_id` as its trace ID and the `parent_id` as its parent span ID, and MUST echo the `trace_flags` byte forward unless it deliberately changes the sampling decision. The `tracestate` header is the escape hatch for vendor-specific state that does not fit into the rigid `traceparent` format.

```text
                 HTTP request headers
┌─────────────────────────────────────────────────────┐
│ traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-    │
│              00f067aa0ba902b7-01                     │
│ tracestate:    vendor1=opaqueValue,vendor2=t67s3     │
│ baggage:       userId=42,tenant=acme,experiment=B    │
└─────────────────────────────────────────────────────┘
        ▲                            ▲
        │                            │
   W3C-mandated            W3C-defined but
   (every vendor            vendor-extensible
   must honor)              (max 32 list members)
```

The reason every backend framework in section 05 ultimately converges on W3C TraceContext is that it is the lowest common denominator — every major vendor's SDK can now both inject and extract it, and OTel's default `W3CTraceContextPropagator` is the propagator enabled by default in every language SDK. The compatibility concession is `CompositePropagator`, which injects and extracts multiple formats (B3 + W3C + Jaeger) in parallel during migration windows. The failure mode of skipping W3C and staying on B3 indefinitely is that you cannot deploy a sidecar proxy (Envoy, Istio, Linkerd) that only speaks W3C — your mesh silently starts new traces at every hop. The Istio distribution shipped W3C-only in 1.10, which forced a lot of B3-only shops to migrate.

### `traceparent`: `version-trace_id-parent_id-trace_flags` (e.g., `00-4bf92f3577b34da6a3ce929d0e0e47...

The `traceparent` header value is a fixed-grammar string with four hyphen-separated fields, and the format is rigid enough that a one-character mistake invalidates the whole header. The grammar is:

```text
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             ─┬ ────────┬──────────────────────── ─────┬───── ─┬
              │         │                              │       │
           version   trace_id (32 hex / 16 bytes)   parent_id   trace_flags
           ("00")                                      (16 hex    (2 hex / 1 byte
                                                     / 8 bytes)   bit 0 = sampled)
```

The `version` byte (`00` as of 2024) lets the W3C evolve the format later. A receiver that sees an unknown version MUST NOT try to parse the rest — it must drop the header and start a fresh trace. The `trace_id` is 16 bytes (32 lowercase hex characters) and MUST be globally unique — OTel generates it from a CSPRNG; an all-zero trace_id is invalid and must be rejected. The `parent_id` is 8 bytes (16 hex characters) and identifies the immediate caller's span; it is what makes the receiver's first span a child rather than a root. The `trace_flags` byte is currently one bit: bit 0 (the least significant bit) is the `sampled` flag — `01` means "this trace is being sampled, please record your spans", `00` means "do not record, but still propagate so a downstream sampled decision can flip it on". The remaining 7 bits are reserved.

The W3C mandates lowercase hex; some legacy B3 implementations used mixed case, which broke header parsers. The W3C also mandates that hyphens are the literal `-` byte (0x2D); any deviation invalidates the header. The total length is exactly 55 bytes for version `00` (`00-` + 32 + `-` + 16 + `-` + 2). The `trace_flags` byte is the only field a downstream service is allowed to mutate: if it implements a sampling override, it can flip bit 0 from `0` to `1` (or `1` to `0`), but it MUST then echo the updated `traceparent` on the next outbound call so the decision propagates. This is what makes head-based sampling work — the ingress proxy (Istio, ALB, OTel Collector) decides once at the edge and the decision flows with the request.

```text
Valid:    00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
Invalid:  00-4BF92F3577B34DA6A3CE929D0E0E4736-00f067aa0ba902b7-01   (uppercase)
Invalid:  00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7       (missing flags)
Invalid:  00-00000000000000000000000000000000-00f067aa0ba902b7-01     (zero trace_id)
Invalid:  01-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01     (unknown version)
Invalid:  4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01        (missing version)
```

The production failure mode here is the **truncated header**: a load balancer or proxy with a default header-size limit (Envoy's default max request headers is 60 KiB but per-header limits exist in some WAFs, AWS ALB has a 16 KiB total header limit, and a misconfigured `proxy_buffer_size` in nginx can chop a long `tracestate`) silently drops the trailing bytes. The receiver sees a malformed `traceparent` (wrong length, missing flags), rejects it per spec, and starts a new trace. The symptom is intermittent trace breakage that only manifests for requests with large `tracestate` (which carries vendor extensions and grows with each hop). The fix is to audit every proxy in the path for header-size limits and to keep `tracestate` under ~512 bytes total (the W3C caps it at 32 list members).

### `tracestate`: Vendor-specific state propagation

`traceparent` is intentionally minimal — just trace ID, parent ID, and one sampled bit. If a vendor needs to carry anything else (a sampling decision with a probability, an upstream account ID, a trace-level tagging decision, a vendor-specific correlation token), there is no room in `traceparent`. The `tracestate` header is the W3C's answer: a comma-separated list of `key=value` pairs, where each key is a vendor name followed by a vendor-specific suffix (e.g., `aws=` for X-Ray, `datadog=` for DataDog, `jaeger=` for Jaeger, `lightstep=` for Lightstep, `cisco=` for Cisco). A receiver that does not recognize a key MUST forward it unchanged; a receiver that recognizes its own key MAY read and update it. This is what allows multiple vendors to share a single trace without colliding.

The grammar is `tracestate: vendor1=value1,vendor2=value2,...`. Each value is an opaque string up to 256 characters; each key is up to 256 characters; the total header size is capped at 512 bytes and the list at 32 members. When a vendor wants to update its own entry, it MUST move that entry to the front of the list (most-recently-modified first) and MUST drop the oldest entries if the list exceeds 32. This LRU-ish ordering is what lets downstream vendors see the chain of upstream modifications without parsing the whole history.

```text
tracestate: datadog=1282210661:0000000000000000:0:1,
            lightstep=md5:abcdef0123456789,
            aws=s=rootcause;clid=abcd1234
            ▲                  ▲                  ▲
            │                  │                  │
        moved to front      unchanged          unchanged
        when Datadog        (vendor unknown   (AWS X-Ray
        updates its entry   to this hop)      tracing header)
```

The reason `tracestate` exists separately from `traceparent` is versioning safety. If a vendor ships a new sampling format that breaks older parsers, only that vendor's `tracestate` entry is affected — the universal `traceparent` keeps working. The reason `baggage` (the third W3C standard in this space) is separate from both is that `baggage` is **not** trace-vendor-specific: it carries application-level key-value pairs (user ID, tenant ID, experiment bucket, request origin) that should propagate identically across every vendor's tracing backend. The split is: `traceparent` is universal and minimal, `tracestate` is vendor-extensible and trace-related, `baggage` is universal and application-level. The production failure mode of `tracestate` is a vendor that decides to be "helpful" and overwrites the entire header instead of just its own entry — this destroys other vendors' state and turns a multi-vendor trace into a single-vendor one. The OTel SDK does this correctly; hand-rolled instrumentation often does not. The other failure mode is the 32-member cap: a service mesh that adds one entry per hop on a 40-hop path silently truncates the oldest entries, which can break tail-based sampling decisions that depended on the early-hop entries.

## Cross-Ecosystem Code

Real context propagation across the four target ecosystems, using the OTel SDK's `TextMapPropagator` interface:

**Spring Boot (Anchor — auto-instrumented):**
```java
// Auto-instrumentation via -javaagent:opentelemetry-javaagent.jar
// No code needed; W3CTraceContextPropagator is the default.
// Manual extraction (only when bypassing auto-instr):
@Autowired io.opentelemetry.api.GlobalOpenTelemetry openTelemetry;

void handle(HttpServletRequest req) {
    Context extracted = openTelemetry.getPropagators()
        .getTextMapPropagator()
        .extract(Context.current(), req,
            new TextMapGetter<>() {
                public Iterable<String> keys(HttpServletRequest c) { return Collections.list(c.getHeaderNames()); }
                public String get(HttpServletRequest c, String key) { return c.getHeader(key); }
            });
    try (Scope s = extracted.makeCurrent()) {
        Span span = tracer.spanBuilder("handle").setParent(extracted).startSpan();
        // ... business logic ...
        span.end();
    }
}
```

**Express (Delta — `@opentelemetry/api` + `auto-instrumentations-node`):**
```typescript
import { trace, context, propagation } from "@opentelemetry/api";

app.get("/checkout", (req, res) => {
  const extracted = propagation.extract(context.active(), req.headers, {
    get: (carrier, key) => carrier[key.toLowerCase()],
    keys: (carrier) => Object.keys(carrier),
  });
  context.with(extracted, () => {
    const span = trace.getTracer("app").startSpan("checkout");
    // ... business logic ...
    span.end();
    res.json({ ok: true });
  });
});
```

**Flask (Delta — `opentelemetry-instrument-flask` does this automatically):**
```python
from opentelemetry import trace, propagate
from opentelemetry.propagate import extract

@app.route("/checkout")
def checkout():
    ctx = extract(request.headers)              # reads traceparent/tracestate
    token = context.attach(ctx)
    try:
        with tracer.start_as_current_span("checkout"):
            # ... business logic ...
            return jsonify({"ok": True})
    finally:
        context.detach(token)
```

**Django (Delta — middleware-driven):**
```python
# settings.py:
# MIDDLEWARE = [..., "opentelemetry.instrumentation.django.middleware.OTelMiddleware", ...]
# In a manual view:
from opentelemetry import trace, propagate, context

def checkout(request):
    ctx = propagate.extract(request.headers)
    token = context.attach(ctx)
    try:
        with tracer.start_as_current_span("checkout"):
            return JsonResponse({"ok": True})
    finally:
        context.detach(token)
```

The Spring Boot and Django versions are auto-instrumented — the `traceparent` header is extracted before your code runs and the active span is set in a request-scoped bean / `ContextVar`. The Express and Flask versions shown here do it explicitly; in production you would use `@opentelemetry/auto-instrumentations-node` and `opentelemetry-instrument-flask` respectively to avoid this boilerplate. The runtime invariant exposed differently: Spring uses `ThreadLocal`-backed `Context` (which breaks across `CompletableFuture` unless wrapped), Node uses `AsyncLocalStorage` (which transparently crosses `await` boundaries), Python uses `contextvars.ContextVar` (which transparently crosses `await` but NOT `ThreadPoolExecutor.submit` without explicit passing).

## How This Connects to the Runtimes

Context propagation is fundamentally a runtime-level concern because the "active context" must follow the unit of execution. Java stores it in a `ThreadLocal` populated by the servlet container's worker thread; Node.js stores it in `AsyncLocalStorage` (V8's continuation-local storage, implemented via async hooks); Python stores it in `contextvars.ContextVar` (PEP 567, also async-aware); Go has no thread-local at all, which is why every Go OTel function takes a `context.Context` as its first argument and you must thread it through explicitly (`ctx, span := tracer.Start(ctx, "handle")`). The async propagation problem (see below) is the direct consequence of these runtime choices. The protocol-layer concern (HTTP vs gRPC vs Kafka vs AMQP) is orthogonal — the same `Context` object gets serialized into whatever carrier the protocol defines.

## Cross-Runtime Comparison

| Runtime | Storage primitive | Async-safe across `await`? | Async-safe across threads? | Failure mode |
|---|---|---|---|---|
| JVM (Spring) | `ThreadLocal` | No (must wrap `CompletableFuture` with `Context.current()` and `Context.wrap(executor)`) | No (same — must wrap executor) | Trace breaks at the first `.thenApplyAsync()` |
| Node.js | `AsyncLocalStorage` (V8 async hooks) | Yes | N/A (single-threaded) | Trace breaks if a callback is registered without `await`/`then` (raw event-emitter) |
| Python | `contextvars.ContextVar` (PEP 567) | Yes | No (must `contextvars.copy_context().run(...)` in thread pool) | Trace breaks at `loop.run_in_executor()` unless context is copied in |
| Go | Explicit `context.Context` parameter | N/A (no async) | Yes (value is passed by value) | Trace breaks if a function forgets to accept/forward `ctx` |

## Hands-On Exercise

```bash
# 1. Run a two-service chain (Python Flask + Go gRPC) instrumented with OTel.
# 2. Send a request and capture both inbound and outbound traceparent headers:
curl -v -H "traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01" \
     http://localhost:5000/checkout 2>&1 | rg -i 'traceparent|tracestate'

# 3. Deliberately corrupt the header (uppercase the trace_id) and verify the
#    receiver rejects it and starts a new trace:
curl -v -H "traceparent: 00-4BF92F3577B34DA6A3CE929D0E0E4736-00f067aa0ba902b7-01" \
     http://localhost:5000/checkout

# 4. Examine the OTel Collector's rejected-headers counter:
curl -s http://localhost:8889/metrics | rg otelcol_receiver_refused

# 5. Send a request with a 600-byte tracestate (50 vendor entries) and verify
#    the W3C 32-member cap truncates the oldest entries:
python3 -c 'print("tracestate: " + ",".join(f"v{i}=x" for i in range(50)))'
```
