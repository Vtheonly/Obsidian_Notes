# 11.04.03. Graceful Shutdown Lifecycles

## What This Is

Graceful shutdown is the protocol a process follows when it has been asked to stop. The kernel sends a `SIGTERM` (signal 15); the process catches it, stops accepting new work, drains in-flight work to completion (or to a timeout), closes its network sockets and database connections cleanly, flushes its logs, and exits with code 0. If the process does not exit within the orchestrator's grace period, the kernel follows up with `SIGKILL` (signal 9) — an unblockable, immediate termination that drops in-flight requests on the floor, leaves database connections half-open, and produces 502 errors for every client currently mid-request.

In the layered mental model, graceful shutdown sits at the intersection of the Linux signal layer (kernel primitives covered in [[02.01.01. The Linux Process Model]]), the application framework layer (Spring Boot's `WebServerGracefulShutdownLifecycle`, Express's `server.close()`, Django's `runserver` shutdown hook), and the orchestration layer (Kubernetes `terminationGracePeriodSeconds` + `preStop` hook + readiness probe). It is the operational counterpart to the deployment strategies in [[11.04.02. Zero-Downtime Deployment Strategies]]: rolling, blue-green, and canary all depend on the old pods shutting down gracefully so the load balancer can route traffic to new pods without dropping requests. Get this wrong and a rolling deploy of 10 pods produces a 30-second window of 502 errors on every pod swap — not "zero downtime" at all.

## The Details

### Linux Termination Signals: `SIGTERM` (Request termination) vs. `SIGKILL` (Forceful death)

The Linux kernel exposes a fixed set of signals — small integer numbers delivered to a process asynchronously by the kernel, by another process (via `kill(2)`), or by the process itself (via `raise(2)`). Two signals dominate the shutdown story: `SIGTERM` (signal 15) and `SIGKILL` (signal 9). They differ in one critical property: `SIGTERM` can be caught, blocked, or ignored; `SIGKILL` cannot. `SIGTERM` is a polite request — "please shut down when convenient". `SIGKILL` is the kernel's last resort — "die now, no appeal, no cleanup".

When a signal arrives, the kernel suspends the process at the next safe point (system call return, signal-safe interrupt), looks up the signal's disposition in the process's signal handler table, and either runs the registered handler (SIG_DFL + custom handler), performs the default action (SIG_DFL — for SIGTERM this is "terminate"), or ignores it (SIG_IGN). For `SIGTERM`, a process that has registered a handler (via `sigaction(2)` in C, `signal(SIGTERM, ...)` in Node.js, `Runtime.getRuntime().addShutdownHook()` in Java) gets to run arbitrary code before exiting. For `SIGKILL`, no handler is consulted; the kernel immediately reclaims the process's memory, closes its file descriptors, reparents its children to init, and frees its PID. There is no opportunity to flush a buffer, close a socket cleanly, or write a final log line.

```text
Signal delivery and handler invocation (simplified):

  User space              Kernel space
  ───────────             ────────────
  process running
  │
  │  (signal pending
  │   in pending_set)
  │
  │ ← kernel checks pending signals
  │   at next safe point
  │
  │ ← sigterm handler runs:
  │     1. stop accept() loop
  │     2. drain in-flight requests
  │     3. close DB connections
  │     4. exit(0)
  │
  X  process exits cleanly

  vs. SIGKILL:

  process running
  │
  │ ← kernel receives SIGKILL
  │ ← NO handler consulted
  │ ← task_struct marked TASK_DEAD
  │ ← mm_struct freed (memory reclaimed)
  │ ← file descriptors closed forcibly
  │ ← sockets RST sent to peers
  X  process gone, peers see ECONNRESET
```

The third signal that matters for shutdown is `SIGINT` (signal 2), sent by Ctrl+C in a terminal. It behaves like `SIGTERM` — catchable, default action is terminate — and most production code uses the same handler for both. There is also `SIGHUP` (signal 1), originally "hangup" (terminal disconnected), now often repurposed as "reload config without restart" — Nginx and Postgres both use `SIGHUP` to reload config files. `SIGQUIT` (signal 3, Ctrl+\) triggers a core dump by default in many runtimes (Java's `kill -3 <pid>` dumps all thread stacks to stdout — invaluable for diagnosing a hung JVM).

The order in which orchestrators send signals matters. Kubernetes sends `SIGTERM` immediately after the Pod is marked for deletion, then waits `terminationGracePeriodSeconds` (default 30s), then sends `SIGKILL`. Systemd sends `SIGTERM` on `systemctl stop`, waits `TimeoutStopSec=` (default 90s), then `SIGKILL`. Docker sends `SIGTERM` on `docker stop`, waits 10s by default (`--time` flag), then `SIGKILL`. A common footgun: an app configured with a 60s graceful shutdown timeout running on Docker default 10s timeout gets `SIGKILL` after 10s, never finishing its drain. Always align the orchestrator's grace period with the app's shutdown timeout, with the orchestrator's grace period slightly longer (e.g., app 30s + orchestrator 35s) so the app exits cleanly before the kill.

The production failure mode is the **uncaught SIGTERM**. A naive Node.js app started with `node server.js` registers no SIGTERM handler. The default disposition for SIGTERM is "terminate", so the process exits immediately — but its `server.close()` was never called, so any in-flight HTTP request gets its TCP connection RST'd, the client sees `ECONNRESET`, and a downstream service depending on this one sees its own request fail. Worse, if the process was holding a Kafka consumer group partition, the broker doesn't know the consumer died until the session timeout (`session.timeout.ms`, default 10s) elapses — during which no other consumer can pick up the partition, and messages back up. The fix is to always register a SIGTERM handler that calls the framework's shutdown method, with a hard timeout fallback that calls `process.exit(0)` if drain takes too long.

### The Graceful Shutdown sequence

The shutdown sequence is a state machine with five states: RUNNING → DRAINING → EMPTY → CLOSING → EXITED. The transitions are driven by the signal handler and gated by counters (active request count, active consumer count, open connection count). Each transition must complete within a budget; if a transition hangs, the next signal (`SIGKILL`) forces the process to EXITED without going through the intermediate states.

```text
Graceful shutdown state machine (Spring Boot 3.x):

  RUNNING ──── SIGTERM received ────► DRAINING
     │                                   │
     │  accept() loop closed              │  WebServerGracefulShutdownLifecycle
     │  ReadinessProbe starts failing    │  waits for active request count → 0
     │  (K8s stops sending new traffic)  │  up to spring.lifecycle.timeout-per-shutdown-phase
     │                                   │
     │                                   ▼
     │                                 EMPTY
     │                                   │
     │                                   │  SmartLifecycle.stop() called on beans
     │                                   │  in reverse Phase order:
     │                                   │    Phase Integer.MAX_VALUE  (web server)
     │                                   │    Phase 0                  (Kafka consumers)
     │                                   │    Phase Integer.MIN_VALUE  (DB pool)
     │                                   ▼
     │                                 CLOSING
     │                                   │  DataSource closed
     │                                   │  Kafka consumer.unsubscribe()
     │                                   │  Log appender flush
     │                                   ▼
     └─────────────────────────────────► EXITED  (JVM returns 0)

  If at any point the wall-clock exceeds terminationGracePeriodSeconds
  (K8s default 30s), the kernel sends SIGKILL and the JVM is gone
  without further cleanup.
```

The sequence in detail:

1. **Receive SIGTERM.** The JVM's signal handler (`sun.misc.Signal.handle("TERM", ...)` registered by Spring) wakes the `SpringApplication` shutdown hook thread. The hook calls `ConfigurableApplicationContext.close()`, which runs the `SmartLifecycle` beans' `stop()` methods in descending phase order.

2. **Stop accepting new requests.** The `WebServerGracefulShutdownLifecycle` (phase `Integer.MAX_VALUE`) runs first. It calls `WebServer.stop()` which internally calls `server.stop()` on the Tomcat/Jetty/Netty server. This stops the `accept()` loop — no new TCP connections are accepted. Existing connections stay open. The Kubernetes readiness probe (`/actuator/health/readiness`) starts returning 503, and `kube-proxy` removes the pod's endpoint from the Service's endpoint list within ~5s. New traffic stops arriving.

3. **Wait for in-flight requests to complete.** Tomcat's `stop()` waits for all in-flight requests to finish, up to `spring.lifecycle.timeout-per-shutdown-phase=30s`. If a request is still running at the 30s mark, Tomcat forcibly closes the connection — the client gets a 502. This is why your SLO for request latency must be well under the shutdown timeout; a 60s request will be killed at the 30s shutdown timeout.

4. **Stop message consumers.** Spring's Kafka listener container (phase 0, after web) calls `KafkaMessageListenerContainer.stop()`, which calls `consumer.unsubscribe()`, commits the current offset (if `enable.auto.commit=false` and ack-mode is `RECORD` or `BATCH`), and closes the consumer. The broker releases the partition and another consumer in the group picks it up via rebalance.

5. **Close the DataSource.** HikariCP (phase `Integer.MIN_VALUE`) calls `close()` on every pooled connection. Each connection sends a `QUIT` packet to Postgres, which rolls back any open transaction. If the app was mid-transaction, the rollback happens here — but only if the transaction was started; an uncommitted `INSERT` that has not yet executed `commit()` is rolled back, which is the correct behavior (the request that started it should have been aborted in step 3).

6. **Flush logs and exit.** Logback's appender (`AsyncAppender` if used) flushes its queue to the underlying appender (file, syslog, Loki). The JVM's `Runtime.getRuntime().addShutdownHook()` hooks run (any user-registered hooks). The JVM calls `System.exit(0)`.

```yaml
# application.yml — Spring Boot 3.x graceful shutdown config
server:
  shutdown: graceful                                  # enables WebServerGracefulShutdownLifecycle
spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s                   # max wait for in-flight requests
  jpa:
    open-in-view: false                               # don't hold DB session open during view render
management:
  endpoint:
    health:
      probes:
        enabled: true                                  # exposes /actuator/health/readiness and /liveness
  health:
    livenessstate:
      enabled: true
    readinessstate:
      enabled: true
```

```java
// Custom shutdown logic via @PreDestroy — runs during SmartLifecycle.stop()
@Component
@RequiredArgsConstructor
public class KafkaConsumerLifecycle implements SmartLifecycle {

    private final KafkaMessageListenerContainer<String, byte[]> container;
    private volatile boolean running = false;

    @Override
    public void start() {
        container.start();
        running = true;
    }

    @Override
    public void stop() {
        // Container.stop() is graceful: it stops polling, commits the last offset,
        // calls consumer.unsubscribe(), and waits up to poll-timeout for the worker thread.
        container.stop();
        running = false;
    }

    @Override
    public boolean isRunning() { return running; }

    @Override
    public int getPhase() {
        // Run after the web server (Phase MAX_VALUE) but before the DataSource (Phase MIN_VALUE).
        // Web server drains HTTP requests first; consumers stop next; DB pool closes last.
        return 0;
    }
}

// Or via JSR-250 @PreDestroy for simpler cases
@Component
public class AuditLogFlusher {

    private final BufferedWriter auditLog;

    @PreDestroy
    public void flush() throws IOException {
        // Called by Spring during context close, after SmartLifecycle.stop() beans
        // of the same phase but before lower phases. Flush the audit buffer to disk
        // so we don't lose the last few seconds of audit entries.
        auditLog.flush();
        auditLog.close();
    }
}
```

The Kubernetes side of the handshake adds two more pieces: the `preStop` hook and the readiness probe. The `preStop` hook runs **before** the SIGTERM is delivered — K8s executes the hook (a command or HTTP request), and only after the hook returns does K8s send SIGTERM. This is essential for service-mesh and load-balancer propagation: when K8s marks a pod for deletion, it removes the pod from the Endpoints object simultaneously with sending SIGTERM, but `kube-proxy` on each node only updates iptables on its own sync interval (default 5s, configurable via `--iptables-min-sync-period`). If the app catches SIGTERM and immediately stops accepting connections, requests still in flight from `kube-proxy`'s stale iptables rules hit a closed socket. The `preStop: exec: command: ["/bin/sh","-c","sleep 10"]` hook gives `kube-proxy` 10 seconds to converge before SIGTERM reaches the app. This is the single most important shutdown config in K8s, and it's almost always missing in naive deployments.

```yaml
# K8s pod spec with preStop hook + readiness probe + grace period
spec:
  terminationGracePeriodSeconds: 45       # 10s preStop + 30s app drain + 5s slack
  containers:
    - name: api
      image: ghcr.io/acme/payments-api:1.0.142-a3f5c8d
      livenessProbe:
        httpGet: { path: /actuator/health/liveness, port: 8080 }
        periodSeconds: 10
        failureThreshold: 3
      readinessProbe:
        httpGet: { path: /actuator/health/readiness, port: 8080 }
        periodSeconds: 5
        failureThreshold: 1                # one failure and the pod is removed from Service
      lifecycle:
        preStop:
          exec:
            command: ["/bin/sh", "-c", "sleep 10"]
```

The readiness probe is the second half of the K8s handshake. When the app receives SIGTERM, the `WebServerGracefulShutdownLifecycle` makes the readiness endpoint return 503. K8s sees the probe fail and removes the pod from the Service's Endpoints — but again, `kube-proxy` takes 5s to converge. The `preStop: sleep 10` covers both the Endpoints removal propagation and the `kube-proxy` iptables convergence. Once the SIGTERM arrives, the readiness probe failing is the belt-and-suspenders: even if `preStop` was insufficient, the probe failure eventually stops new traffic.

The production failure mode is **requests in flight when SIGKILL arrives**. The classic case: an app with a 30s shutdown timeout deployed with the K8s default `terminationGracePeriodSeconds=30`. The sequence is: K8s sends SIGTERM at t=0, app starts draining, but a slow request (say, a 25s report-generation endpoint) is still running at t=30 when K8s sends SIGKILL. The client gets a 502 and the report is lost. The fix is to size `terminationGracePeriodSeconds` to be longer than your slowest acceptable request — typically `max_request_timeout + 10s`. For a service with a 30s request timeout, set `terminationGracePeriodSeconds=45` and `timeout-per-shutdown-phase=30s`. The second failure mode is the **Kafka rebalance storm**: a consumer that doesn't call `consumer.unsubscribe()` on shutdown keeps its session alive until `session.timeout.ms` (default 10s) elapses; during that window, the partition is "owned" by a dead consumer and no other consumer can read it. With a 30s shutdown timeout, that's 30s of unprocessed messages — and during a rolling deploy of 10 pods, that's 30s × 10 = 5 minutes of effective downtime for the consumer group. The fix is to call `consumer.close()` explicitly in the shutdown hook (Spring Boot's `KafkaMessageListenerContainer` does this automatically) and set `session.timeout.ms` short enough (10–15s) that the broker notices the death quickly.

The third failure mode, specific to Java, is the **JVM shutdown hook ordering**. The JVM runs shutdown hooks in arbitrary order (not registration order, not reverse-registration). If your log flusher hook runs before your DB close hook, the log "Database closed" is lost. Spring's `SmartLifecycle` with explicit `getPhase()` ordering solves this for Spring beans, but user code that registers raw `Runtime.getRuntime().addShutdownHook(Thread)` hooks bypasses Spring's ordering. The fix is to never register raw JVM shutdown hooks in a Spring Boot app — always use `@PreDestroy` or implement `SmartLifecycle` with an explicit phase.

## Key Takeaways

1. **`SIGTERM` is a request, `SIGKILL` is a fact.** A well-behaved app catches SIGTERM and drains; the kernel's SIGKILL after `terminationGracePeriodSeconds` is the backstop that ensures the pod eventually dies. Design the shutdown sequence to complete within `grace_period - 5s` of slack; anything that takes longer will be SIGKILLed mid-drain.
2. **The `preStop: sleep 10` hook is non-negotiable in Kubernetes.** Without it, `kube-proxy`'s 5-second iptables convergence window overlaps with the SIGTERM, and requests that should have gone to a different pod arrive at a pod that's already draining. The 10-second sleep covers the Endpoints propagation and the iptables sync, decoupling the app's drain from the network's convergence.
3. **Order matters: drain HTTP first, then consumers, then DB.** Spring's `SmartLifecycle` phases enforce this: web server at `MAX_VALUE` drains in-flight requests, message listeners at `0` unsubscribe from brokers, connection pools at `MIN_VALUE` close last. A custom bean that closes the DB connection in `@PreDestroy` (default phase `Integer.MAX_VALUE`) will close the pool before the web server has finished draining — every in-flight request that needs a DB connection gets a `SQLException: HikariDataSource has been closed`.
