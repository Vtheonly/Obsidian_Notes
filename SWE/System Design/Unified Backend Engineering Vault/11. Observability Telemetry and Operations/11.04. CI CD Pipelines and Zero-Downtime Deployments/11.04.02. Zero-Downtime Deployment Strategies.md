# 11.04.02. Zero-Downtime Deployment Strategies

## What This Is

Zero-downtime deployment is the set of techniques that replace a running version of a service with a new version without dropping user-visible traffic. It is the operational counterpart to CI: CI produces a verified, immutable artifact; deployment strategies consume that artifact and swap it into production. The "zero-downtime" claim is not magic — it depends on (a) a load balancer that can route traffic away from old instances before they're killed, (b) a graceful shutdown lifecycle that drains in-flight requests (see [[11.04.03. Graceful Shutdown Lifecycles]]), and (c) backward compatibility between old and new versions for the duration of the swap. Any of the three failing produces a 502/504 blip or, worse, corrupted state.

In the layered mental model, deployment strategies sit above the orchestration layer (Kubernetes, Nomad, ECS) and below the application layer. The orchestrator provides the primitives — ReplicaSets, Deployments, Services, Ingress — and the deployment strategy is the recipe for using those primitives to swap versions safely. This note covers the three canonical strategies — rolling, blue-green, canary — and the two cross-cutting problems that apply to all of them: database migrations (which break backward compatibility) and rollback (which is the deployment run in reverse).

## The Details

### **Rolling Deployments**: Sequentially replacing old container instances with new instances behind...

A rolling deployment gradually replaces old pods with new pods, keeping both versions running behind the load balancer for the duration of the rollout. It is the default `Deployment.strategy.type=RollingUpdate` in Kubernetes and the right choice for the 90% case: stateless services with backward-compatible changes. The orchestrator maintains a desired replica count (say, 10) and walks the actual count from 10×v1 toward 10×v2 one pod at a time, never dropping below `maxUnavailable` and never exceeding `maxSurge`.

```yaml
# K8s Deployment with explicit rolling-update strategy
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payments-api
spec:
  replicas: 10
  revisionHistoryLimit: 5           # keep 5 old ReplicaSets for rollback
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 25%                  # up to 12.5 → 13 pods during rollout (ceil(10*1.25))
      maxUnavailable: 25%            # never below 7.5 → 7 pods serving traffic
  minReadySeconds: 30                # a new pod must be Ready for 30s before counting as "available"
  progressDeadlineSeconds: 600       # fail the rollout if not done in 10 min
  selector:
    matchLabels: { app: payments-api }
  template:
    metadata:
      labels: { app: payments-api }
    spec:
      containers:
        - name: api
          image: ghcr.io/acme/payments-api:1.0.142-a3f5c8d   # immutable tag
          ports: [{ containerPort: 8080 }]
          readinessProbe:            # gates whether the pod receives traffic
            httpGet: { path: /actuator/health/readiness, port: 8080 }
            initialDelaySeconds: 5
            periodSeconds: 5
            failureThreshold: 3
          lifecycle:
            preStop:                 # see Graceful Shutdown note
              exec:
                command: ["/bin/sh", "-c", "sleep 10"]
```

The walk is: surge to 13 pods (10 v1 + 3 v2), wait for 3 v2 pods to become Ready (passing `readinessProbe` for `minReadySeconds: 30`), terminate 3 v1 pods (down to 7 v1 + 3 v2 = 10), surge again to 10 v1 + 6 v2, and so on until 0 v1 + 10 v2. The `maxUnavailable: 25%` floor means at least 7 pods are always serving — at peak traffic, that's 70% capacity, which is why you size your replica count for 1.5× peak (so 70% of nominal = ~100% of needed). `maxSurge: 25%` means up to 13 pods exist at once — your cluster must have the capacity for this surge or the rollout stalls.

The two knobs have a tradeoff. High `maxSurge` (e.g., 100%) and `maxUnavailable: 0` gives the fastest rollout (10 v1 + 10 v2 = 20 pods in parallel, swap instantaneously) but requires double the resources during the rollout. High `maxUnavailable` (e.g., 50%) and `maxSurge: 0` uses no extra resources but cuts serving capacity in half during the rollout. The default `25%/25%` is a compromise. For latency-critical services with strict SLOs, use `maxUnavailable: 0` and accept the resource cost.

```text
Rolling update walk (replicas=10, maxSurge=25%=3, maxUnavailable=25%=3):

  Step 0: 10 v1, 0 v2   [Ready=10/10]
  Step 1: 10 v1, 3 v2   [surge to 13; wait for 3 v2 Ready + minReadySeconds]
  Step 2: 7 v1, 3 v2    [terminate 3 v1; available=10/10]
  Step 3: 7 v1, 6 v2    [surge to 13; wait for 3 more v2 Ready]
  Step 4: 4 v1, 6 v2    [terminate 3 v1; available=10/10]
  Step 5: 4 v1, 9 v2    [surge to 13; wait]
  Step 6: 1 v1, 9 v2    [terminate 3 v1]
  Step 7: 0 v1, 10 v2   [terminate last v1; rollout complete]

  Total wall-clock: ~6 × (5s readiness probe + 30s minReadySeconds) ≈ 3.5 minutes
```

The production failure mode is **incompatible versions running side-by-side**. The rolling update keeps v1 and v2 alive simultaneously for the duration of the rollout (3–5 minutes for 10 pods). If v2 changed the JSON schema of a response — say, renamed `user_id` to `userId` — and v1 consumers are reading from a v2 producer, they will silently get `undefined` for `user_id` and produce null-pointer exceptions downstream. The mitigation is **backward compatibility in both directions**: v2 must accept v1's requests and produce v1-compatible responses (forward-compatible writes), and v1 must accept v2's responses (backward-compatible reads). This is the same constraint as expand-and-contract database migrations (see below) applied to API schemas. Enforce it with consumer-driven contract tests in CI: Pact or Spring Cloud Contract tests that assert v1's expectations still hold against v2's responses.

### **Blue-Green Deployments**: Running two identical production environments (Blue = Live, Green = I...

Blue-green runs two complete, identical environments — Blue (currently live, taking 100% of traffic) and Green (idle, taking 0%). Deployment is: provision Green with the new version, run smoke tests against Green with no production traffic, then flip a router/Ingress/weighted-load-balancer rule from Blue to Green. The flip is atomic from the perspective of any new connection — once the router updates, new connections go to Green, existing connections to Blue drain. Rollback is the same operation in reverse: flip back to Blue, which is still alive and idle.

```text
Blue-Green topology:

                  ┌─────────────────┐
   users ─────────►  Router / LB    │
                  │  weight:        │
                  │   blue: 100%    │────► Blue Deployment (v1.4.2)
                  │   green:   0%   │      10 pods, taking all traffic
                  └─────────────────┘
                                    │
                                    └────► Green Deployment (v1.4.3)
                                           10 pods, taking 0 traffic
                                           (smoke tests run here)

  Switch: update Router weights to blue:0%, green:100%
  Atomic from new connections; existing blue connections drain via graceful shutdown.
  Blue pods remain alive (idle) for immediate rollback.
```

The advantage over rolling is **atomicity**: every request goes to either v1 or v2, never a mix. This eliminates the version-compatibility problem entirely. The cost is **double infrastructure**: 20 pods running (10 idle) instead of 10–13 during a rolling update. For a service that costs $50K/year in compute, blue-green doubles that to $100K. For services with strict version-isolation requirements (regulatory, financial transaction processing, A/B testing infrastructure), the cost is justified.

In Kubernetes, blue-green is implemented as two Deployments behind a single Service with a `selector` that flips:

```yaml
# Service selects pods with role=blue (currently v1)
apiVersion: v1
kind: Service
metadata:
  name: payments-api
spec:
  selector:
    app: payments-api
    role: blue        # flip to "green" to swap traffic
  ports: [{ port: 80, targetPort: 8080 }]
---
# Blue Deployment — currently live (v1)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payments-api-blue
spec:
  replicas: 10
  selector: { matchLabels: { app: payments-api, role: blue } }
  template:
    metadata: { labels: { app: payments-api, role: blue } }
    spec:
      containers:
        - name: api
          image: ghcr.io/acme/payments-api:1.0.142-a3f5c8d
---
# Green Deployment — idle, new version (v2)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payments-api-green
spec:
  replicas: 10
  selector: { matchLabels: { app: payments-api, role: green } }
  template:
    metadata: { labels: { app: payments-api, role: green } }
    spec:
      containers:
        - name: api
          image: ghcr.io/acme/payments-api:1.0.143-b7e9d22
```

The flip is `kubectl patch service payments-api -p '{"spec":{"selector":{"role":"green"}}}'` — one API call, atomic, instantly routes all new connections to green. Existing connections to blue pods drain via the graceful shutdown lifecycle. Production-grade blue-green uses an Istio `VirtualService` with weighted destinations (`weight: 100` for blue, `weight: 0` for green) instead of K8s Service selectors, because Istio gives finer control: per-request load balancing, traffic mirroring (send a copy of every request to green without affecting the response), and staged weight changes (100/0 → 90/10 → 50/50 → 0/100) which is the canary pattern.

The production failure mode is **database schema coupling**. Blue and Green share a database. If Green's v2 migrated the `users` table to rename `user_id` to `userId` (a "contract" migration), Blue's v1 is now broken because the column it expects doesn't exist. The flip is atomic at the router layer but the schema change is not atomic at the database layer — once v2 runs its migration, v1 cannot serve traffic. This is why blue-green requires the **expand-and-contract** pattern for schema changes: add the new column (expand, both versions can write), backfill, switch reads to the new column, then drop the old column (contract) only after Blue is decommissioned. See the section on database migration problem below for the full sequence.

### **Canary Deployments**: Routing a tiny percentage of production traffic (1% → 10% → 100%) to the ...

Canary routes a small fraction of production traffic to the new version while the old version continues to serve the majority. If the new version is healthy (error rate and latency within SLO over the observation window), the fraction increases; if unhealthy, traffic returns to 100% old. The name comes from the "canary in a coal mine" — the canary dies first, warning the miners before the toxic gas kills them. The new version is the canary; the production traffic is the warning system.

```text
Canary ramp stages (with SLO gate between each stage):

  Stage 0: 100% v1,   0% v2   [deploy v2, no traffic]
  Stage 1:  99% v1,   1% v2   [hold 5 min; gate: err_rate_v2 < 0.1% AND p99_v2 < 300ms]
  Stage 2:  90% v1,  10% v2   [hold 10 min; gate: same]
  Stage 3:  50% v1,  50% v2   [hold 10 min; gate: same]
  Stage 4:  10% v1,  90% v2   [hold 5 min; gate: same]
  Stage 5:   0% v1, 100% v2   [rollout complete; v1 scaled to 0]

  At each gate, if err_rate_v2 > 0.5% (5x SLO) → auto-rollback to Stage 0.
  Gate evaluation: PromQL query against the canary subset's metrics.
```

The gate between stages is the critical mechanism. Without a gate, canary is just a slow rollout — you find out the new version is broken when it has 100% of traffic and production is on fire. The gate evaluates the new version's metrics (error rate, p99 latency, saturation) against the SLO, and either advances to the next stage or rolls back. The evaluation must be statistical: with 1% of traffic on a 1000 RPS service, that's 10 RPS on the canary, and a single 5xx is a 10% error rate. The gate must distinguish "1 error in 30s, statistical noise" from "real 5% error rate". This is what burn-rate alerts (see [[11.03.03. PromQL and Alerting Engineering]]) solve in the alerting layer; canary gates use the same multi-window comparison at the rollout layer.

```yaml
# Argo Rollouts canary strategy — K8s-native progressive delivery
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: payments-api
spec:
  replicas: 10
  strategy:
    canary:
      canaryService: payments-api-canary       # Service pointing at canary pods
      stableService: payments-api-stable        # Service pointing at stable pods
      trafficRouting:
        istio:
          virtualService:
            name: payments-api-vs
            routes: [primary]
      steps:
        - setWeight: 5
        - pause: { duration: 5m }
        - analysis:                             # SLO gate
            templates:
              - templateName: success-rate
            args:
              - name: service-name
                value: payments-api-canary
        - setWeight: 25
        - pause: { duration: 10m }
        - analysis:
            templates:
              - templateName: success-rate
            args:
              - name: service-name
                value: payments-api-canary
        - setWeight: 50
        - pause: { duration: 10m }
        - setWeight: 100
  selector:
    matchLabels: { app: payments-api }
  template:
    metadata: { labels: { app: payments-api } }
    spec:
      containers:
        - name: api
          image: ghcr.io/acme/payments-api:1.0.143-b7e9d22
---
# AnalysisTemplate — the SLO gate
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: success-rate
spec:
  args:
    - name: service-name
  metrics:
    - name: success-rate
      interval: 30s
      count: 10            # 10 evaluations × 30s = 5 min observation window
      successCondition: result[0] >= 0.995
      failureLimit: 2      # 2 failing evaluations out of 10 → rollback
      provider:
        prometheus:
          address: http://prometheus.monitoring:9090
          query: |
            sum(rate(http_requests_total{service="{{args.service-name}}",status!~"5.."}[2m]))
            /
            sum(rate(http_requests_total{service="{{args.service-name}}"}[2m]))
```

The two failure modes here are **ramp-too-fast** (5% → 50% in one step, missing the regression that only manifests at 30% load) and **gate-too-loose** (success rate threshold of 0.99 catches nothing because production is normally 0.9995 and 0.99 looks "fine"). The first is mitigated by following the 1/10/50/90/100 ramp with at least 5 minutes per stage; the second by setting the gate threshold to the SLO (0.999 for a 99.9% SLO service), not to a round number that "feels right". The third failure mode is **session affinity breaking canary**: a sticky-session load balancer sends the same user to v2 every request, so the 1% canary is actually 100% of one user's traffic — if that user happens to be the one who exercises the bug, the canary looks 100% broken; if no canary user exercises the bug, the canary looks 100% healthy. The fix is hash-based load balancing without stickiness, or running the canary analysis on per-request metrics rather than per-user.

**The Database Migration Problem — Expand-and-Contract.** The single hardest cross-cutting problem in zero-downtime deployment is the shared database. Blue and Green (or v1 and v2 in a rolling update) share a database, and any schema change must be safe for both versions to use simultaneously. The naive approach — `ALTER TABLE users DROP COLUMN user_id` — breaks v1 immediately because v1's queries reference `user_id`. The correct approach is **expand-and-contract** (also called parallel-change or backward-compatible migrations):

```text
Expand-and-contract sequence for renaming `user_id` to `userId`:

  Phase 0 (v1 only):      users(user_id, name, email)
                          v1 reads/writes user_id

  Phase 1 — EXPAND:       ALTER TABLE users ADD COLUMN userId BIGINT;
                          v2 deploy:
                            - reads user_id (falls back)
                            - writes BOTH user_id AND userId (dual-write)
                          v1 still reads/writes user_id (unaffected)
                          Backfill: UPDATE users SET userId = user_id WHERE userId IS NULL;

  Phase 2 — SWITCH:       v2 reads userId (primary), still writes both
                          v1 still reads user_id (still works because v2 dual-writes)

  Phase 3 — DECOM v1:     v1 scaled to 0. No traffic to v1.

  Phase 4 — CONTRACT:     ALTER TABLE users DROP COLUMN user_id;
                          v2.1 deploy (only reads/writes userId)
                          Migration complete.
```

Each phase is a separate deploy. Phase 1 (expand) must be backward-compatible: adding a nullable column with no default is safe on Postgres 11+ (no table rewrite, takes milliseconds even on a 1B-row table); adding a NOT NULL column with a default requires either `ADD COLUMN ... DEFAULT ... NOT NULL` (Postgres 11+ handles this in metadata, no rewrite) or a multi-step `ADD COLUMN nullable → backfill → ALTER COLUMN SET NOT NULL` (the safe pattern for MySQL which still rewrites the table). Phase 4 (contract) must happen only after v1 is fully decommissioned — running `DROP COLUMN` while v1 still serves traffic will crash every v1 query. The two-phase window between expand and contract can be days or weeks — long enough to be sure v1 is fully drained. This is why deployment strategies and migrations are coupled: a blue-green deploy of v2 with a contract migration baked in will fail at the flip, because the contract runs immediately on v2 startup and breaks v1. The migration must be a separate deploy from the v2 code deploy, sequenced as: deploy expand migration → deploy v2 with dual-write → drain v1 → deploy contract migration → deploy v2.1 with single-write. The production failure mode is the **big-bang migration**: a single `ALTER TABLE` that locks the table for 30 minutes during "the deploy window", which works fine until the table is 500M rows and the lock takes 6 hours, during which the service is down. The fix is to never run a schema-changing migration during a deploy; run migrations as separate, online operations using tools like `pg-osc` (Postgres online schema change), `gh-ost` (MySQL online schema change), or `pt-online-schema-change`. These tools create a shadow table, copy rows in batches with triggers capturing concurrent writes, and atomic-rename at the end. The application is unaware of the migration; the table is always available for reads and writes.

**The Rollback Problem.** Rollback is the deployment run in reverse: replace the broken v2 with the known-good v1. Each strategy has a different rollback cost. **Rolling**: `kubectl rollout undo deployment/payments-api` reverts to the previous ReplicaSet, walking 10 v2 → 10 v1 one pod at a time — same 3–5 minute rollout, same graceful-shutdown requirement. **Blue-green**: flip the router back to Blue, which is still alive — instant rollback, but Blue has been idle for the entire v2 production window; if the database schema moved forward (expand migration ran), Blue may not work against the new schema. **Canary**: ramp the canary weight back to 0% — instant for traffic, but the canary pods are now scaling down and the stable pods are scaling back up, taking 1–2 minutes.

The universal rollback anti-pattern is **roll forward, not back**. When v2 is broken in production at 02:00, the temptation is to push a v2.1 fix rather than roll back to v1, because rolling back "feels like defeat". This is wrong. Roll forward requires: write the fix → CI pipeline (15 min) → artifact build (5 min) → deploy (5 min) → verify. That's 25 minutes of broken production. Rollback is `kubectl rollout undo` — 3 minutes. Always roll back first, then write the fix at a sane hour.

```bash
# Rollback commands by strategy
# Rolling (K8s Deployment):
kubectl rollout undo deployment/payments-api
kubectl rollout status deployment/payments-api   # watch the rollback progress

# Blue-green (Service selector flip):
kubectl patch service payments-api -p '{"spec":{"selector":{"role":"blue"}}}'

# Canary (Argo Rollouts):
kubectl argo rollouts abort rollout/payments-api
kubectl argo rollouts undo rollout/payments-api

# Force-rollback to a specific revision (disaster recovery):
kubectl rollout undo deployment/payments-api --to-revision=3
```

The hardest rollback problem is the **irreversible migration**. If v2 ran a contract migration (`DROP COLUMN user_id`) and you roll back to v1, v1 cannot read the table — the column it expects no longer exists. The expand-and-contract pattern exists precisely to prevent this: contract migrations are deferred until v1 is fully decommissioned, so rolling back to v1 is always safe (the expand migration added columns v1 ignores, but v1 still works). If you're in a situation where a contract migration has run and you need to roll back, you must restore the dropped column from a backup — a multi-hour operation. This is why the rule is "never contract in the same deploy as the code that needs the contract".

## Key Takeaways

1. **Rolling is the default; canary is the safety net; blue-green is for strict isolation.** Most services should use rolling (it's free, it works, the backward-compatibility cost is manageable). Services with strict SLOs (payments, auth) should use canary with SLO gates. Services that need atomic version switches (regulatory, A/B testing) should use blue-green and accept the double-infrastructure cost.
2. **Schema migrations are not part of the deploy.** Expand-and-contract splits every breaking schema change into 4 phases across multiple deploys. The contract phase (DROP COLUMN) must happen only after the old version is fully drained, which can be days after the new version went live. Never bundle a migration with the code deploy that needs it.
3. **Rollback first, fix forward later.** `kubectl rollout undo` takes 3 minutes; a fix-forward cycle takes 25. Production is broken either way; the question is how long. The exception is when rollback is impossible because a contract migration already ran — which is why you never contract in the same deploy as the code.
