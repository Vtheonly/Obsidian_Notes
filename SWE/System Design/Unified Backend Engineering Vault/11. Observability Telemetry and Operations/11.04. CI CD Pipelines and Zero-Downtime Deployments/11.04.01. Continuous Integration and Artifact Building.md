# 11.04.01. Continuous Integration and Artifact Building

## What This Is

Continuous Integration (CI) is the practice of merging every developer's working copy into a shared mainline branch at high frequency — typically multiple times per day — and running an automated pipeline of checks against each merge candidate. The "I" in CI is the integration: a build server proves that your commit compiles, passes tests, and doesn't break the existing codebase before it lands on `main`. Artifact building is the second half of the same pipeline: once a commit is verified, the CI system produces a **deterministic, immutable artifact** — a container image, a JAR, a wheel, a tarball — tagged with a content hash or a semantic version, and pushes it to a registry. That artifact is the unit of deployment; what runs in production is exactly what CI built, nothing else.

In the layered mental model, CI sits above the version control layer (git) and below the continuous delivery layer (see [[11.04.02. Zero-Downtime Deployment Strategies]]). It bridges the human activity of writing code with the operational activity of running code. The artifact produced by CI is what travels through staging → canary → production; the deployment strategies in the next note operate on artifacts, not on source code. The graceful shutdown lifecycle in [[11.04.03. Graceful Shutdown Lifecycles]] is what makes the deployment strategies actually zero-downtime — CI alone cannot deliver zero-downtime; it can only produce a verified artifact that the deployment layer replaces the old one with.

## The Details

### Automated validation pipelines: Linting, Type Checking, Unit Tests, Integration Tests (Testcontai...

A CI pipeline is a directed acyclic graph (DAG) of jobs, each running in an ephemeral container on a CI runner. The pipeline triggers on a git event — push to a branch, push to `main`, tag creation, pull request open — and walks the DAG in dependency order. The shape of the DAG matters: jobs that can run in parallel (lint, type-check, unit tests) should; jobs that depend on prior outputs (integration tests depend on a built artifact) run serially after their upstream completes. Most production pipelines have 6–10 stages: checkout → lint → compile → unit test → build artifact → integration test → security scan → publish.

The validation stages enforce correctness at different layers. **Linting** (ESLint for TypeScript, Ruff for Python, SpotBugs for Java) catches style and anti-pattern violations cheaply — sub-second per file, no compilation needed. **Type checking** (tsc for TypeScript, mypy for Python, javac for Java) catches type errors that would have become runtime exceptions; `tsc --noEmit` runs the full type checker without emitting JavaScript, taking 10–60 seconds on a large codebase. **Unit tests** (Jest, pytest, JUnit) run in-process against the code under test with mocks for external dependencies, completing in seconds to minutes. **Integration tests** (Testcontainers for Java/Python/JS, Docker Compose for end-to-end) spin up real databases, message brokers, and HTTP services in ephemeral containers and verify the system behaves correctly against them — these take minutes and need Docker-in-Docker or a remote Docker socket on the runner.

```yaml
# .github/workflows/ci.yml — Spring Boot service CI pipeline
name: CI
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

permissions:
  contents: read
  packages: write
  id-token: write   # for OIDC to AWS/GCP

jobs:
  lint-and-test:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_PASSWORD: test
        ports: ['5432:5432']
        options: >-
          --health-cmd pg_isready
          --health-interval 5s
          --health-timeout 5s
          --health-retries 5
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0   # for git-based versioning
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'
          cache: maven

      # 1. Compile — fails fast on type errors
      - name: Compile
        run: ./mvnw -B -q -DskipTests compile

      # 2. Lint / static analysis (SpotBugs + Checkstyle + PMD via spotless)
      - name: Static analysis
        run: ./mvnw -B -q checkstyle:check spotbugs:check

      # 3. Unit tests — fast, in-process, mocked deps
      - name: Unit tests
        run: ./mvnw -B -q test

      # 4. Integration tests — Testcontainers spins up Postgres + Kafka
      - name: Integration tests
        run: ./mvnw -B -q verify -Pintegration
        env:
          TESTCONTAINERS_RYUK_DISABLED: 'false'

  security-scan:
    runs-on: ubuntu-latest
    needs: lint-and-test
    steps:
      - uses: actions/checkout@v4
      - name: Trivy SCA — vulnerable dependencies
        uses: aquasecurity/trivy-action@master
        with:
          scan-type: fs
          scan-ref: .
          severity: CRITICAL,HIGH
          exit-code: '1'
      - name: CodeQL SAST — SQL injection / path traversal
        uses: github/codeql-action/init@v3
        with:
          languages: java
      - uses: github/codeql-action/analyze@v3

  build-and-publish:
    runs-on: ubuntu-latest
    needs: [lint-and-test, security-scan]
    if: github.ref == 'refs/heads/main'
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'
          cache: maven
      - name: Set version from git short SHA
        run: |
          SHA=$(git rev-parse --short HEAD)
          ./mvnw -B versions:set -DnewVersion=1.0.${{ github.run_number }}-$SHA -DprocessAllModules
      - name: Build container image (no daemon, Jib)
        run: ./mvnw -B -q -DskipTests com.google.cloud.tools:jib-maven-plugin:build -Dimage=ghcr.io/acme/payments-api:${{ github.run_number }}-$(git rev-parse --short HEAD)
      - name: Sign image with cosign (keyless, OIDC)
        run: |
          cosign sign --yes ghcr.io/acme/payments-api:${{ github.run_number }}-$(git rev-parse --short HEAD)
```

Each stage has a specific failure-mode it exists to catch. Lint catches the `unused import` / `var instead of const` noise that would otherwise dominate code review. Type-checking catches the `Cannot read property 'foo' of undefined` class of bug that no amount of unit tests will surface. Unit tests catch the algorithmic bug in `calculateTax(order)` that returns -0.5 for a zero-quantity order line. Integration tests with Testcontainers catch the "this JPA `@OneToMany` mapping produces an N+1 query that locks the table for 30 seconds under load" bug — a class of bug that requires a real Postgres to manifest because Hibernate's behavior depends on dialect-specific SQL generation. Security scanning (SAST = static application security testing on source; SCA = software composition analysis on dependencies) catches the `org.apache.logging.log4j:log4j-core:2.14.0` CVE-2021-44228 vulnerability before it ships — and the SQL injection via string concatenation that no type checker will ever flag.

The choice of CI platform affects the pipeline shape. GitHub Actions (used above) uses YAML workflow files in `.github/workflows/`, free for public repos, $0.008/minute for Linux runners on private repos. GitLab CI uses `.gitlab-ci.yml` and shines for self-hosted runners behind a corporate firewall. Jenkins is the legacy choice — a Jenkinsfile groovy pipeline running on a Jenkins controller with N executors — and is still common in regulated industries because of its audit log and plugin ecosystem. CircleCI uses `.circleci/config.yml` with a focus on parallelism and Docker-in-Docker performance. The pipeline DAG is conceptually identical across all four; the syntax differs. The crucial invariant: the pipeline must be **declarative and version-controlled**. A pipeline that lives in a Jenkins UI is not reproducible, cannot be code-reviewed, and silently drifts as operators tweak it.

The production failure mode is **tests that don't actually test**. The most common shape is the integration test that runs against an H2 in-memory database instead of real Postgres — it passes in CI, then production blows up because H2 accepts `BOOLEAN` columns that Postgres rejects, or H2 doesn't enforce foreign keys by default while Postgres does. The second shape is the unit test with `verify(mockRepository).save(any())` — it asserts that `save()` was called, but not what was saved, so a refactor that swaps two fields passes the test and breaks production. The third shape is the SAST scan configured to `continue-on-error: true` so the pipeline doesn't fail on findings — a compliance theater that produces PDF reports nobody reads. The fix for all three is to enforce that the CI pipeline fails the build on any test failure or CRITICAL CVE, and to periodically (monthly) re-run the full integration suite against staging with real traffic replayed.

### Deterministic artifact publishing: Pushing immutable tagged container images to private registries

A build artifact is the immutable output of a CI pipeline. The artifact encapsulates the compiled code, its dependencies, its runtime, and its configuration — everything needed to run the service, frozen at a single point in time. The artifact is what gets deployed; the source code is not. This separation is what makes rollback possible (deploy the previous artifact), what makes audit possible (which artifact is running in prod right now?), and what makes reproducibility possible (redeploy the same artifact in staging and you should see the same behavior).

The artifact format depends on the ecosystem. **Container images** (OCI images, the format standardized after Docker) are the universal choice for polyglot microservices — they encapsulate the JVM, the Node.js runtime, the Python interpreter, and the application code in one immutable tarball. **JAR files** are still used for in-JVM libraries (Maven Central). **Wheels** are the Python equivalent (PyPI). **npm packages** for JavaScript libraries. **Helm charts** for Kubernetes manifests. **Terraform modules** for infrastructure. The pattern is the same in every case: build once, tag with a version, push to a registry, deploy from the registry.

The two pieces that make artifact publishing deterministic are **(a) the build is reproducible** (same commit → same artifact byte-for-byte) and **(b) the artifact is content-addressed** (the tag uniquely identifies the content). For container images, (b) means using the git SHA or a content hash as the tag, not `latest`. `latest` is a moving target — `ghcr.io/acme/api:latest` is a different image today than yesterday, and there's no way to know which one is running. `ghcr.io/acme/api:1.0.142-a3f5c8d` is immutable — once pushed, it never changes, and you can prove in an audit that production is running exactly that image.

```yaml
# Two-tag strategy: deploy with the immutable SHA tag, also tag latest for humans
- name: Build and push image
  uses: docker/build-push-action@v5
  with:
    context: .
    push: true
    tags: |
      ghcr.io/acme/payments-api:1.0.${{ github.run_number }}
      ghcr.io/acme/payments-api:1.0.${{ github.run_number }}-${{ github.sha }}
      ghcr.io/acme/payments-api:latest
    cache-from: type=gha
    cache-to: type=gha,mode=max
    provenance: true
    sbom: true

# Promote image across environments by re-tagging (no rebuild)
- name: Promote to staging
  if: github.ref == 'refs/heads/main'
  run: |
    IMAGE=ghcr.io/acme/payments-api:1.0.${{ github.run_number }}-${{ github.sha }}
    cosign verify --certificate-identity https://github.com/acme/payments-api/.github/workflows/ci.yml@refs/heads/main \
                  --certificate-oidc-issuer https://token.actions.githubusercontent.com $IMAGE
    crane cp $IMAGE ghcr.io/acme/payments-api:staging
```

**Semantic versioning** (SemVer) is the convention for human-readable version tags: `MAJOR.MINOR.PATCH`. A `1.4.2` tag means: API-compatible with `1.4.0` (MINOR bump added features), with a backwards-compatible bug fix over `1.4.1` (PATCH bump). For services with no public API contract (most internal microservices), the SemVer discipline is loose — teams use `1.0.<build_number>-<git_sha>` as the canonical tag, with `latest`, `main`, `staging`, `prod` as floating aliases. The aliases move; the canonical tag is immutable. A git tag (`git tag v1.4.2 && git push --tags`) is the source-of-truth trigger for a release: the CI pipeline runs on tag creation, builds an artifact tagged `v1.4.2`, and that artifact is what gets deployed. This makes the release a first-class git operation: `git log v1.4.1..v1.4.2` shows exactly what changed between releases.

The choice of registry affects operational characteristics. **Docker Hub** is the public default but has aggressive rate limits (100 pulls/6h anonymous, 200 authenticated) that will break a Kubernetes cluster pulling images on pod startup. **GitHub Container Registry (GHCR)** is integrated with GitHub Actions and OIDC, free for public images, $0.10/GB-month for private. **AWS ECR** is the choice for EKS-deployed services — integrated with IAM, no rate limits, $0.10/GB-month. **GCP Artifact Registry** (replacing GCR) is the GKE equivalent. **JFrog Artifactory** and **Sonatype Nexus** are self-hosted for regulated environments where images must not leave the corporate network. The crucial operational detail: configure image retention policies. A service that builds 50 times/day produces 18,000 images/year; without a `lifecycle policy` deleting untagged images older than 30 days, you'll pay for terabytes of stale images and your registry will become unsearchable.

```bash
# ECR lifecycle policy — keep last 30 tagged images per service, delete untagged after 7 days
cat > lifecycle.json <<'EOF'
{
  "rules": [
    {
      "rulePriority": 1,
      "description": "Keep last 30 tagged images",
      "selection": {
        "tagStatus": "tagged",
        "tagPrefixList": ["v", "1.0.", "2.0."],
        "countType": "imageCountMoreThan",
        "countNumber": 30
      },
      "action": { "type": "expire" }
    },
    {
      "rulePriority": 2,
      "description": "Delete untagged images after 7 days",
      "selection": {
        "tagStatus": "untagged",
        "countType": "sinceImagePushed",
        "countUnit": "days",
        "countNumber": 7
      },
      "action": { "type": "expire" }
    }
  ]
}
EOF
aws ecr put-lifecycle-policy --repository-name payments-api --lifecycle-policy-text file://lifecycle.json
```

The production failure mode is the **`latest` tag in production**. Kubernetes Deployment referencing `image: ghcr.io/acme/api:latest` will silently pull a new image on every pod restart, with no audit trail of which version is running, no rollback path, and no way to reproduce a bug ("works on my machine" because the local `:latest` differs from the production `:latest` from yesterday). The fix is a hard policy: deployments must reference immutable tags, enforced by an admission webhook like Kyverno that rejects any pod spec with `image: *:latest`. The second failure mode is **building the artifact outside CI** — a developer runs `docker build -t ghcr.io/acme/api:v1.4.2 .` on their laptop, pushes it, and that's what runs in prod. The artifact was not built by CI, was not scanned, was not signed, and may differ from the CI-built artifact for the same commit because of different local state (different `.env`, different `node_modules` cache, different build-arg). The fix is the same Kyverno policy: require images to be signed by the CI system's OIDC identity, reject unsigned images at admission. This is supply-chain security — see SLSA (Supply-chain Levels for Software Artifacts) level 3 for the full framework.

## Key Takeaways

1. **The pipeline is a DAG, not a script.** Lint, type-check, and unit tests run in parallel; integration tests run after a successful build; security scans run in parallel with integration tests; publishing is gated on all of the above. Each stage exists to catch a specific class of bug at the cheapest possible layer.
2. **Artifacts are immutable and content-addressed.** Deploy `ghcr.io/acme/api:1.0.142-a3f5c8d`, never `:latest`. Promotion across environments is `crane cp` (a tag copy), not a rebuild — the artifact that passed staging is the artifact that runs in production, byte-for-byte.
3. **Testcontainers over H2.** Integration tests against in-memory fakes pass in CI and fail in production because the fake doesn't enforce the same constraints as the real database. Testcontainers spins up a real Postgres/Kafka/Redis in seconds per test class; the cost is 30 extra seconds of CI time, the benefit is catching the N+1 query and the foreign-key violation before they reach staging.
