# 01.02.04. Bootstrapping a Bare-Metal Spring Boot Application

## What This Is

This is the anchor note for sub-section 01.02 — the place where the JVM toolchain comes together into a running HTTP service. We bootstrap a Spring Boot application from scratch: generate the project with Spring Initializr, walk the `@SpringBootApplication` annotation that bootstraps the application context, write a `/health` REST controller that returns structured JSON, and attach the JDWP remote-debug agent so an IDE can attach to the running process. The result is a 50-line Java application that, when built with `mvn package` and run with `java -jar`, listens on port 8080 and answers `GET /health` with `{"status":"UP"}` — the minimum viable backend service. Every subsequent anchor note in this vault assumes you can produce and run this baseline.

Spring Boot is the anchor stack for the vault because it is the most explicit, most heavily-instrumented, and most production-battle-tested of the four ecosystems. The component-scan mechanism, the auto-configuration pipeline, the actuator metrics endpoint, and the JDWP integration are all things every backend framework has an equivalent of — but Spring makes them visible. Once you can read `@SpringBootApplication` and know what it triggers, the equivalent annotations in Express (`app.use`), Django (`INSTALLED_APPS`), and Laravel (the `Application` bootstrap in `bootstrap/app.php`) become legible.

## The Details

### Generating a production-ready application using Spring Initializr (Web, JPA, Actuator dependencies)

Spring Initializr (`start.spring.io`) is a web-based project generator that produces a zip containing a Maven or Gradle project skeleton with the dependencies you selected pre-wired into the `pom.xml` or `build.gradle.kts`. It is also available as a CLI (`curl https://start.spring.io/starter.zip -d dependencies=web,actuator -o myapp.zip`) and as an IntelliJ wizard. The dependencies you select determine which Spring Boot starters get added to your build, which in turn determine which auto-configurations fire at application startup.

For this anchor, we will select three dependencies:

- **Spring Web** (`spring-boot-starter-web`) — pulls in an embedded Tomcat HTTP server, Spring MVC, Jackson for JSON serialization, and the `@RestController`/`@GetMapping`/`@PostMapping` annotations. This is what makes the application an HTTP service.
- **Spring Data JPA** (`spring-boot-starter-data-jpa`) — pulls in Hibernate, Spring Data JPA repositories, and the JPA API. We will not use it in this note's `/health` endpoint, but it is included because every subsequent anchor note in section 06 expects it on the classpath.
- **Spring Boot Actuator** (`spring-boot-starter-actuator`) — pulls in the `/actuator/health`, `/actuator/metrics`, `/actuator/info`, `/actuator/env` endpoints and the Micrometer metrics registry. This is what makes the application observable in production.

```bash
# Generate the project via curl
curl https://start.spring.io/starter.zip \
  -d type=maven-project \
  -d language=java \
  -d bootVersion=3.3.0 \
  -d baseDir=myapp \
  -d groupId=com.example \
  -d artifactId=myapp \
  -d name=myapp \
  -d packageName=com.example.myapp \
  -d javaVersion=21 \
  -d dependencies=web,data-jpa,actuator \
  -o myapp.zip

unzip myapp.zip
cd myapp

# Project layout
# myapp/
# ├── pom.xml
# ├── mvnw, mvnw.cmd              ← Maven wrapper (no need for global mvn install)
# ├── .mvn/wrapper/maven-wrapper.properties
# └── src/
#     ├── main/
#     │   ├── java/com/example/myapp/
#     │   │   └── MyappApplication.java   ← entry point
#     │   └── resources/
#     │       └── application.properties  ← config
#     └── test/
#         └── java/com/example/myapp/
#             └── MyappApplicationTests.java
```

The Maven wrapper (`mvnw`) is a script that downloads the exact Maven version specified in `.mvn/wrapper/maven-wrapper.properties` on first run. This means anyone who clones the repo can build it without installing Maven globally — `./mvnw package` works on a fresh checkout. The same pattern exists for Gradle (`gradlew`). Always use the wrapper in version control; never rely on a globally-installed build tool.

The generated `pom.xml` has the `spring-boot-starter-parent` as its parent, which sets Java 21 as the default, sets UTF-8 encoding, imports the Spring Boot BOM (Bill of Materials), and configures the `spring-boot-maven-plugin` to repackage the jar into a fat jar during `mvn package`. The dependencies you selected appear in the `<dependencies>` block:

```xml
<dependencies>
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
  </dependency>
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-jpa</artifactId>
  </dependency>
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
  </dependency>
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-test</artifactId>
    <scope>test</scope>
  </dependency>
</dependencies>
```

Note the absence of `<version>` tags — these are inherited from the BOM. The BOM pins every Spring-managed dependency to a version known to work together, so you cannot accidentally pick incompatible versions of `spring-core` and `spring-web`. The BOM is the Maven equivalent of a lockfile for Spring's own dependencies; you still need `<dependencyManagement>` for non-Spring dependencies like Jackson or your database driver.

The production failure mode here is "starter sprawl". Spring Initializr lists ~60 dependencies, and the temptation is to check every box you might need. Each starter pulls in 5–20 transitive dependencies, and a project with 15 starters ends up with a 200 MB fat jar, a 30-second startup time, and mysterious auto-configurations firing for features you never use. The discipline is to start with `web` and `actuator`, add others only when you have a concrete use case, and use `mvn dependency:tree | grep spring-boot-starter` to audit which starters are present. Spring Boot also logs every auto-configuration decision at startup under the `--debug` flag (it prints a `CONDITIONS EVALUATION REPORT` showing which `@Conditional*` annotations matched and which did not) — this is the primary tool for diagnosing "why did this bean get created".

The actuator starter (`spring-boot-starter-actuator`) deserves a closer look because it is what makes the application observable in production. It auto-configures a set of HTTP and JMX endpoints under `/actuator/**`, each backed by a Spring `@Endpoint`-annotated bean. The default endpoints include `health` (liveness probe — aggregates `HealthIndicator` beans for DB, disk, ping), `info` (build metadata — group, artifact, version, git commit via `git-commit-id-plugin`), `metrics` (Micrometer registry listing `jvm.memory.used`, `http.server.requests`, `process.cpu.usage`, `executor.pool.size`), `env` (every `Environment` property, with secret masking via `Sanitizer`), `loggers` (view and POST-change log levels at runtime — `POST /actuator/loggers/com.example {"configuredLevel":"DEBUG"}`), `threaddump` (every thread's stack trace), `heapdump` (HPROF binary, multi-MB), and `prometheus` (when `micrometer-registry-prometheus` is on the classpath — emits the Prometheus text exposition format). By default only `health` and `info` are exposed over HTTP; the rest are JMX-only.

```text
  Endpoint              HTTP default   JMX default   Production posture
  ─────────────────────────────────────────────────────────────────────────
  /actuator/health      exposed        exposed       Liveness + readiness probes
  /actuator/info        exposed        exposed       Build/git metadata for dashboards
  /actuator/metrics     hidden         exposed       Use /metrics/{name} for specific value
  /actuator/env         hidden         exposed       DANGEROUS — leaks secrets even with masking
  /actuator/loggers     hidden         exposed       Runtime log level changes (POST)
  /actuator/threaddump  hidden         exposed       Use jstack or jcmd in prod instead
  /actuator/heapdump    hidden         exposed       200 MB download, pauses JVM — use jmap
  /actuator/prometheus  hidden         hidden        Expose over HTTP for Prometheus scrape
  /actuator/health/liveness   exposed   n/a      Kubernetes livenessProbe
  /actuator/health/readiness  exposed   n/a      Kubernetes readinessProbe
```

The `management.endpoints.web.exposure.include=*` property exposes everything (convenient for dev, dangerous in prod — `/env` leaks secrets even with masking, `/heapdump` is a 200 MB download that pauses the JVM). The production discipline is to expose `health,info,prometheus` over HTTP, gate `/actuator/**` behind Spring Security with `ROLE_ADMIN`, and use the health groups added in Spring Boot 2.3 — `/actuator/health/liveness` and `/actuator/health/readiness` — for Kubernetes probes. Splitting liveness from readiness is what prevents a flapping DB from getting the pod killed: liveness reports only "the JVM is up", readiness reports "the DB pool is initialised and the message queue is reachable".

### Anatomy of `@SpringBootApplication`: Component scanning, auto-configuration, and configuration property binding

The entry-point class generated by Spring Initializr is three lines of code with one annotation:

```java
package com.example.myapp;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class MyappApplication {
    public static void main(String[] args) {
        SpringApplication.run(MyappApplication.class, args);
    }
}
```

The `@SpringBootApplication` annotation is a meta-annotation that combines three features:

1. **`@Configuration`** — marks this class as a source of bean definitions. Methods annotated with `@Bean` inside this class (or any class annotated with `@Configuration`) are invoked by Spring at startup, and their return values are registered as singletons in the application context.
2. **`@EnableAutoConfiguration`** — triggers Spring Boot's auto-configuration pipeline. Every jar on the classpath that contains a `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` file is scanned, and the auto-configuration classes listed there are evaluated. Each one is annotated with `@Conditional*` annotations (`@ConditionalOnClass`, `@ConditionalOnBean`, `@ConditionalOnMissingBean`, `@ConditionalOnProperty`) that determine whether it fires. For example, `DispatcherServletAutoConfiguration` fires only if `spring-boot-starter-web` is on the classpath (because it requires the `DispatcherServlet` class); `DataSourceAutoConfiguration` fires only if a JDBC driver is present and no `DataSource` bean has been manually defined.
3. **`@ComponentScan`** — tells Spring to scan the package of the annotated class (`com.example.myapp`) and all sub-packages for classes annotated with `@Component`, `@Service`, `@Repository`, `@Controller`, `@RestController`, `@Configuration`, and a few others. Each found class is instantiated as a singleton bean and added to the application context.

The `SpringApplication.run()` call bootstraps the context: it creates a `SpringApplication` instance, reads the command-line args, sets up the environment (system properties + environment variables + `application.properties`/`application.yml`), creates the `AnnotationConfigServletWebServerApplicationContext`, runs the component scan, runs the auto-configuration, refreshes the context (which is when `@PostConstruct` methods and `InitializingBean.afterPropertiesSet()` callbacks fire), starts the embedded Tomcat server on port 8080, and registers the JVM shutdown hook so `SIGTERM` triggers a graceful shutdown.

```text
  SpringApplication.run(MyappApplication.class, args)
      │
      ▼
  new SpringApplication(primarySource)            ← primary source = MyappApplication.class
      │
      ▼
  SpringApplication.run(args)
      │
      ▼
  prepareEnvironment()                           ← reads application.properties, env vars, CLI args
      │                                            resolves ${...} placeholders
      ▼
  createApplicationContext()                     ← AnnotationConfigServletWebServerApplicationContext
      │
      ▼
  refreshContext()                               ← the big one:
      │                                            1. Component scan → discovers @RestController, @Service...
      │                                            2. Auto-configuration → @ConditionalOnClass decides what fires
      │                                            3. Bean instantiation → constructor injection, @Autowired
      │                                            4. @PostConstruct / InitializingBean callbacks
      │                                            5. Embedded Tomcat starts on port 8080
      │                                            6. ApplicationRunner / CommandLineRunner beans run
      ▼
  afterRefresh()                                 ← logs "Started MyappApplication in 2.347 seconds"
      │
      ▼
  returns SpringApplicationRunListener context  ← application is live
```

Configuration property binding is the third mechanism `@SpringBootApplication` enables. Properties in `application.properties` are bound to typed beans via `@ConfigurationProperties`. For example:

```properties
# application.properties
myapp.greeting=Hello
myapp.features.feature-a.enabled=true
myapp.features.feature-b.enabled=false
```

```java
@ConfigurationProperties(prefix = "myapp")
public record MyAppProperties(
    String greeting,
    Map<String, Feature> features
) {
    public record Feature(boolean enabled) {}
}
```

Spring Boot's `@ConfigurationPropertiesBinding` mechanism uses the `Binder` API to walk the property tree, coerce types (string → boolean, string → int, string → `Duration` with `Pt30s` syntax, string → `List<String>` with comma separator), and validate against `@Validated` constraints. This is the type-safe alternative to `@Value("${myapp.greeting}")` injection, which gives you a raw string with no validation and no IDE refactoring support.

The failure mode that the `@SpringBootApplication` mechanism produces is the "auto-configuration surprise". A developer adds `spring-boot-starter-data-jpa` to a service that does not actually need a database, and the application refuses to start with `Failed to determine a suitable driver class`. The reason is that `DataSourceAutoConfiguration` fires (because the JPA starter is on the classpath), tries to construct a `DataSource`, and fails because no `spring.datasource.url` property is set. The fix is either to exclude the auto-configuration explicitly with `@SpringBootApplication(exclude = {DataSourceAutoConfiguration.class, HibernateJpaAutoConfiguration.class})` or to add the datasource property. The general lesson is: every starter on the classpath activates an auto-configuration, and you must know which ones.

### Writing and executing a minimal REST Controller endpoint (`/health`) returning structured JSON

The Spring Boot actuator already provides a `/actuator/health` endpoint, but for this anchor we will write our own `/health` endpoint to demonstrate the controller layer. A Spring MVC REST controller is a class annotated with `@RestController` (which combines `@Controller` and `@ResponseBody`) that contains methods annotated with HTTP-verb mappings:

```java
// src/main/java/com/example/myapp/health/HealthController.java
package com.example.myapp.health;

import java.time.Instant;
import java.util.Map;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class HealthController {

    @GetMapping("/health")
    public Map<String, Object> health() {
        return Map.of(
            "status", "UP",
            "timestamp", Instant.now().toString(),
            "version", "1.0.0"
        );
    }
}
```

The `@RestController` annotation marks this class for component scanning (it is a specialization of `@Component`), and tells Spring MVC that the return value of every handler method should be written to the HTTP response body as JSON (via Jackson's `ObjectMapper`) rather than interpreted as a view name for template rendering. The `@GetMapping("/health")` annotation maps HTTP `GET /health` to the `health()` method. The method returns a `Map<String, Object>`; Spring MVC's `RequestResponseBodyMethodProcessor` passes this to the configured `HttpMessageConverter` (Jackson by default), which serializes it to JSON and writes it to the response with `Content-Type: application/json`.

To build and run:

```bash
# build the fat jar
./mvnw clean package

# run it
java -jar target/myapp-1.0.0-SNAPSHOT.jar

# in another terminal
curl http://localhost:8080/health
# {"status":"UP","timestamp":"2024-09-20T14:32:11.234Z","version":"1.0.0"}

# the actuator's own health endpoint is also available
curl http://localhost:8080/actuator/health
# {"status":"UP"}

# ─── dev loop: skip the fat-jar step entirely ───────────────────────────
./mvnw spring-boot:run
# The spring-boot-maven-plugin's `run` goal forks a JVM, builds the classpath
# from target/classes/ + every runtime-scoped dependency jar, and invokes
# SpringApplication.run() directly. No `repackage` step, no fat jar — shaves
# 2-5 seconds off each iteration. This is what you should use during development.
```

For hot reload, add `spring-boot-devtools` as a dev-scoped dependency. Devtools watches `target/classes/` for file changes; when your IDE recompiles a class on save, devtools triggers an "application restart" — a fast in-process restart that re-creates the Spring `ApplicationContext` but reuses the JVM and the loaded classes that have not changed. The restart is 5–10× faster than a full JVM restart because the JVM is already warm, the JIT-compiled code for unchanged classes is preserved, and only the Spring bean graph is rebuilt:

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-devtools</artifactId>
    <scope>runtime</scope>
    <optional>true</optional>
</dependency>
```

Devtools also disables template caches (so Thymeleaf edits are visible immediately), enables automatic browser refresh via LiveReload (a WebSocket on port 35729), and is automatically disabled when the application is run from a fat jar (`java -jar`), so it cannot leak into production. The failure mode to know about: devtools' `restartClassLoader` is a *separate* classloader from the system classloader, and `instanceof` checks across the boundary can fail in surprising ways — if your `@Configuration` instantiates a class via `Class.forName(name)` without passing the restart classloader, you get `ClassCastException` from "same class loaded twice".

What happens between the HTTP request and the controller method is the Spring MVC request pipeline. Tomcat accepts the TCP connection, parses the HTTP request, and hands it to Spring MVC's `DispatcherServlet`. The `DispatcherServlet` consults the `RequestMappingHandlerMapping` to find the handler method that matches `GET /health` (our `HealthController.health()`). It then runs the handler through the interceptor chain (Spring Security filters, `@ControllerAdvice` exception handlers, etc.), invokes the method via reflection, and passes the return value through the `HttpMessageConverter` chain to serialize the response. The whole pipeline is synchronous and runs on a Tomcat worker thread from the 200-thread default pool (`server.tomcat.threads.max=200`).

```text
  HTTP request: GET /health
      │
      ▼
  Tomcat NIO connector accepts connection
      │
      ▼
  Tomcat worker thread (from pool of 200)
      │
      ▼
  FilterChain (Spring Security, etc.)
      │
      ▼
  DispatcherServlet.doDispatch()
      │
      ▼
  RequestMappingHandlerMapping.getHandler()  → finds HealthController.health()
      │
      ▼
  HandlerAdapter.handle()                    → invokes method via reflection
      │
      ▼
  HealthController.health()                  → returns Map.of("status","UP",...)
      │
      ▼
  RequestResponseBodyMethodProcessor          → finds Jackson converter
      │
      ▼
  Jackson ObjectMapper.writeValueAsString()   → {"status":"UP",...}
      │
      ▼
  Tomcat writes response to socket
      │
      ▼
  Worker thread returned to pool
```

The failure mode this exposes is the "Tomcat thread pool exhaustion" incident. Every request occupies a worker thread for its entire duration, including time spent waiting for downstream services (database queries, HTTP calls to other services). If a downstream service goes slow and 200 concurrent requests pile up waiting for it, all 200 Tomcat threads are blocked and the next request gets a 503 or a connection-refused. The defences are: configure `server.tomcat.threads.max` to match your downstream capacity, set `server.tomcat.connection-timeout` to drop slow clients, use `RestTemplate`/`WebClient` with explicit timeouts (never the defaults — the default `RestTemplate` has no read timeout), and circuit-break downstream calls with Resilience4j. This is the universal backend failure mode and the reason section 04 (Runtime Concurrency) exists.

### Debugging Spring Boot applications using JVM remote debug flags (`-agentlib:jdwp`)

The JVM ships with a debug wire protocol agent — JDWP (Java Debug Wire Protocol) — that lets an external debugger attach to a running JVM and inspect stack frames, set breakpoints, and evaluate expressions. The agent is loaded with the `-agentlib:jdwp` command-line flag. There are two modes: `server=y` (the JVM listens on a socket and the IDE attaches) and `server=n` (the IDE listens and the JVM attaches on startup). The `server=y` mode is what you want for debugging a Spring Boot app.

```bash
# Run with the JDWP agent listening on port 5005
java -agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=*:5005 \
     -jar target/myapp-1.0.0-SNAPSHOT.jar

# The flags mean:
#   transport=dt_socket   ← use TCP sockets, not shared memory
#   server=y              ← the JVM listens; the IDE connects
#   suspend=n             ← do NOT wait for the debugger to attach before starting
#                           (use suspend=y if you want to debug startup)
#   address=*:5005        ← listen on all interfaces, port 5005
```

In IntelliJ, the attach configuration is *Run → Edit Configurations → + → Remote JVM Debug*, with host `localhost` and port `5005`. In VS Code, the `launch.json` config is:

```json
{
  "type": "java",
  "name": "Attach to Spring Boot",
  "request": "attach",
  "hostName": "localhost",
  "port": 5005
}
```

Once attached, you can set breakpoints in your controller methods, step through code line by line, inspect local variables and field values, evaluate expressions in the immediate window, and watch the call stack. The JVM's JIT makes some optimizations invisible to the debugger (a method that was inlined cannot be stepped into), so for production-debugging accuracy you sometimes need to disable JIT for specific methods with `-XX:CompileCommand=exclude,com.example.MyClass::myMethod`.

`suspend=n` vs `suspend=y` is a frequent confusion. `suspend=y` means the JVM pauses at startup and waits for the debugger to attach before running any code — this is what you want if you are debugging the `main` method or the bean wiring. `suspend=n` means the JVM starts normally and the debugger can attach later — this is what you want if you are debugging a request handler that you will trigger with `curl` after the app is up. For Spring Boot, the common pattern is `suspend=n` for request debugging and `suspend=y` for startup debugging.

For production debugging, the JDWP agent should never be enabled — anyone who can reach port 5005 can read and write arbitrary JVM state, which is a remote code execution vector. The production debugging tools are instead: `jstack <pid>` to print a thread dump, `jmap -dump:live,format=b,file=heap.hprof <pid>` to capture a heap dump, `jcmd <pid> Thread.print` for thread state, `jcmd <pid> GC.heap_info` for heap usage, and the JDK Flight Recorder (`jcmd <pid> JFR.start duration=60s filename=recording.jfr`) for a 60-second profile of CPU, allocations, lock contention, and I/O. The actuator's `/actuator/threaddump` and `/actuator/heapdump` endpoints expose the same data over HTTP, which is how Kubernetes-sidecar debug containers capture them.

The failure mode JDWP debugging reveals is "the bug only happens on the second request". Many Spring beans are lazy — `@Lazy` beans are not instantiated until first use, `@Async` methods run on a different thread pool, and database connections are borrowed on demand. A breakpoint on the first request catches the lazy initialization; the second request is what reveals the actual bug (a stale connection, a cache miss, a thread-local leak). Always reproduce the bug twice before assuming you understand it.

## Key Takeaways

1. **Spring Initializr + `@SpringBootApplication` is the bootstrap.** Three starters (`web`, `data-jpa`, `actuator`) give you an HTTP server, a persistence layer, and an observability surface. Each starter activates auto-configurations gated by `@Conditional*` annotations — know which ones fire by reading the `--debug` conditions report.
2. **A REST controller is `@RestController` + `@GetMapping`.** The return value is serialized to JSON by Jackson via the `RequestResponseBodyMethodProcessor`. Every request occupies a Tomcat worker thread for its full duration, so downstream slowness exhausts the 200-thread default pool.
3. **JDWP (`-agentlib:jdwp`) is the development debugger; never enable it in production.** For production, use `jstack`, `jmap`, `jcmd`, and JFR. Reproduce request-handler bugs twice — lazy initialization masks them on first call.
