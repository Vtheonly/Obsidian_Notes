# 01.02.03. Maven and Gradle Build Architectures

## What This Is

Maven and Gradle are the two build tools that own the JVM ecosystem. Maven, released in 2004, is the established default — every Spring Boot project generated by Spring Initializr ships with a `pom.xml` unless you explicitly opt into Gradle. Gradle, released in 2008 and adopted by Android in 2013, is the faster, more flexible alternative that wins on large codebases and on incremental builds. The two tools solve the same problem — turn source into a deployable artifact, manage transitive dependencies, run tests — but their configuration formats (XML vs. Groovy/Kotlin DSL), their dependency resolution algorithms (nearest-wins vs. highest-version), their lifecycle models (fixed phases vs. task graph), and their performance characteristics (cold start vs. daemon) differ enough that picking one is a real architectural decision. This note explains both side by side, with real `pom.xml` and `build.gradle.kts` snippets, so you can read either in any Spring Boot project you encounter.

The note sits between [[01.02.02. Compiling and Running Vanilla Java from the Terminal]] (which showed the bare `javac`/`jar` workflow these tools wrap) and [[01.02.04. Bootstrapping a Bare-Metal Spring Boot Application]] (which produces a deployable artifact through one of these tools). At the layered mental model, build tools sit one layer above the OS toolchain (`javac` invokes `gcc` for JNI, `jar` is a `zip` archiver, the daemon is a long-running JVM that owns its own file descriptors and process) and one layer below the framework (Spring Boot's auto-configuration depends on what jars the build tool placed on the classpath). The failure modes this note governs surface as "Maven build succeeded locally but failed in CI because of a transitive version conflict", "Gradle build cached a stale output and shipped a broken jar", or "the same `pom.xml` produces different dependency trees on different machines because someone ran `mvn install` instead of `mvn package`".

## The Details

### Anatomy of a `pom.xml`: Coordinates (`groupId`, `artifactId`, `version`), dependencies, plugins, and build lifecycles

A Maven project is defined by its Project Object Model — the `pom.xml` file at the project root. Every POM has four mandatory sections: coordinates (the project's identity in the Maven repository), properties (variable interpolation), dependencies (the libraries the project needs), and build (plugins and lifecycle configuration). The coordinates are the three-tuple `groupId:artifactId:version` — `groupId` is the reverse-DNS organization identifier (`com.example`, `org.springframework.boot`), `artifactId` is the project's slug (`myapp`, `spring-boot-starter-web`), and `version` is the SemVer-ish version string. Together they form the coordinate that other projects use to depend on you, and the path under `~/.m2/repository/` where the built artifact is cached (`com/example/myapp/1.0.0/myapp-1.0.0.jar`).

```xml
<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0">
  <modelVersion>4.0.0</modelVersion>

  <parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>3.3.0</version>
    <relativePath/>
  </parent>

  <groupId>com.example</groupId>
  <artifactId>myapp</artifactId>
  <version>1.0.0-SNAPSHOT</version>
  <packaging>jar</packaging>

  <properties>
    <java.version>21</java.version>
    <spring-boot.version>3.3.0</spring-boot.version>
  </properties>

  <dependencies>
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-starter-web</artifactId>
    </dependency>
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-starter-test</artifactId>
      <scope>test</scope>
    </dependency>
  </dependencies>

  <build>
    <plugins>
      <plugin>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-maven-plugin</artifactId>
      </plugin>
    </plugins>
  </build>
</project>
```

The `<parent>` element lets a project inherit configuration from another POM — here, `spring-boot-starter-parent` provides default Java version, plugin versions, encoding, and the Spring Boot dependency BOM (Bill of Materials). The BOM is imported via `<dependencyManagement>` and pins the versions of every Spring Boot-managed dependency so that you can write `<dependency>` blocks without `<version>` and inherit the version from the BOM. Without the parent or the BOM, you would have to specify a version for every dependency and every transitive conflict would be your problem. The Maven BOM is itself just a POM with a `<dependencyManagement>` block and no `<dependencies>` — you import it with `<scope>import</scope>` and `<type>pom</type>`:

```xml
<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-dependencies</artifactId>
      <version>3.3.0</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>
```

Dependencies have scopes that determine when they are on the classpath: `compile` (default; compile + test + runtime), `test` (test only), `provided` (compile + test; not packaged — assumed to be provided by the runtime, e.g. `servlet-api` in a war deployed to Tomcat), `runtime` (test + runtime; not compile — e.g. JDBC drivers), and `system` (like `provided` but you must specify the absolute path with `<systemPath>`; almost never used). The scope is how Maven keeps test-only libraries like JUnit out of your production jar — a jar that accidentally ships JUnit on its runtime classpath will start a Swing window on boot because JUnit's `junit.textui.TestRunner` has a `main` method that some classpath scanners pick up.

Plugins are the actual build machinery. Maven's default lifecycle (see the next H3) binds plugins to phases — for example, the `maven-compiler-plugin` is bound to the `compile` phase, the `maven-surefire-plugin` to `test`, the `maven-jar-plugin` to `package`. The `spring-boot-maven-plugin` adds a `repackage` goal that runs during `package` and turns the plain jar into a fat jar (see [[01.02.02. Compiling and Running Vanilla Java from the Terminal]] for the fat-jar layout). Plugins can also be invoked directly: `mvn spring-boot:run` runs the application (it forks a JVM, sets up the classpath from `target/classes/` plus all `compile`/`runtime` dependencies, and calls the `main` method), `mvn surefire:test` runs only the tests, `mvn dependency:tree` prints the resolved dependency graph. The colon syntax is `<plugin-prefix>:<goal>` — Maven looks up the prefix in the plugin's `META-INF/maven/plugin.xml` descriptor.

The production failure mode here is the "dependency version drift" problem. Maven's default is nearest-wins: when two dependencies in the graph require different versions of the same transitive dependency, Maven picks the version that is "nearest" to the root of the dependency tree (the one declared earlier in the `<dependencies>` block, or the one declared at a lower depth). If your app depends on `lib-a` which depends on `jackson-databind@2.15.0`, and `lib-b` which depends on `jackson-databind@2.17.0`, Maven picks 2.15.0 if `lib-a` is declared first — regardless of whether 2.17.0's API is needed. The fix is an explicit `<dependencyManagement>` entry that forces the version you want:

```xml
<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>com.fasterxml.jackson.core</groupId>
      <artifactId>jackson-databind</artifactId>
      <version>2.17.0</version>
    </dependency>
  </dependencies>
</dependencyManagement>
```

This `dependencyManagement` block overrides nearest-wins for every transitive occurrence of `jackson-databind`. Run `mvn dependency:tree -Dincludes=com.fasterxml.jackson.core:jackson-databind` to see which version actually resolved and why — the output prints `(managed from 2.15.0)` next to the chosen version, telling you which dependency requested the lower version that was overridden. The deeper layered-model lesson is that the JVM has no built-in dependency manager (unlike Node's `require` resolution algorithm in [[01.03.03. CommonJS vs. ECMAScript Modules]]) — the classpath is a flat list of jars at runtime, and the build tool's resolution algorithm is the only thing standing between you and `NoSuchMethodError` at 3 a.m. in production.

### Maven Lifecycle phases: `validate`, `compile`, `test`, `package`, `verify`, `install`, `deploy`

Maven's lifecycle is a fixed sequence of phases. Each phase is a name; binding a plugin goal to a phase makes that goal run when the phase runs. The phases are ordered, and running a later phase runs all earlier phases first — `mvn package` runs `validate`, `compile`, `test`, `package` in order. This is the central Maven contract: any developer who knows Maven can run `mvn clean install` on any Maven project and get predictable behaviour, because the phase names mean the same thing everywhere.

```text
  validate      ← checks project correctness, e.g. POM is well-formed
      │
  generate-sources / process-sources     ← code generators (antlr, protoc)
      │
  compile       ← maven-compiler-plugin:compile → target/classes
      │
  process-classes               ← post-compilation bytecode manipulation
      │
  generate-test-sources / process-test-sources
      │
  test-compile   ← compiles src/test/java → target/test-classes
      │
  test          ← maven-surefire-plugin:test → runs *Test.java with JUnit
      │
  prepare-package / package     ← maven-jar-plugin:jar → target/myapp-1.0.0.jar
      │
  pre-integration-test / integration-test / post-integration-test
      │                                   ← maven-failsafe-plugin runs *IT.java
      │
  verify        ← runs checks (jacoco coverage, spotbugs, checkstyle)
      │
  install       ← copies the jar to ~/.m2/repository/com/example/myapp/1.0.0/
      │
  deploy        ← uploads to remote repository (Nexus, Artifactory)
```

The phase names are the same in every Maven project; only the bound plugins differ. This is Maven's strength: any developer who knows Maven can run `mvn clean install` on any project and get predictable behaviour. The weakness is rigidity — you cannot run "compile without test" without `mvn -DskipTests=true compile` (which still runs `test-compile`), and you cannot insert a custom phase between `compile` and `test` without writing a plugin. The `clean` lifecycle is separate from the default lifecycle — `mvn clean package` runs the `clean` lifecycle (which has its own phases: `pre-clean`, `clean`, `post-clean`) before the default lifecycle. The `clean` phase deletes `target/`; without it, stale class files from a previous build persist and can cause "ghost class" bugs where a deleted source file still has a compiled artifact that the JVM loads.

The phase that bites production most often is `test`. The `maven-surefire-plugin` by default discovers any class matching `*Test.java`, `*Tests.java`, or `*TestCase.java` under `src/test/java` and runs it with the configured test runner (JUnit 5 by default in Spring Boot 3). Tests run in parallel by default since Surefire 3, with one fork per CPU core. A flaky test that passes in isolation but fails under parallelism (because it shares a database or static state with another test) will pass locally and fail in CI intermittently. The fix is `mvn -Dsurefire.parallel=none test` to disable parallelism, or marking the offending test with `@Execution(ExecutionMode.SAME_THREAD)`.

The other phase that bites is `package`. The `maven-jar-plugin` produces a plain jar by default; the `spring-boot-maven-plugin`'s `repackage` goal replaces this plain jar with the fat jar (the original plain jar is renamed to `myapp-1.0.0.jar.original`). If you run `mvn package` and then try to run `java -cp target/myapp-1.0.0.jar com.example.MyappApplication`, you are running against the fat jar's `BOOT-INF/classes/` layout, which is not on the default classpath — you must use `java -jar target/myapp-1.0.0.jar` instead (see [[01.02.02. Compiling and Running Vanilla Java from the Terminal]]). The `spring-boot:run` goal bypasses the fat jar entirely: it runs the application from `target/classes/` with the dependency jars on the classpath individually, which is faster for local dev (no `repackage` step) but does not test the fat-jar layout that production uses.

The `install` phase copies the jar to your local Maven repository at `~/.m2/repository/`. This is how multi-module projects share artifacts between builds — module A's `mvn install` writes A's jar to `~/.m2/`, and module B's build picks it up from there. The failure mode is "stale local artifact": you edit module A, run `mvn install`, then realize you forgot to recompile. B's build picks up the old A jar from `~/.m2/` and you spend an hour wondering why your fix isn't working. The fix is `mvn clean install` (the `clean` phase deletes `target/` first, forcing a full recompile) or running a multi-module build from the parent POM, which builds all modules in one invocation and uses in-memory artifact passing instead of the local repo. The `deploy` phase uploads to a remote repository — Artifactory or Nexus — via `mvn deploy`. This requires `<distributionManagement>` in the POM with `<repository>` and `<snapshotRepository>` URLs and credentials in `~/.m2/settings.xml`. A misconfigured `settings.xml` produces the cryptic `401 Unauthorized` error; the fix is to verify `cat ~/.m2/settings.xml | grep -A3 <server-id>` matches the `<id>` in the POM's `<distributionManagement>` block.

The `mvn` command itself is a bash script on Unix and a `.cmd` on Windows. It locates `MAVEN_HOME` (or `M2_HOME`), sources `MAVEN_OPTS` (where you put `-Xmx2g -XX:+UseG1GC` to give Maven enough heap for large multi-module builds), and forks a fresh JVM with the `org.apache.maven.cli.MavenCli` main class. The Maven wrapper (`mvnw`) is a project-local version of this script that downloads the exact Maven version specified in `.mvn/wrapper/maven-wrapper.properties` on first run — see [[01.02.04. Bootstrapping a Bare-Metal Spring Boot Application]] for the Spring Initializr-generated wrapper. The wrapper is what makes `./mvnw package` work on a fresh checkout without a global Maven install. Always commit the wrapper to version control; never rely on a globally-installed Maven.

### Gradle architecture: `build.gradle.kts`, task graphs, incremental compilation, and the Gradle Daemon

Gradle replaces Maven's XML with a Groovy or Kotlin DSL, replaces the fixed phase lifecycle with a directed acyclic graph of tasks, and adds three performance features Maven lacks: incremental task inputs, the build cache, and the long-running Gradle Daemon. The result is that a Gradle build of a moderately-sized project can be 5–10× faster than the equivalent Maven build on a warm run. The Kotlin DSL (`build.gradle.kts`) is the modern default — it gives IDE auto-completion and type-checking on the build script itself, which the Groovy DSL (`build.gradle`) does not.

```kotlin
// build.gradle.kts
plugins {
    java
    id("org.springframework.boot") version "3.3.0"
    id("io.spring.dependency-management") version "1.1.5"
}

group = "com.example"
version = "1.0.0-SNAPSHOT"

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(21)
    }
}

repositories {
    mavenCentral()
}

dependencies {
    implementation("org.springframework.boot:spring-boot-starter-web")
    testImplementation("org.springframework.boot:spring-boot-starter-test")
}

tasks.withType<Test> {
    useJUnitPlatform()
}

tasks.withType<JavaCompile> {
    options.encoding = "UTF-8"
    options.release = 21
}
```

The `plugins` block applies plugins by ID and version — `java` for the JVM plugin (provides `compileJava`, `test`, `jar` tasks), `org.springframework.boot` for the Spring Boot plugin (provides `bootJar`, `bootRun`). The `dependencies` block uses "configurations" instead of Maven's "scopes": `implementation` (compile + runtime, not exposed to consumers), `api` (compile + runtime, exposed to consumers — for library projects), `compileOnly` (compile only, like Maven's `provided`), `runtimeOnly` (runtime only, like Maven's `runtime`), `testImplementation`, `testRuntimeOnly`. The `dependency-management` plugin imports the Spring Boot BOM so dependency versions can be omitted, mirroring Maven's `<dependencyManagement>` import. The Gradle equivalent of a pure Maven BOM is a "platform" — a project that publishes only version constraints:

```kotlin
// build.gradle.kts in a platform project
plugins {
    `java-platform`
}

dependencies {
    constraints {
        api("com.fasterxml.jackson.core:jackson-databind:2.17.0")
        api("org.postgresql:postgresql:42.7.3")
    }
}

// consumed in another project:
dependencies {
    implementation(platform("com.example:my-bom:1.0.0"))
    implementation("com.fasterxml.jackson.core:jackson-databind")  // version comes from platform
}
```

The fundamental difference from Maven is the task graph. A Maven build runs phases in a fixed order; a Gradle build runs only the tasks that are required to produce the requested output. If you run `./gradlew build`, Gradle constructs the task graph: `compileJava → processResources → classes → jar → assemble → check → build`. If you run `./gradlew jar`, only `compileJava → processResources → classes → jar` run. Gradle also skips tasks whose inputs have not changed since the last run — if `src/main/java/` has not been modified, `compileJava` is marked `UP-TO-DATE` and the task does nothing. Maven has no equivalent; `mvn package` always recompiles. The task graph is constructed during the "configuration phase" — every line of `build.gradle.kts` is executed top-to-bottom to build the task graph; the tasks themselves only execute in the "execution phase" that follows. This is why a `println` at the top level of `build.gradle.kts` runs even for `./gradlew tasks --help` — configuration always runs.

```text
  $ ./gradlew build --console=plain

  > Task :compileJava UP-TO-DATE        ← no source changes, skipped
  > Task :processResources
  > Task :classes
  > Task :jar
  > Task :assemble
  > Task :compileTestJava UP-TO-DATE
  > Task :processTestResources UP-TO-DATE
  > Task :testClasses
  > Task :test                           ← runs only changed test classes
  > Task :check
  > Task :build

  BUILD SUCCESSFUL in 3s
```

The Gradle Daemon is a long-running JVM process that stays alive between builds. The first `./gradlew build` invocation forks a daemon JVM (cold start: ~2 s); subsequent invocations connect to the daemon via a local socket on `~/.gradle/daemon/<version>/` and reuse the loaded classes, the JIT-warmed code cache, and the in-memory dependency resolution state. A daemon that has been running for an hour can build a Spring Boot project in 2 seconds where a fresh JVM would take 15. Run `./gradlew --status` to see running daemons and `./gradlew --stop` to kill them. CI environments should set `org.gradle.daemon=false` in `gradle.properties` because each CI run is a fresh machine — keeping a daemon alive wastes memory. The `./gradlew` wrapper (note the leading `./`) is a shell script checked into the project that downloads the exact Gradle version specified in `gradle/wrapper/gradle-wrapper.properties`; the `gradle` command without the wrapper uses the global Gradle install, which is what causes "works on my machine" when the global version differs.

The build cache (enabled with `org.gradle.caching=true` in `gradle.properties`) goes further: it hashes a task's inputs (source files, compiler options, dependencies) and stores the task's outputs under that hash. If the same inputs appear on a different machine (or in a different CI run), Gradle fetches the cached outputs instead of re-executing the task. This is what makes Gradle shine on large monorepos — a developer who changes one module fetches cached outputs for the other 200 modules. The remote build cache (an HTTP server like Gradle Enterprise's cache, or a self-hosted nginx with WebDAV) shares cache hits across the whole team. The configuration cache (added in Gradle 6.5, stabilized in 7.0) goes further still: it serializes the configured project state after `settings.gradle.kts` and `build.gradle.kts` run, so the next build skips configuration entirely. The combined stack — daemon + build cache + configuration cache — is what makes Gradle builds of multi-million-line monorepos (Android, LinkedIn, Netflix) tractable.

Gradle's dependency resolution differs from Maven's. Maven uses nearest-wins (see the previous H3); Gradle uses highest-version-wins by default — when two paths to the same dependency request different versions, Gradle picks the highest. This is generally more correct (newer versions usually satisfy older constraints) but can fail when the highest version has a breaking API change. Gradle also surfaces conflicts explicitly: `./gradlew dependencyInsight --dependency jackson-databind` shows every constraint and the chosen resolution. To force a specific version, use a constraint:

```kotlin
dependencies {
    constraints {
        implementation("com.fasterxml.jackson.core:jackson-databind:2.17.0")
    }
}
```

Gradle also supports dependency locking (`./gradlew dependencies --write-locks` produces `gradle.lockfile`) which is the equivalent of `package-lock.json` for Node — every transitive dependency is pinned to a specific version, and subsequent builds fail if the lockfile does not match the resolved graph. This is what you want in production: reproducible builds across machines.

| Aspect | Maven | Gradle |
|---|---|---|
| Build file | `pom.xml` (XML, declarative) | `build.gradle.kts` (Kotlin DSL, imperative) |
| Invocation | `mvn <phase>` (e.g. `mvn package`) | `./gradlew <task>` (e.g. `./gradlew build`) |
| Resolution algorithm | Nearest-wins | Highest-version-wins (overridable) |
| Lifecycle | Fixed phase sequence (`compile`→`test`→`package`→...) | Task DAG; only required tasks run |
| Incremental | No; recompiles everything | Yes; per-task input hashing, `UP-TO-DATE` |
| Build cache | No (per-machine only) | Local + remote cache, content-addressed |
| Daemon | No (fresh JVM per build) | Long-running daemon, ~2s warm builds |
| BOM equivalent | `<dependencyManagement>` import (BOM POM) | `java-platform` plugin (constraints block) |
| Lockfile | None (use `<dependencyManagement>`) | `gradle.lockfile` with `--write-locks` |
| Configuration time | Fast (XML parse) | Slow first run, instant with config cache |
| Best for | Small-medium projects, conventional Spring Boot | Large monorepos, Android, custom builds |

The failure mode that distinguishes Maven from Gradle in production is the "configuration cache invalidation" problem. Gradle's configuration cache serializes the configured project state, but if a build script reads from the filesystem or makes an HTTP call during configuration (a common anti-pattern in older Gradle builds — e.g. `def version = "git rev-parse --short HEAD".execute().text.trim()`), the configuration cache will fail with `configuration cache problems found` and the build will fall back to the slow path. Migrating a legacy Gradle build to be configuration-cache-compatible is a real engineering project — but the payoff is a 2–3× faster local dev loop. The deeper lesson is that the build tool's own state (its daemon, its caches, its lockfile) is itself a production dependency: a corrupted `~/.gradle/caches/` directory can break every Gradle project on the machine, and the fix is `rm -rf ~/.gradle/caches/ && ./gradlew --refresh-dependencies` — nuclear, but reliable.

## Key Takeaways

1. **Maven's `pom.xml` is XML with coordinates, dependencies, plugins, and a fixed phase lifecycle.** Nearest-wins resolution means transitive version conflicts must be resolved with explicit `<dependencyManagement>` entries. `mvn clean install` is the universal build command; `mvn dependency:tree` is the universal debugging command. The BOM is imported via `<dependencyManagement>` with `<type>pom</type><scope>import</scope>`.
2. **Gradle's `build.gradle.kts` is a task graph, not a phase sequence.** Incremental compilation (`UP-TO-DATE`), the build cache (content-addressed across machines), and the long-running Daemon combine to make Gradle 5–10× faster than Maven on warm builds. Highest-version resolution is the default; the BOM equivalent is the `java-platform` plugin with a `constraints` block. `./gradlew` (the wrapper) is the universal invocation — never use a global `gradle`.
3. **The daemon is a liability in CI and an asset locally.** Enable it on developer machines (`org.gradle.daemon=true`); disable it in CI (`org.gradle.daemon=false`). Always run `mvn clean` or `./gradlew clean` before a release build to defeat stale-cache bugs. Use `gradle.lockfile` (`--write-locks`) or Maven's `<dependencyManagement>` to guarantee reproducible builds.
