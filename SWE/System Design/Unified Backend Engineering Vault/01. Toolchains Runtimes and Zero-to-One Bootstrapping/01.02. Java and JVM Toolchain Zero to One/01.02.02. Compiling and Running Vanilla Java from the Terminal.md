# 01.02.02. Compiling and Running Vanilla Java from the Terminal

## What This Is

Before Maven, before Gradle, before Spring Initializr, Java was a language you compiled with `javac` and ran with `java` from a terminal. This note walks that bare-metal workflow end-to-end: writing `HelloWorld.java`, compiling it to a `.class` bytecode file, disassembling that bytecode with `javap` to see what the JVM actually executes, and packaging the result into a runnable `.jar` with the `jar` tool. The point is not that you will do this in production — you won't, you will use Maven or Gradle — but that the build tools are wrappers around these primitives. When Maven prints `Compiling 23 source files to target/classes`, it is calling `javac` under the hood; when Gradle says `Building jar: build/libs/app.jar`, it is calling `jar`. Understanding the primitives is what lets you read a Maven build failure and know whether `javac` rejected your code or `jar` failed to write the manifest.

This note is the prerequisite for [[01.02.03. Maven and Gradle Build Architectures]] — the build tools automate exactly the workflow shown here. It also surfaces the class-file format, the bytecode instruction set, and the JAR manifest format, all of which you need to know to read `javap` output during a production debugging session or to understand why a fat jar produced by Spring Boot's `repackage` goal is not a "normal" jar.

## The Details

### Writing the foundational `HelloWorld.java` with explicit public class and `main` method signatures

A Java source file has three rules that the compiler enforces strictly. First, the file name must match the public class it contains — `HelloWorld.java` must declare `public class HelloWorld`, not `public class Hello` or `public class hello_world`. Second, a file may contain at most one public class (but any number of package-private classes). Third, the entry point of an executable Java program is a method with the exact signature `public static void main(String[] args)` — `public` so the JVM can call it from outside the class, `static` so it can be invoked without an instance, `void` because it returns nothing (the JVM's exit code is set with `System.exit(int)`), and `String[] args` because the command-line arguments are passed as an array of strings.

```java
// HelloWorld.java
public class HelloWorld {
    public static void main(String[] args) {
        System.out.println("Hello, " + (args.length > 0 ? args[0] : "world"));
    }
}
```

The `main` method signature has three common variations that look correct but are not. `public void main(String[] args)` (missing `static`) compiles but throws `NoSuchMethodError` at runtime because the JVM looks for a static method. `public static void main(String args)` (missing `[]`) compiles as an overload but is not the entry point. `public static int main(String[] args)` (returning `int`) does not compile under Java's strict main-method detection — the JVM requires `void`. The `String[] args` parameter may also be written `String... args` (varargs); both compile to the same bytecode and are accepted as entry points. Java 21+ also accepts `void main()` (no `public`, no `static`, no `String[] args`) under JEP 445 (Unnamed Classes and Instance Main Methods, preview) — this is part of the "Project Amber" effort to reduce boilerplate for beginners, but production code still uses the canonical `public static void main(String[] args)` for compatibility.

The `public class` rule exists because the JVM resolves classes by file path at class-loading time: when you run `java HelloWorld`, the classloader looks for `HelloWorld.class` on the classpath. If the file were named `hello.java` and contained `public class HelloWorld`, the compiler would refuse — it cannot guarantee that the resulting `.class` file will be findable by name. Package-private classes (no `public` modifier) may have any file name, but only one public class per file is allowed because the file name is the public class's name.

The `System.out.println` call is a deceptively complex operation under the hood. `System.out` is a `PrintStream` wrapping a `BufferedOutputStream` wrapping a `FileOutputStream` wrapping file descriptor 1 (stdout). `println` synchronizes on the `PrintStream` instance (so concurrent `println` calls don't interleave), writes the string's UTF-8 bytes to the buffer, flushes if the buffer is full or if auto-flush is on (which it is for `System.out` after `println`), and the bytes reach the kernel's `write(2)` syscall. In a containerized environment, stdout is a pipe to the container runtime (Docker, containerd) which forwards it to the logging driver (json-file by default, journald, or a remote log aggregator like Fluentd). This is why `System.out.println` is fine for development but unacceptable in production — production logging must use a real logging framework (SLF4J + Logback or Log4j2) that gives you structured JSON, async appenders, and log-level filtering. The SLF4J `logger.info("Hello, {}", name)` call uses parameterized messages that skip the string concatenation entirely if the INFO level is disabled, which is a measurable performance win in hot paths.

### Compiling single and multi-file source trees via `javac` to generate `.class` bytecode files

The `javac` compiler reads `.java` source files and writes `.class` bytecode files. The simplest invocation is `javac HelloWorld.java`, which produces `HelloWorld.class` in the current directory. For a multi-file project, you pass a source path and an output directory:

```bash
# Project layout (multi-file example):
#   src/com/example/Main.java            ← the entry point
#   src/com/example/model/User.java      ← a domain class
#   src/com/example/util/Logger.java     ← a utility class
#
# Main.java:
#   package com.example;
#   import com.example.model.User;
#   import com.example.util.Logger;
#   public class Main {
#       public static void main(String[] args) {
#           Logger.info("starting");
#           User u = new User("alice", 42);
#           System.out.println(u.greet());
#       }
#   }
#
# model/User.java:
#   package com.example.model;
#   public class User {
#       private final String name; private final int age;
#       public User(String name, int age) { this.name = name; this.age = age; }
#       public String greet() { return "Hello, I'm " + name + " (" + age + ")"; }
#   }
#
# util/Logger.java:
#   package com.example.util;
#   public class Logger {
#       public static void info(String msg) { System.out.println("[INFO] " + msg); }
#   }

# Compile every .java under src/, output to build/
javac -d build/ $(find src -name "*.java")

# Or, with a source path (lets javac find dependencies):
javac -d build/ -sourcepath src/ src/com/example/Main.java

# Resulting layout (bytecode mirroring the package structure):
#   build/com/example/Main.class
#   build/com/example/model/User.class
#   build/com/example/util/Logger.class
#   build/com/example/util/Logger$DebugLevel.class   ← inner class (if any)

# Run the entry point:
java -cp build/ com.example.Main
# [INFO] starting
# Hello, I'm alice (42)
```

The `-d` flag sets the output directory; `javac` creates the package directory structure under it automatically. The `-sourcepath` flag tells `javac` where to look for source files when it encounters an import it cannot resolve from already-compiled classes — without it, `javac` will fail with `cannot find symbol` if `Main.java` imports `com.example.model.User` and `User.java` has not been compiled yet. The two-argument form `javac -sourcepath src src/com/example/Main.java` is sufficient: `javac` will compile `Main.java`, discover its imports, recursively compile `User.java` and `Logger.java`, and write all three `.class` files to `build/`. This is the "minimum viable build" — Maven and Gradle automate it but the underlying mechanism is identical.

The `.class` file format is a binary format defined by the JVM specification. Each file starts with the magic bytes `0xCAFEBABE`, then the major and minor version numbers (Java 21 = major 65, Java 17 = major 61, Java 11 = major 55, Java 8 = major 52), then the constant pool (a table of strings, class names, method names, and other constants referenced by bytecode), then the access flags (`public`, `final`, `abstract`, etc.), then the class name, superclass, interfaces, fields, methods, and attributes. The major version is what produces the `Unsupported class file major version` error when you try to run Java 21-compiled bytecode on a Java 17 runtime — the runtime refuses to load classes newer than itself. The converse (`java.lang.UnsupportedClassVersionError: com/example/Main has been compiled by a more recent version of the Java Runtime (class file version 65.0), this version of the Java Runtime only recognizes class file versions up to 61.0`) is the message you'll see.

```bash
# inspect the class file's version and structure
$ javap -v build/com/example/Main.class | head -20

Classfile /build/com/example/Main.class
  Last modified 20-Sep-2024; size 543 bytes
  SHA-256 checksum 3a4f...
  Compiled from "Main.java"
public class com.example.Main
  minor version: 0
  major version: 65        ← Java 21
  flags: (0x0021) ACC_PUBLIC, ACC_SUPER
  this_class: #2 (com/example/Main)
  super_class: #4 (java/lang/Object)
  interfaces: 0, fields: 0, methods: 2, attributes: 1
Constant pool:
   #1 = Methodref          #4.#18         // java/lang/Object."<init>":()V
   #2 = Class              #19            // com/example/Main
   ...
```

The production failure mode that this primitive workflow exposes is the "stale class file" problem. If you edit `User.java` but only re-run `java -cp build com.example.Main` without recompiling, you are running against the old `User.class`. Maven and Gradle solve this with incremental compilation — they track which source files changed and recompile only those plus their dependents (Maven via the `maven-compiler-plugin`'s `useIncrementalCompilation`, Gradle via its `incremental` feature that does fine-grained class-level dependency tracking) — but the underlying mechanism is the same `javac` call. The reason IDEs like IntelliJ have a "rebuild project" button is that their incremental compiler occasionally gets confused and ships a stale class; a clean rebuild is the sledgehammer. The same problem surfaces in Docker builds — if the `Dockerfile` copies the source before the dependencies and a build cache miss only re-runs the compile step, you can end up with a jar built from half-old, half-new classes. The fix is layer ordering: copy `pom.xml` first, run `mvn dependency:resolve` to cache deps, then copy `src/` and run `mvn package`.

### Inspecting JVM bytecode instructions using the Java Class File Disassembler (`javap -c -v`)

The `javap` tool disassembles a `.class` file and prints the bytecode instructions the JVM will execute. The `-c` flag prints the bytecode of each method; `-v` (or `-verbose`) prints the constant pool, the major/minor version, the access flags, and the attributes (line number table, local variable table, stack map frame). Reading `javap` output is the Java equivalent of reading assembly output from `gcc -S` — it tells you exactly what the machine (in this case the JVM) will execute.

```bash
$ javap -c -p build/com/example/HelloWorld.class

Compiled from "HelloWorld.java"
public class com.example.HelloWorld {
  public com.example.HelloWorld();
    Code:
       0: aload_0
       1: invokespecial #1   // Method java/lang/Object."<init>":()V
       4: return

  public static void main(java.lang.String[]);
    Code:
       0: getstatic     #7   // Field java/lang/System.out:Ljava/io/PrintStream;
       3: new           #13  // class java/lang/StringBuilder
       6: dup
       7: invokespecial #15 // Method java/lang/StringBuilder."<init>":()V
      10: ldc           #16  // String Hello,
      12: invokevirtual #18  // Method java/lang/StringBuilder.append:(Ljava/lang/String;)...
      15: aload_0
      16: arraylength
      17: ifle          34
      20: aload_0
      21: iconst_0
      22: aaload
      23: invokevirtual #18  // Method java/lang/StringBuilder.append:(Ljava/lang/String;)...
      26: invokevirtual #22  // Method java/lang/StringBuilder.toString:()Ljava/lang/String;
      29: goto          39
      32: ldc           #26  // String world
      34: invokevirtual #18  // append
      37: invokevirtual #22  // toString
      40: invokevirtual #28  // Method java/io/PrintStream.println:(Ljava/lang/String;)V
      43: return
}
```

The bytecode is a stack machine: each instruction pushes and pops operands on the JVM's operand stack. `getstatic #7` pushes `System.out` (resolved via constant pool entry #7) onto the stack. `new #13` allocates a `StringBuilder` and pushes its reference. `dup` duplicates the reference (so the constructor can consume one and we keep one). `invokespecial #15` calls the constructor. `ldc #16` loads the string constant `"Hello, "` from the constant pool. `invokevirtual #18` calls `StringBuilder.append`. At the end, `invokevirtual #28` calls `PrintStream.println` and consumes both the `PrintStream` reference and the string reference from the stack.

The numbers in the left column (`0:`, `3:`, `6:`, ...) are byte offsets within the method's code attribute. They are not evenly spaced because instructions have different lengths — `aload_0` is 1 byte, `getstatic` is 3 bytes (opcode + 2-byte constant pool index), `invokespecial` is 3 bytes, `invokeinterface` is 5 bytes (opcode + 2-byte index + 1-byte count + 1-byte 0). The `#7`, `#13`, `#15` etc. are indices into the constant pool, which is the table of strings, class names, method names, and field names the bytecode references. The constant pool is also where the JIT compiler's "speculative" optimizations live — if C2 decides to inline `StringBuilder.append`, it patches the bytecode site with a direct jump to the inlined code, and the constant pool entry for the method ref gains an "inline cache" pointer.

The reason to read `javap` output in production is to diagnose JIT compilation issues and to understand what `synchronized` actually does. A `synchronized` method has the `ACC_SYNCHRONIZED` flag in its access flags; a `synchronized` block compiles to explicit `monitorenter` and `monitorexit` instructions surrounding the block, with an exception handler that calls `monitorexit` if the block throws. A `volatile` field has the `ACC_VOLATILE` flag, which tells the JIT to emit memory-barrier instructions (`mfence` on x86, `dmb` on ARM) on every read and write. When you see a production "the value was visible on one thread but not another" bug, the question is whether the field was `volatile` — `javap -v` answers it definitively.

```bash
# check if a field is volatile
$ javap -v -p build/com/example/Counter.class | grep -A1 "private.*count"
  private int count;
    descriptor: I
    flags: (0x0002) ACC_PRIVATE     ← NOT volatile; cross-thread visibility bug waiting to happen

# vs after adding `volatile`:
  private volatile int count;
    descriptor: I
    flags: (0x0042) ACC_PRIVATE, ACC_VOLATILE   ← JIT will emit memory barriers
```

### Packaging and executing compiled bytecode into an executable `.jar` file using the `jar` CLI utility

A `.jar` file is a ZIP archive with a specific layout: compiled `.class` files in directories matching their package structure, plus a `META-INF/MANIFEST.MF` file at the root. The `jar` tool (located at `$JAVA_HOME/bin/jar`) creates them. The minimum useful jar contains the compiled classes and a manifest that declares which class is the entry point:

```bash
# build the manifest
cat > manifest.txt <<EOF
Main-Class: com.example.HelloWorld
EOF

# create the jar
#   c = create new archive
#   f = specify output file (next argument)
#   m = include manifest from file (next argument)
#   -C dir . = change to dir, include everything in it
jar cfm hello.jar manifest.txt -C build/ .

# inspect the jar's contents (t = table of contents, f = file)
jar tf hello.jar
# META-INF/MANIFEST.MF
# com/example/HelloWorld.class
# com/example/model/User.class
# com/example/util/Logger.class

# extract the manifest from an existing jar (x = extract, f = file)
unzip -p hello.jar META-INF/MANIFEST.MF
# Manifest-Version: 1.0
# Created-By: 21.0.4+7-LTS (Eclipse Adoptium)
# Main-Class: com.example.HelloWorld

# run the jar — the JVM reads Main-Class from the manifest and invokes its main()
java -jar hello.jar Alice
# Hello, Alice
```

The `c` flag means "create", `f` means "specify output file", `m` means "include this manifest file". The `-C build/ .` argument changes to the `build/` directory and includes everything in it. The resulting `hello.jar` can be shipped to any machine with a compatible JVM and run with `java -jar hello.jar` — no classpath needed because the manifest's `Main-Class` entry tells the JVM where to start. The `jar` tool also supports `u` (update an existing jar), `x` (extract files), and `i` (generate an index in `META-INF/INDEX.LIST` for faster classloading in applet-style scenarios, mostly historical now).

The manifest is a text file with `Key: Value` lines, one per line, with at most 72 bytes per line (longer values are continued with a leading space on the next line — the line continuation rule is in RFC 822). The important keys are:

- `Main-Class: com.example.HelloWorld` — the entry point class for `java -jar`.
- `Class-Path: lib/jackson-core-2.17.0.jar lib/jackson-databind-2.17.0.jar` — additional jars to add to the classpath (space-separated, relative to the jar's directory). Used for "thin jars" that depend on external libs.
- `Implementation-Version: 1.0.0` and `Implementation-Title: hello` — metadata exposed by `Package.getImplementationVersion()`, used by Spring Boot's `/info` actuator endpoint.
- `Build-Jdk: 21.0.4` — automatically added by `jar`, used by build tools to detect cross-JDK builds.
- `Multi-Release: true` — for multi-release jars that ship different bytecode for different Java versions (e.g. a Java 8 version of a class in the root, and a Java 17 version under `META-INF/versions/17/`). Modern libraries like `jackson-core` and `slf4j` use this to support Java 8 baseline while taking advantage of Java 17+ APIs on newer runtimes.
- `Sealed: true` (with `Sealed-By: ...` in newer specs) — seals the package so that the JVM rejects classes in the same package loaded from a different jar. Used by JDK modules and security-sensitive libraries.

A "fat jar" (or "uber jar") is a jar that bundles all of the application's dependencies — every transitive jar's `.class` files unzipped into the output jar — so the application can be run with a single `java -jar app.jar` and no classpath. Maven's `maven-shade-plugin` and Gradle's `shadowJar` plugin produce fat jars. Spring Boot's `spring-boot-maven-plugin:repackage` goal produces a special kind of fat jar where the dependencies live under `BOOT-INF/lib/` and the application classes live under `BOOT-INF/classes/`, with a custom `JarLauncher` as the `Main-Class` that builds a classloader from those locations at startup. This is why you cannot run a Spring Boot fat jar with `java -cp app.jar com.example.Main` — the `Main-Class` is `org.springframework.boot.loader.launch.JarLauncher`, not your application class, and the layout is not a flat classpath.

```text
  Plain jar:                       Fat jar (shade):           Spring Boot fat jar:
  hello.jar                        hello.jar                  hello.jar
  ├── META-INF/                    ├── META-INF/              ├── META-INF/
  │   └── MANIFEST.MF              │   └── MANIFEST.MF        │   └── MANIFEST.MF
  └── com/example/                 ├── com/example/           │       Main-Class: org.springframework...
      └── HelloWorld.class         │   └── HelloWorld.class   ├── org/springframework/boot/loader/...
                                  ├── com/fasterxml/...       │   └── launch/JarLauncher.class
                                  ├── org/slf4j/...           ├── BOOT-INF/
                                  └── ... (all deps)          │   ├── classes/
                                                              │   │   └── com/example/...
                                                              │   └── lib/
                                                              │       ├── jackson-databind-2.17.0.jar
                                                              │       ├── spring-boot-3.3.0.jar
                                                              │       └── ... (all deps as jars)
                                                              └── org/springframework/boot/loader/...
```

The failure mode this exposes is the "spring-boot jar vs classpath" confusion. A developer sees `hello.jar`, runs `java -cp hello.jar com.example.HelloWorld`, and gets `Could not find or load main class com.example.HelloWorld` even though `jar tf hello.jar` shows the class is present. The reason is that Spring Boot's fat jar layout puts the class under `BOOT-INF/classes/`, which is not on the JVM's default classpath — only the `JarLauncher` knows how to load from there (it builds a `LaunchedURLClassLoader` that adds `BOOT-INF/classes/` and every `BOOT-INF/lib/*.jar` to the search path). The fix is to run `java -jar hello.jar` (which uses the manifest's `Main-Class`) or to extract the fat jar with `unzip hello.jar -d extracted/` and run against the extracted layout with `java -cp 'extracted/BOOT-INF/classes/:extracted/BOOT-INF/lib/*' com.example.HelloWorld`. A related failure is "exploded Spring Boot jar loses classpath ordering" — Spring's `JarLauncher` adds `BOOT-INF/lib/*.jar` in alphabetical order, but if you extract and use a wildcard classpath, the shell expands the wildcard in lexicographic order too, so the order should match — except on filesystems where directory iteration order is not alphabetical (XFS, ZFS), where you can get `NoSuchMethodError` from classpath shadowing. The fix is to use the `java -jar` form, which lets Spring's loader control the order explicitly.

## Key Takeaways

1. **Java enforces a 1:1 rule between public class name and file name.** The entry point is `public static void main(String[] args)` exactly — any other signature silently fails or fails to compile. The multi-file compile command `javac -d build/ -sourcepath src/ src/com/example/Main.java` recursively compiles dependent sources into the matching package directory structure under `build/`.
2. **`.class` files start with `0xCAFEBABE` and carry a major version (Java 21 = 65).** Running Java 21-compiled bytecode on a Java 17 runtime produces `UnsupportedClassVersionError`. The `javap -c -v` disassembler is the equivalent of `gcc -S` — it shows the constant pool, the access flags, and the bytecode instructions, and is the only way to verify that `volatile`, `synchronized`, and `ACC_SYNCHRONIZED` are actually present.
3. **A JAR is a ZIP with `META-INF/MANIFEST.MF`.** `Main-Class` makes it executable with `java -jar`. Spring Boot fat jars are a special layout (`BOOT-INF/classes`, `BOOT-INF/lib`) that requires the `JarLauncher` — you cannot run them with `java -cp` and you cannot extract-and-run on filesystems with non-deterministic directory ordering.
