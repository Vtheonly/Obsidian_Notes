# 01.02.01. Installing JDK and Environment Configuration

## What This Is

Before you can write, compile, or run any Java code — including every Spring Boot application in this vault — you must install a Java Development Kit (JDK) and wire three environment variables so that the operating system, your shell, and the build tool all agree on which Java to use. This is the most universally botched step in backend onboarding: developers install a JRE instead of a JDK (and wonder why `javac` is missing), they leave `JAVA_HOME` pointing at an old Java 8 install (and wonder why `record` and `var` fail to compile), or they install Java via the OS package manager (and get a build that works on Ubuntu but not on Alpine because glibc vs musl). This note walks the install on macOS, Linux, and Windows; the version-management workflow via SDKMAN; the `JAVA_HOME`/`PATH` wiring; the verification commands; and the classpath and module-path mechanisms that Java 9's JPMS introduced.

The note sits at the bottom of the Java toolchain stack — every other note in sub-section 01.02 assumes you have a working `javac`/`java` pair on your `PATH`. The failure modes it governs are the ones that surface as "command not found", "unsupported class file version", "module not found", and the dreaded `JAVA_HOME is set to an invalid directory`.

## The Details

### Installing OpenJDK distributions (Temurin, Corretto) via SDKMAN

There is no single "Java" — there are several OpenJDK distributions, all built from the same OpenJDK source tree but with different support SLAs, different included tools, and different patch cadences. The five you will encounter in production are:

- **Temurin** (formerly AdoptOpenJDK, now Eclipse Adoptium) — the community reference distribution, free, GPL+CE licensed, no commercial support. The default in most CI images (`eclipse-temurin:21-jre` on Docker Hub). Built from the OpenJDK source by the Adoptium Working Group.
- **Amazon Corretto** — Amazon's distribution, free, long-term support (LTS) patches from Amazon, used inside AWS Lambda and ECS. Adds a few AWS-specific performance patches (e.g. improved cold start with the Cassowary allocator, plus patches for the AWS Nitro Enclaves and Firecracker microVM).
- **Azul Zulu** — Azul's distribution, free builds of OpenJDK, with optional commercial Zing/Zulu Prime builds that ship the C4 pauseless GC (a generational, concurrent, compacting collector that pauses for <10 ms even on multi-TB heaps — at a price).
- **Oracle JDK** — Oracle's commercial build, free for production since Java 17 but with the Java SE Subscription for older versions in enterprise. Ships Flight Recorder and Mission Control (now also in OpenJDK since Java 11).
- **GraalVM** (Oracle, free CE / commercial EE) — a JDK with a different top-tier JIT compiler written in Java (the Graal compiler) that replaces C2, plus the `native-image` AOT compiler that produces a standalone native binary from JVM bytecode. GraalVM is what Quarkus and Spring Native use to bring JVM cold-starts down from seconds to milliseconds for serverless.

The Oracle vs OpenJDK distinction is mostly historical now: since Java 11, Oracle JDK and OpenJDK are essentially identical builds. The reason to choose Temurin/Corretto/Zulu over Oracle JDK is licensing clarity and the patch SLA, not features. The OpenJDK project itself releases a new GA version every 6 months (March and September); vendors then backport security fixes to the LTS versions for 5+ years. The LTS releases are:

```text
  Java LTS timeline (as of 2024):
  ──────────────────────────────────────────────────────────────
  Java 8 LTS   (Mar 2014)  ← still in 60%+ of enterprise prod
                              Oracle Premier Support ended Mar 2022
                              Adoptium LTS support until at least 2030
  Java 11 LTS  (Sep 2018)  ← first LTS with var, HttpClient, module system
                              Oracle Premier Support ended Sep 2023
                              Adoptium LTS support until at least 2026
  Java 17 LTS  (Sep 2021)  ← current Spring Boot 3.x minimum
                              sealed classes, records, pattern matching
                              Adoptium LTS support until at least 2029
  Java 21 LTS  (Sep 2023)  ← current LTS — virtual threads (Project Loom),
                              sequenced collections, pattern matching for switch
                              Adoptium LTS support until at least 2032
  Java 25 LTS  (Sep 2025)  ← next planned LTS (per new 2-year LTS cadence)
  ──────────────────────────────────────────────────────────────
  Non-LTS releases (9, 10, 12, 13, 14, 15, 16, 18, 19, 20, 22, 23, 24):
    supported for 6 months only, never use in production
```

The version manager for Java on macOS and Linux is **SDKMAN**. It installs JDKs into `~/.sdkman/candidates/java/<version>/` and switches between them by symlinking `JAVA_HOME`. Installing it is one curl:

```bash
# macOS / Linux install
curl -s "https://get.sdkman.io" | bash
source "$HOME/.sdkman/bin/sdkman-init.sh"

# list available JDKs (there are ~50)
sdk list java | head -40

# install Temurin 21 LTS (the current LTS at time of writing)
sdk install java 21.0.4-tem

# install Amazon Corretto 17 LTS alongside
sdk install java 17.0.12-amzn

# switch between them
sdk use java 21.0.4-tem      # for current shell
sdk default java 17.0.12-amzn # for all future shells

# verify
java -version
# openjdk version "21.0.4" 2024-07-16 LTS
# OpenJDK Runtime Environment Temurin-21.0.4+7 (build 21.0.4+7-LTS)
# OpenJDK 64-Bit Server VM Temurin-21.0.4+7 (build 21.0.4+7-LTS, mixed mode)
```

On Debian/Ubuntu, the system package manager is `apt-get`, but the OpenJDK packages it ships are often months behind upstream. The `apt-get install default-jdk` command installs whatever the distro calls "default" (typically OpenJDK 17 on Ubuntu 22.04, OpenJDK 21 on Ubuntu 24.04). When you need to switch between multiple system-installed JDKs on Debian, the `update-alternatives` system manages the symlinks in `/usr/bin/`:

```bash
# Debian/Ubuntu: install two JDKs side-by-side
sudo apt-get install -y openjdk-17-jdk-headless openjdk-21-jdk-headless

# list what's installed
sudo update-alternatives --list java
# /usr/lib/jvm/java-17-openjdk-amd64/bin/java
# /usr/lib/jvm/java-21-openjdk-amd64/bin/java

# interactively pick which one /usr/bin/java points to
sudo update-alternatives --config java

# the same for javac
sudo update-alternatives --config javac

# update-alternatives creates these symlinks:
#   /usr/bin/java  → /etc/alternatives/java  → /usr/lib/jvm/java-21-openjdk-amd64/bin/java
# so JAVA_HOME should be /usr/lib/jvm/java-21-openjdk-amd64
```

On Windows, the equivalent is the **Adoptium MSI installer** (downloads from `adoptium.net/temurin/releases/`), which sets `JAVA_HOME` and updates `PATH` automatically. The MSI also offers to associate `.jar` files with the JRE shell and to add a `JAVA_HOME` system variable. For Windows users who need multiple JDK versions, **Scoop** (`scoop install temurin21-jdk`) is the closest equivalent to SDKMAN.

```powershell
# Windows (PowerShell, with Scoop)
scoop install temurin21-jdk
scoop install temurin17-jdk

# switch
scoop reset temurin17-jdk

# verify
java -version
```

The production failure mode here is "I installed Java 8 because that's what the tutorial said, but Spring Boot 3.x requires Java 17+". Always check the Spring Boot version's minimum Java requirement (Spring Boot 3.0+ requires Java 17; Spring Boot 4 will require Java 21; Quarkus 3.x supports both 17 and 21) before installing a JDK. The other classic failure is installing a JRE (Java Runtime Environment) instead of a JDK — modern OpenJDK distributions no longer ship a separate JRE (since Java 11, the JRE was removed as a separate download), but some Linux package managers still install `default-jre` if you ask for `java` instead of `jdk`. A JRE has `java` but no `javac`, so compilation fails with `javac: command not found` even though `java -version` works. The fix is `apt-get install default-jdk` (not `default-jre`), or installing via SDKMAN/Scoop, which always installs a full JDK.

### Configuring `JAVA_HOME`, `PATH`, and verifying compiler installation (`javac -version`, `java -version`)

Two environment variables must be set for the Java toolchain to work: `JAVA_HOME` (the install directory of the JDK) and `PATH` (which must include `$JAVA_HOME/bin`). `JAVA_HOME` is what build tools — Maven, Gradle, IntelliJ, VS Code's Java extension — read to find the JDK. `PATH` is what your shell reads to find `java` and `javac`. SDKMAN sets both automatically when you run `sdk use` or `sdk default`; if you installed manually you must set them yourself.

```bash
# Linux/macOS (bash or zsh) — manual install of Temurin 21
export JAVA_HOME=/opt/jdk-21.0.4+7
export PATH="$JAVA_HOME/bin:$PATH"

# persist to ~/.zshrc or ~/.bashrc
echo 'export JAVA_HOME=/opt/jdk-21.0.4+7' >> ~/.zshrc
echo 'export PATH="$JAVA_HOME/bin:$PATH"' >> ~/.zshrc

# verify BOTH java and javac work
java -version        # the runtime
javac -version       # the compiler
```

```powershell
# Windows (PowerShell, with manually installed JDK)
[Environment]::SetEnvironmentVariable("JAVA_HOME", "C:\Program Files\Eclipse Adoptium\jdk-21.0.4.7-hotspot", "User")
[Environment]::SetEnvironmentVariable("PATH", "$env:JAVA_HOME\bin;$env:PATH", "User")

# verify
java -version
javac -version
```

The two verification commands answer different questions. `java -version` prints the runtime version and the JVM mode (the line `OpenJDK 64-Bit Server VM` confirms the HotSpot Server JIT is active; `Zero` would mean a non-optimized port built without assembly codegen, typically seen on niche architectures like PPC64). `javac -version` prints the compiler version — if it differs from `java -version`, you have multiple JDKs installed and the wrong one is on your `PATH` first. The single most common bug is `javac: command not found` while `java -version` works fine — this means `JAVA_HOME` points to a JRE (which has `java` but not `javac`), or `PATH` was set before `JAVA_HOME/bin` was appended. A close second is the opposite: `java -version` shows Java 8 while `javac -version` shows Java 17 — your IDE pointed its compiler at JDK 17 but your shell PATH still has the old JDK 8 first.

A third verification that catches classpath and module issues early is `java -XshowSettings:properties -version`, which prints every JVM system property including `java.home`, `java.class.path`, `java.library.path`, `os.arch`, and `user.timezone`. If `java.home` points at a different directory than `JAVA_HOME`, your shell environment and the JVM's view of itself have diverged — usually because an `/etc/profile.d/jdk.sh` script is overriding your `.bashrc`. The same command shows `os.arch` (`amd64` vs `aarch64` vs `arm64`), which is what determines whether a native library (a JNI `.so`, a JNA binding) will load.

```bash
$ java -XshowSettings:properties -version 2>&1 | grep -E "(java.home|os.arch|java.class.path)"
    java.home = /home/user/.sdkman/candidates/java/21.0.4-tem
    java.class.path =
    os.arch = amd64
```

The failure mode that bites production here is timezone. `java` reads `user.timezone` from the OS `/etc/localtime` symlink at startup; if the container image's timezone is UTC (the default for `eclipse-temurin:21-jre`) but your database session timezone is `America/New_York`, every `Instant` you persist will be off by the offset. Setting `-Duser.timezone=UTC` in `JAVA_TOOL_OPTIONS` (a JVM flag that applies to every `java` invocation, picked up by Maven, Gradle, and direct `java -jar` alike) is the standard defence, alongside persisting only `Instant` and `OffsetDateTime` (which carry their own offset) and never `LocalDateTime` (which does not). Another common `JAVA_TOOL_OPTIONS` value is `-XX:MaxRAMPercentage=75.0`, which tells the JVM to size its heap to 75% of the container's memory limit instead of the default (which on early JVMs was 25% — the source of many OOMKilled containers in Kubernetes where the pod had 4 GB but the JVM only used 1 GB and the rest went to native memory and got OOMKilled by cgroups).

### Understanding the Java Classpath (`-cp`, `-classpath`) and module-path mechanisms

The classpath is the list of directories and `.jar` files the JVM searches when resolving a class reference at runtime. When your code says `import com.fasterxml.jackson.databind.ObjectMapper;`, the JVM's classloader walks the classpath entries in order and looks for `com/fasterxml/jackson/databind/ObjectMapper.class` in each entry. The first match wins. The classpath is set with `-cp` (short for `-classpath`) on the `java` and `javac` commands:

```bash
# compile a single file that depends on jackson-core and jackson-databind
javac -cp "lib/jackson-core-2.17.0.jar:lib/jackson-databind-2.17.0.jar" \
      -d build/ \
      src/com/example/Main.java

# run the compiled class
java -cp "build/:lib/jackson-core-2.17.0.jar:lib/jackson-databind-2.17.0.jar" \
     com.example.Main
```

The separator is `:` on macOS/Linux and `;` on Windows. The order matters — if two jars on the classpath contain the same fully-qualified class name, the first one wins, and the second one is silently ignored. This is the "classpath shadowing" failure mode: you have `jackson-databind-2.17.0.jar` and `jackson-databind-2.15.0.jar` on the classpath, the 2.17 version wins, but a transitive dependency that requires 2.15's API gets a `NoSuchMethodError` at runtime because the 2.17 version of the class doesn't have the method it expects. This is precisely what Maven's nearest-wins rule and Gradle's highest-wins rule exist to prevent — by enforcing a single version per coordinate across the entire dependency tree, they make this failure impossible (or at least visible at build time, not at runtime).

```text
  Classpath search (JVM, when resolving com.example.Foo):

  -cp "build/:lib/a.jar:lib/b.jar:lib/c.jar"

  build/com/example/Foo.class     ← checked first
  lib/a.jar → com/example/Foo.class  ← if not found in build/
  lib/b.jar → com/example/Foo.class  ← if not found in a.jar
  lib/c.jar → com/example/Foo.class  ← if not found in b.jar

  If none contain the class → NoClassDefFoundError at runtime
  If a.jar and b.jar both contain it → a.jar wins, b.jar's version silently ignored
                                         → NoSuchMethodError later if a.jar's version
                                           is missing a method b.jar's callers expect
```

The module path (`-p` or `--module-path`) was introduced in Java 9 alongside the Java Platform Module System (JPMS, codenamed Project Jigsaw). A module is a jar with a `module-info.class` file at its root that declares which packages it exports (`exports com.example.api;`) and which modules it requires (`requires org.slf4j;`). When a jar is placed on the module path instead of the classpath, the JVM enforces these declarations: a module cannot access a package that is not explicitly `exports`-ed, even by reflection (the `--add-opens` flag is needed to break this for libraries that reflectively access JDK internals).

```bash
# Java 9+ module path
java -p "mods/" -m com.example.app/com.example.Main

# mixing classpath and module path (common during migration)
java -cp "lib/legacy.jar" -p "mods/" -m com.example.app/com.example.Main
```

The classpath vs. module-path distinction matters because Spring Boot 3+ ships its application as a fat jar on the *classpath* (Spring's loader is not JPMS-aware — it loads classes from `BOOT-INF/classes/` and `BOOT-INF/lib/` via a custom classloader, not via the module system), but the JDK itself has been fully modularized since Java 11. The `java.*` and `javax.*` packages you import are modules (`java.base`, `java.desktop`, `java.sql`, `java.transaction.xa`, etc.) loaded from the JDK's `jmods/` directory. If your code reflectively accesses `sun.misc.Unsafe` or `java.lang.reflect` internals, Java 17+ will throw `InaccessibleObjectException` unless you pass `--add-opens java.base/java.lang.reflect=ALL-UNNAMED` on the command line. This is why Spring Boot, Lombok, Mockito, and many other libraries ship with `argLine` configuration in their build that adds dozens of `--add-opens` flags — they need to break the module boundary to do their work. GraalVM `native-image` makes this even stricter: it requires a `reflect-config.json` listing every reflective access at build time, and the build fails if your code reflects a class not in the config.

The failure mode that reveals this is the upgrade from Java 11 to Java 17. A library that worked on 11 silently fails on 17 because the internal package it reflectively accessed is now sealed. The error message is `java.lang.reflect.InaccessibleObjectException: Unable to make field private final java.lang.String java.lang.StackTraceElement.classFileName accessible: module java.base does not "opens java.lang" to unnamed module @4eec7777`. The fix is the `--add-opens` flag on the JVM command line, or migrating the library to a version that doesn't access internals. This is why Maven Surefire and Gradle Test configurations in modern Spring Boot projects have a `argLine` block full of `--add-opens` entries — they pre-empt the error for the test JVM. A typical Spring Boot 3.x test config has lines like `--add-opens=java.base/java.lang=ALL-UNNAMED`, `--add-opens=java.base/java.util=ALL-UNNAMED`, `--add-opens=java.base/java.lang.reflect=ALL-UNNAMED`, `--add-opens=java.base/java.lang.invoke=ALL-UNNAMED` — one for every JDK internal package that Lombok, Mockito, or ByteBuddy reaches into.

## Key Takeaways

1. **Install a JDK, not a JRE, and pick a distribution by its support SLA.** Temurin is the community default; Corretto is the AWS default; Zulu adds pauseless GC for paying customers; GraalVM adds AOT `native-image` for serverless cold-starts. Manage multiple versions with SDKMAN (mac/Linux), `update-alternatives` (Debian), or Scoop (Windows). Target LTS releases only (8, 11, 17, 21) — non-LTS releases are 6-month experiments.
2. **Verify with both `java -version` and `javac -version`.** If they differ, your `PATH` has a stale JDK earlier in the search order. If `javac` is missing, you installed a JRE (or the JDK bin dir is not on `PATH`). Use `java -XshowSettings:properties -version` to inspect `java.home`, `os.arch`, and `java.class.path` directly from the JVM.
3. **The classpath is order-dependent and silently shadowing.** Two jars with the same class produce a `NoSuchMethodError` at runtime, not at compile time — Maven's nearest-wins and Gradle's highest-wins exist to prevent this. The module path (`-p`) enforces `exports`/`requires` declarations and is what the JDK itself uses since Java 9. Spring Boot fat jars live on the classpath via a custom loader, not the module path.
