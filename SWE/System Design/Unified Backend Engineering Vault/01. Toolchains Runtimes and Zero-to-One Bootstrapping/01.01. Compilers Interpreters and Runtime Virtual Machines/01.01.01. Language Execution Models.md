# 01.01.01. Language Execution Models

## What This Is

Every backend language you will touch in this vault — Java, TypeScript, Python, PHP — gets from your source code to a running process through one of three execution models: ahead-of-time (AOT) compilation to native machine code, just-in-time (JIT) compilation of an intermediate bytecode, or pure interpretation. The model your language uses determines its startup time, its peak throughput, its memory footprint, and — most importantly for production debugging — the shape of the artefacts you must ship and the kind of profiling data you can collect. This note is the conceptual foundation for every runtime-specific note in sections 01.02 through 01.05: you cannot reason about JVM warmup, V8 turbofan deoptimizations, CPython's GIL, or PHP-FPM's per-request teardown until you can place each runtime on the AOT/JIT/interpreter spectrum and articulate what its compiler pipeline actually produces.

The note sits in the toolchain layer — below it is the OS (section 02), which provides the process, the virtual memory, and the CPU the runtime targets; above it are the framework notes (section 05) whose idioms assume a particular runtime model. When a Spring Boot service takes 25 seconds to accept its first request, or when a Lambda cold-starts in 800 ms vs 50 ms depending on the language, or when a Python web worker saturates a single CPU core despite four being available, the root cause traces back to this note.

## The Details

### Ahead-of-Time (AOT) Compilation vs. Just-In-Time (JIT) Compilation vs. Pure Interpretation

AOT compilation is the model where the entire program is translated from source to native machine code *before* it ever runs. The canonical AOT pipeline in C is `gcc hello.c -o hello`, which internally forks four stages: `cpp` (preprocessor, expands `#include` and `#define`), `cc1` (the real compiler, lexes/parses/optimizes/emits assembly), `as` (assembler, turns assembly into an `.o` object file of machine code), and `ld` (linker, resolves symbols across object files and shared libraries, emits the final ELF binary). Go is the most backend-relevant AOT language: a statically-linked Go binary starts in single-digit milliseconds because there is no VM to initialize, no bytecode to verify, and no JIT to warm up. Rust adds LLVM IR as an intermediate step — `rustc` lowers source to LLVM IR, LLVM runs ~60 optimization passes, and LLVM's codegen emits native code. The price AOT pays is flexibility: the compiler cannot see runtime behaviour, so all optimization decisions are made from static analysis. If a generic function is called with 30 different types, an AOT compiler either monomorphizes 30 copies (binary bloat — Rust's `cargo bloat` will show you) or emits one polymorphic dispatch (runtime cost). The Go compiler mostly chooses the latter and accepts the dispatch overhead.

JIT compilation sits in the middle. The toolchain produces a portable bytecode ahead of time — JVM `.class` files, V8's ignition bytecode, CPython's `.pyc`, .NET's IL — and a runtime virtual machine loads that bytecode at process start, interprets it, profiles which methods are hot, and recompiles the hot ones to native code on the fly. The Java pipeline is `javac Hello.java` → `Hello.class` (bytecode) → the JVM's classloader loads it → the interpreter (template interpreter in HotSpot) starts executing → after ~10,000 invocations the C1 compiler kicks in (tier 3) → after ~10,000 more the C2 compiler kicks in (tier 4) with aggressive optimizations based on profiling data. JavaScript in V8 follows a similar tiering: source → Ignition bytecode interpreter → Sparkplug baseline compiler → Maglev mid-tier → TurboFan optimizing compiler. PyPy uses a tracing JIT that records the actual control flow of a hot loop and compiles a specialized version. .NET's RyuJIT does tiered compilation since .NET 6. The advantage is two-fold: the bytecode is portable (compile once on a developer laptop, run on any JVM), and the JIT can use runtime profiling that an AOT compiler cannot — it knows that `list.size()` returns 4 every time this loop runs, so it inlines the call and unrolls four iterations. The cost is warmup: a JVM that handles 5,000 req/s at steady state might handle 500 req/s for the first 30 seconds while the JIT compiles. In serverless this is fatal — AWS Lambda's provisioned concurrency exists precisely to keep JVMs warm — and in CLI tools it is why `java -jar` feels slow even for a hello world.

Pure interpretation is the oldest model: the runtime walks the AST or token stream and executes each node directly, with no compilation step at all. Early CPython (pre-2.6 ish), Ruby MRI < 1.9, bash, and most shell tools are pure interpreters. The advantage is simplicity and instant start — there is no compile step, no bytecode cache, no JIT warmup. The disadvantage is throughput: every iteration of a hot loop re-parses the same AST nodes. Modern "interpreted" languages are almost all bytecode interpreters in disguise — CPython compiles to bytecode (a stack-machine format with ~250 opcodes like `LOAD_FAST`, `BINARY_ADD`, `CALL_FUNCTION`) and caches it in `__pycache__`, then the `PyEval_EvalFrameDefault()` function in `Python/ceval.c` runs a giant `switch (opcode)` loop over the bytecode. Ruby 1.9+ uses the YARV bytecode VM. PHP 4+ compiles source to Zend opcodes (the `ZEND_AST` → `zend_compile()` → `op_array` pipeline in `Zend/zend_compile.c`) and executes them via `execute_ex()` in `Zend/zend_vm_execute.h`; PHP 8's OPcache caches the compiled opcodes across requests and the optional JIT (via the dynasm library) compiles hot opcodes to native code. The only place pure interpretation survives is glue: bash, awk, the Python REPL's `-c` flag.

```text
                    AOT (Go, Rust, C/C++)
  source ──[cpp→cc1→as→ld]──► native ELF/Mach-O/PE ──[execve]──► CPU
                                ▲
                                │ static optimization only
                                │ fast startup (5–50 ms), no warmup
                                │ binary not portable (per-arch)

                    JIT (JVM, V8, .NET, PyPy)
  source ──[javac / tsc / compile()]──► bytecode (.class / .pyc / IL)
                                          │
                                          ▼
                                    ┌────────────┐
                                    │ VM loader  │
                                    │ interpreter│ ──fast startup, slow steady-state
                                    │  (template │   JVM: HotSpot interpreter
                                    │   /Ignition│   V8:   Ignition interpreter
                                    │   /ceval)  │   Py:   PyEval_EvalFrameDefault
                                    └─────┬──────┘
                                          │ profile hot methods
                                          │   (10k invocations threshold)
                                          ▼
                                    ┌────────────┐
                                    │ JIT compiler│ ──slow startup, fast steady-state
                                    │ (C2/TurboFan│  uses runtime profiling:
                                    │  /RyuJIT)   │  inlining, escape analysis,
                                    └─────┬──────┘   spec devirtualization
                                          ▼
                                      native code in code cache
                                      (per-method nmethod / Code object)

                    Interpreter (bash, awk, REPL -c)
  source ──[parse]──► AST ──[walk]──► execute
                          ▲
                          │ no compilation, no cache
                          │ instant start, worst throughput
```

The production failure mode that distinguishes these three is cold-start budget. An AOT Go binary in an AWS Lambda cold-starts in ~50 ms. A JVM Lambda cold-starts in 800–3000 ms depending on whether you've layered in Spring (Spring's component scan and auto-configuration add ~2 s on top of JVM init). A Python Lambda sits in the middle at ~200 ms. When you architect for serverless or for Kubernetes scale-from-zero, this difference is the difference between a 1-second and a 5-second first response — and the only way to fix it is to switch language or to use a native-image AOT compiler like GraalVM `native-image` for the JVM, which trades peak throughput (no JIT can recompile based on runtime profiling) for ~50 ms cold-start. GraalVM native-image is what Quarkus and Spring Native use to bring JVM cold-starts down to the Go/Rust range; the trade-off is that reflection must be configured at build time via `reflect-config.json`, and any class that the analyzer misses will fail at runtime with a `ClassNotFoundException` that an interpreter/JIT JVM would have loaded lazily.

### Source Code → Abstract Syntax Tree (AST) → Intermediate Representation (IR) → Bytecode → Native M...

Every compiler — AOT or JIT — walks the same pipeline. Source text enters at the top and machine code exits at the bottom; the intermediate representations are the contracts between passes. Understanding this pipeline is what lets you read a compiler error message and know which pass produced it, or read a `-XX:+PrintCompilation` log and know whether the JIT deoptimized before or after inlining.

Lexical analysis (the lexer, or scanner) reads source characters and emits tokens. `x = 1 + 2` becomes `IDENT(x) EQUALS INT(1) PLUS INT(2)`. Whitespace and comments are discarded here. The lexer's job is also to reject characters that cannot be part of any token — a stray `@` in C is a lexer error. In gcc this is `libcpp`'s tokenizer; in CPython it is `Parser/tokenize.c`; in V8 it is `src/parsing/scanner.cc`; in the HotSpot `javac` it is `com.sun.tools.javac.parser.Scanner`. Parsing consumes the token stream and builds an AST that captures the *syntactic* structure: `BinaryOp(+, IntLiteral(1), IntLiteral(2))` assigned to `x`. The grammar (LL, LR, PEG, Pratt) determines which syntactic forms are accepted; this is where Python's significant whitespace, JavaScript's automatic semicolon insertion, and Ruby's `do |x| ... end` blocks are validated.

Semantic analysis walks the AST and resolves names, checks types, and applies scope rules. `x = 1 + 2` requires that `+` is defined for `int`, that `x` is in scope (or is being declared), and that the assignment is well-typed. This is where most of the user-visible error messages come from — "cannot find symbol", "expected Int but got String", "use of possibly uninitialized variable". After semantic analysis the AST is lowered to an intermediate representation (IR): a lower-level, more uniform language designed for optimization passes. LLVM IR (used by Rust, Clang, Swift), the JVM bytecode format, .NET's CIL, CPython's `dis` output, and Go's SSA (`cmd/compile/internal/sssa`) are all IRs. The IR is where optimization happens — constant folding (`1 + 2` becomes `3`), dead code elimination, inlining, escape analysis, loop unrolling, devirtualization. The JVM's C2 compiler has roughly 60 optimization passes that run on its SSA-form "sea-of-nodes" IR. GraalVM replaces C2 with a Java-written optimizer called Graal that exposes the same IR through the `org.graalvm.compiler` API. Go's compiler is famously light on optimization — it does inlining, escape analysis, and a small number of SSA passes, but skips the aggressive auto-vectorization and polyhedral loop transforms that LLVM does, which is part of why Go binaries have predictable but rarely stellar performance.

Finally the IR is emitted as either bytecode (for a JIT runtime to consume later) or as native machine code (for AOT). For native code, a linker resolves symbols against shared libraries and emits the final ELF/Mach-O/PE binary. For bytecode, the linker step happens at runtime — the JVM's classloader resolves symbolic references in `.class` files against the classpath on first use. This is why a Java program can compile fine and then throw `NoClassDefFoundError` at runtime: the linker step is deferred. CPython does the same trick with `__pycache__/*.pyc` — the bytecode is the cached IR, and if the source's mtime + size + magic tag matches, the `.pyc` is loaded directly without re-running the lexer/parser.

```text
   hello.java             hello.py                hello.go                hello.c
       │                      │                       │                       │
       ▼                      ▼                       ▼                       ▼
    lexer ──► tokens       lexer ──► tokens       lexer ──► tokens       cpp ──► tokens
       │                      │                       │                       │
       ▼                      ▼                       ▼                       ▼
    parser ──► AST         parser ──► AST         parser ──► AST         cc1 parser ──► AST
   (OpenJDK                (PEG parser,            (go/parser)            (gcc)
    javac)                  Grammar/)                  │
       │                      │                       │                       │

    (resolve, check        (symtable.c,           (gc.Type)               (c-typeck.c)
     types)                 ast_optimize.c)
       │                      │                       │                       │
       ▼                      ▼                       ▼                       ▼
    IR: JVM bytecode       IR: CPython            IR: SSA (Go)           IR: GIMPLE → RTL

     machine)               stack machine)            │                       │
       │                      │                       ▼                       ▼
       ▼                      ▼                   [AOT] codegen             [AOT] codegen
    [runtime JIT           [runtime                 → ELF/Mach-O            → ELF/Mach-O
```

The failure mode that this pipeline explains is the difference between a *compile-time error* and a *runtime error*. In Java, type errors are caught at semantic analysis (compile time). In Python, type errors are caught when the bytecode interpreter executes the bad instruction (runtime). In TypeScript, type errors are caught by `tsc` (compile time) but erased before runtime — your `number` annotation does not exist in the emitted JavaScript, so a function declared `(x: number) => x * 2` becomes `(x) => x * 2` and silently misbehaves if called with a string at runtime. In PHP with `declare(strict_types=1)`, type errors in function signatures are checked at the Zend VM's opcode handler level — without strict_types, PHP coerces `"5"` to `5` silently, which is the source of countless off-by-one bugs. Knowing which pass catches a given bug is the difference between "fix it in the editor before saving" and "find it in the production logs at 3 a.m.".

### CPU Instruction Sets (x86-64 vs. ARM64) and platform ABI (Application Binary Interface) boundaries

A "native binary" is only native to one CPU instruction set. An ELF compiled for x86-64 cannot run on an ARM64 machine — the opcodes mean different things, the register file is different, the calling convention is different. This is why Docker images are tagged `amd64` and `arm64`: a `python:3.12` image pulled on an M2 MacBook (arm64) is a different binary from the same tag pulled on an Intel Xeon server (amd64). The M2's Rosetta 2 translator exists precisely to bridge this gap, translating x86-64 opcodes to ARM64 opcodes on the fly at a ~20% performance penalty. AWS Graviton (arm64) instances are ~20% cheaper than equivalent x86-64 instances, which is why many teams cross-compile their Go/Rust binaries with `GOARCH=arm64 go build` or `rustup target add aarch64-unknown-linux-gnu` to ship to Graviton fleets.

The instruction set is only half the story. The Application Binary Interface (ABI) defines the calling convention: which registers hold the first integer argument, which hold the first floating-point argument, how the stack is aligned, how variadic functions pass arguments, how return values are passed back, and how exception unwinding works. The System V AMD64 ABI (Linux, macOS) puts the first six integer arguments in `rdi, rsi, rdx, rcx, r8, r9` and the first eight floating-point arguments in `xmm0–xmm7`. The Microsoft x64 ABI (Windows) uses `rcx, rdx, r8, r9` for the first four integer arguments and requires 32 bytes of shadow space on the stack. The AArch64 ABI (ARM64, both Linux and macOS) puts the first eight integer arguments in `x0–x7` and the first eight FP arguments in `v0–v7`. A static library compiled with one ABI cannot link against a program built with another.

```text
                     x86-64 (System V)         x86-64 (Windows)         ARM64 (AArch64)
  first int arg      rdi                       rcx                      x0
  second int arg     rsi                       rdx                      x1
  third int arg      rdx                       r8                       x2
  fourth int arg     rcx                       r9                       x3
  first FP arg       xmm0                      xmm0                     v0
  stack alignment    16 bytes                  16 bytes                 16 bytes
  shadow space       no                        32 bytes                 no
  syscall number     rax                       (Windows API)            x8
  syscall instr      syscall                   (Wow64)                  svc #0
  return value       rax                       rax                      x0
  callee-saved       rbx, rbp, r12-r15         rbx, rbp, rdi, rsi,      x19-x28, x29(fp)
                                              r12-r15
  frame pointer      rbp                       rbp                      x29 (fp)
  link register      (none, return on stack)   (none)                   x30 (lr)
```

This matters for backend engineering in three concrete places. First, when you build a multi-arch Docker image with `docker buildx`, you are implicitly rebuilding the same source for two different instruction sets and producing two separate binaries under the same image tag with different manifest digests. The `docker manifest inspect` command shows the per-architecture entries. Second, when you link a native library (a Python C extension, a JNI `.so`, a Node `.node` addon), the library must match both the CPU instruction set and the ABI of the host process — a `cp38-cp38-manylinux2014_x86_64.whl` wheel will refuse to install on `linux_aarch64` because the CPython extension ABI tag encodes the platform. The error from `pip install` is `ERROR: Package 'X' has a metadata issue: Cannot install on aarch64`; the fix is to find a `cp38-cp38-manylinux2014_aarch64.whl` or build from source with a working C toolchain. Third, when you compile a Rust or Go binary on an M2 Mac and `scp` it to an Intel Linux server, it will fail with `Exec format error` because the binary is ARM64 and the kernel is x86-64 — you must cross-compile with `GOARCH=amd64 go build` or `cargo build --target x86_64-unknown-linux-gnu`.

The cross-architecture story is also why the JVM's "compile once, run anywhere" pitch is misleading. The Java *source* compiles to portable bytecode, but the JVM itself is a native binary that must be compiled separately for each instruction set — there is a `java` for x86-64 Linux, a different `java` for arm64 macOS, a different `java` for s390x mainframe. The bytecode is portable; the runtime that interprets and JIT-compiles it is not. The same is true for Node.js (V8 has separate code generators for x64 and arm64 in `src/codegen/`), CPython (the interpreter loop in `Python/ceval.c` is compiled per-arch with macro specialization that produces different machine code for `LOAD_FAST` on x86-64 vs arm64), and PHP (the Zend VM in `Zend/zend_vm_execute.h` is C compiled per-arch, and the JIT backend in `ext/opcache/jit/` has separate files for x86_64 and arm64). When you ship a "portable" language runtime into production, you are shipping a per-architecture native binary that knows how to interpret your portable bytecode — and that native binary, in turn, is compiled by gcc/clang with a specific ABI, against a specific libc (glibc vs musl — the source of the Alpine Docker image incompatibility with Debian-built binaries), for a specific kernel version range. The "compile once, run anywhere" guarantee is real, but only at the bytecode layer; everything below that is per-arch and per-OS.

## Key Takeaways

1. **Cold-start budget is dictated by execution model.** AOT binaries start in tens of milliseconds (Go, Rust, GraalVM native-image); JIT runtimes pay 200 ms–3 s of warmup before peak throughput (JVM C1→C2 tiering, V8 Ignition→TurboFan, PyPy tracing); pure interpreters start instantly but never get fast (bash, awk). Choose your runtime by whether your workload is long-running (JIT wins) or ephemeral (AOT wins).
2. **The compiler pipeline is the same six stages in every language.** Lexer → parser → semantic analysis → IR → optimization → codegen. Knowing which stage produced an error tells you whether it is fixable in the editor or only at runtime — Java types are compile-time, Python types are runtime, TypeScript types are compile-time-only and erased.
3. **"Native" is per-architecture and per-ABI.** A binary compiled for x86-64 System V will not run on ARM64 AArch64, and a shared library compiled for one ABI will not link against a process built with another. Multi-arch container images, wheel platform tags, and JNI `.so` files all encode this constraint — and the JVM/Node/CPython/PHP "portable bytecode" runtimes are themselves per-arch native binaries.
