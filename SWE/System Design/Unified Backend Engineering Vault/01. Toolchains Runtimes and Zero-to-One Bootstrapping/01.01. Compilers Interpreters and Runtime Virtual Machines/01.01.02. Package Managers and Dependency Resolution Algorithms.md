# 01.01.02. Package Managers and Dependency Resolution Algorithms

## What This Is

A package manager is the part of the toolchain that takes a declaration of "I depend on these libraries" and produces a concrete, on-disk installation of those libraries — including every library they in turn depend on, transitively, down to the leaves. Every backend ecosystem has one: `npm`/`pnpm`/`yarn` for Node, `pip`/`poetry`/`uv` for Python, `composer` for PHP, `maven`/`gradle` for the JVM. They differ in their manifest format, their lockfile format, and their on-disk layout, but they all solve the same algorithmic problem: resolve a set of version constraints over a dependency graph into a single, acyclic, satisfiable assignment of versions. This note explains the resolution algorithm, the semver range language the constraints are written in, and the role lockfiles play in making the resolution deterministic. Without this machinery, "works on my machine" is the only deployment story you have.

The note sits at the same conceptual layer as [[01.01.01. Language Execution Models]] — both are about how the toolchain transforms source into a running process — but where that note covers the *compilation* half, this one covers the *composition* half. The two halves meet at the import statement: when your `import express from "express"` line runs, the runtime asks the package manager's on-disk layout to find the entry point, and the layout was produced by the resolution algorithm explained below. The failure modes this note governs are the ones that produce `ModuleNotFoundError`, `Cannot find module`, `Class not found`, or — worse — silently using a different version of a transitive dependency in CI than on your laptop.

## The Details

### Dependency graph construction, transitive dependencies, and Directed Acyclic Graphs (DAGs)

A dependency graph is a directed graph where an edge from A to B means "A requires B". The graph is required to be acyclic — if A depends on B and B depends on A, neither can be built, and the package manager rejects the cycle. The graph is also versioned: each edge carries a version constraint ("A requires B at version ^1.2.0"), and each node has a single concrete version chosen by the resolver. The resolver's job is to pick, for every node in the graph, a single version that satisfies every incoming edge simultaneously. If A requires `B@^1.0.0` and C requires `B@^1.2.0`, the resolver must find a version of B that is `>=1.2.0, <2.0.0` — for example `B@1.4.7`.

Transitive dependencies are the nodes you didn't ask for but got anyway. You declared `express@^4.18`, but `express` itself depends on `body-parser`, `cookie`, `debug`, `qs`, `send`, and ~60 other packages, each of which depends on more packages, and the closure of that relation can easily reach 200 packages for a single web framework. This is why `npm install express` writes 200 entries to `node_modules` — the package manager is materializing the transitive closure of the dependency graph, not just the one package you asked for. Maven prints this closure with `mvn dependency:tree`, Gradle with `./gradlew dependencies`, pip with `pip show <pkg>` (direct deps) or `pip-tools`'s `pip-compile` (full tree with hashes), Composer with `composer show --tree`, and npm with `npm ls --all`.

The diamond problem is the canonical hard case. App depends on LibA and LibB. LibA depends on `Utils@^1.0.0`. LibB depends on `Utils@^2.0.0`. There is no version of Utils that satisfies both constraints simultaneously — `^1.0.0` means `>=1.0.0, <2.0.0` and `^2.0.0` means `>=2.0.0, <3.0.0`. Different package managers handle this differently:

```text
  App
   ├── LibA ──► Utils@^1.0.0   (>=1.0.0, <2.0.0)
   └── LibB ──► Utils@^2.0.0   (>=2.0.0, <3.0.0)

  npm / yarn (classic):  install BOTH versions side-by-side
                          node_modules/
                            libA/node_modules/utils/   ← 1.4.7  (nested)
                            libB/node_modules/utils/   ← 2.1.0  (nested)
                          (npm v3+ "flattens" by hoisting the first-seen
                           version to top-level and nesting the others)

  pnpm:                  single source of truth in a content-addressable store
                          ~/.local/share/pnpm/store/v3/files/
                            xx/xxxxxx  ← content hash, deduplicated
                          node_modules/
                            .pnpm/                    ← virtual store
                              utils@1.4.7/node_modules/utils   → symlink to store
                              utils@2.1.0/node_modules/utils   → symlink to store
                              libA/node_modules/utils           → symlink to ../utils@1.4.7/...
                              libB/node_modules/utils           → symlink to ../utils@2.1.0/...
                            utils/                    ← top-level, only direct deps
                          (saves disk: 200-package Express install ~700MB
                           under npm vs ~80MB under pnpm)

  pip (without resolver):   installs whichever it sees LAST
                            (pre-2020 pip was non-deterministic here; pip 20.3+
                             introduced the new resolver that backtracks)

  maven:   picks the NEAREST version in the dependency tree
           (whichever Lib is declared first in pom.xml wins → Utils@1.4.7)
           coordinates are groupId:artifactId:version, e.g.
           com.fasterxml.jackson.core:jackson-databind:2.17.0

  gradle:  picks the HIGHEST version that satisfies any constraint
           → conflict, because no single version satisfies both
           → either force a version or exclude one transitive dep

  composer:   refuses to install, reports the conflict,
              requires an explicit alias or conflict declaration
```

The DAG property is what makes resolution tractable: a topological sort gives the install order, and a SAT solver can find a satisfying assignment in polynomial time for most real-world graphs. pip's old resolver was greedy and depth-first — it walked the graph in declaration order, picked the first satisfying version for each package, and never backtracked when a later constraint failed. This is why `pip install` historically produced "I got version 1.4.7 last week but 1.5.0 this week with the same requirements.txt" — the resolver's choices depended on the order packages appeared in the file. The new resolver (pip 20.3, December 2020) uses backtracking and produces a deterministic, reproducible resolution given the same input. PubGrub, the algorithm used by Dart's pub and adopted by other ecosystems, is the modern state of the art: it combines version range solving with conflict-driven clause learning borrowed from SAT solvers.

Peer dependencies are a special edge type: A *peers* B means "A requires that the consumer of A also install B, in a compatible version, alongside A". This is how plugin ecosystems work — `react-dom` peers `react`, `@nestjs/typeorm` peers `@nestjs/core` and `typeorm`, `@angular/core` peers `rxjs` and `zone.js`. The peer constraint is not satisfied by the resolver installing B in a nested node_modules; it is satisfied only by B being present at the top level of the consumer's dependency tree. npm 7+ auto-installs peer dependencies, which has caused many silent breakages when a package's peer range is too permissive and the resolver picks a version that breaks at runtime. Maven has no concept of peer deps — every dep is a normal dep — which is why transitive dependency conflicts in Maven are so common. Composer has the `provide` keyword for similar cases (a package declares that it provides an interface another package requires), and pip has no peer concept at all, which is why Django + Celery + Redis client version compatibility must be hand-curated. The production failure mode is "works in dev, breaks in CI" because the local `node_modules` was installed by `npm install` (which updates the lockfile) while CI ran `npm ci` (which strictly installs the lockfile) — see the lockfile section below for the fix.

### Semantic Versioning (`semver`) parsing: Exact, tilde (`~`), caret (`^`), and version ranges

Semantic Versioning (semver) is the convention that version numbers communicate compatibility. A version is `MAJOR.MINOR.PATCH`: MAJOR increments on backwards-incompatible changes, MINOR on backwards-compatible feature additions, PATCH on backwards-compatible bug fixes. The contract is that a consumer who depends on `1.2.3` can safely upgrade to any `1.x.y` (the MINOR and PATCH bumps are guaranteed not to break them) but must treat a bump to `2.0.0` as a breaking change requiring migration. Semver 2.0.0 (the spec at semver.org) also defines pre-release suffixes (`1.0.0-alpha.1`, `1.0.0-beta.2`, `1.0.0-rc.1`) and build metadata (`1.0.0+20240915`); pre-releases sort before the release, so `1.0.0-rc.1 < 1.0.0`.

Range operators express how flexible the consumer is about which versions satisfy them:

| Operator | Example | Meaning | Accepts `1.2.3`? | Accepts `1.3.0`? | Accepts `2.0.0`? |
|---|---|---|---|---|---|
| Exact | `1.2.3` | only `1.2.3` | yes | no | no |
| Caret `^` | `^1.2.3` | `>=1.2.3, <2.0.0` (allow MINOR + PATCH) | yes | yes | no |
| Tilde `~` | `~1.2.3` | `>=1.2.3, <1.3.0` (allow PATCH only) | yes | no | no |
| Range | `>=1.0.0 <2.0.0` | explicit bounds | yes | yes | no |
| Wildcard | `1.2.x` | any `1.2.*` | yes | no | no |
| `||` | `^1.0.0 \|\| ^2.0.0` | union of ranges | yes (in 1.x) | yes (in 1.x) | yes (in the 2.x) |

The caret `^` is npm's default and the most permissive sensible range — it trusts the package author to honor semver and lets the resolver upgrade MINOR versions automatically. The tilde `~` is more conservative: it only allows PATCH upgrades. Pinning to an exact version (`1.2.3` with no operator) is the most conservative of all and is what lockfiles effectively do for the resolved set. The npm CLI's `npm install express` writes `"express": "^4.18.0"` to `package.json` by default; you can change this with `--save-exact` or `npm config set save-exact=true`. Python's `pip` has no equivalent default — `pip install` doesn't modify any manifest; you must explicitly run `pip freeze > requirements.txt` (which captures exact versions, like npm's `--save-exact`) or use `pip-compile` (which respects your declared ranges and produces an exact lockfile).

The dirty secret of semver is that it is a social contract, not a mechanical one. A package author who bumps the version from `1.4.0` to `1.4.1` (a PATCH) but accidentally changes the behaviour of a function has broken the contract — and there is no automated check that catches this. The npm registry's left-pad incident in 2016 (an 11-line package unpublished, breaking thousands of builds including React and Babel) is the canonical example of why trusting transitive caret ranges is dangerous. The defence is the lockfile: even if the upstream package is republished at a different version, your lockfile pins the exact version and integrity hash you tested against.

Maven's version ranges are subtly different. `[1.2.3]` is an exact version (square brackets, not bare), `[1.2.3, 2.0.0)` is a half-open range (`>=1.2.3, <2.0.0` — square bracket = inclusive, parenthesis = exclusive), and a bare `1.2.3` is treated as a "soft" version that the resolver may override if a different version is requested elsewhere in the graph. This is why Maven builds frequently resolve to a different version than the one declared in `pom.xml` — the nearest-wins rule means a transitive dependency's version can override your direct declaration if it appears closer to the root of the graph. Composer uses tilde and caret with the same semantics as npm. pip's requirement specifiers support `==`, `>=`, `<=`, `>`, `<`, `~=`, and `===`; `~=1.4.2` means `>=1.4.2, <1.5.0` (compatible with caret semantics for the last bumped component), `==1.4.*` is a wildcard match, and `===` is an arbitrary-equality operator used only for hash-pinned installs. Composer's caret has one quirk: for versions `0.x.y`, caret behaves like tilde (allows only PATCH bumps) because pre-1.0 versions are assumed to be unstable.

### Lockfiles (`pom.xml`, `package-lock.json`, `poetry.lock`, `composer.lock`): Deterministic builds ...

A lockfile is the resolution algorithm's output, frozen in time. It records the exact version of every package in the transitive closure, plus an integrity hash (sha-512 for npm, sha-256 for pip, sha-384 for composer) of the package's tarball. The lockfile is what makes a build reproducible: given the same lockfile, the package manager installs the exact same bytes on every machine, regardless of when the install runs or what versions upstream maintainers have published since.

The manifest vs. lockfile distinction is the key mental model. The *manifest* (`package.json`, `pyproject.toml`, `composer.json`, the `<dependencies>` block of `pom.xml`) is what you, the developer, write: it contains ranges. The *lockfile* (`package-lock.json`, `poetry.lock`, `composer.lock`, the effective resolved `<dependencyManagement>` block in Maven) is what the package manager generates: it contains exact versions. The manifest is human-authored and lives in version control. The lockfile is machine-authored and *also* lives in version control — committing the lockfile is the single most important discipline in dependency management.

```text
  package.json (manifest, human-written):
    "dependencies": {
      "express": "^4.18.0"      ← a range; allows any 4.x ≥ 4.18.0
    }

  ─── npm install ───►   resolves the graph, picks versions, writes:

  package-lock.json (lockfile, machine-written, committed to git):
    "node_modules/express": {
      "version": "4.19.2",      ← the chosen version
      "resolved": "https://registry.npmjs.org/express/-/express-4.19.2.tgz",
      "integrity": "sha512-5So/...==",   ← sha-512 of the tarball
      "requires": { ... }       ← transitive deps with their exact versions
    },
    "node_modules/body-parser": { "version": "1.20.2", ... },
    ... 200 more entries ...

  ─── npm ci ───►   reads lockfile, downloads exactly those tarballs,
                    verifies each integrity hash, refuses to proceed
                    if a hash mismatches. Deterministic.

  ─── npm install ───►   reads manifest, MAY update lockfile if
                          upstream has published a newer 4.x.
                          Non-deterministic. NEVER run this in CI.
```

The two install commands that look identical — `npm install` and `npm ci` — behave completely differently, and conflating them is the most common CI bug in Node projects. `npm install` resolves the manifest, may upgrade the lockfile to newer satisfying versions, and writes the new lockfile. `npm ci` deletes `node_modules`, reads the lockfile, installs exactly those versions, and never updates the lockfile. CI must always use `npm ci`. The pip equivalents are `pip install -r requirements.txt` (may upgrade, like `npm install`) and `pip install --require-hashes -r requirements.txt` (verifies hashes, like `npm ci`). Composer has `composer install` (lockfile-respecting) and `composer update` (manifest-respecting, upgrades the lockfile) — the same two-command split. Poetry makes this even more explicit: `poetry install` reads `poetry.lock` and `poetry update` re-resolves and writes a new `poetry.lock`. Yarn has `yarn install` (lockfile-respecting, with `--frozen-lockfile` for CI) and `yarn upgrade`. Modern Gradle added `--write-locks` to generate `gradle.lockfile`, but by default Gradle resolves at every build from the manifest — there is no committed lockfile unless you explicitly opt in.

Maven is the odd one out: it has no separate lockfile format. The `pom.xml` itself is both manifest and lockfile, because Maven's convention is to declare exact versions (not ranges) for every dependency, including transitive ones via `<dependencyManagement>`. The `mvn dependency:tree` command reconstructs the resolved graph from the effective POM; the `mvn dependency:purge-local-repository` command forces a fresh resolve. The Maven coordinate system — `groupId:artifactId:version` (e.g. `org.springframework.boot:spring-boot-starter-web:3.3.0`) plus an optional `classifier` and `type` for variants like `sources` or `javadoc` — is what identifies a unique artifact in any Maven repository (Maven Central, an internal Nexus, or GitHub Packages). The same coordinate system is used by Gradle (`implementation "org.springframework.boot:spring-boot-starter-web:3.3.0"`).

The integrity hash is the lockfile's defence against supply-chain attacks. When npm downloads `express-4.19.2.tgz`, it computes the sha-512 of the bytes and compares against the `integrity` field in `package-lock.json`. If they mismatch — because someone compromised the registry, or because a maintainer republished the same version with different code (npm allows this within 72 hours of publish), or because a corporate proxy injected a different tarball — npm refuses to install. This is why `npm audit` runs against the lockfile, not the manifest: the audit knows exactly which version of every package you have installed, including transitives. Composer adds an additional defence: the `composer.lock` records the commit hash of every package if it was installed from source (e.g. from a GitHub repo rather than Packagist), making `composer install` bit-for-bit reproducible even when the upstream `master` branch moves.

The other half of determinism is *isolation*. The Node `node_modules` directory is per-project by default — every project gets its own tree. Python is the opposite: `pip install` historically wrote into the system Python's `site-packages`, which polluted the system interpreter and caused "I uninstalled the package but `apt-get` broke" disasters. The fix is `venv` (standard library, `python -m venv .venv`) which creates an isolated Python environment with its own `site-packages`. `pipx` goes one step further and installs CLI tools (like `black`, `mypy`, `httpie`) each in their own venv, then symlinks the binary onto `~/.local/bin`. `poetry` and `uv` manage venvs per-project automatically. The ultimate isolation is the container: `docker run --rm -it python:3.12-slim` gives you a fresh Python that has never seen your system's packages. The PHP story is similar — Composer installs everything into `vendor/` per-project (the equivalent of `node_modules`), and the PHP-FPM pool runs as a per-app process. Java's story is different: Maven's `~/.m2/repository/` is a *global* cache shared across all projects on the machine (like pip's old behaviour), but because Maven coordinates are globally unique (`groupId:artifactId:version`), there is no conflict — every project pulls its exact version from the cache. This is also why a clean Maven build is fast after the first one: the artifacts are already in `~/.m2/repository/` and don't need to be re-downloaded.

The failure mode this prevents is "my laptop has version 1.4.7, CI has version 1.5.0, production has 1.4.9" — three different versions of the same transitive dependency, all satisfying the same `^1.4.0` range, all installed at different times as the upstream package released patches. The bug only manifests in production because production is the only environment running 1.4.9, and the only way to reproduce it locally is to delete `node_modules`, run `npm ci`, and hope the lockfile was committed. The fix is process discipline: commit the lockfile, use `npm ci` in CI, never run `npm install` against a registry that has changed since the lockfile was written, and rotate dependencies with Dependabot/Renovate in small, reviewable PRs that re-run the test suite against the upgraded lockfile.

## Key Takeaways

1. **The dependency graph is a versioned DAG with constraints on every edge.** The resolver's job is to pick one version per node that satisfies all incoming edges; the diamond problem (two paths to the same node with incompatible ranges) is the hard case every resolver must handle — npm nests, pnpm symlinks from a content-addressable store, Maven picks nearest-wins, Gradle picks highest, Composer refuses.
2. **Semver is a social contract enforced by ranges.** Caret `^` allows MINOR+PATCH upgrades, tilde `~` allows only PATCH, exact `1.2.3` pins. Trust the contract for direct dependencies; verify it with the lockfile for transitives. Maven's coordinate system (`groupId:artifactId:version`) is the JVM equivalent of npm's `name@version`.
3. **The lockfile is the contract between your laptop and production.** Commit it to git, install from it with `npm ci`/`pip install --require-hashes`/`composer install`/`poetry install`, and treat any drift between manifest and lockfile as a CI failure. Isolation (`venv`, `pipx`, per-project `vendor/`, Maven's global `~/.m2`) is the other half of determinism — never `sudo pip install` into the system interpreter.
