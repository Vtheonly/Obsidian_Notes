# 01.03.01. Installing Node.js and Version Management

## What This Is

Node.js is the JavaScript runtime built on the V8 engine, the libuv event loop, OpenSSL, and a small set of C libraries. To write TypeScript backend services you must install the Node.js binary, set up a version manager so multiple projects can use different Node versions side-by-side, and configure the package manager (`npm` or `pnpm`). This is the Node equivalent of [[01.02.01. Installing JDK and Environment Configuration]] for the JVM, and it sits at the same conceptual layer — every subsequent note in sub-section 01.03 assumes you have a working `node` and `npm` on your `PATH`. The failure modes this note governs are the ones that surface as "this project requires Node 20 but I have 18 installed", "`nvm: command not found` in CI", or "pnpm install creates a different `node_modules` than npm install did on the same `package.json`".

The Node toolchain differs from the JVM toolchain in one important respect: Node has no concept of "LTS releases the way Java does". The Node release schedule alternates between LTS (Long-Term Support, 30 months) and Current (6 months) every major version — even-numbered majors (18, 20, 22) become LTS, odd-numbered (19, 21, 23) are short-lived. This means a Node project pinned to "Node 21" becomes unsupported within months, while one pinned to "Node 20" gets security patches for 2.5 years. Always target an LTS in production.

## The Details

### Installing Node.js via Fast Node Manager (`fnm`) and Node Version Manager (`nvm`)

A version manager lets you install multiple Node versions side-by-side and switch between them per-project, driven by a `.nvmrc` or `.node-version` file in the project root. Without one, you are stuck with whatever the OS package manager shipped (which is usually 6–12 months behind, and you cannot have two versions installed at once). The two dominant version managers are `nvm` (Node Version Manager, bash-based, slow, the original) and `fnm` (Fast Node Manager, Rust-based, fast, the modern choice).

```bash
# ─── nvm (bash, slow, ubiquitous) ─────────────────────────────
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.39.7/install.sh | bash
# adds the following to ~/.bashrc (or ~/.zshrc):
#   export NVM_DIR="$HOME/.nvm"
#   [ -s "$NVM_DIR/nvm.sh" ] && \. "$NVM_DIR/nvm.sh"

source ~/.bashrc

nvm install 20          # install Node 20 LTS
nvm install 22          # install Node 22 LTS
nvm use 20              # switch to Node 20 in current shell
nvm alias default 20    # set default for new shells
nvm ls                  # list installed versions

# .nvmrc file in project root:
echo "20.18.0" > .nvmrc
# now `nvm use` (no arg) reads .nvmrc and switches automatically

# ─── fnm (Rust, fast, modern) ─────────────────────────────────
curl -fsSL https://fnm.vercel.app/install | bash
# adds to ~/.bashrc:
#   export PATH=/home/user/.local/share/fnm:$PATH
#   eval "$(fnm env --use-on-cd)"

fnm install 20
fnm install 22
fnm use 20
fnm default 20
fnm list

# .node-version file (works with fnm, asdf, nodenv):
echo "20.18.0" > .node-version
# with `--use-on-cd` configured, `cd` into the project auto-switches
```

The `eval "$(fnm env --use-on-cd)"` line is what makes `fnm` switch versions automatically when you `cd` into a directory containing a `.node-version` file. It installs a shell hook on `cd` that reads the file and calls `fnm use`. The same hook exists for `nvm` but it is slower (each `cd` re-sources `nvm.sh`, which is a 600-line bash script). For a developer who switches between 10 microservices daily, `fnm` saves seconds per `cd` — over a day, minutes.

On Windows, the equivalents are `nvm-windows` (a separate project from `nvm` — written in Go, not bash) and `volta` (Rust-based, similar to `fnm`). Scoop also has `nodejs` and `nodejs-lts` packages:

```powershell
# Windows with nvm-windows
choco install nvm.portable    # or: scoop install nvm
nvm install 20.18.0
nvm use 20.18.0

# Windows with Volta (recommended)
scoop install volta
volta install node@20
 volta pin node@20.18.0       # in project root, writes to package.json
```

The production failure mode here is `nvm` in CI. GitHub Actions runners come with Node pre-installed via the `setup-node` action, which handles version selection itself — but if your CI script calls `nvm use` directly, it must `source` the nvm init script first (`source ~/.nvm/nvm.sh`), because `nvm` is a shell function (not a binary) and shell functions are not inherited by subshells. The symptom is `nvm: command not found` in CI but works locally — your local shell sourced `nvm.sh` at login, the CI shell did not. The fix is to use `actions/setup-node@v4` with `node-version: 20` and let the action handle the path, or to `source ~/.nvm/nvm.sh && nvm use` explicitly in each step.

### The Node.js binary architecture: V8 Engine, libuv, OpenSSL, and c-ares dependencies

The `node` binary is not a single program — it is a compilation of five major components, each with its own upstream project. Knowing what each contributes is what lets you read a Node crash dump and know whether the bug is in V8 (a stack overflow in a recursive function), in libuv (a `UV_ECONNRESET` from a dropped TCP connection), in OpenSSL (a handshake failure), in c-ares (a DNS timeout), or in the JavaScript standard library (a `TypeError` from a misuse of `Array.push`).

```text
  ┌─────────────────────────────────────────────────────────┐
  │                    node binary                          │
  │                                                         │
  │  ┌─────────────┐  ┌─────────────┐  ┌─────────────────┐ │
  │  │  V8 Engine  │  │   libuv     │  │     OpenSSL     │ │
  │  │             │  │             │  │                  │ │
  │  │ JavaScript  │  │ Event loop  │  │  TLS handshakes  │ │
  │  │ → bytecode  │  │ (epoll/     │  │  Cert validation │ │
  │  │ → native    │  │  kqueue/    │  │  Crypto primitives│ │
  │  │ code via    │  │  IOCP)      │  │                  │ │
  │  │ TurboFan    │  │             │  │                  │ │
  │  │ JIT         │  │ Thread pool │  │                  │ │
  │  │             │  │ (4 threads  │  │                  │ │
  │  │ Heap + GC   │  │  default)   │  │                  │ │
  │  └──────┬──────┘  └──────┬──────┘  └────────┬────────┘ │
  │         │                │                  │          │
  │  ┌──────┴──────────────────┴──────────────────┴───────┐ │
  │  │           Node.js Standard Library (JS)             │ │
  │  │   fs, http, https, net, dns, stream, crypto, ...   │ │
  │  └─────────────────────────────────────────────────────┘ │
  │                                                         │
  │  ┌─────────────────┐                                     │
  │  │     c-ares      │  Asynchronous DNS resolution       │
  │  │                 │  (used by dns.lookup)              │
  │  └─────────────────┘                                     │
  │                                                         │
  │  ┌─────────────────┐                                     │
  │  │     llhttp      │  HTTP request/response parser      │
  │  │                 │  (C, used by http.IncomingMessage) │ │
  │  └─────────────────┘                                     │
  └─────────────────────────────────────────────────────────┘
```

**V8** is Google's JavaScript engine, originally built for Chrome. It parses JavaScript, compiles it to bytecode (Ignition), interprets the bytecode, profiles hot functions, and recompiles them to native machine code via TurboFan. The same V8 runs in Chrome and in Node — they share the engine, only the host APIs differ. V8 owns the JavaScript heap and the garbage collector (Orinoco, a generational mark-and-sweep with concurrent compaction). When a Node process reports `FATAL ERROR: Ineffective mark-compacts near heap limit Allocation failed - JavaScript heap out of memory`, that is V8 refusing to grow the heap past its default 1.4 GB (32-bit) or 4 GB (64-bit) limit. The limit is raised with `--max-old-space-size=4096` (4 GB) on the `node` command line.

**libuv** is the asynchronous I/O library originally written for Node and now used by many other projects. It provides the event loop (a single-threaded loop that polls for I/O readiness via `epoll` on Linux, `kqueue` on macOS, or IOCP on Windows), a thread pool (default 4 threads, used for filesystem operations and DNS lookups that have no async API), and abstractions over TCP, UDP, pipes, and TTY. Every `fs.readFile` call posts work to the libuv thread pool; every `net.Socket` reads from a libuv TCP handle that was made readable by an `epoll` event. The default 4-thread pool is why four concurrent `fs.readFile` calls finish in the same time as one, but a fifth call queues — set `UV_THREADPOOL_SIZE=16` in the environment to grow it.

**OpenSSL** provides TLS, certificate handling, and the cryptographic primitives behind `crypto.createHash`, `crypto.randomBytes`, `crypto.publicEncrypt`, and the `https` module. Node ships a specific OpenSSL version (e.g. Node 20 ships OpenSSL 3.0.x); when CVEs land in OpenSSL, Node releases a patch version within days. The cost is that Node's `crypto` API exposes OpenSSL concepts directly — cipher names like `aes-256-gcm`, key derivation functions like `scrypt`, and the `createSign`/`createVerify` API that wraps OpenSSL's EVP_DigestSign operations. Knowing that the crypto module is OpenSSL is what explains the error `error:0308010C:digital envelope routines::unsupported` you get when running an old webpack build on Node 17+ — webpack 4 used an OpenSSL algorithm that OpenSSL 3 disabled by default, and the fix is `NODE_OPTIONS=--openssl-legacy-provider`.

**c-ares** is the asynchronous DNS resolver. Node's `dns.lookup()` (the function the OS-level `http.get` uses internally) goes through c-ares and the libuv thread pool; `dns.resolve4()` and `dns.resolve6()` use c-ares directly with the system's configured DNS servers. The split matters because `dns.lookup` honours `/etc/hosts` and `/etc/nsswitch.conf` (it calls `getaddrinfo`), while `dns.resolve*` talks directly to the DNS server and ignores `/etc/hosts`. A common production bug is "the service works in the browser but not in Node" because the browser uses `/etc/hosts` and the Node code used `dns.resolve4` which skipped it.

The failure mode the architecture exposes is "the event loop blocked" incident. Node runs JavaScript on a single thread; if any synchronous operation takes longer than ~100 ms, every other request stalls. A `JSON.parse` of a 50 MB payload, a `crypto.pbkdf2` without `salt` length limits, or a tight `for` loop over 10 million elements all block the event loop. The metric that reveals it is the event loop lag (the difference between when a `setTimeout(fn, 0)` was scheduled and when it actually ran) — exposed via `perf_hooks.monitorEventLoopDelay()` or the `node --inspect` Performance panel. The fix is to move CPU-bound work to a worker thread (`worker_threads`), to a child process (`child_process.fork`), or to a native addon that uses the libuv thread pool.

### Package manager setups: Installing and configuring `pnpm` and `npm`

Node ships with `npm` (the Node Package Manager) bundled in the same binary — installing Node also installs `npm`. `npm` is the default package manager and the one used by every Node tutorial, but it has two competitors: `pnpm` (Fast, Disk-Efficient Package Manager) and `yarn` (Facebook's alternative). The three differ in their `node_modules` layout, their lockfile format, and their performance characteristics.

```bash
# npm comes with Node; verify
node -v        # v20.18.0
npm -v         # 10.8.2

# install pnpm globally via npm
npm install -g pnpm
pnpm -v        # 9.12.0

# install yarn (modern Berry version)
npm install -g yarn
yarn -v        # 1.22.22 (Classic) or 4.x (Berry via corepack)
```

The critical difference is the `node_modules` layout:

```text
  npm / yarn classic (flat node_modules):
  node_modules/
  ├── express/                  ← hoisted to top level
  │   └── node_modules/
  │       └── qs/               ← nested if version conflicts
  ├── qs/                       ← also hoisted (version 6.x for express)
  └── body-parser/
      └── node_modules/
          └── qs/               ← different version (4.x) if conflict

  pnpm (symlinked, content-addressed):
  node_modules/
  ├── .pnpm/                    ← single source of truth
  │   ├── express@4.19.2/
  │   │   └── node_modules/
  │   │       ├── express/      ← real files
  │   │       └── qs/ → ../../qs@6.13.0/node_modules/qs   ← symlink
  │   └── qs@6.13.0/
  │       └── node_modules/qs/  ← real files
  ├── express → .pnpm/express@4.19.2/node_modules/express  ← symlink
  └── qs → .pnpm/qs@6.13.0/node_modules/qs                  ← symlink
```

npm's flat layout hoists every package to the top of `node_modules` if no version conflict exists, and nests it under the consumer if a conflict does exist. This means your code can `require("qs")` and it will resolve even if you never declared `qs` as a direct dependency — it was hoisted from a transitive dep. This is the "phantom dependency" bug: your code works, you delete `express` from `package.json`, your code still works (because `qs` is still hoisted), you ship, and the next `npm ci` in CI fails because `qs` is no longer installed. pnpm's symlink layout fixes this — only packages you declared as direct dependencies are symlinked to the top of `node_modules`, so phantom dependencies fail with `Cannot find module` immediately.

pnpm also deduplicates by content hash: the same version of a package is stored once in a global store (`~/.local/share/pnpm/store/`) and hard-linked into each project. A monorepo with 50 services all using `express@4.19.2` has 50 symlinks to one physical copy on disk. This saves disk space and install time — `pnpm install` on a warm cache is sub-second.

| Aspect | npm | pnpm | yarn classic |
|---|---|---|---|
| Default since | Node ships it | Opt-in | Opt-in |
| node_modules layout | Flat (hoisted) | Symlinked (strict) | Flat (hoisted) |
| Phantom dependencies | Allowed | Blocked | Allowed |
| Disk usage per project | Full copy | Hard links to global store | Full copy |
| Install speed (warm) | ~3 s | ~0.5 s | ~2 s |
| Lockfile | `package-lock.json` | `pnpm-lock.yaml` | `yarn.lock` |
| Workspace (monorepo) support | npm v7+ | Native, fast | Native |
| Strict peer deps | Optional (npm 7+) | Enforced | Optional |

The global package directory (`npm prefix`) is where globally-installed packages live (`npm install -g prettier`). The default is `/usr/local/lib/node_modules` on macOS/Linux (requires `sudo`) and `%APPDATA%\npm` on Windows. Configure a user-writable prefix to avoid `sudo`:

```bash
# set the npm prefix to a user-writable directory
mkdir -p ~/.npm-global
npm config set prefix '~/.npm-global'
echo 'export PATH=~/.npm-global/bin:$PATH' >> ~/.bashrc
source ~/.bashrc

# now `npm install -g` works without sudo
npm install -g typescript prettier
```

The failure mode this prevents is "I ran `sudo npm install -g something` and now half my filesystem is owned by root". Once `sudo npm install -g` runs, the global `node_modules` directory and everything in it is owned by root; subsequent `npm install -g` without sudo fails with `EACCES`, and the only fix is `sudo chown -R $(whoami) /usr/local/lib/node_modules` to undo the damage. Setting a user-writable prefix avoids the entire problem.

`corepack` is the modern alternative to globally installing `pnpm` or `yarn` via `npm install -g`. It has shipped with Node since version 16.10 (no separate install needed) and acts as a shim: when you run `pnpm install`, corepack checks the `packageManager` field in `package.json` and runs the exact version of `pnpm` declared there. This eliminates the "works on my machine" bug where one developer has `pnpm@9` and another has `pnpm@8`, producing different `pnpm-lock.yaml` files from the same source. Enable it once with `corepack enable` (creates the `pnpm` and `yarn` shims in your npm prefix), then pin a version per project:

```bash
corepack enable                                # one-time, creates pnpm/yarn shims in npm prefix
corepack prepare pnpm@9.12.0 --activate         # download and pin a version globally
cd myapp && corepack use pnpm@9.12.0            # writes "packageManager": "pnpm@9.12.0" to package.json
# now `pnpm install` in this project always uses 9.12.0, regardless of what's globally installed
```

The `packageManager` field is read by corepack on every invocation. A monorepo with `"packageManager": "pnpm@9.12.0"` in its root `package.json` will use pnpm 9.12.0 on every developer machine and every CI runner, with no global install step. This is the Node equivalent of the Maven wrapper (see [[01.02.03. Maven and Gradle Build Architectures]]) — a project-local declaration of the build tool version. The failure mode corepack prevents: a new developer joins, runs `npm install -g pnpm`, gets pnpm 10 (which has a different lockfile format), and produces a `pnpm-lock.yaml` diff that breaks every other developer's install.

The `.npmrc` file is where project-level and user-level npm configuration lives. It is read from four locations in order (each overrides the previous): the project-level `.npmrc` in the project root, the user-level `~/.npmrc`, the global `$PREFIX/etc/npmrc`, and the built-in defaults. The settings that matter most for backend engineering:

```ini
# .npmrc — project root
registry=https://registry.npmjs.org/           # or your private Artifactory/Nexus URL
engine-strict=true                              # fail install if Node version doesn't match package.json engines
save-exact=true                                 # write "1.2.3" not "^1.2.3" to package.json (reproducible)
audit-level=high                                # npm audit exits non-zero only on high/critical
fund=false                                      # silence the "X packages are looking for funding" message
# private registry with auth token (scoped to @mycompany packages):
@mycompany:registry=https://npm.artifactory.mycompany.com/
//npm.artifactory.mycompany.com/:_authToken=${NPM_TOKEN}
```

The `engine-strict=true` setting is the single most impactful one for backend teams. Without it, `npm install` silently succeeds on Node 18 even if `package.json` declares `"engines": {"node": ">=20" }` — the install completes, the runtime then fails with `SyntaxError: Unexpected token '??='` (the logical-assignment operator added in Node 15). With `engine-strict=true`, the install itself fails, surfacing the version mismatch before any code runs. The `${NPM_TOKEN}` environment variable is how CI injects the registry auth token without writing it to disk — never check a real token into `.npmrc`; always reference it via `${VAR}` and set the variable in CI secrets. The `npm config ls -l` command prints every setting and where it came from (project, user, global, or default), which is the primary tool for diagnosing "why is npm using a different registry than I configured".

## Key Takeaways

1. **Use a version manager — `fnm` for speed, `nvm` for ubiquity — and pin per-project with `.nvmrc` or `.node-version`.** Always target an LTS (even-numbered major) in production; odd-numbered majors are unsupported within months.
2. **Node is V8 (JS + JIT + GC) + libuv (event loop + thread pool) + OpenSSL (TLS + crypto) + c-ares (DNS) + llhttp (HTTP parsing).** Each component produces its own class of errors — read the prefix to know which layer failed.
3. **pnpm's symlinked layout prevents phantom dependencies.** Use `npm ci` (not `npm install`) in CI; the strict version is `pnpm install --frozen-lockfile`. Set a user-writable npm prefix to avoid `sudo npm install -g` and the subsequent root-owned filesystem.
