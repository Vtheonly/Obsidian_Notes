# 01.03.03. CommonJS vs. ECMAScript Modules

## What This Is

Node.js supports two module systems: CommonJS (CJS, the original, designed in 2009 by Kevin Dangoor) and ECMAScript Modules (ESM, the standard, finalized in 2015 by TC39). The two systems use different syntax (`require`/`module.exports` vs `import`/`export`), different resolution algorithms (synchronous file lookup vs. static analysis with `exports` field), and different runtime semantics (live bindings vs. copies, hoisting vs. temporal dead zone). A Node project picks one by setting `type: "module"` (ESM) or omitting it (CJS, the default) in `package.json`. The two systems can interoperate, but the interop is full of footguns — `__dirname` does not exist in ESM, `require` cannot load ESM, default imports of CJS modules behave differently under `esModuleInterop`, and a package that ships both formats can accidentally load twice (the "dual-package hazard"). This note explains the resolution algorithm, the syntactic differences, the interop rules, and how `tsconfig.json`'s `module` setting controls what `tsc` emits. Every backend TypeScript project will eventually hit one of these footguns; this note is how you recognize them.

The note is the conceptual backbone of sub-section 01.03 — [[01.03.02. TypeScript Compiler and Configuration Mechanics]] controls the `module` setting described here, and [[01.03.04. Bootstrapping a Bare-Metal Express TypeScript Application]] produces an Express app that must pick a module system. The failure modes it governs are the ones that surface as `SyntaxError: Cannot use import statement outside a module`, `ReferenceError: __dirname is not defined in ES module scope`, `ERR_REQUIRE_ESM`, and the silent "the same module loaded twice with different state" bug.

## The Details

### Synchronous file-based loading (`require`, `module.exports`) vs. Asynchronous static loading (`import`, `export`)

CommonJS modules load synchronously. When Node executes `const fs = require("fs")`, it does the following, in order, on the calling thread: (1) resolve the module specifier `"fs"` to a file path by walking the `node_modules` directories; (2) check the `require.cache` map — if the path is already there, return the cached `module.exports`; (3) if not cached, read the file, wrap it in a function `(function(exports, require, module, __filename, __dirname) { ... })`, compile it with V8, and invoke the function; (4) the module's code runs, populating `module.exports`; (5) cache `module.exports` and return it. The entire operation is synchronous and blocks the event loop — `require` is not async.

```javascript
// CommonJS: lib.js
const fs = require("fs");             // synchronous load
let count = 0;
function increment() { count++; }
module.exports = { increment, getCount: () => count };

// app.js
const lib = require("./lib");          // synchronous, cached
lib.increment();
console.log(lib.getCount());           // 1

const lib2 = require("./lib");         // returns the SAME object from cache
console.log(lib === lib2);             // true
```

ESM modules load asynchronously and statically. When Node encounters `import fs from "fs"`, it does not execute any code immediately — it parses the file, finds all `import` declarations, builds a module graph, then loads the graph in dependency order, then evaluates the modules. The `import` statement is "static" because the module specifier must be a string literal at parse time — you cannot `import` from a variable, you cannot `import` inside an `if` block, and you cannot conditionally `import` (use `await import(...)` for that). The staticness is what enables tree-shaking (a bundler can determine at parse time which exports are used and which can be dropped).

```javascript
// ESM: lib.mjs (or .js with type:module in package.json)
import fs from "fs";                   // static, top-level only
let count = 0;
export function increment() { count++; }
export const getCount = () => count;

// app.mjs
import { increment, getCount } from "./lib.mjs";   // live binding
increment();
console.log(getCount());               // 1
```

The "live binding" difference is the deepest semantic gap. In CommonJS, `module.exports` is a snapshot — when you `require` a module, you get the value of its `exports` at that moment. If the module later mutates a variable, you do not see the change unless you re-`require` it (and the cache returns the same object). In ESM, `import { increment }` creates a *live binding* to the `increment` export — if the exporting module reassigns `increment` to a different function, the importing module sees the new function. Live bindings exist because they enable cross-module cyclic imports to work: A imports B, B imports A, and both see the latest state of the other's exports.

| Aspect | CommonJS | ESM |
|---|---|---|
| Syntax | `require`, `module.exports` | `import`, `export` |
| Loading | Synchronous | Asynchronous |
| Specifier | Any expression (`require("./" + name)`) | String literal only |
| Top-level | `await` not allowed (use async IIFE) | `await` allowed (top-level await) |
| Exports | Object snapshot | Live bindings |
| Cyclic imports | Returns partial `module.exports` (may be `undefined`) | Live binding (resolves when assigned) |
| `this` at top level | `module.exports` | `undefined` |
| `__dirname`, `__filename` | Available | Not available (use `import.meta.url`) |
| `require.cache` | Yes, mutable | No module-level cache (URL-keyed) |
| Hoisting | No (runtime evaluation) | Yes (imports hoisted to top) |
| Strict mode | Optional (`"use strict"`) | Always strict |

The failure mode this produces is the cyclic-import bug. In CommonJS, if A requires B which requires A, B gets A's `module.exports` at the moment B's `require("./a")` runs — which is *before* A has finished executing, so `module.exports` is still the default `{}`. B's code sees an empty object and either crashes with `X is not a function` or silently uses `undefined`. In ESM, the same cycle works because A and B are connected by live bindings — when A finally assigns its export, B sees it. This is why many packages that previously failed under CommonJS cycles were rewritten to ESM during 2020–2022.

### The `"type": "module"` configuration and handling file extension resolution in Node.js

The `type` field in `package.json` is how Node decides whether `.js` files in that package are CommonJS or ESM. The rule is per-directory: each `package.json` declares a `type`, and that determines the module system for every `.js` file in that directory and its sub-directories (until a deeper `package.json` overrides it). The two values are `"commonjs"` (the default if `type` is omitted) and `"module"`.

```text
  myapp/
  ├── package.json          { "type": "module" }     ← .js files here are ESM
  ├── src/
  │   ├── server.js         ← ESM (inherits from root package.json)
  │   └── routes/
  │       ├── users.js      ← ESM
  │       └── package.json  { "type": "commonjs" }   ← overrides!
  │           (this makes routes/*.js CommonJS)
  └── scripts/
      └── migrate.cjs       ← .cjs is always CommonJS regardless of type
      └── data.mjs          ← .mjs is always ESM regardless of type
```

The file extensions are the escape hatches. `.cjs` is always CommonJS even if `package.json` says `type: module`. `.mjs` is always ESM even if `package.json` says `type: commonjs` (or has no `type` field). `.js` follows the `type` field. This is how a project can have a mostly-ESM codebase with one CommonJS migration script: name the script `migrate.cjs` and Node will treat it as CommonJS regardless of the package's `type`.

The module resolution algorithm differs between the two systems. For CommonJS, Node uses the "Node resolution algorithm": given a specifier like `"./lib"` or `"express"`, it tries, in order:

1. If the specifier starts with `/` or `./` or `../`, treat as a path. Try `./lib` as a file (with extensions `.js`, `.json`, `.node` in that order), then as a directory (look for `./lib/package.json`'s `main` field, fall back to `./lib/index.js`).
2. If the specifier is bare (`"express"`), walk up the directory tree looking for `node_modules/express/`, then `../node_modules/express/`, then `../../node_modules/express/`, until found.
3. Once the package directory is found, apply step 1's file/directory logic to its entry point.

```text
  require("./lib")            from /app/src/server.js

  Try as file:
    /app/src/lib              ← no
    /app/src/lib.js           ← yes? use it
    /app/src/lib.json         ← yes? use it
    /app/src/lib.node         ← yes? use it
  Try as directory:
    /app/src/lib/package.json → "main": "./index.js"
                                → /app/src/lib/index.js
    /app/src/lib/index.js     ← fallback if no package.json or no main

  require("express")          from /app/src/server.js

  Walk up node_modules:
    /app/src/node_modules/express     ← no
    /app/node_modules/express         ← YES
      → /app/node_modules/express/package.json
      → "main": "index.js"
      → /app/node_modules/express/index.js
```

For ESM, Node uses the same algorithm but with stricter rules and an additional step that consults the `exports` field in `package.json`. The `exports` field is the modern replacement for `main` — it allows a package to declare multiple entry points, restrict which subpaths are public, and provide different files for `import` vs `require`:

```json
{
  "name": "mylib",
  "main": "./dist/cjs/index.js",
  "exports": {
    ".": {
      "import": "./dist/esm/index.js",
      "require": "./dist/cjs/index.js",
      "types": "./dist/types/index.d.ts"
    },
    "./utils": {
      "import": "./dist/esm/utils.js",
      "require": "./dist/cjs/utils.js"
    },
    "./package.json": "./package.json"
  }
}
```

A consumer doing `import "mylib"` gets `./dist/esm/index.js`; a consumer doing `require("mylib")` gets `./dist/cjs/index.js`. A consumer doing `import "mylib/nonexistent"` gets `ERR_PACKAGE_PATH_NOT_EXPORTED` — subpaths not declared in `exports` are forbidden. This is the security/correctness improvement over `main`: a package author can guarantee that consumers cannot reach internal files by `import "mylib/internal/secret"`.

ESM also requires file extensions in relative imports. `import "./lib"` fails with `ERR_MODULE_NOT_FOUND` — you must write `import "./lib.js"` (or `.mjs`, `.ts` if using `tsx`). This is because the ESM spec does not permit the extension-trying behaviour CommonJS does; the resolver must find the file at the exact path. The TypeScript convention is to write `import "./lib.js"` even in `.ts` source — `tsc` does not rewrite the specifier, and Node sees the `.js` path which exists post-compilation.

```javascript
// ESM (src/server.ts → dist/server.js)
import { router } from "./routes/users.js";   // .js extension required
                                              // (even though source is .ts)
```

The failure mode here is the "package is CommonJS but I tried to import it from ESM" error. A package without `"type": "module"` in its `package.json` and without an `exports` field is treated as CommonJS. If you `import someCjsPackage from "some-cjs-package"` from an ESM file, Node loads it as CommonJS and synthesizes a default export from `module.exports`. This works under `esModuleInterop`. But if the package's `exports` field is set and only declares `"require"` (not `"import"`), Node refuses to load it from ESM with `ERR_REQUIRE_ESM`. The fix is either to use `await import("some-cjs-package")` (which can load CJS from ESM) or to find a newer version of the package that ships ESM.

### Interoperability challenges: Default exports, named exports, and dynamic imports (`import()`)

The two module systems can interoperate, but the interop rules are subtle. The general direction is: ESM can import CJS, but CJS cannot `require` ESM. The reason is that `require` is synchronous and ESM loading is asynchronous — `require` would have to block the event loop until the ESM graph finishes loading, which Node refuses to do. CJS can load ESM only via the dynamic `import()` expression, which returns a Promise.

```javascript
// ESM importing CJS — works under esModuleInterop
import express from "express";          // express is CJS; default import = module.exports
import * as expressNs from "express";   // namespace import = { default: module.exports, ... }
console.log(express === expressNs.default);   // true

// ESM importing CJS named exports — only works if the CJS package
// declares them via static analysis (the cjs-module-lexer tool)
import { readFile } from "fs";          // works: fs is special-cased
import { useRouter } from "some-cjs-lib";  // may fail: only sees default unless cjs-module-lexer finds named exports

// CJS importing ESM — only via dynamic import
async function loadEsm() {
  const esm = await import("./esm-lib.js");
  return esm.namedExport;
}
// const esm = require("./esm-lib.js");   ← SyntaxError: ERR_REQUIRE_ESM
```

The `__dirname`/`__filename` gap is the most common ESM migration pain. In CommonJS, every module is given `__dirname` (the directory containing the current file) and `__filename` (the absolute path of the current file) as injected variables. In ESM, these do not exist — the ESM spec does not define them. The replacement is `import.meta.url`, which is the file's URL (`file:///app/src/server.js`). To get the directory path, you must manually convert:

```javascript
// CommonJS
const path = require("path");
const fs = require("fs");
const data = fs.readFileSync(path.join(__dirname, "data.json"));

// ESM
import { readFileSync } from "fs";
import { fileURLToPath } from "url";
import { dirname, join } from "path";

const __filename = fileURLToPath(import.meta.url);
const __dirname = dirname(__filename);
const data = readFileSync(join(__dirname, "data.json"));

// or the one-liner:
import { readFileSync } from "fs";
const data = readFileSync(new URL("./data.json", import.meta.url));
```

The temporal dead zone (TDZ) is the other semantic difference. In ESM, `import` statements are hoisted to the top of the module and executed before any other code. You cannot use a variable before its `import` has executed — `console.log(x); import { x } from "./lib"` throws `ReferenceError: Cannot access 'x' before initialization`. In CommonJS, `require` is a function call executed in source order — `console.log(x); const { x } = require("./lib")` runs `console.log(x)` first (with `x` undefined) and then assigns. The TDZ is what catches accidental forward references that CommonJS silently allowed.

```javascript
// ESM — TDZ
import { config } from "./config.js";
console.log(config.port);        // works (config is initialized by the time this runs)

// forward reference — TDZ error
console.log(value);              // ReferenceError: Cannot access 'value' before initialization
import { value } from "./value.js";

// CommonJS — no TDZ
console.log(value);              // undefined (require not yet called)
const { value } = require("./value.js");
```

The dual-package hazard is the nastiest interop failure. A package that ships both a CJS version (`require` → `./dist/cjs/index.js`) and an ESM version (`import` → `./dist/esm/index.js`) of the same code can be loaded twice in the same process — once via `require` by one consumer, once via `import` by another. The two copies have separate module state (separate `static` fields, separate singletons, separate caches), so a singleton that should be process-global becomes two-coordinated-but-distinct instances. This breaks `instanceof` checks (an object created by the CJS copy is not an instance of a class defined in the ESM copy), breaks global registries (a route registered via CJS is invisible to the ESM copy), and breaks lock ordering (two separate lock instances where there should be one).

```text
  myapp/
  ├── package.json     { "type": "module", "exports": {
  │                       "import": "./esm/index.js",
  │                       "require": "./cjs/index.js" } }
  ├── esm/index.js     export const state = new Map();
  └── cjs/index.js     module.exports = { state: new Map() };

  consumer-a (CJS):    const { state } = require("mylib");   ← cjs/index.js's Map
  consumer-b (ESM):    import { state } from "mylib";         ← esm/index.js's Map

  state === state?     No — two different Map instances in the same process.
```

The fix is to either ship only one format (pick ESM, document that CJS consumers must use dynamic `import()`), or to have the ESM version `require` the CJS version under the hood (`export const state = require("../cjs/index.js").state;` — `require` is available inside ESM via `createRequire(import.meta.url)`). The latter is what most packages do today; it preserves a single source of module state.

The TypeScript angle: `tsconfig.json`'s `module` setting controls what `tsc` emits. `module: "CommonJS"` emits `require`/`module.exports`. `module: "NodeNext"` emits `import`/`export` if `package.json` has `type: "module"`, and `require`/`module.exports` if it has `type: "commonjs"`. The `module` setting must match `package.json`'s `type` — if you set `module: "NodeNext"` in `tsconfig.json` but leave `package.json` without a `type` field, `tsc` will compile to CommonJS and you will get the CJS behaviour. The `moduleResolution` setting must also match: `module: NodeNext` requires `moduleResolution: NodeNext`. The full modern combination is:

```jsonc
// package.json
{ "type": "module" }

// tsconfig.json
{
  "compilerOptions": {
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "esModuleInterop": true,
    "verbatimModuleSyntax": true
  }
}
```

The `verbatimModuleSyntax` flag enforces that `import type` is used for type-only imports — `tsc` will not elide a regular `import { Foo }` even if `Foo` is only used as a type, which means the emitted JavaScript has a real `import` that would fail at runtime if the imported module does not actually export `Foo`. This catches a class of bugs where `tsc` was silently stripping an import that the runtime needed.

## Key Takeaways

1. **CommonJS loads synchronously with `require`/`module.exports`; ESM loads asynchronously with `import`/`export`.** ESM uses live bindings and TDZ; CommonJS uses snapshots and runtime evaluation. `package.json`'s `type` field picks the system for `.js` files; `.mjs` and `.cjs` are explicit overrides.
2. **ESM requires file extensions in relative imports and uses the `exports` field for package entry points.** `import "./lib.js"` not `import "./lib"`. Subpaths not declared in `exports` are forbidden. `__dirname`/`__filename` do not exist in ESM — use `import.meta.url`.
3. **The dual-package hazard is when a package ships both CJS and ESM and is loaded twice.** Pick one format and stick to it, or have ESM delegate to CJS via `createRequire`. Set `module: NodeNext` and `moduleResolution: NodeNext` in `tsconfig.json` to match `package.json`'s `type`.
