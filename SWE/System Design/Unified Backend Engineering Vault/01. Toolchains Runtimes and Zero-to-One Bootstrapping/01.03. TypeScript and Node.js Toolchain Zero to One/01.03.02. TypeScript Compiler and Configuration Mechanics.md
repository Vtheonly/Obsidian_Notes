# 01.03.02. TypeScript Compiler and Configuration Mechanics

## What This Is

TypeScript is a superset of JavaScript that adds static types, then erases those types at compile time to produce plain JavaScript. The compiler, `tsc`, is itself written in TypeScript and shipped as an npm package (`typescript`). To use TypeScript for a backend service you must initialize a `package.json`, install TypeScript as a dev dependency, generate a `tsconfig.json` that tells `tsc` how to compile your code, and pick a development runner (`tsc --watch`, `tsx`, or `ts-node`) for the local dev loop. This note walks each step and explains every important `tsconfig.json` flag — `target`, `module`, `moduleResolution`, `strict`, `esModuleInterop`, `outDir`, `sourceMap` — because the wrong combination produces bugs that only manifest at runtime ("`__dirname is not defined in ES module scope`", "cannot use import statement outside a module", "`require` of ES module not supported").

The note sits between [[01.03.01. Installing Node.js and Version Management]] (which installs `node` and `npm`) and [[01.03.03. CommonJS vs. ECMAScript Modules]] (which explains the module systems `tsconfig.json`'s `module` setting selects between). The failure modes it governs are the ones where the code type-checks fine but fails at runtime because `tsc` emitted the wrong module format, targeted a too-old JavaScript version, or did not emit source maps and so the production stack trace points to the wrong line.

## The Details

### Initializing a Node.js project: `package.json` manifest structure, scripts, and module definitions

Every Node.js project begins with a `package.json` file at the project root. It is the manifest: it declares the project's name and version, its entry point, its dependencies, its npm scripts, and — critically for [[01.03.03. CommonJS vs. ECMAScript Modules]] — its module system. Generate it with `npm init` (interactive) or `npm init -y` (defaults):

```bash
mkdir myapp && cd myapp
npm init -y
```

```json
{
  "name": "myapp",
  "version": "1.0.0",
  "description": "",
  "main": "index.js",
  "scripts": {
    "test": "echo \"Error: no test specified\" && exit 1"
  },
  "keywords": [],
  "author": "",
  "license": "ISC"
}
```

The fields that matter for backend engineering:

- **`name`** and **`version`** — the package identity. If you publish to npm, these must be unique. For internal apps, they appear in `process.env.npm_package_name` and `npm_package_version` at runtime, which is how many apps inject their version into log output.
- **`type`** — the module system. `"commonjs"` (the default if omitted) means `.js` files are CommonJS (`require`/`module.exports`). `"module"` means `.js` files are ECMAScript modules (`import`/`export`). This single field is what determines whether `node index.js` works or throws `Cannot use import statement outside a module` — see [[01.03.03. CommonJS vs. ECMAScript Modules]].
- **`main`** — the entry point when someone does `require("myapp")` or `import "myapp"`. Defaults to `index.js`. For a TypeScript project that compiles to `dist/`, this should point to `dist/index.js`.
- **`exports`** — the modern replacement for `main`. Allows defining different entry points for different consumers (`import` vs `require` vs `types`) and restricting which subpaths are public. If `exports` is set, `main` is ignored for new consumers.
- **`scripts`** — npm scripts, runnable with `npm run <name>`. The `start`, `test`, `install`, and `publish` scripts have special aliases (`npm start` works without `run`). Scripts run with `node_modules/.bin` on the `PATH`, which is why `npm run build` can invoke `tsc` without a global install.
- **`dependencies`** vs **`devDependencies`** — runtime deps go in `dependencies`; build-time and test-time deps (TypeScript, ESLint, Jest, type definitions) go in `devDependencies`. When you `npm install --production`, only `dependencies` are installed — this is what production Docker builds should do to keep the image small.
- **`engines`** — declares the required Node version. `"engines": { "node": ">=20" }` causes `npm install` to warn (or, with `.npmrc` `engine-strict=true`, to fail) if the consumer is on an older Node.
- **`private: true`** — prevents accidental `npm publish`. Set this on every app that is not a library.

A typical backend `package.json` after setup:

```json
{
  "name": "myapp",
  "version": "1.0.0",
  "private": true,
  "type": "module",
  "engines": { "node": ">=20.0.0" },
  "scripts": {
    "build": "tsc -p tsconfig.json",
    "dev": "tsx watch src/server.ts",
    "start": "node dist/server.js",
    "test": "node --test --import tsx src/**/*.test.ts",
    "lint": "eslint src/"
  },
  "dependencies": {
    "express": "^4.19.2"
  },
  "devDependencies": {
    "@types/express": "^4.17.21",
    "@types/node": "^20.14.0",
    "tsx": "^4.7.0",
    "typescript": "^5.5.0"
  }
}
```

The `scripts` block is where the build pipeline lives. `npm run dev` runs `tsx watch`, which restarts on every file change. `npm run build` compiles to `dist/`. `npm start` runs the compiled output. `npm test` uses Node's built-in test runner (`node --test`) with `tsx` as a loader for TypeScript. The advantage of putting all of this in `scripts` is that a developer who clones the repo only needs to know `npm install && npm run dev` — the script abstracts away which runner, which flags, which environment variables.

The failure mode here is "the script works on my machine but not in CI". The cause is almost always that the script depends on a tool that is not in `devDependencies` — `nodemon` installed globally, `jq` installed via Homebrew, a shell function defined in `~/.bashrc`. The fix is to declare every tool the script invokes as a `devDependency` and to invoke it via `npx` (which finds it in `node_modules/.bin`). For shell tools like `jq`, either replace them with a Node equivalent (`node -e 'console.log(JSON.parse(require("fs").readFileSync(0)).version)'`) or document the install in the README and verify it in CI with a `which jq` step before the build.

### TypeScript installation and initialization: Generating and analyzing `tsconfig.json`

Install TypeScript as a dev dependency (never globally — global TypeScript causes version drift between projects):

```bash
npm install -D typescript
npx tsc --version    # 5.5.4
```

The `npx` prefix finds `tsc` in `node_modules/.bin` and runs it. Generate a starter `tsconfig.json` with:

```bash
npx tsc --init --module commonjs --target es2022 --strict --esModuleInterop \
        --moduleResolution node --outDir dist --rootDir src --sourceMap
```

This produces a `tsconfig.json` with the specified flags pre-set and every other flag commented out as documentation. The minimum useful configuration for a backend TypeScript project:

```jsonc
// tsconfig.json
{
  "compilerOptions": {
    "target": "ES2022",                  // emit JS targeting Node 20's V8
    "module": "NodeNext",                // ESM if package.json type=module, CJS otherwise
    "moduleResolution": "NodeNext",      // matches module setting
    "lib": ["ES2022"],                   // built-in type definitions (no DOM)
    "outDir": "./dist",                  // emit to dist/
    "rootDir": "./src",                  // source root
    "sourceMap": true,                   // emit .js.map for debugging
    "strict": true,                      // enable all strict type checks
    "esModuleInterop": true,             // allow default-import of CJS modules
    "skipLibCheck": true,                // skip type-checking .d.ts files (speed)
    "forceConsistentCasingInFileNames": true,
    "resolveJsonModule": true,           // allow `import data from "./data.json"`
    "declaration": false,                // emit .d.ts (only for libraries)
    "removeComments": true               // strip comments from emitted JS
  },
  "include": ["src/**/*"],               // compile every .ts under src/
  "exclude": ["node_modules", "dist", "**/*.test.ts"]
}
```

The `include`/`exclude` arrays tell `tsc` which files to compile. `src/**/*` matches every file under `src/` recursively. The `exclude` patterns override `include`; `node_modules` is excluded by default but listing it explicitly is conventional.

A separate `tsconfig.json` for tests is common — tests need different settings (no `removeComments`, include the `vitest`/`jest` types, allow `src/**/*.test.ts`):

```jsonc
// tsconfig.test.json
{
  "extends": "./tsconfig.json",
  "compilerOptions": {
    "types": ["node", "vitest/globals"]
  },
  "include": ["src/**/*", "test/**/*"]
}
```

The `extends` keyword inherits all settings from the base config and overrides only what is listed. This is the TypeScript equivalent of inheritance in OOP — keep one base config and specialize per use case (build, test, e2e).

The failure mode here is "tsconfig drift". As a project grows, developers add flags to `tsconfig.json` without understanding them, the type-checking becomes slower, and eventually someone sets `"skipLibCheck": false` to be "more strict" — which forces `tsc` to type-check every `.d.ts` file in `node_modules`, taking 30 seconds instead of 3. The fix is to audit `tsconfig.json` periodically with `npx tsc --showConfig` (which prints the fully-resolved config after extends and inheritance) and to remove flags that are no-ops or that hurt performance without adding safety.

### Strict TypeScript configurations: `target`, `module`, `moduleResolution`, `strict`, `esModuleInterop`, and `outDir`

Each compiler option controls a different aspect of the compilation. Knowing what each does — and what breaks when you get it wrong — is what separates a TypeScript project that compiles cleanly across machines from one that only works with one specific `tsc` version.

| Flag | Values | Effect |
|---|---|---|
| `target` | `ES2015` through `ESNext` | The JavaScript version `tsc` emits. `ES2022` is the right choice for Node 20+ (matches V8's capabilities); `ES5` for old browsers. Determines whether `async`/`await` is emitted as-is or down-leveled to `Promise.then` chains. |
| `module` | `CommonJS`, `NodeNext`, `ES2020`, `ESNext` | The module syntax emitted. `CommonJS` → `require`/`module.exports`. `ESNext` or `NodeNext` → `import`/`export`. See [[01.03.03. CommonJS vs. ECMAScript Modules]]. |
| `moduleResolution` | `node`, `node16`, `nodenext`, `bundler` | How `import "./foo"` resolves to a file. `node` (classic) uses Node's old algorithm. `node16`/`nodenext` uses Node's modern algorithm with `exports` field support. `bundler` matches webpack/Vite behavior. |
| `lib` | `ES2015`–`ESNext`, `DOM`, `DOM.Iterable` | Built-in type definitions. `["ES2022"]` for Node (no DOM). Including `DOM` in a backend project is a common mistake that lets you accidentally use `document` and `window` in code that has no DOM. |
| `strict` | `true`/`false` | Master switch for: `noImplicitAny`, `strictNullChecks`, `strictFunctionTypes`, `strictBindCallApply`, `strictPropertyInitialization`, `alwaysStrict`, `noImplicitThis`, `useUnknownInCatchVariables`. Always set `true` for new projects. |
| `esModuleInterop` | `true`/`false` | Allows `import express from "express"` (default import) for CommonJS modules that use `module.exports = ...`. Without it, you must use `import * as express from "express"`. Set `true`. |
| `skipLibCheck` | `true`/`false` | Skip type-checking `.d.ts` files in `node_modules`. Always `true` for performance; the library author already type-checked their own code. |
| `outDir` | `./dist` | Where to emit compiled `.js`. |
| `rootDir` | `./src` | The root of the source tree. Enforces that all sources are under one directory; emits with the same structure under `outDir`. |
| `sourceMap` | `true`/`false` | Emit `.js.map` files alongside `.js`, so debuggers can map back to TypeScript source. |
| `declaration` | `true`/`false` | Emit `.d.ts` files. Only needed for libraries that will be consumed by other TypeScript projects. |
| `isolatedModules` | `true`/`false` | Required by `tsx`/`esbuild`/`vite`: each file must be compilable in isolation (no cross-file type information at transpile time). Enforces that `export type` is used correctly. |
| `verbatimModuleSyntax` | `true`/`false` | Stricter version of `isolatedModules`: never elide imports, never use `import elided = require()`. The future default. |

The `target` flag is the most consequential because it determines the runtime cost of every modern syntax feature. `target: ES2022` keeps `async`/`await`, optional chaining (`?.`), nullish coalescing (`??`), class private fields (`#foo`), and top-level `await` as-is — V8 implements them natively. `target: ES2017` would down-level `??` to a polyfill that is 10× slower. `target: ES5` down-levels `async`/`await` to `regenerator-runtime` calls — a 5 KB per file overhead and a noticeable CPU cost in hot paths. Always target the highest version your runtime supports: Node 20 supports ES2022, Node 22 supports ES2023.

The `module` and `moduleResolution` flags must be set consistently. The modern combination is `module: NodeNext` + `moduleResolution: NodeNext`, which respects the `type` field in `package.json` and resolves modules exactly the way Node does — including requiring file extensions in relative imports (`import "./foo.js"` not `import "./foo"`). The legacy combination is `module: CommonJS` + `moduleResolution: node`, which permits extensionless imports and works on any Node version. Migrating from the legacy combination to the modern one is the single most common TypeScript upgrade pain — every relative import in the codebase must have its extension added.

`strict: true` is the single most important flag. It enables `strictNullChecks` (which forces you to handle `null` and `undefined` explicitly — the difference between a TypeScript codebase that catches bugs at compile time and one that ships `TypeError: Cannot read property 'foo' of undefined` to production), `noImplicitAny` (which forbids `function foo(x)` — you must write `function foo(x: unknown)` or `function foo(x: string)`), and six other strict flags. A project with `strict: false` is barely TypeScript; a project with `strict: true` is the type-safety story the language promises.

The failure mode that catches every TypeScript newcomer is the `esModuleInterop` confusion. The library `express` is CommonJS — its `index.js` ends with `module.exports = app;`. Without `esModuleInterop`, you must import it as `import * as express from "express"`, because the `*` namespace import is the only way to capture `module.exports` as a single object. With `esModuleInterop`, `tsc` emits a helper that synthesizes a `default` export from the `module.exports` value, so `import express from "express"` works. The flag has been default-true in `tsc --init` output since 2018, but old configs still disable it and old tutorials still tell you to use `import * as express`. Set `esModuleInterop: true` and use default imports — it is the modern, idiomatic form.

### Transpilation workflows: Using `tsc`, `tsx`, and `ts-node` for local development execution

Three tools will transpile TypeScript to JavaScript for the local dev loop, and they make different trade-offs:

- **`tsc`** — the official TypeScript compiler. Type-checks the entire project, emits `.js` files to `outDir`. Slow (3–10 s for a moderate project), but it is the only tool that produces compiler-level type errors. Use it for production builds.
- **`tsx`** — a wrapper around `esbuild` that transpiles TypeScript file-by-file, ignoring type errors, and runs the result with Node. Fast (~50 ms startup). Use it for the dev loop where you want fast restarts and the IDE is already doing the type-checking.
- **`ts-node`** — the older alternative to `tsx`. Transpiles with `tsc` (slower) but supports type-checking. Largely superseded by `tsx` for new projects.

```bash
# ─── tsc: production build ─────────────────────────────────
npx tsc -p tsconfig.json
# emits dist/server.js, dist/server.js.map, dist/routes/users.js, ...
node dist/server.js

# ─── tsx: dev loop ─────────────────────────────────────────
npx tsx src/server.ts                # run once
npx tsx watch src/server.ts          # restart on file change
# tsx uses esbuild to transpile each file in isolation (no type-checking)
# then runs the result with node --import

# ─── ts-node: legacy dev loop ──────────────────────────────
npx ts-node src/server.ts
npx ts-node-dev --respawn src/server.ts
# uses tsc under the hood, slower but type-checks
```

The trade-off is type-checking vs. speed. `tsc` type-checks the entire project on every build — for a 100-file project this is 3–10 seconds. `tsx` skips type-checking entirely and uses `esbuild` (a Go-based transpiler that is 10–100× faster than `tsc`) to strip types and emit JavaScript. The IDE (VS Code) does the type-checking in real time as you type, so the dev loop does not need to repeat it — `tsx` is the right choice. The CI build runs `tsc` and fails on type errors; the local dev loop runs `tsx` and fails only on runtime errors.

```text
  Local dev:
    VS Code type-checks every keystroke (red squiggles)
    npm run dev → tsx watch src/server.ts → restart on save (50ms)
    IDE catches type errors; tsx catches runtime errors

  CI:
    npm ci
    npm run build → tsc -p tsconfig.json → type-check + emit
    npm test      → node --test dist/**/*.test.js
    docker build  → copy dist/ into image
    npm start     → node dist/server.js
```

The production failure mode here is "the code worked with `tsx` in dev but failed in production". The cause is that `tsx` (via `esbuild`) does not respect every `tsconfig.json` flag — it ignores `verbatimModuleSyntax`, it does not respect `decorators` metadata, and it does not type-check. A codebase that compiles cleanly with `tsc` but fails to run with `tsx` is usually one that depends on `tsc`'s emission behaviour (e.g. `enum` const-ness, `parameter property` in constructors). The fix is to ensure CI runs `tsc --noEmit` as a separate step (type-check without emitting) before `tsx`-style transpilation for the actual runtime. This pattern — `tsc --noEmit` for type-checking, `esbuild` for transpilation — is what `vite`, `remix`, and `next` all do internally.

`tsc --watch` (or `tsc -w`) is the incremental watch mode: `tsc` compiles once, then subscribes to the filesystem for changes and recompiles only the affected files. The incremental state is persisted to `tsconfig.tsbuildinfo` (a binary file containing the program graph) so that even a cold restart of `tsc --watch` is faster than a fresh `tsc` invocation. The watch mode uses the same incremental builder as `tsc --incremental`, which tracks the dependency graph between files and knows that a change to `types.ts` requires recompiling every file that imports it, while a change to `users.ts` only requires recompiling `users.ts` itself. For a 500-file project, a full `tsc` build takes 8 seconds; a `tsc --watch` rebuild after a one-file change takes 200 ms:

```bash
npx tsc --watch                # equivalent to tsc -w -p tsconfig.json
npx tsc --incremental          # one-shot, but persists tsconfig.tsbuildinfo for next time
npx tsc --incremental --watch  # both — fastest local dev loop using tsc
# tsconfig.tsbuildinfo is gitignored — never commit it
```

The `.tsbuildinfo` file is the cache that makes `--incremental` fast. It contains the project's type-checking state: every file's hash, its resolved imports, its exported symbols, and the types of every declaration. A corrupted `.tsbuildinfo` (e.g. after a Git merge that changed both `tsconfig.json` and source files) produces phantom type errors that point at the wrong line. The fix is `rm tsconfig.tsbuildinfo && npx tsc --noEmit` — a full rebuild that regenerates the cache.

`tsc -b` (build mode) is the higher-level orchestration mode designed for multi-project repositories. It accepts one or more `tsconfig.json` files as arguments, builds them in dependency order, and skips projects whose outputs are up-to-date. The prerequisite is "project references" — a `tsconfig.json` field that declares dependencies between TypeScript projects. This is how a monorepo with `packages/shared`, `packages/server`, and `packages/web` builds incrementally: a change to `shared` rebuilds `server` and `web` (the downstream consumers) but a change to `server` rebuilds only `server`:

```jsonc
// tsconfig.json (solution file at repo root)
{
  "files": [],
  "references": [
    { "path": "./packages/shared/tsconfig.json" },
    { "path": "./packages/server/tsconfig.json" },
    { "path": "./packages/web/tsconfig.json" }
  ]
}

// packages/server/tsconfig.json
{
  "compilerOptions": {
    "composite": true,                    // required for project references
    "declaration": true,                  // required: emits .d.ts for downstream consumers
    "outDir": "./dist",
    "rootDir": "./src"
  },
  "references": [
    { "path": "../shared" }               // server depends on shared
  ],
  "include": ["src/**/*"]
}
```

With `composite: true` and `declaration: true`, each project emits `.d.ts` files alongside its `.js` outputs. When `packages/server` imports from `packages/shared`, `tsc -b` resolves the import to `packages/shared/dist/index.d.ts` instead of the source — this is what makes incremental builds across a monorepo fast. Run `tsc -b --watch` for a continuous build, and `tsc -b --clean` to wipe all `dist/` and `*.tsbuildinfo` files when the cache goes stale. The failure mode is a missing `composite: true` on a referenced project — `tsc -b` throws `Referenced project may not disable emit` or `Referenced project must have setting composite: true`, and the build fails until you add it.

```text
  $ npx tsc -b --verbose
  [11:42:03] Projects in this build: shared, server, web
  [11:42:03] Project 'shared' is up to date in build 1/3
  [11:42:03] Project 'server' is out of date with build 1/3 because output file 'dist/index.js' does not exist
  [11:42:04] Project 'server' built in 1.2s
  [11:42:04] Project 'web' is out of date with build 1/3 because dependency 'server' was rebuilt
  [11:42:05] Project 'web' built in 0.8s
  [11:42:05] Build succeeded in 2.1s
```

The bundler-vs-tsc distinction matters for production builds. `tsc` is a *compiler*: it type-checks, it emits one `.js` per `.ts`, and it stops. It does not bundle — `dist/` will contain 500 separate `.js` files mirroring the `src/` tree, and Node loads each via `import` at runtime. A *bundler* (esbuild, swc, vite, rollup, webpack) takes the same `src/` tree and produces one or a few files by inlining imports, tree-shaking unused exports, and minifying the output. For a Node backend, you usually do not need a bundler — `tsc && node dist/server.js` is sufficient. For a browser frontend, you always need a bundler because browsers do not resolve `node_modules`. For a serverless function (Lambda, Cloudflare Worker), a bundler is essential to keep the cold-start artifact small (a 50 KB bundled Lambda starts in 100 ms; a 50 MB `dist/` folder starts in 2 s):

```text
  tsc alone:                  bundler (esbuild):
  src/                        src/
  ├── server.ts               ├── server.ts
  ├── routes/users.ts         └── routes/users.ts
  └── lib/db.ts               └── lib/db.ts
  ↓ tsc                       ↓ esbuild src/server.ts --bundle --platform=node
  dist/                       dist/
  ├── server.js               └── server.js   ← single file, ~150 KB,
  ├── routes/users.js                             all deps inlined, tree-shaken
  └── lib/db.js               (3 files, ~80 KB total,
                                runtime resolves imports via node_modules)
```

esbuild (Go, by Evan Wallace) is the dominant bundler for TypeScript in 2024 — it is 10–100× faster than `tsc` because it parses, type-strips, and emits in a single parallelized pass without doing type-checking. swc (Rust, by Vercel) is the alternative — same approach, used by Next.js for its fast refresh and production builds. vite (esbuild + rollup, by Evan You) is the dev-server layer that wraps esbuild for HMR. rollup is the production bundler that vite uses for its final build — slower than esbuild but produces smaller output via more aggressive tree-shaking. webpack is the legacy bundler — still widely used but 10–50× slower than esbuild for the same input. None of these type-check; the contract is "the IDE type-checks as you type, CI runs `tsc --noEmit`, the bundler handles the production emit". This split is what every modern TypeScript project does.

| Tool | Language | What it does | Type-checks? | Use case |
|---|---|---|---|---|
| `tsc` | TypeScript | Compile + emit one `.js` per `.ts` | Yes | Production builds for Node backends |
| `tsc --noEmit` | TypeScript | Type-check only, no emit | Yes | CI gate; runs in parallel with bundler |
| `tsc -b` | TypeScript | Build multi-project monorepos with project refs | Yes | Monorepos (packages/shared, packages/server) |
| `esbuild` | Go | Transpile + bundle, no type-check | No | Fast dev loop, fast production bundling |
| `swc` | Rust | Transpile + bundle (used by Next.js) | No | Next.js build pipeline |
| `vite` | JS (wraps esbuild + rollup) | Dev server + HMR + production bundler | No | Frontend dev experience |
| `rollup` | JS | Production bundler, aggressive tree-shaking | No | Library builds, vite's production step |
| `tsx` | JS (wraps esbuild) | Run `.ts` files directly without emit | No | Local dev loop for Node scripts |
| `ts-node` | JS (wraps tsc) | Run `.ts` files with type-checking | Yes (optional) | Legacy dev loop, mostly replaced by `tsx` |

## Key Takeaways

1. **`package.json` is the project manifest — `type: "module"` switches between CommonJS and ESM.** Put every build-time tool in `devDependencies` and invoke via `npx`. Set `private: true` on apps.
2. **`tsconfig.json`'s `strict: true`, `target: ES2022`, `module: NodeNext`, `esModuleInterop: true` is the modern baseline.** Audit with `npx tsc --showConfig`. Never use global TypeScript.
3. **`tsc` for production builds (type-check + emit), `tsx` for the dev loop (transpile-only, fast).** Run `tsc --noEmit` in CI to catch type errors that `tsx` skipped. The IDE does the type-checking that `tsx` omits.
