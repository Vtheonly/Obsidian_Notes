# 01.03.04. Bootstrapping a Bare-Metal Express TypeScript Application

## What This Is

This is the delta-flavoured anchor note for sub-section 01.03 — the Node equivalent of [[01.02.04. Bootstrapping a Bare-Metal Spring Boot Application]]. We bootstrap an Express + TypeScript HTTP service from scratch: install Express and its type definitions, write a typed entry point with explicit `Request`/`Response`/`NextFunction` annotations, configure source maps so stack traces and IDE breakpoints map back to TypeScript source, and run the result with `tsx` in development and `node` against the compiled output in production. The result is a 60-line TypeScript application that listens on port 3000 and answers `GET /health` with `{"status":"ok"}` — the same minimum viable service as the Spring Boot anchor, expressed in a different runtime.

Express is the anchor choice because it is the most-deployed Node web framework and the one with the most explicit request lifecycle (no magic, no decorators, just `app.get(path, handler)`). The lesson this note teaches that Spring Boot does not is the cost of the type-system escape hatch: TypeScript types are erased at runtime, so a `req.body: CreateUserRequest` annotation does not actually validate the request body — you must add a runtime validator (Zod, Valibot, or `express-validator`) to get the safety Spring Boot gets for free via `@Valid`.

## The Details

### Installing `express`, `@types/express`, `@types/node`, and development dependencies

Express is published as a CommonJS package with no bundled TypeScript types. To get type-checking, you must install three things: `express` itself (the runtime), `@types/express` (the type definitions for Express's API), and `@types/node` (the type definitions for Node's built-in modules like `fs`, `http`, `path`). The `@types/*` packages come from DefinitelyTyped, a community-maintained repository of type definitions for libraries that do not ship their own.

```bash
mkdir myapp && cd myapp
npm init -y

# install runtime dependencies
npm install express

# install dev dependencies (types + dev tooling)
npm install -D typescript tsx @types/express @types/node

# verify versions
npx tsc --version       # 5.5.4
node -e "console.log(require('express/package.json').version)"   # 4.19.2
```

The reason `@types/express` is a separate package and not bundled with `express` is historical: Express 4 was released in 2014, before TypeScript was widely adopted. Express 5 (still in beta as of 2024) ships its own types. For any package whose README does not say "ships with TypeScript types", you need a `@types/<package>` lookup — `npm install -D @types/<package>` or, if no such package exists, you write a custom declaration file (`declarations.d.ts` with `declare module "some-untyped-lib";`).

The resulting `package.json`:

```json
{
  "name": "myapp",
  "version": "1.0.0",
  "private": true,
  "type": "module",
  "engines": { "node": ">=20.0.0" },
  "scripts": {
    "dev": "tsx watch src/index.ts",
    "dev:nodemon": "nodemon --exec \"tsx src/index.ts\" --watch src",
    "build": "tsc -p tsconfig.json",
    "start": "node --enable-source-maps dist/index.js",
    "start:prod": "tsc -p tsconfig.json && node --enable-source-maps dist/index.js",
    "test": "node --test --import tsx src/**/*.test.ts"
  },
  "dependencies": {
    "express": "^4.19.2"
  },
  "devDependencies": {
    "@types/express": "^4.17.21",
    "@types/node": "^20.14.0",
    "tsx": "^4.7.0",
    "typescript": "^5.5.0"
  }
}
```

The five npm scripts encode the project's lifecycle. `npm run dev` starts `tsx watch`, which watches `src/index.ts` and restarts on every file change (~50 ms restart time) — this is the modern replacement for `ts-node-dev` and is what most TypeScript projects use in 2024. `npm run dev:nodemon` shows the legacy alternative: `nodemon` is a process supervisor that watches files and runs the command in `--exec` on every change. Before `tsx`, the typical chain was `nodemon --exec ts-node src/index.ts`; today the chain is `nodemon --exec tsx src/index.ts` only if you need nodemon's specific features (delayed restart, signal handling, ignore patterns). For new projects, prefer `tsx watch` — it is faster and has fewer moving parts.

`npm run build` runs `tsc` for type-checking and emission to `dist/`. The production equivalent `npm run start:prod` chains the build and the run in one command: `tsc -p tsconfig.json && node --enable-source-maps dist/index.js`. The `&&` short-circuits — if `tsc` finds a type error (exit code 1), the `node` step is skipped, preventing you from running stale bytecode against changed source. This is the same contract as `mvn package && java -jar target/app.jar` in the Spring Boot world: build artefact must exist before runtime. `npm start` runs the compiled output with plain `node` (assumes `npm run build` has been run separately — typical for Docker images where build and run are separate stages).

The failure mode here is "missing types break the build". A package without types compiles to `any` — TypeScript silently allows any operation on it, and type-checking becomes a lie. The defence is `strict: true` plus the `noImplicitAny` flag (which is part of `strict`), which makes any untyped import a compile error. The fix is either to install `@types/<package>` or to write a minimal ambient declaration:

```typescript
// src/types/declarations.d.ts
declare module "some-untyped-lib" {
  export function doSomething(input: string): Promise<void>;
}
```

A subtler failure mode is "@types version drift". The `@types/express` major version tracks the Express major version: `@types/express@4.x` matches `express@4.x`. If you upgrade Express to 5.0 (which ships its own types) but leave `@types/express@4.x` in `devDependencies`, TypeScript will use the stale 4.x types and silently miss 5.x API changes — or worse, fail to compile because the 4.x types reference APIs removed in 5.x. The fix is to remove `@types/express` from `devDependencies` when upgrading to Express 5, and to verify with `npx tsc --noEmit` that nothing breaks.

### Writing a typed `server.ts` entry point with explicit `Request`, `Response`, and `Application` types

The Express application is an `Application` object created by calling `express()`. Routes are registered on it with `app.get(path, handler)`, `app.post(path, handler)`, etc. The handler is a function `(req, res, next) => void` where `req` is `Request`, `res` is `Response`, and `next` is `NextFunction` from `@types/express`.

```typescript
// src/app.ts — the application factory, importable and testable
import express, {
  type Request,
  type Response,
  type NextFunction,
  type Application,
  json,
} from "express";

export function createApp(): Application {
  const app = express();

  // JSON body parser — must be registered before routes
  app.use(json());

  // Health check endpoint
  app.get("/health", (_req: Request, res: Response) => {
    res.json({
      status: "ok",
      timestamp: new Date().toISOString(),
      version: process.env.npm_package_version ?? "0.0.0",
    });
  });

  // Centralized error handler — must be the LAST middleware registered
  app.use((err: Error, _req: Request, res: Response, _next: NextFunction) => {
    console.error(err);
    res.status(500).json({ error: "internal server error" });
  });

  return app;
}

export default createApp;
```

```typescript
// src/index.ts — the entry point, owns process concerns (port, listen, signals)
import { createApp } from "./app.js";

const app = createApp();
const PORT = Number(process.env.PORT ?? 3000);

const server = app.listen(PORT, () => {
  console.log(`Server listening on http://localhost:${PORT}`);
});

// graceful shutdown: stop accepting new connections, drain in-flight
process.on("SIGTERM", () => {
  console.log("SIGTERM received, shutting down");
  server.close(() => process.exit(0));
});
```

Splitting the application into `src/app.ts` (creates and exports the `Application`) and `src/index.ts` (imports it, binds a port, wires process signals) is the Express equivalent of Spring Boot separating `@SpringBootApplication` from the embedded Tomcat lifecycle. The benefit is testability: integration tests can `import { createApp } from "../src/app.js"` and call `request(app).get("/health")` against the in-memory application without binding a port. The same pattern is used by Fastify (`fastify()` factory), Koa (`new Koa()`), and Hapi (`server = Hapi.server()`).

The `app.use(express.json())` line registers the JSON body parser as a global middleware. It must be registered *before* any route that uses `req.body` — Express middleware runs in registration order, and `req.body` is `undefined` until the parser populates it. The parser reads the request stream, parses it as JSON, and assigns the result to `req.body`. If the body is not valid JSON, it throws a `SyntaxError` that is forwarded to the error handler.

The `Request<Params, ResBody, ReqBody>` generic parameters let you type the URL parameters, response body, and request body respectively. `app.post("/users", (req: Request<{}, {}, CreateUserRequest>, ...) => ...)` tells TypeScript that `req.body` is a `CreateUserRequest`. The type annotation is a compile-time hint only — Express does not validate the request body at runtime, so a malformed request with `{"name": 123}` will pass the type-checker but produce `name: 123` at runtime. To get runtime validation, add Zod:

```typescript
import { z } from "zod";

const CreateUserSchema = z.object({
  name: z.string().min(1),
  email: z.string().email(),
});

app.post("/users", (req, res, next) => {
  try {
    const { name, email } = CreateUserSchema.parse(req.body);  // throws ZodError on invalid
    // ... rest of handler
  } catch (err) {
    next(err);
  }
});
```

The error handler middleware has a 4-argument signature `(err, req, res, next)`. Express identifies error handlers by arity (the number of arguments) — a middleware with 4 arguments is an error handler, with 3 it is a regular middleware. The error handler must be registered last; everything after it is unreachable. The `next(err)` call in any middleware or route handler jumps to the next error handler in the chain.

The `app.listen(PORT, callback)` call binds a TCP socket on `0.0.0.0:PORT` and starts accepting connections. Internally it calls Node's `http.createServer(app).listen(PORT)`. The callback fires when the socket is bound. The server runs until `process.exit()` is called, `SIGINT`/`SIGTERM` is received and not handled, or the event loop becomes empty (which never happens for a server with active connections). Calling `server.close()` (as the `SIGTERM` handler above does) stops accepting new connections and waits for in-flight requests to finish before the underlying socket is released — this is the kernel-level mechanic that makes zero-downtime Kubernetes rolling deploys possible.

The failure mode this exposes is the "unhandled async error" crash. If a route handler is `async` and throws, Express 4 does not catch the rejection — the promise rejects, Node sees an unhandled rejection, and the process exits with code 1. Express 5 (in beta) catches async errors automatically; Express 4 requires you to wrap every async handler in a `try/catch` and call `next(err)`, or to install a wrapper like `express-async-handler`:

```typescript
import asyncHandler from "express-async-handler";

app.post("/users", asyncHandler(async (req, res) => {
  const user = await userService.create(req.body);  // rejection → forwarded to next(err)
  res.status(201).json(user);
}));
```

Without this pattern, a single unhandled async error in any route handler crashes the entire Node process, taking down every other in-flight request. This is the Node equivalent of Spring Boot's Tomcat thread pool — except where Spring isolates per-thread failures, Node's single-thread model means every failure is process-wide. The defence in production is to run under a process supervisor (PM2, systemd, or a Kubernetes Deployment with `restartPolicy: Always`) so the container restarts on crash, and to install a `process.on("unhandledRejection", ...)` hook that logs the rejection and exits gracefully rather than letting Node's default behaviour (log + continue in a corrupted state) take over.

### Configuring source-maps for native TypeScript line-by-line debugging in IDEs and Chrome DevTools

When `tsc` compiles `server.ts` to `server.js`, the emitted JavaScript has different line numbers than the source — TypeScript's type annotations are stripped, decorators are down-leveled, and the resulting file is shorter. A stack trace from the compiled JavaScript points to line 47 of `server.js`, but you wrote `server.ts` and want to know which line of *that* file threw. Source maps bridge the gap: a `.map` file alongside `server.js` records the mapping from emitted-line/column to source-line/column, and debuggers read it to translate stack traces and breakpoints.

Enable source maps in `tsconfig.json`:

```jsonc
{
  "compilerOptions": {
    "sourceMap": true,                 // emit .js.map files
    "inlineSources": false,            // do not embed source in the .map (keep .map small)
    "sourceRoot": "./src",             // where the debugger should look for sources
    "mapRoot": "./dist",               // where the .map files are
    // ... other options
  }
}
```

For stack traces to use source maps at runtime, install the `source-map-support` package and import it at the very top of your entry point:

```bash
npm install source-map-support
```

```typescript
// src/index.ts — first line
import "source-map-support/register.js";

// now stack traces show app.ts:42 instead of app.js:38
```

Or, run Node with the `--enable-source-maps` flag (Node 12+), which is built in and requires no package:

```bash
node --enable-source-maps dist/index.js
```

The `--enable-source-maps` flag is the modern, recommended approach — it works for any Node program without code changes, and it works for both stack traces and `Error.prepareStackTrace` customizations. The only reason to use `source-map-support` is if you are stuck on Node <12 or need the `retrieveFile` hook for non-standard source map locations.

For IDE debugging, VS Code's `launch.json` launches the Node process with `--inspect` and attaches the debugger. The `outFiles` glob tells VS Code where to find the source maps:

```json
// .vscode/launch.json
{
  "version": "0.2.0",
  "configurations": [
    {
      "type": "node",
      "request": "launch",
      "name": "Debug Express",
      "runtimeArgs": ["--enable-source-maps", "-r", "tsx/cjs", "src/index.ts"],
      "console": "integratedTerminal",
      "skipFiles": ["<node_internals>/**"],
      "outFiles": ["${workspaceFolder}/dist/**/*.js"]
    },
    {
      "type": "node",
      "request": "attach",
      "name": "Attach by PID",
      "processId": "${command:PickProcess}",
      "skipFiles": ["<node_internals>/**"]
    }
  ]
}
```

The first configuration runs `src/index.ts` directly via `tsx` with the debugger attached — useful for development, where you want fast restarts and TS-aware breakpoints. The second attaches to an already-running process — useful for debugging a Docker container that exposes port 9229 (the default `--inspect` port).

For Chrome DevTools, run Node with `--inspect` (or `--inspect-brk` to break on the first line):

```bash
node --inspect-brk=0.0.0.0:9229 --enable-source-maps dist/index.js

# then open chrome://inspect in Chrome and click "inspect" under "Remote Target"
```

DevTools opens a familiar Chrome debugger UI — Sources panel with the original TypeScript files (loaded via source maps), breakpoints, watch expressions, call stack, scope variables, and the console. The same DevTools protocol powers VS Code's debugger, so the experience is identical.

```text
  Source map data flow:

  server.ts (TypeScript source, what you wrote)
      │
      │  tsc -p tsconfig.json  (with sourceMap: true)
      ▼
  server.js (emitted JavaScript, what Node runs)
  server.js.map (JSON mapping: { "version": 3, "sources": ["../src/server.ts"],
                                  "mappings": "AAAA,CAAC...", "file": "server.js" })

  ─── at runtime ───

  Error thrown at server.js:47:15
      │
      │  Node reads server.js.map (because --enable-source-maps)
      │  V8 source map codec decodes the "mappings" field
      ▼
  Mapped to server.ts:52:10 (the original TypeScript line)
      │
      ▼
  Stack trace printed:
    at app.get (/app/src/server.ts:52:10)
```

The failure mode that source maps fix is the "production stack trace points to the wrong line" incident. Without source maps, a production error logged as `at Object.<anonymous> (/app/dist/server.js:47:15)` is unreadable — you have to manually find line 47 of the compiled JavaScript and figure out which TypeScript line it came from. With source maps and `--enable-source-maps`, the same error logs as `at Object.<anonymous> (/app/src/server.ts:52:10)` and is immediately actionable. The corollary failure mode is "source maps in production leak source code" — if your `.map` files are deployed alongside `.js`, anyone with read access to the deployed files can recover the original TypeScript source (the `sourcesContent` field of the `.map` embeds the source text). For client-side code this is a concern; for backend code deployed inside a private network it is usually acceptable. If you want strict source confidentiality, set `"sourceMap": false` and `"inlineSourceMap": false` in production builds — but then you must keep the original `dist/` artefacts indexed by git commit SHA so you can map a production stack trace back to source.

```typescript
// src/routes/users.ts — Express Router for the /api/users subtree
import { Router, type Request, type Response, type NextFunction } from "express";
import { z } from "zod";

export const usersRouter = Router();

interface User {
  id: string;
  name: string;
  email: string;
}

// in-memory store — replace with a database in production
const USERS = new Map<string, User>();

// GET /api/users/:id — dynamic route parameter at the path level
usersRouter.get("/:id", (req: Request<{ id: string }>, res: Response, next: NextFunction) => {
  try {
    const { id } = req.params;
    const user = USERS.get(id);
    if (!user) {
      res.status(404).json({ error: `user ${id} not found` });
      return;
    }
    res.json(user);
  } catch (err) {
    next(err);
  }
});

const CreateUserSchema = z.object({
  name: z.string().min(1),
  email: z.string().email(),
});

usersRouter.post("/", (req: Request, res: Response, next: NextFunction) => {
  try {
    const { name, email } = CreateUserSchema.parse(req.body);
    const user: User = { id: crypto.randomUUID(), name, email };
    USERS.set(user.id, user);
    res.status(201).json(user);
  } catch (err) {
    next(err);  // ZodError → forwarded to global error handler
  }
});
```

```typescript
// src/app.ts — application factory
import "source-map-support/register.js";
import express, {
  type Request,
  type Response,
  type NextFunction,
  type Application,
  json,
} from "express";
import { healthRouter } from "./routes/health.js";
import { usersRouter } from "./routes/users.js";

export function createApp(): Application {
  const app = express();

  app.use(json());                  // JSON body parser, before routes
  app.use(healthRouter);            // GET /health
  app.use("/api/users", usersRouter);  // GET /api/users/:id, POST /api/users

  // 404 handler — runs if no route matched
  app.use((_req: Request, res: Response) => {
    res.status(404).json({ error: "not found" });
  });

  // error handler — 4-arg signature, must be last
  app.use((err: Error, _req: Request, res: Response, _next: NextFunction) => {
    console.error(err);
    const status = (err as { status?: number }).status ?? 500;
    res.status(status).json({ error: err.message || "internal server error" });
  });

  return app;
}
```

```typescript
// src/index.ts — entry point: process concerns only
import { createApp } from "./app.js";

});

process.on("SIGINT", () => {
  console.log("SIGINT received, draining connections");
```

## Key Takeaways

1. **Install `express`, `@types/express`, `@types/node`, plus `typescript` and `tsx` as dev dependencies.** The five-script pattern (`dev`/`dev:nodemon`/`build`/`start`/`start:prod`) is the universal Node + TypeScript baseline — `start:prod` chains `tsc && node dist/index.js` so a type error aborts the run.
2. **Express 4 does not catch async errors — wrap every async handler in try/catch or use `express-async-handler`.** A single unhandled rejection crashes the entire process. Use Zod for runtime body validation; TypeScript types alone are erased. Split the app into `src/app.ts` (factory, testable) and `src/index.ts` (process entry, owns `app.listen()` and `SIGTERM` handling).
3. **Source maps (`sourceMap: true` + `node --enable-source-maps`) make production stack traces point to TypeScript source.** VS Code's `launch.json` with `outFiles` enables line-by-line debugging in the IDE. The same DevTools protocol powers Chrome DevTools via `--inspect`.
