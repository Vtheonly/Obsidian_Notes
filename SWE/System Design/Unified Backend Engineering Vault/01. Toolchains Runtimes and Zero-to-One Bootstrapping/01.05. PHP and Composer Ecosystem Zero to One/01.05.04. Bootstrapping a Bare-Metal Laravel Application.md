# 01.05.04. Bootstrapping a Bare-Metal Laravel Application

## What This Is

This is the anchor note for sub-section 01.05 — the PHP equivalent of [[01.02.04. Bootstrapping a Bare-Metal Spring Boot Application]], [[01.03.04. Bootstrapping a Bare-Metal Express TypeScript Application]], [[01.04.03. Bootstrapping a Bare-Metal Flask Application]], and [[01.04.04. Bootstrapping a Bare-Metal Django Application]]. We bootstrap a Laravel application from scratch: create the project via `composer create-project laravel/laravel` or the Laravel installer, walk the generated directory layout, use the Artisan CLI to generate a controller and a route, and serve a JSON `/health` endpoint via `php artisan serve`. The result is a Laravel application with the same minimum-viable shape as the anchors in every other ecosystem — a port that answers HTTP with structured JSON.

Laravel is the anchor choice for PHP because it is the most-deployed PHP framework (the "Rails of PHP") and because its philosophy is closest to Spring Boot's: batteries-included, opinionated, convention-over-configuration. The framework ships with an ORM (Eloquent), a migration system, a templating engine (Blade), a queue system, a task scheduler, an authentication system, an event system, a broadcasting layer, and a testing framework — all configured out of the box. The lesson this note teaches that the bare-metal PHP note ([[01.05.03. Bootstrapping a Vanilla FastCGI Web Script]]) does not is the cost of using a framework: Laravel's bootstrapping, service container, and middleware stack impose ~50 ms of per-request overhead that the bare-metal version does not pay, and the framework's opinions about routing, validation, and persistence are not optional — stepping outside them is fighting the framework.

## The Details

### Initializing a new project via `composer create-project laravel/laravel` or the Laravel Installer

Laravel projects are created by `composer create-project`, which clones the `laravel/laravel` skeleton repository and runs `composer install` on it. The skeleton is a fully-configured Laravel app — `composer.json`, `artisan`, `public/index.php`, `app/`, `config/`, `routes/`, `database/migrations/`, `resources/views/`, `tests/` — ready to run after a single command:

```bash
# Method 1: composer create-project (works everywhere)
composer create-project laravel/laravel myapp
cd myapp
php artisan serve

# Method 2: the Laravel Installer (faster, has more options)
composer global require laravel/installer
# add ~/.composer/vendor/bin to PATH
laravel new myapp
# (it asks: which starter kit? which database? which testing framework? git init?)

# Method 3: with specific options
composer create-project laravel/laravel myapp \
    --prefer-dist \
    --stability=stable \
    --remove-vcs \
    "12.*"

cd myapp
php artisan key:generate     # generate APP_KEY in .env
php artisan serve            # start the dev server
```

The `composer create-project` command is more than `git clone && composer install` — it runs the skeleton's `composer.json` `post-creation-cmd` scripts, which call `php artisan key:generate` (sets `APP_KEY` in `.env`), `php artisan storage:link` (creates the `public/storage` symlink to `storage/app/public`), and `npm install && npm run build` (compiles frontend assets). The result is a runnable app in ~30 seconds.

The `APP_KEY` in `.env` is critical — it is the symmetric key Laravel uses to sign cookies, encrypt session data, and encrypt columns marked with `encrypted` casts. A Laravel app without `APP_KEY` set refuses to start with `RuntimeException: No application encryption key has been specified.`. The key is generated by `php artisan key:generate` and is a 32-character base64 string. Never commit the production `APP_KEY` to version control — it is a secret. The `.env` file is in `.gitignore` by default.

The Laravel installer (`laravel new`) is the more featureful alternative — it offers to install a starter kit (Breeze, Jetstream, None), pick a database (SQLite, MySQL, Postgres), pick a testing framework (PHPUnit, Pest), and initialize a git repo. For backend-only services, pick "None" for the starter kit, "SQLite" for the database (you can change later), and "Pest" for testing (more modern syntax).

The failure mode here is "I forgot to run `php artisan key:generate` in production". The symptom is that sessions do not persist (the cookie signature is invalid), encrypted columns return garbage, or the app refuses to start. The fix is to set `APP_KEY` in the production `.env` (or as an environment variable, which Laravel reads via `env('APP_KEY')`) and to keep it stable across deploys — rotating the key invalidates all existing sessions and makes previously-encrypted columns unreadable.

### Directory architecture: `app/`, `config/`, `routes/`, `database/`, `public/index.php`

The `laravel/laravel` skeleton generates a specific directory structure. Every Laravel app follows this layout — deviation is possible but breaks the framework's conventions:

```text
  myapp/
  ├── app/                          ← application code
  │   ├── Http/
  │   │   ├── Controllers/          ← HTTP controllers (one per resource)
  │   │   ├── Middleware/           ← request middleware (auth, CORS, throttle)
  │   │   ├── Requests/             ← form request validators
  │   │   └── Resources/            ← API response transformers
  │   ├── Models/                   ← Eloquent ORM models
  │   ├── Services/                 ← business logic (service layer)
  │   ├── Providers/                ← service container providers
  │   │   ├── AppServiceProvider.php
  │   │   ├── RouteServiceProvider.php
  │   │   ├── EventServiceProvider.php
  │   │   └── AuthServiceProvider.php
  │   ├── Exceptions/               ← exception handlers
  │   └── Console/
  │       └── Commands/             ← Artisan commands
  ├── bootstrap/                    ← framework bootstrap
  │   ├── app.php                   ← application instance creation (Laravel 11+)
  │   └── providers.php             ← service provider list (Laravel 11+)
  ├── config/                       ← configuration files
  │   ├── app.php                   ← app config (name, env, key, providers)
  │   ├── database.php              ← DB connections
  │   ├── cache.php                 ← cache stores (file, redis, memcached)
  │   ├── queue.php                 ← queue connections (sync, redis, sqs)
  │   ├── session.php               ← session config (driver, lifetime, cookie)
  │   ├── auth.php                  ← auth guards and providers
  │   ├── logging.php               ← log channels (stack, single, daily, slack)
  │   └── ...                       ← 20+ more config files
  ├── database/                     ← database-related files
  │   ├── migrations/               ← migration files (timestamped)
  │   ├── seeders/                  ← database seeders
  │   └── factories/                ← model factories (test data generation)
  ├── public/                       ← web root (nginx document root)
  │   ├── index.php                 ← front controller (the entry point)
  │   ├── .htaccess                 ← Apache URL rewriting
  │   └── robots.txt
  ├── resources/
  │   ├── views/                    ← Blade templates
  │   ├── js/                       ← frontend JavaScript (Vite/Laravel Mix)
  │   ├── css/                      ← frontend styles
  │   └── lang/                     ← localization files
  ├── routes/                       ← route definitions
  │   ├── web.php                   ← routes for web (session, CSRF)
  │   ├── api.php                   ← routes for API (stateless, token auth)
  │   ├── console.php               ← Artisan command definitions
  │   └── channels.php              ← broadcasting channel authorizations
  ├── storage/                      ← file storage (writable by web server)
  │   ├── app/                      ← user-uploaded files
  │   │   └── public/               ← publicly-accessible files (symlinked from public/storage)
  │   ├── framework/                ← framework-generated files (cache, sessions, views)
  │   └── logs/                     ← log files
  ├── tests/                        ← test suite
  │   ├── Feature/                  ← feature tests (HTTP-level)
  │   └── Unit/                     ← unit tests (class-level)
  ├── artisan                       ← Artisan CLI entry point
  ├── composer.json
  ├── composer.lock
  ├── package.json                  ← frontend deps (Vite, Laravel Mix)
  ├── phpunit.xml                   ← PHPUnit config
  ├── .env                          ← environment configuration (gitignored)
  ├── .env.example                  ← template for .env (committed)
  └── .gitignore
```

The `public/` directory is the only one served by the web server — nginx's `root` directive points at `public/`, and `public/index.php` is the front controller. Everything outside `public/` is invisible to HTTP clients, which is why configuration, secrets, and source code are safe in `app/`, `config/`, etc. This is the same security model as Django (where `manage.py` is outside the web root) and the opposite of older PHP apps where every `.php` file was directly URL-accessible.

The `bootstrap/app.php` file (Laravel 11+) is where the application instance is created and configured:

```php
<?php
// bootstrap/app.php (Laravel 11+)
use Illuminate\Foundation\Application;
use Illuminate\Foundation\Configuration\Exceptions;
use Illuminate\Foundation\Configuration\Middleware;

return Application::configure(basePath: dirname(__DIR__))
    ->withRouting(
        web: __DIR__ . '/../routes/web.php',
        api: __DIR__ . '/../routes/api.php',
        commands: __DIR__ . '/../routes/console.php',
        health: '/up',                 ← built-in health check at /up
    )
    ->withMiddleware(function (Middleware $middleware) {
        // append custom middleware
    })
    ->withExceptions(function (Exceptions $exceptions) {
        // custom exception rendering
    })
    ->create();
```

The `public/index.php` file is the front controller — every HTTP request goes through it:

```php
<?php
// public/index.php (Laravel 11+)
use Illuminate\Http\Request;

define('LARAVEL_START', microtime(true));

require __DIR__.'/../vendor/autoload.php';     ← Composer autoloader

(require_once __DIR__.'/../bootstrap/app.php')  ← create Application instance
    ->handleRequest(Request::capture());        ← dispatch the request
```

The flow is: nginx receives the request → `try_files` falls back to `index.php` → `index.php` requires the Composer autoloader → `index.php` requires `bootstrap/app.php` which creates the `Application` instance → `handleRequest()` runs the request through the global middleware stack, the route dispatcher, the controller, and the response formatter → the response is sent to the client.

The failure mode this exposes is the "wrong document root" nginx misconfiguration. If nginx's `root` points at the project root (`/var/www/myapp/`) instead of `public/` (`/var/www/myapp/public/`), then every `.php` file in the project is directly URL-accessible — including `config/app.php` (which contains the `APP_KEY`), `bootstrap/app.php` (which contains internal path configuration), and `tests/` (which may contain database credentials). The exploit is `curl http://example.com/.env` and you have the production secrets. The fix is to always set nginx `root` to the `public/` subdirectory and to verify with `curl -I http://example.com/.env` returning 404.

### The Artisan CLI: Exploring generation commands (`make:controller`, `make:model`, `make:migration`)

Artisan is Laravel's command-line tool — invoked via `php artisan <command>`. It serves the same role as Rails' `rails generate`, Django's `manage.py`, and Spring Initializr's project generators. Artisan has ~50 built-in commands and supports custom commands (registered in `app/Console/Commands/`).

```bash
# list all commands
php artisan list

# common generation commands
php artisan make:controller UserController        ← app/Http/Controllers/UserController.php
php artisan make:controller Api/UserController --api   ← API-style (index, store, show, update, destroy)
php artisan make:model User -mfsc                 ← Model + Factory + Migration + Seeder + Controller
php artisan make:model User -mf                   ← Model + Factory + Migration
php artisan make:migration create_users_table     ← database/migrations/2024_09_20_000000_create_users_table.php
php artisan make:migration add_email_to_users --table=users
php artisan make:seeder UserSeeder                ← database/seeders/UserSeeder.php
php artisan make:factory UserFactory --model=User ← database/factories/UserFactory.php
php artisan make:request StoreUserRequest         ← app/Http/Requests/StoreUserRequest.php
php artisan make:resource UserResource            ← app/Http/Resources/UserResource.php
php artisan make:middleware EnsureUserIsAdmin     ← app/Http/Middleware/EnsureUserIsAdmin.php
php artisan make:command SendReports              ← app/Console/Commands/SendReports.php
php artisan make:job ProcessPayment               ← app/Jobs/ProcessPayment.php
php artisan make:event UserRegistered             ← app/Events/UserRegistered.php

# dev server

```

The `make:*` commands generate boilerplate files with the correct namespace, class name, and parent class. The generated `UserController.php`:

```php
<?php
// app/Http/Controllers/UserController.php (generated)
namespace App\Http\Controllers;

use App\Http\Requests\StoreUserRequest;
use App\Http\Requests\UpdateUserRequest;
use App\Models\User;
use App\Http\Resources\UserResource;
use Illuminate\Http\Request;

class UserController extends Controller
{
    public function index()
    {
        $users = User::paginate();
        return UserResource::collection($users);
    }

    public function store(StoreUserRequest $request)
    {
        $user = User::create($request->validated());
        return new UserResource($user);
    }

    public function show(User $user)        ← route-model binding
    {
        return new UserResource($user);
    }

    public function update(UpdateUserRequest $request, User $user)
    {
        $user->update($request->validated());
        return new UserResource($user);
    }

    public function destroy(User $user)
    {
        $user->delete();
        return response()->noContent();
    }
}
```

The `show(User $user)` signature uses Laravel's route-model binding: Laravel sees the `{user}` URL parameter, resolves it to a `User` model by primary key, and injects the model instance into the controller. If the user does not exist, Laravel returns a 404 automatically. This is the equivalent of Spring's `@PathVariable Long id` + manual `userRepository.findById(id).orElseThrow(() -> new NotFoundException())` — but in one parameter.

The `StoreUserRequest $request` parameter is form request validation. Laravel resolves the `StoreUserRequest` from the service container, runs its `authorize()` method (returns true/false to allow/deny the request), runs its `rules()` method (returns an array of validation rules), and injects the validated data via `$request->validated()`. If validation fails, Laravel redirects back (for web) or returns a 422 JSON response (for API) automatically — no boilerplate in the controller.

`php artisan tinker` is the interactive REPL that ships with every Laravel install — the PHP equivalent of Spring Boot's `jshell`, Django's `shell`, or Rails's `rails console`. It boots the entire application (loads `vendor/autoload.php`, instantiates the `Application` from `bootstrap/app.php`, runs all service providers' `boot()` methods, binds every singleton in the container) and drops you into a PsySH prompt where you can evaluate arbitrary PHP against the live application state. It is the single fastest way to debug a model query, test a service-method edge case, or inspect a configuration value without writing a temporary route:

```bash
$ php artisan tinker

Exit:  \q or exit

>>> App\Models\User::count();
=> 14253

>>> $u = App\Models\User::find(42);

     id: 42,
     email: "alice@example.com",
     created_at: "2024-01-15 10:23:11",
   }

>>> $u->orders()->where('total', '>', 1000)->get();
=> Illuminate\Database\Eloquent\Collection {#4533
     all: [
       App\Models\Order {#4534 id: 7, total: 1500.00, ...},
       App\Models\Order {#4535 id: 19, total: 2200.50, ...},
     ],
   }

>>> config('database.default');          // what DB connection is the app using?
=> "mysql"

>>> app('cache')->getStore();            // what cache driver is bound?

>>> \DB::connection()->getPdo()->query('SELECT version()')->fetchColumn();

     {"query":"select * from `users` where `active` = ? limit 5", "bindings":[1], "time":1.23},

```

The key value of `tinker` over `php -a` (the bare PHP interactive shell) is that it loads the entire framework context: the service container is bound, Eloquent's bootstrapped, facades resolve to real instances, the database connection pool is initialised, the `config/*` files are loaded (so `config('app.url')` returns the resolved value), and any side effects (sending an email, writing to the DB, dispatching a job) actually execute against your local database and queues. This is also its danger — `User::all()->each(fn ($u) => $u->delete())` in tinker deletes every row in the production `users` table if you are connected to production. Always check `env('APP_ENV')` first: it must say `local` (or whatever non-production env you intend); if it says `production`, exit immediately.

The tinker REPL also exposes every Laravel facade (`Cache::`, `Queue::`, `Mail::`, `Log::`, `Event::`, `Route::`, `DB::`, `Config::`, `Artisan::`) for ad-hoc inspection. `Route::getRoutes()` dumps every registered route; `Cache::getStore()` tells you which cache driver is bound; `Queue::size('emails')` returns the depth of the `emails` queue. The same introspection in a Spring Boot app would require writing a temporary `@RestController` endpoint, deploying it, and curling it — tinker collapses that loop into seconds. The failure mode to watch for is calling `tinker` against a production database with a typo in a `where` clause (`User::where('id', '>', 0)->delete()` is a real-world incident from 2019); the defence is the `APP_ENV` check above and the discipline of never running tinker against a production replica that has write credentials.

The failure mode here is "I edited a config file but Laravel does not see the change". The reason is `php artisan config:cache`, which compiles all `config/*.php` files into a single cached PHP file at `bootstrap/cache/config.php`. When the cache exists, Laravel reads it instead of the `config/*.php` files — so editing `config/database.php` has no effect until you run `php artisan config:clear` (or `config:cache` again to refresh). The same applies to `route:cache`, `view:cache`, and `event:cache`. In dev, never run the `:cache` commands; in production, always run `php artisan optimize` after each deploy (which builds all the caches), and run `php artisan optimize:clear` before each deploy if you are doing rolling updates.

### Writing a minimal JSON API route in `routes/api.php` and executing the application via `php artisan serve`

Laravel's router is configured in `routes/web.php` (for web routes, with session and CSRF middleware) and `routes/api.php` (for API routes, stateless, with `auth:sanctum` middleware and `/api` prefix). For a JSON API, edit `routes/api.php`:

```php
<?php
// routes/api.php
use App\Http\Controllers\HealthController;
use Illuminate\Support\Facades\Route;

Route::get('/health', [HealthController::class, 'check']);
```

```php
<?php
// app/Http/Controllers/HealthController.php
namespace App\Http\Controllers;

use Illuminate\Http\JsonResponse;

class HealthController extends Controller
{
    public function check(): JsonResponse
    {
        return response()->json([
            'status' => 'ok',
            'timestamp' => now()->toISOString(),
            'version' => app()->version(),
        ]);
    }
}
```

Generate the controller with Artisan, register the route, and run the dev server:

```bash
# generate the controller
php artisan make:controller HealthController

# edit routes/api.php (add the route above)

# verify the route is registered
php artisan route:list --path=api/health
# GET|HEAD  api/health  ...  HealthController@check

# start the dev server
php artisan serve
# INFO  Server running on [http://127.0.0.1:8000].

# in another terminal
curl http://localhost:8000/api/health
# {"status":"ok","timestamp":"2024-09-20T14:32:11.000000Z","version":"12.0.0"}
```

The `response()->json($data)` helper creates a `JsonResponse` object — the Laravel equivalent of Flask's `jsonify` and Django's `JsonResponse`. It serializes the array to JSON with `json_encode`, sets the `Content-Type: application/json` header, and returns the response. The optional second argument is the HTTP status code (`response()->json($data, 201)`), and the third is an array of headers (`response()->json($data, 200, ['X-Request-Id' => $id])`).

The `now()` helper is a Laravel global that returns a `Carbon\Carbon` instance (a wrapper around PHP's `DateTime`). `now()->toISOString()` returns an ISO 8601 timestamp. Carbon is one of Laravel's most loved features — it makes date arithmetic readable: `now()->addDays(7)->startOfDay()`, `Carbon::parse('2024-01-15')->diffForHumans()`, `$user->created_at->isWeekend()`.

The `app()->version()` returns the Laravel framework version (e.g. `"12.0.0"`). The `app()` helper returns the service container, which is the central registry of Laravel's dependency injection system.

For production, Laravel does not run under `php artisan serve` — it runs behind nginx + PHP-FPM (see [[01.05.01. Installing PHP CLI and PHP-FPM Runtimes]]). The nginx config points at `public/index.php` as the front controller:

```nginx
server {
    listen 80;
    server_name example.com;
    root /var/www/myapp/public;
    index index.php;

    location / {
        try_files $uri $uri/ /index.php?$query_string;
    }

    location ~ \.php$ {
        fastcgi_pass unix:/run/php/php8.3-fpm.sock;
        fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
        include fastcgi_params;
    }

    location ~* \.(css|js|png|jpg|svg|ico)$ {
        expires 30d;
        access_log off;
    }
}
```

The deploy sequence:

```bash
# 1. install dependencies (no dev deps, optimized autoloader)
composer install --no-dev --optimize-autoloader

# 2. build frontend assets
npm ci && npm run build

# 3. cache configuration, routes, views, events
php artisan optimize

# 4. run pending migrations
php artisan migrate --force

# 5. restart PHP-FPM workers (to clear OPcache)
sudo systemctl reload php8.3-fpm
# or: opcache_reset() via a request to /opcache-reset
```

The `--force` flag on `migrate` skips the prompt that asks "you are running in production, are you sure?". In CI/CD, the prompt would block the deploy; `--force` makes it non-interactive.

The failure mode that catches every Laravel newcomer is the "stale OPcache" deploy bug. PHP-FPM workers cache compiled bytecode in OPcache; when you deploy new code, the cached bytecode is the old code, and the new code is not picked up until OPcache is cleared. Setting `opcache.validate_timestamps = 0` in production (for performance) makes this worse — OPcache never checks file mtimes. The fix is to call `opcache_reset()` after deploy (via an HTTP endpoint, a CLI command, or by sending `SIGUSR2` to PHP-FPM which triggers a graceful reload and OPcache reset). Laravel 11+ has `php artisan optimize:clear` which clears the Laravel caches but not OPcache — you need a separate step for OPcache.

## Key Takeaways

1. **`composer create-project laravel/laravel` + `php artisan key:generate` bootstraps a runnable Laravel app.** The `APP_KEY` in `.env` signs cookies and encrypts columns — generate it once and never rotate it casually.
2. **The `public/` directory is the only web-served directory; `public/index.php` is the front controller.** nginx's `root` must point at `public/`, never at the project root — otherwise `.env` and `config/` are URL-accessible.
3. **Artisan generates controllers, models, migrations, and runs the dev server.** Run `php artisan optimize` after each production deploy to cache config/routes/views/events; clear OPcache separately by reloading PHP-FPM. The `php artisan route:list` command is the universal "what routes are registered?" debugging tool.
