# 01.05.01. Installing PHP CLI and PHP-FPM Runtimes

## What This Is

PHP has two SAPIs (Server API modes) that matter for backend engineering: the CLI SAPI (`php-cli`, used for scripts, cron jobs, queues, and the Laravel/Artisan console) and the FastCGI Process Manager SAPI (`php-fpm`, used behind nginx or Apache to serve HTTP requests). The two SAPIs run the same Zend Engine but with different process models, different `php.ini` defaults, and different lifecycle hooks. This note walks the install of both on Ubuntu (`ondrej/php` PPA), macOS (Homebrew), and Windows (windows.php.net MSI), the `php.ini` configuration that every production deployment must tune (`memory_limit`, `max_execution_time`, `error_reporting`, `extension=`), and the verification commands (`php -v`, `php -m`, `php-fpm -t`). The PHP runtime sits between the OS (section 02) and the framework (section 05 — Laravel); its per-request teardown model (no shared state between requests, no long-lived in-process state) is what makes PHP applications behave fundamentally differently from JVM/Node/Python applications.

The note is the PHP equivalent of [[01.02.01. Installing JDK and Environment Configuration]] and [[01.04.01. Installing Python and Environment Isolation]]. The failure modes it governs are the ones that surface as `PHP Fatal error: Allowed memory size of 134217728 bytes exhausted`, `504 Gateway Timeout` from PHP-FPM workers exceeding `max_execution_time`, `Class 'PDO' not found` because the `pdo_pgsql` extension was not loaded, and the classic "Composer requires PHP 8.2 but the system has 7.4" install error.

## The Details

### Installing PHP runtime, development headers, and standard extensions via package managers (`ondrej/php` PPA, Homebrew)

PHP is shipped as multiple packages — the runtime itself (`php8.3-cli`, `php8.3-fpm`), the development headers (`php8.3-dev`), and dozens of extensions (`php8.3-pgsql`, `php8.3-curl`, `php8.3-mbstring`, `php8.3-xml`, `php8.3-zip`, `php8.3-intl`, `php8.3-bcmath`, `php8.3-redis`, etc.). The extensions are loadable shared objects (`.so` files installed to `/usr/lib/php/<version>/`) that you enable in `php.ini` with `extension=pgsql.so`. A bare PHP install with no extensions is useless for backend engineering — you need at minimum `curl`, `mbstring`, and `xml` for any modern framework.

The `ondrej/php` PPA is the canonical PHP source on Ubuntu. It is maintained by Ondřej Surý (Debian PHP maintainer) and provides PHP 5.6 through 8.x side-by-side. Install it:

```bash
# Ubuntu / Debian
sudo add-apt-repository ppa:ondrej/php        # Ubuntu
sudo apt update

# or for Debian, use sury.org's repo:
# sudo apt install -y ca-certificates lsb-release curl
# sudo curl -sSLo /etc/apt/trusted.gpg.d/php.gpg https://packages.sury.org/php/apt.gpg
# sudo sh -c 'echo "deb https://packages.sury.org/php $(lsb_release -sc) main" > /etc/apt/sources.list.d/php.list'
# sudo apt update

# install PHP 8.3 CLI + FPM + common extensions
sudo apt install -y \
    php8.3-cli \
    php8.3-fpm \
    php8.3-pgsql \
    php8.3-mysql \
    php8.3-curl \
    php8.3-mbstring \
    php8.3-xml \
    php8.3-zip \
    php8.3-intl \
    php8.3-bcmath \
    php8.3-gd \
    php8.3-opcache \
    php8.3-redis \
    php8.3-dev \
    php-pear

# verify
php -v               # PHP 8.3.11 (cli) (built: Aug 27 2024 14:29:14) (NTS)
php-fpm8.3 -v        # PHP 8.3.11 (fpm-fcgi)
php -m               # list loaded extensions
```

```bash
# macOS with Homebrew
brew install php@8.3
brew install shivammathur/php/php@8.3    # or use the shivammathur tap for more versions

# link it
brew link --force --overwrite php@8.3

# verify
php -v                # PHP 8.3.11 (cli)
which php             # /opt/homebrew/bin/php (Apple Silicon) or /usr/local/bin/php (Intel)
```

```powershell
# Windows
# Download from https://windows.php.net/download/ — pick the "Non Thread Safe" zip for IIS/FastCGI,
# or "Thread Safe" for Apache mod_php.
# Extract to C:\php\, add C:\php\ to PATH.

# or with Scoop:
scoop install php8.3

php -v
```

The Ubuntu `ondrej/php` PPA installs side-by-side versions: you can have `php8.1`, `php8.2`, and `php8.3` installed simultaneously, with separate `php.ini` files at `/etc/php/8.1/cli/php.ini`, `/etc/php/8.2/cli/php.ini`, etc. The `php` command on `PATH` is symlinked to the most recent version (`/usr/bin/php → /etc/alternatives/php → /usr/bin/php8.3`); switch the default with `sudo update-alternatives --config php`.

The `php-dev` package is needed if you want to compile PECL extensions (e.g. `sudo pecl install xdebug`). It installs the `phpize` build helper, the PHP header files (`/usr/include/php/8.3/`), and the `php-config` script that returns compiler flags. For most projects you do not need it — every common extension is packaged.

PECL (PHP Extension Community Library, https://pecl.php.net/) is the analogue of npm or PyPI for compiled PHP extensions. Where `composer require` downloads pure-PHP source code that the autoloader picks up at runtime, `pecl install` downloads a C source tarball, runs `phpize` to generate a `configure` script tailored to your exact PHP build, runs `./configure && make && make install`, and drops a shared object (`.so`) into the extension directory (`/usr/lib/php/20230831/` for PHP 8.3 — the numeric suffix is the Zend Module API number, which changes every time the ABI breaks). The final step is to add `extension=xdebug.so` (or `zend_extension=xdebug.so` for Zend extensions) to a `conf.d/20-xdebug.ini` file so PHP-FPM and CLI load it. Modern Ubuntu/Debian packages wrap this whole dance: `sudo apt install php8.3-xdebug` does the compile-once-and-package work upstream, so you get a pre-built binary and an `ini` file in `conf.d/`. Reach for `pecl` directly only when you need a version not yet packaged (e.g. a beta of `xdebug 3.4`, or the `relay` extension for Redis). After a `pecl install`, always run `php-fpm8.3 -t` and `sudo systemctl reload php8.3-fpm` — a missing `.so` or an ABI mismatch (`PHP Warning: xdebug: Unable to initialize module Module compiled with module API=20220829 PHP compiled with module API=20230831`) takes down the entire FPM pool.

In the layered mental model, this install procedure is the PHP instantiation of the toolchain layer (Section 01). The runtime that gets installed here sits directly on the POSIX primitives from Section 02: every PHP-FPM worker is a `fork()`+`exec()`-launched OS process (`/proc/<pid>/status` shows `Name: php-fpm`), every `fread()`/`fwrite()` is a `read()`/`write()` syscall on a file descriptor, and the shared-nothing process model that distinguishes PHP from the JVM and Node (Section 04) is a direct consequence of PHP-FPM being a process pool rather than an in-memory runtime. The extensions you enable here are what the framework layer (Section 05 — Laravel, Symfony) calls into: Laravel's `redis` cache driver needs the `phpredis` extension (or falls back to a pure-PHP userland implementation that is 5–10× slower); Laravel's `pdo_pgsql` driver needs the `pdo_pgsql` extension to talk to Postgres (Section 06.02); Laravel's encryption needs `openssl`. Get the extensions right at install time and the framework can be exercised end-to-end; miss one and the framework blows up on first request with `Class 'PDO' not found`.

The failure mode here is "missing extension at runtime". The symptom is `Fatal error: Uncaught Error: Class "PDO" not found` (the `pdo` extension is not loaded) or `Call to undefined function curl_init()` (the `curl` extension is not loaded). The fix is `sudo apt install php8.3-curl` (or whatever extension is missing) and restarting PHP-FPM (`sudo systemctl restart php8.3-fpm`). Always install extensions via the package manager rather than compiling from source unless you need a specific version.

### Configuring `php.ini`: Memory limits, execution timeouts, error reporting, and extension loading

`php.ini` is PHP's configuration file. It is a plain INI file with `[section]` headers and `key = value` lines. There are separate `php.ini` files for the CLI SAPI and the FPM SAPI — `/etc/php/8.3/cli/php.ini` and `/etc/php/8.3/fpm/php.ini` — because the two SAPIs have different defaults (the CLI never times out, has unlimited memory, and shows all errors; FPM times out at 30 seconds, limits memory to 128 MB, and hides errors by default).

The settings every production deployment must tune:

```ini
; /etc/php/8.3/fpm/php.ini (production)

; ─── Error reporting ──────────────────────────────────────────
error_reporting = E_ALL & ~E_DEPRECATED & ~E_STRICT
display_errors = Off              ; never expose errors to clients in production
display_startup_errors = Off
log_errors = On                   ; send errors to error_log
error_log = /var/log/php/fpm-error.log
error_log_format = "%s: %s"      ; PHP 8.3+ structured log format

; ─── Memory and execution limits ──────────────────────────────
memory_limit = 256M               ; per-request memory limit (was 128M)
max_execution_time = 30           ; seconds before FPM kills the worker (was 30)
max_input_time = 60               ; seconds for parsing input (POST, GET)
max_input_nesting_level = 64
max_input_vars = 1000             ; max POST fields (was 1000; raise for big forms)

; ─── File uploads ─────────────────────────────────────────────
file_uploads = On
upload_max_filesize = 10M         ; max size per uploaded file
post_max_size = 12M               ; max size of total POST body
upload_tmp_dir = /tmp

; ─── Sessions ─────────────────────────────────────────────────
session.save_handler = redis      ; use Redis instead of files (Laravel default)
session.save_path = "tcp://redis:6379"
session.gc_maxlifetime = 1440     ; seconds before session is garbage-collected
session.cookie_secure = On        ; only over HTTPS
session.cookie_httponly = On      ; not accessible via JavaScript
session.cookie_samesite = Strict

; ─── OPcache (bytecode cache — critical for performance) ──────
opcache.enable = 1
opcache.enable_cli = 0            ; not useful for one-shot CLI scripts
opcache.memory_consumption = 128  ; MB of shared memory for bytecode (was 64)
opcache.max_accelerated_files = 10000   ; was 2000 — too low for large apps
opcache.validate_timestamps = 0   ; do NOT check file mtimes in production (perf)
                                  ; requires `opcache_reset()` on deploy
opcache.preload = /app/preload.php   ; preload files at FPM startup (PHP 7.4+)
opcache.preload_user = www-data

; ─── Extensions ───────────────────────────────────────────────
extension = pgsql.so
extension = pdo_pgsql.so
extension = curl.so
extension = mbstring.so
extension = opcache.so             ; OPcache is an extension
zend_extension = xdebug.so         ; Xdebug is a *Zend* extension (different keyword)
```

```ini
; /etc/php/8.3/cli/php.ini (CLI defaults — overrides for scripts)
memory_limit = -1                  ; unlimited (CLI scripts often need more)
max_execution_time = 0             ; never time out
error_reporting = E_ALL
display_errors = On                ; CLI always shows errors
```

The critical settings are `memory_limit` and `max_execution_time`:

- **`memory_limit`** is the per-request memory ceiling. PHP's Zend Engine allocates memory with `emalloc()` (a wrapper around `malloc`) and tracks every allocation; when the running total exceeds `memory_limit`, PHP aborts the request with `Fatal error: Allowed memory size of X bytes exhausted (tried to allocate Y bytes)`. The default 128 MB is too low for many Laravel applications — a moderate Dusk test suite or a large eloquent collection easily exceeds it. Raise to 256 MB for typical web apps, 512 MB or 1 GB for batch jobs.
- **`max_execution_time`** is the wall-clock seconds a request can run before PHP kills it. Default 30 seconds. For a web request, 30 s is reasonable; for a queue worker or long-running script, set it to 0 (unlimited) via `set_time_limit(0)` in the script or `max_execution_time = 0` in CLI `php.ini`.

The `display_errors = Off` setting in production is non-negotiable. PHP's default error output includes the full file path, the line number, the function arguments (which may contain passwords or API keys), and the surrounding source code. Exposing this to clients is an information disclosure vulnerability. Always set `display_errors = Off` and `log_errors = On` in production, then monitor the error log.

The `opcache.validate_timestamps = 0` setting is the production-only performance optimization. By default, OPcache checks every PHP file's mtime on every `include`/`require` and recompiles if the file changed. In production, files do not change between deploys — so checking mtime is wasted work. Setting `validate_timestamps = 0` makes OPcache cache bytecode indefinitely until `opcache_reset()` is called. The deploy script must call `opcache_reset()` (or send `SIGUSR2` to PHP-FPM) after each deploy to invalidate the cache.

The failure mode here is "I edited the `php.ini` but nothing changed". The reason is almost always that there are two `php.ini` files (CLI and FPM), and you edited the wrong one. Or that the `php.ini` you edited is not the one PHP loads — `php --ini` shows which file the CLI SAPI loads, and `php-fpm8.3 -tt` shows the FPM SAPI's effective config. Always verify with these commands after editing.

The two verification commands answer different questions:

# php -m: which extensions are loaded?
$ php -m

The list is split into two sections: `[PHP Modules]` (regular extensions, loaded via `extension=`) and `[Zend Modules]` (Zend extensions, loaded via `zend_extension=` — these hook the Zend Engine itself and include OPcache, Xdebug, and Blackfire). The difference matters because the `extension=` keyword only loads regular extensions; trying to load OPcache with `extension=opcache.so` fails silently (the extension is not loaded).

The `php --ini` command shows the configuration files PHP loaded:

```bash
$ php --ini
Configuration File (php.ini) Path: /etc/php/8.3/cli
Loaded Configuration File:         /etc/php/8.3/cli/php.ini
Scan for additional .ini files in: /etc/php/8.3/cli/conf.d
Additional .ini files parsed:      /etc/php/8.3/cli/conf.d/10-opcache.ini,
                                   /etc/php/8.3/cli/conf.d/20-pdo.ini,
                                   /etc/php/8.3/cli/conf.d/20-pgsql.ini,
                                   /etc/php/8.3/cli/conf.d/20-curl.ini,
                                   ...
```

The "additional .ini files" mechanism is how the Ubuntu/Debian PHP packages manage extensions: each extension ships its own small `.ini` file in `conf.d/` that contains one `extension=...` line. This is cleaner than putting all extensions in `php.ini` directly — you enable/disable an extension by symlinking (or removing) its `conf.d/20-foo.ini` file. The numeric prefix controls load order (10 before 20 before 30), which matters when one extension depends on another.

```bash
# check the FPM SAPI's config
$ php-fpm8.3 -tt 2>&1 | grep memory_limit
php_admin_value[memory_limit] = 256M

# check PHP-FPM pool configuration
$ cat /etc/php/8.3/fpm/pool.d/www.conf | grep -v '^;' | grep -v '^$'
[www]
user = www-data
group = www-data
listen = /run/php/php8.3-fpm.sock
listen.owner = www-data
listen.group = www-data
pm = dynamic
pm.max_children = 50         ; max concurrent PHP-FPM worker processes
pm.start_servers = 5
pm.min_spare_servers = 5
pm.max_spare_servers = 10
pm.max_requests = 1000       ; restart each worker after 1000 requests (memory leak defence)
```

The PHP-FPM pool configuration (`/etc/php/8.3/fpm/pool.d/www.conf`) is where you tune the worker process model. `pm = dynamic` means FPM adjusts the worker count between `pm.min_spare_servers` and `pm.max_children` based on load. `pm = static` runs a fixed number of workers. `pm = ondemand` spawns workers on demand and kills them after `pm.process_idle_timeout` seconds. The `pm.max_requests = 1000` setting is the defence against memory leaks — every PHP-FPM worker is reused across many requests, and any leak (an extension that allocates and does not free, a global that grows) accumulates. Restarting workers after N requests bounds the leak.

The `php-fpm8.3 -t` command checks the syntax of `php.ini` and the FPM pool config without starting the server. Always run it before restarting FPM in production — a syntax error in `php.ini` causes FPM to refuse to start, taking down the entire site. The exit code is 0 on success, non-zero on error:

```bash
$ sudo php-fpm8.3 -t
[01-Oct-2024 12:34:56] NOTICE: configuration file /etc/php/8.3/fpm/php-fpm.conf test is successful

$ echo $?
0

# introduce a syntax error and re-check:
$ sudo php-fpm8.3 -t
[01-Oct-2024 12:35:00] ERROR: [/etc/php/8.3/fpm/php.ini:245] unknown entry 'memory_limit'
[01-Oct-2024 12:35:00] ERROR: failed to load configuration file /etc/php/8.3/fpm/php-fpm.conf

$ echo $?
1
```

Beyond `php -v` and `php -m`, two more introspection commands earn their keep in every PHP engineer's muscle memory. The first is `php -i`, which dumps `phpinfo()` to stdout — every loaded configuration value, every `$_SERVER` entry the SAPI sets, every extension's `ini` settings, the compile-time `Configure Command` (which tells you whether PHP was built with `--with-zlib` or `--enable-mbstring`), the Zend OPcache build, the ICU version used by `intl`, the OpenSSL version used by `openssl_random_pseudo_bytes()`. Because the output is several thousand lines, always pipe it through `grep`:

```bash
# what is the actual memory_limit the CLI SAPI sees?
$ php -i | grep memory_limit
memory_limit => -1 => -1

# what OpenSSL is PHP linked against? (matters for TLS 1.3 + ALPN support)
$ php -i | grep -E 'OpenSSL (Library|Header) Version'
OpenSSL Library Version => OpenSSL 3.0.13 30 Jan 2024
OpenSSL Header Version  => OpenSSL 3.0.13 30 Jan 2024

# what is the exact value of opcache.memory_consumption actually in effect?
$ php -i | grep 'opcache.memory_consumption'
opcache.memory_consumption => 128 => 128

# the web-equivalent: drop a file containing <?php phpinfo(); ?> into the doc root,
# visit /info.php in a browser, then DELETE it before the internet finds it.
# The phpinfo() page also reveals the 'Loaded Configuration File' and the
# 'Scan this dir for additional .ini files' — the same data `php --ini` shows.
```

The second command is `php -S` (the built-in development server), which lets you run a PHP web application without nginx, Apache, or PHP-FPM. It is the PHP analogue of Node's `http.createServer().listen(8000)`, Python's `python -m http.server`, and Java's embedded Jetty. The internal architecture is single-process, single-threaded, blocking I/O — every request is served serially in the same PHP process that lives for the lifetime of the server. This makes it useless for production (a single slow request blocks every other request; there is no keepalive, no HTTP/2, no TLS termination, no graceful shutdown) but ideal for local development and for trying out a script:

```bash
# serve the current directory on port 8000 — any .php file is executed, anything else is served as a static file
$ php -S localhost:8000
[Mon Sep 23 12:00:00 2024] PHP 8.3.11 Development Server (http://localhost:8000) started
[Mon Sep 23 12:00:05 2024] 127.0.0.1:54321 Accepted
[Mon Sep 23 12:00:05 2024] 127.0.0.1:54321 [200]: GET /index.php

# serve a custom document root, with a front-controller router script
$ php -S localhost:8000 -t public/ public/index.php

# bind to all interfaces (for testing from a phone on the LAN)
$ php -S 0.0.0.0:8000 -t public/
```

The `-S` server populates the same `$_SERVER`, `$_GET`, `$_POST`, `$_FILES` superglobals that PHP-FPM populates, so code that runs under `php -S` will run (almost) identically under nginx + PHP-FPM. The differences are subtle: `$_SERVER['SERVER_SOFTWARE']` is `PHP 8.3.11 Development Server` (so framework code that detects the dev server can short-circuit behaviours like HTTPS redirects); the `Content-Type` header for static files is guessed from the file extension via the `mime.types` list compiled into PHP, not from nginx's `mime.types`; and `php -S` has no concept of `try_files` — the front-controller router pattern requires an explicit router script (see [[01.05.03. Bootstrapping a Vanilla FastCGI Web Script]]). The dev server also respects the `PHP_CLI_SERVER_WORKERS` environment variable on Linux (PHP 7.4+) to fork N concurrent workers, but it is still single-threaded per worker and not safe for production.

The failure mode here is the "502 Bad Gateway" incident. nginx returns 502 when it cannot reach the PHP-FPM socket — either FPM is not running, the socket path is wrong, or all workers are busy. The diagnosis is `systemctl status php8.3-fpm` (is it running?), `ls -l /run/php/php8.3-fpm.sock` (does the socket exist with the right permissions?), and `ss -lnt | grep 9000` (if using TCP instead of Unix socket, is anything listening on port 9000?). The fix depends on which failed: restart FPM, fix the socket path in nginx's `fastcgi_pass`, or raise `pm.max_children` if workers are exhausted. The 504 Gateway Timeout is the related failure — FPM is reachable but the request takes longer than `max_execution_time` to complete, and FPM kills the worker, leaving nginx waiting.

## Cross-Runtime Comparison

| Aspect | JVM (HotSpot) | Node.js (V8) | CPython | PHP (Zend) |
|---|---|---|---|---|
| Threading | OS threads (1:1) | Single thread + libuv pool | OS threads + GIL | Processes (shared-nothing) |
| Memory | GC (G1/ZGC) | GC (Scavenger + Mark-Sweep) | Ref counting + cyclic GC | Per-request cleanup |
| Concurrency model | Multi-threaded | Event loop (epoll) | GIL serializes bytecode | Process-per-request via FPM |
| Cold start | Slow (~2s) | Fast (~50ms) | Medium (~200ms) | Fast (~10ms) |
| State sharing | In-process singletons | In-process singletons | In-process singletons | None between requests (must use Redis/memcached) |
| Long-lived connections | Native (Tomcat pool) | Native (EventEmitter) | Native (asyncio) | Possible in Swoole/RoadRunner; not in vanilla FPM |
| Best for | CPU-bound, enterprise | I/O-bound, real-time | Scripts, ML, data | Web apps, request-response |

The PHP "shared-nothing" model is the most consequential difference. Every HTTP request gets a fresh PHP-FPM worker (or a reused worker with reset global state); there are no in-process caches, no in-process connection pools, no in-process singletons. The advantage is isolation — a memory leak in one request cannot affect the next request. The disadvantage is that everything cross-request (sessions, caches, locks, connection pools) must live in an external service (Redis, memcached, the database). This is why Laravel ships with Redis as the default cache/session/queue driver and why PHP applications have historically been easier to scale horizontally than JVM applications (no JMX, no in-process state to drain before scaling down).

The other consequence of shared-nothing is that PHP applications do not have long-lived processes. A Spring Boot app starts once and runs for weeks; a PHP-FPM worker starts, handles ~1000 requests, and is restarted. Long-running tasks (queues, websockets, cron jobs) require a separate process manager — Laravel Horizon for queues, Laravel Reverb or Swoole for websockets, systemd timers for cron. This is the architectural price PHP pays for its per-request simplicity.
