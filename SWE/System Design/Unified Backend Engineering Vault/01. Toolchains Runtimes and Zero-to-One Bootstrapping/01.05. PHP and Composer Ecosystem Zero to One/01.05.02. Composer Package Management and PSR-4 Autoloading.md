# 01.05.02. Composer Package Management and PSR-4 Autoloading

## What This Is

Composer is the de facto package manager for PHP, occupying the same niche in the PHP ecosystem as npm in Node, pip in Python, Maven in Java, and Bundler in Ruby. It reads a `composer.json` manifest declaring dependencies (with semver ranges), resolves the transitive dependency graph into exact versions, writes the resolution to `composer.lock`, downloads the packages from Packagist (the default package repository), and generates an autoloader (`vendor/autoload.php`) that lets your code `use` any class from any installed package without manual `require` statements. The autoloader follows PSR-4, the PHP Standards Recommendation that maps namespace prefixes to directory paths — `"Acme\\": "src/"` means the class `Acme\Foo\Bar` is loaded from `src/Foo/Bar.php`. This note walks the install, the manifest-vs-lockfile split, the PSR-4 algorithm, the optimized autoloader, and the `declare(strict_types=1)` modern PHP idiom. Every Laravel and Symfony application depends on Composer at every stage of its lifecycle.

The note sits at the same conceptual layer as [[01.01.02. Package Managers and Dependency Resolution Algorithms]] (which covers the general algorithm) — this note is the PHP-specific instantiation. The failure modes it governs are the ones that surface as `Class 'App\Foo\Bar' not found` (autoloader misconfiguration), `composer install` running for 5 minutes in CI (no optimized autoloader), and the classic "lockfile out of sync with manifest" CI failure.

## The Details

### Installing Composer globally and understanding `composer.json` vs. `composer.lock`

Composer is distributed as a single `composer.phar` file — a PHP archive (a zip with a PHP stub) that contains the entire Composer executable. Install it once globally and you can run `composer` from anywhere:

```bash
# download the installer and verify its signature
curl -sS https://getcomposer.org/installer | php

# this produces composer.phar in the current directory
# verify
php composer.phar --version
# Composer version 2.7.9 2024-09-04 14:25:18

# move it to a global location and rename
sudo mv composer.phar /usr/local/bin/composer
chmod +x /usr/local/bin/composer

# now `composer` works from any directory
composer --version
```

```bash
# Windows: download Composer-Setup.exe from https://getcomposer.org/download/
# it adds composer to PATH automatically

# or via Scoop:
scoop install composer
```

Once installed, the workflow for a new project is:

```bash
mkdir myapp && cd myapp

# generate a composer.json interactively
composer init
# (it asks for package name, description, author, license, dependencies)

# or generate a minimal one
composer init --name="myorg/myapp" --author="Alice <alice@example.com>" \
              --type=project --license=MIT --no-interaction

# add a dependency
composer require monolog/monolog

# this does three things:
#   1. adds "monolog/monolog": "^3.5" to composer.json's "require"
#   2. resolves the dependency graph and writes composer.lock
#   3. downloads monolog-3.5.0 (and its deps) into vendor/

# install everything from the lockfile (CI pattern)
composer install --no-dev --optimize-autoloader

# update one dependency to the latest matching version
composer update monolog/monolog

# update everything (rare — use with care)
composer update
```

The `composer.json` manifest declares what your project needs (with ranges); the `composer.lock` lockfile records what was resolved (with exact versions + integrity hashes). The two-file split is identical to npm's `package.json` / `package-lock.json`:

```json
// composer.json (manifest, human-authored)
{
    "name": "myorg/myapp",
    "description": "A bare-metal PHP app",
    "type": "project",
    "license": "MIT",
    "require": {
        "php": ">=8.2",
        "monolog/monolog": "^3.5",
        "vlucas/phpdotenv": "^5.6"
    },
    "require-dev": {
        "phpunit/phpunit": "^11.0",
        "squizlabs/php_codesniffer": "^3.10"
    },
    "autoload": {
        "psr-4": {
            "MyOrg\\MyApp\\": "src/"
        }
    },
    "autoload-dev": {
        "psr-4": {
            "MyOrg\\MyApp\\Tests\\": "tests/"
        }
    },
    "scripts": {
        "test": "phpunit",
        "lint": "phpcs src/"
    }
}
```

```json
// composer.lock (lockfile, machine-authored, committed to git)
{
    "_readme": ["This file locks the dependencies of your project to a known state"],
    "content-hash": "a1b2c3d4e5f6...",
    "packages": [
        {
            "name": "monolog/monolog",
            "version": "3.5.0",
            "source": {
                "type": "git",
                "url": "https://github.com/Seldaek/monolog.git",
                "reference": "c1b62f029..."
            },
            "dist": {
                "type": "zip",
                "url": "https://api.github.com/repos/Seldaek/monolog/zipball/c1b62f029",
                "reference": "c1b62f029...",
                "shasum": ""
            },
            "require": {
                "php": ">=8.1",
                "psr/log": "^2.0|^3.0"
            },
            "type": "library",
            "autoload": {
                "psr-4": {"Monolog\\": "src/Monolog"}
            },
            "license": ["MIT"],
            "authors": [{"name": "Jordi Boggiano"}],
            "description": "Sends your logs to files, sockets, inboxes, databases..."
        }
        // ... 20 more packages (every transitive dep with exact version)
    ],
    "packages-dev": [
        // dev-only packages (phpunit, phpcs)
    ],
    "aliases": [],
    "minimum-stability": "stable",
    "stability-flags": [],
    "prefer-stable": true,
    "prefer-lowest": false
}
```

The `content-hash` field is computed from the entire `composer.json` content (not just the dependencies) — if any field changes, the hash changes, and `composer install` warns that the lockfile is out of sync. This catches the case where you added a new dependency to `composer.json` but forgot to run `composer update` to refresh the lockfile. In CI, run `composer install --no-dev --optimize-autoloader` (or `composer install --no-ansi --no-interaction --no-progress --no-scripts --optimize-autoloader`) — if the lockfile is out of sync, the install fails with `The lock file is not up to date with the latest changes in composer.json`.

The version constraints in the `require` block use Composer's own semver dialect, which is a strict superset of the npm semver range syntax (and a near-match for Bundler's pessimistic `~>` operator). Every constraint resolves to a *range* of acceptable versions; Composer picks the highest version inside that range that satisfies all transitive constraints. The four operators that show up in every real `composer.json`:

```text
  Constraint     Meaning                                         Range accepted
  ─────────────   ─────────────────────────────────────────────    ─────────────────────────────
  "^3.5"         caret: compatible with 3.5                     >=3.5.0  < 4.0.0
                  (allows minor + patch, locks major)             (3.5.0, 3.5.1, 3.6.0, 3.9.9…  but NOT 4.0.0)
  "~3.5"         tilde: allows patch, locks minor               >=3.5.0  < 3.6.0
                  (allows patch releases only)                     (3.5.0, 3.5.1, 3.5.2…  but NOT 3.6.0)
  "3.*"          wildcard: any 3.x                                >=3.0.0  < 4.0.0
                                                                   (equivalent to ^3.0 in practice, but explicit)
  "dev-main"     branch alias: track the main branch             whatever HEAD of 'main' is right now
                  ( Composer clones the git ref at install time)
  "^3.5|^4.0"   union: any version matching either side          >=3.5.0 <5.0.0 (excluding 4.0.0-beta if min-stability=stable)
  ">=3.0 <5.0"  range: any version in the explicit range         >=3.0.0  < 5.0.0
  "3.5.0"       exact: only this version                          3.5.0 (no patches, no minors)
  "v3.5.0"       same as 3.5.0 — the 'v' prefix is stripped        3.5.0
```

The `^` (caret) operator is the right default for libraries and applications: it follows SemVer's promise that minor and patch releases are backward-compatible, so `^3.5` lets Composer pull in 3.5.1 (bugfix) and 3.6.0 (new feature) automatically when you run `composer update`, but refuses to cross the 4.0 boundary where breaking changes are allowed. The `~` (tilde) operator is more conservative — it allows only patches, locking the minor version. Use `~` when a library has a history of breaking changes in minor releases (a violation of SemVer, but common in PHP-land). The `dev-*` constraint tracks a branch and should almost never appear in `require` — it makes builds non-reproducible (the branch HEAD moves) and bypasses the version-stability guarantee. Use it in `require-dev` for forks you are testing, and pin to a tagged release for production. The `minimum-stability` setting (default `stable`) further filters: if you only want stable releases, you must explicitly allow `dev`, `alpha`, `beta`, `RC` either per-package (`"monolog/monolog": "3.5.0-beta1@beta"`) or globally (`"minimum-stability": "beta"`).

The `--no-dev` flag skips the `require-dev` packages (PHPUnit, PHPCS, etc.) — production deployments should never install dev dependencies because they bloat the deploy artifact and may include code that should not be on production (e.g. test fixtures, debugging tools). The `--optimize-autoloader` flag (covered in the next H3) generates a performance-optimized autoloader.

The failure mode here is "lockfile out of sync" in CI. The symptom is `Your lock file does not contain a compatible set of packages for your PHP version (8.3)` or `The lock file is not up to date with the latest changes in composer.json`. The fix is to run `composer update` locally (which updates the lockfile), commit the updated lockfile, and let CI run `composer install`. Never run `composer update` in CI — it produces non-deterministic builds (the resolved versions depend on what Packagist returns at install time). The subtler failure mode is a caret constraint quietly crossing a minor version that introduces a regression: `^3.5` accepts 3.6.0 the moment it is tagged on Packagist, so a passing build on Monday breaks on Tuesday even though no `composer.json` change was committed. The defence is to commit `composer.lock` (which pins the exact resolved versions) and only re-resolve deliberately via `composer update <package>`.

### PSR-4 (PHP Standards Recommendation 4): Namespaces to directory path mappings

PHP namespaces (`namespace Acme\Foo;`) were added in PHP 5.3 (2009). Before namespaces, every class lived in the global namespace, and the only way to avoid name collisions was to prefix class names (`Zend_Db_Adapter_Pdo_Mysql`, `PEAR_HTTP_Request2`). Namespaces solved the collision problem; PSR-4 (2014) solved the autoloading problem by defining a deterministic mapping from a fully-qualified class name to a file path.

The PSR-4 rule is: given a namespace prefix `Acme\` mapped to the directory `src/`, the class `Acme\Foo\Bar` is loaded from the file `src/Foo/Bar.php`. The namespace prefix is stripped, the remaining namespace segments become directory names, and the class name becomes the filename with `.php` appended.

```text
  composer.json:
    "autoload": {
        "psr-4": {
            "MyOrg\\MyApp\\": "src/"
        }
    }

  Class name resolution:
  ──────────────────────────────────────────────────────
  use MyOrg\MyApp\Foo\Bar;
  new Bar();                    ← triggers autoload

  1. PHP calls the registered autoloader (vendor/autoload.php)
  2. Autoloader looks up the class in the PSR-4 map:
     "MyOrg\MyApp\" → "src/"
  3. Strip the prefix: "Foo\Bar"
  4. Replace \ with / and append .php: "src/Foo/Bar.php"
  5. require "src/Foo/Bar.php"

  Project layout:
  myapp/
  ├── composer.json
  ├── src/
  │   ├── Foo/
  │   │   ├── Bar.php          ← contains class MyOrg\MyApp\Foo\Bar
  │   │   └── Baz.php          ← contains class MyOrg\MyApp\Foo\Baz
  │   └── Controllers/
  │       └── UserController.php  ← contains class MyOrg\MyApp\Controllers\UserController
  └── vendor/
      └── autoload.php         ← the generated autoloader
```

The PSR-4 rule is strict: the class name must match the file name (case-sensitive on Linux, case-insensitive on macOS/Windows by default — this is a frequent portability bug), the namespace segments must match the directory names, and the file must be at exactly the computed path. A class `MyOrg\MyApp\Foo\Bar` placed in `src/Foo/Barr.php` will not be found — the autoloader looks for `src/Foo/Bar.php` and gets a "file not found" error.

The `autoload` section can declare multiple prefixes:

```json
{
    "autoload": {
        "psr-4": {
            "MyOrg\\MyApp\\": "src/",
            "MyOrg\\MyApp\\Tests\\": "tests/",
            "MyOrg\\Legacy\\": "legacy/lib/"
        },
        "files": [
            "src/helpers.php"
        ],
        "classmap": [
            "src/Classes/",
            "app/LegacyClasses.php"
        ]
    }
}
```

- **`psr-4`**: the modern standard. Maps namespace prefixes to directories. Used by every new project.
- **`files`**: a list of files that are always `require`-d on autoloader load. Used for files that define functions (not classes) — PHP has no way to autoload functions, so they must be explicitly loaded. Common examples: `vlucas/phpdotenv`'s `env()` helper, `laravel/helpers`'s `Str::random()`-style functions.
- **`classmap`**: a list of directories or files to scan for classes. The autoloader builds a map of "class name → file path" by scanning every `.php` file in those directories. Used for legacy code that does not follow PSR-4 (e.g. PEAR-style `Foo_Bar_Baz` class names, or classes with no namespace).

After editing `autoload`, run `composer dump-autoload` to regenerate the autoloader. The autoloader is a PHP file at `vendor/autoload.php` that Composer generates; it knows the PSR-4 mappings, the file list, and the classmap. PHP's `spl_autoload_register` is called once at the start of your application (`require __DIR__ . '/vendor/autoload.php';`) to register the autoloader as the class loader; thereafter, every `new SomeClass()` call goes through the autoloader.

The failure mode this exposes is the "class not found" error. The symptom is `Error: Class "App\Services\PaymentGateway" not found`. The cause is almost always one of: (1) the namespace in the PHP file does not match the directory structure (`namespace App\Services;` in `app/Services/PaymentGateway.php` is correct, but `namespace App\Service;` (singular) is wrong); (2) the class name does not match the file name (`class PaymentService` in `PaymentGateway.php`); (3) the `autoload` mapping in `composer.json` is wrong (`"App\\": "app/"` vs `"App\\": "src/"`); (4) you added a new class but did not run `composer dump-autoload`. The fix is to verify the namespace, the file path, the autoload mapping, and to regenerate the autoloader.

The case-sensitivity bug is the most insidious version. On macOS (default APFS) and Windows (NTFS), file names are case-insensitive — `app/Services/PaymentGateway.php` and `app/services/paymentgateway.php` are the same file. On Linux (ext4), they are different files. A developer on macOS writes `namespace App\Services;` and `class PaymentGateway` — works locally. Deployed to a Linux server, the autoloader looks for `app/Services/PaymentGateway.php` but the file is `app/services/PaymentGateway.php` (lowercase `s`) — file not found. The fix is to use `composer dump-autoload --strict-psr` (PHP 8.3+) which warns about case mismatches, and to enforce case consistency via CI on a Linux runner.

### Generating the optimized class autoloader via `composer dump-autoload -o`

The default autoloader that Composer generates is a "classmap-authoritative: false" loader. When a class is referenced, the autoloader does PSR-4 path computation (`MyOrg\Foo\Bar → src/Foo/Bar.php`) and calls `file_exists()` to check if the file exists. If it does, `require` it. This works but has overhead: every class load does a filesystem stat call.

The optimized autoloader (`composer dump-autoload --optimize`, or `-o`) precomputes a classmap — a giant associative array of every class name to its file path — at dump time, by scanning every `.php` file in the project's `autoload` directories. At runtime, the autoloader does an array lookup instead of a filesystem stat:

```php
// vendor/composer/autoload_classmap.php (generated by `composer dump-autoload -o`)
return array(
    'MyOrg\\MyApp\\Controllers\\UserController' => __DIR__ . '/../..' . '/src/Controllers/UserController.php',
    'MyOrg\\MyApp\\Foo\\Bar' => __DIR__ . '/../..' . '/src/Foo/Bar.php',
    'MyOrg\\MyApp\\Foo\\Baz' => __DIR__ . '/../..' . '/src/Foo/Baz.php',
    'Monolog\\Logger' => __DIR__ . '/..' . '/monolog/monolog/src/Monolog/Logger.php',
    // ... 5000 more entries for a typical Laravel app
);
```

The performance difference is real. For a Laravel app with ~5000 classes, the default autoloader does ~5000 `file_exists()` calls during the first request (one per class loaded); the optimized autoloader does zero. The first-request latency drops from ~200 ms to ~50 ms. In production, every request pays this cost (because PHP-FPM workers are stateless — there is no cross-request autoloader cache), so the optimization compounds. Always run `composer dump-autoload -o` as part of the production build.

```bash
# dev: use the default autoloader (PSR-4 lookup, fast iteration)
composer install

# production: use the optimized autoloader (classmap lookup, fast runtime)
composer install --no-dev --optimize-autoloader

# or, if the dependencies are already installed, just regenerate the autoloader:
composer dump-autoload --optimize --no-dev

# for absolute maximum performance, use classmap-authoritative mode:
composer dump-autoload --optimize --classmap-authoritative
# this makes the autoloader ONLY use the classmap; if a class is not in the map,
# it returns false instead of falling back to PSR-4 lookup.
# Use this when you are confident every class is in the map (no dynamically-named classes).
```

The `--apcu-autoloader` flag (PHP 7.0+) adds an APCu cache layer on top. The classmap is stored in APCu (shared memory) on first load; subsequent PHP-FPM workers in the same process pool read from APCu instead of recomputing. This is the closest PHP gets to cross-request autoloader caching:

```bash
composer dump-autoload --optimize --apcu-autoloader
```

The failure mode here is "first request in production is slow". A user hits the site, the PHP-FPM worker handles the request, the autoloader does ~5000 `file_exists()` calls, the request takes 200 ms; the second request (same worker, autoloader already ran for those classes) takes 50 ms. The user perceives the site as slow on first hit. The fix is `--optimize-autoloader` in the build script, which makes every request fast.

The other failure mode is "production cannot find a class that works in dev". This happens when `--classmap-authoritative` is enabled and a class is loaded via a dynamic name (`$class = "App\\Services\\$serviceType"; new $class();`) — the classmap was generated at build time and does not know about every possible dynamic name. The fix is to drop `--classmap-authoritative` (use plain `--optimize` instead, which falls back to PSR-4 if the class is not in the map), or to ensure every dynamically-loaded class is enumerated in the classmap via the `classmap` section of `composer.json`.

### Writing and executing a vanilla Object-Oriented PHP script with strict types enabled (`declare(strict_types=1);`)

PHP 7.0 (2015) added scalar type declarations and return type declarations to function signatures. PHP 7.1 added `declare(strict_types=1)`, which makes the type checks coercive vs. strict. Without it, PHP silently coerces — `function add(int $a, int $b): int { return $a + $b; } add("5", "10")` returns `15` (the strings are coerced to ints). With it, the same call throws `TypeError: Argument 1 passed to add() must be of the type int, string given`.

```php
<?php
// src/Greeter.php
declare(strict_types=1);

namespace MyOrg\MyApp;

class Greeter
{
    public function __construct(
        private readonly string $greeting = "Hello"
    ) {}

    public function greet(string $name): string
    {
        return "{$this->greeting}, {$name}!";
    }
}
```

The `declare(strict_types=1)` directive must be the first statement in the file (after the `<?php` opening tag), and it applies only to the file in which it appears — not to included files, not to the calling file. This is per-file strict mode (a design decision to avoid breaking backward compatibility with libraries that rely on coercion).

```php
<?php
// greet.php
declare(strict_types=1);

require __DIR__ . '/vendor/autoload.php';

use MyOrg\MyApp\Greeter;

$greeter = new Greeter(greeting: "Bonjour");
echo $greeter->greet(name: "Alice") . PHP_EOL;
// Bonjour, Alice!

// These throw TypeError under strict_types=1:
// $greeter->greet(42);                  // int instead of string
// $greeter->greet(["Alice"]);            // array instead of string
// new Greeter(greeting: 123);            // int instead of string
```

The PHP 8.0+ features used here:

- **Constructor property promotion** (`private readonly string $greeting = "Hello"` in the constructor signature) — declares the property, assigns the parameter, and sets visibility in one line. PHP 8.0+.
- **`readonly` properties** — cannot be reassigned after construction. PHP 8.1+.
- **Named arguments** (`greeting: "Bonjour"`, `name: "Alice"`) — pass arguments by parameter name instead of position. PHP 8.0+.
- **Null-safe operator** (`?->`) — short-circuits method chains on null. PHP 8.0+.
- **Match expression** — `match($x) { 1 => "one", 2 => "two", default => "other" }`. PHP 8.0+.
- **Readonly classes** (`readonly class Foo {}`) — all properties are readonly. PHP 8.2+.
- **`enum`** (backed enums) — `enum Status: string { case Active = 'active'; case Inactive = 'inactive'; }`. PHP 8.1+.

Run the script:

```bash
$ php greet.php
Bonjour, Alice!
```

The failure mode that strict types prevents is the silent-coercion bug. A function that takes `int $userId` is called with `string $userId` (because it came from `$_GET['id']`, which is always a string in PHP). Without strict types, PHP coerces `"42"` to `42` and the function works — most of the time. The coercion fails on `"42abc"` (PHP 8.0+ throws a `TypeError`; PHP 7.x coerced to `42` with a deprecation warning). Strict types make the failure immediate and explicit, which is what you want in production.

The other failure mode is the "wrong type from database" bug. PDO returns database columns as strings by default — `SELECT id FROM users` returns `"42"` (string), not `42` (int), even if the column is an integer. Without strict types, `$user->setId($pdoResult['id'])` silently works (string→int coercion); with strict types, it throws `TypeError`. The fix is `PDO::ATTR_EMULATE_PREPARES => false` (which makes PDO use the database's native types) or to cast explicitly (`(int) $pdoResult['id']`).

## Key Takeaways

1. **Composer is the PHP package manager; `composer.json` is the manifest, `composer.lock` is the lockfile.** Commit the lockfile, run `composer install` (not `update`) in CI, use `--no-dev --optimize-autoloader` for production builds.
2. **PSR-4 maps namespace prefixes to directories: `"Acme\\": "src/"` means `Acme\Foo\Bar` is loaded from `src/Foo/Bar.php`.** Class name must match file name (case-sensitive on Linux). Run `composer dump-autoload` after adding new classes or editing the `autoload` section.
3. **`declare(strict_types=1)` makes PHP's type checks strict instead of coercive — put it as the first line of every file.** Use PHP 8+ features (constructor promotion, readonly, named arguments, enums, match) — they catch bugs at the type-check layer that would otherwise surface at runtime.
