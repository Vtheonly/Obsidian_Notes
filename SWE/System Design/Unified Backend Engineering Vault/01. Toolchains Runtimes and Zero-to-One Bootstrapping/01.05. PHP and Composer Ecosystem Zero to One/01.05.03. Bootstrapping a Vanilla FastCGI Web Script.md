# 01.05.03. Bootstrapping a Vanilla FastCGI Web Script

## What This Is

Before Laravel, before Symfony, before any framework — PHP was a templating language that ran inside a web server. You wrote `index.php`, the web server invoked the PHP interpreter, the interpreter populated superglobals (`$_GET`, `$_POST`, `$_SERVER`, `$_FILES`), your script ran, and any output (HTML, JSON, headers) was sent back to the client. This note bootstraps a vanilla PHP web script using the built-in PHP development server (`php -S localhost:8000`), explains the superglobal model, and writes a front-controller `index.php` that parses `REQUEST_URI` and emits JSON. The result is a 50-line PHP application that handles HTTP without any framework — the same minimum viable service as the Spring Boot, Express, Flask, and Django anchors, expressed in the most bare-metal form possible. The point is not that you should build production apps this way — you should use Laravel (next note) — but that Laravel is a wrapper around these primitives. When Laravel's router fails, you fall back to understanding `REQUEST_URI` and `$_SERVER`.

The note is the PHP equivalent of [[01.02.02. Compiling and Running Vanilla Java from the Terminal]] (which showed bare `javac`/`java`) and [[01.04.02. Python Execution Model and Module System]] (which showed a bare `python hello.py`). The failure modes it governs are the ones that surface as "headers already sent by output started at..." (output buffering), "Undefined index: id" (superglobal access without checking), and "the router does not match my pretty URL" (front-controller misconfiguration).

## The Details

### Running the built-in PHP development web server (`php -S localhost:8000`)

PHP ships with a single-threaded, single-process development web server — the equivalent of Flask's Werkzeug dev server, Django's `runserver`, or Express's `app.listen`. It is invoked with `php -S`:

```bash
# serve the current directory on port 8000
php -S localhost:8000

# serve a specific document root
php -S localhost:8000 -t public/

# serve with a router script (front-controller pattern)
php -S localhost:8000 -t public/ public/index.php

# bind to all interfaces (for testing from another machine)
php -S 0.0.0.0:8000 -t public/

# PHP 7.4+ supports a default router via .htaccess-like fallback:
# if no router is specified, PHP serves static files (.html, .css, .js, .png)
# directly, and returns 404 for missing files.
```

The router script is the key to using the dev server for an application (rather than just static files). When a router is specified, PHP invokes it for every request — the router decides whether to serve a static file or to handle the request as an application request:

```php
<?php
// public/index.php (router script)

// serve existing static files as-is
$requestedFile = __DIR__ . $_SERVER['REQUEST_URI'];
if (preg_match('/\.(css|js|png|jpg|svg|ico)$/', $_SERVER['REQUEST_URI']) && file_exists($requestedFile)) {
    return false;  // tell PHP's dev server to serve the file as a static asset
}

// otherwise, handle as an application request
require __DIR__ . '/../app/bootstrap.php';
```

The `return false;` from the router script is the magic incantation — it tells PHP's dev server "I declined to handle this; please serve the file from the document root as a static asset". Returning anything else (or `return true;`, or echoing output) means "I handled this request; the output I echoed is the response".

The dev server is for development only — it is single-threaded, has no keepalive, no HTTP/2, no TLS, no graceful shutdown, and leaks memory on long-running requests. Production PHP runs behind a real web server: nginx + PHP-FPM (the most common), Apache + mod_php (legacy), or FrankenPHP/Caddy (modern, Go-based).

```text
  Development:                  Production:

  ┌──────────────────┐          ┌──────────────────┐
  │  php -S :8000    │          │     nginx        │
  │  (single process,│          │  (web server)    │
  │   single thread) │          └────────┬─────────┘
  └────────▲─────────┘                   │ FastCGI protocol
           │ HTTP                        │ over TCP/Unix socket
           │                             ▼
       ┌───┴────┐              ┌──────────────────┐
       │ curl   │              │    php-fpm       │
       │        │              │  (pool of worker │
       └────────┘              │   processes)     │
                               └────────▲─────────┘
                                        │ exec php
                                        ▼
                                ┌──────────────────┐
                                │  public/index.php │
                                └──────────────────┘
```

The failure mode that distinguishes dev from prod is the "router script behavior differs from FPM". The `return false;` magic only works with `php -S` — under PHP-FPM, every request goes through `index.php` (because nginx's `try_files $uri /index.php?$query_string;` rule always falls back to `index.php`). A router script that worked in dev fails in prod if it relied on `return false;` semantics. The fix is to test under PHP-FPM (or under nginx + PHP-FPM in Docker) before deploying.

### Understanding PHP Superglobals: `_SERVER`, `_GET`, `_POST`, `_COOKIE`, and `$_FILES`

PHP populates five "superglobals" — associative arrays available in every scope, automatically populated by the SAPI before the script runs. They are the PHP equivalent of Node's `req.query`/`req.body`/`req.headers`, but exposed as plain arrays with no encapsulation. Every PHP web application reads these arrays directly.

```php
<?php
// print all superglobals (for debugging)
var_dump($_GET, $_POST, $_SERVER, $_COOKIE, $_FILES);
```

| Superglobal | Contains | Example |
|---|---|---|
| `$_GET` | URL query string parameters (parsed) | `?id=42&name=Alice` → `["id" => "42", "name" => "Alice"]` |
| `$_POST` | POST body parameters (from `application/x-www-form-urlencoded` or `multipart/form-data`) | `<input name="email">` → `["email" => "alice@example.com"]` |
| `$_SERVER` | Server and request metadata (CGI variables + PHP-specific keys) | `["REQUEST_METHOD" => "POST", "REQUEST_URI" => "/api/users", "HTTP_HOST" => "localhost"]` |
| `$_COOKIE` | Cookies (parsed from `Cookie:` header) | `Cookie: session=abc123` → `["session" => "abc123"]` |
| `$_FILES` | Uploaded files (from `multipart/form-data`) | `<input type="file" name="avatar">` → `["avatar" => ["tmp_name" => "/tmp/phpXXXX", "name" => "photo.jpg", "size" => 12345, ...]]` |
| `$_REQUEST` | Merged `$_GET` + `$_POST` + `$_COOKIE` (in `request_order` ini order) | Avoid — security risk because of name collisions |

The `$_SERVER` superglobal is the most important one for routing — it contains everything you need to dispatch a request:

```php
<?php
// common $_SERVER keys for routing:
echo $_SERVER['REQUEST_METHOD'];   // "GET", "POST", "PUT", "DELETE", "PATCH"
echo $_SERVER['REQUEST_URI'];      // "/api/users/42?include=posts" (full path + query)
echo $_SERVER['PATH_INFO'];        // "/api/users/42" (path only, no query) — only with router
echo $_SERVER['QUERY_STRING'];     // "include=posts"
echo $_SERVER['HTTP_HOST'];        // "example.com"
echo $_SERVER['HTTP_USER_AGENT'];  // browser UA
echo $_SERVER['HTTP_AUTHORIZATION']; // Authorization header (if present)
echo $_SERVER['REMOTE_ADDR'];      // client IP (or proxy IP if behind proxy)
echo $_SERVER['HTTPS'];            // "on" if HTTPS, undefined otherwise
echo $_SERVER['SERVER_PORT'];      // 80, 443, 8000, etc.
```

Every `HTTP_*` key in `$_SERVER` is a request header, uppercased with hyphens replaced by underscores and prefixed with `HTTP_`. So `Content-Type: application/json` becomes `$_SERVER['HTTP_CONTENT_TYPE']`. The headers without the `HTTP_` prefix (`Content-Length`, `Content-Type`, `Authorization` in some SAPIs) are special-cased by the CGI spec — but PHP normalizes most of them, so always use the `HTTP_` form for portability.

The critical rule for accessing superglobals is **never trust user input**. Every value in `$_GET`, `$_POST`, `$_COOKIE`, and `$_SERVER['HTTP_*']` is attacker-controlled. A client can send any header, any query parameter, any cookie value. Always validate:

```php
<?php
// bad — undefined index warning if 'id' is missing, no type check
$id = $_GET['id'];
getUser($id);

// better — check existence and validate type
if (!isset($_GET['id']) || !ctype_digit($_GET['id'])) {
    http_response_code(400);
    echo json_encode(['error' => 'id must be a positive integer']);
    exit;
}
$id = (int) $_GET['id'];
getUser($id);
```

`ctype_digit($s)` returns true only if `$s` is a non-empty string of digits (`"42"` → true, `"42a"` → false, `"-1"` → false, `""` → false). It is the strict way to validate an integer-like string. The cast `(int) "42abc"` returns `42` silently — PHP's coercion — which is why strict validation matters.

`$_FILES` is the most complex superglobal because file uploads involve temporary files that PHP cleans up after the script ends. The structure is:

```php
$_FILES['avatar'] = [
    'name' => 'photo.jpg',           // original filename from client (untrusted!)
    'tmp_name' => '/tmp/phpXXXXXX',   // server-side temp path (where the bytes are)
    'size' => 12345,                  // size in bytes
    'type' => 'image/jpeg',           // MIME type from client (UNTRUSTED!)
    'error' => UPLOAD_ERR_OK,         // 0 = OK, see UPLOAD_ERR_* constants
];

// validate the upload
if ($_FILES['avatar']['error'] !== UPLOAD_ERR_OK) {
    throw new RuntimeException("Upload failed: " . $_FILES['avatar']['error']);
}

// validate the actual MIME type (do NOT trust $_FILES['avatar']['type'])
$finfo = new finfo(FILEINFO_MIME_TYPE);
$actualMime = $finfo->file($_FILES['avatar']['tmp_name']);
if (!in_array($actualMime, ['image/jpeg', 'image/png', 'image/webp'], true)) {
    throw new RuntimeException("Unsupported file type: $actualMime");
}

// move to permanent location (if not moved, PHP deletes the temp file at script end)
move_uploaded_file($_FILES['avatar']['tmp_name'], '/var/uploads/' . uniqid('avatar_', true) . '.jpg');
```

The `$_FILES['avatar']['type']` field is the `Content-Type` header the client sent with the upload — completely attacker-controlled and routinely spoofed. Always re-validate the MIME type with `finfo` (which reads the file's magic bytes) before trusting it. The `move_uploaded_file()` function is the only safe way to move an uploaded file — it checks that the source path is actually an uploaded file (defending against path traversal attacks where an attacker passes a server-side path as `tmp_name`).

`$_SESSION` is the odd one out among the superglobals because it is not populated by the SAPI from request data — it is populated by PHP itself from server-side storage after you call `session_start()`. The other superglobals (`$_GET`, `$_POST`, `$_SERVER`, `$_COOKIE`, `$_FILES`) represent request data that came in over the wire; `$_SESSION` represents state that lives on the server between requests. The lifecycle is:

```php
<?php
// login.php — start the session and stash the user ID
session_start();                       // loads or creates a session
$_SESSION['user_id'] = $user->id;       // mutable in any scope
$_SESSION['login_at']  = time();
header('Location: /dashboard');

// dashboard.php — read it back on the next request
session_start();
if (!isset($_SESSION['user_id'])) {
    header('Location: /login');
    exit;
}
$userId = $_SESSION['user_id'];

// logout.php — destroy it
session_start();
$_SESSION = [];                          // empty the array
session_destroy();                       // delete the file on disk
```

Behind the scenes, `session_start()` does four things: (1) reads the `PHPSESSID` cookie from the request (or generates a new 26-character session ID if none exists), (2) computes the path `sess_<id>` under `session.save_path` (default `/var/lib/php/sessions/` on Ubuntu, `/tmp/` on macOS), (3) opens that file, reads its contents (a serialized `$_SESSION` array produced by `session_encode()` at the end of the previous request), and unserializes it back into `$_SESSION`, and (4) acquires an exclusive `flock()` on the file so concurrent requests from the same browser serialize rather than race. At request end, PHP serializes the modified `$_SESSION` back to the file and releases the lock. This is the file-based session store that ships with every vanilla PHP install:

```bash
# inspect the session store
$ ls -la /var/lib/php/sessions/
-rw------- 1 www-data www-data  124 Sep 23 12:00 sess_a3f8b9c1d2e4f5a6b7c8d9e0f1a2b3c4
-rw------- 1 www-data www-data   58 Sep 23 12:01 sess_b4e9c0d2e3f4a5b6c7d8e9f0a1b2c3d4

# contents are PHP-serialized — user_id|i:42;login_at|i:1727097600;
$ sudo cat /var/lib/php/sessions/sess_a3f8b9c1d2e4f5a6b7c8d9e0f1a2b3c4
user_id|i:42;login_at|i:1727097600;csrf_token|s:40:"a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0";

# the matching cookie on the client
$ curl -sI http://localhost:8000/login.php | grep Set-Cookie
Set-Cookie: PHPSESSID=a3f8b9c1d2e4f5a6b7c8d9e0f1a2b3c4; path=/; HttpOnly
```

The file-based store works for a single-server deployment but breaks the moment you load-balance across two PHP-FPM servers — server A has the session file, server B does not, the user is logged out on every other request. The fix is to swap the storage backend via `session.save_handler` and `session.save_path` in `php.ini`: `session.save_handler = redis` and `session.save_path = "tcp://redis:6379"` makes Redis the session store, so every PHP-FPM server sees the same session state. Laravel's `session.php` config wraps this same mechanism — `'driver' => env('SESSION_DRIVER', 'database')` maps to one of `file`, `cookie`, `database`, `redis`, `memcached`, `dynamodb`, `array`. This is the canonical reason every Laravel app is deployed with at least one shared cache server (Redis) — without it, horizontal scaling breaks sessions.

The failure mode this exposes is the "session file lock" problem. Because `session_start()` acquires an exclusive `flock()` on the session file, any second concurrent request from the same browser (e.g. an AJAX poll fired while the dashboard is still loading) blocks until the first request calls `session_write_close()` or exits. The symptom is the second request hanging for the full `max_execution_time` (30 seconds), then timing out. The fix is to call `session_write_close()` as early as possible in long-running scripts, or to switch to a session handler that does not lock (Redis with `phpredis` does not lock per-key; the database handler serializes via row-level locks).

The failure mode here is the "undefined index" warning becoming a 500 in production. Accessing `$_GET['id']` when the query string has no `id` parameter emits `Warning: Undefined array key "id"` (PHP 8.0+; was `Notice: Undefined index` in PHP 7.x). In dev, this is a log message; in production with `display_errors = Off` and strict error handlers, this can become a thrown `ErrorException` (if you register an error handler that converts warnings to exceptions — Laravel does this). The fix is `isset()` or the null-coalescing operator `??`:

```php
$id = $_GET['id'] ?? null;
if ($id === null) { /* return 400 */ }
```

### Writing a native front-controller pattern (`index.php`) that parses `REQUEST_URI` and outputs JSON

The front-controller pattern is the universal PHP web architecture: every HTTP request is routed to a single PHP file (`index.php`), which parses the URL, dispatches to the appropriate handler, and returns the response. Laravel, Symfony, and every modern PHP framework use this pattern; the only difference is that the framework provides the router, the controller abstractions, and the response object. The bare-metal version is ~30 lines:

```php
<?php
// public/index.php
declare(strict_types=1);

header('Content-Type: application/json; charset=utf-8');

// parse the request
$method = $_SERVER['REQUEST_METHOD'];
$uri    = parse_url($_SERVER['REQUEST_URI'], PHP_URL_PATH);
$uri    = rtrim($uri, '/');   // normalize trailing slash

// simple in-memory store
$users = [
    ['id' => 1, 'name' => 'Alice', 'email' => 'alice@example.com'],
    ['id' => 2, 'name' => 'Bob',   'email' => 'bob@example.com'],
];

// route table: METHOD + URI pattern => handler
$routes = [
    'GET    /health'      => 'healthHandler',
    'GET    /users'       => 'listUsersHandler',
    'GET    /users/{id}'  => 'getUserHandler',
    'POST   /users'       => 'createUserHandler',
];

// match the route
$matched = false;
foreach ($routes as $pattern => $handler) {
    [$routeMethod, $routePath] = explode('  ', $pattern, 2);

    // convert /users/{id} to a regex: /^\/users\/(?P<id>[^\/]+)$/
    $regex = '#^' . preg_replace('/\{(\w+)\}/', '(?P<$1>[^/]+)', $routePath) . '$#';

    if ($method === $routeMethod && preg_match($regex, $uri, $matches)) {
        $params = array_filter($matches, 'is_string', ARRAY_FILTER_USE_KEY);  // keep named groups only
        $matched = true;
        $response = $handler($params, $users);
        break;
    }
}

if (!$matched) {
    http_response_code(404);
    echo json_encode(['error' => 'not found', 'path' => $uri]);
    exit;
}

http_response_code($response['status'] ?? 200);
echo json_encode($response['body'], JSON_UNESCAPED_SLASHES | JSON_UNESCAPED_UNICODE);

// ─── Handlers ────────────────────────────────────────────────

function healthHandler(array $params, array $users): array
{
    return ['body' => [
        'status' => 'ok',
        'timestamp' => date('c'),
        'version' => '1.0.0',
    ]];
}

function listUsersHandler(array $params, array $users): array
{
    return ['body' => $users];
}

function getUserHandler(array $params, array $users): array
{
    $id = (int) $params['id'];
    foreach ($users as $user) {
        if ($user['id'] === $id) {
            return ['body' => $user];
        }
    }
    http_response_code(404);
    return ['body' => ['error' => "user $id not found"]];
}

function createUserHandler(array $params, array $users): array
{
    $body = json_decode(file_get_contents('php://input'), true);
    if (!is_array($body) || !isset($body['name'], $body['email'])) {
        return ['status' => 400, 'body' => ['error' => 'name and email are required']];
    }
    $newUser = [
        'id' => count($users) + 1,
        'name' => $body['name'],
        'email' => $body['email'],
    ];
    return ['status' => 201, 'body' => $newUser];
}
```

The key mechanics:

1. **`header('Content-Type: ...')` must be called before any output.** PHP buffers headers and sends them when the first byte of body output is sent (or when the script ends). If you `echo` anything before calling `header()`, you get `Warning: Cannot modify header information - headers already sent by ...`. The fix is `ob_start()` at the top of the script (output buffering) or to never echo before setting headers. Laravel uses output buffering everywhere.
2. **`parse_url($_SERVER['REQUEST_URI'], PHP_URL_PATH)` strips the query string.** `REQUEST_URI` is `/api/users?include=posts`; `parse_url(...PHP_URL_PATH)` returns `/api/users`. Without this, the router would try to match `/api/users?include=posts` against `/api/users` and fail.
3. **`preg_replace('/\{(\w+)\}/', '(?P<$1>[^/]+)', $routePath)` converts path parameters to regex named groups.** `/users/{id}` becomes `/users/(?P<id>[^/]+)`, and a match against `/users/42` produces `["id" => "42"]`. This is the minimum viable router; Laravel's `symfony/routing` does the same thing with more features (optional params, regex constraints, HTTP method matching, scheme matching).
4. **`file_get_contents('php://input')` reads the raw request body.** `php://input` is a stream that gives you the raw POST body, regardless of `Content-Type`. For JSON APIs (where the body is `application/json`, not form-encoded), this is the only way to read it — `$_POST` is empty for JSON bodies. The `json_decode(..., true)` parses it into an associative array; the `true` argument makes it return arrays instead of objects.
5. **`json_encode(..., JSON_UNESCAPED_SLASHES | JSON_UNESCAPED_UNICODE)`** prevents `\/` escaping (so URLs in JSON look like `"http://..."` not `"http:\/\/..."`) and prevents `\uXXXX` escaping of non-ASCII characters (so `"café"` is output as UTF-8, not `"\u00e9"`).

Run it:

```bash
$ php -S localhost:8000 -t public/ public/index.php
PHP 8.3.11 Development Server (http://localhost:8000) started

# in another terminal
$ curl http://localhost:8000/health
{"status":"ok","timestamp":"2024-09-20T14:32:11+00:00","version":"1.0.0"}

$ curl http://localhost:8000/users
[{"id":1,"name":"Alice","email":"alice@example.com"},{"id":2,"name":"Bob","email":"bob@example.com"}]

$ curl http://localhost:8000/users/1
{"id":1,"name":"Alice","email":"alice@example.com"}

$ curl -X POST http://localhost:8000/users \
    -H "Content-Type: application/json" \
    -d '{"name":"Carol","email":"carol@example.com"}'
{"id":3,"name":"Carol","email":"carol@example.com"}

$ curl http://localhost:8000/nonexistent
{"error":"not found","path":"/nonexistent"}
```

The production deployment uses nginx + PHP-FPM instead of the dev server. The nginx config:

```nginx
# /etc/nginx/sites-available/myapp
server {
    listen 80;
    server_name example.com;
    root /var/www/myapp/public;
    index index.php;

    location / {
        try_files $uri $uri/ /index.php?$query_string;
    }

    location ~ \.php$ {
        fastcgi_pass unix:/run/php/php8.3-fpm.sock;
        fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
        include fastcgi_params;
    }

    location ~* \.(css|js|png|jpg|svg|ico)$ {
        expires 30d;
        access_log off;
    }
}
```

The `try_files $uri $uri/ /index.php?$query_string;` directive is the front-controller rule: try to serve the file at `$uri` (for static assets), then try `$uri/` (for directories), then fall back to `/index.php` with the original query string. This is what makes every URL go through `index.php` — and the framework's router inside `index.php` dispatches to the right controller. Every Laravel deployment has this exact nginx config (it ships in the Laravel docs).

The failure mode that the front-controller pattern prevents is the "one PHP file per URL" anti-pattern. Without a front controller, you have `users.php`, `products.php`, `orders.php`, `login.php`, etc. — each with its own copy of the database connection, the session handling, the header/footer HTML, and the error handler. The duplication makes maintenance impossible and security holes inevitable (forgetting to validate input in one file, missing CSRF token in another). The front controller centralizes all of this — one entry point, one bootstrap, one set of middlewares, one router. This is why every modern PHP framework uses the pattern.

The other failure mode is "the router does not match my pretty URL". nginx's `try_files` falls back to `index.php`, but `$_SERVER['REQUEST_URI']` is the *original* URL (`/users/42`), not `/index.php`. The router reads `REQUEST_URI` and matches against `/users/{id}`. If you configure nginx to rewrite instead of try_files (`rewrite ^ /index.php last;`), the `REQUEST_URI` becomes `/index.php` and the router fails. Always use `try_files`, never `rewrite`.

## Cross-Runtime Comparison

| Aspect | JVM (HotSpot) | Node.js (V8) | CPython | PHP (Zend) |
|---|---|---|---|---|
| Threading | OS threads (1:1) | Single thread + libuv pool | OS threads + GIL | Processes (shared-nothing) |
| Memory | GC (G1/ZGC) | GC (Scavenger + Mark-Sweep) | Ref counting + cyclic GC | Per-request cleanup |
| Concurrency model | Multi-threaded | Event loop (epoll) | GIL serializes bytecode | Process-per-request via FPM |
| Cold start | Slow (~2s) | Fast (~50ms) | Medium (~200ms) | Fast (~10ms) |
| State sharing | In-process singletons | In-process singletons | In-process singletons | None between requests (must use Redis/memcached) |
| Request input | `HttpServletRequest` | `req` object | `request` object (Django/Flask) | `$_GET`/`$_POST`/`$_SERVER` superglobals |
| Front-controller | `DispatcherServlet` | Express `app` | Flask `app` / Django URLconf | `index.php` with `try_files` |

The PHP superglobal model is the most different from the other runtimes. Where Node's `req.body` is a parsed object, Django's `request.POST` is a dict-like, and Spring's `@RequestBody` is a typed POJO, PHP's `$_POST` is a raw associative array — no encapsulation, no methods, no validation. The framework (Laravel's `Request` object) wraps this in an object-oriented API, but the underlying array is still there. This is the PHP philosophy: "the framework is a wrapper; the primitives are always accessible."
