# 01.00. Map of Content: Toolchains and Bootstrapping

## Overview

This section covers **01. Toolchains Runtimes and Zero-to-One Bootstrapping**. It is part of the unified backend engineering vault described in [[00.01. Master Architectural Mental Model]]. The notes below are organized by concept, not by framework. Each concept is taught once at the conceptual level, then implemented deeply in the Spring Boot anchor stack, then rapidly translated into Express, Django, Flask, and Laravel as deltas.

Section 01 establishes the lowest layer of the backend stack that you actually touch as an engineer: the language runtime, the compiler or interpreter that executes your source, the package manager that resolves third-party code into a closure, and the build tool that turns source on disk into an artifact you can deploy. Everything in sections 02 through 12 — POSIX, sockets, concurrency, frameworks, persistence, messaging — assumes you can already produce a working process that opens a socket and answers HTTP. That working process is what this section teaches you to assemble from scratch, in five different ecosystems, with the JVM/Node/CPython/Zend runtime differences made explicit.

The section is also the first place where the anchor-and-delta protocol from [[00.02. The Anchor and Delta Learning Protocol]] becomes load-bearing. The Spring Boot toolchain (JDK + Maven/Gradle + Spring Initializr) is the anchor, and the other four ecosystems are deltas that differ in their dependency model, their module syntax, and their server bootstrap idiom but solve the same problem: turn a directory of source files into a long-running process that listens on a port.

## Section Map

### 01.01. Compilers Interpreters and Runtime Virtual Machines

- [[01.01.01. Language Execution Models]] — Distinguishes AOT compilation (Go, Rust, C/C++ via gcc/clang/rustc emitting native ELF/Mach-O/PE), JIT compilation (HotSpot JVM C1→C2 tiered pipeline, V8 Ignition interpreter → TurboFan optimizing compiler, PyPy tracing JIT, .NET RyuJIT), and pure interpretation (bash, awk, early CPython AST walkers). Walks the source → tokens → AST → semantic analysis → IR/bytecode → native code pipeline and explains why the ABI boundary between x86-64 (System V vs Microsoft calling conventions) and ARM64 (AArch64) makes "compile once, run anywhere" harder than it looks.
- [[01.01.02. Package Managers and Dependency Resolution Algorithms]] — Builds the dependency DAG, shows how npm/pnpm/Yarn, pip, Composer, Maven, and Gradle resolve transitive constraints, and explains the diamond problem, peer dependencies, semver range operators (`^`, `~`, `>=`), the npm flat `node_modules` layout vs pnpm's symlinked content-addressable store, the Maven coordinate `groupId:artifactId:version`, Python `venv`/`pipx`/container isolation, PHP PSR-4 namespace-to-path autoloading, and why lockfiles (`package-lock.json`, `poetry.lock`, `composer.lock`) are non-negotiable in CI.

### 01.02. Java and JVM Toolchain Zero to One

- [[01.02.01. Installing JDK and Environment Configuration]] — Installs OpenJDK distributions (Temurin, Corretto, Zulu, Liberica, GraalVM) via SDKMAN on macOS/Linux, via the Adoptium MSI on Windows, and via `apt-get` + `update-alternatives` on Debian/Ubuntu. Wires `JAVA_HOME`, `PATH`, `javac -version`/`java -version` verification, the LTS release timeline (8, 11, 17, 21 with 25 next), and the classpath (`-cp`) and module-path (`-p`) mechanisms introduced by JPMS in Java 9.
- [[01.02.02. Compiling and Running Vanilla Java from the Terminal]] — Writes `HelloWorld.java` with the public-class-matches-filename rule and the `public static void main(String[] args)` signature, compiles multi-file source trees with `javac -d build/ -sourcepath src/` to produce `.class` bytecode, disassembles it with `javap -c -v` to read the constant pool and operand stack, and packages it into an executable `.jar` with a `Main-Class` manifest entry — ending with a side-by-side comparison of plain jars, Maven shade fat jars, and Spring Boot's `BOOT-INF/classes` + `BOOT-INF/lib` layout.
- [[01.02.03. Maven and Gradle Build Architectures]] — Dissects `pom.xml` (coordinates, dependencies, plugins, lifecycle) side-by-side with `build.gradle.kts` (task graph, configuration avoidance, daemon), compares Maven's nearest-wins conflict resolution against Gradle's highest-version resolution, and shows when incremental compilation and the build cache actually pay off.
- [[01.02.04. Bootstrapping a Bare-Metal Spring Boot Application]] — Uses Spring Initializr to generate a project with Web/JPA/Actuator, then explains `@SpringBootApplication` (component scan + auto-configuration + property binding), builds a `/health` REST controller returning JSON, and attaches the JDWP agent (`-agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=*:5005`) for remote debugging.

### 01.03. TypeScript and Node.js Toolchain Zero to One

- [[01.03.01. Installing Node.js and Version Management]] — Installs Node via `fnm` (fast, Rust-based) and `nvm` (slow, bash-based), explains why the Node binary bundles V8 + libuv + OpenSSL + c-ares and what each contributes, and configures `npm` and `pnpm` with the global prefix and the symlinked `node_modules` layout.
- [[01.03.02. TypeScript Compiler and Configuration Mechanics]] — Generates `package.json` and `tsconfig.json`, then walks every important compiler option (`target`, `module`, `moduleResolution`, `strict`, `esModuleInterop`, `outDir`, `sourceMap`) and compares `tsc` (full compile), `tsx` (esbuild-based dev runner), and `ts-node` (transpile-on-demand) for the dev loop.
- [[01.03.03. CommonJS vs. ECMAScript Modules]] — Explains the `require`/`module.exports` synchronous loader vs the `import`/`export` static loader, the Node module resolution algorithm (`node_modules` traversal, `main` field, `exports` field), the temporal dead zone, the `__dirname`/`__filename` gap in ESM, the dual-package hazard, and how `tsconfig.json`'s `module` setting controls what `tsc` emits.
- [[01.03.04. Bootstrapping a Bare-Metal Express TypeScript Application]] — Installs `express`, `@types/express`, `@types/node`, and dev deps, writes a typed `server.ts` with explicit `Request`/`Response`/`NextFunction` annotations, wires source maps for Chrome DevTools line-by-line debugging, and runs via `tsx watch`.

### 01.04. Python Ecosystem Toolchain Zero to One

- [[01.04.01. Installing Python and Environment Isolation]] — Installs CPython via `pyenv` (compiles from source per version) and explains why you must never `pip install` into the system interpreter, then creates `venv`/`virtualenv` environments and adopts `pyproject.toml` with `poetry` or `pip-tools` for deterministic lockfiles.
- [[01.04.02. Python Execution Model and Module System]] — Runs `hello.py` through CPython's compile→bytecode→eval loop, explains the `__name__ == "__main__"` guard, the `__pycache__/*.pyc` invalidation rules (mtime + source size + magic tag), and the import system: `sys.modules` cache, meta path finders, path-based loaders, regular packages with `__init__.py`, and namespace packages.
- [[01.04.03. Bootstrapping a Bare-Metal Flask Application]] — Installs Flask inside an isolated `venv`, writes `app.py` with `Flask(__name__)`, defines a dynamic route returning JSON via `jsonify`, then contrasts the Werkzeug dev server against `gunicorn -w 4 -k gevent` for production WSGI serving.
- [[01.04.04. Bootstrapping a Bare-Metal Django Application]] — Installs Django, runs `django-admin startproject`, dissects the generated layout (`manage.py`, `settings.py`, `urls.py`, `wsgi.py`, `asgi.py`), creates an app with `python manage.py startapp core`, registers it in `INSTALLED_APPS`, and routes a JSON view through URLconf.

### 01.05. PHP and Composer Ecosystem Zero to One

- [[01.05.01. Installing PHP CLI and PHP-FPM Runtimes]] — Installs PHP via `ondrej/php` PPA on Ubuntu, Homebrew on macOS, and the windows.php.net MSI on Windows; configures `php.ini` (`memory_limit`, `max_execution_time`, `error_reporting`, `extension=...`); and verifies the install with `php -v`, `php -m`, and `php-fpm -t`.
- [[01.05.02. Composer Package Management and PSR-4 Autoloading]] — Installs Composer globally, contrasts `composer.json` (declared ranges) with `composer.lock` (resolved exact versions + integrity hashes), explains the PSR-4 namespace-to-path mapping (`"Acme\\": "src/"`), runs `composer dump-autoload -o` for the production class map, and writes a `declare(strict_types=1)` OO script.
- [[01.05.03. Bootstrapping a Vanilla FastCGI Web Script]] — Runs `php -S localhost:8000 -t public/ public/index.php` to start the built-in dev server with a router script, walks the `$_SERVER`/`$_GET`/`$_POST`/`$_FILES` superglobals, and writes a front-controller `index.php` that parses `REQUEST_URI` and emits `Content-Type: application/json`.
- [[01.05.04. Bootstrapping a Bare-Metal Laravel Application]] — Runs `composer create-project laravel/laravel` or `laravel new`, walks the generated directory (`app/`, `config/`, `routes/`, `database/`, `public/index.php`), uses the Artisan CLI (`make:controller`, `make:model`, `make:migration`), and adds a JSON route to `routes/api.php` served by `php artisan serve`.

## How to Read This Section

1. **Read the concept notes first.** [[01.01.01. Language Execution Models]] and [[01.01.02. Package Managers and Dependency Resolution Algorithms]] establish the mental model that the rest of the section relies on — without the AOT/JIT/interpreter distinction and the dependency-DAG mental model, the ecosystem-specific notes are just command-line recipes.
2. **Implement the anchor.** The Java sub-section (01.02) is the anchor. Work through it end-to-end: install the JDK, compile `HelloWorld.java`, build with Maven, then bootstrap a Spring Boot app and curl `/health`. That sequence is the reference implementation every other ecosystem translates from.
3. **Run the delta pass.** Pick one ecosystem per day from 01.03 (Node), 01.04 (Python), and 01.05 (PHP). Each one is shorter than the anchor because the *concept* is already in your head — only the syntax differs. Write down what is automatic and what is manual in each ecosystem.
4. **Connect.** Follow the Related Notes links at the bottom of every note to reinforce the cross-ecosystem graph. The Spring Boot `pom.xml` ↔ the Express `package.json` ↔ the Django `pyproject.toml` ↔ the Laravel `composer.json` are four spellings of the same artifact.

> [!tip] Reading order
> If you are new to this section, follow the numeric ordering. If you are revising, jump directly to whichever concept you forgot — every note is self-contained and explicitly links back to the concept notes it depends on.

## Conceptual Roadmap

Section 01 is structured as a layered funnel: one conceptual layer at the top (01.01) feeding into four ecosystem-specific layers below (01.02 → 01.03 → 01.04 → 01.05). The five sub-sections are deliberately ordered so that the most explicit, most verbose ecosystem comes first and the most implicit, most convention-driven ecosystem comes last. By the time you reach PHP, you have internalized the universal problem each toolchain solves, so the convention-over-configuration style is a delta you can decode rather than a magic incantation you have to memorize.

The **01.01 fundamentals** layer teaches the two problems every toolchain must solve: how source becomes a running process (the compiler/interpreter question, [[01.01.01. Language Execution Models]]) and how third-party code is declared, resolved, and locked (the package-manager question, [[01.01.02. Package Managers and Dependency Resolution Algorithms]]). Without these two mental models, the ecosystem-specific notes collapse into a list of commands with no theory connecting them.

The **01.02 Java (anchor)** layer is the deepest because Java is the anchor stack for the entire vault. Java teaches the explicit version of every concept: a classpath you set with `-cp`, a module path you set with `-p`, a `pom.xml` that declares every dependency by Maven coordinate (`groupId:artifactId:version`), a `Main-Class` manifest entry you write by hand, and a `@SpringBootApplication` annotation you read in source. Every other ecosystem implements the same machinery with progressively less ceremony.

The **01.03 TypeScript/Node** layer translates the anchor into V8 + libuv. Where Java has `javac` + JVM bytecode, Node has `tsc` + V8 Ignition bytecode → TurboFan JIT. Where Java has `pom.xml`, Node has `package.json`. Where Java has Maven's nearest-wins resolution, npm has flat `node_modules` with nested copies for conflicts and pnpm has a content-addressable store with symlinks. The new concepts that Node introduces — the single-threaded event loop, the CommonJS-vs-ESM schism — are covered in their own H3s.

The **01.04 Python** layer translates the anchor into CPython. Where Java has `javac` + JVM, Python has `compile()` + `ceval.c`'s main interpreter loop (a giant `switch` on opcode in `Python/ceval.c`). Where Java has `pom.xml`, Python has `pyproject.toml`. Where Java has the classpath, Python has `sys.path` and `__pycache__`. The new concept Python introduces is the `venv` isolation model — there is no equivalent of "pollute the system Java" because Java does not have a system package registry the way Debian's `apt-get install python3-requests` pollutes the system Python.

The **01.05 PHP** layer translates the anchor into the Zend VM + PHP-FPM process model. Where Java has the JVM, PHP has the Zend VM that compiles source to Zend opcodes and executes them via `zend_execute()`. Where Java has Spring Boot's long-running process, PHP has the traditional per-request process model: php-fpm forks a worker, the worker loads `auto_prepend_file`, runs the request, tears down, and the next request starts from a clean slate. Composer is the npm of PHP; PSR-4 autoloading is the equivalent of Node's `node_modules` resolution algorithm. Laravel is the Spring Boot of PHP — same component-container, same routing, same ORM, same middleware pipeline, all expressed with PHP's lighter syntax.

The critical cross-cutting insight is that every ecosystem solves the same four problems: (1) where does the bytecode/native code come from, (2) how are third-party packages declared, resolved, and locked, (3) how does the runtime locate and load modules at process start, and (4) how is the entry point of a web application wired so that an incoming HTTP request becomes a function call. Sections 01.02.04, 01.03.04, 01.04.03, 01.04.04, and 01.05.04 are the four answers to question (4) — read them in sequence and the universal shape of "bootstrapping a backend service" becomes visible.

The failure modes this section governs are the ones that bite in the first week of a new project: a `JAVA_HOME` pointing at a JRE instead of a JDK, a `package-lock.json` that drifted from `package.json` because someone ran `npm install` instead of `npm ci`, a system Python polluted by `sudo pip install`, a PHP-FPM pool with `memory_limit=128M` that OOMs under load, a Spring Boot app that takes 25 seconds to start because the dev didn't exclude `HibernateJpaAutoConfiguration` from a non-persistence service. Each of these is a Section 01 failure — the runtime, the package manager, or the bootstrap step was misconfigured — and each one is fixed by knowing the mechanics this section teaches.
