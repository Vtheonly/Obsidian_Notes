# 01.04.01. Installing Python and Environment Isolation

## What This Is

Python ships preinstalled on macOS and almost every Linux distribution, and that preinstall is exactly the Python you must never use for development. The system Python is owned by the OS package manager (`apt`, `yum`, `brew`); installing packages into it with `pip` pollutes the system, breaks OS utilities that depend on specific package versions, and produces an environment you cannot reproduce on a colleague's machine. The correct workflow is to install Python via a version manager (`pyenv` on macOS/Linux, the official installer on Windows), never `sudo pip install` anything, and isolate every project's dependencies in a virtual environment (`venv` or `virtualenv`) that lives inside the project directory. This note walks the install, the isolation primitives, and the modern `pyproject.toml`-based dependency management workflow with Poetry or pip-tools, plus the increasingly popular `uv` (a Rust-based reimplementation of pip + virtualenv that is 10–100× faster).

The note sits at the bottom of the Python toolchain — [[01.04.02. Python Execution Model and Module System]] assumes a working `python` on the `PATH`, [[01.04.03. Bootstrapping a Bare-Metal Flask Application]] and [[01.04.04. Bootstrapping a Bare-Metal Django Application]] assume an isolated `venv` to install Flask/Django into. The failure modes this note governs are the ones that surface as `ModuleNotFoundError: No module named 'flask'` in production (because you deployed without freezing requirements), as `error: externally-managed-environment` (PEP 668, the "do not pollute system Python" enforcement), and as the time-honoured "`sudo pip install` broke my Ubuntu's `apt`".

## The Details

### Installing Python runtimes via `pyenv` and managing multiple system versions

Python has two actively-supported major versions in production today: Python 3.11 (released October 2022, end-of-life October 2027) and Python 3.12 (released October 2023). Python 3.13 (October 2024) adds experimental free-threaded build (`--disable-gil`) and a JIT compiler preview. Every Django, Flask, FastAPI, and Celery project picks one and pins it; the CPython interpreter is not ABI-compatible across minor versions, so a wheel compiled for 3.11 will not install on 3.12 (`cp311-cp311-manylinux_2_17_x86_64.whl` refuses to install on a `cp312` interpreter).

`pyenv` is the version manager for Python on macOS and Linux. It clones the CPython source from GitHub and compiles it locally with `gcc`, then symlinks `~/.pyenv/versions/3.12.4/bin/python3.12` to `~/.pyenv/shims/python` so the active version appears first on the `PATH`. Compiling takes 3–5 minutes per version but produces a Python with the exact `--enable-shared`, `--enable-optimizations`, and `--with-lto` flags you specify.

```bash
# install pyenv on macOS
brew install pyenv

# install pyenv on Ubuntu/Debian
curl https://pyenv.run | bash

# add to ~/.bashrc (or ~/.zshrc)
export PYENV_ROOT="$HOME/.pyenv"
export PATH="$PYENV_ROOT/bin:$PATH"
eval "$(pyenv init -)"

# install build dependencies (Ubuntu)
sudo apt install -y make build-essential libssl-dev zlib1g-dev \
    libbz2-dev libreadline-dev libsqlite3-dev wget curl llvm \
    libncursesw5-dev xz-utils tk-dev libxml2-dev libxmlsec1-dev \
    libffi-dev liblzma-dev

# install Python versions
pyenv install 3.12.4           # compiles CPython — takes 3–5 minutes
pyenv install 3.11.9
pyenv install 3.13.0

# list installed versions
pyenv versions

# set the global default
pyenv global 3.12.4

# set a local version for a project (writes .python-version)
cd myapp
pyenv local 3.11.9
# .python-version now contains "3.11.9"
# cd-ing into the project switches python automatically

# verify
python --version         # Python 3.11.9
which python             # /home/user/.pyenv/shims/python
pyenv which python       # /home/user/.pyenv/versions/3.11.9/bin/python
```

The `.python-version` file is the equivalent of Node's `.nvmrc` — a one-line file in the project root that names the Python version. `pyenv` reads it on `cd` (via the shell hook from `pyenv init -`) and switches versions automatically. Commit this file to version control so every developer gets the same Python.

On Windows, `pyenv` is `pyenv-win` (a separate project, installable via PowerShell). The recommended alternative is the official Python installer from `python.org`, which lets you install multiple versions side-by-side into `C:\Python311\`, `C:\Python312\`, etc., and uses the `py` launcher (`py -3.12`) to pick one:

```powershell
# Windows with py launcher (ships with python.org installers)
py -0p                    # list installed versions with paths
py -3.12 -m venv .venv    # create venv with Python 3.12
.venv\Scripts\activate
```

A recurring confusion on every platform is the `python` vs `python3` vs `python3.12` command naming. On Linux, `python` historically meant Python 2 (which is end-of-life since 2020), and `python3` is the Python 3 binary; some distributions (notably Debian and Ubuntu) still refuse to ship a bare `python` command without the `python-is-python3` package installed. The fully-qualified form `python3.12` always points at a specific minor version and is what CI scripts should use. The same naming split exists for pip: `pip` (ambiguous, may not exist), `pip3` (Python 3), `python3 -m pip` (unambiguous, recommended — always uses the pip matching the interpreter you invoked). The `python -m pip` form is safer than `pip` because it cannot accidentally invoke a different Python's pip — the `-m` flag loads the module from the same interpreter that's running. The same rule applies to `python -m venv` (vs `virtualenv`), `python -m http.server`, `python -m pytest`: always use `python -m <module>` to ensure you are invoking the module through the active interpreter.

The production failure mode here is "the Docker image has a different Python version than the developer's laptop". A `python:3.12-slim` Docker image ships Python 3.12.4; if the developer has Python 3.12.0 locally and a wheel was compiled with their version, it may fail to install in the Docker image (rare but possible for C-extension packages). The fix is to pin the exact patch version in both places: use `python:3.12.4-slim` in the Dockerfile and `pyenv install 3.12.4` locally. The other failure mode is "my code uses Python 3.12 syntax (`type X = int`) but production has Python 3.10" — pyenv's `.python-version` does not help here because the production Docker image is built from a different base. Always check the Python version in CI with `python --version` as the first step.

### The critical necessity of isolation: System Python pollution risks and package collision hazards

Why can't you just `pip install flask` into the system Python? Three reasons.

First, **the system Python is owned by the OS package manager**, and the OS may have specific package versions pinned for its own utilities. Ubuntu's `apt` uses Python 3 for `unattended-upgrades`, `ubuntu-advantage-tools`, and several system daemons. If you `sudo pip install requests==2.20.0` to fix a bug in your app, you may downgrade the `requests` that `apt` depends on, and the next `apt update` will fail with `ImportError: cannot import name 'JSONDecodeError' from 'requests'`. macOS is worse: the system Python at `/usr/bin/python3` is symlinked into Xcode's command-line tools, and modifying it breaks `xcrun`, `lldb`, and several macOS utilities.

Second, **`pip install` is global by default**. If you `pip install flask==2.0` for project A and `pip install flask==3.0` for project B, the second install overwrites the first — both projects now have Flask 3.0, and project A breaks because Flask 3.0 removed APIs it depended on. There is no per-project isolation in the system Python.

Third, **PEP 668** (the "externally managed environment" PEP, implemented in Python 3.11+) actively prevents you from making this mistake. When you `pip install flask` into a system Python on Ubuntu 23.04+ or Debian 12+, you get:

```bash
$ pip install flask
error: externally-managed-environment

× This environment is externally managed
╰─> To install Python packages system-wide, try apt install
    python3-<package-name>

note: If you believe this is a mistake, please contact your Linux distribution maintainer.
      You can override this with --break-system-packages, but you probably should not.
```

The `--break-system-packages` flag exists for escape hatches but its name is the warning. PEP 668 marks system Python installations with a `EXTERNALLY-MANAGED` file in the `stdlib` directory, and pip refuses to install into them without the override.

```text
  Without isolation:
  ─────────────────────────────────────────────────────
  System Python (/usr/bin/python3)
  ├── site-packages/
  │   ├── requests==2.31.0   (used by apt's daemons AND by your app)
  │   ├── flask==3.0.0       (your app needs 2.0; apt doesn't care)
  │   └── numpy==1.26.0      (project A needs 1.x; project B needs 2.x)
  └── ...

  Result: every project shares one site-packages.
          Upgrading anything breaks something.
          Production deployment is non-reproducible.

  With isolation:
  ─────────────────────────────────────────────────────
  System Python (/usr/bin/python3)         ← untouched
  ├── site-packages/                       ← OS-managed only

  Project A venv (~/myapp-a/.venv/)
  ├── bin/python → /usr/bin/python3         ← symlink to system interpreter
  ├── lib/python3.12/site-packages/
  │   ├── flask==2.3.0
  │   └── requests==2.31.0

  Project B venv (~/myapp-b/.venv/)
  ├── bin/python → /usr/bin/python3
  ├── lib/python3.12/site-packages/
  │   ├── flask==3.0.0
  │   └── requests==2.32.0
```

The lesson is: never `sudo pip install`, never install into the system Python, always create a `venv` per project. The system Python is for the OS; your project Python is the `venv`.

The deeper question — "venv vs container vs pipx" — has three answers depending on what you are isolating. A **`venv`** isolates a single project's Python *library* dependencies (Flask, Django, requests) by giving it its own `site-packages/` directory; the Python interpreter itself is shared with the system (the venv's `bin/python` is a symlink to `/usr/bin/python3.12`). A **container** (Docker, Podman) isolates the entire OS-level runtime: the Linux distribution, the Python interpreter, the system C libraries (`glibc`, `libssl`), the filesystem, and the project's libraries all together. Use a venv when you only need library isolation (typical for Python-only projects on a developer laptop); use a container when you need OS-level isolation (deploying to Kubernetes, ensuring the production image is byte-identical to the CI image, mixing Python with non-Python services). **`pipx`** is the third isolation level, specifically for *global CLI tools* written in Python — `black`, `mypy`, `ruff`, `poetry`, `httpie`, `awscli` — that you want to invoke from anywhere but whose dependencies you do not want polluting any project's venv. `pipx install poetry` creates a dedicated venv at `~/.local/pipx/venvs/poetry/` and symlinks the `poetry` binary to `~/.local/bin/poetry`. Each tool gets its own isolated venv, so `black`'s `click==8.0` does not conflict with `httpie`'s `click==8.1`. Never `pip install` CLI tools globally; `pipx install` them instead.

### Virtual environments: Creating and activating environments via `venv` and `virtualenv`

`venv` is the standard library module for creating virtual environments (since Python 3.3). `virtualenv` is a third-party package that does the same thing faster and with more features (it can create environments for Python versions you don't have installed, via wheels). For 99% of use cases, `venv` is sufficient.

```bash
# create a venv named .venv in the project directory
python -m venv .venv

# activate it (macOS/Linux)
source .venv/bin/activate

# activate it (Windows PowerShell)
.venv\Scripts\Activate.ps1

# activate it (Windows cmd)
.venv\Scripts\activate.bat

# verify
which python         # /home/user/myapp/.venv/bin/python
which pip            # /home/user/myapp/.venv/bin/pip
python -c "import sys; print(sys.prefix)"
                     # /home/user/myapp/.venv  (vs /usr without venv)

# install packages (now isolated to .venv)
pip install flask

# leave the venv
deactivate
```

What `python -m venv .venv` actually does is create a directory layout that mimics a Python installation:

```text
  .venv/
  ├── bin/                          (Scripts/ on Windows)
  │   ├── python → /usr/bin/python3 ← symlink to the interpreter
  │   ├── python3 → /usr/bin/python3
  │   ├── pip                       ← pip installed into the venv
  │   ├── activate                  ← shell script that sets PATH/VIRTUAL_ENV
  │   └── flask                     ← entry points from installed packages
  ├── lib/
  │   └── python3.12/
  │       └── site-packages/        ← where pip installs packages
  │           ├── flask/
  │           ├── jinja2/
  │           └── ...
  ├── include/                      ← C headers for compilation
  └── pyvenv.cfg                    ← venv metadata
```

The `pyvenv.cfg` file records which Python the venv was created from (`home = /usr/bin`), the Python version, and whether the venv has its own copies of the standard library (no — it inherits from the parent). The `activate` script sets three environment variables: `VIRTUAL_ENV=/path/to/.venv`, `PATH=$VIRTUAL_ENV/bin:$PATH`, and a shell prompt prefix `(.venv)`. Deactivating restores the original values.

The activation step is what makes `pip install` go to the venv's `site-packages` instead of the system's. Without activation, `pip install flask` either fails (PEP 668) or installs to the system (older Python). An alternative to activation is to call the venv's pip directly: `.venv/bin/pip install flask`. This is what CI scripts and Dockerfiles do, because activating a venv in a non-interactive shell is fragile.

```dockerfile
# Dockerfile pattern: create venv, install into it, never activate
FROM python:3.12-slim
WORKDIR /app
RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"     ← put venv first on PATH
COPY requirements.txt .
RUN /opt/venv/bin/pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["/opt/venv/bin/python", "-m", "myapp"]
```

The `uv` reimplementation (from Astral, the company behind `ruff`) is increasingly the default in 2024. `uv` is a single Rust binary that replaces `pip`, `pip-tools`, `virtualenv`, and `pyenv` in one tool. It is 10–100× faster than pip (parallel downloads, global package cache shared across venvs via hardlinks), creates venvs in milliseconds instead of seconds, and has built-in Python version management (`uv python install 3.12`). The workflow is drop-in compatible:

```bash
# install uv (single binary, no Python required)
curl -LsSf https://astral.sh/uv/install.sh | sh

# create a venv with uv (10× faster than python -m venv)
uv venv .venv

# install packages with uv (parallel downloads, global cache)
uv pip install flask
uv pip install -r requirements.txt
uv pip install -e .                # editable install of the current project

# uv can also manage Python versions like pyenv
uv python install 3.12 3.11
uv python list

# uv can run a command in the project venv without activation
uv run python -m myapp
uv run pytest

# uv sync installs from a lockfile (uv.lock) — equivalent to poetry install
uv sync
```

`uv pip install -e .` deserves explanation — the `-e` flag is "editable" or "develop" mode. Instead of copying the package's files into `site-packages/`, it writes a `.pth` file that points back at the source directory. This means edits to the source take effect immediately without reinstalling — critical when you are developing the package itself. The same flag exists in `pip install -e .` and `python setup.py develop` (legacy). Without `-e`, every code change requires `pip install .` again. The failure mode of editable installs is "deployed with `-e`" — the production container ships a `.pth` file pointing at a source directory that may not exist or may have been mounted read-write. Never `pip install -e .` in a Dockerfile; use `pip install .` for a normal install that copies files.

The failure mode here is "I forgot to activate the venv and `pip install` went to the system Python". The symptom is `pip install flask` succeeds, `python -c "import flask"` fails with `ModuleNotFoundError`. The fix is `which pip; which python` — if either points to `/usr/bin/...` instead of `.venv/bin/...`, the venv is not active. The deeper fix is to add a `.envrc` file with `direnv` that auto-activates on `cd`, or to use a tool like Poetry that manages the venv for you.

### Modern dependency management: Configuring `pyproject.toml` with `poetry` and `pip-tools`

The Python ecosystem has converged on `pyproject.toml` as the project manifest, replacing `setup.py`, `setup.cfg`, and `requirements.txt` for new projects. `pyproject.toml` is a TOML file at the project root that declares the project's metadata, dependencies, build system, and tool configuration (ruff, black, mypy, pytest). Three tools build on top of it: **Poetry** (a higher-level project manager that handles venvs, locks, and publishing), **pip-tools** (a lower-level pair of tools that generate locked `requirements.txt` from `pyproject.toml` or `requirements.in`), and **uv** (the modern Rust-based replacement for both, discussed below).

```bash
# install Poetry (one-time)
curl -sSL https://install.python-poetry.org | python3 -
# add to PATH:
export PATH="$HOME/.local/bin:$PATH"

# initialize a new project
poetry new myapp
# creates:
# myapp/
# ├── pyproject.toml
# ├── README.md
# ├── myapp/
# │   └── __init__.py
# └── tests/

# or, initialize in an existing directory
cd existing-project
poetry init

# add dependencies
poetry add flask
poetry add --group dev pytest ruff mypy

# install everything from the lockfile
poetry install

# run commands inside the venv Poetry manages
poetry run python -m myapp
poetry run pytest

# build a wheel + sdist
poetry build
```

The resulting `pyproject.toml`:

```toml
[tool.poetry]
name = "myapp"
version = "0.1.0"
description = "A bare-metal Flask app"
authors = ["Alice <alice@example.com>"]
packages = [{include = "myapp"}]

[tool.poetry.dependencies]
python = "^3.12"
flask = "^3.0.0"

[tool.poetry.group.dev.dependencies]
pytest = "^8.0.0"
ruff = "^0.6.0"
mypy = "^1.11.0"

[build-system]
requires = ["poetry-core"]
build-backend = "poetry.core.masonry.api"
```

Poetry's lockfile is `poetry.lock` — a TOML file that records the exact version, hash, and Python compatibility of every resolved package. `poetry install` reads the lockfile and installs exactly those versions; `poetry update` re-resolves against the manifest's ranges and updates the lockfile. This is the same manifest/lockfile split as npm's `package.json`/`package-lock.json` — `poetry install` is `npm ci`, `poetry update` is `npm install`.

The pip-tools workflow is lower-level — you write `requirements.in` with ranges, run `pip-compile` to produce `requirements.txt` with exact versions and hashes, and run `pip-sync` to install exactly those versions:

```bash
# install pip-tools
pip install pip-tools

# requirements.in
flask>=3.0,<4.0
gunicorn>=22.0

# compile to requirements.txt (exact versions + hashes)
pip-compile requirements.in --generate-hashes --output-file requirements.txt

# install exactly what's in requirements.txt
pip-sync requirements.txt
```

The resulting `requirements.txt`:

```
#
# This file is autogenerated by pip-compile with Python 3.12
# by the following command:
#
#    pip-compile requirements.in --generate-hashes --output-file requirements.txt
#
certifi==2024.8.3 \
    --hash=sha256:3705ea06fe... \
    --hash=sha256:b8ce17af8c...
    # via requests
click==8.1.7 \
    --hash=sha256:0953... \
    --hash=sha256:2cf6...
    # via flask
flask==3.0.3 \
    --hash=sha256:2c7433e... \
    --hash=sha256:4176...
    # via -r requirements.in
gunicorn==22.0.0 \
    --hash=sha256:3503571e... \
    --hash=sha256:6f04d...
    # via -r requirements.in
# ... 30 more transitive dependencies ...
```

The `--generate-hashes` flag adds the sha-256 hash of each wheel's tarball. Installing with `pip install --require-hashes -r requirements.txt` verifies each hash before installing — defence against a compromised PyPI mirror or a maintainer who republished a different tarball under the same version.

The `uv` workflow combines the ergonomics of Poetry with the speed of a Rust binary. `uv` uses the same `pyproject.toml` standard but with a `[project]` table (PEP 621) rather than Poetry's `[tool.poetry]` table:

```toml
# pyproject.toml — PEP 621 standard layout (uv, hatch, pdm all use this)
[project]
name = "myapp"
version = "0.1.0"
description = "A bare-metal Flask app"
requires-python = ">=3.12"
dependencies = [
    "flask>=3.0,<4.0",
    "gunicorn>=22.0",
]

[project.optional-dependencies]
dev = ["pytest>=8.0", "ruff>=0.6", "mypy>=1.11"]

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[tool.uv]
# uv-specific config (cache dir, index URLs, etc.)
```

```bash
# uv commands — faster drop-in for poetry/pip-tools
uv venv                         # create .venv
uv pip install -e ".[dev]"      # editable install with dev extras
uv lock                         # generate uv.lock from pyproject.toml
uv sync                         # install from uv.lock exactly
uv add flask                    # add a dependency and update lock
uv add --dev pytest             # add to dev extras
uv build                        # build wheel + sdist
uv publish                      # publish to PyPI
```

The choice between Poetry, pip-tools, and uv in 2024 is largely a matter of speed and team preference. `uv` is the fastest (a typical `uv sync` of a Flask project completes in under 1 second vs 8–15 seconds for `poetry install`); `poetry` has the most mature ecosystem and the best documentation; `pip-tools` is the most explicit and easiest to use alongside a plain `requirements.txt`-driven Dockerfile. All three produce a lockfile that you should commit to version control.

The failure mode this prevents is "production installed a different version than dev". Without a lockfile, `pip install -r requirements.txt` (with ranges like `flask>=3.0`) installs whatever the latest 3.x is at install time — which on Monday is 3.0.3 and on Friday is 3.0.4 with a regression that breaks your app. The lockfile pins the exact version. Always install from a lockfile in production: `pip install --require-hashes -r requirements.txt` (pip-tools) or `poetry install --no-root` (Poetry) or `uv sync --frozen` (uv). The `--no-root` flag tells Poetry to skip installing the project itself (which you have not built yet) and only install dependencies; `--frozen` tells uv to refuse to update the lockfile if it's out of sync with `pyproject.toml` (fail the deploy rather than silently re-resolving).

## Key Takeaways

1. **Install Python via `pyenv` (macOS/Linux) or the python.org installer (Windows), never use the system Python.** Pin per-project with `.python-version`. Always invoke pip via `python -m pip` (not bare `pip`) to avoid the python-vs-python3 ambiguity. Pin the exact patch version in both `pyenv` and Docker to avoid wheel-ABI drift.
2. **PEP 668 refuses `pip install` into system Python — use a `venv` per project, a container for OS-level isolation, and `pipx` for global CLI tools.** `python -m venv .venv && source .venv/bin/activate` is the universal pattern. Never `sudo pip install`. `uv venv` is the 10×-faster modern alternative.
3. **Use `pyproject.toml` with Poetry, pip-tools, or uv for lockfile-based dependency management.** `poetry install` / `pip-sync` / `uv sync` install from the lockfile; `poetry update` / `pip-compile` / `uv lock` re-resolve. Install with `--require-hashes` (pip-tools) or `--frozen` (uv) in production for supply-chain defence. Use `pip install -e .` for editable installs during development — never in production Dockerfiles.
