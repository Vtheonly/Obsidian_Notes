# 01.04.04. Bootstrapping a Bare-Metal Django Application

## What This Is

Django is the batteries-included Python web framework — it ships with an ORM, a migrations system, an authentication system, an admin interface, a templating engine, a form library, a caching framework, and a security middleware stack, all in a single pip-installed package. Where Flask gives you routing and nothing else, Django gives you the entire web tier of an application. This is the Python equivalent of [[01.02.04. Bootstrapping a Bare-Metal Spring Boot Application]] — both frameworks are "batteries-included", and the mental model transfers almost one-to-one: Spring's `@SpringBootApplication` ↔ Django's `INSTALLED_APPS`; Spring's `@RestController` ↔ Django's class-based `View`; Spring's JPA repositories ↔ Django's model Managers; Spring's application.properties ↔ Django's `settings.py`. We bootstrap a Django project from scratch using `django-admin`, dissect the generated file layout, create an app with `startapp`, register it, define a model, generate and apply migrations, register the model with the admin, and route a JSON view through URLconf.

Django is the right comparison to Spring Boot because both frameworks have explicit "convention over configuration" — they ship defaults that you can override, and the defaults are good enough for most production deployments. The lesson this note teaches that Flask does not is the cost of using the framework's full stack: Django's ORM and migration system impose their own model on your data layer, and stepping outside that model (e.g. using a raw SQL query, a NoSQL database, or a different migration tool) is fighting the framework.

## The Details

### Installing Django and utilizing the `django-admin` CLI generator

Django is a single pip package, `django`. Installing it gives you both the framework (`import django`) and the `django-admin` CLI tool. Install inside a virtual environment (see [[01.04.01. Installing Python and Environment Isolation]]):

```bash
mkdir mysite && cd mysite
python -m venv .venv
source .venv/bin/activate

pip install django

# verify
python -m django --version    # 5.0.7
django-admin --version        # 5.0.7

# generate a new project (creates a directory called mysite/)
django-admin startproject mysite .

# the trailing "." creates the project in the current directory
# (without it, you get mysite/mysite/ which is awkward)

ls -la
# manage.py          ← project management script
# mysite/             ← the project package
#   __init__.py
#   asgi.py          ← ASGI entry point (async)
#   settings.py      ← project configuration
#   urls.py          ← root URLconf
#   wsgi.py          ← WSGI entry point (sync)

# freeze dependencies
pip freeze > requirements.txt
```

The `django-admin` CLI is the umbrella for all Django project operations: `startproject` (creates a project), `startapp` (creates an app within a project), `migrate` (applies database migrations), `makemigrations` (generates new migrations from model changes), `createsuperuser` (creates an admin user), `shell` (opens a Python shell with Django context loaded), `dbshell` (opens the configured database's CLI), `test` (runs the test suite), `runserver` (starts the dev server), `collectstatic` (copies static files into `STATIC_ROOT` for production serving). After `startproject`, you typically use `python manage.py <command>` instead of `django-admin <command>` — `manage.py` is a thin wrapper that sets `DJANGO_SETTINGS_MODULE` to your project's `settings.py` and calls `django-admin`.

```python
# manage.py (auto-generated, do not edit)
#!/usr/bin/env python
import os
import sys

def main():
    os.environ.setdefault("DJANGO_SETTINGS_MODULE", "mysite.settings")
    try:
        from django.core.management import execute_from_command_line
    except ImportError as exc:
        raise ImportError(
            "Couldn't import Django. Are you sure it's installed and "
            "available on your PYTHONPATH environment variable? Did you "
            "forget to activate a virtual environment?"
        ) from exc
    execute_from_command_line(sys.argv)

if __name__ == "__main__":
    main()
```

The `DJANGO_SETTINGS_MODULE` environment variable is what Django reads to find its configuration — `mysite.settings` means "the `settings` module inside the `mysite` package". Every `manage.py` command, every `gunicorn` invocation, every Celery worker reads this env var. The failure mode is "I have two settings modules (`settings.py` for dev, `settings_prod.py` for prod) and the wrong one is loaded" — the symptom is database connection strings pointing at the dev database in production. The fix is to set `DJANGO_SETTINGS_MODULE` explicitly in the production environment (in the Dockerfile's `ENV`, in the systemd unit's `Environment=`, or in gunicorn's `--env` flag) and never rely on the default.

### Anatomy of a Django project: `manage.py`, `settings.py`, `urls.py`, `wsgi.py`, and `asgi.py`

The `startproject` command generates five files. Each has a specific role in the Django architecture:

```text
  mysite/                          ← project root (any name)
  ├── manage.py                    ← CLI entry point (sets DJANGO_SETTINGS_MODULE)
  └── mysite/                      ← project package (matches project name)
      ├── __init__.py              ← empty, makes the directory a package
      ├── settings.py              ← configuration: INSTALLED_APPS, DATABASES, MIDDLEWARE
      ├── urls.py                  ← root URLconf: maps URLs to views
      ├── wsgi.py                  ← WSGI entry point (for gunicorn, uWSGI, mod_wsgi)
      └── asgi.py                  ← ASGI entry point (for uvicorn, daphne, hypercorn)
```

**`settings.py`** is the project's configuration. It is a plain Python module — not YAML, not TOML, not JSON. This means settings can be computed programmatically (read environment variables, conditionally enable features, build lists from string env vars). The important settings are:

```python
# mysite/settings.py (abridged)
from pathlib import Path
import os

BASE_DIR = Path(__file__).resolve().parent.parent

SECRET_KEY = os.environ.get("DJANGO_SECRET_KEY", "django-insecure-change-me")
DEBUG = os.environ.get("DJANGO_DEBUG", "False") == "True"
ALLOWED_HOSTS = os.environ.get("DJANGO_ALLOWED_HOSTS", "localhost,127.0.0.1").split(",")

INSTALLED_APPS = [
    "django.contrib.admin",
    "django.contrib.auth",
    "django.contrib.contenttypes",
    "django.contrib.sessions",
    "django.contrib.messages",
    "django.contrib.staticfiles",
    # local apps (we will add 'polls' below)
]

MIDDLEWARE = [
    "django.middleware.security.SecurityMiddleware",
    "django.contrib.sessions.middleware.SessionMiddleware",
    "django.middleware.common.CommonMiddleware",
    "django.middleware.csrf.CsrfViewMiddleware",
    "django.contrib.auth.middleware.AuthenticationMiddleware",
    "django.contrib.messages.middleware.MessageMiddleware",
    "django.middleware.clickjacking.XFrameOptionsMiddleware",
]

ROOT_URLCONF = "mysite.urls"
WSGI_APPLICATION = "mysite.wsgi.application"
ASGI_APPLICATION = "mysite.asgi.application"

DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.postgresql",
        "NAME": os.environ.get("DB_NAME", "mysite"),
        "USER": os.environ.get("DB_USER", "postgres"),
        "PASSWORD": os.environ.get("DB_PASSWORD", ""),
        "HOST": os.environ.get("DB_HOST", "localhost"),
        "PORT": os.environ.get("DB_PORT", "5432"),
        "CONN_MAX_AGE": 60,        # persistent connection lifetime in seconds
        "CONN_HEALTH_CHECKS": True,  # Django 4.1+: check connection before reusing
        "OPTIONS": {
            "connect_timeout": 5,
            "keepalives": 1,
            "keepalives_idle": 30,
        }
    }
}

STATIC_URL = "/static/"
STATIC_ROOT = BASE_DIR / "staticfiles"
LANGUAGE_CODE = "en-us"
TIME_ZONE = "UTC"
USE_I18N = True
USE_TZ = True
DEFAULT_AUTO_FIELD = "django.db.models.BigAutoField"
```

`INSTALLED_APPS` is the registry of Django apps loaded at startup. Each entry is a Python package containing a `AppConfig` subclass (or just a package, in which case Django looks for `apps.py`). Apps contribute models, template tags, middleware, URL patterns, and management commands. The six built-in apps provide admin, auth, sessions, content types, messages, and static files — together they implement the "batteries-included" admin and auth system. Adding `'polls'` to this list registers our application (created in the next H3).

`MIDDLEWARE` is the request/response pipeline. Each middleware is a callable that wraps the view: `process_request` runs before the view, `process_response` runs after. The order matters — `SecurityMiddleware` must be first to set security headers before anything else runs; `SessionMiddleware` must run before `AuthenticationMiddleware` (because auth reads the session). Django's default middleware stack is well-tuned for security and includes CSRF protection (`CsrfViewMiddleware`), clickjacking protection (`XFrameOptionsMiddleware`), and HSTS/SSL redirection (`SecurityMiddleware`).

The `DATABASES` setting is a dict of connection configs — `default` is required, and additional keys (e.g. `replica`) let you target a read replica. The `CONN_MAX_AGE` setting controls persistent connections: by default Django opens a fresh connection per request (`CONN_MAX_AGE=0`); setting it to 60 makes Django keep the connection open for 60 seconds between requests, amortising the TCP handshake + auth round-trip across requests. Under gunicorn with 4 sync workers, `CONN_MAX_AGE=60` reduces per-request DB latency by 5–15 ms but multiplies the number of open Postgres connections by up to `workers * threads_per_worker` (4 workers × 1 thread = 4 persistent connections). Set Postgres `max_connections` accordingly (default 100).

**`urls.py`** is the root URLconf — the entry point for URL routing. It contains a `urlpatterns` list of `path()` or `re_path()` entries, each mapping a URL prefix to a view or to a sub-URLconf (`include()`):

```python
# mysite/urls.py
from django.contrib import admin
from django.urls import path, include

urlpatterns = [
    path("admin/", admin.site.urls),           # built-in admin
    path("api/", include("polls.urls")),       # delegate /api/* to the polls app
    path("health/", include("polls.health_urls")),  # /health/
]
```

The `include("polls.urls")` call loads `polls/urls.py` and prepends the `api/` prefix to every pattern in it. This is how Django projects compose URL trees — each app owns its own URL subtree, and the root URLconf just includes them.

**`wsgi.py`** is the WSGI entry point. It contains a single `application` variable, which is the WSGI callable that gunicorn/uWSGI invoke:

```python
# mysite/wsgi.py
import os
from django.core.wsgi import get_wsgi_application

os.environ.setdefault("DJANGO_SETTINGS_MODULE", "mysite.settings")
application = get_wsgi_application()
```

gunicorn is invoked with `gunicorn mysite.wsgi:application --bind 0.0.0.0:8000 --workers 4` — the `mysite.wsgi:application` spec means "import the `application` variable from the `mysite.wsgi` module". The `asgi.py` file is the async equivalent, used by `uvicorn`/`daphne`/`hypercorn` for ASGI servers:

```python
# mysite/asgi.py
import os
from django.core.asgi import get_asgi_application

os.environ.setdefault("DJANGO_SETTINGS_MODULE", "mysite.settings")
application = get_asgi_application()
```

The ASGI entry point serves the same purpose as WSGI but supports async — long-lived websockets, server-sent events, and `async def` views. A Django project can run under either WSGI or ASGI; the choice is made by which server you point at the entry point. Mixing the two is fine: typical setups use ASGI for the public-facing web tier (where websockets matter) and WSGI for background Celery workers (which do not need async). The `asgi.py` file is the production path for any Django 3.1+ project that uses Django Channels, async ORM queries (`async def` views with `await Model.objects.aget(...)`), or streaming responses.

The failure mode this exposes is the "settings drift" incident. Because `settings.py` is a Python module, developers are tempted to put conditional logic in it that reads from environment variables — and the conditionals grow over time until no one is sure what configuration production is running. The defence is to split settings into `settings/base.py`, `settings/dev.py`, `settings/prod.py` and set `DJANGO_SETTINGS_MODULE=mysite.settings.prod`. The `django-environ` package helps parse env vars into typed values; `django-configurations` is a more heavyweight alternative that uses class-based settings.

### Creating a dedicated Django App (`python manage.py startapp core`)

A Django *project* is a deployment unit (a website); a Django *app* is a reusable feature module (a blog, a forum, an API). A project contains multiple apps. The `startapp` command generates the app skeleton — here we create the canonical `polls` app from the official Django tutorial:

```bash
python manage.py startapp polls

ls polls/
# __init__.py        ← empty, makes it a package
# admin.py           ← admin site registration
# apps.py            ← AppConfig subclass
# models.py          ← database models (ORM)
# tests.py           ← test cases (convention: tests/ package instead)
# views.py           ← view functions or classes
# migrations/        ← auto-generated migration files
#   __init__.py
```

```python
# polls/apps.py
from django.apps import AppConfig

class PollsConfig(AppConfig):
    default_auto_field = "django.db.models.BigAutoField"
    name = "polls"
```

The `AppConfig` subclass is the app's metadata — `name` is the Python path to the app package, `default_auto_field` is the type used for auto-created primary keys. The `ready()` method is called once after the app registry is fully loaded — it is where you register signals, run app-level initialization, or import modules that have side effects (e.g. registering template tags).

After `startapp`, you must add the app to `INSTALLED_APPS` in `settings.py`:

```python
INSTALLED_APPS = [
    "django.contrib.admin",
    "django.contrib.auth",
    # ... other built-ins ...
    "polls",                       # ← add our app
]
```

Until the app is in `INSTALLED_APPS`, Django will not load its models, its migrations, its template tags, or its URLconfs. The symptom of forgetting this is `ModuleNotFoundError: No module named 'polls'` from a URLconf include, or models that do not create database tables on `migrate`.

With the app registered, define the data model. Django's ORM maps Python classes to database tables:

```python
# polls/models.py
import datetime
from django.db import models
from django.utils import timezone


class Question(models.Model):
    """A poll question with a publication date."""
    question_text = models.CharField(max_length=200)
    pub_date = models.DateTimeField("date published")

    def __str__(self) -> str:
        return self.question_text

    def was_published_recently(self) -> bool:
        return timezone.now() >= self.pub_date >= timezone.now() - datetime.timedelta(days=1)


class Choice(models.Model):
    """A choice belonging to a Question, with a vote tally."""
    question = models.ForeignKey(Question, on_delete=models.CASCADE, related_name="choices")
    choice_text = models.CharField(max_length=200)
    votes = models.IntegerField(default=0)

    def __str__(self) -> str:
        return self.choice_text
```

Each `models.Field` becomes a column in the database table: `Question.question_text` becomes a `varchar(200)` column, `Question.pub_date` becomes a `timestamptz`, `Choice.question` becomes a `foreign key` to `polls_question.id`. The `related_name="choices"` makes `question.choices.all()` return all related choices (the default would be `question.choice_set.all()`). The `on_delete=models.CASCADE` makes deleting a question delete all its choices — the same database-level `ON DELETE CASCADE` constraint. Django's ORM is not lazy like SQLAlchemy's default — it issues SQL queries immediately when you access `question.choices`, which can be a performance surprise (the N+1 query problem). The fix is `select_related` (for foreign keys) or `prefetch_related` (for many-to-many).

Now generate the migration that creates the `polls_question` and `polls_choice` tables, and apply it:

```bash
# Step 1: detect model changes and write a migration file
python manage.py makemigrations polls
# Migrations for 'polls':
#   polls/migrations/0001_initial.py
#     - Create model Question
#     - Create model Choice

# Inspect the generated SQL (does NOT apply it — useful for review)
python manage.py sqlmigrate polls 0001
# BEGIN;
# --
# -- Create model Question
# --
# CREATE TABLE "polls_question" (
#     "id" bigint NOT NULL PRIMARY KEY,
#     "question_text" varchar(200) NOT NULL,
#     "pub_date" timestamp with time zone NOT NULL
# );
# --
# -- Create model Choice
# --
# CREATE TABLE "polls_choice" (
#     "id" bigint NOT NULL PRIMARY KEY,
#     "question_id" bigint NOT NULL,
#     "choice_text" varchar(200) NOT NULL,
#     "votes" integer NOT NULL
# );
# ALTER TABLE "polls_choice"
#   ADD CONSTRAINT "polls_choice_question_id_polls_question_id_..." FOREIGN KEY ("question_id")
#   REFERENCES "polls_question" ("id") DEFERRABLE INITIALLY DEFERRED;
# CREATE INDEX "polls_choice_question_id_..." ON "polls_choice" ("question_id");
# COMMIT;

# Step 2: apply the migration to the database
python manage.py migrate
# Operations to perform:
#   Apply all migrations: admin, auth, contenttypes, polls, sessions
# Running migrations:
#   Applying polls.0001_initial... OK
```

The two-step `makemigrations` → `migrate` workflow is the Django equivalent of Hibernate's `hbm2ddl=update` but explicit and reviewable. `makemigrations` writes a Python file (`polls/migrations/0001_initial.py`) that *describes* the schema change as a sequence of `CreateModel` and `AddField` operations; `migrate` executes those operations against the database. The migration file is committed to version control, so every developer and CI/CD applies the same migrations in the same order. The `django_migrations` table in the database records which migrations have been applied — Django skips already-applied migrations and applies only the new ones.

Register the models with the admin site so they appear in the auto-generated admin UI:

```python
# polls/admin.py
from django.contrib import admin
from .models import Question, Choice


class ChoiceInline(admin.TabularInline):
    """Edit choices on the Question admin page (instead of separately)."""
    model = Choice
    extra = 3  # show 3 blank choice rows when adding a new question


@admin.register(Question)
class QuestionAdmin(admin.ModelAdmin):
    list_display = ("question_text", "pub_date", "was_published_recently")
    list_filter = ("pub_date",)
    search_fields = ("question_text",)
    fieldsets = [
        (None, {"fields": ["question_text"]}),
        ("Date information", {"fields": ["pub_date"]}),
    ]
    inlines = [ChoiceInline]
```

The `@admin.register(Question)` decorator (equivalent to `admin.site.register(Question, QuestionAdmin)`) tells Django's admin site to expose the `Question` model with the customised `QuestionAdmin` configuration. `list_display` controls which columns appear in the list view, `list_filter` adds a sidebar filter, `search_fields` adds a search box, `fieldsets` groups fields into sections on the edit form, `inlines` lets you edit related models on the same page. The admin UI is generated entirely from these declarations — no HTML, no JavaScript, no forms. It is the most distinctive feature of Django and the reason Django is the default choice for content-management back-ends.

Create an admin user so you can log in to the admin UI:

```bash

python manage.py createsuperuser

# or non-interactively (CI, scripts) via env vars:
```

After running `migrate` (which creates the `auth_user`, `auth_group`, `auth_permission` tables among others) and `createsuperuser`, you can start the dev server and log in:

```bash

```

A Django app is reusable — you can copy the `polls/` directory into another project, add it to `INSTALLED_APPS`, run `migrate`, and its models, views, and URLs work. This is how `django-rest-framework`, `django-celery-beat`, `django-allauth`, and the entire Django package ecosystem distribute functionality: as installable apps.

The failure mode here is the "app vs project" confusion. Beginners often put models in the project package (`mysite/models.py`) instead of in an app (`polls/models.py`) — this works but breaks reusability and confuses Django's app registry. The convention is: the project package (`mysite/`) contains only project-level concerns (settings, root URLconf, WSGI/ASGI entry points); every feature goes in an app (`polls/`, `users/`, `billing/`). A typical production Django project has 5–20 apps. The other failure mode is "I edited `models.py` but `migrate` says nothing to do" — you forgot to run `makemigrations` first. The fix is to run `makemigrations` after every model change; the CI pipeline should fail if `makemigrations --check --dry-run` reports missing migrations (catches a developer who edited models but forgot to commit the migration).

### Configuring `INSTALLED_APPS`, routing an HTTP view through URLconf, and serving a JSON response

A Django view is a callable that takes an `HttpRequest` and returns an `HttpResponse`. Views can be functions (`def health(request): ...`) or classes (`class HealthView(View): def get(self, request): ...`). For this anchor we use the function form for simplicity:

```python
# polls/views.py
from datetime import datetime, timezone
from django.http import HttpRequest, JsonResponse, HttpResponseNotAllowed
from django.views.decorators.http import require_http_methods
from django.shortcuts import get_object_or_404
from .models import Question, Choice


@require_http_methods(["GET"])
def health(request: HttpRequest) -> JsonResponse:
    """Health check endpoint."""
    return JsonResponse({
        "status": "ok",
        "timestamp": datetime.now(timezone.utc).isoformat(),
        "version": "1.0.0",
    })


@require_http_methods(["GET"])
def question_detail(request: HttpRequest, question_id: int) -> JsonResponse:
    """GET /api/questions/<id>/ — returns a question with its choices."""
    question = get_object_or_404(Question, pk=question_id)
    return JsonResponse({
        "id": question.id,
        "question_text": question.question_text,
        "pub_date": question.pub_date.isoformat(),
        "choices": [
            {"id": c.id, "choice_text": c.choice_text, "votes": c.votes}
            for c in question.choices.all()
        ],
    })


@require_http_methods(["POST"])
def vote(request: HttpRequest, question_id: int) -> JsonResponse:
    """POST /api/questions/<id>/vote/ — increments the chosen choice's vote count."""
    choice_id = request.POST.get("choice")
    if not choice_id:
        return JsonResponse({"error": "no choice provided"}, status=400)
    question = get_object_or_404(Question, pk=question_id)
    choice = get_object_or_404(Choice, pk=choice_id, question=question)
    choice.votes += 1
    choice.save(update_fields=["votes"])  # only UPDATE the votes column
    return JsonResponse({"id": choice.id, "votes": choice.votes})
```

```python
# polls/urls.py (create this file)
from django.urls import path
from . import views

urlpatterns = [
    path("health", views.health, name="health"),
    path("questions/<int:question_id>", views.question_detail, name="question_detail"),
    path("questions/<int:question_id>/vote", views.vote, name="vote"),
]
```

```python
# mysite/urls.py (root URLconf — already exists, edit it)
from django.contrib import admin
from django.urls import path, include

urlpatterns = [
    path("admin/", admin.site.urls),
    path("api/", include("polls.urls")),    # /api/health, /api/questions/<id>, ...
]
```

The request flows: `gunicorn` calls `application(environ, start_response)` → Django's WSGI handler creates an `HttpRequest` from the WSGI `environ` → Django runs the middleware chain (request phase) → Django resolves the URL (`/api/questions/5` matches `path("api/", include("polls.urls"))`, then `path("questions/<int:question_id>", views.question_detail)`) → Django calls `views.question_detail(request, question_id=5)` → the view loads the Question via `get_object_or_404` (which issues `SELECT * FROM polls_question WHERE id = 5`) and returns a `JsonResponse` → Django runs the middleware chain (response phase) → Django calls `start_response` with the status and headers → Django writes the response body to the WSGI server.

```text
  HTTP request: GET /api/questions/5
      │
      ▼
  gunicorn worker → WSGI handler (application callable)
      │
      ▼
  HttpRequest object created from WSGI environ
      │
      ▼
  Middleware: process_request (Security, Session, Common, CSRF, Auth, ...)
      │
      ▼
  URLResolver: matches "api/" → includes polls.urls
      │
      ▼
  URLResolver: matches "questions/<int:question_id>" → polls.views.question_detail
      │  (question_id=5 extracted from URL, converted to int by the converter)
      ▼
  View: question_detail(request, question_id=5)
      │
      ▼
  ORM: get_object_or_404(Question, pk=5)
      │  → SELECT * FROM polls_question WHERE id = 5 LIMIT 1
      │  → if no row: raise Http404 → caught by middleware → 404 response
      ▼
  question.choices.all()
      │  → SELECT * FROM polls_choice WHERE question_id = 5
      ▼
  JsonResponse({...}) → JSON serialised, Content-Type set
      │
      ▼
  Middleware: process_response (reverse order)
      │
      ▼
  HttpResponse → WSGI start_response + body
      │
      ▼
  gunicorn writes response to socket
```

The `@require_http_methods(["GET"])` decorator restricts the view to GET requests — a POST returns 405 Method Not Allowed. The `JsonResponse` class is a subclass of `HttpResponse` that JSON-serializes its first argument and sets `Content-Type: application/json`. It is the Django equivalent of Flask's `jsonify`. The `<int:question_id>` path converter is the Django equivalent of Flask's `<int:uid>` — it matches digits and converts them to a Python `int` before passing to the view.

The `python manage.py shell` command opens a Python REPL with Django's app registry loaded — every model is importable, every database query works, every setting is readable. It is the Django equivalent of Spring Boot's DevTools restart-classloader and of Rails' `rails console`. Use it for one-off data exploration, manual data fixes, and prototyping ORM queries you intend to put in a view. The `python manage.py dbshell` command drops you into the database's own CLI (`psql` for Postgres, `sqlite3` for SQLite) using the credentials from `DATABASES` — useful for inspecting the actual schema when the ORM lies.

```bash
#   (W614) SECURE_SSL_REDIRECT is not set
#   (W615) SECURE_HSTS_SECONDS is not set
```

The failure mode that catches Django newcomers is "DEBUG=True in production". Django's `DEBUG=True` setting renders detailed error pages with full stack traces, local variables, and SQL queries — catastrophic in production because it leaks source code, database schema, and secret keys. The fix is to read `DEBUG` from an environment variable (`DEBUG = os.environ.get("DJANGO_DEBUG", "False") == "True"`) and verify with `python manage.py check --deploy` before deploying. The `check --deploy` command runs a checklist of production-readiness warnings: `DEBUG` is False, `SECRET_KEY` is not the default, `ALLOWED_HOSTS` is not `*`, `SECURE_SSL_REDIRECT` is True, `SECURE_HSTS_SECONDS` is set, etc. Run it in CI and fail the build on any warning. The other recurring prod failure is "the migration was committed but not applied" — `python manage.py migrate` was run in dev but the CI/CD pipeline skipped it. The fix is to run `migrate` as the first step of every deploy (in the Docker entrypoint, in the systemd ExecStartPre, or in the Kubernetes init container) and to fail the deploy loudly if `python manage.py showmigrations --list` reports any `[ ]` (unapplied) migrations.

```python
# polls/models.py
import datetime
from django.db import models
from django.utils import timezone


class Question(models.Model):
    question_text = models.CharField(max_length=200)
    pub_date = models.DateTimeField("date published")

    def __str__(self) -> str:
        return self.question_text

    def was_published_recently(self) -> bool:
        return timezone.now() >= self.pub_date >= timezone.now() - datetime.timedelta(days=1)


class Choice(models.Model):
    question = models.ForeignKey(Question, on_delete=models.CASCADE, related_name="choices")
    choice_text = models.CharField(max_length=200)
    votes = models.IntegerField(default=0)

    def __str__(self) -> str:
        return self.choice_text
```

```python
# polls/views.py
from datetime import datetime, timezone
from django.http import HttpRequest, JsonResponse
from django.views.decorators.http import require_http_methods
from django.shortcuts import get_object_or_404
from .models import Question


@require_http_methods(["GET"])
def health(request: HttpRequest) -> JsonResponse:
    return JsonResponse({
        "status": "ok",
        "timestamp": datetime.now(timezone.utc).isoformat(),
        "version": "1.0.0",
    })


@require_http_methods(["GET"])
def question_detail(request: HttpRequest, question_id: int) -> JsonResponse:
    question = get_object_or_404(Question, pk=question_id)
    return JsonResponse({
        "id": question.id,
        "question_text": question.question_text,
        "pub_date": question.pub_date.isoformat(),
        "choices": [
            {"id": c.id, "choice_text": c.choice_text, "votes": c.votes}
            for c in question.choices.all()
        ],
    })
```

## Key Takeaways

1. **`django-admin startproject` + `python manage.py startapp` is the bootstrap.** The project package holds settings and root URLconf; each app holds its own models, views, admin, and URLconfs. Add every app to `INSTALLED_APPS` in `settings.py`. Define models as `models.Model` subclasses; `makemigrations` writes the migration file, `migrate` applies it, `createsuperuser` creates the admin user.
2. **`settings.py` is Python, not YAML — read environment variables for prod-vs-dev config.** Set `DJANGO_SETTINGS_MODULE` explicitly in production. Run `python manage.py check --deploy` in CI to catch `DEBUG=True`, weak `SECRET_KEY`, and missing security middleware. Run `migrate` as the first step of every deploy.
3. **A view is a callable that takes `HttpRequest` and returns `HttpResponse`.** `JsonResponse` returns JSON. Routes are declared in `urls.py` via `path()` and composed with `include()`. The admin UI is generated from `admin.py` registrations — no HTML or JS. Run with `gunicorn mysite.wsgi:application` (sync) or `uvicorn mysite.asgi:application` (async) in production, never with `python manage.py runserver`.
