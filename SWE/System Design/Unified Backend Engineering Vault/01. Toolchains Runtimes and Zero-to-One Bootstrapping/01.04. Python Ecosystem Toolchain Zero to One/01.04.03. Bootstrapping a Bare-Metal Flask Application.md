# 01.04.03. Bootstrapping a Bare-Metal Flask Application

## What This Is

This is the delta-flavoured anchor note for Flask — the Python equivalent of [[01.02.04. Bootstrapping a Bare-Metal Spring Boot Application]] and the sibling of [[01.03.04. Bootstrapping a Bare-Metal Express TypeScript Application]]. We bootstrap a Flask HTTP service from scratch: create a virtual environment, install Flask, write an `app.py` (or, for the larger `src/` layout, `src/myapp/__init__.py` with a `create_app()` factory) with a minimal route returning JSON via `jsonify`, and run it under both the Werkzeug development server and `gunicorn` for production WSGI serving. The result is a 30-line Python application that listens on port 5000 and answers `GET /health` with `{"status":"ok"}` — the same minimum viable service as the Spring Boot and Express anchors, expressed in CPython.

Flask is the delta choice for the Python anchor (rather than Django) because it is minimal: 3,000 lines of source, no ORM, no auth, no admin, no migrations, no opinions. Where Spring Boot gives you everything, Flask gives you nothing but routing — you wire the rest yourself. The lesson this note teaches that Spring Boot does not is the cost of being explicit: Flask does not have dependency injection, auto-configuration, or actuator; every cross-cutting concern is your responsibility. The contrast with Django (next note) is the inverse — Django is "batteries-included" to the same degree as Spring Boot, just with different defaults.

## The Details

### Installing Flask within an isolated virtual environment

The Flask package is `flask` on PyPI; it pulls in `Werkzeug` (WSGI utilities and dev server), `Jinja2` (templating), `itsdangerous` (signed cookies), `click` (CLI), and `markupsafe` (HTML escaping). Install it inside a virtual environment, never into the system Python (see [[01.04.01. Installing Python and Environment Isolation]]):

```bash
# create project directory
mkdir myapp && cd myapp

# create a venv
python -m venv .venv

# activate it (macOS/Linux)
source .venv/bin/activate

# activate it (Windows PowerShell)
.venv\Scripts\Activate.ps1

# upgrade pip and install Flask
pip install --upgrade pip
pip install flask

# verify
python -c "import flask; print(flask.__version__)"    # 3.0.3
flask --version                                        # Flask 3.0.3, Python 3.12.4
```

The Flask package exposes a `flask` CLI command (installed into `.venv/bin/flask` by the package's entry points). The CLI is the canonical way to run a dev server, run custom commands, and inspect routes. It reads the `FLASK_APP` environment variable to know which module contains the application object — `FLASK_APP=app` means "look for an `app` variable in `app.py`".

`python-dotenv` is the package that lets you commit environment variables to a checked-in file instead of typing them into every shell. Flask auto-loads two files: `.flaskenv` (for Flask-specific vars like `FLASK_APP` and `FLASK_DEBUG`, intended to be committed) and `.env` (for secrets like `DATABASE_URL` and `SECRET_KEY`, intended to be gitignored). Install it as a dependency:

```bash
pip install python-dotenv
```

```bash
# .flaskenv (committed to git)
FLASK_APP=myapp:create_app
FLASK_DEBUG=1

# .env (gitignored, contains secrets)
DATABASE_URL=postgresql://user:pass@localhost/myapp
SECRET_KEY=dev-only-not-for-production
```

When you run `flask run`, Flask looks for `.flaskenv` and `.env` in the current directory, loads them via `python-dotenv`'s `load_dotenv()` function, and only then reads `FLASK_APP`. The order matters: if `FLASK_APP` is set in `.flaskenv` but `DATABASE_URL` is in `.env`, both are loaded before the Flask app is imported, so the application code can read both via `os.environ`. The same mechanism is used by Django (via `django-environ`) and by FastAPI (via `pydantic-settings`); the convention is universal across the Python web ecosystem.

Freeze the dependencies to a `requirements.txt` so the install is reproducible:

```bash
pip freeze > requirements.txt
# requirements.txt:
#   blinker==1.8.2
#   click==8.1.7
#   flask==3.0.3
#   itsdangerous==2.2.0
#   jinja2==3.1.4
#   markupsafe==2.1.5
#   python-dotenv==1.0.1
#   werkzeug==3.0.4

# rebuild on another machine:
pip install -r requirements.txt
```

`pip freeze` captures exact versions but not hashes. For production supply-chain safety, use `pip-compile --generate-hashes` (see [[01.04.01. Installing Python and Environment Isolation]]). For this anchor, `requirements.txt` is sufficient.

The failure mode here is "I activated the wrong venv" or "I forgot to activate". The symptom is `ModuleNotFoundError: No module named 'flask'` even though you ran `pip install flask` last week. The fix is `which python; which pip` — if either points to `/usr/bin/python` or `/usr/local/bin/python` instead of `.venv/bin/python`, the venv is not active. The deeper fix is to use `direnv` (auto-activates on `cd`) or Poetry (manages the venv for you, `poetry run python` always uses the right one). A subtler failure mode is "the `.flaskenv` is not loaded because I ran `flask run` from a subdirectory" — Flask only searches the current directory for `.flaskenv`, not parent directories; always `cd` to the project root before invoking the CLI.

### Writing a clean `app.py` instantiation with explicit WSGI-compatible entry points

The Flask application object is created by calling `Flask(__name__)`. The `__name__` argument is the import name of the module — Flask uses it to locate resources relative to the package (templates, static files). Pass `__name__` always; passing a hardcoded string breaks static file resolution when the module is imported under a different name.

```python
# app.py — single-file Flask app (the simplest layout)
from flask import Flask, jsonify, request

app = Flask(__name__)


@app.get("/health")
def health():
    """Health check endpoint — returns JSON status."""
    return jsonify({
        "status": "ok",
        "timestamp": __import__("datetime").datetime.utcnow().isoformat(),
        "version": "1.0.0",
    })


@app.post("/users")
def create_user():
    data = request.get_json(silent=True)
    if not data or "name" not in data or "email" not in data:
        return jsonify({"error": "name and email are required"}), 400

    # In a real app: validate email format, check for duplicates, persist
    import uuid
    user = {"id": str(uuid.uuid4()), "name": data["name"], "email": data["email"]}
    return jsonify(user), 201


@app.errorhandler(404)
def not_found(error):
    return jsonify({"error": "not found"}), 404


@app.errorhandler(500)
def server_error(error):
    app.logger.exception("Unhandled exception")
    return jsonify({"error": "internal server error"}), 500


if __name__ == "__main__":
    app.run(host="0.0.0.0", port=5000, debug=True)
```

For any project larger than a single file, the **application factory pattern** is the Flask idiom: a `create_app()` function that constructs and returns the `Flask` instance, with routes registered inside it. The factory pattern is mandatory for running the same app under multiple configurations (test, dev, prod), for loading configuration from environment variables at construction time, and for writing integration tests that need a fresh app per test. The `flask --app myapp:create_app run` CLI invokes the factory and runs the returned app.

```python
# src/myapp/__init__.py — application factory pattern
from flask import Flask, jsonify
from .config import Config
from .routes.health import health_bp
from .routes.users import users_bp


def create_app(config_class: type[Config] = Config) -> Flask:
    """Application factory — constructs a Flask app with all blueprints registered."""
    app = Flask(__name__)
    app.config.from_object(config_class)

    # register blueprints (modular route groups)
    app.register_blueprint(health_bp)
    app.register_blueprint(users_bp, url_prefix="/api/users")

    # error handlers — must be registered after blueprints
    @app.errorhandler(404)
    def not_found(error):
        return jsonify({"error": "not found"}), 404

    @app.errorhandler(500)
    def server_error(error):
        app.logger.exception("Unhandled exception")
        return jsonify({"error": "internal server error"}), 500

    return app
```

```python
# src/myapp/config.py — configuration classes (one per environment)
import os
from dataclasses import dataclass

@dataclass
class Config:
    SECRET_KEY: str = os.environ.get("SECRET_KEY", "dev-only")
    SQLALCHEMY_DATABASE_URI: str = os.environ.get("DATABASE_URL", "sqlite:///app.db")
    SQLALCHEMY_TRACK_MODIFICATIONS: bool = False

@dataclass
class ProductionConfig(Config):
    DEBUG: bool = False

@dataclass
class DevelopmentConfig(Config):
    DEBUG: bool = True
```

```python
# src/myapp/routes/health.py — Blueprint with the health route
from flask import Blueprint, jsonify
from datetime import datetime, timezone

health_bp = Blueprint("health", __name__)


@health_bp.get("/health")
def health():
    return jsonify({
        "status": "ok",
        "timestamp": datetime.now(timezone.utc).isoformat(),
    })
```

```python
# src/myapp/routes/users.py — Blueprint for the /api/users subtree
from flask import Blueprint, jsonify, request
import uuid

users_bp = Blueprint("users", __name__)

# in-memory store — replace with a database in production
USERS: dict[str, dict] = {}


@users_bp.get("/<uuid:uid>")
def get_user(uid: uuid.UUID):
    user = USERS.get(str(uid))
    if user is None:
        from werkzeug.exceptions import NotFound
        raise NotFound(f"user {uid} not found")
    return jsonify(user)


@users_bp.post("/")
def create_user():
    data = request.get_json(silent=True)
    if not data or "name" not in data or "email" not in data:
        return jsonify({"error": "name and email are required"}), 400
    user = {"id": str(uuid.uuid4()), "name": data["name"], "email": data["email"]}
    USERS[user["id"]] = user
    return jsonify(user), 201
```

A **Blueprint** is Flask's mechanism for grouping related routes into a reusable module. The Blueprint object is created with `Blueprint("users", __name__)` and routes are registered on it via the same `@blueprint.get(...)` decorator syntax. The blueprint itself is not mounted until `app.register_blueprint(users_bp, url_prefix="/api/users")` is called inside `create_app()` — at which point every route in the blueprint gets the `url_prefix` prepended. This is the Flask equivalent of Spring Boot's `@RequestMapping("/api/users")` at the controller class level. The `url_prefix` lets you mount the same blueprint at different paths in different environments (e.g. `/api/v1/users` in one app, `/api/v2/users` in another), and it lets third-party Flask extensions (Flask-RESTful, Flask-API, Flask-Security) ship their routes as installable blueprints.

The `app.config.from_object(config_class)` call copies every uppercase attribute of the class into `app.config` — a dict-like object accessed via `app.config["SECRET_KEY"]`. This is the Flask equivalent of Spring Boot's `@ConfigurationProperties` — a typed, environment-aware configuration object that the rest of the application reads from.

The `if __name__ == "__main__":` block (see [[01.04.02. Python Execution Model and Module System]]) runs the dev server when you execute `python app.py` directly. It does NOT run when you import `app` (e.g. from gunicorn). This is critical: gunicorn imports the `app` object and serves it via WSGI; it never calls `app.run()`. The dev server `app.run()` is for development only — it should never serve production traffic. For the factory pattern, the equivalent entry point is a `wsgi.py` file:

```python
# src/myapp/wsgi.py — WSGI entry point for gunicorn
from myapp import create_app
app = create_app()
```

```bash
# gunicorn invokes: gunicorn myapp.wsgi:app --bind 0.0.0.0:8000 --workers 4
```

The WSGI entry point is the `app` object itself. A WSGI server (gunicorn, uWSGI, mod_wsgi) calls `app(environ, start_response)` for each request, where `environ` is a dict of CGI-style environment variables (`REQUEST_METHOD`, `PATH_INFO`, `QUERY_STRING`, `HTTP_*` headers) and `start_response` is a callable that sets the response status and headers. Flask's `Flask` class implements `__call__` to satisfy this protocol — that is why `gunicorn app:app` works (it imports `app` from `app.py` and calls it as a WSGI app).

The failure mode here is the "leaky traceback" incident. Flask's debug mode (`debug=True`) renders full Python tracebacks in the browser when an exception occurs, including local variables, source code snippets, and an interactive console (Werkzeug's debugger). This is invaluable in development and catastrophic in production — the interactive console allows arbitrary code execution from the browser. Never run with `debug=True` in production; the environment variable `FLASK_DEBUG=1` is the same as `debug=True` and equally dangerous. The deeper defence is `app.config["PROPAGATE_EXCEPTIONS"] = False` (the default in production mode), which makes Flask catch exceptions and route them to the `@app.errorhandler(500)` handler. A common production bug is `FLASK_DEBUG=1` left in the `.env` file that gets deployed with the image — verify with `print(app.config["DEBUG"])` at startup and fail fast if it's `True` in a production-named environment.

### Defining a basic dynamic route returning JSON via `jsonify`

Flask's routing is built on Werkzeug's `Map` and `Rule` classes. Each `@app.route(...)` decorator creates a `Rule` and adds it to the `Map`; the `Map` is compiled into a routing matcher on first request. URL matching is done by trying rules in registration order and returning the first match.

```python
from flask import Flask, jsonify, request

app = Flask(__name__)

# Static route
@app.get("/health")
def health():
    return jsonify({"status": "ok"})

# Dynamic route with int converter
@app.get("/users/<int:uid>")
def get_user(uid: int):
    user = find_user(uid)   # hypothetical lookup
    if user is None:
        from werkzeug.exceptions import NotFound
        raise NotFound(f"user {uid} not found")
    return jsonify(user)

# Dynamic route with string converter (default)
@app.get("/users/<name>")
def get_user_by_name(name: str):
    return jsonify({"name": name})

# Dynamic route with path converter (matches slashes)
@app.get("/files/<path:subpath>")
def serve_file(subpath: str):
    return jsonify({"requested": subpath})
```

The converters are: `string` (default, matches any text without slashes), `int` (matches positive integers), `float` (matches positive floats), `path` (matches any text including slashes), `uuid` (matches UUID strings). The matched value is converted to the appropriate Python type and passed as a keyword argument to the view function. A converter mismatch causes Flask to skip the rule and try the next one — `GET /users/abc` does not match `/users/<int:uid>` (because `abc` is not an int) but does match `/users/<name>`.

```bash
$ curl http://localhost:5000/users/42
{"id": 42, "name": "Alice"}

$ curl http://localhost:5000/users/abc
{"name": "abc"}

$ curl http://localhost:5000/users/42/
404 Not Found         ← trailing slash not allowed by default

$ curl http://localhost:5000/files/docs/readme.txt
{"requested": "docs/readme.txt"}
```

The `jsonify` function does several things: (1) converts the Python object to a JSON string with `json.dumps(obj, indent=None, separators=(",", ":"))`, (2) creates a `Response` object with that string as the body, (3) sets `Content-Type: application/json`, (4) sets `Content-Length`, (5) returns the response. The compact JSON (no spaces around separators) is a Flask default — pass `app.json.compact = False` (Flask 2.3+) to get pretty-printed JSON in development.

The reason to use `jsonify` instead of `json.dumps` directly is the `Content-Type` header. If you `return json.dumps({"status": "ok"})`, Flask returns the string with `Content-Type: text/html; charset=utf-8` (the default for string returns) — and a client that does `response.json()` (which checks the Content-Type) will fail. Always use `jsonify` (or return a dict — Flask 2.0+ auto-jsonifies dicts).

```python
# Modern Flask 2.0+ shorthand: just return a dict
@app.get("/health")
def health():
    return {"status": "ok"}    # Flask auto-converts to a JSON Response
```

The `url_prefix` on a Blueprint interacts with the route path in a non-obvious way: the blueprint's `url_prefix` is prepended *before* the rule, but the rule's leading slash is stripped. So `users_bp.get("/<uuid:uid>")` mounted at `url_prefix="/api/users"` produces the final URL `/api/users/<uuid:uid>` — not `/api/users//<uuid:uid>`. The same normalisation applies to the root rule: `users_bp.get("/")` mounted at `/api/users` produces `/api/users/` (with trailing slash, which Werkzeug will redirect to `/api/users` by default — the trailing-slash surprise from the previous paragraph). The clean convention is: blueprint routes that match a resource collection use `"/"` (mapped to `url_prefix` itself), routes that match a single resource use `"/<id>"` (mapped to `url_prefix/<id>`), and the `url_prefix` itself never ends in a slash.

The failure mode here is the "trailing slash redirect" surprise. `@app.route("/users")` (no trailing slash) returns 404 for `/users/` (with trailing slash). `@app.route("/users/")` (with trailing slash) returns 308 Permanent Redirect from `/users` to `/users/`. The redirect breaks clients that POST without following redirects — a POST to `/users` becomes a GET to `/users/` (the body is dropped), and the handler sees an empty body. The fix is to be consistent: pick one convention (no trailing slash is the API norm) and stick to it. The Werkzeug rule `strict_slashes=False` disables the redirect and matches both forms.

### Running the Flask application via development servers and production WSGI servers (`gunicorn`)

Flask ships with the Werkzeug development server, which is single-threaded, single-process, and restarts on file changes. It is suitable for development only — it cannot handle concurrent requests, it has no graceful shutdown, and it leaks memory on long-running requests. Production Flask apps run under a WSGI server: `gunicorn` (the most popular, written in Python), `uWSGI` (the most configurable, written in C), or `mod_wsgi` (Apache module).

```bash
# ─── Development: Werkzeug dev server ─────────────────────────
# Option A: use the flask CLI (loads .flaskenv automatically)
export FLASK_APP=app
export FLASK_DEBUG=1
flask run --host=0.0.0.0 --port=5000
# * Serving Flask app 'app'
# * Debug mode: on
# * Running on http://0.0.0.0:5000
# * Restarting with stat
# * Debugger is active!
# * Debugger PIN: 123-456-789

# Option B: with the factory pattern, point FLASK_APP at the factory
export FLASK_APP="myapp:create_app"
flask run

# Option C: run app.py directly (calls app.run in the __main__ block)
python app.py

# ─── Production: gunicorn ─────────────────────────────────────
pip install gunicorn

# 4 worker processes, default sync worker, bind to port 8000
# For the single-file app.py layout:
gunicorn app:app --bind 0.0.0.0:8000 --workers 4

# For the factory pattern (src/myapp/), use the wsgi.py entry point:
gunicorn myapp.wsgi:app --bind 0.0.0.0:8000 --workers 4

# Or invoke the factory directly (gunicorn supports the () syntax):
gunicorn "myapp:create_app()" --bind 0.0.0.0:8000 --workers 4

# with uvloop (faster event loop) and httptools (faster HTTP parser)
gunicorn myapp.wsgi:app --bind 0.0.0.0:8000 --workers 4 \
    --worker-class uvicorn.workers.UvicornWorker \
    --worker-tmp-dir /dev/shm

# with gevent (for high-concurrency I/O-bound workloads)
pip install gevent
gunicorn myapp.wsgi:app --bind 0.0.0.0:8000 --workers 4 \
    --worker-class gevent --worker-connections 1000

# graceful reload on SIGHUP (zero-downtime deploy)
kill -HUP $(cat gunicorn.pid)
```

The `app:app` argument tells gunicorn to import the `app` object from the `app` module (i.e. `app.py`). The format is `<module>:<variable>`. For a package layout where the app object is in `myapp/wsgi.py`, the spec is `myapp.wsgi:app`. For a factory, the spec is `myapp:create_app()` (with parentheses to invoke the factory). gunicorn forks the specified number of worker processes (default 4, recommended formula `2 * CPU + 1`) and load-balances incoming requests across them. Each worker is a separate Python process with its own GIL, so 4 workers can use 4 CPU cores.

```text
  Production Flask architecture (gunicorn + sync workers):

                   ┌────────────────────┐
                   │  gunicorn master   │
                   │  (PID 1 in Docker) │
                   │   binds :8000      │
                   └────────┬───────────┘
                            │ fork()
              ┌─────────────┼─────────────┐
              │             │             │
         ┌────▼────┐   ┌────▼────┐   ┌────▼────┐
         │ worker 1│   │ worker 2│   │ worker N│   (4 processes)
         │  Flask  │   │  Flask  │   │  Flask  │
         │  app    │   │  app    │   │  app    │
         └────┬────┘   └────┬────┘   └────┬────┘
              │             │             │
              ▼             ▼             ▼
            [PostgreSQL connection pool, one per worker]
```

The choice of worker class determines the concurrency model:

- **`sync`** (default): one request at a time per worker. Simple, correct, but blocks on slow I/O. Use for CPU-bound or low-concurrency workloads. 4 workers = 4 concurrent requests.
- **`gevent`** (or `eventlet`): cooperative coroutines via monkey-patching. One worker handles thousands of concurrent connections by yielding on I/O. Use for I/O-bound workloads (proxies, websockets, slow upstream services). Requires `gevent.monkey.patch_all()` to be called before any other import — gunicorn does this automatically when `--worker-class gevent` is set.
- **`uvicorn.workers.UvicornWorker`**: ASGI worker for async Flask (Flask 2.0+ supports async views). Uses uvloop (a faster event loop) and httptools. Use only if you have `async def` views; otherwise sync is simpler and faster.

The `--worker-tmp-dir /dev/shm` flag is a performance optimization. gunicorn workers write a heartbeat file to a temp directory every second; the master checks the heartbeat to detect hung workers. If the temp directory is on disk (the default `/tmp` on most filesystems), the heartbeat write is a `fsync` syscall that blocks the worker. Putting the temp directory on tmpfs (`/dev/shm` is a ramfs on Linux) makes the heartbeat write essentially free. This is a real, measurable 5–10% throughput improvement on high-traffic services.

The failure mode that distinguishes dev from prod is the "works in dev, hangs in prod" bug. The Werkzeug dev server is single-threaded but uses no connection pool — every request opens a fresh database connection, runs the query, and closes it. Under gunicorn with 4 sync workers, 4 concurrent requests open 4 database connections; if your DB pool is sized for 2, the third request hangs waiting for a connection. The fix is to size the DB pool to `max_connections = workers * threads_per_worker`, and to set `--timeout 30` (gunicorn's default is 30 seconds) so hung requests are killed and logged rather than blocking forever.

The other prod failure mode is the "no graceful shutdown" incident. `gunicorn`'s default `--timeout 30` kills workers that take longer than 30 seconds to respond, but the kill is `SIGKILL` (no cleanup). Set `--graceful-timeout 30` so workers get `SIGTERM` first, finish in-flight requests, and exit cleanly. Kubernetes rolling deploys rely on this — `kubectl delete pod` sends `SIGTERM` to PID 1, gunicorn forwards it to workers, workers finish current requests, then exit. Without graceful shutdown, in-flight requests are dropped on every deploy. The Flask `teardown_appcontext` and `teardown_request` hooks run during this drain phase — use them to release database connections and close file handles explicitly, because Python's garbage collector is not guaranteed to run before the worker exits.

# in-memory store (replace with a real database in production)
USERS: dict[str, dict] = {}


@users_bp.get("/<uuid:uid>")
def get_user(uid: uuid.UUID):
    user = USERS.get(str(uid))
    if user is None:
        raise NotFound(f"user {uid} not found")
    return jsonify(user)


@users_bp.post("/")
def create_user():
    data = request.get_json(silent=True)
    if not data or "name" not in data or "email" not in data:
        return jsonify({"error": "name and email are required"}), 400
    user = {"id": str(uuid.uuid4()), "name": data["name"], "email": data["email"]}

## Key Takeaways

1. **`Flask(__name__)` creates the WSGI app; `@app.route` registers handlers; `jsonify()` returns JSON responses.** For projects larger than one file, use the application factory pattern — `create_app()` returns a configured `Flask` instance; blueprints modularise routes; `pip install -e .` makes the package importable. `python-dotenv` + `.flaskenv` commit `FLASK_APP` to the repo; `.env` holds secrets (gitignored).
2. **Never run with `debug=True` in production — the Werkzeug debugger allows arbitrary code execution from the browser.** Use `@app.errorhandler(Exception)` to catch unhandled exceptions and return JSON 500s. Verify `app.config["DEBUG"]` is `False` at startup in prod-named environments.
3. **gunicorn with sync workers (`--workers 4`) is the default production setup.** Use `gevent` workers for I/O-bound workloads, `uvicorn` for async views. Set `--graceful-timeout 30` and `--worker-tmp-dir /dev/shm` for clean shutdowns and 5–10% throughput gain. For the factory pattern, gunicorn invokes `myapp:create_app()` or imports `myapp.wsgi:app`.
