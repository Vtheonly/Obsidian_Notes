# 01.04.02. Python Execution Model and Module System

## What This Is

CPython, the reference Python implementation, is a bytecode interpreter. When you run `python hello.py`, CPython reads the source file, parses it into an AST, compiles the AST to bytecode (a stack-machine instruction set defined in `Include/opcode.h`), and executes the bytecode in an evaluation loop. The bytecode is cached on disk as a `.pyc` file under `__pycache__/` so the next run skips the parse-and-compile step. Python's module system — the `import` statement — sits on top of this: every `.py` file is a module, every directory with an `__init__.py` is a package, and the import machinery (`sys.modules` cache + meta path finders + path-based loaders) controls how module names resolve to files. This note walks the execution pipeline, the `__name__ == "__main__"` guard, the `.pyc` cache invalidation rules, the import system's finders and loaders, and the `from __future__ import annotations` directive that has become load-bearing for Python's typing story. The Python execution model is the foundation for every Flask and Django app — without it, the difference between a script and a module, the `__main__` guard, and the package layout that makes `from myapp.views import users` work are all black magic.

The note sits at the same conceptual layer as [[01.01.01. Language Execution Models]] (which covers the AOT/JIT/interpreter spectrum) — Python is a bytecode interpreter that caches its bytecode, which is the third of the three execution models in that note. The failure modes this note governs are the ones that surface as `ModuleNotFoundError: No module named 'myapp'` (sys.path issue), `ImportError: attempted relative import with no known parent package` (running a module as a script), `SyntaxError: invalid syntax` from a stale `.pyc` after a Python upgrade, or the classic "I installed the package but `python -c "import it"` says it is not there" (different Python).

## The Details

### Writing and running a bare-metal `hello.py` via the `python` interpreter

The simplest possible Python program is a single file with one `print` statement:

```python
# hello.py
def greet(name: str) -> str:
    return f"Hello, {name}!"

if __name__ == "__main__":
    import sys
    name = sys.argv[1] if len(sys.argv) > 1 else "world"
    print(greet(name))
```

Run it from the terminal:

```bash
$ python hello.py Alice
Hello, Alice!

$ python hello.py
Hello, world!
```

What happens between the shell invoking `python hello.py` and the terminal printing "Hello, Alice!" is a multi-stage pipeline. First, the CPython interpreter boots: it initializes the runtime, sets up the GIL (Global Interpreter Lock — a mutex that serializes bytecode execution across threads), creates the `builtins` module, and parses command-line arguments. Then it opens `hello.py`, reads the source bytes, decodes them as UTF-8, and runs them through the lexer/parser to produce an AST. The AST is compiled to bytecode — a sequence of opcodes like `LOAD_NAME`, `CALL_FUNCTION`, `POP_TOP`, `RETURN_VALUE`. The bytecode is then executed in the eval loop, a giant `switch` statement in `Python/ceval.c` that dispatches on the opcode number.

```text
  python hello.py Alice
        │
        ▼
  ┌─────────────────────────────────┐
  │  CPython runtime initialization │
  │  - GIL                           │
  │  - sys module                    │
  │  - builtins module               │
  │  - sys.path setup                │
  └─────────────┬───────────────────┘
                │
                ▼
  ┌─────────────────────────────────┐
  │  Read hello.py                   │
  │  Decode UTF-8 → str              │
  └─────────────┬───────────────────┘
                │
                ▼
  ┌─────────────────────────────────┐
  │  Tokenizer (Parser/tokenize.c)   │
  │  source → tokens                 │
  └─────────────┬───────────────────┘
                │
                ▼
  ┌─────────────────────────────────┐
  │  Parser (Parser/parser.c)        │
  │  tokens → AST                    │
  │  (PEG parser since Python 3.9)   │
  └─────────────┬───────────────────┘
                │
                ▼
  ┌─────────────────────────────────┐
  │  Compiler (Python/compile.c)     │
  │  AST → bytecode (CodeType obj)   │
  │  - also writes __pycache__/      │
  │    hello.cpython-312.pyc         │
  └─────────────┬───────────────────┘
                │
                ▼
  ┌─────────────────────────────────┐
  │  Eval loop (Python/ceval.c)      │
  │  bytecode → execute              │
  │  - LOAD_NAME, CALL, etc.         │
  │  - sys.argv = ["hello.py", ...]  │
  │  - __name__ = "__main__"         │
  └─────────────┬───────────────────┘
                │
                ▼
  "Hello, Alice!" printed to stdout
```

The bytecode itself is inspectable with the `dis` module:

```python
>>> import dis
>>> def greet(name): return f"Hello, {name}!"
>>> dis.dis(greet)
  1           0 RESUME                   0
              2 LOAD_CONST               1 ('Hello, ')
              4 LOAD_FAST                0 (name)
              6 FORMAT_SIMPLE
              8 BUILD_STRING             2
             10 RETURN_VALUE
```

The opcodes here are `LOAD_CONST` (push the string `"Hello, "` onto the value stack), `LOAD_FAST` (push the local variable `name`), `FORMAT_SIMPLE` (convert to str), `BUILD_STRING` (concatenate), `RETURN_VALUE` (pop and return). Each opcode is one or two bytes; the numbers in the left column are byte offsets.

Two Python versions differ in their bytecode format — Python 3.11 introduced the `MAKE_CELL`, `COPY_FREE_VARS`, and `RESUME` opcodes as part of the "adaptive interpreter" (PEP 659), and Python 3.12 added specialized opcodes like `LOAD_FAST_BORROW`. This is why a `.pyc` file compiled with Python 3.11 cannot be loaded by Python 3.12 — the opcode numbers do not match. The "magic number" at the start of every `.pyc` file (a 4-byte value identifying the bytecode format version) makes this explicit.

The `from __future__ import annotations` directive (PEP 563) is a special compiler flag that changes how Python evaluates type annotations. By default, Python evaluates annotations eagerly at module-import time — `def greet(name: str) -> str:` resolves `str` to the `str` builtin and stores it in `greet.__annotations__["name"]`. With `from __future__ import annotations`, the compiler does not evaluate the annotation expressions at all — it stores them as the *string* `"str"` instead. This deferred evaluation is what lets you write annotations that reference classes not yet defined (forward references), use complex generic types like `list[User] | None` without quoting, and avoid importing heavy modules just for typing:

```python
# Without __future__ annotations — fails with NameError on User
def create_user(data: dict) -> User:    # User not defined yet!
    ...
class User: ...

# With __future__ annotations — annotation stored as "User" string,
# resolved only if something calls typing.get_type_hints(create_user)
from __future__ import annotations
def create_user(data: dict) -> User:    # works!
    ...
class User: ...
```

This directive was supposed to become the default in Python 3.10 (PEP 563), but the Python steering council deferred it indefinitely at the last minute because it broke runtime introspection tools (Pydantic V1, FastAPI's older versions, anything that calls `typing.get_type_hints()` to resolve annotations). The current recommendation is: add `from __future__ import annotations` to every new module — it lets you use forward references and modern syntax without the runtime cost — but be aware that any tool that calls `get_type_hints()` will need to resolve the strings, which means the names must be importable at that point. Python 3.14 (planned for 2025) is expected to make this the default via PEP 649 / PEP 749 (lazy annotations via descriptor protocol).

The production failure mode here is "works on my laptop, fails in CI" because the developer's Python is 3.12 and CI's Python is 3.11. The symptom is `SyntaxError: invalid syntax` for syntax that 3.12 added (e.g. the `type X = int` statement from PEP 695) or `ImportError` from a `.pyc` cached locally but stale in CI. The fix is to pin Python in both places via `.python-version` (see [[01.04.01. Installing Python and Environment Isolation]]) and to delete `__pycache__/` directories before deploying (or set `PYTHONDONTWRITEBYTECODE=1` to disable bytecode caching entirely — useful in Docker images where the bytecode is regenerated on every build anyway).

### Understanding the `__name__ == "__main__"` execution guard

The `if __name__ == "__main__":` block is the Python idiom for "this code runs only when the file is executed as a script, not when it is imported as a module". It exists because Python has no separate "script" vs "module" distinction — every `.py` file is a module, and the same file can be either run directly or imported.

When you run `python hello.py`, CPython sets the `__name__` global of the executing module to the string `"__main__"`. When you `import hello` from another module, CPython sets `hello.__name__` to `"hello"`. The `if __name__ == "__main__":` check distinguishes the two cases:

```python
# hello.py
def greet(name): return f"Hello, {name}!"

print("this runs on both run and import")

if __name__ == "__main__":
    print("this runs only on `python hello.py`")
    import sys
    print(greet(sys.argv[1] if len(sys.argv) > 1 else "world"))
```

```bash
$ python hello.py Alice
this runs on both run and import
this runs only on `python hello.py`
Hello, Alice!

$ python -c "import hello"
this runs on both run and import

# Note: the __main__ block did NOT execute on import.
```

The reason this matters is that Python modules often contain both reusable functions (which should be importable) and demo/test code (which should only run when invoked directly). Without the `__main__` guard, importing `hello` would also execute `print(greet(sys.argv[1]))` — which would crash if `sys.argv` was empty, or print unwanted output, or even start an HTTP server that blocks the import.

The guard is also where `sys.argv` parsing happens. When you run `python hello.py Alice`, `sys.argv` is `["hello.py", "Alice"]` — the first element is the script name, the rest are arguments. When `hello` is imported, `sys.argv` is whatever the importing script's argv was (usually `[""]` for the REPL, or the importing script's path). The `__main__` guard ensures `sys.argv` parsing only happens when the module is the entry point.

A subtler use of the guard is in `__main__.py` files. When you run a package with `python -m myapp`, Python executes `myapp/__main__.py`. That file's `__name__` is `"__main__"` (because it is the entry point), and any code at module level in it runs — no `if __name__ == "__main__":` check needed because `__main__.py` is never imported, only executed. This is how `python -m http.server`, `python -m json.tool`, and `python -m pip` work — they all have a `__main__.py` in their package.

```text
  python hello.py            → hello.__name__ = "__main__"
  python -m hello            → hello.__name__ = "__main__"  (run as module)
  python -m myapp            → myapp/__main__.py runs, its __name__ = "__main__"
  python -c "import hello"   → hello.__name__ = "hello"     (imported, not run)
```

The distinction between `python hello.py` (script mode) and `python -m hello` (module mode) is one of the most consequential differences in Python, and it matters whenever a file uses relative imports or expects `__package__` to be set. In script mode (`python hello.py`), Python sets `hello.__name__` to `"__main__"` and `__package__` to `None` (or `""`) — the file is treated as a top-level script with no parent package. In module mode (`python -m hello`), Python sets `hello.__name__` to `"__main__"` *but* also sets `__package__` to `""` (top-level module) or `"myapp.views"` (sub-module), preserving the package context. This is why `python -m myapp.views.users` works when `python myapp/views/users.py` does not: relative imports like `from ..models import User` require `__package__` to know where "up one level" is, and only `python -m` sets `__package__` correctly. The same logic applies to `python -m pytest` vs `python /path/to/pytest/main.py`: the former resolves pytest's internal relative imports; the latter breaks them. The rule is: **for any module that lives inside a package, invoke it with `python -m` from the project root, never `python path/to/file.py`**.

The failure mode that the `__main__` guard prevents is the "import side effect" bug. A module that does `app.run(host="0.0.0.0", port=5000)` at top level (without the guard) starts an HTTP server every time it is imported — including when a test file imports it, blocking the test runner. The Flask convention `if __name__ == "__main__": app.run(...)` exists precisely so that `flask_app.py` can be both imported by `gunicorn` (which calls `app` directly) and run as `python flask_app.py` (which calls `app.run`).

### CPython Bytecode caching: The creation, validation, and invalidation of `__pycache__` and `.pyc` files

Compiling Python source to bytecode takes time — for a moderately-sized project, 100 ms or more. To avoid recompiling on every run, CPython caches the compiled bytecode as `.pyc` files under a `__pycache__/` directory next to the source. The next time the module is imported, Python loads the `.pyc` instead of recompiling.

```bash
$ python hello.py
$ ls __pycache__/
hello.cpython-312.pyc

# the filename is: <module>.cpython-<major><minor>.pyc
# the "cpython-312" tag identifies the interpreter that produced it
```

The `.pyc` file is a binary file with a specific format:

```text
  Offset  Length  Content
  ──────  ──────  ───────────────────────────────────────
  0       4       Magic number (identifies bytecode version)
  4       4       Bit field (Python 3.7+: includes hash flag)
  8       4       Source modification time (mtime) OR hash
  12      4       Source size in bytes
  16      ...     Marshalled CodeType object
```

The first 16 bytes are the header. The magic number is a 2-byte value identifying the bytecode format (e.g. `0x6f0d` for Python 3.12) followed by `\r\n`. The mtime (or hash, depending on the invalidation mode) and source size are how Python decides whether the `.pyc` is still valid.

The invalidation algorithm is one of two modes, controlled by `--check-source-hash` or the `PYTHONDONTWRITEBYTECODE`/`PYTHONPYCACHEPREFIX` env vars:

- **Timestamp mode** (default): the `.pyc` is valid if the source file's mtime matches the mtime recorded in the `.pyc` header AND the source file's size matches. If either differs, the `.pyc` is regenerated. The flaw: if you edit the source and then `touch -t` it back to the original mtime, the `.pyc` will not be regenerated and Python will run stale bytecode.
- **Hash mode** (opt-in via `--check-source-hash` or setting `invalidation_mode` in the source): the `.pyc` is valid if the sha-256 hash of the source file matches the hash recorded in the header. Slower to validate (must hash the whole source on every import) but immune to mtime manipulation.

```bash
# force hash-based invalidation
python -X pycache_mode=hash hello.py

# or with the env var
export PYTHONDONTWRITEBYTECODE=1     # disable .pyc writing entirely
python hello.py                       # parses + compiles on every run

# or set a custom pycache location (useful for read-only filesystems)
export PYTHONPYCACHEPREFIX=/tmp/pycache
python hello.py                       # writes /tmp/pycache/.../hello.cpython-312.pyc
```

The bytecode version magic is the most common reason a `.pyc` is rejected. Python 3.12's magic number is different from 3.11's, so a `.pyc` produced by 3.11 is silently ignored by 3.12 (Python recompiles the source). This is why you can copy a Python project between machines with different Python versions and it still works — the stale `.pyc` files are simply not loaded.

The failure mode this exposes is the "stale `.pyc` after a Python upgrade" bug. You upgrade Python from 3.11 to 3.12, the upgrade happens to preserve the existing `__pycache__/` directory (e.g. in a Docker layer cache), and the next run fails with `ImportError: bad magic number in 'hello': expected ...`. The fix is `find . -name __pycache__ -exec rm -rf {} +` to delete all bytecode caches after the upgrade, or `python -B` (which sets `PYTHONDONTWRITEBYTECODE`) to disable caching during the migration. The same bug occurs with `pip install --editable .` (egg-link installs) when the source moves but the `.egg-info` directory stays — the `.pth` file points at the old location, and the stale `.pyc` files mask the move.

The deeper failure mode is in Docker builds. A multi-stage Dockerfile that copies `requirements.txt` first, installs dependencies, then copies `src/` produces a layer with `__pycache__/` from the dependency install but no source — when the source is added in the next layer, every import recompiles. The fix is to add `PYTHONDONTWRITEBYTECODE=1` to the Dockerfile to disable caching (the runtime cost is negligible for a long-running server, which only compiles once at startup). For read-only-rootfs deployments (Kubernetes `readOnlyRootFilesystem: true`), you must either set `PYTHONDONTWRITEBYTECODE=1` or set `PYTHONPYCACHEPREFIX=/tmp` to a writable tmpfs mount, because Python cannot write `.pyc` files next to read-only source. A service that starts fine in development (writable filesystem) and fails to import on Kubernetes (read-only filesystem) with `OSError: [Errno 30] Read-only file system: '__pycache__'` is hitting this exact issue.

The isolation-tier taxonomy from [[01.04.01. Installing Python and Environment Isolation]] directly affects `.pyc` behaviour. In a **venv**, `.pyc` files live next to the source in the project tree (or in the venv's `site-packages/`) and are owned by you. In a **container**, `.pyc` files are baked into the Docker image layer at `pip install` time and never recompiled — the `PYTHONDONTWRITEBYTECODE=1` recommendation is universal here. With **pipx**-installed CLI tools, the `.pyc` files live in `~/.local/pipx/venvs/<tool>/lib/python3.XX/site-packages/` — and a Python upgrade that breaks the magic number silently breaks every pipx-installed tool until you `pipx reinstall-all`. The defence is to make Python upgrades a deliberate, system-wide event that triggers a `pipx reinstall-all` and a re-build of every project's venv.

### Python's import system: `sys.path`, packages, modules, and `__init__.py` initialization mechanics

The `import` statement is the most complex single operation in Python. When you write `from myapp.views import users`, Python must (1) check `sys.modules` to see if `myapp.views.users` is already loaded, (2) if not, find the module by walking the meta path finders, (3) load the module's source code, (4) compile it to bytecode, (5) execute the module's top-level code in a new namespace, (6) bind the `users` name in the importing namespace to the loaded module, and (7) record the module in `sys.modules` so subsequent imports return the cached object.

```python
import sys
print(sys.modules.keys())  # all loaded modules — a dict
print(sys.path)            # the search path for modules
```

`sys.path` is a list of directories Python searches for modules. It is initialized at startup from: the current directory (`""`), `PYTHONPATH` env var, the interpreter's `site-packages` directory, and any `.pth` files in `site-packages` (which can add additional paths). You can modify `sys.path` at runtime to add directories — this is what `pip install --editable .` does, by adding a `.pth` file that points to your source directory.

```python
import sys
print(sys.path)
# ['/home/user/myapp',          ← current directory (or script's dir)
#  '/usr/lib/python312.zip',    ← stdlib (frozen)
#  '/usr/lib/python3.12',       ← stdlib
#  '/usr/lib/python3.12/lib-dynload',  ← C extensions
#  '/home/user/myapp/.venv/lib/python3.12/site-packages']  ← third-party
```

`PYTHONPATH` is the environment variable that prepends entries to `sys.path` before any Python code runs. It is a colon-separated list (semicolon-separated on Windows) of directories, and it is the escape hatch for situations where you cannot install a package via `pip` — for example, running a script that imports a sibling module without setting up a package:

```bash
# Run a script that does `from lib.helpers import foo`, where lib/ is in ../
PYTHONPATH=/path/to/lib python script.py

# Or set it permanently in .bashrc for a project
export PYTHONPATH="$HOME/projects/myapp/src:$PYTHONPATH"
```

The danger of `PYTHONPATH` is that it makes your environment non-reproducible — a colleague without the same `PYTHONPATH` will get `ModuleNotFoundError` on the same code. The modern alternatives are: structure your project as a package and `pip install -e .` it (which writes a `.pth` file that does the same thing but is project-local); or use a `conftest.py` at the test root to add paths for pytest only. Reserve `PYTHONPATH` for one-off scripts and never commit it to a Dockerfile or systemd unit.

The import machinery uses a chain of "finders" (objects that know how to find modules) and "loaders" (objects that know how to load them). The finders are stored in `sys.meta_path`:

```python
import sys
print(sys.meta_path)
# [<class '_frozen_importlib.BuiltinImporter'>,       ← built-in modules like sys, builtins
#  <class '_frozen_importlib.FrozenImporter'>,         ← frozen modules (compiled to C)
#  <class '_frozen_importlib.PathFinder'>]             ← file-system-based modules
```

`PathFinder` is the one that does the file-system search. For each directory in `sys.path`, it looks for a file matching the module name: `myapp` becomes `myapp.py` (module) or `myapp/` (package). For a package, it requires an `__init__.py` (regular package) — without one, it can still be a namespace package (PEP 420), which is a package spread across multiple directories.

A regular package is a directory containing `__init__.py`:

```text
  myapp/
  ├── __init__.py          ← runs on `import myapp`
  ├── views/
  │   ├── __init__.py      ← runs on `import myapp.views`
  │   ├── users.py         ← runs on `import myapp.views.users`
  │   └── products.py
  └── models/
      ├── __init__.py
      └── user.py
```

The `__init__.py` file is executed once, the first time the package is imported. Its namespace becomes the package's namespace — anything defined in `myapp/__init__.py` is accessible as `myapp.foo`. This is how `from myapp import db` works when `db` is defined in `myapp/__init__.py`. The `__init__.py` is also where packages often re-export their public API: `from .views.users import User` in `myapp/__init__.py` makes `from myapp import User` work.

A namespace package is a directory *without* an `__init__.py`. Multiple directories on `sys.path` can contribute to the same namespace package — useful for splitting a large package across multiple repositories (e.g. `google.cloud.storage` and `google.cloud.pubsub` are separate PyPI packages that both contribute to the `google.cloud` namespace). The mechanism is: `PathFinder` finds no `__init__.py` in any directory named `google.cloud`, but finds `google/cloud/` directories in multiple `site-packages` paths; it creates a namespace package that aggregates all of them. Namespace packages are the cause of one of Python's most confusing error messages: if you have a local file named `enum.py` and you try to `import enum` from the stdlib, Python may load your local file (because `""` is first on `sys.path`) and silently shadow the stdlib — `AttributeError: module 'enum' has no attribute 'IntEnum'` is the symptom. The fix is to rename your local file, or to never put Python files with stdlib-collision names in the project root.

The failure mode the import system produces is the "ran the module as a script, relative imports broke" bug:

```python
# myapp/views/users.py
from ..models import User      # relative import: go up one level to myapp, then into models
```

```bash
$ python myapp/views/users.py
ImportError: attempted relative import with no known parent package
```

The reason: when you run `python myapp/views/users.py`, Python sets `users.__name__` to `"__main__"` (not `"myapp.views.users"`) and `__package__` to `None`. The relative import `from ..models import User` requires `__package__` to be set so Python knows where "up one level" is — but as a script, the module has no package. The fix is to run it as a module: `python -m myapp.views.users`. This sets `__name__` to `"__main__"` and `__package__` to `"myapp.views"`, and the relative import resolves. The lesson is: never run a module that uses relative imports as a script — always use `python -m`.

The other failure mode is the "circular import" deadlock. `myapp/__init__.py` does `from .views import app`, `myapp/views/__init__.py` does `from myapp.models import User`, and `myapp/models/__init__.py` does `from myapp import db` (defined in `myapp/__init__.py`). Python's import system detects the cycle and returns the partially-initialized `myapp` module — `db` does not yet exist on it, so `myapp.models` raises `ImportError: cannot import name 'db' from partially initialized module 'myapp' (most likely due to a circular import)`. The fix is to defer one of the imports to runtime (move the `from myapp import db` inside a function instead of at module top level), or to restructure the package layout to break the cycle. Django's `AppConfig.ready()` method exists precisely to handle this — model registration is deferred until all apps are imported, so `from django.contrib.auth.models import User` inside `ready()` works even though `auth.models` itself cannot be imported at module-load time without causing a cycle.

## Key Takeaways

1. **Python is a bytecode interpreter: source → AST → bytecode → eval loop.** The bytecode is cached in `__pycache__/<module>.cpython-<ver>.pyc` with a magic number that identifies the bytecode format version. Stale `.pyc` files cause `bad magic number` errors after a Python upgrade. `from __future__ import annotations` defers annotation evaluation to runtime (stores them as strings), enabling forward references — add it to every new module.
2. **`if __name__ == "__main__":` distinguishes "run as script" from "imported as module".** Use it for any code that should only run on direct invocation — argument parsing, server startup, demo code. Run modules with `python -m myapp.foo` (not `python myapp/foo.py`) when they use relative imports — only `python -m` sets `__package__` correctly.
3. **The import system is `sys.modules` cache + meta path finders + path-based loaders.** `sys.path` is the search path (modifiable at runtime; `PYTHONPATH` prepends to it); `__init__.py` makes a directory a regular package; namespace packages omit `__init__.py` and aggregate across `sys.path` entries. Circular imports produce "partially initialized module" errors — defer imports to runtime (`AppConfig.ready()` in Django) to break the cycle.
