# 02.04.01. Inter-Process Communication Mechanics

## What This Is

**Inter-Process Communication Mechanics** is the family of kernel primitives that let two processes exchange data. Processes in Linux have isolated address spaces (covered in 02.02.01), so they cannot read or write each other's memory directly — every IPC primitive is a kernel-mediated channel that copies bytes (or, in the case of shared memory, maps the same physical pages into both processes) between them. The reason this note sits in section 02 is that every backend system uses IPC: a shell pipeline (`ls | grep`) uses pipes, a Docker container talking to its host uses UNIX domain sockets, PostgreSQL and Redis use UNIX domain sockets for localhost clients, Nginx and PHP-FPM use UNIX domain sockets or TCP, and every Kubernetes pod uses shared volumes (which are file-backed IPC). Every runtime in section 04 wraps one or more of these primitives — Java's `Pipe`, Node's `child_process.spawn` (which uses pipes), Python's `multiprocessing.Queue` (which uses pipes and shared memory), PHP's `proc_open` (pipes again).

The five IPC mechanisms covered here are: **anonymous pipes** (created with `pipe()`, used between parent and child via `fork`), **named pipes / FIFOs** (created with `mkfifo()`, usable by unrelated processes), **shared memory** (created with `shm_open()` + `mmap(MAP_SHARED)` or `shmget()` + `shmat()`, the fastest IPC because no copy is involved), **message queues** (created with `mq_open()`, a kernel-managed queue of fixed-size messages), and **semaphores** (created with `sem_open()` or `semget()`, used to synchronize access to shared resources, especially shared memory). UNIX domain sockets (covered in 02.04.02) are technically a sixth IPC mechanism but deserve their own note because of their unique properties (file-descriptor passing, peer credentials, the socket file on disk).

## The Details

### Anonymous Pipes (`pipe()`) and Named Pipes/FIFOs (`mkfifo()`)

The **anonymous pipe** is the oldest and most-used IPC mechanism in Unix. `pipe(int fds[2])` creates a one-way, in-kernel byte stream and returns two file descriptors: `fds[0]` is the read end, `fds[1]` is the write end. Data written to `fds[1]` is buffered in the kernel (default capacity 64 KB on Linux, configurable via `fcntl(F_SETPIPE_SZ)`) and can be read from `fds[0]` in FIFO order. The pipe is "anonymous" because it has no name in the filesystem — it exists only as long as the two FDs are open, and it is destroyed when both ends are closed. The canonical use is between a parent and child process: the parent calls `pipe()`, then `fork()`; both processes now have both ends of the pipe open; the parent closes the read end (it only writes), the child closes the write end (it only reads), and they have a one-way channel. This is exactly what the shell does for `ls | grep` — it forks twice, creates a pipe, connects `ls`'s stdout to the pipe's write end, and connects `grep`'s stdin to the pipe's read end.

Pipes have several important properties. First, they are **byte streams**, not message boundaries — if the writer writes "hello" then "world", the reader may receive "helloworld" or "hello" + "world" or any other split; there is no framing. (For message-style IPC, use message queues or UNIX domain sockets with `SOCK_DGRAM`.) Second, they are **unidirectional** — to have two-way communication you need two pipes, or you need a UNIX domain socket. Third, they have **flow control built in** — if the writer fills the kernel buffer (64 KB by default), the writer's `write()` call blocks until the reader drains some data; if the reader tries to read from an empty pipe, the reader's `read()` blocks until the writer writes. Fourth, **EOF is signaled when all write ends are closed** — `read()` returns 0, which is the conventional EOF signal. This is why the shell's pipe cleanup matters: every process in the pipeline must close the FDs it is not using, or the downstream process will never see EOF and will hang forever.

The **named pipe** (also called a **FIFO**) is the filesystem-resident variant. `mkfifo(path, mode)` creates a special file in the filesystem with type `S_IFIFO`; any process can `open(path, O_RDONLY)` to read or `open(path, O_WRONLY)` to write, and the kernel connects them via the same in-kernel byte-stream mechanism as anonymous pipes. The FIFO persists in the filesystem until explicitly `unlink`'d, but the data flowing through it is still in-kernel (not on disk). The interesting behavior of FIFOs is that `open()` blocks until both a reader and a writer are present — `open(path, O_RDONLY)` blocks until someone opens it for writing, and vice versa. This makes FIFOs useful for synchronization: a server can `mkfifo` a control channel and `open(path, O_RDONLY)`, blocking until a client opens the same path for writing to send a command.

```c
/* The canonical pipe + fork pattern (what the shell does for `ls | grep`). */
#include <unistd.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/wait.h>

int main(void) {
    int pipefd[2];
    if (pipe(pipefd) < 0) { perror("pipe"); exit(1); }

    pid_t pid = fork();
    if (pid < 0) { perror("fork"); exit(1); }

    if (pid == 0) {
        /* Child: reads from pipe, execs grep.
           Close write end (we don't write), dup read end to stdin. */
        close(pipefd[1]);                       /* close unused write end */
        dup2(pipefd[0], STDIN_FILENO);          /* pipe read end → stdin */
        close(pipefd[0]);                       /* original now redundant */
        execlp("grep", "grep", "foo", NULL);    /* replace image with grep */
        _exit(127);                              /* only reached if exec fails */
    } else {
        /* Parent: writes to pipe, execs ls.
           Close read end (we don't read), dup write end to stdout. */
        close(pipefd[0]);                       /* close unused read end */
        dup2(pipefd[1], STDOUT_FILENO);         /* pipe write end → stdout */
        close(pipefd[1]);                       /* original now redundant */
        execlp("ls", "ls", NULL);               /* replace image with ls */
        _exit(127);
    }
    return 0;
}
```

```bash
# Create and use a named pipe (FIFO)
$ mkfifo /tmp/myfifo
$ ls -la /tmp/myfifo
prw-r--r-- 1 user user 0 Mar 14 10:00 /tmp/myfifo
#            ↑
#            'p' = type is FIFO (named pipe)

# Open a reader (blocks until a writer appears)
$ cat /tmp/myfifo &
[1] 12345
# (cat is now blocked in open(), waiting for a writer)

# Open a writer from another shell
$ echo "hello through the FIFO" > /tmp/myfifo
hello through the FIFO          # (received by cat in the first shell)

# Inspect pipe buffer size and current contents
$ cat /proc/<pid>/fdinfo/3 | grep -E "pos|flags|pipe"
pos:    0
flags:  02000000
mnt_id: 35
pipe buffer size: 65536 bytes   ← 64 KB (default)

# Tune pipe buffer size (must be a power of 2, max 1 MB by default)
$ echo 1048576 | sudo tee /proc/sys/fs/pipe-max-size
$ # or per-pipe: fcntl(fd, F_SETPIPE_SZ, 1048576)
```

The connection to the upper layers is that every runtime's subprocess API uses pipes under the hood. Java's `ProcessBuilder.inheritIO()` and `Redirect.PIPE` create pipes; Node's `child_process.spawn(cmd, args, { stdio: ['pipe', 'pipe', 'pipe'] })` creates three pipes (stdin, stdout, stderr); Python's `subprocess.Popen` with `stdout=subprocess.PIPE` creates a pipe; PHP's `proc_open` with descriptors creates pipes. Every "I spawned a subprocess and read its output" idiom is the same pipe + fork + exec pattern, just wrapped in a friendlier API. The failure mode is also the same in every runtime: if the parent does not drain the pipe fast enough, the child's `write()` blocks (because the pipe's 64 KB buffer is full); if the child is a long-running process writing to a pipe nobody is reading, it eventually hangs. The fix is to either drain the pipe continuously (the standard approach), use a larger pipe buffer (`F_SETPIPE_SZ`), or use a different IPC mechanism for high-volume communication.

### Shared Memory (`shmget()`, `shmat()`, POSIX `shm_open()`): Zero-copy local IPC

Shared memory is the fastest IPC mechanism because it involves no kernel-mediated copying — the kernel maps the same physical pages into the virtual address spaces of two (or more) processes, so a write by one process is immediately visible to the other. The trade-off is that the kernel provides no synchronization, so the processes must coordinate access themselves (typically with semaphores or pthread mutexes configured with the `PTHREAD_PROCESS_SHARED` attribute). There are two APIs for shared memory on Linux: the older System V API (`shmget` / `shmat` / `shmdt` / `shmctl`) and the newer POSIX API (`shm_open` / `ftruncate` / `mmap` / `munmap` / `shm_unlink`). The POSIX API is preferred for new code because it integrates with the file descriptor abstraction (the shared memory object is referenced by an FD, so it can be passed via `SCM_RIGHTS`, polled via `epoll`, and so on).

The POSIX shared memory workflow is: `shm_open("/my_region", O_CREAT | O_RDWR, 0600)` creates (or opens) a shared memory object named `/my_region` in the `/dev/shm` tmpfs filesystem; `ftruncate(fd, 4096)` sets its size to 4 KB (newly-created shared memory objects are zero-length); `mmap(NULL, 4096, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0)` maps it into the calling process's address space; the FD can then be closed (the mapping persists). Any other process that calls `shm_open("/my_region", ...)` and `mmap` with `MAP_SHARED` gets a mapping to the same physical pages — writes by one process are visible to the other immediately. The region persists until `shm_unlink("/my_region")` is called (which removes the name; the underlying memory is freed when all processes have unmapped it). The region's lifetime is independent of any individual process — it survives as long as at least one process has it mapped or until the system reboots (shared memory is in RAM, not on disk).

The synchronization story is critical and often overlooked. Without synchronization, two processes writing to the same shared memory region will corrupt each other's data — the writes interleave at the cache-line level, producing garbage. The standard solution is to place a `pthread_mutex_t` (or a `sem_t`) at a known offset in the shared region, initialize it with `pthread_mutexattr_setpshared(&attr, PTHREAD_PROCESS_SHARED)`, and use it to protect every read-modify-write operation. The kernel provides `futex` ("fast userspace mutex") as the underlying primitive — a `futex` call only enters the kernel when there is contention (the common case of an uncontended lock is handled entirely in userspace via atomic operations, which is why uncontended mutex acquisition is ~25 ns instead of microseconds). The same `futex` primitive underlies pthread mutexes, `sem_t`, and Rust's `Mutex`/`RwLock`.

```c
/* POSIX shared memory with a process-shared mutex. */
#include <sys/mman.h>
#include <sys/stat.h>
#include <fcntl.h>
#include <unistd.h>
#include <pthread.h>
#include <stdio.h>
#include <string.h>
#include <stdlib.h>

typedef struct {
    pthread_mutex_t lock;        /* must be process-shared */
    int              counter;
} shared_state_t;

int main(void) {
    int fd = shm_open("/my_counter", O_CREAT | O_RDWR, 0600);
    ftruncate(fd, sizeof(shared_state_t));

    shared_state_t *st = mmap(NULL, sizeof(shared_state_t),
                              PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
    close(fd);   /* mapping persists after FD is closed */

    /* Initialize the mutex as process-shared (only the first creator does this;
       use a separate init step or file lock to coordinate). */
    pthread_mutexattr_t attr;
    pthread_mutexattr_init(&attr);
    pthread_mutexattr_setpshared(&attr, PTHREAD_PROCESS_SHARED);
    pthread_mutex_init(&st->lock, &attr);
    pthread_mutexattr_destroy(&attr);
    st->counter = 0;

    pid_t pid = fork();
    if (pid == 0) {
        /* Child: increment counter 100000 times. */
        for (int i = 0; i < 100000; i++) {
            pthread_mutex_lock(&st->lock);
            st->counter++;
            pthread_mutex_unlock(&st->lock);
        }
        _exit(0);
    } else {
        /* Parent: increment counter 100000 times. */
        for (int i = 0; i < 100000; i++) {
            pthread_mutex_lock(&st->lock);
            st->counter++;
            pthread_mutex_unlock(&st->lock);
        }
        waitpid(pid, NULL, 0);
        printf("counter = %d (expected 200000)\n", st->counter);
        /* Without the mutex, counter would be some random value < 200000
           due to lost updates from concurrent read-modify-write. */
    }

    shm_unlink("/my_counter");
    return 0;
}
```


The connection to the upper layers is that every high-performance IPC backend uses shared memory. PostgreSQL uses shared memory for `shared_buffers` (the buffer pool that all backend processes share), the lock table, and the process table — every Postgres backend process maps the same shared memory regions, which is why Postgres can scale to many processes without IPC bottleneck. Redis Cluster uses shared memory for the bus between nodes. Nginx's shared memory zones (`ssl_session_cache`, `proxy_cache`, `limit_req_zone`) are shared between worker processes. Java's `ByteBuffer.allocateDirect` does not create shared memory by default, but a Java process can attach to an existing POSIX shared memory region via `sun.misc.Unsafe` or JNI for high-performance IPC with native code. The lesson is that shared memory is the lowest-latency IPC for high-volume data, but the synchronization complexity means it should be used only when the bandwidth requirement justifies it — for low-volume control messages, pipes or sockets are simpler and safer.

### POSIX Message Queues (`mq_open()`) and System V IPC primitives

POSIX message queues (`mq_open`, `mq_send`, `mq_receive`, `mq_close`, `mq_unlink`) are a kernel-managed queue of fixed-size messages, addressed by name (like `/my_queue`) and accessible across processes. Unlike pipes (which are byte streams with no framing), message queues preserve message boundaries — each `mq_send` adds one message to the queue, and each `mq_receive` removes one message. The maximum message size and maximum queue depth are set when the queue is created (via `mq_attr`), with system-wide limits in `/proc/sys/fs/mqueue/msg_max` (default 10) and `/proc/sys/fs/mqueue/msgsize_max` (default 8192 bytes). Message queues also support priority — `mq_send` takes a priority argument, and `mq_receive` returns the highest-priority message first. They also support asynchronous notification via `mq_notify`, which can deliver a signal or start a thread when a message arrives on a previously-empty queue.

The System V IPC primitives (`msgget` / `msgsnd` / `msgrcv` for message queues, `semget` / `semop` for semaphores, `shmget` / `shmat` for shared memory) are the older API, predating POSIX standardization. They use integer keys instead of names, are managed via `ipcs` and `ipcrm`, and have slightly different semantics (no built-in priority, no async notification, but they are widely available on every Unix). Modern code should use the POSIX API for new development because it integrates better with the file descriptor abstraction (the queue is referenced by an FD, can be polled, can be passed via `SCM_RIGHTS`). The System V API remains in production use mainly in older databases (PostgreSQL originally used System V shared memory before 9.3 added POSIX support; Oracle uses System V semaphores heavily).

Semaphores are the synchronization primitive that pairs with shared memory. A semaphore is a counter that supports two atomic operations: `wait` (decrement, block if zero) and `post` (increment, wake one waiter). POSIX semaphores (`sem_open` / `sem_wait` / `sem_post` / `sem_close` / `sem_unlink`) are named (like message queues) and can be used across processes.Unnamed semaphores (`sem_init` with the `pshared` flag) live in memory and are typically placed in a shared memory region. System V semaphores (`semget` / `semop`) are array-based (one `semget` call creates a set of N semaphores, all manipulated atomically via `semop`), which is useful for multi-resource locking (e.g., the producer-consumer pattern with empty-count and full-count semaphores plus a mutex).

```c
/* POSIX message queue — producer/consumer pattern. */
#include <mqueue.h>
#include <stdio.h>
#include <string.h>
#include <fcntl.h>
#include <sys/stat.h>

#define QUEUE_NAME "/my_queue"
#define MAX_MSG_SIZE 256
#define MAX_MSGS     10

int main(void) {
    struct mq_attr attr = {
        .mq_flags = 0,
        .mq_maxmsg = MAX_MSGS,
        .mq_msgsize = MAX_MSG_SIZE,
        .mq_curmsgs = 0,
    };
    mqd_t mq = mq_open(QUEUE_NAME, O_CREAT | O_RDWR, 0600, &attr);

    pid_t pid = fork();
    if (pid == 0) {
        /* Child: consumer */
        char buf[MAX_MSG_SIZE];
        unsigned prio;
        for (int i = 0; i < 5; i++) {
            ssize_t n = mq_receive(mq, buf, sizeof(buf), &prio);
            printf("consumer: got message (prio=%u): %.*s\n", prio, (int)n, buf);
        }
        mq_close(mq);
        _exit(0);
    } else {
        /* Parent: producer */
        const char *messages[] = {"hello", "world", "foo", "bar", "baz"};
        for (int i = 0; i < 5; i++) {
            mq_send(mq, messages[i], strlen(messages[i]) + 1, i);  /* prio = i */
            printf("producer: sent (prio=%d): %s\n", i, messages[i]);
        }
        waitpid(pid, NULL, 0);
        mq_close(mq);
        mq_unlink(QUEUE_NAME);
    }
    return 0;
}
```

The connection to the upper layers is that every backend's queueing layer can use these primitives for in-process or local-only message passing. Spring Boot's `ApplicationEventPublisher` and Spring Integration's channels are typically JVM-internal (no IPC), but for cross-process work, a queue backed by POSIX message queues or shared memory can be used. Redis and RabbitMQ use TCP sockets (not message queues) for portability. Java's `java.util.concurrent.BlockingQueue` is in-process only; for cross-process, JMS or a real message broker is used. The reason POSIX message queues are rarely used in modern backend engineering is that the use case (high-throughput local-only queueing between two processes on the same host) is small — most queueing is either in-process (use a `BlockingQueue`) or cross-host (use a real broker). The notable exception is real-time and embedded systems, where the kernel-managed priority queueing and bounded latency of POSIX message queues are valuable. When you read the messaging notes in section 07, every broker is network-based, and the local-only message queue is a historical curiosity for most backend work — but understanding it is what makes the IPC landscape complete.

## How This Connects to the Runtimes

Every runtime covered in section 04 is a user-space wrapper around these kernel primitives:

- **JVM**: Maps Java threads 1:1 to OS threads via NPTL. The JVM's memory model (section 04.01) is a specification layered on top of the kernel's virtual memory system described here.
- **Node.js / libuv**: The event loop (section 04.02) is a Reactor pattern built on `epoll_wait()`. The worker thread pool uses OS threads for operations that cannot be multiplexed (file I/O, DNS, crypto).
- **CPython**: The GIL (section 04.03) is a mutex that serializes Python bytecode execution across OS threads. Multi-processing in Python uses `fork()` to bypass the GIL.
- **PHP-FPM**: Each worker is a separate OS process (section 04.04). The shared-nothing model is a direct consequence of the process isolation described in the Linux Process Model note.

When you read those runtime notes, come back here and trace which kernel primitive each runtime feature maps to.
