# 02.04.02. UNIX Domain Sockets vs. Network Sockets

## What This Is

**UNIX Domain Sockets vs. Network Sockets** is the decision every backend service makes when two processes on the same host need to talk: do they open a TCP socket to `127.0.0.1:PORT`, or do they open a UNIX domain socket (UDS) at `/var/run/service.sock`? Both are file descriptors created by the same `socket()` syscall and consumed by the same `read`/`write`/`send`/`recv` calls — the difference is entirely in the address family (`AF_UNIX` vs `AF_INET`/`AF_INET6`) and the kernel code path the data traverses. A UDS never enters the IP stack: there is no IP header, no TCP header, no checksum, no congestion window, no MTU fragmentation, no TIME_WAIT. The kernel simply copies bytes from the writer's `sk_buff` queue into the reader's `sk_buff` queue via `unix_stream_sendmsg` → `skb_queue_tail` → `unix_stream_read_generic` (in `net/unix/af_unix.c`). The result is that UDS round-trip latency on the same host is roughly 30–50% lower than TCP localhost, and throughput is 1.5–3× higher for large payloads.

The reason this note sits in section 02 is that the choice is structurally visible across the entire backend stack. PostgreSQL accepts connections on `/var/run/postgresql/.s.PGSQL.5432` by default; Redis listens on `/var/run/redis/redis.sock` when configured for local use; Docker's API is exposed at `/var/run/docker.sock`; systemd's `notify` and `listen` socket-activation primitives use UDS; container runtimes pass file descriptors between the orchestrator and the container init process via the `SCM_RIGHTS` ancillary message, which is a UDS-only feature. Every runtime in section 04 exposes both options — Java's `java.net.Socket` vs `junixsocket`, Node's `net.connect(port, host)` vs `net.connect('/path/to.sock')`, Python's `socket.AF_INET` vs `socket.AF_UNIX`, PHP's `stream_socket_client('tcp://...')` vs `stream_socket_client('unix://...')`. Every database driver in section 06 has a `host=/var/run/...` mode that skips the TCP stack entirely. Choosing UDS over TCP for same-host traffic is the single highest-leverage latency optimization available to a backend engineer — and choosing TCP over UDS for cross-host traffic is non-negotiable.

The mental model is: a socket is a kernel object (`struct socket` in `include/linux/net.h`, wrapping `struct sock` in `include/net/sock.h`), and the address family determines which `struct proto_ops` dispatch table is attached to it. For `AF_INET` + `SOCK_STREAM`, the dispatch table is `inet_stream_ops` and the proto is `tcp_prot`; every `sendmsg` call descends through `inet_sendmsg` → `tcp_sendmsg` → `tcp_write_xmit` → `ip_queue_xmit` → `dev_queue_xmit` and finally lands on the loopback driver `lo`. For `AF_UNIX` + `SOCK_STREAM`, the dispatch table is `unix_stream_ops` and the proto is `unix_proto`; `sendmsg` calls `unix_stream_sendmsg`, which calls `skb_queue_tail` to enqueue the data on the peer's receive queue and wakes the peer. The UDS path is two function calls and one memcpy; the TCP loopback path is fifteen function calls, two checksums (computed and then immediately discarded because the loopback driver doesn't actually need them), one clone (for `tcpdump` if any sniffer is attached), and one congestion-window check that always succeeds. Both paths satisfy the syscall contract; only one of them is the short path.

## The Details

### UNIX Domain Sockets (UDS): Stream (`AF_UNIX`, `SOCK_STREAM`) and Datagram (`AF_UNIX`, `SOCK_DGRAM`)

A UNIX domain socket is created with `socket(AF_UNIX, SOCK_STREAM, 0)` for stream semantics (in-order, reliable, connection-oriented, like TCP) or `socket(AF_UNIX, SOCK_DGRAM, 0)` for datagram semantics (unordered, unreliable, message-boundary-preserving, like UDP). The address structure is `struct sockaddr_un` (defined in `<sys/un.h>`), which has only two fields: `sun_family` (always `AF_UNIX`) and `sun_path` (a char array of 108 bytes on Linux per `/usr/include/linux/un.h` — historically 104 on System V, 108 on BSD; the Linux kernel's `UNIX_PATH_MAX` is 108). The server calls `bind(fd, (struct sockaddr*)&addr, sizeof(addr))` to associate the socket with a path; the kernel creates a special filesystem entry of type socket (visible with `ls -la` as the `s` permission bit) at that path. The socket file persists on disk until `unlink`'d — closing the listening FD does not remove the file, which is the root of the classic "Address already in use" production incident after a crash.

The stream variant (`SOCK_STREAM`) is what most backends use: the server `bind`s, `listen`s, and `accept`s; the client `connect`s; both sides `send` and `recv` over a connected byte stream. Connection establishment is a single in-kernel state transition (no SYN/SYN-ACK/ACK) — the `connect` syscall blocks until the server's `accept` returns, which happens within microseconds on the same CPU. The datagram variant (`SOCK_DGRAM`) is connectionless and preserves message boundaries — each `sendto` produces one datagram, each `recvfrom` returns one datagram — which is useful for request/response patterns where the cost of framing in the byte-stream API would dominate. Redis 6+'s "Resp3 over UDS datagram" mode and the D-Bus system bus both use `SOCK_DGRAM` over UDS for this reason. Both variants share the same data path (no IP stack), so the latency advantage is identical.

The single most powerful UDS-only feature is `SCM_RIGHTS` ancillary message passing, which lets one process send an open file descriptor to another process over a UDS — the kernel literally transfers the `struct file*` from the sender's FD table to the receiver's FD table. This is impossible over TCP because TCP only carries bytes, not kernel objects. `SCM_RIGHTS` is the foundation of: (1) systemd's socket activation — systemd opens the listening socket, forks the service, and passes the FD via `SCM_RIGHTS` over a UDS, so the service starts up "already listening" without ever calling `socket` or `bind`; (2) container runtimes — runc/containerd pass the container's stdio pipes, the OCI runtime's seccomp notify FD, and the CRIU checkpoint FDs via `SCM_RIGHTS`; (3) nginx's upstream FD passing for zero-downtime binary upgrades — the new master inherits the listening sockets from the old master via `SCM_RIGHTS` over a UDS between them; (4) Wayland — the compositor hands the client a graphics buffer FD (a dma-buf) via `SCM_RIGHTS`. The mechanism is `sendmsg` with `msg_control` populated by a `cmsg` of type `SCM_RIGHTS`, and on the receive side the kernel allocates a new FD number in the receiver's table pointing to the same `struct file`.

```c
/* UDS server: bind, listen, accept — and the socket file on disk. */
#include <sys/socket.h>
#include <sys/un.h>
#include <unistd.h>
#include <stdio.h>
#include <string.h>
#include <errno.h>

#define SOCK_PATH "/tmp/demo.sock"

int main(void) {
    int srv = socket(AF_UNIX, SOCK_STREAM | SOCK_CLOEXEC, 0);

    /* Critical: unlink any stale socket file from a previous crash.
       Otherwise bind() fails with EADDRINUSE. */
    unlink(SOCK_PATH);

    struct sockaddr_un addr;
    memset(&addr, 0, sizeof(addr));
    addr.sun_family = AF_UNIX;
    strncpy(addr.sun_path, SOCK_PATH, sizeof(addr.sun_path) - 1);

    /* bind creates the socket file on disk. */
    if (bind(srv, (struct sockaddr*)&addr, sizeof(addr)) < 0) {
        perror("bind"); return 1;
    }
    if (listen(srv, 128) < 0) { perror("listen"); return 1; }

    /* ls -la now shows the socket file with type 's'. */
    fprintf(stderr, "listening on %s (sun_path = %zu bytes)\n",
            SOCK_PATH, sizeof(addr.sun_path));

    for (;;) {
        int cli = accept4(srv, NULL, NULL, SOCK_CLOEXEC);
        if (cli < 0) { perror("accept4"); continue; }
        char buf[256];
        ssize_t n = recv(cli, buf, sizeof(buf) - 1, 0);
        if (n > 0) { buf[n] = 0; printf("got: %s\n", buf); }
        send(cli, "ok\n", 3, 0);
        close(cli);
    }
    close(srv);
    unlink(SOCK_PATH);
    return 0;
}
```

```bash
# Or with Python's standard library.
$ python3 -c "

#  u_str = UDS stream, LISTEN = listening, 128 = backlog
```

The connection to the layered mental model is the "everything is a file" payoff covered in [[02.03.01. The File Descriptor Abstraction]] — UDS uses the FD abstraction, the `struct file` indirection, and the VFS layer, all of which are reused from the file-IO world. The `struct socket` sits behind the same FD that the application reads and writes; the only difference is which `proto_ops` table the VFS dispatches to. The production failure mode is the leftover socket file: if the server crashes without `unlink`ing the path, the next start's `bind` returns `EADDRINUSE`, the service fails to start, and the on-call engineer who doesn't know to `rm /tmp/demo.sock` is stuck. The fix is either `unlink` before `bind` (the standard idiom, shown above) or `connect`-first-to-check-and-then-unlink (what systemd does for socket activation). The other production failure mode is `sun_path` truncation: if your path is longer than 107 bytes, `bind` silently truncates and creates a socket at the wrong path, leading to clients connecting to nothing.

### Performance optimizations of UDS: Bypassing TCP/IP checksumming, packet routing, and network interface stacks

The UDS performance advantage comes from skipping the entire TCP/IP stack on every send. When a process calls `write(udfd, buf, n)` or `send(udfd, buf, n, 0)`, the kernel descends through `sock_write_iter` → `unix_stream_sendmsg` (in `net/unix/af_unix.c`), which allocates one `sk_buff`, copies the user buffer into it via `skb_copy_datagram_from_iter`, enqueues the `sk_buff` on the peer's receive queue with `skb_queue_tail`, and wakes the peer. That's the entire send path: one allocation, one copy, one enqueue, one wakeup. By contrast, a TCP send on loopback goes `sock_write_iter` → `inet_sendmsg` → `tcp_sendmsg` → `tcp_sendmsg_locked` (which respects the congestion window, the send buffer, and Nagle's algorithm) → `tcp_write_xmit` → `tcp_transmit_skb` (which builds the TCP header, computes the TCP checksum) → `ip_queue_xmit` (which builds the IP header, computes the IP header checksum, and routes the packet — the routing table lookup hits the `lo` device) → `ip_local_out` → `ip_output` → `ip_finish_output2` → `dev_queue_xmit` → `loopback_xmit` (which calls `netif_rx` to inject the packet back into the network stack on the receive side) → `ip_rcv` (which validates the IP header, recomputes the IP checksum, discards it) → `tcp_v4_rcv` → `tcp_v4_do_rcv` → `tcp_rcv_established` (which validates the TCP checksum, discards it, and copies the payload into the receiver's socket buffer). The TCP loopback path traverses the network stack twice (once as sender, once as receiver) and computes and discards two checksums on every packet.

The double traversal is the dominant cost. On a modern x86_64 kernel, the full TCP loopback round-trip is ~10–15 µs; the UDS round-trip is ~3–5 µs (the difference is mostly the second traversal of the IP/TCP stack on the receive side). For throughput, the loopback MTU is 65536 (`ip link show lo` shows `mtu 65536`), so TCP can carry up to 64 KB per packet without fragmentation, but each packet still pays the protocol header cost (~40 bytes for IP+TCP) and the checksum cost. UDS has no protocol header — every byte in the `sk_buff` is payload. For a 1 MB bulk transfer, UDS achieves ~5–7 GB/s on a typical NVMe-era server; TCP loopback achieves ~2–3 GB/s on the same hardware (limited by the protocol overhead and the `sk_buff` clone-for-sniffers cost when `tcpdump` is attached). The exact numbers depend on `tcp_{r,w}mem`, the `sk_buff` allocator slab, and whether any packet capture is running — `tcpdump -i lo` doubles the cost of every loopback packet because each one is cloned once for the AF_PACKET socket.

There are several less-visible optimizations that compound the headline numbers. First, UDS does not maintain TIME_WAIT state — when one side `close`s, the kernel simply frees the `struct sock` and the `sk_buff` queue; there is no 60-second lingering state. This means a server that accepts and closes 100,000 short-lived UDS connections per second has zero state accumulation, while the same workload over TCP accumulates up to 100,000 TIME_WAIT entries (each ~250 bytes of kernel memory, plus a hash-table entry that slows future socket lookups). Second, UDS does not have Nagle's algorithm — there is no `TCP_NODELAY` flag to set, because the concept doesn't exist. The 40 ms coalescing delay that haunts TCP localhost services running request/response workloads (the "TCP_NODELAY + delayed ACK interaction" classic) is structurally impossible on UDS. Third, UDS does not have a congestion window — there is no slow start, no recovery, no `tcp_cwnd` check, no pacing. Fourth, UDS does not have keepalives — if the peer dies, the kernel marks the socket `ECONNRESET` on the next `send`, but it does not probe the peer every two hours the way TCP keepalive does. These absences are features, not bugs: the underlying transport is the kernel's own scheduler, which is already reliable.

The connection to the layered mental model is that every runtime in section 04 pays for the kernel path it chooses. When Node's `net.connect(port, 'localhost')` is used, every byte goes through the TCP loopback path above; when `net.connect('/var/run/redis.sock')` is used, every byte goes through the UDS path. The application code is identical (a `Socket` object with `on('data', ...)`), but the kernel work done per byte is 5× lower. The production failure mode is the silent latency tax: an engineering team that defaults every same-host service-to-service call to TCP because "it's portable" pays 30–50% latency on every call for the entire lifetime of the service, never realizes it, and is confused why their p99 is 4 ms when the database itself responds in 0.5 ms. The diagnosis is `strace -c -e trace=sendto,recvfrom` on the process — if you see `sendto` on a TCP socket, every call traverses the full IP stack; switch to UDS and the same syscall count produces half the wall-clock time.

### Benchmark comparisons: UDS throughput vs. Localhost Loopback (`127.0.0.1`) TCP sockets

Concrete benchmarks on commodity hardware tell the story. The standard `ipc-bench` suite (and equivalent `nc`/`socat` ad-hoc tests) consistently shows: for 1 KB payloads, UDS round-trip latency is ~3–5 µs vs TCP loopback's ~10–15 µs (a 3× advantage for UDS); for 64 KB payloads, UDS throughput is ~5–7 GB/s vs TCP loopback's ~2–3 GB/s (a 2–3× advantage for UDS); for 1 MB payloads, both saturate around the same throughput (the kernel's `sk_buff` allocator and the memory-bandwidth limit dominate, and the protocol overhead is amortized). The latency advantage is largest for small payloads (where the fixed per-call protocol cost dominates); the throughput advantage is largest for medium payloads (where the per-byte copy cost is comparable but the protocol overhead still matters). At very large payloads, the differences converge because both paths become memcpy-bound.

Real-world database benchmarks confirm these numbers. PostgreSQL's `pgbench` on the same host with `host=/var/run/postgresql` (UDS) vs `host=127.0.0.1` (TCP) shows: for a read-heavy workload of `SELECT * FROM accounts WHERE aid = ?` (single-row point lookup), the UDS configuration achieves ~15–20% higher TPS than TCP — small because the query execution time dominates over the connection round-trip. For a write-heavy workload of `INSERT INTO history (aid, bid, delta, mtime) VALUES (...)` (cheap query, dominated by round-trip), UDS achieves ~30–40% higher TPS. For Redis, the difference is even more pronounced because Redis is single-threaded and every microsecond of kernel overhead is a microsecond the event loop is not handling another command: `redis-benchmark -s /var/run/redis/redis.sock -t get,set -n 1000000` typically shows ~30–50% higher RPS than `redis-benchmark -h 127.0.0.1 -p 6379 -t get,set -n 1000000` on the same hardware.

The Docker networking layer multiplies the TCP cost further. A container that exposes a port via `docker run -p 8080:8080` goes through three traversals on every request: container → veth pair → docker-proxy (userspace) → host loopback. The `docker-proxy` userspace hop alone adds ~50–100 µs per connection, and the `iptables` DNAT rules add another ~5–10 µs. Running the client in the same Docker network as the server (so they communicate over the bridge directly) cuts one hop; running them with `--network=host` (so they share the host's network namespace) cuts both hops and approaches the loopback numbers. The lowest-latency option is to mount the UDS socket file into both containers via a shared volume (`-v /var/run/service.sock:/var/run/service.sock`) and have them communicate over UDS — this skips the Docker networking layer entirely. The throughput advantage on a busy microservice host can be 5–10×, because the docker-proxy userspace hop becomes the bottleneck under load.

The decision rule for production is: use UDS when the client and server are guaranteed to be on the same host (and you control the path-layout); use TCP when they might be on different hosts (including a migration path that splits them later); use UDS-plus-optional-TCP when you want a config-driven choice (PostgreSQL's `host=` vs `hostaddr=`, Redis's `unixsocket` vs `port`, Docker's `--network=host` vs bridge). The "might be on different hosts" caveat is the reason most microservice frameworks default to TCP even on the same host — the migration cost of later splitting services is high enough that the latency tax is considered acceptable. The teams that do switch to UDS are typically the ones with the tightest latency budgets: high-frequency trading systems, ad-tech bid responders, game servers, and any service whose p99 SLA is under 5 ms.

The connection to the layered mental model is the operational cost accounting for [[02.04.03. The POSIX Socket Lifecycle]] and [[02.04.04. Kernel Socket Buffers and Socket Tuning]] — every byte a runtime sends over a socket becomes an `sk_buff`, and every `sk_buff` traverses a chain of kernel functions determined by the address family. The production failure mode is the silent regression: a team that migrates a service from UDS to TCP "for portability" without benchmarking sees p99 latency climb from 1.5 ms to 3 ms, the SLA starts breaching under load, and nobody connects the regression to the transport change because the application code is unchanged. The diagnosis is `ss -x -a` (which lists UDS connections) and `ss -t -a` (which lists TCP) on the host — if a same-host service pair has TCP entries instead of UDS entries, the team is paying the latency tax unnecessarily. The fix is mechanical: change the connection string (`host=/var/run/service.sock` instead of `host=127.0.0.1`), restart, and re-measure.

## How This Connects to the Runtimes

Every runtime covered in section 04 exposes the UDS-vs-TCP choice through its standard library, and the choice is always a one-line config change. **JVM** exposes UDS via the standard `java.net.Socket` only on JDK 16+ (`Socket.connect(UnixDomainSocketAddress.of(path))`); on older JDKs you need the `junixsocket` library or `org.newsclub.net.UnixSocketChannel`. The JVM's standard NIO `SocketChannel` and the Netty `EpollSocketChannel` both support UDS via `DomainSocketAddress`, and Netty's epoll transport uses `O_NONBLOCK` + `epoll` on UDS the same way it does on TCP — the event loop is identical, only the address family differs. **Node.js / libuv** has had UDS support since v0.x: `net.connect('/var/run/redis.sock')` instead of `net.connect(6379, '127.0.0.1')`, and the returned `Socket` object is the same class with the same `'data'`/`'end'`/`'error'` events — the application code is byte-identical, only the connection arguments change. libuv internally calls `socket(AF_UNIX, SOCK_STREAM, 0)` and `connect()` with a `sockaddr_un`, then registers the FD with `epoll` exactly as it would a TCP FD. **CPython** exposes UDS via `socket.socket(socket.AF_UNIX, socket.SOCK_STREAM)` — same `send`/`recv`/`makefile` API as `AF_INET`, only the address argument changes from `(host, port)` to a path string. asyncio's `loop.create_unix_connection(path)` is the async equivalent. **PHP-FPM** uses UDS via `stream_socket_client('unix:///var/run/service.sock')` or the cURL-style `unix:///var/run/docker.sock` URL scheme — the Zend Engine wraps the same `socket()` + `connect()` syscalls. When you read the runtime notes in section 04, the event-loop and concurrency content is identical for UDS and TCP because the kernel-level primitive (an FD with `O_NONBLOCK` + `epoll`) is identical — the transport is a config detail, and every runtime's "production-ready" recipe includes setting `SO_REUSEADDR` on TCP and `unlink()`-before-`bind()` on UDS as the only transport-specific lines.
