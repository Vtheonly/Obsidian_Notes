# 02.04.04. Kernel Socket Buffers and Socket Tuning

## What This Is

Every byte that crosses a TCP or UDP socket in Linux passes through two kernel-managed queues: a receive queue and a send queue. These queues are not abstract API contracts — they are concrete `sk_buff` (socket buffer) chains hanging off the `struct sock` object inside the kernel, sized by sysctls and tunable per-socket via `setsockopt()`. The size of those queues determines the latency, throughput, and backpressure behaviour of every runtime in section 04: the JVM's NIO `SocketChannel`, Node's `uv_tcp_t`, Python's `socket.socket`, and PHP's stream wrappers all funnel through the same `sk_buff` allocator.

This note covers the four production knobs that the kernel exposes: `SO_RCVBUF`/`SO_SNDBUF` (per-socket queue sizes), `SO_REUSEADDR`/`SO_REUSEPORT` (port reuse and kernel-level load balancing), `SO_RCVTIMEO`/`SO_SNDTIMEO`/`SO_KEEPALIVE` (timeout and dead-peer detection), and `TCP_NODELAY` (Nagle's algorithm toggle). Understanding them is what separates a server that holds 100k idle connections at 5% CPU from one that trips over its own buffers at 2k.

## The Details

### Socket Receive Buffer (`SO_RCVBUF`) and Socket Send Buffer (`SO_SNDBUF`)

Inside `struct sock` (defined in `include/net/sock.h` in the kernel source) every socket carries two `sk_buff_head` queues: `sk_receive_queue` for inbound packets the kernel has acknowledged but the application has not yet consumed with `recv()`/`read()`, and `sk_write_queue` for outbound bytes the application has handed to `send()`/`write()` but that TCP has not yet transmitted (or has transmitted but not yet had ACKed, while they wait in the retransmit buffer). Each `sk_buff` is itself a metadata struct pointing at a contiguous data block plus header space reserved for the lower-layer headers that will be prepended as the packet walks down the IP/TCP stack. Memory for these buffers comes from the kernel's `sk_buff_head` cache and counts against the per-socket `sk_rmem_alloc` / `sk_wmem_alloc` counters — those counters are what the sysctls cap.

The four global sysctls that govern default and maximum sizes are `net.core.rmem_default` / `net.core.rmem_max` (receive) and `net.core.wmem_default` / `net.core.wmem_max` (send). On a stock Ubuntu 22.04 kernel the defaults are `rmem_default=212992` (208 KiB), `rmem_max=212992`, `wmem_default=212992`, `wmem_max=212992`. A production Nginx box is typically tuned to `rmem_max=13497728` and `wmem_max=13497728` (13 MiB), with `rmem_default=262144` and `wmem_default=262144`. Setting `SO_RCVBUF` via `setsockopt()` requests a size, but the kernel silently doubles whatever the application asks for (to cover overhead) and clamps it to `rmem_max`. So a `setsockopt(fd, SOL_SOCKET, SO_RCVBUF, &256*1024)` on the stock kernel actually yields a 208 KiB buffer — the only way to actually get 256 KiB is to first raise `rmem_max`.

For TCP there is a second, more important layer: the `tcp_rmem` and `tcp_wmem` sysctl triples. Each is `min default max` in bytes. On a typical production server:

```text
net.ipv4.tcp_rmem = 4096 87380 6291456
net.ipv4.tcp_wmem = 4096 65536 4194304
```

This enables **TCP autotuning** (governed by `net.ipv4.tcp_moderate_rcvbuf=1`, which is default on). The kernel dynamically grows the receive buffer up to `tcp_rmem[2]` (6 MiB here) based on the measured BDP (bandwidth × delay product) of the connection. A long-fat pipe to a transatlantic client at 100 ms RTT and 100 Mbit/s needs ~1.25 MiB of window to fill the pipe; autotuning grows the buffer to that, then shrinks it back when the flow stops. Manually setting `SO_RCVBUF` disables autotuning for that socket — which is almost always the wrong choice on a server that serves clients with heterogeneous RTTs. The static buffer sizes from `net.core.*` only apply to UDP, raw sockets, and TCP sockets where autotuning has been turned off.

The third piece of the puzzle is how the receive buffer maps to the TCP advertised window. The window field in every TCP ACK tells the peer "I have RCV.WND bytes of free buffer." `net.ipv4.tcp_window_scaling=1` (RFC 7323, default on since Linux 2.6.8) allows windows larger than 65535 by sending a scale factor in the SYN. `net.ipv4.tcp_adv_win_scale` controls how aggressively the kernel under-advertises the buffer to leave headroom for the application to drain: with `tcp_adv_win_scale=1` (default) the advertised window is `rcvbuf/2 - rcvbuf/2^1 = rcvbuf/2`; with `tcp_adv_win_scale=2` it is `rcvbuf - rcvbuf/4 = 3·rcvbuf/4`. The mismatch between the actual buffer and the advertised window is what propagates backpressure to the sender — when the application stops reading, the receive buffer fills, the advertised window shrinks, and the sender's TCP stack stalls.

The production failure mode here is **bufferbloat**. An operator sees packet loss on a transcontinental link, assumes the receive buffer is too small, and cranks `tcp_rmem[2]` to 64 MiB. Now a single slow-reading client can hold 64 MiB of in-flight data buffered in the kernel, all of which adds to the latency of every other flow sharing that client's bottleneck. The fix is the opposite: keep buffers modest (4–8 MiB max for TCP) and rely on autotuning to grow them only when the BDP actually warrants it. The metric that reveals this is `ss -tin`'s `cwnd` and `wnd` columns — if `wnd` stays at the maximum while `cwnd` is small, the application is not draining and you have a slow-consumer problem, not a buffer problem.

```bash
# Production sysctl values on a 64-core Nginx edge node serving ~80k concurrent TCP connections
net.core.rmem_default = 262144
net.core.rmem_max     = 13497728
net.core.wmem_default = 262144
net.core.wmem_max     = 13497728
net.ipv4.tcp_rmem     = 4096 87380 6291456
net.ipv4.tcp_wmem     = 4096 65536 4194304
net.ipv4.tcp_moderate_rcvbuf = 1
net.ipv4.tcp_window_scaling  = 1
net.ipv4.tcp_adv_win_scale   = 1
```

### Reusing local ports and addresses: `SO_REUSEADDR` (avoiding TIME_WAIT blocks) and `SO_REUSEPORT` ...

When a TCP server calls `close()` on an actively closed connection, the local socket enters `TIME_WAIT` for `2*MSL` (typically 60 seconds on Linux, governed by `net.ipv4.tcp_fin_timeout` for the FIN-WAIT-1→2 transition and the harder-coded 60s for TIME_WAIT itself). During that window the (src_ip, src_port, dst_ip, dst_port) 4-tuple is reserved so that a stray retransmitted segment from the old connection cannot be misinterpreted as belonging to a new one. The side that called `close()` first — the server, in the typical HTTP case — holds TIME_WAIT, which means a server that restarts immediately cannot rebind to its listening port: `bind()` returns `EADDRINUSE` because the kernel still considers the 4-tuple in use, even though the listening socket itself is gone.

`SO_REUSEADDR` lifts this restriction for `bind()`: with the option set, `bind()` succeeds as long as no actively LISTENING socket conflicts, ignoring sockets in `TIME_WAIT`. This is why every `bind()` example since BSD 4.2 sets it before calling `listen()`. Without it, a server that crashes and is restarted by systemd within 60 seconds fails to bind — which is fatal for any service managed by an automated restarter.

`SO_REUSEPORT` (Linux 3.9, 2013) goes further: it allows multiple sockets — even in different processes — to bind to the *same* `(IP, port)` pair as long as all of them set the option. The kernel then keeps a per-port hash table of all listening sockets and dispatches incoming SYN packets across them using a hash of the 4-tuple. This is the foundation of Nginx's `listen 80 reuseport;` directive and Node.js's cluster mode: instead of one master process `accept()`ing and hand-feeding connections to workers via a Unix domain socket (which makes the master a single-threaded bottleneck under high request rates), every worker holds its own listening socket and the kernel itself does the load balancing in O(1) per packet.

The dispatch is deterministic — the same source (src_ip, src_port) hash always lands on the same worker — which is desirable because it preserves per-flow TCP state and keeps the connection-level CPU cache warm. The trade-off is unevenness: a few connections that happen to hash to worker 3 can saturate that worker while workers 0–2 sit idle, because the kernel cannot see how busy each worker is. Linux 4.6 (`attachtype_ebpf` for `SO_REUSEPORT`) added an eBPF hook that lets the application inspect the SYN and dispatch to the least-loaded worker — Cloudflare and Facebook both use this for their L7 load balancers. The standard `reuseport` directive in Nginx uses the hash-based dispatch, which is good enough for most workloads but produces a 30–50% p99 latency variance compared to eBPF-aware dispatch under skewed request-size distributions.

```text
Without SO_REUSEPORT (master/worker via fd passing):

  Master ─► accept() ─┬─► sendmsg(fd, worker_0)
                      ├─► sendmsg(fd, worker_1)
                      └─► sendmsg(fd, worker_2)
  (Master is a serial bottleneck; one syscall per connection.)

With SO_REUSEPORT (kernel-level dispatch):

  NIC RX ─► kernel hash(src_ip,src_port,dst_ip,dst_port) % N
            │
   ┌────────┼────────┬────────┐
   ▼        ▼        ▼        ▼
 worker_0  worker_1  worker_2  worker_3
 (Each worker has its own listening socket. Zero master involvement.)
```

The production failure mode of `SO_REUSEPORT` is connection skew when one worker is slow. Because dispatch is hash-based, a worker that is CPU-bound on a single slow request will keep accepting new connections that hash to it, growing its `accept_queue` (governed by `net.core.somaxconn`, default 4096 on modern kernels) until it overflows and the kernel starts dropping SYNs silently. The client experiences this as a multi-second stall followed by a TCP retransmit storm. The diagnostic is `ss -ltn` showing wildly different `Recv-Q` counts across the worker listening sockets — they should all be near zero under healthy load.

### Controlling socket timeouts: `SO_RCVTIMEO`, `SO_SNDTIMEO`, and `SO_KEEPALIVE`

`SO_RCVTIMEO` and `SO_SNDTIMEO` take a `struct timeval` and convert blocking `recv()`/`read()` and `send()`/`write()` calls into bounded waits: if no data arrives within the specified interval, the call returns -1 with `errno=EAGAIN` (or `EWOULDBLOCK`, which on Linux is the same value). The kernel implements this by arming an hrtimer (high-resolution timer) on the wait queue the calling thread is sleeping on; when the timer fires, the wait queue entry is woken with `-EINTR` translated to `-EAGAIN` before the syscall returns. This is the simplest way to put a hard ceiling on per-request latency without going fully non-blocking and switching to `epoll`. A blocking HTTP server that wants to drop slowloris-style slow-body clients sets `SO_RCVTIMEO` to 30 seconds on every accepted socket and lets the kernel do the timeout bookkeeping.

`SO_KEEPALIVE` solves a different problem: detecting a peer whose host has crashed, been network-partitioned, or had its NIC silently fail — none of which send a TCP FIN. Without keepalive, a server that sends nothing will hold the connection open forever, leaking a file descriptor and an `sk_buff` allocation. With `SO_KEEPALIVE` set, the kernel starts sending probe segments (a 0-byte segment with sequence number one less than the highest sent, triggering an ACK from a live peer) after `tcp_keepalive_time` seconds of idle (default 7200s = 2 hours on stock Linux), repeating every `tcp_keepalive_intvl` (default 75s), and giving up after `tcp_keepalive_probes` (default 9) unanswered probes. After `2h + 9*75s = 2h11m15s` of dead peer, the kernel returns `ETIMEDOUT` on the next `recv()`/`send()`.

The 2-hour default is a relic of 1980s ARPANET billing and is wrong for every modern workload. Per-socket tuning uses the `TCP_KEEPIDLE`, `TCP_KEEPINTVL`, and `TCP_KEEPCNT` socket options (Linux-specific extensions) — for example a chat server might set `TCP_KEEPIDLE=60`, `TCP_KEEPINTVL=10`, `TCP_KEEPCNT=3` so dead peers are detected in ~90 seconds. Globally, the sysctls `net.ipv4.tcp_keepalive_time`, `net.ipv4.tcp_keepalive_intvl`, and `net.ipv4.tcp_keepalive_probes` tune every socket that has `SO_KEEPALIVE` set but did not override per-socket. A production setting for an HTTP API server is `tcp_keepalive_time=300` (5 min) — short enough to detect a NAT reboot within a request cycle, long enough to not waste bandwidth on idle HTTP/1.1 keepalive connections.

The interaction with mobile clients is the failure mode that bites people. Cellular NATs typically time out idle TCP mappings in 5–10 minutes; if the server's `tcp_keepalive_time` is 2 hours, the NAT silently drops the mapping before the first probe is ever sent, and the next `send()` from the server returns `EPIPE`/`SIGPIPE` after the kernel's retransmit timeout (about 15 retries, ~924 seconds with default `tcp_retries2=15`). The fix is to either lower `tcp_keepalive_time` below the NAT timeout or — better — run an application-level heartbeat (WebSocket PING, gRPC keepalive) at 30–60 second intervals, because only the application knows whether the idle connection is supposed to be alive.

```c
/* Production keepalive settings for a mobile-facing API server */
int opt = 1;
int idle = 60;     /* TCP_KEEPIDLE: seconds before first probe */
int intvl = 10;    /* TCP_KEEPINTVL: seconds between probes */
int cnt = 3;       /* TCP_KEEPCNT: probes before giving up */
setsockopt(fd, SOL_SOCKET,  SO_KEEPALIVE,   &opt,   sizeof(opt));
setsockopt(fd, IPPROTO_TCP, TCP_KEEPIDLE,   &idle,  sizeof(idle));
setsockopt(fd, IPPROTO_TCP, TCP_KEEPINTVL,  &intvl, sizeof(intvl));
setsockopt(fd, IPPROTO_TCP, TCP_KEEPCNT,    &cnt,   sizeof(cnt));

struct timeval tv = { .tv_sec = 30, .tv_usec = 0 };
setsockopt(fd, SOL_SOCKET, SO_RCVTIMEO, &tv, sizeof(tv));
setsockopt(fd, SOL_SOCKET, SO_SNDTIMEO, &tv, sizeof(tv));
```

### TCP performance tuning: Disabling Nagle's Algorithm via `TCP_NODELAY`

Nagle's algorithm (RFC 896, John Nagle, 1984) addresses the "small-packet problem" of 1980s WANs: when an application writes one byte at a time over a 56 kbit/s link, each byte costs 41 bytes of TCP+IP header overhead, and the network drowns in tinygrams. The rule is: if there is unACKed data in flight, hold small writes in the send buffer until either an ACK arrives or enough data accumulates to fill an MSS (typically 1460 bytes). On a transatlantic link with 100 ms RTT, this means a 100-byte write followed by another 100-byte write is delayed by 100 ms while waiting for the ACK of the first.

The delayed ACK mechanism (RFC 1122) compounds the problem. To reduce pure-ACK traffic, a receiver does not ACK every segment immediately — it waits up to 40 ms (default `tcp_delack_min` on Linux, hardcoded; `tcp_ato` runs up to 40 ms via `tcp_ack_timer`) for either reverse traffic to piggyback on or for a second segment to arrive that triggers an immediate ACK. When a sender writes small payloads and waits for a response (the canonical request-response pattern of Redis, HTTP, MySQL, gRPC) Nagle delays the second write while delayed ACK delays the ACK that would release it — producing a steady 40 ms latency floor on every request that happens to land just after a previous ACK.

The combination is so common it has a name: **Nagle+delayed-ACK interaction**, the source of most "my latency is mysteriously 40ms" reports. The fix is `TCP_NODELAY`, which disables Nagle entirely and lets every `send()` go out immediately. Every modern low-latency protocol sets it: Redis (`tcp-nodelay yes` by default since 2.8), Nginx (always sets `TCP_NODELAY` on client sockets; controlled on upstream sockets via `proxy_tcp_nodelay`), gRPC (the HTTP/2 transport sets it on every connection), PostgreSQL (`tcp_nodelay` parameter, default on). For interactive protocols (SSH, terminal emulators, gaming) disabling Nagle is non-negotiable — 40 ms of input lag on every keystroke is unacceptable.

The opposite knob is `TCP_CORK` (Linux-specific): when set, the kernel holds back small packets entirely until either the cork is released (the application calls `setsockopt(TCP_CORK, 0)`) or the buffer fills an MSS. This is the right tool when an application knows it is about to emit a burst of small writes that should be coalesced into one segment — for example, an HTTP server sending headers then a small body. The Nginx `sendfile on;` directive, combined with `tcp_nopush on;` (the Nginx name for `TCP_CORK`), lets Nginx cork the socket before calling `sendfile(2)`, so the HTTP headers and the first chunk of file data go out in a single TCP segment, then uncorks for the rest of the file. This is why a stock Nginx can saturate a 10 Gbit/s link with default settings where a naive server cannot.

The production failure mode is two-directional: leaving Nagle enabled on a request-response protocol produces the 40 ms floor; disabling it on a write-heavy streaming protocol that emits many 1-byte writes (a logging agent sending JSON line-by-line) can quadruple bandwidth usage and saturate the kernel's packet allocator. The diagnostic is `tcpdump -i any -A -s0 port 6379 | wc -l` on a Redis client — if you see one packet per `SET` command, Nagle is doing its job; if you see three (one for the command, one for the ACK, one for the response), you have either Nagle or delayed-ACK overhead. The right answer is almost always `TCP_NODELAY` for the application layer and explicit batching (a single `send()` for the whole request, or `TCP_CORK` for header+body patterns) for the transport layer.

```c
/* The canonical low-latency socket setup used by Redis, Nginx, and gRPC */
int opt = 1;
setsockopt(fd, IPPROTO_TCP, TCP_NODELAY, &opt, sizeof(opt));

/* HTTP server sending headers + body in one segment */
int cork = 1;
setsockopt(fd, IPPROTO_TCP, TCP_CORK, &cork, sizeof(cork));
write(fd, headers, hdr_len);          /* buffered, not sent */
sendfile(fd, file_fd, &off, body_len); /* buffered with headers */
cork = 0;
setsockopt(fd, IPPROTO_TCP, TCP_CORK, &cork, sizeof(cork)); /* flush now */
```

## How This Connects to the Runtimes

Every runtime covered in section 04 is a user-space wrapper around these kernel primitives:

- **JVM**: Maps Java threads 1:1 to OS threads via NPTL. The JVM's memory model (section 04.01) is a specification layered on top of the kernel's virtual memory system described here. Netty's `ChannelOption.SO_RCVBUF` and `ChannelOption.TCP_NODELAY` map 1:1 to the `setsockopt()` calls above.
- **Node.js / libuv**: The event loop (section 04.02) is a Reactor pattern built on `epoll_wait()`. The worker thread pool uses OS threads for operations that cannot be multiplexed (file I/O, DNS, crypto). libuv sets `TCP_NODELAY` by default on every `uv_tcp_t`.
- **CPython**: The GIL (section 04.03) is a mutex that serializes Python bytecode execution across OS threads. Multi-processing in Python uses `fork()` to bypass the GIL. Python's `socket.setsockopt()` is a thin FFI around `setsockopt(2)`.
- **PHP-FPM**: Each worker is a separate OS process (section 04.04). The shared-nothing model is a direct consequence of the process isolation described in the Linux Process Model note.

When you read those runtime notes, come back here and trace which kernel primitive each runtime feature maps to.
