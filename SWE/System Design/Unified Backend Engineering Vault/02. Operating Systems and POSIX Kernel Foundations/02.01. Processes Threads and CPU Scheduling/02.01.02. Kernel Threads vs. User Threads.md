# 02.01.02. Kernel Threads vs. User Threads

## What This Is

**Kernel Threads vs. User Threads** is the second foundational primitive in the process-and-scheduling stack. Where 02.01.01 covered the process (an isolated address space with its own PID), this note covers the thread (a schedulable execution context that may share an address space with siblings). The distinction matters because every runtime in section 04 makes an explicit choice about its threading model: the JVM and CPython use the 1:1 model (one OS thread per language-level thread, so blocking calls block the OS thread), Node.js and Redis use a single-thread reactor (one OS thread driving many user-space continuations), and Go and Java (with Project Loom) use the M:N model (many user-space schedulable units multiplexed onto a small pool of OS threads). The choice dictates how the runtime handles blocking syscalls, how it scales across CPU cores, and how it responds to a 100-millisecond `fsync` or a 30-second DNS lookup.

The reason this note sits in section 02 is that the threading model is a kernel ABI contract, not a language feature. `clone()` is the syscall every thread creation ultimately calls, regardless of whether the language calls it `pthread_create`, `Thread.start`, `threading.Thread`, `go func()`, or `Thread.ofVirtual().start()`. The differences are entirely in user-space scheduling policy — what the runtime does between the language-level "thread" and the OS-level `task_struct`. Understanding the three models (1:1, N:1, M:N) and their tradeoffs is what lets you read a runtime's documentation and immediately predict its blocking-call behavior.

## The Details

### The 1:1 Threading Model (Linux NPTL - Native POSIX Thread Library) vs. M:N Green Threading Models

Linux implements threads using the **1:1 model**: every user-space thread is exactly one kernel-schedulable entity, and there is no user-space scheduler deciding which thread runs on which OS thread. The syscall that creates a thread is `clone()`, which is the same syscall that creates a process (`fork()` is just `clone()` with a restrictive set of flags). The flags that turn a fork into a thread creation are `CLONE_VM` (share the virtual memory descriptor — same address space), `CLONE_FILES` (share the file descriptor table), `CLONE_SIGHAND` (share signal handlers), `CLONE_THREAD` (put the new task in the same thread group, so it has the same PID but a different TID), `CLONE_FS` (share the working directory and root), and `CLONE_SETTLS` (set up a new Thread Local Storage segment). This is the **Native POSIX Thread Library (NPTL)** implementation, which replaced the older LinuxThreads M:N-ish model in kernel 2.6 (2003) and is what every modern glibc `pthread_create` calls.

The 1:1 model has two enormous advantages. First, blocking syscalls are transparent: if a 1:1 thread calls `read()` on a socket with no data, the kernel parks that one `task_struct` on the socket's wait queue, and every other thread in the process keeps running. There is no user-space scheduler that has to notice the block and migrate work to another OS thread. Second, multi-core parallelism is automatic: the kernel scheduler (CFS, see 02.01.03) will run one thread on each available CPU with no user-space coordination. The cost of these advantages is that every thread is a real kernel object: it consumes a `task_struct` (~8 KB of kernel memory), a kernel stack (8 KB or 16 KB depending on config), and a user-space stack (default 8 MB reserved, ~80 KB committed at startup), and it must be scheduled by the kernel even when it has nothing to do. A million OS threads is not feasible — the kernel memory alone is 24 GB before any application code runs, and the kernel scheduler cannot reasonably manage a runqueue of that size.

The **M:N model** (many user-space threads on a few OS threads) exists to break that scaling ceiling. In an M:N runtime, the language exposes millions of "lightweight threads" or "goroutines" or "virtual threads" or "processes" (Erlang's term), and a user-space scheduler maps these onto a small pool of OS threads (typically `GOMAXPROCS` for Go, `ForkJoinPool.commonPool` parallelism for Java virtual threads, the number of schedulers for Erlang). The user-space scheduler can do context switches in tens of nanoseconds (just save a few registers and swap a stack pointer — no kernel involvement, no TLB flush) and can size thread stacks dynamically (Go's goroutines start at 2 KB and grow by copying, Java's virtual threads start at ~512 bytes and use the heap for their stack). The cost is that any operation that would block the OS thread must be intercepted by the runtime so it can park the lightweight thread and run another — Go does this by replacing every blocking syscall with a non-blocking equivalent and yielding the OS thread back to the scheduler; Java's Project Loom does this by hooking into the JDK's networking stack so that `Socket.read` parks the virtual thread instead of the carrier OS thread. The **N:1 model** (many user threads on exactly one OS thread, like the old Java green threads pre-1.2) is now historical curiosity — it cannot use multiple cores and a single blocking syscall freezes the entire runtime.

```c
/* NPTL 1:1 — what pthread_create actually calls.
   Simplified; the real glibc code does TLS setup, stack guard pages, etc. */
#include <sched.h>
#include <sys/syscall.h>

int my_pthread_create(void *(*start)(void *), void *arg) {
    void *stack = mmap(NULL, 8 * 1024 * 1024,         // 8 MB stack
                       PROT_READ | PROT_WRITE,
                       MAP_PRIVATE | MAP_ANONYMOUS | MAP_STACK,
                       -1, 0);
    /* clone() is the syscall; the flags below say: share VM, FDs, signal
       handlers, and treat the result as a thread (same PID, new TID). */
    long tid = syscall(SYS_clone,
                       CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SIGHAND
                       | CLONE_THREAD | CLONE_SIGHAND | CLONE_SETTLS,
                       (char *)stack + 8 * 1024 * 1024,  /* child stack */
                       NULL, NULL, NULL);
    if (tid == 0) {                /* in the child (thread) */
        start(arg);
        _exit(0);
    }
    return (int)tid;                /* in the parent */
}
```

```go
// M:N — Go goroutines.  One million of these is routine.
// Internally, go func() schedules a G (goroutine) on a P (processor)
// bound to an M (OS thread).  The G's stack starts at 2 KB and grows
// by copying if the function recurses deeply.
package main

import (
    "fmt"
    "sync"
)

func main() {
    var wg sync.WaitGroup
    for i := 0; i < 1_000_000; i++ {
        wg.Add(1)
        go func(n int) {
            defer wg.Done()
            // Each goroutine blocks on its own channel; the runtime
            // parks the G and runs others on the same M.
            ch := make(chan int, 1)
            ch <- n
            _ = <-ch
        }(i)
    }
    wg.Wait()
    fmt.Println("done")
}
```

```java
// M:N — Java 21 virtual threads (Project Loom).  A virtual thread is a
// continuation that the JDK schedules onto carrier threads from a
// ForkJoinPool sized to Runtime.availableProcessors().
public class VT {
    public static void main(String[] args) throws InterruptedException {
        try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
            IntStream.range(0, 1_000_000).forEach(i ->
                exec.submit(() -> {
                    Thread.sleep(Duration.ofMillis(100)); // parks the VT, not the carrier
                    return null;
                }));
        }
        // Total memory footprint: ~1 GB for 1M virtual threads;
        // doing the same with platform threads would need ~8 TB of stack.
    }
}
```

The connection to the layered model is direct: the JVM platform threads, the CPython `threading.Thread` (each backed by an NPTL thread, serialized by the GIL), and the C++ `std::thread` are all 1:1 — they cost 8 MB of stack each, they block the OS thread on syscall, and they cannot scale past tens of thousands per process. Go's goroutines, Java's virtual threads, and Erlang's processes are all M:N — they cost a few KB each, they yield to the runtime on blocking calls, and they scale to millions. When you read the runtime notes in section 04, the first thing to identify for each runtime is which model it uses, because that single fact determines its concurrency ceiling.

### Thread creation via `clone()` with shared virtual memory, file descriptor tables, and signal handlers

The `clone()` syscall is the single primitive that creates both processes and threads in Linux — `fork()` and `vfork()` and `pthread_create()` are all wrappers around it. The first argument to `clone()` is a function pointer (the child's entry point), the second is a stack pointer (the child's stack — `clone` does NOT allocate one for you), and the third is the flags word that determines what is shared with the parent. The flags break into three categories: resource-sharing flags (`CLONE_VM`, `CLONE_FILES`, `CLONE_FS`, `CLONE_SIGHAND`, `CLONE_PARENT`, `CLONE_IO`), identity flags (`CLONE_THREAD` makes the child part of the parent's thread group; without it, the child is a separate process), and namespace/cgroup flags (`CLONE_NEWPID`, `CLONE_NEWNET`, `CLONE_NEWUSER`, `CLONE_NEWNS` — these are what `unshare` and container runtimes use). The full list is in `man 2 clone`; the ones every backend engineer should know by heart are `CLONE_VM` (share address space — without this you have a process, with it you have a thread), `CLONE_FILES` (share the FD table — this is why all threads in a JVM can write to `System.out` simultaneously), and `CLONE_THREAD` (the new task is in the parent's thread group, so the parent's `wait()` will not reap it; instead the whole thread group is waited on via `tgkill` and the thread exit signal).

The signal-handler sharing (`CLONE_SIGHAND`) is the subtle one. Threads in the same process share signal handlers — if thread A calls `signal(SIGTERM, handler)`, thread B will use the same handler. But signal *masking* is per-thread (`sigprocmask` operates on the calling thread only), and signal *delivery* is per-thread — a signal sent via `tgkill(tgid, tid, sig)` goes to a specific thread, while a signal sent via `kill(pid, sig)` is delivered to any thread in the process that has it unblocked. This is why `pthread_kill` exists: it lets you direct a signal to a specific thread. The default behavior is that the kernel picks an unblocked thread arbitrarily, which means a signal handler in a multi-threaded program must be re-entrant (multiple threads can be inside it simultaneously) and must only call async-signal-safe functions. The shared-signal-handler constraint is the reason NPTL requires `CLONE_SIGHAND` to be set if `CLONE_THREAD` is set — having different threads in the same thread group with different signal handlers would be incoherent.

The file-descriptor-table sharing (`CLONE_FILES`) is the most consequential for I/O. When a thread opens a file (`open()`), the new FD is added to the shared `files_struct` — every other thread in the process can immediately see and use that FD. This is what makes thread pools possible: a single acceptor thread can call `accept()` and hand the resulting client FD to a worker thread by writing it to a queue; the worker thread reads the FD integer off the queue and immediately uses it in `recv()`. There is no need to "transfer" the FD because it was always in the shared table. The shared table is also why closing a socket in one thread while another is reading from it is a real and dangerous bug — the close happens at the table level, and the read on the (now-stale) FD will either return `EBADF` or, worse, succeed against an unrelated FD that was reallocated to the same integer by a concurrent `open()` in a third thread. The fix is to use `O_CLOEXEC` for FDs that should not survive `execve`, and to coordinate closes with explicit ownership transfer (or use `dup`/`dup2` to give each thread its own FD that points to the same open-file description, then close that one FD without affecting the others).

```bash
# Watch pthread_create call clone() under the hood
$ strace -e trace=clone -f ./a.out 2>&1 | head -4
clone(child_stack=0x7f00a0000f00,
      flags=CLONE_VM|CLONE_FS|CLONE_FILES|CLONE_SIGHAND|CLONE_THREAD
            |CLONE_SYSVSEM|CLONE_SETTLS|CLONE_PARENT_SETTID
            |CLONE_CHILD_CLEARTID, parent_tidptr=0x7f00a00009d0,
      tls=0x7f00a0000700, child_tidptr=0x7f00a00009d0) = 12345
```

The production failure mode here is FD racing in multi-threaded servers. A classic bug: thread A accepts a connection (FD 7), hands 7 to thread B in a queue, then accepts another connection — but `accept()` may reuse FD 7 if thread B has not yet called `recv()` on it (the kernel recycles the lowest available integer). Now thread B calls `recv(7)` and is reading from the wrong client. The fix is either to use `accept4` with `SOCK_CLOEXEC` so the FD is not accidentally shared with a forked child, or to coordinate via a real ownership-transfer API like Go's `os.NewFile(fd).Fd()` pattern that wraps the integer in a higher-level object. The lesson is that the 1:1 model makes sharing easy (everything is shared by default) and that easiness is also the hazard — the developer must explicitly opt out of sharing (`O_CLOEXEC`, `pthread_attr_setguardsize`, `pthread_mutexattr_setpshared`) when isolation is needed.

### Thread Local Storage (TLS): Stack allocations, thread-specific heap pointers, and lifecycle management

Thread Local Storage (TLS) is the mechanism by which each thread gets its own private copy of a variable, accessed through a single shared name. Without TLS, every shared variable in a multi-threaded program would need a lock — and locks are expensive (an uncontended `pthread_mutex_lock` is ~25 nanoseconds, a contended one is microseconds, plus the cache-line bouncing across cores). TLS sidesteps the lock entirely: the variable lives in a per-thread memory region, accessed through the FS (or GS on x86-64 Windows) segment register, which the CPU uses as a base address. Reading a TLS variable is one instruction (`mov %fs:0x10, %rax`) — no lock, no cache miss across cores, no contention. The Linux kernel sets up the FS base for each new thread via the `CLONE_SETTLS` flag to `clone()`; the value passed is the address of a `pthread` struct that glibc maintains for each thread.

The C11, C++11, and Java `ThreadLocal` keywords all map to this mechanism. `__thread int x;` in C, `thread_local int x;` in C++, `static ThreadLocal<Integer> x = ...;` in Java, `__declspec(thread) int x;` on MSVC — all allocate the variable in per-thread storage that the runtime initializes lazily on first access or eagerly on thread creation, depending on the implementation. The lifecycle is critical: TLS variables are constructed when the thread starts (or on first use, for some implementations) and destructed when the thread exits, but they are NOT inherited across `fork()` — a child process gets fresh TLS state (the kernel copies the parent's TLS block, but C++ TLS destructors do not run in the child, which is a known footgun). TLS is also the storage class used by every runtime to find "the current thread": CPython stores a pointer to the current `PyThreadState` in TLS so that `PyThreadState_Get()` is O(1); the JVM stores a pointer to the current `JavaThread*` so that JNI code can find the thread's `JNIEnv` quickly; glibc stores the current thread's `errno` location in TLS so that `errno` is per-thread (without TLS, `errno` would have to be a global, and concurrent syscalls in different threads would corrupt each other's error codes).

Each thread also has its own stack — allocated from the mmap region, default 8 MB on Linux (configurable via `ulimit -s` shell-builtin, or `pthread_attr_setstacksize` programmatically, or `RLIMIT_STACK` rlimit). The stack is reserved lazily: the 8 MB is a virtual reservation, but only the pages actually touched are committed to physical RAM. The kernel implements this by setting a `MAP_GROWSDOWN` flag on the stack VMA and using guard pages — a 4 KB page at the bottom of the stack is mapped `PROT_NONE`, so that a stack overflow triggers a `SIGSEGV` (rather than silently corrupting the next VMA, which is usually the heap). The default 8 MB is enormous for most workloads — Java's HotSpot defaults to 1 MB per platform thread, Go uses 2 KB initial for goroutines, Erlang uses 4 KB — and the 8 MB number exists for historical reasons (legacy code with deep recursion). The reason this matters for backend engineering is that the stack size caps the number of threads you can have: 8 MB × 10,000 threads = 80 GB of virtual address space (with ~80 KB actually committed), which is fine on a 64-bit system but does consume page-table entries and TLB slots. Reducing the stack to 256 KB lets you have 80,000 threads in the same address space budget, which is why Java app servers almost always tune `-Xss256k`.

```c
/* TLS via __thread keyword (C11) — compiles to a single fs-segment load. */
#include <stdio.h>
#include <pthread.h>
#include <errno.h>

static __thread int  tls_counter = 0;       // per-thread, zero-initialized
static __thread char tls_buf[64];           // per-thread scratch buffer

void *worker(void *arg) {
    tls_counter = (int)(long)arg;
    snprintf(tls_buf, sizeof tls_buf, "thread #%d", tls_counter);
    printf("tid=%lu  buf=%s  errno_addr=%p\n",
           (unsigned long)pthread_self(), tls_buf, &errno);
    return NULL;
}

int main(void) {
    pthread_t t1, t2;
    pthread_create(&t1, NULL, worker, (void*)1);
    pthread_create(&t2, NULL, worker, (void*)2);
    pthread_join(t1, NULL);  pthread_join(t2, NULL);
    // Each thread sees its own tls_counter, tls_buf, and errno.
    // No locking was required.
}
```

```bash
# Confirm each thread has its own errno address
$ ./tls_demo
tid=139849182947072  buf=thread #1  errno_addr=0x7f1d4c3f0694
tid=139849174554368  buf=thread #2  errno_addr=0x7f1d4bbf4694
# Different errno_addr values = different TLS blocks = no false sharing.

# See the TLS segment in /proc/<pid>/maps
$ cat /proc/self/maps | grep -E '\[stack|tls|\[heap'
7f1d4c3f1000-7f1d4c3f3000 rw-p 00000000 00:00 0     # TLS region
7ffdf80a3000-7ffdf80c4000 rw-p 00000000 00:00 0 [stack]
```

The connection to the upper layers is direct: every runtime that exposes thread identity uses TLS to find it. When you call `Thread.currentThread()` in Java, the implementation is essentially `return (Thread) tls_get(current_thread_key);` — a single fs-segment load. When you call `asyncio.get_running_loop()` in Python, the same trick: the current event loop is stored in TLS so that any coroutine can find its scheduler. The failure mode is abuse: TLS is so cheap that it becomes a global-variable escape hatch, and engineers start storing per-request state (like the current user, the current trace span, the current tenant) in TLS — which then leaks across requests if the thread is pooled and the TLS is not reset between requests. This is the source of countless "user A sometimes sees user B's data" bugs in Java app servers, and it is why modern frameworks (Spring 6, Micronaut, Quarkus) explicitly recommend RequestScoped beans backed by thread-local ScopedValue, not raw ThreadLocal.

### Cost of concurrency: Stack allocation overhead per thread (default 1MB/8MB limits) and system-wide thread limits

The cost of a 1:1 OS thread is dominated by three things: the user-space stack (8 MB reserved on Linux, ~80 KB committed at startup), the kernel structures (`task_struct` ~8 KB, kernel stack 8 KB or 16 KB), and the page-table entries needed to map the stack. On a 64-bit system the virtual address space is enormous (2^47 bytes user-space), so the 8 MB reservation is not a problem in terms of address space — but the page-table entries are real. Each 4 KB stack page that is touched requires a PTE, and the kernel must track the VMA. For 10,000 threads, that is 80 GB of reserved address space, ~800 MB of committed memory, and roughly 100,000 PTEs across 10,000 VMAs — which is enough to noticeably inflate the process's RSS just from kernel bookkeeping. For 100,000 threads, the numbers get prohibitive, and for 1,000,000 threads the kernel cannot keep up at all.

This ceiling is what drove the invention of M:N runtimes. A Go goroutine starts with a 2 KB stack (growable on demand by copying to a larger allocation), so 1,000,000 goroutines need ~2 GB of memory — a 400x reduction over OS threads. A Java virtual thread starts with a stack allocated from the JVM heap (typically a few hundred bytes for a shallow call chain, growing as needed), so 1,000,000 virtual threads need a few hundred MB. An Erlang process starts at ~300 bytes. The tradeoff is that the runtime must intercept every blocking syscall — Go does this in its runtime, Java does it in the JDK's networking classes, Erlang does it by replacing every syscall with a message-passing equivalent — and the user-space scheduler must run on top of OS threads, adding a layer of context-switch cost when a goroutine migrates from one OS thread to another.

There are also hard system-wide limits. `RLIMIT_NPROC` (set via `ulimit -u`) caps the number of threads a single user can have across all processes. `/proc/sys/kernel/threads-max` caps the system total. `/proc/sys/kernel/pid_max` caps the number of PIDs (Linux allocates thread IDs from the same pool, so this also caps threads). The default `pid_max` on most distros is 32768, which means a system cannot have more than 32K threads/processes total until you `echo 4194304 > /proc/sys/kernel/pid_max`. Cgroups add another layer: the `pids` controller can cap threads per cgroup via `pids.max`. The classic EMFILE-equivalent for threads is `EAGAIN` from `pthread_create` — meaning either `RLIMIT_NPROC` or `threads-max` or `pids.max` has been hit. A common Docker footgun is running a JVM inside a container with the default `pids.max` of 4096 — the JVM will hit `EAGAIN` long before the host does.

```bash
# System-wide thread ceiling
$ cat /proc/sys/kernel/threads-max
63184
$ cat /proc/sys/kernel/pid_max
4194304
$ ulimit -u            # RLIMIT_NPROC for the current shell
63184

# See the count of threads on the system
$ ps -eLf | wc -l
8421

# See the per-process thread count
$ ps -o nlwp,pid,comm -p <pid>      # nlwp = number of lightweight processes
   72  4231  java

# Inside a container — cgroup pids controller
$ cat /sys/fs/cgroup/pids.max
4096
$ cat /sys/fs/cgroup/pids.current
419

# Memory math for 1:1 vs M:N
# 1:1   — 1,000,000 platform threads × 8 MB stack = 8,000 GB (impossible)
# M:N   — 1,000,000 goroutines × 2 KB stack     =   2 GB (routine)
# M:N   — 1,000,000 virtual threads × ~1 KB     =   1 GB (routine)
```

The connection to the layered model is the central lesson of 02.01.02: **if your runtime is 1:1 (JVM platform threads, CPython with the GIL, PHP, raw C/C++ pthreads), your concurrency ceiling is in the tens of thousands and you must use an event loop or a thread pool, not unbounded thread-per-connection**. If your runtime is M:N (Go, Java virtual threads, Erlang, Kotlin coroutines, Python `asyncio` in a different sense — it is single-threaded M:1 but with cooperative scheduling), your concurrency ceiling is in the millions and you can write thread-per-connection code that scales. The C10K problem (see 02.05.01) was the historical inflection point: in 1999, 1:1 threading made 10,000 concurrent connections impossible, which forced the invention of `epoll`-based event loops in C and the M:N runtimes that came later. When you read the runtime notes in section 04, the threading model is the single most important architectural fact about each runtime, and it is decided at this kernel-primitive layer.

## How This Connects to the Runtimes

Every runtime covered in section 04 is a user-space wrapper around these kernel primitives:

- **JVM**: Maps Java threads 1:1 to OS threads via NPTL. The JVM's memory model (section 04.01) is a specification layered on top of the kernel's virtual memory system described here.
- **Node.js / libuv**: The event loop (section 04.02) is a Reactor pattern built on `epoll_wait()`. The worker thread pool uses OS threads for operations that cannot be multiplexed (file I/O, DNS, crypto).
- **CPython**: The GIL (section 04.03) is a mutex that serializes Python bytecode execution across OS threads. Multi-processing in Python uses `fork()` to bypass the GIL.
- **PHP-FPM**: Each worker is a separate OS process (section 04.04). The shared-nothing model is a direct consequence of the process isolation described in the Linux Process Model note.

When you read those runtime notes, come back here and trace which kernel primitive each runtime feature maps to.
