# 02.01.01. The Linux Process Model

## What This Is

**The Linux Process Model** is the load-bearing primitive that every backend runtime — the JVM, V8, CPython, and the Zend Engine — sits on top of. You cannot reason about thread pools, event loops, memory pressure, container isolation, or file-descriptor exhaustion without understanding the kernel mechanism underneath. The reason this note sits in section 02 (before any framework or runtime note) is that every subsequent layer is a wrapper around `task_struct`, `fork`, `execve`, and the process-state machine described here. When a JVM thread blocks on `synchronized`, what is really happening is that a `task_struct` is being moved from the runqueue to a wait queue; when PHP-FPM spawns a worker, what is really happening is `fork()` + `execve()` against the PHP binary. Every runtime concept in section 04 maps to one of the primitives in this note.

The Linux process model is unusual in two ways. First, Linux does not distinguish internally between a "process" and a "thread" — both are `task_struct`s; the difference is which kernel resources they share (memory, file table, signal handlers) via the `clone()` flags. Second, Linux uses a strict parent-child tree rooted at PID 1, and the failure modes of that tree (zombies, orphans, PID-1 reaping) are responsible for an entire category of production container incidents. This note covers both the data structure (`task_struct`) and the lifecycle (creation, state transitions, termination, reaping), then connects them to the runtime behaviors you will see in section 04.

## The Details

### Anatomy of a Process: Task structures (`task_struct`), Process Control Blocks (PCB), and Process IDs (PID)

In Linux, every process and every thread is represented in kernel memory by a `task_struct` — a roughly 8 KB structure (defined in `include/linux/sched.h`) that is the kernel's Process Control Block. It holds the PID (an `pid_t` allocated from a per-namespace idr tree), the PPID, the real and effective UID/GID, the list of open file descriptors (`files_struct`), the memory descriptor (`mm_struct` containing the VMA list and PGD pointer), the signal handlers (`signal_struct` and `sighand_struct`), the scheduling parameters (`sched_entity` containing `vruntime`, nice value, and CPU affinity mask), the saved CPU register state from the last context switch (`thread_struct`), and the credentials (`cred_struct`). Every system call that operates on a process — `kill`, `ptrace`, `sched_setaffinity`, `getpriority` — ultimately looks up a `task_struct` and reads or writes one of these fields.

The PID is not a single global integer the way newcomers often imagine. It is allocated per-namespace: a process can be PID 1000 in the host's init namespace and PID 1 inside a child PID namespace. This is the kernel feature that makes containers work — `unshare(CLONE_NEWPID)` creates a new PID namespace where the first process forked becomes PID 1 in that namespace, even though it has a different PID on the host. The `task_struct` therefore carries a `pids[PIDTYPE_MAX]` array linking it into multiple per-namespace PID hashes, which is why `ps` inside a container sees one PID and `ps` on the host sees another for the same kernel task.

To observe the structure of a running process, the canonical interfaces are `/proc/<pid>/status` (human-readable summary) and `/proc/<pid>/stat` (machine-readable). The `status` file dumps most of the `task_struct` fields you would ever care about — name, state, Tgid, Pid, PPid, Uids, Gids, VmRSS, VmSize, Threads, CapEff. `htop` and `top` are essentially pretty-printers over this file. For the deepest possible visibility, `crash` against a live kernel or a vmcore dump lets you walk `task_struct` fields directly with `struct task_struct.tasks.next`.

```bash
# /proc/<pid>/status is the human-readable view of task_struct
$ cat /proc/self/status | head -25
Name:   bash
Umask:  0022
State:  R (running)
Tgid:   4231
Pid:    4231
PPid:   4229
Threads: 1
...
VmRSS:   5120 kB        # resident set size
VmData:  1680 kB        # heap
VmStk:    136 kB        # stack
voluntary_ctxt_switches:    142
nonvoluntary_ctxt_switches:  3
```

The connection to higher layers is direct: when the JVM's `jstack` reports a thread's `tid`, that number is the Linux TID assigned to the underlying `task_struct`. When CPython's `threading.get_ident()` returns an integer, it is the same value. Every runtime that exposes thread identity is passing through the kernel's `task_struct->pid` field. The failure mode here is resource accounting: because `task_struct` is allocated from a dedicated slab cache (`task_struct_cachep`), a system that forks faster than it reaps will exhaust that cache and `fork()` will start returning `EAGAIN` — the classic fork-bomb symptom. Modern kernels cap this with `RLIMIT_NPROC` and cgroup `pids.max`, both covered in 02.03.03.

### The Process Lifecycle: Creation via `fork()`, program execution via `execve()`, and termination via `exit()`

A new process is created in Linux in two distinct steps that are almost always paired but are mechanically independent: `fork()` clones the caller, and `execve()` replaces the clone's memory image with a new program. `fork()` is implemented in the kernel as `sys_clone` / `sys_fork`, which calls `copy_process()`. That function allocates a new `task_struct` from the slab cache, copies the parent's `mm_struct` via copy-on-write (page-table entries are made read-only on both sides; the actual copy happens lazily when either side writes — see 02.02.01 for the page-fault mechanics), duplicates the file descriptor table (the child's `files_struct` now references the same open-file descriptions as the parent — they share file offsets, which is why shell pipes work), inherits signal handlers, allocates a new PID, attaches the new task to the parent's children list, and returns. The child receives return value 0; the parent receives the child's PID. This dual-return-value semantics is one of the most counterintuitive things in C for newcomers — the same function call returns two different values depending on which process is reading it.

`execve(path, argv, envp)` is the second half. It does not create a new process; it replaces the current process's image. The kernel reads the ELF header of the new executable, unmaps the old VMAs (text, data, heap, stack), maps the new text and data segments read-only / read-write respectively, zero-fills the `.bss`, sets up the initial stack with `argv` and `envp`, fixes up the auxiliary vector (which carries things like `AT_PAGESZ` and `AT_RANDOM` for ASLR), and jumps to the ELF entry point. File descriptors are preserved across `execve` unless they have the `FD_CLOEXEC` flag set — this is the mechanism by which a parent can hand an open socket to a child it spawns (the shell uses it for `2>&1`, the inetd-style superserver uses it for socket activation, systemd uses it for socket-activated units). Modern code uses `posix_spawn` or `vfork`+`execve` to avoid the cost of duplicating page tables in the parent's address space only to throw them away moments later.

Termination happens via `exit(status)` (or `_exit()` for the raw syscall). The kernel frees the process's `mm_struct` (unmaps all VMAs), closes all file descriptors (decrementing the open-file-table refcounts), releases signals and timers, sets the exit code in `task_struct->exit_code`, transitions the task to `EXIT_ZOMBIE` state, and sends `SIGCHLD` to the parent. The `task_struct` itself is NOT freed yet — the parent must call `wait()` or `waitpid()` to read the exit code, at which point `release_task()` frees the structure. If the parent never reaps, the zombie persists indefinitely.

```c
// Canonical fork + exec pattern with proper error handling.
#include <unistd.h>
#include <sys/wait.h>
#include <errno.h>
#include <string.h>
#include <stdio.h>

pid_t pid = fork();
switch (pid) {
case -1:
    perror("fork");              // EAGAIN (RLIMIT_NPROC) or ENOMEM
    _exit(127);
case 0: {                         // child
    char *argv[] = {"echo", "hello from child", NULL};
    char *envp[] = {NULL};
    execve("/bin/echo", argv, envp);
    _exit(127);                   // only reached if execve failed
}
default: {                        // parent
    int status;
    if (waitpid(pid, &status, 0) == -1) {
        perror("waitpid");
    } else if (WIFEXITED(status)) {
        printf("child exited with %d\n", WEXITSTATUS(status));
    } else if (WIFSIGNALED(status)) {
        printf("child killed by signal %d\n", WTERMSIG(status));
    }
}}
```

The production failure mode here is the half-fork-half-exec pattern: a process that forks but never execs (e.g., a worker pool that just calls `fork()` and runs application code in the child) inherits the parent's entire memory layout and file descriptor table. If the parent had a database connection open, the child now has the same connection — and two processes writing to the same Postgres connection will corrupt the wire protocol within seconds. This is why CPython's `multiprocessing` library warns about inherited handles, why Java's `ProcessBuilder` explicitly closes inherited FDs by default, and why Go's `os/exec` package defaults to `/dev/null` for stdin/stdout/stderr unless you override it. The fix in C is to set `FD_CLOEXEC` on every long-lived FD the moment you open it (or use `O_CLOEXEC` in the `open()` flags) so that an accidental `execve` does not leak it.

### Process Trees: Parent-child relationships, Process Groups, Sessions, and the init process (PID 1)

Every `task_struct` carries a `parent` pointer and a `children` list, and these form a single tree rooted at PID 1 — the init process (systemd on modern Linux, `init`/`upstart` on older systems). The tree is exposed through `/proc/<pid>/stat` and is what `pstree` renders. When a parent process dies before its children, the kernel re-parents those orphans to PID 1 (or, more precisely, to the nearest subreaper if one has been declared via `prctl(PR_SET_CHILD_SUBREAPER)` — this is the mechanism Docker uses so that container init can reap zombies even when intermediate processes die). This re-parenting is essential because the kernel needs SOMEONE to be available to call `waitpid()` on the orphans when they exit; PID 1 is the only process guaranteed to outlive everything else.

On top of the parent-child tree, the kernel maintains two more groupings: **process groups** and **sessions**. A process group is identified by a PGID (usually equal to the PID of the group leader) and is set with `setpgid()`. A session is identified by a SID and is set with `setsid()`. These exist so that the kernel can deliver signals to a coherent group: `kill -9 -PGID` sends SIGKILL to every process in the group, and a controlling terminal sends `SIGINT` (Ctrl-C) and `SIGHUP` (terminal hangup) to the entire foreground process group. This is why `Ctrl-C` in a shell kills the foreground command and not your shell itself — the shell puts the command in its own process group before `execve`-ing it, then makes that group the foreground group. Daemon processes call `setsid()` precisely to detach from any controlling terminal so that a `SIGHUP` from a closing SSH session does not kill them.

PID 1 has special responsibilities beyond reaping orphans. It is the only process that the kernel will not SIGKILL by default during shutdown (it gets a grace period, then is killed last). It is the only process that can ignore `SIGTERM` and `SIGKILL` is delayed until it has called `reboot()` or exited. Critically, PID 1 must call `waitpid()` on adopted orphans — if it does not, the zombie pile-up will eventually exhaust the PID namespace. This is why naive Docker containers that run `java -jar app.jar` directly as PID 1 are a production hazard: the JVM does not implement zombie reaping, signal forwarding, or orphan adoption. The standard fix is to install `tini` (a tiny init written in C, ~10 KB) as PID 1, which does three things and only three things: reaps zombies, forwards signals to the JVM, and exits when the JVM exits.

```bash
# Show the process tree rooted at PID 1
$ pstree -p 1
systemd(1)─┬─systemd-journal(421)
           ├─systemd-udevd(463)
           ├─dbus-daemon(514)
           ├─sshd(876)───sshd(1234)───bash(1240)───pstree(1305)
           └─...

# Show the session and process group of the current shell
$ ps -o pid,ppid,pgid,sid,tty,comm
  PID  PPID  PGID   SID TT       COMM
 1240  1239  1240  1240 pts/0    bash
 1305  1240  1240  1240 pts/0    ps
# Note: ps is in the same PGID/SID as bash because it was forked from bash
```

The connection to the upper layers is direct. PHP-FPM's process manager is a tree: a master process forks N worker children, each worker accepts one request, handles it, and exits (or is recycled). The master must `waitpid()` on each worker to read its exit status and decide whether to spawn a replacement; if the master is killed with `SIGKILL` and no subreaper is set, the workers get re-parented to PID 1 and become orphans — still consuming memory and still listening on the PHP-FPM socket. The same pattern appears in Celery, in Sidekiq, in the JVM's `ProcessHandle` API, and in every forking supervisor ever written. The failure mode is always the same: a parent that dies without reaping leaves zombies; a parent that is killed without a subreaper leaves orphans; and a PID 1 that does not implement signal forwarding (like the raw `java -jar` container) ignores `SIGTERM` and gets SIGKILLed after the Docker grace period, losing in-flight requests.

### Process States: Running (`TASK_RUNNING`), Interruptible Sleep (`TASK_INTERRUPTIBLE`), Uninterruptible Sleep (`TASK_UNINTERRUPTIBLE`), Stopped, and Zombie (`EXIT_ZOMBIE`)

A Linux process is always in exactly one task state, exposed as the third field of `/proc/<pid>/stat` and as the `STAT` column in `ps`. The state machine is the contract between the scheduler and the rest of the kernel: the scheduler only runs tasks in `TASK_RUNNING`; everything else is on a wait queue somewhere and will be woken by an event (I/O completion, signal, timeout, child exit). The five states a sysadmin cares about are R (running or runnable), S (interruptible sleep), D (uninterruptible sleep), T (stopped), and Z (zombie). There are a few more (`TASK_KILLABLE`, `TASK_TRACED`, `TASK_PARKED`, `TASK_IDLE`) but the five above are what you will see in `top` and what every on-call runbook keys off.

```text
                 ┌──────────────────────────┐
       fork()    │   TASK_RUNNING (R)       │  ← on a runqueue
       ───────►  │   runnable or running    │     ready to consume CPU
                 └──────────┬───────────────┘
                            │
              ┌─────────────┼──────────────┐
   read/recv/ │              │              │ clock IRQ + need_resched
   wait/sleep │              │              │ (preemption)
              ▼              │              ▼
  ┌───────────────────┐      │     ┌────────────────────┐
  │ TASK_INTERRUPTIBLE│      │     │  still TASK_RUNNING │
  │   (S)             │      │     │  (running on CPU)   │
  │ on a wait queue;  │      │     └────────────────────┘
  │ signal can wake   │      │
  └─────────┬─────────┘      │
            │ I/O done or    │
            │ signal arrived │
            └────────────────┘

   Disk I/O / NFS / fsync    SIGSTOP / ptrace attach      exit()
        ▼                          ▼                          ▼
  ┌───────────────────┐     ┌──────────────────┐    ┌──────────────────┐
  │TASK_UNINTERRUPTIBLE│     │ TASK_STOPPED (T) │    │  EXIT_ZOMBIE (Z) │
  │   (D)              │     │ frozen until     │    │  dead but parent │
  │ cannot be killed   │     │ SIGCONT          │    │  has not reaped  │
  └─────────┬──────────┘     └──────────────────┘    └──────────────────┘
            │ I/O done                                 │ waitpid() by parent
            └──────────────────────────────────────────┘
```

`TASK_INTERRUPTIBLE` (state `S`) is by far the most common state for an idle backend process. A web server waiting on `accept()` is in `S`. A JVM thread blocked on `synchronized` is in `S`. A Python worker waiting on `recv()` is in `S`. The defining property is that the task is on a kernel wait queue and can be woken by a signal — `SIGTERM` will dequeue it, run its signal handler, and (usually) cause the process to exit cleanly. This is why `kill <pid>` works on a sleeping server: the signal arrives, the kernel marks the task `TASK_RUNNING` again, the scheduler picks it up, and the signal handler runs.

`TASK_UNINTERRUPTIBLE` (state `D`) is the dangerous one. A task in `D` cannot be woken by a signal — not even `SIGKILL`. The kernel puts a task in `D` when it is in the middle of an operation that cannot be safely interrupted, typically a disk I/O operation in progress. The classic causes are: an `fsync()` that is waiting on the disk controller, an NFS read waiting on a remote server that has gone away, a page fault on a memory-mapped file that needs to be paged in, or a kernel-mode driver bug. A process stuck in `D` state will hold its file descriptors, its memory, and its port bindings open until the I/O completes (which may be never) or the system reboots. The standard diagnostic is `cat /proc/<pid>/stack` to see the kernel call stack — if it shows `nfs_wait_bit_killable` or `io_schedule` or a SCSI driver function, you have found the culprit. There is no user-space recovery; the only fix is to repair the underlying I/O (re-mount the NFS share, replace the failing disk, reboot).

`EXIT_ZOMBIE` (state `Z`) is the post-termination pre-reaping state. The process has called `exit()`, all its resources are freed, but its `task_struct` is kept alive so the parent can call `waitpid()` and read the exit code. A zombie consumes almost no memory (just the `task_struct` and the PID slot) but it does consume a PID — and PIDs are a finite resource (default `pid_max` is 32768, raised to 4194304 on modern systems). A server that leaks zombies will eventually be unable to fork new workers because the kernel has run out of PIDs, and the symptom in `ps` will be hundreds of `<defunct>` processes. The fix is always the same: the parent must call `waitpid()`, and if the parent is itself wedged, killing the parent (or sending it `SIGCHLD`) is the recovery path.

### Zombie processes and Orphan processes: Mechanics of `wait()`, `waitpid()`, and reaping dead children

A zombie is what remains of a child process after it has called `exit()` but before its parent has acknowledged the death by reading the exit code. Mechanically, the child's `task_struct` is in `EXIT_ZOMBIE` state, its `mm_struct` and `files_struct` are already freed, but the `task_struct` itself and the PID are pinned until the parent calls `wait()` or `waitpid()` (or `waitid()`, which is the modern preferred interface). The kernel keeps the zombie because the exit code, the resource usage (`rusage` — user CPU time, system CPU time, max RSS, page faults, context switches), and the exit signal reason are all stored in the `task_struct` and have to be readable by the parent. Once the parent reads them, `release_task()` runs and the structure is freed back to the `task_struct_cachep` slab.

`waitpid(pid, &status, options)` is the syscall that performs the reaping. Its first argument is the child PID to wait for (or `-1` for any child, or `-PGID` for any child in a process group), the second is a pointer to an int that will receive the exit status (decoded with the `WIFEXITED`/`WEXITSTATUS`/`WIFSIGNALED`/`WTERMSIG` macros), and the third is a flags word — most commonly `0` (block until the child exits) or `WNOHANG` (return immediately, with return value 0 if no child has exited yet). The `WNOHANG` variant is what a long-running supervisor uses to reap children without blocking: it polls `waitpid(-1, &status, WNOHANG)` in its main loop (often triggered by a `SIGCHLD` handler that just sets a flag and returns, because `waitpid` is async-signal-safe but most other things are not). The standard idiom in a `SIGCHLD` handler is a `while ((pid = waitpid(-1, &status, WNOHANG)) > 0) { /* log */ }` loop — note the `while`, because multiple children may have exited in the same time quantum and SIGCHLD is not queued, so a single signal may represent several deaths.

Orphans are the dual problem: a child whose parent has died before the child has exited. The kernel re-parents the orphan to the nearest ancestor that is a child subreaper, or to PID 1 if there is none. PID 1 is expected to call `waitpid()` on these adopted children automatically — systemd does this in its main loop, and `tini` does this in container init. The failure mode is when PID 1 is NOT a real init — for example, when you run `docker run java:17 java -jar app.jar` and the JVM is PID 1. The JVM does not call `waitpid()` on adopted children, so any process the JVM spawns (e.g., a shell-out to `Runtime.exec`) that itself forks (e.g., the shell spawns a subprocess and exits before the subprocess finishes) will leave a zombie that the JVM never reaps. The zombies accumulate until the container hits its PID limit and the JVM cannot start new threads (because Linux internally allocates thread IDs from the same pool as PIDs). The fix is to run the JVM under `tini` or `dumb-init` — `docker run --init java:17 java -jar app.jar` enables tini automatically.

```c
// Correct SIGCHLD handler: async-signal-safe, reaps all pending children.
// In production this is wrapped in a self-pipe or signalfd so the main loop
// can handle the actual logging/cleanup off the signal handler.
static void sigchld_handler(int signo) {
    int saved_errno = errno;            // MUST preserve errno
    pid_t pid;
    int   status;
    // Loop: multiple children may have died; SIGCHLD is not queued.
    while ((pid = waitpid(-1, &status, WNOHANG)) > 0) {
        if (WIFEXITED(status))      log_child_exit(pid, WEXITSTATUS(status));
        else if (WIFSIGNALED(status)) log_child_signal(pid, WTERMSIG(status));
    }
    errno = saved_errno;
}

int main(void) {
    struct sigaction sa = {0};
    sa.sa_handler = sigchld_handler;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_RESTART | SA_NOCLDSTOP;   // do not receive SIGCHLD on stop/continue
    sigaction(SIGCHLD, &sa, NULL);
    // ... spawn workers, run main loop ...
}
```

```bash
# Diagnose zombies: anything in state Z is a zombie
$ ps -eo pid,ppid,stat,comm | awk '$3 ~ /^Z/'
 8421  8401 Z    <defunct>
 8422  8401 Z    <defunct>

# The parent (PPID 8401) is the one failing to reap. Send it SIGCHLD to
# nudge it, or kill it if it is wedged.
$ kill -CHLD 8401

# Watch a process become a zombie, then get reaped
$ (sleep 1 & exit 0) &
$ ps -o pid,ppid,stat,comm -p $!        # may briefly show S+ before reaping
```

The production failure pattern is almost always a supervisor that spawns children but never reaps them — a Java `ProcessBuilder.start()` that does not call `process.waitFor()`, a Python `subprocess.Popen` whose `poll()` is never called, a Go `cmd.Start()` without `cmd.Wait()`. Each leaks one zombie per invocation; at a thousand requests per second this fills the PID table in seconds. The 02.01.01 note connects forward to every runtime note in section 04 — the JVM's `ProcessHandle`, Node's `child_process`, CPython's `multiprocessing` — because each runtime wraps the same `fork`/`exec`/`wait` primitives and exposes its own idiom for reaping. If a runtime's documentation does not mention zombie reaping, the runtime is leaving it to you.

## How This Connects to the Runtimes

Every runtime covered in section 04 is a user-space wrapper around these kernel primitives:

- **JVM**: Maps Java threads 1:1 to OS threads via NPTL. The JVM's memory model (section 04.01) is a specification layered on top of the kernel's virtual memory system described here.
- **Node.js / libuv**: The event loop (section 04.02) is a Reactor pattern built on `epoll_wait()`. The worker thread pool uses OS threads for operations that cannot be multiplexed (file I/O, DNS, crypto).
- **CPython**: The GIL (section 04.03) is a mutex that serializes Python bytecode execution across OS threads. Multi-processing in Python uses `fork()` to bypass the GIL.
- **PHP-FPM**: Each worker is a separate OS process (section 04.04). The shared-nothing model is a direct consequence of the process isolation described in the Linux Process Model note.

When you read those runtime notes, come back here and trace which kernel primitive each runtime feature maps to.
## Hands-On Exercise

Open a terminal on a Linux machine and run the following commands to see these concepts in action:

```bash
# See process states (R/S/D/T/Z) for the whole system
ps -eo pid,ppid,stat,comm | head -20

# Watch context switches per second system-wide (cs column)
vmstat 1 5

# See the file descriptor table of a process
ls -la /proc/$$/fd

# See the memory layout (VMA list) of a running process
cat /proc/self/maps | head -20

# See TCP socket states
ss -tan state established | head

# See the kernel stack of a process stuck in D state
sudo cat /proc/<pid>/stack

# Trace every syscall a process makes
strace -f -e trace=process,signal ./your_program 2>&1 | head -80

# Watch a parent fork children and reap them
strace -e trace=fork,clone,wait4,exit_group -f /bin/bash -c 'echo hi | cat'
```

Correlate each line of output with the bullets above. If you cannot match a row in the output to a concept in this note, re-read the relevant section. The single most educational command is the last `strace` — it shows you exactly how `bash` uses `clone` + `wait4` to implement a shell pipeline.
