# 02.01.03. CPU Scheduling and Context Switching Mechanics

## What This Is

**CPU Scheduling and Context Switching Mechanics** is the third primitive in the process-and-scheduling stack. Where 02.01.01 covered the process as a unit of resource ownership and 02.01.02 covered the thread as a unit of execution, this note covers the *scheduler* — the kernel subsystem that decides which runnable thread runs on which CPU, when, and for how long. Every runtime in section 04 is constrained by the Linux scheduler: a JVM that spawns 200 platform threads is at the mercy of CFS for which thread runs next, a Node.js event loop blocked on a long-running computation will be preempted mid-request, and a Go runtime's `GOMAXPROCS` setting is bounded by the number of CPUs the kernel exposes. The scheduling policy dictates latency, throughput, and fairness — and the context switch cost dictates how cheaply you can interleave work.

The reason this note sits in section 02 is that the scheduler is the load-bearing primitive behind every "why is my p99 latency 50ms when my p50 is 2ms?" question. The answer is almost always scheduling: a thread blocked on I/O gets woken by an interrupt, the kernel context-switches to it (3-10 µs), the thread discovers its data is not in L1 cache (another ~10 µs of cache-miss stalls), it does a few microseconds of work, then blocks again. If 200 threads are doing this simultaneously on 8 cores, the scheduler is juggling 200 ready threads across 8 CPUs and each thread is paying context-switch and cache-miss tax on every wakeup. The numbers add up fast. This note explains the CFS algorithm, the context switch anatomy, the cost components, and the monitoring tools — so that when you see a `vmstat` showing 50,000 context switches per second, you know exactly what is happening and what to do about it.

## The Details

### The Completely Fair Scheduler (CFS): Red-Black Trees, `vruntime` (virtual runtime), and scheduling classes

The Linux **Completely Fair Scheduler (CFS)**, introduced in kernel 2.6.23 (2007), is the default scheduler for normal-priority tasks. Its design goal is right there in the name: be fair. Every runnable thread gets an equal share of CPU time, modulo its nice priority. The data structure is a **red-black tree** keyed by `vruntime` — a per-thread quantity that represents how much CPU time the thread has consumed, weighted by its priority. The leftmost node in the tree (the one with the smallest `vruntime`) is the next thread to run. When the running thread has consumed enough time that its `vruntime` is no longer the smallest, the scheduler picks the new leftmost and switches. The red-black tree was chosen because it guarantees O(log N) insertion, deletion, and lookup, which means scheduling decisions scale well to thousands of runnable threads.

`vruntime` is the heart of CFS. It is incremented on every clock tick while the thread is running, but the increment is weighted by the thread's nice value. A thread at nice 0 (default) has its `vruntime` incremented by the actual nanoseconds it ran. A thread at nice -5 (higher priority) has its `vruntime` incremented more slowly, so it appears to have run less than it actually did — meaning it stays near the left of the tree longer and gets picked more often. A thread at nice +5 (lower priority) has its `vruntime` incremented faster, so it slides right and gets picked less often. The weight table is precomputed (`prio_to_weight` in `kernel/sched/core.c`) and is approximately a 1.25x multiplier per nice level (so nice -5 vs nice 0 is about 3x more CPU, nice +5 vs nice 0 is about 1/3 the CPU). This is the same nice semantics Unix has always had, but CFS implements it precisely rather than via heuristic time-slice tweaking.

CFS is just one of several **scheduling classes** in the kernel. The classes, in priority order, are: `stop_sched_class` (used internally for migration), `dl_sched_class` (SCHED_DEADLINE, Earliest Deadline First for hard real-time), `rt_sched_class` (SCHED_FIFO and SCHED_RR, real-time priorities 1-99), `fair_sched_class` (SCHED_NORMAL / SCHED_BATCH / SCHED_IDLE — this is CFS), and `idle_sched_class` (the per-CPU idle task). When the scheduler picks the next task to run on a CPU, it walks the classes in priority order and picks the highest-priority runnable task. This means a SCHED_FIFO task at priority 99 will preempt any CFS task instantly and run to completion (or until it yields) — which is why SCHED_FIFO is dangerous in production (a buggy real-time thread can lock up the entire CPU) and why most distributions do not grant `CAP_SYS_NICE` to containers by default.

```bash
# Show the scheduling policy and priority of every thread
$ ps -eLo pid,tid,cls,rtprio,pri,ni,comm | head -10
  PID   TID CLS RTPRIO PRI  NI COMM
    1     1 TS       -  19   0 systemd
    2     2 TS       -  19   0 kthreadd
   ...
# CLS=TS means SCHED_NORMAL (CFS, time-sharing).  CLS=FF means SCHED_FIFO,
# CLS=RR means SCHED_RR, CLS=B means SCHED_BATCH, CLS=IDL means SCHED_IDLE.

# Change a process to real-time FIFO priority 50 (DANGEROUS — can lock the CPU)
$ sudo chrt -f -p 50 <pid>

# Make a long-running batch job use SCHED_IDLE (only runs when nothing else wants CPU)
$ sudo chrt -i -p 0 <pid>
```

```text

                                ┌─────────────┐
                                │ vruntime=120│  ← root
                                └──────┬──────┘
                                       │
                ┌──────────────────────┴───────────────────────┐

        ┌─────────────┐                                ┌─────────────┐
        │ vruntime=80 │                                │ vruntime=200│
        └──────┬──────┘                                └─────────────┘
               │
       ┌───────┴────────┐
       ▼                ▼
 ┌───────────┐    ┌───────────┐
 │  vruntime │    │ vruntime  │
 │  = 40     │    │  = 95     │
 │  ← leftmost node, picked next by scheduler
 └───────────┘    └───────────┘

When the leftmost thread runs, its vruntime increases; once it exceeds
the next-leftmost, the tree is rebalanced and a new thread is picked.
Pick operation: O(1) (cached leftmost).  Insert/delete: O(log N).
```

The connection to the upper layers is direct. When the JVM's `Thread.getState()` returns `RUNNABLE`, it means the underlying `task_struct` is in CFS's runqueue. When it returns `BLOCKED` or `WAITING`, the `task_struct` has been dequeued from CFS and placed on a kernel wait queue (a `wait_queue_head_t` associated with the monitor, condition variable, or I/O resource). The JVM thread priority (`Thread.setPriority(1..10)`) is supposed to map to OS nice values, but on Linux this mapping is a no-op by default — the JVM uses `java.util.concurrent` locks and `Thread.yield()` for actual priority control, not OS-level nice. The lesson is that CFS gives you fairness for free; if you want unfairness (e.g., dedicate a core to your database's WAL flusher thread), you need `sched_setaffinity` and `SCHED_FIFO`, not the JVM's priority API.

### Voluntary vs. Involuntary Context Switches: Yielding on I/O vs. Preemption by timer interrupts

Every context switch falls into one of two categories: **voluntary** (the thread chose to give up the CPU) or **involuntary** (the kernel took the CPU away). A voluntary switch happens when the running thread calls a blocking syscall (`read`, `recv`, `accept`, `futex`, `epoll_wait`, `nanosleep`, `waitpid`) — the syscall places the thread on a wait queue, calls `schedule()`, and the kernel picks the next thread. An involuntary switch happens when the running thread has consumed its time slice (the `sched_slice` calculation, typically 1-10 ms depending on `sched_min_granularity_ns` and the number of runnable threads) and the scheduler tick interrupt fires, or when a higher-priority thread becomes runnable and preempts it. The two are tracked separately in `/proc/<pid>/status` as `voluntary_ctxt_switches` and `nonvoluntary_ctxt_switches`, and the ratio is a powerful diagnostic.

A high voluntary count is healthy — it means your threads are blocking on I/O as expected, which is what backend threads do. A web server handling a hundred requests per second with 50 worker threads will show ~5,000 voluntary switches per second (each request blocks at least once on `accept`, once on `recv`, once on `send`, once on `write` to a log). A high involuntary count is a red flag — it means your threads are being preempted by the scheduler, which usually means they are CPU-bound (doing real computation, not blocking) but the runqueue is over-subscribed (more runnable CPU-bound threads than cores). A JVM doing GC, a Python worker chewing through a 50MB JSON, a Go program with `GOMAXPROCS=64` on an 8-core machine — all of these will show elevated involuntary switches. The fix is to reduce the number of runnable CPU-bound threads to match the core count, or to pin threads to cores with `sched_setaffinity` so the scheduler does not migrate them.

The kernel preemption model adds nuance. Linux is fully preemptive in user-space since 2.6.23 — any thread can be preempted at any instruction boundary in user-space, not just at syscall entries. Kernel-mode preemption is configurable: with `CONFIG_PREEMPT_NONE` (default on server distros), the kernel is non-preemptive in kernel mode (a syscall runs to completion or until it voluntarily yields); with `CONFIG_PREEMPT_VOLUNTARY`, the kernel has explicit `might_sleep()` annotations that yield more often; with `CONFIG_PREEMPT` (default on desktop), most kernel code can be preempted; with `CONFIG_PREEMPT_RT` (real-time patch, mainlined in 6.12), nearly all kernel code is preemptable and IRQ handlers run as kernel threads. Server distros ship `PREEMPT_VOLUNTARY` because it is the best latency/throughput tradeoff for throughput-oriented workloads; embedded and audio systems ship `PREEMPT_RT` for bounded latency.

The connection to the layered model is the operational rule of thumb: **for I/O-bound workloads (web servers, RPC clients), voluntary switches dominate and you have plenty of headroom; for CPU-bound workloads (GC, parsing, compression, ML inference), involuntary switches dominate and you are paying context-switch tax you can avoid.** When you read the runtime notes in section 04, the JVM's GC threads (04.01), Node's libuv worker pool (04.02), CPython's GIL contention (04.03), and PHP-FPM's worker count (04.04) are all directly affected by this ratio. The standard remediation is `taskset` or `cset shield` to pin CPU-bound threads to specific cores, eliminating the cache-miss tax of migration.

### Anatomical breakdown of a Context Switch: CPU register save/restore, stack pointer swap, Program Counter (PC) swap, and MMU Page Table flush

A context switch is the kernel's act of taking the CPU away from one thread and giving it to another. The mechanics are implemented in `__switch_to` in `arch/x86/kernel/process_64.c` (for x86-64) and `switch_to` in `arch/x86/include/asm/switch_to.h`. The function takes two `task_struct*` arguments (the prev and the next) and does the following, in order: save the FPU state of prev (XSAVEOPT of the XMM/YMM/ZMM registers and the MXCSR control word — this is expensive, hundreds of cycles, so the kernel uses lazy FPU saving where possible), save the general-purpose registers that the C calling convention does not preserve across calls (RBX, RBP, R12-R15 — the rest were already saved by the compiler on prev's stack), swap the kernel stack pointer (load next's `task_struct->thread.sp` into RSP — this is the act that "switches" the thread from the kernel's perspective), update the per-CPU `current` pointer to point at next, swap the FS and GS base registers if next has a different TLS pointer or is a different thread (this is what gives each thread its own TLS), update the TLS descriptor in the GDT, swap the I/O bitmap if either task uses `ioperm`, and finally return — the `ret` instruction pops next's saved RIP off the new stack and execution continues in next where it left off.

The most consequential step is the **page table swap** — only if the switch is between threads of different processes (different `mm_struct`). The kernel writes next's PGD physical address into the `CR3` register, which is the hardware pointer the MMU uses to walk page tables. Writing CR3 invalidates the entire TLB (Translation Lookaside Buffer) on every CPU that has run prev, because the TLB entries are now stale (they map virtual addresses to the wrong physical frames). On modern CPUs with PCID (Process Context IDentifier) support, the TLB is tagged with a process ID and not fully flushed — only the entries for the new process's PCID are loaded — but the cost is still measurable. The TLB flush is the dominant cost of a process-process context switch; the register save/restore is cheap (~5-20 ns), but rebuilding a warm TLB takes thousands of cycles as the new process's hot pages are faulted in.

For a **thread-thread context switch within the same process**, the CR3 write does not happen (both threads share the same `mm_struct`), so the TLB stays warm. This is why thread-thread switches are 3-5x cheaper than process-process switches, and why threads are preferred to processes for fine-grained concurrency. The cost numbers: a thread-thread switch is roughly 100-300 ns (mostly register save/restore and kernel scheduler overhead), while a process-process switch is 1-3 µs (adds the TLB refill). Both numbers are dwarfed by the cache-miss cost that follows: when next starts running, its hot data is not in L1/L2 (prev's data is), so the first few hundred memory accesses are L3 or RAM latency (~10 ns and ~100 ns respectively). This is the "cache pollution" cost — the real reason you want to avoid context switches is not the switch itself, it is the cache cold-start that follows.

```text
Context switch anatomy (x86-64, same-process thread switch)

  prev thread running                  switch_to(prev, next)
  ─────────────────────                ────────────────────────────
  user-space                           1. syscall/interrupt → kernel
  RIP = 0x401234                          (saves user RAX..R15 to
  RSP = 0x7fff_1234                       prev's kernel stack via
                                          pt_regs on entry)
                                       2. __switch_to_asm:
                                          - push RBX, RBP, R12-R15
                                          - load next's saved RSP
                                          - pop RBX, RBP, R12-R15
                                       3. __switch_to:
                                          - XSAVEOPT prev's FPU state
                                          - load next's FS/GS base (TLS)
                                          - update current = next
                                          - update task_thread_info
                                       4. ret → pops next's saved RIP
                                          → resumes next inside its
                                            own __switch_to call
                                       5. (next eventually returns to
                                          user-space via its pt_regs)

  For process-process switch, step 2.5 also writes CR3 = next_pgd_phys,
  which flushes the TLB.  Cost: ~3-10 µs total (mostly TLB refill).
  For thread-thread switch, no CR3 write — ~100-300 ns total.
```

```bash
# Measure context switch cost on this machine
$ perf bench sched messaging -l 10000    # higher = slower scheduler
# or:
$ lmbench_all lat_ctx -s 0 2             # µs per context switch with 2 processes
$ lmbench_all lat_ctx -s 0 2 -P         # same but with threads (much cheaper)
```

The connection to the layered model is the single most important rule in 02.01.03: **the cost of a context switch is dominated by TLB and cache effects, not by the switch itself**. This is why `epoll`-based event loops (Node, Nginx, Netty) outperform thread-per-connection at high concurrency: they do all their I/O from a single thread, never switching, never paying TLB tax, never evicting their cache. It is also why `taskset`-pinned databases (Oracle, PostgreSQL with `numactl`) outperform unpinned ones: by binding a thread to a core, you eliminate migration-induced cache misses. When you read the runtime notes in section 04, every "the runtime uses a thread pool of size N" decision is implicitly a context-switch-cost decision: N should match the core count for CPU-bound work, and should match the I/O concurrency target for I/O-bound work.

### CPU Cache invalidation and Translation Lookaside Buffer (TLB) shootdowns during context switches

The performance cost of a context switch is not the switch itself — it is the cache state that the switch invalidates. Three caches matter: the **L1/L2/L3 data and instruction caches** (per-core for L1/L2, shared across cores for L3), the **TLB** (per-core, virtual-to-physical address translation cache, typically 64-1024 entries split between 4 KB pages and huge pages), and the **branch predictor** (per-core, learned branch patterns). When the scheduler takes the CPU away from prev and gives it to next, next's hot data is not in L1 (prev's is), next's page-table translations are not in the TLB (prev's are), and the branch predictor has learned prev's branch patterns (not next's). All three need to be re-warmed, and that re-warming takes thousands of cycles.

The TLB is the most expensive to refill. A TLB hit is ~1 cycle (the translation is in the cache, the load proceeds immediately); a TLB miss requires a page-table walk, which on x86-64 is four memory accesses (one per page-table level: PGD, PUD, PMD, PTE), each of which may be an L3 hit (~10 ns) or a RAM access (~100 ns). A TLB miss costs ~100-400 ns in the worst case. A typical L1 cache footprint for a server thread is a few thousand unique cache lines (a few hundred KB), and rebuilding that from L3 takes ~10 µs (a few thousand loads × ~5 ns per L3 hit). The full cost of a context switch, including cache and TLB refill, is therefore 5-20 µs in practice — an order of magnitude more than the raw register-save cost.

**TLB shootdowns** are a separate, worse problem. When the kernel changes a page-table entry (e.g., unmaps a page, changes a page's permissions, or evicts a page to swap), the change must be propagated to every CPU that has the old translation cached in its TLB. The kernel does this via an **IPI (Inter-Processor Interrupt)**: it sends a "shootdown" IPI to every CPU that has run the affected process, each CPU invalidates its TLB entries for the affected pages, and each CPU acks the IPI. The originating CPU waits for all acks before proceeding. On a many-core system (e.g., 64 cores), a single TLB shootdown can take tens of microseconds because every core must be interrupted and must respond. This is why `munmap` of a large mapping is expensive on multi-core systems, why JVM GC pauses correlate with TLB shootdown counts, and why transparent huge pages (THP) reduce TLB pressure (a 2 MB huge page replaces 512 4 KB PTEs with one PMD entry, so the TLB covers 512x more address space with the same number of entries).

```bash
# Hardware TLB info
$ cat /proc/cpuinfo | grep -i "model name" | head -1
# Then look up the architecture's TLB size, or:

$ perf stat -e instructions,iTLB-load-misses,dTLB-load-misses \
          ./your_program 2>&1 | tail -10
   1234567890      instructions
      8234198      iTLB-load-misses          # 0.07% of instructions
      9234198      dTLB-load-misses          # 0.08% of instructions
# Each miss costs 100-400 ns; a 0.1% miss rate at 3 GHz is 30 ms/sec of
# pure TLB refill cost.

# See huge page usage (reduces TLB pressure)
$ cat /proc/meminfo | grep -i huge
AnonHugePages:    8192 kB
HugePages_Total:     0
HugePages_Free:      0
Hugepagesize:     2048 kB

# Reserve 100 2 MB huge pages (200 MB) for the JVM
$ echo 100 | sudo tee /proc/sys/vm/nr_hugepages
# Then start the JVM with -XX:+UseLargePages
```

The connection to the layered model is the operational lesson: **reduce context switches, reduce TLB pressure, and use huge pages for big heaps.** Every runtime in section 04 inherits these costs. The JVM's G1GC and ZGC are designed to minimize TLB shootdowns during compaction (ZGC uses colored pointers and load barriers to avoid stop-the-world shootdowns entirely). Node's libuv uses a single thread so its TLB stays warm for the event loop. PostgreSQL supports `huge_pages=on` in `postgresql.conf` for exactly this reason. When you tune a production JVM, the order of operations is: (1) size the heap to fit in huge pages, (2) pin the GC threads to specific cores with `numactl --cpunodebind`, (3) confirm with `perf stat` that TLB misses are under 0.05% of instructions. When you tune a load balancer, the order is: (1) keep the worker count equal to the core count, (2) use `SO_REUSEPORT` so the kernel hashes connections to specific workers and each worker's connection set stays cache-warm, (3) confirm with `pidstat -w` that involuntary switches are under 5% of total.

### Monitoring context switches via `/proc/sys/kernel`, `vmstat`, and `pidstat -w`

The kernel exposes context switch counters in three places, each at a different granularity. **System-wide totals** are in `/proc/stat` (the `ctxt` line gives the cumulative count since boot) and `/proc/vmstat` (the `ctxt` line is the same; `pgmajfault` and `pgfault` are nearby if you want page-fault counts too). **Per-process counts** are in `/proc/<pid>/status` under `voluntary_ctxt_switches` and `nonvoluntary_ctxt_switches` — these are cumulative since the process started. **Per-thread counts** require `pidstat -t -w` (or parsing `/proc/<pid>/task/<tid>/status` for each thread). The system-wide rate (switches per second) is what `vmstat 1` shows in its `cs` column. A healthy idle server shows ~1000-5000 cs/sec; a busy I/O server shows ~50,000-200,000 cs/sec; a CPU-bound server with thread oversubscription shows ~500,000+ cs/sec and is usually the symptom of a misconfigured thread pool.

The tuning knobs live in `/proc/sys/kernel/`. The most important ones are: `sched_min_granularity_ns` (the minimum time a thread runs before it can be preempted — default 1 ms on server kernels, lower for latency-sensitive workloads like trading), `sched_wakeup_granularity_ns` (the minimum vruntime advantage a waking thread needs to preempt the currently-running thread — higher values reduce wakeup preemption and improve throughput at the cost of latency), `sched_latency_ns` (the target scheduling period — CFS tries to give every runnable thread at least `sched_latency_ns / num_runnable` of CPU per period), and `sched_migration_cost_ns` (the cost the scheduler imputes to migrating a task between CPUs — higher values reduce migration, keeping cache warmer). For most backend workloads the defaults are fine; the one knob worth knowing is `sched_min_granularity_ns` for latency-sensitive services — dropping it to 100 µs cuts tail latency at the cost of throughput.

For real-time monitoring, `pidstat -w 1` (voluntary + involuntary per process per second), `pidstat -t -w 1` (per thread), `vmstat 1` (system total in `cs` column), and `perf stat -e context-switches,cpu-migrations` (for a specific command) are the standard tools. For deep diagnosis, `perf record -e sched:sched_switch -g` captures every context switch with a stack trace, and `perf script` lets you see exactly which code path was preempted. The `runqlat` and `runqslat` bpftrace tools (from the bcc-tools package) give histograms of run-queue latency — the time between a thread becoming runnable and actually getting a CPU — which is the most direct measurement of "is my server overloaded?"

```bash
# Cumulative system-wide context switches since boot
$ grep '^ctxt' /proc/stat
ctxt 48329483029

# Per-process voluntary + involuntary switches
$ grep ctxt /proc/<pid>/status
voluntary_ctxt_switches:    4523
nonvoluntary_ctxt_switches: 821

# Real-time per-process switch rates
$ pidstat -w 1
Linux 6.5.0-... (hostname)   03/14/2025  _x86_64_  (8 CPU)

10:00:01 AM   UID       PID  cswch/s nvcswch/s  Command
10:00:01 AM     0      4231     12.34      0.45  java
10:00:01 AM     0      4232     78.91    124.50  java        ← high involuntary = CPU-bound
10:00:01 AM     0      4233    102.34      1.20  nginx

# Real-time per-thread switch rates (look for runaway threads)
$ pidstat -t -w 1 | head -10

# CFS tunables (server kernels ship sane defaults — change with care)
$ sysctl kernel.sched_min_granularity_ns kernel.sched_latency_ns \
         kernel.sched_wakeup_granularity_ns kernel.sched_migration_cost_ns
kernel.sched_min_granularity_ns = 1000000
kernel.sched_latency_ns = 6000000
kernel.sched_wakeup_granularity_ns = 500000
kernel.sched_migration_cost_ns = 500000

# Runqueue latency histogram — the most direct "is my server overloaded" measure
$ sudo bpftrace -e 'tracepoint:sched:sched_wakeup { @q[kpid] = nsecs; }
                    tracepoint:sched:sched_switch { @lat = hist(nsecs - @q[args->prev_pid]); }'
```

The connection to the layered model is the operational rule: **every backend engineer should be able to glance at `pidstat -w 1` output and diagnose the workload type in seconds.** A thread showing 100 voluntary switches/sec and 1 involuntary is doing I/O (healthy). A thread showing 50 voluntary and 200 involuntary is CPU-bound (oversubscribed). A thread showing 5 voluntary and 0 involuntary is idle (wasting a slot in the pool). When you read the runtime notes in section 04 — JVM thread pool sizing (04.01), Node's libuv pool sizing (04.02), CPython GIL contention (04.03), PHP-FPM `pm.max_children` (04.04) — the way you know the sizing is correct is by reading these numbers. Every misconfigured thread pool shows up first as an elevated involuntary-context-switch rate, long before it shows up as elevated latency in your monitoring.

## How This Connects to the Runtimes

Every runtime covered in section 04 is a user-space wrapper around these kernel primitives:

- **JVM**: Maps Java threads 1:1 to OS threads via NPTL. The JVM's memory model (section 04.01) is a specification layered on top of the kernel's virtual memory system described here.
- **Node.js / libuv**: The event loop (section 04.02) is a Reactor pattern built on `epoll_wait()`. The worker thread pool uses OS threads for operations that cannot be multiplexed (file I/O, DNS, crypto).
- **CPython**: The GIL (section 04.03) is a mutex that serializes Python bytecode execution across OS threads. Multi-processing in Python uses `fork()` to bypass the GIL.
- **PHP-FPM**: Each worker is a separate OS process (section 04.04). The shared-nothing model is a direct consequence of the process isolation described in the Linux Process Model note.

When you read those runtime notes, come back here and trace which kernel primitive each runtime feature maps to.
