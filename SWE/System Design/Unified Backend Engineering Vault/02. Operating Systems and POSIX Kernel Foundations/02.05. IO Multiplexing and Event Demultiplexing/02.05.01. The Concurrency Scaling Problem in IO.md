# 02.05.01. The Concurrency Scaling Problem in IO

## What This Is

The "concurrency scaling problem" in I/O is the question every backend engineer eventually hits: how many simultaneously-open network connections can a single process actually serve, and what stops it from serving more? In 1999 Dan Kegel framed it as the **C10K problem** — handle 10,000 concurrent connections from one box — and at the time it was a serious research question because the obvious thread-per-connection model collapsed well before 10k. Today C10K is a solved problem (a stock Nginx or Node.js process holds 100k+ idle connections on a small VM), but the same scaling laws now press against **C10M**: 10 million concurrent flows on a single machine, which requires abandoning the kernel's socket API entirely in favour of kernel-bypass network stacks like DPDK.

This note sits in section 02 because every runtime in section 04 — the JVM's NIO, Node's libuv, CPython's asyncio, PHP-FPM's process pool — is a different answer to the same question. Their threading models, schedulers, and event-loop implementations are downstream design decisions forced by the kernel primitives documented here. Understanding the scaling problem means you can predict, before benchmarking, why Node.js beats thread-per-connection Spring Boot on idle-connection count and loses on CPU-bound throughput, and why neither holds a candle to a ScyllaDB shard-per-core design on a 64-core box.

## The Details

### The Thread-per-Connection model: Thread stack memory explosion and CPU context switch s...

The naive server loops on `accept()` and spawns a thread per accepted connection. Each thread blocks in `recv()` until data arrives, processes the request, and writes the response. This is the model classical Java Servlets (pre-3.0), Apache HTTPD prefork/worker MPMs, and every beginner's socket tutorial teach. It works fine at 100 connections and collapses by 5,000 — and the reasons are entirely structural, not implementation bugs.

The first wall is **stack memory**. Every OS thread on Linux defaults to an 8 MiB virtual stack reservation (`ulimit -s` = 8192), of which the first 16–64 KiB is faulted into physical pages lazily as the stack grows. The JVM stacks are smaller (`-Xss512k` is the default on 64-bit HotSpot, often lowered to 256 KiB), but they are still reserved address space. 10,000 threads × 8 MiB = 80 GiB of *virtual* address space, which on a 64-bit kernel is fine but on a 32-bit process is impossible (the 3 GiB user-space ceiling is exhausted at ~375 threads). Physical memory is the real ceiling: even with only 64 KiB of actual stack touched per thread, 10,000 threads × 64 KiB = 640 MiB of just stack, plus per-thread kernel structures (`struct task_struct` ~8 KiB, kernel stack 8 KiB on x86_64, TLS area) — another ~200 MiB. Add Java thread stacks (`-Xss1m` default × 10k = 10 GiB of *committed* virtual), and a 16 GiB box is out of memory before it accepts a single byte of payload.

The second wall is **context-switch cost**. The Linux CFS scheduler assigns each thread a time slice proportional to its `nice` value; with 10,000 runnable threads and a 10 ms target latency, each thread gets a 1 µs slice — which is shorter than the cost of switching to it. A context switch on a modern x86_64 CPU is 1–10 µs of pure kernel overhead (save/restore registers, TLB flush if the switch crosses address spaces — though threads share the same MM so no TLB flush here, but the scheduler still walks the runqueue). At 10,000 threads each waking on every packet, you spend 100% of CPU in the scheduler and the application makes no forward progress. The diagnostic is `vmstat 1` showing `cs` (context switches per second) above 100,000 with `us` (user CPU) below 20% — the kernel is busy bookkeeping and the application is starved.

The third wall is **cache pollution**. Each context switch evicts the L1/L2 cache of the previously-running thread; the new thread's hot data (its stack, its request buffer, its handler code) must be fetched from L3 or RAM, costing 50–100 ns per cache line. A server that context-switches on every packet sees its L1 hit rate collapse from 95%+ to under 60%, which alone multiplies per-request CPU time by 3–5×. This is why a single-threaded Redis on one core outperforms a 64-thread MySQL on the same hardware for simple GET/SET workloads: the single thread keeps its working set hot in L1.

```text
Per-thread memory anatomy on Linux x86_64 (JVM thread shown):

  User space:
    ┌──────────────────────┐ high addrs
    │ Java thread stack    │  -Xss1m default → 1 MiB committed
    │  (frames, locals)    │
    ├──────────────────────┤
    │ C/C++ native frames  │  ~16 KiB typical
    ├──────────────────────┤
    │ TLS / pthread vars   │  ~8 KiB
    └──────────────────────┘
  Kernel space (per-thread):
    struct task_struct  ~8 KiB  (slab-allocated)
    kernel stack        8 KiB   (16 KiB on some configs)
    ──────────────────────────
    Total per thread:   ~1 MiB committed + ~24 KiB kernel

  10,000 threads ⇒ 10 GiB committed virtual + 240 MiB kernel
                   + ~100 µs scheduler overhead per round trip
                   + L1 cache thrashed every quantum
```

The production failure mode here is the "thread bomb": an application spawns a thread per inbound request, traffic spikes 10×, the OS thrashes, latency goes from 50 ms to 30 seconds, the load balancer's health check times out, the node is marked dead, traffic shifts to the surviving nodes which then thread-bomb in turn, and the cluster collapses in a cascading failure. The metric that catches it early is `Threads` (JMX `java.lang:type=Threading/ThreadCount`, or `/proc/<pid>/status` `Threads:` line) — anything over 1,000 on a JVM service is a smell; over 5,000 is an incident. The fix is not bigger hardware; it is the Reactor pattern (covered in [[02.05.05. High-Performance Event Architecture Patterns]]).

### The C10K and C1000K scaling thresholds

Dan Kegel published [www.kegel.com/c10k.html](http://www.kegel.com/c10k.html) in 1999, framing the question that drove a decade of backend runtime design: "It's time for web servers to handle ten thousand clients simultaneously, and it isn't clear how to do that." On the hardware of the day (single-core 500 MHz Pentium III, 256 MiB RAM, 100 Mbit/s NIC), thread-per-connection died at ~1,000 connections for the reasons above, and the OS primitives available — `select(2)` and `poll(2)` — could not scale beyond a few thousand file descriptors because of their O(N) scan (see [[02.05.02. Legacy Multiplexing Systems select and poll]]).

The C10K answer that emerged between 2000 and 2005 was a combination of three things: (1) `epoll` on Linux 2.6 (2002) and `kqueue` on FreeBSD 4.1 (2000), which provide O(1) readiness notification; (2) non-blocking sockets set via `fcntl(fd, F_SETFL, O_NONBLOCK)`; (3) the **Reactor pattern** (Schmidt et al., POSA2) — a single-threaded event loop that calls `epoll_wait()`, dispatches ready FDs to handlers, and never blocks on I/O. By 2005, Nginx, lighttpd, and Tornado (Python) all implemented this pattern. By 2010, Node.js (2009) made it the default for JavaScript backends, and Java's NIO.2 (2011) gave the JVM a usable async socket channel. C10K was solved.

The threshold then moved. Yahoo in 2006 published work on serving 100,000+ Comet (long-poll) connections from a single box. WhatsApp in 2012 reported 1 million concurrent TCP connections on a single FreeBSD box running Erlang — that pushed the industry to **C1M**. The lessons from C1M were operational, not algorithmic: you need `ulimit -n 1048576`, you need `net.ipv4.ip_local_port_range = 10000 65535` expanded, you need to track ephemeral port exhaustion, you need `net.ipv4.tcp_tw_reuse=1`, you need `fs.file-max=2097152`, and you need to remember that every connection costs ~3.5 KiB of kernel memory for the `sock` + `tcp_sock` + `sk_buff` headers, so 1M idle connections = ~3.5 GiB of kernel slab (visible in `/proc/slabinfo` as `sock_inode_cache`, `tcp_sock`, `skbuff_head_cache`).

The current frontier is **C10M**: 10 million concurrent flows from one machine, articulated by Robert Graham at BlackHat 2013. C10K and C1M both still route packets through the kernel's network stack (`sk_buff` allocations, softirq processing, socket lookup in `__inet_lookup_established`). At 10M packets per second the kernel itself becomes the bottleneck — softirq takes 100% of every core. The C10M solutions bypass the kernel entirely: **DPDK** (Intel, 2010) maps the NIC's RX/TX rings directly into user space via VFIO/PCI passthrough, so a user-space process polls the NIC's descriptor ring in a tight `while(1)` loop with zero syscalls and zero interrupts. **AF_XDP** (Linux 4.18, 2018) is a softer middle ground — XDP programs in eBPF redirect packets from the NIC driver straight into an AF_XDP socket, skipping most of the kernel stack but keeping the syscall interface. Cloudflare, Facebook, and the major CDNs run their L4 load balancers on this stack; your application almost certainly does not need to.

```text
Scaling thresholds and their defeating technology:

  1K     ─►  thread-per-connection (Apache prefork, Tomcat bio)
              Default ceiling: ~1k threads before scheduler thrash
  10K    ─►  epoll + Reactor (Nginx, Node.js, Netty, Tornado)
              Dan Kegel's 1999 problem; solved by 2005
  100K   ─►  Comet long-poll servers (Yahoo 2006)
              Requires ulimit, somaxconn, ephemeral port tuning
  1M     ─►  Erlang/OTP (WhatsApp 2012)
              Each connection ~3.5 KiB kernel slab; need 4 GiB+ RAM
  10M    ─►  DPDK / AF_XDP kernel bypass (Cloudflare/FB L4)
              User-space polling, zero syscalls, dedicated cores
  100M+  ─►  Not yet demonstrated on commodity hardware
```

The production failure mode at C1M is **ephemeral port exhaustion on outbound connections** — a load test client that opens 1M outbound TCP connections runs out of (src_ip, src_port) tuples, because even with `ip_local_port_range = 10000 65535` there are only ~54k ports per remote IP. The kernel logs `bind(0): cannot assign requested address` and the test collapses. The fix is either multiple source IPs (a /26 of source IPs gives ~3.5M outbound ports) or `tcp_tw_reuse=1` to recycle TIME_WAIT slots. The diagnostic is `ss -s` showing a high `TCP` total with most of it in `time-wait`.

### Non-blocking I/O mode (`fcntl(fd, F_SETFL, O_NONBLOCK`): Returning `EAGAIN` / `EWOULDBLOCK on empty queues

The kernel primitive that makes the Reactor pattern possible is `O_NONBLOCK`. Setting it on a socket FD changes the semantics of every `read()`, `write()`, `recv()`, `send()`, `accept()`, and `connect()` call: instead of blocking the calling thread until data is available or the buffer has space, the call returns immediately. If there is nothing to read, it returns -1 with `errno=EAGAIN` (POSIX name) or `EWOULDBLOCK` (BSD name — on Linux the two are the same numeric value, 11). If there is some data but not as much as requested, it returns the partial count. The application is now responsible for retrying, which is what the Reactor's event loop does on every iteration of `epoll_wait()`.

The `fcntl` call itself is a one-time setup cost on each socket: `fcntl(fd, F_SETFL, fcntl(fd, F_GETFL, 0) | O_NONBLOCK)`. After that, the file's status flags carry `O_NONBLOCK` for the lifetime of the FD, and every I/O call observes it. Crucially, `O_NONBLOCK` is a property of the *file description* (the entry in the system-wide open file table), not the file descriptor — so `dup()` and `fork()` inherit it. This matters for Nginx's worker model: the master sets `O_NONBLOCK` on the listening socket before forking workers, and every worker inherits a non-blocking listener.

The interaction with `accept()` is the most common surprise. On a blocking listening socket, `accept()` blocks until a new connection arrives. On a non-blocking listener, `accept()` returns -1/EAGAIN when the accept queue (the backlog, bounded by `net.core.somaxconn` and the `listen()` second argument) is empty. The Reactor pattern registers the listening socket with `epoll` for `EPOLLIN`, gets woken when the accept queue is non-empty, and loops calling `accept()` until it returns EAGAIN — draining the entire accept queue in one wakeup. The same drain loop applies to `recv()` on a connected socket: read until EAGAIN, because `epoll_wait()` is edge-triggered-by-default... no, level-triggered by default, but the principle still applies — drain to keep buffer occupancy low and to coalesce multiple short packets into one read burst.

The connection to the Reactor is the design payoff. Without `O_NONBLOCK`, a single thread can serve exactly one connection. With `O_NONBLOCK` plus `epoll`, one thread can monitor millions of FDs: each FD costs ~100 bytes of state in the kernel's epoll red-black tree plus ~200 bytes of `struct epoll_event` in user space, plus the `struct sock` and `tcp_sock` of the connection itself (~3.5 KiB total per TCP socket). The syscall overhead drops from one-syscall-per-FD-per-quantum (blocking) to one-`epoll_wait`-per-loop-iteration (which returns N ready FDs at once). This is the difference between Node.js serving 50k connections on a 1 GiB VM and Tomcat bio serving 500 connections on the same VM.

```c
/* The non-blocking setup that every Reactor implementation performs. */
int flags = fcntl(fd, F_GETFL, 0);
fcntl(fd, F_SETFL, flags | O_NONBLOCK);

/* A drain loop: read everything the kernel has, then yield. */
char buf[4096];
ssize_t n;
while ((n = read(fd, buf, sizeof(buf))) > 0) {
    /* process n bytes of buf */
    app_consume(buf, (size_t)n);
}
if (n == -1 && errno == EAGAIN) {
    /* drained; re-arm in epoll and yield to the event loop */
} else if (n == 0) {
    /* peer closed */
} else {
    /* errno == EINTR: retry; errno == EBADF: fd closed */
}
```

The production failure mode here is the **forgotten EAGAIN loop**. A developer reads one `recv()`, processes the result, and goes back to `epoll_wait()` — but if the peer sent 8 KiB of data and the kernel only delivered 4 KiB before the first `recv()` returned, the remaining 4 KiB sits in the receive buffer until the peer sends more data, which may never happen (an HTTP request that fit in one MSS is a classic case). The application sees a hung request. The diagnostic is `ss -tin` showing `Recv-Q` > 0 on a long-lived connection. The fix is the drain loop shown above — read until EAGAIN, then return to the event loop. This is also why edge-triggered `epoll` (covered in [[02.05.04. Edge-Triggered vs. Level-Triggered Notification]]) makes the drain loop *mandatory* rather than optional — under ET, forgetting the loop loses data permanently.

## Cross-Ecosystem Implementation

The same scaling problem maps to different concurrency primitives in each runtime. The table below shows how each runtime answers "how do I serve 10,000 concurrent connections from one process":

| Runtime | Concurrency primitive | Default ceiling | Notes |
|---|---|---|---|
| JVM (HotSpot) | Platform threads (1:1 to OS) | ~3,000 per GB of heap | `-Xss512k` stack; Loom virtual threads lift to millions |
| JVM (Loom) | Virtual threads (M:N to carrier pool) | ~10,000,000 | Carriers = `ForkJoinPool` sized to cores; ~1 KiB per vthread |
| Node.js / libuv | Single-threaded event loop on `epoll` | ~100,000 | Worker pool (`UV_THREADPOOL_SIZE=4`) only for fs/DNS/crypto |
| Python asyncio | Single-threaded event loop on `epoll` | ~50,000 | GIL serializes bytecode; one slow handler stalls all |
| Python gevent | Greenlets (M:N) | ~100,000 | `monkey.patch_socket()` rewrites stdlib to non-blocking |
| Go runtime | Goroutines (M:N) | ~1,000,000 | 2 KiB stack grows; preemptive scheduler at function-call boundaries |
| Erlang BEAM | Processes (M:N) | ~10,000,000 | ~300 bytes per process; preemptive at reduction count |
| PHP-FPM | Process-per-request | ~256 | `pm.max_children`; shared-nothing; restart workers per N requests |

When you read the runtime notes in section 04, identify which cell of this table each runtime occupies. The delta notes in sections 05–12 then show how each framework exposes its runtime's concurrency primitive to application code.

## Hands-On Exercise

```bash
# See your system's hard ceilings
ulimit -n                # max FDs per process (default 1024, prod 65536+)
sysctl net.core.somaxconn
sysctl net.ipv4.ip_local_port_range
cat /proc/sys/fs/file-max

# Watch a thread-per-connection server die under load
# Start a naive Java socket server, then:
ab -n 100000 -c 5000 http://127.0.0.1:8080/
#   Meanwhile in another terminal:
watch -n 1 "ps -eL | grep -c java; vmstat 1 2 | tail -1"
#   Watch Threads count climb to 5000+ and `cs` (context switches) to 100k+/s

# Compare: a single-threaded Nginx worker holding 10k idle connections
#   Open 10k idle connections from another box:
seq 1 10000 | xargs -P 50 -I{} sh -c 'nc 127.0.0.1 80 </dev/null &'
#   Watch the worker's RSS stay flat at ~30 MiB, CPU at ~1%
ss -tan state established '( sport = :80 )' | wc -l

# Verify non-blocking I/O is in use:
strace -p $(pgrep -nf 'nginx: worker') -e trace=epoll_wait,recvfrom,sendto 2>&1 | head -20
#   You should see epoll_wait returning immediately with N events,
#   followed by recvfrom returning EAGAIN after draining.
```
