# 02.05.02. Legacy Multiplexing Systems select and poll

## What This Is

Before `epoll` and `kqueue` existed, Unix gave programmers two system calls for waiting on multiple file descriptors at once: `select(2)` (4.2BSD, 1983) and `poll(2)` (SVR3, 1986). Both let a single thread block until at least one of N file descriptors becomes readable, writable, or error-conditioned, then return the count of ready descriptors so the application can iterate and find them. They are the historical answer to "how do I serve many connections from one thread without spawning one thread per connection," and every modern multiplexing API — `epoll`, `kqueue`, `io_uring`, Windows IOCP — is best understood as a fix for the specific defects of these two.

This note covers what the `select` and `poll` APIs actually look like at the syscall level, why they collapse at scale, and what the collapse looked like in production before the Linux 2.6 kernel shipped `epoll` in October 2002. The kernels still ship these syscalls today (every POSIX system has them) and many libraries still use them — Python's `selectors` module falls back to `select` if `epoll` is unavailable, and Java's old `java.nio.channels.Selector` was a thin wrapper over `poll` on Linux before JDK 1.5 plugged in `epoll`. Knowing their failure modes is what lets you read a 2003-era server codebase and explain exactly why it cannot break 5,000 concurrent connections.

## The Details

### `select()`: Bitmap file descriptor sets (`fd_set`), `FD_SETSIZE` (1024 limit), and the O(N) linear scanning overhead

The `select` syscall is declared in `<sys/select.h>` as:

```c
int select(int nfds, fd_set *readfds, fd_set *writefds,
           fd_set *exceptfds, struct timeval *timeout);
```

The caller fills three `fd_set` bitmaps (one for read-readiness, one for write-readiness, one for exceptional conditions like out-of-band data), passes the highest FD number plus one as `nfds`, and blocks. On return, the kernel has *destructively* modified the bitmaps in place — every bit that was set for an FD that is *not* ready is cleared; only the ready FDs keep their bits. The return value is the total count of bits still set across all three sets. The application then must walk every FD from 0 to `nfds-1`, calling `FD_ISSET(fd, &readfds)` for each, to find which ones are ready. The four macros that manipulate the bitmaps are:

```c
void FD_ZERO(fd_set *set);          /* clear all bits */
void FD_SET(int fd, fd_set *set);   /* set bit for fd */
void FD_CLR(int fd, fd_set *set);   /* clear bit for fd */
int  FD_ISSET(int fd, fd_set *set); /* return nonzero if bit for fd is set */
```

`fd_set` is implemented as a fixed-size array of `unsigned long` words, with one bit per FD. On Linux the array is sized so that it can hold FDs 0 through `FD_SETSIZE-1`, where `FD_SETSIZE` is defined as **1024** in `<bits/types/sizes.h>`. This is the fatal constraint: any FD with a numeric value ≥ 1024 cannot be put into an `fd_set` at all — `FD_SET` will silently corrupt adjacent memory rather than fail, and on kernels built with the default config the syscall returns `EINVAL`. The 1024 ceiling exists because BSD in 1983 chose 256 bytes per `fd_set` (1024 bits), and 40 years of POSIX compatibility have frozen it. You can rebuild glibc with a larger `FD_SETSIZE` — many old web servers did this — but then you cannot link against any third-party library that was compiled with the default 1024, because the struct layout differs. The only correct fix is to not use `select`.

Even if you live within the 1024 limit, the performance profile is brutal. Every call to `select` requires the kernel to copy all three `fd_set` bitmaps from user space into the kernel (because the kernel modifies them in place), then walk every bit from 0 to `nfds-1` checking each FD's readiness, then copy the modified bitmaps back. With `nfds=1024` that is 384 bytes copied each way and 1024 FD-inspection calls per invocation — and you do this *every iteration of the event loop*. If you have 100 connections that are mostly idle, you still scan all 1024 slots every time, even though the typical return is "1 ready." The complexity is `O(N)` per call where N is the size of the monitored set, regardless of how many FDs are actually ready. The cost scales with the largest FD number, not with the number of FDs you care about, which is why classic `select`-based servers (Apache 1.3 with the threaded MPM, old Java NIO) topped out around 1,000 connections on commodity hardware.

```c
/* select(2) — the 1983 API. Note the bitmap manipulation and the
 * mandatory O(N) scan over every FD number from 0 to max_fd-1.
 */
fd_set rfds;
struct timeval tv = { .tv_sec = 1, .tv_usec = 0 };
int max_fd = -1;

FD_ZERO(&rfds);
for (int i = 0; i < n_conns; i++) {
    if (conns[i].fd >= FD_SETSIZE) { /* impossible to monitor */ abort(); }
    FD_SET(conns[i].fd, &rfds);
    if (conns[i].fd > max_fd) max_fd = conns[i].fd;
}

int ready = select(max_fd + 1, &rfds, NULL, NULL, &tv);
if (ready < 0) { perror("select"); return; }
/* Now scan every FD we set to find which are still set: O(N). */
for (int i = 0; i < n_conns; i++) {
    if (FD_ISSET(conns[i].fd, &rfds)) {
        handle_read(conns[i].fd);
    }
}
```

The production failure mode is two-fold. First, when an application opens more than 1024 FDs (multiple databases, multiple HTTP clients, lots of sockets), the next `select` call silently corrupts memory or returns `EINVAL`, and the server crashes or hangs. This is the bug behind half of the "random crashes after a few hours of high load" reports on legacy Java apps. Second, the O(N) scan means CPU usage grows linearly with the connection count even when most are idle — a server holding 900 idle connections burns 5–10% of one core just running `select` in a loop, while the same workload under `epoll` is < 0.1%. The diagnostic is `strace -c -p <pid>` showing `select` as the top syscall by total time. The fix is to migrate to `epoll` (or to a runtime that already does so, like modern Java NIO or Python's `selectors`).

### `poll()`: Array of `pollfd` structures, removal of the 1024 descriptor limit, but persistent O(N) scanning in kernel space

The `poll(2)` syscall, declared in `<poll.h>`, replaces the bitmap with an array of explicit structs:

```c
struct pollfd {
    int   fd;         /* file descriptor (-1 means ignore this slot) */
    short events;     /* requested events: POLLIN, POLLOUT, POLLERR, POLLHUP... */
    short revents;    /* returned events: filled in by kernel on return */
};

int poll(struct pollfd *fds, nfds_t nfds, int timeout_ms);
```

The caller allocates an array of `pollfd` structs (one per monitored FD), fills in the `fd` and `events` fields, and passes the array plus its length. The kernel walks the array, checks each FD's readiness, fills the `revents` field with what actually happened, and returns the count of slots with non-zero `revents`. The `fd` can be any valid file descriptor — there is no `FD_SETSIZE` ceiling — so a `poll`-based server can monitor descriptor 50000 just as easily as descriptor 5. This single change resolved the "cannot serve more than 1024 connections" ceiling that haunted `select`-based servers for two decades.

The events bitmask is richer than `select`'s three-set model. The commonly used bits are `POLLIN` (data available to read), `POLLOUT` (writing would not block now), `POLLRDHUP` (peer half-closed, Linux 2.6.17+), `POLLERR` (error condition), `POLLHUP` (peer fully closed), and `POLLNVAL` (the FD is not open — useful for detecting application bugs). The separate `revents` field means the kernel does not need to copy the input back to user space intact and then modify it — it can read `events` from user space, write `revents` to user space, and the caller's requested-event list is preserved. This means the application can keep the `pollfd` array allocated across calls and only update `events` when its interest changes — a small but real improvement over `select`'s destructive bitmap semantics.

What `poll` does *not* fix is the O(N) scan. The kernel still walks every `pollfd` in the array on every call, calling the underlying `struct file_operations.poll` callback for each. With 10,000 monitored FDs and a typical return of 5 ready ones, `poll` does 10,000 readiness checks to find those 5. Worse, the kernel must copy the entire array from user space into kernel space on entry (or use `copy_from_user` page-by-page during the walk), so the per-call memory copy is `10,000 × 8 bytes = 80 KiB` each way. On a 2004-era server, this capped a `poll`-based event loop at around 5,000–10,000 connections before CPU saturated; modern hardware lifts this to maybe 50,000, but the scaling law is the same — linear in the size of the interest set, not in the number of ready FDs.

```c
/* poll(2) — 1986 API, no 1024 ceiling but still O(N) per call.
 * The pollfd array can be allocated once and reused across calls.
 */
struct pollfd fds[MAX_FDS];
nfds_t nfds = 0;

for (int i = 0; i < n_conns; i++) {
    fds[nfds].fd      = conns[i].fd;
    fds[nfds].events  = POLLIN | POLLRDHUP;
    fds[nfds].revents = 0;
    nfds++;
}

int ready = poll(fds, nfds, 1000 /* ms */);
if (ready < 0) { perror("poll"); return; }
/* Still O(N): walk the whole array looking for revents != 0. */
for (nfds_t i = 0; i < nfds; i++) {
    if (fds[i].revents & POLLIN)     handle_read(fds[i].fd);
    if (fds[i].revents & POLLRDHUP)  handle_close(fds[i].fd);
    if (fds[i].revents & POLLHUP)    handle_close(fds[i].fd);
    if (fds[i].revents & POLLNVAL)   abort();   /* bug: closed fd */
}
```

The production failure mode of `poll` is "works fine in QA, dies in production." QA tests 500 connections — `poll` walks 500 FDs in microseconds, all green. Production hits 20,000 connections and `poll` now takes 2 ms per call, the event loop is doing 500 `poll` calls per second because of timeouts, CPU hits 100%, latency climbs. There is no error message and no log line — just a slow service. The diagnostic is `perf top -p <pid>` showing `poll` and the per-driver `.poll` callbacks at the top of the profile. The fix is the same as for `select`: switch to `epoll`. Python's `selectors.PollSelector` is `poll`-based and used to be the default on Linux before 3.4; modern Python uses `EpollSelector` automatically. Java's `java.nio.channels.Selector.open()` returned a `poll`-based selector on Linux before JDK 1.5; since 1.5 it uses `epoll` automatically. If you are debugging an old codebase, the migration is usually invisible at the API level and dramatic at the performance level.

### Memory copy overhead: Passing descriptor sets back and forth between user space and kernel space on every iteration

The third defect of `select` and `poll` is the one that `epoll` was specifically designed to eliminate: the *per-call* memory copy of the interest set. Both `select` and `poll` are **stateless syscalls** — the kernel has no memory of what FDs you monitored last time. Every call must re-transmit the full interest list from user space to kernel space, the kernel must walk it, and (for `select`) copy the modified result back. The interest set is not cached; the kernel does not remember which FDs you care about.

To see why this matters at scale, do the arithmetic. A `poll`-based server holding 10,000 idle connections has a 10,000-element `pollfd` array = 80 KiB. On every iteration of its event loop, it calls `poll(fds, 10000, 1000)`. That is 80 KiB copied from user to kernel, 10,000 readiness checks inside the kernel, and the array written back with `revents`. Even if no FDs are ready and the call just times out after 1 second, that work is redone on the next call. If the event loop's wake frequency is 1 kHz (driven by a 1 ms timeout), the kernel is copying 80 KiB × 1000 = 80 MiB/s of FD metadata for *zero useful work*. On a 2 GHz CPU that is roughly 4% of one core burned purely on `copy_from_user` and `copy_to_user` for the `pollfd` array.

`select` is even worse because of the bitmap's destructive semantics. Because `select` clears bits for FDs that are not ready, the application must *rebuild* the `fd_set` from its model of the world before every call. There is no way to call `select` twice with the same interest set without reconstructing it — the kernel has eaten the bitmap. A `select`-based server with 1,000 monitored FDs does 1,000 `FD_SET` operations per loop iteration, then the kernel does 1,000 readiness checks, then the application does 1,000 `FD_ISSET` checks. Six thousand operations to discover "1 FD is ready." At 10,000 iterations per second (100 µs per loop, typical of an idle-but-busy-polling server) that is 60 million bitmap operations per second — measurable as a steady 5–10% CPU load on a server that is doing literally nothing.

The structural fix is to make the syscall **stateful** — to let the application tell the kernel once "I am interested in FD 5, FD 17, FD 42" and have the kernel remember that across calls. That is exactly what `epoll` does: `epoll_ctl(ADD)` registers an FD once, `epoll_wait` returns only the ready ones, and the interest set lives in kernel memory for the lifetime of the `epoll` FD. The transition is from O(N) per call (where N = interest set size) to O(M) per call (where M = ready set size, typically 1–10). On the same 10,000-connection workload, `epoll_wait` copies 1–10 `epoll_event` structs (24 bytes each = 24–240 bytes total) per call, versus `poll`'s 80,000 bytes — a 300–3000× reduction in syscall memory bandwidth.

```text
Per-call cost comparison at N=10,000 monitored FDs, M=5 ready:

  select(2):
    User→Kernel copy: 3 × 1280 B (3 bitmaps @ 1024 bits each) = 3840 B
    Kernel scan:      1024 FD checks (capped by FD_SETSIZE)
    Kernel→User copy: 3840 B
    User scan:        1024 FD_ISSET calls
    Total:            ~2048 bitmap ops + ~8 KiB copy per call

  poll(2):
    User→Kernel copy: 10,000 × 8 B = 80,000 B (pollfd array in)
    Kernel scan:      10,000 FD checks
    Kernel→User copy: 10,000 × 8 B = 80,000 B (pollfd array out, revents filled)
    User scan:        10,000 revents inspections
    Total:            ~30,000 ops + 160 KiB copy per call

  epoll_wait(2):
    User→Kernel copy: 0 (interest set is already in kernel)
    Kernel scan:      0 (kernel walks only the ready list)
    Kernel→User copy: 5 × 12 B = 60 B (5 epoll_event structs)
    User scan:        5 events
    Total:            ~5 ops + 60 B copy per call   ← O(M), not O(N)

  Speedup at N=10000, M=5: epoll is ~6000× cheaper per call than poll,
  ~2500× cheaper than select.
```

The production failure mode is the silent one: nothing crashes, nothing logs an error, the server just gets slower as connection count grows. The metric that reveals it is CPU usage plotted against concurrent connection count — a `select`/`poll`-based server shows a straight-line climb (CPU proportional to N), while an `epoll`-based server shows a flat line until something else (bandwidth, request CPU) becomes the bottleneck. The fix is always the same: stop calling `select`/`poll` in a hot loop. Either migrate to `epoll` directly, or use a runtime whose event loop already does so. Every runtime in section 04 — Node's libuv, Python's asyncio, Java's NIO.2, PHP's `stream_select` (the one outlier still using `select`/`poll` under the hood, which is why PHP-FPM never scales past a few hundred concurrent connections per worker) — has already made this choice for you.

## How This Connects to the Runtimes

Every runtime in section 04 picks one of the three multiplexing APIs and hides it behind an abstraction. The choice is invisible at the application layer but determines the runtime's hard ceiling:

- **Node.js / libuv**: Uses `epoll` on Linux, `kqueue` on BSD/macOS, IOCP on Windows. The libuv `uv_poll_t` API is a thin wrapper around `epoll_ctl` / `epoll_wait`. The default `UV_THREADPOOL_SIZE=4` covers only operations that cannot be multiplexed (file I/O on Linux pre-5.x kernels, DNS via `getaddrinfo`, crypto).
- **Java NIO (JDK ≥ 1.5)**: `java.nio.channels.Selector` is backed by `epoll` on Linux via the `EPollSelectorProvider` (default since JDK 1.5). Before 1.5 it used `poll`, which is why pre-Tomcat 6 servers did not scale.
- **Python asyncio**: `selectors.DefaultSelector` returns `EpollSelector` on Linux, `KqueueSelector` on BSD/macOS, `SelectSelector` as the lowest-common-denominator fallback. The fallback exists for legacy POSIX systems without `epoll`/`kqueue` (essentially: embedded RTOSes).
- **PHP**: `stream_select` is a thin wrapper around `select(2)` and inherits the `FD_SETSIZE=1024` ceiling. This is the structural reason PHP-FPM cannot hold more than ~1024 file descriptors per worker, and why long-running PHP daemons (ReactPHP, Swoole) replace it with `epoll`.

When you read those runtime notes, come back here and trace which syscall each runtime feature maps to. The runtime's "max concurrent connections" claim is, underneath, a claim about which row of the multiplexing-API table it sits on.

## Hands-On Exercise

```bash
# Confirm your libc's FD_SETSIZE — the 1024 ceiling that haunts select()
echo '#include <sys/select.h>' | gcc -E -dM - | grep FD_SETSIZE
#   expected output: #define FD_SETSIZE 1024

# Watch an old select() server die at >1024 FDs
#   Start a Python server using select.select() in a loop, then:
ulimit -n 65536
python3 -c "
import socket, select
ls = socket.socket(); ls.bind(('',9000)); ls.listen(65535)
conns = []
import sys
for i in range(2000):
    c, _ = ls.accept(); c.setblocking(False); conns.append(c)
    if i % 100 == 0: print(f'accepted {i} conns')
" &
# from another host:
seq 1 2000 | xargs -P 100 -I{} nc 127.0.0.1 9000
# Watch the server crash with 'ValueError: filedescriptor out of range in select()'
#   the moment it tries to add FD >= 1024 to the fd_set.

# Compare select vs poll vs epoll under load (microbenchmark):
#   git clone https://github.com/frevd/io_bench
#   Run with N=100, 1000, 5000, 10000 monitored FDs.
#   Plot: epoll stays flat; select hits EINVAL above 1024;
#   poll CPU grows linearly with N.

# Confirm epoll is what Node actually uses:
strace -f -e trace=epoll_create,epoll_ctl,epoll_wait,select,poll \
    node -e 'require("net").createServer().listen(9000)' 2>&1 | head -10
#   On Linux you should see ONLY epoll_* syscalls, never select() or poll().
```
