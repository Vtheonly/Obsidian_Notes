# 02.05.05. High-Performance Event Architecture Patterns

## What This Is

An "event architecture pattern" is the structural decision about how an application organises the relationship between its event loop, its threads, its I/O, and its per-connection state. The kernel gives you `epoll` (or `kqueue`, or `io_uring`); the application decides how many threads run `epoll_wait`, how connections are distributed across them, and whether the application code is written as a state machine (callback-driven), a coroutine (suspends and resumes), or an actor (message-passing). These are the patterns that sit on top of the kernel primitives in [[02.05.03. Modern IO Multiplexing epoll and kqueue]] and below the framework abstractions in section 05.

This note covers the three pattern families that have dominated backend architecture since 2000: the **Reactor** (readiness-based, the de facto standard on POSIX — used by Nginx, Redis, Node.js, Netty, asyncio, Tokio), the **Proactor** (completion-based, native on Windows via IOCP, emulated everywhere else), and **`io_uring`** (Linux 5.1+, the convergence point that makes Proactor-style completion semantics available on POSIX without emulation). Each one is examined as a structural choice with its own scalability profile, complexity cost, and signature failure mode. Knowing which pattern a runtime uses is what lets you predict its behaviour under load before reading a single line of its source.

## The Details

### The Reactor Pattern: Synchronous event demultiplexing and dispatching to registered handlers.

The Reactor pattern was formalised by Douglas Schmidt et al. in *Pattern-Oriented Software Architecture, Volume 2* (POSA2, 2000). The definition: a single **event demultiplexer** (typically `epoll_wait` / `kevent` / `WaitForMultipleObjects`) blocks until one or more event sources are ready; the **Reactor** then dispatches each ready event to the **event handler** that registered for it. The handler runs synchronously in the Reactor's thread — it does the I/O, updates state, possibly schedules more I/O, and returns. The Reactor then loops back to `epoll_wait`. There is no async I/O in the Reactor pattern; the I/O is non-blocking and synchronous, and the "asynchrony" is at the dispatch layer, not the syscall layer.

The simplest deployment is the **single-loop single-thread** Reactor: one thread, one `epoll` FD, all connections in the interest set. This is the architecture of Redis (the `ae.c` event loop), Node.js (libuv's main thread), and most Python asyncio applications. The beauty is that no locks are needed — only one thread ever touches application state, so all data structures can be plain non-atomic types. The cost is that the application cannot use more than one CPU core for its event loop, and a single CPU-bound handler stalls every other connection. Redis handles this by keeping every command O(log N) or better and never doing disk I/O on the main thread (the `fork()`-based BGSAVE runs in a child process). Node.js handles it with the libuv thread pool (`UV_THREADPOOL_SIZE=4`) for fs/DNS/crypto and tells users to spawn worker processes (`cluster` module) for CPU-bound work. This works until it does not — a single slow regular expression in a request handler can stall a Node.js event loop for seconds, and there is no way to detect it from inside the process.

The **master-worker multi-Reactor** scales the pattern to multiple cores. A master process binds the listening socket, then forks N worker processes, each of which inherits the listening FD (or binds its own via `SO_REUSEPORT`). Each worker runs its own single-threaded Reactor on its own `epoll` FD. The kernel does the load balancing: under `SO_REUSEPORT`, the NIC RX path hashes the 4-tuple to one worker; under classic fd-inheritance, each worker calls `accept()` on the shared listener and the kernel hands each connection to whichever worker wins the lock. Nginx is the canonical example: `worker_processes auto;` forks one worker per CPU, `listen 80 reuseport;` enables kernel-level dispatch, and each worker runs an independent `epoll` loop. The advantage over the single-thread Reactor is N-fold throughput (one core per worker); the disadvantage is that connections cannot share in-process state — every worker has its own connection pool, its own cache, its own Lua state. Nginx's `proxy_cache` is therefore per-worker by default, with shared memory zones (`proxy_cache_path ... keys_zone=NAME:SIZE`) for cache sharing across workers via explicit shared memory.

The **thread-per-core sharded Reactor** (ScyllaDB's Seastar, 2014) goes further: it pins one Reactor thread per CPU core, disables the kernel scheduler's migration (`sched_setaffinity`), and **shards all application state** by a partition key. There are no shared data structures and no locks — every shard owns its portion of the data, and cross-shard communication happens via lock-free single-producer single-consumer queues (`seastar::smp_message_queue`) between cores. ScyllaDB uses this to do millions of IOPS on a single node with sub-millisecond p99 latency. The cost is that the application must be written in the Seastar programming model (a C++ future/promise library) and that re-sharding requires moving data physically between cores. The win is that the per-core working set fits in L2/L3 cache, so cache misses are rare and throughput scales linearly with core count.

The **actor model** (Erlang/OTP, 1973→1986→open source 1998; Akka for the JVM, 2009) is a Reactor variant where each "actor" is a single-threaded event loop with a mailbox. Actors communicate by sending immutable messages to each other's mailboxes; the runtime schedules actors onto carrier threads (Erlang BEAM uses ~one scheduler thread per core, plus async thread pools for I/O). The pattern is Reactor at the per-actor level — each actor's `receive` is an `epoll_wait` over its mailbox — but the runtime is free to schedule millions of actors onto a small number of OS threads. Erlang's BEAM preempts at every reduction (a counter, ~2000 function calls) so a CPU-bound actor cannot starve others. This is the structural fix to Node.js's "one slow handler stalls the loop" problem — Erlang has the same single-threaded-per-actor model, but preemption makes it safe under hostile workloads. WhatsApp ran 1M+ concurrent TCP connections on a single Erlang node in 2012 using exactly this pattern.

The **async/await Reactor** (Tokio for Rust, async-std, .NET's `async`/`await`, Python's `asyncio` with `await`, JavaScript's `async`/`await` on top of libuv) expresses the Reactor pattern with compiler-supported coroutines. Each `async fn` compiles to a state machine; `await` is a suspension point that returns `Poll::Pending` to the executor (the Reactor). The executor (`tokio::runtime::Runtime`'s worker pool) runs `epoll_wait` and wakes the appropriate `Future` when its FD becomes ready. The advantage over callback-style Reactor is that local variables and the call stack survive across suspension points, so application code reads like blocking code but executes like an event loop. Tokio uses **work-stealing**: each worker thread has its own run queue, and idle workers steal futures from busy workers' queues, which gives the multi-core scaling of master-worker without the per-worker connection pool duplication. This is the architecture used by most Rust async services (Discord, Cloudflare's Pingora, AWS Firecracker's API server) and increasingly by Java via Project Loom's virtual threads (which are conceptually the same — user-space scheduled coroutines over a carrier thread pool).

```text
The Reactor family — structural comparison:

  Pattern                Threads    Sharing model       Examples
  ─────────────────────────────────────────────────────────────────────
  Single-loop            1          none (no locks)     Redis, Node.js
  Master-worker          N proc     none (per-worker)   Nginx, PHP-FPM
  Thread-per-core        N threads  none + sharded      ScyllaDB/Seastar
  Actor model            M:N        immutable msgs      Erlang, Akka
  Async/await+work-steal N threads  futures + atomic    Tokio, Loom, .NET
```

The production failure mode common to all Reactor variants is **handler starvation**. Because the Reactor runs handlers synchronously in its own thread, any handler that blocks (a synchronous database call, a CPU-bound computation, an accidental `Thread.sleep`) stalls every other connection on that Reactor. The diagnostic is `perf top` showing application code (not `epoll_wait`) taking the majority of CPU time while `epoll_wait`'s call frequency drops to near zero. The fix is to move blocking work off the Reactor thread: a worker thread pool (libuv's `UV_THREADPOOL_SIZE`, Python's `loop.run_in_executor`, Java's `CompletableFuture.supplyAsync`), or a separate process (Nginx's `--with-threads` for fs reads). Every Reactor runtime documents this; every Reactor runtime has users who learn it the hard way during a production incident.

### The Proactor Pattern: Asynchronous I/O completion handlers (POSIX AIO, Windows IOCP)

The Proactor pattern (also from POSA2) is the dual of the Reactor. Where the Reactor says "tell me when an FD is *ready* for I/O, and I will do the I/O synchronously," the Proactor says "I will *initiate* the I/O now, and you tell me when it has *completed*." The application calls an asynchronous-initiation function (`ReadFileEx` on Windows, `aio_read` on POSIX, `io_uring_prep_read` + `io_uring_submit` on Linux 5.1+) which returns immediately. The kernel (or a kernel-side thread pool) performs the I/O and posts a completion event to a completion port or queue. A Proactor thread waits on the completion queue and dispatches each completion to the application's completion handler, which processes the result. The application code is written as "I have initiated N reads; here is what to do with each one when it finishes."

On Windows, this is the native model. `CreateIoCompletionPort` associates a file handle with an I/O completion port; `GetQueuedCompletionStatusEx` blocks waiting for batches of completions; `ReadFile`/`WriteFile` with an overlapped `OVERLAPPED` structure initiate async I/O. The thread pool that calls `GetQueuedCompletionStatusEx` is typically sized to the number of CPUs, and the OS distributes completions to threads that are not busy. This is what IIS, SQL Server, .NET's `ThreadPool` and `async`/`await` are built on. Windows has had this since NT 3.5 (1994) and it is the reason Windows servers historically outperformed Linux on I/O-bound workloads until Linux got `epoll` (2002) and later `io_uring` (2019).

On POSIX, the Proactor pattern has historically been **emulated** rather than native. The POSIX AIO APIs (`aio_read`, `aio_write`, `aio_error`, `aio_return`) are implemented in glibc via a user-space thread pool that calls synchronous `pread`/`pwrite` — there is no kernel-level completion port. The performance is therefore worse than plain threads, because every AIO request spawns work onto a fixed-size thread pool (`/etc/conf/libc.aio` / `aio_read` uses `pthread_create` under the hood). Linux's native `aio_*` syscalls (`io_setup`, `io_submit`, `io_getevents`) require `O_DIRECT` files (they silently fall back to blocking for buffered I/O), making them useless for general-purpose file I/O and socket I/O. As a result, every cross-platform Proactor runtime — boost::asio with `io_context::post`, libuv with `uv_queue_work`, Java NIO.2's `AsynchronousChannel` — is actually a Reactor underneath, with a thread pool that does blocking I/O and posts completions back to the event loop. This is what is meant by "fake Proactor": the API looks like Proactor, the implementation is Reactor + threads.

The reason the Proactor pattern is appealing despite the emulation cost is that completion semantics compose better than readiness semantics for some workloads. A Reactor handler that wants to "read 4 KiB, then write the result, then close" must register for `EPOLLIN`, read, register for `EPOLLOUT`, write, deregister, close — a sequence of `epoll_ctl` calls. The equivalent Proactor code is "submit a 4 KiB read; on completion submit a write; on completion close" — a chain of continuations submitted at once. Modern async/await runtimes collapse this syntactically (the `await` keyword hides the registration dance), but the underlying syscall pattern is the same: Reactor runtimes do more `epoll_ctl` calls per request than Proactor runtimes do completion submissions. Under high request rates (100k+ rps per core) the difference is measurable — a few percent of CPU spent on `epoll_ctl` that the Proactor equivalent does not spend.

```text
Reactor vs Proactor — where the work happens:

  Reactor (Linux, readiness):
    thread ── epoll_wait() ── events[] ── dispatch ── handler ── read()
            └─── repeat ────┘
    I/O is initiated by the application when ready.
    Syscalls per request: epoll_wait + read + epoll_ctl(MOD) + write + ...

  Proactor (Windows IOCP, or io_uring on Linux 5.1+):
    thread ── GetQueuedCompletionStatus() ── completion ── handler
            └──────── repeat ──────────────┘
    I/O is initiated by the application *before* waiting.
    Syscalls per request: ReadFile + GetQueuedCompletionStatus + ...

  Fake Proactor (POSIX, libuv, boost::asio):
    thread ── epoll_wait() ── handler ── submits to thread pool ──┐
    thread pool ── blocking read() ── posts completion ───────────┘
    thread ── epoll_wait(EVFD) ── runs completion handler
    Same syscall pattern as Reactor + extra thread-pool overhead.
```

The production failure mode of the Proactor pattern is **completion-handler starvation under backpressure**. When completions arrive faster than the application's handlers can process them, the completion queue fills and the kernel either drops completions (POSIX AIO's `aio_suspend` will then return unexpected errors) or applies implicit flow control by not initiating new I/O (IOCP's behavior when the per-port queue is full). The diagnostic is the completion queue depth climbing (visible in `io_getevents`'s return value or `GetQueuedCompletionStatus`'s timeout rate) while application CPU stays low. The fix is explicit application-level flow control: limit the number of in-flight async I/Os per connection (a semaphore in handler context), and reject new requests when the limit is reached. Without this, a Proactor server under load exhibits a death spiral: queue grows → memory grows → GC pressure mounts (in managed runtimes) → handlers slow down → queue grows faster. The same pattern affects Reactor servers, but the Reactor's natural backpressure (the application stops calling `epoll_wait`, so the kernel's socket buffers fill, so the peer's TCP window closes) provides a self-correcting feedback loop that the Proactor pattern lacks unless explicitly implemented.

### Next-Generation Linux I/O: `io_uring` architecture, shared Submission and Completion Ring Buffers, and zero-syscall I/O operations.

`io_uring` (Linux 5.1, May 2019; substantially extended in 5.2–6.x) is Linux's first true kernel-level asynchronous I/O API. It replaces both the emulated POSIX AIO and the `epoll` + blocking-I/O combination with a pair of shared ring buffers between user space and kernel space, plus an optional kernel-side polling thread. The design goal, articulated by Jens Axboe (the author), is to make every I/O operation take zero syscalls in the steady state — eliminating the syscall overhead that dominates high-IOPS workloads.

The architecture is two single-producer single-consumer rings, mapped into user-space memory via `mmap` after `io_uring_setup()`:

- **Submission Queue (SQ)** — user space writes Submission Queue Entries (`struct io_uring_sqe`, 64 bytes each) here describing the I/O to perform: opcode (`IORING_OP_READ`, `IORING_OP_WRITE`, `IORING_OP_ACCEPT`, `IORING_OP_SEND`, `IORING_OP_RECV`, `IORING_OP_CONNECT`, `IORING_OP_OPENAT`, `IORING_OP_CLOSE`, `IORING_OP_STATX`, etc.), file descriptor, buffer address, length, offset, and a `user_data` field that the kernel will echo back on completion. The kernel consumes entries from this ring.
- **Completion Queue (CQ)** — the kernel writes Completion Queue Entries (`struct io_uring_cqe`, 32 bytes each) here when an I/O finishes: `user_data` (matching the SQE), `res` (the result, like the return value of `read`), and `flags`. User space consumes entries from this ring.

The key insight is that **the rings are mapped into both user space and kernel space as shared memory**. To submit an I/O, user space writes an SQE (no syscall), updates the SQ tail pointer (a memory write, no syscall), and then either calls `io_uring_enter()` to notify the kernel (one syscall) or — if `IORING_SETUP_SQPOLL` was set at setup — does nothing, because a dedicated kernel thread is polling the SQ and picks up the new entry within microseconds. To collect completions, user space reads the CQ head pointer (a memory read, no syscall) and processes CQs until the head equals the tail. With SQPOLL, the steady state is: zero syscalls per I/O. The first benchmark numbers (Axboe, 2019) showed io_uring doing 1.6M IOPS on a single NVMe device where `aio` did 600K and synchronous `pread` did 200K — the syscall elimination is what makes the difference.

```c
#include <liburing.h>
#include <stdio.h>

int main(void) {
    struct io_uring ring;
    io_uring_queue_init(/* entries */ 256, &ring, /* flags */ 0);

    int fd = open("file.bin", O_RDONLY | O_DIRECT);

    /* Submit a read: write an SQE, no syscall yet */
    struct io_uring_sqe *sqe = io_uring_get_sqe(&ring);
    io_uring_prep_read(sqe, fd, buf, sizeof(buf), 0);
    io_uring_sqe_set_data(sqe, (void *)my_request_cookie);

    /* Notify kernel (one syscall); with SQPOLL this call is omitted */
    io_uring_submit(&ring);

    /* Wait for completion */
    struct io_uring_cqe *cqe;
    io_uring_wait_cqe(&ring, &cqe);
    int res = cqe->res;             /* bytes read, or -errno */
    void *cookie = io_uring_cqe_get_data(cqe);
    io_uring_cqe_seen(&ring, cqe);  /* advance CQ head */

    io_uring_queue_exit(&ring);
}
```

`io_uring` is fundamentally a **Proactor** API: you initiate I/O by submitting an SQE, the kernel completes it asynchronously, and you receive a completion. This is the first time the Proactor pattern has been native on Linux without emulation. The implications for runtime design are significant — libuv, Tokio, and Java's Project Loom have all added io_uring backends since 2020. Tokio's `tokio-uring` crate uses io_uring for file I/O (where it eliminates the thread-pool overhead of the standard `tokio::fs`) and is exploring it for socket I/O. libuv added `uv_uring` experiments but has not flipped the default. The adoption is gradual because io_uring's API surface is large and several early kernels (5.1–5.7) had security issues that allowed unprivileged users to escape via crafted SQEs — fixed in 5.12+ but slow to backport to LTS kernels.

The `IORING_SETUP_SQPOLL` mode deserves special attention. With SQPOLL enabled, the kernel spawns a dedicated thread (visible in `ps` as `iou-sqp-CPU`) that busy-polls the SQ ring. This thread consumes CPU continuously — typically pinned to one core — even when the application is idle, unless `IORING_SETUP_SQ_AFF` is also set and the SQPOLL thread parks itself when the SQ is empty for `sq_cpu` milliseconds. The trade-off is: burn one core permanently for zero-syscall I/O. This is a great deal if the workload is high-IOPS (a database doing 500K+ IOPS — the saved syscalls are worth far more than one core's time) and a terrible deal if the workload is bursty (the SQPOLL thread wastes a core during idle periods). Production deployments use SQPOLL only on dedicated I/O threads on dedicated cores, never on the application's general-purpose threads.

The connection to the Reactor/Proactor comparison is that `io_uring` finally lets Linux applications use the Proactor pattern natively, with the same syscall-elimination properties Windows IOCP has had since 1994. For the first time on Linux, a runtime can be a "real Proactor" rather than a "fake Proactor." Tokio's design is interesting here: its main scheduler stays a Reactor (using `epoll` for socket readiness), but its file I/O uses io_uring (a Proactor). This is because socket I/O is naturally readiness-driven (the kernel knows when a packet arrives), while file I/O is naturally completion-driven (the kernel does not have a "file became readable" notification, only "this read completed"). The two patterns coexist in the same runtime, each used where it fits.

```text
io_uring steady-state syscall pattern (with SQPOLL):

  User thread            Shared memory           Kernel
  ──────────────────────────────────────────────────────────
  write SQE              ──► SQ ring
  update SQ.tail (memory write)                   ── SQPOLL thread
                                                     polls SQ.tail
                                                     sees new entry
                                                     initiates I/O
                                                     on completion:
                                                     writes CQE ◄── CQ ring
                                                     updates CQ.head
  read CQ.head (memory read)
  process CQ             ◄── CQ ring

  Syscalls in steady state: ZERO (with SQPOLL)
  Syscalls without SQPOLL: one io_uring_enter() per batch of submissions
```

The production failure mode of `io_uring` is its youth. As of 2024, the API is still being extended — every kernel release adds new opcodes, new flags, and new behaviors, and not all of them are stable. Several high-severity CVEs in 2024 (notably CVE-2024-0582, a use-after-free in `io_uring`'s registered-buffer path) prompted Google to disable `io_uring` entirely on production servers (Project Zero, "Disable io_uring on systems where it is not needed", February 2024). The advice for application authors is: use `io_uring` for the IOPS-bound workloads where it actually helps (databases, storage appliances, high-throughput media servers), keep using `epoll` for socket-heavy workloads where the syscall overhead is not the bottleneck, and stay on a recent LTS kernel (5.15+ or 6.1+) to get the security fixes. The runtime notes in section 04 will track which runtimes have an `io_uring` backend and whether it is on by default — as of 2024, only Tokio ships it in production, and only for file I/O.

## Cross-Ecosystem Implementation

The five patterns map to runtimes and frameworks as follows. Each framework in section 05 inherits its runtime's pattern choice — the framework cannot pick a different concurrency model than the runtime it sits on.

| Pattern | Runtime (section 04) | Framework (section 05) | Throughput ceiling | Tail latency profile |
|---|---|---|---|---|
| Single-loop single-thread | Redis, Node.js (libuv main) | Express, Nest, Koa, Fastify | 1 core for app loop; pool for fs/DNS | p99 spikes on slow handler |
| Master-worker | Nginx, PHP-FPM, Puma (clustered) | Laravel (PHP-FPM), Rails (Puma) | N cores × 1 connection pool each | flat under load, per-worker skew |
| Thread-per-core / sharded | ScyllaDB (Seastar), LMAX Disruptor | (none in section 05 — too specialised) | linear in core count | sub-ms p99 if sharded correctly |
| Actor model | Erlang BEAM, Akka (JVM) | Phoenix (Elixir), Play (Akka) | millions of actors; preemptive | flat under high fan-out |
| Async/await + work-steal | Tokio, .NET, Loom (JVM), asyncio | Axum, Actix, FastAPI, Spring WebFlux | N cores, shared pools | flat with bounded queues |
| io_uring native | Tokio (file I/O only, 2024) | (none yet for full stack) | TBD | TBD |
| Windows IOCP Proactor | .NET CLR, IIS | ASP.NET Core | high on Windows, lower on Linux port | flat under load on Windows |

When you read the runtime notes in section 04, identify which row of this table each runtime occupies. The delta notes in section 05 then show how each framework exposes the runtime's pattern to application code — for example, Express's callback signature is a direct expression of Node's single-loop Reactor, while Spring WebFlux's `Mono`/`Flux` is an expression of Reactor Netty's work-stealing async/await model.

## Hands-On Exercise

```bash
# Confirm which Reactor pattern your favourite server uses:
# - Single-loop (Redis): one process, one thread visible
redis-server --port 9000 --daemonize yes
ps -M $(pgrep -nf redis-server) | head -5      # shows 1 thread

# - Master-worker (Nginx): N worker processes, each 1 thread
nginx -c /etc/nginx/nginx.conf
ps -eLf | grep 'nginx: worker' | wc -l         # = worker_processes

# - Async/await work-stealing (Tokio): one process, M threads
#   Run a Rust Tokio binary and count threads:
ps -M $(pgrep -nf my_tokio_app) | wc -l        # ~ num_cpus + 1

# Watch io_uring in action (Linux 5.1+):
uname -r                                       # need 5.1+
grep io_uring /proc/kallsyms | head -3         # symbols present?
sudo apt install liburing-dev                  # on Debian/Ubuntu
# Compile and run the small io_uring read example from this note:
#   gcc -O2 -luring io_demo.c -o io_demo && ./io_demo

# Compare syscall counts for the same workload:
#   - Nginx (epoll, Reactor)
sudo perf stat -e 'syscalls:sys_enter_*' -- nginx -c /etc/nginx/nginx.conf &
wrk -t 4 -c 1000 -d 30s http://127.0.0.1:80/
# Note epoll_wait, epoll_ctl, accept4, recvfrom, sendto counts.
#
#   - Tokio-uring app on the same hardware
sudo perf stat -e 'syscalls:sys_enter_*' -- ./my_tokio_uring_app &
wrk -t 4 -c 1000 -d 30s http://127.0.0.1:8081/
# Note io_uring_enter (much rarer with SQPOLL), no epoll_*, no read/write syscalls.

# Identify a Reactor handler starvation incident in production:
#   - `perf top -p <pid>` shows application code (not epoll_wait) at >80% CPU
#   - `epoll_wait` call count drops to near zero in `perf stat`
#   - p99 latency climbs while p50 stays flat
#   - Fix: move the blocking handler to a worker pool
```
