# 02.05.04. Edge-Triggered vs. Level-Triggered Notification

## What This Is

When you register a file descriptor with `epoll` (or `kqueue`), you choose between two readiness-notification semantics. **Level-triggered (LT)** — the default — means `epoll_wait` will keep returning the FD as long as its buffer has data the application has not yet consumed. **Edge-triggered (ET)** — requested with the `EPOLLET` flag on `epoll_ctl` or `EV_CLEAR` on `kevent` — means `epoll_wait` returns the FD exactly once when its state transitions from "empty" to "has data," and will not return it again until the application drains the buffer to empty *and* new data arrives. The two modes have identical correctness — every byte reaches the application eventually — but radically different syscall counts, latency profiles, and bug surfaces.

This note covers what each mode does at the kernel data-structure level, why edge-triggered requires non-blocking sockets (and what breaks if you forget), and the starvation risk that edge-triggered introduces along with the `EPOLLONESHOT` / `EPOLLEXCLUSIVE` mitigations. Every runtime in section 04 has made this choice: Nginx and Redis use edge-triggered for fewer syscalls; Java NIO, Python asyncio, and Node.js libuv default to level-triggered for easier reasoning. Knowing which is which explains why a Redis event-loop trace looks different from a Node.js event-loop trace under the same load.

## The Details

### Level-Triggered (LT) Mode: Continuous notifications as long as buffer data is present (default mode, simpler error recovery).

Level-triggered is the default mode for both `epoll` and `kqueue`. The semantics are: after `epoll_ctl(EPOLL_CTL_ADD, fd, EPOLLIN)`, `epoll_wait` will include `fd` in its returned events on every call where the kernel's socket receive buffer is non-empty. If the application calls `epoll_wait`, gets the FD, reads 100 bytes (but 500 more remain in the buffer), and calls `epoll_wait` again — the same FD comes right back. The FD keeps coming back, every iteration, until the application calls `read()` enough times to drain the buffer to zero (at which point `read()` returns -1/EAGAIN).

This is exactly the semantics of `select` and `poll` — those APIs are also level-triggered. The application's mental model is "ask the kernel what is ready right now, do something about it, ask again." It is straightforward to reason about: if your `epoll_wait` call returned the FD, there is definitely data; if it did not return the FD, there is definitely no data (right now). You cannot lose data by reading too little, because the kernel will keep reminding you. The bug surface is correspondingly small.

The cost is wakeup frequency. Under level-triggered semantics, a single TCP segment that arrives in two pieces (because the peer's segment was fragmented by the network) will produce two `epoll_wait` wakeups: one for the first fragment, one for the second. If the application reads the first fragment but not the second, the next `epoll_wait` returns the FD again — even though the application could have handled both fragments in one read pass. The wakeup-to-work ratio is higher than strictly necessary, which under high packet rates translates into more syscalls, more context switches, and lower throughput. Benchmark numbers (Nginx LT vs ET on the same hardware) typically show a 5–15% throughput difference in favour of ET for the request-per-second bound on small-payload HTTP.

```c
/* Level-triggered epoll loop. Read what is convenient, yield, repeat.
 * The kernel will wake us again if there is more data. */
for (;;) {
    int n = epoll_wait(epfd, events, 1024, -1);
    for (int i = 0; i < n; i++) {
        int fd = events[i].data.fd;
        char buf[4096];
        ssize_t r = read(fd, buf, sizeof(buf));
        if (r > 0) {
            app_consume(buf, (size_t)r);
            /* It's fine to stop here. If more data is in the kernel
             * buffer, epoll_wait will return this fd again next call. */
        } else if (r == 0) {
            epoll_ctl(epfd, EPOLL_CTL_DEL, fd, NULL);
            close(fd);
        } else if (errno != EAGAIN && errno != EWOULDBLOCK) {
            /* real error */
        }
    }
}
```

The production failure mode of level-triggered is the opposite of edge-triggered's: **excess wakeups**. A slow-reading client that never quite drains its buffer (because the application processes one byte at a time, say) produces a steady stream of wakeups on every `epoll_wait` iteration — possibly thousands per second — each of which does almost no useful work. The diagnostic is `strace -c` showing `epoll_wait` and `recvfrom` as the top two syscalls by count, with `recvfrom` returning very small payloads. The fix is usually architectural (process the whole buffer in one pass, even under LT) rather than a switch to ET. The simplicity of LT — no requirement to drain, no risk of lost events, no need for non-blocking sockets — is why Java NIO, Python asyncio, and libuv all default to it. Nginx and Redis are the exceptions that chose ET explicitly for the throughput win.

### Edge-Triggered (ET) Mode: Notification triggered strictly on state transitions (requires non-blocking drained reads in a loop).

Edge-triggered mode is requested by OR-ing `EPOLLET` into the `events` field at registration time:

```c
struct epoll_event ev = { .events = EPOLLIN | EPOLLET, .data.fd = fd };
epoll_ctl(epfd, EPOLL_CTL_ADD, fd, &ev);
```

With `EPOLLET` set, `epoll_wait` returns the FD only on the *transition* from "no data available" to "data available." If the application reads part of the buffer and leaves some bytes behind, `epoll_wait` will *not* return that FD again — it has already notified you, and from the kernel's perspective the state did not change back to "no data." The only way the FD will be returned again is if (a) the application drains the buffer completely to empty, *and* (b) new data arrives after the drain. If the application fails to drain, the bytes left in the kernel buffer are effectively stranded until the peer sends more data — and if the peer is waiting for a response to those bytes, the connection deadlocks.

This is why edge-triggered mode **mandates** non-blocking sockets. The application must call `read()` in a loop until it returns -1 with `errno=EAGAIN` (or `EWOULDBLOCK`). On a blocking socket, that loop's final `read()` (the one that finds the buffer empty) would *block the entire event loop* — the thread hangs in `recvmsg()` waiting for data that may never come, while every other monitored FD goes un-serviced. The combination of `EPOLLET` and a blocking socket is one of the classic causes of "my server randomly hangs at 100% CPU and never recovers" bugs in hand-rolled event loops.

The correct edge-triggered read pattern is the drain loop:

```c
/* Edge-triggered epoll loop. MUST drain to EAGAIN, MUST be non-blocking. */
for (;;) {
    int n = epoll_wait(epfd, events, 1024, -1);
    for (int i = 0; i < n; i++) {
        int fd = events[i].data.fd;
        char buf[65536];
        /* Drain everything the kernel has for this fd. */
        for (;;) {
            ssize_t r = read(fd, buf, sizeof(buf));
            if (r > 0) {
                app_consume(buf, (size_t)r);
                continue;            /* loop back for more */
            } else if (r == 0) {
                epoll_ctl(epfd, EPOLL_CTL_DEL, fd, NULL);
                close(fd);
                break;
            } else if (errno == EAGAIN || errno == EWOULDBLOCK) {
                break;                /* drained; safe to wait for next edge */
            } else if (errno == EINTR) {
                continue;             /* signal interrupted, retry */
            } else {
                /* real error (EBADF, ECONNRESET, etc.) */
                epoll_ctl(epfd, EPOLL_CTL_DEL, fd, NULL);
                close(fd);
                break;
            }
        }
    }
}
```

The payoff is the steady-state syscall count. Under ET, the kernel calls `ep_poll_callback` exactly once per transition — one wakeup per packet batch. Under LT, the kernel re-adds the FD to `rdllist` on every `epoll_wait` call where the buffer is non-empty. On a 100 Gbit/s link with 64-byte packets and 1,000 active connections, ET produces roughly 1 wakeup per connection per packet (1k wakeups/s); LT can produce 10k–100k wakeups/s depending on how fast the application drains. For Nginx serving small static files, ET was measured at 18% higher requests-per-second than LT on the same hardware (Nginx internal benchmarks circa 2010; the gap has narrowed as kernels have optimised LT, but ET still wins by 5–10%).

The production failure mode is the **missing drain loop** — a developer reads once, processes the result, and returns to `epoll_wait` without looping to EAGAIN. The kernel has delivered its edge notification and will not deliver another until the buffer transitions empty→non-empty. The unread bytes sit in the kernel's `sk_receive_queue` indefinitely. If the protocol is request-response (HTTP, Redis, gRPC), the peer is waiting for a response to the bytes the application never saw; the peer times out; the connection is torn down; the application logs "client closed connection" with no indication that the cause was its own bug. The diagnostic is `ss -tin` showing `Recv-Q` > 0 on long-lived ET-registered connections. The fix is the drain loop shown above — non-negotiable, on every `EPOLLET`-registered FD. See also the `EPOLLRDHUP` flag, which lets `epoll_wait` tell you when the peer half-closed the read side (so you can stop draining).

### Starvation risks in Edge-Triggered mode and mitigations using bounded drain loops

Edge-triggered mode introduces a fairness problem that level-triggered does not have. Consider an event loop with two monitored FDs: `fd_A` (a peer sending a continuous 1 Gbit/s stream) and `fd_B` (a peer sending one byte every second). When `epoll_wait` returns, it may return both FDs. The application drains `fd_A` first — but `fd_A` never drains to empty, because the peer is filling it as fast as the application reads. The application's drain loop on `fd_A` runs forever; `fd_B`'s single byte sits unserviced. Under LT, the application would naturally yield after a bounded read (one buffer's worth) and check `fd_B` on the next iteration; under ET, the application is incentivised to drain completely, which under continuous-traffic conditions means draining forever.

The mitigation is a **bounded drain loop**: cap the number of `read()` calls per FD per `epoll_wait` wakeup (say, 32), and if the cap is hit without draining, do something to ensure the FD is serviced again soon. Options:

1. **Re-arm via `EPOLL_CTL_MOD`.** After exhausting the cap, call `epoll_ctl(epfd, EPOLL_CTL_MOD, fd, &ev)` with the same events mask. This forces `epoll` to re-evaluate the FD's readiness and, if there is still data, re-add it to `rdllist`. This works under both LT and ET, but under ET it is the canonical way to "ask the kernel to remind me later."
2. **Use `EPOLLONESHOT`.** Register the FD with `EPOLLIN | EPOLLET | EPOLLONESHOT`. After `epoll_wait` returns the FD, the kernel disables it (no further events until `EPOLL_CTL_MOD` re-arms). The application drains as much as it wants, then explicitly re-arms. This makes the "I'll come back to this" pattern explicit — the FD cannot fire again until the application says so. Nginx's worker model uses this for connection fairness.
3. **Maintain an explicit ready-list in user space.** When `epoll_wait` returns N FDs, push them all into a queue. Process one at a time, doing a bounded read on each, round-robin. When the queue is empty, call `epoll_wait` again. This is the standard `mio` / Tokio approach.

```c
/* Bounded drain: at most 32 reads per fd per wakeup. */
#define MAX_READS_PER_WAKEUP 32

for (int i = 0; i < n; i++) {
    int fd = events[i].data.fd;
    char buf[65536];
    int reads = 0;
    for (; reads < MAX_READS_PER_WAKEUP; reads++) {
        ssize_t r = read(fd, buf, sizeof(buf));
        if (r > 0) {
            app_consume(buf, (size_t)r);
        } else if (errno == EAGAIN || errno == EWOULDBLOCK) {
            break;   /* drained within the budget; fair to other fds */
        } else if (r == 0) {
            epoll_ctl(epfd, EPOLL_CTL_DEL, fd, NULL);
            close(fd);
            break;
        }
    }
    /* If we hit the cap, the fd was not drained. Under EPOLLET we MUST
     * re-arm or schedule a future read, or the residual data is lost. */
    if (reads == MAX_READS_PER_WAKEUP) {
        /* Option A: re-arm via MOD (forces re-evaluation). */
        epoll_ctl(epfd, EPOLL_CTL_MOD, fd, &events[i]);
        /* Option B: add to a user-space pending list for explicit processing. */
        /* pending_fds_push(fd); */
    }
}
```

A second starvation pattern is the **thundering herd** under multi-threaded `epoll`. If multiple threads call `epoll_wait` on the same `epfd` (a shared `epoll` instance, common in master-worker architectures), every thread wakes when any FD becomes ready — they all race to `accept()` the same connection, and N-1 of them return EAGAIN. Under high connection rates this multiplies CPU usage by N. The mitigation is `EPOLLEXCLUSIVE` (Linux 4.5, 2016): when multiple `epoll` instances (or one `epoll` FD shared across threads via `epoll_ctl` registrations) monitor the same FD with `EPOLLEXCLUSIVE`, the kernel wakes only *one* thread per event. This is the same idea as `SO_REUSEPORT`'s kernel-level dispatch (see [[02.04.04. Kernel Socket Buffers and Socket Tuning]]) but at the `epoll` layer. `EPOLLEXCLUSIVE` is incompatible with `EPOLLET` on the same FD in some kernel versions — check `epoll_ctl(2)` for the matrix.

The production failure mode of edge-triggered starvation is the "noisy neighbour" pattern: one client with a high-bandwidth streaming upload monopolises the event loop, and every other client sees multi-second latency. The application's p50 latency is fine, but p99 climbs to 30+ seconds and triggers client-side timeouts even though the server is healthy. The diagnostic is to plot per-FD read counts per `epoll_wait` wakeup — a healthy ET loop shows roughly equal reads per FD; a starving loop shows one FD with thousands and the rest with zero. The fix is the bounded drain loop plus either re-arming or user-space fairness scheduling. This is why the Nginx worker code has an explicit `ngx_event_t.ready` flag and a separate `ngx_epoll_process_events` that limits how many events each connection can process per loop iteration — pure edge-triggered without fairness is unusable in production, and the kernel gives you no help.

```text
Event delivery comparison at the same load (1 fast sender + 1 slow sender):

  Level-triggered (default):
    epoll_wait returns {fd_fast, fd_slow}          every iteration
    read fd_fast → 4 KiB → yield                    (kernel re-queues)
    read fd_slow → 1 byte → yield                   (kernel re-queues)
    Fairness: automatic (kernel keeps reminding you)
    Syscalls per packet: ~2 (epoll_wait + read)

  Edge-triggered with naive drain:
    epoll_wait returns {fd_fast, fd_slow}           once
    drain fd_fast forever (peer keeps filling)      fd_slow starves
    Syscalls per packet: ~1 (just read in the loop)
    Fairness: NONE — fd_slow's byte is stuck

  Edge-triggered with bounded drain (32 reads):
    epoll_wait returns {fd_fast, fd_slow}
    read fd_fast 32 times → 128 KiB → yield         (re-arm via MOD)
    read fd_slow 1 time → 1 byte → yield            (drained, no re-arm)
    epoll_wait returns {fd_fast} again               (fd_slow silent)
    Fairness: explicit via bounded budget + re-arm
    Syscalls per packet: ~1.5 (read + occasional MOD)
```

## How This Connects to the Runtimes

Each runtime in section 04 has chosen LT or ET, and the choice shows up in the runtime's API contract:

- **Node.js / libuv**: Defaults to **level-triggered**. The libuv `uv_poll_t` API never exposes `EPOLLET`; the runtime guarantees that `uv_poll_cb` will be re-invoked as long as the FD is ready and the user has not paused the poller. This is why Node.js code does not need explicit drain loops — the runtime does the reminding.
- **Java NIO**: Defaults to **level-triggered** (`Selector` does not set `EPOLLET`). The `SelectionKey.interestOps()` API is fundamentally LT — a key stays ready until the application adjusts its interest set. Netty's `EpollEventLoop` exposes ET via `ChannelOption.EPOLL_MODE = EpollMode.EDGE_TRIGGERED`, but it is opt-in and rarely used.
- **Python asyncio**: Defaults to **level-triggered** via `selectors.EpollSelector`. The `loop.add_reader(fd, callback)` contract is "call me when there is data" — the runtime re-adds the FD after each callback, equivalent to LT semantics.
- **Nginx**: Uses **edge-triggered** by default for both client and upstream sockets (`worker_aio_requests` and the `epoll` event module set `EPOLLET`). This is one of the structural reasons Nginx outperforms Apache on small-payload HTTP.
- **Redis**: Uses **edge-triggered** (`ae.c` sets `AE_READABLE | AE_WRABLE` mapped to `EPOLLIN | EPOLLOUT | EPOLLET`). The single-threaded event loop relies on ET for low syscall count.
- **Tokio / `mio` (Rust)**: Uses **edge-triggered**. The `mio::Poll` API returns `Token` values and expects the user to drain; `EPOLLONESHOT` is used for fairness in the multi-threaded scheduler.

When you read those runtime notes, come back here and check which row of the LT/ET table each runtime sits on. The runtime's "do I need to drain?" contract is decided at this layer.

## Hands-On Exercise

```bash
# Confirm what mode your favourite runtime uses:
# Node.js (libuv) — should be level-triggered (no EPOLLET in trace)
strace -f -e trace=epoll_ctl node -e 'require("net").createServer().listen(9000)' \
    2>&1 | grep -i EPOLLET | head -5
# Expected: no output (libuv does not set EPOLLET)

# Redis — should be edge-triggered
redis-server --port 9000 --daemonize yes
strace -f -e trace=epoll_ctl -p $(pgrep -nf redis-server) 2>&1 &
sleep 1; redis-cli -p 9000 SET k v; sleep 1; kill %1 2>/dev/null
# Expected: epoll_ctl(..., EPOLL_CTL_ADD, ..., EPOLLIN|EPOLLET|EPOLLRDHUP)

# Reproduce the missing-drain-loop bug under ET:
# Write a tiny C server with EPOLLET, read once per wakeup, watch Recv-Q climb
gcc -o et_bug et_bug.c   # server from this note's first C block, with the
                         # drain loop replaced by a single read()
nc 127.0.0.1 8080 < /dev/urandom | head -c 100000  # send 100KB
ss -tin 'sport = :8080'
# Expected: Recv-Q shows ~99KB stranded; client never gets a response.

# Compare wakeup counts under LT vs ET for the same workload:
perf stat -e 'syscalls:sys_enter_epoll_wait,syscalls:sys_enter_read' \
    -- ./your_server_lt  # then ./your_server_et
# Expect ET to show 5–10× fewer epoll_wait calls than LT at steady state.
```
