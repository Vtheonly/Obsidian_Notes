# 02.05.03. Modern IO Multiplexing epoll and kqueue

## What This Is

`epoll` (Linux 2.6, October 2002) and `kqueue` (FreeBSD 4.1, June 2000) are the two stateful I/O multiplexing APIs that every modern event loop is built on. Where `select` and `poll` are stateless — the kernel has no memory of what you asked last time, so every call re-transmits the full interest set — `epoll` and `kqueue` maintain a persistent kernel data structure of the FDs the application cares about, and a `wait` call returns only the FDs that have actually changed state. This is the kernel-level fix for the C10K problem, and it is why Nginx, Redis, Node.js, Envoy, and every JVM NIO selector on Linux can hold hundreds of thousands of idle connections at < 1% CPU.

This note covers the internal architecture of the `epoll` data structures (a red-black tree of monitored FDs plus a ready list of FDs with events), the three syscalls that comprise the API, the complexity analysis that makes it O(1) per ready event, and the BSD/macOS `kqueue` API which is conceptually similar but uses a richer filter model. Every runtime in section 04 — Node's libuv, Java's NIO, Python's asyncio, Rust's `mio`, Go's runtime poller — is a thin wrapper around one of these two APIs. The runtime-specific abstractions (`Promise`, `Future`, `Coroutine`, `Channel`) sit on top; the kernel primitive is what they all converge to.

## The Details

### Linux `epoll` architecture: State persistence in kernel memory via Red-Black Trees and Ready Lists (Doubly-Linked Lists).

The kernel object behind an `epoll` instance is `struct eventpoll`, defined in `fs/eventpoll.c` (not in any public header — it is internal to the kernel). It holds three pieces of state that together implement the O(1) readiness notification:

- **`rbr`** — a red-black tree of every FD currently registered, keyed by the FD number. Each entry is a `struct epitem` carrying the FD, the requested `events` bitmask, the user-supplied `epoll_data_t` (typically a pointer or an int the application uses to find its own per-connection state), and a list of every `epoll` instance this FD is registered with (a single FD can be in multiple `epoll` sets).
- **`rdllist`** — a doubly-linked list of `epitems` that are *currently ready* (have at least one of their requested events pending). This list is what `epoll_wait` walks and copies into the user-supplied output buffer. It is the hot path.
- **`wq`** — a wait queue of threads currently blocked in `epoll_wait`. When a new FD becomes ready, the kernel wakes one (or, with `EPOLLEXCLUSIVE`, one per CPU socket) thread from this queue.

The magic that connects socket activity to `rdllist` is a **callback registered on each monitored FD's wait queue**. When you call `epoll_ctl(epfd, EPOLL_CTL_ADD, fd, &ev)`, the kernel does not just store `fd` in `rbr` — it also calls the file's `.poll` operation (e.g., `tcp_poll` for a TCP socket) to register `ep_poll_callback` as a callback on the socket's wait queue. Later, when a packet arrives and the socket transitions from "no data" to "data available" (in `tcp_rcv_established` → `__wake_up` → `ep_poll_callback`), the callback adds the corresponding `epitem` to `rdllist` and wakes the thread sleeping on `epoll_wait`. The readiness signal is *pushed* from the data path to the wait path — the kernel does not poll on `epoll_wait`; the wait is asleep until woken.

This push-based architecture is the structural difference from `select`/`poll`. In `poll`, every call walks every FD's `.poll` operation synchronously. In `epoll`, the `.poll` operation is called once at `EPOLL_CTL_ADD` time and once at each `EPOLL_CTL_MOD`; thereafter, the kernel calls back into `epoll` only when something interesting happens. The cost of monitoring 100,000 idle sockets is exactly zero CPU — they sit in the red-black tree, no callbacks fire, no scans happen. The cost of one socket becoming readable is one `ep_poll_callback` invocation, one list insertion, one thread wakeup. That is the architectural payoff.

```text
struct eventpoll (kernel, one per epoll_create1() call):

  ┌────────────────────────────────────────────────────────────────┐
  │ eventpoll                                                      │
  │                                                                │
  │   rbr  ──► Red-Black Tree of epitems (the "interest set")      │
  │            │                                                   │
  │            ├─ epitem {fd=3, events=EPOLLIN, data=ptr=0x7ff..}  │
  │            ├─ epitem {fd=5, events=EPOLLIN|EPOLLOUT, ...}      │
  │            ├─ epitem {fd=17,...}  (idle — no callback pending) │
  │            └─ epitem {fd=42,...}  (idle)                       │
  │                                                                │
  │   rdllist ──► Doubly-linked list of READY epitems              │
  │                ┌──┐    ┌──┐                                    │
  │                │fd3│◄─►│fd5│   ← ep_poll_callback inserted    │
  │                └──┘    └──┘     these when sockets became     │
  │                                   ready                        │
  │   wq ──► wait queue of threads in epoll_wait()                 │
  │           [thread A sleeping]  ← woken when rdllist non-empty  │
  └────────────────────────────────────────────────────────────────┘

  Data flow on packet arrival:
    NIC RX → softirq → tcp_v4_rcv → tcp_rcv_established
            → sock_def_readable → __wake_up_sync(sk, EPOLLIN)
            → ep_poll_callback(wq_entry)   ← O(1) list insert
            → epitem added to eventpoll.rdllist
            → wake thread in eventpoll.wq
            → epoll_wait() returns with the epitem
```

The production failure mode is subtle: an `epoll` instance itself is a file descriptor, and it is possible (and legal) to register an `epoll` FD with another `epoll` instance, nesting them. The kernel limits the nesting depth to 5 (`EP_MAX_NESTS` in `eventpoll.c`) to prevent stack overflow in the callback chain. An application that creates nested `epoll` instances in a loop will hit `EINVAL` ("epoll loop detected") — most commonly seen in test harnesses that wrap a library that already uses `epoll`. The fix is to use a single `epoll` instance per thread, which is what every sensible runtime does.

### The three `epoll` system calls: `epoll_create1()`, `epoll_ctl()` (`EPOLL_CTL_ADD`, `EPOLL_CTL_MOD`, `EPOLL_CTL_DEL`), and `epoll_wait()`.

The `epoll` API is intentionally small — three syscalls, one struct, one bitmask. The whole surface area:

```c
#include <sys/epoll.h>

int epoll_create1(int flags);
/* flags: 0 (legacy) or EPOLL_CLOEXEC (set FD_CLOEXEC on the epfd) */
/* returns: epfd ≥ 0 on success, -1 on error */
/* Old epoll_create(size) is deprecated; size is ignored since Linux 2.6.8. */

int epoll_ctl(int epfd, int op, int fd, struct epoll_event *event);
/* op: EPOLL_CTL_ADD | EPOLL_CTL_MOD | EPOLL_CTL_DEL */
/* returns: 0 on success, -1 on error (errno: EBADF, EEXIST, ENOENT, EINVAL) */

int epoll_wait(int epfd, struct epoll_event *events,
               int maxevents, int timeout);
/* timeout: -1 = block forever, 0 = poll, >0 = ms to wait */
/* returns: n ≥ 0 (number of ready events), -1 on error */

struct epoll_event {
    uint32_t      events;   /* bitmask of EPOLLIN | EPOLLOUT | EPOLLET | ... */
    epoll_data_t  data;     /* union: void *ptr | int fd | uint32_t u32 | uint64_t u64 */
} __attribute__((packed));
```

The `events` bitmask supports the readiness bits `EPOLLIN` (data available to read, including peer half-close), `EPOLLOUT` (writing would not block), `EPOLLERR` (error, always monitored even if not requested), `EPOLLHUP` (hang-up, always monitored), `EPOLLRDHUP` (peer half-closed the read side, Linux 2.6.17), `EPOLLPRI` (urgent/out-of-band data), `EPOLLNVAL` (FD not open, only ever returned — never requested). The notification-mode bits are `EPOLLET` (switch to edge-triggered — see [[02.05.04. Edge-Triggered vs. Level-Triggered Notification]]), `EPOLLONESHOT` (deliver one event then disable the FD until `EPOLL_CTL_MOD` re-arms), `EPOLLEXCLUSIVE` (wake only one thread when multiple `epoll` instances monitor the same FD — the thundering-herd mitigation, Linux 4.5+), and `EPOLLWAKEUP` (prevent system suspend while events are pending).

A complete, runnable end-to-end example — accept connections on a listening socket, read HTTP requests, write responses — using only `epoll` and non-blocking I/O:

```c
#include <sys/epoll.h>
#include <sys/socket.h>
#include <netinet/in.h>
#include <fcntl.h>
#include <unistd.h>
#include <stdio.h>
#include <errno.h>
#include <string.h>

static void set_nonblock(int fd) {
    int fl = fcntl(fd, F_GETFL, 0);
    fcntl(fd, F_SETFL, fl | O_NONBLOCK);
}

int main(void) {
    int lfd = socket(AF_INET, SOCK_STREAM, 0);
    int one = 1;
    setsockopt(lfd, SOL_SOCKET, SO_REUSEADDR, &one, sizeof(one));
    struct sockaddr_in addr = { .sin_family=AF_INET,
                                .sin_addr.s_addr=INADDR_ANY,
                                .sin_port=htons(8080) };
    bind(lfd, (struct sockaddr *)&addr, sizeof(addr));
    listen(lfd, 4096);
    set_nonblock(lfd);

    int epfd = epoll_create1(EPOLL_CLOEXEC);

    struct epoll_event ev = { .events = EPOLLIN, .data.fd = lfd };
    epoll_ctl(epfd, EPOLL_CTL_ADD, lfd, &ev);

    struct epoll_event events[1024];
    char buf[4096];
    for (;;) {
        int n = epoll_wait(epfd, events, 1024, -1);   /* block */
        for (int i = 0; i < n; i++) {
            int fd = events[i].data.fd;
            if (fd == lfd) {
                /* accept loop: drain the accept queue (level-triggered default) */
                int cfd;
                while ((cfd = accept(lfd, NULL, NULL)) >= 0) {
                    set_nonblock(cfd);
                    struct epoll_event cev = { .events = EPOLLIN, .data.fd = cfd };
                    epoll_ctl(epfd, EPOLL_CTL_ADD, cfd, &cev);
                }
                /* EAGAIN here means accept queue drained; fall through */
            } else {
                /* read what is available; partial reads are fine */
                ssize_t r = read(fd, buf, sizeof(buf));
                if (r > 0) {
                    /* ...parse the request, generate response... */
                    const char *resp = "HTTP/1.1 200 OK\r\nContent-Length: 2\r\n\r\nhi";
                    write(fd, resp, strlen(resp));
                } else if (r == 0 || (r < 0 && errno != EAGAIN)) {
                    /* peer closed or error: tear down */
                    epoll_ctl(epfd, EPOLL_CTL_DEL, fd, NULL);
                    close(fd);
                }
            }
        }
    }
}
```

Three subtleties in this example deserve explanation. First, the `accept` loop is critical under level-triggered mode: when multiple connections arrive between `epoll_wait` calls, only one `EPOLLIN` event is delivered for the listening socket, but the accept queue may hold dozens of pending connections — you must loop `accept()` until it returns EAGAIN to drain them all. Second, the read also handles partial data: a single `epoll_wait` wakeup does not mean a full request is available, so the application must buffer until it sees the request terminator (`\r\n\r\n` for HTTP/1.1). Third, `EPOLL_CTL_DEL` is necessary before `close()` — if you close an FD that is still registered, the kernel auto-removes it (since Linux 2.6.9), but if a new connection later gets the same FD number, you may briefly see stale events. Always `EPOLL_CTL_DEL` before `close` in production code.

The production failure mode is the missing `EPOLL_CTL_MOD` after a write that did not drain the send buffer. If the application writes more than fits in the kernel's send buffer, `write()` returns a short count and the application must buffer the rest and wait for `EPOLLOUT`. The mistake is to register only for `EPOLLIN`, write until EAGAIN, and forget to call `epoll_ctl(EPOLL_CTL_MOD, fd, EPOLLIN|EPOLLOUT)` to add write-readiness to the interest set. The buffered bytes then sit forever — the kernel never tells the application that the send buffer has drained, because the application never asked to be told. The diagnostic is `ss -tin` showing a high `Send-Q` on a long-lived connection. The fix is to track per-FD pending-write state and toggle `EPOLLOUT` on and off as buffers fill and drain.

### Algorithmic complexity: Achieving true O(1) event readiness notifications

The complexity claim for `epoll` is `O(1)` per ready event — meaning the cost of `epoll_wait` returning N ready events is `O(N)`, not `O(M)` where M is the size of the interest set. This is structurally different from `select`/`poll`, which are `O(M)` per call regardless of how many events are returned. The complexity story has three parts:

**Registration is `O(log M)`.** `epoll_ctl(ADD)` inserts an `epitem` into the red-black tree keyed by FD number. A red-black tree insertion is `O(log M)` — about 17 comparisons for M = 100,000. This is paid once per connection's lifetime, so even at 100,000 connections/s connection rate it is 1.7M comparisons/s, well under 1% of one core. `epoll_ctl(MOD)` is the same — find the node (`O(log M)`) and update its event mask. `epoll_ctl(DEL)` is also `O(log M)` to find the node, plus `O(1)` to remove it from the tree and from `rdllist` if present. None of these are hot-path operations.

**Wait is `O(N)` where N is the ready count.** `epoll_wait` walks `rdllist` — the ready list, not the interest set — copies the first `maxevents` `epitems` into the user-supplied buffer, removes them from `rdllist`, and returns. If `rdllist` is empty and the timeout is non-zero, the thread sleeps on `eventpoll.wq` until either `ep_poll_callback` adds something to `rdllist` and wakes it, or the timeout fires. The walk is `O(N)`, the copy is `O(N)`, the wakeup mechanism is `O(1)`. If no FDs are ready, the call returns 0 after the timeout with zero work done — no scan of the interest set, no memory copy. This is the property that makes 100,000 idle connections free.

**Callback is `O(1)`.** When a socket becomes ready, `ep_poll_callback` runs in the softirq context of the packet receive path. It does an `O(1)` list insertion into `rdllist` and an `O(1)` wakeup of one thread on `eventpoll.wq`. The callback does not scan the interest set, does not look at any other FD. This is the property that makes one ready FD not affect any other monitored FD.

```text
Complexity comparison at M=100,000 monitored FDs, N=10 ready per call:

  Operation            select       poll         epoll
  ─────────────────────────────────────────────────────────
  Register FD          N/A (rebuild bitmap every call)    O(log M) ≈ 17 ops
  Modify interest      N/A                              O(log M) ≈ 17 ops
  Remove FD            N/A                              O(log M) ≈ 17 ops
  Wait (M idle)        O(M) = 100,000 scans + 12 KB copy  O(0) (sleeps)
  Wait (N ready)       O(M) = 100,000 scans + 12 KB copy  O(N) = 10 list walks + 240 B copy
  Per-ready-FD cost    O(M/N) = 10,000 ops                O(1) = 1 list walk + 24 B

  Memory footprint     3 × 12.5 KB bitmaps               ~80 B per epitem in rbr
                                                         + 24 B per ready event in buf
```

The production failure mode is the misdiagnosis: an operator sees `epoll_wait` taking 5 ms in `perf` and concludes "epoll is slow." It is not — `epoll_wait` taking 5 ms means the kernel returned 5,000 ready events in one call (because `maxevents` was set to 8192 and 5,000 sockets became ready simultaneously, which happens during a thundering-herd accept storm or a fan-out broadcast). The fix is not to tune `epoll`; it is to investigate *why* 5,000 sockets went ready at once. The diagnostic is to plot `epoll_wait` return-value distribution — a healthy server shows a long tail of `n=1` and occasional `n=10–50`; an `n=5000` spike is a fan-out event somewhere upstream.

### BSD / macOS `kqueue` and `kevent`: Filter-based event monitoring for sockets, files, and signals

`kqueue` (FreeBSD 4.1, 2000; macOS since 10.3 Panther, 2003) is the BSD answer to `epoll`. The design predates `epoll` by two years and is in several ways more general. Instead of an "events" bitmask restricted to socket readiness, `kqueue` is built around **filters** — a `kqueue` monitors a `(identifier, filter)` pair, where the identifier is typically an FD and the filter is one of a fixed list of kernel-defined event types. The filter model means `kqueue` can monitor things `epoll` cannot:

| Filter | Monitors | epoll equivalent |
|---|---|---|
| `EVFILT_READ` | Socket / pipe / file readability | `EPOLLIN` |
| `EVFILT_WRITE` | Socket / pipe writability | `EPOLLOUT` |
| `EVFILT_AIO` | POSIX AIO completion | (none — Linux uses `io_uring`) |
| `EVFILT_VNODE` | Filesystem events (open, write, delete, rename, attrib change) | `inotify` (separate API) |
| `EVFILT_PROC` | Child process exit/fork/exec | `waitid()` / `pidfd_open()` (Linux 5.3+) |
| `EVFILT_SIGNAL` | Signal delivery (counts undelivered signals) | `signalfd` (Linux 2.6.22) |
| `EVFILT_TIMER` | Kernel-managed timer (no `timerfd` needed) | `timerfd_create` (Linux 2.6.25) |
| `EVFILT_USER` | User-level trigger (fast IPC between threads) | `eventfd` (Linux 2.6.22) |
| `EVFILT_EXCEPT` | Out-of-band data, exception state | `EPOLLPRI` (limited) |

The API is two syscalls: `kqueue()` creates a new kqueue FD (analogous to `epoll_create1`), and `kevent(kq, changelist, nchanges, eventlist, nevents, timeout)` is a combined register-and-wait call — it applies every entry in `changelist` (which can be a mix of `EV_ADD`, `EV_DELETE`, `EV_ENABLE`, `EV_DISABLE`) and then blocks waiting for up to `nevents` ready events to be returned in `eventlist`. The combined register-and-wait is one syscall where `epoll` would need two (`epoll_ctl` + `epoll_wait`), which is a small but real win under heavy churn.

```c
#include <sys/event.h>
#include <sys/socket.h>

int main(void) {
    int kq = kqueue();
    int lfd = /* ...listening socket, non-blocking... */;

    /* Register the listening socket for EVFILT_READ.
     * EV_CLEAR is the kqueue equivalent of EPOLLET (edge-triggered). */
    struct kevent change;
    EV_SET(&change, lfd, EVFILT_READ, EV_ADD | EV_CLEAR, 0, 0, NULL);
    kevent(kq, &change, 1, NULL, 0, NULL);

    struct kevent events[1024];
    for (;;) {
        int n = kevent(kq, NULL, 0, events, 1024, NULL);   /* block */
        for (int i = 0; i < n; i++) {
            int fd = (int)events[i].ident;
            if (events[i].filter == EVFILT_READ) {
                if (fd == lfd) {
                    int cfd;
                    while ((cfd = accept(lfd, NULL, NULL)) >= 0) {
                        fcntl(cfd, F_SETFL, O_NONBLOCK);
                        struct kevent c[1];
                        EV_SET(&c[0], cfd, EVFILT_READ,
                               EV_ADD | EV_CLEAR, 0, 0, NULL);
                        kevent(kq, c, 1, NULL, 0, NULL);
                    }
                } else {
                    char buf[4096];
                    ssize_t r = read(fd, buf, sizeof(buf));
                    /* ...handle read... */
                }
            }
        }
    }
}
```

The `EV_SET` macro takes a `struct kevent *` and the fields `(ident, filter, flags, fflags, data, udata)`. The `data` field on return carries useful per-event metadata: for `EVFILT_READ` it is the number of bytes available to read (so you can size your `read()` buffer exactly); for `EVFILT_WRITE` it is the space available in the send buffer; for `EVFILT_TIMER` it is the number of times the timer has fired since the last `kevent` returned. `epoll` does not provide this — you must call `recv()`/`ioctl(FIONREAD)` separately to find the byte count, which is one extra syscall per event.

The richness of `kqueue` is also its complexity. `EVFILT_VNODE` requires an open FD on the file you want to watch (and consumes an FD per watched file), where `inotify` uses a single watch FD for many files. `EVFILT_PROC` requires the parent process to have the child's PID; `pidfd_open` is similar but newer. The cross-platform story is: `kqueue` is available on FreeBSD, OpenBSD, NetBSD, macOS, and (with caveats) DragonFly BSD. It is **not** on Linux. The reverse is true for `epoll`: Linux only, not on BSD/macOS. Every cross-platform event loop — libuv, libevent, `mio` (Rust), Python's `selectors`, Java NIO — picks one at compile time based on the host OS.

The production failure mode is macOS-specific. macOS's `kqueue` implementation has historically had performance issues that Linux's `epoll` does not: high CPU usage on `kevent` with large interest sets (the internal data structure was a hash table, not a red-black tree, until recent macOS releases), and incorrect `EVFILT_VNODE` event delivery on network filesystems (NFS, SMB). A developer who benchmarks on macOS and deploys on Linux may see a 3–5× event-loop performance improvement that is purely the kernel primitive difference, not the application. The reverse — developing on Linux and deploying on macOS Server (rare, but it happens for some CI/CD appliances) — shows the same effect in the other direction. Always benchmark on the deployment OS. See [[02.05.04. Edge-Triggered vs. Level-Triggered Notification]] for the `EV_CLEAR`/`EPOLLET` semantics comparison.

## How This Connects to the Runtimes

Every runtime in section 04 wraps one of these two APIs behind a higher-level abstraction:

- **Node.js / libuv**: `uv_loop_t` holds an `epoll` FD on Linux, a `kqueue` FD on BSD/macOS, an IOCP handle on Windows. The libuv `uv_poll_t` API is the thinnest wrapper; `uv_tcp_t`, `uv_udp_t`, `uv_timer_t`, `uv_signal_t` are built on top of `uv_poll_t`. libuv was the first widely-deployed runtime to use `kqueue` on macOS and `epoll` on Linux from a single codebase.
- **Java NIO**: `java.nio.channels.Selector.open()` returns an `EPollSelectorProvider` on Linux (default since JDK 1.5), a `KqueueSelectorProvider` on macOS, a `PollSelectorProvider` on ancient systems. Netty's `NioEventLoop` wraps `Selector`; `EpollEventLoop` and `KQueueEventLoop` are native alternatives that expose `epoll`/`kqueue`-specific features (`TCP_CORK`, `TCP_FASTOPEN`, `SO_REUSEPORT`) that the JDK abstraction hides.
- **Python asyncio**: `selectors.DefaultSelector` returns `EpollSelector` on Linux, `KqueueSelector` on BSD/macOS. Python's `loop.add_reader(fd, callback)` is a thin wrapper over `selector.register(fd, EVENT_READ, callback)`.
- **Rust `mio`**: `Poll::new()` returns a `Selector` backed by `epoll`/`kqueue`/IOCP. `mio` exposes the API as a single `Registry::register(&token, interest)` interface; the `token` is what makes Rust's async model safe — every event carries the user's `Token`, never a raw FD.
- **Go runtime**: Uses a network poller (`runtime/netpoll_epoll.go` on Linux, `runtime/netpoll_kqueue.go` on BSD/macOS) to wake goroutines blocked on `net.Conn.Read()`. The poller runs in its own thread and dispatches ready events via `runtime.netpollready()`; goroutines themselves never touch `epoll_wait` directly.

When you read those runtime notes, come back here and trace which syscall each runtime feature maps to. The runtime's "async" abstraction is, at the bottom, `epoll_wait` or `kevent`.

## Hands-On Exercise

```bash
# Confirm your kernel exposes epoll
grep Epoll /proc/self/status 2>/dev/null || uname -r   # 2.6+ has epoll

# Watch Node's epoll usage live
strace -f -e trace=epoll_create1,epoll_ctl,epoll_wait \
    node -e 'require("http").createServer((q,s)=>s.end("ok")).listen(9000)' \
    2>&1 | head -20
# Expect: epoll_create1(EPOLL_CLOEXEC) → epoll_ctl(EPOLL_CTL_ADD, listen_fd, EPOLLIN)
#         → epoll_wait(...) blocking
# Then in another terminal:
curl http://127.0.0.1:9000/
# Expect: epoll_wait returns, accept/read/write fire, epoll_wait re-enters

# Inspect the red-black tree of a process's epoll instance
# (requires CONFIG_EPOLL_DEBUG or a kernel module — usually not available)
# Easier: use perf to count epoll activity
perf stat -e 'syscalls:sys_enter_epoll_*' -p <pid> -- sleep 5

# Compare with Java NIO using epoll directly:
strace -f -e trace=epoll_create1,epoll_ctl,epoll_wait \
    java --add-opens java.base/sun.nio.ch=ALL-UNNAMED \
    -e 'var s=java.nio.channels.Selector.open();' 2>&1 | head -10

# Verify kqueue on macOS:
sudo dtruss -f -t kqueue,kevent node -e 'require("net").createServer().listen(9000)' 2>&1 | head -10
```
