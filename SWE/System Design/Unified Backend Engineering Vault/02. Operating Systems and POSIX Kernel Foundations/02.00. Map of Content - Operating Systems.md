# 02.00. Map of Content: Operating Systems

## Overview

This section covers **02. Operating Systems and POSIX Kernel Foundations**. It is the bedrock on which every runtime in section 04 (the JVM, V8, CPython, the Zend Engine) and every framework in section 05 (Spring Boot, Express, Django, Flask, Laravel) stands. The vault's thesis is that backend engineering is one discipline expressed in different syntaxes — and the syntax that matters most is the POSIX kernel ABI: the system calls, the file descriptor table, the page table, the socket buffer, the event queue. Every higher-level abstraction — Java's NIO `Selector`, Node's libuv event loop, Python's `asyncio` selector, PHP's `stream_select` — is a thin wrapper around these primitives, and every production outage you will ever debug (FD exhaustion, GC stalls, request timeouts, OOM kills, accept-queue drops) ultimately reduces to one of the mechanisms taught here.

The notes are organized in five sub-sections that move from the CPU outward: processes and threads (the schedulable unit), virtual memory (the addressable unit), file descriptors (the I/O handle), sockets (the network I/O handle), and event multiplexing (the technique that lets one thread drive ten thousand of those handles). Each sub-section is taught once, at the conceptual level, in this section; the runtime-specific mappings are taught in section 04 and the framework-specific mappings in section 05.

## Section Map

### 02.01. Processes Threads and CPU Scheduling

- [[02.01.01. The Linux Process Model]] — Walks through the `task_struct`, the `fork()` + `execve()` two-step process creation dance, the five process states (`R`/`S`/`D`/`T`/`Z`), zombie reaping with `waitpid()`, PID namespaces, and why every container needs a PID-1 init like `tini` to reap orphaned children. The foundation for understanding JVM process layout, PHP-FPM worker pools, and Python `multiprocessing`.
- [[02.01.02. Kernel Threads vs. User Threads]] — The 1:1 threading model (Linux NPTL via `clone()`), the historical N:1 green-threads model, and the modern M:N schedulers (Go goroutines, Java virtual threads via Project Loom, Erlang processes). Compares real pthread, Go, and Java virtual-thread code side by side and shows why the 8 MB default stack makes million-thread OS concurrency impossible.
- [[02.01.03. CPU Scheduling and Context Switching Mechanics]] — The Completely Fair Scheduler's red-black tree of `vruntime`, niceness weighting, the anatomy of a context switch (register save/restore, `CR3` swap, TLB flush, L1/L2 cache pollution), and CPU pinning via `sched_setaffinity` for database workloads. Explains why event loops beat thread-per-connection at scale.

### 02.02. Virtual Memory Allocation and Management

- [[02.02.01. Virtual Address Spaces and Page Translation]] — The 48-bit virtual address space, the four-level page table (PGD → PUD → PMD → PTE), the TLB cache, huge pages, minor vs. major page faults, and `mmap` semantics including copy-on-write. The substrate that every GC algorithm and every runtime heap is built on.
- [[02.02.02. Process Memory Layout Internals]] — The text/`.data`/`.bss`/heap/mmap/stack segment breakdown, ASLR randomization, and the concrete layouts of a JVM process (JVM heap vs. Java heap vs. metaspace vs. thread stacks) and a Node.js process (V8 heap vs. native heap vs. libuv thread-pool stacks). Explains why `/proc/<pid>/maps` is the first thing to read on a memory leak.
- [[02.02.03. Dynamic Memory Allocation and Fragmentation]] — `malloc`/`free` internals, the `brk`/`sbrk` vs. `mmap` threshold (default 128 KB), the arena model in `ptmalloc`/`jemalloc`/`tcmalloc`, internal vs. external fragmentation, and why JVM and Node both bypass glibc malloc entirely. Includes OOM-killer heuristics and `oom_score_adj` tuning.

### 02.03. File Descriptors and POSIX File IO

- [[02.03.01. The File Descriptor Abstraction]] — The three-level kernel lookup (process FD table → system-wide open file table → VFS inode table), the everything-is-a-file philosophy, `dup`/`dup2`/`fcntl`, `O_CLOEXEC`, and the canonical special files `/dev/null`, `/dev/urandom`, `/proc/self/fd`. The single most important abstraction in POSIX — every socket, pipe, and device is an integer.
- [[02.03.02. Synchronous File IO System Calls]] — `open`/`read`/`write`/`pwrite`/`fsync`/`fdatasync`, the page cache, `O_DIRECT` vs. `O_SYNC`, and why PostgreSQL uses `O_DIRECT` on `shared_buffers` while still `fsync`-ing the WAL on every commit. Shows the durability hierarchy: a successful `write` is not durable; only `fsync` is.
- [[02.03.03. System Resource Limits and File Descriptor Leaks]] — `ulimit -n`, `RLIMIT_NOFILE`/`RLIMIT_NPROC`/`RLIMIT_MEMLOCK`, the `fs.file-max` sysctl, the `EMFILE` ("Too many open files") failure mode, the systemd `LimitNOFILE=` directive, and why load balancers and databases always blow past the 1024 default. Includes the `lsof` and `/proc/<pid>/fd` inspection workflow.

### 02.04. POSIX Sockets and Network IPC

- [[02.04.01. Inter-Process Communication Mechanics]] — Anonymous pipes (`pipe()`), named pipes/FIFOs (`mkfifo()`), System V and POSIX shared memory (`shmget`/`shmat`/`shm_open`), message queues, and semaphores. Shows real `pipe()` + `fork()` code and explains why shared memory is the fastest IPC (zero copy) but the most dangerous (no synchronization primitives baked in).
- [[02.04.02. UNIX Domain Sockets vs. Network Sockets]] — `AF_UNIX` vs. `AF_INET`, the `sockaddr_un` struct, the on-disk socket file, why PostgreSQL and Redis default to UNIX sockets for localhost, and the `SCM_RIGHTS` file-descriptor passing mechanism that Docker and systemd use to hand FDs between processes.
- [[02.04.03. The POSIX Socket Lifecycle]] — The full `socket()` → `bind()` → `listen()` → `accept()` → `recv()`/`send()` → `close()` server-side dance with real C code. Covers `SO_REUSEADDR`, `SO_KEEPALIVE`, `TCP_NODELAY`, the SYN queue vs. accept queue, and `htons`/`htonl` byte-order conversion.
- [[02.04.04. Kernel Socket Buffers and Socket Tuning]] — The `rmem_default`/`rmem_max`/`wmem_default`/`wmem_max` sysctls, the `tcp_rmem`/`tcp_wmem` triples, `SO_RCVBUF`/`SO_SNDBUF`, the TCP sliding window, buffer bloat, and the exact Nginx tuning block that production deployments copy. Explains how backpressure propagates from a slow reader to a fast writer through a full receive buffer.

### 02.05. IO Multiplexing and Event Demultiplexing

- [[02.05.01. The Concurrency Scaling Problem in IO]] — The C10K problem (Dan Kegel, 1999), the failure mode of thread-per-connection at 10,000 concurrent sockets (80 GB of stack address space), and the Reactor and Proactor architectural patterns that emerged as responses. The note that motivates the entire sub-section.
- [[02.05.02. Legacy Multiplexing Systems select and poll]] — The `FD_SET` bitmap, the `FD_SETSIZE` 1024-fd limit in `select`, the `pollfd` array that removes the limit but keeps the O(N) kernel scan, and the per-call user/kernel memory copy. Shows real `select()` C code and explains why neither scales past a few thousand connections.
- [[02.05.03. Modern IO Multiplexing epoll and kqueue]] — `epoll_create1`/`epoll_ctl`/`epoll_wait` on Linux, the red-black tree interest set plus the ready-list doubly-linked list, O(1) per ready FD, and the BSD/macOS `kqueue` + `kevent` filter-based equivalent. Shows real epoll and kqueue C code side by side. This is the kernel primitive behind every modern event loop.
- [[02.05.04. Edge-Triggered vs. Level-Triggered Notification]] — `EPOLLET` semantics, why edge-triggered requires non-blocking IO and a drain-to-`EAGAIN` loop, the thundering-herd problem, and the classic production bug where a half-read socket silently stalls. The single most footgun-prone topic in high-performance IO.
- [[02.05.05. High-Performance Event Architecture Patterns]] — The single-loop single-thread pattern (Redis, Node), the master-worker pattern (Nginx, PHP-FPM), the thread-per-core / shared-nothing pattern (ScyllaDB, Seastar), the actor model (Erlang/OTP, Akka), and the new `io_uring` shared-ring-buffer architecture. Compares throughput, latency-tail, and operational complexity across all four patterns.

## Conceptual Roadmap

Section 02 is not a flat list — it is a layered stack where each sub-section builds on the one before it. Read it in order, because the later notes assume the earlier primitives.

```text

└────────────┬────────────────────────────────────┬───────────────┘

             ▼                                     ▼
┌────────────────────────┐         ┌──────────────────────────────┐
│ 02.04 Sockets & IPC    │◄────────│ 02.03 File Descriptors       │

└───────────┬────────────┘         └───────────────┬──────────────┘
            │ runs in                            │ backed by
            ▼                                    ▼
┌─────────────────────────────────────────────────────────────────┐

└───────────────────────────────┬─────────────────────────────────┘

                                ▼
┌─────────────────────────────────────────────────────────────────┐
│ 02.02 Virtual Memory (4-level page table, TLB, mmap, malloc, OOM)│
└─────────────────────────────────────────────────────────────────┘
```

The mental model is: **a process (02.01) owns a virtual address space (02.02) and a file descriptor table (02.03); file descriptors index into sockets (02.04); a single thread can wait on many sockets at once via multiplexing (02.05).** Every runtime in section 04 is a user-space wrapper around this stack — the JVM wraps the thread primitive, V8 wraps the event-loop primitive, CPython wraps the GIL-on-top-of-NPTL primitive — and every framework in section 05 is a user-space wrapper around a runtime. When you debug a production issue, you drill down through the same layers: framework → runtime → OS primitive. This section is the bottom of that drill.

The other axis is **synchronous vs. asynchronous**: 02.03 and 02.04 teach the synchronous system calls (`read`, `write`, `recv`, `send`) that block the calling thread; 02.05 teaches the multiplexing primitives (`select`, `poll`, `epoll`, `kqueue`, `io_uring`) that let one thread drive thousands of those synchronous handles without blocking. The transition from "one thread per connection" (02.01) to "one thread per core driving many connections" (02.05) is the single most important architectural shift in modern backend engineering, and it is the conceptual hinge of this section.

## How to Read This Section

1. **Read the concept notes first.** They establish the mental model. Each concept note is self-contained — you can read 02.02.01 (page tables) without having read 02.01.01 (process model), but the cross-references will make more sense if you follow the numeric ordering.
2. **Run the hands-on commands.** Every concept note ends with a `## Hands-On Exercise` section containing real `ps`, `cat /proc/<pid>/...`, `strace`, `ss`, and `perf` commands. Run them on a Linux box — the muscle memory of seeing `/proc/<pid>/maps` output is what makes the abstraction real.
3. **Connect to the runtimes.** When you finish a sub-section, jump to the corresponding runtime note in section 04 and trace how the runtime wraps the kernel primitive. For example, after 02.05.03 (epoll), read the libuv event-loop note and confirm that `uv_run` is a `epoll_wait` wrapper.
4. **Connect to the frameworks.** When you reach section 05, every framework's request-handling model should now be transparent: Spring Boot's thread-per-request maps to 02.01 (NPTL threads), Express's single event loop maps to 02.05 (epoll), PHP-FPM's process pool maps to 02.01 (fork + accept).

> [!tip] Reading order
> If you are new to this section, follow the numeric ordering — the notes are sequenced so that each one references only primitives already introduced. If you are revising, jump directly to whichever concept you forgot; the H3 sub-headings under `## The Details` are the index.
