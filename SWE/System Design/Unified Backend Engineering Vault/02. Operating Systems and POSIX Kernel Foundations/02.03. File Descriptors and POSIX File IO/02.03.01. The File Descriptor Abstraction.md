# 02.03.01. The File Descriptor Abstraction

## What This Is

**The File Descriptor Abstraction** is the single most important unifying concept in POSIX — the principle that "everything is a file" is implemented as "everything is referenced by a small non-negative integer that supports `read`, `write`, `close`, and `poll`." A regular file on disk is an integer. A network socket is an integer. A pipe is an integer. A terminal is an integer. A block device is an integer. A `timerfd` is an integer. A `signalfd` is an integer. An `eventfd` is an integer. The kernel's VFS (Virtual File System) layer routes every syscall on these integers through a per-file-type `file_operations` struct, so the same `read(7, buf, 4096)` call works whether FD 7 is a disk file, a TCP socket, or a character device. The reason this note sits in section 02 is that every runtime in section 04 and every framework in section 05 is built on this abstraction: Java's `InputStream` wraps an FD, Node's `fs.createReadStream` wraps an FD, Python's `socket.socket.fileno()` returns the underlying FD, PHP's `stream_get_meta_data` reports the FD — every runtime's I/O API is a layer of sugar on top of integer file descriptors and the `read`/`write`/`poll`/`close` syscalls.

The mental model has three levels of indirection that you must internalize. A file descriptor (an integer in user-space) is an index into a per-process table; that table points to a system-wide table of open file descriptions (which hold the file offset and status flags); that table points to the inode (or socket, or device) that backs the file. The three-level indirection is what makes `dup`, `fork`, and `pipe` work: it allows multiple FDs (and multiple processes) to share a single underlying file description (and thus a shared offset), while still tracking per-FD flags like `O_CLOEXEC` and `O_NONBLOCK`. Understanding these three tables is what lets you read `lsof` output, understand why shell pipes work, and debug the inevitable `EMFILE` (too many open files) production incident.

## The Details

### The UNIX Philosophy: "Everything is a stream of bytes exposed via an integer index."

The Unix philosophy (originated by Ken Thompson and Dennis Ritchie at Bell Labs in the late 1960s, codified by Doug McIlroy in 1978) holds that the operating system should expose its resources through a small, uniform set of primitives. The single most important of these is the **file**: a sequence of bytes that supports `open`, `read`, `write`, `seek`, and `close`. By making every resource look like a file — a disk file, a terminal, a printer, a network socket, a kernel counter — Unix made it possible to compose programs in ways the original designers did not anticipate. The shell pipe `ls | grep foo | wc -l` works only because `ls` writes bytes to FD 1, `grep` reads bytes from FD 0 and writes bytes to FD 1, and `wc` reads bytes from FD 0 — none of them knows or cares that the bytes are flowing through a kernel pipe rather than a file. The abstraction is the protocol.

The "integer index" part is the implementation trick. A file descriptor is just a non-negative integer — typically 0, 1, 2, 3, ..., up to the per-process limit (`ulimit -n`, default 1024 on most distros). The integer is an index into the process's private file descriptor table, an array of pointers to `struct file` objects in the kernel. When you call `read(7, buf, 4096)`, the kernel looks up `current->files->fdt[7]`, gets the `struct file*`, follows its `f_op` (file operations) pointer to a `file_operations` struct, and calls `f_op->read(file, buf, 4096, &file->f_pos)`. For a regular file, that function is `generic_file_read`; for a socket, it is `sock_read_iter`; for a pipe, it is `pipe_read`; for `/dev/null`, it returns 0 immediately; for `/dev/urandom`, it calls the kernel's CSPRNG. The caller sees only `read(7, ...)` returning some bytes — the dispatch is invisible.

The reason this matters for backend engineering is that every I/O library in every language is built on this dispatch. Java's `FileInputStream.read()` ultimately calls the `read` syscall on an FD; Node's `fs.readFile()` ultimately calls the `read` syscall on an FD (via libuv's thread pool, because `read` on a regular file blocks); Python's `socket.recv()` calls the `recv` (or `read`) syscall on an FD; PHP's `fread()` calls `read` on an FD. The runtime wraps the syscall in a friendlier API and adds buffering, type safety, and error handling, but the underlying primitive is the same FD integer. When you debug an "EMFILE: too many open files" error in Node, you are debugging the same kernel limit a C programmer would debug; when you tune `ulimit -n` for a Java server, you are tuning the same kernel limit. The abstraction is the contract.

The connection to the upper layers is the design lesson: every runtime's I/O library is a wrapper around the same handful of FD syscalls. Java's NIO `Channel` is a thin wrapper around FD + non-blocking mode. Node's libuv `uv_stream_t` is a thin wrapper around FD + epoll. Python's `io.BufferedReader` is a thin wrapper around FD + a userspace buffer. The runtime adds value via type safety, buffering, async semantics, and ergonomics, but it does not change the fundamental operations. When a runtime advertises "non-blocking I/O" it means "we set `O_NONBLOCK` on the FD and use `epoll` to know when to retry"; when it advertises "buffered I/O" it means "we read a large chunk into userspace and hand it back in small pieces." The FD is the primitive; the runtime is policy.

### Three-level kernel lookup structure: Process File Descriptor Table → System-Wide Open File Table → VFS Inode Table

The file descriptor abstraction is implemented in the kernel as three levels of indirection, each with a different lifetime and scope. The first level is the **per-process file descriptor table** (`struct files_struct` in `include/linux/fdtable.h`), an array of `struct file*` pointers indexed by the FD integer. Every process has its own table; the table is duplicated on `fork()` (via `dup_fd`) and reset on `execve()` (FDs without `FD_CLOEXEC` survive). The second level is the **system-wide open file table** — a slab-allocated pool of `struct file` objects, each representing one "open file description" (a position-independent handle with a file offset, status flags, and a reference count). Multiple FDs in the same or different processes can point to the same `struct file` (via `dup`, `dup2`, `fork`, or `SCM_RIGHTS` FD-passing). The third level is the **VFS inode table** (`struct inode`), which represents the actual on-disk file (or socket, or device) — there is exactly one inode per file, shared by every `struct file` that points to it.

The reason for the three-level indirection is that file offset must be shared by `dup` and `fork` but not by independent `open`s of the same file. When you `open("/etc/passwd")` twice, you get two FDs with two independent file offsets — reading from one does not affect the other. The kernel achieves this by allocating two separate `struct file` objects, each with its own `f_pos` field, both pointing to the same inode. When you `dup(fd)` or `fork()`, the kernel does NOT allocate a new `struct file` — it just adds a new entry to the FD table pointing to the existing `struct file`, and increments the `struct file`'s reference count. The two FDs now share the offset: a `read` from one advances the offset for both. This is how shell append redirection `>> file` works across forked children, and how a parent and child can both write to the same log file in append mode without overwriting each other.

The `struct file` carries the file offset (`f_pos`), the open flags (`f_flags`, including `O_NONBLOCK`, `O_APPEND`, `O_DIRECT`), the file mode (`f_mode`, read/write permissions), the pointer to the `dentry` (directory entry, which points to the `inode`), the pointer to the `file_operations` struct (the dispatch table), and the owner's credentials (`f_cred`). The `f_pos` is what makes sequential reads work — every `read(fd, buf, n)` advances `f_pos` by the number of bytes returned, so the next `read` starts where the previous one left off. `lseek(fd, offset, whence)` lets you change `f_pos` explicitly: `SEEK_SET` sets it to an absolute offset, `SEEK_CUR` adjusts it relative to the current position, `SEEK_END` sets it relative to the file's end. Sockets and pipes do not support `lseek` (they are not seekable) — `lseek` on a socket returns `ESPIPE` ("Illegal seek").

The connection to the upper layers is the production-debugging story. When a backend service "leaks FDs" (the most common production incident after memory leaks), the diagnostic is always: `ls /proc/<pid>/fd | wc -l` to see the count, then `ls -la /proc/<pid>/fd` to see what they are. If you see 10,000 sockets to the same Postgres port, you have a connection-pool leak. If you see 10,000 pipes, you have a subprocess-spawning leak. If you see 10,000 anonymous `[eventpoll]` or `[timerfd]` entries, you have an event-loop leak. Every runtime in section 04 exposes this same kernel state through its own idioms — `jcmd <pid> Thread.print` for the JVM, `process._getActiveHandles()` for Node, `gc.get_objects()` for CPython — but the underlying state is the kernel's `files_struct`. Learning to read `/proc/<pid>/fd` is the single most useful skill for FD-leak debugging.

### Standard streams: Standard Input (0), Standard Output (1), Standard Error (2)

Every process begins life with three file descriptors already open: FD 0 (standard input, `stdin`), FD 1 (standard output, `stdout`), and FD 2 (standard error, `stderr`). These are inherited from the parent process — when a shell runs a command, it forks itself, then in the child uses `dup2` to point FD 0/1/2 at the appropriate target (the terminal, a pipe, a file, `/dev/null`), then `execve`s the command. The command starts up with its three standard streams already wired up; it does not have to open them. By convention, programs read input from FD 0, write normal output to FD 1, and write diagnostics to FD 2. This convention is so universal that the C library exposes the three streams as `stdin`, `stdout`, and `stderr` (`FILE*` pointers wrapping the underlying FDs), and every language's standard library does the same.

The reason `stderr` (FD 2) is separate from `stdout` (FD 1) is that they can be redirected independently. The shell's `>` operator redirects only FD 1; the `2>` operator redirects only FD 2; the `2>&1` operator duplicates FD 2 to point at whatever FD 1 points to. This is why `./my_app > output.log 2> error.log` splits the two streams into separate files, and why `./my_app 2>&1 | grep ERROR` lets you filter diagnostics through a pipe while keeping stdout on the terminal. The Unix convention that diagnostics go to stderr (not stdout) is what makes this work — if your program writes errors to stdout, they get mixed with the real output, and you cannot filter or redirect them independently. Java's `System.err`, Python's `sys.stderr`, Node's `process.stderr`, PHP's `fwrite(STDERR, ...)` — every runtime preserves this distinction because the kernel preserves it.

The standard streams are inherited across `fork()` and `execve()`. When a shell runs `bash -c 'echo hello'`, the chain is: shell forks → child inherits FD 0/1/2 from the parent (pointing at the terminal) → child calls `execve("/bin/bash", ["-c", "echo hello"], envp)` → the new bash process starts with FD 0/1/2 still pointing at the terminal → bash forks again for `echo` → the echo grandchild inherits FD 0/1/2 from bash → echo writes "hello\n" to FD 1 → echo exits → bash's `waitpid` returns → bash exits. The FDs were never closed or re-opened; they were inherited through the chain. This is also why `nohup ./my_app &` works: `nohup` redirects FD 0 from `/dev/null`, FD 1 to `nohup.out`, and FD 2 to follow FD 1, then `exec`s the command — so when the shell exits and sends `SIGHUP` to the process group, the command ignores it (because `nohup` set `signal(SIGHUP, SIG_IGN)`) and keeps writing to its inherited FDs.

```c
#include <stdio.h>
#include <unistd.h>

int main(void) {
    /* Three equivalent ways to write to stdout: */
    printf("via printf\n");              /* C stdio, buffered, FD 1 */
    fputs("via fputs\n", stdout);        /* C stdio, FD 1 */
    write(1, "via write\n", 11);         /* POSIX syscall, FD 1, unbuffered */

    /* Three equivalent ways to write to stderr: */
    fprintf(stderr, "via fprintf\n");    /* C stdio, FD 2 */
    fputs("via fputs\n", stderr);        /* C stdio, FD 2 */
    write(2, "via write\n", 11);         /* POSIX syscall, FD 2, unbuffered */

    /* The FDs are just integers: */
    fprintf(stderr, "stdout is FD %d, stderr is FD %d\n",
            fileno(stdout), fileno(stderr));
    /* Output: "stdout is FD 1, stderr is FD 2" */

    return 0;
}
```

The connection to the upper layers is the production-logging story. Every backend service writes logs to stdout (FD 1) or stderr (FD 2) so that the container runtime (Docker, Kubernetes) can capture them. The 12-factor app methodology (factor 11: "Treat logs as event streams") is built on this convention — applications should not manage log files, they should write to stdout/stderr and let the platform route the streams to a log aggregator. When a Java app uses `System.out.println`, when a Node app uses `console.log`, when a Python app uses `print()`, when a PHP app uses `echo`, they are all writing to FD 1. The runtime adds buffering (Java's `System.out` is line-buffered to a tty, block-buffered to a pipe — the same C library rule), but the underlying destination is the kernel FD. When you debug "my logs are not showing up in Kibana," the first thing to check is whether the app is actually writing to stdout (and not to a file that nothing is reading), whether the buffering has not flushed, and whether the container's stdout pipe is healthy.

### Operations on FDs: `dup()`, `dup2()`, `fcntl()`, and adjusting descriptor flags (`FD_CLOEXEC`, `O_NONBLOCK`)

The FD-manipulation syscalls are the toolkit for redirecting, duplicating, and modifying file descriptors without re-opening the underlying file. `dup(oldfd)` returns the lowest available FD number that points to the same `struct file` as `oldfd` — the two FDs now share the file offset and status flags. `dup2(oldfd, newfd)` does the same but forces the new FD to be `newfd` — if `newfd` was already open, it is silently closed first. This is what the shell uses for redirection: `> file` is implemented as `dup2(open(file, O_WRONLY|O_CREAT|O_TRUNC, 0644), 1)` — open the file, then duplicate its FD onto FD 1 (stdout), so subsequent writes to FD 1 go to the file. `2>&1` is `dup2(1, 2)` — duplicate FD 1 onto FD 2, so stderr goes wherever stdout goes.

`fcntl(fd, F_DUPFD, min_fd)` is a more flexible variant of `dup` that lets you specify a minimum FD number for the duplicate (useful when you want to ensure the new FD is above some threshold, like avoiding 0/1/2 for a long-lived FD). `fcntl(fd, F_GETFD)` and `fcntl(fd, F_SETFD, flags)` operate on the FD itself — the only flag here is `FD_CLOEXEC`, which controls whether the FD is automatically closed on `execve`. The default is "no" (the FD survives `execve`), which is the legacy Unix behavior and the source of countless FD leaks — if you `open()` a file, then `fork()` and `execve()` a child, the child inherits the FD unless you set `FD_CLOEXEC`. The POSIX-2008 fix is to use `open(path, flags | O_CLOEXEC, mode)` so the FD is created with `FD_CLOEXEC` already set, eliminating the race between `open` and `fcntl(F_SETFD)`.

`fcntl(fd, F_GETFL)` and `fcntl(fd, F_SETFL, flags)` operate on the underlying `struct file`'s status flags — the most important being `O_NONBLOCK` (sets the FD to non-blocking mode, so `read` and `write` return `EAGAIN` instead of blocking) and `O_APPEND` (every `write` atomically seeks to the end of the file first, which is what makes concurrent appends to a log file safe). Note the distinction: `F_SETFD` affects only the FD (per-process); `F_SETFL` affects the underlying `struct file` (shared by all FDs that point to it via `dup` or `fork`). This distinction matters: if you `dup` an FD and then `F_SETFL` `O_NONBLOCK` on one of the duplicates, both duplicates become non-blocking, because they share the same `struct file`. If you want one duplicate to be blocking and the other non-blocking, you have to `open` the file twice (or use `dup` and accept that they share flags).

The `O_NONBLOCK` flag is the foundation of every event-loop runtime. When a socket is in non-blocking mode, `read` returns immediately — either with data (if any was available), or with `-1` and `errno = EAGAIN` (or `EWOULDBLOCK`, which is the same value on Linux). The application is then expected to use `epoll_wait` (see 02.05.03) to learn when the socket has data again. Without `O_NONBLOCK`, a `read` on a socket with no data blocks the calling thread until data arrives — which means the thread cannot service any other connection while waiting, which is the thread-per-connection model that does not scale past a few thousand connections. Every runtime in section 04 that uses event loops (Node, Nginx, Netty, asyncio) sets `O_NONBLOCK` on every socket and uses `epoll` to know when to retry — the FD + `O_NONBLOCK` + `epoll` trio is the architectural foundation of modern high-concurrency backends.

```c
/* dup2 in action — what the shell does for `> file` */
#include <fcntl.h>
#include <unistd.h>

void redirect_stdout_to(const char *path) {
    int fd = open(path, O_WRONLY | O_CREAT | O_TRUNC | O_CLOEXEC, 0644);
    if (fd < 0) { perror("open"); return; }
    if (dup2(fd, STDOUT_FILENO) < 0) {   /* force FD 1 to point at our file */
        perror("dup2");
        close(fd);
        return;
    }
    close(fd);                            /* the original FD is no longer needed */
    /* Now every printf/write(1, ...) goes to the file. */
    /* Note: FD_CLOEXEC was NOT set on FD 1 (dup2 clears it), so the
       redirection survives execve — which is what we want for shell
       command substitution. */
}

/* Setting O_NONBLOCK on a socket — the foundation of every event loop */
#include <fcntl.h>
#include <errno.h>

void set_nonblocking(int fd) {
    int flags = fcntl(fd, F_GETFL, 0);
    if (flags < 0) { perror("fcntl F_GETFL"); return; }
    if (fcntl(fd, F_SETFL, flags | O_NONBLOCK) < 0) {
        perror("fcntl F_SETFL");
    }
}

/* Reading from a non-blocking socket */
ssize_t recv_nonblock(int fd, void *buf, size_t len) {
    ssize_t n = read(fd, buf, len);
    if (n < 0 && (errno == EAGAIN || errno == EWOULDBLOCK)) {
        /* No data available right now — caller should epoll_wait and retry. */
        return -1;  /* caller checks errno */
    }
    return n;
}

/* The O_CLOEXEC race — why you should always use O_CLOEXEC in open() */
/* BAD: */
int fd = open(path, O_RDWR);          /* FD is NOT cloexec */
/* If another thread forks + execs here, the child inherits this FD. */
fcntl(fd, F_SETFD, FD_CLOEXEC);       /* too late — race already lost */

/* GOOD: */
int fd = open(path, O_RDWR | O_CLOEXEC);   /* atomic: FD is cloexec from the start */
```

The connection to the upper layers is the O_CLOEXEC and O_NONBLOCK story in every runtime. Java's `AsynchronousFileChannel.open()` sets `O_NONBLOCK` and uses `epoll` underneath; Java's `ProcessBuilder` uses `O_CLOEXEC` on every inherited FD to prevent leaks. Node's `net.Server` calls `fcntl(O_NONBLOCK)` on every accepted socket; Node's `child_process.spawn` defaults to `stdio: 'pipe'` (which uses `pipe2(O_CLOEXEC)`) to prevent FD leaks into children. Python's `socket.setblocking(False)` calls `fcntl(F_SETFL, O_NONBLOCK)`; Python's `subprocess.Popen` with `close_fds=True` (the default since 3.2) closes all FDs above 2 in the child before `execve`, eliminating the leak entirely. The lesson is that the FD primitives — `dup`, `dup2`, `fcntl`, `O_CLOEXEC`, `O_NONBLOCK` — are the same primitives every runtime uses, and every runtime's "child process management" and "non-blocking I/O" features are policy layers on top of these syscalls. When you read the runtime notes in section 04, every runtime's I/O model is a wrapper around FD + flags + epoll, and every runtime's process-spawning model is a wrapper around fork + fcntl(FD_CLOEXEC) + execve. The FD abstraction is the contract.

## How This Connects to the Runtimes

Every runtime covered in section 04 is a user-space wrapper around these kernel primitives:

- **JVM**: Maps Java threads 1:1 to OS threads via NPTL. The JVM's memory model (section 04.01) is a specification layered on top of the kernel's virtual memory system described here.
- **Node.js / libuv**: The event loop (section 04.02) is a Reactor pattern built on `epoll_wait()`. The worker thread pool uses OS threads for operations that cannot be multiplexed (file I/O, DNS, crypto).
- **CPython**: The GIL (section 04.03) is a mutex that serializes Python bytecode execution across OS threads. Multi-processing in Python uses `fork()` to bypass the GIL.
- **PHP-FPM**: Each worker is a separate OS process (section 04.04). The shared-nothing model is a direct consequence of the process isolation described in the Linux Process Model note.

When you read those runtime notes, come back here and trace which kernel primitive each runtime feature maps to.
