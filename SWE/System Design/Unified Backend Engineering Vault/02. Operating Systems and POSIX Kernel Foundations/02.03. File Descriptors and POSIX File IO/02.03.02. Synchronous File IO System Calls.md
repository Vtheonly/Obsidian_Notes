# 02.03.02. Synchronous File IO System Calls

## What This Is

**Synchronous File IO System Calls** is the layer immediately above the FD abstraction (02.03.01) — the actual syscalls that move bytes between user-space buffers and kernel data structures. Where 02.03.01 covered *what* an FD is and *how* the kernel looks it up, this note covers *what happens* when you call `read(fd, buf, n)` or `write(fd, buf, n)`, and the surprising fact that `write` returning successfully does NOT mean your data is on disk. The reason this note sits in section 02 is that every database durability guarantee, every log-message persistence claim, and every "we lost data after a crash" production incident reduces to one of three syscalls: `write` (cheap, NOT durable), `fsync` (expensive, durable), and `O_DIRECT` (bypasses the cache entirely). Every runtime in section 04 wraps these syscalls — Java's `FileOutputStream.write` is a `write` syscall, Node's `fs.writeFile` is a `write` + `fsync`, Python's `os.write` is a `write`, PHP's `fwrite` is a `write` — and every runtime's "flush" method calls `fsync` under the hood.

The mental model is: the kernel maintains a **page cache** in RAM — a large pool of 4 KB pages holding the contents of recently-accessed files. `write(fd, buf, n)` copies your bytes into the page cache (immediate, fast, in-memory) and returns. The page is now "dirty" (modified in RAM but not yet on disk). The kernel writes dirty pages back to disk asynchronously via background `flusher` threads (or via `kupdate`/`pdflush` on older kernels), based on age (default 30 seconds) or memory pressure. If the machine crashes between the `write` returning and the page being flushed, the data is lost. The only way to guarantee durability is `fsync(fd)`, which blocks until every dirty page belonging to that FD is physically on the storage device (the kernel issues a barrier command to the disk controller and waits for the disk's ack). Databases call `fsync` on every transaction commit; log aggregators call `fsync` on every log file rotation; applications that skip `fsync` lose data on crash.

## The Details

### Low-level primitives: `open()`, `read()`, `write()`, `lseek()`, and `close()`

The five core file I/O syscalls form the minimum POSIX API for working with files. `open(path, flags, mode)` resolves the path through the filesystem (VFS layer, then the specific filesystem like ext4 or xfs), allocates a new `struct file` and a new `struct inode` (or reuses an existing inode if the file already exists), assigns the lowest available FD number to it, and returns the FD integer. The `flags` argument is a bitmask that controls the open mode: `O_RDONLY` / `O_WRONLY` / `O_RDWR` (one of these is required), `O_CREAT` (create the file if it does not exist), `O_EXCL` (fail if the file already exists, used for atomic lock-file creation), `O_TRUNC` (truncate the file to zero length on open), `O_APPEND` (every write atomically seeks to end of file), `O_NONBLOCK` (open in non-blocking mode — relevant for FIFOs and sockets), `O_CLOEXEC` (set FD_CLOEXEC on the new FD), `O_DIRECT` (bypass the page cache), `O_SYNC` (every write is durable before returning), `O_DSYNC` (every write is data-durable before returning — slightly weaker than `O_SYNC`). The `mode` argument is the file's permission bits (only used if `O_CREAT` is set and the file is being created), masked by the process's `umask`.

`read(fd, buf, count)` and `write(fd, buf, count)` are the workhorses. `read` copies up to `count` bytes from the file (starting at the current offset `f_pos`) into `buf`, advances the offset by the number of bytes read, and returns the count (or 0 for EOF, or -1 for error). `write` is the dual: copies up to `count` bytes from `buf` into the file at the current offset, advances the offset, returns the count. Both can return fewer bytes than requested — `read` on a socket returns whatever data is available, `read` on a regular file always returns the full count unless EOF is hit, `write` to a pipe or socket can return a partial count if the kernel buffer is full. Production code must always loop on partial reads/writes — the standard idiom is `while ((n = read(fd, buf, count)) > 0) { buf += n; count -= n; }` to handle partial reads correctly.

`lseek(fd, offset, whence)` moves the file offset `f_pos` to a new position: `SEEK_SET` (absolute position from the start), `SEEK_CUR` (relative to the current position), `SEEK_END` (relative to the end of the file). `lseek` does no I/O — it just updates the in-memory `f_pos` field. The combination `lseek(fd, 0, SEEK_END); write(fd, buf, n);` is the manual-append pattern, but it has a race condition if multiple processes do it concurrently (the lseek and the write are not atomic) — that is what `O_APPEND` solves, by making every `write` atomically seek to end first. `close(fd)` decrements the `struct file`'s reference count; if it reaches zero, the kernel frees the `struct file` and decrements the inode's reference count, and if THAT reaches zero and the file was unlinked, the inode is freed and the disk blocks are reclaimed. Forgetting to `close` is an FD leak; closing too early while another thread is using the FD is a use-after-close bug; both are common production hazards.

```c
/* The complete low-level file I/O pattern in C. */
#include <fcntl.h>
#include <unistd.h>
#include <errno.h>
#include <string.h>

/* Read a file completely into a malloc'd buffer. */
char *read_file(const char *path, size_t *out_len) {
    int fd = open(path, O_RDONLY | O_CLOEXEC);   /* O_CLOEXEC prevents child leaks */
    if (fd < 0) return NULL;

    /* Get file size by seeking to end and back. */
    off_t size = lseek(fd, 0, SEEK_END);
    lseek(fd, 0, SEEK_SET);

    char *buf = malloc(size + 1);
    if (!buf) { close(fd); return NULL; }

    /* Loop on partial reads — read may return fewer bytes than requested. */
    size_t total = 0;
    while (total < (size_t)size) {
        ssize_t n = read(fd, buf + total, size - total);
        if (n < 0) {
            if (errno == EINTR) continue;        /* interrupted by signal — retry */
            free(buf); close(fd); return NULL;
        }
        if (n == 0) break;                       /* EOF (shouldn't happen on regular file) */
        total += n;
    }
    buf[total] = '\0';
    close(fd);
    *out_len = total;
    return buf;
}

/* Write a buffer to a file with full durability (fsync). */
int write_file_durable(const char *path, const char *data, size_t len) {
    int fd = open(path, O_WRONLY | O_CREAT | O_TRUNC | O_CLOEXEC, 0644);
    if (fd < 0) return -1;

    /* Loop on partial writes — write may return fewer bytes than requested
       if the kernel's page cache is under pressure or if writing to a pipe/socket. */
    size_t total = 0;
    while (total < len) {
        ssize_t n = write(fd, data + total, len - total);
        if (n < 0) {
            if (errno == EINTR) continue;
            close(fd); return -1;
        }
        total += n;
    }

    /* CRITICAL: write() only put data in the page cache.  To guarantee it
       is on physical disk, we MUST fsync().  Without this, a power loss
       after write() returns may lose the data. */
    if (fsync(fd) < 0) { close(fd); return -1; }

    /* Best practice: fsync the directory too, so the file's metadata
       (size, mtime) is also durable.  Otherwise a crash may leave the
       file present but with stale metadata. */
    int dirfd = open(".", O_RDONLY | O_DIRECTORY);
    if (dirfd >= 0) { fsync(dirfd); close(dirfd); }

    close(fd);
    return 0;
}
```

The connection to the upper layers is the runtime-buffering story. C's `stdio` (`fopen`, `fread`, `fwrite`, `fclose`) wraps the FD syscalls in a `FILE*` with a userspace buffer — `fwrite` to a `FILE*` may not call `write` at all (it may just copy into the userspace buffer), and `fflush` is needed to force the buffer to the kernel via `write`. Java's `BufferedOutputStream` does the same — `write()` to a `BufferedOutputStream` may not call the underlying `write` syscall until the buffer fills or `flush()` is called. Python's `io.BufferedWriter` does the same. The buffering dramatically reduces syscall overhead (one 64 KB `write` is much cheaper than 64 1 KB `write`s), but it means that "I called write but the data is not on disk" has TWO layers of indirection: the userspace buffer (flushed by `fflush` / `flush()`) and the kernel page cache (flushed by `fsync`). Production code that needs durability must call BOTH — the runtime's `flush()` to drain the userspace buffer to the kernel, AND the runtime's `fsync()` (or `getFD().sync()` in Java, `os.fsync(fd)` in Python, `fs.writeFileSync(path, data, {flag: 'wx'})` plus `fs.fsyncSync(fd)` in Node) to drain the kernel cache to disk. Missing either one is a data-loss bug.

### OS Page Cache: Dirty pages, write buffering, background write-back daemons (`flusher` threads)

The Linux page cache is a pool of 4 KB pages in RAM that hold the contents of recently-accessed files. When a process calls `read(fd, buf, n)`, the kernel first checks if the requested pages are in the page cache — if they are (a "cache hit"), the read is satisfied entirely from RAM (microsecond latency); if they are not (a "cache miss"), the kernel schedules a disk read, suspends the calling thread until the I/O completes (typically a major page fault, 10-100 ms), and inserts the resulting page into the cache. When a process calls `write(fd, buf, n)`, the kernel copies the data into a page-cache page (marking it "dirty" — modified in RAM but not yet on disk) and returns immediately — the actual disk write happens later, asynchronously. The page cache thus serves two purposes: it caches reads (avoiding disk access for hot data) and it buffers writes (allowing the kernel to coalesce many small writes into a few large disk writes, which is critical for performance because disks are much faster at sequential large writes than at random small ones).

The kernel writes dirty pages back to disk via background **flusher threads** (the `kworker` threads, or `pdflush` on kernels before 2.6.32). The flusher algorithm has two triggers: a time-based trigger (dirty pages older than `vm.dirty_writeback_centisecs`, default 30 seconds, are written back) and a memory-pressure trigger (when the fraction of dirty pages exceeds `vm.dirty_ratio`, default 20% of RAM, the flusher becomes aggressive; when it exceeds `vm.dirty_bytes` / `vm.dirty_background_ratio`, default 10%, the flusher starts running in the background). The flusher is also triggered explicitly by `fsync(fd)` and `sync()`. The flusher uses a writeback policy that tries to be disk-friendly: it sorts dirty pages by their underlying disk block address and writes them out in roughly sequential order, which is dramatically faster than random writes on rotational disks (and still measurably faster on SSDs due to internal parallelism and write-amplification reduction).

The page cache is shared by all processes on the system — when process A reads `/etc/passwd`, the page is in the cache and process B's subsequent read of `/etc/passwd` is a hit. This is why a freshly-restarted database is slow for the first few minutes (the working set is not in the cache) and then speeds up — the kernel has "warmed up" the cache. The cache can be inspected via `/proc/meminfo` (the `Cached:` line shows the total page cache size, and the `Dirty:` line shows how many KB are dirty waiting for writeback). The cache can be dropped manually via `echo 3 > /proc/sys/vm/drop_caches` (useful for benchmarking to ensure cold-cache behavior, but dangerous in production because it forces every process to re-fault its hot data). The size of the cache is bounded only by available RAM — the kernel will use whatever RAM is not needed by processes, and will evict pages (using an LRU-like algorithm) when memory is needed for something else. This is why `free -h` shows a small "free" number and a large "buff/cache" number on a healthy Linux server — the kernel is using all available RAM for the cache, which is the correct behavior.

The connection to the upper layers is the double-caching problem. A database like PostgreSQL maintains its own buffer pool (`shared_buffers`, default 128 MB, typically tuned to 25% of RAM) for caching frequently-accessed data pages. Without `O_DIRECT`, the kernel's page cache ALSO caches those pages — so every database page is in memory twice: once in `shared_buffers` (managed by Postgres) and once in the page cache (managed by the kernel). This wastes memory and adds an extra memcpy on every read. The fix is `O_DIRECT`, which bypasses the page cache and lets the database be the sole cache manager — but `O_DIRECT` requires the user buffer to be page-aligned (`posix_memalign`), the offset to be page-aligned, and the length to be a multiple of the block size, which is awkward. PostgreSQL does NOT use `O_DIRECT` by default (it uses `O_DSYNC` on the WAL and regular writes for the data files, with `fsync` on commits); MySQL's InnoDB DOES use `O_DIRECT` (configurable via `innodb_flush_method=O_DIRECT`). The runtime choice is a policy decision: do you want the kernel to manage the cache (simpler, but double-cached) or the application (more work, but no duplication)? When you read the persistence notes in section 06, every database has made this choice differently.

### Enforcing physical durability: `fsync()` (data and metadata flush), `fdatasync()` (data-only flush), and `O_SYNC` flags

`fsync(fd)` is the syscall that converts a successful `write` into actual on-disk durability. It blocks the calling thread until every dirty page belonging to `fd` (in the page cache) has been written to the physical storage device AND the storage device has acknowledged the write. On a modern NVMe SSD, this takes ~50-200 µs per call; on a SATA SSD, ~200 µs to 1 ms; on an HDD, 5-20 ms (rotational latency + seek time); on a network-attached store like EBS or NFS, 1-10 ms. The kernel issues a "barrier" command (or a "flush" command, depending on the device protocol) to the storage device, which forces the device's internal write cache to be flushed to the persistent medium before acking. Without `fsync`, a power loss or kernel crash can lose any data that was only in the page cache — this is the root cause of countless "we lost the last few minutes of data after the machine crashed" production incidents.

`fsync` flushes both file data AND file metadata (inode size, mtime, ctime, etc.). For most workloads, the metadata flush is unnecessary overhead — if the file already exists and you are only modifying its contents, the size, mtime, and ctime changes are not load-bearing for crash recovery. `fdatasync(fd)` is a faster variant that flushes ONLY the file data and the metadata that is strictly necessary for data recovery (e.g., the file size, because without it the file would be truncated on recovery). It skips flushing the mtime/atime/ctime changes, which the disk can flush lazily. On most filesystems and most workloads, `fdatasync` is 10-30% faster than `fsync` with identical durability guarantees for data. Databases that care about latency (PostgreSQL, MySQL) use `fdatasync` for transaction commits; applications that need full metadata durability (e.g., creating a new file and ensuring its existence survives a crash) use `fsync`.

`O_SYNC` is a per-FD flag (set at `open` time) that makes every `write` call behave like `write + fsync`. This is convenient because it eliminates the need for an explicit `fsync` call after every write, but it is also slower than batching — if you call `write(fd, buf, 4)` ten times on an `O_SYNC` FD, you pay ten disk flushes, whereas if you call `write(fd, buf, 40)` once on a regular FD followed by `fsync(fd)`, you pay one disk flush for the same data. `O_DSYNC` is the equivalent of `O_SYNC` but with `fdatasync` semantics (data only, no metadata). `O_SYNC` and `O_DSYNC` exist primarily for compliance with POSIX and for applications that want the "every write is durable" guarantee baked into the FD rather than sprinkled through the code. Databases almost never use them — they prefer explicit `fdatasync` calls so they can control batching.

The filesystem matters enormously for `fsync` cost. **ext4** with `data=ordered` (the default) flushes data before metadata, which means `fsync` is fast but a crash can leave recently-written data visible even if the application did not call `fsync` (the kernel's journal flushes data first). **ext4** with `data=journal` (full journaling) is slower for writes but offers stronger guarantees. **xfs** is faster for large files and high-throughput workloads but has slightly different crash semantics. **ZFS** and **btrfs** (copy-on-write filesystems) have different durability characteristics — every write is effectively copy-on-write, so `fsync` is fast but the file may be fragmented. NFS is famously bad for `fsync` because the network round-trip dominates the latency — a 1 ms `fsync` on local disk becomes a 5-10 ms `fsync` on NFS, which is why databases on NFS are a known performance hazard.

```c
/* The durability hierarchy — what each call guarantees. */
#include <fcntl.h>
#include <unistd.h>

/* Level 0: write only.  Data is in the page cache, NOT on disk.
   A crash can lose this data.  Fast (~1 µs per write). */
write(fd, data, len);

/* Level 1: write + fdatasync.  Data is on disk; metadata (mtime) may lag.
   Safe for transaction commits.  Slower (~1 ms per call on SSD). */
write(fd, data, len);
fdatasync(fd);

/* Level 2: write + fsync.  Data AND metadata on disk.
   Safe for file creation, renames, deletes.  Slowest (~1-2 ms per call). */
write(fd, data, len);
fsync(fd);

/* Level 3: O_SYNC at open time.  Every write is fsync'd implicitly.
   Convenient but slow if you make many small writes. */
int fd = open(path, O_WRONLY | O_CREAT | O_SYNC, 0644);
write(fd, data, len);   /* blocks until data + metadata on disk */

/* Level 4: O_DIRECT.  Bypasses the page cache entirely.
   Application manages its own cache.  Buffer must be page-aligned. */
void *buf;
posix_memalign(&buf, 4096, 4096);   /* must be sector-aligned */
memcpy(buf, data, len);
int fd = open(path, O_WRONLY | O_CREAT | O_DIRECT, 0644);
write(fd, buf, 4096);   /* direct to disk, no page cache involvement */

/* The atomic rename pattern — how databases and loggers replace a file safely. */
int fd = open("/tmp/log.new", O_WRONLY | O_CREAT | O_TRUNC | O_CLOEXEC, 0644);
write(fd, new_contents, len);
fsync(fd);                    /* MUST fsync the data */
close(fd);
fsync(open("/tmp", O_RDONLY | O_DIRECTORY));   /* MUST fsync the directory */
rename("/tmp/log.new", "/tmp/log");            /* atomic on POSIX */
fsync(open("/tmp", O_RDONLY | O_DIRECTORY));   /* MUST fssync the directory AGAIN */
```

The connection to the upper layers is the database durability story. PostgreSQL's WAL (Write-Ahead Log) records every transaction's modifications; on commit, Postgres calls `fsync` (or `fdatasync`, depending on `wal_sync_method`) on the WAL file. This is the cost you pay for every transaction commit — 1 ms of `fsync` on a fast SSD, 10 ms on a slow one. A database doing 1000 transactions per second spends 1 full second of CPU time per second on `fsync` calls; this is why disk IOPS is the dominant bottleneck for write-heavy databases, not CPU. MySQL's InnoDB has the same pattern (`innodb_flush_log_at_trx_commit=1` means `fsync` on every commit). MongoDB's `journalCommitInterval` defaults to 100 ms (it batches commits). Redis's `appendfsync` setting defaults to `everysec` (one `fsync` per second, trading durability for throughput — a crash can lose up to 1 second of writes). Every persistence choice in section 06 reduces to this `fsync` cost model. When you read the persistence notes, the database's durability setting is exactly this `write + fsync` pattern, and the database's write throughput is bounded by `1 / fsync_latency × batch_size`.

### Direct I/O (`O_DIRECT`): Bypassing the kernel page cache for user-managed database buffer pools

`O_DIRECT` is a flag passed to `open()` that tells the kernel to bypass the page cache for all I/O on this FD. Reads and writes go directly between the user-space buffer and the disk, with no intermediate copy through the page cache. The motivation is to avoid the double-caching problem: if the application maintains its own cache (PostgreSQL's `shared_buffers`, MySQL's `InnoDB buffer pool`, Oracle's `buffer cache`), the kernel's page cache is redundant — every database page ends up in memory twice, wasting 50% of the RAM allocated to caching. `O_DIRECT` lets the application be the sole cache manager, which is more efficient when the application has better cache-replacement logic than the kernel (which it usually does, because the application knows the access pattern).

`O_DIRECT` comes with strict alignment requirements that make it awkward to use. The user-space buffer passed to `read`/`write` must be aligned to the disk's logical block size (typically 512 bytes for older disks, 4096 bytes for modern 4K-native disks) — `malloc` does NOT guarantee this alignment, so the application must use `posix_memalign` or `aligned_alloc`. The file offset must be a multiple of the block size. The length passed to `read`/`write` must be a multiple of the block size. Violating any of these returns `EINVAL`. The aligned-buffer requirement is the most annoying part — it means the application cannot just `write(fd, arbitrary_struct, sizeof(arbitrary_struct))`; it must copy into an aligned buffer first. This is why `O_DIRECT` is used almost exclusively by databases that already manage their pages in fixed-size blocks (PostgreSQL uses 8 KB pages, MySQL uses 16 KB pages, Oracle uses 8 KB by default).

`O_DIRECT` does NOT imply durability — it only bypasses the page cache, it does not force the disk to acknowledge the write before returning. To get both cache bypass AND durability, you need `O_DIRECT | O_SYNC` (or `O_DIRECT` plus an explicit `fsync`). The kernel documentation in `Documentation/filesystems/dax.txt` and `man 2 open` is explicit about this: "O_DIRECT is not a synonym for O_SYNC; it does not provide any durability guarantees." Many production bugs come from this confusion — applications that switch from regular writes to `O_DIRECT` expecting durability and discovering that they still need `fsync` for crash safety. The Linux kernel maintainer Linus Torvalds is famously skeptical of `O_DIRECT` (he called it "a stupid interface" in a 2009 mailing list post) because it is so easy to misuse, but it remains the standard way to bypass the page cache.

The performance characteristics of `O_DIRECT` are workload-dependent. For sequential large reads/writes (e.g., a database doing a full table scan), `O_DIRECT` is comparable to or slightly slower than cached I/O (the kernel's readahead is good at sequential access). For random small reads/writes (e.g., a database doing point lookups), `O_DIRECT` is faster IF the application's cache is effective (because the page cache is being polluted with cold data that displaces hot data). For workloads where the application's cache is not effective (e.g., a database whose working set is larger than `shared_buffers`), `O_DIRECT` is slower than cached I/O because the page cache would have helped. The general rule is: use `O_DIRECT` if your application has its own cache AND the cache is large enough to hold the working set; otherwise, let the kernel manage the cache.

```c
/* O_DIRECT example — must align buffer, offset, and length. */
#define _GNU_SOURCE
#include <fcntl.h>
#include <unistd.h>
#include <stdlib.h>
#include <stdio.h>
#include <string.h>

int main(void) {
    /* Allocate a page-aligned buffer (posix_memalign). */
    void *buf;
    if (posix_memalign(&buf, 4096, 4096) != 0) {
        perror("posix_memalign"); return 1;
    }
    memcpy(buf, "hello, direct I/O world\n", 24);

    /* Open with O_DIRECT — bypass page cache. */
    int fd = open("/tmp/direct_test", O_WRONLY | O_CREAT | O_TRUNC | O_DIRECT, 0644);
    if (fd < 0) { perror("open"); return 1; }

    /* Write — offset must be 4096-aligned, length must be 4096-aligned,
       buffer must be 4096-aligned.  All three conditions met. */
    ssize_t n = pwrite(fd, buf, 4096, 0);   /* pwrite = positioned write */
    if (n < 0) { perror("pwrite"); return 1; }
    printf("wrote %zd bytes via O_DIRECT (no page cache involvement)\n", n);

    /* fsync is STILL needed for durability — O_DIRECT does not imply O_SYNC. */
    if (fsync(fd) < 0) { perror("fsync"); return 1; }

    close(fd); free(buf);
    return 0;
}
```

```bash
# Compare cached vs O_DIRECT throughput on sequential writes
$ dd if=/dev/zero of=/tmp/cached bs=1M count=1000
1000+0 records out
1048576000 bytes (1.0 GB) copied, 0.832 s, 1.3 GB/s       ← page cache absorbs, returns instantly

$ dd if=/dev/zero of=/tmp/direct bs=1M count=1000 oflag=direct
1000+0 records out
1048576000 bytes (1.0 GB) copied, 4.512 s, 232 MB/s        ← direct to disk, slower

# But: after the cached write, the data is still in the page cache, NOT on disk.
# Sync it:
$ time sync
real    0m3.234s                                              ← the actual disk write cost

# So cached + sync ≈ O_DIRECT in throughput for sequential writes.
# O_DIRECT wins for random access where page cache pollution matters.

# Configure a database to use O_DIRECT
# PostgreSQL: does NOT use O_DIRECT by default; uses regular writes + fsync.
#   Add-on: pgfsync can be patched to use O_DIRECT for the WAL.
# MySQL:  innodb_flush_method=O_DIRECT in my.cnf
# Oracle: FILESYSTEMIO_OPTIONS=DIRECTIO in init.ora
```

The connection to the upper layers is the database-tuning story. Every persistence note in section 06 references this `O_DIRECT` choice. PostgreSQL deliberately avoids `O_DIRECT` because the developers believe the kernel's page cache is beneficial as a second-level cache (data not in `shared_buffers` may still be in the page cache, giving a faster second access). MySQL's InnoDB defaults to `O_DIRECT` because the developers believe the double-caching waste outweighs the second-level benefit. Oracle supports both modes and lets the DBA choose. Redis does not use `O_DIRECT` because it is single-threaded and the page cache helps it. The choice is always a tradeoff between cache duplication (waste) and second-level cache benefit (free win), and the right answer depends on the workload's working-set-to-RAM ratio. When you read the database notes in section 06, the `O_DIRECT` setting is one of the first things to check on any "my database is slow" investigation — and the fix is not always to flip the setting, but to understand whether the bottleneck is cache pollution (use `O_DIRECT`) or cache misses (do not use `O_DIRECT`).

## How This Connects to the Runtimes

Every runtime covered in section 04 is a user-space wrapper around these kernel primitives:

- **JVM**: Maps Java threads 1:1 to OS threads via NPTL. The JVM's memory model (section 04.01) is a specification layered on top of the kernel's virtual memory system described here.
- **Node.js / libuv**: The event loop (section 04.02) is a Reactor pattern built on `epoll_wait()`. The worker thread pool uses OS threads for operations that cannot be multiplexed (file I/O, DNS, crypto).
- **CPython**: The GIL (section 04.03) is a mutex that serializes Python bytecode execution across OS threads. Multi-processing in Python uses `fork()` to bypass the GIL.
- **PHP-FPM**: Each worker is a separate OS process (section 04.04). The shared-nothing model is a direct consequence of the process isolation described in the Linux Process Model note.

When you read those runtime notes, come back here and trace which kernel primitive each runtime feature maps to.
