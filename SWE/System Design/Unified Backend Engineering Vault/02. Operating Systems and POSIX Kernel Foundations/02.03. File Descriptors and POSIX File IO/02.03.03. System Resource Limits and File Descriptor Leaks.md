# 02.03.03. System Resource Limits and File Descriptor Leaks

## What This Is

**System Resource Limits and File Descriptor Leaks** is the operational chapter of the FD abstraction — what happens when the abstraction runs out of resources, how to monitor the resource usage, and how to fix the inevitable production incidents. Every backend service that opens files, accepts network connections, or talks to databases consumes file descriptors; every service that fails to close them eventually hits the per-process FD limit (`EMFILE`) or the system-wide FD limit (`ENFILE`). The reason this note sits in section 02 is that the limits are kernel-enforced and runtime-agnostic — a Java server, a Node process, a PHP-FPM worker, and a C database all hit the same `EMFILE` error with the same root cause, and the recovery procedure is the same in every case. Understanding the limit hierarchy (per-process soft, per-process hard, system-wide, cgroup) and the monitoring tools (`lsof`, `/proc/<pid>/fd`, `ss`) is what separates engineers who can diagnose an FD-leak incident at 3 a.m. from engineers who can only restart the service and hope.

The mental model is: every process has a soft FD limit (the current limit, raiseable by the process itself up to the hard limit) and a hard FD limit (the maximum, raiseable only by root). The system has a system-wide FD limit (the total across all processes). Cgroups add a per-cgroup FD limit. When a process tries to `open()` or `accept()` a new FD and the per-process soft limit is hit, the syscall returns `-1` with `errno = EMFILE` ("Too many open files"). When the system-wide limit is hit, the syscall returns `-1` with `errno = ENFILE` ("Too many open files in system"). `EMFILE` is far more common and is the classic "Too many open files" error that every backend engineer encounters. The default soft limit is 1024 on most Linux distros — a number set in the 1990s that is wildly inadequate for modern high-concurrency servers, which is why every production deployment raises it.

## The Details

### Monitoring open file descriptors: Inspecting `/proc/<PID>/fd` and using the `lsof` utility

The kernel exposes every process's open FDs through `/proc/<pid>/fd/`, a directory containing one symlink per open FD. The symlink's name is the FD integer (`0`, `1`, `2`, `3`, ...); the symlink's target is the file path (or socket endpoint, or pipe inode) that the FD points to. Listing this directory tells you exactly what FDs a process has open and what they are connected to — the single most useful diagnostic for FD leak investigations. The `/proc/<pid>/fdinfo/<n>` files contain additional per-FD metadata: the file position (`pos`), the open flags (`flags`), the mount ID (`mnt_id`), and (for eventpoll/timerfd/signalfd) the registered events. Together, `/proc/<pid>/fd` and `/proc/<pid>/fdinfo` give a complete picture of the process's open-file state without needing any external tools.

`lsof` (LiSt Open Files) is the standard userspace tool that parses `/proc` and presents the data in a more friendly format. `lsof -p <pid>` lists every open FD for a process; `lsof -i :8080` lists every process with a socket bound to port 8080; `lsof /var/log/syslog` lists every process with that file open. `lsof` is slower than reading `/proc/<pid>/fd` directly (it parses every process's `/proc` entry, which can take seconds on a busy system), but it is more convenient for cross-process queries. The faster alternative for "how many FDs does process X have open" is `ls /proc/<pid>/fd | wc -l` — instant, no parsing needed. For ongoing monitoring, the `pidstat -f 1` command shows the FD count per process per second, which is useful for watching a leak develop in real time.

The FD count is just the number of entries in `/proc/<pid>/fd` — it does not tell you what kinds of FDs they are. The leak diagnostic is to look at the symlink targets: `ls -la /proc/<pid>/fd | sort -k11 | uniq -c -f10 | sort -rn` shows the most common FD types. If you see thousands of sockets to the same database port, you have a connection-pool leak (the pool is opening new connections without closing old ones). If you see thousands of pipes, you have a subprocess-spawning leak (the parent is spawning children without reaping them, leaving the pipe FDs open). If you see thousands of `socket:[NNNN]` entries, you have a network connection leak (sockets are being opened without being closed). If you see thousands of regular files, you have a file-handle leak (files are being opened without being closed). Each leak type has a different fix, but the diagnostic is the same: count the FDs, look at the types, find the leak source.

The connection to the upper layers is the production-debugging recipe. Every runtime in section 04 has its own FD-leak symptoms: a JVM throws `java.net.SocketException: Too many open files` and the GC log shows tens of thousands of unreachable sockets; Node throws `Error: EMFILE, too many open files` and the libuv event loop stalls; Python raises `OSError: [Errno 24] Too many open files`; PHP-FPM returns 500 errors with `EMFILE` in the error log. The diagnostic in every case is the same: `ls /proc/<pid>/fd | wc -l` to confirm the leak, `ls -la /proc/<pid>/fd` to identify the type, then read the runtime's specific tooling (`jcmd <pid> Thread.print` for the JVM, `process._getActiveHandles()` for Node, `gc.get_objects()` filtered by `hasattr(o, 'fileno')` for CPython). The fix is always in the application code — a missing `close()` call, a connection pool without idle eviction, a subprocess without `wait()`. The kernel limits are the symptom; the application leak is the disease.

### Soft vs. Hard limits: Configuring `ulimit -n` and editing `/etc/security/limits.conf`

Every process has two FD limits: the **soft limit** (the current maximum, which the process can raise up to the hard limit using `setrlimit(RLIMIT_NOFILE, ...)`) and the **hard limit** (the ceiling, which only root can raise). The kernel enforces the soft limit — any `open()` or `accept()` that would push the FD count above the soft limit fails with `EMFILE`. The defaults are set at login time by the PAM `pam_limits` module, which reads `/etc/security/limits.conf`. The default soft limit on most Linux distros is 1024, and the default hard limit is 4096 (or 1048576 on newer systemd-based distros that ignore `/etc/security/limits.conf` for system services — see below). The 1024 default is a historical artifact from the 1990s that is wildly inadequate for modern servers, which is why every production deployment raises it.

The `ulimit -n` shell builtin (and the `getrlimit` / `setrlimit` syscalls) let you inspect and change the limits at runtime. `ulimit -n` (no argument) prints the current soft limit; `ulimit -n 65536` raises the soft limit to 65536 (if the hard limit allows it); `ulimit -Hn` prints the hard limit. The change applies only to the current shell and its children — it does not affect other processes. To make a change persistent across reboots, you edit `/etc/security/limits.conf` (for PAM-managed logins) or the systemd unit file (for systemd-managed services). The modern Linux stack uses systemd, which does NOT read `/etc/security/limits.conf` — instead, you set `LimitNOFILE=65536` in the `[Service]` section of the unit file. This is a common production gotcha: engineers edit `limits.conf`, restart the service, and find the limit unchanged because systemd ignored their edit.

The limits cascade from the parent process to the child via `fork`/`exec` — a child inherits the parent's limits. So if you `ulimit -n 65536` in a shell and then run `./my_server`, the server starts with a 65536 soft limit. If you start the server from systemd with `LimitNOFILE=65536`, the same thing happens. If you start it from a Docker container with `docker run --ulimit nofile=65536:65536`, the limit is set in the container. The tricky case is when the limit is set on the parent but the child lowers it (which it can, down to the soft limit) — the child can never raise its soft limit above the parent's hard limit. This is why it is important to set the limit as early as possible in the process tree (in systemd, in the shell, in the container runtime) rather than in the application code itself.

```bash
# Inspect the current limits
$ ulimit -n               # soft limit
1024
$ ulimit -Hn              # hard limit
4096

# Raise the soft limit (only up to the hard limit)
$ ulimit -n 65536
-bash: ulimit: open files: cannot modify limit: Operation not permitted
# (Failed because 65536 > hard limit of 4096)

# Raise both (must be root or have CAP_SYS_RESOURCE)
$ sudo bash -c 'ulimit -n 65536 && ulimit -Hn 65536 && exec su $SUDO_USER'
$ ulimit -n
65536

# Permanent: /etc/security/limits.conf (PAM-managed logins only)
$ sudo tee -a /etc/security/limits.conf <<EOF
*       soft    nofile  65536
*       hard    nofile  65536
EOF

# Permanent: systemd service (the modern way for production services)
$ sudo systemctl edit postgresql
[Service]
LimitNOFILE=65536
# (then: sudo systemctl restart postgresql)

# Permanent: Docker container
$ docker run --ulimit nofile=65536:65536 my-app

# Permanent: Kubernetes pod (via securityContext)
apiVersion: v1
kind: Pod
spec:
  containers:
  - name: app
    image: my-app
    securityContext:
      runAsNonRoot: true
    resources:
      limits:
        memory: "1Gi"

# Confirm the limit took effect for a running process
$ cat /proc/<pid>/limits | grep "open files"
Max open files            65536                65536                files
#                          ^^^^^                ^^^^^
#                          soft                 hard

# Set RLIMIT_NOFILE programmatically in C
#include <sys/resource.h>
struct rlimit rl = { .rlim_cur = 65536, .rlim_max = 65536 };
if (setrlimit(RLIMIT_NOFILE, &rl) < 0) {
    perror("setrlimit");
    /* fall back to the inherited limit */
}
```

```text
Limit cascade — how limits propagate from parent to child

  systemd (PID 1)
  │
  │  LimitNOFILE=65536 set in unit file
  ▼
  postgres (PID 1234)         ← soft=65536, hard=65536 (from systemd)
  │
  │  fork() + execve() (limits inherited)
  ▼
  postgres: worker (PID 1235) ← soft=65536, hard=65536 (inherited from parent)

  If the worker calls setrlimit(RLIMIT_NOFILE, {1024, 65536}):
  │  soft lowered to 1024 (allowed — soft can be lowered freely)
  │  hard stays at 65536 (allowed — hard can be lowered but not raised above parent)
  ▼
  postgres: worker (PID 1235) ← soft=1024, hard=65536 (worker lowered its own soft)

  If the worker then tries setrlimit(RLIMIT_NOFILE, {100000, 100000}):
  →  FAILS: cannot raise hard above parent's hard (65536)
  →  soft stays at 1024, hard stays at 65536

Lesson: set the limit as high as you will ever need at the EARLIEST point
in the process tree (systemd, container runtime, shell).  Children cannot
raise the hard limit; they can only lower it.
```

The connection to the upper layers is the deployment story. Every runtime in section 04 has a documented "set `LimitNOFILE=65536` in systemd" or "set `--ulimit nofile=65536:65536` in Docker" recommendation. The JVM in particular has a special case: by default, the JVM on Linux caps its own FD limit at `min(RLIMIT_NOFILE hard, 10240)` for legacy reasons (the JVM internally uses FD numbers as small array indices in some places), and you must pass `-XX:-MaxFDLimit` to disable this cap and use the full system limit. This is a frequent production gotcha — engineers set `ulimit -n 100000`, start the JVM, and find it is still capped at 10240 until they add the flag. The lesson is that the kernel limit is necessary but not sufficient: the runtime may impose its own lower limit, and you must check both.

### System-wide file limits: Tuning `/proc/sys/fs/file-max`

Above the per-process limit is the system-wide FD limit, controlled by `/proc/sys/fs/file-max`. This is the maximum number of file descriptors that can be open across ALL processes on the system. The kernel maintains a counter (`nr_file` in `fs/file_table.c`) of currently-open `struct file` objects; when this counter reaches `file-max`, new `open()` calls fail with `ENFILE` ("Too many open files in system") instead of `EMFILE` ("Too many open files" per-process). `ENFILE` is rarer than `EMFILE` because `file-max` is typically much larger than the per-process limits summed — but on shared hosts (e.g., a CI server running many builds, or a Kubernetes node running many pods), `ENFILE` does happen, and the recovery is more disruptive (you have to find the system-wide hog, not just one process).

The kernel computes a default `file-max` at boot based on the system's memory: roughly `memory_in_kb / 10240` (which gives ~100K files per GB of RAM). On a 16 GB server, the default is around 1.6 million — usually plenty. To inspect it, read `/proc/sys/fs/file-max`; to change it temporarily, `echo 2000000 | sudo tee /proc/sys/fs/file-max`; to change it permanently, add `fs.file-max = 2000000` to `/etc/sysctl.conf` and run `sysctl -p`. The companion file `/proc/sys/fs/file-nr` shows the current usage: `allocated` (currently-open files), `pre-allocated` (files in the slab cache that are not currently used but available for fast allocation), and `max` (the file-max value). A healthy system shows `allocated` well below `max`; a system approaching the limit shows `allocated` climbing toward `max`, and you should investigate before it hits.

The system-wide limit interacts with the per-process limits in a non-obvious way. If you have 100 processes each with a per-process limit of 65536, the theoretical maximum is 6,553,600 open files — but the system-wide limit may be far lower (e.g., 1.6 million). In that case, the processes cannot all hit their per-process limits simultaneously; one of them will hit `ENFILE` first. This is why shared environments (Kubernetes nodes, multi-tenant servers) need the system-wide limit set generously, and why cgroup-level limits (see below) are useful for isolating noisy tenants. The cgroup-level limit is set via `pids.max` for processes/threads (covered in 02.01.02) and `memory.max` for memory (covered in 02.02.03); the analogous limit for FDs is `rlimit` in cgroup v2's `pids` controller (or the older cgroup v1 `devices` controller, which is more restrictive).

The standard production tuning for a database or load-balancer host is: per-process limit 65536 (or 1 million for very high-concurrency load balancers like Envoy or HAProxy), system-wide limit 2-4x the sum of per-process limits expected at peak. The sum is usually dominated by one or two big processes (the database, the load balancer), with many small processes (SSH daemons, monitoring agents, cron jobs) contributing little. For a Kubernetes node running 30 pods each with a 65536 limit, the math is 30 × 65536 = ~2 million, so the system-wide limit should be at least 4 million to leave headroom. The default 1.6 million is too low for this case, which is why production Kubernetes nodes always have `fs.file-max` raised in their node-image configuration.

```bash
# See the current system-wide limit and usage
$ cat /proc/sys/fs/file-max
1600000                       ← maximum open files system-wide

$ cat /proc/sys/fs/file-nr
1234    567    1600000
#       │     │     │
#       │     │     └── max (same as file-max)
#       │     └── pre-allocated (free, available for fast alloc)
#       └── allocated (currently open across all processes)

# So: 1234 files are open right now, 567 are pre-allocated for fast use,
# and the max is 1.6 million.  Plenty of headroom.

# Raise the limit temporarily
$ echo 4000000 | sudo tee /proc/sys/fs/file-max
4000000

# Raise the limit permanently
$ echo "fs.file-max = 4000000" | sudo tee -a /etc/sysctl.conf
$ sudo sysctl -p
fs.file-max = 4000000

# Find which processes are using the most FDs (system-wide hog identification)
$ for pid in /proc/[0-9]*; do
    p=$(basename $pid)
    count=$(ls $pid/fd 2>/dev/null | wc -l)
    echo "$count $p $(cat $pid/comm 2>/dev/null)"
  done | sort -rn | head -5
   5120  9012  java           ← system-wide hog
   1024  5678  nginx
    512  4231  postgres
    256  1234  redis-server
    128  4321  php-fpm

# Cgroup-level FD limit (cgroup v2)
$ cat /sys/fs/cgroup/system.slice/docker-<container_id>/pids.max
4096                          ← cgroup's process/thread limit (see 02.01.02)
# (There is no dedicated cgroup-level FD limit in cgroup v2 — FDs are
#  bounded by the per-process rlimit and the system-wide file-max.
#  Use rlimits in the container runtime to bound FDs per container.)

# Docker container with explicit FD limit
$ docker run --ulimit nofile=65536:65536 my-app
```

The connection to the upper layers is the deployment checklist. Every backend service in production should have: (1) `LimitNOFILE` set in its systemd unit (or `--ulimit nofile` in Docker, or `securityContext` in Kubernetes), (2) `fs.file-max` set high enough in `/etc/sysctl.conf` to accommodate the sum of per-process limits, (3) monitoring on `cat /proc/<pid>/fd | wc -l` with alerts at 70% and 90% of the limit. Without these, the service will work fine in development (low FD count) and fail in production (high FD count) — the classic "works on my machine" pattern. When you read the runtime notes in section 04, every runtime's production deployment guide includes these settings, and the failure mode of skipping them is always the same `EMFILE` error at the worst possible moment.

### File descriptor exhaustion failure mode (`EMFILE` - Too many open files) and recovery strategies

The `EMFILE` failure mode is the production incident every backend engineer dreads. The symptom is sudden, severe, and propagates quickly: the application starts returning errors on every request, the error log fills with `EMFILE` or `Too many open files` messages, and the service appears hung. The root cause is almost always a leak — the application is opening FDs (sockets, files, pipes) faster than it is closing them, and the count has climbed past the per-process limit. The first sign is usually `accept()` failing with `EMFILE` on the listening socket, which means the server cannot accept new connections — every client connection attempt times out. The second sign is `socket()` or `open()` failing inside the application, which usually surfaces as `java.net.SocketException` in Java, `Error: EMFILE` in Node, `OSError: [Errno 24]` in Python, or `fopen(): failed to open stream: Too many open files` in PHP.

The recovery procedure is well-defined but must be executed carefully. The immediate fix is to raise the per-process limit (`prlimit --nofile=65536:65536 --pid=<pid>` on Linux can do this on a running process, though the application must check the limit on each new FD allocation to benefit). The longer-term fix is to identify the leak: `ls /proc/<pid>/fd | wc -l` to confirm the count is at the limit, `ls -la /proc/<pid>/fd` to see what types of FDs are open, then read the application code (with the runtime's specific tooling — `jstack`, `process._getActiveHandles()`, etc.) to find what is not being closed. If the leak is in a connection pool, the fix is to add idle-eviction (close connections that have been idle for more than N seconds). If the leak is in subprocess spawning, the fix is to ensure every `Popen` / `ProcessBuilder.start` has a matching `wait()` / `waitFor()`. If the leak is in file handles, the fix is to use try-with-resources (Java) or `with` statements (Python) or `defer file.Close()` (Go) to guarantee closure.

The prevention strategy is layered. **Set the limit high enough** that you have time to detect and fix a leak before it causes an outage — 65536 is the standard for application servers, 1 million for high-concurrency load balancers. **Monitor the FD count** with Prometheus or Datadog, with alerts at 70% (warning) and 90% (critical) of the limit. **Use connection pools with bounded size and idle eviction** so the pool cannot grow without bound. **Use timeouts on every `accept()` and `connect()`** so a wedged peer cannot hold an FD indefinitely. **Test for leaks in CI** by running load tests against the application and asserting that the FD count returns to baseline after the test ends. **Use static analysis tools** (Spotbugs for Java, eslint for Node, pylint for Python) that flag obvious leak patterns (unclosed resources, missing `finally` blocks). The combination of high limits, monitoring, and leak prevention is the production recipe — no single one is sufficient.

```bash
# Diagnose EMFILE on a running process

# 1. Confirm the FD count is at the limit
$ cat /proc/<pid>/limits | grep "open files"
Max open files            1024                 4096                files
#                          ^^^^
#                          soft limit is 1024 — almost certainly the cause

$ ls /proc/<pid>/fd | wc -l
1024                          ← at the limit, confirmed

# 2. See what types of FDs are open
$ ls -la /proc/<pid>/fd | awk '{print $11}' | sed 's/\[[0-9]*\]//; s/[0-9]*//g' | sort | uniq -c | sort -rn | head

      3 /dev/pts/
      1 /var/log/app.log
```

The connection to the upper layers is the production-readiness checklist. Every runtime in section 04 has documented FD-limit settings: the JVM needs `-XX:-MaxFDLimit` to use the full system limit; Node has no internal cap but inherits the system limit; Python inherits the system limit; PHP-FPM inherits the system limit and uses it per-worker. The connection-pool libraries (HikariCP for Java, pg-pool for Node, SQLAlchemy for Python) all have explicit `maxSize` and `idleTimeout` configurations that bound FD usage. The connection-pool leak is the single most common cause of FD exhaustion in production — and the fix is always the same: bound the pool size, evict idle connections, monitor the FD count. When you read the runtime notes in section 04 and the persistence notes in section 06, every "connection pool" recommendation reduces to this FD-management story, and every "production deployment" checklist includes the `LimitNOFILE` setting that prevents the EMFILE incident.

## How This Connects to the Runtimes

Every runtime covered in section 04 is a user-space wrapper around these kernel primitives:

- **JVM**: Maps Java threads 1:1 to OS threads via NPTL. The JVM's memory model (section 04.01) is a specification layered on top of the kernel's virtual memory system described here.
- **Node.js / libuv**: The event loop (section 04.02) is a Reactor pattern built on `epoll_wait()`. The worker thread pool uses OS threads for operations that cannot be multiplexed (file I/O, DNS, crypto).
- **CPython**: The GIL (section 04.03) is a mutex that serializes Python bytecode execution across OS threads. Multi-processing in Python uses `fork()` to bypass the GIL.
- **PHP-FPM**: Each worker is a separate OS process (section 04.04). The shared-nothing model is a direct consequence of the process isolation described in the Linux Process Model note.

When you read those runtime notes, come back here and trace which kernel primitive each runtime feature maps to.
## Hands-On Exercise

Open a terminal on a Linux machine and run the following commands to see these concepts in action:

```bash
# See process states
ps -eo pid,stat,comm | head -20

# See context switches per second
vmstat 1 5

# See file descriptors for a process — the most important command for this note
ls -la /proc/$$/fd

# See memory layout of a running process
cat /proc/self/maps | head -20

# See socket states
ss -tan state established | head

# Inspect per-process and system-wide FD limits
ulimit -n
ulimit -Hn
cat /proc/<pid>/limits | grep "open files"
cat /proc/sys/fs/file-max
cat /proc/sys/fs/file-nr

# Find the system-wide FD hog
for pid in /proc/[0-9]*; do
  p=$(basename $pid)
  count=$(ls $pid/fd 2>/dev/null | wc -l)
  echo "$count $p $(cat $pid/comm 2>/dev/null)"
done | sort -rn | head -5

# Use lsof for cross-process queries
lsof -p $$ | head
lsof -i :80
```

Correlate each output with the bullets above. If you cannot match a row in the output to a concept in this note, re-read the relevant section.
