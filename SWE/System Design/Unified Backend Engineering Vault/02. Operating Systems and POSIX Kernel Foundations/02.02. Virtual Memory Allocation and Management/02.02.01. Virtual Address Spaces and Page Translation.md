# 02.02.01. Virtual Address Spaces and Page Translation

## What This Is

**Virtual Address Spaces and Page Translation** is the load-bearing primitive that makes process isolation, memory overcommit, copy-on-write `fork`, memory-mapped files, and lazy heap allocation possible. Every backend runtime — the JVM's heap, V8's isolate heap, CPython's `pymalloc` arena, the Zend Engine's `emalloc` arena — is layered on top of this mechanism. The reason this note sits in section 02 is that every "why does my container OOM at 2 GB when it should be using 500 MB?" question, every "why is my JVM heap RSS 4x the Xmx value?" question, and every "why does `fork()` not actually copy 4 GB of memory?" question reduces to the kernel's virtual memory machinery. The four-level page table, the TLB cache, the minor-vs-major page fault distinction, and the `mmap` semantics are the substrate on which every higher-level allocator is built.

The mental model is: each process sees a private, contiguous, 48-bit virtual address space (256 TB on x86-64), as if it had its own private RAM the size of a small data center. The kernel translates each virtual address the process touches into a physical RAM address using a per-process page table. Because the translation is per-process, two processes can both think they have a variable at address `0x4000` and the kernel will silently route them to different physical frames. Because the translation is granular (4 KB pages), the kernel can mark individual pages as read-only, no-execute, copy-on-write, swap-backed, file-backed, or huge — giving it the control surface for every memory feature POSIX offers. This note walks through the data structure, the cache, the fault types, and the failure modes that production engineers hit.

## The Details

### Physical Memory (RAM) vs. Virtual Memory: Memory isolation, security boundaries, and address spaces

Physical RAM is a flat array of cells, indexed by physical address, shared by every CPU core and every device on the memory bus. If user-space programs addressed physical memory directly, two processes could (and would) overwrite each other's data, a buggy driver could corrupt the kernel, and a malicious program could read another process's secrets by simply loading from the right physical address. Virtual memory solves all three problems by giving each process its own private virtual address space and translating every memory access through a per-process page table. The translation is enforced in hardware by the MMU (Memory Management Unit) on every load and store — there is no user-space escape hatch, no "raw physical access" syscall, no way to bypass the page table from user-space. The kernel itself is mapped into every process's address space (the upper 128 TB of the 47-bit user-space hole, or `CONFIG_X86_5LEVEL` for 56-bit), but mapped with supervisor-only permissions so user-space code cannot read or write it.

The isolation boundary is the page table itself. Each process has its own PGD (Page Global Directory), the root of its page table tree, and the physical address of that PGD is stored in the `mm_struct->pgd` field of the process's `task_struct`. When the scheduler switches from process A to process B, it loads B's PGD physical address into the `CR3` register — this single register write is what switches the entire virtual-to-physical mapping for the CPU. From that point on, every virtual address the CPU issues is translated through B's page tables, not A's. This is the architectural fact that makes process isolation cheap: no copying of memory, no per-process memory mapping API, just a single CR3 write on context switch. (The cost of that write — TLB flush — is covered in 02.01.03.)

The security boundary is enforced by permission bits in each page-table entry (PTE). Every PTE has three relevant permission bits: `R/W` (read-only or read-write), `U/S` (user or supervisor), and `NX` (no-execute). The kernel checks these on every memory access: a user-space store to a read-only page triggers a fault, a user-space load from a supervisor page triggers a fault, a user-space instruction fetch from an NX page triggers a fault. These checks are what make buffer overflows hard to exploit (the stack and heap are typically NX), what prevent user-space from reading kernel memory (every kernel PTE has U/S=supervisor), and what allow `mprotect` to mark pages read-only for copy-on-write or for security hardening. The most important modern hardening is **ASLR (Address Space Layout Randomization)** — the kernel randomizes the base address of the executable, the heap, the libraries, the stack, and (with `mmap`'s `MAP_RANDOMIZED` or just by leaving the address NULL) every mmap region. ASLR does not change the page-table structure; it changes where in the virtual address space things are placed, so that an attacker who finds a buffer overflow cannot predict the address of useful code (like libc's `system()` function).

The connection to the upper layers is direct: the JVM's `-Xms` and `-Xmx` are mmap calls that reserve a contiguous virtual range for the Java heap; the JVM then commits and protects individual pages within that range as objects are allocated and GC moves them around. CPython's `pymalloc` calls `mmap` for arenas (256 KB each). Redis's `zmalloc` uses `mmap` for the `jemalloc` arena. Every runtime heap is a layer of policy on top of `mmap`, and every runtime GC is a layer of policy on top of `mprotect` (to find live objects, GC may protect pages and catch the SIGSEGV) and `madvise` (to hint to the kernel that a page is no longer needed). When you read the runtime notes in section 04, the first thing to understand about each runtime's memory model is how it uses these three syscalls (`mmap`, `mprotect`, `madvise`) to build its abstraction on top of the kernel's page table.

### Memory Paging Architecture: Pages (4KB default) and Page Frames in physical memory

Memory is divided into fixed-size **pages** — the unit of allocation, protection, and transfer between RAM and disk. On x86-64 the default page size is 4 KB (4096 bytes), chosen in the early 1990s as a tradeoff between internal fragmentation (smaller pages waste less memory in slack space) and TLB coverage (larger pages cover more address space per TLB entry). The kernel also supports **huge pages** of 2 MB and 1 GB on x86-64, which trade internal fragmentation for drastically reduced TLB pressure — a 1 GB huge page replaces 262,144 4 KB PTEs with a single PMD entry, which is why databases with multi-GB working sets (PostgreSQL, Oracle) and large JVM heaps (anything > 4 GB) almost always benefit from huge pages.

Physical RAM is divided into **page frames** of the same size, and the page table maps virtual pages to physical frames. The mapping is many-to-one in the sense that multiple virtual pages from multiple processes can map to the same physical frame (this is how shared memory works, how `fork`'s copy-on-write works, and how `mmap` of a file works). The kernel maintains a `struct page` for every physical frame (in the `vmemmap` array) — this is roughly 64 bytes of metadata per 4 KB frame, or 1.6% of physical RAM, which is why the kernel's `memmap` overhead on a 1 TB server is ~16 GB. Each `struct page` tracks the frame's reference count, its current owner (which process or the page cache), its position on an LRU list, and its current state (free, active, inactive, dirty, writeback, swap-backed, etc.).

A virtual address on x86-64 is split into the page number (the high bits) and the page offset (the low 12 bits for 4 KB pages). The CPU uses the page number to look up the translation in the page table; the offset is concatenated with the resulting physical frame number to form the physical address. The split is what makes 4 KB pages work — every address within a page translates through the same PTE, so the translation is done once per page, not once per byte. This is why `printf` of a 4 KB buffer is one translation, not 4096 translations.

The connection to the upper layers is the huge-page story. A JVM with a 32 GB heap on 4 KB pages needs 8 million PTEs to cover it — that is 16,000 TLB entries worth of address space (a typical TLB has ~1,000 entries for 4 KB pages). The TLB cannot hold that, so almost every heap access becomes a TLB miss, costing 100-400 ns each, which adds up to tens of milliseconds of pure TLB-refill time per GC cycle. The same JVM on 2 MB huge pages needs only 16,000 PMD entries — fits in the L1 TLB entirely, and the heap accesses are TLB hits. This is why `+UseLargePages` (Java), `large_pages = on` (PostgreSQL), and `--enable-huge-pages` (Redis) are standard production tuning for memory-heavy workloads, and why the Linux kernel's Transparent Huge Pages (THP) feature exists to do this automatically — though THP has its own pitfalls (it can cause latency spikes when it defragments memory in the background, which is why many production setups disable THP and use explicit huge pages instead).

### Multi-Level Page Tables on x86-64: PGD, P4D, PUD, PMD, and PTE structures

A single-level page table for a 48-bit address space with 4 KB pages would need 2^36 entries (one per page) × 8 bytes each = 512 GB of page table per process — obviously infeasible. The multi-level page table solves this by being sparse: only the portions of the address space that are actually used have page-table entries, and the rest is just a NULL pointer at the top level. On x86-64 with 4 KB pages, the standard configuration is four levels: PGD → PUD → PMD → PTE, each level being a 4 KB page containing 512 8-byte entries, indexed by 9 bits of the virtual address. Each level's entry points to the physical address of the next level's page (or, in the case of the PTE, to the physical frame of the actual data). A virtual address is split into 4 × 9-bit indices + a 12-bit offset, which is exactly 48 bits — the architectural limit of x86-64's user-space address space.

The four levels can be extended to five (PGD → P4D → PUD → PMD → PTE) on CPUs that support 57-bit virtual addresses (Intel's 5-level paging, available since Cascade Lake server CPUs in 2017, enabled via `CONFIG_X86_5LEVEL`). Five-level paging extends the address space from 256 TB to 128 PB per process — relevant only for in-memory databases and ML training workloads that genuinely need petabyte address spaces. The kernel maintains API compatibility by always exposing a P4D level (on 4-level systems, P4D is a no-op that always has a single entry covering the whole PGD), so the kernel code is the same regardless of CPU support.

The "present" bit in each page-table entry is what makes this multi-level scheme memory-efficient. If a PUD entry has its present bit clear, the kernel does NOT allocate the PMD page that entry would point to — the entire 1 GB region it represents is unmapped, costing zero bytes of page-table memory. Only the regions of the address space that are actually mapped (the text segment, the heap, the stack, the loaded libraries, the mmap regions) consume page-table memory, and that memory is proportional to the number of distinct 4 KB pages touched, not the size of the address space. A process with a 256 TB virtual address space (because it called `mmap` with a NULL hint and got an address near the top of the range) but only 100 MB of actual mapped data uses roughly 100 MB / 2 MB (the PMD coverage) = 50 PMD pages = 200 KB of page-table memory, not 512 GB.

```text
Memory cost of multi-level page tables (4-level, 4 KB pages)

A fully-mapped 48-bit address space would need:
   1 PGD page  (4 KB)
   512 PUD pages  (2 MB)

This is exactly what `Vmalloc` / `vmstat`'s "page tables" field reports.
```

The connection to the upper layers is the page-table-walk cost. Every TLB miss triggers a four-deep memory walk, and each step is itself a memory access that may miss in L1/L2/L3. On a modern CPU with a 100 ns DRAM latency, a worst-case page-table walk is 400 ns. This is the fundamental reason TLB hit rate matters so much, and the reason huge pages matter — they collapse the walk to two levels (PGD → PMD-huge) instead of four, and they cover 512x as much address space per TLB entry. When the JVM's GC pauses correlate with `perf stat` showing TLB misses at 5% of instructions, the fix is almost always to enable huge pages — not to tune the GC. Every runtime in section 04 inherits this cost; the runtime cannot tune it away; only the kernel can.

### The Translation Lookaside Buffer (TLB): Hardware caching of virtual-to-physical address mappings

The **Translation Lookaside Buffer (TLB)** is a small, very fast hardware cache inside the CPU that stores recent virtual-to-physical translations. Every load and store instruction first checks the TLB; if the translation is present (TLB hit, ~1 cycle), the load proceeds immediately; if not (TLB miss), the MMU walks the page table in memory (100-400 ns), inserts the result into the TLB (possibly evicting an older entry), and the load finally proceeds. Because every memory access requires a translation, the TLB hit rate is one of the single most important performance numbers for any memory-intensive workload — and the TLB's small size (typically 64-1024 entries) means it is easy to exhaust on large working sets.

Modern x86 CPUs split the TLB into multiple levels and by page size. A typical Intel server CPU has: an L1 dTLB (data) of 64 entries for 4 KB pages and 32 entries for 2 MB pages; an L1 iTLB (instruction) of 128 entries for 4 KB pages and 8 entries for 2 MB pages; an L2 STLB (second-level, shared between instruction and data) of 1536-2048 entries for 4 KB pages and 16-32 entries for 2 MB pages. The effective coverage is therefore: 64 × 4 KB = 256 KB at L1, 32 × 2 MB = 64 MB at L1 with huge pages, 2048 × 4 KB = 8 MB at L2, 32 × 2 MB = 64 MB at L2 with huge pages. A workload with a 1 MB working set fits comfortably in the L2 TLB; a workload with a 100 MB working set is TLB-miss-bound on 4 KB pages but fine on huge pages; a workload with a 32 GB working set (like a JVM heap) is TLB-miss-bound even on huge pages unless the access pattern is sequential (which lets the prefetcher hide the latency).

The TLB is flushed on every process context switch because the translations belong to the previous process's page table — the kernel writes the new PGD address into CR3, and the hardware invalidates the entries that do not have the "Global" bit set. The kernel's pages have the Global bit set, so they survive context switches (which is why the kernel mapping is identical in every process's page table). User-space pages do not, so they are evicted on every switch. This is the dominant cost of process-process context switches, as covered in 02.01.03. The hardware mitigation is **PCID (Process Context Identifier)**, a feature that tags each TLB entry with a 12-bit process ID, so the hardware can keep multiple processes' TLB entries resident simultaneously and only flush entries for the specific PCID being evicted. PCID is enabled by default on modern Intel CPUs and is exposed in `/proc/cpuinfo` as the `pcid` flag.

```bash
# Confirm PCID and other TLB-related CPU features
$ grep -E " pcid | invpcid " /proc/cpuinfo | head -1
flags: ... pcid invpcid ...

# Measure TLB miss rate for a workload
$ perf stat -e dTLB-load-misses,iTLB-load-misses,instructions \
            ./your_memory_bound_program 2>&1 | tail -8
   1,234,567,890      instructions
      45,678,901      dTLB-load-misses          # 3.7% of instructions
          123,456      iTLB-load-misses          # 0.01% of instructions

# 3.7% dTLB miss rate at 3 GHz = ~17 ms/sec of pure TLB-refill cost
# (3e9 × 0.037 × 150ns avg page-table walk ÷ 1e9 ns/s = 16.65 ms/s)

# Use huge pages to drop this — measure again
$ sudo hugeadm --pool-pages-min 2048KB:200      # reserve 200 2 MB huge pages
$ LD_PRELOAD=libhugetlbfs.so HUGETLB_MORECORE=yes ./your_memory_bound_program

   1,234,567,890      instructions
         567,890      dTLB-load-misses          # 0.046% — 80x reduction
```

The connection to the upper layers is that **TLB miss rate is the single most overlooked performance metric in backend engineering.** Most engineers monitor CPU utilization, memory utilization, GC pauses, request latency — but never TLB miss rate. The result is that "unexplained" 100 ms latency spikes on JVM workloads are often TLB-refill storms during GC compaction (the compaction moves objects, invalidating TLB entries, and the subsequent re-accesses all miss). The fix is huge pages, both at the JVM level (`-XX:+UseLargePages` or `-XX:+UseTransparentHugePages`) and at the OS level (`echo always > /sys/kernel/mm/transparent_hugepage/enabled` for THP, or explicit `nr_hugepages` for pinned huge pages). When you read the runtime notes in section 04, every runtime with a multi-GB heap (JVM, V8 with `--max-old-space-size`, Redis with `maxmemory`) has a documented huge-page tuning recommendation, and the recommendation exists for exactly this reason.

### Page Faults: Minor (Page present in RAM, PTE unmapped) vs. Major (Page read from disk swap/file)

A **page fault** is the kernel's mechanism for lazily materializing memory. When a process accesses a virtual address whose PTE is not present (the "present" bit is 0), the MMU raises a page-fault exception. The kernel's page-fault handler (`do_page_fault` on x86) inspects the faulting address, determines why the PTE was not present, and either maps the page (a minor fault) or loads it from disk (a major fault) and then maps it. The fault is invisible to user-space — the instruction that faulted is replayed after the kernel has fixed the mapping, and the process continues as if nothing happened. This lazy materialization is what makes `mmap(NULL, 1 GB, ...)` instant — the 1 GB is reserved in the page table as a VMA, but no physical pages are allocated until the process touches them.

A **minor page fault** (also called a soft fault) is one where the page is already in physical RAM but the PTE is missing. This happens in three common situations: (1) the process touches a page for the first time after `mmap` (the kernel zero-fills a fresh page from the zero-page pool and inserts the PTE), (2) the process writes to a copy-on-write page after `fork` (the kernel allocates a new physical page, copies the original, and remaps), (3) the process accesses a page that was previously freed but is still in the page cache (e.g., a memory-mapped file whose page was evicted to the page cache, then re-referenced — no disk I/O needed). Minor faults are cheap — typically 1-5 µs — because no disk I/O is involved. A freshly-started JVM will register millions of minor faults as it touches its heap, the loaded bytecode, and the metaspace; this is normal and expected.

A **major page fault** (also called a hard fault) is one where the page must be read from disk. This happens when (1) the page was swapped out to the swap partition and is being brought back in, (2) the page belongs to a memory-mapped file and was evicted from the page cache, or (3) the page is being demand-paged from an executable or shared library that has not yet been loaded. Major faults are catastrophic for latency — typically 50-100 µs for an NVMe SSD, 1-10 ms for a SATA SSD, 5-20 ms for an HDD, and 10-100 ms for a network filesystem (NFS, EBS). A single major fault during a request adds 10 ms to the p99; a hundred major faults during a request adds a full second. This is why production databases spend enormous effort avoiding them: PostgreSQL's `shared_buffers` and MySQL's `InnoDB buffer pool` exist precisely to keep hot data in RAM so that query execution never triggers a major fault, and the `vmstat`'s `majflt` column is one of the first things a DBA looks at when query latency spikes.

The connection to the upper layers is the operational rule: **major page faults are the single most common cause of unexplained latency spikes in production backend systems.** When a JVM has been idle for hours and suddenly receives a request, the first request triggers major faults on every code and data page that was evicted; p99 latency for that first request is hundreds of milliseconds, even though the steady-state p99 is 2 ms. The mitigations are workload-specific: for databases, size `shared_buffers` to hold the working set and pre-warm it on startup (`pg_prewarm` extension); for JVMs, use `-XX:+AlwaysPreTouch` to touch every heap page on startup (eliminating the gradual RSS climb at the cost of slower startup); for hot services, configure `mlockall` to lock the hot pages into RAM and prevent the kernel from evicting them under memory pressure. When you read the runtime notes in section 04, every runtime's startup behavior is shaped by these choices, and every "the first request after deploy is slow" incident traces back to a major-fault storm.

## How This Connects to the Runtimes

Every runtime covered in section 04 is a user-space wrapper around these kernel primitives:

- **JVM**: Maps Java threads 1:1 to OS threads via NPTL. The JVM's memory model (section 04.01) is a specification layered on top of the kernel's virtual memory system described here.
- **Node.js / libuv**: The event loop (section 04.02) is a Reactor pattern built on `epoll_wait()`. The worker thread pool uses OS threads for operations that cannot be multiplexed (file I/O, DNS, crypto).
- **CPython**: The GIL (section 04.03) is a mutex that serializes Python bytecode execution across OS threads. Multi-processing in Python uses `fork()` to bypass the GIL.
- **PHP-FPM**: Each worker is a separate OS process (section 04.04). The shared-nothing model is a direct consequence of the process isolation described in the Linux Process Model note.

When you read those runtime notes, come back here and trace which kernel primitive each runtime feature maps to.
