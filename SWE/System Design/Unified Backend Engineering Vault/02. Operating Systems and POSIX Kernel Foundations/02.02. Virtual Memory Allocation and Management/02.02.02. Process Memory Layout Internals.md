# 02.02.02. Process Memory Layout Internals

## What This Is

**Process Memory Layout Internals** is the next layer up from 02.02.01: where that note covered the page-table machinery that translates virtual addresses to physical frames, this note covers the higher-level regions the kernel carves out of a process's virtual address space and what each one is for. Every backend runtime's memory model is a layer of policy on top of these regions — the JVM's heap is a large `mmap`-backed region inside the mmap segment, V8's isolate heap is another mmap region inside the same segment, CPython's `pymalloc` arenas are 256 KB mmap chunks, and PHP's `emalloc` pool lives in the heap. You cannot read `/proc/<pid>/maps` usefully without knowing what each segment is, and you cannot debug a "RSS is 4x the heap size" incident without knowing which segment is responsible.

The reason this note sits in section 02 is that the segment layout is the contract between the linker (`ld`), the kernel's ELF loader, and every runtime that comes after. The kernel loads the ELF, maps the text/`.data`/`.bss` segments at fixed (or ASLR-randomized) addresses, sets up the stack at the top of the user-space address range, and hands the rest of the address space to `mmap` and `brk`. Everything a runtime does — every `malloc`, every `new Object()`, every thread stack, every JITted code buffer, every shared library — is carved out of one of these regions. This note walks through the segment breakdown, the stack, the heap, and the mmap region, then shows what the layout looks like for a JVM process and a Node process to make it concrete.

## The Details

### Segment breakdown: Text (Executable Code), Initialized Data (`.data`), Uninitialized Data (`.bss`), Heap, Memory Mapping Segment, and Stack

A Linux process's virtual address space is divided into six canonical regions, each with a different purpose, permission set, and growth direction. The layout is established by the kernel's ELF loader (`fs/binfmt_elf.c`) at `execve` time, and it is exposed for any running process via `/proc/<pid>/maps`. The six regions are: the **text segment** (the executable's machine code, mapped read-only and executable, shared across processes that exec the same binary), the **initialized data segment** (`.data`, holding global and static variables with non-zero initial values, mapped read-write), the **uninitialized data segment** (`.bss`, holding global and static variables that are zero-initialized — the kernel zero-fills these on demand, so the on-disk ELF has no `.bss` content), the **heap** (grows upward from the end of `.bss` via `brk`/`sbrk`, used by `malloc` for small allocations), the **memory mapping segment** (grows downward from a randomized base near the middle of the address space, used by `mmap` for large allocations, shared libraries, file-backed mappings, and thread stacks), and the **stack** (grows downward from the top of the user-space address range, used for function call frames).

The text/`.data`/`.bss` segments come straight from the ELF file's program headers (`PT_LOAD` entries). The kernel maps each `PT_LOAD` segment with the permissions specified in the header — typically `r-x` for text (read + execute), `rw-` for `.data` and `.bss` (read + write), and `r--` for read-only data like string literals. The kernel's loader also maps the dynamic linker (`ld-linux.so`) and processes the `PT_INTERP` header to find it. Every shared library loaded by `ld-linux` (`libc.so.6`, `libpthread.so`, `libz.so`, etc.) becomes another set of text/`.data`/`.bss` mappings in the mmap segment. ASLR randomizes the base address of the executable (if compiled with `-pie`), the libraries (always), the heap base, the mmap base, and the stack base — so the same binary run twice will have different addresses in `/proc/maps`, which is why attackers cannot hard-code addresses in exploits.

The heap and the mmap segment are the two regions that grow dynamically at runtime, and they grow in opposite directions to avoid colliding. The heap grows upward via `brk(addr)` (or the older `sbrk(increment)`), which simply moves the "program break" — the boundary between committed heap and unallocated address space — to a higher address. The mmap segment grows downward: each new `mmap` call gets an address below the previous one (the kernel uses a randomized "mmap base" and a per-thread `mmap_cache` to find free space efficiently). The two regions meet in the middle of the address space, which is why a process with a 1 TB heap reservation (a JVM with `-Xmx1t`) and a 100 GB mmap usage does not collide — the heap is at the bottom of the address space and the mmap region is in the middle, with hundreds of TB of room between them.

The connection to the upper layers is the JVM-vs-Node-vs-Python layout story. A JVM process has all six standard regions, plus an enormous `mmap`-backed heap (visible in `/proc/maps` as a single huge anonymous mapping) and a separate `mmap`-backed metaspace (visible as another, smaller anonymous mapping). A Node process has the standard regions plus V8's old-space heap (anonymous mmap) and new-space heap (smaller anonymous mmap) and a libuv thread-pool stack region (one stack per worker thread). A Python process has the standard regions plus a `pymalloc` arena region (multiple 256 KB anonymous mmaps). Every runtime's `/proc/maps` output tells you exactly what the runtime is doing in memory; learning to read it is the single most useful diagnostic skill for memory leaks, because RSS without `/proc/maps` is just a number.

### The Stack: Stack frames, Base Pointer (`%rbp`), Stack Pointer (`%rsp`), local variables, return addresses, and Stack Overflow exploits

The stack is a LIFO data structure that grows downward (from high addresses to low addresses) and holds one entry per active function call — the **stack frame**. Each frame contains the function's local variables, the saved frame pointer of the caller, the return address (where to jump back to when this function returns), and any register values the function needs to preserve across calls. On x86-64 the convention is: `RSP` (stack pointer) points to the top of the stack (the lowest address in use); `RBP` (base pointer) points to the saved RBP of the caller, marking the start of the current frame; the function's local variables are at negative offsets from RBP; the function's arguments (for arguments beyond the first six, which are passed in registers) are at positive offsets from RBP. The function prologue does `push %rbp; mov %rsp, %rbp; sub $N, %rsp` to set up its frame, and the epilogue does `mov %rbp, %rsp; pop %rbp; ret` to tear it down.

The stack's size is bounded — default 8 MB on Linux, configurable via `ulimit -s` or `RLIMIT_STACK`. When a function's locals plus call depth exceed this limit, the kernel raises `SIGSEGV` — the classic **stack overflow**. The kernel implements this protection by mapping a 4 KB guard page at the bottom of the stack VMA with `PROT_NONE`, so the first access beyond the limit triggers a page fault that the kernel resolves by sending SIGSEGV. This is why infinite recursion produces a SIGSEGV rather than corrupting memory silently. The default 8 MB is generous; deep recursion in C is fine, but in languages with bigger frames (Java's HotSpot uses 1 MB by default; Go uses 2 KB initial goroutine stacks that grow on demand) the limit is tighter and stack overflows happen more easily. JVM thread stacks are also bounded by `-Xss` (default 1 MB on HotSpot), so a JVM thread that recurses too deeply throws `StackOverflowError` rather than SIGSEGV — but the underlying mechanism is the same guard-page trick.

The **stack overflow exploit** is the canonical security vulnerability that stack protection mechanisms defend against. The classic attack: a C function uses `gets()` (or `strcpy()` without bounds checking) to read user input into a stack-allocated buffer; the attacker sends more bytes than the buffer holds; the overflow corrupts the adjacent stack frame, including the saved return address; when the function returns, it jumps to an address the attacker chose. Modern defenses are layered: **stack canaries** (the compiler inserts a random value between the locals and the saved return address; if the canary is corrupted on function return, the program aborts via `__stack_chk_fail`), **NX stack** (the stack is mapped `rw-`, not `rwx`, so even if the attacker writes executable code to the stack, the CPU refuses to execute it), **ASLR** (the stack base address is randomized, so the attacker cannot predict where their injected code will land), and **PIE** (the executable itself is position-independent, so function addresses are also randomized). The combination makes classic stack-smashing extremely difficult on modern Linux — but the underlying layout (locals below saved RBP below return address) has not changed since the 1970s.

The connection to the upper layers is the **thread stack** story. Every OS thread has its own stack, allocated from the mmap region (not the [heap] segment — that is only for the main thread's brk-heap). A JVM with 200 platform threads has 200 separate 1 MB stack VMAs in its mmap segment; a Node.js process with a libuv pool of 4 workers has 4 worker stacks plus the main thread stack; a Python `threading.Thread` default stack is 8 MB. The total stack memory footprint is `num_threads × stack_size`, which is why the thread count × stack size math of 02.01.02 dominates the memory budget of high-concurrency 1:1 servers. Go's goroutines and Java's virtual threads sidestep this by allocating tiny (2 KB / 512 byte) stacks from the heap and growing them on demand — the same call-depth semantics at 1000x less memory.

### The Heap: Dynamic runtime allocation, heap growth toward high memory, and the program break (`brk`/`sbrk`)

The heap is the region used for dynamically-allocated memory whose lifetime is controlled by the program — every `malloc()` / `free()`, every `new` / `delete`, every `pymalloc` arena. On Linux the heap is bounded below by the end of the `.bss` segment and grows upward via the `brk(addr)` syscall, which moves the **program break** — the boundary between the committed heap region and the unallocated address space above it. The historical `sbrk(increment)` is a libc wrapper that calls `brk(current_break + increment)` and returns the previous break. The kernel simply extends the heap VMA: it does not allocate physical pages immediately, but the next time the process writes to an address within the new VMA range, the page-fault handler zero-fills a physical page and inserts the PTE. This lazy growth is what makes `sbrk(1 GB)` instant — the 1 GB is reserved in the page table but no RAM is consumed until touched.

The heap is exclusively owned by `malloc` in a simple C program: `malloc` calls `brk` to extend the heap when its free lists are exhausted, and `free` does NOT return memory to the kernel by lowering the break — instead, `free` adds the block to its free list for future `malloc` calls. This is why the heap's RSS tends to grow monotonically and never shrink: once the break is raised, it stays raised. The only way to lower the break is for `malloc` to detect that the top of the heap is a large contiguous free region (which only happens if the program frees everything it recently allocated) and explicitly call `brk` to shrink. Modern `malloc` implementations (glibc's ptmalloc2) do this for sufficiently large frees at the top, but in practice the heap's high-water mark is sticky — a process that allocates 1 GB and frees it will see the break remain at 1 GB for the rest of its life. This is one of the two reasons `malloc` falls back to `mmap` for large allocations (see 02.02.03): an mmap'd region can be un-mapped entirely on free, returning the address space and the RSS.

The heap is also where every runtime's allocator starts before it migrates to mmap. CPython's `pymalloc` uses `malloc` for objects larger than 512 bytes (so they end up in the brk-heap or in an mmap chunk if large), and uses its own arena allocator for smaller objects (the arenas themselves are 256 KB chunks obtained via `mmap`). The JVM uses `mmap` for the Java heap (it must, because the heap is huge and needs to be physically contiguous-ish), and `malloc` for native allocations (JNI, JVM internals, JIT code cache). PHP's `emalloc` (engine malloc) uses the brk-heap for the per-request arena, which is freed en masse at request end — this is the shared-nothing model that gives PHP its memory-leak immunity. Node's V8 heap is mmap-backed, but V8's external allocations (Buffers, native objects) go through libuv's `malloc`.

The connection to the upper layers is the operational rule: **the heap is small allocations only; everything large goes through mmap.** This matters because the heap cannot be returned to the kernel easily, while mmap regions can. A JVM that allocates and frees a 100 MB byte array in a tight loop will not leak heap RSS (the array is mmap-backed); a Python script that does the same with `bytearray(100*1024*1024)` may leak RSS if the bytes end up in the brk-heap (depending on whether `pymalloc` chose mmap or brk for that size class — for >512 byte objects CPython falls through to `malloc`, which uses mmap for >128 KB by default, so the bytearray goes through mmap and is properly returned on `del`). This single fact — the brk-vs-mmap threshold — is the most overlooked allocator behavior in backend engineering, and it is covered in detail in 02.02.03.

### Memory Mapping via `mmap()`: Anonymous memory allocation, memory-mapped file I/O, and shared memory allocations

`mmap()` is the most general-purpose memory allocation syscall in POSIX. It maps a region of a file (or an anonymous region backed by swap space) into the process's virtual address space, returning a pointer the process can use to read and write the data. Three flavors dominate backend engineering. **Anonymous mmap** (`MAP_ANONYMOUS | MAP_PRIVATE`) allocates a chunk of zero-filled memory that is not backed by any file — this is what `malloc` uses for large allocations and what runtimes use for their heaps. **File-backed mmap** (`mmap(fd, len, PROT_READ|PROT_WRITE, MAP_SHARED, offset)`) maps a file's contents directly into memory; reads become pointer dereferences (the kernel pages in the file on demand), and writes (if `MAP_SHARED`) propagate back to the file via the page cache. **Shared memory mmap** (`shm_open` followed by `mmap(MAP_SHARED)`) creates a region that multiple processes can map simultaneously — the same physical frames back the mappings in every process, so writes by one are visible to all (with synchronization required).

The `mmap` syscall signature is `mmap(addr, length, prot, flags, fd, offset)`. The `addr` is a hint — pass NULL to let the kernel pick (recommended, especially under ASLR); pass a non-NULL address to request a specific location (the kernel will try to honor it but may not). The `length` is the size of the region to map (rounded up to a page boundary). The `prot` is `PROT_READ`, `PROT_WRITE`, `PROT_EXEC`, or `PROT_NONE` (combined with `|`). The `flags` are where the real choice happens: `MAP_PRIVATE` (copy-on-write — writes are private to this process and do not affect the file or other mappings), `MAP_SHARED` (writes propagate to the file and to other `MAP_SHARED` mappings of the same file), `MAP_ANONYMOUS` (no file backing), `MAP_FIXED` (require the exact address — dangerous, can overwrite existing mappings silently), `MAP_HUGETLB` (use huge pages), `MAP_POPULATE` (pre-fault all pages — useful for latency-sensitive workloads where you cannot afford the page-fault cost later), `MAP_NORESERVE` (do not reserve swap space — risky, can cause SIGKILL if memory is exhausted), `MAP_LOCKED` (lock the pages into RAM, equivalent to calling `mlock` on the result).

The two flavors of mmap that matter most for backend engineering are **anonymous mmap** (the runtime heap primitive) and **file-backed mmap** (the database primitive). Anonymous mmap is what the JVM uses to allocate the Java heap: `mmap(NULL, 32 GB, PROT_READ|PROT_WRITE, MAP_PRIVATE|MAP_ANONYMOUS|MAP_HUGETLB, -1, 0)`. File-backed mmap is what databases like SQLite and LMDB use to access their data files: instead of `read()`-ing pages into a buffer cache, they `mmap` the entire file and let the kernel's page cache do the work. The advantage of file-backed mmap is that there is no user-space buffer copy — the page in the page cache IS the page the application reads, mapped directly into its address space. The disadvantage is that page faults become a kernel concern (a slow disk can stall the application in `D` state), and writing to a mmap'd file is asynchronous (the dirty pages are written back by the kernel's flusher threads, so a crash can lose data unless you `msync`).

```c
/* mmap examples — the three flavors that matter for backend engineering */

#include <sys/mman.h>
#include <sys/stat.h>
#include <fcntl.h>
#include <unistd.h>

/* 1. Anonymous mmap — what malloc does for large allocations. */
void *p = mmap(NULL, 64 * 1024 * 1024,             /* 64 MB */
               PROT_READ | PROT_WRITE,
               MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
/* No physical memory is committed until you touch the pages. */
memset(p, 0, 64 * 1024 * 1024);                   /* forces commit */
munmap(p, 64 * 1024 * 1024);                      /* returns to kernel immediately */

/* 2. File-backed read-only mmap — what SQLite does for SELECT. */
int fd = open("database.sqlite", O_RDONLY);
struct stat st;  fstat(fd, &st);
void *db = mmap(NULL, st.st_size, PROT_READ, MAP_SHARED, fd, 0);
/* db[0] is the first byte of the file; db[st.st_size - 1] is the last.
   Page faults bring in 4 KB chunks on demand. */
close(fd);
/* (do not unmap until done — and call msync if you wrote, which you did not here) */

/* 3. Shared memory between processes — what Redis-style IPC could use. */
int fd = shm_open("/my_region", O_CREAT | O_RDWR, 0600);
ftruncate(fd, 4096);                              /* set the size */
void *shared = mmap(NULL, 4096, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
/* Any process that opens /my_region and mmaps it sees the same memory. */
/* Synchronization required: a pthread_mutex with pshared attr, or a
   semaphore, or an atomic flag with appropriate memory_order. */
```

The connection to the upper layers is the mmap-vs-read/write choice that every database and every runtime makes. SQLite and LMDB and a few other databases mmap their data files directly (file-backed mmap) and let the kernel page cache manage the working set — this is simplest and leverages the kernel's existing page-replacement logic, but it gives up control over eviction and is vulnerable to page-fault stalls. PostgreSQL and MySQL's InnoDB use `pread`/`pwrite` into their own buffer pools (anonymous mmap for the buffer pool, plus `read`/`write` to move data between the buffer pool and the data files) — this duplicates the kernel's page cache but gives the database full control over eviction and writeback. The JVM uses anonymous mmap exclusively for the heap (the GC needs full control over the layout, which file-backed mmap does not provide). Every runtime in section 04 inherits this same choice: the runtime's heap is anonymous mmap, the runtime's I/O is either `read`/`write` or file-backed mmap depending on whether it wants kernel-managed caching or runtime-managed caching. The failure mode of file-backed mmap is the `D`-state stall (a slow disk wedges the process in uninterruptible sleep); the failure mode of anonymous mmap is the OOM kill (the runtime committed more than the system can supply); both are covered in 02.02.03.

## How This Connects to the Runtimes

Every runtime covered in section 04 is a user-space wrapper around these kernel primitives:

- **JVM**: Maps Java threads 1:1 to OS threads via NPTL. The JVM's memory model (section 04.01) is a specification layered on top of the kernel's virtual memory system described here.
- **Node.js / libuv**: The event loop (section 04.02) is a Reactor pattern built on `epoll_wait()`. The worker thread pool uses OS threads for operations that cannot be multiplexed (file I/O, DNS, crypto).
- **CPython**: The GIL (section 04.03) is a mutex that serializes Python bytecode execution across OS threads. Multi-processing in Python uses `fork()` to bypass the GIL.
- **PHP-FPM**: Each worker is a separate OS process (section 04.04). The shared-nothing model is a direct consequence of the process isolation described in the Linux Process Model note.

When you read those runtime notes, come back here and trace which kernel primitive each runtime feature maps to.
## Hands-On Exercise

Open a terminal on a Linux machine and run the following commands to see these concepts in action:

```bash
# See process states
ps -eo pid,stat,comm | head -20

# See context switches per second
vmstat 1 5

# See file descriptors for a process
ls -la /proc/$$/fd

# See memory layout of a running process — the most important command in this section
cat /proc/self/maps | head -20

# See socket states
ss -tan state established | head

# Detailed per-VMA memory accounting
cat /proc/<pid>/smaps_rollup

# The JVM heap region (huge anonymous mmap)
cat /proc/<jvm_pid>/maps | grep -E "rw-p .* 00:00 0$" | head

# The program break (end of heap)
grep '\[heap\]' /proc/self/maps
```

Correlate each output with the bullets above. If you cannot match a row in the output to a concept in this note, re-read the relevant section. The single most educational command is `cat /proc/self/maps` — it shows you every region described above.
