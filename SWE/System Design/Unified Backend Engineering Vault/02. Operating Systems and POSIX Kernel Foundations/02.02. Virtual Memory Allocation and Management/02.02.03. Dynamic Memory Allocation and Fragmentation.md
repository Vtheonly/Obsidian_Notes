# 02.02.03. Dynamic Memory Allocation and Fragmentation

## What This Is

**Dynamic Memory Allocation and Fragmentation** is the user-space layer on top of the kernel's virtual memory primitives (02.02.01) and segment layout (02.02.02). Where the kernel provides `brk`/`mmap` and the page-fault handler, the C library's `malloc` (and the JVM's `malloc`, and Python's `pymalloc`, and V8's allocator, and PHP's `emalloc`) provides size-classed, free-list-managed, thread-cached allocation. The reason this note sits in section 02 is that every runtime in section 04 has its own allocator strategy, and the choice of allocator dominates the runtime's behavior under load: glibc's `ptmalloc2` is fine for short-lived processes but fragments badly under multi-threaded long-running loads; `jemalloc` and `tcmalloc` are designed for the multi-threaded server case and are the standard drop-in replacements for databases (Redis defaults to `jemalloc`, MariaDB ships with `jemalloc`, Facebook's services all use it); the JVM and V8 do not use glibc malloc at all for their managed heaps, because they need precise control over object placement that glibc cannot provide.

The mental model is: `malloc(N)` is a user-space function that maintains a pool of memory obtained from the kernel via `brk` (for small allocations, growing the heap) or `mmap` (for large allocations, typically > 128 KB). The pool is organized into size classes (8-byte, 16-byte, ..., 256 KB, 512 KB) with separate free lists per class, so a `malloc(24)` request can be served by picking the head off the 32-byte free list in O(1) without scanning. `free(p)` returns the block to its size class's free list, again in O(1). The pool grows when a free list is empty (extend the heap with `brk` or grab a new region with `mmap`) and shrinks rarely (only when the top of the heap is a large contiguous free region). The complexity — and the engineering — is in the multi-threaded case: a single global lock on the free lists would serialize every thread's allocations, so modern allocators partition the heap into per-thread arenas or per-CPU caches, with fallback paths for cross-thread frees.

## The Details

### User-space allocators: `glibc malloc`, `jemalloc`, and `tcmalloc`

The Linux ecosystem has three production-grade allocators that backend engineers must know: **glibc's `ptmalloc2`** (the default on every Linux distro, derived from Doug Lea's `dlmalloc` with thread-arena support added by Wolfram Gloger), **Facebook's `jemalloc`** (Jason Evans's allocator, originally for FreeBSD, now the default in FreeBSD and Rust and the explicit choice of Redis, MariaDB, and many Facebook services), and **Google's `tcmalloc`** (Google's thread-cached allocator, used internally at Google and in many open-source projects). All three expose the same `malloc`/`free` API, but their internal architectures are very different, and the choice matters more than most engineers realize.

`ptmalloc2` organizes the heap into **arenas** — one arena per thread by default, up to a maximum of `8 × num_cpus` arenas. Each arena has its own mutex, so two threads allocating from different arenas do not contend. The problem is **cross-thread frees**: if thread A allocates a block (it goes into arena 1) and thread B frees it (it must be returned to arena 1), thread B must take arena 1's lock — serializing against thread A. In a workload with extensive object handoff between threads (request-queue servers, message-passing systems), ptmalloc2's lock contention becomes the dominant bottleneck. The symptom is high `sy` (system) CPU time and high `futex` syscall counts in `perf`. The other ptmalloc2 issue is fragmentation: its free lists are not aggressively coalesced, so a long-running multi-threaded process can accumulate 50%+ RSS overhead in fragmented-but-unreturnable heap. The fix is either `MALLOC_TRIM_THRESHOLD_` environment variable tuning (lower the threshold for returning memory to the kernel) or switching to `jemalloc`.

`jemalloc` was designed from the start for the multi-threaded server case. It uses per-thread caches (tcache) for small allocations — each thread gets a private cache of free objects in each size class, so small allocs and frees never touch a lock. Cross-thread frees go to "arenas" (one per CPU, not per thread — bounded count), and within an arena, frees are batched per-thread to reduce lock contention. `jemalloc` also aggressively coalesces free regions and proactively returns memory to the kernel via `madvise(MADV_DONTNEED)` — this is why Redis, which allocates and frees huge numbers of objects under normal workload, defaults to jemalloc and has documented 30%+ RSS savings vs ptmalloc2. `jemalloc` also has built-in heap profiling (`malloc_stats_print`) and a per-size-class fragmentation report.

`tcmalloc` is Google's design: similar per-thread caches (called "thread-local caches"), but with a different size-class layout (more size classes, smaller size-class jumps, less internal fragmentation for common sizes) and a more aggressive large-allocation path (everything > 256 KB goes directly through `mmap`, bypassing the central heap). `tcmalloc` is the standard at Google internally and is the allocator used by the Go runtime (a heavily modified tcmalloc variant). Its main advantage over jemalloc is slightly better throughput under extreme allocation rates (think a JIT compiler allocating millions of small objects per second); its main disadvantage is that it is less well-integrated with the rest of glibc and requires explicit linking.

The connection to the upper layers is direct: **every runtime that calls `malloc` is bound by the allocator's behavior**. CPython's `pymalloc` uses `malloc` for >512 byte objects, so the underlying allocator choice (glibc vs jemalloc) affects CPython's RSS for big-object workloads. Node's V8 uses its own allocator for the JS heap (a zone-based allocator that does NOT call `malloc` for JS objects), but Node's `Buffer` and native modules DO call `malloc`, so the underlying allocator affects Node's RSS for I/O buffers. PHP's `emalloc` is its own arena allocator, but the per-request arena frees back to `malloc` at request end — and `malloc` may or may not return that memory to the kernel depending on the allocator. The JVM uses `mmap` directly for the Java heap and `malloc` for native allocations; for a JVM doing heavy JNI or NIO direct-buffer work, swapping to jemalloc can reduce RSS by 30%. When you read the runtime notes in section 04, the allocator choice is one of the first things to check on any "RSS is higher than expected" investigation.

### The mechanics of `malloc()`: Small allocations via bin management vs. Large allocations via `mmap()`

The `malloc(N)` function in glibc has a fast path and a slow path, and which one is taken depends on the size of N. For **small allocations** (up to ~128 KB on 64-bit glibc — the threshold is configurable via `M_MMAP_THRESHOLD`), `malloc` searches the appropriate free list (called "bins" in ptmalloc2's terminology) for a best-fit block. The bins are organized by size class: **fastbins** for sizes 16, 32, 48, 64, 80, 96, 112, 128 bytes (single-linked list, last-in-first-out, never coalesced); **smallbins** for sizes 16 to 1024 bytes in 16-byte increments (circular doubly-linked list, exact-fit only); **unsorted bin** for recently-freed blocks that have not yet been classified (this is the first bin searched after fastbins and before smallbins); **largebins** for sizes 1024+ bytes (a tree of bins indexed by size, allowing logarithmic-time best-fit search). If a suitable block is found, it is removed from the bin and returned to the caller (possibly splitting if the block is much larger than requested). If no suitable block exists, `malloc` extends the heap via `brk` (raises the program break) and carves a new block out of the "top chunk" — the wilderness at the top of the heap.

For **large allocations** (above `M_MMAP_THRESHOLD`, default 128 KB), `malloc` skips the heap entirely and calls `mmap(NULL, size, PROT_READ|PROT_WRITE, MAP_PRIVATE|MAP_ANONYMOUS, -1, 0)` to allocate a separate anonymous memory region. This has three benefits: (1) the region can be `munmap`'d on `free`, returning the address space AND the physical memory to the kernel immediately (no fragmentation, no RSS leak); (2) the region does not contend with the heap's lock; (3) the region is page-aligned by default, which is required for some APIs. The downside is that `mmap` is a system call (more expensive than a free-list pop) and that the region is allocated in 4 KB increments (so a 130 KB allocation actually consumes 132 KB of address space). The threshold is dynamically adjusted: ptmalloc2 raises `M_MMAP_THRESHOLD` after a large allocation is freed successfully, on the theory that if the program freed a 200 KB block it will probably allocate a similar size again, and using the heap for that would cause excessive `brk` churn. This dynamic threshold is the reason `M_MMAP_THRESHOLD` is hard to reason about — it is not a fixed number, it is a moving target.

The free path mirrors the allocation path: `free(p)` looks at the chunk header (the 16 bytes immediately before the user pointer, which contains the chunk size and the in-use bit) to determine the size class. For small chunks, `free` pushes the block onto the appropriate fastbin (if the size fits) or inserts it into the unsorted bin. For large chunks (originally mmap'd), `free` calls `munmap` directly. The interesting subtlety is that fastbins are NOT coalesced — adjacent freed fastbin blocks stay as separate chunks, which means the heap can become fragmented even when there is plenty of free space. Coalescing happens only when the unsorted bin is processed (which happens on the next `malloc` that misses the fastbins) or when the top chunk is large enough to be returned to the kernel via `brk` trim. This deferred-coalescing design is a throughput optimization (fewer pointer manipulations per `free`), but it is the root cause of ptmalloc2's fragmentation in long-running processes.

```c
/* malloc internals — what really happens for different sizes */
#include <stdlib.h>
#include <stdio.h>
#include <malloc.h>

int main(void) {
    /* Small allocation (16 bytes) → goes through fastbin.
       Internally: malloc searches fastbin for size 32 (16 user + 16 header).
       If empty, takes from smallbin or unsorted bin or top chunk. */
    char *small = malloc(16);

    /* Medium allocation (1 KB) → goes through smallbin.
       Internally: searches smallbin for size 1024; if empty, searches
       unsorted bin, then largebin, then top chunk. */
    char *medium = malloc(1024);

    /* Large allocation (200 KB) → bypasses heap, calls mmap directly.
       Internally: mmap(NULL, 200704, PROT_READ|PROT_WRITE,
                        MAP_PRIVATE|MAP_ANONYMOUS, -1, 0)
       The returned pointer will be far from the heap in /proc/maps. */
    char *large = malloc(200 * 1024);

    /* Inspect the arena state */
    malloc_info(0, stdout);   /* XML dump of arena state */
    malloc_stats();           /* one-line summary per arena */

    free(small);   /* → pushed to fastbin */
    free(medium);  /* → pushed to unsorted bin */
    free(large);   /* → munmap'd, returned to kernel immediately */

    return 0;
}
```

The connection to the upper layers is the operational rule: **small allocations stick; large allocations are returnable.** If your program allocates and frees a 100 MB buffer, the RSS will return to baseline (because the buffer went through `mmap` and was `munmap`'d). If your program allocates and frees 100 million 1 KB objects, the RSS will NOT return to baseline (because the objects went through the heap, the heap never shrinks, and the freed blocks sit in fastbins waiting to be reused). This is why CPython's `pymalloc` uses 256 KB arenas via `mmap` (not the brk heap) — when an arena is fully empty, it can be `munmap`'d, returning the memory entirely. It is why the JVM's heap is one giant `mmap` (the GC compacts and can return unused regions via `madvise(MADV_DONTNEED)`). It is why long-running Node services that allocate lots of small buffers can balloon in RSS — V8's external allocations go through `malloc`, the small ones stick in the heap, and the heap never shrinks. The fix in every case is the same: either use jemalloc (which proactively returns memory), or batch small allocations into large arenas yourself.

### Memory Fragmentation: Internal fragmentation (slack space in allocations) vs. External fragmentation (scattered free memory)

Fragmentation is the gap between what an allocator has reserved from the kernel and what the application is actually using. There are two kinds, and they are conceptually distinct. **Internal fragmentation** is the slack space within each allocated block — when you `malloc(17)`, the allocator rounds up to the next size class (32 bytes for most allocators), and the 15 bytes between your 17 and the 32 are wasted inside the block you hold. Internal fragmentation is bounded by the size-class granularity: an allocator with 16-byte size classes wastes an average of 8 bytes per allocation (half of 16), which is 8% on a 100-byte allocation and 0.008% on a 1 MB allocation. `jemalloc` and `tcmalloc` use finer-grained size classes than `ptmalloc2` (16-byte, 32-byte, 48-byte, 64-byte, 80-byte, 96-byte, 112-byte, 128-byte, 160-byte, 192-byte, ... rather than 16/32/48/64/80/96/112/128/256/512/...), so they waste less on small allocations. The total internal fragmentation is typically 5-15% of allocated memory.

**External fragmentation** is the gap between the free blocks scattered across the heap and the largest contiguous block that can be served from them. Imagine a 100 MB heap where the program has freed every other 4 KB page — there is 50 MB of free memory, but a request for 8 KB contiguous cannot be served (no two adjacent 4 KB pages are both free). External fragmentation grows over time as the heap churns: every allocation and free perforates the heap with holes, and the free-list coalescing that ptmalloc2 does on `free` can only merge adjacent free blocks, not compact the whole heap. The metric to watch is **RSS divided by in-use heap bytes** — a ratio of 1.0 means no fragmentation, 1.5 means 33% of RSS is wasted in fragmented-but-unreturnable heap, 2.0+ is a problem.

The mitigations for fragmentation fall into three categories. **Allocator-level mitigation**: use an allocator with better coalescing (jemalloc, tcmalloc) or one with explicit compaction (the JVM's G1/ZGC compact the heap during GC, eliminating external fragmentation entirely). **Application-level mitigation**: use object pools (allocate a large arena of fixed-size objects once and reuse them — eliminates fragmentation by making every allocation the same size), use arena allocators (CPython's `pymalloc`, PHP's `emalloc` — allocate from a bounded arena and free the whole arena at once, eliminating fragmentation at the cost of holding the arena until empty). **Kernel-level mitigation**: `madvise(MADV_DONTNEED)` to tell the kernel "I am done with these pages, take them back" — the kernel then unmaps the physical pages but keeps the virtual range, so a subsequent access re-materializes a zero page. This is what jemalloc does proactively; ptmalloc2 does it only on `malloc_trim`. The best mitigation depends on the workload, but the rule of thumb is: short-lived processes (CLI tools, scripts) tolerate ptmalloc2 fine; long-running multi-threaded servers should use jemalloc or tcmalloc; runtimes with their own GC (JVM, V8, .NET) manage their own heaps and do not need this advice for the managed portion.

The connection to the upper layers is the production rule: **measure fragmentation before you tune anything else.** A JVM showing 4 GB RSS with 2 GB live heap has 50% overhead — but that overhead is mostly the JVM's internal bookkeeping (card tables, remembered sets, mark bitmaps), not fragmentation. A Redis showing 4 GB RSS with 2 GB of stored data has 50% overhead — and most of that IS fragmentation (Redis does not compact, so the only fix is jemalloc + `activedefrag yes` configuration). A CPython process showing 4 GB RSS with 1 GB of live Python objects has 75% overhead — some of which is fragmentation in `pymalloc` arenas, some of which is fragmentation in the underlying `malloc` heap (jemalloc or ptmalloc2). The diagnostic in every case is `cat /proc/<pid>/smaps_rollup` for RSS, `pmap -x <pid>` for per-region breakdown, and the runtime's own heap dump (jmap, heapdump, pympler) for in-use bytes. The fix in every case is either to switch allocators, enable compaction, or use object pools for the churny allocation hotspots.

### Out of Memory (OOM) Killer: Heuristics, `oom_score`, `oom_score_adj`, and protecting critical backend services

The Linux **OOM Killer** is the kernel's last-resort response to memory exhaustion. When the system runs out of commitable memory (the kernel has overcommitted — sold more virtual address space than it has physical RAM + swap — and a process now touches a page that the kernel cannot supply), the kernel invokes the OOM killer to pick a victim process, send it `SIGKILL`, and reclaim its memory. The decision is made by `out_of_memory()` in `mm/oom_kill.c`, which calls `select_bad_process()` to walk every process on the system and compute an `oom_score` for each. The victim is the process with the highest `oom_score`.

The `oom_score` is computed by `oom_badness()` in `mm/oom_kill.c`. The base score is the process's RSS plus its swap usage plus its page-table memory (roughly "how much memory will we free by killing this process"). The score is then normalized to a 0-1000 range relative to the total memory on the system. Several adjustments are applied: child processes that share memory with the candidate are counted (killing a parent with many children is more valuable); processes running as root get a slight penalty (the kernel prefers to kill user processes over system services); the process's `oom_score_adj` (a user-settable value from -1000 to +1000) is added to the score before normalization. The `oom_score_adj` is the knob that production engineers must use: a value of -1000 makes the process un-killable by OOM; a value of +1000 makes it the first to be killed; a value of -500 (common for critical databases) makes it nearly un-killable.

The OOM killer has multiple modes, controlled by `vm.oom_kill_allocating_task` (default 0). In the default mode, when memory is exhausted, the kernel picks the worst offender system-wide. In the alternative mode (set to 1), the kernel kills the task that triggered the OOM — the one that just tried to allocate and found no memory. The default is usually better for production because it kills the actual memory hog rather than the unlucky thread that hit the wall. There is also `vm.panic_on_oom` (default 0) — set to 1, the kernel panics and reboots instead of killing a process. This is appropriate for embedded systems and some appliances, but almost never for backend servers (a reboot is usually worse than killing one process).

The production mitigations for OOM fall into three categories. **Cgroup limits**: set `memory.max` in the cgroup to cap the process's memory, so the kernel kills the process when it exceeds the limit rather than letting it grow into the OOM killer's territory. This is what Docker's `--memory` flag does, and it gives you a clean `OOMKilled` exit reason rather than a system-wide OOM event. **`oom_score_adj` tuning**: set the critical database to -1000 (or near it), set the can-be-restarted cache layer to +500 (Redis with `activedefrag no`, sidekiq workers, etc.), so that when OOM does fire, it kills the cache layer rather than the database. **Sufficient memory + swap**: size the box so that the working set fits in RAM, and configure swap as an emergency pressure-release valve (even a small swap partition prevents OOM kills during transient spikes). The combination is the standard production recipe: cgroup limit + `oom_score_adj` + headroom in RAM + small swap as a safety net.

```bash
# See the current oom_score of every process (higher = more likely to be killed)
$ ps -eo pid,comm | while read pid comm; do
    score=$(cat /proc/$pid/oom_score 2>/dev/null)
    echo "$score  $pid  $comm"
done | sort -rn | head
   872  1234  postgres       ← high RSS, default oom_score_adj
   654  5678  redis-server
   234  4231  java
   ...

# See a specific process's score and adjustment
$ cat /proc/<pid>/oom_score
872
$ cat /proc/<pid>/oom_score_adj
0

# Protect a critical process from OOM (set to -1000 = unkillable)
$ echo -1000 | sudo tee /proc/<pid>/oom_score_adj
-1000

# Make a cache layer more likely to be killed (set to +500)
$ echo 500 | sudo tee /proc/<redis_pid>/oom_score_adj
500

# Permanently in systemd (this is the recommended production pattern)
# /etc/systemd/system/postgresql.service
[Service]
OOMScoreAdjust=-1000
# /etc/systemd/system/redis.service
[Service]
OOMScoreAdjust=500

# Cgroup-based memory limit (the Docker way)
$ docker run --memory=4g --memory-swap=4g my-app
# Inside the container, the process sees a memory.max of 4 GB.
# If it exceeds 4 GB, the kernel OOM-kills it (cleanly, with reason=OOMKilled)
# instead of touching the system-wide OOM killer.

# Disable the OOM killer entirely (DANGEROUS — failures will panic the kernel)
$ echo 1 | sudo tee /proc/sys/vm/panic_on_oom
```

The connection to the upper layers is the production rule: **every backend service must set `oom_score_adj` and every container must set a memory limit.** A database running with the default `oom_score_adj=0` is at risk of being killed by the OOM killer whenever any other process on the host misbehaves — and the database's death is far more consequential than the cache layer's death. A container without `--memory` can grow without bound until the host OOMs, at which point the kernel's victim selection is essentially arbitrary. When you read the runtime notes in section 04, every runtime's deployment guide includes a `oom_score_adj` recommendation and a cgroup memory limit — the JVM has `-XX:MaxRAMPercentage`, Node has `--max-old-space-size`, Python has no built-in limit (you must rely on the cgroup), PHP-FPM has `memory_limit`. None of these alone is sufficient; the cgroup limit is the enforcement mechanism, and `oom_score_adj` is the prioritization mechanism. Both must be set for production safety.

## How This Connects to the Runtimes

Every runtime covered in section 04 is a user-space wrapper around these kernel primitives:

- **JVM**: Maps Java threads 1:1 to OS threads via NPTL. The JVM's memory model (section 04.01) is a specification layered on top of the kernel's virtual memory system described here.
- **Node.js / libuv**: The event loop (section 04.02) is a Reactor pattern built on `epoll_wait()`. The worker thread pool uses OS threads for operations that cannot be multiplexed (file I/O, DNS, crypto).
- **CPython**: The GIL (section 04.03) is a mutex that serializes Python bytecode execution across OS threads. Multi-processing in Python uses `fork()` to bypass the GIL.
- **PHP-FPM**: Each worker is a separate OS process (section 04.04). The shared-nothing model is a direct consequence of the process isolation described in the Linux Process Model note.

When you read those runtime notes, come back here and trace which kernel primitive each runtime feature maps to.
