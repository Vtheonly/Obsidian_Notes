# 07.01.01. The Architectural Divide in Asynchronous Messaging

## What This Is

Asynchronous messaging on the backend has two equally valid shapes, and the choice between them is the single most consequential decision a backend engineer makes when designing an async pipeline. On one side sits the **traditional message queue** — RabbitMQ, ActiveMQ, AWS SQS, IBM MQ, Azure Service Bus — where a message is delivered to one consumer, acknowledged, and destroyed. On the other side sits the **distributed append-only commit log** — Apache Kafka, AWS Kinesis, Apache Pulsar, Redpanda — where messages are appended to an immutable, retention-bounded stream that many independent consumer groups can read, re-read, and tail concurrently. The two models overlap in feature checklists but diverge sharply in the operations and failure modes they imply.

This note is the conceptual fork in the road for Section 07. Every subsequent note — 07.01.02 (AMQP/RabbitMQ), 07.02.x (Kafka storage and cluster), 07.03.x (Kafka consumers), 07.04.x (background jobs), 07.05.x (outbox/CDC) — assumes you understand which model fits which workload and why. Pick the queue model when you need one-shot task distribution (order confirmation emails, image thumbnailing, payment authorisation retries). Pick the log model when you need durable replay (event sourcing, CQRS read-model feeds, microservice integration events, audit trails, stream-processing pipelines that recompute materialised views). The wrong choice is multi-month expensive to undo: queues cannot replay history after a message is acked, and logs cannot efficiently distribute one-shot work across a fleet of workers because the consumer group must own partitions rather than individual messages.

The layered mental model is in full force here. The queue model is built on TCP connection multiplexing (RabbitMQ's channels) and immediate dispatch under backpressure; the log model is built on sequential disk appends (Section 02.04 — page cache, `sendfile`) and pull-based polling. The queue model fits naturally with the request/response framework abstractions of Section 05 (each message is a one-shot RPC); the log model fits naturally with the persistence primitives of Section 06 (the commit log *is* a WAL that never truncates). Understanding the divide is the prerequisite for understanding why the two ecosystems evolved such different APIs, configs, and operational playbooks.

## The Details

### Traditional Message Queues (RabbitMQ, AWS SQS) vs. Distributed Event Logs (Apache Kafka)

The traditional message queue and the distributed event log both move bytes from a producer to a consumer without coupling them in time, but they differ on four structural axes: where the message lives, how long it lives, who can read it, and how the system scales. A queue stores each message *in memory or in a small on-disk spool*, hands it to *one consumer*, and *deletes it on ack*. A log appends each message *to a partition file on disk*, retains it *for a configured time window regardless of whether anyone has read it*, allows *multiple independent consumer groups to read the same message*, and scales by *adding partitions and brokers*. The table below maps the product landscape against these axes.

| Axis | RabbitMQ / ActiveMQ / SQS (Queue) | Kafka / Kinesis / Pulsar / Redpanda (Log) |
|---|---|---|
| Storage substrate | Memory + ephemeral disk spool | Append-only segment files on disk |
| Message lifetime | Until acked by one consumer | Until retention (`retention.ms`/`retention.bytes`) expires |
| Number of consumers per message | 1 (queue) or N subscribers (topic fan-out, but each subscriber gets its own copy and acks it) | N consumer groups, each reads independently at its own offset |
| Replay past messages | No — once acked, the message is gone | Yes — seek to any offset within retention window |
| Ordering unit | Per-queue (single consumer) or per-routing-key | Per-partition (parallelism = partition count) |
| Throughput ceiling | ~10k–50k msg/s per node (RabbitMQ), 3k msg/s per queue (SQS) | 100k–1M msg/s per broker (Kafka), millions per partition per second |
| Latency floor | Sub-millisecond when in-memory | 5–50 ms end-to-end (producer linger + consumer poll) |
| Operational complexity | Low — single broker handles everything | High — brokers, controllers, KRaft/ZooKeeper, partition rebalancing |
| Typical use case | Task hand-off, RPC-style request/reply, work distribution | Event streaming, audit log, CDC, microservice integration, stream processing |

The decision procedure is not "Kafka is faster so use Kafka." Throughput is rarely the deciding factor; the deciding factor is **whether you ever need to re-read the message**. If a downstream consumer is added six months later and needs historical data, only the log model can serve it. If a consumer's logic changes and you want to recompute the materialised view from the start of time, only the log model can do that. If a consumer crashes mid-processing and you want to know what it had consumed, only the log model can answer (because the offset is durably stored in `__consumer_offsets` and the message is still on disk). Queues optimise for *delivery*; logs optimise for *retention and replay*. Most production systems end up with both — RabbitMQ for the order-email task, Kafka for the order event stream — and the transactional outbox pattern (07.05.02) exists precisely to bridge them.

```text
   PRODUCER                 BROKER                       CONSUMER
   ────────                ───────                       ────────

   [Queue model]                          ┌── consumer A (acks msg, msg destroyed)
        └── publish ──>  [msg]  ──────────┘
                          (in memory,
                           deleted on ack)

   [Log model]            ┌── partition file on disk ──────┐
        └── publish ──>  │ offset 0  [msg0]              │──> consumer group A @ offset 5
                          │ offset 1  [msg1]              │──> consumer group B @ offset 0  (new, reads from start)
                          │ offset 2  [msg2]              │──> consumer group C @ offset 2  (paused, resumes)
                          │ ...                           │
                          │ offset N  [msgN]  (latest)    │
                          └───────────────────────────────┘
                            retained for retention.ms (default 7 days)
```

The production failure mode of picking the wrong model is silent and expensive. Picking a queue when you needed a log shows up six months later when a new microservice wants to subscribe to "all order events" and you have to explain that the last six months of events are gone forever. Picking a log when you needed a queue shows up immediately as a throughput cliff — Kafka's per-partition overhead and consumer-group rebalancing make it a poor fit for million-message-per-second task distribution across thousands of ephemeral workers, where SQS or RabbitMQ will happily round-robin messages across workers without any partition-ownership overhead. See [[07.05.01. The Dual-Write Problem]] for the canonical case where the choice of broker interacts with database transaction semantics.

### Lifecycle: Transient Task Queuing with message destruction post-acknowledgment vs. Persistent App...

The lifecycle of a message in a queue is *born → delivered → acked → destroyed*. The lifecycle of a message in a log is *appended → retained → eventually deleted by retention policy*. These two lifecycles imply fundamentally different operational realities: a queue's storage footprint is bounded by the *rate* of incoming work (it drains as fast as consumers ack), while a log's storage footprint is bounded by the *retention window* (it accumulates regardless of consumer progress). A queue that handles 1 M messages/sec with slow consumers will OOM the broker; a log that handles 1 M messages/sec with no consumers at all will simply fill disk at the retention-determined rate and roll off the back.

In RabbitMQ, a message's lifecycle is governed by the queue's durability flag (`durable=true` survives broker restart, `durable=false` is in-memory only), the message's `delivery_mode` property (`delivery_mode=2` is persistent — written to disk; `delivery_mode=1` is transient — kept in RAM), and the consumer's ack mode (`auto_ack=true` destroys on deliver, `auto_ack=false` requires an explicit `basic.ack`). When a consumer dies without acking, the broker requeues the message and delivers it to another consumer — but only the *unacked* copy; the original is still tracked in the queue's metadata until ack. In AWS SQS the lifecycle is similar but uses a *visibility timeout* (default 30 seconds, max 12 hours): when a consumer receives a message, the message becomes invisible to other consumers for the timeout window; if the consumer does not `DeleteMessage` within the window, the message reappears for redelivery. Visibility timeouts are SQS's answer to "what if the consumer crashes mid-process?" — the timeout is the upper bound on how long a consumer is allowed to take.

```text
   SQS VISIBILITY TIMEOUT LIFECYCLE
   ─────────────────────────────────

   t=0    producer ──> SendMessage ──> [msg] visible in queue
   t=1    consumer A ──> ReceiveMessage ──> [msg] invisible (visibility=30s starts)
   t=2..30  consumer A processes msg (takes 45 seconds)
   t=30   visibility expires, [msg] visible again
   t=31   consumer B ──> ReceiveMessage ──> [msg] invisible
   t=33   consumer A finally calls DeleteMessage ──> ERROR: ReceiptHandle invalid
          (consumer A processed msg but couldn't delete it; consumer B will now reprocess)
   t=35   consumer B processes msg, calls DeleteMessage ──> msg destroyed

   ──> Duplicate processing! Consumer A and consumer B both saw the message.
       This is why SQS documents "at-least-once" delivery and consumers MUST be idempotent.
```

In Kafka the lifecycle is entirely different. A message is appended to a partition's active segment, and there it stays until either (a) the segment rolls (when it hits `segment.bytes` default 1 GB or `segment.ms` default 168 hours = 7 days) and the *whole segment* is then eligible for retention-based deletion, or (b) on a compacted topic, until a newer message with the same key arrives and the log compactor rewrites the segment to keep only the latest value per key. Consumers do not destroy messages — they only advance their offset. A consumer that is six hours behind still sees every message from six hours ago; a brand-new consumer group can seek to offset 0 and replay the entire retention window. The producer's `acks` setting controls durability across brokers (`acks=0` fire-and-forget, `acks=1` leader-only, `acks=all` leader + all ISR), not message lifetime — once appended and acked, the message lives until retention policy or compaction reaps it.

```bash
# Kafka: inspect a partition's on-disk segments (retention in action)
ls -lh /var/lib/kafka/data/orders-0/
#  00000000000000000000.index         10M   (rolled segment, offset 0..999)
#  00000000000000000000.log           1.0G  (rolled segment)
#  00000000000000000000.timeindex     10M
#  00000000000000001000.index         10M   (rolled segment, offset 1000..1999)
#  00000000000000001000.log           1.0G
#  00000000000000001000.timeindex     10M
#  00000000000000002000.index         10M   (active segment, still being appended to)
#  00000000000000002000.log           450M  (active, growing)
#  00000000000000002000.timeindex     10M

# Inspect the topic's retention config
kafka-configs.sh --bootstrap-server localhost:9092 \
  --entity-type topics --entity-name orders --describe
#  retention.ms=604800000  (7 days)
#  retention.bytes=-1      (unlimited by size)
#  segment.bytes=1073741824 (1 GB)
#  segment.ms=604800000    (7 days)
#  cleanup.policy=delete   (or "compact" for compacted topics)
```

The production failure mode of the queue lifecycle is **silent message loss when an acked message can never be re-delivered**. If a consumer acks a message and then crashes before persisting its side effect (e.g., before committing the database write that the message triggered), the message is gone — no replay is possible. This is the dual-write problem in disguise, and it is the canonical reason why the transactional outbox pattern (07.05.02) exists. The production failure mode of the log lifecycle is **disk exhaustion when retention exceeds capacity** — a Kafka broker whose `retention.bytes` exceeds its disk will silently stop accepting produces, and a broker with `log.retention.check.interval.ms=300000` (5 minutes) may take up to 5 minutes after crossing the threshold before it starts deleting old segments. The metric to watch is `kafka.log.Log.Size` per partition vs. `kafka.log.Log.FlushPercent`, and the disk-full alert must fire at 80% — by 95% the broker is already refusing produces.

### Topologies: Point-to-Point Task Workers vs. Publish-Subscribe Event Fanout

The *topology* of an async system — the shape of the producer→consumer graph — is the third axis on which queues and logs diverge. Point-to-point topology routes each message to exactly one consumer out of a pool of competing workers; pub/sub topology routes each message to *every* subscribed consumer. Both models support both topologies, but with very different ergonomics: queues do point-to-point natively and pub/sub as a bolt-on feature (RabbitMQ's `fanout` and `topic` exchanges), while logs do pub/sub natively and point-to-point only via consumer-group partition assignment.

In a queue model, point-to-point is the default: declare a single queue, attach N consumers, and the broker round-robins messages across them. RabbitMQ does this transparently — every consumer that calls `basic.consume` on the same queue becomes a competing consumer, and the broker's internal scheduler hands each message to the next available consumer in round-robin order. AWS SQS does the same with `ReceiveMessage` calls — any worker that polls the queue can get any message, and the visibility timeout prevents double-delivery within the window. The topology is dynamic: workers can be added or removed at any time, and the broker adjusts immediately. There is no partition count to plan around and no rebalancing protocol to wait for.

```text
   POINT-TO-POINT TOPOLOGY (queue model)
   ──────────────────────────────────────

   producer ──> ┌────────────┐
                │  RabbitMQ  │ ── msg1 ──> worker 1 (basic.consume, prefetch=10)
                │   queue    │ ── msg2 ──> worker 2 (basic.consume, prefetch=10)
                │  "orders"  │ ── msg3 ──> worker 3 (basic.consume, prefetch=10)
                └────────────┘ ── msg4 ──> worker 1 (round-robins back)

   Add worker 4: just call basic.consume — broker starts round-robining to it immediately.
   Remove worker 3: cancel the consumer — broker stops routing to it. No rebalance protocol.
```

In a log model, point-to-point is achieved through *consumer groups*: every consumer in the same `group.id` is a competing consumer, and Kafka's coordinator assigns each consumer a subset of partitions. If a topic has 12 partitions and the consumer group has 4 consumers, each consumer gets 3 partitions; if you add a 5th consumer, the coordinator triggers a rebalance and one partition is reassigned from each of 3 consumers to the new one. The catch: parallelism is *bounded by partition count* — if you have 12 partitions, you cannot have more than 12 consumers in the group doing useful work; the 13th consumer will be idle. This is the most common Kafka scaling gotcha: under-provisioned partition counts cap your consumer parallelism forever, and increasing partition count after the fact changes the key→partition hash mapping and breaks ordering guarantees for existing keys.

```text
   PUB/SUB TOPOLOGY (log model, multiple consumer groups)
   ──────────────────────────────────────────────────────

                                  ┌── consumer group "search-indexer" (3 consumers, 4 partitions each)
   producer ──> ┌──────────┐     │     ├─ partition 0 ──> consumer 1 (indexes into Elasticsearch)
                │  Kafka   │ ────┼── ──┤
                │ topic    │     │     ├─ partition 1 ──> consumer 2
                │ "orders" │     │     └─ partition 2 ──> consumer 3
                │ 12 parts │     │
                └──────────┘     │
                                 │
                                 ├── consumer group "audit-log" (1 consumer reads all 12 partitions sequentially)
                                 │     └─ partitions 0..11 ──> consumer 1 (writes to S3 cold storage)
                                 │
                                 ├── consumer group "fraud-detection" (Flink job, 12 parallel tasks)
                                 │     └─ partition N ──> task N (stateful stream processing)
                                 │
                                 └── consumer group "cache-warmer" (12 consumers, 1 partition each)
                                       └─ partition N ──> consumer N (updates Redis cache)

   Each group reads the SAME messages independently at its OWN offset.
   Adding a new consumer group does not affect existing groups.
```

The pub/sub topology is where the log model shines and the queue model struggles. In Kafka, adding a new subscriber means creating a new consumer group with a fresh `group.id` and pointing it at the topic — the new group starts reading from `auto.offset.reset` (default `latest`), and no existing consumer is affected. In RabbitMQ, pub/sub is implemented via `fanout` or `topic` exchanges: each subscriber declares its own queue and binds it to the exchange, and the exchange routes a copy of every message to every bound queue. The model works, but each subscriber's queue is a separate copy of the data with its own ack/retry semantics, and the broker's memory footprint grows linearly with subscriber count. Kafka's pub/sub is more efficient because the data is stored once on disk and every consumer group reads the same bytes via zero-copy `sendfile` — the cost of a 10th consumer group is approximately zero in storage terms.

The production failure mode for point-to-point topology is **uneven work distribution under key skew**. In Kafka, if you partition by `user_id` and one user generates 80% of the traffic, the partition owning that user's key becomes a hot spot — one consumer does 80% of the work while the others sit idle. The fix is to use a custom partitioner that adds a random suffix to the key for high-volume producers, but that breaks the ordering guarantee. The failure mode for pub/sub topology in the queue model is **subscriber queue memory pressure**: if one subscriber is slow to ack, its queue grows unboundedly until the broker runs out of memory and refuses new publishes. RabbitMQ's `max-length` queue property caps this at the cost of dropping messages (set `overflow=reject-publish` to make the publisher see the backpressure). See [[07.01.02. AMQP Protocol and RabbitMQ Architecture]] for the prefetch (`basic.qos`) mechanism that prevents this, and [[07.03.01. Consumer Groups and Partition Balancing]] for the consumer-group rebalance protocol that handles Kafka's point-to-point topology.

### Push Delivery (Broker pushes to consumers) vs. Pull Polling (Consumers pull from brokers)

The fourth and final axis of the divide is the direction of data flow on the wire: does the broker push messages to the consumer, or does the consumer pull messages from the broker? RabbitMQ pushes (the broker's channel calls `basic.deliver` to the consumer's callback as soon as a message is available); Kafka pulls (the consumer's `poll()` loop issues `Fetch` requests to the broker and the broker returns whatever is available). The two models imply opposite backpressure semantics, opposite batching characteristics, and opposite failure-detection mechanisms.

RabbitMQ's push model is optimised for **low latency**. When a producer publishes a message, the broker's exchange routes it to a queue, and the queue immediately delivers it to any attached consumer via `basic.deliver`. The consumer's prefetch count (`basic.qos prefetch_count`, default unlimited in classic queues, default 10 in quorum queues) caps how many unacked messages the broker will push before it stops and waits for acks. With `prefetch_count=1`, the broker delivers one message, waits for the ack, then delivers the next — this gives perfect fairness but kills throughput. With `prefetch_count=1000`, the broker floods the consumer with up to 1000 unacked messages, which is great for throughput but terrible for fairness: if the consumer is processing 1000 messages in parallel and one of them takes 60 seconds, all 999 other messages are blocked behind it. The push model gives the broker control over pacing; the consumer must explicitly opt into backpressure via `basic.qos`.

```bash
# RabbitMQ: prefetch=10 means broker pushes at most 10 unacked messages per consumer
# Set via basic.qos on the channel before basic.consume:
#
#   channel.basicQos(10);                    // Java
#   channel.basic_consume(prefetch_count=10)  # Python pika
#   $channel->basic_qos(null, 10, null);      // PHP php-amqplib

# Inspect a queue's consumers and their prefetch counts
rabbitmqctl list_consumers --formatter=pretty_table | grep orders
#  queue_name  channel_pid  consumer_tag  ack_required  prefetch_count  active
#  orders      <pid>        consumer-1    true          10              true
#  orders      <pid>        consumer-2    true          10              true
#  orders      <pid>        consumer-3    true          10              true
#  ──> 30 unacked messages max in flight across the consumer pool
```

Kafka's pull model is optimised for **throughput and replay**. The consumer's `poll(Duration.ofMillis(100))` call issues a `Fetch` request to the leader of each assigned partition, asking for "messages starting at offset X, up to `fetch.max.bytes` (default 50 MB) bytes." The broker responds with whatever it has — possibly zero messages, possibly thousands. The consumer then processes the batch, commits the offset (manually or via auto-commit), and calls `poll()` again. Because the consumer pulls, it controls its own pace: if it's slow, it polls less often and the broker simply accumulates data on disk; if it's fast, it polls more often and gets bigger batches. There is no need for a `basic.qos`-style prefetch cap because the consumer is the one asking for data — backpressure is implicit in the poll rate.

```java
// Kafka consumer: pull-based polling loop
Properties props = new Properties();
props.put("bootstrap.servers", "kafka-1:9092,kafka-2:9092");
props.put("group.id", "order-processor");
props.put("enable.auto.commit", "false");         // manual commits for at-least-once
props.put("auto.offset.reset", "earliest");
props.put("max.poll.records", "500");             // max records per poll()
props.put("fetch.max.bytes", "52428800");         // 50 MB max per fetch request
props.put("max.poll.interval.ms", "300000");      // 5 min — if poll() not called within this, consumer is kicked out of the group

KafkaConsumer<String, String> consumer = new KafkaConsumer<>(props);
consumer.subscribe(List.of("orders"));

while (running) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
    for (ConsumerRecord<String, String> record : records) {
        processOrder(record.value());  // synchronous, slow
    }
    consumer.commitSync();  // commit offsets after successful processing
}
```

The pull model has a subtle but profound implication: **a slow consumer does not backpressure the producer**. In a queue model, when consumers slow down, the queue fills, the broker's memory pressure rises, and eventually the broker refuses new publishes (or, in SQS, the queue's `ApproximateNumberOfMessagesVisible` grows unboundedly and you start hitting API throttling). In a log model, when consumers slow down, the broker keeps accepting produces at full speed and the data accumulates on disk — the consumer's `consumer_lag` metric grows, but the producer is unaffected. This is what makes Kafka suitable as the persistence layer for bursty event streams: a 10× traffic spike that would OOM RabbitMQ simply makes the consumer lag spike on Kafka, and the lag drains when traffic returns to normal. The cost is operational: consumer lag must be monitored (`kafka.consumer.consumer-fetch-manager-metrics.records-lag-max`) and alerting must distinguish "lag is growing because the consumer is dead" from "lag is growing because traffic spiked and the consumer is keeping up at 80% throughput."

The failure mode of the push model is the **unbounded prefetch death spiral**: a queue with `prefetch_count=0` (unlimited) and slow consumers will accumulate unacked messages in memory until the broker OOMs and restarts, losing all unacked messages. The failure mode of the pull model is the **`max.poll.interval.ms` exile**: if a consumer's `poll()` loop blocks for longer than `max.poll.interval.ms` (default 5 minutes — common when `max.poll.records=500` and each record takes 1 second to process), the coordinator assumes the consumer is dead, triggers a rebalance, and reassigns its partitions to another consumer — but the exiled consumer, when it finally returns from processing, will try to commit offsets for partitions it no longer owns and crash. The fix is to either reduce `max.poll.records` so the batch always finishes within `max.poll.interval.ms`, or to process records in a separate thread pool and pause the partition (so `poll()` returns empty) until the thread pool drains. See [[07.03.02. Offset Management and Commit Strategies]] for the offset-commit implications and [[07.03.03. Delivery Guarantees and Idempotent Processing]] for the exactly-once semantic that this enables.
