# 07.01.02. AMQP Protocol and RabbitMQ Architecture

## What This Is

**AMQP** — the Advanced Message Queuing Protocol — is the wire-level specification that defines how a traditional message queue speaks to its clients. The protocol's most widely deployed version is **AMQP 0.9.1**, published in 2008 and implemented by RabbitMQ, Qpid, and ActiveMQ's AMQP module. (AMQP 1.0, published in 2014, is a different protocol — it dropped the exchange/binding model and is closer to a generic messaging frame format; RabbitMQ supports it via a plugin but the RabbitMQ-native API remains 0.9.1.) AMQP 0.9.1 is unique among messaging protocols in that it specifies not just the wire format but the *routing topology*: the protocol defines exchanges, queues, bindings, and the four exchange types (direct, fanout, topic, headers) as first-class protocol entities, not as broker implementation details. This is why RabbitMQ's routing model is portable across every AMQP 0.9.1 client library in every language — the JMS-style "destination" abstraction does not exist; what exists is a graph of exchanges and queues that the client declares and binds at runtime.

RabbitMQ is the dominant AMQP 0.9.1 broker. It is written in Erlang and runs on the Erlang/OTP VM, which gives it the actor-model concurrency semantics that make it well-suited to managing tens of thousands of concurrent connections and queues. (Erlang processes are lightweight — about 300 bytes per process — so a RabbitMQ broker can run millions of them; the limit is RAM, not process-table slots.) The broker's job is to accept AMQP connections, multiplex them into channels, route published messages through exchanges to bound queues, and deliver queued messages to attached consumers via push. RabbitMQ also implements the operational layer that AMQP 0.9.1 leaves to the broker: durable queues, persistent messages, dead-letter exchanges, prefetch limits, the management plugin (HTTP API on port 15672), the cluster formation protocol, and the migration from classic mirrored queues to Raft-based quorum queues (the default for new queues since RabbitMQ 3.10, the only option in 4.0+).

This note sits in the layered mental model above Section 03 (TCP networking — AMQP runs over TCP port 5672 plain and 5671 with TLS, and the AMQP frame format is a length-prefixed binary protocol that multiplexes many channels over one TCP connection) and below Section 05 (frameworks — Spring AMQP, amqplib, pika, the PHP AMQP extension all expose the AMQP model as language-native objects). Understanding AMQP at the protocol level means you can debug the failure modes that frameworks hide: messages routed to the wrong queue because the binding key was misspelled, queues silently dropping messages because they hit `max-length`, dead-letter loops, and the difference between a `basic.nack` (negative ack, broker requeues or dead-letters) and a `basic.reject` (same but for a single message at a time).

## The Details

### Core components: Exchanges (Direct, Fanout, Topic, Headers), Bindings, Queues

The AMQP 0.9.1 routing model is a three-entity graph: **producers publish to exchanges**, **exchanges route to queues via bindings**, **consumers attach to queues**. This indirection — the producer never names a queue, only an exchange — is what gives AMQP its routing power. The producer's only responsibility is to publish a message with a `routing_key` and an `exchange` name; the broker's responsibility is to look up the exchange, evaluate its type, and route copies of the message to every queue that has a binding matching the exchange's rules. The four exchange types each implement a different matching algorithm, and RabbitMQ ships all four pre-declared along with two built-in exchanges: the empty-named default exchange (a direct exchange that routes by queue name) and `amq.rabbitmq.trace` (a topic exchange that the broker publishes to for debugging).

| Exchange type | Routing key match | Use case | RabbitMQ pre-declared name |
|---|---|---|---|
| **direct** | Exact string equality | Per-queue unicast, RPC-style request/reply, simple work distribution | `amq.direct` |
| **fanout** | Ignored — every bound queue gets every message | Broadcast notifications, cache invalidation, fan-out to multiple subsystems | `amq.fanout` |
| **topic** | Dot-separated pattern with `*` (one word) and `#` (zero or more words) wildcards | Hierarchical routing keys like `orders.us.west.created`, `logs.app.error`, event routing | `amq.topic` |
| **headers** | Match on message headers (any/all of) instead of routing key | Content-based routing where the routing decision depends on multiple attributes | `amq.headers` (and `amq.match` as an alias) |

A binding is the rule that connects an exchange to a queue. The binding's arguments depend on the exchange type: for direct and topic exchanges, the binding carries a `binding_key` string; for fanout exchanges, the binding has no arguments (every bound queue receives every message); for headers exchanges, the binding carries a map of `key=value` header requirements plus an `x-match` argument of `any` or `all` (default `all`). Bindings are dynamic — a consumer can declare a queue, bind it to an exchange with one key, run for a while, then rebind with a different key without restarting the broker. This is what makes topic exchanges the workhorse for event routing: a monitoring consumer can bind with `logs.*.error` to get only errors, a debug consumer can bind with `logs.#` to get everything, and a third consumer can bind with `logs.app.*` to get only application logs — all reading from the same exchange, all getting the subset of messages they care about.

```text
   producer ──> publish(exchange="events", routing_key="orders.us.west.created", body=...)

                                  ┌──────────────────┐
                                  │  exchange        │

              │                            │                            │
              ▼                            ▼                            ▼

       "orders.us.west.*"            "orders.#"                    "#"
              │                            │                            │
              ▼                            ▼                            ▼
       ┌──────────┐                ┌──────────┐                ┌──────────┐
       │ queue    │                │ queue    │                │ queue    │
       │ "region" │                │ "all-    │                │ "audit"  │
       │          │                │ orders"  │                │          │
       └─────┬────┘                └─────┬────┘                └─────┬────┘
             │                           │                           │

       consumer A                  consumer B                  consumer C
       (us-west handler)           (all-order indexer)         (audit log)

   Message "orders.us.west.created" matches ALL THREE bindings → copied to 3 queues.
   Message "orders.eu.east.created" matches only "orders.#" and "#" → copied to 2 queues.

```

The connection-vs-channel distinction is the other core AMQP concept. A **connection** is a single TCP socket to the broker (port 5672 plain, 5671 for `amqps://` TLS). A **channel** is a virtual connection multiplexed over that TCP socket — AMQP frames carry a channel ID and the broker demultiplexes them. Each channel is a separate logical conversation with its own consumer tags, prefetch counts, and ack state, but all channels on a connection share one TCP socket's congestion window and one TLS session. The pattern in production is one long-lived connection per process (opened at startup, kept alive via heartbeats — `heartbeat=60` is the default in most clients), with one channel per thread or per logical operation. Channels are cheap to open and close (no TCP handshake, no TLS handshake); connections are expensive (a TCP handshake + AMQP `Connection.Start`/`Connection.Tune`/`Connection.Open` negotiation + optional TLS = 50–200 ms). A common bug is opening a new connection per publish, which under load melts the broker's connection-acceptor and exhausts the kernel's ephemeral port range (`net.ipv4.ip_local_port_range`) within minutes.

```python
# Python pika: one connection, multiple channels, one channel per thread
import pika
import threading

# Long-lived connection shared across the process
connection = pika.BlockingConnection(pika.ConnectionParameters(
    host='rabbitmq-1', port=5672,
    credentials=pika.PlainCredentials('guest', 'guest'),
    heartbeat=60,                # AMQP heartbeats every 60s
    blocked_connection_timeout=300,  # fail-fast if broker blocks the connection
))

def worker(queue_name, binding_key):
    # One channel per thread — channels are NOT thread-safe in pika
    channel = connection.channel()
    channel.queue_declare(queue=queue_name, durable=True)        # survives broker restart
    channel.queue_bind(queue=queue_name, exchange='events',
                       routing_key=binding_key)                  # bind to topic exchange
    channel.basic_qos(prefetch_count=10)                         # max 10 unacked msgs
    channel.basic_consume(queue=queue_name,
                          on_message_callback=handle_msg,
                          auto_ack=False)                        # we will basic_ack explicitly
    channel.start_consuming()

for q, k in [('region', 'orders.us.west.*'), ('all-orders', 'orders.#'), ('audit', '#')]:
    threading.Thread(target=worker, args=(q, k), daemon=True).start()
```

The production failure mode of the routing model is **silent message drop on mis-routed messages**. If a producer publishes to an exchange with a routing key that no binding matches, the broker's default behavior is to silently discard the message (the AMQP `mandatory` flag overrides this — when set, the broker returns the message with a `basic.return` frame if no queue received it, and the client must register a `ReturnListener` to see it). The other silent failure is the **alternate exchange** (`x-alt-exchange` exchange argument) being misconfigured: if a producer expects unroutable messages to land on a dead-letter exchange but the alternate exchange name is misspelled, the messages vanish. The diagnostic is `rabbitmqctl list_exchanges name type durable arguments` — verify the `x-alternate-exchange` argument matches an existing exchange, and watch the `rabbitmq.exchange.messages_unroutable` metric for non-zero values in production.

### Message Acknowledgments (`basic.ack`, `basic.nack`, `basic.reject`) and Dead Letter Exc...

AMQP acknowledgments are the protocol-level mechanism by which a consumer tells the broker "I have processed this message; you may discard it" or "I have failed to process this message; please requeue it or dead-letter it." The acknowledgment is what makes the queue model **at-least-once**: the broker holds the message in the queue's unacked-set until the consumer acks, and if the consumer's channel dies (TCP disconnect, process crash) before acking, the broker requeues the message for redelivery to another consumer. The three acknowledgment methods — `basic.ack`, `basic.nack`, `basic.reject` — have subtly different semantics, and using the wrong one in the wrong place is the source of the most common RabbitMQ production bugs.

`basic.ack` is the positive acknowledgment: the consumer tells the broker "I'm done with this message; delete it." It takes the `delivery_tag` (a channel-scoped monotonically increasing integer the broker assigned when it delivered the message) and a `multiple` flag (if true, acks all messages up to and including this delivery_tag — useful for batch acks). `basic.nack` is the negative acknowledgment, introduced in AMQP 0.9.1 as a protocol extension (RabbitMQ-specific, not in the original spec): it takes `delivery_tag`, `multiple`, and `requeue`. If `requeue=true`, the broker puts the message back at the front of the queue for redelivery; if `requeue=false`, the broker applies the queue's dead-letter policy (if a DLX is configured) or drops the message. `basic.reject` is the original-spec negative acknowledgment and is identical to `basic.nack` except it has no `multiple` flag — it rejects exactly one message at a time. In modern code, `basic.nack` is preferred because it can batch-reject and is more uniform with `basic.ack`.

```text
   ACK/NACK FLOW WITH DEAD-LETTER EXCHANGE
   ────────────────────────────────────────

   broker ──basic.deliver(delivery_tag=7, msg="order.create")──> consumer
                                                              │
                                                              │  process_msg() throws
                                                              │  PaymentTimeoutException
                                                              ▼
   broker <──basic.nack(delivery_tag=7, requeue=false)─────── consumer
           │
           │  requeue=false + DLX configured on queue
           ▼
   ┌─────────────────────────┐
   │ queue "orders"          │  (x-dead-letter-exchange="orders.dlx",
   │                         │   x-dead-letter-routing-key="orders.failed")
   └────────────┬────────────┘
                │
                ▼
   ┌─────────────────────────┐
   │ exchange "orders.dlx"   │  (direct exchange)
   └────────────┬────────────┘
                │  binding_key="orders.failed"
                ▼
   ┌─────────────────────────┐
   │ queue "orders.failed"   │  (inspected by humans, retried by a separate consumer)
   │                         │  Original headers preserved PLUS:
   │                         │   x-death[0].queue="orders"
   │                         │   x-death[0].reason="rejected"
   │                         │   x-death[0].time="2024-..."
   │                         │   x-death[0].routing-keys=["order.create"]
   └─────────────────────────┘
```

The **dead-letter exchange** (DLX) is the queue argument `x-dead-letter-exchange` that names an exchange to which the broker routes messages that are rejected with `requeue=false` or that expire from the queue's `x-message-ttl`. The DLX is the RabbitMQ-native way to implement retry queues with exponential backoff: bind the dead-letter queue to a second-level queue that has its own TTL and its own `x-dead-letter-exchange` pointing back to the original queue — when a message expires from the second-level queue, it lands back on the original queue for retry. The pattern looks like `orders` (DLX → `retry.5s`) → `retry.5s` (TTL=5s, DLX → `retry.30s`) → `retry.30s` (TTL=30s, DLX → `retry.5m`) → `retry.5m` (TTL=5m, DLX → `orders`). Each retry adds an `x-death` header entry so the consumer can see how many times the message has been retried and decide whether to give up.

```bash
# Declare a queue with a dead-letter exchange and message TTL via rabbitmqadmin
rabbitmqadmin declare queue name=orders durable=true \
  arguments='{"x-dead-letter-exchange":"orders.dlx",
              "x-dead-letter-routing-key":"orders.failed",
              "x-message-ttl":3600000}'

# Declare the dead-letter exchange and bind a queue to it
rabbitmqadmin declare exchange name=orders.dlx type=direct durable=true
rabbitmqadmin declare queue name=orders.failed durable=true
rabbitmqadmin declare binding source=orders.dlx destination=orders.failed \
  routing_key=orders.failed

# Inspect a dead-lettered message's headers (x-death array)
rabbitmqadmin get queue=orders.failed ackmode=ack_requeue_false count=1 | jq '.[0].payload'
# {
#   "payload": "{\"order_id\":42,...}",
#   "properties": {
#     "headers": {
```

The production failure mode of acknowledgments is the **acknowledgment-storm from auto-ack misuse or from a consumer that crashes mid-batch**. The classic bug is `auto_ack=true` on a consumer that does work-after-ack: the broker destroys the message on delivery, the consumer starts processing, the consumer crashes — the message is gone forever with no work done. The mirror-image bug is a consumer that acks *before* doing the work ("ack early to keep throughput high") and then crashes — same outcome. The correct pattern is `auto_ack=false`, process the message, ack only after the side effect (e.g., the database write) has committed, and accept that a crash between process-complete and ack will cause a duplicate (which is why consumers must be idempotent — see [[07.03.03. Delivery Guarantees and Idempotent Processing]]). The other failure mode is the **DLX routing loop**: if `orders` dead-letters to `orders.dlx` and `orders.failed` dead-letters back to `orders` (without a TTL gate), a perpetually-failing message will bounce between the two queues infinitely, consuming CPU and producing ever-growing `x-death` header arrays until the message size exceeds the broker's frame limit (default 128 MB) and the broker drops it. Always pair a DLX round-trip with a TTL or a max-retry counter that the consumer checks in the `x-death` header.

### Flow Control and Backpressure: Prefetch Count (`basic.qos`) and TCP socket window backp...

RabbitMQ has two independent flow-control layers: the **AMQP-level prefetch limit** (`basic.qos`) that caps how many unacked messages a consumer will hold, and the **broker-level memory/disk alarm** that blocks publisher connections when the broker is under resource pressure. The first is per-consumer tuning; the second is broker self-protection. Both must be understood to operate RabbitMQ at production scale — the prefetch limit governs throughput and fairness, and the broker alarms are what you see when your producers are out-pacing your consumers.

The `basic.qos` method takes three arguments: `prefetch_count` (the max number of unacked messages the broker will push to a channel), `prefetch_size` (the max total bytes of unacked messages — rarely used, default 0 = unlimited), and `global` (a flag that, when false, applies the limit per-consumer-on-the-channel; when true, applies it across all consumers on the channel — the modern RabbitMQ default is false). The prefetch count is the single most important RabbitMQ throughput knob. At `prefetch_count=1`, the broker delivers one message, waits for the ack, then delivers the next — round-trip latency dominates and throughput collapses to ~1/RTT messages per second (so a 1 ms RTT gives 1000 msg/s, a 10 ms RTT gives only 100 msg/s). At `prefetch_count=250`, the broker floods the consumer with up to 250 unacked messages and the consumer processes them in parallel; throughput rises 10–100× but the consumer's heap grows and individual message latency rises (a message delivered to position 250 waits for 249 others to finish before it's processed). The rule of thumb: start at `prefetch_count=10`, measure, double until throughput stops improving, back off one notch.

```text
   PREFETCH COUNT vs THROUGHPUT / LATENCY (typical, 1ms LAN, 1ms process/msg)
   ─────────────────────────────────────────────────────────────────────────

   prefetch_count=1     throughput: ~500 msg/s    p99 latency: 2ms     fairness: perfect
   prefetch_count=10    throughput: ~5,000 msg/s  p99 latency: 12ms    fairness: good
   prefetch_count=50    throughput: ~10,000 msg/s p99 latency: 60ms    fairness: okay
   prefetch_count=250   throughput: ~12,000 msg/s p99 latency: 300ms   fairness: poor (head-of-line)
   prefetch_count=0     throughput: ~12,000 msg/s p99 latency: 5000ms+ fairness: catastrophic (OOM)
                        (unlimited — broker floods consumer until RAM exhausted)

   ──> Sweet spot is typically prefetch_count=20..100 for CPU-bound work,
       prefetch_count=1..5 for I/O-bound work where ordering within a consumer matters,
       prefetch_count=250+ only for high-throughput batch processing where fairness is irrelevant.
```

The **broker-level memory alarm** fires when the broker's RSS exceeds `vm_memory_high_watermark` (default 0.4 of system RAM, configurable via `rabbitmq.conf` as a fraction or absolute bytes value). When the alarm fires, the broker sends a `connection.blocked` frame to every publisher connection and stops accepting `basic.publish` frames until RSS drops below the watermark minus a hysteresis margin. The publisher's client library must register a `BlockedListener` and pause publishing when blocked — if it doesn't, the publish calls simply queue in the client's buffer until the client OOMs. The **disk alarm** fires when free disk drops below `disk_free_limit` (default 50 MB, must be raised in production — at least 1 GB or 1.5× RAM, whichever is larger). The disk alarm also blocks publishers, because every persistent message must be `fsync`ed to disk before ack, and if the disk is full the broker cannot honor persistence. Both alarms are visible in `rabbitmqctl status` and in the management UI's overview page.

```bash
# Tune memory and disk watermarks in /etc/rabbitmq/rabbitmq.conf
# Memory alarm at 60% of RAM (default 40%):
vm_memory_high_watermark.relative = 0.6
# Or absolute: vm_memory_high_watermark.absolute = 4GB

# Disk alarm at 2GB free (default 50MB — way too low for production):
disk_free_limit.absolute = 2GB
# Or relative to RAM (recommended): disk_free_limit.relative = 1.5

# Paging threshold — when broker starts paging messages to disk before the alarm:
# Default is 0.5 of the high watermark (so at 30% RAM if watermark is 60%)
vm_memory_high_watermark_paging_ratio = 0.5

# Inspect current alarm state
rabbitmqctl status | grep -A2 memory
#  {vm_memory_high_watermark,0.6},
#  {vm_memory_limit,5153960755},          # 4.8 GB
#  {disk_free_limit,2000000000},          # 2 GB
#  {disk_free,473804484608},              # 441 GB free — alarm not tripped

rabbitmqctl list_connections name state | grep blocked
#  publisher-1  blocked
#  publisher-2  blocked
#  consumer-1   running
#  ──> Both publishers are blocked because the broker is above the memory watermark.
#       Consumers keep running; the queue drains and the alarm clears when RSS drops.
```

The TCP-level backpressure is what happens *underneath* AMQP when neither prefetch nor the broker alarms have engaged: when the broker's TCP send buffer to a slow consumer fills, the kernel's TCP stack stops acking the consumer's data and the consumer's `recv` calls block. This is the same TCP receive-window mechanics from Section 03.02 — RabbitMQ's `basic.qos` is the AMQP-layer projection of that TCP backpressure, giving the application a knob to set before TCP has to engage. The relationship between the layers is: if you set `prefetch_count` correctly, the consumer throttles itself via ack pacing and TCP backpressure never engages; if you set `prefetch_count=0` (unlimited), the broker floods the consumer, the consumer's TCP receive buffer fills, TCP stops acking, the broker's TCP send buffer fills, the broker's channel publish calls block, the queue grows, the broker RSS rises, and eventually the memory alarm engages — at which point the publisher is blocked at the AMQP layer and the whole pipeline stalls. The diagnostic chain in a RabbitMQ incident is therefore: (1) check `rabbitmqctl list_queues` for messages_ready growing, (2) check `rabbitmqctl list_consumers` for missing consumers or zero-prefetch consumers, (3) check `rabbitmqctl status` for memory/disk alarms, (4) check `ss -tin` for `Recv-Q` growing on consumer connections (TCP-layer saturation).

The production failure mode of prefetch tuning is the **long-tail latency from a few slow messages in a large prefetch batch**. If `prefetch_count=250` and one message takes 60 seconds (e.g., a third-party API call that times out), the other 249 messages in the prefetch batch wait behind it — the consumer's p99 latency is dominated by the slowest message in any given prefetch batch, even though the *average* throughput is fine. The fix is either (a) reduce `prefetch_count` so the slow message blocks fewer siblings, (b) move slow messages to a separate queue with `prefetch_count=1` so they don't poison the fast-message queue, or (c) implement a per-message timeout in the consumer that calls `basic.nack` with `requeue=true` after a deadline (and use a dead-letter retry queue to avoid infinite requeue loops). The failure mode of the broker alarms is the **publishers-stall-forever death loop**: if the disk alarm trips and the disk does not free up (e.g., because the consumer is also dead and the queue is unbounded), publishers block forever and the application's publish calls hang indefinitely — the fix is the `blocked_connection_timeout` connection parameter (default `None` = infinite; set to 300 seconds so the client raises an exception instead of hanging). See [[07.01.01. The Architectural Divide in Asynchronous Messaging]] for how this differs from Kafka's pull model where slow consumers do not backpressure producers at all.

## How This Connects to the Frameworks

Every framework in Section 05 has an AMQP client integration that exposes the exchange/queue/binding model as language-native objects. Spring Boot ships `spring-boot-starter-amqp` which auto-configures a `CachingConnectionFactory` (one long-lived AMQP connection, channels borrowed from a pool per operation) and a `RabbitTemplate` that wraps `basic.publish` with serialization and routing-key resolution. The `@RabbitListener` annotation on a method declares a queue, binds it to an exchange, registers a consumer, and dispatches each delivered message to the annotated method — the framework handles `basic.ack` automatically (after the method returns successfully) and `basic.nack` (after the method throws, controlled by a `RetryTemplate` and a `MessageRecoverer`).

```java
// Spring Boot: declarative RabbitMQ consumer with retry + DLQ
@Configuration
class RabbitConfig {
    @Bean TopicExchange events() { return new TopicExchange("events", true, false); }
    @Bean Queue orders() {
        return QueueBuilder.durable("orders")
            .withArgument("x-dead-letter-exchange", "orders.dlx")
            .withArgument("x-dead-letter-routing-key", "orders.failed")
            .build();
    }
    @Bean Binding bindOrders() {
        return BindingBuilder.bind(orders()).to(events()).with("orders.#");
    }
}

@Component
class OrderConsumer {
    @RabbitListener(queues = "orders", concurrency = "3-10", ackMode = "AUTO")
    public void handle(OrderCreated event) {        // Spring acks on return; nacks on throw
        orderService.process(event);                // throws → DLX gets the message
    }
}
```

Express (Node.js) uses `amqplib` directly — there is no Spring-style annotation magic. The developer opens a connection at app startup, opens a channel per worker, declares exchanges and queues with `assertExchange`/`assertQueue`/`bindQueue`, and calls `consume` with a callback that receives the message and must explicitly call `channel.ack(msg)` or `channel.nack(msg)`. Django/Flask use `pika` (synchronous) or `aio_pika` (async); the wiring is manual, identical in shape to the Node code. Laravel has `php-amqplib` and the `vluzrmos/laravel-rabbitmq` package that integrates RabbitMQ with Laravel's `Queue` facade — the framework abstracts AMQP behind the same `Bus::dispatch(new SendOrderEmail($order))` API you would use for any other queue driver, which is convenient but hides the routing topology from the developer. The takeaway across ecosystems: AMQP's exchange/binding model is the same everywhere; what differs is how much of the topology declaration the framework does for you (Spring: all of it via annotations; Express: none of it, you write the wiring code) and how the acknowledgment semantics are surfaced (Spring: implicit via method return; Express: explicit `channel.ack()` call).
