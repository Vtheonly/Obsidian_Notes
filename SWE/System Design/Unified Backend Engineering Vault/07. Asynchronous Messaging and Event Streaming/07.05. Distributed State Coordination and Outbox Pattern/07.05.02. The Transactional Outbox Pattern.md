# 07.05.02. The Transactional Outbox Pattern

## What This Is

The transactional outbox pattern is the standard answer to the dual-write problem from [[07.05.01. The Dual-Write Problem]]. The trick is to make the message you wanted to publish to Kafka *itself a row in a database table*, and to insert that row in the **same database transaction** as the business mutation it describes. Because both writes go through one PostgreSQL `BEGIN`/`COMMIT`, they share the same WAL commit record — either both are durable or neither is, and the dual-write problem disappears. A separate process — the "publisher" — then reads the outbox table and forwards rows to Kafka. If the publisher crashes or Kafka is unreachable, the rows simply accumulate in the outbox; when Kafka comes back, the publisher catches up. No message is ever lost, because the message was already committed to the database before Kafka was even contacted.

This note covers the four facets that matter in production: the architecture and how it eliminates dual-write; the two main event-relaying strategies (polling publisher vs. CDC/log-tailing); the specifics of the polling publisher with `SELECT ... FOR UPDATE SKIP LOCKED`; and the specifics of transaction-log tailing (Debezium reading the WAL/binlog). Each strategy has different operational characteristics: the polling publisher is simpler to deploy but adds query load to the database and a seconds-level latency floor; CDC is more complex (Kafka Connect cluster + connector configuration + schema-history topic) but has sub-second latency and zero query load on the business tables.

The mental model: the outbox pattern is the bridge between the ACID world (section 06 — databases, transactions, WAL) and the eventually-consistent world (section 07 — Kafka, RabbitMQ, async messaging). It uses the ACID guarantee of one system to fake an ACID guarantee across two systems. The outbox table is the seam. See [[07.05.01. The Dual-Write Problem]] for *why* this is necessary; see [[07.05.03. Change Data Capture (CDC) and Debezium]] for *how* the CDC variant reads the row out of the database without polling.

## The Details

### Architecture: Writing domain mutations and outbox event records within the same ACID da...

The outbox pattern's invariant is **one transaction, two writes, one commit record**. Inside a single database transaction, the application writes (a) the business mutation (an `INSERT`/`UPDATE`/`DELETE` against a domain table) and (b) an `INSERT` into the `outbox` table capturing the corresponding event. Both writes share the same WAL record, the same MVCC snapshot, and the same commit record. If the transaction commits, both are durable; if it rolls back, neither exists. The dual-write problem is dissolved because there is only one write target — the database — and the broker is downstream of it, not parallel to it.

```text
   Application             PostgreSQL                       Kafka
   ───────────             ───────────                       ─────
   BEGIN;
   INSERT INTO orders ...        ┐
   INSERT INTO outbox ...        ├─ same txn, same WAL commit record
   COMMIT;                       ┘
                          ↓ (commit succeeds, both rows durable)
                          │
                          │   (separate process, the "publisher")
                          │   SELECT * FROM outbox WHERE published_at IS NULL;
                          │   for each row: kafka.send(...)
                          │   UPDATE outbox SET published_at = now() WHERE id = ?;
                          └──────────────────────────────────► topic "orders"
```

The outbox table itself is deliberately boring — a flat, append-only event log with no foreign keys to the domain tables (so domain row deletion cannot cascade-delete the event):

```sql
CREATE TABLE outbox (
    id              BIGSERIAL    PRIMARY KEY,
    aggregate_id    VARCHAR(64)  NOT NULL,        -- e.g. "order-42"
    aggregate_type  VARCHAR(32)  NOT NULL,        -- e.g. "Order"
    event_type      VARCHAR(64)  NOT NULL,        -- e.g. "OrderPlaced"
    payload         JSONB        NOT NULL,        -- the event body
    headers         JSONB        NOT NULL DEFAULT '{}',  -- trace-id, etc.
    created_at      TIMESTAMPTZ  NOT NULL DEFAULT now(),
    published_at    TIMESTAMPTZ                      -- NULL = not yet published
);

CREATE INDEX outbox_unpublished_idx
    ON outbox (created_at)
    WHERE published_at IS NULL;                  -- partial index, fast scans

-- Optional: an in-flight marker for the polling publisher's two-phase claim
ALTER TABLE outbox ADD COLUMN claimed_at TIMESTAMPTZ;
ALTER TABLE outbox ADD COLUMN claimed_by  TEXT;
```

The crucial schema decisions: (1) the `id` is `BIGSERIAL` so it provides a globally monotonic order across all event types — you can replay events in insertion order. (2) `aggregate_id` is a *string* (`order-42`), not a foreign key, because foreign keys to domain tables would couple the outbox to domain deletes (an `ON DELETE CASCADE` would silently nuke audit events when an order is deleted). (3) `payload` is `JSONB` so the schema is forward-compatible: adding a field to an event does not require a migration. (4) The partial index `WHERE published_at IS NULL` keeps the index small (it only indexes unpublished rows, which is the working set the publisher scans) — without it, every published row would bloat the index forever. (5) `published_at` (and optionally `claimed_at`) is the publisher's progress marker; rows with `published_at IS NULL` are still pending.

Here is the Spring Boot code that implements the pattern, end-to-end. The `@Transactional` boundary covers both writes; the publisher is a separate `@Component`:

```java
// Service — does both writes inside one @Transactional block
@Service
class OrderService {
    private final OrderRepository orderRepo;
    private final OutboxRepository outboxRepo;

    @Transactional
    public Order placeOrder(OrderRequest req) {
        Order order = orderRepo.save(req.toOrder());        // (1) business mutation

        outboxRepo.save(new OutboxEvent(                    // (2) event row, same txn
            "order-" + order.getId(),
            "Order",
            "OrderPlaced",
            Map.of("orderId", order.getId(),
                   "customerId", order.getCustomerId(),
                   "total", order.getTotal(),
                   "placedAt", order.getCreatedAt()),
            Map.of("traceId", MDC.get("traceId"))
        ));
        return order;
    }
}

// JPA entity — append-only
@Entity @Table(name = "outbox")
class OutboxEvent {
    @Id @GeneratedValue(strategy = IDENTITY)
    Long id;
    String aggregateId, aggregateType, eventType;
    @JdbcTypeCode(SqlTypes.JSON) Map<String, Object> payload;
    @JdbcTypeCode(SqlTypes.JSON) Map<String, String> headers;
    Instant createdAt = Instant.now();
    Instant publishedAt;          // null until publisher confirms Kafka ack
}
```

The outbox pattern eliminates dual-write entirely. Inside `placeOrder`, there is no Kafka producer call. The transaction commits with the order row and the outbox row together. If the database crashes between commit and recovery, the ARIES algorithm (see [[06.03.04. WAL, Undo Log, and ARIES Recovery]] or your equivalent) replays the WAL and both rows either survive or don't — there is no scenario where one survives and the other doesn't. The only failure window is now between "database commits" and "publisher reads and forwards to Kafka", and that window is **safe by construction**: the outbox row is in the database, durable, and the publisher will eventually pick it up. Worst case the publisher is slow; the message is never lost.

The production failure mode of the outbox pattern itself (not the relay strategy — see the next three H3s for those) is **table bloat**. The outbox grows by one row per business mutation, forever. A system doing 1000 orders/sec writes ~86M outbox rows per day, ~2.5B per month. At ~500 bytes per row that's ~1.2TB/month of outbox data, all of it indexed by the partial index until the publisher marks it published. Even with the partial index keeping the working set small, the table itself grows without bound. The standard fix is a `partition by range (created_at)` and a scheduled job that drops partitions older than N days after the publisher has confirmed everything in them is published. The metric that reveals bloat: `pg_total_relation_size('outbox')` grows monotonically, and `SELECT count(*) FROM outbox WHERE published_at IS NULL` stays small (good) while `SELECT count(*) FROM outbox` explodes (bad — you need partitioning or archival).

### Event Relaying strategies

Once the outbox row exists, *something* has to read it and publish to Kafka. There are exactly two strategies in production use today, and the choice between them is the most consequential outbox decision you will make:

| Strategy | Mechanism | Latency | DB load | Operational complexity | Failure mode |
|---|---|---|---|---|---|
| **Polling publisher** | `SELECT ... FOR UPDATE SKIP LOCKED` every N seconds | seconds (typically 1-5s) | one query per poll cycle + index maintenance | low — a single worker process | missed rows on partition boundary; load on DB |
| **CDC / log tailing** (Debezium) | tail the WAL/binlog, emit `INSERT` events as Kafka messages | sub-second (typically 100-500ms) | zero query load on business tables | high — Kafka Connect cluster + connector config + schema history topic | connector restart replays from last offset; schema changes break the connector |
| **Trigger + listen/notify** | Postgres `NOTIFY` on insert; publisher `LISTEN`s | sub-second | one NOTIFY per insert, low | medium — fragile across DB restarts | NOTIFY payload size capped at 8KB; missed notifications on listener disconnect |

The polling publisher is the simplest possible thing that works: a periodic job runs `SELECT * FROM outbox WHERE published_at IS NULL ORDER BY id LIMIT 1000 FOR UPDATE SKIP LOCKED`, publishes each row to Kafka, and marks it published. The `FOR UPDATE SKIP LOCKED` clause is the magic that lets multiple publisher instances run concurrently — each one skips rows already locked by the others, so they divide the work without coordination. This is the strategy that fits "we have one Postgres and one Kafka and we want this to just work" — it's a 50-line Go/Java/Python program with no dependencies beyond the DB driver and the Kafka client.

The CDC strategy is more sophisticated: a separate piece of software (Debezium is the dominant open-source option, but Maxwell's daemon for MySQL and pgoutput-based tools for Postgres also exist) connects to the database as a replication client and reads the logical replication stream. Every `INSERT`/`UPDATE`/`DELETE` against any watched table appears as an event in the stream. Because the outbox table is just a table, every `INSERT` into it shows up in the WAL, and Debezium emits it as a Kafka message. The publisher step is now the database's own replication machinery, not a polling query — there is zero query load on the business tables and the latency is bounded by the WAL flush interval (typically 100-200ms).

The third option, Postgres `LISTEN`/`NOTIFY`, is worth mentioning because it's seductively simple: a trigger on the outbox table fires `NOTIFY outbox_channel, '<row_id>'` on every insert, and the publisher `LISTEN`s on that channel and wakes up instantly. But NOTIFY payloads are capped at 8KB, listeners silently miss notifications sent while they were disconnected, and the trigger overhead adds write latency to every business transaction. Most teams that try LISTEN/NOTIFY abandon it within a year for either polling (simpler) or CDC (lower latency and more robust).

```text
  Polling publisher timeline:
  t=0ms   Application commits txn with outbox row.
  t=500ms Publisher wakes up, SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1000.
  t=510ms Kafka send() returns ack.
  t=515ms UPDATE outbox SET published_at = now() WHERE id = ?.
  Total end-to-end latency: 500-1500ms (dominated by poll interval).

  CDC timeline (Debezium):
  t=0ms   Application commits txn with outbox row.
  t=2ms   WAL flush (wal_level=logical, synchronous_commit=on).
  t=5ms   Debezium's replication slot receives the logical change.
  t=10ms  Debezium publishes to Kafka via Kafka Connect.
  t=15ms  Kafka ack.
  Total end-to-end latency: 15-50ms.
```

The key trade-off is **operational complexity vs. latency**. A polling publisher is a single `java -jar publisher.jar` you can run anywhere; if it crashes, you restart it. A Debezium deployment is a Kafka Connect cluster (which itself runs as either a standalone process or as a set of workers with a backing `connect-configs`/`connect-offsets`/`connect-status` topics in Kafka), with a connector definition in JSON, with a schema-history topic, with a Postgres replication slot that must be monitored for lag. If you're already running Kafka Connect for other CDC use cases, adding an outbox connector is cheap; if you're not, the polling publisher is almost always the right first step and CDC is the upgrade path when latency requirements tighten.

The ordering guarantee is the same in both strategies if you scope it correctly. **Events for the same `aggregate_id` must be delivered to Kafka in the order they were written to the outbox** — otherwise the consumer might see `OrderCancelled` before `OrderPlaced` and reject the cancellation as a no-op. Both strategies preserve this *if* the publisher routes by `aggregate_id`: partition the Kafka topic by `hash(aggregate_id) mod N`, so all events for the same aggregate go to the same partition, and Kafka's per-partition ordering does the rest. The polling publisher must explicitly use `aggregate_id` as the Kafka partition key; CDC tools like Debezium default to using the table's primary key (`id`) as the Kafka message key, which is *not* what you want for the outbox (you want `aggregate_id`, not the outbox row's monotonic id), so you configure a Single Message Transform (SMT) to extract the `aggregate_id` field from the payload and use it as the key. See [[07.05.03. Change Data Capture (CDC) and Debezium]] for the SMT configuration.

### Polling Publisher: Background worker polling the outbox table (`SELECT ... FOR UPDATE S...

The polling publisher is a loop: every N seconds, claim a batch of unpublished rows, publish each to Kafka, mark each as published. The crucial SQL primitive is `SELECT ... FOR UPDATE SKIP LOCKED`, which is the Postgres / MySQL 8+ / SQL Server way of doing concurrent work-stealing without contention. `FOR UPDATE` acquires a row-level lock on each returned row; `SKIP LOCKED` causes the query to silently skip rows that are already locked by another transaction. So if publisher A and publisher B both run `SELECT * FROM outbox WHERE published_at IS NULL ORDER BY id LIMIT 1000 FOR UPDATE SKIP LOCKED` at the same time, A gets the first 1000 unpublished rows and B gets the next 1000 — without ever blocking each other. This is the same primitive Laravel uses internally for its database-backed queue.

```java
@Component
class OutboxPollingPublisher {
    private final JdbcTemplate jdbc;
    private final KafkaTemplate<String, String> kafka;
    private final MeterRegistry meters;

    @Scheduled(fixedDelay = 1000)   // every 1s after the previous run completes
    @Transactional
    public void drain() {
        List<OutboxRow> batch = jdbc.query(
            """
            SELECT id, aggregate_id, aggregate_type, event_type, payload, headers
            FROM outbox
            WHERE published_at IS NULL
            ORDER BY id
            LIMIT 500
            FOR UPDATE SKIP LOCKED
            """,
            (rs, i) -> new OutboxRow(
                rs.getLong("id"),
                rs.getString("aggregate_id"),
                rs.getString("event_type"),
                rs.getString("payload"),
                rs.getString("headers"))
        );

        if (batch.isEmpty()) return;

        for (OutboxRow row : batch) {
            try {
                kafka.send("outbox-events",
                           row.aggregateId(),          // partition key — preserves order
                           row.payload()).get();       // synchronous ack
                jdbc.update("UPDATE outbox SET published_at = now() WHERE id = ?",
                            row.id());
                meters.counter("outbox.published").increment();
            } catch (Exception e) {
                meters.counter("outbox.publish_failed").increment();
                throw e;     // rolls back the @Transactional — rows stay unpublished
                             // and will be retried by the next cycle
            }
        }
    }
}
```

There are four subtle implementation decisions in this code that separate a production-grade polling publisher from a tutorial one. **First**, the Kafka `send().get()` is synchronous — without `.get()`, you'd mark the row published before knowing the broker actually acked it, recreating the dual-write problem inside the publisher itself. The latency cost is one round-trip per row (typically 1-5ms within a datacenter); if that's too slow, batch the sends with `kafka.executeInTransaction(ts -> { batch.forEach(r -> kafka.send(...)); })` and use the Kafka Transactions API to get atomic "all-or-nothing" acks across the batch. **Second**, the `@Transactional` on `drain()` means the `SELECT ... FOR UPDATE SKIP LOCKED` locks and the `UPDATE published_at` updates commit together — so if the JVM crashes mid-batch, the locks are released and the rows go back to "unpublished", to be retried by the next cycle. Without `@Transactional`, a crash after `kafka.send()` but before `UPDATE published_at` would mean the message was sent to Kafka but the row still looks unpublished, and the next cycle would re-send it — duplicate delivery.

**Third**, the `LIMIT 500` batch size matters. Too small (e.g. 10) and you spend most of the cycle on round-trips; too large (e.g. 100000) and a single `@Transactional` runs for minutes, holding locks and growing the WAL. The sweet spot is "what you can publish in 1-2 seconds" — typically 100-1000 rows depending on payload size and Kafka latency. **Fourth**, the `@Scheduled(fixedDelay = 1000)` (not `fixedRate`) ensures you don't get overlapping runs if one cycle takes 3 seconds; `fixedRate` would start a new cycle every 1s regardless, piling up `@Async` invocations and eventually exhausting the scheduler pool. For multi-instance deployments, you need a leader-election layer (ShedLock for Spring, a Redis SET NX lock, or a database-backed advisory lock) so that only one instance polls at a time — otherwise every instance runs the same query, the `SKIP LOCKED` saves you from duplicates, but you're paying N× the DB load for no benefit.

```text
  Polling publisher failure modes:
  ┌──────────────────────────────┬───────────────────────────────────────────┐
  │ Failure                      │ Effect on outbox                         │
  ├──────────────────────────────┼───────────────────────────────────────────┤
  │ JVM crash mid-batch          │ Locks released, rows stay unpublished,    │
  │                              │ retried by next cycle. SAFE.             │
  │ Kafka unreachable            │ send().get() throws, txn rolls back,     │
  │                              │ rows stay unpublished. SAFE.             │
  │ kafka.send() succeeds,       │ If outside @Transactional: duplicate.    │
  │ UPDATE fails                 │ If inside @Transactional: row stays       │
  │                              │ unpublished, retried → duplicate.        │
  │                              │ → consumer must be idempotent.           │
  │ Outbox grows unbounded       │ Tail latency grows, index bloats.        │
  │                              │ Fix: partition + archive.                │
  │ Poll interval too long       │ End-to-end latency grows; SLO breach.    │
  │                              │ Fix: switch to CDC.                      │
  │ Multiple instances, no lock  │ SKIP LOCKED saves you from duplicates    │
  │                              │ but you pay N× DB load. Use leader-elec. │
  └──────────────────────────────┴───────────────────────────────────────────┘
```

The production failure mode for the polling publisher is **the duplicate-send on retry**. The pattern guarantees *at-least-once* delivery, not *exactly-once*. If `kafka.send()` succeeds but the surrounding `@Transactional` rolls back (e.g. because of a connection blip on the `UPDATE published_at`), the row stays unpublished and will be sent again on the next cycle — Kafka now has two copies. This is not a bug in the publisher; it is a structural property of any at-least-once relay. Consumers must be idempotent — typically by tracking the `outbox.id` of every event they've processed and ignoring duplicates. The metric that reveals duplicates: consumer-side counter `events_processed` is higher than producer-side `events_published` for the same window; or a consumer-side idempotency-key table is rejecting rows.

### Transaction Log Tailing: Tailing database write logs (WAL / Binlog) without table polli...

The CDC strategy replaces the polling publisher's `SELECT` with a replication stream: the database is already writing every committed change to its WAL (PostgreSQL) or binlog (MySQL) for the benefit of replicas and PITR. A CDC connector connects to the database as a logical replication client and receives a stream of row-level change events. No queries hit the business tables; the only DB-side cost is the maintenance of a logical replication slot that holds the WAL until the connector has consumed it. The outbox table is just another watched table, so every `INSERT` into it appears as a CDC event that Debezium (or Maxwell, or pgoutput) forwards to Kafka.

```text
   Application              PostgreSQL primary              Kafka Connect / Debezium          Kafka
   ───────────              ────────────────────             ──────────────────────────        ─────
   BEGIN; INSERT orders;    writes WAL record                (idle, no polling)
   INSERT outbox;           writes WAL record
   COMMIT;                  writes WAL commit record,        ┌─ replication slot receives
                           fsync(WAL)            ─────────► │  logical change: "INSERT into
                                                          │  outbox row id=42 payload={...}"
                                                          │
                                                          │  Debezium transforms to:
                                                          │  { "op":"c","after":{...}, "source":{...} }
                                                          └────────────────────────────────────►  topic:
                                                                                                    dbserver1.outbox
```

PostgreSQL's logical replication works at the row level: every committed transaction appears as a sequence of change records (`INSERT`/`UPDATE`/`DELETE` against specific tables) followed by a commit message. The connector subscribes to a *logical replication slot* (created with `pg_create_logical_replication_slot('debezium', 'wal2json')` or `pg_create_logical_replication_slot('debezium', 'pgoutput')`) and reads changes via the `pg_logical_slot_get_changes()` function or the streaming replication protocol. The slot acts as a bookmark: it tracks the LSN (Log Sequence Number) of the last change the connector consumed, and Postgres will not recycle WAL files past that LSN until the connector advances the slot. **If the connector is down for too long, WAL files accumulate on the primary's disk and eventually fill it** — this is the most common Debezium-related production incident.

MySQL's binlog works similarly but at the statement/row level depending on `binlog_format`. CDC tools require `binlog_format=ROW` (so the binlog contains the actual before/after row images, not the SQL statement). The connector connects as a replication slave (it speaks the MySQL replication protocol, `COM_BINLOG_DUMP`), receives binlog events, and translates them. The slot equivalent is the binlog filename + position (e.g. `mysql-bin.000042:12345`) which the connector persists in its `connect-offsets` topic.

The outbox pattern with CDC has a specific elegant property: **the outbox row is a self-describing event envelope**. Debezium emits every `INSERT` into the outbox table as a Kafka message whose `value` contains the row's columns (`aggregate_id`, `event_type`, `payload`, etc.). You then apply a Single Message Transform (SMT) called `ExtractTopic` and `SetSchemaMetadata` to project the `payload` JSON out of the Debezium envelope and route it to a topic named after `event_type` — so `OrderPlaced` events go to `order-placed`, `OrderCancelled` events go to `order-cancelled`, etc. The application code that wrote the outbox row didn't need to know the topic name; the CDC connector decides routing at emission time.

```json
// Raw Debezium event for an outbox INSERT (before SMT):
{
  "op": "c",
  "before": null,
  "after": {
    "id": 42,
    "aggregate_id": "order-42",
    "aggregate_type": "Order",
    "event_type": "OrderPlaced",
    "payload": {"orderId": 42, "customerId": 7, "total": 99.95},
    "headers": {"traceId": "abc-123"},
    "created_at": "2024-05-01T10:23:45.123Z",
    "published_at": null
  },
  "source": {
    "db": "shop",
    "schema": "public",
    "table": "outbox",
    "txId": 12345,
    "lsn": 678901,
    "ts_ms": 1714559025123
  },
  "transaction": {"id": "tx-12345"}
}
```

```json
// After EventRouter SMT (Debezium's outbox-specific transform):
// Topic: order-placed   (routed from event_type)
// Key:   order-42       (extracted from aggregate_id, preserves per-aggregate order)
// Value: {"orderId": 42, "customerId": 7, "total": 99.95, "traceId": "abc-123"}
```

The production failure mode of the CDC strategy is the **schema-change surprise**. The outbox table's schema can drift over time — a new column added, a column renamed, a type widened. Logical replication sends the row's column values *by name*, and if the connector's in-memory schema (which it persists to the `debezium_schema_history` topic) doesn't match the actual table schema at emit time, the connector will fail to deserialize the row and either skip it (silent data loss) or stop the connector entirely (visible outage). The mitigation is to either (a) freeze the outbox schema — once you've started CDC, no DDL on the outbox table without a coordinated connector pause — or (b) use a Debezium version that supports schema evolution (>= 1.9 with `schema.history.internal.kafka.topic` correctly configured). The metric that reveals this: the connector's `millisSinceLastEvent` metric spikes to infinity and the consumer-side topic goes silent while the database keeps writing rows. The `pg_replication_slots.confirmed_flush_lsn` for the Debezium slot lags behind `pg_current_wal_lsn()`, and `pg_stat_replication` shows the slot's `restart_lsn` stuck. See [[07.05.03. Change Data Capture (CDC) and Debezium]] for the deep dive on the connector internals, the SMT inventory, and the exactly-once guarantee when combined with Kafka transactions.

## How This Connects to the Frameworks

The outbox pattern is fundamentally a database pattern, not a framework pattern — but every framework that does dual-write needs an outbox implementation. Spring Boot has the cleanest story via `@Transactional` + a `JdbcTemplate` polling loop, or via Debezium's direct integration with Spring Boot 3's `spring-boot-starter-artemis` for ActiveMQ. Django's `transaction.on_commit()` callback lets you enqueue a Celery task that publishes to Kafka only after the commit succeeds — this is half of the outbox (it eliminates phantom messages) but doesn't eliminate lost messages, so a Django shop serious about durability either rolls a polling publisher or runs Debezium. Laravel's `DB::afterCommit()` is the equivalent. Node.js shops typically use a small BullMQ job enqueued on commit, with the worker doing the Kafka send — but again, this is only "half" the outbox. The cleanest framework-agnostic answer is always "CDC the outbox table" because it removes the polling process entirely and lets the database's own replication machinery do the relay.

```bash
# Spin up Postgres + Kafka + Debezium via the Debezium tutorial docker-compose:
git clone https://github.com/debezium/debezium-examples.git
cd debezium-examples/tutorial
docker-compose up -d

# Create the outbox table and a logical replication slot:
psql -h localhost -U postgres -d shop -c "
CREATE TABLE outbox (
    id BIGSERIAL PRIMARY KEY,
    aggregate_id VARCHAR(64) NOT NULL,
    aggregate_type VARCHAR(32) NOT NULL,
    event_type VARCHAR(64) NOT NULL,
    payload JSONB NOT NULL,
    headers JSONB NOT NULL DEFAULT '{}',
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    published_at TIMESTAMPTZ
);
```
