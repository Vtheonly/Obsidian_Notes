# 07.05.01. The Dual-Write Problem

## What This Is

The dual-write problem is the single most expensive bug in event-driven microservices. It arises whenever a service has to perform **two state mutations that must both succeed or both fail**, but the two mutations touch different systems that do not share a transaction coordinator. The textbook case: a service writes a row to its own PostgreSQL database *and* publishes a message to Kafka, and the business invariant is "if the database write committed, the message must be delivered — no exceptions, no compromises". There is no atomic, all-or-nothing primitive that spans a Postgres connection and a Kafka producer. You can either commit-then-publish (and lose the message if the publish fails), or publish-then-commit (and emit a phantom message if the commit fails), or attempt two-phase commit and pay the latency and availability cost.

This note is the conceptual root of the entire 07.05 sub-section: [[07.05.02. The Transactional Outbox Pattern]] and [[07.05.03. Change Data Capture (CDC) and Debezium]] exist specifically because the dual-write problem has no clean solution at the broker layer. The outbox pattern smuggles the broker write *into* the database transaction by writing the event as a row in an `outbox` table; CDC then tails that table from the WAL and emits it to Kafka. The outbox pattern is not a "neat trick" — it is the only practical answer to dual-write when 2PC is unacceptable, which is almost always. Read this note first to understand *why* the outbox has to exist; then read the outbox note to see *how* it works.

The mental model: at the OS layer from section 02, an `fsync` on a local file is atomic across crashes because the kernel knows about the inode. At the database layer from section 06, a `COMMIT` is atomic across crashes because the WAL has a single commit record that either made it to disk or didn't. But the moment you cross a process boundary, you have left the kernel's atomicity domain. Kafka's producer `send()` is a network write to a different process — there is no shared inode, no shared WAL, no shared commit record. The two systems have independent failure modes, and any sequence of "do A then do B" has a window between them where A has happened and B has not. The dual-write problem is the precise name for that window.

## The Details

### Root Cause: Inability to execute atomic transactions spanning a local database write and an exter...

A database transaction is atomic because the database engine, the WAL, and the storage layer all live inside one process tree and cooperate on a single commit record. When you call `COMMIT`, the engine writes one record to the WAL and `fsync`s it. If the `fsync` returns, the transaction is durable; if the kernel panics before the `fsync` returns, the engine will roll the transaction back during recovery because no commit record exists. There is no such shared commit record across "PostgreSQL commit" and "Kafka produce" — they are two separate processes talking to each other over TCP, and TCP gives you exactly-once delivery *of bytes*, not exactly-once *commits of business state*. The producer might successfully send the bytes to a Kafka broker, receive an ack, and crash before recording that it did so — leaving the message orphaned in Kafka with no record of who sent it.

Here is the dual-write code that *looks* fine and is in fact broken in three distinct ways:

```java
@Transactional
public void placeOrder(OrderRequest req) {
    Order order = orderRepo.save(req.toOrder());    // (1) DB write
    inventoryRepo.decrement(order.getSku(), order.getQty());
    kafka.send("orders", order.getId(), order.toJson());  // (2) broker publish
}
```

The three failure windows:

```text
  Sequence:    save(decrement)  ──►  COMMIT  ──►  kafka.send()  ──►  kafka.ack()
                                                ▲                  ▲
                                Window A:        │                  │
                                commit succeeded, kafka.send() throws
                                  → DB has the order, Kafka has no message
                                  → downstream consumers never learn about it
                                  → the shipping service never ships
                                Window B:                          │
                                kafka.send() succeeded, ack lost on the wire
                                  → producer retries → DUPLICATE message in Kafka
                                  → consumer double-processes the order
                                Window C (the @Transactional trap):
                                kafka.send() is inside @Transactional, but
                                  Kafka is NOT a participant in the JPA
                                  transaction — so if the COMMIT fails AFTER
                                  kafka.send() returned, the message is in
                                  Kafka but the DB has no order.
                                  → "phantom" message referencing non-existent order
```

Window A is the obvious one and the one engineers think about: the broker is down, or the network is partitioned, or the producer timed out. Window B is more subtle: the producer's `send()` is internally idempotent only if `enable.idempotence=true` and a `transactional.id` is set; without those, a retry after a network blip produces duplicate messages. Window C is the silent killer that catches Java engineers specifically, because `@Transactional` *looks like* it wraps everything inside one atomic boundary — but it only wraps the JPA EntityManagers that are registered with the Spring `PlatformTransactionManager`. Kafka is not registered. The Kafka `send()` will go out *immediately* (or be buffered in the producer and flushed at unknown time), regardless of whether the surrounding `@Transactional` later commits or rolls back.

The reason no clean fix exists at the broker layer is **the absence of a shared transaction coordinator**. The only generic protocol that provides atomic commit across heterogeneous resource managers is XA / two-phase commit (see next section), and it requires *every* participant — Postgres, the JDBC driver, Kafka, the Kafka producer — to implement the XA protocol. Kafka does not implement XA. Even if it did, the practical answer would still be "don't", because 2PC's latency and availability characteristics are unacceptable for the 99% of services that just need to send an email or update a search index. The dual-write problem is therefore not a bug to be fixed but a structural constraint to be designed around, and the two design answers are (a) the outbox pattern (write the broker write into the DB transaction) or (b) eventual-consistency with reconciliation (accept that some messages will be lost or duplicated and build idempotency + reconciliation jobs to detect and repair). Both answers are downstream of accepting that the dual-write itself cannot be atomic.

### Failure Scenarios: Database commits but broker publish fails; Broker publish succeeds but databas...

Concretely, the four production failure modes of dual-write — every senior engineer has debugged at least one of these in anger:

**Scenario 1: DB commits, Kafka publish fails.** A `OrderService.placeOrder()` calls `orderRepo.save()` then `kafka.send()`. The broker is briefly unreachable (a Kafka leader election, a network blip, the producer's `delivery.timeout.ms` of 120s expires). The Kafka producer throws `TimeoutException`. If the code is naively written, the exception propagates up and the user sees a 500 — but the `@Transactional` block has *already* committed the row to the database (because `kafka.send()` was the last line and the transaction auto-committed on successful return... or because `kafka.send()` is fire-and-forget and the exception comes from a callback). Result: the order is in the database, the customer's credit card is charged, but no `OrderPlaced` event was published. The shipping service never learns. The order sits "awaiting fulfilment" forever. A customer-service rep looks at the order in the admin panel and sees it exists. Nobody can explain why nothing was shipped. This is the "phantom order" incident — caused by the broker write failing after the DB commit. The metric that reveals it: `orders_committed_total` is higher than `order_placed_events_published_total` for the same minute.

**Scenario 2: DB commits, Kafka publish appears to succeed but the message is lost.** This is worse because there is no exception. The producer's `send()` is asynchronous by default — `kafka.send()` returns a `FutureMetadata` and the actual network send happens on a background thread. If the producer's buffer is full (`queue.buffering.max.messages` default 10000), or the broker is slow to ack, or the producer's background I/O thread dies, the send can fail silently. If your code doesn't `.get()` on the future, you never see the exception. Result: identical to Scenario 1, but with no exception in the logs. You find out three days later when a customer complains. The fix is to *always* `.get()` on the future (turning async into sync) and to log every failure — but that throws away the throughput benefit of async sends, which is why so many teams don't do it.

**Scenario 3: Kafka publish succeeds, DB rolls back — the phantom message.** If the code publishes to Kafka *before* the DB commit (because someone thought "let's get the event out early"), and then the DB transaction rolls back (a constraint violation, a deadlock, an application exception), the message is now in Kafka referencing a state that never persisted. Downstream consumers will process an `OrderPlaced` event for an order that doesn't exist in the source-of-truth database. They'll fail, retry, fail, exhaust retries, and either DLQ the message or silently drop it. Worse: if they cache or denormalise the order on their side, they now have a "ghost order" in their own database that the source system has no record of. Reconciliation jobs discover these by joining consumer-side state against producer-side state and finding rows that exist on one side but not the other.

**Scenario 4: Duplicate publish on retry — the at-least-once tax.** Even with `enable.idempotence=true` on the producer (which de-duplicates based on producer epoch + sequence number), the deduplication only works *within a single producer session*. If the producer crashes and a new instance starts up with a new `transactional.id` epoch, the dedup window is gone. Now a retry sends the same business event twice. Downstream consumers that aren't idempotent (e.g. "increment `orders_count`") will double-count. The naive mental model "Kafka is exactly-once" is wrong three times over: (a) Kafka's exactly-once semantics (EOS) only apply within a Kafka-to-Kafka transaction, not across DB-to-Kafka; (b) EOS requires `transactional.id` + `initTransactions` + `sendOffsetsToTransaction` and is rarely configured correctly; (c) even with EOS, the *consumer* side still needs to be idempotent because consumers can crash between processing and committing the offset, triggering a re-delivery.

```text
  Failure-mode matrix:
  ┌────────────────────┬────────────────┬────────────────┬───────────────────────┐
  │ Sequence           │ DB final state │ Kafka topic    │ Downstream consequence│
  ├────────────────────┼────────────────┼────────────────┼───────────────────────┤
  │ Commit → send ok   │ committed      │ 1 message      │ Correct               │
  │ Commit → send fail │ committed      │ 0 messages     │ Lost event, ghost row │
  │ Send ok → rollback │ rolled back    │ 1 message      │ Phantom event, DLQ    │
  │ Send ok → retry    │ committed      │ 2 messages     │ Duplicate processing  │
  │ Send async, drop   │ committed      │ 0 messages     │ Silent loss           │
  └────────────────────┴────────────────┴────────────────┴───────────────────────┘
```

Two-phase commit is the only generic protocol that provides atomic commit across heterogeneous resource managers. The protocol has two phases: in **phase 1 (prepare)**, a coordinator asks every participant "can you commit?" and each participant writes a prepare record to its own WAL and replies YES or NO. If all reply YES, in **phase 2 (commit)** the coordinator writes a commit record to its own log and asks every participant to commit; each participant commits and acks. If any participant replied NO, the coordinator sends ROLLBACK to all. The protocol's correctness rests on the coordinator's log being durable and on every participant being able to either commit or roll back unilaterally *after* it has voted YES, even across its own crashes (it must remember its vote in its WAL until the coordinator tells it the outcome).

```text
   Coordinator                Participant A           Participant B (Postgres)   Participant C (Kafka?)
   ───────────                ──────────────          ─────────────────────────  ──────────────────────
   PREPARE ──────────────────►│ vote YES, WAL ───────►│
   PREPARE ───────────────────────────────────────────────────────────────────►│  ← does Kafka support this?
                                                                       vote YES │
   ◄───────── YES, YES
   write commit record to coordinator log, fsync()
   COMMIT ──────────────────►│ apply, ack            │
   COMMIT ───────────────────────────────────────────────────────────────────►│  ← and this?
   ◄──────── ack, ack
```

XA is the Java/Jakarta standardisation of 2PC, exposing `XAResource.start()` / `XAResource.end()` / `XAResource.prepare()` / `XAResource.commit()` to application code via `UserTransaction`. PostgreSQL supports XA via its JDBC driver (`PGXADataSource`). MySQL supports XA via the `XA START` / `XA END` / `XA PREPARE` / `XA COMMIT` SQL syntax. **Kafka does not support XA** — the closest it has is its own Transactions API (`transactional.id` + `beginTransaction` + `commitTransaction`), which is Kafka-internal only and cannot enlist a Postgres write. So out of the box, you cannot do XA across Postgres + Kafka. Even if you could, 2PC's failure mode is infamous:

**Blocking on coordinator failure.** If the coordinator crashes after a participant has voted YES but before sending COMMIT or ROLLBACK, the participant is *blocked* — it cannot unilaterally commit (the coordinator might have decided rollback) nor roll back (the coordinator might have decided commit). It must hold its locks and wait for the coordinator to recover. During this window, every row the participant has locked is unreadable to other transactions. In Postgres this looks like `pg_stat_activity` showing many `idle in transaction` sessions with `wait_event = 'XidGen'` or lock waits; in MySQL it shows as `SHOW PROCESSLIST` rows with `State = 'Waiting for table metadata lock'`. A coordinator outage of minutes can lock the entire database for the duration. Production 2PC outages have been known to take entire order systems offline for hours while DBAs manually `XA RECOVER` and `XA COMMIT` one transaction at a time.

**Performance.** 2PC adds at least four extra network round-trips per transaction (prepare + vote + commit + ack) and two extra WAL `fsync`s per participant (one for the prepare record, one for the commit record). On a 1ms-latency network with NVMe storage (~100µs per fsync), a single-DB commit is ~200µs; a 2PC commit across Postgres + another participant is ~5ms — a 25× slowdown. On cross-region networks (50-100ms RTT), 2PC commits take 200-400ms each, which is incompatible with interactive workloads. This is why virtually no modern microservice architecture uses 2PC; the latency cost alone is disqualifying, and the blocking-on-coordinator-failure risk is the second nail.

**The practical reality: no atomic cross-system transaction without 2PC.** If you need atomic commit across two heterogeneous systems, your options are exactly: (a) use 2PC and accept the latency and blocking risk (almost never acceptable in microservices), (b) smuggle both writes into one system's transaction via the outbox pattern (see [[07.05.02. The Transactional Outbox Pattern]]), (c) accept eventual consistency and build idempotent consumers + reconciliation jobs, or (d) use a single system that owns both states (e.g. Kafka Streams's state stores + changelog topics, or an event-sourced system where the broker *is* the source of truth and the DB is a materialised view). Most production systems pick (b) for the DB-to-Kafka case because it preserves ACID semantics at the source and only requires eventual consistency at the consumer, which is the simplest possible model.

## How This Connects to the Frameworks

Every framework in section 05 that touches a database *and* a message broker exposes the dual-write problem to the application code. Spring Boot's `@Transactional` makes it especially insidious because the annotation *looks like* it covers everything inside the method, but Kafka/RabbitMQ/JMS producers are not transactional participants. Django's `transaction.on_commit(lambda: kafka.send(...))` hook is the Pythonic answer — it at least guarantees the publish only fires *after* a successful commit, eliminating Scenario 3 (phantom message). Laravel's `DB::beginTransaction()` + `DB::afterCommit(function () use ($event) { Kafka::send($event); })` is the equivalent. None of these eliminate Scenario 1 (lost message on broker failure) — for that you need the outbox.

## Hands-On Exercise

```bash
# Reproduce Scenario 1 (lost message):
# 1. Start a Postgres + a Kafka broker in Docker.
docker compose up -d postgres kafka
# 2. Run a service that does save-then-send, with the broker briefly unreachable.
docker compose stop kafka
# 3. Issue an order. The DB row is committed; the publish throws. Inspect:
psql -c "SELECT * FROM orders WHERE id = 1;"   # row exists
docker compose start kafka
kafka-console-consumer --bootstrap-server localhost:9092 --topic orders --from-beginning
# → empty: the message was never sent.

# Reproduce Scenario 3 (phantom message):
# 1. Code that publishes BEFORE commit, inside a transaction that fails.
docker compose start kafka
# 2. Add a NOT NULL constraint violation to force rollback after publish.
# 3. Issue the order. The publish happens, the commit fails. Inspect:
psql -c "SELECT * FROM orders WHERE id = 1;"   # row absent
kafka-console-consumer --bootstrap-server localhost:9092 --topic orders --from-beginning
# → message exists referencing order_id=1 that doesn't exist.

# Inspect 2PC behaviour in Postgres directly (no Kafka involved):
psql -c "CREATE TABLE accounts (id int PRIMARY KEY, balance int);"
psql -c "INSERT INTO accounts VALUES (1, 100), (2, 100);"
psql -c "BEGIN; UPDATE accounts SET balance = balance - 10 WHERE id = 1; PREPARE TRANSACTION 'tx1';"
# Now disconnect and reconnect — 'tx1' is still prepared and holding its lock:
psql -c "SELECT * FROM pg_prepared_xacts;"
psql -c "SELECT pid, state, wait_event FROM pg_stat_activity;"
# Either commit or roll back manually:
psql -c "COMMIT PREPARED 'tx1';"
# (Imagine the coordinator crashed between PREPARE and COMMIT — you'd be
# stuck doing this for every prepared transaction by hand.)
```
