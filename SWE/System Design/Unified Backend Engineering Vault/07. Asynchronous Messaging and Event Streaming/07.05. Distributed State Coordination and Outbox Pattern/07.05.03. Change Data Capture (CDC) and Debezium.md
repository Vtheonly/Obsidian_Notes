# 07.05.03. Change Data Capture (CDC) and Debezium

## What This Is

Change Data Capture is the technique of turning a database into an event stream by reading its transaction log — the WAL in PostgreSQL, the binlog in MySQL, the oplog in MongoDB, the transaction log in SQL Server, the redo log in Oracle. Instead of polling tables with `SELECT` queries (which adds load to the business workload and only sees the *current* state, not the change history), CDC taps the same log that the database uses internally for crash recovery and replication, and emits each row-level change as an event. The log is the single source of truth: it already contains every committed mutation in commit order, and reading it once gives you a perfect audit trail of every state transition the database has ever seen. CDC makes a static table feel like a Kafka topic.

Debezium is the dominant open-source CDC platform. It is implemented as a set of Kafka Connect source connectors — one per database engine — that subscribe to the database's replication stream, decode the log records, normalise them into a uniform change-event envelope, and publish them to Kafka topics. Debezium's contribution is not the CDC idea (database vendors have offered log-based replication for decades) but the *normalisation*: the same envelope shape across Postgres, MySQL, MongoDB, SQL Server, and Oracle, so downstream consumers don't have to know which engine produced a given event. Debezium is the layer that makes "every database is an event stream" a concrete operational reality rather than a vendor pitch.

This note covers the three facets that matter in production: the CDC principle (turning tables into streams by reading the log), the Debezium architecture (Kafka Connect source connectors + logical replication slots + schema history), and the event schema (the `before`/`after`/`op`/`source`/`transaction` envelope). For the *use* of CDC in the outbox pattern, see [[07.05.02. The Transactional Outbox Pattern]] — this note is about the CDC mechanism itself, applicable to outbox tailing, cache invalidation, search-index synchronisation, data warehouse loading, audit logging, and any other "react to a database change" use case.

The mental model: CDC sits at the seam between section 06 (databases — WAL, MVCC, logical replication) and section 07 (messaging — Kafka topics, partitions, consumer groups). It uses the layer-6 primitive (the WAL record from [[06.03.04. WAL, Undo Log, and ARIES Recovery]]) as input and produces the layer-7 primitive (the Kafka message with key, value, headers, partition, offset). The translation between them is what Debezium does.

## The Details

### CDC Principles: Converting static database tables into live event streams by reading th...

A table is, by definition, a snapshot — `SELECT * FROM orders` returns the current state, with no record of how it got there. CDC inverts this: instead of asking the table what its current state is, you ask the database's transaction log what *changes* have happened. The transaction log is an append-only sequence of records where every committed mutation is written before it is applied to the table's data pages — this is the WAL rule from [[06.03.04. WAL, Undo Log, and ARIES Recovery]]. By reading the log from a known position, you get the complete history of every row-level change, in commit order, without ever touching the table itself.

```text
   Application writes            Database transaction log (WAL / binlog)        CDC consumer
   ──────────────────            ───────────────────────────────────────        ────────────
   BEGIN;                        ─► LSN 1001: BEGIN txid=42
   INSERT INTO orders ...        ─► LSN 1002: INSERT row orders id=99 {...}
   INSERT INTO outbox ...        ─► LSN 1003: INSERT row outbox  id=1  {...}
   UPDATE inventory SET ...      ─► LSN 1004: UPDATE row inventory id=7 {...}
   COMMIT;                       ─► LSN 1005: COMMIT txid=42
                                              │
                                              │  (CDC connector reads from here)
                                              ▼
                                              Change event 1: { op:c, after:{orders.id:99,...} }
                                              Change event 2: { op:c, after:{outbox.id:1,...} }
                                              Change event 3: { op:u, before:{inv.qty:10}, after:{inv.qty:9} }
                                              (all three are atomically grouped by txid=42)
```

The two reasons CDC beats polling are **load** and **history**. On load: a polling publisher that runs `SELECT * FROM outbox WHERE published_at IS NULL` every second adds one query per second to the database's workload, plus the index maintenance on the partial index that supports the query. At 1000 inserts/sec on the outbox, that's a query that returns 1000 rows every second — not free. CDC, by contrast, reads the WAL via the replication protocol, which is a single long-lived connection that streams changes as they happen. There is no per-change query cost. On history: a polling publisher only sees the *current* state of `outbox` rows — if a row is deleted (by an archival job, say) before the publisher picks it up, the event is lost. CDC sees the `INSERT`, the `UPDATE`, and the `DELETE` as separate events — even if the row no longer exists, the change history is preserved in the log until the CDC consumer has consumed it.

There are two flavours of CDC: **log-based** (what Debezium does) and **query-based** (the older approach, where a trigger writes to a shadow table that a job polls). Query-based CDC is what you get if you build CDC yourself with triggers; it's simpler to reason about but adds write-path overhead (every `INSERT`/`UPDATE`/`DELETE` to the business table now also does an `INSERT` to the shadow table, doubling write amplification) and only sees the latest state of each row (intermediate updates within the same second are coalesced). Log-based CDC has zero write-path overhead on the business tables — the WAL is being written anyway — and preserves every intermediate state. The only log-based CDC cost is the replication slot's hold on WAL retention: Postgres won't recycle WAL files past the slot's `confirmed_flush_lsn`, so a slow consumer fills the primary's disk. The trade-off is therefore "free read load, but monitor disk space" vs. "extra write cost, but bounded disk usage".

The CDC delivery guarantee is **exactly-once with respect to the log, at-least-once with respect to Kafka**. Every committed transaction in the database appears in the log exactly once; the CDC connector sees each change record exactly once. But the connector's "I published this to Kafka" state is its own offset (stored in the `connect-offsets` topic), and if the connector crashes after publishing to Kafka but before advancing its offset, the next incarnation of the connector will re-read the same WAL record and re-publish to Kafka — a duplicate. To get true exactly-once across DB-to-Kafka, you need Debezium's transaction metadata feature plus Kafka Transactions API: the connector opens a Kafka transaction at the start of a database transaction, publishes all the transaction's changes within that Kafka transaction, and commits the Kafka transaction atomically with advancing its offset. This is the "exactly-once" guarantee that Debezium advertises — but it requires `transactional.id` to be set on the Kafka producer, `isolation.level=read_committed` on consumers, and the source database to provide transaction boundaries in its log (Postgres does via the `pgoutput` plugin's transaction messages, MySQL does via `BEGIN`/`COMMIT` markers in the binlog).

### Debezium Architecture: Kafka Connect source connectors parsing PostgreSQL logical repli...

Debezium is implemented as a set of Kafka Connect source connectors. Kafka Connect is a framework that ships with Apache Kafka for running source connectors (DB → Kafka) and sink connectors (Kafka → DB) as managed workers. A Connect cluster is a set of worker processes (JVMs) that share configuration, offsets, and status via three internal Kafka topics (`connect-configs`, `connect-offsets`, `connect-status`). Connectors are submitted as JSON to the REST API on `http://connect:8083/connectors`; the framework assigns the connector's tasks to workers, restarts them on failure, and rebalances them when workers join or leave. Debezium's connectors are *source* connectors — they pull from a database and write to Kafka.

```text
   ┌─────────────────┐         ┌─────────────────────────────────────────────┐         ┌──────────────┐
   │ PostgreSQL      │         │ Kafka Connect cluster (Debezium workers)    │         │ Kafka        │
   │ (source DB)     │         │                                              │         │              │
   │  WAL            │◀────────│ 1. PostgresConnector task opens             │         │ topics:      │
   │  logical        │ stream  │    replication connection with slot         │         │  shop.public.│
   │  replication    │         │    name="debezium"                          │────────│  orders       │
   │  slot           │         │ 2. Receives change events via pgoutput      │         │  shop.public.│
   │                 │         │    protocol                                 │         │  outbox       │
   │                 │         │ 3. Decodes to Debezium envelope             │         │  shop.public. │
   │                 │         │ 4. Looks up schema in schema-history topic  │         │  inventory    │
   │                 │         │ 5. Produces to Kafka topic                  │         │              │
   │                 │         │    named "{server}.{schema}.{table}"        │         │  + __schema_  │
   │                 │         │ 6. Advances offset (LSN) in                 │         │    history.   │
   │                 │         │    connect-offsets topic                    │         │    shop-db    │
   └─────────────────┘         └─────────────────────────────────────────────┘         └──────────────┘
```

Each connector has a specific configuration. The most important knobs for the Postgres connector:

```json
{
  "name": "shop-postgres-connector",
  "config": {
    "connector.class": "io.debezium.connector.postgresql.PostgresConnector",
    "database.hostname": "postgres-primary",
    "database.port": "5432",
    "database.user": "debezium",
    "database.password": "${env:DEBEZIUM_PASSWORD}",
    "database.dbname": "shop",
    "database.server.name": "shop-db",
    "plugin.name": "pgoutput",
    "slot.name": "debezium_shop",
    "publication.name": "dbz_shop_pub",
    "table.include.list": "public.orders,public.outbox,public.inventory",
    "column.exclude.list": "public.orders.credit_card_number",
    "tombstones.on.delete": "true",
    "snapshot.mode": "initial",
    "slot.drop.on.stop": "false",
    "slot.max.retries": "6",
    "slot.retry.delay.ms": "10000",
    "schema.history.internal.kafka.topic": "shop-db.schema-history",
    "schema.history.internal.kafka.bootstrap.servers": "kafka:9092",
    "transforms": "unwrap,extractTopic",
    "transforms.unwrap.type":
        "io.debezium.transforms.ExtractNewRecordState",
    "transforms.extractTopic.type":
        "org.apache.kafka.connect.transforms.RegexRouter",
    "transforms.extractTopic.regex": "shop-db.public.(.*)",
    "transforms.extractTopic.replacement": "shop.$1"
  }
}
```

The configuration knobs that matter most:

- **`connector.class`** selects the engine: `PostgresConnector`, `MySqlConnector`, `MongoDbConnector`, `SqlServerConnector`, `OracleConnector`. Each implements the same Kafka Connect source-connector interface but parses its engine's specific log format.
- **`database.server.name`** is the logical name that becomes the prefix for all emitted Kafka topic names — every change to `shop.orders` goes to topic `shop-db.public.orders` (server name + schema + table). This lets you run multiple Debezium connectors pointed at different databases without topic-name collisions.
- **`table.include.list`** (formerly `table.whitelist`) restricts CDC to specific tables — every table not in this list is ignored. The complement is `table.exclude.list`; you use one or the other.
- **`plugin.name`** for Postgres is one of `pgoutput` (the default since Debezium 1.0, uses Postgres's native logical replication protocol), `wal2json` (a third-party output plugin that emits JSON), `decoderbufs` (Protocol Buffers). `pgoutput` is what Postgres ships built-in since version 10; the others require installing an extension.
- **`slot.name`** and **`publication.name`** are Postgres-specific. A *publication* is a set of tables that Postgres will replicate (`CREATE PUBLICATION dbz_shop_pub FOR TABLE orders, outbox, inventory`); a *replication slot* is the bookmark that tracks how far the consumer has read. Debezium creates both automatically on first start; you can verify with `SELECT * FROM pg_replication_slots` and `SELECT * FROM pg_publication`.
- **`snapshot.mode`** controls what happens on the connector's first start, when there is no offset yet. `initial` (the default) takes a consistent snapshot of every watched table before starting to stream the WAL — this lets the connector emit existing rows as `INSERT` events before catching up to live changes. `schema_only` skips the snapshot and starts at the current WAL position (you lose history before the connector started). `never` is the same as `schema_only` but is deprecated. `recovery` re-syncs the schema history topic without re-snapshotting data.
- **`schema.history.internal.kafka.topic`** is critical. The CDC stream contains row-level changes but to decode them, the connector needs to know the table's schema (column names, types, nullability) *at the time of each change*. Schema changes (DDL) on the watched tables are interleaved with data changes in the WAL, and Debezium persists them to a Kafka topic so the connector can re-build the schema at any LSN on restart. **Losing this topic is catastrophic** — the connector cannot decode the WAL without the schema, and the only recovery is `snapshot.mode=schema_only_recovery` (which re-snapshots the schema) or, worst case, dropping the replication slot and re-snapshotting from scratch.

The **single-message transforms (SMTs)** are a Kafka Connect feature that Debezium leans on heavily. An SMT is a small in-pipeline transformer that modifies each record before it lands in Kafka. The most useful Debezium-specific SMTs are:

- `io.debezium.transforms.ExtractNewRecordState` — flattens the Debezium envelope, dropping the `before` field and emitting only the `after` state. Useful when consumers don't care about the before-image (most analytics use cases).
- `io.debezium.transforms.outbox.EventRouter` — the outbox-specific SMT described in [[07.05.02. The Transactional Outbox Pattern]]. Projects the `payload` JSON out of the envelope and routes by `event_type` to per-event-type topics.
- `io.debezium.transforms.ByLogicalKeyRouter` — repartitions events by a key extracted from the row's fields (e.g. use `customer_id` instead of the table's primary key, so all events for a customer land in the same Kafka partition).
- `org.apache.kafka.connect.transforms.SetSchemaMetadata` — overrides the schema name/version, useful when downstream consumers expect a specific schema name.
- `org.apache.kafka.connect.transforms.TimestampConverter` — normalises timestamp formats across engines (Postgres uses microseconds, MySQL uses seconds, etc.).

The production failure mode of Debezium is **the replication-slot WAL retention explosion**. Postgres will not recycle WAL segments past a replication slot's `restart_lsn` until the slot has confirmed consumption. If Debezium is stopped (a connector crash, a Kafka Connect cluster outage, a misconfigured `slot.drop.on.stop=true` that someone set during testing and forgot to unset) for hours or days, the primary's `pg_wal/` directory grows unbounded until the disk fills and the database crashes. The mitigation is (a) monitor `pg_replication_slots.restart_lsn` vs `pg_current_wal_lsn()` and alert when lag exceeds a threshold (e.g. 1GB); (b) configure `max_slot_wal_keep_size` (Postgres 13+) to cap the WAL retained for a slot at, say, 10GB — beyond that the slot becomes "inactive" and Postgres will recycle WAL past it (which means the connector cannot recover without a re-snapshot, but the database stays up); (c) use a separate Postgres replica for Debezium rather than connecting to the primary, so CDC reads happen against the replica's WAL — but this only works if the replica is also a logical replication source (`hot_standby_feedback=on` and the slot is on the replica, not the primary). The metric that reveals an impending disaster: `pg_wal_size` growing linearly and `pg_replication_slots.active = false` for the Debezium slot — the connector is not consuming and the WAL is piling up.

### Event Schemas: Capturing `before` state, `after` state, operation type (`CREATE`, `UPDA...

Every Debezium event is a single Kafka message whose value is a structured envelope with five top-level fields: `before`, `after`, `op`, `source`, `transaction`. The envelope is the same shape across all five supported databases — that's Debezium's main value-add, normalising the engine-specific log formats into one consumer-friendly schema. Understanding the envelope is the prerequisite to consuming Debezium events: every downstream service, every stream processor, every schema registry entry keys off this shape.

```json
{
  "before": {
    "id": 42,
    "customer_id": 7,
    "total": 100.00,
    "status": "PENDING"
  },
  "after": {
    "id": 42,
    "customer_id": 7,
    "total": 100.00,
    "status": "SHIPPED"
  },
  "op": "u",
  "ts_ms": 1714559025123,
  "source": {
    "version": "2.5.0.Final",
    "connector": "postgresql",
    "name": "shop-db",
    "db": "shop",
    "schema": "public",
    "table": "orders",
    "txId": 12345,
    "lsn": 678901,
    "xmin": null,
    "ts_ms": 1714559025000
  },
  "transaction": {
    "id": "12345:7",
    "total_order": 3,
    "data_collection_order": 2
  }
}
```

Field-by-field:

- **`op`** is the operation type. Four values: `c` (create / insert), `u` (update), `d` (delete), `r` (read — emitted during the initial snapshot, not a real mutation). The `r` op is the source of much confusion: it makes the snapshot look like a stream of inserts, but downstream consumers that filter `op != 'd'` will process snapshot rows as if they were live inserts. This is usually what you want (you want the consumer's state to mirror the database's current state after the snapshot), but if your consumer has side effects (sends an email on every `OrderPlaced`), you must filter `op == 'r'` events to avoid sending emails for every historical order during a backfill.
- **`before`** is the row's state *before* the mutation. For `c`/`r` operations, this is `null`. For `u`/`d` operations, it contains the previous column values. Postgres only populates `before` if the table has `REPLICA IDENTITY FULL` (the default is `DEFAULT`, which only populates the primary key for `DELETE`s and only the changed columns for `UPDATE`s) — set `ALTER TABLE orders REPLICA IDENTITY FULL` if you need the full before-image. MySQL's binlog always includes the before-image for `UPDATE`/`DELETE` if `binlog_row_image=FULL` (the default since MySQL 5.6); setting `binlog_row_image=MINIMAL` strips it to save space.
- **`after`** is the row's state *after* the mutation. For `d` operations, this is `null`. For `c`/`u`/`r` operations, it contains the new column values.
- **`source`** is the metadata about where this change came from. `lsn` (Log Sequence Number) is the Postgres WAL position; `binlog.file` + `binlog.pos` is the MySQL equivalent; `ts_ms` is the time the database committed the change (not the time Debezium processed it — the difference can be hundreds of milliseconds under load). `txId` is the transaction ID, which lets you group events that were committed together.
- **`transaction`** is present only if the connector has `"transaction.metadata.enabled": "true"`. It tells you this event was the 2nd of 3 row changes in transaction `12345`. This is essential for consumers that need to apply transactional semantics on the consumer side (e.g. a stream processor that emits per-transaction aggregates).

```text
  Operation matrix:
  ┌──────┬─────────────┬─────────────┬────────────────────────────────────────────┐
  │ op   │ before      │ after       │ when emitted                              │
  ├──────┼─────────────┼─────────────┼────────────────────────────────────────────┤
  │ "r"  │ null        │ full row    │ initial snapshot, one per existing row    │
  │ "c"  │ null        │ full row    │ INSERT committed                         │
  │ "u"  │ full row*   │ full row    │ UPDATE committed (* depends on REPLICA ID)│
  │ "d"  │ full row*   │ null        │ DELETE committed (* depends on REPLICA ID)│
  └──────┴─────────────┴─────────────┴────────────────────────────────────────────┘

  After a DELETE, Debezium also emits a "tombstone" record (value = null)
  if tombstones.on.delete=true (default). This lets Kafka compaction
  physically delete the key from the topic, preventing unbounded growth.
```

The **exactly-once guarantee** when combined with Kafka transactions requires three components working together. (1) The Debezium connector must have `"provide.transaction.metadata": "true"` so the WAL's transaction boundaries propagate to Kafka. (2) The Kafka producer used by the connector must be configured with `transactional.id=debezium-shop-db` and `enable.idempotence=true`, and the connector wraps each database transaction's worth of changes in a Kafka `beginTransaction()` / `commitTransaction()` pair. (3) The Kafka consumer must have `isolation.level=read_committed` so it only sees messages from committed Kafka transactions. With all three, the guarantee is: a database transaction's changes either all appear in Kafka (committed Kafka transaction) or none appear (aborted Kafka transaction). Without all three, you get at-least-once delivery with potential duplicates on connector restart.

The **schema-evolution failure mode** is the most common cause of Debezium production outages. When you `ALTER TABLE orders ADD COLUMN discount_code TEXT`, the WAL starts including the new column in subsequent row changes. Debezium needs to know the new schema to decode the row — it gets this from the DDL event that precedes the data events in the WAL, which it persists to the `schema.history.internal.kafka.topic`. If the schema-history topic is unavailable (the Kafka cluster is partitioned, the topic was accidentally deleted, the topic's retention was set too low and old DDL events aged out), Debezium cannot decode the new WAL records and the connector fails. The recovery is `snapshot.mode=schema_only_recovery`, which re-snapshots the schema without re-snapshotting data, but it requires the connector to be stopped and restarted with the new mode, during which time no changes are emitted. The mitigation: (a) set `schema.history.internal.kafka.topic` to a topic with `cleanup.policy=compact` and infinite retention (never let the schema history age out); (b) treat any DDL on a Debezium-watched table as a coordinated change that requires pausing the connector and verifying the schema-history topic is healthy before resuming; (c) monitor the connector's `LastError` metric and alert on any schema-decode failures. See [[07.05.02. The Transactional Outbox Pattern]] for how CDC slots into the broader dual-write / outbox picture.

## How This Connects to the Frameworks

CDC is infrastructure, not framework code — the application does not call Debezium directly. But every framework that touches a database ends up needing CDC for one of three use cases: (1) cache invalidation (the application caches reads; CDC events trigger cache eviction when the underlying row changes), (2) search-index synchronisation (Postgres is the source of truth; Elasticsearch is the read-optimised view; CDC keeps them in sync), (3) event publishing (the outbox pattern from [[07.05.02. The Transactional Outbox Pattern]]). Spring Boot has `debezium-embedded` for running a Debezium connector in-process (no Kafka Connect cluster needed — useful for single-service cache invalidation), and `spring-cloud-stream-binder-kafka` for consuming the resulting Kafka topics. Django and Laravel shops typically run Debezium as a separate Kafka Connect cluster and consume from Kafka in their application workers — no framework integration beyond "use the Kafka client". The point is that CDC is broker-level infrastructure: the application code that produces the changes is unaware that CDC exists; the application code that consumes the changes sees a Kafka topic, not a database table.

## Hands-On Exercise

```bash
# Spin up the canonical Debezium tutorial stack:
git clone https://github.com/debezium/debezium-examples.git
cd debezium-examples/tutorial
docker-compose up -d

# Verify Postgres has the wal_level=logical setting required for CDC:
docker-compose exec postgres psql -U postgres -c "SHOW wal_level;"
# wal_level should be "logical". If "replica" or "minimal", CDC cannot work.

# Create the replication slot and publication manually (Debezium would do this
# automatically, but doing it by hand helps you see what's happening):
docker-compose exec postgres psql -U postgres -c "
SELECT * FROM pg_create_logical_replication_slot('debezium', 'pgoutput');
CREATE PUBLICATION dbz_pub FOR TABLE inventory.products;
"

# Register a Postgres connector:
curl -i -X POST -H "Content-Type: application/json" \
  http://localhost:8083/connectors \
  --data '{
    "name": "inventory-connector",
    "config": {
      "connector.class": "io.debezium.connector.postgresql.PostgresConnector",
      "database.hostname": "postgres",
      "database.port": "5432",
      "database.user": "postgres",
      "database.password": "postgres",
      "database.dbname": "inventory",
      "database.server.name": "shop",
      "plugin.name": "pgoutput",
      "slot.name": "debezium",
      "publication.name": "dbz_pub",
      "table.include.list": "inventory.products"
    }
  }'

# Verify the connector is running:
curl http://localhost:8083/connectors/inventory-connector/status | jq

# Watch the topic (Debezium names topics as {server}.{schema}.{table}):
docker-compose exec kafka kafka-console-consumer \
    --bootstrap-server kafka:9092 \
    --topic shop.inventory.products --from-beginning

# In another terminal, make a change in Postgres:
docker-compose exec postgres psql -U postgres -d inventory -c "
INSERT INTO products (name, description, weight) VALUES ('foo', 'bar', 1.0);
UPDATE products SET description = 'updated' WHERE name = 'foo';
DELETE FROM products WHERE name = 'foo';"
# You should see three events: op=c, op=u, op=d (plus a tombstone).

# Inspect the replication slot's lag (CRITICAL metric):
docker-compose exec postgres psql -U postgres -c "
SELECT slot_name, active, restart_lsn, confirmed_flush_lsn,
       pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn) AS lag_bytes
FROM pg_replication_slots;"

# Inspect the schema-history topic:
docker-compose exec kafka kafka-console-consumer \
    --bootstrap-server kafka:9092 \
    --topic shop.schema-history --from-beginning | jq .

# Make a schema change and watch the connector handle it (or break):
docker-compose exec postgres psql -U postgres -d inventory -c "
ALTER TABLE products ADD COLUMN discount_code TEXT;"
# Then check the connector status — if it failed, the schema-history
# topic needed to record the DDL; check it has the new column.

# Try the outbox EventRouter SMT — see the outbox note for the full config:
# transforms=outbox,transforms.outbox.type=io.debezium.transforms.outbox.EventRouter

# Clean up:
docker-compose down -v
```
