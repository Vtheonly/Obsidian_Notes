# 07.03.03. Delivery Guarantees and Idempotent Processing

## What This Is

Delivery semantics describe the relationship between "the consumer received this record", "the consumer's side effects fired", and "the consumer committed the offset" — specifically, what happens when those three events are not atomic. Kafka offers three points on the spectrum: at-most-once (each record is processed zero or one times — silent data loss is possible), at-least-once (each record is processed one or more times — duplication is possible, loss is not), and exactly-once (each record is processed exactly one time — neither loss nor duplication). The first two are achievable with ordinary consumer configuration; the third requires the Kafka transactions API and an idempotent downstream system, and even then it is exactly-once **within the Kafka cluster**, not end-to-end against arbitrary external systems.

This note sits in 07.03 because delivery semantics are the consequence of the offset-management decisions covered in 07.03.02 and the rebalance behavior covered in 07.03.01. The order of operations — commit-then-process vs process-then-commit — is the entire mechanism by which a consumer picks at-most-once or at-least-once. The transactions API is the add-on that closes the gap between at-least-once and exactly-once by making the commit and the side-effect-write atomic. The poison-pill + DLQ pattern at the end of the note is the operational escape hatch: when a record cannot be processed at all (bad schema, null pointer, downstream 5xx), the consumer must be able to skip it without losing the rest of the partition — and that requires a deliberate error-handling policy, not a `try/catch` that swallows the exception.

## The Details

### At-Most-Once: Committing offsets before processing message payloads (risk of data loss)

At-most-once is the commit-then-process pattern: the consumer calls `poll()`, immediately commits the offset of the last record in the batch, and only then runs the handler. If the consumer crashes after the commit but before the handler finishes, the offset is durably advanced past those records — the new owner resumes at offset N+1, and records 0..N are silently skipped. The tradeoff is extreme: in exchange for accepting data loss on crash, the consumer can never duplicate a record (because the offset has already moved past it before processing begins), and the handler can take arbitrarily long without risking a `max.poll.interval.ms` violation.

```text
  At-most-once timeline:
  ──────────────────────────────────────────
  t0   consumer.poll()        →  [r0, r1, r2, r3]   (last offset = r3 = 4230)
  t1   consumer.commitSync()  →  committed = 4231   (offset of "next to read")
  t2   handler(r0)            →  side effect ✓
  t3   handler(r1)            →  side effect ✓
  t4   ★ CONSUMER CRASH ★
  t5   new owner resumes      →  starts at 4231
                                r2 and r3 are NEVER processed — silent loss
```

The implementation is one line of code, but you have to disable auto-commit first or the auto-committer will fight you:

```java
props.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, "false");
KafkaConsumer<String, byte[]> c = new KafkaConsumer<>(props);
c.subscribe(List.of("metrics"));
while (running) {
    ConsumerRecords<String, byte[]> batch = c.poll(Duration.ofMillis(100));
    if (!batch.isEmpty()) {
        long lastOffset = batch.iterator().next().offset();      // commit before processing
        // Walk to the actual last record's offset:
        long hi = -1;
        for (ConsumerRecord<String, byte[]> r : batch) hi = r.offset();
        c.commitSync(Map.of(
            new TopicPartition("metrics", /*partition*/), new OffsetAndMetadata(hi + 1)));
    }
    for (ConsumerRecord<String, byte[]> r : batch) handle(r);    // ★ crashes here lose data
}
```

The right use cases for at-most-once are narrow but real: high-volume metrics and telemetry where dropping 0.1% of points is acceptable (because the dashboard aggregates over 30-second windows anyway), logging pipelines where individual log lines do not matter, and any case where the cost of duplicate processing outweighs the cost of lost data (e.g., idempotency is impossible and double-charging a credit card is worse than missing a charge). The failure mode to fear is implicit at-most-once: a team that thinks they have at-least-once because auto-commit is on, but their handler is so slow that auto-commit fires before processing finishes — they get the worst of both worlds, silent data loss without even knowing it. The fix is to monitor `records-consumed-rate` vs `records-processed-rate`; if consumed > processed over a 5-minute window, you are silently dropping records.

### At-Least-Once: Processing payloads before committing offsets (risk of duplicate processing)

At-least-once is the process-then-commit pattern and the de facto default for production Kafka consumers. The consumer calls `poll()`, processes every record in the batch, then commits the offset of the last record processed. If the consumer crashes mid-batch, the offset commit never fires, and the new owner resumes from the last committed offset — reprocessing the records that were already handled. The tradeoff is the inverse of at-most-once: no data loss, but the handler must be **idempotent** — running it twice on the same record must produce the same observable state as running it once.

```text
  At-least-once timeline:
  ──────────────────────────────────────────
  t0   consumer.poll()        →  [r0, r1, r2, r3]   (last committed offset before = 4226)
  t1   handler(r0)            →  side effect ✓ (e.g., INSERT INTO orders VALUES (id=42))
  t2   handler(r1)            →  side effect ✓ (e.g., INSERT INTO orders VALUES (id=43))
  t3   ★ CONSUMER CRASH ★
  t4   new owner resumes      →  starts at 4227 (last commit)
                                r0 and r1 will be reprocessed → INSERT (id=42) again →
                                duplicate-key error if there's a UNIQUE constraint,
                                or a duplicate row if there isn't.
```

Idempotency is implemented in one of three ways, in order of robustness. **Natural-key uniqueness**: insert with `INSERT ... ON CONFLICT (id) DO NOTHING` (Postgres) or `INSERT IGNORE` (MySQL) or `upsert` (MongoDB) — the database deduplicates based on a key that already exists in the record. This works when the record has a stable business identifier (order ID, event UUID) and the side effect is a single database write. **Deduplication table**: before processing, insert the record's `(event_id)` into a `processed_events` table with a UNIQUE constraint; if the insert fails with a duplicate-key error, skip the record. This works for any side effect (HTTP call, email send, file write) but adds a database round-trip per record. **Monotonic operation**: design the side effect so that re-running it is a no-op — e.g., `UPDATE accounts SET balance = balance + 10 WHERE user_id = 42 AND last_applied_event_id < 4230` only fires if the event has not already been applied, using the event offset as a high-water mark. This is the cleanest pattern but requires the downstream store to expose a conditional-update primitive.

```sql
-- Pattern 2: deduplication table (idiomatic Postgres)
CREATE TABLE processed_events (
    event_id     TEXT PRIMARY KEY,         -- the record's idempotency key
    processed_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    consumer     TEXT NOT NULL             -- group.id of the consumer that handled it
);

-- Inside the handler:
INSERT INTO processed_events (event_id, consumer)
VALUES ('evt-abc-123', 'billing-group')
ON CONFLICT (event_id) DO NOTHING
RETURNING event_id;
-- If RETURNING yields a row → this is the first time, proceed with the side effect.
-- If RETURNING yields nothing → already processed, skip the side effect entirely.
```

The failure mode that catches teams off guard is **partial-batch duplication**: the handler successfully processed r0 and r1, then crashed on r2 (uncaught exception in handler), then on restart the consumer resumes from r0 — re-running the side effects for r0 and r1 even though they were already done. This is why `commitSync()` after each record (rather than after each batch) is safer for non-idempotent side effects, and why the dedup-table pattern is worth the per-record database cost when the side effect is expensive (sending an email, charging a card). The metric to watch is `records-reprocessed` — if it is consistently >0 even when no consumer restarts, your `poll()` loop is throwing exceptions that are being retried, and you should investigate whether the handler is actually idempotent or whether you need to add a dedup table.

### Exactly-Once Semantics (EOS): Idempotent Producers (sequence numbers and Producer IDs) + Transactional API (`sendOffsetsToTransaction`)

Exactly-once in Kafka is two layered mechanisms: idempotent producers (which prevent duplication on the producer side) and the transactions API (which makes a producer's writes and a consumer's offset commits atomic). Together they make the **Kafka-internal** pipeline exactly-once: a stream processing job that reads from topic A, transforms records, and writes to topic B can guarantee that every input record is reflected in topic B exactly once, even across crashes and rebalances. They do **not** make end-to-end exactly-once against arbitrary external systems free — if the side effect is a charge to Stripe or an insert into Postgres, you still need an idempotent consumer pattern from the at-least-once section above.

**Idempotent producers** (KIP-98, Kafka 0.11): the broker assigns each producer a `PID` (Producer ID) on `initProducerId`, and the producer attaches a monotonically increasing `sequence_number` to every record batch. The broker tracks `(PID, partition) → highest_committed_sequence_number` and rejects any batch whose sequence is less than or equal to the committed one with `OUT_OF_ORDER_SEQUENCE_NUMBER`. This means a producer that retries a batch (because the original ack was lost) will not produce a duplicate — the broker recognizes the sequence number and silently drops the retry. Setting `enable.idempotence=true` is now the default in Kafka 3.x, but it requires `acks=all` and `max.in.flight.requests.per.connection <= 5` (older code paths allowed only 1 in-flight without idempotence, which killed throughput — the 5-in-flight allowance is the entire reason idempotence exists).

```java
// Idempotent producer (default in Kafka 3.x, opt-in before)
props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, "true");
props.put(ProducerConfig.ACKS_CONFIG, "all");
props.put(ProducerConfig.MAX_IN_FLIGHT_REQUESTS_PER_CONNECTION, "5");
KafkaProducer<String, String> p = new KafkaProducer<>(props);
// p.send() retries are now deduplicated by (PID, partition, sequence_number) —
// the consumer will see each logical record exactly once, even if the producer
// retried due to a transient network blip.
```

**Transactional API** (KIP-98): the `transactional.id` config makes the PID stable across producer restarts (instead of being random per process), which is what allows a crashed producer to recover its in-flight batches and either commit or abort them. The producer calls `initTransactions()` once at startup (which fences out any older producer with the same `transactional.id` and aborts any in-flight transaction it left behind), then wraps each unit of work in `beginTransaction()` / `commitTransaction()` (or `abortTransaction()`). The consumer side reads committed transactions only when `isolation.level=read_committed` — it skips records from aborted transactions and stops reading at the last committed record, even if more records from an in-progress transaction are already in the partition.

```text
  Producer (transactional.id = "billing-pipeline-1")           Consumer
  ──────────────────────────────────────────────              ────────────────
  initTransactions()  ◀── fence old producer (epoch bump)
  beginTransaction()
    producer.send(out_topic_A, r0')   ◀── written, NOT visible to read_committed
    producer.send(out_topic_B, r1')   ◀── written, NOT visible
    producer.sendOffsetsToTransaction(
        {input_topic_partition: offset}, consumerGroupId)     ◀── offsets pending
  commitTransaction()  ◀── atomic marker: A, B, and offset commit all become visible
                                                              ★ consumer now sees r0', r1'
                                                              ★ input offset is committed

  If the producer crashes before commitTransaction():
    on restart → initTransactions() aborts the in-flight txn
    → A, B records are skipped by read_committed consumers
    → input offset is NOT committed → input records will be reprocessed from last commit
```

The EOS pattern for a consume-process-produce pipeline is:

```java
// Consumer config
props.put(ConsumerConfig.ISOLATION_LEVEL_CONFIG, "read_committed");
props.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, "false");
// Producer config
producerProps.put(ProducerConfig.TRANSACTIONAL_ID_CONFIG, "billing-pipeline-1");
producerProps.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, "true");

producer.initTransactions();
while (running) {
    ConsumerRecords<String, String> in = consumer.poll(Duration.ofMillis(100));
    if (in.isEmpty()) continue;
    producer.beginTransaction();
    try {
        for (ConsumerRecord<String, String> r : in) {
            producer.send(new ProducerRecord<>("out", transform(r)));
        }
        // ★ Atomically commit input offsets alongside the output writes
        producer.sendOffsetsToTransaction(
            offsetsFor(in), consumer.groupMetadata());
        producer.commitTransaction();
    } catch (Exception e) {
        producer.abortTransaction();
        // Re-throw or skip — depends on whether the error is retryable
    }
}
```

The throughput cost of EOS is real and worth understanding: idempotent producers add ~5% overhead (sequence-number tracking on broker), and transactions add ~20–40% overhead per produce because each transaction requires an extra control-record write and a `TransactionMarker` to be appended to every partition the transaction touched. For a 1-million-records-per-second pipeline this is the difference between saturating a 1 Gbps link and not. The reason EOS still does not free you from idempotent consumers for external side effects is that the transaction only covers Kafka writes — if your handler also calls `stripe.charges.create()`, that call is outside the transaction boundary, and a crash between `charges.create()` and `commitTransaction()` will re-charge on retry. For end-to-end exactly-once against an external system you must combine EOS (for the Kafka side) with the dedup-table pattern (for the external side), keyed on a stable business identifier. See [[07.02.03. Kafka Producer Architecture]] for the producer-side details of `enable.idempotence` and `transactional.id`.

### Poison Pill messages and configuring Dead Letter Queues (DLQ) with non-blocking error handlers

A poison-pill message is one that the consumer cannot process — typically because it violates a schema assumption, references a missing entity, or triggers an unhandled exception in the handler (NullPointerException on a missing field, deserialization failure on a corrupt payload, foreign-key violation on a database insert). The defining property is that retrying the message will fail every time, so a naive retry loop will block the partition forever: the consumer reads the poison pill, throws, retries, throws again, and the offset never advances past it. Every record behind the poison pill in the partition is starved, the lag grows monotonically, and the only way out is human intervention.

The fix is the **Dead Letter Queue (DLQ) pattern**: when the handler throws after N retries, the consumer publishes the failed record (with its exception context) to a separate `orders.DLQ` topic and then commits the original offset, allowing the partition to advance. The poison pill is preserved in the DLQ for offline inspection and replay (once the underlying bug is fixed, a consumer can read from the DLQ, fix the payload, and republish to the original topic). The cost is operational: someone has to triage the DLQ regularly, or it grows unbounded and consumes broker disk.

```text
  Topic: orders                          Topic: orders.DLQ
  ────────────────────────               ────────────────────────────────
  P0: [r0][r1][r2POISON][r3][r4]         [r2POISON + exception context]
                ▲                          ▲
                │ handler throws          │ DLQ producer sends here
                │ retry 1: throws         │
                │ retry 2: throws         │
                │ retry 3: throws (max)   │
                │                         │
                └─── DLQ recoverer ───────┘
                then commits offset of r2POISON → partition advances to r3
```

The blocking-vs-non-blocking distinction is what separates a well-behaved error handler from one that takes down the consumer group. A **blocking** error handler (`Spring's SeekToCurrentErrorHandler` in older spring-kafka, or a manual `consumer.seek()` to retry) re-reads the poison pill in a tight loop — this is fine for transient errors (downstream 5xx, brief network blip) but catastrophic for true poison pills, because the consumer will block forever, eventually blow past `max.poll.interval.ms`, get ejected, and trigger a rebalance storm as the new owner inherits the same poison pill. A **non-blocking** error handler (`DefaultErrorHandler` in spring-kafka 2.8+, kafkajs's `eachMessage` try/catch, the deduplication pattern) commits the offset after the retry budget is exhausted and moves on — this is what you want for poison pills. The retry budget is typically implemented with a `RetryTemplate` (Spring) or an exponential-backoff-with-jitter loop that retries N times before invoking the recoverer.

```java
// Spring Boot non-blocking error handler with DLQ (spring-kafka 2.8+)
@Bean
public DefaultErrorHandler errorHandler(KafkaTemplate<Object, Object> template) {
    DeadLetterPublishingRecoverer recoverer = new DeadLetterPublishingRecoverer(
        template,
        (record, ex) -> new TopicPartition(record.topic() + ".DLQ", record.partition())
    );
    // Retry 3 times with exponential backoff 1s, 2s, 4s, then give up and DLQ
    ExponentialBackOff backOff = new ExponentialBackOff(1000L, 2.0);
    backOff.setMaxElapsedTime(10_000L);
    DefaultErrorHandler handler = new DefaultErrorHandler(recoverer, backOff);
    // Don't retry on these — go straight to DLQ
    handler.addNotRetryableExceptions(DeserializationException.class,
                                       SerializationException.class);
    return handler;
}
```

```javascript
// kafkajs non-blocking handler with DLQ producer
const dlqProducer = kafka.producer();
await dlqProducer.connect();

await consumer.run({
  eachMessage: async ({ topic, partition, message }) => {
    try {
      await handleMessage(message);
    } catch (err) {
      // Non-blocking: publish to DLQ and let kafkajs auto-commit the offset
      await dlqProducer.send({
        topic: `${topic}.DLQ`,
        messages: [{
          key: message.key,
          value: message.value,
          headers: {
            'error-class': err.constructor.name,
            'error-message': err.message,
            'original-topic': topic,
            'original-partition': String(partition),
            'original-offset': String(message.offset),
            'original-timestamp': String(message.timestamp),
          },
        }],
      });
    }
  },
});
```

The DLQ records should carry enough context that a human or automated replayer can reconstruct the original event: the original topic, partition, offset, and timestamp as headers (so the replayer can seek back if needed), the original key and value verbatim, and the exception class and message (so the triager knows what broke without re-running the handler). The most common production failure mode is a DLQ topic that nobody monitors — records accumulate for months, the broker disk fills, and the team discovers the problem only when production Kafka crashes with `DISK_FULL`. The fix is to treat the DLQ like any other critical queue: alert on `DLQ-records-in-per-minute > 0`, set up a Grafana panel that shows DLQ depth by original topic, and run a weekly triage job that either fixes-and-replays or formally drops each DLQ record. The deeper fix is to prevent poison pills at the source — enable Schema Registry (Avro/Protobuf) so the producer cannot publish a record the consumer cannot deserialize, and write contract tests that catch schema regressions in CI before they reach production. See [[07.04.02. Ecosystem Implementations]] for how BullMQ, Celery, and Laravel Queues express the equivalent dead-letter/retry-abandoned-job pattern for non-Kafka task queues.

## How This Connects to the Frameworks

- **Spring Boot** (`spring-kafka` 2.8+): `@KafkaListener` with a `DefaultErrorHandler` bean. `DeadLetterPublishingRecoverer` is the standard DLQ producer. Spring's `KafkaTransactionManager` wraps the producer in a JTA-style transaction so `@Transactional` on the listener method gives you EOS for consume-transform-produce. `ChainedKafkaTransactionManager` lets you coordinate a DB transaction + Kafka transaction.
- **Node.js** (`kafkajs`): no built-in transaction manager — the `eachBatch` handler exposes `batch.commitOffsetsIfNecessary()` which you call inside your own try/catch + DLQ producer pattern. kafkajs's `transaction()` API supports EOS via `producer.transaction(async () => { producer.send(...); producer.sendOffsets(...); })`.
- **Python** (`confluent-kafka`): `Producer.init_transactions()`, `Producer.begin_transaction()`, `Producer.send_offsets_to_transaction()`, `Producer.commit_transaction()`. The Python `avro` library + `confluent-kafka[avro]` Schema Registry client is the standard poison-pill prevention pattern.
- **PHP** (`rdkafka` extension): `RdKafka\Producer::initTransactions()`, `::beginTransaction()`, `::commitTransaction()`. The `avro-php` library + a Schema Registry HTTP client provides wire-format validation.

The framework differences are mostly syntactic — the underlying librdkafka / Java client API is identical across all four. The framework-specific decisions are which retry policy is the default (Spring's `DefaultErrorHandler` retries 3× with backoff; kafkajs has no built-in retry, you implement it; librdkafka has no built-in retry, you implement it) and whether EOS is wired into a higher-level abstraction (Spring's `@Transactional` annotation is the highest-level wrapper; the other three require explicit `beginTransaction`/`commitTransaction` calls).

## Hands-On Exercise

```bash
# 1. Create a topic and a DLQ topic
docker exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic numbers --partitions 3 --replication-factor 1
docker exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic numbers.DLQ --partitions 3 --replication-factor 1 \
  --config retention.ms=604800000  # 7-day retention on the DLQ

# 2. Produce a mix of valid records and one poison pill (e.g., "not-a-number")
for i in 1 2 3 4 5; do echo "$i" | docker exec -i kafka /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 --topic numbers; done
echo "POISON" | docker exec -i kafka /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 --topic numbers
for i in 6 7 8; do echo "$i" | docker exec -i kafka /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 --topic numbers; done

# 3. Run a consumer (any language) that parses each record as int and crashes on "POISON"
#    Without a DLQ handler: consumer blocks on POISON forever, records 6/7/8 are starved
#    With a DLQ handler: POISON goes to numbers.DLQ, partition advances, 6/7/8 process normally

# 4. Inspect the DLQ to recover the poison pill payload + error context
docker exec kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic numbers.DLQ --from-beginning \
  --property print.headers=true --property print.partition=true

# 5. Verify EOS end-to-end: count records in input topic vs output topic after a consumer crash
docker exec kafka /opt/kafka/bin/kafka-run-class.sh kafka.tools.GetOffsetShell \
  --broker-list localhost:9092 --topic numbers
docker exec kafka /opt/kafka/bin/kafka-run-class.sh kafka.tools.GetOffsetShell \
  --broker-list localhost:9092 --topic numbers-output
#   With isolation.level=read_committed + transactional.id, the output topic count
#   should equal the input topic count exactly, regardless of how many times the
#   consumer crashed and restarted.

# 6. Verify idempotent producer: send the same key 100 times rapidly
docker exec kafka /opt/kafka/bin/kafka-producer-perf-test.sh \
  --topic idempotent-test --num-records 100 --record-size 100 --throughput -1 \
  --producer-props bootstrap.servers=localhost:9092 acks=all enable.idempotence=true
#   Then count distinct offsets in the topic — should be 100, not more.
```

Step 3 demonstrates the poison-pill pattern most directly: without a DLQ the consumer hangs, with a DLQ the partition advances. Step 5 is the EOS sanity check — if input and output counts match exactly across crashes, your transactional pipeline is working; if output < input, you are silently dropping records (an aborted transaction that the consumer never reprocessed); if output > input, you are duplicating (a non-idempotent producer retrying without `enable.idempotence`).
