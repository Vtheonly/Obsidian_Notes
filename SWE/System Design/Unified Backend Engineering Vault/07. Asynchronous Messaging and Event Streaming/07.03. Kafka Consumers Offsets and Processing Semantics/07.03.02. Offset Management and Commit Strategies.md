# 07.03.02. Offset Management and Commit Strategies

## What This Is

An offset is the integer position of a record inside its partition — record 0 is the first record ever written, record 1 is the second, and so on forever. The committed offset for a (consumer group, topic, partition) triple is the position the group will resume from after a restart or a rebalance. Managing those offsets correctly is the single decision that determines whether your consumer delivers at-most-once, at-least-once, or somewhere unstable in between. Get offset commits wrong and you get one of two production incidents: silent data loss (committed past records you never processed) or unbounded duplication (reprocessing the same records on every restart because the commit never landed).

Kafka stores committed offsets in a regular Kafka topic — `__consumer_offsets` — rather than in ZooKeeper or an external database. This is a deliberate design choice: it makes offset commits use the same replication, durability, and append-only log machinery as application data, with no extra dependencies. This note covers the on-disk shape of that topic and the three commit modes the consumer client exposes (auto, sync, async), plus the offset-reset behavior that decides what happens when no committed offset exists.

## The Details

### The `__consumer_offsets` internal topic

`__consumer_offsets` is a single Kafka topic, created automatically on the first offset commit, with 50 partitions by default (`offsets.topic.num.partitions=50`) and a replication factor controlled by `offsets.topic.replication.factor` (default 1 in dev, **must** be set to 3 in production). The topic uses the **compact** cleanup policy rather than the default **delete** policy — old offset records are not aged out by time, they are superseded by newer records with the same key. This means the topic grows monotonically in size (new commits keep arriving) but each `(group, topic, partition)` key only ever has one live value: the most recently committed offset.

The key for each offset record is an 8-byte composite: a 2-byte version prefix, the group ID length + bytes, the topic length + bytes, and a 4-byte partition number. The value carries the 8-byte offset itself, plus optional metadata (typically the consumer's host or client ID, used by monitoring tools) and a timestamp. The same topic also stores group-metadata records — keyed by group ID alone, value describing the group's current generation, members, and assignment — which is how the group coordinator rebuilds group state on a broker failover. The partition that owns a given (group, topic, partition) key is computed as `murmur2(group.id) % 50`, which is the same hash that picks the group coordinator broker — that broker is the leader of the offset-record's partition, so it serves both roles.

```text
  Topic: __consumer_offsets   (50 partitions, compact cleanup policy)
  ─────────────────────────────────────────────────────────────────────
  Partition 7  (because murmur2("billing") % 50 == 7, hypothetically):

    key  = (group="billing", topic="orders", partition=0)
    val  = { offset: 42317, metadata: "consumer-1@10.0.1.5", ts: 1716000000000 }

    key  = (group="billing", topic="orders", partition=3)
    val  = { offset: 9821, metadata: "consumer-2@10.0.1.6", ts: 1716000003000 }

    key  = (group="billing", topic="orders", partition=0)         ← later commit
    val  = { offset: 43128, metadata: "consumer-1@10.0.1.5", ts: 1716000005000 }

    key  = (group="billing" /* group metadata */)
    val  = { generation: 14, members: [c-1, c-2], protocol: "cooperative-sticky" }

  After compaction, only the latest offset per (group, topic, partition) survives.
  Group-metadata records use a special "tombstone" (null value) for group removal.
```

You can inspect the topic directly with the offset-debug formatter that ships with the broker:

```bash
# Dump offset records (skipping group-metadata records) for a specific group
docker exec kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 \
  --topic __consumer_offsets \
  --partition 7 --from-beginning \
  --formatter "kafka.coordinator.group.GroupMetadataManager\$OffsetsMessageFormatter"
#   Output:  [billing,orders,0]::OffsetAndMetadata(offset=43128, leaderEpoch=...,
#             metadata=consumer-1@10.0.1.5, commitTimestamp=1716000005000, ...)

# Inspect the cleanup policy and partition count
docker exec kafka /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --describe --topic __consumer_offsets
#   Topic: __consumer_offsets  PartitionCount: 50  ReplicationFactor: 1
#     Configs: cleanup.policy=compact,segment.bytes=104857600,
#              compression.type=producer
```

The production failure modes for this topic fall into three buckets. First, **under-replication**: a cluster stood up with `offsets.topic.replication.factor=1` survives a single-broker outage by losing all committed offsets — every consumer group restarts from `auto.offset.reset` (typically `earliest`), reprocessing days of data. The fix is `offsets.topic.replication.factor=3` set before any group is created; changing it after creation requires manually altering the topic config and increasing the partition count, which is disruptive. Second, **compaction lag**: a high-churn consumer group committing thousands of times per second can produce compaction backlog — the `kafka.log.LogCleanerManager` metric `max-clean-time-io` climbs, disk usage grows, and lookups slow down. The fix is to commit less frequently (every 1000 records instead of every record) or to raise `min.cleanable.dirty.ratio` to defer compaction. Third, **wrong partition count**: a 200-consumer-group deployment with 50 offset partitions can produce hot partitions on the coordinator broker if many groups hash to the same partition; monitor `under-replicated-partitions` on `__consumer_offsets` specifically and consider `offsets.topic.num.partitions=100` for very large deployments.

### Offset Commit modes: Automatic commits (`enable.auto.commit=true`) vs. Manual Synchronous (`commitSync()`) vs. Manual Asynchronous (`commitAsync()`)

The consumer client offers three commit modes, each with a different tradeoff between simplicity, latency, and correctness. The choice is not aesthetic — it is the single decision that determines whether your consumer delivers at-most-once, at-least-once, or unstable semantics where the answer changes from restart to restart.

**Automatic commit** (`enable.auto.commit=true`, the default, `auto.commit.interval.ms=5000`) is the simplest: the consumer's poll loop calls `commitSync()` on your behalf at most once per `auto.commit.interval.ms`, using the offset of the **last record returned by the most recent `poll()`** — not the last record you actually processed. This is the at-least-once-vs-at-most-once trap: if your handler takes 8 seconds per batch and you call `poll()` every 100 ms, the auto-committer will happily commit offset 5000 while your handler is still working on offset 4230. If the consumer then crashes, the new owner resumes at offset 5001 and records 4230–5000 are **never processed** — silent data loss with no error log. Auto-commit is appropriate only when your handler is faster than `auto.commit.interval.ms` × poll cycle, and even then it is fragile because there is no signal back to your code when a commit succeeds or fails.

**Manual synchronous commit** (`consumer.commitSync()`) blocks the calling thread until the broker acknowledges the commit. It retries automatically on retryable errors (`NOT_COORDINATOR`, `COORDINATOR_NOT_AVAILABLE`, `REBALANCE_IN_PROGRESS`), throws `CommitFailedException` on non-retryable ones (the most common being "the group has rebalanced and you no longer own this partition"), and is the right choice for the **shutdown path** — `consumer.close()` will not commit for you, so a `commitSync()` in a `finally` block guarantees the last batch's offsets are durably recorded. The cost is latency: each commit is a full network round-trip, so calling `commitSync()` after every record caps throughput at roughly `1 / (handler_time + commit_rtt)`. For a 1 ms handler and a 2 ms broker RTT, that is a hard ceiling of 333 records/sec/consumer — typically 10–100× lower than the broker can actually sustain.

**Manual asynchronous commit** (`consumer.commitAsync(callback)`) sends the OffsetCommit request and returns immediately, invoking the supplied `Callback<OffsetAndMetadata, Exception>` when the broker replies. It does **not** retry on failure (because by the time the failure callback fires, a later commit may already have succeeded, and retrying would commit a stale offset out of order). The standard production pattern combines both: use `commitAsync()` in the steady state for throughput, and on shutdown call `commitSync()` once to guarantee the final offset lands before the consumer exits. This is the pattern Spring Kafka implements internally when `ContainerProperties.AckMode = RECORD` or `BATCH`.

```java
Properties props = new Properties();
props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
props.put(ConsumerConfig.GROUP_ID_CONFIG, "billing");
props.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, "false");  // ★ mandatory
props.put(ConsumerConfig.AUTO_OFFSET_RESET_CONFIG, "earliest");

KafkaConsumer<String, String> consumer = new KafkaConsumer<>(props);
consumer.subscribe(List.of("orders"));

try {
    while (running) {
        ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
        for (ConsumerRecord<String, String> r : records) {
            process(r);   // ← handler; at-least-once if this throws and we crash before commit
        }
        // Steady state: async commit (fast, no retry)
        consumer.commitAsync((offsets, exc) -> {
            if (exc != null) {
                log.warn("Async commit failed for {} — will retry next cycle", offsets);
            }
        });
    }
} finally {
    try {
        // Shutdown: synchronous commit (blocking, retries, guaranteed)
        consumer.commitSync();
    } finally {
        consumer.close();
    }
}
```

The fourth knob that affects commit semantics is `auto.offset.reset` (default `latest`). It only fires when the consumer has **no committed offset** for a partition — either because the group is new, or because the previously committed offset is outside the current log range (e.g., the offset was 5000 but the topic was deleted and recreated, so the new log only goes 0–100). The three values are `earliest` (resume from offset 0, reprocessing the entire topic — useful for new groups that want full history), `latest` (resume from the log-end at the moment of registration — useful for new groups that only want new data, but dangerous because it silently skips anything produced between topic creation and consumer registration), and `none` (throw `NoOffsetForPartitionException` and refuse to start — the right production choice for any group where skipping data is unacceptable, because it forces the operator to make a deliberate decision). The `seek()` API (`consumer.seek(partition, offset)`) is the escape hatch for explicit position control — useful for reprocessing a specific range, for skipping a poison-pill record, or for bootstrapping a new consumer group from an external checkpoint. The failure mode to fear with auto-commit is a `CommitFailedException` swallowed by a generic `try/catch` in the handler — the consumer keeps processing, every commit fails, every restart reprocesses from the last successful commit, and the duplication grows monotonically until the backlog is unrecoverable. The fix is to make `commitSync()` failures fatal — exit the consumer process and let the orchestrator restart it cleanly, rather than soldiering on with no progress.

## How This Connects to the Frameworks

- **Spring Boot** (`spring-kafka`): the `@KafkaListener` container exposes commit mode via `ContainerProperties.AckMode`. `AckMode.BATCH` (default) commits after each `poll()` batch — equivalent to manual async. `AckMode.RECORD` commits after each message — slowest but safest. `AckMode.MANUAL` exposes `Acknowledgment.acknowledge()` to your handler so you decide when to commit. `factory.getContainerProperties().setSyncCommits(true)` switches to blocking commits.
- **Node.js** (`kafkajs`): `consumer.run({ eachMessage: ..., eachBatch: ..., autoCommit: false })` then `await consumer.commitOffsets([{topic, partition, offset}])`. Default `autoCommit: true` with `autoCommitInterval: 5000`. kafkajs's `eachBatch` handler exposes `batch.commitOffsetsIfNecessary()` which auto-throttles commits to one per second.
- **Python** (`confluent-kafka`): `Consumer({'enable.auto.commit': False})`, then `consumer.commit(message=msg, asynchronous=False)` for sync, `asynchronous=True` for async. The `commit()` call without an argument commits the offset of the last record returned by `poll()`; passing a specific `Message` commits only up to that record's offset.
- **PHP** (`rdkafka`): `$conf->set('enable.auto.commit', 'false')`, then `$consumer->commitAsync()` or `$consumer->commit()`. The PHP extension's `commit()` blocks by default; `commitAsync()` returns immediately and delivers the result to a `DrMsgCb` callback.

In all four ecosystems the underlying librdkafka / Java client behavior is identical: auto-commit is enabled by default, manual commits require opting out, sync commits block, async commits do not. The framework-specific knob is whether the framework auto-commits for you on every message (Spring `AckMode.RECORD`) or expects you to call commit yourself (kafkajs `autoCommit: false`). The "what is automatic vs manual" question is purely about which layer wraps the call, not about what the broker sees on the wire.

## Hands-On Exercise

```bash
# 1. Produce 100 records to a topic
docker exec kafka /opt/kafka/bin/kafka-producer-perf-test.sh \
  --topic offsets-demo --num-records 100 --record-size 100 --throughput -1 \
  --producer-props bootstrap.servers=localhost:9092 acks=all

# 2. Start a consumer group with auto-commit disabled, read 50 records, then SIGKILL
docker exec -it kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic offsets-demo --group demo \
  --enable-auto-commit false --max-messages 50 --from-beginning
# (Ctrl-C cleanly — or pkill -9 from another shell to simulate a crash)

# 3. Inspect the committed offset for group "demo"
docker exec kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --describe --group demo
#   CURRENT-OFFSET will be 0 (no commit landed) — restart will re-read all 100 records

# 4. Repeat step 2 but with --enable-auto-commit true (default) and clean Ctrl-C
docker exec -it kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic offsets-demo --group demo \
  --max-messages 50 --from-beginning
# (Ctrl-C — the consumer closes cleanly, auto-commit fires on shutdown)

# 5. Re-describe — CURRENT-OFFSET should now show ~50
docker exec kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --describe --group demo

# 6. Inspect the raw __consumer_offsets records for group "demo"
docker exec kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic __consumer_offsets --from-beginning \
  --formatter "kafka.coordinator.group.GroupMetadataManager\$OffsetsMessageFormatter" \
  --timeout-ms 5000 | grep "demo,offsets-demo"
```

Steps 3 vs 5 demonstrate the silent-data-loss-vs-at-least-once distinction: a crash with auto-commit disabled loses the in-flight offset (restart reprocesses everything since the last commit); a clean shutdown with auto-commit enabled commits the last polled offset even if the handler had not finished processing it (potential silent skip on the next start). Both are wrong in subtle ways — that is why production consumers use manual `commitSync()` on the shutdown path and manual `commitAsync()` in the steady state.
