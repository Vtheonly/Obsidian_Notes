# 07.03.01. Consumer Groups and Partition Balancing

## What This Is

A Kafka consumer group is the read-side scaling primitive: it is a logical subscriber made up of one or more consumer processes that together own a topic's partitions, with the guarantee that each partition is consumed by exactly one consumer in the group at any moment. Where producers achieve throughput by batching writes, consumer groups achieve throughput by partitioning reads — spin up more consumers, the group coordinator hands each one a slice of the partitions, and aggregate throughput scales until you run out of partitions to hand out. This is the single most important reason Kafka scales horizontally for reads, and it is also the source of the rebalance storms that have haunted production deployments since 0.8.

This note sits in section 07.03 because the consumer group is the substrate on which offset management (07.03.02) and delivery semantics (07.03.03) are layered. The rebalance protocol decides **who** owns which partition; offset commits decide **where** the owner resumes; the delivery semantics decide **what happens** to a record that is processed but not yet committed when a rebalance yanks the partition away. Frameworks in section 05 (Spring `@KafkaListener`, kafkajs `consumer.group`, confluent-kafka `Consumer` with `subscribe`) are all wrappers around the same underlying group protocol described here, and the rebalance-related production incidents (stop-the-world pauses, repeated reprocessing, infinite rebalance loops) are identical across them.

## The Details

### The Consumer Group Model: Horizontal scaling of partition reads across worker instances

A consumer group is identified by a single string — `group.id` — and the Kafka cluster treats every consumer that joins with the same `group.id` as a member of the same logical subscriber. The membership is dynamic: a consumer can join, leave, or crash at any time, and the cluster will rebalance partition ownership so that every partition always has exactly one active consumer within the group. This is fundamentally different from a traditional message queue (RabbitMQ, ActiveMQ classic) where consumers compete for individual messages from a shared queue — in Kafka the unit of ownership is the **partition**, not the message, and a consumer that owns a partition owns **every** message in that partition until it gives up ownership.

The hard constraint that drives every design decision is: **one partition, one consumer in the group**. This is what gives Kafka per-partition ordering (the consumer sees records in the order the producer wrote them) and is also what limits the group's parallelism to the partition count. A topic with 6 partitions cannot be read in parallel by more than 6 consumers in the same group — a 7th consumer will sit idle, assigned zero partitions, burning resources. The corollary is that partition count is a capacity-planning decision that is expensive to reverse: increasing partitions later breaks the key-to-partition mapping for existing records (because `murmur2(key) % newNumPartitions` will route old keys to different partitions), so producers that depend on key ordering must be ready for the migration.

```text
  Topic "orders" — 6 partitions                Consumer group "billing"
  ┌──────────┬──────────┬──────────┐           ┌──────────────────────────┐
  │  P0      │  P1      │  P2      │           │  consumer-1 (10.0.1.5)   │ ← owns P0, P1, P2
  │  msgs... │  msgs... │  msgs... │  ───────▶ │  consumer-2 (10.0.1.6)   │ ← owns P3, P4
  ├──────────┼──────────┼──────────┤           │  consumer-3 (10.0.1.7)   │ ← owns P5
  │  P3      │  P4      │  P5      │           │  (consumer-4 sits idle)  │ ← owns nothing
  └──────────┴──────────┴──────────┘           └──────────────────────────┘

  Different group "analytics" — same topic, independent position
  ┌────────────────────────────────┐           ┌──────────────────────────┐
  │  consumer-A (10.0.2.5)         │ ◀──────── │ Subscribes with          │
  │  consumer-B (10.0.2.6)         │ ◀──────── │ group.id="analytics"     │
  └────────────────────────────────┘           └──────────────────────────┘
  Two groups can read the same topic independently — different offsets,
  different pace, different parallelism (subject to partition count cap).
```

The second useful property, visible in the diagram, is that **different consumer groups are independent subscribers**. The billing group and the analytics group both subscribe to the `orders` topic, but each maintains its own offsets in `__consumer_offsets` and reads at its own pace. This is the publish-subscribe property of Kafka at the topic level: add a new consumer group, point it at the topic, and it starts reading from `auto.offset.reset` (earliest or latest) without affecting any other consumer. The failure mode to watch for is under-partitioning: a team launches a hot new service with `group.id=notifications`, scales it to 12 replicas, and discovers throughput is identical to 3 replicas because the topic has 4 partitions and 8 of the 12 consumers are idle. The fix is to plan partition count up-front against your peak consumer parallelism — typically 2–4× the expected consumer count to leave room for growth — and to monitor `assigned-partitions` per consumer as a critical metric.

### Dynamic Partition Assignment Strategies: Range, RoundRobin, Sticky, Cooperative Sticky Assignors

When a rebalance fires (a consumer joins, leaves, or fails its heartbeat), the group leader — one of the consumers, elected by the group coordinator — must produce a new partition-to-consumer assignment that every member agrees on. The assignment strategy is the algorithm the leader uses to compute that mapping. The choice of strategy affects two production-relevant properties: how balanced the assignment is across consumers, and how much partition movement happens on each rebalance (movement is expensive because it forces the new owner to re-fetch state and re-establish its read position).

The four built-in strategies are:

| Strategy           | Class                                  | Algorithm                                                        | Balance | Movement on rebalance | Stop-the-world? |
|--------------------|----------------------------------------|------------------------------------------------------------------|---------|------------------------|------------------|
| Range              | `RangeAssignor` (default pre-2.4)      | Per-topic: sort partitions by ID, slice into N contiguous chunks | Uneven  | High                   | Yes              |
| RoundRobin         | `RoundRobinAssignor`                   | Across all subscribed topics, interleave partitions to consumers | Even    | High                   | Yes              |
| Sticky             | `StickyAssignor` (Kafka 0.11+)         | Like RoundRobin but tries to keep existing assignments           | Even    | Low                    | Yes              |
| CooperativeSticky  | `CooperativeStickyAssignor` (2.4+)     | Sticky + incremental (only revoked partitions pause)             | Even    | Lowest                 | **No**           |

`RangeAssignor` is the historical default and the source of the most common imbalance bug. It works per-topic: for each subscribed topic it sorts partitions numerically `[0, 1, 2, 3, 4, 5]` and divides them into N roughly-equal contiguous slices. If the topic has 7 partitions and 3 consumers, the slices are `[0,1,2]`, `[3,4]`, `[5,6]` — the first consumer always gets the extra partition when the division is uneven. With multiple subscribed topics the imbalance compounds: 7 topics × the same 3 consumers means consumer-1 always gets the extra partition on every topic, ending up with 21 partitions vs 14 vs 14. `RoundRobinAssignor` fixes this by interleaving across all subscribed topics, giving a perfectly even 49/49/49 split. `StickyAssignor` goes further by trying to preserve the previous assignment when membership changes — if consumer-2 dies, only consumer-2's partitions need to be reassigned, instead of reshuffling the whole topic.

The big jump is `CooperativeStickyAssignor` (KIP-429, 2.4+). All previous strategies were **eager** (also called "stop-the-world"): on every rebalance every consumer must revoke all its partitions, the leader computes the new full assignment, and only then can consumers resume. For a topic with stateful consumers — say, a stream processing job that maintains a RocksDB state store per partition — this means a full state-store handoff every rebalance, which can take minutes. The cooperative protocol is **incremental**: only the partitions that actually need to move are revoked, the rest keep processing continuously. The protocol achieves this by running two rebalance cycles — the first proposes the delta ("consumer-2 should give up P3 to consumer-1"), the second confirms once consumer-2 has stopped reading P3. The cost is one extra rebalance round-trip; the benefit is that steady-state processing never pauses.

```text
  Eager rebalance (Range/RoundRobin/Sticky):
  ──────────────────────────────────────────
  t0:   consumer-2 crashes
  t1:   coordinator triggers rebalance
  t2:   ALL consumers revoke ALL partitions (processing stops cluster-wide)
  t3:   leader computes new full assignment
  t4:   ALL consumers receive assignment, re-init state, resume
  ── visible pause: 2-30 seconds, all partitions silent ──

  Cooperative rebalance (CooperativeSticky):
  ──────────────────────────────────────────
  t0:   consumer-2 crashes
  t1:   coordinator triggers rebalance
  t2:   leader computes delta: only P3, P4 need to move (from dead c-2 to c-1)
  t3:   c-1 keeps processing P0, P1, P5 throughout — no pause
  t4:   c-1 starts processing P3, P4 after handshake
  ── visible pause: 0 seconds on already-owned partitions ──
```

The strategy is set on the consumer via `partition.assignment.strategy` (a comma-separated list, the first that satisfies everyone wins). The right production default is `CooperativeStickyAssignor` for any new deployment; migrating from an eager strategy requires a rolling bounce because the two protocols are incompatible mid-group. The failure mode to fear is a large consumer group (50+ members) running `RangeAssignor` on many topics — a single consumer bounce causes a full-cluster stop-the-world that takes 30+ seconds, during which no records are processed, and the backlog can take hours to drain. Switching to `CooperativeStickyAssignor` typically eliminates 90%+ of the visible pause.

### The Consumer Rebalance Protocol: Group Coordinator Broker and Consumer Group Leader responsibilities

The rebalance protocol is a multi-message dance between three roles: the **Group Coordinator** (a specific broker, picked by hashing `group.id` into `__consumer_offsets` partition 0..49 and finding that partition's leader), the **Group Leader** (one of the consumers, elected by the coordinator — by convention the first consumer to join), and the **member consumers** (everyone else in the group). The coordinator drives the protocol; the leader computes the assignment; the members execute it. Understanding which role does what is the key to debugging rebalance failures, because the symptoms of a stuck protocol look completely different depending on which role is misbehaving.

The protocol has four phases — FindCoordinator, JoinGroup, SyncGroup, Heartbeat — and they execute on every membership change:

```text
  Consumer                    Coordinator (broker)              Leader (consumer #1)
  ────────                    ─────────────────────              ────────────────────
  1. FindCoordinator ───────▶  hash(group.id) → partition N
                               leader of partition N is coord
  ◀─── CoordinatorResponse ─── (broker id)

  2. JoinGroupRequest ──────▶  collect all members' subscriptions
                               wait min(max.poll.interval.ms, all joined)
                               elect first-joiner as leader
  ◀─── JoinGroupResponse ────  "you are leader; here are all member IDs + subscriptions"

  3. (leader only) compute assignment using chosen Assignor

  4. SyncGroupRequest ──────▶  forward assignment to coordinator
       (members: empty)        (leader: full assignment map)
  ◀─── SyncGroupResponse ───  each member receives its own slice

  5. Heartbeat (loop) ──────▶  every heartbeat.interval.ms (~3s)
  ◀─── HeartbeatResponse ───  "you're still in, keep going"
                               (or: REBALANCE_IN_PROGRESS → restart at step 2)
```

The **JoinGroup** phase is where the coordinator collects all members' subscriptions and decides who the leader is. The coordinator waits up to `max.poll.interval.ms` (default 30 s) for all currently-known members to send their JoinGroup before responding — if a member is slow to join, the whole group waits. The leader receives the complete roster in its JoinGroup response, runs the configured `PartitionAssignor` to produce a `Map<MemberId, List<TopicPartition>>`, and sends that map back to the coordinator inside its SyncGroup request. The coordinator fans out the per-member slices: each member's SyncGroup response contains only its own assignment. This round-trip is what makes the leader-elected approach scalable — only the leader has to do the assignment computation, and the coordinator only has to route per-member responses.

The **Heartbeat** loop is what keeps the group alive between rebalances. Each consumer sends a heartbeat every `heartbeat.interval.ms` (default 3 s); the coordinator replies with either "OK" or "REBALANCE_IN_PROGRESS". If the coordinator does not receive a heartbeat from a member within `session.timeout.ms` (default 45 s in Kafka 3.x, was 10 s in older versions), it considers that member dead and triggers a rebalance. The producer-side equivalent of this is the `max.in.flight.requests.per.connection` knob — but for consumers the failure mode is much more visible: a long GC pause or a slow `poll()` handler that takes longer than `max.poll.interval.ms` causes the consumer to be ejected from the group even though it is still alive, triggering a spurious rebalance. The fix is to either keep `poll()` loops short (sub-second) or raise `max.poll.interval.ms` to comfortably exceed your worst-case processing time, and to monitor `sync-time-ns` and `heartbeat-response-time-max` — both will spike before a rebalance storm.

### Heartbeats and Rebalance Triggers: Tuning `session.timeout.ms`, `heartbeat.interval.ms`, and `max.poll.interval.ms`

The three timeouts form a contract: heartbeats must arrive faster than the session timeout, and `poll()` must be called faster than the poll interval, or the consumer gets ejected. They look similar but govern different failure modes, and getting any of them wrong is the single most common cause of consumer-group production incidents.

`heartbeat.interval.ms` (default 3 s) is how often the consumer's background heartbeat thread sends a HeartbeatRequest to the coordinator. It runs on a separate thread from the poll loop, so even if your message handler blocks for 30 s, heartbeats keep flowing. `session.timeout.ms` (default 45 s since KIP-62 / Kafka 0.10.1; older versions defaulted to 30 s and required tight heartbeat tuning) is how long the coordinator will wait without receiving a heartbeat before declaring the member dead. The rule of thumb is `session.timeout.ms >= 3 × heartbeat.interval.ms` — three missed heartbeats is the failure signal, which avoids declaring a member dead on a single network blip.

`max.poll.interval.ms` (default 30 s, was 5 min before KIP-62) is the maximum time between two consecutive `consumer.poll()` calls. It exists to catch the case where the consumer is alive (heartbeats flowing) but is stuck processing a batch and not making progress. If your handler takes 60 s to process a batch of 500 records and you call `poll()` once a minute, you are right at the edge — the next `poll()` had better happen before 30 s elapses or you will be ejected with a `CommitFailedException` ("Commit cannot be completed since the group has already rebalanced and assigned the partitions to another member").

```text
  ┌──────────────────────────────────────────────────────────────────────┐
  │  Timeline (seconds)                                                  │
  │                                                                      │
  │  0s    consumer.poll() returns 500 records                           │
  │  3s    heartbeat sent (background thread) ◀── still alive            │
  │  6s    heartbeat sent                                                 │
  │  ...   (handler is processing records, ~50ms each = 25s total)       │
  │  28s   heartbeat sent                                                 │
  │  29s   handler finishes, app calls commitSync()                       │
  │  30s   ←── max.poll.interval.ms DEADLINE — must call poll() by now   │
  │  30s   consumer.poll() called — just in time                         │
  │                                                                      │
  │  If handler had taken 35s:                                           │
  │  30s   max.poll.interval.ms exceeded                                 │
  │  31s   coordinator marks member dead, triggers rebalance             │
  │  35s   handler finishes, app calls commitSync()                      │
  │         → CommitFailedException (group already rebalanced)           │
  │         → 500 records will be reprocessed by new owner               │
  └──────────────────────────────────────────────────────────────────────┘
```

The right production configuration depends on the workload. For a fast handler (<100 ms per record), defaults are fine: `heartbeat.interval.ms=3000`, `session.timeout.ms=45000`, `max.poll.interval.ms=300000` (the modern default was raised to 5 min). For a slow handler that processes batches of large records (e.g., image processing, ML inference), the standard pattern is to set `max.poll.records` low (e.g., 10 or 1) so each poll returns a small batch that finishes within the poll interval, and raise `max.poll.interval.ms` to 5–10 min as a safety margin. The most common incident is the inverse: a team that uses `max.poll.records=500` (the default) with a 200 ms handler, expecting each poll to take 100 s — they immediately blow past `max.poll.interval.ms=30000`, get ejected, and reprocess the same batch forever, a cycle that only ends when they pause the consumer and clear the backlog manually. The metrics to watch are `poll-idle-ratio-avg` (should be > 0.5; < 0.1 means the consumer is spending almost all its time in `poll()` and is close to the limit) and `commit-latency-avg` (a spike here means the broker is slow to commit, which can push the next `poll()` past the deadline).

## How This Connects to the Frameworks

- **Spring Boot** (`spring-kafka`): `@KafkaListener(topics = "orders", groupId = "billing")` registers a consumer. `ContainerProperties` exposes `setSyncCommits()`, `setAckMode()`. `ConcurrentMessageListenerContainer` runs N `KafkaMessageListenerContainer` threads — the `concurrency` parameter on `@KafkaListener(concurrency = "3")` spins up 3 listener threads, each is a separate consumer instance in the group, each will own a slice of partitions. Spring's `ConsumerRebalanceListener` integration lets you commit offsets on partition assignment/revocation.
- **Node.js** (`kafkajs`): `new Consumer({ groupId: 'billing' })` then `await consumer.subscribe({ topic: 'orders', fromBeginning: true })`. `consumer.run({ eachMessage: async ({message}) => ... })` wraps the poll loop. Rebalance events surface as `consumer.on(consumer.events.REBALANCE_SYNC, ...)`. kafkajs supports cooperative sticky via `partitionAssigners: [PartitionAssigners.cooperativeSticky]`.
- **Python** (`confluent-kafka`): `Consumer({'group.id': 'billing', 'enable.auto.commit': False, 'partition.assignment.strategy': 'cooperative-sticky'})` then `consumer.subscribe(['orders'], on_assign=on_assign_cb)`. The `on_assign` callback is where you commit last-seen offsets for newly-assigned partitions, key for at-least-once correctness.
- **PHP** (`rdkafka` extension): `new RdKafka\Consumer($conf); $consumer->newQueue()->consume(1000);` with `$conf->set('group.id', 'billing')`. The PHP extension is a librdkafka binding, so it inherits librdkafka's sensible defaults — including cooperative-sticky as the default assignor in modern versions.

The conceptual shape is identical across all four: subscribe with a `group.id`, let the broker pick a coordinator, run the rebalance protocol in the background, expose hooks for partition assignment/revocation. The differences are in default values (Spring defaults to `RangeAssignor` for compatibility; kafkajs defaults to `RoundRobinAssignor`; librdkafka-based clients default to `CooperativeStickyAssignor`) and in how rebalance events surface to application code (callback in Java/PHP, event emitter in Node, callback in Python).

## Hands-On Exercise

```bash
# 1. Run a 3-consumer group against a 6-partition topic and watch the assignment
docker exec kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic perf --group demo \
  --partition-assignment-strategy org.apache.kafka.clients.consumer.CooperativeStickyAssignor \
  --from-beginning &

# 2. In another shell, inspect the group membership and partition ownership
docker exec kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --describe --group demo
#   Output columns: TOPIC PARTITION CURRENT-OFFSET LOG-END-OFFSET LAG CONSUMER-ID HOST CLIENT-ID

# 3. Launch a second consumer in the same group → rebalance fires, partitions redistribute
docker exec kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic perf --group demo &

# 4. Re-run describe — note that with cooperative-sticky, existing partitions stayed put
docker exec kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --describe --group demo

# 5. Kill one consumer abruptly (SIGKILL) → coordinator waits session.timeout.ms, then rebalances
pkill -9 -f kafka-console-consumer
docker exec kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --describe --group demo --state
#   State column cycles: Stable → PreparingRebalance → CompletingRebalance → Stable

# 6. Reset the group to earliest (simulates fresh start)
docker exec kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --group demo --reset-offsets \
  --to-earliest --topic perf --execute
```

Steps 2 and 4 together show the difference between eager and cooperative rebalancing: with `CooperativeStickyAssignor` the partitions already owned by the first consumer should not move when the second consumer joins, whereas with `RangeAssignor` they would have reshuffled completely.
