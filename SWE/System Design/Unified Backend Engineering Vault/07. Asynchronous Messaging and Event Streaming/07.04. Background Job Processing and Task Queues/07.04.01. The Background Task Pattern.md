# 07.04.01. The Background Task Pattern

## What This Is

The background task pattern is the architectural answer to a simple observation: an HTTP request handler has roughly 200 ms of user-tolerated latency budget, and a surprising fraction of useful work takes longer than that. Sending a welcome email through SES, generating a PDF invoice, transcoding an uploaded video, calling a third-party REST API that occasionally takes 30 s, running a nightly reconciliation job over 10 million rows — none of these can fit inside a request/response cycle without either degrading the user experience or risking a load-balancer timeout (AWS ALB cuts you off at 60 s). The pattern's answer is to **enqueue** the work as a serializable unit (a "job") and return immediately to the user, while a separate worker process picks up the job later and runs it with its own retry, timeout, and observability semantics.

This note sits at the top of section 07.04 because it defines the conceptual contract that the ecosystem-specific implementations (07.04.02) build on. The pattern is intentionally distinct from the Kafka consumer pattern in 07.03: a Kafka consumer reads from a partitioned log with at-least-once delivery and an unbounded backlog; a task queue reads from a FIFO queue (Redis LIST, RabbitMQ, Postgres table) with per-job acknowledgment, a visibility timeout, and a dead-letter destination. Both are asynchronous work offloaders, but the data structure and the failure model differ — task queues optimize for per-job retry and DLQ semantics, Kafka optimizes for partition-ordered high-throughput streaming. Most production systems use both: Kafka for the event stream and a task queue for the per-event fan-out work that needs richer retry semantics than Kafka's rebalance protocol provides.

## The Details

### Offloading blocking I/O, heavy computational work, and third-party API integrations from the critical HTTP request path

The HTTP request path is a critical section: every millisecond spent in the handler is a millisecond of user-perceived latency, a millisecond of held database connection, a millisecond of occupied worker slot that cannot serve another request. The 200 ms budget breaks down roughly as 20 ms for the load balancer + TLS handshake, 20 ms for the framework's routing/middleware/serialization overhead, 50–100 ms for the database query, and 50–100 ms of slack for cache misses and serialization. Anything that takes longer than ~50 ms and is not strictly required to produce the HTTP response is a candidate for offload. The decision is rarely about the average case — it is about the tail: if the third-party email API takes 50 ms at p50 but 8 s at p99, you cannot serve it inline without occasionally exhausting your HTTP worker pool.

Four classes of work belong in the background. **Blocking I/O to slow third parties**: email/SMS providers (SES, Twilio), payment gateways (Stripe, Adyen), legacy SOAP services — these have p99 latencies measured in seconds and failure rates of 0.1–1%, both unacceptable inline. **Heavy computation**: PDF generation (WeasyPrint, wkhtmltopdf), image/video transcoding (ffmpeg, Pillow), ML inference (PyTorch, ONNX), report aggregation over millions of rows — these saturate CPU for seconds to minutes and would block a worker thread from serving any other request. **Periodic / scheduled work**: nightly reconciliation, hourly cache warming, daily summary emails — these have no user waiting at all and should run on a cron-triggered worker, not on an HTTP request. **Decoupled fan-out**: an event happens ("user signed up") and five independent side effects should fire (welcome email, analytics event, CRM update, audit log, referral credit) — running all five inline multiplies the failure surface, while enqueuing five jobs lets each one fail and retry independently.

```text
  Inline (synchronous) vs Background (asynchronous):
  ────────────────────────────────────────────────────────────────────
  INLINE:   user ──HTTP──▶ app ──▶ DB write ──▶ SES.send() ──▶ HTTP 200
            ◀── total ~250-8000ms (depends on SES p99) ────────────

  BACKGROUND:  user ──HTTP──▶ app ──▶ DB write ──▶ enqueue(email_job) ──▶ HTTP 202
               ◀── total ~30ms ──────────────────────────────────────

                              [queue]  ──▶ worker ──▶ SES.send() ──▶ ack
                                                (3 retries with backoff on failure)
```

The visible-vs-invisible failure distinction is the part most teams underweight. When work runs inline and fails, the user gets a 500 and can retry — the failure is **visible**. When work runs in the background and fails, the user gets a 202 (Accepted) and assumes success; the failure is **invisible** until someone checks the DLQ. This means the background pattern requires you to add observability that the inline pattern got for free: a worker healthcheck endpoint, a queue-depth metric, a DLQ-depth alert, and ideally a per-job status endpoint that the frontend can poll (`GET /api/jobs/{id}` → `{status: "completed" | "failed" | "running"}`). The corollary is that background jobs are the **wrong** choice when the user needs the result to respond to the request — if you need the PDF to render before you can return the response, you want synchronous in-process work, or an RPC call to a separate rendering service, or a job + polling-with-short-timeout hybrid (enqueue + poll for completion for up to 5 s, then return "still processing, check back later"). The failure mode that hurts is using a background job for what should be synchronous (e.g., "validate the user's upload before acknowledging") — the user gets a 202, assumes it worked, and moves on, only to discover hours later that the upload was rejected. The fix is to keep validation synchronous and only offload the slow post-validation side effects.

### Anatomy of a Background Job: Job ID, Payload Serialized Data, Attempt Count, Max Retries, Backoff Strategy (Exponential + Jitter), Expiration TTL

A background job is a serializable record carried by the queue, mutated by the worker, and persisted across retries. Every mature task queue — Celery, BullMQ, Sidekiq, Laravel Queues, Spring's `QueueMessage` — models essentially the same fields under different names, because the operational requirements are universal: dedup, retry, backoff, expiration, and observability. Understanding the field set is what lets you reason about failure modes ("what happens if the worker crashes between picking up the job and acking it?") and to compare implementations across ecosystems.

| Field             | BullMQ                | Celery                 | Sidekiq              | Laravel                | Purpose                                              |
|-------------------|-----------------------|------------------------|----------------------|------------------------|------------------------------------------------------|
| Job ID            | `id` (UUID)           | `id` (UUID)            | `jid` (UUID)         | `uuid`                 | Dedup, tracing, idempotency key                      |
| Payload           | `data` (JSON)         | `args` (JSON/pickle)   | `args` (JSON)        | `payload` (serialized) | The input to the handler                             |
| Attempt count     | `attemptsMade`        | `request.retries`      | `retry_count`        | `attempts`             | Track retry budget                                    |
| Max retries       | `attempts` config     | `max_retries`          | `retry` option       | `$tries` property      | Cap before DLQ                                        |
| Backoff strategy  | `backoff` (exponential/jittered) | `retry_backoff` | `sidekiq_retry_in`   | `$backoff` property    | Delay schedule between retries                       |
| Expiration TTL    | `jobId` expiry in Redis | `expires`             | `expiry`             | `retryUntil` / `timeout` | Discard stale jobs                                   |
| Priority / queue  | `priority` + `queue`  | `queue`                | `queue`              | `queue` + `delayed`    | Routing to specific worker pools                     |
| Scheduled-at      | `delay` (timestamp)   | `eta`                  | `at`                 | `delayed`              | Future-execution scheduling                          |
| Idempotency key   | `jobId` (dedup)       | `task_id` (custom)     | `jid`                | custom                 | Safe retry — handler checks "have I done this?"      |

The **backoff strategy** is the field that does the most operational work. Pure exponential backoff (`delay = base * 2^attempt`) is correct in shape but produces thundering-herd behavior: if 1000 jobs all fail at the same instant (a downstream outage), they will all retry at exactly `base * 2`, then exactly `base * 4`, then `base * 8`, hammering the recovering downstream service in synchronized waves. The standard fix is **decorrelated jitter**: `delay = random_between(base, prev_delay * 3)`, which spreads retries across a random window and breaks the synchronization. The AWS Architecture Blog's "Exponential Backoff and Jitter" article (2015) is the canonical reference; both BullMQ and Celery implement this as the default jittered-exponential strategy.

```text
  Pure exponential (BAD — synchronized retry waves):
  ─────────────────────────────────────────────────────
  t=0     1000 jobs fail simultaneously
  t=1s    1000 jobs retry → downstream still recovering → all fail again
  t=2s    1000 jobs retry → all fail again
  t=4s    1000 jobs retry → all fail again
  t=8s    1000 jobs retry → downstream up → all succeed simultaneously (load spike)

  Exponential + decorrelated jitter (GOOD — spread retries):
  ──────────────────────────────────────────────────────
  t=0          1000 jobs fail simultaneously
  t=0.1–1.0s   1000 retries spread across 900ms window → downstream still warming
  t=0.4–4.0s   second retries spread across 3.6s window
  t=1.6–16s    third retries spread across 14.4s window → downstream up → trickle of success
  t=...        steady recovery, never more than ~5 jobs/sec hitting downstream
```

```python
# Celery task with full anatomy
from celery import Celery
import random, time

app = Celery("billing", broker="redis://localhost:6379/0", backend="redis://localhost:6379/1")

@app.task(
    bind=True,
    max_retries=5,                            # max retries before DLQ
    default_retry_delay=0,                    # we use custom backoff below
    autoretry_for=(TimeoutError, ConnectionError),
    retry_backoff=1,                          # base delay in seconds
    retry_backoff_max=300,                    # cap at 5 minutes
    retry_jitter=True,                        # decorrelated jitter
    queue="billing-high",                     # routing to a dedicated worker pool
    time_limit=120,                           # hard kill at 2 minutes
    soft_time_limit=90,                       # SoftTimeLimitExceeded at 90s
)
def charge_card(self, order_id, customer_id, amount_cents):
    # Idempotency: dedup table keyed on (order_id, customer_id)
    if already_processed(order_id, customer_id):
        return {"status": "duplicate-skipped"}
    try:
        stripe.Charge.create(amount=amount_cents, customer=customer_id,
                             idempotency_key=f"order-{order_id}")
        mark_processed(order_id, customer_id)
    except stripe.error.CardError as exc:
        # Card errors are NOT retriable — go straight to DLQ
        raise self.discard()
    except stripe.error.RateLimitError as exc:
        # Rate limited — retriable, use Celery's backoff
        raise self.retry(exc=exc)
```

The Stripe `idempotency_key` in the example is the **external idempotency** layer: Stripe's API deduplicates on the key, so even if Celery retries the job after a network timeout, Stripe will not double-charge. This is the correct pattern for any third-party API that supports idempotency keys — combine the queue's retry with the API's dedup, and you get effective exactly-once against the external system without needing Kafka transactions. The production failure mode to fear is a job that has no idempotency key anywhere (not in the dedup table, not in the third-party API call): a retry produces a second side effect (double email, double charge, double count), and the operator has to manually reconcile. The fix is to make `idempotency_key` a required field on every job definition and enforce it in code review.

### Worker concurrency: Multi-process vs. Multi-threaded worker pools

The worker concurrency model determines how many jobs a single host can process in parallel and how isolated those jobs are from each other. The two dominant models are **multi-process** (the worker spawns N child processes, each handling one job at a time) and **multi-threaded** (the worker is one process with N threads, each handling one job). The choice is rarely free — it is forced by the runtime's threading characteristics: Python's GIL pushes Celery to multi-process (prefork), PHP's shared-nothing process model pushes Laravel Horizon to multi-process (php-fpm workers), Java's mature threading pushes Spring Batch to multi-threaded `ThreadPoolTaskExecutor`, and Node.js's single-threaded event loop pushes BullMQ to a single-process multi-coroutine model.

**Multi-process** (Celery prefork, Laravel Horizon, Sidekiq with multi-process): each worker is a separate OS process with its own memory space, its own GC, its own connection pool. The isolation is excellent — a memory leak in one job affects only that process; a SIGKILL cleanly reclaims all resources; a C-extension segfault takes down one worker, not the whole pool. The cost is memory duplication: each process loads the full application (framework, dependencies, bytecode), so a 200 MB Spring Boot app becomes 200 MB × N processes. For N=8 workers on a 4 GB box, that is 1.6 GB just for the worker processes, before any actual job memory. The fix is to keep the worker bootstrap lean (lazy-load heavy dependencies, use a slim framework profile) and to tune `--max-tasks-per-child` (Celery) or `--max-jobs` (Horizon) so each worker recycles after K jobs, preventing slow memory leaks from accumulating.

**Multi-threaded** (Spring `ThreadPoolTaskExecutor`, Java `ExecutorService`, Python `ThreadPoolExecutor` for I/O-bound work): one process, N threads sharing memory. Memory cost is one process plus per-thread stacks (~1 MB per thread by default in the JVM, configurable down to 256 KB). Startup cost is one bootstrap, not N. The cost is shared fate — a thread that crashes (uncaught exception) is recoverable but a thread that leaks memory poisons the whole process; a long GC pause stalls every thread. For I/O-bound work (HTTP calls, DB queries, third-party APIs), threads are the right model because they spend most of their time blocked on I/O and the JVM can scale to thousands of threads if each is mostly waiting.

```text
  Multi-process worker pool (Celery prefork example):
  ──────────────────────────────────────────────────
  celery-master (orchestrator)         RAM: ~50 MB
   ├── fork → worker-1 (job in flight)  RAM: ~250 MB (full app + job heap)
   ├── fork → worker-2                  RAM: ~250 MB
   ├── fork → worker-3                  RAM: ~250 MB
   ├── fork → worker-4                  RAM: ~250 MB
   └── (idle)                            ← spawns more on demand, kills after --max-tasks-per-child
                                       Total RAM: 4 × 250 = ~1 GB

  Multi-threaded worker pool (Spring @Async example):
  ──────────────────────────────────────────────────
  jvm-process (single OS process)      RAM: ~300 MB (shared app + JIT code cache)
   ├── Thread[pool-1-thread-1]         RAM: ~1 MB stack
   ├── Thread[pool-1-thread-2]         RAM: ~1 MB stack
   ├── Thread[pool-1-thread-3]         RAM: ~1 MB stack
   └── Thread[pool-1-thread-4]         RAM: ~1 MB stack
                                       Total RAM: ~304 MB
```

Pool size tuning depends on whether the job is **CPU-bound** or **I/O-bound**. For CPU-bound jobs (image processing, ML inference, hashing), the optimal pool size is roughly `num_cores` — more workers than cores just thrash the CPU scheduler. For I/O-bound jobs (HTTP calls, DB queries), the optimal pool size is bounded by Little's Law: `pool_size = throughput_target × average_latency`, which can be much higher than the core count. A job that takes 500 ms and needs 1000 jobs/sec throughput needs `pool_size = 1000 × 0.5 = 500` workers — well above any reasonable core count, achievable because most of those workers are blocked on I/O at any moment. The standard production failure mode is a team that configures a CPU-bound worker pool with `concurrency=100` on a 4-core box and wonders why throughput is no better than `concurrency=4` — the answer is that the extra 96 workers are just context-switching each other to no benefit, while burning 100× the memory. The fix is to identify the job class and tune accordingly: CPU-bound → `concurrency ≈ num_cores`, I/O-bound → `concurrency ≈ Little's Law target × latency`, and monitor `worker-busy-ratio` (should be >0.7 at peak; <0.3 means you have too many workers, >0.95 means you have too few).

The **visibility timeout** and **graceful shutdown** complete the model. The visibility timeout (called differently in each queue: `visibility_timeout` in SQS, `lock_timeout` in BullMQ, `visibility_timeout` in Celery's Redis broker) is how long a job is hidden from other workers after being picked up — if the original worker does not ack within this window, the job becomes visible again and another worker picks it up (at-most-once becomes at-least-once for slow workers). Set it to ~3× the worst-case job latency to avoid double-processing, and never set it shorter than your longest job. Graceful shutdown is the symmetric concern: when deploying a new version, you need to stop accepting new jobs, finish in-flight jobs, and then exit — `SIGTERM` → stop polling → wait up to `shutdown_timeout` → `SIGKILL`. Spring's `ThreadPoolTaskExecutor.setWaitForTasksToCompleteOnShutdown(true)` + `setAwaitTerminationSeconds(30)` implements this; Celery's `--time-limit` and `worker_stop_after` are the equivalent; BullMQ's `worker.close(true)` does the same. The failure mode to fear is a hard deploy that SIGKILLs workers mid-job — the visibility timeout eventually expires and the job is retried, but only after the timeout window, during which the user-visible effect is delayed by minutes.

## How This Connects to the Frameworks

- **Spring Boot**: `@EnableAsync` + `@Async("billingExecutor")` on a method routes it to a `ThreadPoolTaskExecutor` bean. For heavier job-queue semantics (DLQ, retry, persistence), Spring Batch or Spring Cloud Data Flow. Spring Integration's `MessageChannel` + `ServiceActivator` is the in-process equivalent of a task queue.
- **Node.js**: BullMQ over Redis is the dominant choice — delayed jobs, parent-child workflows (`FlowProducer`), priority queues, rate limiting per concurrency, built-in dashboard (Bull Board). Agenda over MongoDB is the alternative for teams already on Mongo.
- **Python**: Celery over Redis/RabbitMQ is the workhorse — `@app.task`, `task.retry()`, `chord`/`group`/`chain` primitives for complex workflows. Dramatiq is a modern alternative with a cleaner API and no pickle-by-default. RQ (Redis Queue) is the lightweight option.
- **PHP**: Laravel Queues with Redis/database/Beanstalkd/SQS driver, Horizon dashboard for Redis. The `ShouldQueue` marker interface + `dispatch(new SendWelcomeEmail($user))` is the API. Symfony Messenger is the framework-agnostic alternative.

The conceptual shape is identical across all four: a job is a serializable record, the queue is a FIFO with visibility timeout and DLQ, the worker is a process or thread pool with retry budget and backoff, the framework provides the marshalling glue. The differences are in default choices (Python defaults to multiprocessing because of the GIL; Java defaults to threading because the JVM threads are cheap; PHP defaults to multiprocessing because PHP-FPM is already a process pool; Node defaults to single-process coroutines because V8's event loop makes threading unnecessary for I/O-bound work).

## Hands-On Exercise

```bash
# 1. Run Redis as the queue backend
docker run -d --name redis -p 6379:6379 redis:7-alpine

# 2. Enqueue a delayed job from a one-off Python script
pip install redis rq
python -c "
from datetime import timedelta
from redis import Redis
from rq import Queue
q = Queue('default', connection=Redis(host='localhost', port=6379))
job = q.enqueue_in(timedelta(seconds=30), print, 'hello from the future')
print(f'Enqueued job {job.id}, status={job.get_status()}')
"

# 3. Start a worker (separate terminal) — it will pick up the delayed job at t+30s
rq worker default --url redis://localhost:6379

# 4. Inspect Redis directly to see the job anatomy
docker exec redis redis-cli KEYS 'rq:job:*'         # all job keys
docker exec redis redis-cli HGETALL 'rq:job:<id>'   # the serialized payload + retries

# 5. Trigger a poison-pill job (one that always throws) and watch it retry → DLQ
python -c "
from rq import Queue
from redis import Redis
def always_fails(): raise RuntimeError('poison pill')
Queue(connection=Redis()).enqueue(always_fails)
"
# Watch the worker log: retry 1 → retry 2 → retry 3 → moved to 'failed' queue

# 6. Inspect the failed queue (the DLQ)
docker exec redis redis-cli LLEN 'rq:queue:failed'
docker exec redis redis-cli LRANGE 'rq:queue:failed' 0 5

# 7. Load test the worker to find the right concurrency
rq worker default --url redis://localhost:6379 --burst --workers 4  # multi-process
# Then with --workers 8, 16, 32 and measure jobs/sec — find the inflection point
# where more workers stops helping (CPU-bound) or keeps helping (I/O-bound).
```

Steps 4 and 6 directly expose the job anatomy (fields like `created_at`, `origin`, `description`, `data`, `enqueued_at`, `exc_info`) that this note describes abstractly. Step 7 is the empirical version of the pool-size-tuning discussion: by measuring jobs/sec at different `--workers` values on your real workload, you can see whether your jobs are CPU-bound (plateau at `num_cores`) or I/O-bound (linear scaling until you hit the downstream rate limit).
