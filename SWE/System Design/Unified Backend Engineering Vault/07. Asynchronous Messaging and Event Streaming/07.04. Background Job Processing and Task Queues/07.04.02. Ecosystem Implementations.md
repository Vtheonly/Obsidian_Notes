# 07.04.02. Ecosystem Implementations

## What This Is

Background job ecosystems are the concrete implementations of the abstract "task queue" idea from [[07.04.01. The Background Task Pattern]]. Each major backend stack ships a working job runner with its own answer to the same four questions: *where do jobs live while waiting*, *how does a worker atomically claim one*, *how are failures retried without thundering-herd duplicate execution*, and *how is the queue observed in production*. The answers differ in mechanism — a Redis Lua script vs. a Postgres `SKIP LOCKED` scan vs. an AMQP `basic.consume` — but the shape is identical because the underlying layer-7 problem is identical: serialize units of work, deliver them at-least-once, and survive crashes of both the producer and the consumer.

This note is the cross-ecosystem tour: Spring Boot (`@Async` + `ThreadPoolTaskExecutor` + Spring Batch + Spring Cloud Stream + Spring Kafka), Node.js (BullMQ over Redis), Python (Celery over Redis or RabbitMQ with the `@app.task` decorator + the worker process + the beat scheduler), and PHP (Laravel Queues with `queue:work` / `queue:listen` + Horizon). Each section dives into the specific primitives, the configuration knobs that actually matter, and the production failure mode that the ecosystem's defaults quietly expose.

The mental model: section 07.04.01 defined the abstract "job" abstraction; this section grounds it in real implementations that sit on the runtime primitives from section 02 (the JVM thread pool in Spring's case, the libuv event loop in Node's case, the CPython process model in Celery's case, the PHP-FPM/Swoole process model in Laravel's case) and on the messaging brokers from section 07.01–07.03 (Redis Streams, RabbitMQ, Kafka). Each ecosystem's defaults reflect its host runtime's strengths and constraints, which is why a Node.js shop reaches for BullMQ and a Java shop reaches for Spring Batch without either being "wrong".

## The Details

### *Java / Spring Boot*: Spring `@Async`, `ThreadPoolTaskExecutor`, Spring Batch chunk-based processing

Spring Boot gives you three layered options for background work, and picking the wrong one is the most common Spring performance bug in production. The simplest is `@Async`, which works by wrapping a bean method in a JDK dynamic proxy or CGLIB subclass: when caller code invokes `emailService.send(user)`, the proxy intercepts the call, submits a `Runnable` to a `TaskExecutor`, and returns immediately with a `null`/`void` (or a `Future`/`CompletableFuture` if the method returns one). The crucial invariant is that `@Async` only works on **public methods called from outside the bean** — a self-invocation like `this.send(user)` skips the proxy and runs synchronously on the request thread, which is the production incident nobody warned you about. You enable it with `@EnableAsync` on a `@Configuration` class, and you customise the executor with a bean:

```java
@Configuration
@EnableAsync
@EnableScheduling
class AsyncConfig {

    @Bean(name = "emailExecutor")
    public ThreadPoolTaskExecutor emailExecutor() {
        var ex = new ThreadPoolTaskExecutor();
        ex.setCorePoolSize(8);              // threads kept warm
        ex.setMaxPoolSize(32);              // burst ceiling
        ex.setQueueCapacity(200);           // bounded — see failure mode below
        ex.setKeepAliveSeconds(60);
        ex.setThreadNamePrefix("email-");
        ex.setRejectedExecutionHandler(
            new ThreadPoolExecutor.CallerRunsPolicy()); // back-pressure
        ex.initialize();
        return ex;
    }

    @Bean
    public ThreadPoolTaskScheduler taskScheduler() {
        var s = new ThreadPoolTaskScheduler();
        s.setPoolSize(4);
        s.setThreadNamePrefix("sched-");
        return s;
    }
}

@Service
class EmailService {
    @Async("emailExecutor")           // pick the executor by qualifier
    public CompletableFuture<Void> send(User user) {
        // runs on email-1..email-32, never on http-nio-*
        smtpClient.send(user.getEmail(), render(user));
        return CompletableFuture.completedFuture(null);
    }
}

@Component
class NightlyReportJob {
    @Scheduled(cron = "0 0 2 * * *", zone = "America/New_York")
    public void run() {
        reportService.generateDailyReport(LocalDate.now().minusDays(1));
    }
}
```

The `ThreadPoolTaskExecutor` is a thin wrapper around `java.util.concurrent.ThreadPoolExecutor` whose behaviour follows the JDK's documented but counter-intuitive rule: a new task first tries `corePoolSize`, then the `queueCapacity`-deep `LinkedBlockingQueue`, and only when the queue is full does it spawn threads up to `maxPoolSize`. So if you set `corePoolSize=32`, `maxPoolSize=64`, and `queueCapacity=Integer.MAX_VALUE` (the default), **the pool will never grow past 32 threads** because the unbounded queue never fills. The fix is to either cap the queue (so back-pressure kicks in) or set `corePoolSize == maxPoolSize` so all threads are eagerly created. The `CallerRunsPolicy` rejection handler is the cheapest back-pressure mechanism: when the queue is full the producer thread runs the task itself, which slows the producer down without dropping work — exactly what you want for a job whose whole point is to protect the HTTP path from overload.

`@EnableScheduling` + `@Scheduled` is the cron-tier option: a single `ThreadPoolTaskScheduler` (default pool size 1!) wakes up at the cron tick and runs every `@Scheduled` method. Because the default scheduler pool is one thread, a slow `@Scheduled` job **blocks every other scheduled job in the application** — you must raise `spring.task.scheduling.pool.size` (default 1) to at least the number of concurrent cron jobs you expect, or one job's 30-second database call will silently delay the midnight backup. For real batch work — millions of rows, restart-safe checkpoints, parallel chunk processing — you reach for **Spring Batch**, whose `Step` is configured with `chunkSize(1000)` so the framework reads 1000 items from an `ItemReader`, hands them to an `ItemProcessor`, writes them via an `ItemWriter`, and commits the chunk's transaction. If the JVM crashes mid-step, on restart Spring Batch consults `BATCH_STEP_EXECUTION_CONTEXT` and resumes from the last committed chunk. For pub-sub async (event-driven microservices), Spring Cloud Stream + Spring Kafka replace the in-process `TaskExecutor` with a `KafkaListenerContainer` that pulls from a Kafka topic, and the same `@SendTo` + `StreamBridge` pattern lets a service publish a message without blocking.

The production failure mode for Spring async is the **thread-pool leak via unbounded `ThreadLocal` accumulation**: if your `@Async` method uses `ThreadLocal` for transaction/audit context (Spring's `RequestContextHolder` does this implicitly), and your executor reuses threads, then stale request-scoped state from one job bleeds into the next. The fix is `TaskDecorator` that clears `ThreadLocal`s before each task runs. The metric that reveals it: `executor.activeCount` stays high while `executor.queueSize` is low, but throughput collapses because jobs are spending their time in someone else's N+1 Hibernate session.

### *TypeScript / Node.js*: BullMQ over Redis: Redis Streams, Lua atomic state transitions, delayed j...

BullMQ is the modern successor to Bull, written in TypeScript and built on three Redis primitives: **Redis Streams** for the FIFO backlog, **sorted sets** for delayed-job scheduling, and **Lua scripts** for atomic state transitions. The central insight is that Redis is single-threaded, so a Lua script runs atomically — nobody can observe a half-moved job. BullMQ uses this to implement the classic "move job from WAITING → ACTIVE → COMPLETED" state machine in one round-trip:

```typescript
import { Queue, Worker } from "bullmq";
import IORedis from "ioredis";

const connection = new IORedis("redis://cache:6379", {
  maxRetriesPerRequest: null,   // BullMQ requires this — otherwise retry loops break
});

const emailQueue = new Queue("email", { connection });

// Producer — pushes a job with optional delay, priority, and parent-child links
await emailQueue.add(
  "send-welcome",
  { userId: 42, template: "welcome" },
  { delay: 5_000,           // ms — uses a ZSET scored by ready-at timestamp
    attempts: 5,            // retry cap
    backoff: { type: "exponential", delay: 1_000 },
    priority: 1,            // lower = higher priority
    removeOnComplete: 1000, // keep last 1k completed for debugging
    removeOnFail: 5000 }    // bounded graveyard — protects Redis memory
);

// Worker — pulls jobs, runs them, acks/fails them
const worker = new Worker(
  "email",
  async (job) => {
    const user = await db.users.findById(job.data.userId);
    await mailer.send(user.email, render(job.data.template, user));
    // returning normally → BullMQ runs a Lua script to mark COMPLETED
    // throwing    → BullMQ schedules a retry with backoff, or fails
  },
  { connection,
    concurrency: 16,                     // per-worker in-flight cap
    limiter: { max: 100, duration: 1000 } } // 100 jobs/sec rate-limit
);

worker.on("failed", (job, err) => {
  logger.error({ id: job.id, attempts: job.attemptsMade }, err);
});
```

Internally BullMQ stores every job as a Redis hash at key `bull:email:<jobId>` with fields `data`, `opts`, `name`, `progress`, `attemptsMade`, `returnvalue`, `failedReason`, `finishedOn`. The queue's lifecycle keys are: `bull:email:wait` (a LIST of pending job IDs), `bull:email:active` (a LIST of jobs being processed), `bull:email:delayed` (a ZSET scored by ready-at timestamp), `bull:email:completed` and `bull:email:failed` (ZSETs scored by finished-at), and `bull:email:priority` (a ZSET scored by priority value). The `moveToActive` Lua script atomically pops the highest-priority job from `wait`/`priority`/`delayed`, pushes it to `active`, and returns its payload — all in one Redis round-trip and with no race window, which is why BullMQ survives a producer and a worker racing for the same job without double-dispatch.

The killer feature for complex workflows is **parent-child flows** (a.k.a. "flows" / "DAG" support). A parent `FlowProducer` builds a tree where the parent job is only moved to `wait` after every child has reached `completed`. This is how you compose "fan out to send-verify-email + send-welcome-email + create-billing-record, and once all three succeed, trigger a single onboarding-complete job". BullMQ stores the dependency graph as Redis sets (`bull:email:<parentId>:processed` and `bull:email:<parentId>:unprocessed`) and a Lua script on each child completion checks whether `unprocessed` is now empty; if so, it atomically moves the parent from `wait-children` to `wait`. The equivalent in Celery is a `chord`, the equivalent in Spring is a `Split` + `Aggregator` from Spring Integration.

The Node-specific production failure mode is **the single-threaded event loop + CPU-bound job**: if your `worker` function does a synchronous 200ms JPEG resize, it blocks every other in-flight job (and every BullMQ timer) for those 200ms. At concurrency=16 you might expect 16× throughput, but a CPU-bound job caps you at one job per 200ms = 5 jobs/sec regardless of concurrency. The fix is to offload CPU work to `worker_threads` (`import { Worker } from "worker_threads"`) or to a child process via `child_process.fork`, leaving the main worker thread free to drain the queue. The metric that reveals it: `eventLoopLag` from `perf_hooks.monitorEventLoopDelay()` exceeds 100ms while BullMQ's `active` count is at the concurrency ceiling.

### *Python*: Celery over Redis/RabbitMQ: Prefetch limits, visibility timeouts, task routing, canvas ...

Celery is the de-facto Python job runner and has been since 2009. Its architecture splits cleanly into three processes: the **producer** (your web app, calling `task.delay(arg)` or `task.apply_async(args=[arg], countdown=60)`), the **broker** (Redis, RabbitMQ, or Amazon SQS — the durable backlog), and the **worker** (a separate process started with `celery -A tasks worker --loglevel=info --concurrency=8`). The worker is a prefork pool by default: a master process forks N child processes (N = CPU count by default), and each child pops messages from the broker, deserializes the payload, runs the task function, and acks. The split is the same as Spring's `@Async` + broker: the producer never blocks on the task body, and the worker can be restarted without losing in-flight jobs as long as the broker is durable.

```python
# tasks.py
from celery import Celery, chain, group, chord

app = Celery("orders",
             broker="redis://cache:6379/0",
             backend="redis://cache:6379/1",
             task_serializer="json",
             result_serializer="json",
             accept_content=["json"],
             task_acks_late=True,                 # ack after success, not on receive
             worker_prefetch_multiplier=1,        # one in-flight per child — see below
             task_reject_on_worker_lost=True,     # redeliver if child segfaults
             visibility_timeout=3600)             # Redis-specific requeue timeout

@app.task(bind=True, max_retries=5,
          autoretry_for=(TimeoutError, ConnectionError),
          retry_backoff=True, retry_backoff_max=600, retry_jitter=True)
def process_payment(self, order_id: int):
    try:
        charge = stripe.Charge.create(amount=..., currency="usd")
        return {"charge_id": charge.id}
    except stripe.error.CardError as e:
        raise self.retry(exc=e, countdown=2 ** self.request.retries)

# Canvas — workflows composed of tasks
workflow = chain(
    group(import_csv.s(fp) for fp in files),     # fan-out: parallel
    dedupe.s(),                                    # then dedupe
    chord(process_batch.s(), send_report.s(me))   # then fan-in -> report
)
workflow.apply_async()

@app.task
def import_csv(fp: str) -> list[int]:
    ...
```

Three Celery knobs are non-obvious and misconfigured in ~80% of production deployments. **`worker_prefetch_multiplier`** (default 4) controls how many messages a single worker child pulls into its local buffer at once. With the default of 4 and `--concurrency=8`, one worker can prefetch 32 messages — and if your queue has 50 long-running jobs and one short one, the short one might be stuck behind 32 prefetched long ones in another child's buffer, while a free child sits idle. Set `worker_prefetch_multiplier=1` for long-running tasks (anything over 1 second) and leave it at 4 only for fast (sub-100ms) tasks where the round-trip overhead matters. **`task_acks_late=True`** changes the ack semantics from "ack on receive" (the default, which loses the task if the child crashes mid-execution) to "ack on success" — combined with `task_reject_on_worker_lost=True`, this guarantees at-least-once delivery even if a child segfaults. **`visibility_timeout`** (Redis-only; defaults to 3600s) is the time a message stays invisible after being delivered — if the worker doesn't ack within this window, Redis assumes it died and redelivers the message. Set this to **at least 2× the longest possible task runtime**, otherwise a long task will be silently redelivered while the original is still running, producing duplicate side effects (double-charged credit cards, double-sent emails).

The **canvas** primitives are Celery's answer to BullMQ's parent-child flows and Spring's `Aggregator`: `chain` runs tasks sequentially passing each one's return value to the next; `group` fans out in parallel; `chord` is a `group` followed by a callback that receives the list of all results; `chunks` splits a big list into N-sized chunks processed in parallel. Under the hood a chord writes the count of uncompleted children to a Redis counter (`celery-taskset-meta-<chord-id>`) and decrements it atomically; when it hits zero, the callback fires. The production gotcha: if a child of a chord fails (raises an uncaught exception and exhausts its retries), the chord's callback **never fires** — the parent sits waiting forever for a child that has moved to the failed state. Celery 4.x added `chord_error` callbacks to handle this; without one, the dashboard shows a permanently pending chord and downstream pipelines stall silently.

The Python-specific failure mode is **the GIL + prefork pool vs `--pool=solo`/`--pool=gevent`**: the prefork pool (default) sidesteps the GIL by using separate processes, so a CPU-bound task at `--concurrency=8` actually uses 8 cores. But if you switch to `--pool=gevent` (because your tasks are I/O-bound and you want 1000 concurrent greenlets), a CPU-bound task will freeze every greenlet in the worker — the GIL has no preemption, so a tight `while True` in one greenlet starves every other. The metric that reveals it: Celery's `celery@worker.active` shows 1000 in-flight tasks but throughput drops to zero and `prefetch_time` climbs. The fix is to keep prefork for CPU work and use gevent only for pure I/O, or move CPU work to a separate queue with its own pool type.

### *PHP / Laravel*: Laravel Queue Workers: Redis/Database drivers, worker daemon lifecycles, failed ...

Laravel Queues is the most ergonomic job API in any major framework: a single `dispatch(new SendEmail($user))` call from anywhere in the codebase pushes a job onto the configured connection, and a long-running `php artisan queue:work` daemon polls the connection and runs the job's `handle()` method. The job class itself is a plain POPO (Plain Old PHP Object) with a `handle()` method; Laravel serializes the job (including its constructor-injected data) via PHP's `serialize()`, pushes the JSON-wrapped blob onto Redis/Database/SQS/Beanstalkd, deserializes it on the worker side, and resolves `handle()`'s type-hinted dependencies from the service container. The same job code runs unchanged across all five drivers because the driver just implements `push($payload)` and `pop(): $payload`.

```php
// app/Jobs/SendWelcomeEmail.php
namespace App\Jobs;

use App\Models\User;
use App\Mail\WelcomeMail;
use Illuminate\Bus\Queueable;
use Illuminate\Contracts\Queue\ShouldQueue;
use Illuminate\Foundation\Bus\Dispatchable;
use Illuminate\Queue\InteractsWithQueue;
use Illuminate\Queue\SerializesModels;
use Illuminate\Support\Facades\Mail;

class SendWelcomeEmail implements ShouldQueue {
    use Dispatchable, InteractsWithQueue, Queueable, SerializesModels;

    public int $tries = 5;                // retry cap
    public int $timeout = 60;             // SIGTERM after 60s
    public int $backoff = 30;             // first retry delay
    public array $backoff = [30, 60, 120, 300]; // or per-attempt array

    public function __construct(public User $user) {
        $this->onQueue('emails');         // route to a named queue
    }

    public function handle(): void {
        Mail::to($this->user)->send(new WelcomeMail($this->user));
    }

    public function failed(\Throwable $e): void {
        // called when tries exhausted — alert Sentry, push to failed_jobs
        logger()->error("welcome email failed", [
            'user_id' => $this->user->id, 'err' => $e->getMessage()]);
    }
}

// Anywhere in the app:
SendWelcomeEmail::dispatch($user)->delay(now()->addMinutes(5));
SendWelcomeEmail::dispatch($user)->onConnection('database');
```

The worker daemon is started with `php artisan queue:work redis --queue=emails,default --tries=3 --max-time=3600 --max-jobs=1000 --memory=128`. The flags matter: `--max-jobs=1000` causes the worker to gracefully self-restart after processing 1000 jobs (releasing any leaked memory, since PHP is shared-nothing and a long-running daemon accumulates state in statics and Eloquent's model cache); `--max-time=3600` does the same after an hour; `--memory=128` kills the worker if it exceeds 128MB (typically a sign of a query returning an unbounded result set). The lifecycle is: master process forks a child per `--worker=N`, the child does `pop` → `unserialize` → `handle()` → `ack` (or `release` for retry, or `fail` after `tries` exhausted). Supervisor or systemd restarts the master if it dies, and `php artisan queue:restart` (broadcast via a Redis flag that workers poll every 5s) lets you gracefully drain workers after a deploy without killing in-flight jobs.

**Horizon** is Laravel's first-party dashboard and supervisor for Redis queues. It runs as a separate `php artisan horizon` daemon that auto-scales worker pools based on queue depth (configurable in `config/horizon.php` as `'minProcesses' => 1, 'maxProcesses' => 12`), exposes a dashboard at `/horizon` with per-queue throughput / latency / failure-rate, and stores recent job payloads for debugging. It also adds a `Supervisor` concept where each "queue" (e.g. `emails`, `default`, `billing`) gets its own worker pool sized independently, which is how you prevent a slow `billing` queue from starving `emails`. The killer Horizon feature is **job tagging**: any job that implements `tags()` returning `['user:42', 'order:9981']` can be searched in the dashboard, so when a customer reports "I never got my receipt", you search `user:42` and see every job touching that user, with its payload, attempts, and duration.

The PHP-specific failure mode is the **shared-nothing mental model breaking down in long-running daemons**. PHP-FPM workers are recycled every request, so global state (DB connections, static caches, container singletons) is reset constantly. But `queue:work` is a long-running daemon — it sets up the container once at startup, then runs thousands of jobs. If you set `DB_CONNECTION=mysql` and use the default `config('database.connections.mysql')`, the worker holds one MySQL connection open for the whole hour; if MySQL `wait_timeout` is 60s and a job takes 90s, the connection silently drops and the next job gets `MySQL server has gone away`. The fix is `php artisan queue:work --max-jobs=100` (recycle often) or use Laravel's `DB::disconnect()` in job `handle()`. Eloquent's static relation cache (`Model::$resolver`) also leaks: every `User::find(1)` in a job adds to an in-memory map that grows unboundedly until the worker restarts. The metric that reveals it: RSS memory grows linearly with jobs processed, eventually hitting the `--memory` limit and triggering worker churn. See [[02.03.06. The Long-Running PHP Runtime]] for the deep dive on this whole class of bug.

## Cross-Ecosystem Comparison

The same job (send a welcome email to user 42, 5 retries with exponential backoff) across all four ecosystems:

| Aspect | Spring Boot | Node.js (BullMQ) | Python (Celery) | PHP (Laravel) |
|---|---|---|---|---|
| Enqueue API | `@Async("emailExecutor")` on a bean method | `emailQueue.add("send-welcome", {userId:42}, {attempts:5})` | `send_welcome.delay(42)` or `send_welcome.apply_async(args=[42])` | `SendWelcomeEmail::dispatch($user)` |
| Define job | Java method on `@Service` bean | `new Worker("email", async (job) => {...})` | `@app.task def send_welcome(uid): ...` | `class SendWelcomeEmail implements ShouldQueue { handle() {...} }` |
| Backing store | In-process `ThreadPoolTaskExecutor` (lost on JVM crash) | Redis Streams + ZSETs | Redis LIST / RabbitMQ queue | Redis LIST / `jobs` table |
| Retry / backoff | `@Retryable(maxAttempts=5, backoff=@Backoff(delay=1000, multiplier=2))` | `attempts: 5, backoff: { type: "exponential", delay: 1000 }` | `autoretry_for=(...), retry_backoff=True, max_retries=5` | `public int $tries = 5; public array $backoff = [30,60,120,300];` |
| Cron scheduler | `@Scheduled(cron = "0 0 2 * * *")` + `@EnableScheduling` | external (`bullmq-board` or `node-cron`) | `celery -A tasks beat` daemon + `@app.task` + `beat_schedule` dict | Laravel Scheduler: `$schedule->job(new NightlyReport)->dailyAt('02:00')` |
| Atomic claim | JVM-internal lock on the queue | Lua script (Redis single-threaded) | `BRPOPLPUSH` (Redis) or AMQP `basic.consume` ack | `LPOP` (Redis) or `SELECT ... FOR UPDATE SKIP LOCKED` (DB) |
| Dashboard | Spring Boot Actuator + Micrometer | Bull Board / BullMQ Pro UI | Flower | Laravel Horizon |
| Crash recovery | None for `@Async` (in-memory) | Durable (Redis) | Durable (broker) | Durable (Redis/DB) |
| Memory model | JVM threads + heap | Single-threaded event loop + libuv thread pool | Prefork processes (sidesteps GIL) | Long-running PHP daemon (shared-nothing violated) |

The pattern that emerges: **Spring `@Async` is the odd one out** because it is in-process and loses work on JVM crash — for true durability, Spring Boot services reach for Spring Cloud Stream + Kafka, which then looks structurally identical to BullMQ/Celery/Laravel (broker + worker). The other three are all broker-backed and durable by default, differing only in default broker (Redis for BullMQ, Redis-or-RabbitMQ for Celery, Redis-or-DB for Laravel) and in the host-runtime's concurrency model that the worker inherits.

## How This Connects to the Frameworks

Every framework in section 05 ends up needing a job runner because the HTTP request path has a 30-second ceiling (the browser's timeout, the load balancer's idle timeout from [[03.02.02]]) and most real work — generating reports, calling third-party APIs, sending transactional emails, processing uploads — takes longer than that or fails too often to be inline-safe. The choice of runner is dictated by the framework's host runtime, not by the framework itself:

- **Spring Boot** inherits the JVM's mature thread-pool primitives (`ThreadPoolExecutor`, `ForkJoinPool`) and so `@Async` is cheap — but the same runtime makes durable broker work feel heavyweight because Spring's DI container is "the truth", and externalising work to Kafka feels like an admission of defeat. This is why so many Java shops delay adopting Kafka until they hit a scale wall that `@Async` cannot cross.
- **Express / NestJS** runs on Node's single-threaded event loop, where CPU-bound work blocks everything — so BullMQ's pattern of offloading to worker threads or separate processes is not optional, it is the only way to do CPU work without freezing the HTTP path.
- **Django / Flask** inherits CPython's GIL, which makes Celery's prefork pool mandatory for CPU work — the framework's async support (Django 3.1+, Flask 2.0+) is for I/O concurrency, not for CPU work.
- **Laravel** inherits PHP's shared-nothing history, where the queue worker daemon is the only place long-running PHP state exists — which is why Horizon exists as a first-party tool: it is the missing supervisor that PHP-FPM used to be for the request path.
