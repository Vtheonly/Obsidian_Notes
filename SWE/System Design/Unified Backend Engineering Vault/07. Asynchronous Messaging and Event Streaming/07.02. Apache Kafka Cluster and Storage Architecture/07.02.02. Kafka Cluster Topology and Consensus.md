# 07.02.02. Kafka Cluster Topology and Consensus

## What This Is

A Kafka cluster is a set of **brokers** (typically 3 to 7 in production) that jointly hold the partitions of every topic, replicate each partition across a subset of brokers for durability, and elect one broker as the **controller** to coordinate partition leadership and broker membership. The controller is the cluster's brain: it tracks which brokers are alive, decides which broker leads which partition, and pushes leadership-change notifications to brokers and clients. The controller's metadata — the cluster's "this broker exists, this partition lives on these brokers, this broker leads this partition" state — was historically stored in Apache ZooKeeper (a separate distributed coordination service running alongside Kafka), but starting with Kafka 2.8 (preview) and 3.3 (production-ready), Kafka can store its own metadata in a Kafka topic using the **KRaft** (Kafka Raft) consensus protocol, eliminating the ZooKeeper dependency entirely. KRaft became the default for new clusters in Kafka 3.3 (October 2022) and ZooKeeper was removed entirely in Kafka 4.0 (March 2025).

This note covers the cluster-level topology that sits on top of the on-disk storage described in [[07.02.01. The Physical Commit Log on Disk]]. The storage note covered how one broker lays out segments on its local disk; this note covers how multiple brokers cooperate to make those segments durable, available, and consistent in the face of broker failures, network partitions, and rolling restarts. The four sub-concepts — broker/controller/KRaft topology, partition leadership, ISR and `min.insync.replicas`, and unclean leader election — together answer the question "what happens when a broker dies?" The answer determines Kafka's durability guarantees: with `acks=all` and `min.insync.replicas=2` on a replication factor 3 topic, the cluster can lose one broker without losing data; with `unclean.leader.election.enable=true`, the cluster can lose all ISR brokers and still serve reads (at the cost of acknowledged-but-lost data).

The layered mental model is in full force here. KRaft is an implementation of the Raft consensus algorithm from Section 08 (distributed systems) — the same algorithm that powers etcd, Consul, and CockroachDB. The partition replication protocol is the same leader-follower pattern as MySQL semisync replication, Postgres physical replication, and MongoDB replica sets — the leader accepts writes, the followers fetch the writes from the leader's log, and the leader tracks how far each follower has caught up. The high-watermark mechanism is the same as the "committed offset" in a database WAL: data is only visible to readers after it has been replicated to a quorum. The contribution of this note is to show how Kafka combines these primitives into a single coherent system that handles tens of thousands of partitions across a small broker fleet without a per-partition consensus round-trip.

## The Details

### Brokers, Controller Nodes, and Metadata Management via KRaft (Kafka Raft Metadata Mode)

A Kafka broker is a single JVM process that owns some subset of the cluster's partitions (as leader or follower) and serves produce and fetch requests for those partitions. Brokers are identified by an integer `broker.id` (set in `server.properties` or auto-assigned by KRaft via `node.id`), and they communicate with each other and with clients over TCP (default port 9092 for plaintext, 9093 for SSL, 9094 for SASL). A production cluster typically runs 3 brokers for small workloads, 5–7 for medium, and 12+ for high-throughput deployments — the broker count is determined by storage capacity and partition fan-out, not by CPU or RAM (each broker can handle 4,000+ partitions and 1 Gbps+ of produce throughput on its own). The `broker.rack` config identifies the broker's failure domain (an AZ, a rack, a power circuit) and Kafka uses it to spread partition replicas across racks so that a single rack failure does not take down a partition's entire replica set.

The **controller** is one broker in the cluster that has additional responsibilities: it tracks broker membership (which brokers are alive, via heartbeat timeouts), it assigns partition leadership (when a broker dies, the controller picks a new leader from the surviving ISR), and it pushes metadata updates to all brokers (which brokers own which partitions). In a ZooKeeper-based cluster (pre-3.3), the controller is elected via a ZooKeeper ephemeral node — the first broker to create `/controller` becomes the controller, and if it dies the ephemeral node disappears and another broker races to claim it. In a KRaft cluster, the controller is elected via the Raft consensus algorithm over a special internal topic `__cluster_metadata` — a quorum of "controller nodes" (brokers configured with `process.roles=broker,controller` or `process.roles=controller`) runs Raft to elect a leader, and that leader is the active controller.

```text
   KRaft CLUSTER TOPOLOGY (3 brokers, all combined broker+controller nodes)
   ───────────────────────────────────────────────────────────────────────

   broker-1 (node.id=1)        broker-2 (node.id=2)        broker-3 (node.id=3)
   process.roles=broker,controller   process.roles=broker,controller   process.roles=broker,controller
   controller.quorum=1@b1:9093,2@b2:9093,3@b3:9093 (Raft quorum config)
   ┌────────────────────┐     ┌────────────────────┐     ┌────────────────────┐
   │  Raft follower     │     │  Raft LEADER       │     │  Raft follower     │
   │  (controller       │     │  (active           │     │  (controller       │
   │   standby)         │     │   controller)      │     │   standby)         │
   ├────────────────────┤     ├────────────────────┤     ├────────────────────┤
   │  Broker (active)   │     │  Broker (active)   │     │  Broker (active)   │
   │  Leads partitions: │     │  Leads partitions: │     │  Leads partitions: │
   │   orders-0         │     │   orders-1         │     │   orders-2         │
   │   orders-2 (follower)  │  │   orders-0 (follower) │  │   orders-1 (follower) │

   └────────────────────┘     └────────────────────┘     └────────────────────┘

   ──> The Raft leader (broker-2) is the active controller.
   ──> All 3 brokers serve produce/fetch requests for the partitions they lead or follow.
   ──> If broker-2 dies, Raft elects broker-1 or broker-3 as the new controller (~1-2 seconds).
   ──> The __cluster_metadata topic (single partition, RF=3) stores ALL cluster state:
        broker registrations, partition assignments, ISR sets, leadership assignments.
```

KRaft replaced ZooKeeper for three reasons. First, ZooKeeper was an additional distributed system to operate — every Kafka SRE had to also be a ZooKeeper SRE, with its own JVM tuning, snapshot management, and quorum-loss recovery procedure. Second, ZooKeeper had a hard scalability limit of around 200,000 partitions per cluster because every metadata change required a ZooKeeper write (which goes through ZooKeeper's own ZAB consensus across the 3-5 ZK nodes), and the controller's metadata-push fan-out to all brokers became a bottleneck. Third, ZooKeeper's metadata model was a tree of znodes that the controller had to keep in sync with the brokers' in-memory cache — a class of subtle bugs known as "controller failover inconsistency" where a new controller would inherit a slightly-stale view of cluster state and make wrong decisions. KRaft stores metadata in a single-partition compacted Kafka topic, which means metadata updates are subject to the same replication, durability, and log-replay semantics as application data — the controller is just a special consumer and producer of `__cluster_metadata`.

```bash
# KRaft broker config (server.properties or KRaft format)

  --config /etc/kafka/server.properties \
  --cluster-id $(kafka-storage.sh random-uuid)
#  Formatting metadata directory /var/lib/kafka/data with cluster-id MkU3OEVBNTcwNTJENDl6Nw

kafka-metadata-quorum.sh --bootstrap-server broker-1:9092 describe --status
#  ClusterId:              MkU3OEVBNTcwNTJENDl6Nw

#  LeaderEpoch:            17
#  HighWatermark:          1234
#  MaxFollowerLag:         1
#  MaxFollowerLagTimeMs:   2
#  CurrentVoters:          [1,2,3]
#  CurrentObservers:       []           ← broker-only nodes would appear here in mixed clusters

# List brokers (note: this is now metadata fetched from the KRaft quorum, not ZooKeeper)
kafka-broker-api-versions.sh --bootstrap-server broker-1:9092 | head
```

The production failure mode of KRaft is **quorum loss** — if 2 of 3 controller nodes die simultaneously, the cluster loses the ability to elect a controller, and no metadata changes (no new topics, no partition reassignments, no broker decommissions) can happen until at least 2 of the 3 are back. The cluster can still serve produce and fetch requests for existing partitions because the brokers' in-memory metadata cache is still valid, but any operation that requires controller approval (creating a topic, triggering a partition rebalance, recovering from a broker failure) is blocked. The fix is to size the controller quorum for the desired fault tolerance: 3 controller nodes tolerate 1 failure (recommended minimum), 5 tolerate 2 failures (recommended for production), 7 tolerate 3 failures (overkill for most deployments). The other failure mode is **`__cluster_metadata` log corruption** — because KRaft stores all metadata in a Kafka topic, a bug that corrupts that topic (e.g., a disk failure that truncates the active segment) can leave the cluster unable to elect a controller. The diagnostic is `kafka-metadata-quorum.sh describe --status` returning `LeaderId: -1` (no leader), and the recovery procedure is documented in KIP-833 (manual metadata snapshot recovery) — not for the faint of heart. See [[08. Distributed Systems Architecture and Big Data Compute/08.02.03. Consensus Algorithms (Paxos, Raft, and Paxos Variants)]] for the Raft algorithm's internals that KRaft implements.

### Partition Leadership: Leader Partitions (handling all reads/writes) vs. Follower Partitions (repl...

Every partition in a Kafka topic has exactly one **leader** broker and zero or more **follower** brokers. The leader is the broker that all clients talk to: producers send `Produce` requests only to the leader, consumers send `Fetch` requests only to the leader (with the rare exception of follower-fetching for read-scaling, which is not the default). The followers' job is purely to maintain a copy of the partition's log by fetching records from the leader in the same way a consumer does — the only difference is that followers fetch with a special "follower" flag set in the fetch request, which the leader uses to track the follower's replication progress for ISR purposes. This architecture is the same as MySQL primary-replica replication and MongoDB replica sets: one node accepts writes, the others tail the write log.

The leadership assignment is the controller's most important job. When a topic is created (via `kafka-topics.sh --create`), the controller picks brokers for each partition's replicas using a rack-aware round-robin algorithm: for a topic with `replication.factor=3` on a 3-broker cluster with `broker.rack=us-east-1a/b/c`, partition 0 might be assigned replicas `[1,2,3]` (leader=1, followers=2,3), partition 1 assigned `[2,3,1]` (leader=2, followers=3,1), and so on, ensuring that the leader of each partition is on a different broker and the replicas are spread across all three racks. When a broker dies, the controller (after detecting the death via missed heartbeats — `broker.session.timeout.ms` default 10 seconds in KRaft) selects a new leader from the surviving replicas in the ISR, updates the `__cluster_metadata` topic, and pushes the change to all brokers via a `LeaderAndIsr` request. Clients discover the change when they next try to send a request to the dead leader and get a `NOT_LEADER_OR_FOLLOWER` error, at which point they refresh their metadata (via a `Metadata` request to any broker) and retry against the new leader.

```text
   PARTITION LEADERSHIP & REPLICATION (topic "orders", 3 partitions, RF=3, 3 brokers)
   ─────────────────────────────────────────────────────────────────────────────────

   broker-1 (rack us-east-1a)    broker-2 (rack us-east-1b)    broker-3 (rack us-east-1c)
   ┌──────────────────────┐     ┌──────────────────────┐     ┌──────────────────────┐
   │ orders-0 LEADER      │     │ orders-0 follower     │     │ orders-0 follower     │
   │   accepts produces   │◀────│   fetches from b-1    │◀────│   fetches from b-1    │
   │   accepts fetches    │     │                       │     │                       │
   ├──────────────────────┤     ├──────────────────────┤     ├──────────────────────┤
   │ orders-1 follower     │     │ orders-1 LEADER      │     │ orders-1 follower     │
   │   fetches from b-2    │────▶│   accepts produces   │────▶│   fetches from b-2    │
   │                       │     │   accepts fetches    │     │                       │
   ├──────────────────────┤     ├──────────────────────┤     ├──────────────────────┤
   │ orders-2 follower     │     │ orders-2 follower     │     │ orders-2 LEADER      │
   │   fetches from b-3    │────▶│   fetches from b-3    │────▶│   accepts produces   │
   │                       │     │                       │     │   accepts fetches    │
   └──────────────────────┘     └──────────────────────┘     └──────────────────────┘

   ──> Each partition has exactly 1 leader, 2 followers.
   ──> Producers/consumers for orders-0 talk only to broker-1, etc.
   ──> Followers fetch from the leader using the same Fetch API as consumers (with a flag).

   If broker-1 dies:
     - Controller detects missed heartbeat after ~10s (broker.session.timeout.ms).
     - Controller picks a new leader for orders-0 from the ISR (say, broker-2).
     - Controller updates __cluster_metadata and pushes LeaderAndIsr to brokers 2 and 3.
     - Clients hitting broker-1 get connection refused → refresh metadata → retry to broker-2.
     - Recovery time: 10s (heartbeat timeout) + 1s (controller decision) + 1s (client metadata refresh)
                    = ~12 seconds of produce failures for orders-0 (producers retry → messages buffered).
```

The leader-follower replication protocol is **fetch-based**, not **push-based**. The leader does not proactively send records to followers — followers pull records by issuing `Fetch` requests to the leader at a configurable interval (`replica.fetch.wait.max.ms` default 500 ms, `replica.fetch.min.bytes` default 1 byte). This pull model is the same one consumers use, and it has the same property: a slow follower does not backpressure the leader, it just falls behind. The leader tracks each follower's fetch offset in its in-memory `LeaderEpoch` cache, and a follower is considered "in-sync" (in the ISR) if its fetch offset is within `replica.lag.time.max.ms` (default 30 seconds) of the leader's high-watermark. The high-watermark itself is the leader's estimate of "the offset up to which all ISR members have replicated" — consumers only see messages up to the high-watermark, so a message appended to the leader but not yet replicated to any follower is invisible to consumers until replication catches up.

```bash

#  Topic: orders   Partition: 1   Leader: 2   Replicas: 2,3,1   Isr: 2,3,1
#  Topic: orders   Partition: 2   Leader: 3   Replicas: 3,1,2   Isr: 3,1,2
#        ↑                       ↑               ↑                ↑
#        topic name              current leader  all replicas     in-sync replicas (subset of Replicas)

# Inspect the replica's fetch lag (how far behind each follower is)

# JMX metric: kafka.server:type=FetcherLagMetrics,name=ConsumerLag,clientId=ReplicaFetcherBrokerId-2,topic=orders,partition=0
```

The production failure mode of partition leadership is the **leadership-flap storm under network partition**. If brokers 1 and 2 lose their network link (but both can still talk to broker 3), broker 1 might think broker 2 is dead and trigger a leadership change for partitions broker 2 was leading; meanwhile broker 2 thinks broker 1 is dead and does the same. The controller (say, broker 3) receives conflicting reports and may oscillate leadership assignments, causing clients to repeatedly refresh metadata and fail to make progress. The fix is the `controller.quorum.fetch.timeout.ms` (default 2000 ms in KRaft) — set it high enough that genuine network hiccups do not trigger false deaths, but low enough that real broker failures are detected quickly. The other failure mode is **partition skew** — if a 6-broker cluster has a topic with 12 partitions and RF=3, but 8 of the 12 partitions happen to have their leader on broker 1, broker 1 handles 2/3 of the cluster's produce traffic and becomes a hot spot while the other 5 brokers sit idle. The fix is to run `kafka-reassign-partitions.sh` to spread leadership more evenly, and to use `kafka-preferred-replica-election.sh` to periodically restore each partition's preferred leader (the first replica in the Replicas list).

### In-Sync Replicas (ISR) and Minimum In-Sync Replicas (`min.insync.replicas`)

The **ISR** (In-Sync Replicas) is the dynamically-tracked set of replicas that are caught up with the leader within `replica.lag.time.max.ms` (default 30 seconds). The ISR is a subset of the partition's full replica list (`Replicas`) — a partition with `Replicas: 1,2,3` might have `Isr: 1,2` if broker 3 has fallen behind. The leader maintains the ISR set and updates it whenever a follower catches up (added to ISR) or falls behind (removed from ISR). Each ISR change is recorded in the `__cluster_metadata` topic so that the controller and all brokers have a consistent view. The ISR is the foundation of Kafka's durability guarantee: a message is considered "committed" only when it has been replicated to all ISR members, and only committed messages are visible to consumers (via the high-watermark).

The **`min.insync.replicas`** config (default 1, set per-topic via `kafka-configs.sh`) is the floor below which the broker refuses produces when `acks=all`. With `min.insync.replicas=2` and `replication.factor=3`, the broker accepts a produce only if at least 2 of the 3 replicas are in the ISR — so if one broker dies, the ISR drops to 2, but produces still succeed (2 ≥ 2); if a second broker dies, the ISR drops to 1, and produces fail with `NOT_ENOUGH_REPLICAS`. This is the single most important durability knob in Kafka: the combination of `acks=all` + `min.insync.replicas=2` + `replication.factor=3` gives you "tolerate one broker failure without data loss and without downtime"; reducing any of those values trades durability for availability.

| Config combination | Failure tolerance | Tradeoff |
|---|---|---|
| `acks=1`, `min.insync.replicas=1`, `RF=3` | Lose 0 brokers → no data loss; lose leader → recent messages lost | Maximum throughput, minimum durability (fire-and-forget-ish) |
| `acks=all`, `min.insync.replicas=1`, `RF=3` | Lose 1 broker → no data loss; lose 2 → recent messages lost | Good throughput, weak durability (a single slow follower can be the only sync replica) |
| `acks=all`, `min.insync.replicas=2`, `RF=3` | Lose 1 broker → no data loss, no downtime; lose 2 → produces fail (recent messages safe on surviving broker) | **Production standard** — best balance of durability and availability |
| `acks=all`, `min.insync.replicas=3`, `RF=3` | Lose 0 brokers → fine; lose 1 → produces fail | Maximum durability, zero failure tolerance (defeats the purpose of RF=3) |
| `acks=all`, `min.insync.replicas=2`, `RF=5` | Lose 2 brokers → no data loss, no downtime; lose 3 → produces fail | High durability, more storage cost (5 copies of every byte) |

The interaction between `acks`, `min.insync.replicas`, and the ISR is subtle. The `acks=all` producer setting means "wait for all ISR members to ack, not all RF members" — so if ISR has shrunk to 1 (because two followers fell behind), `acks=all` only requires that one broker ack, which is a weaker guarantee than the name suggests. The `min.insync.replicas` config closes this loophole by refusing produces when the ISR is too small, even though `acks=all` would technically allow them. The combination is the only way to get the "tolerate one failure without data loss" guarantee: `acks=all` makes the producer wait for replication, `min.insync.replicas=2` makes the broker refuse produces if replication is degraded, `RF=3` ensures that one broker failure still leaves 2 ISR members.

```bash
# Set min.insync.replicas on a topic (default is 1 — set to 2 for production durability)
kafka-configs.sh --bootstrap-server broker-1:9092 \
  --entity-type topics --entity-name orders --alter \
  --add-config min.insync.replicas=2

# Verify the config
kafka-configs.sh --bootstrap-server broker-1:9092 \
  --entity-type topics --entity-name orders --describe
#  Dynamic configs for topic orders are:
#    min.insync.replicas=2

# Producer config (Java) — acks=all is required for min.insync.replicas to be enforced
Properties props = new Properties();
props.put("bootstrap.servers", "broker-1:9092,broker-2:9092,broker-3:9092");
props.put("acks", "all");                          // wait for all ISR
props.put("enable.idempotence", "true");           // dedupes retries (Kafka 0.11+)
props.put("max.in.flight.requests.per.connection", "5");
props.put("retries", "2147483647");                // effectively infinite retries
props.put("delivery.timeout.ms", "120000");        // give up after 2 minutes
props.put("request.timeout.ms", "30000");          // per-request timeout

# Inspect the ISR shrink/grow events in the broker log
journalctl -u kafka -g "ISR" | tail
#  broker-1: [2024-05-30 10:23:14] INFO [Partition orders-0 broker=1] Shrinking ISR from 1,2,3 to 1,2 (broker 3 lagged)
#  broker-1: [2024-05-30 10:23:45] INFO [Partition orders-0 broker=1] Expanding ISR from 1,2 to 1,2,3 (broker 3 caught up)
```

The production failure mode of ISR mechanics is the **ISR thrash under sustained network jitter**. If a follower repeatedly falls behind (dropped from ISR) and catches up (added back to ISR) every few minutes, every transition is a metadata write to `__cluster_metadata`, which the controller must replicate to all brokers — at scale (thousands of partitions), this thrash can saturate the controller's metadata-update pipeline and cause all brokers to see stale ISR states, leading to spurious `NOT_ENOUGH_REPLICAS` errors even when replication is healthy. The fix is to raise `replica.lag.time.max.ms` from the default 30 seconds to 60–120 seconds for workloads with bursty produce patterns, so transient follower lag does not trigger ISR shrink. The other failure mode is the **`min.insync.replicas=2` availability cliff** — if 2 of 3 brokers in a partition's replica set are down, produces fail with `NOT_ENOUGH_REPLICAS` and the producer's retry loop will exhaust `delivery.timeout.ms` (default 2 minutes) before giving up. The application must handle this by either (a) failing the user-facing request (correct for order placement, wrong for analytics), or (b) falling back to a local spool (Kafka itself, a different topic, a Redis list, a database outbox table) and replaying when the brokers recover. See [[07.05.02. The Transactional Outbox Pattern]] for the spool pattern.

### Unclean Leader Election risks and High Watermark mechanics

**Unclean leader election** is the controversial Kafka behavior of electing a follower that is *not* in the ISR as the new partition leader when all ISR members are unavailable. The setting `unclean.leader.election.enable=true` (default `true` in Kafka < 2.0, default `false` in Kafka ≥ 2.0) trades durability for availability: if true, when all ISR members die, the broker picks the most-caught-up non-ISR follower (which may be missing the last few messages that were committed before the ISR died) and makes it the leader, accepting that those last few messages are now lost; if false, the partition goes offline until an ISR member comes back, preserving all acknowledged messages but sacrificing availability. The decision is one of the most consequential in Kafka operations, and the default flipped in Kafka 2.0 (KIP-226) because the operational team decided that silent data loss was worse than temporary unavailability for the vast majority of use cases.

The **high watermark** is the leader's notion of "the offset up to which all ISR members have acknowledged replication" — only messages with offset ≤ high-watermark are visible to consumers. The leader advances the high-watermark by computing `min(fetch_offset of each ISR follower)` after every fetch response from a follower; when the high-watermark advances, the leader piggybacks the new value on the next fetch response to each follower, and followers advance their own high-watermark to match (followers do not advance their high-watermark beyond what the leader has told them is safe). This two-phase propagation is what guarantees that consumers never see a message that has not been replicated to all ISR — even if a consumer reads from a follower (which it doesn't by default, but the high-watermark contract still holds), the follower will only serve messages up to its leader-informed high-watermark.

```text
   HIGH-WATERMARK PROPAGATION (leader L, followers F1, F2; ISR = {L, F1, F2})
   ──────────────────────────────────────────────────────────────────────────

   t=0:   LEO(L)=100  LEO(F1)=95  LEO(F2)=92   HW(L)=92  HW(F1)=90  HW(F2)=88
          (HW(L) = min(LEO(L), LEO(F1), LEO(F2)) = 92, but HW is propagated lazily)

   t=1:   F2 sends Fetch(offset=92) to L
          L responds with messages 92..100 AND HW=92 (the leader's current HW)
          F2 advances LEO(F2) to 100, advances HW(F2) to 92 (the leader-informed value)

   t=2:   F1 sends Fetch(offset=95) to L
          L responds with messages 95..100 AND HW=95 (leader advanced HW to min(100,100,92)=95... no wait)
          ──> Actually: HW(L) advances in two phases:
              (a) L updates its HW = min(LEO(L), LEO(F1), LEO(F2)) after each fetch from a follower
              (b) L sends the new HW to each follower in the NEXT fetch response
              So F2's fetch at t=1 received HW=92, F1's fetch at t=2 receives HW=95 (the new value),
              F2 will learn about HW=95 on its NEXT fetch (t=3).

   t=3:   F2 sends Fetch(offset=100) to L
          L responds with no new messages (LEO(L)=100 still) AND HW=95
          F2 advances HW(F2) to 95.

   ──> Consumer reading from L sees messages only up to HW=95, even though LEO(L)=100.
       Messages 96..100 are appended to L's log but not yet committed (not all ISR have acked).
       If L crashes before any follower fetches 96..100, those messages are lost (they were
       never committed, so no consumer saw them — no inconsistency, just data loss for the producer).

   UNCLEAN LEADER ELECTION SCENARIO (ISR = {L, F1}; F2 was dropped from ISR for lagging):
   t=10:  L crashes. F1 crashes. Only F2 is alive.
          F2's LEO = 92 (it was behind). Last HW was 92.
          ──> If unclean.leader.election.enable=true:
              Controller makes F2 the leader. F2's log starts at offset 0..92.
              Messages 93..100 (which were on L and F1 but never reached F2) are LOST.
              Producer continues to publish to F2 as new leader; new messages get offsets 93+.
              Consumers see offsets 93+ as if nothing happened — but offsets 93..100 from the
              old leader are silently gone.
          ──> If unclean.leader.election.enable=false:
              Partition goes OFFLINE. No leader. Producers get NOT_LEADER_OR_FOLLOWER.
              Consumers get NOT_LEADER_OR_FOLLOWER. Partition stays offline until L or F1
              comes back. No data loss, but availability is sacrificed.
```

The trade-off is between **availability** and **durability** in the rare case where all ISR members fail simultaneously. With `unclean.leader.election.enable=false` (the modern default), a partition with RF=3 and `min.insync.replicas=2` can lose 2 brokers without losing data — the partition is offline until a third broker comes back, but no acknowledged message is lost. With `unclean.leader.election.enable=true`, the same partition can lose 2 brokers and stay online by electing the lagging third — but the last few acknowledged messages (between the high-watermark and the lagging follower's LEO) are silently lost, and the producer is not notified. The lost messages were `acks=all` acknowledged to the producer, so the producer considers them durable — the data loss is invisible to the application until a downstream consumer notices a gap.

```bash
# Check the cluster's unclean leader election setting (broker-level default)
kafka-configs.sh --bootstrap-server broker-1:9092 \
  --entity-type brokers --entity-default --describe | grep unclean
#  Default configs for brokers in the cluster are:
#    unclean.leader.election.enable=false      ← modern default (Kafka 2.0+)

# Override per-topic (e.g., enable for an analytics topic where availability > durability)
kafka-configs.sh --bootstrap-server broker-1:9092 \
  --entity-type topics --entity-name clickstream-analytics --alter \
  --add-config unclean.leader.election.enable=true

# Inspect leader-epoch history (debugging tool for understanding past leadership changes)
kafka-leader-election.sh --bootstrap-server broker-1:9092 \
  --election-type clean --topic orders --partition 0
#  This triggers a clean leader election (preferred replica if in ISR).

# Monitor high-watermark in real time via JMX
#   kafka.log:type=Log,name=LogEndOffset,topic=orders,partition=0   (LEO — leader's local append position)
#   kafka.log:type=Log,name=LogStartOffset,topic=orders,partition=0 (oldest retained offset)
#   kafka.server:type=ReplicaManager,name=UnderReplicatedPartitions (count of partitions with ISR < Replicas)
#   kafka.server:type=ReplicaManager,name=UnderMinIsrPartitionCount (count of partitions with ISR < min.insync.replicas)
```

The production failure mode of unclean leader election is the **silent acknowledged-data-loss incident**. The classic scenario: a 3-broker cluster has `unclean.leader.election.enable=true` (legacy default, not changed during an upgrade), broker 1 (leader of `orders-0`) and broker 2 (the only ISR follower) both experience simultaneous disk failures — within seconds of each other, before the controller can react. Broker 3, the lagging follower not in ISR, becomes the leader. The producer continues publishing; messages 1234-1240 (which were on brokers 1 and 2 but not on broker 3) are silently gone. The application's order-placement flow continues to work, customers see "order confirmed" emails, but the orders 1234-1240 are not in the downstream database and never will be. The diagnostic is comparing the producer's `RecordMetadata.offset()` returned for the affected messages against the offsets that actually exist on the new leader's log — a gap means data was lost. The prevention is `unclean.leader.election.enable=false` in production, full stop. The other failure mode is the **high-watermark stall under partition leadership change**: when a new leader takes over, it must wait for at least one follower to fetch from it (advancing the new follower's LEO past the old HW) before it can advance the HW — until then, consumers see no new messages even though the leader has them in its log. This is a 1-2 second stall on every leadership change and is the reason rolling restarts cause brief consumer-side latency spikes. See [[07.03.02. Offset Management and Commit Strategies]] for how consumer offset commits interact with the high-watermark, and [[08.03.01. Distributed Consensus and Leader Election (Paxos, Raft)]] for the consensus-theory foundation that KRaft's leader election builds on.
