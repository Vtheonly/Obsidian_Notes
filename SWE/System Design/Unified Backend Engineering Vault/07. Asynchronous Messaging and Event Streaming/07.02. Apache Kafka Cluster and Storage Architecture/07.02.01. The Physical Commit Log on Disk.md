# 07.02.01. The Physical Commit Log on Disk

## What This Is

Kafka's storage layer is the cleanest production example of an **append-only commit log** in wide deployment. Unlike a traditional message queue that stores each message in an in-memory structure and spills to disk only when RAM is exhausted, Kafka writes every message to a regular file on a regular filesystem, in the order it arrives, and never modifies a byte after it has been written. The result is a storage engine that exploits three OS-level primitives to the hilt: sequential disk writes (which are 100× faster than random writes on spinning disks and still 5–10× faster on SSDs, because sequential I/O avoids the write-amplification penalty of flash translation layers), the Linux page cache (which holds the recently-written and recently-read file data in RAM so that subsequent reads do not touch disk at all), and the `sendfile` syscall (which copies data from the page cache directly to a network socket's buffer via DMA, bypassing user space entirely). The combination lets a single Kafka broker saturate a 10 Gbps network link at 20% CPU — a feat that no in-memory queue can match because the in-memory queue has to copy bytes from broker RAM to client RAM through user space.

This note is the on-disk counterpart to [[06.01.02. Write-Ahead Logging (WAL) and Crash Recovery]] — Kafka's commit log is, mechanically, exactly the same kind of file as a database's WAL: an append-only sequence of records, with each record carrying its position in the log as its identity. The differences are operational: a database WAL is truncated after the corresponding data pages are flushed to disk (so the WAL stays small), while a Kafka log is retained for days or weeks (so the log grows to terabytes). A database WAL records internal page mutations that are meaningless outside the database; a Kafka log records application-level events that any consumer can read directly. This note covers the on-disk layout — topics, partitions, segments, index files, the rolling policy, retention, and compaction. The cluster-level replication of those files across brokers is covered in [[07.02.02. Kafka Cluster Topology and Consensus]], and the producer-side batching that fills those files is covered in [[07.02.03. Kafka Producer Architecture]].

## The Details

### Topics, Partitions, and physical segment files (`.log`, `.index`, `.timeindex`)

A Kafka topic is a logical name for a stream of records; the physical unit of storage is the **partition**, and within each partition Kafka writes records to a sequence of **segment files** on disk. A topic with 12 partitions on a broker manifests as 12 directories under the broker's `log.dirs` (default `/tmp/kafka-logs` in dev, `/var/lib/kafka/data` in production): `orders-0/`, `orders-1/`, ..., `orders-11/`. Each partition directory contains, at any moment, one **active segment** (the segment currently being appended to) and zero or more **rolled segments** (segments that were closed because they hit the rolling threshold and are now eligible for retention-based deletion or compaction).

Each segment is a triple of files with a common base offset as the filename prefix. The base offset is the offset of the first message in the segment, zero-padded to 20 digits — so a segment that starts at message offset 0 is named `00000000000000000000.log`, the next segment that starts at offset 1234 is named `00000000000000001234.log`, and so on. The three files are: the `.log` file (the actual record batch data — variable-length binary records with CRC, timestamp, key, value), the `.index` file (a sparse index from relative offset → physical byte position within the `.log` file, written one entry per `index.interval.bytes` of `.log` data, default 4 KB), and the `.timeindex` file (a sparse index from timestamp → offset, used to satisfy `consumer.seek-by-timestamp` requests). The `.index` and `.timeindex` are sparse — they don't index every message, only every Nth one — because the binary search across the index plus a linear scan within the indexed range is fast enough (a 1 GB segment with 4 KB index interval has 250k index entries, each 8 bytes = 2 MB of index for 1 GB of data).

```text
   ON-DISK LAYOUT: topic "orders" with 3 partitions on one broker
   ─────────────────────────────────────────────────────────────────

   /var/lib/kafka/data/
   ├── orders-0/
   │   ├── 00000000000000000000.index          (rolled: base offset 0)
   │   ├── 00000000000000000000.log            1.0 GB  ← segment hit segment.bytes, rolled
   │   ├── 00000000000000000000.timeindex
   │   ├── 00000000000000123456.index          (rolled: base offset 123456)
   │   ├── 00000000000000123456.log            1.0 GB  ← segment hit segment.bytes, rolled
   │   ├── 00000000000000123456.timeindex
   │   ├── 00000000000000250000.index          (ACTIVE: base offset 250000, still appending)

   │   └── 00000000000000250000.timeindex

   └── orders-2/

   INDEX FILE FORMAT (.index, 8 bytes per entry):
   ┌─────────────────────────────────────────────────────┐
   │ relative_offset (4 bytes, int32) │ position (4 bytes)│
   ├─────────────────────────────────────────────────────┤
   │ 0                                │ 0                │  ← entry for offset 250000
   │ 100                              │ 4096             │  ← entry for offset 250100, at byte 4096
   │ 200                              │ 8192             │  ← entry for offset 250200, at byte 8192
   │ ...                                                 │
   └─────────────────────────────────────────────────────┘
```

The offset itself is the consumer's primary handle into the log. An offset is a 64-bit integer that monotonically increases within a partition — every record appended to a partition gets the next offset in sequence, and the broker guarantees that there are no gaps (a record at offset 250000 is immediately followed by a record at offset 250001, never by 250005). The offset is not stored in the record itself as a field that the producer chooses; it is assigned by the broker at append time, returned in the produce response, and stored in the record batch header. When a consumer asks for "messages starting at offset 250100", the broker does a binary search across the segment's `.index` file to find the largest indexed offset ≤ 250100, seeks to that byte position in the `.log` file, and linearly scans forward until it finds offset 250100 (or returns "not found" if the offset is beyond the active segment's last written offset). The segment + index + log triple is therefore the on-disk equivalent of a B+Tree's page + leaf-pointer + record layout — a sparse index over a sorted contiguous file.

The production failure mode of the segment layout is **small-segment syndrome from mis-tuned `segment.ms`**. If `segment.ms` is set very low (e.g., 60 seconds on a low-volume topic that receives 10 messages per second), the broker rolls a new segment every minute, each segment holds only ~600 messages, and within a week you have 10,000 segment files per partition. The broker's `LogFlusher` thread must open and fsync each segment on every checkpoint (controlled by `log.flush.interval.checkpoint`, default 60 seconds), the OS file descriptor table fills up, and broker startup time balloons because the broker must enumerate and mmap every segment file at boot. The fix is to size `segment.ms` so that each segment holds at least 100 MB of data at typical traffic — for a topic receiving 1 MB/sec, `segment.ms=600000` (10 minutes) gives 600 MB segments, which is reasonable. The other failure mode is **too-few partitions bottlenecking throughput** — a topic with 1 partition caps consumer parallelism at 1, and a single broker's disk can only write ~100 MB/sec sequential, so a 200 MB/sec producer will fall behind. See [[07.03.01. Consumer Groups and Partition Balancing]] for the consumer-side implications.

### Sequential disk appends and exploiting the Linux OS Page Cache

Kafka's storage performance is dominated by one architectural choice: every write is a **sequential append**, and every read is a **sequential scan**. There are no random writes — no in-place updates, no B+Tree page splits, no LSM compaction rewriting the same keys. There are no random reads — a consumer reads from offset X forward, and the broker's read-ahead prefetcher turns the sequential scan into a streaming operation that the disk can serve at full sequential bandwidth. The result is that Kafka's disk I/O is the *cheapest* kind the hardware can offer: sequential writes at ~100–200 MB/sec on a single SATA SSD, ~500 MB/sec on an NVMe SSD, ~1–2 GB/sec on a high-end NVMe RAID. Compare this to a B+Tree random-update pattern (e.g., a Postgres `UPDATE` on an indexed table) which runs at 5,000–50,000 updates/sec per spindle because each update requires a random read (the page) + a random write (the modified page) + a sequential write (the WAL).

The Linux page cache is the other half of the performance story. Every byte Kafka writes to a `.log` file goes through the kernel's `write()` syscall, which does **not** perform a disk I/O — it copies the data into the page cache (marking the page dirty) and returns immediately. The kernel's `pdflush`/`writeback` thread later writes the dirty pages to disk asynchronously, in the background, in large sequential chunks that the disk can serve efficiently. The `fsync()` syscall forces a synchronous flush, but Kafka calls `fsync()` only on a configurable schedule (`log.flush.interval.messages` default `Long.MaxValue` = never force, `log.flush.interval.ms` default `null` = never force, `log.flush.interval.checkpoint` default 60 seconds = periodic checkpoint) — instead, Kafka relies on the kernel's normal writeback to durably persist data, and uses **replication to other brokers** as the durability mechanism rather than `fsync()`. This is the same insight that makes LevelDB/RocksDB fast: don't pay the `fsync()` cost per write, accept that one broker might lose a few seconds of data on power loss, and replicate to multiple brokers so that the loss of any single broker is recoverable from the others.

```text
   WRITE PATH: producer → broker → page cache → disk (async)
   ──────────────────────────────────────────────────────────

   producer ──produce──> broker JVM heap
                          │
                          ▼
                    RecordAccumulator (in-memory batch)
                          │
                          ▼  (Sender thread, when batch full or linger.ms hits)
                    java.nio.FileChannel.write(recordBatch)
                          │
                          ▼  (write() syscall — copies to page cache, returns immediately)
                    PAGE CACHE  (in RAM, dirty pages)
                          │
                          ▼  (kernel writeback, every ~30s by default, or fsync())
                    DISK (sequential write to .log file's active segment)

   READ PATH: consumer → broker → page cache (HIT) → socket  (NO disk I/O if cached!)
   ──────────────────────────────────────────────────────────

   consumer ──fetch(offset=250100)──> broker
                                       │
                                       ▼
                                  binary search .index
                                       │
                                       ▼  (position 4096 in .log file)
                                  FileChannel.read(position=4096, length=1024)
                                       │
                                       ▼  (read() syscall)
                                  PAGE CACHE  ── if recently written or recently read: HIT
                                       │            (zero disk I/O — page is in RAM)
                                       ▼
                                  sendfile(socket_fd, file_fd, position, count)
                                       │
                                       ▼  (DMA transfer page cache → socket buffer)
                                  consumer's TCP receive buffer

   ──> In steady state (producer and consumer running concurrently), the consumer's reads
       almost always hit the page cache because the producer just wrote the data there.
       Disk I/O happens only for: (a) cold reads from rolled segments beyond page cache,
       (b) kernel writeback of dirty pages, (c) fsync() calls on checkpoint.
```

The page cache is sized by the kernel as a fraction of total RAM, and Kafka's design assumes that the broker can use almost all of available RAM as page cache. The rule of thumb is that a Kafka broker should have at least enough RAM to hold the *working set* of recently-written data — for a broker receiving 100 MB/sec with a 30-second writeback window, that's 3 GB of dirty pages; for a broker serving a consumer that is 1 hour behind on a 100 MB/sec topic, that's 360 GB of page cache required to avoid disk reads on the catch-up. This is why Kafka brokers in production are typically configured with 64–256 GB of RAM: not because the JVM needs it (the JVM heap is usually 6–12 GB), but because the OS page cache needs to absorb the working set. The other implication is that **Kafka must be the only major I/O workload on the box** — co-locating Kafka with a database or a heavy log emitter means the two workloads fight for page cache and one will be evicted to disk.

```bash
# Inspect page cache usage of Kafka's log files (linux-fincore or vmtouch)

#  Files: 1
#  Directories: 0
#  Resident pages: 45056/115200  (44%)
#  Elapsed: 0.012 seconds

# Kafka broker tuning: disable OS swap (swap kills Kafka latency)

# Kafka JVM tuning: -Xms6g -Xmx6g  (fixed heap to avoid resize pauses)
# Leave the remaining 58 GB of a 64 GB box for the OS page cache.
```

The production failure mode of sequential-append/page-cache tuning is the **dirty-page writeback stall**. When the producer writes faster than the disk can flush, dirty pages accumulate; when they exceed `vm.dirty_ratio` (default 20% of RAM), the kernel switches *every* `write()` call to synchronous mode until dirty pages drain below the threshold — this manifests as `produce` latency spiking from 1 ms to 100 ms+ for a 10-second window while the disk catches up. The fix is either (a) reduce `vm.dirty_ratio` to 5–10% so the stall happens earlier and is shorter, (b) use faster disks (NVMe instead of SATA SSD), or (c) accept the occasional stall and rely on producer-side retry. The other failure mode is **page-cache eviction under mixed workload** — running Kafka on the same box as a Cassandra or Elasticsearch node that does random reads causes Kafka's sequential pages to be evicted by the other workload's random pages, dropping Kafka's read hit-rate from 95% to 30% and bottlenecking on disk read IOPS. The diagnostic is `iostat -x 1` showing high `r/s` (reads per second) on the Kafka disk, and `sar -B 10` showing high `pgmajfault/s` (major page faults) on the broker JVM. The fix is to dedicate the box to Kafka.

### The Zero-Copy Optimization: Direct DMA data transfers from Page Cache to Network Socket via the `...

The `sendfile()` syscall, introduced in Linux 2.2 and refined in 2.4 and 2.6, is the single most important kernel primitive in Kafka's read path. It allows a process to copy data from one file descriptor (a regular file) to another file descriptor (a socket) **without the data ever entering user space** — the kernel DMA-copies the file's pages from disk (or page cache) directly into the socket's kernel buffer, and from there the network card DMAs the data onto the wire. The traditional alternative requires four kernel-to-user and user-to-kernel copies and two syscalls (`read()` then `write()`), plus a context switch for each. For a 1 MB record batch served to a consumer, the traditional path costs ~2 ms of CPU on a modern x86; the `sendfile` path costs ~50 µs — a 40× reduction that, multiplied across millions of fetches per second, is the difference between saturating a 10 Gbps NIC at 20% CPU and saturating it at 100% CPU.

```text
   TRADITIONAL READ + WRITE PATH (no sendfile): 4 copies, 2 syscalls, 2 context switches
   ──────────────────────────────────────────────────────────────────────────────────────

     user-space        │        kernel-space
                        │
                        │   ┌─────────────────────┐
                        │   │  PAGE CACHE         │  ← file data lives here
                        │   │  (file's pages)     │
                        │   └──────────┬──────────┘
                        │              │ 1. DMA copy (disk → page cache, if not cached)
                        │              ▼
     read(fd, buf, n)   │   ┌─────────────────────┐
     ───────────────────▶   │  kernel read buffer │
                        │   └──────────┬──────────┘
                        │              │ 2. CPU copy (kernel → user)
                        │              ▼
     ┌─────────────┐    │   ┌─────────────────────┐
     │ user buf    │◀───┼───│  user-space buffer  │  ← JVM heap, in process memory
     └─────────────┘    │   └─────────────────────┘
                        │
     write(socket, buf, n)
     ───────────────────▶   ┌─────────────────────┐
                        │   │  kernel socket      │  ← 3. CPU copy (user → kernel)
                        │   │  send buffer        │
                        │   └──────────┬──────────┘
                        │              │ 4. DMA copy (kernel → NIC)
                        │              ▼
                        │   ┌─────────────────────┐
                        │   │  NETWORK CARD       │  ← data on the wire
                        │   └─────────────────────┘

   ──> 4 copies (2 DMA, 2 CPU), 2 syscalls (read+write), 2 context switches (user→kernel→user→kernel→user)


   SENDFILE PATH: 1 syscall, 0 user-space copies, 0 context switches into user space
   ──────────────────────────────────────────────────────────────────────────────────

     user-space        │        kernel-space
                        │
                        │   ┌─────────────────────┐
                        │   │  PAGE CACHE         │  ← file data lives here
                        │   │  (file's pages)     │
                        │   └──────────┬──────────┘
                        │              │
     sendfile(socket, fd, offset, n)   │
     ───────────────────▶              │  (kernel does it all internally)
                        │              ▼
                        │   ┌─────────────────────┐
                        │   │  kernel socket      │  ← 1. CPU copy (page cache → socket buffer,
                        │   │  send buffer        │      or with SG-DMA, no copy at all)
                        │   └──────────┬──────────┘
                        │              │ 2. DMA copy (kernel → NIC)
                        │              ▼
                        │   ┌─────────────────────┐

```

Kafka uses `sendfile` via Java's `FileChannel.transferTo()` method, which the JVM maps to the `sendfile` syscall on Linux. The broker's read path for a fetch request is: receive the fetch request → look up the partition's log → binary-search the index for the requested offset → call `FileChannel.transferTo(socketChannel, position, count)` on the `.log` file at the computed byte position → the kernel copies the requested byte range from the page cache to the socket. The broker JVM never sees the message bytes — they go from page cache to NIC without ever touching JVM heap. This is why Kafka brokers can serve millions of fetches per second with a 6 GB JVM heap: the heap holds only the request/response metadata and the offset indexes, not the message payloads. Without `sendfile`, every fetch would require a JVM heap allocation for the response buffer, GC pressure would be enormous, and the broker would be CPU-bound at 1–2 Gbps instead of network-bound at 10 Gbps.

The zero-copy optimization is the reason Kafka is the only major messaging system that benefits from being disk-backed rather than RAM-backed. RabbitMQ, ActiveMQ, and most JMS brokers store messages in JVM heap (or in a separate off-heap direct buffer) and must copy each message from broker memory to the consumer's TCP socket via the JVM's `write()` path — the broker JVM touches every byte, twice (once to read from queue, once to write to socket). Kafka stores messages in the OS page cache and lets the kernel copy them to the socket via DMA — the broker JVM touches none of the payload bytes. The trade-off is that Kafka's `sendfile` path requires the message to be in a file, which means Kafka cannot do in-memory routing or transformation the way an AMQP exchange can — the broker's job is "fetch bytes from offset X and send them to socket Y," nothing more. This is why Kafka has no exchange/binding model (every consumer group reads from a fixed partition set) and why Kafka Streams exists as a separate library rather than being built into the broker: the broker's storage layer is optimized for one thing (zero-copy file-to-socket transfer), and anything that would require touching the bytes in user space must be pushed to the client.

```java
// The Kafka broker's send path, simplified from org.apache.kafka.storage.internals.log.Log.read()
public FetchDataInfo read(long startOffset, int maxLength) {
    FileRecords.LogOffsetPosition position = index.lookup(startOffset);
    // position.position = byte offset in .log file; position.offset = first message offset >= startOffset

    FileChannel fileChannel = segment.log().channel();
    long filePosition = position.position;
    int readLength = Math.min(maxLength, (int)(segment.size() - filePosition));

    // The actual transfer happens in FileRecords.sendTo, which calls:
    //   fileChannel.transferTo(filePosition, readLength, socketChannel);
    // Under the hood, this is the sendfile(2) syscall on Linux.
    return new FetchDataInfo(position, segment.log().slice(filePosition, readLength));
}

// Verify sendfile is being used: strace the broker process while a consumer is fetching
//   sudo strace -p <kafka_pid> -e trace=sendfile -c
//   sendfile(64, 78, [12345678], 1048576) = 1048576   ← 1 MB transferred, 0 bytes through JVM
```

The production failure mode of zero-copy is **TLS termination breaking the optimization**. The `sendfile` syscall only works when the destination socket is a plain TCP socket — if TLS is enabled on the broker (Kafka's `ssl.` config), the kernel cannot DMA-encrypt the data, so the broker falls back to the traditional `read()` + JVM-side TLS encrypt + `write()` path, which means every fetch byte touches the JVM heap. A Kafka broker with TLS enabled typically runs at 30–50% of its non-TLS throughput and at 2–3× the CPU. The other failure mode is **message-level transformation** — if a developer adds an interceptor that deserializes each message to log it or to add a header, the broker must read the message into JVM heap, deserialize, transform, reserialize, and write back — the zero-copy path is bypassed and throughput drops to in-memory-queue levels. The diagnostic is `perf stat -p <pid>` showing high `context-switches` and `cpu-migrations` (the TLS and transformation paths cause more kernel-user transitions than the zero-copy path).

### Log Compaction: Retaining the latest state per message key on disk for event-sourced tables

Kafka's retention model has two policies, selected per-topic via the `cleanup.policy` config: **`delete`** (the default — segments are deleted when they exceed `retention.ms` or `retention.bytes`) and **`compact`** (segments are rewritten to keep only the latest value per message key, so the topic acts as a changelog that converges to the current state of each key). A topic can also have `cleanup.policy=compact,delete` — compact first, then delete compacted segments after their retention window. Compaction is what lets Kafka act as a **durable key-value store**: a compacted topic with key=user_id and value=user_profile is, after compaction, a snapshot of the current state of every user, replayable from the start of the topic to reconstruct the full state. This is the foundation of Kafka Streams' `KTable` abstraction and of the `__consumer_offsets` topic itself (which is compacted — only the latest offset per consumer group matters).

The compactor is a background thread that runs on each broker, scanning the partition's rolled segments (the active segment is never compacted — it's still being appended to). For each key, the compactor finds the latest occurrence across all rolled segments and writes that occurrence to a new "clean" segment; older occurrences of the same key are dropped. The compactor runs incrementally — it does not rewrite the entire log on every pass; it identifies "dirty" segments (those with many duplicate keys) and rewrites only those, leaving "clean" segments alone. The `min.cleanable.dirty.ratio` config (default 0.5) controls when a segment becomes eligible for compaction — a segment is compacted when the ratio of duplicate-key bytes to total bytes exceeds this threshold. The `delete.retention.ms` config (default 24 hours) controls how long tombstones (messages with `null` value, signaling a key deletion) are retained before the compactor removes the key entirely.

```text
   LOG COMPACTION: BEFORE vs AFTER (compacted topic, key=user_id, value=profile JSON)
   ─────────────────────────────────────────────────────────────────────────────────

   BEFORE COMPACTION (raw log, all writes preserved):
   ┌────────────────────────────────────────────────────────────────────┐
   │ offset 0   key=alice   value={"name":"Alice","city":"NYC"}        │
   │ offset 1   key=bob     value={"name":"Bob","city":"LA"}           │

   │ offset 3   key=carol   value={"name":"Carol","city":"SF"}         │

   ──> Reading from offset 0 after compaction yields:
        alice → Chicago (not NYC, not Boston)
        bob → tombstone (consumer sees null value, knows bob was deleted)
        carol → Portland (not SF)
        dave → Austin
   ──> The compacted log is a snapshot of current state per key, not a history of changes.
```

The compaction process preserves the **offsets** of the surviving messages — offset 5 is still offset 5 after compaction, even though offsets 0, 1, 2, 3, 4 are gone. This is critical for consumer correctness: a consumer that was at offset 5 before compaction can resume at offset 5 after compaction and not skip or duplicate any data, because offset 5 still refers to the same logical message (the latest alice update). The offsets that are removed leave **gaps** in the offset sequence — a consumer reading from offset 0 after compaction will see offsets 5, 6, 7, 8 (with 0–4 missing). The consumer client transparently handles these gaps: the broker's fetch response includes the offsets of the messages it actually returned, and the consumer advances its position based on the highest returned offset, not by counting messages.

The production failure mode of compaction is **tombstone loss before consumers see them**. A tombstone (message with `null` value) is the only way to signal a key deletion in a compacted topic — the compactor sees the tombstone, marks the key for deletion, and after `delete.retention.ms` removes the key entirely. But if a consumer is offline for longer than `delete.retention.ms` (default 24 hours), it will miss the tombstone and on restart will see the key as "never existed" rather than "was deleted" — its downstream state (e.g., a materialized view in a database) will retain the stale value forever. The fix is to either (a) ensure consumers never go offline longer than `delete.retention.ms`, or (b) raise `delete.retention.ms` to a value longer than your longest plausible consumer outage (7 days is a common production setting). The other failure mode is **compaction falling behind** — if the compactor thread cannot keep up with the producer rate (because `min.cleanable.dirty.ratio` is too low, the partition is too large, or the broker is under CPU pressure), duplicate keys accumulate in rolled segments and disk usage grows unboundedly. The metric to watch is `kafka.log.Log.Size` per partition vs. the expected compacted size; if the ratio exceeds 5×, compaction is falling behind and the broker needs more CPU or the topic needs more partitions to spread the load.
