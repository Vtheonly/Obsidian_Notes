# 07.02.03. Kafka Producer Architecture

## What This Is

The Kafka producer is the write side of the commit log: it serializes application objects into byte arrays, picks a partition, accumulates records into per-partition batches, and ships those batches over TCP to the partition leader. It is not a thin socket wrapper — it is a throughput engine whose entire design is built around the observation that one large network write is dramatically cheaper than many small ones, and that brokers are happiest appending large sequential blocks to their segment files. Every tunable on the producer (`batch.size`, `linger.ms`, `compression.type`, `acks`, `max.in.flight.requests.per.connection`) is a dial on the latency/throughput/durability tradeoff triangle.

This note sits in section 07.02 because the producer is the producer-side counterpart to the cluster storage architecture covered in 07.02.01 (the physical commit log) and 07.02.02 (cluster topology and consensus). The bytes the producer ships land in segment files on the leader, get replicated to ISR followers, and are later read by the consumers covered in 07.03. The producer's correctness contract (idempotence, transactions) is what makes the delivery guarantees in 07.03.03 possible. Frameworks from section 05 (Spring Kafka, NestJS KafkaJS, Celery+Kafka, Laravel Kafka) are all thin wrappers around the same underlying `KafkaProducer` semantics described here.

## The Details

### Record Batching: `batch.size` and `linger.ms` tuning for high throughput

A `KafkaProducer.send(ProducerRecord)` call does **not** write to the network. It hands the record to a `Partitioner`, which selects a partition, then to the `RecordAccumulator`, which appends the serialized record to the tail of a per-partition `Deque<ProducerBatch>`. A single background thread — the `Sender` — runs in a loop, drains completed batches from the accumulator, and writes them to the broker via the `NetworkClient` (built on Java NIO `Selector`). This decoupling is what allows a producer to sustain hundreds of thousands of records per second on a single thread: `send()` is essentially a memory append, and the actual I/O is amortized over many records per TCP write.

Two knobs govern how full a batch is when the Sender picks it up. `batch.size` (default 16384 bytes = 16 KiB) is the **maximum** size of a single batch — when a batch reaches this many bytes it is closed and queued for immediate send regardless of `linger.ms`. `linger.ms` (default 0) is the **maximum** time the producer will wait for a batch to fill before sending it even if it is not full. With `linger.ms=0` (the default) the producer behaves like a request-response system — every `send()` triggers a network write as soon as the Sender loop wakes up. With `linger.ms=5` (a typical production value) the producer will hold a small batch for up to 5 ms in the hope that more records arrive, then ship whatever it has. Bigger `batch.size` improves throughput (better compression, fewer TCP writes, larger broker appends) at the cost of more memory per partition and slightly higher worst-case latency.

```text
  Application thread (calls send())        Sender thread (single, background)
  ─────────────────────────────            ────────────────────────────────
  send(record0, partition=2)  ──┐
  send(record1, partition=2)  ──┤  Partitioner → RecordAccumulator
  send(record2, partition=2)  ──┘         │
                                          │  per-partition deque:
                                          │   p0: [batch(empty)]
                                          │   p1: [batch(2 records, 4 KiB)]
                                          │   p2: [batch(3 records, 8 KiB)] ◀─ ready when
                                          │                                            batch.size hit
                                          │                                  OR linger.ms elapsed
                                          ▼
                              NetworkClient.send() → NIO Selector → broker TCP
```

The producer's total memory budget is `buffer.memory` (default 32 MiB). When all batches together exceed this and no batch is ready to send, `send()` blocks for up to `max.block.ms` (default 60 s) before throwing `TimeoutException`. This is the backpressure mechanism: a slow broker cannot OOM the producer, but it can stall the application thread that called `send()`. The corresponding failure mode in production is a broker hiccup (leader election, GC pause on the broker, network blip) causing every application thread calling `send()` to block for 60 s, which a downstream HTTP server experiences as a request timeout cascade. The fix is to never call `send()` on the HTTP request thread — always hand off to a dedicated producer thread or use the callback API, and monitor `record-send-rate` and `record-queue-time-avg` metrics; a queue time climbing past 100 ms means the producer is bottlenecked on the broker.

### Producer Acknowledgments: `acks=0` (Fire and forget), `acks=1` (Leader write confirmed), `acks=all` / `acks=-1` (Full ISR quorum write confirmed)

The `acks` configuration controls how many brokers must durably acknowledge a produce request before the producer considers it successful. With `acks=0` the producer writes the batch to the TCP socket and immediately considers it sent — it never reads the response. There is no retry, no error callback (the callback fires with `null` for `metadata` and `null` for `exception`), and the broker could be down entirely without the producer noticing. This is the right choice for high-volume telemetry or metrics where losing 0.1% of data points is acceptable and per-record latency must stay sub-millisecond; it is the wrong choice for anything that resembles a financial transaction.

With `acks=1` (the historical default before Kafka 3.0) the leader writes the batch to its local segment file, flushes to the OS page cache, and immediately returns an ack without waiting for followers. This is fast but has a well-known durability hole: if the leader crashes between acking and the followers replicating, the batch is lost, and the new leader (an ISR follower that did not have the batch) will start accepting writes from a position that skips the lost records. With `acks=all` (the default since Kafka 3.0) the leader waits for the batch to be replicated to the entire **current ISR** before acking. The size of the ISR is bounded by the broker's `min.insync.replicas` setting — typically `min.insync.replicas=2` paired with `replication.factor=3`, which means the producer will block until at least 2 of the 3 replicas have the data, tolerating one broker failure without data loss.

```text
  acks=0:   Producer ──TCP write──▶ Leader                (no response read)
  acks=1:   Producer ──produce──▶ Leader ──writes local log──▶ ack  (followers async, optional)
  acks=all: Producer ──produce──▶ Leader ──replicate──▶ ISR{f1, f2}
                                              ◀── all ISR acked ──
                                              ◀── ack to producer ──
```

The interaction with `retries` (default `Integer.MAX_VALUE` since Kafka 3.0) and `delivery.timeout.ms` (default 120 s) is what determines whether a transient failure surfaces to the application. A produce request that fails with `NOT_LEADER_OR_FOLLOWER` (the leader moved) or `NOT_ENOUGH_REPLICAS` (ISR shrank below `min.insync.replicas`) will be retried by the producer for up to `delivery.timeout.ms`, with backoff controlled by `retry.backoff.ms` (default 100 ms) and `retry.backoff.max.ms` (default 1 s). The most common production incident is a misconfigured `acks=1` producer with `min.insync.replicas=1` losing data during a rolling broker upgrade — the operator thinks they have `replication.factor=3` durability, but the producer is acking on a single broker and a leader election during the upgrade wipes the un-replicated tail of the log. The fix is `acks=all` + `min.insync.replicas=2` + `replication.factor=3`, accepting roughly 1.5× the per-record latency for 3 orders of magnitude better durability.

### Partitioning Strategies: Default MurmurHash2 key hashing, Round-Robin, Custom Partitioners

The partitioner runs after the serializer and before the RecordAccumulator, and answers one question: given a topic, a key (possibly null), a value, and the current cluster metadata, which partition number should this record go to? The choice is load-bearing because partition is the unit of parallelism on the consumer side (one partition = one consumer in the group) and the unit of ordering (records within a partition are strictly ordered; across partitions they are not). Picking the wrong partition for the wrong reason produces hot partitions, uneven consumer load, and broken ordering guarantees that surface as application bugs weeks later.

The default `org.apache.kafka.clients.producer.internals.DefaultPartitioner` uses a two-mode algorithm. If the record has a non-null key, it computes `murmur2(key.getBytes(StandardCharsets.UTF_8)) % numPartitions` — a stable hash that pins every record for a given key to the same partition. This is what makes "all events for user 42 land on the same partition" true, which is what makes per-user event ordering possible. If the key is null, the producer uses the **sticky partitioner** (KIP-480, Kafka 2.4+): instead of round-robining across all partitions (which produced tiny batches on every partition and tanked throughput), it picks one partition at a time and sticks to it for `linger.ms`, so that keyless records accumulate into a single large batch per cycle. The sticky partition rotates on each batch drain, giving statistical round-robin over time but big batches in the steady state.

```java
// Custom partitioner — pin "VIP" customers to partition 0, hash the rest
public final class VipAwarePartitioner implements Partitioner {
    private String vipPrefix;

    @Override
    public int partition(String topic, Object key, byte[] keyBytes,
                         Object value, byte[] valueBytes, Cluster cluster) {
        int numPartitions = cluster.partitionCountForTopic(topic);
        String k = key != null ? key.toString() : "";
        if (k.startsWith(vipPrefix)) {
            return 0;                                  // VIPs always on partition 0
        }
        // Default MurmurHash2 behaviour for non-VIP keys
        return Utils.toPositive(Utils.murmur2(keyBytes)) % numPartitions;
    }

    @Override public void configure(Map<String, ?> configs) {
        this.vipPrefix = (String) configs.get("vip.prefix");
    }
    @Override public void close() {}
    @Override public void onNewBatch(String topic, Cluster cluster, int prevPartition) {}
}
// Producer config: partitioner.class=com.example.VipAwarePartitioner, vip.prefix=vip_
```

A custom partitioner is configured via `partitioner.class` and is the right answer when the default hash distribution is wrong — typically because one key dominates the traffic (a "whale" customer producing 60% of events all hashing to the same partition, which then becomes a hot spot no amount of consumer scaling can fix). The failure mode to watch for is partition skew: monitor `record-send-rate-per-partition` and rebalance either by re-keying (e.g., append a random shard suffix `user42#0`, `user42#1`, ...) or by writing a custom partitioner that spreads hot keys across N partitions while preserving ordering for cold keys. Round-robin partitioning (the pre-2.4 behaviour for null keys, now reachable via `UniformStickyPartitioner`) is rarely the right choice for keyed data because it throws away the ordering guarantee the key was supposed to provide.

### Compression codecs: Snappy, LZ4, Gzip, Zstandard

Kafka compresses **batches**, not individual records. The producer concatenates the varint-prefixed record batches in memory, runs the chosen codec over the whole batch, and writes the compressed blob to the wire with a single `compression` byte in the record-batch header. The broker stores the batch on disk in compressed form — it does not decompress on write — and consumers receive compressed batches and decompress locally. This means compression is paid for once (on the producer) and benefits every hop after: less network bandwidth producer→broker, less broker disk I/O, less page-cache pressure, less network bandwidth broker→consumer. The amortization is why `compression.type` is one of the highest-leverage producer settings.

The four codecs trade compression ratio against CPU cost. **Snappy** (Google, 2011) is the historical default — ~250 MB/s compress, ~500 MB/s decompress on a modern core, ratio around 1.5–2.0× on JSON-ish payloads. **LZ4** is the modern throughput leader — faster than Snappy on both sides with a slightly better ratio, and the right default for new deployments. **Gzip** (using `gzip` levels 1–9, default 6) gives the best ratio (typically 3–4×) at 5–10× the CPU cost; it makes sense for cold-storage topics where producer CPU is plentiful and consumer read rate is low. **Zstandard** (Facebook, 2015, RFC 8478) is the modern ratio champion — at compression level 3 it approaches Gzip-level ratios at LZ4-like speeds, and at level 19+ it beats Gzip on ratio at lower CPU; it is the right choice when both ends run Kafka 2.1+ (the broker must understand the codec to recompress on produce if the topic's `compression.type` differs).

| Codec     | Compress MB/s | Ratio (JSON) | Latency add | Notes                                   |
|-----------|---------------|--------------|-------------|-----------------------------------------|
| none      | —             | 1.0×         | 0 ms        | Baseline, no CPU overhead                |
| snappy    | ~250          | 1.8×         | <1 ms       | Default pre-2.1, ubiquitous compatibility|
| lz4       | ~400          | 2.0×         | <1 ms       | Fastest end-to-end, default for new clusters |
| gzip      | ~50 (lvl 6)   | 3.2×         | 5–15 ms     | Best ratio on legacy infra, CPU-heavy   |
| zstd      | ~200 (lvl 3)  | 3.0×         | 2–5 ms      | Modern default — LZ4 speed, Gzip ratio  |

The synergy with batching is the part most teams miss. Compression ratio depends on the volume of similar data the codec sees at once — a 16 KiB batch compresses 1.5×, a 256 KiB batch (reachable by raising `batch.size` and `linger.ms`) compresses 3×. So `compression.type=lz4` with default `batch.size=16384` may give worse end-to-end throughput than `compression.type=none` with `batch.size=262144` and `linger.ms=20`, because the larger batches amortize the per-batch overhead and the broker writes fewer, larger segment appends. The production failure mode is a team that sets `compression.type=gzip` on a producer that's already CPU-bottlenecked (running at 80% on a 2-core box) and watches producer throughput collapse by 5× because the compression thread is starving the sender thread. Monitor `compression-rate-avg` (should be >1.5 for any codec to be worth it) and producer CPU together; if CPU is the bottleneck before compression is, switch from gzip → zstd → lz4 → snappy in that order.

## How This Connects to the Frameworks

Every framework in section 05 that integrates Kafka ships a thin wrapper around `KafkaProducer`:

- **Spring Boot** (`spring-kafka`): `KafkaTemplate<K, V>` wraps `KafkaProducer` and exposes `send().addCallback()`. The `@Bean ProducerFactory` configures `acks`, `batch.size`, etc. as a `Map<String, Object>`. Spring's `KafkaTemplate.send()` returns `ListenableFuture<SendResult<K, V>>` whose `RecordMetadata` carries the partition and offset. Transactions are exposed via `@Transactional` + `KafkaTemplate.executeInTransaction()`.
- **Node.js** (`kafkajs`): `new Producer({ acks: -1, compression: CompressionTypes.LZ4 })`. `await producer.send({ topic, messages: [...] })` batches at the library level — you push an array and kafkajs assembles the batch. No `linger.ms` equivalent in the original API; later versions added `linger.ms` under `producer.send()` options.
- **Python** (`confluent-kafka` — librdkafka binding): `Producer({'bootstrap.servers': ..., 'acks': 'all', 'linger.ms': 5})`. The C library exposes `producer.produce(topic, key, value, callback=cb)` which is non-blocking; `producer.poll(0)` pumps the callback queue.
- **PHP** (`laravel-kafka` / `rdkafka` extension): `Producer::on($topic)->withConfigKey('compression.codec', 'zstd')->withMessage(...)->send()`. The `rdkafka` extension is a librdkafka binding identical in semantics to the Python one.

The conceptual model is identical across all four; only the syntax and the default values differ. Spring defaults to `acks=1` (override to `all` in any production config), kafkajs defaults to `acks=-1`, confluent-kafka defaults to `acks=1`, rdkafka defaults to `acks=1`. The first thing to verify when adopting any of these is to print the resolved config and confirm `acks=all` is actually being applied — defaults have burned many teams.

## Hands-On Exercise

```bash
# 1. Start a single-broker Kafka (KRaft mode, no Zookeeper) on localhost:9092
docker run -d --name kafka -p 9092:9092 \
  -e KAFKA_NODE_ID=1 \
  -e KAFKA_PROCESS_ROLES=broker,controller \
  -e KAFKA_LISTENERS=PLAINTEXT://:9092,CONTROLLER://:9093 \
  -e KAFKA_ADVERTISED_LISTENERS=PLAINTEXT://localhost:9092 \
  -e KAFKA_CONTROLLER_LISTENER_NAMES=CONTROLLER \
  -e KAFKA_CONTROLLER_QUORUM_VOTERS=1@localhost:9093 \
  -e KAFKA_INTER_BROKER_LISTENER_NAME=PLAINTEXT \
  -e CLUSTER_ID=MkU3OEVBNTcwNTJENDM2Qk \
  apache/kafka:3.7.0

# 2. Create a 6-partition topic with replication factor 1 (single broker)
docker exec kafka /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --create --topic perf \
  --partitions 6 --replication-factor 1

# 3. Benchmark the producer with acks=all, linger.ms=10, batch.size=64KiB, lz4
docker exec kafka /opt/kafka/bin/kafka-producer-perf-test.sh \
  --topic perf --num-records 1000000 --record-size 1024 \
  --throughput -1 --producer-props bootstrap.servers=localhost:9092 \
  acks=all linger.ms=10 batch.size=65536 compression.type=lz4

# 4. Compare against acks=1, linger.ms=0, no compression
docker exec kafka /opt/kafka/bin/kafka-producer-perf-test.sh \
  --topic perf --num-records 1000000 --record-size 1024 \
  --throughput -1 --producer-props bootstrap.servers=localhost:9092 \
  acks=1 linger.ms=0 compression.type=none

# 5. Inspect the per-partition distribution (skew check) after writing keyed records
docker exec kafka /opt/kafka/bin/kafka-run-class.sh \
  kafka.tools.GetOffsetShell --broker-list localhost:9092 --topic perf
```

Step 3 vs step 4 should show 3–5× throughput improvement with batching + compression. Step 5 reveals partition skew — if one partition has dramatically more offsets than the others, your key distribution is broken and no amount of consumer scaling will recover the throughput on the hot partition.
