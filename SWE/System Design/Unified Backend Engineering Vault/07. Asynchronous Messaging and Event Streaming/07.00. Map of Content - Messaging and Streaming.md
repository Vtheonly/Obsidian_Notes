# 07.00. Map of Content: Messaging and Streaming

## Overview

Section 07 is where the unified backend vault turns from synchronous request/response to **asynchronous, decoupled, replayable** communication. Everything below this section — Section 02's kernel primitives (file descriptors, `epoll`, page cache, `sendfile`), Section 03's TCP and binary protocols, Section 04's runtime threads, Section 05's framework abstractions, Section 06's persistence engines (WAL, B+Trees, LSMs) — is the foundation. Section 07 takes that foundation and builds the three async primitives a backend engineer must master: the **message queue** (transient task hand-off), the **append-only commit log** (durable, replayable event stream), and the **background task runner** (out-of-band work). Section 08 then layers distributed consensus, sagas, and big-data compute on top of what Section 07 produces.

The section's central thesis is the **architectural divide** between two equally valid models. On one side sits the *traditional queue* — RabbitMQ, ActiveMQ, AWS SQS, IBM MQ — where a message is delivered to one consumer, acknowledged, and destroyed. On the other side sits the *distributed log* — Kafka, Kinesis, Pulsar, Redpanda — where messages are appended to an immutable, retention-bounded stream that many independent consumer groups can read, re-read, and tail concurrently. Picking the wrong model is the single most expensive messaging mistake you can make: queues cannot replay history, and logs cannot efficiently distribute one-shot work across a fleet of workers. Subsection 07.01 establishes the divide; 07.02–07.03 go deep on Kafka because Kafka is the most operationally demanding and most widely deployed log broker; 07.04 covers the task-queue pattern that runs on top of either model; 07.05 closes the loop with the transactional outbox and CDC, the patterns that let a relational database participate atomically in an async pipeline.

The vault's layered mental model is in full force here. The page-cache and `sendfile` zero-copy machinery from Section 02.04 is what lets Kafka saturate a 10 Gbps NIC at 20% CPU. The TCP backpressure and window mechanics from Section 03.02 are what RabbitMQ's `basic.qos` prefetch count exposes at the AMQP layer. The B+Tree and WAL internals from Section 06.01 are what Kafka's index files and `__consumer_offsets` topic reuse. The thread pools and executors from Section 04 are what every consumer client runs handlers on. If you skipped Sections 02–06, you will read Section 07 as a list of config keys; if you did not skip them, you will read Section 07 as the capstone where every previous layer finally does work in production.

## Section Map

### 07.01. Message Queues vs Append-Only Commit Logs

- [[07.01.01. The Architectural Divide in Asynchronous Messaging]] — Establishes the four-axis comparison between traditional message queues (RabbitMQ, ActiveMQ, AWS SQS, IBM MQ) and distributed event logs (Kafka, Kinesis, Pulsar, Redpanda). Covers lifecycle (transient task queue with destruction-after-ack vs. durable append-only log with replayable offsets), topology (point-to-point task workers vs. fan-out pub/sub), delivery model (broker push vs. consumer pull), and the failure-mode mapping that determines which model fits a given workload.
- [[07.01.02. AMQP Protocol and RabbitMQ Architecture]] — Deep dive into AMQP 0.9.1 as the canonical wire protocol for queue-style messaging. Covers the exchange/binding/queue routing model, the four exchange types (direct, fanout, topic, headers), connections vs. channels, the `basic.publish`/`basic.consume`/`basic.ack`/`basic.nack`/`basic.reject` method surface, durable exchanges/queues and persistent messages, prefetch (`basic.qos`), dead-letter exchanges, and the migration from classic mirrored queues to Raft-based quorum queues.

### 07.02. Apache Kafka Cluster and Storage Architecture

- [[07.02.01. The Physical Commit Log on Disk]] — How a topic → partition → segment hierarchy is laid out on a broker's filesystem, with the on-disk layout of `00000000000000000000.log`, `00000000000000000000.index`, and `00000000000000000000.timeindex` files. Covers append-only writes, the active segment, the rolling policy (`segment.bytes` default 1 GB, `segment.ms` default 7 days), the offset as a byte position in the log, sequential reads, page-cache exploitation, `sendfile` zero-copy, retention (`retention.bytes`, `retention.ms`, `log.retention.check.interval.ms`), and log compaction for compacted topics.
- [[07.02.02. Kafka Cluster Topology and Consensus]] — Brokers, controllers, and the KRaft consensus protocol that replaced ZooKeeper in Kafka 3.3+. Covers partition leadership (leader handles all reads/writes, followers replicate via fetch requests), the ISR (In-Sync Replicas) set, `min.insync.replicas` as the durability floor, the `acks=all` producer setting, the high-watermark and leader-epoch machinery, and the unclean-leader-election tradeoff between availability and durability.
- [[07.02.03. Kafka Producer Architecture]] — The producer pipeline from `KafkaProducer.send()` to broker append: the per-partition record accumulator, `batch.size` (default 16 KB) and `linger.ms` (default 0 ms) tuning, the `Sender` thread that batches records into produce requests, the `compression.type` (none/gzip/snappy/lz4/zstd), idempotent producers (`enable.idempotence=true` since 0.11), and the transactions API (`transactional.id`) for exactly-once semantics across consume-process-produce pipelines.

### 07.03. Kafka Consumers Offsets and Processing Semantics

- [[07.03.01. Consumer Groups and Partition Balancing]] — The consumer-group model: how N consumers in the same `group.id` split M partitions, the partition-assignment strategies (range, round-robin, sticky, cooperative-sticky), the rebalance protocol (join-group/sync-group/heartbeat), the static membership feature (`group.instance.id`) that avoids rebalances during rolling restarts, and the consumer coordinator broker that owns the group.
- [[07.03.02. Offset Management and Commit Strategies]] — The `__consumer_offsets` internal topic (50 partitions by default, compacted), the commit-offset record format, auto-commit (`enable.auto.commit=true`, `auto.commit.interval.ms=5000`) vs. manual `commitSync()`/`commitAsync()`, the offset-reset policy (`auto.offset.reset=latest/earliest/none`) for first-time consumers, and the partition-assignment + offset-fetch protocol the consumer runs on startup.
- [[07.03.03. Delivery Guarantees and Idempotent Processing]] — At-most-once (commit before processing — risky), at-least-once (default — commit after processing, requires idempotent consumers), and exactly-once (Kafka transactions with `isolation.level=read_committed` on the consumer + `transactional.id` on the producer). Covers the idempotency-key pattern, deduplication tables, the zombie-fence problem, and the cost of EOS (lower throughput, longer end-to-end latency).

### 07.04. Background Job Processing and Task Queues

- [[07.04.01. The Background Task Pattern]] — Why heavy work must move off the HTTP request path: p99 latency budgets, request-thread exhaustion, third-party API failure isolation, retry-with-backoff semantics, and the visibility-timeout mechanism that prevents double-processing when a worker dies mid-job. Covers the immediate/deferred/scheduled/recurring job taxonomy and the failure-handling primitives (retry, dead-letter, kill).
- [[07.04.02. Ecosystem Implementations]] — Side-by-side implementations of the same background-job feature across Spring (`@Async`, `ThreadPoolTaskExecutor`, `@Scheduled`, Spring Batch chunk-oriented processing), Express (BullMQ on Redis, Agenda on MongoDB), Django/Flask (Celery with Redis/RabbitMQ broker, RQ, APScheduler), and Laravel (the `queue` worker, Horizon dashboard, job dispatch via `Bus::dispatch`). Highlights what each runtime makes automatic and what each makes you configure by hand.

### 07.05. Distributed State Coordination and Outbox Pattern

- [[07.05.01. The Dual-Write Problem]] — Why you cannot atomically write to a database and publish to a message broker in the same logical operation: the lack of a two-phase commit across heterogeneous systems, the failure window between the COMMIT and the broker publish, and the resulting torn-state inconsistency. Demonstrates the problem with a concrete order-create + email-publish example that loses or duplicates messages under node crash.
- [[07.05.02. The Transactional Outbox Pattern]] — The fix: write the domain mutation and an outbox event row in the same ACID database transaction, then have a separate relay process poll the outbox table (or use CDC) and publish to the broker. Covers the outbox table schema (id, aggregate_id, event_type, payload, created_at, processed_at), the relay's at-least-once delivery guarantee, the idempotent consumer requirement, and the throughput ceiling of polling.
- [[07.05.03. Change Data Capture (CDC) and Debezium]] — How Debezium turns a database transaction log (PostgreSQL WAL, MySQL binlog, Oracle redo log, SQL Server CDC, MongoDB oplog) into a Kafka topic by tailing the log rather than polling tables. Covers the log-based CDC advantage over poll-based, the Debezium source connector topology, the schema-registry integration, and the snapshot-then-stream bootstrap procedure for existing data.

## Conceptual Roadmap

Section 07 unfolds as a three-act narrative that builds from *pick the right primitive* → *operate the log primitive at scale* → *make async safe alongside your database*.

```text
   ┌──────────────────────────────────────────────────────────────────┐
   │                    SECTION 07 — THREE ACTS                       │
   └──────────────────────────────────────────────────────────────────┘

   ACT I — The fork in the road                       07.01.01 / 07.01.02
   ┌─────────────────────────────────────────────────────────────────┐
   │  Async work has two shapes:                                     │
   │   (a) Transient task → one consumer → destroy after ack         │
   │       (RabbitMQ, SQS, ActiveMQ, IBM MQ — AMQP/JMS wire models) │
   │   (b) Durable event log → many consumer groups → replay        │
   │       (Kafka, Kinesis, Pulsar, Redpanda — commit-log model)    │
   │                                                                 │
   │  Pick wrong and you pay forever: queues can't replay history,  │
   │  logs can't efficiently distribute one-shot work.              │
   └─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
   ACT II — Operating the log primitive               07.02 / 07.03
   ┌─────────────────────────────────────────────────────────────────┐
   │  Kafka is the most demanding log broker, so we go deep:         │
   │   07.02.01  On-disk layout (segments, .log/.index/.timeindex)   │

   │   07.02.03  Producer pipeline (batching, linger, idempotence)   │
   │   07.03.01  Consumer groups & rebalancing                       │
   │   07.03.02  __consumer_offsets & commit strategies              │

                              │
                              ▼

   ┌─────────────────────────────────────────────────────────────────┐
   │  07.04  Background jobs: move work off the HTTP path, give it   │
   │         retry semantics, visibility timeouts, dead-letter queues│
   │  07.05  Outbox + CDC: make the database participate atomically  │
   │         in the async pipeline, since dual-writes are torn-state │
   │         and a relational DB can't 2PC with Kafka.               │
   └─────────────────────────────────────────────────────────────────┘
```

Read **Act I** first — the architectural divide is the decision that determines everything downstream. If you skip 07.01.01 you will reach for RabbitMQ when you need Kafka, or for Kafka when you need a one-shot task queue, and either mistake is multi-month expensive to undo. Read **Act II** in order — the on-disk layout determines what the cluster topology can promise, which determines what the producer can ack, which determines what the consumer can deliver. Each note assumes the previous note's vocabulary. Read **Act III** last — it shows how to actually use the async primitives in production code without creating dual-write inconsistencies or zombie background jobs.

The single most important cross-section link: the transactional outbox pattern in 07.05.02 is the bridge between Section 06 (persistence) and Section 07 (messaging). It is the only correct way to make a relational database emit events. If you remember one pattern from this section, remember that one.

## How to Read This Section

1. **Read the concept notes first.** 07.01.01 establishes the queue-vs-log divide that every subsequent note assumes. Read it before anything else in 07.02 — if you don't understand why a log is not a queue, Kafka's segment files and ISR sets will look arbitrary.
2. **Implement the Kafka anchor.** Kafka is the most operationally demanding broker in the section, so the deep implementations live on Kafka. The Spring Boot anchor for Kafka producer/consumer code lives in the subsection-07.02 and 07.03 anchor notes.
3. **Run the delta pass.** The same producer/consumer pattern expressed in Express (`kafkajs`), Django (`confluent-kafka-python`), and Laravel (`rdkafka` PHP extension) is in the delta notes — read them side by side to internalise that the wire protocol is identical and only the client API differs.
4. **Connect to persistence.** The outbox pattern in 07.05.02 is the seam between Section 06 and Section 07. Read it after 06.01.02 (WAL) so the parallel — "WAL is to a database what the commit log is to Kafka" — lands cleanly.

> [!tip] Reading order
> If you are new to messaging, follow the strict numeric ordering: 07.01.01 → 07.01.02 → 07.02.01 → 07.02.02 → 07.02.03 → 07.03.01 → 07.03.02 → 07.03.03 → 07.04.01 → 07.04.02 → 07.05.01 → 07.05.02 → 07.05.03. If you are revising, jump directly to whichever concept you forgot — every note is self-contained and cross-links to the others.
