# Private Networks (VPC)

#network/vpc #security/networking #cloud/aws

## What Is a VPC?

A **Virtual Private Cloud (VPC)** is your own isolated network within a cloud provider's infrastructure. Within a VPC, you define IP address ranges (CIDR blocks), create subnets, configure route tables, and set up security boundaries. Your instances communicate with each other over private IP addresses, completely isolated from other AWS customers.

Think of a VPC as your own virtual data center within AWS. You control the network topology, IP addressing, routing, and security policies — just as you would with physical networking equipment, but with software-defined automation.

## Subnets: Dividing the VPC

A VPC is divided into **subnets**, each mapped to a specific Availability Zone (AZ). The two fundamental types:

### Public Subnet
- Has a route to an **Internet Gateway (IGW)**, allowing direct internet access
- Instances have public IP addresses (or Elastic IPs) in addition to private IPs
- Use case: load balancers, NAT gateways, bastion hosts

### Private Subnet
- **No direct internet access** — no route to an IGW
- Instances have only private IP addresses
- Can access the internet through a **NAT Gateway** (for outbound-initiated connections like API calls, package downloads)
- Use case: application servers, databases, internal services

```
VPC: 10.0.0.0/16
├── Public Subnet (AZ-a): 10.0.1.0/24 → Internet Gateway
├── Public Subnet (AZ-b): 10.0.2.0/24 → Internet Gateway
├── Private Subnet (AZ-a): 10.0.10.0/24 → NAT Gateway → Internet
├── Private Subnet (AZ-b): 10.0.11.0/24 → NAT Gateway → Internet
└── Database Subnet (AZ-a): 10.0.20.0/24 → No internet access
```

## Why the Video Used a Private Network

The benchmark was conducted with the load generator (Autocannon) and the application servers **within the same VPC**. This is critical for accurate benchmarking because:

1. **Eliminates internet variability**: Public internet latency, packet loss, and routing fluctuations would introduce noise into the measurements. A private network provides consistent, predictable latency.
2. **Avoids egress charges**: Data transfer within a VPC (and even across AZs within the same region) is far cheaper than internet egress ($0.01/GB vs. $0.09/GB). At 6 GB/s, the savings are enormous.
3. **Saturates the right bottleneck**: Testing over the internet would introduce the public internet as a variable; the private network ensures you're testing *your* infrastructure, not the internet's.

## VPC Peering

**VPC Peering** connects two VPCs, allowing instances in each VPC to communicate using private IP addresses as if they were in the same network. Key characteristics:

- Peering is **not transitive**: if VPC-A peers with VPC-B and VPC-B peers with VPC-C, VPC-A cannot communicate with VPC-C through VPC-B
- Peered VPCs can be in the same or **different AWS accounts**
- Peered VPCs can be in the **same or different regions** (with some latency implications)
- All traffic remains on the AWS network — it never traverses the public internet

Use case in the 1M RPS architecture: a separate VPC for the database tier (for enhanced isolation and security), peered with the application tier VPC.

## Security Groups

Security groups are **instance-level firewalls** that control inbound and outbound traffic. They are **stateful** — if you allow inbound HTTP (port 80), the response traffic is automatically allowed regardless of outbound rules.

- Each instance can have up to 5 security groups
- Rules are evaluated as a union — traffic is allowed if ANY security group permits it
- Can reference other security groups as sources/destinations (not just CIDR blocks)

Example for the video's architecture:
- **ALB Security Group**: Allow inbound 443 from 0.0.0.0/0; allow outbound to App Server SG on port 3000
- **App Server Security Group**: Allow inbound 3000 from ALB SG; allow outbound to RDS SG on port 5432
- **RDS Security Group**: Allow inbound 5432 from App Server SG; no outbound internet

See [[13.6 Security Groups]] for the introductory treatment.

## Network ACLs

**Network ACLs (NACLs)** are **subnet-level firewalls** — they apply to all instances in a subnet. Unlike security groups, NACLs are **stateless**: you must explicitly allow both inbound AND outbound traffic for each connection.

- NACLs have numbered rules evaluated in order (lowest number first)
- Default NACL allows all inbound and outbound traffic
- Most architectures use the default NACL and rely on security groups for fine-grained control
- NACLs are useful for "defense in depth" — blocking entire CIDR ranges at the subnet level

## Why Production Uses Private Subnets with a Public Load Balancer

The standard production architecture places application servers in **private subnets** with an **Application Load Balancer (ALB)** in a **public subnet**:

1. Users connect to the ALB (public IP, accessible from the internet)
2. The ALB forwards traffic to application servers (private IPs, not directly accessible from the internet)
3. Application servers connect to the database (also in a private subnet, or in a separate VPC)

This architecture ensures that **application servers and databases are never directly exposed to the internet**, reducing the attack surface dramatically. The ALB acts as the single entry point, handling TLS termination, request routing, and health checking.
