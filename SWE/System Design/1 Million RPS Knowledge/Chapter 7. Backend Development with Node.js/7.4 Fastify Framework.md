# Fastify Framework

#nodejs/fastify #performance/frameworks #nodejs/optimization

## Definition

**Fastify** is a high-performance Node.js web framework designed with speed and low overhead as its primary goals. Released in 2016 by Matteo Collina (a Node.js technical steering committee member), Fastify was built from the ground up to address the performance limitations of [[7.3 Express Framework]] while maintaining a similar developer experience. Its slogan — "Fast and low overhead web framework, for Node.js" — reflects this philosophy precisely.

## Core Performance Principles

Fastify's speed advantage comes from several deliberate architectural decisions:

### 1. Schema-Based Serialization

This is Fastify's **single biggest performance advantage**. When you define a response schema using JSON Schema, Fastify uses it to generate an optimized serialization function at startup time. Instead of calling `JSON.stringify()` at runtime (which must inspect every property, determine types, and build a string), Fastify pre-compiles a serialization function that directly concatenates the response string using known types and field names.

```javascript
const schema = {
  response: {
    200: {
      type: 'object',
      properties: {
        message: { type: 'string' },
        timestamp: { type: 'number' }
      }
    }
  }
};

fastify.get('/api', { schema }, (request, reply) => {
  return { message: 'hello', timestamp: Date.now() };
});
```

At startup, Fastify reads this schema and generates a function roughly equivalent to:
```javascript
function serialize(data) {
  return '{"message":"' + data.message + '","timestamp":' + data.timestamp + '}';
}
```

This pre-compiled serializer avoids the overhead of `JSON.stringify()`'s runtime type inspection. For a 30KB JSON response, this optimization alone can save **hundreds of microseconds per request** — which compounds dramatically at high RPS.

### 2. Hook System Instead of Middleware Chain

Fastify replaces Express's linear middleware chain with a **lifecycle hook system**. Hooks are attached to specific points in the request lifecycle: `onRequest`, `preParsing`, `preValidation`, `preHandler`, `preSerialization`, `onSend`, `onResponse`, and `onError`. Each hook is registered once and looked up by route, avoiding the O(n) iteration through a middleware array for every request.

```mermaid
flowchart LR
    A[Incoming Request] --> B[onRequest]
    B --> C[preParsing]
    C --> D[preValidation]
    D --> E[preHandler]
    E --> F[Route Handler]
    F --> G[preSerialization]
    G --> H[onSend]
    H --> I[onResponse]
    style F fill:#e94560,color:#ffffff
```

This design means each hook is executed with minimal dispatch overhead. Fastify also uses `fast-uri` for RFC 3986-compliant URL parsing, which is significantly faster than Node.js's built-in `url.parse()`.

### 3. Tree-Shakeable Architecture

Fastify is designed to be tree-shakeable — unused features can be excluded at bundle time. If you don't use the built-in CORS plugin, schema validator, or reply decorator, those code paths are never loaded into memory. This contrasts with Express, where the entire framework is loaded regardless of which features you use.

### 4. Radix-Tree Router

Fastify uses a **radix tree** (also called a compressed trie) for route matching instead of Express's linear array scan. Radix tree lookups are O(k) where k is the length of the URL path, making route dispatch essentially constant-time regardless of how many routes are registered.

## Benchmark Results

From the 1M RPS video benchmarks:

| Framework | Simple Route (`/simple`) | RPS |
|-----------|-------------------------|-----|
| Express | ~18,000–20,000 | Baseline |
| **Fastify** | **~66,000** | **~3.3x faster** |
| CP (custom) | ~73,000 | ~3.6x faster |

Fastify's 66,000 RPS is a dramatic improvement over Express, but it's important to note that this is still **far from 1M RPS**. The remaining gap is caused by V8's inherent overhead (JIT compilation, garbage collection, dynamic type checks) and Node.js's event loop infrastructure — limitations that no JavaScript framework can overcome.

## When to Use Fastify Over Express

| Factor | Choose Express | Choose Fastify |
|--------|---------------|----------------|
| Performance requirements | < 10K RPS | 10K–100K+ RPS |
| Team experience | Express-heavy team | Willing to learn new API |
| Ecosystem needs | Need many community middleware | Need specific, focused plugins |
| Response schema available | No / dynamic responses | Yes / stable API contracts |
| Project phase | Prototype / MVP | Production API service |

## Trade-offs

### Less Ecosystem
Fastify's plugin ecosystem is smaller than Express's middleware ecosystem. While Fastify has plugins for most common needs (CORS, JWT, Swagger, etc.), you'll find fewer third-party integrations and tutorials compared to Express.

### Stricter Schema Requirements
Fastify's performance depends on schemas. If you don't define response schemas, you lose the serialization advantage. This requires more upfront design work and makes Fastify less suitable for APIs with highly dynamic response shapes.

### Learning Curve
The hook lifecycle is more complex to understand than Express's simple `app.use()` chain. Developers must learn when each hook fires and what they can modify at each stage.

### Breaking Changes
Fastify has been more aggressive about breaking changes between major versions compared to Express (which barely changes its API). This means more maintenance work when upgrading.

## Key Insight for the 1M RPS Challenge

Fastify demonstrates that **within the constraints of Node.js and V8**, significant performance gains are possible through careful architecture. Schema-based serialization, radix-tree routing, and lifecycle hooks are all patterns that carry over to systems languages. The lesson: **pre-compute everything you can at startup, and minimize per-request work**. This philosophy is exactly what [[8.2 Drogon Framework]] and [[8.3 RapidJSON]] apply in C++.
