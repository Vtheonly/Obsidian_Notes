# Express Framework

#nodejs/express #performance/frameworks #web-development/middleware

## Definition

**Express** (often referred to as Express.js) is the most popular web application framework for Node.js. First released in 2010 by TJ Holowaychuk, it provides a thin layer of fundamental web application features without obscuring Node.js's capabilities. Express is to Node.js what Flask is to Python or Sinatra is to Ruby — a minimal, unopinionated framework that gives developers control over how they structure their applications.

## Middleware Architecture

Express's core design pattern is **middleware chaining**. Every request passes through a sequence of functions (middleware) before reaching a final response handler. Each middleware function receives three arguments: `req` (the request object), `res` (the response object), and `next` (a function to pass control to the next middleware).

```javascript
app.use((req, res, next) => {
  console.log(`${req.method} ${req.url}`);
  next(); // Pass control to the next middleware
});

app.use((req, res, next) => {
  req.timestamp = Date.now();
  next();
});

app.get('/api/data', (req, res) => {
  res.json({ timestamp: req.timestamp, data: 'hello' });
});
```

The middleware chain is processed **in order of registration**. If a middleware calls `next()`, control passes to the next registered middleware. If it doesn't (e.g., it sends a response directly), the chain stops. This pattern is powerful for composing request processing logic — logging, authentication, body parsing, error handling — in a modular way.

Internally, Express maintains an array of route and middleware handlers. For each incoming request, Express iterates through this array, matching the request's method and path against each registered handler. The path matching uses string comparison (with support for patterns like `:param` and `*` wildcards), which adds overhead compared to simpler dispatch mechanisms.

## Routing

Express provides methods for all HTTP verbs:

| Method | Use Case |
|--------|----------|
| `app.get()` | Retrieve resources |
| `app.post()` | Create resources |
| `app.put()` | Full resource replacement |
| `app.patch()` | Partial resource updates |
| `app.delete()` | Delete resources |
| `app.all()` | Match any HTTP method |

Routes can include parameters (`/users/:id`), wildcards (`/files/*`), and regular expressions. Express also supports Router objects for modular route organization.

## Why Express is SLOW

Express's performance limitations stem from several architectural decisions made during its development:

### 1. Heavy Middleware Overhead
Express's middleware chain means every request traverses multiple function calls. Each `next()` invocation adds a function call to the stack, and the framework must manage the state of the chain (tracking the current position, handling errors). Even a minimal Express app has several built-in middleware layers that process every request.

### 2. String-Based Route Matching
Express matches routes using string comparison and pattern matching. For every incoming request, it iterates through registered routes until it finds a match. This is O(n) in the number of registered routes — compared to hash-based or trie-based routing that can achieve O(1) or O(k) where k is the path length.

### 3. Deprecated and Legacy Features
Express still carries baggage from its long history. Deprecated features, backward compatibility shims, and the `req`/`res` object extensions (augmenting Node.js's native HTTP objects with additional properties) all add runtime overhead.

### 4. Object Allocation
Express creates new wrapper objects and context objects for each request. The `req` and `res` objects are extended with additional properties, which involves property lookups and object shape transitions that degrade V8's optimization capabilities.

## Benchmark Results

From the 1M RPS video benchmarks:

| Scenario | RPS |
|----------|-----|
| Simple route (`/simple`) — 1 instance | ~18,000–20,000 |
| Complex route (`/update`) — 1 instance | ~8,000 |
| Complex route (`/update`) — 12-instance cluster | ~42,000 |

A "simple route" returns a small JSON response. A "complex route" involves receiving a 30KB JSON payload, parsing it, performing some logic, and returning a 30KB JSON response. The gap between simple and complex routes (20K vs 8K) reveals how expensive JSON parsing and serialization are in Express's middleware chain.

### Express vs Raw Node.js HTTP

The raw Node.js `http.createServer()` can handle significantly more requests than Express for the same route. The overhead percentage is substantial — Express can add 30–50% latency compared to a bare HTTP server. This overhead comes from middleware dispatch, route matching, request/response object augmentation, and the framework's internal bookkeeping.

## When Express Is Appropriate

Despite its performance limitations, Express remains the right choice in many scenarios:

- **Rapid prototyping** — the fastest way to get a Node.js API up and running
- **Low-to-moderate traffic applications** — when you're serving thousands, not millions, of requests per second
- **Large ecosystem requirements** — thousands of middleware packages exist (authentication, CORS, compression, session management)
- **Team familiarity** — most Node.js developers know Express, reducing onboarding time
- **When developer productivity > raw performance** — Express trades performance for ergonomics

## Key Takeaway

Express is not slow because it's poorly written. It's slow because its design priorities — flexibility, middleware composition, backward compatibility, and developer ergonomics — inherently conflict with raw performance. Every abstraction layer, every convenience method, every backward-compatible shim adds overhead. At 1M RPS, those overheads become unacceptable. Understanding *why* Express is slow teaches you what a high-performance framework must avoid.
