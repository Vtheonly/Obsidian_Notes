# 6.1 Big O Notation

#algorithms/big-o #algorithms/complexity #fundamentals #computer-science

## Overview

Big O notation is the mathematical framework computer scientists use to describe how an algorithm's resource consumption grows as input size increases. It is the language of algorithmic efficiency — the tool you use to predict whether your code will handle 10 records, 10 million records, or 10 billion records without testing it at every scale. At 1 million requests per second, Big O is not academic theory; it is the difference between a system that works and one that catastrophically fails. This connects directly to [[1.3 The Engineering Mindset at Scale]].

---

## What Is Big O Notation?

Big O notation describes the **upper bound** of an algorithm's growth rate — specifically, how the runtime (or memory usage) scales as the input size n approaches infinity.

### Formal Definition

A function f(n) is O(g(n)) if there exist positive constants c and n₀ such that:

$$f(n) \leq c \cdot g(n) \text{ for all } n \geq n_0$$

In plain English: f(n) is Big O of g(n) if, beyond some input size n₀, f(n) never grows faster than g(n) multiplied by some constant c.

### What Big O Ignores

Big O notation deliberately drops:
- **Constants**: O(2n) = O(n). The constant factor 2 doesn't change the growth class.
- **Lower-order terms**: O(n² + n) = O(n²). The n term becomes negligible as n → ∞.
- **Specific hardware**: Big O describes the algorithm, not the machine. An O(n) algorithm on a supercomputer is still O(n).

This simplification is intentional — it focuses on the **asymptotic behavior** (what happens at very large n), which is what matters at scale.

## Best Case, Average Case, Worst Case

Big O typically describes the **worst case**, but all three cases exist:

### Example: Linear Search in an Array

```javascript
function linearSearch(arr, target) {
  for (let i = 0; i < arr.length; i++) {
    if (arr[i] === target) return i;
  }
  return -1;
}
```

| Case | Scenario | Complexity |
|---|---|---|
| **Best case** | Target is at index 0 | O(1) — one comparison |
| **Average case** | Target is somewhere in the middle | O(n/2) = O(n) |
| **Worst case** | Target is not in the array | O(n) — must check every element |

### Convention

When people say "this algorithm is O(n)," they usually mean **worst-case O(n)** unless specified otherwise. For [[6.2 O(n) Linear Time]] analysis in database queries, we focus on worst case because that determines your system's performance ceiling.

## Time Complexity vs. Space Complexity

Big O applies to both time and memory:

- **Time complexity**: How many operations the algorithm performs as a function of input size.
- **Space complexity**: How much additional memory the algorithm allocates as a function of input size.

Example: Merge sort is O(n log n) time but O(n) space (needs a temporary array). Quick sort is O(n log n) average time but O(log n) space (recursive call stack). Both are acceptable trade-offs — but at 1M RPS, both time and space matter because memory allocation triggers garbage collection.

---

## Why Big O Matters at Scale

The difference between O(n) and O(log n) is barely noticeable at n = 100. At n = 10 million, it is the difference between a system that works and one that crashes.

### Concrete Example

| Operation | Complexity | n = 10,000 | n = 1,000,000 | n = 100,000,000 |
|---|---|---|---|---|
| Indexed lookup | O(log n) | 13 steps | 20 steps | 27 steps |
| Full table scan | O(n) | 10,000 steps | 1,000,000 steps | 100,000,000 steps |

At 1M RPS, an O(n) operation that takes 43 seconds (as shown in the video for [[10.3 SELECT with ORDER BY RANDOM]]) means:
- **43 seconds per request** — utterly useless
- You would need **43 million seconds** (498 days) to serve 1M requests
- You would need **1 million servers** to serve them in 1 second (impractical)

Meanwhile, the same operation at O(1) or O(log n):
- **40ms per request** — 25 requests per second per thread
- With 12 threads: **300 requests per second per server**
- With caching (O(1)): **400,000+ RPS** per server

This 1,000× difference is why algorithm choice is the single most impactful optimization at scale.

## How to Analyze Big O

### Step 1: Identify the Input
What is n? (array length, number of rows, string length, etc.)

### Step 2: Count Operations as a Function of n
- Single loop over n → O(n)
- Nested loop → O(n²)
- Loop that halves n each iteration → O(log n)
- No dependency on n → O(1)

### Step 3: Drop Constants and Lower-Order Terms
- O(3n² + 7n + 42) → O(n²)
- O(500) → O(1)

### Step 4: Consider All Branches
- If one branch is O(n) and another is O(1), worst case is O(n).
- If execution alternates, use the dominant complexity.

---

## Common Mistakes

- **Ignoring constants for small n**: At n = 10, O(n²) might be faster than O(n log n) due to constant factors. Big O is about large n.
- **Confusing average case with worst case**: "Binary search is O(1) on average" — no, it's O(log n) in the worst case (and average).
- **Forgetting about space complexity**: An algorithm that's fast but uses O(n²) memory will crash on large inputs.
- **Not considering real-world factors**: Big O ignores cache effects, branch prediction, and pipeline stalls. In practice, O(n) algorithms can be faster than O(log n) ones for small n due to spatial locality.
