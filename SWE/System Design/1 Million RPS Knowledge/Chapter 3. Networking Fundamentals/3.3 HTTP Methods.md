# HTTP Methods

#networking/http #fundamentals/api #performance/methods

## What Are HTTP Methods?

HTTP methods (also called HTTP verbs) define the **action** the client wants to perform on a resource. They are part of the request line in every HTTP request and determine the semantics of the interaction: should the server retrieve data? Create it? Update it? Delete it?

The correct use of HTTP methods is not merely a convention—it has **direct performance implications** at scale. Caching infrastructure, CDNs, proxies, and load balancers all make decisions based on the HTTP method. A GET request can be cached; a POST request cannot. Using the wrong method can disable caching and force every request to hit your origin servers.

## The Five Core Methods

### GET — Retrieve Data

The GET method requests a **representation** of the specified resource. The server should return the current state of the resource without modifying it.

**Key properties:**
- **Idempotent**: Making the same GET request multiple times produces the same result (assuming the resource hasn't changed). This enables safe retries.
- **Cacheable**: GET responses can be cached by browsers, CDNs, and proxies. This is the single most important performance property of any HTTP method at scale.
- **No request body**: The URL itself carries all the information. Parameters are sent via query strings (`?key=value&key2=value2`).
- **Safe**: Does not modify server state.

Example:
```
GET /api/users/123 HTTP/1.1
Host: api.example.com
Accept: application/json
```

**Performance impact**: Because GET is cacheable, a well-designed API that uses GET for read operations can serve the vast majority of requests from cache, reducing origin server load by orders of magnitude. At 1M RPS, if 90% of requests are cacheable GETs, your origin servers only need to handle 100K RPS.

### POST — Create Data

The POST method submits data to the server, typically for **creating a new resource** or triggering an action.

**Key properties:**
- **Not idempotent**: Making the same POST request twice may create two resources. Submitting a form twice might create two orders.
- **Not cacheable**: POST responses are not cached by default (though they can be with explicit `Cache-Control` headers, this is rare).
- **Has a request body**: The data being created or the action parameters are sent in the body.

Example:
```
POST /api/users HTTP/1.1
Host: api.example.com
Content-Type: application/json
Content-Length: 45

{"name":"Alice","email":"alice@example.com"}
```

**Performance impact**: POST requests always hit the origin server (no caching) and typically require database writes (see [[2.4 RAM vs Disk vs Network Speeds]]). At 1M RPS, if all requests are POSTs, you cannot use HTTP-level caching and must rely on database-level caching and replication.

### PUT — Replace Data

The PUT method replaces the **entire** resource at the specified URI with the provided data. If the resource does not exist, it may be created.

**Key properties:**
- **Idempotent**: Sending the same PUT request multiple times produces the same result. The resource is in the same state regardless of how many times the PUT is applied.
- **Not cacheable** (for requests; responses may be cached).
- **Has a request body**: Contains the complete replacement for the resource.

Example:
```
PUT /api/users/123 HTTP/1.1
Host: api.example.com
Content-Type: application/json
Content-Length: 56

{"name":"Alice Updated","email":"alice.new@example.com"}
```

### PATCH — Partial Update

The PATCH method applies **partial modifications** to a resource. Unlike PUT, which replaces the entire resource, PATCH only changes the specified fields.

**Key properties:**
- **Not necessarily idempotent**: Depends on the implementation. A PATCH that increments a counter is not idempotent; a PATCH that sets a field to a specific value is idempotent.
- **Not cacheable**.
- **Has a request body**: Contains only the fields to be modified, often in JSON Patch or JSON Merge Patch format.

Example:
```
PATCH /api/users/123 HTTP/1.1
Host: api.example.com
Content-Type: application/json
Content-Length: 28

{"email":"alice.updated@example.com"}
```

**Performance impact**: PATCH can be more efficient than PUT because it sends less data over the network. At 1M RPS, if each request is 500 bytes (PUT) vs. 50 bytes (PATCH), the bandwidth difference is 450 MB/s—a significant saving on a 10 Gbps link.

### DELETE — Remove Data

The DELETE method removes the specified resource.

**Key properties:**
- **Idempotent**: Deleting a resource that has already been deleted returns the same result (typically 404 or 204).
- **Not cacheable**.
- **No request body** (by convention; some APIs allow body for bulk deletes).

Example:
```
DELETE /api/users/123 HTTP/1.1
Host: api.example.com
```

## HTTP Methods and CRUD

HTTP methods map naturally to CRUD (Create, Read, Update, Delete) operations:

| CRUD Operation | HTTP Method | Idempotent | Cacheable | Has Body |
|----------------|-------------|------------|-----------|----------|
| **Create**     | POST        | No         | No        | Yes      |
| **Read**       | GET         | Yes        | Yes       | No       |
| **Update** (full) | PUT     | Yes        | No        | Yes      |
| **Update** (partial) | PATCH | Maybe    | No        | Yes      |
| **Delete**     | DELETE      | Yes        | No        | No       |

## Why Method Choice Affects Caching and Performance

The impact of HTTP method choice on system performance scales dramatically:

1. **Cache hit ratio**: GET requests that hit a CDN cache consume zero origin server resources. POST requests always reach the origin. If an API redesign can convert 50% of POST requests to GETs (by making operations idempotent and query-based), the origin server load drops by 50%.

2. **Network bandwidth**: Methods without bodies (GET, DELETE) send less data. At 1M RPS, eliminating a 500-byte request body saves 500 MB/s of bandwidth.

3. **Retry safety**: Idempotent methods (GET, PUT, DELETE) can be safely retried by clients, proxies, and load balancers without causing unintended side effects. Non-idempotent methods (POST, some PATCH) require careful retry logic with deduplication.

4. **TCP connection behavior**: GET requests typically generate small requests and potentially large responses. POST requests often have large request bodies. This affects TCP buffer sizing and congestion window behavior.

## Common Mistakes

1. **Using POST for everything.** This disables caching, prevents safe retries, and makes the API harder to reason about. Use GET for reads, POST for creates.
2. **Using GET with side effects.** A GET request that modifies server state (e.g., `GET /api/users/123/delete`) violates HTTP semantics and can be triggered by pre-fetching crawlers, browser prefetch, and proxy caches.
3. **Ignoring PATCH.** Sending a full PUT when only one field changed wastes bandwidth and can cause race conditions when multiple clients update different fields of the same resource simultaneously.
