## What Is JSON?

**JSON (JavaScript Object Notation)** is a lightweight, text-based data interchange format derived from JavaScript object literal syntax. Defined in RFC 8259, JSON has become the **de facto standard** for web APIs, configuration files, and data exchange between services. Its ubiquity in modern software is nearly absolute: REST APIs, NoSQL databases (MongoDB, CouchDB), configuration files (package.json, tsconfig.json), and log formats all use JSON.

A JSON document is built from two fundamental structures:
- **Objects**: Unordered collections of key-value pairs, enclosed in curly braces: `{"key": "value"}`
- **Arrays**: Ordered lists of values, enclosed in square brackets: `[1, 2, 3]`

Values can be strings, numbers, booleans, null, objects, or arrays—enabling arbitrary nesting:

```json
{
  "userId": 123,
  "name": "Alice",
  "email": "alice@example.com",
  "active": true,
  "roles": ["admin", "editor"],
  "address": {
    "city": "San Francisco",
    "state": "CA",
    "zip": "94105"
  }
}
```

## Why JSON Dominates Web APIs

JSON's dominance is not accidental—it results from a combination of practical advantages:

1. **Human-readable**: Unlike binary formats, JSON can be read and written by humans without special tools. This dramatically speeds up development and debugging.
2. **Language-agnostic**: Every modern programming language has built-in or library-based JSON support. Parsing JSON in Python, Go, Java, or Rust is trivial.
3. **Self-describing**: Keys in JSON objects serve as field names, making the data structure implicit in the data itself. No external schema is required (though JSON Schema exists for validation).
4. **Browser-native**: `JSON.parse()` and `JSON.stringify()` are built into every web browser, making it the natural choice for web APIs.
5. **Flexible schema**: Adding new fields to a JSON object does not break existing parsers that ignore unknown keys. This enables backward-compatible API evolution.

## The Serialization/Deserialization Overhead

At normal scale, JSON parsing is "fast enough." At 1 million requests per second, **JSON serialization/deserialization is one of the most expensive operations in the request path.**

Consider a typical request lifecycle at 1M RPS:
1. Receive HTTP request with JSON body (~10 μs for TCP + HTTP parsing)
2. **Parse JSON into internal data structures (~5-50 μs depending on size and parser)**
3. Execute business logic (~1-100 μs)
4. **Serialize response data into JSON (~5-50 μs)**
5. Send HTTP response (~10 μs)

JSON parsing and serialization can consume **30-80% of the total per-request processing time**, especially for smaller payloads where the fixed overhead dominates.

### Why JSON Parsing Is Expensive

1. **String scanning**: The parser must scan every character of the input, checking for structural characters (`{`, `}`, `[`, `]`, `:`, `,`) and escape sequences.
2. **String allocation**: Each JSON string value requires allocating a new string in the target language's memory. For an object with 10 string fields, that is 10 heap allocations.
3. **Number parsing**: Converting JSON number strings to native numeric types (integer, float, double) requires string-to-number conversion, which involves character-by-character parsing and bounds checking.
4. **UTF-8 validation**: RFC 8259 requires that JSON text be valid UTF-8. Parsers must validate encoding, which requires examining every byte.
5. **Memory allocation and garbage collection**: The parsed object tree lives on the heap. In garbage-collected languages (Java, Go, Node.js), these objects increase GC pressure. At 1M RPS, that is 1 million temporary object allocations per second—each of which must eventually be collected.

## Alternatives to JSON

When JSON's performance overhead becomes unacceptable, several alternatives exist:

| Format | Type | Size vs JSON | Parse Speed vs JSON | Use Case |
|--------|------|--------------|---------------------|----------|
| **MessagePack** | Binary | ~50-70% | 2-5x faster | High-performance internal APIs |
| **Protocol Buffers (Protobuf)** | Binary | ~30-50% | 5-10x faster | gRPC, structured data with schemas |
| **CBOR** | Binary | ~60-80% | 2-3x faster | IoT, constrained environments |
| **XML** | Text | ~150-200% | 5-10x slower | Legacy systems, SOAP |
| **FlatBuffers** | Binary | ~30-50% | 10-20x faster (zero-copy) | Gaming, real-time systems |

### Protocol Buffers (Protobuf)

Protobuf requires a schema definition (`.proto` file) that is compiled into code for each target language. This pre-compilation enables extremely fast serialization and deserialization because the parser knows the exact structure beforehand—no string scanning or dynamic allocation needed.

### MessagePack

MessagePack is a binary serialization format that is essentially "binary JSON." It maintains JSON's data model (objects, arrays, strings, numbers, booleans, null) but encodes values in compact binary rather than verbose text. It is a popular choice when you want JSON-like flexibility with better performance.

## JSON Parsing Performance: RapidJSON vs. Built-in Parsers

The performance gap between JSON parsers is enormous:

| Parser | Language | Throughput (MB/s) | Relative Speed |
|--------|----------|--------------------|----------------|
| `JSON.parse()` | Node.js (V8) | ~200-400 MB/s | 1x (baseline) |
| `json.Unmarshal()` | Go | ~300-500 MB/s | 1-1.5x |
| `Jackson` | Java | ~500-800 MB/s | 2-3x |
| `simdjson` | C++ (SIMD) | ~3,000+ MB/s | 10-15x |
| **RapidJSON** | **C++** | **~1,500+ MB/s** | **5-8x** |
| `serde_json` | Rust | ~500-800 MB/s | 2-3x |

**RapidJSON** is a C++ JSON parser that exploits modern CPU features (SIMD instructions, cache-friendly access patterns) to achieve parsing speeds 5-8x faster than Node.js's built-in `JSON.parse()`. At 1M RPS with 500-byte JSON payloads, RapidJSON could process the entire stream on a single core, while Node.js might require 5-8 cores just for JSON parsing.

**simdjson** goes even further, using SIMD (Single Instruction, Multiple Data) CPU instructions to parse multiple characters simultaneously. It can parse JSON at over 3 GB/s—approaching the speed of a RAM read.

### Connection to [[8.3 RapidJSON]]

The choice of JSON parser can be the difference between a system that handles 1M RPS and one that cannot. When building the fastest possible HTTP server (as explored in the 1 Million RPS course), switching from a built-in parser to RapidJSON or simdjson is one of the highest-impact optimizations available. ## Content-Type Header

When sending JSON over HTTP, the `Content-Type` header must be set to `application/json`:

```
Content-Type: application/json
```

This header tells the client how to interpret the response body and enables proper content negotiation. Omitting it or using an incorrect value (e.g., `text/plain`) can cause browsers and API clients to mishandle the response.

## Practical Tips for JSON at Scale

1. **Minimize field count and nesting.** Each field adds parsing time and memory allocation. Flatten nested objects where possible.
2. **Use short key names in hot paths.** The key `"u"` is parsed faster than `"userId"` because there are fewer characters to compare.
3. **Consider binary formats for internal service-to-service communication.** Keep JSON only for external APIs where human readability matters.
4. **Pre-allocate buffers.** In languages like C++ and Rust, pre-allocating the output buffer for serialization avoids repeated reallocation.
5. **Avoid unnecessary serialization.** If both the producer and consumer are in the same process (or same language), consider passing in-memory data structures directly instead of serializing to JSON and back.
