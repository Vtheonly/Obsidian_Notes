# Memory Management

#cpp/memory #performance/memory #fundamentals/computer-science

## Overview

Memory management is the single most impactful factor in achieving 1M RPS. At 1 million requests per second with 30KB JSON payloads, your server moves **30 gigabytes of data per second**. How that memory is allocated, used, and freed determines whether you succeed or fail. This note covers memory management from fundamentals to the specific strategies used in [[8.2 Drogon Framework]] and [[8.3 RapidJSON]].

## Stack vs Heap Memory

### Stack Memory
The stack is a contiguous region of memory managed automatically by the CPU. When a function is called, its local variables are pushed onto the stack. When the function returns, they are popped. Stack allocation is essentially **free** — it's just incrementing/decrementing a pointer (the stack pointer register).

| Property | Stack | Heap |
|----------|-------|------|
| **Allocation speed** | ~1 nanosecond (pointer increment) | ~50–500 nanoseconds (malloc/search) |
| **Deallocation speed** | ~1 nanosecond (pointer decrement) | ~50–500 nanoseconds (free/coalesce) |
| **Lifetime** | Automatic (function scope) | Manual or GC |
| **Size** | Limited (~1–8 MB per thread) | Virtually unlimited (physical RAM) |
| **Cache locality** | Excellent (sequential) | Poor (scattered) |
| **Fragmentation** | None | Yes (external fragmentation) |
| **Thread safety** | Each thread has its own stack | Shared, requires synchronization |

### Heap Memory
Heap memory is allocated dynamically at runtime using `malloc`/`new` (C/C++) or automatically by the runtime (Java, Go, Node.js). The allocator must search for a free block of appropriate size, track allocations, and eventually free and coalesce blocks. This is expensive.

**Rule of thumb at 1M RPS:** If you can allocate on the stack, do it. Every heap allocation is a potential bottleneck.

## Garbage Collection

### How GC Works

Most high-level languages use garbage collection to automatically free memory that is no longer referenced. The most common GC algorithms:

**Mark-and-Sweep:**
1. **Mark phase:** Traverse all reachable objects from root references (stack, global variables)
2. **Sweep phase:** Free all objects not marked as reachable

**Generational GC (used by V8/Node.js, JVM):**
- Objects are divided into "young" (newly allocated) and "old" (survived multiple GC cycles) generations
- Young generation is collected frequently (minor GC, fast, few objects)
- Objects that survive several minor GCs are promoted to old generation
- Old generation is collected infrequently (major GC, slow, many objects)

**Tri-color Mark-and-Sweep (used by Go):**
- Objects are colored white (unvisited), gray (visited, children not scanned), black (fully scanned)
- GC runs concurrently with the application, but requires brief "stop-the-world" pauses for certain phases

### Why GC Is a Problem at 1M RPS

| GC Type | Typical Pause Duration | At 1M RPS, Requests Affected |
|---------|----------------------|------------------------------|
| Minor (V8) | 1–10 ms | 1,000–10,000 |
| Major (V8) | 10–100 ms | 10,000–100,000 |
| G1GC (Java) | 1–50 ms | 1,000–50,000 |
| ZGC (Java) | <1 ms | <1,000 |
| Go concurrent | 100–500 μs | 100–500 |

Even the best GC (Java ZGC) adds ~1ms of latency to 1,000 requests every time it runs. At P99 latency requirements, these pauses are the difference between meeting and missing SLAs.

### Allocation Pressure Amplifies GC

The more you allocate, the harder the GC works. At 1M RPS with 30KB JSON:

```
Node.js: JSON.parse() creates thousands of small objects
→ High allocation rate → Frequent GC → Latency spikes

C++ (RapidJSON): In-situ parsing modifies buffer in place
→ Near-zero allocation → No GC → Consistent latency
```

## Manual Memory Management in C++

### Raw Pointers (Legacy)
```cpp
char* buffer = new char[30720];  // Allocate
// ... use buffer ...
delete[] buffer;  // Must remember to free!
```
**Danger:** Forgetting to `delete` → memory leak. Double `delete` → undefined behavior. Accessing after `delete` → use-after-free. These bugs are catastrophic in long-running servers.

### Smart Pointers (Modern C++)
```cpp
// unique_ptr: exclusive ownership, freed when out of scope
auto buffer = std::make_unique<char[]>(30720);

// shared_ptr: shared ownership, reference counted
auto data = std::make_shared<JsonDocument>();
```
**Advantage:** RAII guarantees deallocation when the pointer goes out of scope — even if exceptions are thrown. Zero overhead compared to raw pointers when using `unique_ptr`. Small overhead for `shared_ptr` (atomic reference count increments).

## Memory Pools

A memory pool pre-allocates a large block of memory and sub-allocates from it:

```cpp
class MemoryPool {
    char* buffer_;
    size_t offset_;
    static constexpr size_t POOL_SIZE = 1024 * 1024; // 1MB
public:
    MemoryPool() : buffer_(new char[POOL_SIZE]), offset_(0) {}
    
    void* allocate(size_t size) {
        void* ptr = buffer_ + offset_;
        offset_ += size;
        return ptr;  // O(1) — just bump a pointer!
    }
    
    ~MemoryPool() { delete[] buffer_; }  // One free for the entire pool
};
```

**Performance impact:** Allocation drops from ~50–500ns (malloc) to ~1–2ns (pointer bump). Deallocation drops from ~50–500ns to **zero** (the entire pool is freed at once). This is the strategy [[8.3 RapidJSON]] uses with its `MemoryPoolAllocator`.

## Buffer Reuse

Creating a new buffer for every request is expensive — even with memory pools, you pay for cache misses when the buffer is freshly allocated (the memory is cold — not in L1/L2 cache). The solution: **reuse buffers across requests.**

```cpp
thread_local std::vector<char> reusableBuffer(30720);

void handleRequest(Request& req, Response& res) {
    // Buffer is already allocated and likely in cache
    // Just overwrite it — zero allocation
    req.readBody(reusableBuffer.data(), reusableBuffer.size());
    // ... parse, process, respond ...
}
```

Using `thread_local` ensures each thread has its own buffer, eliminating the need for synchronization. The buffer stays "hot" in the CPU cache across requests, providing consistent sub-microsecond access times.

## Memory Fragmentation

Over time, repeated allocations and deallocations of varying sizes cause **external fragmentation** — the heap has enough total free memory, but not in a contiguous block large enough for the next allocation. This forces the allocator to request more memory from the OS (via `brk`/`mmap`), increasing the process's virtual memory footprint and reducing cache efficiency.

**Symptoms in long-running servers:**
- Gradually increasing memory usage (even with no leaks)
- Increasing P99 latency (larger heaps → more cache misses)
- Occasional allocation failures despite having "free" memory

**Solutions:**
- **Memory pools** — allocate from fixed-size blocks, eliminate fragmentation
- **Arena allocators** — allocate from a contiguous region, reset periodically
- **Object pools** — pre-allocate objects, reuse via free list
- **Restart periodically** — the "nuclear option" that many Java/Node.js deployments use

## How Drogon and RapidJSON Minimize Allocations

| Technique | Used By | Effect |
|-----------|---------|--------|
| Stack-allocated request/response objects | Drogon | Zero heap allocation for HTTP metadata |
| In-situ JSON parsing | RapidJSON | Zero allocation for string data |
| Memory pool allocator | RapidJSON | O(1) allocation, O(1) deallocation |
| `std::string_view` (non-owning reference) | Drogon | Pass strings without copying |
| Pre-allocated response buffers | Drogon | Reuse buffers across requests |
| `thread_local` buffers | Drogon | Thread-safe without locks, cache-hot |
| SIMD-optimized parsing | RapidJSON | Fewer instructions = fewer intermediate values = fewer allocations |

## The Grand Equation

At 1M RPS:
- **Per-request allocation budget: ~0** (ideally)
- Every `malloc`/`new`/`GC allocation` is amplified 1 million times
- A 100ns allocation × 1M RPS = 100ms of CPU time per second (10% of a core) **just for allocation**
- C++ with pools and in-situ parsing: ~1ns per request allocation overhead = 1ms of CPU time per second (0.1% of a core)

This 100x difference in allocation overhead is why [[8.1 C++ for High Performance]] was necessary and why [[8.5 Memory Management]] is the most important systems engineering topic for high-throughput servers.
