# 04.08 — Gateway Design Constraints

> [!abstract] The Same-Subnet Rule
> A host's **default gateway** must reside in the **same subnet** as the host itself. If it doesn't, the host can't ARP-resolve the gateway, can't send packets off-subnet, and appears "offline" to the outside world even though local subnet traffic works fine. This is one of the most common — and most easily missed — configuration errors.

---

##  The Rule

For host `H` with IP `H.IP/Prefix` and configured gateway `G.IP`:

$$H.\text{IP} \text{ AND } H.\text{mask} = G.\text{IP} \text{ AND } H.\text{mask}$$

In words: bitwise-ANDing the host IP with its own mask must yield the **same subnet ID** as bitwise-ANDing the gateway IP with the host's mask. If the two subnet IDs differ, the gateway is in a different subnet, and the configuration is invalid.

---

##  Worked Example

**Given host configuration:**
- Host IP: `143.27.172.101/18`
- Configured gateway: `143.27.105.1`

**Question:** Is this configuration valid?

### Step 1: Compute the host's subnet

Mask `/18` = `255.255.192.0` (third octet `192` = `11000000`, so the third octet has 2 network bits and 6 host bits).

| Octet | Host IP | Mask | Subnet bits |
| :-: | :-: | :-: | :-: |
| 1 | 143 | 255 | 143 |
| 2 | 27 | 255 | 27 |
| 3 | 172 = `10101100` | 192 = `11000000` | `10000000` = 128 |
| 4 | 101 | 0 | 0 |

**Host's subnet: `143.27.128.0/18`**.
Usable range: `143.27.128.1` to `143.27.191.254`.
Broadcast: `143.27.191.255`.

### Step 2: Check if gateway is in this subnet

Gateway IP: `143.27.105.1`. Is `143.27.105.1` in `143.27.128.0/18`?

Third octet `105` = `01101001`. With mask `11000000`, the subnet bits are `01000000` = `64`. So gateway is in subnet `143.27.64.0/18` (range `143.27.64.1` to `143.27.127.254`).

### Conclusion

- Host is in `143.27.128.0/18`.
- Gateway is in `143.27.64.0/18`.
- **Different subnets → configuration INVALID.**

The host would attempt to ARP for `143.27.105.1`, but no router on its local segment would have that IP, so the ARP would fail, and the host would be unable to send any traffic off-subnet.

> [!example] Fix
> Either:
> - Change the gateway to an IP in `143.27.128.0/18` (e.g., `143.27.128.1`), **or**
> - Change the host's IP to be in the same subnet as `143.27.105.1` (e.g., `143.27.105.101/18`).

##  IP Allocation Best Practices for Gateways

Within a subnet, two conventions dominate for assigning the gateway IP:

1. **First usable IP** (e.g., `.1`) — most common in home networks and SMB. Example: subnet `192.168.1.0/24`, gateway `192.168.1.1`.
2. **Last usable IP** (e.g., `.254`) — common in larger enterprises and ISPs. Example: subnet `10.0.0.0/24`, gateway `10.0.0.254`.

The reason for the second convention: human users tend to pick low IPs (`192.168.1.5`, `192.168.1.10`, etc.) for servers and printers. By reserving the top of the range for network infrastructure (gateway, HSRP/VRRP VIP, switch management), you avoid collisions.

> [!tip] HSRP/VRRP VIP allocation
> In redundant gateway designs, you typically have:
> - Physical gateway 1: `192.168.1.2`
> - Physical gateway 2: `192.168.1.3`
> - Virtual VIP (HSRP/VRRP): `192.168.1.1`
>
> Hosts point to `.1` as their gateway. If gateway 1 fails, gateway 2 takes over the `.1` MAC via VRRP/HSRP and traffic continues. This is invisible to end hosts.

##  Diagnostic — "Host Can't Reach the Internet"

When a single host can't reach the internet but others on the same subnet can, walk this checklist:

1. **`ipconfig` / `ip addr`** — confirm the host's IP, mask, and gateway are what you expect.
2. **Compute host's subnet** — `IP AND mask`.
3. **Compute gateway's subnet** — `gateway IP AND host's mask`.
4. **Compare** — they must match. If not, the gateway config is wrong.
5. **Ping the gateway** — if step 4 passes but ping fails, the gateway is down or there's a cable/switch issue.
6. **Ping 8.8.8.8** — if gateway ping works but this fails, the gateway isn't routing or your ISP is down.
7. **Ping 8.8.8.8 with `ping -n 8.8.8.8` (or `nslookup google.com`)** — if step 6 works but DNS fails, the DNS server config is wrong.

The "same subnet" rule catches step 4. It's worth automating — a 10-line Python script can validate every host config in a DHCP scope.
