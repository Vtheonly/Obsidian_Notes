# 11.08 — FTP & TFTP

> [!abstract> Two File Transfer Protocols
> **FTP (File Transfer Protocol)** is the classic internet file-transfer protocol — feature-rich but complex, with separate control and data channels. **TFTP (Trivial File Transfer Protocol)** is its tiny cousin — minimal, lockstep, used for PXE boot and embedded device config. Both are still in production, though both have largely been replaced by SFTP/HTTPS for new deployments.

---

##  FTP (File Transfer Protocol, RFC 959)

| Property | Value |
| :--- | :--- |
| Ports | 21 (control), 20 (active mode data) |
| Transport | TCP |
| Style | Command-response on control channel; data channel opens per transfer |

FTP uses **two TCP connections**:
- **Control channel** (port 21): commands like `USER`, `PASS`, `LIST`, `RETR`, `STOR`. Stays open for the whole session.
- **Data channel** (port 20 or high port): actual file content and directory listings. Opened fresh for each transfer.

### Active vs Passive Mode

The two modes differ in **who initiates the data connection**:

#### Active Mode
```
Client (random port N) → Server:21 (control)
Server:20 → Client:N+1 (data, server initiates)
```
- Client sends `PORT N+1` command telling the server "I'll listen on port N+1 for data".
- Server connects *from* port 20 *to* the client's port N+1.
- **Problem:** client-side firewalls/NAT block incoming connections. Active mode rarely works behind a home router.

#### Passive Mode
```
Client (random port N) → Server:21 (control)
Client (random port M) → Server:random port P (data, client initiates)
```
- Client sends `PASV` command.
- Server replies "I'll listen on port P for data".
- Client connects *from* a random port *to* the server's port P.
- **Works behind client-side NAT/firewall** (the client initiates both connections).
- Default mode in modern FTP clients.

> [!info] Why passive mode is the default
> Most clients are behind NAT. Active mode requires the server to connect back to the client, which NAT blocks. Passive mode has the client initiate both connections, which NAT allows.

### FTP Commands

```
USER alice              # username
PASS secret             # password
SYST                    # query server OS
PWD                     # print working directory
CWD /pub                # change directory
PASV                    # enter passive mode
LIST                    # list directory
RETR file.txt           # download file
STOR file.txt           # upload file
DELE file.txt           # delete file
MKD newdir              # make directory
QUIT                    # close session
```

### FTP Security
- **Plain FTP** sends passwords in clear text. Don't use on the public internet.
- **FTPS (FTP over SSL/TLS)** — RFC 4217 — adds TLS to FTP. Two flavors: explicit (STARTTLS upgrade on port 21) and implicit (TLS from the start on port 990).
- **SFTP (SSH File Transfer Protocol)** — completely different protocol, runs over SSH on port 22. Despite the name, it's not FTP at all. Often confused with FTPS.

##  TFTP (Trivial File Transfer Protocol, RFC 1350)

| Property | Value |
| :--- | :--- |
| Port | 69 |
| Transport | UDP |
| Style | Lockstep, no auth, no directory listing |

TFTP is intentionally minimal:
- **No authentication** — anyone can read/write (subject to file permissions).
- **No directory listing** — you must know the exact filename.
- **No subdirectories navigation** — paths are flat (though `/path/to/file` syntax works).
- **UDP transport** — uses lockstep ACKs to ensure reliability.
- **Tiny implementation** — fits in ROM, used by diskless workstations and network boot.

### TFTP Use Cases
1. **PXE boot** — diskless workstations fetch their bootloader and OS image via TFTP.
2. **Network device config save/restore** — Cisco routers/switches can `copy running-config tftp:`.
3. **Firmware updates** — some embedded devices fetch firmware over TFTP.
4. **VoIP phone bootstrapping** — IP phones load their config and firmware via TFTP.

### TFTP Protocol
- Client sends `RRQ` (read request) or `WRQ` (write request) to server port 69.
- Server replies from a random port with `DATA` (block 1, up to 512 bytes).
- Client ACKs each block; server sends the next.
- A block smaller than 512 bytes signals end of file.

The lockstep nature (one block in flight at a time) makes TFTP slow but very simple.

##  FTP vs TFTP vs SFTP vs FTPS

| Protocol | Transport | Auth | Encrypted | Use |
| :--- | :-: | :-: | :-: | :--- |
| FTP | TCP | Yes | No | Legacy file transfer |
| FTPS | TCP | Yes | Yes (TLS) | Secure FTP |
| SFTP | TCP (SSH) | Yes (SSH) | Yes (SSH) | Modern secure file transfer |
| TFTP | UDP | No | No | PXE boot, device config |

For new deployments, **SFTP** is almost always the right choice. It's secure, simple (one port, one connection), and supported everywhere.
