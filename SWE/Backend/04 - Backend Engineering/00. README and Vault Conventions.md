# README and Vault Conventions

> [!important] Read this first
> This file defines the **non-negotiable** conventions for the entire Backend Engineering vault. Every note in every chapter follows these rules. If you add a new note, follow these rules. If you edit an existing note, do not break them.

---

## 1. Audience and Purpose

This vault is a **personal long-term knowledge base** for backend engineering. It is not a tutorial, not a textbook, and not a public-facing reference. The audience is the author — someone who knows the basics but routinely forgets the details, the exact directive name, the precise default behavior, or the subtle gotcha that bites in production.

Every note is therefore written to satisfy three goals simultaneously:

1. **Self-contained reading.** A note must be understandable without leaving the page. Background knowledge that the author "should" remember is restated briefly, not assumed.
2. **Exhaustive correctness.** Every claim is either self-evident from the code on the page or accompanied by the reasoning. No "trust me" statements.
3. **Production realism.** Examples are written the way they would appear in a real codebase — with error handling, security considerations, and the trade-offs that drove the choice.

## 2. File Naming

| Rule | Correct | Wrong |
| ---- | ------- | ----- |
| Folders and files start with a number. | `01. Backend Fundamentals/` | `Backend Fundamentals/` |
| Number is followed by a period and a space. | `1.1. HTTP Protocol.md` | `1.1_HTTP_Protocol.md` |
| No underscores anywhere. | `3.2.1. Introduction to Flask.md` | `3.2.1_Intro_to_Flask.md` |
| Title uses Title Case. | `Cookies and Session Management` | `cookies and session management` |
| File extension is `.md`. | `…Management.md` | `…Management.markdown` |

Numbering scheme:

- **Chapter folders**: `NN. Chapter Name` (e.g., `02. Databases`).
- **Notes in a chapter**: `N.X. Note Title` (e.g., `2.3. MySQL Engine Internals.md`).
- **Notes in a framework sub-folder**: `N.M.K. Note Title` (e.g., `3.2.10. Sessions and Cookies in Flask.md`).
- **Chapter index**: `N.0. Chapter Index.md` — always the first file in the chapter.

## 3. Note Structure

Every note follows this skeleton:

```markdown
---
tags: [Tag1, Tag2, Tag3]
---

# Note Title

> [!info] One-paragraph orientation.
> What this note covers and why it matters.

## 1. First Major Section
...

## 2. Second Major Section
...

## Summary
A 3–5 sentence wrap-up.

## See Also
- [[Related Note 1]]
- [[Related Note 2]]

## References
- Official docs, spec, or book citation.
```

Numbered section headings (`## 1.`, `## 2.`) are preferred because they make the note's structure scannable in Obsidian's outline pane. They also survive copy-paste into other tools better than bulleted headings.

## 4. Diagrams — Mermaid Only

> [!warning] No raw ASCII diagrams
> This is repeated five times in the source brief because the author has a strong preference. **Do not** use Unicode box-drawing characters (the double-line and single-line corner / tee / cross / horizontal / vertical glyphs commonly used to draw boxes and trees in plain text) to draw diagrams.

Allowed diagram types and when to use them:

| Diagram type | Use case | Example |
| ------------ | -------- | ------- |
| `graph TD` / `graph LR` | Component relationships, request flow, folder structures. | Request → Nginx → PHP-FPM → MySQL |
| `sequenceDiagram` | Time-ordered interactions between actors. | OAuth flow, TCP handshake, JWT verification. |
| `flowchart TD` | Decision trees with branching logic. | "Should I use Docker or Apache for PHP?" |
| `classDiagram` | Object models, ORM class hierarchies. | SQLAlchemy `Base` → `User` → `Post`. |
| `stateDiagram-v2` | State machines. | HTTP connection states, session lifecycle. |
| `erDiagram` | Entity relationships. | User–Post–Comment schema. |

Tables are **not** considered diagrams — use Markdown tables freely.

## 5. Code Blocks

- Always specify the language: ` ```bash `, ` ```python `, ` ```php `, ` ```sql `, ` ```http `, ` ```nginx `, etc.
- Inline code uses single backticks: `` `php -S localhost:8000` ``.
- Long command output is wrapped in its own block, separated from the command:
  ```bash
  sudo systemctl status apache2
  ```
  ```text
  ● apache2.service - The Apache HTTP Server
       Loaded: loaded (/lib/systemd/system/apache2.service; enabled)
       Active: active (running) since ...
  ```
- Shell prompts (`$`, `#`) are omitted unless the prompt itself is meaningful (e.g., `mysql>` to show a MySQL REPL).

## 6. Tags

Tags are flat (no nested `parent/child` tags). Every note has 3–7 tags. The first tag is always the chapter or technology (e.g., `PHP`, `Flask`, `PostgreSQL`, `Docker`). The remaining tags describe the note's concepts (e.g., `Middleware`, `Transactions`, `JWT`).

---

## 7. Cross-References

- Use wikilinks: `[[Note Title]]`. Obsidian resolves these by filename, so they survive folder moves.
- When the link text should differ from the note title, use the alias form: `[[3.6.1. PHP Execution Models|PHP execution model]]`.
- Add a `## See Also` section at the end of every note with 2–5 links. This keeps the graph view useful.
- Do **not** link to notes that do not exist yet — Obsidian will create dangling links and the graph will lie. Either create the target note in the same session, or omit the link.

## 8. Length and Depth

The brief from the author is explicit:

> *Make the notes long for better explanation.*
> *Provide the most absolute, detailed, exhaustive, and rigorous explanation possible, written as very long, structured, and polished, with no steps skipped and no assumptions left implicit.*

Operational targets:

| Note type | Minimum length | Typical length |
| --------- | -------------- | -------------- |
| Concept note (e.g., HTTP lifecycle, MongoDB sharding) | 800 words | 1,200–2,000 words |
| Framework API note (e.g., Flask routes, Express middleware) | 600 words | 900–1,500 words |
| Language primitive note (e.g., PHP `echo`, PHP arrays) | 400 words | 600–1,000 words |
| Chapter index | 300 words | 400–600 words |

Single-sentence paragraphs are forbidden. Each paragraph is at least 3–5 sentences and develops one idea.

## 9. What This Vault Does NOT Cover

To avoid scope creep and overlap with the author's other vaults:

- **System Design** (capacity planning, sharding math, CAP theorem proofs, consensus algorithms like Paxos/Raft, queue theory, back-of-envelope scaling math) is out of scope. A topic that drifts into System Design territory gets a one-paragraph summary and the marker *"Covered in the System Design vault."*
- **Frontend frameworks** (React, Vue, Angular) are out of scope, except where a serverless platform (Vercel, Cloudflare) directly couples to them.
- **SQL language tutorial** is out of scope. The author already knows SQL and PL/SQL. The Databases chapter covers **engines and internals**, not syntax.
- **DevOps tooling outside deployment** (CI/CD pipelines, Kubernetes operators, Terraform modules) is out of scope except for a passing mention where relevant.

## 10. Maintenance Workflow

When you add or edit a note:

1. Update the chapter index (`X.0. Chapter Index.md`) in the same session.
2. If the note is the first in a new chapter section, update the chapter index's reading order.
3. If the note introduces a new tag, add it to at least one other note so it does not become an orphan in the tag pane.
4. Run Obsidian's "Check all links" periodically to catch broken wikilinks.
