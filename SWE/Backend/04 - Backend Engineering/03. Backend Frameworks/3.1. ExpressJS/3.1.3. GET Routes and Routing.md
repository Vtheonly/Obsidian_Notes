# 3.1.3. GET Routes and Routing

> [!info] Orientation
> This note covers the Express routing API in depth: how `app.get` and the other method handlers work, how path patterns and route parameters are matched, how multiple handlers chain on a single route, how `express.Router` modularizes route files, and how the 404 fallback behaves. It expands on the old vault's "GET Route" note and is a prerequisite for understanding middleware composition in [[3.1.6. Express Middleware Architecture]].

## 1. The `app.get` Signature

Every HTTP route in Express is registered by calling a method on the application (or router) object named after the HTTP verb. `app.get(path, ...handlers)` is the most common, but `app.post`, `app.put`, `app.patch`, `app.delete`, and `app.all` follow the same shape. The `path` argument is either a string, a string pattern, or a regular expression that Express compiles into an internal matcher; the `handlers` are one or more middleware functions executed in order when the path and method both match.

```javascript
app.get('/health', (req, res) => {
  res.json({ status: 'ok' });
});
```

Each handler receives `(req, res, next)`. The first handler that calls a terminal method on `res` (such as `send`, `json`, `end`) finishes the response; if no handler terminates the response, Express eventually sends an empty 200 and logs a warning. Calling `next()` without arguments hands control to the next handler in the chain, while calling `next(err)` jumps straight to the error-handling middleware described in [[3.1.6. Express Middleware Architecture]].

## 2. Path Patterns and Route Parameters

Express path strings support named parameters prefixed with a colon. When a request matches, the captured substring is exposed on `req.params` as a property whose name is the parameter name. Parameters are always strings — even `/users/42` populates `req.params.id` as `"42"`, so you must explicitly coerce with `Number(req.params.id)` or a validation library before doing arithmetic or database lookups.

```javascript
app.get('/users/:id', (req, res) => {
  const id = Number(req.params.id);
  if (Number.isNaN(id)) return res.status(400).json({ error: 'Invalid id' });
  res.json({ id });
});
```

Path strings also support optional parameters (`/users/:id?`), wildcards (`/files/*` captures the rest of the path into `req.params[0]`), and a limited set of regex-like operators. For full control, pass a real `RegExp` instead of a string. The example below matches any UUID-shaped path segment and is a common pattern when you want to validate the shape of an id at the routing layer rather than inside the handler.

```javascript
app.get(/^\/users\/([0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12})$/i, (req, res) => {
  res.json({ uuid: req.params[0] });
});
```

## 3. Multiple Handlers on One Route

A single route can take any number of handler functions, either as separate arguments or as an array. Each handler must call `next()` to delegate to the next one, and only the last handler in the chain should call a terminal `res` method. This is the building block for per-route middleware: authentication checks, input validation, ownership checks, and the final business handler can all live on one `app.get` call without polluting the global middleware stack.

```javascript
app.get(
  '/admin',
  requireAuth,
  requireAdmin,
  (req, res) => {
    res.json({ admin: req.user });
  }
);
```

The array form is equivalent and reads better when the handler list is long or generated dynamically. Mixing styles — `app.get('/x', [mw1, mw2], handler)` — also works and is the convention used by `express.Router` internally. Whatever the form, Express flattens the list into one ordered queue of layers and executes them top to bottom.

## 4. `app.route` for Verbs on One Path

When several HTTP verbs share a path, `app.route(path)` returns a chainable object with `.get`, `.post`, `.put`, `.patch`, `.delete`, and `.all` methods. This avoids repeating the path string four times and keeps the related handlers visually grouped. The chainable form is purely syntactic sugar; the resulting route table is identical to four separate `app.get`/`app.post`/etc. calls.

```javascript
app.route('/articles/:id')
  .get(getArticle)
  .put(updateArticle)
  .delete(deleteArticle);
```

## 5. `express.Router` for Modular Route Files

Once a project grows past a handful of routes, putting them all in `app.js` becomes unmanageable. `express.Router()` returns a mini-application with the same `get`, `post`, `use`, and `route` methods as `app`, but it does not bind a port and is meant to be mounted at a path prefix on the parent application. This is the canonical way to split routes into one file per resource.

```javascript
// routes/users.js
import { Router } from 'express';

const router = Router();

router.get('/', listUsers);
router.get('/:id', getUser);
router.post('/', createUser);

export default router;
```

Mounting the router attaches every route it defines under the supplied prefix. The snippet below makes the three user routes available at `/users`, `/users/:id`, and `POST /users` respectively, without the routes file needing to know its mount path. Re-mounting the same router under a different prefix (say `/v2/users`) is a one-line change in `app.js`.

```javascript
// app.js
import usersRouter from './routes/users.js';

app.use('/users', usersRouter);
```

## 6. Method Handlers and `app.all`

Express ships with method handlers for every standard HTTP verb: `get`, `post`, `put`, `patch`, `delete`, `head`, `options`, and a couple of WebDAV verbs most people never use. `app.all(path, ...handlers)` matches any method, which is useful for logging, authentication, or returning `405 Method Not Allowed` from a single handler instead of registering seven separate stubs. `app.use(path, ...handlers)` is similar but matches any method **and** any path that begins with the prefix, which is why it is the canonical way to mount routers and global middleware.

## 7. Order Matters and the 404 Fallback

Express evaluates routes top-to-bottom in registration order and stops at the first match that sends a response. This means a specific route must be registered before a more general one that would also match, or the specific route is shadowed and never reached. The classic bug is registering `/users/me` after `/users/:id`, which causes `/users/me` to be captured by the parameter route with `req.params.id === "me"` and the dedicated `/users/me` handler never to run.

```javascript
// Correct order: specific before generic
app.get('/users/me', getMe);
app.get('/users/:id', getUser);
```

When no registered route matches the request path and method, Express falls through to the end of the middleware stack. If you have not registered a 404 handler there, Express sends its built-in `Cannot GET /path` HTML response with a 404 status. The standard pattern is to register a final middleware **without a path** at the very bottom of `app.js`, after every route, that responds with your preferred 404 format. Because it has no path it matches everything that fell through, and because it is registered last it only runs when nothing above it claimed the request.

```javascript
// After all real routes
app.use((req, res) => {
  res.status(404).json({ error: 'Not found', path: req.path });
});
```

## 8. Strict Routing and Trailing Slashes

By default Express treats `/users` and `/users/` as the same route, which is convenient but means relative links and reverse proxies can produce inconsistent URLs that confuse caches and analytics. `app.set('strict routing', true)` disables this normalization so the two paths are distinct routes that must be registered separately. The companion setting `app.set('case sensitive routing', true)` makes `/Users` and `/users` distinct as well. Both default to `false` for backward compatibility; new API-only projects usually enable both to avoid ambiguity in the URL space.

## Summary

Express routing is a top-to-bottom scan of an ordered layer list, where each layer combines a path matcher and a method filter. Named parameters capture URL segments into `req.params` as strings, multiple handlers chain on a single route, `app.route` groups verbs on one path, and `express.Router` modularizes routes into files mounted under prefixes. Route order is significant because the first matching layer wins, so specific routes must precede generic ones, and a final path-less middleware catches everything that fell through to produce a clean 404.
