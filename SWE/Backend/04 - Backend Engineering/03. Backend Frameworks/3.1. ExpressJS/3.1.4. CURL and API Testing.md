# 3.1.4. CURL and API Testing

> [!info] Orientation
> `curl` is the lingua franca of HTTP debugging: it ships pre-installed on macOS, Linux, and Windows 10+, runs in any shell, and produces output that is trivial to copy into a bug report or a Slack message. This note covers the curl flags every backend developer should know cold, shows how to read the verbose output, and surveys the GUI and CLI alternatives (HTTPie, Postman, Insomnia, Bruno, VS Code REST Client) and when each one earns its place in the workflow.

## 1. Why cURL Is Non-Negotiable

Every backend engineer eventually finds themselves on a production server with only an SSH session and a broken endpoint to diagnose. In that moment `curl` is the only HTTP client guaranteed to be available, and being fluent with it means the difference between fixing the problem in two minutes and waiting for a colleague to SSH in with their own tools. GUI clients are excellent for design and exploration, but the lowest common denominator — the one tool that works on a bastion host, inside a Docker container, on a CI runner, and across every operating system — is `curl`. Treat it as a core skill, not a fallback.

There is also a documentation benefit. A `curl` one-liner is self-contained and reproducible in a way that a Postman collection export is not: you can paste it into a README, a Jira ticket, or a `curl | bash` install script, and the reader can run it without installing anything or importing a collection. Every API doc that respects its readers ships curl examples alongside language-specific snippets.

## 2. The Basic GET

The simplest invocation is `curl URL`. curl defaults to `GET`, follows no redirects, prints only the response body to stdout, and exits with status 0 if the TCP connection and HTTP exchange completed regardless of the HTTP status code. This last point is a frequent source of confusion: a 500 response still makes curl exit 0; you must inspect the body or use the `-w` flag to extract the status code if you want curl to fail on server errors.

```bash
curl http://localhost:3000/users
```

```text
[{"id":1,"name":"Alice"},{"id":2,"name":"Bob"}]
```

## 3. Verbose Output

The `-v` (or `--verbose`) flag makes curl print the entire HTTP exchange to stderr — connection establishment, request method and headers, response status line and headers — while the body still goes to stdout. The lines starting with `>` are request bytes curl is sending, the lines starting with `<` are response bytes the server sent back, and the lines starting with `*` are curl's own diagnostics about TLS handshake, DNS resolution, and connection reuse.

```bash
curl -v http://localhost:3000/users
```

```text
*   Trying 127.0.0.1:3000...
* Connected to localhost (127.0.0.1) port 3000 (#0)
> GET /users HTTP/1.1
> Host: localhost:3000
> User-Agent: curl/8.4.0
> Accept: */*
>
< HTTP/1.1 200 OK
< X-Powered-By: Express
< Content-Type: application/json; charset=utf-8
< Content-Length: 53
<
[{"id":1,"name":"Alice"},{"id":2,"name":"Bob"}]
```

Reading this output top to bottom tells you whether DNS resolved, whether the TCP connection succeeded, what request headers curl actually sent (often different from what you think you sent), what status line the server returned, and what response headers accompanied the body. Nine out of ten "the API is broken" tickets can be diagnosed from this single output.

## 4. Method Override and Headers

To send a non-GET request, use `-X METHOD` (or `--request`). For `POST`/`PUT`/`PATCH` you usually also need to send a body and set `Content-Type`, both of which curl will not infer for you. Headers are added with `-H "Name: Value"` and can be repeated. The example below posts a JSON body to a login endpoint with the correct `Content-Type` header.

```bash
curl -X POST http://localhost:3000/login \
  -H "Content-Type: application/json" \
  -d '{"email":"alice@example.com","password":"hunter2"}'
```

A useful shortcut: `-d` automatically sets the method to `POST` and the `Content-Type` to `application/x-www-form-urlencoded` unless overridden. The explicit `-X POST` is therefore redundant for form posts but is still useful for `PUT`/`PATCH`/`DELETE` with a body, where curl's method inference is less obvious.

## 5. Request Bodies from Files and Stdin

Long JSON bodies are painful to inline on the shell because of quoting and escaping. curl accepts `@filename` as a `-d` argument to read the body from a file, and it accepts `@-` to read from stdin, which lets you pipe the output of `jq` or another tool into the request body. The `Content-Type` header still has to be set explicitly because curl has no way to infer it from the file extension.

```bash
curl -X PUT http://localhost:3000/users/1 \
  -H "Content-Type: application/json" \
  -d @payload.json
```

## 6. Pretty-Printing JSON with jq

curl writes the raw response body to stdout with no formatting. For JSON APIs the result is often a single very long line that is unreadable. Piping through `jq` (with no arguments) pretty-prints the JSON and color-codes it; piping through `jq '.users[0].name'` extracts a specific field. `jq` is a separate install (`apt install jq`, `brew install jq`) but is worth its weight in gold for any JSON-heavy workflow.

```bash
curl -s http://localhost:3000/users | jq '.[0].name'
```

```text
"Alice"
```

The `-s` (or `--silent`) flag suppresses curl's progress meter and error messages so the only thing on stdout is the body, which is what you want when piping to another tool.

## 7. Following Redirects, Saving Output, and Cookies

By default curl does not follow `3xx` redirects — it prints the redirect response and exits. The `-L` (or `--location`) flag tells curl to follow up to 50 redirect hops, printing only the final body. Combine with `-L --post301 --post302` if you want to preserve the POST method across redirects (curl by default rewrites POST to GET on 301/302, matching browser behavior, which is sometimes not what you want for an API).

To save the response body to a file instead of stdout, use `-o filename` (lowercase o, you choose the name) or `-O` (uppercase O, curl uses the remote filename from the URL). To save response headers alongside, add `-D headers.txt`. For cookie-based session testing, `-b cookies.txt` sends cookies from a file and `-c cookies.txt` writes any `Set-Cookie` headers received back to the file; using both flags together gives you a cookie jar that persists across curl invocations.

```bash
# Log in, save session cookie, then hit a protected endpoint
curl -c cookies.txt -X POST http://localhost:3000/login -d 'email=alice&password=hunter2'
curl -b cookies.txt http://localhost:3000/me
```

## 8. Common Flags Cheat Sheet

| Flag | Long form | Effect |
| ---- | --------- | ------ |
| `-X METHOD` | `--request` | Override the HTTP method. |
| `-H "Name: Val"` | `--header` | Add a request header. Repeatable. |
| `-d DATA` | `--data` | Send body (implies POST and `application/x-www-form-urlencoded`). |
| `-d @file` | `--data @file` | Read body from a file. |
| `-L` | `--location` | Follow redirects. |
| `-o file` | `--output` | Write body to file. |
| `-O` | `--remote-name` | Write body to file named after URL. |
| `-D file` | `--dump-header` | Write response headers to file. |
| `-b file` | `--cookie` | Send cookies from file. |
| `-c file` | `--cookie-jar` | Save received cookies to file. |
| `-v` | `--verbose` | Print request/response exchange to stderr. |
| `-s` | `--silent` | Suppress progress meter. |
| `-S` | `--show-error` | With `-s`, still print errors. |
| `-i` | `--include` | Include response headers in output. |
| `-w FMT` | `--write-out` | Print custom format (e.g. `%{http_code}`). |
| `-k` | `--insecure` | Skip TLS certificate verification. |
| `-u user:pass` | `--user` | HTTP Basic authentication. |
| `--connect-timeout S` | — | Max seconds to establish TCP. |
| `--max-time S` | `--max-time` | Max seconds for whole request. |

## 9. Alternatives and When to Use Each

`HTTPie` is a curl alternative designed for humans: `http POST localhost:3000/login email=alice password=hunter2` is far more readable than the equivalent curl invocation, and it pretty-prints JSON by default. It is excellent for interactive terminal work but is not pre-installed anywhere, so it cannot replace curl for production debugging.

`Postman` is the dominant GUI client. It excels at managing large collections of requests, environments with variable substitution, and team-shared workspaces, but it is a heavy Electron app, has a history of questionable privacy decisions around synced data, and the free tier has been progressively restricted. `Insomnia` is a lighter, more developer-friendly alternative in the same category; `Bruno` is a newer open-source alternative that stores collections as plain text files in your git repository, which solves the version-control problem that Postman never quite figured out.

The `VS Code REST Client extension` lets you write `.http` files with `###`-separated request blocks, send them with a click, and see the response in a side panel. It is the right choice when your API requests are part of a codebase and you want them version-controlled alongside the server code, with the `Send Request` button one keystroke away. For day-to-day Express development, the combination of `curl` for production debugging, the REST Client extension for documented repeatable requests checked into the repo, and Bruno or Insomnia for ad-hoc exploration covers every workflow.

## Summary

`curl` is the one HTTP client that works everywhere and is worth knowing cold: `-X` to set the method, `-H` for headers, `-d` for bodies, `-v` for verbose output, `-L` for redirects, `-b`/`-c` for cookies, and `-s` with `jq` for pretty JSON. GUI tools earn their place for collection management and exploration — Postman and Insomnia for individual use, Bruno for git-checked-in collections, and the VS Code REST Client extension for documented requests that live next to the code. None of them replaces `curl` on a bare production server.
