# 3.1.5. Query Parameters and Request Object

> [!info] Orientation
> This note expands the old vault's "req.query.name" page into a full tour of the Express `req` and `res` objects. It covers how query strings are parsed (including arrays and nested objects), why you must never trust `req.query` without validation, and the surface area of the request and response objects that every Express handler relies on.

## 1. URL Structure and Query Parsing

A URL breaks into scheme, host, path, query, and fragment. The query portion starts at the `?` character and runs to the end of the URL or to a `#` fragment marker. Within the query, key-value pairs are separated by `&`, and keys are separated from values by `=`. Express parses this substring into a plain JavaScript object exposed as `req.query`, so `?name=Alice&age=30` becomes `{ name: 'Alice', age: '30' }`. The values are always strings, even when they look like numbers, because the URL format has no type information.

```javascript
app.get('/search', (req, res) => {
  const q = req.query.q ?? '';
  const page = Number(req.query.page ?? 1);
  res.json({ q, page });
});
```

The default parser is the `qs` library, which Express bundles internally. It supports richer syntax than Node's built-in `URLSearchParams`, including arrays and nested objects. If you only want flat string-to-string parsing without that complexity, set `app.set('query parser', 'simple')` to switch to `querystring.parse`. The `extended` setting mentioned in some older tutorials was a `body-parser` option and is not the same thing; the query parser setting is independent.

## 2. Array and Nested Query Parameters

The `qs` parser produces arrays and nested objects when the query string uses the bracket syntax. `?tags=js&tags=node` produces `{ tags: ['js', 'node'] }`, and `?filter[name]=Alice&filter[age]=30` produces `{ filter: { name: 'Alice', age: '30' } }`. This is convenient for filter-heavy APIs but introduces a parsing surprise: `?tags=a,b` produces `{ tags: 'a,b' }` (a string), not an array, because the comma is not a delimiter in `qs`. To get an array, repeat the key or use bracket notation.

```javascript
// GET /products?tags=red&tags=cotton&filter[price_min]=10
app.get('/products', (req, res) => {
  const tags = req.query.tags;             // ['red', 'cotton']
  const priceMin = Number(req.query.filter?.price_min); // 10
  res.json({ tags, priceMin });
});
```

The cost of this flexibility is that the shape of `req.query` is not predictable from a TypeScript signature alone — the same key can be a string, an array, or an object depending on what the client sent. This is the core reason that validation is not optional on query parameters.

## 3. Never Trust `req.query`

`req.query` is parsed directly from the URL with no schema, no type coercion, and no length limits. A client can send `?page=abc`, `?page[]=1&page[]=2`, or `?page=<script>alert(1)</script>` and Express will happily pass all three through to your handler as `req.query.page`. Treating any of these as a number or interpolating them into a database query without validation is how SQL injection, NoSQL injection, and reflected XSS happen in Express apps.

The fix is to run every external input through a validator before using it. The three most common choices in the Node ecosystem are `zod` (schema-first, TypeScript-native, runtime inference), `joi` (schema-first, older, very mature), and `express-validator` (a thin wrapper around `validator.js` with per-route middleware). All three reject invalid input, coerce types where safe, and produce consistent error shapes your error handler can format. The example below uses `zod` to validate a pagination query with sensible defaults.

```javascript
import { z } from 'zod';

const paginationSchema = z.object({
  page: z.coerce.number().int().min(1).default(1),
  limit: z.coerce.number().int().min(1).max(100).default(20),
  sort: z.enum(['created_at', 'name']).default('created_at'),
  order: z.enum(['asc', 'desc']).default('desc'),
});

app.get('/users', (req, res) => {
  const result = paginationSchema.safeParse(req.query);
  if (!result.success) {
    return res.status(400).json({ errors: result.error.flatten() });
  }
  const { page, limit, sort, order } = result.data;
  res.json({ page, limit, sort, order });
});
```

## 4. The Full `req` Object Surface

Beyond `req.query`, Express decorates the incoming request with a standard set of properties that cover almost everything a handler needs. Some are populated by Express core, others by middleware you register (`express.json` populates `req.body`, `cookie-parser` populates `req.cookies`). Knowing which property comes from where saves time when something is unexpectedly `undefined`.

| Property | Source | Contents |
| -------- | ------ | -------- |
| `req.params` | Route definition | Named path segments (`/users/:id` → `{ id }`). |
| `req.query` | URL parser | Parsed query string object. |
| `req.body` | `express.json` / `express.urlencoded` | Parsed request body. `undefined` if no body parser ran. |
| `req.headers` | Node core | Lowercased header name → string value. |
| `req.cookies` | `cookie-parser` middleware | Parsed cookie object. |
| `req.signedCookies` | `cookie-parser` with `secret` | Verified signed cookies. |
| `req.ip` | Express core | Remote IP, respecting `trust proxy`. |
| `req.ips` | Express core | Array when `trust proxy` is set. |
| `req.method` | Node core | HTTP method string (`GET`, `POST`, ...). |
| `req.path` | Express core | Path portion of the URL, no query. |
| `req.url` / `req.originalUrl` | Node / Express | Full URL including query. |
| `req.protocol` | Express core | `http` or `https`, respecting `trust proxy`. |
| `req.hostname` | Express core | Host header value, respecting `trust proxy`. |
| `req.get(name)` | Express core | Case-insensitive header lookup. |

The `trust proxy` setting matters whenever your Express app sits behind a load balancer, CDN, or reverse proxy (which is essentially always in production). Without it, `req.ip` is the proxy's IP and `req.protocol` is `http` even when the client connected over HTTPS. Set `app.set('trust proxy', 1)` for a single proxy hop or `'loopback'` for local development; the value is the number of hops to trust, since each trusted hop strips one `X-Forwarded-For` entry.

## 5. The `res` Object Surface

The response object mirrors the request object: a Node `http.ServerResponse` extended with convenience methods. The most common are `res.send(body)` (auto-detects content type and sets `Content-Length`), `res.json(obj)` (stringifies and sets `Content-Type: application/json`), and `res.status(code)` (chainable, sets the status code). `res.set(name, value)` sets a response header, `res.cookie(name, value, opts)` writes a `Set-Cookie` header, and `res.redirect(url)` sends a 302 with a `Location` header.

```javascript
app.get('/me', requireAuth, (req, res) => {
  res.set('Cache-Control', 'private, max-age=60');
  res.cookie('lastSeen', Date.now(), { httpOnly: true, sameSite: 'lax' });
  res.json({ user: req.user });
});
```

`res.end()` terminates the response without sending a body — useful for `204 No Content` responses or after manually calling `res.write()`. The status-code chaining pattern `res.status(201).json(...)` is idiomatic Express and reads more cleanly than the equivalent `res.set('Content-Type', 'application/json'); res.statusCode = 201; res.end(JSON.stringify(...))` that pure Node would require.

## 6. Streaming Responses

For large or unbounded responses — server-sent events, file downloads, real-time logs — buffering the entire body in memory before calling `res.send` is wasteful or impossible. Express delegates to Node's stream API: call `res.write(chunk)` repeatedly to push chunks to the client as they become available, then call `res.end()` to close the response. Between writes you can `await` database queries, file reads, or upstream API calls, and the client receives each chunk as it is produced.

```javascript
app.get('/stream', (req, res) => {
  res.set('Content-Type', 'text/event-stream');
  res.set('Cache-Control', 'no-cache');
  res.set('Connection', 'keep-alive');

  const interval = setInterval(() => {
    res.write(`data: ${JSON.stringify({ ts: Date.now() })}\n\n`);
  }, 1000);

  req.on('close', () => clearInterval(interval));
});
```

The `req.on('close')` listener is essential: when the client disconnects, you must stop writing to `res` and release any resources (timers, database cursors, file handles) that were producing the stream, otherwise your server leaks resources and eventually exhausts its file descriptors.

## Summary

Query strings parse into `req.query` as a plain object, with `qs` supporting arrays and nested objects via bracket syntax. Because the URL carries no type information, every value from `req.query` is a string until you coerce it, and trusting the raw values invites injection attacks — always validate with `zod`, `joi`, or `express-validator`. The `req` object exposes `params`, `query`, `body`, `headers`, `cookies`, `ip`, `method`, `path`, and `protocol`, while `res` offers `send`, `json`, `status`, `set`, `cookie`, `redirect`, and the streaming `write`/`end` pair. Set `trust proxy` whenever Express sits behind a reverse proxy so `req.ip` and `req.protocol` reflect the real client.
