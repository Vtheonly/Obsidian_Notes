# 3.6.18. htmlspecialchars and Output Escaping

> [!info] Whenever you display data on a webpage that originates from an untrusted source — user input, content from your own database, data from a third-party API — you create a potential Cross-Site Scripting (XSS) vulnerability. `htmlspecialchars()` is PHP's primary defence against XSS. It converts characters with special meaning in HTML into their harmless entity equivalents. This note covers how XSS works, what `htmlspecialchars` does, the important flags (`ENT_QUOTES`, `ENT_HTML5`), the difference from `htmlentities`, and why modern template engines auto-escape for you.

## 1. What Is Cross-Site Scripting (XSS)?

XSS is an attack where a malicious user injects client-side scripts — usually JavaScript — into a webpage that is then viewed by other users. The browser, not knowing the script is malicious, executes it as if it were a legitimate part of the website. The result can range from annoying (a popup alert) to catastrophic (session cookie theft, account takeover, defacement).

### 1.1 A Simple Analogy

Imagine you have a blog with a comments section. A normal user, Alice, leaves a comment: `"Great article!"`. Your website stores this in the database and displays it on the page for everyone to see. A malicious user, Mallory, leaves a comment, but instead of text she inputs a script: `<script>alert('You have been hacked!');</script>`.

In a vulnerable application, when another user Bob visits the page, the PHP code might do this:

```php
<?php
// --- VULNERABLE CODE ---
$commentFromDatabase = "<script>alert('You have been hacked!');</script>";
echo "<div class='comment'>" . $commentFromDatabase . "</div>";
```

Bob's browser receives the following HTML:

```html
<div class='comment'><script>alert('You have been hacked!');</script></div>
```

The browser sees the `<script>` tag and executes the JavaScript inside it. Bob sees an alert box pop up saying "You have been hacked!".

### 1.2 Why XSS Is Dangerous

An alert box is just a harmless proof of concept. A real attacker could use a more dangerous script to **steal session cookies** (allowing them to hijack a user's logged-in session and impersonate them), **redirect users** to a phishing site to steal credentials, **deface the website** by changing content, or **log keystrokes** to capture passwords as they are typed. XSS is consistently in the OWASP Top 10 web vulnerabilities because it is common, easy to exploit, and high-impact.

## 2. How `htmlspecialchars()` Works

The `htmlspecialchars()` function provides the solution by "defanging" the user's input. It converts special characters that have meaning in HTML into their corresponding **HTML entities**. An HTML entity is a safe, text-only representation of a character.

| Character | Special meaning in HTML | `htmlspecialchars()` converts it to | Browser displays |
| --------- | ----------------------- | ------------------------------------ | ---------------- |
| `<` | Starts an HTML tag | `&lt;` | `<` |
| `>` | Ends an HTML tag | `&gt;` | `>` |
| `&` | Starts an HTML entity | `&amp;` | `&` |
| `"` | Defines an attribute value | `&quot;` | `"` |
| `'` | Defines an attribute value | `&#039;` (or `&apos;`) | `'` |

When the browser sees `&lt;`, it knows "this is not the start of a tag; this is just the literal less-than symbol that I should display on the screen." **The special meaning is removed.**

## 3. The Golden Rule of Output

> **ALWAYS escape any data that comes from an external source before you display it on a webpage.**

This rule applies to data from `$_GET`, `$_POST`, `$_COOKIE`, the database, an API call, a file — anything that was not literally typed into the source code by the developer.

### 3.1 The Fixed Code

```php
<?php
// --- SECURE CODE ---
$commentFromDatabase = "<script>alert('You have been hacked!');</script>";
echo "<div class='comment'>" . htmlspecialchars($commentFromDatabase) . "</div>";
```

Bob's browser now receives this HTML source:

```html
<div class='comment'>&lt;script&gt;alert('You have been hacked!');&lt;/script&gt;</div>
```

Because the `<` and `>` have been converted to `&lt;` and `&gt;`, the browser does **not** see a script tag to execute. Instead, it renders the literal text onto the screen. What Bob sees on the page is the literal string `<script>alert('You have been hacked!');</script>` — the attack is completely neutralised. The malicious code is displayed as harmless text instead of being executed.

## 4. The Important Flags

The default behaviour of `htmlspecialchars()` since PHP 8.1 is `ENT_QUOTES | ENT_SUBSTITUTE`, which converts both single and double quotes. Before PHP 8.1, the default was `ENT_HTML401 | ENT_COMPAT`, which only converted double quotes — single quotes were left intact, leaving attribute-injection vulnerabilities.

The two most important flags to know are:

- **`ENT_QUOTES`** — converts both single and double quotes. Always use this. If you ever need to support PHP versions older than 8.1, pass it explicitly: `htmlspecialchars($str, ENT_QUOTES)`. Without it, an attacker who can inject into a single-quoted attribute (`<input value='$userInput'>`) can break out with a `'`.
- **`ENT_HTML5`** — uses the HTML5 doctype's entity table. Use this when your page is HTML5 (which it almost certainly is). It is more correct than the default `ENT_HTML401` for modern pages.
- **`ENT_SUBSTITUTE`** — replaces invalid byte sequences with the Unicode replacement character (`U+FFFD`) instead of returning an empty string. Helps with debugging encoding issues.
- **`ENT_NOQUOTES`** — leaves both single and double quotes unconverted. Almost never what you want.

A robust default for modern PHP is `htmlspecialchars($str, ENT_QUOTES | ENT_HTML5, 'UTF-8')`. Specifying the encoding explicitly as `UTF-8` avoids issues where the default encoding is `UTF-8` but legacy `php.ini` settings override it.

## 5. `htmlspecialchars` vs `htmlentities`

The two functions are easily confused. `htmlspecialchars` converts only the five characters that have special meaning in HTML: `<`, `>`, `&`, `"`, `'`. `htmlentities` converts *every* character that has an HTML entity equivalent — including accented characters, currency symbols, and emoji.

In practice, `htmlspecialchars` is almost always what you want. It is faster (fewer characters to replace), produces smaller output, and does not break UTF-8 content. `htmlentities` is useful only when you need to display characters that the page's character set cannot represent (a rare scenario in the UTF-8 era). Use `htmlspecialchars` for routine output escaping.

## 6. Context Matters — One Function Does Not Fit All

`htmlspecialchars` is the right tool for escaping data that goes into HTML body text or into HTML attribute values. It is **not** the right tool for other contexts:

- **Inside a `<script>` block** — use `json_encode($value, JSON_HEX_TAG | JSON_HEX_AMP | JSON_HEX_APOS | JSON_HEX_QUOT)` to safely embed data as a JavaScript literal.
- **Inside a `style` attribute or `<style>` block** — escaping rules differ; prefer not to put user data in CSS at all.
- **Inside a URL** — use `urlencode()` for query string parameters and `rawurlencode()` for path segments.
- **Inside a JavaScript string in an event handler** — `json_encode` is the right tool, not `htmlspecialchars`.

The rule: identify the context where the data will be placed, and use the escaper for that context. Using the wrong escaper can leave a vulnerability even when you "remembered to escape."

## 7. Modern Alternative — Template Engines

Calling `htmlspecialchars` on every output value is verbose and error-prone. If you forget it on a single line, you have a vulnerability. Modern PHP frameworks solve this with templating engines that **auto-escape** by default:

- **Twig** (Symfony's default) escapes every variable output with `htmlspecialchars($var, ENT_QUOTES, 'UTF-8')` unless you explicitly mark it as safe with the `|raw` filter.
- **Blade** (Laravel's default) escapes every `{{ $variable }}` automatically; you opt out of escaping with the `{!! $variable !!}` syntax, which is reserved for trusted HTML.

Using a template engine is the modern best practice for output escaping. It removes the human error of forgetting to call `htmlspecialchars` on a single line, and it centralises the escaping logic in one place where it can be audited. See [[3.5.1. Laravel Overview and Installation]] for Blade and [[3.6.7. Mixing PHP and HTML]] for the raw PHP alternative.

## 8. Production Pitfalls

A few XSS-related mistakes recur in production code. The first is double-escaping — calling `htmlspecialchars` on a value that has already been escaped, producing visible `&lt;` on the page. This usually happens when a value is escaped at the data layer and again at the presentation layer. The fix is to escape only at the output boundary, never at storage time. The second is forgetting to escape values that come from the developer's own database — the developer assumes the database is trusted, but if any user input was ever stored without sanitisation, the database contains attacker-controlled content. The rule is: escape at output, regardless of source. The third is using `htmlspecialchars` inside JavaScript or URL contexts, where it does not provide protection (see the previous section).

## Summary

XSS is the most common web vulnerability, and `htmlspecialchars` is PHP's primary defence. It converts `<`, `>`, `&`, `"`, and `'` into their HTML entity equivalents, neutralising any HTML or JavaScript the data might contain. Always pass `ENT_QUOTES` (or rely on the PHP 8.1+ default) and prefer `ENT_HTML5` with explicit `'UTF-8'` encoding. `htmlspecialchars` is preferred over `htmlentities` because it is faster and produces smaller output. Use the right escaper for the context: `htmlspecialchars` for HTML body and attributes, `json_encode` for JavaScript, `urlencode` for URLs. Modern template engines (Twig, Blade) auto-escape by default and are the recommended approach.
