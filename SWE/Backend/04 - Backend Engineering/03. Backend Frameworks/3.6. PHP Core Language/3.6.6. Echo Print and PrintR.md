# 3.6.6. Echo Print and PrintR

> [!info] PHP has five common ways to send data to output: `echo`, `print`, `print_r`, `var_dump`, and `var_export`. They look similar but serve different purposes — `echo` is for production output, `print_r` and `var_dump` are for debugging, and `var_export` is for generating valid PHP code. Choosing the wrong one is a common beginner mistake that produces confusing output or leaks information in production.

## 1. echo — The Production Output Construct

`echo` is the most commonly used tool for outputting strings, numbers, and other simple data. It is a **language construct**, not a function, which means it is a core part of the PHP language itself rather than a callable in the standard library. The distinction matters for syntax: parentheses are optional, and `echo` cannot be used in expressions that expect a return value.

The key characteristics are: it has no return value (its return type is `void`), it can accept multiple arguments when used without parentheses, and the community convention is to use it without parentheses. Its primary use is generating HTML and outputting content to the user.

```php
<?php
$user = 'Ninja';

echo 'Hello, world!';     // Basic usage
echo '<br>';
echo $user;               // Outputting a variable's value
echo '<br>';
echo 'Welcome, ', $user, '!';  // Multiple arguments, no parentheses
```

Trying to assign the result of `echo` to a variable (`$result = echo 'hi';`) is a syntax error. Trying to use `echo` with multiple arguments *inside* parentheses (`echo('a', 'b');`) is also an error in modern PHP — the parentheses force single-argument semantics.

## 2. print — The Other Output Construct

`print` is very similar to `echo` and can often be used interchangeably for simple cases. It is also a language construct, but it behaves more like a function in one important way: it always returns the integer `1`. This means `print` can be used in expressions, although doing so is rare and generally considered poor practice.

`print` accepts only a single argument — you cannot pass a comma-separated list of items. Because it has a return value, it is marginally slower than `echo`, though in real-world applications the difference is negligible.

```php
<?php
$user = 'Mario';

print 'Hello, world!';
print '<br>';
print 'Welcome, ' . $user . '!';   // Concatenation, not multiple args

$result = print 'This works.';     // Outputs: This works.
echo $result;                       // Outputs: 1
```

The expression `$result = print 'This works.'` is legal precisely because `print` returns `1`. This is occasionally useful in arcane contexts (some template engines use it), but in everyday code it just makes the line harder to read.

## 3. print_r — Human-Readable Debugging

`print_r()` is completely different from `echo` and `print`. It is a true function designed specifically for debugging. Its purpose is to output a *human-readable* representation of a variable, especially complex types like arrays and objects. Where `echo` and `print` would just show the word "Array" (and trigger a Notice on objects), `print_r` displays the entire structure of the array, including its keys and values.

`print_r` is a debugging tool and should not be used for final user output on a live site. By default it prints the information directly and returns `true`, but if you pass `true` as a second argument (`print_r($var, true)`), it returns the output as a string instead of printing it.

```php
<?php
$ninjas = ['Shaun', 'Yoshi', 'Mario', 'Peach'];

echo $ninjas;   // Output: Array (and a Notice in PHP 8+)

echo '<pre>';
print_r($ninjas);
echo '</pre>';
```

The `<pre>` tags make the browser respect whitespace and newlines, which is essential because `print_r` formats its output with indentation that browsers would otherwise collapse. The output looks like this:

```text
Array
(
    [0] => Shaun
    [1] => Yoshi
    [2] => Mario
    [3] => Peach
)
```

## 4. var_dump — Detailed Type Information

`var_dump()` is `print_r`'s more verbose cousin. It is the function to reach for when you need to know the exact type and value of a variable, not just a readable summary. It prints the data type, the length (for strings and arrays), and the value, recursively for nested structures.

```php
<?php
$data = ['name' => 'Yoshi', 'active' => true, 'score' => 0];

echo '<pre>';
var_dump($data);
echo '</pre>';
```

Output:

```text
array(3) {
  ["name"]=>
  string(5) "Yoshi"
  ["active"]=>
  bool(true)
  ["score"]=>
  int(0)
}
```

The crucial difference from `print_r` is that `var_dump` shows the type. This matters when debugging type-juggling bugs: `print_r` displays `0`, `false`, `null`, and `''` all as nothing or empty, while `var_dump` distinguishes them. `var_dump` is also invaluable for booleans — `echo true` prints `1`, `echo false` prints nothing, but `var_dump(true)` prints `bool(true)` and `var_dump(false)` prints `bool(false)`.

## 5. var_export — Valid PHP Code

`var_export()` outputs or returns a parseable, valid PHP representation of a variable. It is used when you want to serialise data into PHP source code — typically for caching configuration values to a file that can later be `include`d.

```php
<?php
$config = ['host' => 'localhost', 'port' => 3306, 'debug' => true];

$code = var_export($config, true);  // Return as string
file_put_contents('config.cache.php', "<?php return $code;\n");

// Later, in another request:
$loaded = require 'config.cache.php';
// $loaded === ['host' => 'localhost', 'port' => 3306, 'debug' => true]
```

This is a lightweight caching technique. Note that `var_export` does not handle circular references or closures and produces a file containing user-supplied data — so never write `var_export` output of untrusted data to a file that is later `include`d as PHP, as that would be a code injection vulnerability.

## 6. Comparison Table

| Feature | `echo` | `print` | `print_r` | `var_dump` | `var_export` |
| ------- | ------ | ------- | --------- | ---------- | ------------ |
| Type | Language construct | Language construct | Function | Function | Function |
| Return value | `void` | `1` | `true` or string | `void` | `void` or string |
| Arguments | Multiple (no parens) | Single | Single + optional bool | Multiple | Multiple + optional bool |
| Shows types | No | No | No | **Yes** | Yes (as PHP syntax) |
| Output is valid PHP | No | No | No | No | **Yes** |
| Primary use | Production output | Production output | Debugging | Debugging | Caching / codegen |

## 7. When to Use Which

Use `echo` for 99% of production output needs. It is the community standard, it is fast, and it is flexible with multiple arguments. Use `print` only if you have a very specific reason to check its return value, or if you simply prefer its syntax — most developers stick with `echo`.

Use `print_r` for quick debugging when you just need to see what is inside an array or object and do not care about exact types. Use `var_dump` when you need exact type information, especially when debugging booleans, `null` vs `''` vs `0`, or nested structures. Use `var_export` when you want to serialise a value to a PHP file for caching.

A useful workflow when debugging is to wrap any of `print_r`, `var_dump`, or `var_export` in `<pre>` tags in a small helper:

```php
function dump(mixed $var): void {
    echo '<pre>';
    var_dump($var);
    echo '</pre>';
}
```

This avoids the "everything is on one line in the browser" problem without littering your code with `<pre>` tags.

## Summary

`echo` is the production output construct — fast, void, and accepts multiple arguments. `print` is `echo` with a return value of `1`, which is rarely useful. `print_r`, `var_dump`, and `var_export` are debugging and code-generation tools: `print_r` for human-readable summaries, `var_dump` for detailed type information, and `var_export` for valid PHP source code. Using `echo` on an array produces "Array" and a Notice; using `print_r` or `var_dump` shows you the contents. In production, never leave `var_dump` or `print_r` output visible to end users — it leaks implementation details that attackers can use.
