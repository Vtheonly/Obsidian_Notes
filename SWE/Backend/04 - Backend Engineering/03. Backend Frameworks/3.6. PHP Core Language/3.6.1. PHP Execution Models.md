# 3.6.1. PHP Execution Models

> [!info] PHP can run in two fundamentally different ways: the classic share-nothing request/response model and the modern long-running application-server model. Every deployment choice — Apache mod_php, PHP-FPM, `php -S`, Swoole, RoadRunner, CLI — is just an instance of one of these two models. Understanding which model is in use explains most of PHP's performance characteristics, memory behaviour, and debugging quirks.

## 1. The Two Core Execution Models

Everything about how PHP runs falls into one of two categories. Knowing which one is active in a given process answers most "why does PHP behave like this?" questions before they are asked.

### 1.1 The Share-Nothing Request/Response Model

This is the traditional and still dominant way PHP is used for web sites. A separate, long-running program — a web server like Apache or Nginx — is constantly listening for HTTP requests on port 80 or 443. When a request for a `.php` file arrives, the web server recognises it, hands it to a PHP worker, the worker executes the script from top to bottom, the script emits output (usually HTML), the output is streamed back to the browser, and then the worker tears down its entire state.

The "share-nothing" label refers to that teardown step. Every variable, every object, every database connection handle, every in-memory cache is destroyed at the end of the request. The next request starts from a clean slate. This is what makes PHP so forgiving: memory leaks almost never accumulate, and a bug in one request cannot corrupt the state of the next request. The web server and a process manager like PHP-FPM do stay alive across requests, but the script's execution context does not.

A useful mental model is a pizza shop. The shop (the web server) is always open. When you call (the request), the manager hires a temporary chef (the PHP worker), the chef makes your pizza (executes the script), hands it to the driver (the response), and then immediately goes home. For the next order, the manager hires a completely new chef. Nothing carries over.

### 1.2 The Long-Running / Application-Server Model

This model is closer to how Node.js, Python WSGI, or Java servlet containers traditionally work. A single PHP script is started from the command line, and that script uses a special library — Swoole, RoadRunner, ReactPHP, or FrankenPHP — to start its own server and listen for requests on a specific port. The PHP process does not exit. It stays resident in memory, waiting for connections.

When a request arrives, the application's internal code handles it without re-initialising the framework on every request. Database connections are pooled, in-memory caches survive between requests, and route tables are compiled once. The trade-off is that the developer now has to think about memory leaks, mutable state, and connection limits — exactly the kinds of problems PHP's share-nothing model was designed to avoid.

The mental model here is a fine-dining restaurant. The head chef (the long-running PHP process) is always in the kitchen. When an order arrives from a waiter (the request), the chef prepares the dish and sends it out, but remains in the kitchen with all tools and knowledge intact, ready for the next order.

## 2. How PHP Gets Executed in Different Environments

The execution model abstracts over many concrete environments. The same model shows up in different packaging.

### 2.1 Linux Server (LAMP and LEMP Stacks)

This is the classic production environment for PHP. In a **LAMP** stack (Linux, Apache, MySQL, PHP), Apache is the web server and uses either the legacy `mod_php` module or, far more commonly today, **PHP-FPM** (FastCGI Process Manager) to execute PHP. PHP-FPM maintains a pool of pre-forked worker processes, ready to accept requests. This avoids the cost of starting a new PHP interpreter on every request while still preserving the share-nothing model — each worker reinitialises the script's state but the interpreter itself stays warm.

In a **LEMP** stack (Linux, Nginx, MySQL, PHP), Nginx is the high-performance web server. Unlike Apache, Nginx cannot execute PHP itself; it must forward the request to an external PHP-FPM process. The flow is request → Nginx → PHP-FPM → Nginx → user. This is the gold standard for production PHP in the request/response model. See [[3.6.2. Apache Server and PHP-FPM]] for the Apache-specific details and [[6.3. Nginx Reverse Proxy and Load Balancing]] for the broader Nginx topology.

### 2.2 XAMPP and Bundled Environments

XAMPP is not a different execution model. It is a pre-configured software bundle that installs Apache, MariaDB, and PHP together so that they work out of the box. When Apache is started from the XAMPP control panel, it runs the same request/response model as a Linux production server. Visiting `http://localhost/dashboard/` simply sends a request to the local Apache process, which executes the corresponding PHP script.

### 2.3 Windows with IIS or Manual Apache/Nginx

On Windows, Internet Information Services (IIS) is the built-in web server. It is configured with the FastCGI module to talk to a PHP installation, behaving just like the Nginx + PHP-FPM topology. Alternatively, Apache or Nginx can be installed directly on Windows and configured to work with PHP using the same request/response model.

### 2.4 Docker Containers

Docker packages an application and its entire environment into a portable container. A typical modern PHP Docker setup uses multiple containers linked together with `docker-compose`: an `nginx` container as the web server, a `php-fpm` container running the FastCGI process manager, and a `mysql` container for the database. The execution flow is identical to a LEMP stack — the request hits the Nginx container, which forwards the PHP request to the PHP-FPM container, which executes the script and returns the result. See [[6.1. Docker Containerization and Networking]] and [[6.2. Docker vs Apache for PHP]] for the deployment-angle details.

### 2.5 PHP's Built-in Server and CLI

PHP ships with a single-process development server. Running `php -S localhost:8000` starts a PHP process that listens for requests on port 8000. It is a long-running process in the sense that it does not exit, but each request still reinitialises the script's state. It is explicitly not for production use; see [[3.6.3. PHP Built-in Server and CLI]] for the gotchas.

The command-line interface (`php script.php`) is the purest form of PHP execution. It has nothing to do with web servers or HTTP. The interpreter executes the script once, prints any output to the console, and exits. This is used for maintenance tasks, cron jobs, command-line tools like Composer, and data processing pipelines.

## 3. Request/Response Flow Diagram

```mermaid
sequenceDiagram
    participant Browser
    participant WebServer as Apache / Nginx
    participant FPM as PHP-FPM Pool
    participant Worker as PHP Worker
    participant DB as MySQL / MariaDB

    Browser->>WebServer: HTTP GET /index.php
    WebServer->>FPM: FastCGi request (FCGI_BEGIN_REQUEST)
    FPM->>Worker: Hand off free worker
    Worker->>Worker: Bootstrap script (parse + compile)
    Worker->>DB: Query (PDO / mysqli)
    DB-->>Worker: Result set
    Worker-->>FPM: Generated HTML (stdout)
    FPM-->>WebServer: FastCGI response
    WebServer-->>Browser: HTTP 200 + body
    Note over Worker: Worker is recycled;<br/>all state destroyed
```

The diagram shows the share-nothing contract clearly: the worker is recycled and its state destroyed at the end of the request. The FPM pool and the web server stay resident; the script does not.

## 4. Summary Table

| Environment / Method | Primary Execution Model | Who Listens? | Does PHP Stay Running? |
| -------------------- | ----------------------- | ------------- | ---------------------- |
| Linux Server (LEMP / LAMP) | Request/Response via PHP-FPM | Nginx or Apache | No — the server and FPM stay, but each worker exits |
| XAMPP | Request/Response | Bundled Apache | No — Apache stays, each script process exits |
| Windows with IIS | Request/Response via FastCGI | IIS | No — IIS stays, each script process exits |
| Docker (typical setup) | Request/Response via PHP-FPM | Nginx container | No — containers stay, each worker exits |
| PHP Built-in Server (`php -S`) | Long-Running (dev only) | PHP process itself | Yes, until Ctrl+C |
| PHP CLI (`php script.php`) | Execute-and-Exit | Nobody | No — runs once and exits |
| Advanced PHP (Swoole / RoadRunner) | Long-Running (production) | PHP application process | Yes — designed as an application server |

## 5. Why This Distinction Matters in Practice

The execution model dictates which language features are safe to use and which patterns are dangerous. In the share-nothing model, you can safely use static singletons to cache a value for the duration of a request without worrying about leaks. In a long-running model, that same singleton accumulates across requests and becomes a memory leak. Connection pooling is unnecessary in share-nothing (each worker opens and closes its own connection per request) and essential in long-running (a single process handling thousands of requests must reuse connections).

The model also explains why PHP frameworks have historically been heavier to bootstrap than Node or Python frameworks: every request pays the bootstrap cost. Tools like Swoole and Laravel Octane exist precisely to amortise that cost by bootstrapping once and serving many requests, at the price of giving up the share-nothing safety net. When debugging a "stale data" bug in an Octane application, the first question to ask is whether a service container was accidentally made stateful across requests.

## Summary

PHP supports two execution models: the share-nothing request/response model that powers almost every traditional PHP deployment, and the long-running application-server model used by Swoole, RoadRunner, and similar tools. The model in use determines whether memory leaks accumulate, whether connection pooling matters, and whether in-memory caches survive between requests. Most PHP developers spend their entire careers in the request/response world and never need the long-running model — but knowing that the second model exists explains both PHP's historical performance reputation and the modern tools that are changing it.
