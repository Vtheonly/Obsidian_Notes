# 3.7.10. Containerization with Docker Multi-Stage Builds

> [!info] Orientation
> Containerization is the foundation of modern application deployment. However, poorly configured containers can bundle development libraries, compilers, and source code into production, leading to bloated images and security vulnerabilities. This note details **Docker Multi-Stage Builds** to produce small, highly secure images for Node.js, Spring Boot, and Laravel.

---

## 1. Why Multi-Stage Builds?

When building container images, you often need development tools, SDKs, and compilers (like npm, Maven, or composer) to compile dependencies and compile assets.

However, once the application is compiled, these tools are no longer required at runtime. Including them in the final production image is poor practice:
* **Large Image Sizes:** Bloated images (often >1GB) slow down CI/CD deployments and container scaling.
* **Security Risks:** Extra binaries and compilers increase the container's attack surface, leaving it vulnerable to exploits.

**Multi-Stage Builds** allow you to declare multiple temporary build containers inside a single `Dockerfile`. You compile your application in the first stage, and then copy *only* the compiled assets or production dependencies into a lightweight second stage (often Alpine or distroless based), leaving the heavy development SDKs and compilers behind.


## 2. Multi-Stage Dockerfile Blueprint: Node.js (Express)

This Dockerfile uses multi-stage builds to compile assets and install dependencies, and then runs the Express server as a non-root user in a lightweight Alpine image:

```dockerfile
# ==============================================================================
# STAGE 1: Build dependencies & compile assets
# ==============================================================================
FROM node:20-alpine AS builder
WORKDIR /app

# Copy dependency manifests first to leverage Docker layer caching
COPY package*.json ./

# Install ALL dependencies (including devDependencies required for bundling)
RUN npm ci

# Copy remaining source code files
COPY . .

# Run build step (e.g., transpiling TypeScript, bundling assets)
RUN npm run build

# ==============================================================================
# STAGE 2: Lightweight Production runtime
# ==============================================================================
FROM node:20-alpine AS runner
WORKDIR /app

# Enforce secure production variables
ENV NODE_ENV=production

# Copy package manifests
COPY package*.json ./

# Install ONLY production dependencies (ignoring devDependencies)
RUN npm ci --only=production

# Copy compiled assets from Stage 1 (builder)
COPY --from=builder /app/dist ./dist

# Run container as a secure, non-root user
USER node

# Expose server port
EXPOSE 3000

# Start server
CMD ["node", "dist/server.js"]
```

## 3. Multi-Stage Dockerfile Blueprint: Java (Spring Boot)

This Dockerfile compiles a Spring Boot application using Maven in the first stage, and then copies the compiled executable JAR file into a slim Java Runtime Environment (JRE) container:

```dockerfile
# ==============================================================================
# STAGE 1: Compile Application using Maven
# ==============================================================================
FROM maven:3.9-eclipse-temurin-17 AS builder
WORKDIR /app

# Copy maven configurations first to leverage layer caching
COPY pom.xml .
RUN mvn dependency:go-offline -B

# Copy application source code
COPY src ./src

# Compile application executable jar (skipping test suite execution for speed)
RUN mvn package -DskipTests

# ==============================================================================
# STAGE 2: Lightweight JRE Runtime environment
# ==============================================================================
FROM eclipse-temurin:17-jre-alpine AS runner
WORKDIR /app

# Create a secure, custom non-root system group and user
RUN addgroup -S spring && adduser -S spring -G spring
USER spring:spring

# Copy ONLY the executable JAR file from Stage 1 (builder)
COPY --from=builder /app/target/*.jarapp.jar

EXPOSE 8080

CMD ["java", "-jar", "app.jar"]
```

## 4. Multi-Stage Dockerfile Blueprint: PHP (Laravel)

This Dockerfile handles Composer dependency management and frontend asset bundling, and then runs Laravel using PHP-FPM and Nginx:

```dockerfile
# ==============================================================================
# STAGE 1: Install Composer Dependencies
# ==============================================================================
FROM composer:2.7 AS composer_builder
WORKDIR /app

COPY database/database.sqlite ./database/
COPY composer.json composer.lock ./

RUN composer install \
    --ignore-platform-reqs \
    --no-interaction \
    --no-plugins \
    --no-scripts \
    --no-dev \
    --prefer-dist

# ==============================================================================
# STAGE 2: Lightweight PHP-FPM Runtime environment
# ==============================================================================
FROM php:8.3-fpm-alpine AS runner
WORKDIR /var/www/html

# Install required PHP extensions (e.g., PDO MySQL)
RUN docker-php-ext-install pdo pdo_mysql

# Copy application code from host
COPY . .

# Copy production vendor folder from Stage 1 (composer_builder)
COPY --from=composer_builder /app/vendor ./vendor

# Set correct ownership permissions for Laravel storage/cache folders
RUN chown -R www-data:www-data /var/www/html/storage /var/www/html/bootstrap/cache

EXPOSE 9000

CMD ["php-fpm"]
```

---

## Summary

Containerizing applications using Docker Multi-Stage Builds is an essential devops practice. By isolating heavy development dependencies (like Node compilers or Maven libraries) in temporary build environments and running the compiled binaries inside slim Alpine or JRE images as a non-root user, developers can achieve fast deployment speeds and robust production security.
