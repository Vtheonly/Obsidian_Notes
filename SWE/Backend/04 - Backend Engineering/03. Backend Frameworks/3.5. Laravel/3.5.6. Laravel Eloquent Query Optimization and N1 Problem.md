# 3.5.6. Laravel Eloquent Query Optimization and the N+1 Problem

> [!info] The N+1 query problem is the single most common performance bottleneck in Active Record ORMs. It occurs when lazy relations are evaluated inside loops, triggering repetitive database round-trips.
> This note explains the causes of N+1, demonstrates eager loading (`with()`) and lazy eager loading (`load()`), and details mass assignment protection strategies using `$fillable` and `$guarded`.

---

## 1. Under the Hood: Why the N+1 Problem Occurs

The **N+1 query problem** is a direct consequence of Eloquent's **Lazy Loading** feature.

By default, when you retrieve models from the database, Eloquent does not fetch their related models. Instead, it waits until you explicitly access the relationship property (e.g., `$post->user`). At that exact moment, Eloquent runs a fresh SQL query to resolve the relation.

This is convenient, but if you access a lazy relation inside a loop over a collection of $N$ parent objects, you will trigger:
* **$1$ Query** to retrieve the parent models.
* **$N$ separate Queries** to retrieve the related model for *each* parent model.

This results in **$N+1$ database queries**. If $N$ is 100, your server makes 101 database round-trips, which can cause significant latency over a network.

```mermaid
mindmap
  root((N+1 Problem))
    Causes
      Default Lazy Loading
      Accessing relations inside loops
    Solutions
      Eager Loading - with() up front
      Lazy Eager Loading - load() on collection
      Strict Mode - preventLazyLoading()
    Security Safeguard
      Mass Assignment whitelists ($fillable)
      Blacklists ($guarded)
```

## 2. Diagnosing and Simulating the Bottleneck

Consider the following controller action, which retrieves all articles and prints their author's name:

```php
// ❌ INCORRECT (Triggers N+1 Queries)
$articles = Article::all();

foreach ($articles as $article) {
    // Accessing 'author' triggers a database lookup on every iteration!
    echo $article->author->name;
}
```

### The Compiled SQL Log:
If you have 5 articles, the SQL logging stream will show:

```sql
-- Query 1 (The "+1" query): Fetch all parent articles
SELECT * FROM articles;

-- Query 2 (The first parent row): Fetch author for Article 1
SELECT * FROM users WHERE id = 1 LIMIT 1;

-- Query 3 (The second parent row): Fetch author for Article 2
SELECT * FROM users WHERE id = 2 LIMIT 1;

-- Query 4: Fetch author for Article 3
SELECT * FROM users WHERE id = 3 LIMIT 1;

-- Query 5: Fetch author for Article 4
SELECT * FROM users WHERE id = 4 LIMIT 1;

-- Query 6: Fetch author for Article 5
SELECT * FROM users WHERE id = 5 LIMIT 1;
```

## 3. Resolving N+1 Using Eager Loading

To solve the N+1 problem, you must instruct Eloquent to pre-fetch relationships up front.

### 3.1 Eager Loading (`with()`)
Using the `with()` method, Eloquent queries the parent rows and the related rows immediately, performing the join in PHP memory. This reduces the number of database round-trips to **exactly two queries**, regardless of how many records are retrieved:

```php
// ✅ CORRECT (Eager Loaded)
$articles = Article::with('author')->get();

foreach ($articles as $article) {
    // Already loaded in memory! No extra queries are executed.
    echo $article->author->name;
}
```

### The Optimized SQL Execution:

```sql
-- Query 1: Fetch all parent articles
SELECT * FROM articles;

-- Query 2: Fetch all related authors in a single IN statement
SELECT * FROM users WHERE id IN (1, 2, 3, 4, 5);
```

### 3.2 Lazy Eager Loading (`load()`)
If you have already retrieved a collection of models and need to eager-load a relationship after the fact (for example, based on conditional logic), use the `load()` method:

```php
$articles = Article::all(); // Uneager loaded

if ($showAuthors) {
    // Eager-loads the relationship on the existing collection
    $articles->load('author'); 
}
```

### 3.3 Preventing Lazy Loading Globally
To prevent N+1 queries from slipping into production, you can instruct Laravel to throw an exception whenever a model attempts to lazy-load a relationship.

Add this check to the `boot()` method of your `AppServiceProvider`:

```php
// app/Providers/AppServiceProvider.php
use Illuminate\Database\Eloquent\Model;

public function boot(): void
{
    // Throws an exception if lazy loading is attempted in local development
    if ($this->app->isLocal()) {
        Model::preventLazyLoading();
    }
}
```

This ensures that any unoptimized query is caught immediately during local testing before it can reach production.

## 4. Mass Assignment Protection

Mass assignment occurs when you pass a user-supplied array of data (such as an incoming HTTP request payload) directly to a model’s creation or update method:

```php
// If unregulated, this is a severe security vulnerability!
Article::create($request->all());
```

If the database table has an `is_admin` or `billing_tier` column, a malicious user could inject `is_admin: true` into their POST payload and escalate their privileges.

Laravel mitigates this vulnerability by requiring models to declare mass-assignment constraints.

### 4.1 Whitelists (`$fillable`)
The `$fillable` array defines a whitelist of attributes that are safe to be mass-assigned. Any key in the input array that is not explicitly defined in the whitelist is silently ignored:

```php
namespace App\Models;

use Illuminate\Database\Eloquent\Model;

class Article extends Model
{
    // Whitelist of columns that can be safely written via mass-assignment
    protected $fillable = ['title', 'body', 'status'];
}
```

If a payload containing `['title' => 'New', 'view_count' => 1000]` is passed, Laravel writes the `title` to the database and filters out the `view_count` update.

### 4.2 Blacklists (`$guarded`)
The `$guarded` array acts as a blacklist of columns that must not be mass-assigned. All other fields are allowed:

```php
class Article extends Model
{
    // Blacklist. Everything except 'id' and 'is_featured' is mass-assignable.
    protected $guarded = ['id', 'is_featured'];
}
```

### 4.3 Why Whitelists are Highly Recommended
* **Security by Default:** When you add a new sensitive column (e.g., `verified_at` or `credit_limit`) to your table via a migration, a whitelist (`$fillable`) naturally protects it because you must explicitly modify your model file to allow writing to it.
* **Guarded Risks:** If you use `$guarded = []` (allowing everything) and add a sensitive column to the table, that column is immediately exposed to mass-assignment vulnerabilities across all endpoints unless you update your model files.

---

## 5. Summary

The N+1 query problem is caused by Eloquent's default lazy-loading model, which executes a query per parent row when relations are accessed inside loops. To prevent this, developers can use eager loading with `with()` or lazy eager loading with `load()` to group database queries. Mass assignment vulnerabilities can be managed using whitelists (`$fillable`) or blacklists (`$guarded`), with whitelists being the recommended standard for secure model development.
