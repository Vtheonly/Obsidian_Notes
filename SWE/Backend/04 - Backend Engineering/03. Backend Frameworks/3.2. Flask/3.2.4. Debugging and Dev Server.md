# 3.2.4. Debugging and Dev Server

> [!info] Orientation
> The Flask development server is what runs your code locally. This note covers the `flask run` command, environment variables, what debug mode actually enables (and why you must never use it in production), how to expose the server on your network, modern `--app` and `--debug` flags, basic logging configuration, and the common startup errors you will hit.

## 1. The Built-in Development Server

Flask ships with a WSGI server based on Werkzeug. It is intentionally minimal: single-threaded by default, no HTTP/2, no production-grade connection handling. Its job is to give you the fastest possible feedback loop during development — start the server, edit code, refresh the browser. It is **not** a production server. Werkzeug's own documentation says so explicitly. For production you put a real WSGI server (Gunicorn, uWSGI) behind a reverse proxy (Nginx, Caddy). The dev server is also the home of the interactive debugger, which is one of the best development tools in the Python web ecosystem.

## 2. Starting the Server

There are two equivalent ways to start the dev server. The first is the `flask run` CLI command, which is the modern recommended approach. The second is calling `app.run()` directly inside a Python file, which is simpler for tiny scripts and tutorials.

```bash
# Method 1: flask run
export FLASK_APP=app.py
flask run
```

```python
# Method 2: app.run()
from app import app

if __name__ == "__main__":
    app.run(debug=True)
```

With method 1, Flask needs to know where your app is. The `FLASK_APP` environment variable points to the module (`app.py`), package (`myproject`), or factory (`myproject:create_app`) that produces the Flask instance. With method 2, the location is implicit — you are already in the file that imports the app.

## 3. Modern --app and --debug Flags

Flask 2.2 introduced `--app` and `--debug` as command-line flags, removing the need to set environment variables for the common case. The flags set the same state as `FLASK_APP` and `FLASK_DEBUG`, but only for the duration of the command.

```bash
flask --app app.py run
flask --app app.py --debug run
flask --app 'myproject:create_app()' run --host=0.0.0.0 --port=8000
```

The `--app` value follows the same rules as `FLASK_APP`: a module path, optionally followed by `:factory_name` to call a factory function. The `--debug` flag enables debug mode (reloader + interactive debugger) for that single invocation. Using the flags instead of exported variables keeps your shell clean and makes the launch command self-documenting — a single `flask --app app.py --debug run` is enough to read at a glance what is happening.

## 4. What Debug Mode Enables

`debug=True` (or `FLASK_DEBUG=1`, or `--debug`) turns on two distinct features.

**The reloader** watches your Python source files for changes and restarts the server automatically when any of them change on disk. Without it, every code change requires stopping the server (`Ctrl-C`) and restarting it. With it, you save a file in your editor and the next browser refresh already reflects the change. The reloader can also watch extra files (`--extra-files path1,path2`) for projects that depend on non-Python configuration files.

**The Werkzeug interactive debugger** replaces the generic 500 error page with a full interactive traceback. Each frame in the traceback shows the source code, local variables, and a small console icon that opens a Python REPL in the context of that frame. You can inspect variables, evaluate expressions, and even call functions to test fixes without leaving the browser. This is invaluable for diagnosing bugs that depend on the exact request state.

## 5. The Debugger PIN

The interactive console can execute arbitrary Python code, so Werkzeug protects it with a PIN. The first time you click a console icon, the browser prompts for a PIN that Werkzeug has printed to the terminal at startup. The PIN is derived from the machine's hostname, MAC address, and username, so it is stable across restarts on the same machine but not guessable remotely.

```text
 * Debugger PIN: 123-456-789
```

The PIN is a defense-in-depth measure, not a license to expose debug mode to a network. If `debug=True` and your dev server is bound to `0.0.0.0`, anyone on your local network who can guess the PIN — or, on some Werkzeug versions, exploit weaknesses in the PIN derivation — gets full Python execution on your machine. Treat debug mode as you would treat root access.

## 6. Why Debug Mode Must Never Reach Production

The debugger is a remote code execution vector. Every public-facing Flask application that has been caught running with `debug=True` has been compromised within hours, often through automated scanners. The rule is absolute: `debug=True` is for development only. Production deployments use `debug=False` (the default) and rely on logs and an error tracker (Sentry, Rollbar) for diagnostics. If you absolutely must inspect a running production app, attach a remote debugger like `debugpy` over an SSH tunnel, never the Werkzeug debugger.

## 7. Host and Port

By default the dev server binds to `127.0.0.1:5000` — loopback only, so only your machine can reach it. To test from another device on your LAN (a phone, a colleague's laptop), bind to `0.0.0.0`:

```bash
flask --app app.py run --host=0.0.0.0 --port=8000
```

```python
app.run(host="0.0.0.0", port=8000, debug=True)
```

Binding to `0.0.0.0` exposes the server to every interface on the host. On a coffee-shop Wi-Fi, that means everyone in the shop. Use it only on trusted networks and only when necessary. For testing mobile clients, a tool like `ngrok` or `cloudflared` tunnelled through your own machine is safer than opening the dev server directly.

## 8. Logging Configuration

Flask's `app.logger` is a standard `logging.Logger` with the name `flask.app`. By default it writes to stderr at the `WARNING` level. For development, configure it explicitly so you see debug and info messages from your own code:

```python
import logging

logging.basicConfig(
    level=logging.DEBUG,
    format="%(asctime)s %(levelname)s %(name)s: %(message)s",
)

@app.route("/")
def index():
    app.logger.info("Index page visited")
    app.logger.debug("Request headers: %s", dict(request.headers))
    return "Hello"
```

For production, attach handlers (file, syslog, Sentry) and set the level to `INFO` or `WARNING`. Never use `print()` for production diagnostics — it bypasses the logging framework, cannot be filtered, and writes to a stdout that may or may not be captured depending on how the WSGI server is configured. Use `app.logger.exception()` inside an error handler to log the full traceback automatically.

## 9. Common Startup Errors

A handful of errors account for most "why won't my server start" moments.

**Port already in use.** Werkzeug raises `OSError: [Errno 98] Address already in use`. The fix is either to find and kill the process holding port 5000 (`lsof -i :5000` on macOS/Linux) or to start Flask on a different port (`--port=5001`). A common cause on macOS is the system ControlCenter, which uses port 5000 for AirPlay Receiver; either disable AirPlay Receiver or pick another port.

**Module not found.** Flask raises `Error: Failed to find Flask application or factory` or `ModuleNotFoundError: No module named 'myproject'`. The cause is usually one of three: `FLASK_APP` / `--app` points to the wrong path, the virtual environment is not activated, or the package's `__init__.py` is missing. Verify with `python -c "import myproject"` from the same shell you use to run `flask run`.

**Circular import.** A `ImportError: cannot import name 'app' from partially initialized module` means two modules import each other at top level. The fix is the application factory pattern from [[3.2.2. Project Structure]] — move the `app` creation into a function and import blueprints inside the function body.

**SyntaxError.** Python prints the file and line. Edit the file, save, and the reloader restarts automatically. If the syntax error is in the file Flask is trying to import as the app, the server will not start until it is fixed.

## Summary

The Flask dev server runs locally, supports the `flask run` CLI and `app.run()` direct invocation, and exposes debug mode through `FLASK_DEBUG=1`, `--debug`, or `debug=True`. Debug mode enables the reloader and the Werkzeug interactive debugger, which is indispensable for development and dangerous in production. Bind to `0.0.0.0` only on trusted networks. Configure logging explicitly and never use `print()` for diagnostics. Most startup failures are port conflicts, module-not-found, or circular imports — all diagnosable with a one-line shell command.
