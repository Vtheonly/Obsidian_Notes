# 3.2.10. Sessions and Cookies in Flask

> [!info] Orientation
> HTTP is stateless; Flask sessions bridge that gap. This note covers Flask's default signed-cookie session, the role of `secret_key`, the `session` object API, why default sessions are not server-side, swapping to Flask-Session for Redis/filesystem/memcached backends, manual cookie handling with `request.cookies` and `set_cookie`, and the security flags every cookie should carry.

## 1. Why Sessions Exist

Every HTTP request is independent — the server has no built-in way to know that two requests came from the same user. Without a session layer, you would have to send the user's identity and preferences in every request, which is impractical and insecure. Sessions add a small piece of state keyed by a token stored in a cookie. The browser sends the cookie automatically with every request, and the server uses the token to look up (or decrypt) the session state.

Flask provides two distinct cookie mechanisms. The lower-level one is `set_cookie` / `request.cookies`, where you write and read arbitrary cookies by hand. The higher-level one is the `session` object, which is a dict-like API on top of a single signed cookie named `session` by default. For most stateful features (login, cart, flash messages) you want the `session` object, not raw cookies.

## 2. The Default Session: Signed Cookies

Flask's default session implementation stores the entire session data, JSON-serialized, in a single cookie on the user's browser. The cookie is signed with HMAC using `app.secret_key` so that the user cannot tamper with it — change one byte and the signature fails. The cookie is **not encrypted**: anyone who can read the cookie (the user, anyone with access to the browser, anyone sniffing HTTP) can decode it and read its contents. The signature only protects against modification.

```python
from flask import session

@app.route("/login", methods=["POST"])
def login():
    user = authenticate(request.form["username"], request.form["password"])
    if user:
        session["user_id"] = user.id
        session["login_at"] = datetime.utcnow().isoformat()
        return redirect(url_for("dashboard"))
    return "Invalid credentials", 401

@app.route("/dashboard")
def dashboard():
    user_id = session.get("user_id")
    if not user_id:
        return redirect(url_for("login"))
    return f"Welcome, user {user_id}"
```

The `session` object behaves like a Python dict. `session["key"] = value` writes; `session.get("key")` reads; `session.pop("key")` removes; `session.clear()` wipes everything. The cookie is sent on every response that modifies the session. The default cookie name is `session`; override it with `app.config["SESSION_COOKIE_NAME"]`.

## 3. The Secret Key

`app.secret_key` is the HMAC key used to sign the session cookie. It must be set to a long, random, unguessable string. If it is empty or default, Flask raises a runtime error the first time you touch `session`. If it is short or predictable, an attacker can forge a session cookie with any contents they want — including `{"user_id": 1}` to log in as admin.

```python
# Set from environment variable, fail loudly if missing
app.secret_key = os.environ["SECRET_KEY"]
```

Generate a strong key with `python -c "import secrets; print(secrets.token_hex(32))"` and store it in `.env`. Never commit a real secret key to version control. Rotating the key invalidates all existing sessions (every user is logged out), so rotation is a planned event, not an everyday operation.

## 4. What the Default Session Is Not

The default Flask session is **not server-side**. There is no server-side store; the cookie is the store. This has three consequences you must internalize.

First, **size**. Cookies are limited to 4 KB total per domain. A Flask session cookie includes the data, the timestamp, and the signature, so the practical limit is about 3.5 KB of data. Storing a shopping cart with 50 items will blow that limit and Flask will silently drop the cookie.

Second, **privacy**. The contents are visible to the user. Do not store anything sensitive (passwords, tokens, internal IDs you do not want exposed) in the default session. The user can base64-decode the cookie in their browser devtools and read every byte.

Third, **revocation**. Because the state lives on the client, you cannot invalidate a session server-side. If a user's laptop is stolen, you cannot log them out remotely — the cookie is still valid until it expires or the secret key is rotated.

## 5. Server-Side Sessions with Flask-Session

When the default session is not enough, install Flask-Session and swap the backend to Redis, the filesystem, memcached, or a database. The session data lives on the server; the cookie holds only a session ID.

```bash
pip install Flask-Session
```

```python
# config.py
class Config:
    SECRET_KEY = os.environ["SECRET_KEY"]
    SESSION_TYPE = "redis"
    SESSION_PERMANENT = False
    SESSION_USE_SIGNER = True       # sign the session ID cookie
    PERMANENT_SESSION_LIFETIME = timedelta(hours=1)
```

```python
# app/__init__.py
from flask_session import Session

def create_app():
    app = Flask(__name__)
    app.config.from_object(Config)
    Session(app)
    return app
```

The `session` object API is unchanged — you still write `session["user_id"] = user.id` and read `session.get("user_id")`. The difference is that the cookie now contains only a session ID, and Flask-Session fetches the data from the configured backend on each request. The 4 KB limit disappears, the contents are not visible to the user, and you can revoke a session by deleting it from the backend.

| `SESSION_TYPE` | Backend | Use case |
| --------------- | ------- | -------- |
| `redis` | Redis | Production, fast, supports expiry natively |
| `filesystem` | Local files | Single-process apps, dev, tests |
| `memcached` | Memcached | High-throughput ephemeral sessions |
| `mongodb` | MongoDB | When you already run Mongo |
| `sqlalchemy` | SQL database | When you want sessions in your existing DB |

For a deeper comparison of when to use server-side sessions vs stateless tokens (JWTs), see [[1.3. Cookies and Session Management]] and [[1.5. Stateless vs Stateful APIs]].

## 6. Manual Cookie Handling

For everything outside the `session` object — "remember me" tokens, feature flags, analytics IDs — use `request.cookies` to read and `response.set_cookie` to write.

```python
from flask import make_response

@app.route("/set-theme")
def set_theme():
    theme = request.args.get("theme", "light")
    resp = make_response(redirect(url_for("index")))
    resp.set_cookie("theme", theme, max_age=365*24*3600, httponly=True, samesite="Lax")
    return resp

@app.route("/")
def index():
    theme = request.cookies.get("theme", "light")
    return render_template("index.html", theme=theme)
```

`request.cookies` is a dict-like object; missing keys return `None` (or the default you pass to `get`). `set_cookie` accepts the full set of RFC 6265 attributes: `max_age`, `expires`, `path`, `domain`, `secure`, `httponly`, `samesite`. Setting a cookie to an empty value with `max_age=0` deletes it.

## 7. Cookie Security Flags

Three flags on every authentication-related cookie are non-negotiable in production.

**`HttpOnly=True`** prevents JavaScript from reading the cookie via `document.cookie`. This stops the most common form of session theft — an XSS payload that exfiltrates the session cookie. The `session` object sets this by default; for `set_cookie` you must set it explicitly.

**`Secure=True`** ensures the cookie is only sent over HTTPS. Without it, the cookie is sent in the clear on any HTTP request, exposing it to anyone on the same network. In production behind HTTPS, set this; in local dev over HTTP, leave it off so you can actually use the cookie.

**`SameSite`** controls when the cookie is sent on cross-site requests. `SameSite=Strict` never sends the cookie on cross-site requests (most secure, but breaks links from email). `SameSite=Lax` sends the cookie on top-level GETs from other sites (the modern default, good for most apps). `SameSite=None; Secure` sends the cookie everywhere (required for third-party cookies and iframes, must be paired with `Secure`).

```python
app.config.update(
    SESSION_COOKIE_SECURE=True,     # HTTPS only
    SESSION_COOKIE_HTTPONLY=True,   # no JS access
    SESSION_COOKIE_SAMESITE="Lax",  # send on top-level GETs only
)
```

Flask's `session` cookie honors these settings; set them globally on `app.config` rather than per-response.

## 8. Session Lifetime and Expiry

By default, Flask sessions are browser-session cookies — they disappear when the browser closes. To make them persistent, set `PERMANENT_SESSION_LIFETIME` and call `session.permanent = True`:

```python
from datetime import timedelta

app.config["PERMANENT_SESSION_LIFETIME"] = timedelta(days=7)

@app.route("/login", methods=["POST"])
def login():
    # ...
    session.permanent = True   # cookie lives for 7 days, not just this browser session
    session["user_id"] = user.id
    return redirect(url_for("dashboard"))
```

Flask's signed-cookie session embeds the lifetime in the cookie and respects it client-side. Flask-Session backends store the lifetime server-side and delete expired entries automatically (for Redis, via native key expiry). For "log me out everywhere" features, server-side sessions are required — there is no way to revoke a signed cookie without rotating the secret key.

## 9. Flash Messages

The `flash(message, category)` function stores a one-time message in the session, intended to be displayed on the next request after a redirect. It is the canonical way to show "post created" or "invalid login" feedback.

```python
from flask import flash

@app.route("/post/new", methods=["POST"])
def new_post():
    # ... create post ...
    flash("Post created successfully.", "success")
    return redirect(url_for("show_post", post_id=post.id))
```

```html
<!-- in template, after redirect -->
{% with messages = get_flashed_messages(with_categories=true) %}
  {% if messages %}
    <ul class="flashes">
      {% for category, message in messages %}
        <li class="flash-{{ category }}">{{ message }}</li>
      {% endfor %}
    </ul>
  {% endif %}
{% endwith %}
```

`get_flashed_messages` pops the messages from the session, so they appear once. The `with_categories=true` argument returns `(category, message)` tuples so you can style by category.

## Summary

Flask's default session is a signed (not encrypted) cookie named `session`, signed with `app.secret_key`. It is limited to ~3.5 KB, not private, and not revocable. For larger or sensitive data, swap to Flask-Session with Redis or filesystem backends. For cookies outside the session, use `request.cookies` and `response.set_cookie` with `HttpOnly`, `Secure`, and `SameSite=Lax` set. The session lifetime is controlled by `PERMANENT_SESSION_LIFETIME` and `session.permanent = True`. The next note, [[3.2.11. Blueprints and Modular Design]], shows how to organize a Flask app that has grown past a single routes file.
