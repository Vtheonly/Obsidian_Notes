# 3.2.12. Authentication Basics in Flask

> [!info] Orientation
> Flask has no built-in auth system — you build it from Werkzeug's password helpers, the session object, and optionally Flask-Login for the user-loading machinery. This note covers password hashing, the login flow, the `@login_required` decorator, Flask-Login's `LoginManager`, logout, "remember me", and HTTP Basic/Bearer auth via Flask-HTTPAuth.

## 1. The Authentication Problem

Authentication answers "who is making this request?". The standard answer for browser apps is the **session cookie**: the user logs in once, the server stores their user ID in the session, the browser sends the session cookie on every subsequent request, and the server reads the cookie to identify the user. For API clients that do not want cookies, the answer is a **bearer token**: the user logs in once, the server issues a signed token, the client sends it in the `Authorization` header on every subsequent request. Flask supports both, and a real app often supports both simultaneously — sessions for the web UI, tokens for the API.

Authentication is layered on top of four Flask features covered elsewhere in this chapter: `session` ([[3.2.10. Sessions and Cookies in Flask]]), blueprints ([[3.2.11. Blueprints and Modular Design]]), error handling ([[3.2.14. Error Handling]]), and the request/response cycle ([[3.2.3. Routes and Views]]). This note covers the auth-specific pieces that sit on top of those foundations.

## 2. Password Hashing with Werkzeug

Never store passwords in plaintext. Never store them with a fast hash like MD5 or SHA-256 — those can be brute-forced at billions of attempts per second on modern GPUs. Use a slow, salted hash designed for passwords. Werkzeug provides `generate_password_hash` and `check_password_hash`, which use PBKDF2-HMAC-SHA256 by default with a per-password salt and a configurable iteration count.

```python
from werkzeug.security import generate_password_hash, check_password_hash

# At registration:
user.password_hash = generate_password_hash("correct horse battery staple")

# At login:
if check_password_hash(user.password_hash, submitted_password):
    # password is correct
else:
    # password is wrong
```

`generate_password_hash(password, method="scrypt", salt_length=16)` produces strings like `scrypt:32768:8:1$<salt>$<hash>`. The method and parameters are embedded in the string, so you can change the default later without invalidating existing hashes — `check_password_hash` reads the method from the stored value. For a new project, prefer `scrypt` (Werkzeug 2.3+) or `pbkdf2:sha256:600000` (a high iteration count). Never invent your own hashing scheme.

## 3. The Login Flow

A login flow has three parts: a form to collect credentials, a view to verify them and set the session, and a way to read the session on subsequent requests to identify the user.

```python
# auth/routes.py
from flask import Blueprint, request, session, redirect, url_for, render_template, flash
from werkzeug.security import check_password_hash
from app.models import User

bp = Blueprint("auth", __name__, url_prefix="/auth")

@bp.route("/login", methods=["GET", "POST"])
def login():
    if request.method == "POST":
        username = request.form["username"]
        password = request.form["password"]
        user = User.query.filter_by(username=username).first()
        if user and check_password_hash(user.password_hash, password):
            session.clear()
            session["user_id"] = user.id
            return redirect(url_for("dashboard"))
        flash("Invalid username or password.", "error")
    return render_template("auth/login.html")
```

The `session.clear()` before setting the new `user_id` is important — it prevents session fixation, where an attacker tricks the user into logging in with an attacker-known session ID. Starting with a fresh session on every login ensures the attacker cannot ride on it.

## 4. Loading the Current User

On every request that needs to know who is logged in, you have to translate `session["user_id"]` into a `User` object. Doing this in every view is repetitive; the standard solution is a `before_request` hook (or Flask-Login's `user_loader`, covered below) that loads the user and attaches it to the request.

```python
from flask import g

@app.before_request
def load_logged_in_user():
    user_id = session.get("user_id")
    g.user = User.query.get(user_id) if user_id else None
```

Now every view can access `g.user` — `None` if not logged in, the `User` object otherwise. The `g` object lives for the duration of the request and is torn down at the end, so there is no cross-request leakage.

## 5. The @login_required Decorator

Routes that require authentication should be protected by a decorator that checks for the user and redirects to login if absent.

```python
from functools import wraps
from flask import redirect, url_for, request, session

def login_required(view):
    @wraps(view)
    def wrapped(*args, **kwargs):
        if g.get("user") is None:
            return redirect(url_for("auth.login", next=request.path))
        return view(*args, **kwargs)
    return wrapped

@app.route("/dashboard")
@login_required
def dashboard():
    return f"Welcome, {g.user.username}"
```

The `next=request.path` query parameter lets the login view redirect back to the originally-requested page after successful authentication. Always validate `next` is a relative URL before redirecting to it — an open redirect to `https://evil.com` is a real vulnerability.

## 6. Flask-Login

Flask-Login is a small library that handles the user-loading machinery, the `current_user` proxy, the "remember me" cookie, and the `@login_required` decorator. It is not an auth system itself — you still do password hashing and the login view — but it removes the boilerplate.

```bash
pip install Flask-Login
```

```python
# extensions.py
from flask_login import LoginManager
login_manager = LoginManager()
login_manager.login_view = "auth.login"
login_manager.login_message_category = "info"
```

```python
# models/user.py
from flask_login import UserMixin

class User(UserMixin, db.Model):
    id = db.Column(db.Integer, primary_key=True)
    username = db.Column(db.String(80), unique=True, nullable=False)
    password_hash = db.Column(db.String(255), nullable=False)

    # UserMixin provides: is_authenticated, is_active, is_anonymous, get_id()
```

```python
# app/__init__.py
@login_manager.user_loader
def load_user(user_id):
    return User.query.get(int(user_id))
```

```python
# auth/routes.py
from flask_login import login_user, logout_user, login_required, current_user

@bp.route("/login", methods=["GET", "POST"])
def login():
    # ... validate credentials ...
    login_user(user, remember=True)   # sets the session, handles "remember me"
    return redirect(request.args.get("next") or url_for("dashboard"))

@bp.route("/logout")
@login_required
def logout():
    logout_user()                     # clears the session
    return redirect(url_for("index"))

@app.route("/dashboard")
@login_required
def dashboard():
    return f"Welcome, {current_user.username}"
```

`current_user` is a thread-local proxy that resolves to the loaded user (or an `AnonymousUserMixin` if not logged in). `login_user(user, remember=True)` sets the session and creates a separate long-lived "remember me" cookie so the user stays logged in across browser restarts. `logout_user()` clears both.

## 7. The user_loader Callback

Flask-Login calls `user_loader` once per request to translate the session's user ID into a `User` object. The callback receives the ID as a string (whatever `get_id()` returned) and returns the user or `None`.

```python
@login_manager.user_loader
def load_user(user_id):
    return db.session.get(User, int(user_id))
```

`db.session.get(User, id)` is the modern SQLAlchemy 2.0 way to load by primary key; it uses the identity map cache, so repeated calls in the same request do not hit the database. For high-throughput apps where the user object is large, cache it in Redis keyed by user ID, with a short TTL.

## 8. Remember Me

The "remember me" feature stores a separate token cookie (named `remember_token` by default) that survives browser restarts, in addition to the session cookie that disappears when the browser closes. Flask-Login generates and validates this token automatically when you pass `remember=True` to `login_user`. The token is signed with `SECRET_KEY` and contains the user ID plus a hash of the user's password — so changing the password invalidates all "remember me" tokens for that user, a useful security property.

For custom (non-Flask-Login) implementations, "remember me" means setting `session.permanent = True` and `PERMANENT_SESSION_LIFETIME` to a long duration (e.g., 30 days). The trade-off is convenience against the risk of a stolen laptop having a 30-day-old valid session.

## 9. Logout

Logout clears the session. With raw Flask:

```python
@bp.route("/logout")
def logout():
    session.clear()
    return redirect(url_for("index"))
```

With Flask-Login:

```python
@bp.route("/logout")
@login_required
def logout():
    logout_user()
    return redirect(url_for("index"))
```

`logout_user()` also clears the "remember me" cookie. After logout, the user must log in again to access protected routes.

## 10. HTTP Basic and Bearer Auth with Flask-HTTPAuth

For APIs that authenticate with HTTP Basic or Bearer tokens rather than cookies, Flask-HTTPAuth is the standard library. It provides decorators that run a verification callback before the view and expose the authenticated user via `current_user`.

```bash
pip install Flask-HTTPAuth
```

```python
from flask_httpauth import HTTPBearerAuth
from werkzeug.security import check_password_hash

bearer_auth = HTTPBearerAuth()

@bearer_auth.verify_token
def verify_token(token):
    user = User.verify_auth_token(token)
    if user:
        return user
    return None

@bp.route("/api/profile")
@bearer_auth.login_required
def api_profile():
    return {"username": bearer_auth.current_user().username}
```

For issuing tokens, the standard pattern is a `POST /api/token` endpoint that takes username + password (verified with `check_password_hash`) and returns a signed token (using `itsdangerous.URLSafeTimedSerializer` or a JWT). The client stores the token and sends it in the `Authorization: Bearer <token>` header on every subsequent request. For a deeper treatment of token formats, see [[1.4. Token-Based Authentication]] and [[1.6. API Authentication Patterns]].

## Summary

Password hashing uses Werkzeug's `generate_password_hash` / `check_password_hash` with PBKDF2 or scrypt; never store plaintext or fast-hashed passwords. The login flow verifies credentials, clears the session (to prevent fixation), and sets `session["user_id"]`. The `@login_required` decorator protects routes; Flask-Login provides the same machinery plus `current_user`, `user_loader`, and "remember me". For APIs, Flask-HTTPAuth handles HTTP Basic and Bearer tokens. Always validate redirect targets, set `Secure`/`HttpOnly`/`SameSite` on session cookies, and rotate `SECRET_KEY` only as a planned event. The next note, [[3.2.13. APIs with Flask and JSON]], builds on this for JSON-first API design.
