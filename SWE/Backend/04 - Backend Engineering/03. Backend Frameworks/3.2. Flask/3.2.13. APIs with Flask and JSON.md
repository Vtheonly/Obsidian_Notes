# 3.2.13. APIs with Flask and JSON

> [!info] Orientation
> Flask is a popular choice for JSON APIs because `jsonify()` and `request.get_json()` cover the basics in two lines. This note covers returning JSON, parsing request bodies, status codes and headers, content negotiation, JSON error handlers, the `/api/v1` blueprint pattern, and the higher-level libraries Flask-RESTful, Flask-RESTX, and Flask-Smorest that add request parsing, response marshalling, and automatic OpenAPI generation.

## 1. JSON in Flask

Flask 1.1 made returning a `dict` from a view function equivalent to returning `jsonify(dict)`. Flask 2.2 added `list` return values to the same shortcut. So a minimal JSON endpoint is:

```python
@app.route("/api/health")
def health():
    return {"status": "ok", "version": "1.0"}
```

Flask serializes the dict with its JSON provider (which defaults to a thin wrapper around the stdlib `json` module), sets `Content-Type: application/json`, and returns `200 OK`. For full control, use `jsonify()` explicitly:

```python
from flask import jsonify

@app.route("/api/users/<int:user_id>")
def get_user(user_id):
    user = db.session.get(User, user_id)
    if user is None:
        return jsonify(error="User not found"), 404
    return jsonify(id=user.id, username=user.username, email=user.email)
```

`jsonify` accepts keyword arguments or a single dict/list, and returns a `Response` object — so you can chain status codes and headers naturally: `return jsonify(...), 201, {"Location": url_for("get_user", user_id=42, _external=True)}`.

## 2. Parsing the Request Body

For JSON request bodies, `request.get_json()` is the standard call. It returns the parsed Python object (usually a dict) or raises `400 Bad Request` if the body is not valid JSON. Pass `silent=True` to get `None` instead of an exception, and `force=True` to parse regardless of `Content-Type` (use sparingly).

```python
@app.route("/api/users", methods=["POST"])
def create_user():
    data = request.get_json()
    if not data or "username" not in data or "email" not in data:
        return jsonify(error="Missing required fields"), 400

    user = User(username=data["username"], email=data["email"])
    db.session.add(user)
    db.session.commit()
    return jsonify(id=user.id, username=user.username), 201
```

For form-encoded bodies, use `request.form`. For multipart uploads, use `request.files`. For query string parameters, use `request.args`. The four sources (`args`, `form`, `files`, `json`) are mutually exclusive on a single request — you do not get both `form` and `json` from the same body.

## 3. Status Codes and Headers

A view can return a tuple of `(body, status)`, `(body, status, headers)`, or a `Response` object directly. For APIs, the second form is the most common:

```python
@app.route("/api/posts", methods=["POST"])
def create_post():
    data = request.get_json()
    post = Post(title=data["title"], body=data["body"], author_id=current_user.id)
    db.session.add(post)
    db.session.commit()
    location = url_for("get_post", post_id=post.id, _external=True)
    return jsonify(post.to_dict()), 201, {"Location": location}
```

The HTTP status code semantics that matter for APIs:

| Code | Meaning | When to use |
| ---- | ------- | ----------- |
| `200 OK` | Success on GET / PUT / PATCH / DELETE | Default for successful reads and updates |
| `201 Created` | New resource created | After successful POST that creates a row |
| `204 No Content` | Success with no body | After successful DELETE |
| `400 Bad Request` | Malformed input | Missing fields, wrong types, invalid JSON |
| `401 Unauthorized` | Authentication required or failed | No token, bad token |
| `403 Forbidden` | Authenticated but not allowed | Wrong role, no permission |
| `404 Not Found` | Resource does not exist | ID not in DB |
| `409 Conflict` | State conflict | Duplicate unique field |
| `422 Unprocessable Entity` | Valid JSON but semantically wrong | Validation failure |
| `500 Internal Server Error` | Server bug | Unhandled exception |

The `Location` header on a `201 Created` response should point to the URL of the newly-created resource; this is a REST convention that lets clients fetch the new resource without you embedding the URL in the body.

## 4. Content Negotiation

A real API serves both JSON and (sometimes) XML or other formats, based on the client's `Accept` header. Flask's `request.accept_mimetypes` lets you inspect what the client wants:

```python
@app.route("/api/posts/<int:post_id>")
def get_post(post_id):
    post = db.session.get(Post, post_id)
    if post is None:
        return jsonify(error="Not found"), 404
    if request.accept_mimetypes.best == "application/xml":
        return Response(post_to_xml(post), mimetype="application/xml")
    return jsonify(post.to_dict())
```

In practice, modern APIs are JSON-only and you can ignore content negotiation. If you do support multiple formats, push the dispatch into a helper function rather than scattering `if` statements through your views. For a deeper treatment of content negotiation and the REST constraints, see [[1.2. RESTful API Design and Constraints]].

## 5. JSON Error Responses

API clients expect errors as JSON, not HTML. The error handler from [[3.2.14. Error Handling]] should detect API requests and respond accordingly.

```python
@app.errorhandler(400)
def bad_request(error):
    if request.path.startswith("/api/"):
        return jsonify(error=str(error.description)), 400
    return render_template("errors/400.html"), 400

@app.errorhandler(404)
def not_found(error):
    if request.path.startswith("/api/"):
        return jsonify(error="Resource not found", path=request.path), 404
    return render_template("errors/404.html"), 404

@app.errorhandler(500)
def server_error(error):
    app.logger.exception("Unhandled error in API")
    if request.path.startswith("/api/"):
        return jsonify(error="Internal server error"), 500
    return render_template("errors/500.html"), 500
```

A more robust version checks `request.is_json` (true if `Content-Type` or `Accept` is JSON) rather than the path prefix, which handles the case where an API is mounted at `/` instead of `/api/`. The shape of the error body should be consistent across the whole API — pick `{error: "..."}` or RFC 7807 problem+json and stick with it.

## 6. The /api/v1 Blueprint Pattern

Versioning your API from day one is cheap insurance against future breaking changes. The standard pattern is to mount the API blueprint at `/api/v1`:

```python
# api/__init__.py
from flask import Blueprint
bp = Blueprint("api", __name__, url_prefix="/api/v1")

from . import routes  # noqa: register views
```

```python
# app/__init__.py
from .api import bp as api_bp
app.register_blueprint(api_bp)
```

When you need to ship a breaking change, create a second blueprint mounted at `/api/v2` with the new behavior, and leave `/api/v1` running for existing clients. Deprecate the old version with a `Sunset` header, give clients a migration window, and remove the old blueprint when telemetry shows no traffic.

URL-prefix versioning is the simplest and most compatible approach. Header-based versioning (`Accept: application/vnd.myapp.v2+json`) is more elegant but harder for clients to use and harder to debug. Query-string versioning (`?version=2`) is the worst of the options because it gets cached and logged separately from the path.

## 7. Input Validation

Manual validation grows tedious fast. The standard solutions are:

| Library | Approach |
| ------- | -------- |
| Pydantic | Type-annotated model classes with auto-validation |
| Marshmallow | Schema classes with explicit field definitions |
| Flask-Smorest | Marshmallow + OpenAPI generation |
| Flask-RESTX | Built-in input models with auto-generated Swagger UI |

A Pydantic-based endpoint looks like this:

```python
from pydantic import BaseModel, EmailStr, ValidationError
from flask import abort

class CreateUserRequest(BaseModel):
    username: str
    email: EmailStr

@app.route("/api/users", methods=["POST"])
def create_user():
    try:
        req = CreateUserRequest.model_validate(request.get_json())
    except ValidationError as e:
        return jsonify(error="validation_failed", details=e.errors()), 422
    user = User(username=req.username, email=req.email)
    db.session.add(user)
    db.session.commit()
    return jsonify(id=user.id), 201
```

Pydantic validates the input, returns helpful error details, and gives you a typed object to work with. Marshmallow serves the same need with a slightly different API and is more common in the Flask ecosystem because of Flask-Smorest.

## 8. Flask-RESTful, Flask-RESTX, Flask-Smorest

Three libraries sit on top of Flask and add API-specific structure: request parsing, response marshalling, and (for the latter two) automatic OpenAPI / Swagger UI generation.

**Flask-RESTful** is the oldest and lightest. It adds a `Resource` class with one method per HTTP verb and a `reqparse` object for input validation. It is in maintenance mode — new projects should pick one of the others.

**Flask-RESTX** is a fork of Flask-RESTful that adds automatic Swagger UI generation and a richer input-model system. It is the right pick if you want a batteries-included API framework with a browsable docs UI.

**Flask-Smorest** is the most modern, built on Marshmallow and `apispec`. It generates a clean OpenAPI 3.0 spec from your Marshmallow schemas, with minimal boilerplate:

```python
from flask_smorest import Api, Blueprint, abort
from marshmallow import Schema, fields

blp = Blueprint("users", "users", url_prefix="/api/users", description="User operations")

class UserSchema(Schema):
    id = fields.Integer(dump_only=True)
    username = fields.String(required=True)
    email = fields.Email(required=True)

@blp.route("/")
class UsersList(Resource):
    @blp.arguments(UserSchema)
    @blp.response(201, UserSchema)
    def post(self, new_user):
        user = User(**new_user)
        db.session.add(user)
        db.session.commit()
        return user

    @blp.response(200, UserSchema(many=True))
    def get(self):
        return User.query.all()

api = Api(app, spec_kwargs={"title": "My API", "version": "v1"})
api.register_blueprint(blp)
```

The `@blp.arguments` decorator validates the request body against the schema; `@blp.response` validates the response and documents it in the OpenAPI spec. The spec is served at `/api/openapi.json` and you can mount Swagger UI or ReDoc to browse it.

## 9. CORS

Browser-based clients on a different origin from your API will need CORS headers. Flask-CORS is the standard library:

```bash
pip install Flask-CORS
```

```python
from flask_cors import CORS

CORS(app, resources={r"/api/*": {"origins": ["https://myapp.com", "http://localhost:3000"]}})
```

For public APIs, you can allow `*` (any origin) but be aware this disables credentialed requests. For APIs with cookies or auth headers, you must enumerate the allowed origins explicitly.

## Summary

Flask returns JSON when a view returns a dict or `jsonify(...)`, and parses JSON requests with `request.get_json()`. Use the right status code per HTTP semantics, include a `Location` header on `201 Created`, and keep error responses as JSON for API routes. Mount your API at `/api/v1` from day one so you can ship breaking changes later. For larger APIs, Flask-Smorest (Marshmallow + OpenAPI) is the modern recommendation; Flask-RESTX is a good alternative if you want a built-in Swagger UI. The next note, [[3.2.14. Error Handling]], covers the error path in more depth.
