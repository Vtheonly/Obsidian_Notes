# 3.2.14. Error Handling

> [!info] Orientation
> Errors are inevitable. Flask gives you the tools to handle them gracefully: `abort()` for short-circuiting, `@app.errorhandler` for custom responses, custom exception classes for domain errors, `app.logger` for logging, and Sentry for production error tracking. This note covers each, with emphasis on the security rules (never leak tracebacks to users) and the API-vs-HTML dispatch pattern.

## 1. How Flask Handles Errors

When a view function raises an exception, Flask's error handling machinery catches it and tries to produce a sensible response. The flow is:

1. If the exception is an `HTTPException` (e.g. `NotFound`, `BadRequest`), Flask looks for an error handler registered for that status code.
2. If the exception is any other type, Flask wraps it in a 500 and looks for a 500 handler.
3. If no custom handler is registered, Flask renders its default error page (a terse HTML page in production, a full traceback in debug mode).

The handlers are looked up by status code or by exception class. You can register a handler for `404` (status code) or for `werkzeug.exceptions.NotFound` (exception class) — they are equivalent, because `abort(404)` raises `NotFound`.

## 2. abort() — Raising HTTP Errors

`abort(status_code, description=None)` raises an `HTTPException` immediately, stopping view execution. It is the right way to bail out of a view when a precondition fails.

```python
from flask import abort

@app.route("/post/<int:post_id>")
def show_post(post_id):
    post = db.session.get(Post, post_id)
    if post is None:
        abort(404, description="No such post")
    if post.draft and post.author_id != current_user.id:
        abort(403)
    return render_template("post.html", post=post)
```

You can also raise the exception classes directly, which reads more Pythonic:

```python
from werkzeug.exceptions import NotFound, Forbidden

if post is None:
    raise NotFound(description="No such post")
if post.draft and post.author_id != current_user.id:
    raise Forbidden()
```

Both forms are equivalent. `abort()` is a function call; `raise NotFound()` is a statement. Pick the form you find more readable and use it consistently.

## 3. Custom Error Pages with @app.errorhandler

`@app.errorhandler(code_or_exception)` registers a function that handles errors of that code or class. The handler receives the exception object and returns a response.

```python
from flask import render_template, jsonify, request

@app.errorhandler(404)
def not_found(error):
    if request.path.startswith("/api/"):
        return jsonify(error="Not found", path=request.path), 404
    return render_template("errors/404.html"), 404

@app.errorhandler(403)
def forbidden(error):
    if request.path.startswith("/api/"):
        return jsonify(error="Forbidden"), 403
    return render_template("errors/403.html"), 403

@app.errorhandler(400)
def bad_request(error):
    if request.path.startswith("/api/"):
        return jsonify(error=str(error.description) or "Bad request"), 400
    return render_template("errors/400.html"), 400
```

The `request.path.startswith("/api/")` check dispatches JSON for API requests and HTML for browser requests. A more robust version checks `request.is_json` or `request.accept_mimetypes.best`, which handles APIs mounted at other prefixes. The handler returns a tuple `(body, status)`; the status can be omitted if it matches the handler's code, but including it explicitly is clearer.

## 4. The 500 Handler — Log but Do Not Leak

The 500 handler is special because the underlying exception is almost certainly a bug in your code, not a user error. The handler's job is to log the full traceback for you to diagnose, and to return a generic message to the user that does not leak stack details.

```python
@app.errorhandler(500)
def internal_server_error(error):
    app.logger.exception("Unhandled server error: %s", error)
    if request.path.startswith("/api/"):
        return jsonify(error="Internal server error", request_id=getattr(g, "request_id", None)), 500
    return render_template("errors/500.html"), 500
```

`app.logger.exception(msg)` logs at the `ERROR` level and automatically attaches the current traceback. Never include the traceback in the response — that is debug mode's job, and debug mode must never be in production. If you want to give the user a way to reference the error in a support ticket, attach a request ID (from a middleware or `g.request_id`) so they can quote it without seeing the stack.

## 5. Custom Exception Classes

For domain-specific errors, define your own exception classes. They let you raise meaningful errors from deep inside your service layer and have a single handler convert them to the right HTTP response.

```python
# errors.py
class DomainError(Exception):
    """Base class for domain errors. Subclasses set status_code and message."""
    status_code = 400
    message = "Domain error"

class UserNotFound(DomainError):
    status_code = 404
    message = "User not found"

class DuplicateEmail(DomainError):
    status_code = 409
    message = "Email already registered"

class InsufficientCredits(DomainError):
    status_code = 402
    message = "Not enough credits to perform this action"
```

```python
# Register a single handler for the base class
@app.errorhandler(DomainError)
def handle_domain_error(error):
    if request.path.startswith("/api/"):
        return jsonify(error=error.message, type=error.__class__.__name__), error.status_code
    return render_template("errors/generic.html", message=error.message), error.status_code
```

```python
# services/billing.py
def charge_user(user_id, amount):
    user = get_user(user_id)
    if user.credits < amount:
        raise InsufficientCredits()
    user.credits -= amount
    db.session.commit()
```

Now the service layer raises business-meaningful exceptions and does not need to know about HTTP. The single `DomainError` handler translates all of them. Adding a new error type is a one-class change.

## 6. Logging Errors

`app.logger` is a standard `logging.Logger` with the name `flask.app`. Use four methods depending on severity:

| Method | Level | When |
| ------ | ----- | ---- |
| `app.logger.debug(msg)` | DEBUG | Diagnostic detail, off in production |
| `app.logger.info(msg)` | INFO | Routine events (user logged in, post created) |
| `app.logger.warning(msg)` | WARNING | Something unusual but recoverable |
| `app.logger.error(msg)` | ERROR | A request failed but the app is healthy |
| `app.logger.exception(msg)` | ERROR + traceback | An unhandled exception |

For production, configure logging to write to stderr (where the platform's log collector picks it up) or to a file with rotation:

```python
import logging
from logging.handlers import RotatingFileHandler

if not app.debug:
    handler = RotatingFileHandler("app.log", maxBytes=10*1024*1024, backupCount=5)
    handler.setFormatter(logging.Formatter(
        "%(asctime)s %(levelname)s %(name)s [%(request_id)s] %(message)s"
    ))
    app.logger.addHandler(handler)
    app.logger.setLevel(logging.INFO)
```

The `[%(request_id)s]` formatter requires a `request_id` filter that pulls from `g.request_id` (set by a `before_request` hook from a UUID or the `X-Request-ID` header). With request IDs in every log line, you can grep for one ID and see the full sequence of log entries for that request — invaluable for diagnosing multi-step failures.

## 7. Returning JSON Errors for APIs vs HTML for Pages

The pattern of dispatching on `request.path.startswith("/api/")` works but is brittle. Three better approaches:

**Check `request.is_json`** — true if `Accept` or `Content-Type` mentions JSON. This handles APIs mounted anywhere.

**Use blueprint-scoped handlers** — register `@bp.errorhandler(404)` on the API blueprint to return JSON, and a separate app-level `@app.errorhandler(404)` for HTML. The blueprint handler wins for blueprint routes.

**Use a content negotiation helper** — a single function that checks `Accept` and dispatches to JSON or HTML renderers. This is the most flexible but the most code.

```python
def render_error(error, status, message):
    if request.is_json or request.path.startswith("/api/"):
        return jsonify(error=message, status=status), status
    return render_template(f"errors/{status}.html", message=message), status
```

## 8. Sentry Integration

For production error tracking beyond log files, Sentry is the standard. The `sentry-sdk` package captures unhandled exceptions, logs them with full stack traces and request context, and deduplicates them so you see one issue per unique error rather than one per occurrence.

```bash
pip install sentry-sdk
```

```python
import sentry_sdk
from sentry_sdk.integrations.flask import FlaskIntegration

sentry_sdk.init(
    dsn=os.environ["SENTRY_DSN"],
    integrations=[FlaskIntegration()],
    traces_sample_rate=0.1,        # 10% of requests traced for performance
    environment=os.environ.get("ENV", "production"),
    release=os.environ.get("GIT_SHA"),
)
```

With Sentry initialized, unhandled exceptions are sent to Sentry automatically — no `try/except` needed. The Flask integration also captures the request URL, headers (with sensitive values redacted), form data, and the current user. Set `release` to the git SHA so Sentry can tell you which deploy introduced a regression. The 500 handler should still log locally (so you have logs when Sentry is down) but does not need to call Sentry explicitly — the integration handles that.

## 9. Common Patterns

**Validation errors as 422, not 400.** HTTP 400 means "malformed request" (broken JSON, missing required header). HTTP 422 means "syntactically valid but semantically wrong" (e.g. email field is not a valid email). Many APIs collapse both into 400; the distinction is more useful for clients that want to differentiate "I sent garbage" from "I sent valid JSON that failed business rules".

**Idempotent 404s.** A `DELETE /api/posts/42` on a non-existent post should return 404 the first time and 404 the second time, not 200 then 404. This makes retries safe.

**Rate-limit errors as 429.** When you rate-limit, return `429 Too Many Requests` with a `Retry-After` header indicating when the client can retry. The 429 status is the difference between a well-behaved client backing off and a confused one retrying aggressively.

**Don't catch `Exception` blindly.** A bare `except Exception:` in a view swallows programming errors that should propagate to your 500 handler and Sentry. Catch only the specific exceptions you intend to handle; let the rest propagate.

## Summary

Use `abort(code)` or `raise HTTPException` to short-circuit views with HTTP errors. Register `@app.errorhandler(code_or_exception)` to customize the response; dispatch on `request.is_json` or use blueprint-scoped handlers to return JSON for APIs and HTML for browsers. Define a `DomainError` base class for business errors and a single handler for it. The 500 handler logs with `app.logger.exception` and returns a generic message — never leak tracebacks to users. Use Sentry in production for error tracking, and configure logging with request IDs for grep-able logs. The next note, [[3.2.15. Deploying to Railway or Render]], covers what happens when your well-handled app ships to the internet.
