# 3.2.15. Deploying to Railway or Render

> [!info] Orientation
> Flask's dev server is for development only. Production needs a real WSGI server in front of the app, a process manager to keep it alive, and a platform to run it on. This note covers the WSGI server concept, Gunicorn basics and worker types, Procfile format, Railway and Render deployment, Dockerfiles vs buildpacks, health check endpoints, custom domains and HTTPS, and secrets management.

## 1. Why the Dev Server Cannot Go to Production

Flask's built-in Werkzeug server is single-threaded, has no graceful restart, has no worker pool, and is not designed for concurrency or robustness. Werkzeug's own documentation says "this server is for development purposes only". Three concrete problems make it unsuitable for production. First, it handles one request at a time, so a single slow request blocks every other request. Second, it has no worker supervision — if the process crashes, it stays crashed. Third, it serves the interactive debugger if `debug=True`, which is a remote code execution vulnerability. Production needs a different server.

A production WSGI server (Gunicorn, uWSGI, Waitress) does three things the dev server does not. It runs multiple worker processes so a crash in one does not take down the app. It pre-forks workers so requests are handled in parallel. It integrates with a process manager (systemd, Docker, the platform's scheduler) so the server starts on boot and restarts on failure. In front of the WSGI server you usually put a reverse proxy (Nginx, Caddy) for TLS termination, static file serving, and load balancing — see [[6.3. Nginx Reverse Proxy and Load Balancing]].

## 2. Gunicorn Basics

Gunicorn is the most popular WSGI server for Flask. It is pre-forking, synchronous by default, and configuration is a single command line.

```bash
pip install gunicorn
gunicorn 'wsgi:app' --workers 4 --bind 0.0.0.0:8000
```

`wsgi:app` is the Python path `module:attribute` — Gunicorn imports `wsgi` and uses the `app` attribute. If you use the application factory, the syntax is `gunicorn 'app:create_app()'` — Gunicorn calls `create_app()` and uses the returned object. `--workers 4` runs four worker processes; `--bind 0.0.0.0:8000` listens on all interfaces at port 8000.

The worker count rule of thumb is `2 * CPU_cores + 1` for CPU-bound workloads. For IO-bound workloads (most Flask apps), more workers help up to the point where memory or database connection pool limits become the bottleneck. Each worker is a separate process with its own Python interpreter and its own SQLAlchemy connection pool — four workers with `pool_size=10` is forty database connections.

## 3. Gunicorn Worker Types

Gunicorn supports several worker classes via `--worker-class`. The default is `sync`, which handles one request at a time per worker. The others trade off latency, throughput, and complexity.

| Worker class | Best for | Trade-off |
| ------------ | -------- | --------- |
| `sync` (default) | CPU-bound work, simple apps | One request per worker at a time |
| `gevent` | Many idle connections, WebSockets via polling | Monkey-patches stdlib; not all libraries compatible |
| `eventlet` | Same as gevent, alternative implementation | Same monkey-patching concerns |
| `uvicorn.workers.UvicornWorker` | ASGI apps (use with Quart or FastAPI) | Not for WSGI Flask apps |
| `tornado` | Long-polling without gevent | Less common, smaller ecosystem |

For a typical Flask app, `sync` workers are the right default. Switch to `gevent` only if you have a measurable bottleneck with idle connections (e.g. thousands of clients polling at 1-second intervals) and your database driver and other dependencies are gevent-compatible. Monkey-patching silently breaks some libraries, so test thoroughly before adopting it.

Gunicorn's `--threads N` flag runs N threads inside each sync worker, which gives concurrency within a process for IO-bound work without monkey-patching. `--workers 4 --threads 8` runs 4 processes × 8 threads = 32 concurrent requests, sharing 4 database connection pools. This is a sweet spot for many Flask apps.

## 4. The Procfile

The Procfile is a Heroku-originated convention adopted by Render and other platforms. It declares the process types your app needs. The `web` process type is special — it is the one the platform exposes on a public URL.

```text
web: gunicorn 'wsgi:app' --workers 4 --threads 8 --timeout 30 --bind 0.0.0.0:$PORT
```

`$PORT` is set by the platform; you must bind to it (not a hardcoded port) because the platform's router expects your app on that exact port. The `--timeout 30` tells Gunicorn to kill and restart a worker that takes longer than 30 seconds on a single request; tune this up for endpoints with legitimate long-running work (file uploads, report generation).

Other process types in the Procfile are background workers — `worker: python -m app.worker` runs a Celery worker, `release: flask db upgrade` runs migrations during deploy. Railway uses a similar concept via its "Services" UI; Render supports Procfiles for both web services and background workers.

## 5. Deploying to Railway

Railway is a modern PaaS that runs your code on a managed infrastructure. The deploy flow is:

1. Connect your GitHub repository (or use `railway up` from the CLI).
2. Railway detects Python, reads `requirements.txt` or `pyproject.toml`, and builds.
3. Railway looks for a Procfile, a `Dockerfile`, or a default `gunicorn` invocation.
4. Set environment variables in the Railway dashboard (or via `railway variables set`).
5. Railway assigns a public URL like `myapp.up.railway.app`.

```bash
# Install the Railway CLI
npm install -g @railway/cli

# From your project root
railway login
railway init
railway up
```

The minimum environment variables Railway needs:

```text
SECRET_KEY=<32-byte hex>
DATABASE_URL=postgresql://...    # from Railway's Postgres plugin
FLASK_ENV=production
PYTHON_VERSION=3.12
```

The Railway Postgres plugin provisions a managed PostgreSQL instance and exposes its connection string as `DATABASE_URL`. Your `config.py` reads it with `os.environ["DATABASE_URL"]`. For Redis (needed for Flask-Session server-side sessions, Celery, or caching), add the Redis plugin and read `REDIS_URL`.

Railway runs your `release` process type before each deploy goes live — this is where you run `flask db upgrade`. If the release command fails, the deploy is aborted and the previous version stays live.

## 6. Deploying to Render

Render is a similar platform with a slightly different model. You create a "Web Service" pointing at your repository, choose Python as the runtime, and configure the build and start commands:

```text
Build Command:  pip install -r requirements.txt
Start Command:  gunicorn 'wsgi:app' --workers 4 --bind 0.0.0.0:$PORT
```

Render auto-detects Python from `requirements.txt` or `pyproject.toml`. The `$PORT` environment variable is provided by Render and must be used in the bind address. For the database, add a "PostgreSQL" service; Render exposes the connection string as `DATABASE_URL` (internal to Render's network) and `EXTERNAL_DATABASE_URL` (reachable from outside).

Render's free tier sleeps the web service after 15 minutes of inactivity, which means the first request after sleep takes 30+ seconds while the container cold-starts. For production, use a paid tier that stays warm. Render's "Background Worker" service type runs non-web processes (Celery workers, scheduled tasks) — these are the equivalent of non-`web` entries in a Procfile.

## 7. Dockerfile vs Buildpack

Both Railway and Render can build your app in two ways: a buildpack (auto-detected from `requirements.txt`) or a Dockerfile you write. Buildpacks are zero-config and great for getting started. Dockerfiles give you full control and are the right choice for anything non-trivial.

```dockerfile
# Dockerfile
FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

RUN pip install --no-cache-dir gunicorn

EXPOSE 8000

CMD ["gunicorn", "wsgi:app", "--workers", "4", "--threads", "8", \
     "--timeout", "30", "--bind", "0.0.0.0:8000"]
```

The two-stage `COPY requirements.txt` then `COPY .` is important: it lets Docker cache the `pip install` layer so that code changes do not reinstall dependencies. Use a `.dockerignore` to exclude `venv/`, `__pycache__/`, `.env`, and `instance/` from the build context. For a deeper treatment of Docker concepts, see [[6.1. Docker Containerization and Networking]].

## 8. Health Check Endpoints

Both platforms periodically hit a URL on your app to check if it is alive. If the URL returns non-200 within a timeout, the platform restarts the container. The convention is a `/health` or `/healthz` endpoint that does the minimum work necessary to confirm the app is running:

```python
@app.route("/health")
def health():
    # Cheap check: can we reach the database?
    try:
        db.session.execute(db.text("SELECT 1")).scalar()
    except Exception:
        return "database down", 503
    return "ok", 200
```

The health check should be fast (under 100 ms) and not require authentication. A more sophisticated version distinguishes "liveness" (is the process running?) from "readiness" (is the app ready to serve traffic, including DB connectivity?). Liveness is `GET /healthz` returning 200 if the process is up; readiness is `GET /readyz` returning 200 only if the app can actually serve requests. The platform routes traffic only to containers that pass readiness.

## 9. Custom Domains and HTTPS

Both Railway and Render provision a `*.up.railway.app` or `*.onrender.com` subdomain with automatic HTTPS via Let's Encrypt. For a custom domain (`myapp.com`), point a CNAME at the platform's hostname and the platform renews the cert automatically.

For a Flask app behind a proxy, set `ProxyFix` so Flask sees the real client IP and scheme from the proxy's headers:

```python
from werkzeug.middleware.proxy_fix import ProxyFix
app.wsgi_app = ProxyFix(app.wsgi_app, x_for=1, x_proto=1, x_host=1, x_prefix=1)
```

Without `ProxyFix`, `request.remote_addr` is the proxy's IP and `request.is_secure` is `False` even when the user is on HTTPS. The `x_for=1` argument trusts one layer of proxy; increase it if you are behind multiple proxies (CDN → load balancer → app).

## 10. Secrets Management

Never bake secrets into your Docker image or commit them to git. Both Railway and Render provide a secrets UI (or environment variables UI) where you set `SECRET_KEY`, `DATABASE_URL`, `SENTRY_DSN`, and so on. These are exposed to the app as environment variables at runtime.

For team workflows, both platforms support "config groups" or "environment groups" that you can attach to multiple services, so a database URL is set once and shared across the web service and the worker. For rotating secrets, change the value in the dashboard and trigger a redeploy — the new value is picked up on next start. For more sophisticated secret management (per-environment, audit trails, automatic rotation), use a dedicated secrets manager like AWS Secrets Manager, Doppler, or Vault, and have the app fetch secrets at startup.

The `SECRET_KEY` rotation deserves special mention: rotating it invalidates every signed cookie (sessions, "remember me" tokens, signed URLs). Plan a rotation as a deploy with a brief period of all users being logged out, and never rotate it as a side effect of another change.

## Summary

Production Flask runs on Gunicorn (or uWSGI), not the dev server. Pick `sync` workers with `--threads 8` as the default; switch to `gevent` only with measured need and full testing. Deploy with a Procfile or Dockerfile; both Railway and Render detect Python and run your app on `$PORT`. Add a `/health` endpoint for the platform's liveness checks, set `ProxyFix` for correct client IPs behind the proxy, and use the platform's secrets UI for all credentials. The next note, [[3.2.16. Resume Project Example]], ties together everything in this chapter into a single deployable Flask app.
