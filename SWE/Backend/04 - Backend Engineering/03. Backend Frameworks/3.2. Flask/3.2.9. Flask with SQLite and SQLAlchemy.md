# 3.2.9. Flask with SQLite and SQLAlchemy

> [!info] Orientation
> Flask does not ship with a database layer. This note covers the raw-sqlite approach using the `g` object for per-request connections, the Flask-SQLAlchemy integration pattern, model definition and the query API, session lifecycle, schema initialization, migrations with Flask-Migrate (Alembic), and connection pooling for production databases.

## 1. The Two Paths to Persistence

Flask gives you nothing for databases by default — there is no built-in ORM, no migrations, no connection pool. You choose one of two paths. The first is raw database access: import `sqlite3` (or `psycopg`, `pymysql`), open a connection per request, run SQL, close it. This is simple, transparent, and fine for tiny apps. The second is an ORM: install Flask-SQLAlchemy, define models as Python classes, query with method calls, and let the ORM handle connections and SQL. Most Flask apps of any size pick the ORM path because the productivity gain outweighs the abstraction cost. This note covers both, in that order.

## 2. Raw SQLite with the g Object

The `g` object is a per-request namespace on the application context. Anything you attach to `g` lives for the duration of one request and is torn down at the end. The standard pattern for raw SQLite stores the connection there:

```python
import sqlite3
from flask import g, current_app

def get_db():
    if "db" not in g:
        g.db = sqlite3.connect(current_app.config["DATABASE"])
        g.db.row_factory = sqlite3.Row  # rows behave like dicts
    return g.db

@app.teardown_appcontext
def close_db(exception):
    db = g.pop("db", None)
    if db is not None:
        db.close()

@app.route("/users")
def list_users():
    db = get_db()
    rows = db.execute("SELECT id, username FROM users ORDER BY id").fetchall()
    return {"users": [dict(r) for r in rows]}
```

`get_db()` opens the connection lazily on first access and caches it on `g`. The `teardown_appcontext` handler runs after every request, regardless of success or failure, and closes the connection. `sqlite3.Row` as `row_factory` lets you address columns by name (`row["username"]`) instead of by index. This pattern is from the official Flask tutorial and is the right baseline for a no-ORM app.

The raw approach has advantages: zero dependencies, full SQL power, no abstraction leaks. It has disadvantages: no schema migration tool, no type-safe model classes, manual SQL string concatenation (which is the SQL injection attack surface if you are not careful). Use parameterized queries always — `db.execute("SELECT ... WHERE id = ?", (id,))` — and never string-format user input into SQL.

## 3. Flask-SQLAlchemy Setup

Flask-SQLAlchemy is a thin integration layer that wraps SQLAlchemy, binds it to the Flask app, and provides a `db` object you import throughout your code. Install it with `pip install Flask-SQLAlchemy`.

```python
# extensions.py
from flask_sqlalchemy import SQLAlchemy

db = SQLAlchemy()
```

```python
# app/__init__.py
from flask import Flask
from .extensions import db
from .config import Config

def create_app(config_class=Config):
    app = Flask(__name__)
    app.config.from_object(config_class)
    db.init_app(app)
    # Register blueprints, etc.
    return app
```

```python
# config.py
class Config:
    SQLALCHEMY_DATABASE_URI = os.environ["DATABASE_URL"]
    SQLALCHEMY_TRACK_MODIFICATIONS = False
    SQLALCHEMY_ENGINE_OPTIONS = {
        "pool_size": 10,
        "pool_recycle": 1800,  # recycle connections older than 30 min
        "pool_pre_ping": True, # test connections before checkout
    }
```

`SQLALCHEMY_DATABASE_URI` is a SQLAlchemy URL like `postgresql://user:pass@host:5432/dbname`, `mysql+pymysql://...`, or `sqlite:///app.db`. `SQLALCHEMY_TRACK_MODIFICATIONS` should be `False` — the default `True` adds a signal listener on every model change and is wasteful. `SQLALCHEMY_ENGINE_OPTIONS` are passed straight to SQLAlchemy's `create_engine`; the three options shown are the standard production setup for PostgreSQL and MySQL.

## 4. Defining Models

A model is a Python class that inherits from `db.Model`. Each `db.Column` becomes a database column; the type maps to a SQL type.

```python
# models/user.py
from datetime import datetime
from app.extensions import db

class User(db.Model):
    __tablename__ = "users"

    id = db.Column(db.Integer, primary_key=True)
    username = db.Column(db.String(80), unique=True, nullable=False)
    email = db.Column(db.String(120), unique=True, nullable=False, index=True)
    password_hash = db.Column(db.String(255), nullable=False)
    created_at = db.Column(db.DateTime, default=datetime.utcnow, nullable=False)

    posts = db.relationship("Post", backref="author", lazy="dynamic")

    def __repr__(self):
        return f"<User {self.username}>"
```

```python
# models/post.py
class Post(db.Model):
    __tablename__ = "posts"

    id = db.Column(db.Integer, primary_key=True)
    title = db.Column(db.String(200), nullable=False)
    body = db.Column(db.Text, nullable=False)
    user_id = db.Column(db.Integer, db.ForeignKey("users.id"), nullable=False)
    published_at = db.Column(db.DateTime, nullable=True, index=True)

    def __repr__(self):
        return f"<Post {self.title!r}>"
```

`db.ForeignKey("users.id")` creates the foreign-key relationship at the database level. `db.relationship("Post", backref="author")` creates the Python-side navigation: `user.posts` returns the user's posts, and `post.author` returns the user who wrote the post. `lazy="dynamic"` returns a query object instead of a list, so you can chain filters before hitting the database: `user.posts.filter_by(published_at=None).all()`. Indexes on `email` and `published_at` speed up the lookups you will actually do.

## 5. The Query API

Flask-SQLAlchemy 3.x exposes queries through `Model.query` (a query object pre-bound to that model) or through `db.session.execute(db.select(Model))` (the modern SQLAlchemy 2.0 style). Both work; the `select()` form is preferred for new code because it is closer to pure SQLAlchemy.

```python
# Old style (still supported)
user = User.query.filter_by(username="alice").first()
users = User.query.order_by(User.created_at.desc()).limit(10).all()

# New style (SQLAlchemy 2.0)
from sqlalchemy import select
stmt = select(User).where(User.username == "alice").limit(1)
user = db.session.execute(stmt).scalar_one_or_none()

stmt = select(User).order_by(User.created_at.desc()).limit(10)
users = list(db.session.execute(stmt).scalars())
```

For relationships, `db.select(Post).join(User).where(User.username == "alice")` does a join. For aggregations, `db.select(db.func.count(Post.id)).scalar()` returns the count. The query API is the same SQLAlchemy you would use outside Flask; Flask-SQLAlchemy only adds the `db` namespace and the `Model.query` shortcut. For a deeper treatment, see [[4.2. SQLAlchemy Core vs ORM Internals]].

## 6. The Session Lifecycle

SQLAlchemy's `Session` is the unit of work — it tracks objects you load, queues changes, and writes them to the database on `commit()`. In Flask-SQLAlchemy, the session is scoped to the request by default: `db.session` is a proxy that resolves to a thread-local session, and Flask-SQLAlchemy removes the session at the end of each request.

```python
# Create
user = User(username="alice", email="alice@example.com", password_hash=hash_pw("..."))
db.session.add(user)
db.session.commit()           # user.id is now populated

# Update
user.email = "alice@newdomain.com"
db.session.commit()

# Delete
db.session.delete(user)
db.session.commit()
```

If an exception is raised before `commit()`, the session is in an undefined state and must be rolled back with `db.session.rollback()` before it can be used again. A common pattern is to wrap mutations in a try/except that rolls back on failure:

```python
try:
    db.session.add(user)
    db.session.commit()
except Exception:
    db.session.rollback()
    raise
```

Forgetting the rollback after a failed commit is the most common SQLAlchemy bug — once a session has an error, every subsequent operation on it raises "This Session's transaction has been rolled back due to a previous exception".

## 7. Schema Initialization

`db.create_all()` inspects all registered models and creates the corresponding tables if they do not exist. It is the right call for the very first run of an app and for tests with an in-memory database. It is **not** a migration tool: it does not add columns to existing tables, does not drop tables that no longer have models, and does not detect type changes. For any app that will ever evolve, use Flask-Migrate from day one.

```python
@app.cli.command("init-db")
def init_db():
    db.create_all()
    print("Database initialized.")
```

```bash
flask --app app init-db
```

## 8. Migrations with Flask-Migrate

Flask-Migrate is a Flask wrapper around Alembic, SQLAlchemy's migration engine. It generates migration scripts from the difference between your models and the current database schema, and applies them with `upgrade` / `downgrade` commands.

```bash
pip install Flask-Migrate
flask --app app db init          # creates the migrations/ folder
flask --app app db migrate -m "add users and posts"
flask --app app db upgrade       # applies the migration
flask --app app db downgrade     # rolls back the last migration
flask --app app db history       # shows migration history
```

The workflow is: change a model, run `db migrate` to generate a draft migration, review the generated script in `migrations/versions/`, run `db upgrade` to apply it. The draft script is editable — Alembic's autogenerate detects column adds and drops but not column renames (it sees them as drop+add, which loses data), so renames must be hand-edited. Commit the `migrations/` folder to version control; every developer and every deployment runs the same migrations.

In production, `flask db upgrade` runs as part of the deploy (typically in a release step before the new code goes live). Never run `db.create_all()` in production — it will leave the schema out of sync with migrations and the next migration will fail.

## 9. Connection Pooling

SQLAlchemy maintains a pool of database connections that it reuses across requests, because opening a fresh TCP connection to PostgreSQL takes 20-50 ms and is wasteful to do per request. The pool's behavior is controlled by `SQLALCHEMY_ENGINE_OPTIONS`. Three settings cover most production cases.

`pool_size` is the number of persistent connections to keep open. `max_overflow` is the number of additional connections to open under load before queueing requests. `pool_recycle` is the lifetime in seconds of a connection before it is recycled — important for MySQL, which has an 8-hour default `wait_timeout` after which the server closes idle connections, leaving stale connections in your pool. `pool_pre_ping=True` issues a `SELECT 1` before each checkout to detect stale connections; the small overhead is worth the reliability.

```python
SQLALCHEMY_ENGINE_OPTIONS = {
    "pool_size": 10,
    "max_overflow": 20,
    "pool_recycle": 1800,
    "pool_pre_ping": True,
}
```

For SQLite, pooling is largely irrelevant — SQLite is file-based and connections are cheap. The `sqlite:///app.db` URL uses a default pool that is fine for development. For tests, `sqlite:///:memory:` creates an in-memory database that disappears when the last connection closes; combine it with `ScopedSession` per test for isolation.

## Summary

For raw SQL, use the `g` object to hold a per-request SQLite connection and `teardown_appcontext` to close it. For anything larger, use Flask-SQLAlchemy: define models as `db.Model` subclasses, query with `db.select()` or `Model.query`, commit mutations with `db.session.commit()`, and rollback on failure. Initialize the schema with `db.create_all()` only for the first run; use Flask-Migrate (Alembic) for all schema changes after that. Configure connection pooling with `pool_size`, `pool_recycle`, and `pool_pre_ping` for production databases. The next note, [[3.2.10. Sessions and Cookies in Flask]], covers the other stateful side of a Flask app — the per-user data that lives in cookies.
