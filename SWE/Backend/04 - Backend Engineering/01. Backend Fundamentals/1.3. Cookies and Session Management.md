# 1.3. Cookies and Session Management

> [!info] Orientation
> HTTP is stateless by design, but almost every real web application needs to remember who the current user is across requests. Cookies are the standard transport for that memory; sessions are the server-side state that the cookie points to. This note covers what a cookie actually is (an HTTP header, nothing more), the full anatomy of the `Set-Cookie` directive, the cookie lifecycle, server-side session stores and their trade-offs, and the security attacks — fixation, hijacking, CSRF — that proper cookie configuration defends against.

## 1. What a Cookie Actually Is

A cookie is not a file format, not a database, and not a JavaScript object. It is, mechanically, an HTTP header line. The server sends cookies to the browser using the `Set-Cookie` response header (one cookie per header line), and the browser returns them to the server using the `Cookie` request header (all matching cookies comma-separated in one line). Everything else — the browser's on-disk `cookies.sqlite` file, the `document.cookie` JavaScript API, the dev-tools "Application" tab — is a convenience layer built on top of that header exchange.

Because cookies are sent automatically by the browser on every matching request, they are the natural transport for authentication state in classical server-rendered web applications. They are also the reason HTTP requests "feel" stateful: the server's session middleware reads the cookie, looks up the session, and injects the user into the request context. Remove the cookie and the application reverts to the stateless HTTP baseline.

## 2. Anatomy of the Set-Cookie Directive

A single `Set-Cookie` header has the form `name=value; attribute; attribute; ...`. The name/value pair is mandatory and is URL-encoded; the attributes are optional but the security-relevant ones should always be set.

```http
Set-Cookie: session_id=abc123xyz; Domain=example.com; Path=/; Max-Age=86400; Secure; HttpOnly; SameSite=Lax
```

| Attribute | Purpose |
| :--- | :--- |
| `Name=Value` | The cookie's key and value. URL-encoded. |
| `Domain=example.com` | Which hosts receive the cookie. Defaults to the origin host; a leading dot (`.example.com`) includes all subdomains. |
| `Path=/` | URL prefix that the cookie applies to. Defaults to the path of the resource that set it. |
| `Expires=Wed, 09 Jun 2027 10:18:14 GMT` | Absolute expiry timestamp. Makes the cookie persistent across browser restarts. |
| `Max-Age=86400` | Seconds until expiry. Preferred over `Expires`; both can be present but `Max-Age` wins. |
| `Secure` | Only send the cookie over HTTPS. |
| `HttpOnly` | Forbid JavaScript access via `document.cookie`. |
| `SameSite=Strict|Lax|None` | Controls cross-site cookie transmission. |

If neither `Expires` nor `Max-Age` is set, the cookie is a **session cookie** — it lives only until the browser is closed. Browsers cap cookie sizes at roughly **4 KB (4096 bytes) per cookie** and **50 cookies per domain**, with a hard ceiling of around **3000 cookies total per browser**. Hitting these limits causes silent cookie eviction, which is why cookies should hold a session ID, not the session payload itself.

## 3. The Cookie and Session Lifecycle

The full interaction between a browser and a session-aware server looks like the following sequence. The browser takes care of all cookie storage and retransmission automatically once the server has issued a `Set-Cookie`.

```mermaid
sequenceDiagram
    autonumber
    Client->>Server: POST /login (username, password)
    Note over Server: Verify credentials,<br/>generate session_id,<br/>store user meta in session store
    Server-->>Client: 200 OK + Set-Cookie: session_id=abc; HttpOnly; Secure; SameSite=Lax
    Note over Client: Browser persists cookie<br/>for the cookie jar of example.com
    Client->>Server: GET /profile (Cookie: session_id=abc)
    Note over Server: Middleware reads Cookie,<br/>looks up session_id in store,<br/>injects user into request
    Server-->>Client: 200 OK (profile HTML/JSON)
    Client->>Server: POST /logout (Cookie: session_id=abc)
    Note over Server: Delete session from store,<br/>send Set-Cookie with Max-Age=0
    Server-->>Client: 200 OK + Set-Cookie: session_id=; Max-Age=0
```

The crucial distinction is between the **cookie** (a small string the browser holds and retransmits) and the **session** (the server-side state indexed by the cookie value). Flask's default `session` object is an exception — it serializes the entire session payload into a signed cookie — but most production frameworks (Express with `express-session`, Django, Rails, Spring) keep only an opaque session ID in the cookie and store the actual state server-side. See [[3.2.10. Sessions and Cookies in Flask]] for the Flask-specific implementation.

## 4. Server-Side Session Stores

Where the session state physically lives determines how your application scales, how it survives restarts, and how much latency each authenticated request adds.

| Store | Latency | Persistence | Scalability | Best for |
| :--- | :--- | :--- | :--- | :--- |
| In-memory (process RAM) | Near-zero | Lost on crash/restart | Poor — pins sessions to one instance, requires sticky sessions | Local dev, single-instance prototypes |
| Filesystem | Low (disk read) | Survives restart, lost on disk failure | Poor — same pinning problem, shared filesystem is fragile | Single-server production |
| Relational DB (PostgreSQL, MySQL) | Higher (indexed lookup) | High durability | Moderate — adds load to the transactional DB | Small-to-mid apps, low auth traffic |
| In-memory cache (Redis, Memcached) | Extremely low (sub-ms) | Configurable (Redis AOF/RDB) | Excellent — shared cluster accessible from all app instances | Large, high-throughput production |

Redis is the de-facto standard session store for horizontally scaled applications. It is fast enough that the per-request session lookup is barely measurable, it survives a clean restart if you enable persistence, and it is shared by every application instance so any server can serve any request. Memcached is faster still but has no persistence — a restart wipes every session, forcing mass re-login.

## 5. Session Fixation and Session Hijacking

Two attacks dominate the session-management threat model.

**Session fixation** happens when an attacker forces a known session ID onto a victim before the victim logs in. The attacker visits the site, receives a session ID, then tricks the victim (via a malicious link or an injection into an unsecured page) into using that same session ID. When the victim logs in, the server binds the attacker's session ID to the victim's authenticated state, and the attacker can now use the same ID to act as the victim. The defense is straightforward: **always regenerate the session ID immediately after a successful login**, and discard the old ID. Every framework exposes a helper for this (`flask.session.regenerate`, `req.session.regenerate` in Express, `Session::migrate` in Symfony).

**Session hijacking** happens when an attacker steals a victim's session ID — by intercepting unencrypted HTTP on a shared Wi-Fi network, by reading it from `document.cookie` after a successful XSS attack, or by guessing/predicting IDs from a weak random source. Defenses are layered: use `Secure` so the cookie is never sent over HTTP, use `HttpOnly` so XSS cannot read it, generate session IDs from a cryptographic random source (at least 128 bits of entropy), and rotate the ID on privilege changes.

## 6. SameSite and CSRF Defense

`SameSite` controls whether the browser sends a cookie on cross-site requests. It is the modern, primary defense against **Cross-Site Request Forgery (CSRF)**, where a malicious site tricks the victim's browser into making an authenticated request to your site using the victim's existing session cookie.

`SameSite=Strict` withholds the cookie on all cross-site navigations, including top-level link clicks from external sites. This is maximally secure but UX-poor: a user who clicks a link from a Gmail message to your bank arrives "logged out" because the cookie is suppressed.

`SameSite=Lax` (the modern browser default) withholds the cookie on cross-site subresource requests (images, iframes, AJAX `fetch`) but sends it on top-level `GET` navigations. This blocks the classic CSRF attack (which uses a hidden form `POST` or a `fetch` from the attacker's site) while preserving the "click a link, arrive logged in" UX.

`SameSite=None` sends the cookie on all cross-site requests. This is required for legitimate third-party cookie use (embedded widgets, cross-domain SSO) but **must** be combined with `Secure`. Modern browsers reject `SameSite=None` without `Secure`.

When `SameSite=Lax` is not enough — for example, when you must support cross-site POST from a trusted partner — fall back to **CSRF tokens**: include a server-generated, per-session random token as a hidden form field or custom header, and reject any state-changing request that does not match the cookie-bound token. The double-submit cookie pattern is the most common implementation.

## 7. Cookie Size and Count Limits

Browsers enforce hard limits. The widely cited rule of thumb is **4 KB (4096 bytes) per cookie, 50 cookies per domain, 3000 cookies total** across all domains. Exceeding the per-cookie limit silently truncates the cookie; exceeding the per-domain limit evicts the oldest cookies. Practical implications: never put JSON blobs, base64-encoded images, or large preference structures in cookies — put them in the server-side session store and keep the cookie value to an opaque ID. Flask's signed-cookie sessions are a common trap here: serialize a list of 100 cart items into the Flask session cookie and you will blow past the 4 KB limit and get a cryptic `BadSignature` error.

## Summary

Cookies are HTTP headers — `Set-Cookie` on responses, `Cookie` on requests — that the browser persists and retransmits automatically. The `Set-Cookie` directive's attributes (`Domain`, `Path`, `Max-Age`, `Secure`, `HttpOnly`, `SameSite`) are the configuration surface for security and scope, and every authentication cookie should set at least `HttpOnly`, `Secure`, and `SameSite=Lax`. The cookie's value is typically just an opaque session ID pointing to server-side state, which lives in an in-memory cache like Redis for horizontally scaled applications. Session fixation is prevented by regenerating the session ID at login; session hijacking is mitigated by `Secure` + `HttpOnly` + cryptographic randomness in ID generation; CSRF is primarily prevented by `SameSite=Lax` and supplemented by CSRF tokens where cross-site requests are legitimate. The 4 KB / 50 cookies / 3000 cookies ceilings are the practical reason sessions belong server-side and cookies stay small.
