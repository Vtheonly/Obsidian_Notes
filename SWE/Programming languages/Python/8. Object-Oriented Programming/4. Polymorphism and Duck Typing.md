# 4. Polymorphism and Duck Typing

## Why This Matters

Polymorphism — Greek for "many forms" — is the ability of different objects to respond to the same message (method call) in their own way. It's what lets you write `for x in things: x.draw()` and have circles, squares, and SVG paths all draw themselves without your loop knowing or caring which is which.

In statically typed OO languages like C++ or Java, polymorphism is tied to inheritance: you declare a virtual method on a base class, derive subclasses, and the compiler ensures type safety. Python takes a fundamentally different approach: **duck typing**. If an object has the methods you need, you can use it — no inheritance required, no `virtual` keyword, no interface declaration. This makes Python code dramatically more flexible and more concise, but it also shifts responsibility for type-correctness from the compiler to the programmer (and to tests, type checkers, and runtime checks).

This note explains:

- What polymorphism is, in language-agnostic terms.
- How Python's duck typing differs from C++/Java's static polymorphism.
- The role of **structural typing** via `typing.Protocol` (introduced in Python 3.8, see [[3. Protocols and Structural Typing]]).
- The EAFP ("Easier to Ask Forgiveness than Permission") idiom.
- When you do need `isinstance`, ABCs, or explicit type checks.
- How Python's "protocols" (the runtime concept — iter, len, etc.) make polymorphism pervasive.

By the end you'll understand why Python's `len(x)` works on strings, lists, dicts, NumPy arrays, and your custom class — with no shared base class required.

## Background

Polymorphism comes in several flavours:

1. **Ad hoc polymorphism** — function overloading. Python doesn't have it directly (use `functools.singledispatch` instead — see [[2. partial and singledispatch]]).
2. **Parametric polymorphism** — generics (`List[T]`). Python has these via `typing` — see [[2. Generics and TypeVar]].
3. **Subtype polymorphism** — a base-class reference, an instance of a derived class, method dispatch at runtime. The classic OO form.
4. **Structural polymorphism** — "if it has these methods, it's this kind of thing." Python's duck typing. Also Python's `Protocol` type.

Subtype polymorphism in C++ looks like this:

```cpp
class Shape {
public:
    virtual double area() const = 0;   // pure virtual
    virtual ~Shape() = default;
};

class Circle : public Shape {
public:
    double area() const override { return 3.14 * r * r; }
private:
    double r;
};

void print_area(const Shape& s) {       // takes Shape reference
    std::cout << s.area() << "\n";      // virtual dispatch
}
```

In C++, `print_area` requires `Shape` as a base class. The compiler checks that `s.area()` is a valid call by walking the class hierarchy. Dispatch is virtual — at runtime, the right `area` is called based on the dynamic type of `s`.

Python has no `virtual`, no explicit interface declaration, and no compile-time type checker (by default). Polymorphism "just works" because attribute lookup is dynamic:

```python
def print_area(s):
    print(s.area())   # works on anything with .area()

class Circle:
    def __init__(self, r): self.r = r
    def area(self): return 3.14 * self.r ** 2

class Square:
    def __init__(self, s): self.s = s
    def area(self): return self.s ** 2

print_area(Circle(1))   # 3.14
print_area(Square(2))   # 4
```

`Circle` and `Square` share no base class. `print_area` doesn't care. This is **duck typing**.

## The Duck Typing Maxim

> "If it walks like a duck and quacks like a duck, it must be a duck."

— attributed to James Whitcomb Riley, popularised in Python by Alex Martelli.

The Pythonic version: **don't check whether an object *is* a duck; check whether it *quacks* like one. Or, even more Pythonic: just call `.quack()` and handle the `AttributeError` if it doesn't.**

```python
def quack(thing):
    """Make any duck-like thing quack."""
    thing.quack()
```

`thing` can be a `Duck`, a `Goose` that happens to have a `quack` method, a `Toy` with a sound chip, a `Mock` object in a test, or a proxy object in a RPC framework. The function doesn't care.

### Comparison with C++ static polymorphism

```mermaid
flowchart LR
    subgraph CPP["C++ static polymorphism"]
        direction TB
        C1["Shape* s"] --> C2{compiler checks<br/>s has area()}
        C2 -->|yes| C3["runtime vtable dispatch"]
        C3 --> C4["calls correct area()"]
        C2 -->|no| CE["compile error"]
    end
    subgraph PY["Python duck typing"]
        direction TB
        P1["s in hand"] --> P2["runtime: look up<br/>s.area"]
        P2 -->|found| P3["call it"]
        P2 -->|not found| PE["AttributeError"]
        PE --> PF["or caught by caller"]
    end
```

C++ checks *at compile time* that the call is valid (via the type system), then dispatches at runtime via vtable. Python skips the compile-time check and goes straight to runtime lookup, raising `AttributeError` if the method is missing.

The trade-off:

- **C++**: errors caught at compile time; faster dispatch; more rigid — you must declare interfaces and inherit from them.
- **Python**: errors surface at runtime (or via mypy if you add type hints); slightly slower dispatch; vastly more flexible — any object with the right method works.

## Polymorphism Without Inheritance

Classic example: the **iteration protocol**. The `for` loop works on anything that has `__iter__` (or `__getitem__` as a fallback):

```python
class Countdown:
    def __init__(self, start):
        self.start = start

    def __iter__(self):
        n = self.start
        while n > 0:
            yield n
            n -= 1

for x in Countdown(3):
    print(x)   # 3 2 1
```

`Countdown` doesn't inherit from `Iterable` or any other class. It just implements the `__iter__` protocol. `for`, `list()`, `sum()`, `any()`, `all()`, `tuple()`, `*unpacking` — all work on it.

Likewise, `len(x)` works on anything with `__len__`. `x in y` works on anything with `__contains__` (or `__iter__` as a fallback). `with x:` works on anything with `__enter__`/`__exit__`. These are **protocols** — implicit interfaces defined by dunder methods. See [[6. Magic Methods]] for the full list.

### A polymorphic example

```python
class JsonLogger:
    def write(self, data):
        import json
        print(json.dumps(data))

class CsvLogger:
    def write(self, data):
        print(",".join(str(v) for v in data.values()))

class NullLogger:
    def write(self, data):
        pass   # discard

def process(records, logger):
    for r in records:
        logger.write(r)   # polymorphic: any .write(data) works

records = [{"a": 1, "b": 2}, {"a": 3, "b": 4}]
process(records, JsonLogger())
process(records, CsvLogger())
process(records, NullLogger())
```

`process` doesn't know or care which logger it gets. Any object with a `.write(dict)` method works. This is the essence of Pythonic polymorphism.

## EAFP: Easier to Ask Forgiveness than Permission

Duck typing's natural idiom is EAFP: **just try the operation, and catch the error if it fails.** Contrast with LBYL ("Look Before You Leap"):

```python
# LBYL — check first
if hasattr(obj, "save") and callable(obj.save):
    obj.save()
else:
    print("can't save")

# EAFP — just try it
try:
    obj.save()
except AttributeError:
    print("can't save")
```

EAFP is more Pythonic because:

- It avoids a TOCTOU (time-of-check-time-of-use) race: in LBYL, the attribute could disappear between `hasattr` and the call. With EAFP, you try and find out.
- It's typically faster when the success case is common — `hasattr` does a `getattr` internally, so LBYL does two lookups; EAFP does one.
- It composes well with custom `__getattr__` and proxies objects (see [[6. Magic Methods]]).

> [!warning] Don't catch `Exception` when you mean `AttributeError`
> EAFP doesn't mean "wrap everything in a bare `except:`." Catch the specific exception you expect — usually `AttributeError`, `KeyError`, `ValueError`, etc. A bare `except Exception:` swallows programming errors (like `TypeError` from passing the wrong number of arguments) and makes bugs invisible.

See [[7. EAFP and Duck Typing]] (Chapter 10) for a full treatment.

## Protocol Classes (Structural Typing)

PEP 544 (Python 3.8+) added `typing.Protocol`, which lets you **declare** a structural interface for static type checkers (mypy, pyright). A `Protocol` says "anything with these methods is considered this type" — at static-analysis time, without inheritance.

```python
from typing import Protocol

class SupportsArea(Protocol):
    def area(self) -> float: ...

def print_area(s: SupportsArea) -> None:
    print(s.area())

class Circle:
    def area(self) -> float:
        return 3.14

print_area(Circle())   # mypy: OK — Circle has the right method
print_area(42)         # mypy: error — int has no .area()
```

`Circle` does **not** inherit from `SupportsArea`. mypy checks structurally: "does `Circle` have a method `area` returning `float`?" If yes, it satisfies the protocol.

This combines the flexibility of duck typing with the safety of static checking. See [[3. Protocols and Structural Typing]] and [[2. Protocols]] for the full story.

### Runtime `isinstance` with Protocols

```python
from typing import Protocol, runtime_checkable

@runtime_checkable
class Drawable(Protocol):
    def draw(self) -> None: ...

isinstance(Circle(), Drawable)   # True — checks structurally
```

`@runtime_checkable` lets you use `isinstance` against a Protocol — but only checks method *names*, not signatures. Limited but occasionally useful.

## The Implicit Protocols of Python

Python has many built-in protocols — implicit interfaces that any class can implement by adding the right dunder methods. This is the engine of Python's pervasive polymorphism:

| Protocol | Methods | Used by |
|----------|---------|---------|
| Iterable | `__iter__` | `for`, `list()`, `*unpack`, comprehensions |
| Iterator | `__iter__`, `__next__` | `for`, `next()` |
| Sized | `__len__` | `len()`, `bool()` (with `__bool__` absent) |
| Container | `__contains__` | `in` operator |
| Sequence | `__getitem__`, `__len__`, optionally `__iter__`, `__contains__`, `__reversed__`, `index`, `count` | indexing, slicing, `for`, `in` |
| Mapping | `__getitem__`, `__len__`, `__iter__`, `keys`, `values`, `items` | `dict()`-like access |
| Callable | `__call__` | `obj()` syntax |
| Hashable | `__hash__`, `__eq__` | set/dict keys |
| Comparable | `__eq__`, `__lt__`, `__le__`, `__gt__`, `__ge__` | `<`, `>`, `sorted`, `min`, `max` |
| Context manager | `__enter__`, `__exit__` | `with` statement |
| Descriptor | `__get__`, `__set__`, `__delete__` | Attribute access on classes |

Full details on each in [[6. Magic Methods]]. The key insight: implementing any of these protocols makes your object polymorphic with the corresponding built-in operations. You don't have to inherit from anything — you just have to provide the methods.

### Example: making a class work with `len()` and `in`

```python
class SparseVector:
    def __init__(self, data):
        self._data = dict(data)

    def __len__(self):
        return max(self._data.keys(), default=-1) + 1

    def __contains__(self, i):
        return i in self._data

    def __getitem__(self, i):
        return self._data.get(i, 0)

v = SparseVector({0: 1, 5: 2, 100: 3})
print(len(v))   # 101 — last index + 1
print(5 in v)   # True
print(6 in v)   # False
print(v[5])     # 2
print(v[6])     # 0 (default)
```

No `Iterable` or `Sized` base class required. Just the right dunder methods.

## When Inheritance Still Matters

Duck typing doesn't make inheritance obsolete. Inheritance is still the right tool when:

1. **You have a true "is-a" relationship** — `Dog` *is an* `Animal`. Inheriting captures this and gets you the parent's behaviour for free.
2. **You want code reuse via template method** — a base class defines the algorithm skeleton, subclasses override specific steps.
3. **You want to register a class with `isinstance` checks** — e.g., `isinstance(x, collections.abc.Sequence)`.
4. **You want to enforce an interface** with an ABC — `class Shape(ABC): @abstractmethod def area(self): ...`.

The point is: **don't use inheritance *just* to enable polymorphism.** Polymorphism in Python comes for free from method names. Use inheritance when it captures a real type relationship.

### Template Method pattern

```python
from abc import ABC, abstractmethod

class DataProcessor(ABC):
    """Template method: load → clean → save."""

    def run(self, path):
        data = self.load(path)
        cleaned = self.clean(data)
        self.save(cleaned, path + ".out")

    @abstractmethod
    def load(self, path): ...

    @abstractmethod
    def clean(self, data): ...

    @abstractmethod
    def save(self, data, path): ...


class CsvProcessor(DataProcessor):
    def load(self, path):
        import csv
        with open(path) as f:
            return list(csv.DictReader(f))

    def clean(self, data):
        return [{k: v.strip() for k, v in row.items()} for row in data]

    def save(self, data, path):
        import csv, sys
        with open(path, "w", newline="") as f:
            w = csv.DictWriter(f, fieldnames=data[0].keys())
            w.writeheader()
            w.writerows(data)
```

`run` is the template — it defines the algorithm. `CsvProcessor` provides the steps. Different subclasses (`JsonProcessor`, `ParquetProcessor`) provide different steps but share the algorithm. This is inheritance used well.

## When You DO Need `isinstance`

Duck typing isn't always enough. Use `isinstance` when:

1. **You're at an API boundary** and want a clear error message instead of an obscure `AttributeError` deep in a call stack.
2. **You're dispatching on type** (consider `functools.singledispatch` instead — see [[2. partial and singledispatch]]).
3. **You're checking against a `Protocol` or ABC** that defines a meaningful interface.
4. **You're writing framework code** that needs to treat strings differently from other iterables (the classic `isinstance(x, str)` check before iterating).

```python
def flatten(items):
    """Flatten a nested list, but keep strings as atoms."""
    for x in items:
        if isinstance(x, str):
            yield x            # strings are iterable, but we want them whole
        else:
            try:
                yield from flatten(x)
            except TypeError:
                yield x

list(flatten([1, [2, 3], "ab", [4, [5]]]))
# [1, 2, 3, 'ab', 4, 5]
```

Without the `isinstance(x, str)` check, `"ab"` would be iterated into `'a', 'b'` — almost certainly not what you want.

> [!tip] The string-iterable trap
> This is the canonical example of when duck typing bites. Strings are iterable, so any code that does `for x in maybe_a_string` will iterate characters. The fix is `isinstance(x, str)` — a deliberate departure from pure duck typing in service of correctness. See [[6. Comprehensions Deep Dive]] (Chapter 10) for more.

## Polymorphism via `functools.singledispatch`

When you want to dispatch a function on the type of its first argument, `singledispatch` is the Pythonic answer (PEP 443). It's a form of ad hoc polymorphism — like function overloading in C++, but resolved at runtime:

```python
from functools import singledispatch
import json

@singledispatch
def to_json(obj):
    raise TypeError(f"Cannot serialize {type(obj).__name__}")

@to_json.register(str)
def _(obj):
    return json.dumps(obj)

@to_json.register(int)
def _(obj):
    return str(obj)

@to_json.register(list)
def _(obj):
    return "[" + ", ".join(to_json(x) for x in obj) + "]"

@to_json.register(dict)
def _(obj):
    return "{" + ", ".join(f'"{k}": {to_json(v)}' for k, v in obj.items()) + "}"

print(to_json({"name": "Alice", "age": 30, "tags": ["a", "b"]}))
# {"name": "Alice", "age": 30, "tags": ["a", "b"]}
```

`singledispatch` is great when:

- The dispatch logic is on the *receiver*, not on the value (in which case method polymorphism is fine).
- You can't modify the classes you want to support (e.g., adding `.to_json()` to `int` is impossible).
- You want to keep the logic in one place rather than spread across many classes.

See [[2. partial and singledispatch]] (Chapter 19) for the full story, including `singledispatchmethod` for methods.

## Comparison: Python vs C++ Polymorphism

| Feature | C++ | Python |
|---------|-----|--------|
| Dispatch | Virtual function table | Runtime attribute lookup |
| Inheritance required? | Yes for `virtual` dispatch | No — duck typing works on any object with the method |
| Interface declaration | `class I { virtual void f() = 0; };` | ABC (`@abstractmethod`) or `Protocol` (typing) |
| Static checking | Compiler enforces interface | Optional — mypy / pyright |
| Overloading | Yes (compile-time resolution) | No — use `singledispatch` or default args |
| Generic dispatch | Templates (compile-time) | `Protocol`, `TypeVar`, generics via `typing` |
| Performance | Very fast (direct vtable call) | Slower (attribute lookup, descriptor protocol) |
| Flexibility | Rigid — must declare everything | High — anything that quacks is a duck |
| Error visibility | Compile-time type errors | Runtime `AttributeError` (or static-only via mypy) |

Both styles work; they reflect different philosophies. C++ trades flexibility for safety and speed. Python trades safety and speed for flexibility — and offers mypy as an optional layer to recover safety.

## A Worked Example: A Plugin System

Let's combine everything — duck typing, ABCs, Protocol, and polymorphism — in a single coherent example.

```python
from typing import Protocol, runtime_checkable
from abc import ABC, abstractmethod


# --- Protocol: structural interface (mypy-checkable) ---

@runtime_checkable
class Sink(Protocol):
    def write(self, data: bytes) -> int: ...


# --- ABC: abstract base class for plugins ---

class Plugin(ABC):
    name: str

    @abstractmethod
    def process(self, data: bytes) -> bytes:
        ...


# --- Concrete plugins (don't inherit from Sink) ---

class ConsoleSink:
    def write(self, data: bytes) -> int:
        print(f"[console] {data.decode()}")
        return len(data)


class FileSink:
    def __init__(self, path):
        self.path = path
    def write(self, data: bytes) -> int:
        with open(self.path, "ab") as f:
            f.write(data)
        return len(data)


# --- A plugin that uses any Sink ---

class UppercasePlugin(Plugin):
    name = "upper"

    def __init__(self, sink: Sink):
        self.sink = sink   # typed as Protocol — accepts ConsoleSink, FileSink, etc.

    def process(self, data: bytes) -> bytes:
        out = data.upper()
        self.sink.write(out)
        return out


# --- Usage ---

plugin = UppercasePlugin(ConsoleSink())
plugin.process(b"hello")   # [console] HELLO
print(isinstance(ConsoleSink(), Sink))   # True — runtime protocol check
```

What's happening:

- `Sink` is a **Protocol** — any class with a `write(bytes) -> int` method satisfies it, structurally.
- `ConsoleSink` and `FileSink` don't inherit from `Sink`. They just have the right method.
- `UppercasePlugin` is type-annotated with `Sink` — mypy will accept any compatible class.
- `Plugin` is an **ABC** with an abstract `process` method — concrete subclasses must implement it.
- `isinstance(ConsoleSink(), Sink)` works at runtime because `Sink` is `@runtime_checkable`.

This is the modern Pythonic way: structural typing via Protocol for "interface" relationships, ABC for "must implement" enforcement, and duck typing at runtime for flexibility.

## Common Pitfalls

### 1. Over-checking types instead of duck-typing

```python
# Bad — overly restrictive
def double(x):
    if isinstance(x, int):
        return x * 2
    elif isinstance(x, str):
        return x + x
    else:
        raise TypeError("only int or str")

# Good — duck-typed
def double(x):
    return x + x
```

### 2. The string-iterable trap

```python
def flatten(items):
    for x in items:
        yield from flatten(x)   # iterates strings into characters!

list(flatten(["ab", "cd"]))   # ['a', 'b', 'c', 'd'] — probably not what you wanted
```

Fix: `if isinstance(x, str): yield x; else: try: yield from flatten(x)`.

### 3. Calling `len()` on something without `__len__`

```python
class Infinite:
    def __iter__(self):
        i = 0
        while True:
            yield i
            i += 1

len(Infinite())   # TypeError: object of type 'Infinite' has no len()
```

`len()` requires `__len__`. If you have an "iterable but not sized" object, `len()` won't work — use `list(it)` (which may run forever!) or redesign.

### 4. EAFP with too-broad except

```python
try:
    obj.save()
except Exception:   # too broad!
    pass
```

This swallows `KeyboardInterrupt`, `SystemExit`, `MemoryError`, programming errors... Always catch the specific exception (`AttributeError`, `IOError`, etc.).

### 5. Protocols don't enforce signatures at runtime

```python
@runtime_checkable
class Adder(Protocol):
    def add(self, a: int, b: int) -> int: ...

class BadAdder:
    def add(self):   # wrong signature!
        return 0

isinstance(BadAdder(), Adder)   # True — runtime check only verifies method name
```

`@runtime_checkable` is name-only. Use mypy for full signature checking.

### 6. ABCs with non-abstract methods can be misleading

```python
class Base(ABC):
    @abstractmethod
    def step(self): ...

    def run(self):
        for _ in range(10):
            self.step()
```

`Base.run` calls `self.step`. If a subclass forgets to implement `step`, you can't instantiate the subclass — good. But if a subclass *overrides* `run` and forgets to call `step`, the abstract method's intent is silently violated. ABCs enforce *presence*, not *use*.

### 7. Subtype polymorphism where structural would do

```python
# Overengineered
class Animal(ABC):
    @abstractmethod
    def speak(self): ...

class Dog(Animal):
    def speak(self): return "woof"

class Cat(Animal):
    def speak(self): return "meow"

# Simpler — just use duck typing
def make_speak(a):
    return a.speak()
```

If you don't need the ABC for `isinstance` or `issubclass` checks, you don't need it.

### 8. Method resolution surprises with multiple inheritance

Polymorphism can be tricky when method dispatch goes through the MRO — see [[3. Inheritance]]. A method you expect to be called might be shadowed by a sibling class earlier in the MRO.

### 9. Using `type(x) is Foo` instead of `isinstance`

```python
type(True) is int    # False — bool is a subclass of int
isinstance(True, int)   # True
```

`type(x) is Foo` doesn't consider subclassing. `isinstance` does. For most uses, `isinstance` is correct.

### 10. Assuming duck typing means "no contracts"

Duck typing doesn't mean "no documentation." Document the methods you expect, ideally with a `Protocol` type hint. Otherwise, callers have to read your code to know what shape of object to pass.

## Tips and Tricks

- **Default to duck typing.** Don't add `isinstance` checks unless you have a real reason.
- **Use `typing.Protocol` for static-checkable duck typing.** It documents the contract and gets you mypy/pyright support.
- **Use ABCs when you want to enforce "must implement"** at instantiation time.
- **Use `functools.singledispatch`** for type-based dispatch on free functions.
- **EAFP over LBYL** — try the operation, catch the specific exception.
- **Catch specific exceptions**, not bare `except:`.
- **Implement Python's protocols** (`__iter__`, `__len__`, `__contains__`, `__getitem__`, `__enter__`/`__exit__`) to make your class play nicely with built-ins.
- **Always check `isinstance(x, str)` before iterating** if you want strings treated as atoms.
- **Don't inherit just to polymorph.** If two classes happen to share a method name but have no real "is-a" relationship, leave them separate.
- **Document the duck-typed interface** in the docstring, even if you don't use a Protocol.
- **Use `@runtime_checkable` Protocols sparingly** — name-only checks can give false confidence.
- **Subclass `collections.abc.Sequence` / `Mapping` / `Set`** to get a lot of mixin methods for free, just by implementing a few core ones.
- **`isinstance(x, Callable)`** (from `collections.abc`) checks if `x` is callable — useful for "function or callable object" parameters.
