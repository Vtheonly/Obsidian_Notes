# 8. Composition vs Inheritance

## Why This Matters

"Favor **object composition** over **class inheritance**."

— *Design Patterns* (Gang of Four, 1994), the most quoted advice in OOP.

Inheritance is seductive. It feels elegant: `Dog` extends `Animal`, `Square` extends `Rectangle`, `Manager` extends `Employee`. Code reuse is automatic! Type relationships are explicit! Polymorphism is free!

But inheritance has a dark side:

- **Rigid hierarchies** — once `Dog` inherits from `Animal`, you can't change your mind without breaking every subclass.
- **Fragile base classes** — changing `Animal` can break `Dog` in subtle ways.
- **Liskov violations** — `Square extends Rectangle` seems natural, but squares can't have independent width and height, which breaks the rectangle contract.
- **Deep coupling** — a subclass is intimately tied to its parent's implementation, not just its interface.
- **Multiple inheritance complexity** — once you mix in two parents, the MRO can produce surprising dispatch order (see [[3. Inheritance]]).
- **Runtime surprises** — in Python, method resolution is dynamic and depends on the MRO, which can change as the hierarchy evolves.

Composition offers an alternative: instead of saying "`Dog` *is an* `Animal`," say "`Dog` *has an* `Animal`-like body, *has a* `Bark` behaviour, *has a* `Diet`." Build objects out of smaller objects, each with a clear, narrow responsibility. This is more flexible, more testable, and more maintainable.

This note covers the **IS-A vs HAS-A** distinction, the **delegation pattern**, **runtime composition**, the pitfalls of multiple inheritance, and **mixins** as a middle ground. After this, you'll know when to inherit, when to compose, and how to migrate from one to the other when your design outgrows its first draft.

---

## Background

Two ways to reuse code:

- **Inheritance** (IS-A): `B(A)` means `B` is a kind of `A`. `B` gets `A`'s attributes and methods automatically.
- **Composition** (HAS-A): `B` *contains* an instance of `A` as an attribute. `B` delegates to `A` for the relevant behaviour.

```python
# Inheritance
class Animal:
    def eat(self): print("eating")

class Dog(Animal):
    def bark(self): print("bark")

d = Dog()
d.eat()    # inherited
d.bark()   # own

# Composition
class Animal:
    def eat(self): print("eating")

class Dog:
    def __init__(self):
        self.animal = Animal()    # HAS-A
    def eat(self):
        self.animal.eat()         # delegate
    def bark(self): print("bark")

d = Dog()
d.eat()    # delegated
d.bark()   # own
```

The composition version is more code, but it's also more flexible:

- `Dog` can swap its `Animal` for a different implementation at runtime.
- `Dog` can compose multiple objects: `self.body`, `self.legs`, `self.diet`, `self.sound`.
- Changes to `Animal` don't automatically affect `Dog` — only the methods `Dog` explicitly delegates to.

The GoF advice isn't "never inherit" — it's "**favor** composition." Inheritance is still the right tool when there's a true IS-A relationship and the base class is stable. Composition is the right tool when you want flexibility, want to combine behaviours from multiple sources, or want to change behaviour at runtime.

## IS-A vs HAS-A

The two relationships answer different questions:

- **IS-A**: "Is every `B` also a kind of `A`?" If yes, `B` may inherit from `A`. Examples: `Dog` IS-A `Animal`, `Circle` IS-A `Shape`, `Sedan` IS-A `Car`.
- **HAS-A**: "Does `B` *contain* an `A` as part of its state?" If yes, `B` should compose `A`. Examples: `Car` HAS-A `Engine`, `House` HAS-A `Room`, `Order` HAS-A `Customer`.

### The Square-Rectangle problem

A classic Liskov violation. `Square` IS-A `Rectangle`, right? Mathematically yes. But in code:

```python
class Rectangle:
    def __init__(self, w, h):
        self.width = w
        self.height = h
    def set_width(self, w):
        self.width = w
    def set_height(self, h):
        self.height = h
    def area(self):
        return self.width * self.height

class Square(Rectangle):
    def set_width(self, w):
        self.width = w
        self.height = w   # keep square
    def set_height(self, h):
        self.width = h
        self.height = h   # keep square
```

A user holding a `Rectangle` reference expects `set_width(5)` to change only width. If the actual object is a `Square`, `set_width(5)` changes height too. The contract is violated. This is the **Liskov Substitution Principle** (the L in SOLID — see [[3. SOLID Principles]]).

Composition fixes it cleanly:

```python
class Rectangle:
    def __init__(self, w, h):
        self.width, self.height = w, h

class Square:
    def __init__(self, side):
        self._rect = Rectangle(side, side)
    @property
    def side(self):
        return self._rect.width
    @side.setter
    def side(self, s):
        self._rect = Rectangle(s, s)
```

`Square` is no longer a `Rectangle` — it has one. No contract violation; the user of a `Rectangle` is never surprised by a `Square`.

### IS-A relationships that work

```python
class Shape: ...
class Circle(Shape): ...    # IS-A — every Circle is a Shape
class Square(Shape): ...    # IS-A — every Square is a Shape
```

If `Shape` is an ABC with abstract `area` and `perimeter`, and subclasses fully implement the contract, inheritance works. The contract is clear and stable.

### HAS-A relationships that work

```python
class Engine:
    def start(self): ...
    def stop(self): ...

class Car:
    def __init__(self):
        self.engine = Engine()   # HAS-A
    def start(self):
        self.engine.start()
```

`Car` doesn't inherit from `Engine` — that would mean every `Car` IS-A `Engine`, which is absurd. It composes an `Engine`.

## The Delegation Pattern

Composition's main cost is **boilerplate**: if `Dog` should expose 20 of `Animal`'s 30 methods, you need 20 wrapper methods. The **delegation pattern** automates this.

### Manual delegation

```python
class Animal:
    def eat(self): print("eating")
    def sleep(self): print("sleeping")
    def breathe(self): print("breathing")

class Dog:
    def __init__(self):
        self.animal = Animal()

    # Delegate
    def eat(self): return self.animal.eat()
    def sleep(self): return self.animal.sleep()
    def breathe(self): return self.animal.breathe()

    # Own behaviour
    def bark(self): print("bark")
```

Verbose but explicit. Each delegated method is a one-liner. Easy to read, easy to test.

### `__getattr__` delegation

`__getattr__` is called only when normal attribute lookup fails. We can use it to forward missing methods to the wrapped object:

```python
class Dog:
    def __init__(self):
        self._animal = Animal()

    def bark(self):
        print("bark")

    def __getattr__(self, name):
        # Called only if `name` isn't found normally
        return getattr(self._animal, name)

d = Dog()
d.eat()      # not defined on Dog → __getattr__ → Animal.eat
d.sleep()    # not defined on Dog → __getattr__ → Animal.sleep
d.bark()     # defined on Dog → called directly
```

This is the **proxy pattern** — `Dog` looks like an `Animal` to anyone calling methods on it. See [[6. Magic Methods]] for `__getattr__` details.

> [!warning] `__getattr__` is only called for missing attributes
> If `Dog` defines `eat` (even as `None`), `__getattr__` won't be called for `eat`. Don't accidentally shadow delegated methods.

### `__getattr__` with multiple composed objects

```python
class FlexibleDog:
    def __init__(self):
        self._animal = Animal()
        self._legs = Legs()
        self._diet = Diet()

    def __getattr__(self, name):
        # Try each composed object
        for component in [self._animal, self._legs, self._diet]:
            try:
                return getattr(component, name)
            except AttributeError:
                continue
        raise AttributeError(name)

    def bark(self):
        print("bark")
```

This dispatches unknown method calls to whichever component has them. Powerful but potentially ambiguous — if two components define the same method, the first wins. Document the order carefully.

### `functools.wraps` for delegation helpers

For one-off delegations, a small helper can reduce boilerplate:

```python
def delegate(to, methods):
    """Class decorator: delegate `methods` to `to`."""
    def decorator(cls):
        for m in methods:
            def make_method(name):
                def method(self, *args, **kwargs):
                    return getattr(getattr(self, to), name)(*args, **kwargs)
                return method
            setattr(cls, m, make_method(m))
        return cls
    return decorator

@delegate("_animal", ["eat", "sleep", "breathe"])
class Dog:
    def __init__(self):
        self._animal = Animal()
    def bark(self): print("bark")
```

Use sparingly — explicit delegation is clearer when there are only a few methods.

## Runtime Composition

Inheritance is fixed at class definition. Composition is dynamic — you can swap components at runtime:

```python
class Engine:
    def start(self): return "vroom"

class ElectricMotor:
    def start(self): return "whirr"

class Car:
    def __init__(self, engine):
        self.engine = engine    # any object with .start() works

    def start(self):
        return self.engine.start()

gas_car = Car(Engine())
electric_car = Car(ElectricMotor())
print(gas_car.start())      # vroom
print(electric_car.start()) # whirr

# Swap at runtime
gas_car.engine = ElectricMotor()
print(gas_car.start())      # whirr
```

You can't do this with inheritance — a `GasCar` can't become an `ElectricCar` without changing its class. Composition lets you change behaviour dynamically.

### Strategy pattern

This is the **Strategy pattern**: encapsulate behaviour in a separate object, inject it, swap it at runtime.

```python
from typing import Protocol

class SortStrategy(Protocol):
    def sort(self, data): ...

class QuickSort:
    def sort(self, data):
        return sorted(data)   # placeholder

class MergeSort:
    def sort(self, data):
        return sorted(data, reverse=True)

class Sorter:
    def __init__(self, strategy: SortStrategy):
        self.strategy = strategy
    def sort(self, data):
        return self.strategy.sort(data)

s = Sorter(QuickSort())
print(s.sort([3, 1, 2]))   # [1, 2, 3]
s.strategy = MergeSort()
print(s.sort([3, 1, 2]))   # [3, 2, 1]
```

## Multiple Inheritance Pitfalls

Python allows multiple inheritance, and the MRO (see [[3. Inheritance]]) handles diamond problems deterministically. But MI has its own pitfalls beyond diamonds:

### 1. The Fragile Base Class problem

```python
class Base:
    def action(self):
        self.prepare()
        self.do_work()
        self.cleanup()

    def prepare(self): print("base prepare")
    def do_work(self): print("base work")
    def cleanup(self): print("base cleanup")

class Mixin:
    def prepare(self):
        print("mixin prepare")
        super().prepare()   # cooperative
```

If you compose `class Derived(Mixin, Base)`, calling `Derived().action()` invokes `Base.action`, which calls `self.prepare` — which is `Mixin.prepare`. If `Mixin.prepare` doesn't call `super().prepare()`, `Base.prepare` is silently skipped. The base class is "fragile" because its internal method calls depend on subclasses behaving cooperatively.

### 2. Unpredictable method dispatch

```python
class A:
    def f(self): return "A"

class B(A):
    def f(self): return "B"

class C(A):
    def f(self): return "C"

class D(B, C):
    pass

print(D().f())   # 'B' — D's MRO is (D, B, C, A, object)
```

`D` gets `B.f`. If you change to `class D(C, B)`, you get `C.f`. The order of bases is significant and easy to forget.

### 3. `__init__` complexity

With multiple inheritance, every class must use cooperative `super().__init__(**kwargs)` and pop the kwargs it consumes. One non-cooperative class breaks the chain. See [[3. Inheritance]] for the full pattern.

### 4. State coupling

If two parent classes both use `self.x` for different purposes, you get mysterious bugs. Name mangling (`__x`) helps, but only for double-underscore names.

### 5. "Giant hierarchy" anti-pattern

```python
class Vehicle: ...
class LandVehicle(Vehicle): ...
class RoadVehicle(LandVehicle): ...
class Car(RoadVehicle): ...
class Sedan(Car): ...
class LuxurySedan(Sedan): ...
```

Six levels deep. Any change at the top ripples through every subclass. Refactor to composition: `LuxurySedan` has-a `Chassis`, has-a `Engine`, has-a `TrimPackage`.

## Mixins — A Middle Ground

A **mixin** is a class designed to be multiply inherited, providing a single piece of optional behaviour. Mixins are usually small, focused, and don't make sense standalone.

```python
class LogMixin:
    """Adds logging to any class."""
    def log(self, msg):
        print(f"[{type(self).__name__}] {msg}")

class JsonMixin:
    """Adds JSON serialisation."""
    def to_json(self):
        import json
        return json.dumps(self.__dict__)

class ReprMixin:
    def __repr__(self):
        attrs = ", ".join(f"{k}={v!r}" for k, v in self.__dict__.items())
        return f"{type(self).__name__}({attrs})"


class User(LogMixin, JsonMixin, ReprMixin):
    def __init__(self, name, email):
        self.name = name
        self.email = email

u = User("Alice", "alice@example.com")
u.log("created")            # [User] created
print(u.to_json())          # {"name": "Alice", "email": "alice@example.com"}
print(u)                    # User(name='Alice', email='alice@example.com')
```

Mixins work well when:

- Each mixin is **independent** — doesn't depend on attributes or methods of other mixins.
- The composition is **orthogonal** — `LogMixin` is independent of `JsonMixin`.
- The base class is **explicit** — `User` clearly inherits from `LogMixin, JsonMixin, ReprMixin`, not from a deep hierarchy.

Mixins can fail when:

- Two mixins define the same method (collisions, MRO-dependent).
- A mixin depends on attributes the class doesn't have (implicit contract).
- The hierarchy grows: `class FancyUser(LogMixin, JsonMixin, ReprMixin, AuditMixin, CacheMixin, PermissionMixin, User)` — getting silly.

For full treatment, see [[3. Mixins]] (Chapter 18). When mixins get complicated, switch to composition.

## When to Inherit vs Compose

### Inherit when:

1. **True IS-A relationship** — `Dog` IS-A `Animal`, `Circle` IS-A `Shape`.
2. **You want to override specific methods** of a base class (template method pattern).
3. **You need `isinstance` checks** to work — `isinstance(dog, Animal)` is `True` if `Dog` inherits from `Animal`.
4. **You're subclassing an ABC** to implement an interface — see [[1. Abstract Base Classes]].
5. **The base class is stable** — you trust it not to change in ways that break you.
6. **You want code reuse via shared implementation** — but be honest about whether the relationship is IS-A.

### Compose when:

1. **HAS-A relationship** — `Car` HAS-A `Engine`.
2. **You want to swap implementations at runtime** — strategy pattern.
3. **You want to combine multiple behaviours** without the complexity of MI.
4. **The "base" isn't yours** — subclassing third-party classes is risky.
5. **You need multiple "kinds" of the same thing** — `Car` HAS-A `Engine` and HAS-A `Tire` set; you can't inherit from both.
6. **The contract might be violated by inheritance** — Square/Rectangle.
7. **You're tempted to use `isinstance` to dispatch** — composition + polymorphism is often cleaner.

### Heuristic: the "is-a" sentence test

Try to say "`B` is a `A`" out loud. Does it sound natural?

- "A `Dog` is an `Animal`" — yes. Inherit.
- "A `Car` is an `Engine`" — no, that's absurd. Compose.
- "A `Manager` is an `Employee`" — maybe. Sometimes (manager has different pay rules) it's a violation.
- "A `Stack` is a `List`" — tempting, but `Stack` shouldn't expose `insert(0, x)`. Compose: `Stack` HAS-A `List`.

### Heuristic: the "Liskov" test

Can a `B` be used *anywhere* an `A` is expected, without surprises?

- `Circle` for `Shape` — yes (as long as `Circle` implements all of `Shape`'s abstract methods).
- `Square` for `Rectangle` — no (set_width breaks). Compose instead.
- `Ostrich` for `Bird` (with `fly` method) — no (ostriches can't fly). Either make `fly` optional in the base, or compose.

If Liskov fails, compose.

## Refactoring: From Inheritance to Composition

A common refactor: you inherited because it was quick, but the hierarchy is now rigid. Move to composition.

### Before (inheritance)

```python
class JSONLogger:
    def log(self, msg):
        import json
        print(json.dumps({"msg": msg}))

class TimedJSONLogger(JSONLogger):
    def log(self, msg):
        import time
        super().log({"time": time.time(), "msg": msg})
```

`TimedJSONLogger` IS-A `JSONLogger`. But what if you also want a `TimedCSVLogger`? Inheriting from both `TimedJSONLogger` and `CSVLogger` is messy.

### After (composition)

```python
class JSONFormatter:
    def format(self, msg):
        import json
        return json.dumps({"msg": msg})

class CSVFormatter:
    def format(self, msg):
        return f"msg,{msg}"

class TimestampDecorator:
    def __init__(self, inner):
        self.inner = inner
    def format(self, msg):
        import time
        return self.inner.format({"time": time.time(), "msg": msg})

class Logger:
    def __init__(self, formatter):
        self.formatter = formatter
    def log(self, msg):
        print(self.formatter.format(msg))

# Combine freely
Logger(JSONFormatter()).log("hello")
Logger(TimestampDecorator(JSONFormatter())).log("hello")
Logger(CSVFormatter()).log("hello")
Logger(TimestampDecorator(CSVFormatter())).log("hello")
```

Now `JSONFormatter` and `TimestampDecorator` are independent. You can stack them in any combination. This is the **decorator pattern** (in the GoF sense — not Python's `@decorator` syntax).

## A Worked Example: A `Character` in a Game

Let's build a game character using both inheritance and composition, and see why composition wins for the game-character case.

```python
# === Components (HAS-A) ===

class Health:
    def __init__(self, max_hp):
        self.max_hp = max_hp
        self.hp = max_hp
    def damage(self, amount):
        self.hp = max(0, self.hp - amount)
    def heal(self, amount):
        self.hp = min(self.max_hp, self.hp + amount)
    def is_alive(self):
        return self.hp > 0

class Inventory:
    def __init__(self):
        self.items = []
    def add(self, item):
        self.items.append(item)
    def remove(self, item):
        self.items.remove(item)

class Weapon:
    def __init__(self, name, damage):
        self.name = name
        self.damage = damage
    def attack(self, target):
        target.health.damage(self.damage)

class Movement:
    def __init__(self, speed):
        self.speed = speed
        self.x, self.y = 0, 0
    def move(self, dx, dy):
        self.x += dx * self.speed
        self.y += dy * self.speed


# === The Character (composes components) ===

class Character:
    def __init__(self, name, hp=100, speed=1):
        self.name = name
        self.health = Health(hp)
        self.inventory = Inventory()
        self.movement = Movement(speed)
        self.weapon = None

    def equip(self, weapon):
        self.weapon = weapon

    def attack(self, target):
        if self.weapon is None:
            raise RuntimeError(f"{self.name} has no weapon")
        print(f"{self.name} attacks {target.name}")
        self.weapon.attack(target)

    def move(self, dx, dy):
        print(f"{self.name} moves to ({self.movement.x + dx * self.movement.speed},"
              f" {self.movement.y + dy * self.movement.speed})")
        self.movement.move(dx, dy)

    def __repr__(self):
        return (f"Character({self.name!r}, hp={self.health.hp}/{self.health.max_hp},"
                f" weapon={self.weapon.name if self.weapon else None})")


# === Subclasses (inheritance, for IS-A) ===

class Warrior(Character):
    """IS-A Character, but with a default weapon and higher HP."""
    def __init__(self, name):
        super().__init__(name, hp=150, speed=0.8)
        self.equip(Weapon("Sword", 25))

class Archer(Character):
    def __init__(self, name):
        super().__init__(name, hp=90, speed=1.2)
        self.equip(Weapon("Bow", 18))


# === Usage ===

w = Warrior("Conan")
a = Archer("Legolas")
print(w)   # Character('Conan', hp=150/150, weapon='Sword')
print(a)   # Character('Legolas', hp=90/90, weapon='Bow')

w.attack(a)
print(a)   # hp=72/90
```

Things to notice:

- `Character` HAS-A `Health`, `Inventory`, `Movement`, and an optional `Weapon`. These are independent, swappable components.
- `Warrior` and `Archer` ARE-A `Character` — they share the basic character interface but have different defaults. This is a true IS-A relationship that's stable (a warrior is always a character).
- If we'd tried to model this with deep inheritance (`Character` → `Fighter` → `Warrior`, `Character` → `Ranged` → `Archer`), adding a `Mage` who is both a `Fighter` and `Ranged` would require MI. With composition, just swap the `Weapon`.
- The components can be tested in isolation: `Health`, `Inventory`, `Movement`, `Weapon` are all standalone classes with their own tests.

This is the GoF advice in action: `Warrior` inherits for the IS-A relationship with `Character`, but everything that varies (HP, speed, weapon) is composed rather than put into a deep hierarchy.

## Common Pitfalls

### 1. Inheriting for code reuse alone

```python
class Bad:
    """Inherits from list just to add one method."""
    def sum(self):
        return sum(self)

class Bad2(list):   # IS-A list?
    def sum(self):
        return sum(self)
```

If `Bad2` doesn't really IS-A `list` (e.g., it doesn't support all list operations meaningfully), compose instead:

```python
class Good:
    def __init__(self, items):
        self._items = list(items)
    def sum(self):
        return sum(self._items)
```

### 2. Subclassing third-party classes

```python
class MyDict(dict):
    """I want a dict that..."""
    pass
```

Subclassing `dict`, `list`, `str` is risky — their C-level operations don't always call your Python overrides. Prefer `collections.UserDict` / `UserList` / `UserString`, or compose.

### 3. Deep hierarchies

```python
class A: ...
class B(A): ...
class C(B): ...
class D(C): ...
class E(D): ...
class F(E): ...
```

Six levels deep is suspicious. Refactor — usually some of those layers should be composed objects, not inherited.

### 4. Mixin soup

```python
class Thing(LogMixin, AuditMixin, CacheMixin, PermissionMixin,
            ValidationMixin, SerializationMixin, Base): ...
```

If you have five mixins, you have five implicit contracts that interact unpredictably. Switch to composition: `Thing` HAS-A `Logger`, HAS-A `Auditor`, HAS-A `Cache`, etc.

### 5. Fragile base class

If a base class's internal `self.helper()` calls are essential to its behaviour, and a subclass can override `helper` to break the contract, the base is fragile. Either make `helper` private (`_helper` and document "don't override"), or restructure so the base doesn't depend on overridable methods.

### 6. Liskov violations

`Square(Rectangle)`, `Ostrich(Bird)` with `fly`, `ReadOnlyList(list)` with `append` raising — all violate LSP. Compose instead.

### 7. God objects via composition

Composition can produce its own monster: a class with 20 component attributes is just as bad as a class with 20 base classes. Each component should have a clear, narrow responsibility.

### 8. Delegation that breaks interfaces

```python
class Dog:
    def __init__(self):
        self._animal = Animal()
    def __getattr__(self, name):
        return getattr(self._animal, name)
```

This delegates everything. If `Animal` later adds a method you don't want `Dog` to expose, you've leaked it. Be explicit about what you delegate.

### 9. Forgetting to delegate `__repr__`, `__eq__`, etc.

If you wrap an object and forward methods via `__getattr__`, dunders are looked up on the **type**, not the instance, so `__getattr__` won't catch them. You need to define them explicitly:

```python
class Dog:
    def __init__(self):
        self._animal = Animal()
    def __getattr__(self, name):
        return getattr(self._animal, name)
    def __repr__(self):
        return f"Dog({self._animal!r})"
    def __eq__(self, other):
        if isinstance(other, Dog):
            return self._animal == other._animal
        return NotImplemented
```

### 10. Overusing inheritance for "types"

```python
class FileLogger: ...
class ConsoleLogger: ...
class NetworkLogger: ...
# All three are loggers, but unrelated by inheritance.
```

If they share an interface, define an ABC or Protocol. Don't make them inherit from each other just to share code — they probably don't IS-A each other.

## Tips and Tricks

- **Ask "IS-A" out loud.** If the sentence sounds wrong, compose.
- **Favor composition** for behaviour you want to vary at runtime.
- **Favor inheritance** for stable IS-A relationships and interface sharing (via ABCs).
- **Use ABCs or Protocols** to define interfaces — let classes compose rather than inherit when possible.
- **The Strategy pattern** is composition's killer app: inject behaviour, swap at runtime.
- **The Decorator pattern** (GoF, not Python `@decorator`) stacks composition layers — e.g., `Logging(Caching(Auth(HttpClient)))`.
- **Keep inheritance shallow.** Three levels is a lot.
- **Mixins for orthogonal concerns** — but stop at 3-4 mixins max.
- **Subclass `collections.abc`** for containers, not `list`/`dict`/`set` directly.
- **Compose value objects** — `Money` HAS-A `Decimal` and a currency string; don't subclass `Decimal`.
- **Test components independently** — composition makes unit testing vastly easier.
- **Document the composed interface** — if `Car` expects its `engine` to have `.start()`, say so (ideally with a `Protocol`).
- **Use `__getattr__` for delegation** when there are many methods to forward.
- **Don't forget dunders when delegating** — `__repr__`, `__eq__`, `__len__` won't go through `__getattr__`.
- **Refactor inheritance to composition** when the hierarchy gets rigid. It's usually not as hard as it looks.
- **Prefer `@dataclass` + composition** over inheritance for value types.
