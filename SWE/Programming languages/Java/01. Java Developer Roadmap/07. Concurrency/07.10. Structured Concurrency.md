# Structured Concurrency

## Overview

Concurrency in Java has long had a structural weakness: when you start a thread or submit a task to an executor, the lifetime of that task is independent of the code that started it. A child task can outlive its parent, fail silently, or leak resources. Debugging such code requires tracing every submitted task and reasoning about every possible interleaving. Structured concurrency, introduced as a preview feature in Java 21 and finalised in later releases, addresses this by tying the lifetime of child tasks to a scope, in the same way that structured programming ties the lifetime of local variables to a block.

The core idea is simple: when a method opens a `StructuredTaskScope`, all child tasks forked within that scope must complete (or be cancelled) before the scope closes. The scope can configure a policy: wait for all children, wait for the first successful one, wait for the first one of any kind, and so on. This makes fan-out workloads easy to write correctly and easy to reason about.

This note covers structured concurrency in depth. We will explore the motivation, the `StructuredTaskScope` API, the built-in `ShutdownOnFailure` and `ShutdownOnSuccess` policies, custom policies, error handling, integration with virtual threads, and the relationship between structured concurrency and `ScopedValue`. We will also cover the limitations of the preview API and the migration path from `CompletableFuture` and `ExecutorService` to structured concurrency.

## Background Knowledge

Before reading this note, you should be comfortable with:

- Virtual threads, covered in the previous note. Structured concurrency is designed to be used with virtual threads, because each child task gets its own virtual thread.
- `CompletableFuture` and its combinators, particularly `allOf` and `anyOf`, which structured concurrency replaces for many use cases.
- Exceptions in concurrent code: how `ExecutionException` wraps task failures, and how cancellation works via `Future.cancel`.

The defining principle of structured concurrency is that the call tree mirrors the concurrency tree. If method `handleRequest` forks three child tasks to fetch user data, orders, and recommendations, the call to `handleRequest` does not return until all three children have completed (or been cancelled). This is in contrast to submitting tasks to an executor and returning immediately, which leaves the caller with no way to know when the children are done.

## The Problem Structured Concurrency Solves

Consider a typical fan-out pattern using `ExecutorService`:

```java
public Profile loadProfile(long userId) throws Exception {
    Future<User> userF = executor.submit(() -> fetchUser(userId));
    Future<List<Order>> ordersF = executor.submit(() -> fetchOrders(userId));
    Future<List<String>> recsF = executor.submit(() -> fetchRecommendations(userId));

    // What if fetchUser throws? The other two tasks keep running,
    // wasting resources and possibly failing silently.
    return new Profile(userF.get(), ordersF.get(), recsF.get());
}
```

Several problems exist with this code:

1. **No cancellation on failure**: if `fetchUser` throws, `ordersF` and `recsF` continue running. They consume threads, network connections, and database capacity, even though their results will never be used.
2. **No error propagation**: each `get()` call can throw, and the order in which you call them determines which errors you see. If `fetchUser` succeeds but `fetchOrders` throws, you have already paid for `fetchUser` and cannot roll it back.
3. **No lifecycle binding**: the caller of `loadProfile` has no way to cancel all three child tasks at once. If the request is cancelled, the children keep running.
4. **Leaked resources**: if any of the child tasks open a file or a database connection, those resources may not be released until the child completes, which can be long after the parent has given up.

Structured concurrency fixes all four problems by binding the lifetime of the children to a scope.

## The StructuredTaskScope API

The `StructuredTaskScope` class is the heart of structured concurrency. It is a preview feature in Java 21; enable it with `--enable-preview`.

### Basic Structure

```java
try (var scope = new StructuredTaskScope<Object>()) {
    // Fork child tasks; each runs on its own virtual thread.
    Subtask<User> userTask = scope.fork(() -> fetchUser(userId));
    Subtask<List<Order>> ordersTask = scope.fork(() -> fetchOrders(userId));
    Subtask<List<String>> recsTask = scope.fork(() -> fetchRecommendations(userId));

    // Wait for all children to complete (or be cancelled).
    scope.join();

    // Process results.
    return new Profile(
        userTask.get(),
        ordersTask.get(),
        recsTask.get()
    );
}
```

The key elements:

1. **`try-with-resources`**: the scope is `AutoCloseable`. When the `try` block exits, the scope's `close` method waits for any unfinished children to complete (or cancels them, depending on the policy). This guarantees that no child task outlives the scope.
2. **`fork`**: starts a new virtual thread for the task. Returns a `Subtask<T>` that you can later query for the result.
3. **`join`**: blocks until all forked children have completed (or been cancelled). It does not throw on child failure; the policy determines how to handle failures.
4. **`get`**: returns the result of a successful subtask, or throws if the subtask has not completed or has failed.

### Subtask State

A `Subtask` has a state, accessible via `state()`:

- `UNAVAILABLE`: the task has not completed.
- `SUCCESS`: the task completed successfully; `get()` returns the result.
- `FAILED`: the task threw an exception; `exception()` returns the throwable.

```java
Subtask<User> task = scope.fork(() -> fetchUser(userId));
scope.join();
switch (task.state()) {
    case SUCCESS -> System.out.println("Got " + task.get());
    case FAILED  -> System.err.println("Failed: " + task.exception());
    case UNAVAILABLE -> throw new IllegalStateException("should not happen");
}
```

## The Built-in Policies

The base `StructuredTaskScope` waits for all children, but does not handle errors. In practice, you almost always use one of two built-in subclasses that implement common policies.

### ShutdownOnFailure

`ShutdownOnFailure` shuts down the scope (cancels remaining children) as soon as any child fails. After `join`, you call `throwIfFailed` to propagate the first failure as an exception.

```java
public Profile loadProfile(long userId) throws Exception {
    try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
        Subtask<User> userTask = scope.fork(() -> fetchUser(userId));
        Subtask<List<Order>> ordersTask = scope.fork(() -> fetchOrders(userId));
        Subtask<List<String>> recsTask = scope.fork(() -> fetchRecommendations(userId));

        // Wait for all children, or until any fails.
        scope.join();

        // Propagate the first failure (if any) as an exception.
        scope.throwIfFailed(ex -> new ProfileLoadException(ex));

        // All children succeeded; safe to call get().
        return new Profile(
            userTask.get(),
            ordersTask.get(),
            recsTask.get()
        );
    }
}
```

If `fetchUser` throws, the scope shuts down, cancelling `fetchOrders` and `fetchRecommendations`. `join` returns, and `throwIfFailed` throws a `ProfileLoadException`. The other two tasks are interrupted and never complete.

### ShutdownOnSuccess

`ShutdownOnSuccess` shuts down the scope as soon as any child succeeds. This is the structured-concurrency equivalent of `invokeAny`: you have several redundant sources and you want the first successful result.

```java
public String queryReplica(String query) throws Exception {
    try (var scope = new StructuredTaskScope.ShutdownOnSuccess<String>()) {
        for (String replica : List.of("r1", "r2", "r3")) {
            scope.fork(() -> queryReplica(replica, query));
        }
        // Wait for the first success, or for all to fail.
        scope.join();
        // Return the first successful result.
        return scope.result();
    }
}
```

If `r1` returns first, the scope shuts down, cancelling the requests to `r2` and `r3`. `result()` returns the value from `r1`. If all three fail, `result()` throws the last exception.

### Comparison with ExecutorService

| Property                  | ExecutorService.invokeAny | ShutdownOnSuccess | ExecutorService.invokeAll | ShutdownOnFailure |
|---------------------------|---------------------------|-------------------|---------------------------|-------------------|
| First successful wins     | Yes                       | Yes               | No                        | No                |
| Cancels losers            | Yes                       | Yes               | No                        | Yes (on failure)  |
| Lifecycle bound to caller | No                        | Yes               | No                        | Yes               |
| Works with virtual threads | Possible                | Yes               | Possible                  | Yes               |

The structural difference is that `ShutdownOnFailure` and `ShutdownOnSuccess` cancel remaining children automatically, while `ExecutorService` leaves them running.

## Custom Policies

You can extend `StructuredTaskScope` to implement custom policies. Override the `handleComplete` method, which is invoked when a subtask completes:

```java
public class FirstSuccessful<T> extends StructuredTaskScope<T> {
    private volatile T result;
    private volatile Throwable firstFailure;

    @Override
    protected void handleComplete(Subtask<? extends T> subtask) {
        switch (subtask.state()) {
            case SUCCESS -> {
                result = subtask.get();
                shutdown();  // cancel remaining children
            }
            case FAILED -> {
                if (firstFailure == null) {
                    firstFailure = subtask.exception();
                }
            }
            default -> { /* UNAVAILABLE, ignore */ }
        }
    }

    public T result() throws Throwable {
        if (result != null) return result;
        throw firstFailure;
    }
}
```

This policy returns the first successful result, but unlike `ShutdownOnSuccess`, it records the first failure for diagnostic purposes if no task succeeds.

Custom policies should be careful about thread safety: `handleComplete` may be called concurrently from multiple threads. Use `volatile` or atomic operations to update shared state.

## The Lifecycle in Detail

```mermaid

    participant Scope as StructuredTaskScope
    participant VT1 as Virtual thread 1
    participant VT2 as Virtual thread 2
    participant VT3 as Virtual thread 3

    Parent->>Scope: open scope
    Parent->>VT1: fork (fetchUser)
    Parent->>VT2: fork (fetchOrders)
    Parent->>VT3: fork (fetchRecommendations)
    Note over VT1,VT3: All three run concurrently

    VT2-->>Scope: completed successfully
    VT1-->>Scope: throws exception
    Note over Scope: handleComplete invoked<br/>ShutdownOnFailure triggers shutdown()
    Scope->>VT3: interrupt
    Note over VT3: cancelled
    Parent->>Scope: join() returns
    Parent->>Scope: throwIfFailed()
    Scope-->>Parent: throws ProfileLoadException
    Parent->>Scope: close() (no-op; already shutdown)
```

The key insight is that `join` does not return until either all children complete or the scope is shut down. `shutdown` interrupts all unfinished children; they receive the interrupt and may exit cleanly. `close` guarantees that no child task is still running when the try-with-resources block exits, even if `join` was not called.

## Error Handling

Structured concurrency changes the error-handling model for fan-out workloads. With `ExecutorService`, each `Future.get()` can throw `ExecutionException`, and you must handle each individually. With `StructuredTaskScope.ShutdownOnFailure`, you call `throwIfFailed` once after `join`, and the scope handles cancellation of the rest.

```java
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    var userTask = scope.fork(() -> fetchUser(userId));
    var ordersTask = scope.fork(() -> fetchOrders(userId));

    scope.join();
    scope.throwIfFailed();  // throws ExecutionException wrapping first failure

    // Only reached if both succeeded.
    return new Profile(userTask.get(), ordersTask.get());
}
```

The argument to `throwIfFailed` is a `Function<Throwable, Throwable>` that lets you wrap the failure in a domain-specific exception:

```java
scope.throwIfFailed(ex -> new ProfileLoadException("Failed to load profile " + userId, ex));
```

## Integration with ScopedValue

`ScopedValue` and `StructuredTaskScope` are designed to work together. A `ScopedValue` bound in the parent is automatically inherited by all children forked in the scope:

```java
private static final ScopedValue<String> REQUESTID = ScopedValue.newInstance();
private static final ScopedValue<User> CURRENTUSER = ScopedValue.newInstance();

public void handle(Request req) {
    ScopedValue.where(REQUESTID, req.id()).where(CURRENTUSER, req.user()).run(() -> {
        try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
            // Children inherit REQUESTID and CURRENTUSER.
            scope.fork(() -> audit("start"));
            scope.fork(() -> process(req));
            scope.fork(() -> audit("end"));
            scope.join().throwIfFailed();
        }
    });
}
```

This is a major improvement over `ThreadLocal` with `InheritableThreadLocal`, which does not work correctly with thread pools and produces leaks. With `ScopedValue` and `StructuredTaskScope`, the binding is automatically cleaned up when the scope exits, and there is no per-thread map pollution.

### Why ScopedValue Pairs Naturally with StructuredTaskScope

The combination of `ScopedValue` and `StructuredTaskScope` solves a problem that `ThreadLocal` cannot: propagating request context across a fan-out of child tasks without leaking memory. When a `ThreadLocal` value is set in a parent and read in a child, the child's thread carries that value forever (unless explicitly removed). With `ScopedValue`, the binding is scoped to the lexical block where `where(...).run(...)` is invoked, and any child forked inside that block inherits the binding only for the duration of the fork. When the scope closes, the bindings are automatically unbound.

This means you can fork millions of virtual tasks within a single request, each inheriting the request ID and current user, without ever worrying about cleanup. The structural guarantee of `StructuredTaskScope` (children complete before the parent) combined with the lexical guarantee of `ScopedValue` (bindings end when the block ends) means there is no possibility of a stale binding leaking into the next request.

## Use Cases

### Fan-out and gather

The most common use case: fetch multiple independent resources in parallel and combine the results.

```java
public OrderDetails loadOrderDetails(long orderId) throws Exception {
    try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
        var order = scope.fork(() -> orderService.find(orderId));
        var customer = scope.fork(() -> customerService.findByOrder(orderId));
        var items = scope.fork(() -> itemService.listByOrder(orderId));
        var shipments = scope.fork(() -> shipmentService.listByOrder(orderId));

        scope.join().throwIfFailed();

        return new OrderDetails(order.get(), customer.get(), items.get(), shipments.get());
    }
}
```

### Racing replicas

Query multiple replicas and use the first response:

```java
public Response query(String q) throws Exception {
    try (var scope = new StructuredTaskScope.ShutdownOnSuccess<Response>()) {
        for (String replica : replicas) {
            scope.fork(() -> queryReplica(replica, q));
        }
        scope.join();
        return scope.result();
    }
}
```

### Time-bounded computation

Combine `ShutdownOnFailure` with `orTimeout` to bound the total time:

```java
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    scope.fork(() -> fetchUser(userId));
    scope.fork(() -> fetchOrders(userId));

    scope.joinUntil(Instant.now().plusSeconds(2)).throwIfFailed();
    // ...
}
```

`joinUntil(deadline)` blocks until all children complete, the scope is shut down, or the deadline elapses. If the deadline elapses, the scope is shut down (cancelling children) and `joinUntil` throws `TimeoutException`.

### Tree-structured computation

Scopes can be nested, creating a tree of tasks:

```java
try (var outer = new StructuredTaskScope.ShutdownOnFailure()) {
    var profile = outer.fork(() -> {
        try (var inner = new StructuredTaskScope.ShutdownOnFailure()) {
            var user = inner.fork(() -> fetchUser(id));
            var orders = inner.fork(() -> fetchOrders(id));
            inner.join().throwIfFailed();
            return new Profile(user.get(), orders.get());
        }
    });
    var recommendations = outer.fork(() -> fetchRecommendations(id));

    outer.join().throwIfFailed();
    return new Dashboard(profile.get(), recommendations.get());
}
```

The inner scope's children are cancelled if the outer scope shuts down. This is the structural analogue of nested function calls: a child scope cannot outlive its parent.

## Comparison with CompletableFuture

`CompletableFuture` and structured concurrency solve overlapping problems but with different philosophies.

| Property                  | CompletableFuture                    | StructuredTaskScope                |
|---------------------------|--------------------------------------|-------------------------------------|
| Programming style         | Functional, callback-based           | Imperative, block-structured       |
| Lifecycle binding         | Tasks can outlive callers            | Tasks are bound to a scope          |
| Error handling            | `exceptionally`, `handle`            | `throwIfFailed`, custom policies    |
| Cancellation              | Manual, per future                   | Automatic, scope-wide               |
| Reads                     | Via callbacks or `join`              | Via `Subtask.get()` after `join`    |
| Inheritance               | No                                   | Inherits ScopedValue bindings       |

`CompletableFuture` is better for long-lived pipelines where tasks are added over time and the pipeline is exposed as an API. `StructuredTaskScope` is better for fan-out workloads where the caller wants to wait for all results. The two can be combined: you can use `CompletableFuture` inside a `StructuredTaskScope` to integrate with APIs that return futures.

## Limitations and Migration Path

Structured concurrency is a preview feature in Java 21. It is finalised in later releases, but the API may change. Before adopting it in production, you should:

1. Check the current status in your target Java version.
2. Enable preview features with `--enable-preview`.
3. Be prepared to update your code if the API changes.

For code that must run on Java 21 today, the migration path is:

- Replace `ExecutorService.invokeAll` with `ShutdownOnFailure` when you want all-or-nothing semantics.
- Replace `ExecutorService.invokeAny` with `ShutdownOnSuccess` when you want the first successful result.
- Replace `CompletableFuture.allOf` chains with `ShutdownOnFailure` for fan-out.
- Replace `CompletableFuture.anyOf` chains with `ShutdownOnSuccess` for racing.

In each case, the structured version is shorter, handles cancellation automatically, and binds the lifetime of children to the caller.

## Common Pitfalls

### Forgetting to call join

Without `join`, the scope's `close` method will block until all children finish anyway, but you lose the ability to handle results or failures. Always call `join` (or `joinUntil`) before processing results.

### Calling get on a subtask before join

`Subtask.get()` throws `IllegalStateException` if the subtask has not completed. Always call `join` first, then `get`.

### Using ShutdownOnFailure without throwIfFailed

`ShutdownOnFailure.join` does not throw on failure. If you forget `throwIfFailed`, you silently ignore failures and may call `get` on a failed subtask, which throws `IllegalStateException`.

### Holding locks across fork and join

If you hold a `synchronized` block or `ReentrantLock` while forking children, and a child also acquires the same lock, you create a deadlock (the child waits for the parent to release, the parent waits for the child to finish). The same applies to virtual threads: holding `synchronized` while waiting can pin the carrier.

### Forking tasks that mutate shared state without synchronization

Children forked in the same scope run concurrently on virtual threads. If they share mutable state, you must synchronize access. Prefer immutable state or use `ConcurrentHashMap`.

### Expecting fork to block

`fork` returns immediately; it does not wait for the task to complete. The task runs on a virtual thread in the background. `join` is what waits.

### Using the base StructuredTaskScope directly

The base `StructuredTaskScope` waits for all children but does not handle errors. If any child throws, the exception is swallowed unless you write a custom policy. Use `ShutdownOnFailure` or `ShutdownOnSuccess` unless you have a specific reason to use the base class.

### Mixing structured and unstructured concurrency

If you fork tasks in a scope and also submit tasks to an external `ExecutorService`, the external tasks are not bound to the scope. This breaks the structural guarantee: the scope may close while the external task is still running. Keep all related work inside the scope.

## Tips and Tricks

### Use ShutdownOnFailure as the default

For most fan-out workloads, `ShutdownOnFailure` is the right choice. It cancels remaining children on failure and propagates the first error cleanly.

### Use ShutdownOnSuccess for racing

When you have redundant sources and want the fastest, `ShutdownOnSuccess` cancels the losers automatically.

### Combine with ScopedValue for context propagation

`ScopedValue` bindings are inherited by all children forked in a scope, automatically and without leaks. This is the modern replacement for `ThreadLocal` in fan-out workloads.

### Use joinUntil for time-bounded operations

```java
scope.joinUntil(Instant.now().plusSeconds(2));
```

This replaces manual timeout tracking with `CompletableFuture.orTimeout`. If the deadline elapses, the scope is shut down and `joinUntil` throws `TimeoutException`.

### Wrap results in a record

The combination of records (immutable, concise) and structured concurrency (parallel, clean lifecycle) is powerful:

```java
public record Profile(User user, List<Order> orders, List<String> recommendations) {}

public Profile load(long userId) throws Exception {
    try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
        var user = scope.fork(() -> fetchUser(userId));
        var orders = scope.fork(() -> fetchOrders(userId));
        var recs = scope.fork(() -> fetchRecommendations(userId));
        scope.join().throwIfFailed();
        return new Profile(user.get(), orders.get(), recs.get());
    }
}
```

### Use custom policies for advanced use cases

If you need "all results, but tolerate specific failures" or "first success with a quorum", write a custom policy by extending `StructuredTaskScope`.

### Audit for synchronized blocks when migrating

If you migrate to structured concurrency with virtual threads, audit your code for `synchronized` blocks that may block on I/O. Replace them with `ReentrantLock` to avoid pinning.

### Use try-with-resources to guarantee cleanup

Always open the scope with try-with-resources. Even if you forget `join`, `close` will block until all children complete (or cancel them if the scope was shut down). This guarantees no child task outlives the scope.

### Use Subtask.get() only after join

After `join` returns successfully (with `ShutdownOnFailure`, after `throwIfFailed` did not throw), all subtasks have either succeeded or been cancelled. `get()` on a successful subtask is safe and does not block.

## Interview Questions

### Q1: What is structured concurrency?

A programming discipline in which the lifetime of child tasks is bound to a scope, in the same way that structured programming ties the lifetime of local variables to a block. When a method opens a `StructuredTaskScope`, all child tasks forked within that scope must complete (or be cancelled) before the scope closes.

### Q2: What problem does structured concurrency solve?

It eliminates several issues with unstructured concurrency: child tasks can outlive their parent, failures are not propagated cleanly, cancellation is per-task rather than scope-wide, and resources may leak. Structured concurrency makes fan-out workloads easier to write correctly and easier to reason about.

### Q3: How do you create a StructuredTaskScope?

You open one with try-with-resources, fork children with `scope.fork(...)`, wait with `scope.join()`, and process results with `Subtask.get()`:

```java
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    var t = scope.fork(() -> compute());
    scope.join().throwIfFailed();
    return t.get();
}
```

### Q4: What is ShutdownOnFailure?

A `StructuredTaskScope` subclass that shuts down the scope (cancels remaining children) as soon as any child fails. After `join`, you call `throwIfFailed` to propagate the first failure as an exception. It is the standard policy for all-or-nothing fan-out workloads.

### Q5: What is ShutdownOnSuccess?

A `StructuredTaskScope` subclass that shuts down the scope as soon as any child succeeds. After `join`, you call `result()` to retrieve the first successful result. It is the structured-concurrency equivalent of `invokeAny`.

### Q6: What is a Subtask?

A handle to a task forked in a `StructuredTaskScope`. It has a state: `UNAVAILABLE`, `SUCCESS`, or `FAILED`. After `join`, you can call `get()` to retrieve the result of a successful subtask, or `exception()` to retrieve the throwable of a failed one.

### Q7: How does structured concurrency handle cancellation?

When `shutdown()` is called on a scope, all unfinished children are interrupted. The children receive the interrupt and may exit cleanly. `close` blocks until all children have finished, ensuring no child task outlives the scope.

### Q8: How does structured concurrency integrate with virtual threads?

Each `fork` starts a new virtual thread for the task. The scope does not use a thread pool in the traditional sense; each task gets its own virtual thread, which is cheap to create and dispose of. The carrier pool (a `ForkJoinPool`) handles multiplexing.

### Q9: How does structured concurrency integrate with ScopedValue?

`ScopedValue` bindings made in the parent are automatically inherited by all children forked in the scope. The bindings are cleaned up automatically when the scope exits, with no leaks. This is the modern replacement for `InheritableThreadLocal`.

### Q10: What is the difference between join and joinUntil?

`join` blocks until all children complete or the scope is shut down. `joinUntil(deadline)` blocks until all children complete, the scope is shut down, or the deadline elapses. If the deadline elapses, the scope is shut down and `joinUntil` throws `TimeoutException`.

### Q11: Can you nest StructuredTaskScopes?

Yes. Scopes can be nested, creating a tree of tasks. The inner scope's children are cancelled if the outer scope shuts down. This is the structural analogue of nested function calls.

### Q12: How do you write a custom policy?

Extend `StructuredTaskScope` and override `handleComplete(Subtask)`. The method is invoked when a subtask completes; you can inspect its state, store results, and call `shutdown()` to cancel remaining children. Custom policies should be thread-safe because `handleComplete` may be called concurrently.

### Q13: What happens if you forget to call join?

The scope's `close` method will block until all children finish anyway, but you lose the ability to process results or handle failures in a structured way. Always call `join` before processing results.

### Q14: What happens if you call Subtask.get() before join?

`Subtask.get()` throws `IllegalStateException` if the subtask has not completed. Always call `join` first.

### Q15: How does structured concurrency compare to CompletableFuture?

`CompletableFuture` is functional, callback-based, and allows tasks to outlive callers. `StructuredTaskScope` is imperative, block-structured, and binds task lifetimes to a scope. `CompletableFuture` is better for long-lived pipelines; `StructuredTaskScope` is better for fan-out workloads where the caller wants to wait for all results.

## Summary

Structured concurrency is the final piece of Java's modern concurrency story. It complements virtual threads by binding the lifetime of child tasks to a scope, ensuring that no task outlives its parent and that cancellation, error propagation, and resource cleanup happen automatically.

The `StructuredTaskScope` API is built around three concepts: `fork` to start a child task on a virtual thread, `join` to wait for all children to complete (or be cancelled), and `get` to retrieve the result of a successful subtask. Two built-in policies cover the most common cases: `ShutdownOnFailure` cancels remaining children when any child fails, and `ShutdownOnSuccess` cancels remaining children when any child succeeds. For more complex cases, you can extend `StructuredTaskScope` with a custom `handleComplete` method.

Combined with `ScopedValue` for context propagation and virtual threads for cheap concurrency, structured concurrency allows you to write fan-out workloads in a simple, synchronous style that scales to millions of concurrent tasks. The call tree mirrors the concurrency tree, making the code easy to read, easy to debug, and easy to reason about.
