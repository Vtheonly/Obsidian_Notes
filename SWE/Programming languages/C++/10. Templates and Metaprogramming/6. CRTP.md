# CRTP

## Why This Matters

The **Curiously Reccurring Template Pattern** (CRTP) is C++'s answer to the question: *how do I get polymorphism without paying for virtual dispatch?*

Virtual functions are wonderful — they let you write code that works on a `Shape*` and does the right thing for `Circle`, `Square`, `Triangle` at runtime. But every virtual call costs a vtable indirection and (often) a cache miss, and every virtual class pays a per-object vptr. In hot loops, graphics engines, expression-template libraries, and signal-processing code, those costs add up.

CRTP achieves **static (compile-time) polymorphism**: the base class knows the derived class's type at compile time and can inline calls directly to the derived implementation — no vptr, no indirection, no cache miss. It is the technique behind `std::enable_shared_from_this`, `std::iterator` (deprecated but illustrative), Eigen's expression templates, many CRTP-based mixin libraries, and the **Barton-Nackman trick** for defining operators generically.

This note covers the canonical CRTP form, its use for static interfaces, the mixin pattern, the Barton-Nackman trick, comparison with virtual dispatch, the known pitfalls (object slicing, friend injection, derived-from-CRTP-base requirements), and the modern alternatives (`if constexpr`, concepts, deducing-this in C++23).

It builds on [[1. Function Templates]], [[2. Class Templates]], and [[5. Concepts (C++20)]].

## Background

### The pattern

```cpp
template <typename Derived>
struct Base {
    void interface() {
        static_cast<Derived*>(this)->implementation();
    }
};

struct Derived : Base<Derived> {
    void implementation() { std::cout << "Derived::implementation\n"; }
};
```

That's the whole pattern. The base class is a template parameterised on its own derived class; the derived class inherits from `Base<Derived>`, passing itself as the template argument. The base can then `static_cast<this)` to a `Derived*` and call the derived class's methods directly.

The name "curiously recurring" comes from the apparent circularity: `Derived` is defined in terms of `Base<Derived>`, which is defined in terms of `Derived`. The cycle is broken because `Base<Derived>` doesn't actually need the complete definition of `Derived` at the point it's instantiated — only at the point its member functions are *called*, by which time `Derived` is complete.

### History

The pattern was named by James Coplien in 1995, but it had been used since the early 1990s. The Barton-Nackman trick (John Barton and Lee Nackman, 1994) used CRTP to define operators (like `==`, `!=`, `<`) for a class hierarchy in a single base class, exploiting argument-dependent lookup (ADL). `std::enable_shared_from_this` (C++11) is the most widely-used CRTP example in the standard library.

## Main Content

### 1. Static polymorphism: the core use case

CRTP lets you write a base class that exposes an interface, where each call dispatches to the derived class at compile time.

```cpp
#include <iostream>

template <typename Derived>
struct Shape {
    double area() const {
        return static_cast<const Derived*>(this)->area_impl();
    }
    double perimeter() const {
        return static_cast<const Derived*>(this)->perimeter_impl();
    }
};

class Circle : public Shape<Circle> {
    double r_;
public:
    explicit Circle(double r) : r_(r) {}
    double area_impl()       const { return 3.14159265 * r_ * r_; }
    double perimeter_impl()  const { return 2 * 3.14159265 * r_; }
};

class Square : public Shape<Square> {
    double s_;
public:
    explicit Square(double s) : s_(s) {}
    double area_impl()       const { return s_ * s_; }
    double perimeter_impl()  const { return 4 * s_; }
};

int main() {
    Circle c{1.0};
    Square q{2.0};
    std::cout << c.area() << ' ' << q.area() << '\n';
}
```

`Shape<Circle>::area()` calls `Circle::area_impl()`. The compiler can inline this entirely — no vtable lookup, no indirect call. The cost is the same as if you had called `c.area_impl()` directly.

### 2. Comparison with virtual dispatch

| Property                     | Virtual functions            | CRTP                            |
| ---------------------------- | ---------------------------- | ------------------------------- |
| Dispatch time                | Runtime (vtable indirection) | Compile-time (direct call)      |
| Inlinability                 | Usually no (compiler can't see target) | Yes                  |
| Object size overhead         | +1 vptr per object           | None                            |
| Heterogeneous containers     | Yes (`vector<Shape*>`)       | No (types unrelated)            |
| Adding derived class         | Just inherit; no recompile of users | Must recompile users        |
| Runtime type discovery       | RTTI / `dynamic_cast` works  | Not directly                    |
| Code bloat                   | One set of vtable code       | One specialisation per derived  |

CRTP is the right tool when:

- You know all derived types at compile time.
- You need every cycle of performance (inner loops, ETLs, DSP).
- You don't need heterogeneous containers of base pointers.

Virtual functions are the right tool when:

- The set of derived types is open (plugins, scripts, runtime-loaded modules).
- You need heterogeneous containers.
- You need runtime type discovery.

Note that `Shape<Circle>` and `Shape<Square>` are **unrelated types** — they don't share a common base (unless you give them one, defeating the point of CRTP). This is the fundamental trade-off: you trade the ability to store heterogeneous types for the speed of direct dispatch.

### 3. The mixin pattern

CRTP is the natural basis for **mixins**: small classes that add a single piece of behaviour, composable by inheritance.

```cpp
template <typename Derived>
struct Counter {
    static inline int count = 0;
    Counter()    { ++count; }
    Counter(const Counter&) { ++count; }
    ~Counter()   { --count; }
    static int alive() { return count; }
};

template <typename Derived>
struct Named {
    std::string name;
    void describe() const {
        std::cout << "I am " << name
                  << " (derived: " << typeid(Derived).name() << ")\n";
    }
};

class Widget : public Counter<Widget>, public Named<Widget> {};

int main() {
    Widget w; w.name = "primary";
    std::cout << Widget::alive() << '\n';      // 1
    w.describe();
}
```

Each mixin is parameterised on the final derived type, so it can `static_cast<Derived*>(this)` to reach sibling members if needed.

### 4. Variadic mixin chains

Combining CRTP with variadic templates gives you a way to compose mixins without writing them out by hand:

```cpp
template <template <typename> class... Mixins>
struct Compose : Mixins<Compose<Mixins...>>... {};

using MyWidget = Compose<Counter, Named>;
```

Each mixin must be designed to take `Compose<...>` as its `Derived` parameter. This is the foundation of policy-based design (Alexandrescu's *Modern C++ Design*).

### 5. The Barton-Nackman trick

The Barton-Nackman trick uses CRTP + ADL to define operators generically. The pattern:

```cpp
template <typename Derived>
struct Equality {
    friend bool operator==(const Derived& a, const Derived& b) {
        return a.equal_to(b);
    }
    friend bool operator!=(const Derived& a, const Derived& b) {
        return !(a == b);
    }
};

class Rational : public Equality<Rational> {
    int num_, den_;
public:
    bool equal_to(const Rational& other) const {
        return num_ == other.num_ && den_ == other.den_;
    }
};

Rational r1{1, 2}, r2{1, 2}, r3{1, 3};
r1 == r2;     // true
r1 != r3;     // true
```

The key is the `friend` declaration: each instantiation of `Equality<Rational>` injects a *non-template* `operator==` into the surrounding namespace, found via ADL when called on `Rational` arguments. This predates C++11's explicit comparison-operator-concept idioms and is still used in many libraries.

The Barton-Nackman trick was originally a workaround for the absence of partial specialisation of function templates in early C++; today it survives because it produces clean, ADL-dispatched, inlinable operators.

### 6. `std::enable_shared_from_this`

The classic standard-library CRTP example. It allows an object managed by `std::shared_ptr` to hand out more `shared_ptr`s to itself, correctly participating in the control block.

```cpp
#include <memory>

class Node : public std::enable_shared_from_this<Node> {
public:
    std::shared_ptr<Node> get_self() {
        return shared_from_this();   // safe: shares the existing control block
    }
};

int main() {
    auto p = std::make_shared<Node>();
    auto q = p->get_self();
    // p and q share the same control block; refcount is 2, not 2 separate
    // blocks that would double-delete on destruction
}
```

The mechanism: `enable_shared_from_this<T>` holds a `weak_ptr<T>` member; the `shared_ptr` constructor recognises inheritance from `enable_shared_from_this` and stores a weak pointer back to the control block in that member. `shared_from_this()` then locks the weak pointer to produce a new `shared_ptr` sharing the original control block.

Calling `shared_from_this()` before the object is owned by a `shared_ptr` is undefined behaviour (the internal weak_ptr is empty). This is the most common pitfall.

### 7. CRTP for static interface checking

You can use CRTP to assert at compile time that the derived class implements required methods:

```cpp
template <typename Derived>
class Iterable {
public:
    void iterate() {
        // Will fail to compile if Derived doesn't have begin()/end()
        auto it = static_cast<Derived*>(this)->begin();
        auto end = static_cast<Derived*>(this)->end();
        for (; it != end; ++it) process(*it);
    }
private:
    void process(const auto&) {}
};

// In C++20, prefer to use a concept for this — see Concepts note.
```

In C++20 this use case is largely subsumed by [[5. Concepts (C++20)]] — a `template <Iterable T>` declaration gives the same guarantee with a much better error message. CRTP survives for cases where you also want to *share* implementation, not just check for an interface.

### 8. Simulating virtual dispatch with a hybrid

A common production pattern: provide a virtual interface *and* a CRTP optimisation path.

```cpp
class Shape {
public:
    virtual double area() const = 0;
    virtual ~Shape() = default;
};

template <typename Derived>
class ShapeCRTP : public Shape {
public:
    double area() const final {
        return static_cast<const Derived*>(this)->area_impl();
    }
};

class Circle : public ShapeCRTP<Circle> {
    double r_;
public:
    explicit Circle(double r) : r_(r) {}
    double area_impl() const { return 3.14159265 * r_ * r_; }
};
```

The `final` keyword tells the compiler that no further override exists, which often allows it to devirtualise the call. Combined with CRTP's static dispatch into `area_impl`, you get the best of both worlds: callers using `Shape*` get virtual dispatch (and devirtualisation where possible); callers using `Circle` directly get inline-able calls.

### 9. CRTP with `if constexpr` and concepts

Modern CRTP can replace the brittle `static_cast<Derived*>(this)` calls with `if constexpr` or concepts:

```cpp
template <typename Derived>
class Base {
public:
    void do_work() {
        if constexpr (requires { static_cast<Derived*>(this)->fast_path(); }) {
            static_cast<Derived*>(this)->fast_path();
        } else {
            slow_path();
        }
    }
private:
    void slow_path() { /* … */ }
};
```

A derived class can opt in to the fast path by simply defining `fast_path()`. The `requires` expression (see [[5. Concepts (C++20)]]) makes the check explicit and readable.

### 10. The deducing-this alternative (C++23)

C++23 introduced **explicit object member functions** (a.k.a. "deducing this"), which provide a cleaner syntax for some CRTP uses:

```cpp
struct Base {
    template <typename Self>
    void interface(this Self&& self) {
        std::forward<Self>(self).implementation();
    }
};

struct Derived : Base {
    void implementation() { std::cout << "Derived\n"; }
};

Derived d;
d.interface();      // Self deduced as Derived&; calls implementation directly
```

Deducing-this is not a full replacement for CRTP (it doesn't handle the mixin case as cleanly, and it doesn't inject `friend` operators the way Barton-Nackman does), but for many "static interface" use cases it's the modern idiom.

### 11. Pitfall: object slicing and `static_cast` safety

CRTP relies on `static_cast<Derived*>(this)`. This cast is safe **only if** the `this` pointer really points to a `Derived` (or something derived from `Derived`). If someone misuses the base class — for example by instantiating `Base<Derived>` standalone, or by inheriting `Base<Other>` from `Derived` — the cast is undefined behaviour.

A common defensive idiom is to make the base class's constructors `protected`, so users can't accidentally instantiate it directly:

```cpp
template <typename Derived>
class Base {
protected:
    Base() = default;       // only Derived can construct
public:
    void interface() { static_cast<Derived*>(this)->implementation(); }
};
```

A more thorough check uses `static_assert(std::is_base_of_v<Base<Derived>, Derived>)` inside the constructor body. C++23's deducing-this avoids the issue entirely for the use cases it covers.

### 12. Pitfall: incomplete type in base-class member functions

When `Base<Derived>` is instantiated, `Derived` is *incomplete* (you're still inside its class body). This is fine for declaring member functions — they're not instantiated until called. But it means:

- You can't use `sizeof(Derived)` inside the base class body.
- You can't have a data member of type `Derived` inside the base.
- You can have a `Derived*` or `Derived&` member, but you must be careful with the constructor.

### 13. Pitfall: friend injection and the Barton-Nackman trick

The `friend` declarations in the Barton-Nackman trick inject one non-template function *per instantiation* of the base class. Two unrelated types that both inherit `Equality<TheirType>` get *different* `operator==` functions, found only via ADL. This is what makes the trick work — but it also means `operator==` is *not* a template, which has subtle implications for overload resolution.

A side effect: if you call `operator==` between two *different* CRTP-derived types (e.g., `Rational{1,2} == Complex{1,2}`), the lookup will fail cleanly — there's no implicit conversion path. This is usually what you want.

## Code Examples

### Example A: a CRTP-based counter mixin

```cpp
#include <iostream>

template <typename Derived>
class Counter {
    static inline std::size_t n_ = 0;
public:
    Counter() noexcept         { ++n_; }
    Counter(const Counter&) noexcept { ++n_; }
    Counter(Counter&&) noexcept { ++n_; }
    Counter& operator=(const Counter&) = default;
    Counter& operator=(Counter&&)      = default;
    ~Counter()                 { --n_; }
    static std::size_t alive() { return n_; }
};

class Session : public Counter<Session> {};

int main() {
    Session a, b;
    {
        Session c;
        std::cout << Session::alive() << '\n';    // 3
    }
    std::cout << Session::alive() << '\n';        // 2
}
```

### Example B: expression templates for lazy arithmetic

```cpp
#include <vector>
#include <algorithm>

template <typename E>
struct VecExpr {
    double operator[](std::size_t i) const {
        return static_cast<const E&>(*this)[i];
    }
    std::size_t size() const {
        return static_cast<const E&>(*this).size();
    }
};

class Vec : public VecExpr<Vec> {
    std::vector<double> data_;
public:
    explicit Vec(std::vector<double> v) : data_(std::move(v)) {}
    double operator[](std::size_t i) const { return data_[i]; }
    std::size_t size() const { return data_.size(); }
    template <typename E> Vec& operator+=(const VecExpr<E>& other) {
        for (std::size_t i = 0; i < size(); ++i) data_[i] += other[i];
        return *this;
    }
};

template <typename L, typename R>
class VecSum : public VecExpr<VecSum<L, R>> {
    const L& l_; const R& r_;
public:
    VecSum(const L& l, const R& r) : l_(l), r_(r) {}
    double operator[](std::size_t i) const { return l_[i] + r_[i]; }
    std::size_t size() const { return l_.size(); }
};

template <typename L, typename R>
VecSum<L, R> operator+(const VecExpr<L>& l, const VecExpr<R>& r) {
    return VecSum<L, R>(static_cast<const L&>(l), static_cast<const R&>(r));
}

// Usage: Vec a, b, c; a + b + c computes a single fused loop with no temporaries.
```

Expression templates (as in Eigen) use CRTP to delay evaluation until assignment, fusing multiple operations into a single loop. The cost: aggressive code bloat (each unique expression type is a separate class) and complex error messages.

### Example C: a CRTP base that injects an `operator<<`

```cpp
#include <iostream>

template <typename Derived>
class Printable {
    friend std::ostream& operator<<(std::ostream& os, const Derived& d) {
        d.print(os);
        return os;
    }
};

class Point : public Printable<Point> {
    int x_, y_;
public:
    Point(int x, int y) : x_(x), y_(y) {}
    void print(std::ostream& os) const { os << '(' << x_ << ',' << y_ << ')'; }
};

int main() { std::cout << Point{3, 4} << '\n'; }
```

## Common Pitfalls

- **Calling `static_cast<Derived*>(this)` when `this` doesn't actually point to a `Derived`.** UB. Make base constructors protected and consider a `static_assert(std::is_base_of_v<…>)`.
- **Inheriting from the wrong instantiation.** `class Wrong : public Base<Other>` is a typo that compiles silently and produces a `static_cast<Other*>` on a `Wrong*` — UB. Naming conventions help (`class MyType : public Base<MyType>`).
- **Forgetting to define the implementation in `Derived`.** Causes a compile error inside the base, often with a confusing "no member named 'implementation'" message pointing at the base, not the derived class.
- **Constructing the base before `Derived` is complete.** You can't call `Derived` methods from the base's constructor — the vptr (in the virtual case) and the type itself (in CRTP) aren't ready.
- **Forgetting that `Base<Derived1>` and `Base<Derived2>` are unrelated types.** You can't put them in a single container without a non-template common base.
- **Mixing CRTP with virtual dispatch naively.** A `Base<Derived>`-style class without a `virtual` destructor can't be deleted through a base pointer safely. If you need polymorphic deletion, add a `virtual ~Base() = default`.
- **`enable_shared_from_this` misuse.** Calling `shared_from_this()` before the object is owned by a `shared_ptr` is UB. Same for the constructor.
- **Friend-injected operators and ADL.** The Barton-Nackman trick requires unqualified calls (`a == b`) for ADL to find the operator. A qualified `::operator==(a, b)` won't find it.
- **CRTP with multiple inheritance diamond issues.** If `Derived : Base<Derived>, OtherBase<Derived>`, both bases reference the same `Derived` — usually fine, but multiple-base-cast ambiguities can arise.
- **Code bloat from many derived types.** Each `Derived` produces a fresh instantiation of every base method. For tiny methods the compiler usually collapses them; for large methods the binary can grow significantly.

## Tips and Tricks

- Use CRTP when you need **static polymorphism** with shared implementation, not just an interface check (for that, use [[5. Concepts (C++20)] instead]).
- Make the base's constructors **protected** to prevent misuse.
- Use **`static_assert(std::is_base_of_v<Base<Derived>, Derived>)`** in the base's constructor for a defensive check.
- Combine CRTP with **`final` virtual functions** for hybrid dispatch: virtual on the boundary, CRTP-style static dispatch inside.
- Use the **Barton-Nackman trick** for `==`, `!=`, `<`, `<=`, `>`, `>=` on value types — it's far less repetitive than writing each by hand.
- For **expression templates**, keep the expression class hierarchy shallow to limit code bloat. Use `if constexpr` to short-circuit when the expression is trivial.
- For **mixins**, design each mixin to be self-contained (no cross-mixin dependencies) so they compose cleanly.
- In C++20+, prefer **concepts + `if constexpr`** to express "if Derived has X, use it" instead of `static_cast` + always-callable interface methods.
- In C++23+, prefer **deducing-this** for new "static interface" code; it's cleaner and safer than CRTP for that pattern.
- Always **name the derived class after the CRTP base in inheritance lists**: `class Widget : public Counter<Widget>` — the redundancy is a feature, making typos visible.
- Document each CRTP base with the **list of methods the derived class must implement**. The compiler error is unhelpful without it.
- Avoid CRTP for **plugin architectures** — you'd have to recompile every plugin when the base changes.
