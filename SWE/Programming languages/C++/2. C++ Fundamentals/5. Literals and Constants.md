## Why This Matters

A **literal** is a fixed value written directly into your source code: `42`, `3.14f`, `"hello"`, `true`, `nullptr`. Every variable, every constant, every compile-time computation starts life as a literal somewhere. Knowing the full literal vocabulary of C++ lets you write code that is concise, type-correct, and self-documenting: `0xFF` instead of `255`, `0b1010'1100` instead of `172`, `3.14e10f` instead of a comment-laden `31400000000.0f`, `R"(C:\Users\Me)"` instead of a forest of backslashes.

This note also covers the three "const-ness" keywords — `const`, `constexpr`, `constinit` — which together let you express *exactly* how immutable a value is and when its value is computed. Used well, they let the compiler optimize aggressively and catch large classes of bugs at compile time. Used poorly (or not at all), they leave performance on the table and let bugs slip through to production.

## Background

### What Counts as a Literal?

A literal is a *token* in the C++ grammar. The lexer recognizes it as a value of a specific type and stores it directly in the compiled binary. The fundamental categories are:

- **Integer literals**: `42`, `0xFF`, `0b1010`, `0755`.
- **Floating-point literals**: `3.14`, `6.022e23`, `1.0f`.
- **Character literals**: `'A'`, `'\n'`, `u8'×'`, `U''`.
- **String literals**: `"hello"`, `u8"utf-8"`, `R"(raw)"`.
- **Boolean literals**: `true`, `false`.
- **Pointer literal**: `nullptr`.
- **User-defined literals**: `90.0_deg`, `1h`, `"foo"s`.

### Why This Matters for Type Safety

Every literal has a *type* chosen by the compiler based on its syntax. `42` is an `int`; `42u` is `unsigned int`; `42ULL` is `unsigned long long`; `42.0` is `double`; `42.0f` is `float`. The type determines how the literal participates in expressions: `0xFFFFFFFF` may overflow an `int` (UB on signed overflow) but be a perfectly valid `unsigned int`. Choosing the right suffix is not pedantry — it is correctness.

## Main Content

### 1. Integer Literals

#### Bases (Radices)

| Prefix | Base | Example | Decimal value |
| --- | --- | --- | --- |
| (none) | 10 (decimal) | `42` | 42 |
| `0` | 8 (octal) | `052` | 42 |
| `0x` or `0X` | 16 (hexadecimal) | `0x2A` | 42 |
| `0b` or `0B` (C++14) | 2 (binary) | `0b101010` | 42 |

> [!warning] The Octal Trap
> A leading `0` makes a literal octal. `int x = 010;` is `8`, not `10`. This is a decades-old source of bugs. Modern style guides forbid leading zeros on decimal literals. The compiler flag `-Werror=octal` will catch this.

#### Digit Separators (C++14)

The single quote `'` separates digits for readability — it has no semantic effect:

```cpp
int million      = 1'000'000;
long big_number  = 123'456'789'012;
int hex_color    = 0xFF'FF'FF;
int bitmask      = 0b1111'0000'1100'0011;
```

#### Type Suffixes

The compiler picks the smallest type that can hold the value, respecting the suffix:

| Suffix | Type (chosen from) |
| --- | --- |
| (none) | `int`, `long`, `long long` (first that fits) |
| `u` or `U` | `unsigned int`, `unsigned long`, `unsigned long long` |
| `l` or `L` | `long`, `long long` |
| `ul`, `lu`, etc. | `unsigned long`, `unsigned long long` |
| `ll` or `LL` | `long long` |
| `ull`, `llu`, etc. | `unsigned long long` |

```cpp
auto a = 42;          // int
auto b = 42u;         // unsigned int
auto c = 42l;         // long
auto d = 42ul;        // unsigned long
auto e = 42ll;        // long long
auto f = 42ull;       // unsigned long long
```

> [!tip] Always Suffix Large Literals
> `auto x = 5'000'000'000;` overflows `int` and is UB on most platforms. Write `5'000'000'000LL` to make the intent and type unambiguous.

### 2. Floating-Point Literals

| Form | Example | Type |
| --- | --- | --- |
| Default | `3.14`, `6.022e23`, `.5`, `1.` | `double` |
| `f` or `F` suffix | `3.14f`, `1.0F` | `float` |
| `l` or `L` suffix | `3.14L` | `long double` |

```cpp
auto pi = 3.14;          // double — NOT float!
auto pi_f = 3.14f;       // float
auto pi_ld = 3.14L;      // long double
```

> [!warning] `3.14` Is `double`, Not `float`
> The default floating-point literal is `double`. Writing `float pi = 3.14;` triggers a *narrowing* conversion from `double` to `float` (which can lose precision) — and brace-init `float pi{3.14};` is a compile error. Always write `3.14f` when you mean a float.

#### Hexadecimal Floating-Point (C++17)

```cpp
double d = 0x1.8p1;     // = (1 + 0.5) * 2^1 = 3.0
```

The format is `0x` *mantissa* `p` *exponent*, where the exponent is base-2. Useful for exact bit patterns.

### 3. Character Literals

| Form | Type | Example | Notes |
| --- | --- | --- | --- |
| `'c'` | `char` | `'A'`, `'\n'` | Narrow character. |
| `u8'c'` (C++17) | `char8_t` (C++20) | `u8'×'` | UTF-8. |
| `u'c'` (C++11) | `char16_t` | `u'α'` | UTF-16. |
| `U'c'` (C++11) | `char32_t` | `U''` | UTF-32. |
| `L'c'` | `wchar_t` | `L'β'` | Platform-defined width. |

#### Escape Sequences

| Sequence | Meaning |
| --- | --- |
| `\n` | newline (LF) |
| `\r` | carriage return (CR) |
| `\t` | horizontal tab |
| `\v` | vertical tab |
| `\f` | form feed |
| `\a` | alert (bell) |
| `\b` | backspace |
| `\0` | null character (NUL) |
| `\\` | backslash |
| `\'` | single quote |
| `\"` | double quote |
| `\?` | question mark (disables trigraphs) |
| `\xNN` | hexadecimal value (e.g., `\x41` = 'A') |
| `\NNN` | octal value (e.g., `\101` = 'A') |
| `\uNNNN` | universal character name (4 hex digits, UTF-16) |
| `\UNNNNNNNN` | universal character name (8 hex digits, UTF-32) |

### 4. String Literals

A double-quoted sequence of characters is a **string literal**. Its type is "array of `const char`" with length = visible characters + 1 (for the null terminator).

```cpp
auto s = "hello";       // type: const char[6]  (5 chars + '\0')
sizeof("hello");        // 6
```

#### Encodings

| Prefix | Type | Example |
| --- | --- | --- |
| (none) | `const char[]` | `"hello"` |
| `u8` (C++17) | `const char[]` (UTF-8) | `u8"héllo"` |
| `u` (C++11) | `const char16_t[]` | `u"hello"` |
| `U` (C++11) | `const char32_t[]` | `U"hello"` |
| `L` | `const wchar_t[]` | `L"hello"` |

#### Raw String Literals (C++11)

`R"(...)"` lets you write strings without escaping backslashes or quotes:

```cpp
std::string path  = R"(C:\Users\Me\Documents\file.txt)";    // no \\ needed
std::string regex = R"(\d{3}-\d{4})";                       // no \\d needed
std::string json  = R"({"key": "value", "n": 42})";         // no \" needed
```

The `*` in `R"*(...)*"` is a custom delimiter that lets you embed `)"` literally:

```cpp
std::string s = R"x(This string contains )" and even )" again)x";
```

#### `std::string` Literals (C++14)

The `s` suffix produces a `std::string` (not a `const char*`):

```cpp
using namespace std::string_literals;   // required to enable _s

auto s1 = "hello";        // const char*  — C-style string
auto s2 = "hello"s;       // std::string  — has .size(), concatenation, etc.

auto combined = "Hello, "s + "world!"s;   // works because both are std::string
```

> [!tip] Always Use `"..."s` in New Code
> A bare string literal is a `const char*` — a pointer to a static array. Concatenating `"a" + "b"` is *pointer arithmetic*, not string concatenation, and is UB. The `s` suffix gives you a real `std::string` with all the operators you expect. See [[3. Strings and Character Data]].

#### String Literal Lifetimes

String literals live for the entire duration of the program — they are stored in a read-only data section of the binary. Returning a `const char*` to a string literal from a function is safe; returning a `const char*` to a local `char[]` is not.

### 5. Boolean Literals

`true` and `false` are the only two boolean literals. They have type `bool` and convert to `1` and `0` respectively in integer contexts.

```cpp
bool ready = true;
int  count = false;   // count == 0
```

### 6. The Pointer Literal: `nullptr`

`nullptr` (C++11) is a literal of type `std::nullptr_t` that represents a null pointer of *any* pointer type. It replaces the legacy `NULL` macro and the `0` integer literal.

```cpp
int*    p1 = nullptr;
void*   p2 = nullptr;
void(*fp)() = nullptr;
```

> [!danger] Never Use `NULL` in C++
> `NULL` is a macro defined as `0` (or `((void*)0)` in C). In C++ this causes problems with overload resolution:
>
> ```cpp
> void f(int);
> void f(char*);
> f(NULL);   // Calls f(int)! Surprising and bug-prone.
> f(nullptr); // Calls f(char*) — correct.
> ```
>
> Always use `nullptr`. See [[6. Pointers and References]].

### 7. User-Defined Literals (C++11)

C++ lets you define your own literal suffixes by overloading `operator""`:

```cpp
constexpr long double operator"" _deg(long double deg) {
    return deg * 3.14159265358979L / 180.0L;
}

constexpr long double operator"" _rad(long double rad) {
    return rad;
}

auto right_angle = 90.0_deg;   // type: long double, value: π/2
auto straight    = 3.14159265358979_rad;
```

#### Standard Library User-Defined Literals

The standard library provides several (note: these require `using namespace std::literals` or the specific `using namespace`):

| Suffix | Header | Produces |
| --- | --- | --- |
| `s` | `<string>` | `std::string` |
| `h`, `min`, `s`, `ms`, `us`, `ns` | `<chrono>` | `std::chrono::duration` |
| `complex` suffixes `i`, `if`, `il` | `<complex>` | `std::complex` |

```cpp
using namespace std::chrono_literals;
auto one_hour = 1h;          // std::chrono::hours
auto half_sec = 500ms;       // std::chrono::milliseconds
auto wait_for = 1h + 30min;  // 90 minutes
```

> [!warning] Reserve the Underscore
> Only user-defined literals with a leading underscore (`_deg`, `_km`) are reserved for you. Suffixes without an underscore (`deg`, `km`) are reserved for the standard library — using them is undefined behavior.

### 8. Constants: `const`, `constexpr`, `constinit`

These three keywords express different shades of immutability.

#### `const` — Runtime Immutability

```cpp
const int max_users = read_config("max_users");  // value computed at runtime
// max_users = 10;  // ERROR: const
```

`const` promises the value will not change after initialization, but the value itself can be computed at runtime. Used widely for function parameters and local variables.

#### `constexpr` — Compile-Time Evaluability

```cpp
constexpr int square(int x) { return x * x; }
constexpr int s = square(5);   // evaluated at compile time: s == 25

int runtime_input;
std::cin >> runtime_input;
int r = square(runtime_input); // evaluated at runtime — fine, just not constexpr
```

`constexpr` (variables) means "this value is computable at compile time." `constexpr` (functions) means "this function *may* be evaluated at compile time when called with constant expressions." Since C++14, `constexpr` functions may contain loops, local variables, and `if`; since C++20 they may even contain `try`/`catch` and `dynamic_cast`.

> [!tip] Use `constexpr` Aggressively
> Push computation to compile time. Compile-time computation is *free* at runtime, can be verified with `static_assert`, and lets the compiler fold the result into surrounding code. `constexpr` is one of the biggest wins of modern C++.

#### `consteval` (C++20) — Forced Compile-Time

```cpp
consteval int compile_time_only(int x) { return x * 2; }
int v = compile_time_only(5);     // OK — must be compile-time

int y = std::cin.get();
int z = compile_time_only(y);     // ERROR — y is not a constant expression
```

`consteval` (the "immediate function") *must* be evaluated at compile time; calling it with runtime values is a hard error.

#### `constinit` (C++20) — Compile-Time Initialization, Runtime Mutability

```cpp
constinit int counter = compute_initial();   // initialized at compile time
// counter can be modified at runtime
counter = 5;
```

`constinit` solves the **static initialization order fiasco**: globals declared `constinit` are guaranteed to be initialized before any other code runs, but they can still be mutated. This is invaluable for global configuration flags.

#### Comparison Table

| Keyword | When initialized? | Mutable after init? | Use case |
| --- | --- | --- | --- |
| `const` | Run-time | No | Runtime-immutable values, function parameters. |
| `constexpr` (var) | Compile-time | No | Compile-time constants (`pi`, array sizes, template args). |
| `constexpr` (fn) | Either | n/a | Functions usable in constant expressions. |
| `consteval` (fn) | Compile-time only | n/a | Functions that *must* run at compile time (e.g., reflection). |
| `constinit` (var) | Compile-time | **Yes** | Globals that need safe static init but can be mutated. |

## Common Pitfalls

1. **`int x = 010;`** — that's `8`, not `10`. Octal literal. Always use `-Werror=octal`.
2. **`float pi = 3.14;`** — silent narrowing. Use `3.14f` or brace-init to catch it.
3. **Forgetting `LL` on large integer literals** — `5'000'000'000` overflows `int` (UB on signed). Use `5'000'000'000LL`.
4. **Treating `"hello"` as a `std::string`** — it's a `const char*`. `"a" + "b"` is pointer arithmetic, UB. Use `"a"s + "b"s`.
5. **Modifying a string literal** — `char* s = "hello"; s[0] = 'H';` is UB (string literals live in read-only memory). Always use `char s[] = "hello";` (mutable copy) or `std::string`.
6. **Concatenating adjacent string literals with different encodings** — `"hello" u8"world"` is ill-formed. All concatenated literals must have the same encoding prefix.
7. **Using `NULL` instead of `nullptr`** — overload resolution surprise.
8. **Trigraphs (removed in C++17)** — `??=` used to mean `#`. Modern compilers disable them by default; do not rely on them.
9. **Universal character names in identifiers vs. strings** — `"\u00E9"` is fine in a string literal; `\u00E9` *inside an identifier* must be a valid identifier character per Unicode rules.
10. **Confusing `const` and `constexpr`** — `const` does not imply compile-time. Only `constexpr` does. Use `constexpr` for true compile-time constants (array sizes, template arguments).
11. **`consteval` called with runtime values** — hard compile error. Either ensure all call sites use constant expressions, or fall back to `constexpr`.
12. **Forgetting `using namespace std::literals`** — `_s`, `_h`, etc. won't compile without the using directive.

## Tips and Tricks

- **Use `0b` + digit separators for bitmasks**: `0b1111'0000'1100'0011` is far more readable than `0xF0C3` or `61635`.
- **Suffix every large integer literal** (`ULL`, `LL`) to make its type unambiguous and avoid overflow UB.
- **Prefer `"..."s` over `"..."` in modern code** — gives you a real `std::string` with operators you expect.
- **`R"(...)"` raw strings are perfect for regex, file paths, JSON, SQL** — anywhere backslashes are common.
- **`constexpr` everywhere** — declare every function you can as `constexpr`. It costs nothing and unlocks compile-time use.
- **`static_assert` your constants**: `static_assert(buffer_size > 0);` catches configuration mistakes before runtime.
- **`consteval` for security-critical compile-time checks** — e.g., `consteval bool is_valid_id(int) { ... }` cannot be bypassed by runtime input.
- **Hex floats for exact bit patterns** — `0x1.0p0` is exactly 1.0; useful for IEEE 754 tests.
- **Universal character names in identifiers** let you write `int naïve_count;` (legal since C++11). It's cute but controversial; most style guides forbid non-ASCII identifiers for portability.
- **User-defined literals for type safety**: `2_km + 500_m` can be made to compile only when units match, preventing the Mars Climate Orbiter disaster class of bugs.

## Appendix: Constness Decision Tree

When you find yourself wondering "should this be `const`? `constexpr`? `consteval`? `constinit`? nothing?" walk this tree:

1. **Is it a function?**
   - Yes, and I want it usable at compile time → `constexpr`.
   - Yes, and it *must* be compile-time only → `consteval` (C++20).
   - Yes, and I want to forbid overrides → add `final`.
   - Otherwise → no special keyword.
2. **Is it a variable?**
   - Yes, and the value is known at compile time and never changes → `constexpr`.
   - Yes, and the value is computed at runtime but never changes after init → `const`.
   - Yes, and it's a global that must be initialized at compile time but can be mutated at runtime → `constinit` (C++20).
   - Yes, and it's a function parameter that should not be modified inside the function → `const` (e.g., `void f(const std::string& s)`).
   - Otherwise → no special keyword.

> [!tip] Const-Correctness Is Viral — and That's Good
> Once you start making things `const`, you'll find yourself forced to make *other* things `const` (a `const` member function can only call other `const` member functions). This "virality" feels annoying at first but is exactly what makes const-correct codebases so robust. Start at the leaves (leaf functions, simple variables) and work upward.
