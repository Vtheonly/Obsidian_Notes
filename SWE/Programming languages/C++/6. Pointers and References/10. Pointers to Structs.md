# Pointers to Structs

## Why This Matters

Once you combine two of C++'s most fundamental features — structs (aggregate types) and pointers (indirection) — you unlock the entire world of pointer-based data structures: linked lists, trees, graphs, hash-map buckets, polymorphic object hierarchies, and every container ever written in C. The single syntactic tool that makes this work is the **arrow operator `->`**, which dereferences a struct pointer and accesses a member in one stroke.

This note covers the arrow operator, its relationship to `(*p).member`, the linked-list node pattern (the canonical example), memory ownership concerns that arise whenever you have a pointer to a struct, and the modern C++ alternative: smart pointers.

## Background

C inherited the `struct` keyword from BCPL and the pointer concept from BCPL and ALGOL. Combining them — a struct containing a pointer to another struct of the same type — gave C programmers recursive data structures with a natural syntax. C++ preserved this verbatim. The arrow operator `->` was originally defined as syntactic sugar for `(*p).member`, and it remains so in C++.

C++ adds classes with private members, virtual functions (which add a hidden vtable pointer to every polymorphic object), constructors and destructors (which complicate the lifetime of struct pointers), and smart pointers (which automate the lifetime). But the fundamental pattern is the same: a struct pointer points to a struct, and you access members through `->`.

## Main Content

### 1. The Arrow Operator `->`

```cpp
struct Point {
    double x, y;
    void print() const;
};

Point p{1.0, 2.0};
Point* ptr = &p;

// Two equivalent ways to access members:
std::cout << (*ptr).x << '\n';     // explicit dereference, then dot
std::cout << ptr->x << '\n';       // arrow operator — preferred

(*ptr).print();                    // OK but ugly
ptr->print();                      // idiomatic
```

The arrow operator `->` is exactly `(*p).member` in one operator. It exists because `(*p).member` requires parentheses (the postfix `.` binds tighter than the prefix `*`), which makes the syntax noisy and error-prone. The arrow is universally preferred for pointer-to-struct access.

### 2. The `->` Definition

The C++ standard defines `p->member` as a shorthand for `(*p).member`. They are exactly equivalent in all contexts. Use `->` always when accessing a member through a pointer.

### 3. The Linked-List Node Pattern

The canonical application of pointers to structs is the linked list. Each node is a struct containing data and a pointer to the next node:

```cpp
struct Node {
    int   value;
    Node* next;     // pointer to next Node, or nullptr at end
};

int main() {
    // Build a small list: 1 -> 2 -> 3 -> nullptr
    Node* head = new Node{1, nullptr};
    head->next = new Node{2, nullptr};
    head->next->next = new Node{3, nullptr};

    // Traverse the list:
    for (Node* p = head; p != nullptr; p = p->next) {
        std::cout << p->value << ' ';
    }
    std::cout << '\n';

    // Free the list:
    Node* p = head;
    while (p != nullptr) {
        Node* next = p->next;
        delete p;
        p = next;
    }
}
```

#### Linked-List Node Diagram

```mermaid
flowchart LR
    Head["head (Node*)"] --> N1
    N1["Node\nvalue=1\nnext →"] --> N2
    N2["Node\nvalue=2\nnext →"] --> N3
    N3["Node\nvalue=3\nnext →"] -> NULL["nullptr"]
```

Each node's `next` field points to the next node; the last node's `next` is `nullptr`, marking the end. Traversal is a simple loop advancing `p = p->next` until `p` is null.

### 4. Why Linked Lists Are Usually Wrong in Modern C++

Despite being the textbook example, linked lists are usually the wrong data structure in modern C++. They:
- Defeat the CPU cache (each node is allocated separately; traversing the list produces a cache miss per node).
- Allocate per node (slow, fragmenting).
- Store two pointers of overhead per element (16 bytes on x86-64).
- Are harder to make thread-safe than contiguous storage.

`std::vector<T>` is almost always faster for the same workload due to cache locality and bulk allocation. Linked lists remain useful when:
- You need O(1) insertion or removal in the middle, and you already have an iterator to the position.
- The elements are very large (so copying is expensive) and you cannot use `std::vector<std::unique_ptr<T>>`.
- You are implementing a queue with concurrent producers and consumers (where `std::deque` may not suffice).

For most code, prefer `std::vector<T>`. See Chapter 11 (STL Deep Dive) for more.

### 5. Pointer to Struct as Function Parameter

```cpp
struct BigData { int payload[1024]; };

// By value — copies 4 KB on every call (slow):
void process_copy(BigData d);

// By const reference — no copy, read-only (preferred):
void process_cref(const BigData& d);

// By const pointer — no copy, read-only, allows nullptr:
void process_cptr(const BigData* d);

// By non-const pointer — no copy, can modify, allows nullptr:
void process_ptr(BigData* d);
```

The reference form is preferred for read-only access; the pointer form is preferred when null is a legitimate input. For struct parameters larger than two words, never pass by value (unless you intend to take a sink copy).

### 6. Pointer to Struct Returned from a Function

```cpp
struct Widget {
    int value;
};

Widget* make_widget(int v) {
    return new Widget{v};        // heap-allocated — caller must delete
}

std::unique_ptr<Widget> make_widget_modern(int v) {
    return std::make_unique<Widget>(Widget{v});   // RAII — caller does not delete
}

int main() {
    Widget* w = make_widget(42);
    std::cout << w->value << '\n';
    delete w;                    // easy to forget

    auto w2 = make_widget_modern(42);
    std::cout << w2->value << '\n';
    // no delete needed
}
```

Returning a raw `Widget*` from a factory function transfers ownership — the caller is responsible for `delete`. Returning `std::unique_ptr<Widget>` makes ownership explicit and automatic.

### 7. The Arrow Operator on Smart Pointers

`std::unique_ptr<T>` and `std::shared_ptr<T>` overload `operator->` so you can use the same syntax as a raw pointer:

```cpp
auto w = std::make_unique<Widget>(Widget{42});
std::cout << w->value << '\n';     // works — calls operator-> on unique_ptr
w->value = 100;                    // works
```

The smart pointer's `operator->` returns the inner raw pointer, and then the language applies the arrow again to access the member. (Technically `operator->` is a "chaining" operator: it is applied repeatedly until a raw pointer is reached.)

The same applies to `operator*`:

```cpp
Widget& ref = *w;                  // dereferences the unique_ptr
```

### 8. Memory Ownership Concerns

The single most important question when you see a `T*` in C++ code is: **who owns this memory?** The answer determines who is responsible for `delete`-ing it, and getting it wrong produces leaks or double-frees.

| Pointer kind                            | Who owns the memory?            | When is it freed?                       |
|-----------------------------------------|---------------------------------|-----------------------------------------|
| Raw `T*` from `new`                     | Caller (must `delete`)          | When the caller deletes                 |
| Raw `T*` from `new[]`                   | Caller (must `delete[]`)        | When the caller deletes                 |
| `std::unique_ptr<T>`                    | The unique_ptr                  | When the unique_ptr goes out of scope   |
| `std::shared_ptr<T>`                    | The shared_ptr group            | When the last shared_ptr dies           |
| `T*` from `std::vector::data()`         | The vector                      | When the vector is destroyed            |
| `T*` from `&local_variable`             | The enclosing scope             | When the scope exits                    |
| `T*` parameter to a function            | The caller (function borrows)   | When the caller decides                 |

The modern C++ way to make ownership clear:
- Use `std::unique_ptr<T>` and `std::shared_ptr<T>` for owned heap objects.
- Use raw `T*` and `T&` only for non-owning borrows.
- Use `gsl::owner<T*>` (GSL) to mark a raw owning pointer where a smart pointer cannot be used.
- Document in the API whether a returned `T*` is owned or borrowed.

### 9. Linked List with Smart Pointers

A modern linked list uses `std::unique_ptr<Node>` for the next pointer, expressing ownership explicitly:

```cpp
#include <memory>
#include <iostream>

struct Node {
    int value;
    std::unique_ptr<Node> next;
};

int main() {
    auto head = std::make_unique<Node>(Node{1, nullptr});
    head->next = std::make_unique<Node>(Node{2, nullptr});
    head->next->next = std::make_unique<Node>(Node{3, nullptr});

    for (Node* p = head.get(); p != nullptr; p = p->next.get()) {
        std::cout << p->value << ' ';
    }
    std::cout << '\n';
    // No deletes needed — destructors cascade automatically.
}
```

When `head` goes out of scope, its destructor runs, which destroys `next`, whose destructor runs, which destroys its `next`, and so on. The whole list is freed in one cascade.

> [!warning] Recursive Destruction
> For very long lists (10,000+ nodes), recursive destructor calls may overflow the stack. Use iterative cleanup or an iterative container like `std::vector` if the list can be that long.

### 10. Pointer to Polymorphic Struct (Class)

When the struct has virtual functions, accessing it through a pointer to its base class enables polymorphism:

```cpp
#include <memory>
#include <iostream>

struct Shape {
    virtual ~Shape() = default;
    virtual double area() const = 0;
};

struct Circle : Shape {
    double r;
    explicit Circle(double r) : r(r) {}
    double area() const override { return 3.14159 * r * r; }
};

struct Square : Shape {
    double s;
    explicit Square(double s) : s(s) {}
    double area() const override { return s * s; }
};

int main() {
    std::unique_ptr<Shape> s = std::make_unique<Circle>(2.0);
    std::cout << s->area() << '\n';   // 12.5664 — calls Circle::area

    s = std::make_unique<Square>(3.0);
    std::cout << s->area() << '\n';   // 9 — calls Square::area
}
```

The `virtual` keyword adds a hidden vtable pointer to each `Shape` instance; calling `s->area()` does an indirect call through the vtable. This is how runtime polymorphism works in C++ — and it requires a pointer or reference to the base class. See Chapter 9 for the full story.

### 11. Pointer to Struct Member

You can take the address of a struct member:

```cpp
struct Point { double x, y; };

Point p{1.0, 2.0};
double* px = &p.x;     // pointer to the x member of p
*px = 100.0;
std::cout << p.x << '\n';   // 100
```

This is the basis of pointer-based APIs that fill in struct members (e.g. `getsockopt`).

### 12. Pointer to Struct Through an Array

```cpp
struct Item { int id; double price; };
Item inventory[100];

for (Item* it = inventory; it != inventory + 100; ++it) {
    it->id = 0;
    it->price = 0.0;
}
```

`it->id` is `(*it).id`, which is `(*(&inventory[i])).id` — i.e. `inventory[i].id`. The arrow operator composes with pointer arithmetic.

## Common Pitfalls

> [!warning] Using `.` instead of `->` on a pointer
> `p.x` where `p` is `Point*` is a compile error. Use `p->x`.

> [!warning] Using `->` on a value
> `p->x` where `p` is a `Point` (not a pointer) is a compile error. Use `p.x`.

> [!warning] Returning a pointer to a local struct
> ```cpp
> Point* bad() { Point p{1, 2}; return &p; }   // UB — p destroyed on return
> ```

> [!warning] Memory leaks in linked structures
> Forgetting to free every node in a linked structure leaks memory. Use smart pointers to automate cleanup.

> [!warning] Recursive destructor stack overflow
> A `std::unique_ptr<Node>` chain of 100,000 nodes will overflow the stack on destruction. Use iterative cleanup for very long chains.

> [!warning] Dangling pointer after container resize
> ```cpp
> std::vector<Point> v = {...};
> Point* p = &v[0];
> v.push_back(...);     // may reallocate
> // p is now dangling
> ```

> [!warning] Calling `delete` on a pointer obtained from `new[]`
> `Item* items = new Item[100]; delete items;` is UB. Use `delete[] items`.

> [!warning] Deleting a pointer to a base class without a virtual destructor
> ```cpp
> struct Base { ~Base() {} };   // non-virtual
> struct Derived : Base { std::string s; };
> Base* p = new Derived;
> delete p;   // UB — Derived's destructor not called, std::string leaks
> ```
> Always make the destructor of a polymorphic base class `virtual` (or `= default`).

> [!warning] Smart pointer with array of derived
> `std::unique_ptr<Base[]>` with `Derived` elements is UB — there is no virtual destructor on each element. Use `std::vector<std::unique_ptr<Base>>` instead.

## Tips and Tricks

- **Use `->` always** when accessing a struct member through a pointer. It is clearer than `(*p).member` and required when `.` would bind to the wrong thing.
- **Prefer `std::unique_ptr<T>` and `std::shared_ptr<T>`** over raw `T*` for owned heap structs.
- **Use raw `T*` only for non-owning borrows** (e.g. traversal pointers, function parameters).
- **Always make the destructor of a polymorphic base class `virtual`** — this is the most common memory-related bug in C++.
- **Document ownership** in APIs: returning `T*` should be rare; returning `std::unique_ptr<T>` makes ownership explicit.
- **Use `gsl::owner<T*>`** to mark raw owning pointers when smart pointers cannot be used (e.g. in C-compatible struct layouts).
- **For linked structures, prefer smart pointers** to automate cleanup, but be aware of recursive destructor stack overflow for very long chains.
- **For most use cases, prefer `std::vector<T>` over a hand-rolled linked structure** — cache locality usually wins.
- **Compile with `-fsanitize=address`** to catch use-after-free, dangling pointer dereferences, and leaks at runtime.
- **Use `[[nodiscard]]` on functions returning `std::unique_ptr<T>`** to remind callers not to discard the result.
