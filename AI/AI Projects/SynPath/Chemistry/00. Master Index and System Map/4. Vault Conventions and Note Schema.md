# 4. Vault Conventions and Note Schema

> [!abstract] Core Idea
> Every note in this vault follows one strict 9-section schema, one naming convention, one tag taxonomy, and one diagram policy. This page documents them so the vault stays coherent and scalable as you add notes over time.

## 1. The Folder Hierarchy

- **3D-SynTree Vault** (the root)
  - **00. Master Index and System Map** — this module: navigation and meta notes
  - **01. through 10. Module folders** — one per scientific domain
    - **0. Module Name MOC.md** — the module's navigation hub
    - **Chapter N. Chapter Name** — thematic groups inside the module
      - **N. Concept Name.md** — atomic, one-concept-per-note files

- **Modules** are the ten scientific domains of the project (chemistry, medicinal chemistry, spatial chemistry, structural biology, pharmacology, cheminformatics, geometric deep learning, circular statistics, MDPs and GFlowNets, benchmarking).
- **Chapters** group related concept notes inside a module.
- **Concept notes are atomic**: one coherent concept per note, split further rather than bloated.

## 2. Naming Conventions

- Numbers are followed by a **period and a space** — `1. Atomic Structure and Electrons.md`. Underscores are never used in any file or folder name.
- Module MOCs are numbered `0.` so they sort first: `0. Chemistry Foundations MOC.md`.
- The `# ` H1 title of every note equals its filename exactly.
- Section headings inside notes are numbered the same way: `## 1. What It Is` ... `## 9. Further Dependencies`.

## 3. The 9-Section Concept Schema

| Section | Purpose |
| --- | --- |
| 1. What It Is | Formal definition from absolute zero; every technical word defined |
| 2. Why It Exists | The physical, chemical, or mathematical problem the concept addresses |
| 3. How It Works | Mechanisms, derivations, and rules — the longest section, with worked examples |
| 4. What It Consists Of | Component parts and specialized vocabulary |
| 5. What You Must Understand | Non-negotiables, pitfalls, easy-to-forget reminders (warning, tip, example callouts) |
| 6. Prerequisites | Wikilinks to notes that must be mastered first, each with a reason |
| 7. Project Connection | Direct mapping to 3D-SynTree code, tensors, or architecture |
| 8. Required Depth | Essential, Supporting, or Advanced, with justification |
| 9. Further Dependencies | Wikilinks to notes that build on this one |
| Concept Mind Map | A Mermaid mind map of the note's knowledge hierarchy and related notes |

## 4. Tag Taxonomy

| Tag | Meaning |
| --- | --- |
| `moc` | Navigation hub note |
| `3dsyntree` | Every note in this vault |
| `domain/chemistry` ... `domain/benchmarking` | The module's scientific domain (one per module) |
| `depth/essential`, `depth/supporting`, `depth/advanced` | The note's required depth |
| `topic/...` | Optional extra topical tags for discovery |

Tags are stored in YAML frontmatter, so the tag pane and `tag:` searches work everywhere.

## 5. Callout Conventions

| Callout | Used for |
| --- | --- |
| `> [!abstract]` | The one-sentence essence at the top of a note |
| `> [!tip]` | Memory hooks and exam-style reminders |
| `> [!warning]` | Pitfalls and points students often miss |
| `> [!example]` | Worked numeric or chemical examples |
| `> [!note]` | Extra context that would break the flow |
| `> [!question]` | Gate-check self-exams in MOCs |

## 6. Diagram Policy

The only diagrams in this vault are **Mermaid mind maps**. They visualize the knowledge hierarchy, topic relationships, and learning paths. There are deliberately no flowcharts, no sequence diagrams, and no ASCII-art drawings — if a relationship matters, it is expressed as a mind map branch, a wikilink, or prose. Mind map labels use plain letters, digits, periods, and hyphens (write `SO2`, never `SO(2)`), so every diagram renders cleanly in Obsidian's built-in Mermaid engine.

## 7. Linking Etiquette

- Link with `[[exact note name]]` — the full name including its number prefix.
- Every note links **backwards** (Prerequisites) and **forwards** (Further Dependencies), and weaves 2–6 inline links into the body text.
- Links are dense on purpose: the vault is a knowledge graph, not a book. Use the backlinks panel and Graph View to travel.
- Never link to a note that does not exist yet; create a stub with the schema first.

## 8. How to Add a New Note (Expansion Protocol)

1. **Pick the chapter** where the concept belongs; if it fits nowhere, that is a signal a new chapter (or module) is needed.
2. **Name it** `next number, period, space, Title` with no underscores.
3. **Copy the schema** — all 9 sections plus the Concept Mind Map, frontmatter with module, chapter, domain, and depth tags.
4. **Link both ways** — add it to its chapter's notes in the module MOC table, give it Prerequisites and Further Dependencies, and update the affected MOC mind map.
5. **Preserve, do not replace** — this vault grows iteratively: add files and sections, fix inconsistencies, but never delete existing content without merging its links elsewhere first. The vault must remain one unified, coherent knowledge base.
6. **Re-run the gate check** — can you explain the new note's mind map from memory? If not, it is not finished.

## 9. Quality Bar for New Content

- Explain from zero; define every term on first use; no "obviously" or "as you know".
- Include at least one worked example with real numbers where the concept is quantitative.
- Include the pitfalls and easy-to-forget reminders — the notes exist because the reader explicitly asked for them.
- Connect to the project concretely (file, tensor, mechanism), or say honestly that the connection is conceptual.
- Keep every promise the schema makes: a section header with no content is a bug.
