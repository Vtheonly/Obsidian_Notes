### 1. Concept Definition & Invalidation Mechanics
An in-place operation modifies the memory values of an existing tensor storage buffer directly, rather than allocating a new buffer (denoted by trailing underscores, e.g., `tensor.add_()`, `tensor.copy_()`, `tensor[idx] = val`).

While in-place operations reduce memory allocations, they can break automatic differentiation:
If tensor $\mathbf{x}$ was saved during the forward pass by `ctx.save_for_backward` to evaluate an upcoming backward step, modifying $\mathbf{x}$ in place changes the values needed by the backward pass.

PyTorch tracks memory modifications via an internal counter on every tensor (`._version`):
1. When a tensor is instantiated, its version counter starts at zero: `x._version == 0`.
2. Any in-place modification increments the counter: `x._version += 1`.
3. When `backward()` executes, autograd compares each saved tensor's current version against the version recorded during the forward pass. If the versions differ, autograd halts with an exception:
   `RuntimeError: one of the variables needed for gradient computation has been modified by an inplace operation`

```python
# CODE CRASH EXAMPLE: Modifying intermediate activations in-place
x = torch.randn(64, 256, requires_grad=True)
y = torch.relu(x)   # ReLu saves its output tensor 'y' to evaluate the backward step
y.add_(2.0)         # FATAL IN-PLACE CORRUPTION: y._version is incremented!

loss = y.sum()
# CRASHES: loss.backward() -> Raises RuntimeError due to version mismatch
```
