# 08.2. Graph Theory, MultiDiGraphs, and Complexity

The original vault's Chapter 8.2 contained a **mathematically false claim**: *"Searching for a connection is a Constant Time operation ($O(1)$), meaning the graph stays fast even if you add a million rare diseases."* This is wrong in two ways:

1. **Adjacency lookup is $O(1)$, but only for checking if two specific nodes are directly connected.** Finding whether two nodes are connected by a path of any length is $O(|V| + |E|)$ (BFS/DFS), and shortest-path computation is $O((|V| + |E|) \log |V|)$ (Dijkstra).
2. **Multi-hop pathfinding scales exponentially with depth** — $O(b^d)$ where $b$ is the branching factor — which is the opposite of "constant time."

This note corrects the complexity claims, explains when NetworkX is and is not the right tool, and covers the actual algorithmic costs of the operations the project performs.

This chapter covers: (1) directed graphs (DiGraphs), (2) MultiDiGraphs (multiple edges between the same nodes), (3) index-free adjacency and what it actually buys, (4) the corrected complexity table for common graph operations, (5) when NetworkX breaks down, and (6) when to move to a distributed graph database.

---

## 1. Directed Graphs (DiGraphs)

Medicine is a "one-way street":

- **Correct**: `Disease → has_symptom → Symptom`. Albinism causes white hair.
- **Incorrect**: `Symptom → has_symptom → Disease`. White hair does not "cause" Albinism.

Every edge in the project's Knowledge Graph has a **directional arrow**. This is implemented in NetworkX as a `DiGraph` (directed graph), where edges have a source and a target. Traversing the graph in the wrong direction (e.g., from symptom to disease via a `has_symptom` edge) is meaningless, and the directed representation prevents this.

---

## 2. MultiDiGraphs — Multiple Edges Between the Same Nodes

In biology, two entities can be related in multiple ways simultaneously. A regular `DiGraph` allows only one edge between a given (source, target) pair; a `MultiDiGraph` allows multiple edges, each with its own predicate and attributes.

### 2.1. The Project's Use Case

For `Orpha:92` (Albinism) and `HP:0000639` (Nystagmus):

- Edge 1: `has_phenotype` (Albinism has Nystagmus as a phenotype), frequency = 0.85.
- Edge 2: `is_primary_diagnostic_marker` (Nystagmus is how Albinism is diagnosed), specificity = 0.92.
- Edge 3: `has_onset` (Nystagmus in Albinism has congenital onset).

A `DiGraph` would collapse these into one edge, losing information. A `MultiDiGraph` preserves all three.

### 2.2. NetworkX Implementation

```python
import networkx as nx

G = nx.MultiDiGraph()
G.add_edge("Orpha:92", "HP:0000639",
           predicate="has_phenotype", frequency=0.85)
G.add_edge("Orpha:92", "HP:0000639",
           predicate="is_primary_diagnostic_marker", specificity=0.92)
G.add_edge("Orpha:92", "HP:0000639",
           predicate="has_onset", onset="HP:0003577")

# Retrieving all edges between these nodes
edges = G.get_edge_data("Orpha:92", "HP:0000639")
# edges is a dict: {0: {"predicate": "has_phenotype", ...},
#                    1: {"predicate": "is_primary_diagnostic_marker", ...},
#                    2: {"predicate": "has_onset", ...}}
```

## 3. Index-Free Adjacency — What It Actually Buys

The original vault conflated two different operations under the label "constant time." Let's separate them.

### 3.1. Adjacency Lookup — $O(1)$

Given a node $v$ and a neighbour $u$, checking whether the edge $(v, u)$ exists is $O(1)$ in an adjacency-list representation (which NetworkX uses). The adjacency list of $v$ is a hash table; looking up $u$ in it is a hash operation.

```python
# O(1)
G.has_edge("Orpha:92", "HP:0000639")

# O(1) — get all direct neighbours of a node
list(G.successors("Orpha:92"))
list(G.predecessors("HP:0000639"))
```

This is the operation that is genuinely $O(1)$ and that scales to millions of nodes. It is what makes graph databases fast for **local** queries ("who are this node's neighbours?").

### 3.2. Pathfinding — $O(|V| + |E|)$ or Worse

Finding whether a path exists between two nodes (of any length) requires traversing the graph:

```python
# O(|V| + |E|) — BFS or DFS
nx.has_path(G, "HP:0000639", "Orpha:92")

# O((|V| + |E|) log |V|) — Dijkstra (weighted shortest path)
nx.shortest_path(G, "HP:0000639", "Orpha:92", weight="frequency")

# O(|V| * |E|) — Bellman-Ford (handles negative weights)
nx.bellman_ford_path(G, "HP:0000639", "Orpha:92")
```

These operations are **not** $O(1)$. For a graph with 1 million nodes and 10 million edges, BFS is $O(11\text{M})$ — about 100 ms on a modern CPU. Dijkstra with a Fibonacci heap is $O((|V| + |E|) \log |V|) \approx O(11\text{M} \times 20) = 220\text{M}$ operations — about 1 second.

### 3.3. Multi-hop Pathfinding — $O(b^d)$

Finding all paths of length $\leq d$ between two nodes scales as $O(b^d)$, where $b$ is the average branching factor (number of neighbours per node) and $d$ is the depth. For HPO with $b \approx 10$ and $d = 4$, this is $10^4 = 10{,}000$ paths — manageable. For $d = 6$, it is $10^6$ — slow. For $d = 8$, it is $10^8$ — intractable.

This is the **path explosion** problem, and it is why the project uses depth-limited search (Chapter 8.4) and hub-node down-weighting to keep the effective $b$ small.

## 4. Corrected Complexity Table

| Operation | Complexity | NetworkX Function |
| :--- | :--- | :--- |
| Check if edge $(u, v)$ exists | $O(1)$ | `G.has_edge(u, v)` |
| Get all neighbours of $v$ | $O(\deg(v))$ | `G.successors(v)` |
| Check if any path exists between $u, v$ | $O(\|V\| + \|E\|)$ | `nx.has_path(G, u, v)` |
| Shortest path (unweighted) | $O(\|V\| + \|E\|)$ | `nx.shortest_path(G, u, v)` |
| Shortest path (weighted, Dijkstra) | $O((\|V\| + \|E\|) \log \|V\|)$ | `nx.dijkstra_path(G, u, v)` |
| All-pairs shortest paths | $O(\|V\|(\|V\| + \|E\|))$ | `nx.all_pairs_shortest_path(G)` |
| All paths up to length $d$ | $O(b^d)$ | `nx.all_simple_paths(G, u, v, cutoff=d)` |
| Connected components | $O(\|V\| + \|E\|)$ | `nx.weakly_connected_components(G)` |
| PageRank | $O(\|V\| + \|E\|)$ per iteration | `nx.pagerank(G)` |
| Betweenness centrality | $O(\|V\| \|E\|)$ | `nx.betweenness_centrality(G)` |

### 4.1. What This Means for the Project

For the project's Knowledge Graph (~10,000 diseases, ~17,000 phenotypes, ~50,000 edges):

- **Adjacency lookup**: $O(1)$ — instant.
- **BFS / shortest path**: $O(77\text{k})$ — ~1 ms.
- **All-pairs shortest paths**: $O(27\text{k} \times 77\text{k}) = O(2\text{B})$ — ~20 seconds. Pre-computed once.
- **All paths up to length 4**: $O(10^4) = 10{,}000$ paths per query — ~100 ms.

These are all tractable on a single machine. The original vault's $O(1)$ claim is wrong, but the corrected complexities are still fast enough for the project's scale.

## 5. When NetworkX Breaks Down

NetworkX is a **pure-Python, in-memory** graph library. It has three limitations:

### 5.1. Single-Machine Memory

NetworkX stores the graph in RAM. For a graph with 1 million nodes and 10 million edges, the memory footprint is ~10–20 GB (NetworkX's Python object overhead is substantial). Beyond this, you need a distributed graph database.

### 5.2. No Native SPARQL

NetworkX does not support SPARQL (the RDF query language). If the application needs SPARQL queries (e.g., "find all diseases treated by drug X via mechanism Y"), it must use a proper triple store like GraphDB, Apache Jena, or Stardog.

### 5.3. No OWL Reasoning

NetworkX does not support **OWL reasoning** — the automatic inference of new triples from ontology axioms. For example, if the ontology says *"A is-a B"* and *"B is-a C"*, an OWL reasoner infers *"A is-a C"* automatically. NetworkX requires this to be pre-computed (the transitive closure of Chapter 7.1).

### 5.4. When to Switch to a Graph Database

| Symptom | Recommended Migration |
| :--- | :--- |
| Graph exceeds 10M edges | Neo4j, Memgraph, or distributed (JanusGraph, DGraph) |
| Need SPARQL queries | GraphDB, Apache Jena, Stardog, Virtuoso |
| Need OWL reasoning | GraphDB, Pellet, HermiT |
| Need multi-tenant isolation | Neo4j (with separate databases) |

The project's current scale (~50k edges) is well within NetworkX's comfort zone. Migration to a graph database would be triggered by growth to millions of edges (e.g., if the project ingests all of PubMed's entity-relation annotations).

## 6. Distributed Graph Databases — When Scale Demands

For graphs that exceed single-machine memory, three families of distributed graph database exist:

### 6.1. Neo4j (Single-Server, Optimised)

Neo4j is the most popular graph database. It is single-server (not distributed) but is heavily optimised: it stores the graph in a native adjacency-list format on disk, with constant-time adjacency lookup. It supports Cypher (a declarative graph query language) but not SPARQL natively (a plugin exists).

### 6.2. Distributed Graph Databases (JanusGraph, DGraph, NebulaGraph)

These distribute the graph across multiple machines, enabling horizontal scaling. They support billions of nodes and edges. The tradeoff is higher latency per query (network round-trips) and more operational complexity.

### 6.3. RDF Triple Stores (GraphDB, Apache Jena, Stardog, Virtuoso)

These are designed for RDF data and support SPARQL natively. Some (GraphDB) also support OWL reasoning. They can scale to hundreds of millions of triples on a single server and to billions with sharding.

### 6.4. The Project's Migration Path

If the project's graph grows beyond NetworkX's capacity, the recommended migration is to **GraphDB** (or Apache Jena if open-source is required), because:

1. The graph is already in RDF/Turtle format (Chapter 8.1), so the data model transfers directly.
2. The project may need SPARQL queries in the future (e.g., for complex clinical research questions).
3. OWL reasoning would enable automatic inference of new associations, reducing manual curation.

The migration would replace the `rdf_to_networkx` bridge with direct SPARQL queries against the triple store. The similarity and pathfinding algorithms (Chapters 8.3, 8.4) would need to be reimplemented in SPARQL or in a graph-database-native API.

---

## 7. The Architectural Tradeoff

The original vault implied that NetworkX is universally fast. The corrected picture is:

- **NetworkX is fast enough for the project's current scale** (~50k edges, all operations <1 second).
- **NetworkX is not fast for graphs 100× larger** (>5M edges, all-pairs shortest paths would take hours).
- **NetworkX is not the right tool for SPARQL or OWL reasoning** — use a triple store.

The project's choice of NetworkX is justified by the current scale and by the fact that the graph is built once (at ontology-load time) and queried many times (at patient-note-retrieval time). If the project scales to ingest all of PubMed's annotations (millions of edges), the migration to GraphDB should be planned.
