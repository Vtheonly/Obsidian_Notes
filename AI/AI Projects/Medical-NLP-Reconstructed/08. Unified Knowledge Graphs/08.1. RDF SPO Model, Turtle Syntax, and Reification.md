# 08.1. RDF SPO Model, Turtle Syntax, and Reification

The final architecture of the project's Knowledge Graph is based on **RDF (Resource Description Framework)**, the W3C standard for representing knowledge as triples. The original vault presented the Subject-Predicate-Object triple model and Turtle syntax but completely omitted the critical problem of **edge metadata**: how do you store the fact that *"Albinism causes Nystagmus with 85% frequency"* when standard RDF predicates cannot have attributes? The original vault also did not explain the transition from RDF (a Semantic Web standard) to NetworkX (a Python in-memory graph library), nor the architectural tradeoffs of this choice.

This note covers: (1) the RDF triple model, (2) Turtle syntax, (3) URIs and Linked Data, (4) the edge-metadata problem, (5) RDF Reification, (6) Named Graphs, (7) RDF-star (RDF*), and (8) the RDF-to-NetworkX bridge.

---

## 1. The RDF Triple Model

Every fact in RDF is broken into its smallest possible unit: a **triple** of Subject, Predicate, Object.

| Role | Example | Type |
| :--- | :--- | :--- |
| Subject | `orpha:92` (Oculocutaneous Albinism Type 1) | URI |
| Predicate | `orpha:has_phenotype` | URI |
| Object | `hpo:0000639` (Nystagmus) | URI or literal |

The triple `(orpha:92, orpha:has_phenotype, hpo:0000639)` asserts: *"Oculocutaneous Albinism Type 1 has the phenotype Nystagmus."*

### 1.1. Why Triples?

In a relational database, information is trapped in rows and columns; adding a new attribute requires a schema migration. In a triple store, knowledge is an **infinite web**: adding a new fact is just adding a new triple. The schema is open-world — any triple can be added at any time without breaking existing data.

This flexibility is essential for medical knowledge, which evolves continuously. When a new gene-phenotype association is discovered, the project simply adds a new triple; no schema change is needed.

### 1.2. Direction

Triples are **directed**: the arrow goes from Subject to Object. `(Albinism, has_phenotype, Nystagmus)` is a different triple from `(Nystagmus, has_phenotype, Albinism)`. The direction encodes the semantic relationship: Albinism **causes** Nystagmus, not the reverse.

## 2. Turtle (.ttl) Syntax

Turtle is the standard human-readable serialization of RDF. The project's Knowledge Graph is stored as Turtle files:

```turtle
@prefix orpha: <http://www.orphanet.org/id/> .
@prefix hpo: <http://purl.obolibrary.org/obo/HP_> .
@prefix mondo: <http://purl.obolibrary.org/obo/MONDO_> .
@prefix hgnc: <http://identifiers.org/hgnc/> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .
@prefix owl: <http://www.w3.org/2002/07/owl#> .

# Defining Oculocutaneous Albinism Type 1
orpha:92 rdfs:label "Oculocutaneous Albinism Type 1" ;
         rdfs:subClassOf mondo:0008754 ;
         orpha:has_phenotype hpo:0000639 ;  # Nystagmus
         orpha:has_phenotype hpo:0001022 ;  # Albinism
         orpha:has_phenotype hpo:0000572 ;  # Photophobia
         orpha:associated_gene hgnc:8047 .   # OCA1 = TYR gene

# Defining the OCA1 gene
hgnc:8047 rdfs:label "TYR" ;
          rdfs:comment "Tyrosinase gene" .
```

### 2.1. Syntax Conventions

- **Prefixes** (`@prefix`) define shorthand for URIs, making the file readable.
- **Semicolons** (`;`) separate multiple predicates with the same subject.
- **Periods** (`.`) end a statement.
- **Comments** start with `#`.
- **Literals** (strings, numbers) are quoted; URIs are not.

### 2.2. The Power of URIs

Every node and edge in RDF is a **URI** (Uniform Resource Identifier). The URI `http://purl.obolibrary.org/obo/HP_0000639` is globally unique and resolvable — it can be looked up on the web to retrieve the official HPO definition. This makes the graph **interoperable**: any other RDF system in the world can reference the same URI and the meaning is unambiguous.

## 3. The Edge-Metadata Problem (Critical Gap)

The original vault's RDF model can represent `(Albinism, has_phenotype, Nystagmus)` but **cannot** represent the fact that this association has metadata:

- **Frequency**: Nystagmus occurs in ~85% of Albinism Type 1 patients (vs. 30% in Albinism Type 2).
- **Evidence**: This association is supported by PubMed PMID 12345678.
- **Onset**: Nystagmus in Albinism typically presents at birth.
- **Certainty**: This is an "established" association, not a "suspected" one.

In standard RDF, **predicates cannot have attributes**. The triple `(Albinism, has_phenotype, Nystagmus)` is a single arc; there is no way to attach "frequency = 0.85" to that arc.

This is a critical limitation for clinical NLP, where the **strength of evidence** matters as much as the existence of the association. A disease-phenotype link with 85% frequency is much stronger evidence than one with 5% frequency, and the retrieval system must weight them differently.

Three solutions exist: Reification, Named Graphs, and RDF-star.

---

## 4. RDF Reification

**Reification** is the original RDF solution: turn the triple into a resource, then attach metadata to that resource.

```turtle
# The original triple
orpha:92 orpha:has_phenotype hpo:0000639 .

# Reified: create a "Statement" resource
:stmt1 rdf:type rdf:Statement ;
       rdf:subject orpha:92 ;
       rdf:predicate orpha:has_phenotype ;
       rdf:object hpo:0000639 ;
       orpha:frequency 0.85 ;
       orpha:evidence pmid:12345678 ;
       orpha:onset hpo:0003577 ;  # Congenital onset
       orpha:certainty "established" .
```

### 4.1. Pros and Cons

- **Pros**: Standard RDF; works with any triple store.
- **Cons**: Verbose (4 triples to represent 1 statement + N triples for metadata). The original triple is still in the graph, so the data is duplicated. Querying is complex (you must join through the reified statement).

Reification is rarely used in modern RDF systems because of its verbosity.

---

## 5. Named Graphs

A **Named Graph** is a set of triples identified by a URI. Metadata can be attached to the named graph as a whole:

```turtle
@prefix ex: <http://example.org/> .

# The named graph
ex:AlbinismNystagmusAssociation {
    orpha:92 orpha:has_phenotype hpo:0000639 .
}
ex:AlbinismNystagmusAssociation orpha:frequency 0.85 ;
                                orpha:evidence pmid:12345678 .
```

### 5.1. Pros and Cons

- **Pros**: Less verbose than reification; supported by SPARQL.
- **Cons**: Each edge with metadata needs its own named graph, which is awkward for graphs with millions of edges. Metadata is at the graph level, not the edge level (though in practice each "graph" can contain a single triple).

Named Graphs are a reasonable compromise and are used in some production systems.

---

## 6. RDF-star (RDF*)

**RDF-star** (Hartig et al., 2021) is the modern solution: it allows triples to be the subject or object of other triples. This is exactly what is needed for edge metadata.

```turtle
# A triple with metadata, in RDF-star
<<orpha:92 orpha:has_phenotype hpo:0000639>>
    orpha:frequency 0.85 ;
    orpha:evidence pmid:12345678 ;
    orpha:onset hpo:0003577 ;
    orpha:certainty "established" .
```

The `<<...>>` syntax denotes a **quoted triple** — a triple that is itself the subject of another triple. This is the most natural representation of edge metadata.

### 6.1. Pros and Cons

- **Pros**: Compact, readable, semantically clean. Supported by modern triple stores (GraphDB, Oxigraph, Jena).
- **Cons**: Not yet a W3C standard (as of 2024); not supported by older triple stores or by NetworkX natively.

### 6.2. The Project's Choice

The project uses **RDF-star** for storing edge metadata because:

1. **Compactness**: One triple + N metadata triples vs. 4 + N for reification.
2. **Readability**: The Turtle-star syntax is clear and easy to audit.
3. **Future-proofing**: RDF-star is on the W3C standards track and is widely supported.

For the NetworkX in-memory representation (Chapter 8.2), the project uses NetworkX's **edge attribute dictionaries**, which are the Python-native equivalent of RDF-star edge metadata:

```python
graph.add_edge("orpha:92", "hpo:0000639",
               predicate="has_phenotype",
               frequency=0.85,
               evidence="pmid:12345678",
               onset="hpo:0003577",
               certainty="established")
```

## 7. The RDF-to-NetworkX Bridge

The original vault introduced RDF in 8.1 and NetworkX in 8.2 without explaining how the two connect. The bridge is necessary because RDF is a **data model** (a way to represent knowledge) while NetworkX is a **data structure** (an in-memory Python object). The pipeline:

1. **Loads** the Turtle file into an `rdflib.Graph` (an in-memory RDF triple store).
2. **Converts** the RDF graph to a NetworkX `MultiDiGraph` using `rdflib.extras.describer` or a custom traversal.
3. **Operates** on the NetworkX graph for similarity computation and pathfinding.
4. **Optionally exports** the modified NetworkX graph back to Turtle for persistence.

### 7.1. The Conversion Code

```python
import rdflib
import networkx as nx

def rdf_to_networkx(turtle_path):
    g = rdflib.Graph()
    g.parse(turtle_path, format="turtle")
    
    nx_graph = nx.MultiDiGraph()
    for subj, pred, obj in g:
        nx_graph.add_edge(
            str(subj),
            str(obj),
            predicate=str(pred)
        )
    return nx_graph
```

### 7.2. Edge Metadata in the Conversion

For RDF-star edge metadata, the conversion is more involved:

```python
def rdf_star_to_networkx(turtle_path):
    g = rdflib.Graph()
    g.parse(turtle_path, format="turtle-star")
    
    nx_graph = nx.MultiDiGraph()
    
    # First pass: add base triples
    for subj, pred, obj in g.triples((None, None, None)):
        if not isinstance(subj, rdflib.term.Statement):
            nx_graph.add_edge(str(subj), str(obj), predicate=str(pred))
    
    # Second pass: add edge metadata from RDF-star quoted triples
    for stmt, meta_pred, meta_obj in g.triples((None, None, None)):
        if isinstance(stmt, rdflib.term.Statement):
            subj, pred, obj = stmt
            if nx_graph.has_edge(str(subj), str(obj)):
                # Update the edge's attributes
                for key, val in nx_graph[str(subj)][str(obj)].items():
                    if val.get("predicate") == str(pred):
                        val[str(meta_pred)] = str(meta_obj)
    
    return nx_graph
```

### 7.3. Architectural Tradeoffs

The RDF → NetworkX bridge has a known limitation: **NetworkX does not support SPARQL** (the RDF query language). If the application needs SPARQL queries (e.g., "find all diseases treated by drug X"), it should operate on the `rdflib.Graph` directly, not on the NetworkX conversion.

The project's pipeline uses NetworkX for:

- **Similarity computation** (Jaccard, Resnik, Lin — Chapter 8.3).
- **Pathfinding** (BFS, Dijkstra — Chapter 8.4).
- **Graph-theoretic metrics** (degree, betweenness).

It uses `rdflib.Graph` (or a proper triple store like GraphDB) for:

- **SPARQL queries** (complex joins that NetworkX cannot express).
- **OWL reasoning** (inferring new triples from existing ones via ontology axioms).
- **Persistence** (storing the graph as Turtle files).

The two representations coexist; the choice depends on the operation.

## 8. Summary

| Feature | Standard RDF | Reification | Named Graphs | RDF-star |
| :--- | :--- | :--- | :--- | :--- |
| Edge metadata | Not supported | Supported (verbose) | Supported (graph-level) | **Supported (clean)** |
| Triples per edge+metadata | 1 + 0 | 1 + 4 + N | 1 + 1 + N | 1 + N |
| SPARQL support | Yes | Yes | Yes | Yes (extended) |
| NetworkX native support | No | No | No | No (use edge attrs) |
| W3C standard | Yes | Yes | Yes | In progress |

The project uses **RDF-star** for persistence (Turtle files) and **NetworkX edge attribute dictionaries** for in-memory computation. The bridge between them is the `rdf_to_networkx` conversion function.
