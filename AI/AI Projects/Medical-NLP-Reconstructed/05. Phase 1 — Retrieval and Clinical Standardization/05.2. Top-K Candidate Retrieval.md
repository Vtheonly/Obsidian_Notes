# 05.2. Top-K Candidate Retrieval

Calculating the cosine similarity between a patient note and every one of the ~10,000 Orphanet disease definitions is computationally expensive — and the original vault's claim that "for production scale, we would use FAISS" left the engineer with no information about **which FAISS index** to use, **how the index types differ**, or **what the latency/recall tradeoff looks like**. A naive brute-force implementation works for a 10k-disease demo but fails at production scale (millions of triplets), and the wrong FAISS index choice can sacrifice 20% recall for a 2× speedup that the application does not need.

This note covers: (1) the search space and the choice of $K$, (2) the brute-force baseline (FAISS FlatL2 / FlatIP), (3) the IVF-Flat index with inverted files, (4) the IVF-PQ index with product quantization, (5) the HNSW index (hierarchical navigable small worlds), (6) the latency/recall tradeoff comparison, and (7) the project's production choice.

---

## 1. The Search Space

The project's disease database contains:

- ~10,000 Orphanet rare disease entries.
- Each entry has a textual definition (typically 50–200 words).
- Each definition is encoded by BioBERT into a 768-dim vector.
- The vectors are $L_2$-normalised so that inner-product search is equivalent to cosine similarity (Chapter 4.2).

For each patient query, the task is: **find the $K = 20$ disease vectors with the highest cosine similarity to the patient vector.**

### 1.1. Why $K = 20$?

The choice of $K$ is a recall/precision tradeoff:

- **$K$ too small (e.g., $K = 1$)**: If BioBERT produces a slightly wrong ranking at the top, the correct disease is lost immediately. Stage 3 (Knowledge Graph) and Stage 4 (Neural Ranker) have no candidates to work with.
- **$K$ too large (e.g., $K = 100$)**: Stage 4's pairwise tournament scales as $O(K^2)$, so $K = 100$ means 9,900 pairwise comparisons per patient note — too slow for interactive use. Also, the bottom of the Top-100 is dominated by semantically unrelated diseases that distract the ranker.

Empirical tuning on the project's validation set showed that the correct disease is in the Top-20 for ~95% of patient notes (using BioBERT), and that increasing $K$ beyond 20 provides diminishing returns while linearly increasing the Stage 4 cost. $K = 20$ is the sweet spot.

### 1.2. Why "Recall @ 20" Is the Phase 1 Metric

The metric for Phase 1 retrieval is **Recall @ K**: out of all patient notes for which the correct disease is in the database, what fraction has the correct disease in the Top-K? The project's target is **Recall @ 20 ≥ 0.95**.

Recall @ 20 is the right metric because the downstream stages (3 and 4) cannot recover a disease that Phase 1 missed. If Recall @ 20 is 0.95, the best possible Top-1 accuracy after Stages 3 and 4 is also 0.95 — they can only reorder the Top-20, not add to it.

## 2. The Brute-Force Baseline — FAISS FlatL2 / FlatIP

The simplest retrieval method is **exact nearest-neighbor search**: compute the cosine similarity between the query and every database vector, then return the top $K$.

```python
import faiss
import numpy as np

# Build the index
dim = 768
index = faiss.IndexFlatIP(dim)  # Inner product = cosine on L2-normalised vectors
vectors = np.array(disease_vectors).astype('float32')
faiss.normalize_L2(vectors)  # Ensure normalisation
index.add(vectors)

# Query
query = np.array([patient_vector]).astype('float32')
faiss.normalize_L2(query)
scores, indices = index.search(query, k=20)
```

### 2.1. Performance Characteristics

For a 10,000-vector database on a single CPU:

- **Index build time**: <1 second (just copies the vectors into a contiguous array).
- **Query time**: ~5 ms (one matrix multiplication: 768 × 10,000 = 7.68M FLOPs).
- **Recall**: 100% (exact search).

This is perfectly adequate for the project's 10k-disease demo. Brute-force becomes the right choice **whenever the database fits in memory and query latency is acceptable**.

### 2.2. When Brute-Force Fails

Brute-force scales linearly with database size. For a 1-million-vector database:

- Query time: ~500 ms per query (100× slower).
- Memory: 1M × 768 × 4 bytes = 3 GB (just fits on a typical machine).

For a 100-million-vector database (e.g., embedding every PubMed abstract):

- Query time: ~50 seconds per query (unusable).
- Memory: 300 GB (requires sharding).

At this scale, **Approximate Nearest Neighbor (ANN)** algorithms are required. They trade a small recall loss (typically 1–5%) for orders-of-magnitude speedups.

---

## 3. Approximate Nearest Neighbor (ANN) — The Algorithmic Landscape

ANN algorithms share a common strategy: **build an index structure that prunes the search space**, so only a small fraction of the database is examined per query. The three dominant families are:

1. **Inverted File (IVF)**: Partition the space into Voronoi cells; only search the cell containing the query (plus a few neighbours).
2. **Product Quantization (PQ)**: Compress vectors into short codes; compute approximate distances on the codes.
3. **Graph-based (HNSW)**: Build a navigable small-world graph; traverse it greedily from a starting node toward the query.

Each family has different latency/recall/memory tradeoffs, and FAISS supports all three (and combinations thereof).

---

## 4. IVF-Flat — Inverted File Index

### 4.1. How IVF Works

IVF partitions the vector space into $n_{\text{list}}$ Voronoi cells using k-means clustering. Each cell has a centroid. At query time:

1. Find the $n_{\text{probe}}$ nearest centroids to the query.
2. Search only the vectors in those cells (brute-force within each cell).

The `nprobe` parameter controls the latency/recall tradeoff:

- `nprobe = 1`: Search only the cell of the nearest centroid. Fastest, lowest recall.
- `nprobe = nlist`: Search all cells. Equivalent to brute-force, 100% recall.

Typical settings: `nlist = 100`, `nprobe = 10` → search 10% of the database, recall ~95%.

### 4.2. FAISS Implementation

```python
nlist = 100  # Number of Voronoi cells
quantizer = faiss.IndexFlatIP(dim)
index = faiss.IndexIVFFlat(quantizer, dim, nlist, faiss.METRIC_INNER_PRODUCT)
index.train(vectors)  # Run k-means to find centroids
index.add(vectors)
index.nprobe = 10  # Search 10 cells per query
```

### 4.3. Tradeoffs

- **Memory**: Same as Flat (full-precision vectors stored).
- **Query time**: ~10× faster than Flat for `nprobe = 10` on a 100k-vector database.
- **Recall**: 90–98% depending on `nprobe`.
- **Build time**: Requires k-means training (~seconds for 100k vectors).

IVF-Flat is the right choice for medium-scale databases (100k–1M vectors) where memory is not the bottleneck but query latency matters.

---

## 5. IVF-PQ — Inverted File with Product Quantization

### 5.1. How PQ Works

Product Quantization compresses each 768-dim vector into a short code (typically 8–64 bytes) by:

1. Splitting the 768-dim vector into $m$ sub-vectors of dimension $768/m$.
2. Running k-means (typically $k = 256$) on each sub-vector independently, producing $m$ codebooks of 256 centroids each.
3. Encoding each sub-vector by the index of its nearest centroid (one byte per sub-vector if $k = 256$).

The compressed code is $m$ bytes. For $m = 64$, this is a 12× compression (768 × 4 bytes = 3072 bytes → 64 bytes).

### 5.2. Approximate Distance Computation

The cosine similarity between a query and a database vector is approximated by summing the pre-computed distances between the query sub-vectors and the database centroids. This is a lookup table operation, not a dot product, so it is extremely fast.

### 5.3. IVF + PQ

IVF-PQ combines the two: IVF partitions the space (reducing the number of vectors to scan), and PQ compresses each vector (reducing the cost per scan). This is the standard production index for billion-scale vector search.

```python
nlist = 100
m = 64  # Number of sub-quantizers
nbits = 8  # Bits per sub-quantizer (256 centroids)
quantizer = faiss.IndexFlatIP(dim)
index = faiss.IndexIVFPQ(quantizer, dim, nlist, m, nbits)
index.train(vectors)
index.add(vectors)
index.nprobe = 10
```

### 5.4. Tradeoffs

- **Memory**: 12–50× smaller than Flat.
- **Query time**: ~100× faster than Flat.
- **Recall**: 85–95% (the quantization introduces error).
- **Build time**: Substantial (k-means on each sub-vector).

IVF-PQ is the right choice for large-scale databases (1M+ vectors) where memory is constrained.

## 6. HNSW — Hierarchical Navigable Small World

### 6.1. How HNSW Works

HNSW (Malkov & Yashunin, 2018) builds a multi-layer graph where:

- Each node is a vector.
- Each node has edges to its nearest neighbors (in vector space).
- The graph is hierarchical: the top layer is sparse (long-range connections), the bottom layer is dense (short-range connections).

At query time, the algorithm starts at a random node in the top layer and greedily moves toward the query (each step goes to the neighbor closest to the query). When no improvement is possible, it drops to the next layer (which has more nodes) and repeats. The bottom layer contains all nodes, and the final greedy search produces the approximate nearest neighbors.

### 6.2. FAISS Implementation

```python
M = 16  # Number of edges per node
ef_construction = 200  # Build-time search depth
ef_search = 64  # Query-time search depth

index = faiss.IndexHNSWFlat(dim, M)
index.hnsw.efConstruction = ef_construction
index.hnsw.efSearch = ef_search
index.add(vectors)
```

### 6.3. Tradeoffs

- **Memory**: Larger than Flat (stores the graph edges in addition to the vectors), but smaller than IVF-Flat at scale.
- **Query time**: ~10–100× faster than Flat, depending on `ef_search`.
- **Recall**: 95–99% with appropriate `ef_search`.
- **Build time**: Slow (each insertion requires a graph traversal).
- **No training**: Unlike IVF/PQ, HNSW does not require k-means training, so it works on streaming data.

HNSW is the right choice for medium-scale databases (10k–10M vectors) where recall is critical (≥95%) and the database is updated frequently.

## 7. The Latency/Recall Tradeoff — Quantitative Comparison

On a 1-million-vector database (768-dim, L2-normalised):

| Index | Build Time | Memory | Query Time (1 thread) | Recall @ 10 |
| :--- | :--- | :--- | :--- | :--- |
| FlatIP (brute-force) | 0s | 3 GB | 500 ms | 100% |
| IVF-Flat (nlist=4096, nprobe=16) | 30s | 3 GB | 8 ms | 96% |
| IVF-PQ (nlist=4096, m=64, nprobe=16) | 60s | 80 MB | 2 ms | 91% |
| HNSW (M=16, ef=64) | 600s | 4.5 GB | 1.5 ms | 98% |

The right choice depends on the application:

- **Flat**: If the database fits in memory and 500 ms latency is acceptable, use Flat for 100% recall.
- **IVF-Flat**: If 96% recall is acceptable and you want 60× speedup, use IVF-Flat.
- **IVF-PQ**: If memory is the bottleneck (e.g., edge deployment), use IVF-PQ.
- **HNSW**: If recall is critical (≥98%) and you can afford the build time, use HNSW.

---

## 8. The Project's Production Choice

For the project's 10,000-disease database, the production choice is **HNSW** because:

1. **Recall is critical.** Missing the correct disease at Phase 1 means the downstream stages cannot recover it. HNSW's 98% recall is the best available.
2. **The database is small.** 10k vectors × 768 dims × 4 bytes = 30 MB — trivial memory footprint. HNSW's graph overhead (~50% extra) is negligible.
3. **The database is updated infrequently.** Orphanet releases quarterly updates; the slow HNSW build is acceptable.
4. **Query latency is sub-millisecond.** Even with `ef_search = 128` (high-recall setting), HNSW returns results in <2 ms per query.

The implementation:

```python
import faiss
import numpy as np

# Build
dim = 768
M = 32  # Higher M for better recall on small databases
ef_construction = 400
index = faiss.IndexHNSWFlat(dim, M, faiss.METRIC_INNER_PRODUCT)
index.hnsw.efConstruction = ef_construction
index.hnsw.efSearch = 128  # High-recall query setting

vectors = np.array(disease_vectors).astype('float32')
faiss.normalize_L2(vectors)
index.add(vectors)

# Query
def retrieve_top_k(patient_vector, k=20):
    query = np.array([patient_vector]).astype('float32')
    faiss.normalize_L2(query)
    scores, indices = index.search(query, k)
    return indices[0], scores[0]
```

## 9. Multi-Model Retrieval

The project runs five embedding models in parallel (Chapter 3.2). Each model has its own HNSW index. The Top-20 from each model are unioned, and the union is passed to Stage 3. This multiplies the recall improvement: if each model has 95% recall, the union of five models has recall $\approx 1 - (1 - 0.95)^5 \approx 99.999\%$ (assuming independence, which is approximate but illustrative).

The cost is 5× the encoding time and 5× the index memory — both acceptable for a 10k-disease database.
