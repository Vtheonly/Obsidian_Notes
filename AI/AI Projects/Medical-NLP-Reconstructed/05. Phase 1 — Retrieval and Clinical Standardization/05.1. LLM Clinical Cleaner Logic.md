# 05.1. LLM Clinical Cleaner Logic

Before any vector math runs, the project uses a Large Language Model (Gemini, GPT-4, or equivalent) as a **clinical translator**. The original vault described this step as "send the raw note to an LLM with a medical prompt" but omitted the actual **system prompt**, the **Pydantic output schema**, the **retry logic** for malformed outputs, and the **hallucination backstop** for entities not in the target ontology. Without these, a developer cannot reproduce the pipeline — the LLM Cleaner is the single most prompt-sensitive component in the architecture, and "just call the API" produces unusable output.

This note covers: (1) the input problem, (2) the system prompt template, (3) the Pydantic schema for structured output, (4) the retry-on-failure loop, (5) hallucination detection via ontology lookup, and (6) the integration with the downstream retrieval stage.

---

## 1. The Input Problem

Patient notes arrive in three flavours of messiness:

### 1.1. Verbatim Patient Report

> *"My 4-year-old has had shaky eyes since birth. His hair and skin are very white. He squints in bright light. The doctor mentioned something about albinism but I want a second opinion."*

This is a parent's narrative, full of colloquialisms (*shaky eyes*), temporal information (*since birth*), and meta-commentary (*I want a second opinion*) that should not be extracted.

### 1.2. Doctor's Shorthand

> *"Pt c/o SOB on exertion, PMH of CHF. NKA. Pt started on Lasix 40mg PO daily."*

This is telegraphic, abbreviation-heavy, and syntactically incomplete. Standard NLP parsers cannot handle it.

### 1.3. Mixed Clinical Note

> *"Patient is a 6yo male presenting with nystagmus, hypopigmentation of skin and hair, and photophobia. Father has history of Huntington disease. Patient denies chest pain, SOB, palpitations. Developmental milestones normal."*

This contains negation (*denies chest pain*), family history (*Father has Huntington disease*), and current symptoms — all of which must be correctly tagged with their assertion status.

The LLM Cleaner must extract:
- The **current patient phenotypes** (with `present` assertion).
- The **family-history phenotypes** (tagged for separate reasoning).
- The **negated phenotypes** (to exclude from the patient subgraph).
- The **genes/proteins** mentioned, if any.

And it must output this as **structured, validated JSON** — not free text — so the downstream pipeline can consume it programmatically.

## 2. The System Prompt Template

The system prompt is the single most important engineering artifact in the LLM Cleaner. It must be specific enough to produce consistent output across thousands of notes, yet general enough to handle novel phenotypes. The project's template (below) is the result of several iterations.

```
You are a clinical entity extraction system specialised in rare disease phenotyping.
Your task is to extract phenotypes, genes, and proteins from the input clinical note
and return them as structured JSON.

EXTRACTION RULES:
1. Extract ONLY phenotypes, genes, and proteins explicitly mentioned in the note.
   Do not infer, hallucinate, or "complete" the picture.
2. For each phenotype, determine:
   - The HPO label (use the most specific term that matches the note's wording).
   - The assertion: "present" | "absent" | "family_history" | "historical"
   - The experiencer: "patient" | "family_member" | "other"
   - The temporality: "current" | "historical" | "hypothetical"
   - The certainty: "certain" | "probable" | "possible"
3. Expand all abbreviations using standard medical lexicons.
4. If an abbreviation is ambiguous (e.g., "APC"), use surrounding context to disambiguate.
   If context is insufficient, omit it and do not guess.
5. Negation scope: if "denied" or "no" or "negative for" appears, mark all governed
   phenotypes as "absent", but DO NOT extend the negation past punctuation boundaries.
6. Family history: phenotypes of relatives (parents, siblings) must be tagged with
   experiencer="family_member" and assertion="family_history".

OUTPUT FORMAT:
Return ONLY a JSON object matching this schema. Do not include any prose,
explanations, or markdown fences.

{
  "phenotypes": [
    {
      "label": "Nystagmus",
      "assertion": "present",
      "experiencer": "patient",
      "temporality": "current",
      "certainty": "certain"
    }
  ],
  "genes": ["FBN1"],
  "proteins": ["fibrillin-1"]
}

If the note contains no extractable phenotypes, genes, or proteins, return:
{"phenotypes": [], "genes": [], "proteins": []}

INPUT NOTE:
<<<NOTE>>>
{patient_note}
<<<END NOTE>>>
```

### 2.1. Why Each Rule Matters

- **Rule 1 (no inference)**: The LLM Cleaner must not "complete" the patient picture. If the note says *"shaky eyes"*, the cleaner outputs the label *Nystagmus* — but if the note does not mention *photophobia*, the cleaner must not output it, even though photophobia commonly co-occurs with nystagmus. Inference is the Knowledge Graph's job (Chapter 8.4), not the cleaner's.
- **Rule 4 (ambiguous abbreviations)**: APC, MS, CP, and dozens of other abbreviations have multiple meanings. Guessing produces false positives; omission is recoverable later.
- **Rule 5 (negation scope)**: This is the failure mode documented in Chapter 1.1 §3. The LLM is asked to implement negation scope resolution inline, which it does well because of its implicit syntactic understanding.
- **Rule 6 (family history)**: This is the failure mode documented in Chapter 1.1 §4. Misattributing family history to the patient is one of the most dangerous clinical NLP errors.

### 2.2. Prompt Sensitivity

Even a single-word change to the prompt can shift the output. The project's iterative development found:

- *"Extract phenotypes"* produces 15% more extractions than *"Extract symptoms"*, because the LLM interprets "symptoms" narrowly (subjective complaints) and "phenotypes" broadly (any observable abnormality).
- *"Return JSON"* without "ONLY" produces ~5% of responses wrapped in markdown fences or preceded by *"Here is the JSON:"*.
- The `<<<NOTE>>>` delimiters reduce prompt-injection risk: if the patient note contains text like *"Ignore previous instructions"*, the delimiters make it clear this is data, not a command.

## 3. The Pydantic Output Schema

The output must be validated against a schema before it is trusted. The project uses **Pydantic** (Python data validation library) to enforce the schema:

```python
from pydantic import BaseModel, Field, validator
from typing import Literal
from enum import Enum

class Assertion(str, Enum):
    PRESENT = "present"
    ABSENT = "absent"
    FAMILY_HISTORY = "family_history"
    HISTORICAL = "historical"

class Experiencer(str, Enum):
    PATIENT = "patient"
    FAMILY_MEMBER = "family_member"
    OTHER = "other"

class Temporality(str, Enum):
    CURRENT = "current"
    HISTORICAL = "historical"
    HYPOTHETICAL = "hypothetical"

class Certainty(str, Enum):
    CERTAIN = "certain"
    PROBABLE = "probable"
    POSSIBLE = "possible"

class Phenotype(BaseModel):
    label: str = Field(..., min_length=1, max_length=200)
    assertion: Assertion
    experiencer: Experiencer
    temporality: Temporality
    certainty: Certainty

class ClinicalExtraction(BaseModel):
    phenotypes: list[Phenotype]
    genes: list[str] = Field(default_factory=list)
    proteins: list[str] = Field(default_factory=list)

    @validator("genes", "proteins")
    def normalize_gene_case(cls, v):
        # HGNC convention: uppercase
        return [g.upper().strip() for g in v]
```

### 3.1. Why Pydantic (Not Raw JSON Parsing)

Pydantic provides three guarantees that `json.loads()` does not:

1. **Type checking.** If the LLM returns `"assertion": "yes"` instead of `"assertion": "present"`, Pydantic raises a `ValidationError`. Raw JSON parsing would silently accept the malformed value and propagate it downstream.
2. **Field validation.** The `min_length=1` constraint catches empty-string labels (which LLMs sometimes produce for missing fields).
3. **Custom validators.** The `normalize_gene_case` validator enforces HGNC convention (Chapter 3.5) at parse time, so the downstream pipeline never sees inconsistent casing.

### 3.2. Pydantic vs. Structured Generation (Outlines, Instructor)

Pydantic validates **after** the LLM produces output. An alternative is **structured generation**, which constrains the LLM's decoding to only produce schema-valid tokens. Two libraries implement this:

- **Outlines** (Dottori-Attorre et al., 2024): Builds a finite-state machine from the Pydantic schema and forces the LLM's next-token distribution to only emit tokens that lead to a valid schema completion.
- **Instructor** (Liu, 2023): A Pydantic-friendly wrapper around OpenAI's function-calling API that retries on validation failure.

The project's pipeline uses **Instructor** because it works with OpenAI/Gemini function calling, which is more reliable than free-text generation + regex parsing. If the LLM API does not support function calling, the pipeline falls back to free-text generation + Pydantic validation + retry (§4 below).

## 4. The Retry-on-Failure Loop

Even with structured generation, LLM outputs occasionally fail validation (truncation, schema mismatch, malformed JSON). The pipeline implements a **retry loop with exponential backoff**:

```python
import instructor
from tenacity import retry, stop_after_attempt, wait_exponential
from openai import OpenAI

client = instructor.from_openai(OpenAI())

@retry(
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=1, min=1, max=10),
)
def extract_clinical_entities(patient_note: str) -> ClinicalExtraction:
    try:
        return client.chat.completions.create(
            model="gpt-4o-mini",
            response_model=ClinicalExtraction,
            messages=[
                {"role": "system", "content": SYSTEM_PROMPT},
                {"role": "user", "content": patient_note},
            ],
            temperature=0.0,  # Deterministic (Chapter 6.3)
        )
    except Exception as e:
        # Log the failure for offline analysis
        log_extraction_failure(patient_note, str(e))
        raise
```

### 4.1. Why Three Retries

- **Retry 1**: Catches transient API errors (rate limits, network blips).
- **Retry 2**: Catches the occasional malformed output that the LLM produces non-deterministically even at temperature 0.
- **Retry 3**: Catches edge cases where the note is borderline (e.g., heavy code-switching between languages).

Three retries is a balance — more retries waste API budget; fewer retries leak failures into the pipeline. Failures after 3 retries are logged for manual review and the note is flagged as "extraction failed" rather than silently dropped.

### 4.2. Why Temperature 0.0

Temperature 0.0 makes the LLM deterministic (Chapter 6.3): the same input always produces the same output. This is critical for scientific reproducibility — running the pipeline twice on the same note must produce the same diagnosis. It also makes the retry loop more useful: if retry 1 produces a malformed output, retry 2 (with the same input) is more likely to produce a different (and hopefully valid) output only if there is some non-determinism in the API.

## 5. Hallucination Detection and Ontology Lookup

Even with a perfect prompt and perfect validation, the LLM can produce **hallucinated entities** — labels that sound medical but do not exist in HPO. The pipeline must detect and discard these before they enter the Knowledge Graph.

### 5.1. The Hallucination Backstop

After extraction, each phenotype label is looked up in the HPO dictionary:

```python
def verify_against_hpo(extraction: ClinicalExtraction, hpo_labels: set[str]) -> ClinicalExtraction:
    verified_phenotypes = []
    for pheno in extraction.phenotypes:
        # Exact match
        if pheno.label.lower() in hpo_labels:
            verified_phenotypes.append(pheno)
            continue
        # Fuzzy match (SapBERT embedding similarity > 0.85)
        best_match, score = find_best_hpo_match(pheno.label, threshold=0.85)
        if score >= 0.85:
            pheno.label = best_match  # Replace with canonical HPO label
            verified_phenotypes.append(pheno)
        else:
            log_hallucination(pheno.label, score)
    extraction.phenotypes = verified_phenotypes
    return extraction
```

### 5.2. Three Outcomes per Extracted Phenotype

1. **Exact match**: The LLM's label is in the HPO dictionary. Accept.
2. **Fuzzy match (SapBERT similarity ≥ 0.85)**: The LLM's label is a synonym or near-synonym of an HPO term. Replace with the canonical HPO label and accept.
3. **No match**: The LLM's label is not in HPO and has no close SapBERT neighbour. **Reject** as a hallucination and log for offline review.

The threshold 0.85 was tuned empirically: below 0.80, false positives (unrelated terms being matched) rise sharply; above 0.90, true synonyms (e.g., *shaky eyes* → *Nystagmus*) start being rejected.

### 5.3. Why This Two-Stage Approach

The LLM Cleaner is asked to output HPO labels directly, but LLMs are not perfect HPO lookup tables — they may output a synonym, a related-but-not-identical term, or (rarely) a hallucinated label. The SapBERT fuzzy-match step catches the first two cases and the rejection step catches the third. The combination produces a pipeline that:

- **Recall**: catches synonyms the LLM might use (via SapBERT fuzzy matching).
- **Precision**: rejects hallucinations the LLM might produce (via threshold rejection).
- **Auditability**: every rejection is logged, so the threshold can be tuned over time.

## 6. Integration with the Downstream Retrieval Stage

Once the LLM Cleaner produces a verified `ClinicalExtraction`, the pipeline:

1. **Constructs the patient subgraph.** Each verified phenotype becomes a node in the patient subgraph (Chapter 8), with the assertion/experiencer/temporality stored as edge metadata.
2. **Constructs the cleaned text for embedding.** The verified phenotype labels are joined into a single string: *"Patient exhibits Nystagmus, Hypopigmentation, Photophobia."* This string is what BioBERT encodes for the Stage 2 retrieval.
3. **Stores the raw extraction.** The full `ClinicalExtraction` object (including negated and family-history phenotypes) is stored alongside the patient record for downstream reasoning and audit.

The cleaned text is dramatically shorter and cleaner than the original note, which:

- **Reduces token fragmentation** in BioBERT (Chapter 3.1).
- **Aligns the vocabulary** with the Orphanet definitions (which also use HPO labels).
- **Raises the cosine similarity** from ~0.7 (raw note vs. Orphanet definition) to ~0.9+ (cleaned note vs. Orphanet definition).

This is the mathematical mechanism behind the project's "0.7 → 0.9 shift" — it is not magic, it is the LLM Cleaner producing a string that is lexically closer to the target.
