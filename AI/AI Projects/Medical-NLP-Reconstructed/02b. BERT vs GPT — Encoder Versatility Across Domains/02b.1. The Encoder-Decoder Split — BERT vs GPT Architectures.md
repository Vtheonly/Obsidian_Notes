# 02b.1. The Encoder-Decoder Split — BERT vs GPT Architectures

The original Transformer (Vaswani et al., 2017) was a single architecture with two halves: an **encoder** that read the input bidirectionally, and a **decoder** that generated the output autoregressively. Within two years, the field had split that architecture into two specialised families — **BERT** (encoder-only, Devlin et al., 2018) and **GPT** (decoder-only, Radford et al., 2018) — and this single architectural decision determined the next decade of NLP. BERT became the workhorse of domain-specific NLP (medical, legal, scientific, financial), while GPT became the workhorse of general-purpose generation (ChatGPT, Copilot). This chapter explains the split, the mathematical difference between the two families, and why it matters for the project's architecture.

This chapter is the conceptual bridge between [[02.1. Self-Attention and the QKV Math]] (which introduced the Transformer mechanism) and [[03.2. ClinicalBERT, PubMedBERT, and SapBERT]] (which surveys the medical BERT variants). Without this bridge, the reader knows *how* attention works but not *why* the project chose an encoder (BioBERT) for retrieval and a decoder (Gemini) for generation.

---

## 1. The Original Transformer — Encoder + Decoder

The original Transformer was designed for **sequence-to-sequence** tasks like machine translation: given a French sentence, produce an English sentence. The architecture had two stacks:

```
French input → [Encoder Stack (6 layers)] → encoded representations
                                                        │
                                                        ▼
English output ← [Decoder Stack (6 layers)] ← encoded representations + English-so-far
```

- The **encoder** read the entire French sentence bidirectionally — every token could attend to every other token in both directions. This produced a rich, context-aware representation of the input.
- The **decoder** generated the English sentence autoregressively — each English token could attend to all previously generated English tokens (causal mask) plus all encoded French tokens (cross-attention).

This two-stack design was necessary because translation requires **two different operations**: understanding the input (bidirectional) and generating the output (autoregressive). The encoder and decoder were each specialised for one of these operations.

---

## 2. The Split — BERT Takes the Encoder, GPT Takes the Decoder

In 2018, two papers published within months of each other made a bold bet: **use only half the Transformer**.

### 2.1. BERT — Encoder-Only (Devlin et al., October 2018)

BERT (**B**idirectional **E**ncoder **R**epresentations from **T**ransformers) kept only the encoder stack. The input is read bidirectionally in a single forward pass, and the output is a contextualised embedding for every token. There is no generation step.

- **Architecture**: Transformer encoder, 12 layers (Base) or 24 layers (Large).
- **Attention mask**: Bidirectional — every token attends to every other token.
- **Training objective**: Masked Language Modeling (MLM) + Next Sentence Prediction (NSP).
- **Input**: A single sequence (or two sequences separated by `[SEP]`).
- **Output**: A contextualised embedding per token, with the `[CLS]` token's embedding serving as the sentence-level representation.

### 2.2. GPT — Decoder-Only (Radford et al., June 2018)

GPT (**G**enerative **P**re-trained **T**ransformer) kept only the decoder stack. The model reads the input left-to-right and predicts the next token, then the next, then the next — autoregressively. There is no bidirectional encoding step.

- **Architecture**: Transformer decoder, 12 layers (GPT-1) to 96 layers (GPT-3).
- **Attention mask**: Causal (lower-triangular) — token $i$ attends only to tokens $\leq i$.
- **Training objective**: Next-token prediction (autoregressive language modeling).
- **Input**: A single sequence (the prompt + generated-so-far).
- **Output**: A probability distribution over the vocabulary for the next token.

### 2.3. The Mathematical Difference — One Mask

The entire architectural difference between BERT and GPT reduces to **one matrix**: the attention mask. Recall from [[02.1. Self-Attention and the QKV Math]] §5 that the attention computation is:

$$\text{Attention}(Q, K, V, M) = \text{softmax}\!\left(\frac{Q K^\top}{\sqrt{d_k}} + M\right) V$$

The mask $M$ is what differs:

- **BERT (bidirectional mask)**: $M_{ij} = 0$ for all real tokens $j$ (and $-\infty$ for padding). Every token sees every other token.
- **GPT (causal mask)**: $M_{ij} = 0$ if $j \leq i$, $-\infty$ if $j > i$. Each token sees only the past and present, never the future.

This single difference cascades into everything else: the training objective, the kind of tasks each model is good at, the inference speed, the fine-tuning paradigm, and — most importantly for this chapter — the versatility across domains.

---

## 3. Why the Mask Determines Everything

### 3.1. Bidirectional Attention → Rich Embeddings

BERT's bidirectional mask means the representation of token $i$ is computed using information from **every** token in the sequence, including tokens that come after $i$. This produces a **holistic** representation: the vector for *"bank"* in *"the river bank was muddy"* incorporates information from *"river"* and *"muddy"* to disambiguate the sense.

This holistic representation is what makes BERT embeddings useful for **understanding** tasks:

- **Classification**: Is this review positive or negative?
- **NER**: Which tokens in this sentence are gene names?
- **Retrieval**: Does this patient note match this disease definition?
- **Question answering**: What is the answer to this question, given this context?

All of these require understanding the full input, which bidirectional attention enables.

### 3.2. Causal Attention → Generation

GPT's causal mask means the representation of token $i$ is computed using only tokens $\leq i$. This is **necessary** for generation: when generating token $i+1$, the model cannot peek at token $i+1$ (which has not been generated yet). The causal mask enforces this.

The cost is that GPT's representations are **less rich** for understanding tasks. The vector for *"bank"* in *"the river bank"* (generated left-to-right) does not yet know about *"muddy"* (which comes later). GPT can still disambiguate, but it must do so using only the left context, which is harder.

### 3.3. The Tradeoff

| Property | BERT (Bidirectional) | GPT (Causal) |
| :--- | :--- | :--- |
| Understanding tasks | **Strong** | Weaker |
| Generation tasks | Impossible (no generation) | **Strong** |
| Embedding quality | **High** | Moderate |
| Inference (single pass) | Fast (one forward pass) | N/A |
| Inference (generation) | N/A | Slow (autoregressive, $O(N)$ passes) |
| Fine-tuning paradigm | Task-specific head + fine-tune | Prompt engineering / few-shot |
| Training objective | MLM (fill in blanks) | Next-token prediction |
| Best for | Classification, NER, retrieval, embeddings | Generation, dialogue, code, creative writing |

The two families are **complementary**, not competitive. The project uses both: BERT (BioBERT) for understanding (retrieval) and GPT (Gemini) for generation (cleaning). Chapter 06.1 explains this hybrid in detail.

## 4. The Pre-Training Objectives — MLM vs. Next-Token Prediction

The architectural difference (bidirectional vs. causal) forces different training objectives.

### 4.1. BERT — Masked Language Modeling (MLM)

Because BERT can see the full sequence, it cannot be trained on next-token prediction (that would be trivially easy — the next token is in the input). Instead, BERT is trained on **Masked Language Modeling**: randomly mask 15% of tokens, and predict them from the surrounding context.

$$\mathcal{L}_{\text{MLM}} = -\sum_{i \in \text{masked}} \log P(x_i \mid x_{\setminus i})$$

This objective forces BERT to learn **deep semantic understanding**: to predict a masked token, the model must understand the surrounding context. The resulting embeddings are rich and transferable to downstream tasks.

### 4.2. GPT — Next-Token Prediction

Because GPT can only see the past, it is naturally trained on **next-token prediction**: given tokens $1, \dots, i$, predict token $i+1$.

$$\mathcal{L}_{\text{NTP}} = -\sum_{i=1}^{N} \log P(x_i \mid x_{<i})$$

This objective forces GPT to learn **generation**: the model must produce a coherent continuation. The resulting model is a powerful generator but a weaker embedder.

### 4.3. Why MLM Produces Better Embeddings

MLM is a **harder** objective than next-token prediction for producing rich representations. To predict a masked token in the *middle* of a sentence, the model must use both the left and right context, which forces it to learn bidirectional relationships. Next-token prediction only requires the left context, so the model can get away with shallower representations.

Empirically, BERT embeddings outperform GPT embeddings on sentence-similarity and classification benchmarks by 5–15 points (Reimers & Gurevych, 2019). This is the embedding-quality advantage that motivates the project's use of BioBERT (not GPT) for retrieval.

## 5. The Scale Difference — Why GPT Grew, BERT Didn't

A natural question: if BERT is better for understanding, why did GPT scale to 175 billion parameters (GPT-3) and beyond, while BERT stayed at 110 million (BERT-Base) to 340 million (BERT-Large)?

### 5.1. Generation Rewards Scale

GPT's generation capability improves **dramatically** with scale. GPT-1 (117M parameters) could barely produce coherent paragraphs; GPT-3 (175B) produces fluent essays; GPT-4 (estimated >1T) produces expert-level reasoning. The scaling laws (Kaplan et al., 2020) show that generation quality improves as a power law of parameter count.

### 5.2. Understanding Plateaus Earlier

BERT's understanding capability improves more slowly with scale. BERT-Base (110M) already achieves >90% on most GLUE benchmarks; BERT-Large (340M) adds only a few points. The marginal return on parameters is much smaller for understanding tasks than for generation.

### 5.3. The Economic Consequence

Because GPT rewards scale, OpenAI invested billions in training ever-larger GPT models. Because BERT plateaus, the community invested in **domain-specific variants** instead — BioBERT, SciBERT, LegalBERT, FinBERT, etc. Each domain variant is still ~110–340M parameters, but trained on domain-specific text. This is why there are dozens of BERT variants across many fields and relatively few domain-specific GPT variants (the general GPT-4 is "good enough" for most domains via prompting).

This economic dynamic is the topic of [[02b.3. The BERT Family Tree — Variants Across Domains]].

## 6. The Fine-Tuning Paradigm Difference

### 6.1. BERT — Fine-tune with a Task Head

BERT is designed to be **fine-tuned** for each downstream task. The standard recipe:

1. Take pre-trained BERT.
2. Add a small task-specific head (a linear layer for classification, a token-level classifier for NER, a span predictor for QA).
3. Fine-tune the entire model (BERT + head) on the task's labeled data for a few epochs.

This produces a **specialised** model for each task. The fine-tuning is cheap (a few hours on a single GPU) because BERT's pre-trained weights already encode most of the needed knowledge.

### 6.2. GPT — Prompt Engineering / Few-Shot

GPT (especially GPT-3+) is designed to be used **without fine-tuning**, via prompt engineering. Instead of adding a task head and fine-tuning, you craft a prompt that describes the task, and the model generates the answer.

```
Prompt: "Classify the sentiment of this review as positive or negative.
Review: 'The food was terrible.'
Sentiment:"
GPT-3 output: "negative"
```

This **zero-shot** or **few-shot** paradigm is powerful because it requires no labeled data and no fine-tuning. The tradeoff is that GPT is less accurate than a fine-tuned BERT on most understanding tasks (a fine-tuned BERT typically beats few-shot GPT-3 by 5–10 points on classification benchmarks).

### 6.3. Why the Project Uses Both Paradigms

The project uses:

- **BERT (BioBERT)** for retrieval, where fine-tuning produces the best embeddings and the task is repeated millions of times (so the fine-tuning cost is amortised).
- **GPT (Gemini)** for the LLM Cleaner, where the task is generation (produce JSON from free text) and few-shot prompting is sufficient (no fine-tuning needed, and the task evolves as the prompt is refined).

This is the architectural rationale for the hybrid: each paradigm is assigned the task it is best at.

## 7. Summary — The Architectural Decision Tree

```
Do you need to GENERATE text?
├── Yes → GPT family (decoder-only, causal mask, next-token prediction)
│         Examples: ChatGPT, Gemini, LLaMA, Claude
│         Project use: LLM Clinical Cleaner (Stage 1)
│
└── No → Do you need to UNDERSTAND text?
    ├── Yes → BERT family (encoder-only, bidirectional mask, MLM)
    │         Examples: BERT, BioBERT, PubMedBERT, SciBERT, LegalBERT
    │         Project use: Retrieval + entity linking (Stages 2, 3)
    │
    └── You need both → T5 / BART (encoder-decoder)
                        Examples: T5, BART, mT5
                        Project use: Not used (the project splits the two tasks
                                     across separate BERT and GPT models instead)
```

The project's architecture (BERT for understanding, GPT for generation) is the standard production pattern. The encoder-decoder alternative (T5) would combine both in one model but at the cost of higher complexity and lower embedding quality than a dedicated BERT.

## 8. Why This Matters for the Rest of the Vault

Every subsequent chapter assumes this architectural split:

- **Chapter 03** (Multi-Embedding Strategy) surveys five BERT variants — all encoders, all trained with MLM, all producing embeddings. None of them is a GPT.
- **Chapter 05** (Retrieval) uses BioBERT embeddings for cosine similarity — this only works because BioBERT is an encoder producing holistic sentence vectors.
- **Chapter 06** (Entity Extraction) uses Gemini (a decoder) for generation — this is necessary because the Cleaner must produce JSON output, which BERT cannot do.
- **Chapter 09** (Neural Ranker) trains a small MLP on BERT embeddings — the embeddings are the input, and their quality (which comes from BERT's bidirectional architecture) determines the ranker's accuracy.

If the project had used GPT embeddings instead of BERT embeddings, the retrieval accuracy would drop by 5–15 points. If it had used BERT for generation instead of GPT, it could not generate the JSON output at all. The architectural split is not a stylistic choice — it is a functional necessity.
