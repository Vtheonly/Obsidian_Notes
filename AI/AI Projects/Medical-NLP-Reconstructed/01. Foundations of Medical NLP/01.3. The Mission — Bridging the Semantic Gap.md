# 01.3. The Mission — Bridging the Semantic Gap

The **Unified Medical Knowledge Architecture** is, at its core, a **clinical bridge**. It accepts "messy human talk" — a parent describing a child's symptoms in everyday language — and produces "rigid scientific truth": a ranked list of Orphanet disease identifiers, each backed by a verifiable biological path through an ontology. The reason this requires a four-stage pipeline rather than a single end-to-end model is that each stage resolves a different category of failure documented in [[01.1. The Medical Text Problem]] and [[01.2. The Evolution of NLP Vectors]].

This note is the architectural map for the entire vault. Every later chapter zooms into one box of the diagram below.

---

## 1. The Semantic Gap

There is a structural mismatch between how patients (and often how doctors) describe symptoms and how medical databases store them:

- **Patient Talk**: *"My kid's eyes keep shaking and his skin is very pale."*
- **Clinical Record**: *"Patient exhibits spontaneous nystagmus and oculocutaneous hypopigmentation."*
- **Ontology**: `HP:0000639` (Nystagmus) and `HP:0001010` (Hypopigmentation).

The distance between these three layers is the **Semantic Gap**. A pure keyword search cannot bridge it (the words are different). A pure embedding model can partially bridge it (cosine similarity > 0) but cannot guarantee biological truth — embeddings capture "vibes," not facts. The bridge must combine both: embeddings for retrieval, ontologies for verification.

## 2. The Four-Stage Pipeline

```
┌─────────────────────────────────────────────────────────────────────┐
│  RAW PATIENT NOTE                                                   │
│  "Kid has shaky eyes and white eyelashes. Skin is very pale."       │
└──────────────────────────────────┬──────────────────────────────────┘
                                   │
                                   ▼
┌─────────────────────────────────────────────────────────────────────┐
│  STAGE 1 — LLM Clinical Cleaner  (Chapter 5.1, Chapter 6)           │
│  - Expand abbreviations (UMLS SPECIALIST Lexicon)                   │
│  - Resolve negation scope, temporality, experiencer (4-D assertion) │
│  - Extract phenotypes/genes/proteins as Pydantic-validated JSON     │
│  Output: [{"phenotype": "HP:0000639", "assertion": "present"},     │
│           {"phenotype": "HP:0001010", "assertion": "present"}]      │
└──────────────────────────────────┬──────────────────────────────────┘
                                   │
                                   ▼
┌─────────────────────────────────────────────────────────────────────┐
│  STAGE 2 — Phase 1 Retrieval  (Chapter 4, Chapter 5.2)              │
│  - Encode cleaned note with BioBERT/SapBERT (768-D vectors)         │
│  - Top-K cosine search against 10k Orphanet disease vectors         │
│  - FAISS HNSW index for sub-millisecond retrieval                   │
│  Output: Top-20 candidate OrphaIDs with cosine scores               │
└──────────────────────────────────┬──────────────────────────────────┘
                                   │
                                   ▼
┌─────────────────────────────────────────────────────────────────────┐
│  STAGE 3 — Knowledge Graph Verification  (Chapter 7, Chapter 8)     │
│  - Build patient subgraph from extracted HPO IDs                    │
│  - Look up each Top-20 candidate's full HPO profile                 │
│  - Compute hierarchical similarity (Resnik/Lin, not flat Jaccard)   │
│  - Down-weight hub nodes (Fever, Pain) via IDF                      │
│  Output: Verified Top-20 with biological evidence paths             │
└──────────────────────────────────┬──────────────────────────────────┘
                                   │
                                   ▼
┌─────────────────────────────────────────────────────────────────────┐
│  STAGE 4 — Phase 2 Neural Pairwise Ranking  (Chapter 9)             │
│  - All-pairs tournament among Top-20 (PyTorch MLP ranker)           │
│  - Bradley-Terry / Copeland to resolve non-transitive cycles        │
│  - BCE-trained interaction features (vector diff + Hadamard)        │
│  Output: Final ranked list, Rank #1 = definitive diagnosis          │
└──────────────────────────────────┬──────────────────────────────────┘
                                   │
                                   ▼
┌─────────────────────────────────────────────────────────────────────┐
│  STAGE 5 — Statistical Validation  (Chapter 10)                     │
│  - Mann-Whitney U-test vs. baseline (p < 0.05)                      │
│  - NDCG + MRR + Top-K Accuracy with 95% confidence intervals        │
│  - Seaborn visualisation with error bars                           │
│  Output: Defensible scientific evidence for jury / publication      │
└─────────────────────────────────────────────────────────────────────┘
```

Each stage's output is the next stage's input. Each stage also constrains the next stage's search space — Stage 2 narrows 10,000 candidates to 20, Stage 3 narrows 20 to a verified subset, Stage 4 orders that subset. This funnel is what makes the system tractable: a single end-to-end model cannot operate over 10,000 diseases, but a two-stage retrieve-then-rank pipeline can.

## 3. Why This Architecture Wins (The Three-Layer Principle)

The pipeline combines three fundamentally different paradigms of AI:

### 3.1. Connectionist AI (Stages 1, 2, 4)
Neural networks — LLMs and BioBERT — handle **pattern recognition at scale**. They can read a free-text note and produce a vector; they can compare two vectors and produce a similarity; they can be trained to compare two candidates and produce a preference. They are good at "vibes" and bad at "facts."

### 3.2. Symbolic AI (Stage 3)
The Knowledge Graph is a discrete, logical structure. Each node is an ontology ID; each edge is a typed predicate; each path is verifiable against the source literature. The graph cannot "hallucinate" — every fact in it was inserted explicitly from HPO, MONDO, Orphanet, or UniProt. It is good at "facts" and bad at "vibes."

### 3.3. Supervised AI (Stage 4)
The Neural Ranker is a small supervised model trained on labeled pairs (correct disease, wrong disease). It learns the *specific* boundary that separates true matches from plausible mimics in this domain — a boundary that cosine similarity cannot compute because it is not linear. This is the only layer that learns from project-specific ground truth.

### 3.4. Why All Three Are Required

- **Connectionist alone** (pure LLM or pure BioBERT) hallucinates and is non-deterministic.
- **Symbolic alone** (pure Knowledge Graph) cannot ingest free-text notes — it needs the entities extracted first.
- **Supervised alone** cannot scale to 10,000 candidates; it needs a retrieve-then-rank funnel.

The combination is what gives the system its three clinically-mandatory properties:

1. **Explainability** — every diagnosis can be traced back through the Knowledge Graph path (Stage 3 output), so the doctor sees *why* the system recommended it.
2. **Determinism** — temperature-0 LLM, fixed BioBERT weights, deterministic tournament, fixed statistical test. Run the same note twice, get the same diagnosis.
3. **Interoperability** — every entity is a URI/HPO/MONDO ID, so the graph can plug into any other medical database on the Semantic Web.

## 4. The Patient-Level Pipeline Walk-Through

To make this concrete, here is what happens to one real patient note:

> **Note**: "My 4-year-old has had shaky eyes since birth. His hair and skin are very white. He squints in bright light."

| Stage | Input | Output |
| :--- | :--- | :--- |
| 1. LLM Cleaner | Raw note | `[{"HP:0000639", "Nystagmus", "present", "patient", "current"}, {"HP:0001012", "Hypopigmentation of skin", "present", "patient", "current"}, {"HP:0001022", "Albinism", "present", "patient", "current"}, {"HP:0000572", "Photophobia", "present", "patient", "current"}]` |
| 2. Phase 1 Retrieval | Patient vector | Top-20 OrphaIDs ranked by cosine: `Orpha:92 (0.94), Orpha:794 (0.92), Orpha:3526 (0.91), …` |
| 3. KG Verification | Patient subgraph | Resnik-similarity check: `Orpha:92` shares 4 phenotypes hierarchically; `Orpha:794` shares 2; `Orpha:3526` shares 1. Hub-node down-weighting applied. |
| 4. Phase 2 Tournament | Top-20 verified | All-pairs MLP tournament: `Orpha:92` wins 18/19 matches. Final Rank #1. |
| 5. Validation | Final ranking | MRR = 1.0 for this case; Mann-Whitney p < 0.001 across the full test set vs. baseline. |

The output the doctor sees is:

```
Rank 1: Orpha:92 — Oculocutaneous Albinism Type 1A   (confidence: 0.94)
        Evidence path: HP:0000639 + HP:0001012 + HP:0001022 + HP:0000572
        → all four are direct descendants of HP:0000479 (Abnormality of the eye)
        → all four are listed as HP:0000639 in Orpha:92's HPO profile

Rank 2: Orpha:794 — Oculocutaneous Albinism Type 2   (confidence: 0.87)
        Evidence path: ... (fewer matching phenotypes)
```

Every claim is traceable. The doctor can audit the path, agree or disagree, and the system never produces a confident-sounding answer without a verifiable biological justification.

## 5. What This Architecture Does NOT Claim

For scientific honesty, the boundaries of the system must be stated:

- **It is a decision-support tool, not a diagnostic oracle.** The doctor is the final decision-maker; the system surfaces and ranks candidates.
- **It only works for diseases present in Orphanet/MONDO.** A truly novel disease cannot be diagnosed — the system would rank its closest neighbours and flag low confidence.
- **Its recall is bounded by Stage 1.** If the LLM Cleaner fails to extract a critical phenotype (e.g., misses a developmental delay because the note was vague), no later stage can recover it. This is why Stage 1 prioritises recall over precision (Chapter 6.5).
- **It is only as current as the ontology versions loaded.** Deprecated HPO IDs must be mapped to current ones (Chapter 7.2), and the system must be re-indexed when ontologies update.

These limitations are addressed in the relevant chapters; they are noted here so the reader understands the design tradeoffs from the outset.
