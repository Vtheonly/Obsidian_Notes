# 07.3. Semantic Normalization

This note covers the **bridge** from messy text to clean ontology IDs — a process called **semantic normalization**. The original vault described a two-stage solution (LLM translation + dictionary matching) but completely omitted the **abbreviation expansion** step that must happen before the LLM sees the text, the **UMLS SPECIALIST Lexicon** that powers it, and the **word-sense disambiguation** logic that resolves ambiguous abbreviations. Without these, the LLM Cleaner receives raw clinical shorthand (`Pt c/o SOB, PMH of CHF`) and produces garbage because it cannot reliably expand the abbreviations.

This note covers: (1) the semantic gap, (2) the three-stage normalization pipeline, (3) abbreviation expansion via the SPECIALIST Lexicon, (4) word-sense disambiguation for clinical homonyms, (5) the LLM translation stage, and (6) dictionary matching to ontology IDs.

---

## 1. The Semantic Gap

There are three levels of representation for any clinical concept:

- **Patient Talk**: *"My eyes won't stop shaking when I look at things."*
- **Clinical Record**: *"Patient exhibits spontaneous nystagmus."*
- **Ontology ID**: `HP:0000639` (Nystagmus).

The distance between these levels is the **Semantic Gap**. If the AI only looks for the exact string "Nystagmus," it fails to help the patient who says "shaking eyes." If it only uses embeddings (cosine similarity), it produces a fuzzy match (0.91) that is not a confirmed link.

Semantic normalization is the process of bridging all three levels: from patient talk to clinical record (via the LLM), and from clinical record to ontology ID (via dictionary matching). The first stage is approximate; the second is exact. The combination produces a confirmed, auditable link.

---

## 2. The Three-Stage Normalization Pipeline

The original vault described two stages (LLM translation + dictionary matching). The corrected pipeline has **three** stages, because abbreviation expansion must happen before the LLM sees the text:

```
Raw patient note
    │
    ▼
[Stage 1: Abbreviation Expansion + WSD]
    │  (SPECIALIST Lexicon, contextual disambiguation)
    ▼
Expanded note: "Patient complains of shortness of breath on exertion."
    │
    ▼
[Stage 2: LLM Translation]
    │  (Gemini/GPT, temperature 0, Pydantic-validated JSON output)
    ▼
Cleaned extraction: {"phenotype": "Dyspnea", "assertion": "present"}
    │
    ▼
[Stage 3: Dictionary Matching]
    │  (Exact HPO lookup + SapBERT fuzzy match fallback)
    ▼
Ontology ID: HP:0002093 (Dyspnea)
```

Each stage is necessary:

- **Stage 1** expands abbreviations so the LLM sees clean text. Without it, `SOB` may be misinterpreted by the LLM (it could mean *shortness of breath* or *son of a b*****, and the LLM may pick the wrong one.
- **Stage 2** translates colloquial language to formal clinical terminology. The LLM is the only component capable of understanding that *"shaky eyes"* = *Nystagmus*.
- **Stage 3** maps the clinical term to the ontology ID. This is exact (or fuzzy via SapBERT), and it is the step that produces the "hard fact" for the Knowledge Graph.

---

## 3. Abbreviation Expansion via the SPECIALIST Lexicon

The **UMLS SPECIALIST Lexicon** (Chapter 3.6 §2.3) is the canonical source of abbreviation expansions in clinical NLP. For each abbreviation, it lists:

- The full expansion(s).
- The syntactic category (noun, verb, etc.).
- The source vocabulary (MeSH, SNOMED-CT, etc.).

### 3.1. The Abbreviation Table

A subset of the project's abbreviation table (curated from SPECIALIST + project-specific additions):

| Abbreviation | Expansion | Notes |
| :--- | :--- | :--- |
| `SOB` | Shortness of breath | → HPO `HP:0002093` (Dyspnea) |
| `PMH` | Past medical history | (Not a phenotype; used for assertion tagging) |
| `CHF` | Congestive heart failure | → HPO `HP:0001635` (CHF) |
| `NKA` | No known allergies | (Not a phenotype) |
| `Pt` | Patient | (Not a phenotype) |
| `c/o` | Complains of | (Verb; used for assertion = present) |
| `APC` | Adenomatous Polyposis Coli (gene) **or** Activated Protein C (protein) **or** Argon Plasma Coagulation (procedure) | **Ambiguous; requires WSD** |
| `MS` | Multiple Sclerosis **or** Mitral Stenosis **or** Morphine Sulfate | **Ambiguous; requires WSD** |
| `CP` | Chest Pain **or** Cerebral Palsy **or** Cricoid Pressure | **Ambiguous; requires WSD** |

### 3.2. The Expansion Algorithm

```python
def expand_abbreviations(note, abbreviation_table):
    tokens = tokenize(note)
    expanded_tokens = []
    for token in tokens:
        if token in abbreviation_table:
            entry = abbreviation_table[token]
            if entry.is_unambiguous:
                expanded_tokens.append(entry.expansion)
            else:
                # Ambiguous; defer to WSD stage
                expanded_tokens.append(("AMBIGUOUS", token, entry.candidates))
        else:
            expanded_tokens.append(token)
    return expanded_tokens
```

Unambiguous abbreviations are expanded inline. Ambiguous abbreviations are flagged for the WSD stage.

## 4. Word-Sense Disambiguation (WSD) for Clinical Homonyms

The original vault assumed the LLM resolves all homonyms. This is too optimistic — LLMs make WSD errors, and the pipeline needs an explicit backstop. The project uses a **two-stage WSD** approach:

### 4.1. Stage 1: LLM-Driven Expansion

The LLM Cleaner's system prompt (Chapter 5.1 §2) includes the rule:

> *"Expand all abbreviations using standard medical lexicons. If an abbreviation is ambiguous (e.g., 'APC'), use surrounding context to disambiguate. If context is insufficient, omit it and do not guess."*

The LLM, with its implicit understanding of context, usually picks the right expansion:

- *"Patient with APC mutation"* → *Adenomatous Polyposis Coli* (gene context)
- *"APC level is low"* → *Activated Protein C* (protein context)
- *"APC performed to stop bleeding"* → *Argon Plasma Coagulation* (procedure context)

### 4.2. Stage 2: Lexical Backstop

For abbreviations the LLM flags as ambiguous (or omits), the pipeline consults the SPECIALIST Lexicon and scores candidate expansions by co-occurrence with surrounding tokens:

```python
def wsd_backstop(ambiguous_token, context_tokens, candidates):
    scores = {}
    for expansion in candidates:
        # Score = sum of PMI(expansion, context_token) over context tokens
        score = sum(pmi(expansion, ct) for ct in context_tokens)
        scores[expansion] = score
    best = max(scores, key=scores.get)
    if scores[best] > AMBIGUITY_THRESHOLD:
        return best
    else:
        return None  # Surface for human review
```

The PMI (Pointwise Mutual Information) is computed from a corpus of clinical text:

$$\text{PMI}(w_1, w_2) = \log \frac{P(w_1, w_2)}{P(w_1) P(w_2)}$$

High PMI between a candidate expansion and a context token means they co-occur more often than chance, which is evidence that the expansion is correct in this context.

### 4.3. Why Two Stages

The LLM is good at WSD but not perfect. The lexical backstop catches the LLM's mistakes and provides an auditable score (the PMI) that a human reviewer can inspect. Two stages are necessary because:

- **Stage 1 (LLM)** handles novel abbreviations not in the lexicon.
- **Stage 2 (Lexicon)** handles abbreviations the LLM mis-disambiguates.

Neither stage alone is sufficient; the combination produces ~95% WSD accuracy on the project's test set.

## 5. The LLM Translation Stage

After abbreviation expansion and WSD, the cleaned text is passed to the LLM Cleaner (Chapter 5.1). The LLM:

1. Reads the expanded note.
2. Extracts phenotypes, genes, and proteins.
3. Tags each with assertion, experiencer, temporality, certainty (Chapter 1.1 §4).
4. Outputs a Pydantic-validated `ClinicalExtraction` object.

The output is in **formal clinical terminology** — *Nystagmus* instead of *shaky eyes*, *Dyspnea* instead of *shortness of breath*, *Hypopigmentation* instead of *very pale skin*. This is the "translation" that the original vault described.

### 5.1. Why the LLM Is the Right Tool for This Stage

- **Synonym normalisation** requires understanding that *shaky eyes* and *Nystagmus* refer to the same concept. This is a semantic judgement, not a lexical one, and LLMs are uniquely good at it.
- **Assertion tagging** requires understanding the syntax of negation, family history, and temporality. This is a syntactic judgement, which LLMs also handle well.
- **Context-dependent extraction** requires understanding that *"the patient feels down"* should not extract *Down syndrome*. This is a contextual judgement, which LLMs handle better than rule-based systems.

The LLM is the only component in the pipeline that can perform all three judgements in a single pass.

## 6. Dictionary Matching to Ontology IDs

The LLM's output is in clinical terminology but not yet in ontology IDs. The final stage is **dictionary matching**: looking up each extracted phenotype label in the HPO dictionary.

### 6.1. Exact Match

```python
def exact_hpo_match(label, hpo_labels):
    """Return the HPO ID for the label, or None."""
    canonical = label.lower().strip()
    return hpo_labels.get(canonical)
```

If the LLM outputs *Nystagmus* and the HPO dictionary contains *Nystagmus* → `HP:0000639`, the exact match returns the ID.

### 6.2. Fuzzy Match (SapBERT)

If the exact match fails (e.g., the LLM outputs *involuntary eye movements* instead of *Nystagmus*), the pipeline uses SapBERT (Chapter 3.2) to find the closest HPO label:

```python
def fuzzy_hpo_match(label, sapbert_model, hpo_label_embeddings, threshold=0.85):
    label_vec = sapbert_model.encode(label)
    similarities = cosine_similarity(label_vec, hpo_label_embeddings)
    best_idx = np.argmax(similarities)
    best_score = similarities[best_idx]
    if best_score >= threshold:
        return hpo_ids[best_idx], best_score
    return None, best_score
```

The threshold 0.85 was tuned empirically (Chapter 5.1 §5). Above the threshold, the match is accepted; below, the label is rejected as a hallucination.

### 6.3. Why Two-Stage Matching

- **Exact match** is fast (hash lookup) and 100% precise. It handles the common case where the LLM outputs a canonical HPO label.
- **Fuzzy match** is slower (one SapBERT encoding + similarity search) but handles synonyms and near-synonyms. It is the fallback for the ~20% of cases where the exact match fails.

The combination produces ~98% coverage (only 2% of extracted labels fail both stages and are rejected as hallucinations).

## 7. The Complete Normalization Walkthrough

Input note:

> *"Pt c/o SOB on exertion. PMH of CHF. Father has Huntington disease. Pt has shaky eyes since birth."*

Stage 1 (Abbreviation Expansion + WSD):

> *"Patient complains of shortness of breath on exertion. Past medical history of congestive heart failure. Father has Huntington disease. Patient has shaky eyes since birth."*

Stage 2 (LLM Translation):

```json
{
  "phenotypes": [
    {"label": "Dyspnea", "assertion": "present", "experiencer": "patient", "temporality": "current", "certainty": "certain"},
    {"label": "Congestive heart failure", "assertion": "historical", "experiencer": "patient", "temporality": "historical", "certainty": "certain"},
    {"label": "Huntington disease", "assertion": "family_history", "experiencer": "family_member", "temporality": "current", "certainty": "certain"},
    {"label": "Nystagmus", "assertion": "present", "experiencer": "patient", "temporality": "current", "certainty": "certain"}
  ],
  "genes": ["HTT"],
  "proteins": []
}
```

Stage 3 (Dictionary Matching):

| LLM Label | Match Type | HPO/MONDO ID |
| :--- | :--- | :--- |
| Dyspnea | Exact | `HP:0002093` |
| Congestive heart failure | Exact | `HP:0001635` |
| Huntington disease | Exact | `MONDO:0007739` |
| Nystagmus | Exact | `HP:0000639` |

Output: a verified `ClinicalExtraction` object with HPO/MONDO IDs, ready for the Knowledge Graph.

Note that:

- The **assertion tagging** correctly marks *CHF* as `historical` (it is in the PMH) and *Huntington disease* as `family_history` (the father has it, not the patient).
- The **experiencer tagging** correctly attributes *Huntington disease* to `family_member`, not `patient`.
- The **abbreviation expansion** correctly expanded `Pt`, `c/o`, `SOB`, `PMH`, `CHF`.
- The **LLM translation** correctly normalised *shaky eyes* → *Nystagmus*.

This is the full semantic normalization pipeline: from messy clinical shorthand to verified ontology IDs, with auditable intermediate steps.

## 8. Why This Is Superior to Pure NLP

The original vault's framing — "BioBERT says *this sounds like Nystagmus (0.91)*; normalization says *this IS HP:0000639 (confirmed)*" — is correct in spirit. The deeper point is that **normalization converts a probabilistic embedding match into a deterministic graph link**:

- **Without normalization**: The patient note's BioBERT vector has cosine 0.91 with the Nystagmus definition's vector. This is a probability, not a fact. It can be wrong (anisotropy, vocabulary mismatch, etc.).
- **With normalization**: The patient note contains the string "Nystagmus" (after LLM cleaning), which exactly matches HPO `HP:0000639`. This is a deterministic lookup. It cannot be wrong (assuming the LLM did not hallucinate, which is checked by the ontology backstop).

The Knowledge Graph (Chapter 8) operates on these deterministic links, not on cosine similarities. This is what makes the system auditable and explainable — every graph edge can be traced back to a specific string in the patient note, which was matched to a specific ontology ID by a specific (exact or fuzzy) lookup.
