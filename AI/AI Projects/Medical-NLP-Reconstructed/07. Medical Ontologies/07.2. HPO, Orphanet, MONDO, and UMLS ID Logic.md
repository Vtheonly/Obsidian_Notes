# 07.2. HPO, Orphanet, MONDO, and UMLS ID Logic

The original vault treated ontology IDs (`HP:XXXXXXX`, `Orpha:XXXX`, `MONDO:XXXX`) as **static, permanent values**. This is dangerously wrong. Medical ontologies are **versioned**: IDs are routinely merged, split, deprecated, and re-assigned. A production system that does not handle versioning will silently break when the ontology is updated, producing wrong diagnoses on patient records that contain deprecated IDs. The original vault also did not explain the **cross-ontology mapping** that MONDO and UMLS provide, leaving the reader unable to ingest multi-hospital datasets that use conflicting codes.

This note covers: (1) the three core ontologies (HPO, Orphanet, MONDO), (2) why IDs (not strings) are used, (3) ontology versioning and concept drift, (4) deprecation and `owl:sameAs` mapping, (5) cross-ontology mapping via MONDO and UMLS CUIs, and (6) the project's versioning strategy.

---

## 1. The Three Core Ontologies

### 1.1. HPO (Human Phenotype Ontology) — Symptoms

- **Purpose**: The dictionary of **phenotypes** (clinical signs and symptoms).
- **Format**: `HP:XXXXXXX` (7-digit zero-padded).
- **Examples**:
  - `HP:0000639` — Nystagmus
  - `HP:0001022` — Albinism
  - `HP:0002093` — Dyspnea
- **Size**: ~17,000 phenotypic abnormality terms, organised as a DAG (Chapter 7.1).
- **Maintainer**: The HPO Consortium (Robinson et al.).
- **Project role**: Used to label the phenotypes extracted by the LLM Cleaner. The patient subgraph is built from HPO IDs.

### 1.2. Orphanet — Rare Diseases

- **Purpose**: The global authority on **rare diseases**.
- **Format**: `Orpha:XXXX` (1–6 digit, no zero-padding).
- **Examples**:
  - `Orpha:92` — Oculocutaneous Albinism Type 1
  - `Orpha:558` — Marfan Syndrome
  - `Orpha:399` — Huntington Disease
- **Size**: ~6,000 rare disease entries.
- **Maintainer**: Orphanet (French INSERM).
- **Project role**: The "anchor nodes" in the Knowledge Graph. Each Orpha ID links a disease to its phenotypes, genes, and proteins.

### 1.3. MONDO (Mondo Disease Ontology) — The Bridge

- **Purpose**: An "ontology of ontologies" that merges Orphanet, OMIM, ICD-10, ICD-11, SNOMED-CT, MeSH, and other disease vocabularies into a single unified hierarchy.
- **Format**: `MONDO:XXXXXXX` (7-digit zero-padded).
- **Examples**:
  - `MONDO:0008754` — Oculocutaneous Albinism Type 1 (cross-references `Orpha:92`, `OMIM:203100`, `ICD-10:E70.3`)
  - `MONDO:0007938` — Marfan Syndrome (cross-references `Orpha:558`, `OMIM:154700`)
- **Size**: ~25,000 disease entries.
- **Maintainer**: Monarch Initiative.
- **Project role**: The interoperability layer. When a hospital sends a patient record with an ICD-10 code, MONDO maps it to the corresponding Orpha ID for the Knowledge Graph.

### 1.4. UMLS CUIs — The Universal Pivot

UMLS CUIs (Chapter 3.6) are the deepest layer: they unify not just diseases but all biomedical concepts (phenotypes, genes, proteins, drugs, procedures). The project uses CUIs as the **intermediate pivot** when mapping between vocabularies that MONDO does not directly cover.

## 2. Why IDs (Not Strings) Are Used

The original vault correctly noted that IDs are "global, unique, and fast for graph math," but it undersold the importance. Three reasons:

### 2.1. Language Independence

A doctor in Algeria writes *"Mélasse"* (molasses, for *Melena* — black tarry stool). A doctor in Japan writes 黒色便. A doctor in the U.S. writes *Melena*. All three should map to the same HPO term (`HP:0002573`, Melena). Using IDs makes this possible: the LLM Cleaner normalises the language to an HPO ID, and the ID is the same regardless of the input language.

### 2.2. Uniqueness

There are dozens of types of albinism: Oculocutaneous Type 1A, Type 1B, Type 2, Type 3, Type 4, Ocular Albinism, Hermansky-Pudlak Syndrome, Chediak-Higashi Syndrome, etc. The string "albinism" is ambiguous; the ID `Orpha:92` is not. Using IDs ensures the system is talking about the exact sub-type.

### 2.3. Computational Efficiency

Comparing two integers (`92 == 92`) is $O(1)$ and branchless. Comparing two strings (`"Oculocutaneous Albinism Type 1" == "Oculocutaneous Albinism Type 1"`) is $O(n)$ where $n$ is the string length. For a Knowledge Graph with millions of edges, this difference compounds.

### 2.4. Auditability

Every ID has a permanent URI (e.g., `http://purl.obolibrary.org/obo/HP_0000639`). This URI can be looked up in the source ontology, providing an auditable trail back to the curated definition. A string label has no such trail.

## 3. Ontology Versioning and Concept Drift

The original vault treated IDs as permanent. They are **not**. Ontologies are living resources, updated quarterly (HPO) to annually (Orphanet). Three types of change occur:

### 3.1. Term Addition

New terms are added as medical knowledge grows. Example: `HP:0031936` (*Sialorrhea*, excessive drooling) was added in HPO 2021. Older patient records do not contain this ID; newer ones may.

### 3.2. Term Deprecation

Terms are **deprecated** when they are found to be redundant, ambiguous, or incorrectly defined. A deprecated term is **not** deleted (to preserve backward compatibility) but is marked `owl:deprecated true` and is typically mapped to a replacement via `owl:replacedBy`.

Example: `HP:0009882` (*Short distal phalanges of finger*) was deprecated in HPO 2023 and replaced by `HP:0006236` (*Short middle phalanges of the hand*). Any patient record containing the old ID must be re-mapped to the new one.

### 3.3. Term Splitting

A single term may be split into multiple more specific terms. Example: a generic *Eye abnormality* term might be split into *Abnormal eye color*, *Abnormal eye shape*, and *Abnormal eye movement*. The old ID is deprecated, and three new IDs are created.

### 3.4. Term Merging

Two terms that were thought to be distinct may be merged when research shows they are the same concept. One ID is deprecated; the other absorbs its annotations.

### 3.5. Concept Drift

Even when an ID is preserved, its **definition** may shift. `HP:0001250` (*Seizure*) was historically defined broadly; newer versions may narrow the definition to exclude certain paroxysmal events. A patient record annotated under the old definition may not match a disease annotated under the new definition, even though the ID is the same.

## 4. Deprecation and `owl:sameAs` Mapping

When an ID is deprecated, the ontology provides a mapping to the replacement:

```turtle
HP:0009882 rdf:type owl:Class ;
           owl:deprecated true ;
           owl:replacedBy HP:0006236 ;
           rdfs:label "Short distal phalanges of finger (deprecated)" .
```

The project's pipeline handles deprecation at load time:

```python
def load_hpo_with_deprecations(hpo_owl_path):
    onto = load_ontology(hpo_owl_path)
    deprecation_map = {}
    for cls in onto.classes():
        if cls.deprecated:
            replacement = cls.replacedBy
            if replacement:
                deprecation_map[cls.id] = replacement.id
            else:
                log_warning(f"Deprecated term {cls.id} has no replacement")
    return onto, deprecation_map

def normalise_hpo_id(hpo_id, deprecation_map):
    """Map a possibly-deprecated ID to its current canonical ID."""
    visited = set()
    while hpo_id in deprecation_map and hpo_id not in visited:
        visited.add(hpo_id)
        hpo_id = deprecation_map[hpo_id]
    return hpo_id
```

The `visited` set prevents infinite loops in case of accidental cycles in the deprecation map.

### 4.1. Cross-Ontology Mapping with `owl:sameAs`

When the same concept exists in multiple ontologies (e.g., a disease in both Orphanet and OMIM), MONDO provides the cross-ontology mapping:

```turtle
MONDO:0008754 owl:equivalentClass Orpha:92 ;
              owl:equivalentClass OMIM:203100 ;
              skos:exactMatch ICD10:E70.3 .
```

The project's pipeline uses MONDO as the canonical disease identifier internally, and the `owl:equivalentClass` / `skos:exactMatch` triples to map to/from Orphanet, OMIM, and ICD-10 as needed.

## 5. Cross-Ontology Mapping — The Multi-Hospital Problem

Different hospitals use different vocabularies:

- Hospital A (U.S. academic medical center): ICD-10 for billing, SNOMED-CT for problem lists.
- Hospital B (European rare-disease registry): Orphanet.
- Hospital C (research genomics lab): OMIM.

A patient who visits all three hospitals will have three different codes for the same disease. Without cross-ontology mapping, the project's Knowledge Graph would treat these as three separate diseases.

### 5.1. The MONDO Solution

MONDO's cross-references resolve this:

```python
def unify_disease_id(raw_id, raw_vocabulary):
    """Map any disease ID to the canonical MONDO ID."""
    if raw_vocabulary == "ORPHANET":
        return mondo_lookup_by_orpha(raw_id)  # e.g., Orpha:92 → MONDO:0008754
    elif raw_vocabulary == "OMIM":
        return mondo_lookup_by_omim(raw_id)
    elif raw_vocabulary == "ICD10":
        return mondo_lookup_by_icd10(raw_id)
    elif raw_vocabulary == "MONDO":
        return raw_id
    else:
        raise ValueError(f"Unknown vocabulary: {raw_vocabulary}")
```

All patient records are normalised to MONDO IDs at ingestion time. The Knowledge Graph stores only MONDO IDs internally; the original vocabulary IDs are preserved as metadata for traceability.

### 5.2. The UMLS CUI Fallback

For vocabularies that MONDO does not cover (e.g., LOINC for lab tests, RxNorm for drugs), the pipeline falls back to UMLS CUIs (Chapter 3.6):

```python
def unify_concept_id(raw_id, raw_vocabulary):
    # Try MONDO first (for diseases)
    mondo_id = try_mondo_mapping(raw_id, raw_vocabulary)
    if mondo_id:
        return ("MONDO", mondo_id)
    # Fall back to UMLS CUI (for non-disease concepts)
    cui = try_umls_mapping(raw_id, raw_vocabulary)
    if cui:
        return ("CUI", cui)
    raise ValueError(f"Cannot unify {raw_id} from {raw_vocabulary}")
```

This two-layer mapping (MONDO for diseases, CUI for everything else) handles essentially every clinical vocabulary in use.

## 6. The Project's Versioning Strategy

The project's pipeline includes a **versioning manifest** that records which ontology versions are loaded:

```yaml
# ontology_versions.yaml
hpo: "2024-03-01"
orphanet: "2024-01-01"
mondo: "2024-02-06"
umls: "2024AA"
```

At load time:

1. The pipeline downloads the specified versions (or loads them from a local cache).
2. The deprecation maps are built.
3. The transitive closures (Chapter 7.1) are computed.
4. The versioning manifest is embedded in every output (so a diagnosis can be traced back to the exact ontology versions that produced it).

### 6.1. Updating Ontologies

When a new ontology version is released:

1. Download the new version.
2. Re-compute the deprecation maps and transitive closures.
3. Re-encode all disease definitions with the updated ontology (BioBERT embeddings do not change, but the HPO annotations may).
4. Re-run the evaluation on the gold-standard set (Chapter 6.5) to verify that performance has not regressed.
5. If performance is acceptable, update the versioning manifest and deploy.

### 6.2. Backward Compatibility

Patient records annotated under older ontology versions are **re-normalised** at load time using the deprecation map. A record containing the deprecated `HP:0009882` is automatically mapped to `HP:0006236` before it enters the Knowledge Graph. This ensures that historical records remain queryable even as ontologies evolve.
