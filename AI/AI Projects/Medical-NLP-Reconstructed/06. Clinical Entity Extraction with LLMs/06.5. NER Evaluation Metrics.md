# 06.5. NER Evaluation Metrics

After the LLM extracts clinical entities, the project must measure the extraction's accuracy scientifically. The original vault presented Precision, Recall, and F1 but omitted two critical refinements: **boundary matching criteria** (strict vs. loose) and **micro vs. macro averaging**. Without these, an evaluation on a highly imbalanced rare-disease dataset (where some phenotypes appear in 1000 notes and others in 5) will produce misleading numbers. A model that performs well on common phenotypes and terribly on rare ones can still report a high "F1" under micro-averaging, hiding the failure.

This note covers: (1) Precision, Recall, and F1 (review), (2) strict vs. loose boundary matching for NER, (3) micro-averaging, (4) macro-averaging, (5) weighted averaging, (6) why the project prioritises recall, and (7) the gold-standard comparison methodology.

---

## 1. Precision, Recall, and F1 (Review)

Given a set of extracted entities and a set of ground-truth entities, we classify each extraction as:

- **True Positive (TP)**: Extracted and is in the ground truth.
- **False Positive (FP)**: Extracted but not in the ground truth.
- **False Negative (FN)**: Not extracted but is in the ground truth.

### 1.1. Precision

$$\text{Precision} = \frac{TP}{TP + FP}$$

*"Out of all the entities the AI claimed it found, how many were actually real?"*

High precision = low false-positive rate. The AI does not hallucinate.

### 1.2. Recall

$$\text{Recall} = \frac{TP}{TP + FN}$$

*"Out of all the entities in the ground truth, how many did the AI successfully find?"*

High recall = low false-negative rate. The AI does not miss real entities.

### 1.3. F1-Score

$$F_1 = 2 \times \frac{\text{Precision} \times \text{Recall}}{\text{Precision} + \text{Recall}}$$

The harmonic mean of precision and recall. The harmonic mean (rather than the arithmetic mean) penalises imbalances: a model with precision 1.0 and recall 0.1 has $F_1 = 0.18$, not $0.55$.

## 2. Strict vs. Loose Boundary Matching

For NER, "correct" extraction is not just about the entity type — it is also about the **span** of text the entity covers. Consider the note:

> *"Patient exhibits oculocutaneous hypopigmentation."*

Ground truth: `oculocutaneous hypopigmentation` (chars 17–47), type `PHENOTYPE`.

Suppose the LLM extracts:

- `hypopigmentation` (chars 31–47), type `PHENOTYPE`.

Is this a TP or an FP? It depends on the matching criterion:

### 2.1. Strict Matching

The extracted span must **exactly match** the ground-truth span (same start, same end, same type). In the example above, the extraction is an **FP** (because the span is wrong) and the ground truth is an **FN** (because it was not exactly matched).

Strict matching is the standard for academic NER benchmarks (CoNLL-2003, GENIA). It penalises partial matches heavily.

### 2.2. Loose (Partial) Matching

The extracted span must **overlap** the ground-truth span (any non-empty intersection) and have the same type. In the example above, the extraction is a **TP** (because `hypopigmentation` overlaps `oculocutaneous hypopigmentation`).

Loose matching is more forgiving and is sometimes used for clinical NER where exact span boundaries are ambiguous.

### 2.3. Type-Level Matching (Relaxed)

The extraction is a TP if the entity **type** is correct and the extracted text is a **substring or superstring** of the ground truth (or vice versa). This is the loosest criterion and is appropriate when the downstream task (e.g., ontology linking) does not care about exact spans.

### 2.4. The Project's Choice

The project uses **type-level matching** because the downstream task is ontology linking, not span extraction. If the LLM extracts `hypopigmentation` and the ground truth is `oculocutaneous hypopigmentation`, both will be linked to the same HPO term after SapBERT normalisation, so the difference in span does not matter for the diagnosis.

## 3. Micro-Averaging

**Micro-averaging** pools all TPs, FPs, and FNs across all entity types (or all notes) and computes a single precision, recall, and F1:

$$\text{Precision}_{\text{micro}} = \frac{\sum_i TP_i}{\sum_i (TP_i + FP_i)}, \qquad \text{Recall}_{\text{micro}} = \frac{\sum_i TP_i}{\sum_i (TP_i + FN_i)}$$

where $i$ indexes entity types (or notes).

### 3.1. What Micro-Averaging Measures

Micro-averaging gives **each instance equal weight**. If there are 1000 instances of *Fever* and 5 instances of *Oculocutaneous Albinism*, the micro-averaged F1 is dominated by *Fever* — the model's performance on *Albinism* barely matters.

### 3.2. When Micro-Averaging Is Appropriate

- When the application cares about **overall** performance, not per-class performance.
- When the class distribution in the test set matches the class distribution in production.

### 3.3. When Micro-Averaging Is Misleading

- When the test set is **imbalanced** (which it always is for rare diseases) and you care about performance on the rare classes.
- When a model that does well on common classes but fails on rare ones reports a deceptively high micro-F1.

For rare-disease evaluation, micro-averaging **hides the failures on rare phenotypes**, which is exactly where the project needs to perform well.

---

## 4. Macro-Averaging

**Macro-averaging** computes precision, recall, and F1 **per class** (or per note), then takes the **unweighted mean** across classes:

$$\text{Precision}_{\text{macro}} = \frac{1}{C}\sum_{c=1}^C \text{Precision}_c, \qquad \text{Recall}_{\text{macro}} = \frac{1}{C}\sum_{c=1}^C \text{Recall}_c$$

where $C$ is the number of classes.

### 4.1. What Macro-Averaging Measures

Macro-averaging gives **each class equal weight**, regardless of frequency. The model's performance on *Oculocutaneous Albinism* (5 instances) counts as much as its performance on *Fever* (1000 instances).

### 4.2. When Macro-Averaging Is Appropriate

- When you care about **per-class** performance, especially for rare classes.
- When the test set is imbalanced and you want to detect models that fail on the long tail.

### 4.3. When Macro-Averaging Is Misleading

- When a class has **very few instances** (e.g., 1 or 2), the per-class F1 is high-variance and can swing wildly with a single misclassification.
- When the class distribution in production is **not** uniform (which it never is for rare diseases).

For the project's evaluation, macro-averaging is the **primary metric** because rare-disease diagnosis inherently cares about the long tail.

---

## 5. Weighted Averaging

**Weighted averaging** computes per-class metrics and takes a **frequency-weighted mean**:

$$\text{Precision}_{\text{weighted}} = \frac{\sum_c N_c \cdot \text{Precision}_c}{\sum_c N_c}$$

where $N_c$ is the number of ground-truth instances of class $c$.

### 5.1. What Weighted Averaging Measures

Weighted averaging is between micro and macro: it gives more weight to common classes but does not let them dominate entirely. A class with 1000 instances gets 200× the weight of a class with 5 instances (vs. 1× under macro and 200× under micro).

### 5.2. When to Use It

Weighted averaging is a compromise. It is useful when you want to acknowledge that common classes matter more than rare ones (because they appear more often in production) but you do not want rare classes to be invisible.

The project reports **both micro and macro F1** in its evaluation, with macro as the primary metric.

---

## 6. Why the Project Prioritises Recall

In most NLP applications (spam filtering, search ranking), precision is prioritised — false positives are costly. In **rare-disease medicine**, recall is prioritised:

### 6.1. The Diagnostic Stakes

- **Low precision** (10 false positives): The AI suggests 10 extra symptoms that are not in the note. A doctor reviews them in 30 seconds and discards them. Cost: minimal.
- **Low recall** (1 false negative): The AI misses the **one** specific phenotype that identifies a deadly genetic mutation. The patient remains undiagnosed for years. Cost: catastrophic.

### 6.2. The Pipeline Architecture Supports This

The project's pipeline is designed to tolerate false positives at the extraction stage:

- Stage 2 (retrieval) uses the extracted phenotypes to find candidate diseases. Extra phenotypes produce extra candidates, which Stage 3 (Knowledge Graph) filters out.
- Stage 3 verifies each candidate against the patient's extracted phenotype **set**. A hallucinated phenotype that does not match any disease's HPO profile is silently dropped.
- Stage 4 (Neural Ranker) orders the verified candidates. False positives at Stage 1 do not affect the final ranking because they are filtered at Stage 3.

So the cost of low precision is borne by Stage 3's verification logic, which is cheap. The cost of low recall (a missed phenotype → a missed diagnosis) cannot be recovered by any later stage.

### 6.3. The Recall Target

The project's extraction target is **Recall ≥ 0.95** (macro-averaged) at the cost of Precision ≥ 0.70. This means the AI may produce ~30% false positives, but it must not miss more than 5% of real phenotypes.

## 7. The Gold-Standard Comparison

To compute precision, recall, and F1, the project needs a **gold standard** — a set of patient notes manually annotated by clinicians. The annotation process:

### 7.1. Annotation Protocol

1. **Select** a stratified sample of 200 patient notes (stratified by disease family: 20 notes each from 10 disease families).
2. **Annotate** each note independently by two clinicians. They mark every phenotype, gene, and protein with its span and assertion status.
3. **Reconcile** disagreements via discussion. The reconciled annotations are the gold standard.
4. **Compute inter-annotator agreement** (Cohen's kappa). If kappa < 0.7, the annotation protocol needs refinement.

### 7.2. Computing the Metrics

For each note in the gold standard:

1. Run the LLM Cleaner to produce the extracted entities.
2. Compare extracted entities to gold-standard entities using type-level matching (§2.3).
3. Compute TP, FP, FN per note.
4. Aggregate: micro-average across all notes, macro-average across disease families.

### 7.3. Reporting

The project reports:

- **Micro-F1**: overall extraction quality.
- **Macro-F1**: per-disease-family extraction quality (the primary metric).
- **Recall (macro)**: the project's success criterion (target ≥ 0.95).
- **Per-family breakdown**: a table showing F1 for each of the 10 disease families, to identify weak spots.

This reporting standard is what makes the evaluation scientifically defensible — a jury can see not just "the AI is 85% accurate" but "the AI is 95% accurate on common phenotypes and 70% accurate on rare ones, so we need to improve X."
