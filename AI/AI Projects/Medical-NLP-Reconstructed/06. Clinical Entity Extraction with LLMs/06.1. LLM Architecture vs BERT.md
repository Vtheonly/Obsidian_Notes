# 06.1. LLM Architecture vs BERT

The project uses two fundamentally different types of Transformer model: **encoder-only models** (BERT, BioBERT, PubMedBERT) for embedding and retrieval, and **decoder-only models** (Gemini, GPT-4, LLaMA) for the LLM Clinical Cleaner. The original vault described the difference as "BERT compresses, LLMs expand" — a useful slogan but technically incomplete. The real architectural difference is the **attention mask**: BERT uses a bidirectional (fully-visible) mask, while decoder LLMs use a **causal (lower-triangular) mask**. This single difference cascades into everything else: the kind of tasks each model is good at, the inference speed (decoders need KV-caching to be fast), and the training objective (MLM vs. next-token prediction).

This note covers: (1) the encoder vs. decoder distinction, (2) the attention mask difference, (3) the causal mask and autoregressive generation, (4) KV-caching and why it makes decoders fast, (5) why the project uses both, and (6) the compute-efficiency argument.

---

## 1. Encoder vs. Decoder — The Architectural Split

The original Transformer (Vaswani et al., 2017) had both an encoder and a decoder. Subsequent models specialised:

| Family | Architecture | Examples | Attention Mask | Training Objective |
| :--- | :--- | :--- | :--- | :--- |
| **Encoder-only** | Transformer encoder stack | BERT, BioBERT, PubMedBERT, ClinicalBERT, SapBERT | Bidirectional (all tokens visible to all) | Masked Language Modeling (MLM) |
| **Decoder-only** | Transformer decoder stack | GPT-2/3/4, LLaMA, Mistral, Gemini | Causal (token $i$ sees only tokens $\leq i$) | Next-token prediction (autoregressive) |
| **Encoder-decoder** | Both | T5, BART, original Transformer | Encoder bidirectional, decoder causal | Masked LM + denoising |

The project uses encoder-only models for embedding (Stage 2 retrieval) and decoder-only models for the LLM Cleaner (Stage 1). The choice is not arbitrary — it follows from the architectural strengths of each family.

## 2. The Attention Mask Difference

Recall from [[02.1. Self-Attention and the QKV Math]] that the attention computation is:

$$\text{Attention}(Q, K, V, M) = \text{softmax}\!\left(\frac{Q K^\top}{\sqrt{d_k}} + M\right) V$$

where $M$ is the attention mask. The difference between encoder and decoder is the mask:

### 2.1. Encoder Mask (BERT)

$$M_{ij}^{\text{encoder}} = \begin{cases} 0 & \text{if } j \text{ is a real token} \\ -\infty & \text{if } j \text{ is padding} \end{cases}$$

Every real token can attend to every other real token. The representation of *"patient"*$ is computed using information from every other word in the sentence, in both directions. This is called **bidirectional attention**.

### 2.2. Decoder Mask (GPT, Gemini)

$$M_{ij}^{\text{decoder}} = \begin{cases} 0 & \text{if } j \leq i \text{ and } j \text{ is real} \\ -\infty & \text{if } j > i \text{ or } j \text{ is padding} \end{cases}$$

Token $i$ can attend only to tokens $j \leq i$ (the past and present, not the future). This is the **causal mask**, and it is what makes the model autoregressive: the representation of *"patient"* is computed only from the tokens that came before it.

### 2.3. Why the Mask Determines the Use Case

- **Bidirectional (encoder)**: Best when you have the entire input and want a single, holistic representation. This is the case for embedding: you have the full patient note, and you want one `[CLS]` vector that captures its meaning.
- **Causal (decoder)**: Best when you are generating text one token at a time and cannot peek at the future. This is the case for the LLM Cleaner: it generates the JSON output token by token, and each token must be produced without seeing the tokens that come after it.

A bidirectional model cannot generate text (it would need to see the future tokens it is supposed to produce). A causal model can generate text but produces weaker embeddings because each token's representation lacks future context.

## 3. The Causal Mask and Autoregressive Generation

A decoder-only model generates text by:

1. Taking the input tokens (the prompt).
2. Running a forward pass to compute the logits for the next token.
3. Sampling the next token from the logits (with temperature, top-p, etc. — Chapter 6.3).
4. Appending the sampled token to the input.
5. Repeating from step 2.

This is **autoregressive generation**: each token is produced one at a time, conditioned on all previous tokens.

### 3.1. The Generation Loop

```python
def generate(model, prompt_tokens, max_new_tokens=100):
    tokens = prompt_tokens
    for _ in range(max_new_tokens):
        logits = model.forward(tokens)  # (seq_len, vocab_size)
        next_token_logits = logits[-1]  # Last position
        next_token = sample(next_token_logits, temperature=0.0)
        tokens = tokens + [next_token]
        if next_token == EOS_TOKEN:
            break
    return tokens
```

### 3.2. The Naive Cost

Each `model.forward(tokens)` call processes the entire sequence from scratch. For a 1000-token output, this means 1000 forward passes, each processing an increasingly long sequence. The total cost is $O(N^2 \cdot d)$ where $N$ is the final sequence length — quadratic in the output length.

For a 1000-token output on a 7B-parameter model, this would take ~30 seconds per query on a single GPU. Unacceptable for production.

## 4. KV-Caching — The Decoder's Inference Optimisation

**KV-caching** is the optimisation that makes autoregressive generation tractable. The key observation is that at each step, the Keys and Values for the **existing** tokens do not change — only the new token's Key and Value need to be computed.

### 4.1. The Caching Mechanism

Recall that $K = X W^K$ and $V = X W^V$, where $X$ is the input matrix. In autoregressive generation:

- **Step 1**: Input is `[prompt]`. Compute $K_1, V_1$ for all prompt tokens. Cache them.
- **Step 2**: Input is `[prompt, token_1]`. We only need to compute $K, V$ for `token_1` — the prompt tokens' $K, V$ are already in the cache. Append the new $K, V$ to the cache.
- **Step 3**: Input is `[prompt, token_1, token_2]`. Compute $K, V$ only for `token_2`. Append.
- ...

Each step now costs $O(1 \cdot d)$ (one token's $K, V$ computation) instead of $O(N \cdot d)$ (the whole sequence). The total cost over $N$ generation steps drops from $O(N^2 \cdot d)$ to $O(N \cdot d)$ — **linear** in the output length.

### 4.2. The Attention Computation with Cache

At step $t$, the attention for the new token is:

$$\text{Attention}(q_t, [K_{1:t}], [V_{1:t}]) = \text{softmax}\!\left(\frac{q_t [K_{1:t}]^\top}{\sqrt{d_k}}\right) [V_{1:t}]$$

where $q_t$ is the new token's Query (a single vector) and $[K_{1:t}], [V_{1:t}]$ are the cached Keys and Values for all tokens so far. The cost is $O(t \cdot d)$ per step (one query against $t$ keys), so the total over $N$ steps is $O(N^2 \cdot d)$ in the attention computation but $O(N \cdot d)$ in the K/V projection computation. The cache turns the dominant cost from "recompute everything" to "compute only the new token's contribution."

### 4.3. Memory Cost

The KV cache stores $N \times d$ Keys and $N \times d$ Values per layer, per head. For a 32-layer, 32-head, 4096-dim model generating 2048 tokens:

$$\text{Cache size} = 2 \times 32 \times 2048 \times 4096 \times 2 \text{ bytes (FP16)} = 1 \text{ GB}$$

This is a substantial memory cost, and it grows linearly with sequence length. Long-context models (32k+ tokens) require multi-GPU serving or memory-efficient attention (FlashAttention, PagedAttention) to keep the cache manageable.

### 4.4. Why Encoder Models Do Not Need KV-Cache

Encoder models process the entire input in a single forward pass — there is no autoregressive loop, so there is no opportunity to cache and reuse. The bidirectional attention mask also means that every token's representation depends on every other token, so there is no "incremental" computation to exploit.

This is why encoder inference (one forward pass over a 512-token sequence) is cheap (~5 ms on a GPU), while decoder generation (500 sequential forward passes, each producing one token) is expensive even with KV-caching (~1–5 seconds for 500 tokens).

## 5. Why the Project Uses Both

### 5.1. Decoder LLM for Stage 1 (Cleaning)

The LLM Cleaner must:

- Read a free-text patient note.
- **Generate** a structured JSON output that did not exist in the input.

Generation is the decoder's strength. The LLM takes the prompt (patient note + system instructions) and autoregressively produces the JSON, token by token. No encoder model can do this.

The downside is cost: each Cleaner call is ~1 second of LLM inference (vs. ~5 ms for a BioBERT forward pass). For a batch of 10,000 patient notes, the Cleaner costs ~3 hours of LLM time. This is acceptable because the Cleaner runs once per note (offline), not at query time.

### 5.2. Encoder BioBERT for Stage 2 (Retrieval)

The retrieval must:

- Encode the patient note into a single vector.
- Encode each of 10,000 disease definitions into a single vector.
- Compute 10,000 cosine similarities.

Encoding is the encoder's strength. Each BioBERT forward pass is ~5 ms, and the 10,000 disease vectors are pre-computed once and indexed. At query time, only the patient note needs to be encoded (5 ms), and the FAISS retrieval is sub-millisecond (Chapter 5.2). The total query latency is dominated by the BioBERT encoding, which is ~100× faster than calling an LLM.

### 5.3. Why Not Use the LLM for Retrieval?

A decoder LLM **could** in principle be used for retrieval: prompt it with *"Does this patient note match this disease definition?"* and read the yes/no answer. But this would require:

- 10,000 LLM calls per patient query (one per disease).
- ~10,000 seconds per query at 1 second/call.

Compared to BioBERT's ~5 ms per query, this is **2 million times slower**. The encoder's bidirectional architecture is also better for producing a single holistic sentence vector — decoder `[CLS]`-equivalents (the last token's hidden state) are weaker because they only see the past.

### 5.4. Why Not Use BioBERT for Cleaning?

BioBERT is an encoder — it cannot generate text. Even if it could, it has not been trained on the "read a note and output JSON" task; it has been trained on MLM. Fine-tuning BioBERT for generation would require substantial additional training and would still be inferior to a decoder LLM, which has been trained on billions of tokens of natural-language generation.

The hybrid architecture (decoder for cleaning, encoder for retrieval) is therefore not a compromise — it is the optimal assignment of models to tasks.

## 6. The Compute-Efficiency Argument

The original vault mentioned that "it is much faster to run a small BERT model for 10,000 similarity checks than to ask a massive LLM to compare 10,000 pairs of text." This is true but undersells the magnitude:

| Operation | Cost |
| :--- | :--- |
| One BioBERT forward pass (encode one note) | ~5 ms |
| One LLM call (clean one note) | ~1,000 ms |
| BioBERT encode 10,000 diseases (one-time precompute) | ~50 seconds |
| LLM compare 10,000 disease pairs (per query) | ~10,000 seconds (2.7 hours) |
| FAISS Top-20 retrieval (per query, after precompute) | ~2 ms |

The precompute of disease embeddings is a one-time cost; after that, each query is ~7 ms (5 ms encode + 2 ms FAISS). The LLM Cleaner runs once per note (offline), so its 1-second cost is amortised.

This is the engineering justification for the two-stage architecture: **use the slow, expensive LLM where it is necessary (cleaning) and use the fast, cheap encoder where it is sufficient (retrieval)**.
