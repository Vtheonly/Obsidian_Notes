# 09.2. Pairwise Dataset Construction

The original vault's Chapter 9.2 described generating training pairs $(A, B)$ from the Top-20 retrieved candidates for every patient note, but it omitted the **validation splitting strategy** — and the audit identified this as a **critical** gap. If the train-test split is performed randomly at the *pair* level rather than the *patient-note* level, pairs derived from the same patient note will appear in both the training and validation sets. This is **data leakage**: the model has seen information about the validation patient notes during training, artificially inflating validation accuracy and causing the model to fail on truly unseen clinical cases.

This note covers: (1) the pairwise dataset construction, (2) the data leakage problem with a concrete example, (3) the **group-aware split** (patient-note-level split) that prevents leakage, (4) tournament pruning for $O(K^2)$ cost reduction, (5) class balance, and (6) the data augmentation effect.

---

## 1. Pairwise Dataset Construction

For each patient note in the training set, the project generates pairwise training examples:

### 1.1. The Construction Algorithm

```python
def build_pairwise_dataset(patient_notes, retrieval_model, k=20):
    pairs = []
    for note in patient_notes:
        # Stage 1 retrieval: get Top-K candidates
        candidates = retrieval_model.retrieve(note, k=k)
        ground_truth = note.correct_disease
        
        # Generate all pairs (A, B) from the Top-K
        for i, cand_a in enumerate(candidates):
            for j, cand_b in enumerate(candidates):
                if i == j:
                    continue
                # Label: 1 if A is the ground truth, 0 otherwise
                label = 1 if cand_a.id == ground_truth else 0
                pairs.append({
                    "note": note,
                    "candidate_a": cand_a,
                    "candidate_b": cand_b,
                    "label": label
                })
    return pairs
```

### 1.2. The Labeling Logic

The label is **asymmetric**: the pair $(A, B)$ with $A$ = ground truth gets label 1, but the pair $(B, A)$ with $B$ = ground truth gets label 0. This teaches the model to prefer the correct disease regardless of which position it appears in.

For a Top-20 with 1 correct disease and 19 wrong diseases:

- Pairs where A = correct: 19 pairs, all label 1.
- Pairs where A = wrong, B = correct: 19 pairs, all label 0.
- Pairs where both A and B are wrong: $19 \times 18 = 342$ pairs, all label 0.

Total: $20 \times 19 = 380$ pairs per patient note, of which 19 are positive and 361 are negative.

### 1.3. The Data Augmentation Effect

For 100 patient notes, the pairwise dataset contains $100 \times 380 = 38{,}000$ training examples — a 380× augmentation over the original 100 notes. This is substantial and is one reason the Neural Ranker can learn effectively from a modest number of patient notes.

## 2. The Data Leakage Problem (Critical)

The audit identified this as a **critical** issue. Consider what happens with a naive random split at the pair level:

### 2.1. The Naive (Wrong) Split

```python
from sklearn.model_selection import train_test_split

# WRONG: Split at the pair level
train_pairs, val_pairs = train_test_split(all_pairs, test_size=0.2, random_state=42)
```

This randomly assigns each of the 38,000 pairs to train or validation. With probability ~0.2, any given pair is in validation. But the 380 pairs from a single patient note are distributed across train and validation, so:

- The training set contains ~304 pairs from patient note #1.
- The validation set contains ~76 pairs from patient note #1.

The model has seen 304 examples derived from patient note #1 during training. When it encounters the remaining 76 examples in validation, it is **not** being evaluated on a truly unseen patient note — it is being evaluated on examples whose context (the patient note's embedding, the candidate embeddings) it has already seen.

### 2.2. Why This Inflates Validation Accuracy

The model learns to memorise patient-note-specific features. For example, if patient note #1 has a distinctive embedding (because it mentions a rare combination of symptoms), the model learns that "this embedding pattern → prefer candidate X." When the validation set contains other pairs from the same patient note, the model applies the memorised pattern and gets the answer right — but this is recall of memorised information, not generalisation to new patient notes.

In production, the model encounters patient notes it has never seen. Without the memorised patterns, it performs substantially worse. The validation accuracy was a **lie** — it measured memorisation, not generalisation.

### 2.3. Concrete Example

Suppose patient note #1 mentions *"Nystagmus, hypopigmentation, photophobia"* (Albinism). The Top-20 retrieval returns 20 candidate diseases, including Albinism (correct) and Hermansky-Pudlak Syndrome (a related albinism-like disease).

- Training pair: (Albinism, Hermansky-Pudlak) → label 1.
- Validation pair: (Albinism, Marfan) → label 1.

The model has learned from the training pair that "for this patient note's embedding, prefer Albinism." When it sees the validation pair, it applies the same learned preference and gets it right — but only because it has seen this patient note before. On a truly unseen patient note mentioning *"shaky eyes, white skin, light sensitivity"*, the model may fail because it has not learned the general pattern (Albinism symptoms → Albinism), only the specific pattern (this exact embedding → Albinism).

This is the leakage: the validation accuracy is inflated by patient-note-specific memorisation.

## 3. The Group-Aware Split (Patient-Note-Level Split)

The correct approach is to split at the **patient-note level**, not the pair level. All pairs from a given patient note go entirely into train or entirely into validation:

```python
def group_aware_split(patient_notes, test_size=0.2, random_state=42):
    # Split the patient notes, not the pairs
    train_notes, val_notes = train_test_split(
        patient_notes, test_size=test_size, random_state=random_state
    )
    
    # Build pairs separately for train and val
    train_pairs = build_pairwise_dataset(train_notes, retrieval_model)
    val_pairs = build_pairwise_dataset(val_notes, retrieval_model)
    
    return train_pairs, val_pairs
```

### 3.1. Why This Prevents Leakage

With the group-aware split:

- Patient notes 1–80 → training. Their 30,400 pairs are in training.
- Patient notes 81–100 → validation. Their 7,600 pairs are in validation.

No patient note appears in both sets. The model cannot memorise patient-note-specific features because each validation patient note is truly unseen.

### 3.2. The Cost

The group-aware split reduces the effective training set size. With 100 patient notes and a 20% validation split, the training set has 80 notes (30,400 pairs) instead of 100 notes (38,000 pairs). This is a ~20% reduction, which is the standard cost of a held-out validation set.

### 3.3. Stratified Group-Aware Split

For rare-disease diagnosis, the split should also be **stratified by disease family** — each disease family should be proportionally represented in both train and validation. Otherwise, rare disease families may be entirely in validation (no training examples) or entirely in training (no validation examples).

## 4. Tournament Pruning — Reducing the $O(K^2)$ Cost

The original vault did not discuss pruning. For $K = 20$, the $K^2 = 400$ pairs per note is tractable. For $K = 100$, it is 10,000 pairs per note — expensive. Three pruning strategies reduce the cost:

### 4.1. Active Candidate Elimination

After each comparison, eliminate candidates that have lost to many others. If candidate $A$ has lost to 5 other candidates, it is unlikely to be the winner and can be removed from subsequent comparisons. This reduces the effective $K$ as the tournament progresses.

### 4.2. Divide-and-Conquer Tournament Trees

Instead of all-pairs, use a single-elimination tournament bracket: $K/2$ comparisons in round 1, $K/4$ in round 2, etc. Total comparisons: $K - 1$ (linear, not quadratic). The tradeoff is that the winner is not necessarily the same as the all-pairs winner — single-elimination can produce a different winner if the bracket is unlucky.

### 4.3. Top-K Pruning

Only generate pairs where at least one candidate is in the Top-5 by Stage 1 cosine. This reduces the pair count from $K^2$ to $5K$ (linear in $K$). The assumption is that the correct disease is almost always in the Top-5 by cosine, so pairs between two low-ranked candidates are uninformative.

### 4.4. The Project's Choice

The project uses **all-pairs** at $K = 20$ (380 pairs per note) because the cost is tractable and the all-pairs tournament produces the most stable ranking. If $K$ grows to 50+, the project would switch to Top-K pruning.

## 5. Class Balance

The pairwise dataset is highly imbalanced: 19 positive pairs vs. 361 negative pairs per patient note (§1.2). Training on this imbalanced data produces a model biased toward predicting "negative" (i.e., $A$ is not the ground truth).

### 5.1. The Imbalance Problem

Without correction, the model learns to always predict $P(A > B) = 0.05$ (the base rate of positives), which gives 95% accuracy on the imbalanced training set but is useless for ranking.

### 5.2. Three Solutions

1. **Class weighting**: Weight positive pairs 19× more heavily in the loss:
   $$\mathcal{L} = -\frac{1}{N}\sum_i \left[w \cdot y_i \log p_i + (1 - y_i) \log(1 - p_i)\right]$$
   where $w = 19$ (the negative-to-positive ratio).

2. **Oversampling**: Duplicate positive pairs 19× to balance the dataset.

3. **Undersampling**: Sample only 19 negative pairs per note (one per wrong candidate), matching the 19 positive pairs.

### 5.3. The Project's Choice

The project uses **class weighting** because it does not change the dataset size and is computationally cheapest. The weight is set to the inverse class frequency: $w = |\text{negatives}| / |\text{positives}| = 361/19 \approx 19$.

## 6. The Data Augmentation Effect (Revisited)

The pairwise construction's 380× augmentation is not free — it has a subtle cost. The 380 pairs from a single patient note are **not independent**; they all share the same patient-note embedding and the same candidate embeddings. Training on all 380 is equivalent (in information content) to training on the original patient note with a richer loss signal, not to training on 380 independent notes.

This means:

- The effective training set size is closer to 100 patient notes than to 38,000 pairs.
- The model can still overfit to patient-note-specific features if the patient-note set is small.
- The group-aware split (§3) is essential — without it, the 380× augmentation amplifies the leakage problem.

### 6.1. Mitigating Overfitting

To mitigate overfitting on small patient-note sets:

1. **Dropout** in the Neural Ranker (Chapter 9.3) — randomly zero out 50% of hidden units during training, preventing the model from memorising specific embedding patterns.
2. **Early stopping** — monitor validation loss and stop training when it starts to increase.
3. **Data augmentation** — generate synthetic patient notes via LLM (at $T > 0$ for diversity, Chapter 6.3) to increase the effective patient-note set size.

---

## 7. Summary

| Issue | Naive Approach | Corrected Approach |
| :--- | :--- | :--- |
| Train-test split | Random at pair level | **Group-aware at patient-note level** |
| Stratification | None | **By disease family** |
| Class imbalance | Ignored | **Class weighting ($w = 19$)** |
| $O(K^2)$ cost | All pairs | All pairs at $K=20$; Top-K pruning if $K$ grows |
| Overfitting | Ignored | **Dropout + early stopping + LLM data augmentation** |

The group-aware split is the single most important correction. Without it, the project's reported validation accuracy is inflated by patient-note-specific memorisation, and the model will fail in production on truly unseen patient notes.
