# 4. Defining the Benchmark

> **The benchmark in one sentence**: The Chess Commentary Verification Benchmark (CCVB) is a 2000-example labeled dataset where each example contains a PGN, an English commentary, and per-claim ground-truth verdicts, used to evaluate how well a system can verify chess commentary against the board.

This note specifies the benchmark in enough detail that a collaborator could reproduce it.

---

## 4.1 Why a Benchmark Matters

A benchmark transforms a one-off project into a research area. Without a benchmark:

- Other researchers cannot compare their systems to yours.
- Progress cannot be measured over time.
- The task remains "your project" rather than "a research area".

With a benchmark:

- Anyone can build a system and compare.
- Progress is measurable.
- The task becomes a shared research object.

The benchmark IS the research contribution that outlives any specific system. Long after the v1 verifier is obsolete, the CCVB benchmark will still be used to evaluate new verifiers.

## 4.3 Construction Protocol

### 4.3.1 Source sampling

Sample from three sources in proportion:

- ACL Chess Commentary dataset: 60% (1200 examples).
- Synthetic Chess Commentary dataset: 30% (600 examples).
- Manually authored examples: 10% (200 examples, covering edge cases).

The manually authored examples are critical for coverage. They should include:

- Multi-claim sentences.
- Anaphora (pronouns referring to pieces).
- Strategic and positional claims (underrepresented in forum data).
- Comparison claims (for v2).
- Ambiguous claims (where the ground truth is genuinely unclear).

### 4.3.2 Claim extraction

For each sampled commentary, run the LLM claim extractor (Chapter 3.3). The extracted claims become the unit of labeling. Each claim gets one ground-truth verdict.

### 4.3.3 Annotation

Three trained annotators label each claim. Annotators must be:

- At least 1500 Elo on Lichess or Chess.com (for tactical and material claims).
- At least 1800 Elo for strategic and positional claims (or have a grandmaster reviewer for these).
- Trained on a 50-example pilot set with feedback.

Annotators see:

- The PGN.
- The commentary with the claim highlighted.
- The extracted claim structure (type, params).
- The facts database for the relevant plies.

Annotators choose one of the six verdict labels and provide a one-sentence justification.

### 4.3.4 Aggregation

Majority vote determines the ground-truth label. If all three annotators disagree, the example is flagged for review by a senior annotator (or grandmaster).

Inter-annotator agreement is computed as Cohen's kappa pairwise, then averaged. Target: kappa >= 0.7 overall, >= 0.8 for tactical/material claims, >= 0.5 for strategic/positional claims.

### 4.3.5 Splits

- Train: 60% (1200 examples).
- Dev: 20% (400 examples).
- Test: 20% (400 examples).

Splits are stratified by claim type to ensure each split has proportional representation.

## 4.4 Baseline Specifications

To make the benchmark useful, the paper releasing it must also report results for four baselines:

### 4.4.1 LLM-only

- Prompt GPT-4 (or current frontier) with the position (as FEN) and the commentary.
- Ask "for each claim in the commentary, output a verdict: Verified / Contradicted / etc."
- Parse the LLM's structured output.
- Compute precision, recall, F1.

Expected result: poor performance on tactical and material claims (~50% accuracy), better on move descriptions (~80%).

### 4.4.2 Stockfish-only

- For each claim, derive a heuristic verdict from the engine eval.
- "White wins material" → check if eval > +1 at the relevant ply.
- "King is exposed" → check if eval dropped significantly.
- "Move is correct" → check if the played move matches the engine's best move.
- Compute precision, recall, F1.

Expected result: poor performance on move descriptions (the engine does not care about the played move's description) and captures (the engine does not report captures as such), decent on strategic claims.

### 4.4.3 Rule-based

- Regex-based claim extraction (no LLM).
- Rule-based verification (no engine, no attack maps).
- Compute precision, recall, F1.

Expected result: poor extraction (regex cannot handle natural language variety), decent verification on the extracted claims. Overall poor performance.

### 4.4.4 Hybrid (proposed system)

- LLM for extraction.
- Symbolic verifier (python-chess + Stockfish) for verification.
- Compute precision, recall, F1.

Expected result: best overall, especially on tactical and material claims where the symbolic layer excels.

## 4.5 Release Checklist

When releasing the benchmark:

- [ ] Data files (JSON or JSONL) with all examples.
- [ ] Annotator guidelines (PDF).
- [ ] Annotation raw data (per-annotator labels, not just majority vote).
- [ ] Inter-annotator agreement statistics.
- [ ] Source attribution for each example.
- [ ] License (CC-BY 4.0 recommended).
- [ ] Code for loading and evaluating.
- [ ] Precomputed facts databases for the test games.
- [ ] Baseline results in a standard format.

The release should be on Hugging Face Datasets (for discoverability) and on GitHub (for code).

---

## 4.6 Long-Term Maintenance

A benchmark is a long-term commitment. Plan for:

- **Versioning**: v1, v2, etc. Bugs in labeling get fixed in new versions, with clear changelog.
- **Test set protection**: the test set should not be used for prompt engineering or system tuning. Document and enforce this.
- **Refresh**: every 2-3 years, refresh the test set with new examples to prevent overfitting from LLM training data contamination.
- **Community contributions**: accept community-submitted examples via pull requests, with review.

Without long-term maintenance, the benchmark becomes stale and loses value.

---

## 4.7 Why This Benchmark Is the Right Size

2000 examples is small by NLP standards (where benchmarks can have 100k+ examples) but appropriate for this task:

- Each example requires 3 trained annotators and ~5 minutes per claim, so 2000 examples × 2 claims each × 3 annotators × 5 minutes = 500 annotator-hours. Significant but feasible.
- The task is harder than typical NLP classification (annotators must verify against the board), so quality matters more than quantity.
- 2000 examples is enough for train/dev/test splits with statistical power, especially with stratified sampling.

A larger benchmark (5000+ examples) is a v2 goal if the v1 benchmark is well-received.

---

## 4.8 Key Reminders

- The benchmark IS the long-term research contribution. It will outlive any specific verifier.
- Schema: per-example with PGN, commentary, claims, ground-truth verdicts, annotator labels.
- Construction: 60% ACL, 30% Synthetic, 10% manual. 3 annotators per claim, majority vote.
- Splits: 60/20/20, stratified by claim type.
- Target kappa: >= 0.7 overall, >= 0.8 for binary claims, >= 0.5 for soft claims.
- Four baselines required: LLM-only, Stockfish-only, rule-based, hybrid.
- Release on Hugging Face + GitHub with annotator guidelines, raw labels, code, and CC-BY 4.0 license.
- Long-term maintenance: versioning, test set protection, periodic refresh, community contributions.
- 2000 examples is the right size for v1. Larger is a v2 goal.
