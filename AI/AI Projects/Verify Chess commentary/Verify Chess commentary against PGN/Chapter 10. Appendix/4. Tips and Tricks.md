## 4.1 Python and python-chess Tips

### 4.1.1 Use `board.copy()` not `copy.copy(board)`

`board.copy()` is a built-in method of `chess.Board` and is faster than the generic `copy.copy()`. Always use the built-in.

```python
# Good
new_board = board.copy()
new_board.push(move)

# Bad (slower)
import copy
new_board = copy.copy(board)
```

### 4.1.2 Use `board.parse_san()` not `Move.from_san()`

`Move.from_san()` is deprecated and unreliable. Always parse SAN in the context of a board.

```python
# Good
move = board.parse_san("Nf3")

# Bad (deprecated, may fail)
move = chess.Move.from_san("Nf3")
```

### 4.1.3 Use `chess.SQUARES` to iterate over all squares

`chess.SQUARES` is a list of all 64 square indices. Use it instead of `range(64)`.

```python
for square in chess.SQUARES:
    piece = board.piece_at(square)
    if piece and piece.piece_type == chess.KNIGHT:
        print(f"Knight on {chess.square_name(square)}")
```

### 4.1.4 Use `chess.square_name()` and `chess.parse_square()` for conversion

These convert between square names ("e4") and indices (28). Use them instead of manual arithmetic.

```python
square = chess.parse_square("e4")  # 28
name = chess.square_name(28)  # "e4"
```

### 4.1.5 Use `board.attackers(color, square)` for attack queries

This returns the set of squares attacking the given square for the given color. Faster and cleaner than manually iterating pieces.

```python
attackers = board.attackers(chess.WHITE, chess.E4)
for attacker_square in attackers:
    piece = board.piece_at(attacker_square)
    print(f"{piece} on {chess.square_name(attacker_square)} attacks e4")
```

### 4.1.6 Use `board.pin(color, square)` for pin detection

This returns the set of squares forming the pin ray on the given piece. Faster and more reliable than manually checking line geometry.

```python
pin_ray = board.pin(chess.BLACK, chess.F6)
if pin_ray:  # non-empty set means the piece is pinned
    print(f"Knight on f6 is pinned along: {pin_ray}")
```

### 4.1.7 Use `chess.pgn.read_game()` in a loop for multi-game PGN files

`read_game()` reads ONE game. Call it repeatedly until it returns `None`.

```python
with open("many_games.pgn") as f:
    while True:
        game = chess.pgn.read_game(f)
        if game is None:
            break
        process(game)
```

## 4.2 Stockfish Tips

### 4.2.1 Set `Threads` and `Hash` for performance

Default Stockfish uses 1 thread and small hash. Set these for better performance.

```python
engine._send("setoption name Threads value 4")
engine._send("setoption name Hash value 256")  # 256 MB hash
```

### 4.2.2 Use `go depth N` not `go time N` for consistent evaluation

`go depth 18` searches to depth 18 regardless of time. `go time 1000` searches for 1 second regardless of depth. Depth-based search is more consistent across runs.

```python
engine._send("go depth 18")
```

### 4.2.3 Always send `ucinewgame` before a new game

This clears Stockfish's internal state (hash table, etc.).

```python
engine._send("ucinewgame")
engine._send("isready")
engine._wait_for("readyok")
```

### 4.2.4 Strip halfmove clock and fullmove number from FEN for caching

The halfmove clock and fullmove number do not affect evaluation (for our purposes). Strip them when caching to maximize cache hits.

```python
def cache_key(fen):
    parts = fen.split()
    return " ".join(parts[:4])  # piece placement, active color, castling, en passant
```

### 4.2.5 Set Contempt to 0

Non-zero Contempt biases evaluations away from draws. For verification, you want neutral evaluations.

```python
engine._send("setoption name Contempt value 0")
```

### 4.2.6 Use MultiPV when you need top-N lines

```python
engine._send("setoption name MultiPV value 3")
# Now `go depth 18` returns the top 3 lines
```

## 4.3 LLM Tips

### 4.3.1 Use structured output mode

Modern LLMs support structured output. Use it. Do not rely on "please output JSON" prompts.

```python
# OpenAI
response = client.chat.completions.create(
    model="gpt-4o-mini",
    response_format={"type": "json_schema", "json_schema": {...}},
    messages=[...]
)

# Anthropic
response = client.messages.create(
    model="claude-3-5-sonnet",
    tools=[{...}],
    messages=[...]
)
```

### 4.3.2 Use temperature 0

For claim extraction, determinism is more important than creativity.

```python
response = client.chat.completions.create(
    model="gpt-4o-mini",
    temperature=0,
    ...
)
```

### 4.3.3 Include 2-3 few-shot examples

Pick examples that span claim types and ambiguity levels. Include the LLM's expected output for each.

```text
Example 1:
Input: "The knight moves to f3."
Output: {"claim_type": "move_description", "params": {"color": null, "piece": "knight", "destination_square": "f3"}}

Example 2:
Input: "White captures the rook."
Output: {"claim_type": "capture", "params": {"color": "white", "target_piece": "rook"}}

Example 3:
Input: "Black has the initiative."
Output: {"claim_type": "strategic_initiative", "params": {"color": "black", "direction": "strong"}}
```

### 4.3.4 Cache by (prose_hash, prompt_version, model_version)

Cache key includes the prose hash, the prompt version (so changes to the prompt invalidate the cache), and the model version (so model upgrades invalidate the cache).

```python
import hashlib

def cache_key(prose, prompt_version, model_version):
    prose_hash = hashlib.sha256(prose.encode()).hexdigest()
    return f"{prose_hash}_{prompt_version}_{model_version}"
```

### 4.3.5 Use a cheaper model first, fall back to a stronger model

Start with GPT-4o-mini (cheap, fast). If validation fails (LLM output does not match schema), retry with GPT-4 (expensive, more reliable).

```python
def extract_claims(prose):
    for model in ["gpt-4o-mini", "gpt-4o"]:
        result = call_llm(model, prose)
        if validate(result):
            return result
    raise ExtractionFailedError("Both models failed validation.")
```

## 4.4 Verifier Design Tips

### 4.4.1 Make the verifier a pure function

No I/O. No global state. No randomness. Same inputs always produce the same output. This is the verifier's defining property.

```python
def verify(claim: Claim, facts: FactsDatabase) -> Verdict:
    # Pure function. No I/O, no side effects.
    handler = HANDLERS.get(claim.claim_type)
    if handler is None:
        return Verdict("Cannot verify automatically", f"Unsupported type: {claim.claim_type}")
    return handler(claim, facts)
```

### 4.4.2 Use a dispatcher pattern

Map claim types to handlers via a dict. Adding a new claim type = adding a new entry.

```python
HANDLERS = {
    "move_description": handle_move_description,
    "capture": handle_capture,
    "material_gain": handle_material_gain,
    "tactical_fork": handle_fork,
    # ... etc.
}
```

### 4.4.3 Always include an explanation

Bare verdicts ("Verified") are not useful. Always include a one-sentence explanation referencing a specific board fact.

```python
# Bad
return Verdict("Verified", "")

# Good
return Verdict("Verified", f"The move at ply {ply.ply_index} is {ply.san}, a {color} {piece} moving to {square}.")
```

### 4.4.4 Use exception classes for graceful degradation

Define `AmbiguousClaimError`, `FactLookupError`, etc. Handlers raise these; the dispatcher catches and converts to verdicts.

```python
class AmbiguousClaimError(Exception): pass
class FactLookupError(Exception): pass

def verify(claim, facts):
    try:
        return HANDLERS[claim.claim_type](claim, facts)
    except AmbiguousClaimError as e:
        return Verdict("Ambiguous", str(e))
    except FactLookupError as e:
        return Verdict("Cannot verify automatically", str(e))
```

### 4.4.5 Test with property-based tests

Use Hypothesis or similar to generate random claims and facts databases. Check invariants: verifier never crashes, always returns a valid label, etc.

```python
from hypothesis import given, strategies as st

@given(random_claim(), random_facts())
def test_verifier_never_crashes(claim, facts):
    verdict = verify(claim, facts)
    assert verdict.label in VALID_LABELS
```

## 4.5 Caching Tips

### 4.5.1 Use SQLite for engine eval cache

A SQLite database with FEN as the primary key is fast, persistent, and concurrent-safe.

```python
import sqlite3

conn = sqlite3.connect("eval_cache.db")
conn.execute("CREATE TABLE IF NOT EXISTS evals (fen TEXT PRIMARY KEY, eval_cp INTEGER, ...)")

def cached_eval(fen):
    row = conn.execute("SELECT eval_cp FROM evals WHERE fen = ?", (fen,)).fetchone()
    if row:
        return row[0]
    eval_cp = stockfish.evaluate(fen)
    conn.execute("INSERT INTO evals VALUES (?, ?)", (fen, eval_cp))
    conn.commit()
    return eval_cp
```

### 4.5.2 Use file-based cache for facts databases

Each game's facts database is a single JSON file. Cache key is the source file path + PGN block hash.

```python
import hashlib, json, os

def get_facts(markdown_path, pgn_block):
    pgn_hash = hashlib.sha256(pgn_block.encode()).hexdigest()[:16]
    cache_path = f"facts/{os.path.basename(markdown_path)}_{pgn_hash}.json"
    if os.path.exists(cache_path):
        return json.load(open(cache_path))
    facts = build_facts(pgn_block)
    json.dump(facts, open(cache_path, "w"))
    return facts
```

### 4.5.3 Include version stamps in cache keys

Cache keys should include the Stockfish version, python-chess version, and prompt version. Otherwise, cache hits return stale results after upgrades.

```python
def cache_key(...):
    return f"{prose_hash}_{prompt_version}_{model_version}_{stockfish_version}_{python_chess_version}"
```

## 4.6 Testing Tips

### 4.6.1 Use known games for invariant tests

Kasparov-Topalov 1999, Karpov-Kasparov 1985, etc. Their FENs at specific plies are documented. Use them as test fixtures.

```python
def test_kasparov_topalov_1999():
    facts = build_facts(load_pgn("kasparov_topalov_1999.pgn"))
    assert facts.plies[44].fen_after == "r1bq1rk1/pp2bppp/2n1p3/8/..."
```

### 4.6.2 Test edge cases explicitly

- Castling (both sides).
- En passant.
- Promotion (to queen, rook, bishop, knight).
- Check, checkmate, stalemate.
- Threefold repetition (if v2 supports it).
- 50-move rule (if v2 supports it).

### 4.6.3 Test failure modes

- Malformed PGN.
- Missing PGN block.
- Empty prose.
- LLM returns malformed JSON.
- LLM returns fields outside the schema.
- Stockfish crashes.

The verifier should handle all of these gracefully (not crash).

## 4.7 Workflow Tips

### 4.7.1 Build the facts database first

Phase 1 is the foundation. Get it right before anything else. Without a correct facts database, every verdict is suspect.

### 4.7.2 Build a CLI early

Even a basic CLI (`python verify.py note.md`) makes iteration much faster than running scripts manually.

### 4.7.3 Use rich for terminal output

The `rich` library makes terminal output much more readable. Use it for the CLI's progress bars, tables, and colors.

### 4.7.4 Commit early and often

The verifier evolves. Commit every working state. Tag releases (v0.1, v0.2, etc.).

### 4.7.5 Write the README before the code

A good README forces you to clarify the design. Write it first; update it as the code evolves.

## 4.8 Author Tips (for Users of the Verifier)

When writing chess notes that this verifier will check:

### 4.8.1 Specify the color

"The white knight" is unambiguous; "the knight" might require disambiguation.

### 4.8.2 Use SAN squares

"e5" is clearer than "the fifth square of the e-file".

### 4.8.3 Mention special moves explicitly

"Castles kingside", "promotes to a queen", "captures en passant".

### 4.8.4 Avoid pronouns

"The bishop captures the rook" is better than "It captures the rook".

### 4.8.5 One move per sentence

"The knight moves to e5, then the bishop pins the rook" is two claims in one sentence. Split them.

### 4.8.6 Hedge strategic claims

"White appears to have the initiative" is safer than "White has the initiative".

### 4.8.7 Cite specific evidence

"White's bishop on d3 controls the long diagonal" is more verifiable than "White has active pieces".

### 4.8.8 Use engine evaluation as a sanity check

If Stockfish evaluates the position as equal, claims of "decisive advantage" are likely wrong.

## 4.9 Documentation Tips

### 4.9.1 Document every design decision

When you make a design decision, write down: (a) the decision, (b) the alternatives considered, (c) the rationale. This is invaluable when you revisit the decision months later.

### 4.9.2 Keep a running list of known issues

A `KNOWN_ISSUES.md` file is more useful than scattered GitHub issues. Review it periodically.

### 4.9.3 Write examples for every claim type

Each claim type should have at least one worked example in the documentation. This vault's Chapter 9 is the template.

### 4.9.4 Update the glossary as terms emerge

New terms will emerge as the project evolves. Add them to the glossary (Chapter 10.1) as they appear.
