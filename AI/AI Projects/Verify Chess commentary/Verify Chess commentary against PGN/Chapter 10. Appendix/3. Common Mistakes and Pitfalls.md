# 3. Common Mistakes and Pitfalls

> A catalog of the mistakes most commonly made when building a chess commentary verifier. Each entry describes the mistake, explains why it is tempting, explains why it is wrong, and gives the correct approach.

This note is the project's scar tissue. Read it before starting implementation; re-read it when debugging.

---

## 3.1 Architecture Mistakes

### 3.1.1 Letting the LLM judge truth

**Mistake**: Asking the LLM "is this sentence true given this position?" and using its answer as the verdict.

**Why tempting**: One LLM call is simpler than building a facts database, claim extractor, and verifier. It feels like the LLM should be able to do it.

**Why wrong**: LLMs produce confident errors (Chapter 1.2). They cannot reliably track board state past ~15-20 plies (AAAI 2023). They cannot count material or identify pins reliably (ChessQA). The verdict is the most important output of the system; it cannot be left to a probabilistic model.

**Correct approach**: Use the LLM only for claim extraction. Verify claims symbolically. See [[Chapter 2. System Architecture/2. The Core Idea Separation of Concerns|2. The Core Idea Separation of Concerns]].

---

### 3.1.2 Letting the LLM see the PGN

**Mistake**: Including the PGN in the LLM prompt so it has "context" for claim extraction.

**Why tempting**: The LLM might be able to use the PGN to disambiguate claims. More context seems better.

**Why wrong**: This breaks the separation of concerns. The LLM will start to use the PGN to judge truth (even if you tell it not to), reintroducing the LLM-as-judge anti-pattern. The information boundary is what keeps the architecture honest.

**Correct approach**: LLM sees prose only. The verifier sees PGN-derived facts only. They communicate only through structured claims and the facts database.

---

### 3.1.3 Calling Stockfish on the fly in the verifier

**Mistake**: Having the verifier call Stockfish when it needs an evaluation that is not in the facts database.

**Why tempting**: It avoids precomputing evaluations for positions that may never be queried. Saves time on average.

**Why wrong**: Breaks determinism (Stockfish can produce slightly different evaluations across runs due to threading). Breaks testability (verifier now depends on Stockfish, making unit tests hard). Breaks performance budget (on-the-fly Stockfish calls are slow).

**Correct approach**: Precompute all evaluations when the facts database is built. If a fact is missing, the verifier emits `Cannot verify automatically`.

---

### 3.1.4 Collapsing verdict labels to binary

**Mistake**: Reducing the six verdict labels to "correct" or "incorrect".

**Why tempting**: Binary is simpler to evaluate and to communicate.

**Why wrong**: Loses too much information. Cannot distinguish "wrong" from "unverifiable" from "invented". Authors need the distinction to know how to respond.

**Correct approach**: Use all six verdict labels. See [[Chapter 2. System Architecture/3. Inputs and Outputs|3. Inputs and Outputs]].

## 3.2 Implementation Mistakes

### 3.2.1 Parsing SAN without board context

**Mistake**: Using `chess.Move.from_san("Nf3")` (deprecated) instead of `board.parse_san("Nf3")`.

**Why tempting**: Looks simpler; does not require a board object.

**Why wrong**: SAN is context-dependent. "Nf3" could mean different moves in different positions. `Move.from_san` either throws or returns a wrong move.

**Correct approach**: Always parse SAN against the board on which the move was made. Use `board.parse_san()`.

---

### 3.2.2 Forgetting to copy the board before push

**Mistake**: Calling `board.push(move)` and then expecting the original board to be unchanged.

**Why tempting**: `push` is a common method name and feels like it should be non-mutating.

**Why wrong**: `push` mutates the board in place. Subsequent code that uses the original board gets the post-move state.

**Correct approach**: Use `board.copy()` to preserve the original. Or use `board.push(move)` and then `board.pop()` to undo.

---

### 3.2.3 Off-by-one in line numbers

**Mistake**: Verifier reports "Line 24" when the actual line is 25.

**Why tempting**: Zero-indexed vs one-indexed is easy to confuse. Different tools use different conventions.

**Why wrong**: Authors rely on line numbers to find errors. Off-by-one errors make the report useless.

**Correct approach**: Use one-indexed line numbers (matching Markdown editor displays). Test line numbers against a known file.

---

### 3.2.4 Not caching Stockfish evaluations

**Mistake**: Re-running Stockfish on every verification pass.

**Why tempting**: Caching adds complexity. The first run is fine; why bother?

**Why wrong**: Re-running Stockfish is slow (seconds per position) and expensive. Iterative development becomes painful. The user will not tolerate a 30-second delay on every keystroke in the Obsidian plugin.

**Correct approach**: Cache evaluations keyed by FEN (with halfmove clock and fullmove number stripped). Use SQLite for cross-vault persistence. See [[Chapter 3. Core Components/2. Stockfish|2. Stockfish]].

---

### 3.2.5 Not caching LLM outputs

**Mistake**: Re-running the LLM on every verification pass.

**Why tempting**: Same as above.

**Why wrong**: LLM calls cost money and add latency. Re-running on unchanged prose wastes both.

**Correct approach**: Cache LLM outputs keyed by `(prose_hash, prompt_version, model_version)`. Re-use cached output when the prose has not changed.

---

### 3.2.6 Using `is_capture` without checking the captured piece

**Mistake**: In a capture claim, checking only `ply.is_capture` and not `ply.captured_piece`.

**Why tempting**: `is_capture` is a single boolean; `captured_piece` requires another check.

**Why wrong**: The claim might specify the captured piece ("bishop captures the rook"). Without checking `captured_piece`, the verifier would verify any capture by the bishop, even if it captured a pawn.

**Correct approach**: Check all relevant fields: `is_capture`, `captured_piece`, `captured_color`, `to_square`.

---

### 3.2.7 Confusing en passant target square with captured square

**Mistake**: Assuming the captured pawn is on the destination square for en passant captures.

**Why tempting**: For normal captures, the captured piece IS on the destination square. The pattern is the same... except for en passant.

**Why wrong**: For en passant, the captured pawn is on a different square (one rank closer to the capturer's starting rank). The destination square is empty before the capture.

**Correct approach**: Check `is_en_passant`. If true, the captured pawn is on a different square. Mention this in the verdict explanation.

---

## 3.3 Evaluation Mistakes

### 3.3.1 Test set contamination

**Mistake**: Using the test set to tune the verifier or the LLM prompts.

**Why tempting**: The test set is the most representative data; using it for tuning feels natural.

**Why wrong**: Results on a contaminated test set are not generalizable. The system will perform worse in production.

**Correct approach**: Strict separation of train/dev/test. Tune only on dev. Run on test only once, at the end.

---

### 3.3.2 Annotator bias

**Mistake**: Showing annotators the verifier's output before they label.

**Why tempting**: Showing the verifier's output might help annotators calibrate.

**Why wrong**: Annotators will be biased toward agreeing or disagreeing with the verifier, depending on their personality. The labels become a function of the verifier, not an independent ground truth.

**Correct approach**: Annotators label without seeing the verifier's output. The verifier is evaluated against labels that were produced independently.

---

### 3.3.3 Cherry-picking qualitative examples

**Mistake**: In qualitative analysis, showing only the verifier's best examples.

**Why tempting**: Best examples make the system look good.

**Why wrong**: Reviewers and users will see the verifier as stronger than it is. When they encounter failures in practice, they will be disappointed.

**Correct approach**: Pick representative examples: 10 successes, 10 failures, 10 borderline. Categorize failures and discuss patterns.

---

### 3.3.4 Ignoring latency and cost

**Mistake**: Reporting only F1, ignoring latency and cost.

**Why tempting**: F1 is the primary metric; latency and cost are "engineering concerns".

**Why wrong**: A system with F1 = 0.85 but $0.10 per note is worse in practice than a system with F1 = 0.80 and $0.005 per note. Reviewers and users care about all three.

**Correct approach**: Report F1, latency, and cost together. Discuss trade-offs.

---

## 3.4 Prompt Engineering Mistakes

### 3.3.1 Not using structured output mode

**Mistake**: Asking the LLM to "output JSON" without using the model's structured output feature.

**Why tempting**: Structured output mode is a recent feature; older code examples do not use it.

**Why wrong**: Without structured output mode, the LLM produces malformed JSON ~5% of the time. Parsing fails, and the system becomes unreliable.

**Correct approach**: Use the model's structured output mode (JSON mode, function calling, or whatever the API provides). Validate the output against the schema.

---

### 3.3.2 Setting temperature above 0

**Mistake**: Using temperature 0.5 or higher for claim extraction.

**Why tempting**: Higher temperature produces more varied output, which might be more creative.

**Why wrong**: Claim extraction should be deterministic. Higher temperature introduces variability that complicates debugging and benchmarking.

**Correct approach**: Use temperature 0 (or the model's equivalent). Cache the output to ensure reproducibility.

---

### 3.3.3 Not including few-shot examples

**Mistake**: Using a zero-shot prompt for claim extraction.

**Why tempting**: Zero-shot is simpler and uses fewer tokens.

**Why wrong**: Zero-shot claim extraction is unreliable, especially for ambiguous sentences. Few-shot examples dramatically improve consistency.

**Correct approach**: Include 2-3 worked examples in the prompt, covering different claim types and ambiguity levels.

---

### 3.3.4 Not validating LLM output strictly

**Mistake**: Accepting any JSON from the LLM as a valid claim list.

**Why tempting**: Strict validation is more code. If the LLM produces valid JSON, why bother?

**Why wrong**: The LLM sometimes includes fields outside the schema (e.g., `is_true: false` — the LLM trying to do the verifier's job). Without strict validation, these fields leak into the verifier.

**Correct approach**: Validate against a strict schema. Reject any output with fields not in the schema. Re-prompt on validation failure.

## 3.5 Strategic Mistakes

### 3.5.1 Trying to support all claim types in v1

**Mistake**: Building tactical, strategic, and positional claim handlers in v1.

**Why tempting**: The full claim type catalog is more impressive than a subset.

**Why wrong**: v1 should focus on the highest-volume, easiest-to-verify claim types (move descriptions, captures, material). Adding tactical and strategic claims in v1 delays the release and increases the bug surface.

**Correct approach**: v1 supports three claim types. v2 adds tactical. v3 adds strategic and positional. See [[Chapter 8. Implementation Roadmap/1. Step by Step Build Plan|1. Step by Step Build Plan]].

---

### 3.5.2 Skipping the benchmark

**Mistake**: Building the verifier without building the benchmark.

**Why tempting**: The verifier is more interesting than the benchmark. The benchmark takes time to label.

**Why wrong**: Without a benchmark, you cannot evaluate the verifier rigorously. The project becomes engineering, not research. Publishability suffers.

**Correct approach**: Build the benchmark in parallel with the verifier. Even a 200-example pilot benchmark is better than none. See [[Chapter 7. Novelty and Research Value/4. Defining the Benchmark|4. Defining the Benchmark]].

---

### 3.5.3 Not publishing early

**Mistake**: Waiting until the system is "perfect" before publishing.

**Why tempting**: Embarrassment about imperfections. Desire to make a strong first impression.

**Why wrong**: Someone else might publish first. Early publication establishes priority and invites feedback.

**Correct approach**: Post an arXiv preprint as soon as the benchmark and v1 verifier are ready, even if results are not yet optimal. Iterate publicly.

---

### 3.5.4 Treating this as a one-person project

**Mistake**: Trying to do everything yourself: NLP, chess engine integration, software engineering, chess domain expertise, annotation, paper writing.

**Why tempting**: Independence feels simpler than coordination.

**Why wrong**: The project requires cross-disciplinary expertise that no single person has. Quality suffers.

**Correct approach**: Collaborate. Find a chess expert for the claim type taxonomy. Find an NLP expert for the LLM prompting. Find a software engineer for the pipeline. Find annotators for the benchmark.

---

## 3.6 Key Reminders

- Architecture mistakes: LLM-as-judge, LLM-sees-PGN, on-the-fly Stockfish, binary verdicts.
- Implementation mistakes: SAN parsing without board, mutating board without copy, off-by-one line numbers, no caching, missing field checks, en passant confusion.
- Evaluation mistakes: test contamination, annotator bias, cherry-picking, ignoring latency/cost.
- Prompt engineering mistakes: no structured output, temperature > 0, no few-shot, no strict validation.
- Strategic mistakes: too many claim types in v1, skipping benchmark, not publishing early, one-person project.
- The biggest single mistake is letting the LLM judge truth. Everything else is secondary.
- Read this note before starting implementation. Re-read it when debugging.
