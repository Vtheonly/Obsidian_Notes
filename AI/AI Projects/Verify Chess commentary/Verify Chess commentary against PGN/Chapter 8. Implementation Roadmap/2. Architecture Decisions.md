# 2. Architecture Decisions

> **Architecture decisions in one sentence**: The system makes seven key architecture decisions — separation of concerns, per-ply granularity, structured LLM output, six-verdict label set, deterministic verifier, aggressive caching, and local Stockfish — each justified by a specific reason.

This note records each decision, the alternatives considered, and the rationale.

---

## 2.1 Decision 1: Strict Separation of Language and Reasoning

**Decision**: The LLM extracts claims; the symbolic engine verifies them. The LLM never sees PGN; the verifier never sees English.

**Alternatives considered**:
- **Single LLM call** (LLM sees position + commentary, outputs verdict). Rejected: produces confident errors.
- **LLM co-pilot** (LLM proposes verdicts, engine confirms). Rejected: introduces LLM into the judging step, which compromises determinism.

**Rationale**: The 2022 hybrid paper (Chapter 5.2) validates this separation for generation. Empirical evidence (Chapter 5.5) shows LLMs cannot reliably track board state. The separation is necessary regardless of LLM strength.

**Trade-offs**: 
- Pro: determinism, auditability, easy benchmarking.
- Con: requires building a facts database and a verifier, which is more engineering than a single LLM call.

---

## 2.2 Decision 2: Per-Ply Granularity for the Facts Database

**Decision**: The atomic unit of the facts database is a ply (half-move), not a move or a position.

**Alternatives considered**:
- **Per-move** (two plies). Rejected: most claims refer to a specific ply, not a move. Off-by-one errors are common with per-move indexing.
- **Per-position** (one entry per unique FEN). Rejected: claims often refer to "the move that produced this position", which requires ply context.

**Rationale**: A ply is the smallest unit of chess action. Every claim can be aligned to a ply. Per-ply indexing makes claim-to-ply alignment unambiguous.

**Trade-offs**:
- Pro: unambiguous alignment, simple verification rules.
- Con: more records than per-move (2x), but each record is small.

---

## 2.3 Decision 3: Structured LLM Output

**Decision**: The LLM produces JSON conforming to a strict schema. Validation rejects any output with fields outside the schema.

**Alternatives considered**:
- **Free-form text**. Rejected: parsing free-form text is unreliable.
- **Function calling / tool use**. Considered: this is equivalent to structured output mode in modern LLMs; use whichever the model supports.

**Rationale**: Structured output mode in modern LLMs (GPT-4, Claude 3.5, GLM-4) produces valid JSON >99.9% of the time. Strict schema validation catches the remaining 0.1%.

**Trade-offs**:
- Pro: deterministic parsing, easy validation, easy testing.
- Con: less natural for the LLM (might constrain its reasoning). Mitigated by including a `notes` field for the LLM to express uncertainty.

---

## 2.4 Decision 4: Six-Verdict Label Set

**Decision**: The verifier emits one of six verdicts: Verified, Contradicted, Supported (soft), Ambiguous, Cannot verify automatically, Possible hallucination.

**Alternatives considered**:
- **Binary (correct/incorrect)**. Rejected: loses too much information. Cannot distinguish "wrong" from "unverifiable".
- **Three labels (correct/incorrect/uncertain)**. Rejected: still loses the distinction between "soft support" and "binary verification".
- **Numeric confidence (0-100)**. Considered: used inside strategic claim verification, but not as the top-level label. Numeric confidence is hard for authors to interpret.

**Rationale**: The six labels cover the full space of verification outcomes:
- Binary claims get Verified or Contradicted.
- Soft claims get Supported (soft) or Contradicted (soft) (low confidence).
- Genuinely unclear claims get Ambiguous.
- Unsupported claim types get Cannot verify automatically.
- Invented facts get Possible hallucination.

**Trade-offs**:
- Pro: precise communication, easy to act on.
- Con: more labels means more annotator disagreement. Mitigated by clear definitions and training.

---

## 2.5 Decision 5: Deterministic Verifier

**Decision**: The verifier is a pure function of `(claim, facts) -> verdict`. No I/O, no LLM, no engine calls on the fly.

**Alternatives considered**:
- **Engine-on-the-fly** (verifier calls Stockfish when needed). Rejected: slow and nondeterministic (Stockfish evaluations can vary slightly across runs due to threading).
- **LLM disambiguation** (verifier asks LLM to clarify ambiguous claims). Rejected: introduces LLM into the verifier, breaking determinism.

**Rationale**: Determinism is essential for benchmarking and debugging. If the verifier is deterministic, you can unit-test it, ablate it, and trust its outputs. If it is not, you cannot.

**Trade-offs**:
- Pro: testable, auditable, cacheable.
- Con: cannot handle claims that require ad-hoc analysis. Mitigated by marking such claims `Cannot verify automatically`.

---

## 2.6 Decision 6: Aggressive Caching

**Decision**: Cache facts databases (by PGN hash + Stockfish version), LLM outputs (by prose hash + prompt version + model version), and verdicts (by claim hash + facts hash).

**Alternatives considered**:
- **No caching**. Rejected: too slow for iterative development. Re-running Stockfish on every change is unusable.
- **In-memory only**. Rejected: cache is lost on restart. Cross-vault reuse impossible.
- **SQLite**. Chosen for engine eval cache (key = FEN). JSON files chosen for facts databases and LLM outputs.

**Rationale**: Engine analysis is the most expensive step (~5s per game). LLM calls are also expensive (~2-5s plus API cost). Caching reduces both to near-zero on unchanged input.

**Trade-offs**:
- Pro: massive speedup on iterative development.
- Con: cache invalidation is tricky. Mitigated by including version stamps in cache keys.

---

## 2.7 Decision 7: Local Stockfish

**Decision**: Run Stockfish as a local subprocess. Do not use cloud engines.

**Alternatives considered**:
- **Lichess Cloud Eval API**. Rejected: rate-limited, network latency, reproducibility issues.
- **Chess.com analysis API**. Rejected: not publicly available; same concerns.
- **Cloud Stockfish providers**. Rejected: cost, latency, privacy.

**Rationale**: Local Stockfish is fast (no network), free (no API cost), private (no data leaves the user's machine), and reproducible (version is pinned). For an Obsidian plugin, local execution is essential — users will not tolerate cloud dependencies for inline feedback.

**Trade-offs**:
- Pro: fast, free, private, reproducible.
- Con: requires the user to install Stockfish. Mitigated by bundling Stockfish with the plugin or providing a download script.

---

## 2.8 Decision 8: Markdown as the Input Format

**Decision**: The system reads Markdown files. PGN is identified by fenced code blocks; prose is everything else.

**Alternatives considered**:
- **Custom format**. Rejected: Markdown is the standard for chess notes (Obsidian, GitHub, Reddit).
- **HTML**. Rejected: harder to parse, less human-readable.
- **Direct PGN files**. Rejected: cannot include prose.

**Rationale**: Markdown is the lingua franca of personal knowledge management. Obsidian uses it. GitHub renders it. The target user (chess authors with personal vaults) already uses it.

**Trade-offs**:
- Pro: maximally compatible with existing workflows.
- Con: identifying PGN blocks requires heuristics (fenced code with `pgn` language hint, or content matching PGN patterns). Mitigated by accepting both.

---

## 2.9 Decision 9: Python as the Implementation Language

**Decision**: The verifier and pipeline are implemented in Python. The Obsidian plugin (Phase 7) is TypeScript, calling the Python backend via HTTP or porting the verifier to TypeScript.

**Alternatives considered**:
- **TypeScript end-to-end**. Considered: would simplify the plugin. But python-chess has no JavaScript equivalent with the same feature coverage, and Stockfish integration is cleaner in Python.
- **Rust**. Considered: faster, but the verifier is not the bottleneck (LLM and Stockfish are), and Rust's development speed is slower.

**Rationale**: Python has the best chess ecosystem (python-chess, easy Stockfish integration, mature NLP libraries). The verifier's performance is irrelevant (1-2 ms per claim), so Python's speed is fine.

**Trade-offs**:
- Pro: rich ecosystem, fast development.
- Con: plugin requires either a Python backend or a TypeScript port. Mitigated by the port being relatively simple (the verifier is ~1000 lines of Python).

---

## 2.10 How to Reverse a Decision

Architecture decisions should be reversible if evidence demands it. The process:

1. **Identify the decision** that is failing (e.g., "the six-verdict label set is too coarse").
2. **Document the failure** with specific examples (e.g., "in the CCVB benchmark, 15% of verdicts are borderline between Supported and Ambiguous").
3. **Propose the change** (e.g., "add a confidence score to soft verdicts").
4. **Evaluate the change** against the original rationale. Does the new evidence outweigh the original rationale?
5. **Implement the change** with a version bump and migration plan.

Do not reverse decisions lightly. Each reversal costs time and introduces bugs. But do not let a bad decision stand out of stubbornness.

---

## 2.11 Key Reminders

- Nine key architecture decisions, each with a specific rationale.
- Decision 1 (separation of concerns) is the most important. All others follow from it.
- Decision 5 (deterministic verifier) is what enables benchmarking and publishing.
- Decision 6 (aggressive caching) is what makes the system usable in practice.
- Decision 7 (local Stockfish) is what makes the Obsidian plugin viable.
- Each decision has trade-offs. Document them; do not pretend they don't exist.
- Reversing decisions is allowed but expensive. Do it only with strong evidence.
- When in doubt, prefer the decision that enables benchmarking and reproducibility. Research value > engineering convenience.
