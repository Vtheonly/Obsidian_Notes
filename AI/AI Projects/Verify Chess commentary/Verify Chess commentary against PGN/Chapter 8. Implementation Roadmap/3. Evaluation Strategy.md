# 3. Evaluation Strategy

> **Evaluation in one sentence**: Measure the verifier on precision, recall, F1 (overall and per-claim-type), inter-annotator agreement, ablation studies, and qualitative error analysis — against three baselines (LLM-only, engine-only, rule-based) on the CCVB benchmark.

This note specifies the evaluation in enough detail to write the experiments section of a paper.

---

## 3.1 Primary Metrics

### 3.1.1 Precision

Of the claims the verifier labeled `Verified` or `Contradicted`, what fraction match the ground truth?

```text
precision = TP / (TP + FP)
```

Where:
- TP (true positive): verifier says `Verified` or `Contradicted`, ground truth agrees.
- FP (false positive): verifier says `Verified` or `Contradicted`, ground truth disagrees (or is `Ambiguous`).

### 3.1.2 Recall

Of the claims the ground truth labels `Verified` or `Contradicted`, what fraction did the verifier also label correctly?

```text
recall = TP / (TP + FN)
```

Where:
- FN (false negative): ground truth says `Verified` or `Contradicted`, verifier says something else (or does not extract the claim).

### 3.1.3 F1

```text
F1 = 2 * (precision * recall) / (precision + recall)
```

F1 is the harmonic mean of precision and recall. It is the primary metric for ranking systems.

### 3.1.4 Per-claim-type breakdown

Compute precision, recall, F1 separately for each claim type:

- move_description
- capture
- material_gain
- tactical_fork
- tactical_pin
- strategic_king_safety
- positional_doubled_pawns
- (etc.)

This breakdown reveals where the system is strong and weak. Overall F1 can hide important per-type variation.

## 3.2 Secondary Metrics

### 3.2.1 Inter-annotator agreement (Cohen's kappa)

Measures how often annotators agree, corrected for chance agreement. Computed pairwise, then averaged.

```text
kappa = (P_observed - P_expected) / (1 - P_expected)
```

Where:
- `P_observed` = fraction of claims where annotators agree.
- `P_expected` = fraction of agreement expected by chance (given the marginal label distribution).

Target: kappa >= 0.7 overall. Per-type targets: >= 0.8 for binary claims, >= 0.5 for soft claims.

### 3.2.2 Verifier agreement with ground truth (kappa)

Same metric, but comparing verifier labels to majority-vote ground truth. This is a stricter measure than precision/recall because it corrects for chance.

### 3.2.3 Extraction accuracy

Of the claims the LLM extracted, what fraction are "correct extractions" (i.e., the LLM correctly identified the claim type and parameters)?

This is measured by comparing extracted claims to a manually labeled "gold extraction" on a sample of 200 examples. The verifier depends on extraction; if extraction is bad, verification cannot be good.

### 3.2.4 End-to-end latency

Time from "user submits note" to "report produced". Includes:
- Notation extraction: <100 ms.
- Facts database build (with cache): <500 ms cold, <50 ms warm.
- LLM claim extraction: 2-5 s.
- Verification: <50 ms.
- Report generation: <50 ms.

Total: 3-6 s cold, 1-2 s warm. Acceptable for batch; needs optimization for interactive use.

### 3.2.5 Cost per note

API cost (LLM calls) + compute cost (Stockfish). Target: < $0.01 per note for frontier LLMs, < $0.002 per note for mini LLMs.

## 3.3 Ablation Studies

Ablations answer: "how much does each component contribute?"

### 3.3.1 Remove the LLM (rule-based extraction only)

Replace the LLM claim extractor with a regex-based extractor. Measure F1. Expected: large drop, especially on multi-claim sentences and anaphora.

### 3.3.2 Remove the attack maps

Strip the attack map fields from the facts database. The verifier cannot check tactical claims. Measure F1. Expected: large drop on tactical claims, no change on move descriptions.

### 3.3.3 Remove Stockfish

Strip the Stockfish fields from the facts database. The verifier cannot check strategic claims. Measure F1. Expected: large drop on strategic claims, no change on tactical claims (which use attack maps, not Stockfish).

### 3.3.4 Use a weaker LLM

Replace GPT-4 with GPT-4o-mini or Llama-3-8B. Measure F1. Expected: moderate drop, especially on complex multi-claim sentences.

### 3.3.5 Reduce Stockfish depth

Reduce Stockfish depth from 18 to 12 or 8. Measure F1 on strategic claims. Expected: small drop at depth 12, larger drop at depth 8.

### 3.3.6 Collapse verdict labels

Collapse the six labels to three (Verified/Contradicted/Ambiguous). Measure F1. Expected: small change in F1, large change in the usefulness of the report.

## 3.4 Qualitative Analysis

Numbers do not tell the whole story. A qualitative analysis of 20-30 examples (10 successes, 10 failures, 10 borderline) reveals patterns the numbers miss.

### 3.4.1 Success cases

Pick 10 examples where the verifier clearly outperforms baselines. Show the input commentary, the ground truth, and the verifier's verdict. Explain why the verifier succeeded (e.g., "the symbolic attack map correctly identified the pin, which the LLM-only baseline missed").

### 3.4.2 Failure cases

Pick 10 examples where the verifier is clearly wrong. Categorize the failures:

- Extraction errors (LLM extracted the wrong claim).
- Fact lookup errors (verifier could not find the right ply).
- Rule errors (verifier applied the rule incorrectly).
- Strategic claim errors (verifier's heuristic disagreed with human judgment).

This categorization guides future work: extraction errors suggest LLM improvements; rule errors suggest verifier improvements; strategic errors suggest heuristic improvements.

### 3.4.3 Borderline cases

Pick 10 examples where the verifier's verdict is defensible but not the only correct answer. These reveal the inherent subjectivity of the task and set expectations for users.

## 3.5 Baseline Specifications

### 3.5.1 LLM-only baseline

Prompt GPT-4 (or current frontier) with:
- The position as FEN.
- The commentary.
- Instructions: "for each claim in the commentary, output a verdict."

Parse the LLM's structured output. Map to the six-verdict label set.

Expected: F1 ~ 0.5-0.6 overall, with strong performance on move descriptions (~0.8) and weak performance on tactical and material claims (~0.3-0.4).

### 3.5.2 Engine-only baseline

For each claim, derive a heuristic verdict from engine eval:
- "White wins material" → check if eval > +1 at the relevant ply.
- "King is exposed" → check if eval dropped significantly.
- "Move is correct" → check if the played move matches the engine's best move.

Expected: F1 ~ 0.4-0.5 overall, with strong performance on strategic claims and zero performance on move descriptions (the engine does not care about descriptions).

### 3.5.3 Rule-based baseline

- Regex-based claim extraction (no LLM).
- Rule-based verification (no engine, no attack maps).
- Heuristics like "if the claim mentions a piece type and a square, check if any piece of that type is on that square in the FEN".

Expected: F1 ~ 0.3-0.4 overall, with strong performance on simple move descriptions and zero on tactical or strategic claims.

### 3.5.4 Hybrid (proposed system)

- LLM for extraction.
- Symbolic verifier (python-chess + Stockfish) for verification.

Expected: F1 ~ 0.75-0.85 overall, with strong performance across all claim types.

---

## 3.6 Statistical Significance

For each baseline comparison, compute:
- 95% confidence intervals on F1 (using bootstrap resampling).
- Paired t-test or McNemar's test on per-example verdicts.

Report results as "Hybrid F1 = 0.82 ± 0.03, LLM-only F1 = 0.55 ± 0.04, p < 0.001".

Statistical significance matters for top-tier publication. Reviewers will ask.

---

## 3.7 Evaluation Pitfalls

### 3.7.1 Test set contamination

If the test set was used to tune the verifier or the LLM prompts, results are not generalizable. Strict separation of train/dev/test is essential.

### 3.7.2 Annotator bias

If annotators know the verifier's output before labeling, they may be biased toward agreeing or disagreeing. Annotators must label without seeing the verifier's verdict.

### 3.7.3 Cherry-picking examples

In qualitative analysis, do not pick only the verifier's best examples. Pick representative examples, including failures.

### 3.7.4 Overfitting to the metric

F1 is the primary metric, but it is not the only thing that matters. A system with higher F1 but worse explanations is worse in practice. Include user studies or qualitative assessment of explanation quality.

### 3.7.5 Ignoring latency and cost

A system with F1 = 0.85 but $0.10 per note is worse than a system with F1 = 0.80 and $0.005 per note, in practice. Report cost and latency alongside F1.

---

## 3.8 Key Reminders

- Primary metrics: precision, recall, F1, both overall and per-claim-type.
- Secondary metrics: kappa, extraction accuracy, latency, cost.
- Ablations: remove LLM, remove attack maps, remove Stockfish, weaker LLM, lower depth, collapse labels. Six ablations.
- Qualitative analysis: 10 successes, 10 failures, 10 borderline. Categorize failures.
- Three baselines: LLM-only, engine-only, rule-based. Plus the proposed hybrid.
- Statistical significance: 95% CI, McNemar's test. Required for top-tier publication.
- Pitfalls: test contamination, annotator bias, cherry-picking, metric overfitting, ignoring cost.
- The evaluation IS the research contribution. Without rigorous evaluation, the project is engineering, not research.
