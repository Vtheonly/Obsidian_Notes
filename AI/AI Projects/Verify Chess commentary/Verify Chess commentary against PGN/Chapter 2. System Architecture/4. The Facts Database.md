# 4. The Facts Database

> **The facts database in one sentence**: A structured, per-ply record of every board fact the verifier might need — FENs, SAN, captures, material counts, attack maps, and Stockfish evaluations — precomputed once per game and reused for every claim.

The facts database is the **single source of truth** for the verifier. Get its schema right, and the verifier is straightforward. Get it wrong, and every claim type becomes painful to verify.

---

## 4.1 Design Principles

Three principles guide the schema:

1. **Precompute, do not recompute.** Every fact the verifier might need is computed once when the game is replayed. The verifier never calls python-chess or Stockfish on the fly.
2. **Per-ply granularity.** The atomic unit is a ply (half-move). Every fact is indexed by ply. There is no "per-move" or "per-position" indexing — those are derivable from per-ply records.
3. **Verifiable from raw data.** Every field in the database is either a raw board fact (FEN, SAN) or a deterministic function of raw facts (material count, attack map). No opinions, no heuristics in the database itself.

> [!info] Why per-ply and not per-move
> A "move" in chess is two plies (White + Black). Most claims refer to a specific ply, not a move: "White plays Nf3" is one ply, not a move. Indexing by ply avoids off-by-one errors and makes claim resolution unambiguous.

---

## 4.2 Top-Level Schema

The facts database is a single JSON file per game. Top-level structure:

```json
{
  "schema_version": "1.0",
  "game_id": "sicilian-middlegame",
  "source_file": "notes/sicilian.md",
  "pgn_block_line_range": [5, 9],
  "headers": {
    "Event": "Casual game",
    "White": "Player A",
    "Black": "Player B",
    "Result": "1-0"
  },
  "plies": [ /* array of ply records, see 4.3 */ ],
  "material_timeline": [ /* see 4.4 */ ],
  "game_result": "1-0",
  "total_plies": 30
}
```

The `headers` field preserves PGN headers. The `plies` array is the heart of the database. The `material_timeline` is a denormalized view for fast material-claim verification.

---

## 4.3 Per-Ply Record

Each entry in the `plies` array has the following fields:

```json
{
  "ply_index": 12,
  "move_number": 7,
  "mover": "white",
  "san": "Bxh7+",
  "uci": "b1h7",
  "is_capture": true,
  "captured_piece": "p",
  "captured_square": "h7",
  "is_check": true,
  "is_checkmate": false,
  "is_castling": false,
  "is_en_passant": false,
  "is_promotion": false,
  "promotion_piece": null,
  "piece_type": "b",
  "from_square": "b1",
  "to_square": "h7",
  "fen_before": "rnbqkbnr/pppppppp/8/8/8/8/PPPPPPPP/RNBQKBNR w KQkq - 0 1",
  "fen_after": "rnbqkbnr/pppppp1p/7B/8/8/8/PPPPPPPP/RNBQKBNR b KQkq - 0 1",
  "board_before": { /* see 4.3.1 */ },
  "board_after": { /* see 4.3.1 */ },
  "material_before": { "white": {"p":8,"n":2,"b":2,"r":2,"q":1}, "black": {"p":8,"n":2,"b":2,"r":2,"q":1} },
  "material_after":  { "white": {"p":8,"n":2,"b":2,"r":2,"q":1}, "black": {"p":7,"n":2,"b":2,"r":2,"q":1} },
  "attack_map_before": { /* see 4.3.2 */ },
  "attack_map_after":  { /* see 4.3.2 */ },
  "stockfish": {
    "depth": 18,
    "eval_cp": 220,
    "eval_pawns": 2.2,
    "is_mate": false,
    "mate_in": null,
    "best_move_uci": "g8h8",
    "best_move_san": "Kh8",
    "pv_uci": ["g8h8", "h7g8", ...],
    "pv_san": ["Kh8", "Bxg8", ...]
  }
}
```

### 4.3.1 Board representation

`board_before` and `board_after` are 64-entry arrays, one per square in algebraic order (a1, b1, ..., h8). Each entry is either `null` (empty) or an object:

```json
{ "piece": "p", "color": "w" }
```

This is denser than FEN for programmatic access. The verifier uses it to answer "is there a knight on f3?" without re-parsing FEN.

### 4.3.2 Attack map

`attack_map_before` and `attack_map_after` record, for each square, which pieces attack it. Format:

```json
{
  "h7": {
    "white_attackers": [{"piece": "b", "from": "b1"}],
    "black_attackers": [{"piece": "k", "from": "g8"}]
  },
  "e5": {
    "white_attackers": [],
    "black_attackers": []
  }
}
```

This is the most expensive field to compute, but it makes tactical verification (forks, pins, skewers) trivial. See [[Chapter 4. Claim Types and Verification/3. Tactical Claims|3. Tactical Claims]].

## 4.4 Material Timeline

The `material_timeline` is a denormalized view of material counts at every ply. It is redundant with `material_before`/`material_after` per ply, but it makes material claims O(1) to verify.

```json
[
  {"ply_index": 0, "white": 39, "black": 39, "delta": 0},
  {"ply_index": 1, "white": 39, "black": 39, "delta": 0},
  ...
  {"ply_index": 12, "white": 39, "black": 38, "delta": 1},
  ...
]
```

- `white` and `black` are total material in centipawns (pawn=1, knight=3, bishop=3, rook=5, queen=9, king=0).
- `delta` is `white - black` from White's perspective.

To verify "White wins a rook" between ply 12 and ply 20, the verifier checks: `material_timeline[20].white - material_timeline[12].white >= 5` AND the gain was specifically a rook (compare per-piece counts).

## 4.5 What Belongs in the Facts Database (and What Does Not)

### Belongs

- Raw board state (FEN, piece placement).
- Move data (SAN, UCI, capture/check/checkmate flags).
- Material counts (per piece type, per side, per ply).
- Attack maps (who attacks each square).
- Stockfish evaluations (depth, eval, best move, PV).
- PGN headers (for context, not verification).

### Does NOT belong

- LLM output of any kind. The LLM never writes to the facts database.
- Heuristic assessments ("White is better here"). The database stores raw facts; the verifier interprets them.
- Natural-language move descriptions. SAN is sufficient.
- Comments from the PGN. They are stripped during parsing.
- Variations. Not supported in v1.
- Time control or clock data. Not relevant to verification.

> [!warning] Avoid "interpretive" fields
> A common mistake is to add fields like `is_king_exposed: true` to the per-ply record. That is a heuristic, not a fact. The database should store the raw inputs (king position, pawn shield, attacker count) and let the verifier compute "is the king exposed" via a documented rule. Mixing heuristics into the database makes the verifier's logic opaque.

## 4.6 Storage and Caching

### 4.6.1 File layout

Each game's facts database is stored as a single JSON file under `facts/<game_id>.json`. The `game_id` is derived from the source file name and the PGN block's line range.

### 4.6.2 Cache invalidation

The facts database is invalidated (and recomputed) when:

- The source Markdown file changes.
- The PGN block within the file changes.
- The Stockfish version changes (recorded in the database).
- The python-chess version changes (recorded in the database).

Otherwise, the cached database is reused. This is critical for performance: re-running Stockfish on every verification pass would make the system unusably slow.

### 4.6.3 Size estimates

A typical 40-ply game produces a facts database of about **200-500 KB** uncompressed, ~50-100 KB gzipped. Most of the size is the per-ply attack maps. For a vault of 1000 games, that is ~500 MB uncompressed — manageable on a local disk, expensive in memory.

If memory becomes a problem, attack maps can be moved to a separate sidecar file and loaded lazily per ply.

## 4.7 Schema Evolution

The `schema_version` field at the top of the database is the single source of truth for compatibility. The verifier checks the schema version on load and refuses to proceed if the version is incompatible.

Schema changes follow semver:

- **Patch** (1.0.0 → 1.0.1): bug fixes that do not change the schema.
- **Minor** (1.0.0 → 1.1.0): additive changes (new optional fields). Old verifiers continue to work.
- **Major** (1.0.0 → 2.0.0): breaking changes (removed or renamed fields). Old verifiers must be updated.

When in doubt, bump the minor version and add a field. Never rename or remove a field without a major version bump.

## 4.8 Testing the Facts Database

The facts database must be tested independently of the verifier. Three test categories:

### 4.8.1 Round-trip tests

Given a known PGN, the database should produce specific FENs at specific plies. Use classic games with well-documented positions:

```python
def test_kasparov_topalov_1999_ply_44():
    facts = build_facts("kasparov_topalov_1999.pgn")
    assert facts.plies[44].fen_after == "r1bq1rk1/pp2bppp/2n1p3/8/..."
```

### 4.8.2 Invariant tests

For every ply in every test game:

- `material_after` matches a manual count of `board_after`.
- `attack_map_after` matches a fresh `chess.Board(fen_after).attacks(...)` call.
- `material_timeline[ply].white == sum(board_after white pieces)`.

These invariants catch almost every bug in the database builder.

### 4.8.3 Performance tests

Building the facts database for a 40-ply game should complete in under 5 seconds on commodity hardware. If it takes longer, something is wrong — usually a redundant Stockfish call or an O(n²) attack-map computation.

---

## 4.9 Key Reminders

- The facts database is the **single source of truth** for the verifier.
- Atomic unit: per-ply records, not per-move.
- Every field is either a raw board fact or a deterministic function of raw facts. No heuristics.
- Precompute everything. The verifier never calls python-chess or Stockfish on the fly.
- Attack maps are expensive but make tactical verification trivial. Budget the storage.
- Cache aggressively. Re-running Stockfish on every verification pass is unusably slow.
- Schema versioning is mandatory. Bump the version on every schema change.
- Test the database independently of the verifier — round-trip tests, invariant tests, performance tests.
- If you find yourself wanting to add an "interpretive" field like `is_king_exposed`, stop. Store the raw inputs and let the verifier compute the interpretation.
