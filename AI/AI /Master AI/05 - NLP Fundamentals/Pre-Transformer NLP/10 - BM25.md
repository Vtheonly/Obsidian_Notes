# 10 - BM25

> [!info] TL;DR
> BM25 (Okapi BM25, Robertson et al. 1995) is the standard scoring function for keyword search. Improves on TF-IDF with term saturation and document length normalization. Still SOTA for keyword retrieval in 2026 — and a critical component of hybrid RAG.

## The Formula

For a query $q$ with terms $q_1, \ldots, q_n$ and a document $d$:

$$
\text{BM25}(q, d) = \sum_{i=1}^{n} \text{IDF}(q_i) \cdot \frac{\text{tf}(q_i, d) \cdot (k_1 + 1)}{\text{tf}(q_i, d) + k_1 \cdot \left(1 - b + b \cdot \frac{|d|}{\text{avgdl}}\right)}
$$

Where:
- $\text{tf}(q_i, d)$: term frequency of $q_i$ in $d$.
- $|d|$: length of document $d$.
- $\text{avgdl}$: average document length in the corpus.
- $k_1$: term frequency saturation parameter (typically 1.2–2.0).
- $b$: document length normalization (typically 0.75).

## Two Key Improvements over TF-IDF

### 1. Term Frequency Saturation

In raw TF-IDF, $\text{tf}$ grows linearly: a word appearing 100 times scores 10x a word appearing 10 times. But after the first few occurrences, more occurrences don't really make the document more relevant.

BM25's $\frac{\text{tf} \cdot (k_1+1)}{\text{tf} + k_1}$ saturates — it asymptotes to $k_1 + 1$ as tf → ∞. The first occurrence matters most; subsequent occurrences add diminishing returns.

### 2. Document Length Normalization

Longer documents naturally have higher term frequencies (more chances to mention a term). Without normalization, long docs always rank higher.

BM25's $(1 - b + b \cdot |d|/\text{avgdl})$ factor normalizes for length. $b = 1$ means full normalization; $b = 0$ means no normalization. $b = 0.75$ is the standard.

## Why BM25 Still Wins

Despite being 30 years old, BM25 remains the standard for keyword search:

- **Exact match**: BM25 nails queries like `error code 0xC0000005` where exact tokens matter.
- **No training required**: works out of the box on any corpus.
- **Interpretable**: scores decompose by term.
- **Fast**: inverted indexes (Elasticsearch, OpenSearch, Lucene) make BM25 sub-millisecond per query.
- **Cheap**: no model to run, no embeddings to compute.

## BM25 vs Vector Search

| Property                | BM25                          | Vector Search                     |
|-------------------------|-------------------------------|-----------------------------------|
| Match type              | Exact token                   | Semantic                          |
| Misspellings            | Misses                        | Can match (depending on embedder) |
| Synonyms                | Misses                        | Matches                           |
| Long-tail terms         | Strong                        | Often weak (embedders undertrain) |
| Speed                   | Very fast (inverted index)    | Slower (vector similarity)        |
| Cost                    | Cheap                         | More expensive (embedding compute)|
| Setup                   | Just index                    | Need embedding model              |

### The hybrid answer

**Both**. Hybrid search (BM25 + vector, with reranking) is the production standard. BM25 catches exact-match queries; vector catches semantic. See [[17 - RAG/MOC|RAG MOC]].

## Worked Example

```python
from rank_bm25 import BM25Okapi

docs = [
    "the cat sat on the mat".split(),
    "the dog ran in the park".split(),
    "cats and dogs are common pets".split(),
]
bm25 = BM25Okapi(docs)

query = "cat on mat".split()
scores = bm25.get_scores(query)
print(scores)  # highest for docs[0]
```

For production, use Elasticsearch / OpenSearch / Meilisearch / Tantivy — they implement BM25 efficiently with inverted indexes.

## Tuning k1 and b

- **k1** (term saturation): lower (0.5–1.0) for shorter documents; higher (1.5–2.0) for longer.
- **b** (length normalization): 0.75 is standard. Lower (0.5) if you want to give long documents a chance; higher (0.9) if you want to penalize them more.

Most users don't tune these — the defaults are well-chosen. Tune only if you have an evaluation pipeline.

## BM25 Variants

- **BM25F**: per-field BM25 (different weighting for title, body, etc.).
- **BM25+**: addresses the "over-penalization" of long documents.
- **BM25L**: another length-normalization variant.

For most use cases, plain BM25 (Okapi) is fine.

## Why This Matters for AI

- **Every RAG system should consider BM25.** Pure vector search misses exact-match queries — product codes, error messages, names, IDs. BM25 catches them.
- BM25 is the **baseline that vector search must beat** for keyword-heavy queries. Often it doesn't.
- For **hybrid RAG**, BM25 + vector + cross-encoder reranker is the production standard.
- BM25 is **infrastructure-level** — Elasticsearch, OpenSearch, Postgres (via `tsvector`), Tantivy, Meilisearch all implement it. Knowing it lets you read IR papers and tune search systems.

## Production Implications

- **Use an inverted-index engine** for BM25 at scale: Elasticsearch / OpenSearch for managed, Tantivy / Meilisearch for self-hosted.
- **Index fields separately** (title, body, metadata) so you can weight them differently.
- **Hybrid scoring**: combine BM25 and vector scores with a weighted sum or learned fusion (e.g., Reciprocal Rank Fusion).
- **Tune k1 and b** only with a labeled eval set. Don't tune blind.
- **Multi-language**: BM25 works per-language if you tokenize correctly (CJK needs special handling).

## Common Pitfalls

- **No stemming or lemmatization** — "running" and "run" are different tokens. Use a stemmer (Porter, Snowball) or lemmatizer.
- **No stop-word removal** — common words dominate the score.
- **Treating BM25 as ground truth** — it's a baseline; for semantic queries, vector search wins.
- **Forgetting to re-index when corpus changes** — BM25 indexes must be updated when documents change.
- **Wrong analyzer for the language** — English analyzer doesn't handle Chinese / Arabic / etc. correctly.

## BM25 vs. TF-IDF: The Two Improvements (Detailed)

BM25 improves on TF-IDF in two specific ways:

### 1. Term frequency saturation
In TF-IDF, the score grows linearly with term frequency: a document with 10 occurrences of "cat" scores 10× higher than one with 1 occurrence. This is wrong — after a few occurrences, more occurrences don't make the document more relevant.

BM25 uses a **saturation function**:
$$
\text{TF saturation} = \frac{(k_1 + 1) \cdot f(t, d)}{k_1 + f(t, d)}
$$

This saturates at $k_1 + 1$ as $f(t, d) \to \infty$. With $k_1 = 1.2$, the function reaches ~50% of its max at $f = 1$, ~75% at $f = 3$, ~90% at $f = 10$. More occurrences help, but with diminishing returns.

### 2. Document length normalization
In TF-IDF, longer documents naturally have higher term frequencies — they're unfairly favored. BM25 normalizes by document length:
$$
\text{Length norm} = 1 - b + b \cdot \frac{|d|}{\text{avgdl}}
$$

With $b = 0.75$, a document 2× the average length gets a 1.75× penalty on term frequency. This ensures fair comparison across documents of different lengths.

### Why these matter
Without saturation: a 1000-word document with 50 mentions of "cat" would dominate search results, even if a 100-word document with 3 mentions is more relevant. Without length normalization: long documents always win. BM25 fixes both with two intuitive parameters ($k_1$ for saturation, $b$ for length normalization).

## Hyperparameter Tuning (k1 and b)

The two BM25 parameters control its behavior:

### k1 (term frequency saturation)
- Range: typically 1.0 to 2.0.
- Default: 1.2.
- Lower (1.0): term frequency saturates faster — even 2-3 occurrences give near-max score.
- Higher (2.0): term frequency matters more — more occurrences keep helping.
- Tuning: for short queries (1-3 words), k1 = 1.2 is good. For long queries (5+ words), k1 = 1.5-2.0 may help.

### b (document length normalization)
- Range: 0 to 1.
- Default: 0.75.
- b = 0: no length normalization — long and short documents treated equally.
- b = 1: full length normalization — term frequency fully divided by length.
- b = 0.5: moderate normalization.
- Tuning: for collections with uniform document length, b = 0.5 is fine. For collections with highly variable lengths (web pages, articles), b = 0.75 (default) is good.

### Empirical tuning
Most production systems use the defaults (k1=1.2, b=0.75). Tuning gives 1-5% improvement on retrieval benchmarks — often not worth the effort. If you do tune, use a validation set with relevance judgments and grid search over k1 ∈ {1.0, 1.2, 1.5, 2.0} and b ∈ {0.5, 0.75, 1.0}.

## BM25 in Modern Hybrid RAG (2026)

BM25 is not obsolete — it's a critical component of hybrid RAG systems:

### Why BM25 still matters
1. **Exact match**: BM25 finds exact keyword matches (product codes, names, error messages) that embeddings miss.
2. **Rare terms**: BM25 handles rare terms well; embeddings may not have seen them in training.
3. **Interpretability**: BM25 scores are explainable — you can see which terms contributed.
4. **Speed**: BM25 is faster than embedding-based search (inverted index vs. ANN).
5. **No model needed**: BM25 doesn't require a trained model — just statistics.

### Hybrid search pattern
```python
def hybrid_search(query, top_k=10, bm25_weight=0.3, embedding_weight=0.7):
    # BM25 search
    bm25_scores = bm25_index.search(query, top_k=top_k * 2)
    # Embedding search
    query_emb = embedding_model.encode(query)
    embedding_scores = vector_index.search(query_emb, top_k=top_k * 2)
    # Reciprocal Rank Fusion (RRF)
    fused = reciprocal_rank_fusion(bm25_scores, embedding_scores)
    return fused[:top_k]

def reciprocal_rank_fusion(bm25_results, embedding_results, k=60):
    """RRF: rank-based fusion that doesn't need score calibration."""
    scores = {}
    for rank, (doc_id, _) in enumerate(bm25_results):
        scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank)
    for rank, (doc_id, _) in enumerate(embedding_results):
        scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank)
    return sorted(scores.items(), key=lambda x: -x[1])
```

### When BM25 wins over embeddings
- **Exact match queries**: "iPhone 15 Pro Max 256GB" — BM25 finds exact product codes; embeddings may match semantically similar but wrong products.
- **Rare entity names**: "Zbigniew Brzezinski" — BM25 finds exact name; embeddings may not have seen this name in training.
- **Error messages**: "Error 404: NotFound" — BM25 finds exact error; embeddings may match similar errors.
- **Code search**: `function_name()` — BM25 finds exact function names; embeddings may match similar functions.

### When embeddings win over BM25
- **Semantic queries**: "how to fix a slow computer" — embeddings match "performance optimization"; BM25 may miss if the doc doesn't use those exact words.
- **Paraphrasing**: "laptop" vs. "notebook computer" — embeddings match semantically; BM25 requires exact terms.
- **Multilingual**: "chat" (French) vs. "cat" (English) — embeddings cross languages; BM25 doesn't.

## Worked Example: BM25 Implementation

```python
import math
from collections import Counter, defaultdict

class BM25:
    def __init__(self, documents, k1=1.2, b=0.75):
        self.k1 = k1
        self.b = b
        self.documents = documents
        self.doc_len = [len(doc.split()) for doc in documents]
        self.avgdl = sum(self.doc_len) / len(self.doc_len)
        self.doc_freqs = [Counter(doc.split()) for doc in documents]
        self.N = len(documents)
        # Inverse document frequency
        self.idf = self._compute_idf()

    def _compute_idf(self):
        """IDF with BM25 smoothing: idf(t) = log((N - df + 0.5) / (df + 0.5) + 1)"""
        idf = {}
        for term in set().union(*[set(df.keys()) for df in self.doc_freqs]):
            df = sum(1 for doc_freq in self.doc_freqs if term in doc_freq)
            idf[term] = math.log((self.N - df + 0.5) / (df + 0.5) + 1)
        return idf

    def score(self, query, doc_idx):
        """BM25 score for a query against a specific document."""
        score = 0.0
        doc_freq = self.doc_freqs[doc_idx]
        doc_len = self.doc_len[doc_idx]
        for term in query.split():
            if term not in self.idf:
                continue
            f = doc_freq.get(term, 0)
            if f == 0:
                continue
            # Term frequency saturation
            tf = (f * (self.k1 + 1)) / (f + self.k1 * (1 - self.b + self.b * doc_len / self.avgdl))
            score += self.idf[term] * tf
        return score

    def search(self, query, top_k=5):
        """Return top-k documents for the query."""
        scores = [(i, self.score(query, i)) for i in range(self.N)]
        scores.sort(key=lambda x: -x[1])
        return [(self.documents[i], score) for i, score in scores[:top_k]]

# Usage
docs = [
    "the cat sat on the mat",
    "the dog sat on the log",
    "cats and dogs are pets",
    "the cat chased the mouse",
]
bm25 = BM25(docs)
results = bm25.search("cat sat", top_k=2)
# Returns docs with "cat" and "sat" — high BM25 score
```

## Common Failure Modes

| Symptom | Likely Cause | Fix |
|---------|--------------|-----|
| BM25 returns irrelevant results | No stemming/lemmatization | Apply stemming (Porter); lowercase; remove stopwords |
| Rare terms not found | IDF smoothing too aggressive | Use standard BM25 IDF formula; check vocabulary |
| Long documents always win | Length normalization too weak | Increase b (toward 1.0); check avgdl computation |
| BM25 misses semantic matches | BM25 is lexical, not semantic | Use hybrid search (BM25 + embeddings) |
| BM25 too slow | Naive implementation | Use inverted index (Elasticsearch, Lucene); precompute IDF |
| BM25 scores not comparable across queries | IDF depends on corpus | Use the same corpus for all queries; don't compare raw scores |

## Interview Questions

1. **Q: What are the two improvements BM25 makes over TF-IDF?**
   A: (1) Term frequency saturation: BM25 uses $\frac{(k_1+1) \cdot f}{k_1 + f}$ instead of linear TF — more occurrences help with diminishing returns, not linearly. (2) Document length normalization: BM25 divides TF by $1 - b + b \cdot |d|/\text{avgdl}$ — longer documents get a penalty so they don't dominate. Without these, TF-IDF favors long documents with many term occurrences.

2. **Q: What do the BM25 parameters k1 and b control?**
   A: k1 (default 1.2) controls term frequency saturation — higher k1 means more occurrences keep helping; lower k1 means faster saturation. b (default 0.75) controls document length normalization — b=0 means no normalization; b=1 means full normalization. Most systems use defaults; tuning gives 1-5% improvement, often not worth the effort.

3. **Q: Why is BM25 still used in 2026 despite embedding-based search?**
   A: Four reasons. (1) Exact match: BM25 finds exact keywords (product codes, names, errors) that embeddings miss. (2) Rare terms: BM25 handles rare terms; embeddings may not have seen them. (3) Interpretability: BM25 scores are explainable. (4) Speed: BM25 (inverted index) is faster than ANN search. Modern RAG uses hybrid search (BM25 + embeddings with reciprocal rank fusion) to get the best of both.

4. **Q: How does hybrid search combine BM25 and embedding results?**
   A: Two methods. (1) Score fusion: weighted sum of normalized BM25 and embedding scores. Requires calibration — scores from different distributions. (2) Reciprocal Rank Fusion (RRF): $\text{score}(d) = \sum_r 1/(k + \text{rank}_r(d))$ where $r$ indexes retrievers and $k=60$. RRF is rank-based, doesn't need score calibration, and is the standard for hybrid RAG. Most production systems use RRF.

5. **Q: When does BM25 beat embedding-based search?**
   A: Four cases. (1) Exact match queries (product codes, names, error messages) — BM25 finds exact matches; embeddings may match semantically similar but wrong items. (2) Rare entity names — BM25 finds exact names; embeddings may not have seen them. (3) Error messages — BM25 finds exact errors; embeddings match similar errors. (4) Code search (function names) — BM25 finds exact functions; embeddings match similar functions.

6. **Q: How does BM25's IDF differ from TF-IDF's IDF?**
   A: TF-IDF IDF: $\log(N / df)$ or $\log(N / (1 + df))$. BM25 IDF: $\log((N - df + 0.5) / (df + 0.5) + 1)$ — probabilistic formulation with smoothing. BM25's IDF can be negative (when a term appears in more than half the documents), which TF-IDF's can't (with the +1 smoothing). The smoothing prevents extreme values for very common or very rare terms.
