# 29 — GQA (Ainslie et al., 2024)

> [!info] TL;DR
> GQA (Grouped-Query Attention) interpolates between Multi-Head Attention (MHA, one KV head per query head) and Multi-Query Attention (MQA, one KV head shared across all query heads). GQA uses a small number of KV head "groups" shared across query heads, achieving MQA-like KV cache efficiency with MHA-like quality. GQA is now the default attention variant for modern LLMs (Llama 3, Mistral, Qwen, Gemma) — it's the standard solution to the KV cache bottleneck.

## Citation

Ainslie, J., Lee-Thorp, J., de Jong, M., Zemlyanskiy, Y., Lebrón, F., & Sanghai, S. (2023). *GQA: Training Generalized Multi-Query Transformer Models from Multi-Head Checkpoints*. EMNLP 2023. arXiv:2305.13245.

## The Problem Being Solved

The KV cache is the dominant memory cost in LLM inference. For a model with `n_heads` heads and `d_head` dimensions per head, each token's KV cache is `2 × n_heads × d_head` elements. For a 70B model (64 heads × 128 dim = 8192 elements per token × 2 for K and V = 16,384), serving 32K context to 32 users requires 16GB just for KV cache.

Two extreme attention variants existed:

- **MHA (Multi-Head Attention)**: one KV head per query head. Maximum quality, maximum KV cache size. Used by GPT-2, GPT-3, original Transformer.
- **MQA (Multi-Query Attention)**: one KV head shared across all query heads. Minimum KV cache size (1/n_heads of MHA), but quality degrades — sharing one KV across all heads is too aggressive.

The question: is there a middle ground that gets most of MQA's efficiency with most of MHA's quality? GQA answers yes.

## The Key Idea: KV Head Groups

GQA uses `n_kv_heads` KV head groups, where `1 ≤ n_kv_heads ≤ n_heads`. Each KV head group is shared by `n_heads / n_kv_heads` query heads.

```
MHA:  n_kv_heads = n_heads       (each query head has its own KV)
GQA:  1 < n_kv_heads < n_heads   (query heads share KV in groups)
MQA:  n_kv_heads = 1             (all query heads share one KV)
```

For example, with 32 query heads and 8 KV head groups (GQA-8):
- 8 KV heads, each shared by 4 query heads.
- KV cache is 8/32 = 25% of MHA's. 4× reduction.
- Quality is close to MHA (much better than MQA).

## The Conversion Trick: Uptraining

The paper's most practical contribution: a method to convert an existing MHA checkpoint to GQA without training from scratch.

1. **Average KV heads within groups**: for each group of `n_heads / n_kv_heads` query heads, average their K and V projection weights to create a single shared KV head.
2. **Fine-tune briefly (uptraining)**: fine-tune the converted model for a small fraction of the original training (e.g., 5% of pretraining compute) to recover quality.

This means existing MHA models (Llama, T5) can be converted to GQA without full retraining — a huge practical win. The paper demonstrated this on T5 and Llama, showing that uptrained GQA matched natively-trained GQA.

## Key Results

GQA was evaluated on T5 and Llama architectures:

| Variant            | KV Cache Size | Quality (vs MHA) |
|--------------------|---------------|------------------|
| MHA (32 heads)     | 100%          | baseline         |
| GQA-8 (8 KV groups)| 25%           | -0.2% (negligible)|
| GQA-4 (4 KV groups)| 12.5%         | -0.5%            |
| GQA-2 (2 KV groups)| 6.25%         | -1.2%            |
| MQA (1 KV head)    | 3.125%        | -3.5% (significant)|

The sweet spot is GQA-4 to GQA-8: 4–8× KV cache reduction with minimal quality loss. Below GQA-4, quality starts to degrade noticeably.

### Inference Speedup
On a 70B model serving 32K context:
- MHA: limited by KV cache memory, small batch sizes.
- GQA-8: 4× smaller KV cache, 4× larger batches possible, ~3× throughput improvement.
- MQA: even smaller KV cache, but quality loss makes it impractical.

GQA-8 gives most of the throughput benefit of MQA without the quality cost.

## Why It Worked

### KV Heads Are Redundant
The key empirical finding: different attention heads in MHA models learn similar K and V projections. There's significant redundancy — many heads compute nearly-identical K/V. GQA exploits this by sharing, with minimal information loss.

### Grouping Preserves Diversity
Unlike MQA (which forces all heads to share one KV), GQA preserves some diversity — different groups can specialize in different aspects (syntactic, semantic, positional). This is why GQA-8 retains quality while MQA doesn't.

### Uptraining Recovers Quality
The averaging step loses some information, but brief fine-tuning recovers it. The model re-learns to use the shared KV heads effectively. This makes GQA practical to adopt on existing models.

### Clean Trade-off
GQA provides a clean knob (`n_kv_heads`) to trade KV cache memory for quality. Engineers can choose the right point on the spectrum for their application — more groups for quality-critical tasks, fewer groups for memory-critical deployments.

## Limitations

### Conversion Isn't Free
Uptraining requires ~5% of original pretraining compute. For a 70B model trained with 10²⁵ FLOPs, that's 5×10²³ FLOPs — not trivial, but much cheaper than full retraining.

### Quality Still Slightly Below MHA
GQA-8 has ~0.2% quality loss compared to MHA. For most applications this is negligible, but for frontier-quality models where every fraction matters, MHA (or MLA) might be preferred.

### Less Efficient Than MLA
[[28 - DeepSeek-V2 and V3 2024|MLA]] achieves much larger KV cache reductions (30–100×) than GQA (2–8×) by exploiting low-rank structure. GQA is simpler and more widely supported, but MLA is more efficient for extreme long-context.

### Not Optimal for Very Long Contexts
For 128K+ context, GQA's KV cache is still significant. Models targeting million-token context (Gemini 1.5) use additional techniques (sliding window, sparse attention, MLA) on top of or instead of GQA.

## Adoption

GQA is now the default attention variant for open-weights LLMs:

| Model      | n_heads | n_kv_heads | Reduction |
|------------|---------|------------|-----------|
| Llama 3 8B | 32      | 8          | 4×        |
| Llama 3 70B| 64      | 8          | 8×        |
| Mistral 7B | 32      | 8          | 4×        |
| Qwen 2.5 7B| 28      | 4          | 7×        |
| Gemma 2 9B | 16      | 8          | 2×        |

The pattern: most models use 4–8 KV head groups, giving 4–8× KV cache reduction. This is the empirically-validated sweet spot.

Closed-source models (GPT-4, Claude, Gemini) likely use GQA or MLA, though architectures are not officially disclosed.

## Impact and Legacy

GQA's influence on the LLM ecosystem:

1. **Standardized KV cache efficiency**. Before GQA, KV cache was a major bottleneck for LLM serving. GQA's 4–8× reduction made large-batch serving practical without exotic hardware.

2. **Enabled the open-weights LLM ecosystem**. Mistral 7B, Llama 3, Qwen, Gemma — all use GQA. Without it, these models would be much more expensive to serve, limiting adoption.

3. **Established the "conversion + uptraining" pattern**. The technique of converting an existing checkpoint to a more efficient variant (and recovering quality with brief fine-tuning) became standard. The same pattern is used for quantization, sparsification, and other efficiency techniques.

4. **Informed MLA development**. GQA demonstrated that KV heads are redundant. DeepSeek took this further with MLA, exploiting not just inter-head redundancy but intra-head low-rank structure. GQA was the conceptual stepping stone.

5. **Made long-context economically viable**. GQA's KV cache reduction was a prerequisite for the 32K–128K context models that became standard in 2024. Without GQA, the KV cache for 128K context would be prohibitive.

For AI engineers, GQA is invisible infrastructure — every modern LLM uses it, and you rarely need to think about it. But understanding GQA matters when: choosing `n_kv_heads` for a custom model, reasoning about KV cache memory, or comparing attention variants (MHA vs GQA vs MLA).
