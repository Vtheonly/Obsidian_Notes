# 01. The Encoder-Decoder Pattern — Conditional Generation

> **Prerequisites:** [[01. LSTM - Gates as Learned Traffic Controllers]] or [[02. GRU - Simplifying the LSTM]] (we need a recurrent cell to build this), [[01. Why Sequence Models - The Limits of Feedforward Networks]] (why variable-length I/O matters)
> **Connections:** [[02. Teacher Forcing and Exposure Bias]] (training technique), [[01. The Bottleneck Problem - Why One Vector Is Not Enough]] (the limit that motivates attention), [[08 - Attention and Transformers]] (the chapter that fixes this bottleneck)

This is one of the most important notes in the entire vault. The Encoder-Decoder pattern is the conceptual bridge from "RNNs that classify sequences" to "RNNs that generate sequences" — and the bottleneck you discover here is *exactly* the problem that Attention was invented to solve. If you understand this note, you understand 80% of the motivation for the Transformer.

---

## The problem: variable-length input, variable-length output

So far, our RNNs have done one of two things:

- **Many-to-one:** read a sequence, emit one label (sentiment classification). Input is variable-length, output is a fixed-size label.
- **Many-to-many (synced):** read a sequence, emit one label per input (POS tagging). Input and output have the same length.

But many real tasks have **variable-length input AND variable-length output, with no alignment between them**:

- **Translation:** "how are you?" (3 words) → "comment ça va ?" (3 words, but a 30-word sentence may translate to a 25-word sentence — no fixed ratio).
- **Summarization:** a 500-word article → a 50-word summary.
- **Speech recognition:** 10 seconds of audio (200 frames) → "hello world" (2 words).
- **Code generation:** a natural-language spec (30 tokens) → a Python function (100 tokens).

No single RNN can do this. The input and output live in different spaces, have different lengths, and have no positional correspondence. The solution is to use **two** RNNs: one to read the input, one to write the output, with a handoff in between.

---

## The architecture

### The encoder

The **encoder** is an RNN (LSTM or GRU) that reads the input sequence one token at a time, updating its hidden state. It produces **no output** during this phase — it just reads. At the end, the encoder's final hidden state $h_T^{enc}$ is a summary of the entire input.

$$h_t^{enc} = \mathrm{RNN}_{enc}(h_{t-1}^{enc}, x_t) \quad \text{for } t = 1, \ldots, T$$

After reading all $T$ input tokens, we have $h_T^{enc}$ — a single fixed-size vector that is supposed to contain everything the decoder needs.

### The context vector

$h_T^{enc}$ is repurposed as the **context vector** $c$. In the simplest version, $c = h_T^{enc}$. (In fancier versions, $c$ is a function of all encoder hidden states, but we start with the simple version.)

This context vector is the *only* information that passes from the encoder to the decoder. It is the bottleneck — but we will get to that in the next note. For now, accept that $c$ is the decoder's only view of the input.

### The decoder

The **decoder** is a *second* RNN (LSTM or GRU) that generates the output sequence one token at a time, conditioned on the context vector.

The trick is initialization: **the decoder's initial hidden state is set to the context vector**, $h_0^{dec} = c$. This is how the input "flows into" the decoder.

At each step, the decoder:

1. Takes the previous output token as input (during training: the previous *true* token; during inference: the previous *predicted* token — see [[02. Teacher Forcing and Exposure Bias]]).
2. Updates its hidden state: $h_t^{dec} = \mathrm{RNN}_{dec}(h_{t-1}^{dec}, y_{t-1})$.
3. Projects its hidden state to a vocabulary distribution: $p_t = \mathrm{softmax}(W_{out} h_t^{dec})$.
4. Samples (or argmaxes) the next token: $y_t \sim p_t$.
5. Repeats until it emits a special `<EOS>` (end-of-sequence) token.

The loss is the cross-entropy of the predicted distributions against the true target tokens, summed over all decoder steps.

## The full picture

```
ENCODER                              DECODER
                                                      
 x_1 → [Enc] → h_1                   h_0 = c = h_T
 x_2 → [Enc] → h_2                          ↓
 x_3 → [Enc] → h_3                   [Dec] → y_1 (e.g. "comment")
 ...                                  ↓ y_1
 x_T → [Enc] → h_T ──── c ────▶      [Dec] → y_2 (e.g. "ça")
                                      ↓ y_2
                                      [Dec] → y_3 (e.g. "va")
                                      ↓ y_3
                                      [Dec] → <EOS>
```

The encoder reads left-to-right and hands off a single vector $c$. The decoder then runs autonomously, generating one token at a time, until it decides to stop.

---

## Why this design is non-obvious

Three things about this architecture are worth pausing on.

**1. Why two separate RNNs?** You might think one RNN could both read and write. But a single RNN has one hidden state, and that state would have to serve as both "summary of the input so far" and "plan for the output so far" — two different jobs. Splitting into encoder and decoder gives each its own state and its own parameters, so each can specialize.

**2. Why initialize the decoder with $c$ rather than feeding $c$ as input at every step?** Both are possible. Initializing is the original (Sutskever et al. 2014) design and works well. Feeding $c$ at every step (Bahdanau et al. 2015, in the attention paper) also works and is slightly more robust — it prevents the decoder from "forgetting" the input over long output sequences. The attention mechanism, which we cover in [[08 - Attention and Transformers]], generalizes this by feeding a *different* context at every step.

**3. How does the decoder know when to stop?** The decoder is trained to emit a special `<EOS>` token at the end of every target sequence. At inference time, generation halts when `<EOS>` is emitted. This is the mechanism that handles variable output length.

## The information bottleneck — a preview of the next chapter

Look at the diagram above. The entire input sequence — whether it is 5 words or 500 words — is compressed into a single fixed-size vector $c$ before the decoder ever sees it. This is the **bottleneck**, and it is the single most important limitation of the Encoder-Decoder RNN.

Consider translating a 50-word sentence. The encoder must compress the meaning of all 50 words — the subject, the tense, the entities, the relationships, the tone — into a vector of, say, 1024 numbers. The decoder must then reconstruct a 50-word translation in another language from those 1024 numbers alone. This is an extreme information bottleneck, and it has two visible failure modes:

1. **The decoder "forgets" the beginning of the input** by the time it generates the end of the output. The encoder's final hidden state is dominated by the most recent tokens; early tokens have been overwritten.
2. **Long sentences translate worse than short ones.** Empirically, Encoder-Decoder RNN translation quality degrades sharply for sentences above ~30 words, because the fixed-size context cannot hold that much information.

This bottleneck is not an accident of the implementation — it is inherent to the design. And it is *exactly* the problem that **attention** was invented to solve. Instead of forcing the decoder to look at a single context vector, attention lets the decoder "look back" at all the encoder's hidden states and decide, at each output step, which parts of the input are most relevant. That idea — which we develop in [[08 - Attention and Transformers]] — is the foundation of modern NLP.

The next two notes flesh out the practical details of training (teacher forcing) and decoding (beam search), and then the final note in this chapter makes the bottleneck argument precise and hands off to the Transformer chapter.

---

## What you should walk away with

1. The Encoder-Decoder pattern uses two RNNs: an encoder that reads the input and produces a context vector $c$, and a decoder initialized with $c$ that generates the output token-by-token.
2. The decoder generates until it emits `<EOS>`, which is how variable-length output is handled.
3. The context vector $c$ is the *only* path from encoder to decoder — and it is a fixed-size bottleneck.
4. This bottleneck is the structural limitation that attention was invented to fix.
5. Understanding this note is the prerequisite for understanding why attention exists.
