# Physical Storage: Wide-Column and Document Databases

Advanced database systems are not limited to classical row-oriented relational storage. Different workloads motivate alternative physical layouts and query models.

## 1. Wide-Column Storage

A wide-column database stores data by column families rather than requiring every row to have the same set of populated columns. It is designed for very large, sparse, distributed datasets.

Typical characteristics:

* rows are identified by a row key;
* related columns are grouped into column families;
* different rows may contain different numbers of columns;
* data is partitioned across nodes using a key-based distribution strategy;
* storage is optimized for workloads that access a predictable subset of columns for a row or partition.

This differs from a relational heap/table where the schema and physical layout are normally centered around fixed tuples and pages.

## 2. Document / JSON Storage

Document databases store records as self-contained documents, commonly using JSON-like structures. Nested objects and arrays can be represented directly instead of being normalized into multiple relations.

Example document:

```json
{
  "student_id": 101,
  "name": "Sara",
  "courses": [
    {"code": "DB", "grade": 16},
    {"code": "AI", "grade": 14}
  ]
}
```

The physical design trade-off is different from a normalized relational schema: reads of an aggregate object can become cheaper because related data is colocated, while updates to duplicated or nested data may become more complex.

## 3. JSONiq / Declarative Document Queries

JSON-oriented query languages such as **JSONiq** provide declarative operations over structured JSON data. The same high-level idea applies as in relational systems: the user describes the result, while the execution engine determines an efficient physical evaluation strategy.

## 4. Relational vs. Alternative Physical Layouts

| Model | Primary Physical Idea | Typical Strength |
| :--- | :--- | :--- |
| Relational row store | Tuples organized in pages/blocks | General-purpose transactional workloads |
| Wide-column | Column families distributed by row/partition key | Large sparse distributed datasets |
| Document | Self-contained hierarchical documents | Aggregate-centric reads and flexible schemas |

The important optimization principle is to choose a physical model whose access pattern matches the workload. Physical design is therefore part of query performance, not merely storage implementation.
