# Advanced Physical Design Structures

Logical optimization changes the algebraic plan; **physical design** changes how the data and derived results are stored so that important workloads can execute with less I/O.

## 1. Table Clustering

A clustered organization stores related rows physically close together according to a cluster key. This can be useful when queries frequently join or retrieve rows sharing the same key.

Illustrative Oracle-style syntax:

```sql
CREATE CLUSTER Dept_Emp_Cluster (Dept_ID INT);
CREATE INDEX idx_cluster_dept ON CLUSTER Dept_Emp_Cluster;

CREATE TABLE Dept (
    Dept_ID INT PRIMARY KEY,
    Dept_Name VARCHAR(50)
) CLUSTER Dept_Emp_Cluster (Dept_ID);

CREATE TABLE Emp (
    Emp_ID INT PRIMARY KEY,
    Emp_Name VARCHAR(50),
    Dept_ID INT REFERENCES Dept(Dept_ID)
) CLUSTER Dept_Emp_Cluster (Dept_ID);
```

**Advantages**

* Related rows may be fetched with fewer data-page reads.
* Joins and grouped access by the cluster key can benefit from physical locality.

**Trade-offs**

* Maintaining the physical organization can make inserts and some updates more expensive.
* A clustering choice optimized for one access pattern can be less useful for unrelated scans.
* Exact syntax and clustering guarantees are DBMS-specific.

## 2. Materialized Views

A **materialized view** stores the result of a query physically instead of recomputing the query every time it is requested.

Typical use case: a complex aggregation over millions of rows that is queried frequently but does not need second-by-second freshness.

**Advantages**

* Reduces repeated computation for complex joins and aggregations.
* Can make reporting queries significantly faster.

**Trade-offs**

* Stored results can become stale.
* Refreshing the result consumes CPU, I/O, and possibly locking resources.
* Refresh policy may be `ON COMMIT`, scheduled, incremental, or DBMS-specific.

## 3. Denormalization

**Denormalization** intentionally introduces controlled redundancy into a normalized design to reduce expensive joins or repeated calculations.

Example: storing `Total_Sales` in a `Store` row instead of computing it from every `Sale` row on every request.

**Advantages**

* Faster read-heavy workloads.
* Reduced join and aggregation cost for selected queries.

**Risks**

* Multiple copies of logically equivalent information can diverge.
* Every write path must maintain the redundant value correctly.
* Triggers, application code, or scheduled reconciliation may be used to keep derived values synchronized.

## 4. Choosing a Physical Structure

The decision should be based on workload characteristics:

| Structure | Main Benefit | Main Cost |
| :--- | :--- | :--- |
| Clustered storage | Physical locality for related/range data | Insert/update and layout constraints |
| Materialized view | Fast repeated complex queries | Refresh/storage overhead and staleness |
| Denormalization | Fewer joins and computations | Redundancy and consistency maintenance |

Physical design is therefore a trade-off between read performance, write cost, storage, freshness, and workload stability.
