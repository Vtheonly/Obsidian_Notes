# 5. Cost Estimation & Calculations

To verify if a plan is better, we calculate its **Cost**. In databases, cost is usually measured in **I/O (Input/Output) units** (pages read/written) or cardinality (number of tuples processed).

## Basic Formulas

Let $|R|$ be the number of rows in table $R$.
Let $|S|$ be the number of rows in table $S$.

### 1. Cartesian Product ($R \times S$)

- **Result Size:** $|R| \times |S|$
- **Example:** If $|R|=1,000$ and $|S|=1,000$, result = $1,000,000$ rows.
- _This is why a raw Cartesian product is usually undesirable._

### 2. Selection ($\sigma$)

- **Cost:** Depends on **selectivity** (the fraction/probability of rows satisfying the condition).
- **Formula:** $|Result| = |R| \times Selectivity$
- **Example:** A unique key equality predicate has selectivity approximately $1/|R|$ and usually returns one row.

### 3. Join ($R \bowtie S$)

- **Result Size:** Difficult to predict exactly without statistics, but generally:
  $0 \le |Result| \le |R| \times |S|$
- **For a foreign-key-to-primary-key join:** Under the usual one-to-many assumptions, the join cardinality is often close to the number of matching child rows.

## Calculation Example (From TD N°4)

**Scenario:**

- `Train` Table: 60,000 rows.
- `Wagon` Table: 200,000 rows.
- Query: Find the wagon type for Train #4002.

**Approach A (Naive / Bad): Join then Filter**

1. **Join:** Process the train/wagon relationship before the train-number filter.
2. **Filter:** Scan the intermediate result to find Train #4002.
3. **Problem:** A large intermediate relation is created before a highly selective predicate is applied.

**Approach B (Optimized): Filter then Join**

1. **Filter `Train`:** $\sigma_{NoTrain=4002}(Train)$.
2. **Join:** Join the reduced relation to `Wagon`, ideally through an appropriate index/access path.
3. **Benefit:** The input to the join is much smaller.

## 4. Page-Based Cost Variables

For disk-oriented exercises, distinguish **cardinality** from **physical size**:

* $T_R$ or $|R|$: number of tuples in relation $R$.
* $B_R$: number of disk pages occupied by relation $R$.
* $V(A,R)$: number of distinct values of attribute $A$ in relation $R$.
* $s$: selectivity factor, where $0 \le s \le 1$.

For a simple equality predicate on a uniformly distributed attribute:

$$s(A=c) \approx \frac{1}{V(A,R)}$$

and therefore:

$$|\sigma_{A=c}(R)| \approx \frac{|R|}{V(A,R)}$$

For a join on $R.A=S.B$, a common uniform-distribution estimate is:

$$|R \bowtie S| \approx \frac{|R|\times|S|}{\max(V(A,R),V(B,S))}$$

These are **estimates**, not guarantees; skew, correlations, `NULL`s, and referential constraints can change the real cardinality.

## 5. Page-I/O Exercise: CINEMA / HALL

Suppose:

* `CINEMA`: $T_1=300$ tuples, $B_1=30$ pages.
* `HALL`: $T_2=1200$ tuples, $B_2=120$ pages.
* Only 5% of `HALL` tuples satisfy `capacity > 150`.

A simplified block nested-loop calculation for a canonical join-first plan is:

$$30 + (30\times120)=3630\text{ page reads}$$

If the selection is pushed to `HALL`, the estimated filtered relation occupies:

$$120\times0.05=6\text{ pages}$$

The filtering stage may therefore be approximated as:

$$120\text{ reads}+6\text{ writes}=126\text{ I/O}$$

and a simplified join stage as:

$$30+6=36\text{ I/O}$$

giving:

$$126+36=162\text{ I/O}$$

The numerical result depends on the assumed physical algorithm, buffer availability, materialization policy, and whether temporary results are actually written, but the exercise demonstrates why reducing intermediate cardinality can drastically reduce I/O.

## 6. CPU Instruction Model for Join Ordering

For a simplified nested-loop exercise with:

* $n_1=|T1|=100$;
* $n_2=|T2|=10$;
* $n_1'$ rows of `T1` satisfy the filter;
* $n_2'$ rows of `T2` satisfy the filter;
* $n_3$ rows exist in the final unfiltered join result.

Three plans can be modeled as:

$$Cost_A = n_1n_2+n_3$$

$$Cost_B = n_2+ n_2'n_1$$

$$Cost_C = n_1+ n_1'n_2$$

For the median scenario $n_1'=50$, $n_2'=5$, $n_3=250$:

* $Cost_A=1000+250=1250$
* $Cost_B=10+5(100)=510$
* $Cost_C=100+50(10)=600$

To compare Plans B and C algebraically:

$$10+100n_2' < 100+10n_1'$$

which simplifies to:

$$10n_2' - n_1' < 9$$

This demonstrates why an optimizer needs cardinality/selectivity estimates rather than choosing a fixed join order for every dataset.

## 7. Statistics and Selectivity Estimation

A cost-based optimizer relies on metadata such as:

* table/page counts;
* tuple cardinalities;
* number of distinct values per attribute;
* index statistics;
* data-distribution histograms.

Histograms can represent skewed distributions more accurately than a single uniform-distribution assumption. Common forms include **equi-width** and **equi-depth/equi-height** histograms.

Statistics may be refreshed periodically (for example with `ANALYZE`/DBMS-specific statistics tools) or maintained through engine-specific sampling/automatic mechanisms. Stale or inaccurate statistics can cause the optimizer to choose an inappropriate access path or join order.
