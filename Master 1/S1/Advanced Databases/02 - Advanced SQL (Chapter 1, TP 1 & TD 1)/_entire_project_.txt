# The University Database Setup, Constraints & DML

This note integrates **Chapter 1 (Slides 6–7, 44–48)**, **TP 1 (Parts A–S)**, and **TP 2 Part I**, serving as the complete reference for setting up, populating, modifying, and auditing the **`university`** database in **PostgreSQL / pgAdmin 4**.

## 1. Environment Setup & Connecting via pgAdmin 4 (TP 1 Parts A–B, TP 2 Part I)

### Tool Roles

- **SQL:** The declarative language used to communicate with the database.
- **PostgreSQL:** The RDBMS server that executes SQL statements (default port `5432`, superuser `postgres`).
- **pgAdmin 4:** The graphical administration interface used to manage servers and run SQL via the **Query Tool** (click Run or press **F5**).

### Database Creation & Verification Workflow

1. Open pgAdmin 4, expand **Servers**, connect to your PostgreSQL server, open a **Query Tool**, and create the database:
   ```sql
   CREATE DATABASE university;
   ```
2. Refresh **Databases**, locate `university`, right-click it, and open a new **Query Tool** connected specifically to `university` (tables created while connected to the default `postgres` database will not be inside `university`!).
3. Verify the connection and existing base tables (TP 1 Part B.1 & TP 2 Part I):

   ```sql
   SELECT current_database(), current_user, version();

   SELECT table_name
   FROM information_schema.tables
   WHERE table_schema = 'public'
     AND table_type = 'BASE TABLE'
   ORDER BY table_name;
   ```

   _(Important TP 2/TP 3 reminder: Always reuse the `university` tables and data created in TP 1; do not recreate the four main tables or duplicate TP 1 `INSERT` statements.)_

## 2. The `university` Relational Schema & DDL (TP 1 Parts C–E)

The database contains four core entity tables (`department`, `class`, `teacher`, `student`) plus the N:N junction table (`teacher_class`) introduced in TP 1 Part E:

```mermaid
erDiagram
    DEPARTMENT ||--o{ TEACHER : "employs (ON DELETE SET NULL)"
    DEPARTMENT ||--o{ CLASS : "contains (ON DELETE CASCADE)"
    CLASS ||--o{ STUDENT : "enrolls (ON DELETE SET NULL)"
    TEACHER ||--o{ TEACHER_CLASS : "teaches (ON DELETE CASCADE)"
    CLASS ||--o{ TEACHER_CLASS : "taught in (ON DELETE CASCADE)"

    DEPARTMENT {
        integer department_id PK
        varchar department_name "NOT NULL UNIQUE"
    }
    TEACHER {
        integer teacher_id PK
        varchar last_name "NOT NULL"
        varchar first_name "NOT NULL"
        numeric salary "DEFAULT 30000"
        integer department_id FK "nullable"
    }
    CLASS {
        integer class_id PK
        varchar class_name "NOT NULL"
        integer department_id FK
    }
    STUDENT {
        integer student_id PK
        varchar last_name "NOT NULL"
        varchar first_name "NOT NULL"
        integer age "NOT NULL CHECK (age > 0 AND age < 150)"
        integer class_id FK "nullable"
    }
    TEACHER_CLASS {
        integer teacher_id PK_FK
        integer class_id PK_FK
    }
```

### Complete Table Creation Scripts (TP 1 Parts D & E)

```sql
-- 1. department (no dependencies)
CREATE TABLE department (
    department_id INTEGER PRIMARY KEY,
    department_name VARCHAR(50) NOT NULL UNIQUE
);

-- 2. teacher (depends on department)
CREATE TABLE teacher (
    teacher_id INTEGER PRIMARY KEY,
    last_name VARCHAR(50) NOT NULL,
    first_name VARCHAR(50) NOT NULL,
    salary NUMERIC(10,2) DEFAULT 30000,
    department_id INTEGER REFERENCES department(department_id)
        ON DELETE SET NULL
        ON UPDATE CASCADE
);

-- 3. class (depends on department)
CREATE TABLE class (
    class_id INTEGER PRIMARY KEY,
    class_name VARCHAR(50) NOT NULL,
    department_id INTEGER REFERENCES department(department_id)
        ON DELETE CASCADE
        ON UPDATE CASCADE
);

-- 4. student (depends on class)
CREATE TABLE student (
    student_id INTEGER PRIMARY KEY,
    last_name VARCHAR(50) NOT NULL,
    first_name VARCHAR(50) NOT NULL,
    age INTEGER NOT NULL CHECK (age > 0 AND age < 150),
    class_id INTEGER REFERENCES class(class_id)
        ON DELETE SET NULL
        ON UPDATE CASCADE
);

-- 5. teacher_class (N:N junction table; depends on teacher AND class)
CREATE TABLE teacher_class (
    teacher_id INTEGER NOT NULL,
    class_id INTEGER NOT NULL,
    PRIMARY KEY (teacher_id, class_id),
    FOREIGN KEY (teacher_id) REFERENCES teacher(teacher_id)
        ON DELETE CASCADE
        ON UPDATE CASCADE,
    FOREIGN KEY (class_id) REFERENCES class(class_id)
        ON DELETE CASCADE
        ON UPDATE CASCADE
);
```

_(Schema comparison note: Lecture Ch 1 Slide 6 summarizes `student.age` as `SMALLINT` without `CHECK` and omits `DEFAULT 30000` on `salary`; TP 1 defines the complete PostgreSQL lab DDL above.)_

### Why `teacher_class` Is Designed This Way (TP 1 Part E Q1–Q7)

1. **Why not add `class_id` to `teacher`?** Each teacher could reference only **one** class.
2. **Why not add `teacher_id` to `class`?** Each class could reference only **one** teacher.
3. **Why not store `'10, 20, 30'` in one column?** Violates **First Normal Form (1NF)** (non-atomic cell), breaks foreign-key validation, and prevents standard SQL joins.
4. **Junction table principles:** `teacher_class` holds one row per `(teacher, class)` assignment, uses `PRIMARY KEY (teacher_id, class_id)` (a compound key preventing duplicate assignments), leaves `teacher` and `class` completely unmodified, and can later hold relationship attributes like `academic_year` or `semester` (Part P.5 / Part R.23).

## 3. Foreign-Key Referential Actions (TP 1 Part H Q1–Q8)

For the complete table of referential actions (`CASCADE`, `SET NULL`, `RESTRICT`, `NO ACTION`, `SET DEFAULT`), see [[03 - Keys, Data Types & Static Constraints (PostgreSQL)]]. Here are the exact answers to **TP 1 Part H.4 (`Q1`–`Q8`)**:

- **Q1 (Deleting a department):** `teacher.department_id` becomes `NULL` (`ON DELETE SET NULL`), while `class` rows for that department are deleted (`ON DELETE CASCADE`).
- **Q2 (Updating `department.department_id`):** `teacher.department_id` and `class.department_id` automatically update to the new ID (`ON UPDATE CASCADE`).
- **Q3 (Why `SET NULL` instead of `CASCADE` on `teacher.department_id`?):** Teachers are valuable university staff; removing or reorganizing a department must preserve teacher records so they can be reassigned later.
- **Q4 (What if `ON DELETE CASCADE` were used on `teacher.department_id`?):** Deleting a department would accidentally delete all its teachers from the database!
- **Q5 (What if `ON UPDATE CASCADE` were replaced by `ON UPDATE RESTRICT`?):** Any attempt to renumber a `department_id` that still has teachers (or classes) would be **rejected** by PostgreSQL.
- **Q6 (Can `ON DELETE SET NULL` be used on a `NOT NULL` FK?):** **No**—setting the column to `NULL` on parent deletion would violate the `NOT NULL` constraint (PostgreSQL rejects the action/invalidates the rule).
- **Q7 (Concrete SQL triggering `ON UPDATE CASCADE`):**
  ```sql
  UPDATE department SET department_id = 100 WHERE department_id = 1;
  -- All teachers and classes previously in department 1 now have department_id = 100
  ```
- **Q8 (Why `ON DELETE CASCADE` in `teacher_class` instead of `SET NULL`?):** Both `teacher_id` and `class_id` are `NOT NULL` and form the **composite primary key** of `teacher_class`. Primary key columns can never be `NULL`, and an assignment without a teacher or class is meaningless, so removing a teacher or class must cascade-delete its junction rows.

## 4. Insertion Order & Complete TP 1 Seed Dataset (TP 1 Parts I–K)

Because foreign keys require referenced parent rows to exist first, insertion must follow the **dependency graph**:

```mermaid
flowchart LR
    D["1. department<br/>(no dependencies)"] --> T["2a. teacher<br/>(depends on department)"]
    D --> C["2b. class<br/>(depends on department)"]
    C --> S["3. student<br/>(depends on class)"]
    T --> TC["4. teacher_class<br/>(depends on teacher AND class)"]
    C --> TC
```

### Answers to Insertion Order Questions (TP 1 Part I.2 Q1–Q8)

- **Q1–Q4:** `department` has no FKs, so it goes first; `teacher` and `class` reference `department`, so they follow `department`; `student` references `class`, so it follows `class`; `teacher_class` references **both** `teacher` and `class`, so it must be inserted last.
- **Q5 (Insert student with non-existent `class_id = 99`):** PostgreSQL rejects the insertion with a **foreign-key constraint violation** (`insert or update on table "student" violates foreign key constraint`).
- **Q6–Q7 (Insert teacher with `department_id = NULL` or student with `class_id = NULL`):** **Yes!** Both FK columns are nullable (no `NOT NULL` constraint). In SQL, a `NULL` foreign key means "no parent assigned yet" and satisfies referential integrity (e.g., **student 8 Farah Ines** has `class_id = NULL`).
- **Q8 (Insert `teacher_class` with missing `teacher_id`):** Rejected by PostgreSQL with a foreign-key constraint violation.

## 5. DML Operations: `INSERT`, `UPDATE`, `DELETE` (Ch 1 Slides 44–48 & TP 1 Part M)

### `INSERT` Forms (Ch 1 Slides 45–46)

1. **Single row (positional):** `INSERT INTO department VALUES (6, 'Biologie');`
2. **Multiple rows:** `INSERT INTO department VALUES (7, 'Génie Civil'), (8, 'Chimie Industrielle');`
3. **Explicit column list:** `INSERT INTO department (department_id, department_name) VALUES (9, 'Biotechnologie');` (omitted columns receive `DEFAULT` or `NULL`).
4. **From another query (`INSERT ... SELECT`):**
   ```sql
   INSERT INTO destination_table
   SELECT ... FROM source_table WHERE ...;
   ```

### `UPDATE` & Composite-Key Replacement (TP 1 Part M.1–M.5)

Always use `WHERE` unless you intend to overwrite every row in the table! Use `BEGIN; ... ROLLBACK;` (or restore values afterwards) when running temporary tests.

```sql
-- M.1: Modify one teacher's salary
UPDATE teacher SET salary = 78000 WHERE teacher_id = 101;

-- M.2: Increase department 1 salaries by 5% (explicitly excluding NULL)
UPDATE teacher SET salary = salary * 1.05
WHERE department_id = 1 AND salary IS NOT NULL;

-- M.3: Assign student 8 to class 10
UPDATE student SET class_id = 10 WHERE student_id = 8;

-- M.4: Increase salaries below 50000 by 10%
UPDATE teacher SET salary = salary * 1.10 WHERE salary < 50000;

-- M.5: Reassign teacher 103 from class 30 to class 40 in junction table
-- Note: Replace composite key via DELETE + INSERT (not direct UPDATE of PK!)
DELETE FROM teacher_class WHERE teacher_id = 103 AND class_id = 30;
INSERT INTO teacher_class (teacher_id, class_id) VALUES (103, 40);
```

### `DELETE` (Ch 1 Slide 48)

```sql
DELETE FROM table_name WHERE condition;

- **R.14 (`INSERT` vs `UPDATE` vs `ALTER TABLE` vs `SELECT`):**
  - `INSERT` (DML): adds **new rows** to an existing table.
  - `UPDATE` (DML): modifies **existing row values** in a table.
  - `ALTER TABLE` (DDL): modifies the **table structure/schema** (columns, data types, constraints).
  - `SELECT` (DQL/DML): **reads/queries** data without changing stored tables or structure.

JOIN teacher_class tc ON c.class_id = tc.class_id
JOIN teacher t ON tc.teacher_id = t.teacher_id
ORDER BY c.class_name, t.last_name;

-- R.20: Teachers teaching more than 2 classes
SELECT t.teacher_id, t.last_name, t.first_name, COUNT(tc.class_id) AS class_count
FROM teacher t JOIN teacher_class tc ON t.teacher_id = tc.teacher_id
GROUP BY t.teacher_id, t.last_name, t.first_name
HAVING COUNT(tc.class_id) > 2;

FROM class c JOIN teacher_class tc ON c.class_id = tc.class_id
GROUP BY c.class_id, c.class_name
HAVING COUNT(tc.teacher_id) = 1;

-- R.22: Teachers who teach no class
SELECT t.teacher_id, t.last_name, t.first_name
FROM teacher t LEFT JOIN teacher_class tc ON t.teacher_id = tc.teacher_id
WHERE tc.class_id IS NULL;

-- R.23: Add semester column to teacher_class and set to 'S1'
ALTER TABLE teacher_class ADD COLUMN semester VARCHAR(10);
UPDATE teacher_class SET semester = 'S1';

-- R.24–R.25: Deleting a teacher or class (inside reversible test)
BEGIN;
DELETE FROM teacher WHERE teacher_id = 109; -- corresponding rows in teacher_class (109, 20) vanish via ON DELETE CASCADE
DELETE FROM class WHERE class_id = 50;      -- corresponding rows in teacher_class (106, 50), (107, 50) vanish via ON DELETE CASCADE
ROLLBACK;

-- R.26: All constraints of teacher using pg_constraint
SELECT c.conname, c.contype, pg_get_constraintdef(c.oid) AS definition
FROM pg_constraint c
JOIN pg_class t ON c.conrelid = t.oid
WHERE t.relname = 'teacher';

-- R.27: All constraints of class using information_schema
SELECT constraint_name, constraint_type
FROM information_schema.table_constraints
WHERE table_schema = 'public' AND table_name = 'class';

-- R.28: ON DELETE and ON UPDATE rules of all foreign keys in public schema
SELECT tc.table_name, rc.constraint_name, rc.delete_rule, rc.update_rule
FROM information_schema.referential_constraints rc
JOIN information_schema.table_constraints tc
  ON rc.constraint_name = tc.constraint_name
 AND rc.constraint_schema = tc.constraint_schema
WHERE tc.table_schema = 'public'
ORDER BY tc.table_name, rc.constraint_name;
```

# Set Operations, Subqueries, CTEs & CASE Expressions

This note integrates **Chapter 1 (Slides 30–43, 49)**, **TD 1 (Questions 20\*–29, 31)**, **TP 2 Ex 12 Task 9**, and advanced querying/optimization concepts (`ANY`/`ALL`/`SOME`, Set Ops vs. Joins, Division, and SQL best practices).

## 1. Set Operations (`UNION`, `INTERSECT`, `EXCEPT`) vs. Joins

Set operations combine results **vertically** (requiring identical column count and compatible types); joins link rows **horizontally**.

### Course `university` Examples (Ch 1 Slides 31–33)

```sql
-- UNION (removes duplicates; use UNION ALL to keep duplicates & avoid sort/hash overhead)
SELECT last_name FROM student WHERE class_id = 10
UNION
SELECT last_name FROM student WHERE class_id = 20;
-- Result: Ahmed, Ali, Amine, Benali

-- INTERSECT (common rows)
SELECT last_name FROM student WHERE class_id = 10
INTERSECT
SELECT last_name FROM student WHERE class_id = 20;
-- Result: Ali

-- EXCEPT (in first query, absent from second)
SELECT last_name FROM student WHERE class_id = 10
EXCEPT
SELECT last_name FROM student WHERE last_name = 'Ahmed';
-- Result: Ali
```

### Three Critical Differences: `INTERSECT` vs. `INNER JOIN`

1. **Duplicates:** `INTERSECT` (set) returns each matching value **once**. `INNER JOIN` **multiplies** duplicates ($5 \times 5 = 25$ rows if an ID appears 5 times on each side; requires `DISTINCT` to mimic `INTERSECT`).
2. **`NULL` Values:** **`INTERSECT` treats `NULL = NULL` as a match**, whereas **`INNER JOIN` drops `NULL` rows** (because `NULL = NULL` evaluates to `UNKNOWN`).
3. **Column Flexibility:** `INTERSECT` requires identical schemas in both queries; `INNER JOIN` can project arbitrary columns from both tables.
   _(Dialect note: PostgreSQL supports `UNION`, `INTERSECT`, and `EXCEPT` natively. Older MySQL lacks `INTERSECT` and `EXCEPT`, requiring `WHERE col IN (...)` and `WHERE col NOT IN (...)` / `NOT EXISTS`.)_

---

## 2. Subqueries, Correlation & `EXISTS` vs. `JOIN`

- **Non-Correlated Subquery:** Inner query executes independently once and returns a scalar or set (`WHERE salary > (SELECT AVG(salary) FROM teacher)`).
- **Correlated Subquery:** Inner query references a column from the outer row (`WHERE t.department_id = d.department_id`). Logically evaluated per outer row.
- **`EXISTS (SELECT 1 FROM ...)`:** Stops scanning the inner table the instant **one** matching row is found (often much faster than `JOIN` when you only test existence and don't need columns from the inner table; writing `SELECT 1` is standard convention because only row existence matters).
- **The `NOT IN` NULL Trap:** If a subquery inside `NOT IN (...)` returns **even a single `NULL`**, `x NOT IN (1, 2, NULL)` evaluates to `UNKNOWN` for every row and returns **0 rows**! Always prefer **`NOT EXISTS`** (or add `WHERE col IS NOT NULL` inside the subquery).

---

## 3. Quantified Operators: `ANY`, `SOME`, and `ALL` (Ch 1 Slides 40–41)

Multi-row subqueries cannot be compared with plain `>` or `=`. SQL provides `ANY`, `SOME` (exact synonym of `ANY`), and `ALL`:

| Operator                       | Meaning                                                   | Mathematical Equivalent (No `NULL`s) |
| :----------------------------- | :-------------------------------------------------------- | :----------------------------------- |
| `x > ANY (S)` / `x > SOME (S)` | True if $x$ is greater than **at least one** value in $S$ | `x > MIN(S)`                         |
| `x < ANY (S)`                  | True if $x$ is less than **at least one** value in $S$    | `x < MAX(S)`                         |
| `x = ANY (S)`                  | Equal to at least one value in $S$                        | `x IN (S)`                           |
| `x > ALL (S)`                  | True if $x$ is greater than **every** value in $S$        | `x > MAX(S)`                         |
| `x < ALL (S)`                  | True if $x$ is less than **every** value in $S$           | `x < MIN(S)`                         |
| `x <> ALL (S)`                 | Not equal to any value in $S$                             | `x NOT IN (S)`                       |

> [!WARNING] Two `ALL` Traps on Exams!
>
> 1. **The `NULL` Trap:** If the subquery returns `[100, 200, NULL]`, `x > ALL (...)` expands to `x > 100 AND x > 200 AND x > NULL`, yielding **`UNKNOWN`** and returning **0 rows**! Always filter `AND salary IS NOT NULL` inside `ALL` subqueries when `NULL` is possible.
> 2. **Ch 1 Slide 41 (`> ALL` on Department 2):** `SELECT last_name, salary FROM teacher WHERE salary > ALL (SELECT salary FROM teacher WHERE department_id = 2);` returns **0 rows**! Why? Department 2 (`Mathématiques`) contains `Karim` (`48000`) and `Haddad` (`85000`), and `85000` is already the maximum salary across the entire university—no teacher earns strictly more than `85000`.
>    _(Meanwhile, Slide 40 `> ANY` on Department 2 returns the 6 teachers earning $> 48000$: Benali `75000`, Saidi `62000`, Haddad `85000`, Mansouri `55000`, Rahmani `72000`, Ahmed `68000`.)_

## 4. Common Table Expressions (`WITH`) & Conditional `CASE`

### Common Table Expressions (`WITH`) — Ch 1 Slides 42–43

A **CTE** defines a named temporary virtual table scoped strictly to a single query, replacing unreadable nested subqueries:

```sql
-- Ch 1 Slide 43: Teachers earning more than the overall average salary
WITH average_salary AS (
    SELECT AVG(salary) AS avg_salary
    FROM teacher
)
SELECT t.last_name, t.salary
FROM teacher t, average_salary a
WHERE t.salary > a.avg_salary;
-- Result: Benali (75000), Haddad (85000), Rahmani (72000), Ahmed (68000)
```

### `CASE` Conditional Expression — Ch 1 Slide 49

Evaluates `WHEN` conditions top-to-bottom and returns the first match:

```sql
SELECT last_name, salary,
       CASE
           WHEN salary >= 70000 THEN 'High'
           WHEN salary >= 50000 THEN 'Medium'
           WHEN salary IS NOT NULL THEN 'Low'
           ELSE 'Not reported'
       END AS category
FROM teacher;
```

_(Notice why `WHEN salary IS NOT NULL THEN 'Low'` works safely after `>= 70000` and `>= 50000`: any `NULL` salary fails all three comparisons and falls cleanly into `ELSE 'Not reported'` for Khelifi Nora.)_

# Querying, Filtering, Aggregation & Joins

This note integrates **Chapter 1 (Slides 12–29)**, **TP 1 (Parts L & N)**, **TD 1 (Questions 1*–19*, 30)**, and the complete join mechanics from the vault (`INNER`, `LEFT`, `RIGHT`, `FULL OUTER`, `CROSS`, `SELF JOIN`, `NATURAL JOIN`, 3-table chains, and `NOT NULL` foreign key interactions).

---

## 1. `SELECT` Syntax, Logical Execution Order & Quoting Rules

### Standard `SELECT` Syntax (Ch 1 Slides 12–13)

```sql
SELECT [ DISTINCT | ALL ] select_list
FROM table1 [, table2 ...]
[ WHERE condition ]
[ GROUP BY grouping_columns ]
[ HAVING group_condition ]
[ ORDER BY sort_expressions ]
[ OFFSET n ROWS ]
[ FETCH FIRST m ROWS ONLY ];
```

- **Logical Processing Order (Critical for Avoiding Errors!):**
  1. `FROM` / `JOIN` (build working table)
  2. `WHERE` (filter raw rows)
  3. `GROUP BY` (form groups)
  4. `HAVING` (filter groups)
  5. `SELECT` (evaluate expressions & create column aliases)
  6. `DISTINCT` (remove duplicate output rows; `ALL` is the default)
  7. `ORDER BY` (sort by expression, alias, or 1-based column position; `ASC` default, `DESC` descending)
  8. `OFFSET ... ROWS` / `FETCH FIRST ... ROWS ONLY` (skip first $n$ rows, return at most $m$ rows; PostgreSQL/MySQL also support `LIMIT m OFFSET n`).
- Because `SELECT` runs _after_ `WHERE`, **column aliases cannot be used in `WHERE`** (they _can_ be used in `ORDER BY`).

### Quoting Rules (Common Exam Pitfall!)

- **Single quotes (`'...'`):** **String literals** (`WHERE first_name LIKE '%am%'`, `WHERE last_name = 'Ahmed'`). _Never use double quotes for strings in PostgreSQL—PostgreSQL treats `"..."` as a column/table identifier!_
- **Double quotes (`"..."`):** **Identifiers** containing spaces or case sensitivity (`SELECT salary AS "Monthly Salary"`). Simple lowercase aliases (`AS monthly_salary`) need no quotes. _(MySQL uses backticks `` `...` `` for identifiers and permissively accepts `"..."` for strings, which violates ANSI SQL.)_

---

## 2. Filtering (`WHERE`), Pattern Matching & `NULL`

- **Logical Operator Precedence:** `NOT` binds tightest, then `AND`, then `OR`. Always parenthesize `OR` conditions combined with `AND` (`WHERE age BETWEEN 21 AND 23 AND (class_id = 10 OR class_id = 20)`).
- **`BETWEEN a AND b`:** Inclusive interval ($a \le x \le b$).
- **`IN (v1, v2, ...)`:** Membership in an explicit list.
- **`LIKE` vs. PostgreSQL `ILIKE` (TP 1 Part N.7–N.8):**
  - `%` matches **0 or more** characters; `_` matches **exactly 1** character.
  - `LIKE 'A%'` is **case-sensitive** in PostgreSQL (matches `'Ahmed'`, skips `'ahmed'`).
  - `ILIKE 'a%'` is a **PostgreSQL extension** for case-insensitive pattern matching.
- **`NULL` Testing:** `salary = NULL` or `salary <> NULL` evaluates to `UNKNOWN` (excluded by `WHERE`). Always test **`IS NULL`** and **`IS NOT NULL`**.
- **Sorting with `NULL`:** In PostgreSQL, `ORDER BY salary DESC` places `NULL`s **first** by default (`NULLS FIRST` for `DESC`, `NULLS LAST` for `ASC`). Add `NULLS LAST` when sorting top salaries (`ORDER BY salary DESC NULLS LAST`).

---

## 3. Built-in Functions, Aggregations & Grouping Nuances

### Scalar & Aggregate Functions (Ch 1 Slide 15)

| Category        | Functions                                                    | Example             |
| :-------------- | :----------------------------------------------------------- | :------------------ |
| **Aggregation** | `COUNT(*)`, `COUNT(col)`, `SUM()`, `AVG()`, `MIN()`, `MAX()` | `AVG(salary)`       |
| **Character**   | `UPPER()`, `LOWER()`, `LENGTH()`                             | `UPPER(last_name)`  |
| **Numeric**     | `ROUND(val, n)`, `ABS(val)`                                  | `ROUND(average, 2)` |
| **Dates**       | `CURRENT_DATE`, `CURRENT_TIMESTAMP`                          | `CURRENT_TIMESTAMP` |

### `NULL` Semantics in Aggregations (Critical Nuance!)

- **`COUNT(*)`** counts **every physical row** in the table/group (returns `9` on `teacher`).
- **`COUNT(col)`, `SUM(col)`, `AVG(col)`, `MIN(col)`, `MAX(col)` ignore `NULL`s completely!**
  - Teacher 109 (`Khelifi Nora`) has `salary = NULL`. Thus `COUNT(salary)` is `8` (not 9), and `AVG(salary)` in department 1 (`75000`, `62000`, `68000`, `NULL`) computes $(75000 + 62000 + 68000)/3 = \mathbf{68333.33}$ (Ch 1 Slide 20)!
  - **Fixing `NULL` math when needed:** Use `COALESCE(salary, 0)` (ANSI SQL / PostgreSQL; `IFNULL(salary, 0)` in MySQL) inside `AVG(COALESCE(salary, 0))` if missing salaries should count as `0`.
- **Empty set:** `COUNT(*)` returns **`0`**, whereas `AVG`, `SUM`, `MIN`, `MAX` return **`NULL`**.

### `GROUP BY` and `HAVING` vs. `WHERE`

- **`WHERE`** filters raw rows **before** grouping (cannot reference aggregate functions like `AVG(salary)`).
- **`GROUP BY`** collapses rows sharing identical values in the grouping column(s). Every non-aggregated column in `SELECT` must appear in `GROUP BY`.
- **`HAVING`** filters aggregated groups **after** `GROUP BY` (`HAVING AVG(salary) > 60000` returns only department `1` with `68333.33`, Ch 1 Slide 20).

## 4. Complete Guide to SQL Joins

In a normalized database, joins belong to **DQL/DML** (`SELECT`)—they reassemble fragmented tables virtually without altering stored tables.

```mermaid
flowchart LR
    T1["Left Table (A)"] --> J{"Join Strategy"}
    T2["Right Table (B)"] --> J
    J -->|"CROSS JOIN"| C["All A x B combinations"]
    J -->|"INNER JOIN"| I["Matched pairs only"]
    J -->|"LEFT OUTER JOIN"| L["All A + matched B (NULL gaps)"]
    J -->|"RIGHT OUTER JOIN"| R["All B + matched A (NULL gaps)"]
    J -->|"FULL OUTER JOIN"| F["All A + All B (NULL gaps)"]
```

### A. `CROSS JOIN` (Cartesian Product)

Pairs every row of Table A with every row of Table B (Ch 1 Slide 21: `9 teachers × 5 departments = 45 rows`):

```sql
SELECT t.last_name, t.first_name, d.department_name
FROM teacher AS t CROSS JOIN department AS d;
```

_(Old SQL-89 comma syntax `FROM teacher t, department d` without `WHERE` produces a `CROSS JOIN`; in ANSI-92, `JOIN` without `ON` is a syntax error unless `CROSS JOIN` or `NATURAL JOIN` is used.)_

### B. `INNER JOIN` (Match or Die)

Returns **only rows matching the `ON` condition** in both tables. The `INNER` keyword is optional (`JOIN` = `INNER JOIN`), and logical table order (`A JOIN B` vs. `B JOIN A`) does not change the result set.

- **Filtering effect:** On `student s INNER JOIN class c ON s.class_id = c.class_id` (Ch 1 Slide 22), **9 students appear** and **Farah Ines** (`class_id = NULL`) disappears! Similarly, in a `Customer` / `Card` schema, customers with no card (`Sarah`) vanish; in `Student(SID, Name, DeptID)` / `Department`, a student with an unmatched `DeptID = 99` (`Leila`) disappears.

#### Multi-Table `INNER JOIN` Chains & Cumulative Filtering

Chaining `INNER JOIN`s evaluates matches pairwise—every additional join acts as an extra filter, shrinking unmatched orphans out of the result:

1. **Course `university` 3-Table Chain (Ch 1 Slide 27):** `student s JOIN class c ON s.class_id = c.class_id JOIN department d ON c.department_id = d.department_id` $\to$ displays each enrolled student, class, and department (drops Farah).
2. **Banking Lookup Pattern (`customer` $\to$ `card` $\to$ `card_type`):** Connects `customer` to `card` on `customer_id`, then `card` to lookup table `card_type` (`Visa`, `Mastercard`, `rate`) on `card_type_id`. Any customer with no card or unissued `card_type` (`Amex`) disappears.
3. **Video-Sharing Walkthrough (`user` $\to$ `comment` $\to$ `video`):**
   - Suppose 6 users (`1..6`, where `6: BestSpeller` has no comments), 8 videos (`1..8`, where `8: Database Design 8` has no comments), and 6 comments (`comment.user_id` and `comment.video_id` both `NOT NULL`).
   - Step 1 (`user INNER JOIN comment`): keeps all 6 comments, drops `BestSpeller`.
   - Step 2 (`... INNER JOIN video`): keeps all 6 comments, drops `Database Design 8`.

### C. Outer Joins (`LEFT`, `RIGHT`, `FULL OUTER`)

Preserve unmatched rows from one or both sides, filling missing columns with `NULL` (keyword `OUTER` is optional):

- **`LEFT OUTER JOIN`:** Keeps **all rows from the left table** (`student s LEFT JOIN class c` keeps **Farah** with `class_name = NULL`, Ch 1 Slide 23; `Customers LEFT JOIN Orders` keeps **Charlie** with `OrderID = NULL`).
- **`RIGHT OUTER JOIN`:** Keeps **all rows from the right table** (`student s RIGHT JOIN class c` keeps **M1-Physique** with `last_name = NULL`, Ch 1 Slide 24; `customer RIGHT JOIN card` keeps unassigned card `104` with `name = NULL`). Every `A RIGHT JOIN B` can be rewritten equivalently as `B LEFT JOIN A`; preferring `LEFT JOIN` consistently makes multi-table queries easier to read.
- **Finding Orphans Pattern:** `LEFT JOIN ... WHERE right_table.pk IS NULL` returns only unmatched left rows (e.g., customers with no card, teachers with no class).
- **`FULL OUTER JOIN`:** Keeps **all rows from both tables** (`student s FULL OUTER JOIN class c` keeps **both Farah and M1-Physique**, Ch 1 Slide 25).
  - _DBMS Note:_ **PostgreSQL supports `FULL OUTER JOIN` natively.** **MySQL does not**; simulate it in MySQL via `(SELECT ... LEFT JOIN ...) UNION (SELECT ... RIGHT JOIN ...)` (using `UNION` to deduplicate matched rows).

#### Chaining Outer Joins Across 3 Tables (`user` $\to$ `comment` $\to$ `video`)

- **Sequential Trap:** `FROM user LEFT JOIN comment ... RIGHT JOIN video ...` first preserves all users (`Carol`, `Dave` with `NULL` comments), then Step 2 (`RIGHT JOIN video`) **eliminates `Carol` and `Dave`** because their `NULL` `video_id` fails to match any video, while keeping Video 3 (`Joins`) with `NULL` user/comment!
- **Clean Strategy:** Always place the primary table whose rows must ALL survive first in `FROM`, and chain `LEFT OUTER JOIN`s consistently (`FROM video LEFT JOIN comment ... LEFT JOIN user ...`).

### D. How `NOT NULL` Foreign Keys Affect Joins

When a child FK like `comment.user_id` is declared **`NOT NULL`**, every comment is guaranteed to match a user:

| Join Query                | Users Included           | Comments Included | `NULL`s Produced                       |
| :------------------------ | :----------------------- | :---------------- | :------------------------------------- |
| `user INNER JOIN comment` | Only users with comments | All               | None                                   |
| `comment LEFT JOIN user`  | Only users with comments | All               | None (**identical to `INNER JOIN`**!)  |
| `user LEFT JOIN comment`  | **All users**            | All               | `NULL` comment fields for silent users |

_(By contrast, when `card.customer_id` is nullable, `card LEFT JOIN customer` differs from `INNER JOIN` by preserving unassigned cards.)_

### E. `SELF JOIN` & Table Aliases

There is no `SELF JOIN` keyword—you join a table to itself using **mandatory distinct table aliases** (`t1` and `t2`, `e` and `m`):

1. **Same-Group Pairs without Duplicates (Ch 1 Slide 26 — `university`):**
   Find pairs of teachers in the same department:
   ```sql
   SELECT t1.last_name AS teacher1, t2.last_name AS teacher2, t1.department_id
   FROM teacher t1
   JOIN teacher t2
     ON t1.department_id = t2.department_id
    AND t1.teacher_id < t2.teacher_id;
   ```

   - **Why `t1.teacher_id < t2.teacher_id`?** (1) Prevents pairing a teacher with themselves (`Benali, Benali`); (2) keeps each unordered pair **once** (`Benali, Saidi` without `Saidi, Benali`). Produces 8 pairs: 6 in dept 1, 1 in dept 2 (`Karim, Haddad`), 1 in dept 3 (`Mansouri, Rahmani`). _(Using `E1.ID <> E2.ID` prevents self-matches but emits both `(A,B)` and `(B,A)`.)_
2. **Hierarchical Employee-Manager (`Diana Prince`, `Bruce Wayne`, `Clark Kent`):**
   ```sql
   SELECT e.first_name AS employee, m.first_name AS manager
   FROM employee AS e
   LEFT OUTER JOIN employee AS m ON e.manager_id = m.employee_id;
   ```
   Using `LEFT OUTER JOIN` ensures the CEO (`Diana`, `manager_id = NULL`) stays in the output with `NULL` manager rather than vanishing under `INNER JOIN`. Same pattern applies to referral chains (`u1.referred_by = u2.user_id`).
3. **Sequential Lookup:** Find flights departing from the same city as `'F09'`:
   ```sql
   SELECT F2.code FROM Flight F1 JOIN Flight F2 ON F1.departure = F2.departure WHERE F1.code = 'F09';
   ```

### F. `NATURAL JOIN`

`SELECT * FROM student NATURAL JOIN class;` (Ch 1 Slides 28–29) auto-joins on the shared column `class_id`, eliminates the duplicate column (`7` columns total instead of `8`), and returns the 9 enrolled students (dropping Farah Ines). **Avoid in production** because adding an unrelated same-named column later breaks the join silently.

SELECT student_id, last_name, first_name, age, age + 5 AS age_after_5_years FROM student;

-- 14*. Total teachers, avg salary, min salary
SELECT COUNT(*) AS total_teachers, AVG(salary) AS average_salary, MIN(salary) AS minimum_salary FROM teacher;

-- 15*. Number of teachers in each department (teacher table only)
SELECT department_id, COUNT(*) AS number_of_teachers FROM teacher GROUP BY department_id;

-- 16*. Per department: count, avg, min, max
SELECT department_id, COUNT(*) AS number_of_teachers,
       AVG(salary) AS average_salary, MIN(salary) AS minimum_salary, MAX(salary) AS maximum_salary
FROM teacher GROUP BY department_id;

-- 17*. Departments having at least two teachers
SELECT department_id, COUNT(*) AS number_of_teachers
FROM teacher GROUP BY department_id HAVING COUNT(*) >= 2;

-- 18*. Each teacher with department name (INNER JOIN)
SELECT t.last_name, t.first_name, d.department_name, t.salary
FROM teacher t INNER JOIN department d ON t.department_id = d.department_id;

-- 19*. All departments, including departments with no teachers (LEFT JOIN)
-- Critical: COUNT(t.teacher_id) returns 0 for Chimie; COUNT(*) would wrongly return 1!
SELECT d.department_id, d.department_name, COUNT(t.teacher_id) AS number_of_teachers
FROM department d LEFT JOIN teacher t ON d.department_id = t.department_id
GROUP BY d.department_id, d.department_name
ORDER BY d.department_id;

-- 30.1 Departments without teachers (Chimie) -> NOT EXISTS avoids duplicate rows & short-circuits
SELECT d.* FROM department d
WHERE NOT EXISTS (SELECT 1 FROM teacher t WHERE t.department_id = d.department_id);

-- 30.2 Classes without students (M1-Physique) -> NOT EXISTS short-circuits on first student
SELECT c.* FROM class c
WHERE NOT EXISTS (SELECT 1 FROM student s WHERE s.class_id = c.class_id);

-- 30.3 Students without classes (Farah Ines) -> LEFT JOIN + IS NULL (or directly WHERE s.class_id IS NULL)
SELECT s.* FROM student s
LEFT JOIN class c ON s.class_id = c.class_id
WHERE c.class_id IS NULL;
