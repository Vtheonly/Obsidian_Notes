# Transaction and Recovery Edge Cases

This note collects the deeper transaction-control and crash-recovery details needed for exercises where the basic ACID summary is not enough.

## 1. Explicit Transactions and Auto-Commit

A transaction may be controlled explicitly:

```sql
START TRANSACTION;

UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;

COMMIT;
```

Use `ROLLBACK` instead of `COMMIT` when the operation must be cancelled.

In auto-commit mode, each completed statement is committed independently. This is convenient for isolated operations but dangerous for a multi-step business operation because an error in a later statement does not automatically undo earlier statements that have already committed.

```sql
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
-- This statement may already be committed in auto-commit mode.
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
```

For a transfer, order placement, or registration workflow, the related modifications should therefore be grouped into one transaction.

## 2. Savepoints and Partial Rollback

A savepoint is a recovery marker inside an open transaction.

```sql
START TRANSACTION;

INSERT INTO Logs VALUES (...);
SAVEPOINT step1;

UPDATE Accounts SET ...;
SAVEPOINT step2;

DELETE FROM Accounts WHERE ...;

ROLLBACK TO SAVEPOINT step2;
-- DELETE is undone; earlier work remains.

COMMIT;
```

### Savepoint lifecycle

* `SAVEPOINT name` creates or replaces a marker.
* `ROLLBACK TO SAVEPOINT name` undoes work after the marker while keeping the transaction active.
* A full `ROLLBACK` ends the transaction and removes its savepoints.
* `COMMIT` ends the transaction and removes its savepoints.
* Rolling back to an earlier savepoint invalidates later savepoints in the same transaction.

## 3. Crash Timing and the Transaction Log

The effect of a crash depends on the point at which the transaction failed.

| Crash point | Transaction status | Typical recovery action |
| :--- | :--- | :--- |
| Before `COMMIT` | Uncommitted | UNDO the incomplete transaction |
| During `COMMIT`, before the commit record is durable | Commit not recorded | Treat as uncommitted and UNDO |
| During `COMMIT`, after the commit record is durable | Committed in the log | REDO as necessary |
| During rollback | Transaction still incomplete | Recovery continues the rollback/UNDO work |

The important boundary is the durable commit record in the log, not merely the moment the client sent the `COMMIT` command.

## 4. Buffer Management Policies

Two useful implementation dimensions describe how a DBMS handles dirty pages:

* **STEAL:** The buffer manager may write an uncommitted transaction's modified page to disk. Because uncommitted data can reach disk, recovery needs an **UNDO** mechanism.
* **NO-STEAL:** Uncommitted dirty pages are kept out of permanent storage until commit. This simplifies UNDO but requires more memory.
* **FORCE:** At commit, all pages modified by the transaction are forced to disk. This can simplify REDO but increases commit I/O.
* **NO-FORCE:** Commit does not require every modified data page to be written immediately. WAL plus REDO provides durability after a crash.

Modern systems commonly favor **STEAL + NO-FORCE**, which makes logging and recovery more important but allows efficient buffer management.

## 5. Write-Ahead Logging Details

The WAL principle requires the relevant log record to be durable before the corresponding modified data page is written to permanent storage.

A useful abstract log record contains:

| Field | Purpose |
| :--- | :--- |
| `LSN` | Log Sequence Number identifying record order |
| `prevLSN` | Links the same transaction's previous record |
| `TxID` | Identifies the transaction |
| `Type` | `START`, `UPDATE`, `COMMIT`, `ABORT`, `CLR`, etc. |
| `PageID` | Identifies the affected data page |
| Before image | Value needed for UNDO |
| After image | Value needed for REDO |

The log is sequentially ordered, allowing recovery to determine transaction history even when data pages were written in a different order.

## 6. Checkpoints

A checkpoint records a known recovery position. Its purpose is to reduce startup work by allowing the recovery manager to focus on the relevant part of the log instead of scanning from the beginning of the database's history.

A simplified checkpoint sequence is:

1. Record checkpoint information in the log.
2. Flush required log records according to WAL rules.
3. Flush some or all dirty pages according to the checkpoint method.
4. After a crash, begin analysis from an appropriate checkpoint position and account for transactions that were still active.

The exact checkpoint algorithm is DBMS-specific; not every system literally freezes all work or writes every dirty page at once.

## 7. ARIES-Style Recovery: Analysis, REDO, UNDO

A simplified ARIES-style recovery process can be understood in three phases:

### Analysis
Reconstruct the state of transactions and dirty pages from the log, identifying:

* transactions that committed;
* transactions that were still active at the crash;
* the point from which REDO must begin.

### REDO
Repeat history from the appropriate log position so that committed changes are reflected on the data pages. REDO is designed to make the database state consistent with the durable log history.

### UNDO
Roll back transactions that were incomplete at crash time. UNDO follows transaction history backward and restores the required earlier state.

### Compensation Log Records (CLRs)
During recovery UNDO, the DBMS may write **Compensation Log Records** that record the fact that an earlier action has been undone. This makes recovery itself restartable if another crash occurs during recovery.

## 8. Worked Recovery Example

Suppose the log contains:

| LSN | Tx | Operation | Before | After |
| :---: | :---: | :--- | :---: | :---: |
| `001` | `T1` | `START` | — | — |
| `002` | `T1` | `UPDATE Account1.balance` | 500 | 300 |
| `003` | `T2` | `START` | — | — |
| `004` | `T2` | `UPDATE Account2.balance` | 300 | 500 |
| `005` | `T1` | `COMMIT` | — | — |
| `006` | — | `CRASH` | — | — |

At crash time:

* `T1` is a **winner** because its `COMMIT` record is present.
* `T2` is a **loser** because it has no matching `COMMIT` or completed abort record.

Recovery must ensure:

1. `T1`'s change survives by REDO as required.
2. `T2`'s uncommitted change is removed by UNDO.
3. Final values are `Account1.balance = 300` and `Account2.balance = 300`.

## 9. Exam Pattern: Multi-Step Transaction

For a process such as student registration:

```sql
START TRANSACTION;

UPDATE StudentAccount
SET balance = balance - fee
WHERE id = 10;

INSERT INTO Enrollment(student_id, course_id, enrollment_date)
VALUES (10, 20, CURRENT_DATE);

UPDATE Course
SET places_available = places_available - 1
WHERE id = 20;

COMMIT;
```

If the system crashes before the commit is durable, recovery must not leave a state where money was removed and enrollment was recorded while the course capacity remained unchanged. Atomicity requires the incomplete transaction to be undone.

## 10. Golden Rules for Exercises

1. Treat a transaction as one logical unit of work, not as a sequence of unrelated statements.
2. Use savepoints when partial rollback is required but the whole transaction should remain active.
3. Distinguish **logical commit** from **durable commit record** when analyzing crash timing.
4. Use WAL to explain why committed work can be REDOed and incomplete work can be UNDOed.
5. For recovery exercises, classify transactions at the crash point before choosing REDO or UNDO.
