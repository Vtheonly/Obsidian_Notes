# Cursors & Row-by-Row Processing

This note integrates **Chapter 2 Cursor Module (Slides 43–60)**, **TP 3 (Part I Exercises 1–7 & Part III Exercise 15)**, **TD 3 (Part I Exercises 1*–6)**, **TD 2 Exercise 3***, and **Legacy Airline TD 4 Cursors (`total_hvol_AF` & `Gestion_Pilotes`)**.

---

## 1. What Is a Cursor & When Should We Use One?

A `SELECT` query may return zero, one, or many rows. Whereas standard SQL is **set-oriented**, a **cursor** is a named handle (like a bookmark moving down a list of rows) enabling a stored routine to process query results **one row at a time**.
- *Important distinction:* A cursor is a **programming interface**—it does not necessarily mean the DBMS physically reads disk blocks one row at a time.

### Cursor vs. Set-Based SQL (Ch 2 Slides 46, 54 & TD 3 Ex 6)
Before writing a cursor, ask: **"Can one SQL statement handle all qualifying rows?"**
- **Prefer Set-Based SQL** (`UPDATE ... WHERE`, `DELETE ... WHERE`, `INSERT ... SELECT`, `GROUP BY`, `CASE`) for ordinary bulk transformations, filtering, and aggregation—it executes far faster inside the optimizer without row-by-row context switching or long-held locks.
- **Use a Cursor** when each row requires sequential row-by-row decisions, complex multi-step procedural validation, calling a stored procedure or printing row-level `RAISE NOTICE` diagnostics per row, or maintaining sequential stateful accumulators (such as stopping mid-way when a running budget hits zero).

---

## 2. The 6-Step Explicit Cursor Lifecycle & Syntax Comparison

```mermaid
flowchart LR
    D["1. DECLARE<br/>Bind cursor to SELECT"] --> O["2. OPEN<br/>Execute query & activate"]
    O --> F["3. FETCH<br/>Load next row into variables"]
    F --> T{"Row fetched?"}
    T -->|"Yes"| P["4. PROCESS<br/>Execute row logic"]
    P -->|"5. REPEAT"| F
    T -->|"No (NOT FOUND)"| CL["6. CLOSE<br/>Release cursor resources"]
```

### Side-by-Side: ISO SQL/PSM vs. PostgreSQL PL/pgSQL

| Step | ISO SQL/PSM (Ch 2 Slides 48–52, 58) | PostgreSQL PL/pgSQL Explicit Cursor (TP 3) |
| :--- | :--- | :--- |
| **1. Declare** | `DECLARE c CURSOR FOR SELECT ...;` | `c CURSOR FOR SELECT ...;` inside `DECLARE` |
| **End-of-Data** | `DECLARE v_done BOOLEAN DEFAULT FALSE;`<br>`DECLARE CONTINUE HANDLER FOR NOT FOUND SET v_done = TRUE;` | Check built-in **`NOT FOUND`** immediately after `FETCH`: `EXIT WHEN NOT FOUND;` |
| **2. Open** | `OPEN c;` | `OPEN c;` |
| **3. Fetch & Test** | `read_loop: LOOP`<br>&nbsp;&nbsp;`FETCH c INTO v1, v2;`<br>&nbsp;&nbsp;`IF v_done THEN LEAVE read_loop; END IF;` | `LOOP`<br>&nbsp;&nbsp;`FETCH c INTO v1, v2;`<br>&nbsp;&nbsp;`EXIT WHEN NOT FOUND;` |
| **4–6. Close** | `END LOOP; CLOSE c;` | `END LOOP; CLOSE c;` |

### Tracing the Loop & Five Common Cursor Errors (Ch 2 Slides 52–53)
An **extra `FETCH` after the final row** is how the loop discovers the result set is exhausted (`v_done = TRUE` / `NOT FOUND`).
1. **Forgetting `OPEN`:** `FETCH` fails because the cursor is not active.
2. **Forgetting end-of-data handling (or testing *after* processing):** Never assume variable values are valid after a failed `FETCH`! Checking `v_done` / `NOT FOUND` *after* processing duplicates the last row's calculation or crashes.
3. **Wrong number or order of target variables:** `SELECT` columns must align positionally and by type with `FETCH ... INTO` variables (use `table.col%TYPE`).
4. **Forgetting `CLOSE`:** Keeps memory/cursor resources allocated longer than necessary.
5. **Long-running cursor loops:** Prolong transactions and hold locks or MVCC snapshots.

## 3. Cursor `FOR` Loops, Types, Attributes & Row Locking

### PostgreSQL Cursor `FOR` Loop (TP 3 Part I.1.2 & Ex 6–7, 15)
Automatically declares an implicit cursor, opens it, fetches each row into `rec RECORD`, exits at end-of-data, and closes it:
```sql
DO $$
DECLARE rec RECORD;
BEGIN
    FOR rec IN SELECT teacher_id, last_name, first_name FROM teacher ORDER BY teacher_id LOOP
        RAISE NOTICE 'Teacher ID: %, Name: % %', rec.teacher_id, rec.first_name, rec.last_name;
    END LOOP;
END $$;
```

### Cursor Types, Attributes & `FOR UPDATE` Locking (Ch 2 Slide 55 & `05 PLSQL`)
- **Forward-only** (default, single direction) vs. **Scrollable** (`SCROLL`, moves backward/jumps) vs. **Read-only** (retrieving data).
- **Implicit Cursor Attributes (Oracle/PLSQL):** `SQL%FOUND`, `SQL%NOTFOUND`, `SQL%ROWCOUNT`; **Explicit:** `emp_cursor%ISOPEN`, `%FOUND`, `%NOTFOUND`, `%ROWCOUNT`.
- **Pessimistic Row Locking (`FOR UPDATE`):** Adding `FOR UPDATE` to `DECLARE c CURSOR FOR SELECT ... FOR UPDATE;` places **Exclusive (X) locks** on selected rows on `OPEN` until `COMMIT`/`ROLLBACK`. *(Oracle uses `UPDATE ... WHERE CURRENT OF c;`; PostgreSQL/MySQL update using the fetched primary key `WHERE teacher_id = v_id;`.)*

```sql
-- TP 3 Ex 1: Display Teachers Using an Explicit Cursor
DO $$
DECLARE
    v_id teacher.teacher_id%TYPE;
    v_last_name teacher.last_name%TYPE;
    v_first_name teacher.first_name%TYPE;
    c_teachers CURSOR FOR SELECT teacher_id, last_name, first_name FROM teacher ORDER BY teacher_id;
BEGIN
    OPEN c_teachers;
    LOOP
        FETCH c_teachers INTO v_id, v_last_name, v_first_name;
        EXIT WHEN NOT FOUND;
        RAISE NOTICE 'Teacher ID: %, Name: % %', v_id, v_first_name, v_last_name;
    END LOOP;
    CLOSE c_teachers;
END $$;

-- TP 3 Ex 2: Classify Teachers According to Their Salaries
DO $$
DECLARE
    v_id teacher.teacher_id%TYPE;
    v_last_name teacher.last_name%TYPE;
    v_salary teacher.salary%TYPE;
    v_category VARCHAR(30);
    c_teachers CURSOR FOR SELECT teacher_id, last_name, salary FROM teacher ORDER BY teacher_id;
BEGIN
    OPEN c_teachers;
    LOOP
        FETCH c_teachers INTO v_id, v_last_name, v_salary;
        EXIT WHEN NOT FOUND;
        IF v_salary IS NULL THEN v_category := 'Unknown salary';
        ELSIF v_salary >= 70000 THEN v_category := 'High salary';
        ELSIF v_salary >= 50000 THEN v_category := 'Medium salary';
        ELSE v_category := 'Low salary';
        END IF;
        RAISE NOTICE 'Teacher: %, Salary: %, Category: %', v_last_name, v_salary, v_category;
    END LOOP;
    CLOSE c_teachers;
END $$;

-- TP 3 Ex 3: Count Teachers Using a Cursor (+ Set Equivalent: SELECT COUNT(*) FROM teacher;)
DO $$
DECLARE
    v_teacher_id teacher.teacher_id%TYPE;
    v_count INTEGER := 0;
    c_teachers CURSOR FOR SELECT teacher_id FROM teacher;
BEGIN
    OPEN c_teachers;
    LOOP
        FETCH c_teachers INTO v_teacher_id;
        EXIT WHEN NOT FOUND;
        v_count := v_count + 1;
    END LOOP;
    CLOSE c_teachers;
    RAISE NOTICE 'Total number of teachers: %', v_count;
END $$;

-- TP 3 Ex 4: Calculate Total Salary (Ignoring NULLs!)
DO $$
DECLARE
    v_salary teacher.salary%TYPE;
    v_total NUMERIC := 0;
    c_salaries CURSOR FOR SELECT salary FROM teacher;
BEGIN
    OPEN c_salaries;
    LOOP
        FETCH c_salaries INTO v_salary;
        EXIT WHEN NOT FOUND;
        IF v_salary IS NOT NULL THEN
            v_total := v_total + v_salary;
        END IF;
    END LOOP;
    CLOSE c_salaries;
    RAISE NOTICE 'Total salary: %', v_total;
END $$;

-- TP 3 Ex 5: Display Teachers and Their Departments (Cursor with Join)
DO $$
DECLARE
    v_id teacher.teacher_id%TYPE;

        SELECT t.teacher_id, t.last_name, d.department_name

BEGIN

END $$;

-- TP 3 Ex 7: Identify Teachers Eligible for a Bonus (Cursor FOR Loop)
DO $$
DECLARE rec RECORD;
BEGIN
    FOR rec IN SELECT teacher_id, last_name, salary FROM teacher ORDER BY teacher_id LOOP
        IF rec.salary IS NULL THEN
            RAISE NOTICE '%: Salary unavailable', rec.last_name;
        ELSIF rec.salary < 60000 THEN

-- TP 3 Ex 15: Combined Cursor Processing (Counts, Total & Non-NULL Average)
DO $$
DECLARE
    rec RECORD;
    v_total_teachers INTEGER := 0;
    v_paid_teachers INTEGER := 0;
    v_total_salary NUMERIC := 0;
    v_average_salary NUMERIC;
BEGIN
    FOR rec IN SELECT teacher_id, last_name, salary FROM teacher LOOP
        v_total_teachers := v_total_teachers + 1;
        IF rec.salary IS NOT NULL THEN
            v_paid_teachers := v_paid_teachers + 1;
            v_total_salary := v_total_salary + rec.salary;
        END IF;
    END LOOP;

    IF v_paid_teachers > 0 THEN
        v_average_salary := v_total_salary / v_paid_teachers;
    ELSE
        v_average_salary := NULL;
    END IF;

    RAISE NOTICE 'Total teachers: %', v_total_teachers;
    RAISE NOTICE 'Teachers with a salary: %', v_paid_teachers;
    RAISE NOTICE 'Total salary: %', v_total_salary;
    RAISE NOTICE 'Average salary: %', v_average_salary;
END $$;
```

## 5. Worked Solutions: TD 3 Part I (Exercises 1*–6)

### TD 3 Ex 1* (Individual Raises by Dept ID) & Ex 6 (Cursor vs. Set-Based SQL)
Rules: Dept 1 (`5%`), Dept 2 (`7%`), Dept 3 (`6%`), Dept 4 (`4%`), Others (`3%`); `NULL` salary ineligible.
```sql
-- SQL/PSM Solution for TD 3 Ex 1*
BEGIN ATOMIC
    DECLARE v_done BOOLEAN DEFAULT FALSE;
    DECLARE v_id INTEGER;
    DECLARE v_salary DECIMAL(10,2);
    DECLARE v_dept INTEGER;
    DECLARE v_rate DECIMAL(5,2);
    DECLARE v_raise DECIMAL(10,2);
    DECLARE v_new_salary DECIMAL(10,2);

    DECLARE c_teachers CURSOR FOR SELECT teacher_id, salary, department_id FROM teacher;
    DECLARE CONTINUE HANDLER FOR NOT FOUND SET v_done = TRUE;

    OPEN c_teachers;
    read_loop: LOOP
        FETCH c_teachers INTO v_id, v_salary, v_dept;
        IF v_done THEN LEAVE read_loop; END IF;

        IF v_salary IS NULL THEN
            SELECT v_id AS teacher_id, 'Ineligible (NULL salary)' AS status;
        ELSE
            CASE v_dept
                WHEN 1 THEN SET v_rate = 5;
                WHEN 2 THEN SET v_rate = 7;
                WHEN 3 THEN SET v_rate = 6;
                WHEN 4 THEN SET v_rate = 4;
                ELSE SET v_rate = 3;
            END CASE;
            SET v_raise = v_salary * (v_rate / 100.0);
            SET v_new_salary = v_salary + v_raise;
            SELECT v_id AS teacher_id, v_salary AS current_salary, v_raise AS raise_amount, v_new_salary AS new_salary;
        END IF;
    END LOOP;
    CLOSE c_teachers;
END;
```
**TD 3 Ex 6 Comparison — Single Set-Based `UPDATE` Equivalent:**
```sql
UPDATE teacher
SET salary = salary * (1 + (
    CASE department_id
        WHEN 1 THEN 0.05
        WHEN 2 THEN 0.07
        WHEN 3 THEN 0.06
        WHEN 4 THEN 0.04
        ELSE 0.03
    END
))
WHERE salary IS NOT NULL;
```
- **Which is preferable for bulk updates?** The **single set-based `UPDATE`**—one set scan, optimized execution plan, minimal lock duration, no cursor overhead.
- **When is a cursor more appropriate?** When each row requires custom row-by-row diagnostic printing, calling an external stored procedure/API, or sequential stateful logic (e.g., allocating raises sequentially until a global department budget runs out).

### TD 3 Ex 2, Ex 3, Ex 4, Ex 5 (PL/pgSQL / SQL-PSM Ready Implementations)
```sql
-- TD 3 Ex 2: Compare Teachers' Salaries with Department Average
DO $$
DECLARE
    v_name VARCHAR(101);
    v_salary teacher.salary%TYPE;
    v_dept department.department_name%TYPE;
    v_dept_avg NUMERIC;
    v_rec_msg VARCHAR(30);
    c_comp CURSOR FOR
        SELECT t.first_name || ' ' || t.last_name, t.salary, d.department_name,
               (SELECT AVG(t2.salary) FROM teacher t2 WHERE t2.department_id = t.department_id)
        FROM teacher t LEFT JOIN department d ON t.department_id = d.department_id
        ORDER BY t.teacher_id;
BEGIN
    OPEN c_comp;
    LOOP
        FETCH c_comp INTO v_name, v_salary, v_dept, v_dept_avg;
        EXIT WHEN NOT FOUND;
        IF v_salary IS NULL THEN v_rec_msg := 'Salary unknown';
        ELSIF v_salary < v_dept_avg THEN v_rec_msg := 'Raise recommended';
        ELSE v_rec_msg := 'Salary acceptable';
        END IF;
        RAISE NOTICE 'Teacher: %, Salary: %, Dept: %, Status: %', v_name, v_salary, v_dept, v_rec_msg;
    END LOOP;
    CLOSE c_comp;
END $$;
```
- **TD 3 Ex 3 (Classify Teachers):** Note boundary detail—TD 3 writes `< 50000` Low, `between 50000 and 70000` Medium, `> 70000` High, `NULL` Unknown (`IF v_salary IS NULL ... ELSIF v_salary < 50000 ... ELSIF v_salary <= 70000 ... ELSE 'High salary'`), whereas TP 2 / TD 2 classify `>= 70000` as High (`< 70000` Medium). Always match the wording of the active question!
- **TD 3 Ex 4 (Classify Students by Age):** `IF v_age IS NULL` $\to$ `'Age unknown'`, `ELSIF v_age < 20` $\to$ `'Young student'`, `ELSIF v_age <= 25` $\to$ `'Regular student'`, `ELSE` $\to$ `'Mature student'`.

## 6. Legacy Airline TD 4 Cursors (`total_hvol_AF` & `Gestion_Pilotes`)

Preserved from `05 PLSQL` (MySQL syntax with `DECLARE CONTINUE HANDLER FOR NOT FOUND` and `FOR UPDATE` row locking):
- **`total_hvol_AF()`:** Sums `nbHVol` for `comp = 'AF'` row-by-row. Notice **declaration order in MySQL is strict**: (1) Local variables $\to$ (2) Cursors $\to$ (3) Handlers! Tracing 2 rows (`1200.00`, `850.50`): Fetch 1 $\to$ `v_total = 1200.00`; Fetch 2 $\to$ `v_total = 2050.50`; Fetch 3 fails $\to$ `NOT FOUND` sets `v_done = TRUE` $\to$ `IF v_done THEN LEAVE` prevents adding `850.50` twice!
- **`Gestion_Pilotes()` (Cursor with `FOR UPDATE` + Transaction Atomicity):**
```sql
DELIMITER $$
CREATE PROCEDURE Gestion_Pilotes()
BEGIN
    DECLARE v_done INT DEFAULT FALSE;
    DECLARE v_error_flag INT DEFAULT FALSE;
    DECLARE v_brevet VARCHAR(6);
    DECLARE v_comp VARCHAR(4);

    DECLARE cur_pilotes CURSOR FOR SELECT brevet, comp FROM Pilote FOR UPDATE;
    DECLARE CONTINUE HANDLER FOR NOT FOUND SET v_done = TRUE;
    DECLARE CONTINUE HANDLER FOR SQLEXCEPTION SET v_error_flag = TRUE;

    START TRANSACTION;
    OPEN cur_pilotes;
    pilot_loop: LOOP
        FETCH cur_pilotes INTO v_brevet, v_comp;
        IF v_done OR v_error_flag THEN LEAVE pilot_loop; END IF;

        IF v_comp = 'AF' THEN
            UPDATE Pilote SET nbHVol = nbHVol + 100 WHERE brevet = v_brevet;
        ELSEIF v_comp = 'SING' THEN
            UPDATE Pilote SET nbHVol = nbHVol - 100 WHERE brevet = v_brevet;
        ELSE
            DELETE FROM Pilote WHERE brevet = v_brevet;
        END IF;
    END LOOP pilot_loop;
    CLOSE cur_pilotes;

    IF v_error_flag THEN ROLLBACK; ELSE COMMIT; END IF;
END $$
DELIMITER ;
```

# Procedural SQL (SQL/PSM & PL/pgSQL), Control Flow & Exceptions

This note integrates **Chapter 2 Part II (Slides 16–33)**, **TP 2 (Part II.4–7, Exercises 4–7, Part IV Q12–14)**, **TD 2 (Exercises 3*, 4, 6, 7*, 8)**, and foundational procedural SQL mechanics (delimiters, variable scoping, control flow, and exception handling across **ISO SQL/PSM**, **PostgreSQL PL/pgSQL**, **MySQL**, and **Oracle PL/SQL**).

---

## 1. Declarative SQL vs. Procedural Programming (Ch 2 Slides 16–18)

Plain SQL (`SELECT`, `INSERT`, `UPDATE`, `DELETE`) is **declarative**: you specify *what* data you want, and the optimizer decides *how* to fetch it. While inline `CASE` expressions exist inside queries, plain SQL **cannot** express loops, program-flow `IF/ELSE` branching, local state variables, custom error recovery, or multi-step server algorithms.

**Why move from Views to Server-Side Programming?** Views only *present* data; when the university requires *"Every salary increase must be controlled, calculated according to a rate, and automatically recorded in a history"*, we need server-side **procedural SQL** running inside the DBMS engine (avoiding client round-trips):
1. **ISO/IEC SQL/PSM (SQL Persistent Stored Modules):** Standardized procedural SQL taught in lectures and conceptual TDs (**Ch 2, TD 2, TD 3**).
2. **PL/pgSQL:** **PostgreSQL's** procedural language used in labs (**TP 2, TP 3, pgAdmin 4**).
3. **Oracle PL/SQL & MySQL Procedural SQL:** Vendor dialects encountered in historical BDA exams and TD 4 (**PL/SQL** is Oracle-exclusive, Ada-style with packages; **MySQL** has its own procedural SQL/PSM-like dialect—never confuse the two!).

---

## 2. Dialect Comparison & Delimiter Parsing Mechanics (TD 2 Ex 6)

Because **TD 2 Ex 6** specifically asks *"which parts of the syntax may depend on the DBMS"*, compare all four dialects side-by-side:

| Feature | ISO SQL/PSM (Lectures / TD 2–3) | PostgreSQL PL/pgSQL (TP 2–3 / pgAdmin) | MySQL Procedural (TD 4 / Legacy) | Oracle PL/SQL (Legacy) |
| :--- | :--- | :--- | :--- | :--- |
| **Anonymous Block** | `BEGIN ATOMIC ... END` | `DO $$ DECLARE ... BEGIN ... END $$;` | Inside `CREATE PROCEDURE` | `DECLARE ... BEGIN ... END; /` |
| **Assignment** | `SET v = val;` | `v := val;` (also `=`) | `SET v = val;` | `v := val;` |
| **Conditionals** | `IF ... ELSEIF ... ELSE ... END IF;` | `IF ... ELSIF ... ELSE ... END IF;` | `IF ... ELSEIF ... ELSE ... END IF;` | `IF ... ELSIF ... ELSE ... END IF;` |
| **Output / Print** | `SELECT v;` | `RAISE NOTICE 'Msg: %', v;` | `SELECT v;` | `DBMS_OUTPUT.PUT_LINE(v);` |
| **Missing Row** | `DECLARE CONTINUE HANDLER FOR NOT FOUND ...` | `IF NOT FOUND` (or `SELECT INTO STRICT` $\to$ `no_data_found`) | `DECLARE CONTINUE HANDLER FOR NOT FOUND ...` | `EXCEPTION WHEN NO_DATA_FOUND` |
| **Error Handler** | `DECLARE EXIT HANDLER FOR SQL EXCEPTION ...` | `BEGIN ... EXCEPTION WHEN division_by_zero THEN ... WHEN OTHERS THEN ... SQLERRM ... END;` | `DECLARE EXIT\|CONTINUE HANDLER FOR SQLEXCEPTION ...` | `EXCEPTION WHEN ZERO_DIVIDE THEN ... WHEN OTHERS THEN ...` |
| **Raise Error** | `SIGNAL SQLSTATE ...` | `RAISE EXCEPTION 'msg';` | `SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = '...';` | `RAISE_APPLICATION_ERROR(-20001, '...');` |

### Why Delimiters Matter (`DELIMITER //` in MySQL vs. `$$` Dollar-Quoting in PostgreSQL)
In interactive clients, `;` terminates a single SQL statement. Inside a procedure/function, multiple internal statements end with `;`:
- **MySQL CLI Conflict:** Sending `CREATE PROCEDURE ... BEGIN INSERT ...; UPDATE ...; END;` with `;` active causes the client to truncate at the first `;` and crash with syntax error `1064`. Therefore, MySQL scripts use the **client-side directive** `DELIMITER // ... END // DELIMITER ;` (note: `DELIMITER` is a client tool directive, not SQL!).
- **PostgreSQL Solution (`$$` Dollar-Quoting):** PostgreSQL wraps procedural bodies inside `AS $$ ... $$;` (or `DO $$ ... $$;`), so internal `;` characters and single quotes `'...'` inside the body need no escaping or client delimiter switches!

---

## 3. Variables, Scopes & `SELECT ... INTO` Mechanics

### PostgreSQL Variables (TP 2 Part II.4 & TP 3)
- Declared between `DECLARE` and `BEGIN` inside `DO $$ ... $$;` or a function/procedure.
- **Anchored type (`%TYPE`):** `v_salary teacher.salary%TYPE;` automatically inherits the column's exact type (`NUMERIC(10,2)`), remaining resilient if the column schema widens later.
- **Generic row (`RECORD`):** `rec RECORD;` holds any row structure dynamically (used in cursor `FOR` loops).
- **`SELECT ... INTO` Rules:**
  - In PostgreSQL PL/pgSQL, `SELECT salary INTO v_salary FROM teacher WHERE teacher_id = 101;` stores the retrieved column into `v_salary` and updates the automatic boolean **`FOUND`** (`TRUE` if $\ge 1$ row, `FALSE` if 0 rows).
  - Without `STRICT`, 0 rows leaves `v_salary = NULL` and sets `FOUND = FALSE`; multiple rows assign only the first row unless `STRICT` is specified (`SELECT ... INTO STRICT` enforces exactly 1 row, raising `no_data_found` or `too_many_rows`!).
  - *(In MySQL/Oracle, `SELECT ... INTO` returning 0 rows raises `NOT FOUND` / `NO_DATA_FOUND`, and >1 row raises `TOO_MANY_ROWS` `21000`.)*

### Legacy MySQL Variable Scopes (For Reading TD 4 & Past Exams)
| Scope | Syntax | Lifespan | Typing |
| :--- | :--- | :--- | :--- |
| **Local Variable** | `DECLARE v INT DEFAULT 0;` | Current `BEGIN...END` block only (stack-allocated) | Strongly & statically typed |
| **Session Variable** | `SET @v = 10;` | Entire connection session (no `DECLARE` needed) | Weakly & dynamically typed |
| **System Variable** | `@@GLOBAL.var` / `@@SESSION.var` | Server/session configuration | Strongly typed |

---

## 4. Conditionals, `NULL` vs. Missing Row & Loops (TP 2 Ex 4–6, TD 2 Ex 3*–4)

### Critical Rules for `IF / ELSIF`, `CASE`, `NULL`, and `FOUND` (TP 2 Part II.5 & Ex 4–5)
1. **PL/pgSQL spelling:** Always write **`ELSIF`** (never `ELSE IF` or `ELSEIF`!).
2. **Test `IS NULL` explicitly:** Because `NULL >= 70000` evaluates to `UNKNOWN` (not `TRUE`), omitting `IS NULL` lets `NULL` fall silently into the `ELSE` branch (`'Low'`)!
3. **Distinguish a `NULL` attribute from a missing row (TP 2 Ex 4 & TD 2 Ex 4):**
   - Teacher `109` (`Khelifi Nora`) **exists** with `salary = NULL` (`FOUND = TRUE`, `v_salary IS NULL`).
   - Teacher `999` **does not exist** (`FOUND = FALSE`). Treating these identically corrupts reports or hides data-integrity gaps.
4. **Check `FOUND` immediately (TP 2 Ex 5 Correction Note):** Check `IF NOT FOUND` **immediately after `SELECT INTO`**, before any other SQL statement overwrites `FOUND`!

```sql
-- TP 2 Ex 4 & 5: Robust classification (IF/ELSIF and CASE)
DO $$
DECLARE
    v_salary NUMERIC(10,2);
    v_category VARCHAR(20);
BEGIN
    SELECT salary INTO v_salary FROM teacher WHERE teacher_id = 109;

    IF NOT FOUND THEN
        v_category := 'Teacher not found';
    ELSIF v_salary IS NULL THEN
        v_category := 'Unknown';
    ELSIF v_salary >= 70000 THEN
        v_category := 'High';
    ELSIF v_salary >= 50000 THEN
        v_category := 'Medium';
    ELSE
        v_category := 'Low';
    END IF;

    RAISE NOTICE 'Salary: %, category: %', v_salary, v_category;
END $$;
```
*(In `CASE` expression form: `v_category := CASE WHEN NOT FOUND THEN 'Teacher not found' WHEN v_salary IS NULL THEN 'Unknown' WHEN v_salary >= 70000 THEN 'High' WHEN v_salary >= 50000 THEN 'Medium' ELSE 'Low' END;` — valid only when evaluated right after `SELECT INTO`.)*

### TD 2 Ex 4: Processing Students 1..10 & Handling `NULL` `class_id` vs. Non-Existent Student
```sql
DO $$
DECLARE
    i INTEGER;
    v_class_id student.class_id%TYPE;
BEGIN
    FOR i IN 1..10 LOOP
        SELECT class_id INTO v_class_id FROM student WHERE student_id = i;
        IF NOT FOUND THEN
            RAISE NOTICE 'Student % does not exist.', i;
        ELSIF v_class_id IS NULL THEN
            RAISE NOTICE 'Student % exists, but class_id is NULL (unassigned).', i;
        ELSE
            RAISE NOTICE 'Student % is in class %.', i, v_class_id;
        END IF;
    END LOOP;
END $$;
```
*Why they must not be treated as equivalent:* Student `8` (`Farah Ines`) is a valid enrolled student awaiting class assignment (`class_id IS NULL`), whereas ID `11` does not represent any student at all—treating both as "unassigned" or both as "missing" would either drop real students or fabricate nonexistent ones.

### Loop Constructs & `CONTINUE WHEN` (Ch 2 Slides 28–32, TP 2 Ex 6, TD 2 Ex 3*)
- **PostgreSQL PL/pgSQL:**
  - `FOR i IN 1..5 LOOP ... END LOOP;` (known integer range; `REVERSE` for descending).
  - `WHILE condition LOOP ... END LOOP;` (pre-tested; forgetting `i := i + 1;` causes an infinite loop!).
  - `LOOP ... EXIT WHEN condition; ... END LOOP;` (infinite until `EXIT` / `EXIT WHEN`).
  - `CONTINUE` / `CONTINUE WHEN cond;` skips to the next iteration—**always increment before `CONTINUE WHEN`** in `WHILE`/`LOOP`!
- **ISO SQL/PSM & MySQL additions:** `REPEAT ... UNTIL cond END REPEAT;` (post-tested—executes **at least once**!), `label: LOOP ... LEAVE label; ... ITERATE label; END LOOP;`.

```sql
-- TD 2 Ex 3* / TP 2 Ex 6 Task 1: Iterate department IDs 1..5 + skipping evens safely
DO $$
DECLARE i INTEGER := 0;
BEGIN
    WHILE i < 5 LOOP
        i := i + 1;
        CONTINUE WHEN i % 2 = 0; -- safe because increment already occurred!
        RAISE NOTICE 'Department ID (odd): %', i;
    END LOOP;
END $$;
```

## 5. Exception Handling, `NOT FOUND` Handlers & Validation (TP 2 Ex 7, TD 2 Ex 6–8)

### Why Handle Exceptions & How PostgreSQL Rolls Back Protected Blocks (TP 2 Part II.7)
Runtime errors arise from division by zero, constraint violations (`23000`/`23505`), missing data (`02000`), or business logic checks (`45000`).
> [!IMPORTANT] Crucial PostgreSQL `EXCEPTION` Rollback Rule (TP 2 Part II.7)
> In PL/pgSQL, a `BEGIN ... EXCEPTION ... END;` block creates an implicit subtransaction. **When an exception is caught, PostgreSQL rolls back all database changes made inside that protected block back to its entry state before executing the handler**, while allowing outer execution after `END;` to continue!
> Moreover, **specific handlers (`WHEN division_by_zero`) are strongly preferred over `WHEN OTHERS`** because catching everything can silently hide programming typos or unrelated constraint bugs.

### Worked Solutions: TP 2 Ex 7, TD 2 Ex 6, TD 2 Ex 7*, TD 2 Ex 8

**TP 2 Ex 7 / TD 2 Ex 6 — Division by Zero (PL/pgSQL vs. SQL/PSM):**
```sql
-- PostgreSQL PL/pgSQL (TP 2 Ex 7)
DO $$
DECLARE v_result NUMERIC;
BEGIN
    BEGIN
        v_result := 100 / 0; -- Change to 100 / 4 -> prints Result: 25
        RAISE NOTICE 'Result: %', v_result;
    EXCEPTION
        WHEN division_by_zero THEN
            RAISE NOTICE 'Error: division by zero is not allowed.';
        WHEN OTHERS THEN
            RAISE NOTICE 'Unexpected error: %', SQLERRM;
    END;
    RAISE NOTICE 'Execution continues after the handled inner block.';
END $$;
```
*(In ISO SQL/PSM, Ch 2 Slide 33 uses `DECLARE EXIT HANDLER FOR SQL EXCEPTION BEGIN ... END;` inside `BEGIN ATOMIC ... END;`, where block delimiters `BEGIN ATOMIC`, `DECLARE ... HANDLER`, `EXCEPTION WHEN`, `RAISE NOTICE`, and `SQLERRM` are all DBMS-dependent syntax elements!)*

**TD 2 Ex 7* — Handling Missing Student 100:**
- If student `100` exists, display their retrieved attributes normally; if not, emit an explicit not-found message/status rather than proceeding with `NULL`/uninitialized variables (explicit handling prevents silent garbage outputs or false updates).
```sql
-- ISO SQL/PSM style (TD 2 Ex 7*)
BEGIN ATOMIC
    DECLARE v_last_name VARCHAR(50);
    DECLARE v_first_name VARCHAR(50);
    DECLARE v_not_found BOOLEAN DEFAULT FALSE;
    DECLARE CONTINUE HANDLER FOR NOT FOUND SET v_not_found = TRUE;

    SELECT last_name, first_name INTO v_last_name, v_first_name
    FROM student WHERE student_id = 100;

    IF v_not_found THEN
        SELECT 'Student 100 does not exist.' AS status;
    ELSE
        SELECT v_last_name, v_first_name;
    END IF;
END;
```
*(In PostgreSQL PL/pgSQL, either use `SELECT ... INTO` followed by `IF NOT FOUND THEN RAISE NOTICE ...` or `SELECT ... INTO STRICT` inside a `BEGIN ... EXCEPTION WHEN no_data_found THEN ... END;` block!)*

**TD 2 Ex 8 — Controlled 10% Salary Update for Teacher 101:**
Validate *before* executing `UPDATE` so invalid/NULL rows are never modified, error causes are clearly distinguished (`teacher missing` vs. `NULL salary`), and locks/audit triggers are never triggered on bad states:
```sql
DO $$
DECLARE v_salary teacher.salary%TYPE;
BEGIN
    SELECT salary INTO v_salary FROM teacher WHERE teacher_id = 101;

    IF NOT FOUND THEN
        RAISE EXCEPTION 'Update aborted: teacher 101 does not exist.';
    ELSIF v_salary IS NULL THEN
        RAISE EXCEPTION 'Update aborted: teacher 101 has a NULL salary.';
    ELSE
        UPDATE teacher SET salary = salary * 1.10 WHERE teacher_id = 101;
        RAISE NOTICE 'Teacher 101 salary increased by 10%%.';
    END IF;
END $$;
```
*(Wrap in `BEGIN; ... ROLLBACK;` in lab sessions to keep the TP 1 baseline intact.)*

### Legacy MySQL Error Codes (`SQLSTATE`) & Transaction Handler Pattern
Standardized `SQLSTATE` classes: `00000` (Success), `01000` (Warning/Truncation), `02000` (`NOT FOUND`), `23000` (Integrity constraint violation), `45000` (User-defined exception via `SIGNAL`). In MySQL procedures, declare variables $\to$ declare handlers (`DECLARE CONTINUE HANDLER FOR SQLEXCEPTION SET exit_flag = 1;`) $\to$ run `START TRANSACTION` $\to$ `IF exit_flag = 1 THEN ROLLBACK; ELSE COMMIT; END IF;` (or `RESIGNAL;` inside an `EXIT HANDLER` to log and rethrow).

## 6. Review Questions Summary (TP 2 Part IV Q12–Q14)
- **Q12 (`DO` block vs. Stored Function vs. Stored Procedure):** A `DO $$ ... $$;` block executes one-time anonymous procedural code without storing anything in the database; a **stored function** is saved permanently, returns a value, and can be embedded in `SELECT` expressions; a **stored procedure** is saved permanently, performs actions without requiring a return value, and is invoked with `CALL`.
- **Q13 (Why test `NULL` explicitly?):** Relational comparisons like `salary >= 70000` or `salary <> 50000` evaluate to `UNKNOWN` when `salary` is `NULL`, causing `IF`/`ELSIF` conditions to fall unexpectedly into `ELSE`. Always check `IS NULL` / `IS NOT NULL` (or `IS DISTINCT FROM`) first.
- **Q14 (`EXCEPTION`, `WHEN`, `RAISE NOTICE`, `RAISE EXCEPTION`):** `EXCEPTION` opens the error-handling section of a block; `WHEN` selects the specific SQLSTATE/condition to catch; `RAISE NOTICE` prints an informational message to the Messages tab without stopping execution; `RAISE EXCEPTION` deliberately triggers an error, aborting normal execution and rolling back the block unless caught by an enclosing handler.

# Stored Functions, Stored Procedures & Dynamic SQL

This note integrates **Chapter 2 Slides 34–42**, **TP 2 (Exercises 8–9, Ex 12 Tasks 5–7, Part IV Q12, Q18, Q19)**, **TD 2 (Exercises 9*–15)**, **Dynamic SQL (`PREPARE`/`EXECUTE`, `EXECUTE IMMEDIATE`)**, and **Legacy Airline TD 4 Stored Routines** (`EffectifsHeure`, `PlusExperimente`, `factorielle`).

## 1. Stored Functions vs. Stored Procedures

```mermaid
flowchart LR
    subgraph Stored Function
        FI["Input Parameters"] --> FL["Computation / Read Query"] --> FR["RETURNS single value / set<br/>Used inside SELECT / WHERE"]
    end
    subgraph Stored Procedure
        PI["IN / OUT / INOUT Parameters"] --> PL["Business Action / DML / Tx Control"] --> PR["Invoked via CALL proc(...)<br/>No RETURNS required"]
    end
```

| Property | Stored Function | Stored Procedure |
| :--- | :--- | :--- |
| **Primary Purpose** | Calculate and return a result | Perform an action (modify data, run multi-step workflows) |
| **Return Clause** | **Must** declare `RETURNS type` and execute `RETURN val;` | **No `RETURNS` clause** (outputs via `OUT`/`INOUT` params or result sets in MySQL) |
| **Invocation** | Inside SQL expressions (`SELECT number_of_teachers(1);`) | Standalone statement (`CALL increase_department_salaries(1, 5);`) |
| **DML / Transactions** | Avoid/restrict side effects (forbidden from `COMMIT`/`ROLLBACK`) | Can execute `INSERT`/`UPDATE`/`DELETE` and transaction control (`COMMIT`/`ROLLBACK` in PostgreSQL/MySQL) |
| **Benefits** | Reuse logic across queries, encapsulate calculations, centralize formulas | Centralize business validation & safe multi-step updates |

### Determinism & MySQL Replication Hazard (Legacy Note)
In MySQL with Statement-Based Binary Logging (`binlog`), calling a non-deterministic function (`NOW()`, `RAND()`) inside an `INSERT`/`UPDATE` can write `0.45` on the Master and `0.82` when replayed on a Replica (`Error 1418`). Always declare functions with `DETERMINISTIC`, `NO SQL`, or `READS SQL DATA` in MySQL (or set `SET GLOBAL log_bin_trust_function_creators = 1;` only under Row-Based Replication). PostgreSQL supports `IMMUTABLE` / `STABLE` / `VOLATILE` optimization markers instead.

## 2. Worked Stored Functions (Ch 2 Slides 34–39, TP 2 Ex 8, TD 2 Ex 9*–12)

### A. Counting Teachers by Department (`number_of_teachers` / `count_teachers_by_department`)
**Ch 2 Slides 38–39, TP 2 Ex 8 Task 1, TD 2 Ex 9* & Ex 12 Task 6:**
```sql
-- ISO SQL/PSM (Ch 2 Slide 38):
-- CREATE FUNCTION number_of_teachers(p_department INTEGER) RETURNS INTEGER
-- BEGIN ATOMIC DECLARE nb INTEGER; SELECT COUNT(*) INTO nb FROM teacher WHERE department_id = p_department; RETURN nb; END;

-- PostgreSQL PL/pgSQL (TP 2 Ex 8 Task 1 / TD 2 Ex 9*):
CREATE OR REPLACE FUNCTION number_of_teachers(p_department INTEGER)
RETURNS INTEGER
LANGUAGE plpgsql
AS $$
DECLARE
    nb INTEGER;
BEGIN
    SELECT COUNT(*) INTO nb
    FROM teacher
    WHERE department_id = p_department;

    RETURN nb;
END;
$$;

-- Test single call and per-department listing (also solves TP 2 Ex 12 Task 6 via count_teachers_by_department):
SELECT number_of_teachers(1); -- returns 4
SELECT number_of_teachers(5); -- returns 0

SELECT department_id, department_name, number_of_teachers(department_id) AS number_of_teachers
FROM department
ORDER BY department_id;
-- Expected: (1, Informatique, 4), (2, Mathématiques, 2), (3, Électronique, 2), (4, Physique, 1), (5, Chimie, 0)
```
- **Why does department 5 (`Chimie`) appear with `0` even though it has no teachers (TD 2 Ex 9* & TP 2 Ex 8)?**
  1. The outer query runs `FROM department`, so every row in `department` (including department `5`) is visited and passed into `number_of_teachers(department_id)`.
  2. Inside the function, `COUNT(*)` over 0 matching rows in `teacher` evaluates to **`0`**, **not `NULL`**. (`RETURN` sends that result back to the caller and terminates the function.)

### B. Average Salary by Department (`average_salary` — TD 2 Ex 10)
```sql
CREATE OR REPLACE FUNCTION average_salary(p_department INTEGER)
RETURNS NUMERIC(10,2)
LANGUAGE plpgsql
AS $$
DECLARE
    v_avg NUMERIC(10,2);
BEGIN
    SELECT AVG(salary) INTO v_avg
    FROM teacher
    WHERE department_id = p_department;

    RETURN v_avg;
END;
$$;

SELECT average_salary(1); -- 68333.33 (averages 75000, 62000, 68000; skips teacher 109's NULL)
SELECT average_salary(5); -- NULL
```
- **Why does `average_salary(5)` return `NULL` while `number_of_teachers(5)` returns `0`?**
  When a department has 0 teachers (or when all its teachers have `NULL` salary), `COUNT(*)` is `0`, whereas **`AVG(salary)` returns `NULL`** because dividing by 0 non-null elements is mathematically undefined.

### C. Salary Classification (`salary_category` — TP 2 Ex 8 Tasks 2–3, Ex 12 Task 5, TD 2 Ex 11)
Notice the two curriculum signatures:
- **Signature 1 (`salary_category(p_salary)` — TP 2 Ex 8 Task 2):** Takes a numeric salary directly so it can be reused inside any `SELECT` expression (`SELECT teacher_id, last_name, first_name, salary, salary_category(salary) AS category FROM teacher ORDER BY teacher_id;`) without duplicating `IF/ELSIF` logic across queries.
- **Signature 2 (`salary_category(p_teacher_id)` — TD 2 Ex 11):** Takes a teacher ID, queries `teacher`, and explicitly handles **non-existent teacher IDs** via `IF NOT FOUND`:
```sql
CREATE OR REPLACE FUNCTION salary_category(p_teacher_id INTEGER)
RETURNS VARCHAR(20)
LANGUAGE plpgsql
AS $$
DECLARE
    v_salary teacher.salary%TYPE;
BEGIN
    SELECT salary INTO v_salary
    FROM teacher
    WHERE teacher_id = p_teacher_id;

    IF NOT FOUND THEN
        RETURN 'Teacher not found'; -- alternative: RAISE EXCEPTION 'Teacher % does not exist.', p_teacher_id;
    ELSIF v_salary IS NULL THEN
        RETURN 'Unknown';
    ELSIF v_salary >= 70000 THEN
        RETURN 'High';
    ELSIF v_salary >= 50000 THEN
        RETURN 'Medium';
    ELSE
        RETURN 'Low';
    END IF;
END;
$$;
```

### D. Calculating a Salary Increase (`calculate_increased_salary` — TD 2 Ex 12)
Formula: $S_{\text{new}} = S_{\text{old}} \times \left(1 + \frac{r}{100}\right)$.
- **NULL salary:** Return `NULL` (an unknown salary remains unknown; never invent a number).
- **Invalid rate:** If `p_rate IS NULL` or `p_rate <= 0` (or exceeds policy caps), raise an exception (`RAISE EXCEPTION`) rather than decreasing salaries or returning silent garbage.
```sql
CREATE OR REPLACE FUNCTION calculate_increased_salary(p_salary NUMERIC, p_rate NUMERIC)
RETURNS NUMERIC(10,2)
LANGUAGE plpgsql
AS $$
BEGIN
    IF p_rate IS NULL OR p_rate <= 0 THEN
        RAISE EXCEPTION 'Invalid increase rate: %. Must be strictly positive.', p_rate;
    END IF;
    IF p_salary IS NULL THEN
        RETURN NULL;
    END IF;
    RETURN ROUND(p_salary * (1 + p_rate / 100.0), 2);
END;
$$;
```

## 3. Worked Stored Procedures (Ch 2 Slides 40–42, TP 2 Ex 9 & 12, TD 2 Ex 13–15)

### A. Department Salary Increase (`increase_salaries` / `increase_department_salaries` — Ch 2 Slide 42, TP 2 Ex 9, TD 2 Ex 13)
```sql
-- TP 2 Ex 9 / TD 2 Ex 13 (validated PostgreSQL procedure)
CREATE OR REPLACE PROCEDURE increase_department_salaries(
    p_department_id INTEGER,
    p_rate NUMERIC
)
LANGUAGE plpgsql
AS $$
BEGIN
    IF p_rate IS NULL OR p_rate <= 0 OR p_rate > 20 THEN
        RAISE EXCEPTION 'Rate must be greater than 0 and at most 20 percent.';
    END IF;

    IF NOT EXISTS (SELECT 1 FROM department WHERE department_id = p_department_id) THEN
        RAISE EXCEPTION 'Department % does not exist.', p_department_id;
    END IF;

    UPDATE teacher
    SET salary = salary * (1 + p_rate / 100.0)
    WHERE department_id = p_department_id
      AND salary IS NOT NULL;

    RAISE NOTICE 'Salary increase applied to department %.', p_department_id;
END;
$$;
```
**Key rules tested in TP 2 Ex 9 & Ex 12 (Task 7):**
- Invoke via **`CALL increase_department_salaries(1, 5);`** (not `SELECT`).
- Calling with `p_rate = 25` raises an exception (`> 20`).
- Calling with `p_department_id = 5` (Chimie, 0 teachers) succeeds with 0 rows modified.
- `AND salary IS NOT NULL` ensures teachers with `NULL` salaries (like 109) stay `NULL` rather than entering arithmetic.
- Always test inside `BEGIN; CALL increase_department_salaries(1, 5); SELECT ...; ROLLBACK;` so original TP 1 salaries are preserved!

### B. Safely Increasing One Teacher's Salary (`increase_teacher_salary` — TD 2 Ex 14*)
Checks all 3 preconditions before performing the `UPDATE`:
```sql
CREATE OR REPLACE PROCEDURE increase_teacher_salary(p_teacher_id INTEGER, p_rate NUMERIC)
LANGUAGE plpgsql
AS $$
DECLARE
    v_salary teacher.salary%TYPE;
BEGIN
    IF p_rate IS NULL OR p_rate <= 0 THEN
        RAISE EXCEPTION 'Increase rate must be positive.';
    END IF;

    SELECT salary INTO v_salary FROM teacher WHERE teacher_id = p_teacher_id;
    IF NOT FOUND THEN
        RAISE EXCEPTION 'Teacher % does not exist.', p_teacher_id;
    END IF;
    IF v_salary IS NULL THEN
        RAISE EXCEPTION 'Teacher % has a NULL salary and cannot be increased.', p_teacher_id;
    END IF;

    UPDATE teacher
    SET salary = salary * (1 + p_rate / 100.0)
    WHERE teacher_id = p_teacher_id;
END;
$$;
```

### C. Conditional Department Raises Using `CASE` (TD 2 Ex 15)
Rates: Informatique `5%`, Mathématiques `7%`, Électronique `6%`, Physique `4%`, Chimie `3%`.
- **Department with 0 teachers (Chimie):** Zero rows join in `teacher`, so 0 rows update cleanly without error.
- **Department not covered by rules:** Always include **`ELSE 0`** (or raise an explicit error / check) inside `CASE`—**if you omit `ELSE`**, an uncovered department makes `CASE` return `NULL`, turning `salary * (1 + NULL / 100.0)` into `NULL` and wiping out the teacher's salary!
```sql
CREATE OR REPLACE PROCEDURE apply_department_raises_case()
LANGUAGE plpgsql
AS $$
BEGIN
    UPDATE teacher t
    SET salary = salary * (1 + (
        CASE d.department_name
            WHEN 'Informatique' THEN 5
            WHEN 'Mathématiques' THEN 7
            WHEN 'Électronique' THEN 6
            WHEN 'Physique' THEN 4
            WHEN 'Chimie' THEN 3
            ELSE 0
        END
    ) / 100.0)
    FROM department d
    WHERE t.department_id = d.department_id
      AND t.salary IS NOT NULL;
END;
$$;
```

### Persistence & Cleanup Rules (TP 2 Part IV Q18 & Q19)
- **Stored permanently in DB catalog:** Views, materialized views, stored functions, stored procedures, audit tables (`salary_history`), triggers, and `manager` table. Anonymous `DO $$` blocks execute once and are **not** stored.
- **Why roll back / restore test updates?** To preserve the baseline TP 1 data assumptions (e.g., `teacher 101 = 75000`, `teacher 109 = NULL`, `student 8 = NULL`) so subsequent exercises and percentage increases remain accurate and repeatable.

## 4. Dynamic SQL & SQL Injection Defense (From `05 PLSQL`)

Static SQL validates table/column names at compile time. **Dynamic SQL** builds SQL strings at runtime (e.g., when a table name is passed as a parameter):
- **MySQL:** `PREPARE stmt FROM @sql; EXECUTE stmt USING @param; DEALLOCATE PREPARE stmt;`
- **Oracle:** `EXECUTE IMMEDIATE 'UPDATE emp SET salary = :1 WHERE id = :2' USING v_sal, v_id;`
- **PostgreSQL PL/pgSQL:** `EXECUTE 'DELETE FROM ' || quote_ident(p_table) || ' WHERE id = $1' USING p_id;`
> [!WARNING] SQL Injection Prevention
> Never concatenate user values directly into dynamic SQL (`'WHERE user = ''' || input || ''''`). Always pass values via **bind variables** (`?`, `:1`, `$1` + `USING`) and sanitize dynamic object identifiers (like table names via `quote_ident()` in PostgreSQL).

## 5. Legacy Airline TD 4 Worked Routines (Preserved from `05 PLSQL`)

### 1. `EffectifsHeure(pcomp, pheuresVol)` — Scalar Function
Counts pilots exceeding `pheuresVol` in `pcomp` (or across all companies if `pcomp IS NULL`):
```sql
DELIMITER $$
CREATE FUNCTION EffectifsHeure(pcomp VARCHAR(4), pheuresVol DECIMAL(7,2))
RETURNS SMALLINT
DETERMINISTIC READS SQL DATA
BEGIN
    DECLARE v_resultat SMALLINT DEFAULT 0;
    IF pcomp IS NULL THEN
        SELECT COUNT(*) INTO v_resultat FROM Pilote WHERE nbHVol > pheuresVol;
    ELSE
        SELECT COUNT(*) INTO v_resultat FROM Pilote WHERE nbHVol > pheuresVol AND comp = pcomp;
    END IF;
    RETURN v_resultat;
END $$
DELIMITER ;
```

### 2. `PlusExperimente(INOUT pcomp, OUT pnom, OUT pheuresVol)` — `INOUT` / `OUT` Procedure
If `pcomp IS NOT NULL`, finds the top pilot in that company; if `pcomp IS NULL`, finds the top pilot globally and writes their company code back into `INOUT pcomp`:
```sql
DELIMITER $$
CREATE PROCEDURE PlusExperimente(
    INOUT pcomp VARCHAR(4),
    OUT pnom VARCHAR(15),
    OUT pheuresVol DECIMAL(7,2)
)
BEGIN
    IF pcomp IS NOT NULL THEN
        SELECT nom, nbHVol INTO pnom, pheuresVol
        FROM Pilote WHERE comp = pcomp ORDER BY nbHVol DESC LIMIT 1;
    ELSE
        SELECT nom, nbHVol, comp INTO pnom, pheuresVol, pcomp
        FROM Pilote ORDER BY nbHVol DESC LIMIT 1;
    END IF;
END $$
DELIMITER ;
-- Usage: SET @c = NULL; CALL PlusExperimente(@c, @name, @hrs); SELECT @c, @name, @hrs;
```

### 3. Recursive `factorielle(n)` & Recursion Safeguards
$$n! = \begin{cases} 1 & n \le 1 \\ n \times (n-1)! & n > 1 \end{cases}$$
- Trace for `factorielle(4)`: `4 * factorielle(3)` $\to$ `3 * factorielle(2)` $\to$ `2 * factorielle(1)` $\to$ base case `1` $\to$ unwinds `2 -> 6 -> 24`.
- **MySQL limitation:** Recursive *functions* trigger **`Error 1424: Recursive stored functions and triggers are not allowed`**. Recursive *procedures* require raising `SET max_sp_recursion_depth = 255;`. Prefer iterative loops (`WHILE`/`LOOP`) in production to avoid stack memory overhead.

# Recursive Queries (`WITH RECURSIVE`)

This note integrates **Chapter 2 (Slides 77–103)**, **TP 2 (Exercise 11 & Part IV Q17)**, **TD 2 (Exercise 5)**, **TP 3 (Part II Exercises 8–14 & Part III Exercise 16)**, and **TD 3 (Part II Exercises 7*–9)**.

---

## 1. Motivation & Self-Referencing Hierarchies (Ch 2 Slides 77–89)

Hierarchical structures appear everywhere with an **unknown or variable number of levels**:
1. **Company/Organizational charts** (CEO $\to$ Managers $\to$ Team Leads $\to$ Employees).
2. **Folders and directories** (`/` $\to$ `Users` $\to$ `keith` $\to$ subfolders).
3. **E-commerce categories & subcategories** (Category $\to$ Sub-category $\to$ Products).
4. **University management hierarchies** (Board $\to$ Rector $\to$ Pro-Rectors $\to$ Faculties $\to$ Departments).

### Critical Structural Distinction (Ch 2 Slide 83)
- `department` $\to$ `class` $\to$ `student` is **NOT recursive** because it connects **different types of entities** across fixed tables.
- **`manager(manager_id, name, supervisor_id REFERENCES manager(manager_id))`** **IS recursive** because rows of the **same table** reference other rows in that **same table** via a **self-referencing foreign key** (`node_id, parent_id`).
- A single self-join (`FROM manager m LEFT JOIN manager s ON m.supervisor_id = s.manager_id`, Ch 2 Slides 90–91) retrieves **only one level** (the immediate supervisor). Without recursion, traversing arbitrary depth is impossible in standard SQL.

---

## 2. `WITH RECURSIVE` Mechanics, `UNION ALL`, and Termination

```sql
WITH RECURSIVE cte_name AS (
    -- 1. Anchor member: starting row(s) -> T0
    SELECT ...
    FROM source_table
    WHERE root_condition

    UNION ALL

    -- 2. Recursive member: references cte_name -> T1, T2, ...
    SELECT ...
    FROM source_table AS s
    JOIN cte_name AS c ON s.parent_id = c.id
)
SELECT * FROM cte_name;
```

### Key Elements (TP 2 Part IV Q17 & Ch 2 Slides 92, 100, 103)
- **Anchor Member:** Non-recursive base query executed **once** to seed the initial working table $T_0$ (e.g., `WHERE supervisor_id IS NULL` or `WHERE manager_id = 1`).
- **Recursive Member:** Repeatedly joins the source table against **the rows produced by the immediately preceding step** ($T_{i-1} \to T_i$), incrementing `level + 1`.
- **`UNION ALL` vs. `UNION`:** `UNION ALL` combines $T_0, T_1, T_2, \dots$ **without removing duplicates**, which is standard and faster for trees because each depth level contributes new rows. (`UNION` deduplicates rows.)
- **Termination & Cycle Risk (TP 2 Ex 11):** Recursion terminates automatically when an iteration produces **0 new rows** ($T_k = \emptyset$) or a predicate stops matching. **If the data contains a cycle** (A reports to B and B reports to A), `UNION ALL` enters **infinite recursion** unless cycle prevention (e.g., tracking visited IDs in an array `NOT (m.manager_id = ANY(visited_path))` or PostgreSQL `CYCLE` clause) is used!

Extending `department(department_id, department_name, parent_department_id)` where `parent_department_id` references `department_id`:
```sql
WITH RECURSIVE dept_hierarchy AS (
    -- Anchor: start at department 1
    SELECT department_id, department_name, parent_department_id, 0 AS level
    FROM department
    WHERE department_id = 1
    UNION ALL
    -- Recursive: find direct subdepartments of already discovered departments
    SELECT d.department_id, d.department_name, d.parent_department_id, dh.level + 1

```

### TD 2 Ex 5 & TD 3 Ex 8: Generating Integers 1 to 10 (+ Recursive CTE vs. Loop)
```sql
WITH RECURSIVE numbers(n) AS (
    SELECT 1          -- Anchor member: initial value 1
    UNION ALL
    SELECT n + 1      -- Recursive member: increments previous row
    FROM numbers
    WHERE n < 10      -- Termination condition: stops generating once n reaches 10
)
SELECT n FROM numbers;
```
- **Recursive CTE vs. Procedural Loop (TD 2 Ex 5.4):** A **recursive CTE** is a **declarative SQL query** producing a relation/result set directly inside `SELECT` (no mutable variables or procedural statements), whereas a **procedural loop** (`FOR`, `WHILE`, `LOOP`) is an **imperative control flow** construct inside SQL/PSM or PL/pgSQL used to execute step-by-step instructions, side effects, or DML.

### TD 3 Ex 9: Tracing Recursive Iterations (`WHERE n < 5`)
```sql
WITH RECURSIVE numbers(n) AS (
    SELECT 1
    UNION ALL
    SELECT n + 1
    FROM numbers
    WHERE n < 5
)
SELECT n FROM numbers;
```
1. **Result:** **`1, 2, 3, 4, 5`** (5 rows!).
2. **Anchor query:** `SELECT 1` (produces `{1}`).
3. **Recursive query:** `SELECT n + 1 FROM numbers WHERE n < 5`.
4. **Iterations:**
   - Iter 1 reads `1` (`1 < 5` true) $\to$ outputs `2`.
   - Iter 2 reads `2` (`2 < 5` true) $\to$ outputs `3`.
   - Iter 3 reads `3` (`3 < 5` true) $\to$ outputs `4`.
   - Iter 4 reads `4` (`4 < 5` true) $\to$ outputs **`5`**.
5. **Why recursion stops:** In Iteration 5, the working row is `5`. Since `5 < 5` is **false**, the recursive query produces **0 rows**, terminating recursion! *(Exam trap: `WHERE n < 5` stops at **5**, not 4, because `4 < 5` generates `4 + 1 = 5`!)*

# Standard Views, Updatability & Materialized Views

This note integrates **Chapter 2 Part I (Slides 4–15)**, **TP 2 (Exercises 1–3, Ex 12 Task 4, Part IV Q10–11)**, **TD 2 (Exercises 1* & 2*)**, and access-control / simplification patterns from the course (`GRANT`/`REVOKE`, "Max of Sums", and Relational Division views).

---

## 1. Standard Views (Virtual Relations)

A **standard view** is a **virtual relation defined from a named SQL `SELECT` query** stored in the database catalog. Unlike a base table (or a materialized view), a standard view **does not store a physical copy of its rows**. Whenever you query the view, the DBMS runs its defining `SELECT` query in real time against the current state of the underlying base tables.

### Five Core Purposes of Views (Ch 2 Slide 6)
1. **Hide certain columns / Confidentiality:** For example, an academic coordinator needs to consult teachers without seeing their `salary` (Ch 2 Slide 5).
2. **Simplify queries:** Encapsulate repeated multi-table joins (`teacher_department_view`) or nested aggregates behind a single virtual table.
3. **Present data in an appropriate form:** Rename, concatenate, format, or handle `NULL`s (`COALESCE(work_email, personal_email, 'none')`).
4. **Reuse and layer query logic:** Build nested views on top of existing views (TD 2 Ex 1.3).
5. **Provide logical data independence:** If underlying tables are restructured (e.g., splitting `full_name` into `first_name` and `last_name`), updating the view keeps client applications working unchanged.

### General Syntax & Management (TP 2 Part II.1 & Ch 2 Slides 7–10)
```sql
CREATE OR REPLACE VIEW view_name [(alias_col1, alias_col2, ...)] AS
SELECT column1, column2
FROM table_name
WHERE condition;

DROP VIEW view_name;
```
- **`CREATE OR REPLACE VIEW`** updates an existing view definition in place without dropping its `GRANT` permissions (if column types/order stay compatible).
- **`DROP VIEW`** removes **only the view definition** from the data dictionary—never the underlying base-table data.
- **Restriction on `ORDER BY`:** Standard SQL generally forbids `ORDER BY` inside `CREATE VIEW` definitions because a relation is conceptually unordered; apply `ORDER BY` when *querying* the view (`SELECT * FROM teacher_view ORDER BY teacher_id;`).

## 2. Worked View Exercises: Chapter 2, TP 2 (Ex 1) & TD 2 (Ex 1*)

### A. Column-Hiding & Live Reflection (Ch 2 Slide 7 & 10, TP 2 Ex 1 Tasks 1 & 3, TD 2 Ex 1.1)
```sql

SELECT * FROM teacher_public_view WHERE first_name = 'Ahmed';
```
**Key conceptual answers (TP 2 Ex 1 Tasks 1 & 3):**
- *Which columns are hidden?* `salary` (and any column omitted from the view's `SELECT` list).
- *Is `salary` still stored in `teacher`?* Yes—the base table is untouched.
- *Does the view store an independent copy of rows?* No—it stores only the query definition.
- *What happens if a teacher's `first_name` changes in `teacher`?* Subsequent queries against the view show the updated `first_name` immediately.
- *Reversible transaction test (TP 2 Ex 1 Task 3):*
  ```sql
  BEGIN;
  UPDATE teacher SET salary = 80000 WHERE teacher_id = 101;
  SELECT * FROM teacher WHERE teacher_id = 101;       -- shows salary = 80000
  SELECT * FROM teacher_view WHERE teacher_id = 101;  -- columns remain unchanged (no salary column)
  ROLLBACK;
  ```
  Updating `salary` changes the base row, not the view's column schema!

## 3. Views for Access Control (DCL) & Query Simplification (Archived BDA Patterns)

### A. Security Matrix with `GRANT` / `REVOKE`
Views combined with DCL (`GRANT`, `REVOKE`) enforce **column-level**, **row-level**, and **context-aware** security without copying tables:
- **Column-level:** `CREATE VIEW V_Public_Emp AS SELECT Name, Function, Email FROM Employees; GRANT SELECT ON V_Public_Emp TO U1;` (U1 cannot access salaries).
- **Row-level:** `CREATE VIEW CLIENTS_ALGER AS SELECT * FROM CLIENT WHERE Adresse = 'ALGER';`.
- **Context-aware (Oracle legacy example):** `CREATE VIEW V_Secure AS SELECT * FROM T WHERE userenv('TERMINAL') = 'T100';`.
- **Solved Multi-Table Access Matrix:** Given `T1(a1..a5)` and `T2(b1..b3)`:
  - User U1 sees `(a1, a2)` where `COND`: `CREATE VIEW V1 AS SELECT a1, a2 FROM T1 WHERE COND; GRANT SELECT ON V1 TO U1;`
  - User U2 sees `(a4, a5)`: `CREATE VIEW V2 AS SELECT a4, a5 FROM T1; GRANT SELECT ON V2 TO U2;`
  - User U3 needs `(a4, a5, b1, b2)` joined on `a4 = b1`: build `V3` directly on top of `V2` and `T2` (`CREATE VIEW V3 AS SELECT V2.a4, V2.a5, T2.b1, T2.b2 FROM V2, T2 WHERE V2.a4 = T2.b1; GRANT SELECT ON V3 TO U3;`).

### B. Simplification Patterns: "Max of Sums" & Relational Division
Standard SQL forbids nested aggregates like `MAX(SUM(km))`. Views solve this cleanly in two steps:
1. **"Max of Sums" (`Chef de Service` Mission Mileage):**
   ```sql
   CREATE VIEW R11 AS
   SELECT chef.SRV_Libelle, chef.EMP_Num, chef.EMP_Nom,
          SUM(m.MIS_KlmRetour - m.MIS_KlmDepart) AS NbKil
   FROM chef, MISSION m WHERE chef.EMP_Num = m.EMP_Num
   GROUP BY chef.SRV_Libelle, chef.EMP_Num, chef.EMP_Nom;

   SELECT * FROM R11 WHERE NbKil = (SELECT MAX(NbKil) FROM R11);
   ```
   *(Same pattern for top turnover store last month using view `V21(mag_num, Chiffre_Affaire)`.)*
2. **Relational Division via Intermediate View (`V20`):** Articles sold by ALL shops:
   ```sql
   CREATE VIEW V20 AS SELECT DISTINCT art_num, mag_num FROM VENTES;
   SELECT V.art_num, A.art_nom FROM V20 V, ARTICLES A
   WHERE V.art_num = A.art_num
   GROUP BY V.art_num, A.art_nom
   HAVING COUNT(*) = (SELECT COUNT(*) FROM MAGASINS);
   ```

## 4. Updatable Views & `WITH CHECK OPTION` (Ch 2 Slides 11–12, TP 2 Ex 3, TD 2 Ex 1.4)

### When Is a View Automatically Updatable?
A view allows `INSERT`, `UPDATE`, and `DELETE` through it **only when every row in the view maps 1-to-1 to a single row in one base table**. A view is **NOT automatically updatable** if its query uses:
- `GROUP BY` or `HAVING` (1 virtual row maps to many physical rows).
- Aggregate functions (`SUM`, `AVG`, `COUNT`, `MIN`, `MAX`).
- `DISTINCT` (collapses duplicates, destroying 1-to-1 identity).
- Set operations (`UNION`, `UNION ALL`, `INTERSECT`, `EXCEPT`).
- Multi-table `JOIN`s (generally not automatically updatable in PostgreSQL—to make a join view writable, attach an **`INSTEAD OF` trigger**; see [[01 - Triggers, Automatic Auditing & Constraints vs Triggers]]).

### The Phantom Write Problem & `WITH [LOCAL] CHECK OPTION`
Suppose you create a filtered view without `CHECK OPTION`:
`CREATE VIEW Paris_Employees AS SELECT id, name, city FROM Employees WHERE city = 'Paris';` (or `CREATE VIEW Adults AS SELECT * FROM Users WHERE age > 18;`).
Inserting `(99, 'John', 'London')` through `Paris_Employees` (or `age = 10` through `Adults`) succeeds on the base table, yet John **immediately vanishes** from the view!

Adding **`WITH CHECK OPTION`** (or PostgreSQL's **`WITH LOCAL CHECK OPTION`**) blocks any `INSERT` or `UPDATE` *made through the view* whose resulting row would fail the view's `WHERE` condition:

```sql
-- TP 2 Ex 3 / Ch 2 Slide 11 / TD 2 Ex 1.4
CREATE OR REPLACE VIEW department_1_teachers AS
SELECT teacher_id, last_name, first_name, salary, department_id
FROM teacher
WHERE department_id = 1
WITH LOCAL CHECK OPTION;

-- SUCCEEDS: teacher 101 stays in department 1
UPDATE department_1_teachers SET salary = 79000 WHERE teacher_id = 101;

-- REJECTED ("new row violates check option for view"): moves row outside department_id = 1
UPDATE department_1_teachers SET department_id = 2 WHERE teacher_id = 101;
```

> [!WARNING] What `WITH CHECK OPTION` Does and Does NOT Guarantee (TP 2 Part IV Q11)
> - **Guarantees:** Any `INSERT` or `UPDATE` executed **through the view** must leave the row satisfying the view's `WHERE` condition (`department_id = 1`).
> - **Does NOT guarantee:** It **never blocks** direct `INSERT`/`UPDATE` statements executed on the underlying `teacher` base table (`UPDATE teacher SET department_id = 2 WHERE teacher_id = 101;` succeeds!).
> - **`LOCAL` vs. `CASCADED`:** `WITH LOCAL CHECK OPTION` validates only the current view's `WHERE` condition; `WITH CASCADED CHECK OPTION` (standard default for `WITH CHECK OPTION` in PostgreSQL) also checks conditions of any underlying nested views.
> - **Different from `CHECK` constraint:** A table `CHECK` constraint enforces domain integrity on *all* writes to the table regardless of path; `WITH CHECK OPTION` enforces scope consistency *only* for writes issued through the view.

## 5. Materialized Views (Ch 2 Slides 13–15, TP 2 Ex 2, TD 2 Ex 2*)

A **materialized view** executes its query upon creation and **physically stores the resulting rows on disk**. It is designed for expensive analytical or aggregation reports executed frequently where slightly stale data is acceptable.

```sql
-- TP 2 Ex 2 (mv_department_salary) / TD 2 Ex 2* (department_average_salary)
CREATE MATERIALIZED VIEW department_average_salary AS
SELECT department_id, AVG(salary) AS average_salary
FROM teacher
GROUP BY department_id;

-- Query stored snapshot (fast—no re-aggregation of teacher!)
SELECT * FROM department_average_salary ORDER BY department_id;

-- Observe staleness & manual refresh workflow (TP 2 Ex 2)
UPDATE teacher SET salary = 78000 WHERE teacher_id = 101;
SELECT * FROM department_average_salary ORDER BY department_id; -- STILL shows old average!

REFRESH MATERIALIZED VIEW department_average_salary;
SELECT * FROM department_average_salary ORDER BY department_id; -- Now shows updated average

-- Restore original salary and refresh again so stored snapshot matches restored data
UPDATE teacher SET salary = 75000 WHERE teacher_id = 101;
REFRESH MATERIALIZED VIEW department_average_salary;

-- Drop if starting fresh
DROP MATERIALIZED VIEW department_average_salary;
```
*(Note: Grouping directly on `teacher` omits department 5 `Chimie` because it has 0 rows in `teacher`; join from `department LEFT JOIN teacher` if all departments should be materialized.)*

### Regular View vs. Materialized View Comparison (Ch 2 Slide 15, TP 2 Part IV Q10, TD 2 Ex 2.5–2.6)

| Dimension | Regular (Standard) View | Materialized View |
| :--- | :--- | :--- |
| **Data Storage** | Stores **only the SQL query definition** (logical result; 0 data storage) | **Physically stores query result rows** on disk (can be indexed) |
| **Query Execution** | Re-runs its defining query against base tables on every `SELECT` | Reads precomputed rows directly from disk (very fast for heavy reports) |
| **Result Freshness** | **Always up-to-date** (current data) | **May become outdated/stale** after source tables change |
| **Refresh Required?** | **No `REFRESH` required** | **`REFRESH MATERIALIZED VIEW` required** to recompute stored data |
| **Advantage / Limitation** | Advantage: zero redundancy & always live; Limitation: slow for repeated heavy aggregations | **Advantage (TD 2 Ex 2.6):** Dramatic speedup on expensive salary statistics/reports; **Limitation:** consumes storage and serves stale results until explicitly refreshed |
